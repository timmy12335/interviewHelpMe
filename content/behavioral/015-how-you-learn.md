# 題目

「你平常怎麼學新技術」——怎麼回答才不會變成列出一堆看過的書和課程？

## 核心答案

這題測的不是你學了多少，而是**你有沒有一套可重複的方法，以及你怎麼決定要學什麼**。列清單（看了哪些書、上了哪些課）沒有說服力，因為輸入不等於能力。有效的回答有三個部分：**一、選擇的依據**——你怎麼決定學這個而不是那個（通常是手上的問題需要、或是判斷某個方向的價值），這顯示你有判斷力而不是隨波逐流。**二、學習的路徑**——我的做法是「**先做出一個能動的東西，再回頭補原理**」，因為沒有具體問題時讀原理很難留下來；做出來之後帶著疑問回去看文件，理解會深得多。**三、怎麼驗證真的學會了**——最可靠的檢驗是**能不能講清楚它的取捨**：什麼情況該用、什麼情況不該用、它解決了什麼問題又帶來什麼代價。能講出取捨才叫理解，只會用是熟悉。最好的答案會用**一個具體的例子**貫穿這三點，而不是抽象描述方法論。

## 詳細解析

**從問題出發比從技術出發有效**：因為有真實問題時，你會自然遇到邊界情況、踩到坑、需要查文件，這些都是留得住的學習。反過來，為了「跟上潮流」而學的東西，通常在三個月後就忘光了。所以在面試中講「我當時遇到的問題是 X，評估之後選了 Y 這個方向」比「我最近在學 Y」有力得多。

**官方文件優先於二手教學**：二手教學的價值在於快速上手，但它們常常過期、簡化掉重要的取捨、或反映作者的特定用法。建立習慣是：**用二手資源快速跑通第一個例子，然後立刻回到官方文件**，特別是設計理念、限制、以及「什麼時候不該用它」的章節。很多工具的官方文件都有明確寫出適用邊界，但多數人不看。

**讀原始碼的時機與方法**：不要一開始就讀，那沒有脈絡。有效的時機是**你已經用過、而且遇到了不理解的行為**——帶著具體問題進去，沿著一條呼叫路徑往下追，遠比從入口開始通讀有效。另一個好時機是評估要不要採用某個函式庫時，看它的錯誤處理與測試品質，往往比看 star 數更能判斷可靠性。

**輸出是最有效的檢驗**：寫一篇說明、在團隊分享一次、或回答別人的問題，都會立刻暴露出你以為懂但其實模糊的地方。在面試中提到「我學完之後會在團隊做一次分享」有雙重價值——既顯示你的檢驗機制，也顯示你會把知識擴散給團隊。

**要能講出「不學什麼」**：技術太多，選擇不學同樣是判斷力。合理的過濾原則包括：解決的問題我目前沒有、社群還太小風險高、和現有技術棧差異太大導致遷移成本不划算。能講出你**刻意跳過了什麼以及為什麼**，會比列出學過的東西更能顯示成熟度——它代表你在管理有限的注意力。

## 面試回答方式

不要列書單或課程清單，直接給你的**方法**。第一段講選擇依據——從手上的問題出發，這顯示判斷力。第二段講路徑，明確說出「**先做出能動的東西，再回頭補原理**」並解釋理由。第三段講檢驗方式，主張**能講清楚取捨才叫理解，只會用叫熟悉**。全程用**一個具體例子**貫穿這三點，比抽象描述有說服力。加分點有兩個：一是提到你會回官方文件看「什麼時候不該用」的部分；二是主動講你**刻意不學什麼以及為什麼**，這顯示你在管理有限的注意力而不是追逐每個新東西。

## 講稿

我的學習幾乎都是從手上的問題出發，不是從技術出發。因為有真實問題的時候，我會自然踩到坑、需要查文件，這些才留得住。為了跟上潮流學的東西，三個月後大概就忘了。

路徑上我的順序是先做出一個能動的東西，再回頭補原理。沒有具體問題的時候讀原理很難留下來，但做出來之後帶著疑問回去看文件，理解會深很多。

補原理的時候我會優先看官方文件而不是二手教學。二手的適合快速上手，但常常過期，也會簡化掉重要的取捨。官方文件我特別會去看設計理念跟限制那幾章，很多工具其實有明確寫什麼時候不該用它，只是大部分人不看。

至於怎麼確認我真的學會了，我的標準是能不能講清楚它的取捨。什麼情況該用、什麼情況不該用、它解決了什麼問題又帶來什麼代價。講得出取捨才叫理解，只會用叫熟悉。

我通常也會在團隊分享一次，因為要講給別人聽的時候，那些自己以為懂但其實模糊的地方會馬上暴露出來。

另外我也會刻意決定不學什麼。注意力有限，我會過濾掉目前沒有對應問題、或者社群太小風險高的東西。

## 常見追問

### 講一個你最近學的東西，以及你怎麼判斷該不該用它

**核心答案**：這題要用**具體例子加上取捨判斷**回答，而且判斷的部分比技術本身重要。好的結構是：我遇到什麼問題 → 我評估了哪幾個方向 → 我選了哪個、理由是什麼 → 它帶來什麼新的代價 → 事後回看這個判斷對不對。重點在於**你有沒有評估過替代方案**，只講「我學了 X，它很好用」會被判斷成缺乏批判性。

**詳細解析**：面試官在意的是**你會不會為了用新技術而用新技術**。所以主動說出你考慮過但沒選的方案、以及不選的理由，是很強的信號。同樣有價值的是誠實說出**採用後才發現的代價**——運維複雜度上升、團隊學習曲線、除錯工具不成熟、社群資源少。能講出這些代表你真的在生產環境用過，而不只是跑過教學。如果你最近學的東西還沒有實際採用，那就講你的評估結論以及**你會在什麼條件下採用**，這同樣展現判斷力。

**面試回答方式**：用「問題、評估的選項、選擇與理由、新的代價、事後回看」這個結構講一個具體例子。重點放在你考慮過但沒選的方案以及理由。加分點是誠實說出採用後才發現的代價，那是實際用過才有的觀察。

### 沒有工作上的機會接觸新技術怎麼辦？

**核心答案**：**先在現有工作中找機會，再考慮工作之外**。多數系統裡都有可以改善的地方——把手動流程自動化、為缺乏測試的模組補上測試、給沒有監控的服務加上告警。這些都是真實的問題，而且解決它們的過程中自然會用到新東西。工作之外的專案也有價值，但要注意**選擇有真實使用者或真實資料的專案**，因為玩具專案不會逼你面對可靠性、效能與邊界情況，而那才是能力的分水嶺。

**詳細解析**：這題常見的弱答案是「我在做一個側專案」然後說不出它解決了什麼問題。強一點的版本會說明**規模與限制**——「我做了一個定時抓取資料的工具，每天處理大約十萬筆，過程中我才理解重試與冪等性為什麼重要，因為來源 API 會間歇失敗」。另一條路徑是**參與開源**，即使只是修文件或小 bug，它會讓你經歷完整的協作流程（issue 討論、PR review、CI）。要避免的是把學習講成純消費（追課程、看影片），因為它無法證明能力，只能證明時間投入。

**面試回答方式**：先給「在現有工作中找真實問題」這個主路徑並舉三個例子（自動化、補測試、加監控）。談側專案時強調要有真實使用者或真實資料，並示範怎麼講出規模與限制。加分點是提到參與開源能經歷完整協作流程，以及明確反對把學習講成純消費。

### 你怎麼跟上這個領域的變化？

**核心答案**：**建立有限但穩定的來源，而不是追每一則新聞**。實用的組合是：幾個**官方部落格或發布說明**（掌握你在用的東西的變化，這是最直接相關的）、一到兩個**深度來源**（願意寫取捨與失敗經驗的作者或團隊部落格）、以及**同儕的討論**（團隊分享、社群、實際用過的人的評價）。重點是**穩定與可持續**，一週花一小時持續三年，遠勝過某個月密集追一堆然後放棄。

**詳細解析**：更有價值的一點是**如何過濾**。新技術的資訊多數是行銷或早期熱度，判斷是否值得投入注意力的信號包括：有沒有人在生產環境用了一年以上並寫出踩坑經驗、它解決的問題我現在有沒有、以及維護者的活躍度與治理模式（單一公司主導還是有基金會）。另一個實用的做法是**刻意延遲**——讓新東西先跑一兩年，等社群把坑踩完再評估，除非你有明確的需求非它不可。在面試中講出這種節制，通常比表現得什麼都知道更能贏得信任，因為它顯示你會為團隊的長期成本負責。

**面試回答方式**：給出有限而穩定的來源組合，並強調可持續比密度重要。重點放在過濾標準：有沒有生產環境的長期經驗分享、我現在有沒有對應的問題、維護者的治理模式。加分點是主動講「刻意延遲」這個策略，展現你會為團隊長期成本負責。
