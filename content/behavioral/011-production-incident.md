# 題目

「講一次你處理線上事故的經驗」——面試官想確認什麼？

## 核心答案

他們要確認的是**你在壓力下有沒有章法**，而不是你技術多強。事故處理的正確順序是**止血、通報、定位、修復、覆盤**，而多數人的直覺會直接跳到定位——想搞清楚為什麼壞掉。這是錯的：**先讓損失停止**（回滾、關閉功能開關、切流量、降級），再慢慢查原因。第二個關鍵是**通報要早**：在你還不知道原因的時候就該同步「目前有這個現象、影響範圍大概是這樣、我正在處理、下次更新在十五分鐘後」。等到查清楚才通報，會讓客服、業務、主管在最需要資訊的時候什麼都不知道。第三個關鍵是**覆盤要對事不對人**——寫下時間軸、根因、以及為什麼現有的機制沒有更早發現，並產出可執行的行動項。能講出「這次事故讓我們補上了什麼監控或流程」，比講「我很快就修好了」有價值得多。

## 詳細解析

止血優先於找原因，因為兩者的時間尺度不同：找根因可能要幾小時，止血通常幾分鐘就能做到。如果最近有部署，先回滾——即使你不確定是不是它造成的，回滾的成本遠低於繼續流血。如果有功能開關就關掉，如果是某個下游拖垮系統就先降級或熔斷。**先恢復服務，再做事後調查**是所有成熟團隊的共識。

**通報的內容要有結構**：好的事故通報包含四項——**現象**（使用者看到什麼）、**影響範圍**（多少人、哪些功能、從什麼時候開始）、**目前狀態**（正在調查、已止血、已修復）、**下次更新時間**。最後一項最常被忽略但最重要，它讓其他人不必反覆來問。影響範圍不確定時就說不確定，並給一個上界估計，不要為了好看而低報——低報後修正的信任損失遠大於一開始就說不確定。

**定位要用二分法而不是靠猜**：有效的做法是先問「**什麼時候開始的**」，然後對照那個時間點前後發生了什麼——部署、設定變更、流量變化、上游或下游的異動。多數事故有明確的觸發點，找到時間點通常就找到了範圍。同時要善用可以快速排除的假設：是所有使用者還是部分？所有機器還是特定機器？所有 API 還是特定端點？每個問題都能砍掉一半的可能性。

覆盤的核心問題不是「誰做錯了」而是「為什麼系統允許這件事發生」：一個工程師改錯設定造成事故，真正的問題是為什麼沒有審查、為什麼沒有驗證、為什麼沒有在造成大範圍影響前被監控抓到。**無指責文化**不是不追究，而是把追究的對象從人換成機制——因為在指責文化下，下一次事故會被隱瞞，那才是最危險的。

**行動項要有負責人與期限**：覆盤報告裡寫「我們應該加強監控」等於沒寫。有效的行動項是「在下週前為訂單服務的失敗率加上告警，門檻設為 1%，由某某負責」。而且行動項數量要克制——列二十項通常一項都不會做，列三項最重要的反而會完成。

## 面試回答方式

先把順序講出來——止血、通報、定位、修復、覆盤，並明確說明**止血優先於找原因**，因為多數人的直覺會反過來。通報那一段要具體：講出你會同步哪四項資訊，特別是「下次更新時間」這一項。定位講方法而不是講技術——先確認開始時間、對照那個時間點的變更、用二分法排除可能性。覆盤是最能加分的一段，把重點放在「為什麼系統允許這件事發生」而不是誰做錯，並說明行動項要有負責人與期限、數量要克制。整段講完，面試官應該覺得你處理過而不是讀過。

## 講稿

我的順序是止血、通報、定位、修復，最後覆盤。這個順序我想特別說明，因為大部分人的直覺會直接跳到定位，想先搞清楚為什麼壞掉。

但止血跟找原因的時間尺度差很多。找根因可能要好幾個小時，止血通常幾分鐘就能做。如果剛剛有部署，我會先回滾，就算不確定是不是它造成的也回，因為回滾的成本遠低於繼續流血。有功能開關就先關掉，是下游拖垮的就先降級。

通報我會很早就做，不會等查清楚。我同步四件事，現象是什麼、影響範圍大概多大、我現在在做什麼、下次更新在什麼時候。最後那一項最容易被忽略，但它讓其他人不用一直來問。影響範圍不確定我就說不確定，給一個上界，不會為了好看低報。

定位我用二分法。先問什麼時候開始的，然後對照那個時間點前後發生什麼，部署、設定變更、流量變化。再用幾個問題砍範圍，是全部使用者還是部分、全部機器還是特定機器。

覆盤我問的不是誰做錯，是為什麼系統允許這件事發生。行動項一定要有負責人跟期限，而且不要列二十項，列三項最重要的才會真的完成。

## 常見追問

### 事故當下你發現是自己造成的，會怎麼處理？

**核心答案**：立刻說出來，而且是在止血的同時說。知道原因的人隱瞞會讓其他人浪費大量時間往錯的方向查，這個代價遠大於承認的尷尬。正確的做法是「我剛剛部署了 X，時間點吻合，我先回滾」——這句話同時提供了關鍵資訊與行動。事後在覆盤中誠實記錄，並把重點放在「為什麼這個錯誤能通過現有的檢查」。

**詳細解析**：這題實質在測**誠信與心理安全感**。面試官想知道你會不會為了保護自己而讓團隊付出代價。值得主動補充的是你怎麼看待這件事對團隊文化的影響——如果一個團隊裡承認錯誤會被懲罰，那所有人都會傾向隱瞞，事故的平均修復時間就會拉長。所以帶頭承認本身就是在建立更好的文化。另一個細節是**區分當下與事後**：事故當下不是檢討的時機，先把服務救回來，情緒與責任的討論留到覆盤。急著在事故當下道歉或自責反而會拖慢處理。

**面試回答方式**：明確說會立刻說出來，並強調是在止血的同時而不是之後。給出具體說法（我剛部署了 X，時間點吻合，我先回滾）。加分點是講出這對團隊文化的影響——隱瞞文化會拉長平均修復時間，以及事故當下不是檢討的時機。

### 如果你不是值班的人，但發現了問題呢？

**核心答案**：先通報，再判斷要不要自己動手。發現問題的人有責任讓它被知道，但不一定該直接介入——尤其在不熟悉的系統上，好意的操作可能讓情況更糟。合適的做法是通知值班人員與相關負責人，說明你觀察到什麼、以及你的證據，然後主動說「我可以幫忙做 X，需要的話跟我說」。如果聯絡不上而影響持續擴大，那就依照團隊的升級規則往上找，而不是自己硬上。

**詳細解析**：這題在測**主動性與邊界感的平衡**。只顧自己的工作範圍、看到問題不出聲是消極；不了解狀況就跳進去改東西是魯莽。中間的正確位置是「確保資訊流動、提供協助、尊重負責人的決策」。實務上還有一個常見情境：你發現的問題被負責人判斷為不重要。這時的處理方式是把觀察與風險寫下來、留下紀錄，而不是反覆爭論或私下處理——如果後來真的出事，紀錄能幫助覆盤；如果沒出事，你也沒有浪費團隊的時間。

**面試回答方式**：核心是先通報再判斷是否介入，並說明不熟悉的系統上好意操作可能更糟。給出具體的協助說法。加分點是處理「負責人認為不重要」這個延伸情境——留下紀錄而不是反覆爭論或私下處理。

### 覆盤報告要寫給誰看？要寫多細？

**核心答案**：**主要讀者是未來的自己人**——半年後遇到類似問題的工程師、以及需要判斷要不要投入資源改善的主管。所以核心內容是時間軸、影響範圍、根因、以及為什麼沒有更早發現，加上三到五個有負責人與期限的行動項。技術細節要足夠讓別人能重現與理解，但不需要貼滿日誌；真正的細節可以連結到相關的票或討論串。

**詳細解析**：一份好的覆盤報告有兩個容易被忽略的部分。一是**「哪些做對了」**——如果告警在三分鐘內就響了、如果回滾很順利，這些要記錄下來，因為它們是值得保留的機制。只寫壞的部分會讓報告變成檢討大會。二是時間軸要包含「什麼時候知道什麼」，而不只是「什麼時候發生什麼」——這能揭露資訊落差在哪裡，例如「事故在 10:05 開始，但我們在 10:40 才知道」就直接指出監控不足。至於篇幅，一頁到兩頁通常最有效，太長的報告沒有人會讀，而沒有人讀的報告等於沒寫。

**面試回答方式**：先界定讀者（未來遇到類似問題的人、要決定投資源的主管），再給核心內容清單。強調兩個常被忽略的部分：記錄哪些做對了、以及時間軸要含「什麼時候知道什麼」。加分點是講篇幅的實用判準——太長沒人讀，等於沒寫。
