# 題目

你做的技術選型被主管或同事質疑「為什麼不用更簡單的做法」，你會怎麼回應？

## 核心答案

第一個動作應該是**確認質疑的內容**，而不是辯護。多數質疑背後有一個具體的擔憂——成本、風險、學習曲線、維護人力——把它問出來，才知道要回應什麼。第二個動作是**回到決策當時的依據**：你考慮過哪些選項、用什麼標準比較、為什麼選了這個。如果你當時就有寫下取捨（哪怕只是一段設計文件或 PR 描述），這時候會非常有價值。第三個動作是誠實區分「我當時的判斷」和「現在看來的判斷」——如果新的資訊顯示對方是對的，直接承認並提出調整方案，這比堅持立場加分得多。最重要的心態是：**質疑技術決策不是質疑你**。能把討論保持在方案層面、不進入自我防衛，是資深工程師最明顯的特徵之一，也是這題真正在評的東西。

## 詳細解析

「為什麼不用更簡單的做法」通常是合理的質疑：工程上簡單幾乎永遠是預設值，複雜度需要理由。所以被這樣問的時候，正確的反應不是覺得被冒犯，而是檢查自己是否真的有充分理由。常見的糟糕理由包括：為了學新技術、因為別的公司這樣做、因為未來可能需要。常見的好理由包括：現有方案已經量測到具體的瓶頸、有明確的合規或可靠性要求、簡單方案的維護成本已經超過遷移成本。能區分這兩類理由本身就是判斷力的展現。

用資料回應比用論點回應有效：「我覺得會有效能問題」是意見，「我壓測過，簡單版本在每秒三千筆的時候延遲會跳到 2 秒，而我們的尖峰是四千筆」是證據。如果來不及量測，至少給出**可以驗證的預測**：「如果照這個做法，我預期在資料量到一百萬筆的時候會出現這個問題，我們可以先跑一個壓測確認」。把爭論轉成可驗證的形式，是最快收斂的方法。

「當初的決定」和「現在的最佳選擇」要分開講：時間會帶來新資訊，一年前合理的決定現在看起來可能是錯的，這不代表當初的判斷有問題。分開講的好處是你既能維護自己的專業判斷，又能接受現況需要改變——「當時我們只有兩個人維護，選這個方案是為了降低運維負擔，這個判斷在當時是對的。現在團隊到八個人、流量也翻了三倍，我同意該重新評估了。」

**要有承認錯誤的具體版本**：如果對方是對的，最好的回應是**明確承認加上具體的下一步**：「你說得對，我當時沒有把備份還原的複雜度算進去。我想我們可以先評估遷移成本，如果在兩週以內我建議現在就改。」承認得乾脆，比含糊地說「這個我再想想」有力，也讓討論可以繼續往前。

留下決策紀錄是這題的長期解：把「考慮過哪些方案、為什麼選這個、什麼情況下該重新評估」寫進設計文件或架構決策紀錄，讓每次質疑都能回到當時的脈絡，而不是憑記憶爭論。這個習慣值得在面試中主動提出——它顯示你思考的是團隊層級的問題，而不只是怎麼贏一次辯論。

## 面試回答方式

第一句話就把姿態定調——質疑技術決策不是質疑我，所以我第一個動作是把對方的具體擔憂問清楚，而不是辯護。接著說明你會回到決策當時的依據：考慮過哪些選項、標準是什麼。強調用**資料或可驗證的預測**回應，而不是用意見對意見。主動區分「當時的判斷」與「現在的最佳選擇」，展現你能同時維護專業判斷與接受改變。如果對方是對的，示範一個乾脆承認加上具體下一步的說法。加分點是提到你會把決策依據寫成文件，讓下一次的討論有脈絡可回。

## 講稿

我第一個動作不是辯護，是把質疑聽清楚。有人問為什麼不用更簡單的做法，背後通常有具體的擔憂，可能是維護人力、可能是風險、可能是他不熟這個技術。不問出來我就不知道要回應什麼。

而且說實話，這個質疑通常是合理的。工程上簡單應該是預設值，複雜要有理由。所以被問的時候我會先檢查自己的理由夠不夠好。為了學新技術、因為別人這樣做、因為未來可能需要，這些都不算好理由。

如果我的理由站得住，我會盡量用資料講而不是用意見講。我覺得會有效能問題，這是意見。我壓測過簡單版本在每秒三千筆的時候延遲會跳到兩秒，而我們尖峰是四千，這才是證據。來不及量的話，我至少會給一個可以驗證的預測，然後提議先跑一次壓測。

如果對方是對的，我會直接承認然後給下一步。像是你說得對，我當時沒把備份還原的複雜度算進去，我建議先評估遷移成本，兩週以內的話現在就改。

我也會把這些取捨寫進設計文件，下次討論就有脈絡可以回。

## 常見追問

### 如果你當初的決策確實錯了，而且已經造成成本了呢？

**核心答案**：承認、量化影響、提出止損方案，三件事一次做完。含糊帶過或強調「當時資訊不足」會讓人覺得你在推責。好的處理是：「這個選型確實是錯的，目前造成的額外成本大約是每月多兩台機器加上每次部署多二十分鐘。我評估過三個方向，最務實的是先把最耗資源的那一塊搬走，兩週可以完成，剩下的部分維持現狀。」重點在**你提出的是行動而不是解釋**。

**詳細解析**：在面試中回答這題，關鍵是展現**沉沒成本不會綁架你的判斷**。很多人在錯誤的技術決策上繼續投入，是因為承認錯誤的心理成本太高——能明確講出「我當時錯了，我建議停損」的人在組織裡很有價值。同時要注意**不要過度修正**：不是每個錯誤決策都值得推倒重來，如果遷移成本高於繼續維護的成本，最理性的選擇是承認錯誤但維持現狀，並記錄下來避免重複。能講出這種**分情況的判斷**，比一味強調勇於承認錯誤更成熟。

**面試回答方式**：給出三段式處理（承認、量化影響、提出止損），強調重點是提出行動而非解釋。點出核心信號是沉沒成本不綁架判斷。加分點是補充「不是每個錯誤都值得推倒重來」，展現分情況的成本判斷。

### 面試官在白板題中途說「這樣不對」，你會怎麼處理？

**核心答案**：先確認他指的是哪一部分，再用具體例子驗證。回應是「你是說這個邊界條件的部分，還是整體方向？讓我用一個兩個元素的例子走一遍」——這既澄清了範圍，又用實例檢驗而不是空口爭論。如果驗證後發現真的錯了，明確說「你是對的，這裡少處理了長度為 1 的情況」然後修正；如果沒錯，用例子說明你的推論，語氣是討論而非防衛。

**詳細解析**：這個情境有時是面試官**真的看到錯誤**，有時是在**測試你會不會被輕易動搖**。用具體例子驗證同時應付兩種情況，所以是最安全的反應。要避免的兩個極端是：一聽到質疑就把程式碼整段改掉（顯示你對自己的推理沒有信心，而且常常引入新錯誤），以及堅持自己沒錯卻拿不出驗證（顯示固執）。另外整個過程的**語氣**很重要——這題實質上是在模擬工作中被同事質疑的場景，你的反應方式就是他們預期你入職後的反應方式。

**面試回答方式**：給出標準動作——先確認範圍、再用具體例子驗證，並說明這同時應付「真的錯了」與「在測你會不會動搖」兩種情況。點出兩個要避免的極端。加分點是指出這題實質是在模擬工作場景，語氣本身就是被評估的內容。

### 怎麼判斷一個技術方案的複雜度是不是「值得」？

**核心答案**：問三個問題。一、現在有沒有實際量測到的問題——如果沒有，複雜度是在為想像中的需求付費。二、簡單方案失效時的遷移成本有多高——如果將來要換的成本不高，就先簡單做；如果換的成本極高（例如資料模型一旦定型難以更動），就值得先想清楚。**三、團隊有沒有能力維護**——一個沒人懂的精巧方案，長期成本遠高於一個大家都會的笨方案。

**詳細解析**：這三個問題實際上對應到「YAGNI」「可逆性」「巴士因子」三個原則。其中**可逆性**是最實用的判準：可逆的決定應該快速做、錯了再改；不可逆的決定值得多花時間評估。資料庫選型、資料模型、對外 API 契約通常是不可逆的；框架、內部模組劃分、部署方式通常是可逆的。用這個分類可以避免兩種常見錯誤：在可逆的小事上過度設計，以及在不可逆的大事上草率決定。面試中能講出這個分類，會顯示你的判斷有框架而不是憑感覺。

**面試回答方式**：給出三個判斷問題（有沒有實測問題、遷移成本多高、團隊能不能維護），並對應到 YAGNI、可逆性、巴士因子三個原則。重點放在可逆性這個最實用的判準，並舉出哪些決定可逆、哪些不可逆。加分點是指出它同時避免了過度設計與草率決定兩種相反的錯誤。
