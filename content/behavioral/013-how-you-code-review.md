# 題目

你在 review 別人的 PR 時，會看什麼、怎麼給意見？

## 核心答案

我的檢查順序是**由大到小**：先看**這個改動要解決什麼問題、方向對不對**（方向錯的話，行內的細節意見全是浪費）、再看**介面與資料模型**（這兩者最難事後改）、然後是**正確性與邊界情況**（空值、併發、失敗路徑、冪等性）、最後才是**可讀性與命名**。給意見的原則是**區分嚴重程度**——用明確的標記分開「這個必須改」「這個建議改」「這只是我的偏好，你可以不理」，因為把偏好和缺陷混在一起講，會讓對方無法判斷輕重，也容易讓 review 變成品味之爭。第三個原則是**對事不對人、並且說明理由**：「這裡如果請求重送會產生兩筆訂單，建議加上冪等鍵」比「這樣寫不對」有用得多。最後，**看到寫得好的地方要說出來**——review 不只是找問題，明確肯定一個好的設計會讓對方知道什麼是團隊認可的方向。

## 詳細解析

**先看描述再看程式碼**：如果 PR 的描述沒有說清楚要解決什麼問題、怎麼驗證，第一個意見就該是請對方補上，而不是硬著頭皮猜。一個沒有脈絡的 review 幾乎必然變成只挑格式問題。反過來，作為提交者，**寫好 PR 描述是最能提升 review 品質的投資**。

**大 PR 是 review 品質的頭號殺手**：超過幾百行的改動，人的注意力會顯著下降，通過率反而變高——因為看不完就只好相信。合理的做法是在收到大 PR 時請對方拆分，並說明理由。如果實在無法拆（例如大規模重新命名），就明確約定 review 的重點放在哪幾個檔案，其餘的信任自動化檢查。

**能自動化的不要靠人**：格式、命名慣例、import 排序、明顯的靜態問題應該交給 formatter 與 linter，在 CI 就擋掉。人的 review 應該用在機器看不出來的東西——設計是否合理、抽象是否恰當、有沒有漏掉的業務情境、錯誤處理是否完整。如果你的 review 意見有一半是格式問題，那是工具鏈的缺失而不是同事的問題。

**邊界情況是最有價值的檢查點**：具體要問的包括——空集合與 null 會怎樣、失敗時會不會留下半完成的狀態、重試會不會造成重複、併發存取有沒有競態、外部呼叫有沒有逾時、錯誤有沒有被吞掉。這些是最容易漏且事後最貴的問題。經驗豐富的 reviewer 之所以有價值，多半體現在這裡。

**溝通方式決定 review 的長期效果**：用問句而非命令（「這裡如果 list 是空的會怎麼樣？」）能保留對方解釋的空間，也避免你自己誤判時的尷尬。爭論超過兩個來回就改成直接對話——非同步的文字討論在意見分歧時效率極低，而且容易累積情緒。另外**時效性很重要**：一個放了三天的 PR 會讓作者失去上下文、也拖慢整個團隊，即使只能先給部分意見也比讓它躺著好。

## 面試回答方式

先給你的**檢查順序**（方向、介面與資料模型、正確性與邊界、可讀性），並解釋為什麼由大到小——方向錯的話細節意見都是浪費。接著講意見的**嚴重程度標記**，說明混在一起會讓對方無法判斷輕重。第三點強調**說明理由**並舉一個具體例子（冪等鍵那種）。主動提出兩個工程觀點：能自動化的交給工具、大 PR 要請對方拆分。邊界情況那一段要具體列幾項（空值、失敗後的半完成狀態、重試重複、逾時），這是最能顯示經驗的地方。最後補一句你會肯定寫得好的部分，並強調 review 的時效性。

## 講稿

我看 PR 的順序是由大到小。

最先看的是這個改動要解決什麼問題、方向對不對。如果方向錯了，我在行內留的那些細節意見全部都是浪費。所以如果 PR 描述沒寫清楚要解決什麼、怎麼驗證，我的第一個意見就是請他補上。

方向沒問題之後看介面跟資料模型，因為這兩個最難事後改。再來是正確性跟邊界情況，空集合會怎樣、失敗的時候會不會留下半完成的狀態、重送會不會產生兩筆、有沒有逾時。這些是最容易漏而且事後最貴的東西。可讀性跟命名我放在最後。

給意見我會標清楚嚴重程度，這個必須改、這個建議改、這個只是我的偏好你可以不理。因為把缺陷跟偏好混在一起講，對方沒辦法判斷輕重，review 就會變成品味之爭。

我也盡量說明理由，不會只說這樣不對。像是這裡如果請求重送會產生兩筆訂單，建議加冪等鍵，這樣對方知道我在擔心什麼。

還有兩件事我覺得是工程問題不是人的問題。格式那類的應該交給工具在 CI 擋掉，還有太大的 PR 我會請對方拆，因為看不完的時候人會傾向直接相信。

## 常見追問

### 如果對方不接受你的意見呢？

**核心答案**：**先分辨這是缺陷還是偏好**。如果是偏好（命名風格、寫法習慣），我會直接放行，並在必要時把它變成團隊的共同約定而不是個別 PR 的爭論。如果是真正的缺陷（會導致錯誤、安全問題、資料不一致），我會把**具體的失敗情境**寫出來——「如果兩個請求同時進來，這兩行之間的空窗會導致重複扣款」——用可驗證的場景取代主觀判斷。如果對方仍然不同意，就約十分鐘直接談，非同步爭論超過兩個來回就該轉成同步。

**詳細解析**：這裡的分寸在於**你的 review 不是為了贏**。實務上多數僵局來自雙方在不同層次上對話：一方在講「這樣寫比較好維護」（抽象），另一方在講「現在能動」（具體）。轉成具體場景通常能打破僵局。如果真的談不攏而且是重要的缺陷，可以請第三個人看——不是仲裁誰對，而是引入另一個視角。要避免的是**用職權或資歷壓過去**，那會讓對方下次不敢提出不同意見，長期損害團隊的技術討論品質。反過來，如果你被說服了，明確說「你說得對，我沒想到那個情境」也是重要的示範。

**面試回答方式**：先給缺陷與偏好的分辨，並說明偏好就放行、必要時轉成團隊約定。缺陷則用具體失敗情境取代主觀判斷。加分點是點出兩個來回就轉同步、以及不要用資歷壓過去的理由——會讓對方下次不敢提出不同意見。

### 你會 review 到多細？時間怎麼分配？

**核心答案**：**依風險調整深度**。碰到金流、權限、資料遷移、對外 API 的改動，我會逐行看並主動跑一次；一般的功能新增看設計與邊界情況；純粹的文案或設定調整快速掃過即可。時間上，我傾向**當天回應**——即使只能給初步意見。因為 PR 放越久，作者的上下文流失越多，來回的成本越高。

**詳細解析**：一個實用的原則是**看不懂就是問題**。如果你認真看了十分鐘還理不清這段程式碼在做什麼，那多半不是你的問題，而是它需要更好的命名、拆分或註解——把這個感受直接說出來是有價值的回饋。另外要控制單次 review 的長度：連續看超過四五十分鐘之後，發現問題的能力會明顯下降，分兩次看比硬撐好。至於「要不要在本地跑一次」，判準是改動的**可觀察性**——UI 或體驗相關的改動，看程式碼是看不出問題的，一定要實際跑；純邏輯的改動則讀程式碼加上檢查測試通常足夠。

**面試回答方式**：給出依風險調整深度的分級，並列出哪些類型要逐行看。強調當天回應的理由是上下文流失。加分點是提出「看不懂就是問題」這個原則，以及依可觀察性決定要不要在本地實際跑。

### 你自己的 PR 會怎麼準備，讓別人比較好 review？

**核心答案**：**先自己 review 一遍**，然後把脈絡補齊。具體做法是：PR 描述寫清楚**要解決什麼問題、採取什麼做法、怎麼驗證、有什麼已知的取捨**；把**重構和功能改動分開提交**，不要混在同一個 PR 裡（那會讓 reviewer 無法區分哪些改動是必要的）；控制大小，超過一定規模就拆；並在容易誤解的地方**自己先留下註解說明為什麼這樣寫**。

**詳細解析**：最有效的一招是**在送出前自己看一次 diff**——你會抓到大量的殘留除錯程式碼、註解掉的舊實作、不小心改到的無關檔案。這件事只花五分鐘卻能省下對方的來回。另一個高價值的做法是在 PR 描述中主動指出**你自己不確定的地方**（「這裡的鎖粒度我不確定夠不夠，想聽聽意見」），這會把 reviewer 的注意力導到最需要的地方，也讓 review 從檢查變成協作。最後，**回應意見的態度**同樣重要——每一條意見都要有回覆（採納、說明為什麼不採納、或另開票追蹤），沉默地忽略某些意見會讓 reviewer 下次失去投入的意願。

**面試回答方式**：核心是送出前自己先看一次 diff，並補齊脈絡（問題、做法、驗證、取捨）。強調重構與功能改動要分開提交的理由。加分點是提到主動標示自己不確定的地方，把 review 從檢查變成協作，以及每條意見都要有回覆。
