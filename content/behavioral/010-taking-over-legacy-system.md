# 題目

你被指派接手一個原作者已離職、文件幾乎沒有的系統。前兩週你會怎麼安排？

## 核心答案

順序是**先能觀察、再能安全改動、最後才談重構**。第一週的目標是**建立可見度**：把系統的入口點找出來（有哪些 API、排程、訊息消費者）、確認它依賴什麼與被誰依賴、把日誌與監控補到「線上出事時我知道發生什麼」的程度。第二週的目標是**建立安全網**：找出核心路徑並補上測試（優先是特徵測試——不管內部怎麼寫，先鎖住現在的輸出行為），確認能在本地或測試環境重現一次完整流程，並演練一次部署與回滾。這兩件事做完之後才有資格談改動，因為在沒有可見度和測試的情況下改 legacy，等於在黑暗中拆炸彈。最重要的心態是**先不要評價**——舊程式碼看起來荒謬的地方，往往是某個你還不知道的業務規則或事故留下的補丁。先理解為什麼，再決定要不要改。

## 詳細解析

**最有價值的資訊來源不是程式碼**：優先順序是**線上行為**（監控、日誌、資料庫實際內容）、**票務與事故紀錄**（過去出過什麼問題，通常直接指出脆弱點）、**版本控制歷史**（`git log` 與 `git blame` 能看出哪些檔案改動頻繁——那通常是核心或問題所在）、**還在的人**（客服、營運、PM 知道業務規則，即使工程師走了）。程式碼是最後才讀的，因為沒有脈絡的程式碼很難理解。

**特徵測試是 legacy 改動的關鍵工具**：它不驗證「應該是什麼」，而是鎖住「現在是什麼」——把現有輸入輸出記錄下來當成基準，之後任何改動只要輸出變了就會被抓到。這讓你能在不完全理解程式碼的情況下安全重構。實務做法是找出核心函式，用真實資料跑一批輸入、把輸出存下來當快照。這比試圖為 legacy 寫「正確」的單元測試務實得多。

**不要一上來就重寫**：全面重寫的失敗率極高，因為舊系統裡累積的無數邊緣處理是隱形的需求規格，重寫時必然遺漏。比較安全的路線是**絞殺者模式**——在舊系統外圍建立新的介面層，把流量一塊一塊導到新實作，舊的部分逐步縮小直到可以移除。這個過程隨時可以停下來，而且每一步都有可驗證的價值。

**要在前兩週產出一些可見的成果**：純粹的「研究」兩週會讓周圍的人焦慮。合理的做法是把可見度工作變成交付物——一份系統地圖（有哪些元件、資料怎麼流動、外部依賴是什麼）、一份已知問題清單、以及至少一個小而確定的改善（補上一個缺失的告警、修掉一個反覆出現的小錯誤）。這既建立了信任，也讓你的理解被檢驗。

**記錄你理解的過程**：邊看邊寫下來，一方面是給下一個人的文件（你正在解決自己遇到的問題），一方面是讓你的理解被別人糾正。把系統地圖丟到群組問「我的理解對嗎」，通常會有人補上關鍵資訊——這比一個人埋頭研究快得多。

## 面試回答方式

用「先能觀察、再能安全改動、最後才重構」這個順序當骨架，這句話本身就展現了紀律。第一週講可見度：找入口點、確認依賴、補日誌與監控。第二週講安全網：特徵測試、能重現流程、演練回滾。主動說明資訊來源的優先順序——**線上行為與事故紀錄比程式碼更有價值**，這是很多人不會提的一點。明確表態**不會一上來就重寫**，並給出絞殺者模式作為替代。最後強調你會在前兩週產出可見的交付物（系統地圖、已知問題清單、一個小改善），因為純研究會讓周圍的人焦慮。

## 講稿

我的順序是先能觀察、再能安全改動，最後才談重構。

第一週我做可見度。先把入口點找出來，有哪些 API、有哪些排程、有哪些訊息消費者，然後確認它依賴什麼、又被誰依賴。同時把日誌跟監控補到一個程度，就是線上出事的時候我知道發生什麼事。

第二週做安全網。我會找出核心路徑補測試，優先是特徵測試，不管裡面怎麼寫，先把現在的輸出行為鎖住。這樣我就可以在還沒完全理解程式碼的情況下安全地改。另外會演練一次部署跟回滾。

這裡我想特別講一件事，我讀程式碼的順序是很後面的。最有價值的資訊其實是線上行為跟事故紀錄，過去出過什麼問題通常直接指出脆弱在哪。還有 git 的歷史，改動頻繁的檔案通常就是核心或者問題所在。

還有一個心態上的原則，我不會太早評價。舊程式碼裡看起來很荒謬的地方，常常是某個我還不知道的業務規則，或者上一次事故留下來的補丁。

前兩週我也會產出一份系統地圖跟已知問題清單，然後丟到群組問我的理解對不對。

## 常見追問

### 什麼情況下你會建議重寫而不是漸進改善？

**核心答案**：三種情況值得考慮重寫。**一、底層技術已經不可維護**（語言或框架停止支援、有無法修補的安全漏洞、找不到人會維護）。**二、業務需求已經根本改變**，舊系統的核心假設不再成立，改起來比重做還費力。**三、系統規模夠小**，重寫成本可估且風險可控。除此之外，預設應該是漸進改善，因為重寫的最大風險是**隱形需求**——舊系統裡有大量沒有文件、只存在於程式碼中的邊緣處理。

**詳細解析**：即使決定重寫，也應該分批進行而不是一次切換。**絞殺者模式**的做法是新舊並行、逐塊遷移，每一塊都可以獨立驗證與回滾。另一個關鍵是**先建立可比對的基準**——讓新舊系統同時處理相同輸入，比對輸出差異（影子流量），這能在真正切換前抓出絕大多數的行為落差。要特別小心的是重寫過程中**舊系統仍在變動**，如果業務持續提新需求，就會出現「新系統永遠追不上舊系統」的困境，所以重寫期間通常需要凍結舊系統的非必要改動，這件事需要事先取得共識。

**面試回答方式**：給出三個值得重寫的情況，並明確說明預設是漸進改善、理由是隱形需求。接著給執行方式：絞殺者模式分批遷移、用影子流量比對新舊輸出。加分點是提到重寫期間必須處理舊系統持續變動的問題，需要事先取得凍結共識。

### 沒有測試又不敢改，怎麼開始？

**核心答案**：**先在最外層建立特徵測試，再往內收斂**。不需要為每個函式寫單元測試——那在 legacy 上通常做不到，因為程式碼耦合嚴重、依賴無法替換。可行的起點是**在系統邊界（API 或整個批次流程）記錄真實輸入輸出**，把它們當成基準測試。有了這層保護，就可以開始把內部的邏輯拆出來，每拆一塊再補一層更細的測試。

**詳細解析**：這個過程有個標準的技巧叫「**接縫**」——找到可以在不改動行為的前提下插入替換點的位置（通常是外部呼叫、時間、隨機數），把它們抽成可注入的依賴，程式碼就變得可測了。最常見的具體障礙是**隱藏的外部依賴**：直接 new 出資料庫連線、直接讀系統時間、寫死的外部 API 位址。優先處理這幾個，可測性通常會大幅改善。另外要接受**不是所有程式碼都值得補測試**——優先順序應該依「改動頻率乘以壞掉的代價」排序，很少改又不重要的角落可以先放著。

**面試回答方式**：給出「從外層特徵測試開始、再往內收斂」這個路徑，說明為什麼不從單元測試開始。介紹接縫這個技巧與三個最常見的障礙（直接 new 依賴、讀系統時間、寫死位址）。加分點是提出補測試也要排優先順序，依改動頻率乘以壞掉的代價來決定。

### 如果原作者還在但不願意交接呢？

**核心答案**：**降低對單一資訊來源的依賴，並把需求變成具體且低成本的請求**。與其要求「跟我完整交接」（對方會覺得是一件大工程），不如問具體的問題——「這個排程失敗的時候會怎麼樣」「這個欄位為什麼有兩種格式」。具體問題的回答成本低，對方通常願意答，而且你會逐步累積出全貌。同時透過線上行為、事故紀錄、版本歷史自行補足，減少卡在對方身上的部分。

**詳細解析**：不願意交接的原因通常不是惡意——可能是本身工作滿載、可能是覺得說不清楚、也可能是對這個系統有情感或不安全感。理解原因會影響做法：如果是時間問題，就把請求切小並約定固定的短時段；如果是不安全感，就明確表達你是來接手維護而不是來評價他的程式碼。在面試中回答這題要**避免把對方描述成障礙**，重點放在你如何在資訊不完整的情況下仍然推進——那才是這題想測的能力。另外可以主動提到你會**把學到的東西寫成文件**，讓知識不再依賴任何單一個人，這是對組織有價值的行為。

**面試回答方式**：核心是降低對單一來源的依賴，並把大請求切成具體的小問題。說明不願交接通常不是惡意，並依原因調整做法。加分點是強調回答時不要把對方描述成障礙，並主動提你會把知識文件化讓它不再依賴個人。
