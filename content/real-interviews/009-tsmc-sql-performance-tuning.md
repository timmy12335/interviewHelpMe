# 題目

這是台積電資訊處（以及同類型擁有**大量內部報表和資料分析系統**的台灣科技／製造業公司）在後端／資料庫相關職位面試裡**相當常見**的實務題（根據公開面試經驗分享整理歸納而成，並非逐字官方紀錄）：**「有一段用來產生月報表的 SQL 查詢，執行時間需要將近 10 分鐘，業務單位抱怨太慢，你會怎麼一步一步分析、優化？」**這類題目**反映了**台灣傳統科技業／製造業常見的技術情境——**內部大量的報表和資料分析需求**，而不是像中國互聯網大廠那樣**以高並發的對外服務**為主。

## 核心答案

面對**長時間執行的報表查詢**，建議的排查思路是——**(1) 先用 `EXPLAIN` 分析這段 SQL 的執行計畫**：確認是**哪一個環節**特別耗時（是某個特定的 JOIN 操作、還是某個子查詢）；**(2) 檢查是否存在可以額外建立的索引**（見 [[../database/001-btree-index.md]]、[[../database/004-composite-index.md]]），特別是**報表類查詢經常涉及大量的聚合（GROUP BY）、排序（ORDER BY）**，這類操作如果能命中恰當設計的索引，能帶來顯著的效能提升（見 [[../database/014-index-covering-and-sorting.md]]）；**(3) 考慮是否需要額外的『彙總表（Summary Table）』或報表專用資料表**：如果這份報表是**定期（如每月）**執行、而**原始明細資料非常龐大**，與其每次都重新對龐大的原始明細資料表做即時的複雜聚合運算，不如**額外設計一張已經預先計算、彙總好**的報表資料表，讓**報表系統只需要去查詢這張已經整理好的彙總表**，而不需要每次都重新計算。

## 詳細解析

**製造業／科技業內部報表系統的獨特情境——不是高並發，而是單一次、大量資料的複雜運算**：這題和前面（見 [[002-tencent-mysql-index-sharding.md]]）已經討論過的**中國互聯網公司情境**有一個**值得注意**的核心差異——中國互聯網大廠面對的挑戰通常是**「大量並行，但每一筆查詢本身相對單純」**的高並發場景；而**台灣科技業的內部報表系統**面對的往往是**「單一次查詢，但這一次查詢本身涉及大量資料的複雜聚合運算」**這種**截然不同**的效能挑戰（這某種程度上是 **OLTP（線上交易處理）**和 **OLAP（線上分析處理）**這兩種截然不同的資料庫使用模式的差異）。理解這種情境差異很重要——**針對高並發場景的優化手段**（如前面已經討論過的分庫分表）**未必**是**這種大量、單次複雜聚合運算**場景的正確解方，因應這種情境更**應該優先考慮**的是**「如何讓單一次複雜的聚合運算執行得更快」**這個不同的問題，而這正是**索引優化、以及前面已經提到的彙總表設計**之所以特別適用於這類情境的核心原因。

**彙總表設計的核心思路——用『空間換取時間』，把複雜運算提前算好**：**彙總表（Summary Table）**這個解法本質上是一種**「用空間去換取時間」**的經典權衡——與其讓**每一次需要產生報表**的請求都**即時地**去對**龐大的原始明細資料**重新執行一次**耗時的聚合運算**，不如**提前地（例如每天深夜批次執行一次）**把**這些聚合運算的結果****預先計算好，儲存成一張額外的彙總表**，之後**任何需要查詢報表**的請求都只需要去**查詢這張已經算好的彙總表**（這通常會遠比**即時重新計算**快上許多）——**代價**是**需要額外佔用儲存空間去儲存這張額外的彙總表**，以及**這張彙總表的資料**通常**不是完全即時**的（它反映的是**上一次批次計算時**的狀態，而不是**當下這一秒**的最新狀態）。這種**「犧牲一定程度的即時性和額外的儲存空間，去換取查詢速度的顯著提升」**的思路，某種程度上也呼應了這篇文章反覆強調的核心分析框架——**任何一種技術方案都是一種權衡取捨，而不是沒有代價的完美解方**。

**台灣科技業面試特有的風格——更重視你是否具備實際在大型企業內部系統運作過的實務經驗**：相較於中國互聯網大廠那種**追問到底、故意刁難**的面試風格，台灣本地科技業（尤其是**傳統大型製造業的資訊部門**）面試風格通常**更加務實、著重實際經驗**——面試官很常會直接問**「你過去實際處理過類似的效能優化案例嗎？當時是怎麼解決的？」**這類**要求你分享真實經驗**的問題。建議準備 **1-2 個自己曾經實際處理過**（即使只是在 side project 或學校專題裡）的具體 SQL 優化案例，**具備能夠講出具體細節**的準備，會比**只能泛泛地談論理論**更能在這類面試裡留下好印象。

## 面試回答方式

先給出循序漸進的排查思路——「先用EXPLAIN分析執行計畫，確認是哪個環節特別耗時;檢查是否有可以額外建立的索引，報表類查詢常涉及大量聚合排序，如果能命中恰當設計的索引能帶來顯著效能提升;考慮是否需要額外的彙總表，如果報表是定期執行且原始明細資料非常龐大，與其每次都重新計算，不如額外設計一張已預先計算彙總好的報表資料表」。可以點出這類報表場景和高並發場景的本質差異——「這和中國互聯網公司常見的高並發場景不同，製造業科技業的內部報表系統面對的往往是單一次查詢但涉及大量資料複雜聚合運算的挑戰，這是OLTP和OLAP兩種截然不同資料庫使用模式的差異，針對高並發場景的優化手段未必是這種情境的正確解方」。可以詳細說明彙總表的核心權衡——「彙總表本質上是用空間換取時間，提前批次算好聚合結果存成一張額外表，查詢時只需要查這張已經算好的表，代價是需要額外儲存空間，且資料不是完全即時的」。可以主動分享自己實際處理過的具體案例，展現務實的實務經驗，而非只談理論。

## 常見追問

### 如果這張彙總表需要**每天凌晨**批次重新計算，你會怎麼確保這個批次計算的過程不會影響到**白天正常上班時間**的其他系統效能？

**核心答案**：核心思路是**「把這種大量耗費資源的批次運算安排在系統負載相對較低的時段執行，並控制它實際佔用的資源」**——具體做法包括——**(1) 排程在離峰時段**：明確地安排這個批次任務在**深夜、系統整體負載最低**的時段執行（這也是為什麼這類批次任務經常被稱為「夜間批次（Nightly Batch）」）；**(2) 限制批次任務實際佔用的資源**：例如控制這個批次任務每次**只處理一部分資料**，分批次執行，避免一次性地佔用大量的資料庫連線或運算資源；**(3) 如果這個資料庫本身同時需要服務白天的即時查詢需求，考慮把這種批次運算額外地導向一個獨立的唯讀複本**（見前面已經討論過的讀寫分離（Read-Write Splitting）概念），讓**批次運算的負載**和**日常即時查詢的負載**完全隔離開來。

**詳細解析**：這題考察是否理解**「批次處理」和「即時處理」這兩種不同性質的工作負載，如果被混雜在同一個資源池裡一起競爭，可能會互相干擾**。這某種程度上呼應了前面（見 [[../system-design/020-batch-vs-stream-processing.md]]）已經深入討論過的批次處理與流式處理核心概念——批次處理的特性是**「在相對不那麼即時緊迫的時間框架內，一次性地處理大量資料」**，這種特性決定了它**天生適合被安排在系統整體負載較低的時段**去執行；如果讓這種**「不那麼緊急、但資源消耗較大」**的任務，和**「時效性要求很高」**的日常業務查詢在**同一段時間**去**競爭同一批有限的資料庫資源**，就可能導致日常的業務查詢**因為資源被批次任務大量佔用**而出現**非預期的效能延遲**。

**面試回答方式**：先給出核心思路——「核心是把這種大量耗費資源的批次運算安排在系統負載相對較低的時段執行，並控制它實際佔用的資源」。給出具體做法——「排程在深夜這種離峰時段執行(這也是為什麼被稱為夜間批次);限制批次任務實際佔用的資源，例如分批次處理避免一次性佔用大量連線;如果資料庫同時要服務白天即時查詢，可以考慮把批次運算導向一個獨立的唯讀複本，讓批次負載和日常查詢負載完全隔離」。可以連結到批次vs流式處理的核心概念——「這呼應了批次處理和即時處理這兩種不同性質工作負載，如果混雜在同一資源池裡競爭會互相干擾這個核心概念，批次處理天生適合被安排在系統負載較低的時段執行」。

### 如果這個 SQL 查詢涉及好幾張不同的表做 JOIN，而且其中某幾張表資料量特別龐大，你會特別注意什麼？

**核心答案**：需要特別注意 **JOIN 的順序和方式**——資料庫的查詢優化器通常會**自動地**嘗試決定最有效率的 JOIN 順序，但理解**「應該盡量先用篩選條件，把每一張表各自需要參與 JOIN 的資料量縮小到最小，再執行 JOIN」**這個原則依然很重要——建議**確認每一張參與 JOIN 的表，各自的篩選條件（WHERE 子句）是否都有恰當的索引支援**，避免出現**「先把兩張龐大的表整個做完整 JOIN，之後才做篩選」**這種**效率低落**的執行方式（理想上應該是**先篩選、縮小每一張表各自需要參與運算的資料量，再做 JOIN**）。

**詳細解析**：這題考察是否理解**資料庫執行 JOIN 操作的基本原理**，以及如何透過**恰當的索引設計**去引導資料庫的查詢優化器選擇**更有效率的執行路徑**——這某種程度上是前面核心答案和詳細解析已經提到的**「先用 EXPLAIN 分析執行計畫」**這個基本原則的具體延伸——透過 `EXPLAIN` 的結果，可以具體地看到**資料庫實際上選擇的 JOIN 順序和方式**；如果發現**這個順序或方式**看起來**不夠理想**（例如**先對一張龐大的表做全表掃描**才去做 JOIN），就需要回頭去**檢查是否缺少恰當的索引**來引導優化器做出更好的選擇。這也再次印證了這題整體的核心考點——**「面對效能問題，是否具備用工具（EXPLAIN）去實際驗證、而不是單純憑猜測」**這種務實的排查思維。

**面試回答方式**：先給出核心關注點——「需要特別注意JOIN的順序和方式，理解應該盡量先用篩選條件把每張表各自需要參與JOIN的資料量縮小到最小再執行JOIN這個原則，確認每張參與JOIN的表各自的篩選條件是否都有恰當的索引支援，避免先把兩張龐大的表整個做完整JOIN之後才做篩選這種低效率方式」。可以連結回EXPLAIN的實務排查方法——「這呼應了先用EXPLAIN分析執行計畫這個基本原則，透過EXPLAIN結果可以具體看到資料庫實際選擇的JOIN順序和方式，如果發現不夠理想就回頭檢查是否缺少恰當索引來引導優化器做出更好選擇」。

### 如果業務單位希望這份報表能夠做到「即時」呈現（而不是每天凌晨才更新一次的彙總表），你會怎麼平衡「即時性」和「效能」這兩個可能衝突的需求？

**核心答案**：需要先**釐清『即時』具體指的是多即時**——如果業務單位實際上能接受**幾分鐘甚至幾十分鐘**的延遲（只是**不能忍受整整一天**的延遲），可以考慮**把彙總表的計算頻率從『每天一次』提高成『每幾分鐘重新計算一次』**這種折衷方案；如果業務單位真的需要**近乎即時**的結果，則可能需要考慮**更進階的架構**，例如**流式處理（Stream Processing）**（見 [[../system-design/020-batch-vs-stream-processing.md]]）——**每當有新的原始資料產生**就**即時地去更新彙總結果**，而不是**定期批次重新計算整批**資料。

**詳細解析**：這題考察是否能**避免把『即時性』這個需求當作一個非黑即白的二元選項**，而是能**具體地去釐清『到底需要多即時』**，再依照這個更精確的需求去選擇恰當的架構方案——這呼應了這篇文章反覆強調的核心原則——**任何一個技術決策都應該回到『具體、實際的需求是什麼』**去做判斷，而不是**只看到『即時』這兩個字**就直接跳到**最複雜、最昂貴**的解決方案（如完整的流式處理架構）——很多時候**業務單位口中的『即時』**實際上**可以被接受的延遲範圍**遠比字面上聽起來寬鬆得多，只需要**適度地提高批次計算的頻率**就能滿足實際的業務需求，**而不需要**投入**遠更高的架構複雜度和開發成本**，去追求一個**業務上其實並不真正需要**的絕對即時性。

**面試回答方式**：先給出核心思路——「需要先釐清即時具體指的是多即時，如果業務單位實際上能接受幾分鐘甚至幾十分鐘的延遲，只是不能忍受整整一天的延遲，可以考慮把彙總表計算頻率從每天一次提高成每幾分鐘一次這種折衷方案;如果真的需要近乎即時的結果，才考慮更進階的流式處理架構，每當有新資料產生就即時更新彙總結果」。給出核心的判斷原則——「任何技術決策都應該回到具體實際需求是什麼去判斷，而不是只看到即時兩個字就直接跳到最複雜昂貴的解決方案，很多時候業務單位口中的即時，實際上能接受的延遲範圍遠比字面上聽起來寬鬆得多」。
