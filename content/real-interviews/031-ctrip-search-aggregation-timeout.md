# 題目

「多資料源的聚合與逾時控制」是攜程這類**OTA（線上旅遊）平台**常被回報的題目（根據公開的面試經驗分享整理歸納而成，並非逐字官方紀錄）：「查詢機票時要同時向十幾家航空公司或供應商的介面詢價，其中有幾家很慢甚至會超時。你會怎麼設計，才能既保證整體的回應時間，又盡可能給出完整的結果？」這題考察的是併發呼叫、逾時預算與部分失敗的處理，而它在真實系統中極為常見。

## 核心答案

核心原則是「整體的逾時預算固定，慢的參與者不應該拖垮所有人」。

**做法是四點**：並行呼叫所有供應商而非串行（總耗時等於最慢的那一個而非全部之和）；給整體設一個硬性的截止時間（例如三秒），時間到就用已經回來的結果回應；對每個供應商各自設更短的逾時並用斷路器隔離持續失敗的（見 [[../backend-engineering/007-circuit-breaker-pattern.md]]）；以及明確地告知使用者「結果可能不完整」而非假裝完整。

而更進一步的優化是「分階段回應」——先在一秒內回傳已到的結果讓使用者開始瀏覽，再用推送或輪詢補上後到的；這比讓使用者盯著載入畫面等三秒好得多。

要避免的是「用固定的逾時串行呼叫」——十家各給一秒的逾時，最壞情況是十秒；**這是這題最常見的錯誤答案。**

## 詳細解析

「逾時預算必須從上游往下傳遞」（見 [[../backend-engineering/025-timeout-and-deadline.md]]）：如果閘道給這個請求三秒——那聚合服務就只有三秒減去自己的處理時間可以分配；而如果每一層都獨立地設一個「三秒」，總時間會層層疊加。正確的做法是傳遞一個絕對的截止時間戳而非相對的逾時值——於是每一層都知道「還剩多少時間」而不是「我可以用多少時間」；這個差別在多層呼叫的系統中影響很大。

「斷路器讓長期故障的供應商不再浪費時間」：如果某家供應商已經連續失敗五分鐘——每次請求都還花一秒等它逾時是純粹的浪費；斷路器在失敗率超過門檻後直接快速失敗，並定期用少量請求試探是否恢復。這把「每次都付出逾時的成本」變成了「只在試探時付出」。

「快取能大幅降低對慢供應商的依賴」：機票的價格雖然會變但不是每秒都變——把結果快取幾十秒到幾分鐘，能讓大部分的查詢不需要真的呼叫供應商；而快取的時效性需要與業務協商（見 [[../system-design/006-caching-strategies.md]]）——價格顯示與最終下單時的價格不一致，是這類系統的固有問題，通常靠「下單前再確認一次」解決。

**「部分失敗的呈現方式很重要」**：如果少了兩家供應商的結果卻不告訴使用者——他可能錯過更便宜的選項而不自知；而明確地顯示「部分供應商暫時無法取得報價，正在重試」既誠實又降低了客訴。這是一個技術決策直接影響信任的例子。

## 面試回答方式

先給核心原則（整體逾時預算固定，慢的不拖垮所有人）與四點做法，並指出用固定逾時串行呼叫是最常見的錯誤答案。加分點有四個：逾時預算要從上游傳遞絕對的截止時間戳而非相對值；斷路器把「每次都付逾時成本」變成「只在試探時付」；快取能大幅降低對慢供應商的依賴，而價格不一致靠下單前再確認解決；以及**分階段回應**與**部分失敗要誠實呈現**。

## 講稿

核心原則是整體的逾時預算固定，慢的參與者不應該拖垮所有人。

做法有四點。並行呼叫所有供應商而不是串行，總耗時等於最慢的那一個。給整體設一個硬性截止時間，時間到就用已經回來的結果回應。對每個供應商各自設更短的逾時，並用斷路器隔離持續失敗的。最後明確告知使用者結果可能不完整。

這裡我想強調一個容易被忽略的細節。逾時預算必須從上游往下傳遞，而且要傳絕對的截止時間戳，不是相對的逾時值。因為如果每一層都獨立設一個三秒，總時間會層層疊加。傳絕對時間的話，每一層都知道還剩多少時間。

斷路器的價值是把每次都付出逾時成本，變成只在試探時付出。某家供應商已經連續失敗五分鐘，每次還花一秒等它逾時是純粹浪費。

另外我會加上快取。機票價格會變但不是每秒都變，快取幾十秒能讓大部分查詢不用真的呼叫供應商。而價格不一致的問題靠下單前再確認一次解決。

## 常見追問

### 並行呼叫十幾個服務，執行緒會不會不夠用？

**核心答案**：用非同步的 I/O 或反應式的模型而非一個呼叫一個執行緒。如果每個請求都要佔用十幾個執行緒等待 I/O——在高並發下執行緒池會迅速耗盡；而非同步的模型讓等待 I/O 的請求不佔用執行緒（見 [[../java-concurrency/012-future-vs-completablefuture.md]]），於是併發能力與執行緒數解耦。

**詳細解析**：這考察「阻塞式 I/O 在扇出場景中的成本被放大」——一個請求扇出到十個下游，意味著執行緒的需求乘以十；這正是聚合型服務特別容易耗盡執行緒池的原因。而 Java 的虛擬執行緒（見 [[../java-concurrency/024-virtual-threads-suitable-scope.md]]）讓這個問題有了更簡單的解法——可以繼續用直觀的阻塞式寫法而不必改成回呼或反應式的風格；這是近年 JVM 生態中對這類服務影響最大的變化之一。能指出「扇出讓執行緒需求倍增」這個具體的機制，比籠統地說「要用非同步」深入得多。

**面試回答方式**：給做法（**非同步 I/O 或反應式模型**）並說明它讓併發與執行緒數解耦。核心加分點是點出阻塞式 I/O 在扇出場景中成本被放大——一個請求扇出到十個下游意味著執行緒需求乘以十，這是聚合服務特別容易耗盡執行緒池的原因。收在新選項：虛擬執行緒讓這個問題有了更簡單的解法——可以繼續用直觀的阻塞式寫法。

### 怎麼決定每個供應商的逾時該設多少？

**核心答案**：依它的實際回應時間分布而非拍腦袋。看歷史資料中該供應商的第 95 或第 99 百分位——**把逾時設在那附近**；而不是所有供應商都設同一個值。因為有些供應商本來就慢（但仍在可接受範圍），而有些平常很快卻偶爾卡住，兩者需要不同的處理。

**詳細解析**：這考察**「逾時值應該由資料決定」**這個工程習慣——設得太短會誤殺本來能成功的請求（而重試又增加了下游的負擔），設得太長則失去了保護的意義；而「設在 P99 附近」的理由是它保留了絕大多數正常請求，同時擋掉了真正異常的。**更進階的做法是「動態逾時」**——根據近期的實際分布自動調整，於是在下游變慢時能自動放寬（避免大量誤殺）而在下游恢復後收緊；但要小心它可能掩蓋了持續劣化的問題，所以動態調整的範圍應該有上限並在觸及上限時告警。這個「自適應但有邊界」的設計原則，在很多自動調節的機制中都適用。

**面試回答方式**：給做法（依實際回應時間分布，設在 P95 或 P99 附近）並說明為什麼不該所有供應商同一個值。核心加分點是解釋設太短與太長各自的問題，並提出**動態逾時**這個進階做法。收在原則：動態調整的範圍應該有上限並在觸及時告警——否則它會掩蓋持續劣化的問題；「自適應但有邊界」在很多自動調節的機制中都適用。

### 結果不完整時，排序會不會出問題？

**核心答案**：會，而且這是一個容易被忽略的正確性問題。如果「最便宜」的那家供應商剛好逾時——使用者看到的最低價就是錯的；所以除了顯示不完整的提示外，還應該考慮「等待策略要與排序的關鍵性掛鉤」：對價格排序這種對完整性敏感的查詢可以多等一點，而對「查看所有選項」這類瀏覽性的查詢可以早點回應。

**詳細解析**：這考察「部分結果的品質不只是數量問題」——少了十分之一的結果聽起來不嚴重，但如果那十分之一恰好包含最優解，那使用者的決策就被實質影響了；而這在按價格排序的場景中特別明顯。**可行的緩解包括**：對歷史上經常提供最低價的供應商給予更長的逾時、在快取中保留該供應商上次的報價作為參考（並標示為可能過期）、以及在結果不完整時弱化「最低價」這類絕對性的用語。這個「技術上的部分失敗如何轉譯成使用者能理解的資訊」的思考，是聚合類系統中最考驗產品意識的部分。

**面試回答方式**：給明確的答案（會，而且是容易被忽略的正確性問題）並用「最便宜的那家逾時」說明。核心加分點是提出等待策略要與排序的關鍵性掛鉤，並列出三個緩解手段（給重要供應商更長逾時、用快取的舊報價並標示、弱化絕對性用語）。收在洞察：技術上的部分失敗如何轉譯成使用者能理解的資訊，是聚合類系統中最考驗產品意識的部分。
