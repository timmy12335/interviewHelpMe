# 題目

這是 91APP（以及同類型的台灣電商 SaaS／新創公司）在後端工程師面試裡**相當常見**的實務系統設計題（根據公開面試經驗分享整理歸納而成，並非逐字官方紀錄）：**「請設計一個購物車系統，需要同時支援『已登入使用者』和『訪客（未登入）』這兩種情境，並考慮訪客之後登入時，購物車內容應該如何被妥善合併」**這題**結合了**資料儲存設計，以及一個相當實際、容易被忽略的**訪客購物車合併**細節。

## 核心答案

**已登入使用者**的購物車通常直接**儲存在後端的資料庫（或者額外搭配 Redis 做快取加速）**，用**使用者 ID** 作為索引；而**未登入的訪客**因為**沒有一個固定的使用者身份**可以識別他，通常會**依靠瀏覽器的 Cookie 或 LocalStorage** 去**在前端本地**儲存這位訪客的購物車內容（或者額外地用一個**臨時的、隨機產生的訪客 ID（Session ID）**，把購物車內容暫存在後端，用這個臨時 ID 作為索引）。這裡**最關鍵**的設計環節是**「訪客合併」**這個場景——當一位**原本是訪客身份、已經把一些商品加入到購物車**的使用者**後來登入（或註冊）了帳號**，系統需要**把這位訪客原本在前端（或臨時後端）累積的購物車內容**，和**這個帳號原本已經存在的購物車內容（如果有的話）**做**妥善的合併**，而**不是**讓**其中一份購物車內容被直接覆蓋消失**。

## 詳細解析

**訪客購物車合併的細節——是「合併」而不是「取代」，需要處理商品重複的情況**：這是這題**最容易被忽略、但也最能展現實務經驗**的細節——很多**經驗較不足**的候選人可能會直覺地設計成**「登入之後就直接用帳號原本的購物車，覆蓋掉訪客的購物車」**，這種做法會導致**使用者在訪客期間辛苦挑選、加入購物車的商品****憑空消失**，這是一種**相當糟糕**的使用者體驗——正確的做法應該是**「合併」**而**不是「取代」**——具體需要處理**「如果訪客的購物車和帳號原本的購物車都有同一件商品，應該怎麼處理？」**（常見做法是**把兩邊的數量加總**、或者**取其中較大的那個數量**，依照實際業務規則決定）。這種**「合併而非取代」**的思路，是讓你**在這類題目上展現實務經驗**的關鍵加分點。

**購物車的儲存位置選擇——這反映了你對不同儲存方案取捨的理解**：這題也**呼應了**前面（見 [[../redis/001-data-types.md]] 相關概念）已經深入討論過的 **Redis 資料類型應用**——購物車這種**「經常被讀取和修改、但相對不需要絕對永久保存」**的資料，某種程度上**特別適合**被儲存在 **Redis** 這類**記憶體資料庫**裡（用 **Hash** 這種資料結構去儲存**「一位使用者的購物車裡有哪幾件商品、各自數量是多少」**這種結構化資料），而**不一定**需要**每一次購物車內容的變動**都即時地寫入到**傳統的關聯式資料庫**。這種**「依照資料本身的性質（是否需要絕對持久、存取頻率高低）去選擇恰當的儲存媒介」**的判斷，正是這題除了**訪客合併**這個核心考點以外，另一個值得展現的技術判斷力。

**這題在台灣電商新創面試裡的定位——考察你是否具備從使用者實際使用情境出發，去思考系統設計的能力**：台灣的電商 SaaS 新創（如 91APP 這類**服務眾多不同品牌客戶**的公司）面試風格通常**特別重視**候選人是否具備**「從真實使用者的實際使用流程，去反推系統應該怎麼設計」**這種**產品思維和技術能力兼具**的能力，**訪客購物車合併**這個場景正是一個**絕佳的例子**——如果你**只是**從**純技術角度**去設計**「怎麼儲存購物車資料」**，卻**完全沒有考慮到「使用者實際上會經歷從訪客到登入這種身份轉換的完整旅程」**，你設計出來的系統**技術上或許可行**，但**在真實的使用情境下**卻會讓使用者**經歷糟糕的體驗（購物車內容無故消失）**。這種**「技術設計必須緊密呼應真實使用者旅程」**的思維，是電商／消費性產品相關公司特別重視的核心素養。

## 面試回答方式

先給出已登入和未登入兩種情境的基本儲存設計——「已登入使用者的購物車直接儲存在後端資料庫或搭配Redis快取，用使用者ID作為索引;未登入訪客因為沒有固定使用者身份，通常依靠瀏覽器Cookie或LocalStorage在前端本地儲存，或用一個臨時隨機產生的訪客ID暫存在後端」。一定要主動深入說明訪客合併這個核心細節——「最關鍵的設計環節是訪客合併場景，當一位原本是訪客身份、已經把商品加入購物車的使用者後來登入了帳號，系統需要把這位訪客原本累積的購物車內容，和帳號原本已存在的購物車內容做妥善合併，而不是讓其中一份被直接覆蓋消失，常見做法是如果兩邊都有同一件商品，把數量加總或取較大值，依照實際業務規則決定」。可以補充儲存媒介的選擇考量——「購物車這種經常被讀取修改、但相對不需要絕對永久保存的資料，特別適合用Redis這類記憶體資料庫儲存，不一定需要每次變動都即時寫入傳統關聯式資料庫」，展現你不只是從純技術角度思考儲存方式，更能從真實使用者的完整使用旅程去反推系統應該怎麼設計。

## 常見追問

### 如果同一位使用者同時在「手機 App」和「網頁版」這兩個不同裝置上都登入了同一個帳號，並且各自在不同裝置上把不同的商品加入了購物車，你會怎麼設計，讓這兩個裝置上的購物車保持同步？

**核心答案**：既然這兩個裝置用的是**同一個已登入的帳號**，最直接的做法是**讓購物車的資料本質上就是儲存在後端、以這個帳號的使用者 ID 為索引的單一份資料**，**不管是 App 還是網頁版**都只是**去讀取、修改這同一份儲存在後端的購物車資料**，這樣**天然地**就能確保**「不管使用者從哪個裝置去查看購物車，看到的都是同一份最新的內容」**——這某種程度上和前面已經討論過的**「訪客」**情境不同——**訪客**因為**沒有固定身份**，才需要**依賴前端本地儲存**；但**已登入的使用者**因為**具備固定、可識別**的身份（使用者 ID），**理應**讓**購物車資料****統一以後端的紀錄為唯一的真實來源（Single Source of Truth）**，而**不是**讓**每一個裝置**各自維護一份獨立的購物車資料。

**詳細解析**：這題考察是否理解**「已登入使用者」和「未登入訪客」**這兩種情境**本質上需要採用不同的資料儲存策略**——這某種程度上呼應了前面核心答案已經建立的核心區分——訪客之所以需要**依賴前端本地儲存**，是因為**「沒有固定身份，沒辦法在後端用一個可靠、跨裝置共通的識別碼去索引他的資料」**；而**已登入使用者**因為**具備這種固定身份**，就**應該善用這個優勢**，讓**購物車資料****統一存放在後端一個唯一的位置**，這樣**「跨裝置同步」**這個需求**自然而然**就被滿足了（因為本質上就只有**唯一一份**資料，不存在**「需要額外同步多份各自獨立的資料」**這個問題）。這種**「理解不同情境背後的根本差異（有無固定身份），並依照這種根本差異選擇對應恰當的架構策略」**的思路，正是這題真正想考察的核心架構判斷力。

**面試回答方式**：先給出核心答案——「既然是同一個已登入帳號，最直接做法是讓購物車資料本質上就是儲存在後端、以這個帳號使用者ID為索引的單一份資料，不管App還是網頁版都只是去讀取修改同一份後端資料，天然就能確保不管從哪個裝置查看看到的都是同一份最新內容」。可以連結回訪客情境的核心區分——「這和訪客情境不同，訪客因為沒有固定身份才需要依賴前端本地儲存;但已登入使用者具備固定可識別身份，理應讓購物車資料統一以後端紀錄為唯一真實來源，而不是讓每個裝置各自維護獨立的購物車資料，這樣跨裝置同步這個需求就自然而然被滿足了，因為本質上就只有唯一一份資料，不存在需要額外同步多份各自獨立資料這個問題」。

### 如果購物車裡某一件商品的庫存，在使用者把它加入購物車之後、卻在使用者真正結帳之前被其他人買光了，你會怎麼設計來因應這種情況？

**核心答案**：核心原則是**「把商品存在購物車裡，和『真正保留這件商品的庫存』這兩件事分開看待」**——**「把商品加入購物車」**這個動作本身**通常不應該**就**立即實際地去鎖定或預先扣減**這件商品的庫存（因為使用者**可能把商品加入購物車後過了很久才結帳、甚至永遠不結帳**，如果一加入購物車就**預先鎖定**庫存，會導致大量庫存被**沒有真正購買意圖**的使用者**長期佔用**）。正確的做法是**只有在使用者真正進入結帳流程、準備實際下單**的那一刻，才**真正地去檢查、鎖定庫存**——如果**這時候發現購物車裡的某件商品庫存已經不足**，就**在結帳的當下**明確地**告知使用者**「這件商品庫存不足，請調整數量或移除」，而**不是**讓使用者**到了最後**才發現**下單失敗**。

**詳細解析**：這題考察是否理解**「購物車」**和**「真正的庫存鎖定／扣減」**是**兩個不同層次的概念，不應該被混為一談**——這直接呼應了前面（見 [[004-meituan-flash-sale-system-design.md]]）已經深入討論過的**秒殺場景庫存扣減**核心概念——**購物車**本質上只是**「使用者表達想要購買這些商品」這個意圖的一份暫存清單**，它**不應該**被賦予**「能直接影響到真實庫存」**這個重量級的能力；**真正涉及庫存增減的操作**應該被**謹慎地限縮**在**「使用者真正進入結帳流程」**這個更加明確、也更加接近真實購買意圖的具體時間點才觸發。這種**「把『使用者的意圖表達（加入購物車）』和『真正具備實際約束力的操作（鎖定／扣減庫存）』明確地區分開來，只有在後者真正發生的那個時間點，才真正去動用那些更加昂貴、且需要更嚴謹並行控制的機制」**的設計思路，是很多電商系統設計裡容易被忽略、但相當重要的核心原則。

**面試回答方式**：先給出核心設計原則——「核心原則是把商品的存在購物車裡，和真正保留這件商品的庫存這兩件事分開看待，把商品加入購物車這個動作本身通常不應該就立即實際去鎖定或預先扣減庫存，因為使用者可能加入購物車後很久才結帳甚至永遠不結帳，如果一加入就預先鎖定庫存，會導致大量庫存被沒有真正購買意圖的使用者長期佔用」。給出正確的處理時機——「正確做法是只有在使用者真正進入結帳流程準備實際下單的那一刻，才真正去檢查鎖定庫存，如果發現庫存不足就在結帳當下明確告知使用者調整或移除，而不是讓使用者到最後才發現下單失敗」。可以連結回之前的核心概念——「這呼應了之前討論秒殺場景時的核心原則，把使用者意圖表達和真正具備實際約束力的操作明確區分開來，只有在後者真正發生時才去動用那些更嚴謹的並行控制機制」。

### 如果這個購物車系統未來需要支援「多個不同賣場」（例如 91APP 服務不同的品牌客戶，各自經營獨立的賣場），你會怎麼設計購物車的資料結構？

**核心答案**：核心設計思路是**在購物車的資料結構裡**明確地**額外加入「賣場／商店識別碼」**這個維度——原本可能只是**「使用者 ID → 購物車內容」**這種簡單的對應關係，需要擴充成**「使用者 ID + 賣場 ID → 對應這個特定賣場的購物車內容」**，讓**同一位使用者**在**不同的賣場**能夠各自擁有**獨立、互不干擾**的購物車（例如使用者在「賣場 A」裡的購物車加入了幾件商品，和他在「賣場 B」裡的購物車內容應該是**完全獨立**的兩份不同資料，而**不會**因為是**同一位使用者**就被**錯誤地混在一起**）。

**詳細解析**：這題考察是否能**預見到 91APP 這類 SaaS 平台**特有的**多租戶（Multi-tenant）**架構需求——91APP 本質上是**同時服務眾多不同品牌客戶（各自經營獨立的賣場）**的平台，這意味著**任何一個涉及使用者資料的功能設計（不只是購物車，也包括訂單、會員資料等）**都**必須**考慮到**「這份資料是屬於哪一個具體的賣場／租戶」**這個額外的維度。如果**設計時沒有考慮到**這個多租戶的需求（例如天真地假設「一位使用者只對應一份唯一的購物車」），未來當**業務真的需要**擴展到**服務多個不同賣場**時，就會發現**原本的資料結構****沒辦法**正確地支援這種需求，需要**大幅度地重新設計、遷移**。這種**「提前預見到這類 SaaS 平台特有的多租戶架構需求，並在一開始設計時就把這個維度納入考量」**的前瞻性，正是**在 SaaS 相關公司面試**裡特別容易被用來**區分資深和資淺**候選人的關鍵能力。

**面試回答方式**：先給出核心設計思路——「核心是在購物車資料結構裡明確加入賣場或商店識別碼這個維度，原本可能只是使用者ID對應購物車內容的簡單關係，需要擴充成使用者ID加賣場ID對應這個特定賣場的購物車內容，讓同一位使用者在不同賣場能各自擁有獨立互不干擾的購物車」。可以展現對SaaS多租戶架構的前瞻理解——「這反映了91APP這類SaaS平台特有的多租戶架構需求，平台本質上是同時服務眾多不同品牌客戶各自經營獨立的賣場，任何涉及使用者資料的功能設計都必須考慮這份資料是屬於哪個具體賣場租戶這個額外維度，如果一開始設計時沒考慮到，未來業務真的需要擴展到服務多個賣場時，就會發現原本資料結構沒辦法支援，需要大幅重新設計遷移」。
