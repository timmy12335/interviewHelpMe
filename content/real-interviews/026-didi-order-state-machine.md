# 題目

「訂單狀態的管理」是滴滴這類**交易與履約流程複雜**的公司常被回報的題目（根據公開的面試經驗分享整理歸納而成，並非逐字官方紀錄）：「一筆叫車訂單會經過待接單、已接單、司機到達、行程中、已完成、已取消等狀態。如果多個來源（乘客端、司機端、系統逾時）同時想改變狀態，你會怎麼設計才不會出錯？」這題考察的是**狀態機的建模**、**併發控制**與**業務規則的落地位置**。

## 核心答案

核心是「把合法的轉移明確地定義出來，並讓所有的變更都經過同一個入口」——用一張「當前狀態 × 事件 → 新狀態」的轉移表（見 [[../design-patterns/018-state-pattern-order-machine.md]]），**而不是在各處寫 if 判斷**；表格化之後，非法的轉移在程式碼層面就無法被表達。

併發的處理靠資料庫的條件更新：`UPDATE orders SET status = '行程中' WHERE id = ? AND status = '司機已到達'`——用受影響的列數判斷是否成功；這是一個 CAS 的操作，於是兩個同時的請求只有一個會成功（見 [[../database/024-optimistic-vs-pessimistic-lock.md]]）。

而狀態變更必須產生一筆不可變的事件記錄——誰、在什麼時間、把狀態從什麼改成什麼、原因是什麼；因為訂單的爭議處理與對帳都依賴這份歷史，而只保留當前狀態會讓任何問題都無法追查。

**要特別小心的是「終態」**：已完成與已取消是終態——任何從終態出發的轉移都應該被拒絕；這一條規則能擋掉大部分的重複回呼與延遲訊息造成的問題。

## 詳細解析

「用條件更新而非先讀後寫」是這題最關鍵的實作細節：`SELECT status` 然後在應用層判斷再 `UPDATE`——在兩個請求同時進來時，兩者都會讀到舊狀態並都認為可以更新；而把條件放進 UPDATE 的 WHERE 子句，讓資料庫的行鎖保證了只有一個會成功。這個模式不需要額外的分散式鎖，效能也更好——在面試中能主動指出「這裡不需要分散式鎖」，通常比提出一個複雜的鎖方案更能得分。

「逾時與外部回呼是狀態機最大的挑戰」：支付回呼可能延遲十分鐘才到——而那時訂單可能已經被系統逾時取消了；所以每個外部事件的處理都要先檢查當前狀態是否還能接受它，而不能假設事件會按預期的順序到達。這正是「終態拒絕所有轉移」這條規則存在的原因。

**「狀態的數量要克制」**：把每一個細微的業務差異都變成一個新狀態——轉移表會爆炸成無法維護的規模；更好的做法是「用較少的主狀態加上若干個獨立的標記」（例如「已完成」加上「是否已評價」「是否已開發票」這些布林欄位），因為那些標記彼此獨立而不該進入狀態機。

「補償與人工介入的路徑要預留」：真實的系統一定會出現卡在某個狀態的訂單——司機失聯、支付系統故障、資料不一致；所以需要一個受權限控制的管理介面能強制轉移狀態並記錄操作者，否則客服只能請工程師改資料庫，那既慢又危險。

## 面試回答方式

先給核心做法（**轉移表加上單一入口**）與併發的處理（**資料庫的條件更新**），再強調**事件記錄**與**終態**這兩條規則。加分點有四個：**用條件更新而非先讀後寫**，**而這裡不需要分散式鎖**；逾時與外部回呼是最大的挑戰——不能假設事件按預期順序到達；**狀態的數量要克制**，**獨立的標記不該進入狀態機**；以及補償與人工介入的路徑要預留。

## 講稿

核心是把合法的轉移明確定義出來，並且讓所有變更經過同一個入口。我會用一張當前狀態乘上事件對應到新狀態的轉移表，而不是在各處寫 if 判斷。表格化之後，非法的轉移在程式碼層面就無法被表達。

併發我會用資料庫的條件更新。更新的時候在 WHERE 裡帶上預期的舊狀態，用受影響的列數判斷成功與否。這是一個 CAS 操作，兩個同時的請求只有一個會成功。

這裡我想特別說一點，這個做法不需要額外的分散式鎖，效能也更好。如果先讀出狀態再在應用層判斷，兩個請求會同時讀到舊值並都認為可以更新。

而狀態機最大的挑戰其實是逾時跟外部回呼。支付回呼可能延遲十分鐘才到，那時訂單可能已經被系統取消了。所以每個外部事件都要先檢查當前狀態能不能接受它，不能假設事件會按預期順序到達。

另外已完成跟已取消是終態，任何從終態出發的轉移都拒絕。這一條能擋掉大部分重複回呼造成的問題。

## 常見追問

### 如果狀態機的規則很複雜，是不是該用工作流引擎？

**核心答案**：看規則的變化頻率與是否需要非工程師調整。如果狀態轉移是穩定的技術流程——用程式碼裡的轉移表最簡單也最好維護；而如果流程經常變動、需要視覺化、或者需要營運人員自行調整（例如審批流程），那工作流引擎的投資才划算。

**詳細解析**：這考察「不要為了架構的漂亮而引入不必要的元件」這個判斷——工作流引擎帶來的是額外的部署、學習成本、以及除錯時要跨越兩套系統的困難；而多數的訂單狀態機其實只有十幾種轉移，用一張表加上單元測試就能覆蓋得很好。判斷的具體問題是「過去一年這個流程改過幾次，是誰要求改的」——如果是每季由營運提出的變更，引擎有價值；如果一年才改一次而且是工程需求，那就不需要。這種「用實際的變更頻率決定抽象程度」的思路，比抽象地討論方案優劣更能展現工程判斷。

**面試回答方式**：給判準（規則的變化頻率與是否需要非工程師調整）並各給對應的選擇。核心加分點是誠實列出工作流引擎的成本（部署、學習、跨系統除錯）與多數訂單狀態機只有十幾種轉移這個現實。收在具體的判斷問題：過去一年這個流程改過幾次、是誰要求改的——用實際的變更頻率決定抽象程度。

### 訂單量很大時，狀態變更的歷史怎麼儲存？

**核心答案**：**分開儲存並分級保留**。當前狀態放在訂單主表（高頻讀寫）——而變更歷史寫進一張只追加的事件表，並按時間分區（見 [[../database/046-partitioning.md]]）；熱資料保留在資料庫，超過一定期限的歸檔到成本更低的儲存（物件儲存或資料倉儲）。

**詳細解析**：這考察「不同存取模式的資料應該分開儲存」這個原則——訂單主表需要低延遲的點查與更新，而歷史記錄是只寫不改、偶爾按訂單 ID 查詢的；混在一起會讓主表膨脹並拖慢核心的查詢。而按時間分區的好處在於「歸檔變成一個 DDL 操作而非大量的刪除」——直接卸載舊分區，比 `DELETE WHERE created_at < ?` 快好幾個數量級且不會產生大量的 undo log（見 [[../database/026-undo-log.md]]）。這個「用分區讓資料的生命週期管理變便宜」的技巧，是大表設計時應該一開始就考慮的；**事後再加分區的成本高得多。**

**面試回答方式**：給做法（主表與事件表分開、按時間分區、分級歸檔）並說明兩者的存取模式不同。核心加分點是**按時間分區讓歸檔變成 DDL 操作**——比大量 DELETE 快好幾個數量級且不產生大量 undo log。收在建議：這應該在大表設計時一開始就考慮，事後再加分區的成本高得多。

### 怎麼確保狀態機的邏輯有被完整測試？

**核心答案**：**用轉移表本身生成測試**。既然合法的轉移是一張表——就可以自動地產生「所有非法的組合都應該被拒絕」這組測試；而合法的轉移則逐一驗證副作用（是否發出了對應的事件、是否更新了正確的欄位）。這種由資料驅動的測試，覆蓋率遠高於手寫個案。

**詳細解析**：這考察**「把規格變成可執行的東西」**這個工程習慣——如果轉移表是唯一的真實來源，那測試、程式碼與文件都可以從它生成；**於是三者不可能不同步**。具體的做法是遍歷所有的「狀態 × 事件」組合，對不在表中的組合斷言會拋出錯誤——這通常是幾十行的測試碼卻覆蓋了數百個組合。而它的額外價值是「新增一個狀態時，測試會立刻告訴你哪些組合還沒被考慮」；這把「有沒有想到所有情況」這個靠人記憶的問題，變成了一個機器會提醒你的問題。

**面試回答方式**：給做法（用轉移表生成測試，非法組合全部斷言被拒絕）並說明它的覆蓋率高於手寫個案。核心加分點是點出這是**「把規格變成可執行的東西」**——轉移表作為唯一真實來源，測試、程式碼與文件不可能不同步，並給出實際的規模（幾十行測試覆蓋數百個組合）。收在額外價值：新增狀態時測試會立刻指出哪些組合還沒考慮，把靠人記憶的問題變成機器會提醒的問題。
