# 題目

這是台灣許多**中小型新創公司**（電商、SaaS、O2O 服務等）在後端工程師面試裡**相當常見**的實作導向題（根據公開面試經驗分享整理歸納而成，並非逐字官方紀錄）：**「請用 Spring Boot 設計一組管理使用者訂單的 RESTful API，包含查詢、建立、取消訂單，並說明你的 API 設計考量」**新創公司的面試風格通常**不像大廠那樣追問到極深的底層原理**，而是更重視**你是否能快速、實際地把一個功能設計並落地**。

## 核心答案

一組，**符合RESTful原則**的訂單API，設計大致會是——**(1) `GET /orders`**：查詢，目前使用者的訂單列表(需要，考慮分頁參數)；**(2) `GET /orders/{orderId}`**：查詢，單一筆訂單的詳細內容；**(3) `POST /orders`**：建立一筆新訂單；**(4) `PATCH /orders/{orderId}`或`DELETE /orders/{orderId}`**：取消訂單(用，狀態變更的方式標記取消而**不是**真的把這筆訂單從資料庫刪除)。設計時需要考量幾個，核心原則(見 [[../backend-engineering/001-restful-api-design.md]])——**用，恰當的HTTP方法**(GET用於查詢、POST用於建立、PATCH用於部分更新)、**用，恰當的HTTP狀態碼**(200成功、201建立成功、404找不到資源、400請求格式錯誤)、以及，**「取消訂單」這個操作，本身應該要是冪等的**(見 [[../backend-engineering/003-idempotency-design.md]])——重複呼叫同一個，「取消訂單」請求，好幾次結果都應該是，一致的(這筆訂單，最終就是，處於「已取消」狀態，而不會因為重複呼叫而出現任何，額外的副作用)。

## 詳細解析

**「取消訂單」為什麼，用PATCH或狀態變更，而不是，真的DELETE：這反映了，你，對業務本質的理解**：這，是這題一個，很好的**加分細節**——很多，**經驗較，不足**的候選人，可能會直覺地認為「取消訂單」就應該對應`DELETE`,這個HTTP方法，但**真正理解，電商/訂單業務**的工程師，會，指出——**「訂單，一旦被取消通常並不會真的從系統裡徹底消失」**因為**業務上**很可能還需要**保留這筆，已取消訂單的完整紀錄**(用於，**財務對帳、客訴查詢、數據分析**等目的)，因此，**更恰當**的做法，是，**只是把，這筆訂單的狀態欄位，更新成「已取消」**，而**不是**真的執行，資料庫層級的刪除操作，這種**「用狀態變更取代，真正的刪除」**的設計，某種程度上，也呼應了，**軟刪除(Soft Delete)**這個，常見的資料庫設計模式，這種能夠**主動地展現你對，實際業務情境的理解，而不是只機械式地套用，HTTP方法的字面意義**的回答方式，正是讓面試官判斷你是否具備**實務，產品開發經驗**的關鍵細節。

**新創公司面試，特有的追問方向——會，更關心你是否考慮到，實際的維運和擴充性**：相較於，大廠(尤其是，中國大廠那種，追問底層原理到極致)的面試風格，**台灣新創公司**,的面試官更，常見的追問方向，是，**「這個API，設計未來如果需要擴充，新功能(例如，訂單需要支援部分退貨)會不會很難修改？」**或者**「如果，這個API，同時被好幾個，不同的前端(網頁版、App版)使用，你會怎麼設計避免，重複的邏輯」**這类，**更貼近，實際團隊協作和產品迭代**的問題——這，反映了新創公司**團隊規模通常較小、資源相對有限**這個，現實——他們，特別需要**能夠快速迭代、但又不會因為求快而讓系統變得，難以維護**的工程師，建議回答時主動提到**你會如何設計讓，這組API，具備，合理的擴充性**(例如，用，恰當的資料傳輸物件DTO，讓API，的請求/回應格式，和，內部的資料庫結構，保持，一定程度的解耦)。

**API，版本控制——如果，未來需要調整，這組API，的格式你會怎麼處理才不會影響到，既有的使用者？**：這是另一個值得主動，提到的考量——實務上，一個已經上線，運作的API，**未來幾乎必然**會遇到**需要調整，格式或行為**的情況，如果**直接修改，既有的API**，可能會讓**目前正在使用，舊版本格式**的使用者(例如，還沒更新到，最新版本的手機App)，**突然收到，不相容的回應格式**，而出現錯誤因應這種情況，常見的做法，是**引入，API版本控制**(見 [[../backend-engineering/002-api-versioning.md]])例如，在網址裡加入版本號(`/v1/orders`、`/v2/orders`)讓**新舊版本**能夠**同時並存**給使用者，足夠的時間，逐步遷移到新版本而不是**強迫，所有使用者**，在**同一時間**都必須立即更新。

## 面試回答方式

先給出具體的API端點設計——「GET /orders查詢訂單列表(考慮分頁)、GET /orders/{orderId}查詢單一訂單詳情、POST /orders建立新訂單、PATCH或DELETE /orders/{orderId}取消訂單」。給出核心設計原則——「用恰當的HTTP方法對應語意、用恰當的HTTP狀態碼、以及取消訂單這個操作本身應該要是冪等的，重複呼叫同一個取消請求好幾次結果都應該一致」。一定要主動點出取消訂單不是真的刪除這個展現業務理解的細節——「取消訂單通常不會真的從系統刪除，因為業務上很可能還需要保留這筆已取消訂單的完整紀錄用於財務對帳客訴查詢，更恰當的做法是只把狀態欄位更新成已取消，這是軟刪除這個常見資料庫設計模式的展現」。可以主動提到API版本控制的考量——「實務上已上線的API未來幾乎必然會遇到需要調整格式的情況，如果直接修改既有API可能影響正在使用舊版本的使用者，因應做法是引入API版本控制，讓新舊版本能同時並存，給使用者足夠時間逐步遷移」，展現你不只是懂RESTful原則的字面規則，更具備實際業務理解和產品迭代維護的完整工程視野。

## 常見追問

### 如果，「建立訂單」這個API,`POST /orders`因為網路問題前端不確定這次請求究竟有沒有成功送達於是，前端自動重試了，同一個請求，你會怎麼避免，因此，建立出兩筆，重複的訂單？

**核心答案**：這，正是前面(見 [[011-cathay-payment-idempotency.md]])已經，深入討論過的**冪等性設計**核心概念的直接應用——解法，是讓**前端**在**第一次發起，這個建立訂單請求時**，額外地**附帶一個，唯一的冪等性金鑰(Idempotency Key)**，後端在**真正，建立訂單之前**，先**檢查這個金鑰是否已經被處理過**如果是，**重複的請求(相同的金鑰)**，直接回傳**第一次已經，成功建立的那筆訂單**的資訊，而**不會**再真的建立，第二筆重複訂單。

**詳細解析**：這題，考察是否能把前面(見 [[011-cathay-payment-idempotency.md]])已經，深入討論過的支付冪等性設計，**遷移應用到，這個，新的、看似不同的具體API設計場景**——「建立訂單」和「支付扣款」，表面上是，**不同的業務操作**，但它們**共享，相同的核心風險**——**「一個，涉及實際，副作用(建立一筆，實際存在的訂單紀錄)的操作，可能因為網路重傳而被意外執行超過一次」**只要能**識別出這種，共通的根本風險**，就能看出**同一套，冪等性設計的解法**，同樣適用於這裡這也再次印證了這篇文章反覆，強調的核心價值——**能夠，識別出不同具體場景背後，共享的相同根本模式，而不是把每一個，新的具體情境，都當作一個需要重新思考解法，的全新問題**。

**面試回答方式**：先給出核心答案——「這是冪等性設計的直接應用，讓前端在第一次發起建立訂單請求時附帶一個唯一的冪等性金鑰，後端在真正建立訂單前先檢查這個金鑰是否已被處理過，如果是重複請求就直接回傳第一次已成功建立的訂單資訊，而不會再建立第二筆重複訂單」。可以主動連結到之前的核心概念——「建立訂單和支付扣款表面上是不同業務操作，但共享相同核心風險——一個涉及實際副作用的操作可能因網路重傳而被意外執行超過一次，只要識別出這種共通根本風險，就能看出同一套冪等性設計解法同樣適用」。

### 如果，這個訂單系統，未來需要同時支援，「網頁版」和「手機App版」這，兩個不同的前端，你會怎麼設計讓，同一組API，可以同時服務這兩個，不同的前端？

**核心答案**：**核心原則，是讓API的設計保持,『前端無關(Frontend-agnostic)』**——也就是，**這組API，的請求/回應格式**，不應該**為某一個，特定的前端(例如，只考慮，網頁版的顯示需求)**，去做客製化設計而應該設計成**一套，通用、標準化，的資料格式**，讓**任何前端**都能依照，自己實際的呈現需求，去**自行解讀、組織這些，標準化的資料**，如果，**不同的前端**，真的存在**顯著，不同**的資料需求(例如，App版可能需要**更精簡的資料**以節省，行動網路流量)，可以考慮**額外地設計，不同的API端點，或者允許透過查詢參數去客製化，回傳的欄位**，而**不是**讓，**同一個API**，去**內建判斷『這個請求是從哪個前端，發出的』**這種，邏輯。

**詳細解析**：這題，考察是否理解，**後端API，和，前端呈現邏輯，之間應該保持，恰當的關注點分離(Separation of Concerns)**——如果，**後端的API**，內建了**「針對不同前端客製化，回應格式」**這種，邏輯會導致**後端程式碼****混雜了**，**「不屬於後端，應該負責」**的**前端呈現邏輯**，讓**後端程式碼**變得**更加複雜、更加難以維護**(例如未來如果**新增，第三個前端**，可能就需要回頭**修改這個已經混雜著，多種前端邏輯**的後端API)，一個**設計得更加，乾淨**的架構，應該是**讓後端只負責提供，標準化、通用的資料**，而**把『如何依照，不同前端的呈現需求，去組織，呈現這些資料』**這個，責任**交還給前端自己**去處理這種**「明確地劃分好不同層次各自應該，負責的職責範圍」**的思路，是設計任何**需要同時服務多個，不同呈現端**的系統時，都值得反覆，套用的核心架構原則。

**面試回答方式**：先給出核心設計原則——「核心原則是讓API保持前端無關，這組API的請求回應格式不應該為某個特定前端做客製化設計，而應該設計成一套通用標準化的資料格式，讓任何前端都能依照自己實際呈現需求去自行解讀組織這些資料」。給出處理顯著差異需求的做法——「如果不同前端真的存在顯著不同的資料需求，例如App版需要更精簡資料以節省行動網路流量，可以考慮額外設計不同API端點或允許透過查詢參數客製化回傳欄位，而不是讓同一個API內建判斷這個請求是從哪個前端發出的邏輯」。可以總結核心架構原則——「這反映了後端API和前端呈現邏輯之間應該保持恰當的關注點分離，明確劃分好不同層次各自應該負責的職責範圍，是設計任何需要同時服務多個不同呈現端系統時值得反覆套用的核心架構原則」。

### 如果，主管要求你，這組訂單API，需要額外考慮「安全性」你會特別注意哪些面向？

**核心答案**：核心的安全考量，包括——**(1) 身份驗證(Authentication)**：確認，這個，發起請求的使用者，究竟是誰(通常透過見 [[../backend-engineering/004-jwt-authentication.md]]已經，深入討論過的JWT，或者，類似機制)；**(2) 授權(Authorization)**：即使，確認了，使用者身份，還需要額外檢查，**這位使用者，是否有權限去，查詢或操作，這一筆，特定的訂單**(這，是一個很容易被，忽略的細節——需要，明確地檢查「這筆訂單是不是真的屬於這位，發起請求的使用者」，而**不是**只要使用者**通過了身份驗證**就允許他查詢，任何一筆訂單，即使那筆訂單是屬於別人的)；**(3) 輸入驗證**：對，所有，前端傳入的資料，做，嚴謹的格式和合理性驗證，避免，惡意或不合法的輸入。

**詳細解析**：這題，考察是否理解，**「身份驗證」**和**「授權」**，是**兩個容易被，混為一談、但，實際上，是，不同層次**的安全考量——**身份驗證**，回答的是**「你是誰？」**這個問題；而**授權**回答的是**「即使我知道你是誰你是否有權限去做這件，具體的事情？」**這個，更進一步的問題——這題，最容易被忽略、也最容易出現，實際安全漏洞的地方，正是**「只做了身份驗證，卻忘記額外做，授權檢查」**這種，情況——舉例來說，如果，一個API，只檢查了**「這個請求是否帶著一個，合法有效的登入憑證」**，卻**沒有進一步檢查****「這位已經，通過身份驗證的使用者，是否真的有權限去查詢這一筆，特定的訂單」**，就可能導致**「使用者A透過修改，網址裡的訂單編號**，去**查詢到原本屬於使用者B，的訂單資訊」**這種，**相當常見、也相當，嚴重**的實際安全漏洞(這種，漏洞在資安領域有一個，專門的名稱，稱為，**「不安全的直接物件參照(Insecure Direct Object Reference, IDOR)」**)。

**面試回答方式**：先給出三個核心安全考量——「身份驗證確認發起請求的使用者是誰(通常透過JWT);授權則是即使確認身份後，還要額外檢查這位使用者是否有權限查詢或操作這一筆特定訂單;輸入驗證則是對所有傳入資料做嚴謹格式和合理性驗證」。一定要深入解釋身份驗證和授權的區別，並點出常見漏洞——「身份驗證回答的是你是誰這個問題，授權回答的是即使知道你是誰，你是否有權限做這件具體事情這個更進一步的問題，最容易被忽略也最容易出現實際安全漏洞的地方，正是只做了身份驗證卻忘記額外做授權檢查，例如只檢查請求是否帶著合法登入憑證，卻沒進一步檢查這位使用者是否真的有權限查詢這一筆特定訂單，可能導致使用者A透過修改網址裡的訂單編號查詢到原本屬於使用者B的訂單資訊，這種漏洞在資安領域有個專門名稱叫做不安全的直接物件參照IDOR」。
