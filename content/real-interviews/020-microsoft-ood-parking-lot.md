# 題目

「Design a Parking Lot」是 Microsoft（以及同類型重視**物件導向設計（Object-Oriented Design, OOD）**能力的歐美科技公司）面試裡**經典**的 OOD 題目（根據公開面試經驗分享整理歸納而成，並非逐字官方紀錄）：**「請用物件導向的方式設計一個停車場管理系統，需要支援不同大小的車輛（機車、汽車、大型車）、不同的停車位類型，並能計算停車費用」**這題**不像**前面（見 [[017-google-url-shortener-system-design.md]]、[[018-meta-newsfeed-system-design.md]]）討論過的 System Design 題那樣重視**大規模分散式架構**，而是考察**你是否能用恰當的類別（Class）設計、繼承、介面**，把一個真實世界的業務邏輯**乾淨地建模出來**。

## 核心答案

核心的類別設計，大致，包含——**(1) `Vehicle`(車輛)**：作為，一個**抽象基礎類別或介面**，定義「車輛」共通，具備的屬性(車牌號碼、車輛類型)，再由**`Motorcycle`(機車)、`Car`(汽車)、`Truck`(大型車)**這幾個,**具體子類別**，去繼承並各自定義**自己，特有的屬性**(例如，大小不同)；**(2) `ParkingSpot`(停車位)**：同樣，可以設計成，**不同大小(機車位、標準汽車位、大型車位)**，每一個停車位需要知道**「自己目前是否，被佔用、目前，停的是，哪一台車」**；**(3) `ParkingLot`(停車場)**：**整合，管理**，所有的停車位，提供**「幫某台車找到一個，可用的停車位」、「這台車，離開時計算應該，收取的費用」**這些，核心功能；**(4) `Ticket`(停車票證)**：記錄，**「這台車是什麼時候進場的」**用來在**離場時**計算，停留的時間、進而，計算費用。設計時，**核心的物件導向原則**，是**「讓不同種類的車輛、不同種類的停車位，各自的差異行為，透過繼承和多型(Polymorphism)，自然地被表達出來而不是在單一個，巨大的函式裡，用大量的if-else，去判斷各種，不同的情況」**。

## 詳細解析

**為什麼要用「繼承」而不是，單一個類別加上大量欄位去區分車輛類型——這反映了，物件導向設計的核心價值**：這，是這題，最核心的考點——一個，**經驗較，不足**的候選人，可能會設計成**「只有，一個單一的`Vehicle`類別裡面有一個`type`欄位(用，字串或enum，表示，是機車還是汽車)，再在，程式裡的各個地方**，用**`if (vehicle.type == "car") {...} else if (vehicle.type == "motorcycle") {...}`**這種判斷邏輯去因應，不同車型的差異」——這種做法，雖然**短期內也能運作**，但會導致**「每當新增一種，全新的車輛類型(例如，未来需要支援電動車或自行車)」**就**需要回頭去修改****每一個曾經寫過，這種if-else判斷**的地方，這違反了，**物件導向設計，裡，重要的『開放封閉原則(Open-Closed Principle)』**——**「應該，對擴充開放，但對修改，封閉」**——透過，**用繼承和多型**讓**每一種，具體的車輛子類別**，各自定義，**自己特有的行為**(例如，`Car`和`Motorcycle`各自覆寫「這台車佔用的停車位，大小需求」這個方法)，未來**新增一種，全新的車輛類型**時，只需要**新增一個，新的子類別**，而**不需要**去**修改任何，既有的程式碼**。

**Microsoft，和其他歐美科技公司，考OOD題，想，看到的核心能力——你，是否能把，模糊的業務需求，轉化成，具體、乾淨的類別結構**：這类，**OOD題**，某種程度上，考察的是**和前面已經，討論過的System Design題，不同的能力面向**——System Design，考察的是**「大規模，分散式架構，的權衡取捨」**；而**OOD題**考察的是**「面對一個相對單機、但涉及眾多，不同種類物件、彼此關係複雜的業務邏輯**，你是否能用，**物件導向的思維**，去把這種複雜性妥善地拆解、建模讓，最終寫出來的程式碼，**具備良好的可讀性、可維護性、可擴充性**」——面試官，通常會**特別關注**你，設計的類別之間的**關係**——「這，兩個類別之間是，繼承關係、還是，組合(Composition)關係？」、「這個功能應該被放在，哪一個類別裡，才合理？」這種**「合理地劃分，職責、設計清楚的類別關係」**的能力，正是這类OOD題真正想要，考察的核心。

**這題也可以延伸出，設計模式的討論——例如，「找，可用停車位」這個功能，可以套用，什麼設計模式？**：這題**進一步延伸**經常會涉及，**具體的設計模式**討論——例如，**「不同大小的停車位對應，不同的收費策略(機車，和汽車每小時的費率不同)」**這個需求可以**套用，策略模式(Strategy Pattern)**——把，**「計算費用」**這個，行為抽象成一個，獨立的**策略介面**，讓**不同的收費規則**，各自實作這個介面`ParkingLot`系統可以**在執行時動態地選用，恰當的收費策略**，而**不需要**把，**「不同車型的收費邏輯」**，寫死在單一個，龐大的計算函式裡——這種，**「用具體的設計模式，去因應某種，特定的擴充彈性需求」**的思考，是**OOD面試，裡展現更深，技術功力**的加分環節(但，**不是**，每一次OOD面試，都一定需要主動提到，具體的設計模式名稱，重點依然是，**你的類別設計，本身是否，乾淨、合理**)。

## 面試回答方式

先給出核心類別設計——「Vehicle作為抽象基礎類別或介面，定義車輛共通屬性，再由Motorcycle、Car、Truck這些具體子類別繼承並定義各自特有屬性;ParkingSpot設計成不同大小，知道自己是否被佔用;ParkingLot整合管理所有停車位，提供找可用車位和計算離場費用這些核心功能;Ticket記錄進場時間用來計算停留時長和費用」。一定要主動解釋為什麼用繼承而非單一類別加if-else——「如果只用一個類別加type欄位配合大量if-else判斷去區分車型，未來新增一種全新車輛類型就需要回頭修改每個曾經寫過這種判斷的地方，這違反了開放封閉原則——應該對擴充開放但對修改封閉，透過繼承和多型讓每種具體車輛子類別各自定義自己特有行為，未來新增車型只需要新增一個新子類別，而不需要修改任何既有程式碼」。可以補充展現和System Design題目的核心能力差異——「OOD題考察的是面對一個相對單機、但涉及眾多不同種類物件彼此關係複雜的業務邏輯，是否能用物件導向思維妥善拆解建模，讓最終程式碼具備良好可讀性可維護性可擴充性」。可以延伸提到設計模式，例如策略模式應用在不同收費規則上，展現更深的技術功力，但強調重點依然是類別設計本身是否乾淨合理。

## 常見追問

### 如果，這個停車場，需要額外支援「電動車，充電位」這種，新的停車位類型(除了，能停車還能額外充電可能有，不同的計費方式)，你會怎麼調整你的設計才能最不影響，既有的程式碼？

**核心答案**：如果，前面已經正確地用，**繼承和多型**，去設計了，**停車位**這個類別體系(而，**不是**用單一個巨大類別加上，大量if-else)，新增，「電動車充電位」這個，新類型只需要**新增一個，新的子類別(例如,`ElectricChargingSpot`)**讓它繼承自，原本的停車位基礎類別，並**額外地覆寫或擴充**它，**特有的行為**(例如，額外的充電功能、額外的計費邏輯)——這種做法，能夠**完全不需要去修改****任何既有已經寫好、且，正常運作**的程式碼，這正是，前面(見 核心答案和詳細解析)已經，深入討論過的**開放封閉原則**，**具體，發揮效用**的實際展現。

**詳細解析**：這題，是一個**直接驗證**前面已經，提到的架構設計原則，是否真的，經得起考驗的**具體測試情境**——如果，你一開始，的類別設計，確實是**恰當地**運用了，**繼承和多型**，這種**「新增一種全新類型**只需要**新增一個，新的子類別**，而**完全不需要**去**修改任何，既有程式碼**」的效果，就會**自然而然，發生**——這，某種程度上，也是面試官透過**這種追問**去**驗證**你前面，给出的設計，是不是**真的經得起考驗、真的具備，良好的擴充性**，而**不是****表面上看起来用了繼承，但實際上，依然隱藏著大量難以，擴充的問題**。

**面試回答方式**：先給出核心答案——「如果前面已經正確用繼承和多型設計了停車位類別體系，新增電動車充電位這種新類型，只需要新增一個新子類別繼承自原本的停車位基礎類別，並額外覆寫或擴充它特有的行為(如充電功能和計費邏輯)，完全不需要修改任何既有已經寫好且正常運作的程式碼」。可以總結這是對之前設計的驗證——「這是直接驗證前面架構設計原則是否真的經得起考驗的具體測試情境，如果一開始的類別設計確實恰當運用了繼承和多型，這種新增類型只需新增子類別、不需修改既有程式碼的效果就會自然發生」。

### 如果，「找一個，可用的停車位」這個功能，需要考慮「盡量幫小型車輛優先分配到離出入口，較近的停車位，以提升，整體的停車效率」這種，更複雜的分配策略，你會怎麼設計讓這種分配邏輯能方便地被，調整、替換？

**核心答案**：這裡，適合套用，**策略模式(Strategy Pattern)**——把，**「如何決定要分配哪一個，具體停車位，给，這台車」**這個，決策邏輯抽象成一個，**獨立的『停車位分配策略』介面**，`ParkingLot`本身只負責**呼叫這個策略介面**去取得**「應該分配，哪一個停車位」**這個，決策結果而**不需要**自己內部去寫死，**具體的分配邏輯**——之後，如果**業務需求**需要**調整，分配策略**(例如，改成「優先把，最靠近電梯的位置，留給行動不便人士」)只需要**替換或新增一個，新的策略實作**，而**不需要**去動到`ParkingLot`本身，的核心邏輯。

**詳細解析**：這題，考察是否能**識別出****「當某個，具體的業務邏輯(如，分配策略)未來很可能需要被頻繁地，調整、替換」**這個，信號時應該**主動地把這部分邏輯額外抽象成一個，獨立的介面**，而**不是**把這種**「可能需要，經常變動」**的邏輯，**直接寫死**在，**核心的業務類別**裡——這種，**「識別出系統裡哪些部分是，相對穩定、哪些部分，則可能經常需要被調整替換並針對後者額外地做，抽象化、介面化的設計」**的判斷能力，是**物件導向設計裡，運用設計模式時真正，核心的思考依據**(而，不是**單純地把，設計模式的名稱，死记硬背下来**，卻**不理解，什麼情況下，才真正適合套用哪一個，具體的設計模式**)。

**面試回答方式**：先給出核心答案——「這裡適合套用策略模式，把如何決定分配哪個具體停車位這個決策邏輯，抽象成一個獨立的停車位分配策略介面，ParkingLot本身只負責呼叫這個策略介面取得決策結果，而不需要自己內部寫死具體的分配邏輯，之後如果業務需求需要調整分配策略，只需要替換或新增一個新的策略實作，而不需要動到ParkingLot本身的核心邏輯」。可以總結核心判斷依據——「這反映了識別出系統裡哪些部分相對穩定、哪些部分可能經常需要被調整替換，並針對後者額外做抽象化介面化設計這個核心思考依據，而不是單純死記硬背設計模式的名稱，卻不理解什麼情況下才真正適合套用哪個具體設計模式」。

### 如果，面試官繼續追問「如果，這個停車場，系統需要支援多個，不同的實體停車場(每一個，實體停車場，各自有，自己的收費標準)，你的設計需要怎麼調整？」你會怎麼回答？

**核心答案**：需要，額外地**引入一個，更高層次的抽象**——例如，一個**`ParkingLotChain`(或者`ParkingFacilityManager`)**這種**「管理多個，獨立ParkingLot，實例」**的更高層類別，**每一個獨立的`ParkingLot`實例**各自**擁有，自己的一套，停車位集合、以及，自己，獨立的收費策略**(這，正是前面(見 核心答案)已經，提到的策略模式，能夠發揮作用的地方——**不同的停車場實例**，可以**各自注入，不同的收費策略實作**)，這種**「讓同一套，核心的類別設計(`ParkingLot`、`ParkingSpot`等)能夠被多個，獨立的實例**，各自依照，自己的具體設定，重複使用」的思路，正是物件導向設計裡，**良好的封裝和抽象**，帶來的核心效益——**核心的類別邏輯，只需要被設計、實作一次**之後就能**透過建立，不同的物件實例、給，予，不同的初始設定**，去**因應多種，不同的具體使用情境**。

**詳細解析**：這題，考察是否理解，**「良好的物件導向設計」**，之所以**具備價值**核心原因正是，**「核心的類別邏輯，只需要被正確地，設計、實作一次，之後就能透過建立多個各自獨立、可以分别，客製化設定的物件實例**，去重複地應用在**多種，不同的具體場景**」，這種**「一套設計，多处複用」**的能力，正是**物件導向程式設計**相較於**「每次遇到略微，不同的需求，就重新寫一套，全新的、彼此，獨立、無法共用**的程式碼」，所带来的核心效益——如果，你**一開始**就把`ParkingLot`設計成**一個可以被多次建立、且每次建立時能接受，不同初始設定(如，不同的收費策略)的類別**，**「支援多個，不同的實體停車場」**這個，**看似是，全新需求**的功能，實際上，**幾乎不需要**任何額外，的架構調整，就能被自然地滿足。

**面試回答方式**：先給出核心答案——「需要額外引入一個更高層次的抽象，例如ParkingLotChain這種管理多個獨立ParkingLot實例的更高層類別，每個獨立的ParkingLot實例各自擁有自己的停車位集合和獨立的收費策略，這正是之前提到的策略模式能發揮作用的地方——不同停車場實例可以各自注入不同的收費策略實作」。可以總結物件導向設計的核心價值——「這反映了良好物件導向設計的核心價值，核心類別邏輯只需要被正確設計實作一次，之後就能透過建立多個各自獨立、可以分別客製化設定的物件實例，去重複應用在多種不同的具體場景，如果一開始就把ParkingLot設計成可以被多次建立且每次接受不同初始設定的類別，支援多個實體停車場這個看似全新的需求，實際上幾乎不需要任何額外架構調整就能被自然滿足」。
