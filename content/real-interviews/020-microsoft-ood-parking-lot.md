# 題目

「Design a Parking Lot」是 Microsoft（以及同類型重視**物件導向設計（Object-Oriented Design, OOD）**能力的歐美科技公司）面試裡**經典**的 OOD 題目（根據公開面試經驗分享整理歸納而成，並非逐字官方紀錄）：**「請用物件導向的方式設計一個停車場管理系統，需要支援不同大小的車輛（機車、汽車、大型車）、不同的停車位類型，並能計算停車費用」**這題**不像**前面（見 [[017-google-url-shortener-system-design.md]]、[[018-meta-newsfeed-system-design.md]]）討論過的 System Design 題那樣重視**大規模分散式架構**，而是考察**你是否能用恰當的類別（Class）設計、繼承、介面**，把一個真實世界的業務邏輯**乾淨地建模出來**。

## 核心答案

核心的類別設計大致包含——**(1) `Vehicle`（車輛）**：作為一個**抽象基礎類別或介面**，定義「車輛」共通具備的屬性（車牌號碼、車輛類型），再由 **`Motorcycle`（機車）、`Car`（汽車）、`Truck`（大型車）**這幾個**具體子類別**去繼承，並各自定義**自己特有的屬性**（例如大小不同）；**(2) `ParkingSpot`（停車位）**：同樣可以設計成**不同大小（機車位、標準汽車位、大型車位）**，每一個停車位需要知道**「自己目前是否被佔用、目前停的是哪一台車」**；**(3) `ParkingLot`（停車場）**：**整合管理**所有的停車位，提供**「幫某台車找到一個可用的停車位」、「這台車離開時計算應該收取的費用」**這些核心功能；**(4) `Ticket`（停車票證）**：記錄**「這台車是什麼時候進場的」**，用來在**離場時**計算停留的時間、進而計算費用。設計時**核心的物件導向原則**是**「讓不同種類的車輛、不同種類的停車位各自的差異行為，透過繼承和多型（Polymorphism）自然地被表達出來，而不是在單一個巨大的函式裡用大量的 if-else 去判斷各種不同的情況」**。

## 詳細解析

**為什麼要用「繼承」而不是單一個類別加上大量欄位去區分車輛類型——這反映了物件導向設計的核心價值**：這是這題最核心的考點——一個**經驗較不足**的候選人可能會設計成**「只有一個單一的 `Vehicle` 類別，裡面有一個 `type` 欄位（用字串或 enum 表示是機車還是汽車），再在程式裡的各個地方**用 **`if (vehicle.type == "car") {...} else if (vehicle.type == "motorcycle") {...}`** 這種判斷邏輯去因應不同車型的差異」——這種做法雖然**短期內也能運作**，但會導致**「每當新增一種全新的車輛類型（例如未來需要支援電動車或自行車）」**就**需要回頭去修改每一個曾經寫過這種 if-else 判斷**的地方，這違反了**物件導向設計裡重要的『開放封閉原則（Open-Closed Principle）』**——**「應該對擴充開放，但對修改封閉」**——透過**用繼承和多型**，讓**每一種具體的車輛子類別**各自定義**自己特有的行為**（例如 `Car` 和 `Motorcycle` 各自覆寫「這台車佔用的停車位大小需求」這個方法），未來**新增一種全新的車輛類型**時只需要**新增一個新的子類別**，而**不需要**去**修改任何既有的程式碼**。

**Microsoft 和其他歐美科技公司考 OOD 題想看到的核心能力——你是否能把模糊的業務需求轉化成具體、乾淨的類別結構**：這類 **OOD 題**某種程度上考察的是**和前面已經討論過的 System Design 題不同的能力面向**——System Design 考察的是**「大規模分散式架構的權衡取捨」**；而 **OOD 題**考察的是**「面對一個相對單機、但涉及眾多不同種類物件、彼此關係複雜的業務邏輯，你是否能用物件導向的思維去把這種複雜性妥善地拆解、建模，讓最終寫出來的程式碼具備良好的可讀性、可維護性、可擴充性」**——面試官通常會**特別關注**你設計的類別之間的**關係**——「這兩個類別之間是繼承關係、還是組合（Composition）關係？」、「這個功能應該被放在哪一個類別裡才合理？」。這種**「合理地劃分職責、設計清楚的類別關係」**的能力，正是這類 OOD 題真正想要考察的核心。

**這題也可以延伸出設計模式的討論——例如「找可用停車位」這個功能可以套用什麼設計模式？**：這題**進一步延伸**經常會涉及**具體的設計模式**討論——例如**「不同大小的停車位對應不同的收費策略（機車和汽車每小時的費率不同）」**這個需求，可以**套用策略模式（Strategy Pattern）**——把**「計算費用」**這個行為抽象成一個獨立的**策略介面**，讓**不同的收費規則**各自實作這個介面，`ParkingLot` 系統可以**在執行時動態地選用恰當的收費策略**，而**不需要**把**「不同車型的收費邏輯」**寫死在單一個龐大的計算函式裡——這種**「用具體的設計模式去因應某種特定的擴充彈性需求」**的思考，是 **OOD 面試裡展現更深技術功力**的加分環節（但**不是**每一次 OOD 面試都一定需要主動提到具體的設計模式名稱，重點依然是**你的類別設計本身是否乾淨、合理**）。

## 面試回答方式

先給出核心類別設計——「Vehicle作為抽象基礎類別或介面，定義車輛共通屬性，再由Motorcycle、Car、Truck這些具體子類別繼承並定義各自特有屬性;ParkingSpot設計成不同大小，知道自己是否被佔用;ParkingLot整合管理所有停車位，提供找可用車位和計算離場費用這些核心功能;Ticket記錄進場時間用來計算停留時長和費用」。一定要主動解釋為什麼用繼承而非單一類別加if-else——「如果只用一個類別加type欄位配合大量if-else判斷去區分車型，未來新增一種全新車輛類型就需要回頭修改每個曾經寫過這種判斷的地方，這違反了開放封閉原則——應該對擴充開放但對修改封閉，透過繼承和多型讓每種具體車輛子類別各自定義自己特有行為，未來新增車型只需要新增一個新子類別，而不需要修改任何既有程式碼」。可以補充展現和System Design題目的核心能力差異——「OOD題考察的是面對一個相對單機、但涉及眾多不同種類物件彼此關係複雜的業務邏輯，是否能用物件導向思維妥善拆解建模，讓最終程式碼具備良好可讀性可維護性可擴充性」。可以延伸提到設計模式，例如策略模式應用在不同收費規則上，展現更深的技術功力，但強調重點依然是類別設計本身是否乾淨合理。

## 常見追問

### 如果這個停車場需要額外支援「電動車充電位」這種新的停車位類型（除了能停車，還能額外充電，可能有不同的計費方式），你會怎麼調整你的設計，才能最不影響既有的程式碼？

**核心答案**：如果前面已經正確地用**繼承和多型**去設計了**停車位**這個類別體系（而**不是**用單一個巨大類別加上大量 if-else），新增「電動車充電位」這個新類型，只需要**新增一個新的子類別（例如 `ElectricChargingSpot`）**讓它繼承自原本的停車位基礎類別，並**額外地覆寫或擴充**它**特有的行為**（例如額外的充電功能、額外的計費邏輯）——這種做法能夠**完全不需要去修改任何既有已經寫好、且正常運作**的程式碼，這正是前面核心答案和詳細解析已經深入討論過的**開放封閉原則****具體發揮效用**的實際展現。

**詳細解析**：這題是一個**直接驗證**前面已經提到的架構設計原則是否真的經得起考驗的**具體測試情境**——如果你一開始的類別設計確實是**恰當地**運用了**繼承和多型**，這種**「新增一種全新類型只需要新增一個新的子類別，而完全不需要去修改任何既有程式碼」**的效果就會**自然而然發生**——這某種程度上也是面試官透過**這種追問**去**驗證**你前面給出的設計，是不是**真的經得起考驗、真的具備良好的擴充性**，而**不是****表面上看起來用了繼承，但實際上依然隱藏著大量難以擴充的問題**。

**面試回答方式**：先給出核心答案——「如果前面已經正確用繼承和多型設計了停車位類別體系，新增電動車充電位這種新類型，只需要新增一個新子類別繼承自原本的停車位基礎類別，並額外覆寫或擴充它特有的行為(如充電功能和計費邏輯)，完全不需要修改任何既有已經寫好且正常運作的程式碼」。可以總結這是對之前設計的驗證——「這是直接驗證前面架構設計原則是否真的經得起考驗的具體測試情境，如果一開始的類別設計確實恰當運用了繼承和多型，這種新增類型只需新增子類別、不需修改既有程式碼的效果就會自然發生」。

### 如果「找一個可用的停車位」這個功能需要考慮「盡量幫小型車輛優先分配到離出入口較近的停車位，以提升整體的停車效率」這種更複雜的分配策略，你會怎麼設計，讓這種分配邏輯能方便地被調整、替換？

**核心答案**：這裡適合套用**策略模式（Strategy Pattern）**——把**「如何決定要分配哪一個具體停車位給這台車」**這個決策邏輯抽象成一個**獨立的『停車位分配策略』介面**，`ParkingLot` 本身只負責**呼叫這個策略介面**去取得**「應該分配哪一個停車位」**這個決策結果，而**不需要**自己內部去寫死**具體的分配邏輯**——之後如果**業務需求**需要**調整分配策略**（例如改成「優先把最靠近電梯的位置留給行動不便人士」），只需要**替換或新增一個新的策略實作**，而**不需要**去動到 `ParkingLot` 本身的核心邏輯。

**詳細解析**：這題考察是否能**識別出「當某個具體的業務邏輯（如分配策略）未來很可能需要被頻繁地調整、替換」**這個信號時，應該**主動地把這部分邏輯額外抽象成一個獨立的介面**，而**不是**把這種**「可能需要經常變動」**的邏輯**直接寫死**在**核心的業務類別**裡——這種**「識別出系統裡哪些部分是相對穩定、哪些部分則可能經常需要被調整替換，並針對後者額外地做抽象化、介面化的設計」**的判斷能力，是**物件導向設計裡運用設計模式時真正核心的思考依據**（而不是**單純地把設計模式的名稱死記硬背下來**，卻**不理解什麼情況下才真正適合套用哪一個具體的設計模式**）。

**面試回答方式**：先給出核心答案——「這裡適合套用策略模式，把如何決定分配哪個具體停車位這個決策邏輯，抽象成一個獨立的停車位分配策略介面，ParkingLot本身只負責呼叫這個策略介面取得決策結果，而不需要自己內部寫死具體的分配邏輯，之後如果業務需求需要調整分配策略，只需要替換或新增一個新的策略實作，而不需要動到ParkingLot本身的核心邏輯」。可以總結核心判斷依據——「這反映了識別出系統裡哪些部分相對穩定、哪些部分可能經常需要被調整替換，並針對後者額外做抽象化介面化設計這個核心思考依據，而不是單純死記硬背設計模式的名稱，卻不理解什麼情況下才真正適合套用哪個具體設計模式」。

### 如果面試官繼續追問「如果這個停車場系統需要支援多個不同的實體停車場（每一個實體停車場各自有自己的收費標準），你的設計需要怎麼調整？」，你會怎麼回答？

**核心答案**：需要額外地**引入一個更高層次的抽象**——例如一個 **`ParkingLotChain`（或者 `ParkingFacilityManager`）**這種**「管理多個獨立 `ParkingLot` 實例」**的更高層類別，**每一個獨立的 `ParkingLot` 實例**各自**擁有自己的一套停車位集合、以及自己獨立的收費策略**（這正是前面核心答案已經提到的策略模式能夠發揮作用的地方——**不同的停車場實例**可以**各自注入不同的收費策略實作**）。這種**「讓同一套核心的類別設計（`ParkingLot`、`ParkingSpot` 等）能夠被多個獨立的實例，各自依照自己的具體設定重複使用」**的思路，正是物件導向設計裡**良好的封裝和抽象**帶來的核心效益——**核心的類別邏輯只需要被設計、實作一次**，之後就能**透過建立不同的物件實例、給予不同的初始設定**，去**因應多種不同的具體使用情境**。

**詳細解析**：這題考察是否理解**「良好的物件導向設計」**之所以**具備價值**，核心原因正是**「核心的類別邏輯只需要被正確地設計、實作一次，之後就能透過建立多個各自獨立、可以分別客製化設定的物件實例，去重複地應用在多種不同的具體場景」**。這種**「一套設計，多處複用」**的能力，正是**物件導向程式設計**相較於**「每次遇到略微不同的需求，就重新寫一套全新的、彼此獨立、無法共用的程式碼」**所帶來的核心效益——如果你**一開始**就把 `ParkingLot` 設計成**一個可以被多次建立、且每次建立時能接受不同初始設定（如不同的收費策略）的類別**，**「支援多個不同的實體停車場」**這個**看似是全新需求**的功能，實際上**幾乎不需要**任何額外的架構調整就能被自然地滿足。

**面試回答方式**：先給出核心答案——「需要額外引入一個更高層次的抽象，例如ParkingLotChain這種管理多個獨立ParkingLot實例的更高層類別，每個獨立的ParkingLot實例各自擁有自己的停車位集合和獨立的收費策略，這正是之前提到的策略模式能發揮作用的地方——不同停車場實例可以各自注入不同的收費策略實作」。可以總結物件導向設計的核心價值——「這反映了良好物件導向設計的核心價值，核心類別邏輯只需要被正確設計實作一次，之後就能透過建立多個各自獨立、可以分別客製化設定的物件實例，去重複應用在多種不同的具體場景，如果一開始就把ParkingLot設計成可以被多次建立且每次接受不同初始設定的類別，支援多個實體停車場這個看似全新的需求，實際上幾乎不需要任何額外架構調整就能被自然滿足」。
