# 題目

「Design a Parking Lot」是 Microsoft（以及同類型重視**物件導向設計（Object-Oriented Design, OOD）**能力的歐美科技公司）面試裡**經典**的 OOD 題目（根據公開面試經驗分享整理歸納而成，並非逐字官方紀錄）：**「請用物件導向的方式設計一個停車場管理系統，需要支援不同大小的車輛（機車、汽車、大型車）、不同的停車位類型，並能計算停車費用」**這題**不像**前面（見 [[017-google-url-shortener-system-design.md]]、[[018-meta-newsfeed-system-design.md]]）討論過的 System Design 題那樣重視**大規模分散式架構**，而是考察**你是否能用恰當的類別（Class）設計、繼承、介面**，把一個真實世界的業務邏輯**乾淨地建模出來**。

## 核心答案

核心的類別設計，大致，包含——**(1) `Vehicle`(車輛)**：作為，一個,**抽象基礎類別或介面**，定義，「車輛」共通,具備的屬性(車牌號碼、車輛類型)，再，由，**`Motorcycle`(機車)、`Car`(汽車)、`Truck`(大型車)**這幾個,**具體子類別**，去，繼承，並，各自，定義，**自己,特有的屬性**(例如，大小,不同)；**(2) `ParkingSpot`(停車位)**：同樣，可以，設計成，**不同大小(機車位、標準汽車位、大型車位)**，每一個,停車位，需要，知道，**「自己,目前,是否,被佔用、目前,停,的是,哪一台車」**；**(3) `ParkingLot`(停車場)**：**整合,管理**，所有的停車位，提供，**「幫,某台車,找到,一個,可用的停車位」、「這台車,離開時，計算,應該,收取的費用」**這些,核心功能；**(4) `Ticket`(停車票證)**：記錄，**「這台車,是,什麼時候,進場的」**，用來，在，**離場時**，計算，停留的時間、進而，計算,費用。設計時，**核心的物件導向原則**，是，**「讓,不同種類的車輛、不同種類的停車位,各自的差異行為，透過,繼承和多型(Polymorphism)，自然地，被,表達出來，而，不是，在,單一個,巨大的函式裡，用，大量的if-else，去，判斷,各種,不同的情況」**。

## 詳細解析

**為什麼要用「繼承」而不是,單一個類別加上大量欄位去區分車輛類型——這反映了,物件導向設計的核心價值**：這，是，這題，最核心的考點——一個，**經驗較,不足**的候選人，可能，會，設計成，**「只有,一個單一的`Vehicle`類別，裡面,有,一個,`type`欄位(用,字串或enum,表示,是機車還是汽車)，再，在，程式裡的各個地方**，用，**`if (vehicle.type == "car") {...} else if (vehicle.type == "motorcycle") {...}`**這種,判斷邏輯，去，因應，不同車型的差異」——這種做法，雖然，**短期內,也能運作**，但，會，導致，**「每,當,新增,一種,全新的車輛類型(例如,未来,需要,支援,電動車或,自行車)」**，就，**需要,回頭,去，修改**，**每一個,曾經,寫過,這種if-else判斷**的地方，這，違反了，**物件導向設計,裡,重要的『開放封閉原則(Open-Closed Principle)』**——**「應該,對,擴充,開放，但，對,修改,封閉」**——透過，**用,繼承,和,多型**，讓，**每一種,具體的車輛子類別**，各自，定義，**自己特有的行為**(例如，`Car`,和,`Motorcycle`,各自,覆寫,「這台車,佔用,的停車位,大小需求」這個方法)，未來，**新增一種,全新的車輛類型**時，只，需要，**新增,一個,新的子類別**，而，**不需要**，去，**修改,任何,既有的程式碼**。

**Microsoft,和,其他歐美科技公司,考OOD題,想,看到的核心能力——你,是否,能,把,模糊的業務需求，轉化,成,具體、乾淨的類別結構**：這类，**OOD題**，某種程度上，考察的，是，**和,前面已經,討論過的System Design題,不同的能力面向**——System Design,考察的，是，**「大規模,分散式架構,的權衡取捨」**；而，**OOD題**，考察的，是，**「面對,一個,相對,單機、但,涉及,眾多,不同種類物件、彼此關係複雜的業務邏輯**，你，是否，能，用，**物件導向的思維**，去，把，這種,複雜性，妥善地，拆解、建模，讓，最終寫出來的程式碼，**具備,良好的可讀性、可維護性、可擴充性**」——面試官，通常，會，**特別,關注**，你，設計的類別之間的**關係**——「這，兩個,類別之間，是，繼承關係、還是，組合(Composition)關係？」、「這個功能，應該，被，放在,哪一個類別裡,才,合理？」，這種，**「合理地,劃分,職責、設計清楚的類別關係」**的能力，正是，這类,OOD題,真正,想要,考察的核心。

**這題,也可以,延伸出,設計模式的討論——例如,「找,可用停車位」這個功能，可以,套用,什麼設計模式？**：這題，**進一步,延伸**，經常，會，涉及，**具體的設計模式**討論——例如，**「不同大小,的停車位,對應,不同的收費策略(機車,和,汽車，每小時,的費率,不同)」**這個,需求，可以，**套用,策略模式(Strategy Pattern)**——把，**「計算費用」**這個,行為，抽象,成，一個,獨立的**策略介面**，讓，**不同的收費規則**，各自，實作，這個,介面，`ParkingLot`,系統，可以，**在,執行時，動態地，選用,恰當的收費策略**，而，**不需要**，把，**「不同車型的收費邏輯」**，寫死,在，單一個,龐大的計算函式裡——這種，**「用,具體的設計模式，去，因應,某種,特定的擴充彈性需求」**的思考，是，**OOD面試,裡，展現,更深,技術功力**的加分環節(但，**不是**，每一次OOD面試,都,一定,需要,主動,提到,具體的設計模式名稱，重點,依然,是，**你的類別設計,本身,是否,乾淨、合理**)。

## 面試回答方式

先給出核心類別設計——「Vehicle作為抽象基礎類別或介面,定義車輛共通屬性,再由Motorcycle、Car、Truck這些具體子類別繼承並定義各自特有屬性;ParkingSpot設計成不同大小,知道自己是否被佔用;ParkingLot整合管理所有停車位,提供找可用車位和計算離場費用這些核心功能;Ticket記錄進場時間用來計算停留時長和費用」。一定要主動解釋為什麼用繼承而非單一類別加if-else——「如果只用一個類別加type欄位配合大量if-else判斷去區分車型,未來新增一種全新車輛類型就需要回頭修改每個曾經寫過這種判斷的地方,這違反了開放封閉原則——應該對擴充開放但對修改封閉,透過繼承和多型讓每種具體車輛子類別各自定義自己特有行為,未來新增車型只需要新增一個新子類別,而不需要修改任何既有程式碼」。可以補充展現和System Design題目的核心能力差異——「OOD題考察的是面對一個相對單機、但涉及眾多不同種類物件彼此關係複雜的業務邏輯,是否能用物件導向思維妥善拆解建模,讓最終程式碼具備良好可讀性可維護性可擴充性」。可以延伸提到設計模式,例如策略模式應用在不同收費規則上，展現更深的技術功力，但強調重點依然是類別設計本身是否乾淨合理。

## 常見追問

### 如果，這個停車場，需要，額外,支援，「電動車,充電位」這種,新的停車位類型(除了,能停車,還,能,額外,充電，可能,有,不同的計費方式)，你，會，怎麼,調整，你的設計，才能，最,不影響,既有的程式碼？

**核心答案**：如果，前面，已經，正確地，用，**繼承和多型**，去，設計了，**停車位**這個類別體系(而，**不是**，用，單一個,巨大類別,加上,大量if-else)，新增，「電動車充電位」這個,新類型，只，需要，**新增,一個,新的子類別(例如,`ElectricChargingSpot`)**，讓，它，繼承,自，原本的停車位基礎類別，並，**額外地，覆寫,或,擴充**，它，**特有的行為**(例如，額外的充電功能、額外的計費邏輯)——這種做法，能夠，**完全,不需要，去，修改**，**任何,既有,已經,寫好、且，正常運作**的程式碼，這，正是，前面(見 核心答案和詳細解析)已經,深入討論過的**開放封閉原則**，**具體,發揮效用**的實際展現。

**詳細解析**：這題，是，一個，**直接,驗證**，前面已經,提到的架構設計原則,是否,真的,經得起考驗的**具體測試情境**——如果，你，一開始，的類別設計，確實，是，**恰當地**，運用了，**繼承和多型**，這種，**「新增,一種,全新類型**，只，需要，**新增,一個,新的子類別**，而，**完全,不需要**，去，**修改,任何,既有程式碼**」的效果，就，會，**自然而然,發生**——這，某種程度上，也，是，面試官，透過，**這種,追問**，去，**驗證**，你，前面,给出的設計，是不是，**真的,經得起,考驗、真的,具備,良好的擴充性**，而，**不是**，**表面上,看起来,用了繼承,但,實際上,依然,隱藏著,大量,難以,擴充的問題**。

**面試回答方式**：先給出核心答案——「如果前面已經正確用繼承和多型設計了停車位類別體系,新增電動車充電位這種新類型,只需要新增一個新子類別繼承自原本的停車位基礎類別,並額外覆寫或擴充它特有的行為(如充電功能和計費邏輯),完全不需要修改任何既有已經寫好且正常運作的程式碼」。可以總結這是對之前設計的驗證——「這是直接驗證前面架構設計原則是否真的經得起考驗的具體測試情境,如果一開始的類別設計確實恰當運用了繼承和多型,這種新增類型只需新增子類別、不需修改既有程式碼的效果就會自然發生」。

### 如果，「找,一個,可用的停車位」這個功能，需要，考慮，「盡量,幫,小型車輛，優先,分配到,離出入口,較近的停車位，以,提升,整體的停車效率」這種,更複雜的分配策略，你，會，怎麼,設計，讓，這種,分配邏輯，能，方便地，被，調整、替換？

**核心答案**：這裡，適合，套用，**策略模式(Strategy Pattern)**——把，**「如何,決定,要,分配,哪一個,具體停車位,给,這台車」**這個,決策邏輯，抽象,成，一個，**獨立的『停車位分配策略』介面**，`ParkingLot`,本身，只，負責，**呼叫,這個,策略介面**，去，取得，**「應該,分配,哪一個停車位」**這個,決策結果，而，**不需要**，自己,內部，去，寫死，**具體的分配邏輯**——之後，如果，**業務需求**，需要，**調整,分配策略**(例如，改成，「優先,把,最靠近電梯的位置，留給,行動不便,人士」)，只，需要，**替換,或,新增,一個,新的策略實作**，而，**不需要**，去，動到，`ParkingLot`,本身,的核心邏輯。

**詳細解析**：這題，考察，是否，能，**識別出**，**「當,某個,具體的業務邏輯(如,分配策略)，未來,很可能,需要,被,頻繁地,調整、替換」**這個,信號時，應該，**主動地，把,這部分,邏輯，額外,抽象,成，一個,獨立的介面**，而，**不是**，把，這種，**「可能,需要,經常變動」**的邏輯，**直接,寫死**，在，**核心的業務類別**裡——這種，**「識別出,系統裡,哪些部分,是,相對穩定、哪些部分,則,可能,經常需要,被,調整替換，並，針對,後者，額外地，做,抽象化、介面化的設計」**的判斷能力，是，**物件導向設計裡，運用,設計模式,時，真正,核心的思考依據**(而，不是，**單純地，把,設計模式的名稱，死记硬背下来**，卻，**不理解，什麼情況下，才,真正,適合，套用,哪一個,具體的設計模式**)。

**面試回答方式**：先給出核心答案——「這裡適合套用策略模式,把如何決定分配哪個具體停車位這個決策邏輯,抽象成一個獨立的停車位分配策略介面,ParkingLot本身只負責呼叫這個策略介面取得決策結果,而不需要自己內部寫死具體的分配邏輯,之後如果業務需求需要調整分配策略,只需要替換或新增一個新的策略實作,而不需要動到ParkingLot本身的核心邏輯」。可以總結核心判斷依據——「這反映了識別出系統裡哪些部分相對穩定、哪些部分可能經常需要被調整替換,並針對後者額外做抽象化介面化設計這個核心思考依據,而不是單純死記硬背設計模式的名稱,卻不理解什麼情況下才真正適合套用哪個具體設計模式」。

### 如果，面試官，繼續,追問，「如果，這個停車場,系統，需要，支援，多個,不同的實體停車場(每一個,實體停車場,各自,有,自己的收費標準)，你，的設計，需要，怎麼,調整？」，你，會，怎麼,回答？

**核心答案**：需要，額外地，**引入,一個,更高層次的抽象**——例如，一個，**`ParkingLotChain`(或者，`ParkingFacilityManager`)**這種,**「管理,多個,獨立ParkingLot,實例」**的更高層類別，**每一個,獨立的`ParkingLot`,實例**，各自，**擁有,自己的一套,停車位集合、以及，自己,獨立的收費策略**(這，正是，前面(見 核心答案)已經,提到的策略模式,能夠,發揮作用的地方——**不同的停車場實例**，可以，**各自,注入,不同的收費策略實作**)，這種，**「讓,同一套,核心的類別設計(`ParkingLot`、`ParkingSpot`等)，能夠，被，多個,獨立的實例**，各自,依照,自己的具體設定，重複使用」的思路，正是，物件導向設計裡，**良好的封裝和抽象**，帶來的核心效益——**核心的類別邏輯，只，需要，被，設計、實作,一次**，之後，就，能，**透過,建立,不同的物件實例、給,予,不同的初始設定**，去，**因應,多種,不同的具體使用情境**。

**詳細解析**：這題，考察，是否，理解，**「良好的物件導向設計」**，之所以，**具備,價值**，核心原因，正是，**「核心的類別邏輯，只需要,被,正確地,設計、實作一次，之後，就，能，透過,建立,多個,各自,獨立、可以,分别,客製化設定的物件實例**，去，重複地，應用在，**多種,不同的具體場景**」，這種，**「一套設計，多处複用」**的能力，正是，**物件導向,程式設計**，相較於，**「每次遇到,略微,不同的需求，就，重新,寫,一套,全新的、彼此,獨立、無法共用**的程式碼」，所，带来的核心效益——如果，你，**一開始**，就，把，`ParkingLot`,設計成，**一個，可以，被，多次,建立、且，每次,建立時，能，接受,不同初始設定(如,不同的收費策略)的類別**，**「支援,多個,不同的實體停車場」**這個，**看似,是,全新需求**的功能，實際上，**幾乎,不需要**，任何,額外,的架構調整，就，能，被，自然地，滿足。

**面試回答方式**：先給出核心答案——「需要額外引入一個更高層次的抽象,例如ParkingLotChain這種管理多個獨立ParkingLot實例的更高層類別,每個獨立的ParkingLot實例各自擁有自己的停車位集合和獨立的收費策略,這正是之前提到的策略模式能發揮作用的地方——不同停車場實例可以各自注入不同的收費策略實作」。可以總結物件導向設計的核心價值——「這反映了良好物件導向設計的核心價值,核心類別邏輯只需要被正確設計實作一次,之後就能透過建立多個各自獨立、可以分別客製化設定的物件實例,去重複應用在多種不同的具體場景,如果一開始就把ParkingLot設計成可以被多次建立且每次接受不同初始設定的類別,支援多個實體停車場這個看似全新的需求,實際上幾乎不需要任何額外架構調整就能被自然滿足」。
