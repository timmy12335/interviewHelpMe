# 題目

這是國泰金控（以及同類型的台灣金融科技／銀行業後端職位）**幾乎必考**的支付系統設計題（根據公開面試經驗分享整理歸納而成，並非逐字官方紀錄）：**「使用者在網路不穩定或者手滑的情況下，對同一筆付款連續點擊了兩次『確認付款』按鈕，你會怎麼設計系統，確保這位使用者不會被重複扣款兩次？」**這題是前面（見 [[../backend-engineering/003-idempotency-design.md]]）深入討論過的**冪等性設計**核心概念，在**金融支付**這個**容錯度極低**的具體場景裡的實戰應用。

## 核心答案

核心解法是**引入一個由，客戶端(或者，伺服器在使用者第一次，發起付款請求時)產生的，獨一無二的『冪等性金鑰(Idempotency Key)』**——具體流程，是——**(1) 使用者，第一次點擊，付款按鈕**時，前端會產生(或者向後端請求)一個**這一次付款請求，專屬的唯一識別碼**；**(2) 這個識別碼**會**跟著，這次的付款請求**，一起送到後端；**(3) 後端在真正執行扣款操作之前**先**檢查這個識別碼是否已經被，處理過**(通常，會把**已經，處理過的識別碼**，記錄在一個，快速查詢的儲存空間裡，如Redis)——**如果，已經被處理過**直接回傳**上一次那筆已經，成功處理的結果**(而，**不會**再真正執行，第二次的扣款操作)；**如果是第一次**才**真正執行扣款**並把這個識別碼連同，**這次的處理結果**，記錄下來。這種做法讓**即使同一筆付款請求**因為，任何原因(使用者，手滑、網路重傳)被**重複送達，後端好幾次**，後端都能**準確地識別出**這其實，是**同一筆請求**只真正處理一次。

## 詳細解析

**冪等性金鑰，的檢查和寫入，必須是，原子操作——否則，依然可能出現，競態條件**：這，是這題最容易被深入，追問的細節——如果，**「檢查，這個識別碼，是否已經被，處理過」**和**「如果，沒有處理過才真正執行扣款並記錄」**這兩個步驟被**拆解成兩個，獨立的操作**，在**極端，巧合**的情況下(例如，兩次，重複的請求，因為網路延遲幾乎同時到達後端)依然可能出現，**競態條件**——兩個請求，**幾乎同時**各自檢查發現，**這個識別碼，還沒有被處理過**於是，**兩者都繼續往下真正地執行了扣款操作**導致，**重複扣款**——這，直接呼應了前面(見 [[004-meituan-flash-sale-system-design.md]])已經深入討論過的**「檢查，和修改必須是，原子操作」**這個，核心原則——正確的做法，是**用，類似前面已經討論過的Redis,`SET key value NX`這種原子性的操作**，去**同時完成『檢查，這個key，是否存在』和『如果不存在，就設定它』**這兩個動作只有**第一個成功地，用這種原子操作，設定了這個，識別碼**的請求，才被視為**真正需要，執行扣款的那一個**，其餘**後續，到達**的相同識別碼請求，一律**被視為重複請求**直接回傳之前已經，處理的結果。

**冪等性金鑰，的『產生時機』，也是，關鍵——太晚產生，可能無法涵蓋所有，重複場景**：另一個，容易被，忽略的細節，是**「這個，冪等性金鑰，應該在什麼時候被產生？」**——如果這個識別碼是在**「使用者點擊，確認付款按鈕」**這個，動作發生之後才由**前端當下**即時產生那如果**使用者連續，點擊了兩次**，這兩次點擊很可能會**各自產生兩個，不同**的識別碼(因為，是兩次，獨立的點擊動作，各自觸發一次產生)導致後端**依然把這兩個請求當作兩筆不同的合法請求**去分別，處理——正確的做法，應該是**在使用者一開始進入這個，付款頁面(或者，產生這筆訂單)時**就**先產生好這個，唯一的識別碼**，並讓**這個，付款頁面上，所有後續的『確認付款』點擊**，都**共用同一個**已經事先，產生好的識別碼，這樣才能確保**「同一次付款嘗試，裡的所有重複點擊」**，都會**攜帶著，完全相同的識別碼**，被後端正確地識別成，重複請求。

**這題在金融科技場景，特別重要的原因——重複扣款，造成的是，真實的金錢損失，和信任危機**：這題，之所以在，**金融相關公司，的面試**裡特別受到重視是因為**支付系統，裡的重複扣款**，造成的**不是**像，一般網頁應用，那樣可能，只是**顯示，錯誤的資料**這種，相對可以被，容忍的問題，而是，**真實、具體的金錢損失**，一旦發生不僅需要**額外處理退款這種善後成本**更會**嚴重損害使用者對這個金融服務的信任**(對，銀行/金融科技公司，而言**信任**是，最核心的商業資產)，這也是為什麼，**冪等性設計**，在金融科技領域，被視為**幾乎是，一切支付相關功能**，都**必須，具備的基本要求**，而**不是**一個，**可有可無的加分項目**。

## 面試回答方式

先給出核心解法——「引入一個冪等性金鑰，使用者第一次進入付款流程時就產生這個唯一識別碼，跟著付款請求一起送到後端，後端在真正執行扣款前先檢查這個識別碼是否已被處理過，如果已處理過就直接回傳上一次的結果而不重複執行扣款，如果是第一次才真正執行扣款並記錄」。一定要主動點出必須用原子操作，避免競態條件——「檢查和寫入這個識別碼必須是原子操作，如果拆成兩個獨立步驟，極端巧合下兩次重複請求幾乎同時到達，可能都各自檢查發現識別碼還沒被處理，於是都繼續執行扣款導致重複扣款，正確做法是用類似Redis SET key value NX這種原子操作同時完成檢查和設定」。可以主動補充一個容易被忽略的細節——「冪等性金鑰的產生時機也很關鍵，應該在使用者一開始進入付款頁面時就先產生好，讓這個付款頁面上所有後續的確認付款點擊都共用同一個識別碼，而不是每次點擊才各自產生新的識別碼，否則連續點擊兩次可能會產生兩個不同識別碼，依然無法被正確識別成重複請求」。可以強調金融場景的特殊重要性——「支付系統的重複扣款造成的是真實具體的金錢損失，不僅需要額外處理退款善後，更會嚴重損害使用者對金融服務的信任，這是為什麼冪等性設計在金融科技領域被視為所有支付功能都必須具備的基本要求」，展現你對冪等性設計在高風險金融場景裡的深度理解。

## 常見追問

### 如果，冪等性金鑰，和對應的處理結果，是儲存在，Redis裡，如果，Redis，本身，發生故障或重啟，導致這些記錄遺失了會發生，什麼問題？你會怎麼因應？

**核心答案**：如果，這些**冪等性記錄**，真的**遺失了**系統會**失去識別，重複請求的能力**，導致**萬一剛好在這段，記錄遺失的期間**，收到一筆**其實，是重複**的付款請求，系統可能會**誤判**它是**一筆，全新的請求**，而**再次執行，扣款**——因應這種風險，實務上**不應該只依靠，Redis，這種以，效能為優先考量，的儲存系統**，去保存**這麼關鍵、攸關，金錢正確性**的記錄，而應該**額外地把這些，冪等性記錄，也同步寫入到一個更具備，持久性保證，的資料庫**裡(可以，把Redis，當作一層，加速查詢的快取，但**真正的，可靠來源(Source of Truth)**，應該是，**持久化的資料庫**)。

**詳細解析**：這題，考察是否理解**「用，Redis，來實作，冪等性檢查」**這個，常見做法本身也**繼承了**前面(見 [[001-alibaba-distributed-lock-redis.md]])已經深入討論過的**Redis，本身可能因為故障而，遺失資料**這個，固有風險而**在金融支付這種對正確性容錯度，極低**的場景裡，**單純依靠，Redis**，去保存**這麼，關鍵**的資訊，某種程度上，是**過於，冒險**的做法——一個，**更加穩健**的架構，應該採用，**「Redis，作為快速查詢的第一層快取；持久化資料庫，作為真正，可靠、不會遺失的最終記錄」**這種，**分層式**的設計——每一次，**真正處理一筆付款**時**同時把這個，冪等性記錄，寫入，Redis(供，後續快速查詢)也寫入，持久化資料庫(作為，最終，可靠的記錄)**，如果，**Redis，真的，發生故障、記錄遺失**，系統依然可以**退回去查詢，持久化資料庫**，確認這筆請求是否真的已經被處理過，只是這種查詢會**比直接，查詢Redis，慢一些**，但**依然能正確地避免，重複扣款**這種，更加嚴重的後果。

**面試回答方式**：先給出風險說明——「如果冪等性記錄真的遺失，系統會失去識別重複請求的能力，萬一剛好在記錄遺失期間收到一筆其實重複的付款請求，系統可能誤判是全新請求而再次執行扣款」。給出更穩健的架構建議——「不應該只依靠Redis這種以效能為優先考量的儲存系統，去保存這麼關鍵攸關金錢正確性的記錄，應該採用分層式設計，Redis作為快速查詢的第一層快取，持久化資料庫作為真正可靠不會遺失的最終記錄，每次處理付款時同時寫入Redis和持久化資料庫，如果Redis故障記錄遺失，系統依然可以退回查詢持久化資料庫確認，只是查詢會慢一些，但依然能正確避免重複扣款這種更嚴重的後果」。

### 如果，這個冪等性金鑰，的記錄永遠不會過期會有，什麼問題？你會怎麼設定，合理的保留期限？

**核心答案**：如果，冪等性記錄，**永遠不過期**會導致**這些記錄**隨著時間**持續無限制地累積**佔用，**越來越多**的儲存空間，這某種程度上，是一種**資源持續，洩漏**的問題(即使，不是，傳統意義上，程式碼裡的記憶體洩漏（Memory Leak），但本質上是**類似的，持續累積、缺乏清理機制**這個，問題)，合理的做法，是**設定一個，恰當的保留期限**——通常，可以依照**「這筆付款實際上，可能被重複提交，的合理時間窗口，大概是多久」**去決定(例如**使用者因為網路問題而，重新整理頁面、重新，提交付款**這種，情況通常**不會發生在原始請求，的好幾天之後**，設定一個**幾小時到，一兩天**的保留期限，通常就足夠涵蓋絕大多數，合理的重複提交情境)。

**詳細解析**：這題，考察是否理解**「任何需要額外記錄下來用來做比對判斷的資訊」**都需要**額外地考慮，它的生命週期管理**，而**不能**天真地假設**「記錄下來就好不需要考慮什麼時候應該，被清理」**——這，某種程度上，呼應了前面(見 [[../ai-agent/004-memory-systems.md]]相關概念)已經，在其他技術領域裡，**反覆，出現**的核心思路——**任何一種，持續累積的記錄或記憶**，都需要**明確的保留期限或清理機制**，才能避免**無限制地持續佔用資源**判斷，**「合理的保留期限，應該是多久」**，核心的思考依據，是**「這筆記錄真正需要被拿來比對判斷，的實際時間窗口，究竟，有多長」**——只，需要涵蓋**這個實際，合理的時間窗口**，而**不需要**為了**某種理論上，極端罕見**的情境(例如，使用者在**一個月後**才重新提交同一筆，已經過期的付款請求)，就**盲目地永久保留**，所有的記錄。

**面試回答方式**：先給出核心問題——「如果永遠不過期，冪等性記錄會隨時間持續無限制累積，佔用越來越多儲存空間，是一種資源持續洩漏的問題」。給出設定合理保留期限的思考依據——「合理做法是依照這筆付款實際上可能被重複提交的合理時間窗口大概多久去決定，例如使用者因網路問題重新整理頁面重新提交，通常不會發生在原始請求好幾天之後，設定幾小時到一兩天的保留期限通常就足夠涵蓋絕大多數合理的重複提交情境」。可以總結成更普遍的原則——「任何需要額外記錄下來用來做比對判斷的資訊，都需要考慮它的生命週期管理，不能天真假設記錄下來就好不需要考慮清理，判斷合理保留期限的核心依據，就是這筆記錄真正需要被拿來比對判斷的實際時間窗口究竟有多長」。

### 除了，支付場景以外你還能想到哪些其他需要，冪等性設計，的場景?

**核心答案**：常見的其他場景，包括——**(1) 訂單建立**：避免，使用者重複提交，同一筆訂單，導致**建立出多筆，重複的訂單**；**(2) 訊息佇列（Message Queue）的消費**：前面(見 [[../backend-engineering/012-message-delivery-semantics.md]])已經深入討論過的**「至少一次(At Least Once)」訊息傳遞語意**，本身就**可能導致，同一則訊息，被重複消費**消費端需要具備，冪等性設計，才能正確地因應；**(3) 第三方API，的重試機制**：前面(見 [[../backend-engineering/018-retry-and-backoff.md]])已經深入討論過的重試策略，如果**呼叫一個會，產生實際副作用**的API(例如，發送簡訊通知)，重試時也需要考慮**是否會導致，重複的副作用**(例如，使用者收到好幾條，重複的簡訊通知)。

**詳細解析**：這題，考察是否能**把這篇文章在支付場景裡，深入討論過的冪等性設計核心概念**，**遷移應用到，其他，不同的技術情境**，考察是否具備**識別出,『這個核心概念，可以被廣泛應用在，哪些不同場景』**的融會貫通能力——理解，**冪等性設計**,之所以**在這麼多不同場景**都**普遍需要**，核心的共通原因，在於——**「任何一個，涉及實際，副作用(不管是，金錢交易、建立訂單、發送通知)的操作，一旦因為，任何原因(網路重傳、系統重試、使用者重複操作)，被意外地執行了不只一次就可能造成，非預期的重複後果」**這個，普遍存在的風險，只要一個系統涉及**任何具備，實際副作用的操作**，就**幾乎必然**需要去思考**「這個操作如果意外地被執行超過一次會不會有問題？如果會應該怎麼設計，冪等性保護？」**這個核心問題。

**面試回答方式**：先列出三個常見場景——「訂單建立(避免使用者重複提交同一筆訂單導致建立出多筆重複訂單)、訊息佇列的消費(至少一次的訊息傳遞語意本身就可能導致同一則訊息被重複消費，消費端需要冪等性設計因應)、以及第三方API的重試機制(如果呼叫的是會產生實際副作用的API，重試時也需要考慮是否會導致重複副作用，例如使用者收到好幾條重複簡訊通知)」。給出核心的共通原因——「冪等性設計之所以在這麼多不同場景都普遍需要，核心共通原因是任何一個涉及實際副作用的操作，一旦因為任何原因被意外執行不只一次，就可能造成非預期的重複後果，只要系統涉及任何具備實際副作用的操作，就幾乎必然需要思考這個操作如果意外被執行超過一次會不會有問題」。
