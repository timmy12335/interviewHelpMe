# 題目

這是國泰金控（以及同類型的台灣金融科技／銀行業後端職位）**幾乎必考**的支付系統設計題（根據公開面試經驗分享整理歸納而成，並非逐字官方紀錄）：**「使用者在網路不穩定或者手滑的情況下，對同一筆付款連續點擊了兩次『確認付款』按鈕，你會怎麼設計系統，確保這位使用者不會被重複扣款兩次？」**這題是前面（見 [[../backend-engineering/003-idempotency-design.md]]）深入討論過的**冪等性設計**核心概念，在**金融支付**這個**容錯度極低**的具體場景裡的實戰應用。

## 核心答案

核心解法，是，**引入,一個,由,客戶端(或者,伺服器,在,使用者,第一次,發起付款請求時)產生的,獨一無二的『冪等性金鑰(Idempotency Key)』**——具體流程,是——**(1) 使用者，第一次，點擊,付款按鈕**時，前端，會，產生(或者，向,後端,請求)一個，**這一次,付款請求,專屬的唯一識別碼**；**(2) 這個,識別碼**，會，**跟著，這次的付款請求**，一起，送到,後端；**(3) 後端，在，真正,執行,扣款,操作之前**，先，**檢查，這個,識別碼，是否,已經,被,處理過**(通常，會，把，**已經,處理過的識別碼**，記錄,在，一個，快速查詢的儲存空間裡，如,Redis)——**如果，已經,被,處理過**，直接，回傳，**上一次,那筆,已經,成功處理的結果**(而，**不會**，再，真正,執行，第二次的扣款操作)；**如果，是,第一次**，才，**真正,執行,扣款**，並，把，這個,識別碼，連同，**這次的處理結果**，記錄下來。這種做法，讓，**即使，同一筆,付款請求**，因為，任何原因(使用者,手滑、網路,重傳)，被，**重複,送達,後端好幾次**，後端，都，能，**準確地,識別出**，這，其實，是，**同一筆,請求**，只，真正,處理,一次。

## 詳細解析

**冪等性金鑰,的檢查和寫入,必須,是,原子操作——否則,依然,可能,出現,競態條件**：這，是，這題，最容易，被，深入,追問的細節——如果，**「檢查,這個識別碼,是否,已經,被,處理過」**和**「如果,沒有,處理過，才，真正,執行扣款,並,記錄」**這，两個步驟，被，**拆解,成，兩個,獨立的操作**，在，**極端,巧合**的情況下(例如，兩次,重複的請求，因為,網路延遲,幾乎,同時,到達後端)，依然，可能，出現，**競態條件**——两個請求，**幾乎,同時**，各自，檢查，發現，**這個識別碼，還沒有,被,處理過**，於是，**兩者，都，繼續，往下，真正地，執行了,扣款操作**，導致，**重複扣款**——這，直接，呼應了，前面(見 [[004-meituan-flash-sale-system-design.md]])已經,深入討論過的**「檢查,和,修改,必須,是,原子操作」**這個,核心原則——正確的做法，是，**用,類似前面已經討論過的Redis,`SET key value NX`,這種,原子性的操作**，去，**同時完成,『檢查,這個key,是否存在』和『如果不存在,就,設定它』**這,两個,動作，只有，**第一個,成功地，用這種原子操作，設定,了,這個,識別碼**的請求，才，被，視為，**真正,需要,執行扣款的那一個**，其餘，**後續,到達**的相同識別碼請求，一律，**被，視為,重複請求**，直接，回傳，之前,已經,處理的結果。

**冪等性金鑰,的『產生時機』，也是,關鍵——太晚產生，可能,無法,涵蓋,所有,重複場景**：另一個，容易，被，忽略的細節，是，**「這個,冪等性金鑰，應該，在，什麼時候,被,產生？」**——如果，這個,識別碼，是，在，**「使用者,點擊,確認付款按鈕」**這個,動作,發生之後，才，由**前端,當下**,即時,產生，那，如果，**使用者,連續,點擊了两次**，這，兩次,點擊，很可能，會，**各自,產生,兩個,不同**的識別碼(因為，是，两次,獨立的點擊動作，各自,觸發,一次,產生)，導致，後端，**依然,把,這,兩個,請求，當作,兩筆,不同的,合法請求**，去，分別,處理——正確的做法，應該，是，**在，使用者,一開始,進入,這個,付款頁面(或者,產生,這筆,訂單)時**，就，**先，產生,好,這個,唯一的識別碼**，並，讓，**這個,付款頁面上，所有,後續的『確認付款』點擊**，都，**共用,同一個**，已經，事先,產生好的識別碼，這樣，才能，確保，**「同一次,付款嘗試,裡的所有重複點擊」**，都，會，**攜帶,著,完全相同的識別碼**，被，後端，正確地，識別成，重複請求。

**這題,在,金融科技,場景,特別重要的原因——重複扣款,造成的,是,真實的金錢損失,和,信任危機**：這題，之所以，在，**金融相關公司,的面試**裡，特別，受到,重視，是因為，**支付系統,裡的重複扣款**，造成的，**不是**，像，一般網頁應用,那樣，可能，只是，**顯示,錯誤的資料**這種,相對,可以,被,容忍的問題，而是，**真實、具體的金錢損失**，一旦，發生，不僅，需要，**額外,處理,退款,這種,善後成本**，更，會，**嚴重,損害,使用者,對,這個,金融服務,的信任**(對，銀行/金融科技公司,而言，**信任**，是，最核心的商業資產)，這，也，是，為什麼，**冪等性設計**，在，金融科技領域，被，視為，**幾乎,是,一切支付相關功能**，都，**必須,具備的基本要求**，而，**不是**，一個，**可有可無的加分項目**。

## 面試回答方式

先給出核心解法——「引入一個冪等性金鑰,使用者第一次進入付款流程時就產生這個唯一識別碼,跟著付款請求一起送到後端,後端在真正執行扣款前先檢查這個識別碼是否已被處理過,如果已處理過就直接回傳上一次的結果而不重複執行扣款,如果是第一次才真正執行扣款並記錄」。一定要主動點出必須用原子操作,避免競態條件——「檢查和寫入這個識別碼必須是原子操作,如果拆成兩個獨立步驟,極端巧合下兩次重複請求幾乎同時到達,可能都各自檢查發現識別碼還沒被處理,於是都繼續執行扣款導致重複扣款,正確做法是用類似Redis SET key value NX這種原子操作同時完成檢查和設定」。可以主動補充一個容易被忽略的細節——「冪等性金鑰的產生時機也很關鍵,應該在使用者一開始進入付款頁面時就先產生好,讓這個付款頁面上所有後續的確認付款點擊都共用同一個識別碼,而不是每次點擊才各自產生新的識別碼,否則連續點擊兩次可能會產生兩個不同識別碼,依然無法被正確識別成重複請求」。可以強調金融場景的特殊重要性——「支付系統的重複扣款造成的是真實具體的金錢損失,不僅需要額外處理退款善後,更會嚴重損害使用者對金融服務的信任,這是為什麼冪等性設計在金融科技領域被視為所有支付功能都必須具備的基本要求」，展現你對冪等性設計在高風險金融場景裡的深度理解。

## 常見追問

### 如果，冪等性金鑰,和,對應的處理結果，是，儲存,在,Redis裡，如果,Redis,本身,發生故障或重啟，導致,這些,記錄,遺失了，會,發生,什麼問題？你，會，怎麼,因應？

**核心答案**：如果，這些，**冪等性記錄**，真的，**遺失了**，系統，會，**失去,識別,重複請求的能力**，導致，**萬一，剛好，在,這段,記錄遺失的期間**，收到，一筆，**其實,是,重複**的付款請求，系統，可能，會，**誤判**，它，是，**一筆,全新的請求**，而，**再次,執行,扣款**——因應這種風險，實務上，**不應該，只，依靠,Redis,這種,以,效能為優先考量,的儲存系統**，去，保存，**這麼,關鍵、攸關,金錢正確性**的記錄，而，應該，**額外地，把，這些,冪等性記錄，也，同步,寫入,到,一個,更具備,持久性保證,的資料庫**裡(可以，把，Redis,當作,一層,加速查詢的快取，但，**真正的,可靠來源(Source of Truth)**，應該，是，**持久化的資料庫**)。

**詳細解析**：這題，考察，是否，理解，**「用,Redis,來,實作,冪等性檢查」**這個,常見做法，本身，也，**繼承了**，前面(見 [[001-alibaba-distributed-lock-redis.md]])已經,深入討論過的**Redis,本身,可能,因為,故障,而,遺失資料**這個,固有風險，而，**在,金融支付,這種,對,正確性,容錯度,極低**的場景裡，**單純,依靠,Redis**，去，保存，**這麼,關鍵**的資訊，某種程度上，是，**過於,冒險**的做法——一個，**更加,穩健**的架構，應該，採用，**「Redis,作為,快速查詢的第一層快取；持久化資料庫,作為,真正,可靠、不會遺失的最終記錄」**這種，**分層式**的設計——每一次，**真正,處理,一筆,付款**時，**同時，把，這個,冪等性記錄，寫入,Redis(供,後續,快速查詢)，也，寫入,持久化資料庫(作為,最終,可靠的記錄)**，如果，**Redis,真的,發生故障、記錄遺失**，系統，依然，可以，**退回,去，查詢,持久化資料庫**，確認，這筆,請求，是否，真的，已經,被,處理過，只是，這種,查詢，會，**比,直接,查詢Redis,慢一些**，但，**依然,能，正確地，避免,重複扣款**這種,更加,嚴重的後果。

**面試回答方式**：先給出風險說明——「如果冪等性記錄真的遺失,系統會失去識別重複請求的能力,萬一剛好在記錄遺失期間收到一筆其實重複的付款請求,系統可能誤判是全新請求而再次執行扣款」。給出更穩健的架構建議——「不應該只依靠Redis這種以效能為優先考量的儲存系統,去保存這麼關鍵攸關金錢正確性的記錄,應該採用分層式設計,Redis作為快速查詢的第一層快取,持久化資料庫作為真正可靠不會遺失的最終記錄,每次處理付款時同時寫入Redis和持久化資料庫,如果Redis故障記錄遺失,系統依然可以退回查詢持久化資料庫確認,只是查詢會慢一些,但依然能正確避免重複扣款這種更嚴重的後果」。

### 如果，這個,冪等性金鑰,的記錄，永遠,不會,過期，會，有,什麼問題？你，會，怎麼,設定,合理的保留期限？

**核心答案**：如果，冪等性記錄，**永遠,不,過期**，會，導致，**這些,記錄**，隨著，時間，**持續,無限制地,累積**，佔用，**越來越多**的儲存空間，這，某種程度上，是，一種，**資源,持續,洩漏**的問題(即使，不是,傳統意義上,程式碼裡的記憶體洩漏（Memory Leak），但，本質上，是，**類似的,持續累積、缺乏清理機制**這個,問題)，合理的做法，是，**設定,一個,恰當的保留期限**——通常，可以，依照，**「這筆付款,實際上,可能,被,重複提交,的合理時間窗口,大概,是,多久」**去，決定(例如，**使用者，因為,網路問題,而,重新整理頁面、重新,提交付款**這種,情況，通常，**不會，發生在，原始請求,的好幾天之後**，設定,一個，**幾小時,到,一两天**的保留期限，通常，就，足夠，涵蓋，絕大多数,合理的重複提交情境)。

**詳細解析**：這題，考察，是否，理解，**「任何,需要,額外,記錄下來,用來,做,比對判斷,的資訊」**，都，需要，**額外地，考慮,它的生命週期管理**，而，**不能**，天真地，假設，**「記錄下來,就好，不需要,考慮,什麼時候,應該,被清理」**——這，某種程度上，呼應了，前面(見 [[../ai-agent/004-memory-systems.md]]相關概念)已經,在,其他技術領域裡，**反覆,出現**的核心思路——**任何一種,持續累積的記錄或記憶**，都，需要，**明確的保留期限或清理機制**，才能，避免，**無限制地,持續,佔用,資源**，判斷，**「合理的保留期限,應該,是,多久」**，核心的思考依據，是，**「這筆,記錄,真正,需要,被,拿來,比對判斷,的實際時間窗口，究竟,有多長」**——只，需要，涵蓋，**這個,實際,合理的時間窗口**，而，**不需要**，為了，**某種,理論上,極端罕見**的情境(例如，使用者，在，**一個月後**，才，重新,提交,同一筆,已經過期的付款請求)，就，**盲目地，永久保留**，所有的記錄。

**面試回答方式**：先給出核心問題——「如果永遠不過期,冪等性記錄會隨時間持續無限制累積,佔用越來越多儲存空間,是一種資源持續洩漏的問題」。給出設定合理保留期限的思考依據——「合理做法是依照這筆付款實際上可能被重複提交的合理時間窗口大概多久去決定,例如使用者因網路問題重新整理頁面重新提交,通常不會發生在原始請求好幾天之後,設定幾小時到一兩天的保留期限通常就足夠涵蓋絕大多數合理的重複提交情境」。可以總結成更普遍的原則——「任何需要額外記錄下來用來做比對判斷的資訊,都需要考慮它的生命週期管理,不能天真假設記錄下來就好不需要考慮清理,判斷合理保留期限的核心依據,就是這筆記錄真正需要被拿來比對判斷的實際時間窗口究竟有多長」。

### 除了,支付場景,以外，你，還，能，想到，哪些,其他,需要,冪等性設計,的場景?

**核心答案**：常見的其他場景，包括——**(1) 訂單建立**：避免，使用者，重複,提交,同一筆訂單，導致，**建立,出,多筆,重複的訂單**；**(2) 訊息佇列（Message Queue）的消費**：前面(見 [[../backend-engineering/012-message-delivery-semantics.md]])已經,深入討論過的**「至少一次(At Least Once)」訊息傳遞語意**，本身，就，**可能，導致,同一則訊息，被,重複消費**，消費端，需要，具備，冪等性設計，才能，正確地,因應；**(3) 第三方API,的重試機制**：前面(見 [[../backend-engineering/018-retry-and-backoff.md]])已經,深入討論過的重試策略，如果，**呼叫,一個,會,產生實際副作用**的API(例如，發送簡訊通知)，重試時，也，需要，考慮，**是否,會,導致,重複的副作用**(例如，使用者，收到,好幾條,重複的簡訊通知)。

**詳細解析**：這題，考察，是否，能，**把，這篇文章,在,支付場景,裡,深入討論過的冪等性設計核心概念**，**遷移應用到，其他,不同的技術情境**，考察，是否，具備，**識別出,『這個核心概念,可以,被,廣泛應用在,哪些,不同場景』**的融會貫通能力——理解，**冪等性設計**,之所以，**在,這麼多,不同場景**，都，**普遍,需要**，核心的共通原因，在於——**「任何一個,涉及,實際,副作用(不管是,金錢交易、建立訂單、發送通知)的操作，一旦，因為,任何原因(網路重傳、系統重試、使用者重複操作)，被，意外地,執行了,不只一次，就，可能，造成,非預期的重複後果」**這個,普遍存在的風險，只要，一個系統,涉及，**任何,具備,實際副作用的操作**，就，**幾乎,必然**，需要，去，思考，**「這個操作，如果，意外地,被,執行,超過一次，會不會,有問題？如果,會，應該,怎麼,設計,冪等性保護？」**這個,核心問題。

**面試回答方式**：先列出三個常見場景——「訂單建立(避免使用者重複提交同一筆訂單導致建立出多筆重複訂單)、訊息佇列的消費(至少一次的訊息傳遞語意本身就可能導致同一則訊息被重複消費,消費端需要冪等性設計因應)、以及第三方API的重試機制(如果呼叫的是會產生實際副作用的API,重試時也需要考慮是否會導致重複副作用,例如使用者收到好幾條重複簡訊通知)」。給出核心的共通原因——「冪等性設計之所以在這麼多不同場景都普遍需要,核心共通原因是任何一個涉及實際副作用的操作,一旦因為任何原因被意外執行不只一次,就可能造成非預期的重複後果,只要系統涉及任何具備實際副作用的操作,就幾乎必然需要思考這個操作如果意外被執行超過一次會不會有問題」。
