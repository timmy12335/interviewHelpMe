# 題目

「多供應商的庫存同步」是台灣旅遊與電商平台常被回報的實務題（根據公開的面試經驗分享整理歸納而成，並非逐字官方紀錄）：**「我們的商品來自幾十家供應商，庫存和價格在他們那邊。有些提供 API 可以即時查、有些只給每小時的檔案。你會怎麼設計，才能讓使用者看到的資訊夠準確又不會超賣？」**這題考察的是**在資料來源不受控時如何設計可靠的系統。**

## 核心答案

**核心的認知是「你無法讓所有供應商都變得即時，所以要設計成能容忍不準確」。**

**做法分三層**：**顯示層用快取的資料並標示時效**（「價格與空位僅供參考」）；**下單前做一次即時的確認**（對有 API 的供應商即時查詢、對只有檔案的則用平台自己維護的可售數量）；**下單後若供應商拒絕則進入補償流程**（通知使用者、退款、並提供替代方案）。

**同步的策略要按供應商的能力分級**：**有即時 API 的可以在關鍵時刻查詢**；**只有定時檔案的則平台要自己維護一個保守的可售量**（例如只賣八成，留兩成緩衝）；**而完全沒有介面的則需要人工維護或者改用「先預約再確認」的模式。**

**而最重要的設計是「把不確定性明確地呈現給使用者」**——**「即時確認」與「需要供應商確認，24 小時內回覆」是兩種不同的商品體驗**；**混在一起會讓使用者對整個平台的可靠度產生懷疑。**

## 詳細解析

**「保守的可售量是處理不可靠來源的標準手法」**：如果供應商每小時給一次庫存——**那這一小時內的實際變化你不知道**；**所以平台只賣一部分並保留緩衝，是用「少賣一些」換取「幾乎不超賣」**。**而緩衝的比例應該由歷史的超賣率動態調整**——**某個供應商的資料一直很準就縮小緩衝，經常出錯就放大**；**這比對所有供應商用同一個固定比例有效得多。**

**「拉取與推送要看供應商能提供什麼」**：能主動推送變更的最好（延遲最低且成本最小）——**只能被輪詢的則要在頻率與成本之間權衡**；**而輪詢的頻率應該依商品的熱度分級**：**熱門商品每分鐘查、冷門商品每小時查**；**平均分配頻率是常見的浪費。**

**「失敗的訂單需要一個明確的補償流程」**（見 [[../backend-engineering/014-saga-pattern-deep-dive.md]]）：使用者付了款但供應商說沒位子——**這時的處理必須是自動且快速的**：**立即退款、主動通知、並且如果可能就提供替代方案**；**而這個流程的品質直接決定了使用者會不會再回來**。**很多平台在這裡處理得很差（需要客服介入、退款要等三天），而那是可以用系統設計解決的。**

**「價格的一致性比庫存更敏感」**：看到的價格與結帳的價格不同——**使用者的反應通常比「沒位子」更負面**；**所以常見的做法是「顯示的價格在一段時間內鎖定」（例如加入購物車後十五分鐘），差額由平台吸收**；**這個成本是可以被量化並當成營運成本的，而它換來的是信任。**

## 面試回答方式

先給核心認知（**無法讓所有供應商即時，所以要能容忍不準確**）與三層做法，再說明按供應商能力分級的同步策略。加分點有四個：**保守的可售量**與**緩衝比例應該由歷史超賣率動態調整**；**輪詢頻率應該依商品熱度分級**；**失敗訂單的補償流程品質決定使用者會不會再回來**；以及**價格的一致性比庫存更敏感**，**用短期鎖價並把差額當成營運成本**。

## 講稿

核心的認知是我無法讓所有供應商都變得即時，所以系統要設計成能容忍不準確。

做法我分三層。顯示層用快取的資料並標示時效。下單前做一次即時確認，有 API 的即時查，只有檔案的用平台自己維護的可售量。下單後如果供應商拒絕就進入補償流程。

同步策略要按供應商的能力分級。只有定時檔案的，平台要自己維護一個保守的可售量，比如只賣八成留兩成緩衝。而這個緩衝比例應該由歷史的超賣率動態調整。某家的資料一直很準就縮小，經常出錯就放大。這比對所有供應商用同一個固定比例有效得多。

另外輪詢的頻率我會依商品熱度分級。熱門的每分鐘查、冷門的每小時查。平均分配是常見的浪費。

而我覺得最重要的設計是把不確定性明確呈現給使用者。即時確認跟需要供應商確認是兩種不同的商品體驗，混在一起會讓使用者對整個平台的可靠度產生懷疑。

## 常見追問

### 供應商的 API 很慢或者掛掉時怎麼辦？

**核心答案**：**降級到快取的資料並明確標示，同時用斷路器避免拖垮自己**（見 [[../backend-engineering/007-circuit-breaker-pattern.md]]）。查詢逾時就用上一次同步的資料——**而在下單的關鍵路徑上，如果無法即時確認，就把商品改成「需要確認」的模式而非直接失敗**；**因為「先收下訂單再人工確認」比「顯示錯誤讓使用者離開」的轉換率高得多。**

**詳細解析**：這考察**「降級不是只有『顯示錯誤』一個選項」**——**在電商的場景中，把一個原本即時的流程降級成非即時的流程，往往比中斷交易好**；**而這個決定需要業務端的認可（因為它增加了後續的人工成本）**。**能主動說出「這個降級策略需要跟業務端確認可接受的比例」，展示的是理解技術決策的業務影響**。**而斷路器在這裡的價值是雙重的**：**保護自己不被慢的供應商拖垮，同時也避免在對方已經過載時繼續發送請求讓情況惡化**；**這個「保護下游也是保護自己」的觀點，在多方整合的系統中特別重要。**

**面試回答方式**：給降級的做法（**用快取資料並標示、斷路器隔離、改成「需要確認」模式**）並說明為什麼比直接失敗好。核心加分點是指出**降級不是只有「顯示錯誤」一個選項**，並主動說明這個決定需要業務端認可。收在斷路器的雙重價值：**保護自己也避免在對方過載時繼續加重它的負擔**。

### 幾十家供應商的介面各不相同，程式碼會不會很難維護？

**核心答案**：**用一個統一的內部模型加上每家一個轉接器**（見 [[../design-patterns/006-adapter-pattern.md]]）。平台內部只認識一套自己的商品與庫存模型——**每家供應商的差異被封裝在各自的轉接器中**；**於是新增一家供應商是「寫一個新的轉接器」而不是「改動核心邏輯」。**

**詳細解析**：這考察**「防腐層」這個模式的實際應用**（見 [[../design-patterns/039-anticorruption-layer.md]]）——**如果讓外部系統的概念滲透進核心，那核心會被幾十種不同的資料格式與業務規則污染**；**而一個明確的邊界讓核心保持乾淨**。**實務上的關鍵是「內部模型要能表達所有供應商的差異但不為任何一家特化」**——**這需要在接入前幾家時就刻意地抽象，而不是先為第一家寫死再慢慢重構**；**因為後者的重構成本會隨供應商數量成長**。**而轉接器層還有一個常被忽略的價值**：**它是放置「這家供應商的怪癖」的自然位置**（例如某家的時區是錯的、某家的空字串代表零），**而那些怪癖如果散落在核心邏輯中會非常難維護**。

**面試回答方式**：給架構（**統一的內部模型加上每家一個轉接器**）並說明新增供應商的成本因此降低。核心加分點是點出這是**防腐層**模式並說明沒有邊界時核心會被污染，以及實務關鍵：**內部模型要在接入前幾家時就刻意抽象**。收在常被忽略的價值：**轉接器是放置「這家供應商的怪癖」的自然位置**，**而那些怪癖散落在核心邏輯中會非常難維護**。

### 怎麼知道某家供應商的資料品質有問題？

**核心答案**：**用監控指標而非等客訴**。可以追蹤的包括：**該供應商的下單失敗率**（顯示有位子但實際沒有）、**價格變動的頻率與幅度**、**同步的成功率與延遲**、**以及客訴中提及該供應商的比例**；**而這些指標應該有各自的告警門檻。**

**詳細解析**：這考察**「外部依賴的品質應該被量化而非憑印象」**——**「某家好像常出問題」是一個模糊的感覺，而「這家上個月的下單失敗率是 8%，平均值是 1.2%」是一個可以拿去跟對方談判的事實**；**而後者往往能促成對方真的去修**。**而這些指標的另一個用途是「自動化的處置」**：**失敗率超過門檻就自動放大該供應商的庫存緩衝、或者在搜尋結果中降低它的排序**；**於是系統能自我保護而不需要每次都靠人介入**。**這個「把外部品質變成一個可被系統自動反應的訊號」的設計，是多方整合平台中很有價值的一環**；**而它也讓供應商有實際的誘因去改善資料品質。**

**面試回答方式**：列出四個可追蹤的指標並指出**不要等客訴**。核心加分點是說明**量化讓它從模糊的感覺變成可以拿去談判的事實**，並給出自動化處置的做法（自動放大緩衝、降低排序）。收在洞察：**把外部品質變成系統能自動反應的訊號**，**同時也讓供應商有實際的誘因去改善**。
