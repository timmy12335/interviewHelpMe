# 題目

「Design a URL Shortener」是 Google（以及幾乎所有歐美大型科技公司）System Design 面試裡**最經典的入門題**（根據公開面試經驗分享整理歸納而成，並非逐字官方紀錄）：**「請設計一個短網址服務（像 bit.ly）。使用者輸入一個很長的原始網址，系統回傳一個很短的網址；之後使用者訪問這個短網址，會被重新導向回原始的長網址」**這題之所以是 **System Design 面試的『Hello World』**，是因為它**規模相對可控**，卻**同時涵蓋資料庫設計、編碼演算法、快取、擴展性這幾個**核心的系統設計元素。

## 核心答案

核心設計包含幾個部分——**(1) 短碼產生方式**：常見做法是**用一個全域遞增的唯一 ID**（可以透過資料庫的自增主鍵，或者一個獨立的 ID 產生服務），再把這個十進位的 ID 數字**轉換成 base62 編碼（用 0-9、a-z、A-Z 這 62 個字元）**，這樣一個 **7 位數的 base62 字串**就能表示**超過三千五百億種**不同的組合，足夠涵蓋長期的使用需求；**(2) 資料儲存**：用一張簡單的資料表儲存**「短碼 → 原始長網址」**這個對應關係（見 [[../system-design/008-url-shortener-design.md]]）；**(3) 讀取路徑的快取**：因為**短網址一旦產生**通常**很少再被修改**，且**讀取（訪問短網址並被重新導向）的頻率**遠高於**寫入（產生新的短網址）**，這是一個**典型適合大量運用快取**的場景，可以**把熱門的短碼對應關係**快取在 Redis 裡，減少**每一次訪問**都直接打資料庫的次數。

## 詳細解析

**為什麼用 base62 編碼，而非直接用遞增 ID 當作短碼——這是為了讓短碼更加精簡**：這題經常被追問**「為什麼不直接把遞增的數字 ID 當作短碼？」**——答案是**如果直接用十進位數字**，當**這個 ID** 成長到**幾百萬、幾千萬**時，這個數字本身的**位數**也會跟著**變得很長**，喪失了「短」網址原本想要達成的目的；而透過 **base62 編碼**，因為**每一位數可以表示 62 種不同的可能（而不是十進位的 10 種）**，能夠用**遠比十進位更少的位數**去表示**同一個數值範圍**（這某種程度上類似**「用更大的進位制，去壓縮表示同一個數值所需要的位數」**這個基本數學原理）。這也是為什麼**幾乎所有**實際的短網址服務都選擇**用 base62（或類似的高進位制編碼）**，而**不是**直接用十進位數字。

**面試官最愛追問的細節——如何產生「全域唯一」的 ID，才不會在多台伺服器同時產生短碼時出現重複衝突**：這是這題**進入更深層次**的核心考點——如果這個短網址服務是**由多台伺服器**同時服務**大量並行的產生短網址請求**，而**每一台伺服器**都**各自獨立地**去決定**下一個要使用的 ID**，很容易出現**不同伺服器各自產生了相同的 ID** 這種衝突——常見的解法包括——**(1) 用一個獨立的、專門負責分配 ID 的中央服務**（例如一個運用前面（見 [[../database/007-transaction-acid.md]] 相關的自增主鍵機制）的獨立資料庫，或者**分散式 ID 產生器（如 Twitter 開源的 Snowflake 演算法）**）；**(2) 讓每一台伺服器****預先一次性地跟中央服務申請一段範圍的 ID 區間**（例如「這台伺服器這次拿到 1000 到 1999 這 1000 個 ID，可以自己獨立依序使用，不需要每次都重新跟中央要」）。這種**「批次預先領取一段 ID 區間，減少每次都要跟中央同步的頻率」**的優化思路，某種程度上也呼應了一個在**分散式系統設計裡相當常見**的核心優化模式——**「用批次處理（Batching）去減少頻繁跨系統同步溝通所帶來的開銷」**。

**這題在歐美 System Design 面試裡的角色——面試官更重視你是否能主動估算規模，並依照規模做出恰當的架構決策**：延續前面（見 [[../system-design/016-capacity-estimation.md]]）已經深入討論過的**容量估算（Back-of-the-Envelope Estimation）**核心概念——歐美大型科技公司的 System Design 面試特別重視**你是否能主動地**在一開始就**先估算這個系統大概的規模**（例如「假設每天有一億次新的短網址被建立，需要儲存多久，每一筆資料大概佔用多少空間」），並**依照這種估算結果**去**判斷**是否**需要**考慮**額外的擴展性設計**（例如「如果資料量真的成長到某個規模，是否需要考慮前面已經深入討論過的分庫分表？」）——這種**「先估算規模，再依照估算結果做出恰當的架構決策」**的思考順序，是**歐美科技公司 System Design 面試的標準流程**，也是**和中國大廠那種更著重單一技術細節深挖**的面試風格相較之下**很鮮明**的一個差異。

## 面試回答方式

先給出核心設計三大塊——「短碼產生用base62編碼(0-9、a-z、A-Z 共 62 個字元)，把一個全域遞增的唯一ID轉換成base62字串;資料儲存用一張簡單的資料表儲存短碼對應原始長網址的關係;讀取路徑加上快取，因為短網址讀取頻率遠高於寫入，適合大量運用快取，減少每次訪問都直接打資料庫」。可以解釋為什麼用base62而非直接用數字——「如果直接用十進位數字，當ID成長到幾百萬幾千萬時位數會變長，喪失短網址的目的，base62因為每位數能表示62種可能而非十進位的10種，能用更少位數表示同一個數值範圍」。一定要主動提到分散式環境下如何產生全域唯一ID這個進階考點——「如果由多台伺服器同時服務大量並行請求，每台伺服器各自獨立決定下一個ID容易出現衝突，常見解法是用一個獨立的中央服務負責分配ID，或者讓每台伺服器預先一次性申請一段ID區間，減少每次都要跟中央同步的頻率，這種批次預先領取的優化思路，是分散式系統設計裡相當常見的核心模式」。可以主動展現容量估算的習慣——「一開始就先估算這個系統大概的規模，例如假設每天有一億次新短網址被建立，依照估算結果判斷是否需要考慮額外的擴展性設計」，展現你熟悉歐美System Design面試特別重視的先估算規模、再依照估算結果做架構決策這個標準流程。

## 常見追問

### 如果使用者想要自己指定一個「客製化的短碼」（例如 `bit.ly/my-brand`），而不是由系統隨機產生，你會怎麼調整設計？

**核心答案**：需要額外地**在「儲存短碼對應關係」之前**先**檢查這個使用者想要指定的客製化短碼**是否**已經被別人使用過**——因為**客製化短碼**本質上是**使用者自己選擇**的字串（而**不是**系統依照固定演算法產生的），**衝突的機率**遠比**系統自動產生**的短碼高得多（因為可能**很多不同使用者**都**想要用同一個好記、有意義的字串**），因此需要**在資料庫層面**對**短碼**這個欄位加上**唯一性約束（Unique Constraint）**，並在**寫入時**妥善處理**「這個客製化短碼已經被使用」**這種衝突情況（告知使用者需要換一個其他字串）。

**詳細解析**：這題考察是否理解**「系統自動產生」**和**「使用者自訂」**這兩種產生短碼方式**背後面臨的挑戰截然不同**——**系統自動依照遞增 ID 轉換而成的短碼**因為**產生的邏輯本身**就**保證了不會重複**（每一個 ID 都是唯一的，轉換而成的短碼自然也是唯一的），**天生不太需要**擔心衝突問題；但**使用者自訂的短碼**因為**完全是人類自由選擇**的字串，**沒有辦法**事先用任何演算法去保證**不會和別人選擇的字串撞名**，因此**必須**額外地在**寫入的當下****做明確的唯一性檢查**。這種**「依照資料是系統自動產生、還是使用者自由輸入，去判斷是否需要額外的唯一性檢查機制」**的思路，是設計任何**涉及識別碼**的系統時都值得反覆套用的核心考量。

**面試回答方式**：先給出核心答案——「需要在儲存短碼對應關係之前，先檢查使用者想要指定的客製化短碼是否已被別人使用過，因為客製化短碼是使用者自己選擇的字串，衝突機率遠比系統自動產生的短碼高得多，需要在資料庫層面對短碼欄位加上唯一性約束，並在寫入時妥善處理已被使用的衝突情況」。可以解釋核心差異——「系統自動依照遞增ID轉換而成的短碼，因為產生邏輯本身就保證不會重複，天生不太需要擔心衝突;但使用者自訂的短碼完全是人類自由選擇的字串，沒辦法事先用任何演算法保證不會撞名，必須額外在寫入當下做明確的唯一性檢查」。

### 如果這個短網址服務需要額外提供「這個短網址總共被點擊了多少次」這個統計功能，你會怎麼設計，才不會讓這個統計功能拖慢原本「重新導向」這個核心功能的回應速度？

**核心答案**：核心思路是**「把『記錄這次點擊』和『真正執行重新導向』這兩件事解耦、非同步化」**——當使用者訪問一個短網址時，**應該優先盡快地**完成**「查詢原始長網址、回傳重新導向指令」**這個核心動作（這是使用者**真正在等待**的部分），而**「記錄這次點擊發生了」**這個統計相關的動作，則可以**非同步地**（例如透過前面已經深入討論過的訊息佇列（Message Queue））在背景慢慢地處理，**不需要**讓使用者**等待這個統計記錄真正寫入完成**才能收到**重新導向**的回應。

**詳細解析**：這題考察是否理解**「核心的關鍵路徑（Critical Path）」**和**「非核心的附加功能」**應該被**明確區分開來**，並**分別採用不同的處理優先順序**——這直接呼應了前面（見 [[004-meituan-flash-sale-system-design.md]]）已經深入討論過的**「非同步化較不緊急的後續步驟，讓核心流程能優先快速回應」**這個核心思路——對使用者而言，**「點擊短網址之後多快能被重新導向到正確的目標網址」**是**真正影響使用者體驗的關鍵指標**；而**「這次點擊的統計數字究竟是立即、還是晚個幾秒才被記錄下來」**則是**使用者完全不會察覺、也不在乎**的細節。透過**明確地識別出「哪一部分是真正影響使用者體感的關鍵路徑，哪一部分是可以被非同步、稍後處理的附加功能」**，並**只讓核心的關鍵路徑**追求**極致的回應速度**，是任何一個**追求良好使用者體驗**的系統設計都應該具備的核心思考習慣。

**面試回答方式**：先給出核心設計思路——「核心是把記錄這次點擊和真正執行重新導向這兩件事解耦非同步化，當使用者訪問短網址時應該優先盡快完成查詢原始長網址、回傳重新導向指令這個核心動作，而記錄點擊發生這個統計相關動作，可以透過訊息佇列在背景非同步處理，不需要讓使用者等待統計記錄真正寫入完成才收到重新導向回應」。可以連結到之前討論過的核心思路——「這呼應了之前秒殺系統設計裡討論過的非同步化較不緊急後續步驟、讓核心流程能優先快速回應這個思路，明確識別出哪部分是真正影響使用者體感的關鍵路徑、哪部分是可以非同步稍後處理的附加功能，只讓核心關鍵路徑追求極致回應速度」。

### 如果面試官追問「這個短網址服務如果未來規模成長到全球數十億使用者，你會怎麼做進一步的擴展？」，你會怎麼回答？

**核心答案**：規模進一步擴大之後，需要額外考慮的擴展方向包括——**(1) 資料庫分片**（見 [[../database/017-sharding.md]]）：當**短碼對應關係**的總量成長到**單一個資料庫無法負荷**時，需要依照**恰當的分片鍵（例如依照短碼本身的雜湊值）**把資料分散到多個資料庫節點；**(2) 地理位置相關的擴展**：如果使用者**遍布全球**，可以考慮**在不同的地理區域**各自部署**獨立的服務節點和快取**，讓**使用者的請求**能被**導向離他地理位置最近**的節點，減少**網路傳輸的延遲**（這某種程度上呼應了前面（見 [[../system-design/005-cdn-design.md]]）已經深入討論過的 CDN 核心概念）。

**詳細解析**：這題考察是否具備**「隨著規模持續擴大，主動地重新審視原本的架構是否依然適用」**這個持續性的架構演進思維——歐美大型科技公司（尤其是 Google 這類本身就是經營全球性、超大規模服務的公司）特別重視這種**「不只是設計出一個在當下規模可行的方案，還要展現對未來規模持續成長的前瞻性思考」**的能力——回答這類「規模再擴大」的追問時，建議**依照不同的擴展面向（資料儲存規模、地理分佈）分別**提出對應的因應思路，而**不是**只籠統地回答**「加更多伺服器就好」**這種缺乏具體架構思考的答案。

**面試回答方式**：先給出兩個核心擴展方向——「資料庫分片，當短碼對應關係總量成長到單一資料庫無法負荷時，依照恰當分片鍵把資料分散到多個資料庫節點;地理位置相關的擴展，如果使用者遍布全球，可以考慮在不同地理區域各自部署獨立服務節點和快取，讓使用者請求能導向離他地理位置最近的節點減少網路延遲，這呼應了之前討論過的CDN核心概念」。可以總結展現前瞻性思維——「這反映了隨著規模持續擴大主動重新審視原本架構是否依然適用這個持續性架構演進思維，而不是只籠統回答加更多伺服器就好」。
