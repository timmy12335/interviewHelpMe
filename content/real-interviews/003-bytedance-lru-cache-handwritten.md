# 題目

這是字節跳動（以及拼多多、快手等同樣強調 coding 能力的公司）面試裡**相當經典**的**現場手寫程式碼**題（根據公開面試經驗分享整理歸納而成，並非逐字官方紀錄）：**「請現場實作一個 LRU（Least Recently Used，最近最少使用）Cache，要求 `get` 和 `put` 這兩個操作的時間複雜度都要是 O(1)」**這類題目**不只考演算法能力**，更考你是否能在**有限的面試時間裡**清楚說明自己的資料結構選擇，並**實際寫出能正確運作的程式碼**。

## 核心答案

要同時達成 `get` 和 `put` 都是 O(1) 的時間複雜度，標準做法是**結合兩種資料結構**——**(1) 雜湊表（HashMap）**：提供 **O(1) 的查詢能力**，讓 `get(key)` 能快速地找到這個 key 對應的節點；**(2) 雙向鏈結串列（Doubly Linked List）**：用來**維護這些資料被使用的先後順序**——每一次某個 key 被 `get` 或 `put`，就把這個對應的節點**移動到鏈結串列的頭部**（代表『最近被使用過』）；當 Cache 的容量滿了需要淘汰資料時，就**直接淘汰鏈結串列尾部**的節點（代表『最久沒有被使用過』的資料）。雜湊表裡的每一個 value 直接儲存**指向這個 key 所對應的那個雙向鏈結串列節點的參照**，這樣就能同時達成——**用雜湊表快速定位到節點（O(1)）**，以及**用雙向鏈結串列快速地把這個節點移動到頭部或從尾部移除（O(1)）**。

## 詳細解析

**為什麼一定要用「雙向」鏈結串列，而不是單向的**：這是這題一個容易被追問到的細節——**單向鏈結串列**只能從**頭部往尾部**單一方向走訪，如果要把**串列中間某一個節點**移動到頭部，需要先找到**這個節點的前一個節點**（才能把它從原本的位置摘除），但單向鏈結串列**沒有辦法直接從某一個節點反過來找到它的前一個節點**，只能**從頭開始重新走訪**去找到這個前置節點，這樣就會讓「移動節點」這個操作退化成 **O(n)** 而**不再是** O(1)；而**雙向鏈結串列**因為**每一個節點都同時紀錄了指向前一個和後一個節點**的參照，可以**直接透過這個節點本身就立即找到它的前一個節點**，讓「摘除並移動到頭部」這個操作能真正維持在 O(1)。

**面試現場的節奏——面試官通常會要求你邊寫邊說明**：字節跳動這類公司的手寫程式碼面試，通常**不會只是要求你安靜地寫完整段程式碼**，而是會要求你**一邊寫、一邊說明你現在正在處理哪一個環節**——這種**「邊寫邊解說」**的節奏其實是在考驗**你是否真的理解自己正在寫的每一行程式碼**，而不是只是**憑記憶把一個背下來的標準答案默寫出來**——建議練習時特別注意**用文字清楚地說明**「為什麼這一步要這樣做」，例如在實作 `get(key)` 時明確地說出「因為這個 key 被存取了，代表它變成最近使用過的資料，所以我需要把它對應的節點移動到鏈結串列的頭部」，而不是只默默地寫出程式碼卻不做任何口頭解釋。

**常見的實作陷阱——邊界情況的處理**：實際動手實作時容易出錯的地方包括——**(1) 鏈結串列通常會額外設計兩個『虛擬的哨兵節點（Dummy Node）』**，分別作為**頭部和尾部固定不變的邊界標記**，這樣可以**避免處理『串列目前是空的』或『只有一個節點』**這類邊界情況時需要寫額外的特殊判斷邏輯；**(2) `put` 操作時需要先判斷這個 key 是否已經存在**——如果已經存在，只需要更新它的 value 並移動到頭部；如果是全新的 key，才需要判斷 **Cache 是否已經滿了**，如果滿了要先淘汰尾部節點才能加入這個新的節點。這些看似瑣碎的邊界判斷，正是**候選人實際動手寫程式碼的能力**和**只是口頭說明原理**這兩者之間真正的差異所在。

## 面試回答方式

先給出資料結構選擇並說明理由——「用雜湊表加雙向鏈結串列的組合，雜湊表提供O(1)查詢能力讓get能快速定位到節點;雙向鏈結串列維護資料被使用的先後順序，每次get或put就把對應節點移動到頭部代表最近使用過，容量滿了就直接淘汰尾部節點代表最久沒用過的資料，雜湊表裡每個value直接存指向鏈結串列節點的參照，同時達成O(1)查詢和O(1)移動」。主動說明為什麼要用雙向而非單向——「因為要把某個節點移動到頭部，需要先找到它的前一個節點才能摘除，單向鏈結串列沒辦法直接從某節點反過來找到前一個節點，只能從頭走訪，會讓操作退化成O(n)，雙向鏈結串列每個節點都直接記錄前一個節點的參照，能維持真正的O(1)」。實際寫程式碼時邊寫邊口頭解釋每一步在做什麼，並主動提到用哨兵節點簡化邊界情況處理，展現你不只是背了標準答案，而是真正理解每一行程式碼的作用。

## 常見追問

### 如果不用雙向鏈結串列，改用 Java 現成的 `LinkedHashMap` 可以嗎？

**核心答案**：**可以——`LinkedHashMap` 本身已經內建了「依照存取順序排序」的功能，某種程度上直接就是一個現成的 LRU Cache 實作基礎**——`LinkedHashMap` 建構時可以傳入一個 `accessOrder=true` 參數，讓它**每次被存取（get 或 put）**就自動地把這個元素**移動到內部順序的末端**，再額外地覆寫它的 `removeEldestEntry` 方法，讓它在**元素數量超過設定的容量上限**時自動地**移除最舊（最久沒被存取）**的元素。這種做法能**大幅簡化**手動實作雙向鏈結串列和雜湊表整合的工作量。

**詳細解析**：這題考察是否了解 **Java 標準函式庫本身已經提供哪些現成、可以直接運用的工具**，而不是任何情況下都需要**從零開始手動實作所有底層資料結構**——面試官問這題，通常是想確認你**除了知道如何從頭手寫以外**，是否也**熟悉語言本身既有的標準函式庫**，能判斷**在實際工作情境下**什麼時候應該**直接善用現成的工具**，而不是**為了炫技而堅持從零手刻**。需要補充的是——面試官即使聽到你提到 `LinkedHashMap` 這個做法，通常依然會接著要求你**額外地手動實作一遍**（因為這題最初的考察目的本來就是**測試你的資料結構底層原理和手寫 coding 能力**），所以**知道 `LinkedHashMap` 這個捷徑是加分的展現廣度**，但**依然需要準備好完整地手動實作**，才能真正通過這一題。

**面試回答方式**：先說明LinkedHashMap的可行性——「可以，LinkedHashMap建構時傳入accessOrder=true參數，能讓它每次被存取就自動移到內部順序末端，再覆寫removeEldestEntry方法讓它在超過容量時自動移除最舊的元素，能大幅簡化手動實作的工作量」。但主動說明這通常不能取代手寫——「不過即使提到這個做法，面試官通常還是會要求額外手動實作一遍，因為這題最初的考察目的就是測試底層資料結構原理和手寫coding能力，提到LinkedHashMap是加分展現廣度，但依然要準備好完整手寫的能力」。

### 如果要求你把這個 LRU Cache 改造成支援多執行緒並行安全的版本，你會怎麼做？

**核心答案**：最直接的做法是**在 `get` 和 `put` 這兩個操作的關鍵區塊加上同步鎖**（例如用 `synchronized` 關鍵字或 `ReentrantLock`），確保**同一時間只有一個執行緒能夠去修改內部的雜湊表和鏈結串列**，避免多個執行緒同時修改這些共享的資料結構而導致狀態不一致或程式崩潰。如果想要**更進一步提升並行效能**，可以考慮**把整個 Cache 切割成多個獨立的分段（Segment）**，每個分段各自維護自己的鎖，讓**不同分段的存取可以真正平行進行**，只有**存取到同一個分段**的請求才需要互相等待。

**詳細解析**：這題直接呼應了前面（見 [[../java-concurrency/014-concurrenthashmap-internals.md]]）已經深入討論過的 **`ConcurrentHashMap` 如何透過分段／CAS 機制去提升並行存取效能**的核心思路——考察是否能把**已經學過的並行資料結構設計原則**遷移應用到**這個現場手寫的 LRU Cache** 上。回答這題時一個值得特別注意的細節是——**LRU Cache 的『移動節點到頭部』這個動作，本身是一個需要同時修改雙向鏈結串列裡多個節點關聯（前後指標）**的操作，這種**涉及多個步驟、需要保持整體一致性**的操作**不能**只是簡單地對單一個共享變數做原子操作（如 `AtomicInteger`）就足夠，而是**確實需要**一個**能涵蓋整個『移動節點』這一連串步驟**的鎖來保護。這種「識別出哪些操作只需要簡單的原子性保護、哪些操作需要更完整的鎖保護」的判斷能力，是這題更深層的考察重點。

**面試回答方式**：先給出基本做法——「最直接的做法是在get和put這兩個關鍵操作加上同步鎖，確保同一時間只有一個執行緒能修改內部的雜湊表和鏈結串列，避免多執行緒同時修改導致狀態不一致」。可以補充更進階的優化並連結先前知識——「如果想進一步提升並行效能，可以參考之前討論過的ConcurrentHashMap分段鎖思路，把整個Cache切割成多個獨立分段，各自維護自己的鎖，讓不同分段的存取能真正平行進行，只有存取到同一分段的請求才需要互相等待」。可以補充一個重要細節——「需要注意LRU Cache裡移動節點到頭部這個動作，本身涉及同時修改多個節點的前後指標關聯，這種涉及多步驟、需要保持整體一致性的操作，不能只用簡單的原子變數保護，而是確實需要一個能涵蓋整個移動過程的鎖」。

### 如果 Cache 的容量非常大（例如百萬級元素），你會考慮哪些額外的優化或取捨？

**核心答案**：當 Cache 容量變得非常龐大時，需要額外考慮的面向包括——**(1) 記憶體開銷**：**雙向鏈結串列的每一個節點**除了儲存實際的資料以外，還需要額外的空間去儲存前後指標，這種額外開銷在元素數量非常龐大時會變得相當可觀，需要評估是否**值得**用這種額外的記憶體開銷去換取 O(1) 的操作效率；**(2) 是否應該改用近似 LRU 演算法**：一些更大規模的快取系統（例如 Redis 本身）在處理巨量資料的淘汰策略時，實際上**不會維護一份完全精確**的 LRU 順序（因為維護完全精確的順序本身就有額外開銷），而是**改用近似演算法**（例如隨機抽樣幾個候選項，比較它們的存取時間，淘汰其中最久沒被存取的那一個），用**些微犧牲淘汰精確度**去換取**顯著更低**的維護成本。

**詳細解析**：這題把這個現場手寫題延伸到**「當規模擴大到極致時，原本的方案是否依然適用」**這個更加務實的工程判斷，考察是否具備**隨著規模量級改變重新評估方案取捨**的能力——這某種程度上呼應了前面（見 [[../redis/009-eviction-policy.md]]）已經深入討論過的 **Redis 本身的淘汰策略**設計思路——Redis 作為一個**追求極致效能**的系統，在實作它自己的 LRU 淘汰機制時**並沒有**選擇維護一份完全精確的雙向鏈結串列，而是**刻意地選擇了一種近似演算法**。這種**「為了追求更低的系統開銷，主動選擇犧牲一定程度的精確度」**的設計哲學，正是**大規模系統設計裡相當常見、也相當重要**的一種權衡取捨思路。能主動提到這種**規模擴大之後，原本精確方案可能不再是最佳選擇**的認知，展現你具備**超越單一道 coding 題目**的更宏觀系統設計視野。

**面試回答方式**：先給出兩個核心考量面向——「容量變得非常龐大時，需要考慮雙向鏈結串列每個節點的額外指標開銷是否值得，以及是否應該改用近似LRU演算法」。詳細說明近似演算法的思路並連結到Redis的實際設計——「一些更大規模的快取系統像Redis本身，實際上不會維護一份完全精確的LRU順序，而是改用近似演算法，例如隨機抽樣幾個候選項比較存取時間，淘汰其中最久沒被存取的那個，用些微犧牲淘汰精確度去換取顯著更低的維護成本」。展現超越單一題目的宏觀視野——「這反映了大規模系統設計裡相當常見的權衡取捨思路——為了追求更低的系統開銷，主動選擇犧牲一定程度的精確度」。
