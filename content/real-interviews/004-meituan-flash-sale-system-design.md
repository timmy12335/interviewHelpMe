# 題目

「秒殺系統設計」是美團（以及京東、拼多多等同類型的電商／團購公司）**幾乎必考**的系統設計題（根據公開面試經驗分享整理歸納而成，並非逐字官方紀錄）：**「請設計一個秒殺系統（例如限量搶購某個商品），需要考慮瞬間湧入的極高並發流量，同時確保不能超賣」**這題**結合了**高並發架構設計以及資料一致性這兩個都相當核心的技術面向。

## 核心答案

秒殺系統設計的核心思路是**「層層過濾、削峰填谷」**——透過多層不同的機制**盡可能地在請求真正打到最底層的資料庫之前，就把大量不必要或無效的流量過濾掉**——**(1) 前端限流（Rate Limiting）**：在使用者端加上**按鈕防重複點擊、驗證碼**等機制，過濾掉明顯重複、或者機器人發起的請求；**(2) 閘道層限流**：在 API 閘道層套用前面（見 [[../backend-engineering/006-rate-limiting-algorithms.md]]）已經深入討論過的限流演算法，**只放行一定速率內**的請求，超出速率的直接拒絕；**(3) 用 Redis 做庫存預先扣減**：把**商品的庫存數量**載入到 Redis 裡，讓**扣減庫存**這個動作透過 **Redis 單執行緒天然的原子性**（見 [[../redis/003-single-thread-model.md]]）快速地在記憶體層完成判斷（庫存是否足夠）和扣減，**只有真正搶購成功**的少量請求才繼續往下觸發**非同步的訂單建立**流程；**(4) 用訊息佇列（Message Queue）非同步處理後續流程**：把**建立訂單、扣減資料庫裡的實際庫存**這類相對耗時的操作透過訊息佇列（見 [[../backend-engineering/011-message-queue-fundamentals.md]]）**非同步、排隊處理**，而不是讓使用者同步地等待整個流程完成。

## 詳細解析

**為什麼要「層層過濾」——每往前攔截一批無效流量，後面的壓力就減輕一分**：秒殺場景最核心的架構挑戰是**「瞬間湧入的巨大流量，和真正有效的庫存數量之間存在巨大落差」**（例如可能有**上百萬**使用者同時搶購**只有幾百件**的商品），這意味著**絕大多數的請求最終都是無效的**（注定搶不到）。秒殺架構設計的核心哲學正是**「盡可能提早地在越前端的層級，就過濾掉這些注定無效的請求」**——**每多攔截一層**，後面需要真正處理的請求量就**大幅減少一批**，讓**最後真正需要寫入持久化資料庫**的請求只剩下**極少數真正有效**的部分。這種**「越靠近底層（資料庫）的系統越需要被保護，只讓真正有效的少量請求才能觸及」**的設計思路，是任何面對極端高並發場景的系統設計時都值得反覆套用的核心原則。

**Redis 扣減庫存的關鍵細節——一定要用原子操作避免超賣**：這是這題最核心、也最容易被追問到的細節——**如果扣減庫存這個動作**被拆解成**「先查詢目前庫存是否足夠」和「如果足夠再執行扣減」**這兩個獨立的步驟，在高並發情境下就會出現**經典的競態條件**——多個請求可能**同時查詢到『庫存還足夠』這個（可能已經過時的）結果**，導致**實際扣減的總量超過真正的庫存**（這就是**超賣**）。正確的做法是**用 Lua 腳本把『檢查庫存』和『扣減庫存』這兩個步驟包在同一個原子操作裡執行**（這直接呼應了前面（見 [[001-alibaba-distributed-lock-redis.md]]）已經深入討論過的分散式鎖（Distributed Lock）設計裡同樣強調的核心原則——**「涉及檢查和修改的操作必須是原子性的」**）。Redis 本身因為**單執行緒**這個架構特性（見 [[../redis/003-single-thread-model.md]]）天然地就具備**執行單一個 Lua 腳本期間不會被其他請求打斷**的原子性保證，這正是秒殺系統普遍選擇用 **Redis 而非直接操作資料庫**去做庫存扣減的核心原因。

**非同步下單和最終一致性——訂單可能晚一點才真正被建立，這樣可以嗎？**：秒殺架構之所以選擇**把建立訂單這件事非同步化**（使用者搶購成功之後看到的只是**『搶購成功，訂單處理中』**這種提示，而不是立即就看到一筆完整的訂單紀錄），核心原因在於——**如果要求每一個搶購成功的請求，都同步地等待一整套包含建立訂單、扣減資料庫實際庫存、觸發後續通知等一連串較耗時**的完整流程都執行完成才回應使用者，這會讓**整個系統能夠承受的並行處理能力被這些較耗時的後續步驟嚴重拖累**。透過**把這些相對不那麼緊急、可以稍微晚一點再處理**的後續步驟丟進**訊息佇列**，讓**系統先快速地回應使用者『搶購成功』**這個關鍵結果，再**依照佇列裡累積的訊息依序慢慢地在背景把後續流程處理完成**。這種**「犧牲一部分即時性（訂單不是立刻就完全建立好），去換取系統整體能夠承受的並行能力」**的設計是一種**典型的最終一致性（Eventual Consistency）**取捨——**使用者最終**一定會看到一筆完整、正確的訂單紀錄，只是**不是在搶購成功的那一瞬間就立即看到**。

## 面試回答方式

先給出整體核心架構思路——「秒殺系統設計核心是層層過濾削峰填谷，透過前端限流(防重複點擊驗證碼)、閘道層限流(限流演算法只放行一定速率內的請求)、用Redis做庫存預先扣減(利用Redis單執行緒天然原子性快速判斷和扣減庫存)、以及用訊息佇列非同步處理後續建立訂單流程，這幾層機制盡可能在流量真正打到底層資料庫之前就過濾掉大量無效請求」。解釋為什麼要層層過濾——「秒殺場景最核心的挑戰是瞬間湧入的巨大流量和真正有效庫存數量之間存在巨大落差，絕大多數請求最終都是無效的，設計哲學是盡可能提早在越前端的層級就過濾掉這些注定無效的請求，每多攔截一層後面需要真正處理的請求量就大幅減少」。一定要強調Redis扣減庫存必須用原子操作——「如果檢查庫存和扣減庫存被拆成兩個獨立步驟，高並發下會出現競態條件導致超賣，正確做法是用Lua腳本把這兩步驟包在同一個原子操作裡執行，這和之前討論過的分散式鎖設計裡強調的原子性原則是同一個核心邏輯」。可以補充非同步下單的最終一致性概念——「把建立訂單這件事非同步化，是為了不讓這些較耗時的後續步驟拖累系統整體並行能力，這是一種典型的最終一致性取捨——犧牲一部分即時性換取系統整體能承受的並行能力」，展現完整的高並發系統設計思路。

## 常見追問

### 如果秒殺活動開始的那一刻瞬間湧入的流量，遠遠超過你前面設計的所有防護機制所能承受的上限，系統應該怎麼辦？

**核心答案**：這種情況下**應該讓系統優雅地拒絕超出承載能力的流量，而不是讓整個系統被壓垮、癱瘓**——具體的做法包括——**(1) 設定明確的流量上限，超過就直接拒絕（返回『目前搶購人數過多，請稍後再試』這類友善的提示）**，而**不是**讓這些**超出處理能力**的請求繼續往下堆積、消耗系統資源；**(2) 提前做好容量規劃和壓力測試**：透過**事先估算預期的流量規模**（見 [[../system-design/016-capacity-estimation.md]]）並進行**實際的壓力測試**，去驗證系統**在預期的流量規模下**是否真的撐得住，而不是等到真正上線才發現容量不足。

**詳細解析**：這題考察是否理解**「保護系統整體的可用性，比讓每一個請求都得到處理更重要」**這個核心原則——這直接呼應了前面（見 [[../backend-engineering/008-service-degradation.md]]）已經深入討論過的**服務降級（Service Degradation）**核心思路——當系統面臨**遠超承載能力**的流量時，**與其讓所有請求都去搶奪有限的系統資源，導致整個系統因為資源耗盡而全面癱瘓（甚至可能波及到其他原本運作正常的服務）**，更好的做法是**主動地在系統即將承受不住之前，就先果斷地拒絕一部分超出負荷的流量**，用**犧牲一部分使用者的搶購機會**去**換取整個系統依然能維持基本的正常運作**。這種**「主動設限、優雅降級，而不是來者不拒、最終同歸於盡」**的設計哲學，是任何面對極端流量場景的系統都必須具備的核心韌性設計思維。

**面試回答方式**：先給出核心答案——「應該讓系統優雅地拒絕超出承載能力的流量，而不是讓整個系統被壓垮癱瘓，具體做法包括設定明確流量上限超過就直接拒絕並給出友善提示，以及提前透過容量估算（Back-of-the-Envelope Estimation）和實際壓力測試去驗證系統是否真的撐得住」。連結到服務降級的核心思路——「這呼應了之前討論過的服務降級核心思路，與其讓所有請求都去搶奪有限資源導致整個系統癱瘓、甚至波及其他服務，更好的做法是主動在系統即將承受不住之前就果斷拒絕超出負荷的流量，用犧牲一部分使用者的搶購機會，換取整個系統依然能維持基本正常運作」。

### 如果同一個使用者用腳本或多個帳號惡意地發起大量重複的搶購請求，你會怎麼防範？

**核心答案**：常見的防範手段包括——**(1) 對單一使用者（或者單一 IP）的請求頻率額外做更嚴格的限流**（不只是針對整體系統做限流，還需要額外針對『同一個使用者／IP 在短時間內是否發起了異常密集的請求』做更細緻的判斷）；**(2) 引入驗證機制**：例如圖形驗證碼、或者需要額外的人機驗證，來增加**機器人腳本發起大量請求**的難度和成本；**(3) 帳號行為分析**：對**歷史上曾經被判定有異常搶購行為**的帳號額外地做更嚴格的審查或限制。

**詳細解析**：這題把前面（見 [[../backend-engineering/006-rate-limiting-algorithms.md]]）已經深入討論過的限流演算法**從『針對整體系統流量』這個粒度延伸到『針對單一使用者／IP 這個更細的粒度』**，考察是否理解**限流可以同時在不同的粒度層次上被套用**——單純地只對**整體系統**做限流**沒有辦法**防範**「大量看起來合法的個別請求，但實際上都來自同一個惡意使用者」**這種情況，需要額外地針對**更細的維度（單一使用者 ID、單一 IP 位址）**去做**額外的、更嚴格的限流規則**。這種**「同時在不同粒度層次做分層限流」**的思路能夠更全面地防範各種不同型態的異常流量，而不是只依靠**單一個粗粒度**的整體流量限制。

**面試回答方式**：先給出三個常見防範手段——「對單一使用者或單一IP的請求頻率額外做更嚴格的限流、引入圖形驗證碼或人機驗證增加機器人腳本的難度和成本、以及對歷史上有異常搶購行為的帳號額外做更嚴格審查」。解釋這和之前限流概念的關聯與延伸——「這是把之前討論過的限流演算法，從針對整體系統流量這個粒度，延伸到針對單一使用者IP這個更細粒度，單純只對整體系統限流沒辦法防範大量看似合法的個別請求實際上都來自同一惡意使用者這種情況，需要同時在不同粒度層次做分層限流，才能更全面防範各種異常流量」。

### 如果秒殺結束後發現實際賣出的商品數量比庫存多了幾件（真的發生了超賣），你會怎麼補救？這種情況理論上不是已經被前面設計的機制防止了嗎？

**核心答案**：即使**理論上**前面已經設計的原子操作機制應該能防止超賣，實務上依然需要**準備一套補救機制**作為**最後一道防線**——具體做法包括——**(1) 對帳機制**：**定期地（或者秒殺活動結束後立即）比對 Redis 裡記錄的『已扣減庫存數』和資料庫裡真正建立的訂單數量**是否一致，如果**發現不一致**，代表某個環節出了非預期的問題，需要**進一步追查**；**(2) 若真的發生超賣，需要有明確的業務處理流程**：例如**依照搶購成功的時間先後順序**只保留前面真正在庫存範圍內的訂單，對**超賣的那幾筆訂單**主動聯繫使用者說明情況並提供補償（如優惠券或其他替代方案）。

**詳細解析**：這題要求展現一種**「即使理論上設計得很完善，依然要準備一套萬一出錯的補救機制」**這種**務實、不天真**的工程心態——這呼應了這篇文章反覆強調的核心認知——**任何一個理論上看似完美的機制，在真實世界裡的實際運作都可能因為各種未曾預料到的原因**（例如程式碼本身存在某個尚未被發現的 bug、或者 Redis 和資料庫之間在某個極端情況下出現資料不一致）而**依然出現例外**。一個**真正成熟、負責任**的系統設計**不應該**天真地假設**「我的機制理論上是完美的，所以不需要準備任何補救方案」**，而是應該**同時設計好「萬一真的發生了理論上不應該發生的情況，應該怎麼妥善補救」**這個額外的保護層。這種**「防範於未然」和「萬一真的出事如何善後」兩者都要準備**的思維，是一個經驗豐富的資深工程師和一個只會紙上談兵的候選人之間很鮮明的差異所在。

**面試回答方式**：先給出核心答案——「即使理論上原子操作機制應該能防止超賣，實務上依然需要準備一套補救機制作為最後一道防線，具體做法包括定期做對帳機制比對Redis記錄的已扣減庫存數和資料庫真正建立的訂單數量是否一致，以及如果真的發生超賣，要有明確的業務處理流程，例如依照搶購成功時間先後順序只保留真正在庫存範圍內的訂單，對超賣的訂單主動聯繫使用者說明並提供補償」。給出更深層的工程心態——「這反映了任何理論上看似完美的機制，在真實世界的實際運作都可能因為各種未曾預料的原因而出現例外，一個真正成熟負責任的系統設計不應該天真假設機制完美就不需要準備補救方案，而應該同時設計好萬一真的發生理論上不該發生的情況時應該如何妥善善後，這種防範於未然和萬一出事如何善後兩者都要準備的思維，正是資深工程師和只會紙上談兵的候選人之間很鮮明的差異」。
