# 題目

限流（Rate Limiting）器設計是拼多多（以及同類型的電商／社交裂變型公司，他們的流量經常因為活動或裂變分享而出現劇烈的瞬間波動）**相當常見**的面試題（根據公開面試經驗分享整理歸納而成，並非逐字官方紀錄）：**「請設計一個限流器元件，用來保護你的後端服務不會被突然湧入的流量打垮，並比較你會選用哪一種限流演算法」**

## 核心答案

常見的限流演算法主要有幾種——**(1) 固定視窗計數器（Fixed Window Counter）**：在一個固定的時間視窗內（例如每秒）累計請求數，超過門檻就拒絕，實作最簡單，但存在**視窗邊界的流量突刺**問題（見 [[../backend-engineering/006-rate-limiting-algorithms.md]]）；**(2) 滑動視窗（Sliding Window）**：改善固定視窗的邊界問題，用**更細緻的時間切片**去平滑地計算最近一段時間內的請求數；**(3) 漏桶演算法（Leaky Bucket）**：把請求放入一個固定容量的『桶』裡，用**固定不變的速率**往外處理，能強制把**忽快忽慢的流量整形成固定、平穩**的輸出速率；**(4) 令牌桶演算法（Token Bucket）**：**定期地往桶裡補充令牌**，請求需要**拿到令牌**才能被處理，這種做法**允許一定程度的突發流量（只要桶裡還有累積的令牌）**，同時長期而言依然能把平均速率控制在設定範圍內。實務上**令牌桶**是**最常被實際採用**的演算法，因為它能在**「限制長期平均速率」和「允許合理範圍內的突發流量」**之間取得較好的平衡。

## 詳細解析

**為什麼令牌桶比漏桶更受歡迎——允許合理的突發流量，更貼近真實使用情境**：**漏桶演算法**的核心特性是**強制把輸出速率壓平成固定不變**，這某種程度上是一種**過度保守**的設計——真實世界裡的流量**很少是完全均勻穩定**的，即使是**完全正常、合理**的使用情境，也可能出現**短暫的請求密集期**（例如使用者一次性地批次上傳好幾張照片），如果用漏桶這種**完全不允許任何突發**的設計，這種**合理的正常使用行為**也會被**不必要地限制、延遲**。**令牌桶**則透過**「允許累積一定數量的令牌，可以被一次性快速地消耗掉」**這個機制，讓**短暫的合理突發流量**能被正常地處理，只有**長時間持續**的高速率請求才會因為**令牌補充的速度跟不上消耗的速度**而逐漸被限制住。這種**「對短暫的合理突發更加寬容，但對長期持續的過量請求依然有效限制」**的特性，讓令牌桶更加**貼近真實世界的使用情境**。

**這題在拼多多這類社交裂變型公司特別重要的原因——流量經常因為分享裂變而瞬間暴增**：拼多多這類**依靠使用者互相分享、邀請**來驅動成長的產品，有一個**相當獨特**的流量特性——**「某一個分享連結可能因為被某個擁有大量粉絲的使用者轉發分享，而在極短時間內湧入遠超乎平常水準的巨量流量」**。這種**「流量規模事先完全無法預測、且可能在極短時間內劇烈飆升」**的特性，讓**限流機制**變得**格外重要**——如果沒有妥善的限流保護，一次**意外爆紅的分享**可能就會讓後端服務**直接被瞬間湧入的流量壓垮**。這也是為什麼面試官特別喜歡針對**這類社交裂變型產品**，考察候選人是否具備**設計能夠承受劇烈流量波動**的限流機制的能力。

**限流器應該設在哪一層——單一節點限流與全域分散式限流**：一個容易被追問到的細節是——**「你的限流器是只保護單一個伺服器節點，還是需要對整個系統做全域的流量控制」**——如果你的服務是**由多個節點一起共同承擔流量**，單純地讓**每一個節點各自獨立維護自己的限流計數**，可能會導致**「單一個使用者的請求剛好被分散打到不同的多個節點上」**，造成**「即使每一個節點各自看起來都沒有超過限制，但這個使用者實際上發出的總請求量早已遠遠超過你原本希望限制的總量」**。因應這種情況，需要把**限流的計數狀態集中儲存在一個所有節點共享的地方（例如 Redis）**，讓**所有節點**都**依照同一份共享的計數狀態**去做判斷，這種**「全域分散式限流」**才能真正準確地控制**整個系統對單一個使用者或單一個資源**的**總體**流量。

## 面試回答方式

先給出四種常見演算法的比較——「固定視窗計數器實作最簡單但存在視窗邊界流量突刺問題;滑動視窗用更細緻時間切片改善邊界問題;漏桶演算法把請求放入固定容量的桶，用固定不變速率往外處理，能強制整形流量;令牌桶演算法定期往桶裡補充令牌，請求需要拿到令牌才能被處理，允許一定程度突發流量同時長期依然能控制平均速率」。給出實務推薦——「令牌桶是最常被實際採用的演算法，因為能在限制長期平均速率和允許合理範圍內突發流量之間取得較好平衡」。可以解釋為什麼令牌桶更受歡迎——「漏桶強制把輸出速率壓平成固定不變是一種過度保守設計，真實世界的流量很少完全均勻穩定，令牌桶允許累積的令牌可以一次性快速消耗掉，讓短暫合理突發流量能被正常處理，只有長時間持續的高速率請求才會被逐漸限制住，更貼近真實使用情境」。一定要主動提到限流器應該設在哪一層這個關鍵細節——「如果服務由多個節點共同承擔流量，單純讓每個節點各自獨立維護限流計數，可能導致單一使用者請求分散打到不同節點，即使每個節點都沒超過限制，實際總請求量早已超過預期，需要把限流計數狀態集中儲存在所有節點共享的地方如Redis，做全域分散式限流」，展現你對限流器設計有完整且觸及架構層面細節的理解。

## 常見追問

### 令牌桶和漏桶這兩種演算法聽起來很相似（都涉及一個桶），你能更精確地說明它們運作機制的核心差異嗎？

**核心答案**：**核心差異在於『桶裡裝的是什麼』以及『驅動運作的方向』**——**漏桶**裝的是**請求本身**，請求先進入桶裡排隊，再由系統**用固定速率往外取出、處理**這些請求（如果桶滿了，新進來的請求就被丟棄）——這是**「控制輸出的速率」**；**令牌桶**裝的則是**令牌（一種抽象的許可憑證）**，系統**定期地往桶裡補充令牌**，而**請求本身**是**先嘗試去拿取一個令牌**，拿到才能被處理（拿不到就被拒絕或等待）——這是**「控制請求被允許通過的速率」**。這**兩者**雖然都涉及「桶」這個比喻，但**桶裡裝的東西和運作方向是相反的**。

**詳細解析**：這題要求對這兩個**容易被混為一談**的演算法做**更精確的機制區分**，而不是只停留在**「兩個都是某種流量控制演算法」**這種籠統的理解。理解這兩者的核心差異，關鍵在於思考**「這個桶到底在限制什麼」**——**漏桶****限制的是『輸出』**——不管**進來的請求速率有多快、多不規律**，漏桶都**強制用一個固定不變的速率**去處理它們，這種設計讓**輸出的速率永遠平穩，不會有任何突發**；而**令牌桶****限制的是『通過的許可』**——它**不直接對請求本身做任何速率上的整形**，而是透過**「令牌補充的速率」**去間接地控制**長期而言平均能夠通過的請求數量**，但**只要桶裡還有累積的令牌**，請求就可以**瞬間、一次性地**被處理（不受任何速率整形的限制）。這正是為什麼前面核心答案已經提到**令牌桶允許突發流量、而漏桶不允許**這個核心差異的根本原因。

**面試回答方式**：先給出核心差異——「核心差異在於桶裡裝的是什麼、以及驅動運作的方向，漏桶裝的是請求本身，先進入桶裡排隊，再由系統用固定速率往外取出處理，這是控制輸出的速率;令牌桶裝的是令牌這種抽象的許可憑證，系統定期往桶裡補充令牌，請求本身是先嘗試拿取一個令牌，拿到才能被處理，這是控制請求被允許通過的速率」。可以用一句話總結區別——「漏桶強制對輸出做速率整形讓輸出永遠平穩不允許任何突發;令牌桶不直接整形請求本身，只要桶裡還有累積令牌，請求就能瞬間被處理，這是為什麼令牌桶允許突發流量而漏桶不允許的根本原因」。

### 如果你的限流器判斷某個請求應該被拒絕，你會直接回傳錯誤，還是讓這個請求排隊等待？這兩種做法各自的取捨是什麼？

**核心答案**：這取決於**這個業務場景對即時性的要求**——如果這是一個**需要即時回應**的場景（例如使用者在前端頁面上等待一個 API 回應），**直接回傳錯誤**（如 HTTP 429 Too Many Requests）通常是更好的選擇——**讓使用者清楚地知道『目前系統忙碌，請稍後再試』**，比**讓他長時間乾等卻不知道究竟要等多久**體驗更好；但如果這是一個**非同步、對即時性要求不高**的場景（例如背景的批次處理任務），讓這個請求**進入一個佇列排隊等待**依序被處理，可能是更合理的做法（不浪費這個已經發出的請求，只是讓它晚一點才被處理）。

**詳細解析**：這題考察是否理解**限流之後的『因應方式』同樣需要依照具體業務場景做恰當選擇**，而不是只有單一種標準做法——這某種程度上呼應了這篇文章反覆強調的核心分析框架——**任何一個技術決策都需要回到『這個具體場景實際的需求是什麼』**去做出恰當的判斷——**同步、面向使用者的即時互動場景**優先重視**「讓使用者快速地得到一個明確的結果（即使是拒絕）」**；而**非同步、背景處理的場景**則可以更加重視**「盡可能不浪費已經發出的請求，只是稍微延後處理」**。這種**「先判斷場景性質，再決定恰當的因應方式」**的思路，正是避免把**任何一種單一做法一體適用套用到所有情境**的核心工程判斷力。

**面試回答方式**：先給出核心判斷準則——「這取決於這個業務場景對即時性的要求，如果是需要即時回應的場景，直接回傳錯誤(如HTTP 429)通常是更好選擇，讓使用者清楚知道系統目前忙碌請稍後再試，比讓他長時間乾等卻不知道要等多久體驗更好;但如果是非同步、對即時性要求不高的場景，讓請求進入佇列排隊等待依序處理，可能是更合理的做法」。可以總結——「限流之後的因應方式同樣需要依照具體業務場景做恰當選擇，而不是只有單一種標準做法」。

### 如果這個限流器是用來保護一個呼叫外部第三方 API 的服務（例如呼叫銀行的付款 API），你會額外考慮什麼？

**核心答案**：除了**保護自己的服務**以外，還需要額外地**遵守這個外部第三方 API 自己規定的呼叫頻率限制**（通常第三方 API 供應商會明確地公告「每秒最多允許幾次呼叫」這類限制）——這某種程度上是**限流器的方向反過來了**——這裡不是要保護自己不被別人打垮，而是要**確保自己不會因為呼叫過於頻繁**而**觸犯對方的限流規則**，被對方**拒絕服務、甚至被暫時封鎖**。因應這種情況，需要**明確地依照對方公告的限制**去設定自己這一端的**主動節流**機制，並且**額外地設計好『當對方真的拒絕了我的請求時，應該如何重試』**這類錯誤處理和重試策略（可以連結到前面已經深入討論過的重試與退避，見 [[../backend-engineering/018-retry-and-backoff.md]]）。

**詳細解析**：這題把**限流**這個核心概念延伸到一個**方向相反**的應用場景——考察是否能夠理解**限流機制不只是用來『保護自己』**，也可以被用來**『節制自己對外部依賴的呼叫行為，避免自己變成那個造成別人困擾的過量請求方』**。這種**「限流的角色可以是防守方、也可以是自律的請求方」**的雙重視角，是很多候選人容易忽略的面向——特別值得注意的是，當**呼叫外部服務真的遭到拒絕**時**不應該天真地立即重試**（這可能會讓情況變得更糟，甚至被對方判定為惡意的高頻攻擊），而應該套用**指數退避（Exponential Backoff）**這類**逐步拉長重試間隔**的策略，這直接呼應了前面（見 [[../backend-engineering/018-retry-and-backoff.md]]）已經深入討論過的核心重試設計原則。

**面試回答方式**：先給出核心額外考量——「除了保護自己的服務，還需要額外遵守這個外部第三方API自己規定的呼叫頻率限制，這裡限流器的方向反過來了，不是保護自己不被打垮，而是確保自己不會因為呼叫過於頻繁而觸犯對方限流規則，被拒絕服務甚至暫時封鎖」。給出具體的因應做法——「需要明確依照對方公告的限制，設定自己這端的主動節流機制，並額外設計好當對方真的拒絕請求時應該如何重試，不應該天真立即重試，而應該套用指數退避這類逐步拉長重試間隔的策略，避免情況變得更糟甚至被判定為惡意攻擊」。
