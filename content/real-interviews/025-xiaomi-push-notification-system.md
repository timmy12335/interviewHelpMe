# 題目

「設計一個推播系統」是小米這類**做手機與 IoT 裝置的公司**常被回報的系統設計題（根據公開的面試經驗分享整理歸納而成，並非逐字官方紀錄）：「我們需要在幾分鐘內把一則通知推送給一千萬台線上裝置。你會怎麼設計這個系統？」它同時考察**長連線的維護**、**大規模扇出（fan-out）**、**訊息可靠性**與**成本控制**，是一道能問得很深的題目。

## 核心答案

**整體拆成三層**。

**連線層**——**維護與裝置的長連線**（WebSocket 或自訂的 TCP 協定），**負責心跳與重連**；它需要記錄「哪個裝置連在哪一台接入伺服器上」這份路由資訊（通常放在 Redis）。

**推送層**——接收業務方的推播請求，做目標篩選（全體、標籤、名單）並產生任務；把大任務切成小批次寫進訊息佇列（見 [[../message-queue/001-kafka-architecture.md]]），由多個工作節點並行地取出並投遞。

**投遞層**——依照路由資訊找到裝置所在的接入伺服器並轉發；離線的裝置則寫入離線訊息儲存，等它上線時補推。

而千萬級的扇出關鍵在於「分批加並行」——把一千萬個目標切成數千個批次，由數百個工作節點並行處理；估算時要先算出「每秒要投遞多少則」再反推需要多少節點與連線層的容量。

## 詳細解析

「路由資訊的維護是這題的核心難點」：一千萬個長連線分佈在數百台接入伺服器上——而「裝置 A 連在哪一台」這份對應關係需要被高頻讀取；放 Redis 是常見做法，而要注意它的容量（一千萬個鍵）與更新頻率（每次連線與斷線都要寫）。**而斷線的清理特別容易出錯**——如果接入伺服器當機而沒有清掉路由，投遞層會把訊息送到一台已經死掉的機器；所以路由記錄應該帶 TTL 並由心跳續期，讓失效的記錄自動消失。

「長連線的成本主要在記憶體與檔案描述符」：每個連線需要維持緩衝區與狀態——單機幾十萬連線需要仔細調整核心參數與緩衝區大小（見 [[../computer-network/017-socket-and-port-exhaustion.md]]）；而連線層應該做得很薄（只負責收發與心跳），把業務邏輯放在後面的服務中，這樣才能用較少的資源支撐更多連線。

**「訊息的可靠性要分級」**：不是所有推播都需要同樣的保證——營運活動的通知丟一則沒關係，而支付成功的通知必須送到；**所以應該支援不同的等級**：盡力投遞（不重試）、至少一次（帶確認與重試）、以及需要落地的離線訊息；而全部用最高等級會讓成本無法承受。

**「重試與退避要小心驚群」**（見 [[../backend-engineering/018-retry-and-backoff.md]]）：一次機房故障後，數百萬台裝置會同時重連——如果沒有隨機的退避，剛恢復的接入層會立刻被打垮；所以客戶端的重連必須帶隨機抖動，而伺服器端也要有連線速率的限制。

## 面試回答方式

先給三層的拆分（連線層、推送層、投遞層）與各自的職責，再說明**千萬級扇出靠分批加並行**並主動做一次容量估算。加分點有四個：**路由資訊的維護是核心難點**，而路由記錄要帶 TTL 由心跳續期，避免當機後的殘留；長連線的成本主要在記憶體與檔案描述符，**所以連線層要做得很薄**；**訊息的可靠性要分級**——全部用最高等級成本無法承受；以及**重連的驚群效應**與隨機退避。

## 講稿

我會拆成三層。連線層、推送層、投遞層。

連線層維護跟裝置的長連線，負責心跳跟重連，並且記錄哪個裝置連在哪一台接入伺服器上。推送層接收業務方的請求，做目標篩選並把大任務切成小批次寫進訊息佇列。投遞層依照路由找到裝置所在的機器並轉發，離線的裝置寫進離線儲存，等它上線再補。

千萬級的扇出關鍵是分批加並行。我會先估算，如果要五分鐘內推完一千萬，那是每秒大約三萬三千則，再反推需要多少工作節點。

而我覺得這題的核心難點在路由資訊的維護。一千萬個連線分佈在幾百台機器上，這份對應關係要被高頻讀取。而斷線清理特別容易出錯，如果接入伺服器當機而沒清掉路由，投遞就會送到一台死掉的機器。所以路由記錄要帶存活時間，由心跳續期，讓失效的自動消失。

另外訊息可靠性要分級。營運通知丟一則沒關係，支付通知必須送到。全部用最高等級成本會撐不住。

## 常見追問

### 一次機房故障後，幾百萬台裝置同時重連怎麼辦？

**核心答案**：客戶端必須帶隨機抖動的指數退避，伺服器端要有連線速率的限制與分批放行。如果所有裝置在斷線後立刻重連——剛恢復的接入層會在一秒內收到數百萬個握手請求並再次崩潰；這就是驚群效應，而它會讓一次短暫的故障變成長時間的無法恢復。

**詳細解析**：這考察是否理解「恢復的過程本身也需要被設計」——很多系統的故障不是壞在當機那一刻，而是壞在恢復時被自己的客戶端打垮。**具體的手段有三個**：**客戶端的退避要有隨機成分**（如果所有裝置都是「等 1 秒、2 秒、4 秒」，它們仍然會同步）；伺服器端要能拒絕超出容量的連線並回傳「稍後再試」而非直接崩潰；以及可以在推播的下發中攜帶「建議的重連時間」讓伺服器主動打散。這個「把恢復當成一個需要被限流的流程」的思路，和前面討論過的限流與降級（見 [[../backend-engineering/008-service-degradation.md]]）是同一套原則的應用。

**面試回答方式**：先給三個手段（客戶端隨機退避、伺服器連線限流、伺服器主動指定重連時間）。核心加分點是指出很多系統不是壞在當機那一刻，而是壞在恢復時被自己的客戶端打垮，並補上細節：退避沒有隨機成分的話，所有裝置仍然會同步。收在連結：這是「把恢復當成需要被限流的流程」，和限流與降級是同一套原則。

### 怎麼支援「只推給特定標籤的使用者」？

**核心答案**：用預先建好的標籤到裝置的倒排索引，而不是在推播時掃全表。把「所有在台北、使用 Android、最近七天活躍」這類條件預先計算成裝置清單——**推播時直接取出並分批投遞**；而如果條件是任意組合的，就需要一個支援多條件交集的索引結構（例如用 bitmap 做集合運算，見 [[../redis/030-bitmap-operations.md]]）。

**詳細解析**：這考察「把查詢的成本從推播時移到寫入時」這個核心取捨——推播是一個對延遲敏感的操作（活動開始了要立刻推），而標籤的更新可以是非同步的；**所以預先計算是正確的方向**。用 bitmap 表示「有這個標籤的裝置集合」特別合適——因為多條件的交集與聯集就是位元運算，一千萬個裝置的 bitmap 只有約 1.25MB，而交集運算是毫秒級的。這個「用位元運算做大規模集合篩選」的技巧，在廣告投放與使用者分群系統中被廣泛使用；能主動提出它，通常會被認為對這類系統有實際的理解。

**面試回答方式**：給核心做法（預先建好標籤到裝置的倒排索引，不要在推播時掃全表）。核心加分點是說明取捨：把查詢成本從推播時移到寫入時，因為推播對延遲敏感而標籤更新可以非同步，並具體提出 **bitmap 做集合運算**（一千萬裝置約 1.25MB，交集是毫秒級）。收在應用：這個技巧在廣告投放與使用者分群系統中被廣泛使用。

### 怎麼避免同一則訊息被推兩次？

**核心答案**：**在投遞的路徑上做冪等**（見 [[../backend-engineering/003-idempotency-design.md]]）。給每則訊息一個唯一 ID——客戶端記錄最近收到的 ID 並丟棄重複的；同時伺服器端在重試時要帶同一個 ID 而非產生新的。因為在「至少一次」的投遞語意下，重複是無法完全避免的，所以去重必須在接收端做。

**詳細解析**：這考察是否理解「訊息系統的精確一次語意在端到端上是靠去重達成的」（見 [[../message-queue/012-idempotent-producer-transaction.md]]）——網路的不確定性意味著「送出了但沒收到確認」永遠可能發生；而在那個情況下，重試會造成重複而不重試會造成遺失；兩害相權，選擇重試加上接收端去重是標準的做法。而客戶端的去重需要一個有界的記憶（例如最近一千個 ID 或最近一小時內的），因為無限期地記住所有 ID 不實際；這個「有界的去重視窗」在實務上足夠，因為重試通常發生在短時間內。能指出「去重必須有時間或數量的邊界」，是這題比較深入的部分。

**面試回答方式**：給做法（唯一訊息 ID、重試時帶同一個、接收端去重）並說明為什麼去重必須在接收端。核心加分點是解釋「送出了但沒收到確認」永遠可能發生，於是重試加去重是兩害相權的標準做法。收在實務細節：客戶端的去重需要有界的記憶（最近 N 個或最近一小時），因為無限期記住所有 ID 不實際，而重試通常發生在短時間內所以這樣就夠。
