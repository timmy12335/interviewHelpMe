# 題目

這是京東（以及同類型的電商公司）在微服務（Microservices）架構相關職位面試裡**相當經典**的分散式一致性題（根據公開面試經驗分享整理歸納而成，並非逐字官方紀錄）：**「訂單服務和支付服務是兩個獨立的微服務，各自有自己的資料庫。當使用者下單付款時，需要同時『扣減庫存』和『完成扣款』，如果其中一個操作成功、另一個卻失敗了，你會怎麼設計，確保這兩個跨服務的操作最終能保持一致？」**

## 核心答案

這種**跨越多個獨立微服務、各自擁有獨立資料庫**的場景**沒有辦法**像在單一個資料庫裡那樣，直接依靠**傳統的資料庫交易（ACID）**去保證一致性（見 [[../database/007-transaction-acid.md]]）。業界常見的因應方案包括——**(1) 兩階段提交（2PC）**：透過一個中央協調者先詢問所有參與方是否都準備好可以提交，只有**全部都回答可以**才正式要求大家一起提交，這種做法能提供較強的一致性保證，但**效能較差、且協調者本身容易成為單點故障**；**(2) Saga 模式**：把整個跨服務的大流程拆解成一連串各自獨立的本地交易，**每一個步驟都額外設計一個對應的補償操作**，如果中途任何一步失敗，就依序執行前面已經成功步驟的補償操作，去把狀態撤銷、還原（見 [[../backend-engineering/014-saga-pattern-deep-dive.md]]）；**(3) 訊息佇列（Message Queue）加最終一致性（Eventual Consistency）**：用**可靠的訊息傳遞機制（如 Outbox Pattern，見 [[../backend-engineering/015-outbox-pattern.md]]）**確保「本地資料庫更新」和「發送通知其他服務的訊息」這兩件事要嘛一起成功、要嘛一起失敗，再透過**訊息佇列**讓其他服務最終都能收到這個變更通知，逐步達成最終一致性。實務上**電商場景最常見**的做法是 **Saga 模式搭配訊息佇列**，因為 2PC 的效能代價和單點故障風險通常**不適合**這種**高並發、高可用性要求**的場景。

## 詳細解析

**為什麼電商場景普遍不用 2PC——效能和可用性的權衡**：**兩階段提交**雖然理論上能提供**較強的一致性保證**，但它有一個**致命的實務缺陷**——在**第一階段（詢問是否準備好）和第二階段（要求正式提交）之間**，所有參與方都需要**持續鎖定自己的相關資源**，等待協調者的最終指令。這種**「長時間鎖定資源等待協調」**的做法在**高並發**的電商場景下（可能同一時間有**大量**訂單同時在處理）會導致**大量資源被長時間鎖住**，嚴重拖累整體的並行處理能力；同時**協調者本身**如果**發生故障**，所有正在等待它指令的參與方都會**被卡住**。這直接呼應了前面（見 [[../backend-engineering/016-cap-theorem.md]]）已經深入討論過的 CAP 權衡取捨——2PC 某種程度上是**用犧牲可用性和效能去換取更強的一致性**，而電商這類場景通常**更重視系統的可用性和處理效能**，因此普遍會選擇 **Saga 這類犧牲一部分即時一致性（改用最終一致性）去換取更高可用性和效能**的替代方案。

**Saga 模式的核心挑戰——補償操作不一定能完美地還原**：Saga 模式雖然解決了 **2PC 的效能和單點故障問題**，但它也帶來一個**需要被特別重視**的挑戰——**「補償操作是否真的能完美地把狀態還原到原本的樣子」**——舉例來說，「扣減庫存」這個操作，它對應的補償操作是「把庫存加回去」，這**相對直接**；但如果這中間**其他使用者**剛好也在同時搶購，**這筆被加回去的庫存**可能**已經被別人買走了**。這種**「補償操作不能簡單地假設世界還是原本的樣子」**的複雜性，是 Saga 模式實作時需要被特別審慎考量的細節——因此設計**每一個步驟對應的補償操作**時，都需要**仔細地思考**：「這個補償操作在**經過一段時間、且可能有其他並行操作介入**之後，依然能正確地達成補償的目的嗎？」

**Outbox Pattern 解決的具體問題——如何確保『更新本地資料庫』和『發送訊息通知』這兩件事不會只成功一半**：這是這題另一個容易被深入追問的細節——如果服務先**更新自己本地的資料庫（例如把訂單狀態改成已扣款）**，再**額外地去發送一則訊息**通知其他服務，這兩個動作**本身並不是**一個原子操作——如果**資料庫更新成功**，但**發送訊息這個動作卻剛好失敗**（例如網路瞬間中斷），就會導致**「本地狀態已經更新，但其他服務卻永遠不會收到這個變更通知」**這種不一致的窘境。**Outbox Pattern** 的解法是**把「需要被發送的訊息內容」也當作一筆資料，寫入到和業務資料同一個本地資料庫的交易裡**（這樣「更新業務資料」和「記錄需要被發送的訊息」就變成**同一個本地資料庫交易裡的兩個操作，具備原子性**），再透過一個**額外的背景程序**持續去讀取這個 Outbox 資料表裡的訊息紀錄，真正地把它發送出去。這種**「把原本需要橫跨兩個不同系統的原子性需求（本地 DB + 訊息佇列），轉化成只需要在單一個本地資料庫裡保證原子性」**的巧妙設計，正是 Outbox Pattern 之所以能有效解決這個一致性難題的核心巧思。

## 面試回答方式

先給出整體方案框架——「跨服務的一致性問題，沒辦法像單一資料庫那樣直接靠傳統交易保證，常見方案包括兩階段提交(協調者詢問所有參與方是否準備好才統一提交，但效能較差且協調者容易成為單點故障)、Saga模式(拆解成一連串本地交易，每步驟都設計對應的補償操作，失敗就依序執行前面已成功步驟的補償)、以及訊息佇列加最終一致性(用Outbox Pattern確保本地更新和發送通知訊息這兩件事一起成功或一起失敗)」。給出實務上的推薦選擇——「電商場景最常見的做法是Saga模式搭配訊息佇列，因為2PC的效能代價和單點故障風險，通常不適合高並發高可用性要求的場景」。可以補充Saga模式的細膩挑戰——「補償操作不一定能完美還原狀態，例如扣減庫存的補償是把庫存加回去，但如果中間有其他使用者搶購了這筆被加回去的庫存，補償操作就不能簡單假設世界還是原本的樣子」。可以補充Outbox Pattern的核心巧思——「把需要發送的訊息內容也當作一筆資料，寫入和業務資料同一個本地資料庫交易裡，這樣兩者就具備原子性，再透過背景程序持續讀取這個訊息紀錄真正發送出去，把原本需要橫跨兩個系統的原子性需求，轉化成只需要在單一本地資料庫裡保證」，展現你對分散式一致性問題有完整、且觸及實作細節的理解。

## 常見追問

### 如果選擇 Saga 模式，你會用「編排（Orchestration）」還是「協同（Choreography）」這兩種不同的 Saga 實作風格？各自的優缺點是什麼？

**核心答案**：**「編排（Orchestration）」**是設計一個**中央的協調者**，明確地依序去**指揮**每一個參與的服務該執行哪一個步驟，這種做法**流程清晰、容易追蹤和除錯**，但**這個中央協調者本身需要額外設計、維護**；**「協同（Choreography）」**則是**不存在任何中央協調者**，每一個服務**各自監聽其他服務發出的事件**，依照這些事件**自主地決定**自己接下來該做什麼（例如訂單服務發出『訂單已建立』事件，庫存服務監聽到這個事件，自己決定去扣減庫存），這種做法**服務之間耦合度更低**，但**當流程變得複雜**時，**整個流程的全貌**會變得**分散、難以被完整地掌握和追蹤**。

**詳細解析**：這題考察是否理解**這兩種設計風格本質上是『集中式控制』和『去中心化自主協調』**之間的權衡取捨——這某種程度上呼應了前面（見 [[../ai-agent/005-multi-agent-systems.md]] 相關概念）在**其他技術領域裡也反覆出現**的類似設計哲學——**編排（集中式）**讓**「整個流程的邏輯被集中記錄在單一個地方」**，這帶來**易於理解、易於除錯**的優勢（要理解整個流程，只需要去看這一個協調者）；而**協同（去中心化）**讓**每一個服務更加獨立自主**，不需要依賴一個中央協調者（這帶來更好的服務解耦），但代價是**當需要理解、除錯整個流程**時，你**沒有一個單一可以查看的地方**，必須**分散地去檢查好幾個不同服務各自的事件監聽邏輯**，才能拼湊出完整的流程全貌。實務上**流程相對複雜、涉及較多步驟**的場景通常更適合用**編排**（集中管理複雜度）；而**流程相對單純**的場景則可以考慮**協同**（享受更好的服務解耦）。

**面試回答方式**：先分別定義兩種風格——「編排是設計一個中央協調者明確依序指揮每個參與服務該執行哪個步驟，流程清晰容易追蹤除錯，但協調者本身需要額外設計維護;協同是不存在中央協調者，每個服務各自監聽其他服務發出的事件，自主決定自己接下來該做什麼，服務間耦合度更低，但流程複雜時整個流程全貌會變得分散難以完整掌握」。給出實務選擇建議——「流程相對複雜涉及較多步驟的場景通常更適合用編排來集中管理複雜度;流程相對單純的場景則可以考慮協同享受更好的服務解耦」。

### 如果 Outbox 表裡累積了大量還沒被成功發送的訊息，這代表什麼？你會怎麼排查？

**核心答案**：這代表**負責把 Outbox 表裡的訊息真正發送出去的那個背景程序**出現了某種問題——可能的原因包括——**(1) 這個背景程序本身當機或效能不足**：需要檢查這個背景程序的運作狀態，以及它**處理訊息的速度**是否跟得上**訊息被寫入的速度**；**(2) 訊息佇列服務本身發生故障或壅塞**：如果這個背景程序是把訊息**送往一個外部的訊息佇列服務**，需要確認這個外部服務本身是否正常運作。

**詳細解析**：這題考察是否理解 **Outbox Pattern 本身雖然解決了『本地更新和發送訊息不會只成功一半』**這個原子性問題，但它**並沒有**解決**「這則訊息最終究竟什麼時候會真正被發送出去」**這個**時效性**問題——Outbox Pattern 提供的是**「最終一定會被發送」**這種保證，但**「最終」究竟需要多久**，取決於**負責實際發送的背景程序是否正常、且有足夠的處理能力**。如果**這個背景程序本身出了問題**，即使 Outbox 表裡的訊息紀錄本身**依然完整存在**（不會遺失），這些訊息也會因為**沒有任何機制真正去把它們發送出去**，而**持續累積、遲遲無法被其他服務真正收到**。因此**監控 Outbox 表裡『尚未成功發送』的訊息數量是否持續異常累積**，是運維一個採用 Outbox Pattern 的系統時相當重要的**必要監控指標**。

**面試回答方式**：先給出核心判斷——「這代表負責把Outbox表裡的訊息真正發送出去的那個背景程序出現了問題，可能原因包括背景程序本身當機或效能不足跟不上訊息寫入速度、或者訊息佇列服務本身發生故障壅塞」。給出更深層的理解——「Outbox Pattern解決的是本地更新和發送訊息不會只成功一半的原子性問題，但沒有解決訊息最終究竟什麼時候會真正被發送出去這個時效性問題，如果背景程序本身出了問題，即使訊息紀錄本身完整存在不會遺失，也會持續累積遲遲無法被其他服務真正收到，因此監控Outbox表裡尚未成功發送的訊息數量是否持續異常累積，是運維這種系統的必要監控指標」。

### 如果「扣庫存」這個操作本身需要考慮前面已經討論過的高並發搶購場景（見前面美團那題），這和這裡討論的跨服務一致性問題要怎麼結合起來？

**核心答案**：這兩個問題實際上是處於**不同層次、但需要同時被滿足**的需求——**「高並發下如何正確地扣減庫存不超賣」**（見 [[004-meituan-flash-sale-system-design.md]]）處理的是**單一個庫存服務自己內部**如何正確、高效地處理大量並行的扣庫存請求；而**「跨服務一致性」**處理的是**「扣庫存這個動作本身成功之後，如何確保訂單服務、支付服務這些其他相關服務也都跟著正確地同步更新」**。實務上**這兩個機制需要被疊加組合**——**先**用**高並發安全的方式**（如 Redis 原子操作）快速地完成庫存的扣減判斷；**扣減成功之後**，才把**這個『庫存已扣減』的結果作為一個事件**，透過 **Saga 模式（或 Outbox Pattern）**去驅動後續訂單、支付這些其他服務的協調流程。

**詳細解析**：這題要求把**這篇文章兩個先前已經分別討論過的獨立主題（高並發庫存扣減、跨服務一致性）整合起來**，考察是否能看出這兩者實際上是**互補、而非互相衝突**的關係——**高並發庫存扣減**關注的是**『這個瞬間大量並行的請求湧入同一個服務時，如何快速、正確地處理』**這個**單一服務內部**的效能和正確性問題；而**跨服務一致性**關注的是**『這個單一服務的操作結果確定下來之後，如何正確地擴散傳播到其他相關服務』**。這兩者某種程度上是**先後接續**的關係（先在單一服務內快速正確地處理完眼前的高並發壓力；再把這個已經確定下來的結果，透過跨服務一致性機制傳播出去），而**不是****互相取代**的競爭方案。理解了這種**「不同的技術挑戰可能分別作用在不同的階段／層次，因而需要被依序疊加組合，而不是只能擇一」**的思路，某種程度上也呼應了這整個題庫反覆強調的核心分析框架。

**面試回答方式**：先釐清兩者處於不同層次——「高並發下如何正確扣庫存不超賣，處理的是單一庫存服務自己內部如何正確高效處理大量並行請求;跨服務一致性處理的是扣庫存成功之後，如何確保訂單支付這些其他服務也跟著正確同步更新，這兩個問題是不同層次但需要同時被滿足」。給出具體的整合做法——「實務上需要疊加組合，先用高並發安全的方式(如Redis原子操作)快速完成庫存扣減判斷，扣減成功之後才把這個結果作為一個事件，透過Saga模式或Outbox Pattern去驅動後續訂單支付等其他服務的協調流程」。
