# 題目

「彈幕系統的設計」是嗶哩嗶哩這類**影音社群平台**常被回報的題目（根據公開的面試經驗分享整理歸納而成，並非逐字官方紀錄）：**「一支熱門影片可能有數十萬條彈幕，而直播間裡每秒可能有上千條新彈幕。這兩種情況你會分別怎麼設計？」**這題的巧妙之處在於**點播與直播的需求完全不同**，而能否分辨這一點就是評分的分水嶺。

## 核心答案

**點播與直播是兩個不同的問題，必須分開設計。**

**點播的彈幕是「按時間軸的靜態資料」**——**使用者打開影片時，一次性或分段地拉取該時間區間的彈幕**；**所以它本質上是一個讀多寫少的儲存問題**：**按「影片 ID + 時間分片」組織資料（例如每五分鐘一個分片），用 CDN 或快取分發**（見 [[../system-design/005-cdn-design.md]]）；**因為同一支影片的彈幕對所有人都相同，快取的命中率極高。**

**直播的彈幕是「即時的廣播」**——**每條新彈幕要推送給房間內所有人**；**這是一個扇出問題**：**用長連線加房間的訂閱模型**，**而超大房間（十萬人以上）需要分層廣播**（一台機器負責一組使用者，訊息先到各機器再由各機器本地扇出）。

**兩者的共同要點是「限流與過濾」**——**單一使用者的發送頻率限制、敏感詞過濾、以及在彈幕過密時的抽樣顯示**（因為畫面本來就放不下每秒一千條）。

## 詳細解析

**「點播彈幕的分片設計決定了體驗」**：如果整支影片的彈幕一次拉完——**一支有五十萬條彈幕的影片會讓首次載入非常慢**；**而按時間分片（例如每三分鐘一段）並在播放接近下一段時預先載入，能讓載入量與播放進度相稱**。**而因為同一支影片的同一個分片對所有使用者都是相同的內容，它可以被 CDN 完整快取**——**這把一個看起來的高並發讀問題，變成了一個靜態資源分發問題**；**能指出這一點，通常會被認為抓到了題目的核心。**

**「直播的超大房間需要分層扇出」**：如果一台機器要把一條訊息推給十萬個連線——**它會成為瓶頸**；**而分層的做法是「訊息先廣播到所有持有該房間連線的機器（幾十台），再由每台機器對自己的幾千個連線本地推送」**；**於是扇出的成本被分散**。**這與前面討論過的推播系統（見 [[025-xiaomi-push-notification-system.md]]）是同一個模式。**

**「彈幕過密時的抽樣是必要的」**：畫面上能同時顯示的彈幕有物理上限——**每秒一千條全部推給客戶端既浪費頻寬又無法顯示**；**所以伺服器端應該做抽樣（保留一定比例）並優先保留高互動或付費的彈幕**；**而客戶端也要有自己的顯示上限。**

**「儲存的成本要考慮」**：彈幕的量極大而單條很小——**用關聯式資料庫逐條儲存的成本很高**；**常見的做法是「按分片聚合成一個大物件」（例如把一個時間分片的所有彈幕壓縮成一筆記錄或一個檔案），於是儲存與讀取的效率都大幅提升**；**代價是新增彈幕時需要處理併發的追加。**

## 面試回答方式

先明確區分**點播與直播是兩個不同的問題**並分別給出設計，再給共同的要點（限流、過濾、抽樣）。加分點有四個：**點播的分片設計**與**它可以被 CDN 完整快取**這個關鍵洞察；**直播的超大房間需要分層扇出**；**彈幕過密時的抽樣是必要的**；以及**儲存的成本**與按分片聚合的做法。

## 講稿

我覺得這題的關鍵是點播跟直播是兩個不同的問題，必須分開設計。

點播的彈幕是按時間軸的靜態資料。使用者打開影片時分段拉取該時間區間的彈幕。所以它本質上是一個讀多寫少的儲存問題。我會按影片 ID 加上時間分片來組織，比如每三分鐘一段，播放接近下一段時預先載入。

而這裡有一個關鍵，同一支影片的同一個分片對所有使用者都是相同的內容。所以它可以被 CDN 完整快取。這就把一個看起來的高並發讀問題，變成了靜態資源分發問題。

直播的彈幕完全不同，它是即時廣播，每條要推給房間內所有人。這是扇出問題。而超大房間需要分層廣播，訊息先到所有持有該房間連線的機器，再由每台機器對自己的幾千個連線本地推送。

另外彈幕過密時抽樣是必要的。畫面能顯示的有物理上限，每秒一千條全推給客戶端既浪費頻寬又顯示不出來。

## 常見追問

### 彈幕要怎麼跟影片的播放進度精確對齊？

**核心答案**：**彈幕記錄的是「影片內的相對時間」而非發送的絕對時間**。每條彈幕存的是「這條出現在影片的第幾秒」——**於是無論使用者何時觀看、是否有快轉或暫停，都能正確地對齊**；**而客戶端在播放時依照當前的播放位置決定要顯示哪些。**

**詳細解析**：這考察**「選對時間的參考系」這個看似簡單但常被弄錯的設計**——**如果存的是發送的牆上時間，那只有直播的當下有意義，而錄影回放時就完全對不上**；**這也解釋了為什麼直播的彈幕在轉成回放時需要一次轉換（把絕對時間換算成相對於影片開始的偏移）**。**而快轉與拖曳帶來的實際問題是「跳到某個位置時要快速取得那個位置附近的彈幕」**——**這正是按時間分片儲存的另一個好處：拖曳到第二十分鐘時只需要載入對應的那一個分片**；**如果彈幕是一整包，就得等全部載完。**

**面試回答方式**：給核心（**存影片內的相對時間而非發送的絕對時間**）並說明它為什麼能正確對齊。核心加分點是指出**選對時間的參考系**這個設計，並說明直播轉回放時需要一次換算。收在連結：**拖曳時要快速取得該位置的彈幕，正是按時間分片儲存的另一個好處**——**只需載入對應的分片而非整包**。

### 敏感詞過濾要怎麼做才夠快？

**核心答案**：**用多模式字串匹配的資料結構（AC 自動機或字典樹）而非逐個詞比對**（見 [[../algorithms/014-trie.md]]）。把所有敏感詞建成一棵樹並加上失敗指標——**於是掃描一條彈幕的成本是 O(彈幕長度)，與詞庫的大小無關**；**而逐個詞用字串搜尋則是 O(詞數 × 長度)，在詞庫有數萬個詞時完全不可行。**

**詳細解析**：這考察**「用對資料結構把複雜度的量級降下來」**——**AC 自動機本質上是 KMP 演算法（見 [[../algorithms/015-string-matching-kmp.md]]）在多模式上的推廣**；**它一次掃描就能找出所有出現的敏感詞**。**而實務上的難點不在演算法而在對抗**：**使用者會用同音字、拆字、插入符號、或者諧音來繞過**；**所以除了精確匹配還需要正規化（去除符號、繁簡轉換、拼音比對）與模型判斷**。**這個「規則負責高精度的已知樣式、模型負責泛化的未知變體」的組合，是內容審核系統的標準架構**（見 [[../system-design/043-content-moderation-design.md]]）；**而純規則的系統會不斷被繞過，純模型的系統則誤判太多。**

**面試回答方式**：給資料結構（**AC 自動機或字典樹**）與複雜度的對比。核心加分點是指出它是 **KMP 在多模式上的推廣**並說明一次掃描找出所有詞。收在實務難點：**難點不在演算法而在對抗**（同音字、拆字、插入符號），**所以需要正規化加模型判斷**；**而「規則負責高精度的已知樣式、模型負責泛化的未知變體」是內容審核的標準架構**。

### 如果一支影片突然爆紅，彈幕量暴增怎麼辦？

**核心答案**：**讀的部分靠快取與 CDN 自然吸收，寫的部分靠限流與非同步落地**。因為熱門影片的彈幕讀取是高度可快取的——**讀的壓力反而不大**；**而寫入的暴增則用訊息佇列削峰**（見 [[../message-queue/010-consumer-lag-backlog.md]]），**先寫進佇列並立即回應使用者，再由消費者按穩定的速率落地。**

**詳細解析**：這考察**「讀與寫的擴展策略截然不同」**這個基本認知——**讀可以靠快取與複本近乎無限地擴展，而寫必須真正落地所以只能靠削峰與分片**；**而彈幕的場景恰好是「讀極多但可快取、寫較少但突發」**。**用佇列削峰在這裡特別合適，因為彈幕對「立即持久化」的要求不高**——**使用者發出後立刻在自己的畫面上看到（樂觀顯示），而實際落地晚幾百毫秒完全無感**。**這個「用業務對延遲的容忍度換取系統的彈性」的判斷，是熱點處理中最有價值的一步**；**而它的前提是你真的問過「這裡到底需要多即時」**。

**面試回答方式**：分讀與寫給出不同的策略並指出熱門影片的讀取高度可快取。核心加分點是**讀與寫的擴展策略截然不同**——**讀可以靠快取近乎無限擴展，寫只能靠削峰與分片**。收在關鍵判斷：**用業務對延遲的容忍度換取系統的彈性**——**彈幕發出後樂觀顯示，實際落地晚幾百毫秒完全無感**；**而前提是你真的問過「這裡到底需要多即時」**。
