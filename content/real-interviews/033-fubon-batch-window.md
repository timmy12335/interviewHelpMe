# 題目

「批次作業視窗不足」是台灣金控與銀行的資訊部門常被回報的實務題（根據公開的面試經驗分享整理歸納而成，並非逐字官方紀錄）：**「我們的日終批次原本兩小時跑完，現在要跑五小時，而營業時間開始前必須完成。你會怎麼分析與處理？」**這題考察的不是新技術，而是**在既有約束下做有效優化的能力**——**而這正是傳統金融業資訊部門最需要的能力。**

## 核心答案

**第一步一定是「先量測而非先優化」**——**把整個批次拆成各個作業並記錄各自的耗時**；**因為多數情況下，五小時中有四小時集中在一兩個作業上，而不是均勻分布**（見 [[../database/016-slow-query-optimization.md]]）。

**接著按四個方向處理**：

**消除不必要的工作**——**是不是每天都在全量重算本來可以增量處理的東西**；**這通常是收益最大的一項。**

**優化最慢的那幾個**——**索引、SQL 改寫、批次大小的調整、以及避免逐筆處理**（見 [[../database/006-explain.md]]）。

**改變依賴的結構讓能並行的並行**——**畫出作業之間的依賴圖，把沒有依賴關係的作業同時跑**；**很多批次是歷史上串成一條線的，實際上大部分可以並行。**

**最後才是「把部分工作移出視窗」**——**改成日中的增量處理或者準即時的串流**（見 [[../system-design/020-batch-vs-stream-processing.md]]）。

## 詳細解析

**「依賴圖是這題最有價值的產出」**：許多長年運行的批次，作業之間的順序是「當年寫的時候的順序」而非真正的資料依賴——**畫出實際的依賴之後，常常會發現二十個作業中只有五個必須串行**；**而把其餘的並行化，可能直接把時間砍半**。**這個分析的成本不高（讀程式碼與訪談維護者）而收益很大**；**它也是「先理解再優化」這個原則的具體實踐。**

**「逐筆處理是傳統批次最常見的效能殺手」**：在迴圈中對每一筆資料執行一次 SQL——**一百萬筆就是一百萬次往返**；**改成批次讀取、在記憶體中處理、批次寫回，常常能有數十倍的改善**（見 [[../database/045-bulk-loading.md]]）。**而這類程式碼在舊系統中極為常見，因為它寫起來最直觀。**

**「可重跑性比速度更重要」**：批次跑到一半失敗——**如果不能從斷點繼續而必須整個重來，那在視窗緊張時是災難**；**所以每個作業都應該是冪等的且能記錄進度**（見 [[../backend-engineering/003-idempotency-design.md]]）。**在優化的同時補上這個能力，往往比單純的加速更有價值**——**因為它把「失敗的成本」從幾小時降到幾分鐘。**

**「改成即時處理不是萬靈丹」**：把日終的計算改成即時，聽起來很現代——**但它會讓系統複雜度大幅提升、需要處理亂序與遲到的資料、而且對帳的難度增加**；**在金融的核心帳務中，日終批次的「有一個明確的結算時點」本身就是一個有價值的性質**。**所以應該優先窮盡前三個方向，把架構的改變當成最後手段。**

## 面試回答方式

先強調**第一步是量測而非優化**並說明耗時通常集中在少數作業，再給四個方向並排出順序。加分點有四個：**依賴圖是最有價值的產出**——**常常發現二十個作業只有五個必須串行**；**逐筆處理是最常見的效能殺手**；**可重跑性比速度更重要**——**它把失敗的成本從幾小時降到幾分鐘**；以及**改成即時處理不是萬靈丹**，**日終批次的明確結算時點本身就是有價值的性質**。

## 講稿

第一步一定是先量測而不是先優化。我會把整個批次拆成各個作業並記錄各自耗時。因為多數情況下，五小時裡有四小時集中在一兩個作業上，不是均勻分布的。

接著我會按四個方向處理，而且有順序。

第一是消除不必要的工作，看是不是每天都在全量重算本來可以增量的東西。這通常收益最大。第二是優化最慢的那幾個，索引、SQL 改寫、避免逐筆處理。

第三我覺得是最有價值的一項，畫出作業之間的依賴圖。很多長年運行的批次，順序是當年寫的時候的順序而不是真正的資料依賴。畫出來之後常常會發現二十個作業裡只有五個必須串行，把其餘的並行化可能直接把時間砍半。

第四才是把部分工作移出視窗，改成日中的增量或串流。

另外我會順手補上可重跑性。批次跑到一半失敗如果不能從斷點繼續，在視窗緊張時是災難。

## 常見追問

### 如果那個最慢的作業是一段沒人敢改的舊程式呢？

**核心答案**：**先建立「改動前後結果一致」的驗證機制，再動它**。具體的做法是：**把某一天的輸入與輸出完整地保存下來作為基準**、**寫一個能自動比對新舊結果的腳本**、**然後在測試環境用真實的資料驗證改動不改變輸出**；**有了這層保護，改舊程式的風險就從「不敢動」變成「可控」。**

**詳細解析**：這考察**「處理遺留系統的正確順序是先建立安全網再改動」**（見 [[../behavioral/010-taking-over-legacy-system.md]]）——**沒有驗證機制時，任何改動都是賭博，所以理性的人選擇不動**；**而一旦有了自動比對，改動就變成一件可以逐步進行的事**。**而對批次系統來說這特別可行，因為它的輸入輸出是明確的資料集而非互動式的行為**——**「同樣的輸入產生同樣的輸出」是一個容易自動化的驗證**。**這個「先讓改動變得可驗證，再開始改」的順序，在面試中比直接說「我會重構它」有說服力得多**；**因為它展示了你理解為什麼那段程式碼一直沒人敢動。**

**面試回答方式**：給三個步驟（保存基準、寫比對腳本、用真實資料驗證）並指出它把風險從「不敢動」變成「可控」。核心加分點是點出**處理遺留系統的正確順序是先建立安全網再改動**，並說明批次系統特別適合（輸入輸出是明確的資料集）。收在說服力：**這比直接說「我會重構它」有說服力，因為它展示了你理解為什麼那段程式碼一直沒人敢動**。

### 增加硬體能解決嗎？

**核心答案**：**能爭取時間但通常不是根本解**。如果瓶頸是 CPU 或 I/O 且作業本身能並行——**加硬體確實有效**；**但如果瓶頸是「串行的依賴」或者「單一 SQL 的執行計畫很差」，加再多機器也沒用**。**所以判斷的順序仍然是先找出瓶頸的性質，再決定加硬體是不是對的答案。**

**詳細解析**：這考察**「Amdahl 定律在實務中的意義」**（見 [[../java-concurrency/041-amdahl-and-contention.md]]）——**如果一個流程中有百分之四十是無法並行的部分，那即使把可並行的部分加速到無限快，總時間也只能降到原本的百分之四十**；**所以「串行部分的佔比」決定了加硬體的收益上限**。**而在金融的批次中，串行的部分往往是「必須等前一個作業產出的結果」這類真實的資料依賴**——**它們無法靠硬體解決，只能靠改變流程或者消除依賴**。**能用這個框架回答「加硬體有沒有用」，比憑直覺回答有力得多**；**而它也給了一個具體的量化方式：先算出串行部分的比例，就知道加硬體最多能省多少。**

**面試回答方式**：給條件式的答案（**能爭取時間但通常不是根本解**）並區分兩種瓶頸。核心加分點是引用 **Amdahl 定律**——**串行部分的佔比決定了加硬體的收益上限**，並指出金融批次中的串行部分往往是真實的資料依賴。收在量化：**先算出串行部分的比例，就知道加硬體最多能省多少**。

### 怎麼說服主管投入時間做這件事？

**核心答案**：**用「風險」而非「效率」來論述**。「批次跑五小時而視窗只有六小時，一旦某天資料量增加或發生一次重跑，就會延誤開業」——**這是一個營運風險而非技術債**；**而金融業的主管對「延誤開業」這件事的敏感度，遠高於對「跑得比較快」的興趣。**

**詳細解析**：這考察**「把技術問題翻譯成對方在乎的語言」**（見 [[../behavioral/036-selling-tech-debt-work.md]]）——**同一件事說成「我想優化批次效能」與說成「我們現在只剩一小時的緩衝，去年已經有兩次差點延誤」，得到的回應完全不同**；**而後者是可以被量化與追蹤的**。**具體的做法是「把緩衝時間畫成一張趨勢圖」**——**過去十二個月的批次耗時與視窗的比例，如果那條線在收斂，那圖本身就是最好的論據**；**而這種「用趨勢展示風險正在逼近」的呈現方式，比任何論述都更能促成決定**。**因為它把一個抽象的擔憂，變成了一個看得見的時間表。**

**面試回答方式**：給核心策略（**用風險而非效率論述**）並示範措辭的差別。核心加分點是指出金融業主管對「延誤開業」的敏感度遠高於「跑得比較快」，並給出具體做法：**把緩衝時間畫成過去十二個月的趨勢圖**。收在效果：**用趨勢展示風險正在逼近，比任何論述都更能促成決定**——**它把抽象的擔憂變成看得見的時間表**。
