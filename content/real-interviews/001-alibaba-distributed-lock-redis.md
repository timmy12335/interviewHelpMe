# 題目

這是，中國一線大廠(阿里巴巴,及,同類型公司如,騰訊、京東)，在，後端/中介軟體相關職位面試裡，**相當,經典、幾乎,必考**的一題(根據，公開的面試經驗分享,整理,歸納,而成，並非,逐字,官方紀錄)：**「如果，要，你，用,Redis,實作一個,分散式鎖，你，會，怎麼設計？這個,設計，可能，存在,哪些,漏洞或風險？」**面試官，通常，會，依照，你，第一輪的回答，持續,追問,好幾層，一路,逼問到，你，是否，真的，理解,每一個,細節,背後的原因。

## 核心答案

一個，**相對,完整**的Redis分散式鎖設計，至少，需要，涵蓋，几個關鍵環節——**(1) 上鎖,要,用,原子操作**：用，`SET key value NX PX <expire_time>`,這種,單一,原子指令,同時完成,『檢查鎖是否存在』和『設定鎖,並，帶上過期時間』，而，**不能**，分成，兩個,獨立的指令(先,檢查、再,設定)，因為，這種，分開的做法，在，並行環境下，會，出現，競態條件；**(2) 鎖的value,需要,是,一個,獨一無二的識別碼**(例如，UUID)，**而，不是**，一個，固定的值，這樣，才能，確保，**「解鎖時，只，解開,自己上的那把鎖，而，不會，誤解,別人的鎖」**；**(3) 解鎖,同樣,需要,是，原子操作**——用，Lua腳本，把，「檢查,這把鎖的value,是否,真的,是,自己」和「刪除這把鎖」，包在，同一個,原子操作裡執行；**(4) 一定要,設定,過期時間**，避免，如果，持有鎖的服務,意外,當機，這把鎖，永遠,不會被釋放，導致，其他服務，永久,無法,取得鎖(死鎖)。這種設計，依然，存在,幾個,已知的風險——**業務執行時間,超過,鎖的過期時間、以及,Redis主從架構下的鎖失效問題**，這，兩點，正是，面試官，最愛，追問的核心。

## 詳細解析

**這題,真正,在,考什麼——面試官,想知道,你,是否,真的,理解,原子性,和,並行安全**：中國大廠,的面試風格，特別,偏好，用，這種，**看似,常見、但，魔鬼藏在細節裡**的題目，去，篩選，候選人，是否，只是，**背了,結論(用Redis的SETNX做鎖)**，還是，**真正,理解**，每一個,設計決策,背後的並行安全考量——如果，你，回答，「上鎖,就是,用SETNX,指令」，卻，**答不出來**，「為什麼,不能,先用GET,檢查,再用SET上鎖」，面試官，會，立刻，判斷，你，只是，**記憶了,表面的答案**，這個題目，其實，是，前面(見 [[../redis/014-distributed-lock.md]])已經,深入討論過的分散式鎖核心概念,的一個,**應用實戰版本**——建議，先，回頭，把，那一題,的核心原理，徹底,搞懂，再，回來，練習，這一題，怎麼，在，面試現場，**用,更精簡、更貼近,面試節奏**的方式，把，這些,原理，講清楚。

**中國大廠,面試,特有的追問節奏——會,一路,問到,你,故意,設計出來的方案,依然,有漏洞為止**：中國一線大廠(尤其是，阿里、騰訊,這類，**中介軟體/基礎架構團隊**特別,重視,細節)的面試風格，有，一個，**相當,鮮明**的特徵——**面試官，不會，滿足於,你,給出,一個,『看起來,正確』的方案，就，停止追問**，而是，會，持續地，**針對，你，剛剛,提出的方案，故意，設計出,一個,更刁鑽的邊界情境**，去，測試，你，的方案，是否，依然，禁得起考驗——例如，你，可能，回答，「加上過期時間，就，能，避免死鎖」，面試官，很可能，立刻，追問，「如果，你的業務邏輯，執行,超過了,鎖的過期時間，會，發生,什麼事？」，這種，**「持續深挖,直到,找出方案的破綻」**的面試風格，某種程度上，反映了，這些,公司,實際上,面對的工程情境——他們，的系統，通常，**規模龐大、流量極高**，任何一個，看似,細微的邊界情況,漏洞，在，真實的高流量場景下，都，可能，被，放大,成，嚴重的生產事故，因此，他們，特別，重視，候選人，是否，具備，這種，**主動,發現、質疑,自己方案漏洞**的工程思維，而，不是，只，滿足於，一個，表面上，可以運作的答案。

**如何,在,面試現場,展現,你,已經,想過,更進階的方案(Redlock)，但,依然,能,講清楚,它的取捨**：一個，能，讓，面試官，眼睛一亮的加分回答方式，是，**主動,提到**，Redis作者提出的**Redlock演算法**(在,多個,獨立的Redis節點上，同時,嘗試上鎖，只有，在，超過半數節點,都，成功上鎖時，才，視為，真正取得鎖)，這種，做法，能夠，緩解，**單一個Redis節點,發生故障或主從切換,導致鎖失效**這個風險，但，同時，**誠實地，指出**，Redlock,本身，也，存在，學術界的爭議(如，知名的分散式系統學者Martin Kleppmann,曾經,提出,質疑，認為，Redlock,在，某些,極端的時序情境下，依然，無法，保證，絕對的安全性)，這種，**「知道,更進階的方案、但，也，理解,這個方案,本身,的侷限，而，不是，把它,當作,萬靈丹」**的回答方式，遠比，單純地，丟出一個,聽起來厲害的名詞,更能，展現，你，**真正的技術判斷力**。

## 面試回答方式

先，給出基本設計——「用SET key value NX PX expire這個原子指令上鎖，value用UUID這種獨一無二的識別碼，解鎖時用Lua腳本原子性地檢查value是否是自己、再刪除」。主動,點出，這個設計,依然存在的已知風險，展現,批判性思維——「這個設計依然有兩個已知風險：第一是業務執行時間可能超過鎖的過期時間，導致鎖提前釋放；第二是如果Redis是主從架構，主節點在鎖還沒同步到從節點時當機，可能導致鎖失效」。可以,主動,提出，緩解方案——「針對第一個風險，可以用背景執行緒定期幫鎖續期(這種做法在一些成熟的分散式鎖框架裡被稱為看門狗機制)；針對第二個風險，可以考慮Redlock演算法，但同時要誠實說明它本身在極端時序下依然有理論上的爭議，不是絕對安全的銀彈」。展現,你，理解，這類問題,沒有,完美答案，只有,依照,實際業務場景,做,恰當取捨。

## 常見追問

### 如果,業務邏輯,執行時間,不確定，可能,超過,鎖的過期時間，你，會，怎麼處理？

**核心答案**：常見的做法，是，引入，一個，**「看門狗(Watchdog)」機制**——在，成功,取得鎖之後，額外地，啟動,一個,背景執行緒，**定期地(例如,每隔,過期時間的1/3)，去，檢查，這個業務邏輯，是否，還在，執行中**，如果，還在，就，**主動地，去，幫,這把鎖，續期(重新,延長,它的過期時間)**，直到，業務邏輯，真正,執行完成，才，讓，這個看門狗，停止續期、並，正常地，釋放鎖，這種做法，在，一些，成熟的分散式鎖框架(如,Redisson)裡，已經，是，**內建的標準機制**。

**詳細解析**：這題，考察，是否，能，針對，自己,主動,提出的風險，給出，一個，具體、可行的緩解方案，而，不是，只，停留在，「知道有這個風險」這個層次。看門狗機制,的核心思路，是，**把，『鎖的存活時間』，和，『業務邏輯,實際,需要,執行多久』，這，两件事情，解耦**——不再，天真地，假設，一開始，設定的過期時間，一定，足夠，涵蓋，整個業務邏輯,的執行時間，而是，**持續地，用一個,獨立的背景機制，去，監控、動態延長**，這把鎖的有效期，直到，業務,真正,結束。需要，補充的是，這種機制，也，帶來，新的複雜度——如果，這個,持有鎖的服務,本身，**發生了,某種,異常(如,執行緒,卡死、或,GC,長時間停頓)**，導致，看門狗,本身,也，無法,正常運作，這把鎖，依然，可能，因為，**沒有,被,續期**，而，過期釋放，這種,情況下，某種程度上，又，回到了，最初，需要,靠,過期時間,來,避免死鎖,的保護機制，這，某種程度上，也，呼應了，這篇文章,反覆,強調的核心認知——任何一種,緩解機制，都，有，它，自己的適用邊界，不能，被，當作,絕對萬能的解方。

**面試回答方式**：直接給出方案——「引入看門狗機制，取得鎖後額外啟動一個背景執行緒，定期檢查業務邏輯是否還在執行，如果是就主動幫鎖續期，直到業務完成才停止續期並正常釋放鎖，這在Redisson這類成熟框架裡是內建標準機制」。可以補充邊界情況——「但如果持有鎖的服務本身發生異常導致看門狗也無法正常運作，這把鎖依然可能因沒被續期而過期釋放，這種機制不是絕對萬能的」。

### 如果,你的服務,同時,需要,用到,好幾把,不同的分散式鎖，你，會，特別,注意,什麼，避免,造成死鎖？

**核心答案**：**需要，特別,注意，加鎖的順序,是否,一致**——如果，不同的服務,實例，各自，用，**不一致的順序**，去，取得，多把,不同的鎖(例如，服務A，先，取得鎖1、再，取得鎖2；但，服務B，卻，先，取得鎖2、再，取得鎖1)，就，可能，出現，**經典的死鎖情境**——服務A,持有鎖1、等待鎖2；服務B,持有鎖2、等待鎖1，兩者，互相,等待，永遠，無法，繼續，因應，這種風險，最，直接的做法，是，**明確地，規定,一套,固定的加鎖順序**(例如，永遠，依照,鎖的名稱,字母順序，由小到大,依序,取得)，確保，**所有,需要,同時,取得,多把鎖**的服務，都，遵循，同一套,固定順序。

**詳細解析**：這題，把，Java併發程式設計裡，早已,深入討論過的**多鎖死鎖**核心概念(見 [[../java-concurrency/017-deadlock-conditions-and-troubleshooting.md]])，直接，遷移應用到，分散式鎖,這個,新的具體場景，考察，是否，能，看出，**這，兩個,情境(單機多執行緒、分散式多服務)，背後,共享,相同的核心成因**——不管，是，**單一台機器裡的多個執行緒**、還是，**分散在,不同機器上的多個服務**，只要，涉及，**多個,獨立的執行單位，需要，同時,取得,多個,共享資源**，如果，**取得資源的順序,不一致**，就，都，可能，導致，經典的**循環等待,死鎖**，這種，「識別出,不同層次的技術情境,背後,共享,相同的核心成因」的能力，是，中國大廠,面試官,特別,喜歡,考驗的**融會貫通**能力——他們，很常，故意，用，一個，**看起來,是,全新技術情境**的問題(如，分散式鎖)，去，測試，你，是否，能，把，**基礎的作業系統/並行程式設計原理**，正確地，遷移應用過來，而，不是，把，每一個,新技術名詞，都，當成，一個，需要，重新,學習的獨立知識點。

**面試回答方式**：先給出核心答案——「需要特別注意加鎖順序是否一致，如果不同服務用不一致順序取得多把鎖，可能出現經典的循環等待死鎖，因應做法是明確規定一套固定加鎖順序，例如永遠依照鎖名稱字母順序由小到大依序取得」。可以主動連結到基礎知識——「這其實和單機多執行緒情境下,為什麼要求鎖的取得順序一致以避免死鎖,是同一個核心原理,只是場景從單機的執行緒換成分散式的多個服務而已」。

### 除了,Redis,以外，你，還，知道,哪些,實作分散式鎖的方式？各自的優缺點,是,什麼？

**核心答案**：常見的替代方案，包括，**(1) 基於,Zookeeper的分散式鎖**：利用,Zookeeper的**暫時性,循序節點(Ephemeral Sequential Node)**特性,來,實作，優勢,是，**天生,具備,更強的一致性保證**(Zookeeper,本身，是，基於，ZAB這種,共識演算法,設計，比,單純的Redis,更不容易,出現前面已經討論過的主從切換,鎖失效問題)，但，**效能,相對,較低**(每次,加鎖解鎖,都，涉及，較,複雜的節點,建立/監聽機制)；**(2) 基於,資料庫的分散式鎖**：利用,資料庫的,唯一索引約束,或,悲觀鎖(見 [[../database/024-optimistic-vs-pessimistic-lock.md]])，實作,相對,簡單，但，**效能,通常,是,這幾種方案裡,最差的**(每次,加解鎖，都，需要，一次,資料庫,I/O)。**Redis**,的優勢，則，是，**效能最高**(基於,記憶體運作)，但，需要，額外,處理，前面,已經,深入討論過的,主從一致性議題。

**詳細解析**：這題，考察，是否，具備，**技術選型的全局視野**，而，不是，只，把，Redis,當成,唯一的分散式鎖實作方式——中國大廠,的面試官，很,喜歡，用，這種，**「除了A,還有沒有其他方案」**的問法，去，檢驗，候選人，的技術廣度，以及，是否，能，針對，**不同方案,各自的取捨**，給出，**有條理的比較**，而，不是，只，含糊地，說，「都，可以，用」。回答，這類問題,的核心，關鍵，在於，**清楚地，指出，每一種方案,背後，所，依賴的底層機制**——Zookeeper,之所以，一致性更強，是，因為，它，底層，依賴，**共識演算法**這種，**為了,一致性,而,設計**的機制(這，會，帶來，額外的效能代價)；資料庫,之所以，效能較差，是，因為，**每一次,加解鎖，都，涉及，一次,完整的磁碟I/O和交易處理流程**；而，Redis,之所以，效能最高，是，因為，它，**本質上，是，一個,基於,記憶體運作的系統**，這種，「把，每一種方案的優缺點，回歸到，它，底層,運作機制,的根本差異，而，不是，只，背誦,表面的優缺點清單」的回答方式，能，展現，**更,紮實的系統設計理解**。

**面試回答方式**：先列出三種常見方案並各自定位——「除了Redis,常見的還有基於Zookeeper的分散式鎖(利用暫時性循序節點實作)、以及基於資料庫的分散式鎖(利用唯一索引約束或悲觀鎖)」。給出優缺點比較並回歸到底層機制——「Zookeeper基於共識演算法設計,一致性保證最強但效能較低;資料庫方案實作最簡單但效能通常是三者裡最差的,因為每次加解鎖都要一次資料庫I/O;Redis效能最高因為是基於記憶體運作,但需要額外處理主從一致性議題」。可以總結——「實務上會依照業務對一致性和效能的相對要求,去選擇最適合的方案,沒有絕對最好的選擇」。
