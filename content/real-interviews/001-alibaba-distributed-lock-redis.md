# 題目

這是中國一線大廠（阿里巴巴及騰訊、京東等同類型公司）在後端／中介軟體相關職位面試裡**相當經典、幾乎必考**的一題（根據公開面試經驗分享整理歸納而成，並非逐字官方紀錄）：**「如果要你用 Redis 實作一個分散式鎖（Distributed Lock），你會怎麼設計？這個設計可能存在哪些漏洞或風險？」**面試官通常會依照你第一輪的回答持續追問好幾層，一路逼問到你是否真的理解每一個細節背後的原因。

## 核心答案

一個**相對完整**的 Redis 分散式鎖設計至少需要涵蓋幾個關鍵環節——**(1) 上鎖要用原子操作**：用 `SET key value NX PX <expire_time>` 這種單一原子指令同時完成『檢查鎖是否存在』和『設定鎖並帶上過期時間』，而**不能**分成兩個獨立的指令（先檢查、再設定），因為這種分開的做法在並行環境下會出現競態條件；**(2) 鎖的 value 需要是一個獨一無二的識別碼**（例如 UUID）**而不是**一個固定的值，這樣才能確保**「解鎖時只解開自己上的那把鎖，而不會誤解別人的鎖」**；**(3) 解鎖同樣需要是原子操作**——用 Lua 腳本把「檢查這把鎖的 value 是否真的是自己」和「刪除這把鎖」包在同一個原子操作裡執行；**(4) 一定要設定過期時間**，避免如果持有鎖的服務意外當機，這把鎖永遠不會被釋放，導致其他服務永久無法取得鎖（死鎖）。這種設計依然存在幾個已知的風險——**業務執行時間超過鎖的過期時間，以及 Redis 主從架構下的鎖失效問題**，這兩點正是面試官最愛追問的核心。

## 詳細解析

**這題真正在考什麼——面試官想知道你是否真的理解原子性和並行安全**：中國大廠的面試風格特別偏好用這種**看似常見、但魔鬼藏在細節裡**的題目，去篩選候選人是否只是**背了結論（用 Redis 的 SETNX 做鎖）**，還是**真正理解**每一個設計決策背後的並行安全考量——如果你回答「上鎖就是用 SETNX 指令」，卻**答不出來**「為什麼不能先用 GET 檢查、再用 SET 上鎖」，面試官會立刻判斷你只是**記憶了表面的答案**。這個題目其實是前面（見 [[../redis/014-distributed-lock.md]]）已經深入討論過的分散式鎖核心概念的一個**應用實戰版本**——建議先回頭把那一題的核心原理徹底搞懂，再回來練習這一題怎麼在面試現場**用更精簡、更貼近面試節奏**的方式把這些原理講清楚。

**中國大廠面試特有的追問節奏——會一路問到你設計出來的方案依然有漏洞為止**：中國一線大廠（尤其是阿里、騰訊這類**中介軟體／基礎架構團隊**特別重視細節）的面試風格有一個**相當鮮明**的特徵——**面試官不會滿足於你給出一個『看起來正確』的方案就停止追問**，而是會持續地**針對你剛剛提出的方案故意設計出一個更刁鑽的邊界情境**，去測試你的方案是否依然禁得起考驗——例如你可能回答「加上過期時間就能避免死鎖」，面試官很可能立刻追問「如果你的業務邏輯執行超過了鎖的過期時間，會發生什麼事？」。這種**「持續深挖，直到找出方案的破綻」**的面試風格，某種程度上反映了這些公司實際上面對的工程情境——他們的系統通常**規模龐大、流量極高**，任何一個看似細微的邊界情況漏洞，在真實的高流量場景下都可能被放大成嚴重的生產事故，因此他們特別重視候選人是否具備這種**主動發現、質疑自己方案漏洞**的工程思維，而不是只滿足於一個表面上可以運作的答案。

**如何在面試現場展現你已經想過更進階的方案（Redlock），但依然能講清楚它的取捨**：一個能讓面試官眼睛一亮的加分回答方式，是**主動提到** Redis 作者提出的 **Redlock 演算法**（在多個獨立的 Redis 節點上同時嘗試上鎖，只有在超過半數節點都成功上鎖時，才視為真正取得鎖），這種做法能夠緩解**單一個 Redis 節點發生故障或主從切換導致鎖失效**這個風險，但同時**誠實地指出** Redlock 本身也存在學術界的爭議（如知名的分散式系統學者 Martin Kleppmann 曾經提出質疑，認為 Redlock 在某些極端的時序情境下依然無法保證絕對的安全性）。這種**「知道更進階的方案，但也理解這個方案本身的侷限，而不是把它當作萬靈丹」**的回答方式，遠比單純地丟出一個聽起來厲害的名詞更能展現你**真正的技術判斷力**。

## 面試回答方式

先給出基本設計——「用SET key value NX PX expire這個原子指令上鎖，value用UUID這種獨一無二的識別碼，解鎖時用Lua腳本原子性地檢查value是否是自己、再刪除」。主動點出這個設計依然存在的已知風險，展現批判性思維——「這個設計依然有兩個已知風險：第一是業務執行時間可能超過鎖的過期時間，導致鎖提前釋放；第二是如果Redis是主從架構，主節點在鎖還沒同步到從節點時當機，可能導致鎖失效」。可以主動提出緩解方案——「針對第一個風險，可以用背景執行緒定期幫鎖續期(這種做法在一些成熟的分散式鎖框架裡被稱為看門狗機制)；針對第二個風險，可以考慮Redlock演算法，但同時要誠實說明它本身在極端時序下依然有理論上的爭議，不是絕對安全的銀彈」。展現你理解這類問題沒有完美答案，只有依照實際業務場景做恰當取捨。

## 常見追問

### 如果業務邏輯執行時間不確定，可能超過鎖的過期時間，你會怎麼處理？

**核心答案**：常見的做法是引入一個**「看門狗（Watchdog）」機制**——在成功取得鎖之後額外地啟動一個背景執行緒，**定期地（例如每隔過期時間的 1/3）去檢查這個業務邏輯是否還在執行中**，如果還在就**主動地去幫這把鎖續期（重新延長它的過期時間）**，直到業務邏輯真正執行完成，才讓這個看門狗停止續期並正常地釋放鎖。這種做法在一些成熟的分散式鎖框架（如 Redisson）裡已經是**內建的標準機制**。

**詳細解析**：這題考察是否能針對自己主動提出的風險給出一個具體、可行的緩解方案，而不是只停留在「知道有這個風險」這個層次。看門狗機制的核心思路是**把『鎖的存活時間』和『業務邏輯實際需要執行多久』這兩件事情解耦**——不再天真地假設一開始設定的過期時間一定足夠涵蓋整個業務邏輯的執行時間，而是**持續地用一個獨立的背景機制去監控、動態延長**這把鎖的有效期，直到業務真正結束。需要補充的是，這種機制也帶來新的複雜度——如果這個持有鎖的服務本身**發生了某種異常（如執行緒卡死、或 GC 長時間停頓）**，導致看門狗本身也無法正常運作，這把鎖依然可能因為**沒有被續期**而過期釋放；這種情況下某種程度上又回到了最初需要靠過期時間來避免死鎖的保護機制。這某種程度上也呼應了這篇文章反覆強調的核心認知——任何一種緩解機制都有它自己的適用邊界，不能被當作絕對萬能的解方。

**面試回答方式**：直接給出方案——「引入看門狗機制，取得鎖後額外啟動一個背景執行緒，定期檢查業務邏輯是否還在執行，如果是就主動幫鎖續期，直到業務完成才停止續期並正常釋放鎖，這在Redisson這類成熟框架裡是內建標準機制」。可以補充邊界情況——「但如果持有鎖的服務本身發生異常導致看門狗也無法正常運作，這把鎖依然可能因沒被續期而過期釋放，這種機制不是絕對萬能的」。

### 如果你的服務同時需要用到好幾把不同的分散式鎖，你會特別注意什麼來避免造成死鎖？

**核心答案**：**需要特別注意加鎖的順序是否一致**——如果不同的服務實例各自用**不一致的順序**去取得多把不同的鎖（例如服務 A 先取得鎖 1、再取得鎖 2；但服務 B 卻先取得鎖 2、再取得鎖 1），就可能出現**經典的死鎖情境**——服務 A 持有鎖 1、等待鎖 2；服務 B 持有鎖 2、等待鎖 1，兩者互相等待，永遠無法繼續。因應這種風險最直接的做法是**明確地規定一套固定的加鎖順序**（例如永遠依照鎖的名稱字母順序由小到大依序取得），確保**所有需要同時取得多把鎖**的服務都遵循同一套固定順序。

**詳細解析**：這題把 Java 併發程式設計裡早已深入討論過的**多鎖死鎖**核心概念（見 [[../java-concurrency/017-deadlock-conditions-and-troubleshooting.md]]）直接遷移應用到分散式鎖這個新的具體場景，考察是否能看出**這兩個情境（單機多執行緒、分散式多服務）背後共享相同的核心成因**——不管是**單一台機器裡的多個執行緒**、還是**分散在不同機器上的多個服務**，只要涉及**多個獨立的執行單位需要同時取得多個共享資源**，如果**取得資源的順序不一致**，就都可能導致經典的**循環等待死鎖**。這種「識別出不同層次的技術情境背後共享相同的核心成因」的能力，是中國大廠面試官特別喜歡考驗的**融會貫通**能力——他們很常故意用一個**看起來是全新技術情境**的問題（如分散式鎖）去測試你是否能把**基礎的作業系統／並行程式設計原理**正確地遷移應用過來，而不是把每一個新技術名詞都當成一個需要重新學習的獨立知識點。

**面試回答方式**：先給出核心答案——「需要特別注意加鎖順序是否一致，如果不同服務用不一致順序取得多把鎖，可能出現經典的循環等待死鎖，因應做法是明確規定一套固定加鎖順序，例如永遠依照鎖名稱字母順序由小到大依序取得」。可以主動連結到基礎知識——「這其實和單機多執行緒情境下，為什麼要求鎖的取得順序一致以避免死鎖，是同一個核心原理，只是場景從單機的執行緒換成分散式的多個服務而已」。

### 除了 Redis 以外，你還知道哪些實作分散式鎖的方式？各自的優缺點是什麼？

**核心答案**：常見的替代方案包括——**(1) 基於 Zookeeper 的分散式鎖**：利用 Zookeeper 的**暫時性循序節點（Ephemeral Sequential Node）**特性來實作，優勢是**天生具備更強的一致性保證**（Zookeeper 本身是基於 ZAB 這種共識演算法設計，比單純的 Redis 更不容易出現前面已經討論過的主從切換鎖失效問題），但**效能相對較低**（每次加鎖解鎖都涉及較複雜的節點建立／監聽機制）；**(2) 基於資料庫的分散式鎖**：利用資料庫的唯一索引約束或悲觀鎖（Pessimistic Lock）（見 [[../database/024-optimistic-vs-pessimistic-lock.md]]）實作，相對簡單，但**效能通常是這幾種方案裡最差的**（每次加解鎖都需要一次資料庫 I/O）。**Redis** 的優勢則是**效能最高**（基於記憶體運作），但需要額外處理前面已經深入討論過的主從一致性議題。

**詳細解析**：這題考察是否具備**技術選型的全局視野**，而不是只把 Redis 當成唯一的分散式鎖實作方式——中國大廠的面試官很喜歡用這種**「除了 A，還有沒有其他方案」**的問法，去檢驗候選人的技術廣度，以及是否能針對**不同方案各自的取捨**給出**有條理的比較**，而不是只含糊地說「都可以用」。回答這類問題的核心關鍵在於**清楚地指出每一種方案背後所依賴的底層機制**——Zookeeper 之所以一致性更強，是因為它底層依賴**共識演算法**這種**為了一致性而設計**的機制（這會帶來額外的效能代價）；資料庫之所以效能較差，是因為**每一次加解鎖都涉及一次完整的磁碟 I/O 和交易處理流程**；而 Redis 之所以效能最高，是因為它**本質上是一個基於記憶體運作的系統**。這種「把每一種方案的優缺點回歸到它底層運作機制的根本差異，而不是只背誦表面的優缺點清單」的回答方式，能展現**更紮實的系統設計理解**。

**面試回答方式**：先列出三種常見方案並各自定位——「除了Redis，常見的還有基於Zookeeper的分散式鎖(利用暫時性循序節點實作)、以及基於資料庫的分散式鎖(利用唯一索引約束或悲觀鎖)」。給出優缺點比較並回歸到底層機制——「Zookeeper基於共識演算法設計，一致性保證最強但效能較低;資料庫方案實作最簡單但效能通常是三者裡最差的，因為每次加解鎖都要一次資料庫I/O;Redis效能最高因為是基於記憶體運作，但需要額外處理主從一致性議題」。可以總結——「實務上會依照業務對一致性和效能的相對要求，去選擇最適合的方案，沒有絕對最好的選擇」。
