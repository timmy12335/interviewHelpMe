# 題目

這是中國一線大廠（阿里巴巴及騰訊、京東等同類型公司）在後端／中介軟體相關職位面試裡**相當經典、幾乎必考**的一題（根據公開面試經驗分享整理歸納而成，並非逐字官方紀錄）：**「如果要你用 Redis 實作一個分散式鎖（Distributed Lock），你會怎麼設計？這個設計可能存在哪些漏洞或風險？」**面試官通常會依照你第一輪的回答持續追問好幾層，一路逼問到你是否真的理解每一個細節背後的原因。

## 核心答案

一個**相對，完整**的Redis分散式鎖設計，至少需要涵蓋，幾個關鍵環節——**(1) 上鎖，要用，原子操作**：用，`SET key value NX PX <expire_time>`這種單一原子指令同時完成,『檢查鎖是否存在』和『設定鎖，並帶上過期時間』，而**不能**分成兩個，獨立的指令(先，檢查、再設定)因為這種，分開的做法，在並行環境下，會出現，競態條件；**(2) 鎖的value，需要是一個，獨一無二的識別碼**(例如，UUID)**而不是**一個固定的值這樣才能確保**「解鎖時只解開，自己上的那把鎖，而不會誤解，別人的鎖」**；**(3) 解鎖同樣需要是，原子操作**——用，Lua腳本，把「檢查，這把鎖的value，是否真的是，自己」和「刪除這把鎖」，包在同一個，原子操作裡執行；**(4) 一定要設定過期時間**避免如果，持有鎖的服務，意外當機這把鎖永遠，不會被釋放，導致其他服務永久無法，取得鎖(死鎖)。這種設計依然存在幾個，已知的風險——**業務執行時間，超過，鎖的過期時間、以及，Redis主從架構下的鎖失效問題**，這兩點正是面試官最愛，追問的核心。

## 詳細解析

**這題真正在，考什麼——面試官，想知道你是否真的理解原子性和，並行安全**：中國大廠，的面試風格，特別偏好用這種**看似常見、但，魔鬼藏在細節裡**的題目，去篩選候選人是否，只是**背了，結論(用Redis的SETNX做鎖)**，還是**真正理解**每一個設計決策，背後的並行安全考量——如果，你回答「上鎖就是，用SETNX，指令」，卻**答不出來**「為什麼不能，先用GET，檢查，再用SET上鎖」，面試官會立刻判斷你，只是**記憶了，表面的答案**，這個題目其實，是前面(見 [[../redis/014-distributed-lock.md]])已經深入討論過的分散式鎖核心概念，的一個,**應用實戰版本**——建議，先回頭把那一題，的核心原理，徹底搞懂再回來練習這一題怎麼在面試現場**用，更精簡、更貼近，面試節奏**的方式，把這些原理講清楚。

**中國大廠面試，特有的追問節奏——會，一路問到你故意，設計出來的方案，依然有漏洞為止**：中國一線大廠(尤其是，阿里、騰訊這類，**中介軟體/基礎架構團隊**特別，重視，細節)的面試風格，有一個**相當，鮮明**的特徵——**面試官，不會滿足於你給出一個『看起來，正確』的方案，就停止追問**，而是會持續地**針對你剛剛，提出的方案，故意設計出一個，更刁鑽的邊界情境**，去測試你的方案是否依然，禁得起考驗——例如，你可能回答，「加上過期時間，就能避免死鎖」面試官很可能立刻追問「如果，你的業務邏輯，執行超過了，鎖的過期時間，會發生什麼事？」這種**「持續深挖直到，找出方案的破綻」**的面試風格，某種程度上，反映了這些公司實際上，面對的工程情境——他們，的系統通常，**規模龐大、流量極高**，任何一個看似，細微的邊界情況，漏洞在，真實的高流量場景下，都可能被放大成，嚴重的生產事故，因此，他們特別重視候選人是否具備這種**主動發現、質疑，自己方案漏洞**的工程思維，而不是只滿足於一個表面上，可以運作的答案。

**如何在面試現場展現你已經想過，更進階的方案(Redlock)，但依然能講清楚，它的取捨**：一個，能讓面試官，眼睛一亮的加分回答方式，是**主動提到**，Redis作者提出的**Redlock演算法**(在，多個獨立的Redis節點上，同時嘗試上鎖只有在，超過半數節點，都成功上鎖時，才視為，真正取得鎖)，這種做法能夠緩解，**單一個Redis節點，發生故障或主從切換，導致鎖失效**這個風險，但同時**誠實地指出**，Redlock，本身也存在，學術界的爭議(如，知名的分散式系統學者Martin Kleppmann，曾經提出質疑認為，Redlock，在某些，極端的時序情境下，依然無法保證，絕對的安全性)，這種**「知道，更進階的方案、但，也理解這個方案本身的侷限而不是把它當作，萬靈丹」**的回答方式，遠比單純地丟出一個，聽起來厲害的名詞，更能展現你，**真正的技術判斷力**。

## 面試回答方式

先，給出基本設計——「用SET key value NX PX expire這個原子指令上鎖，value用UUID這種獨一無二的識別碼，解鎖時用Lua腳本原子性地檢查value是否是自己、再刪除」。主動點出這個設計，依然存在的已知風險，展現，批判性思維——「這個設計依然有兩個已知風險：第一是業務執行時間可能超過鎖的過期時間，導致鎖提前釋放；第二是如果Redis是主從架構，主節點在鎖還沒同步到從節點時當機，可能導致鎖失效」。可以主動提出，緩解方案——「針對第一個風險，可以用背景執行緒定期幫鎖續期(這種做法在一些成熟的分散式鎖框架裡被稱為看門狗機制)；針對第二個風險，可以考慮Redlock演算法，但同時要誠實說明它本身在極端時序下依然有理論上的爭議，不是絕對安全的銀彈」。展現你理解這類問題沒有完美答案只有依照，實際業務場景，做恰當取捨。

## 常見追問

### 如果，業務邏輯執行時間不確定可能超過，鎖的過期時間，你會，怎麼處理？

**核心答案**：常見的做法，是引入一個，**「看門狗(Watchdog)」機制**——在，成功，取得鎖之後，額外地啟動一個，背景執行緒，**定期地(例如，每隔，過期時間的1/3)，去檢查，這個業務邏輯，是否還在執行中**如果還在就**主動地去幫這把鎖續期(重新延長，它的過期時間)**，直到業務邏輯真正執行完成才讓，這個看門狗，停止續期、並，正常地釋放鎖這種做法在一些，成熟的分散式鎖框架(如，Redisson)裡，已經是，**內建的標準機制**。

**詳細解析**：這題，考察是否能針對自己主動，提出的風險，給出一個，具體、可行的緩解方案，而不是只停留在，「知道有這個風險」這個層次。看門狗機制，的核心思路，是**把『鎖的存活時間』，和『業務邏輯實際需要執行多久』這两件事情，解耦**——不再，天真地假設一開始，設定的過期時間，一定足夠涵蓋，整個業務邏輯，的執行時間，而是**持續地用一個，獨立的背景機制，去監控、動態延長**，這把鎖的有效期，直到業務真正結束。需要補充的是這種機制也帶來，新的複雜度——如果，這個持有鎖的服務，本身**發生了某種異常(如執行緒卡死、或GC，長時間停頓)**，導致看門狗本身也無法正常運作這把鎖依然可能因為**沒有被續期**而過期釋放這種情況下，某種程度上，又回到了最初需要靠過期時間來避免死鎖，的保護機制，這某種程度上，也呼應了這篇文章反覆，強調的核心認知——任何一種，緩解機制都有它，自己的適用邊界，不能被當作，絕對萬能的解方。

**面試回答方式**：直接給出方案——「引入看門狗機制，取得鎖後額外啟動一個背景執行緒，定期檢查業務邏輯是否還在執行，如果是就主動幫鎖續期，直到業務完成才停止續期並正常釋放鎖，這在Redisson這類成熟框架裡是內建標準機制」。可以補充邊界情況——「但如果持有鎖的服務本身發生異常導致看門狗也無法正常運作，這把鎖依然可能因沒被續期而過期釋放，這種機制不是絕對萬能的」。

### 如果，你的服務同時需要用到好幾把，不同的分散式鎖，你會特別注意什麼避免，造成死鎖？

**核心答案**：**需要，特別注意，加鎖的順序，是否一致**——如果，不同的服務，實例各自用，**不一致的順序**，去取得多把，不同的鎖(例如，服務A先，取得鎖1、再，取得鎖2；但服務B，卻先，取得鎖2、再，取得鎖1)就可能出現，**經典的死鎖情境**——服務A，持有鎖1、等待鎖2；服務B，持有鎖2、等待鎖1，兩者互相等待永遠無法繼續因應這種風險最，直接的做法，是**明確地規定一套，固定的加鎖順序**(例如，永遠依照鎖的名稱字母順序由小到大依序取得)確保**所有需要同時取得，多把鎖**的服務，都遵循同一套，固定順序。

**詳細解析**：這題，把Java併發程式設計裡，早已，深入討論過的**多鎖死鎖**核心概念(見 [[../java-concurrency/017-deadlock-conditions-and-troubleshooting.md]])直接遷移應用到，分散式鎖這個，新的具體場景，考察是否能看出**這兩個，情境(單機多執行緒、分散式多服務)，背後共享，相同的核心成因**——不管，是**單一台機器裡的多個執行緒**、還是，**分散在，不同機器上的多個服務**，只要涉及**多個，獨立的執行單位，需要同時取得多個共享資源**如果，**取得資源的順序，不一致**就都可能導致，經典的**循環等待，死鎖**這種「識別出，不同層次的技術情境，背後共享，相同的核心成因」的能力，是中國大廠面試官特別喜歡，考驗的**融會貫通**能力——他們，很常故意用一個**看起來是，全新技術情境**的問題(如，分散式鎖)去測試你是否能把，**基礎的作業系統/並行程式設計原理**，正確地，遷移應用過來，而不是把每一個，新技術名詞，都當成一個需要重新，學習的獨立知識點。

**面試回答方式**：先給出核心答案——「需要特別注意加鎖順序是否一致，如果不同服務用不一致順序取得多把鎖，可能出現經典的循環等待死鎖，因應做法是明確規定一套固定加鎖順序，例如永遠依照鎖名稱字母順序由小到大依序取得」。可以主動連結到基礎知識——「這其實和單機多執行緒情境下，為什麼要求鎖的取得順序一致以避免死鎖，是同一個核心原理，只是場景從單機的執行緒換成分散式的多個服務而已」。

### 除了，Redis，以外你還知道哪些，實作分散式鎖的方式？各自的優缺點，是什麼？

**核心答案**：常見的替代方案，包括**(1) 基於，Zookeeper的分散式鎖**：利用，Zookeeper的**暫時性，循序節點(Ephemeral Sequential Node)**特性，來實作優勢是**天生具備，更強的一致性保證**(Zookeeper，本身是基於，ZAB這種，共識演算法，設計比，單純的Redis，更不容易，出現前面已經討論過的主從切換，鎖失效問題)，但**效能相對較低**(每次加鎖解鎖都涉及較，複雜的節點，建立/監聽機制)；**(2) 基於，資料庫的分散式鎖**：利用，資料庫的，唯一索引約束，或悲觀鎖（Pessimistic Lock）(見 [[../database/024-optimistic-vs-pessimistic-lock.md]])實作相對簡單，但**效能通常是，這幾種方案裡，最差的**(每次，加解鎖都需要一次資料庫I/O)。**Redis**,的優勢則是，**效能最高**(基於，記憶體運作)，但需要額外處理前面已經，深入討論過的，主從一致性議題。

**詳細解析**：這題，考察是否具備，**技術選型的全局視野**，而不是只把，Redis，當成，唯一的分散式鎖實作方式——中國大廠，的面試官很喜歡用這種**「除了A，還有沒有其他方案」**的問法，去檢驗候選人，的技術廣度，以及是否能針對**不同方案，各自的取捨**，給出，**有條理的比較**，而不是只含糊地說「都可以用」。回答這類問題的核心關鍵在於**清楚地指出，每一種方案，背後所，依賴的底層機制**——Zookeeper，之所以，一致性更強，是因為它底層依賴，**共識演算法**這種，**為了一致性而，設計**的機制(這，會帶來額外的效能代價)；資料庫之所以效能較差是因為**每一次加解鎖都涉及一次，完整的磁碟I/O和交易處理流程**；而Redis，之所以效能最高是因為它**本質上是一個基於，記憶體運作的系統**，這種「把，每一種方案的優缺點，回歸到它底層運作機制，的根本差異，而不是只背誦，表面的優缺點清單」的回答方式，能展現**更，紮實的系統設計理解**。

**面試回答方式**：先列出三種常見方案並各自定位——「除了Redis，常見的還有基於Zookeeper的分散式鎖(利用暫時性循序節點實作)、以及基於資料庫的分散式鎖(利用唯一索引約束或悲觀鎖)」。給出優缺點比較並回歸到底層機制——「Zookeeper基於共識演算法設計，一致性保證最強但效能較低;資料庫方案實作最簡單但效能通常是三者裡最差的，因為每次加解鎖都要一次資料庫I/O;Redis效能最高因為是基於記憶體運作，但需要額外處理主從一致性議題」。可以總結——「實務上會依照業務對一致性和效能的相對要求，去選擇最適合的方案，沒有絕對最好的選擇」。
