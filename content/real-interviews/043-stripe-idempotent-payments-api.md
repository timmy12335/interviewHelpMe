# 題目

「設計一個冪等的支付 API」是 Stripe 這類**金融基礎設施公司**常被回報的深度題（根據公開的面試經驗分享整理歸納而成，並非逐字官方紀錄）：**「客戶端呼叫你的付款 API，網路逾時了但它不知道到底成功沒有。它重試會發生什麼？你要怎麼設計才能保證不重複扣款？」**這題考察的是**分散式系統中最根本的問題之一**——**而它的正確答案有很多細節。**

## 核心答案

**核心機制是「客戶端提供的冪等鍵（Idempotency-Key）」**——**客戶端為每一次邏輯上的付款生成一個唯一的鍵並放在請求標頭中**；**伺服器端用這個鍵判斷「這是新的請求還是重試」。**

**伺服器端的處理有三種情況**：**鍵是新的**——**執行付款並把「鍵、請求的指紋、結果」一起儲存**；**鍵已存在且請求相同**——**直接回傳先前的結果，不再執行**；**鍵已存在但請求的內容不同**——**回傳錯誤，因為那表示客戶端誤用了同一個鍵。**

**而最容易被忽略的細節是「請求進行中的併發重試」**——**如果第一次還沒完成、第二次就來了**；**這時應該回傳「處理中，請稍後重試」而非同時執行兩次**；**做法是先用鍵搶一個鎖或者插入一筆「處理中」的記錄（用唯一約束）。**

**另外要決定「鍵保留多久」**——**通常是 24 小時到數天**；**太短會讓延遲的重試失效，太長則儲存成本增加。**

## 詳細解析

**「記錄請求的指紋是關鍵的安全措施」**：如果只用鍵判斷而不比對請求的內容——**一個 bug 讓客戶端用同一個鍵送出不同金額的付款，第二次會靜默地回傳第一次的結果**；**於是使用者以為付了 200 元其實只付了 100 元**。**所以要把請求的內容雜湊後一起儲存並在重試時比對**；**不一致就回傳明確的錯誤，讓問題在開發階段就被發現。**

**「冪等記錄與業務操作必須在同一個交易中」**（見 [[../database/007-transaction-acid.md]]）：如果先扣款成功、寫冪等記錄前程序崩潰——**重試時會找不到記錄而再扣一次**；**所以兩者必須原子地一起完成**；**而如果扣款涉及外部的支付通道（無法納入本地交易），那就需要「先寫入處理中的記錄、呼叫外部、再更新結果」這個順序，並用一個對帳流程處理中間狀態卡住的記錄。**

**「客戶端也要正確地生成鍵」**：如果客戶端每次重試都生成新的鍵——**那冪等機制完全失效**；**所以鍵應該與「業務上的那一次付款意圖」綁定（例如在使用者按下付款按鈕時生成一次並在整個重試過程中沿用）**。**而在 API 文件中明確說明這一點，是這個機制能真正生效的前提**——**因為多數的重複扣款事故，根因是客戶端的鍵用錯了而非伺服器端的實作有問題。**

**「冪等不等於重試安全」**：一個冪等的 API 讓重試不會造成重複的效果——**但客戶端仍然需要正確的重試策略（指數退避、上限、以及對不同錯誤碼的區分）**（見 [[../backend-engineering/018-retry-and-backoff.md]]）；**而 4xx 的錯誤重試沒有意義（請求本身有問題），5xx 與網路逾時才該重試。**

## 面試回答方式

先給核心機制（**客戶端提供的冪等鍵**）與三種處理情況，再點出**併發重試**這個容易被忽略的細節與鍵的保留期限。加分點有四個：**記錄請求的指紋**——**否則同鍵不同金額會靜默回傳舊結果**；**冪等記錄與業務操作必須原子地一起完成**，**而涉及外部通道時要用「先寫處理中、呼叫、再更新」加對帳**；**客戶端也要正確生成鍵**——**多數重複扣款的根因在客戶端**；以及**冪等不等於重試安全**。

## 講稿

核心機制是客戶端提供的冪等鍵。客戶端為每一次邏輯上的付款生成一個唯一的鍵放在標頭裡，伺服器用它判斷這是新請求還是重試。

伺服器端有三種情況。鍵是新的就執行並把鍵、請求指紋、結果一起存起來。鍵已存在而且請求相同，直接回傳先前的結果。鍵已存在但請求內容不同，回傳錯誤。

記錄請求指紋這一點很關鍵。如果只用鍵判斷不比對內容，一個 bug 讓客戶端用同一個鍵送出不同金額，第二次會靜默回傳第一次的結果。使用者以為付了兩百其實只付了一百。

而最容易被忽略的細節是併發的重試。第一次還沒完成第二次就來了，這時應該回傳處理中而不是同時執行兩次。做法是先用鍵插入一筆處理中的記錄，靠唯一約束擋住。

還有一點，冪等記錄跟業務操作必須在同一個交易裡。如果先扣款成功、寫記錄前崩潰，重試時會找不到記錄而再扣一次。

## 常見追問

### 如果外部的支付通道無法納入本地交易呢？

**核心答案**：**用「先寫入意圖、再呼叫外部、最後更新結果」的三段式，並用對帳處理卡住的記錄**。第一段在本地交易中寫入一筆「處理中」的記錄——**第二段呼叫外部通道**；**第三段把結果寫回**。**而如果在第二段之後崩潰，那筆記錄會停在「處理中」，由一個定期的對帳任務去外部查詢真實的狀態並補上。**

**詳細解析**：這考察是否理解**「跨系統的原子性無法達成，只能達成最終一致」**（見 [[../backend-engineering/015-outbox-pattern.md]]）——**任何時刻都可能崩潰，所以必須設計成「崩潰後能查明真相並修復」而非「保證不會出錯」**；**而「先寫意圖」的價值就在於崩潰後你知道有一筆交易需要被確認**。**如果沒有那筆記錄，那個交易就完全消失在系統中而只能靠使用者投訴才發現**。**這也解釋了為什麼所有成熟的支付系統都有一個「查詢外部真實狀態」的介面與定期的對帳任務**——**它們不是可選的附加功能，而是這個架構成立的必要條件**；**能指出這一點，展示的是對支付系統本質的理解。**

**面試回答方式**：給三段式的流程與對帳任務的角色。核心加分點是說明**跨系統的原子性無法達成，只能設計成「崩潰後能查明真相」**，並指出**「先寫意圖」的價值是崩潰後你知道有交易需要確認**——**沒有那筆記錄它就完全消失只能靠投訴發現**。收在洞察：**對帳不是可選的附加功能而是這個架構成立的必要條件**。

### 冪等鍵應該由客戶端還是伺服器端生成？

**核心答案**：**必須由客戶端生成**。因為冪等的目的是讓「客戶端不確定結果時能安全重試」——**如果鍵由伺服器在第一次請求時生成，客戶端在沒收到回應時就不知道那個鍵是什麼**；**於是重試時無法引用它，機制就失效了。**

**詳細解析**：這考察**「理解機制的目的而非只記得做法」**——**很多人知道「要有冪等鍵」卻答不出為什麼一定要客戶端生成**；**而這個問題正好檢驗那個理解**。**而由客戶端生成帶來一個責任的移轉**：**客戶端必須確保鍵的唯一性（通常用 UUID）與正確的沿用時機**；**所以好的 API 設計會在文件中明確說明，並且在偵測到明顯的誤用（例如同一個鍵在很短時間內用於大量不同的請求）時發出警告**。**這個「把使用方的正確使用當成 API 設計的一部分」的思路，是設計公開 API 時很重要的意識**——**因為你的 API 的實際可靠性，等於「設計的可靠性」乘上「使用者正確使用的比例」。**

**面試回答方式**：給明確的答案（**必須由客戶端生成**）並用「沒收到回應時就不知道鍵是什麼」說明理由。核心加分點是指出這個問題**檢驗的是理解機制的目的而非記得做法**，並說明它帶來的責任移轉（客戶端要確保唯一性與正確沿用）。收在 API 設計意識：**把使用方的正確使用當成設計的一部分**——**實際的可靠性等於設計的可靠性乘上正確使用的比例**。

### 這個機制對讀取的 API 也需要嗎？

**核心答案**：**不需要，因為讀取本來就是冪等的**。GET 請求重複執行不會改變狀態——**所以重試是天然安全的**；**而冪等鍵只對「會改變狀態」的操作有意義（建立付款、退款、轉帳）**。**但要注意「看起來是讀取但實際有副作用」的介面**——**例如一個 GET 卻會消耗配額或觸發計費，那它就需要被當成寫入處理。**

**詳細解析**：這考察**「HTTP 方法的語意約定為什麼重要」**（見 [[../computer-network/011-get-vs-post.md]]）——**瀏覽器、代理、CDN 與各種中介都假設 GET 是安全且冪等的**；**於是它們可能自行重試、預先取得、或者快取結果**；**而一個有副作用的 GET 會在這些情況下造成非預期的行為**（歷史上有過爬蟲把所有「刪除」連結都點過一遍的案例）。**所以遵守方法的語意不只是風格問題而是正確性問題**。**而 PUT 與 DELETE 在定義上也是冪等的（重複執行結果相同），只有 POST 不是**——**這也是為什麼冪等鍵最常出現在 POST 的介面上**；**能說清楚這個對應關係，展示的是對 HTTP 語意的紮實理解。**

**面試回答方式**：給明確的答案（**不需要，讀取本來就冪等**）並提醒**「看起來是讀取但有副作用」的介面要當成寫入處理**。核心加分點是說明**HTTP 方法的語意約定是正確性問題而非風格問題**——**中介會自行重試、預取或快取，而歷史上有爬蟲把所有刪除連結點過一遍的案例**。收在對應關係：**PUT 與 DELETE 在定義上也是冪等的，只有 POST 不是**——**這正是冪等鍵最常出現在 POST 介面上的原因**。
