# 題目

這是騰訊（以及阿里、字節等同類型公司）在後端職位面試裡**相當常見**的一種情境題（根據公開面試經驗分享整理歸納而成，並非逐字官方紀錄）：**「有一張訂單表，資料量已經成長到千萬級，查詢速度越來越慢，你會怎麼一步一步優化？」**這類題目**不是**考單一個知識點，而是考你是否具備**依照問題規模循序漸進選擇對應手段**的完整優化思路。

## 核心答案

面對這類問題，**建議的思路**是依照**優化成本由低到高**的順序依序考慮——**(1) 先檢查、優化索引**：用 `EXPLAIN` 分析慢查詢（Slow Query），確認是否命中索引、是否存在可以額外建立的複合索引（見 [[../database/004-composite-index.md]])，來避免全表掃描；**(2) 檢查 SQL 語句本身是否寫得不夠理想**：例如是否有不必要的 `SELECT *`、是否可以改寫成能命中覆蓋索引（Covering Index）（見 [[../database/014-index-covering-and-sorting.md]]）的寫法；**(3) 引入快取層**：把**高頻查詢、但資料相對不常變動**的內容快取到 Redis，減少直接打資料庫的次數；**(4) 讀寫分離（Read-Write Splitting）**：如果讀取的流量遠高於寫入，把讀取分散到多個唯讀從節點；**(5) 到最後才考慮分庫分表**：因為分庫分表（見 [[../database/017-sharding.md]]）會帶來顯著的架構複雜度（跨庫查詢、分散式交易等問題），只有在前面幾個較輕量的手段都已經用盡、資料量依然持續成長時，才值得付出這個較高的架構成本。

## 詳細解析

**為什麼這題要依照順序回答——面試官想看你的優化思路有沒有章法**：這類題目**最忌諱**的回答方式，是**跳過前面較輕量的手段，直接說『分庫分表』**——這某種程度上會讓面試官判斷你**只是記得一個聽起來厲害的名詞**，卻**沒有真正具備依照實際成本效益循序判斷該用哪個手段**的工程思維。騰訊這類**服務規模極為龐大**的公司特別重視**「先用最低成本的手段解決問題；只有真的必要時，才動用更昂貴、更複雜的架構調整」**這種**務實的工程判斷力**，因為在真實的生產環境裡，**每一次架構調整都伴隨著實際的開發成本、上線風險、甚至可能引入新的 bug**，一個**濫用昂貴手段**的工程師即使技術能力再強，也可能讓團隊付出**不必要的額外成本**。

**索引優化的細節追問——面試官很可能會拿著一個具體的 EXPLAIN 結果問你**：面試官很常會**直接秀出一段具體的 `EXPLAIN` 執行計畫結果**要求你判讀——例如如果 `type` 欄位顯示 `ALL`（全表掃描）、或者 `key` 欄位顯示 `NULL`（沒有命中任何索引），你需要能**立即判斷出問題**。這某種程度上回到前面（見 [[../database/001-btree-index.md]]、[[../database/005-index-invalidation.md]]）已經深入討論過的**索引失效常見情境**（例如對索引欄位做了函式運算、使用了不符合最左前綴（Leftmost Prefix）原則的複合索引查詢條件）——建議把那幾題索引失效的具體情境逐一複習，並練習實際地用 `EXPLAIN` 指令去驗證這些情境，因為這正是中國大廠面試現場**最常被拿出來實際操作測試**的環節。

**分庫分表是最後手段——一定要主動提到它帶來的新問題**：如果回答到**「最終需要分庫分表」**這一步，一個能展現更深度思考的加分做法，是**主動提到**分庫分表之後**會引入哪些新的複雜度**——例如**「原本單一資料庫就能搞定的 join 查詢，分表之後可能需要改成在應用層做資料整合」**、**「原本單一資料庫天然保證的交易一致性，跨多個分片之後需要額外引入分散式交易（見 [[../backend-engineering/013-distributed-transaction-solutions.md]]）機制來處理」**。這種**「知道一個方案不只是解決原本的問題，還會帶來哪些新問題」**的完整視野，正是讓面試官判斷你**是否真正在生產環境操作過大規模系統**的關鍵依據。

## 面試回答方式

先給出循序漸進的優化思路架構——「會依照優化成本由低到高的順序，先用EXPLAIN分析確認索引是否命中、有沒有可以額外建立的複合索引;再檢查SQL語句本身是否可以優化，例如避免不必要的SELECT *、改寫成能命中覆蓋索引的寫法;接著引入快取層減少高頻查詢直接打資料庫的次數;再來考慮讀寫分離;最後才考慮分庫分表」。強調為什麼要依照這個順序——「因為每一種手段的架構複雜度和成本不同，應該先用低成本手段解決問題，只有資料量真的持續成長到前面手段都用盡時，才值得付出分庫分表這種較高的架構成本」。如果被問到分庫分表細節，主動補充它帶來的新問題——「分庫分表之後，原本單一資料庫就能處理的join查詢可能需要改到應用層處理，原本天然的交易一致性，跨分片後也需要額外引入分散式交易機制」，展現完整的架構視野而非只丟出一個名詞。

## 常見追問

### 如果你看到一個慢查詢的 EXPLAIN 結果，`type` 是 `ALL`，你會怎麼判斷並優化？

**核心答案**：`type` 顯示 `ALL` 代表這個查詢**進行了全表掃描，完全沒有命中任何索引**，需要先去**檢查這個查詢的 WHERE 條件所使用的欄位是否存在對應的索引**——如果**完全沒有索引**，需要依照這個查詢的實際篩選條件去**建立恰當的索引**（如果查詢涉及多個欄位一起篩選，考慮建立複合索引，並注意最左前綴原則）；如果**已經存在索引、卻依然顯示 `ALL`**，則需要進一步檢查是否**查詢語句本身的寫法**導致了**索引失效**（例如對索引欄位做了函式運算或隱式型別轉換）。

**詳細解析**：這題是前面已經提到的索引失效情境的具體實作演練——考察是否能**實際地動手操作**，而不是只停留在理論知識。回答時可以具體地舉出幾個**常見導致索引失效的具體寫法**（見 [[../database/005-index-invalidation.md]]）——例如 `WHERE YEAR(create_time) = 2024` 這種對索引欄位做函式運算的寫法，即使 `create_time` 本身有索引，也會導致索引失效（因為資料庫無法直接利用索引去比對函式運算後的結果），正確的寫法應該改成 **`WHERE create_time >= '2024-01-01' AND create_time < '2025-01-01'`** 這種**保持索引欄位本身不被額外運算**的寫法。

**面試回答方式**：先給出判讀方式——「type顯示ALL代表全表掃描，需要先檢查WHERE條件使用的欄位是否有對應索引，沒有的話依照實際篩選條件建立恰當索引;如果已經有索引卻依然ALL，就要檢查查詢寫法本身是否導致索引失效」。舉出具體例子——「例如對索引欄位做函式運算，像WHERE YEAR(create_time)=2024這種寫法，即使create_time有索引也會失效，正確做法應該改成用範圍查詢WHERE create_time >= '2024-01-01' AND create_time < '2025-01-01',讓索引欄位本身保持不被額外運算」。

### 如果決定要做讀寫分離，你會怎麼處理「寫入主庫之後立刻去讀取，卻讀不到剛寫入的資料」這種主從延遲問題？

**核心答案**：這是讀寫分離架構裡**幾乎必然會遇到**的**主從延遲（Replication Lag）**問題，常見的緩解做法包括——**(1) 強制讀主庫**：針對**寫入之後需要立即讀取到最新結果**的關鍵場景（例如使用者剛下單完成，立刻要看到這筆訂單），**明確地指定這個讀取請求繞過從庫，直接去讀主庫**；**(2) 判斷主從延遲時間動態決定**：如果系統能即時監控到主從之間的延遲時間，可以在**延遲超過某個門檻**時暫時把讀取流量也導回主庫；**(3) 業務層面做適度的容忍**：對於**不需要絕對即時性**的場景（例如瀏覽其他人的訂單紀錄），可以接受讀到略有延遲的資料，不需要額外的特殊處理。

**詳細解析**：這題考察是否理解讀寫分離這種架構選擇**並非沒有代價**——它用**犧牲一定程度的即時一致性**去換取**讀取效能的水平擴展（Horizontal Scaling）能力**，這某種程度上是一種**經典的 CAP 權衡取捨**（見 [[../backend-engineering/016-cap-theorem.md]]）——選擇了**更高的可用性和效能**，某種程度上就需要接受**較低的即時一致性保證**。正確地識別出**「這個具體業務場景是否真的需要絕對的即時一致性」**，並依照這個判斷去決定**應該對哪些特定的查詢**做**強制讀主庫**這種**針對性的例外處理**（而不是一律強制讀主庫，那會讓讀寫分離原本的效能優化效果大打折扣），正是這題真正想考驗的架構判斷力。

**面試回答方式**：先給出核心概念和三種因應做法——「這是讀寫分離架構幾乎必然會遇到的主從延遲問題，常見做法包括對需要立即讀到最新結果的關鍵場景強制讀主庫、動態監控主從延遲超過門檻時暫時導回主庫、以及對不需要絕對即時性的場景業務層面容忍一定延遲」。可以連結到更根本的權衡認知——「這其實是讀寫分離這種架構選擇的CAP權衡取捨，用犧牲一定即時一致性換取讀取效能的水平擴展能力，關鍵是判斷具體業務場景是否真的需要絕對即時一致性，只針對真正需要的場景做強制讀主庫的例外處理，而不是一律強制讀主庫讓讀寫分離的效能優化效果大打折扣」。

### 如果這張訂單表最終真的需要分庫分表，你會怎麼選擇分片鍵（Sharding Key）？

**核心答案**：選擇分片鍵核心的考量原則是——**「大多數的查詢請求是否都帶有這個欄位作為篩選條件」**——如果**絕大多數查詢**都是**依照使用者 ID 去查詢這位使用者的訂單**，那**用使用者 ID 作為分片鍵**通常是恰當的選擇（這樣大多數查詢都能被正確地導向唯一一個對應的分片，而不需要同時查詢所有分片再彙整結果）；但如果同時也存在**大量依照訂單建立時間去查詢**的需求（例如後台報表常常依照日期區間查詢），用**使用者 ID 作為分片鍵**就會導致**這類依照時間查詢的請求必須同時掃描所有分片**。這種情況下需要額外考量是否需要**額外建立一份依照時間維度的索引或彙整資料**，來補足這個缺口。

**詳細解析**：這題考察是否理解**分片鍵的選擇本質上是一種需要權衡不同查詢模式**的架構決策——延續前面（見 [[../backend-engineering/017-consistent-hashing.md]]）已經深入討論過的一致性雜湊（Consistent Hashing）相關概念，選擇分片鍵這件事**沒有一個放諸四海皆準的標準答案**，而是需要回到**「這個系統實際上最常見的查詢模式是什麼」**這個根本問題——一個**設計得恰當**的分片鍵，應該讓**絕大多數實際發生的查詢**都能被**準確地導向單一個分片**，而**不需要**退化成**「同時查詢所有分片，再彙整結果」**這種**幾乎喪失分片原本效益**的低效模式。因此回答這題的關鍵不是直接丟出「用使用者 ID」這個答案，而是**先反問（或者主動說明）這個系統實際上的查詢模式分佈是什麼**，再依照這個分佈去推導出恰當的分片鍵選擇。

**面試回答方式**：先給出選擇分片鍵的核心原則——「核心考量是大多數查詢請求是否都帶有這個欄位作為篩選條件，如果絕大多數查詢都是依照使用者ID查詢訂單，用使用者ID作為分片鍵通常是恰當選擇，這樣大多數查詢能被正確導向唯一分片而不需要同時查詢所有分片再彙整」。主動點出可能的例外情況——「但如果同時也有大量依照時間區間查詢的報表需求，用使用者ID當分片鍵會導致這類查詢必須掃描所有分片，這種情況需要額外考慮是否要建立一份依時間維度的額外索引或彙整資料來補足」。可以總結——「分片鍵的選擇本質上是依照這個系統實際查詢模式分佈去做的架構權衡，沒有放諸四海皆準的標準答案」。
