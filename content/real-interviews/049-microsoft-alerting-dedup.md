# 題目

「告警系統的設計」是 Microsoft 這類**經營大型雲端服務的公司**常被回報的題目（根據公開的面試經驗分享整理歸納而成，並非逐字官方紀錄）：**「一個資料庫掛掉會讓五十個服務同時報錯，值班的人收到上百則通知。你會怎麼設計這個告警系統？」**這題的核心不是「怎麼發通知」而是**「怎麼讓收到通知的人真的能行動」**。

## 核心答案

**核心的問題是「告警疲勞」**——**當通知太多時，人會開始忽略它們，於是真正重要的告警也被錯過**；**所以設計的目標不是「不漏掉任何異常」而是「每一則送出的通知都值得被看」。**

**四個關鍵機制**：**去重**（同一個問題在一段時間內只通知一次，用一個指紋鍵識別「同一個問題」）；**聚合**（把相關的告警合併成一則，例如「五十個服務都在報同一個資料庫的連線錯誤」應該是一則而非五十則）；**抑制**（有明確因果關係時，只通知根因——資料庫掛了就不必再報下游的逾時）；**以及分級與路由**（不同嚴重程度走不同的通道，P1 打電話而 P3 只進看板）。

**而最重要的設計是「告警要對應到行動」**——**如果收到一則通知而不知道該做什麼，那則通知就不該存在**；**所以每個告警規則都應該附上「這代表什麼、影響是什麼、第一步該做什麼」。**

## 詳細解析

**「去重的鍵設計決定了效果」**：如果指紋包含了時間戳或者請求 ID——**每一次都是新的告警而去重完全失效**；**正確的指紋應該由「告警規則 + 受影響的實體」組成**（例如「資料庫連線失敗 + db-prod-01」）；**而選對這個粒度需要理解「什麼算是同一個問題」。**

**「抑制需要一份依賴關係」**：要知道「資料庫掛了會導致哪些服務報錯」——**系統需要一份服務的依賴圖**；**而這份圖可以從服務註冊、分散式追蹤（見 [[../backend-engineering/020-distributed-tracing.md]]）或者人工維護取得**。**自動從追蹤資料推導依賴，比人工維護的準確且不會過時**——**這是可觀測性投資的一個常被忽略的回報。**

**「告警的品質應該被量化」**：可以追蹤的指標包括**「被確認為誤報的比例」**、**「收到後多久被處理」**、**以及「有多少告警從未被任何人點開」**；**而最後一項特別有價值——長期沒人看的告警規則應該被刪除或降級**。**沒有這個回饋循環的告警系統，規則只會越加越多而品質越來越差。**

**「送達的可靠性本身要被保證」**：如果告警系統與被監控的系統共用基礎設施——**那機房掛掉時告警也發不出來**；**所以告警的通道應該獨立（不同的雲端區域、不同的通知供應商）**，**而且要有一個「心跳」機制：如果監控系統本身停止回報，那本身就是一個最高級的告警**（dead man's switch）。

## 面試回答方式

先點出核心問題（**告警疲勞**）並給出設計的目標，再列出四個機制。加分點有四個：**去重的鍵設計**——**指紋包含時間戳或請求 ID 會讓去重完全失效**；**抑制需要一份依賴圖**，**而從追蹤資料自動推導比人工維護準確且不會過時**；**告警的品質應該被量化**，**尤其是「從未被點開的比例」**；以及**送達的可靠性**與 dead man's switch 這個機制。

## 講稿

核心的問題是告警疲勞。當通知太多，人會開始忽略，於是真正重要的也被錯過。所以我的設計目標不是不漏掉任何異常，而是每一則送出的通知都值得被看。

四個關鍵機制。去重、聚合、抑制、還有分級路由。

去重是同一個問題在一段時間內只通知一次。而這裡的關鍵是指紋鍵的設計。如果指紋包含時間戳或請求 ID，每一次都是新告警，去重就完全失效了。正確的指紋應該是告警規則加上受影響的實體。

聚合是把相關的合併成一則。五十個服務都在報同一個資料庫的連線錯誤，那應該是一則。

抑制是有明確因果關係時只通知根因。而這需要一份服務的依賴圖，我會從分散式追蹤的資料自動推導，比人工維護準確而且不會過時。

另外我會量化告警的品質。追蹤誤報比例、處理時間、還有從未被任何人點開的比例。最後這一項特別有價值，長期沒人看的規則應該被刪掉或降級。

## 常見追問

### 怎麼決定一個告警該是 P1 還是 P3？

**核心答案**：**用「使用者是否受影響」與「是否需要立刻行動」這兩個維度**。**使用者已經受影響且需要立刻處理**是 P1（打電話叫醒人）；**使用者尚未受影響但趨勢在惡化**是 P2（工作時間內處理）；**只是需要被知道的資訊**是 P3（進看板不通知）。**而不該用「技術上有多嚴重」來分級——一台機器掛了但有備援，那對使用者沒有影響。**

**詳細解析**：這考察**「告警應該基於症狀而非原因」**這個 SRE 的核心原則（見 [[../backend-engineering/034-slo-and-error-budget.md]]）——**「CPU 使用率超過 90%」是一個原因，而它可能完全沒有影響**；**「錯誤率超過 1% 且持續五分鐘」是一個症狀，它直接對應到使用者的體驗**。**基於症狀的告警數量少得多、誤報率低得多、而且不會因為架構的改變而失效**；**而基於原因的告警會隨著系統的複雜度線性增長**。**一個實用的檢驗是「如果這個告警觸發了但沒有人做任何事，會發生什麼」**——**如果答案是「沒事」，那它就不該是一個會叫醒人的告警**。

**面試回答方式**：給兩個維度（**使用者是否受影響、是否需要立刻行動**）與三級的對應，並指出**不該用技術上的嚴重程度分級**。核心加分點是說明**告警應該基於症狀而非原因**並對比兩個例子，指出基於症狀的告警數量少、誤報低、且不隨架構改變而失效。收在檢驗方法：**如果這個告警觸發但沒有人做任何事會發生什麼**——**答案是「沒事」就不該叫醒人**。

### 值班的人收到告警之後呢？

**核心答案**：**系統要支援完整的事件生命週期**：**確認（有人開始處理了，避免多人重複投入）**、**升級（一段時間沒有人確認就通知下一級）**、**協作（相關的人能看到同一份上下文）**、**以及關閉與復盤**。**而最有價值的是「告警要附上執行手冊的連結」**——**讓被叫醒的人不需要從頭思考。**

**詳細解析**：這考察**「告警只是事故處理的入口而非全部」**（見 [[../backend-engineering/048-incident-response.md]]）——**一個好的告警系統應該把人從「收到通知」帶到「開始正確的處理」**；**而執行手冊（runbook）正是那座橋**。**而手冊的品質決定了它有沒有用**：**「檢查服務狀態」是無用的，而「執行這個指令看輸出、如果 X 就做 A、如果 Y 就聯絡某某團隊」才是可執行的**。**一個實務的判準是「一個沒有這個系統背景知識的人，能不能照著做」**——**因為凌晨三點被叫醒的人，認知能力本來就打折**。**而每次事故之後更新手冊，是把個人經驗轉成團隊能力的最直接方式。**

**面試回答方式**：列出事件生命週期的四個階段並指出**最有價值的是附上執行手冊的連結**。核心加分點是說明**告警只是事故處理的入口**與手冊是那座橋，並給出手冊品質的判準（**一個沒有背景知識的人能不能照著做**）與理由（**凌晨三點被叫醒的人認知能力本來就打折**）。收在實務：**每次事故之後更新手冊，是把個人經驗轉成團隊能力的最直接方式**。

### 如何避免告警規則越加越多？

**核心答案**：**建立「新增規則要有負責人與複審週期」的流程，並定期清理**。每個規則登記時記錄「誰負責、觸發時該做什麼、以及什麼條件下應該被移除」——**而定期（例如每季）檢視「過去三個月觸發過幾次、有幾次是真的問題」**；**沒有觸發過或者全是誤報的規則應該被刪除。**

**詳細解析**：這考察**「規則庫和程式碼一樣需要維護」**——**但它常常沒有主人，於是只會累積**；**因為新增一個規則很容易（出過一次事就加一條）而刪除需要有人承擔「萬一以後出事」的責任**。**打破這個不對稱的方法是「把清理變成常規流程而非個人決定」**：**在季度檢視中，沒有人主動說要保留的規則就自動降級或刪除**；**於是「不作為」的預設從保留變成移除**。**這個「改變預設值來對抗累積」的手法，在很多治理問題上都適用**——**權限、功能開關、以及設定項目都有同樣的累積傾向**；**而它的關鍵不在於規則本身而在於誰要承擔決定的責任。**

**面試回答方式**：給流程（**新增要有負責人與移除條件、定期檢視觸發次數與誤報率**）。核心加分點是分析**為什麼規則只會累積**——**新增容易而刪除需要承擔「萬一以後出事」的責任**，並給出打破的方法：**把清理變成常規流程，讓「不作為」的預設從保留變成移除**。收在通用性：**這個手法在權限、功能開關與設定項目上同樣適用**。
