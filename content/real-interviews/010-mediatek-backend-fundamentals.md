# 題目

這是聯發科（以及同類型擁有**內部管理系統、韌體／軟體整合平台**的台灣硬體科技公司，在其後端／軟體職位面試裡）**相當基礎、但幾乎必問**的一題（根據公開面試經驗分享整理歸納而成，並非逐字官方紀錄）：**「請說明 HashMap 的底層資料結構和原理，並比較它和 Hashtable 的差異」**這類基礎 Java 題是台灣科技業面試裡**相當常見的『暖身題』**——通常出現在面試的**前半段**，用來快速確認候選人是否具備**紮實的 Java 基礎**，才會繼續進入更深入的追問。

## 核心答案

`HashMap`,的底層,是，**「陣列,加,鏈結串列(或紅黑樹)」**的資料結構——當，一個,key-value,配對，被，加入,`HashMap`,時，會，先，計算，這個,key,的`hashCode()`，經過，一定的運算，決定，它，應該，被，放到，**陣列裡的哪一個索引位置(桶,Bucket)**；如果，**多個,不同的key**，剛好，被，計算,到，**同一個桶**(雜湊碰撞)，這些,元素，就，會，用，**鏈結串列**的方式，串接,在，同一個桶裡(在,JDK8之後，如果，**同一個桶裡的鏈結串列,長度**，超過,某個門檻(預設,8)，會，**自動轉換,成,紅黑樹**，來，改善，查詢效率，見 [[../java/005-hashmap-internals.md]])。`HashMap`,和`Hashtable`,最核心的差異，在於——**(1) 執行緒安全性**：`Hashtable`,的每一個方法，都，加上了，`synchronized`,關鍵字，本身，是,執行緒安全的；而，`HashMap`,則，**完全,沒有,任何,同步機制**，在，多執行緒環境下，**並不安全**；**(2) 是否,允許null**：`HashMap`,允許，**key和value,都可以是null**；`Hashtable`,則，**完全,不允許**，任何,null的key或value(如果，嘗試,放入null，會，直接,拋出例外)。

## 詳細解析

**為什麼,現在,幾乎,不再使用Hashtable——`ConcurrentHashMap`,才是,更好的選擇**：這題，經常，會，被，追問——**「既然,Hashtable,是,執行緒安全的，為什麼,實務上,大家,還是,更常用HashMap,搭配,額外的同步機制？」**——答案，是，`Hashtable`,那種，**把,每一個方法,都,直接,加上,synchronized**的做法，是，一種，**過於,粗暴、效能低落**的同步方式(這，某種程度上，等同於，**整個,Hashtable,同一時間，只能，被,一個執行緒,存取**，即使，這，两個,執行緒，實際上，是，要，存取，**完全不同的key**，也，會，被，**強制,互相,排隊等待**)，如果，真的，需要，一個,執行緒安全的Map，實務上，更好的選擇，是，前面(見 [[../java-concurrency/014-concurrenthashmap-internals.md]])已經,深入討論過的**`ConcurrentHashMap`**——它，透過，**更加,細緻的鎖粒度(分段鎖或CAS機制)**，在，保證,執行緒安全的同時，能，提供，**遠比,Hashtable,更好**的並行效能。

**HashMap,的雜湊碰撞,和,擴容機制——這是,經常,被,深入追問的細節**：如果，這題，開頭，回答得,順利，面試官，很常，會，繼續，追問，**「當,HashMap,裡的元素數量，越來越多，它，是,怎麼,擴容的？」**——`HashMap`,內部，有，一個，**負載因子(Load Factor)**的概念(預設,0.75)，當，**已經,存放的元素數量,除以,陣列容量**，超過，這個,負載因子門檻，`HashMap`,就，會，**自動地，把,內部的陣列容量,擴大成,原本的兩倍**，並，把，**所有,原本已經存在的元素**，**重新,計算,雜湊值、重新,分配**,到，這個,新的、更大的陣列裡(這個,過程，稱為，**Resize**)，這個,重新分配的過程，本身，**是,相對,昂貴**的操作(需要，重新,走訪，所有的既有元素)，如果，**事先,就,知道**，這個,`HashMap`,大概,會,存放,多少筆資料，**在,建立時，就,直接,給定,一個,足夠大的初始容量**，能，**避免**，之後，**因為,反覆,擴容**，而，造成的額外效能開銷。

**這題,在,台灣科技業面試,的角色——通常,是,用來,快速篩選,而,非,深度考察**：這类，**基礎Java知識題**，在，台灣本地科技業(尤其是，**硬體/系統整合公司**，他們，可能，不像，中國互聯網大廠,那樣,對,後端技術,鑽研,到,極致細節)的面試裡，扮演的角色，通常，是，**「快速確認,候選人,是否,具備,基本的Java素養」**，而，**不會**，像，前面(見 [[003-bytedance-lru-cache-handwritten.md]])討論過的字節跳動,那種,現場手寫程式碼題,那樣，要求，你，**現場,實作**，只，需要，能，**清楚、有條理,地，口頭,講解**，這些,核心原理，通常，就，已經，足夠，通過，這一個環節，建議，把，準備的重心，放在，**「能不能,用,簡潔、有邏輯的方式，把,原理,講清楚」**，而，不需要，過度,擔心，會，被，要求，**當場,把,HashMap,的底層邏輯，完整地,手寫,出來**。

## 面試回答方式

先給出底層資料結構——「HashMap底層是陣列加鏈結串列(或紅黑樹)的結構,加入key-value時先計算key的hashCode決定放到陣列哪個索引(桶),多個不同key碰撞到同一個桶就用鏈結串列串接,JDK8之後如果同一桶的鏈結串列長度超過門檻(預設8)會自動轉換成紅黑樹改善查詢效率」。給出和Hashtable的兩個核心差異——「執行緒安全性方面,Hashtable每個方法都加了synchronized本身是執行緒安全的,HashMap完全沒有同步機制在多執行緒下不安全;是否允許null方面,HashMap允許key和value都可以是null,Hashtable完全不允許」。可以主動補充實務建議——「實務上如果需要執行緒安全的Map,更好的選擇是ConcurrentHashMap,因為它透過更細緻的鎖粒度,能在保證執行緒安全的同時提供遠比Hashtable更好的並行效能,而不是回頭用Hashtable這種把每個方法都直接加synchronized的粗暴同步方式」，展現你對這題基礎知識有紮實且具備延伸視野的理解。

## 常見追問

### 為什麼,HashMap,的初始容量，一定,要是,2的次方(如16、32、64)？

**核心答案**：這，是，為了，讓，**「計算,一個key,應該,被放到,哪一個桶」**這個,運算，能，用，**效率,更高的位元運算(AND)**，去，取代，**效率,較低的取餘數運算(%)**——當，陣列容量,是,**2的次方**時，`(容量-1)`,這個数值,的二進位表示，會，是，**一連串連續的1**(例如，容量是16，`16-1=15`,的二進位,是,`1111`)，這時候，**「雜湊值,和(容量-1),做AND位元運算」**，得到的結果，會，**完全,等同於**，「雜湊值,對,容量,做取餘數運算」的結果，但，**位元運算(AND)，在,底層硬體層次，執行的速度，遠比，取餘數運算(%)，來得快**，這，正是，`HashMap`,要求，容量,必須,是,2的次方,的核心原因。

**詳細解析**：這題，考察，是否，理解，`HashMap`,這種，**看似,只是,一個,武斷的實作限制**，背後，其實，蘊含著，**具體的效能考量**——這，某種程度上，展現了，Java標準函式庫,的設計者，**在，追求,極致效能**時，會，**深入到,底層硬體運算層次**，去，思考，**如何，用，更有效率的運算方式**，去，達成，**在,數學上,完全,等价**的結果——理解，這種，「表面上,看起來,只是,一個,武斷的限制條件，其實，背後,蘊含著,具體的效能考量」的思維方式，能，幫助，你，在，面對，其他类似，**「為什麼,某個,函式庫,要,這樣設計」**這类,問題時，**具備，更深入,挖掘,背後原因**的思考習慣，而，不是，只，把，這些,設計,當成，**理所當然、不需要,追問**的既定事實。

**面試回答方式**：先給出核心答案——「這是為了讓計算一個key應該被放到哪個桶這個運算,能用效率更高的位元運算AND去取代效率較低的取餘數運算%,當陣列容量是2的次方時,容量減1這個數值的二進位表示會是一連串連續的1,這時候雜湊值和容量減1做AND運算,得到的結果會完全等同於雜湊值對容量取餘數的結果,但位元運算在底層硬體層次執行速度遠比取餘數運算來得快」。可以補充展現思考習慣——「這種看似武斷的實作限制,背後其實蘊含著具體效能考量,展現了Java標準函式庫設計者在追求極致效能時,會深入到底層硬體運算層次去思考如何用更有效率的方式達成數學上等價的結果」。

### 如果，你，用,一個,自訂的類別(Custom Class),作為,HashMap,的key，你，需要，額外,注意,什麼？

**核心答案**：需要，**同時,正確地,覆寫(Override),這個,類別的`equals()`方法,和`hashCode()`方法**——而且，這，两個方法，需要，**保持,一致**——這，正是，前面(見 [[../java/001-equals-hashcode-contract.md]])已經,深入討論過的**equals,和,hashCode,契約**——如果，**只，覆寫,了,equals()，卻，沒有，同步,覆寫,hashCode()**，會，導致，**兩個,依照,equals(),判斷,邏輯上,應該相等的物件**，卻，可能，**擁有,不同的hashCode()**，這，會，讓，`HashMap`,在，**內部,判斷,雜湊碰撞**時，出錯，導致，你，**明明,已經,用,一個,邏輯上,相等的key,放入過資料**，之後，卻，**查詢不到**這筆,已經存在的資料。

**詳細解析**：這題，直接，考察，是否，理解，前面已經深入討論過的**equals,和,hashCode,契約**，這個核心原理，在，`HashMap`,這個,具體資料結構,裡,的實际運作意義——`HashMap`,在，**判斷,兩個key,是否,相同**時，並，**不是**，只，依靠,單一個方法，而是，**先，用,hashCode(),快速地，判斷，這兩個,物件，是否，可能,落在,同一個桶裡**(如果，hashCode(),不同，就，**直接,確定**，這,兩個,物件，一定,不是,同一個key，**根本,不需要**，再，去，呼叫,較,昂貴的equals()方法)；**只有，當,hashCode(),相同**時，才，會，**進一步,呼叫equals()**，去，做，**更精確的比對**，確認，這，兩個,物件，是否，真的，是，**邏輯上,相等**的key，這種，「先,用,較,快速,但,較,粗略的雜湊值,做,初步篩選，再，用,較,精確,但,較,昂貴的equals(),做,最終確認」的**兩階段判斷機制**，正是，`HashMap`,之所以，**要求,equals(),和,hashCode(),必須,保持一致**的根本原因——如果，這，两者，**不一致**，這種，**兩階段判斷**，就，會，**在，第一階段(用hashCode,做初步篩選)**，就，出錯。

**面試回答方式**：先給出核心答案——「需要同時正確覆寫這個類別的equals方法和hashCode方法,而且這兩個方法需要保持一致,這是equals和hashCode契約的具體展現,如果只覆寫equals卻沒同步覆寫hashCode,會導致兩個邏輯上應該相等的物件卻擁有不同hashCode,讓HashMap判斷雜湊碰撞時出錯,導致明明已經用一個邏輯相等的key放入過資料,之後卻查詢不到」。可以補充HashMap的兩階段判斷機制加深理解——「HashMap判斷兩個key是否相同時,先用hashCode快速判斷是否可能落在同一個桶裡,如果hashCode不同就直接確定不是同一個key不需要再呼叫較昂貴的equals;只有hashCode相同時才進一步呼叫equals做更精確比對,這種先快速篩選再精確確認的兩階段機制,正是為什麼equals和hashCode必須保持一致的根本原因」。

### 如果,要求,你,在,一個,多執行緒的環境下,使用HashMap,但,又,不想,像Hashtable那樣,粗暴地,對每個方法都加鎖,你,有,什麼,建議?

**核心答案**：**最,直接的建議，是，改用,`ConcurrentHashMap`，而，不是，設法,讓,`HashMap`,自己,變得,執行緒安全**——`ConcurrentHashMap`,是，Java標準函式庫,專門，為了，**「在,多執行緒環境下，安全,且,高效地,使用Map」**這個,需求，所，設計的資料結構，它，透過，前面(見 [[../java-concurrency/014-concurrenthashmap-internals.md]])已經,深入討論過的**更細緻的鎖粒度機制**，能，在，保證,執行緒安全的同時，維持,遠比,Hashtable,更好的並行效能，除非，有，非常,特殊的理由(例如，需要，維持,和,舊系統的相容性)，**實務上，幾乎,不會，有，任何,情境**，需要，你，自己,手動,去，設計,一套,額外的同步機制，包在,原本的HashMap外面。

**詳細解析**：這題，考察，是否，具備，**「優先,運用,語言標準函式庫,已經,提供好的成熟解決方案，而，不是，自己,重新造輪子」**這個,核心工程原則——面試官，如果，聽到，你，回答，**「我，會，自己，在，HashMap,外面，包一層,同步機制(如,用synchronized包住每一次的存取)」**，可能，會，追問，**「那，這，和，直接,使用,Hashtable，有,什麼,本質上的差異？」**，藉此，引導,你，發現，**這種,做法，本質上，就是，重新,發明,了,一次,Hashtable,那種,粗暴的全域鎖定方式**，並，沒有，帶來，任何,額外的好處，正確的回答方向，應該，是，**直接,指向,`ConcurrentHashMap`,這個,已經,被，設計得，更加,精細、且，經過,充分驗證**的現成解決方案，而，不是，自己，**重新,發明一套,效果,更差**的替代方案。

**面試回答方式**：先給出核心建議——「最直接的建議是改用ConcurrentHashMap,而不是設法讓HashMap自己變得執行緒安全,ConcurrentHashMap透過更細緻的鎖粒度機制,能在保證執行緒安全同時維持遠比Hashtable更好的並行效能」。可以補充為什麼不該自己包一層同步機制——「如果自己在HashMap外面包一層同步機制,本質上就是重新發明了一次Hashtable那種粗暴的全域鎖定方式,並沒有帶來任何額外好處,除非有非常特殊的理由,實務上幾乎不會有任何情境需要自己手動設計額外同步機制,直接使用ConcurrentHashMap這個已經被設計得更精細且經過充分驗證的現成方案才是正確做法」。
