# 題目

「單機的連線數上限」是華為這類**重視底層與網路的公司**常被回報的深度題（根據公開的面試經驗分享整理歸納而成，並非逐字官方紀錄）：「一台伺服器理論上最多能維持多少 TCP 連線？實際上會先卡在哪裡？如果要支撐一百萬個長連線，你會怎麼做？」這題會一路追問到作業系統的層次，而它能有效地區分「用過框架」與「理解底層」。

## 核心答案

**先破除一個常見的誤解**：「端口號只有 65535，所以最多六萬多個連線」是錯的——那個限制是針對「主動發起連線的一方」；而伺服器端的一個監聽端口可以接受無數連線，因為連線是由「來源 IP、來源端口、目的 IP、目的端口」這個四元組區分的（見 [[../computer-network/017-socket-and-port-exhaustion.md]]）。

**實際會先撞到的限制有四個**：**檔案描述符的上限**（每個連線是一個 fd，預設通常只有 1024，要調 `ulimit` 與系統層級的 `fs.file-max`）；**記憶體**（每個連線的收發緩衝區加上應用層的物件，是百萬連線最主要的成本）；**核心的連線追蹤表**（如果經過有狀態的防火牆或 NAT）；**以及應用層的模型**（一個連線一個執行緒的模型在幾千連線就會崩潰）。

支撐百萬連線的關鍵是三件事：**用 I/O 多工的事件驅動模型**（epoll，見 [[../redis/004-io-multiplexing.md]]）；**調小每個連線的緩衝區**（預設值乘上一百萬會遠超記憶體）；以及把連線層做薄，讓每個連線的應用層狀態盡可能小。

## 詳細解析

「記憶體是真正的瓶頸」值得算一次：Linux 的 TCP 讀寫緩衝區預設可能各是幾十 KB——一百萬個連線光緩衝區就是幾十 GB；所以必須把 `net.ipv4.tcp_rmem` 與 `tcp_wmem` 的最小值與預設值調小（例如 4KB），讓核心按實際需要動態增長而非一開始就配置大塊。加上應用層每個連線的物件（若是 1KB 則是 1GB），一台記憶體足夠的機器確實能撐到百萬級——這也是為什麼「單機百萬連線」是一個可達成但需要仔細調校的目標。

「執行緒模型決定了上限的數量級」：一個連線一個執行緒——每個執行緒的堆疊預設 1MB，一萬個執行緒就是 10GB 且上下文切換的成本壓垮 CPU；而事件驅動的模型用少數幾個執行緒輪詢大量的 fd，於是連線數與執行緒數解耦。這正是 Nginx、Redis 與各種現代網路框架的共同選擇；而理解「為什麼不能一個連線一個執行緒」，比記住 epoll 的 API 更重要。

**「TIME_WAIT 是主動關閉方的問題」**（見 [[../computer-network/003-tcp-four-way-wave-time-wait.md]]）：伺服器如果主動關閉大量短連線，會累積大量的 TIME_WAIT 佔用資源——而在長連線的場景中這個問題較小；這也是「能用長連線就不要用短連線」的一個實際理由。

「連線的維護成本不只在建立時」：心跳的頻率直接影響 CPU 與網路——一百萬個連線每三十秒一次心跳，是每秒三萬三千個封包；所以心跳的間隔需要在「多快發現斷線」與「成本」之間權衡，而利用 TCP 自身的 keepalive 或者更長的應用層心跳間隔加上被動的失敗偵測，往往是更好的組合。

## 面試回答方式

先破除**端口數限制**這個常見誤解並說明四元組，再列出四個真正的限制與支撐百萬連線的三個關鍵。加分點有四個：**記憶體是真正的瓶頸**並實際算一次緩衝區的量；執行緒模型決定上限的數量級——理解「為什麼不能一個連線一個執行緒」比記住 epoll 的 API 更重要；**TIME_WAIT 是主動關閉方的問題**，這是「能用長連線就不要用短連線」的實際理由；以及**心跳的成本**與間隔的權衡。

## 講稿

我想先破除一個常見的誤解。端口號只有六萬多所以最多六萬多個連線，這是錯的。那個限制是針對主動發起連線的一方。伺服器端的一個監聽端口可以接受無數連線，因為連線是由來源 IP、來源端口、目的 IP、目的端口這個四元組區分的。

實際會先撞到的有四個。檔案描述符上限、記憶體、核心的連線追蹤表、還有應用層的執行緒模型。

而真正的瓶頸是記憶體，這個值得算一次。Linux 的讀寫緩衝區預設可能各是幾十 KB，一百萬個連線光緩衝區就是幾十 GB。所以要把緩衝區的最小值跟預設值調小，讓核心按實際需要動態增長。

執行緒模型決定了數量級。一個連線一個執行緒的話，每個堆疊預設一 MB，一萬個就是十 GB，而且上下文切換會壓垮 CPU。事件驅動的模型用少數執行緒輪詢大量的描述符，連線數就跟執行緒數解耦了。

另外心跳的成本也要算。一百萬個連線每三十秒一次心跳，是每秒三萬三千個封包。

## 常見追問

### epoll 和 select 的差別是什麼？

**核心答案**：差在「每次呼叫的成本是否隨監聽的 fd 數量成長」。`select` 每次都要把整個 fd 集合從使用者空間複製到核心並線性掃描——於是成本是 O(n)，而且有 1024 個 fd 的硬上限；epoll 把「關注哪些 fd」註冊在核心中（只做一次），每次只回傳「真的有事件的那些」——成本與就緒的 fd 數量成正比而與總數無關。

**詳細解析**：這考察是否理解「epoll 的優勢來自資料結構而非單純的實作優化」——核心用紅黑樹管理註冊的 fd、用一個就緒列表收集有事件的 fd；於是「新增/移除關注」是 O(log n) 而「取得就緒事件」是 O(就緒數)。這個設計的價值在連線數大而活躍比例低時最明顯——十萬個連線中同時只有幾百個在傳資料，是長連線場景的典型分布；而如果所有連線都同時活躍，epoll 的優勢就沒那麼大。能指出「epoll 的優勢取決於活躍比例」而非籠統地說它比較快，展示的是真正理解而非背誦。

**面試回答方式**：給核心差別（每次呼叫的成本是否隨 fd 總數成長）並說明各自的機制。核心加分點是指出 **epoll 的優勢來自資料結構**（紅黑樹加就緒列表）並給出各操作的複雜度。收在關鍵條件：它的優勢在連線數大而活躍比例低時最明顯——如果所有連線同時活躍，優勢就沒那麼大；能指出這個條件而非籠統說它快，展示的是真正理解。

### 百萬連線的服務要怎麼做水平擴展？

**核心答案**：在四層做負載平衡，並讓連線的路由資訊可被查詢。因為長連線一旦建立就固定在某台機器上——所以七層的負載平衡在這裡意義不大，通常用四層（LVS 或雲端的 NLB）分發新的連線（見 [[../computer-network/038-l4-vs-l7-load-balancing.md]]）；而「要推訊息給某個使用者」需要知道他連在哪台機器上，所以要維護一份路由表。

**詳細解析**：這考察「有狀態服務的擴展與無狀態服務不同」——無狀態服務可以隨意增減機器，而長連線服務的每台機器都持有一部分使用者的連線；於是「縮容」意味著要斷開一批使用者並讓他們重連到別處，那是一次可感知的中斷。**所以擴縮容應該是漸進的**：新增機器後由新連線自然分流（而非強制遷移現有連線）；縮容時先停止接受新連線、等現有連線自然減少、再下線。這個「優雅排空」的模式與一般服務的滾動更新（見 [[../kubernetes/029-rolling-update-strategy.md]]）思路一致，但在長連線服務上時間尺度長得多——**可能需要幾十分鐘而非幾秒。**

**面試回答方式**：給做法（四層負載平衡加上可查詢的路由表）並說明為什麼七層在這裡意義不大。核心加分點是有狀態服務的擴展與無狀態不同——縮容意味著斷開一批使用者，那是可感知的中斷，並給出漸進的擴縮容做法。收在對照：這與一般服務的滾動更新思路一致，但時間尺度長得多——可能需要幾十分鐘而非幾秒。

### 怎麼判斷一台機器現在是不是快到極限了？

**核心答案**：**看四組指標而非只看連線數**：**檔案描述符的使用率**（`/proc/sys/fs/file-nr`）、**記憶體與 TCP 緩衝區的佔用**（`ss -m`）、**軟中斷與單核的 CPU 使用率**（網路處理常常集中在少數幾個核心上）、以及重傳率與佇列的溢位計數（`netstat -s` 中的 drop 與 overflow）。

**詳細解析**：這考察**「瓶頸常常不在你以為的地方」**——很多人只監控 CPU 的總體使用率，而網路密集的服務可能在總體只有百分之三十時，某一個核心的軟中斷已經滿載；因為網路卡的中斷若沒有正確地分散到多個核心（RSS 或 RPS 的設定），所有的封包處理會擠在一個核心上。所以正確的監控要看「每個核心」而非平均值。而佇列溢位的計數是一個很有價值的早期信號——`somaxconn` 或 accept 佇列滿了會靜默地丟棄連線請求，而客戶端只會看到連線逾時；這類「靜默的丟棄」如果沒有被監控，排查起來會非常困難。

**面試回答方式**：給四組指標與各自的查看方式。核心加分點是**瓶頸常常不在你以為的地方**——總體 CPU 只有三成時某一個核心的軟中斷可能已經滿載，因為網路卡中斷沒有分散，所以要看每個核心而非平均。收在早期信號：**佇列溢位的計數**——accept 佇列滿了會靜默丟棄連線而客戶端只看到逾時，這類靜默的丟棄沒被監控的話排查非常困難。
