# 題目

「分散式限流」是 Google 與各大公司常被回報的 System Design 題（根據公開的面試經驗分享整理歸納而成，並非逐字官方紀錄）：「每個 API key 每分鐘最多一千次請求。但你的服務跑在一百台機器上，每台都只看到一部分的請求。你會怎麼設計？」這題的關鍵在於「精確性、延遲與可用性之間的取捨」——而它沒有一個標準答案，只有明確的權衡。

## 核心答案

**最直接的做法是「集中計數」**——所有節點都去同一個 Redis 遞增計數並判斷是否超限（見 [[../redis/038-rate-limiting.md]]）；精確、實作簡單，代價是每個請求多一次網路往返，且 Redis 成為單點與瓶頸。

降低延遲與依賴的做法是「本地配額加定期同步」——把總配額分配給各節點（一千除以一百等於每台十次），節點在本地計數；簡單但在流量分布不均時會誤殺（某台收到大部分流量時它先用完配額而其他台還有餘額）。

折衷是「本地計數加非同步匯報」——節點在本地計數並定期（例如每秒）把用量匯報給中心，中心重新分配配額；於是多數請求不需要等待網路往返，而配額能隨流量分布動態調整；**代價是有短暫的超額可能。**

而最重要的判斷是「這個限流是為了什麼」——保護後端不被打垮的話，稍微超額沒關係，選低延遲的方案；而如果是計費相關的配額（超過就要收錢），那就需要精確，值得付出集中計數的成本。

## 詳細解析

「演算法的選擇影響突發流量的處理」（見 [[../backend-engineering/006-rate-limiting-algorithms.md]]）：**固定視窗**實作最簡單但有邊界問題（視窗交界處可能通過兩倍的流量）；**滑動視窗**精確但需要更多的儲存；**令牌桶**允許一定的突發（桶中累積的令牌），這通常更符合真實的使用模式；**漏桶**則強制平滑的輸出。而多數 API 限流選令牌桶，因為它既限制了平均速率又容忍短暫的突發。

「Redis 上的實作要用 Lua 腳本保證原子性」（見 [[../redis/031-lua-scripting.md]]）：讀取當前計數、判斷、遞增——這三步如果分開執行，在高併發下會有競態；用一個 Lua 腳本讓它們原子地完成，是標準做法。而這也是「把多個操作合併成一次往返」的效能優化。

「限流服務本身故障時該怎麼辦」是一個必須回答的問題：如果 Redis 掛了——**是全部放行（fail-open）還是全部拒絕（fail-close）**；對保護型的限流通常選 fail-open（限流掛掉不該讓服務不可用），而對計費或安全型的限流則可能選 fail-close。能主動提出這個問題並說明判斷依據，通常比討論演算法的細節更能展現系統思維。

**「限流的回應要對客戶端友善」**：回傳 429 狀態碼並附上 `Retry-After` 標頭與剩餘配額的資訊——讓客戶端能正確地退避而非盲目重試；因為一個不知道何時該重試的客戶端，會用重試把情況變得更糟。

## 面試回答方式

先給三種方案（集中計數、本地配額、本地計數加非同步匯報）與各自的取捨，再點出最重要的判斷：**這個限流是為了什麼**。加分點有四個：演算法的選擇影響突發流量的處理，而令牌桶通常最符合真實的使用模式；**Redis 上要用 Lua 腳本保證原子性**；**限流服務故障時 fail-open 還是 fail-close** 的判斷；以及**回應要附上 `Retry-After`**，因為不知道何時重試的客戶端會把情況變得更糟。

## 講稿

最直接的做法是集中計數，所有節點都去同一個 Redis 遞增並判斷。精確、實作簡單，代價是每個請求多一次網路往返，而且 Redis 是單點。

另一端是本地配額，把一千除以一百，每台十次。簡單但流量分布不均時會誤殺，某台收到大部分流量時它先用完而其他台還有餘額。

折衷是本地計數加非同步匯報。節點在本地計數，每秒把用量匯報給中心，中心重新分配配額。多數請求不用等網路往返，配額也能隨分布動態調整，代價是有短暫的超額可能。

而我覺得最重要的判斷是先問這個限流是為了什麼。如果是保護後端不被打垮，稍微超額沒關係，選低延遲的方案。如果是計費相關的配額，那需要精確，值得付出集中計數的成本。

還有一個必須回答的問題，限流服務本身掛了怎麼辦。是全部放行還是全部拒絕。保護型的通常選放行，因為限流掛掉不該讓服務不可用。計費或安全型的可能選拒絕。

## 常見追問

### 固定視窗的邊界問題具體是什麼？

**核心答案**：在兩個視窗的交界處可能通過兩倍的配額。如果限制是每分鐘一千次——使用者在第 59 秒送出一千次、第 61 秒再送一千次；兩次都在各自的視窗內合法，但在兩秒內實際通過了兩千次；這對「保護後端」的目的來說是一個真實的漏洞。

**詳細解析**：這考察**「簡單的實作有它的隱含假設」**——固定視窗假設流量在視窗內是均勻的，而攻擊者或者高峰的自然流量都不是；而滑動視窗的日誌（記錄每次請求的時間戳，查詢時統計過去六十秒內的數量）能精確解決，代價是儲存每個請求的時間戳。折衷的做法是「滑動視窗計數器」：保留當前與前一個視窗的計數，用加權估計過去六十秒的量（例如當前視窗過了 30% 時，估計值等於前一視窗的 70% 加上當前視窗的全部）；這個近似的誤差很小而儲存成本只有兩個計數。能提出這個折衷方案，通常比只說「用滑動視窗」更能展現對成本的考量。

**面試回答方式**：用具體的秒數說明邊界問題並指出它是保護後端的真實漏洞。核心加分點是點出固定視窗假設流量在視窗內均勻，而攻擊者與自然高峰都不是，並給出滑動視窗日誌的精確解與它的儲存代價。收在折衷：**滑動視窗計數器用加權估計**——誤差很小而儲存只有兩個計數。

### 怎麼支援不同層級的限流規則？

**核心答案**：用多維度的鍵並依序檢查，任一超限就拒絕。真實的系統通常同時有多個規則：**每個 API key 每分鐘一千次**、**每個 IP 每分鐘一百次**、**每個端點的全域上限**、以及每個使用者對某個昂貴操作的更嚴格限制；而檢查的順序應該把最可能觸發且最便宜的放前面。

**詳細解析**：這考察「限流是一組規則而非單一數字」——而規則之間的關係需要被明確定義：多數情況是「全部都要通過」（AND），但有時是「付費用戶豁免某些規則」這類例外；所以規則的設計應該支援優先級與覆寫。而一個實務上的重點是「規則的變更要能即時生效而不需要重新部署」——因為在遭遇異常流量時，臨時收緊某個規則是最快的止血手段；所以規則應該放在設定中心而非寫死在程式碼裡（見 [[../backend-engineering/031-config-and-feature-flags.md]]）。這個「把應急的旋鈕做成設定」的設計，在事故處理時的價值極高。

**面試回答方式**：給多維度的鍵與依序檢查的做法，並列出真實系統常見的幾層規則。核心加分點是指出規則之間的關係需要明確定義（多數是 AND，但有豁免的例外），所以要支援優先級與覆寫。收在實務重點：**規則的變更要能即時生效**——臨時收緊是最快的止血手段，所以規則應該放在設定中心而非寫死。

### 客戶端該怎麼配合限流？

**核心答案**：主動遵守回傳的配額資訊，而非撞到 429 才反應。伺服器在回應中附上剩餘配額與重置時間——**好的客戶端會據此主動放慢**；而在收到 429 時，必須依 `Retry-After` 退避並加上隨機抖動，避免所有被限流的客戶端在同一時刻重試。

**詳細解析**：這考察「限流的效果取決於雙方的配合」——一個伺服器端完美的限流，遇到不斷重試的客戶端，仍然要花費資源處理與拒絕那些請求；所以「讓客戶端容易做對的事」是限流設計的一部分：提供清楚的標頭、在官方的 SDK 中內建正確的退避、以及在文件中明確說明。而對於惡意或者無法改變的客戶端，則需要更上游的防護（在負載平衡器或 WAF 層直接丟棄，成本遠低於進到應用層才拒絕）。這個「把防護放在成本最低的層級」的分層思路，是流量治理的核心——因為在應用層拒絕一個請求的成本，可能是在邊緣丟棄它的一百倍。

**面試回答方式**：給客戶端該做的（主動遵守配額資訊、依 `Retry-After` 退避並加抖動）。核心加分點是指出限流的效果取決於雙方的配合，並說明「讓客戶端容易做對的事」是設計的一部分（清楚的標頭、SDK 內建退避、文件說明）。收在分層：對惡意或無法改變的客戶端要在更上游丟棄——在應用層拒絕一個請求的成本可能是在邊緣丟棄的一百倍。
