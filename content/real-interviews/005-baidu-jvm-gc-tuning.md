# 題目

這是百度（以及同類型擁有大規模 Java 後端服務的公司）面試裡**相當經典的實務排查題**（根據公開面試經驗分享整理歸納而成，並非逐字官方紀錄）：**「線上的一個 Java 服務，最近回應時間（Response Time）突然飆高，你懷疑是 GC 的問題，你會怎麼一步一步排查並找出根本原因？」**這題**考的不是背誦 GC 演算法的理論**，而是**你是否具備真實的線上故障排查經驗和方法論**。

## 核心答案

排查這類問題的**標準流程**大致是——**(1) 先確認是不是 GC 問題**：透過 `jstat -gcutil <pid> 1000` 這類工具、或者查看 **GC 日誌**，確認是否真的存在**頻繁的 Full GC**，以及**每次 GC 所花費的時間**是否異常地長；**(2) 分析 GC 日誌找出觸發原因**：確認是**老年代（Old Generation）持續被填滿**、還是 **Metaspace 不足**、還是**大物件直接晉升到老年代**導致這些 Full GC；**(3) 進一步用工具找出實際佔用記憶體的物件**：用 `jmap -histo`，或者把 **heap dump** 匯出，用 **MAT（Memory Analyzer Tool）**這類工具分析，找出**究竟是哪些物件**佔用了大量的記憶體，導致老年代持續被填滿；**(4) 依照找到的根本原因對症下藥**：可能是**記憶體洩漏（Memory Leak）**（某些物件應該被回收，卻因為程式碼的疏漏而一直被其他物件持有參照，導致無法被回收，見 [[../java-concurrency/008-threadlocal-memory-leak.md]]）、也可能只是**單純的 JVM 堆積大小（Heap Size）設定不足**（見 [[../jvm/013-jvm-tuning-params.md]]），需要依照實際情況分別處理。

## 詳細解析

**這題的核心考點——你是否真的有實際排查過生產環境問題的經驗**：百度這類**擁有大量生產環境 Java 服務**的公司特別重視這種**真實故障排查**的實務經驗——面試官很常會**故意追問非常具體的工具指令**（例如「你會用什麼指令去查看目前的 GC 狀況？」），如果你**只能模糊地說『用工具去看』**，卻**答不出任何具體的指令名稱或參數**，這會讓面試官強烈懷疑你是否**真的曾經在實際的生產環境裡**處理過這類問題——建議**實際地在自己的電腦上動手操作過**這些工具（`jstat`、`jmap`、`jstack` 等）**至少一次**，親自體驗過完整的排查流程，而不是只停留在**理論上知道這些工具的名字**。

**GC 調優和先前已經深入討論過的 GC 演算法知識如何連結——這題是理論知識的實戰應用**：這題**建立在**前面（見 [[../jvm/003-gc-roots-reachability.md]]、[[../jvm/004-gc-algorithms.md]]、[[../jvm/014-gc-troubleshooting.md]]）已經深入討論過的 **GC 核心理論**之上——如果你**不理解「為什麼大物件會直接晉升到老年代」**、或者**「為什麼老年代被持續填滿就會觸發 Full GC」**這類基礎理論，即使記住了一堆工具指令，也**沒辦法真正說明清楚**「你看到的這些現象究竟代表什麼意思」——建議先把那幾題 GC 的核心理論徹底搞懂，再回來練習這一題如何把**理論**和**實務排查工具**結合起來，講出一個**完整、有邏輯**的排查故事。

**回答這類題目最容易犯的錯——直接跳到結論，而沒有展現排查過程**：這類**開放式的故障排查題**一個很常見的失分點，是**候選人直接跳到「這一定是記憶體洩漏」**這種結論，卻**沒有展現出任何實際一步一步排查、驗證**的過程——面試官真正想看到的是**你如何依照一連串的證據****逐步縮小問題範圍，最終才導向一個有根據的結論**，而**不是一開始就憑直覺猜測一個答案**——建議回答時明確地用**「先⋯⋯，接著⋯⋯，如果發現⋯⋯，就代表⋯⋯，再進一步⋯⋯」**這種**具備清楚邏輯順序**的敘事方式，去展現你**完整的排查思路**，而不是只丟出一個**看起來像是正確答案**的結論。

## 面試回答方式

先給出完整的排查流程框架——「標準流程是先用jstat或GC日誌確認是不是真的GC問題，以及頻繁程度和每次耗時;接著分析GC日誌找出觸發原因，是老年代持續被填滿、Metaspace不足、還是大物件直接晉升老年代;然後用jmap或heap dump搭配MAT這類工具，找出實際佔用記憶體的物件;最後依照找到的根本原因對症下藥，可能是記憶體洩漏也可能只是堆積大小設定不足」。展現具體的工具操作經驗——「例如用jstat -gcutil <pid> 1000去即時觀察GC狀況，或者用jmap -histo查看物件佔用排行」。用清楚的邏輯順序敘事展現排查思路，而不是直接跳到結論——「先確認現象，再逐步縮小範圍，最後才導向有根據的結論，而不是一開始就憑直覺猜測答案」，展現你具備真實的生產環境故障排查經驗，而非只是背誦GC理論。

## 常見追問

### 如果你發現是**大量大物件**直接晉升到老年代，導致老年代持續被填滿，你會怎麼處理？

**核心答案**：需要先**確認這些大物件是否真的是業務上必要**的——如果是**不必要的、可以被優化掉**的大物件（例如一次性載入過多不必要的資料到記憶體裡），應該從**業務邏輯本身**去優化，減少這種大物件的產生；如果這些大物件**確實是業務必需**的，可以考慮**調整 JVM 參數**——例如**適度地調高 `-XX:PretenureSizeThreshold` 這個決定多大的物件才會被直接判定為大物件、而直接晉升老年代**的門檻，讓這些物件**先嘗試在新生代（Young Generation）**走正常的晉升流程，而不是**一律直接**繞過新生代晉升到老年代。

**詳細解析**：這題考察是否理解**「大物件直接晉升老年代」這個 JVM 設計機制本身的用意**——這個機制設計的初衷是**避免巨大的物件在新生代裡反覆地被複製、搬移**（見 [[../jvm/004-gc-algorithms.md]]，新生代常用的複製演算法每次 minor GC 都需要把存活的物件複製到另一塊空間，如果一個物件本身就非常大，這種反覆複製的成本會相當可觀），所以才設計了**「夠大的物件乾脆直接放到老年代」**這個捷徑；但如果**大量這種大物件**被**過度頻繁地**直接放進老年代，反而會導致**老年代被過快填滿**。這種「理解一個 JVM 機制原本設計的用意，以及它在什麼情況下可能反而帶來副作用」的深度理解，才能真正判斷應該如何恰當地調整相關參數。

**面試回答方式**：先給出判斷邏輯——「需要先確認這些大物件是否真的是業務上必要的，如果是不必要可以優化掉的大物件，應該從業務邏輯本身去優化;如果確實是業務必需，可以考慮調整JVM參數，例如適度調高PretenureSizeThreshold這個大物件晉升門檻，讓物件先嘗試在新生代走正常晉升流程」。可以補充機制設計原理的理解——「大物件直接晉升老年代這個機制，原本設計初衷是避免巨大物件在新生代反覆被複製搬移的成本，但如果過度頻繁觸發，反而會導致老年代被過快填滿，理解這個機制原本的設計用意，才能判斷應該如何恰當調整參數」。

### 如果你懷疑是記憶體洩漏，你會怎麼具體地找出是哪一段程式碼造成的？

**核心答案**：核心做法是**透過 heap dump 分析工具（如 MAT）找到那些數量異常龐大、或者佔用記憶體異常大**的物件類型，接著**查看這些物件的『GC Roots 引用鏈（Reference Chain to GC Roots）』**——也就是**追蹤這些物件究竟是被哪一個更上層的物件持有著參照，才導致它們無法被回收**；透過**一路追蹤這個引用鏈**，通常就能找到**究竟是程式碼裡的哪一個具體位置**（例如一個全域存在的集合物件持續被加入新元素，卻從未被清除）導致了這種記憶體洩漏。

**詳細解析**：這題考察是否理解**「記憶體洩漏的本質」**——延續前面（見 [[../jvm/003-gc-roots-reachability.md]]）已經深入討論過的 **GC Roots 可達性分析**核心概念——一個物件之所以**不會被 GC 回收**，是因為它**依然存在一條從 GC Roots 出發、能夠到達它的引用鏈**。記憶體洩漏本質上就是**「某個物件本來應該已經不再被業務邏輯實際需要，卻因為某個程式碼上的疏漏，而依然存在著一條通往 GC Roots 的引用鏈，導致垃圾回收（Garbage Collection）器誤判斷它依然是存活、有用的物件」**，因此**找出記憶體洩漏的關鍵方法**正是**反過來去追蹤這條不應該存在、卻依然存在的引用鏈**。這也呼應了前面（見 [[../java-concurrency/008-threadlocal-memory-leak.md]]）已經深入討論過的 **ThreadLocal 記憶體洩漏**這個具體案例——那正是一種**『某個物件（ThreadLocal 的 value）因為某個特定的引用鏈（透過執行緒本身長期存活的 ThreadLocalMap）而遲遲無法被回收』**的典型記憶體洩漏情境。

**面試回答方式**：先給出核心做法——「透過heap dump分析工具如MAT，找到數量異常龐大或佔用記憶體異常大的物件類型，接著查看這些物件的GC Roots引用鏈，追蹤這些物件究竟是被哪個更上層物件持有參照才導致無法被回收，一路追蹤通常就能找到具體是程式碼裡哪個位置造成的洩漏」。可以連結到之前的GC Roots核心概念——「這呼應了之前討論過的GC Roots可達性分析，記憶體洩漏本質上就是某個物件本來應該不再被業務邏輯需要，卻因為程式碼疏漏而依然存在一條通往GC Roots的引用鏈，導致垃圾回收器誤判它依然是存活有用的物件，這也和之前討論過的ThreadLocal記憶體洩漏是同一種本質——某個物件因為特定引用鏈而遲遲無法被回收」。

### 如果這個問題只有在特定的某幾台伺服器上才會出現，其他配置完全相同的伺服器卻沒有這個問題，你會怎麼思考？

**核心答案**：既然**其他配置相同**的伺服器沒有出現這個問題，說明**問題很可能不是出在程式碼本身或 JVM 設定**（因為這些在所有伺服器上都是一致的），而是**這幾台出問題的伺服器實際上承接到的『流量特性』或『資料特性』和其他伺服器不一樣**——需要去檢查——**(1) 負載平衡（Load Balancing）是否真的均勻**：這幾台伺服器是否因為某種原因實際上承接了**更高的流量**、或者**特定某一類更容易觸發問題的請求類型**；**(2) 是否存在某種特定的『熱點資料』（見 [[../redis/019-hotkey-bigkey.md]] 相關概念）剛好只會被路由到這幾台伺服器**。

**詳細解析**：這題考察是否具備**「利用對照組去縮小問題範圍」**這種**科學化的除錯思維**——當你發現**「相同的配置，卻只有部分節點出問題」**這種現象時，這本身就是一個**極為重要的線索**——它**直接排除掉「問題出在程式碼本身或 JVM 設定」**這個可能性（因為如果是這些共通因素造成的，**所有配置相同的伺服器應該都會一樣出問題**），把排查的焦點**準確地導向「這幾台伺服器實際上承受的外部條件，究竟和其他伺服器有什麼不同」**這個更聚焦的方向。這種**「善用『為什麼只有這幾個個案出問題，而不是全部都出問題』這個線索去快速縮小排查範圍」**的能力，是資深工程師在面對**複雜、線索不夠明確**的生產環境問題時一項相當關鍵的實務排查技巧。

**面試回答方式**：先給出核心推理邏輯——「既然其他配置相同的伺服器沒有出現這個問題，說明問題很可能不是出在程式碼本身或JVM設定，因為如果是這些共通因素造成的，所有配置相同的伺服器應該都會一樣出問題，問題很可能是這幾台伺服器實際承接到的流量特性或資料特性不一樣」。給出具體排查方向——「需要檢查負載平衡是否真的均勻，這幾台伺服器是否因某種原因實際承接了更高流量或特定更容易觸發問題的請求類型，以及是否存在某種特定熱點資料剛好只會被路由到這幾台伺服器」。可以總結這種除錯思維的價值——「善用只有部分個案出問題而非全部都出問題這個線索，能快速縮小排查範圍，這是面對複雜生產環境問題時相當關鍵的實務排查技巧」。
