# 題目

多代理架構有什麼代價？什麼情況下單一 Agent 更好？

## 核心答案

多代理的代價有四層，而它們常常被「架構圖看起來很專業」掩蓋。

**成本**——Agent 數量與輪數相乘，通常是單一 Agent 的五到十倍。

**延遲**——串行的交接讓每一步的延遲累加；一個五階段的管線可能要幾十秒。

**可靠性**——每個環節都有失敗機率，串聯之後整體成功率是乘積：**五個各 90% 的環節，整體只有 59%**。

**可除錯性**——問題可能出在任何一個 Agent 或任何一個交接處，而追蹤與歸因的難度遠高於單一 Agent。

所以「單一 Agent 加上好的工具」應該是預設選擇——只有在上下文隔離、權限分離、或真正的並行這三種明確需求下，多代理才值得。

## 詳細解析

「成功率的乘積」是最有說服力的反對理由，而它常常被忽略：每個環節 90% 聽起來不錯——**但五個串起來只剩 59%**。**要讓整體達到 90%，每個環節需要 98%**——**而那是很高的要求**。這解釋了為什麼「看起來合理的多階段設計」在實際跑起來時失敗率高得驚人。緩解的方式是「減少階段數」與「在每個階段加入驗證與重試」——**但後者又增加了成本與延遲**。所以階段數應該被視為一個需要被最小化的量，而不是「拆得越細越專業」。

「用多代理掩蓋單一 Agent 的問題」是一個常見的錯誤路徑：Agent 表現不好——於是加一個「審查者 Agent」來檢查它的輸出。但如果原始的問題是提示不清或工具設計不良，審查者只是在事後修補，**而根因仍在**。正確的順序是「先把單一 Agent 做到最好，再考慮是否需要拆分」——因為多代理會讓根因更難被發現（**問題被分散到多個環節**）。

「人的角色分工不必映射到 Agent 的分工」：真實團隊裡有產品、設計、開發、測試——但這個分工反映的是人的專長與時間限制，而不是任務本身的最佳結構。一個模型不需要「切換角色」才能做不同的事——強行模仿人類的組織結構往往只是增加了交接成本。這個觀察能幫助抵抗「多代理系統看起來更像一個團隊所以更好」這種直覺。

「什麼時候多代理確實值得」也要說清楚：**上下文隔離**（每個子任務需要大量不同的上下文）、**權限分離**（不同的資料存取邊界，是安全要求）、**以及真正的並行**（獨立的子任務同時進行）。這三種都是結構性的理由，而不是「感覺這樣比較好」。

## 面試回答方式

先給四層代價（成本、延遲、可靠性、可除錯性）並主張「單一 Agent 加好工具」應該是預設選擇。加分點有四個：**成功率的乘積最有說服力**——五個各 90% 的環節整體只有 59%，要整體 90% 每個需要 98%，這解釋了為什麼看起來合理的多階段設計實際失敗率高得驚人，所以階段數應該被最小化而非拆得越細越好；**用多代理掩蓋單一 Agent 的問題**是常見的錯誤路徑——加審查者只是事後修補而根因仍在，且多代理讓根因更難發現；人的角色分工不必映射到 Agent 的分工——那反映的是人的專長與時間限制而非任務的最佳結構；以及明確列出**三種結構性的正當理由**。

## 講稿

多代理的代價有四層，而它們常常被架構圖看起來很專業掩蓋。成本、延遲、可靠性、還有可除錯性。

我認為最有說服力的反對理由是成功率的乘積。每個環節九成聽起來不錯，但五個串起來只剩五成九。要讓整體達到九成，每個環節需要九成八，而那是很高的要求。這解釋了為什麼看起來合理的多階段設計，實際跑起來失敗率高得驚人。所以階段數應該被視為一個需要被最小化的量，而不是拆得越細越專業。

還有一個常見的錯誤路徑，用多代理掩蓋單一代理的問題。代理表現不好，於是加一個審查者來檢查它的輸出。但如果原始問題是提示不清或工具設計不良，審查者只是在事後修補，根因仍在，而且多代理會讓根因更難被發現。

另外我想說，人的角色分工不必映射到代理的分工。真實團隊有產品、設計、開發、測試，但那反映的是人的專長跟時間限制，不是任務本身的最佳結構。一個模型不需要切換角色才能做不同的事。

## 常見追問

### 那些「多代理框架」的 demo 為什麼看起來很有效？

**核心答案**：因為 demo 的任務通常是「有明確步驟且每一步都不容易錯」的——在那種任務上，任何合理的架構都會成功。而真實任務的困難在於「模糊的需求、意外的資料、以及需要判斷的情況」——這些恰恰是多代理的交接處最容易出錯的地方。**所以 demo 的成功不能推論到生產。**

**詳細解析**：「評估多代理框架應該用你自己的困難案例」：拿一個你實際遇到過、單一 Agent 做不好的任務去測——如果多代理也做不好，那說明問題不在架構。而更重要的判斷是「這個框架讓我更容易除錯還是更難」：一個好的框架應該提供清晰的追蹤、可回放的執行、以及明確的狀態——如果它只是讓你能用幾行程式碼組出一個多代理系統，卻在出問題時完全看不出發生了什麼，那它解決的是最容易的部分而留下了最難的部分。「容易組裝」與「容易維運」是兩件不同的事，而後者才決定一個系統能不能上生產。

**面試回答方式**：給根本原因——demo 的任務通常每一步都不容易錯，而真實任務的困難在模糊需求、意外資料與需要判斷的情況，恰恰是交接處最容易出錯的地方。核心加分點是給出評估方法：**用你自己的困難案例測**，並提出更重要的判斷——這個框架讓我更容易除錯還是更難。收在原則：「容易組裝」與「容易維運」是兩件不同的事，只讓你幾行程式碼組出系統卻在出問題時看不出發生什麼的框架，解決的是最容易的部分。

### 如果已經做成多代理了，怎麼簡化？

**核心答案**：從「合併相鄰且總是一起成功或失敗的階段」開始。如果 A 之後總是接 B，而且 B 幾乎不會在 A 成功後失敗——**那它們可以合併成一個階段**。然後看「有沒有階段其實只是在做確定性的轉換」——**那些應該變成程式碼而不是 Agent**。最後檢查「每個剩下的階段是否對應一個真實的上下文、權限、或並行需求」。

**詳細解析**：「只是在做確定性轉換的 Agent」是最容易被移除的：一個「格式化 Agent」把上游的輸出轉成下游需要的格式——這件事應該用程式碼做，而不是花一次模型呼叫。這類階段在多代理系統中出乎意料地常見，因為它們是在「上游輸出的格式不符合下游期待」時被加上去的補丁——而正確的修法是統一介面而非加一個翻譯層。移除它們同時降低了成本、延遲、與失敗率，**是簡化中收益最直接的一步**。而更廣的觀察是：多代理系統的複雜度往往是「一層層補丁累積」而非一開始就設計成這樣——所以定期回頭問「每個階段還有存在的必要嗎」是有價值的。

**面試回答方式**：給三步簡化流程（合併總是一起成功失敗的相鄰階段、把確定性轉換變成程式碼、檢查剩下的階段是否對應真實需求）。核心加分點是「只是在做確定性轉換的 Agent」最容易被移除——它們往往是「上游輸出不符合下游期待」時加的補丁，而正確的修法是統一介面而非加翻譯層，移除同時降低成本、延遲與失敗率。收在觀察：多代理的複雜度往往是一層層補丁累積而非一開始就這樣設計，所以定期問「每個階段還有存在的必要嗎」是有價值的。

### 面試官說「我們就是要做多代理」怎麼回應？

**核心答案**：接受方向並談具體的設計選擇。合理的回答是：「我認同，我會關心的是拓撲的選擇與收斂的保證。」 然後給**拓撲的建議**（從主從開始，因為決策集中易於觀察）、**收斂機制**（輪數上限、明確的決策者、無共識時的處理）、**以及可觀測性的要求**（樹狀追蹤、按角色的指標、記錄交接內容）。

**詳細解析**：這個追問測的是「你能不能在既定方向下提出專業意見」——單純反對顯得不合作，全盤接受顯得沒有判斷。而最有價值的具體建議是「先做一個能跑通的最小拓撲，再按實測的瓶頸擴展」：很多多代理專案失敗不是因為方向錯，而是一開始就設計了六個角色的複雜結構，然後在任何一處出問題時都無法定位。從兩個角色開始、把追蹤與評估建好、再逐步增加——這個順序讓每一次增加的價值都能被量測。另一個值得提的是「先確定每個角色的評估標準」：如果無法說出「這個角色做得好不好怎麼判斷」，那個角色的存在就是可疑的——而這個問題往往能在設計階段就篩掉不必要的角色。

**面試回答方式**：給態度——接受方向並談拓撲選擇與收斂保證，然後給三項具體建議。核心加分點是先做能跑通的最小拓撲再按實測瓶頸擴展——很多失敗不是方向錯，而是一開始就設計六個角色然後任何一處出問題都無法定位，從兩個角色開始、建好追蹤與評估、再逐步增加。收在一個能在設計階段篩掉冗餘角色的問題：「這個角色做得好不好怎麼判斷」說不出來的話，那個角色的存在就是可疑的。
