# 題目

編碼類 Agent 有什麼特別的地方？在大型專案上的難點是什麼？

## 核心答案

編碼 Agent 有一個其他領域羨慕的優勢：驗證是自動的。**編譯、型別檢查、測試、lint**——這些讓「輸出對不對」從一個模糊的判斷變成一個確定的結果。這正是編碼類 Agent 比其他類型更早成熟的根本原因。

**而它的難點集中在三處。**

上下文與程式碼庫的規模不匹配——一個十萬行的專案放不進上下文；所以必須靠搜尋與導航而非通讀，而「找到正確的相關程式碼」往往比「寫出正確的程式碼」更難。

**變更的影響範圍難以評估**——改一個函式可能影響二十個呼叫端；**而模型看不到全部**，於是「在局部正確但在整體錯誤」的修改很常見。

**測試的覆蓋不完整**——**測試通過不等於正確**；在測試薄弱的專案上，自動驗證的價值大打折扣。

## 詳細解析

「導航比生成更難」是大型專案上的核心洞察：模型寫一個函式的能力已經相當好——而「知道該改哪個檔案、這個功能在哪裡實作、誰呼叫了它」需要對整個專案的理解。所以編碼 Agent 的能力很大程度上取決於它的工具：高效的內容搜尋、符號定義與引用查找、以及專案結構的概覽。給一個模型好的程式碼搜尋工具，往往比換一個更強的模型收益更大——因為前者解決的是資訊獲取的瓶頸，而那是當前的主要限制。

「驗證的深度決定了自主性的上限」：一個有完整測試與 CI 的專案，Agent 可以自主地嘗試、驗證、修正，直到綠燈；而一個沒有測試的專案，Agent 只能寫出「看起來對」的程式碼並交給人審查。所以「投資測試基礎設施」在採用編碼 Agent 之前比之後更有價值——這是一個違反直覺但很實在的順序建議。

「小步驟加驗證」比「一次寫完」可靠得多：每改一個小部分就跑測試——於是錯誤在產生的當下就被發現，而不是累積到最後。這與人類的開發實踐一致，但對 Agent 更重要，因為它無法像人一樣「感覺哪裡不對」。

「與版本控制整合」是編碼 Agent 的基礎設施要求：每一步提交、可以 diff、可以回滾、可以在分支上工作——這讓 Agent 的工作可以被審查、被撤銷、被合併，而那正是把它接入既有工程流程的方式。

## 面試回答方式

先給優勢——驗證是自動的，這正是編碼類更早成熟的根本原因，再給三個難點（規模不匹配、影響範圍難評估、測試覆蓋不完整）。加分點有四個：**導航比生成更難**——寫函式的能力已經不錯，而「知道該改哪裡」需要對整個專案的理解，所以給好的搜尋工具往往比換更強的模型收益更大；驗證的深度決定自主性的上限——有完整測試的專案讓 Agent 能自主嘗試到綠燈，沒有測試就只能交給人審查，所以投資測試基礎設施在採用之前比之後更有價值；小步驟加驗證比一次寫完可靠——對 Agent 更重要，因為它無法像人一樣感覺哪裡不對；以及與版本控制整合是基礎設施要求。

## 講稿

編碼代理有一個其他領域羨慕的優勢，驗證是自動的。編譯、型別檢查、測試、靜態檢查，這些讓輸出對不對從一個模糊的判斷變成確定的結果。這正是它比其他類型更早成熟的根本原因。

難點集中在三處。上下文跟程式碼庫的規模不匹配、變更的影響範圍難以評估、還有測試覆蓋不完整。

我認為在大型專案上最核心的洞察是導航比生成更難。模型寫一個函式的能力已經相當好，而知道該改哪個檔案、這個功能在哪裡實作、誰呼叫了它，需要對整個專案的理解。所以編碼代理的能力很大程度上取決於它的工具，高效的內容搜尋、符號定義與引用查找、專案結構的概覽。給模型一個好的搜尋工具，往往比換一個更強的模型收益更大。

還有一個違反直覺但很實在的建議。驗證的深度決定了自主性的上限。有完整測試的專案，代理可以自主嘗試、驗證、修正直到綠燈。沒有測試的專案，它只能寫出看起來對的程式碼交給人審查。所以投資測試基礎設施，在採用編碼代理之前比之後更有價值。

## 常見追問

### 怎麼讓 Agent 遵守專案的慣例？

**核心答案**：用可執行的規則優於用文件描述。**linter 與格式化工具**（**違規會直接報錯，Agent 自然會修正**）、**型別系統**（**約束在編譯期被強制**）、**以及範例程式碼**（讓它看到既有的寫法比讀規則有效）。文件形式的慣例（例如一份 CONTRIBUTING.md）作為補充，但不能作為主要的保證。

**詳細解析**：「讓違規變成一個錯誤」是最可靠的機制：Agent 會修正錯誤——所以任何能被表達成 lint 規則的慣例，都會被自動遵守。而只寫在文件裡的慣例，遵守與否取決於它有沒有讀到、記不記得。所以「把團隊的慣例編碼成工具」的投入，在引入編碼 Agent 之後回報大幅提升——因為它從「幫助人類保持一致」變成了「自動地保證 Agent 一致」。另一個實用的做法是「在專案中放一份給 Agent 讀的說明」：架構概覽、關鍵目錄的用途、常見的操作方式——這相當於給新人的入職文件，而它對 Agent 的價值同樣高。很多團隊發現，寫這份文件的過程本身也澄清了團隊內部的模糊之處。

**面試回答方式**：主張**可執行的規則優於文件描述**並給三種手段。核心加分點是讓違規變成錯誤是最可靠的機制——Agent 會修正錯誤，所以能表達成 lint 規則的慣例會被自動遵守，而「把慣例編碼成工具」的投入在引入編碼 Agent 之後回報大幅提升。收在**在專案中放一份給 Agent 讀的說明**（架構概覽、目錄用途、常見操作），**相當於給新人的入職文件**，而寫它的過程本身也澄清了團隊內部的模糊之處。

### Agent 寫的程式碼要怎麼審查？

**核心答案**：與人寫的程式碼同樣審查，但要多注意三類問題。看似合理但不符合實際需求的實作（它可能誤解了需求而寫出一個自洽但錯誤的方案）。**過度的改動**（它可能順手重構了不需要改的部分）。以及「看起來有處理但實際無效」的錯誤處理（捕捉了例外卻只是記錄然後繼續）。

**詳細解析**：「Agent 的程式碼往往表面品質很高」讓審查更容易鬆懈：命名良好、有註解、格式正確——於是審查者容易被表象說服而略過深入檢查。而真正的問題常常在語義層面（誤解了需求、遺漏了邊界情況）而非表面層面。所以審查編碼 Agent 的輸出時，應該把重點放在「這是不是解決了正確的問題」而非「這段程式碼寫得好不好」。一個實用的做法是「先讀它的變更說明與測試，再讀實作」——如果測試沒有覆蓋你關心的情況，那就是一個訊號。另一個是「要求它說明為什麼這樣改」——推理過程中的錯誤假設往往比程式碼本身更容易被發現。

**面試回答方式**：給三類要多注意的問題。核心加分點是Agent 的程式碼表面品質往往很高讓審查更容易鬆懈——命名良好、有註解、格式正確，於是審查者被表象說服，**而真正的問題在語義層面**，所以重點應該是「這是不是解決了正確的問題」而非「寫得好不好」。收在兩個實用做法：先讀變更說明與測試再讀實作（測試沒覆蓋你關心的情況就是訊號）、**要求它說明為什麼這樣改**（推理中的錯誤假設比程式碼更容易被發現）。

### 大型重構這類任務適合交給 Agent 嗎？

**核心答案**：適合機械性的部分，不適合需要判斷的部分。改名、統一格式、批次替換一個 API 的呼叫方式——這些有明確的規則且能被測試驗證，Agent 做得又快又好。而「這個模組該怎麼拆分」「這個抽象合不合理」需要對業務與未來演進的判斷——**那應該由人決定，Agent 執行。**

**詳細解析**：「先由人定計畫、再由 Agent 執行」是大型變更的正確分工：人決定目標架構與拆分邊界——然後把它拆成一系列明確、可驗證的小步驟交給 Agent。這既利用了 Agent 的執行速度，又保留了人的架構判斷。而反過來（讓 Agent 自己決定怎麼重構）風險很高：它可能做出局部合理但整體不一致的決定，而且大範圍的改動一旦方向錯了，修正的成本極高。另一個實務要點是「大重構要能增量驗證」：不要一次改一百個檔案然後跑測試——而是分批改、分批驗證、分批提交，於是問題能在小範圍內被定位。這與人類做大重構的最佳實踐完全一致，只是 Agent 的速度讓「一次改太多」的誘惑更大。

**面試回答方式**：給分類（機械性的適合、需要判斷的不適合）。核心加分點是**先由人定計畫、再由 Agent 執行**這個分工——人決定目標架構與邊界，拆成明確可驗證的小步驟，既利用執行速度又保留架構判斷，並說明反過來的風險（局部合理但整體不一致、方向錯了修正成本極高）。收在**大重構要能增量驗證**——**分批改、分批驗證、分批提交**，與人類的最佳實踐一致，只是 Agent 的速度讓「一次改太多」的誘惑更大。
