# 題目

Agent 要查五個獨立的資料源，怎麼設計才不會一個一個等？

## 核心答案

關鍵是「讓模型一次產出多個工具呼叫，框架並行執行」——而不是每一步只呼叫一個然後等結果。

現代的 function calling 支援在一次回應中產出多個呼叫，框架把它們並行送出並在全部完成後一起回傳。收益是直接的：五個各需 500 毫秒的查詢，從 2.5 秒變成 500 毫秒。

但並行只適用於「彼此不依賴」的呼叫。**有依賴的必須串行**——因為第二個呼叫的參數來自第一個的結果。而模型自己會判斷這一點：獨立的它會一起發，有依賴的它自然會分步——前提是工具的描述讓依賴關係清晰。

**三個要注意的點**：**並行的錯誤處理**（一個失敗時其他的結果要不要保留——通常要保留並一起回傳，讓模型知道哪些成功了）、**並行度的上限**（避免一次發出五十個請求打垮下游）、**以及結果的順序**（回傳時要與呼叫對應，不能錯亂）。

## 詳細解析

「讓模型願意並行」需要提示與工具設計的配合：如果工具描述暗示了順序（「先呼叫 A 取得 ID，再呼叫 B」）——**模型會串行**。而如果明確說明「這幾個查詢彼此獨立，可以同時進行」，並在系統提示中鼓勵「盡可能一次發出所有不相依的呼叫」，**並行的比例會顯著提升**。這是一個「模型有能力但需要被告知這是被期待的」的典型例子——而它的收益（延遲減半以上）遠大於實作成本。

「部分失敗的回傳格式」值得仔細設計：五個呼叫中兩個失敗——應該回傳一個包含五個結果的列表，成功的給資料、失敗的給錯誤說明，**而不是整批失敗**。這讓模型能基於已有的三個結果繼續，並針對失敗的兩個決定重試或繞過。「全有全無」的處理在這裡是明顯的浪費。

「並行不等於更快」在某些情況成立：如果下游有共用的限流或連線池——並行反而會觸發限流並導致整體變慢。所以並行度應該可配置，並根據下游的實際容量設定。這與一般的併發控制是同一個道理，只是這裡的「請求發起者」是一個不了解下游容量的模型——**所以限制必須在框架層施加**。

**「更高層的並行」是另一個維度**：不只是工具呼叫，**多個子任務也可以並行**（例如同時分析三個檔案）。**這需要 Agent 框架支援分支與匯合**——而它帶來的複雜度（狀態管理、部分失敗、結果合併）遠高於工具層的並行，所以應該只在收益明確時才引入。

## 面試回答方式

先給核心做法——讓模型一次產出多個工具呼叫，框架並行執行，並量化收益（五個 500 毫秒的查詢從 2.5 秒變 500 毫秒）。指出並行只適用於彼此不依賴的呼叫，而模型自己會判斷，前提是描述讓依賴關係清晰。加分點有四個：讓模型願意並行需要提示配合——明確說明「這幾個查詢彼此獨立」並鼓勵一次發出所有不相依的呼叫，這是「模型有能力但需要被告知這是被期待的」的典型例子；**部分失敗要回傳完整列表**，成功的給資料失敗的給說明，全有全無是明顯的浪費；**並行不等於更快**——**下游有共用限流時反而變慢**，而限制必須在框架層施加因為模型不了解下游容量；以及更高層的子任務並行複雜度高得多，應該只在收益明確時引入。

## 講稿

關鍵是讓模型一次產出多個工具呼叫，框架並行執行，而不是每一步只呼叫一個然後等結果。現代的函式呼叫支援在一次回應裡產出多個呼叫。收益是直接的，五個各需五百毫秒的查詢，從兩秒半變成五百毫秒。

但要讓模型願意並行，需要提示跟工具設計的配合。如果工具描述暗示了順序，模型就會串行。而如果明確說明這幾個查詢彼此獨立、可以同時進行，並在系統提示裡鼓勵一次發出所有不相依的呼叫，並行的比例會顯著提升。這是一個模型有能力但需要被告知這是被期待的典型例子。

有三個要注意的點。第一是部分失敗的回傳格式，五個裡兩個失敗，應該回傳完整的列表，成功的給資料、失敗的給錯誤說明，而不是整批失敗。第二是並行度要有上限，避免一次發出五十個請求打垮下游。要注意模型並不了解下游的容量，所以限制必須在框架層施加。第三是結果的順序要跟呼叫對應，不能錯亂。

## 常見追問

### 有依賴關係的多步任務怎麼加速？

**核心答案**：先做依賴分析，把能並行的分層。一個任務如果是「查 A、查 B、然後用 A 和 B 的結果查 C」——**A 和 B 可以並行，C 必須等**。**做法有兩種**：**讓模型自己規劃**（在 Plan-and-Execute 模式下，計畫本身可以標註依賴），或者由框架分析工具呼叫的參數來源自動判斷。**前者更靈活，後者更可靠。**

**詳細解析**：「推測性執行」是一個進階但有效的技巧：如果能猜到接下來很可能需要某個查詢——就提前發出它，如果猜對了就省下一輪延遲，猜錯了只是浪費一次便宜的查詢。這與 CPU 的分支預測是同一個思路。在 Agent 中的具體應用是「預取常用的上下文」：例如一個客服 Agent 在收到使用者訊息時，就先並行地取得該使用者的基本資料與最近訂單——**不管模型會不會用到**。判斷划不划算的標準是「預取的成本」與「命中的機率乘以節省的延遲」——在下游查詢便宜而延遲敏感的場景中，這幾乎總是划算的。

**面試回答方式**：給依賴分析與分層的做法，並比較「模型自己規劃」與「框架自動分析」的取捨。核心加分點是**推測性執行**：提前發出很可能需要的查詢，猜對省一輪延遲、猜錯只浪費一次便宜的查詢，**與 CPU 的分支預測是同一個思路**。給具體應用（客服 Agent 預取使用者資料與最近訂單）並收在判斷標準：預取成本與「命中機率乘節省的延遲」的比較，在下游便宜而延遲敏感時幾乎總是划算。

### 並行呼叫的結果太多塞爆上下文怎麼辦？

**核心答案**：在框架層做結果的裁剪與匯總，而不是原樣塞給模型。五個查詢各回傳一百筆——**五百筆全部進上下文是浪費**。處理方式包括：每個結果只保留前 N 筆並註明總數、對結果做結構化的摘要、或者把完整結果寫到檔案而上下文只放摘要與檔案路徑。

**詳細解析**：「讓模型指定它要什麼」是一個更優雅的解法：在工具的參數中提供 `fields`（只回傳需要的欄位）與 `limit`——於是模型可以在呼叫時就控制回傳量。這比事後裁剪好，因為模型知道自己需要什麼。但要注意它可能不會主動使用這些參數——所以應該在描述中明確建議，或者設定一個保守的預設值（例如 limit 預設 10 而非全部）。「安全的預設值」在這裡特別重要：一個預設回傳全部的工具，只要模型忘了設 limit 就會炸掉上下文——而預設 10 的工具最壞情況只是模型需要多問一次。這個「讓預設行為是安全的」的原則，在整個 Agent 工具設計中都適用。

**面試回答方式**：給框架層裁剪與匯總的三種方式。核心加分點是**讓模型指定它要什麼**（`fields` 與 `limit` 參數）——比事後裁剪好，因為模型知道自己需要什麼，但要注意它可能不主動使用，所以要在描述中建議或設保守的預設值。收在原則：**讓預設行為是安全的**——預設回傳全部的工具只要模型忘了設就會炸掉上下文，而預設 10 的最壞情況只是多問一次。

### 並行會讓除錯變難嗎？

**核心答案**：**會，所以追蹤的設計要跟上**。串行的執行有天然的順序——而並行之後，日誌會交錯，因果關係變得不明顯。處理的方式是「每個呼叫帶上一個 ID 並記錄它屬於哪一個模型回合」，追蹤系統以樹狀而非線性的方式呈現——這與分散式追蹤處理並行 span 的方式完全一樣。

**詳細解析**：「Agent 的追蹤天然就是樹狀的」值得指出：一次使用者請求 → 多個模型回合 → 每個回合多個工具呼叫 → 某些工具內部又呼叫其他服務。用線性的日誌表達這個結構會非常難讀——而用現成的分散式追蹤系統（OpenTelemetry）幾乎完美契合：span 的父子關係正好對應這個層次。所以「不要自己發明 Agent 的追蹤格式，直接用分散式追蹤的標準」是一個省事又正確的選擇。額外的好處是它能與後端服務的追蹤打通——於是「一次 Agent 請求最終在哪個資料庫查詢上慢了」變成一個可以直接查看的問題，而那在自建的日誌格式下幾乎不可能。

**面試回答方式**：承認會變難並給處理方式（呼叫 ID、記錄所屬回合、樹狀呈現），指出這與分散式追蹤處理並行 span 完全一樣。核心加分點是**Agent 的追蹤天然就是樹狀的**——請求、模型回合、工具呼叫、下游服務正好對應 span 的父子關係，所以不要自己發明格式，直接用分散式追蹤的標準。收在額外好處：**能與後端服務的追蹤打通**，於是「一次 Agent 請求最終在哪個資料庫查詢上慢了」變成可以直接查看的問題。
