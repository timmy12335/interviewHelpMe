# 題目

Agent 該怎麼部署？跟一般的 Web 服務有什麼不同？

## 核心答案

三種形態，由「執行時長」與「觸發方式」決定。

**同步請求-回應**——**使用者發起、等待結果**；**適合幾秒到幾十秒的任務**。與一般 API 的差別是「連線要維持很久」——所以需要串流回應與較長的逾時設定，而且不適合放在有嚴格逾時的閘道後面。

**非同步任務**——提交後回傳任務 ID，背景執行，完成時通知；**適合幾分鐘以上的任務**。這本質上就是一個任務佇列加工作者的架構——而 Agent 的特殊性在於「執行時間的變異極大」（同類任務可能相差十倍）與「單一任務可能很貴」。

**常駐或事件驅動**——**Agent 持續運行或被事件喚醒**（收到郵件、偵測到告警、定時觸發）；**這是自動化場景的形態**，而它的關鍵挑戰是「沒有人在看」——所以護欄與預算控制必須更嚴格。

## 詳細解析

「執行時間的變異」是 Agent 部署最特別的一點：一般的 API 請求分布相對集中——而 Agent 的同類任務可能一次三步、一次三十步。這讓容量規劃困難（不能用平均值）、讓逾時設定困難（設短會殺掉正常的長任務，設長則故障的任務佔用資源太久）。實用的處理是「按預算而非時間逾時」：限制步數與成本，而不是掛鐘時間——因為前者更能反映「這個任務是不是失控了」。

「狀態的持久化」在非同步與常駐形態下是必需的：工作者可能重啟、可能被驅逐——而一個跑到一半的 Agent 如果狀態只在記憶體裡，重啟就全部丟失。所以每一步之後應該持久化狀態（至少是輕量的檢查點），讓執行可以在另一個工作者上恢復。這與長時間執行的批次任務是同一個要求。

「常駐 Agent 的護欄要更嚴格」有一個具體的理由：同步場景下使用者在看著——**出問題時他會停止**；而常駐的 Agent 在沒有人監督的情況下運行，一個錯誤可能重複幾百次才被發現。所以必須有：頻率限制、成本上限、異常行為告警、以及一個能立即停用的開關。而「定期向人報告做了什麼」也是必要的——不是等出事才看，而是讓人能定期抽查。

「擴縮容的信號」與一般服務不同：CPU 使用率毫無意義（Agent 大部分時間在等模型回應）——應該用「佇列深度」與「正在執行的任務數」。而擴容的速度也受限於模型 API 的配額——加更多工作者但打到同一個限流上，只會讓每個都變慢。

## 面試回答方式

先給三種形態與各自的適用時長，並指出同步形態與一般 API 的差別（連線要維持很久、需要串流、不適合放在嚴格逾時的閘道後）。加分點有四個：**執行時間的變異極大**——同類任務可能相差十倍，讓容量規劃與逾時設定都困難，實用的處理是按預算而非時間逾時；狀態持久化在非同步與常駐下是必需的——工作者可能重啟，狀態只在記憶體裡就全部丟失；**常駐 Agent 的護欄要更嚴格**——沒有人在看，一個錯誤可能重複幾百次才被發現，所以要有頻率限制、成本上限、異常告警、立即停用的開關、以及定期向人報告；以及擴縮容的信號不是 CPU 而是佇列深度，而擴容速度受限於模型 API 的配額。

## 講稿

有三種形態，由執行時長跟觸發方式決定。同步的請求回應、非同步的任務、還有常駐或事件驅動。

同步形態跟一般介面最大的差別是連線要維持很久，所以需要串流回應跟較長的逾時，而且不適合放在有嚴格逾時的閘道後面。

代理部署最特別的一點是執行時間的變異極大。同類任務可能一次三步、一次三十步。這讓容量規劃困難，不能用平均值，也讓逾時難設，設短會殺掉正常的長任務，設長則故障的任務佔用資源太久。所以我會按預算而不是按時間逾時，限制步數跟成本，因為那更能反映這個任務是不是失控了。

常駐形態的護欄要更嚴格，理由很具體。同步場景下使用者在看著，出問題他會停止。而常駐的代理在沒有人監督的情況下運行，一個錯誤可能重複幾百次才被發現。所以必須有頻率限制、成本上限、異常告警、還有一個能立即停用的開關。

另外擴縮容不能看 CPU，因為代理大部分時間在等模型回應。應該用佇列深度。

## 常見追問

### 一個 Agent 任務要跑一小時，怎麼設計？

**核心答案**：拆成可恢復的階段，而不是一個長交易。每個階段完成後**持久化狀態**——於是失敗只需要重跑最後一個階段而非全部。**同時要有進度的可見性**（讓使用者知道跑到哪了）**與中間結果的可用性**（即使最終失敗，已完成的部分應該是有價值的）。

**詳細解析**：「中間結果要有價值」是長任務設計的一個重要原則：一個跑了 50 分鐘後失敗、什麼都沒留下的任務——**浪費了全部的成本**；而一個每完成一個檔案就寫出結果的任務，即使中途失敗也交付了部分價值。這改變了失敗的性質：從「全部白費」變成「完成了 70%」。實作上這意味著「增量地產出而非最後一次性輸出」——而它同時改善了可觀測性（能看到進展）與可恢復性（知道從哪繼續）。另一個要點是「長任務要有心跳」：定期更新一個「我還活著」的標記——否則系統無法區分「還在跑」與「卡死了」，而那兩者需要完全不同的處理。

**面試回答方式**：給拆階段加持久化的設計。核心加分點是**中間結果要有價值**——跑 50 分鐘後失敗什麼都沒留下浪費全部成本，而增量產出即使失敗也交付了部分價值，這把失敗從「全部白費」變成「完成了 70%」，而且同時改善可觀測性與可恢復性。收在**長任務要有心跳**——否則系統無法區分「還在跑」與「卡死了」，而那兩者需要完全不同的處理。

### 多個使用者的 Agent 怎麼共用資源？

**核心答案**：用佇列加公平調度，而不是讓先來的佔滿。單一使用者的一個複雜任務可能跑幾百步——如果沒有公平性控制，它會餓死其他人的簡單請求。**做法是「按使用者分配配額」**（每個使用者同時最多 N 個任務）**與「加權公平調度」**（長時間佔用資源的使用者優先級下降）。

**詳細解析**：「模型 API 的配額是真正的瓶頸」是這個問題的關鍵背景：你的工作者可以有很多——但打到同一個模型 API 的配額上限就沒用了。所以資源的分配實際上是在分配「模型呼叫的配額」，而它應該在呼叫模型之前就被控制（一個共用的限流器）而非在工作者層面。這也意味著「加工作者」並不總是能提高吞吐——在配額受限的情況下，它只會增加排隊。正確的擴容路徑是先確認瓶頸在哪：是工作者不足、還是配額不足、還是下游工具的限制——而多數團隊在沒有確認的情況下加工作者，然後發現沒有改善。

**面試回答方式**：給佇列加公平調度的做法（按使用者配額、加權公平）並指出單一複雜任務會餓死簡單請求。核心加分點是**模型 API 的配額才是真正的瓶頸**——資源分配實際上是在分配模型呼叫的配額，應該用一個共用的限流器在呼叫前控制。收在診斷：**加工作者並不總是提高吞吐**，**在配額受限時只會增加排隊**，所以要先確認瓶頸是工作者、配額、還是下游工具——而多數團隊沒確認就加工作者然後發現沒有改善。

### Agent 服務怎麼做灰度發布？

**核心答案**：與一般服務類似，但比對的指標不同。可以按使用者比例分流到新舊版本——而觀察的不是錯誤率與延遲（那些可能都正常），而是「任務成功率、平均步數、成本、以及人工介入率」。因為 Agent 的退化往往表現為「還是完成了，但繞了更多路」或「更常需要人幫忙」而非直接報錯。

**詳細解析**：「退化是漸進而非二元的」讓 Agent 的灰度比一般服務更難判斷：一個提示的改動可能讓成功率從 85% 變成 82%——**這在小樣本下完全看不出來**，需要足夠的流量與時間才能有統計顯著性。所以 Agent 的灰度期通常要比一般服務長，而且應該同時搭配離線的評估集（快速回饋）與線上的指標（真實驗證）。另一個實務要點是「同一個使用者應該穩定地分到同一個版本」：否則使用者會在對話中感受到行為的不一致（前一輪與後一輪的風格突然變了）——這比任何指標的退化都更影響體驗。

**面試回答方式**：給分流的做法並指出**觀察的指標不同**（任務成功率、平均步數、成本、人工介入率），理由是Agent 的退化表現為「繞了更多路」或「更常需要人幫忙」而非直接報錯。核心加分點是**退化是漸進而非二元的**——85% 變 82% 在小樣本下看不出來，需要足夠流量與時間，所以灰度期要比一般服務長，並搭配離線評估集快速回饋。收在體驗細節：同一個使用者要穩定分到同一版本，否則會在對話中感受到行為的不一致，那比任何指標退化都更影響體驗。
