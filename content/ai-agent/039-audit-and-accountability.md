# 題目

Agent 做錯事之後，怎麼查清楚發生了什麼、責任在誰？

## 核心答案

**審計記錄必須能回答四個問題**：**誰觸發的**（哪個使用者、什麼請求）、**做了什麼**（每一次工具呼叫的參數與結果）、**為什麼**（模型當時的推理與決策依據）、**以及授權是怎麼來的**（使用者確認了嗎、走了哪條權限路徑）。

**與傳統系統審計的關鍵差異是「為什麼」這一項**：傳統系統的行為由程式碼決定，**看程式碼就知道為什麼**；**而 Agent 的行為由模型當時的判斷決定**——**所以必須記錄「當時的完整上下文與模型的原始輸出」**，**否則行為永遠無法被解釋**。

**責任歸屬上有三個角色**：**使用者**（發起請求、做出確認）、**Agent 的運營方**（設計了工具、權限與護欄）、**以及模型提供者**。**多數情況下責任在運營方**——**因為「模型可能出錯」是一個已知的事實，而設計一個沒有足夠防護的系統是運營方的選擇。**

## 詳細解析

**「記錄推理過程」有一個實務上的張力**：完整記錄每次的上下文與輸出會產生大量資料且可能包含敏感內容——**但沒有它，事後完全無法解釋行為**。**折衷的做法是分級**：**所有的工具呼叫（尤其是寫入類）永久記錄**，**模型的完整上下文保留較短的時間（例如 30 天）並做敏感資訊遮罩**。**而「不可逆操作」的相關上下文應該被完整且長期保留**——**因為那正是最可能需要事後追查的**。

**「確認的記錄」需要包含足夠的細節才有意義**：只記錄「使用者點了同意」是不夠的——**要記錄「當時展示給使用者的是什麼內容」**。**因為爭議的核心往往是「使用者到底看到了什麼才同意的」**——**如果展示的內容有誤導或不完整，那個同意的有效性就有問題**。**這與金融產品的告知義務是同一個道理，而在 Agent 系統中它經常被忽略。**

**「Agent 的行為是不確定的」讓責任歸屬變複雜，但不會消除責任**：不能因為「模型的輸出無法預測」就免責——**正如不能因為「使用者的輸入無法預測」就免除輸入驗證的責任**。**運營方的義務是「在已知模型會出錯的前提下，設計足夠的防護」**——**而防護是否足夠，判準是「這類錯誤是可預見的嗎、有沒有標準的防護手段、有沒有實施」**。

**「可追溯性應該延伸到提示與模型版本」**：一個行為異常可能來自提示的變更或模型的更新——**所以每一次執行都應該記錄「用的是哪個提示版本、哪個模型版本」**。**沒有這個，你無法回答「這個問題是什麼時候開始的、因為什麼變更」**——**而那是事故調查最常需要回答的問題**。

## 面試回答方式

先給審計要能回答的四個問題，並指出**與傳統系統的關鍵差異是「為什麼」這一項**——**傳統系統看程式碼就知道，而 Agent 的行為由模型當時的判斷決定，所以必須記錄完整上下文與原始輸出**。給三個角色與**多數情況責任在運營方**的理由。加分點有四個：**記錄推理過程的張力與分級處理**——**不可逆操作的相關上下文要完整且長期保留**；**確認的記錄要包含「當時展示了什麼」**——**因為爭議的核心是「使用者到底看到什麼才同意的」**，**與金融產品的告知義務同理**；**不確定性不會消除責任**——**正如不能因為使用者輸入無法預測就免除輸入驗證的責任**，並給出「防護是否足夠」的判準；以及**可追溯性要延伸到提示與模型版本**。

## 講稿

審計記錄必須能回答四個問題。誰觸發的、做了什麼、為什麼、還有授權是怎麼來的。

跟傳統系統審計的關鍵差異是為什麼這一項。傳統系統的行為由程式碼決定，看程式碼就知道為什麼。而代理的行為由模型當時的判斷決定，所以必須記錄當時的完整上下文跟模型的原始輸出，否則行為永遠無法被解釋。

責任歸屬上有三個角色，使用者、運營方、還有模型提供者。多數情況責任在運營方，因為模型可能出錯是一個已知的事實，而設計一個沒有足夠防護的系統是運營方的選擇。不能因為模型的輸出無法預測就免責，正如不能因為使用者的輸入無法預測就免除輸入驗證的責任。

還有一個細節很多人忽略。確認的記錄要包含當時展示給使用者的是什麼內容，而不只是記錄他點了同意。因為爭議的核心往往是使用者到底看到了什麼才同意的。如果展示的內容有誤導或不完整，那個同意的有效性就有問題。這跟金融產品的告知義務是同一個道理。

## 常見追問

### 敏感資料進了模型的上下文，審計記錄怎麼處理？

**核心答案**：**記錄時遮罩，但保留足夠的結構讓行為可以被理解**。做法是**在記錄前對已知的敏感欄位（身分證號、卡號、聯絡方式）做遮罩或雜湊**——**保留「這裡有一個客戶的電話」這個事實，但不保留號碼本身**。**同時對審計記錄本身施加嚴格的存取控制與保留期限**。

**詳細解析**：**「遮罩的困難在於模型的輸出是自由文字」**：結構化的欄位容易遮罩——**而模型可能在一段自然語言的推理中提到了敏感資訊**，**那需要內容層的偵測而非欄位層的規則**。**實用的做法是「在資料進入模型之前就做去識別化」**：**用代號取代真實的個資，只在最終輸出時還原**——**於是模型的上下文與所有記錄中都不含真實資料**。**這個做法額外的好處是降低了洩漏的風險（連注入攻擊也拿不到真實資料）**，**代價是需要維護一個代號與真實值的映射**。**在高度敏感的領域（醫療、金融），這個投入通常是值得的**——**而它體現了一個原則：不要讓敏感資料進入你無法完全控制的元件。**

**面試回答方式**：給做法（記錄前遮罩、保留結構、對記錄本身施加存取控制與保留期限）。核心加分點是指出**遮罩的困難在於模型輸出是自由文字**——**需要內容層偵測而非欄位規則**，並給出更好的做法：**在資料進入模型之前就去識別化，用代號取代真實個資、只在最終輸出還原**。收在額外好處與原則：**連注入攻擊也拿不到真實資料**，**體現了「不要讓敏感資料進入你無法完全控制的元件」**。

### 怎麼向非技術的人解釋 Agent 做了什麼？

**核心答案**：**把技術軌跡轉譯成「業務層面的行動摘要」**。不是「呼叫了 `update_order` 工具，參數是 {...}」——**而是「將訂單 12345 的狀態從『處理中』改為『已取消』，依據是使用者在 14:32 的取消請求」**。**這個轉譯應該是系統自動產生的，而不是每次由人去解讀原始日誌。**

**詳細解析**：**「面向業務的審計視圖」有兩個獨立的價值**：**對外**——**客服、法務、稽核人員能自己查清楚發生了什麼，不需要工程師介入**；**對內**——**它強迫你把「每個工具呼叫對業務的意義」明確定義出來**，**而那個定義本身有助於發現設計問題**（**如果一個工具的業務意義說不清楚，那個工具的設計可能就有問題**）。**實作上可以在工具的定義中加上一個「業務描述範本」欄位**——**把技術參數填入範本產生人類可讀的描述**。**成本很低而價值持續**：**每一次爭議、每一次稽核、每一次事故調查都會用到它**。

**面試回答方式**：給核心做法（**轉譯成業務層面的行動摘要，而且是系統自動產生**）並給出前後對比的例子。核心加分點是指出它的**兩個獨立價值**：對外讓非工程師能自查、**對內強迫你定義每個工具對業務的意義，而那個定義本身有助於發現設計問題**（說不清楚業務意義的工具設計可能有問題）。收在低成本的實作：**在工具定義中加一個業務描述範本欄位**，**成本低而每次爭議、稽核、事故調查都會用到**。

### 合規要求（例如金融、醫療）對 Agent 有什麼特殊限制？

**核心答案**：**三類典型要求**。**可解釋性**——**必須能說明「為什麼做出這個決定」**，**而模型的推理不總是可靠的解釋**（**它給出的理由未必是真正的原因**）。**人工複核**——**高風險決定必須有人參與，Agent 只能提出建議**。**資料留存與駐留**——**記錄要保存特定年限，資料不能離開特定地域**。

**詳細解析**：**「模型給的理由未必是真正的原因」是可解釋性要求下最棘手的問題**：模型可以流暢地解釋它的答案——**但那個解釋是事後生成的合理化，未必反映實際的計算過程**。**所以在需要嚴格可解釋性的場景，正確的做法不是「讓模型解釋自己」，而是「把決策拆成可審查的步驟」**：**用模型做資訊抽取與初步分類，用明確的規則做最終決定**——**於是決定的依據是規則（完全可解釋），而模型只負責它擅長的部分**。**這個架構同時滿足了合規與能力的需求**，**而它比「試圖讓模型的解釋變得可信」務實得多**。**在高度監管的領域，這往往是唯一可行的落地方式。**

**面試回答方式**：給三類要求並指出**模型的推理不總是可靠的解釋**。核心加分點是展開**「模型給的理由未必是真正的原因」**——**解釋是事後生成的合理化，未必反映實際計算過程**，並給出正確的架構：**把決策拆成可審查的步驟，模型做抽取與初步分類、明確的規則做最終決定**，**於是依據是規則（完全可解釋）而模型只負責它擅長的部分**。收在判斷：**這比「試圖讓模型的解釋變得可信」務實得多，在高度監管的領域往往是唯一可行的落地方式**。
