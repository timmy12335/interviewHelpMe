# 題目

一個客服 Agent 從 demo 到上線，最難的是什麼？

## 核心答案

**demo 與生產的差距主要在三處，而它們都不是模型能力問題。**

**知識的完整性與正確性**——**demo 用幾份精選的文檔，生產要面對散落各處、互相矛盾、且部分過時的真實知識庫**。**這往往是最大的工作量，而且需要業務方參與。**

**長尾的請求**——**demo 測的是典型問題，而真實流量中有大量「模糊的、多意圖的、情緒化的、或者根本不屬於這個系統範圍的」請求**。

**與既有流程的整合**——**Agent 不是孤立的**：**它要能查工單系統、能建立工單、能轉接人工、能在人工接手後交接上下文**。**這些整合的工作量通常超過 Agent 本身。**

**而最重要的落地決定是「自主性的邊界」**：**哪些問題 Agent 可以直接回答、哪些必須轉人工**——**這條線畫錯了，要嘛品質不可接受，要嘛人力沒有節省。**

## 詳細解析

**「轉人工的設計比回答的品質更決定成敗」**：一個能處理 60% 問題並乾淨地轉出其餘 40% 的系統是成功的——**而一個試圖處理 100% 但在其中 20% 上給出錯誤答案的系統是失敗的**。**因為錯誤的答案造成的損害（客訴、錯誤的操作、信任流失）遠大於「無法回答」的成本**。**所以設計時應該從「哪些問題我有信心處理好」開始，而不是從「盡量多處理一些」開始**。

**「轉人工的交接品質」是體驗的關鍵**：**如果使用者要對人工再說一遍所有的事，那個轉接就是負體驗**。**正確的做法是把對話摘要、已確認的資訊、以及 Agent 的判斷一起交給客服人員**——**於是人工可以直接接續而非從頭開始**。**這個交接的品質，往往決定了使用者對整個系統的評價**。

**「知識庫的品質問題會被 Agent 暴露」**：同一個政策在三份文檔裡有三種說法——**人類客服會憑經驗判斷，而 Agent 只會照著檢索到的回答**。**所以 RAG 專案的一部分實際工作是「整理知識庫」**，**而那需要業務方的投入且無法由技術團隊單獨完成**——**這是專案排期時最容易被低估的一項**。

**「效果的量測要看業務指標」**：不是「回答的準確率」，而是**「首次解決率、平均處理時間、轉人工率、以及客戶滿意度」**。**而最有說服力的比較是「與人工客服的基準對照」**——**因為人工也不是 100% 正確的，而合理的目標是「在可接受的品質下降低成本或提升速度」而非「完美」**。

## 面試回答方式

先指出**demo 與生產的差距不是模型能力問題**並給三處（知識完整性、長尾請求、既有流程整合）。給最重要的落地決定——**自主性的邊界**。加分點有四個：**轉人工的設計比回答品質更決定成敗**——**處理 60% 並乾淨轉出其餘的系統是成功的，而試圖處理 100% 但在 20% 上出錯是失敗的**，**因為錯誤答案的損害遠大於無法回答的成本**；**轉人工的交接品質是體驗關鍵**——**要使用者再說一遍就是負體驗**；**知識庫的品質問題會被 Agent 暴露**——**整理知識庫需要業務方投入，是排期時最容易被低估的一項**；以及**效果要看業務指標並與人工基準對照**——**人工也不是 100% 正確的**。

## 講稿

從展示到上線的差距主要在三處，而它們都不是模型能力問題。知識的完整性與正確性、長尾的請求、還有跟既有流程的整合。

而最重要的落地決定是自主性的邊界。哪些問題代理可以直接回答、哪些必須轉人工。這條線畫錯了，要嘛品質不可接受，要嘛人力沒有節省。

我認為轉人工的設計比回答的品質更決定成敗。一個能處理六成問題並乾淨地轉出其餘四成的系統是成功的。而一個試圖處理全部但在其中兩成上給出錯誤答案的系統是失敗的。因為錯誤答案造成的損害，客訴、錯誤的操作、信任流失，遠大於無法回答的成本。所以設計應該從哪些問題我有信心處理好開始，而不是從盡量多處理一些開始。

還有一個容易被低估的工作量。知識庫的品質問題會被代理暴露。同一個政策在三份文檔裡有三種說法，人類客服會憑經驗判斷，而代理只會照著檢索到的回答。所以整理知識庫是專案的一部分，而它需要業務方投入，無法由技術團隊單獨完成。

## 常見追問

### 怎麼決定「哪些問題該轉人工」？

**核心答案**：**三個維度共同判斷**。**信心**——**檢索的相關性低、或者模型自己表示不確定**。**風險**——**涉及金額、承諾、或者不可逆操作的問題**。**情緒**——**使用者明顯不滿或要求真人**（**這時強留在 Agent 只會惡化**）。**而規則應該偏保守：不確定就轉，而不是勉強嘗試。**

**詳細解析**：**「使用者要求真人時應該立即轉接」是一條不該被優化掉的規則**：有些系統為了降低人力成本而設計了多層的挽留——**而那會顯著惡化體驗並最終增加客訴**。**正確的做法是尊重這個請求，同時把已有的對話交接過去**（**於是那段對話不算浪費**）。**至於信心的判斷**：**與其依賴模型自我評估（不可靠），不如用可觀測的信號**——**檢索的最高相關性分數、答案是否有出處支撐、以及是否需要多輪澄清**。**這些是外部的、可量測的，比模型說「我不確定」可靠得多**。**而「多輪澄清仍然沒有進展」是一個特別好的轉接訊號**——**它同時反映了問題的複雜度與使用者的耐心消耗**。

**面試回答方式**：給三個維度並主張**規則應該偏保守**。核心加分點是**使用者要求真人時應該立即轉接**——**多層挽留會顯著惡化體驗並最終增加客訴**，**正確做法是尊重請求並交接已有對話**。第二個是**信心的判斷應該用可觀測的外部信號**（檢索相關性分數、是否有出處、是否需要多輪澄清）**而非模型的自我評估**，並指出**「多輪澄清仍無進展」是特別好的轉接訊號，因為它同時反映問題複雜度與使用者的耐心消耗**。

### 怎麼從人工客服的歷史中學習？

**核心答案**：**三種用法**。**建立評估集**——**真實的對話加上人工給出的正確回應，是最好的測試案例**。**發現知識缺口**——**分析人工經常被問到但知識庫裡沒有的問題**。**以及微調的資料來源**——**經過篩選的優質對話可以用於教模型正確的語氣與處理方式**。

**詳細解析**：**「歷史對話是最有價值也最容易被忽略的資產」**：它包含了真實的問題分布（而非你想像的）、真實的表達方式（口語、錯字、多意圖）、以及經驗豐富的客服的處理方式。**用它來建立評估集，比人工構造測試案例貼近現實得多**。**但要注意兩件事**：**去識別化**（歷史對話包含大量個資，必須處理後才能使用）**與品質篩選**（**不是所有人工的回應都是好的**——**要用滿意度、是否二次來電、或者人工複核來篩選**）。**而最實用的第一步往往是「統計問題的分布」**：**找出佔了 80% 流量的那 20 類問題，先把它們做好**——**這比追求覆蓋所有情況有效得多，也讓專案能更快展現價值**。

**面試回答方式**：給三種用法。核心加分點是**歷史對話是最有價值也最容易被忽略的資產**——**它包含真實的問題分布、真實的表達方式、以及有經驗的客服的處理方式**，**用它建立評估集比人工構造貼近現實得多**，並提醒**去識別化與品質篩選**（不是所有人工回應都是好的）。收在最實用的第一步：**統計問題分布，找出佔 80% 流量的那 20 類先做好**——**比追求覆蓋所有情況有效，也讓專案更快展現價值**。

### 業務流程類的 Agent（例如自動處理申請）有什麼不同？

**核心答案**：**它有明確的狀態機與合規要求，所以「確定性的部分應該用工作流引擎而非交給模型」**。Agent 負責的是**理解非結構化的輸入**（申請書、附件、郵件內容）**與判斷模糊的情況**；**而流程的推進、狀態的轉換、審批的路由應該由既有的流程引擎控制**——**因為那些必須是確定且可審計的**。

**詳細解析**：**「把 Agent 放進工作流而非用 Agent 取代工作流」是這類場景的核心架構判斷**：工作流引擎提供了狀態管理、重試、超時、審批鏈、審計記錄——**這些都是成熟且可靠的能力**；**而 Agent 提供的是「處理非結構化資訊」這個工作流引擎做不到的部分**。**兩者結合比任何一方單獨都好**。**反過來，用 Agent 自由地推進整個流程會失去確定性與可審計性**——**而那在受監管的業務中是不可接受的**。**另一個實務要點是「先自動化最容易的那一段」**：**一個流程有十個步驟，可能只有兩個適合自動化**——**先做那兩個，量測節省了多少，再決定要不要繼續**。**這比追求端到端的全自動化務實得多，也更容易獲得業務方的支持。**

**面試回答方式**：給核心判斷——**確定性的部分用工作流引擎，Agent 負責理解非結構化輸入與判斷模糊情況**。核心加分點是**把 Agent 放進工作流而非用 Agent 取代工作流**——**工作流引擎提供狀態管理、重試、審批鏈、審計，而 Agent 提供處理非結構化資訊的能力，兩者結合比任何一方單獨都好**，並指出**用 Agent 自由推進整個流程會失去確定性與可審計性，在受監管的業務中不可接受**。收在**先自動化最容易的那一段並量測節省**。
