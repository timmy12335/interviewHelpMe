# 題目

公司的核心系統沒有好的 API，Agent 要怎麼接？

## 核心答案

**按可靠性排序有四種接法。**

**既有的 API**——**最理想，但通常需要一層門面把它轉換成適合模型使用的形式**（**內部 API 的粒度與命名往往不適合直接暴露**）。

**資料庫直讀**——**繞過應用層直接查詢**；**快且簡單，但失去了應用層的業務邏輯與權限控制**——**所以應該限於唯讀，且要自己實作權限過濾**。

**RPA 或介面自動化**——**模擬人類操作介面**；**適用於完全沒有程式介面的系統**，**但脆弱（介面一改就壞）、慢、且難以測試**。

**批次檔案交換**——**很多老系統只支援定時的檔案匯入匯出**；**可靠但延遲高，只適合非即時的場景。**

**而不論用哪一種，都應該在中間加一層「為 Agent 設計的介面」**——**而不是讓模型直接面對原始系統的複雜度。**

## 詳細解析

**「門面層是必要的投入而非額外的工作」**：內部系統的 API 是給程式用的——**參數命名晦澀、需要多次呼叫才能完成一件事、錯誤訊息是內部的狀態碼**。**直接暴露給模型的結果是它用不好也修正不了**。**而一個門面層能做四件事**：**把多次呼叫合併成一個有語義的操作**、**把內部術語轉換成業務語言**、**把回應精簡成模型需要的部分**、**以及把錯誤轉換成可行動的指引**。**這一層的工作量通常被低估，但它決定了整個整合的品質。**

**「唯讀先行」是降低風險的標準策略**：先讓 Agent 只能查詢——**驗證它理解得對、用得好、沒有安全問題**；**確認之後再逐步開放寫入**。**這既降低了初期的風險，也讓團隊有時間建立信心與經驗**。**而寫入的開放也應該是漸進的**：**先開放可逆的、影響小的操作，最後才是不可逆的**。

**「介面自動化的脆弱性」需要被明確承認**：頁面改版、元素的位置變化、彈出的提示框——**任何一個都可能讓自動化失敗**。**所以如果選擇這條路，必須有完善的錯誤偵測與告警**，**而且要接受持續的維護成本**。**近年的視覺型 Agent（能看畫面並操作）讓它比傳統的選擇器式 RPA 更有韌性**——**但仍然遠不如 API 可靠**。

**「不要為了接 Agent 而繞過既有的業務規則」**：直接寫資料庫繞過應用層的校驗——**看起來省事，但那些校驗存在是有原因的**。**繞過它們的後果是資料不一致，而那類問題往往在幾週後才顯現且極難追查**。**如果既有系統確實沒有可用的寫入介面，那應該推動補上一個，而不是繞過去。**

## 面試回答方式

先按可靠性給四種接法與各自的取捨，並強調**都應該在中間加一層為 Agent 設計的介面**。加分點有四個：**門面層是必要的投入**——**內部 API 的參數晦澀、需要多次呼叫、錯誤是內部狀態碼**，**而門面能合併呼叫、轉換術語、精簡回應、轉換錯誤**，**這一層的工作量常被低估但決定整合品質**；**唯讀先行是標準策略**，**寫入的開放也應該從可逆的、影響小的開始**；**介面自動化的脆弱性要明確承認**，**視覺型 Agent 比選擇器式 RPA 有韌性但仍遠不如 API**；以及**不要為了接 Agent 而繞過既有的業務規則**——**那類資料不一致往往幾週後才顯現且極難追查**。

## 講稿

按可靠性排序有四種接法。既有的介面、資料庫直讀、介面自動化、還有批次檔案交換。

但不論用哪一種，都應該在中間加一層為代理設計的介面，而不是讓模型直接面對原始系統的複雜度。

這個門面層是必要的投入而不是額外的工作。內部系統的介面是給程式用的，參數命名晦澀、需要多次呼叫才能完成一件事、錯誤訊息是內部狀態碼。直接暴露給模型的結果是它用不好也修正不了。門面層能做四件事，把多次呼叫合併成一個有語義的操作、把內部術語轉成業務語言、把回應精簡、把錯誤轉成可行動的指引。這一層的工作量通常被低估，但它決定了整個整合的品質。

策略上我會唯讀先行。先讓代理只能查詢，驗證它理解得對、用得好、沒有安全問題，確認之後再逐步開放寫入。而寫入也是漸進的，先開放可逆的、影響小的，最後才是不可逆的。

還有一條原則，不要為了接代理而繞過既有的業務規則。直接寫資料庫繞過應用層校驗看起來省事，但那些校驗存在是有原因的。

## 常見追問

### 舊系統的回應太慢，Agent 每步都要等怎麼辦？

**核心答案**：**三個手段**。**快取**——**不常變的資料在門面層快取**。**批次化**——**把多個查詢合併成一次呼叫**（如果舊系統支援）。**非同步化**——**把慢的操作改成「提交加輪詢」，讓 Agent 不必阻塞等待**。**如果都做不到，那就要在產品層面調整預期**（明確告知使用者這個操作需要時間）。

**詳細解析**：**「在門面層加快取」對舊系統整合特別有效**：因為舊系統往往沒有自己的快取層，**而它服務的資料很多是變化緩慢的**（產品目錄、組織架構、政策設定）。**在門面層加一個幾分鐘的快取，可能就把大部分查詢的延遲從幾秒降到毫秒**——**而且它同時降低了舊系統的負載，這對本來就吃緊的老系統是額外的好處**。**另一個實用的做法是「預熱」**：**在對話開始時就把常用的上下文（使用者資料、當前狀態）取回來**——**於是後續的步驟不用再等**。**這與 Agent 的思考時間重疊，實際上是免費的。** **而如果舊系統慢到連預熱都來不及，那應該考慮「資料同步」**：**把需要的資料定期同步到一個快速的儲存，Agent 讀那個副本**——**代價是資料的即時性，但對很多場景可以接受。**

**面試回答方式**：給三個手段並指出**做不到時要在產品層面調整預期**。核心加分點是**在門面層加快取對舊系統特別有效**——**舊系統往往沒有快取層而它的資料多是變化緩慢的**，**幾分鐘的快取能把延遲從幾秒降到毫秒且同時降低舊系統負載**。收在兩個進階做法：**預熱**（與思考時間重疊，實際上免費）與**資料同步到快速儲存**（代價是即時性但很多場景可接受）。

### 沒有測試環境怎麼開發與驗證？

**核心答案**：**用模擬（mock）建立一個假的環境**。錄製真實系統的回應——**然後用它建立一個能重放的模擬服務**；**開發與測試都跑在這個模擬上**。**而在真實環境的驗證則限制在「唯讀操作」與「一個受控的測試帳號」**。

**詳細解析**：**「從真實流量錄製而非手寫模擬」是關鍵**：手寫的模擬回應往往過於理想化——**而真實系統的回應包含各種意外（不一致的格式、缺失的欄位、奇怪的錯誤碼）**，**而那些正是 Agent 容易出錯的地方**。**錄製的做法是「在門面層加一個記錄模式」**——**把每次真實呼叫的請求與回應存下來，再用它們構建模擬**。**這個投入很小而回報很大**：**它同時給了你模擬環境、回歸測試的素材、以及真實行為的文件**。**而在完全沒有測試環境的情況下，「唯讀先行」的策略價值更高**——**因為唯讀操作即使在生產環境執行也不會造成損害，於是可以直接驗證**。

**面試回答方式**：給模擬環境的做法與真實環境驗證的限制。核心加分點是**從真實流量錄製而非手寫模擬**——**手寫的過於理想化，而真實回應包含不一致的格式、缺失欄位、奇怪的錯誤碼，那正是容易出錯的地方**，並給出實作（**在門面層加記錄模式**）。收在回報：**同時給了你模擬環境、回歸測試素材、與真實行為的文件**，**而在沒有測試環境時「唯讀先行」的價值更高，因為唯讀即使在生產執行也不會造成損害**。

### 整合的優先順序怎麼排？

**核心答案**：**按「使用頻率乘以整合難度的倒數」排**——**先做高頻且容易接的**。這通常意味著：**先接查詢類的（唯讀、風險低、頻率高），再接簡單的寫入，最後才是複雜的流程操作**。**而每接一個就量測「它被用了多少次、成功率如何」**——**用實際的使用數據決定下一個接什麼**。

**詳細解析**：**「不要一次接十個系統」是這裡最重要的建議**：每個整合都有持續的維護成本（介面變更、錯誤處理、監控）——**而如果十個裡只有三個真的常被使用，另外七個就是純粹的負擔**。**正確的做法是「接一個、驗證價值、再接下一個」**。**而判斷價值的依據應該是實際的使用數據而非事前的猜測**——**因為使用者實際會問什麼，往往與產品經理設想的不同**。**一個實用的做法是「先讓 Agent 在沒有某個整合的情況下運行，記錄它有多少次表示需要那個資料」**——**這個數字直接告訴你那個整合值不值得做**，**而它比任何需求訪談都準確**。

**面試回答方式**：給排序原則（**使用頻率乘以整合難度的倒數，先做高頻且容易接的**）與典型順序。核心加分點是**不要一次接十個系統**——**每個整合都有持續的維護成本，十個裡只有三個常用的話另外七個是純粹的負擔**。收在一個實用的判斷方法：**先讓 Agent 在沒有某個整合的情況下運行，記錄它有多少次表示需要那個資料**——**這個數字直接告訴你值不值得做，而它比任何需求訪談都準確**。
