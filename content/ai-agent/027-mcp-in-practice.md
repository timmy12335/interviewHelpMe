# 題目

實際要為公司的內部系統寫一個 MCP 伺服器，該注意什麼？

## 核心答案

MCP 提供的三種原語各有適用場景，先選對。**Tools**——模型可以主動呼叫的動作（查詢、寫入）。**Resources**——**可以被讀取的內容**（文件、資料），由客戶端決定要不要載入，不是模型主動呼叫的。**Prompts**——預先定義的提示範本，通常由使用者主動觸發。把所有東西都做成 tool 是最常見的設計錯誤——大量靜態內容應該是 resource，讓客戶端管理載入時機。

**設計上的四個要點**。工具的粒度要對應「一個有意義的操作」而非直接映射內部 API。**權限必須在伺服器端強制**——不能假設客戶端會正確地限制。**回傳要精簡並適合模型消費**——**內部 API 的原始回應通常太冗長**。**錯誤要是自然語言的指引**而非狀態碼。

**部署上要決定「本地還是遠端」**：本地（stdio）簡單、天然繼承使用者的權限；遠端（HTTP）方便多人共用，但必須自己處理認證與租戶隔離。

## 詳細解析

「不要把內部 API 一對一包裝成工具」是最重要的一條。內部 API 的設計是給程式用的——它可能需要三次呼叫才能完成一件事，或者接受十五個參數。直接包裝的結果是模型必須理解你的內部模型，而它不會。正確的做法是「按使用者的意圖設計工具」：`get_customer_summary(customer_id)` 在內部可能呼叫了四個 API 並組合結果——但對模型而言它是一個乾淨的、語義明確的操作。這個「為 Agent 設計專用的門面層」的投入，是決定 MCP 伺服器好不好用的最大因素。

「權限在伺服器端強制」有一個具體的含義：MCP 伺服器不應該有一個超級權限的資料庫連線然後靠提示限制模型——它應該以「當前使用者的身份」執行操作。在本地 stdio 模式下這比較自然（行程繼承使用者權限）；而遠端模式必須傳遞並驗證使用者身份，並在每次操作時檢查該使用者是否有權限。沒有這一層，一次提示注入就等於完整的資料外洩。

**「危險操作要有確認機制」**：MCP 的規範支援標記工具的行為特性（是否有副作用、是否破壞性）——而客戶端可以據此決定要不要要求使用者確認。**但不要只依賴客戶端**：真正危險的操作（刪除、轉帳、對外發送）應該在伺服器端也要求一個明確的確認參數或二次呼叫，因為你不知道客戶端會怎麼實作。

「可觀測性」在 MCP 伺服器上常被忽略：記錄每一次工具呼叫的參數、結果、耗時與呼叫者——這既是除錯的基礎，也是安全審計的要求。而且它讓你能回答「這個工具實際被怎麼使用」，從而改善描述與粒度。

## 面試回答方式

先給三種原語的區分並指出把所有東西都做成 tool 是最常見的設計錯誤。給四個設計要點與部署形態的選擇。加分點有四個：**不要把內部 API 一對一包裝**——內部 API 是給程式用的，直接包裝會逼模型理解你的內部模型，正確做法是按使用者意圖設計工具，內部可以組合多個 API，而這個門面層的投入是決定好不好用的最大因素；權限要在伺服器端以當前使用者的身份執行——不能有超級權限連線然後靠提示限制，否則一次提示注入就等於完整的資料外洩；危險操作在伺服器端也要求確認，因為你不知道客戶端會怎麼實作；以及可觀測性讓你能回答「這個工具實際被怎麼使用」，從而改善描述與粒度。

## 講稿

我會先選對原語。工具是模型可以主動呼叫的動作，資源是可以被讀取的內容由客戶端決定載入時機，提示範本則通常由使用者觸發。把所有東西都做成工具是最常見的設計錯誤，大量靜態內容應該是資源。

設計上最重要的一條是不要把內部介面一對一包裝成工具。內部介面是給程式用的，可能需要三次呼叫才完成一件事，或者接受十五個參數。直接包裝的結果是模型必須理解你的內部模型，而它不會。正確的做法是按使用者的意圖設計，一個看起來簡單的工具在內部可能呼叫了四個介面並組合結果。這個為代理設計專用門面層的投入，是決定好不好用的最大因素。

第二個要點是權限必須在伺服器端以當前使用者的身份強制。不能有一個超級權限的連線然後靠提示限制模型。沒有這一層，一次提示注入就等於完整的資料外洩。

還有危險操作在伺服器端也要求確認，因為你不知道客戶端會怎麼實作。

## 常見追問

### MCP 與直接寫 function calling 有什麼差別？

**核心答案**：差別在「標準化與可重用」而非能力。直接寫 function calling——工具定義綁在你的應用程式碼裡，換一個框架或客戶端就要重寫。MCP 把工具做成一個獨立的伺服器行程——任何支援 MCP 的客戶端都能用，而工具的維護與應用的開發解耦。在只有一個應用、幾個工具的情況下，直接寫更簡單；而在「多個應用要共用一組工具」或「希望工具能被不同的客戶端使用」時，MCP 的價值才顯現。

**詳細解析**：「解耦」的實際好處在組織層面最明顯：擁有某個系統的團隊可以自己維護那個系統的 MCP 伺服器——而不需要修改每一個要用它的 Agent 應用。這與微服務的「誰擁有資料誰提供介面」是同一個結構。**成本是多了一層行程與協定**（啟動、連線管理、錯誤傳播都變複雜）。所以判斷與微服務拆分類似：先問「有幾個消費者、由誰維護」——單一應用單一團隊的情況下，直接寫函式是更務實的選擇，而 MCP 的收益隨消費者數量與團隊分工的複雜度成長。

**面試回答方式**：明確指出差別在標準化與可重用而非能力，並給兩種情況的適用判斷。核心加分點是解耦的好處在組織層面最明顯——擁有系統的團隊自己維護那個 MCP 伺服器，不需要改每一個 Agent 應用，與微服務「誰擁有資料誰提供介面」是同一個結構。收在判斷方式：**先問有幾個消費者、由誰維護**，單一應用單一團隊時直接寫函式更務實。

### 遠端 MCP 伺服器的安全該怎麼做？

**核心答案**：**四層**。**認證**——**驗證呼叫方的身份**（OAuth 或等價機制），並把「使用者身份」與「客戶端身份」分開。**授權**——每次工具呼叫都檢查該使用者是否有權限，而不是在連線建立時檢查一次。**輸入驗證**——模型產生的參數是不可信輸入，必須驗證（**它可能被注入操縱**）。**審計**——記錄誰在什麼時候呼叫了什麼。

**詳細解析**：「模型產生的參數是不可信輸入」這一點常被忽略卻至關重要：開發者容易把它當成「來自我們自己的應用」——但實際上那些參數的內容可能受外部內容影響（間接提示注入）。所以 MCP 伺服器應該用對待外部 API 的標準來對待這些參數：參數化查詢、路徑檢查、範圍限制——而不是因為「呼叫方是我們的 Agent」就放鬆。另一個要點是「不要在工具回傳中夾帶敏感資料」：回傳會進入模型的上下文，而上下文可能被洩漏——所以只回傳完成任務所必需的欄位，內部 ID、其他使用者的資料、以及憑證都不應該出現在回傳裡。

**面試回答方式**：給四層安全（認證、每次呼叫的授權、輸入驗證、審計）並強調授權要每次檢查而非連線時檢查一次。核心加分點是模型產生的參數是不可信輸入——它們的內容可能受外部內容影響，所以要用對待外部 API 的標準對待，而不是因為呼叫方是自己的 Agent 就放鬆。收在**不要在回傳中夾帶敏感資料**——回傳會進入上下文而上下文可能被洩漏，所以只回傳完成任務所必需的欄位。

### 工具很多時 MCP 怎麼組織？

**核心答案**：按領域拆成多個伺服器，而不是一個大伺服器。每個伺服器對應一個系統或一個領域（訂單、客戶、庫存）——這讓權限、部署、維護的責任都與那個領域的擁有者對齊。客戶端可以選擇性地連接需要的伺服器——於是「當前對話暴露哪些工具」變成一個可配置的決定。

**詳細解析**：「按需連接」是控制工具數量的一個天然機制：一個處理訂單問題的對話不需要連接人資系統的伺服器——於是那些工具的描述不佔用上下文，模型也不會誤用它們。實作上可以由使用者選擇、由路由邏輯決定、或者由一個前置的分類步驟判斷。而更根本的建議是「不要因為技術上可以就把所有系統都接上」：每接一個系統，都增加了上下文佔用、選錯的機率、以及攻擊面——而多數 Agent 應用實際只需要三到五個系統。「先做好一個領域再擴展」比「一次接十個系統但每個都用得半調子」有價值得多，而這個判斷在 Agent 專案中經常被急於展示能力的心態壓過。

**面試回答方式**：主張**按領域拆成多個伺服器**並說明這讓權限、部署、維護的責任與領域擁有者對齊。加分點是按需連接是控制工具數量的天然機制——處理訂單的對話不需要連人資系統，那些工具就不佔上下文也不會被誤用。核心加分點是判斷：不要因為技術上可以就把所有系統都接上——每接一個都增加上下文佔用、選錯機率與攻擊面，而「先做好一個領域再擴展」比「一次接十個但每個都半調子」有價值得多。
