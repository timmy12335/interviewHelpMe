# 題目

Agent 回應太慢，怎麼分析與優化？

## 核心答案

先拆解時間的組成，因為優化的方向完全取決於瓶頸在哪。

**四個來源**。**模型推理**——**每一輪的 prefill 加 decode**；通常佔大頭，而且與上下文長度、輸出長度直接相關。**工具執行**——**下游 API、資料庫、外部服務的延遲**。**輪次數量**——**Agent 需要幾輪才能完成**；這往往是最大的槓桿，因為它是乘數。**框架開銷**——**序列化、狀態持久化、日誌**；通常最小但不該被忽略。

優化的順序應該是「先減少輪數，再減少每輪的成本」——因為把十輪變成五輪的收益，遠大於把每輪快 20%。

**而減少輪數的手段包括**：**並行不相依的工具呼叫**、**讓工具的粒度更合適**（一個工具做完一件完整的事，而非需要三次呼叫）、以及更好的提示讓模型少走冤枉路。

## 詳細解析

「輪次是乘數」這一點決定了優化的優先順序：如果一輪要 3 秒——**十輪就是 30 秒**。把每輪優化到 2.5 秒只省 5 秒；而把輪數降到 6 輪省 12 秒。所以第一個要問的問題永遠是「這個任務真的需要這麼多輪嗎」——**而答案往往是否定的**：工具粒度太細（三次呼叫才拿到需要的資料）、提示不清導致試錯、或者沒有並行。

「上下文長度直接影響每輪的 prefill 時間」：隨著對話進行，上下文越來越長，每一輪的 prefill 都要重新處理它——於是後面的輪次比前面慢得多。提示快取能大幅緩解這個問題（固定前綴不重複計算），而上下文管理（壓縮、外部化）能從根本上減少要處理的量。這是「上下文管理同時是品質、成本、與延遲問題」的具體體現。

**「輸出長度的影響常被低估」**：decode 是逐 token 的——**輸出 500 個 token 比 100 個慢五倍**。而 Agent 的中間步驟往往包含大量不必要的輸出（**複述問題、解釋自己要做什麼**）。在提示中要求簡潔的中間輸出，能直接縮短每一輪的時間——而這幾乎沒有代價，因為那些鋪陳對結果沒有貢獻。

「感知延遲的優化」與實際延遲同等重要：串流輸出、即時的進度更新、以及「先返回部分結果」——都能讓相同的實際延遲感覺短很多。在無法進一步壓縮實際時間時，這往往是收益最高的投入。

## 面試回答方式

先拆解四個時間來源並指出優化順序是先減少輪數再減少每輪成本。加分點有四個：**輪次是乘數**——一輪 3 秒的話，把每輪優化到 2.5 秒只省 5 秒，而把十輪降到六輪省 12 秒，所以第一個問題永遠是「真的需要這麼多輪嗎」，並給常見原因（工具粒度太細、提示不清導致試錯、沒有並行）；**上下文長度直接影響每輪的 prefill**——**後面的輪次比前面慢得多**，而這是「上下文管理同時是品質、成本與延遲問題」的體現；**輸出長度的影響常被低估**——中間步驟的鋪陳對結果沒有貢獻，要求簡潔幾乎沒有代價；以及感知延遲的優化在無法壓縮實際時間時往往收益最高。

## 講稿

我會先拆解時間的組成，因為優化方向完全取決於瓶頸在哪。有四個來源，模型推理、工具執行、輪次數量、還有框架開銷。

優化的順序應該是先減少輪數，再減少每輪的成本。因為輪次是乘數。如果一輪要三秒，十輪就是三十秒。把每輪優化到兩秒半只省五秒，而把輪數降到六輪省十二秒。

所以第一個要問的問題永遠是這個任務真的需要這麼多輪嗎。答案往往是否定的。常見原因是工具粒度太細，三次呼叫才拿到需要的資料，或者提示不清導致試錯，或者沒有並行。

還有上下文長度會讓後面的輪次越來越慢，提示快取能大幅緩解。

## 常見追問

### 怎麼量測 Agent 的延遲組成？

**核心答案**：**用分散式追蹤，每一層都有 span**：整個請求 → 每一輪模型呼叫 → 每一次工具呼叫 → 工具內部的下游呼叫。於是「時間花在哪」可以直接從火焰圖上看出來，**而不需要靠猜**。關鍵指標包括：總延遲、輪數、每輪的模型時間、每輪的工具時間、以及首個輸出的時間。

**詳細解析**：「分開統計模型時間與工具時間」是診斷的第一步，而它常常帶來意外的發現：團隊以為是模型慢——**而實際上是某個下游 API 的 p99 很差**。或者反過來，以為是外部服務的問題，實際上是上下文太長導致 prefill 變慢。沒有分層的量測，這兩者無法區分。另一個實用的維度是「按輪次序號統計」：如果第五輪之後的延遲明顯上升，那幾乎確定是上下文長度的問題——這個模式一眼就能從資料中看出來，而如果只有平均值則完全看不到。這類「按維度切分才能看見的模式」，正是為什麼聚合指標不足以支撐效能診斷。

**面試回答方式**：給分散式追蹤的分層設計與關鍵指標。核心加分點是分開統計模型時間與工具時間常常帶來意外發現——以為是模型慢實際是下游 p99 差，或者反過來是上下文太長讓 prefill 變慢，沒有分層量測這兩者無法區分。收在**按輪次序號統計**：第五輪後延遲明顯上升幾乎確定是上下文長度問題，這個模式一眼可見而只有平均值則完全看不到。

### 用小模型能減少延遲嗎？

**核心答案**：能，但要考慮「它可能需要更多輪」。小模型的每輪推理快得多——但如果它更容易選錯工具、更常需要重試、或者無法一次規劃好而要多次試探，總輪數上升可能抵銷甚至超過每輪的節省。所以評估必須看端到端的總時間而非單輪的速度。

**詳細解析**：「按步驟分派不同大小的模型」是更好的做法：簡單的步驟（格式化、分類、抽取）用小模型，複雜的判斷（規劃、處理異常）用大模型——於是既保住了品質，又在多數步驟上獲得速度。實作上這需要框架支援「每次呼叫可以指定模型」，而多數框架都支援。判斷哪些步驟可以降級的方法是「實測」：把某一類步驟換成小模型，跑評估集看端到端指標是否下降——而通常會發現相當多的步驟可以降級。這個優化同時降低了延遲與成本，是投入產出比很高的一項，卻因為「一個 Agent 用一個模型」的預設思維而經常被忽略。

**面試回答方式**：回答能但要考慮**它可能需要更多輪**，並強調評估必須看端到端總時間而非單輪速度。核心加分點是**按步驟分派不同大小的模型**——簡單步驟用小模型、複雜判斷用大模型，既保住品質又在多數步驟獲得速度，並給出判斷方法（實測某類步驟降級後端到端指標是否下降）。收在：這同時降低延遲與成本，投入產出比很高，卻因為「一個 Agent 用一個模型」的預設思維而經常被忽略。

### 工具很慢的時候怎麼辦？

**核心答案**：**四個方向**。**並行**——**不相依的呼叫同時發**。**快取**——**重複的查詢直接回傳**。**預取**——在模型還在思考時就把很可能需要的資料取回來。**以及改造下游**——如果一個工具需要三次內部呼叫，把它們在工具內部並行或合併。

**詳細解析**：「預取」在 Agent 中比在一般系統中更可行，因為有明顯的思考時間：模型產生一輪回應可能要幾秒——**而在那期間下游是閒置的**。如果能預測「接下來很可能需要查使用者資料」，就在那幾秒裡把它取回來——等模型真的要用時已經在快取裡了。預測可以很簡單：根據當前的任務類型預取一組常用的資料。判斷划算與否的標準是「預取的成本乘以未命中率」與「節省的延遲」的比較——在下游便宜的情況下幾乎總是划算。而更根本的做法是重新設計工具的粒度：如果模型總是連續呼叫 A 然後 B，那就提供一個同時做兩件事的工具——這既省了一輪模型推理，也省了一次往返。「觀察實際的呼叫序列並據此設計工具」是一個持續改善的循環，而它需要的資料正是追蹤系統已經記錄的。

**面試回答方式**：給四個方向。核心加分點是預取在 Agent 中比一般系統更可行，因為有明顯的思考時間——模型產生回應的幾秒裡下游是閒置的，並給簡單的預測方式與划算與否的判斷標準。收在更根本的做法：觀察實際的呼叫序列並據此設計工具粒度——模型總是連續呼叫 A 然後 B 的話就提供一個做兩件事的工具，**既省一輪推理也省一次往返**，而這需要的資料正是追蹤系統已經記錄的。
