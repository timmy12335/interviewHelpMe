# 題目

什麼是「Plan-and-Execute」這種 Agent 架構模式？它具體是如何運作的？相較於前面（見 [[002-react-pattern.md]]）深入討論過的 ReAct 模式，它適合用於哪一類特定性質的任務？

## 核心答案

Plan-and-Execute 是一種 Agent 架構模式，它的核心做法是把**「規劃」和「執行」明確地拆分成兩個各自獨立的階段**——**規劃階段**：在任務一開始先運用大型語言模型針對這個整體任務進行前面（見 [[003-planning-task-decomposition.md]]）已經深入討論過的任務分解（Task Decomposition），**一次性地**產出一份**完整的、涵蓋所有必要子步驟的行動計畫**；**執行階段**：依照這份已經規劃好的完整計畫**依序地**去執行計畫裡的每一個子步驟，通常還會額外地加入一個**「重新規劃（Re-planning）」的機制**——如果在執行過程中發現某個子步驟的實際結果和原本規劃時的預期有明顯落差，或者遇到了原本規劃時沒有預料到的意外狀況，就會**觸發重新地回到規劃階段**，依照這個最新的實際狀況**調整、修正**接下來的行動計畫。相較於 ReAct 那種**每執行完一個行動就立即重新思考、決定緊接著唯一的下一步**的**細顆粒度、緊密交錯**的運作方式，Plan-and-Execute **特別適合**用於那些**任務本身具備相對穩定、可以被事先想清楚的整體結構，且需要同時兼顧、協調許多彼此環環相扣的子任務**這類情境（這正是前面（見 [[002-react-pattern.md]]）的常見追問裡已經深入討論過的『結構性複雜』這類任務）——因為 Plan-and-Execute 一開始就先建立一個**對整個任務完整的全局規劃視野**，讓 Agent 在執行任何一個具體的子步驟時都能清楚地知道這個子步驟在整個任務藍圖裡所扮演的角色和定位，這是**單純的 ReAct 那種只聚焦在緊接著下一步的思考模式**相對較難天然具備的優勢。

## 詳細解析

**Plan-and-Execute 的優勢——全局視野帶來的執行效率和一致性**：Plan-and-Execute 最核心的優勢來自於它**在執行任何具體步驟之前，就已經具備一個對整個任務的完整規劃視野**——這種**全局視野**帶來幾個具體的效益——**(1) 能夠識別出彼此不互相依賴、可以被平行執行的子任務**——這呼應了前面（見 [[../ai-llm/022-function-calling.md]]）已經討論過的『多工具協同呼叫情境裡識別平行處理機會』這個議題，因為 Plan-and-Execute 一開始就具備對所有子任務及其依賴關係的完整視野，它能夠**主動地識別出**哪些子任務可以被**同時、平行地執行**（而不需要像 ReAct 那樣因為每次只聚焦在單一個緊接著的下一步，而較難天然發現這種可以平行處理的機會），帶來**整體執行效率的提升**；**(2) 能夠確保不同子步驟之間的行動彼此一致、不互相矛盾**——因為所有的子步驟都是依照**同一份一次性產出的完整規劃**所衍生出來的，這某種程度上確保了這些子步驟彼此之間具備**內在的一致性**（相較之下，ReAct 那種每一步都是**依照最新的局部觀察**獨立地重新決定下一步，理論上存在較高的機率讓某幾個相隔較遠的步驟之間出現某種程度的不一致或自相矛盾）。

**重新規劃（Re-planning）機制——讓 Plan-and-Execute 也能具備一定程度的動態調整能力**：Plan-and-Execute 雖然核心精神是**先規劃、再執行**，但一個成熟的 Plan-and-Execute 實作**並不會**天真地假設一開始制定的規劃永遠都完全正確、不需要任何調整，而是會額外地加入**「重新規劃」**這個機制——這個機制某種程度上是**把前面（見 [[003-planning-task-decomposition.md]]）已經深入討論過的『Agent 發現規劃遭遇障礙應該如何因應』**這個核心議題**具體地內建進 Plan-and-Execute 這個架構模式的標準運作流程裡**——具體來說，Plan-and-Execute 的執行階段通常會在**每執行完一個子步驟**之後額外地檢查這個子步驟的實際結果是否**顯著地偏離原本規劃時的預期**，如果發現這種顯著的偏離（例如某個原本假設存在的關鍵資訊實際上並不存在），就會**觸發重新回到規劃階段**，依照這個最新的實際情況**重新產出一份修正過的行動計畫**。這種「規劃－執行－（必要時）重新規劃」的循環機制，讓 Plan-and-Execute 這種架構在**保有全局規劃視野**這個核心優勢的同時，也能夠**具備一定程度的、應對實際執行過程中意外狀況的動態調整能力**，而不是一個一旦制定就僵固不變的死板流程。

**Plan-and-Execute 的核心侷限——初始規劃的品質對整體任務成敗的決定性影響**：Plan-and-Execute 這種**高度依賴一開始規劃階段的品質**的架構模式，也存在一個需要被仔細考量的侷限——**如果最初規劃階段所產出的行動計畫本身就存在嚴重的疏漏、或是建立在錯誤的前提假設之上**，這種**規劃階段本身的失誤**很可能會**連帶地影響整個後續執行階段的表現品質**（即使有前面已經討論的『重新規劃』機制作為一定程度的補救，但如果最初的規劃**偏離實際情況太過嚴重**，可能需要經過**多次反覆的重新規劃**才能逐漸修正回到一個真正合理的執行路徑，這某種程度上會抵銷掉一部分 Plan-and-Execute 原本希望透過**一開始就把全局規劃想清楚**所帶來的效率優勢）。這種**「初始規劃品質對整體表現的決定性影響」**也呼應了前面（見 [[003-planning-task-decomposition.md]]）已經深入討論過的**規劃審查機制**這個緩解手段的重要性——在 Plan-and-Execute 架構裡**在正式進入執行階段之前，額外地對這份初始規劃進行批判性的審查**這件事，某種程度上比在 ReAct 那種**每一步規劃粒度本身就相對較小**的架構裡更加**具備關鍵性的價值**（因為 Plan-and-Execute 的『規劃』是一次性地涵蓋**整個任務**的完整藍圖，這一份規劃本身的品質某種程度上承擔了比 ReAct 裡任何單一次局部思考更大的責任和影響範圍）。

## 面試回答方式

先給出Plan-and-Execute的核心運作方式——「把規劃和執行明確拆分成兩個各自獨立的階段，規劃階段一開始就一次性運用大型語言模型，針對整體任務進行任務分解，產出一份完整涵蓋所有必要子步驟的行動計畫;執行階段則依序執行計畫裡的每個子步驟，通常還會額外加入重新規劃機制，如果發現某個子步驟的實際結果和原本預期有明顯落差，就觸發重新回到規劃階段，依照最新實際狀況調整修正接下來的計畫」。清楚說明和ReAct的適用情境差異——「相較於ReAct那種每執行完一個行動就立即重新思考緊接著下一步的細顆粒度緊密交錯模式，Plan-and-Execute特別適合任務本身具備相對穩定、可以被事先想清楚整體結構，且需要同時兼顧協調許多環環相扣子任務的情境，因為它一開始就具備對整個任務完整的全局規劃視野」。可以補充全局視野帶來的具體效益——「能夠識別出彼此不互相依賴、可以平行執行的子任務以提升效率;也能確保不同子步驟之間的行動彼此一致不互相矛盾，因為所有步驟都源自同一份完整規劃」。一定要誠實補充核心侷限——「這種高度依賴初始規劃品質的架構，如果最初規劃階段本身就存在嚴重疏漏或建立在錯誤前提之上，會連帶影響整個後續執行階段的表現，即使有重新規劃機制作為補救，可能仍需經過多次反覆才能修正回合理路徑，這也是為什麼在正式執行前對初始規劃做批判性審查，在Plan-and-Execute架構裡更具關鍵價值」，展現你對Plan-and-Execute的運作機制、適用情境、以及核心侷限有完整且平衡的理解。

## 常見追問

### 有沒有可能把 ReAct 和 Plan-and-Execute 這兩種架構模式結合在一起使用，而不是只能二選一？

**核心答案**：**完全可以，而且實務上這種混合式的架構相當常見**——一種典型的混合做法是**在較高的層次採用 Plan-and-Execute 的思路**——先針對整體任務進行一次性的高層次規劃，拆解成幾個主要的子任務；但**在執行每一個具體子任務的內部**則**改用 ReAct 這種細顆粒度、緊密交錯的思考－行動循環**去實際地完成這個具體子任務（因為即使整體任務的高層次結構相對穩定、可以被事先規劃好，**每一個具體子任務內部實際執行的細節**依然可能存在**高度依賴即時回饋、事先難以完全預先規劃**的不確定性，這種細節層次的不確定性正是 ReAct 擅長應對的情境）。這種**「高層次用 Plan-and-Execute 建立全局結構；低層次用 ReAct 靈活應對執行細節」**的混合模式，某種程度上兼顧了**兩種架構各自的核心優勢**，同時緩解了各自單獨使用時所存在的侷限。

**詳細解析**：這題考察是否能夠避免把 ReAct 和 Plan-and-Execute 看成一種**互斥、只能二選一**的競爭關係，而能夠看出這兩種架構模式其實是**分別擅長處理不同層次的問題**，因此**完全可以被恰當地組合、混合使用**。理解這種混合式思路的核心在於回顧前面（見 [[002-react-pattern.md]] 的常見追問）已經建立的核心認知——**「一個任務是否複雜」和「這個任務適合用哪一種架構」，關鍵取決於這個任務（或者這個任務底下的某一個具體子任務）的執行路徑本身的性質**——是**可以被事先相對穩定、完整地想清楚的結構性複雜**，還是**執行路徑本身高度依賴即時回饋、事先難以完全被規劃**的不確定性複雜。而一個**真實世界裡的複雜任務**往往並不是**單純地只屬於這兩種性質其中一種**，而是**同時具備這兩種不同性質的層面**——舉例來說，一個『撰寫一份完整的市場分析報告』這樣的整體任務，它的**高層次結構**（需要先蒐集資料、再分析資料、再撰寫初稿、再審閱修改這幾個主要的階段）相對是**穩定、可以被事先規劃好**的（適合用 Plan-and-Execute 的高層次規劃思路去處理）；但其中**每一個具體子任務的內部**（例如『蒐集資料』這個子任務內部具體要查詢哪些資料來源、依照查到的初步結果決定接下來要再額外查詢哪些補充資訊）卻可能**高度依賴即時查詢結果的回饋，事先難以被完全精確地預先規劃**（這反而更適合用 ReAct 這種緊密依照即時觀察動態調整的思路去處理）。這種**「整體任務的高層次架構，和每個子任務的內部執行細節，可能分別適合用不同架構模式」**的現實情況，正是驅動實務上**混合式架構**變得相當普遍、且具備實際價值的核心原因——透過**在不同的層次各自套用最適合那個層次性質的架構模式**，能夠讓整個 Agent 系統同時享有 **Plan-and-Execute 的全局規劃優勢**以及 **ReAct 的細節層次靈活應對能力**，而不需要被迫在這兩種各自都只適合處理一部分面向的架構模式之間做出一個**削足適履的二選一取捨**。理解「完全可以結合使用，實務上這種混合式架構相當常見，一種典型做法是在較高層次採用Plan-and-Execute的思路先進行一次性高層次規劃，拆解成幾個主要子任務，但在執行每個具體子任務的內部則改用ReAct這種緊密交錯的思考行動循環，因為即使整體任務高層次結構相對穩定，每個具體子任務內部實際執行的細節依然可能存在高度依賴即時回饋、事先難以完全預先規劃的不確定性，這種高層次用Plan-and-Execute建立全局結構、低層次用ReAct靈活應對執行細節的混合模式，兼顧了兩種架構各自的核心優勢，同時緩解各自單獨使用時存在的侷限，這反映了一個真實世界的複雜任務往往同時具備結構性複雜和不確定性複雜這兩種不同性質的層面，不需要被迫在只適合處理一部分面向的架構模式之間做出削足適履的二選一取捨」，展現你不僅理解兩種架構各自的特性，還能看出它們可以在不同層次上互補組合，展現更高階的架構設計視野。

**面試回答方式**：先明確給出核心答案——「完全可以，而且實務上這種混合式架構相當常見」。給出具體的混合做法——「一種典型做法是在較高層次採用Plan-and-Execute的思路，先針對整體任務進行一次性高層次規劃，拆解成幾個主要子任務;但在執行每個具體子任務的內部，則改用ReAct這種細顆粒度、緊密交錯的思考-行動循環，因為即使整體任務的高層次結構相對穩定，每個具體子任務內部實際執行的細節依然可能高度依賴即時回饋、事先難以完全規劃，這正是ReAct擅長應對的情境」。用具體例子幫助理解——「例如撰寫一份市場分析報告，高層次結構(蒐集資料、分析、撰寫初稿、審閱修改)相對穩定適合用Plan-and-Execute處理，但蒐集資料這個子任務內部具體查詢哪些來源、依照查到結果決定接下來查詢什麼，卻更適合用ReAct處理」。給出結論——「這種混合模式兼顧了兩種架構各自的核心優勢，不需要被迫在只適合處理一部分面向的架構模式之間做削足適履的二選一取捨」。

### Plan-and-Execute 裡的「重新規劃」機制，如果被觸發得太過頻繁（幾乎每執行完一個步驟就要重新規劃一次），這是不是代表這個架構模式其實已經退化成和 ReAct 差不多了？

**核心答案**：**某種程度上確實可以這樣理解**——如果「重新規劃」這個機制被觸發得**極度頻繁**（幾乎每執行完一個步驟就因為發現實際結果和預期有落差而觸發重新規劃），這某種程度上**確實意味著**這個系統實際上**已經喪失了 Plan-and-Execute 原本最核心的優勢——『一開始就具備一個相對穩定、值得信賴的全局規劃』**，因為如果這份一開始的規劃**幾乎每一步都需要被重新調整**，這就意味著這份規劃本身其實**並沒有真正發揮它原本應該提供的『穩定全局視野』這個功能**。在這種極端情況下，這個系統的實際運作方式確實某種程度上**退化成和 ReAct 那種『每一步都重新依照最新情況決定接下來怎麼做』相當類似**。這某種程度上也是一個值得被留意的**信號**——如果一個採用 Plan-and-Execute 架構的系統發現**重新規劃被觸發的頻率持續地居高不下**，這某種程度上暗示著這一類的任務**本質上可能並不真正適合用 Plan-and-Execute 這種架構**（因為它的執行路徑可能本質上就是前面（見 [[002-react-pattern.md]]）已經討論過的『高度依賴即時回饋、事先難以完整規劃』這種性質），也許改用**單純的 ReAct**（或者前一題討論的混合式架構）反而會是一個更恰當、更誠實地反映這一類任務實際性質的架構選擇。

**詳細解析**：這題要求對「重新規劃機制被觸發的頻率」這件事做更細緻的**量化思考**，考察是否能夠**把一個抽象的架構概念轉化成一個可以被實際觀察、監控的具體指標**，並依照這個具體指標做出恰當的架構調整判斷，而不是只是停留在**『Plan-and-Execute 和 ReAct 是兩種不同架構』**這個抽象層次的理解。理解這個問題的核心在於認識到——**「重新規劃被觸發的頻率」**本身可以被理解成一個**衡量『這個任務的執行路徑實際上有多不確定、難以事先規劃』**的具體、可以被量化觀測的**代理指標（Proxy Metric）**——如果一個任務**確實具備前面已經反覆強調的『結構性複雜』**這種性質（執行路徑本身相對穩定、可以被事先想清楚），那一開始制定的規劃理論上**應該能夠相對順利地被依序執行完成**，只需要**在少數特殊、確實遭遇意外狀況**的情況下才需要觸發重新規劃；但如果實際觀察到的情況是**重新規劃幾乎每一步都被觸發**，這某種程度上是一個**強而有力的實證訊號**，顯示**這一類任務實際上可能並不真正具備最初被假設的那種『結構性複雜、可以被事先規劃好』的性質**，而是**本質上更接近前面（見 [[002-react-pattern.md]]）已經討論過的『不確定性複雜』**這種性質（執行路徑本身高度依賴即時回饋，事先難以被完整規劃）。這種情況下繼續堅持採用 Plan-and-Execute 這種**核心價值主張（『一開始建立穩定的全局規劃』）**實際上並**不成立**的架構，某種程度上只是在**用一種表面上看起來更有結構、但實際上已經名不符實**的方式，去模擬一個其實更適合用 ReAct 那種**誠實地承認『每一步都需要依照最新情況重新決定』**這個現實的架構來處理的任務。因此**「觀察重新規劃被觸發的實際頻率」**某種程度上可以被當作一個**實務上用來驗證、校準『這個任務究竟更適合用哪一種架構模式』這個先前判斷是否正確**的具體、可操作的檢驗方法——如果實際運作的資料顯示重新規劃的頻率遠高於預期，這就是一個**應該重新審視是否選錯了架構模式**的明確警訊。理解「如果重新規劃機制被觸發得極度頻繁，某種程度上確實意味著這個系統已經喪失Plan-and-Execute原本最核心的優勢——一開始就具備一個相對穩定值得信賴的全局規劃，這種情況下系統的實際運作方式確實退化成和ReAct相當類似，這也是一個值得留意的信號——重新規劃被觸發的頻率本身可以被理解成衡量這個任務執行路徑實際上有多不確定難以事先規劃的具體量化代理指標，如果實際觀察到重新規劃幾乎每一步都被觸發，這是一個強而有力的實證訊號，顯示這類任務實際上可能並不真正具備最初被假設的結構性複雜性質，而是本質上更接近不確定性複雜這種性質，這種情況下繼續堅持採用Plan-and-Execute實際上只是用一種表面上看起來更有結構、但實際上已經名不符實的方式，去模擬一個其實更適合用ReAct處理的任務，因此觀察重新規劃被觸發的實際頻率，可以被當作一個實務上用來驗證校準這個任務究竟更適合用哪種架構模式的具體可操作檢驗方法」，展現你能把一個抽象的架構選擇問題，轉化成一個可以被實際觀察監控的量化指標，並依照這個指標做出動態的架構調整判斷。

**面試回答方式**：先給出核心答案——「某種程度上確實可以這樣理解，如果重新規劃機制被觸發得極度頻繁，確實意味著這個系統已經喪失Plan-and-Execute原本最核心的優勢，實際運作方式確實退化成和ReAct相當類似」。給出這個現象背後的解讀——「重新規劃被觸發的頻率，本身可以被理解成衡量這個任務執行路徑實際上有多不確定、難以事先規劃的具體量化指標，如果重新規劃幾乎每一步都被觸發，這是一個強而有力的訊號，顯示這類任務本質上可能更接近不確定性複雜，而非最初被假設的結構性複雜」。給出實務建議——「這種情況下繼續堅持Plan-and-Execute，只是用一種表面上看起來更有結構、但實際已名不符實的方式，去模擬一個其實更適合用ReAct或混合式架構處理的任務，觀察重新規劃的實際觸發頻率，可以被當作驗證校準架構選擇是否正確的具體檢驗方法」。

### 在 Plan-and-Execute 架構裡，「規劃」這個階段和「執行」這個階段，是不是一定要由同一個模型來擔任？可不可以讓不同的模型分別負責這兩個階段？

**核心答案**：**完全可以讓不同的模型分別負責這兩個階段，而且這某種程度上是一種相當合理、且可能帶來額外效益的架構選擇**——**規劃**這個階段所需要的核心能力是**對整體任務的高層次理解，以及較強的邏輯推理和規劃能力**，這某種程度上**適合交給一個推理能力較強、但可能成本較高、回應速度較慢的『旗艦級』模型**來負責；而**執行**階段所需要的則是**依照已經規劃好的明確步驟去實際執行具體的行動**（這某種程度上是一個相對較不需要高深推理能力的任務，只需要正確地依照指示行事即可），這某種程度上**適合交給一個成本較低、回應速度較快的『輕量級』模型**來負責。這種**「用較強、成本較高的模型負責規劃；用較輕量、成本較低的模型負責執行」**的分工方式，能夠在**維持整體規劃品質**的同時**顯著地降低整體的運算成本**（因為『執行』這個階段通常會涉及**遠比『規劃』階段更多次的模型呼叫**，如果每一次執行的呼叫都使用昂貴的旗艦模型，累積起來的成本會相當可觀）。

**詳細解析**：這題把 Plan-and-Execute 這個架構和**模型選型／成本優化**這個實務上相當重要的工程考量結合起來，考察是否能夠看出 **Plan-and-Execute 這種把規劃和執行明確拆分成兩個獨立階段**的架構特性，某種程度上也**天然地創造了一個可以針對這兩個不同階段各自做出恰當的『模型選型』決策**的機會，而不是只能用**單一個模型**去同時兼顧處理這兩個階段。理解這個問題的核心在於回顧這個系列反覆強調的核心分析框架——**釐清不同的環節各自具體需要的能力和特性是什麼**——**規劃**階段需要模型具備**理解整個任務的完整意圖、識別出需要被拆解的子任務，以及正確地梳理出這些子任務之間的依賴關係**這類**較需要深度推理和理解**的能力，這種能力通常**和模型本身的規模以及訓練的精細程度有較密切的正相關**（這呼應了前面（見 [[../ai-llm/017-scaling-laws.md]]）已經深入討論過的 Scaling Laws 核心概念）；而**執行**階段一旦有了一份明確、清楚的行動計畫，**每一個具體步驟的執行**本身通常**相對直接**（例如依照計畫指示呼叫某個特定工具、把取得的結果做格式上的簡單整理），這種相對較直接的任務即使交給一個**規模較小、成本較低的模型**去執行，通常也能達到**足夠好的表現水準**（這某種程度上呼應了前面（見 [[../ai-llm/024-model-distillation.md]]）已經討論過的核心概念——一個規模較小的模型即使能力上限不如規模龐大的模型，但對於**性質相對直接、不需要太複雜推理**的具體任務依然能夠勝任）。這種**依照每一個環節實際所需要的能力水準去選用恰當規模、恰當成本的模型**，而不是**一律用同一個（通常是能力最強、但也最昂貴）的模型**去處理所有環節，某種程度上也呼應了一個在**設計任何涉及多個不同性質環節的系統時**都值得被反覆套用的核心工程原則——**「不需要用處理最困難情況所需要的最高規格資源去處理每一個環節，而是應該依照每一個具體環節實際的需求做恰如其分的資源配置」**。這種**「規劃用旗艦模型、執行用輕量模型」**的分工方式，正是這個核心原則在 Plan-and-Execute 這個具體架構裡的一個自然延伸應用。理解「完全可以讓不同模型分別負責這兩個階段，規劃階段需要對整體任務的高層次理解和較強的邏輯推理規劃能力，適合交給一個推理能力較強但成本較高的旗艦級模型;執行階段只需要依照已規劃好的明確步驟實際執行具體行動，相對不需要高深推理能力，適合交給一個成本較低、回應速度較快的輕量級模型，這種分工方式能在維持整體規劃品質的同時顯著降低整體運算成本，因為執行階段通常涉及遠比規劃階段更多次的模型呼叫，這呼應了設計任何涉及多個不同性質環節的系統時，不需要用處理最困難情況所需要的最高規格資源去處理每一個環節，而應該依照每個具體環節實際需求做恰如其分資源配置的核心工程原則」，展現你能把Plan-and-Execute架構和模型選型成本優化這個實務工程考量結合起來，看出架構特性天然創造的優化機會。

**面試回答方式**：先給出核心答案——「完全可以，而且這是一種相當合理、可能帶來額外效益的架構選擇」。解釋兩個階段各自適合的模型特性——「規劃階段需要對整體任務的高層次理解和較強邏輯推理規劃能力，適合交給推理能力較強但成本較高的旗艦級模型;執行階段只需要依照已規劃好的明確步驟實際執行，相對不需要高深推理能力，適合交給成本較低、回應速度較快的輕量級模型」。給出這種分工的效益——「這種分工方式能在維持整體規劃品質的同時，顯著降低整體運算成本，因為執行階段通常涉及遠比規劃階段更多次的模型呼叫，如果每次執行呼叫都用昂貴的旗艦模型，累積成本會相當可觀」。可以總結一個更普遍的工程原則——「這呼應了設計任何涉及多個不同性質環節的系統時，不需要用處理最困難情況所需要的最高規格資源去處理每個環節，而應該依照每個環節實際需求做恰如其分的資源配置」。
