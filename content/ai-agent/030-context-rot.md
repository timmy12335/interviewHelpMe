# 題目

Agent 跑了幾十輪之後行為變差了，可能是什麼原因？

## 核心答案

這是一組被稱為「上下文腐化」的現象，而它有四個常見的成因。

**錯誤的累積與強化**——上下文裡的一個早期錯誤（誤讀的資料、失敗的假設）會被後續每一步引用，於是錯誤被不斷強化而不是被修正。

**指令被稀釋**——系統提示的相對權重隨上下文變長而下降，**模型逐漸偏離最初的約束**。

**中間遺失**——**長上下文中段的資訊被忽略**，**於是關鍵的中期發現「消失」了**。

**模式固著**——如果模型連續三次用同一種方式失敗，它傾向於繼續用那種方式（因為上下文中充滿了那個模式）；**這是無限迴圈最常見的成因**。

共同的處理是「不要讓上下文無限累積」：定期整理成結構化的狀態、明確標記已知錯誤、以及在偵測到重複模式時主動中斷並重新規劃。

## 詳細解析

「錯誤會被強化而非修正」是最需要防範的一種：模型讀取上下文時，過去自己的輸出與外部的事實有著相似的地位——於是一個早期的誤判被當成既定事實使用。緩解的做法是「明確地標記錯誤」：當一個假設被證偽時，不要只是繼續下一步，而要在上下文中明確寫下「先前的假設 X 是錯的，正確的是 Y」——**讓修正比原始錯誤更顯著**。而更徹底的做法是「在整理上下文時把已證偽的內容移除」，因為留著它們只會增加被誤用的機率。

「模式固著導致的迴圈」有一個實用的偵測方法：檢查最近 N 步的工具呼叫，如果出現重複的（相同工具加相同參數）就是警訊。偵測到之後不應該只是「再試一次」——那會延續同一個模式；**正確的處理是強制改變策略**：注入一段明確的提示（「你已經嘗試過 X 三次都失敗，請換一個完全不同的方法，或者說明為什麼無法完成」），**或者直接中斷並交給人。**

「越長越糟」不總是成立，但「越長越貴」總是成立：即使品質沒有明顯下降，每一步的成本都隨上下文長度上升——一個跑了五十輪的 Agent，後面幾輪的單步成本可能是前面的十倍。所以上下文管理不只是品質問題，也是成本問題；而這兩個理由加起來，讓「主動控制上下文長度」成為一個沒有爭議的實踐。

**「重新開始有時是最好的處理」**：當上下文已經充滿了失敗的嘗試與混亂的狀態——帶著一份乾淨的任務摘要重新開始，往往比繼續在污染的上下文中掙扎更有效。這與「重啟一個狀態異常的行程」是同一個判斷，而它在 Agent 上經常被忽略。

## 面試回答方式

先給四個成因（錯誤累積與強化、指令稀釋、中間遺失、模式固著）與共同的處理方向。加分點有四個：**錯誤會被強化而非修正**——過去自己的輸出與外部事實在上下文中地位相似，緩解是明確標記「先前的假設是錯的」讓修正比原始錯誤更顯著，或者在整理時直接移除已證偽的內容；**模式固著的偵測方法**——檢查最近 N 步是否有相同工具加相同參數的重複，偵測到之後要強制改變策略而不是再試一次；**「越長越貴」總是成立**——跑了五十輪之後單步成本可能是前面的十倍，所以上下文管理同時是品質與成本問題；以及**重新開始有時是最好的處理**，與重啟一個狀態異常的行程是同一個判斷。

## 講稿

這是一組被稱為上下文腐化的現象，我認為有四個常見成因。

第一是錯誤的累積與強化。上下文裡的一個早期錯誤會被後續每一步引用，於是它被不斷強化而不是被修正。原因是模型讀取上下文時，過去自己的輸出跟外部的事實有著相似的地位。所以緩解的做法是明確標記錯誤，當一個假設被證偽時要寫下先前的假設是錯的、正確的是什麼，讓修正比原始錯誤更顯著。

第二是指令被稀釋，系統提示的相對權重隨上下文變長而下降。第三是中間遺失。

第四是模式固著。如果模型連續三次用同一種方式失敗，它傾向於繼續用那種方式，因為上下文裡充滿了那個模式。這是無限迴圈最常見的成因。偵測的方法很實用，檢查最近幾步的工具呼叫有沒有相同工具加相同參數的重複。偵測到之後不該只是再試一次，那會延續同一個模式，正確的處理是強制改變策略或者交給人。

還有一點，即使品質沒有明顯下降，越長越貴總是成立的。所以主動控制上下文長度沒有爭議。

## 常見追問

### 怎麼在不丟失進度的前提下「重新開始」？

**核心答案**：產生一份結構化的交接摘要，然後用它啟動一個新的上下文。摘要應該包含：原始目標、已完成並驗證的步驟、已知的失敗路徑（避免重蹈）、當前的狀態、以及下一步的建議。**關鍵是「已知的失敗路徑」**——沒有它，新的上下文會重複犯同樣的錯。

**詳細解析**：「交接摘要」的品質決定了重啟的價值，而它不應該由模型自由發揮：用一個固定的 schema 強制它填寫每個欄位——自由文字的摘要容易遺漏關鍵項（尤其是失敗路徑，模型傾向於不提自己的失敗）。這與人類的工作交接完全一樣：有範本的交接比口頭說明可靠得多。 另一個實用的做法是「在整個執行過程中持續維護這份摘要」而非在重啟時才生成——因為那時上下文已經腐化，生成的摘要品質也會受影響。持續維護的摘要既是重啟的基礎，也是給人看的進度報告——一份資料兩個用途，成本攤薄了。

**面試回答方式**：給交接摘要應包含的五項並強調「已知的失敗路徑」是關鍵，沒有它新上下文會重複犯錯。核心加分點是摘要不應該由模型自由發揮，要用固定 schema 強制填寫——自由文字容易遺漏失敗路徑，因為模型傾向於不提自己的失敗，這與人類的工作交接一樣，有範本比口頭說明可靠。收在**持續維護而非重啟時才生成**——那時上下文已腐化，而持續維護的摘要同時是給人看的進度報告。

### 怎麼判斷「該重新開始」而不是繼續？

**核心答案**：**三個訊號**。**重複**——最近幾步在重複同樣的嘗試。**倒退**——**已經完成的部分被破壞了**（例如改壞了之前修好的東西）。**發散**——Agent 在做與原始目標關聯越來越弱的事。加上一個硬性的界線：步數或成本超過預算。

**詳細解析**：「發散」最難自動偵測卻最常發生：Agent 從「修一個 bug」逐漸變成「重構整個模組」——每一步看起來都合理，但整體已經遠離了原始請求。偵測的方法是「定期用原始目標檢查當前行動」：用一個獨立的判斷（另一次模型呼叫或一個規則）問「當前這一步對原始目標有直接貢獻嗎」——**這相當於一個外部的監督者**。而更根本的預防是「在一開始就明確界定範圍」：告訴 Agent「只修這個 bug，不要重構、不要改其他檔案」——明確的邊界比事後的糾正有效得多。這與給人類工程師派任務是完全一樣的道理：模糊的任務描述會得到發散的結果。

**面試回答方式**：給三個訊號加一個硬性界線。核心加分點是發散最難自動偵測卻最常發生——每一步看起來合理但整體已遠離原始請求，並給偵測方法（用獨立的判斷定期問「當前這一步對原始目標有直接貢獻嗎」，相當於一個外部監督者）。收在預防：**在一開始就明確界定範圍**，明確的邊界比事後糾正有效得多——與給人類工程師派任務是一樣的道理。

### 這些問題會隨模型變強而消失嗎？

**核心答案**：**部分會，但不會完全消失**。更強的模型確實更能維持長上下文中的一致性、更少陷入模式固著——但「上下文有限」與「錯誤會被引用」這兩個結構性事實不會改變。所以上下文管理會從「必須做否則不能用」變成「做了會更好更便宜」——**它的必要性下降，但價值仍在**。

**詳細解析**：「成本」是這個問題中最不會被模型能力解決的部分：即使模型能完美處理 100 萬 token 的上下文——每一步都處理那麼多內容仍然是昂貴且慢的。所以「只把必要的內容放進上下文」永遠是有價值的優化，就像「只查詢需要的欄位」在資料庫變快之後仍然是好實踐。另一個不會消失的是「可觀測性」的需求：一個累積了幾百輪的上下文，人類無法審查——而結構化的狀態摘要讓人能理解 Agent 在做什麼。這個價值與模型能力完全無關。所以我的判斷是：上下文管理的技術細節會演變，但「明確地決定上下文包含什麼」這個工程實踐會一直有價值。

**面試回答方式**：給平衡的回答——**部分會但不會完全消失**，並指出「上下文有限」與「錯誤會被引用」是結構性事實。核心加分點是成本是最不會被模型能力解決的部分——即使能完美處理百萬 token，每步都處理那麼多仍然昂貴且慢，就像「只查需要的欄位」在資料庫變快之後仍然是好實踐。收在另一個不變的價值：**可觀測性**——幾百輪的上下文人類無法審查，而結構化摘要讓人能理解 Agent 在做什麼，這與模型能力完全無關。
