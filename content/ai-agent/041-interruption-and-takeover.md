# 題目

使用者在 Agent 執行到一半時想修正方向，系統該怎麼處理？

## 核心答案

**三種介入的形態，複雜度遞增。**

**停止**——**最簡單，但要處理「已完成的操作不會被撤銷」這個語義**，**並展示已經做了什麼**。

**追加指示**——**使用者在執行中補充或修正**（「等等，只處理今年的訂單」）；**技術上是在下一輪把新訊息插入上下文**，**難點是「已經基於舊理解做的事怎麼辦」**——**需要讓 Agent 明確地重新評估已完成的部分**。

**接管**——**人直接執行某一步，然後把結果交回給 Agent 繼續**；**這需要 Agent 的狀態是外部可見且可修改的**，**而不是藏在一個不透明的對話歷史裡**。

**而支撐這三者的前提是「執行是可暫停的」**——**如果 Agent 是一個跑完才回傳的黑箱，任何介入都不可能。**

## 詳細解析

**「追加指示」的難點在於「已完成的工作可能需要作廢」**：使用者說「只處理今年的訂單」時——**Agent 可能已經處理了三筆去年的**。**正確的處理是明確地告知並詢問**（「我已經取消了 3 筆去年的訂單，需要恢復嗎？」）**而不是默默地改變後續行為**。**這需要 Agent 能回顧自己做過什麼並判斷是否受新指示影響**——**而這正是「維護結構化的已完成清單」的價值所在**。

**「接管」的關鍵是狀態的外部化**：如果所有的狀態都在對話歷史裡——**人無法「修改」它，只能用自然語言描述修改**（而那可能被誤解）。**而如果狀態是一份結構化的文件、一組檔案、或一個明確的待辦清單**——**人可以直接編輯，Agent 讀取修改後的狀態繼續**。**這也是「用檔案系統當工作空間」的一個重要價值**：**它讓人與 Agent 能操作同一份東西**。

**「暫停點的設計」影響介入的品質**：在一個工具呼叫的中途無法乾淨地暫停——**所以暫停應該發生在自然的邊界**（一輪結束、一個子任務完成）。**而對長時間的操作，應該提供「軟停止」**（**完成當前這一步就停，而不是立刻中斷**）**與「硬停止」**（**立刻中止，接受可能的不一致**）**兩種選擇**——**因為使用者的意圖可能是「我不想再等了」或「快停下來別再搞了」，這兩者需要不同的處理**。

**「介入的資料是最有價值的改進來源」**：使用者在什麼時候介入、修正了什麼——**這直接告訴你 Agent 在哪裡不符合預期**。**把這些記錄下來並分析，比任何離線評估都更貼近真實的問題**。**而一個介入率持續下降的 Agent，就是一個在真正變好的 Agent。**

## 面試回答方式

先給三種介入形態並指出**前提是執行可暫停**。加分點有四個：**追加指示的難點是已完成的工作可能需要作廢**——**正確處理是明確告知並詢問而非默默改變後續行為**，**而這需要維護結構化的已完成清單**；**接管的關鍵是狀態外部化**——**狀態都在對話歷史裡的話人只能用自然語言描述修改**，**而結構化的文件或檔案能讓人直接編輯**，**這也是「用檔案系統當工作空間」的重要價值**；**暫停點要在自然邊界**，**並提供軟停止與硬停止兩種選擇，因為「我不想再等了」與「快停下別再搞了」需要不同處理**；以及**介入的資料是最有價值的改進來源**——**介入率持續下降的 Agent 就是在真正變好的 Agent**。

## 講稿

有三種介入的形態，停止、追加指示、還有接管。而支撐這三者的前提是執行必須是可暫停的。如果代理是一個跑完才回傳的黑箱，任何介入都不可能。

追加指示的難點在於已完成的工作可能需要作廢。使用者說只處理今年的訂單時，代理可能已經處理了三筆去年的。正確的處理是明確告知並詢問要不要恢復，而不是默默地改變後續行為。這需要代理能回顧自己做過什麼，所以維護一份結構化的已完成清單很有價值。

接管的關鍵是狀態的外部化。如果所有狀態都在對話歷史裡，人無法修改它，只能用自然語言描述修改，而那可能被誤解。如果狀態是一份結構化的文件或一組檔案，人就可以直接編輯，代理讀取修改後的狀態繼續。

還有一點，停止應該分成軟停止跟硬停止。軟停止是完成當前這一步就停，硬停止是立刻中止。因為使用者的意圖可能是我不想再等了，也可能是快停下來別再搞了，這兩者需要不同的處理。

## 常見追問

### 怎麼讓 Agent 在關鍵點主動暫停？

**核心答案**：**用「檢查點」的概念**：在特定的操作前（不可逆的寫入、超過某個金額、影響超過 N 筆資料）**強制暫停並請求確認**。**判斷的規則應該在程式碼中定義，而不是靠模型判斷「這件事重不重要」**——**因為模型的風險感知不可靠，而且可以被說服**。

**詳細解析**：**「規則式的暫停點」與「模型判斷的暫停」應該並存但地位不同**：規則式的是強制的底線（**任何情況都會觸發**）；**而模型也可以主動說「我不確定，需要你確認」**——**後者能覆蓋規則想不到的情況，但不能被依賴**。**設計時應該先列出「哪些操作絕對需要確認」並寫成規則，再鼓勵模型在不確定時主動求助**。**而規則的設定有一個實用的方法：問「如果這一步做錯了，多久能被發現、修復成本多高」**——**發現慢或修復貴的就設檢查點**。**這個標準比「這件事重不重要」具體得多，也更容易在團隊中達成一致**。

**面試回答方式**：給檢查點的概念與典型觸發條件，並強調**規則應該在程式碼中定義而非靠模型判斷**——**因為模型的風險感知不可靠且可以被說服**。核心加分點是說明**規則式與模型判斷的暫停應該並存但地位不同**：**規則是強制的底線，模型主動求助能覆蓋想不到的情況但不能被依賴**。收在設定規則的實用方法：**問「這一步做錯了多久能被發現、修復成本多高」**——**發現慢或修復貴的就設檢查點**，**這比「重不重要」具體得多也更容易達成一致**。

### 使用者中斷後又想繼續，怎麼恢復？

**核心答案**：**需要一個明確的「暫停狀態」而非直接丟棄執行**。保存**當前的上下文摘要、已完成的步驟、以及中斷時正在做的事**——**恢復時先向使用者確認「上次進行到這裡，要繼續嗎？」並展示已完成的部分**。**如果中斷已經過了很久，還應該重新驗證前置條件**（外部狀態可能變了）。

**詳細解析**：**「重新驗證前置條件」是恢復時最容易被忽略的一步**：Agent 三小時前計畫要取消訂單 12345——**而使用者可能已經自己取消了，或者訂單狀態已經改變**。**盲目地執行舊計畫可能造成錯誤或重複操作**。**所以恢復不應該是「從斷點繼續」，而應該是「重新確認當前狀態後決定下一步」**——**這與分散式系統中「不要基於陳舊的狀態做決定」是同一個原則**。**實作上可以在恢復時重新執行一次唯讀的狀態查詢並讓模型比對「與我當初的理解一致嗎」**——**成本很低而能避免一整類的錯誤**。

**面試回答方式**：給恢復的做法（保存暫停狀態、確認後繼續、展示已完成部分）。核心加分點是**重新驗證前置條件最容易被忽略**——**三小時前的計畫可能已經因為外部變化而不適用，盲目執行會造成錯誤或重複操作**，**所以恢復應該是「重新確認當前狀態後決定下一步」而非「從斷點繼續」**，**與分散式系統「不要基於陳舊狀態做決定」是同一個原則**。收在低成本的實作：**恢復時重新執行唯讀查詢並讓模型比對是否與當初理解一致**。

### 人與 Agent 同時操作同一份資源怎麼辦？

**核心答案**：**用樂觀鎖或版本檢查，而不是假設只有 Agent 在動**。Agent 讀取了一份文件並準備修改——**而使用者同時也在編輯**。**正確的處理是「修改時帶上讀取時的版本，版本不符就中止並重新讀取」**——**與任何併發控制的做法一致**。

**詳細解析**：**「Agent 的操作週期很長」讓這個問題比一般的併發更嚴重**：一次讀取到最終寫入之間可能隔了幾十秒甚至幾分鐘（**中間有多輪模型推理**）——**這個窗口遠大於一般程式的讀改寫**。**所以樂觀鎖的衝突機率也高得多**。**而衝突發生時的處理需要特別設計**：**不能只是「重試」，因為 Agent 的決定是基於舊版本內容做的**——**應該重新讀取並讓模型重新評估「我的計畫在新版本下還適用嗎」**。**這個「衝突後要重新推理而非重新執行」的區別，是 Agent 併發控制與傳統併發控制最大的不同**——**而忽略它會導致 Agent 把基於舊內容的修改套用到新內容上，產生難以察覺的錯誤**。

**面試回答方式**：給樂觀鎖或版本檢查的做法。核心加分點是指出**Agent 的操作週期很長讓問題比一般併發更嚴重**——**讀取到寫入之間隔了幾十秒到幾分鐘的多輪推理，窗口遠大於一般程式的讀改寫，所以衝突機率也高得多**。收在最重要的區別：**衝突後要重新推理而非重新執行**——**因為 Agent 的決定是基於舊版本做的**，**忽略它會導致把基於舊內容的修改套用到新內容上，產生難以察覺的錯誤**。
