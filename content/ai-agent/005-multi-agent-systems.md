# 題目

什麼是「多代理系統（Multi-Agent System）」？相較於使用單一個功能包山包海的 Agent 去處理一個複雜任務，為什麼把這個任務拆分給**多個各自職責較為單一、彼此協作**的 Agent 共同完成，通常會是更好的架構選擇？

## 核心答案

多代理系統指的是**由多個各自具備獨立的角色定位、職責範疇、甚至各自配備不同工具集的 Agent，透過彼此之間的溝通、協作、任務分工，共同完成一個單一 Agent 難以獨自妥善勝任的複雜整體任務**的架構模式。相較於使用單一個試圖包山包海、什麼都要自己處理的 Agent，把任務拆分給多個各自職責單一明確的 Agent 協作完成，通常是更好的架構選擇，核心原因在於——這某種程度上是前面（見 [[003-planning-task-decomposition.md]]）已經深入討論過的**任務分解（Task Decomposition）**這個核心思路，**進一步被延伸應用到「負責執行這些子任務的不是同一個萬能 Agent 自己，而是各自由不同、各自更加專精特定領域的獨立 Agent 來分別承擔」**這個更進階的層次。一個試圖同時兼顧處理所有可能類型任務的單一 Agent，它的系統提示（見 [[../ai-llm/006-prompt-engineering.md]]）、可用工具集等等配置勢必需要變得非常龐雜、什麼都要涵蓋；這種**過度龐雜、缺乏專注焦點**的配置，反而可能導致這個單一 Agent 在處理任何一個**具體、需要專精能力**的子任務時，表現都不如一個**專門針對這一類特定子任務而設計、配置**的專精 Agent。多代理系統透過讓**每一個獨立的 Agent 都只需要專注在它自己被賦予的那個特定角色和職責範疇**，讓每一個 Agent 都能具備更聚焦、更專精的表現，再透過**恰當的協調機制**，把這些各自專精的 Agent 所產出的部分成果整合起來，共同達成那個原本單一 Agent 難以獨自妥善勝任的複雜整體目標。

## 詳細解析

**多代理系統的常見協作結構——階層式（Hierarchical）vs. 對等式（Peer-to-Peer）**：多代理系統實務上常見的協作結構，大致可以區分成幾種模式。**(1) 階層式（Hierarchical）結構**：存在一個**負責統籌、協調的「主管型」Agent（有時被稱為 Orchestrator 或 Manager）**，這個主管型 Agent 負責接收整體任務、進行前面已經討論過的任務分解和規劃，再把拆解出來的各個子任務**分派**給底下各自專精不同領域的「子 Agent（Sub-agent）」去分別執行；子 Agent 各自完成被分派的子任務之後，把結果回報給主管型 Agent，由主管型 Agent 負責**整合這些各自的子任務成果，形成最終的整體回覆**。**(2) 對等式（Peer-to-Peer）結構**：不存在一個明確的中央統籌者，多個 Agent **彼此平等、直接地互相溝通、協調**，共同推進任務；這種結構某種程度上更類似一群**地位平等的專家彼此直接討論、協作**，而不是透過一個中央的協調者來居中分派、整合。**階層式**結構的優勢在於**責任歸屬清晰、整體流程相對容易被統一掌控和追蹤**（因為有一個明確的主管 Agent 負責統籌全局）；而**對等式**結構的優勢則在於**更具彈性，不會因為中央的協調者本身出現瓶頸或故障而讓整個系統癱瘓**，但相對地**協調的複雜度可能更高**（因為缺乏一個明確的中央權威來仲裁、整合）。

**多代理系統相較於單一大型 Agent 的核心優勢——「角色專精」帶來的表現提升，以及可維護性**：延續核心答案已經建立的論點——**角色專精**是多代理系統最核心的價值來源。一個被賦予清晰、單一角色定位的 Agent（例如一個專門負責「針對程式碼進行安全性審查」的 Agent，或者一個專門負責「把技術性的分析結果轉換成淺顯易懂的自然語言說明」的 Agent），它的系統提示和工具配置可以被**高度針對這個特定角色的需求做精準的客製化和優化**，而不需要像一個試圖包山包海的單一 Agent 那樣，必須同時兼顧各種可能彼此衝突、甚至互相干擾的不同需求。這種**角色專精**的設計某種程度上也呼應了前面（見 [[../ai-llm/018-mixture-of-experts.md]]）已經深入討論過的**混合專家模型（MoE）**架構背後的核心思路——**讓不同的「專家」（在 MoE 裡是模型內部的子網路，在多代理系統裡則是各自獨立的完整 Agent）各自專精處理不同性質的內容或任務**，這種設計思路在這兩個看似不同的技術層次（模型內部架構，以及更高層次的系統架構）上反覆展現出相似的核心價值。除了表現品質的提升以外，多代理系統還帶來**系統可維護性**上的效益——當各個 Agent 各自只負責一個範疇明確的職責時，未來如果需要針對其中某一個特定的子職責進行調整、優化，只需要針對**那個對應的特定子 Agent** 做修改即可，而不需要擔心這個調整會對整個系統的其他不相關部分造成難以預期的連帶影響（這某種程度上也呼應了前面，見 [[003-planning-task-decomposition.md]]，已經討論過的「任務分解和微服務（Microservices）架構共享相似核心思路」這個洞察，延伸到多代理系統這個更貼近「多個獨立服務單元」的架構層次，同樣適用）。

**多代理系統引入的新挑戰——協調成本和錯誤傳播風險**：多代理系統雖然帶來前面已經討論的效益，但也引入了一些值得被仔細考量的新挑戰。**(1) 協調成本**：多個 Agent 之間需要進行額外的溝通、協調（把中間結果在不同 Agent 之間傳遞、確保彼此對任務當前的狀態有一致的理解），這種額外的協調過程本身就需要額外的運算資源和時間延遲（這某種程度上呼應了前面，見 [[../ai-llm/022-function-calling.md]]，已經討論過的「多工具協同呼叫需要考量的效率議題」，只是在多代理系統的情境裡，這種協調的複雜度通常比單純的多工具呼叫更高）。**(2) 錯誤傳播風險**：如果其中**某一個子 Agent** 因為某種原因（例如它對被分派的子任務理解有誤）產出了一個**品質不佳或錯誤的中間結果**，這個錯誤的結果**可能會被往下傳遞給依賴這個結果的其他後續 Agent**，導致這個最初的錯誤**沿著整個多代理協作的流程被層層放大、擴散**，最終影響整體任務的完成品質。這種**「錯誤可能跨越 Agent 邊界層層傳播、放大」**的風險，是設計一個穩健的多代理系統時，需要額外透過**恰當的品質把關機制**（例如前面，見 [[003-planning-task-decomposition.md]]，已經討論過的規劃審查思路，同樣可以被延伸應用成「在中間結果被傳遞給下一個 Agent 之前，先做妥善的品質把關」）來加以緩解的重要考量。

## 面試回答方式

先給出多代理系統的核心定義——「由多個各自具備獨立角色定位、職責範疇、甚至配備不同工具集的Agent，透過彼此的溝通協作、任務分工，共同完成一個單一Agent難以獨自妥善勝任的複雜整體任務的架構模式」。詳細解釋核心優勢並連結MoE——「核心價值來源是角色專精，一個被賦予清晰單一角色定位的Agent，系統提示和工具配置可以被高度針對這個特定角色的需求做精準客製化，而不需要像一個試圖包山包海的單一Agent那樣同時兼顧各種可能彼此衝突的需求，這呼應了之前討論過的混合專家模型MoE架構背後的核心思路——讓不同專家各自專精處理不同性質的內容或任務，只是分別體現在模型內部架構和更高層次系統架構這兩個不同技術層次上」。可以補充常見協作結構——「階層式結構有一個負責統籌協調的主管型Agent，負責任務分解和最終整合，責任歸屬清晰;對等式結構則沒有明確的中央統籌者，多個Agent彼此平等直接溝通協調，更具彈性但協調複雜度可能更高」。一定要誠實補充新挑戰——「多代理系統也引入了協調成本(額外的溝通協調需要額外的運算資源和時間延遲)、以及錯誤傳播風險(某個子Agent的錯誤中間結果可能被層層傳遞放大，影響最終整體任務品質)，這些是設計多代理系統時需要額外透過品質把關機制來緩解的重要考量」，展現你對多代理系統的優勢和代價有平衡且深入的理解。

## 常見追問

### 如果前面已經討論過的任務分解，本身就能讓單一個 Agent 依序妥善處理好幾個子任務，為什麼還需要進一步引入多代理系統，讓不同的獨立 Agent 各自負責不同子任務？這不會是過度設計嗎？

**核心答案**：**是否需要引入多代理系統，取決於這些被拆解出來的子任務彼此之間所需要的「專業能力差異程度」**——如果一個任務被拆解出來的各個子任務**所需要的能力和知識背景彼此相當相近、相似**（例如都是某種類似性質的資料處理步驟），讓**同一個 Agent** 依序處理這些相近性質的子任務通常就已經足夠，額外引入多代理架構反而可能是一種**不必要的過度設計**（徒增前面已經討論過的協調成本，卻沒有換來相應的效益）；但如果這些子任務**分別需要截然不同、甚至彼此可能存在某種程度衝突的專業能力和知識背景**（例如一個子任務需要深入的法律專業知識，另一個子任務則需要深入的財務數字分析能力），讓**同一個 Agent** 同時兼顧這些**差異懸殊**的不同專業領域，反而會讓這個 Agent 的整體配置變得過於龐雜，難以在任何一個專業領域上都達到理想的表現水準，這種情況下引入多代理系統，讓**各自專精不同領域的 Agent** 分別承擔，才是恰當的架構選擇。

**詳細解析**：這題考察是否能夠避免把多代理系統當成一種**任何情況下都理所當然應該被採用**的萬用架構，而能夠具備**依照具體情境的實際需求做出恰當架構取捨判斷**的能力，也呼應了這篇文章反覆強調的一個核心分析原則——**任何一種架構或技術方案的採用，都應該是依照具體情境的實際需求權衡考量之後做出的判斷，而不是因為這個方案聽起來更先進、更複雜，就不加思考地一律採用**。理解這個問題的核心在於回顧前面已經建立的認知——**多代理系統之所以能夠帶來效益，關鍵在於「角色專精」這個核心價值**。如果一個任務被拆解出來的各個子任務本身**並不需要截然不同的專業能力**（它們彼此所需要的知識背景、處理方式相當相近），那讓**同一個 Agent** 依序處理這些子任務並**不會**因為缺乏「角色專精」而造成任何實質的表現損失（因為這些子任務本身所需要的能力原本就相當相近，同一個 Agent 完全有能力同時勝任）。這種情況下額外引入多代理架構，把這些**其實相當相近**的子任務硬是拆分給不同的獨立 Agent 去分別處理，**並不會帶來任何實質的表現提升**（因為「角色專精」這個核心價值主張在這種情況下根本不成立），反而只是白白增加了前面已經討論過的**協調成本**（需要額外在這些其實能力需求相近的不同 Agent 之間做溝通、協調，這是一種純粹的額外開銷，沒有換來任何相應的效益）——這種情況正是典型的**過度設計**：引入了額外的架構複雜度，卻沒有換來任何實質的效益回報。因此，判斷是否應該採用多代理系統，一個關鍵的判斷準則是——**先仔細評估這個任務被拆解出來的各個子任務，彼此之間所需要的專業能力和知識背景差異程度究竟有多大**，只有當這種**差異確實顯著到讓單一個 Agent 難以同時兼顧、勝任**時，引入多代理系統讓各自專精的 Agent 分別承擔，才是一個**真正能夠換來實質效益，而非只是徒增不必要複雜度**的恰當架構選擇。理解「是否需要引入多代理系統，取決於這些被拆解出來的子任務彼此之間所需要的專業能力差異程度：如果各子任務所需能力和知識背景相當相近，讓同一個 Agent 依序處理通常就已足夠，額外引入多代理架構反而可能是不必要的過度設計，徒增協調成本卻沒有換來相應效益；但如果子任務分別需要截然不同、甚至彼此可能存在衝突的專業能力，讓同一個 Agent 同時兼顧會讓配置過於龐雜，難以在任何領域達到理想表現，這種情況下引入多代理系統讓各自專精的 Agent 分別承擔才是恰當的架構選擇。判斷準則是先評估子任務彼此所需專業能力和知識背景的差異程度，只有差異確實顯著到單一 Agent 難以同時兼顧勝任時，引入多代理系統才是真正能換來實質效益而非徒增複雜度的恰當選擇」，展現你具備依照具體情境實際需求做出恰當架構取捨判斷的能力，而非把多代理系統當成理所當然應該被無條件採用的萬用架構。

**面試回答方式**：先給出核心判斷準則——「是否需要引入多代理系統，取決於這些被拆解出來的子任務彼此之間所需要的專業能力差異程度」。給出兩種情況的對比——「如果各子任務所需能力和知識背景相當相近，讓同一個Agent依序處理通常就已足夠，額外引入多代理架構反而可能是不必要的過度設計，徒增協調成本卻沒有換來相應效益;但如果子任務分別需要截然不同、甚至彼此可能存在衝突的專業能力和知識背景，讓同一個Agent同時兼顧會讓配置過於龐雜，難以在任何一個領域達到理想表現水準，這種情況下引入多代理系統才是恰當的架構選擇」。可以總結——「任何一種架構方案的採用都應該是依照具體情境的實際需求權衡之後做出的判斷，而不是因為方案聽起來更先進複雜就不加思考地一律採用」。

### 在多代理系統裡，如果不同的 Agent 對同一件事情的判斷產生了分歧（例如 Agent A 認為應該採用方案甲，但 Agent B 認為應該採用方案乙），應該如何解決這種分歧？

**核心答案**：解決這種分歧的具體機制，**取決於這個多代理系統採用的是前面已經討論過的哪一種協作結構**。如果是**階層式結構**（存在一個主管型 Agent），最直接的解決方式是**由這個主管型 Agent 扮演最終的仲裁者角色**——蒐集這些產生分歧的不同子 Agent 各自的判斷和理由，依照這些理由做出最終的裁決，決定應該採用哪一個方案（或者是否存在某種能同時兼顧這兩個方案各自考量的折衷做法）。如果是**對等式結構**（不存在明確的中央統籌者），則需要依賴**某種事先設計好的分歧解決機制**——可能是讓這些產生分歧的 Agent **彼此進行額外的溝通、辯論**，嘗試透過交換彼此的理由和考量收斂到一個共識；也可能是引入一個**額外的、專門負責仲裁的第三方 Agent**（某種程度上也是一種臨時性地引入類似階層式結構那種仲裁機制）來做出最終的裁決。

**詳細解析**：這題考察是否理解多代理系統作為一個由多個**各自擁有獨立判斷能力**的 Agent 所組成的系統，天生就存在**這些獨立的判斷彼此可能產生分歧、甚至衝突**這種可能性，而一個成熟的多代理系統架構設計，需要**事先就妥善規劃好因應這種分歧的具體機制**，而不能天真地假設這些不同的 Agent **永遠都會恰好得出彼此一致、不衝突的判斷**。理解這個問題的核心在於認識到——**多代理系統之所以能夠帶來前面已經討論過的「角色專精」這個核心價值**，本質上是因為**每一個 Agent 各自是依照自己獨立的專業視角和判斷**去處理被分派的任務；這種「各自獨立判斷」的特性正是多代理系統能夠帶來效益的來源，但這同時也意味著**不同的 Agent 因為各自擁有不同的專業視角（甚至可能只是因為模型本身在生成過程中固有的隨機性），完全有可能針對同一件事情得出彼此不一致、甚至直接衝突的判斷**。這種**分歧**並不是一種系統運作異常的表徵，而是一個**多代理架構天生就可能會遇到的正常情況**，因此一個成熟的多代理系統**必須**在一開始設計時，就明確規劃好**當這種分歧真的發生時，應該透過什麼樣的機制來加以解決**。**階層式**結構的優勢在這個情境下特別明顯地展現出來——因為存在一個**明確的、擁有最終決策權威的主管型 Agent**，這個分歧解決的問題可以被相對直接地處理（把這個分歧連同各方的理由都呈報給這個主管型 Agent，由它做出最終的裁決）；而**對等式**結構因為**沒有這種天然存在的中央權威**，反而需要額外去設計**某種替代性的分歧解決機制**（不管是讓 Agent 彼此額外溝通、辯論收斂共識，還是臨時引入一個額外的仲裁角色）。這種**對等式結構在處理分歧這件事情上需要額外設計更多機制**的現實，某種程度上也是前面（見核心答案）已經提到的「對等式結構協調複雜度可能更高」這個一般性論點，在「處理分歧」這個具體情境下一個更加具體、可以被清楚感受到的展現。理解「多代理系統天生就存在不同 Agent 的獨立判斷彼此產生分歧甚至衝突的可能性，這正是角色專精這個核心價值帶來效益的來源所隱含的代價；一個成熟的多代理系統必須在設計時就明確規劃好分歧解決機制：如果是階層式結構，可以由存在的主管型 Agent 扮演最終仲裁者角色，蒐集各方理由做出裁決；如果是對等式結構，因為沒有天然存在的中央權威，需要額外設計替代性的分歧解決機制，例如讓 Agent 彼此溝通辯論收斂共識、或臨時引入一個額外的仲裁角色，這也具體展現了對等式結構在協調複雜度上通常更高這個一般性論點」，展現你理解多代理系統裡分歧是天生會發生的正常情況而非異常，並能依照協作結構的不同給出對應的具體解決機制。

**面試回答方式**：先給出核心答案——「解決分歧的具體機制取決於這個多代理系統採用的是哪一種協作結構」。分別說明兩種結構的做法——「如果是階層式結構，存在一個主管型Agent，最直接的解決方式是由它扮演最終仲裁者角色，蒐集各方子Agent的判斷和理由做出裁決;如果是對等式結構，沒有明確的中央統籌者，則需要依賴事先設計好的分歧解決機制，可能是讓產生分歧的Agent彼此溝通辯論收斂共識，也可能是臨時引入一個額外的仲裁Agent」。可以補充一個重要認知——「多代理系統天生就存在不同Agent獨立判斷產生分歧的可能性，這正是角色專精這個核心價值所隱含的代價，一個成熟的多代理系統必須在設計時就明確規劃好因應這種分歧的機制，而不能天真假設不同Agent永遠會得出一致的判斷」。

### 多代理系統裡，不同 Agent 之間傳遞訊息，是不是就是直接把前一個 Agent 生成的完整原始文字輸出原封不動傳給下一個 Agent？這樣做有沒有什麼問題？

**核心答案**：**直接原封不動地把前一個 Agent 完整的原始輸出傳遞給下一個 Agent，雖然是最直觀、最簡單的做法，但並不總是最恰當的做法**，存在幾個值得被仔細考量的問題。**(1) 可能傳遞了過多不相關的雜訊**：前一個 Agent 的完整輸出可能包含許多**只是它自己在思考過程中產生的中間內容（如 ReAct 模式裡的思考步驟），但對於下一個 Agent 接下來需要處理的任務而言並非真正必要**的資訊，把這些不必要的雜訊也一併傳遞過去，某種程度上會稀釋掉真正關鍵的核心資訊。**(2) 格式可能不符合下一個 Agent 預期接收的輸入格式**：不同的 Agent 各自可能被設計成**預期接收某種特定結構化格式的輸入**，如果前一個 Agent 的原始輸出格式和這個預期不符，直接傳遞過去可能會導致下一個 Agent **難以正確解析、理解**這份被傳遞過來的內容。因應這些問題，實務上更恰當的做法通常是**在兩個 Agent 之間額外加入一個「轉換／摘要」的中介步驟**，把前一個 Agent 的完整輸出先**提煉、轉換成一個更精簡、且符合下一個 Agent 預期輸入格式**的版本，再傳遞過去。

**詳細解析**：這題把多代理系統裡容易被想當然爾忽略的一個實務工程細節——**Agent 之間的訊息傳遞介面**——明確提出來討論，考察是否理解設計一個穩健的多代理系統，**不能只是天真地假設把一個 Agent 的輸出直接接到下一個 Agent 的輸入，就自然而然能順利運作**，而是需要像設計任何兩個需要彼此協作的獨立軟體元件之間的介面一樣，**審慎設計這個傳遞介面本身**。理解這個問題的核心在於回顧前面（見 [[../ai-llm/006-prompt-engineering.md]]）已經反覆強調的核心原則——**提供給模型的輸入內容應該是精簡、聚焦、且格式恰當的**。如果直接把一個 Agent 完整、未經處理的原始輸出（可能包含大量只是它自己內部思考過程的細節）原封不動地作為下一個 Agent 的輸入，這某種程度上**違背了這個核心原則**——下一個 Agent 可能需要花費額外的「認知資源」（某種程度上類似前面，見 [[../ai-llm/015-long-context-handling.md]]，已經討論過的 Lost in the Middle 這類挑戰），去從這一大段可能夾雜著大量不相關細節的原始輸出裡**自己判斷、篩選出哪些部分才是它真正需要參照的關鍵資訊**，這種額外的負擔某種程度上會降低整體系統的效率和可靠性。因此，一個更成熟、經過審慎設計的多代理系統，通常會明確地在**每一對需要彼此協作的 Agent 之間**設計一個恰當的**「介面規格」**——明確定義**上一個 Agent 應該用什麼樣的精簡、結構化格式，去總結、呈現它的產出結果**，讓這個被傳遞的內容**恰好就是下一個 Agent 真正需要用到的、且格式恰當**的資訊，不多不少。這種**「審慎設計 Agent 之間的訊息傳遞介面，而非依賴把原始輸出直接傳遞這種偷懶做法」**的實務考量，某種程度上也呼應了一個更普遍的軟體工程原則——**任何兩個需要彼此協作的獨立元件之間，都需要一個經過審慎設計、而非隨意湊合的清晰介面規格**；這個原則不管是在傳統的軟體模組設計、微服務之間的 API 設計、還是這裡討論的多代理系統裡 Agent 之間的訊息傳遞設計，都同樣適用。理解「直接原封不動傳遞前一個 Agent 的完整原始輸出，雖然是最直觀的做法，但存在傳遞過多不相關雜訊、以及格式可能不符合下一個 Agent 預期輸入格式這兩個問題；因應這些問題，更恰當的做法是在 Agent 之間額外加入一個轉換摘要的中介步驟，把前一個 Agent 的完整輸出提煉轉換成一個更精簡且符合下一個 Agent 預期輸入格式的版本。這呼應了提供給模型的輸入應該精簡聚焦、格式恰當這個核心原則，也呼應了任何兩個需要彼此協作的獨立元件之間都需要一個經過審慎設計的清晰介面規格；這個原則不管是傳統軟體模組設計、微服務 API 設計、還是多代理系統裡 Agent 之間的訊息傳遞設計，都同樣適用」，展現你能識別出多代理系統設計裡容易被忽略的訊息傳遞介面這個實務工程細節，並將其連結到更普遍的軟體工程原則。

**面試回答方式**：先給出核心答案——「直接原封不動傳遞前一個Agent的完整原始輸出，雖然是最直觀的做法，但並不總是最恰當的做法」。給出兩個具體問題——「第一，前一個Agent的完整輸出可能包含許多只是它自己思考過程的中間內容，對下一個Agent接下來需要處理的任務而言並非真正必要，傳遞過多不相關雜訊會稀釋真正關鍵的資訊;第二，不同Agent各自可能預期接收某種特定結構化格式的輸入，原始輸出如果格式不符，可能導致下一個Agent難以正確解析理解」。給出更恰當的做法——「實務上更恰當的做法是在兩個Agent之間額外加入一個轉換摘要的中介步驟，把前一個Agent的完整輸出提煉轉換成一個更精簡、且符合下一個Agent預期輸入格式的版本，再傳遞過去」。可以總結——「這呼應了任何兩個需要彼此協作的獨立元件之間，都需要一個經過審慎設計的清晰介面規格，這個原則不管在傳統軟體模組設計、微服務API設計、還是多代理系統的Agent訊息傳遞設計裡都同樣適用」。
