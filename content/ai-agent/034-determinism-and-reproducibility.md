# 題目

Agent 出了問題但重跑一次又正常了，怎麼辦？

## 核心答案

這是 Agent 系統最令人挫折的問題，而根源是「多個隨機來源疊加」。

**隨機來源有四類**：**模型的採樣**（temperature > 0）、**外部世界的變化**（資料變了、服務回應不同）、**並行的時序**（多個工具呼叫的完成順序）、**以及模型本身的非決定性**（即使 temperature = 0，批次組成與硬體差異也會造成微小的不同）。

處理的核心是「記錄足以重現的一切」：每一次模型呼叫的完整輸入與輸出、每一次工具呼叫的參數與回傳、以及所有的隨機種子與時間戳。**有了這些就能「回放」**——用記錄的工具回傳替代真實呼叫，重跑同一段軌跡。

回放的價值在於它把「偶發的問題」變成「可重複的測試案例」——**而那是修復任何 bug 的前提。**

## 詳細解析

「即使 temperature = 0 也不完全確定」是一個需要知道的事實：GPU 上的浮點運算不滿足結合律——而批次的組成會改變運算的順序，於是同樣的輸入在不同的批次中可能得到略微不同的 logits，在接近的候選之間就可能翻轉選擇。所以「設 temperature = 0 就能重現」是一個常見但錯誤的期待。這也意味著「完全的確定性」在使用商業 API 時是做不到的——而回放（用記錄的輸出替代真實呼叫）是唯一可靠的重現手段。

**「回放的兩種模式」各有用途**：**完全回放**——連模型輸出都用記錄的，用於重現一個已知的執行並檢查框架邏輯；**半回放**——只回放工具的回傳，模型重新推理，用於測試「提示改了之後，同樣的外部條件下模型會不會做得更好」。後者是提示迭代最有價值的工具：它讓你能在固定的外部環境下比較不同的提示版本，**而不受外部變化的干擾**。

**「記錄的成本」需要被管理**：完整記錄每次呼叫的輸入輸出會產生大量資料——**尤其是長上下文的請求**。**實務上的做法是分級**：全部請求記錄摘要（哪些工具、成功與否、耗時），失敗與抽樣的請求記錄完整內容。而在開發環境則全部記錄，因為那時的除錯價值最高。

**「時間與隨機性要可注入」**：如果 Agent 的邏輯依賴當前時間或隨機數——那些應該透過一個可替換的介面取得，而不是直接呼叫系統函式。這是傳統軟體測試就有的原則，只是在 Agent 中經常被忽略——而它的缺失會讓回放無法真正重現。

## 面試回答方式

先給根源——**多個隨機來源疊加**，並列出四類。給處理的核心（記錄足以重現的一切並支援回放）與回放的價值（把偶發問題變成可重複的測試案例）。加分點有四個：**即使 temperature = 0 也不完全確定**——GPU 浮點運算不滿足結合律，批次組成會改變運算順序，所以完全的確定性在使用商業 API 時做不到，回放是唯一可靠的重現手段；**回放的兩種模式**——完全回放檢查框架邏輯，半回放（只放工具回傳、模型重新推理）是提示迭代最有價值的工具；**記錄的成本要分級管理**；以及**時間與隨機性要可注入**，這是傳統測試就有的原則但在 Agent 中經常被忽略，而它的缺失會讓回放無法真正重現。

## 講稿

根源是多個隨機來源疊加。模型的採樣、外部世界的變化、並行的時序、還有模型本身的非決定性。

最後那一點很多人不知道。即使把溫度設成零也不完全確定，因為加速卡上的浮點運算不滿足結合律，而批次的組成會改變運算順序，於是同樣的輸入在不同批次中可能得到略微不同的分數，在接近的候選之間就可能翻轉選擇。所以設溫度為零就能重現是一個常見但錯誤的期待。

處理的核心是記錄足以重現的一切，每次模型呼叫的完整輸入輸出、每次工具呼叫的參數跟回傳。有了這些就能回放，用記錄的工具回傳替代真實呼叫，重跑同一段軌跡。回放的價值在於它把偶發的問題變成可重複的測試案例，而那是修復任何問題的前提。

回放有兩種模式。完全回放連模型輸出都用記錄的，用來檢查框架邏輯。半回放只回放工具的回傳，讓模型重新推理。後者是提示迭代最有價值的工具，因為它讓你能在固定的外部環境下比較不同的提示版本，不受外部變化干擾。

## 常見追問

### temperature 該設多少？

**核心答案**：**看任務**。需要精確與一致的任務設 0 或很低（工具呼叫、結構化輸出、事實查詢）——降低隨機性就是降低出錯的機率。**需要多樣性的任務才調高**（創意寫作、產生多個候選方案）。而在 Agent 的主控迴圈中，多數情況應該用低溫度——因為你要的是可靠的執行而非有創意的執行。

**詳細解析**：「低溫度不等於更好的推理」是一個需要澄清的細節：溫度影響的是採樣的隨機性——**它不會讓模型「想得更清楚」**。在某些需要探索的任務上，適度的溫度反而更好（例如自我一致性採樣就需要多樣的推理路徑）。所以正確的表述是「執行類的步驟用低溫、探索類的步驟可以用高溫」——而一個 Agent 的不同階段可以用不同的溫度：規劃階段可以稍高（產生多樣的方案），執行階段用低溫（穩定地呼叫工具）。這種「按階段調整採樣參數」的做法在多數 Agent 實作中沒有被使用，卻是一個成本為零的優化。

**面試回答方式**：給按任務的判斷並指出Agent 主控迴圈多數情況應該用低溫，因為要的是可靠執行而非有創意的執行。核心加分點是澄清**低溫度不等於更好的推理**——溫度影響的是採樣隨機性，不會讓模型想得更清楚，某些需要探索的任務適度的溫度反而更好。收在實用做法：**按階段調整**——規劃階段稍高產生多樣方案、執行階段低溫穩定呼叫工具，這在多數實作中沒被使用卻是成本為零的優化。

### 怎麼建立 Agent 的回歸測試？

**核心答案**：**用回放的軌跡當測試案例**。從生產環境挑選有代表性的執行——保存它們的工具回傳作為固定的「環境」，然後在每次提示或程式碼變更後重跑並比對結果。判準不是「軌跡完全一致」而是「最終結果正確且步數沒有明顯增加」。

**詳細解析**：「用真實軌跡而非人造案例」的價值在於它捕捉了真實的複雜度：人造的測試案例往往是理想化的（乾淨的輸入、標準的回應）——而真實的軌跡包含了各種意外（格式不一致的資料、暫時的失敗、模糊的使用者表述），**那些正是 Agent 容易出錯的地方**。建立這個測試集的方法是「從生產的追蹤中挑選失敗案例與典型成功案例」——失敗案例確保修好的不再壞，成功案例確保沒有退化。而隨著時間推移，這個集合會自然地覆蓋你的系統真正會遇到的情況——這比任何預先設計的測試計畫都貼近現實。「讓生產事故變成測試案例」是這裡最有價值的實踐。

**面試回答方式**：給做法（用回放軌跡當測試案例，保存工具回傳作為固定環境）與判準（不是軌跡完全一致，而是最終結果正確且步數沒明顯增加）。核心加分點是**用真實軌跡而非人造案例**——人造案例是理想化的，而真實軌跡包含各種意外，那正是容易出錯的地方。收在建立方法與價值：從生產追蹤中挑失敗案例與典型成功案例，隨時間推移會自然覆蓋真正會遇到的情況，而「讓生產事故變成測試案例」是最有價值的實踐。

### 並行執行讓重現變難怎麼辦？

**核心答案**：記錄實際的完成順序，回放時按記錄的順序重放。並行的不確定性主要來自完成順序——而只要記錄了「這一輪的五個呼叫實際上以什麼順序返回、各自回傳了什麼」，回放時就能完全重現那個情境。如果問題與順序無關，也可以在測試中強制串行以排除這個變數。

**詳細解析**：「強制串行來隔離問題」是一個實用的除錯手段：如果一個問題在串行模式下消失了——那它很可能與並行的時序有關（競態、共享狀態、或者結果合併的邏輯錯誤）；如果串行下仍然出現，那就與並行無關，可以在更簡單的環境中排查。這個二分法能在幾分鐘內縮小一半的搜尋空間。而在設計上，最好的預防是「讓並行的呼叫真正獨立」——不共享可變狀態、不依賴完成順序、結果的合併是可交換的。如果做到了這三點，並行就不會引入不確定性——而多數工具呼叫本來就滿足這些條件，只有當有人在工具中加入了共享狀態時才會出問題。

**面試回答方式**：給做法（記錄實際完成順序、回放時按記錄重放，或在測試中強制串行）。核心加分點是**強制串行來隔離問題**這個二分法——串行下消失就與時序有關，仍然出現就與並行無關，能在幾分鐘內縮小一半搜尋空間。收在設計上的預防：**讓並行呼叫真正獨立**（不共享可變狀態、不依賴順序、合併可交換），而多數工具呼叫本來就滿足，只有有人加入共享狀態時才出問題。
