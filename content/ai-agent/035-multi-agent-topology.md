# 題目

多個 Agent 協作時，通訊結構怎麼設計？會有什麼問題？

## 核心答案

**四種常見拓撲，複雜度與失控風險遞增。**

**管線（pipeline）**——**固定的順序，A 的輸出是 B 的輸入**。**最可控、最容易除錯，但表達不了需要迭代的任務。**

**主從（supervisor）**——**一個協調者決定調用哪個專才並整合結果**。**最常用，因為它把決策集中在一處，易於觀察與限制。**

**群組討論**——**多個 Agent 互相對話直到達成一致**。**表達力強，但收斂性沒有保證**——**它們可能一直互相同意、一直互相反對、或者陷入禮貌性的循環**。

**去中心化（黑板或訊息匯流排）**——**Agent 各自從共享狀態中取任務**。**最靈活也最難預測。**

**而核心的問題是「收斂」**：**沒有明確的終止機制，多代理討論很容易變成昂貴的空轉**——**所以任何多代理設計都必須有輪數上限、明確的決策者、以及一個「無法達成共識時怎麼辦」的規則。**

## 詳細解析

**「多代理討論常常只是昂貴的自我肯定」是一個需要誠實面對的現象**：同一個模型扮演不同角色——**它們的知識、偏誤、與盲點完全一樣**。**於是「批評者」提出的批評，往往正是「作者」本來就會想到的**；**而真正的盲點兩邊都看不見**。**所以多代理的價值不在於「不同的觀點」，而在於「不同的資訊與工具」**——**一個能查資料庫的 Agent 與一個能跑測試的 Agent 之間有真實的分工，而兩個只有不同人設的 Agent 之間沒有**。**這個判準能過濾掉大部分沒有價值的多代理設計。**

**「錯誤會在多代理中放大」**：一個 Agent 的錯誤輸出成為另一個的輸入——**而後者通常會信任它**（**它看起來像是系統內部的可靠資訊**）。**於是一個早期的小錯誤可能被層層放大**。**緩解的做法是「每個 Agent 對輸入保持懷疑」**（在提示中明確要求驗證）**與「關鍵資訊的傳遞要帶上來源與信心」**——**而不是把上游的輸出當成事實**。

**「成本是乘法而非加法」**：五個 Agent 各跑十輪就是五十次模型呼叫——**而如果它們互相傳遞的上下文很長，成本會更高**。**多代理的成本常常是單一 Agent 的五到十倍**，**而效果的提升往往達不到那個倍數**——**所以「先確認單一 Agent 真的做不到」是必要的前提**。

**「明確的介面比自由對話好」**：讓 Agent 之間交換結構化的資料（一個明確 schema 的物件）而非自由文字——**這減少了誤解、便於驗證、也讓每一步的產出可以被獨立測試**。**自由的自然語言對話看起來更「智能」，但在工程上是更差的選擇。**

## 面試回答方式

先給四種拓撲與各自的取捨，並指出**核心問題是收斂**——**任何多代理設計都必須有輪數上限、明確的決策者、以及無法達成共識時的規則**。加分點有四個：**多代理討論常常只是昂貴的自我肯定**——**同一個模型扮演不同角色，知識、偏誤與盲點完全一樣**，**所以價值不在「不同的觀點」而在「不同的資訊與工具」**，**而這個判準能過濾掉大部分沒有價值的設計**；**錯誤會在多代理中放大**——**下游通常信任上游的輸出**，**緩解是保持懷疑並帶上來源與信心**；**成本是乘法而非加法**——**常常是單一 Agent 的五到十倍而效果提升達不到那個倍數**；以及**明確的介面比自由對話好**——**自由對話看起來更智能，但工程上是更差的選擇**。

## 講稿

有四種常見拓撲，複雜度跟失控風險遞增。管線、主從、群組討論、還有去中心化。實務上最常用的是主從，因為它把決策集中在一處，易於觀察跟限制。

核心的問題是收斂。沒有明確的終止機制，多代理討論很容易變成昂貴的空轉。所以我會要求輪數上限、明確的決策者、還有一個無法達成共識時怎麼辦的規則。

但我想先講一個需要誠實面對的現象。多代理討論常常只是昂貴的自我肯定。同一個模型扮演不同角色，它們的知識、偏誤、盲點完全一樣。於是批評者提出的批評，往往正是作者本來就會想到的，而真正的盲點兩邊都看不見。

所以我認為多代理的價值不在於不同的觀點，而在於不同的資訊與工具。一個能查資料庫的代理跟一個能跑測試的代理之間有真實的分工，而兩個只有不同人設的代理之間沒有。這個判準能過濾掉大部分沒有價值的多代理設計。

另外成本是乘法而不是加法，常常是單一代理的五到十倍，而效果提升往往達不到那個倍數。

## 常見追問

### 主從架構中，協調者該知道多少細節？

**核心答案**：**只知道「子任務的結果與狀態」，不知道子 Agent 的內部過程**。這與函式呼叫的封裝是同一個道理——**協調者需要的是「這個子任務成功了嗎、結果是什麼、有什麼需要注意的」**，**而不是子 Agent 內部的十五步推理**。**把子 Agent 的完整軌跡塞回協調者的上下文，是多代理系統上下文爆炸最常見的原因。**

**詳細解析**：**「子 Agent 要回傳什麼」應該被明確設計成一個 schema**：結果、狀態（成功/部分成功/失敗）、遇到的問題、以及對後續步驟的建議。**自由文字的回傳會讓協調者難以可靠地解析與判斷**。**而「部分成功」這個狀態特別重要**：**子 Agent 完成了一半就卡住時，協調者需要知道「哪一半完成了」才能決定下一步**——**而只有成功/失敗兩種狀態會丟失這個資訊**。**另一個實務要點是「子 Agent 的失敗不應該直接終止整個任務」**：**協調者應該能決定重試、換一個子 Agent、或者調整計畫**——**這正是主從架構相對於固定管線的價值所在**。

**面試回答方式**：給封裝原則（**只知道結果與狀態，不知道內部過程**）並指出**把完整軌跡塞回協調者是上下文爆炸最常見的原因**。核心加分點是**子 Agent 的回傳應該有明確的 schema**（結果、狀態、問題、建議），並強調**「部分成功」這個狀態特別重要**——**只有成功/失敗兩種會丟失「哪一半完成了」的資訊**。收在**子 Agent 的失敗不應該直接終止整個任務**——**協調者能決定重試、換人或調整計畫，這正是主從相對於固定管線的價值**。

### 多代理什麼時候真的比單一 Agent 好？

**核心答案**：**三種情況**。**上下文隔離**——**每個子任務需要大量的、不同的上下文**（例如分析十個檔案，每個都要完整讀入）；**分開處理讓每個子 Agent 的上下文保持乾淨**。**能力或權限不同**——**一個能存取生產資料庫、一個只能讀文檔**；**分開是安全要求而非效率選擇**。**真正的並行**——**多個獨立的子任務同時進行，總時間顯著縮短**。

**詳細解析**：**「上下文隔離」是最被低估卻最實在的理由**：單一 Agent 處理十個檔案時，**前面檔案的內容會一直佔著上下文並干擾後面的判斷**；**而十個子 Agent 各自處理一個，每個的上下文都是乾淨且聚焦的**——**準確率通常明顯更高，而且成本可能更低（因為每個的上下文都短）**。**這是一個「多代理同時提升品質與降低成本」的少數場景**。**相對地，「用不同人設提升思考品質」這個常見的動機在實測上收益很小**——**而它的成本是確定的**。**所以我的判斷順序是：先問「是不是上下文、權限、或並行的需求」**，**三個都不是的話，多代理很可能只是增加了複雜度**。

**面試回答方式**：給三種情況並指出**權限不同時分開是安全要求而非效率選擇**。核心加分點是**上下文隔離最被低估卻最實在**——**單一 Agent 處理十個檔案時前面的內容會干擾後面的判斷，而分開讓每個上下文乾淨聚焦**，**準確率更高且成本可能更低**，**是「同時提升品質與降低成本」的少數場景**。收在判斷順序：**先問是不是上下文、權限或並行的需求，三個都不是的話多代理很可能只是增加複雜度**。

### 多代理的可觀測性怎麼做？

**核心答案**：**樹狀的追蹤加上「每個 Agent 的獨立指標」**。追蹤上——**用父子 span 表達協調者與子 Agent 的關係**，**讓一次請求的完整結構可以被展開查看**。指標上——**每個 Agent 角色分別統計成功率、步數、成本**——**於是能定位「是哪一個角色拖慢了整體」或「哪一個角色的失敗率異常」**。

**詳細解析**：**「按角色分別統計」是多代理特有且必要的**：整體成功率 70% 這個數字沒有指導價值——**而「規劃者成功率 95%、程式碼撰寫者 85%、測試修復者 60%」立刻告訴你該優化哪裡**。**這與微服務按服務分別監控是同一個道理**。**另一個實務要點是「要能看到 Agent 之間傳遞的內容」**：**很多多代理的問題出在交接處**（**上游的輸出不是下游期待的格式或粒度**）——**而如果追蹤只記錄了「呼叫了子 Agent」而沒有記錄傳遞的內容，這類問題無法診斷**。**所以介面上的資料應該被完整記錄，而它也正好是最有價值的除錯資訊。**

**面試回答方式**：給樹狀追蹤加按角色的獨立指標。核心加分點是**按角色分別統計是必要的**——**整體成功率 70% 沒有指導價值，而分角色的數字立刻告訴你該優化哪裡**，**與微服務按服務監控是同一個道理**。收在**要能看到 Agent 之間傳遞的內容**——**很多問題出在交接處（格式或粒度不符）**，**而只記錄「呼叫了子 Agent」無法診斷**，**所以介面上的資料應該被完整記錄，它也正好是最有價值的除錯資訊**。
