# 題目

在前面（見 [[005-multi-agent-systems.md]]）討論過的多代理系統（Multi-Agent System）裡，不同的 Agent 具體是透過什麼樣的方式彼此溝通、交換資訊的？為什麼業界近年會出現像 A2A（Agent-to-Agent）這類**專門針對 Agent 間通訊而設計的標準協定**？

## 核心答案

在多代理系統裡，不同 Agent 之間的溝通本質上是**把一個 Agent 需要傳達給另一個 Agent 的資訊（可能是一個任務請求、一份中間結果，或者一個狀態更新），用某種雙方都能正確理解、解析的格式封裝起來，再透過某種傳輸管道（可能是直接的函式呼叫，也可能是透過網路的 API 請求）傳遞給對方**。之所以業界近年會出現像 **A2A（Agent-to-Agent）** 這類專門的標準協定，核心原因在於——**早期各家不同的 Agent 開發框架和平台各自採用自己獨有、彼此不相容的通訊格式和機制**，這導致**由不同框架、不同廠商所建構出來的 Agent 難以彼此順暢地互相溝通、協作**（就像如果每一個不同的電話系統廠商都各自採用完全不同、彼此不相容的通訊標準，使用不同廠商電話的使用者就沒有辦法彼此互相通話）。A2A 這類標準協定試圖解決的正是這個問題——**透過制定一套各家不同的 Agent 系統都能夠共同遵循的統一通訊規範**（包括如何描述一個 Agent 自己具備哪些能力、如何發起一個任務請求、如何回報任務的執行進度和最終結果等等），讓**即使是由不同廠商、不同框架所建構出來的 Agent**，也能夠依照這套共通的標準規範**彼此順暢地互相溝通、協作**。這種標準化的發展某種程度上呼應了整個軟體產業歷史上反覆出現過的模式——**當一種技術從早期各自為政、百家爭鳴的階段逐漸走向成熟、需要大規模普及應用時，通常都會出現對統一標準協定的需求**（就像網際網路早期各種不同的網路協定最終逐漸收斂到 TCP/IP 這套共通標準；或是不同的 Web 瀏覽器和伺服器需要共同遵循 HTTP 這套共通協定，才能讓網際網路真正普及、暢通運作）。

## 詳細解析

**Agent 間通訊需要規範的核心要素——能力描述、任務委派、狀態回報**：一套完整的 Agent 間通訊協定通常需要規範幾個核心要素——**(1) 能力描述（Capability Description）**：讓每一個 Agent 能夠用一套標準化的方式向其他 Agent **清楚地聲明自己具備哪些能力、能夠處理哪一類的任務**（這樣其他 Agent 或者負責協調的主管型 Agent 才能正確地判斷應該把某個特定的子任務委派給哪一個具備對應能力的 Agent）；**(2) 任務委派（Task Delegation）**：規範一個 Agent 應該用什麼樣的標準格式，去向另一個 Agent **正式地發起一個具體的任務委派請求**（這某種程度上類似前面（見 [[../ai-llm/022-function-calling.md]]）已經深入討論過的 Function Calling 機制裡，『如何用標準化的結構化格式去指定要呼叫哪個工具、需要哪些參數』這個概念，只是這裡被委派的對象不是一個單純的工具函式，而是另一個同樣具備自主決策能力的完整 Agent）；**(3) 狀態回報（Status Reporting）**：規範一個正在執行某個被委派任務的 Agent 應該如何**持續地向委派方回報這個任務目前的執行進度**（尤其是對於那些需要較長時間才能完成的任務，讓委派方能夠即時地掌握這個任務目前究竟進行到哪個階段，而不是只能被動地等待到整個任務完全結束才得知結果）。

**A2A 這類標準協定和前面已經深入討論過的 MCP，兩者的關係與區別**：值得特別釐清的是 **A2A** 和（將在下一題深入討論的）**MCP（Model Context Protocol）**，這兩個近期都相當受到關注的標準協定**各自處理的是不同層次的通訊問題**——**MCP** 主要規範的是**「一個 Agent（或者更廣泛地說，任何一個運用大型語言模型的應用）應該如何用標準化的方式去存取、使用外部的工具和資料來源」**這件事，某種程度上是 **Agent 和它所使用的『工具/資源』之間**的通訊標準；而 **A2A** 規範的則是**「不同的、各自獨立自主的 Agent 彼此之間應該如何溝通、協作」**這件事，是 **Agent 和另一個同樣具備自主決策能力的 Agent 之間**的通訊標準。這兩者某種程度上可以被理解成**分別處理多代理系統裡兩種不同性質的『連接關係』**——**MCP** 對應『Agent 向下連接、使用工具和資料』這個方向；**A2A** 對應『Agent 向平行或上下連接、和其他 Agent 協作』這個方向。一個完整的、成熟的多代理系統通常**同時需要**妥善地處理這兩種不同方向的連接關係。

**標準化通訊協定帶來的核心價值——生態系統的互通性（Interoperability）**：標準化的 Agent 間通訊協定帶來的最核心價值是**互通性**——這某種程度上呼應了前面（見 [[../backend-engineering/009-service-discovery.md]] 相關討論）在微服務（Microservices）架構裡也同樣重要的核心價值——當不同的、獨立開發的軟體元件（不管是微服務還是這裡討論的 Agent）都遵循同一套共通的標準介面規範時，這些元件就能夠**被更自由地組合、替換，以及跨組織地協作**（例如一家公司開發的某個專精特定領域的 Agent，因為遵循共通的 A2A 標準，可以被另一家公司建構的多代理系統直接地納入使用，而不需要為了這個特定整合情境額外地撰寫客製化的轉接程式碼）。這種**生態系統層次的互通性**是讓一整個產業能夠從**各自為政、重複造輪子**的早期階段，逐漸走向**能夠共享、重複利用彼此已經建構好的能力元件**這種更成熟、更有效率的發展階段的關鍵基礎。

## 面試回答方式

先給出Agent間通訊的核心運作方式——「不同Agent之間的溝通，本質上是把一個Agent需要傳達給另一個Agent的資訊，用某種雙方都能正確理解解析的格式封裝起來，透過某種傳輸管道傳遞給對方」。詳細解釋為什麼需要標準協定——「早期各家不同的Agent開發框架各自採用獨有、彼此不相容的通訊格式，導致由不同框架建構出來的Agent難以彼此順暢溝通協作，A2A這類標準協定試圖透過制定一套各家系統都能共同遵循的統一通訊規範，讓不同廠商框架建構的Agent也能彼此順暢協作，這呼應了整個軟體產業歷史上反覆出現的模式——技術從早期百家爭鳴走向成熟普及時，通常都會出現對統一標準協定的需求，就像網際網路早期各種協定最終收斂到TCP/IP這套共通標準」。可以列出協定需要規範的核心要素——「能力描述讓每個Agent能標準化聲明自己具備哪些能力;任務委派規範如何用標準格式向另一個Agent發起具體任務委派請求;狀態回報規範如何持續向委派方回報任務執行進度」。一定要主動釐清和MCP的區別——「MCP規範的是Agent和它所使用的工具資料來源之間的通訊標準，A2A規範的則是不同的、各自獨立自主的Agent彼此之間的通訊標準，兩者分別對應Agent向下連接使用工具、和向平行連接協作其他Agent這兩種不同方向的連接關係，一個成熟的多代理系統通常同時需要妥善處理這兩種連接關係」，展現你對Agent通訊協定的必要性、核心規範要素、以及和相關協定的區別，有完整且精確的理解。

## 常見追問

### 如果沒有像 A2A 這樣的標準協定，是不是就完全無法讓不同框架建構的 Agent 彼此協作？一定要等到大家都採用同一套標準才能開始做多代理系統嗎？

**核心答案**：**並不是完全無法協作**——即使沒有一套各方都共同遵循的標準協定，**依然可以透過額外地撰寫客製化的『轉接/橋接』程式碼**，讓由不同框架建構的 Agent 彼此能夠勉強溝通、協作（把一方輸出的格式轉換成另一方能夠理解的格式），只是這種做法**每多一組需要彼此協作的不同框架 Agent，就需要額外地撰寫一組專門針對這特定兩者之間的客製化轉接程式碼**。隨著需要彼此協作的不同框架/系統的數量增加，這種客製化轉接程式碼的維護成本會**以接近平方級數的速度增長**（N 個不同的系統兩兩之間都可能需要一組各自獨立的轉接程式碼，理論上最多可能需要到接近 N 平方量級的轉接組合），這正是**標準化協定之所以重要**的核心原因——透過讓**所有參與方都共同遵循同一套標準**，把這種**「每一對系統都需要各自客製化轉接」**的問題簡化成**「每一個系統只需要實作一次對這套共通標準的支援，就能夠和所有其他同樣支援這套標準的系統順暢地協作」**，大幅降低整體的協作成本。

**詳細解析**：這題要求把「為什麼需要標準協定」這件事講得更具體、更量化，而不是只是籠統地說「標準協定比較方便」，考察是否能夠用一個更具體、有說服力的論證去解釋標準化協定所能帶來的效益規模。理解這個問題的核心在於回顧一個在**分散式系統和軟體工程領域**相當經典的論證——**「N 個不同的獨立系統如果彼此之間都需要各自客製化的點對點整合，所需要的整合工作量會隨著 N 的增加而呈現接近平方級數的成長」**（更精確地說，是 N 個系統兩兩配對最多可能產生到 N×(N-1)/2 種不同的配對組合，每一種配對都可能需要一組獨立的客製化轉接工作）——舉例來說，如果只有 **2 個**不同框架建構的 Agent 系統需要彼此協作，只需要撰寫 **1 組**針對這兩者之間的客製化轉接程式碼，還算可以接受；但如果有 **10 個**不同框架的系統都希望能夠彼此自由地互相協作，理論上最多可能需要撰寫高達 **45 組（10×9/2）**各自獨立的客製化轉接程式碼，這種**隨著系統數量增加而快速膨脹的整合成本**很快就會變得**難以承受**；相較之下，如果這 10 個系統**都共同遵循同一套標準協定**，每一個系統只需要**各自獨立地**實作一次對這套共通標準的支援（也就是總共只需要 **10 次**獨立的實作工作，而不是 45 組兩兩之間的客製化轉接），就能夠**自動地和所有其他同樣遵循這套標準的系統順暢地彼此協作**。這種**「把協作成本從和系統數量的平方成正比，降低到和系統數量的一次方成正比」**的效益，正是標準化協定之所以能夠帶來如此顯著的整體效率提升的核心數學道理。這種論證方式某種程度上也是一個在評估**任何涉及『多方彼此需要互相協作』**的系統設計情境時（不管是 Agent 通訊、API 整合，還是其他任何涉及多方協作的場景）都值得被反覆套用的核心分析工具——**「先去估算如果沒有共通標準、各自客製化整合，所需要的整合工作量會如何隨著參與方的數量而成長；再去評估導入一套共通標準能夠把這種成長模式從什麼樣的量級降低到什麼樣的量級」**。理解「並不是完全無法協作，即使沒有標準協定，依然可以透過額外撰寫客製化轉接程式碼讓不同框架的Agent勉強溝通，但這種做法每多一組需要協作的不同框架就需要一組專門的客製化轉接程式碼，隨著需要協作的系統數量增加，這種客製化轉接的維護成本會以接近平方級數的速度增長(N個系統兩兩配對最多可能產生N乘以N減一除以二種組合)，相較之下如果所有系統都共同遵循同一套標準，每個系統只需要各自獨立實作一次對這套共通標準的支援，就能自動和所有其他遵循這套標準的系統協作，這種把協作成本從和系統數量的平方成正比降低到和系統數量的一次方成正比的效益，正是標準化協定之所以能帶來如此顯著整體效率提升的核心數學道理」，展現你能用一個更具體、量化的論證，去解釋標準協定的核心價值，而不僅是籠統地說標準協定比較方便。

**面試回答方式**：先明確給出核心答案——「並不是完全無法協作，即使沒有標準協定，依然可以透過額外撰寫客製化的轉接橋接程式碼，讓不同框架建構的Agent彼此勉強溝通協作」。給出這種做法的成本問題——「這種做法每多一組需要協作的不同框架系統，就需要一組專門的客製化轉接程式碼，隨著需要協作的系統數量增加，這種維護成本會以接近平方級數的速度增長，N個系統兩兩配對最多可能產生到接近N平方量級的轉接組合」。給出標準協定的效益——「標準化協定把這種每一對系統都需要各自客製化轉接的問題，簡化成每一個系統只需要實作一次對這套共通標準的支援，就能自動和所有其他系統協作，把協作成本從和系統數量的平方成正比，降低到和系統數量的一次方成正比，這正是標準化協定之所以重要的核心數學道理」。

### A2A 這類 Agent 間通訊協定，在設計上需不需要額外考慮前面 AI 大模型類別已經深入討論過的 Prompt Injection 這類安全風險？

**核心答案**：**需要，而且這是一個相當值得被特別重視的風險考量**——延續前面（見 [[../ai-llm/023-prompt-injection.md]]）已經深入討論過的核心洞察，Prompt Injection 之所以難以被徹底根除，關鍵在於模型**缺乏一種可靠的機制去明確地區分「應該被信任、遵從的指令」和「只是需要被參考處理的資料」**，這個核心風險在**多個 Agent 彼此透過標準協定溝通、傳遞訊息**這個情境下**只會變得更加嚴峻**——因為一個 Agent 接收到的來自**另一個 Agent** 傳遞過來的訊息內容，很可能就是這個 Agent 接下來推理決策時所要參照的『輸入』，如果這個傳遞訊息的另一個 Agent 本身已經遭到惡意內容的污染，或者這兩個 Agent 之間的通訊管道被惡意的第三方攔截、竄改，這種**惡意注入的內容**就有可能**沿著 Agent 和 Agent 之間的通訊鏈路被層層傳播擴散**。因此設計 Agent 間的通訊協定時**必須**額外地考量**如何驗證訊息來源的真實性、如何避免惡意內容透過合法的通訊管道被注入擴散**這類安全性設計。

**詳細解析**：這題要求把前面在 AI 大模型類別裡已經深入討論過的 **Prompt Injection** 這個核心安全議題**具體地延伸應用到 Agent 間通訊這個多代理系統特有的新場景**，考察是否理解這個已經建立的核心風險認知並不會因為換了一個新的技術情境就自動地消失，反而可能因為**多代理系統引入的額外通訊複雜度**而衍生出**新的、更複雜的攻擊面**。理解這個問題的核心在於回顧前面（見 [[../ai-llm/023-prompt-injection.md]]）已經深入討論過的**間接注入（Indirect Prompt Injection）**這種特別危險的攻擊型態——攻擊者**不需要直接地**作為使用者去和目標模型互動，而是**把惡意指令事先埋藏在某個模型很可能會去讀取、參照的外部資料來源裡**。把這個核心洞察遷移到多代理系統的情境裡，可以推導出一個**新的、值得被高度警惕的攻擊路徑**——如果**一個多代理系統裡的其中一個 Agent**（例如一個負責讀取、處理外部網頁內容的 Agent）因為處理到某個**被攻擊者事先動過手腳的外部資料**而遭到 Prompt Injection 攻擊污染，這個被污染的 Agent 接下來**在把它自己處理後的結果傳遞給系統裡的其他 Agent** 時（這正是多代理系統裡 Agent 間通訊協定所負責的環節），很可能**會把這個被惡意注入的內容一併夾帶著傳遞出去**，導致**原本只是污染了單一一個 Agent 的攻擊，透過 Agent 間通訊這個管道被進一步地擴散、傳播到整個多代理系統裡的其他 Agent**。這種**「攻擊可以跨越單一 Agent 的邊界，沿著 Agent 間的通訊鏈路層層擴散」**的風險某種程度上是多代理系統這種**由多個獨立節點彼此緊密連結**的架構所特有的、比單一 Agent 情境更加複雜的新挑戰（這某種程度上也類似傳統資安領域裡『一個被攻陷的節點可能被用來作為跳板，進一步地攻擊、滲透整個網路裡的其他節點』這種橫向移動（Lateral Movement）攻擊模式的概念，在多代理系統這個新情境下的一種具體展現）。因應這種風險，設計 Agent 間通訊協定時，除了前面（見核心答案）已經提到的需要驗證訊息來源真實性以外，也需要考量**引入類似前面（見 [[../ai-llm/023-prompt-injection.md]]）已經討論過的『對高風險操作設置人工確認機制』、『權限最小化原則』這些在單一 Agent 情境下已經建立的核心防範原則**，並把它們**恰當地延伸套用到多代理系統這個涉及多個節點、且攻擊可能跨節點傳播的更複雜情境**上——例如即使某個子 Agent 傳遞過來的訊息看起來似乎要求執行某個高風險操作，接收方的 Agent（或者負責統籌的主管型 Agent）依然**不應該無條件地直接信任、執行這個請求**，而應該同樣地套用恰當的人工確認或審查機制才觸發實際的高風險操作。理解「Agent間通訊需要考量Prompt Injection這類安全風險，而且這個風險在多代理系統情境下只會變得更嚴峻，因為一個Agent接收到來自另一個Agent的傳遞訊息，很可能就是它接下來推理決策的輸入，如果傳遞方的Agent已經因為處理到被攻擊者動過手腳的外部資料而遭到間接注入污染，這個被污染的內容在它把處理結果傳遞給系統裡其他Agent時，很可能會被一併夾帶傳遞出去，導致攻擊沿著Agent間通訊鏈路層層擴散到整個多代理系統，這種攻擊可以跨越單一Agent邊界擴散的風險，某種程度上類似傳統資安領域裡被攻陷節點可能被用作跳板進行橫向移動攻擊其他節點的概念，因應這種風險，設計協定時除了驗證訊息來源真實性，也需要把之前已經建立的對高風險操作設置人工確認、權限最小化這些核心防範原則，恰當延伸套用到多代理系統這個涉及多節點且攻擊可能跨節點傳播的更複雜情境上」，展現你能把已經深入討論過的Prompt Injection核心風險，正確且有洞察力地延伸應用到多代理系統這個全新的、更複雜的技術情境。

**面試回答方式**：先給出核心答案——「需要，而且這是一個相當值得被特別重視的風險考量，因為之前討論過的Prompt Injection核心風險，在多個Agent彼此透過標準協定溝通這個情境下只會變得更嚴峻」。具體解釋攻擊如何跨Agent擴散——「如果多代理系統裡的其中一個Agent，因為處理到被攻擊者動過手腳的外部資料而遭到間接注入污染，這個被污染的Agent在把自己處理後的結果傳遞給系統裡其他Agent時，很可能會把惡意注入的內容一併夾帶傳遞出去，導致原本只污染單一Agent的攻擊，沿著Agent間通訊鏈路層層擴散到整個多代理系統，這某種程度上類似傳統資安裡被攻陷節點被用作跳板進行橫向移動攻擊的概念」。給出因應做法——「設計協定時需要驗證訊息來源的真實性，也需要把之前建立的對高風險操作設置人工確認、權限最小化這些核心防範原則，延伸套用到多代理系統這個更複雜的情境上，即使某個子Agent傳來的訊息看起來要求執行高風險操作，接收方也不應該無條件直接信任執行」。

### Agent 間通訊如果需要透過網路（而非在同一台機器裡的直接函式呼叫），這會額外引入哪些需要被考量的實務工程議題？

**核心答案**：一旦 Agent 間的通訊需要跨越網路（而不是單純在同一個行程或機器裡的直接函式呼叫），就會額外引入**幾乎所有傳統分散式系統設計裡都需要面對的經典工程議題**——**(1) 網路延遲和逾時**：透過網路的溝通天生比本機的直接函式呼叫慢，需要設計恰當的**逾時（Timeout）**機制，避免一個遲遲沒有回應的對方 Agent 讓整個流程無限期地卡住；**(2) 訊息可能遺失或重複**：網路傳輸本身並不保證百分之百可靠，訊息可能遺失，或者因為重試機制而被重複傳送，需要設計恰當的**重試和冪等性（Idempotency）**處理；**(3) 部分失敗（Partial Failure）**：在一個涉及多個透過網路溝通的 Agent 的流程裡，可能發生**其中某些 Agent 成功回應、但另一些 Agent 失敗或沒有回應**這種部分成功、部分失敗的情況，需要額外的邏輯去妥善處理這種不上不下的中間狀態。

**詳細解析**：這題要求把 Agent 間通訊這個議題**具體地連結到傳統分散式系統設計領域早已累積大量成熟經驗**的一系列經典工程挑戰，考察是否能夠**避免把 Agent 間通訊視為一個全新、獨立於既有工程知識體系之外的全新問題**，而能夠看出**多代理系統一旦涉及跨網路的 Agent 間通訊，本質上就是一種分散式系統**，因此**幾乎所有傳統分散式系統設計已經深入研究累積的核心挑戰和最佳實務都同樣適用**。理解這個問題的核心在於認識到——**只要是跨越網路的溝通（不管溝通的雙方是兩個傳統的微服務，還是這裡討論的兩個 Agent）**都會天然地面臨**網路本身固有的不可靠性**這個根本挑戰（這某種程度上呼應了分散式系統理論裡一個經典的告誡——**『網路永遠不能被假設是完全可靠的』**）——**延遲**意味著**不能假設一個請求會立即得到回應**，需要設計合理的逾時和等待策略；**訊息可能遺失或重複**意味著**不能假設『我發送了一個訊息』就等同於『對方一定會收到，且只收到一次這個訊息』**，需要設計**重試機制**（當懷疑訊息可能遺失時重新發送），但重試機制本身又會帶來**訊息可能被重複收到**的新問題，這就需要額外的**冪等性設計**（確保即使同一個訊息或請求被處理多次，最終產生的效果和只被處理一次是相同的，不會因為重複處理而產生錯誤的副作用，例如重複執行某個具備實際金錢交易後果的操作）；**部分失敗**則是分散式系統裡一個**特別棘手、也特別容易被新手忽略**的問題——在一個只涉及單一個行程、單一台機器的系統裡，一個操作通常要嘛完全成功、要嘛完全失敗，不太會出現**『一部分成功、另一部分失敗』**這種模糊的中間狀態；但一旦這個操作涉及**多個透過網路彼此溝通的獨立節點**，這種**部分失敗**的情況就變得相當常見（例如一個主管型 Agent 同時向三個不同的子 Agent 發出委派請求，其中兩個子 Agent 順利回應，但第三個子 Agent 因為網路問題或者它自身發生故障而遲遲沒有回應）。這種情況下**這個主管型 Agent 應該如何因應**（是繼續無限期等待那個沒有回應的第三個子 Agent；還是在等待一段合理的時間之後判斷這個第三個子 Agent 可能已經失敗，轉而採取某種替代方案，或者如實地向使用者回報這個部分失敗的狀況），這種**需要能夠妥善處理『部分失敗』這種模糊中間狀態**的設計要求，正是分散式系統設計裡一個相當核心、且需要被特別重視的挑戰。理解到**Agent 間通訊一旦涉及網路就是一種分散式系統**這個核心洞察之後，就能清楚地看出**設計一個穩健的多代理系統，需要同時具備 Agent 架構本身的知識，以及傳統分散式系統工程的既有知識和最佳實務**，而不是只把多代理系統當作一個**純粹獨立於既有分散式系統工程知識體系之外**的全新領域。理解「一旦Agent間通訊需要跨越網路，就會引入幾乎所有傳統分散式系統設計裡都需要面對的經典工程議題，包括網路延遲需要恰當逾時機制、訊息可能遺失或重複需要重試和冪等性處理、以及部分失敗這種某些Agent成功回應但另一些失敗的模糊中間狀態需要額外邏輯妥善處理，這些都呼應了分散式系統理論裡網路永遠不能被假設完全可靠這個經典告誡，理解到Agent間通訊一旦涉及網路就是一種分散式系統這個核心洞察，就能看出設計一個穩健的多代理系統需要同時具備Agent架構本身的知識、以及傳統分散式系統工程的既有知識和最佳實務，而不是把多代理系統當作一個純粹獨立於既有工程知識體系之外的全新領域」，展現你能把Agent間通訊這個新興議題，正確連結到分散式系統這個早已累積大量成熟經驗的既有工程知識體系，而非把它當成孤立的全新領域。

**面試回答方式**：先給出三個核心議題的框架——「一旦Agent間通訊需要跨越網路，會引入幾乎所有傳統分散式系統設計裡都需要面對的經典工程議題，包括網路延遲和逾時、訊息可能遺失或重複、以及部分失敗」。逐一展開解釋——「延遲方面，需要設計恰當的逾時機制，避免遲遲沒有回應的對方Agent讓整個流程無限期卡住;訊息可靠性方面，需要重試機制來因應可能的遺失，但重試又會帶來重複收到的新問題，需要額外的冪等性設計確保重複處理不會產生錯誤副作用;部分失敗方面，在涉及多個透過網路溝通的Agent流程裡，可能出現某些Agent成功回應、但另一些失敗或沒回應這種模糊的中間狀態，需要額外邏輯妥善處理」。給出結論——「這些都呼應了分散式系統理論裡網路永遠不能被假設完全可靠這個經典告誡，設計一個穩健的多代理系統，需要同時具備Agent架構本身的知識、以及傳統分散式系統工程的既有知識和最佳實務」。
