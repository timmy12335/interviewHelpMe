# 題目

Agent 的錯誤處理跟一般服務有什麼不同？

## 核心答案

最大的不同是「錯誤是給模型看的，而模型會自己決定怎麼反應」——**這既是機會也是風險**。

**機會**：一個好的錯誤訊息能讓 Agent 自我修正（改參數、換工具、換方法）——而傳統服務只能按預設的邏輯處理。

**風險**：**模型的反應是不可預測的**——它可能重試（可能不冪等）、可能繞路（做了你不希望的事）、也可能放棄並編一個答案。

**所以設計上有三條原則**。**錯誤訊息要是可行動的指引**（錯在哪、正確的形式、建議下一步）。危險的重試要在工具層面被阻止（冪等鍵、寫入操作的去重）——不能靠提示告訴模型「不要重試」。而「不可恢復的錯誤」要明確標示——讓模型知道「這條路走不通，不要再試」，否則它會反覆嘗試。

## 詳細解析

「區分可重試與不可重試」應該在錯誤訊息中明確表達：`429 Too Many Requests` 是可重試的（等一下再試）；`404 Not Found` 通常不是（同樣的請求還是找不到）；`403 Forbidden` 完全不是（權限問題，重試一百次也一樣）。如果錯誤訊息只說「失敗」，模型無法區分，於是會用同一種方式處理所有錯誤——通常就是重試，而那對後兩者是純粹的浪費。在錯誤訊息中加一句「這個錯誤無法透過重試解決，請改用其他方法或告知使用者」，能顯著改善 Agent 的行為。

**「部分成功」是 Agent 特有的困難**：一個操作做了一半失敗——**模型不知道做了哪一半**。傳統服務可以用交易回滾，而 Agent 呼叫的工具往往跨越多個系統。處理的原則是「讓工具的粒度對應一個原子的操作」——如果一個工具內部要做三件不可分割的事，那三件事應該在工具內部用交易或補償保證原子性，而不是暴露中間狀態給模型。因為模型無法可靠地處理「做了一半」的狀態。

「失敗的重試會消耗預算」是一個實際的成本問題：每次重試都是一次完整的模型呼叫——在一個會自動重試的 Agent 中，一個持續失敗的下游服務可能燒掉大量的錢。所以重試必須有次數上限，而且應該在框架層強制而非依賴模型的判斷。

「錯誤要被記錄為可分析的事件」：不只是寫進日誌——**應該有結構化的統計**（哪個工具、哪類錯誤、發生頻率）。因為 Agent 的錯誤模式會隨提示、模型、工具的變更而改變——沒有統計就無法發現「某次改動之後某類錯誤翻倍了」。

## 面試回答方式

先給最大的不同——錯誤是給模型看的而模型會自己決定怎麼反應，並拆成機會與風險兩面，再給三條設計原則。加分點有四個：區分可重試與不可重試要在錯誤訊息中明確表達——只說「失敗」的話模型會用同一種方式處理所有錯誤，通常就是重試，而加一句「這個錯誤無法透過重試解決」能顯著改善行為；**「部分成功」是 Agent 特有的困難**——模型無法可靠處理「做了一半」的狀態，所以工具的粒度要對應一個原子操作，內部用交易或補償而不暴露中間狀態；**失敗的重試會消耗預算**，必須在框架層強制上限而非依賴模型判斷；以及**錯誤要有結構化統計**，否則無法發現某次改動之後某類錯誤翻倍。

## 講稿

最大的不同是錯誤是給模型看的，而模型會自己決定怎麼反應。這既是機會也是風險。

機會是一個好的錯誤訊息能讓代理自我修正，改參數、換工具、換方法。風險是模型的反應不可預測，它可能重試、可能繞路做了你不希望的事、也可能放棄並編一個答案。

所以我有三條原則。第一，錯誤訊息要是可行動的指引。而且要區分可不可重試。速率限制是可重試的，找不到通常不是，權限不足完全不是。如果只說失敗，模型無法區分，就會用同一種方式處理所有錯誤，通常就是重試，而那對後兩者是純粹的浪費。加一句這個錯誤無法透過重試解決，能顯著改善行為。

第二，危險的重試要在工具層面被阻止，用冪等鍵或服務端去重，不能靠提示告訴模型不要重試。

第三，部分成功是代理特有的困難，因為模型無法可靠處理做了一半的狀態。所以工具的粒度要對應一個原子操作，內部用交易或補償保證，而不要把中間狀態暴露給模型。

## 常見追問

### Agent 遇到錯誤時編造答案怎麼防？

**核心答案**：**三層**。**提示層**——明確要求「工具失敗時必須告知使用者，不要用你的知識替代」。**驗證層**——檢查答案是否有工具回傳的支撐（**與 RAG 的忠實度檢查同一個機制**）。**結構層**——讓最終回應必須引用具體的工具結果，沒有結果就無法產生合法的回應。

**詳細解析**：「結構層」是最可靠的，因為它不依賴模型的自覺：如果最終答案必須以一個結構化的格式產出，其中包含「依據的工具呼叫 ID」欄位——那麼沒有成功的工具呼叫就填不出這個欄位。這把「不要編造」從一個請求變成一個約束。而更廣的原則是「用結構強制行為，而不是用提示請求行為」——這在所有需要可靠性的地方都適用。至於為什麼模型會編造：它被訓練成盡力回應，而「我做不到」在偏好資料中往往被評為較差的回答——所以這是一個訓練層面的傾向，靠提示只能部分抵銷。理解這個成因，能解釋為什麼提示層的要求總是不夠可靠。

**面試回答方式**：給三層防護。核心加分點是指出結構層最可靠因為它不依賴模型的自覺——最終答案必須包含「依據的工具呼叫 ID」欄位，沒有成功呼叫就填不出來，這把「不要編造」從請求變成約束，並提煉原則：用結構強制行為而非用提示請求行為。收在成因：模型被訓練成盡力回應，而「我做不到」在偏好資料中往往被評為較差——所以這是訓練層面的傾向，靠提示只能部分抵銷。

### 工具的暫時性故障怎麼處理最好？

**核心答案**：在工具層面自己重試，不要讓錯誤傳到模型。網路抖動、限流、暫時的服務不可用——這些用指數退避重試幾次通常就解決了，而讓模型看到並自己決定重試是浪費（一次模型呼叫的成本遠高於一次 HTTP 重試）。只有重試耗盡之後才把錯誤回傳給模型。

**詳細解析**：「什麼該由工具處理、什麼該讓模型知道」是一個重要的分層判斷：技術性的、有標準處理方式的錯誤（網路、限流、逾時）應該在工具層被吸收；語義性的、需要改變策略的錯誤（參數不對、找不到資源、權限不足）才應該讓模型看到。混淆這兩者的後果是：要嘛模型被大量技術噪音干擾（浪費 token 與步數），要嘛真正需要它決策的錯誤被工具層默默吞掉（更糟）。而判斷的標準很簡單：問「模型看到這個錯誤能做出什麼不同的決定嗎」——**不能的話就不該讓它看到**。這個判準同時避免了兩種錯誤，而且它可以逐個工具地應用。

**面試回答方式**：主張在工具層面自己重試不要讓錯誤傳到模型，並給理由（一次模型呼叫的成本遠高於一次 HTTP 重試）。核心加分點是給出分層判斷：技術性、有標準處理方式的錯誤在工具層吸收，語義性、需要改變策略的才讓模型看到，並指出混淆的兩種後果。收在判準：問「模型看到這個錯誤能做出什麼不同的決定嗎」——**不能的話就不該讓它看到**。

### 怎麼設計「不確定操作是否成功」的情況？

**核心答案**：與分散式系統的處理完全一樣：查詢而非猜測。工具呼叫逾時了——**不知道對方執行了沒有**。正確的做法是提供一個「查詢狀態」的工具，並在錯誤訊息中明確指引「請先查詢該操作的狀態再決定是否重試」——**而不是讓模型自己判斷**。

**詳細解析**：「逾時的處理」是 Agent 中最容易造成重複操作的地方：模型看到逾時的直覺反應是重試——而如果那是一個轉帳或下單操作，重試就是災難。所以寫入類工具的逾時錯誤訊息必須明確：「操作狀態未知，請勿直接重試，請先呼叫 check_order_status 確認」——把正確的處理路徑直接寫進錯誤訊息裡。**而更根本的保護仍然是冪等**：如果工具本身用同一個冪等鍵是冪等的，那麼即使模型直接重試也是安全的——這是唯一不依賴模型行為的保護。所以設計的優先順序是：先讓工具冪等（結構保證），再寫好錯誤指引（行為引導）——**兩者都做，但前者是底線。**

**面試回答方式**：給核心做法（查詢而非猜測，提供查詢狀態的工具並在錯誤訊息中指引）。核心加分點是指出逾時是最容易造成重複操作的地方——模型的直覺反應是重試，而那對轉帳或下單是災難，所以錯誤訊息要把正確的處理路徑直接寫進去。收在優先順序：**更根本的保護是冪等**——工具冪等的話即使模型直接重試也安全，這是唯一不依賴模型行為的保護，所以先讓工具冪等再寫好錯誤指引，兩者都做但前者是底線。
