# 題目

什麼是「ReAct（Reasoning + Acting）」模式？它是如何把前面（見 [[../ai-llm/021-chain-of-thought.md]]）已經討論過的 Chain of Thought 推理能力，和 Agent 實際執行行動的能力結合在一起的？

## 核心答案

ReAct 是一種 Agent 架構模式，它的核心做法是讓大型語言模型在執行任務的每一輪循環裡**明確地、以文字的形式交替地生成「思考（Thought）」、「行動（Action）」、「觀察（Observation）」這三種類型的內容**——**思考**是模型針對當前的任務狀態，用類似前面（見 [[../ai-llm/021-chain-of-thought.md]]）討論過的 Chain of Thought 方式，明確地把自己的推理過程、對當前狀況的判斷、以及接下來打算怎麼做用文字表達出來；**行動**是模型依照這個思考過程的結論，決定要呼叫哪一個具體的工具（以及需要提供哪些參數）；**觀察**則是這個被呼叫的工具實際執行後回傳的結果，這個結果會被重新餵回給模型，作為**下一輪思考**的輸入依據。這種「思考→行動→觀察」反覆交替循環的模式之所以重要，核心價值在於——它讓 Agent 在**每一次決定要採取什麼行動之前都先明確地把推理過程展開出來**，這某種程度上是把前面（見 [[../ai-llm/021-chain-of-thought.md]]）已經深入討論過的 CoT『讓模型把運算分散展開到多個詞元，而非壓縮進單一詞元』這個核心效益**具體地套用到 Agent 決定下一步行動這個關鍵決策點上**，讓 Agent 的每一個行動決策都是建立在一個明確、可以被檢視的推理過程之上，而不是模型未經任何展開的中間推理就直接跳到某個行動決策。

## 詳細解析

**ReAct 名稱裡「Re」和「Act」的具體對應，以及為什麼兩者需要交替、而非分開各自單獨執行**：ReAct 這個名字本身就直接點出了它融合的兩個核心能力——**Reasoning（推理）**對應模型用文字展開中間思考過程的能力（如前面已經深入討論的 CoT）；**Acting（行動）**對應模型實際地去呼叫工具、執行操作的能力（如前面已經深入討論的 Function Calling）。ReAct 的關鍵洞察在於**這兩種能力如果被交替、緊密地結合在一起運作，會比把它們完全分開各自獨立運作更加有效**——如果只有**推理**而沒有**行動**（單純的 CoT，沒有搭配任何工具呼叫能力），模型只能依靠自己內化且可能已經過時、不完整的知識去進行推理，沒有辦法取得任何即時、外部的實際資訊來驗證、修正自己的推理；反過來，如果只有**行動**而沒有明確地展開**推理**（模型直接依照某種不透明的內部判斷就決定要呼叫哪個工具，而沒有把這個判斷背後的思考過程明確地表達出來），這種做法某種程度上會喪失前面（見 [[../ai-llm/021-chain-of-thought.md]]）已經深入討論過的 CoT 所能帶來的效益（把複雜運算分散展開到多個詞元，而非壓縮進單一次的決策），也會讓這個行動決策的過程變得**難以被人類事後檢視、除錯**（如果 Agent 做出了一個不恰當的行動，卻沒有任何明確展開的推理過程可以被檢視，會很難判斷這個不恰當的決策究竟是哪個環節出了問題）。ReAct 透過**要求模型在每一次決定行動之前都先明確地展開一段思考**，同時兼顧了**推理品質的提升**以及**整個決策過程的可追溯、可檢視性**這兩個重要的價值。

**觀察（Observation）這個環節的關鍵作用——讓 Agent 的推理建立在真實、即時的外部回饋之上**：ReAct 架構裡容易被忽略、但實際上相當關鍵的一個環節是**觀察**——模型每執行完一個行動（呼叫一個工具）之後**不是直接就決定下一個行動**，而是會先把這個行動實際執行後得到的結果（觀察）**重新納入接下來的思考過程裡**。這種設計確保了 Agent 的每一輪思考都是**建立在最新、最真實的外部世界回饋之上**，而不是單純地依照模型自己一開始一廂情願的假設持續往下推演（如果沒有這種把真實的外部觀察結果重新納入思考過程的機制，Agent 可能會在第一步行動的結果其實不如預期的情況下，卻依然錯誤地假設這一步已經順利成功，繼續基於這個錯誤的假設往下執行後續的步驟，導致整個任務逐漸地偏離正確的軌道）。這種「用真實觀察持續地校正接下來的思考和行動」的機制，是讓 ReAct 這種架構能夠具備某種程度的**自我修正**能力（即使某一步行動的結果不如預期，Agent 也有機會在下一輪的思考裡注意到這個不如預期的觀察結果，進而調整接下來的策略，而不是盲目地依照原本的計畫一路錯到底）的關鍵設計。

**ReAct 的實務侷限——每一輪都展開完整思考所帶來的額外運算和時間成本**：ReAct 這種**要求每一次行動之前都明確地展開一段思考**的做法雖然帶來前面已經討論過的推理品質和可檢視性的提升，但也存在一個需要被權衡考量的代價——**每一輪額外展開的思考內容都意味著額外的模型推理呼叫，以及額外的時間延遲**。如果一個任務需要經過非常多輪的行動才能完成，這種『每一輪都要求完整展開思考』的做法累積起來可能會帶來相當可觀的整體執行時間和運算成本。這種「推理品質的提升」和「額外的運算／時間成本」之間的權衡取捨，是實務上在決定是否要採用 ReAct 這種模式、以及如何具體調校它的運作細節時（例如是否需要針對某些相對簡單、不太需要複雜推理的行動，允許跳過完整的思考展開步驟）需要被仔細納入考量的實務因素。

## 面試回答方式

先給出ReAct的核心做法——「讓大型語言模型在執行任務的每一輪循環裡，明確地以文字形式交替生成思考、行動、觀察這三種內容，思考是模型用類似Chain of Thought的方式展開推理過程，行動是依照這個推理決定要呼叫哪個工具，觀察則是這個工具實際執行後回傳的結果，會被重新餵回作為下一輪思考的輸入依據」。解釋核心價值——「這是把之前討論過的CoT核心效益(讓模型把運算分散展開到多個詞元而非壓縮進單一詞元)，具體套用到Agent決定下一步行動這個關鍵決策點上，讓每一個行動決策都建立在明確、可被檢視的推理過程之上」。可以補充「觀察」環節的關鍵作用——「這個環節確保Agent的每一輪思考都建立在最新、真實的外部世界回饋之上，而不是單純依照一開始的假設持續推演，這種用真實觀察持續校正思考和行動的機制，讓ReAct具備某種程度的自我修正能力」。可以誠實補充實務侷限——「每一輪都要求完整展開思考，也意味著額外的推理呼叫和時間延遲，累積起來可能帶來相當可觀的整體執行成本，這是實務上需要權衡的取捨」，展現你對ReAct不僅理解其運作機制，也理解其設計動機與實務代價的完整認知。

## 常見追問

### ReAct 裡的「思考」步驟，如果模型在思考過程中出現了前面已經討論過的 CoT 不忠實性問題（展開的文字推理和實際內部決策過程不一致），這會對整個 ReAct 流程造成什麼樣的影響？

**核心答案**：**會帶來相當值得關注的潛在風險**——如果模型在 ReAct 的「思考」步驟裡展開的文字內容，和它實際上真正用來決定下一步行動的內部判斷過程存在前面（見 [[../ai-llm/021-chain-of-thought.md]]）已經深入討論過的『不忠實性』落差，這意味著**即使這段展開的思考文字看起來邏輯通順、推理嚴謹**，實際上被執行的那個『行動』也未必真的是依循這段展開的推理過程而得出的決策。這會讓**單純依靠檢視 ReAct 展開的思考文字去判斷一個 Agent 的決策是否合理、可信**這件事變得**不如表面上看起來那麼可靠**。因應這種風險，實務上更穩健的做法是**除了檢視思考文字本身以外，更應該重視實際執行行動之後得到的『觀察』結果是否真的朝著任務目標推進**，而不是單純地因為展開的思考文字讀起來合理就過度地信任這個 Agent 的整體決策品質。

**詳細解析**：這題要求把前面已經深入討論過的 CoT 不忠實性這個侷限（見 [[../ai-llm/021-chain-of-thought.md]] 的常見追問）**具體地延伸應用到 ReAct 這個把 CoT 套用在行動決策情境的架構模式上**，考察是否能識別出這個已經在別的情境下討論過的侷限同樣會對 ReAct 這個更具體的應用場景帶來類似的影響，而不是誤以為把 CoT 套用到行動決策上之後，這個原本已知的侷限就自動地消失了。回顧 CoT 不忠實性這個核心發現——模型展開輸出的文字推理內容**未必**忠實地反映它實際上內部真正依循的決策過程，模型有可能是先透過某種和展開文字不盡相同的內部機制得出一個（可能是正確、也可能是錯誤的）初步傾向，再**事後**生成一段看起來合理、且恰好能夠導向這個傾向的文字說明。這個核心發現套用到 ReAct 的具體情境裡意味著——**ReAct 展開的『思考』文字內容可能也只是模型事後用來包裝、解釋它（透過某種不透明的內部機制）已經傾向的那個行動決策的一段文字說明，而不必然是這個行動決策真正被決定出來的忠實過程**。這帶來一個相當實務、且值得警惕的推論——**單純地因為一個 Agent 在某一輪展開的思考文字讀起來邏輯通順、推理嚴謹，就過度地信任它接下來要執行的那個行動一定是妥當、正確的**，這種推論方式本身存在風險（就像前面 CoT 章節已經討論過的『文字看起來合理，和答案實際上正確，是兩件不完全等同的事情』這個核心告誡，在 ReAct 的具體情境裡可以被重新表達成『思考文字看起來合理，和接下來的行動實際上恰當，是兩件不完全等同的事情』）。因應這種風險，實務上一個更穩健、也更貼近 ReAct 架構本身精神的做法，是**格外重視『觀察』這個環節所回傳的實際、客觀的執行結果**——不管一輪的『思考』文字讀起來多麼言之成理，真正能夠客觀、可靠地反映這一步行動是否真的朝著任務目標有效推進的依據，終究是這個行動**實際執行之後得到的具體、客觀的觀察結果**（例如如果 Agent 執行了一個查詢動作，這個查詢動作是否真的取得了有意義、和任務相關的資訊，這件事可以透過客觀地檢視查詢結果本身來判斷，而不需要完全仰賴模型自己在思考文字裡如何描述、評價這一步的意義）。這種**「重視客觀的執行結果，而不是只信任主觀展開的思考文字」**的判斷原則，某種程度上也呼應了一個更普遍的實務智慧——**評估一個系統的實際表現，應該優先依靠客觀、可驗證的結果指標，而不是單純依靠這個系統自己對自己行為的文字描述或解釋**。理解「ReAct的思考步驟同樣可能存在CoT不忠實性問題，展開的文字推理未必忠實反映模型內部真正的決策過程，這意味著單純依靠檢視ReAct展開的思考文字去判斷Agent決策是否合理可信，會不如表面上看起來那麼可靠，因應這種風險，實務上更穩健的做法是格外重視觀察環節所回傳的實際客觀執行結果，而不是單純因為思考文字讀起來合理就過度信任接下來的行動一定妥當，這呼應了評估一個系統實際表現應該優先依靠客觀可驗證結果指標，而非單純依靠系統自己對自身行為的文字描述這個更普遍的實務智慧」，展現你能把之前已經深入討論過的CoT侷限，正確地遷移應用到ReAct這個新的具體架構情境上，而非把兩者當成無關的獨立主題。

**面試回答方式**：先給出核心答案——「會帶來相當值得關注的潛在風險，如果模型在思考步驟展開的文字內容和它實際內部真正用來決定行動的判斷過程存在CoT已經討論過的不忠實性落差，即使思考文字看起來邏輯通順，實際被執行的行動也未必真的是依循這段推理過程而得出的決策」。指出這帶來的實務影響——「這讓單純依靠檢視ReAct展開的思考文字去判斷一個Agent決策是否合理可信，變得不如表面上看起來那麼可靠」。給出更穩健的因應做法——「實務上更應該重視觀察環節回傳的實際、客觀執行結果，而不是單純因為思考文字讀起來合理，就過度信任這個Agent的整體決策品質，這呼應了評估系統實際表現應該優先依靠客觀可驗證結果、而非系統自己對自身行為文字描述的更普遍實務智慧」。

### ReAct 和前面提到 Agent 常見的另一種架構模式 Plan-and-Execute，最核心的運作方式差異是什麼？

**核心答案**：**核心差異在於「規劃和行動這兩件事是交錯緊密地穿插進行，還是先一次性完整地規劃好再依序執行」**——**ReAct** 是**每執行完一個行動（取得一次觀察結果）之後才重新進行下一輪的思考和規劃**，也就是說**規劃（思考）和行動是以非常細緻的顆粒度緊密地交錯進行**；而 **Plan-and-Execute**（見 [[008-plan-and-execute.md]] 將更深入討論）則是**先在任務一開始的階段就一次性地把完成這個任務所需要的完整步驟序列規劃、列舉出來，再依序地去執行這些已經被事先規劃好的步驟**，也就是說**規劃這件事主要發生在任務最初的一個獨立階段，而後續的執行階段主要是依照這個已經規劃好的步驟清單逐一執行**。這種「規劃和行動顆粒度細緻交錯」對比「規劃和行動分成先後兩個較為獨立的大階段」的核心差異，會進一步衍生出兩種架構在**應對執行過程中意外狀況的靈活度**、以及**整體執行效率**這兩個面向上各自不同的優缺點取捨。

**詳細解析**：這題簡要地預告、對比下一題（見 [[008-plan-and-execute.md]]）將更深入探討的 Plan-and-Execute 架構，考察是否能夠在剛認識完 ReAct 這個架構之後，就具備一定的比較視野，去初步理解 Agent 架構模式並非只有唯一一種選擇。理解這個核心差異的關鍵在於聚焦在**「規劃／思考」和「執行／行動」這兩個環節在時間軸上是如何被安排**這個面向——ReAct 的做法某種程度上可以被理解成**一種『邊做邊想』的模式**——它並不會在任務一開始就試圖一次性地把整個任務所有可能需要的步驟都完整地規劃出來，而是**每完成一個具體的行動、取得一次實際的觀察結果之後，才重新依照這個最新的觀察結果去思考、決定接下來這唯一的下一步應該是什麼**。這種做法的優勢在於**高度的靈活性**——因為每一步的規劃都是緊密地建立在最新的實際觀察結果之上，Agent 能夠非常即時地依照執行過程中實際遇到的任何意外狀況動態地調整接下來的策略；但這種做法也存在一個潛在的侷限——因為 Agent **在任務一開始並沒有一個對整個任務完整的、全局性的規劃視野**（它每一次只是決定緊接著的下一步該做什麼，而不是一次性地思考清楚完成整個任務所需要的完整步驟藍圖），這某種程度上可能會導致 Agent 在執行一個**本身具備較高複雜度、涉及許多環環相扣的子任務**的大型任務時，因為缺乏這種一開始就建立好的全局規劃視野，而在執行過程中某些情況下**做出一些從更宏觀、全局的角度來看並非最有效率、甚至可能需要事後修正的局部決策**（相較之下，Plan-and-Execute 這種先一次性地建立好完整規劃、再依序執行的模式，詳見下一題的深入討論，在這種需要**全局規劃視野**的情境下可能具備一定的優勢，但相對地在面對執行過程中的意外狀況時，可能不如 ReAct 這種邊做邊想的模式來得靈活）。理解「ReAct和Plan-and-Execute的核心差異在於規劃和行動這兩件事，是交錯緊密穿插進行、還是先一次性完整規劃好再依序執行，ReAct是每執行完一個行動取得一次觀察結果之後才重新進行下一輪思考，規劃和行動以非常細緻的顆粒度緊密交錯，這種邊做邊想的模式優勢是高度靈活、能即時依照實際觀察動態調整，但侷限是缺乏對整個任務的全局規劃視野，可能在執行複雜任務時做出並非最有效率的局部決策，這也預告了Plan-and-Execute這種先建立全局規劃再依序執行的替代架構，在需要全局視野的情境下可能具備的優勢」，展現你具備比較不同Agent架構模式的視野，而非把ReAct當成唯一的架構選擇。

**面試回答方式**：先給出核心差異——「核心差異在於規劃和行動這兩件事，是交錯緊密穿插進行、還是先一次性完整規劃好再依序執行，ReAct是每執行完一個行動取得一次觀察結果之後，才重新進行下一輪思考，規劃和行動以非常細緻的顆粒度緊密交錯;而Plan-and-Execute是先在任務一開始就一次性地把完整步驟序列規劃列舉出來，再依序執行這些已經規劃好的步驟」。分析ReAct這種模式的優缺點——「ReAct這種邊做邊想的模式，優勢是高度靈活，能非常即時地依照實際觀察結果動態調整接下來的策略;但侷限是缺乏對整個任務的全局規劃視野，可能在執行複雜、涉及許多環環相扣子任務的大型任務時，做出從宏觀角度來看並非最有效率的局部決策」。可以自然地過渡——「這也是為什麼業界會發展出Plan-and-Execute這種先建立全局規劃再依序執行的替代架構，在需要全局視野的情境下有其優勢」。

### 承接前一題，既然 ReAct 缺乏全局規劃視野，是不是代表 ReAct 不適合用來處理任何複雜的大型任務，只能處理相對簡單的任務？

**核心答案**：**並非如此絕對**——ReAct 缺乏全局規劃視野這個侷限**主要影響的是『需要從一開始就具備對整體任務完整協調視野』這一類特定性質的任務**；但對於另一類**任務本身的性質更接近『不斷依照最新得到的資訊決定下一步該怎麼走』、執行路徑本身高度依賴即時回饋、事先難以被完整規劃**的複雜任務（例如一個需要反覆嘗試、依照每一次嘗試的結果動態調整策略的除錯或研究型任務），ReAct 這種**邊做邊想、緊密依照最新觀察動態調整**的模式反而可能比一個**堅持先制定一份完整規劃**的架構更加適合。因此 ReAct 是否適用於一個複雜任務**不是單純地取決於這個任務『複不複雜』，而是取決於這個任務的執行路徑本身是否高度依賴即時回饋、事先難以被完整規劃**。

**詳細解析**：這題進一步深化前一題已經建立的比較視野，考察是否能夠避免把「ReAct 缺乏全局規劃視野」這個侷限過度簡化延伸成「ReAct 只能處理簡單任務」這個**不夠精確**的結論。理解這個問題的核心在於重新檢視「複雜任務」這個籠統的說法本身其實**涵蓋著性質截然不同的兩種情況**——**第一種**是**任務的複雜度主要來自於『需要同時協調、兼顧許多彼此環環相扣的子任務整體結構』**（例如前一題舉例的一個涉及許多環環相扣子任務的大型專案），這種任務因為**存在一個相對穩定、可以被事先想清楚的整體結構**，確實更適合用前一題討論的 Plan-and-Execute 這種先建立全局規劃的架構去處理；**第二種**則是**任務的複雜度主要來自於『執行路徑本身高度不確定，每一步具體該怎麼走高度取決於前一步實際得到的結果是什麼』**（例如一個開放式的除錯任務——『這個程式為什麼會出錯』，具體該先檢查哪裡、再檢查哪裡，高度取決於每一次檢查實際發現了什麼，事先根本沒有辦法被完整規劃出來）。這種**任務本身的複雜度樣態**恰恰最需要的不是一個**事先制定好、卻可能很快就因為實際情況和預期不符而變得不合時宜的僵固規劃**，而是**前面（見 [[001-agent-fundamentals.md]]）已經反覆強調的那種高度動態、依照每一步實際觀察結果即時調整**的能力，而這恰好正是 ReAct 這種架構最擅長發揮的核心優勢。因此**「一個任務是否複雜」和「這個任務是否適合用 ReAct」是兩件不完全劃上等號的事情**——真正關鍵的判斷準則不是任務表面上看起來複不複雜，而是**這個任務的執行路徑本身具備怎樣的性質**——是一種**可以被事先相對穩定、完整地想清楚的結構性複雜**，還是一種**執行路徑本身高度依賴即時回饋、事先難以被完整規劃**的不確定性複雜——前者更適合 Plan-and-Execute；後者反而正是 ReAct 大展身手的舞台。理解「ReAct缺乏全局規劃視野這個侷限，主要影響的是需要從一開始就具備對整體任務完整協調視野的這一類特定性質任務，但對於另一類任務本身性質更接近不斷依照最新得到的資訊決定下一步該怎麼走、執行路徑本身高度依賴即時回饋事先難以被完整規劃的複雜任務，ReAct這種邊做邊想緊密依照最新觀察動態調整的模式，反而可能比堅持先制定完整規劃的架構更加適合，一個任務是否複雜和這個任務是否適合用ReAct是兩件不完全劃上等號的事情，真正關鍵的判斷準則是這個任務執行路徑本身具備怎樣的性質——是可以被事先相對穩定完整想清楚的結構性複雜，還是執行路徑本身高度依賴即時回饋、事先難以被完整規劃的不確定性複雜」，展現你能避免把架構的某個侷限，過度簡化延伸成一個不夠精確的籠統結論，而能對任務複雜度的不同樣態做出更細緻的區分。

**面試回答方式**：先明確否定過度簡化的結論——「並非如此絕對，ReAct缺乏全局規劃視野這個侷限，主要影響的是需要從一開始就具備對整體任務完整協調視野的這一類特定性質任務」。給出ReAct依然適用的情境——「對於另一類任務，本身性質更接近不斷依照最新得到的資訊決定下一步該怎麼走、執行路徑本身高度依賴即時回饋、事先難以被完整規劃的複雜任務，例如開放式的除錯或研究型任務，ReAct這種邊做邊想的模式反而可能比堅持先制定完整規劃的架構更適合」。給出更精確的判斷準則——「ReAct是否適用不是單純取決於任務複不複雜，而是取決於這個任務的執行路徑本身，是可以被事先相對穩定完整想清楚的結構性複雜，還是執行路徑高度依賴即時回饋、事先難以被完整規劃的不確定性複雜」。
