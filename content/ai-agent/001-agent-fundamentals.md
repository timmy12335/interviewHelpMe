# 題目

什麼是「AI Agent（智能代理）」？它和單純的一次性問答式大型語言模型呼叫，最核心的差異是什麼？一個典型的 Agent 通常由哪些核心組成部分構成？

## 核心答案

AI Agent 指的是一個**以大型語言模型作為核心決策引擎，能夠自主地感知當前所處的環境或任務狀態、依照這個狀態進行推理規劃、決定下一步應該採取的行動、實際執行這個行動（通常透過呼叫某些工具或函式）、觀察這個行動所產生的結果，再把這個結果重新納入考量持續循環這個過程，直到完成一個原本被賦予的、通常較為複雜、需要多個步驟才能達成的任務**的系統。它和單純的一次性問答式呼叫最核心的差異在於——**單純的一次性問答呼叫**是使用者提出一個問題，模型依照這個問題和自己內化的知識生成一次性的文字回覆，這個過程就結束了（即使借助前面已經討論過的 RAG 或 Function Calling 補充額外資訊，本質上依然是在單一次的回合裡完成整個互動）；而 **Agent** 則具備**持續、反覆地在多個回合之間循環運作**的能力——它會依照前一步行動的實際結果動態地調整接下來的規劃和行動，這種『持續循環、依照實際回饋動態調整』的能力，讓 Agent 能夠勝任那些**沒有辦法在單一次回應裡就一次性完成，而是需要經過多個彼此依賴的步驟逐步推進才能達成**的複雜任務。一個典型的 Agent 通常由以下核心組成部分構成：**(1) 核心推理引擎**（通常就是大型語言模型本身，負責理解任務、規劃、決策）；**(2) 工具／行動空間**（Agent 實際可以用來和外部世界互動、執行具體操作的一組工具，如前面（見 [[../ai-llm/022-function-calling.md]]）已經討論過的 Function Calling 機制）；**(3) 記憶模組**（用來儲存先前已經執行過的步驟、已經取得的中間結果，讓 Agent 在做後續決策時能參照這些歷史脈絡）；**(4) 環境／執行迴圈**（負責實際地執行 Agent 決定要採取的行動、把行動的結果回饋給 Agent，並判斷整個任務是否已經完成）。

## 詳細解析

**Agent 的核心特徵——自主性（Autonomy）與持續性（Persistence）**：理解 Agent 這個概念的核心，在於掌握它相較於傳統的單次問答互動多出來的兩個關鍵特徵——**自主性**指的是 Agent 在執行任務的過程中**不需要使用者針對每一個中間步驟都重新下達明確的指令**，而是能夠依照一開始被賦予的高層次目標**自己判斷**應該採取哪些具體的中間步驟（這某種程度上呼應了前面（見 [[../ai-llm/022-function-calling.md]]）已經討論過的多工具協同呼叫情境，只是 Agent 這個概念把這種自主判斷、規劃的能力提升到一個更通用、更貫穿整個任務生命週期的層次）；**持續性**則指的是 Agent 維持一個**跨越多個回合的持續運作狀態**，它不是回答完一個問題就結束了，而是會持續地依照先前步驟的結果決定下一步要做什麼，直到判斷整個任務已經被妥善地完成。這種持續性讓 Agent 能夠處理那些**執行路徑事先無法被完全預先規劃好，而是需要依照實際執行過程中遇到的狀況動態地調整、修正**的任務（例如一個需要先查詢某些資料、再依照查到的具體內容決定接下來該查詢哪些更進一步的資訊，這種執行路徑本身具有不確定性的任務）。

**「感知－決策－行動」迴圈——Agent 運作的核心骨架**：一個 Agent 典型的運作方式可以被理解成一個持續反覆執行的迴圈——**感知（Perceive）**：Agent 接收、理解當前的任務狀態（可能包括使用者原始的請求、先前已經執行過的步驟，以及這些步驟已經取得的結果）；**決策（Decide）**：Agent 依照這個當前狀態，運用它作為核心的大型語言模型進行推理、規劃，決定接下來應該採取哪一個具體的行動（可能是呼叫某個特定的工具；也可能是判斷任務已經完成，可以生成最終的回覆給使用者）；**行動（Act）**：Agent 實際地執行這個被決定的行動（例如真正地呼叫某個工具，取得一個實際的執行結果）；**這個行動的結果會被重新納入下一輪的『感知』步驟裡**。這種**感知－決策－行動持續循環**的運作骨架，是幾乎所有 Agent 架構共通的核心運作邏輯，後面會陸續深入討論的各種更具體的 Agent 架構模式（如 [[002-react-pattern.md]] 討論的 ReAct 模式、[[008-plan-and-execute.md]] 討論的 Plan-and-Execute 模式），本質上都是針對這個核心迴圈的骨架做出各自不同的具體實現方式和優化考量。

**為什麼「工具」和「記憶」是 Agent 不可或缺的組成部分**：一個只是具備『持續循環決策』能力，卻**沒有辦法實際地執行任何具體行動、也沒有能力記住先前步驟結果**的系統，實際上並不能真正勝任複雜的實際任務——**工具**（見 [[../ai-llm/022-function-calling.md]] 已經深入討論過的 Function Calling 機制）提供了 Agent **真正和外部世界互動、取得即時或精確資訊，以及實際執行具備實質後果操作**的能力（沒有這種和外部世界互動的能力，Agent 終究只能依靠自己內化且可能已經過時的知識，這某種程度上就退化回一個單純的問答系統）；**記憶**則提供了 Agent **在執行一個可能涉及許多中間步驟的複雜任務時，保持對整個任務已經推進到哪個階段、已經取得哪些關鍵資訊的連貫理解**的能力（沒有這種記憶機制，Agent 可能會在執行到任務的某個中間階段時『忘記』先前已經做過哪些嘗試、已經取得哪些結果，而重複地做一些已經做過的無效嘗試，或是做出和先前步驟自相矛盾的決策）。這兩個組成部分某種程度上分別對應著 Agent 之所以能夠**真正對外部世界產生實際影響**、以及**在一個延續多個步驟的任務裡保持一致、連貫的行為**這兩個讓 Agent 區別於單純問答系統的核心能力。

## 面試回答方式

先給出Agent的核心定義——「以大型語言模型作為核心決策引擎，能夠自主地感知當前環境或任務狀態、依照這個狀態進行推理規劃、決定並執行下一步行動、觀察行動結果、再把結果重新納入考量持續循環，直到完成一個通常需要多步驟才能達成的任務的系統」。清楚點出和單次問答呼叫的核心差異——「單次問答呼叫是提出問題、生成一次性回覆就結束，而Agent具備持續、反覆在多個回合之間循環運作的能力，會依照前一步行動的實際結果動態調整接下來的規劃和行動」。列出四個核心組成部分——「核心推理引擎(通常就是大型語言模型本身)、工具/行動空間(Function Calling機制讓Agent能實際和外部世界互動)、記憶模組(儲存先前步驟的中間結果供後續決策參照)、環境/執行迴圈(負責實際執行行動、回饋結果、判斷任務是否完成)」。可以用感知-決策-行動這個核心運作骨架來收束——「這是幾乎所有Agent架構共通的核心運作邏輯，後續更具體的架構模式本質上都是針對這個核心迴圈做出不同的具體實現和優化」，展現你對Agent這個概念有紮實、且能作為後續更深入討論基礎的核心理解。

## 常見追問

### 是不是任何有使用到 Function Calling 的系統，就可以被稱為是一個 Agent？兩者之間的界線具體是什麼？

**核心答案**：**不是，單純使用到 Function Calling 並不足以讓一個系統被稱為是 Agent**——關鍵的區分點在於**是否具備前面已經討論過的『持續循環自主決策』這個核心特徵**：如果一個系統只是在單一次的回合裡判斷需要呼叫某一個（或幾個）工具，取得結果之後就直接生成最終回覆結束（即使這個過程可能涉及前面（見 [[../ai-llm/022-function-calling.md]]）討論過的多工具協同呼叫），這本質上依然是一種**單一次回合內完成的互動**，還稱不上是一個 Agent；只有當這個系統具備**依照前一輪行動的實際結果，動態地決定是否需要再進行額外的、事先無法完全預先規劃好的後續步驟，並且這個循環持續進行直到系統自己判斷任務已經完成**，才真正構成前面所定義的 Agent。

**詳細解析**：這題考察是否能夠精確地劃定「Agent」和「單純具備 Function Calling 能力的系統」之間容易被混淆的界線，而不是把任何涉及工具呼叫的系統都籠統地稱作 Agent。理解這個界線的核心，在於聚焦在**「決策的循環次數，和是否事先可以被完全預先規劃好」**這個關鍵判準上——如果一個任務本質上可以被**事先完整地規劃**成一個固定的步驟序列（例如『先呼叫工具 A 取得結果，再把這個結果代入呼叫工具 B 取得最終答案，生成回覆』這種**執行路徑在任務開始之前就已經可以被完全確定**的情況），即使這涉及好幾次的工具呼叫，這種情況某種程度上更接近一個**固定流程（Pipeline）**，而不是真正具備自主性的 Agent（因為整個執行路徑並沒有依照實際執行過程中遇到的新資訊而發生任何真正意義上的『動態調整』）；相較之下，真正的 Agent 場景通常具備**執行路徑本身事先無法被完全預先確定**這個特性——例如 Agent 可能需要先執行某個查詢動作，依照查到的具體結果內容才能判斷接下來究竟應該採取哪一種後續行動（不同的查詢結果可能導致完全不同的後續步驟），這種**「下一步究竟要做什麼，取決於上一步實際得到的結果是什麼」**的動態決策特性，才是真正讓一個系統具備 Agent 所需要的自主性和持續性的關鍵。因此判斷一個系統是否真正構成 Agent，不應該只看它是否用到了 Function Calling 這個機制本身，而應該去檢視它的執行路徑是否真的具備這種**依照實際執行結果動態決定後續步驟**的特性。理解「單純使用到Function Calling並不足以構成Agent，關鍵區分點在於是否具備持續循環自主決策這個核心特徵，如果一個任務的執行路徑可以在開始之前就被完整規劃成固定步驟序列，即使涉及好幾次工具呼叫，這更接近一個固定流程而非真正具備自主性的Agent，真正的Agent場景通常具備執行路徑本身事先無法被完全預先確定這個特性，下一步究竟要做什麼取決於上一步實際得到的結果是什麼，這種動態決策特性才是真正讓一個系統具備Agent所需要自主性和持續性的關鍵」，展現你能精確劃定Agent和單純工具呼叫系統之間的界線，而非把兩者混為一談。

**面試回答方式**：先明確給出核心答案——「不是，單純使用Function Calling並不足以構成Agent，關鍵區分點在於是否具備持續循環自主決策的核心特徵」。給出判斷準則——「如果一個任務的執行路徑可以在開始前就被完整規劃成固定步驟序列，即使涉及多次工具呼叫，這更接近一個固定流程(Pipeline)，而不是真正具備自主性的Agent」。給出真正Agent的判準——「真正的Agent場景通常具備執行路徑本身事先無法被完全預先確定這個特性，下一步要做什麼取決於上一步實際得到的結果，這種依照實際執行結果動態決定後續步驟的特性，才是讓系統具備Agent所需自主性和持續性的關鍵」。

### Agent 的「記憶模組」和之前討論過的 RAG，或者大型語言模型本身的上下文視窗（Context Window），這幾個概念彼此是什麼關係？會不會其實是同一件事情，只是換了個名字？

**核心答案**：**這幾個概念彼此相關、但並不完全是同一件事情**——**上下文視窗**（見 [[../ai-llm/015-long-context-handling.md]]）指的是模型單一次推理時實際上**能夠一次性接收、處理的輸入內容長度上限**，是一個相對底層、和模型架構本身綁定的技術限制；**RAG**（見 [[../ai-llm/008-rag-architecture.md]]）是一種**依照當前查詢的語意內容，動態地從一個龐大、外部的知識庫裡檢索出相關文件片段**的機制，處理的是『如何取得超越模型內化知識範圍的額外背景資訊』這個問題；而 **Agent 的記憶模組**處理的則是**「在執行一個持續進行、可能橫跨許多步驟的任務過程中，如何記住並妥善管理先前已經執行過的步驟、已經取得的中間結果」**這個更貼近任務執行過程本身的問題。三者雖然都某種程度上涉及『管理模型能夠存取到的資訊』這個大方向，但**各自處理的具體問題和運作機制是不同的**。實務上一個完整的 Agent 系統經常會**同時運用**這幾種機制——用上下文視窗承載當下這一輪需要處理的直接資訊；用 RAG 補充任務可能需要用到的外部知識庫背景資訊；用記憶模組追蹤整個任務執行至今的歷史脈絡。

**詳細解析**：這題延續前面在其他章節反覆練習過的核心分析框架——**當面對多個看起來都和『資訊／記憶管理』相關的概念時，仔細地去釐清它們各自具體處理的問題和運作機制，而不是因為表面上都涉及類似的字眼（記憶、上下文、檢索）就把它們混為一談**。理解這三者的具體差異需要逐一釐清——**上下文視窗**是一個**單次推理呼叫**層次的技術限制概念——不管是單純的問答互動，還是 Agent 執行任務過程中的某一次具體的推理步驟，這一次推理能夠『看到』多少輸入內容都受限於這個上下文視窗的長度上限，它本身並不天然地具備『記住好幾輪之前發生過什麼事』這種跨越多輪的持續性（如果想要讓模型在當下這一輪推理時『記得』先前發生過的事情，勢必需要把這些先前的歷史內容重新塞回這一輪的輸入裡，而這就會受到上下文視窗長度限制的制約）；**RAG** 處理的是一個**橫向的、和任務執行歷史本身無關**的資訊補充問題——不管 Agent 執行到任務的哪一個階段，只要這個階段的某個決策需要用到儲存在外部知識庫裡的特定背景知識，都可以透過 RAG 這個機制去檢索、取得這種補充資訊，RAG 本身並不特別關心 Agent 先前已經執行過哪些步驟這件事本身；而 **Agent 的記憶模組**才是**真正專門針對「這個任務執行至今已經發生過什麼事、已經得到哪些關鍵中間結果」這種任務執行歷程本身**所設計的機制——這種記憶可能被實作成把先前步驟的關鍵摘要持續地累積，並在每一輪新的推理呼叫時重新塞入上下文視窗裡（這種做法某種程度上會受到上下文視窗長度限制的制約，如果任務執行的步驟太多、歷史太長，可能需要額外的摘要壓縮機制）；也可能被實作成把這些執行歷程儲存到一個外部的、持久化的儲存系統裡（這種做法某種程度上和 RAG 的概念有一定程度的技術實作上的相似性——都涉及把某些資訊存放到外部系統裡，再依照需要檢索、取回，只是 RAG 檢索的是相對靜態、和任務執行過程本身無關的知識庫內容；而 Agent 記憶檢索的是這個特定任務自己執行過程中累積下來的動態歷程資訊）。理解「上下文視窗是單次推理呼叫層次的技術限制概念，處理模型一次能看到多少輸入內容;RAG處理的是橫向的、和任務執行歷史本身無關的外部知識庫資訊補充問題;Agent的記憶模組則是專門針對這個任務執行至今已經發生過什麼事、已經得到哪些關鍵中間結果這種任務執行歷程本身所設計的機制，三者處理的具體問題和運作機制不同，但實務上一個完整的Agent系統經常會同時運用這幾種機制，分別扮演承載當下直接資訊、補充外部知識庫背景、以及追蹤任務執行歷史脈絡這幾個不同角色」，展現你能仔細釐清這幾個容易被混為一談的相關概念，各自具體處理的問題，而非簡單地把它們等同視之。

**面試回答方式**：先明確否定「同一件事」這個說法——「這幾個概念彼此相關，但並不完全是同一件事」。逐一釐清三者各自處理的問題——「上下文視窗是模型單次推理能一次性接收處理的輸入內容長度上限，是底層技術限制;RAG是依照當前查詢動態從外部知識庫檢索相關文件片段，處理的是如何取得超越模型內化知識範圍的額外背景資訊;Agent的記憶模組處理的是在執行一個持續進行、可能橫跨許多步驟的任務過程中，如何記住並管理先前已經執行過的步驟和取得的中間結果，這是更貼近任務執行過程本身的問題」。給出實務整合的說法——「實務上一個完整的Agent系統經常同時運用這幾種機制，用上下文視窗承載當下這一輪的直接資訊、用RAG補充任務可能需要的外部知識庫背景、用記憶模組追蹤整個任務執行至今的歷史脈絡」。

### 如果一個 Agent 在執行一個長時間、多步驟的任務過程中突然系統當機或程序中斷，重新啟動後它有辦法從中斷的地方接續執行，還是只能從頭重新開始？這取決於什麼樣的設計？

**核心答案**：**這取決於這個 Agent 系統是否具備「狀態持久化（State Persistence）」的設計**——如果 Agent 把它執行至今的所有關鍵狀態（包括先前已經完成的步驟、已經取得的中間結果、當前的任務進度）都只是暫存在記憶體裡（而沒有額外地把這些狀態持久化儲存到某個即使程序中斷、重啟後依然能夠被讀取回來的外部儲存系統裡），那一旦發生當機或程序中斷，這些暫存在記憶體裡的執行狀態就會**完全遺失**，重新啟動後 Agent 只能**從頭重新開始**執行整個任務；反之，如果這個 Agent 系統被設計成**會定期地（或是在每一個關鍵的執行步驟完成後）把它當下的執行狀態明確地寫入某個持久化的外部儲存（如資料庫、檔案系統）裡**，那即使發生當機或中斷，重新啟動後 Agent 就可以**讀取回這個先前已經被持久化保存的狀態，從中斷的那個點接續執行**，而不需要從頭重新開始。

**詳細解析**：這題把 Agent 的記憶概念（前一題已經深入討論過）進一步延伸到一個更貼近實務上**系統可靠性和容錯能力**的具體工程議題，考察是否理解「Agent 有沒有記憶」和「Agent 的記憶是否足夠穩固、能夠撐過系統層級的意外中斷」是**兩個層次不同、需要分別被仔細考量**的問題。理解這個問題的核心需要區分**「記憶存在於哪裡」**這個關鍵的技術細節——如果 Agent 的記憶（前一題討論的那些任務執行歷程）僅僅是被儲存在執行這個 Agent 的**應用程式行程本身的記憶體**裡（例如作為程式裡的某個變數或物件），這種儲存方式本質上是**易失性（Volatile）**的——一旦承載這個行程的伺服器發生當機、或者這個行程本身因為任何原因而被意外地終止、重啟，這個儲存在行程記憶體裡的所有狀態都會**隨著這個行程的終止而完全消失**，沒有辦法被恢復。因應這個風險，一個需要**具備高可靠性、能夠承受意外中斷**的 Agent 系統（尤其是那些執行時間可能長達數十分鐘、甚至數小時以上的複雜長任務，中途發生意外中斷的機率某種程度上也會隨著執行時間拉長而提高）需要額外地設計**「檢查點（Checkpoint）」機制**——具體做法是在 Agent 執行任務的過程中**定期地（或是在每一個關鍵步驟完成後）明確地把當下這個 Agent 完整的執行狀態（包括已經完成到哪個步驟、已經取得的所有關鍵中間結果、當前任務的整體進度）序列化、寫入到一個即使發生系統當機也不會隨之遺失的持久化儲存系統裡**（例如一個獨立的資料庫、或者一個持久化的檔案儲存）。透過這種定期寫入檢查點的做法，即使 Agent 執行過程中不幸遭遇任何意外的系統層級中斷，重新啟動之後這個系統可以**讀取回最近一次被成功寫入的那個檢查點，從那個中斷的時間點附近接續執行**，而不需要從頭完全重新開始（這樣也能避免因為中斷而浪費掉先前已經投入的大量運算資源和時間成本）。這種「透過定期寫入可持久化的檢查點，來讓一個長時間執行的流程具備承受意外中斷、並能夠從中斷點接續執行的韌性能力」的設計思路並不是 Agent 系統獨有的概念——這其實是在處理任何**長時間執行、且需要高可靠性**的運算工作時（例如大型的批次資料處理任務、長時間執行的科學計算流程）一個相當普遍且被廣泛採用的工程實務原則，只是在 Agent 這個具體情境下，需要被持久化保存的『狀態』具體對應到前一題討論的那些任務執行歷程和記憶內容。理解「這取決於Agent系統是否具備狀態持久化的設計，如果記憶僅僅暫存在執行行程本身的記憶體裡，這種儲存方式是易失性的，一旦行程當機或意外終止，這些狀態就會完全遺失，重新啟動後只能從頭開始;因應這個風險，需要具備高可靠性的Agent系統需要額外設計檢查點機制，定期或在每個關鍵步驟完成後把當下完整的執行狀態序列化寫入一個即使系統當機也不會遺失的持久化儲存系統裡，透過這種機制，即使遭遇意外中斷，重啟後也能讀取最近一次成功寫入的檢查點，從中斷點附近接續執行，這種透過定期寫入可持久化檢查點來讓長時間執行流程具備承受意外中斷韌性能力的設計思路，並非Agent系統獨有，而是處理任何長時間執行且需要高可靠性運算工作時普遍採用的工程實務原則」，展現你能把Agent的記憶概念，延伸到更貼近實務系統可靠性和容錯設計的具體工程考量，並識別出這個原則背後更普遍適用的工程實務基礎。

**面試回答方式**：先給出核心判斷——「這取決於這個Agent系統是否具備狀態持久化的設計」。解釋兩種情況——「如果Agent的執行狀態僅僅暫存在應用程式行程本身的記憶體裡，這種儲存方式是易失性的，一旦行程當機或意外終止，這些狀態就會完全遺失，重啟後只能從頭開始;反之如果系統被設計成會定期或在每個關鍵步驟完成後，把當下的執行狀態明確寫入一個持久化的外部儲存系統裡，即使發生中斷，重啟後也能讀取回最近一次成功寫入的檢查點，從中斷點接續執行」。可以補充這個設計思路的普遍性——「這種透過定期寫入可持久化檢查點來讓長時間執行流程具備承受意外中斷韌性的設計，並不是Agent系統獨有的概念，而是處理任何長時間執行且需要高可靠性運算工作時，一個相當普遍且被廣泛採用的工程實務原則」。
