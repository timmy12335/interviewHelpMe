# 題目

Agent 沒有呼叫工具、或者呼叫錯了工具，怎麼診斷？

## 核心答案

**先分清失敗發生在哪一環**，因為四種失敗的處理完全不同。

**該叫而沒叫**——模型直接用自己的知識回答了。通常是「描述沒有讓它意識到這個工具適用」或者「系統提示沒有強調必須用工具查證」。

**叫錯了工具**——多半是工具之間的描述界線模糊；處理是在描述中明確互相區隔。

**叫對了但參數錯**——參數描述不夠具體、缺少格式範例、或者模型需要的資訊根本不在上下文裡（**它只好編一個**）。

**叫對了但不會用回傳結果**——回傳格式太複雜、或者回傳裡沒有它需要的欄位。

診斷的基礎是完整的追蹤記錄：每一步的完整提示、模型的原始輸出、工具的呼叫參數與回傳——沒有這些，所有的改善都是猜測。

## 詳細解析

「模型編造參數」是一個特別值得注意的模式：當它需要一個 ID 但上下文裡沒有——它常常不會說「我需要先查詢」，而是直接編一個看起來合理的值。這在下游是災難性的（用一個不存在的 ID 執行了操作）。**兩個防護**：工具層面驗證參數的存在性並回傳明確的錯誤（「訂單 12345 不存在，請先用 search_orders 查詢」）、以及在系統提示中明確要求「不要猜測 ID，必須從先前的工具回傳中取得」。前者比後者可靠，因為它是強制的。

「該叫而沒叫」在事實查詢類任務上後果最嚴重：模型用內部知識回答了一個應該查資料庫的問題——答案看起來合理但可能完全過時或錯誤，而且沒有任何跡象顯示它沒查。檢測的方法是在評估中檢查「工具呼叫的軌跡」而非只檢查最終答案——這是 Agent 評估與一般 LLM 評估最重要的區別之一。

「改善的順序」有明確的成本梯度：先改工具描述（幾分鐘、零成本）、再改系統提示（幾分鐘）、然後調整工具的粒度或數量（幾小時）、最後才考慮微調模型（幾天）。而實務上超過八成的問題在前兩步就能解決——所以先跳到「模型不夠強」這個結論通常是錯的。

「換一個更強的模型」是一個有效但要謹慎使用的手段：它確實能提升工具使用的準確率——但如果根因是描述模糊，換模型只是把問題推遲到更複雜的場景才爆發。所以應該先確認「一個仔細閱讀描述的人能不能正確使用這些工具」——**不能的話，那不是模型的問題**。

## 面試回答方式

先給四種失敗的分類與各自的典型原因，並強調診斷的基礎是完整的追蹤記錄。加分點有四個：**模型編造參數**這個危險模式——需要 ID 但上下文沒有時它會編一個看起來合理的，防護是工具層面驗證存在性並回傳明確錯誤，比在提示中要求可靠因為它是強制的；**「該叫而沒叫」後果最嚴重**——答案看起來合理卻可能完全過時，而且沒有任何跡象，所以評估要檢查工具呼叫的軌跡而非只看最終答案，這是 Agent 評估與一般 LLM 評估最重要的區別之一；改善的順序有明確的成本梯度，而超過八成的問題在前兩步就能解決；以及**換更強的模型要謹慎**——根因是描述模糊時它只是把問題推遲。

## 講稿

我會先分清失敗發生在哪一環，因為四種的處理完全不同。該叫而沒叫、叫錯工具、叫對但參數錯、還有叫對但不會用回傳結果。

而診斷的基礎是完整的追蹤記錄。每一步的完整提示、模型的原始輸出、工具的呼叫參數跟回傳。沒有這些，所有改善都是猜測。

有一個模式特別值得注意，模型編造參數。當它需要一個編號但上下文裡沒有，它常常不會說我需要先查詢，而是直接編一個看起來合理的值。這在下游是災難性的，用一個不存在的編號執行了操作。防護有兩層，工具層面驗證參數存在性並回傳明確的錯誤，還有在系統提示裡要求不要猜測。前者比後者可靠，因為它是強制的。

另一個後果最嚴重的是該叫而沒叫。模型用內部知識回答了一個應該查資料庫的問題，答案看起來合理但可能完全過時，而且沒有任何跡象顯示它沒查。所以評估時要檢查工具呼叫的軌跡，而不是只看最終答案。

改善的順序我會先改工具描述、再改系統提示、然後調整工具粒度、最後才考慮換模型。實務上超過八成的問題在前兩步就解決了。

## 常見追問

### 怎麼評估 Agent 的工具使用能力？

**核心答案**：建立一組「有標準軌跡」的測試案例：每個案例標註出**正確的工具序列與關鍵參數**，**然後比對實際軌跡**。指標包括：工具選擇準確率、參數正確率、以及「多餘的呼叫次數」（**繞遠路也是一種失敗**）。同時要有「不該呼叫工具」的案例——**測試它會不會濫用工具**。

**詳細解析**：「軌跡不必完全一致才算對」是評估設計的一個關鍵判斷：達成同一個目標可能有多條合理的路徑——嚴格比對序列會把正確的替代方案判為失敗。**更好的做法是分層評估**：檢查「必要的工具有沒有被呼叫」（召回）、「有沒有呼叫不該呼叫的」（精確）、以及「最終結果對不對」——**而不是要求逐步一致**。**另一個實用的指標是「效率」**：同樣達成目標，用 3 步與用 12 步的差別很大——**因為每一步都是延遲與成本**。把步數納入評估，能防止「為了提高成功率而讓 Agent 無限嘗試」這種退化。

**面試回答方式**：給有標準軌跡的測試案例與三類指標，並強調**要有「不該呼叫工具」的案例**。核心加分點是**軌跡不必完全一致才算對**——達成目標可能有多條合理路徑，嚴格比對會把正確的替代方案判為失敗，所以應該分層檢查召回、精確與最終結果。收在**效率指標**：同樣達成目標用 3 步與 12 步差別很大，把步數納入評估能防止「為了成功率而讓 Agent 無限嘗試」的退化。

### 系統提示該怎麼寫才能改善工具使用？

**核心答案**：**四件事**。**明確角色與目標**（它在做什麼、為誰做）。**明確工具使用的原則**（「涉及使用者資料的問題必須查詢，不要依賴你的記憶」）。**明確禁止事項**（「不要猜測 ID」「不要在未確認前執行寫入操作」）。以及給一到兩個完整的軌跡範例——展示「收到這類請求時，正確的工具呼叫順序長什麼樣」。

**詳細解析**：「軌跡範例」是這四項中效果最好卻最少被使用的：它同時示範了工具的選擇、參數的填法、以及如何使用回傳結果——一個好的範例勝過三段抽象的規則。成本是佔用上下文，所以要挑最典型或最容易出錯的場景。另一個要點是「規則要具體到可執行」：「請謹慎使用工具」是無效的，而「執行任何刪除操作前，必須先呼叫 confirm_with_user」是可執行的。而最容易被忽略的一點是「系統提示會隨對話變長而被稀釋」——在長對話中，模型對開頭指令的遵守度會下降；緩解的做法是在關鍵決策點重新注入簡短的提醒，而不是只依賴最初的系統提示。

**面試回答方式**：給四件事並強調軌跡範例效果最好卻最少被使用——它同時示範選擇、參數與如何用回傳結果，一個好範例勝過三段抽象規則。加分點是**規則要具體到可執行**（用「刪除前必須先呼叫確認工具」對比「請謹慎使用工具」）。收在容易被忽略的一點：系統提示會隨對話變長而被稀釋，長對話中模型對開頭指令的遵守度下降，緩解是在關鍵決策點重新注入簡短提醒。

### 什麼時候該用微調來改善工具使用？

**核心答案**：當工具集穩定、呼叫量大、且提示層的優化已經到頂時。微調能讓模型內化「這套工具該怎麼用」——於是不需要在每次請求中都塞入完整的工具描述與範例，**同時提升準確率並降低 token 成本**。**但前提是工具不常變**——每次工具變更都要重新微調，成本很高。

**詳細解析**：「省下的 token 成本可能是微調的主要理由」：如果工具描述加範例佔了 3000 token，**而你每天有一百萬次呼叫**——**那就是每天 30 億個輸入 token**。微調後把這些內化，可以省下絕大部分——在高頻應用中，這個節省可能遠超微調本身的成本。但要注意一個實務陷阱：微調後的模型對「訓練時見過的工具」表現很好，對新增的工具反而可能更差——**因為它形成了固定的模式**。所以工具集的演進節奏必須與微調的節奏匹配，而這通常意味著微調只適合已經穩定下來的核心工具集，新的、實驗性的工具仍然走提示的路線。

**面試回答方式**：給三個前提條件（工具穩定、量大、提示優化到頂）。核心加分點是**省下的 token 成本可能是主要理由**並量化（3000 token 的描述乘一百萬次呼叫）。收在實務陷阱：微調後對新增的工具反而可能更差，因為它形成了固定模式，所以微調只適合已經穩定的核心工具集，新的實驗性工具仍走提示路線。
