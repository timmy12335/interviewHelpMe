# 題目

Agent 執行久了上下文會滿，有哪些管理策略？各自的代價是什麼？

## 核心答案

五種策略，而它們損失的東西不同。

**截斷**——**丟掉最舊的訊息**；最簡單，但可能丟掉關鍵的早期決定（例如使用者最初的需求）。改進是「保留系統提示與最初的任務描述，只截斷中段」。

**摘要**——**把一段歷史壓縮成一段摘要**；**保留了要點但丟失細節**，而且摘要本身可能引入錯誤（模型可能摘錯重點）。

**外部化**——把內容寫到檔案或資料庫，上下文只保留引用；不損失資訊，代價是需要在需要時正確地取回。

**選擇性保留**——只保留與當前子任務相關的部分；**需要一個判斷相關性的機制**。

**分層記憶**——短期（完整）、中期（摘要）、長期（結構化的事實）；**最完整但實作最複雜**。

而選擇的判準是「這個任務的哪些資訊是後續必須精確的」——必須精確的就外部化，可以概括的才摘要。

## 詳細解析

「壓縮發生的時機」比「壓縮的方法」更容易出錯：如果在一個工具呼叫的中途壓縮——模型可能失去了「我剛才呼叫了什麼、為什麼」的脈絡，**於是重複呼叫或走錯方向**。所以壓縮應該在「一個完整的子任務邊界」進行，**而不是簡單地按 token 數觸發**。實務上的做法是「接近上限時等到當前工具呼叫完成再壓縮」，並在壓縮後明確地重述當前的目標與已完成的步驟。

「摘要會累積失真」是長時間運行 Agent 的一個真實問題：對摘要再做摘要——每一次都損失一點，幾輪之後可能已經偏離原意。緩解的做法是「永遠從原始內容摘要，而不是從上一份摘要」——**這需要保留原始內容（外部化）**，於是它與外部化策略天然結合。**另一個做法是「結構化摘要」**：不用自由文字，而是維護一個固定 schema 的狀態物件（目標、已完成、待辦、已知約束、關鍵事實）——結構化的內容在多次更新中比自由文字穩定得多。

「什麼絕對不能丟」需要明確定義：**使用者的原始需求**、已經做出的不可逆操作的記錄（**否則可能重複執行**）、**以及明確的約束與禁止事項**。這些應該被釘在上下文中，不參與任何壓縮。沒有這條規則，壓縮偶爾會造成很難診斷的行為異常——因為 Agent 突然「忘了」某個約束，而你看不出來為什麼。

**「壓縮本身是有成本的」**：它需要一次額外的模型呼叫——在頻繁壓縮的場景中，這個成本不可忽略。所以壓縮的觸發閾值應該權衡「壓縮的成本」與「保留長上下文的成本」，而後者在多數定價下更高，所以壓縮通常是划算的。

## 面試回答方式

先給五種策略與各自損失的東西，並給出判準——必須精確的就外部化，可以概括的才摘要。加分點有四個：壓縮的時機比方法更容易出錯——在工具呼叫中途壓縮會讓模型失去脈絡，所以應該在完整的子任務邊界進行，並在壓縮後重述目標與已完成步驟；**摘要會累積失真**——對摘要再摘要每次都損失一點，緩解是永遠從原始內容摘要（需要外部化配合）或用結構化摘要，因為固定 schema 在多次更新中比自由文字穩定得多；**明確定義什麼絕對不能丟**（原始需求、不可逆操作的記錄、明確約束），否則會造成很難診斷的行為異常；以及**壓縮本身有成本**，需要與保留長上下文的成本權衡。

## 講稿

有五種策略，而它們損失的東西不同。截斷、摘要、外部化、選擇性保留、還有分層記憶。

選擇的判準是這個任務的哪些資訊是後續必須精確的。必須精確的就外部化，可以概括的才摘要。

有一個地方比方法本身更容易出錯，就是壓縮的時機。如果在一個工具呼叫的中途壓縮，模型可能失去了我剛才呼叫了什麼、為什麼的脈絡，於是重複呼叫或走錯方向。所以壓縮應該在完整的子任務邊界進行，而不是單純按詞元數觸發，而且壓縮之後要明確重述當前目標跟已完成的步驟。

第二個問題是摘要會累積失真。對摘要再做摘要，每一次都損失一點。所以我會永遠從原始內容摘要而不是從上一份摘要，或者改用結構化摘要，維護一個固定格式的狀態物件而不是自由文字，因為結構化的內容在多次更新中穩定得多。

還有要明確定義什麼絕對不能丟。使用者的原始需求、已經做過的不可逆操作、還有明確的約束。這些要釘在上下文裡不參與壓縮。

## 常見追問

### 怎麼決定哪些歷史是「相關的」？

**核心答案**：**三種機制，成本遞增**。**基於結構**——保留最近 N 輪加上系統提示與任務描述；零成本但粗糙。**基於檢索**——把歷史存成可檢索的片段，按當前的問題檢索最相關的幾條；**這本質上是對對話歷史做 RAG**。**基於模型判斷**——讓一個便宜的模型評估每一段歷史對當前任務的相關性；最準但最貴。

**詳細解析**：「對話歷史做 RAG」有一個特有的困難：時序性。一般的 RAG 不在乎文檔的順序——而對話歷史的意義高度依賴順序與因果（「然後我改變了主意」這句話單獨檢索出來會誤導）。所以檢索出的片段應該保留時間標記並按時序排列，而不是按相關性排列。另一個實務要點是「不要檢索工具的原始回傳」——它們往往很長且已經被模型消化過；應該檢索模型對它們的總結或結論。更根本的建議是「與其事後檢索，不如在產生時就記錄結構化的事實」：每完成一個子任務就寫下「我確認了 X」「我決定了 Y」——這些短小的結論比原始對話容易檢索也容易保持準確。

**面試回答方式**：給三種機制與成本梯度。核心加分點是對話歷史做 RAG 的特有困難是時序性——一般 RAG 不在乎順序，而對話的意義高度依賴順序與因果，所以檢索結果應該按時序而非相關性排列。收在更根本的建議：與其事後檢索不如在產生時就記錄結構化的事實——每完成一個子任務就寫下確認了什麼、決定了什麼，這些短結論比原始對話容易檢索也容易保持準確。

### 長對話中 Agent 開始「忘記」指令怎麼辦？

**核心答案**：在關鍵決策點重新注入約束，而不是只依賴最初的系統提示。長上下文中，開頭的指令會被大量後續內容稀釋——**這是注意力機制的天然結果**。**實用的做法有三**：把最重要的約束同時放在系統提示與最近的一條訊息中、在每次工具呼叫前注入相關的規則、以及用結構化的狀態物件持續攜帶約束（而不是指望模型記得）。

**詳細解析**：「重要的約束不應該只存在於提示中」是更根本的處理：如果一個約束真的重要（例如「不能刪除生產資料」）——它應該在工具層面被強制，而不是靠提醒模型。提示層的重複注入只能降低違規的機率，而程式碼層的檢查能杜絕它。所以正確的分層是：提示告訴模型「應該怎麼做」，程式碼保證「不能做什麼」。而這也提供了一個實用的分類方法：把所有約束列出來，問「如果模型違反了這一條，後果能接受嗎」——不能接受的就必須有程式碼層的保護，能接受的才靠提示。

**面試回答方式**：給根本原因（長上下文中開頭指令被稀釋，這是注意力機制的天然結果）與三個實用做法。核心加分點是更根本的處理：重要的約束不應該只存在於提示中——提示層的重複注入只能降低違規機率，程式碼層的檢查能杜絕它，所以分層是「提示告訴模型應該怎麼做，程式碼保證不能做什麼」。收在實用的分類方法：把約束列出來問「違反了後果能接受嗎」，不能接受的就必須有程式碼層保護。

### 上下文管理與 RAG 有什麼關係？

**核心答案**：**它們是同一個問題的兩面**：RAG 是「從外部知識中選出相關的放進上下文」，上下文管理是「從歷史中選出相關的留在上下文」——兩者都是在有限的視窗內做取捨。所以 RAG 的所有技術（切分、檢索、重排、評估）都可以遷移到對話歷史的管理上。

**詳細解析**：這個統一的視角帶來一個實用的架構簡化：把「外部知識」與「對話歷史」都當成可檢索的來源，用同一套檢索與排序機制處理——於是上下文的組裝變成一個統一的「按當前需求挑選內容」的問題，**而不是兩套獨立的邏輯**。實作上可以定義一個「上下文預算」（總共多少 token），然後按優先級分配給系統提示、任務描述、檢索到的知識、以及對話歷史——這讓上下文的組成變成一個明確的、可調整的決定，而非隱式的累積結果。很多 Agent 的上下文問題根源正是「沒有人明確地決定上下文該包含什麼」——**它只是被動地累積直到爆掉**。建立明確的預算與優先級，往往是這類問題最有效的解法。

**面試回答方式**：給統一的視角（兩者都是在有限視窗內做取捨）並指出 **RAG 的技術可以遷移到歷史管理**。核心加分點是架構簡化：把外部知識與對話歷史都當成可檢索的來源，用同一套機制處理，並提出**上下文預算**的概念——按優先級分配給系統提示、任務描述、檢索知識、對話歷史。收在診斷：很多 Agent 的上下文問題根源是沒有人明確決定上下文該包含什麼，它只是被動累積直到爆掉，而建立明確的預算與優先級往往是最有效的解法。
