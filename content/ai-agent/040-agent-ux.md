# 題目

Agent 執行需要幾十秒甚至幾分鐘，介面上該怎麼設計？

## 核心答案

核心問題是「長時間的不確定等待會摧毀信任」——而解法是讓過程可見、可預期、可介入。

**四個設計要素。**

**即時的進度**——**串流展示當前在做什麼**（「正在查詢訂單資料…」「正在分析三個檔案…」），**而不是一個轉圈的載入圖示**。知道它在做什麼，等待的容忍度會顯著提高。

**可預期的範圍**——如果能估計，就給出「大約還有幾步」或「預計還需要 30 秒」；不能估計時至少說明「這通常需要一到兩分鐘」。

**可介入**——隨時能停止、能追加說明、能修正方向；看著 Agent 走錯方向卻無法阻止，是最糟糕的體驗。

**可審查的結果**——不只給最終答案，還要能展開看「它做了什麼、依據是什麼」；這既建立信任，也讓使用者能發現錯誤。

## 詳細解析

「展示什麼細節」是一個需要拿捏的設計判斷：展示完整的推理鏈——資訊過載，而且暴露了可能錯誤或混亂的中間思考；完全不展示——使用者不知道發生了什麼。多數成熟的產品選擇「摘要式的進度加上可展開的細節」：預設顯示一行「正在檢查庫存」，點開才看到具體的工具呼叫與結果。這讓一般使用者不被干擾，而需要深究的人能查看。

**「錯誤與不確定要誠實展示」**：Agent 遇到問題時——隱藏它並給一個看起來完整的答案，比坦承「我查不到 X，以下是基於其他資訊的回答」糟糕得多。因為前者會讓使用者在不知情的情況下採信一個不完整的結果。而實務上，坦承限制的產品反而更容易獲得信任——這與人際互動的邏輯完全一致。

**「中斷的語義要明確」**：使用者按下停止之後——**已經執行的操作會怎樣？** 如果 Agent 已經發了三封郵件，停止不會收回它們。所以介面應該說明「已完成的操作不會被撤銷」，並展示已經做了什麼——而不是讓使用者以為停止等於什麼都沒發生。

「等待期間的產品設計」有一個常被忽略的機會：長時間任務可以設計成**非同步**——使用者提交後可以去做別的事，完成時通知。這比讓他盯著一個進度條好得多，尤其是對確定要跑幾分鐘的任務。判斷的標準是「使用者需要立刻用到結果嗎」——不需要的話，非同步加通知幾乎總是更好的體驗。

## 面試回答方式

先給核心問題——長時間的不確定等待會摧毀信任，並給四個設計要素（即時進度、可預期範圍、可介入、可審查結果）。加分點有四個：**展示什麼細節的拿捏**——完整推理鏈會資訊過載並暴露混亂的中間思考，多數成熟產品選擇「摘要進度加可展開的細節」；**錯誤與不確定要誠實展示**——隱藏問題並給看似完整的答案，比坦承限制糟糕得多，而坦承限制的產品反而更容易獲得信任；**中斷的語義要明確**——已完成的操作不會被撤銷，要展示已經做了什麼而非讓使用者以為停止等於什麼都沒發生；以及長時間任務可以設計成非同步加通知，判斷標準是「使用者需要立刻用到結果嗎」。

## 講稿

核心問題是長時間的不確定等待會摧毀信任。解法是讓過程可見、可預期、可介入。

我會做四件事。第一是即時的進度，串流展示當前在做什麼，而不是一個轉圈的圖示。知道它在做什麼，等待的容忍度會顯著提高。第二是可預期的範圍，能估就給出還有幾步，不能估至少說明這通常需要多久。第三是可介入，隨時能停止、能追加說明、能修正方向。看著代理走錯方向卻無法阻止，是最糟糕的體驗。第四是結果可審查。

展示的細節要拿捏。完整的推理鏈會資訊過載，而且暴露了可能錯誤或混亂的中間思考。所以我會用摘要式的進度加上可展開的細節，預設顯示一行正在檢查庫存，點開才看到具體的工具呼叫。

還有一點，錯誤與不確定要誠實展示。隱藏問題並給一個看起來完整的答案，比坦承我查不到某項資訊糟糕得多。因為前者會讓使用者在不知情的情況下採信一個不完整的結果。而實務上坦承限制的產品反而更容易獲得信任。

## 常見追問

### 該不該展示模型的「思考過程」？

**核心答案**：展示摘要，不展示原始的推理鏈。原始推理往往冗長、反覆、包含被否決的方向——展示它會讓使用者困惑，也讓產品顯得不專業。**但完全隱藏又失去了透明度**。折衷是「把推理轉換成幾條簡潔的進度描述」，並在需要時提供完整記錄的入口（例如給進階使用者或用於除錯）。

**詳細解析**：「展示思考有一個意外的副作用：它改變了使用者對錯誤的歸因」。當使用者看到 Agent 的推理過程——它出錯時，使用者更容易理解「它是怎麼想錯的」，於是更能容忍；而一個黑箱式的錯誤答案會被歸因為「這個東西不可靠」。所以適度的透明實際上提升了對錯誤的耐受度。但要注意反面：展示的思考如果本身充滿了自我懷疑與反覆，會降低使用者對結果的信心——**即使最終答案是對的**。所以摘要的措辭很重要：呈現「已完成的步驟」而非「掙扎的過程」。這是一個純粹的產品設計判斷，而它對使用者感受的影響比多數技術優化都大。

**面試回答方式**：給折衷方案（展示摘要、提供完整記錄的入口）並說明原始推理冗長反覆的問題。核心加分點是展示思考改變了使用者對錯誤的歸因——看到推理過程時使用者更能理解「它是怎麼想錯的」因而更能容忍，而黑箱式的錯誤會被歸因為「這東西不可靠」。收在反面與措辭建議：充滿自我懷疑的思考會降低對結果的信心即使答案是對的，所以摘要應該呈現「已完成的步驟」而非「掙扎的過程」。

### Agent 需要使用者提供資訊時，怎麼設計互動？

**核心答案**：盡量減少中斷，能一次問完就不要分次問。在開始執行前先檢查「有沒有缺少的必要資訊」並一次性詢問——而不是跑到一半才發現缺一個參數。如果執行中確實需要，問題要具體且提供選項（「請選擇要取消的訂單：A、B、C」比「請提供訂單編號」好得多）。

**詳細解析**：**「前置檢查」需要 Agent 有規劃能力**：在動手前先想清楚「完成這個任務需要哪些資訊，我現在有哪些」——**這正是 Plan-and-Execute 模式的一個實際價值**（不只是為了規劃步驟，也是為了提前發現缺口）。而提供選項而非開放式提問的價值在於它同時降低了使用者的負擔與後續出錯的機率：開放式的回答需要 Agent 再解析一次（可能解析錯），而選項是結構化的。 另一個實務要點是「問題要能被跳過」：如果使用者不知道或不想回答，應該有「你決定」或「跳過」的選項並說明後果——強制回答會讓使用者卡住或隨便填一個，而後者比不回答更糟。

**面試回答方式**：給原則（能一次問完就不要分次、執行前先檢查缺口、問題要具體並提供選項）。核心加分點是指出**前置檢查需要規劃能力**——這正是 Plan-and-Execute 的一個實際價值：不只規劃步驟，也提前發現缺口；以及提供選項同時降低使用者負擔與後續出錯機率（開放式回答需要再解析一次可能解析錯）。收在**問題要能被跳過**——強制回答會讓使用者隨便填一個，而那比不回答更糟。

### 怎麼讓使用者信任 Agent 的結果？

**核心答案**：**四個機制**。**引用來源**——每個事實性的陳述都能追溯到一個工具回傳或文檔。**展示依據**——「基於這 3 筆訂單的資料」比一個沒有出處的結論可信得多。**表達不確定**——不確定的部分明確標示，而不是一律用肯定的語氣。**以及一致的可靠性**——信任是累積的，而一次嚴重的錯誤會摧毀很多次正確建立的信任。

**詳細解析**：**「信任的不對稱性」值得展開**：建立信任需要幾十次正確的表現，而摧毀它只需要一次明顯的錯誤——**尤其是「自信地說錯」這種形式**。所以產品策略上，「寧可保守也不要自信地出錯」通常是對的：一個經常說「這部分我不確定，建議你確認」的 Agent，長期的使用者信任高於一個總是給出肯定答案但偶爾大錯的。這個判斷影響很多具體的設計決定（閾值設多嚴、什麼時候拒答、什麼時候轉人工）。而它也解釋了為什麼「校準」在產品層面比「準確率」更重要——因為使用者需要的不只是正確的答案，還有「知道什麼時候該相信」的能力。

**面試回答方式**：給四個機制。核心加分點是展開**信任的不對稱性**——建立需要幾十次正確表現，摧毀只需要一次明顯的錯誤，尤其是「自信地說錯」，所以「寧可保守也不要自信地出錯」通常是對的。收在更深的判斷：這解釋了為什麼校準在產品層面比準確率更重要——使用者需要的不只是正確的答案，還有「知道什麼時候該相信」的能力。
