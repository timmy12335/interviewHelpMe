# 題目

在設計一個涉及多個步驟（可能是多個工具呼叫，也可能是多個子 Agent）的 Agent 工作流程時，常見的「編排（Orchestration）模式」有哪幾種？各自適合用於什麼樣的情境？

## 核心答案

Agent 工作流程的編排模式大致可以被區分成幾種**常見的核心型態**——**(1) 序列式（Sequential）**：多個步驟**依照固定的先後順序**一個接著一個依序執行，**前一個步驟的輸出**作為**下一個步驟的輸入**，適合用於**步驟之間存在明確先後依賴關係**的情境（這正是前面（見 [[003-planning-task-decomposition.md]]）已經深入討論過的『子任務之間存在先後依賴關係』這種情況的具體實現）；**(2) 平行式（Parallel）**：多個步驟**彼此不存在依賴關係，被同時平行地發起、執行**，等到**所有平行的步驟都完成**之後再把這些平行步驟各自的結果**彙整起來**，適合用於**多個子任務彼此獨立、可以被同時處理**的情境（這能帶來前面（見 [[../ai-llm/022-function-calling.md]]）已經討論過的『識別平行處理機會以提升效率』這個效益）；**(3) 條件式路由（Conditional Routing）**：依照**當前的具體情境或某個判斷結果**動態地決定**接下來應該走哪一條不同的執行路徑**（而不是一律固定地走同一條路徑），適合用於**任務本身存在多種可能的不同處理方式、需要依照具體情況做出選擇**的情境；**(4) 迴圈式（Loop）**：**反覆地執行同一組步驟**直到某個**明確的終止條件**被滿足為止（這某種程度上呼應了前面（見 [[002-react-pattern.md]]）已經深入討論過的 ReAct 那種持續循環的核心運作方式），適合用於**需要反覆嘗試、逐步逼近目標**的情境。實務上一個**真實、複雜的 Agent 工作流程**經常**不會只單純地套用其中一種模式**，而是**組合、混用這幾種不同的模式**，來應對**這個任務本身實際上存在的複雜結構**。

## 詳細解析

**序列式和平行式的核心判準——依照前面已經深入討論過的『子任務依賴關係』**：判斷**應該用序列式還是平行式**去編排某幾個具體的步驟，核心的判準正是前面（見 [[003-planning-task-decomposition.md]]、[[../ai-llm/022-function-calling.md]]）已經反覆深入討論過的**「這些步驟之間是否存在依賴關係」**——如果**步驟 B 的執行需要依賴步驟 A 先被完成、並取得某個特定結果**，這兩個步驟就**必須**用**序列式**編排（先執行 A、再執行 B）；而如果**這幾個步驟彼此完全獨立、不互相依賴**，就應該優先考慮用**平行式**編排來**縮短整體完成這些步驟所需要的總時間**——實務上一個**經過審慎設計的工作流程**會**仔細地梳理出整個任務被拆解出來的各個具體步驟之間實際上存在著怎樣的依賴關係圖**，只有**那些確實存在先後依賴的步驟**才用**序列式**串接；其餘**彼此獨立**的步驟則**盡可能地用平行式**去同時發起、執行，來**在維持正確性（不違反任何實際存在的依賴關係）的前提下把整體的執行效率最大化**。

**條件式路由——讓工作流程具備依照實際情況動態應變的彈性**：**條件式路由**這種編排模式某種程度上是把前面（見 [[002-react-pattern.md]]）已經深入討論過的**『依照最新的實際觀察結果動態決定接下來怎麼做』**這個核心思路**具體地體現在一個更加結構化的工作流程設計裡**——它讓一個工作流程**不再只是一條單一、固定不變的執行路徑**，而是**在某些關鍵的分岔點依照當時實際遇到的具體情況（可能是某個前置步驟的結果、或者某個明確的判斷條件）動態地選擇接下來應該走哪一條不同的具體路徑**——舉例來說，一個處理客戶請求的工作流程可能在**判斷這個請求的性質**這個環節設置一個條件式路由——如果判斷是**一般性的資訊查詢**，就走**一條相對單純、快速**的處理路徑；但如果判斷是**涉及複雜爭議、需要額外審慎處理**的請求，就改為走**另一條涉及額外審核步驟**的處理路徑。這種**「依照實際情況動態選擇不同執行路徑」**的能力，讓一個工作流程能夠**更加靈活、恰當地因應各種不同性質的具體情境**，而不是**用同一套僵固不變的固定流程**去處理**所有可能性質截然不同**的各種情況。

**混合式編排的實務重要性——真實世界的複雜任務通常需要同時運用好幾種不同的編排模式**：需要被特別強調的是——**真實世界裡一個具備一定複雜度**的 Agent 工作流程**通常並不會只是單純地套用其中單一一種**編排模式，而是**需要在工作流程的不同環節分別套用最適合那個具體環節性質的編排模式**——例如一個完整的工作流程可能是——**先用一個條件式路由去判斷這個任務的整體性質**；接著依照這個判斷結果走某一條具體的處理路徑，這一條路徑本身可能又包含**幾個彼此存在先後依賴關係的序列式步驟**；而這些序列式步驟裡的**其中某一個步驟**可能本身又涉及**需要反覆嘗試好幾輪的迴圈式**運作（例如前面（見 [[002-react-pattern.md]]）已經討論過的 ReAct 那種思考－行動－觀察循環）；而這個序列裡的另一個步驟則可能涉及**幾個彼此獨立、可以被平行處理**的子任務。這種**「在一個完整的工作流程裡，不同的具體環節分別套用最恰當那個環節性質的編排模式」**的思路，正是讓一個 Agent 系統能夠**同時兼顧、發揮**這幾種**不同編排模式各自擅長處理**的不同性質情境所帶來的加乘效益，而不是**被迫用單一種編排模式**去**削足適履地**處理**所有可能性質截然不同**的各種子任務。

## 面試回答方式

先給出四種常見編排模式的框架——「序列式是多個步驟依照固定先後順序依序執行，前一個步驟的輸出作為下一個步驟的輸入，適合步驟之間存在明確先後依賴關係的情境;平行式是多個彼此不存在依賴關係的步驟同時發起執行，等所有平行步驟完成後再彙整結果，適合多個子任務彼此獨立可以同時處理的情境;條件式路由是依照當前具體情境或某個判斷結果動態決定接下來走哪一條不同執行路徑，適合任務本身存在多種可能處理方式需要依情況選擇的情境;迴圈式是反覆執行同一組步驟直到某個明確終止條件被滿足，適合需要反覆嘗試逐步逼近目標的情境」。給出序列式和平行式的核心判準——「判斷用哪種模式的核心判準，正是這些步驟之間是否存在依賴關係，如果存在必須用序列式串接，如果彼此獨立則應優先考慮用平行式來縮短整體完成時間，這呼應了之前討論過的識別平行處理機會以提升效率這個核心思路」。可以補充條件式路由的價值——「這某種程度上是把之前討論過的依照最新實際觀察結果動態決定接下來怎麼做這個核心思路，具體體現在一個更結構化的工作流程設計裡，讓工作流程不再只是單一固定不變的執行路徑，而能在關鍵分岔點依照實際情況動態選擇不同路徑」。一定要強調混合式編排的實務重要性——「真實世界裡具備一定複雜度的Agent工作流程，通常不會只單純套用其中一種模式，而是需要在工作流程的不同環節，分別套用最適合那個具體環節性質的編排模式，同時兼顧發揮這幾種模式各自擅長處理的不同性質情境所帶來的加乘效益」，展現你對Agent工作流程編排模式，有完整、且具備實務混用視野的理解。

## 常見追問

### 如果一個條件式路由的判斷本身是依靠大型語言模型自己去判斷應該走哪一條路徑，而不是依靠明確、固定的規則（例如 if-else 條件式判斷），這和傳統軟體工程裡的條件式邏輯有什麼本質上的不同？

**核心答案**：**核心的本質差異在於「判斷的依據是明確、固定的規則，還是依靠模型基於語意理解所做出的機率性判斷」**——傳統軟體工程裡的條件式邏輯（例如 if-else）依靠的是**明確、可以被程式碼精確定義的判斷條件**（例如『如果這個數值大於某個明確的門檻，就走這條路徑』），這種判斷**具備絕對的確定性和可預測性**（給定相同的輸入，**永遠**會得到**相同的判斷結果**）；而**依靠大型語言模型去做條件式路由**的判斷，本質上是**依靠模型對當前情境的整體語意理解**去做出一個**機率性的判斷**——這種判斷**具備更高的彈性**（能夠處理那些**難以被簡化成明確、固定規則**的模糊、複雜情境），但相對地**也喪失了**傳統條件式邏輯那種**絕對的確定性和可預測性**（同樣的輸入內容，即使只是措辭上些微不同的表達方式，都可能導致模型做出**不同的路由判斷**）。

**詳細解析**：這題要求把**「用大型語言模型去做條件式路由判斷」**這件事情和**傳統軟體工程裡行之有年的 if-else 邏輯判斷**做**具體、精確的比較**，考察是否理解**兩者雖然在『依照某個判斷去決定接下來走哪一條路徑』**這個**表面的功能**上看似相似，但**背後運作的本質其實有著根本性的差異**。理解這個核心差異需要回顧這篇文章反覆建立的核心認知——**大型語言模型本質上是透過對連續的自然語言文字做語意理解，去做出各種判斷和決策**——這種**基於語意理解的判斷方式**相較於傳統的、**基於明確程式碼邏輯**的判斷方式，帶來一組**截然不同的優劣勢權衡**——**優勢**方面：**基於語意理解**的判斷能夠處理那些**本質上難以被簡化成一組窮盡、明確的固定規則**的模糊、開放性情境（例如**『判斷這位使用者提出的請求語氣是否帶有強烈的不滿情緒』**這種判斷很難被簡化成一套**明確、窮盡列舉所有可能情況**的固定規則，但模型透過它對自然語言語意的理解能力卻能夠相對自然地做出這種判斷）；**劣勢**方面：正因為這種判斷是**基於某種機率性的語意理解**，而**不是明確、固定不變**的規則，它就**喪失了**傳統 if-else 邏輯所具備的**絕對確定性**——同樣的『概念性情境』即使只是**用略微不同的措辭方式**去表達，都**有可能**導致模型做出**不完全相同的路由判斷**（這某種程度上也呼應了前面已經反覆討論過的**模型的機率性、非絕對確定性運作本質**這個核心認知）。這種**「用語意理解取代明確規則」**所帶來的**確定性和可預測性**的降低帶來一個相當重要的實務啟示——**在設計一個涉及條件式路由的工作流程時**應該**依照這個具體的路由判斷本身的性質**去**恰當地選擇應該用明確的固定規則、還是用模型的語意理解**去做這個判斷——如果**這個判斷本身其實可以被簡化成一組相對明確、窮盡的固定規則**（例如**『判斷某個數值是否超過某個明確的門檻』**這種相對單純的判斷），**應該優先採用傳統的、明確的規則式邏輯**（這某種程度上呼應了前面（見 [[015-computer-use-browser-agents.md]] 的常見追問）已經討論過的核心思路——**優先採用更加精確、可靠**的判斷方式）；只有在**這個判斷本身確實涉及難以被窮盡列舉成明確規則的模糊、開放性語意理解**時，才**真正值得**交給**大型語言模型**去做這種基於語意理解的判斷。理解「核心的本質差異在於判斷的依據是明確固定的規則、還是依靠模型基於語意理解所做出的機率性判斷，傳統軟體工程的if-else依靠明確可被程式碼精確定義的判斷條件，具備絕對的確定性和可預測性;而依靠大型語言模型做條件式路由判斷，本質上是依靠模型對當前情境的整體語意理解去做出一個機率性判斷，具備更高彈性(能處理難以被簡化成明確固定規則的模糊複雜情境)，但也喪失了傳統條件式邏輯那種絕對確定性和可預測性，同樣的輸入內容即使只是措辭略微不同的表達方式，都可能導致模型做出不同的路由判斷，實務上應該依照這個具體路由判斷本身的性質，恰當選擇用明確固定規則還是用模型語意理解去做判斷，如果判斷本身可以被簡化成相對明確窮盡的固定規則就應該優先採用傳統規則式邏輯，只有在判斷確實涉及難以被窮盡列舉成明確規則的模糊開放性語意理解時，才真正值得交給大型語言模型去做這種基於語意理解的判斷」，展現你能對大型語言模型驅動的條件式路由和傳統程式碼邏輯，做出精確的本質性比較，並給出恰當的技術選型判準。

**面試回答方式**：先給出核心本質差異——「核心差異在於判斷依據是明確固定的規則、還是依靠模型基於語意理解所做出的機率性判斷，傳統軟體工程的if-else依靠明確可被程式碼定義的判斷條件，具備絕對的確定性和可預測性;而依靠大型語言模型做路由判斷，是依靠模型對當前情境的語意理解做出機率性判斷」。給出兩種方式各自的優劣勢——「語意理解判斷的優勢是能處理難以被簡化成明確固定規則的模糊開放情境，但劣勢是喪失了傳統邏輯的絕對確定性，同樣的輸入內容即使措辭略微不同，都可能導致模型做出不同的路由判斷」。給出實務選型判準——「應該依照具體路由判斷本身的性質做選擇，如果判斷本身可以被簡化成相對明確窮盡的固定規則，應該優先採用傳統規則式邏輯;只有判斷確實涉及難以窮盡列舉成明確規則的模糊語意理解時，才真正值得交給大型語言模型」。

### 在設計一個序列式的工作流程時，如果其中某一個步驟執行失敗，整個序列應該如何因應，才不會讓後續的步驟建立在一個錯誤或不完整的基礎上？

**核心答案**：**核心的因應原則是——「明確地停止或調整後續步驟，而不是讓錯誤靜默地被忽略、繼續依照原本的計畫盲目地往下執行」**——具體的做法通常包括幾種選項——**(1) 立即中止整個序列**：如果這個失敗的步驟是後續所有步驟都**不可或缺的關鍵前提**，最直接的做法是**立即停止整個序列的後續執行**，並如實地回報這個失敗，而不是勉強繼續往下執行那些**已經失去必要前提基礎**的後續步驟；**(2) 觸發重新規劃**：這正是前面（見 [[008-plan-and-execute.md]]）已經深入討論過的**重新規劃機制**——依照這個失敗的具體情況重新評估、調整接下來的計畫（例如尋找替代方案、或者調整整體目標）；**(3) 依照預先設計好的錯誤處理路徑，走一條額外的『補救』分支**：這某種程度上是前面（見核心答案）已經討論過的**條件式路由**這個概念具體應用在『因應錯誤』這個特定情境上——事先就針對**『某個關鍵步驟可能失敗』**這種情況額外地設計好一條**專門用來處理這種失敗情況**的補救路徑。

**詳細解析**：這題要求把前面已經反覆強調的一個核心原則——**「錯誤不應該被靜默地忽略，而應該被明確地處理」**（這是前面（見 [[005-multi-agent-systems.md]]）已經深入討論過的、在**多工具協同呼叫**和**多代理系統（Multi-Agent System）**的情境裡反覆出現的核心議題）**具體地套用到序列式工作流程這個更加基礎、通用的情境上**，考察是否能夠把這個**貫穿整篇文章、反覆出現的核心原則**正確地**融會貫通應用到每一個新的具體場景**。理解這個問題的核心在於回顧——**序列式編排**之所以被稱為『序列』，正是因為**後續的每一個步驟本質上都是建立在前面步驟已經成功完成、並提供了某個可靠結果這個前提之上**。如果**這個前提**因為**某個前面的步驟執行失敗**而**不再成立**，卻**依然讓後續的步驟盲目地繼續往下執行**（彷彿這個前面的步驟**依然是成功完成**的），這**幾乎必然**會導致**後續的每一個步驟**都是**建立在一個實際上已經不成立、或者不完整的錯誤基礎之上**。這種**「持續在一個已經出錯的基礎上繼續疊加更多後續動作」**的現象**幾乎總是會讓最終的結果變得更加難以收拾、更加難以追溯問題的真正根源**（這某種程度上也呼應了前面（見 [[012-observability-tracing.md]]）已經深入討論過的『錯誤沿著執行鏈逐步累積、放大』這個核心現象）。因此一個**設計得足夠穩健**的序列式工作流程**必須**在**每一個步驟完成之後**都**額外地做一次明確的『這個步驟是否真的成功完成』的檢查**，而**不是**天真地假設**只要這個步驟被呼叫執行了，它就一定會順利成功**；一旦這個檢查發現**某個步驟實際上失敗**，就**必須明確地觸發**前面提到的這幾種因應機制之一（中止、重新規劃、或是走額外的補救分支），而**絕對不能**讓這個**已經發生的失敗**被**靜默地忽略**，導致後續所有的步驟**都繼續盲目地**在一個**已經失去有效前提**的基礎上運作下去。理解「核心因應原則是明確地停止或調整後續步驟，而不是讓錯誤靜默被忽略、繼續依照原本計畫盲目往下執行，這呼應了之前反覆強調的錯誤不應該被靜默忽略而應該被明確處理這個核心原則，序列式編排之所以被稱為序列，正是因為後續每個步驟本質上都是建立在前面步驟已經成功完成並提供可靠結果這個前提之上，如果這個前提因為某個前面步驟執行失敗而不再成立，卻依然讓後續步驟盲目繼續往下執行，這幾乎必然導致後續每個步驟都建立在一個實際上已經不成立的錯誤基礎之上，這種持續在已出錯基礎上疊加更多後續動作的現象，幾乎總是會讓最終結果變得更難收拾、更難追溯問題根源，這也呼應了之前討論過的錯誤沿著執行鏈逐步累積放大這個核心現象，因此一個設計得足夠穩健的序列式工作流程必須在每個步驟完成後都額外做一次明確的成功與否檢查，一旦發現失敗就必須明確觸發中止、重新規劃、或走額外補救分支這幾種因應機制之一」，展現你能把「錯誤不應被靜默忽略」這個貫穿整篇文章的核心原則，正確且具體地應用到序列式工作流程這個新的具體場景。

**面試回答方式**：先給出核心因應原則——「核心原則是明確地停止或調整後續步驟，而不是讓錯誤靜默被忽略、繼續依照原本計畫盲目往下執行」。給出三種具體因應做法——「立即中止整個序列(如果這個步驟是後續所有步驟都不可或缺的關鍵前提);觸發重新規劃機制(依照失敗情況重新評估調整接下來的計畫);或依照預先設計好的錯誤處理路徑，走一條額外的補救分支」。解釋為什麼這件事很重要——「序列式編排之所以叫序列，正是因為後續每個步驟都建立在前面步驟已經成功完成這個前提之上，如果這個前提不再成立卻依然讓後續步驟盲目繼續執行，幾乎必然導致後續每個步驟都建立在一個已經不成立的錯誤基礎之上，這呼應了之前討論過的錯誤沿著執行鏈逐步累積放大這個核心現象，因此每個步驟完成後都必須額外做一次明確的成功與否檢查」。

### 迴圈式編排如果設計不當，是不是可能導致 Agent 陷入永遠無法滿足終止條件的無窮迴圈？應該如何預防這種情況？

**核心答案**：**確實可能發生這種風險**——這某種程度上呼應了前面（見 [[010-sandbox-code-execution-security.md]]）已經深入討論過的核心風險——**即使完全出於善意、不帶任何惡意企圖**，一個**迴圈式的編排**如果它的**終止條件設計得不夠周全、或者這個任務本身實際上永遠無法滿足這個終止條件**，就可能導致這個 Agent **陷入持續反覆執行、卻永遠無法結束**的無窮迴圈。因應這種風險，實務上**最基本、也最重要**的預防手段是——**除了設計一個『任務實際達成時應該被滿足』的終止條件以外，額外地設置一個『最大反覆次數上限』這種強制性的安全網**——不管這個原本設計的終止條件是否真的被滿足，只要這個迴圈**反覆執行的次數**達到或超過這個事先設定好的上限，就**強制終止**這個迴圈的執行（即使這意味著任務最終**沒有辦法**被真正完成，也好過讓這個 Agent **永遠陷入無法脫身的無窮迴圈**裡）。

**詳細解析**：這題把前面（見 [[010-sandbox-code-execution-security.md]]）已經深入討論過的**『無心疏漏也可能導致資源使用失控』**這個核心洞察**具體地延伸應用到迴圈式編排這個具體的工作流程設計情境**上，考察是否能夠理解**這個已經建立的核心洞察**同樣**適用於這個更加具體的架構設計場景**。理解這個問題的核心在於回顧——**迴圈式編排**之所以能夠**正常、有效地運作**，核心的隱含前提是——**這個迴圈的『終止條件』必須真的會在某個合理的時間點被滿足**——但**這個前提**並**不是一種可以被天真地理所當然假設**的事情——可能因為**這個終止條件本身的設計存在某種疏漏**（例如這個終止條件依靠某個實際上**永遠不會發生**的特定狀況），或者**這個任務本身因為某種原因**（例如這個任務實際上根本**沒有辦法**被這個 Agent **用它目前所具備的能力和工具**真正達成）導致**這個終止條件實際上永遠都不會被滿足**，這種情況下如果**沒有額外的保護機制**，這個迴圈就會**持續不斷地反覆執行下去**。這種**「即使終止條件理論上設計得再周全，依然不能假設它在實際運作時一定會被順利滿足」**的審慎態度帶來一個相當重要的實務啟示——**任何一個涉及反覆迴圈的機制都應該同時具備兩層不同性質的終止條件**——**「任務實際達成時應該被滿足的理想終止條件」**、以及**「不管理想終止條件是否被滿足，都會強制介入終止執行的保底安全網（最大反覆次數上限）」**——只有同時具備這兩層終止條件，才能**確保**即使**理想的終止條件因為任何預期外的原因而始終無法被滿足**，這個系統依然**不會陷入永遠無法脫身的困境**。這種**「同時設置理想終止條件和保底安全網」**的設計思路某種程度上也呼應了一個在設計**任何涉及反覆執行或持續運作**的系統時（不管是這裡討論的 Agent 迴圈、還是傳統程式設計裡的 while 迴圈）都值得反覆提醒自己的核心工程原則——**「永遠不要只依靠單一個理想化的終止條件，而應該額外地準備一層保底的、強制性的安全網」**。理解「確實可能發生這種風險，這呼應了之前討論過的即使完全出於善意也可能導致資源使用失控這個核心洞察，一個迴圈式編排如果終止條件設計不夠周全或這個任務實際上永遠無法滿足這個終止條件，就可能導致Agent陷入持續反覆執行卻永遠無法結束的無窮迴圈，因應這種風險最重要的預防手段是除了設計一個理想的終止條件以外，額外設置一個最大反覆次數上限這種強制性安全網，不管理想終止條件是否被滿足，只要反覆執行次數達到上限就強制終止，任何涉及反覆迴圈的機制都應該同時具備兩層不同性質的終止條件——任務實際達成時應該被滿足的理想終止條件、以及不管理想終止條件是否被滿足都會強制介入終止的保底安全網，這呼應了永遠不要只依靠單一個理想化終止條件、而應該額外準備一層保底強制性安全網這個核心工程原則」，展現你能把之前建立的資源失控風險洞察，延伸應用到迴圈式編排這個具體架構設計情境，並給出具體的雙層終止條件設計原則。

**面試回答方式**：先確認這個風險確實存在——「確實可能發生，這呼應了之前討論過的即使完全出於善意也可能導致資源使用失控這個核心洞察，一個迴圈如果終止條件設計不夠周全或任務本身實際上永遠無法滿足這個終止條件，就可能陷入無窮迴圈」。給出核心預防手段——「最重要的預防手段是除了設計一個任務實際達成時應該被滿足的理想終止條件以外，額外設置一個最大反覆次數上限這種強制性安全網，不管理想終止條件是否被滿足，只要反覆次數達到上限就強制終止」。給出更普遍的設計原則——「任何涉及反覆迴圈的機制都應該同時具備理想終止條件和保底安全網這兩層不同性質的終止條件，這呼應了永遠不要只依靠單一個理想化終止條件、而應該額外準備一層保底強制性安全網這個核心工程原則」。
