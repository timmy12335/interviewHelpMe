# 題目

在實際開發一個 Agent 應用時，面對市面上各種現成的 Agent 開發框架（例如提供現成的 ReAct、Plan-and-Execute 等架構實現的框架工具），相較於**完全從零開始，自己手動撰寫整套 Agent 執行邏輯**，使用這類現成框架通常能帶來什麼樣的效益？實務上選擇是否採用、以及採用哪一個框架時，應該考量哪些因素？

## 核心答案

使用現成的Agent開發框架，相較於**完全從零開始自己手動撰寫**通常能帶來，幾個核心效益——**(1) 省去，重複造輪子的開發成本**：前面(見 [[002-react-pattern.md]]、[[008-plan-and-execute.md]])已經深入討論過的各種核心架構模式(ReAct、Plan-and-Execute等)，這些框架通常已經提供了**現成、經過，一定程度驗證，的實作**開發者不需要**從頭自己重新實作這些已經是業界相對，成熟、標準化，的核心運作邏輯**；**(2) 提供現成的，周邊基礎設施整合**：許多，前面已經深入討論過的周邊機制(如，前面(見 [[012-observability-tracing.md]])的可觀測性/追蹤、前面(見 [[019-state-management-checkpointing.md]])的狀態管理/檢查點、前面(見 [[006-agent-communication-protocols.md]]、[[007-mcp-architecture.md]])的工具整合協定)，很多，成熟的框架，都已經**內建、提供，現成的支援**，不需要開發者自己**從零開始**額外實作。實務上考量是否採用、以及採用哪個框架時，核心的判斷因素，包括——**(1) 這個框架，所支援的核心架構模式，是否真的符合自己，具體應用場景，實際，需要的架構思路**(這，呼應了前面已經，反覆討論過的『依照，具體情境的實際需求，做恰當選擇』這個核心原則)；**(2) 這個框架，是否提供了自己實際上，真的會，用到的那些，周邊基礎設施整合**；**(3) 這個框架的成熟度、社群支援、以及，未來是否會持續得到維護**這类**長期使用，可靠性**方面的考量。

## 詳細解析

**框架帶來的核心價值——避免，重複實作已經是，業界相對成熟共識的核心架構模式**：延續，核心答案已經，提到的核心效益——像，前面已經深入討論過的**ReAct**、**Plan-and-Execute**這些，核心架構模式，某種程度上，已經是**業界經過一定程度實務驗證，累積下來的相對成熟共識**，一個成熟的框架，通常會**把這些已經相對標準化，的核心運作邏輯**，**封裝成現成、可以直接被呼叫，使用的元件**，開發者只需要**依照框架，提供的介面，去設定自己具體任務，所需要的參數(如，系統提示、可用工具)**，就能夠**直接套用這些已經是相對，成熟共識的核心架構邏輯**，而**不需要**自己**從頭去重新實作這些其實，已經有很多人，深入研究、驗證過的核心邏輯**，這種**「不需要重複發明已經，存在的成熟輪子」**的效益，某種程度上，也呼應了一個**軟體工程領域普遍，適用**的核心原則——**「優先，運用既有經過，驗證的成熟方案，而不是盲目地從零開始，重新造輪子」**。

**選型的核心考量——框架，提供的具體能力，是否真的吻合自己，具體場景的實際需求**：**選擇，是否採用一個框架**一個**相當，關鍵**的判斷準則，是——**這個框架，所支援的核心架構模式，和提供的周邊整合能力**，是否**真的吻合**自己,**具體應用場景**的**實際需求**——這，直接呼應了這篇文章反覆，強調的核心原則——**「不同的具體任務，情境適合，不同的具體架構(例如，前面(見 [[002-react-pattern.md]])已經深入討論過的，ReAct，適合執行路徑高度依賴，即時回饋的任務；Plan-and-Execute，則適合需要，全局規劃視野的任務)」**——如果，一個**具體的應用場景**，實際上，**更需要**某種，特定的架構模式(例如，前面(見 [[008-plan-and-execute.md]])已經討論過的Plan-and-Execute)，但，**選用的框架**，卻**只提供了**另一種不那麼，適合的架構模式(例如，只支援，單純的ReAct)，即使這個框架本身**其他方面做得再完善**這種**「框架，提供的核心架構，和自己實際需求，不夠吻合」**的情況，依然**不是，一個理想的選擇**，因此，**選型，的核心判準**，**不應該**只是**看這個框架是否『流行、知名』**而應該**回歸到****「這個框架具體，提供的能力，和架構思路是否真的貼合我自己這個，具體應用場景，實際的需要」**這個，**更加務實、聚焦**的判準。

**「先理解底層原理再選用，框架」——避免，只是盲目地套用框架而不理解，背後的核心運作邏輯**：一個，值得被特別，強調的重要提醒，是——即使，決定**採用一個，現成的框架**，去加速開發依然**強烈建議****先充分理解**前面這整個類別已經，深入討論過的**各種核心概念和運作原理**(例如，ReAct、Plan-and-Execute，各自的核心運作邏輯，和適用情境、記憶系統，的分層設計、狀態管理和檢查點，機制、以及各種，安全性考量)，而**不是**，只是**表面上學會怎麼呼叫這個框架，提供的API，函式**，卻**完全不理解****這些函式背後實際上，是依照，什麼樣的核心邏輯，在運作**——這種，**「理解底層原理而不是只停留在表面的，框架API使用」**的重要性，體現在幾個，方面——**當，這個框架，的預設行為，不符合自己，具體場景的特殊需求**時，**只有****真正理解，底層原理**的開發者，才能**判斷清楚應該如何恰當地客製化調整**，這個框架的具體設定或行為(而，**不是**只能**無助地被，這個框架的預設行為，牽著鼻子走**)；當這個框架**出現某種異常行為或執行不如預期**時**只有**理解，底層原理的開發者，才能**有效地去診斷、除錯**這個問題究竟出在哪裡(而不是只能**茫然地猜測是框架本身有問題**)這種**「框架是加速，開發的實用工具，但不能取代對，底層核心原理，的紮實理解」**的認知，正是這整個Agent類別，所希望能夠傳達的一個**最核心、也最值得被，牢記**的學習心法。

## 面試回答方式

先給出框架帶來的核心效益——「相較於完全從零開始，使用現成框架能省去重複造輪子的開發成本(前面討論過的ReAct、Plan-and-Execute等核心架構模式，框架通常已提供現成經過一定驗證的實作)，以及提供現成的周邊基礎設施整合(如可觀測性追蹤、狀態管理檢查點、工具整合協定，很多成熟框架都已內建支援)」。給出選型的核心判準——「選型時不應該只看框架是否流行知名，而應該回歸到這個框架具體提供的核心架構模式和周邊整合能力，是否真的貼合自己具體應用場景實際的需要這個更務實的判準，例如如果場景更需要Plan-and-Execute那種全局規劃視野，但選用的框架只提供ReAct，即使框架其他方面做得再完善，這種不夠吻合的情況也不是理想選擇」。一定要強調理解底層原理的重要性作為收束——「即使決定採用現成框架，依然強烈建議先充分理解這整個類別已經深入討論過的各種核心概念和運作原理，而不只是表面學會怎麼呼叫框架提供的API，因為只有真正理解底層原理的開發者，才能在框架預設行為不符合特殊需求時判斷如何恰當客製化調整，也才能在框架出現異常行為時有效診斷除錯，框架是加速開發的實用工具，但不能取代對底層核心原理的紮實理解」，展現你對Agent框架選型有務實的判斷準則，並能將這個相對基礎的問題，連結到整個Agent類別最核心的學習心法——理解原理比會用工具更重要。

## 常見追問

### 如果，一個團隊一開始就選用了某個，現成的Agent框架，後來發現這個框架的某些，核心設計理念，和自己實際需求越來越不吻合這時候應該如何，決策——是，忍痛更換框架還是想辦法在，既有框架基礎上，做大量客製化?

**核心答案**：**這，是一個需要仔細權衡,『更換成本』和『長期，持續遷就，不吻合框架，所累積的隱性成本』,這两者，相對輕重**的具體決策，**沒有一個，放諸四海皆準的標準答案**——需要，考量的核心因素，包括——**(1) 目前，這個系統已經圍繞著，這個舊框架，投入了多少，既有的開發成果**(如果，投入已經相當龐大『更換框架』,的直接成本，會相應地更高)；**(2) 這種,『不吻合』的程度，和趨勢**(如果，只是**輕微的不吻合、且未來看起來也不會變得更嚴重**或許值得繼續**在，既有框架基礎上，做適度的客製化**去，將就；但如果這種不吻合**已經相當嚴重、且隨著需求持續演進只會越來越嚴重**長期下來**持續地在一個根本，不適合的框架基礎上，做越来越吃力的客製化將就**付出的**隱性，累積成本(開發效率下降、程式碼，越來越難以維護)**可能，反而**遠超過****一次性忍痛，更換框架**的直接成本。

**詳細解析**：這題，把**框架選型**這個，議題延伸到一個**相當現實、且需要，務實的商業/工程判斷**——**「一開始的選擇，錯了(或者不再適合)之後應該如何決策」**這個情境考察是否能夠**避免給出一個過於，武斷、非黑即白**的簡單答案，而能夠**展現對這类，真實世界的，兩難決策**所，需要的**細膩權衡能力**。理解這個問題的核心在於，認識到——**這类，決策本質上是一種需要比較两種不同性質，成本**的權衡——**「更換框架」**，帶來的是**一次性、但通常相對明確、可以被較精確，估算**的**直接成本**(需要，投入多少人力、多少時間去把，既有的系統，重新遷移、改寫到，新的框架上)；而**「繼續在，不吻合的框架基礎上，做客製化將就」**帶來的則是**持續、且通常較，隱性、不容易，被精確量化，但會隨著時間，持續累積**的**隱性成本**(例如，因為框架本身，的設計理念，和實際需求不吻合導致每一次要新增一個功能都需要**額外繞路、做一些，彆扭的客製化調整**，這種**額外的開發摩擦成本**，可能**單次看起來不算太顯著**，但**長期累積下來**可能**遠遠超過**一開始看起来**相對，明確、可怕**的『更換框架』這個，一次性成本)這種**「一次性明確，成本」vs.「持續、隱性，但長期累積可能更加，龐大的成本」**之間的權衡，某種程度上，也呼應了一個在**軟體工程領域**相當，經典的概念——**「技術債(Technical Debt)」**——**繼續，在一個已經不再，適合的基礎上，勉強將就**，某種程度上，就是在**持續地累積、擴大**一種，**技術債**——**這種，債務****短期內**可能**不會造成，立即、明顯的痛苦**，但**長期累積下來****這種持續累積，的隱性成本**，可能**遠遠超過**及早**忍痛付出一次性代價去，償還(也就是，及早更換到一個真正吻合，需求的框架)**，因此，實務上做這種決策時一個**相當，重要的思考方式**，是**不要，只是狹隘地只聚焦在『更換框架這件事情本身眼前看起來，有多痛苦、多昂貴』**，而應該**額外地去仔細，估算——『如果，繼續選擇不更換維持現狀未來這種，隱性的技術債，持續累積下去長期而言究竟會帶來多大的額外成本』**只有**同時把這两種，不同性質的成本，都納入考量、做，全面的比較**，才能做出一個**真正理性、而非，只是因為害怕眼前，更換的痛苦，而選擇鴕鳥心態，逃避**的決策。理解「這是一個需要仔細權衡更換成本和長期持續遷就不吻合框架所累積隱性成本相對輕重的具體決策，沒有放諸四海皆準的標準答案，需要考量目前已投入多少既有開發成果、以及這種不吻合的程度和演變趨勢，更換框架帶來的是一次性但通常相對明確可估算的直接成本，而繼續在不吻合框架基礎上客製化將就，帶來的是持續且較隱性、不容易精確量化但會隨時間持續累積的成本，這呼應了軟體工程領域相當經典的技術債概念，繼續在已不再適合的基礎上勉強將就，某種程度上就是持續累積擴大一種技術債，這種債務短期內可能不會造成明顯痛苦，但長期累積下來可能遠超過及早忍痛更換所付出的一次性代價，實務上做這種決策時應該避免只狹隘聚焦於更換框架眼前看起來有多痛苦，而應該額外估算如果繼續維持現狀未來這種隱性技術債持續累積下去長期而言究竟會帶來多大額外成本」，展現你對這種真實世界的兩難技術決策，具備細膩的權衡能力，而非給出過於武斷的簡單答案。

**面試回答方式**：先給出核心答案——「這是一個需要仔細權衡更換成本和長期持續遷就不吻合框架所累積隱性成本相對輕重的具體決策，沒有放諸四海皆準的標準答案，需要考量目前已投入多少既有開發成果、以及不吻合的程度和演變趨勢」。給出核心的權衡框架並連結技術債概念——「更換框架帶來的是一次性但相對明確可估算的直接成本;而繼續在不吻合框架基礎上客製化將就，帶來的是持續、較隱性、但會隨時間累積的成本，這呼應了軟體工程領域經典的技術債概念，繼續勉強將就某種程度上就是持續累積擴大技術債，這種債務短期不會造成明顯痛苦，但長期累積下來可能遠超過及早忍痛更換所付出的一次性代價」。給出決策建議——「實務上做這種決策時，不應該只狹隘聚焦於更換框架眼前看起來有多痛苦，而應該額外估算如果繼續維持現狀，未來這種隱性技術債持續累積下去長期而言究竟會帶來多大額外成本，同時把這兩種不同性質的成本都納入考量才能做出真正理性的決策」。

### 如果，一個Agent應用，規模相對簡單(例如只有單一個，固定的工作流程，幾乎不需要，太多的動態彈性)，是不是依然建議使用一個，功能齊全、支援，各種，複雜架構模式的大型框架?

**核心答案**：**不，一定如果應用場景本身相對簡單直接採用一個功能過於龐大、複雜，的大型框架，某種程度上，反而可能是一種，不必要的過度設計**——這，直接呼應了這篇文章反覆，強調的核心原則——**「不應該，盲目地追求採用最先進、最複雜，的技術方案，而應該依照具體情境，實際的需求，程度做，恰如其分的選擇」**——如果，一個應用本身**執行邏輯相對單純、固定****手動撰寫一段相對精簡，直接的程式碼**，去實現這個**相對，單純**的具體流程，可能反而**比引入一個功能龐大、但其中**絕大多數功能**這個簡單應用根本用不到，的大型框架**，更加**簡潔、容易理解、也更容易維護**(引入一個**功能過於龐大，複雜**的框架，某種程度上，也會帶來，額外的**學習成本、以及，理解、除錯這個框架本身，運作機制**的額外負擔，如果這個應用本身**根本用不到**這個框架所提供的**絕大多数複雜功能**這種，額外的負擔，某種程度上，就是一種，**不必要的浪費**)。

**詳細解析**：這題，要求把這篇文章反覆，強調的**「不應該，盲目追求，更複雜、更先進的方案，而應該依照具體需求做，恰如其分選擇」**這個核心原則，**最後一次具體地套用到框架選型這個，實務問題**上，作為**整個Agent類別，收尾**時一個**特別值得被再次，強調**的核心提醒。理解這個問題的核心在於，回顧——**這篇文章，在許多，不同的具體議題上**(從，任務分解（Task Decomposition）的粒度、到，多代理系統（Multi-Agent System）的採用時機、再，到護欄（Guardrails）的敏感度設定)，都**反覆，出現**的一個，共通的核心洞察——**「任何一種，技術方案、架構模式，或工具的採用與否都應該取決於它是否真正恰當地對應到，具體情境的實際需求，而不是因為這個方案聽起来更先進、更複雜就，理所當然地，一律採用」**這個核心洞察**同樣適用於**，**框架選型**這個，最後的具體問題——一個，**功能齊全、支援各種，複雜架構模式**的大型框架，它之所以**具備價值**正是因為它能夠**因應**那些**確實需要這些，複雜功能**的**複雜應用場景**，但如果一個應用**本身並不需要**這種複雜性(它，的執行邏輯，**本身就是相對，單純、固定**的)，這個**大型框架**所提供的**絕大多数****這個簡單應用根本，用不到**的複雜功能，就**不會帶來任何，實質的效益**，反而因為**引入這個大型框架**額外帶來了**學習、理解這個框架本身，運作機制**的額外負擔(而，這種額外負擔對一個**本身相對，簡單**的應用而言，**某種程度上，就是一種，得不償失的過度投入**)，這種**「即使是選擇一個，開發工具或框架，這種看似純粹，技術層面的決策，同樣需要回歸到『是否真正恰當對應，具體需求』這個核心判準，而不是盲目地追求採用功能最齊全、最，先進的方案」**的認知，正是這整篇文章，從Agent，的基本定義，開始一路深入探討到最後，一題框架選型**始終，一以貫之、反覆被強調**的**核心思維方式**——**技術方案的選擇，最終應該服務於，具體、實際的需求，而不是成為一種追求技術本身,『先進、複雜、完整』這種，表面指標，的目的本身**。理解「不一定，如果應用場景本身相對簡單，直接採用功能過於龐大複雜的大型框架，某種程度上反而可能是一種不必要的過度設計，這直接呼應了這篇文章反覆強調的不應盲目追求採用最先進最複雜技術方案、而應依照具體情境實際需求做恰如其分選擇這個核心原則，如果一個應用執行邏輯相對單純固定，手動撰寫一段相對精簡直接的程式碼去實現，可能反而比引入一個功能龐大但絕大多數功能根本用不到的大型框架更簡潔容易理解也更容易維護，引入功能過於龐大複雜的框架會帶來額外的學習成本、以及理解除錯這個框架本身運作機制的額外負擔，如果應用根本用不到這些複雜功能，這種額外負擔就是一種不必要的浪費」，展現你能把這篇文章貫穿始終的核心思維方式——技術方案選擇應服務於具體實際需求、而非追求技術本身的表面先進完整指標，最後一次應用到框架選型這個問題，作為對整個Agent類別核心思維方式的收束總結。

**面試回答方式**：先給出核心答案——「不一定，如果應用場景本身相對簡單，直接採用功能過於龐大複雜的大型框架，某種程度上反而可能是一種不必要的過度設計」。給出具體論證——「這直接呼應了不應盲目追求最先進最複雜方案、而應依照具體情境實際需求做恰如其分選擇這個核心原則，如果應用執行邏輯本身相對單純固定，手動撰寫一段精簡直接的程式碼，可能反而比引入一個絕大多數功能根本用不到的大型框架更簡潔、容易理解、也更容易維護，引入過於龐大複雜的框架會帶來額外的學習成本和理解除錯負擔，如果應用根本用不到這些複雜功能，這種負擔就是不必要的浪費」。可以用這個總結整個類別的核心思維——「技術方案的選擇最終應該服務於具體實際的需求，而不是成為追求技術本身先進複雜完整這種表面指標的目的本身，這也是這整篇文章從Agent的基本定義開始，一路探討到框架選型，始終一以貫之的核心思維方式」。

### 選用，某個框架之後如果未來想要同時運用，前面已經討論過的，多種不同機制(如，子代理委派、狀態檢查點、Human-in-the-Loop)，應該如何判斷這個框架是否能夠妥善支援這些不同機制彼此協同運作而不只是個別支援?

**核心答案**：**核心的判斷方式，是去檢視這個框架是否提供了一套『統一且，一致』的底層抽象概念，讓這些，不同的機制，能夠自然地建立在同一套，共通的基礎之上，彼此協同運作而不是各自獨立、彼此拼湊，而成**——如果，一個框架，**只是個別地分別提供**，**「子代理委派的功能」**、**「狀態檢查點的功能」**、**「Human-in-the-Loop，的功能」**，但這**幾項功能**各自是**基於彼此，不完全一致、甚至，互相，衝突的底層設計假設**，所**分別獨立拼湊而成**即使這個框架**表面上看起来**好像**同時支援**這**幾項，個別的能力**，實際上，要把，**這幾個機制，真正協同結合運用**時很可能會遭遇**各種難以，預期的相容性問題或彆扭的整合摩擦**，一個**真正設計精良**的框架，應該是**從一開始設計時就以一套，一致、統一的核心抽象概念(例如，某種統一的『可以被暫停、可以被持久化、可以被恢復』的任務執行單元概念)，作為基礎**讓，**子代理委派、狀態檢查點、Human-in-the-Loop**這些，不同的具體機制，都是**建立在這同一套統一，抽象概念之上**的**自然延伸和應用**。

**詳細解析**：這題，作為整個Agent類別，最後一道追問，要求對，**「框架選型」**這個議題，做一個**更加深入、也更加，綜合性**的最終檢視，考察是否能夠**把，這整個類別，已經深入討論過的多個核心機制**，**整合起来作為，評估一個框架，是否真正，設計精良**的**綜合性判斷標準**，而不是只停留在**『這個框架是否個別地分別支援這些，功能列表上的每一項』**這種，**較，表層**的檢視方式。理解這個問題的核心在於，認識到——一個，**真正設計精良**的軟體框架(不，只是，Agent框架，這其實，是任何，優秀軟體架構，共通的特質)，它之所以**能夠讓多種，不同的功能，彼此順暢地協同運作而不會出現，格格不入的整合摩擦**，關鍵通常在於這個框架**背後存在著一套，設計精良、一致的『核心抽象概念』**，讓**所有，具體的功能**，都是**依循同一套，共通的核心原則，和設計哲學**所**自然，衍生出來**的，而**不是****各自，獨立、東拼西湊**而成的——舉例來說，如果一個框架**從一開始**就把**「一個，任務(不管是，主任務、還是，委派出去的子任務)，本質上是一個可以被，暫停、可以被，持久化保存狀態、也可以，從保存的狀態，恢復接續執行」**這個核心概念，**作為整個框架，設計的基礎**，那**子代理委派**(委派出去的子任務，某種程度上，也只是另一個同樣遵循這套『可以被，暫停/持久化/恢復』核心概念的，任務單元)、**狀態檢查點**(直接，就是這套核心概念本身最，直接的具體實現)、以及，**Human-in-the-Loop**(等待人類確認，這件事，某種程度上，也只是『暫停任務、等待某個，外部事件(人類回應),、再恢復』這個核心概念的一種，具體應用情境)，這**三種**原本看似，不同的具體機制，就能**自然地統一建立**在**同一套，共通的核心抽象**之上，彼此之間**天然地就能協同運作而不會出現因為各自，底層設計假設，不一致而，導致的相容性摩擦**，理解了這種**「檢視框架是否具備一套，統一、一致的核心抽象概念，作為判斷這個框架是否真正設計精良，的關鍵判準」**，某種程度上，是一種**超越單純『功能列表，個別比對』的、更加，深層，的框架評估能力**，這種能力正是一個**真正資深、有，經驗**的工程師，在做**任何，重要的技術選型決策**時，都值得，具備的**核心鑑別能力**。理解「核心判斷方式是去檢視這個框架是否提供了一套統一且一致的底層抽象概念，讓這些不同機制能自然建立在同一套共通基礎之上彼此協同運作，而不是各自獨立彼此拼湊而成，如果一個框架只是個別分別提供這幾項功能，但各自基於彼此不完全一致甚至互相衝突的底層設計假設分別獨立拼湊而成，即使表面上看起來同時支援這幾項能力，實際上要把這些機制真正協同結合運用時很可能遭遇各種難以預期的相容性問題或彆扭整合摩擦，一個真正設計精良的框架應該是從一開始設計時就以一套一致統一的核心抽象概念作為基礎，讓子代理委派狀態檢查點Human-in-the-Loop這些不同具體機制，都是建立在同一套統一抽象概念之上的自然延伸和應用，例如如果框架從一開始就把一個任務本質上是可以被暫停可以被持久化保存狀態也可以從保存狀態恢復接續執行這個核心概念作為整個框架設計基礎，那子代理委派、狀態檢查點、以及Human-in-the-Loop這三種原本看似不同的具體機制，就能自然統一建立在同一套共通核心抽象之上，彼此之間天然就能協同運作」，展現你能把整個類別已深入討論過的多個核心機制整合起來，作為評估框架是否真正設計精良的綜合性判斷標準，展現超越單純功能列表比對的更深層框架評估能力，作為整個Agent類別的最終收束。

**面試回答方式**：先給出核心判斷方式——「核心判斷方式是去檢視這個框架是否提供了一套統一且一致的底層抽象概念，讓這些不同機制能自然建立在同一套共通基礎之上彼此協同運作，而不是各自獨立彼此拼湊而成」。給出具體判斷的警示訊號——「如果一個框架只是個別分別提供這幾項功能，但各自基於彼此不完全一致甚至互相衝突的底層設計假設拼湊而成，即使表面上看起來都支援，實際要把這些機制真正協同結合運用時，很可能遭遇各種難以預期的相容性問題或整合摩擦」。用具體例子展現統一抽象概念的價值——「一個真正設計精良的框架，可能會把一個任務本質上是可以被暫停、可以被持久化保存狀態、也可以從保存狀態恢復接續執行這個核心概念作為整個框架設計基礎，那子代理委派、狀態檢查點、以及Human-in-the-Loop這三種看似不同的機制，就能自然統一建立在同一套共通核心抽象之上，天然就能協同運作」。
