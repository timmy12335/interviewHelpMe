# 題目

什麼是 Agent 系統裡的「護欄（Guardrails）」機制？它和前面（見 [[011-human-in-the-loop.md]]）深入討論過的 Human-in-the-Loop、以及前面（見 [[010-sandbox-code-execution-security.md]]）深入討論過的沙箱機制，這幾種安全機制之間是什麼樣的關係？

## 核心答案

護欄指的是一套**額外獨立於 Agent 核心決策邏輯（通常是那個負責推理、規劃的大型語言模型）之外，專門負責審視、把關 Agent 的輸入或輸出內容是否符合某些預先定義好的規則或限制**的檢查機制——具體來說，護欄可能被設置在幾個不同的環節——**輸入護欄**：在使用者的請求被正式傳遞給 Agent 處理之前，先檢查這個輸入內容是否存在某些**已知的、明確應該被阻擋**的問題（例如明顯的惡意提示注入嘗試）；**輸出護欄**：在 Agent 產出的最終回覆或行動被正式回傳給使用者、或者被實際執行之前，先檢查這個輸出內容是否符合某些**明確的品質或安全標準**（例如是否包含不當內容、是否洩漏敏感資訊）。護欄和 Human-in-the-Loop、沙箱這幾種機制之間的關係是**互補、而非互相取代**的——**護欄**通常是一種**自動化、快速**的檢查機制（依靠明確的規則、或者一個額外的、專門負責檢查的輕量模型去做快速判斷），適合用來**攔截那些相對明確、容易被自動化辨識**的問題；而 **Human-in-the-Loop** 和**沙箱**則分別針對**「需要真正獨立、人類判斷」**和**「需要把可能的破壞行為實際隔離限制」**這兩種**護欄這種自動化檢查機制較難完全取代**的更深層防護需求。這幾種機制共同構成一個**多層次的整體安全防禦架構**。

## 詳細解析

**護欄和前面已經深入討論過的模型自身安全性（如 RLHF 對齊）的核心差異——護欄是獨立於核心模型之外的『額外』一層檢查**：理解護欄這個概念的一個關鍵切入點，是釐清它和前面（見 [[../ai-llm/019-rlhf.md]]）已經深入討論過的**『透過 RLHF 等訓練手段讓模型本身的行為更加對齊、安全』**這兩者之間的核心差異——**RLHF 這類訓練手段**是**把安全性、對齊這些考量內化到模型本身的參數行為裡**，也就是說，這是**依靠模型自己**去**具備**這種**判斷、遵循安全準則**的能力；而**護欄**則是**刻意地在模型之外額外建立一層獨立的檢查機制**。這種**「額外獨立於核心模型之外」**的設計思路之所以重要，核心原因在於——延續前面（見 [[009-self-correction-reflection.md]] 的常見追問）已經深入討論過的核心洞察——**「任何一個完全依靠同一個模型自己去做出的判斷（不管是生成、還是自我審查），都可能共享著這個模型本身固有的系統性盲點」**——如果**『安全性把關』**這件事情完全只依靠**這個模型本身（透過訓練而具備的對齊能力）**去**自己把關自己**，這種做法某種程度上**同樣繼承了**前面已經反覆討論過的**『自我審查天生存在系統性盲點風險』**這個核心侷限。護欄之所以被設計成**「額外、獨立」**的一層機制（而不是完全依賴核心模型自身的對齊能力），正是為了提供**一種不完全共享核心模型本身可能存在的系統性盲點**的**獨立防線**。

**護欄的具體實作方式——從簡單的關鍵字過濾，到運用額外的輕量分類模型**：實務上護欄的具體實作存在**不同複雜程度**的做法——**(1) 相對簡單的規則式過濾**：例如**明確地檢查輸入或輸出內容是否包含某些已知的、明確應該被阻擋的關鍵字或模式**（這種做法**簡單、快速**，但**彈性較低**，只能因應**能夠被明確窮舉列出**的已知問題模式）；**(2) 運用一個額外、獨立的輕量分類模型**：訓練（或者運用一個現成的）專門針對**「判斷某段內容是否存在某種特定問題（如是否涉及惡意提示注入、是否包含不當內容）」**這個**相對聚焦、單一**任務而特別優化的**輕量模型**去做這種判斷（這種做法相較於**簡單的規則式過濾**具備**更高的彈性**，能夠處理那些**難以被簡化成明確固定規則**的模糊情境；但相較於**動用核心的大型語言模型本身去做這種判斷**，因為這個額外的分類模型通常**規模相對較小、任務也相對單一聚焦**，能夠維持**較低的額外運算成本和延遲**）——這種**「用一個額外、獨立、且相對輕量的專門模型去做把關檢查」**的思路，某種程度上也呼應了前面（見 [[../ai-llm/018-mixture-of-experts.md]]）已經深入討論過的核心概念——**讓不同的『專家』各自專精處理不同性質的任務**，只是這裡這個『專家』被賦予的是**「專門負責安全把關」**這個特定的職責。

**護欄的固有侷限——無法完全取代更深層的 Human-in-the-Loop 和沙箱機制**：需要被誠實承認的是——**護欄**作為一種**相對快速、自動化**的檢查機制**存在它本身固有的侷限**——它**擅長攔截**那些**相對明確、能夠被自動化辨識**的問題（例如**明顯的**惡意提示注入嘗試、**明顯的**不當內容），但對於那些**需要真正深度、細膩的專業判斷**（例如前面（見 [[011-human-in-the-loop.md]] 的常見追問）已經深入討論過的『需要真正具備特定專業領域知識的人類才能妥善判斷』的情境）、或者**需要把可能的破壞行為實際物理性地隔離限制**（這是前面（見 [[010-sandbox-code-execution-security.md]]）已經深入討論過的沙箱所擅長的領域）這類更深層的防護需求，**護欄本身並不足以**完全取代這兩種各自擅長處理不同性質風險的機制。因此一個**真正成熟、完整的 Agent 安全架構**應該**同時運用****護欄（第一層快速的自動化篩查）、Human-in-the-Loop（針對真正高風險或高度不確定情境的獨立人類把關），以及沙箱（針對實際執行行為本身的物理隔離）**這幾種**分別擅長處理不同層次、不同性質風險**的機制，共同構成一個**縱深防禦**的整體安全架構（這直接呼應了前面（見 [[010-sandbox-code-execution-security.md]] 的常見追問）已經深入討論過的縱深防禦核心設計哲學）。

## 面試回答方式

先給出護欄的核心定義——「一套額外獨立於Agent核心決策邏輯之外，專門負責審視把關Agent輸入或輸出內容是否符合預先定義好規則或限制的檢查機制，通常設置在輸入護欄(檢查使用者請求是否存在已知應被阻擋的問題)和輸出護欄(檢查Agent產出內容是否符合品質或安全標準)這兩個環節」。詳細解釋護欄和依靠模型自身對齊的核心差異——「RLHF這類訓練手段是把安全性考量內化到模型本身的參數行為裡，依靠模型自己具備判斷遵循安全準則的能力;而護欄是刻意在模型之外額外建立一層獨立檢查機制，這是因為如果安全把關完全只依靠模型自己去把關自己，同樣繼承了自我審查天生存在系統性盲點這個核心侷限，護欄提供的是一種不完全共享核心模型本身可能存在系統性盲點的獨立防線」。可以補充具體實作方式的層次——「從相對簡單的關鍵字規則式過濾，到運用一個額外獨立的輕量分類模型去做更有彈性的判斷，這呼應了混合專家模型架構裡讓不同專家各自專精處理不同任務這個核心思路，只是這裡的專家被賦予的是專門負責安全把關這個職責」。一定要誠實補充護欄的固有侷限——「護欄擅長攔截相對明確、能被自動化辨識的問題，但對需要真正深度專業判斷或需要把可能破壞行為實際物理隔離這類更深層防護需求，並不足以完全取代Human-in-the-Loop和沙箱這兩種機制，一個真正成熟的Agent安全架構應該同時運用這幾種分別擅長處理不同層次風險的機制，共同構成一個縱深防禦的整體安全架構」，展現你對護欄機制的核心設計理念、實作方式、以及在整體安全架構裡的定位，有完整且深入的理解。

## 常見追問

### 如果輸入護欄和輸出護欄只能擇一先優先建置，應該優先建置哪一個？為什麼？

**核心答案**：**通常建議優先建置輸出護欄**——核心原因在於——**「輸入護欄」**本質上是一種**依靠事先列舉、預測可能存在哪些惡意輸入模式**的防禦方式，這種做法**天生就難以做到完全窮盡**（因為前面（見 [[../ai-llm/023-prompt-injection.md]]）已經深入討論過的核心洞察——**攻擊者總是能夠不斷地設計出新的、事先沒有被預料到的攻擊手法**，去繞過**任何基於已知模式所做的預先防範**）；而**「輸出護欄」**則提供了一種**更加根本、更不容易被繞過**的防護思路——**不管 Agent 是因為什麼樣的原因（不管是被尚未被任何輸入護欄預先識別出來的全新攻擊手法所誤導、還是單純的模型幻覺）而產生了一個不恰當的輸出或行動**，輸出護欄都能夠**在這個不恰當的內容實際造成任何影響之前**做**最後一道把關**。這種**「不去試圖預先窮舉列舉所有可能的攻擊手法（輸入護欄的思路），而改為聚焦在『不管問題是怎麼發生的，只要最終輸出的內容不恰當就攔截』（輸出護欄的思路）」**的設計更加**具備韌性、不容易被新型態的攻擊手法繞過**。

**詳細解析**：這題考察是否能夠理解**「試圖預先窮舉列舉所有可能的攻擊型態」**和**「聚焦在審視最終的實際結果」**這兩種**防禦思路本質上的優劣差異**，並能把這個**已經在前面多次被間接觸及的核心洞察**具體地應用到**「輸入護欄與輸出護欄的優先順序判斷」**這個新的具體問題上。理解這個問題的核心在於回顧前面（見 [[../ai-llm/023-prompt-injection.md]]）已經深入討論過的核心告誡——**「Prompt Injection 這類攻擊之所以特別難以被徹底根除，關鍵原因在於模型缺乏一種可靠的機制去明確地區分指令和資料」**——這個核心限制某種程度上**同樣直接決定了****「輸入護欄」**這種防禦方式的**先天上限**——因為**輸入護欄**本質上是**試圖在問題真正發生之前**就**預先攔截住**那些**可能會導致問題**的輸入內容，但因為**惡意攻擊的具體手法可以是無窮多樣、不斷推陳出新**的（攻擊者總是能夠設計出**目前還沒有被任何防禦方預先考慮納入**的全新手法），**單純地依靠輸入護欄**某種程度上**注定永遠只能是一場『不斷追趕新型態攻擊』的持久戰**，很難**徹底、一勞永逸**地解決問題；相較之下，**「輸出護欄」**採取的是一種**截然不同、更加根本的防禦哲學**——**它不去試圖預先猜測、窮舉『到底有哪些可能的攻擊手法』**，而是**直接聚焦在『不管這個不恰當的輸出究竟是透過什麼樣的具體攻擊手法而產生的，只要這個最終的輸出內容本身確實不恰當，就應該被攔截』**這個更加**『結果導向』**的判準——這種**「不管成因為何、只看最終結果」**的思路帶來一個相當重要的優勢——**即使是一種全新、事先完全沒有被任何輸入護欄預料到的攻擊手法**，只要這種新的攻擊手法**最終依然導致** Agent 產生了某種**客觀上不恰當的輸出結果**（例如洩漏了不應該被洩漏的敏感資訊），**輸出護欄**依然有機會**在最後一刻**攔截住這個不恰當的結果，**不需要**這個**輸出護欄本身**事先就已經**準確地預料到這種全新的具體攻擊手法**。這種**「聚焦審視最終結果，比試圖窮盡預測所有可能的成因更加穩健、更不容易被新型態問題繞過」**的核心洞察，正是判斷**「應該優先建置輸出護欄」**這個具體結論背後的核心分析邏輯。理解「通常建議優先建置輸出護欄，核心原因在於輸入護欄本質上是依靠事先列舉預測可能存在哪些惡意輸入模式的防禦方式，這種做法天生難以做到完全窮盡，因為攻擊者總能不斷設計出新的事先沒被預料到的攻擊手法去繞過任何基於已知模式的預先防範;而輸出護欄提供了一種更根本更不容易被繞過的防護思路——不管Agent是因為什麼原因產生不恰當的輸出或行動，輸出護欄都能在這個內容實際造成影響之前做最後一道把關，這種不去試圖預先窮舉所有可能攻擊手法、而改為聚焦在不管問題怎麼發生只要最終輸出不恰當就攔截的設計，更具備韌性、不容易被新型態攻擊手法繞過」，展現你能識別出「窮舉預防」和「結果導向審查」這兩種防禦思路的本質優劣差異，並將其正確應用到具體的護欄優先順序判斷問題上。

**面試回答方式**：先明確給出核心答案——「通常建議優先建置輸出護欄」。解釋輸入護欄的先天侷限——「輸入護欄本質上是依靠事先列舉預測可能存在哪些惡意輸入模式的防禦方式，這種做法天生難以做到完全窮盡，因為攻擊者總能不斷設計出新的、事先沒被預料到的攻擊手法去繞過基於已知模式的預先防範」。給出輸出護欄的優勢——「輸出護欄採取一種更根本的防禦哲學，不去試圖預先猜測窮舉所有可能攻擊手法，而是直接聚焦在不管成因為何、只要最終輸出內容本身確實不恰當就應該被攔截，即使是一種全新事先完全沒被預料到的攻擊手法，只要最終依然導致產生客觀上不恰當的輸出結果，輸出護欄依然有機會在最後一刻攔截，不需要事先就準確預料到這種全新的具體攻擊手法」。

### 護欄機制本身如果被設計得過於嚴格，是不是也可能帶來某種類似「假陽性（False Positive）」的問題，誤判一些其實正常、無害的內容？這會帶來什麼樣的代價？

**核心答案**：**確實會存在這種『假陽性』風險**——一個設計得**過於嚴格、敏感度過高**的護欄可能會**誤判**一些**其實完全正常、無害的內容**，錯誤地把它們**當作問題內容加以攔截**。這種**過度敏感**的護欄會帶來**明確的實務代價**——**正常使用者的合理請求被不必要地拒絕、阻擋**，導致**使用者體驗顯著下降**（使用者可能會感到困惑、挫折——為什麼一個**看起來完全正常、合理**的請求卻被系統**莫名其妙地拒絕**了）。這種**「安全性與使用體驗」**之間的權衡是設計護欄機制時**需要被審慎拿捏**的核心考量——**護欄設計得太寬鬆**可能**漏掉真正應該被攔截的問題**（這是前面已經討論的核心風險）；但**護欄設計得太嚴格**則會**誤傷大量正常、無害的合理使用情境**，兩者都**不是理想的狀態**。

**詳細解析**：這題要求對護欄機制做**更加平衡、不單方面只強調『越嚴格越安全』**的檢視，考察是否理解**任何一種『過濾／攔截』機制**本質上都**同時面臨『假陰性（漏掉真正的問題）』和『假陽性（誤判無害內容）』**這兩種**性質相反、卻都需要被同時權衡**的錯誤風險，而**不能只是片面地追求『儘可能提高攔截率』**而**完全忽略誤判正常內容所帶來的代價**。理解這個問題的核心在於回顧一個在**任何涉及『二元分類／篩選判斷』**的系統（不管是這裡討論的護欄、還是其他任何類似性質的篩選機制，例如垃圾郵件過濾器）都普遍存在的核心權衡——**『召回率（儘可能不漏掉真正的問題）』和『精確率（儘可能不誤判正常內容）』這兩者往往存在著一種此消彼長的張力**（這某種程度上呼應了前面（見 [[../ai-llm/009-vector-database-similarity-search.md]]）已經深入討論過的向量資料庫相似度搜尋裡也同樣存在的核心權衡）——**一個被設計得越『寬鬆』**（傾向只有在**非常確信**這確實是一個問題時才攔截）的護欄**越不容易誤判正常內容（較高精確率）**，但相對地也**越可能漏掉一些較為隱晦、不那麼明顯的真正問題（較低召回率）**；反過來，**一個被設計得越『嚴格』**（只要存在一絲可疑的跡象就寧可錯殺也要攔截）的護欄**越不容易漏掉真正的問題（較高召回率）**，但相對地也**越容易誤判、錯殺一些其實無害的正常內容（較低精確率）**。這種**『召回率和精確率難以同時兼顧到極致，往往需要做權衡取捨』**的核心規律帶來一個相當重要的實務啟示——設計護欄的『敏感度』時**不應該只是單方面地追求『儘可能提高攔截率（召回率）』**，而應該**依照這個具體應用場景****恰當地權衡『漏掉真正問題所帶來的風險成本』**和**『誤判正常內容所帶來的使用體驗成本』**這兩者之間的**相對輕重**——如果這個具體應用場景涉及的風險極高（例如涉及重大金錢交易或敏感個資），可能值得**容忍較高的假陽性率（較多誤判）**去換取**更高的召回率（更不容易漏掉真正問題）**；但如果這個場景本身的風險相對較低、而使用者的順暢體驗相對更加重要，則可能需要**適度地放寬護欄的敏感度**去**減少不必要的誤判**，即使這意味著需要**承受稍高一些的漏判風險**。這種**「依照具體情境的風險程度恰當地權衡召回率和精確率」**的思路也呼應了這篇文章反覆強調的核心工程智慧——**「一體適用的單一標準很少是最理想的選擇，應該依照具體情境的實際需求做恰如其分的權衡調整」**。理解「確實會存在這種假陽性風險，一個設計得過於嚴格敏感度過高的護欄可能誤判一些完全正常無害的內容，錯誤地把它們當作問題內容加以攔截，這種過度敏感的護欄會帶來明確的實務代價——正常使用者的合理請求被不必要地拒絕阻擋，導致使用者體驗顯著下降，這觸及任何涉及二元分類篩選判斷的系統都普遍存在的核心權衡——召回率(儘可能不漏掉真正問題)和精確率(儘可能不誤判正常內容)往往存在此消彼長的張力，一個被設計得越寬鬆的護欄越不容易誤判正常內容但也越可能漏掉真正問題，反過來越嚴格越不容易漏掉問題但也越容易誤判正常內容，設計護欄敏感度時不應該只單方面追求儘可能提高攔截率，而應該依照具體應用場景恰當權衡漏掉真正問題所帶來的風險成本、和誤判正常內容所帶來的使用體驗成本這兩者的相對輕重，這呼應了一體適用單一標準很少是最理想選擇、應該依照具體情境做恰如其分權衡調整這個核心工程智慧」，展現你能對護欄機制做出平衡的檢視，理解召回率和精確率之間普遍存在的核心權衡，而非片面追求越嚴格越安全。

**面試回答方式**：先確認這個風險確實存在——「確實會存在這種假陽性風險，一個設計得過於嚴格的護欄可能誤判一些完全正常無害的內容，把它們當作問題內容攔截，這會帶來使用者的合理請求被不必要拒絕、使用體驗顯著下降這個明確代價」。給出核心的權衡框架——「這觸及任何涉及篩選判斷的系統都普遍存在的核心權衡——召回率(儘可能不漏掉真正問題)和精確率(儘可能不誤判正常內容)往往存在此消彼長的張力，越寬鬆的護欄越不容易誤判但也越可能漏掉真正問題，越嚴格則相反」。給出實務的權衡建議——「設計護欄敏感度時不應該只單方面追求提高攔截率，而應該依照具體應用場景，權衡漏掉真正問題的風險成本和誤判正常內容的使用體驗成本，如果場景風險極高可能值得容忍較高假陽性率去換取更高召回率;但如果場景風險較低而使用者體驗更重要，則可能需要適度放寬敏感度」。

### 護欄機制如果是用一個額外的輕量分類模型去做判斷，這個分類模型本身是不是也需要像前面已經深入討論過的 Agent 核心模型一樣，做類似的評估和持續監控？

**核心答案**：**需要，而且這是一個容易被忽略、但相當重要的考量**——這某種程度上是一種**遞迴性的認知**——護欄之所以被設計成**一個額外、獨立的機制**，核心目的是為了**提供一道不完全依賴核心 Agent 模型本身**的獨立防線；但這並**不代表**這個**負責把關的護欄機制本身**就**自動地具備完美、絕對可靠**的判斷能力——這個**額外的輕量分類模型****本身**同樣是一個**依靠某種訓練過程而建構出來的模型**，它**同樣可能存在自己固有的判斷誤差、系統性偏誤，甚至隨著時間演進逐漸變得不夠精確**（因為例如新型態的攻擊手法不斷出現，而這個分類模型卻沒有被持續地更新、重新訓練）。因此這個**負責把關的護欄機制本身**同樣需要被**持續地評估、監控其實際表現**，而不是**把它設置好之後就視為一勞永逸、不需要再關注**的固定機制。

**詳細解析**：這題要求識別出一種**在整篇文章反覆出現**的核心模式——**「任何一個被額外引入、用來把關、審視其他機制的新機制，它自己本身也同樣需要被把關、審視」**——這種**遞迴性的審慎態度**是設計一個**真正穩健、而非只是表面上看起來安全**的複雜系統時**極為重要**的核心思維習慣。理解這個問題的核心在於回顧——**護欄機制之所以被引入**，正是因為我們已經認識到**「完全只依靠核心 Agent 模型自己去把關自己」**存在**自我審查天生存在系統性盲點**這個核心風險（見 [[009-self-correction-reflection.md]]）；但**這個邏輯**如果被**仔細地套用到護欄機制自己身上**，就會發現——**「護欄這個額外的分類模型」**某種程度上**同樣只是另一個依靠某種訓練過程而建構出來的模型**，它**同樣不具備某種『天生免疫於所有可能判斷失誤』的特殊豁免權**——如果我們只是**因為護欄機制是額外、獨立地被引入**就**天真地假設**它**因此就自動地具備完美、可以被完全信賴、不需要再額外關注的判斷能力**，這某種程度上**恰恰重蹈了我們一開始就已經識破並試圖避免的那種思維陷阱**——**「因為某個機制被賦予了把關的角色，就想當然爾地假設它本身一定值得被完全信賴」**。這種**「把關者自己也同樣需要被把關」**的**遞迴性反思**帶來一個相當重要的實務啟示——一個**真正成熟、審慎的 Agent 安全架構**不應該只是**滿足於『已經設置了護欄這個機制本身』**，而應該**額外地**去**持續地評估、監控****這個護欄機制本身的實際表現**——例如**定期地去檢驗這個分類模型是否依然能夠準確地識別出最新出現的攻擊手法**（而不是只停留在它最初被訓練時所依據的那些已知模式），以及**這個分類模型本身的假陽性／假陰性率是否維持在合理的水準**。這種**「持續地質疑、審視任何一個被引入的新機制自身的可靠性，而不是把它視為理所當然、一勞永逸、不需要再關注的既定事實」**的思維習慣，正是這篇文章反覆強調、值得被持續培養的一種**最核心的批判性思考能力**。理解「需要，而且這是一個容易被忽略但相當重要的考量，這是一種遞迴性的認知——護欄之所以被設計成額外獨立的機制，核心目的是提供一道不完全依賴核心Agent模型本身的獨立防線，但這不代表這個負責把關的護欄機制本身，就自動具備完美絕對可靠的判斷能力，這個額外的輕量分類模型本身同樣是依靠某種訓練過程建構出來的模型，同樣可能存在固有的判斷誤差系統性偏誤、甚至隨時間演進逐漸變得不夠精確(例如新型態攻擊手法不斷出現而分類模型沒被持續更新)，因此這個負責把關的護欄機制本身同樣需要被持續評估監控其實際表現，而不是設置好之後就視為一勞永逸不需要再關注的固定機制，這種把關者自己也同樣需要被把關的遞迴性反思，是設計一個真正穩健而非只是表面上看起來安全的複雜系統時極為重要的核心思維習慣」，展現你能識別出「任何被額外引入用來把關其他機制的新機制，它自己本身也同樣需要被把關」這個貫穿整篇文章的遞迴性核心模式，並具備持續質疑審視任何新引入機制自身可靠性的批判性思考能力。

**面試回答方式**：先明確給出核心答案——「需要，而且這是一個容易被忽略但相當重要的考量，這是一種遞迴性的認知——護欄被設計成額外獨立機制的目的，是提供一道不完全依賴核心Agent模型本身的獨立防線，但這不代表護欄機制本身就自動具備完美可靠的判斷能力」。解釋為什麼——「這個額外的輕量分類模型本身同樣是依靠某種訓練過程建構出來的模型，同樣可能存在固有判斷誤差、系統性偏誤，甚至隨著新型態攻擊手法不斷出現而逐漸變得不夠精確，如果只因為護欄是額外獨立引入的，就天真假設它自動具備完美判斷能力，某種程度上恰恰重蹈了我們一開始就試圖避免的那種思維陷阱」。給出實務啟示——「一個真正成熟的Agent安全架構不應該只滿足於已經設置了護欄這個機制本身，而應該額外持續評估監控這個護欄機制本身的實際表現，例如定期檢驗分類模型是否依然能準確識別最新出現的攻擊手法、以及假陽性假陰性率是否維持在合理水準」。
