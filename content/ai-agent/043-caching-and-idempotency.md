# 題目

Agent 系統裡有哪些地方可以快取？冪等為什麼特別重要？

## 核心答案

三個層次的快取，收益與難度不同。

**提示快取**——由模型供應商提供，把固定前綴（系統提示、工具定義、少樣本範例）的計算結果快取；收益直接（降低 TTFT 與成本）而幾乎沒有實作成本——前提是把固定內容放在提示的前面並保持穩定。

**工具結果快取**——同一個查詢在短時間內重複時直接回傳快取；Agent 特別容易重複查詢（它可能忘了自己剛查過），所以這個快取的命中率往往出乎意料地高。

**完整回應快取**——相同的請求直接回傳上次的結果；只適用於確定性高且輸入完全相同的場景，實務上命中率低。

而冪等之所以特別重要，是因為「模型會重試」：它看到錯誤或逾時就會再試一次，而它的判斷不受你的控制——所以寫入類的工具必須在服務端保證冪等，不能靠提示約束。

## 詳細解析

「Agent 重複查詢同一件事」比想像中頻繁：多輪對話中它可能反覆查詢同一個訂單的狀態；在推理過程中它可能為了確認而重查；在多代理系統中不同的 Agent 可能各自查了同一份資料。所以工具層的快取（即使只有 30 秒的 TTL）就能顯著降低下游負載與延遲。但要注意「什麼可以快取」的判斷：唯讀且短時間內不會變的可以；而剛剛被自己修改過的資料絕對不能快取——否則 Agent 會讀到自己修改前的舊值並做出錯誤判斷。所以寫入操作應該主動主動使相關的快取失效。

**「冪等鍵的來源」在 Agent 中需要設計**：一般的 API 由客戶端產生冪等鍵——而在 Agent 中，「客戶端」是模型，它不會可靠地產生穩定的鍵。**所以應該由框架產生**：用「當前的執行 ID 加上工具名稱加上參數的雜湊」作為冪等鍵——於是同一輪中的重複呼叫被自動去重，而不同輪的合法重複仍然能執行。這個設計把冪等從「工具作者的責任」變成「框架的保證」，可靠得多。

**「模型回應的快取有一個陷阱」**：如果快取了模型的輸出——那麼同樣的輸入永遠得到同樣的行為，**包括同樣的錯誤**。在需要多樣性或自我修正的場景（例如重試時希望它換個方法），快取會讓重試變得毫無意義。所以模型層的快取應該只用於明確的冪等查詢，而不是 Agent 的主控迴圈。

## 面試回答方式

先給三個層次的快取與各自的收益，並指出提示快取的前提是把固定內容放前面並保持穩定。給冪等重要的理由——模型會重試而它的判斷不受你控制，所以必須在服務端保證。加分點有四個：**Agent 重複查詢比想像中頻繁**（多輪反覆查、推理中重查、多代理各自查），所以即使 30 秒 TTL 的快取命中率也很高；寫入操作要主動使相關快取失效——否則 Agent 會讀到自己修改前的舊值；**冪等鍵應該由框架產生**（執行 ID 加工具名加參數雜湊），把冪等從工具作者的責任變成框架的保證；以及**模型回應快取的陷阱**——同樣的輸入永遠得到同樣的行為包括同樣的錯誤，會讓重試變得毫無意義。

## 講稿

有三個層次的快取。提示快取由模型供應商提供，把固定前綴的計算結果快取起來，收益直接而且幾乎沒有實作成本，前提是把固定內容放在提示前面並保持穩定。工具結果快取是同一個查詢短時間內重複時直接回傳。完整回應快取實務上命中率低。

第二層的命中率往往出乎意料地高，因為代理重複查詢同一件事比想像中頻繁。多輪對話中它可能反覆查同一個訂單，推理過程中為了確認而重查，多代理系統裡不同代理各自查了同一份資料。所以即使只有三十秒的存活時間也有效。

但有一個判斷要注意，剛剛被自己修改過的資料絕對不能快取，否則代理會讀到修改前的舊值並做出錯誤判斷。所以寫入操作要主動使相關快取失效。

至於冪等，它特別重要是因為模型會重試，而它的判斷不受你控制。所以我會讓框架產生冪等鍵，用執行編號加工具名稱加參數雜湊。這樣同一輪中的重複呼叫被自動去重，而不同輪的合法重複仍然能執行。這把冪等從工具作者的責任變成框架的保證。

## 常見追問

### 提示快取要怎麼最大化命中率？

**核心答案**：把提示按「穩定程度」排序，最穩定的放最前面。順序通常是：系統提示 → 工具定義 → 少樣本範例 → 檢索到的知識 → 對話歷史 → 當前輸入。**因為快取的匹配是前綴匹配**——一旦某個位置的內容變了，從那裡之後的快取全部失效。

**詳細解析**：「動態內容放前面」是一個常見卻致命的錯誤：把當前時間、使用者 ID、或者隨機的 session ID 放在系統提示的開頭——於是每個請求的前綴都不同，快取命中率為零。而這類內容通常可以移到後面，或者根本不需要放進提示。另一個容易忽略的是「工具定義的順序不穩定」：如果工具是從一個字典或集合中取出的，順序可能每次不同——於是序列化出來的內容也不同，快取失效。確保工具列表的順序是確定的（例如按名稱排序）是一個一行程式碼的修正，卻能讓命中率從零變成接近百分之百。這類「小細節決定成敗」的問題在快取上特別常見，而它們的診斷方式是直接比對兩次請求的提示前綴。

**面試回答方式**：給按穩定程度排序的做法並解釋**前綴匹配的機制**。核心加分點是動態內容放前面是常見卻致命的錯誤（當前時間、使用者 ID、session ID 讓命中率為零）與**工具定義的順序不穩定**這個容易忽略的問題——從集合中取出的順序可能每次不同，而確保按名稱排序是一行程式碼的修正卻能讓命中率從零變成接近百分之百。收在診斷方式：直接比對兩次請求的提示前綴。

### Agent 的重試會不會導致重複扣款這類問題？

**核心答案**：會，而且這是 Agent 最需要防範的一類風險。因為模型看到逾時或錯誤的直覺反應就是重試——而它不知道那個操作可能已經成功了。**防護有三層**：**工具層的冪等（最可靠）**、錯誤訊息中明確指引「不要直接重試，先查詢狀態」、以及框架層對寫入類工具的自動去重。

**詳細解析**：「框架層的自動去重」是最容易實施且最可靠的一層：把工具標記為「寫入類」——框架在同一次執行中對相同的（工具名, 參數）組合只允許執行一次，第二次直接回傳第一次的結果。這不需要工具作者做任何事，也不依賴模型的判斷。它的限制是「合法的重複執行也會被擋」（例如真的要建立兩張相同的訂單）——所以應該提供一個明確的方式繞過（例如參數中帶一個序號）。而更根本的認知是：在 Agent 系統中，「防止重複」的責任必須從模型移到框架與服務端——因為模型的行為是機率性的，而金錢相關的操作不能建立在機率之上。

**面試回答方式**：明確回答會並指出模型看到逾時的直覺反應就是重試，而它不知道操作可能已經成功。給三層防護。核心加分點是框架層的自動去重最容易實施且最可靠——把工具標記為寫入類，同一次執行中相同的工具與參數只允許執行一次，不需要工具作者做任何事也不依賴模型判斷，並說明它的限制與繞過方式。收在根本認知：「防止重複」的責任必須從模型移到框架與服務端，因為模型的行為是機率性的而金錢相關的操作不能建立在機率之上。

### 快取會不會讓 Agent 讀到過時的資料？

**核心答案**：會，所以快取的 TTL 要根據「這份資料多快會變」與「讀到舊值的後果」共同決定。商品的靜態描述可以快取很久；庫存數量與訂單狀態應該很短或不快取；而「Agent 自己剛剛修改過的東西」必須立即失效。

**詳細解析**：「Agent 讀到自己造成的舊值」是一個特別容易出錯且難以診斷的情況：Agent 更新了訂單狀態，下一步查詢時因為快取而讀到舊狀態——於是它認為更新失敗並再試一次。這種「因為快取而導致重複操作」的連鎖，症狀是隨機的重複執行，而根因藏在快取層。所以「寫入後立即失效相關快取」不是優化而是正確性的要求。實作上最簡單可靠的做法是「寫入類工具執行後，清除該執行上下文中所有相關資源的快取」——**寧可過度失效也不要漏掉**，因為快取的收益遠小於一次錯誤操作的代價。這個「正確性優先於命中率」的取捨，在 Agent 場景比在一般服務中更明顯，因為錯誤的後果由自動化放大了。

**面試回答方式**：給 TTL 的決定因素（資料變化速度、讀到舊值的後果）與分類建議。核心加分點是**Agent 讀到自己造成的舊值**這個特別難診斷的情況——更新後因快取讀到舊狀態，於是認為失敗並重試，症狀是隨機的重複執行而根因藏在快取層。收在取捨：寫入後立即失效相關快取不是優化而是正確性要求，**寧可過度失效也不要漏掉**——因為快取的收益遠小於一次錯誤操作的代價，而錯誤的後果被自動化放大了。
