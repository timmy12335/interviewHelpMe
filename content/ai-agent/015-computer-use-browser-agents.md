# 題目

什麼是「Computer Use（電腦操作能力）」這類讓 Agent 能**直接操作一般圖形化使用者介面（GUI），如同人類一樣點擊、輸入文字、瀏覽網頁**的能力？相較於前面（見 [[../ai-llm/022-function-calling.md]]）深入討論過的傳統 Function Calling 機制，這種能力解決的是什麼樣的不同問題？

## 核心答案

Computer Use 指的是一種讓 Agent 能夠**直接地透過觀察螢幕畫面的視覺內容（通常是把目前的螢幕截圖提供給模型）理解當前畫面上存在哪些可以互動的元素（按鈕、輸入框、選單等），並模擬人類的操作方式（滑鼠點擊、鍵盤輸入、捲動畫面等）去直接操作一般的圖形化使用者介面**的能力。相較於傳統的 Function Calling 機制（需要事先針對每一個想要整合的工具或服務撰寫明確定義的 API 規格），Computer Use 解決的是一個**明顯不同**的問題——**Function Calling** 處理的是「如何讓模型去使用那些**原本就已經具備明確、結構化 API 介面**的服務或工具」；而 **Computer Use** 處理的則是「如何讓 Agent 能夠去操作**那些原本就是設計給人類使用、並沒有提供任何明確 API 介面**的一般性軟體和網頁」這個問題——現實世界裡**存在大量的軟體和網站**，它們**從一開始設計時**就是**只考慮讓人類透過滑鼠、鍵盤這種圖形化介面去操作使用**，而**根本沒有提供**任何**結構化的 API** 讓其他程式能夠直接呼叫存取（這某種程度上是前面（見 [[006-agent-communication-protocols.md]]、[[007-mcp-architecture.md]]）已經深入討論過的核心議題——**只有**那些**已經提供明確 API 或 MCP 整合**的服務或資料來源，才能被 Function Calling 機制直接使用）。Computer Use 這種能夠**直接以人類慣用的圖形化操作方式**去和任何軟體或網頁互動的能力，某種程度上是讓 Agent 能夠**觸及、操作到那些原本完全沒有提供任何程式化整合方式的廣大既有軟體生態系統**的關鍵技術突破。

## 詳細解析

**Computer Use 的核心運作機制——依靠視覺理解而非結構化資料**：Computer Use 之所以需要**額外的、有別於傳統 Function Calling** 的技術實作方式，核心原因在於——它**沒有辦法**像 Function Calling 那樣直接依靠**事先被明確定義好的結構化 API 規格**去理解**目前可以採取哪些行動**，而是**必須**依靠**對當下螢幕畫面的視覺內容做理解和判讀**——具體來說，這通常需要模型具備**多模態（能夠同時處理文字和圖像內容）的理解能力**，模型需要依靠**分析當前的螢幕截圖**去判斷——**畫面上存在哪些具體的按鈕、輸入框、連結等可以互動的元素**；**這些元素各自位於畫面上哪個具體的座標位置**；**依照目前的任務目標，接下來應該點擊或操作哪一個具體的元素**。這種**依靠視覺理解、而非依靠事先定義好的結構化資料**的運作方式本質上是一個**明顯更加複雜、更具挑戰性**的任務——**理解、處理非結構化的原始視覺內容（如一張完整的螢幕截圖），通常比處理已經被整理好、明確標示各個欄位意義的結構化資料需要更加複雜的技術能力**。

**Computer Use 面臨的獨特挑戰——畫面元素的辨識準確性，以及操作的精準度**：相較於 Function Calling 那種**只需要正確地生成一組結構化參數**的相對單純任務，Computer Use 額外面臨幾個更加棘手的挑戰——**(1) 畫面元素辨識的準確性**：模型需要**準確地辨識出**畫面上某個具體的按鈕或連結究竟**位於哪個精確的座標位置**，如果這個辨識出現任何誤差（例如把滑鼠點擊的座標判斷錯了、稍微偏離了那個真正需要被點擊的按鈕的實際位置），這個操作就可能**完全失敗**（點擊到一個完全不相關的其他元素）；**(2) 畫面狀態的動態變化**：**一般的圖形化介面**天生就比**結構化的 API 回應****更容易出現各種動態的、事先難以完全預期的變化**（例如一個彈出視窗突然出現、遮擋了原本預期要點擊的元素；或者網頁的載入速度較慢，導致某個元素還沒有真正出現在畫面上，Agent 就已經嘗試去點擊它）。這種**畫面狀態本身天生具備較高的不確定性**，讓 Computer Use 這種操作方式相較於 Function Calling 需要**額外地具備更強的容錯和恢復能力**，去因應這些**執行過程中經常會出現的意外狀況**。

**Computer Use 帶來的安全性考量——比傳統 Function Calling 更加難以做細緻的權限限縮**：Computer Use 這種能力也額外引入了一些值得被特別重視的安全性考量——回顧前面（見 [[../ai-llm/023-prompt-injection.md]]）已經深入討論過的**權限最小化原則**——在**傳統的 Function Calling** 情境裡，因為**每一個工具都是透過一個明確定義的具體函式去被呼叫**，相對較容易去**針對每一個具體的工具函式**做**細緻的權限限縮**（例如只允許某個特定工具被呼叫、限制這個工具可以被用來存取哪些特定範圍的資料）；但 **Computer Use** 因為它賦予 Agent 的是**「能夠像人類一樣直接操作整個圖形化介面」**這種**遠比單一個具體工具函式更加廣泛籠統的能力**，這某種程度上讓**要做同樣細緻的權限限縮**變得**更加困難**——一旦一個 Agent 被賦予**能夠直接操作整台電腦的圖形化介面**這種能力，理論上它就**具備了能夠觸及、操作到這台電腦上幾乎任何軟體或資訊**的潛在能力（而不是像 Function Calling 那樣可以被精準地限定在某幾個明確列出的具體工具範圍內）。這種**「權限範圍本質上更難被精準限縮」**的特性，讓 Computer Use 這種能力在實際部署運用時需要**更加審慎地**去考量前面（見 [[010-sandbox-code-execution-security.md]]）已經深入討論過的**沙箱隔離**、以及前面（見 [[011-human-in-the-loop.md]]）已經深入討論過的 **Human-in-the-Loop 人工把關機制**，來作為**額外補充的安全防線**。

## 面試回答方式

先給出Computer Use的核心定義——「一種讓Agent能夠直接透過觀察螢幕畫面的視覺內容，理解當前畫面上存在哪些可以互動的元素，並模擬人類的操作方式(滑鼠點擊、鍵盤輸入等)去直接操作一般圖形化使用者介面的能力」。清楚說明它和Function Calling解決的不同問題——「Function Calling處理的是如何讓模型使用那些原本就具備明確結構化API介面的服務或工具;而Computer Use處理的是如何讓Agent能夠操作那些原本設計給人類使用、並沒有提供任何明確API介面的一般性軟體和網頁，讓Agent能觸及操作到那些原本完全沒有提供程式化整合方式的廣大既有軟體生態系統」。可以補充核心運作機制——「Computer Use沒辦法像Function Calling那樣依靠事先定義好的結構化API規格，而必須依靠對當下螢幕畫面的視覺內容做理解和判讀，通常需要模型具備多模態理解能力」。一定要主動指出額外的挑戰——「面臨畫面元素辨識準確性(座標誤差可能導致操作完全失敗)、以及畫面狀態動態變化(彈出視窗、載入延遲等事先難以完全預期的情況)這兩個更棘手的挑戰，需要更強的容錯和恢復能力」。可以延伸提到安全性考量——「因為Computer Use賦予Agent的是能夠像人類一樣直接操作整個圖形化介面這種遠比單一具體工具函式更廣泛籠統的能力，權限範圍更難被精準限縮，實際部署時需要更審慎地考量沙箱隔離和Human-in-the-Loop人工把關機制」，展現你對Computer Use這個新興技術的核心運作機制、獨特挑戰、以及安全考量，有完整且深入的理解。

## 常見追問

### 如果一個網站或軟體已經提供了明確的 API 或 MCP 整合，是不是就應該優先用傳統的 Function Calling／MCP 方式去整合，而不是用 Computer Use 這種模擬人類操作的方式？

**核心答案**：**是的，在這種情況下應該優先採用傳統的 Function Calling／MCP 方式**，而**不是**優先選擇 Computer Use——核心原因在於，**結構化的 API 呼叫**相較於**模擬人類的圖形化操作**具備幾個明顯的優勢——**(1) 更高的可靠性**：直接呼叫一個明確定義的 API 函式**不會**受到前面（見詳細解析）已經深入討論過的『畫面元素辨識誤差、畫面狀態動態變化』這類 Computer Use 特有的不確定性因素影響，通常**明顯更加穩定、可靠**；**(2) 更高的執行效率**：直接的 API 呼叫通常**遠比**需要經過**截圖、視覺辨識、模擬點擊這一連串額外步驟**的 Computer Use 操作方式**快速得多**；**(3) 更容易做細緻的權限控管**：這正是前面（見詳細解析）已經討論過的核心考量——**API 呼叫**相較於**籠統的圖形介面操作****明顯更容易**被精準地限縮權限範圍。Computer Use 這種能力真正**應該被優先運用的場景**，是**那些確實沒有提供任何其他更加結構化、可靠的程式化整合方式的既有軟體或網站**，作為一種**在缺乏更好選項時**依然能夠讓 Agent 具備**觸及、操作**這類系統的能力，而**不是**在**已經存在更加可靠、高效的替代方案（結構化 API）**時依然捨棄這個更好的選項，優先選用**相對較不穩定、效率較低**的 Computer Use 方式。

**詳細解析**：這題要求對 Computer Use 和傳統 Function Calling／MCP 這兩種不同的工具整合方式做**明確的優先順序判斷**，考察是否理解 **Computer Use 並不是一種可以用來取代所有其他整合方式的『萬用優先』技術**，而是**一種專門用來因應『缺乏其他更佳選項』**這種特定情境的**補充、次要**手段。理解這個問題的核心在於回顧前面已經反覆練習過的核心分析框架——**釐清不同的技術手段各自具體擅長處理什麼樣的情境，並依照這個情境的實際特性做出恰當的優先順序判斷**——結構化的 API／MCP 整合之所以**在可行的情況下**應該**被優先**採用，是因為它**本質上提供了一種遠比 Computer Use 更加『精確、可靠、高效』**的溝通方式——這某種程度上可以被類比成**「和一個受過專業訓練的人，用一套雙方都明確理解的專業術語溝通」**，對比**「試圖透過觀察對方模糊的肢體動作和表情去猜測對方想要表達的意思」**——前者顯然**遠比後者**更加**精確、有效率**——只有在**沒有辦法**用前者這種**更加直接、精確**的溝通方式時（例如對方根本不具備那套共通的專業術語系統），才**退而求其次**採用後者這種**相對較間接、也更容易出現誤解**的替代方式。這種**「優先採用更加直接、精確、可靠的溝通／整合方式；只有在缺乏這種更佳選項時，才退而求其次採用較間接、較不穩定的替代方案」**的核心思路，正是判斷**「應該優先採用 Function Calling／MCP、還是 Computer Use」**這個具體問題時最核心的判斷準則。Computer Use 這種能力之所以**依然具備重要的實際價值**，並**不是**因為它**在任何情境下都是最佳選擇**，而是因為**現實世界裡確實存在大量缺乏任何結構化 API 的既有軟體和網站**——如果**完全沒有** Computer Use 這種替代能力，Agent 就**根本沒有辦法**去觸及、操作這一大部分的既有軟體生態系統。Computer Use 的核心價值正是**作為這種『在缺乏更佳選項時的必要補充手段』**，而**不是****「取代結構化 API 整合方式」**的更優越替代方案。理解「是的，在這種情況下應該優先採用傳統的Function Calling/MCP方式，而不是Computer Use，核心原因是結構化API呼叫相較於模擬人類圖形化操作，具備更高可靠性(不會受到Computer Use特有的畫面辨識誤差或動態變化影響)、更高執行效率(不需要經過截圖辨識模擬點擊這些額外步驟)、以及更容易做細緻權限控管這幾個明顯優勢，Computer Use真正應該被優先運用的場景，是那些確實沒有提供任何更結構化可靠程式化整合方式的既有軟體或網站，作為在缺乏更好選項時依然能讓Agent觸及操作這類系統的能力，而不是在已經存在更可靠高效的替代方案時，依然捨棄這個更好選項優先選用相對較不穩定的Computer Use方式，這種優先採用更直接精確可靠的整合方式、只有在缺乏這種更佳選項時才退而求其次採用較間接較不穩定替代方案的核心思路，正是判斷這個問題最核心的判準」，展現你能對Computer Use和傳統Function Calling這兩種技術手段，做出清楚的優先順序判斷，理解Computer Use的核心價值定位是必要補充手段而非優越替代方案。

**面試回答方式**：先明確給出核心答案——「是的，在這種情況下應該優先採用傳統的Function Calling/MCP方式」。給出三個具體優勢——「結構化API呼叫相較於模擬人類圖形化操作，具備更高可靠性(不受畫面辨識誤差或動態變化影響)、更高執行效率(不需要截圖辨識模擬點擊這些額外步驟)、以及更容易做細緻權限控管」。給出Computer Use的正確定位——「Computer Use真正應該被優先運用的場景，是那些確實沒有提供任何更結構化可靠程式化整合方式的既有軟體或網站，它的核心價值是作為在缺乏更好選項時的必要補充手段，而不是取代結構化API整合方式的更優越替代方案」。可以用類比加深理解——「這某種程度上類似和受過專業訓練的人用雙方都理解的專業術語溝通，對比試圖透過觀察模糊的肢體動作去猜測對方意思，前者顯然更精確有效率，只有在沒有前者這種選項時才退而求其次」。

### Computer Use 這種操作能力如果結合前面已經深入討論過的 Prompt Injection 攻擊，會不會帶來更加獨特、值得特別留意的攻擊情境？

**核心答案**：**會帶來一種相當獨特、且特別值得被高度警惕的攻擊情境**——延續前面（見 [[../ai-llm/023-prompt-injection.md]]）已經深入討論過的核心洞察——**間接注入攻擊**可以透過把惡意指令埋藏在模型會讀取、處理的外部內容裡去發動攻擊——在 Computer Use 這個具體情境裡，這種攻擊有了一種**特別直觀、也特別難以防範**的具體實現方式——**攻擊者可以直接地在一個網頁畫面上，用視覺上可見的文字內容（甚至可能是刻意設計成不容易被人類肉眼注意到、但模型在做視覺理解時依然能夠讀取到的隱藏文字，例如用極小的字體、或者和背景色幾乎相同的文字顏色）去埋藏一段偽裝成指令的惡意內容**。當一個正在透過 Computer Use 能力瀏覽、操作這個網頁的 Agent **在做視覺理解的過程中**讀取到這段被刻意隱藏埋藏的惡意文字，就有可能被誤導去執行這段惡意指令所要求的操作（例如被誘導去點擊某個看似無害、但實際上會觸發某種惡意行為的按鈕或連結）。

**詳細解析**：這題要求把前面已經深入討論過的**間接注入攻擊**核心概念**具體地延伸應用到 Computer Use 這個涉及視覺理解的全新情境上**，考察是否能夠識別出**「模型具備視覺理解能力」**這件事情某種程度上也**同時開啟了前面已經討論過的間接注入攻擊的一種全新、且特別直觀的具體實現方式**。理解這個問題的核心在於回顧前面（見 [[../ai-llm/023-prompt-injection.md]]）已經深入討論過的核心洞察——**模型缺乏一種可靠的機制去明確地區分「應該被信任遵從的指令」和「只是需要被參考處理的資料」**——把這個核心洞察**具體地延伸到視覺理解**這個新的資訊管道上——在**傳統的、只涉及文字**的間接注入情境裡，攻擊者需要把惡意指令埋藏在**模型會讀取的文字內容**裡；而在 **Computer Use** 這個**額外涉及視覺理解**的新情境裡，攻擊者多了一種**更加直觀、甚至某種程度上更難被發現**的攻擊手法——**利用視覺呈現本身的特性**去**刻意地讓某段惡意文字內容****對人類肉眼而言難以察覺（或者看起來完全像是網頁的正常背景元素），但對模型的視覺理解能力而言**這段文字依然**清楚可見、能夠被正確地辨識、讀取到**（這某種程度上是因為**人類的視覺注意力**和**模型的視覺理解方式**可能存在**某種程度的差異**——人類可能很自然地會忽略一段字體極小、或者和背景色幾乎融為一體的文字，但模型在**分析、解讀整張截圖的過程中**可能**不會天然地具備這種和人類相同的『視覺忽略』傾向，而依然會把這段文字內容一併納入它理解、判讀的範圍裡**）。這種**「利用人類和模型在視覺理解上可能存在的差異，去設計出一種人類不容易察覺、但模型依然會讀取到的隱藏式惡意指令」**的攻擊手法，是 **Computer Use 這個新的能力**所**特有引入的一種全新攻擊面**。因應這種風險，除了前面（見 [[../ai-llm/023-prompt-injection.md]]）已經深入討論過的各種通用防範原則（對高風險操作人工確認、權限最小化等）以外，可能還需要額外地考量**針對 Computer Use 這種特定情境去設計額外的、專門針對『視覺內容裡是否存在異常、可疑的隱藏文字』**這類更加專門化的偵測機制來作為補充。理解「會帶來一種相當獨特且特別值得被高度警惕的攻擊情境，延續之前討論過的間接注入攻擊核心洞察，可以透過把惡意指令埋藏在模型會讀取處理的外部內容裡發動攻擊，在Computer Use這個涉及視覺理解的具體情境裡，這種攻擊有了一種特別直觀也特別難以防範的具體實現方式——攻擊者可以直接在網頁畫面上用視覺上可見的文字內容(甚至可能刻意設計成人類肉眼不容易察覺、但模型做視覺理解時依然能讀取到的隱藏文字)去埋藏一段偽裝成指令的惡意內容，這種利用人類和模型在視覺理解上可能存在的差異，去設計出人類不容易察覺、但模型依然會讀取到的隱藏式惡意指令的攻擊手法，是Computer Use這個新能力特有引入的一種全新攻擊面，因應這種風險除了通用防範原則以外，可能還需要額外設計專門針對視覺內容裡是否存在異常可疑隱藏文字的偵測機制作為補充」，展現你能把已經深入討論過的間接注入攻擊核心概念，正確且有洞察力地延伸應用到Computer Use這個涉及視覺理解的全新技術情境。

**面試回答方式**：先給出核心答案——「會帶來一種相當獨特且特別值得高度警惕的攻擊情境，這是之前討論過的間接注入攻擊，在Computer Use這個涉及視覺理解的具體情境裡的一種新的具體實現方式」。具體解釋這種攻擊如何運作——「攻擊者可以直接在網頁畫面上用視覺上可見的文字內容，刻意設計成人類肉眼不容易察覺(例如用極小字體或和背景色幾乎相同的顏色)、但模型做視覺理解時依然能讀取到的隱藏文字，去埋藏一段偽裝成指令的惡意內容，當Agent透過Computer Use瀏覽操作這個網頁並讀取到這段隱藏文字時，就可能被誤導執行惡意指令」。指出這種攻擊的獨特性——「這種利用人類和模型在視覺理解上可能存在差異，設計出人類不易察覺但模型依然會讀取到的隱藏式惡意指令，是Computer Use這個新能力特有引入的一種全新攻擊面」。給出因應做法——「除了對高風險操作人工確認、權限最小化這些通用防範原則，可能還需要額外設計專門針對視覺內容裡是否存在異常可疑隱藏文字的偵測機制作為補充」。

### Computer Use 這種能力和前面已經深入討論過的沙箱機制，兩者結合起來會不會存在某種特別需要留意的張力或矛盾？

**核心答案**：**確實存在一種值得被仔細權衡的張力**——回顧前面（見 [[010-sandbox-code-execution-security.md]]）已經深入討論過的核心設計原則，沙箱的核心價值在於**把被執行的行為限制在一個隔離、範圍受限的環境裡**；但 Computer Use 這種能力之所以**具備實際價值**，核心正是因為它能夠讓 Agent 去**操作真實世界裡實際存在、且通常需要被實際地觸及運用的軟體和網頁**（例如真實的公司內部系統、真實的電商網站）——這某種程度上形成了一種**張力**：**如果把 Computer Use 完全限制在一個高度隔離的沙箱環境裡**（例如一個完全獨立、和任何真實外部系統都沒有連結的模擬環境），這雖然能提供**最高強度的安全隔離**，但也會讓這個 Agent **沒有辦法真正地去觸及、操作到它原本被期待能夠操作的那些真實系統**（某種程度上讓這個能力失去了它原本最核心的實用價值）；但**如果讓 Computer Use 直接地操作真實、正式的生產環境系統**，這某種程度上又**削弱了**沙箱原本應該提供的隔離保護效果。

**詳細解析**：這題要求把 **Computer Use** 這個具體技術能力和前面（見 [[010-sandbox-code-execution-security.md]]）已經深入討論過的**沙箱隔離**這個核心安全機制做**具體的整合性思考**，考察是否能夠識別出這兩者之間**存在著一種值得被仔細權衡拿捏的內在張力**，而不是天真地假設**只要同時套用這兩種機制**就能**輕易地同時享有這兩者各自的全部好處，而不需要做任何取捨**。理解這個問題的核心在於認識到——**沙箱和 Computer Use** 這兩者某種程度上**分別追求彼此存在著張力的不同目標**——沙箱追求的是**隔離、限制，讓被執行的行為儘可能地脫離、不觸及任何真實、有價值的外部系統**；而 Computer Use 追求的卻正是**讓 Agent 能夠真正地去觸及、操作到那些真實、有價值的外部系統（這正是它之所以具備實用價值的核心原因）**。這兩個目標某種程度上**天生就存在著一定程度的對立張力**。因應這種張力，實務上一個較為恰當、務實的做法是**採用一種『分層漸進』的策略，而非追求一步到位、完美兼顧這兩個目標**——具體來說可以考慮——**(1) 在開發、測試和驗證階段**優先**在高度隔離的沙箱環境裡**讓 Agent 去**操作一個模擬、複製出來的測試版本系統**（而不是直接操作真實的生產系統），確保這個 Agent 的行為模式已經得到**充分的驗證**；**(2) 在正式上線運用之後**，即使需要讓 Agent **去操作真實的系統**，依然可以**額外地搭配前面（見 [[011-human-in-the-loop.md]]）已經深入討論過的 Human-in-the-Loop 人工把關機制**，作為一種**「即使無法做到完全的環境隔離，依然透過額外的人工審核這道防線來補償、緩解這種張力所帶來的殘餘風險」**的折衷做法。這種**「用分層、漸進、以及多重防線搭配的方式去務實地權衡這種內在張力，而不是天真地追求一步到位、完美無缺的單一解方」**的思路，某種程度上也呼應了前面（見 [[010-sandbox-code-execution-security.md]] 的常見追問）已經深入討論過的**縱深防禦（Defense in Depth）**這個核心安全設計哲學。理解「確實存在一種值得被仔細權衡的張力，沙箱的核心價值在於把被執行的行為限制在一個隔離、範圍受限的環境裡，但Computer Use之所以具備實際價值，核心正是因為它能讓Agent去操作真實世界裡實際存在的軟體和網頁，如果把Computer Use完全限制在高度隔離的沙箱環境裡，雖然能提供最高強度的安全隔離，但也會讓這個Agent沒辦法真正觸及操作到它原本被期待能操作的真實系統，某種程度上讓這個能力失去了最核心的實用價值;但如果讓Computer Use直接操作真實正式的生產環境系統，又削弱了沙箱原本應該提供的隔離保護效果，因應這種張力，實務上較為恰當務實的做法是採用一種分層漸進的策略，在開發測試驗證階段優先在高度隔離沙箱環境裡操作模擬複製出來的測試版本系統，在正式上線運用後即使需要操作真實系統，也額外搭配Human-in-the-Loop人工把關機制，作為即使無法做到完全環境隔離、依然透過額外人工審核來補償緩解殘餘風險的折衷做法，這呼應了縱深防禦這個核心安全設計哲學」，展現你能識別出Computer Use和沙箱隔離這兩個各自重要的機制之間存在的內在張力，並給出務實的分層權衡做法，而非天真假設兩者能被完美兼顧而不需要任何取捨。

**面試回答方式**：先明確給出核心答案——「確實存在一種值得被仔細權衡的張力，沙箱的核心價值在於隔離限制，但Computer Use之所以具備實際價值，正是因為它能讓Agent觸及操作真實世界裡的軟體和網頁，這兩個目標某種程度上天生就存在對立張力」。給出兩個極端各自的問題——「如果把Computer Use完全限制在高度隔離的沙箱環境裡，雖然能提供最高安全隔離，但會讓Agent沒辦法真正觸及它原本被期待能操作的真實系統，失去核心實用價值;但如果直接操作真實生產環境系統，又削弱了沙箱原本應該提供的隔離保護」。給出務實的折衷做法——「較為恰當的做法是採用分層漸進策略，在開發測試驗證階段優先在隔離沙箱裡操作模擬測試版本，正式上線運用後即使需要操作真實系統，也額外搭配Human-in-the-Loop人工把關機制作為補償，這呼應了縱深防禦這個核心安全設計哲學」。
