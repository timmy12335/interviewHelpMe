# 題目

Agent 該以什麼身份執行操作？權限怎麼設計？

## 核心答案

核心原則是「Agent 以使用者的身份執行，而非以一個超級權限的服務帳號」。如果 Agent 用一個能存取所有資料的帳號，那麼一次提示注入就是完整的資料外洩——而使用者本身的權限限制天然地限制了損害範圍。

**四個設計要點。**

**身份傳遞**——使用者的身份必須一路傳到最下游的工具與資料存取，而不是在入口驗證一次之後就用服務帳號執行。

**權限的粒度對應工具**——每個工具宣告它需要什麼權限，而系統在呼叫前檢查當前使用者是否具備。

**危險操作分級**——唯讀、可逆的寫入、不可逆的寫入；**後兩者需要不同層級的確認**。

**權限檢查在服務端而非提示**——「不要刪除生產資料」寫在提示裡是一個可以被說服推翻的建議，寫在程式碼裡才是保證。

## 詳細解析

「以使用者身份執行」在技術上有兩種實作：**憑證傳遞**（把使用者的 token 傳給下游，下游用它呼叫資料源）與**代理授權**（Agent 有自己的身份，但每次操作時附上「代表哪個使用者」並由資源方檢查）。前者更簡單也更安全（權限完全由既有系統決定），後者更靈活但需要資源方支援。而無論哪一種，關鍵是「不要在中間某一層把身份丟掉」——一旦某一層開始用服務帳號，後面的所有權限控制就失效了。

「Agent 的權限應該小於使用者的權限」在某些場景是必要的：使用者本人可以刪除自己的資料——但你未必希望 Agent 在沒有明確指示的情況下也能刪。所以除了使用者的權限，還應該有一層「Agent 能做什麼」的限制——**兩者取交集**。這與行動應用的權限模型類似：應用被授予的權限是使用者權限的子集，且需要明確授予。

「確認機制的設計」比「有沒有確認」更重要：如果每個操作都要確認——使用者會養成無腦點「同意」的習慣，確認就失去意義。所以確認應該只用於真正重要的操作，**並且清楚展示「將要發生什麼」**（不是「Agent 想要執行一個操作」，而是「將刪除訂單 12345，此操作不可復原」）。確認疲勞是安全設計中最常見的失敗模式，而它的成因正是「什麼都要確認」。

「審計記錄」是權限體系的必要組成：誰（哪個使用者）透過哪個 Agent 在什麼時候做了什麼——這既是合規要求，也是事故調查的基礎。特別是「Agent 代表使用者執行」這個模式讓責任歸屬變得模糊，而完整的記錄是釐清它的唯一方式。

## 面試回答方式

先給核心原則——以使用者身份而非超級權限的服務帳號執行，並指出否則一次提示注入就是完整的資料外洩。給四個設計要點並強調**權限檢查在服務端而非提示**。加分點有四個：**身份傳遞的兩種實作**與關鍵（不要在中間某一層把身份丟掉，一旦某層用服務帳號，後面的控制全部失效）；Agent 的權限應該小於使用者的權限——使用者可以刪自己的資料但你未必希望 Agent 也能，所以兩者取交集，**與行動應用的權限模型類似**；確認疲勞是最常見的安全失敗模式——什麼都要確認會讓使用者無腦同意，所以確認要只用於真正重要的操作並清楚展示將要發生什麼；以及審計記錄是釐清責任歸屬的唯一方式。

## 講稿

核心原則是代理以使用者的身份執行，而不是用一個超級權限的服務帳號。因為如果它用一個能存取所有資料的帳號，那麼一次提示注入就是完整的資料外洩。而使用者本身的權限限制，天然地限制了損害範圍。

實作上關鍵是不要在中間某一層把身份丟掉。一旦某一層開始用服務帳號，後面的所有權限控制就都失效了。

還有一點，代理的權限應該小於使用者的權限。使用者本人可以刪除自己的資料，但你未必希望代理在沒有明確指示的情況下也能刪。所以除了使用者權限，還要有一層代理能做什麼的限制，兩者取交集。這跟行動應用的權限模型類似。

至於確認機制，設計比有沒有更重要。如果每個操作都要確認，使用者會養成無腦點同意的習慣，確認就失去意義了。所以確認應該只用於真正重要的操作，而且要清楚展示將要發生什麼。不是代理想要執行一個操作，而是將刪除訂單一二三四五、此操作不可復原。確認疲勞是安全設計中最常見的失敗模式。

## 常見追問

### 唯讀的 Agent 就安全了嗎？

**核心答案**：**不是，唯讀仍然有兩類風險**。**資料外洩**——Agent 讀到的內容會進入模型的上下文，而上下文可能透過輸出洩漏給使用者，或者在間接注入的情況下被送到外部。**推論攻擊**——即使每筆資料的存取都合法，大量查詢的組合可能揭露不該被知道的資訊（例如透過多次查詢推斷出某個人的薪資）。

**詳細解析**：「讀取權限的邊界應該與人的一致」是最基本的要求：如果一個客服人員不能看到其他客戶的訂單——**那麼他使用的 Agent 也不能**。但更微妙的是「Agent 讀取的速度與廣度遠超人類」：一個人不會在一分鐘內查詢一千個客戶，而 Agent 可以——於是「技術上合法但實際上異常」的存取模式成為一個新的風險。所以除了權限檢查，還應該有速率限制與異常偵測：單一使用者的 Agent 在短時間內存取大量不同記錄，應該觸發告警甚至阻擋。這是一個「舊的權限模型在新的存取速度下不夠用」的例子——而它在任何自動化存取資料的系統上都適用。

**面試回答方式**：明確回答不安全並給兩類風險（資料外洩、推論攻擊）。核心加分點是**Agent 讀取的速度與廣度遠超人類**——一個人不會在一分鐘內查一千個客戶而 Agent 可以，於是「技術上合法但實際上異常」的存取模式成為新風險，所以除了權限還要有速率限制與異常偵測。收在概括：這是「舊的權限模型在新的存取速度下不夠用」的例子，在任何自動化存取資料的系統上都適用。

### 怎麼設計「需要確認」的操作流程？

**核心答案**：**四個要素**。**明確的預覽**——展示將要執行的具體操作與影響範圍（不是工具名稱，而是「將把這 3 筆訂單標記為已取消」）。**可撤銷的優先**——能設計成可撤銷的就不要設計成需要確認的（撤銷比確認的使用者體驗好得多）。**批次確認**——一次確認一組相關操作而非逐個。**以及「確認的時效」**——過久未確認應該失效並重新驗證狀態。

**詳細解析**：「可撤銷優於確認」是一個容易被忽略但很重要的設計原則：確認打斷了流程並要求使用者在資訊不足時做決定——而「先執行、提供撤銷」讓使用者看到實際結果後再決定。很多操作可以被設計成可撤銷的（軟刪除、暫存草稿、延遲生效）——**而那比確認對話框好得多**。**至於「確認的時效」**：使用者離開五分鐘後回來點了同意，而那五分鐘裡狀態可能已經變了——所以確認時應該重新檢查前置條件，而不是盲目執行當初計畫的操作。這與分散式系統中「檢查後執行」的競態是同一個問題，而在人機互動中它的時間窗口大得多，因此更需要處理。

**面試回答方式**：給四個要素。核心加分點是**可撤銷優於確認**——確認打斷流程並要求使用者在資訊不足時做決定，而先執行加撤銷讓他看到實際結果再決定，並舉出可撤銷的設計（軟刪除、草稿、延遲生效）。收在**確認的時效**：使用者離開五分鐘後回來點同意，而狀態可能已經變了，**所以要重新檢查前置條件**——這與分散式系統「檢查後執行」的競態是同一個問題，只是時間窗口大得多。

### 多租戶的 Agent 服務怎麼隔離？

**核心答案**：在每一層都帶上租戶標識並檢查。**資料層**——查詢必須帶租戶條件，最好在 ORM 或資料庫層強制（row-level security）而非依賴應用程式碼記得加。**工具層**——每個工具的實作都驗證資源屬於當前租戶。**上下文層**——確保一個租戶的資料不會出現在另一個租戶的提示中（共用的快取與範例是常見的洩漏點）。

**詳細解析**：「共用快取的洩漏」是 Agent 服務特有的一個風險：如果為了省成本而快取了某個查詢的結果——**而快取鍵沒有包含租戶標識**，那麼租戶 A 的資料可能被回傳給租戶 B。同樣的風險存在於「用真實案例做少樣本範例」——一個從 A 的資料中提取的範例，如果被放進所有租戶的提示，就是直接的資料外洩。這類洩漏很隱蔽，因為它不涉及任何權限檢查的失敗，只是快取或範例的作用域畫錯了。所以「所有的快取鍵都必須包含租戶標識」應該是一條硬性規則，而範例應該用去識別化的合成資料而非真實案例——這兩條規則能防住這一整類問題。

**面試回答方式**：給三層檢查（資料層用 row-level security、工具層驗證歸屬、上下文層防止交叉）。核心加分點是共用快取的洩漏是 Agent 服務特有的風險——快取鍵沒包含租戶標識就會把 A 的資料回給 B，同樣的風險存在於用真實案例做少樣本範例，而這類洩漏隱蔽因為它不涉及任何權限檢查失敗，只是作用域畫錯了。收在兩條硬性規則：所有快取鍵必須包含租戶標識、範例用去識別化的合成資料而非真實案例。
