# 題目

為什麼很多 Agent 用檔案系統當工作空間？它解決了什麼問題？

## 核心答案

它解決的是「上下文視窗放不下所有東西」這個根本限制。

**三個具體的作用**。**外部記憶**——把中間結果、筆記、計畫寫成檔案，**需要時再讀回來**；於是上下文只需要放「當前這一步需要的內容」而非全部歷史。**可驗證的產出**——Agent 的工作成果是檔案，而檔案可以被 diff、被測試、被 review；**這讓「Agent 做了什麼」變得可檢查**。**與既有工具鏈整合**——編譯器、測試框架、格式化工具、版本控制都是圍繞檔案設計的；用檔案當介面，Agent 就能直接使用整個生態。

而更深的價值是「檔案系統提供了持久且可定址的狀態」——Agent 可以在多次呼叫、甚至多次會話之間累積工作，**而不是每次都從空白開始**。

## 詳細解析

「用檔案代替上下文」是一個重要的模式轉變：早期的 Agent 把所有中間結果都留在對話歷史裡——於是上下文迅速膨脹，成本上升而且關鍵資訊被淹沒。而「把結果寫到檔案，在上下文中只保留一句『我把分析寫到了 analysis.md』」——上下文保持精簡，需要時再讀取。這與作業系統的虛擬記憶體是同構的思路：主記憶體有限，把不常用的換出去。

「可驗證的產出」讓 Agent 的工作可以被工程流程接住：程式碼 Agent 產生的是 diff——**而 diff 可以跑測試、跑 lint、跑 CI**。這把「模型輸出對不對」這個模糊的問題，轉換成「測試過不過」這個確定的問題——**而後者可以自動化**。這正是編碼類 Agent 比其他類型的 Agent 更早成熟的根本原因：它所在的領域已經有完整的驗證基礎設施。

「工作空間需要隔離」是安全的基本要求：Agent 不應該能讀寫任意路徑——必須限制在一個指定的工作目錄內，**並防範路徑穿越（`../../etc/passwd`）**。更嚴格的做法是在容器或虛擬機中提供工作空間——**這與沙箱執行是同一套機制**。

**「檔案操作要留下軌跡」**：Agent 修改檔案時，應該能回答「它改了什麼、為什麼改」。用版本控制（每一步 commit）是最自然的做法——它同時提供了歷史、diff、與回滾能力。**很多編碼 Agent 正是這樣運作的**，而這個設計讓「人工審查 Agent 的工作」變得可行。

## 面試回答方式

先給它解決的根本限制——**上下文視窗放不下所有東西**，並給三個作用（外部記憶、可驗證的產出、與既有工具鏈整合），收在檔案系統提供了持久且可定址的狀態。加分點有四個：「用檔案代替上下文」的模式轉變——把結果寫到檔案、上下文只留一句話，**與虛擬記憶體是同構的思路**；可驗證的產出讓 Agent 的工作被工程流程接住——diff 可以跑測試，把「模型輸出對不對」轉換成「測試過不過」，這正是編碼類 Agent 更早成熟的根本原因；工作空間需要隔離並防範路徑穿越；以及**用版本控制留下軌跡**——它同時提供歷史、diff 與回滾，讓人工審查變得可行。

## 講稿

它解決的是上下文視窗放不下所有東西這個根本限制。

具體有三個作用。第一是外部記憶，把中間結果跟計畫寫成檔案，需要時再讀回來，於是上下文只需要放當前這一步需要的內容。這跟作業系統的虛擬記憶體是同構的思路，主記憶體有限就把不常用的換出去。

第二是可驗證的產出。代理的工作成果是檔案，而檔案可以被比對、被測試、被審查。這一點我覺得特別重要，因為它把模型輸出對不對這個模糊的問題，轉換成測試過不過這個確定的問題，而後者可以自動化。這正是編碼類代理比其他類型更早成熟的根本原因，它所在的領域已經有完整的驗證基礎設施。

第三是能直接用既有的工具鏈，編譯器、測試框架、版本控制都是圍繞檔案設計的。

安全上工作空間必須隔離，限制在指定目錄並防範路徑穿越。另外我會讓每一步都提交進版本控制，這樣同時有了歷史、比對跟回滾，人工審查也才可行。

## 常見追問

### Agent 讀取大檔案時上下文爆掉怎麼辦？

**核心答案**：**不要讓它一次讀整個檔案**。提供的工具應該支援**分段讀取**（按行號範圍）、**搜尋**（在檔案中找關鍵字並只回傳附近的內容）、**以及結構化的概覽**（列出函式名、章節標題）。讓 Agent 先看目錄與概覽，再決定要讀哪一段——這與人閱讀大文件的方式一致。

**詳細解析**：「搜尋優於通讀」是處理大型程式碼庫的關鍵：一個十萬行的專案不可能被放進上下文——而一個好的 Agent 應該像工程師一樣，用 grep 定位、再讀那個檔案的相關部分。所以工具集應該提供高效的搜尋（內容搜尋、符號搜尋、引用查找）而非只有「讀檔案」。這也解釋了為什麼「給 Agent 一個好的程式碼搜尋工具」往往比「換一個上下文更長的模型」收益更大——因為長上下文既貴又有「中間遺失」的問題，而精準的搜尋直接給出相關的部分。這個判斷在成本與效果上都成立，是設計程式碼類 Agent 時最重要的決定之一。

**面試回答方式**：給三種工具能力（分段讀取、搜尋、結構化概覽）並指出這與人閱讀大文件的方式一致。核心加分點是**搜尋優於通讀**——十萬行的專案不可能放進上下文，好的 Agent 應該像工程師一樣用搜尋定位再讀相關部分。收在判斷：給 Agent 一個好的程式碼搜尋工具往往比換一個上下文更長的模型收益更大——因為長上下文既貴又有中間遺失的問題，而精準搜尋直接給出相關部分。

### 多個 Agent 共用工作空間會有什麼問題？

**核心答案**：與多執行緒共享記憶體完全一樣的問題：**競態**（兩個 Agent 同時改同一個檔案）、**互相干擾**（一個 Agent 刪掉了另一個正在用的中間檔案）、**以及狀態不一致**（Agent A 讀到了 Agent B 寫到一半的內容）。最簡單的解法是「每個 Agent 一個獨立的工作空間」——需要協作時透過明確的交付點（把成果複製到共享區）而非共享可寫目錄。

**詳細解析**：「用 git worktree 或獨立分支給每個 Agent 一個隔離的副本」是編碼場景的標準做法：每個 Agent 在自己的分支上工作，完成後合併——衝突由既有的合併工具處理，而那套機制已經被驗證了幾十年。這是一個「用既有的成熟方案解決新問題」的好例子。而如果確實需要共享可寫的空間，那就需要鎖或者明確的分工（每個 Agent 只能寫特定的目錄）——但那增加了協調的複雜度，通常不值得。判斷的原則是「先問這些 Agent 真的需要同時工作嗎」：很多時候串行執行就夠了，而串行完全避免了這一整類問題。

**面試回答方式**：把問題類比成**多執行緒共享記憶體**並列出三類（競態、互相干擾、狀態不一致），給出**每個 Agent 一個獨立工作空間**的解法。核心加分點是**用 git worktree 或獨立分支**這個編碼場景的標準做法——衝突由既有的合併工具處理，而那套機制已被驗證幾十年，是用成熟方案解決新問題的好例子。收在原則：先問這些 Agent 真的需要同時工作嗎——很多時候串行就夠，而串行完全避免了這一整類問題。

### 工作空間的狀態怎麼在會話之間保持？

**核心答案**：把工作空間持久化，並在恢復時給 Agent 一個「當前狀態的摘要」。**單純保留檔案是不夠的**——Agent 還需要知道「上次做到哪、下一步打算做什麼」。實務上的做法是維護一個明確的狀態檔案（進度、待辦、已知問題），**每一步更新它**，**恢復時先讀它。**

**詳細解析**：「讓 Agent 自己維護狀態檔案」有一個額外的好處：它同時是給人看的。一個持續更新的 `PROGRESS.md` 讓人類隨時能知道 Agent 在做什麼——而不需要去讀冗長的對話歷史。這把「可觀測性」變成了工作產出的一部分而非額外的基礎設施。但要注意一個失敗模式：Agent 可能忘記更新那個檔案，或者更新得不準確——所以關鍵的狀態轉換應該由框架強制記錄，而不是完全依賴模型的自覺。「重要的東西不要只依賴模型記得做」是 Agent 設計的一條通用原則——而它適用於狀態記錄、日誌、以及任何你事後需要依賴的東西。

**面試回答方式**：給做法（持久化工作空間、維護明確的狀態檔案、恢復時先讀它）並指出單純保留檔案不夠，Agent 還需要知道上次做到哪。核心加分點是**狀態檔案同時是給人看的**——一個持續更新的進度檔讓人類隨時知道 Agent 在做什麼，把可觀測性變成工作產出的一部分。收在失敗模式與通用原則：Agent 可能忘記更新或更新得不準確，所以關鍵狀態轉換要由框架強制記錄——「重要的東西不要只依賴模型記得做」。
