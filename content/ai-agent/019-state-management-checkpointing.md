# 題目

在設計一個需要支援**檢查點（Checkpoint）持久化**的 Agent 系統時（讓 Agent 即使遭遇意外中斷，也能從中斷點接續執行），具體需要把哪些內容納入這個被持久化保存的『狀態』裡？這種狀態持久化機制會面臨哪些**技術上的具體挑戰**？

## 核心答案

一個完整的 Agent 檢查點狀態通常需要涵蓋幾個核心組成部分——**(1) 執行進度**：目前這個任務已經執行到整個計畫裡的哪一個具體步驟；**(2) 已經累積的記憶／上下文**：這正是前面（見 [[004-memory-systems.md]]）已經深入討論過的 Agent 記憶內容——包括先前已經執行過的所有步驟、已經取得的中間結果；**(3) 任何尚未完成的、正在進行中的外部操作的狀態**（例如如果 Agent 正在等待某個外部的長時間執行的操作完成，需要記錄這個操作目前的具體狀態或識別碼，才能在恢復執行後正確地接續追蹤這個操作）。這種狀態持久化機制會面臨幾個具體的技術挑戰——**(1) 狀態的大小可能隨著任務執行持續增長**（這直接呼應了前面（見 [[004-memory-systems.md]]）已經深入討論過的記憶系統管理挑戰）；**(2) 需要確保狀態被寫入、持久化的這個動作本身是可靠、且不會遺失資料**的（這涉及前面（見 [[006-agent-communication-protocols.md]] 的常見追問）已經深入討論過的分散式系統可靠性議題）；**(3) 從檢查點恢復執行時，需要正確地處理那些「在中斷發生的那個瞬間，狀態可能不上不下、處於曖昧的中間狀態」的情況**（例如一個外部工具呼叫究竟是在中斷發生**之前**就已經成功完成、還是**尚未**真正被觸發、還是**已經被觸發但尚未得知結果**，這三種不同的可能情況在恢復執行時需要被正確地區分、因應）。

## 詳細解析

**檢查點狀態大小持續增長的挑戰——和前面已經深入討論過的記憶系統管理共享相同的核心思路**：延續前面（見 [[004-memory-systems.md]]）已經深入討論過的核心洞察——**Agent 的記憶（執行歷程）會隨著任務持續執行、輪數增加而持續累積增長**——這個核心洞察**同樣適用於檢查點狀態**——如果一個任務執行了**非常多輪**，每一次都需要把**這個持續增長的完整狀態**重新序列化、寫入到持久化儲存裡，這種**「每一次寫入檢查點都需要處理越來越龐大的狀態內容」**的現象會帶來**寫入檢查點本身所需要的時間和儲存成本也隨之持續增加**這個挑戰。因應這個挑戰的做法，某種程度上也和前面（見 [[004-memory-systems.md]]）已經討論過的記憶管理策略**共享相同的核心思路**——**(1) 增量式檢查點（Incremental Checkpointing）**：不是每一次都重新寫入完整的整體狀態，而是只額外地寫入**「相較於上一次已經寫入的檢查點而言，新增、變化的部分」**（這某種程度上類似前面（見 [[004-memory-systems.md]]）已經討論過的『摘要壓縮』這個緩解思路的另一種具體變化型態——不是透過摘要去壓縮狀態本身的大小，而是透過**只記錄增量變化**去減少**每一次寫入動作**實際需要處理的資料量）；**(2) 定期地對早期已經不再需要被頻繁參照的歷史狀態做適度的整理、壓縮或歸檔**。

**確保狀態寫入的可靠性——避免『寫到一半就中斷』導致檢查點本身已經損壞**：一個特別需要被審慎考量的技術挑戰是——**「寫入檢查點」這個動作本身也可能在執行過程中遭遇意外的中斷**（這某種程度上是一種**遞迴性的風險**——原本設計檢查點機制是為了因應任務執行過程中可能發生的意外中斷；但**寫入檢查點這個動作本身**同樣也可能遭遇類似的意外中斷）——如果**在寫入一個檢查點的過程中**這個寫入動作本身**恰好也遭遇意外（例如系統在寫到一半時突然斷電）**，可能會導致**這個檢查點本身處於一種『寫到一半、內容不完整、甚至損壞』的狀態**；如果之後系統嘗試去讀取、依靠這個**已經損壞**的檢查點去恢復執行，反而可能導致更加嚴重的問題（基於一個已經損壞、不完整的狀態去錯誤地恢復執行）。因應這個挑戰，實務上常見的做法是**運用資料庫系統裡早已成熟的『原子性寫入（Atomic Write）』技術手段**——確保**「寫入一個新的檢查點」**這個動作**要嘛完整、徹底地成功完成；要嘛完全沒有發生（如果中途遭遇任何意外）**，而**不會出現『寫到一半』這種不上不下的中間狀態**（常見的具體實作技巧包括**先把新的檢查點內容寫入到一個全新的暫存位置，等確認這個寫入動作已經完整、正確地完成之後，才透過一個單一、不可分割的操作去把這個新寫入的內容正式地替換掉舊的檢查點**，而不是**直接在原本舊的檢查點檔案上做原地修改**）。

**恢復執行時的『中間狀態曖昧性』問題——需要依靠冪等性（Idempotency）設計去妥善因應**：這是一個相當棘手、且直接呼應了前面（見 [[006-agent-communication-protocols.md]] 的常見追問）已經深入討論過的**冪等性**這個核心概念的挑戰——當一個 Agent 從一個檢查點恢復執行時，它**沒有辦法百分之百確定「在中斷實際發生的那個瞬間，究竟有哪些外部操作是已經真正被完整執行完成、哪些則尚未真正被觸發、又哪些處於『已經被觸發、但尚未得知最終結果』的曖昧中間狀態」**——如果恢復執行時**天真地假設某個操作（例如某一次涉及實際金錢交易的工具呼叫）一定尚未被執行**而**重新再執行一次**，但實際上這個操作**在中斷發生之前**就已經**成功被執行完成**了，這就會導致這個操作**被重複執行兩次**（例如一筆金錢交易被重複扣款兩次）。這種**「恢復執行時可能導致某些操作被意外重複執行」**的風險，正是前面（見 [[006-agent-communication-protocols.md]] 的常見追問）已經深入討論過的**冪等性設計**之所以**對 Agent 狀態管理而言同樣至關重要**的核心原因——**任何一個可能在恢復執行過程中被意外重複觸發的操作**都**應該被設計成具備冪等性**（即使被執行多次，最終產生的效果也等同於只被執行一次，不會因為重複執行而產生額外的、錯誤的副作用），才能**確保**即使恢復執行的過程無法百分之百精確地判斷中斷發生瞬間的確切狀態，這種**判斷上的模糊性**也**不會**導致**實質上錯誤、造成實際損害**的後果。

## 面試回答方式

先給出檢查點狀態需要涵蓋的核心組成部分——「執行進度(目前執行到計畫裡的哪個具體步驟)、已經累積的記憶和上下文(先前執行過的步驟和取得的中間結果)、以及任何尚未完成正在進行中的外部操作狀態」。給出三個具體的技術挑戰——「狀態大小可能隨任務執行持續增長，這直接呼應了之前討論過的記憶系統管理挑戰;需要確保狀態寫入這個動作本身可靠不遺失資料，這涉及分散式系統可靠性議題;以及從檢查點恢復執行時，需要正確處理中斷發生瞬間狀態可能處於曖昧中間狀態的情況」。可以詳細展開狀態增長的因應——「可以採用增量式檢查點，不是每次都重新寫入完整狀態，而是只額外寫入相較於上一次已寫入檢查點而言新增變化的部分，這某種程度上呼應了之前討論過的記憶摘要壓縮這個緩解思路的另一種變化型態」。一定要深入解釋恢復執行的曖昧性挑戰——「當Agent從檢查點恢復執行時，沒辦法百分之百確定中斷發生瞬間某個外部操作究竟是已經完整執行完成、尚未被觸發、還是處於已觸發但尚未得知結果的曖昧中間狀態，如果天真假設某個操作尚未被執行而重新再執行一次，但實際上它已經成功執行完成，就會導致這個操作被重複執行兩次，因應這個風險，任何可能在恢復執行過程中被意外重複觸發的操作都應該被設計成具備冪等性」，展現你對Agent狀態管理和檢查點機制的核心組成、以及其獨特技術挑戰，有深入且具體的理解。

## 常見追問

### 在一個多代理系統（Multi-Agent System）裡（前面已經深入討論過），如果需要支援檢查點恢復，這會比單一個 Agent 的檢查點機制額外複雜多少？具體會多出什麼樣的挑戰？

**核心答案**：**會額外複雜相當多**，核心的額外挑戰在於——**需要確保『所有參與協作的多個子 Agent 各自的個別狀態』能夠被『一致性地（Consistently）』共同恢復到一個彼此吻合、不互相矛盾的整體狀態**——在單一個 Agent 的情境裡只需要管理**單一一份連貫的狀態記錄**；但在多代理系統裡，因為**多個子 Agent 各自獨立運作、各自擁有自己的個別狀態**，如果**在某個中斷發生的時間點**這幾個子 Agent **各自恰好執行到不完全同步的不同進度**（例如子 Agent A 已經把它自己的檢查點寫入到第 10 步；但子 Agent B 卻還只寫入到第 7 步，這中間可能還涉及 A 和 B 之間原本應該要互相同步、傳遞的訊息），恢復執行時就需要**額外審慎地去處理這種『各個子 Agent 彼此狀態不完全同步』**的複雜情況，才能避免**恢復出一個內部自相矛盾、不一致的整體系統狀態**。

**詳細解析**：這題把**單一 Agent 的檢查點機制**延伸到**多代理系統**這個更加複雜的協作情境，考察是否能夠理解**多代理系統因為涉及多個獨立節點**這個核心特性會**同時衍生出一系列在單一 Agent 情境下不需要考量的額外挑戰**，而**檢查點／狀態管理**正是**又一個需要被重新審視的重要面向**（這某種程度上呼應了前面（見 [[012-observability-tracing.md]] 的常見追問）已經深入討論過的**『多代理系統可觀測性需要額外的追蹤識別碼機制，去串接、重建分散在不同 Agent 的個別記錄』**這個核心思路，只是這裡把這個思路延伸到**『恢復執行』**這個新的具體場景）。理解這個問題的核心在於回顧一個在**傳統的分散式系統理論**裡早已被深入研究累積的經典難題——**「分散式系統裡的一致性快照（Consistent Snapshot）」**問題——當一個**由多個獨立節點構成**的系統需要**同時為所有節點拍下一份『快照』**去**捕捉整個系統在某個特定時間點的完整狀態**時，**單純地各自獨立地讓每一個節點分別自行記錄自己當下的狀態****並不足以**確保**這些各自獨立記錄下來的個別快照**組合起來**能夠構成一個真正邏輯上一致、彼此吻合的整體系統狀態**——這是因為**這些不同節點各自拍攝快照的具體時間點**可能**存在些微的時間差異**，而在這個細微的時間差異之間**節點之間可能恰好正在交換某些訊息**，如果**這些正在傳遞中的訊息**在**這種不完全同步的快照捕捉過程中**被**不當地遺漏、或者被重複地計算**，就會導致**最終恢復出來的整體狀態出現不一致**。這種**分散式系統裡一致性快照的核心難題**某種程度上**完全適用於**這裡討論的**多代理系統檢查點機制**——每一個子 Agent 就類似於**分散式系統裡的一個獨立節點**；而**「需要同時為所有子 Agent 建立一個彼此一致的整體檢查點」**正是**分散式系統裡那個經典的一致性快照難題**在多代理系統情境下的一個**具體展現**。因應這個難題，實務上通常需要借助**傳統分散式系統理論裡已經發展出來的成熟解決方案**（例如某些**專門用來協調多個分散節點同步地拍攝一致性快照的成熟演算法**），而**不是**只是**天真地讓每一個子 Agent 各自獨立地去記錄自己的檢查點**。這種**「識別出多代理系統的檢查點挑戰，和傳統分散式系統裡早已被深入研究的一致性快照難題本質相通」**的洞察，再次展現了這篇文章反覆強調的核心價值——**跨越不同技術領域，識別出共通的核心工程規律和既有成熟解決方案**。理解「會額外複雜相當多，核心額外挑戰在於需要確保所有參與協作的多個子Agent各自的個別狀態，能夠一致性地共同恢復到一個彼此吻合、不互相矛盾的整體狀態，單一Agent只需管理單一連貫的狀態記錄，但多代理系統因為多個子Agent各自獨立運作各自擁有個別狀態，如果在中斷發生時各子Agent恰好執行到不完全同步的不同進度，恢復執行時需要額外審慎處理這種各子Agent彼此狀態不完全同步的複雜情況，才能避免恢復出一個內部自相矛盾的整體系統狀態，這個問題本質上和傳統分散式系統理論裡早已被深入研究的一致性快照難題相通——單純各自獨立記錄每個節點的狀態，並不足以確保這些個別快照組合起來能構成一個真正邏輯上一致的整體系統狀態，因應這個難題實務上通常需要借助傳統分散式系統理論裡已發展出來的成熟解決方案，而不是天真地讓每個子Agent各自獨立記錄自己的檢查點」，展現你能把多代理系統的檢查點挑戰，正確連結到分散式系統裡一致性快照這個經典且成熟的既有理論問題，而非把它當成孤立的全新問題。

**面試回答方式**：先給出核心答案——「會額外複雜相當多，核心額外挑戰在於需要確保所有參與協作的多個子Agent各自的個別狀態，能夠一致性地共同恢復到一個彼此吻合、不互相矛盾的整體狀態」。具體說明問題所在——「如果在中斷發生時各子Agent恰好執行到不完全同步的不同進度，例如子Agent A已經寫入到第10步，但子Agent B卻只寫入到第7步，這中間可能還涉及A和B之間原本應該互相同步傳遞的訊息，恢復執行時需要額外審慎處理這種狀態不同步的情況」。連結到既有的成熟理論——「這個問題本質上和傳統分散式系統理論裡早已被深入研究的一致性快照這個經典難題相通，單純各自獨立記錄每個節點的狀態並不足以確保這些個別快照組合起來能構成一個邏輯上一致的整體狀態，因應這個難題通常需要借助分散式系統理論裡已發展出來的成熟解決方案」。

### 如果一個 Agent 系統涉及大量使用者、大量並行的任務同時都需要做狀態持久化，這對底層的儲存系統選型會有什麼樣的具體要求？

**核心答案**：**核心的要求是這個底層儲存系統需要同時具備「高寫入吞吐量（High Write Throughput）」和「低寫入延遲（Low Write Latency）」這兩個特性**——因為延續前面已經深入討論過的核心認知——**檢查點的寫入可能會相當頻繁地發生（例如每完成一個關鍵步驟就寫入一次）**——如果同時有**大量、並行**的 Agent 任務都在**各自頻繁地**觸發這種檢查點寫入動作，這個底層儲存系統需要能夠**在單位時間內承受、處理大量的並行寫入請求（高吞吐量）**，同時**每一次個別的寫入動作本身也需要儘可能快速地完成（低延遲）**（因為如果寫入檢查點這個動作本身速度過慢，會直接地拖慢整個 Agent 任務的實際執行速度）。因應這種需求，實務上常見的選型考量包括**優先選用那些專門針對『高並行、低延遲寫入』**這類使用情境而經過特別優化設計的儲存技術方案（例如某些特定類型的 NoSQL 資料庫、或者鍵值儲存系統，相較於傳統的關聯式資料庫在這種特定情境下可能更具優勢）。

**詳細解析**：這題要求把 Agent 狀態管理這個議題**延伸到大規模、多租戶**這個**實際的商業化應用情境**下所需要額外考量的**底層基礎設施選型**問題，考察是否能夠把前面已經建立的核心概念連結到一個**更加貼近實際大規模系統架構設計**的具體工程決策。理解這個問題的核心在於先釐清 **Agent 檢查點寫入**這種**具體的資料存取模式（Access Pattern）**具備哪些獨特的特徵——**(1) 寫入頻率相對較高**：因為一個 Agent 任務可能涉及好幾十輪的執行，每一輪都可能觸發一次檢查點寫入，如果**同時有大量 Agent 任務並行運作**，這種**寫入請求的總體頻率**會是**相當可觀**的；**(2) 每一筆個別的寫入內容通常是一個相對獨立的完整狀態記錄**（而不是像某些傳統應用場景那樣需要做複雜的跨資料表關聯查詢）。這種**「寫入頻率高、但每一筆寫入內容相對獨立、不需要複雜關聯查詢」**的具體存取模式特徵，正是判斷**這個底層儲存系統選型**的核心依據——**傳統的關聯式資料庫**某種程度上是針對**需要支援複雜關聯查詢、且對資料的一致性要求極為嚴謹**這類情境而被優化設計，這種設計取向某種程度上**未必**是 **Agent 檢查點這種『高頻率、簡單獨立記錄』**存取模式情境下最理想的選擇；反而**某些專門針對『大量、簡單鍵值形式資料的高速讀寫』**這類情境而被特別優化設計的 **NoSQL 資料庫或鍵值儲存系統**可能更加**貼合** Agent 檢查點寫入這種具體的存取模式需求——這種**「先仔細地分析、釐清一個具體應用場景的實際資料存取模式特徵，再依照這種特徵去選擇最恰當吻合的底層儲存技術」**的思路，正是**任何一個涉及底層儲存系統選型**的架構決策都需要遵循的核心方法論——**不應該只是因為某種資料庫技術『比較知名、或者比較常見』就理所當然地直接套用**，而應該**先仔細地去分析這個具體應用場景真正需要的存取模式特性（讀寫比例、並行度、延遲要求、查詢複雜度等），再依照這種分析結果去做恰當的技術選型**。理解「核心要求是這個底層儲存系統需要同時具備高寫入吞吐量和低寫入延遲這兩個特性，因為檢查點寫入可能相當頻繁發生，如果同時有大量並行的Agent任務都在各自頻繁觸發這種檢查點寫入動作，這個底層儲存系統需要能在單位時間內承受處理大量並行寫入請求，同時每一次個別寫入動作本身也需要儘可能快速完成，因應這種需求需要先仔細分析Agent檢查點寫入這種具體資料存取模式的獨特特徵——寫入頻率相對較高、每筆個別寫入內容通常是一個相對獨立完整的狀態記錄、不需要複雜跨資料表關聯查詢，傳統關聯式資料庫是針對需要複雜關聯查詢且對一致性要求極嚴謹這類情境而優化設計，未必是Agent檢查點這種高頻率簡單獨立記錄存取模式下最理想的選擇，反而某些專門針對大量簡單鍵值形式資料高速讀寫這類情境而優化的NoSQL資料庫或鍵值儲存系統可能更貼合這種需求，這種先仔細分析具體應用場景的實際資料存取模式特徵、再依照這種特徵選擇最恰當吻合底層儲存技術的思路，正是任何涉及底層儲存系統選型的架構決策都需要遵循的核心方法論」，展現你能把Agent狀態管理延伸到底層基礎設施選型這個實際大規模系統架構設計問題，並給出基於存取模式分析的具體技術選型方法論。

**面試回答方式**：先給出核心要求——「核心要求是這個底層儲存系統需要同時具備高寫入吞吐量和低寫入延遲這兩個特性，因為檢查點寫入可能相當頻繁發生，如果同時有大量並行任務都在頻繁觸發這種寫入，系統需要能承受大量並行寫入請求，同時每次寫入動作也需要儘可能快速完成」。給出具體的存取模式分析——「Agent檢查點寫入這種資料存取模式的獨特特徵是寫入頻率相對較高、每筆個別寫入內容通常是一個相對獨立的完整狀態記錄、不需要複雜的跨資料表關聯查詢」。給出技術選型的具體建議和方法論——「傳統關聯式資料庫是針對需要複雜關聯查詢且對一致性要求極嚴謹這類情境優化，未必是最理想選擇，反而某些專門針對大量簡單鍵值形式資料高速讀寫優化的NoSQL資料庫或鍵值儲存系統可能更貼合，任何涉及底層儲存選型的決策都應該先仔細分析具體應用場景真正需要的存取模式特性，再依照分析結果做恰當的技術選型」。

### 檢查點和前面已經深入討論過的可觀測性／追蹤記錄，兩者聽起來都涉及「記錄 Agent 過去的執行狀態」，是不是可以直接共用同一份記錄，而不需要分別設計兩套機制？

**核心答案**：**雖然兩者都涉及『記錄 Agent 過去的執行狀態』，但它們服務的目的以及對記錄內容的要求存在關鍵差異，不建議直接共用同一份記錄而不加區分**——**追蹤記錄**（見 [[012-observability-tracing.md]]）主要服務的目的是**「事後除錯、分析」**，它**需要儘可能詳盡、完整地**保留執行過程中的**每一個細節**（包括那些**即使最終沒有影響最終結果**的枝節嘗試），即使這意味著記錄本身**相對冗長、龐大**；而**檢查點**主要服務的目的是**「支援從中斷點恢復執行」**，它**只需要**保留**「足以讓系統正確地接續執行」**這個目的所真正必要的核心狀態資訊（例如不需要保留那些**已經確定失敗、被放棄的枝節嘗試的完整細節**，只需要保留**目前有效的執行進度和關鍵結果**）。這種**「一個追求詳盡完整；另一個追求精簡、聚焦於恢復執行所需的核心資訊」**的目的差異，讓**直接共用同一份記錄**變得**並不是一個理想的做法**。

**詳細解析**：這題要求對**「追蹤記錄」**和**「檢查點」**這兩個**都涉及『記錄過去執行狀態』**這個表面相似字眼的機制做**精確的目的區分**，考察是否能夠避免把**「記錄機制表面上涉及類似的資訊」**簡單地等同於**「這兩個機制可以被直接合併共用」**。理解這個問題的核心在於回顧——**「記錄的目的」本質上決定了「這份記錄應該包含哪些內容，以及應該用什麼樣的格式、儲存方式去保存」**——**追蹤記錄**因為它服務的目的是**「協助人類（或工具）事後理解、診斷整個執行過程究竟發生了什麼」**，它**理應**保留**儘可能豐富、詳盡**的資訊（即使某些資訊事後看來**並非真正關鍵**，多保留一些總好過遺漏掉某個**事後才發現其實很關鍵**的細節），這種**「寧可詳盡冗長，也不要遺漏關鍵細節」**的取向某種程度上**天然地**會導致這份記錄變得**相對龐大、且可能包含大量對『恢復執行』這個目的而言其實並不真正必要**的枝節資訊——例如某個**已經被嘗試過、但最終判斷失敗、被放棄**的探索路徑，它的完整過程細節對**『事後除錯』**而言可能**依然具備價值**（可以幫助理解 Agent 為什麼最終選擇了現在這條路徑、而放棄了那條），但對**『恢復執行』**這個目的而言，這段**已經被確定放棄的失敗嘗試**其實**完全不需要**被包含在用來**支援恢復執行**的檢查點裡（恢復執行時只需要知道**目前有效的、正在被採用的執行路徑和進度**即可，不需要去**重新回顧那些已經被放棄的枝節嘗試**）。這種**「追蹤記錄追求詳盡完整（即使龐大）；檢查點追求精簡聚焦（只保留恢復執行所需的核心資訊）」**的目的性差異，帶來一個相當重要的實務啟示——**應該把「追蹤記錄」和「檢查點」設計成兩套各自獨立、但可以共享部分底層資料來源的機制**（例如檢查點可以被理解成從完整的追蹤記錄裡**額外提煉、篩選出來**的一份精簡子集合，只保留恢復執行真正需要的核心內容），而**不是**天真地把**這兩個服務不同目的的記錄****直接合併視為同一份、不加區分**的單一記錄。這種**「識別出表面相似的機制背後實際上服務不同目的，因而需要被各自獨立設計、而非直接合併」**的分析能力，正是這篇文章反覆強調、值得被持續培養的核心分析能力。理解「雖然兩者都涉及記錄Agent過去的執行狀態，但服務的目的和對記錄內容的要求存在關鍵差異，不建議直接共用，追蹤記錄主要服務事後除錯分析這個目的，需要儘可能詳盡完整地保留執行過程的每個細節，即使某些細節事後看來並非真正關鍵，多保留一些總好過遺漏掉某個其實很關鍵的細節;而檢查點主要服務支援從中斷點恢復執行這個目的，只需要保留足以讓系統正確接續執行這個目的所真正必要的核心狀態資訊，不需要保留那些已經確定失敗被放棄的枝節嘗試的完整細節，這種一個追求詳盡完整、另一個追求精簡聚焦的目的差異，讓直接共用同一份記錄變得並不是理想做法，應該把兩者設計成各自獨立、但可以共享部分底層資料來源的機制，而不是直接合併視為同一份不加區分的單一記錄」，展現你能對兩個表面相似但服務不同目的的機制做出精確區分，而非因表面相似就簡單認定可以合併共用。

**面試回答方式**：先明確給出核心答案——「雖然兩者都涉及記錄Agent過去的執行狀態，但服務的目的和對記錄內容的要求存在關鍵差異，不建議直接共用同一份記錄」。解釋兩者的目的差異——「追蹤記錄主要服務事後除錯分析，需要儘可能詳盡完整地保留每個細節，即使某些細節事後看來並非真正關鍵也寧可保留;而檢查點主要服務支援從中斷點恢復執行，只需要保留足以讓系統正確接續執行的核心狀態資訊，不需要保留已經確定失敗被放棄的枝節嘗試完整細節」。給出實務建議——「應該把追蹤記錄和檢查點設計成兩套各自獨立、但可以共享部分底層資料來源的機制，檢查點可以被理解成從完整追蹤記錄裡額外提煉篩選出來的一份精簡子集合，而不是直接合併視為同一份不加區分的單一記錄」。
