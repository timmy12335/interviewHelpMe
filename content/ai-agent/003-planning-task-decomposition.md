# 題目

在 Agent 的情境裡，「規劃（Planning）」和「任務分解（Task Decomposition）」具體指的是什麼？為什麼讓大型語言模型處理一個**複雜、龐大**的任務時，先進行任務分解，通常會比直接要求模型一次性處理整個複雜任務得到更好的結果？

## 核心答案

在 Agent 的情境裡，**任務分解**指的是**把一個原本龐大、複雜、難以被一步到位直接解決的整體任務，拆解成一系列規模相對較小、目標相對單一明確、彼此之間可能存在特定先後依賴關係的子任務**；而**規劃**則是**依照這些被拆解出來的子任務決定一個合理的執行順序（考量子任務之間的依賴關係），形成一個完成整體任務的具體行動藍圖**。之所以先進行任務分解、規劃再逐步執行這些子任務，通常會比直接要求模型一次性地處理整個複雜任務得到更好的結果，核心原因在於——這某種程度上呼應了前面（見 [[../ai-llm/021-chain-of-thought.md]]）已經深入討論過的 CoT 核心效益——**如果直接要求模型針對一個龐大、複雜的整體任務一次性地就給出完整的解決方案，模型實際上需要在單一次的處理過程裡同時兼顧、處理這個複雜任務裡所有盤根錯節的細節和考量，這很容易超出模型在單一次推理過程裡所能妥善處理的複雜度上限**；而透過先把這個龐大任務拆解成多個各自規模較小、目標較為單一明確的子任務，模型**每一次只需要專注在處理其中一個相對簡單、範疇明確的子任務**，這某種程度上是把原本過於龐大、複雜的整體認知負荷**分散展開到多個獨立、規模較小的處理步驟裡**，讓每一個獨立的步驟都更容易被模型妥善地處理好，進而讓整體任務最終的完成品質和成功率得到顯著的提升。

## 詳細解析

**任務分解的具體實作方式——模型自己動態分解，或依照固定範本結構化分解**：實務上讓 Agent 對一個複雜任務進行任務分解，大致存在幾種不同的具體實作思路——**(1) 讓模型自主地動態生成分解結果**——直接把這個複雜的整體任務描述提供給模型，並明確地要求模型**先**針對這個任務輸出一份它自己判斷出來的、拆解成哪些具體子任務以及這些子任務彼此的先後順序的規劃結果。這種做法的優勢是**靈活、能夠因應各種不同性質、事先難以被窮舉預料的任務類型**，但相對地這個分解結果的品質高度地取決於模型本身對這一類任務的理解和規劃能力（如果模型對某一類特定領域的任務缺乏足夠深入的理解，它自己生成出來的分解方案也可能存在遺漏、或是不夠合理的先後順序安排這類問題）；**(2) 依照某種事先已經設計好的固定範本結構進行分解**——針對某些**性質相對固定、重複出現的任務類型**（例如『撰寫一份市場調查報告』這種任務，可能總是可以被拆解成類似的幾個固定子步驟：蒐集資料、分析資料、撰寫初稿、審閱修改），可以**預先設計好一套針對這種特定任務類型的固定分解範本**，讓 Agent 直接依照這個已經被人類事先設計好的固定範本去進行任務分解（而不需要每一次都重新讓模型自己從零去判斷應該怎麼分解）。這種做法的優勢是**分解結果更加穩定、可預期，也能充分融入人類專家對這一類任務的既有經驗和最佳實務**，但相對地**彈性較低**，難以因應那些性質和既有範本明顯不同的新型態任務。

**規劃時需要考量的核心要素——子任務之間的依賴關係**：進行規劃時一個相當核心、也容易被簡化忽略的考量要素，是**子任務之間是否存在依賴關係**——這某種程度上呼應了前面（見 [[../ai-llm/022-function-calling.md]]）已經討論過的多工具協同呼叫情境裡『呼叫順序的依賴關係』這個議題，只是在 Agent 規劃這個更通用的情境下，這種依賴關係不僅限於具體的工具呼叫順序，而是涵蓋**任何一個子任務的執行是否需要依賴另一個子任務先被完成、並取得某個特定結果**這種更廣泛的情況——一個妥善的規劃需要**正確地識別出哪些子任務之間存在這種必須依照特定先後順序執行的依賴關係（不能被錯誤地同時、或以錯誤的順序執行），而哪些子任務彼此之間並不存在這種依賴（可以被平行、同時地處理以提升整體的執行效率）**。正確地梳理出這種依賴關係的結構，是讓一個規劃真正具備實際可行性、且能兼顧執行效率的關鍵。

**過度細碎的任務分解可能帶來的反效果**：雖然任務分解通常能帶來前面已經討論過的效益，但需要注意的是——**任務分解的粒度並不是越細越好**——如果把一個任務拆解得**過度瑣碎**（例如把一個本身就相對簡單、模型可以一次性妥善處理的子任務，又進一步拆解成好幾個更細瑣碎的子步驟），這**並不會**帶來額外的效益（因為這個子任務本身的複雜度並沒有超出模型單次處理的能力上限），反而會因為**額外增加了需要被執行的獨立步驟數量**而帶來**額外的執行時間延遲以及額外的運算成本**（這某種程度上呼應了前面（見 [[../ai-llm/021-chain-of-thought.md]]）已經深入討論過的『CoT 展開的中間推理步驟並非越長越好，存在邊際效益遞減』這個核心洞察，這裡可以被類比延伸理解成——**任務分解的粒度理想上應該恰好對應到這個子任務本身真正需要的複雜度，而不是一味地追求分解得越細越好**）。因此實務上判斷一個任務應該被分解到多細的粒度，需要依照**這個子任務本身的複雜度是否確實已經超出模型單次處理的能力上限**來做出恰如其分的判斷，而不是盲目地追求分解得越細越好。

## 面試回答方式

先分別定義任務分解和規劃這兩個概念——「任務分解是把一個龐大複雜、難以一步到位解決的整體任務，拆解成一系列規模較小、目標單一明確、彼此可能存在先後依賴關係的子任務;規劃則是依照這些子任務，決定一個合理的執行順序，形成完成整體任務的具體行動藍圖」。詳細解釋核心原因，並主動連結CoT——「這呼應了之前討論過的CoT核心效益，如果直接要求模型一次性處理整個複雜任務，模型需要在單一次推理裡同時兼顧所有盤根錯節的細節，很容易超出單次處理的複雜度上限;而透過先拆解成多個各自規模較小的子任務，模型每次只需專注處理一個相對簡單、範疇明確的子任務，把原本過於龐大的整體認知負荷分散展開到多個獨立步驟裡」。可以補充兩種分解方式的比較——「讓模型自主動態生成分解結果，靈活但品質取決於模型本身的規劃能力;依照事先設計好的固定範本分解，結果更穩定可預期但彈性較低，難以因應新型態任務」。一定要提到依賴關係的重要性——「規劃時需要正確識別哪些子任務之間存在必須依照特定順序執行的依賴關係、哪些可以平行處理以提升效率」。可以誠實補充一個平衡認知——「任務分解的粒度並非越細越好，如果拆解得過度瑣碎，並不會帶來額外效益，反而會增加執行步驟數量帶來的額外時間和運算成本，這呼應了CoT展開步驟並非越長越好、存在邊際效益遞減的核心洞察」，展現你對任務分解和規劃有紮實且平衡的理解。

## 常見追問

### 如果 Agent 在執行規劃好的某個子任務時，發現這個子任務實際上無法達成（例如需要的資訊根本不存在），整個原本已經規劃好的行動藍圖應該如何因應？

**核心答案**：這種情況正是前面（見 [[001-agent-fundamentals.md]]）已經討論過的 Agent『持續性、動態調整』這個核心特徵需要真正發揮作用的時刻——一個設計良好的 Agent 不應該**盲目地依照原本已經規劃好的行動藍圖機械式地繼續往下執行**（即使某個關鍵的前置子任務實際上已經確認無法達成），而應該**把這個『某個子任務無法達成』的新資訊重新納入考量，動態地重新評估、調整接下來的規劃**——具體的因應方式可能包括：**(1) 尋找替代方案**（是否存在另一種不同的做法或路徑，可以繞過這個無法達成的子任務，依然達成整體任務的目標）；**(2) 調整整體任務的範疇或目標**（如果這個無法達成的子任務是達成整體目標不可或缺的關鍵前提，可能需要誠實地向使用者說明整體任務的目標可能需要被適度地調整或縮減）；**(3) 如實地回報這個障礙**（如果前面兩種因應方式都不可行，Agent 應該誠實地向使用者說明遇到了什麼樣的障礙、為什麼無法達成原本的目標，而不是勉強繼續執行，產出一個實際上並沒有真正達成任務目標的低品質結果）。

**詳細解析**：這題把前面（見 [[001-agent-fundamentals.md]]）已經建立的 Agent 核心特徵——**『持續地依照實際回饋動態調整』**——具體地應用到「規劃遭遇執行阻礙」這個實務上相當常見、也相當關鍵的情境上，考察是否能夠避免把「規劃」這個概念誤解成一種**一旦制定就不可更動的僵固藍圖**。理解這個問題的核心在於認識到——**一個規劃終究是依照制定這個規劃時所掌握的資訊所做出的最佳判斷**，而這個規劃制定的當下**不可能完全預見到實際執行過程中可能會遇到的每一種意外狀況**（尤其是像『某個原本假設存在的關鍵資訊實際上並不存在』這種**只有真正嘗試去執行這個子任務之後才能被發現**的障礙）。因此一個真正具備前面已經討論過的『Agent 自主性和持續性』的系統，**必須具備在執行過程中一旦發現原本的規劃因為某些新發現的事實而不再可行時，重新動態地評估、調整規劃**的能力，而**不是**把一開始制定的規劃當作一個不管後續發生什麼狀況都必須機械式地硬著頭皮繼續執行下去的僵固指令。這種「發現規劃不可行時如何恰當地因應」這件事也牽涉到一個更深層的價值判斷——一個設計得當的 Agent 應該被賦予**誠實地回報自己遇到的障礙、以及自己無法達成原本設定目標**的能力和意願，而不是為了表面上看起來『完成了任務』而勉強地產出一個實際上內容空洞、或是帶有前面（見 [[../ai-llm/014-hallucination-problem.md]]）已經深入討論過的幻覺內容的低品質『假結果』——這種**誠實地承認自己的能力邊界和限制**的設計原則，某種程度上比單純地追求『無論如何都要產出一個看起來完整的答案』這個表面上的目標更重要，也更能讓使用者真正信任這個 Agent 系統的整體可靠性。理解「Agent面對規劃遭遇執行阻礙時，不應該盲目依照原本已規劃好的行動藍圖機械式繼續執行，而應該把這個新發現的障礙資訊重新納入考量，動態地重新評估調整接下來的規劃，具體因應方式包括尋找替代方案、調整整體任務的範疇或目標、或誠實地回報這個障礙，一個設計良好的Agent應該被賦予誠實回報自己遇到障礙和能力限制的意願，而不是為了表面上完成任務而勉強產出實際上空洞或帶有幻覺內容的低品質假結果，這種誠實承認能力邊界的設計原則，比單純追求無論如何都要產出看起來完整答案這個表面目標更重要，也更能讓使用者真正信任這個Agent系統的整體可靠性」，展現你理解Agent的規劃不是僵固藍圖，而應具備動態調整的持續性，並且對Agent設計裡「誠實回報限制」這個價值判斷有深刻認識。

**面試回答方式**：先給出核心答案——「這正是Agent持續性、動態調整這個核心特徵需要真正發揮作用的時刻，不應該盲目依照原本已規劃好的行動藍圖機械式繼續執行，而應該把這個新發現的障礙重新納入考量，動態地重新評估調整接下來的規劃」。給出具體的三種因應方式——「尋找替代方案看是否有其他路徑可以繞過這個障礙;如果這是達成目標不可或缺的關鍵前提，可能需要調整整體任務的範疇或目標;如果都不可行，應該誠實地向使用者回報遇到的障礙，而不是勉強產出一個實際上沒有真正達成目標的低品質結果」。可以補充更深層的價值判斷——「一個設計良好的Agent應該被賦予誠實回報自己能力限制的意願，而不是為了表面上完成任務就產出空洞或帶有幻覺的假結果，這種誠實承認限制的設計原則，比單純追求無論如何都要產出看起來完整的答案更重要，也更能讓使用者真正信任這個系統」。

### 「讓模型自己動態生成任務分解方案」這種做法，如果模型自己對分解方案的判斷出現了不合理的地方（例如遺漏了某個必要的子任務，或者把順序搞錯了），有沒有辦法在執行前就先發現、糾正這個問題，而不是等到執行到一半才發現規劃有誤？

**核心答案**：有，一個常見、且相對有效的做法，是在**規劃階段生成完之後、正式進入執行階段之前**額外地加入一個**「規劃審查（Plan Review／Critique）」的環節**——具體做法是把模型自己生成出來的這份任務分解和規劃結果**再次提供給（可能是同一個模型、或是另一個獨立的模型），明確地要求它針對這份規劃本身進行批判性的審查**——檢查是否存在明顯遺漏的必要子任務、子任務之間的先後順序安排是否合理、是否存在任何邏輯上不通順或是明顯不合理的規劃內容，如果這個審查環節發現任何問題，就要求模型**依照這些發現的問題重新修正、調整這份規劃**，直到這份規劃通過審查的檢驗才正式進入實際的執行階段。這種**「先讓模型生成規劃，再額外讓模型（或另一個模型）審查、批評這份規劃本身」**的做法，能夠在一定程度上提前在實際投入執行這個可能存在缺陷的規劃之前，就先攔截、糾正一部分明顯的規劃錯誤。

**詳細解析**：這題考察是否理解「讓模型自己審查、批評自己（或是另一個模型）先前生成的內容」這種設計模式在 Agent 架構裡一個相當常見、且具備實際效益的應用場景。理解這個做法背後的核心思路，需要回顧一個在機器學習和軟體工程領域都相當普遍的原則——**「生成（Generation）」和「審查／驗證（Verification）」往往是兩種性質不完全相同的認知任務**——**生成一份完整、合理的規劃**這件事本身需要同時兼顧、處理非常多的細節和考量（有點類似前面已經討論過的『直接處理一個複雜整體任務所面臨的認知負荷過重』這個問題），這種**從無到有構思出一個完整方案**的任務天生就比較容易出現疏漏；而**針對一份已經存在的具體規劃內容去檢視、審查它是否存在某些明顯的問題**，這件事某種程度上是一個**相對更聚焦、更容易被妥善處理**的任務（這某種程度上呼應了前面（見 [[../ai-llm/019-rlhf.md]]）已經討論過的 RLHF 裡『人類判斷相對優劣，比撰寫絕對答案更容易、更自然』這個核心洞察——**『針對一個已經存在的具體方案去判斷它是否存在問題』，通常比『從零開始構思出一個完美無缺的方案』是一件認知負擔更低的任務**）。因此透過把**『生成規劃』**和**『審查規劃』**拆分成**兩個各自獨立、且各自更聚焦的步驟**，能夠某種程度上**降低整體犯錯的機率**——即使第一步（生成）因為任務本身的複雜度而出現了一些疏漏，第二步（審查）因為是一個相對更聚焦、更容易被妥善執行的任務，有較高的機率能夠捕捉到這些第一步所遺留下來的疏漏。這種**「生成－審查」兩階段拆分**的思路某種程度上也是一種更廣泛的軟體工程和品質保證原則——**「產出一份內容」和「檢查、驗證這份內容的品質」分開由不同的步驟（或不同的人／系統）各自承擔，通常比要求同一個步驟同時兼顧生成和自我審查這兩件事更能提升整體的最終品質**。需要補充的是，這種規劃審查機制並**不能保證百分之百捕捉到所有的規劃缺陷**（審查這個步驟本身同樣是由一個可能存在局限性的模型來執行，它同樣有可能遺漏某些更隱蔽、不容易被發現的規劃問題），但它作為一道**額外的品質把關機制**確實能在一定程度上提升整體規劃的可靠性，降低執行到一半才發現規劃本身存在嚴重缺陷這種情況發生的機率。理解「規劃審查是在規劃生成完之後、正式執行之前，額外加入一個讓模型(或另一個模型)針對這份規劃本身進行批判性審查的環節，這種做法的核心思路是生成和審查往往是兩種性質不完全相同的認知任務，生成一份完整合理的規劃需要同時兼顧處理非常多細節，天生容易出現疏漏，而針對一份已經存在的具體規劃去檢視審查它是否存在問題，是一個相對更聚焦、認知負擔更低的任務，這呼應了RLHF裡人類判斷相對優劣比撰寫絕對答案更容易的核心洞察，透過把生成和審查拆分成兩個各自獨立且更聚焦的步驟，能降低整體犯錯機率，但這種機制並不能保證百分之百捕捉所有規劃缺陷，審查步驟本身同樣可能遺漏更隱蔽的問題」，展現你能把RLHF裡已經建立的核心洞察(判斷相對優劣比從零生成更容易)，遷移應用到Agent規劃審查這個新的具體場景，展現跨主題融會貫通的能力。

**面試回答方式**：先給出核心做法——「常見且相對有效的做法是在規劃生成完之後、正式執行之前，額外加入一個規劃審查的環節，把模型自己生成的任務分解和規劃結果，再次提供給模型(或另一個獨立模型)，明確要求針對這份規劃本身進行批判性審查，檢查是否有遺漏的必要子任務、順序安排是否合理，如果發現問題就要求重新修正，通過審查才正式進入執行階段」。解釋這個做法背後的核心思路——「生成和審查往往是兩種性質不完全相同的認知任務，從零構思出一份完整規劃需要同時兼顧非常多細節，天生容易出現疏漏;而針對一份已存在的具體規劃去檢視它是否有問題，是一個相對更聚焦、認知負擔更低的任務，這呼應了之前RLHF章節討論過的人類判斷相對優劣比撰寫絕對答案更容易這個核心洞察」。誠實補充侷限——「這種機制不能保證百分之百捕捉所有規劃缺陷，審查步驟本身同樣可能遺漏更隱蔽的問題，但作為一道額外的品質把關機制，確實能提升整體規劃的可靠性」。

### 任務分解和之前系統設計類別裡討論過的、把一個大型系統拆解成多個微服務（Microservices），這兩件事在思路上有什麼相似或可以互相借鏡之處？

**核心答案**：**兩者在核心思路上確實存在相當程度的相似性**——都是**把一個原本龐大、複雜、難以被整體一次性妥善處理的東西，拆解成多個規模較小、職責較為單一明確的獨立單元**，並且都需要仔細地處理**這些被拆解出來的獨立單元之間的依賴關係和溝通協調**這個核心挑戰——在任務分解的情境裡，這對應前面已經討論過的『子任務之間的先後依賴關係』；在微服務架構的情境裡（見 [[../backend-engineering/009-service-discovery.md]]、[[../backend-engineering/013-distributed-transaction-solutions.md]] 相關討論），這對應服務之間的呼叫依賴、以及資料一致性協調這類挑戰。兩者都共享著一個更普遍的核心工程智慧——**「拆解能夠降低每一個獨立單元本身的複雜度，讓每個單元更容易被妥善地設計、實作、驗證，但這種拆解也會引入新的挑戰——如何妥善地管理、協調這些被拆解出來的獨立單元之間的互動關係」**。

**詳細解析**：這題考察是否能夠識別出**任務分解**這個 Agent 架構裡的具體概念，和**微服務架構**這個系統設計領域裡更廣為人知的概念，兩者背後其實共享著一個更普遍、更抽象的核心工程原則，展現跨越不同技術領域仍能看出共通模式的融會貫通能力。理解這種相似性的核心在於認識到——不管是**任務分解**還是**微服務拆分**，本質上都是在回應同一個更根本的問題——**當一個需要被處理的整體（不管是一個複雜任務、還是一個龐大的軟體系統）變得過於龐大、複雜，超出單一個處理單元（不管是一次模型推理、還是一個單體式應用程式）所能妥善處理的複雜度上限時，應該如何因應**。兩者給出的答案是**相似的核心策略**——**拆解**，把這個龐大的整體拆分成多個各自職責更單一、範疇更明確、規模更容易被單獨妥善處理的獨立部分。這種拆解之所以有效，背後的道理是共通的——**一個職責單一、範疇明確的獨立單元，不管是一個子任務還是一個微服務，都遠比一個職責龐雜、包山包海的整體更容易被正確地設計、實作，以及驗證其正確性**；但兩者也同樣地都面臨**拆解之後隨之而來的新挑戰**——一旦把一個原本整體的東西拆解成多個獨立單元，就必然會引入**這些獨立單元彼此之間該如何協調、溝通，確保彼此的行為能夠正確地組合起來共同達成原本整體想要達成的目標**這個新問題——在微服務的情境裡，這具體展現為服務之間的 API 呼叫依賴、分散式交易的一致性協調，以及服務之間可能因為網路延遲或故障而產生的各種協調失敗風險；在 Agent 任務分解的情境裡，這具體展現為前面已經討論過的『子任務之間的先後依賴關係』，以及前一題剛討論過的『某個子任務執行失敗時，如何動態地重新協調、調整整體規劃』這類挑戰。這種**「拆解降低個別單元複雜度，但同時引入協調新挑戰」**的核心工程權衡，某種程度上是一個**超越任何特定技術領域、廣泛適用於各種『如何妥善處理一個過於龐大複雜的整體』這類問題**的普遍工程智慧，能夠識別出這種跨越不同具體技術領域（Agent 任務規劃、微服務架構、乃至於其他任何涉及『分而治之』這種策略的工程領域）依然共通適用的抽象原則，展現對工程問題背後更深層規律的掌握能力，而不是只孤立地理解每一個具體技術領域各自的知識點。理解「任務分解和微服務拆分，核心思路上確實存在相當程度的相似性，都是把一個原本龐大複雜、難以整體一次性妥善處理的東西，拆解成多個規模較小、職責較為單一明確的獨立單元，這種拆解之所以有效，是因為職責單一範疇明確的獨立單元遠比職責龐雜包山包海的整體更容易被正確設計實作驗證，但兩者也同樣面臨拆解之後隨之而來的新挑戰——這些獨立單元彼此之間該如何協調溝通確保正確組合共同達成原本整體目標，這種拆解降低個別複雜度但同時引入協調新挑戰的核心工程權衡，是一個超越任何特定技術領域、廣泛適用於分而治之這類策略的普遍工程智慧」，展現你具備跨越Agent架構和系統設計這兩個不同技術領域，依然能識別出共通抽象原則的融會貫通能力。

**面試回答方式**：先給出核心答案——「兩者在核心思路上確實存在相當程度的相似性，都是把一個原本龐大複雜、難以整體一次性妥善處理的東西，拆解成多個規模較小、職責較為單一明確的獨立單元」。解釋拆解為什麼有效這個共通道理——「一個職責單一、範疇明確的獨立單元，不管是一個子任務還是一個微服務，都遠比一個職責龐雜包山包海的整體，更容易被正確設計、實作、驗證」。指出兩者共同面臨的新挑戰——「拆解之後必然引入這些獨立單元彼此之間該如何協調溝通的新問題，在微服務情境裡具體展現為服務間API呼叫依賴、分散式交易一致性;在Agent任務分解情境裡具體展現為子任務間的先後依賴關係、以及某個子任務失敗時如何動態調整整體規劃」。總結為更普遍的工程智慧——「這種拆解降低個別複雜度但同時引入協調新挑戰的核心工程權衡，是一個超越任何特定技術領域、廣泛適用於分而治之這類策略的普遍工程智慧」。
