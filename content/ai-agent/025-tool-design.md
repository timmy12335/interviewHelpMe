# 題目

給 Agent 用的工具該怎麼設計？跟給人用的 API 有什麼不同？

## 核心答案

最大的差異是「模型只能靠名稱與描述理解這個工具」——沒有文件可以查、沒有同事可以問、也沒有型別系統會在編譯期報錯。所以描述的品質直接決定了工具能不能被正確使用。

**四個設計原則。**

**名稱與描述要自我說明**——`search_orders`（描述：依客戶 ID 或日期範圍查詢訂單，回傳最多 50 筆）遠好於 `query`（描述：查詢資料）。描述應該包含「什麼時候該用它」與「什麼時候不該用」。

參數要扁平且有明確的類型與約束——用 enum 限制取值、用 description 說明每個參數的含義與格式；深層巢狀的參數結構顯著降低成功率。

**回傳要簡潔且結構化**——**只給模型需要的資訊**；一個回傳幾千行 JSON 的工具會塞爆上下文並淹沒關鍵內容。

錯誤要能被模型理解並據以修正——「參數 date 格式錯誤，應為 YYYY-MM-DD，你提供的是 2024/1/5」遠好於「400 Bad Request」。

## 詳細解析

「錯誤訊息是給模型的提示」是這裡最重要的觀念轉變。傳統 API 的錯誤訊息是給開發者看的——而 Agent 的錯誤訊息會直接進入模型的上下文並影響它下一步的行動。所以錯誤訊息應該像一個好的同事在指導你：說明錯在哪、正確的形式是什麼、以及建議下一步做什麼。實測上，把錯誤訊息從狀態碼改成自然語言的指引，能顯著提升 Agent 的自我修正成功率——而這是所有改進中成本最低的一項。

「工具的數量與粒度」是一個真實的取捨。工具太多——模型難以選對，而且所有工具的描述都佔用上下文（幾十個工具的 schema 可能就是幾千個 token）。工具太少而粒度太粗——模型必須傳入複雜的參數，出錯機率上升。實務的經驗是「一次對話中暴露的工具控制在 20 個以內」，超過就用分層（先選類別再選具體工具）或動態載入（按當前任務只暴露相關的）。

「工具應該是冪等的或至少可安全重試的」：模型會重試——因為它看到錯誤就會再試一次。如果一個「建立訂單」的工具不冪等，模型的一次重試就變成兩張訂單。所以寫入類的工具應該接受一個冪等鍵，或者在服務端做去重。

「不要讓工具回傳需要模型計算的東西」：回傳原始的數字列表並期待模型加總——**它會算錯**。**應該直接回傳算好的結果**。這條原則與「不要讓模型做確定性的事」是同一個判斷，只是體現在工具的介面設計上。

## 面試回答方式

先給最大的差異——模型只能靠名稱與描述理解工具，沒有文件、沒有同事、也沒有型別系統會報錯。給四個設計原則（自我說明的名稱與描述、扁平且有約束的參數、簡潔結構化的回傳、可據以修正的錯誤）。加分點有四個：**錯誤訊息是給模型的提示**——它會進入上下文並影響下一步，應該像好同事在指導：錯在哪、正確形式是什麼、建議下一步做什麼，而這是所有改進中成本最低的一項；**工具的數量與粒度的取捨**——控制在 20 個以內，超過就分層或動態載入；**工具應該冪等或可安全重試**——模型看到錯誤就會再試，不冪等的建立訂單一次重試就是兩張單；以及不要讓工具回傳需要模型計算的東西。

## 講稿

最大的差異是模型只能靠名稱跟描述理解這個工具。沒有文件可以查、沒有同事可以問、也沒有型別系統會在編譯期報錯。所以描述的品質直接決定了工具能不能被正確使用。

我會遵守四個原則。名稱跟描述要自我說明，而且要包含什麼時候該用、什麼時候不該用。參數要扁平、有明確類型跟約束。回傳要簡潔，只給模型需要的資訊，因為一個回傳幾千行的工具會塞爆上下文。錯誤要能被模型理解並據以修正。

最後一點我想展開。錯誤訊息是給模型的提示，這是一個觀念轉變。傳統的錯誤訊息是給開發者看的，而這裡它會直接進入模型的上下文並影響下一步的行動。所以它應該像一個好同事在指導你，說明錯在哪、正確的形式是什麼、建議下一步做什麼。把狀態碼改成自然語言的指引，能顯著提升自我修正的成功率，而這是所有改進中成本最低的一項。

還有一點，寫入類的工具應該是冪等的。因為模型看到錯誤就會重試，如果建立訂單不冪等，一次重試就變成兩張單。

## 常見追問

### 工具描述該寫多詳細？

**核心答案**：詳細到「一個沒有背景知識的人讀完就知道什麼時候該用、怎麼用」，**但不要長到佔滿上下文**。實用的結構是：一句話說明功能、一句話說明適用時機、一句話說明限制或副作用。參數的 description 則要包含格式與範例值——「日期，格式 YYYY-MM-DD，例如 2024-01-15」比「日期」有效得多。

**詳細解析**：「說明什麼時候不該用」常被忽略卻很有價值：如果有兩個相似的工具（`search_orders` 與 `get_order_by_id`），在描述中明確寫「如果你已經知道訂單編號，請用 get_order_by_id 而不是這個」——**能大幅降低選錯的機率**。這相當於在工具層面做消歧義。另一個實用的技巧是「在描述中放一個典型的呼叫範例」——它比任何抽象說明都有效，理由與少樣本提示相同。而判斷描述夠不夠好的方法很簡單：把它拿給一個不熟悉這個系統的人看，問他知不知道什麼時候該用——人看不懂的，模型多半也用不對。

**面試回答方式**：給詳細程度的標準與實用的三句結構，並強調**參數描述要含格式與範例值**。核心加分點是「說明什麼時候不該用」常被忽略卻很有價值——兩個相似工具之間明確互相指引能大幅降低選錯機率，相當於在工具層面做消歧義。收在一個實用的檢驗：把描述拿給不熟悉這個系統的人看，人看不懂的模型多半也用不對。

### 工具太多導致選錯怎麼辦？

**核心答案**：**三個層次的處理**。**合併**——把相似的工具合併成一個帶 enum 參數的工具（例如把五個查詢工具合併成一個 `search` 帶 `type` 參數）。**分層**——先讓模型選擇一個工具類別，再在該類別內暴露具體工具。**動態載入**——根據當前任務或對話階段只暴露相關的工具（可以用一個檢索步驟從工具庫中挑出最相關的幾個）。

**詳細解析**：「合併與分層是相反方向的解法，適用場景不同」：合併適合「這幾個工具本質上是同一件事的變體」——合併之後模型只需要選對參數而非選對工具，而選參數比選工具容易。分層適合「工具數量大且類別清晰」——它把一次 20 選 1 變成兩次 5 選 1，而後者的準確率高得多。**代價是多一輪互動（延遲增加）**。動態載入最靈活但需要一個額外的檢索機制，而那個機制本身也可能選錯。判斷的順序應該是「先看能不能合併（最省事）、再看能不能分層、最後才做動態載入」——因為複雜度是遞增的，而收益未必。

**面試回答方式**：給三個層次的處理。核心加分點是說明合併與分層是相反方向的解法：合併適合「本質上是同一件事的變體」，因為選參數比選工具容易；分層適合「數量大且類別清晰」，把一次 20 選 1 變成兩次 5 選 1。收在判斷順序：先看能不能合併（最省事）、再分層、最後才動態載入——**因為複雜度遞增而收益未必**。

### 長時間運行的工具怎麼設計？

**核心答案**：**改成非同步的兩段式**：一個工具負責「提交任務並回傳一個任務 ID」，另一個負責「查詢任務狀態」。否則一個要跑十分鐘的工具會讓整個 Agent 迴圈卡住，而且很可能撞上超時。同時要在描述中明確告訴模型「這個操作需要時間，提交後請稍後查詢」——否則它會立刻查詢並得到「進行中」，然後陷入密集輪詢。

**詳細解析**：「防止密集輪詢」需要在工具層面而非提示層面解決：告訴模型「請等待 30 秒再查」是不可靠的——**它沒有真正的時間感**。可靠的做法是讓查詢工具在任務未完成時「阻塞一段時間再回傳」（**服務端的長輪詢**），或者在回傳中明確給出「建議在 N 秒後再查詢」並由框架層強制那個間隔。更好的設計是「讓 Agent 在等待期間可以去做別的事」——這需要 Agent 框架支援並行的任務追蹤，而不是嚴格的串行迴圈。能指出「這是框架能力的限制而非提示能解決的問題」，說明理解了 Agent 執行模型的層次。

**面試回答方式**：給非同步兩段式的設計並強調要在描述中說明需要等待。核心加分點是防止密集輪詢要在工具層面解決——告訴模型「等 30 秒」不可靠，因為它沒有真正的時間感，可靠的做法是服務端長輪詢或由框架強制間隔。收在更好的設計與判斷：讓 Agent 在等待期間去做別的事需要框架支援並行任務追蹤，而這是框架能力的限制，不是提示能解決的問題。
