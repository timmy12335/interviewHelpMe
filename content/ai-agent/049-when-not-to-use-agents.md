# 題目

什麼情況下應該用固定的工作流而不是 Agent？

## 核心答案

**判準是「路徑是否已知」**。**如果你能事先畫出流程圖——那就寫成工作流**：**確定、可測試、便宜、快、可審計**。**Agent 的價值在於「路徑事先不確定，需要根據中間結果決定下一步」**——**而如果路徑其實是確定的，那個自由度只是引入了不確定性而沒有帶來任何好處**。

**四類明確不該用 Agent 的情況**。**流程固定**——**每次都是同樣的五個步驟**。**對確定性有要求**——**財務、合規、或任何需要「每次都一樣」的場景**。**延遲敏感**——**Agent 的多輪推理天然慢**。**以及成本敏感且量大**——**一個工作流的成本可能是 Agent 的百分之一**。

**而最常見的過度設計是「用 Agent 做一件本來可以用一次 LLM 呼叫加幾行程式碼完成的事」**——**多輪的迴圈、工具的選擇、狀態的管理，全都是為一個不存在的問題付出的複雜度。**

## 詳細解析

**「一次 LLM 呼叫 + 程式碼」能解決的問題比多數人以為的多**：抽取結構化資料、分類、摘要、改寫、回答一個有明確上下文的問題——**這些都不需要 Agent**。**判斷的方法很簡單：問「這個任務需要模型自己決定下一步做什麼嗎」**——**不需要的話，那就是一個提示工程問題而非 Agent 問題**。**而把它做成 Agent 的代價是：更慢、更貴、更難測試、行為更不可預測**——**沒有任何一項是好處**。

**「工作流中嵌入 LLM 節點」是最被低估的中間形態**：整體流程是確定的（工作流引擎控制），**而其中某幾步需要理解非結構化的內容（用一次 LLM 呼叫）**——**這既獲得了模型的能力，又保住了流程的確定性與可審計性**。**多數「用 Agent 自動化業務流程」的需求，實際上這個形態就足夠了**，**而它的可靠性與成本都好得多**。

**「Agent 的價值需要真實的分支才顯現」**：如果流程中有「根據查詢結果決定要不要進一步查詢」「根據錯誤類型決定怎麼處理」這類真實的、難以窮舉的分支——**那 Agent 的自由度才有意義**。**而如果分支只有三種且都能列舉，寫成 if-else 更好。**

**「從工作流開始，遇到瓶頸再考慮 Agent」是務實的順序**：**先用確定的流程覆蓋能覆蓋的部分**，**觀察哪些情況處理不了**——**如果那些例外足夠多且模式難以窮舉，才引入 Agent 處理它們**。**這比一開始就做一個 Agent 然後發現八成的情況其實都很固定要好得多。**

## 面試回答方式

先給判準——**路徑是否已知**，並指出**路徑確定時 Agent 的自由度只是引入不確定性而沒有好處**。給四類不該用的情況。加分點有四個：**「一次 LLM 呼叫加程式碼」能解決的問題比多數人以為的多**——**判斷方法是問「需要模型自己決定下一步嗎」**，**不需要的話那是提示工程問題而非 Agent 問題**，**而做成 Agent 的代價沒有一項是好處**；**工作流中嵌入 LLM 節點是最被低估的中間形態**——**多數業務流程自動化的需求這個形態就足夠，可靠性與成本都好得多**；**Agent 的價值需要真實的分支才顯現**——**分支只有三種且能列舉的話 if-else 更好**；以及**從工作流開始、遇到瓶頸再考慮 Agent** 這個務實的順序。

## 講稿

判準是路徑是否已知。如果你能事先畫出流程圖，那就寫成工作流，確定、可測試、便宜、快、可審計。代理的價值在於路徑事先不確定，需要根據中間結果決定下一步。如果路徑其實是確定的，那個自由度只是引入了不確定性而沒有帶來任何好處。

最常見的過度設計，是用代理做一件本來可以用一次模型呼叫加幾行程式碼完成的事。抽取結構化資料、分類、摘要、回答一個有明確上下文的問題，這些都不需要代理。判斷的方法很簡單，問這個任務需要模型自己決定下一步做什麼嗎。不需要的話那就是一個提示工程問題。

還有一個最被低估的中間形態，工作流中嵌入模型節點。整體流程由工作流引擎控制是確定的，而其中某幾步用一次模型呼叫理解非結構化的內容。這既獲得了模型的能力，又保住了流程的確定性與可審計性。多數用代理自動化業務流程的需求，實際上這個形態就足夠了。

所以我的順序是先用確定的流程覆蓋能覆蓋的部分，觀察哪些情況處理不了，如果那些例外足夠多而且模式難以窮舉，才引入代理。

## 常見追問

### 怎麼判斷「例外足夠多」到需要 Agent？

**核心答案**：**用資料而非感覺**。統計「工作流無法處理而落到人工的比例」與**「那些例外的模式有多分散」**——**如果 20% 落到人工，而且那 20% 分成幾十種不同的情況（每種都不夠多到值得寫一條規則）**，**那就是 Agent 的適用場景**。**反之，如果例外集中在三五種模式，加三五條規則就解決了。**

**詳細解析**：**「長尾的形狀決定了架構」是這個判斷的核心**：如果例外的分布是陡峭的（少數幾類佔大部分）——**規則能高效地覆蓋**；**而如果是平坦的長尾（幾十類各佔一點）**——**寫規則的邊際收益快速遞減，而 Agent 的泛化能力才有價值**。**所以這個決定應該建立在對真實資料的分析上，而不是「我們覺得情況很複雜」**。**而實務上有一個好的過渡策略：「規則優先、Agent 兜底」**——**能被規則處理的走規則（快、便宜、確定），落到長尾的才交給 Agent**。**這個組合往往比純規則或純 Agent 都好**，**因為它讓每一種機制處理它擅長的部分**。

**面試回答方式**：主張**用資料而非感覺**並給具體的統計（落到人工的比例、例外模式的分散程度）。核心加分點是**長尾的形狀決定了架構**——**陡峭的分布規則能高效覆蓋，平坦的長尾才需要 Agent 的泛化能力**，**所以決定應該建立在真實資料分析上而非「我們覺得情況很複雜」**。收在過渡策略：**規則優先、Agent 兜底**——**能被規則處理的走規則（快、便宜、確定），落到長尾的交給 Agent**，**讓每種機制處理它擅長的部分**。

### 已經做成 Agent 了，怎麼判斷該不該簡化成工作流？

**核心答案**：**看實際的執行軌跡**。**如果 80% 的請求走的是同一條路徑**——**那條路徑應該被固化成工作流**，**只有偏離它的才進入 Agent 模式**。**這既保住了處理長尾的能力，又讓多數請求變快變便宜。**

**詳細解析**：**「從軌跡中挖掘固定路徑」是一個資料驅動的優化，而它的資料你已經有了**：追蹤記錄裡有每一次執行的完整工具序列——**統計最常見的序列，就能發現哪些是可以固化的**。**這往往會有意外的發現：一個「智能」的 Agent 實際上八成時間都在做同樣的三步**。**固化之後的收益是全面的**：**延遲從幾秒降到幾百毫秒、成本降低一個數量級、行為變得可預測、而且更容易測試**。**而長尾仍然由 Agent 處理，能力沒有損失**。**這個「用 Agent 探索、用工作流固化」的循環，是一個很好的漸進式架構演進模式**——**它讓你不必在一開始就決定用哪一種**。

**面試回答方式**：給做法（**看實際軌跡，80% 走同一條路徑的話固化成工作流，偏離的才進 Agent 模式**）。核心加分點是**從軌跡中挖掘固定路徑是資料驅動的優化而資料你已經有了**——**追蹤裡有完整的工具序列，統計最常見的就知道哪些可以固化**，**而這往往有意外發現：一個「智能」的 Agent 八成時間都在做同樣的三步**。收在收益與模式：**延遲降一個數量級、成本降一個數量級、行為可預測**，**而「用 Agent 探索、用工作流固化」是很好的漸進式演進模式**。

### 那 Agent 到底適合什麼？

**核心答案**：**三類**。**探索性的任務**——**需要根據中間發現調整方向**（除錯、調查、研究）。**長尾的處理**——**情況太多樣，無法窮舉成規則**。**以及需要組合多種能力的任務**——**要查資料、要計算、要寫文件、要驗證，而組合方式因情況而異**。

**詳細解析**：**這三類的共同特徵是「事先無法完整規劃」**——**而那正是 Agent 相對於工作流的唯一結構性優勢**。**如果一個需求不具備這個特徵，那用 Agent 就是用一個更貴、更慢、更不確定的方式做一件能被確定地做好的事**。**而值得補充的是：Agent 的適用範圍會隨模型能力提升而擴大**——**今天需要人介入的判斷，未來可能可以交給模型**；**但「路徑是否已知」這個判準本身不會變**：**已知的路徑永遠應該用確定的方式執行，因為那在任何模型能力下都更可靠也更便宜**。**這個判準的穩定性，正是它值得被記住的原因。**

**面試回答方式**：給三類適用場景並指出**共同特徵是事先無法完整規劃，而那是 Agent 相對於工作流的唯一結構性優勢**。核心加分點是收在判準的穩定性：**Agent 的適用範圍會隨模型能力提升而擴大，但「路徑是否已知」這個判準本身不會變**——**已知的路徑永遠應該用確定的方式執行，因為那在任何模型能力下都更可靠也更便宜**。
