# 題目

回顧整個 Agent 的技術棧，你認為一個可靠的 Agent 系統，可靠性主要來自哪裡？

## 核心答案

**不是來自模型，而是來自模型周圍的結構。**

**三個來源，按貢獻排序。**

**約束**——**能做什麼、不能做什麼由程式碼與權限決定，而不是由提示請求**。**工具的冪等、權限的檢查、預算的上限、危險操作的確認**——**這些在任何模型行為下都成立**。

**驗證**——**每一步的結果被外部檢查而非由模型自我宣告**。**跑測試、檢查格式、確認資料存在、比對出處**——**這把「模型說它做到了」變成「系統確認它做到了」**。

**可觀測與可介入**——**完整的追蹤讓問題能被診斷，而人能在任何時候看見、停止、修正**。

**而模型的能力決定的是「上限」，這三者決定的是「下限」**——**而生產系統的價值主要由下限決定，因為使用者記住的是最糟的那次。**

## 詳細解析

**「用結構取代信任」是這整個類別最核心的一條**。每一次你想寫「請不要做 X」的時候——**都應該問「我能不能讓它做不到 X」**。**前者是一個可以被說服推翻的請求，後者是一個保證**。**這條原則適用於權限、預算、危險操作、資料流、以及重複執行**——**而每一次把「請求」變成「保證」，系統的下限就提高一次**。

**「錯誤不會消失，但可以被限制與發現」是務實的心態**：模型會出錯——**這不是一個能被消除的性質**。**所以設計的目標不是「讓它永遠不錯」，而是「錯了的時候損害有限、而且能被快速發現與修正」**。**這與分散式系統的可靠性思維完全一致**：**不是假設元件不會失敗，而是假設它們會失敗並設計相應的應對。**

**「Agent 是把 LLM 接到真實世界的接線」**：而接線的品質——**工具的設計、錯誤的表達、上下文的管理、狀態的維護**——**決定了同一個模型能發揮多少能力**。**實務上，同樣的模型在好的接線與差的接線下，成功率可能差一倍以上**——**這是一個經常被低估的槓桿，因為它不像「換一個更強的模型」那樣顯眼**。

**而最後的判斷是「先做小而可靠的，再擴大範圍」**：一個能可靠處理三類任務的 Agent，**比一個能處理二十類但每類都不穩的有價值得多**。**因為前者可以被信任並被納入真實的流程，而後者只能停留在展示**。**這個「深度優於廣度」的順序，在 Agent 這個容易被能力展示誘惑的領域裡尤其重要。**

## 面試回答方式

先給核心立場——**可靠性不是來自模型，而是來自模型周圍的結構**，並給三個來源（約束、驗證、可觀測與可介入），收在**模型決定上限、這三者決定下限，而生產系統的價值主要由下限決定，因為使用者記住的是最糟的那次**。加分點有四個：**用結構取代信任**——**每次想寫「請不要做 X」時都應該問「我能不能讓它做不到 X」**，**前者是可被說服推翻的請求，後者是保證**；**錯誤不會消失但可以被限制與發現**——**目標不是「永遠不錯」而是「錯了損害有限且能快速發現」**，**與分散式系統的可靠性思維一致**；**Agent 是把 LLM 接到真實世界的接線**——**同樣的模型在好壞接線下成功率可能差一倍以上，而這是被低估的槓桿**；以及**先做小而可靠的再擴大範圍**。

## 講稿

我認為可靠性不是來自模型，而是來自模型周圍的結構。

有三個來源。第一是約束，能做什麼、不能做什麼由程式碼跟權限決定，而不是由提示請求。工具的冪等、權限的檢查、預算的上限，這些在任何模型行為下都成立。第二是驗證，每一步的結果被外部檢查而不是由模型自我宣告。第三是可觀測與可介入。

模型的能力決定的是上限，這三者決定的是下限。而生產系統的價值主要由下限決定，因為使用者記住的是最糟的那次。

我覺得最核心的一條原則是用結構取代信任。每一次你想寫請不要做某件事的時候，都應該問我能不能讓它做不到。前者是一個可以被說服推翻的請求，後者是一個保證。每一次把請求變成保證，系統的下限就提高一次。

還有一個心態上的調整。錯誤不會消失，這不是能被消除的性質。所以設計的目標不是讓它永遠不錯，而是錯了的時候損害有限、能被快速發現與修正。這跟分散式系統的可靠性思維完全一致，不是假設元件不會失敗，而是假設它們會失敗並設計應對。

## 常見追問

### 一個新的 Agent 專案該從哪裡開始？

**核心答案**：**從一個窄而明確的任務加上評估集開始**。**選一個「你能清楚說出什麼算成功」的任務**——**然後在寫任何提示之前，先建立二三十個評估案例**。**有了它，後續的每一次改動都有量化的回饋**；**沒有它，整個開發過程都是憑感覺**。

**詳細解析**：**「先建評估集」這個順序違反直覺卻極其重要**：多數團隊先寫提示、看起來能跑、然後開始調——**而每次調完只能靠試幾個例子判斷有沒有變好**，**於是很快陷入「改了 A 好了、改了 B 又壞了 A」的循環**。**而有評估集的團隊在幾分鐘內就知道每次改動的淨效果**。**這個差異在專案的第二週就會顯現，並且隨時間拉大**。**至於任務的選擇：應該選「有明確成功標準、有真實需求、且範圍夠窄」的**——**窄的好處是能真正做到可靠，而一個可靠的小範圍比一個不可靠的大範圍更容易獲得信任與擴展的機會**。

**面試回答方式**：給起點（**窄而明確的任務加評估集，在寫提示之前就建立**）。核心加分點是說明**先建評估集這個順序違反直覺卻極其重要**——**多數團隊先寫提示然後靠試幾個例子判斷，於是陷入「改了 A 好了、改了 B 又壞了 A」的循環**，**而有評估集的團隊幾分鐘內就知道淨效果**，**這個差異在第二週就顯現並隨時間拉大**。收在任務選擇：**窄的好處是能真正做到可靠，而可靠的小範圍比不可靠的大範圍更容易獲得信任與擴展的機會**。

### 這個領域變化很快，哪些知識比較保值？

**核心答案**：**那些不依賴特定框架與模型的部分**。**具體的框架 API 會過時**、**模型的能力邊界會移動**——**而「如何設計工具的介面」「如何在不可靠的元件周圍建立可靠的系統」「如何量測與評估」這些不會**。**因為它們本質上是工程問題，而不是關於某個模型的知識。**

**詳細解析**：**「Agent 工程與分散式系統工程高度同構」是一個有價值的觀察**：不可靠的元件、部分失敗、冪等、重試、逾時、可觀測性、狀態管理——**這些概念在兩個領域裡幾乎一一對應**。**所以有分散式系統經驗的工程師學 Agent 會很快**，**而 Agent 遇到的很多問題在分散式系統裡已經有成熟的答案**。**這個對應關係本身就是最保值的知識**——**它讓你在遇到新問題時知道該去哪裡找參考**。**而反過來，只熟悉某個 Agent 框架的用法，在框架更迭時價值會迅速歸零**。**所以學習的重心應該放在「為什麼這樣設計」而非「這個框架怎麼用」。**

**面試回答方式**：給區分（**框架 API 與模型能力邊界會變，而工程問題的答案不會**）。核心加分點是**Agent 工程與分散式系統工程高度同構**——**不可靠元件、部分失敗、冪等、重試、逾時、可觀測性幾乎一一對應**，**所以有分散式經驗的人學得快，而很多問題在分散式系統裡已有成熟答案**。收在：**這個對應關係本身就是最保值的知識，它讓你遇到新問題時知道該去哪裡找參考**，**而只熟悉某個框架的用法在更迭時價值迅速歸零**。

### 面試時怎麼展現 Agent 方面的判斷力？

**核心答案**：**談失敗模式與取捨，而不是談你用過哪些框架**。**「我做過一個 Agent，用了某某框架」是描述**；**「我做過一個 Agent，最大的問題是工具選擇的準確率，我用了三個方法改善，最後發現關鍵是錯誤訊息的寫法」是判斷**。**面試官在意的是後者，因為它證明你理解為什麼。**

**詳細解析**：**「能說出自己方案的弱點」是最有說服力的信號之一**：Agent 系統一定有做不好的地方——**而主動說出「這個設計在 X 情況下會失敗，我接受它是因為 Y」，展示的是清醒的自我評估**。**相反地，把一個 Agent 專案描述成完全順利，通常意味著沒有做到足夠深**。**另一個有效的展現方式是「用具體的數字」**：**成功率從多少提升到多少、成本降低了多少、平均步數從幾步減到幾步**——**因為那證明你建立了量測，而建立量測本身就是這個領域最重要的工程實踐**。**而如果沒有實際專案經驗，談「你會怎麼設計並如何驗證」也同樣有效**——**因為考的是思路而非履歷**。

**面試回答方式**：給核心對比（**描述 vs 判斷**）並用具體的句式示範。核心加分點是**能說出自己方案的弱點是最有說服力的信號之一**——**主動說「這個設計在某情況下會失敗，我接受它是因為某某」展示清醒的自我評估**，**而把專案描述成完全順利通常意味著沒有做到足夠深**。收在兩個補充：**用具體的數字（成功率、成本、步數）因為那證明你建立了量測，而量測本身是這個領域最重要的工程實踐**；**沒有實際經驗時談「你會怎麼設計並如何驗證」同樣有效，因為考的是思路而非履歷**。
