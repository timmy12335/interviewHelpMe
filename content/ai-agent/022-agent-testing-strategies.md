# 題目

在實際開發、上線一個 Agent 系統之前，除了前面（見 [[013-agent-evaluation.md]]）深入討論過的評估方法論以外，實務上還有哪些常見的**測試策略**，能**在正式上線之前**就充分驗證這個 Agent 系統的品質和可靠性？

## 核心答案

除了前面（見 [[013-agent-evaluation.md]]）已經深入討論過的**評估方法論**（關注**衡量已經存在的一個 Agent 系統它的表現好不好**）以外，實務上還需要額外地運用一套**更加聚焦在『在正式上線之前，就主動地找出、暴露潛在問題』**的**測試策略**，常見的做法包括——**(1) 模擬環境測試（Simulation Testing）**：在一個**受控、隔離**的模擬環境裡（而不是直接在真實的生產環境），運用**模擬的外部工具或資料來源（而非真實的外部系統）**去測試 Agent 在各種不同的模擬情境下的表現（這正是前面（見 [[013-agent-evaluation.md]] 的常見追問）已經深入討論過的『先在模擬環境裡驗證，再逐步擴大到真實環境』這個核心思路的具體實踐）；**(2) 對抗性測試（Adversarial Testing）**：**刻意地設計出一些帶有惡意企圖、或者故意製造出異常、邊界狀況**的測試情境（例如故意嘗試前面（見 [[../ai-llm/023-prompt-injection.md]]）已經深入討論過的 Prompt Injection 攻擊手法），去主動地驗證這個 Agent 系統是否具備**足夠的韌性和安全性**；**(3) 回歸測試（Regression Testing）**：每當這個 Agent 系統經過**任何修改、調整**（不管是調整系統提示、更換底層模型、或是調整工作流程的具體編排邏輯）之後，都**重新執行一套已經累積下來的標準測試案例集**，去確保**這次的修改****沒有意外地破壞掉原本已經正常運作的既有功能**。

## 詳細解析

**模擬環境測試——用可控、可重複的模擬環境取代真實、充滿不確定性的生產環境**：這是 Agent 測試策略裡**最基礎、也最重要**的一環——核心思路是**在一個完全受控、和真實生產環境隔離**的模擬環境裡去執行測試——這種模擬環境通常會提供**模擬版本的外部工具或資料來源**（例如一個**假的、模擬的**天氣查詢 API，而不是真正去呼叫一個真實的第三方天氣服務）。這種**模擬環境測試**之所以重要，核心的優勢在於**「可控性」**和**「可重複性」**——因為這個模擬環境裡**外部工具的行為是完全由測試設計者自己掌控**的，可以**刻意地去設計各種不同的、事先精確可控的測試情境**（例如刻意讓這個模擬的外部工具回傳一個**特定的、經過精心設計的異常結果**，來測試 Agent 是否能夠妥善地因應這種特定的異常情況）——這種**「精確控制、可以反覆重現相同的測試情境」**的能力，是**直接在真實生產環境**進行測試**很難做到**的（真實生產環境裡外部系統的實際行為通常**不受測試者直接控制**，難以精確地重現某個**特定、想要測試的異常情況**）。

**對抗性測試——主動地扮演攻擊者的角色，去找出系統的潛在弱點**：這直接呼應了前面（見 [[../ai-llm/023-prompt-injection.md]]、[[010-sandbox-code-execution-security.md]]、[[020-guardrails.md]]）已經深入討論過的各種安全性議題——與其**被動地等待**一個**真正的惡意攻擊者**去**發現、利用**這個系統可能存在的安全漏洞，更加**積極、主動**的做法是**在這個系統正式上線之前**就**主動地扮演一個『假想的攻擊者』**這個角色，去**刻意地設計、嘗試**各種**已知、或者可能想像得到的攻擊手法**（例如各種不同型態的 Prompt Injection 嘗試、故意試圖誘導 Agent 去執行某些明顯不恰當的高風險操作），去**主動地驗證**這個 Agent 系統現有的各種防範機制（如護欄、Human-in-the-Loop、沙箱）是否**真的具備足夠的實際防護效果**——這種**「在正式面對真正的攻擊者之前，先自己扮演攻擊者的角色，去主動地找出、修補潛在的弱點」**的做法，某種程度上也呼應了一個在**傳統資安領域**裡早已相當成熟且被廣泛採用的核心實務——**「滲透測試（Penetration Testing）」**——把這個在傳統資安領域已經深入發展的成熟實務**遷移應用到 Agent 系統**這個新的具體應用場景上。

**回歸測試——確保持續的修改和優化不會意外地破壞掉既有的正常功能**：這是一個在**傳統軟體工程**裡早已相當普及、被廣泛採用的核心測試策略，**同樣適用於** Agent 系統的持續開發、維護——回顧一個在**軟體工程領域**相當普遍的現象——**「修復或優化某一個具體的問題，卻意外地在不知不覺中引入了一個全新的、原本沒有的問題（某種程度上是一種『拆東牆補西牆』的現象）」**——這種現象某種程度上**在 Agent 系統裡**可能會變得**更加容易發生**，因為前面（見 [[001-agent-fundamentals.md]]）已經深入討論過的 Agent 核心特徵——**Agent 的行為模式很大程度上取決於它被賦予的系統提示和工作流程設計**——這些**系統提示或工作流程設計上的任何微小調整**都可能**以某種不容易被事先完全預料到的方式**影響到這個 Agent 在**各種不同情境下的具體行為**。因此**每一次**在對這個系統做出**任何調整**之後，都**重新執行一套已經累積下來的完整標準測試案例集**去**系統性地驗證**這次的調整**是否意外地破壞掉原本已經正常運作**的其他功能，是**確保一個 Agent 系統在持續迭代優化的過程中依然維持整體品質和穩定性**的必要保障機制。

## 面試回答方式

先給出三種常見測試策略的框架——「除了之前討論過的評估方法論關注衡量已存在系統的表現好壞以外，實務上還需要一套更聚焦在主動找出暴露潛在問題的測試策略，包括模擬環境測試(在受控隔離的模擬環境裡運用模擬的外部工具去測試各種不同情境)、對抗性測試(刻意設計帶有惡意企圖或異常邊界狀況的測試情境，主動驗證系統的韌性和安全性)、以及回歸測試(每當系統經過任何修改後，重新執行標準測試案例集，確保沒有意外破壞既有功能)」。詳細說明模擬環境測試的核心優勢——「核心優勢在於可控性和可重複性，因為模擬環境裡外部工具的行為完全由測試設計者掌控，可以刻意設計各種事先精確可控的測試情境，這種精確控制、可以反覆重現相同測試情境的能力，是直接在真實生產環境測試很難做到的」。可以連結到傳統資安實務解釋對抗性測試——「這呼應了之前討論過的各種安全性議題，與其被動等待真正惡意攻擊者發現利用漏洞，更積極的做法是在系統上線前主動扮演假想攻擊者角色，去驗證現有防範機制是否真的具備足夠實際防護效果，這某種程度上呼應了傳統資安領域早已成熟的滲透測試這個核心實務」。可以補充回歸測試對Agent系統的特殊重要性——「Agent的行為模式很大程度上取決於系統提示和工作流程設計，這些設計上的任何微小調整都可能以不容易被事先完全預料到的方式影響各種不同情境下的具體行為，因此每次調整後都重新執行完整標準測試案例集，是確保系統持續迭代優化過程中依然維持整體品質穩定性的必要保障」，展現你對Agent測試策略的多個核心面向，有系統且具體的理解。

## 常見追問

### 如果模擬環境測試表現得非常好，是不是就代表這個 Agent 系統已經充分準備好可以正式上線運用？這和前面已經深入討論過的測試與真實部署表現落差有什麼關聯？

**核心答案**：**不一定，模擬環境測試表現良好並不足以保證充分準備好可以正式上線**——這直接呼應了前面（見 [[013-agent-evaluation.md]] 的常見追問）已經深入討論過的核心洞察——**「測試環境和真實環境之間可能存在分佈落差」**——**模擬環境**終究是**由人類測試設計者依照自己對真實世界情況的理解和想像所刻意建構出來**的一個**簡化、且可能不夠完整全面**的『近似版本』，這個模擬環境**再怎麼精心設計**都**難以百分之百完美地複製**真實世界裡**所有可能發生的複雜細節和邊界情況**（尤其是那些**測試設計者自己一開始根本沒有想到、或者低估其重要性**的意外情況）。因此**模擬環境測試表現良好**只能說明**這個 Agent 系統針對『測試設計者已經想到、且納入模擬環境裡』的這些情境表現良好**，但**沒有辦法**保證這個系統在**真實世界實際上會遭遇到的所有情境**（包括那些**測試設計者並沒有預先想到**的情境）下都**同樣能維持良好表現**。

**詳細解析**：這題要求直接把前面（見 [[013-agent-evaluation.md]] 的常見追問）已經深入建立的核心洞察——**「測試環境和真實環境之間存在分佈落差」**——**再一次**具體地套用到這裡討論的**模擬環境測試**這個具體的測試策略上，考察是否能夠**避免**把**「已經通過模擬環境測試」**這件事情**過度樂觀地等同於「已經充分準備好可以正式上線」**這種**過度自信的錯誤推論**。理解這個問題的核心在於重新確認——**任何一個由人類刻意設計、建構出來的『模擬』環境****本質上**都**受限於這個設計者自己本身對真實世界情況的認知和想像力**——一個**再怎麼經驗豐富、思慮周全**的測試設計者都**不太可能窮盡地事先完整地預見到**真實世界裡未來實際上會發生的每一種可能情況（尤其是那些**非常罕見、或者性質相當獨特、不容易被一般人事先聯想到**的邊界情況、或者**未來才會出現的全新型態問題**）。這種**「模擬環境終究只是一個受限於設計者自身認知的簡化近似版本，而不是真實世界本身」**的認知帶來一個相當重要的實務啟示——**「模擬環境測試表現良好」**應該被理解成**「這個系統通過了我們目前已經能夠想到、且認為重要的這些測試」**，而**不應該**被過度誇大地解讀成**「這個系統已經被證明在任何情況下都絕對可靠、萬無一失」**。因應這種模擬環境終究存在的局限性，實務上一個**更加審慎、負責任**的上線策略通常是**多層次、漸進式**的——即使**已經通過充分的模擬環境測試**，依然建議**先透過前面（見 [[013-agent-evaluation.md]] 的常見追問）已經深入討論過的『先導測試（Pilot）』階段**——讓這個系統**先在一小部分真實（但風險相對可控）的實際場景**下運作，**進一步驗證**它**在真實世界裡是否真的能維持和模擬測試相近的表現**，才**逐步擴大**正式全面上線的規模。這種**「模擬測試只是第一道把關，而非最終、唯一的把關」**的認知，正是避免**過度信賴單一種測試方式**所需要具備的審慎態度。理解「不一定，模擬環境測試表現良好並不足以保證充分準備好可以正式上線，這直接呼應了之前討論過的測試環境和真實環境之間可能存在分佈落差這個核心洞察，模擬環境終究是由人類測試設計者依照自己對真實世界情況的理解和想像所刻意建構出來的一個簡化、且可能不夠完整全面的近似版本，再怎麼精心設計都難以百分之百完美複製真實世界裡所有可能發生的複雜細節和邊界情況，尤其是那些測試設計者自己一開始根本沒想到或低估重要性的意外情況，因此模擬環境測試表現良好只能說明系統針對測試設計者已經想到且納入模擬環境裡的這些情境表現良好，沒辦法保證在真實世界實際上會遭遇到的所有情境下都同樣能維持良好表現，因應這種局限性，一個更審慎的上線策略通常是多層次漸進式的，即使已通過充分模擬環境測試，依然建議先透過先導測試階段讓系統先在一小部分真實但風險可控的實際場景下運作，進一步驗證真實世界表現，才逐步擴大正式上線規模」，展現你能把之前已建立的測試與真實表現分佈落差這個核心洞察，再次正確應用到模擬環境測試這個具體場景，並給出多層次漸進式的審慎上線策略建議。

**面試回答方式**：先明確給出核心答案——「不一定，模擬環境測試表現良好並不足以保證充分準備好可以正式上線，這直接呼應了之前討論過的測試環境和真實環境之間可能存在分佈落差這個核心洞察」。解釋為什麼模擬環境有其局限——「模擬環境終究是由人類測試設計者依照自己對真實世界情況的理解和想像所建構出來的簡化近似版本，再怎麼精心設計都難以百分之百完美複製真實世界所有可能發生的複雜細節和邊界情況，尤其是測試設計者自己一開始根本沒想到的意外情況」。給出正確的解讀方式——「模擬環境測試表現良好應該被理解成這個系統通過了我們目前已經能想到且認為重要的這些測試，而不應該被過度誇大解讀成系統已被證明在任何情況下都絕對可靠」。給出更審慎的上線策略——「一個更審慎的做法通常是多層次漸進式的，即使已通過充分模擬測試，依然建議先透過先導測試階段，讓系統先在一小部分真實但風險可控的場景下運作，進一步驗證真實世界表現，才逐步擴大正式上線規模」。

### 如果對抗性測試已經涵蓋了目前已知的所有攻擊手法，是不是就代表這個 Agent 系統對未來可能出現的全新攻擊手法也具備足夠的防護能力？

**核心答案**：**不一定能這樣保證**——**對抗性測試**本質上是**針對測試設計者目前已經知道、能夠想到的攻擊手法**去做驗證，這種測試方式**天生就只能涵蓋『已知』的攻擊手法**，而**沒有辦法保證**這個系統對**『未來才會被發明出來的、全新、事先完全無法預料的攻擊手法』**也**同樣具備足夠的防護能力**——這直接呼應了前面（見 [[../ai-llm/023-prompt-injection.md]]）已經深入討論過的核心告誡——**「Prompt Injection 這類攻擊之所以特別難以被徹底根除，關鍵原因在於攻擊者總是能夠不斷地設計出新的、事先沒有被預料到的攻擊手法」**。因此即使一個系統通過了**目前涵蓋所有已知攻擊手法**的對抗性測試，這**只能代表**這個系統**對目前已知的威脅**具備一定的防護能力，**不能過度樂觀地推論**它對**未來可能出現的全新威脅**也同樣安全。

**詳細解析**：這題要求把前面（見 [[../ai-llm/023-prompt-injection.md]]）已經深入討論過的核心告誡——**「攻擊者總是能夠不斷設計出新的、事先無法被窮舉預料的攻擊手法」**——具體地應用到對**對抗性測試這種測試策略本身的效力界限**做**誠實、精確的評估**上，考察是否能夠避免把**「通過了對抗性測試」****過度誇大地解讀成「這個系統已經對所有可能的攻擊都是絕對安全的」**這種**過度自信**的推論。理解這個問題的核心在於回顧——**任何一種『測試已知情況以驗證安全性』**的方法論**本質上**都**共享著**一個**相同的固有結構性限制**——**它只能測試那些測試者自己已經能夠想到、預先定義好的具體情況**，而**對於**那些**真正全新、事先測試者完全無法預先想像到**的情況，這種**「只測試已知情況」**的方法論**天生就無能為力**——這某種程度上也呼應了前面（見 [[020-guardrails.md]] 的常見追問）已經深入討論過的核心洞察——**「輸入護欄這種依靠事先窮舉已知模式的防禦方式，天生就難以做到完全窮盡，因為攻擊者總是能夠不斷設計出新的攻擊手法」**。**對抗性測試**這種測試方法論某種程度上**繼承了完全相同的固有限制**——它能夠**有效地驗證**這個系統**對目前已知的攻擊手法**是否具備足夠的防護能力，但**沒有辦法替代**一種**能夠真正完全窮盡、預先涵蓋所有未來可能出現的全新威脅**的絕對保證。因應這種**測試方法論本身固有的局限性**，一個**真正成熟、審慎**的 Agent 安全策略**不應該**把**「已經通過了對抗性測試」**當成**一個可以就此高枕無憂、不需要再額外持續關注**的終點，而應該**把安全防護視為一個需要持續、動態進行的過程**——**持續地關注業界最新出現的攻擊手法和資安研究進展、定期地重新設計、擴充對抗性測試的涵蓋範圍（把新發現的攻擊手法也納入進來）**，以及**額外地**搭配前面（見 [[020-guardrails.md]] 的常見追問）已經討論過的**輸出護欄**這種**更加聚焦在『不管問題是怎麼發生的，只聚焦在最終結果是否恰當』的更加根本、更具韌性**的防護思路作為**額外的補充防線**——這種**「持續、動態更新測試涵蓋範圍，同時額外搭配更根本、不依賴窮舉已知攻擊手法的防護機制」**的組合策略，正是因應**「無法窮盡預測所有未來可能攻擊手法」**這個根本性限制的更加務實、負責任的做法。理解「不一定能這樣保證，對抗性測試本質上是針對測試設計者目前已經知道能想到的攻擊手法去做驗證，天生只能涵蓋已知的攻擊手法，沒辦法保證對未來才會被發明出來的全新事先完全無法預料的攻擊手法也同樣具備足夠防護能力，這直接呼應了之前討論過的攻擊者總是能夠不斷設計出新的事先沒被預料到攻擊手法這個核心告誡，任何一種測試已知情況以驗證安全性的方法論本質上都共享著相同的固有結構性限制，這也呼應了輸入護欄這種依靠事先窮舉已知模式的防禦方式天生難以做到完全窮盡這個核心洞察，因應這種測試方法論本身固有的局限性，一個真正成熟的Agent安全策略不應該把已經通過對抗性測試當成可以高枕無憂的終點，而應該把安全防護視為一個需要持續動態的過程，包括持續關注業界最新攻擊手法、定期重新設計擴充測試涵蓋範圍、以及額外搭配輸出護欄這種更根本不依賴窮舉已知攻擊手法的防護機制作為補充防線」，展現你能把之前建立的核心告誡，一致且精確地應用到對抗性測試這個具體測試策略的效力界限評估上，並給出更務實的組合策略。

**面試回答方式**：先明確給出核心答案——「不一定能這樣保證，對抗性測試本質上是針對測試設計者目前已經知道能想到的攻擊手法去做驗證，天生只能涵蓋已知攻擊手法，沒辦法保證對未來全新事先無法預料的攻擊手法也同樣具備防護能力」。連結到之前的核心告誡——「這直接呼應了之前討論過的攻擊者總是能夠不斷設計出新的、事先沒被預料到攻擊手法這個核心告誡，這也呼應了輸入護欄這種依靠事先窮舉已知模式的防禦方式天生難以做到完全窮盡的相同結構性限制」。給出更務實的因應策略——「一個真正成熟的安全策略不應該把通過對抗性測試當成可以高枕無憂的終點，而應該持續關注業界最新攻擊手法、定期重新設計擴充測試涵蓋範圍、以及額外搭配輸出護欄這種更根本、不依賴窮舉已知攻擊手法的防護機制作為補充防線」。

### 因為 Agent 的行為涉及前面已經深入討論過的機率性判斷（而非傳統程式碼的確定性邏輯），同樣的測試案例在不同次的執行是不是可能得到不完全相同的結果？這對回歸測試這個機制帶來什麼樣的額外挑戰？

**核心答案**：**是的，確實可能得到不完全相同的結果，這帶來一個相當獨特、且傳統軟體工程裡的回歸測試較少需要面對的額外挑戰**——延續前面（見 [[016-orchestration-patterns.md]] 的常見追問）已經深入討論過的核心洞察——**「模型的判斷本質上是基於語意理解的機率性判斷，而不是明確、固定不變的規則」**——這意味著**即使是完全相同的輸入內容，重複執行同一個 Agent 系統好幾次**，也**可能**因為這種**固有的機率性特質**而得到**些微不完全一致**的具體回應或行為軌跡（即使最終的整體結果大方向上可能依然是正確、合理的）。這對傳統的**回歸測試**機制帶來一個核心挑戰——**傳統的回歸測試通常依賴一種『這次的輸出是否和上一次（或者一個明確定義的預期基準）完全精確一致』**這種**較嚴格的比對邏輯**，但**這種嚴格的『逐字精確比對』邏輯****並不適合**直接套用到這種**本質上涉及一定程度機率性變化**的 Agent 行為上（如果堅持採用這種嚴格比對，很可能會**把大量其實依然屬於合理、可接受範圍內的正常變化**都**誤判成回歸測試失敗**）。

**詳細解析**：這題要求把前面（見 [[016-orchestration-patterns.md]] 的常見追問）已經深入討論過的**『模型判斷本質上是機率性而非固定規則』**這個核心認知**具體地延伸應用到回歸測試這個特定的測試機制上**，考察是否能夠識別出這個**已經被建立的核心特性**會對**回歸測試這種傳統的測試方法論**帶來**需要額外調整**的具體衝擊。理解這個問題的核心在於回顧——**傳統軟體工程裡的回歸測試**之所以能夠運作得**相對直接、簡單**，核心的隱含前提是——**傳統程式碼的執行邏輯本質上是確定性（Deterministic）的**——**給定完全相同的輸入**，一段**沒有任何改變**的程式碼**理論上永遠**會得到**完全相同**的輸出，這種**確定性**讓**「拿這次的輸出去和上一次（或一個明確預期的標準答案）做逐字精確比對」**這種簡單的回歸測試邏輯能夠**可靠地運作**——但**一旦這個系統涉及大型語言模型這種本質上基於機率性推斷而運作**的核心元件，前面已經提到的**「確定性」**這個前提**就不再穩固地成立**——**同樣的輸入、重複執行****可能**因為模型本身固有的機率性特質而產生**些微不同、但可能都同樣屬於『合理』範疇**的輸出。這種情況下如果**依然堅持套用傳統那種『逐字精確比對』**的嚴格回歸測試邏輯，很可能會**產生大量其實並非真正代表『功能被破壞』的『假性回歸失敗』警報**（這某種程度上也呼應了前面（見 [[020-guardrails.md]] 的常見追問）已經深入討論過的『假陽性』這個核心概念，只是套用在回歸測試這個新的具體情境上）。因應這種挑戰，實務上**針對 Agent 系統的回歸測試**需要**額外地調整判斷『測試是否通過』的具體標準**——不再追求**『逐字完全一致』**這種過於嚴格的標準，而改為聚焦在**更加語意層次、更加寬鬆的等價性判斷**——例如判斷**「這次的輸出和先前的輸出，雖然具體措辭可能略有不同，但是否依然表達了相同的核心語意、依然達成了相同的核心任務目標」**。這種**「從逐字精確比對轉換成語意層次的等價性判斷」**可能需要**額外地運用某種語意相似度判斷機制**（甚至可能需要額外運用另一個模型去做這種語意等價性的判斷，這某種程度上又呼應了前面（見 [[013-agent-evaluation.md]]）已經深入討論過的 LLM-as-a-Judge 這類評估手段），而**不是**單純地**沿用**傳統軟體工程裡那種**依賴確定性、逐字比對**的簡單回歸測試邏輯。理解「是的確實可能得到不完全相同的結果，這帶來一個傳統回歸測試較少需要面對的額外挑戰，傳統軟體工程的回歸測試之所以能相對直接簡單運作，核心隱含前提是傳統程式碼執行邏輯本質上是確定性的，給定完全相同輸入一段沒有改變的程式碼理論上永遠會得到完全相同輸出，這種確定性讓逐字精確比對這種簡單回歸測試邏輯能可靠運作，但一旦系統涉及大型語言模型這種本質上基於機率性推斷運作的核心元件，確定性這個前提就不再穩固成立，同樣輸入重複執行可能因為模型固有機率性特質而產生些微不同、但可能都同樣屬於合理範疇的輸出，如果依然堅持套用傳統逐字精確比對的嚴格回歸測試邏輯，很可能產生大量並非真正代表功能被破壞的假性回歸失敗警報，因應這種挑戰，針對Agent系統的回歸測試需要額外調整判斷測試是否通過的具體標準，不再追求逐字完全一致，而改為聚焦在更語意層次的等價性判斷，判斷輸出雖具體措辭略有不同，但是否依然表達相同核心語意、達成相同核心任務目標，這可能需要額外運用某種語意相似度判斷機制，甚至運用另一個模型做這種語意等價性判斷」，展現你能把之前建立的模型判斷本質上是機率性而非固定規則這個核心認知，正確延伸應用到回歸測試這個具體測試機制，識別出需要調整的具體判斷標準。

**面試回答方式**：先明確給出核心答案——「是的確實可能得到不完全相同的結果，這帶來一個傳統回歸測試較少需要面對的額外挑戰」。解釋傳統回歸測試依賴的隱含前提——「傳統軟體工程的回歸測試依賴程式碼執行邏輯本質上是確定性的，給定完全相同輸入永遠會得到完全相同輸出，這種確定性讓逐字精確比對這種簡單邏輯能可靠運作，但一旦涉及大型語言模型這種基於機率性推斷運作的核心元件，這個前提就不再穩固成立」。給出具體的調整做法——「如果依然堅持套用傳統逐字精確比對的嚴格邏輯，很可能產生大量假性回歸失敗警報，因應這個挑戰，需要額外調整判斷標準，不再追求逐字完全一致，而改為聚焦在更語意層次的等價性判斷——輸出雖然具體措辭略有不同，但是否依然表達相同核心語意、達成相同核心任務目標，這可能需要額外運用語意相似度判斷機制，甚至運用另一個模型做這種語意等價性判斷」。
