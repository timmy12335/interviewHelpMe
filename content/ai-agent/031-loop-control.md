# 題目

Agent 的執行迴圈該怎麼設計終止條件？怎麼防止它一直跑下去？

## 核心答案

終止條件應該有多重，而且要有一個絕對不會被繞過的硬界線。

**正常終止**——**模型明確宣告任務完成**（呼叫一個 `finish` 工具或產生特定的結束標記）。這是最理想的，但不能是唯一的。

**硬性界線**——最大步數、最大成本、最大掛鐘時間；**任何一個超過就強制停止**。這是防止失控的最後一道防線，必須存在。

**異常終止**——偵測到重複模式、連續失敗超過 N 次、或者發散。

**外部中斷**——使用者主動停止，或者一個監督機制判定應該停止。

而最重要的設計原則是「停止時要留下可用的狀態」——不是簡單地拋出錯誤，而是產出「已完成什麼、卡在哪、建議下一步」的報告，讓人能接手或讓下一次執行能繼續。

## 詳細解析

「讓模型自己宣告完成」有一個典型的失敗模式：它會過早宣稱成功。模型傾向於給出正面的回應——於是在任務其實沒完成時也可能說「已完成」。緩解的做法是「用外部的驗證取代自我宣告」：在編碼場景跑測試、在資料處理場景檢查輸出的結構、在查詢場景驗證答案有出處——**只有驗證通過才算完成**。這與「不要讓模型自己評估自己」是同一條原則，而在終止判斷上它尤其重要，因為錯誤的終止會直接交付一個未完成的結果。

**「預算應該是多維的」**：只設最大步數是不夠的——一步可能很便宜也可能很貴（一次長上下文的呼叫可能是普通呼叫的幾十倍成本）。所以應該同時追蹤步數、累計 token、以及時間，**任一超過就停**。而預算的設定應該基於「這個任務合理的上限」而非「不要跑太久」的模糊感覺——做法是先觀察成功案例的分布，把上限設在 p95 到 p99 附近。

「連續失敗的處理」需要區分兩種情況：同一個操作失敗（可能是暫時性的，重試合理）與不同的操作連續失敗（可能是整體策略錯了，該重新規劃而非繼續）。簡單地「連續失敗 N 次就停」會誤殺前者，而「無限重試」會浪費在後者上——所以判斷應該基於「是不是在重複同一件事」而非單純的失敗計數。

「停止的通知」是產品層面的要求：使用者需要知道 Agent 為什麼停了——「達到步數上限」「連續失敗」「需要你的確認」是完全不同的訊息，對應完全不同的下一步。把它們都表達成「執行失敗」是一個常見但糟糕的設計。

## 面試回答方式

先給四類終止條件並強調硬界線是防止失控的最後一道防線，必須存在，收在**停止時要留下可用的狀態**。加分點有四個：讓模型自己宣告完成會過早宣稱成功——緩解是用外部驗證取代自我宣告（跑測試、檢查結構、驗證出處），而在終止判斷上尤其重要，因為錯誤的終止會直接交付未完成的結果；**預算應該是多維的**——只設步數不夠，一步的成本可能差幾十倍，而上限應該基於成功案例分布的 p95 到 p99 而非模糊感覺；連續失敗要區分「重複同一件事」與「不同操作連續失敗」——**前者可重試、後者該重新規劃**；以及**停止的通知要區分原因**，都表達成「執行失敗」是常見但糟糕的設計。

## 講稿

終止條件應該有多重，而且要有一個絕對不會被繞過的硬界線。

正常終止是模型明確宣告完成，但它不能是唯一的。因為模型傾向於給出正面回應，在任務其實沒完成時也可能說已完成。所以我會用外部驗證取代自我宣告，編碼場景跑測試、資料處理檢查輸出結構、查詢場景驗證答案有出處。只有驗證通過才算完成。

硬性界線是最大步數、最大成本、最大時間，任一超過就強制停止。這裡有一點，預算應該是多維的。只設步數不夠，因為一步可能很便宜也可能很貴，一次長上下文的呼叫可能是普通的幾十倍。而上限應該基於觀察成功案例的分布，設在九十五到九十九百分位附近。

還有異常終止。但連續失敗的處理要區分兩種情況，同一個操作失敗可能是暫時性的，重試合理。不同操作連續失敗則可能是整體策略錯了，該重新規劃而不是繼續。

最後，停止時要留下可用的狀態，說明已完成什麼、卡在哪、建議下一步。

## 常見追問

### 怎麼判斷 Agent「卡住了」？

**核心答案**：**四個訊號**。**重複的工具呼叫**（相同工具加相同參數）。**上下文成長但沒有實質進展**（沒有新的檔案產出、沒有新的確認事實）。在同一個子任務上耗費的步數遠超預期。以及「模型的輸出開始表達困惑」（「我不確定該怎麼繼續」這類語句）。

**詳細解析**：「進展的量化」是這裡最有價值也最難的部分：步數容易數，而「有沒有進展」需要定義。實用的做法是讓 Agent 維護一個明確的待辦清單並在每步後更新——於是「已完成項目數」成為一個可觀測的進度指標；連續五步待辦清單沒有變化就是卡住的訊號。這個做法的額外好處是它讓進度對人可見。而更輕量的代理指標是「新產生的具體產出」：檔案的變更、成功的工具呼叫、確認的事實——如果連續多步只有失敗的嘗試與思考，那就是卡住了。能提出一個可量測的「進展」定義，比列舉症狀更能展現工程思維。

**面試回答方式**：給四個訊號。核心加分點是指出**「進展的量化」最有價值也最難**——步數容易數而「有沒有進展」需要定義，並給出做法：讓 Agent 維護明確的待辦清單並每步更新，於是「已完成項目數」成為可觀測的進度指標，連續五步沒變化就是卡住，**額外好處是進度對人可見**。收在更輕量的代理指標：**新產生的具體產出**（檔案變更、成功的呼叫、確認的事實）。

### 卡住之後該怎麼處理？

**核心答案**：階梯式升級，而不是直接放棄或無限重試。**第一步：換方法**——注入明確的提示要求它嘗試不同的策略。**第二步：縮小範圍**——把任務拆得更小，先做能做的部分。**第三步：求助**——向使用者提問或請求額外資訊。**第四步：交出去**——**產出交接報告並停止**。

**詳細解析**：「求助」這一步在多數 Agent 實作中是缺失的，而它常常是最有效的：Agent 卡住往往是因為缺少某個資訊（一個 ID、一個決定、一個權限）——而那個資訊使用者三秒鐘就能提供。但如果 Agent 沒有「提問」這個動作，它只能繼續猜或者放棄。所以「向使用者提問」應該被設計成一個一等公民的工具，並且在系統提示中明確鼓勵「不確定時就問，不要猜」。這個設計改變的不只是成功率，還有信任：一個會適時提問的 Agent 比一個總是自信地做錯事的 Agent 更容易被接受——而後者正是很多 Agent 產品失敗的原因。

**面試回答方式**：給四步階梯式升級。核心加分點是指出「求助」在多數實作中是缺失的而它常常最有效——Agent 卡住往往是缺少某個使用者三秒鐘就能提供的資訊，所以「向使用者提問」應該是一等公民的工具，並在提示中明確鼓勵「不確定就問，不要猜」。收在更深的價值：這改變的不只是成功率還有信任——會適時提問的 Agent 比總是自信地做錯事的更容易被接受，而後者正是很多產品失敗的原因。

### 多層巢狀的 Agent 怎麼控制總預算？

**核心答案**：預算要能被「傳遞與扣減」而非各自獨立。父 Agent 呼叫子 Agent 時**傳遞剩餘的預算**，子 Agent 的消耗直接扣減自同一個池子——否則十個子 Agent 各自有自己的上限，總量就完全失控。**同時要有一個全局的熔斷**：單次請求的總成本超過閾值就強制中止整棵呼叫樹。

**詳細解析**：「預算傳遞」還需要處理一個分配問題：父 Agent 有 100 單位預算要分給三個子任務——平均分配可能讓一個困難的子任務餓死，而讓子 Agent 自由消耗可能讓第一個就吃光。實用的做法是「給每個子 Agent 一個上限（例如剩餘預算的 50%），並在它結束後重新計算剩餘」——這既防止單一子任務吃光，也讓後續任務能用到未被消耗的部分。另一個要點是「預算耗盡的處理不應該是靜默失敗」：應該明確地回傳「因預算不足而未完成，已完成的部分是 X」——讓上層能做出決定（追加預算、簡化任務、或者交給人）。這與作業系統的資源限制是同一個模式：限制必須是可觀測且可處理的，而不是無聲的中斷。

**面試回答方式**：主張預算要能傳遞與扣減而非各自獨立，並指出否則十個子 Agent 各有上限就完全失控，加上全局熔斷。核心加分點是**分配問題**：平均分配可能餓死困難任務，自由消耗可能讓第一個吃光，實用做法是給每個子 Agent 剩餘預算的一個比例上限並在結束後重新計算。收在**預算耗盡不應該是靜默失敗**——要明確回傳「因預算不足而未完成，已完成的是什麼」讓上層能做決定。
