# 題目

Agent 的行為在某天突然變了，可能是什麼原因？怎麼管理？

## 核心答案

Agent 的行為由四個東西共同決定，而它們都可能獨立地變化。

**模型版本**——**供應商更新或棄用模型**；即使版本號沒變，底層也可能有調整。**提示**——系統提示、工具描述的任何改動。**工具**——工具的實作、回傳格式、或錯誤訊息的變化。**外部世界**——資料變了、下游服務的行為變了。

**所以「版本」必須涵蓋這四者**：每一次執行都記錄「模型版本、提示版本、工具版本、以及執行時間」——沒有這些，「什麼時候開始變的、因為什麼」永遠無法回答。

而管理的核心是「把 Agent 的定義當成一個整體來版本化」：提示、工具定義、以及評估集應該放在同一個 Git 倉庫並一起發布——因為它們是耦合的，分開管理必然會不同步。

## 詳細解析

「模型的靜默更新」是最難防範的一類漂移：你什麼都沒改，但供應商調整了模型，於是行為變了。**防護的做法有三**：盡量鎖定明確的版本號（而非會自動更新的別名）、定期跑評估集監控指標的變化（即使沒有發布也要跑，因為變化可能來自外部）、**以及訂閱供應商的變更通知**。**而第二項是最實在的**——它讓你在使用者投訴之前就發現問題。

「提示的微小改動可能有非線性的影響」：改一個詞、調整一個範例的順序——**可能顯著改變行為**。所以提示的變更應該與程式碼變更受同等對待：經過 review、跑評估集、有版本記錄、可以回滾。把提示存在資料庫並允許隨時修改是一個常見但危險的設計——它讓提示脫離了所有的工程紀律。

**「工具的變更最容易被忽略」**：一個下游 API 增加了一個欄位、改了錯誤訊息的措辭、或者調整了回傳的排序——這些在傳統系統中是無害的向後相容變更，**但可能顯著改變 Agent 的行為**（**因為模型讀的是那些內容**）。所以工具的回傳格式應該被視為一個對模型的契約，**變更時要跑評估集驗證**。

**「漂移的偵測需要持續的基準」**：一個固定的評估集，定期（例如每天）自動執行並記錄分數——於是分數的變化曲線本身就是一個監控指標。這比等到使用者反映有問題有效得多，而它的成本只是每天跑幾十個測試案例。

## 面試回答方式

先給四個獨立變化的來源（模型、提示、工具、外部世界）並指出**版本記錄必須涵蓋這四者**，收在**把 Agent 的定義當成整體來版本化**。加分點有四個：**模型的靜默更新最難防範**——**你什麼都沒改但行為變了**，而定期跑評估集（即使沒發布也要跑）是最實在的防護，讓你在使用者投訴前就發現；提示的微小改動可能有非線性影響，所以應該與程式碼受同等對待，而把提示存在資料庫允許隨時改是危險的設計；**工具的變更最容易被忽略**——傳統上無害的向後相容變更可能顯著改變 Agent 行為，因為模型讀的是那些內容；以及**漂移的偵測需要持續的基準**——每天自動跑評估集，分數曲線本身就是監控指標。

## 講稿

代理的行為由四個東西共同決定，而它們都可能獨立地變化。模型版本、提示、工具、還有外部世界。所以版本記錄必須涵蓋這四者，每一次執行都要記下用的是哪個模型、哪個提示版本、哪個工具版本。沒有這些，什麼時候開始變的、因為什麼，永遠無法回答。

最難防範的是模型的靜默更新。你什麼都沒改，但供應商調整了模型，行為就變了。所以我會盡量鎖定明確的版本號而不是自動更新的別名，並且定期跑評估集監控指標，即使沒有發布也要跑，因為變化可能來自外部。這一項是最實在的，它讓你在使用者投訴之前就發現問題。

還有一個最容易被忽略的來源，工具的變更。一個下游介面增加了欄位、改了錯誤訊息的措辭、或者調整了回傳的排序，這些在傳統系統裡是無害的向後相容變更，但可能顯著改變代理的行為，因為模型讀的正是那些內容。所以工具的回傳格式應該被視為一個對模型的契約，變更時要跑評估集驗證。

## 常見追問

### 提示改動的 review 該看什麼？

**核心答案**：**三件事**。**變更的意圖**——這個改動想解決什麼問題、有沒有對應的失敗案例。**副作用的評估**——這個改動可能影響哪些其他場景（提示是全域的，改一句可能影響所有請求）。**以及評估結果**——**跑過評估集了嗎、分數如何**。

**詳細解析**：「提示改動的副作用範圍比程式碼大」是 review 時最需要警惕的：程式碼的改動有明確的作用域——而系統提示的一句話會影響每一個請求。加一句「回答要簡短」可能同時讓需要詳細說明的場景變差。所以 review 時應該問「這個改動在哪些情況下可能是錯的」而不只是「這個改動能不能解決那個問題」。而最好的防護是評估集包含多樣的場景——**於是副作用會在分數上顯現**。另一個實用的做法是「一次只改一件事」：同時改三處的話，即使分數下降也不知道是哪一處造成的——這與軟體的小步提交是同一個道理，而在提示上因為缺乏靜態分析，它更重要。

**面試回答方式**：給三件要看的事。核心加分點是提示改動的副作用範圍比程式碼大——程式碼有明確作用域而系統提示的一句話影響每個請求，所以要問「這個改動在哪些情況下可能是錯的」而不只是「能不能解決那個問題」。收在**一次只改一件事**——同時改三處的話分數下降也不知道是哪處造成的，與小步提交同理，而在提示上因為缺乏靜態分析更重要。

### 怎麼安全地升級模型版本？

**核心答案**：**四步**。**離線比對**——用固定的評估集在新舊模型上各跑一遍，比對每一個案例的差異。**分析退化案例**——不只看總分，要看「哪些案例變差了」並判斷是否可接受。**灰度發布**——小比例流量先上，監控真實指標。**保留回滾能力**——確認舊版本仍可用，並準備好切換。

**詳細解析**：「逐案例比對」比看總分有價值得多：總分可能持平——但那可能是「一半案例變好、一半變差」，而變差的那一半可能正好是你最在意的場景。所以比對應該產出一份「變好的、變差的、不變的」清單並人工檢視變差的部分。另一個實務要點是「新模型可能需要不同的提示」：針對舊模型調校的提示（包括各種繞過它弱點的技巧）在新模型上可能是多餘甚至有害的——所以升級模型時應該同時檢視提示是否還需要那些補丁。很多團隊升級後表現不如預期，原因正是「用舊提示跑新模型」——而重新調校提示往往能釋放新模型的大部分收益。

**面試回答方式**：給四步流程。核心加分點是**逐案例比對比看總分有價值**——總分持平可能是一半變好一半變差，而變差的那半可能正好是你最在意的場景。第二個是**新模型可能需要不同的提示**——針對舊模型的補丁在新模型上可能多餘甚至有害，很多團隊升級後表現不如預期正是因為用舊提示跑新模型，而重新調校往往能釋放大部分收益。

### 工具的介面變更怎麼做才安全？

**核心答案**：與 API 的向後相容原則一樣，但要多考慮「模型是消費者」這一點。**新增欄位通常安全**；**改名或改變語義不安全**（模型可能依賴舊的欄位名理解含義）；而錯誤訊息與描述的措辭變更也應該被視為介面變更——因為它們直接影響模型的行為。

**詳細解析**：「描述的措辭是介面的一部分」是這裡最特別的一點：傳統 API 的文件改了不影響已部署的客戶端——而工具描述改了會立刻改變模型的行為。所以工具描述應該與程式碼一起版本控制、一起 review、一起測試。另一個實務要點是「回傳格式的變更要考慮模型的解析習慣」：模型可能已經習慣了某種結構（例如它學會了在回傳的第一項中找答案）——改變排序或巢狀結構可能讓它找錯地方。所以介面變更後跑一次評估集不是可選的。而最安全的變更方式仍然是「擴充而非修改」：加新欄位、保留舊欄位一段時間、確認沒有依賴後才移除——這與 API 的擴充收縮模式完全一致，只是這裡的客戶端是一個會自己推理的模型。

**面試回答方式**：給向後相容的原則並指出**要多考慮「模型是消費者」**。核心加分點是**描述的措辭是介面的一部分**——傳統 API 的文件改了不影響已部署的客戶端，而工具描述改了會立刻改變模型行為，所以要與程式碼一起版本控制、review、測試。第二個是回傳格式的變更要考慮模型的解析習慣（改排序可能讓它找錯地方）。收在最安全的方式：**擴充而非修改**，與 API 的擴充收縮模式一致，只是客戶端是一個會自己推理的模型。
