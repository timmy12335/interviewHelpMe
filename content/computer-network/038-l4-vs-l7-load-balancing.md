# 題目

四層與七層負載平衡差在哪？各自適合什麼場景？

## 核心答案

差別在「它看得到什麼」，而那決定了它能做什麼。

**四層（傳輸層）**——**只看 IP 與埠號，轉發 TCP 或 UDP 的封包**；不解析內容、不終止連線（DSR 模式下甚至不看回程流量）。優點是極快、資源消耗低、協定無關（任何 TCP 服務都能用）；缺點是無法基於 URL、標頭、cookie 做路由，也無法做 HTTP 層的重試與健康檢查。

**七層（應用層）**——**終止 TCP 連線並解析 HTTP**；**能基於路徑、主機名、標頭、cookie 路由**、**能改寫請求與回應**、能做基於狀態碼的健康檢查與重試、**能終止 TLS**。代價是每個連線都要處理應用層的資料，成本高得多。

選擇的原則是「需要看內容才能做的決定就用七層，否則用四層」——而實務上常見的是兩者串接：四層做入口與跨區分流，七層做應用內的路由。

## 詳細解析

「七層能做重試而四層不能」是一個很實質的差異：四層轉發的是位元組流——一旦後端在中途掛了，它不知道那個請求是什麼，無法重送；而七層理解請求的邊界，可以在後端失敗時把同一個請求送給另一台。**這對可用性的影響很大**：一次後端的重啟，在四層下表現為使用者看到錯誤，在七層下可能完全無感。所以「面向使用者的流量幾乎總是應該經過七層」。

「四層的效能優勢在大流量下很顯著」：不需要解析、不需要維護應用層的狀態、可以用核心層的機制（IPVS、eBPF、XDP）處理——於是單機能處理的連線數與吞吐高一到兩個數量級。這正是為什麼「入口層用四層做粗分流」在大規模架構中很常見——它把巨大的流量分散開，讓後面的七層層不必單點承擔。

「DSR（直接伺服器回應）」是四層的一個特殊模式：請求經過負載平衡器，而回應直接從後端送回客戶端（不經過負載平衡器）——於是負載平衡器只處理入向流量。這在「回應遠大於請求」的場景（影音、檔案下載）中能大幅降低負載平衡器的頻寬需求。代價是設定複雜且對網路拓撲有要求。

**「健康檢查的深度不同」**：四層只能檢查「TCP 能不能連上」——而一個行程卡住但埠還開著的服務會被認為健康；七層能檢查「HTTP 回應是不是 200」甚至檢查回應的內容——**能發現「活著但不健康」的實例**。這個差異在實務上比路由能力更重要，因為它直接決定了故障實例會不會繼續收到流量。

## 面試回答方式

先給核心差別（它看得到什麼決定了它能做什麼）與各自的能力與代價，給出選擇原則與**兩者串接**的常見架構。加分點有四個：**七層能做重試而四層不能**——一次後端重啟在四層下使用者看到錯誤、在七層下可能完全無感，所以面向使用者的流量幾乎總該經過七層；四層的效能優勢在大流量下顯著（核心層處理、高一到兩個數量級），這是入口層用四層粗分流的原因；**DSR 讓回應不經過負載平衡器**，在回應遠大於請求時大幅降低頻寬需求；以及**健康檢查的深度不同**——四層無法發現「活著但不健康」的實例，而這在實務上比路由能力更重要。

## 講稿

差別在它看得到什麼，而那決定了它能做什麼。

四層只看位址跟埠號，轉發封包，不解析內容。優點是極快、資源消耗低、協定無關。缺點是無法基於路徑、標頭、憑證做路由，也無法做應用層的重試跟健康檢查。

七層終止連線並解析應用協定，能基於路徑主機名標頭路由、能改寫、能做基於狀態碼的健康檢查與重試、能終止加密。代價是每個連線都要處理應用層資料，成本高得多。

我覺得最實質的差異有兩個。第一是重試。四層轉發的是位元組流，後端在中途掛了它不知道那個請求是什麼，無法重送。而七層理解請求的邊界，可以送給另一台。於是一次後端重啟，在四層下使用者看到錯誤，在七層下可能完全無感。

第二是健康檢查的深度。四層只能檢查連得上連不上，而一個行程卡住但埠還開著的服務會被認為健康。七層能檢查回應是不是正常甚至檢查內容。這個差異在實務上比路由能力更重要，因為它直接決定了故障實例會不會繼續收到流量。

實務上常見的是兩者串接，四層做入口與跨區分流，七層做應用內的路由。

## 常見追問

### 負載平衡演算法怎麼選？

**核心答案**：**四種常見的**。**輪詢**——最簡單，適合後端能力相同且請求成本相近的場景。**最少連線**——把新請求給當前連線最少的後端；適合請求處理時間差異大的場景。**加權**——**後端能力不同時按權重分配**。**以及一致性雜湊**——**同一個 key 總是到同一台**；**適合需要快取親和性的場景**。

**詳細解析**：「最少連線比輪詢更能適應真實情況」：輪詢假設每個請求的成本相同——而實際上一個請求可能 1 毫秒、另一個 5 秒；於是輪詢下某台可能積壓了幾個慢請求而仍然收到新的。最少連線天然地避開了這個問題（忙的那台連線數多，就少分給它）——所以它在請求成本不均的場景中明顯更好，而那是多數真實場景。更進階的是「最少未完成請求數（least outstanding requests）」與「基於延遲的加權」——它們用實際觀察到的表現而非連線數來分配，能自動適應後端的效能差異（例如一台機器因為鄰居噪音而變慢）。這個「用實測的表現而非靜態的假設來分配」的思路，是現代負載平衡的方向。

**面試回答方式**：給四種演算法與各自的適用場景。核心加分點是最少連線比輪詢更能適應真實情況——輪詢假設每個請求成本相同，而實際上可能差幾千倍，所以它在多數真實場景中明顯更好。收在進階方向：最少未完成請求數與基於延遲的加權用實測表現而非靜態假設分配，能自動適應後端的效能差異，這是現代負載平衡的方向。

### 健康檢查該怎麼設計？

**核心答案**：**兩種端點，兩種語義**。**存活檢查（liveness）**——**「這個行程還活著嗎」**；**失敗就重啟**。**就緒檢查（readiness）**——**「這個實例現在能處理請求嗎」**；失敗就從負載平衡中移除但不重啟。**兩者不該用同一個端點**——因為「暫時無法服務（例如下游不可用）」不應該導致重啟。

**詳細解析**：「就緒檢查不該檢查下游依賴」是一個容易踩的坑：如果就緒檢查會呼叫資料庫——那麼資料庫一抖動，所有實例同時變成未就緒，於是負載平衡器沒有任何可用的後端，服務完全中斷；而實際上那些實例可能還能處理不需要資料庫的請求，或者資料庫只是短暫慢了。所以就緒檢查應該只反映「這個實例自身的狀態」——而下游的問題應該由熔斷與降級處理，而不是讓自己下線。這個「檢查得夠深但不要太深」的分寸，是健康檢查設計中最需要判斷的部分，而它的錯誤會把一次小抖動放大成全站中斷。

**面試回答方式**：給兩種檢查的區分與**不該用同一個端點**的理由。核心加分點是**就緒檢查不該檢查下游依賴**——資料庫一抖動所有實例同時未就緒，於是沒有任何可用後端、服務完全中斷，而那些實例可能還能處理不需要資料庫的請求。收在原則：下游的問題應該由熔斷與降級處理而非讓自己下線，而這個分寸的錯誤會把一次小抖動放大成全站中斷。

### 負載平衡器本身怎麼做到高可用？

**核心答案**：**它自己不能是單點**。常見的三種做法：**DNS 輪詢到多個負載平衡器**（簡單但故障切換慢，受 DNS 快取影響）、**VIP 加 VRRP/keepalived**（多台共享一個虛擬 IP，主掛了備接管，秒級切換）、**以及 Anycast**（多個地點宣告同一個 IP，由路由自動選最近的，天然的故障轉移與地理分流）。

**詳細解析**：「雲端的託管負載平衡器已經解決了這個問題」是實務上最常見的答案：AWS 的 ALB/NLB、GCP 的負載平衡器——它們本身是分散式且高可用的服務，使用者不需要考慮它的單點問題。所以「自建負載平衡器的高可用」主要是自建機房或特殊需求下的課題。而值得知道的是「託管服務的擴容也需要時間」：一些雲端的負載平衡器在流量突增時需要幾分鐘擴容——於是「預熱」（提前告知雲廠商即將有大流量）在秒殺或大促這類場景中是必要的。這是一個「託管服務不等於無限彈性」的提醒——而不知道它的團隊會在活動開始的那一刻遇到 5xx。

**面試回答方式**：給三種做法與各自的切換特性。核心加分點是指出雲端的託管負載平衡器已經解決了這個問題，所以自建的高可用主要是特殊需求下的課題。收在一個實務提醒：**託管服務的擴容也需要時間**——流量突增時可能需要幾分鐘，所以秒殺或大促前的預熱是必要的，而不知道這一點的團隊會在活動開始那一刻遇到錯誤。
