# 題目

TCP 用哪些機制保證資料不丟、不重、有序？

## 核心答案

五個機制疊在一起：**一、序號**——每個位元組都有編號，接收端據此**排序與去重**，亂序抵達的段可以重組、重複的段可以丟棄。**二、確認**——接收端回報「我已經連續收到到哪個位元組為止」，這個確認是**累積式**的，代表這個號碼之前的資料全部收齊了。**三、逾時重傳**——發送端為送出的資料設定計時器，時間到還沒收到確認就重傳，逾時長度由**動態量測的往返時間**推算而非固定值。**四、快速重傳**——不必等逾時，收到**三個重複的確認**就代表某個段遺失了（後面的段有到、中間缺了一塊），立刻重傳。**五、校驗和**——偵測傳輸過程中的位元錯誤，錯誤的段直接丟棄，靠重傳補回。這五者合起來提供「不丟、不重、有序」，但要注意它保證的範圍是已被 TCP 確認的資料會交付給應用層，不等於業務層面的送達。

## 詳細解析

**累積確認的優點與盲點**：回報「到某個號碼為止都收到了」很省事，一個確認可以涵蓋多個段，遺失的確認也能被後續的確認補上。盲點是它表達不了「中間缺一塊、但後面有收到」——發送端只知道缺口在哪，不知道後面收到了哪些，於是可能重傳已經送達的資料。**選擇性確認（SACK）**就是為此設計的選項，讓接收端額外報告「我還收到了哪幾段」，發送端就只補缺口，避免無謂的重傳。這是高遺失率環境下效能差異很大的一個選項。

**逾時時間怎麼定**：太短會造成不必要的重傳、加重壅塞；太長則遺失後恢復很慢。TCP 持續量測往返時間並取加權平均，同時追蹤其變異程度，用兩者推算逾時值——變異大的網路會得到較寬鬆的逾時。此外每次重傳失敗後逾時會**指數退避**，避免在網路已經壅塞時繼續加壓。

**快速重傳的判斷依據**：接收端每收到一個亂序的段就重發一次「我還在等這個號碼」的確認。發送端收到三個重複確認，代表至少有三個後續的段已經抵達，遺失的機率遠高於單純亂序，於是立刻重傳而不等計時器。**用三個而不是一個**是為了容忍網路中正常的輕微亂序，避免誤判。

**校驗和的強度有限**：它只是簡單的加總，能抓到大多數隨機的位元錯誤，但不足以抵抗刻意的竄改，也可能漏掉某些組合的錯誤。所以資料完整性與真實性要靠 TLS 這類上層機制，TCP 的校驗和只是對抗傳輸雜訊，不是安全機制——這個區分值得主動說明。

**可靠不代表即時**：這些機制的代價是**延遲的不確定性**。遺失發生時，資料要等重傳才會交付，而在此之前後續已抵達的資料全部卡住（隊頭阻塞）。這正是即時應用寧可選 UDP 的原因——它們寧願丟掉遲到的資料，也不要為了完整性而讓整條流卡住。

## 面試回答方式

用**五個機制**組織回答（序號、確認、逾時重傳、快速重傳、校驗和），每個一句話講清它解決什麼，這比籠統說「靠確認與重傳」有結構得多。接著主動展開兩個細節：**累積確認的盲點與 SACK**，以及快速重傳為什麼是三個重複確認（容忍正常的輕微亂序）。加分點有三個：逾時時間是動態量測往返時間推算的、失敗後指數退避；校驗和只對抗傳輸雜訊、不是安全機制；以及誠實指出可靠的代價是延遲不確定與隊頭阻塞，這正是即時應用選 UDP 的理由。

## 講稿

我會拆成五個機制。

第一是序號，每個位元組都有編號，接收端可以據此排序跟去重，亂序到的重組回來、重複的丟掉。

第二是確認。接收端回報我已經連續收到到哪裡為止，這是累積式的，代表這個號碼之前全部收齊了。它的好處是一個確認可以涵蓋很多段，但盲點是表達不了中間缺一塊、後面有收到。所以有選擇性確認這個選項，讓接收端額外報告還收到哪幾段，發送端就只補缺口，不會重傳已經到的資料。

第三是逾時重傳，計時器到了還沒收到確認就重傳。逾時長度是動態量測往返時間算出來的，不是固定值，而且重傳失敗會指數退避。

第四是快速重傳。收到三個重複的確認就代表中間那段大概遺失了，不等計時器直接重傳。用三個而不是一個，是為了容忍網路裡正常的輕微亂序。

第五是校驗和，抓傳輸中的位元錯誤。不過它只是簡單加總，不能對抗刻意竄改，那要靠 TLS。

## 常見追問

### 選擇性確認（SACK）解決了什麼問題？

**核心答案**：解決累積確認無法表達「缺口之後收到了什麼」的問題。只有累積確認時，發送端看到確認停在某個位置，無法判斷後面的段是否抵達，保守的做法是把缺口之後的全部重傳一次——在高延遲或大量資料的情況下浪費極大。SACK 讓接收端在選項欄位中額外報告已收到的區段，發送端就能**只重傳真正缺的那幾段**。

**詳細解析**：效益在**高頻寬延遲乘積**的鏈路上最明顯——這類鏈路上一次可能有大量資料在途中，全部重傳的代價很高。SACK 也讓擁塞控制的判斷更準確，因為發送端能算出實際遺失了多少而不是只知道「有東西丟了」。要注意 SACK 是**選項**，需要兩端在握手時協商啟用；某些老舊的中間設備會剝除或破壞 TCP 選項，導致協商失敗，這是排查「跨某條路徑時效能特別差」的可能原因之一。相關的還有 DSACK，用來回報收到重複的段，幫助發送端判斷是不是自己重傳過度。

**面試回答方式**：講清累積確認的盲點與 SACK 如何補上（只補缺口而非全部重傳）。加分點是說明在高頻寬延遲乘積鏈路上效益最大、它也讓擁塞判斷更準，以及中間設備剝除 TCP 選項會導致協商失敗，這是效能排查的一個方向。

### Nagle 演算法與延遲確認為什麼會互相干擾？

**核心答案**：**Nagle** 會把小資料先攢著，等收到前一批的確認或攢滿一個段才送出，目的是避免大量小封包浪費頻寬。**延遲確認**則讓接收端不立刻回覆確認，等一小段時間看看能不能順便帶上回應資料，目的是減少純確認封包。兩者一起作用時會形成**互相等待**：發送端等確認才送下一批小資料，接收端等資料才順便回確認，於是出現數十到數百毫秒的無謂延遲。

**詳細解析**：這個組合在「**請求小、且一問一答**」的互動式應用上傷害最大——典型是 RPC 或資料庫的小查詢。實務解法有三種：在需要低延遲的連線上**關閉 Nagle**（設定立即送出的選項），這是最常見的做法；**把小寫入合併成一次寫入**，從根源避免產生小封包；或改用批次協定減少往返。要注意關閉 Nagle 不是萬靈丹——如果應用程式本身就會產生大量零碎的小寫入，關閉之後會送出大量小封包，浪費頻寬也增加處理成本，所以**先合併寫入通常比先關 Nagle 正確**。

**面試回答方式**：分別說明兩個機制的目的，再講清互相等待的機制。給出三種解法並排序，強調「先合併寫入再考慮關閉 Nagle」。加分點是點出這個問題在一問一答的 RPC 上傷害最大，以及關閉 Nagle 的副作用。

### 為什麼說 TCP 保證的可靠不等於業務可靠？

**核心答案**：因為 TCP 的保證止於「已確認的資料會按序交付給對端的應用層」。應用程式寫入成功只代表資料進了本機緩衝區；即使送達對端 TCP，對方的應用程式可能還沒讀取或處理就崩潰；連線也可能在中途斷開。所以業務層面的「確實收到並處理完成」必須靠**應用層的確認**，例如訊息佇列的 ack、RPC 的回應、HTTP 的狀態碼。

**詳細解析**：這個落差是分散式系統設計的基本前提，它直接推導出兩個常見的設計要求。**重試**：既然無法確定對方是否處理成功，就必須能重試；**冪等**：既然會重試，就必須保證重複執行不會造成額外影響。這一對是後端設計中反覆出現的組合。另一個相關現象是**連線假死**——如果對端應用程式停止讀取，接收視窗歸零，資料堆在發送端的緩衝區，連線在作業系統看來仍然正常，但業務其實已經停滯。這種情況只有靠**應用層心跳與逾時**才發現，TCP 的 keepalive 間隔通常太長而不夠用。

**面試回答方式**：精確界定 TCP 的保證範圍，並用「對方應用程式讀取前崩潰」說明落差。接著把它推導成兩個設計要求：可重試與冪等。加分點是講連線假死——接收視窗歸零時連線看似正常但業務停滯，要靠應用層心跳發現。
