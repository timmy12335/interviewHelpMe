# 題目

一台伺服器最多能接受多少條連線？「埠號只有六萬多，所以連線數上限是六萬」這個說法對嗎？

## 核心答案

**不對**。連線是由**五元組**唯一識別的：協定、來源 IP、來源埠、目標 IP、目標埠。伺服器端**監聽的埠號只有一個**（例如 80），所有進來的連線目標埠都相同，區分它們的是**來源 IP 與來源埠**——所以理論上伺服器能接受的連線數是「不同來源 IP 乘上不同來源埠」的組合，遠遠超過六萬。伺服器端真正的上限來自**檔案描述符數量、記憶體、以及每條連線的處理成本**，不是埠號。**埠號耗盡是客戶端的問題**——主動發起連線的一方要為每條連線分配一個本機埠，可用範圍通常是三萬多個，加上 `TIME_WAIT` 讓埠號在關閉後還要等待才能重用，高頻建立短連線時就會耗盡。但即使在客戶端，限制也是**針對同一個目標**的——連到不同的目標 IP 或埠時可以重用相同的本機埠，因為五元組仍然不同。

## 詳細解析

**伺服器端的實際限制**：**檔案描述符**是最常先碰到的（每條連線佔一個，行程與系統層級都有上限，預設值往往偏低）；**記憶體**次之（每條連線的收發緩衝區加上應用層的物件，數十 KB 起跳，百萬連線就是可觀的量）；再來是**連線追蹤表**（有狀態防火牆或 NAT 設備會為每條連線建表，表滿了新連線就被丟棄，而這個限制常常在中間設備上而不是伺服器上）。所以「能接多少連線」的答案是**看你先撞到哪個限制**，調參數前要先確認是哪一個。

**客戶端埠號耗盡的完整成因**：可用埠號範圍有限、每條連線佔一個、關閉後因 `TIME_WAIT` 還要等一段時間才能重用。三者相乘，高頻短連線的客戶端很容易在幾分鐘內耗盡。症狀是**連線建立階段就失敗**，而且往往突然大量出現。解法優先序是：**用連線池與 keep-alive 減少連線數**（通常一次解決）、**分散目標**（連到多個後端 IP 就能重用本機埠）、再來才是擴大埠號範圍或啟用 `TIME_WAIT` 重用。

**NAT 後方的埠號才是真正稀缺的**：一群機器共用一個對外 IP 時，NAT 設備要為每條連線分配一個對外埠號，這個資源是**整個網路共用**的。所以在大型的 NAT 環境（企業網路、行動網路、容器叢集的出口）中，埠號耗盡是真實且棘手的問題，症狀往往是「某些人偶爾連不上」而非全面故障。緩解方式是增加對外 IP、減少連線數、或縮短連線追蹤的逾時。

**長連線也不是免費的**：改用長連線解決了埠號問題，但把成本轉移到**記憶體與連線管理**上——閒置的連線仍佔用資源，而且中間設備可能悄悄切斷它們造成「連線池裡都是死連線」。所以連線池需要**健康檢查與最大閒置時間**，並且最大閒置時間應該小於路徑上最短的閒置逾時。這是連線池設定中最常被漏掉的一項。

**排查的起手式**：連線相關的問題要先確認**是哪一端、哪一層**——是客戶端建立不了（看埠號與本機錯誤）、伺服器接受不了（看描述符與佇列溢出）、還是中間設備擋掉（看連線追蹤表與防火牆）。這三個方向的解法完全不同，先分清楚能省下大量時間。

## 面試回答方式

第一句就糾正前提——**連線由五元組識別**，伺服器監聽埠只有一個，區分連線的是來源 IP 與來源埠，所以上限遠超六萬。接著給伺服器端真正的限制：**檔案描述符、記憶體、連線追蹤表**，並強調答案是「看你先撞到哪一個」。然後說明**埠號耗盡是客戶端的問題**，並給解法優先序：連線池與 keep-alive 優先、其次分散目標、最後才調參數。加分點有兩個：**NAT 後方的埠號是整個網路共用的**，所以大型 NAT 環境下耗盡很難查（症狀是偶發而非全面）；以及長連線把成本轉移到記憶體與連線管理，連線池的最大閒置時間要小於路徑上最短的閒置逾時。

## 講稿

這個說法不對。連線是由五元組識別的，協定、來源 IP、來源埠、目標 IP、目標埠。

伺服器監聽的埠號只有一個，所有進來的連線目標埠都一樣，真正區分它們的是來源 IP 跟來源埠。所以理論上能接受的連線數是不同來源 IP 乘上不同來源埠的組合，遠遠超過六萬。

伺服器端真正的上限是檔案描述符、記憶體、還有連線追蹤表。每條連線佔一個描述符，而預設上限往往偏低。緩衝區加上應用層物件，一條連線幾十 KB 起跳。連線追蹤表則常常是在中間設備上而不是伺服器上。所以能接多少連線，答案是看你先撞到哪一個。

埠號耗盡其實是客戶端的問題。主動發起連線的一方要為每條連線分配本機埠，範圍大概三萬多個，加上 TIME_WAIT 讓埠號關閉後還要等才能重用，高頻短連線很容易耗盡。

解法我會照這個順序，先用連線池跟 keep-alive 減少連線數，這通常一次就解決。再來是分散目標，連到不同的後端 IP 就能重用本機埠。最後才是調參數。

另外 NAT 後方的埠號是整個網路共用的，那個更難查，症狀通常是偶發而不是全面故障。

## 常見追問

### 一台機器要撐一百萬條連線，需要處理哪些問題？

**核心答案**：四個層面。**檔案描述符**——行程與系統層級的上限都要調高。**記憶體**——每條連線的核心緩衝區加上應用層物件是主要消耗，需要調小預設緩衝區並精簡應用層的每連線狀態。**IO 模型**——必須用事件驅動（epoll 這類）而非每連線一執行緒，否則光是執行緒堆疊與切換就撐不住。**中間設備**——連線追蹤表、負載平衡器的連線上限往往比伺服器先滿。

**詳細解析**：實務上更關鍵的是**這一百萬條連線在做什麼**。如果是幾乎閒置的長連線（推送通知、IoT 心跳），主要成本在記憶體，優化方向是壓縮每連線的狀態。如果每條連線都有頻繁的訊息往返，瓶頸會變成 CPU 與系統呼叫開銷，這時要考慮批次處理、減少喚醒次數。另外**單機百萬連線通常不是好的架構選擇**——故障影響範圍太大、部署與擴縮容困難，多數情況下用多台機器各撐十萬條、配上一層連線路由，整體更可控。能指出這一點會顯示你在意的是系統而不只是單機極限。

**面試回答方式**：給四個層面並各說明要調什麼。重點是反問「這些連線在做什麼」——閒置的優化記憶體、頻繁往返的優化 CPU 與系統呼叫。加分點是指出單機百萬連線通常不是好架構，故障範圍與部署困難，多台分攤更可控。

### 連線池該怎麼設定才合理？

**核心答案**：四個核心參數。**最大連線數**——依後端的承受能力而非客戶端的需求決定，設太大會把後端壓垮。**最小空閒連線**——維持一批熱連線避免尖峰時大量新建。**最大閒置時間**——必須**小於路徑上最短的閒置逾時**，否則池中會累積被中間設備悄悄切斷的死連線。**取用連線的等待逾時**——池滿時等多久就放棄，這決定了壓力來臨時是快速失敗還是無限堆積。

**詳細解析**：最常見的錯誤是**只設最大連線數而不設等待逾時**——池滿之後請求無限期排隊，表現為「服務沒有報錯但全部卡住」，而且排隊的請求會持續累積直到記憶體爆掉。第二常見的是**最大閒置時間設得比中間設備的逾時長**，症狀是「間歇性的連線重設錯誤」，因為取到的連線其實已經死了；除了調短閒置時間，連線池也應該有**取用前的有效性檢查**。第三是**連線池大小與執行緒池大小不匹配**——連線池遠小於執行緒池時，執行緒會大量卡在等連線上，這時擴大執行緒池反而更糟。這三個問題都很典型，講得出來代表你調過。

**面試回答方式**：給四個參數並說明各自依什麼決定，特別強調最大閒置時間要小於路徑最短逾時。加分點是列出三個典型錯誤：沒設等待逾時導致無限排隊、閒置時間過長導致取到死連線、以及連線池與執行緒池不匹配時擴大執行緒池反而更糟。

### 為什麼有時候換一個負載平衡策略就解決了埠號耗盡？

**核心答案**：因為埠號是**依五元組**區分的——同一個本機埠可以同時用於連往不同的目標 IP 或埠。如果所有請求都打向**單一後端位址**（例如一個 VIP），那麼本機埠就成為唯一的變數，容易耗盡；把流量分散到多個後端 IP 之後，相同的本機埠可以被重複使用，可用組合數立刻放大數倍。

**詳細解析**：這解釋了一個看似違反直覺的現象：**後端擴容之後連線問題反而好轉**，即使原本的瓶頸根本不在後端的處理能力。要注意這只是緩解而非根治——真正的問題仍是連線建立得太頻繁，正確的解法是連線池與 keep-alive。另外在容器環境中還有一個變化：如果客戶端透過服務名稱解析到多個 Pod IP，效果與分散後端相同；但若中間隔著一個做 NAT 的服務閘道，所有連線又會收斂到單一位址，問題就回來了。**理解流量最終收斂在哪一個位址**，是排查這類問題的關鍵視角。

**面試回答方式**：核心是五元組讓相同本機埠可用於不同目標，分散後端就放大了可用組合。點出「後端擴容後連線問題好轉」這個看似違反直覺的現象。加分點是強調這只是緩解、根治要靠連線池，以及在容器環境中要看流量最終收斂到哪個位址。
