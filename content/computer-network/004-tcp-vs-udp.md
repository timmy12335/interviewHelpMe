# 題目

TCP 和 UDP 差在哪？既然 TCP 可靠，為什麼還有那麼多服務用 UDP？

## 核心答案

**TCP 是面向連線的可靠位元組流**——它保證資料**不丟、不重、有序**，代價是要三次握手建立連線、要確認與重傳、要做流量控制與擁塞控制，這些機制都會帶來延遲與開銷。**UDP 是無連線的資料報**——送出去就不管了，不保證送達、不保證順序、也不做擁塞控制，換來的是**極低的延遲與極小的開銷**（標頭只有 8 位元組，TCP 是 20 以上），而且天然支援**廣播與多播**。選 UDP 的判準是：**遲到的資料對我沒有價值，或者我要自己控制重傳策略**。即時語音與影像屬於前者——重傳一個五秒前的音訊封包毫無意義，不如直接跳過；DNS 屬於「一問一答且短小」，用 TCP 建連線的成本高於重問一次；QUIC 與許多遊戲協定屬於後者——它們在 UDP 之上**自己實作可靠性**，因為這樣可以針對場景調整策略，而不必接受 TCP 的通用行為。

## 詳細解析

**TCP 的隊頭阻塞是選 UDP 的重要動機**：TCP 保證**按序交付**，所以一個封包遺失會讓後面已經抵達的資料全部卡住等重傳。對一個同時傳輸多個獨立資源的連線（例如 HTTP/2 的多個串流）來說，這是很不划算的——一個串流的遺失拖累了所有串流。QUIC 選擇建在 UDP 之上，正是為了讓**每個串流獨立處理遺失**，這是 HTTP/3 最核心的改進。

**UDP 不是「不可靠所以品質差」**：它只是**把可靠性的決定權交還給應用層**。應用可以選擇完全不管（監控指標上報，丟幾筆無所謂）、選擇性重傳（影音串流只重傳關鍵影格）、或實作完整的可靠傳輸（QUIC）。TCP 的通用策略對很多場景是「過度保證」，而過度保證的代價是延遲。

**TCP 是位元組流，UDP 是資料報**：這個差別對寫程式的人影響最直接。TCP 沒有訊息邊界——送兩次各 100 位元組，接收端可能一次讀到 200、也可能讀到 60 加 140，所以**應用層必須自己定義邊界**（長度前綴或分隔符），這就是「黏包」問題的根源。UDP 則保留邊界，一次送出對應一次讀取，但**單個資料報過大時會在 IP 層分片**，任一片遺失整個資料報就報廢。

**擁塞控制的公共財問題**：TCP 會在偵測到壅塞時主動退讓，UDP 預設不會。所以大量不受控的 UDP 流量可能擠壓 TCP 流量，造成整體網路品質下降。負責任的 UDP 應用（例如 QUIC）會自己實作擁塞控制，這也是為什麼「用 UDP 就是快」的說法不準確——真正做好的 UDP 應用其實實作了與 TCP 類似的機制，只是更貼合自己的場景。

**選型的實務判準**：需要可靠、有序、且不想自己處理重傳的一般業務通訊，用 TCP（絕大多數情況）。即時性遠比完整性重要、或需要廣播多播，用 UDP。介於中間、想要低延遲又要可靠的，看看能不能直接用 QUIC 這類已經實作好的協定，而不是自己從頭寫一套——**自己在 UDP 上實作可靠傳輸的難度被嚴重低估**，這一句在面試中很值得說。

## 面試回答方式

先給兩者的本質差異——**可靠有序的位元組流 vs 低開銷的資料報**，並直接給出選 UDP 的判準：**遲到的資料沒有價值，或我要自己控制重傳策略**，各舉一個例子（即時語音、QUIC）。接著補上一個關鍵論點：**TCP 的隊頭阻塞**是 HTTP/3 改用 UDP 的核心原因，因為它讓一個封包遺失拖累所有串流。加分點有三個：TCP 是位元組流所以沒有訊息邊界、應用層要自己處理黏包；UDP 不做擁塞控制會擠壓 TCP 流量，所以負責任的 UDP 應用會自己實作；以及誠實表達自己在 UDP 上實作可靠傳輸的難度被低估，能用 QUIC 就不要重造。

## 講稿

TCP 是面向連線的可靠位元組流，保證不丟、不重、有序，代價是握手、確認重傳、流量控制跟擁塞控制，這些都是延遲。UDP 是無連線的資料報，送出去就不管，換來極低的延遲跟很小的開銷。

我判斷要不要用 UDP，看一句話，遲到的資料對我還有沒有價值。即時語音就是典型，重傳一個五秒前的音訊封包毫無意義，不如直接跳過。DNS 也是，一問一答又短，建立連線的成本比重問一次還高。

另外一種情況是我想自己控制重傳策略。QUIC 就是這樣，它建在 UDP 之上自己實作可靠性。原因是 TCP 保證按序交付，一個封包遺失會讓後面已經到的資料全部卡住等重傳。在同時傳很多個獨立串流的時候，這很不划算，一個串流拖累全部。QUIC 讓每個串流獨立處理遺失，這是 HTTP/3 最核心的改進。

還有一個對寫程式很直接的差別，TCP 是位元組流，沒有訊息邊界，所以應用層要自己定長度前綴或分隔符，這就是黏包問題的來源。UDP 則保留邊界。

不過我會誠實說，自己在 UDP 上實作可靠傳輸的難度被嚴重低估，能用現成的 QUIC 就不要重造。

## 常見追問

### DNS 為什麼主要用 UDP，什麼時候會改用 TCP？

**核心答案**：因為 DNS 查詢**短小、一問一答、且重試成本極低**——用 TCP 光是三次握手就多一個往返，比直接重問一次還慢。所以標準做法是先用 UDP。改用 TCP 的情況有兩種：**回應太大放不進單一 UDP 資料報**（回應會被標記為截斷，客戶端改用 TCP 重問），以及**區域傳送**這類需要傳輸大量資料的操作。

**詳細解析**：回應變大的常見原因包括 DNSSEC 的簽章資料、以及一個名稱對應大量記錄。歷史上 UDP 的 DNS 回應有 512 位元組的限制，後來透過擴充機制可以協商更大的尺寸，減少了退回 TCP 的次數，但過大的 UDP 回應又帶來 IP 分片與**放大攻擊**的問題——攻擊者偽造受害者的來源 IP 發出小查詢，讓 DNS 伺服器把大回應打向受害者。這是 UDP 無連線特性被濫用的典型案例，防禦手段包括回應速率限制與來源驗證。能講出這一層，會顯示你理解協定選擇帶來的安全後果。

**面試回答方式**：先給主因（短小、一問一答、重試比握手便宜），再給兩種改用 TCP 的情況。加分點是講 DNS 放大攻擊——偽造來源讓大回應打向受害者，這正是 UDP 無連線特性的代價，並提防禦方向。

### TCP 的可靠是不是代表資料一定不會丟？

**核心答案**：**不是**。TCP 保證的是「**已經被接收端 TCP 確認的資料，會按序交付給應用層**」，但這不等於端到端的業務可靠。應用程式呼叫寫入成功只代表資料進了本機的傳送緩衝區；連線可能在資料真正送達前中斷；即使送達了對端的 TCP，對方的**應用程式也可能還沒讀取就崩潰**。所以業務層面的「確定收到並處理完成」必須靠**應用層的確認**，不能依賴 TCP。

**詳細解析**：這是分散式系統中很重要的一個認知落差。實務上的體現包括：訊息佇列的生產者需要 broker 的應用層 ack 而不是 TCP 的 ack；RPC 需要回應而不只是請求送達；HTTP 的請求送達不代表業務處理成功，所以需要冪等設計來應對重試。另一個相關的細節是**寫入成功不等於送出**——如果對方一直不讀取，接收視窗會歸零，資料就堆在本機緩衝區，此時連線看起來正常但資料實際上沒有前進，這種「假死」需要靠應用層的心跳或逾時才發現。

**面試回答方式**：明確否認，並精確界定 TCP 保證的範圍（已確認的資料按序交付給應用層）。用「對方應用程式讀取前崩潰」說明落差。加分點是連結到訊息佇列與 RPC 需要應用層確認、以及接收視窗歸零造成的假死要靠心跳發現。

### 什麼是可靠 UDP？自己實作要處理哪些問題？

**核心答案**：指在 UDP 之上自行實作可靠傳輸的協定。要處理的問題**幾乎就是 TCP 做過的所有事**：序號與確認、逾時與重傳、亂序重組、去重、流量控制（避免壓垮接收端）、以及**擁塞控制**（避免壓垮網路）。其中擁塞控制最容易被忽略也最難做對——省略它的協定在網路壅塞時不但自己表現差，還會擠壓其他流量。

**詳細解析**：實務上的建議是**盡量不要自己從頭實作**，而是採用已經成熟的方案（QUIC 或現成的可靠 UDP 函式庫），因為這些機制的細節極多、邊界情況難以窮舉，而且錯誤往往只在高延遲或高遺失率的真實網路上才顯現，本地測試完全看不出來。值得自己實作的情況通常是**有非常特殊的需求**——例如遊戲同步只需要「最新狀態送達」而不需要歷史封包，這時用「只重傳最新狀態、舊的直接丟棄」比 TCP 的通用策略好得多。能區分「特殊需求值得自訂」與「一般情況該用現成的」，比單純列出要處理哪些問題更能顯示判斷力。

**面試回答方式**：列出要處理的機制並特別點名擁塞控制最容易被忽略也最有外部影響。加分點是給出明確立場——一般情況用 QUIC 或成熟函式庫，只有像遊戲同步這種「只要最新狀態」的特殊需求才值得自訂，並說明錯誤只在真實網路才顯現。
