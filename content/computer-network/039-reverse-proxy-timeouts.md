# 題目

請求經過 nginx 到後端，有哪些逾時要設？它們該怎麼配合？

## 核心答案

一條請求路徑上有多層逾時，而它們必須從外到內遞減——否則外層先放棄，內層還在做無用功。

**nginx 側的幾個關鍵值**。**`client_header_timeout` 與 `client_body_timeout`**——讀取客戶端請求的逾時；防的是慢速攻擊。**`proxy_connect_timeout`**——與後端建立連線的逾時；應該很短（幾秒），因為連不上通常是立即可知的。**`proxy_send_timeout` 與 `proxy_read_timeout`**——與後端之間傳送與接收的逾時；`read_timeout` 是最常需要調整的（預設 60 秒）。

而配合的原則是「客戶端逾時 > 負載平衡器逾時 > nginx 逾時 > 應用逾時 > 資料庫逾時」——每一層留一點餘裕給下層完成或回報錯誤。

「順序反了」的症狀是「應用日誌顯示成功，而使用者看到 504」——**因為外層已經放棄了。**

## 詳細解析

「逾時的方向搞反是最常見的設定錯誤」：如果應用的逾時是 60 秒而 nginx 的 `proxy_read_timeout` 是 30 秒——那麼在 30 秒時 nginx 回 504 給使用者，而應用還在繼續處理；處理完了寫入資料庫，但沒有人在等那個回應。於是「使用者看到失敗但操作實際成功了」——這在非冪等的操作上會造成重複（使用者重試）。所以逾時的串接不只是體驗問題，也是正確性問題。

「keepalive 到後端」是一個常被遺漏的設定：nginx 預設對後端使用短連線——**每個請求都要重新握手**。設定 `upstream` 區塊中的 `keepalive` 指令（並在 `proxy_set_header` 中設 `Connection ""`）能複用連線——在高 QPS 下這能顯著降低延遲與後端的 TIME_WAIT 數量。這是一個「預設值不適合高流量場景」的例子，而它的改善通常很明顯。

「緩衝的設定影響慢客戶端的處理」：nginx 預設會**緩衝後端的回應**——於是後端可以快速寫完並釋放，而 nginx 慢慢餵給客戶端。這保護了後端不被慢客戶端佔住。但對串流回應（SSE、大檔案）需要關閉緩衝（`proxy_buffering off`）——否則使用者要等全部完成才看到內容。這個「預設對多數場景好、對串流場景壞」的行為，是 SSE 在 nginx 後面「沒有即時輸出」這個經典問題的成因。

**「錯誤的處理與重試」需要謹慎**：`proxy_next_upstream` 決定「什麼情況下試下一台後端」——**預設包含 `error` 與 `timeout`**；而對非冪等的請求（POST），重試可能造成重複執行。所以應該明確設定「只對安全的方法重試」或者依賴應用層的冪等。

## 面試回答方式

先給幾個關鍵逾時與各自的用途，再給**從外到內遞減**的配合原則，並指出順序反了的症狀是「應用顯示成功而使用者看到 504」。加分點有四個：逾時方向搞反不只是體驗問題也是正確性問題——使用者看到失敗但操作實際成功，在非冪等操作上會造成重複；**keepalive 到後端常被遺漏**——預設是短連線，設定後能顯著降低延遲與 TIME_WAIT；緩衝的預設對串流場景是壞的——這是 SSE 在 nginx 後面沒有即時輸出的經典成因；以及**`proxy_next_upstream` 對非冪等請求的重試風險**。

## 講稿

一條請求路徑上有多層逾時，而它們必須從外到內遞減，否則外層先放棄、內層還在做無用功。

nginx 這邊有幾個關鍵值。讀取客戶端請求的逾時防的是慢速攻擊。跟後端建立連線的逾時應該很短，因為連不上通常立即可知。而讀取後端回應的逾時是最常需要調整的。

配合的原則是客戶端大於負載平衡器大於代理大於應用大於資料庫，每一層留一點餘裕給下層完成或回報錯誤。

方向搞反是最常見的設定錯誤，而它的症狀很典型。應用日誌顯示成功，而使用者看到閘道逾時。因為代理在三十秒就放棄了，而應用還在繼續處理，處理完寫入資料庫但沒有人在等那個回應。於是使用者看到失敗但操作實際成功了，在非冪等的操作上會造成重複。所以逾時的串接不只是體驗問題，也是正確性問題。

還有兩個常被遺漏的設定。一是到後端的長連線，預設是短連線，每個請求都要重新握手。二是回應緩衝，預設開啟對多數場景是好的，但對串流回應要關掉，否則使用者要等全部完成才看到內容。

## 常見追問

### 502、504、499 分別代表什麼？

**核心答案**：三個都是 nginx 常見的錯誤，但成因完全不同。**502 Bad Gateway**——連到後端了但收到無效的回應（後端崩潰、回傳了損壞的資料、或者連線被重設）。**504 Gateway Timeout**——**後端沒有在逾時內回應**（後端太慢或卡住）。**499**——這是 nginx 自訂的碼，表示「客戶端在收到回應前就關閉了連線」（使用者取消、或者上游的逾時比 nginx 短）。

**詳細解析**：**「499 是一個被誤解的訊號」**：它不代表你的服務有問題——**而是客戶端不等了**。**大量的 499 通常指向三種情況**：**上游的逾時設得比 nginx 短**（於是它先放棄）、**使用者主動取消**（例如在載入時關閉頁面）、或者你的服務確實太慢導致客戶端超時。區分它們的方法是看「499 的請求耗時分布」——如果集中在某個固定值（例如 3 秒），那幾乎確定是上游的逾時設定。**而 502 與 504 的區分也很有診斷價值**：502 通常指向後端的崩潰或重啟（去看後端的日誌與 OOM 記錄）；504 指向後端的效能問題（去看慢查詢與資源使用）——**兩者的排查方向完全不同。**

**面試回答方式**：給三個碼各自的成因。核心加分點是**499 是一個被誤解的訊號**——它不代表你的服務有問題而是客戶端不等了，並給三種情況與區分方法（看耗時分布，集中在固定值就是上游的逾時設定）。收在**502 與 504 的排查方向完全不同**：502 去看後端的崩潰與 OOM，504 去看慢查詢與資源使用。

### 反向代理該不該做重試？

**核心答案**：只對安全的方法（GET、HEAD）與明確的失敗（連線被拒、後端已關閉）重試——而對逾時與非冪等的方法要謹慎。因為「逾時」意味著「請求可能已經在處理」——**重試就是重複執行**。理想的做法是「讓應用層的冪等保證重試安全」，然後才放心地在代理層重試。

**詳細解析**：「連線被拒與逾時的差別」在重試決策上很關鍵：連線被拒（`ECONNREFUSED`）——明確表示請求沒有被處理，重試絕對安全；而逾時——請求可能正在處理、可能已經完成只是回應慢。所以「對連線失敗重試、對逾時不重試」是一個保守但正確的預設。而如果應用是冪等的，就可以放寬到對逾時也重試——但那需要應用層明確保證，而非代理層假設。這個「重試的安全性取決於失敗的階段」的判斷，與分散式系統中「不確定就查詢而非猜測」是同一個原則——而它在代理層的體現是「預設保守，由應用層明確放寬」。

**面試回答方式**：給重試的邊界（安全方法與明確失敗）並說明逾時意味著請求可能已在處理。核心加分點是連線被拒與逾時的差別在重試決策上很關鍵——前者明確沒被處理所以重試絕對安全，後者可能正在處理，所以「對連線失敗重試、對逾時不重試」是保守但正確的預設。收在原則：重試的安全性取決於失敗的階段，而在代理層的體現是「預設保守，由應用層明確放寬」。

### 多層代理下怎麼追蹤真實的客戶端 IP？

**核心答案**：用 `X-Forwarded-For` 標頭，而它是一個逗號分隔的鏈：每一層代理把它看到的來源 IP 追加上去。取真實 IP 的正確做法不是「取第一個」——因為客戶端可以偽造這個標頭；而是「從右往左數，跳過你信任的代理數量」。**nginx 的 `real_ip` 模組與 `set_real_ip_from` 正是做這件事。**

**詳細解析**：「取第一個是一個常見且危險的錯誤」：攻擊者可以在自己的請求中設 `X-Forwarded-For: 1.2.3.4`——於是所有基於 IP 的限流、封鎖、地理判斷都能被繞過。正確的做法要求你知道「有幾層可信的代理」——而那個數字必須被明確設定而非猜測。在雲端環境中，負載平衡器通常會提供一個「它自己加上的、可信的」標頭（例如 AWS 的 `X-Forwarded-For` 由 ALB 管理）——於是可以信任最後一個由它加上的值。而新的標準 `Forwarded` 標頭提供了更結構化的格式（包含 proto、host、for），但採用度仍然不如舊的。這個「安全性依賴於正確的信任邊界設定」的模式，在很多代理相關的問題中都出現——而錯誤的預設（信任所有輸入）幾乎總是危險的。

**面試回答方式**：給標頭的結構與正確做法是從右往左跳過信任的代理數量。核心加分點是取第一個是常見且危險的錯誤——攻擊者可以偽造，於是所有基於 IP 的限流、封鎖、地理判斷都被繞過，而正確做法要求明確設定可信代理的層數。收在雲端的實務與原則：負載平衡器提供它自己加上的可信值，而「安全性依賴於正確的信任邊界設定」在很多代理問題中都出現。
