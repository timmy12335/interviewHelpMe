# 題目

`Cache-Control`、`ETag`、`Last-Modified` 各自做什麼？怎麼配合？

## 核心答案

**HTTP 快取分成兩層，而它們的成本差一個數量級。**

**強快取（不發請求）**——**由 `Cache-Control: max-age=N` 或 `Expires` 控制**；**在有效期內瀏覽器直接用本地副本，完全不聯網**。**這是最快的，因為它省下了整個往返。**

**協商快取（發請求但可能不傳內容）**——**過期後，瀏覽器帶上 `If-None-Match: <etag>` 或 `If-Modified-Since: <date>` 詢問伺服器**；**沒變的話回 `304 Not Modified`（不含 body），有變才回 200 加新內容**。**它省下的是傳輸量而非往返。**

**配合的標準做法是「內容雜湊命名 + 長期強快取」**：**靜態資源的檔名包含內容的雜湊（`app.a3f9b2.js`）**——**於是可以設 `max-age=31536000, immutable`（一年）**；**內容變了就是新的檔名，天然不需要失效**。**而 HTML 本身用短快取或協商快取，因為它引用了那些帶雜湊的檔名。**

## 詳細解析

**「內容雜湊命名解決了快取失效這個經典難題」**：傳統的做法是「設短的 max-age 讓它盡快過期」——**於是每次都要發請求確認，浪費往返**；**或者「設長的 max-age 但改版時使用者拿到舊的」**。**而雜湊命名讓「內容」與「URL」一一對應**——**於是快取永遠有效（同一個 URL 的內容永不改變），而更新就是引用一個新的 URL**。**這個「讓資源不可變」的設計把一個困難的失效問題轉換成了一個簡單的命名問題。**

**「`ETag` 與 `Last-Modified` 的差別」**：`Last-Modified` 是秒級的時間戳——**於是「一秒內的多次修改」無法區分**；**而且在多台伺服器上，同一個檔案的修改時間可能不同（部署造成）**。**`ETag` 是內容的識別碼（通常是雜湊或版本號），更精確**——**但計算它需要讀取內容**。**兩者可以同時提供，而 `ETag` 的優先級較高。**

**「`Cache-Control` 的常見指令」需要區分清楚**：`no-cache` **不是「不快取」**——**它是「可以快取但每次都要協商」**；**真正的不快取是 `no-store`**。**這個命名造成的混淆極為常見**。**`private` 表示只有瀏覽器可以快取（CDN 不行），`public` 表示中間節點也可以**——**對含使用者資料的回應，設錯這一項會造成嚴重的資料洩漏**。

**「快取的失效比設定更難」**：一旦一個資源帶著長 max-age 被快取——**在它過期前你無法讓瀏覽器重新取得**。**所以對「可能需要緊急更新」的資源（例如設定檔），應該用短快取或協商快取**——**而這正是「HTML 用短快取、靜態資源用長快取」這個模式的理由。**

## 面試回答方式

先分兩層（強快取省往返、協商快取省傳輸量）並說明各自的控制方式，再給**內容雜湊命名加長期強快取**這個標準做法。加分點有四個：**內容雜湊解決了快取失效這個經典難題**——**它把困難的失效問題轉換成簡單的命名問題**；**`ETag` 與 `Last-Modified` 的差別**（秒級精度、多機時間不一致 vs 需要讀取內容計算）；**`no-cache` 不是「不快取」而是「每次都要協商」**，**真正的不快取是 `no-store`**，**這個命名造成的混淆極為常見**；以及**`private` 與 `public` 設錯會造成資料洩漏**。

## 講稿

HTTP 快取分兩層，而它們的成本差一個數量級。

強快取是完全不發請求，在有效期內直接用本地副本。這是最快的，因為省下了整個往返。協商快取是發請求但可能不傳內容，帶上識別碼詢問伺服器，沒變就回三零四，它省下的是傳輸量而不是往返。

配合的標準做法是內容雜湊命名加長期強快取。靜態資源的檔名包含內容雜湊，於是可以設一年的有效期加上不可變標記。內容變了就是新的檔名，天然不需要失效。

我覺得這個設計很優雅，因為它解決了快取失效這個經典難題。傳統做法要嘛設短有效期浪費往返，要嘛設長有效期但改版時使用者拿到舊的。而雜湊命名讓內容跟網址一一對應，快取永遠有效，更新就是引用一個新網址。它把一個困難的失效問題轉換成了一個簡單的命名問題。

還有一個極常見的混淆要澄清。不快取這個指令的名字騙人，它其實是可以快取但每次都要協商。真正的不快取是另一個指令。而公開跟私有這兩個值如果設錯，含使用者資料的回應可能被中間節點快取，那是嚴重的資料洩漏。

## 常見追問

### CDN 的快取與瀏覽器快取怎麼協調？

**核心答案**：**用 `s-maxage` 分別控制**。`Cache-Control: max-age=60, s-maxage=3600`——**瀏覽器快取 60 秒，而 CDN 這類共享快取保留一小時**。**這讓「使用者能較快看到更新」與「回源壓力低」同時成立**。**再配合 CDN 的主動清除（purge），就能在需要時立即更新。**

**詳細解析**：**「CDN 可以被主動清除而瀏覽器不能」是這個分工的根本理由**：你控制 CDN——**發現內容錯了可以立刻清除**；**而已經進了使用者瀏覽器的快取，在過期前你無能為力**。**所以「瀏覽器的 max-age 應該保守，CDN 的可以激進」**。**這也解釋了一個常見的模式：把 HTML 的瀏覽器快取設得很短甚至 no-cache，而在 CDN 上快取較久並用 purge 控制**——**於是既有 CDN 的效能，又保留了立即更新的能力**。**而 `stale-while-revalidate` 進一步改善了體驗**：**過期後先回傳舊的（使用者不用等），同時背景更新**——**這在可以容忍短暫陳舊的場景中幾乎是免費的改善**。

**面試回答方式**：給 `s-maxage` 的分別控制並說明它讓兩個目標同時成立。核心加分點是**CDN 可以被主動清除而瀏覽器不能**這個根本理由——**所以瀏覽器的 max-age 應該保守而 CDN 的可以激進**，並給出「HTML 瀏覽器端短、CDN 端長加 purge」的模式。收在 **`stale-while-revalidate`**：**過期後先回舊的同時背景更新，在可容忍短暫陳舊時幾乎是免費的改善**。

### 為什麼有時候改了程式碼使用者還是看到舊版？

**核心答案**：**按可能性依序檢查五處**。**瀏覽器快取**（強快取未過期）、**CDN 快取**（未清除或清除未生效）、**中間代理的快取**（企業網路的透明代理）、**Service Worker 的快取**（PWA 常見且最容易被忽略）、**以及建置產物本身沒更新**（部署問題）。

**詳細解析**：**「Service Worker 是最容易被忽略的一層」**：它在瀏覽器與網路之間攔截請求並可能回傳自己的快取——**於是即使清除了瀏覽器快取、CDN 也更新了，使用者仍然看到舊版**。**而它的更新有自己的生命週期（安裝、等待、啟用）**——**一個寫得不好的 Service Worker 可能讓使用者永遠停在舊版本**。**所以有 Service Worker 的專案必須有明確的更新策略**（例如檢測到新版本時提示使用者重新載入）。**另一個實用的診斷技巧是「用無痕視窗或不同的瀏覽器測試」**——**如果那裡是新版，問題就在客戶端的快取層**；**如果那裡也是舊版，問題在伺服器或 CDN**。**這個二分能在幾秒內縮小一半的範圍。**

**面試回答方式**：給五處按可能性排序的檢查。核心加分點是**Service Worker 最容易被忽略**——**它在瀏覽器與網路之間攔截，即使清了瀏覽器快取與 CDN 也可能看到舊版**，**而寫得不好的可能讓使用者永遠停在舊版本**。收在診斷技巧：**用無痕視窗測試**——**那裡是新版就是客戶端快取，那裡也舊就是伺服器或 CDN**，**這個二分能在幾秒內縮小一半範圍**。

### API 的回應該不該快取？

**核心答案**：**多數不該，但有例外**。**使用者相關的資料**——**不該被共享快取快取（設 `private` 或 `no-store`）**。**而「所有人看到的都一樣且變化不頻繁」的資料**（設定、商品目錄、公開的統計）——**快取的收益很大，應該設 `public` 加合理的 max-age**。**判斷的關鍵是「這個回應對不同使用者是否相同」與「陳舊多久是可以接受的」。**

**詳細解析**：**「用 `Vary` 標頭處理依賴請求標頭的回應」是一個常被忽略的機制**：如果回應內容依賴 `Accept-Language` 或 `Authorization`——**必須用 `Vary: Accept-Language` 告訴快取「這個標頭不同就是不同的回應」**；**否則快取會把一個使用者的回應給另一個**。**而 `Vary: Authorization` 實際上讓快取幾乎失效（每個 token 一份）**——**所以更好的做法是對需要認證的回應直接設 `private`**。**這類「快取的正確性問題」比效能問題嚴重得多**——**因為它可能造成資料洩漏，而且症狀是間歇性的（只在快取命中時發生）**，**極難重現與診斷**。**所以「不確定的時候選擇不快取」在 API 上是正確的預設。**

**面試回答方式**：給判斷關鍵（**對不同使用者是否相同、陳舊多久可接受**）與兩類的處理。核心加分點是 **`Vary` 標頭**：**回應依賴某個請求標頭時必須宣告，否則快取會把一個使用者的回應給另一個**，並指出 **`Vary: Authorization` 讓快取幾乎失效，所以認證的回應直接設 private 更好**。收在判斷：**快取的正確性問題比效能問題嚴重，症狀間歇且極難重現**，**所以「不確定時選擇不快取」在 API 上是正確的預設**。
