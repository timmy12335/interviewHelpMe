# 題目

瀏覽器怎麼判斷一張憑證可不可信？中間人攻擊在什麼情況下會成功？

## 核心答案

信任建立在一條**信任鏈**上：伺服器憑證由中介憑證機構簽發，中介又由根憑證機構簽發，而根憑證預先內建在作業系統或瀏覽器中。驗證時客戶端沿著這條鏈往上驗簽章，直到碰到自己信任的根為止；同時還要檢查**網域是否相符**、**是否在有效期內**、以及**有沒有被撤銷**。任何一環失敗都應該中止連線。中間人攻擊要成功，攻擊者必須讓客戶端接受一張自己控制私鑰的憑證，途徑有三：客戶端的信任存放區被植入了攻擊者的根憑證（企業的流量檢查設備、惡意軟體都是這樣做的）、**客戶端根本沒有正確驗證**（關掉驗證、只驗簽章不驗網域，這是自行實作客戶端時的經典漏洞）、或是**憑證機構本身被攻破或誤簽**。所以 HTTPS 的安全性其實建立在「**客戶端正確驗證**」加上「**憑證機構值得信任**」這兩個前提上，任何一個不成立，加密就只是在保護一條通往攻擊者的通道。

## 詳細解析

信任鏈的層次設計是有理由的：根憑證的私鑰極度敏感，通常離線保存，所以不直接簽發終端憑證，而是簽發少數中介憑證，由中介去簽發大量的伺服器憑證。好處是中介出事時可以撤銷中介而不必動搖根，把影響範圍縮小。實務上常見的設定錯誤是伺服器沒有送出完整的中介憑證——桌面瀏覽器可能因為已快取過中介而顯示正常，但某些客戶端（行動裝置、命令列工具、其他語言的 HTTP 函式庫）會驗證失敗，症狀是「有些人可以有些人不行」，非常難查。

**撤銷機制長期是弱點**：憑證外洩後要讓它失效，早期靠撤銷清單（清單很大、更新不即時）與線上查詢（每次連線多一次對第三方的往返，而且第三方掛掉時多數客戶端選擇放行而非拒絕，等於防護形同虛設）。改良方向是 **OCSP 裝訂**——由伺服器自己定期取得撤銷狀態的簽章證明並在握手時一併送出，省掉客戶端的額外查詢。更根本的緩解是**縮短憑證有效期**，讓外洩的憑證自然失效的時間變短，這也是憑證有效期逐年縮短並走向自動化續期的原因。

憑證透明度讓誤簽可以被發現：憑證機構誤簽或被攻破時，過去很難察覺。憑證透明度要求簽發的憑證被記錄到公開且可稽核的日誌中，網域擁有者可以監控「有沒有人替我的網域簽發了我不知道的憑證」。這把「防止誤簽」的問題轉成「**誤簽一定會被發現**」，是很聰明的設計取向——當完全防止不可行時，改為保證可偵測。

企業流量檢查是合法的中間人：許多公司在網路出口部署解密設備，並把設備的根憑證推送到員工的機器上，如此就能解密並檢查 HTTPS 流量。技術上這與攻擊完全相同，差別只在信任是被明確授予的。這也解釋了為什麼**憑證釘選**的應用在企業環境會失敗——它刻意拒絕了「信任存放區裡的任何根」這件事。

**HSTS 防的是降級**：即使憑證驗證正確，攻擊者仍可能在使用者第一次以 HTTP 連線時攔截並阻止跳轉到 HTTPS。**HSTS** 讓瀏覽器記住「這個網域只能用 HTTPS」，之後即使使用者輸入 HTTP 也直接改用 HTTPS，不給攔截機會；預載清單更進一步，讓第一次連線就受保護。這是對「首次連線」這個薄弱點的補強。

## 面試回答方式

先講**信任鏈**的結構（伺服器憑證、中介、內建的根）與驗證要檢查的**三件事**（簽章鏈、網域相符、有效期與撤銷）。接著直接回答中間人什麼時候會成功——**三條途徑**：信任存放區被植入、客戶端沒正確驗證、憑證機構被攻破，並歸納成「HTTPS 的安全建立在客戶端正確驗證加上憑證機構值得信任」這兩個前提。加分點有三個：伺服器漏送中介憑證造成「有些客戶端能連有些不能」這種難查的症狀；撤銷機制的弱點與「縮短有效期」這個更根本的緩解；以及憑證透明度把問題從「防止誤簽」轉成「誤簽一定會被發現」。

## 講稿

信任建立在一條鏈上。伺服器憑證由中介機構簽發，中介由根機構簽發，而根憑證是預先內建在作業系統或瀏覽器裡的。驗證的時候客戶端沿著這條鏈往上驗簽章，直到碰到自己信任的根。同時還要檢查網域相不相符、有沒有過期、有沒有被撤銷。

中間人要成功，必須讓客戶端接受一張攻擊者自己有私鑰的憑證。路徑有三條。第一是客戶端的信任存放區被植入了攻擊者的根憑證，企業的流量檢查設備跟惡意軟體都是這樣做的。第二是客戶端根本沒有正確驗證，像是關掉驗證，或者只驗了簽章卻沒驗網域。第三是憑證機構本身被攻破或誤簽。

所以 HTTPS 的安全其實建立在兩個前提上，客戶端有正確驗證，而且憑證機構值得信任。任何一個不成立，加密就只是在保護一條通往攻擊者的通道。

實務上我遇過一個很難查的問題，伺服器沒有送出完整的中介憑證。桌面瀏覽器因為快取過中介所以看起來正常，但行動裝置或命令列工具會失敗，症狀就是有些人可以有些人不行。

## 常見追問

### 憑證撤銷為什麼那麼難做？

**核心答案**：因為兩種傳統機制都有結構性問題。**撤銷清單**要下載整份清單，隨著簽發量成長變得龐大且更新不即時。**線上查詢**每次連線都要對憑證機構多一次往返，增加延遲，而且第三方不可用時多數客戶端選擇放行（否則憑證機構一掛，全網站都連不上），這使得防護在最需要的時候形同虛設。攻擊者只要讓查詢失敗，撤銷就無效了。

**詳細解析**：改良方向有兩條。**OCSP 裝訂**把查詢的責任從客戶端移到伺服器——伺服器定期取得帶簽章與時效的狀態證明，握手時一併送出，客戶端不必額外連線第三方，也消除了隱私問題（憑證機構不再知道誰在造訪哪個網站）。另一條更根本的路是縮短憑證有效期並全面自動化續期——如果憑證只有幾十天有效期，外洩的影響窗口自然很短，撤銷的重要性就下降了。這是「與其把撤銷做好，不如讓憑證本身短命」的思路轉換，也是目前產業實際走的方向。能講出這個轉向，比只描述兩種機制有價值。

**面試回答方式**：講清兩種傳統機制各自的結構性問題，特別是「查詢失敗時放行」讓防護失效這一點。給出兩條改良路徑，並強調「縮短有效期」是思路的轉換而非技術改良。加分點是提到 OCSP 裝訂同時解決了隱私問題。

### 憑證釘選該不該用？

**核心答案**：只在特定場景值得，而且要非常小心。它讓客戶端只接受特定的憑證或公鑰，即使系統信任存放區中有其他受信任的根也拒絕——這能防禦「憑證機構被攻破」與「信任存放區被植入」兩種攻擊，適合金融類行動應用這種高價值目標。代價是**憑證輪替變得危險**：釘選的憑證更換時，還沒更新版本的客戶端會全面無法連線，而行動應用的更新率永遠不是百分之百。

**詳細解析**：安全的做法是**釘選公鑰而非憑證**（續期時沿用同一組金鑰就不受影響）、**同時釘選一組備用金鑰**（主金鑰出事時可以切換）、並且**設定合理的釘選有效期**避免永久鎖死。網頁上曾有對應的機制，但因為誤設造成網站長期無法存取的風險太高而被淘汰，這件事本身就說明了它的危險性。實務建議是：除非你的威脅模型明確包含憑證機構被攻破，否則正確地做好標準驗證加上憑證透明度監控是更務實的選擇。

**面試回答方式**：給出明確立場——只在高價值目標值得，並講清風險（輪替時無法連線、更新率不是百分百）。給三個安全實踐（釘選公鑰、備用金鑰、有效期）。加分點是提到網頁版的對應機制因為誤設風險太高而被淘汰，並建議多數情況做好標準驗證加透明度監控就夠。

### 自簽憑證在內部系統要怎麼正確使用？

**核心答案**：建立自己的內部憑證機構，把內部根憑證分發到所有客戶端的信任存放區，再由它簽發各服務的憑證。不要用「關閉憑證驗證」或「接受任何憑證」來解決——那等於在內網放棄了所有身分保證，而內網並不是安全的（橫向移動、被入侵的機器、內部惡意行為都存在）。

**詳細解析**：實務上的完整做法包括：把內部根憑證的分發納入機器的初始化流程（設定管理、容器映像檔），讓新機器自動信任；為服務憑證建立**自動簽發與續期**機制，避免有效期到了才手動處理；以及**憑證只包含必要的網域**，避免一張萬用憑證覆蓋整個內網（一旦外洩影響範圍極大）。在容器與微服務環境中，這套需求通常由服務網格或專門的憑證管理元件承擔，並且會做到**雙向驗證**——不只客戶端驗伺服器，伺服器也驗客戶端，這是零信任架構的基礎。能講到雙向驗證與自動續期，會顯示你想的是可維運的系統而不只是讓連線通過。

**面試回答方式**：明確反對關閉驗證，給出正確做法（內部憑證機構加上根憑證分發）。列出三個實務要點：分發納入初始化流程、自動簽發續期、憑證範圍最小化。加分點是提到服務網格承擔這件事、以及雙向驗證是零信任的基礎。
