# 題目

TLS 1.3 相比 1.2 改了什麼？0-RTT 為什麼有爭議？

## 核心答案

**三個層面的改進。**

**握手變快**——**從 2-RTT 降到 1-RTT**。做法是**客戶端在第一個訊息中就猜測伺服器會選的金鑰交換參數並直接送出自己的公鑰**——**猜對了（多數情況）就一次往返完成**。**而恢復連線可以做到 0-RTT。**

**演算法大幅精簡**——**移除了所有不提供前向保密的金鑰交換（RSA 金鑰傳輸）、移除了 CBC 模式與 RC4、移除了壓縮**。**於是「設定錯誤導致不安全」的可能性大幅降低**——**這是一個「用減法提升安全性」的設計。**

**握手的更多部分被加密**——**1.2 中憑證是明文傳輸的（於是中間人能看到你連的是哪個網站）**；**1.3 把憑證也加密了**（**雖然 SNI 仍然明文，需要 ECH 才能解決**）。

**0-RTT 的爭議在於「重放」**：**0-RTT 的資料無法被伺服器驗證是否為重送**——**於是只能用於冪等的請求，而這個限制必須由應用層保證。**

## 詳細解析

**「用減法提升安全性」是 TLS 1.3 最值得學習的設計哲學**：1.2 支援大量的演算法組合——**於是「設定出一個不安全的組合」很容易，而且過去十幾年的攻擊多數利用的正是那些遺留的弱選項**（BEAST、POODLE、Lucky13 都與 CBC 有關）。**1.3 直接移除了所有有疑慮的選項**——**於是「預設就是安全的，而且沒有辦法設定成不安全」**。**這個「減少可設定的維度來消除錯誤設定」的思路，在很多安全系統的設計中都適用**——**因為多數的安全事故來自錯誤設定而非演算法本身被破解**。

**「前向保密（forward secrecy）成為強制」的意義**：在 1.2 的 RSA 金鑰傳輸模式下，**伺服器的私鑰洩漏之後，攻擊者能解密所有錄下的歷史流量**；**而在 ECDHE 下，每次連線用臨時的金鑰**——**私鑰洩漏只影響未來的連線（用於身份驗證），已錄下的流量仍然無法解密**。**這對「長期錄製流量等待未來破解」的攻擊模型是一個根本的防禦。**

**「0-RTT 的重放問題」有具體的緩解但無法根除**：伺服器可以維護一個「已見過的 0-RTT 資料」的記錄並拒絕重複——**但那在多台伺服器的叢集中需要共享狀態，成本高**；**而且記錄的保留時間有限（重放窗口）**。**所以實務上的標準做法是「只允許冪等的方法走 0-RTT」**——**CDN 通常預設只對 GET 啟用**。**而應用層仍然需要注意：一個看起來冪等的 GET 如果有副作用（例如「查看即扣點數」），就會出問題。**

**「TLS 的效能影響」在今天主要在握手而非傳輸**：對稱加密有硬體加速（AES-NI），吞吐的影響很小——**而握手的成本（非對稱運算加往返）才是主要的**。**所以「連線復用」是 TLS 效能最重要的優化**——**這也是為什麼 keep-alive 與連線池在 HTTPS 環境中比在明文下更有價值。**

## 面試回答方式

先給三個層面的改進（握手變快、演算法精簡、更多部分加密）並說明 **0-RTT 的爭議在重放**。加分點有四個：**「用減法提升安全性」是最值得學習的設計哲學**——**過去的攻擊多數利用遺留的弱選項，而 1.3 讓「沒有辦法設定成不安全」**，**因為多數安全事故來自錯誤設定而非演算法被破解**；**前向保密成為強制**——**對「長期錄製流量等待未來破解」的攻擊模型是根本防禦**；**0-RTT 的重放有緩解但無法根除**，**所以只對冪等方法啟用，而應用層要注意「看起來冪等但有副作用」的 GET**；以及**TLS 的效能影響主要在握手而非傳輸**，**所以連線復用是最重要的優化**。

## 講稿

有三個層面的改進。

握手從兩次往返降到一次，做法是客戶端在第一個訊息中，就猜測伺服器會選的金鑰交換參數並直接送出公鑰。演算法大幅精簡，移除了所有不提供前向保密的金鑰交換、移除了有問題的加密模式跟壓縮。還有握手的更多部分被加密，包括憑證。

我覺得第二點是最值得學習的設計哲學，用減法提升安全性。一點二支援大量的演算法組合，於是設定出一個不安全的組合很容易，而過去十幾年的攻擊多數利用的正是那些遺留的弱選項。一點三直接移除了所有有疑慮的選項，於是預設就是安全的，而且沒有辦法設定成不安全。這個減少可設定維度來消除錯誤設定的思路很多地方都適用，因為多數安全事故來自錯誤設定而不是演算法被破解。

零次往返的爭議在於重放。那些資料無法被驗證是否為重送，伺服器可以維護記錄拒絕重複，但在多台的叢集中需要共享狀態，成本高。所以實務上只允許冪等的方法走這條路。而應用層仍要注意，一個看起來冪等的請求如果有副作用就會出問題。

## 常見追問

### SNI 洩漏是什麼問題？ECH 怎麼解決？

**核心答案**：**SNI（伺服器名稱指示）是客戶端在 TLS 握手中告訴伺服器「我要連哪個網域」**——**因為一個 IP 可能託管多個網站**。**但它在 TLS 1.3 中仍然是明文的**——**於是中間人（ISP、防火牆）能知道你在訪問哪個網站，即使內容是加密的**。**ECH（Encrypted Client Hello）把整個 ClientHello 加密**——**用一個從 DNS 取得的公鑰加密，於是 SNI 也被保護。**

**詳細解析**：**「ECH 需要 DNS 的配合」是它部署的關鍵難點**：客戶端需要先從 DNS 取得伺服器的 ECH 公鑰——**而如果 DNS 查詢本身是明文的（傳統 DNS），那個查詢就洩漏了你要連哪個網域**。**所以 ECH 實際上需要與 DoH 或 DoT（加密的 DNS）一起使用才有意義**——**這是一個「隱私保護必須端到端才有效」的例子**。**而它也面臨與 QUIC 類似的部署阻力**：**一些國家與企業依賴 SNI 做流量過濾**——**於是 ECH 的普及在某些地區受到主動的阻礙**。**這說明了技術的部署不只是技術問題，也涉及不同方的利益衝突。**

**面試回答方式**：給 SNI 的用途與它明文帶來的洩漏，並說明 ECH 的機制。核心加分點是**ECH 需要 DNS 的配合**——**如果 DNS 查詢是明文的，那個查詢本身就洩漏了目標**，**所以它必須與加密 DNS 一起使用才有意義**，**這是「隱私保護必須端到端才有效」的例子**。收在部署現實：**一些國家與企業依賴 SNI 做過濾，於是普及受到主動阻礙**——**技術的部署不只是技術問題**。

### mTLS 什麼時候該用？

**核心答案**：**當「伺服器也需要驗證客戶端的身份」且客戶端數量可控時**。典型場景是**服務之間的通訊**（零信任網路）、**以及需要強身份保證的 API**（金融、醫療）。**相比帳密或 API key，憑證的優勢是「私鑰不會在網路上傳輸」與「可以用憑證鏈做集中的信任管理」**。**代價是憑證的簽發、輪換、與撤銷是一套完整的基礎設施。**

**詳細解析**：**「憑證的生命週期管理是 mTLS 的主要成本」**：每個客戶端需要一張憑證——**而它們會過期、會需要輪換、會需要在洩漏時被撤銷**。**手動管理在幾十個客戶端時就已經很痛苦**。**所以 mTLS 的實用性高度依賴自動化**：**SPIFFE/SPIRE 這類工作負載身份框架、或者 service mesh 內建的憑證管理（Istio 自動為每個 Pod 簽發並輪換短期憑證）**——**它們讓憑證的生命週期完全自動化，於是 mTLS 從一個運維負擔變成一個透明的能力**。**這也解釋了為什麼「mTLS 在 service mesh 普及之後才真正被廣泛採用」**——**不是因為技術變了，而是因為管理成本被自動化消除了**。

**面試回答方式**：給適用場景與優勢（私鑰不傳輸、集中的信任管理），並指出**代價是完整的憑證基礎設施**。核心加分點是**憑證的生命週期管理是主要成本**——**幾十個客戶端時手動管理就已經很痛苦**，**所以實用性高度依賴自動化**（SPIFFE、service mesh 的自動簽發輪換）。收在觀察：**mTLS 在 service mesh 普及之後才被廣泛採用，不是因為技術變了而是管理成本被自動化消除了**。

### TLS 握手失敗怎麼排查？

**核心答案**：**用 `openssl s_client -connect host:443 -servername host`**——**它會顯示完整的握手過程、憑證鏈、以及失敗的具體階段**。**常見的原因依序是**：**憑證過期**、**憑證鏈不完整（缺中間憑證）**、**主機名不匹配**、**協定或加密套件不相容（一方太舊）**、**以及客戶端的信任庫沒有那個根憑證**。

**詳細解析**：**「憑證鏈不完整」是最常見也最容易誤診的一種**：症狀是「瀏覽器能開但 curl 或某些客戶端失敗」——**因為瀏覽器會自動從網路補齊缺失的中間憑證（AIA fetching），而多數程式庫不會**。**所以「在瀏覽器測沒問題」不能作為憑證設定正確的證明**。**驗證的方法是用 `openssl s_client` 看回傳的憑證鏈是否完整，或者用 SSL Labs 這類線上工具**。**而修正的方法是「在伺服器設定中提供完整的鏈（葉憑證加所有中間憑證，但不含根）」**。**這個問題在更換憑證後特別容易發生**——**因為新的憑證可能有不同的中間憑證，而部署時只換了葉憑證**。

**面試回答方式**：給主要工具與常見原因的排序。核心加分點是**憑證鏈不完整最常見也最容易誤診**——**瀏覽器會自動補齊中間憑證而多數程式庫不會**，**所以「在瀏覽器測沒問題」不能作為設定正確的證明**。收在修正與高發時機：**在伺服器提供完整的鏈（葉加中間但不含根）**，**而這個問題在更換憑證後特別容易發生，因為新憑證可能有不同的中間憑證而部署時只換了葉憑證**。
