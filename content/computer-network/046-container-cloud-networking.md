# 題目

容器化之後多了哪些網路層的問題？

## 核心答案

多了幾層抽象，而每一層都可能是問題的來源。

**網路命名空間**——**每個容器有自己的網路堆疊**；於是「在主機上能連但在容器裡不能」是一個常見的情況，而排查需要進入容器的命名空間。

**額外的封裝與轉換**——**overlay 網路（VXLAN）的封裝讓 MTU 減少**；於是「小封包通得過、大封包卡住」這個經典症狀在容器環境中特別常見。

**NAT 與轉發規則**——**Service 的虛擬 IP、Pod 的 SNAT、以及各種 iptables 或 eBPF 規則**；它們讓「封包實際走了什麼路徑」變得不直觀。

**以及雲端的隱含限制**——每個實例的頻寬、每秒封包數、連線追蹤表大小、以及安全群組的規則數量上限。

排查的關鍵是「知道有哪些層，並能逐層驗證」——而不是把所有問題都當成應用問題。

## 詳細解析

「MTU 問題在容器環境中特別常見且症狀誤導」：overlay 的封裝讓每個封包多出約 50 位元組——如果容器內的 MTU 仍然是 1500，那麼滿載的封包在封裝後會超過底層網路的 MTU；而如果路徑上的 ICMP「需要分片」訊息被防火牆丟棄，路徑 MTU 發現就失效了。症狀是「小請求正常、大請求卡住」——例如「登入可以，但上傳檔案就掛住」。這個症狀很容易被誤診為應用問題，而正確的驗證是用 `ping -M do -s <size>` 測試不同大小的封包能不能通過。

**「DNS 在 Kubernetes 中是一個常見的問題源」**：容器的 `/etc/resolv.conf` 通常有 `ndots:5` 的設定——於是查詢 `api.example.com` 會先嘗試 `api.example.com.default.svc.cluster.local` 等多個後綴才查真正的網域。在外部網域的查詢上這意味著多次無用的查詢——**延遲增加且 CoreDNS 負載上升**。緩解的方式是「在網域後面加一個點」（`api.example.com.` 表示絕對網域）或者調整 Pod 的 `dnsConfig`。這是一個「預設值為叢集內部優化而犧牲了外部查詢」的取捨。

「連線追蹤表是容器環境的一個隱形限制」：每個 NAT 的連線都要被追蹤——**而 `nf_conntrack_max` 有上限**；在高連線數的節點上滿了之後，新連線被丟棄且日誌中出現 `nf_conntrack: table full`。這個問題在「大量短連線」的工作負載中特別容易觸發——而修正是調大上限或者減少短連線（用連線池）。

**「排查應該從容器內開始」**：`kubectl exec` 進去測試（如果有工具）或者用 `kubectl debug` 附加一個帶工具的臨時容器——先確認「從這個容器的視角，目標可達嗎」；再逐層往外（節點上測試、從另一個 Pod 測試）。這個由內而外的順序能快速定位是哪一層的問題。

## 面試回答方式

先給多出的四層抽象（命名空間、封裝、NAT 與轉發、雲端的隱含限制）並指出排查的關鍵是知道有哪些層並能逐層驗證。加分點有四個：**MTU 問題特別常見且症狀誤導**——「登入可以但上傳檔案掛住」很容易被誤診為應用問題，而正確的驗證是用不同大小的封包測試；Kubernetes 的 `ndots:5` 讓外部網域的查詢多次無用嘗試，是「預設值為叢集內部優化而犧牲外部查詢」的取捨；**連線追蹤表是隱形限制**，在大量短連線的工作負載中特別容易觸發；以及排查應該從容器內開始由內而外。

## 講稿

容器化之後多了幾層抽象，而每一層都可能是問題的來源。網路命名空間、額外的封裝、位址轉換與轉發規則、還有雲端的隱含限制。

其中最常見且症狀最誤導的是最大傳輸單元。覆蓋網路的封裝讓每個封包多出大約五十位元組，如果容器內的設定仍然是預設值，那滿載的封包封裝之後會超過底層網路的上限。而如果路徑上的錯誤回報訊息被防火牆丟棄，路徑探測就失效了。

症狀是小請求正常、大請求卡住。例如登入可以但上傳檔案就掛住。這很容易被誤診為應用問題，而正確的驗證是用不同大小的封包測試能不能通過。

第二個常見的是名稱解析。容器的解析設定通常會先嘗試多個叢集內的後綴才查真正的網域，於是查外部網域時有多次無用的查詢，延遲增加而且解析服務的負載上升。緩解是在網域後面加一個點表示絕對網域。

排查上我會從容器內開始，先確認從這個容器的視角目標可達嗎，再逐層往外。這個由內而外的順序能快速定位是哪一層的問題。

## 常見追問

### 為什麼容器內 ping 不通但 curl 可以？

**核心答案**：**因為 ICMP 與 TCP 走的是不同的規則**。很多環境（尤其是雲端的安全群組與網路政策）預設只允許特定的 TCP 端口而封鎖 ICMP——於是 ping 不通完全正常，而服務是可達的。所以「ping 不通」不能作為「網路不通」的證據——應該用 `curl`、`nc`、或 `telnet` 測試實際要用的端口。

**詳細解析**：「用錯誤的工具得出錯誤的結論」在網路排查中很常見：ping 測的是 ICMP 的可達性——而你的應用用的是 TCP 的某個端口；兩者的路徑上可能有完全不同的規則。同樣的誤區還有「traceroute 顯示某一跳不通就認為那裡斷了」（很多路由器不回應 traceroute 但正常轉發）。所以正確的原則是「用與應用相同的協定與端口測試」——**`nc -zv host port` 是最直接的檢查**。而如果需要更接近真實，直接用 `curl` 打實際的端點——因為那還驗證了 TLS 與應用層的可達性。這個「測試應該盡量接近真實使用」的原則，能避免很多基於間接證據的誤判。

**面試回答方式**：給根本原因（ICMP 與 TCP 走不同的規則，很多環境預設封鎖 ICMP）並指出「ping 不通」不能作為「網路不通」的證據。核心加分點是把它提升成原則：用錯誤的工具得出錯誤的結論在網路排查中很常見，並舉 traceroute 的同類誤區。收在正確做法：用與應用相同的協定與端口測試，而直接用 curl 打實際端點還驗證了 TLS 與應用層的可達性。

### Kubernetes 中 Pod 之間連不通怎麼查？

**核心答案**：**按層次由內而外驗證四步**。**一、在來源 Pod 內測試目標的 Pod IP**（排除 Service 與 DNS）。**二、在同節點的另一個 Pod 測試**（排除來源 Pod 自身的問題）。**三、在跨節點的 Pod 測試**（如果同節點通而跨節點不通，那是 CNI 或底層網路的問題）。**四、用 Service 名稱測試**（如果 IP 通而名稱不通，那是 DNS 或 Endpoints 的問題）。

**詳細解析**：「每一步失敗都指向一組明確的原因」是這個流程的價值：第三步失敗（跨節點不通）最常見的原因是雲端的安全群組沒有放行 Pod 的網段或者**overlay 的封裝端口被封鎖**（VXLAN 是 UDP 8472）。第四步失敗則要分「解析失敗」（CoreDNS 問題）與「解析成功但連不上」（Endpoints 是空的）——而後者最常見的原因是「標籤選擇器寫錯」或「Pod 未就緒」。**用 `kubectl get endpoints <svc>` 一眼就能確認**。而 NetworkPolicy 是另一個常見但隱蔽的原因：它生效時流量被靜默丟棄，沒有任何錯誤訊息——所以「有沒有 NetworkPolicy 選中這些 Pod」應該是一個明確的檢查項。

**面試回答方式**：給四步由內而外的驗證流程。核心加分點是說明每一步失敗都指向一組明確的原因：第三步失敗最常見的是安全群組沒放行 Pod 網段或封裝端口被封鎖；第四步要分解析失敗與 Endpoints 為空，而後者用 `kubectl get endpoints` 一眼確認。收在一個隱蔽的原因：NetworkPolicy 生效時流量被靜默丟棄沒有任何錯誤訊息，所以它應該是一個明確的檢查項。

### 服務網格增加了哪些網路層的複雜度？

**核心答案**：每個 Pod 多了一個 sidecar proxy，於是每次呼叫多兩跳（出方向經過自己的 proxy、入方向經過對方的 proxy）。**帶來的問題包括**：**延遲增加（通常幾毫秒）**、啟動順序（應用可能在 proxy 就緒前就發起連線）、以及排查時多了一層需要理解的元件（**流量實際上被 iptables 或 eBPF 重導向了**）。

**詳細解析**：「啟動順序問題」在 sidecar 模式中曾經是一個真實的痛點：應用容器啟動並立刻連線——而 proxy 還沒就緒，於是那些連線失敗；同樣地，關閉時 proxy 可能先退出，讓應用最後的請求失敗。Kubernetes 1.29 的原生 sidecar（在 initContainers 中設 `restartPolicy: Always`）解決了這個問題——它保證 sidecar 在主容器之前啟動、在主容器之後終止。而在那之前，各種變通做法（等待腳本、延遲啟動）都很脆弱。這是一個「平台層的正確支援消除了應用層的變通」的好例子——也說明了為什麼理解底層的生命週期對排查這類問題是必要的。

**面試回答方式**：給多出的兩跳與三個問題。核心加分點是展開**啟動順序問題**——應用可能在 proxy 就緒前發起連線、關閉時 proxy 可能先退出，並指出 **Kubernetes 1.29 的原生 sidecar 解決了它**（保證先啟動後終止）。收在觀察：這是「平台層的正確支援消除了應用層的變通」的好例子，也說明理解底層生命週期對排查這類問題是必要的。
