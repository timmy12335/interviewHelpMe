# 題目

一個對外的服務可能遇到哪些網路層的攻擊？怎麼防？

## 核心答案

按攻擊的層次分成三類，而防護的位置各不相同。

**容量耗盡型（volumetric）**——**UDP flood、放大攻擊（DNS、NTP、memcached 反射）**；它們用巨大的流量塞滿你的頻寬。這一類無法在你的伺服器上防——因為流量在到達之前就已經塞滿了鏈路；**必須靠上游的清洗服務或 CDN。**

**協定型**——**SYN flood（耗盡連線表）、TCP 分片攻擊、ACK flood**。這一類可以在作業系統與防火牆層緩解：SYN cookie、連線速率限制、以及調整半連線佇列。

**應用型**——慢速攻擊（Slowloris：開很多連線但慢慢送）、大量的昂貴請求（打搜尋介面、觸發複雜查詢）。**這一類流量不大但消耗資源**——需要應用層的限流、逾時、以及成本感知的保護。

## 詳細解析

「SYN cookie 的原理」值得知道，因為它是一個優雅的設計：正常的三次握手中，伺服器在收到 SYN 後要分配一個半連線的記錄——於是攻擊者送大量偽造來源的 SYN 就能耗盡那個佇列。SYN cookie 的做法是「不分配記錄，而是把必要的狀態編碼進 SYN-ACK 的序號中」——如果客戶端是真實的，它回的 ACK 會帶回那個序號，伺服器據此重建狀態。於是攻擊者的偽造 SYN 不消耗任何伺服器記憶體。這是一個「用計算換取無狀態」的經典技巧，與很多分散式系統的設計思路相通。

「慢速攻擊最難防也最容易被忽略」：Slowloris 用幾百條連線就能拖垮一台伺服器——流量小到監控完全看不出異常。防護的關鍵是「對連線的各個階段設逾時」：接收請求標頭的逾時、接收 body 的逾時、以及最小傳輸速率（**nginx 的 `client_body_timeout`、`client_header_timeout`**）。而使用事件驅動的伺服器（nginx、以及非阻塞的應用框架）本身就對這類攻擊有很強的抵抗力——因為一條慢連線只佔一個檔案描述符而非一個執行緒。

「放大攻擊的原理」是「小請求換大回應」：向一個開放的 DNS 解析器發一個 60 位元組的查詢——**它可能回傳 4000 位元組**；而如果來源 IP 被偽造成受害者，那 4000 位元組就打到受害者身上。放大倍率可能達到幾十到上萬倍。防護的責任在「不要成為放大器」（關閉開放的遞迴解析、限制回應速率）——而作為受害者只能靠上游清洗。

「防護的第一步是知道自己被攻擊了」：正常的流量高峰與攻擊在指標上可能相似——區分的線索是「來源的分布」（攻擊往往來自異常的地理或 ASN 分布）、「請求的模式」（重複的路徑、缺失的常見標頭）、以及「與業務指標的背離」（流量暴增但轉換率為零）。最後一項尤其有用，而它需要業務指標與技術指標一起看。

## 面試回答方式

先按層次分三類（容量耗盡、協定型、應用型）並指出**防護的位置各不相同**，強調容量型無法在自己的伺服器上防。加分點有四個：**SYN cookie 的原理**——把狀態編碼進序號而不分配記錄，是「用計算換取無狀態」的經典技巧；慢速攻擊最難防也最容易被忽略——**流量小到監控看不出異常**，防護靠對連線各階段設逾時，而事件驅動的伺服器天生抵抗力強；**放大攻擊的原理與倍率**，以及防護責任在「不要成為放大器」；以及防護的第一步是知道自己被攻擊了，而「流量暴增但轉換率為零」這個業務與技術指標的背離最有用。

## 講稿

我會按層次分三類，因為防護的位置不同。

第一類是容量耗盡型，用巨大流量塞滿頻寬。這一類無法在自己的伺服器上防，因為流量在到達之前就已經塞滿鏈路了，必須靠上游的清洗服務或內容分發網路。

第二類是協定型，像是同步洪水攻擊耗盡連線表。這一類可以在作業系統跟防火牆層緩解。這裡有一個很優雅的設計叫同步餅乾。正常握手中伺服器收到請求後要分配一個半連線記錄，於是攻擊者送大量偽造來源的請求就能耗盡佇列。而這個機制不分配記錄，把必要的狀態編碼進回應的序號裡，真實的客戶端會帶回那個序號讓伺服器重建狀態。於是偽造的請求不消耗任何記憶體。這是用計算換取無狀態的經典技巧。

第三類是應用型，流量不大但消耗資源。慢速攻擊最難防也最容易被忽略，幾百條連線就能拖垮一台伺服器，而流量小到監控完全看不出異常。防護的關鍵是對連線的各個階段設逾時。

而防護的第一步是知道自己被攻擊了。最有用的線索是流量暴增但轉換率為零。

## 常見追問

### CDN 怎麼幫忙抵禦攻擊？

**核心答案**：**三個層面**。**吸收容量**——CDN 的總頻寬遠大於任何單一來源站，於是容量型攻擊被分散到全球的節點上。**過濾**——在邊緣識別並丟棄惡意流量（速率限制、WAF 規則、bot 偵測）。**以及隱藏來源**——如果來源站的 IP 沒有洩漏，攻擊者只能打 CDN。

**詳細解析**：「來源站 IP 洩漏」讓 CDN 的保護失效，而洩漏的管道比想像中多：**歷史的 DNS 記錄**（攻擊者可以查詢舊的解析記錄）、**郵件伺服器的標頭**（如果從同一台機器發信）、**憑證透明度日誌**（憑證中的網域可能暴露）、以及任何直接連到來源站的服務（管理後台、API 的另一個網域）。所以「用 CDN」必須配合「在來源站的防火牆上只允許 CDN 的 IP 範圍」——否則攻擊者繞過 CDN 直接打來源站，所有的防護都白費。這個設定經常被遺漏，而它是 CDN 防護能否真正生效的關鍵前提。

**面試回答方式**：給三個層面（吸收容量、邊緣過濾、隱藏來源）。核心加分點是來源站 IP 洩漏讓保護失效，而洩漏管道比想像中多（歷史 DNS 記錄、郵件標頭、憑證透明度日誌、其他直連的服務）。收在關鍵前提：必須在來源站的防火牆上只允許 CDN 的 IP 範圍——否則攻擊者繞過 CDN 直接打，所有防護都白費，**而這個設定經常被遺漏**。

### 限流該怎麼設計才有效？

**核心答案**：**分層且維度要對**。**邊緣層**——按 IP 的粗粒度限流（擋掉明顯的濫用）。**應用層**——按使用者、按 API key、或按資源的細粒度限流（因為 IP 在 NAT 之後可能代表很多真實使用者）。而限流的單位應該對應「成本」而非「請求數」——一個觸發複雜查詢的請求應該消耗更多配額。

**詳細解析**：「按 IP 限流的兩個失效方向」都很常見：**誤傷**——一個公司或學校共用出口 IP，正常使用者被當成攻擊者；**繞過**——攻擊者用大量代理或殭屍網路，每個 IP 的請求數都在限制之內。所以 IP 只適合作為粗粒度的第一層，而精確的控制必須基於已認證的身份。**至於「按成本限流」**：做法是給不同的端點分配不同的權重（**一次搜尋算 10 點、一次讀取算 1 點**）——於是配額真正對應資源消耗而非請求數。這是很多商業 API 採用的模型，而它比單純的「每分鐘 N 次」公平也有效得多——因為它防的是資源耗盡，而資源消耗本來就不是每個請求都一樣。

**面試回答方式**：給分層設計與各層的維度，並指出**IP 在 NAT 之後可能代表很多使用者**。核心加分點是**按 IP 限流的兩個失效方向**（誤傷共用出口的正常使用者、被大量代理繞過），**所以 IP 只適合粗粒度的第一層**。收在**按成本限流**：不同端點分配不同權重，讓配額對應資源消耗而非請求數——比「每分鐘 N 次」公平也有效，因為它防的是資源耗盡。

### 內網服務需要防這些嗎？

**核心答案**：**需要，但威脅模型不同**。內網的容量型攻擊很少——而「一個被攻破的內部服務向其他服務發起攻擊」或者「一個 bug 造成的重試風暴」是更真實的威脅。所以內網的重點是「限流與熔斷」而非「DDoS 防護」——它們防的是「一個異常的內部客戶端拖垮下游」。

**詳細解析**：「內部服務之間的信任不應該是無限的」是零信任的核心主張：傳統的模型是「內網可信、外網不可信」——而一旦攻擊者進入內網（透過釣魚、供應鏈、或一個有漏洞的服務），就暢行無阻。零信任的做法是「每一次呼叫都驗證身份與授權」（mTLS 加細粒度的授權策略）——於是一個被攻破的服務只能做它本來就被授權做的事。而在可用性的層面，內部的限流同樣重要：一個有 bug 的客戶端發起無限重試，能在幾分鐘內打垮一個關鍵的內部服務——而那不是惡意攻擊，只是一個錯誤。所以「防護不只是防惡意，也是防意外」——這個認知讓限流與熔斷從安全措施變成可靠性措施，也更容易在團隊中被接受。

**面試回答方式**：回答需要但威脅模型不同，並指出內網的重點是限流與熔斷而非 DDoS 防護。核心加分點是**零信任的主張**：傳統「內網可信」的模型在攻擊者進入後暢行無阻，而每次呼叫都驗證讓被攻破的服務只能做本來就被授權的事。收在認知：防護不只是防惡意也是防意外——一個 bug 造成的無限重試能在幾分鐘內打垮關鍵服務，這讓限流從安全措施變成可靠性措施，也更容易被團隊接受。
