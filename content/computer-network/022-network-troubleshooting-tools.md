# 題目

服務連不上，你會用哪些工具、按什麼順序排查？

## 核心答案

按**由淺入深、由外而內**的順序：**一、名稱解析**——先確認網域解析到的位址是不是預期的（指定不同的解析器分別查，排除快取問題）。**二、連通性**——用 ping 確認基本可達（但要記得 ICMP 可能被封鎖，不通不代表服務不通）。**三、路徑**——traceroute 看封包走到哪一跳開始異常，判斷問題在自己這端、中間網路、還是對端。**四、埠號層級**——用能指定埠號的工具（telnet、nc 或對應的診斷指令）確認目標埠是否接受連線，這比 ping 更接近真實情況。**五、連線狀態**——在本機用 ss 或 netstat 看連線處於什麼狀態（大量 `SYN_SENT` 代表對方沒回應、大量 `CLOSE_WAIT` 代表自己沒關閉、大量 `TIME_WAIT` 代表短連線太多）。**六、抓包**——前面都無法定位時才用 tcpdump 抓下實際封包，看握手是否完成、有沒有 RST、重傳多不多。順序的價值在於**每一步都能排除一大類可能**，跳著查容易繞遠路。

## 詳細解析

**ping 不通不代表服務不通**：許多網路封鎖 ICMP，所以 ping 失敗只能作為參考而非結論。反過來 **ping 通也不代表服務可用**——它只驗證了網路層，服務可能根本沒在監聽、或應用層已經卡死。所以確認「服務能不能用」要用**指定埠號的測試**，這是最常被跳過但最有價值的一步。

**連線狀態能直接指出問題方向**：大量 `SYN_SENT` 表示自己送出了握手但對方沒回應——可能是防火牆丟棄、對方沒監聽、或路徑不通。大量 `CLOSE_WAIT` 表示對方已關閉而**自己的程式沒呼叫 close**，是程式 bug。大量 `TIME_WAIT` 表示短連線建立得太頻繁，該用連線池。大量連線卡在 `ESTABLISHED` 但沒有流量，可能是應用層假死或對方停止處理。**先看狀態分布再決定往哪查**，比一開始就抓包有效率得多。

**抓包要先想清楚要驗證什麼**：漫無目的地抓會得到大量無用資料。實務上要先形成假設——「我懷疑握手沒完成」就看有沒有 SYN 而沒有 SYN+ACK；「我懷疑對方主動斷線」就找 RST 與 FIN 是誰先送的；「我懷疑網路品質差」就看重傳與亂序的比例。同時要**加上過濾條件**（目標位址、埠號）縮小範圍，並在**兩端同時抓**——只抓一端往往無法判斷封包是沒送出還是送出後在路上消失，這個對照是定位「到底丟在哪裡」的關鍵手段。

**分層排查的通用順序**：實體與連結層（介面狀態、同網段可達性）→ 網路層（跨網段路由、防火牆）→ 傳輸層（埠號、握手、連線狀態）→ 應用層（協定、憑證、認證、業務邏輯）。每一層都有對應的驗證方式，逐層排除能把模糊的「連不上」收斂成具體的一層。**跳過層次直接猜**是最常見的時間浪費。

**先問「什麼時候開始的、變更了什麼」**：多數生產問題有明確的觸發點——部署、設定變更、憑證到期、流量成長、對端變更。在動用任何工具之前先問這兩個問題，往往能直接定位。工具是用來**驗證假設**的，不是用來取代思考的，這一點在面試中主動說出來很有價值。

## 面試回答方式

給出**六步順序**（解析、連通、路徑、埠號、連線狀態、抓包）並說明每一步排除的是哪一類可能——順序本身就是答案。主動糾正一個常見誤區：**ping 不通不代表服務不通，ping 通也不代表服務可用**，所以要用指定埠號的測試。接著把**連線狀態的分布**當成快速定位工具，各給一個判讀（`SYN_SENT` 對方沒回、`CLOSE_WAIT` 自己沒關、`TIME_WAIT` 短連線太多）。加分點有兩個：抓包要**先形成假設並在兩端同時抓**，只抓一端無法判斷封包丟在哪裡；以及動用工具前先問「什麼時候開始的、變更了什麼」，工具是驗證假設的而不是取代思考的。

## 講稿

我的順序是由淺入深、由外而內。

第一步先確認名稱解析，看網域解到的位址對不對，而且會指定不同的解析器分別查，排除快取問題。第二步 ping 確認基本可達。第三步 traceroute 看封包走到哪一跳開始異常，判斷問題在我這端、中間網路、還是對端。

第四步很關鍵，用能指定埠號的工具確認目標埠有沒有接受連線。因為 ping 不通不代表服務不通，很多網路把 ICMP 擋掉了。反過來 ping 通也不代表服務可用，它只驗證了網路層。

第五步我會看連線狀態的分布。大量 SYN_SENT 代表我送了握手但對方沒回。大量 CLOSE_WAIT 代表對方關了而我的程式沒呼叫 close，那是程式 bug。大量 TIME_WAIT 代表短連線建立得太頻繁。這一步常常直接告訴我該往哪查。

最後才抓包，而且我會先形成假設再抓，不然會得到一堆無用資料。可以的話兩端同時抓，因為只抓一端沒辦法判斷封包是沒送出還是送出後在路上消失。

不過在動用任何工具之前，我會先問兩個問題，什麼時候開始的、以及變更了什麼。

## 常見追問

### traceroute 顯示中間某一跳沒有回應，代表那裡有問題嗎？

**核心答案**：**不一定**。traceroute 依賴中間設備回傳 ICMP 逾時訊息，而**很多路由器基於安全或效能考量不回應這類訊息**，或對它們做嚴格的速率限制。所以某一跳顯示為無回應，可能只是那台設備不理你，而封包其實順利通過了。判斷的關鍵是**看後續的跳點**——如果中間某跳沒回應但後面的跳點正常，那就只是不回應而已；如果從某一跳開始**之後全部沒有回應**，才比較可能是真的斷在那裡。

**詳細解析**：另一個常見的誤讀是**延遲數字**。中間跳點顯示的延遲是「到那一跳並回傳」的時間，而路由器處理 ICMP 的優先權很低，所以某一跳延遲很高不代表它拖慢了轉發——真正該看的是**最終目標的延遲**與**延遲從哪一跳開始持續變高**。此外去程與回程的路徑可能不同，traceroute 只反映去程，所以「某一跳看起來有問題」也可能是回程的問題。基於這些限制，traceroute 適合用來**縮小範圍與形成假設**，不適合當成定論——這個認知比會用這個工具更重要。

**面試回答方式**：明確說不一定，並給判斷方式（看後續跳點是否正常）。加分點是指出延遲數字的誤讀（中間跳點的高延遲不代表拖慢轉發，要看最終目標與持續變高的起點）、以及去回程路徑可能不同，所以它只適合縮小範圍不能當定論。

### 兩端同時抓包為什麼重要？

**核心答案**：因為只抓一端**無法區分「沒送出」與「送出但在路上消失」**。如果只在客戶端看到 SYN 而沒有回應，可能是伺服器沒收到（中間丟棄）、也可能是伺服器收到了但回應在路上丟了、還可能是伺服器根本沒回。兩端同時抓才能定位到**具體是哪一段**：伺服器端有沒有看到那個 SYN，就把可能性直接砍半。

**詳細解析**：實務上的操作要點有三個。**時間要對齊**——兩端的時鐘偏差會讓對照變得困難，抓包前確認時間同步，或用封包中的序號來對照而非只靠時間。**過濾條件要一致**——兩端用相同的條件（對方位址與埠號），否則會漏掉關鍵封包。**抓的時機要涵蓋問題發生**——間歇性問題最麻煩，可能需要長時間抓取並設定檔案輪替與大小上限，避免塞爆磁碟。另外在容器或虛擬化環境中要注意**在哪一層抓**——容器內、宿主機、還是實體網卡上看到的封包可能不同（因為中間有虛擬交換與 NAT），選錯位置會誤判。這一點在現代環境中尤其容易出錯。

**面試回答方式**：核心是只抓一端無法區分「沒送出」與「路上消失」，兩端對照能直接砍掉一半可能性。加分點是三個操作要點（時間對齊、過濾條件一致、涵蓋問題發生的時機），以及容器環境中要注意在哪一層抓，不同層看到的封包可能不同。

### 遇到間歇性的網路問題，要怎麼縮小範圍？

**核心答案**：**先找出關聯性**。間歇性問題通常與某個變數相關——特定時段（流量尖峰、排程任務）、特定機器或可用區、特定使用者群體（同一個 NAT 出口、特定地區）、或特定請求類型（大酬載、長連線）。從監控資料中把失敗的請求按這些維度切開，找出**失敗集中在哪一類**，往往一下就把範圍縮到很小。沒有關聯性線索之前就開始抓包，效率極低。

**詳細解析**：常見的關聯模式與對應方向：**只在尖峰失敗**指向資源耗盡（連線數、埠號、佇列）；**只有某台機器失敗**指向該機器的設定或健康狀態；**只有大回應失敗**指向 MTU 或逾時；**固定間隔失敗**指向連線閒置逾時或某個週期性任務；**只有某地區失敗**指向路由或當地網路。這份對照表能讓排查從盲目變成有方向。另外要善用**長期抓取加上觸發條件**——設定在特定錯誤發生時保留前後的封包，比守著抓包等問題重現有效率得多。這類「讓問題自己被記錄下來」的做法在間歇性問題上價值最高。

**面試回答方式**：核心是先從監控資料找關聯性（時段、機器、使用者群、請求類型），縮小範圍後再動用工具。加分點是給出幾組關聯模式與對應方向的對照（尖峰指向資源耗盡、大回應指向 MTU 或逾時、固定間隔指向閒置逾時），以及用觸發式的長期抓取取代守著等重現。
