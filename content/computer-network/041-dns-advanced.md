# 題目

DNS 能不能用來做故障轉移？TTL 該設多少？

## 核心答案

能，但它是一個「慢且不精確」的機制，不該作為主要的故障轉移手段。

**原因是 TTL 不可控**：你設 60 秒，但路徑上的遞迴解析器、作業系統、瀏覽器、以及應用程式的 JVM 都可能有自己的快取策略——有些會忽略短 TTL、有些永久快取（Java 的預設就曾經是永久）。於是「改了 DNS 之後多久生效」實際上是不確定的，長尾可能是幾小時。

**TTL 的設定是一個取捨**：短 TTL（30 到 60 秒）讓變更快速生效，代價是解析請求量大增且對 DNS 服務的依賴變強；長 TTL（幾小時到一天）減少查詢並提高韌性，代價是變更慢。

實務上的做法是「平時用中等 TTL（幾分鐘到一小時），在計畫變更前提前調短」——於是既有平時的效率，又有變更時的靈活。

## 詳細解析

「DNS 故障轉移的真實延遲」比 TTL 大得多：健康檢查的偵測時間（30 秒）+ DNS 記錄更新的傳播（幾秒到幾十秒）+ 客戶端快取過期（TTL）+ 客戶端重新解析並重試——**加起來可能是幾分鐘**。而在那期間所有還持有舊記錄的客戶端都在打故障的 IP。所以對「需要秒級故障轉移」的場景，正確的手段是 Anycast**（路由層自動切換）或者**負載平衡器的健康檢查**（連線層面的即時剔除）——**DNS 只適合「分鐘級可接受」的場景，例如整個區域的災難切換。

「多筆 A 記錄的行為」是一個有用但不可靠的機制：一個網域可以回傳多個 IP——多數客戶端會依序嘗試，第一個連不上就試下一個。**這提供了一定的容錯**；**但行為因客戶端而異**（有些只試第一個、有些有自己的快取與排序），而且「連不上」與「連得上但服務壞了」是不同的（後者不會觸發重試）。所以它是一個「有比沒有好」的機制而非可靠的保證。

「基於地理或延遲的解析」是 DNS 的一個強項：解析伺服器可以根據查詢來源回傳不同的 IP——於是使用者被導向最近的資料中心。但它的判斷依據是「遞迴解析器的 IP」而非使用者的 IP——於是使用公共 DNS（8.8.8.8）的使用者可能被導向錯誤的區域。EDNS Client Subnet 這個擴充讓遞迴解析器可以傳遞使用者的網段來改善這個問題——但它與隱私有衝突，而且並非所有解析器都支援。

**「DNS 的故障影響極廣」**：它是幾乎所有連線的第一步——一次 DNS 故障會表現為「所有東西都掛了」。所以權威 DNS 應該用多家供應商（不同的 Anycast 網路），而應用側應該有本地的解析快取與合理的逾時——因為 DNS 查詢的預設逾時（5 秒）在故障時會讓每個請求都卡 5 秒。

## 面試回答方式

先回答能但慢且不精確，不該作為主要手段，並給根本原因（TTL 不可控，路徑上多層快取可能忽略它）。給 TTL 的取捨與**平時中等、變更前調短**的實務做法。加分點有四個：DNS 故障轉移的真實延遲比 TTL 大得多（偵測加傳播加快取加重試可能是幾分鐘），所以秒級的需求要用 Anycast 或負載平衡器；多筆 A 記錄是「有比沒有好」的機制——行為因客戶端而異，而且「連得上但服務壞了」不會觸發重試；基於地理的解析依據的是遞迴解析器的 IP 而非使用者的，所以用公共 DNS 的使用者可能被導向錯誤的區域；以及**DNS 故障影響極廣**，應該用多家供應商，而應用側的預設逾時會讓每個請求卡 5 秒。

## 講稿

能，但它是一個慢且不精確的機制，不該作為主要的故障轉移手段。

原因是存活時間不可控。你設六十秒，但路徑上的遞迴解析器、作業系統、瀏覽器、應用程式都可能有自己的快取策略。有些會忽略短存活時間，有些甚至永久快取。於是改了記錄之後多久生效實際上是不確定的，長尾可能是幾小時。

而真實的故障轉移延遲比存活時間大得多。健康檢查的偵測時間、記錄更新的傳播、客戶端快取過期、客戶端重新解析並重試，加起來可能是幾分鐘。所以對需要秒級切換的場景，正確的手段是任播或者負載平衡器的健康檢查，這個機制只適合分鐘級可接受的場景，例如整個區域的災難切換。

存活時間的設定我會平時用幾分鐘到一小時，在計畫變更前提前調短。這樣既有平時的效率又有變更時的靈活。

還有一點，這個服務的故障影響極廣，因為它是幾乎所有連線的第一步。一次故障會表現為所有東西都掛了。所以權威伺服器應該用多家供應商，而應用側要有本地快取跟合理的逾時。

## 常見追問

### DNS 解析慢怎麼排查？

**核心答案**：用 `dig +trace` 看完整的解析路徑與每一步的耗時——它會顯示從根伺服器開始逐層查詢的過程。**常見的慢因是**：**遞迴解析器本身慢或過載**、**權威伺服器回應慢**、**CNAME 鏈過長（每一層都要一次查詢）**、以及 IPv6 的查詢失敗導致等待逾時（客戶端同時查 A 與 AAAA）。

**詳細解析**：「CNAME 鏈過長」在使用多層 CDN 或 SaaS 服務時很常見：`www.example.com` → CNAME 到 CDN → CNAME 到區域節點 → 最後才是 A 記錄——每一層可能是一次額外的查詢（如果沒有被一起回傳）。在冷快取的情況下，這可能增加幾十到上百毫秒的首次連線延遲。緩解的方式是「用 ALIAS 或 ANAME 記錄在權威側展平」（部分 DNS 供應商支援）——**於是客戶端只做一次查詢**。另一個常被忽略的是「IPv6 查詢的逾時」：在只有 IPv4 的網路中，AAAA 查詢可能得不到回應而要等逾時——而 Happy Eyeballs 演算法（並行嘗試兩個協定，先連上的贏）正是為了解決這個問題，但不是所有客戶端都實作了它。

**面試回答方式**：給主要工具與常見慢因。核心加分點是**CNAME 鏈過長在多層 CDN 或 SaaS 中很常見**——每一層可能是一次額外查詢，冷快取下增加幾十到上百毫秒，**而 ALIAS 記錄能在權威側展平**。收在另一個常被忽略的點：**IPv6 查詢的逾時**——**只有 IPv4 的網路中 AAAA 查詢要等逾時**，而 Happy Eyeballs 正是為此設計但不是所有客戶端都實作。

### 內部服務用 DNS 做服務發現好嗎？

**核心答案**：**簡單場景可以，複雜場景不夠**。DNS 的優勢是「所有語言、所有框架都天然支援」——**不需要客戶端整合任何 SDK**。限制是「只能給 IP，給不了中繼資料」（版本、權重、健康狀態）、**「快取讓變更生效慢」**、**以及「無法表達複雜的路由」**。所以它適合「服務數量少、變更不頻繁」的場景——而 Kubernetes 的 Service 正是這個模式（DNS 加上一個穩定的 ClusterIP）。

**詳細解析**：「Kubernetes 用 DNS 加穩定 IP 繞過了 TTL 問題」是一個聰明的設計：Service 的 ClusterIP 幾乎不變——於是 DNS 記錄可以長期快取而不影響正確性；而後端 Pod 的變化由 kube-proxy 在 IP 層處理，完全不經過 DNS。這把「服務發現的動態性」與「DNS 的快取特性」分離開來——**於是兩者的缺點都被避開了**。**而 headless Service（直接回傳 Pod IP）就沒有這個保護**——它的 DNS 記錄會隨 Pod 變化，於是客戶端的快取會造成問題；所以使用 headless Service 的客戶端（例如 gRPC 的 DNS 解析器）需要主動地重新解析而非依賴 TTL。理解這個差別，能解釋很多 Kubernetes 中「連到已經不存在的 Pod」的問題。

**面試回答方式**：給優勢（天然支援、無需 SDK）與三個限制，並指出它適合服務少、變更不頻繁的場景。核心加分點是**Kubernetes 用 DNS 加穩定 IP 繞過了 TTL 問題**——ClusterIP 幾乎不變所以可以長期快取，而 Pod 的變化由 IP 層處理不經過 DNS，這把服務發現的動態性與 DNS 的快取特性分離開。收在對比：headless Service 沒有這個保護，客戶端需要主動重新解析，而這能解釋很多「連到已不存在的 Pod」的問題。

### DNS 的安全問題有哪些？

**核心答案**：**三類**。**快取投毒**——攻擊者讓解析器快取錯誤的記錄，把使用者導向惡意伺服器；**DNSSEC 用簽章解決（但部署率不高）**。**竊聽與竄改**——**傳統 DNS 是明文的**；**DoH（over HTTPS）與 DoT（over TLS）加密查詢**。**以及網域劫持**——攻擊者取得你的網域註冊帳號或 DNS 供應商帳號並修改記錄；**這是後果最嚴重的一種。**

**詳細解析**：「網域劫持的後果最嚴重卻最容易被忽略」：一旦攻擊者控制了你的 DNS——他可以把流量導到自己的伺服器、可以簽發你的網域的 TLS 憑證（透過 DNS 驗證）、可以攔截你的郵件。而防護是純粹的帳號安全問題：註冊商帳號的多因素認證、註冊商鎖（registrar lock）防止未授權的轉移、以及 DNS 供應商帳號的嚴格權限控制。**這些是「非技術的技術風險」**——它們不需要任何漏洞利用，只需要一次成功的釣魚。而很多團隊在應用層投入大量的安全資源，卻對這個「一次失守就全盤皆輸」的環節缺乏基本的保護。這個「防護投入與風險不匹配」的模式，值得在任何安全評估中被檢查。

**面試回答方式**：給三類安全問題與各自的緩解。核心加分點是網域劫持後果最嚴重卻最容易被忽略——攻擊者能導流量、簽發你網域的憑證、攔截郵件，而防護是純粹的帳號安全（多因素、註冊商鎖、嚴格權限）。收在觀察：這些是「非技術的技術風險」，不需要漏洞利用只需要一次成功的釣魚，而「防護投入與風險不匹配」的模式值得在任何安全評估中被檢查。
