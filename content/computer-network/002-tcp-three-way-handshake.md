# 題目

TCP 建立連線為什麼需要三次握手？兩次不行嗎？

## 核心答案

因為連線是**雙向**的，兩端各自都要確認「我發得出去、對方收得到」。三次握手是達成這件事的**最少次數**：第一次（SYN）客戶端告知自己的初始序號；第二次（SYN+ACK）伺服器確認收到、並告知自己的初始序號；第三次（ACK）客戶端確認收到伺服器的序號。走完之後兩端都確認了雙向的收發能力與彼此的起始序號。兩次為什麼不行——伺服器送出 SYN+ACK 之後就直接認為連線建立，但它無法確認客戶端是否收到自己的序號，也無法排除一個**歷史的、延遲很久才抵達的舊 SYN**造成的假連線：伺服器會為此配置資源並一直等待，而客戶端根本沒有這個連線。第三次的 ACK 正是用來排除這種舊連線。四次則是多餘的——伺服器的 ACK 與 SYN 可以合併成一個封包送出，所以三次就夠。

## 詳細解析

**初始序號為什麼要隨機**：如果序號從固定值開始，攻擊者就能預測序號並偽造封包插入連線（連線劫持）。所以兩端的初始序號都由亂數產生，這既避免了舊連線的封包被誤認為新連線的一部分，也提高了偽造的難度。序號的另一個作用是**排序與去重**，讓接收端能把亂序抵達的段重組回正確的位元組流。

**SYN 洪水攻擊與 SYN cookie**：伺服器收到 SYN 後會配置一個半連線的控制區塊並回 SYN+ACK，等待第三次 ACK。攻擊者大量送出偽造來源 IP 的 SYN 卻永不回應，就能把半連線佇列塞滿，讓正常使用者連不上。**SYN cookie** 的做法是：佇列滿時不配置資源，而是把必要資訊編碼進自己的初始序號中送出，等對方的 ACK 回來時再從序號還原出連線狀態——攻擊者無法偽造正確的 ACK，所以資源不會被佔用。這是最經典的追問。

**連線佇列有兩個**：半連線佇列（收到 SYN、等待 ACK）與全連線佇列（三次握手完成、等待應用程式呼叫 accept）。**全連線佇列滿了**時新完成的連線會被丟棄或拒絕，症狀是「明明伺服器沒滿載，但連線偶爾失敗或延遲很高」——原因往往是應用程式 accept 太慢或執行緒被阻塞。排查時要同時看兩個佇列的溢出計數，只看其中一個容易誤判。

**連線建立的耗時是一次往返**：三次握手中前兩次構成一個往返，客戶端在送出第三次 ACK 的同時就可以開始傳資料，所以建立連線的延遲成本大約是 **1 RTT**。加上 TLS 握手（1.2 需要兩次往返、1.3 一次）之後，一個 HTTPS 連線的建立成本可能是 2 到 3 個往返——這正是連線重用與 HTTP/2 多工如此重要的原因，也是 QUIC 把傳輸與加密握手合併的動機。

**TCP Fast Open 的取捨**：它允許在第一次 SYN 中就攜帶資料，省下一個往返，做法是首次連線時伺服器發給客戶端一個 cookie，之後憑它直接帶資料。代價是**重放風險**——攜帶的資料可能被重放，所以只適合冪等的請求。這個「用安全性換延遲」的取捨在 TLS 1.3 的 0-RTT 上是同樣的問題。

## 面試回答方式

先給核心理由——連線是雙向的，兩端都要確認自己發得出去、對方收得到，三次是達成這件事的最少次數。接著具體說明兩次為什麼不行：伺服器無法確認客戶端收到了自己的序號，也**排除不掉延遲很久才到的舊 SYN**造成的假連線與資源浪費。四次不必要，因為 ACK 與 SYN 可以合併。加分點有三個：初始序號要隨機是為了防連線劫持；SYN 洪水攻擊與 SYN cookie 的原理；以及**半連線與全連線兩個佇列**，全連線佇列滿了會造成「伺服器沒滿載卻連不上」這種難查的症狀。

## 講稿

因為連線是雙向的，兩端都要確認我發得出去、而且對方收得到。三次是達成這件事的最少次數。

第一次客戶端送 SYN，告訴對方自己的初始序號。第二次伺服器回 SYN 加 ACK，確認收到並且告知自己的序號。第三次客戶端再回 ACK，確認收到伺服器的序號。走完之後兩邊都確認了雙向的收發能力。

兩次為什麼不行。伺服器送出第二次之後就認為連線建立了，但它無法確認客戶端有沒有收到自己的序號。更麻煩的是一個延遲很久才抵達的舊 SYN，伺服器會為它配置資源然後一直等，而客戶端根本沒有這個連線。第三次的 ACK 就是用來排除這種情況。四次則是多餘的，ACK 跟 SYN 可以合併成一個封包。

另外我想補兩個實務上的點。初始序號要隨機，不然攻擊者可以預測序號偽造封包劫持連線。還有伺服器端其實有兩個佇列，半連線跟全連線。全連線佇列滿了的時候，症狀是伺服器明明沒滿載，但連線偶爾失敗或延遲很高，原因通常是應用程式 accept 太慢。

## 常見追問

### SYN 洪水攻擊是怎麼運作的？怎麼防？

**核心答案**：攻擊者送出大量**偽造來源 IP** 的 SYN 封包，伺服器為每一個配置半連線資源並回 SYN+ACK，但因為來源是假的，第三次 ACK 永遠不會來。半連線佇列被塞滿之後，正常使用者的 SYN 就被丟棄，服務等同於不可用。防禦的核心手段是 **SYN cookie**——佇列滿時不配置資源，把連線資訊編碼進初始序號送出，等 ACK 回來再還原狀態。

**詳細解析**：SYN cookie 的巧妙之處是**把狀態從伺服器移到封包裡**，攻擊者無法偽造出攜帶正確序號的 ACK，所以偽造的 SYN 不再消耗記憶體。代價是編碼空間有限，某些 TCP 選項（例如視窗縮放）可能無法完整保留，所以通常只在佇列將滿時才啟用而非永遠開啟。其他防禦層次包括：調大半連線佇列、縮短半連線的逾時、在網路邊界做速率限制與來源驗證、以及使用具備抗 DDoS 能力的前置服務。要注意的是這類攻擊屬於資源耗盡而非協定漏洞，所以沒有單一的完美解法，需要分層緩解。

**面試回答方式**：講清攻擊機制（偽造來源、佔住半連線佇列）與 SYN cookie 的核心思路（把狀態放進封包，讓偽造者無法回出正確的 ACK）。加分點是說明 SYN cookie 的代價（選項可能保不住，所以按需啟用），以及點出這是資源耗盡問題、需要分層緩解。

### 半連線佇列和全連線佇列滿了，症狀有什麼不同？

**核心答案**：**半連線佇列滿**發生在握手中途——伺服器直接丟棄新的 SYN，客戶端收不到 SYN+ACK，表現為**連線逾時**，而且客戶端會重傳 SYN，所以延遲呈現階梯式增長。**全連線佇列滿**發生在握手已完成之後——連線已經建立但應用程式來不及 accept，伺服器可能直接丟棄（客戶端以為連上了、送出請求卻沒有回應，直到逾時）或送出 RST（客戶端收到連線被重設）。

**詳細解析**：兩者的排查方式不同。半連線問題多半與**攻擊或瞬間的連線尖峰**有關，要看半連線佇列的溢出計數與 SYN 重傳次數。全連線問題則幾乎總是**應用程式端的問題**——accept 的執行緒被阻塞、執行緒池耗盡、或處理邏輯太慢導致來不及取走連線，要看全連線佇列的溢出計數與應用的執行緒狀態。實務上「全連線佇列溢出」是很典型的假象：監控顯示 CPU 與記憶體都很閒，但使用者一直遇到偶發的請求失敗，因為瓶頸在應用程式取走連線的速度而不是資源用量。能講出這個場景通常代表你實際查過。

**面試回答方式**：分別給出兩者的發生時機與客戶端看到的現象（逾時 vs 沒有回應或被重設）。強調全連線佇列問題幾乎都是應用程式來不及 accept。加分點是描述「資源看起來很閒但偶發失敗」這個典型假象，並說明要看兩個佇列各自的溢出計數。

### 為什麼建立連線是三次，關閉卻要四次？

**核心答案**：因為關閉時**兩個方向要各自獨立關閉**，而建立時可以合併。收到對方的 FIN 只代表**對方沒有資料要送了**，但自己可能還有資料還沒送完，所以只能先回一個 ACK，等自己的資料送完之後才送出自己的 FIN——這使得 ACK 與 FIN **無法合併**成一個封包。建立連線時伺服器沒有這個顧慮，SYN 與 ACK 可以一起送，所以是三次。

**詳細解析**：這個機制就是 TCP 的**半關閉**狀態：一方關閉了發送方向，仍然可以繼續接收。實務上有應用會利用它——送完請求後關閉發送方向表示「我說完了」，然後繼續讀取回應。如果應用程式在收到 FIN 之後立刻也關閉（沒有待送的資料），作業系統確實可能把 ACK 與 FIN 合併，這時就會看到「三次揮手」，所以四次是最一般的情況而非絕對。理解這一點可以避免把抓包看到的三次揮手誤判成異常。

**面試回答方式**：核心是關閉時兩個方向各自獨立，收到 FIN 只代表對方說完了、自己可能還要送，所以 ACK 與 FIN 無法合併。加分點是說明這就是半關閉狀態、有應用會刻意利用，以及沒有待送資料時可能真的合併成三次揮手，四次不是絕對。
