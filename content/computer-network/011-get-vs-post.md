# 題目

GET 和 POST 差在哪？「GET 有長度限制、POST 沒有」這個說法對嗎？

## 核心答案

真正的差異是**語意**，不是技術限制。GET 的語意是**安全且冪等的讀取**——不改變伺服器狀態、執行多次結果相同；POST 的語意是**提交會產生副作用的操作**，且**不保證冪等**。從這個語意衍生出所有實際差別：GET 可以被**快取**、被瀏覽器**預先載入**、出現在**歷史記錄與伺服器日誌**中、可以被**書籤與分享**；POST 都不行。所謂「GET 有長度限制」**不是規範規定的**，而是各家瀏覽器與伺服器對 URL 長度有各自的實作上限（常見是幾 KB 到幾十 KB），規範本身沒有限制。同樣地「POST 比較安全」也是誤解——**兩者都是明文傳輸**，安全來自 HTTPS 而不是方法；POST 唯一的優勢是參數不出現在 URL 中，因此不會被記錄進伺服器日誌、瀏覽器歷史或 Referer 標頭，這是真實但有限的差別。

## 詳細解析

**語意錯用的實際後果**：用 GET 執行會改變狀態的操作（例如 `GET /delete?id=1`）非常危險，因為任何預先載入或爬蟲都可能觸發它——瀏覽器的預抓取、聊天軟體展開連結預覽、搜尋引擎爬取，都會發出 GET。歷史上有網站因此被爬蟲刪光內容。反過來用 POST 做純查詢也有代價：**失去快取能力**、無法分享連結、瀏覽器上一頁時會出現重新提交的提示。

**參數放哪裡的取捨**：查詢條件放在 URL 的好處是**可分享、可書籤、可被快取**，這對搜尋與篩選類的頁面很重要（也是「篩選條件屬於 URL 狀態」的理由）。但敏感資料絕對不能放 URL——它會出現在瀏覽器歷史、伺服器與代理的存取日誌、以及跳轉到第三方時的 `Referer` 標頭中，等於在多個地方留下明文副本。密碼、令牌、身分證號一律放主體。

**查詢條件太複雜時的折衷**：有時查詢參數複雜到 URL 放不下（大量篩選條件、巢狀結構），實務上有兩種做法：用 POST 送查詢並接受失去快取（常見於內部管理系統），或先用 POST 建立一個查詢資源再用 GET 取結果，兼顧複雜度與可快取性。後者較繁瑣但保留了 REST 的語意，適合對外的 API。

**跨域行為不同**：簡單的 GET 不會觸發預檢請求，而送 JSON 的 POST 會。這在前端呼叫跨域 API 時是實際的延遲差異。同時因為 GET 通常是安全的，CSRF 的防護重點在會改變狀態的方法——這也是「有副作用的操作絕對不能用 GET」的另一個安全理由：`SameSite=Lax` 的 Cookie 在跨站的 GET 導航中仍會被送出。

**冪等不等於安全**：GET 兩者都是；PUT 與 DELETE 冪等但不安全（會改狀態）；POST 兩者都不是。這個區分決定了中間設備與客戶端函式庫敢不敢自動重試。POST 需要重試時，要靠應用層的冪等鍵處理，不能依賴協定本身。

## 面試回答方式

第一句就把重點定在**語意**而非技術限制——GET 是安全冪等的讀取、POST 是有副作用的提交，所有實際差別都從這裡衍生。接著主動糾正兩個常見誤解：**長度限制不是規範規定的**，是各家實作上限；**POST 不比較安全**，兩者都明文，安全靠 HTTPS，POST 只是參數不進 URL。然後給實際後果：用 GET 做刪除會被預抓取與爬蟲觸發，歷史上真的發生過。加分點有三個：敏感資料不放 URL 的具體理由（歷史、日誌、Referer 三處留痕）；查詢太複雜時的折衷做法；以及 `SameSite=Lax` 的 Cookie 在跨站 GET 導航仍會送出，所以有副作用的操作更不能用 GET。

## 講稿

真正的差別是語意，不是技術限制。GET 的語意是安全且冪等的讀取，不改變狀態、執行幾次結果都一樣。POST 是提交會產生副作用的操作，而且不保證冪等。

所有實際的差別都從這裡衍生。GET 可以被快取、被瀏覽器預先載入、會出現在歷史記錄跟日誌裡、可以分享跟加書籤。POST 都不行。

我想糾正兩個很常見的說法。第一，GET 有長度限制不是規範規定的，規範沒有限制，那是各家瀏覽器跟伺服器的實作上限。第二，POST 比較安全也是誤解，兩者都是明文傳輸，安全來自 HTTPS。POST 唯一的優勢是參數不出現在 URL，所以不會被記進伺服器日誌、瀏覽器歷史跟 Referer 標頭。

語意用錯的後果是實際的。如果我用 GET 做刪除，任何預先載入或爬蟲都可能觸發它，瀏覽器預抓取、聊天軟體展開連結預覽、搜尋引擎爬取，都會發 GET。歷史上真的有網站因此被爬光刪光。

另外敏感資料一定不要放 URL，因為它會在瀏覽器歷史、代理日誌、還有跳轉到第三方時的 Referer 這三個地方留下明文。

## 常見追問

### 查詢條件太複雜、URL 放不下怎麼辦？

**核心答案**：兩種做法。**直接用 POST 送查詢**——簡單，代價是失去快取、無法分享連結、上一頁會提示重新提交，適合內部管理系統這類不在意這些的場景。或者先用 POST 建立一個查詢資源、再用 GET 取結果——伺服器回傳一個查詢 ID，之後用 `GET /searches/{id}/results` 取得結果，保留了可快取與可分享的性質，代價是多一次往返與需要管理查詢資源的生命週期。

**詳細解析**：選擇的判準是這個查詢結果需不需要被分享或快取。搜尋結果頁通常需要（使用者會分享連結），複雜的報表查詢通常不需要。還有第三種折衷是**壓縮並編碼查詢條件**放進 URL（例如把 JSON 壓縮後 base64），但這會讓 URL 變得不可讀、也難以除錯，通常不划算。實務上更好的方向往往是**簡化查詢介面**——如果查詢條件複雜到 URL 放不下，值得回頭問這個介面是不是設計得太自由，能不能用預設的幾種常用組合加上少量參數涵蓋大部分需求。

**面試回答方式**：給兩種做法與各自代價，並給選擇判準（結果需不需要被分享或快取）。加分點是提到壓縮編碼放 URL 這個折衷通常不划算，以及反問查詢介面是不是設計得太自由，展現你會回到問題本身而不只是找技巧。

### 為什麼有副作用的操作用 GET 特別危險？

**核心答案**：因為 **GET 會被大量自動化行為觸發**，而這些行為完全不受你控制：瀏覽器的預抓取與預先渲染、搜尋引擎爬蟲、聊天軟體與社群平台展開連結預覽、安全掃描工具、以及使用者的瀏覽歷史同步。任何一個把你的連結掃過一遍，副作用就發生了。此外 `SameSite=Lax` 的 Cookie 在跨站的 GET 導航中仍會被送出，所以用 GET 的操作連 CSRF 的基本防護都繞過了。

**詳細解析**：這個問題在早期網站中造成過實際事故——用連結做刪除按鈕，被爬蟲或瀏覽器的預抓取功能觸發後大量內容消失。正確的做法是**所有改變狀態的操作都用 POST、PUT、DELETE**，並在其上加 CSRF 防護。要注意即使是「看起來只是讀取」的操作，如果有計數、扣配額、寫日誌之類的副作用，也要考慮它被自動化觸發的後果——例如用 GET 觸發的「標記已讀」被預抓取觸發，使用者會發現訊息莫名變成已讀。這類細微的副作用最容易被忽略。

**面試回答方式**：列出會自動觸發 GET 的各種行為，強調它們不受你控制。點出 `SameSite=Lax` 在跨站 GET 導航仍送 Cookie，所以連基本 CSRF 防護都繞過。加分點是舉「標記已讀被預抓取觸發」這種細微副作用，說明判斷不能只看是不是明顯的寫入。

### PUT 和 POST 什麼時候該用哪個？

**核心答案**：判準是**冪等性與資源識別**。**PUT** 是「把這個位址的資源設定成我給的內容」——由**客戶端決定資源的位址**，重複執行結果相同（冪等）。**POST** 是「把這個東西提交給這個集合處理」——通常由**伺服器決定新資源的位址**，重複執行會產生多筆（不冪等）。所以建立資源時，如果客戶端能決定 ID（例如用 UUID）就適合 PUT，如果由伺服器產生自增 ID 就用 POST。

**詳細解析**：實務上這個區分的價值在於**重試的安全性**。用 PUT 加上客戶端產生的 ID，網路逾時後直接重試就好，不會產生重複——這其實是冪等鍵的一種自然形式。用 POST 則必須額外設計冪等機制。另一個常見混淆是 **PUT 與 PATCH**：PUT 語意上是**整體替換**（沒送的欄位應該被清空或設為預設），PATCH 是**部分更新**。很多 API 名為 PUT 實際做部分更新，這種不一致會讓呼叫方困惑——如果實際行為是部分更新，就該用 PATCH，或在文件中明確說明。

**面試回答方式**：用「誰決定資源位址」與「冪等與否」兩個維度區分，並給建立資源時的選擇建議。加分點是講 PUT 加客戶端產生的 ID 讓重試天然安全（是冪等鍵的自然形式），以及澄清 PUT 是整體替換、PATCH 是部分更新，名實不符會讓呼叫方困惑。
