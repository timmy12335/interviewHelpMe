# 題目

要把 10TB 的資料從台北傳到法蘭克福，怎麼設計才快？

## 核心答案

**先算清楚理論上限，再決定手段**。單條 TCP 連線的吞吐上限是 `視窗大小 / RTT`——**台北到法蘭克福的 RTT 約 250 毫秒**，**即使視窗開到 16MB，單條連線的上限也只有約 64MB/s**。**而 10TB 除以 64MB/s 是 43 小時。**

**四個手段，按效益排序。**

**一、多條並行連線**——**N 條連線的總吞吐接近 N 倍**（在頻寬允許的範圍內）；**這是最簡單且最有效的一招**，**因為它繞過了單連線的視窗限制**。

**二、把資料先壓縮**——**壓縮率三倍就等於傳輸時間三分之一**；**對可壓縮的資料這是最划算的。**

**三、用專門的傳輸協定**——**基於 UDP 的傳輸工具（Aspera、UDT、或 rsync over 多執行緒）繞過了 TCP 的擁塞控制與視窗限制。**

**四、物理運送**——**一箱硬碟寄過去的「頻寬」可能遠高於任何網路**；**各大雲端都有這類服務（Snowball、Transfer Appliance），對 PB 級的資料這往往是唯一實際的選擇。**

## 詳細解析

**「單連線的視窗限制是這裡的核心約束」**：即使兩端的網路都是 10Gbps——**單條 TCP 連線受限於「視窗大小除以 RTT」**。**而視窗不能無限大**：**接收緩衝區的記憶體成本、以及丟包時的重傳代價都隨視窗增長**。**所以在高 RTT 的鏈路上，並行連線幾乎總是必要的**——**而這也解釋了為什麼下載工具與傳輸軟體普遍使用多執行緒**。

**「多條連線為什麼有效」需要說清楚**：每條連線有自己的擁塞視窗與流量控制——**於是它們各自獨立地填滿自己的管道份額**；**而丟包只影響那一條，其他的不受影響**。**代價是「對其他流量不公平」**（**你佔了 N 份的擁塞控制份額**）——**在自己的專線上無所謂，在共享的網際網路上則是一個需要節制的行為**。

**「Sneakernet 的頻寬計算」是一個有趣但實際的比較**：一箱 100TB 的硬碟空運 24 小時到達——**等效頻寬約 9.3Gbps**；**而如果是 1PB，等效頻寬接近 100Gbps**。**這正是「永遠不要低估一輛裝滿磁帶的卡車的頻寬」這句老話的來源**——**而它在雲端遷移的實務中至今成立**。

**「延遲與吞吐是兩件事」是這裡最重要的區分**：物理運送的吞吐極高但延遲是幾十小時——**所以它適合「大量資料的一次性搬遷」而非「持續的同步」**。**判斷的方式是「總量除以可接受的時間」與「單次的延遲要求」分別評估**——**兩者的答案可能完全不同。**

## 面試回答方式

先算理論上限（**視窗除以 RTT，台北到法蘭克福 250 毫秒的 RTT 下單連線約 64MB/s，10TB 要 43 小時**），再給四個按效益排序的手段。加分點有四個：**單連線的視窗限制是核心約束**——**即使兩端都是 10Gbps 也受限於視窗除以 RTT，而視窗不能無限大**；**多條連線為什麼有效**（各自獨立的擁塞視窗、丟包只影響一條）**與它的代價**（對其他流量不公平）；**物理運送的等效頻寬計算**——**一箱 100TB 空運 24 小時等效約 9.3Gbps**，**這正是「不要低估一輛裝滿磁帶的卡車的頻寬」的來源**；以及**延遲與吞吐是兩件事**——**物理運送吞吐極高但延遲幾十小時，適合一次性搬遷而非持續同步**。

## 講稿

我會先算理論上限再決定手段。單條連線的吞吐上限是視窗大小除以往返時間。台北到法蘭克福的往返大約兩百五十毫秒，即使視窗開到十六 MB，單條連線也只有大約每秒六十四 MB。十 TB 除下來是四十三小時。

所以最簡單也最有效的一招是多條並行連線。每條有自己的擁塞視窗跟流量控制，各自填滿自己的份額，而丟包只影響那一條。代價是對其他流量不公平，因為你佔了很多份擁塞控制的份額。在自己的專線上無所謂，在共享的網際網路上就要節制。

第二是先壓縮，壓縮率三倍就等於傳輸時間三分之一。第三是用基於使用者資料包協定的專門傳輸工具，繞過視窗限制。

第四個聽起來像玩笑但很實際，物理運送。一箱一百 TB 的硬碟空運二十四小時到達，等效頻寬大約九點三 Gbps。如果是一 PB，等效接近一百 Gbps。各大雲端都有這類服務。

但要區分延遲跟吞吐是兩件事。物理運送的吞吐極高但延遲是幾十小時，所以它適合一次性搬遷而不是持續同步。

## 常見追問

### 持續的跨區資料同步該怎麼設計？

**核心答案**：**先做一次性的批量搬遷，再切換到增量同步**。全量用物理運送或並行傳輸——**而之後只傳變更（CDC、增量備份、或者物件儲存的複製功能）**。**這讓「持續同步」的流量從「全量」降到「變更量」**，**而後者通常小兩三個數量級。**

**詳細解析**：**「切換的時機」是這個流程中最需要設計的部分**：全量搬遷需要幾天——**而那期間源端仍在變化**。**標準的做法是「全量快照 + 記錄快照之後的所有變更 + 搬遷完成後重放那些變更」**——**這與資料庫的備份加 binlog 恢復是同一個模式**。**而重放追平之後才切換寫入**。**另一個要點是「增量同步的延遲要被監控」**：**它決定了災難發生時會丟多少資料（RPO）**——**而在跨洲的鏈路上，一次網路波動可能讓延遲從幾秒漲到幾小時**。**所以應該有明確的延遲目標與告警，而不只是「有在同步」。**

**面試回答方式**：給兩階段（全量搬遷再增量同步）並指出**變更量通常比全量小兩三個數量級**。核心加分點是**切換時機的設計**：**全量快照加上記錄期間的變更再重放追平**，**與資料庫的備份加日誌恢復是同一個模式**。收在監控：**增量同步的延遲決定了 RPO**，**而跨洲鏈路上一次波動可能讓延遲從幾秒漲到幾小時，所以要有明確目標與告警**。

### 為什麼有些傳輸工具用 UDP？

**核心答案**：**為了繞過 TCP 的擁塞控制與有序保證**。TCP 的擁塞控制是為了「公平共享網路」設計的——**而在專線或者你願意佔滿頻寬的場景中，那個保守是不必要的**。**基於 UDP 的工具自己實作速率控制（通常更激進）與可靠性（選擇性重傳），於是能達到接近線路速率的吞吐。**

**詳細解析**：**「自己實作可靠性」的代價值得說明**：需要處理重傳、排序、流量控制、以及擁塞避免——**而那些正是 TCP 幾十年來被打磨的部分**。**所以自己做的品質往往不如 TCP，除非投入很大**。**這也是為什麼這類工具多半是商業產品（Aspera）或者針對特定場景的**。**而 QUIC 是一個有趣的中間點**：**它在 UDP 之上實作了完整的可靠傳輸，但保留了 TCP 的擁塞控制原則**——**它的動機不是「更快」而是「更靈活」（可以在使用者空間迭代、支援多路複用、消除隊頭阻塞）**。**能區分「為了突破限制而用 UDP」與「為了協定演進而用 UDP」，是理解這個領域的一個關鍵。**

**面試回答方式**：給動機（繞過為公平設計的擁塞控制與有序保證）與做法（自己實作速率控制與選擇性重傳）。核心加分點是說明**自己實作可靠性的代價**——**那正是 TCP 幾十年打磨的部分，所以品質往往不如它**，**這也是為什麼這類工具多半是商業產品**。收在區分：**QUIC 用 UDP 的動機不是更快而是更靈活**（使用者空間迭代、多路複用、消除隊頭阻塞），**而能區分這兩種動機是理解這個領域的關鍵**。

### 跨區傳輸的成本怎麼算？

**核心答案**：**雲端的跨區與出網流量是按 GB 計費的，而且單價差異很大**。**同區內部通常免費或極便宜**、**跨可用區有費用**、**跨區域更貴**、**而「出網到公開網際網路」最貴**（**每 GB 可能是幾美分，10TB 就是幾百到上千美元**）。**所以「傳輸一次的成本」在大量資料時是一個需要事前計算的數字。**

**詳細解析**：**「壓縮的價值在成本上比在時間上更明顯」**：三倍的壓縮率讓時間變三分之一——**同時也讓費用變三分之一**。**而 CPU 的成本遠低於跨區流量的成本**，**所以「用 CPU 換頻寬」在跨區傳輸中幾乎總是划算的**。**另一個常被忽略的是「重試的成本」**：**一次失敗的傳輸如果要從頭重來，那些已傳的位元組仍然計費**——**所以支援斷點續傳的工具在大檔案傳輸中不只是方便，也是成本控制**。**而物理運送在這個維度上也很有優勢**：**雲端的資料搬遷服務通常按裝置收費而非按 GB，於是在 PB 級時單位成本低得多**——**這讓「成本」與「時間」在大規模搬遷中指向同一個答案。**

**面試回答方式**：給雲端流量的計費層級與量級（10TB 出網可能幾百到上千美元），指出**這是需要事前計算的數字**。核心加分點是**壓縮的價值在成本上比時間上更明顯**——**CPU 成本遠低於跨區流量，所以「用 CPU 換頻寬」幾乎總是划算**。收在兩個補充：**重試的成本讓斷點續傳不只是方便也是成本控制**；**物理運送按裝置而非按 GB 收費，於是在 PB 級時成本與時間指向同一個答案**。
