# 題目

一個 HTTP 請求花了 2 秒，怎麼知道時間花在哪？

## 核心答案

**把一次請求拆成六段，而每一段都有對應的量測方式。**

**DNS 解析**——**首次連線才有；冷快取時可能幾十到幾百毫秒**。**TCP 握手**——**一個 RTT**。**TLS 握手**——**1.3 是一個 RTT，1.2 是兩個**。**請求傳送與伺服器處理（TTFB 的主體）**——**這通常是最大的一塊，而它又要往下拆（應用邏輯、資料庫、下游呼叫）**。**回應傳輸**——**取決於大小與頻寬**。**以及客戶端的處理與渲染。**

**量測的工具**：**`curl -w` 的格式化輸出能一次給出前五段的時間**（`time_namelookup`、`time_connect`、`time_appconnect`、`time_starttransfer`、`time_total`）；**瀏覽器的 Network 面板與 Resource Timing API 提供同樣的拆解**；**而伺服器端的時間需要應用自己的追蹤。**

**拆解之後，優化的方向就明確了**——**而在拆解之前的任何優化都是猜測。**

## 詳細解析

**「`curl -w` 是一個被低估的診斷工具」**：一行指令就能得到完整的時間拆解——**而它不需要任何埋點或工具安裝**。**典型的用法是寫一個格式檔案輸出各階段的時間，然後對比不同的環境（本地 vs 生產、不同區域）**。**這在「使用者說慢但我測起來很快」的情況下特別有用**——**因為你能請對方跑同一條指令並比對每一段的差異**，**於是「是網路慢還是伺服器慢」立刻有答案。**

**「TTFB 包含了太多東西」是一個常見的誤解來源**：它是「從發出請求到收到第一個位元組」——**包含了網路往返與伺服器的完整處理時間**。**於是「TTFB 高」可能是網路遠、可能是伺服器慢、也可能是兩者**。**正確的拆解是「TTFB 減去 `time_connect` 大致就是伺服器的處理時間」**——**而那個數字才能與伺服器端的日誌對照。**

**「往返次數比單次往返的延遲更重要」**：一次跨洲的往返是 200 毫秒——**而一個需要 DNS、TCP、TLS、然後才發請求的冷連線是四個往返，就是 800 毫秒**。**所以「連線復用」在高延遲鏈路上的價值是巨大的**：**復用之後只剩一個往返**。**這也解釋了為什麼「第一個請求很慢、後續很快」是一個普遍現象**——**而優化的重點應該放在「減少冷啟動的往返」（預連線、HTTP/3 的 0-RTT）而非單純加速伺服器。**

**「客戶端的時間常被忽略」**：伺服器 50 毫秒回應，而使用者感覺 3 秒——**時間可能花在 JavaScript 的解析執行、渲染阻塞、或者串行的資源載入上**。**所以「使用者感受的延遲」與「伺服器的回應時間」是兩個不同的指標**——**而只監控後者的團隊會對「為什麼使用者說慢」感到困惑。**

## 面試回答方式

先把請求拆成六段並給每段的量測方式，指出**在拆解之前的任何優化都是猜測**。加分點有四個：**`curl -w` 是被低估的診斷工具**——**一行指令得到完整拆解且不需埋點**，**在「使用者說慢但我測很快」時特別有用因為能比對每段的差異**；**TTFB 包含太多東西**——**它是網路往返加伺服器處理，正確的拆解是減去連線時間**；**往返次數比單次延遲更重要**——**冷連線的四個往返在跨洲時就是 800 毫秒**，**所以優化重點應該是減少冷啟動的往返**；以及**客戶端的時間常被忽略**——**「使用者感受的延遲」與「伺服器回應時間」是兩個不同的指標**。

## 講稿

我會把一次請求拆成六段。名稱解析、連線握手、加密握手、伺服器處理、回應傳輸、還有客戶端的處理與渲染。

量測上最方便的是 curl 的格式化輸出，一行指令就能給出前五段的時間，而且不需要任何埋點。這在使用者說慢但我測起來很快的情況下特別有用，因為你能請對方跑同一條指令並比對每一段的差異，於是是網路慢還是伺服器慢立刻有答案。

有一個常見的誤解要澄清。首位元組時間包含了太多東西，它是從發出請求到收到第一個位元組，包含網路往返跟伺服器的完整處理。所以它高可能是網路遠、可能是伺服器慢、也可能兩者。正確的拆解是首位元組時間減去連線時間，大致就是伺服器的處理時間。

還有一個原則，往返次數比單次往返的延遲更重要。一次跨洲往返是兩百毫秒，而一個需要解析、連線、加密、才發請求的冷連線是四個往返，就是八百毫秒。所以連線復用在高延遲鏈路上的價值巨大。這也解釋了為什麼第一個請求很慢、後續很快是普遍現象。

## 常見追問

### 只有部分使用者慢怎麼查？

**核心答案**：**先按維度切分找出共同點**：**地區、網路類型（Wi-Fi/行動）、裝置、瀏覽器、以及時間段**。**如果慢的使用者集中在某個維度上——那個維度就是線索**。**而如果分布均勻，那更可能是「請求本身的差異」**（**例如某類查詢特別慢，而那類使用者剛好都碰到了**）。

**詳細解析**：**「真實使用者監控（RUM）是回答這個問題的唯一途徑」**：伺服器端的日誌看不到客戶端的網路與渲染——**而合成監控（從固定地點定期探測）看不到真實使用者的多樣性**。**只有從真實瀏覽器上報的資料，才能按上述維度切分**。**而它的收集成本很低（一個小的 JS 片段加上 Performance API）**，**回報卻很高**：**它把「有人說慢」變成「這個地區用行動網路的使用者 p75 是 4 秒」**——**後者是一個可以行動的事實**。**很多團隊有完整的伺服器端監控卻沒有 RUM**，**於是對「使用者實際體驗到什麼」完全沒有資料**——**而那正是最重要的那個數字**。

**面試回答方式**：給按維度切分的方法與兩種可能的結論。核心加分點是**RUM 是回答這個問題的唯一途徑**——**伺服器日誌看不到客戶端、合成監控看不到真實使用者的多樣性**，並指出**它的收集成本很低而回報很高**（把「有人說慢」變成可行動的事實）。收在觀察：**很多團隊有完整的伺服器端監控卻沒有 RUM，於是對使用者實際體驗到什麼完全沒有資料**。

### p99 遠高於 p50 的原因有哪些？

**核心答案**：**五類常見的**。**資源競爭**——**鎖、連線池、執行緒池的排隊**。**GC 停頓**——**在有 GC 的語言中很常見**。**快取未命中**——**多數命中而少數要走慢路徑**。**重試與逾時**——**特徵性的固定延遲（前面提過的 40 毫秒、1 秒、3 秒）**。**以及扇出的長尾**——**一個請求打到十個下游，最慢的那個決定整體。**

**詳細解析**：**「扇出的長尾放大」是分散式系統中最容易被低估的一類**：如果一個下游有 1% 的機率慢——**打十個下游時，「至少一個慢」的機率是 9.6%**；**打一百個就是 63%**。**於是「每個元件都很快」的系統，整體的 p99 卻很差**。**緩解的手段包括「對沖請求（hedged request）」**（**等待一小段時間後對慢的那個發第二份請求，取先回的**）——**它用少量的額外負載換取顯著的尾部改善**；**以及「盡量減少扇出的寬度」**。**這個「機率在扇出中被放大」的算術，是理解分散式系統延遲特性的關鍵**——**而它也解釋了為什麼「優化 p99」往往需要架構層面的改變而非單點的加速**。

**面試回答方式**：給五類常見原因。核心加分點是展開**扇出的長尾放大**並用機率算給對方看（**1% 的慢，打十個是 9.6%、打一百個是 63%**），指出**「每個元件都很快」的系統整體 p99 卻很差**。收在緩解手段與洞察：**對沖請求用少量額外負載換顯著的尾部改善**，**而這個算術解釋了為什麼優化 p99 往往需要架構層面的改變**。

### 怎麼設定合理的延遲目標？

**核心答案**：**從使用者的感知出發而非從技術能力出發**。**100 毫秒以內感覺是即時的**、**1 秒以內思緒不會中斷**、**10 秒是注意力的極限**——**這是經典的人機互動研究結論**。**所以互動式操作的目標應該是「p95 在 1 秒內」而非「平均 500 毫秒」**——**因為使用者感受的是自己遇到的那次，而非平均**。

**詳細解析**：**「用分位數而非平均值設目標」是這個判斷的核心**：一個平均 200 毫秒但 p99 是 5 秒的系統——**每 100 次操作中有一次讓使用者明顯感到卡頓**；**而如果一個工作階段有 50 次操作，那麼有四成的工作階段會遇到至少一次卡頓**。**這個計算把「p99 只影響 1% 的請求」這個容易被輕視的說法，轉換成「影響四成的使用者體驗」**——**而後者的分量完全不同**。**所以在設定目標與排優先級時，應該用「工作階段層級的體驗」而非「請求層級的比例」來表達**——**這是一個溝通上的技巧，但它反映的是真實的影響。**

**面試回答方式**：給以使用者感知為基礎的三個門檻，並主張**互動式操作應該用 p95 而非平均值設目標**。核心加分點是把「p99 只影響 1%」轉換成工作階段層級的影響：**一個工作階段 50 次操作的話，四成的工作階段會遇到至少一次卡頓**，**而後者的分量完全不同**。收在建議：**用工作階段層級的體驗而非請求層級的比例來表達目標**——**這是溝通技巧但它反映的是真實影響**。
