# 題目

CDN 怎麼決定要不要快取？回源風暴怎麼防？

## 核心答案

**CDN 的快取決策依序看三個來源**：**你的 CDN 設定規則**（優先級最高，可以強制覆蓋）、**來源站回應的 `Cache-Control`**、**以及 CDN 的預設行為**（通常是「有 Cache-Control 就遵守，沒有就用預設或不快取」）。

**快取鍵預設是 URL**——**而「哪些查詢參數要納入鍵」是最重要的設定**：**把追蹤參數（`utm_source`）納入會讓同一個資源被快取很多份，命中率崩潰**；**而漏掉真正影響內容的參數會回傳錯的內容。**

**回源風暴（cache stampede）的防護有三層**。**請求合併（request coalescing）**——**同一個資源的並發回源請求只發一次，其餘等待結果**；**這是最重要的一項，多數 CDN 內建**。**過期後先回舊的再背景更新**（`stale-while-revalidate`）。**以及分層快取**——**邊緣節點回源到區域節點，區域節點才回來源站**；**於是來源站看到的請求數大幅減少。**

## 詳細解析

**「快取鍵的正規化是命中率的關鍵」**：一個帶了 `?utm_source=facebook&fbclid=xxx` 的 URL 與乾淨的 URL 是不同的鍵——**而那些參數對內容毫無影響**。**於是社群分享帶來的流量幾乎全部回源，命中率可能從 95% 掉到 50%**。**正確的做法是「明確列出要納入快取鍵的參數（白名單）而非排除不要的（黑名單）」**——**因為新的追蹤參數會不斷出現，而白名單天然免疫**。**這是一個「用白名單而非黑名單」在快取上的具體體現。**

**「分層快取的價值在來源站的保護」**：如果有 200 個邊緣節點，一個資源過期時可能有 200 個回源請求——**而加一層區域快取後，來源站只看到幾個（每個區域一個）**。**在大型 CDN 中這個層次可能有三層**。**而它的代價是「更新的傳播變慢」**（要逐層失效）——**所以主動清除（purge）的機制需要能穿透所有層。**

**「哪些內容適合放 CDN」比「怎麼設定」更根本**：靜態資源（JS、CSS、圖片、影片）——**理所當然**；**而 API 回應與 HTML 也可以，只要「對所有人相同」或者「能用 Vary 正確區分」**。**近年的趨勢是「把更多動態內容放到邊緣」**（邊緣運算、邊緣渲染）——**因為 RTT 是無法優化的物理限制，而把運算移近使用者是唯一的解**。

**「快取的失效比設定更難」**：一旦一個錯誤的回應被快取——**在它過期前所有使用者都會看到那個錯誤**。**所以「對可能出錯的動態內容設短快取」與「有可靠的 purge 機制」都是必要的**。**而更根本的預防是「不要快取錯誤的回應」**（多數 CDN 預設不快取 5xx，但 4xx 的行為需要確認）。

## 面試回答方式

先給快取決策的三個來源與**快取鍵的設定是最重要的**，再給回源風暴的三層防護並指出**請求合併最重要**。加分點有四個：**快取鍵的正規化是命中率的關鍵**——**追蹤參數讓社群流量幾乎全部回源，命中率可能從 95% 掉到 50%**，**而正確做法是白名單而非黑名單，因為新的追蹤參數會不斷出現**；**分層快取保護來源站**（200 個邊緣的回源變成每區一個）**與它的代價**（更新傳播變慢，purge 要能穿透所有層）；**哪些內容適合放 CDN 比怎麼設定更根本**，**而把運算移近使用者是 RTT 這個物理限制的唯一解**；以及**快取一個錯誤的回應的後果**與預防。

## 講稿

快取決策依序看三個來源，你的設定規則、來源站回應的快取標頭、還有預設行為。

而最重要的設定是快取鍵。預設是網址，於是一個帶了追蹤參數的網址跟乾淨的網址是不同的鍵，而那些參數對內容毫無影響。結果社群分享帶來的流量幾乎全部回源，命中率可能從九成五掉到五成。

正確的做法是明確列出要納入快取鍵的參數，用白名單而不是排除不要的黑名單。因為新的追蹤參數會不斷出現，而白名單天然免疫。

回源風暴的防護有三層。最重要的是請求合併，同一個資源的並發回源只發一次，其餘等待結果，多數服務內建。第二是過期後先回舊的再背景更新。第三是分層快取，如果有兩百個邊緣節點，一個資源過期時可能有兩百個回源請求，而加一層區域快取後來源站只看到幾個。

還有一點，快取一個錯誤的回應很危險，因為在它過期前所有使用者都會看到。所以動態內容要設短快取，而且要有可靠的主動清除機制。

## 常見追問

### CDN 的命中率該怎麼提升？

**核心答案**：**四個方向，按效益排序**。**正規化快取鍵**（前面提過，通常收益最大）。**延長快取時間**——**用內容雜湊命名讓靜態資源可以快取一年**。**提高可快取的比例**——**檢查哪些回應因為 `Cache-Control: no-cache` 或 `Set-Cookie` 而不被快取**（**很多框架預設對所有回應設 cookie，那會讓 CDN 拒絕快取**）。**以及分層與預熱。**

**詳細解析**：**「Set-Cookie 讓回應不可快取」是一個很常見卻難以察覺的問題**：多數 CDN 看到 `Set-Cookie` 就不快取（因為那通常意味著使用者特定的內容）——**而如果你的框架對每個回應都設一個 session cookie（即使是靜態資源），那些資源就全都不被快取**。**症狀是「命中率莫名其妙地低」，而原因藏在框架的預設行為中**。**檢查的方法是「看不被快取的回應有什麼共同點」**——**而 CDN 通常提供「未命中原因」的日誌欄位**。**這類「一個無關的設定導致快取失效」的問題，正是為什麼「命中率」應該是一個被持續監控的指標而非部署時檢查一次的東西。**

**面試回答方式**：給四個方向並指出**正規化快取鍵通常收益最大**。核心加分點是 **`Set-Cookie` 讓回應不可快取**——**框架對每個回應都設 session cookie 會讓靜態資源全都不被快取**，**症狀是命中率莫名其妙地低而原因藏在框架的預設行為中**。收在方法與原則：**看不被快取的回應有什麼共同點，而 CDN 通常提供未命中原因的欄位**，**這正是命中率應該被持續監控的原因**。

### 需要即時更新的內容怎麼用 CDN？

**核心答案**：**三種模式**。**短快取加高頻回源**——**簡單，但保護來源站的效果有限**。**長快取加主動清除（purge）**——**內容變更時主動通知 CDN 失效**；**這是最常用的，前提是「你知道什麼時候變了」**。**以及 `stale-while-revalidate`**——**過期後先回舊的、背景更新**；**使用者永遠不等待，代價是可能看到幾秒的舊內容。**

**詳細解析**：**「purge 的延遲與可靠性需要被理解」**：清除一個資源需要通知所有邊緣節點——**在大型 CDN 中這可能需要幾秒到幾十秒**；**而且某些節點可能失敗**。**所以「purge 之後立刻驗證」是不可靠的，而「依賴 purge 保證即時性」也有風險**。**更穩健的做法是「用版本化的 URL」**——**內容變了就是新的 URL，完全不需要 purge**（**這正是內容雜湊命名的優勢**）。**而對於「必須用同一個 URL」的內容（例如首頁），purge 加上短快取的組合是務實的選擇**。**這個「能用不可變的就不要用可變的」的判斷，在快取設計中反覆出現**——**因為不可變的東西沒有失效問題。**

**面試回答方式**：給三種模式與各自的取捨。核心加分點是**purge 的延遲與可靠性**——**通知所有邊緣可能需要幾秒到幾十秒且某些節點可能失敗**，**所以依賴它保證即時性有風險**。收在更穩健的做法與原則：**用版本化的 URL 完全不需要 purge**，**而「能用不可變的就不要用可變的」在快取設計中反覆出現，因為不可變的東西沒有失效問題**。

### 邊緣運算適合做什麼？

**核心答案**：**適合「輕量、低延遲、且不需要集中狀態」的處理**。典型場景：**A/B 測試的分流**、**基於地理或裝置的路由與重寫**、**認證的初步檢查**（驗證 token 的簽章）、**個人化的片段組裝**、**以及簡單的 API 聚合**。**不適合的是「需要存取中心資料庫」或「運算密集」的工作**——**因為邊緣節點的資源有限，而回中心取資料就失去了就近的意義。**

**詳細解析**：**「把決定移到邊緣」的價值在於它消除了一次往返**：傳統上「判斷使用者屬於哪個實驗組」需要打到來源站——**而在邊緣做完，使用者直接拿到對應的版本**。**在跨洲的場景中這省下 200 毫秒以上**。**而它的限制也很明確：邊緣沒有你的資料庫**。**近年的邊緣 KV 儲存（Cloudflare KV、Workers D1）填補了部分空缺**——**但它們是最終一致的且延遲特性不同**，**所以適合「讀多寫少且能容忍陳舊」的資料（設定、路由規則、A/B 分組）而非交易性資料**。**理解這個邊界，比列舉邊緣運算的功能更能判斷什麼該放上去。**

**面試回答方式**：給適合與不適合的分類與典型場景。核心加分點是**「把決定移到邊緣」的價值在於消除一次往返**——**跨洲場景中省下 200 毫秒以上**。收在邊界的理解：**邊緣沒有你的資料庫，而邊緣 KV 是最終一致的**，**所以適合讀多寫少且能容忍陳舊的資料而非交易性資料**——**理解這個邊界比列舉功能更能判斷什麼該放上去**。
