# 題目

一次 DNS 解析經過哪些步驟？為什麼改了 DNS 紀錄不會立刻生效？

## 核心答案

解析是**逐層快取加逐層委派**的過程。客戶端先查自己的快取（瀏覽器、作業系統、hosts 檔），沒有就問**本地遞迴解析器**（通常是 ISP 或公用 DNS）；解析器若也沒有快取，就從**根伺服器**開始問，根告訴它負責頂級網域的伺服器在哪，頂級網域再告訴它該網域的**權威伺服器**在哪，最後向權威伺服器取得實際紀錄。這條路上**每一層都會依 TTL 快取結果**。改了紀錄不會立刻生效，正是因為這些快取——舊值會在各層留存直到 TTL 過期，而且**有些解析器不完全遵守 TTL**（會設下限或延長），所以實際生效時間可能比你設定的更長。標準做法是**變更前先把 TTL 調短**（例如提前一天調成 60 秒），等舊的長 TTL 在各層過期後再修改紀錄，切換完成再把 TTL 調回。這個「先降 TTL、再改紀錄」的順序是遷移作業的基本功。

## 詳細解析

**遞迴與迭代的分工**：客戶端對本地解析器發出的是**遞迴查詢**（「幫我查到答案為止」），解析器對根、頂級網域、權威伺服器發出的是**迭代查詢**（「你知道就給答案，不知道就告訴我該問誰」）。理解這個分工才能解釋為什麼快取主要集中在解析器上——它是唯一走完全程的角色。

**常見紀錄型別與它們的取捨**：`A` 與 `AAAA` 指向 IP，`CNAME` 指向另一個名稱，`MX` 指郵件伺服器，`TXT` 常用於驗證與設定。要注意 **`CNAME` 不能與其他紀錄共存**，所以根網域通常不能用 `CNAME`（因為根網域必須有 `NS` 與 `SOA`）——這是把根網域指向 CDN 時的經典障礙，各家 DNS 服務商用不同的擴充做法（別名紀錄）繞過它。

**DNS 也是負載平衡與故障轉移的手段**：一個名稱可以對應多個 IP，解析器輪流回傳，達到粗粒度的分流；地理位置感知的 DNS 則依查詢來源回傳最近的節點，這是 CDN 的基礎。但用 DNS 做故障轉移的**反應速度受 TTL 限制**——即使把故障節點從紀錄中移除，仍有大量客戶端在快取過期前繼續連向它。所以 DNS 適合做粗粒度的分流，**不適合當成秒級的故障轉移機制**，那需要健康檢查加上負載平衡器或客戶端側的重試。

**排查時要分清哪一層的快取**：現象是「有些人看到新的、有些人看到舊的」時，要依序確認——權威伺服器上的紀錄是否已更新（直接指定權威伺服器查詢）、公用解析器的結果、以及本機的作業系統與瀏覽器快取。用工具指定不同的解析器查詢，可以快速定位是哪一層還沒更新。另外要記得檢查 **hosts 檔**，開發環境中它是最常被遺忘的覆蓋來源。

**DNS 的安全面向**：傳統 DNS 是**明文且無驗證**的，因此存在**快取污染**（攻擊者搶先回傳偽造的答案）與**竊聽**（觀察者知道你在造訪哪些網站）的問題。**DNSSEC** 用簽章解決真實性但不加密；**DoH 與 DoT** 把查詢包在 HTTPS 或 TLS 中解決隱私與竄改，代價是讓網路管理者失去可見度，因此在企業環境常有爭議。這是「隱私與可管理性衝突」的典型案例。

## 面試回答方式

先講**逐層委派加逐層快取**的流程（本機、遞迴解析器、根、頂級網域、權威），並指出遞迴與迭代的分工。接著直接回答「為什麼不會立刻生效」——各層依 TTL 快取，而且有些解析器不完全遵守 TTL。給出實務做法：**先降 TTL、等舊值過期、再改紀錄**。加分點有三個：`CNAME` 不能與其他紀錄共存，所以根網域指向 CDN 需要別名紀錄這類擴充；DNS 做故障轉移受 TTL 限制，不適合當秒級切換機制；以及排查時用指定解析器的方式逐層定位，並記得檢查 hosts 檔。

## 講稿

解析是逐層委派加上逐層快取。客戶端先查自己的快取，包括瀏覽器、作業系統跟 hosts 檔，沒有就問本地的遞迴解析器。解析器如果也沒快取，就從根伺服器開始問，根告訴它頂級網域的伺服器在哪，頂級網域再告訴它權威伺服器在哪，最後跟權威伺服器拿到紀錄。

這裡有個分工，客戶端對解析器發的是遞迴查詢，幫我查到答案為止。解析器對上面發的是迭代查詢，你知道就給、不知道就告訴我該問誰。所以快取主要集中在解析器，因為它是唯一走完全程的角色。

改了紀錄不會馬上生效，就是因為這條路上每一層都依 TTL 快取。而且有些解析器不完全遵守 TTL，會自己設下限，所以實際生效可能比設定的更久。

我的做法是先降 TTL 再改紀錄。提前一天把 TTL 調成六十秒，等舊的長 TTL 在各層過期之後才修改紀錄，切完再調回來。

另外提醒一點，用 DNS 做故障轉移的反應速度受 TTL 限制，就算把故障節點移掉，還是有大量客戶端在快取過期前繼續連過去。所以它適合粗粒度分流，不適合當秒級的故障切換。

## 常見追問

### 為什麼根網域不能設 CNAME？實務上怎麼解決？

**核心答案**：因為規範規定 **`CNAME` 不能與同名的其他紀錄共存**，而根網域必然要有 `NS` 與 `SOA` 紀錄，兩者衝突。所以想把根網域指向 CDN 或負載平衡器的名稱時，標準的 `CNAME` 用不了。實務上各家 DNS 服務商提供**別名類型的紀錄**（名稱各異）——它在對外回應時表現得像 `A` 紀錄（直接回 IP），但在後台會去解析目標名稱並跟隨其變化，等於在服務商側做掉了這層轉換。

**詳細解析**：另一個常見但較差的替代方案是**把根網域直接設成固定 IP**——問題是 CDN 或雲端負載平衡器的 IP 可能變動，一旦變了就要手動更新，而且失去了依地理位置回傳不同節點的能力。還有一種做法是**把根網域重新導向到 www 子網域**（子網域可以自由使用 `CNAME`），代價是多一次跳轉的延遲，但對 SEO 與快取都可接受，是很多網站的實際選擇。判斷依據是：**目標 IP 會不會變**與**能不能接受一次重新導向**。

**面試回答方式**：講清規範上的衝突（`CNAME` 不能與 `NS`、`SOA` 共存）與服務商的別名紀錄解法。加分點是給出兩個替代方案（固定 IP、重新導向到 www）與各自的代價，並給出判斷依據。

### DNS 快取污染是什麼？怎麼防？

**核心答案**：攻擊者搶在真正的權威回應之前，向解析器送出**偽造的回應**，解析器接受並快取，之後所有向它查詢的使用者都會被導向攻擊者控制的位址。傳統 DNS 之所以脆弱，是因為它**基於 UDP、明文、且驗證機制薄弱**——只靠查詢 ID 與埠號來配對回應，攻擊者可以嘗試猜測。防禦手段包括**來源埠號隨機化**（大幅增加猜測難度）、**DNSSEC**（用簽章驗證回應的真實性）、以及 **DoH 或 DoT**（把查詢放進加密通道，攻擊者看不到也插不進去）。

**詳細解析**：DNSSEC 解決的是**真實性**而非機密性——它讓你確定回應沒被竄改，但查詢內容仍是明文，觀察者依然知道你在查什麼。DoH 與 DoT 則相反，解決**機密性與傳輸中的竄改**，但不驗證權威資料本身的真實性。兩者其實是互補的，理想是同時使用。要注意 DoH 在企業環境有爭議——它讓 DNS 查詢混在一般 HTTPS 流量中，網路管理者失去了以 DNS 為基礎的過濾與可見度能力，因此不少組織會強制走內部解析器並阻擋外部的 DoH。這是安全需求（使用者隱私）與管理需求（企業管控）直接衝突的例子。

**面試回答方式**：講清攻擊原理（搶先偽造回應被快取）與傳統 DNS 的弱點來源。給三種防禦並釐清 DNSSEC 與 DoH 解決的是**不同的問題**（真實性 vs 機密性），兩者互補。加分點是點出 DoH 在企業環境的爭議，說明它是隱私與可管理性的直接衝突。

### DNS 解析很慢，可以怎麼優化？

**核心答案**：**減少查詢次數與縮短查詢路徑**。前端可以用 `dns-prefetch` 提前解析第三方網域、用 `preconnect` 連 TCP 與 TLS 都先建立好；減少頁面上的**第三方網域數量**同樣有效（每個新網域都是一次完整解析）。伺服器端則可以確保**權威伺服器分布合理**（多個地理位置）、TTL 設定平衡（太短增加查詢、太長影響變更速度）、以及使用有全球任播網路的 DNS 服務商縮短到權威的距離。

**詳細解析**：一個容易被忽略的成本是**CNAME 鏈過長**——每一層 `CNAME` 都可能需要額外的解析步驟，某些 CDN 或監控服務的設定會疊出三四層，累積的延遲相當可觀。排查時把整條鏈攤開來看是有價值的。另一個是**首次連線的成本集中在首屏**：使用者第一次造訪時所有網域都要解析，這正是首屏效能中容易被忽略的一塊。要注意 `preconnect` 應該節制使用——每個都佔用連線資源，過多反而拖慢，通常只對確定會用到的關鍵網域使用。

**面試回答方式**：分前端與伺服器端給手段，重點是減少查詢次數與縮短路徑。加分點是提到 CNAME 鏈過長的累積延遲、首次造訪的成本集中在首屏、以及 `preconnect` 要節制使用避免反效果。
