# 題目

要做「伺服器有新資料就通知前端」，這四種方案該怎麼選？

## 核心答案

判準是**方向、頻率與延遲要求**。**短輪詢**是客戶端定時發請求問「有沒有新的」——實作最簡單、相容性最好，代價是**大量無效請求**與**延遲等於輪詢間隔**，適合更新不頻繁且延遲要求寬鬆的場景（例如每分鐘刷新一次的狀態）。**長輪詢**是請求送出後伺服器先不回應，等到有資料或逾時才回，客戶端收到後立刻再發一個——延遲低得多，但每次推送都要重建請求，連線管理成本高。**SSE** 是伺服器**單向**持續推送的標準機制，基於一般的 HTTP，**自帶自動重連與事件 ID 續傳**，適合通知、進度、即時看板這類「只需要伺服器往下推」的場景。**WebSocket** 提供**全雙工**的長連線，適合雙向高頻互動（聊天、協作編輯、遊戲），代價是它脫離了 HTTP 的語意，快取、壓縮、認證、負載平衡都要另外處理。多數需求其實只需要單向推送，SSE 就夠了——一上來就選 WebSocket 是常見的過度設計。

## 詳細解析

**SSE 被嚴重低估**：它是純 HTTP，因此**沿用既有的認證、代理、CDN 與監控**，不需要為它另建一套。瀏覽器端的介面內建了**自動重連**與**事件 ID**——斷線後重連時會把最後收到的 ID 帶回去，伺服器可以從那裡續傳，這對「不能漏訊息」的場景非常實用。它的限制是**單向**（客戶端要送資料仍用一般請求，通常沒問題）與**在 HTTP/1.1 下佔用一條連線**（受同網域連線數限制，但在 HTTP/2 之上因為多工而不成問題）。

**WebSocket 的隱藏成本**：它從 HTTP 升級而來，之後就是自訂的訊框協定，於是**你要自己處理很多事**——心跳與斷線偵測（TCP 層的斷線可能很久才被發現）、重連與退避、訊息的序列化與版本演進、認證（升級握手時只能用 Cookie 或查詢參數帶憑證，兩者各有問題）、以及**水平擴展**（連線是有狀態的，訊息要送到「持有那條連線的那台機器」，通常需要一層訊息匯流排）。這些成本在原型階段看不到，在正式環境全部要付。

**長輪詢仍有它的位置**：在必須相容老舊環境、或代理設備會切斷長連線的網路中，長輪詢的相容性最好。它的實作要點是伺服器端的等待不能佔住執行緒——用非同步或事件驅動的方式掛起請求，否則連線數一多就把執行緒池耗光。這也是為什麼在同步阻塞的框架上做長輪詢特別容易出事。

中間設備是實務上的頭號殺手：企業代理、負載平衡器、雲端閘道往往對**閒置連線設有逾時**（常見 30 到 60 秒），會直接切斷看似沒有流量的長連線。所以不論 SSE 或 WebSocket，**應用層心跳幾乎是必備的**——定期送出小訊息維持活躍，同時也用來偵測對端是否還在。忘記加心跳造成「連線莫名其妙每分鐘斷一次」是非常典型的問題。

**選型的實務順序**：先問**需不需要客戶端也頻繁推送**——不需要就先考慮 SSE。再問**延遲要求**——分鐘級就用短輪詢，最簡單。只有在雙向高頻的場景才用 WebSocket。要注意這個選擇也影響**擴展方式**：無狀態的輪詢可以任意水平擴展，長連線方案則需要處理連線與訊息路由的關係。

## 面試回答方式

用**方向、頻率、延遲**三個判準組織回答，並依複雜度由低到高介紹四種方案。核心主張要明確：多數需求只需要單向推送，SSE 就夠了，一上來選 WebSocket 是常見的過度設計。SSE 的優勢要具體講——純 HTTP 所以沿用既有基礎設施、自帶自動重連與事件 ID 續傳。WebSocket 的成本也要具體講——心跳、重連、認證、水平擴展都要自己處理。加分點是提到**中間設備的閒置逾時**會切斷長連線，所以應用層心跳幾乎必備，這是最常見的實務故障；以及長輪詢的伺服器端必須非同步掛起，否則會耗光執行緒池。

## 講稿

我用三個判準來選，方向、頻率、還有延遲要求。

短輪詢就是定時去問有沒有新的。實作最簡單、相容性最好，缺點是大量無效請求，而且延遲等於輪詢間隔。更新不頻繁、延遲要求寬鬆的話它其實很夠用。

長輪詢是請求送出去之後伺服器先不回，等到有資料或者逾時才回。延遲低很多，但每次推送都要重建請求。實作上要注意伺服器端的等待不能佔住執行緒，要用非同步的方式掛起，不然連線一多就把執行緒池耗光。

SSE 是伺服器單向持續推送，它是純 HTTP，所以可以沿用既有的認證、代理、監控，不用另建一套。而且瀏覽器端內建自動重連跟事件 ID，斷線重連會把最後收到的 ID 帶回去，伺服器可以從那裡續傳。

WebSocket 是全雙工，適合聊天、協作編輯這種雙向高頻的場景。但它脫離了 HTTP 語意，心跳、重連、認證、水平擴展都要自己處理。

我的立場是多數需求其實只要單向推送，SSE 就夠了。一上來就選 WebSocket 是常見的過度設計。

另外不管哪一種長連線，應用層心跳幾乎是必備的，因為中間設備常常對閒置連線設逾時。

## 常見追問

### WebSocket 要怎麼做水平擴展？

**核心答案**：核心問題是**連線是有狀態的**——使用者的連線握在某一台機器上，而產生訊息的可能是另一台。標準解法是引入一層**訊息匯流排**（Redis 的發布訂閱、Kafka 或專用的訊息服務）：任何一台機器要推送訊息時發布到匯流排，所有機器訂閱並判斷「這個目標使用者的連線是不是在我這裡」，是的話就推送出去。這樣任一台都能觸發推送，不必知道連線在哪。

**詳細解析**：延伸的設計考量有三個。**連線與使用者的對應**要維護在共用儲存中，才能做「這個使用者在線嗎」這類查詢，並在斷線時清理（要處理機器崩潰導致的殘留）。**廣播的成本**——若採用「全部機器都收到再各自過濾」的做法，訊息量會隨機器數線性放大，量大時要改成依使用者分片的主題。**優雅關閉**——部署時要讓客戶端有序重連而不是同時斷線重連造成尖峰，做法是分批關閉並在關閉前送出提示，讓客戶端加上隨機退避。最後這一點常被忽略，但它是每次部署都會遇到的實際問題。

**面試回答方式**：核心是用訊息匯流排解耦「誰產生訊息」與「連線在哪台」。加分點是三個延伸考量：連線對應要存共用儲存並處理殘留、廣播成本要靠分片主題控制、以及部署時要分批關閉加隨機退避避免重連尖峰。

### 長連線斷開了要怎麼保證不漏訊息？

**核心答案**：靠**序號與續傳**。伺服器為每個訊息分配遞增的 ID，客戶端記錄最後收到的 ID；重連時把它帶回去，伺服器從該位置之後補送。SSE 內建了這個機制（重連時自動帶上最後的事件 ID），WebSocket 則要自己實作。伺服器端需要保留一段時間的歷史訊息以供補送，保留多久取決於可接受的離線時長。

**詳細解析**：要處理的細節有三個。**保留窗口有限**——離線太久超出保留範圍時，應該明確告訴客戶端「無法續傳，請重新取得完整狀態」，而不是靜默漏掉訊息。**重複與亂序**——網路重試可能造成重複推送，客戶端應該依 ID 去重。**訊息量大時的取捨**——若離線期間累積了上萬條訊息，逐條補送可能拖垮客戶端，這時改為「回傳目前的完整狀態」比補送全部歷史更合理。這個「補增量 vs 給全量」的判斷在同步機制設計中反覆出現，能講出切換的門檻會顯得有實作經驗。

**面試回答方式**：給出序號加續傳的核心機制，並說明 SSE 內建、WebSocket 要自己做。加分點是三個細節：超出保留窗口要明確告知而非靜默漏掉、客戶端要依 ID 去重、以及累積太多時改為回傳完整狀態比逐條補送合理。

### 為什麼說中間設備是長連線的頭號殺手？

**核心答案**：因為代理、負載平衡器、雲端閘道與 NAT 設備普遍對**閒置連線設有逾時**，短則 30 秒長則數分鐘。長連線在沒有訊息時看起來就是閒置的，於是被中途切斷——而且**兩端不一定會立刻知道**，客戶端可能以為連線還在、持續等待永遠不會來的訊息。這造成的症狀是「連線莫名其妙定期斷開」或「訊息突然收不到但沒有錯誤」。

**詳細解析**：解法是**應用層心跳**——定期送出小訊息（WebSocket 有專用的訊框，SSE 可以送註解行），既維持連線活躍，也用來偵測對端是否還在。心跳間隔要**小於路徑上最短的閒置逾時**，實務上常設在 30 秒以下。要注意不能只靠 TCP 的 keepalive，因為它的預設間隔通常是數小時，遠遠不夠用，而且它偵測的是 TCP 連線而非應用是否還能正常處理。另外客戶端也需要**逾時偵測**——若超過一定時間沒收到任何訊息（含心跳），主動關閉並重連，不要無限期等待。這一對「送心跳」與「等不到就重連」必須成對實作才有意義。

**面試回答方式**：講清閒置逾時的機制與「兩端不一定知道」造成的難查症狀。給出應用層心跳的解法與間隔要小於路徑最短逾時。加分點是指出不能只靠 TCP keepalive（間隔太長且偵測層次不同），以及心跳要與客戶端的逾時重連成對實作。
