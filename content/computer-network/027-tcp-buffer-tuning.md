# 題目

TCP 的傳送與接收緩衝區各自影響什麼？什麼時候需要調？

## 核心答案

**接收緩衝區決定了「對方能一次送多少而不用等」**——**因為接收視窗就是「接收緩衝區的剩餘空間」**；**它太小的話，發送方會被流量控制限制，即使網路頻寬充足。**

**傳送緩衝區決定了「應用能寫入多少而不被阻塞」**——**它是應用與核心之間的緩衝**；**太小的話，應用的 write 會頻繁阻塞（或者在非阻塞模式下返回 EAGAIN）。**

**需要調整的典型場景是「高頻寬延遲積（BDP）的鏈路」**：**跨洲的連線、或者高速的資料傳輸**。**BDP = 頻寬 × 往返延遲**——**例如 1Gbps 加 100 毫秒的 RTT，BDP 就是 12.5MB**；**如果緩衝區只有 64KB，實際吞吐會被限制在 5Mbps 左右，只有頻寬的百分之零點五。**

**而現代 Linux 預設開啟自動調整（`tcp_moderate_rcvbuf`）**——**於是多數情況不需要手動設定，只需要確認自動調整的上限（`tcp_rmem` 的第三個值）夠大。**

## 詳細解析

**「BDP 的計算是這個問題的核心，而它常被忽略」**：吞吐的上限是 `視窗大小 / RTT`——**於是在延遲高的鏈路上，小視窗會嚴重限制吞吐**，**而那個限制與實際的頻寬完全無關**。**這解釋了一個常見的困惑：「兩邊都是千兆網路，為什麼跨區傳輸只有幾 Mbps」**——**答案往往就是視窗不夠大**。**而「窗口縮放選項（window scaling）」正是為了突破 TCP 標頭中 16 位元視窗欄位（最大 64KB）的限制**——**沒有它，任何高 BDP 的鏈路都無法達到高吞吐**。

**「手動設定會關閉自動調整」是一個容易踩的坑**：如果應用用 `setsockopt` 明確設定了 `SO_RCVBUF`——**核心的自動調整就不再生效**。**於是「為了優化而手動設定」可能反而讓效能變差**（**因為固定值無法適應不同的連線特性**）。**所以正確的做法通常是「調整系統層級的自動調整上限，而不是在應用中固定設定」**。

**「緩衝區不是越大越好」**：過大的緩衝區會造成 **bufferbloat**——**大量資料排在緩衝區中，導致延遲上升而吞吐沒有提升**。**尤其在中間設備（路由器、交換機）的緩衝區過大時，這個問題會非常明顯**：**封包不丟了，但排隊延遲變成幾百毫秒**——**而 TCP 的擁塞控制依賴丟包作為訊號，於是它感知不到擁塞並繼續加速**。**這正是 BBR 這類「基於延遲與頻寬估計」的擁塞控制被開發出來的原因。**

**「調校前先確認瓶頸」**：如果吞吐低是因為 CPU、磁碟、或應用邏輯——**調緩衝區完全沒用**。**判斷的方法是看「發送方的傳送佇列是否積壓」與「接收方的接收佇列是否積壓」**（`ss -ti` 能看到）——**前者表示網路是瓶頸，後者表示應用讀取太慢。**

## 面試回答方式

先分別給兩個緩衝區的作用，並用 **BDP 的計算**說明什麼時候需要調（1Gbps 加 100 毫秒 RTT 就是 12.5MB，64KB 的緩衝會把吞吐限制在 5Mbps）。指出**現代 Linux 預設自動調整，多數情況只需確認上限夠大**。加分點有四個：**BDP 解釋了「兩邊都是千兆為什麼跨區只有幾 Mbps」**，**而窗口縮放選項正是為了突破 16 位元視窗欄位的限制**；**手動設定會關閉自動調整**，**所以「為了優化而手動設定」可能反而更差**；**緩衝區不是越大越好**——**bufferbloat 讓封包不丟但排隊延遲幾百毫秒，而 TCP 依賴丟包作為訊號於是感知不到擁塞**，**這正是 BBR 被開發的原因**；以及**調校前先確認瓶頸**，並給出判斷方法。

## 講稿

接收緩衝區決定了對方能一次送多少而不用等，因為接收視窗就是接收緩衝區的剩餘空間。傳送緩衝區決定了應用能寫入多少而不被阻塞。

需要調整的典型場景是高頻寬延遲積的鏈路。這個乘積是頻寬乘往返延遲。舉例來說，一 Gbps 加上一百毫秒的往返，乘積就是十二點五 MB。如果緩衝區只有六十四 KB，實際吞吐會被限制在五 Mbps 左右，只有頻寬的千分之五。

這解釋了一個常見的困惑，兩邊都是千兆網路，為什麼跨區傳輸只有幾 Mbps。答案往往就是視窗不夠大。

但緩衝區不是越大越好。過大會造成緩衝區膨脹，大量資料排在緩衝區中，延遲上升而吞吐沒提升。尤其中間設備的緩衝過大時特別明顯，封包不丟了但排隊延遲變成幾百毫秒。而傳統的擁塞控制依賴丟包作為訊號，於是它感知不到擁塞並繼續加速。這正是基於延遲與頻寬估計的新演算法被開發出來的原因。

還有一個坑，如果應用明確設定了緩衝區大小，核心的自動調整就不再生效。所以通常應該調系統層級的上限，而不是在應用中固定設定。

## 常見追問

### 怎麼看一條連線的實際狀況？

**核心答案**：**用 `ss -ti`**——**它會顯示每條連線的 RTT、擁塞視窗（cwnd）、慢啟動閾值（ssthresh）、重傳次數、以及傳送與接收佇列的長度**。**這些數字直接告訴你「這條連線的瓶頸在哪」**：**cwnd 很小加上大量重傳表示網路品質差**；**接收佇列積壓表示應用讀取太慢**；**傳送佇列積壓表示網路送不出去。**

**詳細解析**：**「cwnd 與 RTT 一起看能算出理論吞吐」**：`吞吐 ≈ cwnd × MSS / RTT`——**於是你能判斷「當前的吞吐是不是已經達到這條連線的上限」**。**如果算出來的理論值遠高於實際觀察到的吞吐，那瓶頸不在網路而在應用或磁碟**。**這個計算把「感覺網路慢」變成一個可以驗證的假設**。**另一個實用的觀察是 `retrans` 的比例**：**重傳率超過百分之一通常就是明顯的網路問題**（**而百分之零點一以下是正常的**）。**而如果重傳率高但 cwnd 沒有降下來，可能是「假重傳」（封包只是亂序到達而非丟失）**——**那需要不同的處理（開啟 SACK 與 F-RTO）**。

**面試回答方式**：給 `ss -ti` 與它顯示的關鍵指標，以及各自對應的瓶頸判斷。核心加分點是**cwnd 與 RTT 一起看能算出理論吞吐**——**如果理論值遠高於實際觀察，瓶頸就不在網路**，**這把「感覺網路慢」變成可驗證的假設**。收在重傳率的判斷：**超過百分之一是明顯問題、百分之零點一以下正常**，**而重傳高但 cwnd 沒降可能是假重傳，需要 SACK 與 F-RTO**。

### 應用層的緩衝與 TCP 緩衝怎麼配合？

**核心答案**：**應用層的緩衝負責「組裝完整的邏輯訊息」，TCP 緩衝負責「網路傳輸的流量控制」**——**兩者的目的不同，不應該互相替代**。**常見的錯誤是「應用逐個小片段寫入，指望 TCP 緩衝去合併」**——**那會受 Nagle 的影響或者產生大量小封包**；**正確的做法是應用自己組裝好再一次寫出。**

**詳細解析**：**「write 返回不代表資料送出去了」是一個必須理解的語義**：`write()` 成功只代表「資料被複製進了核心的傳送緩衝區」——**它可能還在排隊、可能還沒被對方收到、甚至連線可能已經斷了**。**所以「write 成功」不能作為「對方收到了」的證據**——**任何需要確認的語義都必須在應用層實作**（回應、ACK 訊息、或者確認機制）。**這個誤解在寫網路程式時很常見，而它的後果是「以為送出去了但實際上丟了」**。**同樣的道理，`close()` 也不保證緩衝區中的資料被送達**——**雖然預設行為會嘗試送完（除非設了 SO_LINGER）**。**理解「核心緩衝是一層非同步的間接」，是寫可靠網路程式的基礎。**

**面試回答方式**：給兩者目的的區分與常見錯誤。核心加分點是**write 返回不代表資料送出去了**——**它只代表被複製進核心緩衝區，可能還在排隊、沒被收到、甚至連線已斷**，**所以「write 成功」不能作為「對方收到了」的證據，任何確認語義都要在應用層實作**。收在延伸：**close 也不保證緩衝中的資料送達**，**而理解「核心緩衝是一層非同步的間接」是寫可靠網路程式的基礎**。

### 容器環境下這些設定怎麼處理？

**核心答案**：**多數 TCP 參數是核心層級的，容器共用宿主的核心**——**所以容器內看到的 `/proc/sys/net/...` 多數是宿主的設定**。**部分參數在網路命名空間內是獨立的（可以在容器內調整），而部分是全域的（需要在宿主調）**。**Kubernetes 用 `sysctls` 欄位允許設定「安全的」命名空間級參數**，**而其他的需要特權容器或在節點上調整。**

**詳細解析**：**「哪些參數是命名空間級的」需要具體確認而非猜測**：例如 `net.ipv4.tcp_keepalive_time` 與 `net.ipv4.ip_local_port_range` 是命名空間級的（可以在 Pod 中設定）——**而 `net.core.somaxconn` 在較新的核心中也是**。**但 `net.ipv4.tcp_rmem` 這類則需要在節點層級調整**。**而更根本的建議是「先確認真的需要調」**：**多數應用在預設值下運作良好**——**而在容器環境中調整核心參數增加了部署的複雜度與環境的耦合**。**所以應該先用前面提到的方法確認瓶頸真的在 TCP 層**，**而不是把調參數當成效能問題的第一反應**。**這個「先診斷再調參」的順序，能避免大量無效的複雜度**。

**面試回答方式**：說明**多數 TCP 參數是核心層級、容器共用宿主核心**，並區分命名空間級與全域的參數與 Kubernetes 的處理方式。核心加分點是指出**哪些是命名空間級的需要具體確認而非猜測**並舉例。收在更根本的建議：**先確認真的需要調**——**多數應用在預設值下運作良好，而在容器環境調核心參數增加部署複雜度與環境耦合**，**所以應該先診斷再調參**。
