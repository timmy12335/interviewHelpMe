# 題目

gRPC 在網路層有什麼特別的？為什麼負載會不均？

## 核心答案

gRPC 建立在 HTTP/2 上，而它的兩個特性直接造成了網路層的差異。

**長連線加多路複用**——**一條連線承載大量的請求**；於是「連線級的負載平衡」完全失效：四層負載平衡器把一條連線固定分給一台後端，而那條連線上的所有請求都去那裡。結果是「加了後端但流量沒有分過去」。

**串流**——一個 RPC 可能持續很久（伺服器串流、雙向串流）；於是「請求級的統計」與「逾時的設定」都與傳統的請求回應不同。

**解法有三條路**：用支援 HTTP/2 的七層負載平衡器（能在請求級別分流）、用客戶端側負載平衡（客戶端拿到所有後端位址自己輪詢）、或者用 service mesh 的 sidecar（本質上是把七層負載平衡放到本地）。

## 詳細解析

「四層負載平衡下 gRPC 的負載不均」是一個很典型的現象：假設有 10 個客戶端與 5 個後端——每個客戶端建立一條連線，於是最多只有 10 條連線分佈在 5 台上；而如果分佈不均（某台拿到 3 條、某台拿到 1 條），流量就是 3 比 1。更糟的是「後端擴容時沒有效果」——新的後端沒有既有的連線，除非客戶端重新連線。所以「gRPC 加四層負載平衡」在擴容時的表現特別差，而這是很多團隊在遷移到 gRPC 之後遇到的第一個意外。

「客戶端側負載平衡」是 gRPC 的原生方案：客戶端透過 DNS（headless Service）或者一個解析器拿到所有後端的位址——對每個建立連線，然後在請求級別輪詢。**優點是沒有中間跳、延遲最低**；缺點是客戶端要處理後端的變化（新增、移除、健康狀態），而那需要 SDK 的支援與正確的設定。在 Kubernetes 中，這需要用 headless Service 並讓 gRPC 客戶端定期重新解析——否則它會一直用最初解析到的那組位址。

**「keepalive 的設定很重要」**：長連線可能被中間設備（NAT、負載平衡器）因為閒置而清理——而 gRPC 的客戶端不知道，直到下次發請求才發現連線已死。所以應該設定 gRPC 的 keepalive（週期性發送 HTTP/2 的 PING）——它既保持連線活著，也能及時偵測到斷開。但要注意伺服器端也要允許那個頻率（`GRPC_ARG_KEEPALIVE_PERMIT_WITHOUT_CALLS` 與最小間隔），否則伺服器會認為客戶端在濫發 PING 而斷開連線——這是一個雙方設定必須匹配的例子。

**「deadline 的傳遞」是 gRPC 一個做得好的設計**：客戶端設定的 deadline 會隨呼叫傳遞到下游——於是整條鏈路共享同一個截止時間，避免了「上游已經放棄而下游還在做」的浪費。這是很多 REST 系統需要自己實作的東西，**而在 gRPC 中是內建的。**

## 面試回答方式

先給兩個特性（長連線加多路複用、串流）與**連線級負載平衡完全失效**這個直接後果，再給三條解法。加分點有四個：**用具體的數字說明負載不均**（10 個客戶端 5 個後端可能是 3 比 1）與「擴容時沒有效果」這個更糟的表現；客戶端側負載平衡是原生方案與它在 Kubernetes 中的實作要點（headless Service 加定期重新解析）；**keepalive 的雙方設定必須匹配**——否則伺服器會認為客戶端濫發 PING 而斷開；以及**deadline 的傳遞是 gRPC 做得好的設計**，避免「上游已放棄而下游還在做」的浪費。

## 講稿

它建立在二版的超文字傳輸協定上，而兩個特性直接造成網路層的差異。

第一是長連線加多路複用，一條連線承載大量請求。於是連線級的負載平衡完全失效。四層負載平衡器把一條連線固定分給一台後端，而那條連線上的所有請求都去那裡。結果是加了後端但流量沒有分過去。

具體來說，假設十個客戶端五個後端，每個客戶端一條連線，如果分佈不均可能是三比一。更糟的是擴容時完全沒有效果，因為新的後端沒有既有連線，除非客戶端重新連線。這是很多團隊遷移之後遇到的第一個意外。

解法有三條路。用支援二版協定的七層負載平衡器、用客戶端側負載平衡、或者用服務網格的邊車。

還有一個設定要注意。長連線可能被中間設備因為閒置而清理，而客戶端不知道直到下次發請求。所以要設定保活探測。但伺服器端也要允許那個頻率，否則它會認為客戶端在濫發而斷開連線。這是一個雙方設定必須匹配的例子。

## 常見追問

### gRPC 的錯誤處理與 HTTP 有什麼不同？

**核心答案**：**gRPC 有自己的一套狀態碼**（`OK`、`INVALID_ARGUMENT`、`NOT_FOUND`、`DEADLINE_EXCEEDED`、`UNAVAILABLE` 等）——而它們透過 HTTP/2 的 trailer 傳遞，不是 HTTP 的狀態碼。**所以「HTTP 200 但 gRPC 狀態是錯誤」是正常的**——這讓「只看 HTTP 狀態碼的監控」對 gRPC 完全失效。

**詳細解析**：「監控與可觀測性工具的相容性」是採用 gRPC 時一個實際的成本：既有的以 HTTP 狀態碼為基礎的告警、儀表板、與負載平衡器的健康判斷——都需要理解 gRPC 的狀態碼才能正確運作。現代的工具多數已經支援（能解析 `grpc-status` trailer），**但舊的或自建的可能不行**。所以遷移時應該明確檢查「我的監控看得到 gRPC 的錯誤嗎」——否則會出現「錯誤率顯示 0% 而使用者一直失敗」的情況。而這類「換了協定但周邊工具沒跟上」的問題，在任何協定遷移中都值得被檢查——因為它的症狀是「看起來一切正常」，而那是最危險的失效模式。

**面試回答方式**：給 gRPC 自己的狀態碼與**透過 trailer 傳遞而非 HTTP 狀態碼**，指出**「HTTP 200 但 gRPC 錯誤」是正常的**。核心加分點是監控工具的相容性是實際的成本——以 HTTP 狀態碼為基礎的告警與健康判斷都需要理解 gRPC 的碼，否則會出現「錯誤率顯示 0% 而使用者一直失敗」。收在原則：「換了協定但周邊工具沒跟上」在任何遷移中都值得檢查，因為它的症狀是「看起來一切正常」，那是最危險的失效模式。

### gRPC 能穿透瀏覽器嗎？

**核心答案**：**原生的不行，需要 gRPC-Web**。因為瀏覽器的 fetch/XHR API **無法完全控制 HTTP/2 的幀**（例如無法讀取 trailer、無法做雙向串流）——**所以 gRPC-Web 定義了一個相容的子集**：支援一元呼叫與伺服器串流，但不支援客戶端串流與雙向串流。而它通常需要一個代理（Envoy 或 grpcwebproxy）做協定轉換。

**詳細解析**：「協定的能力受限於執行環境」是這裡的普遍教訓：gRPC 假設了對傳輸層的完整控制——而瀏覽器出於安全與抽象的考量不提供那種控制。於是「同一個服務要同時給後端與瀏覽器用」需要兩套介面或者一層轉換。近年的 Connect 協定與 gRPC 的 HTTP/JSON 轉碼（transcoding）提供了更順暢的方案——讓同一個服務定義能同時暴露 gRPC 與 REST 風格的介面。這是一個「用工具消除重複而非要求開發者維護兩套」的改進，而它反映了一個實際的需求：多數服務既有內部的呼叫方也有瀏覽器的呼叫方。

**面試回答方式**：回答不行並說明原因（**瀏覽器 API 無法完全控制 HTTP/2 的幀**）與 gRPC-Web 的限制（不支援客戶端串流與雙向串流）及對代理的需求。核心加分點是提煉教訓：**協定的能力受限於執行環境**——gRPC 假設對傳輸層的完整控制而瀏覽器不提供。收在現代方案：Connect 協定與 HTTP/JSON 轉碼讓同一個服務定義同時暴露兩種介面，**是「用工具消除重複」的改進**。

### 什麼時候該用 gRPC 而非 REST？

**核心答案**：內部服務之間的高頻呼叫、需要串流、或者需要強型別的契約時。gRPC 的優勢是二進位序列化（更小更快）、明確的介面定義與程式碼產生、以及原生的串流支援。而 REST 的優勢是「到處都通、人能直接讀、工具生態成熟、瀏覽器原生支援」——所以對外的 API 與需要廣泛相容的場景，REST 通常仍是更好的選擇。

**詳細解析**：「強型別契約的價值在多團隊環境中最明顯」：`.proto` 檔案是一份可執行的契約——它產生客戶端與伺服器的程式碼，於是「介面不匹配」在編譯期就被發現。而 REST 的 OpenAPI 規格雖然也能產生程式碼，但它是「描述」而非「來源」——實作可能與規格不符而沒有任何機制阻止。這個差別在「幾十個服務、多個團隊」的環境中價值很大。但也要說清楚代價：`.proto` 的變更需要協調與重新產生程式碼——於是「快速改一個欄位」變得比 REST 麻煩。所以判斷的關鍵是「介面的穩定性與團隊的協調成本」：穩定且跨團隊的用 gRPC，快速迭代且單團隊的用 REST 可能更靈活。

**面試回答方式**：給各自的優勢與適用場景，並指出對外 API 與需要廣泛相容時 REST 通常更好。核心加分點是強型別契約的價值在多團隊環境中最明顯——`.proto` 是可執行的契約讓介面不匹配在編譯期被發現，而 OpenAPI 是描述而非來源。收在代價與判準：`.proto` 的變更需要協調與重新產生程式碼，所以關鍵是「介面的穩定性與團隊的協調成本」。
