# 題目

什麼是「黏包」？為什麼 TCP 會有這個問題而 UDP 沒有？

## 核心答案

因為 **TCP 是位元組流，沒有訊息邊界的概念**。應用程式呼叫兩次寫入各送 100 位元組，TCP 只保證這 200 位元組**按序抵達**，不保證對方會分成兩次讀到——可能一次讀到 200（黏包），也可能讀到 60 加 140（拆包）。造成這個現象的原因有好幾層：發送端的 Nagle 演算法會把小資料合併、TCP 依據 MSS 切分大資料、接收端的緩衝區也是連續的位元組空間。所以「黏包」其實**不是 TCP 的 bug，而是把它當成訊息協定使用的誤解**。UDP 沒有這個問題，因為它是資料報，一次送出對應一次讀取、邊界被保留。解法是**在應用層自己定義訊息邊界**，標準做法有三種：**固定長度**（簡單但浪費且不彈性）、**分隔符**（適合文字協定，但內容中出現分隔符時要跳脫）、以及**長度前綴**（最通用，先讀固定長度的長度欄位，再讀對應長度的內容）。實務上二進位協定幾乎都用長度前綴。

## 詳細解析

**長度前綴是最穩健的做法**：協定的每個訊息開頭放一個固定寬度的長度欄位（常見 4 位元組），接收端先讀滿這幾個位元組得知長度，再讀滿對應長度的內容。實作要點是**必須處理讀不滿的情況**——一次讀取可能只拿到長度欄位的一半，所以要在緩衝區中累積直到湊滿，這是新手最常寫錯的地方。另外要**限制最大長度**，否則惡意的超大長度值會讓伺服器嘗試配置巨量記憶體，形成阻斷服務漏洞。

**分隔符方案的陷阱**：文字協定（HTTP 標頭、Redis 協定）常用換行當分隔符，好處是人類可讀、也方便用文字工具除錯。陷阱是**內容中出現分隔符**時必須跳脫或編碼，否則會被錯誤切分——這也是某些注入類漏洞的來源（在使用者輸入中塞入換行來偽造額外的協定欄位）。所以用分隔符時，對使用者輸入的驗證與跳脫是必要的安全措施而不只是正確性問題。

**混合式協定很常見**：HTTP 就是典型——標頭部分用換行分隔，主體部分用 `Content-Length` 這個長度前綴（或用分塊傳輸編碼，每一塊自帶長度）。這個組合兼顧了標頭的可讀性與主體的二進位安全。理解 HTTP 的分幀方式，也就理解了為什麼標頭與主體之間需要一個空行。

**框架幫你做掉了，但不代表可以不懂**：Netty 這類網路框架提供現成的解碼器（固定長度、分隔符、長度欄位），多數人不必手寫。但**選錯解碼器或參數配錯**仍會出問題，而且在排查「訊息偶爾錯亂」的問題時，必須理解底層在做什麼才查得出來。此外自訂協定時仍要自己決定分幀方式與最大長度限制。

**為什麼有些人說「UDP 也有黏包」**：這是誤解。UDP 保留邊界，一次 `sendto` 對應一次 `recvfrom`。但 UDP 有另一個問題——**單個資料報超過路徑 MTU 時會在 IP 層分片**，任一片遺失整個資料報就報廢，所以大訊息用 UDP 要自己分片與重組。這是不同的問題，講清楚這個區分能避免把兩件事混為一談。

## 面試回答方式

先把根因講對——**TCP 是位元組流，沒有訊息邊界**，所以這不是 bug 而是使用上的誤解，並說明發送端合併、MSS 切分、接收緩衝區連續三個層面都會造成它。接著給三種分幀方案並表態實務上二進位協定用**長度前綴**。實作細節要主動提兩個：**必須處理讀不滿的情況**（在緩衝區累積），以及**必須限制最大長度**，否則是阻斷服務漏洞。加分點是舉 HTTP 為混合式的例子（標頭用分隔符、主體用長度），以及澄清 UDP 沒有黏包但有 IP 分片的問題，兩者不同。

## 講稿

根因是 TCP 是位元組流，它沒有訊息邊界的概念。我呼叫兩次寫入各送一百個位元組，TCP 只保證這兩百個位元組按序到達，不保證對方分兩次讀到。可能一次讀到兩百，也可能讀到六十加一百四十。

造成這個現象的原因有好幾層。發送端的 Nagle 會把小資料合併，TCP 也會依照 MSS 切分大資料，接收端的緩衝區本來就是連續的位元組空間。

所以黏包其實不是 TCP 的問題，是把它當成訊息協定使用的誤解。UDP 沒有這個現象，因為它是資料報，一次送出對應一次讀取，邊界保留著。

解法是在應用層自己定義邊界。三種做法，固定長度最簡單但浪費也不彈性，分隔符適合文字協定但內容裡出現分隔符要跳脫，長度前綴最通用。二進位協定我幾乎都用長度前綴。

實作上有兩個地方最容易寫錯。第一，一次讀取可能連長度欄位都讀不滿，所以要在緩衝區累積到湊滿為止。第二，一定要限制最大長度，不然一個惡意的超大長度值會讓伺服器嘗試配置巨量記憶體，那是阻斷服務漏洞。

## 常見追問

### HTTP 是怎麼處理訊息邊界的？

**核心答案**：**混合式**。標頭部分用**換行分隔**，標頭與主體之間用一個**空行**分界；主體則有兩種方式——用 `Content-Length` 告知長度（等同長度前綴），或用**分塊傳輸編碼**，把主體切成若干塊、每塊前面帶自己的長度，最後用一個長度為零的塊表示結束。分塊編碼的價值在於**送出時還不知道總長度**的場景，例如動態產生的內容或串流回應。

**詳細解析**：這個設計也帶來一類安全問題——當 `Content-Length` 與分塊編碼同時出現且前後端解析不一致時，攻擊者可以構造請求讓代理與後端對「訊息在哪裡結束」有不同判斷，把一段內容夾帶成下一個請求的開頭，這就是請求走私。防禦的原則是**兩個長度指示同時出現時直接拒絕**，並確保整條鏈路上的解析行為一致。HTTP/2 之後改用二進位分幀，每個訊框自帶長度與型別，從根本上消除了這類歧義——這是「用更嚴謹的分幀取代文字解析」的好例子。

**面試回答方式**：講清標頭用分隔符、主體用長度或分塊，並說明分塊解決「送出時還不知道總長」的場景。加分點是點出兩種長度指示並存造成的請求走私、防禦是直接拒絕，以及 HTTP/2 的二進位分幀從根本消除歧義。

### 用 Netty 這類框架還需要懂分幀嗎？

**核心答案**：**需要**。框架提供的是現成的解碼器，但**選哪一種、參數怎麼配仍然是你的決定**——最大訊息長度、長度欄位的位移與寬度、要不要跳過長度欄位本身，配錯就會解出錯誤的訊息或直接拋錯。而且自訂協定時，分幀方式本來就是協定設計的一部分，框架不會替你決定。

**詳細解析**：更實際的理由是**排查**。當出現「訊息偶爾錯亂」「連線莫名斷開」這類問題時，如果不理解底層在做什麼，就無法判斷是解碼器配置錯、對端的協定實作不一致、還是有中間設備改動了資料。另外框架的預設值往往偏保守（例如較小的最大長度限制），在傳輸大訊息時會遇到「超過限制被拒」的錯誤，若不理解原因很容易誤判成網路問題。最後，理解分幀也有助於做出更好的協定設計決策——例如把長度欄位放在最前面、選擇足夠但不浪費的寬度、以及是否需要在協定中加入版本號以便日後演進。

**面試回答方式**：明確說需要，並給兩個層面的理由：選型與參數仍是你的決定、以及排查時必須理解底層。加分點是提到框架預設的長度限制在傳大訊息時會踩到，以及理解分幀有助於協定設計（欄位位置、寬度、版本號）。

### 自訂二進位協定時，還要考慮哪些設計點？

**核心答案**：除了分幀之外，至少還要決定四件事。**版本號**——協定一定會演進，預留版本欄位讓新舊端能協商或至少能明確拒絕。**位元組序**——網路傳輸慣例是大端序，兩端必須一致。**型別或指令碼**——讓接收端知道這個訊息該怎麼解析。**擴充性**——是否允許未知欄位被忽略，這決定了能不能做到向前相容。

**詳細解析**：實務上更常見的建議是**不要自訂協定**，直接用成熟的序列化框架（Protobuf、FlatBuffers 這類），它們已經處理了型別、版本演進、跨語言相容與高效編碼。自訂只在有特殊需求時才划算——極致的體積或延遲要求、必須相容某個既有的硬體協定、或協定極度簡單以致框架的開銷不值得。要注意**向前與向後相容的規則必須寫進文件並被遵守**（例如欄位編號不重用、不改變既有欄位的型別），否則協定演進到第三版時就會出現難以排查的相容問題。這類治理問題往往比技術實作更早成為瓶頸。

**面試回答方式**：列出四個設計點並各給一句理由。加分點是給出明確立場——多數情況該用成熟的序列化框架而不是自訂，並說明什麼情況自訂才划算，以及相容性規則必須文件化並遵守，否則演進時會出問題。
