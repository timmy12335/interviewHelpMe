# 題目

QUIC 為什麼建立在 UDP 上？它解決了哪些 TCP 解決不了的問題？

## 核心答案

建立在 UDP 上不是為了「更快」，而是為了「能被部署」：**TCP 的實作在作業系統核心中**——任何改動需要作業系統更新，而網際網路上的設備更新極慢；而 UDP 只是一個薄薄的封裝，QUIC 的邏輯全在使用者空間，於是可以隨應用一起更新、快速迭代。

**它解決的四個問題。**

**stream 級的隊頭阻塞**——QUIC 在自己這層實作可靠傳輸，每個 stream 獨立排序；**一個 stream 丟包不影響其他 stream**。**這是 HTTP/2 在 TCP 上做不到的。**

**握手延遲**——**QUIC 把傳輸層與 TLS 握手合併**：**首次連線 1-RTT，恢復連線 0-RTT**（相比之下 TCP 加 TLS 1.3 是 2-RTT）。

**連線遷移**——**QUIC 用「連線 ID」而非五元組識別連線**；於是手機從 Wi-Fi 切到行動網路時，連線不中斷。

**以及中間設備的僵化**——QUIC 的封包幾乎全部加密（包括大部分的標頭），中間設備無法窺探或修改，於是協定可以繼續演進。

## 詳細解析

「協定僵化（ossification）」是 QUIC 設計中一個深刻的動機：TCP 的可擴充欄位在理論上存在——但中間設備（防火牆、NAT、加速器）會丟棄或修改帶有不認識選項的封包；於是「新的 TCP 功能實際上無法部署」。QUIC 的回應是「把所有東西加密，讓中間設備什麼都看不到」——於是它們無法基於內容做判斷，也就無法阻礙演進。這個「用加密換取可演進性」的設計思路，比任何單一的效能改進都更有長遠的影響。

「連線遷移」的價值在行動場景中很實在：傳統的 TCP 連線由五元組識別——IP 一變（換網路、NAT 重新映射），連線就斷了；於是應用要重新建立連線並可能重新認證。而 QUIC 的連線 ID 讓「同一條連線換了地址繼續用」成為可能——使用者從電梯走出來、從 Wi-Fi 切到 5G，正在下載的檔案不會中斷。這是一個純粹來自「協定假設與現代使用場景不符」的修正。

**「0-RTT 的安全代價」需要說清楚**：恢復連線時，客戶端可以在第一個封包中就帶上應用資料——**但那些資料無法防重放攻擊**（**攻擊者可以錄下並重送**）。**所以 0-RTT 只能用於冪等的請求**（GET）——而規格明確要求應用層做這個限制。這是一個「效能與安全的明確取捨，而且責任被推給了應用層」的設計。

「QUIC 的 CPU 開銷較高」是一個實際的代價：協定處理在使用者空間——無法像 TCP 那樣使用網卡的硬體卸載（TSO、GSO）；**於是同樣的吞吐需要更多 CPU**。近年的核心與網卡開始支援 UDP 的分段卸載，情況在改善——但在高吞吐的伺服器上這仍然是一個需要評估的因素。

## 面試回答方式

先給建立在 UDP 上是為了能被部署而非更快（核心的 TCP 改動需要作業系統更新，而 QUIC 在使用者空間），再給四個解決的問題。加分點有四個：**協定僵化是深刻的動機**——中間設備會丟棄帶不認識選項的封包，於是新的 TCP 功能實際上無法部署，而 QUIC 用加密讓它們什麼都看不到，這個「用加密換可演進性」比任何效能改進都更長遠；**連線遷移用連線 ID 而非五元組**，**讓從 Wi-Fi 切到 5G 時下載不中斷**；0-RTT 的資料無法防重放，所以只能用於冪等請求，是「效能與安全的取捨且責任被推給應用層」；以及**QUIC 的 CPU 開銷較高**，因為使用者空間的處理無法用網卡的硬體卸載。

## 講稿

建立在使用者資料包協定上不是為了更快，是為了能被部署。傳輸控制協定的實作在作業系統核心中，任何改動需要系統更新，而網際網路上的設備更新極慢。而這個新協定的邏輯全在使用者空間，可以隨應用一起更新、快速迭代。

它解決四個問題。第一是串流級的隊頭阻塞，每個串流獨立排序，一個丟包不影響其他。第二是握手延遲，把傳輸層跟加密握手合併，首次一次往返、恢復零次往返。第三是連線遷移，用連線識別碼而不是五元組識別，於是手機從無線網路切到行動網路時連線不中斷。第四是中間設備的僵化。

第四點我覺得是最深刻的動機。傳輸控制協定的可擴充欄位在理論上存在，但中間設備會丟棄或修改帶有不認識選項的封包，於是新功能實際上無法部署。而這個協定的回應是把所有東西加密，讓中間設備什麼都看不到，也就無法阻礙演進。這個用加密換取可演進性的思路，比任何單一的效能改進都更有長遠影響。

不過零次往返的資料無法防重放，所以只能用於冪等的請求。這是一個效能與安全的明確取捨，而且責任被推給了應用層。

## 常見追問

### 有些網路會封鎖 UDP，怎麼辦？

**核心答案**：**必須有回退機制**。客戶端先嘗試 QUIC——**失敗或超時就回退到 HTTP/2 over TCP**。而伺服器透過 `Alt-Svc` 標頭告訴客戶端「我也支援 HTTP/3，下次可以試試」——於是第一次連線走 TCP，之後才升級。這個「先用可靠的、再嘗試更好的」的設計，是任何新協定在既有網路上部署的必要條件。

**詳細解析**：**「回退的延遲代價」需要被管理**：如果客戶端等待 QUIC 逾時才回退——**那使用者要多等幾秒**。所以實務上的做法是「並行嘗試」或者「快速失敗」（設一個很短的 QUIC 嘗試超時，例如 100 到 300 毫秒）。Chrome 的做法是記住「這個網路封鎖 UDP」並在該網路下直接用 TCP——**於是只有第一次付出代價**。這類「快取環境特性以避免重複探測」的設計在網路程式中很常見，而它的難點是「環境變了怎麼知道」（例如換了 Wi-Fi）——所以那個快取需要與網路標識綁定並有合理的過期。

**面試回答方式**：給回退機制與 `Alt-Svc` 的升級流程，並指出「先用可靠的、再嘗試更好的」是新協定部署的必要條件。核心加分點是**回退的延遲代價要被管理**——等逾時才回退會多等幾秒，所以要並行嘗試或設很短的超時，並給出 **Chrome 記住「這個網路封鎖 UDP」的做法**。收在難點：那個快取要與網路標識綁定並有合理的過期，因為換了網路環境就變了。

### HTTP/3 對後端服務有什麼影響？

**核心答案**：通常只影響邊緣（CDN 或負載平衡器），後端不用改。標準的部署是「邊緣支援 HTTP/3 對外，內部仍用 HTTP/1.1 或 2 回源」——因為 HTTP/3 的收益主要在「不可靠的最後一哩」，而資料中心內部的網路本來就穩定。所以升級 HTTP/3 通常是一個 CDN 或閘道層的設定變更，而非全鏈路的改造。

**詳細解析**：「收益在哪裡取決於網路特性」是這個判斷的基礎：HTTP/3 的三大優勢——避免隊頭阻塞（需要有丟包才有用）、更快的握手（需要有明顯的 RTT）、連線遷移（需要客戶端會換網路）——**在資料中心內部全都不成立**（丟包率極低、RTT 幾十微秒、機器不換 IP）。所以在內部強推 HTTP/3 是一個典型的「把優化用在錯的地方」。而在行動端與跨國的場景中，那三個優勢全都成立且顯著——這正是它先在瀏覽器與 CDN 之間普及的原因。能說出「收益在哪裡」而非「這個技術更好」，是選型判斷的核心差異。

**面試回答方式**：給標準部署（邊緣支援、內部不變）並說明理由（收益主要在不可靠的最後一哩）。核心加分點是逐一分析三大優勢在資料中心內部全都不成立（丟包率極低、RTT 幾十微秒、機器不換 IP），所以在內部強推是典型的「把優化用在錯的地方」。收在原則：能說出「收益在哪裡」而非「這個技術更好」，是選型判斷的核心差異。

### QUIC 對可觀測性有什麼影響？

**核心答案**：變差了，而這是加密帶來的必然代價。傳統上可以用抓包看 TCP 的握手、重傳、視窗變化——而 QUIC 的封包幾乎全部加密，中間節點什麼都看不到。所以診斷必須依賴端點的日誌與指標（`qlog` 是一個標準化的 QUIC 事件日誌格式）。這對「在網路中間排查問題」的傳統做法是一個根本的改變。

**詳細解析**：「可觀測性從網路中間移到端點」是一個更廣的趨勢：TLS 的普及已經讓「在中間看 HTTP 內容」變得不可能——**而 QUIC 把連線層的資訊也加密了**。於是排查的模式必須從「抓包分析」轉向「端點埋點加分散式追蹤」。**這其實是一個更好的方向**（端點知道的比中間節點多，而且能關聯到業務語義）——但它要求團隊在應用層建立觀測能力，而非依賴基礎設施團隊的抓包。所以「QUIC 讓可觀測性變差」這個說法需要被修正成「它讓可觀測性的責任轉移了」——而沒有做好那個轉移的團隊確實會感受到變差。

**面試回答方式**：誠實回答變差並說明原因（加密讓中間節點什麼都看不到），給出替代（端點日誌、`qlog`）。核心加分點是把它放進更廣的趨勢：可觀測性從網路中間移到端點，而這其實是更好的方向因為端點知道得更多且能關聯業務語義。收在修正：「QUIC 讓可觀測性變差」應該被修正成「它讓可觀測性的責任轉移了」——沒做好那個轉移的團隊確實會感受到變差。
