# 題目

HTTP/1.1、2、3 的核心差別是什麼？每一版解決了前一版的什麼問題？

## 核心答案

主線是**逐步消除隊頭阻塞**。**HTTP/1.1** 是文字協定，一條連線上的請求必須**依序回應**——前一個沒回完，後面的就得等，這是**應用層的隊頭阻塞**。當時的變通做法是對同一網域開六條左右的連線、把資源合併成大檔、或分散到多個網域，這些都是繞路而非解決。**HTTP/2** 改成**二進位分幀**並引入**多工**：一條連線上可以同時傳輸多個串流，訊框交錯傳送，解決了應用層的隊頭阻塞；同時加上**標頭壓縮**（大量重複的標頭只傳差異）與**伺服器推送**。但它跑在 TCP 上，而 TCP 保證按序交付，所以一個封包遺失會卡住連線上的所有串流——問題下沉成了**傳輸層的隊頭阻塞**。**HTTP/3** 換掉傳輸層，改用建在 UDP 之上的 **QUIC**，讓每個串流獨立處理遺失與重傳，徹底解決；順帶還把傳輸與加密握手合併（建立連線更快）並支援**連線遷移**（換網路不斷線）。

## 詳細解析

HTTP/1.1 時代的優化手段現在多半是反效果：合併 CSS 與 JS、雪碧圖、網域分片，這些都是為了繞過「連線數有限、請求要排隊」而生的。在 HTTP/2 之上，多工讓小檔案的成本大幅下降，而合併反而**傷害快取粒度**（改一個小檔要重下整包）；網域分片更是直接**破壞多工**（不同網域就是不同連線）。所以升級協定之後應該回頭移除這些變通，否則會抵銷新協定的好處——這是實務上常被忽略的一步。

**標頭壓縮的價值被低估**：現代請求的標頭往往比主體還大（Cookie、User-Agent、各種自訂標頭），而且同一個連線上大量請求的標頭**幾乎相同**。HTTP/2 用靜態表加動態表，把重複的標頭壓成索引，效果非常顯著。這也意味著**Cookie 過大**的代價在 HTTP/1.1 上比想像中更嚴重，因為每個請求都要完整重傳一次。

**伺服器推送基本上失敗了**：它的想法是伺服器主動把客戶端「將會需要」的資源推過去，省下一次往返。實際上很難判斷客戶端是否已經快取了該資源，容易推送無用的內容浪費頻寬，主流瀏覽器後來移除了支援。取代它的是 **`103 Early Hints`** 與 **`preload`**——由伺服器提示客戶端「你可以先去載入這些」，由客戶端決定要不要載，保留了快取判斷權。這是「推送 vs 提示」的設計取捨，值得在面試中提出來。

**QUIC 的額外好處**：**連線遷移**——連線由連線 ID 識別而非 IP 加埠號，所以手機從 Wi-Fi 切到行動網路時連線不會中斷，這對行動應用體感很明顯。**握手更快**——傳輸層與加密握手合併，通常一個往返就能開始傳資料，重連甚至可以零往返（代價是有重放風險，只適合冪等請求）。**在使用者空間實作**——不必等作業系統核心更新就能演進，這是它能快速迭代的結構性優勢。

**HTTP/3 不是萬靈丹**：UDP 在部分企業網路或中間設備上會被封鎖或降速，所以實務上仍需保留回退到 HTTP/2 的路徑。另外 QUIC 在使用者空間實作意味著**CPU 開銷高於核心中的 TCP**，在極高吞吐的伺服器上這個成本是實際的考量。誠實講出這些限制，比一味推薦新協定更可信。

## 面試回答方式

用**「逐步消除隊頭阻塞」**這條主線串起三個版本，這比逐版列特性清楚得多。HTTP/1.1 是應用層阻塞、HTTP/2 用多工解決但問題下沉到 TCP 層、HTTP/3 換掉傳輸層徹底解決。接著補上每一版的附加價值：HTTP/2 的標頭壓縮、HTTP/3 的連線遷移與更快握手。加分點有三個：HTTP/1.1 時代的優化（合併檔案、網域分片）在 HTTP/2 之上是反效果，升級後要回頭移除；伺服器推送基本失敗、被 Early Hints 這類提示機制取代；以及誠實講 HTTP/3 的限制（UDP 可能被封鎖、CPU 開銷較高），需要保留回退路徑。

## 講稿

我會用一條主線來講，就是逐步消除隊頭阻塞。

HTTP/1.1 是文字協定，一條連線上的請求必須依序回應，前一個沒回完後面就得等。這是應用層的隊頭阻塞。當時的變通是對同一個網域開六條連線、把檔案合併、或者分散到多個網域，這些都是繞路不是解決。

HTTP/2 改成二進位分幀並且支援多工，一條連線上可以同時傳多個串流，訊框交錯送出，應用層的阻塞就解決了。它還加了標頭壓縮，這個價值常被低估，因為現代請求的標頭往往比主體還大，而且同一條連線上幾乎都一樣。

但 HTTP/2 跑在 TCP 上，而 TCP 保證按序交付，所以一個封包遺失會卡住這條連線上的所有串流。問題只是從應用層下沉到傳輸層。

HTTP/3 就是換掉傳輸層，改用建在 UDP 上的 QUIC，每個串流獨立處理遺失，徹底解決。順帶還把傳輸跟加密握手合併，而且支援連線遷移，手機從 Wi-Fi 切到行動網路不會斷。

有一件事很多人會漏掉。升級到 HTTP/2 之後，應該回頭把合併檔案跟網域分片移除，不然反而抵銷新協定的好處。

## 常見追問

### 升級到 HTTP/2 之後，哪些舊優化該移除？

**核心答案**：三類。**檔案合併**（把多個 CSS 或 JS 打成一包、雪碧圖）——多工之後小檔案的成本已經很低，而合併會**傷害快取粒度**，改動一個小地方就要讓整包失效重下。**網域分片**（把資源分散到多個子網域繞過連線數限制）——它會**破壞多工**，因為不同網域就是不同連線，還額外增加 DNS 與 TLS 握手成本。**內聯資源**（把小圖片編成 data URI 塞進 CSS）——同樣傷害快取，而且無法被單獨快取或壓縮。

**詳細解析**：要注意「該移除」不代表「一定要移除到底」——極小的檔案（幾百位元組）仍有每個請求的固定開銷，適度合併仍可能划算；判斷依據應該是**實測**而非教條。另外如果還有相當比例的使用者停留在 HTTP/1.1（老舊客戶端、某些中間代理只支援 1.1），移除變通可能讓那部分使用者變慢，所以要看實際的協定分布再決定。這種「先看資料再決定」的態度在效能優化題上比任何具體手段都重要，因為同一個做法在不同流量結構下的結論可能相反。

**面試回答方式**：列出三類並各說明它在 HTTP/2 下為什麼變成負擔（特別是快取粒度與破壞多工）。加分點是補上判斷要靠實測、以及要看實際的協定版本分布，避免對仍在 1.1 的使用者造成退步。

### QUIC 為什麼建在 UDP 上而不是自己做一個新的傳輸層協定？

**核心答案**：因為**中間設備的相容性**。網際網路上大量的防火牆、NAT 與負載平衡器只認識 TCP 與 UDP，一個全新的傳輸層協定號碼會被大量設備直接丟棄，實務上根本部署不起來。建在 UDP 之上等於借用一個已經被普遍放行的載具，把可靠傳輸、擁塞控制與加密都放在其上的使用者空間實作。

**詳細解析**：這個選擇還帶來一個結構性優勢：**演進速度**。TCP 的實作在作業系統核心中，改進要等系統更新與使用者升級，週期以年計；QUIC 在使用者空間（通常隨瀏覽器或函式庫發布），可以快速迭代新的擁塞控制與功能。代價有兩個：**CPU 開銷較高**（缺少核心與網卡的硬體卸載支援，雖然這一點正在改善）以及**部分網路封鎖或限速 UDP**，所以必須保留回退到 TCP 的路徑。這個「為了可部署性而妥協架構純淨度」的決策，是網路協定演進中反覆出現的模式，能講出這一層會顯得你理解的是工程權衡而不只是規格。

**面試回答方式**：核心是中間設備相容性——新協定號碼會被丟棄，UDP 是能通行的載具。加分點是講使用者空間實作帶來的演進速度優勢，以及誠實給出兩個代價（CPU 開銷、UDP 可能被封鎖需要回退），並把它總結為可部署性優先的工程權衡。

### 伺服器推送為什麼失敗了？

**核心答案**：因為伺服器無法知道客戶端是否已經快取了要推送的資源。推送已經在快取中的內容純粹浪費頻寬，而在行動網路上這個浪費是實際成本；要避免又需要複雜的機制讓客戶端告知快取狀態，得不償失。加上實作複雜、效益不穩定，主流瀏覽器後來移除了支援。

**詳細解析**：取代它的是 **`103 Early Hints`** 與 **`preload`** 這類**提示**機制——伺服器只說「你接下來會需要這些資源」，由客戶端**自己決定**要不要載入（它最清楚自己的快取狀態）。這個從「推送」到「提示」的轉變，本質上是把決策權交還給擁有資訊的一方，是很好的系統設計原則案例。`103` 特別有價值的場景是後端處理較慢時——伺服器可以先回一個 103 讓瀏覽器開始載入靜態資源，等主要回應算完再送 200，等於把等待時間利用起來。能講出這個具體用法，會比只說「推送失敗了」有深度。

**面試回答方式**：核心是伺服器不知道客戶端的快取狀態，推送已快取的內容純屬浪費。接著講被提示機制取代，並把它總結為「把決策權交還給擁有資訊的一方」。加分點是講 `103 Early Hints` 在後端慢時先讓瀏覽器載入靜態資源這個具體用法。
