# 題目

Cookie 的 `HttpOnly`、`Secure`、`SameSite` 各自防什麼？

## 核心答案

三個屬性防的是三種不同的攻擊。

**`HttpOnly`**——**禁止 JavaScript 讀取這個 cookie**；**防的是 XSS 之後的「竊取 session」**。**注意它不防 XSS 本身**——攻擊者仍然可以用受害者的瀏覽器發請求，只是拿不到 cookie 的值帶走。

**`Secure`**——**只在 HTTPS 連線上傳送**；**防的是明文連線中的竊聽**。在全站 HTTPS 的今天這幾乎是必設的。

**`SameSite`**——**控制「跨站請求是否攜帶這個 cookie」**；**防的是 CSRF**。**三個值**：`Strict`（跨站完全不帶，最安全但從外部連結進來會顯示未登入）、`Lax`（頂層的 GET 導航會帶，其他不帶——這是現代瀏覽器的預設）、**`None`（總是帶，但必須同時設 `Secure`）**。

**而正確的組合是「三個都設」**——**它們互補而非替代。**

## 詳細解析

**「`SameSite=Lax` 成為預設是一個重要的變化」**：它讓大量的 CSRF 攻擊自動失效——**因為跨站的 POST 不再攜帶 cookie**。但它也打破了一些既有的整合：第三方的嵌入（iframe 中的服務）、跨站的 POST 表單、以及某些 OAuth 的回呼流程——**這些需要明確設 `SameSite=None; Secure`**。所以「升級之後某些第三方整合壞了」在那段時間是一個普遍的問題，**而理解它的成因能快速定位。**

「`HttpOnly` 不是 XSS 的解藥」需要說清楚：它讓攻擊者無法「竊取 cookie 並在自己的機器上使用」——但攻擊者的腳本仍在受害者的瀏覽器中執行，可以直接發起帶 cookie 的請求（轉帳、改密碼、讀取資料）。**所以真正防 XSS 的是「輸出編碼與 CSP」**——**而 `HttpOnly` 只是降低損害的一層**。把它當成主要防線是一個常見的誤解。

**「Cookie 的作用域規則容易搞錯」**：`Domain` 屬性設成 `example.com` 會讓所有子網域都收到這個 cookie——於是一個不受信任的子網域（例如使用者可以建立內容的 `user.example.com`）可能讀到或設定主站的 cookie。所以「不要設過寬的 Domain」是一個實際的安全建議。而 `__Host-` 前綴的 cookie 強制了「必須是 Secure、Path 為 /、且不能設 Domain」——它是目前最嚴格也最安全的 cookie 形式。

**「Cookie 不是唯一的選擇」**：對純 API 的場景，**把 token 放在 `Authorization` 標頭中完全避開了 CSRF**（**因為瀏覽器不會自動附加它**）；代價是需要自己儲存 token（而放在 localStorage 中對 XSS 更脆弱）。所以「cookie 加 SameSite」與「header 加自行儲存」是兩種各有取捨的方案，**而不是一個明顯優於另一個。**

## 面試回答方式

先分別給三個屬性防的攻擊，並強調**`HttpOnly` 不防 XSS 本身**與 **`SameSite` 三個值的差異**。加分點有四個：`SameSite=Lax` 成為預設打破了一些既有整合（第三方嵌入、跨站 POST、某些 OAuth 回呼），**理解成因能快速定位**；**`HttpOnly` 不是 XSS 的解藥**——攻擊者的腳本仍能在受害者瀏覽器中發起帶 cookie 的請求，**真正防 XSS 的是輸出編碼與 CSP**；Domain 設過寬會讓不受信任的子網域讀到主站 cookie，**而 `__Host-` 前綴是最嚴格的形式**；以及cookie 與 Authorization 標頭是兩種各有取捨的方案，**而非一個明顯更好**。

## 講稿

三個屬性防的是三種不同的攻擊。

僅限 HTTP 這個屬性禁止腳本讀取，防的是跨站腳本攻擊之後的竊取工作階段。但要說清楚，它不防跨站腳本本身。攻擊者的腳本仍在受害者的瀏覽器中執行，可以直接發起帶著憑證的請求去轉帳或改密碼，只是拿不到那個值帶走。所以真正防它的是輸出編碼跟內容安全政策，而這個屬性只是降低損害的一層。把它當成主要防線是常見的誤解。

僅限安全連線防的是明文中的竊聽，全站加密的今天幾乎必設。

同站屬性控制跨站請求是否攜帶，防的是跨站請求偽造。現代瀏覽器預設是寬鬆模式，頂層的導航會帶、其他不帶。這讓大量攻擊自動失效，但也打破了一些第三方嵌入跟某些授權回呼流程，那些需要明確設成無限制加上安全連線。

還有一個作用域的坑。網域屬性設得太寬會讓所有子網域都收到，於是一個不受信任的子網域可能讀到主站的憑證。

## 常見追問

### CSRF 除了 SameSite 還有哪些防護？

**核心答案**：**三種傳統手段**。**CSRF token**——伺服器產生一個隨機值放在表單或標頭中，提交時驗證；**攻擊者無法從跨站讀取它**。**檢查 `Origin` 或 `Referer` 標頭**——**確認請求來自自己的網域**；簡單但這些標頭可能缺失（隱私設定）。**以及「雙重提交 cookie」**——同一個隨機值同時放在 cookie 與請求參數中並比對。

**詳細解析**：**「防禦應該分層而非二選一」**：`SameSite=Lax` 擋掉了絕大多數——但仍有例外（同站的子網域攻擊、以及某些瀏覽器的實作差異）；而 CSRF token 是與瀏覽器行為無關的應用層保證。所以對高風險的操作，兩者都用是合理的。而「檢查 Origin」有一個實務上的優勢：它不需要維護 token 的狀態——尤其在無狀態的 API 中，比 CSRF token 簡單得多。**但要注意「缺失的 Origin 該怎麼處理」**：嚴格拒絕會擋掉一些合法的客戶端，**而放行則失去保護**——通常的做法是「有 Origin 就驗證，沒有就要求其他證明（例如 CSRF token 或自訂標頭）」。這個「多個弱保證組合成一個強保證」的模式，在安全設計中很常見。

**面試回答方式**：給三種傳統手段與各自的機制。核心加分點是主張**防禦應該分層而非二選一**——SameSite 擋掉絕大多數但仍有例外，而 CSRF token 是與瀏覽器行為無關的應用層保證。收在 **Origin 檢查的實務優勢與難點**：它不需要維護狀態，但缺失時嚴格拒絕會擋掉合法客戶端、放行則失去保護，通常「有就驗證、沒有就要求其他證明」——這個「多個弱保證組合成強保證」的模式在安全設計中很常見。

### Session 與 JWT 在 cookie 的使用上有什麼差別？

**核心答案**：Session ID 是一個不透明的引用，狀態在伺服器——於是「登出」就是刪除伺服器端的記錄，立即生效。**JWT 是自包含的，狀態在 token 裡**——於是伺服器不需要儲存，但也無法主動使它失效（除非維護一個黑名單，而那又回到了有狀態）。兩者都可以放在 cookie 中，安全屬性的要求是一樣的。

**詳細解析**：「無法立即撤銷」是 JWT 最實質的限制，而它在安全事件中很致命：發現一個 token 洩漏了——在它過期前你無法阻止它被使用。緩解的方式是「短的有效期加上 refresh token」：access token 幾分鐘就過期，而 refresh 的時候檢查伺服器端的狀態——於是撤銷的延遲被控制在幾分鐘內。這實際上是「用短有效期換取近似的撤銷能力」，而它讓 JWT 的無狀態優勢部分保留（多數請求不查資料庫）同時獲得了可控的撤銷。理解這個折衷比爭論「JWT 好還是 Session 好」有價值得多——因為實務上的方案幾乎總是這兩者的混合。

**面試回答方式**：給核心差別（不透明引用 vs 自包含）與各自的撤銷特性。核心加分點是「無法立即撤銷」是 JWT 最實質的限制且在安全事件中致命，並給出標準緩解：短有效期加 refresh token，撤銷延遲控制在幾分鐘內。收在判斷：這是「用短有效期換取近似的撤銷能力」，理解這個折衷比爭論「JWT 好還是 Session 好」有價值，因為實務方案幾乎總是兩者的混合。

### 跨子網域共享登入怎麼做？

**核心答案**：**把 cookie 的 `Domain` 設成父網域**（`.example.com`）——**於是所有子網域都能收到**。**但這有安全代價**：任何一個子網域被攻破，那個 cookie 就洩漏了；而且不受信任的子網域可以設定它（cookie 的寫入不受同源政策嚴格限制）。所以只有在所有子網域都受同等信任時才適用。

**詳細解析**：「更安全的做法是集中式的單一登入」：把認證集中在一個網域（`auth.example.com`）——其他子網域透過重導向與 token 交換取得自己的 session；於是每個子網域有自己獨立的 cookie，一個被攻破不影響其他。代價是流程更複雜（多一次重導向）。而「cookie 的寫入不受同源政策嚴格限制」這一點值得強調：一個子網域可以設定父網域的 cookie——於是它能「注入」一個 session 給使用者（session fixation 攻擊的一種形式）。**這就是為什麼 `__Host-` 前綴禁止設定 Domain**——它從機制上排除了這一類問題。理解「同源政策對讀與寫的保護程度不同」，是很多瀏覽器安全問題的關鍵。

**面試回答方式**：給簡單做法（Domain 設父網域）與它的安全代價。核心加分點是更安全的做法是集中式單一登入——每個子網域有獨立的 cookie，一個被攻破不影響其他。收在一個關鍵的機制細節：cookie 的寫入不受同源政策嚴格限制，子網域可以設定父網域的 cookie 從而注入 session，**這正是 `__Host-` 前綴禁止設 Domain 的原因**，而「同源政策對讀與寫的保護程度不同」是很多瀏覽器安全問題的關鍵。
