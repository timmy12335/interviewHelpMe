# 題目

HTTP/2 的多路複用解決了什麼？為什麼還是有隊頭阻塞？

## 核心答案

**它解決的是「HTTP/1.1 的應用層隊頭阻塞」**：1.1 的一條連線上，**請求必須依序完成**——**前一個回應沒回來，後面的就得等**（pipelining 在實務上因為代理的相容問題基本不可用）。**於是瀏覽器只好開六條連線，而那本身就有成本（每條都要握手、都要各自做擁塞控制）。**

**HTTP/2 用「二進位分幀」把多個請求拆成帶 stream ID 的幀，在同一條 TCP 連線上交錯傳輸**——**於是一條連線就能並行處理上百個請求，順序無關。**

**但它仍有「TCP 層的隊頭阻塞」**：**所有 stream 共用一條 TCP 連線**——**而 TCP 保證有序交付**；**於是一個封包丟失時，即使後面的封包屬於其他 stream 且已經到達，TCP 也不會交給應用**，**必須等重傳完成**。**丟包率越高，這個問題越嚴重——這正是 HTTP/3 改用 QUIC 的根本動機。**

## 詳細解析

**「一條連線在丟包時反而更糟」是一個反直覺但重要的結論**：HTTP/1.1 的六條連線下，**一條上的丟包只影響那條上的請求**；**而 HTTP/2 的單條連線下，一次丟包會阻塞所有 stream**。**所以在高丟包的網路（行動網路、跨國）中，HTTP/2 的優勢會被削弱甚至反轉**——**這是一個「優化在某些條件下失效」的典型例子，而理解條件比記住結論重要**。

**「伺服器推送（Server Push）基本上失敗了」值得知道**：它的想法是「伺服器預測客戶端接下來要什麼並主動推送」——**而實務上瀏覽器可能已經有那個資源的快取，於是推送是浪費**；**而且推送的優先級管理很複雜**。**主流瀏覽器已經移除了對它的支援**，**取而代之的是 `103 Early Hints`**（**告訴客戶端「你可能會需要這些資源」讓它自己決定要不要取**）——**這是一個「把決定權還給有更多資訊的一方」的修正**。

**「標頭壓縮（HPACK）」是 HTTP/2 一個被低估的收益**：HTTP 的標頭有大量重複（cookie、user-agent、accept 在每個請求中幾乎相同）——**而 HPACK 用一個動態表讓重複的標頭只傳一個索引**。**在大量小請求的場景中，標頭可能比 body 還大**——**所以這個壓縮的實際收益很可觀。**

**「優先級的實作參差不齊」**：HTTP/2 定義了複雜的優先級樹——**但各伺服器的實作品質差異很大，而瀏覽器的使用方式也不一致**；**HTTP/3 因此簡化了優先級模型**。**這是一個「規格過度設計而實作跟不上」的例子。**

## 面試回答方式

先給它解決的問題（**1.1 的應用層隊頭阻塞，以及開六條連線的成本**）與機制（二進位分幀加 stream ID 交錯傳輸），再說明**仍有 TCP 層的隊頭阻塞**及其原因。加分點有四個：**一條連線在丟包時反而更糟**——**1.1 的六條連線下丟包只影響一條，而 2 的單條下會阻塞所有 stream**，**這是「優化在某些條件下失效」的典型例子**；**伺服器推送基本上失敗了**——**瀏覽器可能已有快取所以是浪費，取而代之的 `103 Early Hints` 把決定權還給有更多資訊的一方**；**標頭壓縮是被低估的收益**——**大量小請求時標頭可能比 body 還大**；以及**優先級的實作參差不齊**，**是規格過度設計而實作跟不上的例子**。

## 講稿

它解決的是應用層的隊頭阻塞。一點一的一條連線上請求必須依序完成，前一個回應沒回來後面就得等。於是瀏覽器只好開六條連線，而那本身就有成本。

二版用二進位分幀把多個請求拆成帶串流編號的幀，在同一條連線上交錯傳輸，於是一條連線就能並行處理上百個請求。

但它仍有傳輸層的隊頭阻塞。所有串流共用一條連線，而傳輸層保證有序交付。於是一個封包丟失時，即使後面的封包屬於其他串流而且已經到達，也不會被交給應用，必須等重傳完成。

這帶來一個反直覺但重要的結論。一條連線在丟包時反而更糟。一點一的六條連線下，一條上的丟包只影響那條上的請求。而二版的單條連線下，一次丟包會阻塞所有串流。所以在高丟包的行動網路或跨國鏈路上，它的優勢會被削弱甚至反轉。這是一個優化在某些條件下失效的典型例子，而理解條件比記住結論重要。

另外伺服器推送這個功能基本上失敗了，主流瀏覽器已經移除支援。因為瀏覽器可能已經有那個資源的快取，推送就是浪費。

## 常見追問

### HTTP/2 之後還需要合併資源與雪碧圖嗎？

**核心答案**：**多數情況不需要，但不是完全不需要**。HTTP/1.1 時代的「合併 JS、CSS 雪碧圖、域名分片」都是為了繞過「連線數限制」——**而 HTTP/2 的多路複用讓那些手段的收益消失**。**但「過度細碎」仍有成本**：**每個資源都有標頭與處理開銷**；**而且太多小檔案會影響壓縮率（大檔案的壓縮率更高）**。**所以合理的粒度仍然重要，只是不需要像以前那樣激進地合併。**

**詳細解析**：**「域名分片在 HTTP/2 下是有害的」值得指出**：分片的目的是「繞過每個域名 6 條連線的限制」——**而在 HTTP/2 下，分片會導致多條連線，反而失去了單連線的多路複用與標頭壓縮的收益**；**而且每條連線都要各自建立與做擁塞控制**。**所以升級到 HTTP/2 時應該主動移除域名分片**——**這是一個「舊的優化在新協定下變成反優化」的例子**，**而它在很多長期維護的系統中仍然殘留**。**同樣的道理適用於「內聯小資源」**：**HTTP/1.1 時代把小圖片 base64 內聯進 CSS 以省請求——**而那讓它們無法被單獨快取，在 HTTP/2 下弊大於利。**

**面試回答方式**：回答多數不需要但不是完全不需要，並說明**過度細碎仍有標頭開銷與壓縮率的成本**。核心加分點是**域名分片在 HTTP/2 下是有害的**——**它導致多條連線，失去多路複用與標頭壓縮的收益**，**所以升級時應該主動移除**，**這是「舊的優化在新協定下變成反優化」的例子而它在很多系統中仍殘留**。收在同類例子：**內聯小資源讓它們無法被單獨快取，在 HTTP/2 下弊大於利**。

### 為什麼 gRPC 選擇建立在 HTTP/2 之上？

**核心答案**：**因為它需要的正是 HTTP/2 提供的**：**多路複用**（一條連線上並行多個 RPC）、**雙向串流**（stream 天然支援）、**標頭壓縮**（RPC 的中繼資料重複度高）、**以及既有的基礎設施相容性**（能穿透多數代理與負載平衡器）。**自己設計一個協定可以更精簡，但會失去整個 HTTP 生態的支援。**

**詳細解析**：**「複用既有協定 vs 自己設計」的取捨在這裡很有代表性**：自訂協定能做到更小的開銷與更貼合的語義——**但代價是所有的中間設備、監控工具、負載平衡器都不認識它**。**而建立在 HTTP/2 上讓 gRPC 能被既有的七層負載平衡器處理、被標準的追蹤工具觀察、以及穿透企業防火牆**。**這個「相容性的價值超過效率的損失」的判斷，在協定設計中反覆出現**——**而 HTTP 之所以成為「萬用的傳輸層」，正是因為它是唯一一個到處都通的協定**。**代價是 gRPC 繼承了 HTTP/2 的 TCP 隊頭阻塞問題**——**而這正是 gRPC 也在向 HTTP/3 遷移的原因。**

**面試回答方式**：給四個理由（多路複用、雙向串流、標頭壓縮、基礎設施相容）。核心加分點是把它提升成**「複用既有協定 vs 自己設計」的取捨**：**自訂能更精簡但所有中間設備、監控、負載平衡器都不認識它**，**而「相容性的價值超過效率的損失」在協定設計中反覆出現**，**HTTP 成為萬用傳輸層正是因為它到處都通**。收在代價：**gRPC 繼承了 TCP 隊頭阻塞，這正是它也在向 HTTP/3 遷移的原因**。

### 怎麼確認 HTTP/2 真的生效了？

**核心答案**：**看瀏覽器開發者工具的 Protocol 欄位**（顯示 `h2`）**或者用 `curl -I --http2 <url>` 看回應**。**而更常見的問題是「只有到 CDN 或負載平衡器是 HTTP/2，後端仍是 1.1」**——**那也沒關係（前端的收益已經拿到），但要知道實際的拓撲**。

**詳細解析**：**「協商是透過 TLS 的 ALPN 完成的」是一個實用的細節**：客戶端在 TLS 握手時宣告支援的協定列表——**伺服器選一個**。**所以 HTTP/2 在瀏覽器中實質上要求 HTTPS**（規格上允許明文的 h2c，但瀏覽器不支援）。**這意味著「沒上 HTTPS 就沒有 HTTP/2」**——**而那是很多網站升級 HTTPS 的一個實際動機**。**另一個常見的問題是「中間的舊代理不支援」**：**企業網路的透明代理可能把連線降級到 1.1**——**而使用者不會知道為什麼在公司網路下網站變慢了**。**這類「環境差異造成的效能差異」在排查時很容易被忽略，而「請對方回報 Protocol 欄位」是一個成本極低的診斷步驟。**

**面試回答方式**：給確認方式並指出**常見情況是只有前端是 HTTP/2 而後端仍是 1.1**。核心加分點是**協商透過 TLS 的 ALPN 完成，所以瀏覽器中實質上要求 HTTPS**——**「沒上 HTTPS 就沒有 HTTP/2」是很多網站升級的實際動機**。收在一個容易忽略的排查點：**企業網路的透明代理可能把連線降級到 1.1**，**而「請對方回報 Protocol 欄位」是成本極低的診斷步驟**。
