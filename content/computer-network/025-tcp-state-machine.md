# 題目

`netstat` 看到大量的 `CLOSE_WAIT` 或 `SYN_RECV` 分別代表什麼問題？

## 核心答案

**每個異常狀態都直接指向一個特定的問題，這是它們的診斷價值。**

**`CLOSE_WAIT` 堆積**——**對方已經送了 FIN，而你的應用沒有呼叫 `close()`**。**這幾乎總是應用程式的 bug**：**連線洩漏、沒有在 finally 中關閉、或者處理執行緒卡住了**。**注意它不會自己消失**——**因為 TCP 在等應用決定，而應用永遠不決定**。

**`SYN_RECV` 堆積**——**收到了 SYN 並回了 SYN-ACK，但沒收到最後的 ACK**。**可能是 SYN flood 攻擊、也可能是網路問題導致 ACK 丟失**。

**`TIME_WAIT` 堆積**——**你是主動關閉的一方**；**大量出現通常表示短連線太多**，**而解法的優先順序是「先改用長連線」而非調核心參數**。

**`FIN_WAIT_2` 堆積**——**你關閉了，對方回了 ACK 但一直不送 FIN**——**對方的應用沒有 close，也就是對方有 `CLOSE_WAIT` 問題。**

## 詳細解析

**「`CLOSE_WAIT` 與 `FIN_WAIT_2` 是同一個問題的兩面」是一個實用的診斷關聯**：一方堆積 `CLOSE_WAIT`——**另一方就堆積 `FIN_WAIT_2`**。**所以在客戶端看到大量 `FIN_WAIT_2` 時，應該去看伺服器端是不是有連線洩漏**；**反之亦然**。**這讓「問題在哪一端」變成一個可以直接判斷的事**。

**「`CLOSE_WAIT` 不會超時消失」值得強調**：`FIN_WAIT_2` 有作業系統層級的超時（Linux 的 `tcp_fin_timeout`）——**而 `CLOSE_WAIT` 沒有，因為 TCP 認為「應用還有資料要送」是合法的**。**所以它會一直累積直到耗盡檔案描述符**，**表現為「服務跑一段時間後無法接受新連線」**。**這種「跑幾天就掛」的模式，看到 `CLOSE_WAIT` 堆積就能立刻定位**。

**「半關閉是一個合法的狀態」是理解這些的基礎**：TCP 允許「一方關閉發送但仍能接收」——**這正是為什麼收到 FIN 之後不會自動關閉整條連線**。**這個設計支援了「送完請求就關閉發送方向，但仍等待回應」的模式**（早期 HTTP 的一種用法）。**代價就是「應用忘了 close」這個 bug 無法被 TCP 自動修正。**

**「查看狀態分布」是排查的第一步**：`netstat -ant | awk '{print $6}' | sort | uniq -c` 或 `ss -s`——**先看哪個狀態異常多，再據此判斷方向**。**這比一開始就抓包快得多，也常常直接就給出答案。**

## 面試回答方式

先給每個狀態對應的具體問題，並強調**這是它們的診斷價值**。加分點有四個：**`CLOSE_WAIT` 與 `FIN_WAIT_2` 是同一個問題的兩面**——**一方堆積 CLOSE_WAIT 另一方就堆積 FIN_WAIT_2**，**這讓「問題在哪一端」變成可以直接判斷的事**；**`CLOSE_WAIT` 不會超時消失**——**因為 TCP 認為應用還有資料要送是合法的**，**所以它會累積直到耗盡檔案描述符，表現為「跑幾天就掛」**；**半關閉是合法狀態**是理解這些的基礎；以及**先看狀態分布再據此判斷方向**，**比一開始就抓包快得多**。

## 講稿

每個異常狀態都直接指向一個特定的問題，這是它們的診斷價值。

大量的等待關閉狀態，代表對方已經送了結束訊號，而你的應用沒有呼叫關閉。這幾乎總是應用程式的問題，連線洩漏、沒在最終區塊關閉、或者處理執行緒卡住了。

而它有一個重要的特性，不會自己消失。另一個相關的狀態有作業系統層級的超時，而這個沒有，因為 TCP 認為應用還有資料要送是合法的。所以它會一直累積直到耗盡檔案描述符，表現為服務跑一段時間後無法接受新連線。這種跑幾天就掛的模式，看到它堆積就能立刻定位。

還有一個實用的診斷關聯。這個狀態跟對端的等待結束狀態是同一個問題的兩面。一方堆積這個，另一方就堆積那個。所以在客戶端看到大量等待結束時，應該去看伺服器端是不是有連線洩漏。

排查的第一步我會先看狀態分布，用統計指令看哪個狀態異常多，再據此判斷方向。這比一開始就抓包快得多，也常常直接就給出答案。

## 常見追問

### 連線洩漏怎麼定位到具體的程式碼？

**核心答案**：**用 `lsof -p <pid>` 或 `ss -tnp` 看那些連線的對端位址**——**通常能直接指出「是連到哪個服務的連線在洩漏」**。**然後在程式碼中找對應的客戶端**：**是不是有一條路徑沒有關閉、是不是連線池的設定有問題、或者是不是異常路徑跳過了關閉**。

**詳細解析**：**「異常路徑忘了關閉」是最常見的成因**：正常流程有 `close()`——**而某個 catch 分支直接 return 了**。**所以現代語言的 try-with-resources、`defer`、或 `using` 這類機制是根本的解法**——**它們讓「忘記關閉」在語法上變得困難**。**而在使用連線池時，洩漏的表現不同**：**連線沒有被歸還而非沒有被關閉**——**症狀是連線池耗盡而非檔案描述符耗盡**，**但根因是一樣的（某條路徑沒有釋放資源）**。**兩者的診斷方式也相似：看池的活躍連線數是否持續增長而不下降**。**而「用完就歸還」這件事應該由框架保證而非依賴每個開發者記得**——**這與「不要讓正確性依賴人的紀律」是同一個原則。**

**面試回答方式**：給定位方法（看對端位址找出是哪個服務的連線在洩漏，再回到程式碼）。核心加分點是**異常路徑忘了關閉是最常見的成因**，**而 try-with-resources 這類機制是根本解法，因為它們讓忘記關閉在語法上變得困難**。收在連線池的變體：**表現是連線沒被歸還而非沒被關閉，症狀是池耗盡而非描述符耗盡但根因一樣**，**而「用完就歸還」應該由框架保證**。

### TIME_WAIT 真的需要處理嗎？

**核心答案**：**多數情況不需要**。`TIME_WAIT` 佔用的資源很小（一個連線追蹤條目）——**而 2MSL（通常 60 秒）之後會自動消失**。**只有在「短連線量極大導致埠號耗盡」時才成為問題**，**而那時的正確解法依序是**：**改用長連線（連線池）→ 增加可用埠號範圍 → 開啟 `tcp_tw_reuse`**（**注意 `tcp_tw_recycle` 在 NAT 環境有問題且已被移除**）。

**詳細解析**：**「TIME_WAIT 存在的兩個理由」需要能說清楚，因為它決定了哪些「優化」是安全的**：**一是確保最後的 ACK 能被重傳**（如果對方沒收到 ACK 會重發 FIN）；**二是讓舊連線的殘留封包在網路中消散**，**避免它們被新的同五元組連線誤收**。**第二個理由是為什麼不能簡單地縮短它**——**在丟包率高的網路中，殘留封包確實可能延遲到達**。**而 `tcp_tw_reuse` 之所以相對安全，是因為它只在「新連線的時間戳大於舊連線的」時才重用**——**用時間戳排除了殘留封包的混淆**。**理解這個機制，就知道為什麼它需要兩端都開啟時間戳選項才有效。**

**面試回答方式**：先回答多數情況不需要並給出成為問題的條件與解法的優先順序。核心加分點是說清楚 **TIME_WAIT 存在的兩個理由**（確保最後 ACK 能重傳、讓殘留封包消散）並指出**第二個是為什麼不能簡單縮短**。收在 **`tcp_tw_reuse` 為什麼相對安全**：**它用時間戳排除殘留封包的混淆**，**所以需要兩端都開啟時間戳選項才有效**。

### 為什麼有時候連線莫名其妙斷了？

**核心答案**：**四個常見原因**。**中間設備的閒置超時**——**NAT、防火牆、負載平衡器都會清理長時間沒有流量的連線**，**而它們通常不會通知兩端**。**應用層的閒置超時**——伺服器主動關閉。**TCP keepalive 探測失敗**——**但預設的 2 小時太長，多數情況輪不到它**。**以及對端的行程重啟或崩潰。**

**詳細解析**：**「中間設備的靜默清理」是最陰險的一種**：連線在兩端的狀態表中仍然是 `ESTABLISHED`——**但中間的 NAT 已經丟棄了映射**；**於是下一次發送資料時會收到 RST 或者根本沒有回應**。**這正是「連線池裡的連線用的時候才發現壞了」這個經典問題的成因**。**解法有兩個層次**：**應用層的心跳**（週期性發送一個空請求，比 TCP keepalive 更可控且能穿透應用層代理）**與連線池的健康檢查**（取用前驗證、或者設定小於中間設備超時的最大閒置時間）。**而「連線池的最大閒置時間應該小於路徑上任何設備的超時」是一個實用的規則**——**通常設成 60 秒以內是安全的，因為多數 NAT 的預設是 5 分鐘。**

**面試回答方式**：給四個常見原因並指出 **TCP keepalive 預設 2 小時太長，多數情況輪不到它**。核心加分點是**中間設備的靜默清理最陰險**——**兩端狀態仍是 ESTABLISHED 但中間的映射已丟棄**，**這正是「連線池裡的連線用的時候才發現壞了」的成因**。收在兩層解法與一個實用規則：**連線池的最大閒置時間應該小於路徑上任何設備的超時，60 秒以內通常安全**。
