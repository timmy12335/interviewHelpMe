# 題目

TCP 的流量控制在控制什麼？它和擁塞控制是同一件事嗎？

## 核心答案

不是同一件事，兩者保護的對象不同。**流量控制保護接收端**——避免發送端送得比接收端處理得快，把對方的接收緩衝區撐爆。做法是接收端在每個確認中回報自己的**接收視窗**（還剩多少緩衝空間），發送端未確認的資料量不得超過這個數字。**擁塞控制保護的是網路**——避免所有連線一起把中間鏈路塞爆造成大量遺失，做法是發送端自己維護一個**擁塞視窗**，依據遺失與延遲的訊號動態調整。發送端實際能送出的量是**兩者取較小值**：接收端說「我只能收這麼多」與網路說「你只能送這麼多」，哪個更嚴格就聽哪個。**滑動視窗**則是實作流量控制的機制——發送端維護一個視窗，視窗內的資料可以在未收到確認前就送出，收到確認後視窗往前滑動，這讓 TCP 不必「送一個等一個」，是吞吐量的基礎。

## 詳細解析

滑動視窗為什麼能提升吞吐量：如果每送一段就要等確認，吞吐量會被往返時間死死限制住——高延遲鏈路上即使頻寬很大也跑不快。有了視窗，發送端可以在一個往返時間內送出「視窗大小」那麼多資料，理論吞吐量約等於**視窗大小除以往返時間**。這也解釋了為什麼跨洲的高頻寬鏈路需要**視窗縮放**這個選項——原始的視窗欄位只有 16 位元，最大 64KB，在往返 200 毫秒的鏈路上換算下來吞吐量上限很低，必須靠縮放選項放大。

**零視窗與視窗探測**：當接收端的應用程式來不及讀取，緩衝區滿了，它會回報接收視窗為 0，發送端就必須停止傳送。問題是「視窗打開了」這個通知本身可能遺失，於是發送端會定期送出**視窗探測**封包詢問對方，避免雙方永遠等待。實務上如果看到連線長時間停在零視窗，代表接收端的應用程式處理不過來，要去查對方的消費速度而不是網路。

接收視窗與應用程式的讀取速度直接相關：緩衝區由作業系統管理，應用程式讀走資料才會騰出空間。所以一個處理緩慢的消費端會透過零視窗**反向壓制**發送端——這其實是一種天然的背壓機制。理解這一點有助於解釋「為什麼下游變慢會讓上游也卡住」，在串流處理與訊息佇列的場景中，同樣的背壓概念反覆出現。

兩個視窗的關係在排查時很有用：吞吐量上不去時，先判斷是**接收端受限**（對方回報的視窗很小、或頻繁出現零視窗）還是**網路受限**（有遺失與重傳、擁塞視窗被壓低）。前者要優化對方的處理速度或緩衝區設定，後者要看鏈路品質或調整擁塞控制演算法。搞錯方向會浪費大量時間。

**緩衝區調太大也有代價**：一味放大接收與傳送緩衝區可以提高吞吐量，但會增加**排隊延遲**——資料在緩衝區裡排很久才送出，對延遲敏感的應用反而更糟，這個現象與網路設備上的緩衝膨脹是同一類問題。所以緩衝區大小是**吞吐量與延遲之間的取捨**，不是越大越好。

## 面試回答方式

第一句就把兩者分開——流量控制保護接收端、擁塞控制保護網路，並說明發送端實際能送的量是兩個視窗取較小值。接著解釋滑動視窗為什麼提升吞吐量：一個往返能送出一整個視窗，所以吞吐量約等於視窗除以往返時間，並用這個公式帶出高延遲鏈路需要視窗縮放選項。加分點有三個：零視窗與視窗探測，以及看到長時間零視窗代表對方應用程式處理不過來；接收視窗其實是一種天然的背壓機制；以及緩衝區不是越大越好，過大會增加排隊延遲。

## 講稿

這兩個保護的對象不一樣。流量控制保護接收端，避免我送得比對方處理得快，把它的緩衝區撐爆。擁塞控制保護的是網路，避免所有連線一起把中間鏈路塞爆。

流量控制的做法是接收端在每個確認裡回報自己還剩多少緩衝空間，也就是接收視窗，我未確認的資料量不能超過這個數字。擁塞控制則是我自己維護一個擁塞視窗，依據遺失跟延遲的訊號調整。實際能送多少，就是這兩個取比較小的那一個。

滑動視窗是實作流量控制的機制。有了視窗，我可以在一個往返時間內送出一整個視窗的資料，不用送一個等一個。所以吞吐量大概等於視窗大小除以往返時間。這個公式解釋了為什麼跨洲的高頻寬鏈路需要視窗縮放這個選項，原本的欄位只有十六位元，最大六十四 KB，在往返兩百毫秒的鏈路上算下來上限很低。

排查的時候這兩個視窗很好用。吞吐量上不去，我先判斷是接收端受限還是網路受限。對方回報的視窗很小或常常零視窗，那是對方處理不過來。有遺失跟重傳，那是網路。方向搞錯會浪費很多時間。

## 常見追問

### 出現零視窗代表什麼？該怎麼處理？

**核心答案**：代表**接收端的接收緩衝區已滿**，也就是對方的應用程式讀取速度跟不上。發送端必須停止傳送並定期送出視窗探測，等對方回報視窗打開。處理方向是**去查接收端的處理能力**——執行緒是否被阻塞、消費邏輯是否太慢、是否有下游依賴拖累，而不是調整網路設定。

**詳細解析**：短暫的零視窗是正常的（例如接收端剛好在做一次較久的處理），持續或頻繁出現才是問題。排查時可以看抓包中的零視窗通告與探測封包的頻率。要注意放大接收緩衝區只是把問題往後推——它讓接收端可以先囤積更多資料，但如果消費速度長期低於生產速度，緩衝區終究會滿，而且更大的緩衝區意味著更長的排隊延遲與更大的記憶體佔用。真正的解法是提升消費端的處理能力或在應用層做限流。這個「緩衝不能解決速度不匹配」的道理，在訊息佇列的積壓問題上完全一樣。

**面試回答方式**：明確指出根因在接收端的應用程式，並給排查方向（執行緒阻塞、消費邏輯、下游依賴）。加分點是點出放大緩衝區只是把問題往後推，並把它連結到訊息佇列積壓的同一個道理——緩衝解決不了長期的速度不匹配。

### 為什麼高頻寬高延遲的鏈路需要調整視窗大小？

**核心答案**：因為吞吐量受限於**視窗大小除以往返時間**。跨洲鏈路的往返時間可能是 200 毫秒，如果視窗只有 64KB，理論吞吐量約每秒 320KB，不管實體頻寬有多大都跑不快。要充分利用頻寬，視窗必須**大於等於頻寬與延遲的乘積**——這就是所謂的頻寬延遲乘積。做法是啟用視窗縮放選項並適當放大緩衝區。

**詳細解析**：這解釋了一個常見的困惑：「兩地之間頻寬明明有 1Gbps，為什麼單一連線只跑到幾十 Mbps」。答案通常不是頻寬不足，而是**單一連線的視窗不夠大**——這也是為什麼傳輸大檔案的工具會開多條連線並行傳輸，等於用連線數繞過單連線的視窗限制。要注意視窗縮放需要**兩端都支援並在握手時協商**，而某些中間設備會破壞這個選項導致協商失敗，症狀就是怎麼調緩衝區都沒有效果。另外自動調整緩衝區大小的機制在多數現代系統上預設啟用，所以手動調整前應該先確認它有沒有生效。

**面試回答方式**：給出吞吐量公式與頻寬延遲乘積這個概念，並用「1Gbps 鏈路單連線只跑幾十 Mbps」這個具體困惑切入。加分點是說明多條並行連線是繞過單連線視窗限制的常見手段，以及中間設備破壞選項會讓調整完全沒效果。

### 緩衝區設定得越大越好嗎？

**核心答案**：**不是**。放大緩衝區能提高吞吐量上限，但代價是**排隊延遲增加**——資料在緩衝區中等待的時間變長，對延遲敏感的應用（互動式請求、即時通訊）反而更糟。而且緩衝區佔用記憶體，連線數多時總量可觀。所以它是**吞吐量與延遲之間的取捨**，該依應用特性決定，而不是一律調大。

**詳細解析**：同樣的道理在網路設備上被稱為**緩衝膨脹**——中間路由器配置了過大的緩衝區，壅塞時封包不是被丟棄而是排隊，導致延遲飆升到數百毫秒甚至更高。因為 TCP 傳統的擁塞控制主要靠「遺失」判斷壅塞，緩衝區太大反而讓它偵測不到壅塞、持續加速，形成惡性循環。這也是以延遲為訊號的擁塞控制演算法（例如 BBR）出現的動機之一——它們量測往返時間與頻寬而不是等封包遺失，因此在大緩衝區的環境下表現更好。能把緩衝區設定連結到擁塞控制演算法的演進，會顯示你理解的是系統而不只是參數。

**面試回答方式**：明確否認並給出取捨（吞吐量 vs 排隊延遲與記憶體）。加分點是講緩衝膨脹——過大的緩衝讓傳統以遺失為訊號的擁塞控制失靈，並連結到 BBR 這類以延遲與頻寬為訊號的演算法出現的動機。
