# 題目

HTTP 報文由哪些部分組成？常見狀態碼各自代表什麼，選錯會有什麼後果？

## 核心答案

報文分三段：**起始行**（請求是方法、路徑、版本；回應是版本、狀態碼、原因短語）、**標頭**（每行一個鍵值對，描述內容型別、長度、快取、認證等）、以及**主體**（可選）。標頭與主體之間用**一個空行**分隔，主體的長度由 `Content-Length` 或分塊傳輸編碼決定。狀態碼分五類：**1xx** 資訊、**2xx** 成功、**3xx** 重新導向、**4xx** 用戶端錯誤、**5xx** 伺服器錯誤。選錯的後果是實質的，因為很多基礎設施會依狀態碼自動行動：監控依 5xx 觸發告警、負載平衡器與客戶端函式庫依 5xx 或 429 決定要不要重試、CDN 依 2xx 與快取標頭決定要不要快取、爬蟲依 4xx 決定是否放棄。所以最常見也最傷的錯誤是**把用戶端的錯誤回成 500**（讓告警被無意義的噪音淹沒）與**把錯誤包在 200 裡回傳**（讓所有自動化機制都失效，錯誤率永遠看起來是零）。

## 詳細解析

**4xx 與 5xx 的分界是「誰該修」**：4xx 表示請求本身有問題，重試同樣的請求不會成功，該由呼叫方修正；5xx 表示伺服器端出問題，同樣的請求之後可能成功，所以**允許重試**。這條線決定了自動重試的行為，也決定了值班的人該不該被叫醒。把參數驗證失敗回成 500 是很常見的壞習慣，它會讓真正的伺服器故障被埋在噪音裡。

**幾個容易混淆的狀態碼**：**401 是未認證**（你是誰我不知道，請提供憑證），**403 是已認證但無權限**（我知道你是誰，但你不能做這件事）——搞反會讓客戶端做出錯誤的處理（例如收到 403 卻反覆嘗試重新登入）。**404 是資源不存在**，**400 是請求格式錯誤**，**422 常用於格式正確但語意無效**。**409 衝突**適合表達「與目前狀態不相容」（例如重複建立、版本衝突）。**429 是被限流**，配合 `Retry-After` 標頭告知何時可以重試，這對客戶端實作退避極有幫助。

**3xx 的差別影響 SEO 與行為**：**301 永久**會被瀏覽器與搜尋引擎快取並轉移權重，設錯很難收回（使用者的瀏覽器可能長期記住）；**302 暫時**不轉移權重也不長期快取。**307 與 308** 的關鍵差別是**保持原方法不變**——301 與 302 在歷史實作上可能把 POST 變成 GET，需要嚴格保持方法時要用 307 或 308。

**冪等與安全的區分常被混淆**：**安全**指不改變伺服器狀態（GET、HEAD），**冪等**指執行多次與執行一次效果相同（GET、PUT、DELETE 冪等；POST 通常不冪等）。這個性質決定了**中間設備能不能自動重試**——冪等的方法可以，不冪等的必須由應用層用冪等鍵處理。設計 API 時把這件事想清楚，比事後補救容易得多。

**回應主體的錯誤格式要一致**：狀態碼表達類別，主體表達細節。實務上應該定義一套統一的錯誤結構（錯誤碼、可讀訊息、可選的欄位層級細節、以及追蹤 ID），讓呼叫方能程式化處理。錯誤訊息不應該洩漏內部細節（堆疊追蹤、SQL、內部主機名），這是很常見的資訊洩漏來源。

## 面試回答方式

先給三段結構與空行分界，快速帶過。重點放在狀態碼的選擇為什麼是工程問題而不是風格問題——監控、重試、快取、爬蟲都會依它自動行動，並直接點名兩個最傷的錯誤：把用戶端錯誤回成 500、以及把錯誤包在 200 裡。接著給 4xx 與 5xx 的判準：**誰該修、重試會不會成功**。加分點有三個：401 與 403 的差別（未認證 vs 無權限）以及搞反的後果；301 與 302、307 與 308 的差別，特別是保持方法不變；以及安全與冪等的區分決定了能不能自動重試。

## 講稿

報文分三段，起始行、標頭、主體，標頭跟主體中間用一個空行分開，主體長度由 Content-Length 或者分塊編碼決定。

狀態碼我想多講一點，因為它其實是工程問題不是風格問題。很多基礎設施會依狀態碼自動行動，監控依 5xx 告警，客戶端函式庫依 5xx 或 429 決定要不要重試，CDN 依狀態碼跟快取標頭決定要不要快取。

所以有兩個最傷的錯誤。第一是把用戶端的錯誤回成 500，這會讓真正的伺服器故障被噪音埋掉。第二是把錯誤包在 200 裡面回傳，這會讓所有自動化機制全部失效，錯誤率永遠看起來是零。

我判斷 4xx 還是 5xx，看兩件事，誰該修、以及重試會不會成功。請求本身有問題、重試也不會成功的是 4xx。伺服器出狀況、待會可能就好了的是 5xx。

還有幾個容易搞混的。401 是我不知道你是誰，403 是我知道你是誰但你不能做這件事。搞反的話客戶端會反覆嘗試重新登入。另外 301 是永久的，瀏覽器會長期記住，設錯很難收回，暫時性的要用 302。

## 常見追問

### 為什麼「把錯誤包在 200 裡」是個問題？

**核心答案**：因為它讓所有依賴狀態碼的自動化機制失效。監控看到的錯誤率永遠是零，告警不會觸發；客戶端函式庫與代理不會自動重試（它們以為成功了）；CDN 可能把錯誤回應當成正常內容快取起來，讓後續使用者也拿到錯誤；日誌與追蹤系統無法自動標記失敗的請求。結果是**問題只能靠使用者回報發現**，而不是被系統偵測到。

**詳細解析**：這個做法通常源於歷史包袱或前端框架的限制（早期某些客戶端對非 2xx 的處理不友善），但代價遠大於便利。正確的做法是狀態碼表達類別、主體表達細節，兩者不衝突。如果既有系統已經這樣做，遷移的方式是先在主體中保留原有欄位、同時開始回正確的狀態碼，讓呼叫方逐步切換，再移除舊欄位。另外要注意**部分成功**的情境（批次操作中有些成功有些失敗）確實不好用單一狀態碼表達，這時用 207 這類多重狀態的回應，或明確定義「批次接受成功、個別結果在主體中」的語意，並在文件中說清楚。

**面試回答方式**：列出失效的機制（監控、重試、快取、追蹤）並歸結為「問題只能靠使用者回報」。給出正確原則：狀態碼表達類別、主體表達細節。加分點是給遷移路徑（先雙寫再切換），以及誠實處理批次操作這種確實不好用單一狀態碼表達的情境。

### 什麼時候該用 429，要搭配什麼標頭？

**核心答案**：**觸發速率限制**時用 429，並且**必須搭配 `Retry-After`** 告知呼叫方何時可以再試（可以是秒數或絕對時間）。沒有這個標頭，客戶端只能盲目重試，常見的結果是所有被限流的客戶端同時重試，形成尖峰把服務再打一次。搭配它之後，客戶端函式庫可以自動等待正確的時間。

**詳細解析**：更完整的做法是同時回傳限流的**額度資訊**（剩餘配額、配額重置時間、總額度），讓呼叫方能主動控制節奏而不是撞到牆才反應。客戶端側則應該實作**指數退避加隨機抖動**——抖動很關鍵，它避免所有客戶端在同一時刻重試造成同步的尖峰。要注意 429 與 503 的區分：429 表示「你太快了」，是針對特定呼叫方的；503 表示「我現在不可用」，是服務整體的狀態，通常也搭配 `Retry-After`。兩者都表達「稍後再試」，但原因與後續行動不同，混用會讓客戶端無法正確處理。

**面試回答方式**：明確說必須搭配 `Retry-After`，並解釋沒有它會造成同步重試尖峰。加分點是提出回傳額度資訊讓呼叫方主動控速、客戶端要做指數退避加抖動、以及 429 與 503 的語意差別。

### 冪等和安全的差別是什麼？為什麼重要？

**核心答案**：**安全**指請求不改變伺服器狀態（GET、HEAD、OPTIONS），**冪等**指同一個請求執行多次的效果與執行一次相同（GET、HEAD、PUT、DELETE 冪等，POST 通常不是）。安全的方法必然冪等，反之不然——PUT 會改狀態所以不安全，但重複執行結果一樣所以冪等。重要性在於**它決定了誰可以自動重試**：中間設備與客戶端函式庫可以放心重試冪等的請求，不冪等的則不行。

**詳細解析**：實務上最常見的問題是 **POST 的重試**。網路逾時後客戶端無法確定伺服器是否處理了請求，重試可能造成重複下單或重複扣款。解法是引入**冪等鍵**——客戶端為每次業務操作產生唯一的鍵一併送出，伺服器記錄已處理的鍵並在重複時直接回傳先前的結果。這把不冪等的操作在應用層變成冪等的。另一個細節是 **DELETE 的冪等性**：刪除一個已經被刪除的資源，回 404 還是 204 都算合理，但要在 API 文件中明確定義，否則呼叫方的重試邏輯會依賴不確定的行為。

**面試回答方式**：清楚定義兩者並指出安全必然冪等、反之不然。核心是它決定了誰能自動重試。加分點是講 POST 重試的實際風險與冪等鍵的解法，以及 DELETE 重複刪除的回應要在文件中明確定義。
