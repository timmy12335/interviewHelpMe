# 題目

什麼時候該抓包？抓到之後怎麼看？

## 核心答案

抓包是「最後才用」的工具，因為它成本高：產生大量資料、需要專業知識判讀、而且在加密的今天能看到的內容有限。應該先用日誌、指標、與連線狀態統計——只有在「兩邊各說各話」（客戶端說沒收到、伺服器說送了）時，抓包才是唯一的仲裁。

**抓的時候三個原則**。**用過濾器縮小範圍**——**`tcpdump -i eth0 host 1.2.3.4 and port 443`**；不加過濾在繁忙的機器上幾秒就是幾 GB。**寫入檔案而非直接輸出**——**`-w capture.pcap`，之後用 Wireshark 分析**。**以及限制大小與時間**——`-C 100 -W 5`（輪替五個 100MB 的檔案），避免填滿磁碟。

**分析時最有用的三個視角**：**Statistics 的 Conversations（看哪些連線量最大）**、Expert Information（Wireshark 自動標出的異常：重傳、亂序、視窗滿）、以及跟隨 TCP 流（看一條連線的完整對話）。

## 詳細解析

**「先看 Expert Information」能省下大量時間**：Wireshark 會自動標記重傳、重複 ACK、零視窗、以及各種協定異常——於是不需要逐個封包看，直接跳到有問題的地方。而它的分類（Error、Warning、Note）也提供了嚴重性的排序。很多人打開 Wireshark 就開始逐行捲動，而那是最沒有效率的做法。

「零視窗」是一個非常明確的訊號：接收方宣告視窗為 0——表示它的接收緩衝區滿了，應用讀取不過來；**於是發送方必須停止**。看到零視窗就知道「瓶頸在接收方的應用而非網路」——這一個發現就能把排查方向完全轉過來。而它的對應處理是「看接收方的應用為什麼處理慢」而非調任何網路參數。

「在加密的世界裡抓包還能看什麼」：內容看不到——但仍然能看到連線的建立與關閉、重傳、RTT、視窗變化、以及封包的時序。這些對「網路層的問題」完全夠用。而如果需要看內容，選項是「在 TLS 終止之後抓」（在應用伺服器本機、或者在解密的代理之後）或者**「用 SSLKEYLOGFILE 匯出金鑰讓 Wireshark 解密」**（僅限你控制的客戶端，用於除錯）。

「在容器與雲端抓包」有額外的複雜度：容器內可能沒有 tcpdump——需要用一個帶工具的臨時容器加入同一個網路命名空間（`kubectl debug` 或 `nsenter`）。而在雲端，虛擬網路的某些層次是抓不到的——廠商提供的流量鏡像（VPC Traffic Mirroring）是那時的選項。

## 面試回答方式

先定位**抓包是最後才用的工具**與它的成本，指出只有在「兩邊各說各話」時它才是唯一的仲裁。給抓取的三個原則與分析的三個視角。加分點有四個：**先看 Expert Information 能省下大量時間**——它自動標出重傳、亂序、零視窗並提供嚴重性分類，而逐行捲動是最沒效率的做法；**零視窗是非常明確的訊號**——表示接收方的應用讀取不過來，這一個發現就能把排查方向完全轉過來；加密之後仍能看到連線建立、重傳、RTT、時序，這些對網路層的問題完全夠用；以及在容器與雲端抓包的額外複雜度與對應的工具。

## 講稿

抓包是最後才用的工具，因為它成本高。產生大量資料、需要專業知識判讀、而且在加密的今天能看到的內容有限。應該先用日誌、指標、跟連線狀態統計。只有在兩邊各說各話的時候，客戶端說沒收到而伺服器說送了，抓包才是唯一的仲裁。

抓的時候我有三個原則。用過濾器縮小範圍，因為不加過濾在繁忙的機器上幾秒就是幾 GB。寫入檔案而不是直接輸出。還有限制大小跟時間避免填滿磁碟。

分析時最有用的第一步是看專家資訊，它會自動標記重傳、重複確認、零視窗跟各種異常，於是不需要逐個封包看。很多人打開分析軟體就開始逐行捲動，那是最沒有效率的做法。

而零視窗是一個非常明確的訊號。接收方宣告視窗為零，表示它的緩衝區滿了、應用讀取不過來，於是發送方必須停止。看到它就知道瓶頸在接收方的應用而不是網路。這一個發現就能把排查方向完全轉過來，而對應的處理是去看接收方的應用為什麼慢，不是調任何網路參數。

另外在加密的世界裡雖然看不到內容，但連線建立、重傳、往返時間、視窗變化都還看得到，這些對網路層的問題完全夠用。

## 常見追問

### 怎麼在生產環境安全地抓包？

**核心答案**：**四個原則**。**限制範圍**——只抓相關的主機與端口，避免捕捉到其他使用者的資料。**限制時間與大小**——設定自動停止，避免影響磁碟與效能。**注意隱私與合規**——封包可能包含個資，儲存與傳輸都要謹慎（加密內容相對安全，但明文的內部流量不是）。**以及評估效能影響**——抓包本身消耗 CPU 與磁碟 IO，在高流量的機器上可能造成影響。

**詳細解析**：「抓包的效能影響取決於過濾器的位置」：BPF 過濾器在核心中執行——於是不匹配的封包在複製到使用者空間之前就被丟棄，成本很低；而如果用 tcpdump 抓全部再用 grep 過濾，那每個封包都要被複製與處理，成本高得多。所以「過濾器寫得越精確，影響越小」——這是一個「把過濾下推到最底層」的優化，與資料庫的謂詞下推是同一個思路。另一個實務建議是「在流量鏡像或旁路上抓而非在生產機上」——如果基礎設施支援（交換機的鏡像端口、雲端的流量鏡像），那就完全沒有效能影響；而它的代價是設定的複雜度與可能的額外成本。

**面試回答方式**：給四個原則並提醒明文的內部流量在隱私上不如加密流量安全。核心加分點是效能影響取決於過濾器的位置——BPF 在核心中執行、不匹配的封包在複製前就丟棄，**而抓全部再過濾成本高得多**，這是「把過濾下推到最底層」的優化，與資料庫的謂詞下推同思路。收在更好的做法：在流量鏡像或旁路上抓完全沒有效能影響。

### 有哪些比抓包更輕的工具？

**核心答案**：**幾個按侵入性遞增**。**`ss -ti`**——連線的即時狀態與 TCP 指標，零成本。**`nstat` 或 `netstat -s`**——協定層級的累計計數（重傳、丟棄、錯誤），零成本。**eBPF 工具（`tcpconnect`、`tcpretrans`、`tcplife`）**——在核心中追蹤特定事件並只輸出摘要，成本極低但需要較新的核心。**以及應用層的追蹤**——如果已經有分散式追蹤，那裡的資訊往往比封包更貼近問題。

**詳細解析**：「eBPF 工具是抓包與指標之間的最佳中間點」：它能回答「哪些連線在重傳」「哪個行程建立了這些連線」「連線的生命週期多長」——這些是純指標給不了而抓包成本太高的問題。而它的輸出是結構化的摘要而非原始封包——**於是不需要專業的判讀**。在有較新核心的環境中，`bcc` 或 `bpftrace` 的工具集應該是排查的第二步（在指標之後、抓包之前）。這個「工具的侵入性應該逐步升級」的順序——先看免費的指標、再用低成本的追蹤、最後才抓包——能讓多數問題在前兩步就被解決，而那是排查效率的關鍵。

**面試回答方式**：給按侵入性遞增的工具清單。核心加分點是eBPF 工具是抓包與指標之間的最佳中間點——它能回答純指標給不了而抓包成本太高的問題，且輸出是結構化摘要不需要專業判讀。收在原則：**工具的侵入性應該逐步升級**（免費指標、低成本追蹤、最後抓包），能讓多數問題在前兩步就被解決，而那是排查效率的關鍵。

### 抓到的資料怎麼與應用日誌對照？

**核心答案**：**用時間戳與五元組關聯**。抓包的時間戳與應用日誌的時間戳對齊——於是能看到「應用說它在 12:00:01 送出了回應」對應到封包中的哪一個。而五元組（來源與目標的 IP 與端口）讓你能定位到具體的連線。**前提是「兩邊的時鐘同步」**（NTP），**否則對照會有偏差。**

**詳細解析**：「在應用日誌中記錄本地端口」是一個成本極低但極有用的做法：一條日誌記錄「我用本地端口 54321 連到了 10.0.0.5:443」——於是抓包中的那條連線能被精確定位。沒有它的話，在一台有幾千條連線的機器上找到「就是這一條」非常困難。而多數框架不會預設記錄這個資訊，需要自己加。同樣有用的是「在日誌中記錄追蹤 ID 並在請求標頭中傳遞」——於是能從應用日誌一路對應到下游的日誌；而如果流量是明文的，追蹤 ID 甚至能在封包中被搜尋到，讓「應用視角」與「網路視角」完全打通。這類「事先埋一點資訊以便事後關聯」的投入，在排查困難問題時的回報極高。

**面試回答方式**：給關聯方法（時間戳加五元組）與前提（時鐘同步）。核心加分點是**在應用日誌中記錄本地端口**——沒有它在幾千條連線中找到「就是這一條」非常困難，而多數框架不預設記錄需要自己加。收在延伸與原則：記錄追蹤 ID 並在標頭中傳遞能打通應用與網路視角，而「事先埋一點資訊以便事後關聯」在排查困難問題時回報極高。
