# 題目

HTTPS 的握手過程做了哪些事？為什麼要同時用到對稱與非對稱加密？

## 核心答案

握手要達成三件事：**驗證伺服器身分**、**協商加密演算法**、**安全地產生共用的對稱金鑰**。之所以兩種加密都用，是因為它們各有不可替代之處——**非對稱加密**能在不安全的通道上安全地交換金鑰、也能驗證身分（憑證簽章），但**運算成本高**，不適合加密大量資料；**對稱加密**速度快幾個數量級，但**前提是雙方已經有共用金鑰**。所以流程是：**用非對稱的方式安全地協商出一把對稱金鑰，之後的所有資料都用對稱加密傳輸**。TLS 1.2 的握手需要**兩個往返**：客戶端送出支援的演算法與隨機數，伺服器回傳選定的演算法、憑證與自己的隨機數，雙方再交換金鑰材料並確認。**TLS 1.3 大幅簡化**，把往返壓到**一次**（重連甚至可以零往返），做法是客戶端在第一個訊息中就先送出金鑰交換的參數猜測，同時**移除了所有不安全的舊演算法**。

## 詳細解析

**前向保密是現代 TLS 的關鍵性質**：舊做法是客戶端用伺服器公鑰加密一個預主金鑰送過去，問題是**伺服器私鑰一旦外洩，攻擊者可以解密之前錄下的所有流量**。現代做法改用 Diffie-Hellman 這類金鑰交換——雙方各自產生臨時的金鑰對、只交換公開部分就能算出共用秘密，而**臨時私鑰用完即丟**。這樣即使長期私鑰外洩，過去的流量仍然安全。TLS 1.3 只保留具備前向保密的金鑰交換方式，這是它移除舊演算法的主要動機之一。

**憑證驗證做了什麼**：客戶端要確認三件事——憑證是否由**受信任的憑證機構**簽發（沿著信任鏈驗證到內建的根憑證）、憑證上的**網域是否與正在連線的網域相符**、以及憑證**是否在有效期內且未被撤銷**。任何一項失敗，連線就不該建立。實務上最常見的錯誤是**只驗證了簽章卻沒驗證網域**，這在自行實作 HTTP 客戶端時很容易發生，會讓中間人攻擊直接得逞。

**兩個隨機數與金鑰派生**：握手中雙方各自送出一個隨機數，最終的對稱金鑰由這些隨機數與交換出的共用秘密一起派生。隨機數的作用是**防止重放**——即使攻擊者錄下整段握手也無法重現，因為每次的隨機數不同。這也說明了**亂數品質的重要性**：如果隨機數可預測，整個安全性就崩潰，歷史上有多起因為亂數產生器有缺陷而導致的重大漏洞。

**握手的延遲成本與優化**：TLS 1.2 的兩個往返加上 TCP 的一個往返，建立一個 HTTPS 連線要三個往返；在跨洲鏈路上這就是數百毫秒。優化手段包括：升級到 **TLS 1.3**（省一個往返）、**工作階段恢復**（憑先前的票證跳過完整握手）、**連線重用**（根本不重新握手）、以及 **QUIC**（把 TCP 與 TLS 握手合併）。TLS 1.3 的 **0-RTT** 恢復能在第一個封包就帶資料，代價是**有重放風險**，所以只適合冪等的請求。

**SNI 與加密的邊界**：一台伺服器上通常託管多個網域，客戶端必須在握手初期用 **SNI** 告知要連的網域，伺服器才知道該送哪張憑證。問題是這個欄位在早期是**明文**的——即使流量加密，中間的觀察者仍知道你在連哪個網站。加密 SNI 的相關機制正是為此而生。這是「加密不等於完全隱私」的好例子，值得主動提出。

## 面試回答方式

先講握手要達成的**三個目標**（驗身分、協商演算法、產生對稱金鑰），再用「各有不可替代之處」解釋為什麼兩種加密都用——非對稱能在不安全通道上交換金鑰但慢，對稱快但需要先有共用金鑰。接著給往返成本：TLS 1.2 兩個往返、1.3 壓到一個。加分點有三個：**前向保密**——臨時金鑰用完即丟，所以長期私鑰外洩也不會危及過去的流量，這是 TLS 1.3 移除舊演算法的主因；憑證驗證必須同時檢查**簽章、網域相符、有效期**，只驗簽章不驗網域是自行實作客戶端時的經典漏洞；以及 SNI 明文洩漏了你在連哪個網站，說明加密不等於完全隱私。

## 講稿

握手要達成三件事，驗證伺服器身分、協商加密演算法、還有安全地產生一把共用的對稱金鑰。

為什麼兩種加密都要用，因為它們各有不可替代的地方。非對稱可以在不安全的通道上安全交換金鑰，也可以驗證身分，但運算很貴，不適合加密大量資料。對稱快很多，但前提是雙方已經有共用金鑰。所以流程就是用非對稱的方式協商出一把對稱金鑰，之後的資料全部用對稱加密。

TLS 1.2 的握手要兩個往返，1.3 壓到一個，重連甚至可以零往返。做法是客戶端在第一個訊息就先送出金鑰交換的參數猜測。

我想特別講前向保密。舊做法是客戶端用伺服器公鑰加密一個預主金鑰送過去，問題是伺服器私鑰一旦外洩，攻擊者可以解開之前錄下的所有流量。現在改用臨時的金鑰交換，雙方各自產生臨時金鑰對，用完即丟，所以就算長期私鑰外洩，過去的流量還是安全的。TLS 1.3 只保留有前向保密的方式。

還有一個常見的實作漏洞，驗證憑證的時候只驗了簽章卻沒驗網域是否相符，這樣中間人攻擊會直接成功。

## 常見追問

### TLS 1.3 的 0-RTT 有什麼風險？

**核心答案**：**重放攻擊**。0-RTT 讓客戶端在第一個封包就帶上應用資料，但伺服器此時還沒完成完整的握手驗證，**無法確認這個封包不是攻擊者錄下後重送的**。如果那個請求有副作用（下單、轉帳），重放就會造成重複執行。所以 0-RTT **只適合冪等的請求**，通常限定在 GET 這類讀取操作上。

**詳細解析**：實務上的防禦有幾層：伺服器維護一個**已見過的票證清單**在短時間內拒絕重複（但分散式部署下要同步這份清單，成本不低）、**限制 0-RTT 只用於冪等方法**（最常見也最實際的做法）、以及**限制早期資料的大小**。這個「用安全性換延遲」的取捨與 TCP Fast Open 完全相同，兩者面對的是同一個本質問題——**在完成驗證之前就接受資料**必然帶來重放風險。能把這兩者連起來講，會顯示你抓到的是原理而不是個別特性。

**面試回答方式**：明確指出風險是重放，並解釋原因（驗證未完成就接受資料）。給出三層防禦並說明「限定冪等方法」最實際。加分點是把它與 TCP Fast Open 連起來，指出兩者是同一個本質取捨。

### 憑證驗證失敗時，客戶端不應該怎麼處理？

**核心答案**：**不應該忽略錯誤繼續連線**。實務上最常見的糟糕做法是為了讓程式「先能跑」而關閉憑證驗證或接受任何憑證——這等於完全放棄了 HTTPS 的身分保證，中間人可以自由竊聽與竄改，而流量看起來仍然是加密的，問題極難被發現。正確的處理是**中止連線並回報明確的原因**（憑證過期、網域不符、簽發者不受信任）。

**詳細解析**：憑證問題通常有正當的解法：自簽憑證的內部環境應該**把自己的根憑證加入信任存放區**，而不是關閉驗證；憑證過期就更新並建立自動續期機制；網域不符表示設定有誤，要修正憑證或連線目標。真正需要固定憑證的高安全場景可以用**憑證釘選**，但要注意它讓憑證輪替變得困難，必須配套規劃備用釘選值，否則憑證更換時會導致全面無法連線——這個風險在行動應用上特別嚴重，因為使用者不一定會即時更新版本。

**面試回答方式**：明確說不該忽略，並指出關閉驗證等於放棄身分保證且問題難以察覺。給出三種常見情況的正確解法（加入根憑證、續期、修正設定）。加分點是講憑證釘選的取捨——提高安全但讓輪替困難，需要備用釘選值，在行動應用上風險尤其高。

### HTTPS 的效能開銷主要在哪裡？

**核心答案**：主要在**握手**而不是資料加密本身。握手涉及非對稱運算與額外的往返，成本高；建立之後的對稱加密在現代 CPU 上有專用指令加速，開銷很小，通常不是瓶頸。所以優化的重點是**減少握手次數**——連線重用、keep-alive、工作階段恢復、HTTP/2 多工，這些遠比調整加密套件有效。

**詳細解析**：具體的優化手段包括：**升級到 TLS 1.3** 省一個往返；**啟用工作階段恢復**讓重連跳過完整握手；**OCSP 裝訂**避免客戶端另外去查憑證撤銷狀態（那是額外的往返與第三方依賴）；以及**憑證鏈盡量短**，因為鏈太長會增加握手訊息的大小、可能造成額外的封包。要注意在**大量短連線**的場景（例如高頻的內部服務呼叫），握手成本會非常顯著，這時連線池的價值遠大於任何加密層面的調整。反過來在**長連線大流量**的場景，對稱加密的 CPU 成本才可能浮現，此時選擇有硬體加速的加密套件才有意義。**先確認自己屬於哪一種場景**是這題最重要的判斷。

**面試回答方式**：先糾正方向——成本在握手不在資料加密，因為對稱加密有硬體加速。給出減少握手次數的手段清單。加分點是分場景講：大量短連線該用連線池，長連線大流量才需要在意加密套件的 CPU 成本，並強調要先確認自己屬於哪一種。
