# 題目

什麼是 MTU 與 MSS？為什麼會出現「ping 得通、但傳大檔案就卡住」的情況？

## 核心答案

**MTU** 是一條鏈路一次能傳輸的最大訊框大小（乙太網路典型值 1500 位元組），**MSS** 是 TCP 段中**應用資料**的最大長度，等於 MTU 扣掉 IP 與 TCP 標頭。當封包超過路徑上某一段的 MTU 時，要嘛在該處**分片**，要嘛被丟棄。「ping 得通但傳大檔案卡住」的典型成因是 **PMTU 黑洞**：發送端用一般的封包大小送出並設了「不可分片」的旗標，中途某條鏈路的 MTU 較小（常見於 VPN、隧道、某些寬頻接入方式，因為額外的封裝佔用了空間），該處必須丟棄封包並回報一個 ICMP 訊息告知「太大了，請改用這個大小」——但**很多網路把 ICMP 全部封鎖**，這個通知回不來，發送端不知道要調小，於是持續重傳大封包、全部石沉大海。小封包（例如 ping 的預設大小）不受影響，所以連通性測試看起來完全正常。

## 詳細解析

**路徑 MTU 發現依賴 ICMP**：TCP 會透過交換 MSS 選項協商雙方各自的上限，但那只反映**兩端**的能力，中間鏈路的限制要靠路徑探測——而探測的回報機制就是 ICMP。所以「為了安全把 ICMP 全擋掉」是很常見但代價很大的設定，它直接破壞了這個機制。正確的做法是**允許必要的 ICMP 類型**（尤其是需要分片的通知），而不是一律封鎖。

**分片的代價很高**：IP 分片會讓**任一片遺失就整個封包報廢**（因為上層看到的是一個完整封包），在有遺失的網路上等於放大了失敗率；重組也消耗接收端的資源，而且分片還可能被某些設備直接丟棄。所以現代做法傾向**避免分片**——TCP 藉由 MSS 協商與路徑探測讓自己送出的段不超過限制，UDP 則需要應用層自己控制資料報大小。

**隧道與封裝是 MTU 問題的常見來源**：VPN、疊加網路、容器網路都會在原封包外再加一層標頭，可用空間因此變小。如果沒有相應調低內層的 MTU 或 MSS，就會產生前述的黑洞。實務上常見的緩解是 **MSS 夾制**——由中間設備在握手時把 MSS 選項改小，強制兩端使用較小的段，不依賴 ICMP 也能避免超標。這是容器與 VPN 環境中很實用的一招。

**症狀的識別特徵**：這類問題有很明顯的形態——**小請求正常、大回應卡住**；**握手成功但傳輸中途停住**；**改小傳輸大小就好了**。如果看到「登入正常但載入清單卡住」「短訊息可以但傳圖片不行」，就值得往這個方向查。驗證方式是用指定大小且不可分片的 ping 逐步測試，找出實際可通過的最大值。

**巨型訊框不是萬靈丹**：資料中心內部可以把 MTU 調到 9000 提升吞吐、減少每封包的處理開銷，但**路徑上所有設備都必須一致支援**，只要有一段不支援就會出現黑洞。而且它只在內部網路可控時才適用，跨出去仍然要回到標準大小。所以調大 MTU 是一個**需要端到端規劃**的決定，不是單機設定就能生效的優化。

## 面試回答方式

先定義 MTU 與 MSS 的關係（MSS 等於 MTU 扣掉標頭），再直接用 **PMTU 黑洞**回答那個現象——中途鏈路 MTU 較小、需要回報的 ICMP 被封鎖、發送端不知道要調小，於是大封包全數消失而小封包正常。這個回答本身就展示了排查能力。接著給**症狀的識別特徵**：小請求正常大回應卡住、握手成功但中途停住。加分點有三個：分片的代價是任一片遺失整個封包報廢，所以現代做法傾向避免分片；隧道與容器網路是常見成因，可用 **MSS 夾制**緩解；以及巨型訊框需要路徑上所有設備一致，不是單機設定。

## 講稿

MTU 是一條鏈路一次能傳的最大訊框大小，乙太網路典型是一千五。MSS 是 TCP 段裡應用資料的最大長度，等於 MTU 扣掉 IP 跟 TCP 的標頭。

ping 得通但傳大檔案卡住，典型成因是路徑 MTU 黑洞。發送端用一般大小送出並且設了不可分片，中途某條鏈路的 MTU 比較小，常見於 VPN、隧道或容器網路，因為多了一層封裝。那個節點必須丟棄封包並回一個 ICMP 說太大了、請改用這個大小。

問題是很多網路為了安全把 ICMP 全部擋掉，這個通知回不來，發送端不知道要調小，就一直重傳大封包，全部石沉大海。而小封包不受影響，所以連通性測試看起來完全正常。

這類問題的症狀很有特徵。小請求正常、大回應卡住，握手成功但傳到一半停住，或者把傳輸大小調小就好了。看到登入正常但載入清單卡住，我就會往這邊查。驗證方式是用指定大小而且不可分片的 ping 逐步測，找出實際能通過的最大值。

緩解上，容器跟 VPN 環境常用 MSS 夾制，由中間設備在握手時把 MSS 改小，不依賴 ICMP 也能避免超標。

## 常見追問

### 為什麼不該把 ICMP 全部封鎖？

**核心答案**：因為 ICMP **承載了必要的控制訊息**，不只是 ping。最關鍵的是「**需要分片但設了不可分片**」這個通知——它是路徑 MTU 發現的基礎，封鎖它會直接造成大封包黑洞。另外還有「目標不可達」「逾時」等訊息，它們讓發送端能快速得知失敗原因而不是傻等逾時。全部封鎖換來的安全收益有限（隱藏主機存在），付出的代價卻是難以排查的間歇性故障。

**詳細解析**：合理的做法是**依類型細分**——允許路徑 MTU 相關與必要的錯誤回報，限制或速率限制回應請求這類可能被用於掃描的類型。要注意 IPv6 對 ICMP 的依賴**更深**：它取消了路由器分片，完全依賴路徑 MTU 發現，而且鄰居發現機制本身就建立在 ICMPv6 上，封鎖它會讓網路根本無法運作。所以「封鎖 ICMP」這個在 IPv4 時代就已經有問題的做法，在 IPv6 環境中是直接的錯誤。這個對比是很好的加分點。

**面試回答方式**：說明 ICMP 承載控制訊息而不只是 ping，並以路徑 MTU 通知為最關鍵的例子。給出依類型細分的正確做法。加分點是指出 IPv6 對 ICMP 的依賴更深（取消路由器分片、鄰居發現建立其上），全部封鎖會讓網路無法運作。

### MSS 夾制是什麼？什麼時候需要？

**核心答案**：由**中間設備在 TCP 握手時修改 MSS 選項**，把兩端協商出的值強制改小，讓後續的段不會超過路徑上的最小 MTU。它的價值在於**不依賴 ICMP**——即使路徑上的 ICMP 被封鎖，也能避免產生過大的封包。典型的使用場景是 VPN、隧道與容器網路，因為額外封裝讓可用空間變小而兩端並不知情。

**詳細解析**：它的限制是**只對 TCP 有效**——UDP 沒有握手也沒有 MSS 協商，所以 UDP 上的大資料報仍需應用層自己控制大小，這是 QUIC 這類協定必須自己做路徑 MTU 探測的原因。另外夾制的值要**留足餘裕**：計算時要把所有封裝層的開銷都算進去，少算一層就仍會出問題。實務上遇到 MTU 相關的疑難時，一個快速的驗證手段是**暫時把內層 MTU 調小**看問題是否消失，若消失就確認了方向，再回頭找正確的設定位置。這個「先驗證方向再找根因」的排查順序很實用。

**面試回答方式**：解釋機制（中間設備改寫握手時的 MSS）與價值（不依賴 ICMP）。給出典型場景。加分點是指出它只對 TCP 有效、UDP 要自己處理（所以 QUIC 自己做探測），以及排查時可以先調小 MTU 驗證方向再找根因。

### 資料中心內部把 MTU 調大有什麼好處與風險？

**核心答案**：好處是**減少每封包的處理開銷**——同樣的資料量所需的封包數變少，CPU 中斷與標頭開銷都下降，在大量資料傳輸（儲存同步、備份、分散式運算的洗牌階段）的場景中吞吐提升明顯。風險是**路徑上所有設備都必須一致支援**，只要有一段不支援或設定遺漏，就會出現前述的黑洞，而且症狀是間歇性的、只在大封包時出現，極難排查。

**詳細解析**：實務上的建議是：**只在完全可控的內部網路啟用**，並且把它納入設定管理確保一致；**跨出邊界的流量維持標準大小**；以及**部署後主動驗證**——用指定大小的不可分片測試逐條路徑確認，而不是假設設定生效了。另一個容易忽略的是**虛擬化與容器層**：宿主機、虛擬交換器、容器網路介面都各有 MTU 設定，任一層不一致就會出問題，而這些層次往往由不同團隊管理。所以這類優化的真正成本不在技術而在**協調與驗證**，這一點值得在面試中誠實指出。

**面試回答方式**：給出好處（減少封包數與處理開銷）與適用場景，再給風險（全路徑必須一致、失敗時症狀間歇難查）。加分點是列出實務建議（只在可控網路啟用、邊界維持標準、部署後主動驗證），並指出虛擬化與容器各層 MTU 不一致是常見陷阱，真正成本在協調與驗證。
