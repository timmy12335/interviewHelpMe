# 題目

CORS 到底在保護誰？為什麼有時候會多一次 OPTIONS 請求？

## 核心答案

**先糾正一個常見的誤解：CORS 保護的是「使用者」，而不是「你的伺服器」**。同源政策的目的是**防止惡意網站用使用者的身份去讀取其他網站的資料**——**所以限制是由瀏覽器施加的，而且只限制「讀取回應」**。**非瀏覽器的客戶端（curl、後端服務）完全不受 CORS 影響**——**所以「加了 CORS 就安全了」是錯的，真正的授權必須在伺服器端。**

**預檢（preflight）的 OPTIONS 請求**——**只在「非簡單請求」時發生**。**簡單請求的條件是：方法是 GET、POST、HEAD，而且標頭只有幾個安全的（`Content-Type` 限於三種特定值）**。**一旦用了 `application/json`、自訂標頭、或 PUT/DELETE**——**就會先發一次 OPTIONS 詢問伺服器「這個跨源請求允許嗎」**。

**預檢的結果可以被快取**（`Access-Control-Max-Age`）——**這是消除重複預檢開銷的關鍵設定。**

## 詳細解析

**「為什麼有預檢」需要理解它保護的是什麼**：在 CORS 之前，瀏覽器就允許跨源的表單提交（POST）——**所以那類請求不需要保護（本來就能發）**。**而 PUT、DELETE、或帶自訂標頭的請求是 CORS 才引入的新能力**——**於是必須先徵得伺服器的同意，避免「新的能力讓舊的伺服器受到它沒預期的請求」**。**理解這個歷史脈絡，就知道為什麼「簡單請求」的定義看起來如此隨意**——**它其實是「HTML 表單本來就能做的事」的集合**。

**「預檢的效能代價」在跨源 API 中很實在**：每個非簡單請求都多一次往返——**在跨洲的場景中可能多 200 毫秒**。**所以應該設定 `Access-Control-Max-Age`**（**Chrome 上限 2 小時，Firefox 24 小時**）——**於是同樣的請求類型在有效期內不再預檢**。**這是一個一行設定就能顯著改善跨源 API 延遲的優化，卻經常被忽略。**

**「帶憑證的請求規則更嚴」**：如果請求帶 cookie（`credentials: 'include'`）——**伺服器的 `Access-Control-Allow-Origin` 不能是 `*`，必須是具體的來源**；**而且要設 `Access-Control-Allow-Credentials: true`**。**這個限制是刻意的**——**因為「允許任何來源帶著使用者的 cookie 讀取你的資料」是一個嚴重的漏洞**。

**「動態回顯 Origin 是一個常見的危險做法」**：為了「支援任意來源」而把請求的 `Origin` 直接回顯到 `Access-Control-Allow-Origin`——**再配合 `Allow-Credentials: true`**，**等於允許任何網站用使用者的身份讀取你的資料**。**正確的做法是「維護一個白名單並驗證」**——**而如果真的需要對所有人開放，那就不該有憑證。**

## 面試回答方式

先糾正誤解（**CORS 保護的是使用者而非你的伺服器，非瀏覽器客戶端完全不受影響**）並說明預檢的觸發條件。加分點有四個：**為什麼有預檢的歷史脈絡**——**跨源表單提交本來就允許所以不需要保護，而 PUT、DELETE 與自訂標頭是新能力**，**這解釋了「簡單請求」的定義為何看起來隨意**；**預檢的效能代價與 `Access-Control-Max-Age`**——**一行設定就能顯著改善跨源 API 延遲卻經常被忽略**；**帶憑證時不能用萬用字元**，**這個限制是刻意的**；以及**動態回顯 Origin 加上允許憑證等於允許任何網站讀取你的資料**。

## 講稿

我會先糾正一個常見的誤解。跨源資源共享保護的是使用者，不是你的伺服器。同源政策的目的，是防止惡意網站用使用者的身份去讀取其他網站的資料，所以限制是瀏覽器施加的，而且只限制讀取回應。非瀏覽器的客戶端完全不受影響。所以加了它就安全了是錯的，真正的授權必須在伺服器端。

預檢請求只在非簡單請求時發生。簡單請求的條件是方法為 GET、POST、HEAD，而且標頭只有幾個安全的。一旦用了 JSON 內容類型、自訂標頭、或其他方法，就會先發一次詢問。

為什麼有預檢？因為在這個機制之前，瀏覽器就允許跨源的表單提交，那類請求本來就能發所以不需要保護。而其他方法跟自訂標頭是新引入的能力，必須先徵得伺服器同意。理解這個脈絡，就知道為什麼簡單請求的定義看起來這麼隨意，它其實是表單本來就能做的事的集合。

還有一個常被忽略的優化。預檢的結果可以被快取，設定最大存活時間之後，同樣的請求類型在有效期內不再預檢。這是一行設定就能顯著改善跨源延遲的優化。

## 常見追問

### 為什麼有時候看不到錯誤的細節？

**核心答案**：**因為瀏覽器刻意不把跨源失敗的細節暴露給 JavaScript**——**否則那本身就是一個資訊洩漏管道**（**攻擊者可以透過錯誤訊息探測其他網站的狀態**）。**所以 `fetch` 的錯誤是一個籠統的 `TypeError`，而真正的原因要看瀏覽器主控台的 CORS 警告訊息**——**那裡有明確的說明（缺少哪個標頭、Origin 不匹配等）。**

**詳細解析**：**「不透明回應（opaque response）」是同一個原則的另一個體現**：用 `mode: 'no-cors'` 發的請求會成功——**但你拿到的回應是不透明的（讀不到狀態碼、標頭、body）**。**它的用途是「只需要副作用而不需要回應」的場景（例如上報一個事件）**——**而很多人誤以為它是「繞過 CORS 的方法」**。**它不是**：**它只是讓請求不失敗，但你仍然拿不到資料**。**這個誤解在除錯時會浪費大量時間**——**而理解「CORS 限制的是讀取而非發送」就能立刻排除這條路**。

**面試回答方式**：給根本原因（**暴露細節本身就是資訊洩漏管道**）並指出**真正的原因在主控台的 CORS 警告中**。核心加分點是說明**不透明回應是同一個原則的另一個體現**——**用 no-cors 發的請求會成功但讀不到任何東西**，**而很多人誤以為它是繞過 CORS 的方法**。收在關鍵理解：**CORS 限制的是讀取而非發送**，**理解這一點就能立刻排除那條路**。

### 後端該怎麼正確設定 CORS？

**核心答案**：**四件事**。**維護一個明確的來源白名單並驗證 `Origin`**（不要回顯、不要用萬用字元加憑證）。**明確列出允許的方法與標頭**（`Access-Control-Allow-Methods`、`Allow-Headers`）。**設定 `Max-Age` 減少預檢**。**以及「如果需要讓前端讀取自訂的回應標頭，必須用 `Access-Control-Expose-Headers` 明確列出」**——**這一項最常被遺漏。**

**詳細解析**：**「Expose-Headers 被遺漏」的症狀很典型**：後端明明回傳了 `X-Total-Count`——**而前端 `response.headers.get('X-Total-Count')` 拿到 null**。**因為預設只有幾個「簡單回應標頭」對 JavaScript 可見**（`Content-Type`、`Cache-Control` 等）——**自訂的必須明確暴露**。**這個問題在分頁、限流資訊、追蹤 ID 這類需要從標頭讀取中繼資料的場景中很常見**。**另一個實務建議是「用框架或中介軟體處理 CORS 而非手寫」**——**因為正確處理預檢、憑證、與各種邊界情況的細節很多**，**手寫容易漏掉某一項而在特定情況下失敗**。**而漏掉的那一項往往在某個瀏覽器的某個版本上才暴露，極難排查。**

**面試回答方式**：給四件事並指出 **Expose-Headers 最常被遺漏**。核心加分點是描述它的典型症狀：**後端回傳了自訂標頭而前端拿到 null**，**因為預設只有幾個簡單回應標頭對 JavaScript 可見**，**在分頁、限流資訊、追蹤 ID 這類場景中很常見**。收在建議：**用框架或中介軟體而非手寫**——**細節很多，漏掉的那一項往往在某個瀏覽器的某個版本上才暴露，極難排查**。

### CORS 與 CSP 有什麼關係？

**核心答案**：**方向相反**。**CORS 控制「我的頁面能不能讀取別人的資源」**（由資源方授權）；**CSP 控制「我的頁面能載入哪些來源的資源」**（由頁面方限制）。**前者是「別人允許我讀」，後者是「我限制自己能載入什麼」**——**兩者都由瀏覽器執行，但保護的目標不同：CORS 保護資料，CSP 保護頁面不被注入。**

**詳細解析**：**「CSP 是防禦 XSS 最有效的機制」值得強調**：它讓「即使有注入漏洞，注入的腳本也無法執行」——**因為它們不在允許的來源清單中**。**配合 nonce 或 hash，可以在允許必要的內聯腳本的同時封鎖注入的**。**而它的部署難點是「既有的頁面往往有大量的內聯腳本與樣式」**——**於是需要漸進地遷移**。**標準的做法是「先用 `Content-Security-Policy-Report-Only` 收集違規報告」**——**觀察一段時間，修掉那些違規，最後才切換成強制模式**。**這個「先觀察再強制」的推行模式，與前面提過的各種政策推行是完全一致的**——**而它是任何會阻擋既有行為的規則都應該遵循的順序。**

**面試回答方式**：給方向相反的區分（**CORS 由資源方授權讀取、CSP 由頁面方限制載入**）與各自保護的目標。核心加分點是**CSP 是防禦 XSS 最有效的機制**——**即使有注入漏洞，腳本也因不在允許清單中而無法執行**，並給出部署難點與**先 Report-Only 收集違規再強制**的標準做法。收在原則：**「先觀察再強制」是任何會阻擋既有行為的規則都應遵循的順序**。
