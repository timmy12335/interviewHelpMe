# 題目

NAT 在做什麼？為什麼內網的機器可以主動連外，外面卻連不進來？

## 核心答案

NAT 做的是**位址轉換**：內網機器使用私有位址，這些位址在公網上不可路由，所以出去的封包會被閘道器把來源改成公網 IP、並分配一個對外埠號，同時在**轉換表**中記下「這個對外埠對應內網的哪台機器哪個埠」；回應封包回來時再照表換回去。連得出去是因為**主動連線的那一刻就建立了轉換表項**，回應能照表找回內網主機。連不進來是因為**外部主動送來的封包沒有對應的表項**——閘道器不知道該轉給誰，只能丟棄。要讓外部連進來必須**事先建立映射**：靜態的埠轉發（把公網某個埠固定對應到內網某台機器）、或由內網主動先發出封包打通一條路徑（打洞）。這也解釋了為什麼 NAT 有**順帶的安全效果**——但它只是副作用，**不能當成防火牆**，真正的存取控制仍需要明確的規則。

## 詳細解析

**轉換表項會過期**：閘道器不可能無限保存映射，所以每個表項有**閒置逾時**（TCP 通常較長、UDP 通常很短，可能只有幾十秒）。這是長連線在 NAT 後方會「莫名斷掉」的主因——連線閒置太久，表項被清掉，之後的封包就找不到路。**應用層心跳**在這裡的作用不只是偵測斷線，也是**維持 NAT 表項存活**。這一點在行動網路上特別明顯，因為電信業者的 NAT 逾時往往更短。

**對稱型與錐型 NAT 影響穿透難度**：有些 NAT 對同一個內部來源、連往不同外部目標時會分配**不同的對外埠**（對稱型），這讓第三方難以預測映射，穿透變得困難；另一些則對同一個內部來源固定使用同一個對外埠（錐型），較容易穿透。這是點對點通訊（視訊通話、檔案傳輸）要用 STUN 探測自己的對外位址、必要時退回 TURN 中繼的原因——**當兩端都在對稱型 NAT 後方時，直連往往不可能，只能中繼**。

**埠號是共用資源**：一個公網 IP 後方掛著大量內網機器時，對外埠號（約六萬多）是**所有機器共用**的。連線數多時會耗盡，症狀是「某些人偶爾連不上」而非全面故障——非常難查，因為問題是機率性的且不在應用端。緩解方式是增加對外 IP、減少每台機器的連線數、或縮短連線追蹤的逾時。

**NAT 讓來源 IP 失去意義**：後端看到的來源 IP 是閘道器的，不是真實使用者的。依賴來源 IP 做限流、風控或存取控制時會誤傷——同一個 NAT 後方可能有成千上萬使用者，把他們當成同一個來源限流是不合理的。解法是靠應用層的識別（使用者 ID、裝置指紋）或由可信的代理層傳遞真實來源，但要記得**只信任自己代理寫入的部分**。

**IPv6 減少了對 NAT 的需求但沒有消除**：位址充足之後不必為了節省位址而做轉換，端到端可達性也恢復了。但這也意味著**內網機器變成可直接定址**，存取控制必須完全靠防火牆規則——原本 NAT 順帶提供的隔離效果消失了。所以遷移到 IPv6 時要特別檢查安全設定，不能假設「連不進來」還會自動成立。

## 面試回答方式

先講 NAT 的機制——**轉換位址加上維護轉換表**，並直接用它回答為什麼連得出去：**主動連線時建立了表項**，回應照表找回；外部主動送來的封包沒有表項所以被丟棄。接著給讓外部連進來的兩種方式（埠轉發、打洞）。加分點有三個：**轉換表項會因閒置而過期**，這是 NAT 後方長連線莫名斷線的主因，也是心跳的另一個作用；**對外埠號是整個網路共用的**，耗盡時症狀是偶發而非全面，極難查；以及 **NAT 不是防火牆**，它的隔離只是副作用，遷移到 IPv6 時這個副作用會消失，安全必須明確靠規則。

## 講稿

NAT 做的是位址轉換。內網機器用的是私有位址，在公網上不可路由，所以出去的封包會被閘道器把來源改成公網 IP、分配一個對外埠號，同時在轉換表裡記下這個對外埠對應內網的哪台機器哪個埠。回應回來的時候再照表換回去。

連得出去是因為主動連線的那一刻就建立了表項。連不進來是因為外部主動送來的封包沒有對應的表項，閘道器不知道要轉給誰，只能丟掉。

要讓外面連進來，就得事先建立映射，可以做靜態的埠轉發，或者由內網主動先發封包出去打通一條路徑。

有幾件實務上的事我會特別注意。第一，轉換表項有閒置逾時，UDP 的可能只有幾十秒。這是 NAT 後方長連線莫名斷掉的主因，所以心跳的作用不只是偵測斷線，也是維持表項存活。

第二，對外埠號是整個網路共用的。連線數多的時候會耗盡，症狀是某些人偶爾連不上，不是全面故障，非常難查。

第三，NAT 不是防火牆。它的隔離只是副作用，存取控制還是要靠明確的規則。

## 常見追問

### 為什麼點對點通訊需要 STUN 和 TURN？

**核心答案**：因為兩端都在 NAT 後方時，**彼此都不知道對方的公網位址與埠**，也無法主動連進去。**STUN** 讓一端向外部伺服器詢問「你看到我的來源位址與埠是什麼」，藉此得知自己的對外映射，再把它交換給對方嘗試直連（打洞）。**TURN** 則是在直連失敗時的退路——用一台中繼伺服器轉發雙方的流量，一定能通但成本高、延遲也增加。

**詳細解析**：直連能不能成功取決於**NAT 的類型**。若某一端是對稱型 NAT（對不同目標分配不同的對外埠），對方就無法預測要連往哪個埠，打洞失敗，只能退回中繼。實務上的通訊框架會**同時嘗試多條候選路徑**（本地位址、STUN 得到的位址、TURN 中繼）並選出最先連通的一條，這個過程稱為候選收集與連通性檢查。設計服務時要記得**TURN 的頻寬成本是實際的支出**——所有中繼流量都經過你的伺服器，所以要盡量提高直連成功率並監控中繼的比例。

**面試回答方式**：講清問題根源（雙方都不知道對方的對外映射且無法主動連入），再給 STUN 探測與 TURN 中繼的分工。加分點是說明對稱型 NAT 會讓打洞失敗只能中繼，以及 TURN 的頻寬是實際成本，要監控中繼比例。

### 服務看到的來源 IP 都一樣，怎麼做限流？

**核心答案**：**不要只依賴來源 IP**。NAT 後方可能有成千上萬使用者共用一個 IP，依它限流會把整個公司或整個社區的人一起誤傷。合理的做法是**分層**：對已登入的請求用**使用者 ID** 限流（最精確）；對未登入的用**裝置或工作階段層級的識別**；IP 層級的限制則設成很寬鬆的上限，只用來擋明顯的濫用，而不是日常的公平分配。

**詳細解析**：如果架構上有可信的代理層，可以由它把真實來源寫進標頭傳遞給後端，但**只能信任自己代理寫入的那一段**——這個標頭可以被客戶端偽造，所以要在邊界剝除外部傳來的值、只保留自己加上的。另外要注意**限流的維度應該對應到你想保護的資源**：保護資料庫就依查詢的成本限流、保護第三方 API 配額就依呼叫該 API 的次數限流，單純依請求數限流常常抓不到真正的壓力來源。這個「依資源而非依請求」的觀點在設計限流時很實用。

**面試回答方式**：明確反對只用 IP，給出分層方案（使用者 ID、裝置識別、寬鬆的 IP 上限）。加分點是說明代理傳遞真實來源時只能信任自己寫入的部分，以及限流維度應該對應到想保護的資源而非單純的請求數。

### IPv6 普及之後 NAT 就不需要了嗎？

**核心答案**：**位址層面不再需要，但相關需求並未消失**。IPv6 位址充足，不必為了節省而做轉換，端到端可達性也恢復。但原本由 NAT 順帶提供的**隔離效果消失了**——內網主機變成可直接定址，存取控制必須完全依靠防火牆規則。所以遷移時最大的風險是**沿用了「反正外面連不進來」的假設**，卻沒有補上對應的規則。

**詳細解析**：實務上 IPv6 環境仍會用到類似機制，例如**位址轉換用於策略而非節省**（統一出口位址便於稽核）、或在雙協定環境中做協定間的轉換。另一個實際問題是**雙協定堆疊的排查複雜度**——同一個名稱可能同時有 IPv4 與 IPv6 位址，客戶端優先選哪一個、某一條路徑通另一條不通時的回退行為，都會造成「有時候快有時候慢」或「偶爾連不上」的現象。排查時要明確指定協定版本分別測試，否則很容易誤判。這類問題在混合環境中相當常見。

**面試回答方式**：說明位址層面不再需要，但隔離效果消失、存取控制要明確靠規則，遷移最大的風險是沿用舊假設。加分點是提到雙協定環境的排查複雜度——優先選擇與回退行為造成的間歇性問題，排查要分別指定協定版本測試。
