# 題目

JSON 和 Protobuf 該怎麼選？序列化協定除了體積之外還要考慮什麼？

## 核心答案

選型有四個維度：**體積與效能**、**可讀性與除錯成本**、**跨語言支援**、以及**演進與相容性**。**JSON** 的優勢是人類可讀、無所不在、不需要編譯步驟，除錯時直接看得懂，對外的公開 API 幾乎是預設選擇；代價是**體積大**（欄位名重複出現在每一筆資料中）、**解析慢**、且**沒有型別保證**（數字精度、日期格式都靠約定）。**Protobuf** 的優勢是體積小、解析快、有明確的結構定義與型別，並且**內建了向前向後相容的規則**；代價是**不可讀**（除錯需要工具）、需要**編譯與散布結構定義**、跨團隊時的結構檔管理是額外的協調成本。所以常見的分工是：**對外的公開 API 用 JSON**（生態相容與可除錯性優先），**內部高頻的服務間呼叫用 Protobuf**（效能與契約明確性優先）。真正該優先考慮的其實是第四個維度——協定會演進，而相容性規則沒訂好的代價遠大於序列化效能。

## 詳細解析

**相容性規則比效能更重要**：服務不會同時升級，所以新舊版本必然共存。Protobuf 的設計把這件事放在核心——**欄位以編號識別而非名稱**，未知的欄位會被保留而非丟棄，因此新增欄位不影響舊版解析。但這建立在紀律上：**欄位編號絕不重用**、**不改變既有欄位的型別**、**移除欄位時保留編號**。違反這些規則的錯誤往往在灰度發布時才爆發，而且症狀是資料被錯誤解讀而非明確報錯，極難排查。JSON 沒有這套機制，相容性完全靠團隊約定，因此更需要明確的文件與測試。

**可讀性的價值被低估**：能直接看懂封包內容，在排查生產問題時的價值極高——抓包就能看出送了什麼、回了什麼。二進位協定需要有對應的結構定義與工具才能解讀，若當下手邊沒有正確版本的定義檔，排查會非常痛苦。所以在**除錯頻率高、效能不是瓶頸**的場景，JSON 的整體成本可能更低。

**體積的差距要看資料形態**：Protobuf 對**大量重複的結構化小物件**優勢最大（欄位名不重複、數值用變長編碼）。但如果內容主要是**長字串或二進位資料**，兩者差距不大——因為主體就是那些內容本身。所以「換成 Protobuf 就省很多」不一定成立，應該用實際資料量測。搭配壓縮之後差距會進一步縮小，因為 JSON 的重複欄位名很容易被壓縮掉。

**其他選項各有定位**：需要**零解析成本**（直接在緩衝區上讀取，不必反序列化整份資料）時有對應的格式，適合超低延遲或大檔案的隨機存取。需要**自描述且跨語言**、又要有結構演進能力時，資料處理生態中有另一套常用選擇。而 **MessagePack** 這類可以視為「二進位的 JSON」——保留了 JSON 的彈性與自描述，體積較小，但沒有 Protobuf 那樣嚴謹的結構契約。選擇時先問**要不要強契約**，這個問題通常就把候選縮到兩三個。

**最常被忽略的成本是工具鏈**：二進位協定需要編譯、需要在多個服務間散布結構定義、需要處理版本，這些在小團隊可能比省下的頻寬更貴。實務上的建議是先用 JSON 把事情做對，量測到序列化真的是瓶頸再換——而多數系統的瓶頸並不在這裡。

## 面試回答方式

用**四個維度**組織回答（體積效能、可讀性、跨語言、演進相容），並直接給常見分工：對外用 JSON、內部高頻用 Protobuf。核心主張要明確——真正該優先考慮的是相容性而非效能，因為服務不會同時升級、新舊版本必然共存。接著講 Protobuf 的相容性建立在紀律上（編號不重用、型別不改、移除時保留編號），違反的錯誤在灰度時才爆發且症狀是誤讀而非報錯。加分點有三個：**可讀性在排查時價值很高**，二進位協定沒有正確版本的定義檔就很難查；體積差距**要看資料形態**，長字串為主時差不多，加上壓縮後更接近；以及先用 JSON 做對、量測到瓶頸再換。

## 講稿

我會從四個維度看，體積跟效能、可讀性、跨語言支援、還有演進與相容性。

JSON 的優勢是人類可讀、到處都能用、不需要編譯步驟，除錯的時候直接看得懂。代價是體積大，因為欄位名在每一筆資料裡都重複，解析也比較慢，而且沒有型別保證。

Protobuf 的優勢是體積小、解析快、有明確的結構定義跟型別，還內建了相容性規則。代價是不可讀，除錯要有工具，而且要編譯跟散布結構定義。

所以常見的分工是對外的公開 API 用 JSON，內部高頻的服務呼叫用 Protobuf。

不過我認為真正該優先考慮的是相容性，不是效能。因為服務不會同時升級，新舊版本一定會共存。Protobuf 用編號而不是名稱識別欄位，未知欄位會保留，所以新增欄位不影響舊版。但這建立在紀律上，編號絕對不能重用、既有欄位的型別不能改。違反這些的錯誤通常在灰度發布才爆發，而且症狀是資料被誤讀不是明確報錯，很難查。

還有一點，體積差距要看資料形態。如果內容主要是長字串，兩者其實差不多，加上壓縮之後更接近。

## 常見追問

### Protobuf 的相容性規則具體是什麼？

**核心答案**：三條核心規則。**欄位編號絕不重用**——移除欄位後，該編號要保留在定義中標記為已棄用，若被新欄位重用，舊版程式會把新資料當成舊欄位解讀。**不改變既有欄位的型別**——某些型別在編碼上相容（例如幾種整數型別之間），但語意可能改變，最安全的做法是新增欄位而非修改。**新增欄位必須是可選的**並提供合理的預設值，讓舊版程式忽略它時仍能正常運作。

**詳細解析**：實務上還要注意兩點。**列舉型別的新值**——舊版程式碰到不認識的列舉值時的行為要事先確認，通常會落到預設值，這可能造成語意錯誤（例如新增的狀態被當成初始狀態處理），所以新增列舉值時要檢查所有依賴它做分支的邏輯。**必填欄位是陷阱**——早期版本支援必填，但它讓相容性極度脆弱（一旦某方缺少該欄位就完全解析失敗），後來的建議是**一律使用可選欄位**，必要性由應用層驗證。這兩點都是實際踩過才會知道的細節。

**面試回答方式**：給三條核心規則並各說明違反的後果，特別是編號重用會造成資料被誤讀。加分點是提到列舉新值在舊版會落到預設值可能造成語意錯誤，以及必填欄位讓相容性脆弱、應一律用可選並在應用層驗證。

### 什麼時候值得從 JSON 換成二進位協定？

**核心答案**：當量測到序列化或頻寬確實是瓶頸時。具體的訊號包括：CPU 剖析顯示序列化與反序列化佔了顯著比例、跨區或跨雲的頻寬成本可觀、或延遲要求嚴格到毫秒級而序列化佔了其中不小的部分。反過來，如果瓶頸在資料庫、在下游服務、或在網路往返次數上，換序列化協定完全不會有幫助——這是很常見的優化錯方向。

**詳細解析**：換之前值得先試幾個**成本低得多的改善**：**只回傳需要的欄位**（過度回傳是最常見的浪費）、**啟用壓縮**（對 JSON 特別有效，因為重複的欄位名容易被壓縮）、**減少往返次數**（在高延遲鏈路上往返數往往比酬載大小更決定體感）。這幾項通常能拿到大部分收益而不必付出工具鏈的成本。如果最終決定要換，**漸進遷移**的做法是先在內部高頻的關鍵路徑上採用，保留對外介面不變，這樣風險可控也能實測收益。

**面試回答方式**：給出明確的判準（量測到序列化或頻寬是瓶頸）與反例（瓶頸在別處時換了沒用）。重點是先試三個成本更低的改善：精簡欄位、開壓縮、減少往返。加分點是提出漸進遷移策略——先換內部關鍵路徑、保留對外介面。

### 為什麼有些系統的 API 回傳的數字要用字串？

**核心答案**：因為 JSON 的數字型別在不同語言與環境中的精度不一致。最典型的問題是 JavaScript 的數字是雙精度浮點數，超過安全整數範圍的大整數會失去精度——後端產生的雪花演算法 ID 或大額金額，傳到前端可能末幾位被改掉，而且完全不會報錯。用字串傳遞可以避免這個問題，由接收端自行決定怎麼解析。

**詳細解析**：同樣的問題也出現在**金額**上：用浮點數表示金額會有二進位無法精確表示十進位小數的問題，標準做法是**以最小單位的整數表示**（分而非元），或用字串傳遞由接收端以十進位型別解析。日期也是類似的情況——用字串加上明確的格式與時區，比用時間戳記整數更不容易出錯，因為後者的單位（秒或毫秒）常常被誤解。這幾個案例的共同教訓是：跨系統的資料交換要選擇語意明確、不依賴實作細節的表示方式，即使它看起來不夠精簡。這個原則比記住個別案例更有價值。

**面試回答方式**：核心是 JSON 數字精度在不同環境不一致，用大整數 ID 失去精度且不報錯這個例子最有力。加分點是延伸到金額用最小單位整數或字串、日期用明確格式與時區，並歸納出「跨系統交換要選語意明確、不依賴實作細節的表示」這個原則。
