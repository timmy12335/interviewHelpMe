# 題目

Session、Cookie 與 Token 是什麼關係？分散式系統中該怎麼選？

## 核心答案

三者不是同一個層次的東西。**Cookie 是傳輸機制**——瀏覽器自動在同網域的請求上附帶的一小段資料。**Session 是伺服器端的狀態**——伺服器保存使用者的登入資訊，客戶端只拿到一個識別碼（通常放在 Cookie 中）。**Token 是自包含的憑證**——資訊本身編碼在 token 裡並帶簽章，伺服器**不需要保存狀態**，驗簽通過就信任其中的內容。所以正確的對照不是「Session 對 Token」，而是「伺服器保存狀態」對「狀態放在客戶端手上」。分散式環境下的取捨很清楚：Session 需要**共用儲存**（例如集中式快取）或黏性路由，多一個依賴但**可以即時撤銷**；Token 天然無狀態、水平擴展容易，但**簽發後在到期前無法撤銷**，這是它最大的代價。實務上常見的折衷是**短效存取 token 加上長效更新 token**，把撤銷的粒度控制在可接受的範圍。

## 詳細解析

**Session 的分散式問題與三種解法**：多台伺服器時，使用者的請求可能落到沒有他 session 的機器上。解法一是**黏性路由**（負載平衡器把同一使用者導向同一台）——簡單，但那台掛掉時使用者就被登出，且擴縮容時分布不均。解法二是**集中式儲存**（Redis 這類）——最常見，代價是多一個必須高可用的依賴。解法三是**session 複製**（機器之間互相同步）——網路開銷隨機器數成長，只適合小叢集。實務上絕大多數選集中式儲存。

**Token 無法撤銷的實際後果**：使用者登出、帳號被停用、權限被調整，這些變更**不會反映在已簽發的 token 上**，它在到期前仍然有效。常見的緩解有三種：**縮短有效期**（幾分鐘到一小時），配合更新 token 換發新的；維護一份**黑名單**（但這等於又引入了狀態，抵銷了無狀態的優勢，不過黑名單通常遠小於全部 session）；或在 token 中放入一個**版本號**，使用者改密碼或權限時遞增伺服器端的版本，驗證時比對。要選哪一種取決於**多快需要生效**。

**存放位置決定安全性**：token 放在 `localStorage` 的話，**任何 XSS 都能完整竊取**它，攻擊者可以帶著它在別處冒充使用者。放在 `HttpOnly` Cookie 中則 JavaScript 讀不到，XSS 只能在受害者的瀏覽器中發請求而無法把憑證帶走，損害範圍小得多。代價是 Cookie 會被自動附帶，需要處理 CSRF——但 `SameSite` 加上 CSRF token 已經是成熟的組合。所以「用 token 就一定要放 localStorage」是常見的錯誤聯想，兩者是獨立的決定。

**Token 的內容不是機密**：常見的 token 格式只是**簽章**而非加密，其中的內容是可以被解碼閱讀的。所以**不要在 token 中放敏感資訊**（身分證號、內部 ID 的語意、權限細節），只放必要的識別與必要的宣告。簽章保證的是「內容沒被竄改」，不是「別人看不到」。

**選型的實務判準**：需要**即時撤銷**、有集中式快取可用、且主要是自家的網頁或 App，用 session 加 Cookie 較單純。需要跨服務、跨網域、或給第三方使用、且能接受短暫的撤銷延遲，用 token 較合適。**混用也很常見**——對外的 API 用 token，自家網頁用 session，兩者並不互斥。

## 面試回答方式

先糾正層次——Cookie 是傳輸機制、Session 是伺服器端狀態、Token 是自包含憑證，真正的對照是「狀態放伺服器」對「狀態放客戶端」。接著給分散式下的取捨：Session 需要共用儲存但**可即時撤銷**，Token 無狀態易擴展但**簽發後撤銷困難**。撤銷問題要主動展開三種緩解（縮短有效期、黑名單、版本號）並說明選擇取決於多快要生效。加分點有兩個：**「用 token 就要放 localStorage」是錯誤聯想**，token 一樣可以放 `HttpOnly` Cookie，且那樣更能抵抗 XSS；以及 token 的內容只是簽章不是加密，可以被解碼，所以不要放敏感資訊。

## 講稿

這三個不是同一個層次的東西。Cookie 是傳輸機制，瀏覽器自動在同網域的請求上帶著。Session 是伺服器端的狀態，客戶端只拿到一個識別碼。Token 是自包含的憑證，資訊編碼在裡面並帶簽章，伺服器不用保存狀態。

所以正確的對照不是 Session 對 Token，而是狀態放在伺服器，還是放在客戶端手上。

分散式環境的取捨很清楚。Session 需要共用儲存，多一個依賴，但好處是可以即時撤銷。Token 天然無狀態、擴展容易，但簽發之後在到期前撤銷不了，這是最大的代價。

撤銷問題有三種緩解。縮短有效期配合更新 token、維護黑名單、或者在 token 裡放版本號，改密碼的時候遞增。選哪一種看你需要多快生效。

我想澄清一個常見的錯誤聯想。用 token 不代表要放 localStorage。放那裡的話任何 XSS 都能完整偷走它，帶去別處冒充使用者。放在 HttpOnly 的 Cookie 裡，JavaScript 讀不到，損害小很多。這兩件事是獨立的決定。

還有 token 的內容只是簽章不是加密，可以被解碼看，所以不要在裡面放敏感資訊。

## 常見追問

### 更新 token 的機制要注意什麼？

**核心答案**：關鍵是存取 token 短效、更新 token 長效但只用於換發。存取 token 有效期設短（分鐘級）以縮小外洩的影響窗口；更新 token 有效期長但**只在換發端點使用**、且應該存放在最安全的位置（`HttpOnly` Cookie 或行動裝置的安全儲存）。換發時要考慮**輪替**——每次換發都作廢舊的更新 token 並發新的，這樣舊的若被竊取，重複使用會被偵測到。

**詳細解析**：偵測竊取的標準做法是：如果一個已經被輪替掉的更新 token 又被使用，代表它可能落入他人手中，此時應該**作廢該使用者的整個 token 家族**並要求重新登入。另一個實作上的難題是**並行換發**——多個請求同時發現存取 token 過期而一起去換發，若沒有處理會互相作廢。常見解法是在客戶端加上互斥控制（同時只允許一個換發流程，其他請求等待結果）。這個細節在單頁應用中特別容易踩到，因為多個元件可能同時發起請求。

**面試回答方式**：給出「存取短效、更新長效且只用於換發」的核心結構，並強調更新 token 要輪替。加分點是講重複使用已輪替 token 就作廢整個家族這個竊取偵測手法，以及並行換發需要客戶端互斥控制，這在單頁應用很常踩到。

### 單點登入的情況下，session 和 token 怎麼選？

**核心答案**：單點登入場景通常**傾向 token**，因為它要跨越多個系統甚至多個網域，而 Cookie 受同源限制、session 又依賴各系統共用儲存。標準的做法是由**身分提供者**簽發 token，各應用只需驗證簽章與宣告即可，不必彼此共用狀態——這正是 OAuth 2.0 與 OpenID Connect 這類協定的基礎。

**詳細解析**：實務上的關鍵細節有三個。**登出的傳播**——單點登出比單點登入難得多，因為要通知所有已登入的應用作廢工作階段，常見做法是身分提供者維護一個工作階段清單並在登出時通知各應用，但可靠性與時序都不容易處理。**時鐘偏差**——token 的有效期驗證依賴各系統的時鐘，偏差過大會造成「剛簽發就過期」這類難查的問題，所以通常會允許一個小的容忍窗口。**金鑰輪替**——簽章金鑰要能平滑更換，做法是同時發布多把公鑰並在 token 中標示用了哪一把，讓舊 token 在有效期內仍能驗證。這三點都是實際導入時會踩到的。

**面試回答方式**：說明單點登入偏向 token 的原因（跨系統跨網域、不必共用狀態）。加分點是給出三個實務難點：單點登出的傳播比登入難、時鐘偏差需要容忍窗口、以及金鑰輪替要能同時支援多把公鑰。

### 為什麼說 token 中不該放敏感資訊？

**核心答案**：因為常見的 token 格式只做**簽章而非加密**，其內容是任何拿到它的人都能解碼閱讀的。簽章保證的是「內容沒被竄改」與「來自可信的簽發者」，完全不保證機密性。所以放進身分證號、內部系統的識別碼語意、詳細的權限清單，等於把這些資訊交給每一個經手 token 的環節——包括客戶端本身、以及任何記錄了 token 的日誌。

**詳細解析**：實務上的原則是 token 只放**最小必要的識別與宣告**：使用者 ID、簽發與到期時間、必要的角色或範圍。細節資訊由服務在需要時自己去查。另外要注意**token 出現在日誌與 URL 中**的風險——絕不要把 token 放在查詢參數裡（會進入伺服器日誌、瀏覽器歷史、Referer 標頭），應該放在授權標頭或 Cookie 中；日誌系統也應該對授權標頭做遮罩。如果確實需要在 token 中攜帶機密資料，那就要用**加密的 token 格式**而不是只簽章的格式——但這通常代表設計上可以簡化，值得先回頭問為什麼需要這樣做。

**面試回答方式**：核心是簽章不等於加密，內容可被解碼。給出最小必要原則與服務自行查詢細節的做法。加分點是提醒 token 不能放查詢參數（日誌、歷史、Referer 會留痕）、日誌要遮罩授權標頭，以及真要攜帶機密就得用加密格式，但那通常暗示設計可以簡化。
