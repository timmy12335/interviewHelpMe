# 題目

二元搜尋樹的操作為什麼可能退化成 O(n)？紅黑樹和 AVL 樹的取捨在哪？

## 核心答案

BST 的所有操作都是 **O(h)**，h 是樹高——不是 O(log n)。只有在樹**平衡**時 h 才等於 log n；如果按遞增順序插入，每個新節點都掛在最右邊，樹會退化成一條鏈，h 變成 n，查找、插入、刪除全部變成 O(n)。這就是自平衡樹存在的理由。**AVL 樹**要求左右子樹高度差不超過 1，平衡得最嚴格，所以**查詢最快**，代價是插入刪除時旋轉次數多。**紅黑樹**只保證「最長路徑不超過最短路徑的兩倍」，平衡較鬆，插入刪除的旋轉次數少且有常數上界，所以在**寫入頻繁**的場景勝出——這就是為什麼 Java 的 `TreeMap`、C++ 的 `std::map`、以及 Linux 核心的排程器都選紅黑樹。BST 相對於雜湊表的價值在於**保有順序**：範圍查詢、找前驅後繼、找第 k 小、有序遍歷，這些雜湊表都做不到。

## 詳細解析

中序遍歷遞增是 BST 最好用的性質：驗證是否為 BST、找第 k 小、把 BST 轉成有序雙向串列、找兩個被交換的節點，全部靠這一條。找第 k 小時只要中序走到第 k 個就能提前結束，不必走完整棵樹。如果這個查詢很頻繁，可以在每個節點多存一個「左子樹節點數」，把找第 k 小降到 O(h)——這個增強型 BST 的想法值得知道，它是「在節點上維護額外統計量」這類設計的入門例子。

刪除是唯一有真正難度的操作：分三種情況。沒有孩子直接刪；只有一個孩子就用那個孩子頂替；**兩個孩子**時要用**中序後繼**（右子樹的最左節點）或中序前驅（左子樹的最右節點）來替換自己，然後遞迴刪掉那個替身。用後繼替換之所以正確，是因為它是「所有大於當前值的節點裡最小的」，換上來之後 BST 性質仍然成立。而後繼節點必定**沒有左孩子**，所以刪它只會落到前兩種簡單情況，遞迴不會無限展開。

退化的實際觸發條件比想像中常見：按主鍵遞增插入、按時間戳插入、匯入已排序的資料，全都會讓樸素 BST 退化成鏈。這也是為什麼實務上幾乎沒有人用未平衡的 BST——標準庫提供的一律是自平衡版本。面試中如果被問「你會自己實作 BST 嗎」，正確的答案通常是「不會，我用標準庫的平衡樹」，並說明理由。

**AVL 與紅黑的取捨要用數字講**：AVL 的高度上限約 1.44 log n，紅黑樹約 2 log n，所以查詢紅黑樹稍慢。但插入時 AVL 可能需要 O(log n) 次旋轉，紅黑樹**最多旋轉 2 次**（刪除最多 3 次），其餘靠變色完成，變色比旋轉便宜得多。所以規律是：讀多寫少選 AVL，讀寫都多選紅黑樹。實務上通用容器都選紅黑樹，因為它在兩端都不差；資料庫索引則兩者都不用，改用 B+ 樹，因為磁碟的瓶頸是 I/O 次數，需要的是**極矮的多路樹**而不是二元樹。

**BST 與雜湊表的選型**：只做等值查找，雜湊表平均 O(1) 勝出。一旦需要**順序性**——範圍查詢（找出介於 a 和 b 之間的所有鍵）、前驅後繼、最小值最大值、有序輸出——就必須用平衡樹。這條界線在系統設計裡也成立：Redis 的有序集合用跳表（功能上等價於平衡樹）而不是雜湊表，正是因為要支援按分數排名與範圍查詢。

## 面試回答方式

第一句話就把重點定死——BST 的操作是 O(h) 不是 O(log n)，並舉遞增插入退化成鏈的例子，這句話立刻把「背過」和「懂」分開。接著講自平衡：AVL 平衡嚴格、查詢快、旋轉多；紅黑樹平衡鬆、插入刪除旋轉次數有常數上界，所以通用容器都選它。刪除操作主動說出兩個孩子時用中序後繼替換，並解釋後繼必定沒有左孩子所以遞迴會終止。加分點有兩個：一是點出資料庫索引用 B+ 樹而不是二元樹，因為瓶頸是磁碟 I/O 次數；二是講清楚 BST 相對雜湊表的價值在順序性。

## 講稿

二元搜尋樹的操作是 O(h)，h 是樹高，不是 log n。這個區別很重要。

如果我按照遞增的順序插入，每個新節點都掛在最右邊，整棵樹就退化成一條鏈，查找變成線性。而按主鍵遞增插入、按時間戳插入，這在實務上非常常見，所以樸素的 BST 幾乎沒有人直接用。

自平衡樹就是為了這件事存在的。AVL 要求左右子樹高度差不超過一，平衡最嚴格，所以查詢最快，但插入刪除的旋轉次數多。紅黑樹只保證最長路徑不超過最短路徑的兩倍，平衡比較鬆，換來的是插入最多旋轉兩次，其他靠變色處理，而變色比旋轉便宜很多。所以規律是讀多寫少選 AVL，讀寫都多選紅黑樹。實務上像 TreeMap 這種通用容器都用紅黑樹。

刪除是唯一有難度的操作。兩個孩子的時候要用中序後繼來替換，也就是右子樹最左邊那個節點。它必定沒有左孩子，所以刪掉它只會落到簡單情況。

最後我想補一句，資料庫索引兩個都不用，是用 B 加樹，因為那裡的瓶頸是磁碟的存取次數。

## 常見追問

### 為什麼資料庫索引用 B+ 樹而不是紅黑樹？

**核心答案**：因為瓶頸完全不同。記憶體中的樹在意的是**比較次數**，磁碟上的索引在意的是**I/O 次數**——一次磁碟讀取的成本是記憶體存取的數萬倍，而且一次至少讀一整頁（通常 4KB 或 16KB）。紅黑樹是二元的，高度約 2 log n，一千萬筆資料要走約 46 層，每層一次 I/O 就是災難。B+ 樹是**多路**的，一個節點裝上百個鍵，一千萬筆只要三到四層，配合根節點常駐記憶體，實際磁碟讀取只有一兩次。

**詳細解析**：B+ 樹還有兩個為磁碟量身打造的設計。第一，**資料只放在葉節點**，內部節點只存鍵與指標，所以內部節點能塞更多鍵、樹更矮。第二，**葉節點之間用鏈結串起來**，範圍查詢只要定位到起點再沿著葉節點鏈掃描，不必回到上層——這正是 `WHERE age BETWEEN 20 AND 30` 這類查詢快的原因。相對地，B 樹（非 B+）在內部節點也存資料，單點查詢可能提早命中，但範圍查詢要反覆上下移動，所以資料庫索引普遍選 B+。

**面試回答方式**：直接點出瓶頸不同——記憶體看比較次數、磁碟看 I/O 次數，並用「一千萬筆資料紅黑樹 46 層對上 B+ 樹三四層」這個對比說明。接著補 B+ 樹的兩個設計：資料只在葉節點讓樹更矮、葉節點串鏈讓範圍查詢高效。加分點是說明 B 樹與 B+ 樹的差別以及為什麼資料庫選後者。

### 跳表和平衡樹功能相同，Redis 為什麼選跳表？

**核心答案**：主要是**實作複雜度與可維護性**。跳表用機率決定節點層數，插入刪除不需要旋轉或變色，程式碼短得多、也更容易正確；平衡樹的刪除邏輯出了名地繁瑣。其次跳表的**範圍查詢更直接**——最底層本身就是有序鏈結串列，定位後往後走即可，不需要中序遍歷的堆疊。兩者的期望複雜度都是 O(log n)。

**詳細解析**：Redis 作者曾說明選擇理由包括：實作簡單、範圍查詢方便、以及**記憶體使用可調**（每個節點的層數由機率參數決定，可以在空間與速度之間調整）。跳表的代價是它只有**期望**的 O(log n) 而非最壞保證，理論上可能因為隨機性退化，但機率極低。另外跳表的節點包含多個前進指標，在資料量大時記憶體開銷可能高於紅黑樹。在併發場景下跳表也比較有優勢——因為修改是局部的、不需要旋轉整棵子樹，比較容易做無鎖或細粒度鎖的實作，Java 的 `ConcurrentSkipListMap` 就是這個原因。

**面試回答方式**：把主因放在實作複雜度與範圍查詢的直接性，這兩點最實際。接著誠實指出代價：只有期望複雜度、沒有最壞保證。加分點是提到併發場景下跳表更容易做細粒度鎖，並舉 `ConcurrentSkipListMap` 為例。

### BST 中找第 k 小的元素，有沒有比中序遍歷更快的做法？

**核心答案**：有，在節點上**額外維護「左子樹的節點數」**，就能把單次查詢從 O(k) 降到 **O(h)**。查找時比較 k 與左子樹大小：k 小於等於左子樹大小就往左走，等於左子樹大小加一就是當前節點，否則往右走並把 k 減去「左子樹大小加一」。這是「在節點上維護統計量」的典型應用。

**詳細解析**：代價是插入與刪除時要沿路更新這個計數，所以是用寫入成本換讀取成本。判斷值不值得的準則很簡單：**查詢頻率高就值得**。如果只查一次，中序遍歷提前終止已經是 O(k)，通常夠用。這個增強思路可以推廣——在節點上維護子樹的和、最大值、或其他可合併的統計量，就能支援對應的區間查詢，這正是線段樹的核心思想。面試中被問到這題，除了給出解法，能點出「這是用寫換讀」與「線段樹是同一個思路的一般化」會顯得層次更高。

**面試回答方式**：先給做法（維護左子樹節點數，查找時三向比較），並說明複雜度從 O(k) 降到 O(h)。接著誠實講代價：插入刪除要沿路更新，是用寫換讀，查詢頻繁才划算。加分點是把它一般化成「節點上維護可合併統計量」，並連結到線段樹。
