# 題目

拓撲排序解決什麼問題？Kahn 演算法為什麼能順便偵測環？

## 核心答案

拓撲排序處理的是「有依賴關係的任務要按什麼順序做」——課程的先修關係、建置系統的編譯順序、套件安裝的依賴解析、資料庫遷移的執行順序，全都是同一個問題。它的輸出是一個線性順序，使得每條有向邊的起點都排在終點之前，前提是圖必須是**有向無環圖**。**Kahn 演算法**的做法是：先算出每個節點的入度，把所有入度為 0 的節點放進佇列（它們沒有任何前置依賴），每次取出一個加入結果、並把它指向的節點入度各減 1，減到 0 就入佇列。它能順便偵測環，是因為環上的節點入度永遠不會歸零——環裡每個節點都被環中另一個節點指著，所以彼此永遠在等對方。因此只要最後輸出的節點數少於總節點數，剩下的就在環裡。這個「順便得到」的性質讓 Kahn 成為依賴解析的預設選擇：一次跑完既給出順序，又告訴你有沒有循環依賴。

## 詳細解析

**Kahn 與 DFS 兩種實作的取捨**：DFS 版是在後序位置把節點推入堆疊、最後反轉，程式碼更短。但 Kahn 版有三個實務優勢：一是**環偵測是自然副產品**，DFS 版要額外維護三種狀態；二是**能回報是哪些節點在環裡**（剩下沒輸出的就是），對錯誤訊息很有價值；三是**容易加上優先權**——把佇列換成優先佇列，就能在多個合法順序中選出字典序最小的那個，這是很常見的追加需求。所以面試中預設講 Kahn，並主動說明為什麼。

**拓撲順序通常不唯一**：任何時刻只要有多個入度為 0 的節點，選誰都合法。這意味著題目若要求「唯一的順序」，判斷方式是每一步佇列中是否恰好只有一個節點——只要某一步有兩個以上選擇，順序就不唯一。這是「是否存在唯一拓撲序」這類題的標準解法，也常被用來判斷「這些偏序關係是否足以確定完整排序」。

**有向無環圖上的動態規劃**：DAG 的價值不只在排序。一旦有了拓撲順序，就等於有了**無後效性的處理順序**，可以在上面做動態規劃——最長路徑（在一般圖上是 NP 難，在 DAG 上是線性）、路徑計數、關鍵路徑分析（專案管理的 CPM 就是這個）。做法是按拓撲順序遍歷，每個節點用它所有前驅的結果更新自己。這個「拓撲序保證前驅都算完了」的性質，正是 DAG 上動態規劃能成立的原因。

**實務中的循環依賴處理**：真實系統偵測到環之後，通常不能只回報錯誤了事。建置工具會列出**具體的環路徑**幫助排查（用 DFS 記錄遞迴堆疊可以還原路徑，Kahn 只能給出「哪些節點在環裡」的集合）。Spring 的循環依賴則採取另一條路——用三級快取提前暴露未完成的 Bean，讓部分形態的循環依賴仍能注入成功。所以「偵測到環怎麼辦」的答案分兩種：開發期依賴用報錯，執行期物件圖用打破循環的機制。

**入度計算與圖的建構順序**：實作上常見的錯誤是**邊的方向搞反**。題目說「修課程 B 之前要先修 A」，那麼邊應該是 A 指向 B（A 是前置），B 的入度加 1。方向反了會得到完全顛倒的答案，而且測資對稱時不一定測得出來。習慣做法是動筆前先用一句話寫死方向約定：「邊從前置指向後續」。

## 面試回答方式

先講它解決的是什麼問題並舉兩個真實例子（建置順序、套件依賴），讓題目落地。接著給 Kahn 的流程，重點放在**為什麼能偵測環**——環上節點互相等待、入度永不歸零，所以輸出數量少於總數就代表有環。主動比較 DFS 版並說明你為什麼選 Kahn（環偵測是副產品、能報出環中節點、容易加優先權）。加分點有三個：拓撲序不唯一以及如何判斷唯一性、DAG 上做動態規劃求最長路徑、以及動筆前先寫死邊的方向約定避免反向。

## 講稿

拓撲排序處理的是有依賴關係的任務要按什麼順序做。像課程先修、專案的編譯順序、套件的依賴解析，都是同一個問題。

我會用 Kahn 演算法。先算每個節點的入度，把入度為零的節點放進佇列，因為它們沒有任何前置依賴。每次取出一個放進結果，然後把它指向的節點入度各減一，減到零就入佇列。

它能順便偵測環，原因很直觀。環上的每個節點都被環裡另一個節點指著，所以它們的入度永遠不會歸零，大家彼此在等對方。所以只要最後輸出的節點數少於總數，剩下沒輸出的就是在環裡。

我選 Kahn 而不是 DFS 版本，有三個理由。環偵測是自然的副產品，不用另外維護狀態。它可以回報是哪些節點在環裡，錯誤訊息比較有用。還有把佇列換成優先佇列，就能在多個合法順序裡選字典序最小的，這是很常見的追加需求。

另外提醒一個實作上的坑，邊的方向很容易搞反。題目說修 B 之前要先修 A，那邊是 A 指向 B，B 的入度加一。我會在動筆前先把方向約定寫死。

## 常見追問

### 怎麼判斷拓撲順序是否唯一？

**核心答案**：在 Kahn 的每一輪檢查佇列大小——只要任何一輪的佇列中有兩個以上入度為 0 的節點，順序就不唯一，因為此時選誰都合法。反過來，若每一輪佇列裡都恰好只有一個節點，那麼順序唯一。這個檢查幾乎不增加成本，只是在迴圈裡多一個判斷。

**詳細解析**：這個性質有個實際的用途叫**序列重建**——給定一堆偏序關係，判斷它們是否足以唯一確定一個完整排序。經典場景是「根據多筆兩兩比較的結果判斷能否排出唯一名次」。另一個等價的說法是：拓撲序唯一等於這張 DAG 上存在一條**哈密頓路徑**（依序把每個節點串起來的路徑），也就是相鄰的每一對之間都有直接的邊。面試中能給出「每輪佇列恰好一個」這個簡潔判準，再補一句它等價於存在哈密頓路徑，會顯得理解得比較透。

**面試回答方式**：直接給判準（每一輪佇列大小是否為 1），並說明成本幾乎為零。接著舉序列重建這個應用讓它落地。加分點是點出它等價於 DAG 上存在哈密頓路徑這個更本質的說法。

### 偵測到循環依賴之後，實務上要怎麼處理？

**核心答案**：分兩種情況。**開發期的依賴**（模組相依、套件相依、資料庫遷移）應該直接報錯並列出環的具體路徑，因為循環依賴是設計問題，該由開發者拆開——常見手法是抽出共用介面、引入事件解耦、或合併成同一個模組。**執行期的物件圖**（例如依賴注入的 Bean）則可以用機制打破循環，Spring 用三級快取提前暴露尚未完成初始化的物件參考，讓部分形態的循環注入仍能成功。

**詳細解析**：兩者的差別在於**能不能延後**。物件的循環引用可以靠「先給你一個還沒填滿的參考、之後再補齊」來化解，因為欄位的賦值可以延後；但模組的編譯順序或資料庫遷移的執行順序沒有這種餘地，A 沒編譯完就是不能編譯 B。要注意 Spring 的三級快取也有極限——建構子注入的循環依賴無法解決，因為建構完成前根本拿不到參考，這個界線常被追問。錯誤訊息的品質也值得提：只說「偵測到循環依賴」對使用者幫助有限，列出 `A → B → C → A` 這樣的完整路徑才是好的工程實踐，而這需要用 DFS 記錄遞迴堆疊，Kahn 給不出來。

**面試回答方式**：先把兩種情況分開——開發期報錯拆解、執行期用機制打破。用「能不能延後」解釋差別的根源。加分點是點出 Spring 建構子注入的循環無法用三級快取解決，以及要輸出完整環路徑需要 DFS 而非 Kahn。

### DAG 上的最長路徑為什麼是線性的，一般圖上卻是 NP 難？

**核心答案**：因為 DAG 有**拓撲順序**，它保證處理某個節點時**所有前驅都已經算完**，所以可以直接用「所有前驅的最長路徑取最大值再加一」遞推，一趟 O(V + E) 就結束。一般圖有環，你無法定義一個「先算完誰」的順序，而且環的存在讓「最長路徑」必須加上「不能重複經過節點」的限制，這個限制把問題變成尋找最長簡單路徑，是 NP 難的（它包含哈密頓路徑問題）。

**詳細解析**：這說明了無環這個性質本身就是巨大的結構優勢。同樣的對比出現在最短路徑上——DAG 上的最短路徑可以用拓撲序線性解決，甚至能處理負權邊（Bellman-Ford 需要 O(V·E)，Dijkstra 根本不能處理負權）。這也是為什麼很多系統會刻意把問題建模成 DAG：任務排程、資料流水線、建置系統、區塊鏈的部分結構，都是在用「禁止循環」換取可計算性。面試中能點出「DAG 上很多 NP 難問題變成多項式時間」這個一般性觀察，比只回答這一題更有深度。

**面試回答方式**：核心是拓撲序提供了「前驅都已算完」的保證，讓遞推成立。接著解釋一般圖的困難來自環讓「不重複經過節點」變成必要限制，而那等價於哈密頓路徑。加分點是延伸到 DAG 上的最短路徑也能處理負權邊，並指出系統設計中刻意建模成 DAG 就是在買可計算性。
