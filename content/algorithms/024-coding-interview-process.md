# 題目

拿到一道 coding 題之後，動筆前你會先做什麼？整場四十五分鐘要怎麼分配？

## 核心答案

流程分四段，時間大約是 **5、10、20、10** 分鐘。**第一段澄清**：複述題目確認理解、問輸入範圍（資料量決定可接受的複雜度）、問邊界（空輸入、重複元素、負數、超大值）、問輸出要求（要不要排序、要不要去重、多解時回傳哪一個）。**第二段講方案**：先給一個一定正確的暴力解並說出它的複雜度，再說明瓶頸在哪、要用什麼手法優化，**得到面試官點頭之後才動手**。**第三段實作**：邊寫邊講你在做什麼，變數命名清楚，先寫主體結構、細節可以先用一個有意義的函式名佔位。**第四段驗證**：用一個小例子**手動走一遍**程式碼，特別測邊界（空、單一元素、全相同、最大值），發現問題就當場修。全程最重要的一件事是**不要沉默**——面試官評的是你的思考過程，沉默五分鐘等於交白卷，即使你腦中正在高速運轉。

## 詳細解析

澄清階段最有價值的三個問題：一是**資料規模**——n 是一千還是十億，直接決定 O(n²) 能不能接受，也常常是面試官暗示解法的地方。二是**能不能修改輸入**——決定你能不能用原地排序或原地標記省下空間。三是**特殊輸入怎麼處理**——空陣列回傳什麼、找不到答案回傳什麼、有多組解要回傳哪一組。這三個問題花不到一分鐘，但能避免寫完才發現方向錯誤。反過來，問太多細枝末節的問題會顯得抓不到重點，控制在三到五個為宜。

**先給暴力解不是示弱，是策略**：它讓你在任何時間點都有一個**可交付的答案**，也讓面試官看到你的基準點在哪。更重要的是，優化通常是從暴力解的瓶頸推導出來的——「這裡每次都要在陣列裡找一個值，所以我把它換成雜湊表」比憑空想出最優解更能展示思路。切忌一開始就宣稱要用某個高階資料結構卻說不清為什麼。

**「先講再寫」能省下最多時間**：如果你的方案有根本性錯誤，面試官在你講的時候就會提示，這時改方向只需要一分鐘；如果你埋頭寫了十五分鐘才被指出方向錯了，時間已經回不來。所以口頭方案得到確認之前不要寫程式碼，這是最重要的一條紀律。而確認的方式很簡單，說完之後問一句「這個方向你覺得可以嗎，還是有我沒考慮到的地方」。

**寫程式時的溝通節奏**：不要逐行念出程式碼（「我現在寫一個 for 迴圈」），那是雜訊。要講的是**意圖**——「這個迴圈負責把每個元素的出現次數統計起來，因為後面判斷重複時要用」。遇到卡住時也要出聲：「我在想這裡的邊界要用小於還是小於等於，讓我用一個兩個元素的例子確認一下」——把思考過程外化，面試官才有機會幫你，而且這本身就是他們在評估的協作能力。

驗證階段常被跳過，但那是最容易加分的十分鐘：主動說「我來走一個例子確認」，選一個能覆蓋主要分支的小輸入，逐行追蹤變數。特別要測的邊界包括：空輸入、單一元素、全部相同、最小與最大值、以及會觸發你程式中每個分支的輸入。自己找出 bug 遠比被面試官指出好——前者顯示嚴謹，後者顯示疏忽。時間不夠時至少要口頭說明「如果還有時間，我會測這幾個邊界」。

## 面試回答方式

把流程講成四段並給時間分配，這本身就展示了你有方法。澄清階段主動說出你會問的三個問題（資料規模、能否修改輸入、特殊輸入），並解釋為什麼這三個最關鍵。強調「**先講方案、得到確認才動手**」這條紀律，並說明理由是方向錯了在口頭階段改只花一分鐘。實作時的溝通原則要講清楚——講意圖不是講語法。驗證階段要強調自己找出 bug 比被指出好。最後主動說出最重要的一條：不要沉默，因為面試官評的是思考過程。

## 講稿

我的流程分四段，時間大概是五分鐘澄清、十分鐘講方案、二十分鐘實作、十分鐘驗證。

澄清階段我會問三個問題。第一是資料規模，n 是一千還是十億，這直接決定平方解能不能接受，而且面試官常常在這裡暗示解法。第二是能不能修改輸入，這決定我能不能原地排序或原地標記。第三是特殊輸入怎麼處理，空陣列回傳什麼、有多組解要回哪一組。

接下來我會先講一個一定正確的暴力解，說出它的複雜度，再說瓶頸在哪、我打算怎麼優化。講完我會問一句這個方向可以嗎。這一步很關鍵，如果方向錯了，在口頭階段改只要一分鐘，埋頭寫十五分鐘才被指出來就回不來了。

實作的時候我會邊寫邊講，但講的是意圖不是語法。不會說我現在寫一個迴圈，而會說這個迴圈在統計出現次數，因為後面判斷重複要用。

最後留時間走一個例子驗證，重點測空輸入、單一元素、全部相同這些邊界。自己找出問題比被面試官指出來好很多。

全程最重要的一件事是不要沉默。

## 常見追問

### 想不出解法時該怎麼辦？

**核心答案**：把思考過程說出來，並主動降級目標。先明確講「我目前想到的是暴力解，複雜度是這樣，我知道它不夠好但我先確保有一個正確的版本」，然後把暴力解寫出來。接著說出你觀察到的瓶頸與嘗試的方向：「這裡的重複計算讓我想到記憶化，但我還沒想清楚狀態怎麼定」——這給了面試官一個具體的介入點，他們通常會給提示，而**接得住提示本身就是評分項**。

**詳細解析**：面試官心裡多半有一組分層的提示，你表達得越具體，他們給的提示就越精準。最糟的做法有兩種：一是沉默地卡住，對方不知道你卡在哪、無從幫起；二是不斷換方向，講一半就跳到另一個思路，讓人覺得你沒有系統性。比較好的做法是**縮小問題**——「我先試試看陣列只有正數的情況會怎麼解，再推廣到有負數」，或者「我先用最直接的方式處理，再看能不能優化」。這種降級策略在真實工作中也是正確的做法，所以它傳達的信號是好的。

**面試回答方式**：核心是「說出來並降級」——先交付暴力解、講出瓶頸與嘗試方向，給面試官具體的介入點。點出兩個最糟的反面做法：沉默、以及不斷跳換方向。加分點是提到縮小問題（先解特例再推廣）這個具體技巧，並說明它在真實工作中也是對的。

### 面試官指出你的程式碼有 bug，該怎麼反應？

**核心答案**：先確認再修，不要急著辯解也不要立刻亂改。標準的回應是「讓我用一個例子確認一下」，然後用具體輸入走一遍那一段——如果真的有錯，你會清楚看到錯在哪、修起來也準確；如果其實沒錯，你可以用這個例子說明為什麼，而且態度是討論而非防衛。最忌諱的是聽到質疑就慌張地把程式碼改成另一個版本，那通常會引入新的錯誤。

**詳細解析**：面試官指出問題有時是**真的發現 bug**，有時是**在測你對自己程式碼的理解**。用具體例子驗證這個動作同時應付兩種情況，所以是最安全的反應。修正時要說明你在改什麼、為什麼——「這裡的邊界應該是小於等於，因為長度為 2 時我需要包含最後一個元素」，讓對方跟得上。另外如果 bug 是真的且不只一處，優先修**會導致錯誤結果**的，而不是風格問題。整場下來，能冷靜處理被挑戰、用證據討論而不是防衛，往往比程式碼本身留下更深的印象。

**面試回答方式**：給出標準反應——用具體例子確認，再決定修還是解釋。點出這個做法同時應付「真的有 bug」與「在測你懂不懂」兩種情況。加分點是強調修正時要說明理由讓對方跟得上，以及冷靜面對挑戰本身就是評分項。

### 時間不夠，程式碼還沒寫完怎麼辦？

**核心答案**：優先把主結構寫完整，細節用有意義的函式名佔位。例如主流程寫完，把「檢查是否為有效座標」抽成一個 `isValid(x, y)` 的呼叫並口頭說明它的實作只是幾個範圍比較。這樣面試官看得到完整的解題邏輯，而缺的只是機械性的細節。反過來，把前三分之一寫得很完整、後面完全空白，對方無法判斷你會不會解這題。

**詳細解析**：這個策略反映的是**先骨架後細節**的工程習慣，本身就是正面信號。時間快到時主動說明「主邏輯已經完成，剩下的是這兩個輔助函式，內容是這樣」，並補一句「如果還有時間我會測這幾個邊界」，把未完成的部分講清楚，比讓對方自己猜好得多。事前的預防更重要——如果你在實作進行到一半時發現時間吃緊，就該主動簡化方案，例如放棄空間優化先讓功能正確，並說明這個取捨。**主動管理時間並說明取捨**，是資深職缺面試中很看重的一點。

**面試回答方式**：給出策略——主結構優先、細節用有意義的函式名佔位，並解釋為什麼這比寫完前三分之一好。接著講收尾的說法：說明剩下什麼、以及還有時間會測哪些邊界。加分點是提到中途發現時間吃緊要主動簡化方案並說明取捨，展現時間管理意識。
