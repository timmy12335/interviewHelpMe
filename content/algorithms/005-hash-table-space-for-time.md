# 題目

什麼時候該把一層迴圈換成雜湊表？這個「空間換時間」在什麼情況下不划算？

## 核心答案

雜湊表把「**在集合裡找某個東西**」從 O(n) 降到平均 O(1)，所以只要迴圈的內層在做**查找、計數或去重**，就有機會把它換掉。最典型的轉換是兩層迴圈找配對：外層固定 a、內層找 `target - a`，把內層換成雜湊表就從 O(n²) 變成 O(n)。判斷訊號有三個：「有沒有出現過」「出現幾次」「有沒有重複」。不划算的情況也很明確：**資料量小**時雜湊的常數（計算 hash、處理碰撞、指標跳躍）可能輸給直接掃陣列；**鍵是連續小整數**時用陣列當桶更快也更省；**需要順序性**（找最接近的、找前 k 大、範圍查詢）時雜湊表完全幫不上忙，得換成排序、堆積或平衡樹。空間代價也要說清楚：O(n) 額外記憶體換 O(n) 時間，在記憶體受限或資料流極大時要考慮改用**布隆過濾器**這種機率型結構。

## 詳細解析

**「一趟就好」比「先建表再查」更好**：兩數之和的標準解不是先把全部元素放進表、再掃一次，而是**邊掃邊查、邊查邊放**——對每個元素先問「`target - x` 在表裡嗎」，不在就把 x 放進去。這樣做有兩個好處：只掃一趟，而且天然避免了「自己配自己」的錯誤（因為查的時候 x 還沒放進去）。先建表的版本必須額外判斷索引不相同，多一個容易寫錯的條件。

**平均 O(1) 的前提與最壞情況**：雜湊表的 O(1) 建立在**鍵均勻散布**的假設上。當大量鍵碰撞時，鏈結法會退化成 O(n)。Java 8 之後 HashMap 在單一桶超過門檻時會轉成紅黑樹，把最壞情況拉回 O(log n)。面試時如果你只說「雜湊是 O(1)」而不提最壞情況，遇到追問就會卡住；主動說「平均 O(1)、最壞 O(n)，實務上靠隨機化或樹化桶處理」會顯得扎實。

自訂物件當鍵一定要同時實作 equals 與 hashCode：這是把演算法題搬到真實程式碼時最常見的 bug。兩個邏輯相等的物件如果 hashCode 不同，會被放進不同的桶，查找時永遠找不到，表現出來就是「明明 put 進去了卻 get 不到」。相反地，hashCode 相同但 equals 為 false 只會造成碰撞、效能下降，不會產生錯誤結果。另外一個致命問題是**把可變物件當鍵**：物件放進表之後又修改了參與 hashCode 計算的欄位，它就會留在錯的桶裡，永遠找不回來。

**計數用什麼結構**：字元或小整數當鍵時，長度 26 或 128 的陣列比雜湊表快得多，而且沒有裝箱成本。這在字串題（字母異位詞、字元頻率）非常常見，能主動選陣列而不是無腦用 HashMap，是實務感的展現。反過來，鍵是稀疏的大整數或字串時，陣列會浪費大量空間，這時雜湊表才是對的。

**雜湊表解不了的問題**：只要題目涉及**順序或範圍**——找第 k 大、找最接近的值、輸出排序結果、查詢某區間內有幾個元素——雜湊表就無能為力，因為它刻意打散了順序。這時要換成堆積（前 k 大）、有序集合或平衡樹（範圍查詢）、排序加二分（靜態資料）。面試官常用「那如果要輸出排序結果呢」來測這條界線。

## 面試回答方式

先給判斷訊號，而不是直接說「用 HashMap」——內層迴圈在做查找、計數或去重，就是可以換掉的信號。用兩數之和示範時，強調**一趟邊查邊放**的寫法，並解釋它為什麼比先建表更不容易錯。接著主動說出複雜度的真相：平均 O(1)、最壞 O(n)，並提樹化桶。不划算的三種情況要主動列：資料量小、鍵是連續小整數（改用陣列）、需要順序性（改用堆積或有序結構）。加分點是提到自訂物件當鍵要同時實作 equals 與 hashCode，以及可變物件當鍵會找不回來。

## 講稿

我判斷要不要用雜湊表，看的是內層迴圈在做什麼。如果它在做查找、計數，或者去重，那這一層通常就可以換掉。

以兩數之和為例，暴力解是外層固定一個數、內層找另一個。內層做的就是查找，換成雜湊表就從平方降到線性。這裡我習慣寫成一趟的版本，邊掃邊查、邊查邊放。對每個元素先問補數在不在表裡，不在才把自己放進去。這樣不只少掃一趟，還天然避開自己配自己的問題，因為查的時候它還沒進表。

不過我會補一句，雜湊是平均常數，不是保證常數。鍵大量碰撞的時候會退化，Java 八以後是靠把過長的桶轉成紅黑樹，把最壞情況拉回對數。

也有不該用的情況。資料量很小的時候，雜湊的常數可能輸給直接掃。鍵是連續小整數的時候，開一個陣列當桶更快也更省。最重要的是，只要題目牽涉到順序或範圍，像找第 k 大或者範圍查詢，雜湊就完全幫不上忙，那要換成堆積或者有序的結構。

## 常見追問

### 兩數之和如果要求輸出所有不重複的配對，還適合用雜湊表嗎？

**核心答案**：不太適合，**排序加對撞指針**更自然。雜湊表可以找出配對，但去重需要額外處理：同一個值出現多次時會產生重複的配對，你得再用一個集合把結果去重，或是先對每個配對排序內部順序再比對。排序之後用雙指針，重複元素相鄰，跳過重複只要一個 `while` 迴圈，而且輸出天然有序。

**詳細解析**：這題的價值在於展示**選型會隨需求變化**。只問「存不存在」時雜湊表是 O(n)，最快；問「所有不重複的組合」時排序的 O(n log n) 完全被後續的去重成本抵銷掉，而且程式碼更短。再往上推到三數之和、四數之和，排序加雙指針幾乎是唯一乾淨的做法，因為去重必須在多層都做。另一個變化是「配對計數」——如果只要算有幾對而不用輸出，雜湊表計數仍是最好的，用組合數處理重複值即可。所以真正的答案是：**看輸出要求，不是看題目名稱**。

**面試回答方式**：明確表態「輸出所有不重複配對時我會改用排序加雙指針」，理由是去重成本。接著點出只問存在性或只要計數時雜湊仍然最好，讓對方看到你是依需求選型而不是背固定解法。加分點是提到三數之和以上排序幾乎是唯一乾淨解。

### 雜湊表在最壞情況退化成 O(n)，這在實務上會被利用嗎？

**核心答案**：會，這是真實存在的**雜湊碰撞阻斷攻擊**。攻擊者針對已知的雜湊函式構造大量會落進同一個桶的鍵，送進伺服器的參數解析或 JSON 反序列化，讓原本 O(n) 的處理變成 O(n²)，用很小的流量就打滿 CPU。多個語言的執行環境都因此發過安全更新。

**詳細解析**：防禦手段有兩層。第一層是**隨機化雜湊種子**——每個行程啟動時用隨機種子擾動雜湊函式，攻擊者無法離線預先算出碰撞鍵。第二層是**改變退化後的結構**，Java 8 的 HashMap 把長鏈轉成紅黑樹，即使碰撞成功也只退化到 O(log n)。應用層還可以限制請求參數數量。這題在後端面試中比在演算法面試中更常出現，能答出來會讓面試官覺得你不只是刷題，還理解資料結構在真實系統裡的風險面。

**面試回答方式**：先確認這是真實攻擊而不是理論風險，簡述攻擊方式（構造碰撞鍵讓解析從線性變平方）。接著給兩層防禦：隨機化種子與樹化桶。加分點是補上應用層限制參數數量，展現分層防禦的思路。

### 什麼時候該用布隆過濾器取代雜湊表？

**核心答案**：當資料量大到放不下、而且可以接受偽陽性時。布隆過濾器只用一個位元陣列和幾個雜湊函式，空間遠小於存下所有鍵，代價是查詢結果只有兩種可靠程度：回答「不存在」一定正確，回答「存在」可能是誤判。所以它適合當**前置過濾器**——先擋掉絕大多數必定不存在的查詢，剩下的少數再去查真正的資料來源。

**詳細解析**：最典型的用途是擋快取穿透：大量查詢不存在的鍵會直接打穿快取打到資料庫，先用布隆過濾器擋掉，誤判的少數請求才落到資料庫，成本可以接受。設計時要權衡位元陣列大小、雜湊函式個數與偽陽性率三者，偽陽性率隨資料量成長而上升，所以容量要按預估上限規劃。標準布隆過濾器**不支援刪除**（清掉某個位元會影響其他鍵），需要刪除時要換成計數型布隆過濾器，代價是空間變大。

**面試回答方式**：先講清楚它的不對稱保證——說不存在一定對，說存在可能錯，這決定了它只能當前置過濾器。接著給快取穿透這個具體場景。加分點是提到三個參數的權衡、偽陽性率會隨資料量上升，以及標準版不支援刪除。
