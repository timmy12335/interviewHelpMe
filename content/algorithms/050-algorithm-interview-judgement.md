# 題目

演算法面試到底在考什麼？有限的時間該怎麼分配？

## 核心答案

它考的是四件事，而它們的權重和多數人的想像不同。

一、能不能把想法變成正確的程式碼——這是基礎，也是最常見的淘汰原因；想法對但寫出來有 bug 且找不出來，結果和不會一樣。

二、遇到陌生問題時有沒有系統的方法——而不是「見過就會、沒見過就卡住」；這是面試官真正想預測的，因為工作中的問題總是陌生的。

**三、能不能清楚地溝通思路**——在寫之前說明計畫、在寫的過程中解釋、在寫完後主動測試；沉默地寫出正確答案的評價，低於邊解釋邊寫出同樣答案。

**四、對複雜度與取捨的判斷**——知道自己的解是什麼複雜度、知道規模對應什麼要求、知道什麼時候夠好了。

所以有限的時間應該這樣分配：寫程式碼的熟練度（能無錯地寫出常見模式）> 系統的解題方法 > 覆蓋更多的題型——**而多數人的分配恰好相反。**

## 詳細解析

**「寫不對」比「想不到」淘汰更多人**：這在面試官的回饋中反覆出現——候選人說出了正確的思路，但在實作時出現差一錯誤、邊界處理錯誤、或者變數用錯，而在四十五分鐘內沒能除錯出來。改善它的方法是「限時手寫」而非「在 IDE 裡刷題」——因為 IDE 的自動補全與即時錯誤提示，掩蓋了你真正的熟練度；每週幾次在純文字編輯器裡限時寫出常見模式（二分的邊界、快慢指標、DFS 的框架），效果遠好於多刷二十題。

**「系統的方法可以被明確學習」**：用規模反推複雜度、盤點題目給的條件、識別暴力解中的重複、按清單嘗試優化方向——這些都是具體的、可以練習的步驟，而不是玄妙的「感覺」；而它們的價值在於「即使沒見過這一題也有辦法推進」。**這正是面試官想確認的能力**——因為在真實的工作中，沒有人會給你一道刷過的題。

「溝通不是額外的加分而是評分的一部分」：面試官需要知道「你為什麼這樣做」才能評估你——如果你沉默地寫完，他只能看到結果；而說出「我先考慮用雜湊表，但這裡需要保持順序所以我改用……」讓他看到了判斷的過程。具體的習慣是：寫之前用三十秒說明計畫、卡住時說出你在考慮什麼、寫完後主動說「讓我用這個例子驗證一遍」。

**「準備的邊際效益遞減得很快」**：前五十題帶來的提升遠大於後兩百題——因為常見的模式就那些，而重複只是在鞏固；當你發現「新題目大多是已知模式的組合」時，繼續刷題的收益就低於練習溝通與實作熟練度了。認出這個轉折點並調整策略，是準備效率的關鍵。

## 面試回答方式

先給四件被考察的事並指出它們的權重和多數人的想像不同，然後給出時間分配的結論。加分點有四個：**「寫不對」比「想不到」淘汰更多人**，而改善它要限時手寫而非在 IDE 裡刷題；**系統的方法可以被明確學習**而非玄妙的感覺，它的價值在於「沒見過也有辦法推進」；溝通是評分的一部分而非額外加分，並給出具體的習慣；以及**準備的邊際效益遞減得很快**，認出轉折點並調整策略是效率的關鍵。

## 講稿

我認為它考四件事，而權重跟多數人的想像不同。

第一是能不能把想法變成正確的程式碼。這是最常見的淘汰原因。想法對但寫出來有 bug 又找不出來，結果跟不會一樣。而改善這一點的方法是限時手寫，不是在 IDE 裡刷題。因為自動補全跟即時錯誤提示，掩蓋了你真正的熟練度。

第二是遇到陌生問題時有沒有系統的方法。用規模反推複雜度、盤點題目給的條件、識別暴力解中的重複，這些都是具體可以練習的步驟，不是玄妙的感覺。而它們的價值是即使沒見過這一題也有辦法推進。

第三是溝通。這不是額外加分而是評分的一部分。沉默地寫出正確答案，評價會低於邊解釋邊寫出同樣的答案。

第四是對複雜度跟取捨的判斷。

所以我的時間分配是，寫程式碼的熟練度優先，然後是系統的解題方法，最後才是覆蓋更多題型。多數人的分配恰好相反。

## 常見追問

### 該不該背模板？

**核心答案**：該背少數幾個，但要理解到能推導。二分的邊界、快慢指標、單調堆疊、DFS 與 BFS 的框架、並查集——**這五六個應該熟到不假思索**；但「熟」的標準是「能解釋每一行為什麼是這樣」而非「能默寫出來」。因為變體幾乎必然出現，而只會默寫的人在變體前會直接失效。

**詳細解析**：「二分的邊界」是最能區分這兩種熟練的例子：能默寫 `while (l < r)` 版本的人很多——但被問「為什麼這裡是 `l < r` 而不是 `l <= r`，如果改成 `<=` 需要改哪裡」時就答不出來；而理解「迴圈不變式是什麼、退出時 l 和 r 的關係是什麼」的人，能在任何變體（找左邊界、右邊界、插入位置）中推導出正確的寫法。檢驗自己屬於哪一種的方法很簡單：把模板換一種寫法（左閉右開改成左閉右閉），看你能不能正確地調整所有的邊界；如果不能，那你是在背而非在懂。這個自我檢驗的方法，比做更多題更快地暴露出真實的水準。

**面試回答方式**：給明確的答案（該背少數幾個但要理解到能推導）與具體的清單，並定義「熟」的標準（**能解釋每一行為什麼**而非能默寫）。核心加分點是用**二分的邊界**展示這兩種熟練的差別，並給出自我檢驗的方法：把左閉右開改成左閉右閉，看能不能正確調整所有邊界。收在價值：這個檢驗比做更多題更快地暴露真實水準。

### 面試時卡住了怎麼辦？

**核心答案**：把卡住的狀態說出來，而不是沉默。「我現在想到的是 O(n²) 的做法，我在想能不能用某種結構避免內層的掃描，但還沒想到合適的」——這讓面試官知道你在哪裡、也給了他提示你的機會；而沉默三分鐘會被解讀成「毫無頭緒」。

**詳細解析**：「面試官通常願意給提示，但他需要知道給什麼」：一個說出思路的候選人，面試官可以精準地提示（「你說想避免內層掃描，那如果資料是有序的呢」）——而一個沉默的候選人，面試官只能問「你在想什麼」，那個問題本身就消耗了時間與信心。**而接受提示並不減分**——面試評估的是「在協作中解決問題的能力」而非「獨自閉關的能力」；真實的工作正是在不斷地交流中推進的。我見過的一個常見誤解是「問問題或接受提示等於承認不會」——恰恰相反，在合理的時機提問是資深工程師的標誌；而硬撐到時間結束才是真正的減分。

**面試回答方式**：給具體的做法（**把卡住的狀態說出來**）並示範那句話。核心加分點是面試官通常願意給提示但他需要知道給什麼，並對比說出思路與沉默兩種情況下面試官能做什麼。收在觀念澄清：接受提示並不減分，面試評估的是協作中解決問題的能力；「提問等於承認不會」是常見的誤解，而硬撐到時間結束才是真正的減分。

### 如果最後沒寫完呢？

**核心答案**：沒寫完不一定是失敗，取決於你走到了哪裡。如果思路完整、複雜度分析清楚、程式碼寫了大半只差細節——多數面試官會給出正面的評價；而如果連方向都沒有，那即使寫滿了螢幕也不會通過。所以在時間不夠時，優先確保「思路被完整地表達」而非「程式碼被寫滿」。

**詳細解析**：「在最後五分鐘應該做什麼」是一個值得提前想好的問題：如果快沒時間了——停下來說「讓我總結一下：這個解法是 O(n log n)，剩下的部分是處理邊界情況，具體來說是……」；這比繼續埋頭寫更有價值，因為它讓面試官確認了你知道剩下該做什麼。而更重要的是「不要在最後五分鐘推翻重來」——除非你確定當前的方向是錯的；一個完成度百分之八十的正確方向，遠好過兩個各完成百分之三十的方向。這個「在時間壓力下管理範圍」的能力，本身就是工程中被高度重視的——而面試恰好是一個觀察它的好場合。

**面試回答方式**：給明確的判斷（**取決於你走到哪裡**）並對比兩種情況，給出優先順序（思路被完整表達 > 程式碼被寫滿）。核心加分點是**在最後五分鐘應該做什麼**——停下來總結解法與剩下要做的事，比埋頭寫更有價值，以及**不要在最後五分鐘推翻重來**（八成完成的正確方向遠好過兩個三成的方向）。收在洞察：「在時間壓力下管理範圍」本身就是工程中被高度重視的能力，而面試恰好是觀察它的好場合。
