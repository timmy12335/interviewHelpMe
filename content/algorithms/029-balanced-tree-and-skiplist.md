# 題目

有序集合有哪些實作？紅黑樹、跳表、B 樹各適合什麼？

## 核心答案

**它們解決同一個問題（維持有序並支援 O(log n) 的插入、刪除、查找），差別在「常數、實作複雜度、與對硬體的適應」。**

**紅黑樹**——**嚴格的平衡保證（最壞 O(log n)）、記憶體緊湊**；**代價是「旋轉的邏輯複雜」，而併發下需要鎖住整棵樹的一部分**。**Java 的 `TreeMap`、C++ 的 `std::map` 都是它。**

**跳表**——**用多層的鏈結串列加隨機化達成期望 O(log n)**；**優點是「實作簡單得多」與「併發友善」（只需要局部的指標修改）**；**代價是期望而非保證，且指標的空間開銷較大**。**Redis 的有序集合用它。**

**B 樹與 B+ 樹**——**每個節點存很多鍵**；**專為「一次 IO 讀一整塊」的儲存設計**；**於是樹高極低（幾層就能容納數億筆）**。**資料庫索引用它。**

**選擇的核心是「資料在記憶體還是在磁碟」與「併發的需求」。**

## 詳細解析

**「跳表為什麼併發友善」是它被 Redis 選用的主要理由之一**：平衡樹的旋轉會改動多個節點的父子關係——**於是併發修改需要鎖住較大的範圍**；**而跳表的插入只需要修改幾個指標，且那些修改可以用 CAS 完成**。**這讓「無鎖的並發跳表」成為可行的（Java 的 `ConcurrentSkipListMap` 正是如此）而「無鎖的紅黑樹」極其困難**。**另一個實務理由是「範圍查詢」**：**跳表的最底層就是一個有序鏈結串列，於是「取出某個範圍內的所有元素」只是沿著它走**——**而在樹上需要中序遍歷，程式碼複雜得多。**

**「B 樹的設計動機完全來自硬體」**：磁碟一次讀取一個區塊（例如 4KB 或 16KB）——**而一次隨機讀取的成本遠高於在記憶體中比較幾百次**；**於是「把節點做大以減少樹高」是明顯的優化**。**一個階數為 100 的 B 樹，三層就能容納一百萬筆**——**於是查找只需要三次磁碟讀取**。**這正是「演算法的最優設計取決於成本模型」的一個典型例子**——**在記憶體中二元樹更好，而在磁碟上多路樹更好。**

**「B+ 樹相對於 B 樹的改進」也值得說**：所有的資料只在葉節點——**內部節點只存鍵，於是能容納更多的鍵、樹高更低**；**而葉節點用鏈結串列串起來，讓範圍掃描極其高效**。**這兩點正是資料庫索引需要的（大量的範圍查詢與排序輸出）**——**所以資料庫用 B+ 而非 B 樹。**

**「跳表的隨機化」是它簡單的來源**：每個節點的層數由拋硬幣決定——**於是不需要任何再平衡的邏輯**；**而機率保證了「期望的高度是 O(log n)」**。**這是一個「用隨機化換取實作簡單」的漂亮例子**——**代價是最壞情況理論上可能很差（雖然機率極低）。**

## 面試回答方式

先指出**它們解決同一個問題，差別在常數、實作複雜度與對硬體的適應**，再給三者的特性與代表性的使用者，並給選擇的核心（**資料在記憶體還是磁碟、併發需求**）。加分點有四個：**跳表為什麼併發友善**——**插入只需修改幾個指標且可以用 CAS，而無鎖的紅黑樹極其困難**，**加上範圍查詢天然簡單**；**B 樹的設計動機完全來自硬體**——**一次隨機讀取遠貴於記憶體中比較幾百次，所以把節點做大**，**是「最優設計取決於成本模型」的典型**；**B+ 相對於 B 的改進**（資料只在葉節點、葉節點串成鏈結）**正是資料庫需要的**；以及**跳表的隨機化是它簡單的來源**——**用隨機化換取實作簡單**。

## 講稿

它們解決同一個問題，維持有序並支援對數時間的插入刪除查找，差別在常數、實作複雜度、跟對硬體的適應。

紅黑樹有嚴格的平衡保證、記憶體緊湊，但旋轉的邏輯複雜而且併發下需要鎖住較大的範圍。跳表用多層鏈結串列加隨機化達成期望的對數複雜度，實作簡單得多而且併發友善。B 樹每個節點存很多鍵，專為一次讀取一整塊的儲存設計。

跳表為什麼併發友善值得說。平衡樹的旋轉會改動多個節點的父子關係，而跳表的插入只需要修改幾個指標，那些修改可以用比較並交換完成。這讓無鎖的並發跳表成為可行的，而無鎖的紅黑樹極其困難。另外跳表的最底層就是一個有序鏈結串列，範圍查詢只是沿著它走。

而 B 樹的設計動機完全來自硬體。磁碟一次讀一個區塊，一次隨機讀取的成本遠高於在記憶體中比較幾百次，於是把節點做大以減少樹高是明顯的優化。一個階數一百的樹，三層就能容納一百萬筆。這是演算法的最優設計取決於成本模型的典型例子。

## 常見追問

### 為什麼 Java 的 HashMap 在衝突多時轉成紅黑樹？

**核心答案**：**為了防止「最壞情況退化成 O(n)」**。當大量的鍵雜湊到同一個桶——**鏈結串列的查找變成線性**；**而在惡意構造的輸入下（雜湊碰撞攻擊），這會讓 HashMap 的操作從 O(1) 退化到 O(n)，成為一個 DoS 的向量**。**轉成紅黑樹之後，最壞是 O(log n)。**

**詳細解析**：**「這個改動的主要動機是安全而非效能」值得指出**：在正常的雜湊分布下，一個桶裡有八個以上元素的機率極低（Java 的註解中給出了泊松分布的計算）——**所以這個轉換在正常情況下幾乎不會發生**；**它是為了「不正常的情況」而存在的**。**這是一個「為最壞情況付出少量的複雜度」的設計決定**——**而它的觸發閾值（8 個元素且桶陣列長度至少 64）正是基於那個機率計算的**。**知道這個背景能解釋一個常見的困惑：「為什麼是 8 而不是其他數字」**——**答案是「在正常分布下達到 8 的機率約千萬分之一，所以那幾乎一定意味著雜湊函數有問題或者是惡意輸入」。**

**面試回答方式**：給動機（**防止最壞退化成 O(n)，尤其是雜湊碰撞攻擊**）與改善後的複雜度。核心加分點是指出**主要動機是安全而非效能**——**正常分布下一個桶有八個以上元素的機率極低，所以這個轉換幾乎不會發生，它是為不正常的情況而存在**。收在閾值的來歷：**8 這個數字基於泊松分布的計算，達到它的機率約千萬分之一**，**所以那幾乎一定意味著雜湊函數有問題或是惡意輸入**。

### 有序集合的常見操作有哪些特殊需求？

**核心答案**：**四個超出普通 Map 的操作**。**範圍查詢**（`subMap`、`ZRANGEBYSCORE`）——**取出某個區間內的所有元素**。**前驅與後繼**（`floorKey`、`ceilingKey`）——**找最接近的**。**排名查詢**（第 k 小、某個元素的排名）——**需要在節點中維護子樹大小**。**以及有序遍歷。**

**詳細解析**：**「排名查詢需要額外的維護」是一個容易被忽略的細節**：普通的平衡樹能做 `contains` 與 `range` 但不能 O(log n) 地回答「這個元素排第幾」——**除非每個節點額外記錄「以它為根的子樹有多少個節點」**；**而那個資訊在每次插入與刪除時都要更新（沿著路徑）**。**帶了這個資訊的樹被稱為「順序統計樹」**——**而 Redis 的跳表正是為了支援 `ZRANK` 而在每個指標上記錄了「跨越了多少個節點」**。**這個「為了支援某個查詢而在資料結構中維護額外資訊」的模式很普遍**——**而它的代價是每次修改都要維護那個資訊，所以應該只在真的需要時加。**

**面試回答方式**：給四個超出普通 Map 的操作。核心加分點是**排名查詢需要額外的維護**——**每個節點要記錄子樹大小且每次修改都要沿路徑更新**，**帶了這個資訊的樹叫順序統計樹，而 Redis 的跳表為了支援排名在每個指標上記錄了跨越數**。收在模式與代價：**「為了支援某個查詢而維護額外資訊」很普遍**，**而代價是每次修改都要維護，所以應該只在真的需要時加**。

### 面試中會被要求實作這些嗎？

**核心答案**：**紅黑樹幾乎不會（它的旋轉邏輯太繁瑣，不適合白板）**；**而跳表偶爾會（它的實作簡單得多，而且能考察隨機化與指標操作）**。**更常見的是「說明它們的差異與選擇的理由」**——**而那正是這一題的重點**。**如果真的被要求實作，跳表的插入與查找在二十分鐘內是可行的。**

**詳細解析**：**「知道什麼會被問、什麼不會」本身就是有用的準備資訊**：面試官問資料結構時的意圖通常是「你理解它的性質與取捨嗎」而非「你能不能背出實作」——**所以準備的重心應該在「什麼時候用、為什麼、代價是什麼」**。**而少數需要實作的（跳表、Trie、LRU、堆積）都有一個共同特徵：實作在二三十行內且能考察清晰的思路**——**所以準備時可以按這個標準篩選**。**至於紅黑樹與 B 樹**：**理解它們的性質與動機是必要的，而背誦旋轉的四種情況價值很低**——**因為那個知識既不會被問，實務中也不會自己實作。**

**面試回答方式**：直接回答哪些會被問哪些不會，並指出**更常見的是說明差異與選擇的理由**。核心加分點是提煉準備的原則：**面試官的意圖是「你理解它的性質與取捨嗎」而非「能不能背出實作」**，**所以重心應該在「什麼時候用、為什麼、代價是什麼」**。收在篩選的標準：**少數需要實作的都在二三十行內且能考察清晰思路**，**而背誦紅黑樹的旋轉情況價值很低，因為既不會被問實務中也不會自己實作**。
