# 題目

布隆過濾器與 HyperLogLog 各解決什麼？它們的代價是什麼？

## 核心答案

它們的共同思路是「放棄精確，換取數量級的空間節省」——而關鍵是「那個不精確在你的場景中可以接受」。

**布隆過濾器**——**回答「這個元素在集合中嗎」**；用 k 個雜湊函數把元素映射到一個位元陣列。保證「說不在就一定不在」（無偽陰性）而「說在可能不在」（有偽陽性）；空間可能只有精確集合的百分之一。

**HyperLogLog**——**估計「有多少個不同的元素」**；利用「雜湊值的前導零位數的分布」來推估基數。用約 12KB 就能估計數十億的基數，誤差約 0.81%。

而選擇的核心問題是「哪一種錯誤可以接受」：布隆過濾器的偽陽性意味著「可能多做一次確認」（所以適合當前置的過濾器）；而 HyperLogLog 的誤差意味著「統計數字不精確」（所以適合報表而非計費）。

## 詳細解析

「無偽陰性」是布隆過濾器最有價值的性質：它保證「說不在就一定不在」——於是它適合作為「昂貴查詢的前置過濾」：先問布隆過濾器，說不在就直接返回（省下一次磁碟或網路存取），說在才真的去查。這正是它在資料庫（LSM tree 的 SSTable 查找）與快取（防止快取穿透）中的用法。而如果反過來（有偽陰性而無偽陽性），它就完全沒用了——因為「說不在」不可信意味著每次都要去查。

**「偽陽性率可以被計算與調整」**：它取決於位元陣列的大小 m、元素數 n、與雜湊函數個數 k——**而最優的 k 約為 `(m/n) × ln2`**；於是可以根據「能接受多少偽陽性」反推需要多少空間。這個「先定精確度再算資源」的設計方式，比「隨便給一個大小」可靠得多——而它也讓權衡變成一個明確的計算而非猜測。

「布隆過濾器不能刪除」是它最主要的限制：把某個位元設回 0 可能影響其他元素——於是刪除會引入偽陰性，破壞它的核心保證。解法是「計數布隆過濾器」（每個位置用一個計數器而非一個位元）——**代價是空間增加幾倍**；或者「定期重建」（在能重建的場景中最簡單）。

**「HyperLogLog 的原理很優雅」**：如果雜湊值是均勻分布的——那麼「看到一個有 k 個前導零的雜湊值」大約意味著看過 2^k 個不同的元素；於是記錄「最大的前導零數」就能估計基數。而為了降低方差，它用多個桶（用雜湊值的前幾位決定桶）並取調和平均。理解這個原理比記住它的用法有價值——因為它展示了「用機率的性質做估計」這個在大數據處理中反覆出現的思路。

## 面試回答方式

先給共同思路（放棄精確換取數量級的空間節省）與兩者各自的功能與保證，並給選擇的核心問題（**哪一種錯誤可以接受**）。加分點有四個：無偽陰性是布隆過濾器最有價值的性質——它適合作為昂貴查詢的前置過濾，而反過來就完全沒用；**偽陽性率可以被計算與調整**——讓權衡變成明確的計算而非猜測；**不能刪除是主要限制**與兩個解法；以及**HyperLogLog 的原理**（前導零的分布加多桶取調和平均），它展示了「用機率的性質做估計」這個在大數據處理中反覆出現的思路。

## 講稿

它們的共同思路是放棄精確、換取數量級的空間節省，而關鍵是那個不精確在你的場景中可以接受。

布隆過濾器回答這個元素在集合中嗎。它保證說不在就一定不在，而說在可能不在。空間可能只有精確集合的百分之一。

無偽陰性是它最有價值的性質。因為它讓布隆過濾器能作為昂貴查詢的前置過濾。先問它，說不在就直接返回省下一次磁碟或網路存取，說在才真的去查。這正是它在資料庫的檔案查找與防止快取穿透中的用法。而如果反過來，有偽陰性而無偽陽性，它就完全沒用了，因為說不在不可信意味著每次都要去查。

它最主要的限制是不能刪除，因為把某個位元設回零可能影響其他元素，於是會引入偽陰性破壞核心保證。解法是用計數器取代位元，或者定期重建。

而基數估計的原理很優雅。如果雜湊值均勻分布，那看到一個有 k 個前導零的值，大約意味著看過二的 k 次方個不同元素。於是記錄最大的前導零數就能估計。為了降低方差再用多個桶取調和平均。

## 常見追問

### 還有哪些機率型結構值得知道？

**核心答案**：**三個常見的**。**Count-Min Sketch**——**估計「每個元素出現了幾次」**；用於找 heavy hitter（出現最頻繁的元素）與近似的頻率統計；**它會高估但不會低估**。**Cuckoo Filter**——布隆過濾器的替代，支援刪除且在低偽陽性率下空間更省。**以及 t-digest / HdrHistogram**——估計分位數（p99 這類）而不需要保存所有的樣本。

**詳細解析**：「t-digest 解決的問題在監控中極其常見」：計算 p99 的精確做法是保存所有的樣本並排序——而在每秒幾十萬個請求的系統中那不可行；於是需要一個「用固定的空間估計分位數」的結構。它的核心思路是「在分布的兩端用密集的桶、在中間用稀疏的桶」——因為 p99、p999 這些極端的分位數需要精確，而中位數附近的精確度需求低。這個「按需求分配精確度」的設計非常巧妙，而它也解釋了為什麼「監控系統的 p99 是估計值」——知道這一點能避免對那個數字的過度解讀。另一個實務要點是「分位數不能被平均」：十台機器各自的 p99 取平均不等於整體的 p99——必須用能合併的結構（t-digest 支援合併）才能正確地聚合。

**面試回答方式**：給三個結構與各自的功能。核心加分點是展開 **t-digest 解決的監控問題**——精確計算 p99 要保存所有樣本，而它的思路是「兩端用密集的桶、中間用稀疏的桶」，按需求分配精確度。收在一個重要的實務認知：**分位數不能被平均**——十台機器的 p99 取平均不等於整體的 p99，必須用能合併的結構。

### 布隆過濾器在快取穿透中怎麼用？

**核心答案**：把「所有存在的 key」放進布隆過濾器——**查詢時先問它**；說「不在」就直接返回空（不查資料庫），說「在」才去查快取與資料庫。於是「查詢大量不存在的 key」這種攻擊或異常，被擋在資料庫之前。

**詳細解析**：「偽陽性在這個場景中的影響是可接受的」：一個實際不存在的 key 被判斷成「可能在」——於是多查了一次資料庫，那正是沒有布隆過濾器時的行為；所以偽陽性的代價只是「這個優化對那部分請求無效」而非造成錯誤。這個「錯誤的方向是安全的」正是它適用的關鍵。**而實務上的難點是「維護」**：新增 key 時要加進過濾器（簡單），而刪除 key 時無法從中移除（需要定期重建）；所以它適合「key 的集合增長為主、刪除很少」的場景。**另一個要點是「初始化」**：要把現有的所有 key 掃進去，而在資料量大時那本身是一個成本——所以通常在建立時一次完成並之後增量維護。

**面試回答方式**：給用法（把存在的 key 放進去、說不在就直接返回）。核心加分點是說明偽陽性在這個場景中的影響可接受——它的代價只是「這個優化對那部分請求無效」而非造成錯誤，這個「錯誤的方向是安全的」正是它適用的關鍵。收在實務難點：刪除無法移除所以需要定期重建，適合增長為主的場景；而初始化要掃描現有的所有 key，在資料量大時本身是一個成本。

### 什麼時候不該用這些結構？

**核心答案**：**當「不精確」的後果不可接受時**。計費、對帳、法規要求的統計——這些需要精確的數字，而一個 0.8% 的誤差可能是完全不能接受的。另外，在資料量小到「精確的結構也放得下」時——用一個普通的 Set 或 HashMap 更簡單也更精確，沒有理由引入近似。

**詳細解析**：「先問資料量」是使用這些結構前的必要步驟：布隆過濾器省的是空間——而如果你只有一萬個元素，一個 HashSet 也只佔幾百 KB；那個「省下的空間」完全沒有價值，而你付出了偽陽性與實作複雜度的代價。所以這些結構的門檻是「精確的做法確實放不下或者太慢」——**通常意味著百萬級以上**。而在雲端的環境中，這個門檻可能更高（因為記憶體便宜）——所以「這個優化在我的規模下值得嗎」應該被實際計算而非假設。這個「先確認問題存在再引入解法」的順序，在演算法選擇與系統設計中同樣適用。

**面試回答方式**：給不該用的兩種情況（不精確的後果不可接受、資料量小到精確的也放得下）。核心加分點是**先問資料量是必要的步驟**——一萬個元素用 HashSet 只佔幾百 KB，那個「省下的空間」完全沒有價值而你付出了偽陽性與複雜度的代價。收在門檻與原則：通常要百萬級以上，而雲端環境中門檻可能更高，所以「這個優化在我的規模下值得嗎」應該被實際計算。
