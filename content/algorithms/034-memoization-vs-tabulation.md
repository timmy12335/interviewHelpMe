# 題目

記憶化搜尋（自頂向下）與遞推（自底向上）該怎麼選？

## 核心答案

兩者計算的是同一件事，差別在「誰驅動計算的順序」。

**記憶化搜尋**——從目標狀態出發，需要什麼子問題就遞迴去求，求過的存起來。優點是「狀態轉移的方向與思考的方向一致」（先想「要算 f(n) 需要什麼」）、「只計算真正用到的狀態」（在狀態空間稀疏時省很多）、以及「不需要想清楚計算的順序」。

**遞推**——從基礎狀態出發，按一個明確的順序填表。優點是「沒有遞迴的堆疊開銷與深度限制」、「常數更小」、以及「更容易做空間優化」（滾動陣列）。

實務的建議是「先用記憶化寫出正確的解，再視需要改成遞推」——因為前者更容易寫對（只要定義好狀態與轉移），而後者需要額外想清楚遍歷的順序。

## 詳細解析

「遍歷順序」正是遞推最容易出錯的地方：一個狀態依賴的所有子狀態必須先被計算——而那個順序在多維的 DP 中可能不直觀（例如完全背包的物品與容量的迴圈順序、以及區間 DP 必須按區間長度遞增）。而記憶化搜尋完全不需要考慮這個——遞迴自然地保證了「用到時已經算好」。所以在複雜的狀態轉移中，記憶化的正確性更容易保證。

「稀疏狀態空間」是記憶化的一個明確優勢：如果狀態空間是 10^6 但實際只有 10^3 個狀態會被訪問到——遞推要填滿整張表（10^6 的工作），而記憶化只算那 10^3 個；**於是差了三個數量級**。這在「狀態的定義很寬但實際的路徑受限」的問題中很常見（例如某些博弈或路徑問題）。

「遞迴深度」是記憶化的主要風險：一個 10^5 規模的線性 DP——記憶化的遞迴深度可能是 10^5，而多數語言的預設堆疊放不下；於是必須改成遞推或者手動增大堆疊。所以在資料規模大且狀態是鏈狀依賴時，遞推是更安全的選擇。

「兩者的複雜度相同但常數不同」：記憶化有函數呼叫、雜湊表或陣列查找、以及遞迴的開銷——**通常比遞推慢幾倍**；在對常數敏感的場景（競賽或者效能關鍵的路徑）中，遞推更好。但在面試中，正確性遠比常數重要——所以「先記憶化寫對、有時間再優化」是一個好的策略。

## 面試回答方式

先指出兩者計算的是同一件事，差別在誰驅動計算的順序，再給各自的優點，並給實務建議（先記憶化寫對再視需要改遞推）。加分點有四個：遍歷順序是遞推最容易出錯的地方——而記憶化完全不需要考慮，遞迴自然保證了用到時已經算好；稀疏狀態空間是記憶化的明確優勢——狀態空間 10^6 但只訪問 10^3 個時差三個數量級；遞迴深度是記憶化的主要風險——大規模的鏈狀依賴會堆疊溢位；以及**兩者複雜度相同但常數不同**，而面試中正確性遠比常數重要。

## 講稿

兩者計算的是同一件事，差別在誰驅動計算的順序。

記憶化搜尋從目標狀態出發，需要什麼子問題就遞迴去求，求過的存起來。它的優點是狀態轉移的方向跟思考的方向一致，先想要算這個需要什麼。而且只計算真正用到的狀態，還有不需要想清楚計算的順序。

遞推從基礎狀態出發按一個明確的順序填表。優點是沒有遞迴的堆疊開銷與深度限制、常數更小、也更容易做空間優化。

而遍歷順序正是遞推最容易出錯的地方。一個狀態依賴的所有子狀態必須先被計算，而那個順序在多維的動態規劃中可能不直觀。完全背包的迴圈順序、區間動態規劃必須按長度遞增，這些都是。記憶化完全不需要考慮這個，遞迴自然保證了用到時已經算好。

所以我的實務建議是先用記憶化寫出正確的解，再視需要改成遞推。因為前者更容易寫對，而後者需要額外想清楚順序。

但要注意記憶化的主要風險是遞迴深度。十萬規模的線性動態規劃，遞迴深度可能就是十萬，多數語言的預設堆疊放不下。

## 常見追問

### 狀態該怎麼定義？

**核心答案**：狀態必須包含「做出後續決策所需要的全部資訊」而不多不少。多了——**狀態空間爆炸**；少了——無後效性被破壞（同一個狀態在不同的路徑下有不同的最優解）。判斷的方式是問「如果我只知道這個狀態，能不能決定接下來怎麼走」——**不能的話就缺了資訊。**

**詳細解析**：「無後效性」是這個判斷的正式名稱，而它的違反有一個典型的症狀：測試某些案例通過而某些失敗，且失敗的案例看起來與通過的相似——因為狀態不足導致「不同的歷史被當成了同一個狀態」。而修正的方式是「找出那個被遺漏的資訊並加進狀態」——**代價是狀態空間變大**。經典的例子是「股票買賣加冷凍期」：**只用「第 i 天、是否持有」不夠——**因為「昨天是否剛賣出」影響今天能不能買**；**於是要加一個維度**。**這個「發現狀態不足並補上」的過程，是 DP 題目中最需要思考的部分**——**而它比記住任何具體的轉移方程重要得多。

**面試回答方式**：給定義的標準（包含做出後續決策所需的全部資訊，不多不少）與判斷的方式。核心加分點是說明**無後效性違反的典型症狀**——某些案例通過而相似的失敗，因為不同的歷史被當成同一個狀態，並給出「股票買賣加冷凍期」的具體例子（要加一個維度記錄昨天是否剛賣出）。收在：這個「發現狀態不足並補上」的過程比記住任何轉移方程重要。

### 記憶化的快取該用什麼結構？

**核心答案**：狀態密集且維度已知就用陣列，稀疏或狀態是複雜物件就用 HashMap。陣列——**存取 O(1) 且常數極小**；但需要「所有維度的範圍已知且乘積不會太大」。**HashMap**——適合「狀態是字串、集合、或者範圍未知」的情況；**代價是雜湊的開銷與裝箱**。

**詳細解析**：「多維陣列的索引展平」是一個實用的優化：`dp[i][j][k]` 可以被展平成一維陣列加上手動計算的索引——於是省下了多層的間接存取與陣列物件的開銷；在效能關鍵的場景中這能帶來可觀的改善。而更常見的實務問題是「初始化的標記值」：用什麼表示「這個狀態還沒算過」——如果用 0 而 0 是一個合法的答案，那就會重複計算（或者更糟，回傳錯誤的結果）；所以應該用一個不可能是答案的值（-1、`Integer.MIN_VALUE`、或者一個獨立的 boolean 陣列）。這個「哨兵值必須與合法值區分」的細節，是記憶化實作中最常見的 bug 來源。

**面試回答方式**：給選擇的依據（密集用陣列、稀疏或複雜用 HashMap）與各自的代價。加分點是**多維陣列的索引展平**這個效能優化。核心加分點是**初始化的標記值**這個常見的 bug 來源——用 0 而 0 是合法答案時會重複計算或回傳錯誤結果，所以應該用不可能是答案的值或一個獨立的布林陣列。

### 什麼時候 DP 不是最好的解法？

**核心答案**：當存在貪心的解、或者狀態空間太大時。貪心——如果能證明「局部最優導致全局最優」，那它通常是 O(n) 或 O(n log n) 而 DP 是多項式或指數；所以應該先檢查有沒有貪心解。**狀態空間太大**——如果狀態的維度多或範圍大，DP 的空間可能放不下；這時要考慮「狀態壓縮」「只保留必要的維度」「或者換一個完全不同的角度」。

**詳細解析**：「先試貪心再退回 DP」是一個實用的解題順序：貪心的解法簡單、快、而且容易寫對——所以值得先花一分鐘想「有沒有一個明顯的貪心策略，以及我能不能找到反例」；找不到反例（且能大致論證）就試貪心，找到反例就轉向 DP。而反過來（先寫 DP）在時間有限的面試中可能來不及。另一個實用的觀察是「DP 的狀態數乘以轉移的代價就是複雜度」——於是在寫之前先估算一次，如果那個數字超過了時間限制（例如 10^9），就知道這個狀態定義不可行，需要重新設計；這個「先估算再實作」的習慣能避免寫完才發現超時。

**面試回答方式**：給兩種情況（存在貪心解、狀態空間太大）與各自的處理。核心加分點是**先試貪心再退回 DP** 這個解題順序——花一分鐘想有沒有明顯的貪心以及能不能找到反例。收在實用的習慣：DP 的狀態數乘以轉移代價就是複雜度，在寫之前先估算一次，超過時間限制就知道狀態定義不可行需要重新設計——**這能避免寫完才發現超時**。
