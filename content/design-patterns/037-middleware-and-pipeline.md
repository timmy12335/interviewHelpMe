# 題目

中介軟體（middleware）是什麼模式？它與責任鏈有什麼不同？

## 核心答案

**中介軟體是責任鏈的一個特化形態，而關鍵的差別是「它能包住下一步」**。

**經典的責任鏈**——**每個處理器決定「自己處理」或「傳給下一個」**；**控制流是單向的（傳下去就不回來）**。

**中介軟體**——**每個中介軟體接收「請求」與「下一步的函數」**；**它可以在呼叫下一步之前做事、之後做事、或者根本不呼叫**。**於是它形成的是一個「洋蔥」結構而非一條直線**——**這正是為什麼「記錄請求耗時」「包裝例外」「開啟與提交交易」這類需要前後都介入的關注點能被表達。**

**這個結構的價值是「橫切關注點可以被獨立地新增與移除」**：**加一個認證中介軟體不需要修改任何業務程式碼**；**而它們的順序決定了語義（認證要在授權之前、日誌要在最外層）。**

## 詳細解析

**「洋蔥結構」是這個模式的核心洞察**：`log(auth(rateLimit(handler)))`——**請求進入時經過 log → auth → rateLimit → handler，回應返回時反向經過**；**於是每一層都有「進入時」與「離開時」兩個切入點**。**這與 AOP 的環繞通知（around advice）是完全相同的能力**——**而中介軟體的形式更顯式（你能看到鏈條的組裝）而 AOP 更隱式（靠註解與織入）**。**兩者的取捨是「顯式的可讀性」與「隱式的簡潔」。**

**「順序即語義」是使用中介軟體時最需要注意的**：把錯誤處理放在最外層——**才能捕捉到所有內層的例外**；**把認證放在限流之前還是之後——決定了「未認證的請求算不算進配額」**。**這些順序的決定往往沒有被明確記錄，於是在調整時容易出錯**。**實用的做法是「在組裝的地方加註解說明每一層的理由」**——**因為那個順序是設計決策而非任意的排列。**

**「中介軟體不該包含業務邏輯」是一條實用的界線**：它處理的應該是**橫切的、與具體業務無關的關注點**（認證、日誌、追蹤、壓縮、CORS）——**而「這個訂單能不能被取消」屬於業務邏輯，放進中介軟體會讓它變得難以發現與測試**。**判斷的方式是問「這段邏輯對所有的請求都適用嗎」**——**不是的話它可能不屬於中介軟體。**

**「錯誤處理的位置很重要」**：一個中介軟體拋出的例外——**只能被它外層的中介軟體捕捉**；**所以錯誤處理中介軟體應該在最外層（或者接近最外層）**。**而一個常見的錯誤是「錯誤處理在認證之後」**——**於是認證本身拋出的例外沒有被統一處理，變成了未經格式化的 500**。

## 面試回答方式

先給它與責任鏈的關鍵差別（**它能包住下一步，形成洋蔥而非直線**）與那個結構讓「前後都介入」的關注點能被表達。加分點有四個：**洋蔥結構與 AOP 的環繞通知是相同的能力**，**而取捨是「顯式的可讀性」與「隱式的簡潔」**；**順序即語義**——**認證在限流之前或之後決定了未認證的請求算不算配額**，**而那些決定往往沒有被記錄**；**中介軟體不該包含業務邏輯**，**判斷是問「這段邏輯對所有請求都適用嗎」**；以及**錯誤處理應該在最外層**，**放在認證之後會讓認證的例外變成未格式化的 500**。

## 講稿

中介軟體是責任鏈的一個特化形態，而關鍵的差別是它能包住下一步。

經典的責任鏈中，每個處理器決定自己處理或傳給下一個，控制流是單向的。而中介軟體接收請求跟下一步的函數，它可以在呼叫下一步之前做事、之後做事、或者根本不呼叫。於是它形成的是一個洋蔥結構而不是一條直線。

這正是為什麼記錄請求耗時、包裝例外、開啟與提交交易這類需要前後都介入的關注點能被表達。它跟切面程式設計的環繞通知是完全相同的能力，只是中介軟體的形式更顯式，你能看到鏈條的組裝。

使用時最需要注意的是順序即語義。錯誤處理放在最外層才能捕捉到所有內層的例外。認證放在限流之前還是之後，決定了未認證的請求算不算進配額。這些順序的決定往往沒有被明確記錄，於是調整時容易出錯。所以我會在組裝的地方加註解說明每一層的理由。

還有一條界線，中介軟體不該包含業務邏輯。判斷的方式是問這段邏輯對所有的請求都適用嗎。不是的話它可能不屬於這裡。

## 常見追問

### 中介軟體怎麼傳遞資料給後面的層？

**核心答案**：**透過請求的上下文物件**。認證中介軟體驗證了 token——**把使用者資訊放進 context**；**後面的層從那裡讀取**。**在 Go 中是 `context.WithValue`、在 Node 中常常直接掛在 `req` 上、而在 Java 的 Servlet 中是 request attribute。**

**詳細解析**：**「上下文容易變成一個什麼都往裡塞的垃圾桶」是這個機制的主要風險**：因為它是無型別的鍵值對——**於是「這個 key 存在嗎」「它的型別是什麼」都要靠約定**；**而一個拼錯的 key 會在執行期才被發現**。**緩解的方式是「用型別安全的存取器」**（**定義 `getCurrentUser(ctx)` 這類函數封裝 key 與型別轉換**）——**於是誤用會在編譯期被抓到**。**另一個實用的紀律是「上下文中只放跨層真正需要的東西」**：**使用者身份、追蹤 ID、以及請求範圍的設定**——**而業務資料應該透過參數明確傳遞**。**因為「從上下文中隱式取得資料」讓函數的依賴變得不可見，那與服務定位器的問題完全相同。**

**面試回答方式**：給機制（請求上下文）與各語言的形式。核心加分點是**上下文容易變成什麼都往裡塞的垃圾桶**——**無型別的鍵值對讓誤用只在執行期被發現**，**緩解是用型別安全的存取器**。收在紀律：**只放跨層真正需要的東西，業務資料應該透過參數明確傳遞**——**因為隱式取得讓函數的依賴變得不可見，那與服務定位器的問題完全相同**。

### 非同步的中介軟體有什麼特別的？

**核心答案**：**每一層都必須正確地傳遞非同步的結果**。同步的中介軟體是簡單的函數呼叫——**而非同步的必須 `await` 或者回傳 Promise/Future**；**一個忘記 await 的中介軟體會讓「後續的處理還沒完成就返回了」**。**症狀是「回應提前送出」或者「錯誤處理捕捉不到內層的例外」**——**因為那個例外在中介軟體已經返回之後才發生。**

**詳細解析**：**「忘記傳遞非同步結果」是一個很難診斷的 bug**：程式碼看起來完全正常——**而錯誤處理與計時邏輯靜默地失效**；**測試如果只驗證正常路徑，也不會發現**。**所以在非同步的中介軟體鏈中，「每一層都回傳它呼叫下一步的結果」應該是一條被嚴格遵守的規則**——**而現代的框架與 linter 能檢查「未使用的 Promise」**。**這類「靜默失效」的 bug 特別值得用工具而非紀律來防**——**因為它們的症狀不明顯，靠人的注意力遲早會漏掉**。**而這也是「用型別系統或靜態分析捕捉錯誤」在非同步程式碼中特別有價值的原因。**

**面試回答方式**：給核心要求（**每一層必須正確傳遞非同步結果**）與忘記時的兩個症狀。核心加分點是指出**這是一個很難診斷的 bug**——**程式碼看起來正常而錯誤處理與計時靜默失效，測試如果只驗證正常路徑也不會發現**。收在防護：**用 linter 檢查未使用的 Promise**，**因為這類靜默失效的 bug 特別值得用工具而非紀律來防**。

### 中介軟體與過濾器、攔截器有什麼區別？

**核心答案**：**概念相同，差別在框架的層次與能存取的資訊**。Servlet 的 Filter——**在 Servlet 容器層，看到的是原始的 request/response**。**Spring 的 Interceptor——**在 Spring MVC 層，能存取到 handler 的資訊（知道會呼叫哪個 Controller 方法）**。**而 AOP 的切面——在方法呼叫層，能存取方法的參數與回傳值。**

**詳細解析**：**「選哪一層取決於需要什麼資訊」**：只需要看 URL 與標頭（CORS、壓縮、限流）——**Filter 就夠且效能最好**；**需要知道「這個請求會被哪個方法處理」（例如按註解決定是否需要認證）——需要 Interceptor**；**需要方法的參數（例如記錄某個業務參數）——需要 AOP**。**而越往內層資訊越豐富但耦合也越深**——**Filter 對框架幾乎無依賴，而 AOP 深度綁定**。**所以「用最外層能滿足需求的那一層」是一個好的預設**——**它保持了鬆耦合，也避免了不必要的執行開銷**。**這個「按需要的資訊選擇攔截層次」的判斷，比記住三者的定義有用得多。**

**面試回答方式**：給三者的層次與各自能存取的資訊。核心加分點是**選哪一層取決於需要什麼資訊**並逐一對應（URL 與標頭用 Filter、需要 handler 資訊用 Interceptor、需要方法參數用 AOP）。收在原則：**越往內資訊越豐富但耦合越深**，**所以「用最外層能滿足需求的那一層」是好的預設**——**它保持鬆耦合也避免不必要的開銷**。
