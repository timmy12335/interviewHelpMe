# 題目

值物件與實體的區別是什麼？為什麼這個區分重要？

## 核心答案

**區別在「相等性怎麼判斷」，而它決定了物件的整個行為特性。**

**實體有身份**——**兩個訂單即使所有欄位都相同，它們仍然是不同的訂單**；**相等性由 ID 決定**。**於是實體是可變的（狀態會隨時間改變而仍是同一個實體），需要被追蹤與持久化。**

**值物件沒有身份**——**兩個「100 元台幣」就是同一個東西**；**相等性由所有欄位的值決定**。**於是它應該是不可變的**——**因為「改變一個值物件」在概念上就等於「換成另一個值」。**

**這個區分重要，是因為它決定了三件事**：**能不能共享（值物件可以自由共享，實體不行）**、**要不要追蹤（實體需要，值物件不需要）**、**以及不可變性帶來的所有好處（執行緒安全、無副作用、可以安全地作為 Map 的 key）。**

## 詳細解析

**「把概念建模成值物件而非原生型別」是最實用的一個實踐**：`Money`、`Email`、`PhoneNumber`、`DateRange`——**它們常常被寫成 `BigDecimal`、`String`、`String`、`兩個 LocalDate`**；**而那讓「驗證規則」與「相關的行為」無處可放**。**建模成值物件之後**：**建構時就驗證（不可能存在一個無效的 Email 物件）**、**相關的行為有了歸屬（`money.add(other)` 會檢查幣別）**、**而且型別系統開始幫你**（**不可能把一個 `Money` 傳給需要 `Quantity` 的參數**）。**這個「用型別表達領域概念」的收益，遠大於它的樣板成本**——**尤其在有 record 或 data class 的現代語言中，成本已經很低。**

**「原生型別偏執（primitive obsession）」是這個問題的名字**：所有東西都是 String 與 int——**於是編譯器無法幫你抓到「把使用者 ID 傳給了訂單 ID 的參數」這類錯誤**。**而它的成本在系統長大之後才顯現：一個 `String userId` 到處傳遞，某處被誤用而測試沒覆蓋到**。**用值物件（或者至少是型別別名）能讓這類錯誤在編譯期就被抓到**——**而編譯期的錯誤是最便宜的錯誤。**

**「值物件的不可變性讓很多問題消失」**：不需要防禦性拷貝、可以安全地在多執行緒間共享、可以放進 HashSet 而不擔心被修改後 hash 改變——**而這些都是「可變物件」需要小心處理的問題**。**所以「預設不可變，只有真的需要才可變」是一個好的預設**。

**「實體的相等性應該只看 ID」是一個容易寫錯的細節**：如果 `equals` 比較所有欄位——**那麼「載入後修改了某個屬性」的實體就不等於「原本的自己」了**；**而那會破壞集合的行為**。**而如果 ID 是資料庫生成的，那「未持久化的實體」還沒有 ID**——**於是相等性判斷需要處理這個情況**（**常見的做法是用一個應用層生成的 UUID 作為身份**）。

## 面試回答方式

先給區別（**相等性怎麼判斷**）與各自的特性，再說明**這個區分決定了能不能共享、要不要追蹤、以及不可變性的好處**。加分點有四個：**把概念建模成值物件而非原生型別**——**建構時驗證、行為有歸屬、型別系統開始幫你**，**收益遠大於樣板成本尤其在有 record 的現代語言中**；**「原生型別偏執」是這個問題的名字**，**它的成本在系統長大後才顯現而編譯期的錯誤是最便宜的**；**不可變性讓防禦性拷貝、執行緒安全、hash 穩定這些問題消失**；以及**實體的相等性應該只看 ID**，**而未持久化的實體沒有 ID 這個情況需要處理**。

## 講稿

區別在相等性怎麼判斷，而它決定了物件的整個行為特性。

實體有身份，兩個訂單即使所有欄位相同仍然是不同的訂單，相等性由編號決定。於是它是可變的，需要被追蹤與持久化。值物件沒有身份，兩個一百元就是同一個東西，相等性由所有欄位的值決定。於是它應該是不可變的，因為改變一個值物件在概念上就等於換成另一個值。

這個區分重要是因為它決定了能不能共享、要不要追蹤、還有不可變性帶來的所有好處。

而我覺得最實用的一個實踐是把概念建模成值物件而不是原生型別。金額、電子信箱、電話號碼、日期區間，它們常常被寫成小數、字串、字串。那讓驗證規則跟相關行為無處可放。建模成值物件之後，建構時就驗證，不可能存在一個無效的信箱物件。相關行為有了歸屬，金額相加會檢查幣別。而且型別系統開始幫你，不可能把金額傳給需要數量的參數。

這個問題有一個名字叫原生型別偏執。所有東西都是字串跟整數，於是編譯器無法幫你抓到把使用者編號傳給訂單編號參數這類錯誤。而編譯期的錯誤是最便宜的錯誤。

## 常見追問

### 值物件要不要有 ID？

**核心答案**：**不該有**。如果它有 ID——**那它就是實體了**；**因為 ID 的存在意味著「兩個值相同但身份不同的物件是有意義的」**。**而在持久化時，值物件通常是「內嵌在實體的表中」**（`@Embeddable`）**或者「用一張表但以外鍵加所有欄位作為識別」**——**而非有自己的主鍵。**

**詳細解析**：**「同一個概念在不同的上下文中可能是實體也可能是值物件」是一個重要的認知**：一張「座位」在訂票系統中是實體（第 3 排 12 號是特定的一個座位，有狀態）——**而在座位圖的渲染程式中可能只是一個值物件（一個位置與類型的組合）**。**所以「這是實體還是值物件」不是物件本身的性質，而是「在這個上下文中我們關不關心它的身份」**。**這個觀點也是限界上下文這個概念的一個具體體現**——**同一個名詞在不同的上下文中有不同的模型是正常且正確的**。**而試圖建立一個「所有上下文共用的統一模型」正是很多大型系統複雜度失控的原因。**

**面試回答方式**：明確回答不該有並說明**ID 的存在意味著身份有意義**，給出持久化的做法。核心加分點是**同一個概念在不同上下文中可能是實體也可能是值物件**——**座位在訂票系統中是實體、在渲染程式中是值物件**，**所以這不是物件本身的性質而是「在這個上下文中我們關不關心它的身份」**。收在延伸：**這是限界上下文的具體體現**，**而試圖建立統一模型正是很多大型系統複雜度失控的原因**。

### 不可變物件的效能代價大嗎？

**核心答案**：**通常比預期小得多，而且常常是正的**。每次「修改」產生新物件確實有分配成本——**但現代 JVM 的年輕代分配極快（幾乎就是指標移動），而短命的物件回收也很便宜**。**而不可變帶來的好處包括：不需要防禦性拷貝（反而減少了分配）、可以安全共享（同一個 `Money` 可以被多處引用）、以及編譯器與 JIT 能做更多的優化。**

**詳細解析**：**「真正需要注意的是大型物件的頻繁複製」**：一個包含幾千個元素的不可變集合，每次「新增一個元素」都複製整個集合——**那確實是 O(n) 的成本**。**而解法不是「改成可變」而是「用持久化資料結構」**（**共享未變的部分，只複製路徑上的節點，於是新增是 O(log n)**）——**Clojure 與 Scala 的不可變集合正是這樣實作的**。**在 Java 中，如果需要頻繁修改大型集合，常見的做法是「內部用可變的建構、對外暴露不可變的視圖」**（Builder 模式的一個應用）——**於是建構期高效而使用期安全**。**這個「建構時可變、使用時不可變」的模式，在很多不可變設計中都出現。**

**面試回答方式**：回答通常比預期小且常常是正的，並給出理由（年輕代分配極快、不需要防禦性拷貝、可安全共享）。核心加分點是指出**真正需要注意的是大型物件的頻繁複製**，**而解法不是改成可變而是用持久化資料結構**（共享未變的部分，新增是 O(log n)）。收在 Java 中的實用模式：**內部用可變的建構、對外暴露不可變的視圖**——**建構時高效而使用時安全**。

### 這些概念在函數式語言中還適用嗎？

**核心答案**：**更適用，因為函數式語言天然鼓勵不可變**。值物件在函數式中就是「一個 record 或 case class」——**不需要額外的紀律，因為預設就是不可變**。**而實體的概念仍然存在（有身份的東西）**，**只是它的狀態變化被表達成「產生一個新的狀態」而非「修改一個物件」**——**於是「訂單的歷史」自然地成為一串狀態，而那正好與事件溯源契合。**

**詳細解析**：**「函數式的方式讓狀態變化變得顯式」**：`order.cancel()` 在物件導向中修改了物件——**而 `cancel(order)` 回傳一個新的訂單**；**於是「舊的狀態」仍然存在，可以被比較、被記錄、被回溯**。**這讓「這個訂單經歷了什麼」變成一個可以直接回答的問題**——**而在可變的模型中，那需要額外的審計機制**。**代價是「誰持有當前的狀態」需要被明確管理**（**因為狀態不再是物件的一部分**）——**而那正是各種狀態管理方案（Redux、Elm 架構）要解決的問題**。**理解這個對應，能看出「函數式的狀態管理」與「事件溯源」在本質上是同一個想法的不同表現。**

**面試回答方式**：回答更適用並說明**函數式中值物件就是預設不可變的 record，不需要額外紀律**。核心加分點是**函數式的方式讓狀態變化變得顯式**——**回傳新狀態而非修改，於是舊狀態仍然存在可以被比較記錄回溯**，**這讓「這個訂單經歷了什麼」變成能直接回答的問題**。收在對應：**代價是「誰持有當前狀態」要被明確管理，而那正是各種狀態管理方案要解決的**，**理解這個對應能看出函數式狀態管理與事件溯源本質上是同一個想法**。
