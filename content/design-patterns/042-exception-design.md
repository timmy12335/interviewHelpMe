# 題目

例外該怎麼分類與設計？什麼時候該轉換它？

## 核心答案

先用一個更有用的分類取代「檢查型 vs 非檢查型」：按「呼叫方能不能處理」分。

**呼叫方能處理的**——業務規則違反（餘額不足、庫存不夠、狀態不允許）；這些應該是明確的、帶有足夠資訊的例外，讓呼叫方能做出不同的反應。

**呼叫方不能處理的**——程式錯誤（空指標、參數非法）與基礎設施故障（資料庫連不上）；這些應該冒泡到統一的處理器，記錄並回傳一個通用的錯誤。

**而「轉換」發生在架構的邊界上**：基礎設施的例外（`SQLException`）不該洩漏到領域層——Repository 應該把它轉成領域或應用層的例外；否則上層被迫依賴下層的技術細節。

同樣地，對外的 API 邊界應該把內部的例外轉成明確的錯誤碼與訊息——而不是把堆疊追蹤丟給呼叫方。

## 詳細解析

「按能不能處理分類」比 Java 的檢查型分類實用得多：檢查型例外的初衷是「強制呼叫方處理」——而實際的結果往往是「到處 catch 然後吞掉或者包裝成 RuntimeException」；於是它增加了噪音而沒有增加安全性。現代的 Java 生態（Spring、多數函式庫）普遍傾向非檢查型——而正確的紀律不是靠編譯器強制，而是「在設計時明確區分這兩類，並讓第一類有足夠的資訊」。

「例外要攜帶足夠的資訊」是一個常被忽略的實務要求：`throw new InsufficientBalanceException()` 幾乎沒有用——而 `InsufficientBalanceException(accountId, required, available)` 讓呼叫方能顯示有意義的訊息、也讓日誌能定位問題。**這個差別在排查時極其明顯**：前者只告訴你「發生了」，後者告訴你「發生了什麼」。

「不要用例外控制正常流程」有一個具體的理由與一個例外：理由是例外的建構成本高（填充堆疊追蹤）且它讓程式碼的意圖混亂；而「例外」是「在深層需要中止整個流程」的情況——那時例外的「跨層傳播」正是它的價值（而用回傳值層層傳遞會非常繁瑣）。所以判斷是「這是不是一個真的異常情況」而非教條地避免。

「統一的例外處理器是邊界上的必要設計」：在 Web 層有一個地方把所有例外轉成 HTTP 回應——**於是每個 Controller 不需要各自處理**；而它也保證了「錯誤回應的格式一致」與「內部細節不會洩漏給使用者」。沒有這一層的話，錯誤處理會散落各處且不一致——而那既是體驗問題也是安全問題（堆疊追蹤可能洩漏內部結構）。

## 面試回答方式

先給更有用的分類（**按呼叫方能不能處理**）與兩類的處理方式，再說明**轉換發生在架構邊界上**。加分點有四個：**這個分類比檢查型實用**——檢查型的實際結果往往是到處 catch 然後吞掉，增加噪音而沒增加安全性；**例外要攜帶足夠的資訊**——「發生了」與「發生了什麼」在排查時差別極大；不要用例外控制正常流程的理由與例外——「在深層需要中止整個流程」時它的跨層傳播正是價值；以及統一的例外處理器是邊界上的必要設計，它同時解決了一致性與安全（避免堆疊追蹤洩漏）。

## 講稿

我會用一個比檢查型與非檢查型更有用的分類，按呼叫方能不能處理來分。

能處理的是業務規則違反，餘額不足、庫存不夠、狀態不允許。這些應該是明確的、帶有足夠資訊的例外，讓呼叫方能做出不同的反應。不能處理的是程式錯誤跟基礎設施故障，這些應該冒泡到統一的處理器。

而轉換發生在架構的邊界上。資料庫的例外不該洩漏到領域層，儲存庫應該把它轉成領域或應用層的例外，否則上層被迫依賴下層的技術細節。同樣地，對外的介面邊界應該把內部例外轉成明確的錯誤碼，而不是把堆疊追蹤丟給呼叫方。

有一個常被忽略的實務要求是例外要攜帶足夠的資訊。只拋一個餘額不足幾乎沒有用，而帶上帳戶編號、需要多少、現有多少，才能讓呼叫方顯示有意義的訊息，也讓日誌能定位問題。這個差別在排查時極其明顯，前者只告訴你發生了，後者告訴你發生了什麼。

另外我會在網頁層放一個統一的例外處理器，把所有例外轉成回應。它保證了錯誤格式一致，也保證內部細節不會洩漏給使用者。

## 常見追問

### 例外的階層該怎麼設計？

**核心答案**：**淺而寬優於深而窄**。一個 `BusinessException` 基類加上幾個具體的子類——**通常就夠了**；而三四層的繼承階層讓「該 catch 哪一層」變得困難。設計的依據是「呼叫方會怎麼區分」：如果所有的業務例外都被統一處理，那不需要細分；而如果某幾種需要特別的處理，那它們才需要獨立的型別。

**詳細解析**：「用一個型別加上錯誤碼」是階層之外的另一個選擇：`BusinessException(ErrorCode.INSUFFICIENT_BALANCE, ...)`——於是不需要為每種錯誤定義一個類別；而錯誤碼可以是一個列舉，攜帶訊息範本與 HTTP 狀態的映射。這個做法在「錯誤種類很多但處理方式相似」時明顯更簡潔——而它也讓「錯誤碼的清單」成為一份可以被檢視的文件。代價是失去了「用 catch 區分」的能力（要在 catch 之後判斷錯誤碼）——所以如果確實需要對某幾種做不同的處理，那幾種仍應該有自己的型別。兩種做法混用（少數需要特別處理的用型別、其餘用錯誤碼）通常是最實際的。

**面試回答方式**：給原則（**淺而寬優於深而窄**）與設計依據（**呼叫方會怎麼區分**）。核心加分點是**用一個型別加錯誤碼**這個替代方案——在錯誤種類多但處理方式相似時更簡潔，而錯誤碼清單成為可檢視的文件。收在混用的實際做法：少數需要特別處理的用型別、其餘用錯誤碼。

### 例外的日誌該在哪一層記錄？

**核心答案**：在「有足夠上下文且不會重複」的那一層，通常是最外層的處理器。常見的錯誤是「每一層都 catch、log、然後重新拋出」——於是同一個錯誤在日誌中出現五次；而那讓日誌變得嘈雜且難以判斷「發生了幾次問題」。正確的做法是「中間層只在能加上有價值的上下文時才包裝並重新拋出，而記錄由最外層統一做」。

**詳細解析**：**「catch、log、rethrow 是一個明確的反模式」**：它既不處理錯誤也不減少噪音——**只是複製了資訊**。而正確的中間層行為是兩種之一：要嘛真的處理它（記錄並繼續、或者降級）、要嘛包裝並加上上下文再拋出（`throw new OrderProcessingException("processing order " + orderId, cause)`）。後者的價值在於「異常鏈中每一層都加了自己知道的資訊」——於是最外層的日誌包含了完整的脈絡。而「保留原始的 cause」是這個做法的關鍵——丟掉 cause 的包裝會讓根因永久遺失，那是比不包裝更糟的做法。

**面試回答方式**：給原則（在有足夠上下文且不重複的那一層，通常是最外層）與常見錯誤。核心加分點是把 **catch、log、rethrow 明確定位成反模式**——既不處理也不減少噪音，只是複製資訊，並給出中間層正確的兩種行為。收在關鍵細節：**包裝時必須保留原始的 cause**——丟掉它會讓根因永久遺失，比不包裝更糟。

### 對外 API 的錯誤該怎麼表達？

**核心答案**：穩定的錯誤碼加上人類可讀的訊息，並且區分「給程式看的」與「給人看的」。錯誤碼是契約的一部分（呼叫方會用它做判斷，所以不能隨意改）——而訊息是給開發者或使用者看的，可以調整。另外應該包含「這個錯誤能不能重試」的資訊，因為那直接影響呼叫方的行為。

**詳細解析**：「不要用 HTTP 狀態碼表達所有的業務錯誤」：400 涵蓋了太多情況——呼叫方無法區分「參數格式錯」與「餘額不足」與「狀態不允許」；所以應該用 HTTP 狀態碼表達「大類」，而在回應體中用錯誤碼表達具體的原因。這個分層讓「通用的處理」（例如所有 5xx 都重試）與「具體的處理」（餘額不足要提示儲值）都能被實作。**而 RFC 7807（Problem Details）提供了一個標準的格式**——用它比自己發明一個格式好，因為工具與函式庫可能已經支援。這個「用標準而非自創」的判斷，在錯誤格式這類「沒有創新價值」的地方特別適用。

**面試回答方式**：給組成（穩定的錯誤碼、可讀的訊息、能不能重試的資訊）與**區分給程式看的與給人看的**。核心加分點是不要用 HTTP 狀態碼表達所有業務錯誤——400 涵蓋太多情況讓呼叫方無法區分，應該用狀態碼表達大類、回應體中的錯誤碼表達具體原因，這個分層讓通用處理與具體處理都能實作。收在建議：**用 RFC 7807 這類標準格式而非自創**，因為錯誤格式是沒有創新價值的地方。
