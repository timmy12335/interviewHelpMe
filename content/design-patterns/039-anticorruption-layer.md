# 題目

反腐層（Anticorruption Layer）解決什麼問題？它與轉接器有什麼不同？

## 核心答案

**反腐層防的是「外部系統的模型汙染你的領域模型」**。當你整合一個舊系統或第三方 API——**它的概念、命名、與資料結構往往與你的領域不匹配**；**如果直接讓它的 DTO 流進你的業務邏輯，那些不匹配會逐漸侵蝕你的模型**。

**它與轉接器的差別在「意圖與厚度」**。**轉接器**——**解決「介面不相容」，通常是一個薄薄的簽章轉換**。**反腐層**——**解決「模型不相容」，它包含翻譯、驗證、以及概念的映射**；**通常是一整個套件而非一個類別**。

**它的具體形態是「一個只暴露你的領域語言的介面，內部負責與外部系統對話並翻譯」**——**於是你的領域層只知道 `PaymentGateway.charge(Money)`，而不知道對方的 API 需要三次呼叫、參數用分為單位、且錯誤碼是一串數字。**

## 詳細解析

**「不做反腐層的代價是漸進的」**：一開始只是「直接用了對方的 DTO」——**方便且省時**；**而幾個月後，對方的欄位名稱出現在你的業務邏輯中、對方的錯誤碼被到處判斷、對方的概念（例如它把「訂單」叫做「交易」）滲透進團隊的用語**。**於是「對方改了 API」變成一個影響全系統的變更**——**而那正是反腐層要防的**。**這個成本的漸進性讓它容易被低估：每一次「直接用」都只增加一點耦合，而累積之後就無法回頭。**

**「反腐層應該在哪一側」是一個實用的判斷**：如果外部系統穩定而你頻繁變化——**反腐層在你這側（保護你的模型）**；**如果你是被整合的一方且有很多消費者——你應該提供一個穩定的介面（那也是一種反腐，保護消費者不受你內部變化的影響）**。**而在兩個團隊都會變的情況下，「明確的契約加上雙方各自的翻譯層」是最穩健的**——**代價是兩份翻譯的程式碼。**

**「反腐層的測試是它價值的一部分」**：因為所有與外部的互動都集中在這一層——**你可以在這裡放一個假的實作，讓整個業務層的測試不需要碰到外部系統**；**而反腐層本身用契約測試或錄製的回應來測**。**這個「把不確定性集中在一個地方」的效果，讓測試的策略變得清晰。**

**「什麼時候不需要」**：如果外部系統的模型與你的高度一致（例如同一個團隊的另一個服務，用同樣的領域語言）——**那反腐層只是多餘的轉換**。**判斷的方式是「對方的概念與我的能不能直接對應」**——**能的話直接用，不能的話就需要翻譯。**

## 面試回答方式

先給它防的問題（**外部系統的模型汙染你的領域模型**）與**它與轉接器在意圖與厚度上的差別**，再給具體形態。加分點有四個：**不做的代價是漸進的**——**每次「直接用」只增加一點耦合，累積後無法回頭**，**而「對方改了 API」變成影響全系統的變更**；**反腐層應該在哪一側**的判斷與雙方都會變時的處理；**它的測試價值**——**把不確定性集中在一個地方讓測試策略變清晰**；以及**什麼時候不需要**，**判斷是「對方的概念與我的能不能直接對應」**。

## 講稿

反腐層防的是外部系統的模型汙染你的領域模型。整合一個舊系統或第三方介面時，它的概念、命名、資料結構往往跟你的領域不匹配。如果直接讓它的資料傳輸物件流進業務邏輯，那些不匹配會逐漸侵蝕你的模型。

它跟轉接器的差別在意圖與厚度。轉接器解決介面不相容，通常是薄薄的簽章轉換。反腐層解決模型不相容，包含翻譯、驗證、概念的映射，通常是一整個套件而不是一個類別。

而不做它的代價是漸進的，這讓它容易被低估。一開始只是直接用了對方的資料結構，方便省時。幾個月後對方的欄位名稱出現在你的業務邏輯中、對方的錯誤碼被到處判斷、對方的概念滲透進團隊的用語。於是對方改了介面變成一個影響全系統的變更。每一次直接用都只增加一點耦合，而累積之後就無法回頭。

它還有一個測試上的價值。因為所有與外部的互動都集中在這一層，你可以在這裡放一個假的實作，讓整個業務層的測試不需要碰到外部系統。把不確定性集中在一個地方，讓測試的策略變得清晰。

## 常見追問

### 反腐層會不會造成太多樣板程式碼？

**核心答案**：**會，而那是它明確的成本**。每個外部的概念都要一個對應的內部概念與一個轉換——**在欄位很多時這是可觀的工作量**。**緩解的方式有三**：**只翻譯真正用到的欄位**（不要照抄整個 DTO）、**用映射工具**（MapStruct 這類在編譯期產生轉換程式碼的）、**以及「只在真正需要隔離的邊界上做」**（不是每個外部呼叫都需要完整的反腐層）。

**詳細解析**：**「只翻譯用到的欄位」是最有效的簡化**：一個外部 API 回傳五十個欄位而你只用五個——**那內部模型就只該有那五個**；**照抄全部不只是工作量，還把「你其實不關心的東西」變成了你的模型的一部分**。**而這個克制也有一個額外的好處：當對方新增或修改了你不用的欄位時，你完全不受影響**。**所以「最小化的翻譯」既省工又降低耦合**——**這是少數「省事的做法同時也是正確的做法」的情況**。**而判斷「這個欄位我真的需要嗎」的方式是看它有沒有出現在業務邏輯中**——**只是「順便存下來以備不時之需」的欄位通常不需要進入領域模型。**

**面試回答方式**：承認成本並給三個緩解方式。核心加分點是**只翻譯用到的欄位是最有效的簡化**——**照抄全部不只是工作量，還把不關心的東西變成模型的一部分**，**而克制的額外好處是對方修改你不用的欄位時完全不受影響**。收在：**這是少數「省事的做法同時也是正確的做法」的情況**，**而判斷的方式是看那個欄位有沒有出現在業務邏輯中**。

### 反腐層與整合模式（如轉接器、外觀）怎麼組合？

**核心答案**：**它們常常一起出現且職責互補**。反腐層是**一個邊界的概念**——**而在它內部，可能用轉接器處理介面的形狀、用外觀簡化多次呼叫、用策略處理不同的外部供應商**。**所以反腐層不是一個具體的模式，而是「一個由多個模式組成的邊界層」。**

**詳細解析**：**「一個外部整合常常需要應付多個供應商」是這個組合的典型場景**：支付有三家、簡訊有兩家——**而你的領域只想知道「發送簡訊」**；**於是反腐層內部有一個 `SmsProvider` 介面（策略）與幾個實作（每家一個轉接器），加上一個路由的邏輯（按國家或成本選擇）**。**這個結構讓「換一家供應商」或「新增一家」都不影響領域層**——**而那正是反腐層的價值兌現的時刻**。**所以評估反腐層值不值得的一個實用問題是「這個外部依賴未來可能被替換或增加嗎」**——**會的話它的投入很快就回本；而如果是一個永遠不會變的內部系統，那個投入可能不划算。**

**面試回答方式**：說明**它們職責互補而反腐層是由多個模式組成的邊界層**。核心加分點是給出典型場景（多個供應商）與內部的結構（策略加轉接器加路由），並指出**這讓換或新增供應商都不影響領域層**。收在評估的實用問題：**這個外部依賴未來可能被替換或增加嗎**——**會的話投入很快回本，而永遠不會變的內部系統可能不划算**。

### 微服務之間需要反腐層嗎？

**核心答案**：**看兩個服務是不是同一個限界上下文**。同一個上下文（共用領域語言、同一個團隊）——**直接用共享的契約更簡單**。**不同上下文（例如「訂單」與「會計」對同一件事有不同的模型）——需要翻譯**；**而那個翻譯放在消費方是最常見的做法（因為消費方知道自己需要什麼）。**

**詳細解析**：**「共享一個模型函式庫」是微服務中一個誘人但危險的做法**：讓兩個服務共用同一個 DTO 的 jar——**省下了翻譯的程式碼**；**但它把兩個服務的發布綁在了一起（改一個欄位要同時部署）**，**而那正是微服務要避免的耦合**。**所以「寧可複製一個小的 DTO 也不要共享一個函式庫」是一個常見且正確的建議**——**因為那個重複的成本遠低於耦合的成本**。**而如果契約確實需要被共享，正確的做法是「共享的是契約的定義（OpenAPI、proto）而非產生的程式碼」**——**於是各方各自產生，版本可以獨立演進。**

**面試回答方式**：給判斷（**是不是同一個限界上下文**）與兩種情況，指出**翻譯放在消費方是最常見的做法**。核心加分點是**共享模型函式庫是誘人但危險的做法**——**它把兩個服務的發布綁在一起，而那正是微服務要避免的耦合**，**所以「寧可複製一個小的 DTO 也不要共享函式庫」**。收在正確的共享方式：**共享契約的定義而非產生的程式碼**，**於是各方各自產生、版本獨立演進**。
