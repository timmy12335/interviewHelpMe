# 題目

同一個模式在 Java、Go、與 Rust 中會長成什麼樣？

## 核心答案

**語言的特性決定了模式的形態，而有時候決定了它是否還是一個「模式」。**

**策略**——**Java 用介面加實作類別（或 lambda）**；**Go 用函式型別或小介面**；**Rust 用 trait 物件或泛型**（**後者是零成本的，因為在編譯期單態化**）。

**單例**——**Java 要處理執行緒安全與延遲初始化（列舉或靜態內部類別）**；**Go 用 `sync.Once` 或套件層級的變數**；**Rust 用 `OnceLock`，而且它的所有權系統讓「全域可變狀態」本來就困難**——**於是單例在 Rust 中天然被抑制。**

**裝飾者**——**Java 用繼承或組合加介面**；**Go 用嵌入（embedding）非常自然**；**Rust 用泛型包裝加 trait。**

**而更有趣的是「有些模式在某些語言中消失了」**：**Go 沒有繼承，於是所有「用繼承實作的模式」自然變成組合**；**而 Rust 的所有權讓「觀察者」這類需要互相引用的模式明顯更難寫。**

## 詳細解析

**「Go 的隱式介面改變了依賴的方向」**：Java 中實作類別必須宣告 `implements`——**於是介面的定義者與實作者之間有一個編譯期的耦合**；**而 Go 的介面是隱式滿足的（結構型別）**——**於是「介面定義在使用方而非提供方」成為慣例**。**這讓依賴反轉變得自然：消費者定義自己需要什麼，而任何符合的型別都能被傳入**——**不需要提供方預先知道那個介面的存在**。**這個差別讓 Go 中的「小介面」文化成為可能（`io.Reader` 只有一個方法），而那正是介面隔離原則的一個極致實踐。**

**「Rust 的所有權讓某些模式必須改變形態」**：觀察者模式需要「被觀察者持有觀察者的參考」而觀察者可能也引用被觀察者——**在 Rust 中那是一個循環引用**；**於是需要 `Rc<RefCell<>>` 或者改用「訊息傳遞」的形式**。**這個限制常被批評為「Rust 讓某些設計難寫」**——**而另一種看法是「那些設計本來就有隱藏的複雜度（生命週期與所有權的不明確），而 Rust 只是讓它顯式了」**。**這個觀點在理解 Rust 的設計哲學時很有幫助。**

**「同一個問題的慣用解法可能完全不同」**：錯誤處理——**Java 用例外、Go 用多回傳值、Rust 用 `Result`**；**於是「錯誤處理的模式」在三種語言中幾乎沒有共通的形態**。**所以「把一種語言的慣用法帶到另一種」通常是一個錯誤**——**而識別「這是語言的慣用法還是通用的設計原則」是跨語言工作時最重要的判斷。**

**「通用的是問題與取捨，特定的是表達」**：所有語言都要面對「怎麼讓行為可替換」「怎麼組織相關的功能」「怎麼處理沒有值」——**而每種語言提供了不同的工具**。**所以學習一個新語言時，正確的問題是「這個語言用什麼表達這個常見的需求」而非「這個語言有沒有某某模式」。**

## 面試回答方式

先給幾個模式在三種語言中的形態，並指出**有些模式在某些語言中消失了**。加分點有四個：**Go 的隱式介面改變了依賴的方向**——**介面定義在使用方而非提供方**，**讓依賴反轉變得自然，也讓小介面文化成為可能**；**Rust 的所有權讓某些模式必須改變形態**——**而另一種看法是那些設計本來就有隱藏的複雜度，Rust 只是讓它顯式了**；**同一個問題的慣用解法可能完全不同**（錯誤處理），**所以把一種語言的慣用法帶到另一種通常是錯誤**；以及**通用的是問題與取捨、特定的是表達**——**學新語言時該問「它用什麼表達這個需求」**。

## 講稿

語言的特性決定了模式的形態，而有時候決定了它是否還是一個模式。

策略模式在 Java 中是介面加實作類別或匿名函數，在 Go 中是函式型別或小介面，在 Rust 中是特徵物件或泛型。單例在 Java 中要處理執行緒安全與延遲初始化，在 Go 中用一次性初始化，而在 Rust 中所有權系統讓全域可變狀態本來就困難，於是它天然被抑制。

更有趣的是有些模式在某些語言中消失了。Go 沒有繼承，於是所有用繼承實作的模式自然變成組合。

我覺得最有啟發的是 Go 的隱式介面改變了依賴的方向。Java 中實作類別必須宣告實作了哪個介面，於是定義者與實作者有編譯期的耦合。而 Go 的介面是隱式滿足的，於是介面定義在使用方而不是提供方成為慣例。這讓依賴反轉變得自然，消費者定義自己需要什麼，任何符合的型別都能被傳入。這也是 Go 的小介面文化能成立的原因。

而通用的是問題與取捨，特定的是表達。所有語言都要面對怎麼讓行為可替換、怎麼處理沒有值。所以學一個新語言時，正確的問題是這個語言用什麼表達這個常見的需求，而不是這個語言有沒有某某模式。

## 常見追問

### 動態語言中的模式有什麼不同？

**核心答案**：**多數與型別相關的模式消失或簡化**。**鴨子型別讓「介面」變成一個約定而非宣告**——**於是策略、轉接器這類「為了符合型別而存在」的結構不再需要**；**而「猴子補丁」（執行期修改類別）讓裝飾與代理可以在不修改原始碼的情況下完成**。**代價是「錯誤只在執行期被發現」與「難以靜態分析」。**

**詳細解析**：**「動態語言的靈活性把成本從編譯期移到了執行期與維護期」**：不需要定義介面——**於是開發快**；**但「這個物件到底要有哪些方法」沒有被明確表達，於是靠文件與慣例**。**在小型專案中那完全沒問題**——**而在大型專案中，那個缺失的資訊成為理解與重構的障礙**。**這正是為什麼 Python 加入了型別註解、JavaScript 演化出 TypeScript**——**它們在保留動態的靈活性的同時，補回了「型別作為文件與檢查」的價值**。**而這個演化的方向說明了一件事：那些「用型別表達的模式」的價值不在型別本身，而在它們表達的約束與意圖**——**於是無論語言是否強制，把那些意圖表達出來都是有價值的。**

**面試回答方式**：給主要的差異（**鴨子型別讓介面變成約定、猴子補丁讓裝飾不需修改原始碼**）與代價。核心加分點是**動態語言的靈活性把成本從編譯期移到執行期與維護期**——**「這個物件要有哪些方法」沒有被明確表達，在大型專案中成為理解與重構的障礙**，**這正是 Python 加型別註解、JavaScript 演化出 TypeScript 的原因**。收在洞察：**用型別表達的模式，價值不在型別本身而在它們表達的約束與意圖**。

### 函數式語言中還有設計模式嗎？

**核心答案**：**有，但它們的名字與形態完全不同**。物件導向的模式多數關於「物件的組織」——**而函數式的模式關於「函數與資料的組合」**：**monad（處理有上下文的計算）、functor、以及各種組合子**。**而它們同樣是「被命名的常見解法」**——**只是解決的問題形狀不同。**

**詳細解析**：**「monad 常被過度神秘化，而它的實用價值很具體」**：它是一個「把『有額外上下文的值』串起來」的模式——**`Optional` 的鏈式呼叫、`Promise` 的 then、以及錯誤處理的鏈**，**它們都是同一個結構**。**理解這個共通性的價值在於：一旦你看出「這是一個 monad」，你就知道它有哪些操作（map、flatMap）與哪些性質**——**而那正是模式的價值（一個名字帶來一整組已知的性質）**。**所以函數式的「模式」與物件導向的模式在角色上是相同的：它們都是「被識別、被命名、因而可以被溝通與重用的解法」**——**只是抽象的層次更高、也更數學。**

**面試回答方式**：回答有但**名字與形態完全不同**，並指出物件導向的模式關於物件的組織而函數式的關於函數與資料的組合。核心加分點是**monad 常被過度神秘化而它的實用價值很具體**——**Optional 的鏈式、Promise 的 then、錯誤處理的鏈都是同一個結構**，**而看出「這是一個 monad」就知道它有哪些操作與性質**。收在角色的相同：**它們都是「被識別、被命名、因而可以被溝通與重用的解法」，只是抽象層次更高**。

### 跨語言工作時最該注意什麼？

**核心答案**：**不要把上一個語言的慣用法直接搬過來**。在 Go 中寫 Java 風格的抽象工廠、在 Rust 中試圖用繼承、在 Python 中建立十層的類別階層——**這些都是「用新語言寫舊語言」**；**結果是既失去了新語言的優勢，也讓熟悉那個語言的人難以閱讀**。**正確的做法是「先學習那個語言的慣用法」**——**通常從閱讀它的標準函式庫開始。**

**詳細解析**：**「標準函式庫是慣用法最好的教材」**：它由語言的設計者寫成——**於是它展示了「這個語言認為什麼是自然的」**；**而閱讀它比讀任何風格指南都有效**。**Go 的 `io` 與 `net/http`、Rust 的 `Option` 與 `Iterator`、Python 的 `itertools`——**它們不只是工具，也是設計的示範**。**而一個實用的檢驗是「我的程式碼看起來像標準函式庫的程式碼嗎」**——**不像的話，可能是在用另一種語言的思維寫**。**這個「向標準函式庫學習慣用法」的方法，比背誦「Go 的最佳實踐」有效得多，因為它提供的是大量的具體例子而非抽象的規則。**

**面試回答方式**：給核心建議（**不要把上一個語言的慣用法搬過來**）與那樣做的兩個後果。核心加分點是**標準函式庫是慣用法最好的教材**——**它由語言設計者寫成，展示了這個語言認為什麼是自然的**，並給出各語言的具體例子。收在實用的檢驗：**「我的程式碼看起來像標準函式庫的程式碼嗎」**，**而這個方法比背誦最佳實踐有效，因為它提供的是大量具體例子而非抽象規則**。
