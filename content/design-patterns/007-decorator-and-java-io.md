# 題目

為什麼 Java 的 IO 要寫成一層包一層？裝飾者相對於繼承的優勢在哪？

## 核心答案

因為功能是**可以自由組合**的。串流可能需要緩衝、可能需要壓縮、可能需要加密、可能需要轉成字元——如果用繼承來表達，每一種組合都要一個子類別，四個功能就是十六種組合，類別數量隨功能數量指數成長，而且新增一個功能要新增一整批子類別。裝飾者把每個功能做成一個與被裝飾者實作相同介面的包裝，於是組合在**執行期**完成：要緩衝就包一層緩衝、要壓縮就再包一層壓縮，順序與組合由使用方決定。這是「**組合優於繼承**」最經典的實例。它的代價也很明確：**物件層數多**（除錯時堆疊很深）、**建立方式囉嗦**（一長串巢狀的建構呼叫）、**順序有語意**（先壓縮再加密與先加密再壓縮結果完全不同，而且介面上看不出正確順序）。所以裝飾者適合「**功能正交且需要自由組合**」的場景，功能之間有依賴或順序約束時，它的表達力反而不足。

## 詳細解析

**繼承的組合爆炸是具體的**：假設要支援緩衝、壓縮、加密三種功能，用繼承需要為每一種組合定義類別（緩衝的、壓縮的、緩衝加壓縮的……），共八種；再加一個功能就變十六種。而且這些子類別之間會有大量重複的程式碼。裝飾者則是三個類別，組合在使用時決定。這個對比是說明「組合優於繼承」最直觀的例子。

**順序有語意是它最大的坑**：先壓縮再加密（壓縮率好，因為壓縮的是原始資料）與先加密再壓縮（幾乎壓不動，因為加密後的資料接近隨機）結果差異巨大，但型別系統完全不會阻止你寫錯。這是裝飾者的固有弱點——它把組合的自由交給使用方，也就把正確組合的責任交了出去。緩解方式是提供**預設的組合方法**（一個工廠方法封裝正確的順序），讓多數使用者不必自己組。

**除錯與可讀性成本**：一個包了五層的串流，例外的堆疊追蹤會很長，而且從變數型別上看不出實際的組合。這在排查時是真實的負擔。實務上的緩解是**限制層數**與用有意義的工廠方法封裝常見組合，而不是讓每個使用點自己堆疊。

**現代的替代表達**：在支援函式組合的語言中，裝飾者常常表現為**高階函式的組合**——每個「裝飾」是一個接收函式回傳函式的函式，組合就是把它們串起來。這比類別的形式輕量得多，也更容易閱讀。所以看到需要「層層加功能」的需求時，先問這個語言有沒有更輕的表達方式。

它與中介軟體管線是同一個思路：Web 框架的中介軟體（記錄、認證、壓縮、錯誤處理層層包住處理器）本質上就是裝飾者，只是換了名字與更符合語境的 API。認出這個對應關係，能讓你在設計自己的可插拔流程時直接借用成熟的做法——例如提供明確的註冊順序、以及讓每一層都能決定是否繼續往下傳。

## 面試回答方式

用**組合爆炸**開場——四個功能用繼承要十六個類別，這個具體的數字最有說服力。接著說明裝飾者把組合移到執行期，並定位它為「組合優於繼承」的經典實例。誠實給出三個代價：層數多難除錯、建立囉嗦、**順序有語意但型別系統不擋**。加分點有三個：先壓縮再加密與反過來的結果差異巨大，緩解方式是用工廠方法封裝正確的組合；現代語言中裝飾者常表現為高階函式的組合，比類別形式輕量；以及指出 Web 框架的中介軟體就是同一個思路，認出這個對應能直接借用成熟做法。

## 講稿

因為功能是可以自由組合的。串流可能要緩衝、可能要壓縮、可能要加密、可能要轉成字元。

如果用繼承來表達，每一種組合都要一個子類別。四個功能就是十六種組合，類別數量隨功能數指數成長，而且新增一個功能要新增一整批子類別。

裝飾者把每個功能做成一個實作相同介面的包裝，組合就在執行期完成。要緩衝就包一層緩衝，要壓縮就再包一層。這是組合優於繼承最經典的實例。

代價也很明確。物件層數多，除錯的時候堆疊很深。建立方式囉嗦，一長串巢狀的建構呼叫。還有順序有語意這一點最容易踩。

先壓縮再加密跟先加密再壓縮，結果差非常多。先壓縮的話壓縮率正常，先加密的話幾乎壓不動，因為加密後的資料接近隨機。但型別系統完全不會阻止你寫錯。這是裝飾者的固有弱點，它把組合的自由交給使用方，也就把正確組合的責任交出去了。所以我會提供工廠方法封裝正確的順序，讓多數使用者不必自己組。

另外我想補一點，Web 框架的中介軟體本質上就是裝飾者，只是換了名字。認出這個對應之後，設計自己的可插拔流程就可以直接借用成熟的做法。

## 常見追問

### 裝飾者和繼承什麼時候該選哪個？

**核心答案**：功能正交且需要自由組合用裝飾者，功能是固定的變體用繼承。裝飾者的優勢在於組合的自由度與執行期的彈性，代價是層數與順序的複雜度。如果實際上只有兩三種固定的組合、而且不會再增加，用繼承或直接寫幾個類別反而更直白。判斷方式是問「**這些功能會不會被任意組合**」——會的話裝飾者划算，不會的話它的複雜度是白付的。

**詳細解析**：另一個常被忽略的因素是功能之間有沒有依賴或順序約束。裝飾者假設各層是獨立的、可以任意排列；一旦有「A 必須在 B 之前」或「用了 A 就不能用 C」這類約束，裝飾者無法在型別上表達，只能靠文件與執行期檢查——這時它的表達力反而不足，可能該考慮明確的管線設定或建造者來組裝。認得出這個界線很重要，因為硬套裝飾者到有約束的場景，會產生「看起來很有彈性但實際上一組錯就出事」的設計。

**面試回答方式**：給出「功能正交可自由組合用裝飾者、固定變體用繼承」的判準與具體問法。加分點是指出功能之間有依賴或順序約束時裝飾者的表達力不足，應改用明確的管線設定或建造者，避免「看起來有彈性但一組錯就出事」。

### Java IO 的設計現在看起來有什麼問題？

**核心答案**：**建立方式囉嗦**（讀一個文字檔要包三四層）與**位元組流和字元流的分裂**（兩套平行的類別階層，還需要橋接器轉換）是最常被詬病的。這使得最常見的操作反而寫起來最麻煩，違反了「常見的事應該最簡單」的原則。後來的版本補上了**簡潔的工具方法**（一行讀取整個檔案或逐行處理），本質上就是**用工廠方法封裝常見組合**——這正好印證了裝飾者需要搭配便利入口的觀點。

**詳細解析**：這個演進的教訓值得記住：一個彈性極高的 API 如果沒有為常見情境提供捷徑，使用者會覺得它難用，即使它的設計在原理上是優雅的。好的函式庫設計通常是「簡單的事情簡單做，複雜的事情做得到」——提供一個覆蓋八成情境的便利方法，同時保留底層的組合能力給需要的人。這個原則不只適用於 IO，也適用於你自己設計的任何 API。能從一個經典的設計中提煉出可遷移的原則，比單純批評它有價值得多。

**面試回答方式**：指出建立囉嗦與位元組字元分裂兩個問題，並說明後來的便利方法本質上是用工廠封裝常見組合。加分點是提煉出通用原則——「簡單的事簡單做、複雜的事做得到」，並指出這適用於自己設計的任何 API。

### 怎麼避免裝飾者層數過深造成的除錯困難？

**核心答案**：三個做法。**限制層數**——多數情況三層以內足夠，超過通常代表職責劃分有問題。**用工廠方法封裝常見組合**——使用方拿到的是一個有意義名稱的結果，而不是自己堆一串。**在每一層加上可識別的資訊**——例如讓每個裝飾者的字串表示包含自己的名稱與被裝飾者，這樣印出來就能看出完整的組合，排查時省下大量猜測。

**詳細解析**：第三點特別實用但很少人做——一個包了五層的物件，若能直接印出「緩衝的（壓縮的（檔案的））」這樣的結構，排查時的效率差異很大。同樣的思路也適用於**記錄與追蹤**：讓每一層在出錯時把自己的身分加進錯誤訊息，比只看到最內層的例外有用得多。另外要注意**效能**——每一層都是一次額外的方法呼叫，在極熱的路徑上層數過多會有可量測的成本，但這通常不是主要問題，可讀性與正確性才是。這個「先顧正確與可讀、效能有量測到再說」的順序值得表達。

**面試回答方式**：給三個做法，重點展開第三點——讓每層的字串表示包含自己與被裝飾者，排查時能直接看出完整組合。加分點是延伸到錯誤訊息也該帶上每層的身分，以及提到效能成本但強調可讀性與正確性優先、效能要量測到才處理。
