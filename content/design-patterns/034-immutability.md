# 題目

為什麼「預設不可變」是一個好的建議？什麼時候該例外？

## 核心答案

**不可變帶來四個具體的好處**。**執行緒安全**——不會被修改的東西不需要同步。**沒有意外的副作用**——傳給一個方法之後，你確定它沒有被改。**可以安全地共享與快取**——**不需要防禦性拷貝**。以及可以安全地作為 Map 的 key 或 Set 的元素——**因為 hash 不會改變。**

這四個好處的共同點是「它們消除了一整類的問題而非優化某個指標」——而那正是「預設不可變」值得作為預設的原因。

**該例外的情況有三類**。**大型物件的頻繁修改**——**每次複製的成本不可接受**（而解法通常是持久化資料結構或建構期可變）。**與框架的相容**——ORM、序列化框架常常要求無參建構子與 setter。以及「本質上就是可變狀態」的東西——**快取、連線池、統計計數器。**

## 詳細解析

**「防禦性拷貝的成本常被忽略」**：一個回傳內部 List 的 getter——如果不拷貝，呼叫方能修改你的內部狀態；而如果每次都拷貝，那個成本在頻繁呼叫時可觀。**不可變讓這個兩難消失**：內部的 List 是不可變的，直接回傳它既安全又零成本。所以「不可變其實常常比可變更快」——因為它省下了所有的防禦性拷貝；而那個節省往往超過了「修改時要建新物件」的成本。

「建構期可變、使用期不可變」是處理複雜物件的標準做法：Builder 模式的核心價值之一——在建構過程中逐步設定（可變），`build()` 之後產生一個不可變的物件。於是既有建構的靈活性，又有使用的安全性。而它也解決了「不可變物件的建構子參數太多」這個問題。

「不可變不等於 final 欄位」是一個常見的誤解：一個 `final List<String> items` 的欄位——參考不能變，但 List 的內容可以被修改；於是那個物件仍然是可變的（淺不可變）。真正的不可變需要「所有欄位都是不可變的型別，或者在建構時做防禦性拷貝並在 getter 中回傳不可變視圖」。這個「淺 vs 深」的區別在實作時必須明確處理，否則不可變只是一個假象。

**「不可變讓某些設計變得自然」**：值物件、事件、以及函數式的狀態轉換——**它們都天然是不可變的**；而「歷史狀態仍然存在」讓比較、除錯、與回溯變得容易。所以「預設不可變」不只是防止 bug，還讓一些更好的設計成為可能——這是它比「加鎖」這類防禦性手段更根本的地方。

## 面試回答方式

先給四個好處並指出它們的共同點是消除一整類問題而非優化某個指標，再給三類該例外的情況。加分點有四個：**防禦性拷貝的成本常被忽略**——不可變讓那個兩難消失，所以它常常比可變更快；**建構期可變、使用期不可變**是處理複雜物件的標準做法，也解決了建構子參數太多的問題；**不可變不等於 final 欄位**——`final List` 的內容仍可被修改，真正的不可變需要處理深淺的區別；以及不可變讓某些設計變得自然（值物件、事件、函數式的狀態轉換），這是它比加鎖更根本的地方。

## 講稿

不可變帶來四個好處。執行緒安全、沒有意外的副作用、可以安全共享與快取、還有可以安全作為映射的鍵。這四個的共同點是它們消除了一整類的問題而不是優化某個指標，那正是預設不可變值得作為預設的原因。

而有一個常被忽略的點，不可變其實常常比可變更快。因為一個回傳內部集合的取值方法，如果不拷貝，呼叫方能修改你的內部狀態；而每次都拷貝的成本在頻繁呼叫時可觀。不可變讓這個兩難消失，直接回傳既安全又零成本。那個節省往往超過了修改時要建新物件的成本。

處理複雜物件的標準做法是建構期可變、使用期不可變。建造者模式在建構過程中逐步設定，完成之後產生一個不可變的物件。既有建構的靈活性又有使用的安全性。

還有一個常見的誤解要澄清。不可變不等於欄位加上最終修飾。一個最終的集合欄位，參考不能變但內容可以被修改，那個物件仍然是可變的。真正的不可變需要所有欄位都是不可變型別，或者在建構時做防禦性拷貝並回傳不可變視圖。

## 常見追問

### 記錄（record）與資料類別解決了什麼？

**核心答案**：它們消除了不可變物件的樣板成本。以前寫一個不可變的值物件需要：final 欄位、建構子、getter、equals、hashCode、toString——**幾十行**；**而 record 一行就完成**。這讓「用值物件表達領域概念」的成本從「要考慮一下」變成「隨手就做」——於是那個好的實踐真的被採用了。

**詳細解析**：「降低成本會改變實際的行為」是一個值得注意的規律：一個實踐即使被公認是好的——如果它的成本高，實際的採用率就低；而工具把成本降到接近零之後，採用率會顯著上升。record 對值物件、`var` 對區域變數的型別推斷、以及 async/await 對非同步程式碼——都是這個模式的例子。所以「語言與工具的改進」的價值不只在它們直接提供的能力，還在於它們讓某些好的實踐變得可行。而反過來，評估一個工具時應該問「它讓什麼原本太麻煩的事變得容易了」——那往往比它的功能清單更能說明它的價值。

**面試回答方式**：給它們消除的樣板成本與讓「用值物件表達領域概念」從「要考慮一下」變成「隨手就做」。核心加分點是提煉規律：**降低成本會改變實際的行為**——好的實踐如果成本高採用率就低，而工具把成本降到接近零後採用率顯著上升，並舉出同類例子。收在評估工具的方式：問「它讓什麼原本太麻煩的事變得容易了」比看功能清單更能說明價值。

### 不可變在集合上怎麼處理？

**核心答案**：**三個層次**。**不可變視圖**（`Collections.unmodifiableList`）——包裝一個可變的集合，修改會拋例外；但底層仍可被修改（如果有人持有原始參考）。**真正的不可變集合**（`List.of`、Guava 的 Immutable 系列）——建構後完全無法修改，也沒有底層的可變參考。**以及持久化資料結構**——「修改」產生一個新版本並共享未變的部分；**適合頻繁修改大型集合。**

**詳細解析**：**「不可變視圖的陷阱」值得知道**：它只是一個包裝——如果原始的集合仍然被某處持有並修改，那個「不可變視圖」的內容也會跟著變；於是它提供的是「呼叫方不能改」而非「內容不會變」。在需要真正保證的場景中（例如把一個集合作為 Map 的 key 或者跨執行緒共享），必須用真正的不可變集合或者做一次拷貝。這個「看起來安全但實際上不是」的情況，是不可變設計中最容易出錯的地方——而它的症狀是間歇性的、與時序相關的 bug，極難重現。

**面試回答方式**：給三個層次與各自的保證程度。核心加分點是**不可變視圖的陷阱**——它只是包裝，原始集合被修改時視圖的內容也會變，所以它提供的是「呼叫方不能改」而非「內容不會變」。收在後果：在需要真正保證的場景中必須用真正的不可變集合或做一次拷貝，而這個「看起來安全但實際不是」的情況症狀是間歇性、與時序相關的 bug，極難重現。

### 大量的不可變物件會不會造成 GC 壓力？

**核心答案**：通常不會，因為那些物件多數是短命的。現代的分代 GC 對「大量短命物件」的處理極為高效——年輕代的分配幾乎是指標移動，而回收只複製存活的那少數。真正造成壓力的是「大量存活到老年代的物件」——而那與可變或不可變無關，取決於物件的生命週期。

**詳細解析**：「不可變反而可能減少 GC 壓力」有一個具體的機制：可變的設計常常需要防禦性拷貝——**而那些拷貝也是物件分配**；不可變讓共享成為可能，於是同一個物件被多處引用而非被複製多次。在物件較大或者被頻繁傳遞的場景中，這個節省可能超過「修改時建新物件」的成本。而真正需要注意的是「在迴圈中建立大量中間物件」——例如字串的反覆串接（每次產生一個新字串）；那個問題的解法是「用 StringBuilder 這類建構期可變的工具」而非「放棄不可變」。這再次指向同一個模式：建構期可變、使用期不可變。

**面試回答方式**：回答通常不會並說明分代 GC 對短命物件極為高效，而壓力來自存活到老年代的物件，那與可變性無關。核心加分點是**不可變反而可能減少 GC 壓力**——可變設計的防禦性拷貝也是分配，而不可變讓共享取代複製。收在真正需要注意的情況與解法：迴圈中的大量中間物件（例如字串反覆串接），解法是用建構期可變的工具而非放棄不可變。
