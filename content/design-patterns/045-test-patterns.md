# 題目

測試替身有哪幾種？什麼時候用哪一種？

## 核心答案

五種，而混用術語是常見的問題。**Dummy**——只是為了填參數，永遠不被使用。**Stub**——**回傳預設好的值，不驗證互動**。**Spy**——記錄被怎麼呼叫，測試後可以檢查。**Mock**——預先設定期望的互動，不符合就失敗。**Fake**——**一個簡化但可運作的實作**（記憶體中的 Repository）。

選擇的原則是「盡量用真實的，不行才用 Fake，最後才用 Mock」。因為 Mock 把「實作的細節」寫進了測試——於是重構（改變呼叫的方式但行為不變）會讓測試失敗；而那是「測試阻礙重構」這個常見痛點的主要來源。

**而 Fake 的價值被嚴重低估**：一個記憶體的 Repository 寫一次、所有測試都能用、而且測試讀起來像業務描述（存進去、查出來）——比每個測試各自設定 mock 清楚得多。

## 詳細解析

「過度使用 mock 讓測試變成實作的複本」：`verify(repo).findById(1); verify(repo).save(any())`——這個測試驗證的是「程式碼做了什麼呼叫」而非「它達成了什麼」；於是任何重構都會讓它失敗，而它也不會在行為真的錯了時給出有用的訊息。判斷的方式是問「如果我用另一種方式實作同樣的行為，這個測試還會通過嗎」——不會的話，那個測試綁得太緊了。

**「什麼時候 mock 是對的」也要說清楚**：驗證「與外部系統的互動」確實發生了（例如「訂單完成後確實發出了通知」）——那個互動本身就是被測的行為；**以及「模擬難以觸發的情況」**（網路錯誤、逾時）。**這兩種情況下 mock 是恰當的工具**——而它們的共同點是「互動本身是規格的一部分」。

「測試資料的建構」是另一個容易失控的地方：每個測試各自 `new Order(...)` 加上十個參數——於是新增一個必填欄位要改幾十個測試；而測試的意圖也被那些無關的參數淹沒。**兩個模式解決它**：**Object Mother**（一個提供典型物件的工廠，`OrderMother.pendingOrder()`）與**Test Data Builder**（`anOrder().withStatus(SHIPPED).build()`，未指定的用合理的預設）。後者更靈活，而它讓測試只寫出「與這個測試相關的那些欄位」——**於是意圖立刻清晰。**

「測試的可讀性比生產程式碼更重要」是一個值得強調的立場：因為測試是「規格的可執行形式」——它應該能被閱讀來理解系統的行為；而一個充滿 mock 設定與無關參數的測試無法承擔那個角色。所以在測試中投入可讀性（用 builder、用有意義的名字、用 given-when-then 的結構）是有明確回報的。

## 面試回答方式

先給五種測試替身的區分，再給選擇的原則（盡量用真實的、不行用 Fake、最後才用 Mock）與理由（**Mock 把實作細節寫進測試**）。加分點有四個：過度使用 mock 讓測試變成實作的複本，判斷是問「用另一種方式實作同樣的行為，這個測試還會通過嗎」；**什麼時候 mock 是對的**——驗證與外部的互動、模擬難以觸發的情況，共同點是互動本身是規格的一部分；**測試資料的建構容易失控**與兩個模式（Object Mother、Test Data Builder），後者讓測試只寫出相關的欄位；以及測試的可讀性比生產程式碼更重要，**因為它是規格的可執行形式**。

## 講稿

測試替身有五種，而混用術語是常見的問題。虛設物件只是為了填參數。存根回傳預設好的值。間諜記錄被怎麼呼叫。模擬物件預先設定期望的互動。而假物件是一個簡化但可運作的實作。

選擇的原則是盡量用真實的，不行才用假物件，最後才用模擬物件。因為模擬把實作的細節寫進了測試，於是重構會讓測試失敗，而那是測試阻礙重構這個痛點的主要來源。

判斷的方式是問，如果我用另一種方式實作同樣的行為，這個測試還會通過嗎。不會的話那個測試綁得太緊了。

而假物件的價值被嚴重低估。一個記憶體的儲存庫寫一次、所有測試都能用，而且測試讀起來像業務描述，存進去查出來，比每個測試各自設定模擬清楚得多。

另一個容易失控的地方是測試資料的建構。每個測試各自建構一個帶十個參數的物件，於是新增一個必填欄位要改幾十個測試，而測試的意圖也被無關的參數淹沒。解法是用測試資料建造者，讓測試只寫出跟這個測試相關的那些欄位，未指定的用合理的預設，於是意圖立刻清晰。

## 常見追問

### 該不該 mock 資料庫？

**核心答案**：**通常不該**。因為 Repository 的價值正是「SQL 或 ORM 映射是對的」——**mock 它等於什麼都沒測**。正確的做法是「用一個真實的資料庫做整合測試」（容器化的測試資料庫、或者輕量的內嵌資料庫），而業務邏輯的測試用記憶體的 Fake Repository。

**詳細解析**：「用內嵌資料庫代替真實資料庫」有一個要注意的陷阱：H2 與 PostgreSQL 的行為不同（SQL 方言、型別、以及某些函數）——於是「測試通過但生產失敗」是可能的；而那類問題往往出現在比較複雜的查詢上。所以在使用了資料庫特有功能的專案中，用容器化的真實資料庫（Testcontainers）比內嵌的可靠得多——而它的成本（啟動時間）在現代的硬體上已經可以接受。這個「測試環境與生產環境的差異」是所有整合測試的核心風險——而縮小那個差異的投入通常是值得的，因為它換來的是「測試通過就真的能用」這個信心。

**面試回答方式**：明確回答通常不該並給理由（**mock 它等於什麼都沒測**），給出正確的分層。核心加分點是用內嵌資料庫代替真實的陷阱——方言與型別的差異讓「測試通過但生產失敗」成為可能，所以用容器化的真實資料庫更可靠且成本已可接受。收在原則：測試環境與生產環境的差異是所有整合測試的核心風險，縮小它換來的是「測試通過就真的能用」的信心。

### 測試替身的設定太複雜怎麼辦？

**核心答案**：那通常是被測程式碼的設計問題而非測試的問題。需要 mock 五個依賴才能測一個方法——**表示那個類別依賴太多**；需要設定十層的回傳值——表示呼叫鏈太深。所以「測試難寫」應該被當成一個設計的訊號而非一個要用工具克服的障礙。

**詳細解析**：「測試是設計的第一個使用者」是這個觀點的基礎：如果一個類別難以被測試——那它也難以被其他程式碼使用；因為兩者面對的是同一個介面。所以「為了讓它可測而做的改動」（減少依賴、注入而非自己建立、拆分責任）通常也讓生產程式碼更好。這正是 TDD 的一個核心主張：測試先行會自然地產生更好的設計——而即使不做 TDD，「測試難寫時先檢查設計」仍然是一個有價值的反射。而具體的改善方向通常是三個：拆分過大的類別、把靜態的呼叫改成注入的依賴、以及把「取得資料」與「處理資料」分開（後者讓純邏輯能被無依賴地測試）。

**面試回答方式**：把它定位成**設計問題而非測試問題**並給兩個具體的訊號。核心加分點是**測試是設計的第一個使用者**——難以測試的類別也難以被其他程式碼使用，因為面對的是同一個介面，所以為了可測而做的改動通常也讓生產程式碼更好。收在三個具體的改善方向，尤其是把「取得資料」與「處理資料」分開讓純邏輯能被無依賴地測試。

### 這些模式在測試金字塔中怎麼分配？

**核心答案**：**越往上越少用替身**。**單元測試**——大量使用 Fake 與 Stub，因為要隔離出被測的邏輯。**整合測試**——盡量用真實的元件，只對「外部系統」用替身（第三方 API、支付閘道）。**端到端測試**——幾乎不用替身，因為它驗證的正是「所有東西接起來能用」。

**詳細解析**：「每一層驗證不同的東西」是這個分配的依據：單元測試驗證邏輯的正確——**替身讓它聚焦且快**；整合測試驗證元件之間的接合（SQL 對不對、序列化對不對）——用替身就失去了意義；端到端驗證使用者的流程能走通。所以「在錯的層次用替身」的後果很具體：在整合測試中 mock 了資料庫，於是它退化成一個慢的單元測試，既沒有單元測試的速度也沒有整合測試的價值。這類「測試存在但不驗證任何有意義的東西」的情況比沒有測試更糟——**因為它給了虛假的信心**。而識別它的方式是問「如果這個元件的實作完全壞掉，這個測試會失敗嗎」。

**面試回答方式**：給三層的分配原則（**越往上越少用替身**）與各層的做法。核心加分點是**每一層驗證不同的東西**是分配的依據，並指出在錯的層次用替身的具體後果：整合測試中 mock 資料庫讓它退化成一個慢的單元測試。收在判斷：「測試存在但不驗證任何有意義的東西」比沒有測試更糟，因為它給了虛假的信心，而識別的方式是問「如果這個元件完全壞掉，這個測試會失敗嗎」。
