# 題目

Unit of Work 模式在做什麼？它與交易的關係是什麼？

## 核心答案

**Unit of Work 追蹤「這次業務操作中被改動的物件」，並在最後一次性地把它們寫回**——**於是應用層不需要逐個呼叫 save，而是「改完之後 commit」**。

**它解決三個問題**。**減少資料庫往返**——**多次修改被合併成一批寫入**。**保證一致性**——**要嘛全部寫入要嘛全部不寫**。**以及避免重複寫入**——**同一個物件在一次操作中被改了三次，只寫一次**。

**它與交易的關係是「Unit of Work 是應用層的概念，交易是資料庫層的機制」**——**前者決定「哪些變更屬於同一個工作單元」，後者保證那些變更的原子性**。**多數 ORM（Hibernate 的 Session、EF 的 DbContext）內建了這個模式**——**於是它常常是「被使用而不被察覺」的。**

## 詳細解析

**「Hibernate 的 Session 就是一個 Unit of Work」是理解它最直接的方式**：你載入一個實體、修改它的屬性、然後什麼都不做——**在交易提交時，Hibernate 會偵測到那個改動並自動發出 UPDATE**。**這就是「髒檢查」（dirty checking），而它正是 Unit of Work 的核心機制**。**很多人用了幾年 ORM 卻不知道這個機制的名字，於是在遇到「為什麼我沒呼叫 save 它卻更新了」時感到困惑。**

**「隱式的行為是它的雙面刃」**：好處是程式碼簡潔——**壞處是「什麼時候真的寫入了」變得不明顯**。**典型的問題是「在同一個交易中先修改再查詢，查到的是舊值還是新值」**（**取決於是否觸發了 flush**）；**以及「一個意外的修改被自動持久化」**（**例如在一個唯讀的操作中不小心改了實體的屬性**）。**所以在需要精確控制的場景中，明確地 flush 或者使用唯讀交易是必要的。**

**「一級快取」是同一個機制的另一面**：Unit of Work 需要追蹤物件——**於是它天然地維護了一個「已載入物件」的映射**；**同一個 ID 在同一個工作單元中只會被載入一次**。**這既是效能優化，也是「同一個實體在記憶體中只有一個實例」這個保證的來源**——**而後者對「物件的相等性判斷」很重要**。

**「工作單元的邊界應該與業務操作對齊」**：太大（例如一整個請求）——**會累積大量的追蹤物件，記憶體壓力上升且 flush 的成本高**；**太小（每次修改一個交易）——失去了一致性保證**。**而在 Web 應用中，「一個請求一個工作單元」是常見且合理的預設**——**但對批次處理，應該分批提交而非累積全部**。

## 面試回答方式

先給模式的做法（**追蹤被改動的物件並在最後一次性寫回**）與三個解決的問題，再說明**它是應用層的概念而交易是資料庫層的機制**，並指出**多數 ORM 內建它所以常被使用而不被察覺**。加分點有四個：**Hibernate 的 Session 就是一個 Unit of Work**——**髒檢查正是它的核心機制**，**而很多人不知道這個名字所以在「沒呼叫 save 卻更新了」時感到困惑**；**隱式行為的雙面刃**（先改再查的可見性、意外的修改被持久化）；**一級快取是同一個機制的另一面**，**它也是「同一個實體在記憶體中只有一個實例」的來源**；以及**邊界應該與業務操作對齊**，**批次處理要分批提交而非累積全部**。

## 講稿

這個模式追蹤這次業務操作中被改動的物件，在最後一次性寫回。於是應用層不需要逐個呼叫儲存，而是改完之後提交。

它解決三個問題。減少往返、保證一致性、還有避免重複寫入。

它跟交易的關係是，它是應用層的概念決定哪些變更屬於同一個工作單元，而交易是資料庫層的機制保證那些變更的原子性。

理解它最直接的方式是想 Hibernate 的工作階段。你載入一個實體、修改屬性、然後什麼都不做，在交易提交時它會偵測到改動並自動發出更新。這就是髒檢查，而它正是這個模式的核心機制。很多人用了幾年映射框架卻不知道這個機制的名字，於是在遇到為什麼我沒呼叫儲存它卻更新了的時候感到困惑。

而隱式的行為是雙面刃。好處是簡潔，壞處是什麼時候真的寫入變得不明顯。典型的問題是在同一個交易中先修改再查詢，查到的是舊值還是新值。所以在需要精確控制的場景中，明確地刷出或者使用唯讀交易是必要的。

還有邊界要跟業務操作對齊。批次處理應該分批提交而不是累積全部。

## 常見追問

### 為什麼有時候明明改了資料庫卻沒變？

**核心答案**：**四個常見原因**。**修改的物件不在工作單元的管理範圍內**（**detached 的實體，需要 merge**）。**交易被回滾了**（**可能是後續的操作拋了例外**）。**修改發生在唯讀交易中**（**被忽略或者拋錯**）。**以及「改了但沒有觸發髒檢查」**（**例如直接修改了集合的內部而 ORM 沒察覺**）。

**詳細解析**：**「detached 實體」是最常見也最容易混淆的**：一個實體從一個 Session 載入、Session 關閉之後——**它就與持久化上下文脫離了**；**此時修改它不會有任何效果**。**這在「跨層傳遞實體」的架構中特別容易發生**（Controller 拿到 Service 回傳的實體並修改它）。**正確的處理是「在有效的工作單元內完成修改」或者「明確地 merge 回去」**。**而更根本的建議是「不要把持久化實體傳出領域層」**——**用 DTO 傳遞資料，於是這一整類問題不會發生**。**這個「限制實體的作用域」的紀律，能消除掉 ORM 使用中相當比例的困惑。**

**面試回答方式**：給四個常見原因。核心加分點是**detached 實體最常見也最容易混淆**——**Session 關閉後修改它不會有任何效果，而這在跨層傳遞實體的架構中特別容易發生**。收在根本建議：**不要把持久化實體傳出領域層，用 DTO 傳遞資料**——**這個「限制實體作用域」的紀律能消除 ORM 使用中相當比例的困惑**。

### 批次處理時怎麼用 Unit of Work？

**核心答案**：**分批提交並清空持久化上下文**。處理十萬筆資料——**如果全部累積在一個工作單元中，記憶體會爆掉而且 flush 極慢**；**正確的做法是「每一千筆 flush 並 clear 一次」**（Hibernate 的 `session.flush()` 加 `session.clear()`）。**而如果不需要 ORM 的追蹤，直接用批次的 SQL 或 JDBC 更快。**

**詳細解析**：**「批次處理與 ORM 的設計目標本來就不匹配」**：ORM 為「操作少量物件並追蹤它們」而設計——**而批次處理是「大量資料的簡單轉換」**；**用 ORM 做批次意味著付出物件映射與追蹤的成本卻用不到它的好處**。**所以「批次用原生 SQL 或專門的批次框架」是一個明確的判斷，而非退化**。**而如果必須用 ORM（例如需要領域邏輯的驗證），那分批加清空是必要的紀律**——**同時要注意「clear 之後所有的實體都變成 detached」，於是不能再持有它們的參考**。**這類「工具的適用邊界」的認知，比熟練使用工具本身更能避免問題。**

**面試回答方式**：給分批提交與清空的做法。核心加分點是指出**批次處理與 ORM 的設計目標本來就不匹配**——**ORM 為操作少量物件而設計，用它做批次是付出成本卻用不到好處**，**所以「批次用原生 SQL」是明確的判斷而非退化**。收在必須用時的紀律：**分批加清空，而 clear 之後所有實體變成 detached 不能再持有參考**。

### 微服務中每個服務都有自己的 Unit of Work，跨服務怎麼辦？

**核心答案**：**沒有跨服務的 Unit of Work**——**因為它依賴單一資料庫的交易**。**跨服務的一致性必須用 Saga 或者事件驅動的最終一致**：**每個服務在自己的工作單元中完成本地的變更並發出事件，其他服務消費事件做自己的變更**。**而「本地變更與事件發送的原子性」用 Outbox 模式解決。**

**詳細解析**：**「Outbox 模式與 Unit of Work 配合得很自然」**：在同一個交易中把「業務資料的變更」與「一條待發送的事件」一起寫入——**於是它們原子地成功或失敗**；**而一個獨立的程序負責把 outbox 表中的事件真正發出去**。**這讓「本地交易」與「訊息發送」這兩件本來無法原子的事，透過「都變成本地寫入」而變得原子**。**這個「把跨系統的問題轉換成單系統的問題」的技巧很優雅**——**而它的代價是事件的發送有延遲（取決於輪詢的頻率或 CDC 的延遲）**。**理解這個模式，能解釋為什麼「先寫資料庫再發訊息」與「先發訊息再寫資料庫」都有問題，而 Outbox 是那個正確的第三條路。**

**面試回答方式**：明確回答**沒有跨服務的 Unit of Work**並給替代（Saga 或事件驅動的最終一致），指出**原子性用 Outbox 解決**。核心加分點是說明 **Outbox 與 Unit of Work 配合得很自然**——**在同一個交易中寫業務資料與待發事件，讓兩件本來無法原子的事透過「都變成本地寫入」而變得原子**，**這是「把跨系統的問題轉換成單系統的問題」的技巧**。收在價值：**它解釋了為什麼「先寫再發」與「先發再寫」都有問題**。
