# 題目

設計一個內部框架或函式庫時，該怎麼決定它的靈活性？

## 核心答案

先分清「函式庫」與「框架」，因為它們的設計原則不同。

**函式庫**——**你呼叫它**；設計的重點是「清晰的 API 與最小的假設」；它不強加架構，於是使用者保有控制權。

**框架**——**它呼叫你**（控制反轉）；設計的重點是「明確的擴充點與清楚的生命週期」；它強加了一個結構，換來的是省下大量的樣板。

而靈活性的判斷有一條實用的原則：「讓簡單的事情簡單，讓複雜的事情可能」。具體是「提供一個好用的預設路徑，同時允許在需要時下潛到更低的層次」——而不是「提供一百個可設定的選項讓每個人都要做決定」。

因為每一個擴充點都是一個要被文件化、被測試、被永久維護的承諾——所以它的數量應該由「已經出現的真實需求」決定，而非由「可能的需求」決定。

## 詳細解析

「分層的 API」是「簡單的事簡單、複雜的事可能」的具體實作：最上層是一個「一行就能用」的門面——**多數使用者只需要它**；**中層暴露主要的可設定項**；而底層是完整的能力（可能較繁瑣但無所不能）。於是「多數人不需要學習全部，而少數有特殊需求的人不會被擋住」。這個分層在很多成功的函式庫中都能看到——而它的反面是「只有一個扁平的、有五十個參數的 API」，那讓新手不知從何開始而專家仍然被限制。

「預設值的品質決定了框架的實際體驗」：一個需要設定十個東西才能跑起來的框架——**入門成本高**；而一個「零設定就能用，需要時再調整」的框架，讓使用者能立刻獲得價值。所以「合理的預設」不是一個小細節而是核心的設計工作——它要求設計者理解「多數使用者的多數場景是什麼」。Spring Boot 的成功很大程度上正是「自動設定」帶來的——它沒有增加 Spring 的能力，只是讓那些能力可以在零設定下被使用。

**「向後相容是框架最貴的承諾」**：一旦有人依賴了你的 API——**改變它就是破壞**；於是「早期暴露的每一個東西都成為長期的約束」。所以「先做小、確認有需求再開放」比「先暴露一切、之後再收回」安全得多——因為前者的錯誤是「使用者要求更多」而後者的錯誤是「使用者的程式碼壞掉」。這也是為什麼成熟的框架會明確標示「內部 API」與「實驗性 API」——**它保留了改動的自由。**

「文件與錯誤訊息是框架的一部分」：一個功能強大但錯誤訊息含糊的框架——**實際的可用性很差**；因為使用者遇到問題時無法自行解決。所以「當使用者做錯時，框架能不能告訴他錯在哪、該怎麼改」是評估框架品質的一個核心維度——而它在設計時經常被排在功能之後。

## 面試回答方式

先分清函式庫與框架的設計原則差異，再給「讓簡單的事情簡單，讓複雜的事情可能」這條原則與它的具體含義，並指出每個擴充點都是永久的維護承諾。加分點有四個：分層的 API 是那條原則的具體實作——**上層一行可用、底層完整能力**，反面是一個有五十個參數的扁平 API；**預設值的品質決定實際體驗**——Spring Boot 的成功很大程度是自動設定帶來的，它沒有增加能力只是讓能力在零設定下可用；**向後相容是最貴的承諾**——「先做小再開放」比「先暴露再收回」安全，因為前者的錯誤是使用者要求更多而後者是使用者的程式碼壞掉；以及文件與錯誤訊息是框架的一部分。

## 講稿

我會先分清函式庫跟框架，因為設計原則不同。函式庫是你呼叫它，重點是清晰的介面與最小的假設。框架是它呼叫你，重點是明確的擴充點與清楚的生命週期，它強加了一個結構，換來省下大量樣板。

而靈活性的判斷有一條實用的原則，讓簡單的事情簡單，讓複雜的事情可能。具體是提供一個好用的預設路徑，同時允許在需要時下潛到更低的層次，而不是提供一百個選項讓每個人都要做決定。

因為每一個擴充點都是一個要被文件化、被測試、被永久維護的承諾。所以它的數量應該由已經出現的真實需求決定，而不是由可能的需求決定。

具體的實作是分層的介面。最上層是一行就能用的門面，多數使用者只需要它。中層暴露主要的可設定項。底層是完整的能力。於是多數人不需要學習全部，而少數有特殊需求的人不會被擋住。

還有一點，預設值的品質決定了框架的實際體驗。一個零設定就能跑的框架讓使用者立刻獲得價值。Spring Boot 的成功很大程度上正是自動設定帶來的，它沒有增加能力，只是讓那些能力可以在零設定下被使用。

## 常見追問

### 內部框架與開源框架的設計有什麼不同？

**核心答案**：內部框架可以更激進地改動，也應該更貼近具體的場景。因為使用者都在同一個組織中——你能知道所有的呼叫方、能協調升級、也能直接問他們需要什麼；於是「先做窄、按實際需求擴展」的成本很低。而開源框架面對未知的使用者，必須更保守、更通用、也更重視文件。

**詳細解析**：「內部框架最常見的失敗是過度通用化」：團隊想像「未來會有很多使用者，所以要做得通用」——於是建立了大量的抽象與擴充點；而實際上只有三個團隊在用，而且他們的需求高度相似。結果是「複雜度換來了沒有被使用的靈活性」。正確的做法是「先服務現有的兩三個使用者，做到最好」——而當第四個有不同需求的使用者出現時，再考慮擴展。這與「重構到模式」是同一個原則，只是作用在框架的層次。而一個實用的檢驗是「這個擴充點現在有幾個實作」——只有一個的話，它可能還不需要成為擴充點。

**面試回答方式**：給核心差異（內部可以更激進、更貼近具體場景，因為能知道所有呼叫方）。核心加分點是內部框架最常見的失敗是過度通用化——想像未來會有很多使用者於是建立大量抽象，而實際上只有三個團隊且需求相似，結果是複雜度換來沒被使用的靈活性。收在正確做法與檢驗：先服務現有的使用者做到最好，第四個有不同需求時再擴展；而「這個擴充點現在有幾個實作」是實用的檢驗。

### 怎麼設計一個好的錯誤訊息？

**核心答案**：**回答三個問題**。**發生了什麼**（具體的、不含內部術語的描述）。**為什麼**（可能的原因，尤其是最常見的那個）。**以及該怎麼辦**（具體的下一步，最好包含一個範例或一個連結）。而最重要的是「用使用者的視角描述而非用實作的視角」——「找不到名為 X 的 bean」對懂 Spring 的人有用，而對新手只是一串術語。

**詳細解析**：「好的錯誤訊息能大幅降低支援成本」：一個模糊的訊息會產生一個支援請求——而一個能指出「你可能忘了加上某某註解，範例如下」的訊息讓使用者自行解決；在有很多使用者的框架中，這個差別是數量級的。而寫好錯誤訊息的實用方法是「從真實遇到的問題反推」：每次有人來問「為什麼會這樣」，就檢查那個錯誤訊息能不能自己回答那個問題——**不能的話就改善它**。這個「用支援請求驅動錯誤訊息的改善」的循環，比一開始就試圖寫出完美的訊息更有效，**因為它作用在真實的困惑上。**

**面試回答方式**：給三個要回答的問題與用使用者的視角而非實作的視角這個關鍵。核心加分點是好的錯誤訊息能大幅降低支援成本——在有很多使用者的框架中差別是數量級的。收在實用的方法：**從真實遇到的問題反推**，每次有人問「為什麼會這樣」就檢查那個訊息能不能自己回答——這個循環比一開始就試圖寫出完美的訊息更有效，因為它作用在真實的困惑上。

### 框架該不該強加架構？

**核心答案**：**看它要解決的問題有多明確**。一個「約定優於設定」的框架（Rails、Spring Boot）——強加了一套結構，換來的是「不需要做那些決定」與「所有專案長得一樣，換人接手容易」；而一個不強加架構的函式庫給了自由，代價是每個團隊要自己建立那些約定，而它們往往不一致。

**詳細解析**：「約定的價值隨團隊規模與流動性上升」：一個穩定的小團隊——自己的約定就夠，而框架的約束可能反而礙事；而一個大的、人員會流動的組織——「所有專案都用同樣的結構」讓知識可以遷移、讓工具可以通用、也讓新人的上手時間大幅縮短。所以「強加架構」的價值不在技術上而在組織上——這也解釋了為什麼企業環境特別偏好有強約定的框架。而它的代價是「當你的需求不符合那個約定時會非常痛苦」——於是評估時應該問「我的場景是不是那個框架設想的典型場景」：是的話它省下大量工作，不是的話你會一直在對抗它。

**面試回答方式**：給判斷（**看要解決的問題有多明確**）與兩種取向的取捨。核心加分點是約定的價值隨團隊規模與流動性上升——穩定的小團隊自己的約定就夠，而大的、人員流動的組織讓知識可遷移、工具可通用、新人上手快，所以「強加架構」的價值不在技術上而在組織上。收在評估的問題：「我的場景是不是那個框架設想的典型場景」——是的話省下大量工作，不是的話會一直在對抗它。
