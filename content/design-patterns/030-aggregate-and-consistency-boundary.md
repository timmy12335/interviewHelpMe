# 題目

聚合是什麼？邊界該怎麼劃？

## 核心答案

**聚合是「一組必須一起保持一致的物件」**——**它有一個根（aggregate root），外部只能透過根來存取內部**；**而「一個交易只修改一個聚合」是它的核心約束**。

**劃邊界的判準是「不變量」**：**哪些規則必須立即成立？** 例如「訂單的總金額必須等於明細之和」——**那麼訂單與明細必須在同一個聚合中**；**而「使用者的累計消費金額」不需要立即準確——那就不該被拉進訂單的聚合**。

**邊界的大小是一個取捨**。**大聚合**——**一致性容易保證，但併發衝突多（兩個人改同一個訂單的不同明細會互相阻塞）且載入成本高**。**小聚合**——**併發好、效能好，但跨聚合的一致性需要用最終一致來達成。**

**而 DDD 的建議是「盡量小」**——**因為併發與效能的代價是持續的，而最終一致的複雜度是一次性的設計成本。**

## 詳細解析

**「一個交易只修改一個聚合」這個約束的理由**：它讓聚合成為一個天然的分片單位——**於是「這個系統能不能被拆分」有了明確的答案**；**而在單體階段，它也避免了「一個交易鎖住大量資料」的併發問題**。**很多團隊在單體階段忽略這個約束（因為資料庫交易很方便，跨聚合修改沒有立即的代價）**——**而在拆分服務時才發現「這兩個東西被綁在一起了」**。**所以它是一個「現在遵守以換取未來的選項」的紀律。**

**「用 ID 引用其他聚合」是這個約束的具體實踐**：訂單不該持有一個 `Customer` 物件——**而該持有 `customerId`**；**於是載入訂單不會連帶載入客戶，而修改訂單也不可能意外地修改客戶**。**這個小小的規則消除了一整類的問題**（**意外的級聯載入、意外的級聯修改、以及聚合邊界的模糊**）。

**「跨聚合的一致性用領域事件」**：訂單完成之後要更新客戶的累計消費——**不在同一個交易中做，而是發出一個 `OrderCompleted` 事件，由另一個處理器更新客戶**。**於是兩個聚合各自在自己的交易中被修改**，**而一致性在短時間內達成**。**代價是「中間有一個不一致的窗口」**——**而多數業務規則能容忍那個窗口（幾秒鐘的累計金額不準通常沒有影響）**。

**「如果不變量真的跨聚合怎麼辦」**：例如「一個帳戶的餘額不能為負，而扣款涉及兩個帳戶」——**那有三種選擇**：**合併成一個聚合（如果它們確實不可分）**、**用悲觀鎖或分散式鎖保護那個不變量**、**或者「允許暫時違反並補償」**（先扣、發現不足再回滾）。**而第三種在很多場景中是實際的選擇**——**因為違反的機率低而補償的成本可接受。**

## 面試回答方式

先給聚合的定義與**「一個交易只修改一個聚合」這個核心約束**，再給**用不變量劃邊界**的判準與大小的取捨，並指出 **DDD 建議盡量小**的理由。加分點有四個：**那個約束的理由**——**它讓聚合成為天然的分片單位**，**而很多團隊在單體階段忽略它，拆服務時才發現東西被綁在一起**；**用 ID 引用其他聚合**——**這個小規則消除了意外的級聯載入與修改**；**跨聚合的一致性用領域事件**與它的窗口代價；以及**不變量真的跨聚合時的三種選擇**，**而「允許暫時違反並補償」在很多場景中是實際的選擇**。

## 講稿

聚合是一組必須一起保持一致的物件，它有一個根，外部只能透過根來存取內部。而核心的約束是一個交易只修改一個聚合。

劃邊界的判準是不變量。哪些規則必須立即成立？訂單的總金額必須等於明細之和，那訂單跟明細必須在同一個聚合。而使用者的累計消費不需要立即準確，那就不該被拉進來。

大小是一個取捨。大聚合一致性容易保證但併發衝突多而且載入成本高，小聚合併發好效能好但跨聚合的一致性要用最終一致。而建議是盡量小，因為併發與效能的代價是持續的，最終一致的複雜度是一次性的設計成本。

那個約束的理由是它讓聚合成為天然的分片單位，於是這個系統能不能被拆分有了明確的答案。很多團隊在單體階段忽略它，因為資料庫交易很方便、跨聚合修改沒有立即的代價，而在拆分服務時才發現這兩個東西被綁在一起了。所以它是一個現在遵守以換取未來選項的紀律。

具體的實踐是用編號引用其他聚合而不是持有物件。這個小規則消除了意外的級聯載入跟級聯修改。

## 常見追問

### 聚合太大導致併發衝突怎麼辦？

**核心答案**：**三個方向**。**拆小**——**重新檢視「這些東西真的需要立即一致嗎」，多數情況下不需要**。**細化鎖的粒度**——**如果用樂觀鎖，把版本號放在真正衝突的那個部分而非整個聚合**。**以及改變操作的形狀**——**例如「加一筆明細」不需要載入整個訂單並重寫，可以用一個只追加的操作**。

**詳細解析**：**「操作的形狀決定了衝突的機率」**：如果每次修改都是「讀出整個聚合、改一點、寫回全部」——**那麼任何兩個併發的修改都會衝突**；**而如果操作能表達成「對某個部分的增量變更」，那只有真正修改同一部分的操作才衝突**。**這正是事件溯源的一個優勢**：**「追加一個事件」天然不與其他的追加衝突**（**除非它們違反了同一個不變量**）。**所以「聚合太大」的問題有時候不是邊界劃錯了，而是「操作被表達成了粗粒度的讀改寫」**——**而改變操作的表達方式比重劃邊界成本低得多**。**這個角度在遇到併發問題時值得先檢查。**

**面試回答方式**：給三個方向。核心加分點是**操作的形狀決定了衝突的機率**——**「讀出整個聚合、改一點、寫回全部」讓任何併發修改都衝突，而增量變更只有改同一部分才衝突**，**這正是事件溯源的一個優勢**。收在實用的判斷：**「聚合太大」有時不是邊界劃錯而是操作被表達成粗粒度的讀改寫**，**而改變表達方式比重劃邊界成本低得多**。

### 聚合根怎麼決定？

**核心答案**：**選「外部最常引用的那個」與「生命週期涵蓋其他成員的那個」**。訂單與明細——**明細不會脫離訂單獨立存在，而外部總是先找到訂單**；**所以訂單是根**。**判斷的檢驗是「能不能刪除根而保留成員」**——**如果不能（成員沒有獨立的意義），那根選對了。**

**詳細解析**：**「一個常見的錯誤是把所有相關的東西都拉進一個聚合」**：訂單、客戶、商品、庫存——**它們在業務上相關，但它們的生命週期與不變量是獨立的**；**把它們放在一個聚合中會讓那個聚合巨大且無法併發修改**。**正確的判斷是「這兩個東西必須在同一個瞬間保持一致嗎」**——**訂單與它的明細是（總金額的不變量），訂單與商品不是（商品改價不影響已下的訂單）**。**而「相關」與「必須一致」是兩個完全不同的概念**——**混淆它們是聚合劃分中最常見的錯誤**。**這個區分也解釋了為什麼「按資料庫的外鍵關係劃聚合」通常是錯的：外鍵表達的是「相關」而非「必須一致」。**

**面試回答方式**：給選擇的標準與檢驗方式（**能不能刪除根而保留成員**）。核心加分點是指出**常見的錯誤是把所有相關的東西都拉進一個聚合**，並給出正確的判斷：**「這兩個東西必須在同一個瞬間保持一致嗎」**，用訂單與明細、訂單與商品對比說明。收在關鍵區分：**「相關」與「必須一致」是完全不同的概念**，**這也解釋了為什麼按外鍵關係劃聚合通常是錯的**。

### 這套概念對沒有做 DDD 的專案有價值嗎？

**核心答案**：**有，尤其是「一致性邊界」這個思考方式**。即使不用聚合這個詞——**問「哪些資料必須一起改、哪些可以最終一致」仍然是設計交易與服務邊界時最有用的問題**。**而「用 ID 而非物件引用」這個小規則，在任何 ORM 專案中都能減少意外的級聯行為。**

**詳細解析**：**「這套概念的價值在它提供了一組明確的問題」**：不是「要不要用 DDD」——**而是「這個不變量必須立即成立嗎」「這兩個東西的生命週期一樣嗎」「這個交易涵蓋了什麼」**。**這些問題在任何架構下都要回答，而 DDD 只是提供了回答它們的詞彙與模式**。**所以採用的正確方式是「先用那些問題檢視現有的設計」**——**而往往會發現一些「本來就該分開卻被綁在一起」或者「本來需要一致卻被拆開」的地方**。**這種「用概念做診斷而非用它做重構」的方式，成本極低而且能立刻產出價值**——**而它也是判斷「這套方法論對我們有沒有用」最實際的試驗。**

**面試回答方式**：回答有並指出**「一致性邊界」這個思考方式**與**「用 ID 而非物件引用」這個小規則**在任何專案中的價值。核心加分點是提煉出**這套概念的價值在它提供了一組明確的問題**（必須立即成立嗎、生命週期一樣嗎、交易涵蓋了什麼），**而 DDD 只是提供回答它們的詞彙**。收在採用方式：**先用那些問題檢視現有設計**——**這種「用概念做診斷而非做重構」成本極低且能立刻產出價值**。
