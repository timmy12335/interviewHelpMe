# 題目

建造者模式解決什麼問題？參數多就一定要用它嗎？

## 核心答案

它解決的是**建構函式參數過多且多為可選**時的三個痛點：**可讀性差**（一長串參數看不出誰是誰，`new Order(1, 2, true, false, null)` 完全無法閱讀）、**容易傳錯**（相同型別的相鄰參數順序搞反不會有編譯錯誤）、以及**多載爆炸**（可選參數的組合需要大量多載建構函式）。建造者用**具名的方法逐步設定**取代位置參數，讀起來像在描述意圖；並在最後的建構步驟做**一次性的完整性驗證**，確保產出的物件必定合法。它還天然支援**不可變物件**——所有欄位在建構時決定、之後不可變更。但參數多不一定要用它：**參數少於四五個時**，有名稱的靜態工廠方法通常更輕；**語言支援具名參數或預設值時**，直接用語言特性比手寫建造者乾淨得多。所以判準是**參數數量加上可選程度，再扣掉語言本身提供的能力**。

## 詳細解析

**最後的驗證是被低估的價值**：分步設定的過程中物件是「不完整」的，只有呼叫建構方法時才產出真正的物件——這給了一個**集中驗證的時機**，可以檢查必填欄位是否齊全、欄位之間的關係是否合法（例如結束時間必須晚於開始時間）。相對地，用 setter 逐步設定一個可變物件時，物件在中途處於不合法狀態卻可能被其他程式碼看到，這是「半成品逸出」的典型問題。

**建造者天然適合不可變物件**：目標類別的欄位可以全部宣告為不可變、建構函式設為私有，只能透過建造者產生。這帶來執行緒安全、可安全地當作快取的鍵、以及易於推理的好處。這也是為什麼在強調不可變的現代風格中，建造者的使用反而增加了。

**必填與可選的表達**：一個常見的改良是**把必填參數放在建造者的建構函式中**，可選的才用設定方法——這樣編譯期就能保證必填欄位不會漏。更嚴格的做法是**分階段的介面**（設定完必填欄位才回傳能呼叫建構方法的型別），把順序與完整性都交給型別系統檢查，代價是類別數量增加，通常只在函式庫的公開 API 上才值得。

**不要為了鏈式呼叫而用建造者**：鏈式呼叫只是語法上的便利，本身不構成使用建造者的理由。如果物件是可變的、也沒有複雜的驗證，把 setter 改成回傳自身只是換了個寫法，並沒有解決任何實際問題，反而讓「這個物件是可變的」這件事變得不明顯。**手段與目的要分清楚**。

**程式碼產生工具讓成本大幅下降**：許多語言的註解處理器或 IDE 能自動產生建造者，手寫的樣板程式碼不再是負擔。這改變了取捨——過去「參數要多到一定程度才值得手寫建造者」，現在成本低了，門檻也就降低了。但要注意**自動產生不代表應該到處用**，多一層間接仍然是閱讀成本，判準仍然是參數的數量與可選程度。

## 面試回答方式

先給它解決的**三個痛點**（可讀性、容易傳錯、多載爆炸），這比講結構有說服力。接著主動提出**最後的一次性驗證**是被低估的價值——它確保產出的物件必定合法，避免「半成品逸出」。然後明確表態**參數多不一定要用它**：參數少於四五個時具名的靜態工廠更輕，語言支援具名參數時直接用語言特性更乾淨。加分點有三個：**把必填參數放在建造者的建構函式中**讓編譯期就能檢查；**不要為了鏈式呼叫而用建造者**，那只是語法便利不構成理由；以及**程式碼產生工具降低了成本**，但不代表該到處用。

## 講稿

它解決的是建構函式參數過多而且多半可選的時候，三個很實際的痛點。

第一是可讀性差，一長串參數根本看不出誰是誰。第二是容易傳錯，相同型別的相鄰參數順序搞反，編譯器不會報錯。第三是多載爆炸，可選參數的組合需要大量的多載建構函式。

建造者用具名的方法逐步設定取代位置參數，讀起來像在描述意圖。

不過我覺得它有個被低估的價值，就是最後那一次性的驗證。分步設定的過程中物件是不完整的，只有呼叫建構方法時才產出真正的物件，這給了一個集中驗證的時機，可以檢查必填欄位齊不齊、欄位之間的關係合不合法。相對地，用 setter 逐步設定一個可變物件的時候，物件在中途是不合法狀態卻可能被別人看到。

它也天然適合不可變物件，欄位全部設成不可變、建構函式私有，只能透過建造者產生。

但參數多不一定要用它。少於四五個的時候，有名稱的靜態工廠方法通常更輕。如果語言支援具名參數或預設值，直接用語言特性比手寫乾淨得多。

還有一點，不要為了鏈式呼叫而用建造者，那只是語法上的便利，不構成理由。

## 常見追問

### 建造者和 setter 差在哪？兩者都是逐步設定

**核心答案**：**產出的物件是否可變、以及中途狀態是否會逸出**。setter 直接修改一個已經存在的物件，所以該物件是可變的，而且在設定過程中它處於不完整或不合法的狀態卻已經可以被其他程式碼取用。建造者是**在一個暫存的建造者上累積設定，最後才產出目標物件**——目標物件從誕生那一刻就是完整且合法的，而且可以是不可變的。這個差別在多執行緒與快取場景中特別重要。

**詳細解析**：另一個實際差異是**驗證的時機**。用 setter 時，跨欄位的驗證（例如結束時間要晚於開始時間）不知道該放在哪個 setter 中——放在任何一個都會因為設定順序而誤判。建造者的建構方法提供了一個明確的「所有欄位都設定完畢」的時機，跨欄位驗證放在那裡最自然。所以當物件有**跨欄位的約束**時，建造者的價值特別明顯。反過來，如果物件本來就該是可變的（例如一個持續更新的狀態容器），用 setter 才是對的，硬套建造者反而不自然。

**面試回答方式**：用「產出物件是否可變、中途狀態是否逸出」把兩者分開。加分點是講驗證時機的差異——跨欄位驗證在 setter 中無處安放，建造者提供了明確的時機，並補上「物件本來就該可變時用 setter 才對」的反向情況。

### 怎麼保證必填欄位不會漏？

**核心答案**：三種強度。**最弱**是在建構方法中檢查並拋出例外——執行期才發現，但實作簡單。**中等**是把必填參數放進**建造者的建構函式**——想建立建造者就必須提供它們，編譯期就保證了。**最強**是**分階段的介面**：設定完第一組必填欄位才回傳能設定第二組的型別，全部設完才回傳能呼叫建構方法的型別，順序與完整性完全由型別系統檢查。強度越高，類別與介面數量越多。

**詳細解析**：實務上**中等強度通常是最好的平衡**——必填參數放建構函式既簡單又有編譯期保證，而且清楚表達了「這些是必要的」。分階段介面的成本很高（每個階段一個介面），只在**公開的函式庫 API** 上才值得，因為那裡的使用者無法看到內部實作、也無法快速修正誤用。要注意的是**必填的定義可能隨版本改變**——把某個欄位從可選改成必填是破壞相容性的變更，若它在建構函式中就更難調整。所以在快速演進的內部程式碼中，用執行期檢查配合清楚的錯誤訊息，反而比死板的編譯期約束更有彈性。這個取捨值得說出來。

**面試回答方式**：給三種強度並排序，明確推薦中等強度（必填放建造者建構函式）作為平衡。加分點是說明分階段介面只在公開函式庫值得，以及指出必填的定義會隨版本改變、放建構函式會讓調整更難，快速演進的內部程式碼用執行期檢查反而有彈性。

### 建造者要不要支援複製既有物件再修改？

**核心答案**：**很值得支援**，這是不可變物件的實用配套。不可變物件無法直接修改，所以「基於既有物件產生一個只改了某個欄位的新物件」是很常見的需求；如果沒有這個能力，使用方必須把所有欄位手動複製一遍，既囉嗦又容易在新增欄位時漏掉。標準做法是提供一個「從既有物件建立建造者」的方法，複製所有欄位後讓使用方只修改需要的部分。

**詳細解析**：這裡有一個容易被忽略的維護風險：**新增欄位時忘了在複製方法中加上它**——結果是複製產生的物件少了那個欄位的值，而且不會有任何錯誤提示，是典型的靜默 bug。防範方式是**用程式碼產生工具**（自動涵蓋所有欄位）或**加上測試**（驗證複製後的物件與原物件相等）。後者很容易寫且效果很好，值得作為慣例。這個模式在強調不可變的風格中極為常見，能主動提出它與它的維護風險，會顯示你實際用過不可變設計而不只是知道概念。

**面試回答方式**：明確說值得支援，並解釋不可變物件為什麼需要它。加分點是點出「新增欄位忘了加進複製方法」這個靜默 bug，並給兩個防範方式（程式碼產生工具、或一個驗證複製結果相等的測試）。
