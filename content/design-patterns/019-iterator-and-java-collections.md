# 題目

迭代器模式解決什麼問題？為什麼現在很少人手寫迭代器？

## 核心答案

它解決的是「**遍歷集合而不暴露內部結構**」——使用方只需要「還有沒有下一個、給我下一個」這兩個操作，不必知道底層是陣列、鏈結串列還是樹。價值有三個：**統一了不同集合的遍歷方式**（同一段程式碼能遍歷任何集合）、支援多個獨立的遍歷同時進行（每個迭代器各自維護位置）、以及**支援惰性求值**（元素在被要求時才產生，讓無限序列與串流處理成為可能）。現在很少人手寫，是因為它**已經被語言與標準庫吸收**——增強型的迴圈語法、產生器、串流 API 底層都是迭代器，使用者不必自己實作。但**理解它仍然必要**：迭代過程中修改集合為什麼會拋例外、串流為什麼是惰性的、自訂資料結構要怎麼支援標準的遍歷語法，這些都要靠它解釋。所以正確的說法是模式消失在視野中而非消失在系統中。

## 詳細解析

併發修改的例外來自迭代器的一致性檢查：多數集合的迭代器會記錄集合的修改次數，每次取下一個元素時檢查是否被改過——不一致就立刻拋出例外。這是**快速失敗**的設計：與其讓遍歷產生不可預期的結果（跳過元素、重複、無限迴圈），不如馬上報錯。所以「遍歷時不能修改集合」不是任意的限制，而是為了讓錯誤在發生點就被發現。要在遍歷中刪除元素，正確做法是**用迭代器自己的移除方法**（它會同步更新檢查用的計數），或先收集再批次處理。

惰性是迭代器最被低估的能力：一個迭代器不需要事先擁有所有元素，可以在被要求時才計算下一個。這讓**無限序列**（自然數、隨機數）與**串流處理**（一次只在記憶體中保留一個元素地處理大型檔案）成為可能。串流 API 的中間操作之所以不立即執行、要等終端操作才觸發，正是這個原理。理解惰性也解釋了一個常見困惑：為什麼在串流中間加上記錄卻沒有輸出——因為沒有終端操作，整條鏈根本沒有執行。

**外部迭代與內部迭代**：手動取得迭代器並逐個處理是**外部迭代**——控制權在使用方，可以隨時中斷、可以同時遍歷多個集合。傳一個函式讓集合自己遍歷是**內部迭代**（串流與各種高階函式）——控制權在集合，好處是實作可以優化（平行化、短路）、程式碼更宣告式。兩者各有適用：需要精細控制流程用外部，表達資料轉換用內部。

自訂資料結構要支援標準語法：實作標準的可迭代介面之後，自訂的結構就能被增強型迴圈直接使用，也能接進既有的工具。這是很小的成本卻帶來很好的整合性，設計自訂集合時值得做。要注意**迭代器應該是獨立的**——每次取得都回傳新的實例，若共用同一個實例會讓兩次遍歷互相干擾。

**它與其他模式的關係**：迭代器常與**組合模式**搭配（遍歷樹狀結構）與**訪問者模式**對照（迭代器讓使用方決定對每個元素做什麼，訪問者讓結構決定怎麼遍歷而操作由訪問者提供）。認出這些關係，能在設計自訂結構的遍歷方式時做出更好的選擇。

## 面試回答方式

先給它解決的問題（遍歷而不暴露內部結構）與三個價值，特別強調**惰性求值**——這是最被低估的能力，也是串流處理的基礎。接著回答「為什麼很少手寫」：**被語言與標準庫吸收了**，但理解它仍必要，因為併發修改例外、串流的惰性、自訂結構的遍歷都靠它解釋。加分點有三個：併發修改例外是快速失敗的刻意設計，遍歷中要刪除應該用迭代器自己的移除方法；**外部迭代與內部迭代的取捨**（精細控制 vs 宣告式與可優化）；以及串流沒有終端操作就不會執行，這個困惑正好由惰性解釋。

## 講稿

它解決的是遍歷集合而不暴露內部結構。使用方只需要還有沒有下一個、給我下一個這兩個操作，不用知道底層是陣列、鏈結串列還是樹。

價值有三個。統一了不同集合的遍歷方式。支援多個獨立的遍歷同時進行，每個迭代器各自維護位置。還有支援惰性求值，這個我覺得最被低估。

惰性的意思是迭代器不需要事先擁有所有元素，可以在被要求的時候才計算下一個。這讓無限序列跟串流處理變得可能，一次只在記憶體裡保留一個元素就能處理很大的檔案。串流的中間操作不立即執行、要等終端操作才觸發，就是這個原理。這也解釋了一個常見困惑，為什麼在串流中間加了記錄卻沒有輸出，因為沒有終端操作，整條鏈根本沒執行。

現在很少人手寫，是因為它已經被語言跟標準庫吸收了。增強型迴圈、產生器、串流底層都是迭代器。

但理解它仍然必要。像遍歷時修改集合為什麼會拋例外，那其實是迭代器記錄了集合的修改次數，每次取元素都檢查，不一致就馬上報錯。這是刻意的快速失敗設計，與其讓遍歷產生跳過或重複這種不可預期的結果，不如當場報錯。要在遍歷中刪除，應該用迭代器自己的移除方法。

## 常見追問

### 遍歷中修改集合為什麼會出問題？

**核心答案**：因為迭代器依賴集合的內部結構來定位。集合被修改後（元素移動、陣列擴容、樹重新平衡），迭代器記錄的位置可能失效，繼續遍歷會產生跳過元素、重複回傳、或索引越界等不可預期的結果。多數集合因此加上了**修改次數的檢查**，一發現不一致就立刻拋出例外——這是快速失敗，目的是讓問題在發生點暴露而不是產生錯誤的資料。

**詳細解析**：正確的修改方式有三種：**用迭代器自己的移除方法**（它會同步更新檢查用的計數，是唯一安全的遍歷中刪除方式）、先收集要刪除的元素再批次處理（適合需要刪除多個或條件複雜時）、以及**使用支援併發修改的集合**（它們的迭代器基於某個時間點的快照，遍歷期間的修改不影響當次遍歷，代價是可能讀到稍舊的資料）。第三種在多執行緒環境中很實用，但要理解它的語意——你遍歷到的是開始遍歷時的狀態，不保證是最新的，這個弱一致性必須是可接受的才適用。

**面試回答方式**：解釋迭代器依賴內部結構定位、修改後位置失效，並指出快速失敗是刻意設計而非限制。給三種正確做法。加分點是說明併發集合的迭代器基於快照，遍歷到的是開始時的狀態，這個弱一致性必須可接受才適用。

### 外部迭代和內部迭代該怎麼選？

**核心答案**：需要精細控制流程用外部，表達資料轉換用內部。外部迭代（手動取得迭代器或用迴圈）的控制權在使用方——可以隨時中斷、可以同時推進多個集合、可以在遍歷中做複雜的狀態管理。內部迭代（串流與高階函式）的控制權在集合——程式碼更宣告式、意圖更清楚，而且實作方可以做優化（平行處理、短路、融合多個操作）。

**詳細解析**：實務上的判斷還要考慮**可讀性**——一串轉換與過濾用串流表達通常比巢狀迴圈清楚得多；但一旦邏輯中出現複雜的條件分支、需要跨元素的狀態、或需要提早中斷並回傳多個值，串流反而會變得扭曲，這時迴圈更直白。另一個常被忽略的是**除錯**：串流的中間狀態不容易觀察（要插入除錯的中間操作），而迴圈可以直接下中斷點。所以「哪個更好」沒有絕對答案，用哪個能讓讀的人更快理解意圖才是判準。這個以可讀性為依歸的態度值得表達。

**面試回答方式**：給出「精細控制用外部、資料轉換用內部」的判準與各自的優勢。加分點是補上兩個實務因素：邏輯複雜或需要跨元素狀態時迴圈更直白、以及串流的除錯較不方便，並歸結為「用哪個能讓讀的人更快理解意圖」。

### 自訂資料結構要怎麼支援標準的遍歷？

**核心答案**：**實作標準的可迭代介面**，回傳一個迭代器。這樣自訂結構就能被增強型迴圈直接使用、也能接進既有的工具與函式庫。成本很小但整合性的收益很大。實作時的關鍵是每次取得迭代器都回傳新的實例——共用同一個實例會讓兩次遍歷互相干擾，是很典型的實作錯誤。

**詳細解析**：還有幾個實作要點。**是否要支援移除**——如果結構本身不支援安全的遍歷中刪除，那個方法應該明確拋出不支援的例外，而不是留下一個行為不明的實作。**是否要做修改檢查**——如果結構可能在遍歷中被修改，加上快速失敗的檢查能避免使用者遇到難以理解的錯誤，這個投資通常划算。**惰性的機會**——如果元素可以按需產生（例如從檔案或遠端逐批載入），迭代器是實作惰性的天然位置，能讓使用方以統一的方式處理而不必知道資料怎麼來的。這最後一點常常是自訂迭代器真正的價值所在。

**面試回答方式**：給出實作標準介面的做法與「每次回傳新實例」這個關鍵。加分點是三個實作要點：不支援移除就明確拋例外、加上修改檢查避免難懂的錯誤、以及惰性載入是自訂迭代器真正的價值所在。
