# 題目

外觀模式在做什麼？它和一般所說的「服務層」是同一件事嗎？

## 核心答案

外觀提供一個**簡化的入口**，把一組複雜的子系統呼叫收斂成幾個有意義的方法——使用方不必知道內部有哪些元件、該用什麼順序呼叫、要處理哪些中間狀態。它的價值有三個：**降低使用門檻**（常見情境一行搞定）、**減少耦合**（使用方只依賴外觀，內部重構不影響它）、以及**集中流程知識**（正確的呼叫順序與錯誤處理寫在一個地方，不必每個使用點各自實作）。**服務層本質上就是外觀在應用架構中的體現**——它把資料存取、領域邏輯、外部整合等元件的協作收斂成「以業務動作命名」的方法（下訂單、取消訂單），讓上層（控制器、排程任務、訊息消費者）不必知道內部怎麼組裝。所以兩者不是不同的東西，而是**同一個想法在不同尺度上的應用**。要注意的是外觀**不應該封鎖底層**——需要細緻控制的使用者仍然可以直接使用子系統，外觀只是提供便利路徑而非唯一路徑。

## 詳細解析

**外觀最實際的價值是「集中流程知識」**：一個業務動作往往需要按特定順序呼叫多個元件、處理中間的失敗、維護一致的狀態。如果每個使用點自己組裝，那些知識會被複製多份，而且必然逐漸分歧——某一處忘了呼叫某個步驟、某一處的錯誤處理不同。集中在一個服務方法中之後，正確性只需要維護一份。

**服務層容易變成「什麼都塞」的地方**：它的職責是**協調**而非**實作業務規則**。當服務方法變成幾百行的流程、包含大量條件判斷與計算時，通常代表領域邏輯本該屬於領域物件卻被抽到了服務層——這就是所謂的貧血模型問題。判斷的方式是問「**這段邏輯是關於協調誰先誰後，還是關於業務本身的規則**」，後者應該往下沉。

**外觀不該封鎖底層**：好的外觀是**加法**而非**減法**——它提供了一條方便的路，但不阻止有特殊需求的使用者直接操作子系統。強制所有存取都走外觀，會讓外觀不斷膨脹以應付各種特殊需求，最終變成一個巨大的介面。這個「便利路徑而非唯一路徑」的原則，在函式庫設計中特別重要。

**它與轉接器、代理的區別在意圖**：外觀**簡化並提供新的介面**（通常一對多，一個方法對應多個子系統呼叫），轉接器**改變介面形狀**（通常一對一，功能不變），代理**保持介面並控制存取**。三者結構上都是包一層，用意圖區分最可靠。

**分層之間的資料模型是常被忽略的問題**：服務層回傳的應該是**符合上層需求的資料形狀**，而不是直接把領域物件或資料庫實體往外拋。直接暴露實體會讓上層依賴內部結構（改欄位就影響 API）、也容易造成延遲載入的例外或意外的序列化。建立專門的傳輸物件雖然多一層轉換，但它是**分層真正生效**的關鍵——沒有這一層，分層只是資料夾的劃分而非實際的邊界。

## 面試回答方式

先給外觀的定義與**三個價值**（降低使用門檻、減少耦合、集中流程知識），並直接建立關係：**服務層就是外觀在應用架構中的體現**，兩者是同一想法的不同尺度。接著給最重要的實務提醒：**服務層的職責是協調而非實作業務規則**，判斷方式是問「這段邏輯是關於誰先誰後，還是關於業務本身」，後者該往領域物件下沉。加分點有三個：**外觀應該是便利路徑而非唯一路徑**，強制都走它會讓介面不斷膨脹；用**意圖**區分外觀、轉接器、代理；以及**服務層不該直接回傳領域實體**，否則分層只是資料夾劃分而非真正的邊界。

## 講稿

外觀提供一個簡化的入口，把一組複雜的子系統呼叫收斂成幾個有意義的方法。使用方不用知道內部有哪些元件、該用什麼順序呼叫。

它的價值有三個。降低使用門檻，常見情境一行搞定。減少耦合，使用方只依賴外觀，內部重構不影響它。還有集中流程知識，這個我覺得最實際。一個業務動作往往要按特定順序呼叫多個元件、處理中間的失敗。如果每個使用點自己組裝，那些知識會被複製好幾份，而且必然逐漸分歧，某一處忘了呼叫某個步驟、某一處的錯誤處理不一樣。

服務層本質上就是外觀在應用架構中的體現，把資料存取、領域邏輯、外部整合的協作收斂成以業務動作命名的方法。所以兩者不是不同的東西，是同一個想法在不同尺度上的應用。

不過服務層很容易變成什麼都塞的地方。它的職責是協調而不是實作業務規則。當服務方法變成幾百行、充滿條件判斷跟計算的時候，通常代表領域邏輯本來該屬於領域物件卻被抽到了服務層。我判斷的方式是問，這段邏輯是關於協調誰先誰後，還是關於業務本身的規則。後者應該往下沉。

另外外觀應該是便利路徑而不是唯一路徑，強制所有存取都走它，它會不斷膨脹。

## 常見追問

### 服務層應該回傳領域物件還是專用的傳輸物件？

**核心答案**：**回傳傳輸物件**，尤其是跨越邊界時（服務層到控制器、到外部 API）。直接回傳領域物件或資料庫實體有三個問題：**上層依賴內部結構**（改一個欄位就影響對外的 API 契約）、**意外的行為**（延遲載入的關聯在序列化時觸發查詢或拋例外）、以及**過度暴露**（內部欄位不小心洩漏到 API 回應中）。傳輸物件多了一層轉換，但它讓**內部結構可以自由演進**。

**詳細解析**：常見的反對意見是「多一層轉換很囉嗦」，這在小專案中確實可能不划算——判斷依據是**這個邊界會不會被外部依賴**。內部工具、只有自己使用的服務，直接回傳領域物件可以接受；對外的 API、跨團隊的介面，傳輸物件幾乎是必要的。實作上可以用映射工具減少樣板程式碼，但要注意**自動映射會隱藏欄位不一致的問題**（新增欄位時忘了處理不會有編譯錯誤），所以在重要的邊界上明確撰寫轉換反而更安全。這個「便利與明確之間的取捨」值得說出來。

**面試回答方式**：明確主張跨邊界時回傳傳輸物件，並給三個具體問題（上層依賴結構、延遲載入的意外、過度暴露）。加分點是給判斷依據——這個邊界會不會被外部依賴，以及指出自動映射工具會隱藏欄位不一致的問題，重要邊界上明確撰寫更安全。

### 服務層方法變得很長怎麼辦？

**核心答案**：先分辨**長的原因**。如果是**協調步驟多**（呼叫了八個元件），那可能是這個業務動作本來就複雜，可以把子流程抽成私有方法或更小的服務，讓主方法讀起來像一份流程說明。如果是**充滿業務規則的判斷與計算**，那是職責錯置——這些邏輯該下沉到領域物件中，服務層只負責取得物件、呼叫它的方法、儲存結果。**前者是拆分問題，後者是設計問題**，處理方式完全不同。

**詳細解析**：判斷是哪一種的實用方法是**看程式碼裡的名詞與動詞**——如果大量出現「如果訂單的狀態是 X 且金額大於 Y 就……」這類針對某個物件的規則，那個規則屬於那個物件。把它移進領域物件之後，服務層會變成一連串有意義的呼叫，可讀性大幅提升，而且那些規則變得可以被單獨測試（不需要準備整個服務的依賴）。這個「**可測試性會隨著職責歸位而改善**」的現象是很好的驗證訊號——如果重構之後測試變得更難寫，通常代表方向錯了。

**面試回答方式**：先分辨兩種原因（協調步驟多 vs 業務規則錯置）並說明處理方式不同。給出判斷方法——看程式碼中是否有大量針對某個物件的規則判斷。加分點是提出「可測試性隨職責歸位而改善」是驗證重構方向的訊號。

### 外觀會不會讓系統變得難以擴展？

**核心答案**：**只有在它被設計成唯一入口時才會**。如果外觀是**便利路徑而非唯一路徑**，有特殊需求的使用者仍可直接操作子系統，那它不會限制任何東西。問題出在強制所有存取都走外觀時——各種特殊需求會不斷往外觀上加參數與方法，最終變成一個巨大且難以理解的介面，這時它反而成了瓶頸。

**詳細解析**：實務上有一個平衡的做法：**外觀覆蓋常見情境（八成的使用），並明確記錄「特殊需求請直接使用子系統」**。這保留了兩邊的好處。要注意的是，如果發現大量使用者都在繞過外觀，那是一個訊號——可能外觀的抽象層次選錯了，該重新設計而不是繼續加方法。這個「**用使用方式的回饋來驗證抽象是否正確**」的思路很重要：抽象好不好不是設計者說了算，而是看實際使用時大家有沒有順著它走。這個觀點在 API 設計討論中很有份量。

**面試回答方式**：明確說只有被設計成唯一入口時才會，並解釋參數與方法不斷膨脹的過程。給出平衡做法（覆蓋八成、記錄特殊路徑）。加分點是提出「大量使用者繞過外觀是抽象層次選錯的訊號」，並歸納為「用實際使用方式驗證抽象是否正確」。
