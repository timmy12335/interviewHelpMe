# 題目

哪些設計模式在有 lambda 的語言中變得不必要了？

## 核心答案

**四個最明顯的**。**策略模式**——**一個只有一個方法的介面加上幾個實作類別**；**在有 lambda 的語言中，那就是「傳一個函數」**。**命令模式**——**把操作包成物件以便延後執行或排隊**；**函數本身就是可以被傳遞與儲存的值**。**模板方法**——**固定流程加可變步驟**；**可以用「傳入幾個函數」取代繼承。**觀察者**——**註冊回呼**；**函數就是回呼。**

**而它們「變得不必要」的準確表述是「不再需要為它們建立類別階層」**——**模式所表達的意圖仍然存在，只是表達的形式從「類別」變成了「函數」**。

**所以正確的理解是「模式描述的是問題與解法的結構，而語言決定了表達它的成本」**——**當成本降到接近零，模式就從「一個需要被命名與討論的設計」變成「一個自然的寫法」。**

## 詳細解析

**「GoF 的模式有相當比例是在補償語言的不足」**：C++ 與早期 Java 沒有一等函數——**於是「傳遞一個行為」必須用「傳遞一個實作了某個介面的物件」來模擬**；**而那需要定義介面、寫實作類別、處理實例化**。**模式書把這個繞道命名為「策略模式」並給了它一個類別圖**——**而在 Lisp 或 JavaScript 中，那從來就不是一個「模式」，只是「傳一個函數」**。**Peter Norvig 早在 1996 年就指出「GoF 的 23 個模式中有 16 個在動態語言中變得不可見或簡化」**——**這個觀察至今成立且值得知道。**

**「但不是所有模式都消失了」**：**需要多個方法的介面**（不能用單一 lambda 表達）、**需要維護狀態的策略**、**以及需要被命名與重用的複雜行為**——**這些仍然值得一個類別**。**所以判斷的方式是「這個行為只是一個函數，還是一個有名字、有狀態、有多個操作的概念」**——**後者仍然應該是一個類別。**

**「lambda 的可讀性代價」需要被承認**：一個複雜的 lambda 內聯在呼叫處——**可能比一個有名字的類別更難理解**；**而它也更難被單獨測試**。**所以「簡單的行為用 lambda、複雜的抽出成具名的東西」是一個實用的界線**——**而那個「具名的東西」可以是一個具名的函數而非必然是一個類別**。

**「這個演進對閱讀舊程式碼很重要」**：看到一個「只有一個方法的介面加三個實作」——**要知道那可能是舊語言下的策略模式，而不是一個需要保留的複雜設計**；**於是重構時可以放心地簡化它**。**能識別「這是語言限制的產物」與「這是必要的抽象」，是重構舊程式碼時最有價值的判斷之一。**

## 面試回答方式

先給四個最明顯的模式與各自的函數式對應，再給**準確的表述是「不再需要為它們建立類別階層」而意圖仍然存在**。加分點有四個：**GoF 的模式有相當比例是在補償語言的不足**——**「傳遞一個行為」必須用「傳遞一個物件」模擬**，並引 Norvig 的觀察（23 個中有 16 個在動態語言中簡化）；**不是所有模式都消失了**——**需要多個方法、需要狀態、需要被命名的複雜行為仍值得一個類別**；**lambda 的可讀性代價**與「簡單用 lambda、複雜抽出具名」的界線；以及**這個演進對閱讀舊程式碼很重要**——**能識別「語言限制的產物」與「必要的抽象」是重構時最有價值的判斷之一**。

## 講稿

最明顯的有四個。策略模式在有匿名函數的語言中就是傳一個函數。命令模式把操作包成物件以便延後執行，而函數本身就是可以被傳遞與儲存的值。模板方法可以用傳入幾個函數取代繼承。觀察者就是註冊回呼。

但準確的表述是它們不再需要為自己建立類別階層，模式所表達的意圖仍然存在，只是表達的形式從類別變成了函數。

所以我的理解是，模式描述的是問題與解法的結構，而語言決定了表達它的成本。當成本降到接近零，模式就從一個需要被命名與討論的設計，變成一個自然的寫法。

有一個觀察值得知道。早期的語言沒有一等函數，於是傳遞一個行為必須用傳遞一個實作了某個介面的物件來模擬，而那需要定義介面、寫實作類別、處理實例化。模式書把這個繞道命名並給了它類別圖。而在動態語言中那從來就不是一個模式，只是傳一個函數。有人在九零年代就指出，二十三個模式中有十六個在動態語言中變得不可見或簡化。

這個認知對閱讀舊程式碼很重要。看到一個只有一個方法的介面加三個實作，要知道那可能是語言限制的產物，重構時可以放心簡化。

## 常見追問

### 那還需要學設計模式嗎？

**核心答案**：**需要，但重點應該從「實作」轉向「意圖與取捨」**。模式的價值有三層：**共同的詞彙**（說「這裡用了觀察者」比描述五分鐘快）、**問題的分類**（知道有哪些常見的問題形狀）、**以及取捨的知識**（每個模式解決什麼、代價是什麼）。**前兩層永遠有價值，而第三層正是面試真正在考的。**

**詳細解析**：**「詞彙的價值在多人協作中最明顯」**：一個團隊如果沒有共同的詞彙——**討論設計時要用很長的描述，而且容易誤解**；**而「這裡用責任鏈」一句話就傳達了結構、擴充方式、與已知的注意事項**。**這個溝通效率的提升，是模式即使在語言演進之後仍然值得學習的主要理由**。**而「問題的分類」的價值在於它提供了一個檢查清單**：**遇到一個設計問題時，「這是不是一個已知的形狀」能快速地縮小方案空間**——**而那比從零開始設計快得多也更可靠**。**所以學習的方式應該是「理解每個模式解決的問題」而非「背誦類別圖」**——**因為前者可遷移而後者會過時。**

**面試回答方式**：回答需要但**重點從實作轉向意圖與取捨**，並給價值的三層。核心加分點是**詞彙的價值在多人協作中最明顯**——**「這裡用責任鏈」一句話傳達結構、擴充方式與注意事項**，**這是模式在語言演進後仍值得學的主要理由**。收在學習方式：**理解每個模式解決的問題而非背誦類別圖**——**因為前者可遷移而後者會過時**。

### 函數式的組合能取代繼承嗎？

**核心答案**：**在多數場景中可以，而且往往更好**。繼承的問題是「它把一堆東西綁在一起」——**子類別繼承了父類別的全部（狀態、行為、以及未來的改動）**；**而組合讓你精確地選擇需要的部分**。**函數式的組合更進一步：不需要類別，只需要把函數串起來**。**而繼承仍然有用的場景是「真正的 is-a 關係且需要多型分派」。**

**詳細解析**：**「組合優於繼承」在函數式的形式下更徹底**：物件導向的組合仍然需要定義介面與委派方法——**而函數的組合只是把它們串起來（`f andThen g`）**；**於是「加一個處理步驟」就是「多串一個函數」**。**這正是中介軟體管線（middleware pipeline）的本質**——**而它比責任鏈模式的類別階層簡潔得多**。**但要注意函數組合的限制**：**除錯困難（堆疊追蹤中是一堆匿名函數）、以及難以在執行期檢視組合的結構**（**而基於物件的責任鏈可以被遍歷與檢查**）。**所以在需要可觀測性的場景（例如一個能列出所有已註冊處理器的框架）中，物件的形式仍有價值**——**這是一個「表達的簡潔」與「結構的可檢視」之間的取捨。**

**面試回答方式**：回答多數場景可以且往往更好，給繼承的問題與組合的優勢，並指出**繼承仍有用的場景是真正的 is-a 加多型分派**。核心加分點是**函數式的組合更徹底**——**只是把函數串起來，而這正是中介軟體管線的本質，比責任鏈的類別階層簡潔**。收在限制與取捨：**除錯困難、難以在執行期檢視組合的結構**，**所以需要可觀測性時物件的形式仍有價值**。

### 那些「還沒消失」的模式有哪些共同點？

**核心答案**：**它們解決的是「結構」而非「行為的傳遞」**。**組合模式**（樹狀結構的統一處理）、**轉接器**（介面不相容）、**代理**（存取控制與延遲載入）、**以及外觀**（複雜子系統的簡化入口）——**這些都是關於「物件之間怎麼組織」而非「怎麼把一段行為傳過去」**。**而語言的演進主要解決了後者。**

**詳細解析**：**「這個分類提供了一個預測的方式」**：如果一個模式的核心是「把行為當成值傳遞」——**那它在有一等函數的語言中會消失或簡化**；**而如果核心是「物件的組織方式」，那它與語言特性無關，會一直存在**。**用這個標準檢視 GoF 的 23 個模式，就能預測哪些會過時**。**而更廣的推論是：語言的演進消除的是「表達的繁瑣」而非「設計的問題」**——**問題（怎麼組織程式碼、怎麼管理依賴、怎麼處理變化）永遠存在**；**變的只是表達解法所需要的程式碼量**。**這個區分能解釋為什麼「設計」的知識比「語法」的知識保值得多。**

**面試回答方式**：給共同點（**解決的是結構而非行為的傳遞**）並列舉那些模式。核心加分點是指出**這個分類提供了一個預測的方式**——**核心是「把行為當值傳遞」的會消失，核心是「物件的組織方式」的會一直存在**。收在更廣的推論：**語言的演進消除的是表達的繁瑣而非設計的問題**，**這解釋了為什麼「設計」的知識比「語法」的知識保值得多**。
