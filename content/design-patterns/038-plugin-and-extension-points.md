# 題目

一個系統要支援第三方擴充，該怎麼設計擴充點？

## 核心答案

**擴充點的設計要回答四個問題。**

**在哪裡擴充**——**明確定義「哪些行為可以被替換或增強」**；**而這個決定應該基於「已經出現過的變化需求」而非猜測**。

**怎麼發現與載入**——**設定檔宣告、服務發現機制（Java 的 SPI、`META-INF/services`）、或者掃描特定的目錄**。

**用什麼契約**——**介面加上明確的版本策略**；**這是最需要謹慎的部分，因為契約一旦公開就很難改**。

**以及隔離與安全**——**一個插件崩潰會不會拖垮主程式、它能存取什麼、以及資源怎麼限制。**

**而最重要的判斷是「不要過早設計擴充點」**——**在沒有真實的擴充需求時，每一個擴充點都是被猜測的、而且大機率猜錯的抽象。**

## 詳細解析

**「擴充點的契約是最貴的承諾」**：一旦有第三方依賴了那個介面——**你就不能隨意改它**；**而「支援舊插件」會成為長期的約束**。**所以擴充點應該「窄而穩定」**：**暴露最小的必要介面、用「加方法要有預設實作」的方式保持相容、以及明確標示哪些是穩定 API 哪些是實驗性的**。**很多框架的複雜度來自「早期暴露了太多內部細節，之後無法改動」**——**而那是一個無法回頭的錯誤。**

**「插件的隔離程度是一個明確的取捨」**：**同行程、同類別載入器**——**最快最簡單，但一個插件的例外或記憶體洩漏會影響全域**；**獨立的類別載入器**——**能隔離依賴衝突並支援熱插拔，但複雜度高（OSGi 的複雜度是有名的）**；**獨立的行程**——**完全隔離，但需要 IPC 且效能有代價**。**而近年的一個有趣方向是 WASM**——**它提供了行程內的沙箱與資源限制，是這個取捨的一個新選項。**

**「擴充點應該從真實的分支中提取」是實用的方法**：不要一開始就設計一個「通用的擴充框架」——**而是當「第二個實作出現時」把共同的部分提取成介面**。**這與「三次法則」（同樣的東西出現三次才抽象）是同一個思路**——**而它能大幅降低「設計了一個沒人用的擴充點」的機率**。**很多框架的擴充點是「開發者猜測使用者會需要什麼」的產物，而它們的使用率往往極低。**

**「文件與範例決定了擴充點的實際可用性」**：一個技術上完美但沒有文件的擴充點——**沒有人會用**；**而一個有完整範例的簡單擴充點，會被廣泛採用**。**所以「擴充點的投入」應該包含文件與至少一個參考實作**——**而那個成本經常被低估。**

## 面試回答方式

先給要回答的四個問題（在哪裡、怎麼載入、什麼契約、隔離與安全），並強調**最重要的判斷是不要過早設計擴充點**。加分點有四個：**擴充點的契約是最貴的承諾**——**一旦公開就不能隨意改**，**所以應該窄而穩定**，**而很多框架的複雜度來自早期暴露了太多內部細節**；**隔離程度的三種取捨**與 **WASM 作為新選項**；**擴充點應該從真實的分支中提取**——**第二個實作出現時才抽象，與三次法則同思路**，**而猜測產物的使用率往往極低**；以及**文件與範例決定實際可用性**，**而那個成本經常被低估**。

## 講稿

擴充點的設計要回答四個問題。在哪裡擴充、怎麼發現與載入、用什麼契約、還有隔離與安全。

而我認為最重要的判斷是不要過早設計擴充點。在沒有真實的擴充需求時，每一個擴充點都是被猜測的、而且大機率猜錯的抽象。

因為擴充點的契約是最貴的承諾。一旦有第三方依賴了那個介面，你就不能隨意改它，而支援舊插件會成為長期的約束。所以它應該窄而穩定，暴露最小的必要介面，並且明確標示哪些是穩定的哪些是實驗性的。很多框架的複雜度來自早期暴露了太多內部細節，之後無法改動，那是一個無法回頭的錯誤。

實用的方法是從真實的分支中提取。不要一開始就設計一個通用的擴充框架，而是當第二個實作出現時把共同的部分提取成介面。這跟同樣的東西出現三次才抽象是同一個思路。

隔離程度是另一個取捨。同行程最快但一個插件的問題會影響全域，獨立行程完全隔離但需要跨行程通訊。而近年有一個新選項是網頁組譯，它提供行程內的沙箱與資源限制。

## 常見追問

### 插件的版本相容怎麼管理？

**核心答案**：**明確的版本協商加上寬鬆的介面演進**。插件宣告「我需要哪個版本的 API」——**主程式檢查相容性並拒絕不相容的**。**而介面的演進應該遵守「只加不改」**：**新方法給預設實作（於是舊插件不用改就能繼續運作）**、**參數的新增用一個參數物件而非改變簽章**、**以及廢棄的東西保留一段時間並明確標示。**

**詳細解析**：**「預設方法是介面演進的關鍵工具」**：Java 8 之後介面可以有預設實作——**於是「加一個方法」不再是破壞性變更**；**這讓框架能在不破壞既有插件的情況下擴充能力**。**而在沒有這個特性的語言中，常見的做法是「提供一個抽象基類，插件繼承它而非直接實作介面」**——**於是新方法可以有預設實作**。**兩種做法的本質相同：讓「新增」不強制既有的實作改動**。**而更根本的建議是「介面要小」**——**一個五個方法的介面比一個二十個方法的容易演進**；**需要更多能力時用多個小介面而非一個大的**（**這正是介面隔離原則的實際價值**）。

**面試回答方式**：給版本協商與「只加不改」的演進規則。核心加分點是**預設方法是介面演進的關鍵工具**——**它讓「加一個方法」不再是破壞性變更**，並給沒有這個特性時的替代（抽象基類）。收在更根本的建議：**介面要小**——**五個方法的比二十個的容易演進，需要更多能力時用多個小介面**，**這正是介面隔離原則的實際價值**。

### 怎麼防止插件拖垮主程式？

**核心答案**：**四個層次的防護**。**逾時**——**呼叫插件時設定時間上限，超過就中止**。**例外隔離**——**在呼叫處捕捉所有例外，一個插件的失敗不影響其他**。**資源限制**——**記憶體、執行緒、檔案控制代碼的配額**（**在同行程中很難精確做到，這是行程隔離或沙箱的主要理由**）。**以及熔斷**——**持續失敗的插件被自動停用。**

**詳細解析**：**「在同一個行程中很難真正限制資源」是這個問題的根本困難**：一個插件開了一百個執行緒或者分配了 10GB——**JVM 或 Node 沒有機制阻止它**；**於是「同行程的插件」本質上是一個信任關係**。**所以「第一方的擴充（自己團隊寫的）用同行程、第三方的（不受信任）用隔離」是一個實用的分界**。**而如果必須在同行程中執行不受信任的程式碼，選項是「一個提供資源限制的執行環境」**——**WASM、GraalVM 的隔離堆、或者受限的腳本引擎**；**但它們都限制了插件能做的事**。**這個「隔離程度與能力成反比」的關係是無法迴避的**——**而承認它比假裝「我們的沙箱是安全的」更負責任。**

**面試回答方式**：給四個層次的防護。核心加分點是指出**在同一行程中很難真正限制資源**——**沒有機制阻止插件開一百個執行緒或分配大量記憶體**，**所以同行程的插件本質上是一個信任關係**，並給出實用的分界（第一方同行程、第三方隔離）。收在無法迴避的關係：**隔離程度與能力成反比**，**而承認它比假裝沙箱是安全的更負責任**。

### 什麼時候「不要做成插件」？

**核心答案**：**當擴充的需求只有你自己時**。如果所有的「插件」都是自己團隊寫的、都在同一個倉庫中、都一起發布——**那插件機制帶來的是純粹的間接性**：**動態載入、契約維護、以及除錯的困難**，**而完全沒有拿到「第三方能獨立擴充」這個好處**。**這時「一個介面加幾個實作，在編譯期組裝」更簡單。**

**詳細解析**：**「插件機制的價值在於解耦發布週期」**：第三方能在不修改也不重新編譯主程式的情況下擴充——**那才是動態載入與契約的代價所值的東西**。**如果發布週期是綁定的（一起編譯、一起發布），那所有的動態性都是浪費**。**所以判斷的問題很明確：「擴充者能不能獨立於主程式發布」**——**不能的話就不需要插件機制**。**而一個常見的中間情況是「未來可能需要」**：**這時正確的做法是「先用介面加編譯期組裝，保持設計的乾淨」**——**因為那讓未來要改成動態載入時只需要改組裝的方式，而不需要重新設計抽象**。**這個「保留選項而不提前行使」的策略在很多架構決策中都適用。**

**面試回答方式**：給判斷（**擴充的需求只有你自己時不要做**）與那時純粹的間接性成本。核心加分點是**插件機制的價值在於解耦發布週期**——**發布週期綁定的話所有動態性都是浪費**，**所以問題是「擴充者能不能獨立於主程式發布」**。收在中間情況的處理：**先用介面加編譯期組裝保持設計乾淨**，**未來要改成動態載入時只需要改組裝方式而不需要重新設計抽象**——**這是「保留選項而不提前行使」的策略**。
