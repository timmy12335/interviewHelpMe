# 題目

空物件模式與 Optional 各自解決什麼？什麼時候該用哪個？

## 核心答案

兩者都在處理「沒有值」，但方向相反。

**空物件模式**——提供一個「什麼都不做但符合介面」的實作（`NullLogger`、`GuestUser`）；於是呼叫方不需要判斷，直接呼叫就好。它適合「沒有值時有一個合理的預設行為」的場景。

**Optional**——在型別上明確表達「這裡可能沒有值」；於是呼叫方被迫處理那個情況。它適合「沒有值是一個需要被明確處理的情況」。

選擇的判準是「呼叫方需不需要知道」：不需要知道（記錄日誌、發通知這類可以靜默省略的操作）用空物件；需要知道（找不到使用者、查詢無結果）用 Optional。

而共同的目標是「消除 `if (x != null)` 這種散落各處的防禦性檢查」——因為那些檢查容易被遺漏，而遺漏的後果是 NPE。

## 詳細解析

「空物件的危險是它讓錯誤變得靜默」：一個 `NullPaymentGateway` 什麼都不做——於是「支付失敗」變成「支付看起來成功了」；**這比拋出例外糟糕得多**。所以空物件只適用於「什麼都不做確實是正確行為」的場景——而那個判斷必須是刻意的，不能因為「這樣就不用檢查 null 了」而使用它。判斷的方式是問「如果這個操作被靜默地跳過，會有人發現嗎」——不會的話，那可能不該用空物件。

**「Optional 的正確用法有明確的邊界」**：它設計用於**回傳值**——**表達「這個查詢可能沒有結果」**；而不建議用於欄位（序列化與記憶體成本）或參數（呼叫方可以直接不傳或傳 null，用重載更清楚）。而最重要的反模式是 `optional.get()` 不加檢查——那與直接用 null 沒有差別，只是多了一層包裝。**正確的用法是 `map`、`filter`、`orElse`、`orElseThrow`**——讓「沒有值」的處理成為表達式的一部分。

**「在沒有 Optional 的語言中怎麼辦」**：用**明確的命名慣例**（`findXxx` 可能沒有、`getXxx` 保證有）與**文件或註解**（`@Nullable`、`@NonNull`）——**而靜態分析工具能據此檢查**。Kotlin 這類語言把可空性放進型別系統（`String?` vs `String`）——於是編譯器強制處理，那是最徹底的解法。這也說明了「Optional 是在沒有可空型別的語言中的一個補救」——而不是一個比可空型別更好的設計。

「null 的真正問題是它沒有型別資訊」：`String name = null` 與 `String name = "x"` 在型別上完全相同——於是編譯器無法區分「這裡可能沒有值」與「這裡一定有值」。所有的解法（Optional、可空型別、註解）本質上都是在補回這個資訊。理解這一點，就知道為什麼「檢查 null」是治標而「在型別上表達」才是治本。

## 面試回答方式

先給兩者的方向差異（空物件讓呼叫方不需要判斷、Optional 迫使呼叫方處理）與判準（**呼叫方需不需要知道**）。加分點有四個：空物件的危險是讓錯誤變得靜默——**`NullPaymentGateway` 讓支付失敗變成看起來成功**，判斷的方式是問「被靜默跳過會有人發現嗎」；Optional 的正確邊界（用於回傳值、不建議用於欄位與參數）與最重要的反模式 `get()` 不加檢查；**在沒有 Optional 的語言中的做法**與**Kotlin 的可空型別是最徹底的解法**；以及null 的真正問題是它沒有型別資訊——所有解法本質上都在補回這個資訊，所以檢查是治標而型別表達才是治本。

## 講稿

兩者都在處理沒有值，但方向相反。

空物件模式提供一個什麼都不做但符合介面的實作，於是呼叫方不需要判斷直接呼叫就好。它適合沒有值時有一個合理預設行為的場景。而 Optional 在型別上明確表達這裡可能沒有值，於是呼叫方被迫處理。

判準是呼叫方需不需要知道。不需要知道的，像記錄日誌這類可以靜默省略的操作，用空物件。需要知道的，像找不到使用者，用 Optional。

而空物件有一個危險，它讓錯誤變得靜默。一個什麼都不做的支付閘道會讓支付失敗變成看起來成功，那比拋出例外糟糕得多。所以判斷的方式是問，如果這個操作被靜默地跳過，會有人發現嗎。不會的話那可能不該用它。

至於 Optional，最重要的反模式是不加檢查直接取值，那跟直接用空值沒有差別，只是多了一層包裝。

而更根本的認知是，空值的真正問題是它沒有型別資訊。有值跟沒值在型別上完全相同，於是編譯器無法區分。所有的解法本質上都是在補回這個資訊。所以檢查是治標，在型別上表達才是治本。

## 常見追問

### 例外與回傳空值怎麼選？

**核心答案**：**看「沒有值」是不是異常情況**。**是預期中的**（查詢可能無結果、可選的設定不存在）——**用 Optional 或空集合，因為那不是錯誤**。**是異常的**（依照 ID 取得一個必然存在的實體卻找不到）——拋例外，因為那表示某個假設被違反了。

**詳細解析**：「用例外表達預期中的情況」的代價很具體：例外的建構成本高（要填充堆疊追蹤）——在高頻的路徑上這是可觀的開銷；而更重要的是它讓「正常的流程」被表達成「異常」，程式碼的意圖變得混亂。所以「查不到就拋 NotFoundException」在 Repository 層通常是錯的——而在應用服務層可能是對的（因為那時「找不到」確實表示請求無效）。這個「同一件事在不同層次有不同的語義」的認知很重要：底層報告事實（沒找到），上層決定它是不是錯誤（對這個 use case 而言，找不到就是失敗）。把這個決定推給底層，會讓底層無法被複用在「找不到是正常的」場景中。

**面試回答方式**：給判準（**沒有值是不是異常情況**）與兩種對應。核心加分點是**用例外表達預期情況的代價**（建構成本高、讓正常流程被表達成異常）並指出「查不到就拋例外」在 Repository 層通常是錯的而在應用服務層可能是對的。收在認知：同一件事在不同層次有不同語義——底層報告事實、上層決定它是不是錯誤，把決定推給底層會讓它無法被複用。

### 結果型別（Result/Either）比 Optional 好嗎？

**核心答案**：在「需要知道為什麼失敗」時明顯更好。Optional 只表達「有或沒有」——**而 `Result<T, E>` 能攜帶失敗的原因**；於是呼叫方能區分「找不到」與「權限不足」與「服務暫時不可用」並做不同的處理。代價是它比 Optional 冗長，而且在沒有原生支援的語言中需要自己實作或引入函式庫。

**詳細解析**：「結果型別與例外的取捨」是一個真實的設計選擇：例外是隱式的（不看簽章不知道會拋什麼）——而結果型別是顯式的（失敗是回傳值的一部分，編譯器強制處理）。顯式的好處是「不會有未預期的例外從深處冒出來」；代價是每一層都要處理或傳遞它，於是程式碼變冗長（而這正是 Rust 用 `?` 運算子、Kotlin 用 `runCatching` 來緩解的）。所以判斷的方式是「這個失敗是不是呼叫方應該立即處理的」：**是的話用結果型別讓它顯式**；而「幾乎沒有人能處理」的失敗（資料庫連不上、記憶體不足）用例外讓它冒泡到統一的處理器更合適。混用兩者並明確劃分邊界，比堅持只用一種務實得多。

**面試回答方式**：回答在需要知道為什麼失敗時明顯更好並給各自的代價。核心加分點是展開**結果型別與例外的取捨**：例外隱式而結果型別顯式，顯式避免了未預期的例外但讓程式碼冗長。收在判準：這個失敗是不是呼叫方應該立即處理的——是的話用結果型別，而幾乎沒人能處理的失敗用例外冒泡到統一處理器，混用並明確劃分邊界比堅持只用一種務實。

### 集合該回傳 null 還是空集合？

**核心答案**：永遠回傳空集合，這幾乎沒有例外。因為「沒有元素」是集合的一個完全合法的狀態——**而 null 迫使每個呼叫方都要檢查**；而空集合能被直接迭代、直接 size()、直接串流。「回傳 null 的集合」是一個純粹製造麻煩的設計，沒有任何好處。

**詳細解析**：「這條規則之所以幾乎沒有例外，是因為 null 與空集合的語義差別在實務上幾乎沒有價值」：理論上可以說「null 表示查詢失敗、空集合表示查到了但沒有結果」——但那個區分幾乎從來不被使用，而它的成本（每處都要檢查）是持續的。所以「用型別的自然零值取代 null」是一個廣泛適用的原則：集合用空集合、字串在多數情況用空字串、數字用 0 或一個明確的預設。而它與空物件模式是同一個思路——提供一個「什麼都沒有但行為正常」的值，讓呼叫方不需要特殊處理。這個原則的價值在於它消除了一整類的防禦性程式碼，而那些程式碼正是 bug 的溫床。

**面試回答方式**：給明確的規則（永遠回傳空集合，幾乎沒有例外）與理由。核心加分點是解釋**為什麼幾乎沒有例外**：理論上的語義區分幾乎從來不被使用，而檢查的成本是持續的。收在推廣：「用型別的自然零值取代 null」是廣泛適用的原則，它與空物件模式是同一個思路——消除一整類防禦性程式碼，而那些正是 bug 的溫床。
