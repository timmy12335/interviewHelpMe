# 題目

有哪些常見的架構反模式？它們是怎麼形成的？

## 核心答案

**五個最常見的，而它們的共同成因是「每一步都是局部合理的決定」。**

**上帝物件**——**一個類別知道太多也做太多**；**成因是「加功能時放在最方便的地方」，而那個地方往往是已經很大的那個類別**。

**貧血服務加過程式程式碼**——**物件只有資料，邏輯散落在一堆 Service**；**成因是 CRUD 框架的預設形態加上「先能跑再說」。**

**循環依賴**——**A 需要 B 而 B 也需要 A**；**成因是「需要對方的一個方法就直接注入」而沒有問「這個責任應該在誰那裡」。**

**散彈式修改**——**一個小需求要改十幾個檔案**；**成因是同一個概念的知識被分散在多處。**

**以及過度抽象**——**為了「未來的靈活性」建立了多層的介面與工廠**；**成因是把「可能的變化」當成「已經發生的變化」。**

## 詳細解析

**「每一步都局部合理」是理解反模式最重要的一點**：沒有人會刻意設計一個上帝物件——**它是「五十次『把這個方法加在這裡最方便』」累積的結果**；**而每一次那個決定確實是當下最省事的**。**所以防範的方式不是「提醒大家不要這樣」，而是「建立能發現累積的機制」**：**檔案大小的警告、複雜度的檢查、以及定期的架構檢視**。**而這也解釋了為什麼「code review 中的一句『這個類別是不是太大了』」比任何架構文件都有效**——**因為它作用在累積發生的那一刻。**

**「過度抽象與抽象不足是對稱的錯誤，但它們的成本不同」**：抽象不足——**改動時要改很多地方，痛苦但明顯**；**過度抽象——每次閱讀都要穿過幾層間接，痛苦但不明顯**；**而且它更難修正（移除一層抽象比新增一層更需要勇氣）**。**所以「先具體、痛了再抽象」通常比「先抽象、以防萬一」好**——**因為前者的錯誤容易發現也容易修正**。

**「散彈式修改的診斷很直接」**：看一個典型的需求變更需要改哪些檔案——**如果那些檔案沒有明顯的關聯，那就是這個問題**。**而它的修正是「把相關的東西放在一起」**（按功能而非按層次組織程式碼）——**這正是「垂直切片」與「按功能分包」比「按類型分包（controller/service/repository）」好的理由**。

**「反模式的價值在於它們是一組被命名的診斷」**：說「這裡有上帝物件」比描述五分鐘快——**而且它立刻帶來了已知的修正方向**。**所以認識反模式的實際用途是「快速地識別並溝通問題」**，**而非用來批評別人的程式碼。**

## 面試回答方式

先給五個常見的反模式與各自的成因，並強調**共同成因是「每一步都是局部合理的決定」**。加分點有四個：**「每一步都局部合理」是最重要的認知**——**防範的方式是建立能發現累積的機制而非提醒大家不要這樣**，**而 code review 中的一句話比任何架構文件都有效**；**過度抽象與抽象不足是對稱的錯誤但成本不同**——**前者的痛苦不明顯且更難修正**，**所以「先具體、痛了再抽象」更好**；**散彈式修改的診斷很直接**與**按功能分包優於按類型分包**；以及**反模式的價值在於它們是一組被命名的診斷**。

## 講稿

我會講五個最常見的。上帝物件、貧血服務加過程式程式碼、循環依賴、散彈式修改、還有過度抽象。

而它們的共同成因是每一步都是局部合理的決定。沒有人會刻意設計一個上帝物件，它是五十次把這個方法加在這裡最方便累積的結果，而每一次那個決定確實是當下最省事的。

所以防範的方式不是提醒大家不要這樣，而是建立能發現累積的機制。檔案大小的警告、複雜度的檢查、定期的架構檢視。這也解釋了為什麼程式碼審查中的一句這個類別是不是太大了，比任何架構文件都有效，因為它作用在累積發生的那一刻。

還有一點我想說，過度抽象跟抽象不足是對稱的錯誤，但成本不同。抽象不足的話改動要改很多地方，痛苦但明顯。過度抽象的話每次閱讀都要穿過幾層間接，痛苦但不明顯，而且更難修正，因為移除一層抽象比新增一層更需要勇氣。所以先具體、痛了再抽象通常比先抽象以防萬一好。

而反模式真正的價值在於它們是一組被命名的診斷，說這裡有上帝物件比描述五分鐘快，而且立刻帶來了已知的修正方向。

## 常見追問

### 怎麼判斷一個類別「太大了」？

**核心答案**：**用幾個可量測的訊號加上一個語義的判斷**。**行數**（超過 300 到 500 是一個提醒而非絕對標準）、**方法數**、**依賴數**（建構子參數）、**以及變更頻率**（如果它每次迭代都被改，那它承擔了太多責任）。**而語義的判斷是「能不能用一句話說清楚它的職責」**——**如果需要用「而且」串起來，那就是多個職責。**

**詳細解析**：**「變更頻率」是所有指標中最有價值的一個**：一個一千行但兩年沒改過的類別——**它的大小不是問題**；**而一個三百行但每週被三個不同的需求修改的類別——那才是真正的痛點**。**所以「用版本控制的歷史找出變更最頻繁的檔案」是一個極實用的診斷**（`git log --format= --name-only | sort | uniq -c | sort -rn`）；**而如果那些高頻變更的檔案還被多個不同的原因修改，那就是單一職責被違反的直接證據**。**這個「用歷史而非用直覺」的方法，讓重構的優先級有了客觀的依據**——**而它也避免了「重構了一堆沒人碰的程式碼」這種浪費。**

**面試回答方式**：給可量測的訊號與語義的判斷（**能不能用一句話說清楚職責**）。核心加分點是**變更頻率是最有價值的指標**——**一千行但兩年沒改的不是問題，三百行但每週被三個需求改的才是痛點**，並給出具體的診斷指令。收在價值：**用歷史而非直覺讓重構的優先級有客觀依據**，**也避免了「重構了一堆沒人碰的程式碼」這種浪費**。

### 過度抽象要怎麼收回？

**核心答案**：**內聯它**。一個只有一個實作的介面——**刪掉介面，直接用那個類別**；**一個只被呼叫一次的工廠——直接 new**；**一個穿透多層但每層都只是轉發的呼叫鏈——把中間層拿掉**。**現代 IDE 的「內聯」重構讓這些操作很安全。**

**詳細解析**：**「移除抽象需要的勇氣比新增多」是一個真實的心理障礙**：新增看起來是「為未來準備」——**而移除看起來是「破壞了設計」**；**於是不必要的抽象傾向於永久留存**。**打破它的方式是明確一個判準：「這個抽象有幾個實作、有幾個真實的使用場景」**——**只有一個且沒有具體的第二個在望的，就是候選的移除對象**。**而移除的風險其實很低**（**IDE 的重構是安全的，而且測試會抓到問題**）——**遠低於「保留它並讓每個閱讀者付出理解成本」的持續代價**。**所以「定期檢視並移除不再需要的抽象」應該像「移除死程式碼」一樣被視為正常的維護，而非一個需要特別辯護的行為。**

**面試回答方式**：給具體的操作（內聯介面、工廠、轉發層）並指出 **IDE 的重構讓它很安全**。核心加分點是**移除抽象需要的勇氣比新增多是一個真實的心理障礙**——**新增看起來是為未來準備而移除看起來是破壞設計**，**於是不必要的抽象傾向於永久留存**。收在打破的方式與判斷：**明確判準（幾個實作、幾個真實場景）**，**而移除的風險遠低於保留它讓每個閱讀者付出理解成本的持續代價**。

### 反模式的知識怎麼在團隊中傳遞？

**核心答案**：**用 code review 與具體的例子，而非文件與規範**。一份「不要寫上帝物件」的規範沒有人會記得——**而一次 review 中「這個類別已經 800 行了，這個方法是不是屬於另一個地方」的具體討論會被記住**。**而更有效的是「把檢查自動化」**：**複雜度、檔案大小、以及循環依賴都可以被工具檢查並在 CI 中提示。**

**詳細解析**：**「自動化的檢查與人的判斷各有不可替代的角色」**：工具能發現「量」的問題（太長、太複雜、循環依賴）——**但無法判斷「這個抽象合不合理」或者「這個責任該在誰那裡」**；**而人的 review 能判斷後者但無法可靠地發現前者（沒有人會數行數）**。**所以「工具處理可量化的、review 處理需要判斷的」是一個有效的分工**——**而它也讓 review 的注意力集中在真正需要人的地方**。**另一個實用的做法是「把反模式的例子做成團隊的內部文件，用自己程式碼庫中的真實案例」**——**因為抽象的定義難以記住，而「我們的 OrderService 就是一個上帝物件」的例子立刻讓概念變得具體。**

**面試回答方式**：主張**用 code review 與具體例子而非文件與規範**，並指出**更有效的是把檢查自動化**。核心加分點是**自動化與人的判斷各有不可替代的角色**——**工具發現「量」的問題而人判斷「合不合理」**，**這個分工讓 review 的注意力集中在真正需要人的地方**。收在實用做法：**用自己程式碼庫中的真實案例做內部文件**——**抽象的定義難以記住而具體的例子立刻讓概念變得清晰**。
