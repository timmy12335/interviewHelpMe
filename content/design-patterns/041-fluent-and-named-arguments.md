# 題目

除了建造者模式，還有哪些方式處理複雜的物件建構？

## 核心答案

四種，而語言的特性決定了哪一種最自然。

**具名參數與預設值**（Kotlin、Python、C#）——**`User(name = "A", age = 30)`**；直接解決了「參數太多且順序容易搞錯」的問題，而完全不需要建造者。在有這個特性的語言中，建造者模式的使用場景大幅縮小。

**流暢介面（fluent interface）**——**`query().where(...).orderBy(...).limit(10)`**；適合「一連串的配置或組合」，而且能引導使用者按正確的順序呼叫（用不同的回傳型別限制下一步能做什麼）。

**內部 DSL**（Kotlin 的 builder DSL、Ruby 的 block）——用語言本身的特性建構出讀起來像另一種語言的 API。

**以及不可變的「with」風格**——**`config.withTimeout(5).withRetries(3)`**；每次回傳一個新的物件，適合值物件的部分修改。

## 詳細解析

「用型別引導呼叫順序」是流暢介面一個進階但很有價值的技巧：如果 `select()` 回傳的型別只有 `from()` 方法——那使用者不可能在 select 之後直接呼叫 where；於是「錯誤的順序」在編譯期就被排除。這被稱為「型別狀態」或「階段式建構器」——它把「使用文件」變成了「型別系統的引導」。代價是型別的數量增加（每個階段一個介面）——所以它適合「順序真的重要且錯了後果嚴重」的 API（例如建構一個交易或一個安全設定）。

「建造者模式在有具名參數的語言中大幅退場」值得指出：GoF 的建造者解決的是「參數太多、可選參數的組合爆炸、以及建構過程需要多步」——而具名參數加預設值直接解決了前兩個；於是只剩「建構過程需要多步或需要驗證」的場景仍然需要建造者。這與策略模式在有 lambda 之後的退場是同一個現象——**模式的必要性取決於語言。**

「流暢介面的除錯代價」需要被知道：一長串的鏈式呼叫在堆疊追蹤中只顯示一行——**於是「是哪一步出錯了」不明顯**；**而中斷點也難以設在中間**。所以「鏈不要太長」與「複雜的邏輯不要塞進鏈中」是實用的建議。而現代的 IDE 與語言（例如 Java 14 之後更精確的 NPE 訊息）改善了部分問題。

**「可讀性是選擇的主要依據」**：這些都不是效能問題——**而是「哪種寫法讓意圖最清楚」**。所以判斷的方式是「把它寫出來，念一遍」——讀起來像自然的描述就是對的；而需要看文件才知道每個參數是什麼的，就該換一種形式。

## 面試回答方式

先給四種方式與各自的適用場景，並指出語言的特性決定了哪一種最自然。加分點有四個：**用型別引導呼叫順序**這個進階技巧——它把使用文件變成型別系統的引導，代價是型別數量增加所以適合順序真的重要的 API；建造者在有具名參數的語言中大幅退場——與策略模式在有 lambda 之後是同一個現象，模式的必要性取決於語言；**流暢介面的除錯代價**（堆疊追蹤只顯示一行、中斷點難設）；以及**可讀性是選擇的主要依據**，**判斷的方式是「寫出來念一遍」**。

## 講稿

有四種方式，而語言的特性決定了哪一種最自然。

具名參數加預設值直接解決了參數太多且順序容易搞錯的問題，完全不需要建造者。在有這個特性的語言中，建造者模式的使用場景大幅縮小。流暢介面適合一連串的配置或組合。內部特定領域語言則用語言本身的特性，建構出讀起來像另一種語言的介面。還有不可變的帶入風格，每次回傳一個新物件，適合值物件的部分修改。

流暢介面有一個進階但很有價值的技巧，用型別引導呼叫順序。如果某一步回傳的型別只有特定的幾個方法，那使用者不可能用錯誤的順序呼叫，錯誤在編譯期就被排除。這把使用文件變成了型別系統的引導。代價是型別的數量增加，所以它適合順序真的重要而且錯了後果嚴重的介面。

值得指出的是，建造者模式在有具名參數的語言中大幅退場。它原本解決的是參數太多跟可選參數的組合爆炸，而具名參數直接解決了那些。這跟策略模式在有匿名函數之後的退場是同一個現象，模式的必要性取決於語言。

而選擇的主要依據是可讀性。我的判斷方式是把它寫出來念一遍，讀起來像自然的描述就是對的。

## 常見追問

### 流暢介面怎麼處理必填與選填？

**核心答案**：必填的放建構子或第一個方法，選填的用鏈式。`Email.to("a@b.com").subject("hi").body("...").send()`——**`to` 是必填所以它是入口**；**而 `subject` 與 `body` 是選填的鏈式呼叫**。如果必填的有多個且順序重要，用階段式建構器（每個階段的回傳型別只暴露下一步）能在編譯期強制。

**詳細解析**：「執行期驗證是次佳但常見的選擇」：在 `build()` 或 `send()` 中檢查必填欄位是否都設了——簡單但錯誤只在執行期才發現；而階段式建構器能在編譯期強制，代價是要定義多個介面。判斷的方式是「錯誤的代價有多大」：一個內部的工具類別用執行期檢查就夠；而一個公開的函式庫或者一個錯了會造成嚴重後果的 API（例如安全設定），值得投入型別的引導。這個「用型別強制 vs 用執行期檢查」的取捨在很多 API 設計中出現——而原則是「錯誤越嚴重、使用者越多，就越值得用型別」。

**面試回答方式**：給基本做法（必填放入口、選填用鏈式）與階段式建構器的強制。核心加分點是執行期驗證是次佳但常見的選擇與判斷方式（**錯誤的代價有多大**）：內部工具用執行期檢查就夠，公開函式庫或錯了後果嚴重的值得投入型別引導。收在原則：錯誤越嚴重、使用者越多，就越值得用型別強制。

### 內部 DSL 什麼時候值得？

**核心答案**：當那個領域有足夠的結構且會被反覆使用時。建構測試資料、定義路由、描述設定、或者組裝一個查詢——這些有明確的結構而且會被寫很多次；於是一個讀起來自然的 DSL 能顯著提升可讀性與撰寫速度。而對只用幾次的東西，一般的 API 就夠了。

**詳細解析**：「DSL 的成本在於它是一套需要被學習的東西」：使用者要理解那個 DSL 的規則——而那些規則不在任何一般的文件中；如果它設計得不夠直觀，那個學習成本可能超過它省下的撰寫時間。所以「DSL 應該盡量貼近使用者已經熟悉的概念與用語」——而測試它是否成功的方式是「給一個不熟悉的人看，他能不能讀懂」。另一個實務要點是「IDE 的支援決定了 DSL 的實際體驗」：有自動完成與型別檢查的 DSL 很好用；而一個基於字串或 Map 的「DSL」實際上是把錯誤推遲到執行期，體驗遠差。所以在有型別安全的建構方式時，優先選擇它。

**面試回答方式**：給適用條件（領域有足夠的結構且會被反覆使用）與典型場景。核心加分點是DSL 的成本在於它是一套需要被學習的東西——規則不在一般文件中，設計不夠直觀的話學習成本超過省下的時間，而測試的方式是「給不熟悉的人看能不能讀懂」。收在實務要點：**IDE 的支援決定實際體驗**——基於字串或 Map 的「DSL」把錯誤推遲到執行期，體驗遠差。

### 這些方式在跨語言的 API 設計上有什麼考量？

**核心答案**：**流暢介面與 DSL 的可移植性差**。一個在 Kotlin 中優雅的 DSL——**在 Java 中可能非常笨拙**；而具名參數在不支援的語言中要用建造者模擬。所以「提供給多語言使用的 API」應該用最小公分母的形式（明確的參數或簡單的建造者），而語言特有的優雅形式作為那一層之上的糖。

**詳細解析**：「這正是很多跨語言 SDK 的設計方式」：核心是一個樸素的、每種語言都能自然表達的介面——而各語言的 SDK 在其上提供符合該語言慣例的包裝（Kotlin 的 DSL、Python 的關鍵字參數、Go 的 functional options）。這讓「核心的邏輯只有一份」而「每種語言的使用者都覺得自然」。**代價是要維護多個包裝層**——而那個成本在使用者眾多時是值得的。另一個相關的觀察是「Go 的 functional options 模式」正是 Go 缺少具名參數與預設值的產物——**它用一系列 `WithXxx(...)` 的函數來模擬**；這又一次說明「模式往往是語言不足的補償」。

**面試回答方式**：指出**流暢介面與 DSL 的可移植性差**並給原則（跨語言用最小公分母，語言特有的形式作為糖）。核心加分點是這正是很多跨語言 SDK 的設計方式——核心樸素、各語言 SDK 提供符合慣例的包裝，讓核心邏輯只有一份而每種語言的使用者都覺得自然。收在觀察：**Go 的 functional options 正是缺少具名參數的產物**，又一次說明模式往往是語言不足的補償。
