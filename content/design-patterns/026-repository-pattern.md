# 題目

Repository 模式解決什麼問題？它與 DAO 有什麼不同？

## 核心答案

Repository 的原始定義是「讓領域層感覺自己在操作一個記憶體中的集合」——`orderRepository.findByCustomer(id)` 讀起來像是在查一個 List，而不是在下 SQL。它的目的是「讓領域邏輯不依賴儲存的細節」。

**與 DAO 的差別在抽象的層次**。DAO 通常對應一張表，方法是 CRUD 的映射（`insert`、`updateById`、`selectByCondition`）——**它是「資料存取的封裝」**。Repository 對應一個聚合，方法用領域的語言表達（`findActiveSubscriptions`、`save(order)`）——**它是「領域概念的持久化」**。

而實務上最重要的判斷是「這層抽象值不值得」：**如果你的應用本質上就是 CRUD**——那 Repository 只是在 ORM 之上再包一層，純粹的成本；而如果有真正的領域邏輯且查詢複雜——它讓那些邏輯不被 SQL 汙染，價值明確。

## 詳細解析

「為了可替換性而做抽象」通常是一個站不住的理由：常見的說法是「以後可能換資料庫」——而實際上換資料庫的情況極少，而且真的要換時，Repository 這層抽象也遠遠不夠（交易語義、查詢能力、以及效能特性都不同）。所以真正的理由應該是「讓領域邏輯保持乾淨」與「讓測試不需要真實的資料庫」——**後者尤其實在**。

「Repository 的方法容易膨脹」是一個真實的問題：每個新的查詢需求就加一個方法——幾十個 `findByXxxAndYyy` 之後，這個介面本身就變得難以維護。**兩個緩解**：用規格模式（Specification）把查詢條件物件化，於是一個 `find(Specification)` 就能組合出任意查詢；**或者「複雜的查詢直接繞過 Repository」**——承認「讀」與「寫」的需求不同，讀用專門的查詢物件或直接寫 SQL。**後者是 CQRS 思路的一個輕量體現。**

「Repository 應該回傳領域物件而非資料庫的列」：如果 `findById` 回傳的是一個貧血的 DTO——**那它就退化成 DAO 了**。真正的 Repository 應該負責「把持久化的資料重建成一個完整的、行為健全的領域物件」——**包括它的關聯與不變量**。而這正是它比 DAO 貴的地方，也是它的價值所在。

**「不要讓 Repository 洩漏 ORM 的細節」**：回傳一個 lazy-loading 的代理物件——於是領域層在存取某個屬性時觸發了一次資料庫查詢，而它完全不知道。這種洩漏會讓「N+1 查詢」在領域層以最隱蔽的形式出現。所以邊界應該明確：Repository 回傳的物件應該是完整的，而不是一個會偷偷查資料庫的代理。

## 面試回答方式

先給 Repository 的原始定義（讓領域層感覺在操作記憶體中的集合）與它**與 DAO 在抽象層次上的差別**（表 vs 聚合、CRUD 映射 vs 領域語言），再給**這層抽象值不值得**的判斷。加分點有四個：「為了換資料庫」是站不住的理由——**真要換時這層遠遠不夠**，真正的理由是保持領域乾淨與讓測試不需要真實資料庫；**Repository 的方法容易膨脹**與兩個緩解（規格模式、複雜查詢繞過）；應該回傳領域物件而非資料庫的列，**否則就退化成 DAO**；以及**不要洩漏 ORM 的細節**——lazy-loading 的代理讓 N+1 在領域層以最隱蔽的形式出現。

## 講稿

這個模式的原始定義是讓領域層感覺自己在操作一個記憶體中的集合。查詢讀起來像是在查一個列表，而不是在下語句。目的是讓領域邏輯不依賴儲存的細節。

它跟資料存取物件的差別在抽象的層次。後者通常對應一張表，方法是增刪改查的映射。而它對應一個聚合，方法用領域的語言表達。

但我要說一個常被拿來當理由但站不住的說法，就是以後可能換資料庫。實際上換的情況極少，而且真的要換時這層抽象也遠遠不夠，因為交易語義、查詢能力、效能特性都不同。真正的理由應該是讓領域邏輯保持乾淨，還有讓測試不需要真實的資料庫，後者尤其實在。

實務上它有一個容易膨脹的問題。每個新的查詢需求就加一個方法，幾十個之後這個介面本身就難以維護了。緩解的方式是用規格物件把查詢條件物件化，或者承認讀跟寫的需求不同，複雜的查詢直接繞過去用專門的查詢物件。

還有一個要注意的，不要讓它洩漏映射框架的細節。回傳一個延遲載入的代理，會讓 N 加一查詢在領域層以最隱蔽的形式出現。

## 常見追問

### 有了 ORM 還需要 Repository 嗎？

**核心答案**：看你的領域層需不需要與 ORM 解耦。ORM 本身已經提供了「不寫 SQL 就能存取資料」——所以如果應用是 CRUD 為主，直接用 ORM 的 API 更簡單。而如果有豐富的領域邏輯，多一層 Repository 能讓「領域物件」與「持久化物件」分開——於是領域模型可以按業務設計而非按資料表設計。

**詳細解析**：「領域模型與資料表的形狀不同」是需要這層分離的根本原因：一個訂單的聚合可能包含訂單、明細、與收貨地址——**而它們在資料庫中是三張表**；領域層應該操作「一個訂單」而非「三個實體」。**Repository 負責這個組裝與拆解**。而如果領域模型與資料表一對一（多數 CRUD 應用是這樣），那這層轉換就沒有內容，於是它確實是純粹的樣板。所以判斷的方式很直接：「畫出你的領域模型與資料表，它們的形狀一樣嗎」——**一樣就不需要，不一樣才需要。**

**面試回答方式**：給判斷（**看領域層需不需要與 ORM 解耦**）與兩種情況。核心加分點是領域模型與資料表的形狀不同是需要這層分離的根本原因——一個訂單聚合包含三張表的內容，而領域層應該操作「一個訂單」。收在直接的判斷方式：畫出領域模型與資料表看形狀一不一樣——**一樣就不需要，不一樣才需要**。

### 交易邊界該放在哪一層？

**核心答案**：**應用服務層（use case 層）而非 Repository**。因為一個業務操作可能涉及多個 Repository——交易必須包住整個操作而非單一的存取。**Repository 應該「參與」交易而非「開啟」它**。在 Spring 中這意味著 `@Transactional` 標在應用服務的方法上。

**詳細解析**：「Repository 自己開交易」造成的問題很具體：一個「下單並扣庫存」的操作涉及訂單與庫存兩個 Repository——如果各自開交易，那麼扣庫存失敗時訂單已經提交了。所以交易的邊界必須與「業務操作的邊界」一致——**而那是應用服務層**。這也解釋了為什麼「一個 Repository 方法內部不該有多個獨立的交易」。而更深的一點是「交易邊界與聚合邊界應該對齊」：DDD 的建議是「一個交易只修改一個聚合」——跨聚合的一致性用領域事件與最終一致達成。這個約束在單體應用中常被忽略（因為資料庫交易很方便），而在拆分服務時就會付出代價。

**面試回答方式**：給正確的位置（應用服務層）與理由（**一個業務操作涉及多個 Repository**），並指出 **Repository 應該參與而非開啟交易**。核心加分點是用「下單並扣庫存」的例子說明各自開交易會讓扣庫存失敗時訂單已提交。收在更深的一點：交易邊界應該與聚合邊界對齊——DDD 建議一個交易只修改一個聚合，跨聚合用領域事件與最終一致，而這個約束在單體中常被忽略，拆分服務時就會付出代價。

### 怎麼測試用了 Repository 的程式碼？

**核心答案**：**分兩層**。**領域邏輯與應用服務**——用記憶體中的假 Repository（一個包著 Map 的實作）；測試快、不需要資料庫、而且聚焦在業務邏輯上。**Repository 本身**——用真實的資料庫（或者容器化的測試資料庫）做整合測試；因為它的價值正是「SQL 或 ORM 映射是對的」，用 mock 測它毫無意義。

**詳細解析**：**「用假實作而非 mock」在 Repository 上明顯更好**：mock 需要為每個測試設定「當呼叫 findById 時回傳這個」——**冗長且與實作耦合**；而一個記憶體實作只需要寫一次，之後所有測試都能像操作真實的儲存一樣使用它（存進去、查出來）。它還能捕捉到「先存後查」這類 mock 無法自然表達的行為。寫一個 in-memory Repository 的成本通常不到一小時，而它讓幾百個測試變得簡潔——這是一個投入產出比極高的做法，卻經常被 mock 框架的便利掩蓋。而這也是「Repository 作為介面」的一個實際價值：它讓這種替換成為可能。

**面試回答方式**：給分兩層的測試策略並指出**用 mock 測 Repository 本身毫無意義**。核心加分點是主張**用假實作而非 mock**——mock 冗長且與實作耦合，而記憶體實作只寫一次、所有測試都能像操作真實儲存一樣使用，還能捕捉「先存後查」這類 mock 無法自然表達的行為。收在價值：成本不到一小時而讓幾百個測試變簡潔，這也是「Repository 作為介面」的一個實際價值。
