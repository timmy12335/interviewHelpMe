# 題目

處理併發有哪些設計層面的模式？它們各自消除了什麼問題？

## 核心答案

**併發的困難來自「共享的可變狀態」——而所有的模式本質上都在消除那三個字中的某一個。**

**消除「共享」**——**每個執行緒有自己的副本**（thread-local、Actor 模型的私有狀態）；**於是根本不需要同步**。**Actor 模型是這個思路最完整的形式：狀態被封裝在 actor 內，只能透過訊息互動。**

**消除「可變」**——**不可變物件與函數式的狀態轉換**；**於是共享是安全的**。**這是最簡單有效的一條，也是為什麼「預設不可變」在併發程式碼中特別重要。**

**消除「狀態」**——**無狀態的服務**；**於是每個請求獨立處理，橫向擴展毫無阻力。**

**而在無法消除時，模式提供了結構化的協調方式**：**生產者消費者（用佇列解耦速度差異）、讀寫鎖（區分讀與寫的併發度）、以及不變量集中在單一守衛（把所有的同步集中在一個地方而非散落各處）。**

## 詳細解析

**「Actor 模型的價值在於它讓併發的推理變成單執行緒的推理」**：每個 actor 一次處理一個訊息——**於是它內部的程式碼可以當成單執行緒來寫與理解**；**所有的併發複雜度被推到「訊息的傳遞與順序」上，而那是一個更容易推理的層次**。**代價是「訊息傳遞的開銷」與「失去了直接呼叫的簡潔」**——**而它也帶來了新的問題（訊息的順序、背壓、以及 actor 的失敗處理）**。**所以它適合「狀態明確地分屬於不同實體」的場景（每個使用者、每個連線、每個裝置一個 actor），而不適合「大量共享的全域狀態」。**

**「生產者消費者的關鍵設計是佇列的邊界」**：無界佇列——**在生產快於消費時記憶體會被吃光**；**而有界佇列提供了天然的背壓（生產者被阻塞）**。**所以「有界」幾乎總是正確的選擇**——**而那個界限的大小決定了「能吸收多大的突發」與「延遲的上限」**。**這個「用有界的緩衝提供背壓」的模式，在從執行緒池到訊息佇列的各種層次上重複出現。**

**「把同步集中在一個地方」是一個實用但少被明說的原則**：分散的 `synchronized` 難以推理（要知道所有的鎖與它們的順序）——**而「所有對這個狀態的存取都經過一個類別」讓不變量能被保證且死鎖的分析變得可行**。**這正是為什麼「一個執行緒安全的集合」比「到處自己加鎖」好**——**不只是省事，而是它把正確性集中在一個可以被仔細審查的地方**。

**「效能與正確性的順序」在併發中特別重要**：先寫對（用最簡單的同步方式），**再量測是不是真的是瓶頸，最後才優化**。**因為併發的優化（無鎖結構、細粒度鎖）極容易引入難以重現的 bug**——**而那些 bug 的成本遠高於它們節省的效能。**

## 面試回答方式

先給核心洞察（**困難來自「共享的可變狀態」，模式都在消除其中一個字**）與三種消除方式，再給無法消除時的協調模式。加分點有四個：**Actor 的價值在於讓併發的推理變成單執行緒的推理**，**代價是訊息開銷與新的問題**，**所以它適合狀態明確分屬不同實體的場景**；**生產者消費者的關鍵是佇列的邊界**——**有界提供天然的背壓，而這個模式在各種層次上重複出現**；**把同步集中在一個地方**——**不只是省事，而是把正確性集中在可以被仔細審查的地方**；以及**效能與正確性的順序**——**併發的優化極容易引入難以重現的 bug，成本遠高於節省的效能**。

## 講稿

併發的困難來自共享的可變狀態，而所有的模式本質上都在消除那三個字中的某一個。

消除共享，讓每個執行緒有自己的副本，那是行為者模型的思路。消除可變，用不可變物件，那是最簡單有效的一條。消除狀態，用無狀態的服務。

而在無法消除時，模式提供結構化的協調方式。生產者消費者用佇列解耦速度差異、讀寫鎖區分讀寫的併發度、還有把不變量集中在單一守衛。

行為者模型的價值我認為在於它讓併發的推理變成單執行緒的推理。每個行為者一次處理一個訊息，於是它內部的程式碼可以當成單執行緒來寫。所有的併發複雜度被推到訊息的傳遞與順序上，而那是一個更容易推理的層次。

生產者消費者的關鍵設計是佇列的邊界。無界佇列在生產快於消費時記憶體會被吃光，而有界佇列提供天然的背壓。所以有界幾乎總是正確的選擇。這個用有界緩衝提供背壓的模式，從執行緒池到訊息佇列在各種層次上重複出現。

最後一個原則，在併發中先寫對再優化。因為併發的優化極容易引入難以重現的問題，那些成本遠高於它們節省的效能。

## 常見追問

### 什麼時候該用無鎖結構？

**核心答案**：**當競爭激烈且操作簡單時**。無鎖（CAS 為基礎）的優勢是「沒有執行緒被掛起與喚醒的開銷」——**在高競爭下比鎖快**；**而在低競爭下，一個未被爭用的鎖幾乎沒有成本（偏向鎖、輕量級鎖），無鎖的優勢消失**。**而它的代價是「極難寫對」**——**ABA 問題、記憶體順序、以及活鎖都是陷阱。**

**詳細解析**：**「用現成的無鎖結構而非自己寫」幾乎總是正確的**：`ConcurrentHashMap`、`AtomicLong`、`LongAdder`——**它們被大量的專家審查與測試過**；**而自己寫的無鎖結構，即使通過了測試，也可能在特定的硬體或負載下出錯**。**這類 bug 的特徵是「極難重現且極難診斷」**——**於是它的期望成本遠高於它省下的一點效能**。**而 `LongAdder` 是一個值得知道的例子**：**它在高競爭下比 `AtomicLong` 快得多（分散到多個 cell 減少競爭），代價是讀取時要加總**——**這是一個「用空間與讀取成本換取寫入的併發度」的設計**，**而它說明了「同一個抽象可以有針對不同負載的實作」。**

**面試回答方式**：給適用條件（**競爭激烈且操作簡單**）並指出**低競爭下無鎖的優勢消失**與它極難寫對的代價。核心加分點是主張**用現成的而非自己寫**——**自己寫的即使通過測試也可能在特定硬體或負載下出錯，而那類 bug 極難重現與診斷**。收在 **`LongAdder` 的例子**：**用空間與讀取成本換取寫入的併發度**，**說明同一個抽象可以有針對不同負載的實作**。

### 不可變在併發中真的解決了所有問題嗎？

**核心答案**：**它解決了「資料競爭」但沒有解決「協調」**。不可變讓「讀取時不會看到半完成的狀態」——**但「兩個執行緒都想更新同一個邏輯狀態」的協調問題仍然存在**；**於是仍然需要 CAS、鎖、或者把更新集中到單一的地方**。**所以正確的表述是「不可變消除了一大類的問題，讓剩下的問題更容易處理」。**

**詳細解析**：**「不可變加上一個原子的參考」是一個很有用的組合**：狀態本身不可變——**而一個 `AtomicReference` 指向當前的版本**；**更新是「讀取當前、計算新的、CAS 換上去」**。**於是讀取完全無鎖（拿到的是一個不會變的快照），而寫入用 CAS 協調**。**這正是很多函數式語言中「原子 + 不可變值」的併發模型**（Clojure 的 atom），**而它比「共享可變狀態加鎖」容易推理得多**。**代價是「更新在高競爭下可能反覆重試」**——**而如果更新的計算很貴，那個重試的浪費可觀**；**這時把更新序列化（例如交給一個專門的執行緒）可能更好**。

**面試回答方式**：給精確的區分（**解決了資料競爭但沒解決協調**）與正確的表述。核心加分點是**不可變加上一個原子的參考**這個組合——**讀取無鎖拿到不會變的快照，寫入用 CAS 協調**，**這正是函數式語言的併發模型且比共享可變狀態加鎖容易推理**。收在代價：**高競爭下反覆重試，而如果更新的計算很貴那個浪費可觀**，**這時把更新序列化可能更好**。

### 虛擬執行緒改變了這些模式嗎？

**核心答案**：**改變了成本結構而非正確性的要求**。虛擬執行緒讓「一個請求一個執行緒」的簡單模型重新變得可行——**於是為了避免執行緒成本而採用的複雜方案（響應式程式設計、回呼鏈）在很多場景中不再必要**。**但「共享可變狀態需要同步」這件事完全沒有改變**——**虛擬執行緒之間的競爭與平台執行緒之間的一樣。**

**詳細解析**：**「虛擬執行緒讓簡單的程式碼重新變得可行」是它最大的價值**：響應式的程式碼難寫、難讀、難除錯（堆疊追蹤破碎）——**而它之所以被採用，很大程度上是為了「不要為每個請求佔用一個昂貴的作業系統執行緒」**；**虛擬執行緒消除了那個理由**。**所以在 Java 21 之後，「用阻塞的寫法加虛擬執行緒」在多數 IO 密集的場景中是更好的選擇**。**但要注意兩個新的注意事項**：**`synchronized` 區塊中的阻塞會釘住載體執行緒（較新的版本已改善）**，**以及「執行緒池的意義改變了」**（**虛擬執行緒不該被池化，因為建立它們很便宜；池化反而限制了併發度**）。**這個「舊的最佳實踐在新的成本結構下失效」的模式，值得在採用新特性時主動檢查。**

**面試回答方式**：給精確的回答（**改變了成本結構而非正確性的要求**）並指出**共享可變狀態需要同步這件事完全沒變**。核心加分點是**它讓簡單的程式碼重新變得可行**——**響應式被採用很大程度是為了不佔用昂貴的執行緒，而那個理由被消除了**。收在兩個新注意事項（synchronized 中的阻塞、虛擬執行緒不該被池化）與模式：**舊的最佳實踐在新的成本結構下失效，值得在採用新特性時主動檢查**。
