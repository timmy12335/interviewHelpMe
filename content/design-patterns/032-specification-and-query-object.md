# 題目

規格模式在做什麼？它跟直接寫查詢條件有什麼不同？

## 核心答案

規格模式把「一個條件」變成一個物件——於是條件可以被命名、被組合（and、or、not）、被重用、以及被測試。

**它解決兩個問題**。**業務規則的重複**——「什麼是有效的訂閱」這個判斷可能出現在查詢、驗證、與顯示三個地方；**寫成一個 `ActiveSubscriptionSpec` 之後只有一份**。**以及查詢方法的爆炸**——Repository 中一堆 `findByAAndBAndC`，用規格取代之後只需要一個 `find(Specification)`。

與直接寫條件的關鍵不同是「規格既能在記憶體中判斷也能被翻譯成查詢」：`spec.isSatisfiedBy(order)` 用於驗證單個物件，而同一個規格能被轉成 SQL 的 WHERE 子句——於是「規則只定義一次，兩種用法共用」。

## 詳細解析

「同一個規則有兩種用法」是這個模式最大的價值：「找出所有過期的訂閱」（查詢）與「這個訂閱過期了嗎」（判斷）——在傳統做法中它們是兩份程式碼（一個 SQL、一個 if）；而兩份程式碼會不同步，於是「查詢說過期了但判斷說沒有」這類 bug 出現。規格模式讓它們共用一個定義——這個「單一定義、多處使用」的價值，在規則複雜且會演進時特別明顯。

「實作上的難處在於翻譯成查詢」：一個規格如果只是「一個回傳布林值的函式」——**那它無法被轉成 SQL**；所以需要一個可以被檢視的結構（例如 JPA 的 Criteria API，或者自己定義的表達式樹）。**這增加了實作的複雜度**——而那正是為什麼「完整的規格模式」在實務中不如它的簡化版本常見。常見的簡化是「只用組合的部分」（用 Criteria 或 QueryDSL 建構可組合的查詢條件，但不要求它能在記憶體中求值）——於是拿到了組合與重用的好處而避開了雙重求值的複雜度。

**「規格的命名應該用業務語言」**：`ActiveSubscriptionSpec` 而非 `StatusEqualsActiveAndExpiryAfterNowSpec`——因為前者表達的是概念，而後者只是條件的複述。這個命名的差別決定了「規格模式是否真的提升了可讀性」：用業務名稱組合的查詢讀起來像業務描述，而用條件複述的組合只是把 SQL 換了一種寫法。

**「什麼時候不需要它」**：如果查詢條件簡單且不重複——**直接寫查詢更清楚**；規格模式的間接性只在「同一個規則被多處使用」或「條件需要動態組合」時才划算。而後者的典型場景是「使用者可以自訂篩選條件的介面」——那時把每個篩選項對應到一個規格並動態組合，是一個乾淨的實作。

## 面試回答方式

先給模式的做法（把條件變成物件，可命名、組合、重用、測試）與兩個解決的問題，再說明與直接寫條件的關鍵不同是同一個規格既能在記憶體中判斷也能被翻譯成查詢。加分點有四個：同一個規則有兩種用法是最大的價值——傳統做法中查詢與判斷是兩份會不同步的程式碼；實作上的難處在於翻譯成查詢，而常見的簡化是只用組合的部分；**規格的命名應該用業務語言**——這決定了它是否真的提升可讀性；以及**什麼時候不需要它**，而「使用者自訂篩選條件」是它最划算的典型場景。

## 講稿

規格模式把一個條件變成一個物件，於是條件可以被命名、被組合、被重用、被測試。

它解決兩個問題。業務規則的重複，什麼是有效的訂閱這個判斷可能出現在查詢、驗證、顯示三個地方，寫成一個規格之後只有一份。還有查詢方法的爆炸，一堆組合條件的查詢方法可以被一個接受規格的方法取代。

而它跟直接寫條件的關鍵不同是，同一個規格既能在記憶體中判斷單個物件，也能被翻譯成查詢的條件子句。這是它最大的價值。找出所有過期的訂閱跟這個訂閱過期了嗎，在傳統做法中是兩份程式碼，一個查詢語句一個判斷式。而兩份程式碼會不同步，於是查詢說過期了但判斷說沒有這類問題就出現了。

實作上的難處在於翻譯成查詢。如果規格只是一個回傳布林值的函式，它無法被轉成查詢語句，所以需要一個可以被檢視的結構。這增加了複雜度，所以實務上常見的是簡化版本，只用組合的部分，拿到重用的好處而避開雙重求值的複雜度。

命名上我會用業務語言而不是條件的複述，那決定了它是不是真的提升了可讀性。

## 常見追問

### 這與 QueryDSL 或 Criteria API 有什麼關係？

**核心答案**：它們是規格模式的一種實作基礎。QueryDSL 提供了「型別安全、可組合的查詢條件」——於是你可以把一個 `BooleanExpression` 當成規格傳遞與組合。相比自己實作表達式樹，用它們的好處是「已經解決了翻譯成 SQL 的問題」；而代價是綁定了那個框架，且條件無法在記憶體中對物件求值。

**詳細解析**：「型別安全」是這類工具相對於字串查詢最實質的價值：`order.status.eq(SHIPPED)` 在編譯期就檢查了欄位存在與型別匹配——而 `"status = 'SHIPPED'"` 只有在執行時才會發現拼錯。在有大量查詢且 schema 會演進的專案中，這個差別很明顯：改一個欄位名之後，編譯器會列出所有需要修改的地方。而它的代價是「產生的程式碼」與「額外的建置步驟」——在小專案中那個成本可能不值得。所以判斷的方式與其他工具一樣：查詢的數量與 schema 的變動頻率決定了它是否划算。

**面試回答方式**：說明**它們是規格模式的實作基礎**與各自的好處與代價。核心加分點是**型別安全是最實質的價值**——編譯期檢查欄位與型別，改欄位名時編譯器會列出所有需要修改的地方，而字串查詢只有執行時才發現拼錯。收在判斷：代價是產生的程式碼與額外的建置步驟，所以查詢的數量與 schema 的變動頻率決定它是否划算。

### 複雜的查詢還是該用規格嗎？

**核心答案**：**不一定**。規格擅長「條件的組合」——而複雜的查詢往往涉及 join、聚合、子查詢、以及效能調校；用規格表達它們會非常笨拙且難以優化。所以務實的分工是「簡單而可組合的用規格、複雜的直接寫查詢」——而後者可以放在專門的查詢物件或 DAO 中，與領域層分開。

**詳細解析**：「讀與寫的模型可以不同」是這個分工背後的原則：寫入需要領域物件與規則——而讀取往往只需要一份符合畫面需求的資料；強行用同一套模型會讓兩邊都彆扭（為了顯示一個列表而載入完整的聚合，效能極差）。所以「查詢直接寫 SQL 並回傳一個專用的 DTO」在很多場景中是更好的選擇——**而這正是 CQRS 的輕量形式**。它不需要事件溯源或者分離的資料庫，只需要「承認讀與寫的需求不同」。這個認知能解決很多「ORM 用起來很彆扭」的困惑——因為那些困惑往往來自「用寫入的模型做讀取」。

**面試回答方式**：回答不一定並給分工（簡單可組合的用規格、複雜的直接寫查詢）。核心加分點是**讀與寫的模型可以不同**這個原則——強行用同一套會讓兩邊都彆扭，為了顯示列表而載入完整聚合效能極差，而「查詢直接寫 SQL 回傳專用 DTO」是 CQRS 的輕量形式。收在價值：它不需要事件溯源，只需要承認讀與寫的需求不同，而這能解決很多「ORM 用起來很彆扭」的困惑。

### 規格模式與策略模式有什麼不同？

**核心答案**：規格是「一個判斷」，策略是「一個做法」。規格回答「這個物件符合條件嗎」——它是布林的、可組合的、且有明確的代數（and、or、not）；策略回答「這件事怎麼做」——它可以有任意的回傳值與副作用，而且通常不可組合。規格可以視為策略的一個特化，但它的組合性讓它成為一個獨立有價值的模式。

**詳細解析**：**「組合性是規格獨有的性質」**：兩個策略無法自然地「相加」——而兩個規格可以用 and 組合成一個新的規格，且結果仍然是一個規格。這個閉合性（組合的結果仍是同一種東西）讓規格能被無限地建構——而它正是很多「小的東西組合成大的東西」的設計共有的性質（解析器組合子、函數組合、以及 Unix 的管道）。能看出這個共通性，就能判斷「我的抽象有沒有這個閉合性」——有的話它會很好用，沒有的話組合的邏輯要寫在外面，那通常意味著抽象還可以更好。

**面試回答方式**：給核心區分（**規格是判斷、策略是做法**）與各自的特性。核心加分點是**組合性是規格獨有的性質**——兩個規格可以組合成一個新的規格且結果仍是規格，而這個閉合性讓它能被無限建構。收在共通性：這是很多「小的組合成大的」設計共有的性質（解析器組合子、函數組合、Unix 管道），而「我的抽象有沒有這個閉合性」是一個好用的判斷。
