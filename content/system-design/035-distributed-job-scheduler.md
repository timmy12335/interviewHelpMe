# 題目

設計一個分散式任務排程系統，支援定時任務、延遲任務與失敗重試。

## 核心答案

**拆成三層**：**排程層**（決定「什麼時候該跑什麼」）、**派發層**（把到期的任務交給執行者）、**執行層**（實際跑任務並回報結果）。三層分離的理由是它們的擴展需求完全不同——排程需要一致性，執行需要吞吐。

排程的核心資料結構是「按下次執行時間排序的任務表」。掃描器週期性地取出 `next_run_time <= now` 的任務，**用樂觀鎖或條件更新搶佔**（`UPDATE ... SET status='dispatched' WHERE id=? AND status='pending'`），**避免多個排程器重複派發**。任務量大時改用時間輪或分片掃描：按任務 ID 雜湊分片，每個排程器只負責自己的分片。

**執行的可靠性靠三件事**：**冪等**（任務可能被執行多次，這是必須接受的前提）、**心跳與租約**（執行者定期續租，租約過期則任務被重新派發）、**明確的重試策略**（次數、退避、以及最終進入死信）。

**交付語義只能做到至少一次**——因為「執行完成」與「回報完成」之間永遠有一個窗口。

## 詳細解析

「至少一次」不是實作偷懶，而是分散式的本質。執行者跑完任務後、回報結果前掛掉，排程器無法區分「沒跑」與「跑了但沒回報」——**它只能重新派發**。所以任務的冪等是使用者必須承擔的責任，而系統應該**提供工具**：一個穩定的執行 ID（同一次排程的重試共用），**讓業務方能用它做去重**。

**時間的正確性比想像中難**。**Cron 表達式牽涉時區與夏令時間**——「每天凌晨兩點」在夏令時間切換那天可能不存在或出現兩次。明確的處理是「排程一律用 UTC 儲存與計算，顯示時才轉當地時區」，並對這兩種邊界情況定義行為（不存在則順延、重複則只跑一次）。這是一個小細節，但它在面試中很能區分「做過」與「聽過」。

任務堆積是排程系統最常見的故障。當執行變慢或執行者不足時，到期的任務會累積——而如果排程器不加限制地持續派發，會把下游徹底壓垮。**正確的做法是「派發側限流」**：限制同時處於執行中的任務數，以及每個租戶的併發配額。同時要監控「任務的實際開始時間與預期開始時間的差」——這個延遲指標比「任務成功率」更早暴露問題。

**優先級與隔離**：不同重要性的任務應該進入**不同的佇列與執行者池**，避免一批低優先級的長任務餓死高優先級的短任務。這與執行緒池的隔離是同一個道理——共用資源在異常時會互相拖累。

## 面試回答方式

先給三層拆分（排程、派發、執行）並說明**理由是它們的擴展需求不同**——排程要一致性，執行要吞吐。給排程的核心結構（按下次執行時間排序、條件更新搶佔避免重複派發、量大時分片掃描）與執行的三件事（冪等、心跳與租約、重試策略）。明確指出**只能做到至少一次**。加分點有四個：**「至少一次」是本質而非偷懶**——執行完成與回報完成之間永遠有窗口，所以系統應該提供穩定的執行 ID 讓業務方去重；**時間的正確性**——一律用 UTC 儲存計算、顯示時才轉時區，並對夏令時間造成的「不存在」與「重複」定義行為；**任務堆積要靠派發側限流**，並監控「實際開始與預期開始的差」，它比成功率更早暴露問題；以及優先級要用不同佇列與執行者池隔離。

## 講稿

我會拆成三層，排程、派發、執行。理由是它們的擴展需求完全不同，排程需要一致性，執行需要吞吐。

排程的核心是一張按下次執行時間排序的任務表。掃描器取出到期的任務，用條件更新搶佔，避免多個排程器重複派發。量大的時候就按任務編號雜湊分片，每個排程器只管自己那片。

執行的可靠性靠三件事，冪等、心跳續租、還有明確的重試策略。這裡要說清楚一點，交付語義只能做到至少一次。執行者跑完任務但還沒回報就掛掉的時候，排程器沒辦法區分沒跑跟跑了沒回報，它只能重新派發。所以冪等是業務方必須承擔的責任，而系統該做的是提供一個穩定的執行編號讓他們去重。

還有兩個實務上很常踩的。時間一律用世界協調時間儲存跟計算，顯示才轉當地時區，並且要定義夏令時間那天不存在或重複的行為。另外是任務堆積，派發側一定要限流，而且要監控實際開始時間跟預期開始時間的差，那個指標比成功率更早暴露問題。

## 常見追問

### 延遲任務怎麼實作？

**核心答案**：**三種常見方案，按量級選**。**資料庫輪詢**——最簡單，`WHERE fire_at <= now`，適合每秒幾百筆以內。**Redis ZSet**——以到期時間戳為 score，用 `ZRANGEBYSCORE` 取到期任務，吞吐高但要處理持久化與原子彈出。**時間輪**——記憶體中的環形陣列，O(1) 的新增與到期檢查，適合海量短延遲，但需要自己處理持久化與重啟恢復。

**詳細解析**：「多層時間輪」解決的是長延遲的問題。單層時間輪的槽數決定了最大延遲——要支援一個月後執行就需要巨量的槽。多層設計（秒輪、分輪、時輪）讓長延遲的任務先掛在粗粒度的層，到期時再降級到細粒度的層，這與時鐘的時分秒三個指針是同一個結構。而實務上更常見的選擇是「分層儲存」：遠期任務放資料庫，臨近的（例如未來五分鐘內）才載入到記憶體結構——它結合了資料庫的持久性與記憶體結構的效率，而且重啟恢復很簡單，重新載入未來五分鐘的任務即可。

**面試回答方式**：給三種方案與各自的適用量級（資料庫輪詢、Redis ZSet、時間輪）。加分點是解釋**多層時間輪解決長延遲**——單層的槽數決定最大延遲，多層讓長延遲先掛在粗粒度層、到期再降級，**與時鐘的時分秒指針同構**。真正實用的收尾是**分層儲存**：遠期放資料庫，未來五分鐘內才載入記憶體——結合持久性與效率，而且重啟恢復只需重新載入近期任務。

### 怎麼保證同一個任務不會被兩個執行者同時跑？

**核心答案**：**用租約而非鎖**。派發時給任務一個**帶到期時間的租約**，**執行者必須定期續租**；租約過期後任務才會被重新派發。但這只能降低機率，不能完全排除——執行者可能因為 GC 停頓或網路分割而「以為自己還持有租約」，實際上租約已過期並被重新派發。

**詳細解析**：**這正是分散式鎖的根本限制**：任何基於時間的租約都無法對抗「持有者暫停」的情況。能真正做到互斥的方式是「柵欄令牌」——租約帶一個單調遞增的版本號，執行者對外部系統寫入時帶上它，外部系統拒絕比已見過的更小的版本。但這要求外部系統配合，多數情況做不到。**所以務實的結論回到冪等**：與其追求「絕對不會重複執行」，不如讓「重複執行是無害的」——前者在分散式系統裡不可能，後者只是一個設計約束。能主動說出這個轉換，比背出各種鎖的實作更能證明理解。

**面試回答方式**：先給租約機制與續租，然後誠實指出它只能降低機率不能排除——GC 停頓或網路分割會讓執行者以為自己還持有租約。加分點是說明**這是分散式鎖的根本限制**，並給出**柵欄令牌**這個理論上的解法與它的前提（要求外部系統配合，多數情況做不到）。收在務實的結論：與其追求絕對不重複執行，不如讓重複執行無害——前者在分散式系統裡不可能，後者只是一個設計約束。

### 排程器自己掛了怎麼辦？

**核心答案**：**多實例加分片，而非主從**。每個排程器負責一部分任務分片（按任務 ID 雜湊），用一個協調服務（etcd、ZooKeeper、或資料庫的租約表）管理分片的歸屬。某個實例掛掉時，它的分片被其他實例接管。這比「一主多備」好，因為備用實例平時完全閒置，而且主備切換本身是一個容易出錯的過程。

**詳細解析**：分片重新分配的瞬間是危險窗口：舊持有者可能還沒感知到自己失去了分片，而新持有者已經開始掃描——**於是同一批任務被派發兩次**。緩解方式是「先等待一個租約週期再接管」，**代價是那段時間任務會延遲**。而這又一次指向同一個結論：重複派發是無法完全避免的，冪等是最終的防線。 另一個實務要點是「排程器的掛掉必須被快速發現」——**它的失效是靜默的**（沒有任務被派發，但也沒有錯誤），所以要監控「單位時間內派發的任務數」而非只監控排程器行程是否存活：行程活著但卡住的情況比行程死掉更常見也更難發現。

**面試回答方式**：主張**多實例加分片而非主從**，並給理由（備用實例平時閒置，主備切換本身容易出錯）。加分點是點出分片重新分配的瞬間是危險窗口——舊持有者還沒感知就被新持有者接管會造成重複派發，緩解是先等一個租約週期再接管，代價是延遲，而這再次指向冪等是最終防線。最後給一個容易被忽略的監控要點：**排程器的失效是靜默的**，要監控單位時間派發的任務數而非行程存活——行程活著但卡住比行程死掉更常見也更難發現。
