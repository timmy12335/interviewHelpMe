# 題目

系統中出現熱點資料或熱點分片時，有哪些處理手段？怎麼選？

## 核心答案

先分清熱點的類型，因為它們的解法完全不同。

**讀熱點**——大量請求讀同一個鍵（明星發文、爆款商品）。解法是**多層快取**：**本地快取擋住絕大多數**（同一個鍵在單機上只需要一份），**再到分散式快取**，**最後才是資料庫**。本地快取是這裡效益最高的一招，因為它把「N 台機器都打 Redis」變成「N 台機器各自命中記憶體」。

**寫熱點**——大量寫入落在同一個鍵或同一個分片（秒殺庫存、熱門計數）。解法是**拆分**：把一個計數器拆成 N 個子計數器分散到不同分片，讀取時求和；**或者聚合**：在記憶體中累積一段時間再批次寫入。

**分片傾斜**——某個分片的資料量或流量遠超其他。解法是**改變分片鍵**（加隨機後綴、改用複合鍵）或**單獨拆分那個熱點**。

而所有解法的前提是「先能發現熱點」——沒有按鍵維度的統計，你只會看到「某個分片很慢」而不知道是哪個鍵。

## 詳細解析

「發現熱點」比「處理熱點」更需要被設計。多數監控只有分片級或服務級的指標——它告訴你「這個節點 CPU 很高」，卻不告訴你「因為 product:8848 這個鍵佔了七成請求」。**可行的做法有三種**：**在客戶端做取樣統計**（每 100 次請求記錄一次鍵，成本極低）、**用 Redis 的 hotkeys 或 monitor 抽樣**、**以及在閘道層做 top-k 統計**（用 Count-Min Sketch 這類概率結構，記憶體固定）。建立這個能力之後，熱點從「事故時的猜測」變成「日常可見的指標」。

**本地快取的代價是一致性**。每台機器各自持有一份副本——更新時無法保證所有機器同時失效，所以只適合「短時間陳舊可接受」的資料。**實務的做法是「極短的 TTL」**（1 到 5 秒）：它讓陳舊窗口有明確上限，同時仍能擋掉 99% 以上的請求——因為熱點的定義就是「每秒成千上萬次訪問」，即使只快取一秒也擋掉了幾千次。這個「用極短 TTL 換取巨大收益」的計算，是熱點處理裡最反直覺也最有效的一點。

寫熱點的拆分有一個代價要說清楚：**讀取時需要聚合 N 個子計數器**——**讀變慢了**。所以子計數器的數量是一個取捨：太少擋不住寫入壓力，太多讓讀取變慢。**常見的折衷是「按需拆分」**：平時不拆，偵測到熱點時動態地把該鍵拆成多份——這需要一層間接的路由，但避免了對所有鍵付出代價。

**傾斜有時候是無法消除的**。如果業務本身就是「一個賣家佔了平台一半的訂單」，那麼任何分片策略都會讓那個分片更重——這時正確的做法是承認它並為它單獨配置資源（獨立的分片、更好的硬體、獨立的限流），而不是追求一個並不存在的均勻分布。

## 面試回答方式

先做分類——讀熱點、寫熱點、分片傾斜的解法完全不同，並給各自的手段（多層快取以本地快取為主、拆分計數器或記憶體聚合、改變分片鍵或單獨拆分）。強調所有解法的前提是先能發現熱點。加分點有四個：「發現熱點」比「處理熱點」更需要被設計——多數監控只有分片級指標，告訴你節點 CPU 高卻不告訴你是哪個鍵，並給三種做法（客戶端取樣、Redis hotkeys、閘道層的 Count-Min Sketch）；本地快取用極短 TTL 換取巨大收益——熱點每秒成千上萬次訪問，即使只快取一秒也擋掉幾千次，這是最反直覺也最有效的一點；寫熱點拆分的代價是讀取要聚合，所以子計數器數量是取捨，折衷是按需動態拆分；以及**傾斜有時無法消除**——業務本身就傾斜時，正確做法是承認並為它單獨配置資源。

## 講稿

我會先分清熱點的類型，因為解法完全不同。

讀熱點是大量請求讀同一個鍵。解法是多層快取，而本地快取是效益最高的一招，因為它把 N 台機器都打快取伺服器變成 N 台機器各自命中記憶體。

寫熱點是大量寫入落在同一個鍵或分片。解法是拆分成多個子計數器分散，讀取時求和，或者在記憶體累積一段時間再批次寫。

分片傾斜就是改分片鍵或者把熱點單獨拆出來。

但所有解法的前提是先能發現熱點，而這件事比處理熱點更需要被設計。多數監控只有分片級指標，它告訴你某個節點負載很高，卻不告訴你是哪個鍵造成的。我會在客戶端做取樣統計，或在閘道層用概率結構做 top-k。

還有一個反直覺但很有效的計算。本地快取的代價是一致性，所以我會用極短的存活時間，一到五秒。熱點的定義就是每秒成千上萬次訪問，即使只快取一秒也擋掉了幾千次，而陳舊窗口有明確上限。

## 常見追問

### 快取擊穿與雪崩怎麼防？

**核心答案**：擊穿是「一個熱點鍵過期，瞬間大量請求同時打到資料庫」——**解法是單飛（singleflight）**：同一個鍵的併發請求只讓一個去查資料庫，其餘等待並共用結果。**雪崩是「大量鍵同時過期」**——**解法是給 TTL 加隨機抖動**，**把過期時間分散開**。兩者都可以用「邏輯過期」進一步緩解：快取值本身帶一個過期標記，過期後仍返回舊值，同時觸發背景更新——**讓使用者永遠不等待**。

**詳細解析**：「邏輯過期」是這三個方案裡最強的，但它改變了語意：快取永不真正失效，所以在極端情況下可能返回很舊的資料（如果背景更新持續失敗）。**所以它需要配合監控**——追蹤「返回的值有多舊」，而不只是快取命中率。單飛則有一個容易被忽略的細節：它只在單機內生效——一百台機器就會有一百個請求打到資料庫。如果那還是太多，需要分散式的單飛（用一個短時的分散式鎖），**但那引入了新的失敗模式**（鎖持有者掛掉導致其他人長時間等待）。所以實務上的順序是：先加隨機抖動（幾乎零成本）、再加單機單飛（低成本）、最後才考慮邏輯過期或分散式單飛。

**面試回答方式**：清楚區分擊穿與雪崩並給各自的解法（單飛、TTL 隨機抖動），再給邏輯過期作為更強的方案。加分點是說明**邏輯過期改變了語意**——快取永不真正失效，背景更新持續失敗時可能返回很舊的資料，所以要追蹤「返回的值有多舊」而不只是命中率。第二個是**單飛只在單機內生效**，**一百台機器就是一百個請求**，分散式單飛引入新的失敗模式。收在實務順序：先隨機抖動、再單機單飛、最後才考慮邏輯過期。

### 怎麼判斷該加快取還是該優化查詢？

**核心答案**：**先看「這個查詢本身該多快」**。如果一個查詢因為缺索引或寫法糟糕而需要 500 毫秒，**加快取只是把問題藏起來**——快取失效時它仍然是 500 毫秒，而那時的併發會更糟。正確的順序是「先讓查詢達到它應有的效能，再考慮快取是否還必要」。快取應該用來解決「即使優化到極致仍然太慢或太貴」的問題，而不是用來掩蓋可以修好的問題。

**詳細解析**：「快取掩蓋問題」的代價會在最壞的時刻顯現。快取節點重啟、大規模失效、或者流量模式改變導致命中率下降時——未經優化的查詢會以完整的壓力打到資料庫，而那時系統正處於最脆弱的狀態。所以一個實用的檢驗是「假設快取完全失效，系統還活得下去嗎」：答案是否定的話，那個快取就從「優化」變成了「隱藏的單點」。**這不代表不能依賴快取**——有些場景（例如熱點讀）本來就必須依賴——但那應該是一個明知的、被監控與演練過的依賴，而不是無意中形成的。能區分這兩者，是快取設計裡最重要的判斷。

**面試回答方式**：給明確的順序——先讓查詢達到應有的效能，再考慮快取是否必要，並指出加快取只是把問題藏起來，失效時仍然是 500 毫秒而併發更糟。核心加分點是給出檢驗標準：假設快取完全失效，系統還活得下去嗎——答案否定的話，那個快取就從優化變成了隱藏的單點。收在區分：依賴快取本身沒錯，但那應該是明知的、被監控與演練過的依賴，而不是無意中形成的。

### 熱點是動態變化的，怎麼自動應對？

**核心答案**：**建立「偵測到自動處置」的閉環**。閘道層持續統計 top-k 的鍵；某個鍵的 QPS 超過閾值時自動觸發本地快取（把它加入一個動態的本地快取白名單並下發到所有節點）；**熱度下降後自動移除**。**同時對超標的鍵自動限流**，**保護後端不被單一熱點壓垮**。

**詳細解析**：「自動處置」的風險在於它可能做錯決定——把一個正常的高頻鍵誤判為需要強一致的資料而快取它。所以自動化必須有明確的邊界：只對顯式標記為「可快取」的資料生效，而涉及金額、庫存、權限的鍵永遠不進入自動快取。這條規則應該在程式碼層面表達（例如鍵的命名空間決定它是否可被自動快取），**而不是靠設定或人的記憶**。另一個實務要點是「處置動作要能被快速回退」：自動化在異常情況下可能放大問題（例如誤判導致大量鍵被本地快取而記憶體爆掉）——所以要有一個全域開關能立即停用整套自動處置，**回到人工模式**。任何自動化系統都應該有這個逃生口。

**面試回答方式**：給閉環設計（top-k 統計、超閾值自動啟用本地快取並下發、熱度下降自動移除、超標自動限流）。核心加分點是**自動化必須有明確邊界**：只對顯式標記為可快取的資料生效，涉及金額、庫存、權限的鍵永不進入自動快取，而這條規則要在程式碼層面表達（例如用鍵的命名空間），不能靠設定或人的記憶。收在**處置動作要能快速回退**——自動化在異常時可能放大問題，所以要有全域開關立即回到人工模式，任何自動化系統都應該有這個逃生口。
