# 題目

單機限流器的計數器放在記憶體裡就能運作，但當限流器擴展成多台實例時，會遇到什麼問題？請說明「競態條件」與「同步問題」各自是什麼，以及有哪些解法與取捨。

## 核心答案

單機限流器之所以簡單，是因為「計數」和「判斷」發生在同一份記憶體裡。一旦擴展成多台實例，兩個問題會同時浮現。**（1）競態條件（Race Condition）**——即使所有實例共用一份集中式計數（如 Redis），典型的「讀取目前計數 → 加一 → 寫回」這個三步驟不是原子操作，高併發下多個請求可能都讀到同一個舊值，各自加一後寫回，導致**實際放行的請求數超過門檻**。解法是讓計數更新變成**單一原子操作**——用 Redis 的 `INCR`（本身即原子）搭配 `EXPIRE`，或把整段判斷邏輯寫成 **Lua 腳本**在 Redis 端一次執行完（避免 `INCR` 與 `EXPIRE` 之間出現空隙導致鍵永不過期），而不是用分散式鎖（鎖會讓每個請求都多一輪往返與競爭，嚴重拖慢本應極廉價的限流判斷）。**（2）同步問題（Synchronization）**——如果為了效能讓每台實例各自在本機記憶體計數，就會出現「N 台實例各自允許 X 次，整體實際放行 N×X 次」的超放行；若改用集中式計數雖然準確，但**每個請求都要多一次網路往返**，且集中儲存成為單點與瓶頸。解法是在兩端之間取捨——要求嚴格準確就用集中式計數（並用讀寫分離、分片等方式擴展它）；能容忍誤差就讓每台實例**只分配到總配額的 1/N**，或採用本機計數 + 定期非同步同步彙總的近似做法，用一定的精度換取延遲與可用性。

## 詳細解析

**競態條件的本質，是「檢查」與「行動」之間存在空隙**：限流判斷在邏輯上是「先看目前用了幾次，如果還沒到上限就放行並記一次」，這個描述裡的「看」和「記」是兩個獨立步驟。在單機單執行緒的世界裡這沒有問題，但只要有併發，兩個請求就可能同時完成「看」（都看到 99 次，門檻是 100），然後各自完成「記」（都認為自己是第 100 次），結果放行了 101 次。這是併發程式設計裡典型的 **check-then-act** 問題，與資料庫的樂觀鎖、Java 的 `i++` 非原子性是完全同一類問題。理解這一點的價值在於——**解法的方向是消除空隙，而不是加鎖排隊**。Redis 的 `INCR` 之所以是正確的解法，是因為它把「加一並回傳新值」壓縮成一個不可分割的操作：每個請求拿到的都是**它自己造成的那個唯一結果**，不存在兩個請求拿到同一個值的可能，於是「是否超過門檻」的判斷可以直接基於這個回傳值做出，中間沒有任何空隙。

**為什麼不建議用分散式鎖解決這個競態**：分散式鎖確實能保證正確性，但它的代價與限流器的定位嚴重衝突。限流器位於**每一個請求的關鍵路徑**上，它必須極度廉價；而分散式鎖要求每個請求至少多一次「取鎖」與一次「釋放鎖」的往返，並且在高併發下大量請求會**排隊等待同一把鎖**，把原本可以完全並行的計數操作，硬生生序列化。更糟的是，限流器本來就是在流量暴增時最需要正常工作的元件，而流量暴增正是鎖競爭最劇烈、等待最久的時刻——這等於讓限流器在最需要它的時候表現最差。用原子操作（`INCR`）或把邏輯下推到儲存端一次執行（Lua 腳本）之所以是更好的解法，正是因為它們在**不引入等待**的前提下消除了空隙。

**`INCR` 加 `EXPIRE` 為什麼還需要 Lua**：一個常見的實作是「`INCR` 這個鍵，如果回傳值是 1 代表是本視窗第一次，就再下一個 `EXPIRE` 設定過期時間」。問題在於這兩個命令之間仍有空隙——如果實例在 `INCR` 成功之後、`EXPIRE` 送出之前崩潰，這個鍵就會**永遠不過期**，該維度的計數再也不會重置，等於這個使用者被永久封鎖。把「遞增、必要時設定過期、比較門檻、回傳結果」整段寫成 Lua 腳本交給 Redis 執行，因為 Redis 執行腳本期間不會插入其他命令，整段邏輯就具備了原子性，這個空隙才真正被消除。這也說明了一個更普遍的觀念——**「用了原子命令」不等於「整段邏輯是原子的」，要看的是有沒有把所有必須一起發生的步驟都包進同一個不可分割的單位裡**。

**同步問題是一個精度與成本的取捨，而不是有唯一正解**：本機計數的優點是判斷完全不需要網路、延遲最低、且集中儲存掛掉也不影響限流，缺點是整體放行量會膨脹成 N 倍（N 為實例數）。有人會想用「黏性會話」把同一個使用者永遠導到同一台實例來解決，但這會與負載平衡（見 [[003-load-balancing.md]]）的均衡目標衝突，而且實例增減時對應關係會變動，反而製造新的問題。集中式計數的優點是全域準確，缺點是每個請求多一次往返、且集中儲存本身要能承受全部流量。中間地帶有兩種常見做法：一是**配額均分**，讓每台實例只允許總量的 1/N，實作簡單、不需要任何同步，代價是當流量分佈不均時會過早拒絕（某台實例的配額用完了，但別台還有剩）；二是**本機計數加定期彙總**，各實例在本機快速判斷，同時定期把用量上報並取回全域概況來修正本機門檻，這種做法在精度與延遲之間取得平衡，但實作複雜且在同步週期內仍有誤差。選哪一種，取決於這道限流的目的——如果是保護容量，稍微超放行通常無傷大雅，可以選延遲更低的方案；如果是執行計費配額或安全防護，就必須選全域準確的集中式方案。

## 面試回答方式

先把兩個問題明確分開，很多人會把它們混為一談——「競態條件是就算用了集中式計數也會發生的正確性問題；同步問題是要不要用集中式計數這個架構選擇本身的問題」。談競態時把它歸類到 check-then-act 這個通用模式（和樂觀鎖、`i++` 是同一類），說明解法方向是**消除空隙而非加鎖**，並主動說明為什麼不建議用分散式鎖——限流器在每個請求的關鍵路徑上，而鎖會在流量暴增（也就是最需要限流器的時刻）競爭最劇烈，讓它在最需要它的時候表現最差。接著給出 `INCR` 的解法，並進一步指出 `INCR` + `EXPIRE` 兩個命令之間仍有空隙（實例在中間崩潰會導致鍵永不過期、使用者被永久封鎖），所以要用 Lua 腳本把整段包成原子——這個細節很能展現實作經驗。談同步問題時不要給單一答案，而是給出取捨光譜：本機計數（快、但整體放行 N 倍）、集中式（準、但多一次往返且是瓶頸）、配額均分與定期彙總這兩個中間方案，最後用「這道限流的目的是保護容量還是執行計費／安全契約」作為選擇準則收尾。

## 常見追問

### 集中式計數的 Redis 成為瓶頸或掛掉時，限流器要怎麼辦？

**核心答案**：分兩個層面處理。**效能瓶頸**方面，限流計數的存取模式有一個很好的特性——**不同的限流鍵之間完全獨立**（使用者 A 的計數和使用者 B 的計數毫無關聯），這代表它天生適合**依鍵分片**（見 [[../redis/018-redis-cluster.md]] 的雜湊槽設計），把不同鍵的計數分散到多個 Redis 節點，容量與吞吐可以線性擴展，這比多數需要跨鍵交易的場景容易得多。**可用性**方面，一般的容量保護型限流應該採 **fail-open**——當 Redis 不可用時放行請求，而不是把服務整個擋死；更穩健的做法是**降級到本機計數**，也就是 Redis 正常時用全域準確的集中計數，Redis 故障時自動退回到每台實例各自的本機計數（雖然整體會放行 N 倍，但至少還保有基本的防護，比完全放行好），等 Redis 恢復再切回去。但如果這道限流是為了安全或計費，就必須 fail-close，不能因為儲存故障而放棄執行契約。

**詳細解析**：這題考察是否理解「集中式方案的單點問題，可以分成擴展性與可用性兩個獨立的子問題」，以及能否針對限流這個具體場景給出貼合的答案。關於擴展性，關鍵的洞察是**限流計數的資料存取模式異常單純**——每次操作只涉及單一個鍵、沒有跨鍵的交易需求、也沒有範圍查詢，這種「完全按鍵隔離」的特性，使得水平分片幾乎沒有障礙，這與那些需要跨分片交易或全域排序的場景形成鮮明對比。理解這一點能讓你在面試中給出一個有說服力的判斷：「集中式計數會成為瓶頸」這個擔憂，在限流這個特定場景下，其實比一般的集中式儲存要容易緩解得多。關於可用性，關鍵在於認識到「Redis 掛掉」與「限流失效」之間，其實還有一個**中間狀態**可以利用——多數人會直接跳到 fail-open 或 fail-close 這個二選一，但「降級到本機計數」提供了第三條路：它承認在故障期間無法維持全域準確，但保留了「每台實例仍然會擋掉明顯超量的來源」這個基本能力，把防護從「精確」降級成「粗略」，而不是從「精確」降級成「完全沒有」。這種「故障時降級到一個較弱但仍有效的模式，而非直接放棄功能」的思路，是可用性設計裡很有價值的一般性模式，它同樣體現在快取失效時退回讀資料庫、推薦系統故障時退回熱門榜單等場景。理解「限流計數因為完全按鍵隔離、無跨鍵交易需求，所以水平分片幾乎沒有障礙，擴展性問題比一般集中式儲存好解決；可用性方面除了 fail-open／fail-close 這個二選一之外，還有降級到本機計數這條中間路，把防護從精確降級成粗略而非完全放棄，但安全與計費型的限流仍必須 fail-close」，展現你能把通用的可用性思路，具體落到這個場景的資料特性上。

**面試回答方式**：先把問題拆成擴展性與可用性兩個子問題，不要混在一起答。談擴展性時給出限流資料的關鍵特性——「限流計數是完全按鍵隔離的，沒有跨鍵交易也沒有範圍查詢，所以依鍵分片幾乎沒有障礙，這比一般集中式儲存好擴展得多」。談可用性時，不要停在 fail-open／fail-close 的二選一，主動提出第三條路——「更穩健的做法是降級到本機計數，Redis 正常時用全域準確的集中計數，故障時自動退回每台實例各自計數，防護從精確降級成粗略而不是完全消失」。最後補上例外——「但如果這道限流是為了安全或計費，必須 fail-close，不能因為儲存故障就放棄執行契約」。展現你能給出比標準答案更細緻的中間方案。

### 為什麼滑動視窗計數這類演算法，在分散式環境下比固定視窗更難實作？

**核心答案**：固定視窗只需要維護**一個數字**（這個視窗內的計數），這個數字可以用單一次 `INCR` 原子地更新，狀態極小、同步成本極低。滑動視窗日誌則需要保存**視窗內每一次請求的時間戳**，狀態量與請求量成正比，在分散式環境下這代表：儲存成本高（高流量的鍵可能累積大量時間戳）、每次判斷都要清理過期項目並計數（操作比單純 `INCR` 昂貴得多）、且這一整段「清理 + 計數 + 判斷 + 寫入」必須原子執行，否則又回到競態問題。滑動視窗計數器是常見的折衷——它只保存**目前視窗與前一個視窗的兩個計數**，用加權估算跨越邊界的流量，狀態仍然極小（兩個數字），卻大幅緩解了固定視窗的邊界突刺問題，因此在分散式場景下最常被採用。

**詳細解析**：這題考察是否理解「演算法選擇在分散式環境下，會被一個單機環境不太在意的因素主導——**需要同步的狀態大小與操作複雜度**」。在單機記憶體裡，維護一個時間戳列表和維護一個整數，成本差異不算太顯著；但一旦這份狀態必須被多台實例共享，差異就被急遽放大：整數可以用單一個原子命令更新完畢，一次往返、極小的網路負載；時間戳列表則需要「移除視窗外的舊項目、計算剩餘數量、判斷是否超限、加入新項目」這一整組操作，不但資料量大，而且必須整組原子執行（否則兩個請求可能同時完成清理與計數、各自認為未超限）。這使得原本在單機下「精度更好」的演算法，在分散式下承擔了不成比例的成本，且這個成本在**高流量的熱鍵上最嚴重**——恰恰是最需要限流的那些鍵，狀態最大、操作最貴，形成了與需求相反的成本曲線。滑動視窗計數器的價值就在這裡：它用一個近似的假設（前一個視窗內的請求是均勻分佈的），把「精確追蹤每次請求」換成「只維護兩個計數 + 一次加權計算」，狀態量從 O(請求數) 降回 O(1)，同時保留了大部分的精度改善。這個取捨體現了一個在分散式系統設計中反覆出現的模式——**當一個精確方案的狀態量隨規模增長時，往往值得用一個有界狀態的近似方案取代它**，同樣的思路也出現在用布隆過濾器（見 [[../redis/024-bloom-filter.md]]）取代精確集合、用近似基數統計取代精確去重等場景。理解「分散式環境下演算法的選擇被同步狀態大小與操作原子性主導，滑動視窗日誌的狀態量與請求量成正比且在熱鍵上最貴，形成與需求相反的成本曲線；滑動視窗計數器用均勻分佈的近似假設把狀態壓回常數級，是精度與成本的最佳折衷，這體現了用有界狀態的近似方案取代無界狀態精確方案的通用模式」，展現你能看出演算法取捨在單機與分散式環境下的評判標準會發生轉移。

**面試回答方式**：先點出分散式環境下評判標準的轉移——「單機下比的是精度與記憶體，分散式下真正主導決策的是需要同步的狀態大小與操作能否原子執行」。用對比講清楚差異——「固定視窗只有一個數字，一次 `INCR` 就更新完；滑動視窗日誌要保存視窗內每個時間戳，還要整組原子地做清理、計數、判斷、寫入」。點出最關鍵的矛盾——「而且狀態量與流量成正比，代表最需要限流的熱鍵，狀態最大、操作最貴，成本曲線和需求方向相反」。給出折衷方案與它的假設——「滑動視窗計數器只留目前和前一個視窗兩個計數，用前一視窗均勻分佈的假設加權估算，狀態壓回常數級」。最後提升到通用模式——「這和用布隆過濾器取代精確集合是同一個思路：當精確方案的狀態量隨規模增長，就用有界狀態的近似方案取代它」。

### 如果限流器本身也要多機部署，這些實例之間需要選主或達成共識嗎？

**核心答案**：**通常不需要**。限流器實例之間是**完全對等、無狀態**的——每個實例拿到請求後，各自去讀寫共用的計數儲存並做出判斷，實例之間不需要知道彼此的存在、不需要協調、也沒有「哪一台說了算」的問題，因為**權威狀態被外部化到了計數儲存裡**，實例本身只是無狀態的計算單元。這正是為什麼限流器很容易水平擴展：加機器就是加吞吐，不需要重新選主或搬移狀態。需要共識的情況只出現在**把權威狀態放回實例內部**的設計裡——例如採用「本機計數 + 定期彙總」時，如果要有一個角色負責彙總全域用量並重新分配各實例的配額，那個角色就需要選主與故障接管；但這是為了追求更低延遲而主動引入的複雜度，不是限流本身固有的需求。

**詳細解析**：這題考察是否理解「有狀態」與「無狀態」的判斷準則，以及共識機制該在什麼時候引入。理解的關鍵，在於分辨**狀態放在哪裡**——限流這件事本身當然是有狀態的（必須記得某個使用者已經用了幾次），但這份狀態被放在了實例之外的共用儲存裡，於是**實例本身**變成無狀態的：任何一台實例處理任何一個請求，結果都相同；一台實例掛掉，它身上沒有任何獨有的資料會遺失；新加一台實例，它不需要從別處同步任何東西就能立刻開始工作。這三個性質正是「無狀態服務」的定義，而它們直接推導出「不需要選主、不需要共識、可以任意水平擴展」這個結論。共識機制（如 Raft、Paxos）解決的是「**多個副本各自持有狀態，必須就這些狀態的值達成一致**」這個問題，當狀態根本不在實例上時，這個問題不存在，強行引入共識只會增加延遲與運維複雜度。反過來看，一旦設計改成「每台實例在本機記憶體維護計數」，實例就變成有狀態的了——這時如果還想維持全域準確，就不得不面對「這些分散的計數如何彙總、由誰彙總、彙總者掛了怎麼辦」這一連串問題，共識或選主就會被迫進場。這個對照揭示了一個重要的設計槓桿：**把狀態外部化，往往能把一個需要分散式共識的困難問題，降級成一個只需要水平擴展無狀態實例的簡單問題**，代價是對外部儲存的依賴與一次額外的網路往返。這個模式在無狀態 Web 服務把會話存進 Redis、在計算與儲存分離的架構裡都能看到。理解「限流器實例因為把權威狀態外部化到共用儲存而成為無狀態單元，所以不需要選主或共識、可任意水平擴展；共識只在把狀態放回實例內部（如本機計數加彙總者）時才被迫引入；把狀態外部化能把分散式共識問題降級為無狀態擴展問題，代價是對外部儲存的依賴與一次網路往返」，展現你能從狀態的放置位置，推導出整個架構的複雜度層級。

**面試回答方式**：直接回答「通常不需要」，然後給出根本原因——「限流這件事有狀態，但狀態被外部化到共用儲存了，所以**實例本身**是無狀態的」。用無狀態的三個性質支撐結論——「任何實例處理同一請求結果相同、實例掛掉沒有獨有資料遺失、新實例不需同步任何東西就能工作」，並指出這三點直接推導出不需選主、可任意擴展。接著說明共識什麼時候才會需要——「只有當設計改成每台實例在本機記憶體計數，實例變成有狀態的，才會被迫面對誰來彙總、彙總者掛了怎麼辦這些問題」。最後提煉成通用槓桿——「把狀態外部化，能把一個需要分散式共識的困難問題，降級成只需要水平擴展無狀態實例的簡單問題，代價是多一次網路往返和對外部儲存的依賴」。
