# 題目

設計一個秒殺系統：一萬件商品，預期百萬人同時搶購。

## 核心答案

**核心思路是「層層過濾」**——讓絕大多數請求在到達庫存扣減之前就被擋掉，因為真正需要嚴格處理的只有一萬個請求，其餘 99% 都是註定失敗的。

**從外到內五層**：**靜態化與 CDN**（商品頁完全靜態，不打後端）、**前端限制**（按鈕點擊後禁用、驗證碼打散瞬時峰值）、**閘道限流**（按使用者與 IP，並在活動開始前直接拒絕）、**庫存預熱到 Redis**（用原子操作扣減，賣完立即設一個「售罄」旗標讓後續請求直接返回）、**非同步下單**（Redis 扣減成功後只寫入一條訊息，訂單與支付走佇列慢慢處理）。

**庫存扣減必須是原子的**——用 Lua 腳本在 Redis 裡「檢查加扣減」一次完成，**避免「先讀後寫」的競態**。

**最終一致性由資料庫兜底**：訂單落庫時再用 `UPDATE stock SET n = n - 1 WHERE id = ? AND n > 0` 做一次校驗，**以受影響列數判斷是否成功**。

## 詳細解析

「售罄旗標」是這個設計裡效益最高的一個細節。庫存歸零之後，後續九十幾萬個請求應該在最外層就被回絕——用一個本地快取的布林值判斷，連 Redis 都不需要打。這把系統的壓力從「百萬請求打到 Redis」降成「百萬請求打到記憶體」，**是數量級的差異**。

驗證碼與答題的真正作用是「時間打散」而非防機器人。它把原本集中在同一秒的百萬請求**拉長到十幾秒**，**峰值因此下降一個數量級**——**這比任何後端優化都有效**，因為**削峰永遠比擴容便宜**。

**超賣與少賣是不對稱的**。**超賣是事故**（賣出去的東西沒有貨），**少賣只是損失一點銷售額**。所以所有的取捨都應該偏向「寧可少賣」：Redis 扣減成功但後續下單失敗時，庫存回補應該是非同步且允許延遲的，甚至可以接受少量永久性的少賣。這個不對稱性決定了很多設計選擇，而能主動說出來會比逐項討論技術細節更能展現判斷。

非同步下單的代價是「使用者不知道自己搶到沒有」。處理方式是立即回傳一個「排隊中」的結果加上一個查詢用的 token，前端輪詢或用長連線推送最終結果。**同時要設一個明確的時限**（例如 30 秒內未出結果即視為失敗），**避免使用者無限等待**。

**熱點資料的隔離也很重要**：秒殺商品的快取鍵應該與普通商品分開，必要時把庫存拆成 N 個子庫存分散到不同的 Redis 分片，**避免單一鍵成為熱點**——代價是「某個子庫存賣完但其他還有」時需要跨分片重試。

## 面試回答方式

先給核心思路——層層過濾，讓絕大多數請求在到達庫存扣減之前就被擋掉，因為真正需要嚴格處理的只有一萬個請求，其餘 99% 註定失敗。給五層（靜態化與 CDN、前端限制、閘道限流、Redis 原子扣減、非同步下單）與Lua 腳本保證檢查加扣減的原子性。加分點有四個：**「售罄旗標」效益最高**——庫存歸零後用本地快取的布林值直接回絕，連 Redis 都不打，是數量級的差異；驗證碼的真正作用是時間打散而非防機器人，**削峰永遠比擴容便宜**；**超賣與少賣不對稱**——超賣是事故、少賣只是損失銷售額，所以所有取捨都偏向寧可少賣；以及非同步下單的代價是使用者不知道搶到沒有，需要排隊 token 加輪詢或推送，並設明確時限。

## 講稿

核心思路是層層過濾。真正需要嚴格處理的只有一萬個請求，其餘百分之九十九都註定失敗，所以要讓它們在到達庫存扣減之前就被擋掉。

從外到內大概五層。商品頁完全靜態化走內容分發網路、前端點擊後禁用按鈕、閘道按使用者跟位址限流、庫存預熱到快取用腳本做原子扣減、最後只寫一條訊息進佇列，訂單跟支付慢慢處理。

這裡面效益最高的細節是售罄旗標。庫存歸零之後，後面九十幾萬個請求應該在最外層就被回絕，用一個本地快取的布林值判斷，連快取伺服器都不用打。這是數量級的差異。

驗證碼的真正作用也不是防機器人，是時間打散。它把集中在一秒的請求拉長到十幾秒，峰值就降一個數量級。削峰永遠比擴容便宜。

最後一點我覺得最重要。超賣跟少賣是不對稱的。超賣是事故，少賣只是損失一點銷售額。所以所有的取捨都應該偏向寧可少賣。

## 常見追問

### 為什麼不直接用資料庫的行鎖扛？

**核心答案**：因為熱點行的鎖是完全序列化的。一萬件商品在同一行上扣減，**所有請求排隊等同一把行鎖**——假設每次持鎖 1 毫秒，理論上限就是每秒一千次，**而百萬請求需要一千秒**。更糟的是等鎖的連線會佔滿連線池，讓整個資料庫的其他查詢一起變慢——這是典型的「一個熱點拖垮整個系統」。

**詳細解析**：但這不代表資料庫完全不能參與。合理的分工是「Redis 承擔併發過濾，資料庫承擔最終正確性」：只有通過 Redis 的一萬個請求會打到資料庫，**那個量級行鎖完全扛得住**。而資料庫那一層的 `WHERE n > 0` 是最後的正確性保證——即使 Redis 因為某種原因多放行了幾個，資料庫也不會超賣。如果一定要只用資料庫，可行的做法是「庫存分桶」：把一萬件拆成一百行各一百件，請求隨機打到某一行，**併發度提升一百倍**，代價是某些桶提前賣完時需要重試其他桶。

**面試回答方式**：給量化的理由——熱點行完全序列化，持鎖 1 毫秒就是每秒一千次的上限，並指出更糟的是等鎖的連線佔滿連線池，一個熱點拖垮整個資料庫。加分點是不要全盤否定資料庫：合理的分工是 Redis 承擔併發過濾、資料庫承擔最終正確性，那個 `WHERE n > 0` 是即使 Redis 多放行也不會超賣的最後保證。最後給出只用資料庫時的庫存分桶方案與它的代價。

### Redis 扣減成功但下單失敗怎麼辦？

**核心答案**：用「預佔加確認」的兩段式，並以超時回補兜底。Redis 扣減時同時寫入一筆**預佔紀錄**（帶使用者與時間戳）；**下單成功後刪除預佔**；有一個背景任務掃描超過 N 分鐘仍未確認的預佔，把庫存加回去。**回補必須冪等**——用預佔紀錄的唯一 ID 保證同一筆只回補一次。

**詳細解析**：「回補」是這個系統裡最容易出錯的地方，因為它同時要求不重複與不遺漏。**不重複**靠預佔紀錄的狀態轉換（只有處於「預佔中」的才能被回補，且轉換要原子）。**不遺漏**靠掃描任務本身的可靠性——它必須有監控，因為它靜默失效的話庫存會慢慢消失而沒有人發現。**實務上很多團隊選擇「不回補」**：把未確認的預佔直接視為賣出，活動結束後人工處理——**理由正是前面說的不對稱性**，少賣幾件的成本遠低於一個複雜回補邏輯出錯導致超賣的風險。這個取捨值得主動說出來，因為它展現的是對「複雜度是否值得」的判斷。

**面試回答方式**：給「預佔加確認 + 超時回補」的方案，並強調**回補必須冪等**。加分點是指出回補是最容易出錯的地方，因為它同時要求不重複與不遺漏——不重複靠預佔紀錄的原子狀態轉換，不遺漏靠掃描任務的監控，因為它靜默失效的話庫存會慢慢消失而沒人發現。真正的判斷力在最後：**很多團隊選擇不回補**，把未確認的預佔視為賣出、活動後人工處理，理由正是超賣與少賣的不對稱——少賣幾件的成本遠低於複雜回補邏輯出錯導致超賣的風險。

### 怎麼防止腳本刷單？

**核心答案**：**分層且接受無法完全防住**。**活動前**：資格預校驗（只有符合條件的帳號能參加）、**設備指紋與帳號風險評分**。**活動中**：**驗證碼與答題**（同時起到削峰作用）、**按使用者、裝置、IP 的多維限流**、**請求簽名**（防止直接呼叫介面繞過前端）。**活動後**：**風控複審與取消異常訂單**。

**詳細解析**：「秒殺介面不能被直接呼叫」是一個常被忽略的基礎。如果搶購的 URL 是固定且可預測的，腳本可以跳過所有前端限制直接打。**常見做法是「動態 URL」**——活動開始時才發放一個含隨機串的路徑或 token，**有效期只有幾秒**，**讓腳本無法提前準備**。但更重要的認知是「完全防住是不可能的」：專業的刷單者有大量真實帳號與分散的 IP，任何純技術手段都只是提高成本。所以設計上應該把重點放在「限制單一使用者的收益上限」（每人限購一件、綁定實名、中獎後需在時限內付款），讓刷單的邊際收益趨近於零，而不是追求把所有腳本擋在門外。

**面試回答方式**：給活動前中後的三段防護。第一個加分點是**動態 URL**——固定且可預測的搶購網址讓腳本能跳過所有前端限制直接打，所以活動開始時才發放含隨機串、有效期只有幾秒的路徑。真正的判斷力是承認**完全防住不可能**——專業刷單者有大量真實帳號與分散 IP，任何純技術手段都只是提高成本，所以重點應該放在限制單一使用者的收益上限（限購、實名、付款時限），**讓刷單的邊際收益趨近於零**。
