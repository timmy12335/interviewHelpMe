# 題目

正向代理（Forward Proxy）和反向代理（Reverse Proxy）有什麼差異？各自的典型應用場景是什麼？

## 核心答案

兩者的核心差異在於「**代理是替誰服務、隱藏的是通訊的哪一方**」——**正向代理**代替**客戶端**發起請求，客戶端明確知道自己正在使用代理（並主動設定要透過這個代理連線），代理向真正的目標伺服器發起請求時，目標伺服器**不知道（或不需要知道）真正的客戶端是誰**，只看到代理伺服器的身份，典型場景是「公司內部網路，透過代理伺服器統一存取外部網際網路」（企業可以透過正向代理，統一控管員工能存取哪些外部網站，並隱藏內部真實的員工身份和內部網路架構）。**反向代理**則是站在**伺服器端**，代替後端的真實伺服器，接收來自外部客戶端的請求，客戶端**不知道（也不需要知道）背後真正處理請求的是哪一台或哪幾台伺服器**，只知道自己在和這個反向代理溝通，典型場景包括**負載平衡（Load Balancing）**（見 [[003-load-balancing.md]]，反向代理把請求分散到後端多台伺服器）、**API 閘道**（見 [[../backend-engineering/010-api-gateway.md]]）、以及**隱藏內部伺服器的真實架構和 IP 位址**（提升安全性）。一句話總結——正向代理隱藏「客戶端是誰」、服務於客戶端；反向代理隱藏「伺服器是誰/有幾台」、服務於伺服器端。

## 詳細解析

**正向代理的具體運作與應用場景**：想像一個公司的網路環境，員工的電腦如果要存取外部網站（例如某個新聞網站），並不是直接連線到那個網站的伺服器，而是**先把請求發送給公司內部設定好的正向代理伺服器**，由這個代理伺服器，代替員工，去連線外部的目標網站，取得回應後再轉交給員工。從外部網站的角度看，它收到的請求，來源 IP 是「這個公司的正向代理伺服器」，而不是員工個人電腦的真實 IP，外部網站**不知道**（也不需要知道）具體是哪個員工發起了這次請求。這種架構帶來的價值包括——**統一的存取控管**（公司可以在正向代理這一層，設定「哪些網站允許存取、哪些禁止」的規則）、**內容快取**（正向代理可以快取常被存取的外部內容，減少重複的外部頻寬消耗）、**隱藏內部網路架構**（外部網站只看到代理伺服器的 IP，不知道公司內部實際有多少台電腦、內部網路怎麼配置）。VPN（虛擬私人網路）某種程度上，也可以被視為一種特殊形式的正向代理應用——透過 VPN，客戶端的網路流量，先被導向 VPN 伺服器，再由 VPN 伺服器代為連線目標網站，讓目標網站看到的是 VPN 伺服器的 IP，達到隱藏真實客戶端位置的效果。

**反向代理的具體運作與應用場景**：反向代理站在系統架構裡「靠近伺服器」的那一端——外部客戶端，連線到反向代理（例如透過一個公開的網域名稱），完全不知道（也不需要知道）背後實際上有幾台伺服器在處理請求、這些伺服器分別叫什麼名字、內部網路怎麼配置，反向代理**代替後端的真實伺服器**，接收外部請求並決定要轉發給哪一台（或哪幾台）內部伺服器處理，處理完成後，再把回應轉交給外部客戶端（客戶端全程只和這個反向代理互動）。這種架構帶來的核心價值包括——**負載平衡**（反向代理最常見的應用之一，把外部流量分散到多台後端伺服器，見 [[003-load-balancing.md]]）、**SSL/TLS 終止（SSL Termination）**（把「處理加密連線」這個相對耗費運算資源的工作，集中在反向代理這一層完成，後端的實際應用伺服器，只需要處理未加密的內部流量，簡化後端伺服器的負擔）、**隱藏後端架構、提升安全性**（外部攻擊者，即使想要嘗試攻擊，也只能看到反向代理這一個對外的入口，無法直接得知後端實際伺服器的真實 IP 和架構細節，減少了直接暴露攻擊面）、**快取靜態內容**（反向代理，可以快取一些不常變動的靜態內容，例如圖片、CSS/JS 檔案，不需要每次都請求後端伺服器產生，加速回應並減輕後端負擔）。Nginx 是業界最常用來實作反向代理的軟體之一，也是很多系統架構裡，「API 閘道」（見 [[../backend-engineering/010-api-gateway.md]]）的底層技術基礎。

**兩者的關鍵區分——「代理知道並替誰隱藏」**：釐清兩者最簡單的方式，是問自己「這個代理，是站在客戶端這一側、替客戶端隱藏身份，還是站在伺服器這一側、替伺服器隱藏身份」——正向代理，客戶端是「知情的一方」（客戶端主動設定使用這個代理），被隱藏的是「客戶端的真實身份」（讓最終的目標伺服器，不知道真正是誰在發起請求）；反向代理則相反，**客戶端是「不知情的一方」**（客戶端根本不知道背後有代理、有多少台真實伺服器在運作，客戶端只是單純地連線到一個看起來像是「唯一伺服器」的位址），被隱藏的是「伺服器端的真實架構」。這個「誰知情、誰被隱藏」的區分角度，是理解和記憶這兩個容易混淆的概念，最直接有效的方式。

## 面試回答方式

用一句話給出核心區分——「正向代理服務客戶端、隱藏客戶端身份;反向代理服務伺服器端、隱藏伺服器架構」。用具體場景解釋——「正向代理如公司內部網路統一透過代理存取外部網站，外部網站只看到代理IP不知道真正是哪個員工;反向代理如Nginx做負載平衡，外部客戶端只知道自己在和這一個入口溝通，不知道背後有幾台真實伺服器」。列出反向代理的核心應用——「負載平衡、SSL終止、隱藏後端架構提升安全性、快取靜態內容」，以及正向代理的核心應用——「企業統一存取控管、VPN隱藏真實位置」。可以用「誰知情、誰被隱藏」這個判斷角度總結，幫助釐清這兩個容易混淆的概念，展現你有一套清晰的心智模型來區分它們，而不只是死記兩個定義。

## 常見追問

### 如果一個系統同時用了正向代理和反向代理(比如企業內部員工透過正向代理連到外部的某個服務，而那個外部服務本身，在它自己的伺服器端又用了反向代理做負載平衡)，這個請求完整的路徑會是什麼樣子?

**核心答案**：完整路徑會是——「員工電腦（真實客戶端）→ 公司的正向代理（代替員工發起請求，外部目標服務只會看到這個正向代理的 IP，不知道真正的員工是誰）→ 網際網路 → 目標服務的反向代理（接收所有外部請求，包含剛才那個正向代理轉發過來的請求，反向代理自己不知道也不需要知道「這個請求，其實是經過另一個正向代理轉發的」，只是把它當作一般的外部請求處理）→ 反向代理依照負載平衡策略，把請求轉發給後端某一台真實的應用伺服器 → 應用伺服器處理完成，回應沿著相反的路徑，層層傳回」。這個場景清楚地展現了「正向代理」和「反向代理」是**兩個完全獨立、各自站在不同一方、為不同目的服務**的概念，兩者可以同時存在於同一次請求的完整路徑裡，互不衝突，也互不知情對方的存在。

**詳細解析**：這題透過一個具體、涉及兩種代理同時存在的場景，鞏固對「正向代理和反向代理是兩個獨立概念，服務於通訊路徑的不同兩端」這個核心理解的掌握。理解這個混合場景的關鍵，在於認識到「正向代理」和「反向代理」，各自的存在，和「請求最終要經過多少層代理」這件事本身，並沒有直接的邏輯衝突或依賴關係——正向代理的存在，是因為「公司想要控管和隱藏，自己內部員工對外發起連線」這個需求，這個需求和「外部目標服務，自己內部怎麼架構、有沒有用反向代理做負載平衡」完全無關；同樣地，外部目標服務選擇用反向代理來管理自己的內部架構，這個決策也完全不需要知道、也不關心「發起這次請求的客戶端，是不是本身也透過了某個正向代理」，對這個反向代理而言，所有進來的外部請求，不管它們背後，是不是又經過了層層的正向代理轉發，看起來都只是「一個外部的 HTTP 請求」，反向代理只需要按照自己的邏輯（負載平衡到哪台後端伺服器）處理即可。這種「兩種代理各自獨立運作、彼此不需要知情，卻可能同時出現在同一次請求的完整路徑裡」的現象，某種程度上也印證了這兩個概念真正的本質——它們解決的是**通訊鏈路兩端各自不同的問題**（客戶端這一端想要隱藏自己、伺服器這一端想要隱藏自己），這兩個問題，可以同時存在、也可以各自獨立存在（只有正向代理，而目標服務沒有反向代理；或者反過來），甚至像這個追問描述的場景一樣，同時存在於同一次完整的請求路徑裡。理解「正向代理和反向代理是各自獨立、服務於通訊雙方不同需求的概念，兩者可以同時出現在同一次請求的完整路徑裡，且彼此完全不需要知道對方的存在，這進一步印證了『正向代理服務客戶端、反向代理服務伺服器端』這個核心區分角度的正確性」，展現你能把這兩個概念，套用到更複雜、更貼近真實網路環境的混合場景裡，並依然能清楚地梳理出完整的請求路徑。

**面試回答方式**：完整地描述請求路徑——「員工電腦(真實客戶端)→公司正向代理(代替員工發起請求，外部服務不知道真正的員工身份)→網際網路→目標服務的反向代理(接收所有外部請求，不知道也不需要知道這個請求背後經過了正向代理)→反向代理依負載平衡策略轉發給後端某台真實伺服器→處理完成後沿相反路徑回傳」。點出核心洞察——「這個混合場景清楚展現正向代理和反向代理是兩個完全獨立、服務於通訊雙方不同需求的概念，可以同時存在、互不知情、互不衝突」。展現你能把這兩個概念套用到更複雜的真實網路環境場景裡，並依然清楚梳理完整路徑。

### CDN(內容分發網路)算是正向代理還是反向代理?為什麼?

**核心答案**：CDN 本質上是一種**反向代理的應用**——CDN 節點站在「內容提供方（伺服器端）」這一側，代替源站（Origin Server）接收來自全球各地使用者的請求，使用者（客戶端）連線的是「離自己地理位置最近的 CDN 節點」，而不需要知道（也通常不知道）真正的源站伺服器實際上位於世界的哪個角落，CDN 節點會嘗試用自己快取的內容直接回應使用者（如果快取命中），或者代替使用者，向源站請求最新的內容（如果快取沒有命中或已過期），這個「代替伺服器端接收外部請求、隱藏源站真實位置」的角色定位，完全符合反向代理的定義。

**詳細解析**：這題把「正向代理 vs 反向代理」這組核心概念，延伸應用到 CDN 這個雖然名稱聽起來像是一個完全獨立的技術，但本質上和反向代理有深刻淵源的實際系統，考察是否能把抽象的定義，正確地映射到具體、常見的真實技術架構上。CDN 的核心運作邏輯是——內容提供方（例如一個影音串流網站），把自己的靜態內容（如影片檔案、圖片、CSS/JS），分發並快取到分佈在全球各地的許多 CDN 節點上，當某個地區的使用者，想要存取這個網站的內容時，DNS 解析（或其他路由機制），會引導這個使用者的請求，連接到「地理位置離他最近」的那個 CDN 節點，而不是直接連到位於遠方某處的原始伺服器（源站），這個 CDN 節點，如果已經快取了使用者要的內容，就直接回應（大幅降低延遲，因為地理距離近，且不需要真正打擾到源站）；如果 CDN 節點還沒有快取這個內容（或快取已經過期），CDN 節點會**代替這個使用者**，向源站發起請求，取得最新內容後，一方面回應給使用者，一方面把這份內容快取下來，供之後其他使用者存取時直接使用。從這個運作邏輯可以清楚看出——**使用者（客戶端），完全不需要知道、也通常無法得知，這個網站真正的源站伺服器，實際位於世界上的哪個具體位置**，使用者只知道自己在和「離自己最近的那個 CDN 節點」溝通，這正是「反向代理」的核心特徵——站在伺服器端，隱藏真正處理請求的伺服器（在 CDN 的情境下，被隱藏的是「真正的源站」）；而且 CDN 也承擔了反向代理的典型職責——快取內容（減少對源站的重複請求）、以及某種程度上的負載分散（把原本可能集中湧向單一源站的所有全球流量，分散到各地的 CDN 節點，大幅減輕源站直接承受的壓力）。理解「CDN 本質上是反向代理這個概念，在『地理分佈式內容快取』這個具體應用場景下的實際落地，它站在伺服器端、代替源站接收和回應請求、隱藏源站真實位置，並提供快取和負載分散的效果，這些特徵和反向代理的核心定義完全吻合」，展現你能把抽象的架構概念，正確地連結和映射到 CDN 這個常見但容易被視為「獨立技術」而忽略其本質歸屬的真實系統上。

**面試回答方式**：直接給出答案——「CDN本質上是反向代理的一種應用」。給出具體理由——「CDN節點站在伺服器端，代替源站接收全球各地使用者的請求，使用者連線的是離自己最近的CDN節點，不需要知道也通常不知道真正的源站在哪裡;CDN節點快取內容直接回應，或代替使用者向源站取得最新內容，這個『代替伺服器端接收外部請求、隱藏源站真實位置』的角色定位，完全符合反向代理的定義」。可以補充「CDN也承擔了反向代理典型的職責——快取內容、負載分散(把全球流量分散到各地節點，減輕源站直接承受的壓力)」。展現你能把抽象概念正確映射到CDN這個具體、常見的真實系統上。

### 反向代理做「SSL/TLS 終止」，把加密連線的處理集中在代理這一層，後端伺服器只處理未加密的內部流量，這樣做安全嗎?會不會有風險?

**核心答案**：這種做法在**特定的前提條件下**是相對安全、且業界廣泛採用的常見做法——前提是**「反向代理和後端應用伺服器之間的網路，必須是完全受信任、且外部無法直接存取的內部網路」**（例如在同一個資料中心、同一個私有的 VPC 裡），在這個前提下，「反向代理到後端伺服器」這一段的流量，即使是未加密的，也不會被外部的攻擊者攔截或竊聽（因為外部根本無法接觸到這段內部網路）。但如果這個前提不成立——例如反向代理和後端伺服器之間，是透過某種可能被第三方存取或監聽的網路（如公共雲端環境裡，配置不當、暴露了不該暴露的內部網路），那麼「後端流量未加密」就會是一個實質的安全風險，這種情況下，應該考慮**在反向代理和後端伺服器之間，也額外加上一層加密**（例如透過雙向 TLS，見 [[../backend-engineering/010-api-gateway.md]] 討論過的類似機制），確保即使是內部流量，也有適當的加密保護，而不是無條件地假設「內部網路就一定是安全的」。

**詳細解析**：這題考察對「SSL 終止」這個常見效能優化手段，潛在安全風險的辯證理解，避免不假思索地認為「這是業界常見做法，所以一定沒有問題」。SSL/TLS 終止之所以是一個被廣泛採用的常見做法，核心的效益是「加密和解密的運算，是相對耗費 CPU 資源的操作，把這個負擔集中在反向代理這一層處理（通常反向代理的硬體，可能特別針對這類加解密運算做過優化，或者至少不需要每一台後端應用伺服器，都各自承擔這個額外的運算負擔），讓後端的應用伺服器，可以專注於處理業務邏輯本身，不需要在每一次請求上，都額外花費資源進行加解密運算」，這確實能帶來效能上的提升，也簡化了「憑證管理」的複雜度（只需要在反向代理這一個地方，配置和更新 SSL 憑證，而不需要在每一台後端伺服器上各自配置）。但這個做法的安全性，建立在一個關鍵假設之上——「反向代理到後端伺服器之間傳輸的資料，即使是未加密的明文，也不會被任何不該接觸到這段網路的第三方看到或竄改」，這個假設，在「反向代理和後端伺服器，都位於同一個受到嚴格網路隔離保護的私有網路（例如同一個資料中心的內部網路、或雲端服務商提供的私有 VPC）」這個前提下，通常是成立的（因為外部的網際網路使用者或攻擊者，根本沒有辦法直接接觸到這段內部網路，就像前面 API 閘道章節討論過的「後端服務不應該直接暴露給外部」這個網路隔離原則，見 [[../backend-engineering/010-api-gateway.md]]）；但如果這個網路隔離的前提出現漏洞（例如雲端環境的網路安全群組規則設定不當，意外地讓某些不該有權限的網段，也能存取到這段本應是內部的流量），那麼「後端流量是明文傳輸」這件事，就從「一個基於合理信任前提的效能優化」，轉變成「一個實質的、可能被利用來竊聽敏感資料的安全漏洞」。因此，正確、謹慎的做法，是**不應該無條件地假設『內部網路就是絕對安全的』**，而應該根據具體的部署環境和安全要求等級，評估是否需要在「反向代理到後端」這一段，額外引入加密保護（例如額外的內部 TLS，或者更進階的雙向 TLS 相互驗證，確保這段內部通訊的機密性和真實性都有保障），尤其如果傳輸的資料包含高度敏感的資訊（如金融交易、個人隱私資料），即使是內部網路，額外的加密保護也是一種符合「縱深防禦（Defense in Depth）」原則的謹慎做法，而不能單純依賴「這是內部網路，所以應該是安全的」這個假設。理解「SSL終止在後端流量未加密這件事，安全性完全取決於『反向代理到後端的網路是否真的受到嚴格隔離保護』這個前提是否成立，不應該無條件地假設內部網路絕對安全，而應該根據實際的部署環境和資料敏感度，評估是否需要在內部流量也加上額外的加密保護」，展現你對這個常見的效能優化手段，潛在的安全考量，有辯證、而非想當然爾的理解。

**面試回答方式**：先給出核心判斷——「在特定前提下是相對安全、業界廣泛採用的做法，前提是反向代理和後端伺服器之間的網路必須是完全受信任、外部無法直接存取的內部網路」。點出效益——「把耗費CPU的加解密運算集中在反向代理層，簡化憑證管理」。指出潛在風險——「如果這個網路隔離的前提不成立(如雲端環境配置不當意外暴露內部網路)，後端流量未加密就會是實質的安全風險」。給出謹慎的建議——「不應該無條件假設內部網路絕對安全，應該根據實際部署環境和資料敏感度，評估是否需要額外在內部流量也加上加密保護(如雙向TLS)，這符合縱深防禦的安全原則」。展現你對這個常見效能優化手段的安全性有辯證而非想當然爾的理解。
