# 題目

常見的負載平衡（Load Balancing）演算法有哪些？負載平衡器本身部署在系統的哪個位置，又要怎麼避免它自己成為單點故障？

## 核心答案

常見的負載平衡演算法包括：**（1）輪詢（Round Robin）**——依序把請求輪流分配給後端的每一台伺服器，實作簡單，適合各伺服器規格相近、處理能力差不多的情況；**（2）加權輪詢（Weighted Round Robin）**——依照每台伺服器的處理能力（權重），按比例分配請求（規格較好的伺服器,分配到更多請求）；**（3）最少連線數（Least Connections）**——把新請求分配給「目前正在處理中的連線數最少」的伺服器，適合各個請求的處理時間長短差異較大的情況（輪詢可能導致某些恰好分配到多個「長時間」請求的伺服器過載）；**（4）一致性雜湊（Consistent Hashing）**——依照請求裡的某個特徵（如使用者 ID），計算雜湊值決定路由到哪台伺服器，同一個使用者的請求,總是被路由到同一台伺服器（見 [[../backend-engineering/017-consistent-hashing.md]]），適合需要「會話黏著」或希望善用該伺服器本地快取的場景。負載平衡器通常部署在**客戶端和應用伺服器叢集之間**，是外部流量進入系統的第一道關卡；為了避免它自己成為單點故障，通常會**部署多個負載平衡器實例**，並在更上層,透過 DNS 輪詢、或雲端服務商提供的高可用負載平衡服務、或者更底層的網路技術（如 Anycast IP），確保即使某個負載平衡器實例故障，流量依然能被導向其他健康的負載平衡器實例。

## 詳細解析

**四種演算法的適用場景比較**：**輪詢**是最簡單直觀的策略，但它有一個隱含的假設——「每個請求的處理成本大致相同」，如果實際情況並非如此（例如某些請求需要複雜的運算,耗時遠高於其他簡單的請求），輪詢可能導致「某台伺服器,恰好連續分配到好幾個耗時的請求,累積起來負載明顯偏高」這種不均衡的情況。**最少連線數**演算法針對這個問題做了改進——它不是機械地依序分配，而是動態地觀察「目前每台伺服器,有多少個連線正在處理中」，優先把新請求分配給「目前看起來比較閒」的伺服器，能更好地適應請求處理時間長短不一的情況，但這個演算法需要負載平衡器**即時追蹤每台後端伺服器的當前連線數**，比純粹的輪詢多了一些狀態維護的複雜度。**一致性雜湊**演算法的核心價值,不在於「負載是否均勻」，而在於「**同一個特徵的請求，能穩定地被路由到同一台伺服器**」——這對於「後端伺服器,針對某個使用者的資料做了本地快取（Local Cache）」這類場景特別有價值（如果同一個使用者的後續請求,總是被路由到同一台已經快取過他資料的伺服器，能大幅提升快取命中率,減少重複查詢資料庫的次數）；但這種策略,也繼承了一致性雜湊本身「如果雜湊分佈不夠均勻,可能導致某些伺服器負載偏高」的固有限制（見 [[../backend-engineering/017-consistent-hashing.md]] 討論過的虛擬節點（Virtual Node）如何緩解這個問題）。

**負載平衡器的部署位置**：在一個典型的分層架構裡，負載平衡器通常出現在**多個層次**——最外層,可能有一個（或多個）**面向公網的負載平衡器**，接收所有從網際網路進來的外部請求，把它們分散到多台**應用伺服器**（或 API 閘道,見 [[../backend-engineering/010-api-gateway.md]]）；再往內，**應用伺服器和資料庫（或快取叢集）之間**，也可能存在另一層負載平衡（例如,如果資料庫本身有多個唯讀副本,應用伺服器發起的讀取查詢,可能透過另一個負載平衡機制,被分散導向這幾個唯讀副本，見 [[../database/019-read-write-separation.md]] 討論過的讀寫分離（Read-Write Splitting））。理解「負載平衡不是只有一層,而是可能出現在架構裡多個需要『把流量分散到多個後端目標』的環節」，有助於更全面地理解一個完整系統的流量分佈設計。

**負載平衡器本身避免單點故障的做法**：既然負載平衡器,是所有流量必經的關卡，如果它自己是單一實例、沒有任何備援，一旦這個實例故障,會導致整個系統對外完全不可用——這正呼應了之前在 API 閘道章節討論過的（見 [[../backend-engineering/010-api-gateway.md]]）「任何被賦予集中、統一角色的元件,都需要用同等嚴謹的高可用標準來設計」這個通用原則。常見的解決方式包括——**部署多個負載平衡器實例**（本身也是無狀態的,可以隨意增減），並在**更上層**，透過幾種方式讓客戶端能夠找到這些健康的負載平衡器實例：**DNS 輪詢**（DNS 伺服器,對同一個網域名稱,回應多個不同負載平衡器實例的 IP 位址，客戶端依照 DNS 回應的其中一個 IP 連線，如果某個負載平衡器實例故障，可以搭配健康檢查機制,及時把它從 DNS 回應裡移除）；**浮動 IP（Floating IP）配合心跳偵測**——多個負載平衡器實例之間,透過心跳互相偵測健康狀況，一個共享的「浮動」IP 位址,平常固定綁定在某一個負載平衡器實例上，一旦這個實例故障，心跳偵測機制會自動把這個浮動 IP,重新綁定到另一個健康的實例上，讓客戶端(它們只知道這個固定不變的浮動 IP，不需要知道背後具體是哪個實例在服務)能無縫地繼續連線；許多雲端服務商也直接提供**託管的高可用負載平衡服務**（如 AWS 的 ELB/ALB），這類服務本身已經在雲端服務商的基礎設施層面,做好了高可用的設計，開發者不需要自己額外處理這個問題。

## 面試回答方式

列出四種常見負載平衡演算法並各自說明適用場景——輪詢(簡單,適合請求成本相近)、加權輪詢(依伺服器規格差異分配)、最少連線數(適合請求處理時間長短不一,動態依當前連線數分配)、一致性雜湊(適合需要會話黏著或善用本地快取的場景,同一特徵請求穩定路由到同一伺服器)。講清楚負載平衡器的部署位置——「不只出現在外部客戶端和應用伺服器之間,架構裡多個需要分散流量到多個後端目標的地方都可能出現負載平衡,如應用層和資料庫唯讀副本之間」。最後一定要主動討論「負載平衡器本身怎麼避免單點故障」——「部署多個實例,搭配DNS輪詢或浮動IP+心跳偵測等機制,確保即使某個實例故障,流量依然能導向其他健康實例」，這是容易被忽略但很重要的部分,展現你理解「負載平衡器本身也需要高可用設計」這個貫穿多個相關主題的通用原則。

## 常見追問

### 「最少連線數」演算法,如果後端伺服器規格差異很大(有的很強、有的較弱),單純依照連線數分配會不會有問題?

**核心答案**：確實會有問題——單純的最少連線數演算法,隱含假設「每台伺服器,處理相同數量連線所需要付出的實際負擔是差不多的」，但如果伺服器規格差異很大（例如一台是高階伺服器,另一台是規格較弱的機器），即使兩台伺服器目前「連線數」相同,規格較弱的那台伺服器,實際的資源緊張程度,可能遠高於規格較強的那台。因應這個問題，常見的改進是**「加權最少連線數（Weighted Least Connections）」**——把每台伺服器的處理能力(權重)也納入考量，用「連線數 ÷ 權重」這種正規化（Normalization）後的比較方式（而非直接比較原始的連線數），決定要把新請求分配給哪台伺服器，讓規格較好、權重較高的伺服器,能夠承擔比例上更多的連線數，而不是和規格較弱的伺服器,被要求維持相同數量的連線。

**詳細解析**：這題考察對「最少連線數」演算法一個容易被忽略的隱含假設,以及業界標準的改進方案的理解。純粹的最少連線數演算法，其判斷依據,只單純地比較「各台伺服器目前有幾個連線正在處理中」這個數字本身,完全沒有考慮「不同伺服器,能夠健康地同時處理多少連線,這個能力上限本身可能天差地遠」這個現實因素——如果系統裡混合了「一台擁有 32 核心 CPU、128GB 記憶體的高階伺服器」和「一台只有 4 核心、16GB 記憶體的普通伺服器」，理論上,前者能夠健康地同時處理遠多於後者的連線數，如果純粹依照「連線數是否相同」來分配新請求，很可能出現「兩台伺服器目前都各自維持著 100 個連線」這種表面上「均衡」的狀態，但實際上,規格較弱的那台伺服器,可能已經因為這 100 個連線而 CPU 使用率飆升到接近極限、回應開始變慢，而規格較強的那台伺服器,處理這 100 個連線,可能還游刃有餘,遠遠沒有到達它真正的處理能力上限。加權最少連線數演算法，透過引入「權重」這個額外的維度(通常依照伺服器的硬體規格,人為地設定一個相對的權重值,例如高階伺服器權重設為 4、普通伺服器權重設為 1)，並在比較時，不直接比較原始連線數,而是比較「目前連線數 除以 這台伺服器的權重」這個經過正規化的數值,讓分配決策,更精確地反映「這台伺服器,相對於它自身的處理能力,目前的忙碌程度」，而不是簡單粗暴地假設所有伺服器的處理能力都是均等的。理解「最少連線數演算法,如果不考慮伺服器規格的異質性,可能導致規格較弱的伺服器被過度分配,加權最少連線數透過引入權重,用『連線數/權重』這個正規化的比較指標,更精確地反映各伺服器相對於自身處理能力的忙碌程度」，展現你對負載平衡演算法的實務細節,有更深入、超越教科書式定義的理解。

**面試回答方式**：先確認「確實會有問題,最少連線數隱含假設所有伺服器的處理能力都是均等的」。給出改進方案——「加權最少連線數,引入權重,用『連線數÷權重』這個正規化的指標做比較,而非直接比較原始連線數,讓規格較好、權重較高的伺服器能承擔比例上更多的連線」。展現你理解最少連線數演算法在異質性伺服器叢集下的局限,以及業界標準的加權改進方案。

### 一致性雜湊做負載平衡(依使用者ID路由到固定伺服器)的方式,如果某台伺服器故障需要被移除,原本被路由到那台伺服器的使用者,他們的請求會發生什麼事?

**核心答案**：這些使用者的請求，會依照一致性雜湊的規則,被自動重新分配到「環上,順時針方向下一個健康的伺服器」（見 [[../backend-engineering/017-consistent-hashing.md]] 討論過的一致性雜湊移除節點時的行為），但這也意味著——**這些使用者,原本可能已經在故障伺服器上累積的「本地快取」或「會話狀態」，會因為被重新路由到一台全新的伺服器而完全遺失**（新伺服器對這個使用者而言,是「第一次見面」，沒有任何之前累積的快取或狀態）。因此，如果系統依賴「一致性雜湊,把同一使用者穩定路由到同一伺服器」這個特性,來實現「利用伺服器本地快取加速」的效果，架構設計上就必須考慮「當某台伺服器故障、使用者被重新路由時，怎麼優雅地處理這種『快取冷啟動』的情況」（例如,讓新伺服器,能夠透過查詢一個共享的、持久化的資料來源，重新建立起這個使用者的基本狀態，而不是假設本地快取的存在是永遠可靠的）。

**詳細解析**：這題把一致性雜湊在故障情境下的具體行為,和「依賴本地快取加速」這個設計初衷,放在一起討論,考察是否理解「利用一致性雜湊做會話黏著/本地快取加速」這種設計,天生就帶有「無法完全避免快取失效」這個侷限，而不能天真地假設「只要用了一致性雜湊,快取就永遠有效」。使用一致性雜湊做負載平衡,其中一個重要的動機,正是前面提到的「讓同一使用者的請求,穩定地被路由到同一台伺服器,以便那台伺服器,可以针對這個使用者的資料,建立本地的、記憶體內的快取，避免每次都要重新從資料庫或其他慢速的來源查詢」，這個設計,在「所有伺服器都健康、正常運作」的情況下,確實能帶來效能上的好處(本地記憶體快取的存取速度,遠快於任何需要跨網路查詢的方式)，但這個效益，天生就伴隨著一個現實限制——一旦負責這個使用者的伺服器故障，被移除出叢集，一致性雜湊的路由規則,會自動把這個使用者的後續請求,重新導向到環上的下一個健康節點，這個「新接手」的伺服器，完全沒有任何關於這個使用者的歷史快取資訊，必須從頭開始（可能需要重新查詢資料庫，或者依賴其他機制重建狀態），這意味著,「本地快取加速」這個效益，在伺服器故障、節點變動的情況下,會暫時性地失效，直到新的伺服器,重新為這個使用者累積起足夠的本地快取資訊為止。這個限制,提醒我們，如果一個系統的正確性,「依賴」本地快取必須永遠可用（例如,如果應用邏輯錯誤地假設「這個使用者的狀態,一定存在於這台伺服器的本地記憶體裡，如果查不到就直接視為錯誤」，而不是「查不到就優雅地回退到查詢一個更權威、持久化的資料來源」），那麼一旦發生節點故障導致的重新路由，系統可能出現不易察覺的錯誤（例如誤判使用者狀態不存在），正確的設計原則,應該是把「本地快取」視為一種**單純的效能優化手段**，而不是「唯一的、可靠的資料來源」——本地快取,即使因為節點變動而暫時失效或不存在，系統依然應該有能力,透過查詢一個更持久、更權威的資料來源（例如共享的 Redis,或者最終的資料庫），正確地重建出需要的狀態，只是這個過程可能會比「直接命中本地快取」慢一些（這正是快取失效時,常見的「效能下降但功能依然正確」這種可接受的降級行為，而不是功能本身出錯)。理解「一致性雜湊做的『同一使用者穩定路由到同一伺服器』,只能保證『在沒有節點變動的情況下』本地快取持續有效,一旦發生節點故障導致的重新路由,本地快取會失效,系統設計上必須把本地快取視為效能優化而非唯一可靠的資料來源,確保快取失效時依然能透過查詢權威資料來源正確運作,只是效能會暫時下降」，展現你理解這類基於一致性雜湊的會話黏著/本地快取設計,在故障情境下的具體行為和必須配套的設計原則。

**面試回答方式**：先給出核心答案——「請求會依照一致性雜湊規則,重新分配到環上順時針方向下一個健康的伺服器,但這些使用者原本可能累積的本地快取或會話狀態會完全遺失」。給出正確的設計原則——「本地快取應該被視為單純的效能優化手段而非唯一可靠的資料來源,系統設計上必須確保即使本地快取因節點變動而失效,依然能透過查詢一個更持久、更權威的共享資料來源(如Redis或資料庫)正確重建狀態,只是效能會暫時下降,而不是功能出錯」。展現你理解這種設計天生帶有「無法完全避免快取失效」的侷限,以及正確的架構設計應該如何應對這個侷限。

### 如果面試官問「你會選擇哪一種負載平衡演算法」，怎麼樣的回答,能展現比單純背出演算法名稱更好的判斷力?

**核心答案**：更好的回答方式,是**先反問或釐清這個系統的具體特性**（如「後端伺服器的規格是否一致」、「不同請求的處理時間差異大不大」、「是否需要利用伺服器本地快取」、「後端服務本身是否是無狀態的」），然後**根據這些具體特性,推導出最適合的演算法選擇,並清楚說明推導的邏輯**，而不是脫口而出某一個演算法名稱，或者機械地把幾種演算法的定義都背誦一遍。例如可以說「如果後端伺服器規格一致、且各請求處理時間差異不大,輪詢就足夠簡單有效；但如果我們的服務,有依賴伺服器本地快取來加速的設計，我會傾向於一致性雜湊,即使這意味著負載可能不像輪詢那樣絕對均勻，因為快取命中率帶來的效能提升,可能更值得優先考慮」。

**詳細解析**：這題考察的核心，不是「你記不記得幾種負載平衡演算法的名稱和定義」，而是「你能不能像一個真正的工程師一樣，根據具體的情境和需求，做出有理有據的技術選型判斷」，這也呼應了之前系統設計方法論那道題目裡提到的核心精神——優秀的系統設計回答，應該展現「權衡取捨」的思考過程,而不是機械地陳述知識點。如果面試官問「你會選擇哪一種負載平衡演算法」，一個相對平庸的回答，可能是簡單地列舉「有輪詢、加權輪詢、最少連線數、一致性雜湊這幾種」，然後隨意地挑一個並簡單帶過；但一個更能展現深度的回答，應該表現出「技術選型,永遠是根據具體場景的需求推導出來的，而不是有一個放諸四海皆準的『最佳』演算法」這種思維方式——例如,如果面試官告知（或你主動詢問並確認）「這個系統的後端伺服器規格完全一致、且每個請求的處理時間都差不多（例如一個簡單的、無狀態的 CRUD API）」，那麼最簡單的輪詢演算法,可能就已經完全足夠，沒有必要為了追求「看起來更高級」而選擇更複雜的演算法（額外的複雜度，如果沒有對應的實際收益，是一種不必要的工程負擔）；但如果系統的特性是「每個請求的複雜度差異很大（例如有些請求只是簡單查詢、有些請求涉及複雜的運算）」，這時候簡單的輪詢，可能導致某些伺服器,因為運氣不好、恰好連續分配到多個複雜請求而過載，這種情況下,最少連線數（能動態反映各伺服器目前的實際負擔）會是更合適的選擇；如果系統的特性是「高度依賴伺服器本地快取來加速某些操作（例如,針對特定使用者的資料做記憶體內快取)」，即使這意味著負載分佈,可能不像輪詢那樣絕對均勻（某些使用者可能剛好比較活躍,導致負責他們的那台伺服器承受相對較高的負載），選擇一致性雜湊（以換取更高的快取命中率和整體效能），可能是更划算的權衡。展現這種「先理解具體情境的特性、再推導出最適合的技術選擇、並能清楚說明推導邏輯和背後的權衡考量」的思考方式，遠比單純背誦幾種演算法的名稱和定義，更能讓面試官看到你具備真正解決實際工程問題所需要的判斷力。

**面試回答方式**：先給出核心態度——「不應該直接說出某一個演算法名稱,而應該先釐清系統的具體特性(伺服器規格是否一致、請求處理時間差異大不大、是否需要利用本地快取),再根據這些特性推導出最合適的選擇」。舉出至少兩種不同情境和對應的推導邏輯——「規格一致、請求成本相近就用簡單的輪詢即可,不需要為了看起來高級而選擇更複雜的方案；如果請求複雜度差異大,最少連線數能動態反映實際負擔更合適；如果依賴伺服器本地快取加速,即使犧牲一些負載均勻性,一致性雜湊帶來的快取命中率提升可能更划算」。展現你理解技術選型應該是根據具體情境推導出來的判斷,而非死記硬背知識點的機械式回答。
