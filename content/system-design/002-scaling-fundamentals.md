# 題目

垂直擴展（Vertical Scaling）與水平擴展（Horizontal Scaling）有什麼差異？為什麼大型系統通常最終都會走向水平擴展？

## 核心答案

**垂直擴展（Scale Up）** 指的是「提升單一伺服器的硬體規格」——增加更多的 CPU 核心、更大的記憶體、更快的磁碟,讓同一台機器能處理更多的負載；**水平擴展（Scale Out）** 指的是「增加更多台伺服器,把負載分散到多台機器上共同處理」，而不是依賴單一台機器變得更強大。垂直擴展的優點是**實作簡單**（不需要修改應用程式的架構,只需要換更好的硬體）,缺點是**存在物理上限**（單一機器的硬體規格,不可能無限提升，且成本通常呈非線性增長,規格越高的機器,單位效能的成本越貴），以及**依然是單點故障**（不管這台機器多強大,它掛了整個系統依然會停擺）。水平擴展的優點是**理論上沒有規模上限**（可以持續增加更多機器）、**天然具備高可用性**（部分機器故障,其他機器依然能繼續服務），缺點是**需要應用程式的架構,支援多機器協同運作**（例如需要考慮如何在多台機器之間分配請求、如何處理需要跨機器共享的狀態），架構複雜度顯著提高。大型系統最終走向水平擴展，是因為業務規模的成長,終將超越任何單一機器的硬體上限,且水平擴展帶來的高可用性,對於現代網際網路服務的可靠性要求而言,是不可或缺的。

## 詳細解析

**垂直擴展的物理與經濟限制**：任何一台伺服器，其硬體規格（CPU 核心數、記憶體容量、磁碟 I/O 效能）都有現實世界的物理上限（即使是目前市面上最頂級的伺服器等級硬體，也遠遠比不上把成千上萬台普通伺服器組合起來的整體運算能力）；而且硬體規格和價格之間，通常不是線性關係——把記憶體從 16GB 升級到 32GB 的成本，遠低於把記憶體從 512GB 升級到 1TB 的成本（越接近硬體的技術極限，單位效能提升所需要付出的成本越高，這是一種常見的「規模不經濟」現象）。因此，單純依賴垂直擴展，在面對真正大規模的業務需求時，很快就會遇到「硬體規格已經無法再提升」或「繼續提升的成本效益極差」這個現實瓶頸。

**水平擴展需要克服的架構挑戰——無狀態設計**：要讓一個應用程式,能夠真正地水平擴展（把請求分散到多台伺服器,任何一台都能正確處理任何請求），核心前提是應用程式必須是**無狀態的（Stateless）**——不能把「這個使用者的會話資訊」、「這次請求相關的暫存資料」，儲存在某一台特定伺服器的記憶體裡（因為下一次這個使用者的請求,可能被負載平衡器路由到完全不同的另一台伺服器，如果狀態只存在原本那台機器上，新的伺服器完全不知道這個使用者之前的狀態）。這也是為什麼現代 Web 應用架構,普遍把「使用者的會話狀態」外移到共享的儲存（如 Redis），或者乾脆用 JWT 這類「自包含、不需要伺服器記住任何東西」的憑證（見 [[../backend-engineering/004-jwt-authentication.md]]），確保任何一台應用伺服器,都能獨立、正確地處理任何一個進來的請求，這是水平擴展能夠真正發揮效果的架構基礎。

**負載平衡是水平擴展的必要配套**：一旦有多台伺服器,需要有一個機制,決定「這次進來的請求,應該被送到哪一台伺服器處理」——這正是負載平衡器（見 [[003-load-balancing.md]]）扮演的角色，它站在多台伺服器之前,依照某種策略（輪詢、最少連線數、依照某個 key 做一致性雜湊等）,把流量分散到各台健康的伺服器上，並持續監測各伺服器的健康狀況（見 [[../backend-engineering/021-health-check-graceful-shutdown.md]] 討論過的健康檢查機制），一旦偵測到某台伺服器故障,自動把流量導向其他健康的伺服器,不讓故障的機器繼續拖累使用者體驗。

**資料庫層面水平擴展的額外複雜度**：應用伺服器（Web/API 層）的水平擴展相對直觀（只要應用程式是無狀態的,增加更多台應用伺服器,配合負載平衡即可），但**資料庫層面的水平擴展**，因為涉及「資料的一致性和分佈」這個更複雜的問題（見 [[../database/017-sharding.md]] 討論過的分庫分表挑戰），需要額外的架構設計（分片、複製、分散式交易等），複雜度遠高於應用伺服器層面的擴展。這也是為什麼很多系統的架構演進路徑，通常是先讓「無狀態的應用層」輕鬆地水平擴展，而「有狀態的資料庫層」則需要更謹慎的規劃（例如先做讀寫分離、再考慮分庫分表），兩者的擴展複雜度有本質性的差異。

**混合使用——先垂直再水平，或兩者並行**：實務上，很多系統的擴展策略,並非「非此即彼」，而是**先在合理範圍內做垂直擴展（因為簡單、快速），當垂直擴展的成本效益開始變差、或者需要更高的可用性保證時，再投入水平擴展的架構改造**，兩者可以在不同的元件、不同的階段搭配使用（例如,即使一個系統整體採用水平擴展的架構，架構裡的某些關鍵節點,依然可能透過提升硬體規格的方式,先解決眼前的效能瓶頸，而不是每一個效能問題,都立刻訴諸架構層面的水平擴展改造）。

## 面試回答方式

先給出兩者的核心定義——垂直擴展(提升單一機器規格)vs水平擴展(增加更多機器分散負載)。分別講出各自的優缺點——垂直擴展簡單但有物理和成本上限、依然是單點故障;水平擴展沒有規模上限且高可用,但需要應用架構支援(無狀態設計)、複雜度更高。給出核心洞察——「大型系統最終走向水平擴展,是因為業務規模終將超越單一機器硬體上限,且水平擴展帶來的高可用性對現代服務不可或缺」。可以延伸提到「無狀態設計是水平擴展能真正發揮效果的架構基礎」、「負載平衡是必要配套」、「資料庫層面的水平擴展複雜度遠高於應用層」這幾個重要細節,展現你不只知道兩個名詞的定義,還理解實現水平擴展需要的架構前提和面臨的挑戰。

## 常見追問

### 如果一個應用程式的程式碼,依然在某些地方假設「同一個使用者的連續請求,會被路由到同一台伺服器」(比如把使用者的購物車暫存在伺服器記憶體裡),要讓它支援水平擴展,具體需要做哪些改動?

**核心答案**：核心改動是把「原本存在單一伺服器記憶體裡的狀態」，**遷移到一個所有伺服器都能存取的共享儲存**——以購物車為例，可以把購物車的內容,改為儲存在 Redis 這類共享的快取資料庫裡（見 [[../redis/README.md]]），每台應用伺服器,不管收到的請求是哪個使用者,都透過查詢這個共享的 Redis,取得該使用者目前的購物車狀態,而不是依賴「這個使用者之前的請求,剛好也是這台伺服器處理的」這個脆弱的假設。額外還需要處理**負載平衡器的路由策略**——如果原本依賴「黏性會話（Session Affinity，負載平衡器刻意把同一個使用者的請求,持續路由到同一台伺服器)」這種折衷做法（在還沒有把狀態外移到共享儲存之前,暫時用這種方式讓應用程式「看起來」正常運作），一旦狀態真正外移到共享儲存,理論上就不再需要依賴黏性會話,可以讓負載平衡器用更簡單、更均勻的策略（如輪詢）分配流量。

**詳細解析**：這題把「無狀態設計」這個抽象原則,落實到一個具體、常見的改造場景，考察是否理解實際遷移的步驟和需要注意的細節。很多既有系統，在最初開發時,可能為了圖方便，直接把「使用者的購物車」這類需要在多次請求之間保持的狀態,儲存在應用伺服器自己的記憶體裡（例如用一個全域的雜湊表,以使用者 ID 為鍵,儲存每個使用者的購物車內容），這種做法在「只有一台伺服器」的階段完全沒有問題，但一旦需要水平擴展成多台伺服器，就會立刻暴露問題——如果負載平衡器,把同一個使用者的第一次請求路由到伺服器 A（購物車資料存進了伺服器 A 的記憶體），下一次請求卻被路由到伺服器 B（伺服器 B 的記憶體裡,完全沒有這個使用者的購物車資料，因為狀態只存在伺服器 A），使用者會發現自己的購物車「憑空消失了」，這是典型的因為「狀態綁定在特定伺服器」而導致水平擴展失敗的案例。正確的改造方向，是把這類「需要跨請求保持、且與特定使用者相關」的狀態，從「單一伺服器的私有記憶體」，遷移到「所有伺服器都能存取的共享儲存」——Redis 因為其高效能、支援豐富的資料結構（例如可以用 Hash 結構,方便地儲存一個使用者購物車裡的多筆商品項目），是這類場景常見的選擇。遷移完成後，任何一台應用伺服器,收到任何一個使用者的請求,都透過查詢/更新這個共享的 Redis,來讀取和修改購物車狀態,不再依賴「這個請求必須被路由到之前處理過同一個使用者的那台特定伺服器」這個脆弱的假設，這樣一來，負載平衡器就可以自由地,把任何使用者的任何一次請求,路由到任何一台健康的伺服器,而不用擔心會因此弄丟使用者的狀態。至於「黏性會話」這種折衷方案（在真正完成狀態外移之前，某些系統會暫時採用這種「讓負載平衡器,盡量把同一個使用者的請求,持續導向同一台伺服器」的過渡性做法，來規避狀態不一致的問題），雖然能暫時解決問題，但它本身有明顯的局限——如果那台被「黏住」的特定伺服器故障了，這個使用者的狀態依然會遺失（黏性會話只是把「單點故障」的範圍,從「整個系統」縮小到「這一個使用者的體驗」，並沒有真正解決「狀態綁定在特定機器」這個根本問題），且黏性會話,也會讓負載平衡的效果打折扣（因為某些伺服器可能因為黏住了較多活躍使用者,而承受了不成比例的負載，無法像「完全無狀態、可以自由分配」的架構那樣,實現真正均勻的負載平衡）。理解「讓依賴伺服器本地狀態的既有系統支援水平擴展,核心改造方向是把狀態遷移到共享儲存(如Redis),讓負載平衡器不再需要依賴黏性會話這種治標不治本的折衷方案,就能自由、均勻地分配流量到任何健康的伺服器」，展現你理解從「有狀態」演進到「無狀態」架構的具體改造路徑和其中的權衡考量。

**面試回答方式**：給出核心改造方向——「把原本存在單一伺服器記憶體裡的狀態(如購物車),遷移到所有伺服器都能存取的共享儲存(如Redis),讓任何一台伺服器都能透過查詢共享儲存,正確處理任何使用者的請求」。補充負載平衡器的配套調整——「如果原本依賴黏性會話這種過渡性折衷方案,狀態真正外移後就不再需要依賴它,可以用更簡單均勻的策略(如輪詢)分配流量」。可以延伸點出黏性會話的局限——「黏性會話只是把單點故障的範圍縮小,並沒有真正解決狀態綁定特定機器的根本問題,且會讓負載平衡的效果打折扣」。展現你理解從有狀態演進到無狀態架構的具體改造路徑。

### 除了「應用伺服器的水平擴展」和「資料庫的水平擴展」,系統裡還有哪些元件,也需要考慮擴展性?這些元件的擴展難度,是不是都差不多?

**核心答案**：不是,系統裡不同的元件,擴展的難度和策略差異很大——除了應用伺服器和資料庫，還需要考慮**快取層**（如 Redis,擴展相對容易,可以透過 Redis Cluster 這類方案做水平分片,見 [[../redis/018-redis-cluster.md]]）、**訊息佇列**（如 Kafka,設計上天生就支援透過增加 Partition 和 Broker 節點來水平擴展）、**負載平衡器本身**（見 [[../backend-engineering/010-api-gateway.md]] 討論過的閘道高可用設計)、**檔案/物件儲存**（通常倚賴雲端服務商或分散式檔案系統原生的水平擴展能力）。整體而言，**天生設計為分散式、且元件之間狀態耦合較少的系統(如訊息佇列、大部分 NoSQL 資料庫)，通常比傳統關聯式資料庫這類「原本就是為單機設計、後來才被迫演化出分散式能力」的系統，更容易水平擴展**，因為前者從架構設計之初就把「多節點協同運作」這件事考慮進去，而後者往往需要靠後續疊加的複雜機制（如分庫分表中介軟體）,勉強實現水平擴展的效果。

**詳細解析**：這題延伸到「一個完整系統裡,各種不同性質的元件,擴展難度存在顯著差異」這個容易被忽略的細節，考察是否理解不同技術本身的設計哲學,對其可擴展性有根本性的影響。訊息佇列（如 Kafka）之所以擴展相對容易，是因為它的核心設計,一開始就是為了分散式環境而生的——Kafka 的資料天然按照 Partition 劃分，增加更多的 Broker 節點、增加更多的 Partition,是這個系統設計裡「原生支援」的擴展手段，不需要額外的中介軟體或複雜的改造。快取層（如 Redis Cluster）也類似,雖然原始的單機 Redis 本身不是天生分散式的，但 Redis 官方後來推出的 Cluster 方案，透過雜湊槽（Hash Slot）機制（本質上是一致性雜湊的變體,見 [[../backend-engineering/017-consistent-hashing.md]]），提供了相對成熟、標準化的水平擴展路徑。相較之下，傳統的關聯式資料庫（如 MySQL），最初的設計哲學,是聚焦於「單機上,如何提供最強的一致性和交易保證（ACID）」，並沒有把「原生的多節點協同、資料自動分片」設計進最初的架構裡，這也是為什麼 MySQL 的水平擴展（分庫分表），往往需要依賴額外的中介軟體（如 ShardingSphere）或應用層的邏輯，去彌補資料庫本身「原生不支援分散式」這個先天限制，這個過程,遠比 Kafka 或 Redis Cluster 這類「原生為分散式而生」的系統要複雜得多（見 [[../database/017-sharding.md]] 討論過的分庫分表挑戰，如跨分片查詢、分散式交易等問題,本質上都是「在一個原本沒有考慮分散式的系統上,勉強疊加分散式能力」所必然要付出的額外複雜度）。理解「不同元件的擴展難度,和它們最初的設計哲學(是否從一開始就把分散式協同納入核心設計)有直接關係,天生為分散式而生的系統(訊息佇列、多數NoSQL)通常比傳統關聯式資料庫更容易水平擴展」，展現你對一個完整系統架構裡,不同組成元件在可擴展性這個維度上的本質差異,有更全面、更深入的認識。

**面試回答方式**：列舉除了應用層和資料庫外還需要考慮擴展性的元件——「快取層(Redis Cluster)、訊息佇列(Kafka原生支援透過Partition和Broker擴展)、負載平衡器本身、檔案/物件儲存」。給出核心洞察——「不同元件的擴展難度差異很大,天生設計為分散式的系統(訊息佇列、多數NoSQL)比傳統關聯式資料庫更容易水平擴展,因為前者從架構設計之初就把多節點協同納入考量,後者往往需要靠後續疊加的複雜機制勉強實現」。展現你理解不同元件的擴展難度和它們最初的設計哲學有直接關係，而非籠統地認為「擴展性」是所有元件都同等容易處理的問題。

### 「水平擴展沒有規模上限」這個說法是絕對的嗎?有沒有實務上會遇到的、水平擴展本身也難以突破的瓶頸?

**核心答案**：不是絕對的，水平擴展雖然理論上能持續增加機器數量,但實務上依然會遇到一些難以單純靠「加更多機器」解決的瓶頸——**（1）協調開銷隨節點數量增加而上升**——很多分散式系統，節點之間需要一定程度的協調（例如達成共識、同步狀態），節點數量越多，這種協調的開銷（網路通訊次數、延遲）可能越高，某些協調機制（如需要所有節點兩兩互相通訊的設計）,甚至會隨著節點數量呈非線性增長，導致「加了更多機器,反而整體效能提升有限甚至下降」這種報酬遞減甚至報酬為負的情況；**（2）分散式系統固有的一致性挑戰**（見 [[../backend-engineering/016-cap-theorem.md]]）——節點越多，網路分區、節點故障發生的機率相對也越高，維持資料一致性所需要的協調成本也隨之增加；**（3）某些業務邏輯,天生就難以被拆分成可以獨立平行處理的單位**——如果一個業務流程,本質上需要嚴格依序執行、且無法拆分成多個獨立部分同時處理,單純增加機器數量,並不能加速這個流程本身的完成速度（這呼應了平行運算領域裡「阿姆達爾定律（Amdahl's Law）」的概念——一個任務裡「無法平行化的部分」，會限制整體透過平行化所能達到的加速效果上限）。

**詳細解析**：這題挑戰「水平擴展沒有規模上限」這個經常被過於簡化理解的說法，考察是否理解真實的分散式系統，在規模持續擴大時，依然會遇到一些結構性的限制，而不是「機器越多,效能就無限線性提升」這種過於樂觀的假設。協調開銷的問題,是分散式系統設計裡一個反覆出現的主題——很多需要保證強一致性的分散式協調機制（例如某些需要「多數決」的共識演算法，如 Paxos/Raft），節點數量增加，雖然理論上能提供更高的容錯能力（能容忍更多節點同時故障而依然正常運作），但同時,「達成共識」這件事本身所需要的網路通訊次數和延遲，也會隨之增加，這意味著,盲目地增加節點數量，並不必然帶來系統整體吞吐量的線性提升，某些設計不當或協調機制選擇不當的系統，甚至可能出現「加了更多機器,反而因為協調開銷過大,導致整體效能不升反降」的反直覺現象，這也是為什麼很多分散式系統的架構設計，需要謹慎考慮「協調的範圍和頻率」，盡量把「需要嚴格協調的部分」限制在較小的範圍內（例如只在較小的一組節點內做強一致性協調，而不是要求整個龐大叢集裡的所有節點都參與每一次協調),來緩解這個問題。阿姆達爾定律揭示的限制，則是一個更根本、來自運算理論本身的限制——如果一個完整的任務，其中有一部分工作,天生就是「必須嚴格依序執行、無法被拆解成多個獨立單位平行處理」的（例如某個步驟,必須等待前一個步驟的結果才能開始），那麼不管你投入多少額外的機器去平行化「可以被拆分的那部分工作」，整體任務完成所需要的時間，終究會被那個「無法平行化的部分」所需要的時間給限制住——舉例來說，如果一個任務裡，有 10% 的工作本質上無法平行化，即使你有無限多台機器，能夠讓「可平行化的那 90%」工作瞬間完成，整個任務依然至少需要花費「那 10% 無法平行化的部分」所需要的時間，這意味著,單純的水平擴展（增加更多機器），對於「本質上難以拆分平行處理」的業務邏輯，效果是有其理論上限的，不是無限制地「加機器就能讓速度無限提升」。理解「水平擴展雖然在很多場景下確實能帶來接近線性的擴展效果，但依然存在協調開銷隨節點數量增加而上升、分散式一致性挑戰、以及某些業務邏輯天生難以平行化這幾個結構性限制,不是一個沒有任何邊界的、可以無限套用的萬能解方」，展現你對水平擴展這個概念，有超越「加機器就能解決一切」這種過度簡化理解的、更精確、更貼近理論和實務現實的認識。

**面試回答方式**：明確指出「不是絕對的,實務上依然存在難以單純靠加機器解決的瓶頸」。列舉三個具體限制——「協調開銷隨節點數量增加而上升(某些分散式協調機制,節點越多通訊成本越高,可能出現報酬遞減甚至效能不升反降)」、「分散式一致性的固有挑戰(節點越多,故障和網路分區發生機率相對也越高)」、「業務邏輯天生難以平行化的部分(呼應阿姆達爾定律,無法平行化的部分會限制整體加速效果的理論上限)」。展現你對水平擴展有超越「加機器就能解決一切」這種簡化理解的、更精確的認識。
