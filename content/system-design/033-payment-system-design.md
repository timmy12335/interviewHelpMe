# 題目

設計一個支付系統，處理下單付款、與第三方支付通道對接、以及對帳。

## 核心答案

支付系統的核心不是「把錢扣掉」，而是「在任何故障下都能查清楚錢的狀態」。設計要圍繞三件事：**冪等**、**狀態機**、**對帳**。

**主要元件**：**支付服務**（建立支付單、維護狀態）、**通道適配層**（封裝各家第三方的差異）、**回呼處理**（接收第三方的非同步通知）、**對帳服務**（每日比對本地紀錄與通道帳單）、**帳務服務**（複式記帳的流水）。

**支付單是一個明確的狀態機**：`建立 → 處理中 → 成功 / 失敗 / 未知`。**「未知」必須是一個合法狀態**——網路逾時的時候你確實不知道對方收到沒有，而把未知當成失敗會導致重複扣款。未知狀態靠主動查詢（輪詢通道的查詢介面）與對帳來收斂。

**冪等鍵貫穿全鏈路**：客戶端帶入的請求 ID → 支付單號 → 傳給通道的商戶訂單號。同一個冪等鍵重複提交必須回傳同一張支付單，而不是建立第二張。

## 詳細解析

金額絕對不用浮點數，而且要帶幣別。內部一律用**最小單位的整數**（分、cent）或 `BigDecimal`，並且每一筆金額都與幣別綁在一起——跨幣別的加總是一個必須在型別層被禁止的操作。匯率換算要記錄**當時使用的匯率與時間**，否則事後無法重現。

**回呼是不可信的輸入**。第三方的非同步通知可能**重複**、**亂序**、**遲到數小時**、甚至**偽造**。所以：**驗簽是必須的**、**處理必須冪等**、要用通道的訂單狀態而非通知的內容做最終判斷（收到通知後主動查一次），**而且不能依賴通知一定會到**——**必須有輪詢的兜底**。

對帳是支付系統唯一的真相來源。每日下載通道的帳單並逐筆比對，**差異分成四類**：**本地有通道無**（可能是未真正提交，需查詢確認）、**通道有本地無**（漏記，必須補）、**金額不符**（嚴重，需人工）、**狀態不符**（多數是時序造成，重查後多能收斂）。沒有對帳的支付系統，其帳目的正確性只是一個假設。

**帳務要用複式記帳**。每一筆資金移動記錄借貸兩方，讓「所有帳戶餘額之和恆為零」成為一個可持續驗證的不變量——任何 bug 造成的資金錯誤都會在這個檢查裡暴露，而單邊記帳的系統只能在使用者投訴時才發現。

退款與部分退款要當成獨立的支付單處理，**並在原單上累計已退金額**，避免超額退款；它同樣需要冪等、狀態機與對帳。

## 面試回答方式

先定位問題——核心不是把錢扣掉，而是在任何故障下都能查清楚錢的狀態，並給三個支柱（冪等、狀態機、對帳）。畫出元件（支付服務、通道適配、回呼處理、對帳、帳務）與**支付單的狀態機**，特別強調「未知」必須是一個合法狀態——把未知當成失敗會導致重複扣款，而它靠主動查詢與對帳收斂。加分點有四個：**冪等鍵貫穿全鏈路**（請求 ID → 支付單號 → 商戶訂單號）；金額用最小單位整數並與幣別綁定，跨幣別加總應在型別層被禁止；**回呼不可信**——會重複、亂序、遲到、偽造，所以驗簽、冪等、以查詢結果為準、且必須有輪詢兜底；複式記帳讓「餘額之和恆為零」成為可持續驗證的不變量，否則資金錯誤只能等使用者投訴才發現。

## 講稿

支付系統的核心不是把錢扣掉，而是在任何故障下都能查清楚錢的狀態。我會圍繞三件事設計，冪等、狀態機、還有對帳。

支付單是一個明確的狀態機，建立、處理中、成功或失敗，還有一個未知。未知必須是合法狀態，因為網路逾時的時候你確實不知道對方收到沒有，而把未知當成失敗會導致重複扣款。它靠主動查詢通道跟每日對帳來收斂。

冪等鍵要貫穿全鏈路，從客戶端的請求編號到支付單號再到給通道的商戶訂單號。同一個鍵重複提交必須回傳同一張單。

第三方的回呼是不可信的輸入，可能重複、亂序、遲到幾個小時，甚至偽造。所以我會驗簽、處理冪等、收到通知後主動查一次以通道狀態為準，而且不能依賴通知一定會到，必須有輪詢兜底。

帳務我會用複式記帳，讓所有帳戶餘額之和恆為零變成一個可以持續驗證的不變量。這樣任何 bug 造成的資金錯誤都會被檢查抓到，而不是等使用者投訴。

## 常見追問

### 支付與訂單之間怎麼保持一致？

**核心答案**：用非同步事件加上狀態驅動，不要用分散式交易。訂單服務建立訂單並發起支付，支付成功後由支付服務發出事件，訂單服務消費事件把訂單轉為已付款。事件的投遞用 **Outbox 模式**保證不丟，消費端**冪等**。**同時訂單側要有補償機制**：定期掃描「處於待付款超過 N 分鐘」的訂單並主動查詢支付狀態，不依賴事件一定送達。

**詳細解析**：「不用 2PC」的理由不只是效能，而是第三方通道本身不參與你的交易——你無法讓銀行加入一個兩階段提交，所以最終一致加對帳是唯一可行的模型。設計上最重要的是明確定義「以誰為準」：支付狀態以支付服務為準，而支付服務以通道的查詢結果為準——任何其他地方的狀態都是快取，可以延遲但不能成為判斷依據。這條規則能消除掉絕大多數「兩邊狀態不一致該信誰」的爭議。

**面試回答方式**：明確反對分散式交易，給出事件驅動 + Outbox + 冪等消費 + 定時掃描兜底的方案。真正的加分點是說明不用 2PC 的根本理由不是效能，而是第三方通道不參與你的交易——你無法讓銀行加入兩階段提交。收在設計原則：**明確定義「以誰為準」**（支付以支付服務為準，支付服務以通道查詢為準，其他都是快取），這條規則消除絕大多數狀態不一致的爭議。

### 怎麼設計支付的重試？

**核心答案**：**區分「安全重試」與「不安全重試」**。**查詢類的呼叫可以自由重試**；扣款類的呼叫只有在帶著同一個商戶訂單號、且通道保證冪等的前提下才能重試。如果通道不保證冪等，那就不能盲目重試——要改成「先查詢，確認未成功才重送」。 重試要**指數退避加抖動**，並有**最大次數與總時限**，超過就轉入「未知」狀態交給對帳處理。

**詳細解析**：最危險的錯誤是「對逾時直接重試扣款」。逾時意味著「請求可能已經到達並成功」——**重試一次就可能扣兩次錢**。**正確的處理是「逾時後先查詢」**：用商戶訂單號向通道查詢該筆交易的狀態，有結果就以它為準，查不到才重送。另一個實務細節是「重試的間隔要遠大於通道的處理時間」——如果通道平均要 3 秒，你設 1 秒重試，就是在系統性地製造重複請求。而所有的重試都必須留下紀錄，因為對帳時需要知道「這筆送了幾次」。

**面試回答方式**：先給分類——查詢類可自由重試，扣款類只有在同一商戶訂單號加通道冪等的前提下才行，通道不保證冪等時要改成「先查詢再重送」。核心加分點是點出最危險的錯誤是對逾時直接重試扣款——逾時意味著請求可能已經成功，重試就可能扣兩次。補充兩個實務細節：重試間隔要遠大於通道的處理時間（否則是系統性地製造重複），以及所有重試都要留紀錄供對帳使用。

### 怎麼防止重複支付與惡意刷單？

**核心答案**：**三層防護**。**冪等層**——同一個訂單只能有一張處於進行中的支付單，**用唯一索引在資料庫層強制**。**風控層**——限流（同一使用者、同一裝置、同一卡號的頻率）、金額異常偵測、以及黑名單。**業務層**——**支付單有效期**（超時自動關閉並釋放庫存）、**與訂單金額的強校驗**（支付金額必須等於訂單金額，不能由客戶端傳入）。

**詳細解析**：「金額由客戶端傳入」是支付系統最經典也最嚴重的漏洞。任何與金錢相關的數值都必須由服務端根據訂單重新計算，客戶端傳來的只能用於顯示與比對，不能作為扣款依據。同樣的原則適用於商品價格、折扣、與運費。在防重上，唯一索引比應用層的檢查可靠得多——應用層的「先查再插」在併發下必然失效，而資料庫的唯一約束是唯一能在所有併發情況下成立的保證。**風控層則要接受它會有誤判**，所以需要人工複核的通道與明確的申訴路徑，否則正常使用者被誤攔會造成比詐欺更大的損失。

**面試回答方式**：給三層防護（冪等的唯一索引、風控的限流與異常偵測、業務的有效期與金額強校驗）。最重要的加分點是點名「金額由客戶端傳入」是最經典也最嚴重的漏洞——任何與金錢相關的數值都必須由服務端根據訂單重新計算。第二個是**唯一索引比應用層檢查可靠**——「先查再插」在併發下必然失效，資料庫的唯一約束是唯一能在所有併發情況下成立的保證。收在風控的務實面：它一定會誤判，所以需要人工複核與申訴路徑。
