# 題目

設計一個郵件服務：收發、儲存、搜尋、以及垃圾郵件過濾。

## 核心答案

**拆成兩個幾乎獨立的子系統**：**傳輸**（與外部郵件伺服器用 SMTP 收發）與**存取**（使用者讀取自己的信箱）——它們的流量特性、可用性要求與擴展方式完全不同。

**傳輸側**：**接收走 SMTP 伺服器叢集加佇列**，發送走一個帶重試的投遞佇列——因為對方伺服器可能暫時不可用，郵件協定本身就假設投遞是異步且會重試數天的。

**儲存側**：郵件內容（不可變、體積大）放物件儲存，元資料（寄件者、主旨、時間、標籤、已讀狀態）放資料庫並按使用者分片——這個分離讓元資料的查詢很快，而內容按需載入。

**搜尋要獨立**：用倒排索引服務按使用者建立索引，因為 SQL 的 LIKE 在信件全文上完全不可行。

**去重是一個高價值的優化**：同一封群發郵件對一千個收件者只需要存一份內容，**用內容雜湊做引用計數**。

## 詳細解析

「郵件是不可變的」這個性質應該被充分利用。一封信一旦收到就不再改變——變的只有它的元資料（已讀、標籤、是否刪除）。所以內容可以放進最便宜的、只寫一次的儲存，做強力壓縮與跨使用者去重；而元資料很小、變更頻繁，適合放在關聯式資料庫並建立豐富的索引。這個「大而不變」與「小而多變」的分離，是很多系統都適用的模式——能主動指出它比只描述元件更能展現抽象能力。

投遞的重試策略必須遵循郵件的慣例。臨時失敗（4xx）要重試數小時到數天，逐步拉長間隔；永久失敗（5xx）**立即產生退信**。而重試太積極會被對方視為濫發並列入黑名單——這是一個「協定規範之外但實務上更重要」的約束。發送信譽（sender reputation）是郵件系統的核心資產：IP 與網域的信譽決定了郵件進收件匣還是垃圾桶，所以要嚴格區分交易性郵件與行銷郵件的發送 IP，避免行銷郵件的投訴率拖累密碼重設信的送達率。

**垃圾郵件過濾是多層的**：**連線層**（IP 黑名單、速率限制）、**協定層**（SPF、DKIM、DMARC 驗證寄件者身份）、**內容層**（模型分類）、**使用者層**（個人的黑白名單與檢舉反饋）。**其中 SPF/DKIM/DMARC 的價值最高且成本最低**——它們用網域擁有者的宣告直接判定偽造，是規則性的而非機率性的。

**同步協定的選擇影響體驗**：IMAP 支援多裝置同步狀態（已讀在手機標記後電腦也看得到），**POP3 則是下載即刪的單裝置模型**——現代服務基本上都用 IMAP 或自有的同步協定。

## 面試回答方式

先給兩個子系統的拆分（傳輸與存取）並說明它們的流量特性、可用性要求與擴展方式完全不同。給儲存的分離（內容放物件儲存、元資料放資料庫按使用者分片）、**搜尋要獨立的倒排索引**、以及**群發郵件的內容去重**。加分點有四個：**充分利用「郵件不可變」**——大而不變的內容放最便宜的只寫一次儲存並跨使用者去重，小而多變的元資料放關聯式資料庫，**這個模式很多系統都適用**；**重試太積極會被列入黑名單**，這是協定規範之外但實務上更重要的約束；**發送信譽是核心資產**——要嚴格區分交易性與行銷郵件的發送 IP，避免投訴率拖累密碼重設信的送達率；以及**SPF/DKIM/DMARC 價值最高成本最低**，因為它們是規則性而非機率性的判定。

## 講稿

我會拆成兩個幾乎獨立的子系統，傳輸跟存取。它們的流量特性、可用性要求、擴展方式完全不同。

儲存上有一個性質值得充分利用，就是郵件是不可變的。一封信收到之後內容不再改變，變的只有元資料，已讀、標籤、是否刪除。所以內容可以放進最便宜的只寫一次的儲存，做強力壓縮跟跨使用者去重，一封群發信對一千個收件者只需要存一份。而元資料很小、變更頻繁，適合放關聯式資料庫並建豐富的索引。這個大而不變跟小而多變的分離，其實很多系統都適用。

投遞這邊有一個協定規範之外但實務上更重要的約束。重試太積極會被對方視為濫發並列入黑名單。發送信譽是郵件系統的核心資產，所以要嚴格區分交易性郵件跟行銷郵件的發送位址，避免行銷信的投訴率拖累密碼重設信的送達率。

垃圾郵件過濾我會做多層，其中寄件者身份驗證那一層價值最高成本最低，因為它是規則性的判定而不是機率性的。

## 常見追問

### 郵件搜尋怎麼做到快？

**核心答案**：按使用者建立獨立的倒排索引，而不是一個全域大索引。理由是搜尋永遠限定在單一使用者的信箱內——**分片的維度是天然的**，每個索引只有幾萬到幾十萬份文件，查詢極快，而且新增使用者只是新增一個小索引，水平擴展毫無阻力。索引要包含主旨、寄件者、收件者與正文，並支援按時間範圍與標籤過濾。

**詳細解析**：「天然的分片維度」是這個設計最幸運的地方，而它值得被明確指出——多數搜尋系統的難點正是「查詢會跨越所有分片」（例如電商搜尋要掃全部商品），**而郵件不會**。這讓郵件搜尋在架構上比通用搜尋簡單一個量級。**實務上的難點反而在別處**：**附件的內容抽取**（PDF、Office 文件要解析成文字）、**多語言的分詞**、**以及索引的即時性**（新到的信應該立刻可搜尋，所以索引更新要在收信管線中同步或準即時完成）。另一個成本考量是「舊郵件的索引可以降級」：兩年前的信搜尋頻率極低，可以放在較慢的儲存上，用查詢時的略微延遲換取顯著的成本下降。

**面試回答方式**：給核心設計——**按使用者建獨立索引**，並指出**分片維度是天然的**：每個索引只有幾萬到幾十萬份文件、新增使用者只是新增小索引。核心加分點是明確指出**這是這個設計最幸運的地方**——多數搜尋系統的難點正是查詢跨越所有分片，而郵件不會，這讓它在架構上比通用搜尋簡單一個量級。收在真正的難點（附件內容抽取、多語言分詞、索引即時性）與成本手段（舊郵件的索引降級到較慢儲存）。

### 大附件怎麼處理？

**核心答案**：附件與郵件正文分離儲存，正文只保留引用。**上傳走預簽名 URL 直傳物件儲存**，**不經過應用伺服器**——避免大檔案佔用連線與記憶體。超過大小上限的附件轉為「雲端連結」（存在雲端硬碟，郵件裡只放一個有權限控制的連結）——**這也是主流郵件服務的做法**。

**詳細解析**：「附件去重」在企業環境裡的收益特別大：一份簡報在公司內被轉發數百次，實際只需要存一份——用內容雜湊作為物件鍵，引用計數管理生命週期。**但要注意一個安全問題**：跨使用者的內容去重意味著「知道某份檔案的雜湊就能推測它是否存在」，**在極端情況下可能洩漏資訊**。多數郵件服務接受這個風險（收益遠大於風險），但如果是高安全性的場景，去重應該限制在同一組織內部。 另一個實務點是「附件的病毒掃描」：它必須在附件可被下載之前完成，所以上傳完成到可用之間有一個掃描視窗——設計上要讓這個過程非同步且對使用者可見（顯示「掃描中」而非讓下載直接失敗）。

**面試回答方式**：給分離儲存、預簽名 URL 直傳、超限轉雲端連結的方案。加分點是附件去重在企業環境的收益特別大（一份簡報轉發數百次只存一份），**並主動指出它的安全副作用**：跨使用者去重意味著知道雜湊就能推測檔案是否存在，高安全性場景應限制在同組織內。收在病毒掃描必須在可下載之前完成，所以要讓掃描過程非同步且對使用者可見。

### 怎麼保證郵件不丟？

**核心答案**：**在 SMTP 層面「先落盤再回 250」**。SMTP 的語意是明確的——回覆 250 就代表你承諾負責這封信，所以在持久化完成之前絕不能回覆成功。**寧可回覆 4xx 讓對方稍後重試**（郵件協定天生支援），**也不要回覆成功後把信弄丟**。這是「不確定就讓上游重試」原則在協定層的體現。

**詳細解析**：郵件系統在「不丟」這件事上有一個其他系統羨慕的優勢：協定本身就設計了重試。發送方會在幾小時到幾天內反覆嘗試——所以接收方在任何不確定的情況下都可以安全地拒絕。這讓「可用性換一致性」變得幾乎沒有代價，是一個值得指出的協定設計優點。在內部，落盤之後的處理（分類、索引、投遞到信箱）都應該是可重試的非同步流程，**每一步都有狀態記錄**——因為它們失敗時信已經在系統裡了，不會丟，只會延遲。這種「先確保不丟，再慢慢處理」的結構，比試圖在一個交易裡做完所有事可靠得多。

**面試回答方式**：給核心規則——**先落盤再回 250**，並解釋 SMTP 的語意（回 250 就是承諾負責，所以持久化完成前絕不能回成功），**寧可回 4xx 讓對方重試**。加分點是指出郵件協定本身設計了重試，這讓「可用性換一致性」幾乎沒有代價，是值得指出的協定設計優點。收在內部結構：落盤之後的分類、索引、投遞都是可重試的非同步流程且每步有狀態記錄，這種「先確保不丟再慢慢處理」比在一個交易裡做完所有事可靠得多。
