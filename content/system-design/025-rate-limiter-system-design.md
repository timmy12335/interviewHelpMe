# 題目

設計一個服務端的 API 限流器。除了選用哪一種限流演算法之外，還需要決定：限流器應該放在系統的哪一層？限流規則存在哪裡、怎麼更新？請求被限流時，應該回傳什麼給呼叫端？

## 核心答案

限流演算法（令牌桶、漏桶、滑動視窗等，見 [[../backend-engineering/006-rate-limiting-algorithms.md]]）只是這道題的其中一塊，真正決定設計成敗的是另外三個決策。**（1）部署位置**——放在**用戶端**完全不可信（用戶端程式碼可被竄改、請求可被偽造），只能當作減少無效請求的優化，不能當作防線；放在**應用服務內部**實作簡單、能取得完整業務語境（如「這個使用者的方案等級」），但每個服務都要各自實作一遍，且流量已經打到服務才被擋下；放在**獨立的中介層（API Gateway／反向代理／service mesh sidecar）**是多數系統的選擇，能在流量進入業務服務之前就攔截，且限流邏輯只需維護一份。**（2）規則儲存與載入**——規則（哪個維度、每單位時間允許幾次）應該存成**設定檔或設定中心的資料，而不是寫死在程式碼裡**，由限流器**定期非同步載入到記憶體快取**，這樣改規則不需要重新部署，且每次請求判斷時讀的是本機記憶體、不會多打一次網路。**（3）被限流時的回應**——回傳 **HTTP 429 Too Many Requests**，並帶上 `X-Ratelimit-Limit`（配額上限）、`X-Ratelimit-Remaining`（剩餘次數）、`X-Ratelimit-Retry-After`（多久後可重試）這類標頭，讓呼叫端能**自己知道何時該退避**，而不是盲目重試把系統打得更慘；超量的請求視業務性質決定是**直接丟棄**（如一般查詢）還是**放進佇列稍後處理**（如非即時的批次任務）。

## 詳細解析

**為什麼部署位置是這道題最先要問清楚的事**：限流的目的是「在資源被打爆之前擋下超量流量」，這個目的隱含了一個要求——**攔截點必須在被保護的資源之前**。如果限流器實作在應用服務內部，請求其實已經佔用了連線、執行緒與部分記憶體才被判定為超量，在極端流量下，光是「處理這些將被拒絕的請求」本身就可能把服務拖垮，這就失去了保護的意義。把限流器上移到 API Gateway 或反向代理層（見 [[004-forward-vs-reverse-proxy.md]]），超量流量在更外圍、更廉價的一層就被消化掉，後端服務完全不會感知到。這也是為什麼「限流」常常和「負載平衡」（見 [[003-load-balancing.md]]）被放在同一層討論——它們都是**在流量抵達業務邏輯之前，對流量做整形**。反過來說，中介層也有它的代價：它離業務較遠，能拿到的資訊通常只有 IP、API Key、路徑這類通用維度，如果限流規則需要依賴業務語境（例如「免費方案每天 100 次、付費方案每天 10000 次」），就得想辦法把方案等級這個資訊，用某種方式（如 token 裡的宣告、或閘道去查一次使用者服務並快取）帶到閘道層，這是選擇中介層之後必須一併處理的問題。

**規則不該寫死在程式碼裡，以及為什麼要非同步載入到記憶體**：限流規則是一種**經常需要調整、且調整要快**的設定——上線初期抓不準門檻、遇到突發活動要臨時放寬、發現某個客戶在濫用要臨時收緊，這些都不應該走「改程式碼、重新測試、重新部署」的流程。把規則放在設定檔或設定中心，限流器啟動時載入、之後定期（如每隔幾十秒）在背景重新拉取，就能讓規則變更在很短時間內生效，而不需要動到服務本身。至於「為什麼要載入到記憶體」，關鍵在於**限流判斷位於每一個請求的關鍵路徑上**——限流器要能擋住暴增的流量，它自己的判斷必須極度廉價，如果每次判斷都要去設定中心或資料庫讀一次規則，等於在每個請求上都多加了一次網路往返，限流器自己就會先成為瓶頸，甚至在流量暴增時把設定中心也拖垮。「規則放遠端（方便管理）、副本放本機記憶體（保證判斷夠快）、用背景非同步更新連接兩者」是這類設定的通用處理模式，同樣的思路也出現在功能開關、路由規則等場景。

**回應設計的重點是「讓呼叫端能正確退避」**：很多人把限流的回應設計，簡化成「回一個錯誤就好」，但這會製造出一個危險的迴圈——呼叫端不知道自己為什麼被拒、也不知道什麼時候可以再試，最自然的行為就是**立刻重試**，而重試的請求又會被限流，形成持續不斷的無效請求風暴，反而把限流器和它前面的網路資源都消耗掉。回傳 429 這個**專門表達「你太快了」的語意化狀態碼**（而不是籠統的 400 或 503），加上 `Retry-After` 這類明確告知「等多久」的標頭，才能讓一個行為良好的呼叫端，在收到回應之後**主動安靜下來**，這實際上是把「保護系統」這件事，從單方面的防守，變成了服務端與呼叫端之間的協作。另外，`X-Ratelimit-Remaining` 這種「還剩多少配額」的資訊，能讓呼叫端在**還沒被拒絕之前**就自我調節（例如發現配額快用完，就主動降低送出頻率），把衝突消解在發生之前。

**超量請求是丟棄還是排隊，取決於業務的時效性**：直接丟棄的優點是簡單、資源佔用可預測，適合「這次失敗了，呼叫端重試一次也無所謂」的即時查詢類請求。放進佇列延後處理的優點是不損失請求，適合「這個操作最終一定要被執行，但晚幾秒鐘沒關係」的場景（如寄送通知、產生報表）。但排隊有個必須警惕的前提——**佇列必須有容量上限**，否則在持續超量的情況下，佇列會無限增長，把記憶體吃光，等於把「立刻拒絕」這個明確的失敗，換成了「延遲不斷惡化、最後整個服務崩潰」這個更難處理的失敗，這與艙壁隔離（見 [[../backend-engineering/019-bulkhead-pattern.md]]）強調的「資源必須有明確邊界」是同一個原則。

## 面試回答方式

先點出這道題的框架——「限流演算法只是其中一塊，真正的設計決策有三個：放哪一層、規則怎麼管、被限流時回什麼」，這能立刻和只會背演算法的人拉開差距。談部署位置時給出三個選項與各自取捨，並說明為什麼多數系統選中介層（攔截點必須在被保護資源之前，且邏輯只需維護一份），同時誠實指出中介層的代價（拿不到業務語境，需要額外想辦法把方案等級這類資訊帶過去）。談規則管理時給出「遠端存放、本機記憶體快取、背景非同步更新」這個模式，並說明為什麼不能每次請求都去讀遠端（限流判斷在每個請求的關鍵路徑上，多一次網路往返會讓限流器自己變成瓶頸）。談回應設計時強調 429 加上 `Retry-After` 的價值不只是「告知」，而是**避免呼叫端盲目重試形成無效請求風暴**，把保護系統從單方面防守變成雙方協作。最後補一句排隊方案的前提——佇列一定要有上限，否則只是把明確的失敗換成更難處理的雪崩。

## 常見追問

### 限流的維度應該怎麼選？依 IP、依使用者、還是依 API 端點？

**核心答案**：這三種維度解決的是**不同的問題**，成熟的系統通常**同時套用多層**。**依 IP** 主要防範「匿名的、大量的濫用」（如爬蟲、腳本攻擊），優點是連未登入的請求也能擋，缺點是**同一個 IP 背後可能有大量正常使用者**（企業出口、行動網路的 NAT、校園網路），門檻設太緊會誤傷一整批人。**依使用者／API Key** 是最貼近商業語意的維度（配額本來就是賣給某個帳號的），能精確地區分免費與付費方案，缺點是**只對已驗證的請求有效**，登入之前的流量擋不到。**依 API 端點**解決的是「不同操作的成本差異極大」這個問題——一個查詢可能只花 1 毫秒，一個報表匯出可能花 10 秒，用同一個門檻管理兩者顯然不合理，昂貴的端點必須有自己更嚴格的配額。實務上常見的是**組合套用**：最外層依 IP 擋掉明顯的異常來源，中間依使用者套用商業配額，最內層對特別昂貴的端點再加一道保護，任一層超限即拒絕。

**詳細解析**：這題考察是否理解限流維度不是單選題，而是**每個維度各自對應一種它獨有、其他維度擋不住的威脅**。理解這一點的關鍵，在於把每個維度想成「當這個維度被拿掉時，什麼樣的攻擊或濫用會直接穿透」。如果拿掉 IP 維度，只依使用者限流，那麼**登入端點本身**就完全裸露了——攻擊者可以用無數組帳號密碼組合去暴力嘗試，因為每次嘗試都是「未驗證」的，根本沒有使用者身分可以拿來計數，這也是為什麼登入、註冊、忘記密碼這類端點，幾乎一定要有依 IP（甚至依帳號名稱）的限流。如果拿掉使用者維度，只依 IP 限流，那麼商業上的配額分級就無從實現——付費客戶和免費使用者如果剛好從同一個企業網路出口連進來，會共用同一份配額，這在商業上是不可接受的。如果拿掉端點維度，只依使用者限流，那麼一個「每分鐘 1000 次請求」的配額，對於廉價查詢是合理的，但如果使用者把這 1000 次全部打在最昂貴的報表匯出端點上，實際造成的資源消耗可能是前者的數千倍，配額數字本身失去了「限制資源消耗」的意義——這也提示了一個進階做法：把配額從「請求次數」改成「**成本點數**」，不同端點消耗不同點數，讓配額真正對應到資源消耗而非請求數量。理解「限流維度不是三選一，而是每個維度各自封堵一類其他維度封不住的漏洞，成熟系統會分層組合套用，並且在端點成本差異極大時，可以進一步把配額單位從請求次數改成成本點數」，展現你能從「拿掉這個維度會漏掉什麼」的角度，反推每個維度存在的必要性。

**面試回答方式**：先明確回答「不是三選一，成熟系統會分層組合套用」。用「拿掉會漏掉什麼」的方式論證每個維度的必要性——「拿掉 IP，登入端點就完全裸露，因為暴力破解的請求根本沒有使用者身分可以計數」、「拿掉使用者，就無法實現付費與免費的商業配額分級」、「拿掉端點，使用者可以把配額全部打在最昂貴的操作上，配額數字失去限制資源消耗的意義」。給出實務的分層順序——最外層依 IP、中間依使用者、最內層對昂貴端點加嚴。最後補一個進階做法——「端點成本差異極大時，可以把配額單位從請求次數改成成本點數，讓配額真正對應資源消耗」。

### 為什麼限流器通常建議「失敗時放行（fail-open）」而不是「失敗時拒絕（fail-close）」？有沒有例外？

**核心答案**：限流器通常依賴外部元件（如集中式的計數儲存），當這個依賴掛掉時，限流器面臨「無法判斷這個請求是否超量」的處境。**fail-open（放行）**的理由是——限流器是一個**保護性的附屬設施，而不是業務本身**，如果因為限流器故障就把所有請求都擋下來，等於讓一個附屬元件的故障，升級成整個服務的完全不可用，這通常比「短時間內失去限流保護、少數超量流量進來」嚴重得多。但這**有明確的例外**：當限流的目的不是「保護容量」而是「**執行安全或商業契約**」時，就必須 fail-close——例如防止暴力破解密碼的限流，如果故障時放行，等於在故障期間完全撤掉了防護，攻擊者只要先設法讓計數儲存過載，就能繞過整個機制；同理，用於計費的配額限制，故障時放行等於讓客戶免費超用。所以正確的說法是——**依「這道限流是為了保護容量，還是為了執行安全／商業契約」來決定，前者 fail-open，後者 fail-close**。

**詳細解析**：這題考察是否理解「fail-open 是預設建議，而不是普遍真理」，以及背後的判斷準則。理解的關鍵，在於認識到 fail-open 與 fail-close 的選擇，本質上是在比較**兩種失敗的相對代價**。對於一般的容量保護型限流，失敗的兩種代價是：fail-open 的代價是「限流器故障的這段期間，超量流量會打到後端，後端可能變慢甚至過載」；fail-close 的代價是「限流器故障的這段期間，**所有**流量都被拒絕，服務 100% 不可用」。注意這兩者的量級差異——前者是**機率性的、程度可變的**損害（超量流量不一定真的會打爆後端，即使打爆，後端通常還有自己的降級與熔斷機制作為第二道防線，見 [[../backend-engineering/007-circuit-breaker-pattern.md]]），後者是**確定性的、全面的**損害（不管實際流量多寡，服務直接歸零），在這個比較之下 fail-open 明顯較優，這也呼應了一個更普遍的可用性設計原則——**不要讓非核心元件的故障，具備讓核心功能完全停擺的能力**。但這個比較是建立在「限流的目的是保護容量」這個前提上的，一旦限流的目的變成執行安全或商業契約，代價的天平就完全翻轉了：對於防暴力破解的限流，fail-open 的代價不再是「後端可能變慢」，而是「**帳號可能被攻破**」，這是不可逆的安全損害；對於計費配額，fail-open 的代價是直接的金錢損失，且攻擊者有明確動機去**主動製造限流器的故障**來觸發放行——這一點尤其關鍵，當 fail-open 的行為本身可以被攻擊者當作攻擊路徑（先打垮計數儲存，再繞過限流），fail-open 就從「合理的可用性取捨」變成了「可被利用的設計缺陷」。理解「fail-open 是容量保護型限流的合理預設，因為它把確定性的全面不可用換成機率性的局部降級，且後端通常還有熔斷降級作為第二道防線；但當限流的目的是安全或計費契約時必須 fail-close，因為此時放行的代價是不可逆的安全或金錢損害，且攻擊者有動機主動製造故障來觸發放行」，展現你能辨識預設建議的適用邊界，而不是把它當成無條件的規則。

**面試回答方式**：先給出預設建議與理由——「一般的容量保護型限流建議 fail-open，因為限流器是保護性的附屬設施，不該讓它的故障升級成整個服務完全不可用」。用代價比較把理由講清楚——「fail-open 的代價是機率性的局部降級（而且後端還有熔斷降級作為第二道防線），fail-close 的代價是確定性的服務歸零」。接著主動指出例外——「但如果限流的目的是安全（防暴力破解）或商業契約（計費配額），必須 fail-close」。給出例外的關鍵理由——「此時放行的代價是不可逆的安全或金錢損害，而且更危險的是，攻擊者有明確動機主動去打垮計數儲存來觸發放行，fail-open 本身變成一條攻擊路徑」。展現你能辨識預設建議的適用邊界。

### 限流和熔斷、降級都是保護系統的手段，它們的分工是什麼？

**核心答案**：三者的關鍵差異在於**針對的方向與觸發的依據不同**。**限流**是**入口方向、依據流量**——在請求進入系統之前，判斷「這個來源送得太快了」，主動拒絕超出約定速率的請求，保護的是**自己**不被外部流量壓垮。**熔斷**（見 [[../backend-engineering/007-circuit-breaker-pattern.md]]）是**出口方向、依據下游健康狀態**——當自己呼叫的下游服務持續失敗或逾時，暫時停止呼叫、快速失敗，保護的是**自己不被下游的故障拖垮**（避免執行緒全部卡在等待下游回應上），同時也給下游喘息的空間。**降級**是**依據系統整體資源壓力，主動放棄非核心功能**——在資源緊繃時，關閉推薦、個人化、統計上報這類次要功能，把資源集中保障核心交易路徑，保護的是**核心功能的可用性**。簡單記憶：限流管「進來多少」、熔斷管「出去要不要打」、降級管「保哪些、丟哪些」。

**詳細解析**：這題考察是否能把幾個容易混淆的保護手段，用清晰的維度區分開來，而不是籠統地說「它們都是保護系統的」。理解的關鍵，在於抓住每個手段**觸發判斷所依據的訊號來源**。限流依據的訊號是**請求的到達速率**——它完全不需要知道下游健康與否、也不需要知道系統資源是否吃緊，只要某個來源在單位時間內的請求數超過預設門檻，就拒絕，這是一種**基於約定的、預防性的**控制，它在系統還很健康的時候就已經在工作了。熔斷依據的訊號是**下游呼叫的失敗率或延遲**——它是**反應性的**，必須先觀察到下游真的出問題了才會觸發，而它要解決的問題有一個容易被忽略的重點：不只是「下游壞了，打過去也沒用」，更關鍵的是**如果不熔斷，自己的執行緒會大量卡在等待一個已經失效的下游上，最後自己也因為執行緒耗盡而癱瘓**——也就是說熔斷真正防的是**故障的傳染**，這與艙壁隔離（見 [[../backend-engineering/019-bulkhead-pattern.md]]）的目標高度相關。降級依據的訊號是**系統自身的資源水位或人工判斷**——它不看單一來源的流量、也不看單一下游的健康，而是從整體視角做取捨：現在資源就這麼多，什麼必須活著、什麼可以先關掉，它的決策單位是**功能**而不是請求。把三者放在一起看，會發現它們構成了一條完整的防線：限流在最外圍削掉超量的輸入，降級在中間確保有限資源優先供給核心路徑，熔斷在對外呼叫的邊界上阻止其他系統的故障傳染進來——三者針對的是三個不同的失效來源（外部流量過大、自身資源不足、下游依賴故障），彼此不能互相取代，這也是為什麼成熟的系統通常三者都會具備。理解「限流依據到達速率、是預防性的入口控制；熔斷依據下游失敗率、是反應性的出口控制，真正防的是故障傳染與自身執行緒被拖垮；降級依據自身資源水位、以功能為單位做取捨；三者對應三種不同的失效來源，構成完整防線而不能互相取代」，展現你能用一致的維度（訊號來源、作用方向、決策單位）把相似概念系統性地區分開來。

**面試回答方式**：用一組清晰的維度切開三者，不要籠統帶過——「限流是入口方向、依據到達速率、預防性的；熔斷是出口方向、依據下游失敗率、反應性的；降級是依據自身資源水位、以功能為單位做取捨」。給出一句好記的總結——「限流管進來多少、熔斷管出去要不要打、降級管保哪些丟哪些」。補上熔斷最容易被忽略的重點——「熔斷防的不只是『打過去也沒用』，更關鍵的是避免自己的執行緒大量卡在等待失效的下游，最後自己也被拖垮，它真正防的是故障傳染」。最後把三者連成一條防線——「三者對應外部流量過大、自身資源不足、下游依賴故障這三種不同的失效來源，不能互相取代，所以成熟系統通常三者都有」。
