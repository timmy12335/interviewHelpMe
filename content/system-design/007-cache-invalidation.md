# 題目

快取系統常見的三大經典問題——快取穿透、快取擊穿、快取雪崩——分別是什麼？各自怎麼解決？

## 核心答案

**快取穿透（Cache Penetration）**——查詢一個**根本不存在**的資料（既不在快取裡、資料庫裡也沒有），因為快取沒有這筆資料，每次查詢都會直接打到資料庫，如果有惡意攻擊者，大量查詢這類不存在的 key，會讓資料庫承受大量原本應該被快取擋下的無效查詢。解法包括**快取空值（Cache Null）**——即使查詢結果是「不存在」，也把這個「不存在」的結果快取起來（設定較短的過期時間），下次查詢同一個不存在的 key，直接從快取回應「不存在」，不需要再查資料庫；以及**布隆過濾器（Bloom Filter）**——在查詢資料庫之前，先用布隆過濾器快速判斷「這個 key 是否可能存在」，如果布隆過濾器判定「絕對不存在」，直接拒絕查詢，連快取都不用查。**快取擊穿（Cache Breakdown）**——一個**極度熱門、被大量請求同時查詢**的 key，剛好過期失效的瞬間，導致大量並發請求同時穿透快取，湧向資料庫查詢同一筆資料。解法是**互斥鎖（Mutex Lock）**——只允許第一個發現快取失效的請求，去查詢資料庫並重建快取，其他同時到來的請求，等待這個重建完成後直接使用新的快取結果，而不是每個請求都各自去查資料庫。**快取雪崩（Cache Avalanche）**——**大量不同的 key，幾乎在同一時間點集體過期失效**（或者快取伺服器本身突然大規模故障），導致極大量的請求同時湧向資料庫。解法包括**為不同 key 的過期時間，加上隨機的抖動（Jitter）**，避免大量 key 集中在同一時刻同時過期；以及**提升快取系統本身的高可用性**（如叢集部署），降低快取伺服器整體故障的機率。

## 詳細解析

**快取穿透的攻擊風險與空值快取的取捨**：如果一個惡意攻擊者，故意查詢大量「肯定不存在」的 key（例如刻意構造不存在的使用者 ID），因為這些 key 從來不在快取裡（快取只會快取「存在」的資料），每一次這類查詢，都會直接繞過快取的保護，打到資料庫，如果攻擊者以高頻率、大量地發起這種查詢，可能造成資料庫因為承受大量無效查詢而過載，這正是「穿透」這個名稱的由來——查詢直接穿透了快取這道防線。用「快取空值」來緩解這個問題，代價是**需要為這些「不存在」的結果，額外佔用一些快取空間**（雖然通常設定較短的過期時間），且如果資料**之後真的被建立了**（例如原本不存在的使用者 ID，之後真的被註冊了），需要確保「建立新資料時，能正確地讓這個之前快取的『不存在』標記失效」，否則會出現「明明資料已經存在了，但因為快取裡還殘留著『不存在』的舊標記，導致使用者暫時查不到自己剛建立的資料」這種新的不一致問題。

**布隆過濾器解決快取穿透的原理與代價**：布隆過濾器是一種空間效率極高的機率型資料結構，能夠快速回答「這個元素**可能**存在」或「這個元素**絕對不**存在」（它可能有一定的誤判率，把「不存在」誤判成「可能存在」，但**絕對不會**把「存在」誤判成「不存在」）。把所有真實存在的 key（例如所有真實的使用者 ID），預先建立進一個布隆過濾器裡，查詢請求進來時，先問布隆過濾器「這個 key 有沒有可能存在」，如果布隆過濾器明確回答「絕對不存在」，就直接拒絕，連快取和資料庫都不需要查詢，能非常高效地過濾掉惡意或無意義的無效查詢；如果布隆過濾器回答「可能存在」（可能是真的存在，也可能是誤判），才繼續走正常的「查快取、查資料庫」流程。這種方式的優勢是**極度節省記憶體、判斷速度極快**，缺點是**需要額外維護這個布隆過濾器**（新增資料時，需要同步更新布隆過濾器；且布隆過濾器本身，通常不支援直接刪除元素，這在「資料被刪除」的場景下需要額外的處理機制）。

**快取擊穿與互斥鎖的具體實作**：快取擊穿，特別針對「極度熱門的單一 key」——例如電商首頁的「今日爆款商品」資訊，可能同時被成千上萬的使用者查詢，如果這個 key 恰好在某個瞬間過期失效，這成千上萬個並發請求，會同時發現快取未命中，一窩蜂地衝向資料庫，即使資料庫，本來完全有能力應付「正常情況下，少量查詢」的負載，也可能因為這種瞬間的、集中在同一筆資料上的高並發查詢，而承受不住。互斥鎖的解法是——當第一個請求，發現快取失效需要重建時，先嘗試取得一個針對這個特定 key 的鎖（通常用 Redis 的 `SETNX` 這類原子操作實現，見 [[../redis/014-distributed-lock.md]]），成功取得鎖的這個請求，才真正去查詢資料庫並重建快取；其他幾乎同時到達、發現快取也是失效狀態的請求，因為無法取得這個鎖（鎖已經被第一個請求持有），會**短暫等待**（可能透過輪詢或其他等待機制），等到第一個請求完成資料庫查詢並重建好快取之後，這些等待中的請求，直接從已經重建好的快取讀取結果，而不需要每一個都各自去查一次資料庫，把「原本可能是成千上萬次的資料庫查詢」，收斂成「只有一次」真正的資料庫查詢。

**快取雪崩的兩種成因與各自的緩解手段**：快取雪崩有兩種常見成因——**（1）大量 key 在同一時間點集中過期**（例如系統啟動時，批次地把大量資料一次性載入快取，並統一設定了相同的過期時間，導致這些 key，在未來的某個時間點，會集中一起失效），緩解方式是**為每個 key 的過期時間，額外加上一個小範圍的隨機抖動**（例如「基礎過期時間是 1 小時，額外加上 0 到 5 分鐘之間的隨機值」），讓大量 key 的實際過期時間，分散開來，而不是完全同步地集中在同一秒；**（2）快取伺服器本身發生大規模故障**（例如整個 Redis 叢集，因為某種原因完全無法存取），這種情況下，即使個別 key 的過期時間，已經被錯開分散了，依然無法避免「快取整體不可用」導致的所有請求都直接打向資料庫，緩解方式是**提升快取系統本身的高可用性**（部署主從複製、叢集模式，而非依賴單一的快取實例，見 [[../redis/016-master-slave-replication.md]] 和 [[../redis/018-redis-cluster.md]]），以及在應用層，搭配前面討論過的**服務降級（Service Degradation）**（見 [[../backend-engineering/008-service-degradation.md]]）和**限流（Rate Limiting）**（見 [[../backend-engineering/006-rate-limiting-algorithms.md]]）機制，作為快取系統萬一真的完全失效時的最後防線，避免資料庫被瞬間湧入的全部流量徹底壓垮。

## 面試回答方式

依序講清楚三個經典問題的定義和解法——快取穿透(查詢根本不存在的資料，反覆繞過快取打資料庫，用空值快取或布隆過濾器解決)、快取擊穿(單一極度熱門的key過期瞬間，大量並發請求同時湧向資料庫，用互斥鎖只讓一個請求重建快取、其他請求等待)、快取雪崩(大量不同key集中同時過期，或快取系統整體故障，用過期時間加隨機抖動、以及提升快取系統高可用性來緩解)。用具體場景幫助說明每個問題(如電商爆款商品的快取擊穿)。可以延伸提到布隆過濾器解決穿透的具體原理(絕不會誤判存在為不存在，但可能誤判不存在為存在)和它的代價(需要額外維護、通常不支援直接刪除)。展現你不只知道這三個問題的名稱，還理解每個解法的具體實作機制和權衡。

## 常見追問

### 快取穿透用「空值快取」的方式，如果之後這筆原本不存在的資料真的被建立了，要怎麼避免「快取裡還殘留著舊的不存在標記，導致查不到新資料」這個問題?

**核心答案**：最直接的解法是——**在建立新資料的邏輯裡，額外加上「主動清除這個 key 對應的空值快取標記」這個步驟**，也就是說，新增資料的操作，不只是單純地把資料寫入資料庫，還需要**主動地檢查並刪除**快取裡，可能之前為這個 key 設定的「不存在」空值標記，確保下一次查詢時，因為快取裡已經沒有殘留的舊標記，會正常地觸發「查詢資料庫，發現資料確實存在」的流程，正確地把「存在」的結果重新快取起來。這其實和之前討論過的 Cache-Aside 模式裡「寫入操作，需要讓對應的舊快取失效」這個原則是相通的，只是這裡的「寫入」，是「建立一筆全新的資料」，而不是「更新一筆既有的資料」。

**詳細解析**：這題深入快取穿透解法(空值快取)本身，又會衍生出的一個新的一致性問題，考察是否理解「任何形式的快取，不管快取的是『資料本身』還是『資料不存在』這個判斷結果，都需要有對應的『失效』機制，才能確保快取不會變成永久錯誤的來源」這個更根本的原則。空值快取這個技巧，本質上是把「查詢這個 key，結果是不存在」，也當作一種需要被快取的「結果」來處理，這意味著，這個「不存在」的快取結果，同樣需要遵循快取系統的一般規律——**它終究會過期(通常設定較短的TTL)，或者如果對應的底層資料狀態發生了變化(這裡指的是『從不存在變成存在』這個狀態轉變)，理應也要有一個機制，主動地讓這份已經過時的快取結果失效**，如果只是被動地依賴TTL到期(等待空值快取自然過期)，這意味著，即使一筆資料已經被正確地建立到資料庫裡，在這份空值快取的TTL到期之前，任何查詢這個key的請求，依然會被(過時的)空值快取攔截，得到「不存在」這個錯誤的答案，這段時間的長短，取決於當初空值快取設定的TTL(如果TTL設定得比較保守、較長，這個「明明資料已經存在、卻查不到」的錯誤視窗，也會相應地比較長，這對使用者體驗是不利的，尤其是「剛註冊完帳號，馬上想查詢自己的資料」這類場景，使用者不會理解「為什麼系統說我不存在」)。正確的做法，是把「建立新資料」這個操作，視為一次需要讓相關快取失效的寫入操作——不管這筆資料，之前是否曾經被查詢過、是否曾經觸發過空值快取的建立，建立新資料的邏輯，都應該**主動地**去嘗試刪除快取裡，可能存在的、針對這個 key 的空值標記(即使實際上，這個 key 可能從來沒有被查詢過、根本沒有任何空值快取存在，直接執行一次「刪除」動作，也不會有任何副作用，刪除一個不存在的快取記錄，通常是一個安全的空操作)，這樣一來，新資料建立完成後，緊接著的查詢，會發現快取裡(不管是正常的資料快取，還是空值標記)都已經被清空，觸發正常的「重新查詢資料庫、取得最新且正確的結果、重新快取」流程，確保使用者能夠立即、正確地查詢到自己剛建立的新資料，而不需要等待原本空值快取的TTL自然到期。理解「空值快取這個技巧，本身也需要有配套的失效機制，建立新資料的操作，需要主動地清除可能殘留的空值標記，而不能只依賴TTL被動地等待過期，否則會出現『資料明明已經存在、但因為舊的空值快取還沒過期而查不到』這種令人困惑的體驗問題，這其實是Cache-Aside『寫入操作需要讓相關快取失效』這個一般性原則，在空值快取這個具體場景下的延伸應用」，展現你理解快取失效機制，需要被一致地應用到所有形式的快取內容(包括代表『不存在』的空值快取)，而不是只考慮「正常資料」這一種情況。

**面試回答方式**：給出核心解法——「建立新資料的邏輯，需要主動地清除這個key之前可能存在的空值快取標記，而不能只依賴空值快取自然的TTL到期」。解釋為什麼——「如果只依賴TTL被動等待，在空值快取真正過期之前，即使資料已經建立完成，查詢依然會被過時的空值標記攔截，得到錯誤的不存在結果，這對『剛註冊完馬上想查自己資料』這類場景體驗很不好」。點出這其實呼應了一個更一般的原則——「這是Cache-Aside模式『寫入操作需要讓相關快取失效』這個原則，延伸應用到空值快取這個特殊情境的具體體現，建立新資料某種程度上也是一種需要處理快取失效的寫入操作」。展現你理解快取失效機制需要一致地應用到所有形式的快取內容，而不只是正常資料快取這一種情況。

### 互斥鎖解決快取擊穿時，那些「等待中」的請求，具體要怎麼「等待」？是無限期地等下去嗎？

**核心答案**：不應該無限期地等待，常見的做法是搭配**「短暫的輪詢＋逾時機制」**——沒有取得鎖的請求，會**短暫地睡眠一小段時間**（例如幾十到幾百毫秒），之後再次嘗試查詢快取（此時，如果第一個持有鎖的請求，已經完成了資料庫查詢並重建好快取，這次查詢就能直接命中重建後的快取結果），如果多次嘗試後，依然發現快取還沒有被重建好（可能是持有鎖的那個請求，異常地卡住了或處理得比預期慢），應該設定一個**合理的逾時上限**（例如總共只等待 1-2 秒），一旦超過這個逾時上限，等待中的請求，可以選擇**放棄等待、直接自己去查詢資料庫**（作為最後的降級手段，雖然這意味著，在極端情況下，可能不只一個請求真正查詢了資料庫，但至少避免了「因為鎖持有者異常，導致大量請求無限期卡住」這種更嚴重的問題），或者回傳一個「請稍後再試」的提示給使用者。

**詳細解析**：這題深入互斥鎖解決快取擊穿的具體實作細節，考察是否理解「等待」這個看似簡單的動作，在真實系統設計裡，需要考慮的邊界情況和保護機制。如果「等待中的請求」被設計成**無限期地**卡住，直到鎖被釋放為止，這隱含了一個危險的假設——「持有鎖的那個請求，一定會在合理的時間內順利完成資料庫查詢並釋放鎖」，但真實系統裡，持有鎖的請求，完全有可能因為各種原因而異常地延遲甚至完全卡住(例如資料庫本身暫時回應緩慢、或者持有鎖的那個應用伺服器實例，在完成查詢之前就當機了)，如果沒有任何逾時保護，這種異常情況，會導致**所有正在等待這把鎖的其他請求，也跟著被無限期地卡住**，這不僅不能解決問題，反而可能引發比「大量請求同時查詢資料庫」更嚴重的後果——原本快取擊穿的問題，是「短暫的、瞬間的高並發衝擊」，資料庫即使承受壓力，通常也能在短時間內恢復；但如果因為互斥鎖設計不當，導致大量請求被無限期地卡住，等待著一個可能永遠不會被釋放的鎖，這會演變成一種更持久、更難以自行恢復的系統性阻塞，類似之前討論過的「執行緒池（Thread Pool）被大量卡住的請求佔滿」這種艙壁隔離要解決的問題(見 [[../backend-engineering/019-bulkhead-pattern.md]])。正確的設計，必須為「等待」這個動作，設定**明確的時間界限**——透過「短暫睡眠、然後重新檢查快取狀態」這種輪詢的方式(而非持續阻塞地死等)，讓等待中的請求，能夠週期性地檢查「快取是不是已經被重建好了」，並且設定一個**總的逾時上限**，一旦超過這個上限，就代表「持有鎖的那個請求，可能出了問題，不應該再繼續無限期地等下去」，這時候，系統需要有一個**明確的降級決策**——是選擇「放棄等待、自己也去查一次資料庫」(這是一種務實的權衡——寧可在極端情況下，多付出幾次資料庫查詢的代價，也不要讓大量請求被永久卡住)，還是選擇「乾脆地告知使用者請稍後重試」(把問題明確地暴露出來，而不是讓請求默默地卡在一個看不到盡頭的等待裡)，這個決策，取決於具體業務對「即使犧牲一些效能保護、也要優先保證回應」和「寧可稍微延遲讓使用者知道系統正在忙碌」這兩種傾向之間的權衡。理解「互斥鎖解決快取擊穿時，等待中的請求不能無限期地卡住，必須搭配短暫輪詢和明確的逾時上限，一旦逾時就需要有明確的降級決策(放棄等待自行查詢，或告知使用者稍後重試)，否則一旦鎖的持有者異常延遲，會導致大量請求被無限期卡住，演變成比原本快取擊穿問題更嚴重的系統性阻塞」，展現你理解互斥鎖這個解法，在實際落地時，需要搭配完整的逾時和降級設計，而不只是「用一把鎖擋住其他請求」這麼簡單的概念。

**面試回答方式**：給出核心機制——「不能無限期等待，應該用短暫輪詢+逾時機制，等待中的請求短暫睡眠後重新檢查快取狀態，設定一個總的逾時上限」。解釋為什麼需要逾時——「如果持有鎖的請求異常延遲或當機，沒有逾時保護會導致大量等待中的請求被無限期卡住，演變成比原本快取擊穿問題更嚴重的系統性阻塞」。給出逾時後的降級選擇——「放棄等待自己也去查一次資料庫(務實地接受極端情況下多幾次查詢的代價)，或者回傳提示告知使用者稍後重試」。展現你理解互斥鎖這個解法需要搭配完整的逾時和降級設計才能真正可靠。

### 「快取雪崩」和「快取擊穿」聽起來都是「大量請求同時湧向資料庫」，面試時要怎麼清楚地區分這兩者，避免混淆?

**核心答案**：核心區分在於**「觸發的規模和範圍」**——**快取擊穿**針對的是**單一個（或極少數幾個）特別熱門的 key**，因為這個特定的熱門 key 過期失效，導致大量原本查詢「這一筆資料」的請求集中湧向資料庫；**快取雪崩**則是**大量不同的、彼此無關的 key，同時失效**（或者更嚴重的情況——快取系統整體故障，導致**所有** key 都無法從快取取得），影響的範圍遠比快取擊穿廣泛，衝擊到資料庫的，不是針對某一筆特定資料的高並發查詢，而是原本應該被快取分散開來、五花八門的各種不同查詢，全部一起繞過快取、直接打向資料庫。可以用一個比喻來記憶——快取擊穿像是「一條特別繁忙的道路，臨時封閉了，所有原本走這條路的車，都被迫擠到另一條替代道路上」；快取雪崩則像是「整個城市的所有道路，同時封閉所有車輛，不管原本要去哪裡，全部被迫擠上唯一僅存的替代道路」。

**詳細解析**：這題直接回應一個常見的面試困惑——這兩個聽起來相似、都描述「大量請求湧向資料庫」的問題，需要一個清晰的框架來區分，避免在回答時，把兩者的定義和解法混為一談。理解這兩者差異的關鍵，在於問自己「是**哪些** key 受到了影響」這個問題——快取擊穿的場景，是「系統裡有一個(或極少數幾個)特別熱門、被大量請求持續查詢的資料，只是這**一筆特定的**資料，剛好在某個時間點，快取失效了」，這種情況下，資料庫承受的壓力，本質上是「原本應該被快取擋掉的、針對同一份資料的大量重複查詢」，這是一種**集中在單一資料上的、垂直方向的衝擊**；快取雪崩則完全不同，它的場景是「系統裡原本分散儲存著各種不同資料的快取，因為某種原因(大量key在同一時刻集中過期，或整個快取系統故障)，導致**所有這些原本各自獨立、彼此無關的資料**，一次性地全部無法從快取取得」，這種情況下，資料庫承受的壓力，是「原本應該被快取分散處理的、涵蓋各種不同資料的、大範圍的所有查詢，突然全部一起繞過快取」，這是一種**橫跨大量不同資料的、水平方向的衝擊**。理解了這個「垂直（單一熱門資料）vs 水平（大量不同資料的全面失效）」的區分角度之後，也能更清楚地理解為什麼兩者的**解法方向也不同**——快取擊穿的解法(互斥鎖)，核心思路是「既然大家都在搶同一份資料，那就只讓一個請求去真正查詢、重建，其他人等待這個結果就好」，這個解法，依賴的前提是「問題聚焦在單一資料上」，如果換成快取雪崩的情境(大量不同資料同時失效)，用互斥鎖是沒有意義的(因為每一筆不同的資料，本身就需要各自獨立地重建，鎖不住「所有不同資料的重建」這件事)；快取雪崩的解法(過期時間加隨機抖動、提升快取系統高可用性)，核心思路是「從根源上避免大量不同資料集中在同一時刻失效，或者確保快取系統本身不會整體故障」，這兩種解法的設計思路和適用場景，完全對應著兩個問題各自「垂直集中」和「水平全面」這個本質性的規模差異。理解「快取擊穿和快取雪崩的核心區分在於受影響的規模和範圍——擊穿是單一(或極少數)熱門key的垂直集中衝擊，雪崩是大量不同key或整個快取系統的水平全面失效，這個規模差異也決定了兩者解法思路的本質不同(擊穿用鎖聚焦處理單一資料的重建、雪崩用抖動和高可用從根源避免大範圍集中失效)」，展現你能清晰地拆解這兩個容易被混為一談、但本質規模和解法思路都不同的快取問題。

**面試回答方式**：給出核心區分——「快取擊穿是單一(或極少數)特別熱門的key過期，大量請求集中衝向這一筆資料;快取雪崩是大量不同、彼此無關的key同時失效或整個快取系統故障，影響範圍遠比擊穿廣泛」。可以用比喻幫助理解——「擊穿像一條特別繁忙的道路臨時封閉，車輛被迫擠上替代道路;雪崩像整個城市所有道路同時封閉」。點出這個規模差異如何對應到不同的解法思路——「擊穿用互斥鎖聚焦處理單一資料的重建;雪崩用過期時間加隨機抖動、提升快取系統高可用性，從根源避免大範圍集中失效，兩者解法思路的差異正對應著問題規模的本質不同」。展現你能清晰拆解這兩個容易混淆的快取問題。
