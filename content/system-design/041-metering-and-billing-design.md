# 題目

設計一個 SaaS 的用量計量與計費系統：記錄 API 呼叫量、計算費用、產生帳單。

## 核心答案

分成四個階段，而它們的準確性要求遞增：**計量**（記錄原始用量事件）、**評估**（套用定價規則算出金額）、**出帳**（產生週期性帳單）、**收款**。

計量的關鍵是「事件而非計數器」。每一次用量都記錄成一筆帶時間戳、租戶、資源類型、數量、與唯一 ID 的事件——而不是直接對某個計數器加一。理由是事件可以重算、可以審計、可以在定價規則變更後回溯，計數器一旦錯了就永遠不知道錯在哪。

**評估要與計量解耦**。定價規則（階梯、包月額度、超量費率、折扣）**經常變動且需要能追溯**——每張帳單要記錄「當時使用了哪個版本的定價」，**否則客戶質疑時無法解釋**。

**準確性靠三個機制**：**冪等的事件 ID**（去重）、**端到端的計數校驗**（上報數 = 儲存數 = 計費數）、以及**出帳前的異常檢測**（與上期比對，偏差超過閾值就阻擋並人工複核）。

## 詳細解析

「近即時的用量展示」與「準確的出帳」是兩條路徑。客戶希望在儀表板上馬上看到自己用了多少——那個數字可以是近似的（流式聚合，容忍幾分鐘誤差）。而月底出帳必須從原始事件完整重算。在產品上要明確標示前者是「預估值」，否則客戶會拿它與帳單比對並質疑差異——這是一個純粹的產品決定，但它能消除大量的客服成本。

**用量事件的量可能非常大**。每次 API 呼叫一筆事件，對一個大客戶可能是每天數億筆。**處理方式是分層聚合**：閘道側先做本地的秒級或分鐘級預聚合（同一租戶同一資源的呼叫合併成一筆帶計數的事件），**再上報**——這能把事件量降低幾個數量級，而不損失計費精度（因為計費本來就按總量而非逐次）。**但要注意預聚合會丟失明細**，所以爭議調查所需的抽樣明細要另外保留。

**多維度的定價讓評估變複雜**。同一筆用量可能同時受「方案的包含額度」「階梯費率」「承諾折扣」「促銷」影響——而它們的套用順序會改變結果。設計上要把定價表達成一個明確的規則管線而非硬編碼的 if-else，並讓每張帳單附上「計算過程的逐步展開」（用了多少、扣掉多少額度、剩餘按哪一階計算）——可解釋性在計費系統裡不是加分項而是必需品。

時區與週期邊界是常見的錯誤來源。帳單週期以租戶所在時區為準還是 UTC、**月底 31 日的訂閱在二月怎麼算**、**跨時區的用量歸屬哪一天**——這些都必須明確定義並寫進測試，因為它們造成的差異雖小，卻會直接損害客戶對整個系統的信任。

## 面試回答方式

先給四階段（計量、評估、出帳、收款）並指出**準確性要求遞增**。核心主張是**計量要記錄事件而非計數器**——事件可以重算、審計、在定價變更後回溯，計數器錯了就永遠不知道錯在哪。給評估與計量解耦，每張帳單記錄當時使用的定價版本。加分點有四個：近即時展示與準確出帳是兩條路徑，產品上要明確標示前者是預估值，否則客戶會拿它比對帳單；用量事件量極大，用閘道側的分鐘級預聚合降低幾個數量級而不損失計費精度，但要另外保留抽樣明細供爭議調查；定價要表達成規則管線而非 if-else，並附上逐步展開的計算過程——可解釋性在計費系統裡是必需品；以及時區與週期邊界必須明確定義並寫進測試。

## 講稿

我會分成四個階段，計量、評估、出帳、收款，準確性要求是遞增的。

計量的關鍵是記錄事件而不是計數器。每一次用量都記成一筆帶時間戳、租戶、資源類型、數量、唯一編號的事件。理由是事件可以重算、可以審計、可以在定價規則變更之後回溯，而計數器一旦錯了就永遠不知道錯在哪。

評估要跟計量解耦。定價規則經常變動，所以每張帳單要記錄當時用的是哪個版本，否則客戶質疑的時候你沒辦法解釋。

有一個產品層面的細節我覺得很重要。客戶想在儀表板上馬上看到自己用了多少，那個數字可以是近似的，但一定要明確標示成預估值，否則客戶會拿它跟帳單比對然後質疑差異。這是純粹的產品決定，但能消除大量客服成本。

還有可解釋性。帳單要附上計算過程的逐步展開，用了多少、扣掉多少額度、剩下的按哪一階算。在計費系統裡這不是加分項，是必需品。

## 常見追問

### 用量事件丟失了怎麼辦？

**核心答案**：分兩種情況處理，而且要先承認「完全不丟是做不到的」。**少量丟失**——用端到端計數校驗發現，如果偏差在可接受範圍內（例如萬分之一），選擇「按客戶有利的方向處理」即少收，因為多收造成的信任損害遠大於少收的金額損失。**大量丟失**——**必須能從上游重建**：閘道的存取日誌是天然的備份來源，**用它重跑一次計量管線**。

**詳細解析**：「存取日誌作為兜底」是這個設計裡最實用的一環。它本來就會被保存（用於稽核與排錯），而它包含了計量所需的全部資訊——所以它是一條免費的、完全獨立的重建路徑。設計時應該刻意保持這條路徑可用：確保日誌包含租戶識別與資源類型，且保留期不短於一個計費週期。更廣的原則是「計費系統應該有兩條獨立的資料來源」——當它們一致時你有信心，不一致時你知道要查。只有一條路徑的系統，其正確性永遠只是一個無法驗證的假設。

**面試回答方式**：先誠實承認**完全不丟做不到**，再分兩種情況（少量丟失用計數校驗發現並**按客戶有利的方向處理**，因為多收造成的信任損害遠大於少收的金額損失；大量丟失從上游重建）。核心加分點是**存取日誌作為天然的兜底**——它本來就會被保存、包含計量所需的全部資訊，是一條免費且完全獨立的重建路徑，設計時要刻意保持它可用。收在原則：計費系統應該有兩條獨立的資料來源，一致時你有信心，不一致時你知道要查。

### 怎麼支援即時的額度限制？

**核心答案**：用「近似的即時計數 + 準確的事後結算」。額度檢查放在**閘道的 Redis 計數器**上——**它快但可能有幾秒的誤差**；準確的用量由事件管線另外計算。兩者的差異在超額的邊界上會產生「多放行了一點」，**而正確的處理是接受它**：寧可讓客戶多用一點點，也不要因為等待準確計數而增加每次請求的延遲。

**詳細解析**：「額度用完後怎麼辦」是一個產品決定，而它應該可設定：**硬限制**（直接拒絕，適合免費方案）、**軟限制**（降級或限速，適合付費方案）、**超量計費**（繼續服務但按超量費率收費，適合企業客戶）。最糟的設計是「沒有通知就直接切斷」——客戶的生產系統會突然掛掉，而那會造成遠比欠費更嚴重的關係損害。所以額度接近時的預警（80%、90%、100%）與寬限期，是計費系統的必要功能而非附加功能。 技術上，預警的觸發應該基於「即時計數」而非「出帳時的準確值」——因為預警的價值全在於及時，晚了就沒有意義。

**面試回答方式**：給架構——閘道的 Redis 計數器做近似即時限制，事件管線做準確結算，並主張**接受邊界上的少量多放行**：寧可讓客戶多用一點，也不要為了準確計數而增加每次請求的延遲。加分點是把「額度用完怎麼辦」講成可設定的產品決定（硬限制、軟限制、超量計費），並指出最糟的設計是沒有通知就直接切斷——客戶的生產系統突然掛掉造成的關係損害遠比欠費嚴重。收在預警必須基於即時計數而非出帳值，因為預警的價值全在於及時。

### 定價規則變更怎麼上線？

**核心答案**：新規則只對「生效日之後的用量」適用，絕不回溯。實作上定價規則要有版本與生效時間區間，評估時按用量事件的時間戳選擇對應版本——這讓「跨越生效日的計費週期」能自動地分段計算。**上線前必須做「影子計算」**：用新規則對上個週期的真實用量重算一次，比對差異，確認變化符合預期才正式啟用。

**詳細解析**：「影子計算」是計費系統最重要的安全機制。定價規則的改動看起來很小，實際影響卻可能是某個客戶的帳單翻倍——而那在出帳後才發現是無法挽回的。用真實資料重算能在幾分鐘內給出「哪些客戶的帳單變化超過 X%」的清單，讓決策建立在事實而非推演上。同樣的機制也適用於程式碼變更：任何觸及評估邏輯的改動都應該先跑一次影子計算並比對，**把它做成 CI 的一部分**。這與金絲雀發布是同一個思路，只是這裡比對的不是錯誤率而是金額——而在計費系統裡，金額才是那個真正重要的指標。

**面試回答方式**：給核心規則——新規則只對生效日之後的用量適用、絕不回溯，並給實作（定價版本帶生效時間區間，按事件時間戳選版本，跨生效日的週期自動分段）。核心加分點是**影子計算**：用新規則對上個週期的真實用量重算並比對差異，因為定價的小改動可能讓某個客戶的帳單翻倍，而出帳後才發現無法挽回。收在推廣：任何觸及評估邏輯的程式碼改動都該跑影子計算並做成 CI 的一部分，與金絲雀同一個思路，只是比對的是金額而非錯誤率。
