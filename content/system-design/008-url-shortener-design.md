# 題目

設計一個像 bit.ly 這樣的短網址服務。核心需求：使用者輸入一個長網址，系統回傳一個短網址；使用者存取這個短網址時，系統將其重新導向到原本的長網址。請描述你的整體設計。

## 核心答案

**需求釐清與容量估算（Back-of-the-Envelope Estimation）**：假設每天有 1 億次短網址建立請求、讀取（跳轉）流量是寫入的 100 倍（讀多寫少是這類服務的典型特徵），短網址需要在合理時間內（幾十毫秒等級）完成跳轉。**核心設計**——**（1）短網址生成**——把長網址，對應到一個簡短、唯一的識別碼（如 7 位英數混合字元，可以表示 62^7 約 3 兆種組合），常見做法是用**分散式 ID 生成器**（如雪花演算法或號段模式，見 [[../database/018-distributed-id.md]]），生成一個全域唯一的數字 ID，再把這個數字，轉換成 62 進位（0-9, a-z, A-Z）的字串表示，作為短網址的識別碼；**（2）資料儲存**——用一個簡單的鍵值對映射表（短碼 → 原始長網址），因為讀寫都是依照這個短碼做精確查找，沒有複雜的關聯查詢需求，適合用 NoSQL 或簡單的關聯式資料表儲存，並依短碼建立索引；**（3）讀取路徑的高效能設計**——因為讀取（跳轉）遠多於寫入，在應用層和資料庫之間加入**快取層**（如 Redis），讓絕大多數的跳轉請求，能直接從快取取得原始網址，不需要每次都查詢資料庫；**（4）重新導向的 HTTP 狀態碼選擇**——使用 `302 Found`（暫時性重新導向）而非 `301 Moved Permanently`（永久重新導向），因為 301 會被瀏覽器**快取**，之後同一個短網址的請求，瀏覽器可能不會再次詢問伺服器，直接使用快取的跳轉結果，這會讓伺服器失去追蹤點擊統計的機會，也讓短網址服務失去了進行 A/B 測試或動態更新對應關係的彈性。

## 詳細解析

**短網址生成的具體方案比較**：常見的短碼生成方式有幾種——**（1）雜湊法**——把原始長網址，做 MD5 或其他雜湊運算，取雜湊結果的前幾位作為短碼，優點是實作簡單、不需要維護額外的全域計數器；缺點是**存在雜湊碰撞的風險**（兩個不同的長網址，可能雜湊出相同的短碼），需要額外的碰撞檢測和處理邏輯（例如碰撞時，對原始網址加上一個隨機後綴，重新計算雜湊值)，增加了實作複雜度。**（2）分散式自增 ID + 進位轉換**——用之前討論過的分散式 ID 生成方案（見 [[../database/018-distributed-id.md]]），生成一個嚴格遞增、全域唯一的數字，再把這個數字，轉換成 62 進位的字串表示（例如數字 1 轉換成 "1"、數字 62 轉換成 "10",以此類推），這種方式**天然沒有碰撞問題**（因為底層的數字本身就是唯一的），且短碼的長度，可以隨著數字的增長而自然變長（不需要一開始就規劃好固定長度），是業界更常見的做法。無論選擇哪種方案，都需要考量「短碼裡，要不要排除掉容易混淆的字元」（例如數字 0 和字母 O、數字 1 和字母 l 看起來很像，容易讓使用者手動輸入時出錯，很多實務系統會刻意排除掉這幾個容易混淆的字元)。

**讀取路徑的快取設計與快取穿透（Cache Penetration）防護**：因為短網址服務典型的特徵是「讀取遠多於寫入」，快取層的效益特別顯著——用 Cache-Aside 模式（見 [[006-caching-strategies.md]]），跳轉請求先查快取，快取沒有再查資料庫並回填。因為短網址一旦建立，原始網址通常不會再改變（除非使用者自己更新），這種「一次寫入、多次讀取、內容穩定不變」的特性，特別適合快取，可以設定相對長的過期時間，甚至考慮讓**熱門的短網址**永遠留在快取裡不過期（依照存取頻率，動態決定快取策略）。同時，也需要考慮「使用者存取一個根本不存在（或已經被刪除）的短碼」這種快取穿透場景（見 [[007-cache-invalidation.md]]），搭配空值快取或布隆過濾器（Bloom Filter），避免大量無效的短碼查詢，直接衝擊資料庫。

**為什麼用 302 而非 301 重新導向**：這是短網址服務設計裡一個經常被忽略、但很重要的細節——`301 Moved Permanently` 這個狀態碼，向瀏覽器明確地宣告「這個網址的內容，已經永久地搬到了新位置」，瀏覽器（以及很多中間的快取代理），收到這個回應後，通常會**主動地把這個重新導向的結果快取起來**，之後如果使用者（或同一個瀏覽器），再次點擊同一個短網址，瀏覽器可能**直接使用自己快取的跳轉結果**，根本不會再把請求送到短網址服務的伺服器，這帶來兩個問題——**（1）短網址服務，失去了統計「這個短網址，總共被點擊了幾次」的機會**（因為瀏覽器繞過了伺服器，自己處理跳轉）；**（2）如果服務商之後需要調整這個短網址對應的目標網址**（例如原本的目標網址失效了，需要改指向一個新的網址），因為瀏覽器端可能還快取著舊的 301 跳轉結果，使用者可能會持續被導向舊的（已經不對的）目標，即使伺服器端的對應關係已經更新。改用 `302 Found`（暫時性重新導向），明確地告知瀏覽器「這只是暫時的跳轉，每一次都應該重新向伺服器詢問最新的跳轉目標」，確保短網址服務，能夠持續、可靠地追蹤每一次點擊，並保有隨時調整跳轉目標的彈性。

**分散式 ID 生成器的選擇考量**：短網址服務因為需要生成大量、高頻率的唯一識別碼，且對「ID 的絕對遞增順序」通常沒有嚴格要求（只要求全域唯一），適合用之前討論過的**雪花演算法**（見 [[../database/018-distributed-id.md]]）或**號段模式**——如果選擇雪花演算法，能夠達到「不依賴任何中心化協調、完全本地生成」的高效能和高可用性；如果考慮到「短碼希望盡量簡短（不希望因為雪花演算法裡固定佔用大量位元的時間戳，導致轉換出來的短碼字串過長）」，也可以考慮號段模式（多台伺服器，各自定期向一個中心化的號段分配服務，批次領取一段連續的數字區間，在本地依序消耗使用），能讓生成的數字，相對更緊湊（不需要像雪花演算法那樣，把大量位元花在編碼時間戳上），轉換出來的短碼，也可能因此更簡短。

## 面試回答方式

先給出需求釐清和容量估算的簡短假設(每天多少請求、讀寫比例懸殊)。講清楚核心架構——短網址生成(用分散式ID生成器搭配62進位轉換，而非單純雜湊法，避免碰撞問題)、資料儲存(簡單的鍵值映射，依短碼建索引)、讀取路徑加快取層(因為讀多寫少特別適合快取)。一定要主動提到「用302而非301重新導向」這個容易被忽略但很重要的細節，並解釋清楚原因(301會被瀏覽器快取導致失去點擊統計和跳轉目標調整的彈性)，這是這道系統設計題最能展現細節思考深度的地方。可以延伸提到「快取穿透防護」和「分散式ID生成器的具體選型考量」，展現你能把之前學過的多個相關主題(分散式ID、快取策略、快取穿透)融會貫通地應用到這個具體的系統設計案例裡。

## 常見追問

### 如果需要支援「自訂短碼」(使用者自己指定想要的短網址別名，而不是系統隨機生成)，這個需求會對整體設計帶來什麼額外的挑戰?

**核心答案**：核心挑戰是**需要處理「短碼唯一性檢查」和「併發衝突」的問題**——當使用者提出一個自訂短碼的請求時，系統需要先確認「這個短碼，目前還沒有被其他人使用」，才能建立成功；如果單純地「先查詢是否存在、確認不存在後再插入」，在高並發情境下（兩個使用者，幾乎同時嘗試申請同一個熱門的自訂短碼），會遇到之前討論過的**經典競態條件**（見 [[../backend-engineering/003-idempotency-design.md]] 討論過的類似問題）——兩個請求，都可能在對方完成插入之前，查詢到「還沒被使用」，導致兩者都誤以為自己能成功建立，最終造成資料衝突或其中一個請求的資料被意外覆蓋。正確的解法，是**依賴資料庫的唯一約束（Unique Constraint）**——在短碼欄位建立唯一索引，讓「插入」這個動作本身，具備原子性的唯一性保證，如果兩個請求同時嘗試插入相同的自訂短碼，資料庫會確保只有一個插入成功，另一個會因為違反唯一約束而失敗，應用程式捕捉到這個特定的資料庫錯誤，明確地告知該使用者「這個短碼已經被使用，請換一個」。

**詳細解析**：這題把「自訂短碼」這個看似只是「多一個功能選項」的需求，連結回之前資料庫和後端工程章節，已經深入討論過的「唯一性保證需要依賴資料庫原子性約束，而非應用層自己拼湊的查詢-判斷邏輯」這個核心原則，考察是否能舉一反三地識別出，這其實是同一類問題的又一次具體展現。如果系統隨機生成短碼（如前面核心答案裡描述的方式），因為短碼是由系統自己，依照一個保證唯一的底層數字（如雪花演算法生成的 ID）轉換而來，天然不會有「兩個不同的請求，恰好生成了相同的短碼」這種衝突問題（除非底層的 ID 生成本身出錯）；但一旦允許使用者**自訂**短碼（例如使用者想要申請 "my-brand" 這個好記的別名），系統就失去了「短碼一定唯一」這個天然保證，而需要**主動地驗證和保護**這個唯一性，因為使用者提出的自訂短碼，完全可能和另一個使用者(幾乎同時)提出的自訂短碼要求撞在一起(例如兩個使用者，都恰好想要申請同一個熱門的品牌名稱作為短碼)。這種場景下的正確處理，和之前反覆討論過的「冪等鍵」、「TCC空回滾」等場景背後的核心邏輯完全一致——**不能依賴「先用一個獨立的查詢確認資源是否存在、再用另一個獨立的操作去建立」這種分開的兩步驟邏輯**（因為這兩個步驟之間，存在著讓另一個並發請求插隊的競態視窗），而必須**依賴資料庫本身，對「插入操作」提供的原子性唯一約束保證**——在資料庫層面，對「短碼」這個欄位，建立唯一索引，讓資料庫本身，在真正執行插入這個動作的當下（而不是在這之前的某個獨立查詢步驟），就能保證「這個值，在整個資料表裡，絕對只會有一筆記錄」，如果程式邏輯嘗試插入一個已經存在的短碼，資料庫會直接拒絕這次插入（拋出違反唯一約束的錯誤），應用程式只需要正確地捕捉並處理這個特定的資料庫錯誤，轉換成一個對使用者友善的錯誤訊息（如「這個短碼已經被使用，請嘗試其他名稱」）即可，不需要（也不應該）自己在應用層，土法煉鋼地嘗試用「先查詢、再判斷、再插入」這種天真、卻存在競態漏洞的方式，去實現唯一性保證。理解「自訂短碼這個功能，引入了『唯一性需要被主動保護』這個新挑戰，而正確的保護機制，和之前反覆討論過的冪等鍵、TCC空回滾等場景的核心解法相通——都要依賴資料庫本身對插入操作的原子性唯一約束，而不能靠應用層自己拼湊的查詢-判斷邏輯」，展現你能把之前學過的、貫穿多個不同具體場景的核心設計原則，正確地識別並應用到這個新的系統設計案例裡。

**面試回答方式**：先指出核心挑戰——「自訂短碼引入了唯一性需要被主動保護的新問題，不像系統隨機生成短碼那樣天然唯一」。給出正確解法——「不能靠先查詢是否存在、再插入這種分開步驟的邏輯(有競態漏洞)，必須依賴資料庫在短碼欄位建立唯一約束，讓插入操作本身具備原子性的唯一性保證，衝突時資料庫會直接拒絕插入，應用程式捕捉這個特定錯誤，轉換成對使用者友善的提示」。點出這其實呼應了之前討論過的通用模式——「這和冪等鍵設計、TCC空回滾要解決的核心問題本質相通，都要靠資料庫的原子性約束，而非應用層自己拼湊的查詢-判斷邏輯」。展現你能把之前學過的通用設計原則，正確識別並應用到這個新場景。

### 如果短網址的資料量，持續累積成長到單一資料庫已經放不下(比如累積了幾十億筆記錄)，要怎麼考慮分庫分表?應該用哪個欄位作為分片鍵?

**核心答案**：對於短網址服務，**最合適的分片鍵是「短碼本身」**——因為短網址服務絕大多數的查詢，都是「依照短碼，查詢對應的原始長網址」這種精確匹配查詢（讀取跳轉的核心操作），如果用短碼（或短碼的雜湊值）作為分片鍵，這個系統裡最高頻的查詢操作，天然就「帶著」分片鍵，中介軟體或應用程式，可以直接根據這個短碼，計算出應該去哪個分片查詢，不需要「廣播查詢到所有分片」（見 [[../database/017-sharding.md]] 討論過的分片鍵選擇原則）。至於**「建立短網址」這個寫入操作**，因為需要先確認生成的短碼，在全域範圍內是唯一的(尤其如果採用前面提到的分散式ID生成方案，理論上底層的ID已經保證全域唯一，轉換成短碼後，天然也是唯一的，不太需要額外的跨分片唯一性檢查)，這部分的設計相對單純。

**詳細解析**：這題把之前資料庫章節深入討論過的「分片鍵選擇要對應到最高頻的查詢模式」這個核心原則，具體應用到短網址服務這個系統設計案例上，考察是否能正確地分析出這個系統「最主要的存取模式是什麼」，並據此推導出合適的分片鍵選擇。理解這道題的關鍵，在於先識別出短網址服務的核心存取特徵——絕大多數的請求，都是「使用者點擊一個短網址，系統依照這個短碼，查詢到對應的原始網址並跳轉」，這個操作天生就是「以短碼為查詢條件的精確匹配查詢」，這意味著，如果選擇「短碼」（或者對短碼做雜湊運算後的結果，讓分佈更均勻）作為分片鍵，系統裡絕大多數的查詢請求，都會**天然攜帶**這個分片鍵資訊（因為使用者存取短網址時，本來就必須提供這個短碼），應用程式或資料庫中介軟體，可以直接根據這個短碼，計算出對應的分片位置，精確地把查詢路由到正確的那一個分片，完全不需要像「分片鍵選錯了」的情況那樣，被迫把查詢廣播到所有分片、再彙總結果（那樣做的效能損失和複雜度，遠高於直接命中單一分片）。反過來想，如果選擇了一個和「查詢短碼」這個核心操作無關的分片鍵（例如錯誤地選擇「建立這筆短網址的使用者ID」作為分片鍵），會導致「查詢短網址跳轉」這個系統裡最高頻的操作，反而無法直接推算出應該去哪個分片查詢（因為查詢時，只知道短碼，不知道是誰建立的這筆記錄），必須廣播查詢到所有分片，這是一個明顯不合適的分片鍵選擇。至於「建立短網址」這個相對低頻的寫入操作，因為短碼的生成邏輯(如前面討論的分散式ID搭配進位轉換)，天然保證了全域唯一性，寫入時只需要根據這個(已經確定唯一的)短碼，計算出它應該落在哪個分片，直接寫入那個分片即可，不太需要額外的「跨分片檢查唯一性」這種複雜的協調邏輯（這和前面追問討論過的「自訂短碼」需要額外唯一性保護的情境不同——如果是系統自動生成、底層依賴分散式ID保證唯一性的短碼，天然就不會有跨分片的唯一性衝突問題）。理解「短網址服務最合適的分片鍵是短碼本身，因為這對應到系統裡絕大多數查詢(依短碼查詢跳轉目標)天然攜帶的資訊，能讓查詢直接命中單一分片，而不需要跨分片廣播，這正是分片鍵選擇要優先考慮『最高頻查詢模式是否天然攜帶這個欄位』這個一般性原則，在短網址這個具體案例的正確應用」，展現你能把之前在資料庫章節學到的分片鍵選擇原則，正確地遷移應用到這個新的系統設計案例，並準確地識別出短網址服務的核心存取模式。

**面試回答方式**：直接給出答案——「最合適的分片鍵是短碼本身」。給出理由——「短網址服務絕大多數的查詢，都是依照短碼查詢跳轉目標這種精確匹配查詢，如果用短碼做分片鍵，這個系統裡最高頻的操作天然攜帶分片鍵資訊，能直接命中單一分片，不需要廣播查詢到所有分片」。可以補充「建立短網址這個寫入操作，因為短碼生成邏輯本身已經保證全域唯一(如透過分散式ID)，寫入時不太需要額外的跨分片唯一性檢查」。展現你能把資料庫章節學到的「分片鍵要對應最高頻查詢模式」這個原則，正確應用到這個具體的系統設計案例。

### 短網址服務，如果需要提供「點擊次數統計」這個功能(記錄每個短網址總共被點擊了幾次)，要怎麼設計才不會拖慢核心的跳轉延遲?

**核心答案**：核心原則是**把「記錄點擊次數」這個統計性質的操作，和「執行實際的跳轉」這個核心業務邏輯完全解耦，讓統計記錄以非同步的方式進行，不阻塞使用者實際的跳轉體驗**——具體做法是，當使用者存取短網址、伺服器準備回傳跳轉回應時,**先立即回傳跳轉結果給使用者**（不需要等待點擊記錄真的寫入完成），與此同時把「這次點擊事件」的資訊（如短碼、時間戳、可能的來源資訊），**丟進一個訊息佇列（Message Queue）**（見 [[../backend-engineering/011-message-queue-fundamentals.md]]），由獨立的背景消費者服務，非同步地消費這些點擊事件，批次地累加更新統計數字（例如，可以先在記憶體或 Redis 裡累積計數，定期批次地同步寫回持久化的資料庫，減少對資料庫的頻繁寫入次數）。這樣一來使用者實際感受到的跳轉延遲，完全不會被「記錄統計」這個相對次要的功能拖慢。

**詳細解析**：這題把之前後端工程章節深入討論過的「非同步處理、把耗時或非核心的操作，透過訊息佇列解耦，不阻塞主流程」這個核心設計思路（見 [[../backend-engineering/011-message-queue-fundamentals.md]]），具體應用到短網址服務的點擊統計這個功能需求上，考察是否理解「核心業務邏輯」和「附加的統計/分析功能」之間，應該有明確的優先順序和解耦設計。短網址服務最核心的價值，是「使用者點擊短網址，能夠盡快地被導向到正確的目標網址」，這個跳轉的延遲，直接影響使用者體驗（沒有人喜歡點擊一個連結，卻要等待好幾秒才被導向），因此，任何額外附加的功能（如點擊次數統計），都不應該以犧牲這個核心跳轉延遲為代價。如果天真地把「記錄點擊次數」這個動作，設計成「使用者發起跳轉請求，伺服器**同步地**先把統計數字更新到資料庫，更新成功後才回傳跳轉結果給使用者」，這意味著，每一次跳轉，使用者實際上要等待「查詢跳轉目標」和「更新統計數字」這兩個操作，都完成之後，才能真正被導向，這不必要地拖長了使用者感受到的延遲，而且「更新統計數字」這個操作，如果統計資料庫，恰好因為某種原因暫時緩慢或不可用，甚至可能導致整個跳轉功能，連帶地受到拖累（一個原本應該只是「錦上添花」的附加功能，卻可能拖垮最核心的業務功能，這是一種本末倒置的設計）。正確的做法，是遵循「核心路徑優先、附加功能非同步化」這個原則——伺服器，在確認要跳轉到哪個目標網址之後，**立即**把這個跳轉結果，回傳給使用者(不需要等待任何額外的統計動作完成)，與此同時（或緊接著），把「這次點擊」這個事件，發布到一個訊息佇列裡，交給獨立的、專門處理統計分析的背景服務，去非同步地消費和處理，即使這個統計服務，因為某種原因暫時處理得比較慢、甚至短暫故障，也**完全不會影響**使用者體驗到的核心跳轉功能（跳轉本身，不依賴這個統計服務是否正常運作）。此外，統計數字的更新，通常也不需要「每一次點擊，都精確且即時地更新到持久化的資料庫」，可以採用**批次聚合**的方式（例如，先在 Redis 裡，用一個簡單的計數器，快速地累加每一次點擊，定期(如每分鐘或每小時)才把 Redis 裡累積的計數，批次地同步寫入到持久化的資料庫，大幅減少對資料庫的寫入頻率），進一步降低整體系統的負擔，這種設計也符合「統計性質的資料，通常能夠容忍一定程度的延遲和最終一致性（Eventual Consistency），不需要像核心業務資料那樣要求絕對即時和精確」這個一般性的認識(這其實也呼應了前面 CQRS 章節討論過的、把讀寫模型或不同性質的資料處理，拆分開來分別優化的思路，見 [[../backend-engineering/023-event-driven-cqrs.md]])。理解「點擊統計這類附加的統計功能，應該和核心的跳轉業務邏輯完全解耦，透過訊息佇列非同步處理、搭配批次聚合的方式更新，確保核心跳轉延遲不會被這類非關鍵的附加功能拖累，這是『核心路徑優先、非核心功能非同步化』這個一般性設計原則，在短網址服務點擊統計這個具體場景的應用」，展現你能把之前學過的訊息佇列非同步處理、以及CQRS讀寫分離的思路，正確地整合應用到這個新的系統設計案例裡。

**面試回答方式**：給出核心設計原則——「記錄點擊次數這個統計功能，必須和核心跳轉邏輯完全解耦，不能拖慢使用者實際感受到的跳轉延遲」。給出具體做法——「伺服器確認跳轉目標後立即回傳結果給使用者，不等待任何統計動作;把點擊事件丟進訊息佇列，由獨立的背景服務非同步消費並批次聚合更新統計數字(如先在Redis累加，定期批次同步寫入持久化資料庫)」。可以補充「這呼應了核心路徑優先、非核心功能非同步化的一般性設計原則，以及統計性質的資料通常能容忍延遲和最終一致性，不需要像核心業務資料那樣要求絕對即時精確」。展現你能把訊息佇列非同步處理的思路，正確整合應用到這個具體的系統設計場景。
