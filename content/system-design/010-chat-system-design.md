# 題目

設計一個支援一對一和群組聊天的即時通訊系統（類似 WhatsApp 或 Slack 的核心功能）。需要支援訊息即時送達、離線訊息、以及訊息的已讀狀態。請描述你的整體設計。

## 核心答案

**核心挑戰**——傳統的 HTTP 請求-回應模式（客戶端主動發起請求，伺服器被動回應），無法讓伺服器**主動地**把新訊息推送給客戶端，需要一種能維持**持久連線**的技術。**核心架構**：**（1）連線層——WebSocket**——客戶端和伺服器之間，建立一條持久的 WebSocket 連線（而非每次都重新發起 HTTP 請求），伺服器能透過這條連線，隨時主動推送新訊息給客戶端；**（2）連線管理——連線閘道服務**——因為單一台伺服器，能維持的並發 WebSocket 連線數有限，需要一群專門的「連線閘道」伺服器，各自維護一部分使用者的長連線，並記錄「哪個使用者，目前的連線，是由哪一台連線閘道伺服器維護的」（這份對應關係，通常存在一個共享的儲存如 Redis）；**（3）訊息路由**——當使用者 A 發送訊息給使用者 B，訊息先送達 A 目前連接的閘道伺服器，這台伺服器，查詢「B 目前連接在哪台閘道伺服器上」，把訊息轉發給 B 所在的那台閘道伺服器，再由它透過已建立的 WebSocket 連線，推送給 B；**（4）離線訊息**——如果 B 目前不在線（沒有維持任何 WebSocket 連線），訊息會被持久化儲存到資料庫，等 B 下次上線時，主動拉取這段期間累積的離線訊息；**（5）已讀狀態**——B 讀取訊息後，發送一個「已讀」回執給伺服器，伺服器再轉發給 A，更新 A 這一端看到的已讀狀態。

## 詳細解析

**為什麼需要 WebSocket 而非傳統輪詢**：傳統 HTTP 是「客戶端主動發起請求、伺服器被動回應」的單向模式，如果要模擬「即時通知」的效果，傳統做法是讓客戶端**定期輪詢**（Polling）——每隔幾秒鐘，就主動問伺服器「有沒有新訊息」，這種做法的問題是——**輪詢的頻率如果設得太低，訊息送達的即時性差**（使用者要等到下一次輪詢週期才會看到新訊息)；**如果設得太高，會產生大量不必要的請求**（絕大多數的輪詢，可能都得到「沒有新訊息」的空回應，浪費頻寬和伺服器資源）。WebSocket 協定，讓客戶端和伺服器，在一開始的 HTTP 交握之後，**升級**成一條可以雙向、持續互相傳送訊息的連線（見 [[../backend-engineering/022-grpc-vs-rest.md]] 討論過的雙向串流概念，WebSocket 是實現類似效果的另一種常見技術），伺服器，可以在任何時刻，主動地透過這條已建立的連線，把新訊息**推送**給客戶端，不需要客戶端反覆地主動詢問，兼顧了即時性和效率。

**連線閘道與「使用者在哪」的路由問題**：因為 WebSocket 是一條持久連線，一旦使用者的裝置，和某一台連線閘道伺服器建立了連線，這條連線，通常會**持續維持**在那台特定的伺服器上（不像傳統無狀態的 HTTP 請求，每次都可能被負載平衡（Load Balancing）器路由到不同的伺服器），這帶來了一個特殊的路由挑戰——當使用者 A 要發訊息給使用者 B，系統需要知道「B 目前的 WebSocket 連線，究竟是維持在叢集裡的哪一台連線閘道伺服器上」，才能把訊息正確地轉發過去。常見的解法是，維護一個**共享的「使用者 → 連線所在伺服器」對應表**（通常存在 Redis 這類低延遲的共享儲存裡）——每當使用者成功建立一條 WebSocket 連線，這台連線閘道伺服器，就在這個共享表裡，更新「這個使用者目前連接在我這裡」的記錄；當需要轉發訊息給某個使用者時，先查詢這個共享表，得知目標使用者當下所在的閘道伺服器，再透過內部的服務間通訊（例如透過訊息佇列（Message Queue），或直接的內部 API 呼叫），把訊息轉交給那台正確的閘道伺服器，由它負責透過已建立的連線，推送給使用者。

**離線訊息的處理與訊息持久化**：如果查詢共享表後，發現目標使用者**目前並沒有任何連線**（離線狀態），系統需要把這則訊息，**持久化儲存**到資料庫裡（而不是嘗試立即推送、卻註定失敗），等這個使用者之後重新上線、建立新的 WebSocket 連線時，客戶端會主動向伺服器，查詢「我離線期間，累積了哪些還沒看過的訊息」，伺服器從資料庫，把這些累積的離線訊息，一次性地回傳給客戶端。這個設計也意味著，即使是「線上直接推送」的訊息，同樣應該**先確實地持久化儲存到資料庫**（不能只依賴「訊息已經透過 WebSocket 推送出去了」就認為任務完成），確保「即使推送當下，接收方的連線，恰好因為某種原因短暫中斷（例如網路瞬斷），這則訊息，也不會因此遺失」，這種「持久化優先、推送是錦上添花」的設計思路，能提供更可靠的訊息送達保證。

**已讀狀態的設計與效能考量**：「已讀」狀態的追蹤，在一對一聊天相對單純（每則訊息，記錄「接收方是否已讀」這個布林值即可），但在**群組聊天**場景下，會變得複雜許多——一個群組如果有 100 個成員，一則訊息，理論上需要追蹤「這 100 個成員，各自是否已讀」，如果每個成員的已讀狀態，都需要即時、精確地同步給群組裡的所有其他成員（例如常見的「已讀 15/100」這種顯示方式），這需要相當的設計考量——常見的簡化做法是，不追蹤每一則訊息、每一個成員的精確已讀狀態，而是**只記錄「這個使用者，已經讀到群組裡的哪一則訊息（例如某個訊息的序號或時間戳）為止」**，之後只要比較「這則訊息的序號」和「使用者已讀到的序號」，就能推算出「這則訊息，對這個使用者而言，是否已讀」，不需要為「每一則訊息 × 每一個成員」這種笛卡爾積規模的組合，都各自儲存一筆明確的已讀記錄，大幅簡化了儲存和更新的複雜度。

## 面試回答方式

先指出核心挑戰——「傳統HTTP請求回應模式無法讓伺服器主動推送新訊息，需要能維持持久連線的技術」。依序講出架構的五個關鍵環節——WebSocket連線層、連線閘道服務(管理大量並發長連線)、訊息路由(透過共享的使用者-連線對應表，查詢目標使用者目前連在哪台閘道伺服器)、離線訊息(持久化儲存，上線後主動拉取)、已讀狀態。一定要講清楚「連線閘道和訊息路由」這個最核心、最能展現系統設計深度的環節——為什麼需要一個共享的對應表、訊息怎麼跨伺服器轉發。可以延伸提到「即使是線上推送的訊息，也應該先持久化儲存，而非只依賴推送成功」這個可靠性設計原則，以及「群組已讀狀態用已讀到哪個序號取代逐訊息逐成員記錄」這個簡化技巧，展現你對即時通訊系統的核心技術挑戰和常見優化手法有紮實的理解。

## 常見追問

### 如果使用者 A 的裝置，同時登入了手機和電腦兩個不同的用戶端(多裝置同時在線)，訊息路由要怎麼處理才能讓兩個裝置都收到新訊息?

**核心答案**：「使用者 → 連線所在伺服器」這個對應表，需要從「一對一」的映射，改為**「一對多」的映射**——同一個使用者 ID，可能對應著**多筆**連線記錄（例如「使用者A的手機，連接在閘道伺服器1」和「使用者A的電腦，連接在閘道伺服器3」這兩筆記錄同時存在）。當需要推送一則訊息給使用者A時，系統查詢這個對應表，取得**所有**屬於這個使用者的連線記錄（可能是多筆），並**逐一地、分別向每一筆記錄對應的閘道伺服器**發起轉發請求，確保這則訊息，能透過使用者A目前所有在線的裝置連線，同時推送出去，而不是只推送給其中一個裝置。

**詳細解析**：這題延伸到多裝置同時在線這個真實聊天應用普遍需要支援的場景，考察是否理解「原本假設的一對一路由關係，在真實需求下需要被擴展成一對多」這個設計調整，以及背後需要考慮的細節。如果訊息路由的設計，一開始就天真地假設「每個使用者ID，同一時間只會對應一條連線」，一旦這個假設不成立（使用者確實可能同時用手機和電腦登入同一個帳號），會導致「訊息只能被推送給其中一個裝置（例如只推送給最後一個建立連線的裝置，因為一對一的對應表，可能被後來的連線覆蓋了先前的記錄）」，這對使用者體驗是不可接受的（使用者理應期待，不管用哪個裝置，都能即時看到新訊息）。正確的設計，需要把這個對應關係，從「使用者ID對應到單一一筆連線記錄」，調整為「使用者ID對應到一個連線記錄的集合（可能包含多筆）」，具體實作上，可以用類似 Redis 的 Set 或 Hash 這類資料結構（見 [[../redis/001-data-types.md]] 討論過的資料類型），把「這個使用者目前的所有連線資訊（分別對應到哪些閘道伺服器）」，儲存成一個集合，每當這個使用者的某個裝置，新建立一條連線，就把這筆新的連線資訊，加入這個集合（而不是覆蓋掉既有的記錄）；每當某個裝置，主動登出或連線意外中斷，就把對應的那一筆記錄，從集合裡移除。當需要推送訊息時，系統查詢這個使用者對應的整個連線集合，取得目前所有活躍的連線記錄（可能分佈在不同的閘道伺服器上），對集合裡的**每一筆**連線記錄，分別發起轉發，確保訊息能透過所有目前在線的裝置連線，同步推送出去。這個調整看似只是把「一對一」改成「一對多」這麼簡單，但也連帶引入了一些需要額外考慮的細節——例如「當某個裝置，離線超過一段合理時間後，系統要怎麼確保這筆過時的連線記錄，不會一直殘留在集合裡（因為如果沒有正確清理，可能導致系統誤以為某個裝置依然在線，嘗試向一個實際上已經斷開連線的通道推送訊息，造成無謂的失敗）」，這通常需要搭配類似心跳偵測的機制（連線閘道伺服器，定期確認每條連線是否依然存活，一旦偵測到連線已經失效，就主動地從共享的對應表裡，清除這筆已經過時的記錄）。理解「支援多裝置同時在線，需要把訊息路由的『使用者-連線』對應關係，從一對一擴展成一對多，推送訊息時需要向這個使用者所有目前活躍的連線，逐一轉發，同時需要搭配心跳偵測等機制，確保過時失效的連線記錄能被及時清理，避免系統誤判某個裝置依然在線」，展現你能識別出真實需求(多裝置支援)如何要求對原本簡化的架構假設做出相應的擴展調整。

**面試回答方式**：給出核心調整——「使用者-連線的對應表，需要從一對一擴展成一對多，同一個使用者ID可能同時對應多筆分佈在不同閘道伺服器的連線記錄」。給出推送邏輯——「查詢這個使用者對應的整個連線集合，取得所有目前活躍的連線，逐一分別向每筆連線發起轉發，確保透過所有在線裝置同步推送」。補充需要額外考慮的細節——「需要搭配心跳偵測機制，及時清理已經失效但還殘留在集合裡的過時連線記錄，避免系統誤判某個裝置依然在線而嘗試向一個已斷開的通道推送」。展現你能識別出多裝置支援這個真實需求，如何要求對原本假設一對一路由的架構做出相應的擴展調整。

### 訊息送達要怎麼保證「使用者看到的訊息順序，和實際發送的順序一致」，尤其在群組聊天，多個成員可能幾乎同時發送訊息的情況下?

**核心答案**：保證順序的核心做法是——**為每一則訊息，分配一個嚴格遞增的序號（Sequence Number）**，這個序號的分配，通常依照「群組」（或一對一對話）為單位（而不是全域唯一），確保「同一個對話裡的訊息，其序號嚴格反映了它們被伺服器正式接收和處理的先後順序」，客戶端在顯示訊息時，依照這個序號排序顯示，而不是依賴「訊息到達客戶端裝置的時間先後」（因為網路傳輸的延遲不均，可能導致「後發送的訊息，反而先到達某個客戶端」這種順序錯亂的情況）。序號的生成，通常依賴一個**針對每個對話，單獨維護的計數器**（可以是資料庫的自增主鍵，或者透過 Redis 的原子性遞增操作實現），確保同一個對話裡的訊息序號，不會重複、且嚴格遞增。

**詳細解析**：這題考察對「網路傳輸延遲不均，可能導致訊息到達順序和實際發送順序不一致」這個分散式系統固有問題的理解，以及業界標準的解決手段。理解這個問題的根源，在於認識到「訊息從發送方，經過網路傳輸到伺服器、再從伺服器轉發到接收方」，這整個過程，涉及多次網路傳輸，而網路傳輸的延遲，並不是完全穩定、可預測的——即使使用者A先發送了訊息1、緊接著發送了訊息2，因為網路狀況的隨機波動（例如訊息1恰好經過了一條稍微壅塞的網路路徑，而訊息2走了另一條更順暢的路徑），完全有可能出現「訊息2，反而比訊息1更早抵達伺服器，或更早被推送到接收方的裝置」這種順序錯亂的情況，如果客戶端天真地，依照「我的裝置，收到這則訊息的時間先後」來決定顯示順序，可能會呈現出「訊息2顯示在訊息1之前」這種令人困惑、和實際發送意圖不符的錯誤順序。正確的解法，是**不依賴任何裝置本地觀察到的時間先後，而是由一個具有權威性的中心點（通常是伺服器），為每一則訊息，賦予一個明確、嚴格遞增的序號**，這個序號一旦被賦予，就代表了這則訊息「在整個系統的權威記錄裡，確切的先後順序」，不管這則訊息，實際上花了多久才被推送到各個接收方的裝置、也不管各個裝置，實際上是以什麼樣的先後順序，實際收到這些網路封包，客戶端在顯示訊息列表時，**依照伺服器賦予的序號來排序，而不是依照裝置本地接收到的時間戳**，這樣才能保證，不管網路傳輸的實際延遲和先後順序有多麼不可預測，最終呈現給使用者看到的訊息順序，始終是正確、且和發送方原本的意圖一致的。至於為什麼序號要「依照每個對話單獨維護」而不是「使用一個全域共用的序號」，是因為——如果用一個全域共用的計數器，來為系統裡**所有**對話、**所有**使用者發送的訊息，統一編號，這個全域計數器，會成為一個**巨大的併發瓶頸**（因為系統裡同時可能有成千上萬個不同的對話，同時在發送訊息，如果它們都要爭搶同一個全域計數器來取得下一個序號，這個計數器本身，很容易成為整個系統吞吐量的天花板），且「不同對話之間的訊息，順序是否嚴格一致」，通常也不是使用者真正關心的需求（使用者關心的，是「我和某個朋友的對話裡，訊息的先後順序要對」，而不太會在意「我和朋友A的對話，和我和朋友B的對話，這兩者之間的訊息，誰先誰後」），因此，把序號的維護範圍，縮小到「每一個獨立的對話」這個粒度（而不是整個系統全域），既能滿足使用者真正在意的順序需求，又避免了「所有訊息都爭搶同一個全域計數器」這種不必要的併發瓶頸，是一個更務實、更符合實際需求的設計選擇。理解「保證訊息順序的核心做法，是由伺服器為每一則訊息，依照對話(而非全域)為單位，分配一個嚴格遞增的序號，客戶端依照這個伺服器賦予的序號排序顯示，而不依賴裝置本地觀察到的接收時間先後，這正確地解決了網路傳輸延遲不均可能導致的順序錯亂問題，同時把序號維護的粒度限縮到單一對話，避免了全域計數器帶來的不必要併發瓶頸」，展現你理解即時通訊系統裡訊息順序保證，這個核心可靠性需求背後的具體技術實現和設計權衡。

**面試回答方式**：給出核心做法——「由伺服器為每一則訊息，依照對話為單位(而非全域)，分配一個嚴格遞增的序號，客戶端依照這個序號排序顯示，而不依賴裝置本地接收訊息的時間先後」。解釋為什麼不能依賴本地接收時間——「網路傳輸延遲不均，可能導致後發送的訊息反而先到達，如果依賴本地接收時間排序，會呈現和實際發送意圖不符的錯亂順序」。解釋為什麼序號要以對話為單位而非全域——「全域共用計數器會成為巨大的併發瓶頸，且使用者真正在意的是同一對話內的順序，不同對話之間的順序通常不重要，把序號維護範圍限縮到單一對話能避免不必要的併發瓶頸」。展現你理解訊息順序保證背後具體的技術實現和設計權衡。

### 群組聊天(比如一個有幾萬人的大型公開群組)，如果每個人發的訊息都要推送給所有其他成員，這種「一對多的扇出(Fan-out)」在架構設計上會遇到什麼挑戰?怎麼優化?

**核心答案**：核心挑戰是**「扇出的規模，和群組人數成正比」**——如果一個有 5 萬人的群組，任何一個成員發送一則訊息，系統理論上需要把這則訊息，轉發、推送給另外 4 萬 9999 個成員（假設這麼多人同時在線），這意味著,**單一則訊息的發送，會瞬間觸發數萬次的推送操作**，如果群組裡有多個成員，幾乎同時發送訊息，這種扇出的負擔會急劇疊加，可能對訊息佇列、連線閘道伺服器造成顯著的瞬間壓力。常見的優化手段包括——**（1）依照使用者是否在線，決定扇出的即時性**——只對「目前確實在線」的成員，做即時的推送扇出；對離線的成員，只需要把訊息持久化儲存，不需要嘗試即時推送（反正推送了也送不到，離線成員之後上線，再主動拉取即可）；**（2）批次化處理扇出**——把「需要推送給大量成員」這件事，視為一個可以稍微延遲、批次處理的背景任務，而不是要求每一則訊息，都必須在極短時間內，對所有成員完成推送，透過訊息佇列，把扇出任務分散到多個消費者並行處理，提升整體的處理吞吐量；**（3）對於超大型群組，考慮改變推送模式，從「主動推送給每個人」改為「客戶端定期或依需求主動拉取最新訊息」**（類似前面CDN和快取章節討論過的推送vs拉取模式權衡，見 [[005-cdn-design.md]]），在群組規模極大時，拉取模式可能比強制對所有人即時推送更具擴展性。

**詳細解析**：這題把一對多扇出這個在社群媒體、大型群組場景經常出現的規模化挑戰，和之前系統設計方法論裡強調的「容量估算（Back-of-the-Envelope Estimation）驅動架構決策」這個原則連結起來，考察是否理解「群組人數規模，會直接決定架構設計的複雜度和所需要的優化手段」。理解這個問題的關鍵，在於認識到「一對一聊天」和「大型群組聊天」，雖然表面上都是「發送和接收訊息」這件事，但底層的規模特性有本質性的差異——一對一聊天，一次訊息發送，最多只需要推送給一個接收方，扇出的規模是固定的、很小的（O(1)）；但群組聊天，一次訊息發送，需要推送給的對象數量，隨著群組的成員人數而線性增長，對於一個只有十幾個人的小群組，這個扇出規模依然很小，用之前討論過的、直接查詢連線對應表並逐一轉發的做法，完全沒有問題；但對於一個有幾萬人的大型公開群組（例如某些知名人物或組織的官方群組），一則訊息，理論上需要觸發數萬次的推送操作，如果不加以優化，天真地對每個成員都做「即時、逐一查詢連線對應表、逐一轉發」這種處理，可能瞬間對系統造成巨大的壓力（尤其如果群組裡，恰好同時有多個活躍成員都在發言，這種瞬間的高扇出負擔會不斷疊加）。第一個優化手段——「只對在線成員做即時扇出」，本質上是一個務實的觀察——嘗試把訊息，即時推送給一個「目前根本沒有任何連線、必然無法接收到」的離線成員，是一種徒勞的努力（推送出去也不會有任何效果，因為對方根本沒有連線可以接收），與其浪費資源嘗試這種注定失敗的即時推送，不如直接跳過離線成員的即時扇出部分，只把訊息持久化儲存起來，等這個成員之後真正上線時，再讓他主動拉取，這樣能顯著減少「需要真正處理即時扇出」的實際成員數量（尤其如果一個大群組裡，大部分成員平時並不是時時刻刻都在線，只對「當下真的在線」的那一部分成員做即時扇出，能大幅降低瞬間的處理負擔）。第二個優化手段——「批次化處理」，承認了「對一個超大群組做完整的扇出，本身就是一個相對耗時的操作，不應該假設它必須在極短的、和一對一訊息推送相同的時間標準內完成」，透過把這個扇出任務，拆解成可以分散給多個消費者並行處理的批次工作(例如把5萬個接收目標，拆成50批，每批1000人，分散給50個並行的消費者各自處理自己負責的那一批)，能有效地利用多個消費者的並行處理能力，提升整體完成扇出所需要的總時間效率，即使對於單一則訊息而言，可能不再是「立即、瞬間對所有人完成推送」，而是「在一個相對短暫、但不是絕對零延遲的時間窗口內，逐步地對所有在線成員完成推送」，這種輕微的即時性犧牲，換取了系統整體處理超大規模扇出時的穩定性和可控性。第三個優化手段——「拉取模式」，則是一個更根本性的架構轉變，某種程度上，承認了「當群組規模大到某個程度，強制對所有人即時推送，本身可能已經不是最合適的架構選擇」，轉而讓客戶端，自己主動地、依照自己的節奏，去查詢/拉取最新的群組訊息(可能搭配某種增量拉取的機制，只拉取自己上次查詢之後、新增的訊息)，這種模式，某種程度上犧牲了「絕對即時」的推送體驗，換取更好的系統擴展性（因為伺服器端，不再需要主動地、精確地追蹤每一個群組成員的即時連線狀態並逐一推送，而是被動地回應客戶端主動發起的查詢請求），這種取捨是否值得，取決於具體業務對「即時性」和「系統擴展性」這兩者之間，實際的優先順序權衡。理解「群組聊天的一對多扇出，其規模和挑戰，隨著群組成員人數呈線性增長，面對超大型群組，需要透過只對在線成員做即時扇出、批次化並行處理扇出任務、乃至於在極端規模下考慮改用拉取模式取代強制推送，這幾個層次遞進的優化手段，來因應扇出規模帶來的架構挑戰，這也呼應了容量估算應該驅動架構決策這個系統設計的一般性原則」，展現你理解群組聊天扇出這個問題的規模特性，以及一系列層次遞進的優化思路。

**面試回答方式**：先指出核心挑戰——「扇出的規模和群組人數成正比，大型群組一則訊息理論上要推送給數萬人，單一訊息會瞬間觸發數萬次推送操作，對系統造成顯著壓力」。給出層次遞進的優化手段——「只對目前確實在線的成員做即時扇出(對離線成員，推送也是徒勞，只需持久化儲存等其上線後拉取)、批次化並行處理扇出任務(把大量接收目標拆成多批，分散給多個消費者並行處理，提升整體吞吐量)、在極端規模下考慮改用拉取模式取代強制推送(犧牲絕對即時性換取更好的系統擴展性)」。強調「這呼應了容量估算應該驅動架構決策這個系統設計的一般性原則，群組規模的量級，直接決定了應該採用哪個層次的優化手段」。展現你理解群組聊天扇出問題的規模特性和層次遞進的優化思路。
