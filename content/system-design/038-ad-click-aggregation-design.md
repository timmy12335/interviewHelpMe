# 題目

設計一個廣告點擊統計系統，支援即時查詢與帳務級的準確性。

## 核心答案

這個系統的特殊之處是「同一份資料有兩種正確性要求」：報表的即時查詢容忍幾秒的誤差，而計費必須精確到每一次點擊——用同一條管線同時滿足兩者是不現實的。

**架構是 Lambda 式的雙路**。**快路徑**：點擊事件寫入 Kafka，流式作業做分鐘級的視窗聚合寫入 OLAP 儲存，**供即時儀表板查詢**。**慢路徑**：原始事件落到物件儲存，每小時或每天用批次作業重算並覆蓋快路徑的結果，**作為計費與對帳的依據**。

**去重是核心難題**。同一次點擊可能因為重試或客戶端重送而多次上報，用「點擊 ID + 時間窗」在流處理中做去重（例如 Flink 的狀態後端或 Redis 的布隆過濾器），但流式去重只能覆蓋有限的時間窗——跨窗的重複由批次作業徹底處理。

**分區鍵的選擇決定一切**：按廣告 ID 分區能讓同一個廣告的所有事件落在同一個運算節點，代價是熱門廣告造成資料傾斜。

## 詳細解析

「重算能覆蓋」是這個架構最重要的性質。流式處理在延遲事件、故障恢復、與去重上都只能做到近似——而批次作業擁有完整的資料與無限的時間，可以做到精確。所以設計上要讓批次結果無條件覆蓋流式結果，**而不是試圖修補流式的偏差**。這也意味著原始事件必須被完整保留——它是唯一的真相來源，任何聚合結果都是它的衍生物，可以隨時重建。

資料傾斜的處理是「加鹽再兩階段聚合」。熱門廣告的事件量可能是普通廣告的萬倍——在分區鍵後面加上一個隨機後綴（廣告ID_0 到 廣告ID_99）把它打散到多個節點做局部聚合，**再做一次全域聚合合併**。**代價是多一次 shuffle**，但它把「一個節點被壓垮」變成「所有節點均勻分擔」。

**時間語意必須明確**。**事件時間**（點擊實際發生的時刻）與**處理時間**（系統收到的時刻）可能相差很久——手機離線後重新連網會一次性上報幾小時前的事件。**計費必須按事件時間歸屬**，**否則跨日的邊界會出錯**。而按事件時間聚合就需要水印（watermark）機制：宣告「事件時間早於 T 的資料應該都到齊了」並觸發視窗計算，遲到更久的資料進入側輸出流由批次處理。

作弊偵測是這個系統無法迴避的部分。同一 IP 的高頻點擊、極短的停留時間、以及異常的地理分布都是訊號。**它不必在快路徑做**（那會拖慢延遲），放在批次路徑裡，在計費前過濾——再次體現了「兩條路徑各司其職」的價值。

## 面試回答方式

先點出特殊之處——同一份資料有兩種正確性要求：即時查詢容忍誤差、**計費必須精確到每一次點擊**，用同一條管線同時滿足兩者不現實。給雙路架構（快路徑做分鐘級視窗聚合供儀表板，慢路徑批次重算作為計費依據）與**去重的分層**（流式用點擊 ID 加時間窗，跨窗重複由批次徹底處理）。加分點有四個：「重算能覆蓋」是這個架構最重要的性質——批次無條件覆蓋流式，而不是修補流式的偏差，所以原始事件必須完整保留，它是唯一的真相來源；資料傾斜用加鹽加兩階段聚合處理；**時間語意必須明確**——計費按事件時間歸屬，需要水印機制，遲到更久的走側輸出交給批次；以及作弊偵測放在批次路徑、計費前過濾，體現兩條路徑各司其職。

## 講稿

這個系統的特殊之處是同一份資料有兩種正確性要求。報表的即時查詢容忍幾秒誤差，而計費必須精確到每一次點擊。用同一條管線同時滿足兩者是不現實的。

所以我會用雙路。快路徑把事件寫進訊息佇列，流式作業做分鐘級的視窗聚合供儀表板查。慢路徑把原始事件落到物件儲存，每小時或每天批次重算，覆蓋快路徑的結果，作為計費跟對帳的依據。

這裡最重要的性質是重算能覆蓋。流式處理在延遲事件、故障恢復、去重上都只能做到近似，而批次有完整資料跟無限時間，可以做到精確。所以我不會試圖修補流式的偏差，而是讓批次結果無條件覆蓋。這也意味著原始事件必須完整保留，它是唯一的真相來源。

另外兩個實務重點。資料傾斜要加鹽做兩階段聚合，把熱門廣告打散到多個節點局部聚合再合併。還有時間語意，計費必須按事件時間歸屬而不是處理時間，因為手機離線後會一次上報幾小時前的事件。

## 常見追問

### 為什麼不用單一的流式管線（Kappa 架構）？

**核心答案**：可以，但前提是「重放」足夠可靠且便宜。Kappa 的做法是保留 Kafka 中的全部原始事件，需要修正時就從頭重放一次——它消除了維護兩套邏輯的成本，那是 Lambda 最大的缺點。但它要求：訊息系統能保存長期歷史（成本高）、重放的速度足以在合理時間內趕上、以及流式框架本身能保證精確一次。

**詳細解析**：「維護兩套邏輯」的痛苦被低估了。Lambda 架構下同一個聚合要用流式與批次各寫一次，兩邊的細微差異會導致「即時報表與帳單對不上」——**而排查這種差異極其耗時**。所以如果團隊能滿足 Kappa 的前提，它通常是更好的選擇。實務上的折衷是「用同一套程式碼跑兩種模式」：Flink 與 Spark 都支援批流一體的 API，讓同一份聚合邏輯既能處理串流也能處理歷史檔案——它保留了 Lambda 的重算能力，卻消除了雙份實作的差異風險。這個折衷在多數場景下是最務實的答案。

**面試回答方式**：肯定 Kappa 並給出它的三個前提（長期保存原始事件的成本、重放速度、精確一次保證）。加分點是強調**Lambda 最大的缺點被低估**——兩套邏輯的細微差異會導致即時報表與帳單對不上，而排查極其耗時。收在最務實的折衷：用批流一體的 API 讓同一份聚合邏輯跑兩種模式，保留重算能力又消除雙份實作的差異風險。

### 查詢端該用什麼儲存？

**核心答案**：**列式的 OLAP 儲存**（ClickHouse、Druid、或雲上的對應服務）。理由是**查詢模式高度固定**——按時間範圍、廣告主、廣告位聚合，**只讀少數幾個欄位**；列式儲存讓這種查詢只掃描需要的欄位，並且壓縮率極高。**同時要預先聚合**：保留分鐘級明細用於近期查詢，小時級與日級的彙總用於長期報表，因為沒有人需要查一年前的分鐘級資料。

**詳細解析**：「預聚合的層級劃分」是成本控制的關鍵。原始明細的儲存成本隨時間線性成長而查詢價值快速衰減——七天前的分鐘級資料幾乎不會被查。合理的生命週期是：分鐘級保留 7 天、小時級保留 90 天、日級永久保留，**過期自動降級或刪除**。這個設計能把儲存成本降低一到兩個數量級，而幾乎不影響使用者體驗。另一個要點是「維度基數的控制」：如果允許按任意維度組合查詢，預聚合的組合數會爆炸——所以要明確定義支援哪些維度組合，並對高基數維度（例如使用者 ID）拒絕聚合查詢，引導使用者用明細查詢或抽樣。

**面試回答方式**：給出選型與理由（列式 OLAP，因為查詢模式固定、只讀少數欄位、壓縮率高）與**預聚合的分層**。加分點是**生命週期的成本效益**：分鐘級 7 天、小時級 90 天、日級永久，能把儲存成本降一到兩個數量級而幾乎不影響體驗。第二個是**維度基數的控制**——允許任意維度組合會讓預聚合的組合數爆炸，所以明確定義支援的組合，對高基數維度拒絕聚合查詢並引導到明細或抽樣。

### 怎麼保證計費資料不會少算或多算？

**核心答案**：用可重算加對帳，而不是追求管線的精確一次。每一批計費結果都要能**從原始事件完整重建**，**並與上一次的結果比對**；差異超過閾值就阻擋出帳並告警。**同時要有端到端的計數校驗**：上報端記錄發送總數，儲存端記錄接收總數，聚合端記錄處理總數——三者的差異就是丟失或重複的量。

**詳細解析**：「端到端計數」是一個簡單但極其有效的機制。分散式管線裡任何一個環節都可能靜默丟資料——而只看每個元件自己的健康指標是發現不了的。用一個獨立的計數鏈路（每個環節上報自己處理的事件數到一個獨立的指標系統）能在幾分鐘內暴露問題，**而不是在月底出帳時才發現**。另一個實務原則是「計費結果一旦出帳就不可變」：發現錯誤時要用「調整單」修正，而不是改寫歷史帳單——因為客戶已經看過那份帳單，改寫會摧毀信任，而且無法審計。這條原則與複式記帳的「只增不改」是同一個思路。

**面試回答方式**：給核心策略——可重算加對帳，而非追求管線的精確一次，並給端到端計數校驗（上報、接收、處理三個總數的差異就是丟失或重複量）。加分點是說明**端到端計數為何有效**：任何環節都可能靜默丟資料，而只看各元件自己的健康指標發現不了，獨立的計數鏈路能在幾分鐘內暴露問題而不是月底才發現。收在一條原則：**計費結果一旦出帳就不可變**，用調整單修正而非改寫歷史帳單——**改寫會摧毀信任且無法審計**。
