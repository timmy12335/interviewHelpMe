# 題目

設計一個分散式鍵值儲存系統，支援 `put(key, value)` 與 `get(key)`，要求能水平擴展到數百節點、單一節點故障不影響服務。請說明從單機版本擴展到分散式版本時，需要處理哪些核心議題。

## 核心答案

單機鍵值儲存本質上就是一張雜湊表，難點只在「資料量超過記憶體時怎麼辦」（用**資料壓縮**與**冷資料落磁碟、熱資料留記憶體**緩解）。真正的複雜度來自分散式化，需要處理六個核心議題。**（1）資料分區**——用**一致性雜湊**（見 [[../backend-engineering/017-consistent-hashing.md]]）把鍵映射到節點，使得節點增減時只有少量鍵需要搬移，並用虛擬節點解決負載不均。**（2）資料複製**——每個鍵複製到環上順時針方向的 N 個節點（跳過同一實體機器／機架，避免相關性故障）。**（3）一致性**——用 **N/W/R quorum**（N 個副本、寫入需 W 個確認、讀取需 R 個回應）調節強一致與可用性、延遲之間的取捨。**（4）不一致的解決**——並發寫入無法用時間戳可靠排序，需要**向量時鐘**這類因果關係追蹤機制來偵測真正的衝突。**（5）故障處理**——用 **gossip 協定**做去中心化故障偵測；暫時性故障用**寬鬆 quorum 與 hinted handoff** 維持可用性；永久性故障用 **Merkle tree 反熵**高效比對並修復副本差異；資料中心級故障則靠跨機房複製。**（6）儲存引擎**——寫入走 **commit log + memtable**，滿了刷成不可變的 **SSTable**；讀取先查 **bloom filter** 判斷可能落在哪些 SSTable，避免無謂的磁碟存取。

## 詳細解析

**為什麼這道題的核心不是「怎麼存」而是「怎麼在故障中維持服務」**：單機鍵值儲存的介面極簡單，這反而使它成為一道好的系統設計題——因為介面沒有複雜度可言，所有的設計深度都集中在「當節點數量變多、且節點必然會壞」這個前提上。一個常見的答題失誤是花大量時間描述雜湊表與磁碟結構，卻對「三個副本的資料不一致時，讀到的是哪一份」這類問題沒有準備。實際上，從單機到分散式的每一個議題，都是由**同一個現實**推導出來的：節點會故障、網路會分割、而系統必須在這些事情發生時仍然可用。分區是為了讓資料量與流量超出單機能力後還能擴展；複製是為了讓單節點故障不造成資料遺失；而一旦有了多份副本，一致性、衝突解決、故障偵測與修復這一整串問題就必然接踵而至——**它們不是可選的功能，而是「決定複製」這個選擇的必然後果**。

**CAP 在這裡不是三選二，而是「分割發生時選 C 還是 A」**：CAP 定理（見 [[../backend-engineering/016-cap-theorem.md]]）常被誤述為「一致性、可用性、分割容忍三者只能選兩個」，但在真實的分散式系統裡，**網路分割是無法拒絕的現實**，不可能「選擇不要分割容忍」。所以實際的選擇只發生在分割真的出現時：是**拒絕服務以保證所有人讀到的資料一致（CP）**，還是**繼續服務、接受可能讀到過期資料，等分割修復後再收斂（AP）**。鍵值儲存設計時必須明確表態自己站在哪一邊，因為這個選擇會往下決定 quorum 怎麼配、衝突怎麼解、以及是否需要向量時鐘。銀行帳務類的場景傾向 CP；購物車、社群動態這類「暫時看到舊資料可以接受，但不能讓使用者無法操作」的場景傾向 AP，而 AP 的選擇正是向量時鐘、hinted handoff、反熵修復這一整套機制存在的理由——它們全都是為了讓系統在**先接受了不一致**之後，還能最終收斂到正確狀態。

**六個議題之間的依賴關係**：這六件事不是平行的清單，而是有明確依賴的鏈條。分區決定了「哪些節點負責哪些鍵」，複製在分區的基礎上決定「一份資料放在哪 N 個節點」，quorum 在複製的基礎上決定「讀寫要聯絡幾個副本才算數」，衝突解決處理「quorum 允許的不一致實際發生後怎麼辦」，故障處理讓前面這些機制在節點真的壞掉時還能運作，儲存引擎則是每個單節點內部如何高效落地。在面試中依這個順序展開，能讓論述有清楚的推進感，而不是零散地跳躍。也要注意**跳過同一實體機器或機架選擇副本**這個細節——如果 N 個副本剛好都落在同一個機架上，機架斷電就等於整份資料不可用，複製的意義就被架空了，這類「副本必須分散在故障域之間」的考量，是複製設計裡容易被忽略但很能展現實務經驗的一點。

**寫入與讀取路徑為什麼要分開設計**：鍵值儲存的寫入通常遠比讀取容易優化——寫入可以先追加到 commit log（順序寫，磁碟友善）並更新記憶體中的 memtable，就立刻回應成功，完全不需要在寫入當下處理排序與去重。代價是這些寫入分散在記憶體與多個歷史 SSTable 裡，**讀取因此變複雜**：一個鍵可能存在於 memtable、也可能存在於任何一個舊的 SSTable，讀取必須逐層尋找。bloom filter 就是為了讓「這個鍵是否可能在這個 SSTable 裡」能在記憶體中被極快地判斷，把大量不必要的磁碟存取直接省掉。這種「**用寫入的簡單換讀取的複雜，再用索引結構把讀取成本補回來**」的取捨，是 LSM 類儲存引擎的核心特徵，與傳統 B+ 樹（見 [[../database/001-btree-index.md]]）「寫入時就維持有序、讀取直接定位」的策略形成對照。

## 面試回答方式

先用一句話界定這道題的真正難點——「單機鍵值儲存就是一張雜湊表，這題所有的設計深度都在『節點會壞、網路會斷，但服務要活著』這個前提上」，避免把時間浪費在描述資料結構。接著按依賴鏈條展開六個議題：分區（一致性雜湊 + 虛擬節點）、複製（N 個副本，且必須跨故障域）、一致性（N/W/R quorum）、衝突解決（向量時鐘）、故障處理（gossip 偵測、hinted handoff 應付暫時故障、Merkle tree 反熵修復永久故障）、儲存引擎（commit log + memtable + SSTable + bloom filter）。中間主動釐清 CAP 的常見誤解——「不是三選二，因為網路分割不能拒絕，真正的選擇是分割發生時要 CP 還是 AP」，並說明這個選擇會往下決定 quorum 配置與是否需要向量時鐘，展現你理解這些機制之間的因果而非各自獨立。若時間允許，補上兩個容易加分的細節：副本必須避開同一機架（否則複製形同虛設）、以及 LSM 用寫入的簡單換讀取的複雜、再用 bloom filter 補回讀取成本這個取捨。

## 常見追問

### 為什麼鍵值儲存普遍用一致性雜湊做分區，而不是簡單的「雜湊值取模節點數」？

**核心答案**：因為取模的結果**與節點總數綁定**——節點數從 N 變成 N+1 時，幾乎每個鍵的目標節點都會改變，代表需要搬移接近**全部**的資料。對一個持有數 TB 資料的叢集來說，這意味著擴容一次就要製造一次全叢集規模的資料遷移風暴，期間大量請求會落到還沒收到資料的節點上，實務上不可接受。一致性雜湊把鍵和節點都映射到同一個環上，鍵歸屬於順時針方向遇到的第一個節點，於是**新增或移除一個節點，只影響環上相鄰的那一段區間**，需要搬移的資料量從「全部」降到「大約 1/N」。虛擬節點則進一步解決一致性雜湊本身的兩個問題：節點在環上分佈不均導致的資料傾斜，以及**節點故障時，它的全部負載會集中壓到單一個後繼節點**上——有了虛擬節點，故障節點的負載會被分散給多個不同的實體節點。

**詳細解析**：這題考察是否理解分區演算法的評判標準，在分散式儲存場景下多了一個單機時代不存在的維度——**節點集合變動時的資料搬移量**。取模在單機或節點數固定的場景下是完美的：分佈均勻、計算極快、實作一行。它之所以在這裡不適用，關鍵不在於「不夠均勻」，而在於它的映射函數把節點總數當作參數，導致**參數一變，整個映射關係全部失效**。理解這一點能推導出一致性雜湊的設計動機：它刻意讓映射函數**不依賴節點總數**——鍵映射到環上的位置只由鍵本身決定，節點映射到環上的位置只由節點識別碼決定，兩者都與「目前總共有幾個節點」無關，於是節點集合變動時，已經固定的鍵位置完全不受影響，只有「哪個節點負責這段區間」的歸屬會在局部發生變化。虛擬節點的引入則揭示了另一個層次的問題：一致性雜湊解決了搬移量，但沒有自動保證均勻——少量節點隨機散佈在環上時，各自負責的弧長差異可能很大，造成資料傾斜；更嚴重的是**故障時的負載轉移集中**，某節點下線後它負責的整段區間會全部落到下一個節點身上，這個節點很可能因此過載並跟著崩潰，形成連鎖故障。讓每個實體節點在環上擁有多個虛擬位置，等於把它的負責範圍打散成許多小片段，既讓總負載趨於均勻，也讓任一節點故障時的負載被分攤到多個不同節點，這個「**把大塊的責任切碎再分散，以避免故障時的集中衝擊**」的思路，本身就是一個值得記住的可用性設計模式。理解「取模的問題不是分佈不均而是映射函數依賴節點總數導致變動時全部失效；一致性雜湊刻意讓映射不依賴節點總數，把搬移量從全部降到約 1/N；虛擬節點額外解決分佈傾斜與故障時負載集中轉移導致連鎖崩潰的問題」，展現你能分辨表層現象與根本機制。

**面試回答方式**：先精準指出取模的問題所在——「不是分佈不均，而是它的映射函數把節點總數當參數，節點數一變整個映射全部失效，等於擴容一次就要搬移接近全部的資料」。給出量化對比讓問題具體化——「從搬移全部，降到只搬移約 1/N」。說明一致性雜湊的設計動機——「刻意讓鍵和節點的環上位置都不依賴節點總數，所以節點變動只影響環上局部區間的歸屬」。接著主動補上虛擬節點解決的**兩個**問題，尤其別漏掉第二個——「一是節點少時環上分佈不均造成資料傾斜；二是更嚴重的，某節點故障時它的整段負載會全部壓到下一個節點，可能把它也壓垮形成連鎖故障，虛擬節點讓這份負載被分攤到多個節點」。最後提煉成通用模式——「把大塊責任切碎再分散，避免故障時的集中衝擊」。

### 副本數 N 應該怎麼選？是不是越多越好？

**核心答案**：不是。N 決定的是**容錯能力與成本的取捨**，且它與 quorum 配置耦合。N 越大，能容忍越多節點同時故障、讀取的可選副本越多（有助於分散讀流量），但代價是：**儲存成本線性上升**（N=3 代表要付 3 倍儲存）、**寫入放大**（每次寫入要送到 N 個節點，佔用 N 倍網路與磁碟頻寬）、以及**維持一致性的成本上升**（更多副本代表反熵修復要比對的對象更多、不一致的視窗更難收斂）。實務上 **N=3 是最常見的選擇**，因為它是能同時滿足「容忍單節點故障後仍有多數副本存活」與「成本可接受」的最小值——N=2 時任一節點故障就無法形成多數，N=3 則允許壞掉一個之後，剩下兩個仍能組成 W=2 的多數 quorum。此外 N 的選擇還要考慮**故障域分佈**：三個副本若無法放在三個不同的故障域（機架／可用區），實際容錯能力會低於帳面上的數字。

**詳細解析**：這題考察是否能把「副本數」這個看似單一的參數，展開成它牽動的整組後果。理解的關鍵，在於認識到 N 不只影響容錯，它同時是**寫入成本的乘數**與**一致性維護難度的乘數**。寫入放大這一點特別容易被忽略：在 N=5 的配置下，每一次使用者層面的寫入，在系統內部都變成五次網路傳輸與五次磁碟寫入，這對高寫入量的系統是相當可觀的成本，且它會直接影響叢集能承受的寫入吞吐上限。一致性維護的成本上升則更隱蔽——副本越多，任兩個副本之間出現分歧的機會越多，反熵修復需要進行的比對組合數增加，而在 AP 系統中，更多的副本也意味著並發寫入產生的版本分支可能更複雜。至於為什麼 N=3 成為業界慣例，關鍵在於「多數（majority）」這個概念的門檻效應——分散式系統中大量機制依賴「取得多數副本的同意」來保證正確性（例如 W + R > N 這個保證讀寫重疊的條件），而要在**損失一個節點之後仍能取得多數**，N 至少必須是 3：N=2 時多數是 2，損失一個就湊不齊；N=3 時多數是 2，損失一個還剩兩個，恰好足夠。再往上加到 N=5 雖然能容忍同時損失兩個節點，但成本也隨之上升，只有在可用性要求極高或故障率確實較高的環境才值得。最後，故障域這個維度提醒我們**帳面副本數不等於實際容錯能力**——如果三個副本都在同一個機架上，那麼這個系統實際上只能容忍「單一伺服器故障」，完全無法容忍「機架級故障」，副本數的意義被部署拓撲抵消了，這也是為什麼副本放置策略必須顯式地跨故障域。理解「N 同時是容錯能力、儲存成本、寫入放大與一致性維護難度的乘數；N=3 是因為它是損失一個節點後仍能形成多數的最小值；且帳面副本數若未跨故障域分佈，實際容錯能力會低於數字所示」，展現你能把單一參數展開成它牽動的整組系統後果。

**面試回答方式**：直接否定「越多越好」，然後把 N 展開成它牽動的多個後果——「N 同時是容錯能力、儲存成本、寫入放大、一致性維護難度的乘數」，特別點出容易被忽略的寫入放大——「N=5 代表每次使用者寫入在內部變成五次網路傳輸與五次磁碟寫入，直接壓低叢集的寫入吞吐上限」。解釋 N=3 為何成為慣例時，用「多數」的門檻效應論證——「大量機制依賴取得多數副本同意，而要在損失一個節點後仍能形成多數，N 至少要 3：N=2 時損失一個就湊不齊多數，N=3 時還剩兩個恰好夠」。最後補上部署拓撲的維度——「帳面副本數不等於實際容錯能力，三個副本都在同一機架，就只能容忍單機故障而非機架故障，所以副本放置必須顯式跨故障域」。

### 這樣一套 AP 取向的鍵值儲存，適合拿來存什麼、不適合存什麼？

**核心答案**：適合**「暫時讀到稍舊的資料不會造成實質傷害，但服務中斷會」**的場景——使用者的購物車、會話狀態、偏好設定、社群動態的計數、商品瀏覽紀錄等；這類資料的特徵是**單一使用者的資料彼此獨立、沒有跨鍵的交易需求、且業務邏輯能容忍最終一致**。不適合**需要跨鍵原子性或即時強一致**的場景——最典型的是金額轉帳（必須保證扣款與入帳同時成功或同時失敗，這是跨鍵交易）、庫存扣減（超賣的代價是真實的商業損失，不能靠「最終會收斂」補救）、以及任何需要「讀到的一定是最新值」才能正確判斷的邏輯（如依據餘額決定是否放行交易）。這類需求應該用支援交易的關聯式資料庫，或選擇 CP 取向的儲存。

**詳細解析**：這題考察是否能把技術特性轉譯成選型判斷，而不是停留在「AP 就是可用性高」這種抽象描述。理解的關鍵，在於抓住 AP 鍵值儲存的**兩個結構性限制**，並用它們反推適用邊界。第一個限制是**沒有跨鍵原子性**——鍵值儲存的操作單位是單一個鍵，兩個鍵的更新無法被包在同一個原子操作裡，這直接排除了所有「必須同時成立」的業務語意，轉帳是最經典的例子（見 [[../backend-engineering/013-distributed-transaction-solutions.md]] 討論的分散式交易方案，正是為了在缺乏原生跨鍵交易時補上這個能力）。第二個限制是**讀取可能拿到舊值**——在 AP 配置下，為了低延遲與高可用，讀取可能只聯絡少數副本，這些副本未必收到了最新的寫入。判斷一個場景能否接受這一點，有個實用的提問方式：「**如果使用者剛剛做了一個操作，然後立刻重新整理頁面卻看不到結果，這會造成什麼後果？**」對購物車來說，後果是輕微的困惑，而且下次重新整理通常就好了；對庫存扣減來說，後果可能是兩個人同時買到最後一件商品，造成真實的商業糾紛——**代價的可逆性**是這裡的關鍵分水嶺。值得補充的是，這個判斷不是非黑即白的：許多系統會採取混合策略，把核心交易資料放在強一致的儲存，把周邊的高流量、可容忍延遲的資料放在 AP 鍵值儲存，讓兩種儲存各自承擔它們擅長的部分，而不是強求單一種儲存滿足所有需求。理解「AP 鍵值儲存的兩個結構性限制是沒有跨鍵原子性與讀取可能拿到舊值；判斷適用性的實用提問是『使用者剛操作完立刻重整卻看不到結果會怎樣』，關鍵分水嶺是代價的可逆性；且實務上常採混合策略讓不同性質的資料各得其所」，展現你能把 CAP 的抽象取捨，落成具體可操作的選型準則。

**面試回答方式**：不要停在「AP 適合對可用性要求高的場景」這種空泛回答，而是給出兩個結構性限制作為判斷依據——「沒有跨鍵原子性」與「讀取可能拿到舊值」。針對第一點舉出被排除的場景——「轉帳這種必須同時成功或同時失敗的操作」。針對第二點給出一個實用的提問法——「使用者剛操作完立刻重整卻看不到結果，會造成什麼後果？購物車只是輕微困惑，庫存扣減則可能兩個人同時買到最後一件，造成真實商業糾紛」，並點明關鍵分水嶺是**代價的可逆性**。最後補上實務做法——「不必強求單一儲存滿足所有需求，常見是核心交易資料放強一致儲存，周邊高流量可容忍延遲的資料放 AP 鍵值儲存」。
