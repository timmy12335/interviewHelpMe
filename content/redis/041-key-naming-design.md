# 題目

Redis 的鍵該怎麼命名與設計？有哪些會在後期造成麻煩的決定？

## 核心答案

命名的基本規範是**用冒號分層、由粗到細**：`業務:實體:識別碼:欄位`，例如 `order:detail:12345`、`user:session:abc123`。**冒號是社群約定的分隔符**（`redis-cli --scan --pattern 'order:*'` 與各種管理工具都預期它），而分層讓「掃描某一類鍵」與「理解這個鍵是誰在用」變得容易。

四個會在後期造成麻煩的決定。**沒有統一前綴**——多個服務共用一個 Redis 實例時，無法區分誰的鍵、也無法安全地清理。**鍵名過長**——每個鍵的名稱都佔記憶體，`user:profile:information:detail:12345` 比 `u:p:12345` 多了三十幾位元組，**一千萬個鍵就是三百多 MB**。**沒有 TTL**——忘記設過期的鍵會永久累積，這是記憶體緩慢成長最常見的原因。**用一個大 key 裝所有東西**——後期無法拆分也無法分片。

**最重要的一條是「每個鍵都應該有明確的擁有者與生命週期」**——寫下來（在文件或程式碼的常數裡），而不是散落在各處的字串拼接。

## 詳細解析

**鍵名長度的成本是真實但常被忽略的**。Redis 為每個鍵存一份字串，加上字典項的開銷。**在「大量小值」的場景下，鍵名可能佔總記憶體的一半以上**——例如 `user:last_login_time:1234567890` 這個鍵名 30 位元組，而值只是一個時間戳 8 位元組。**縮短鍵名是最便宜的記憶體優化之一**，但要與可讀性平衡：`u:llt:1234567890` 省了記憶體卻讓維護者看不懂。**折衷是「前綴縮寫但有文件」**——在程式碼裡用常數定義（`KEY_USER_LAST_LOGIN = "u:llt:%s"`），讓縮寫只出現在一處。

**沒有 TTL 的鍵是記憶體洩漏的主要形式**。快取類的鍵一律應該有 TTL——**即使業務上「永遠有效」，也該設一個很長的過期時間**（例如 30 天）作為保底，因為「永遠有效」的假設會隨業務演變而失效，而那時候已經累積了幾千萬個沒人記得的鍵。**掃描沒有 TTL 的鍵**（用 `SCAN` 加 `TTL` 檢查）應該是例行巡檢的一部分。

**共用實例時的命名空間隔離**。多個服務共用 Redis 時，用「服務名」當第一層前綴（`svc-order:...`、`svc-user:...`）**讓「這個鍵是誰的」一目了然**，也讓清理與容量分析變得可能。**更徹底的隔離是用不同的資料庫編號（`SELECT`）或不同的實例**——但資料庫編號在叢集模式下不支援，而且它不提供真正的隔離（`FLUSHALL` 會清掉全部），**所以獨立實例才是真正的隔離**。

**鍵的設計會決定日後能不能分片**。把所有使用者的資料放在一個 Hash（`all_users` 裡有一億個欄位）在單機時可行，**但無法分散到叢集的多個節點上，而且是一個災難級的大 key**。正確的設計是**一個實體一個鍵**（`user:12345`），讓雜湊自然地分散。**「現在能跑」與「將來能擴展」在鍵設計上的差別很大，而重新設計鍵意味著資料遷移——所以這是值得在一開始就想清楚的決定。**

## 面試回答方式

先給命名規範（冒號分層、由粗到細）與冒號是社群約定的理由。給**四個會在後期造成麻煩的決定**（沒有統一前綴、鍵名過長、沒有 TTL、一個大 key 裝所有東西）並各配具體後果。加分點有三個：**鍵名長度的成本是真實的**——在大量小值的場景下鍵名可能佔記憶體的一半以上，但要與可讀性平衡，**折衷是用程式碼常數定義讓縮寫只出現在一處**；**沒有 TTL 是記憶體洩漏的主要形式**，即使業務上「永遠有效」也該設一個很長的保底過期，因為那個假設會隨業務演變失效；以及**鍵的設計決定日後能不能分片**——把一億個欄位放在一個 Hash 在單機可行但無法分散且是災難級大 key，**而重新設計鍵意味著資料遷移，所以值得一開始就想清楚**。

## 講稿

命名的基本規範是用冒號分層、由粗到細，像是業務、實體、識別碼、欄位。冒號是社群約定的分隔符，各種管理工具都預期它，而分層讓掃描某一類鍵跟理解這個鍵是誰在用變得容易。

四個會在後期造成麻煩的決定。沒有統一前綴，多個服務共用一個實例時無法區分誰的鍵。鍵名過長，每個鍵的名稱都佔記憶體，一千萬個鍵多三十位元組就是三百多 MB。沒有過期時間。還有用一個大 key 裝所有東西。

鍵名長度的成本常被忽略。在大量小值的場景，鍵名可能佔總記憶體的一半以上。比如一個三十位元組的鍵名配一個八位元組的時間戳。但要跟可讀性平衡，我的折衷是在程式碼裡用常數定義，讓縮寫只出現在一處。

沒有過期時間是記憶體洩漏最常見的形式。快取類的鍵一律應該有，即使業務上說永遠有效，也該設一個很長的保底，因為那個假設會隨業務演變而失效，而那時候已經累積了幾千萬個沒人記得的鍵。

最後，鍵的設計會決定日後能不能分片。一個實體一個鍵讓雜湊自然分散，而重新設計鍵意味著資料遷移，所以這值得一開始就想清楚。

## 常見追問

### 怎麼找出沒有 TTL 或即將過期的鍵？

**核心答案**：用 `SCAN` 遍歷並對每個鍵 `TTL`——**回傳 -1 表示沒有設過期時間**（-2 表示鍵不存在）。這應該做成一個定期執行的巡檢腳本，**輸出「沒有 TTL 的鍵按前綴分組的統計」**，這樣就能看出是哪一類鍵在累積。**注意不要用 `KEYS`**——那會阻塞整個伺服器。

**詳細解析**：**更有價值的是把它變成一個持續的指標而非一次性的檢查**：定期取樣（例如每小時掃描 1% 的鍵）並把「無 TTL 鍵的比例」與「各前綴的鍵數量」上報成監控指標。**這樣記憶體的成長就能被歸因到具體的鍵前綴**，而不是只看到「總記憶體在漲」。**「能歸因的指標比總量指標有價值得多」是監控設計的一個通則**——總記憶體上漲只告訴你有問題，按前綴分解的鍵數則直接指出是哪個功能。**實作上要注意取樣的成本**：`SCAN` 加逐個 `TTL` 是 N 次往返，應該用 pipeline 批次處理，並限制每次掃描的數量。

**面試回答方式**：給方法（`SCAN` 加 `TTL`，-1 表示沒設）並提醒不要用 `KEYS`。真正的加分點是把它從一次性檢查提升成**持續的指標**：定期取樣並上報「無 TTL 比例」與「各前綴的鍵數」，**讓記憶體成長能被歸因到具體前綴**。收在監控設計的通則：**能歸因的指標比總量指標有價值得多**，並補上實作要點（用 pipeline 批次、限制每次掃描量）。

### 多個服務該不該共用一個 Redis 實例？

**核心答案**：**小規模時可以，但要有明確的命名空間隔離；規模成長後應該拆開**。共用的好處是省成本與維運簡單；壞處是**故障域共享**（一個服務的大 key 或慢命令會影響所有服務）、**容量無法獨立規劃**、以及**難以歸因**（記憶體漲了不知道是誰）。

**詳細解析**：**「故障域共享」是最需要警覺的一項**。Redis 是單執行緒的，**一個服務執行了 `KEYS *` 或刪除一個大 key，所有共用實例的服務都會卡住**——而那些服務的團隊完全不知道發生了什麼。**這種跨團隊的隱性耦合在事故時特別難處理**，因為第一時間沒有人知道問題出在誰身上。**拆分的觸發訊號**是：出現過一次跨服務的影響、記憶體歸因變成常態需求、或者某個服務的用量佔比超過一半。**中間方案是「按重要性分組」**——關鍵服務用獨立實例，非關鍵的共用一個，這比「全部共用」或「每個服務一個」都務實。

**面試回答方式**：給明確立場（小規模可以但要命名空間隔離、規模成長後拆開）與三個壞處。重點展開**故障域共享**：Redis 單執行緒，一個服務的慢命令會卡住所有服務，**而那些團隊完全不知道發生了什麼**，這種跨團隊的隱性耦合在事故時特別難處理。給拆分的觸發訊號（出現過跨服務影響、歸因成為常態需求、某服務佔比過半）。收在中間方案：**按重要性分組**比「全部共用」或「每個服務一個」都務實。

### 鍵設計對叢集有什麼影響？

**核心答案**：兩方面。**分散均勻性**——鍵依 CRC16 雜湊到 16384 個槽，**只要鍵夠多且分散，分佈就會均勻**；但如果大量鍵用了同一個 hash tag（`{fixed}:...`），它們會全部落在同一個槽，造成嚴重傾斜。**跨槽操作的限制**——`MGET`、交易、Lua 腳本要求所有鍵在同一個槽，**這需要 hash tag，而 hash tag 又會影響分散**。

**詳細解析**：**這是一組直接衝突的需求**：要分散就不能用 hash tag，要一起操作就必須用。**解法是「只在真的需要一起操作的最小範圍上使用 hash tag」**——例如一個使用者的幾個相關鍵用 `{user:1000}` 綁在一起（那幾個鍵在同一個槽，但不同使用者散在不同槽），**而不是把所有使用者的所有鍵都綁在一個 tag 上**。**這個「以聚合根為單位共置」的設計，恰好與領域驅動設計中的聚合概念一致**——需要一起維持一致性的資料應該在物理上也在一起，而不同聚合之間則可以自由分散。**認出這個對應關係，就能把叢集的技術限制轉化成一個有意義的領域設計問題。**

**面試回答方式**：給兩方面影響並指出它們是**直接衝突的需求**——要分散就不能用 hash tag，要一起操作就必須用。給解法：**只在真的需要一起操作的最小範圍上使用**（一個使用者的幾個鍵綁在一起，而非所有使用者綁在一個 tag）。真正的加分點是指出**這個「以聚合根為單位共置」的設計與領域驅動設計的聚合概念一致**——需要一起維持一致性的資料在物理上也在一起，**於是叢集的技術限制轉化成了有意義的領域設計問題**。
