# 題目

用 Redis 的 `INCR` 產生分散式 ID 有什麼問題？高頻計數器該怎麼設計？

## 核心答案

`INCR` 產生 ID 的優點是**簡單、單調遞增、全域唯一**。問題有四個。**單點依賴**——Redis 不可用時無法產生 ID，整個寫入路徑掛掉。**持久化的窗口**——Redis 重啟時如果從舊的 RDB 恢復，計數器會**回退**，產生重複的 ID（**這是最危險的一個**）。**效能上限**——每個 ID 一次網路往返，單一 key 的 QPS 受限於單執行緒。**ID 可預測**——連續的整數會洩漏業務量（競爭對手可以用兩個時間點的訂單號估算你的日訂單量）。

改善的做法是**批次預分配**：客戶端用 `INCRBY key 1000` 一次取一段（例如 1000 到 1999），在本地慢慢用完再取下一段。這把往返從每個 ID 一次降到每一千個 ID 一次，也降低了對 Redis 可用性的敏感度（手上還有存量時 Redis 短暫不可用不影響）。**代價是 ID 不再全域單調遞增**（不同實例持有不同的段）且**實例重啟會浪費剩餘的段**。

高頻計數器的關鍵是**避免單一 key 成為熱點**——分片（`counter:{n}` 分成 N 個 key，讀取時加總）是標準做法。

## 詳細解析

「重啟後計數器回退」是最需要警惕的問題。如果 Redis 用 RDB 且上次快照是十分鐘前，重啟後計數器回到十分鐘前的值——接下來產生的 ID 會與那十分鐘內已經產生的重複。而 ID 重複在多數系統裡是災難性的（主鍵衝突、資料覆蓋、對帳錯亂）。**防護方式有三個**：用 AOF 的 `always` 或 `everysec`（縮小窗口但不消除）、啟動時把計數器往前跳一大段（犧牲一段 ID 換取安全）、或者根本不用 Redis 產生需要唯一性保證的 ID。**最後一個才是根本的答案**——需要強唯一性保證時，應該用資料庫的自增主鍵、UUID、或 Snowflake 這類不依賴中心化計數器的方案。

**Snowflake 類的方案值得對比**。它用「時間戳 + 機器 ID + 序號」組成 64 位元整數，完全在本地產生（不需要網路往返）、趨勢遞增、且不依賴任何中心元件。代價是需要分配機器 ID（可以用 Redis 或 ZooKeeper 在啟動時分配一次）與**依賴時鐘**（時鐘回撥會產生重複，需要偵測與處理）。在高吞吐場景下 Snowflake 明顯優於 Redis 的 `INCR`，而 Redis 只在「需要嚴格連續、無間隙」的場景（例如發票號碼）才有優勢——而那類場景通常也需要資料庫的交易保證，不該只靠 Redis。

**計數器的分片與精確度取捨**。分成 N 個 key 之後，寫入分散了但讀取要 `MGET` N 個 key 再加總——這在 N 很大時成本上升。實務上 N 取 CPU 核心數的量級（8 到 32）通常就足夠分散熱點。如果連讀取都很頻繁，可以再加一層：定時把分片加總寫進一個「快照 key」，讀取只讀那個。 代價是讀到的值有幾秒的延遲——對於「總瀏覽數」這類指標完全可以接受，對於「庫存餘量」則不行。

`INCR` 的原子性是它真正的價值。它避免了「讀取、加一、寫回」的競態，這在應用層要用鎖或 CAS 才能達成。所以即使不用它產生 ID，它仍然是計數、限流、以及各種「原子累加」場景的正確工具。

## 面試回答方式

先給 `INCR` 的優點與**四個問題**，並把**重啟後計數器回退**標為最危險的一個——RDB 恢復會讓計數器回到快照時的值，接下來的 ID 與那段時間已產生的重複，而 ID 重複在多數系統裡是災難性的。給改善做法**批次預分配**（`INCRBY` 一次取一段）與它的代價（不再全域單調、重啟浪費剩餘段）。加分點有三個：根本的答案是不用 Redis 產生需要強唯一性保證的 ID；**Snowflake 的對比**——本地產生、無往返、不依賴中心元件，代價是機器 ID 分配與時鐘回撥的處理，**高吞吐下明顯更好**；以及**計數器分片的層次**——分 N 個 key 分散寫入，讀取頻繁時再加一層定時加總的快照 key，代價是幾秒延遲，總瀏覽數可以接受但庫存餘量不行。

## 講稿

用遞增命令產生 ID 的優點是簡單、單調遞增、全域唯一。問題有四個。單點依賴、持久化的窗口、效能上限、還有 ID 可預測會洩漏業務量。

其中最危險的是重啟後計數器回退。如果用快照持久化而上次快照是十分鐘前，重啟後計數器回到十分鐘前的值，接下來產生的 ID 會跟那十分鐘內已經產生的重複。而 ID 重複在多數系統裡是災難性的。

改善的做法是批次預分配，一次取一段在本地慢慢用。這把往返從每個 ID 一次降到每一千個 ID 一次，也降低了對 Redis 可用性的敏感度。代價是 ID 不再全域單調遞增，而且實例重啟會浪費剩下的段。

但我認為根本的答案是，需要強唯一性保證的 ID 不該用 Redis 產生。應該用資料庫的自增主鍵，或是雪花演算法這類不依賴中心化計數器的方案。它用時間戳加機器 ID 加序號組成，完全在本地產生、不需要網路往返、也不依賴任何中心元件。

高頻計數器的關鍵是避免單一 key 成為熱點，分成多個 key 再加總是標準做法。如果讀取也很頻繁，可以定時把分片加總寫進一個快照 key，讀取只讀那個。代價是幾秒的延遲，對總瀏覽數可以接受，對庫存餘量就不行。

## 常見追問

### 時鐘回撥對 Snowflake 有什麼影響？

**核心答案**：可能產生**重複的 ID**。Snowflake 依賴「時間戳單調遞增」——如果系統時鐘往回調（NTP 校正、虛擬機遷移、手動調整），新產生的 ID 的時間戳部分會與之前已經用過的重疊，而同一毫秒內的序號會從頭開始，於是產生重複。標準的防護是記錄「上次產生 ID 的時間戳」並在偵測到回撥時拒絕產生（等待時鐘追上，或直接拋例外）。

**詳細解析**：**回撥的幅度決定了處理策略**。小幅回撥（幾毫秒）可以等待；大幅回撥（幾秒到幾分鐘）等待會讓服務長時間不可用，這時應該直接失敗並告警，讓維運介入——因為那通常表示機器的時間有嚴重問題。更穩健的做法是不依賴系統時鐘的絕對值：有些變體用「單調時鐘 + 啟動時取得的基準」，或者用一個持久化的「上次使用的時間戳」在啟動時恢復。這個問題提醒了一件事：任何依賴時鐘的分散式演算法都必須明確處理時鐘異常——而時鐘異常在真實環境中比想像的常見（虛擬化、容器遷移、NTP 的階躍調整）。「假設時鐘單調遞增」是分散式系統中一個危險的隱含假設。

**面試回答方式**：給機制（時間戳重疊加序號重置導致重複）與標準防護（記錄上次時間戳、偵測回撥時拒絕）。加分點是**依回撥幅度決定策略**——小幅等待、大幅直接失敗告警讓維運介入。收在一般教訓：任何依賴時鐘的分散式演算法都必須明確處理時鐘異常，而時鐘異常在虛擬化與容器環境中比想像的常見，「假設時鐘單調遞增」是一個危險的隱含假設。

### 庫存扣減能不能用 Redis 的 DECR？

**核心答案**：技術上可以且很常見，但必須理解它的邊界。`DECR` 是原子的，所以不會超賣（回傳值小於 0 就拒絕並補回）。**但 Redis 不是事實來源**——真正的庫存在資料庫裡，Redis 只是一個「快速拒絕」的前置關卡。如果 Redis 的值因為重啟、淘汰、或同步問題而與資料庫不一致，就會出現超賣或少賣。

**詳細解析**：成熟的做法是「Redis 擋流量、資料庫保正確」的兩層設計：Redis 的 `DECR` 快速擋掉絕大多數注定失敗的請求（庫存 100 件而有 10 萬個請求時，99.9% 在 Redis 這一層就被拒絕），通過的少數請求再到資料庫做真正的扣減與交易（用 `UPDATE ... SET stock = stock - 1 WHERE stock >= 1` 這種帶條件的更新保證正確性）。這樣既擋住了流量，又保證了正確性。 關鍵是**理解每一層的角色**：Redis 負責「快」，資料庫負責「對」。誤把 Redis 當成事實來源是很多超賣事故的根因——而它們通常在流量高峰時才暴露，因為那時候快取失效、實例重啟、以及各種異常最容易同時發生。

**面試回答方式**：先給明確答案（技術上可以且常見，但 Redis 不是事實來源）。重點是**兩層設計**：Redis 的 `DECR` 快速擋掉絕大多數注定失敗的請求（10 萬請求搶 100 件，99.9% 在這一層被拒），通過的少數再到資料庫做帶條件的更新保證正確。強調理解每一層的角色——Redis 負責快、資料庫負責對。收在警示：誤把 Redis 當成事實來源是很多超賣事故的根因，而它們通常在流量高峰才暴露。

### 計數器需要精確時該怎麼做？

**核心答案**：**看「精確」的定義**。如果是「不能少算也不能多算」（例如計費用的 API 呼叫次數），`INCR` 本身是精確的——問題出在持久化（重啟可能丟失最近的遞增）與複製（主從切換可能回退）。真正需要精確時，計數應該落在資料庫的交易裡，Redis 只當作加速的快照。如果是「數量級正確即可」（瀏覽數、按讚數），Redis 加定期落庫是完全合理的方案。

**詳細解析**：「定期落庫」的實作有一個容易做錯的地方：直接把 Redis 的值覆蓋寫進資料庫，會在「落庫後 Redis 又被遞增、但落庫前的增量已經被寫過」時重複計算或遺漏。正確的做法是用「增量」而非「總量」——Redis 存一個「自上次落庫以來的增量」，落庫時原子地取出並清零（`GETSET` 或 Lua），然後在資料庫裡 `UPDATE ... SET count = count + delta`。這樣即使落庫失敗重試，只要取出與清零是原子的，就不會重複。 更穩健的還要處理「取出成功但寫資料庫失敗」的情況——那個增量會遺失，所以應該先寫進一個持久的中間狀態（或者接受這個小機率的損失，取決於精確度要求）。這個「用增量而非總量同步」的模式在很多資料同步場景都適用，因為它讓操作變成可交換的，順序與重複都不影響最終結果。

**面試回答方式**：先釐清**「精確」的定義**——`INCR` 本身精確，問題在持久化與複製；真正需要精確就該落在資料庫交易裡。展開**定期落庫的正確做法**：**用增量而非總量**，Redis 存「自上次落庫以來的增量」，原子地取出並清零後在資料庫做加法——這樣重試不會重複。加分點是提出「取出成功但寫庫失敗」的殘留問題與處理方向。收在通用模式：用增量而非總量同步，讓操作可交換，順序與重複都不影響最終結果。
