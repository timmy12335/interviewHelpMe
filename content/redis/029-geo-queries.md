# 題目

Redis 的 GEO 是怎麼實作的？它適合什麼場景、不適合什麼？

## 核心答案

GEO 不是一個獨立的資料類型，它就是有序集合。`GEOADD` 把經緯度用 GeoHash 演算法編碼成一個 52 位元的整數，當作有序集合的分數存進去；成員名就是地點的識別碼。所以 `GEOADD` 之後用 `ZRANGE` 也能看到資料，`ZREM` 也能刪除成員。

GeoHash 的核心是**把二維座標交錯編碼成一維**：把經度與緯度各自二分（每次記錄落在哪一半，得到一串位元），然後把兩串位元交錯合併。這樣做的關鍵性質是「地理上接近的點，編碼後的數值也接近」——於是「找附近的點」變成有序集合上的範圍查詢，而那是 O(log N)。

主要命令是 `GEOSEARCH`（Redis 6.2 起，取代舊的 `GEORADIUS`）——支援以某個點或某個成員為中心，用**半徑或矩形**搜尋，並可以排序與限制數量；`GEODIST` 算兩點距離；`GEOPOS` 取回座標。

適合的是「附近的人／店家／司機」這類中小規模的鄰近查詢；不適合複雜的空間查詢（多邊形內、路網距離、空間 join），那需要 PostGIS 這類專門的空間資料庫。

## 詳細解析

「二維降一維」是 GeoHash 的核心思想，也是它的限制來源。交錯編碼讓大部分接近的點編碼也接近，**但邊界情況會失效**——兩個實際距離很近但分屬不同大格子的點，編碼可能差很多（例如剛好在經度分界的兩側）。所以 Redis 的實作在搜尋時會同時查詢中心格子與周圍的八個相鄰格子，再對結果做精確的距離計算與過濾。這解釋了為什麼 GEO 的搜尋不是單純的一次範圍查詢，而是九次範圍查詢加上過濾。

**精度與儲存的取捨**：52 位元的編碼在地球尺度上的精度約為**幾十公分**，對絕大多數應用綽綽有餘。而它「就是有序集合」這個事實帶來了實用的好處——可以用 `ZCARD` 算數量、用 `ZSCAN` 遍歷、也可以和其他有序集合的操作組合。代價是它繼承了有序集合的所有特性，包括「所有資料在一個 key 裡」——一個裝了一百萬個地點的 GEO key 是一個大 key，會有前面提過的所有問題。

**分片是實務上必須考慮的**。全國的司機位置放在一個 key 裡會太大且成為熱點；**依城市或依網格分 key**（`geo:drivers:taipei`、`geo:drivers:grid:23_121`）是標準做法。代價是跨區的查詢要查多個 key 並合併——但那正好對應了業務上「使用者只關心附近」的現實，所以通常不是問題。

更新頻率高的場景要注意寫入成本。司機位置每秒更新一次、一萬個司機就是每秒一萬次 `GEOADD`——每次都是有序集合的插入或更新（O(log N)），加上可能的複製與持久化開銷。這種場景下常見的做法是降低更新頻率（只在移動超過一定距離時更新）或**分片降低單 key 的大小**。

## 面試回答方式

先破除一個常見誤解——GEO 不是獨立的資料類型，它就是有序集合，經緯度被 GeoHash 編碼成 52 位元整數當作分數。解釋 GeoHash 的核心：把二維座標交錯編碼成一維，讓地理上接近的點編碼也接近，於是鄰近查詢變成範圍查詢。加分點有三個：**邊界情況會失效**（剛好在分界兩側的點編碼差很多），所以 Redis 實際上會查中心加周圍八個格子再做精確過濾——這解釋了為什麼不是單純一次範圍查詢；它「就是有序集合」帶來的好處與代價（可以用 ZSET 的命令組合，但也繼承了大 key 的所有問題）；以及**分片是實務上必須的**（依城市或網格分 key），而那正好對應「使用者只關心附近」的業務現實。最後給邊界：複雜空間查詢（多邊形、路網距離）要用 PostGIS。

## 講稿

GEO 不是一個獨立的資料類型，它就是有序集合。經緯度被編碼成一個五十二位元的整數，當作有序集合的分數存進去。所以加完之後用一般的有序集合命令也看得到資料。

編碼的核心是把二維座標交錯成一維。把經度跟緯度各自二分，每次記錄落在哪一半得到一串位元，然後把兩串交錯合併。關鍵性質是地理上接近的點，編碼後的數值也接近。於是找附近的點就變成有序集合上的範圍查詢。

不過這個降維有邊界問題。兩個實際距離很近但分屬不同大格子的點，編碼可能差很多。所以 Redis 在搜尋的時候會同時查中心格子跟周圍的八個相鄰格子，再對結果做精確的距離計算與過濾。所以它不是單純的一次範圍查詢。

實務上分片是必須考慮的。全國的位置放在一個 key 裡會太大而且成為熱點，依城市或依網格分 key 是標準做法。跨區查詢要查多個 key 並合併，但那正好對應了業務上使用者只關心附近的現實。

適合的是附近的人或店家這類中小規模的鄰近查詢。複雜的空間查詢像是多邊形內或路網距離，需要專門的空間資料庫。

## 常見追問

### GEOSEARCH 的效能瓶頸在哪？

**核心答案**：在**候選集的大小**。搜尋會先用 GeoHash 的範圍查詢取出九個格子內的所有成員，再對每一個計算精確距離並過濾——所以成本與「格子內的點數」成正比，而不是與「結果數」成正比。在密集區域（市中心）搜尋半徑一公里，候選集可能有幾萬個點，即使最終只回傳十個。 `COUNT` 參數可以限制回傳數量但**不能減少候選集的計算**（除非加上 `ANY` 選項，那會在找到足夠數量後提前停止，代價是結果不保證是最近的）。

**詳細解析**：這與大 key 的問題疊加起來會很嚴重——一個裝了一百萬個點的 GEO key，在密集區域的一次搜尋可能要遍歷數萬個成員，而那是在單執行緒上執行的，會阻塞所有其他請求。所以「分片」不只是為了記憶體，更是為了控制單次查詢的候選集大小。 實務上的做法是依地理網格分 key，讓每個 key 的點數控制在幾千到幾萬。**另一個做法是限制搜尋半徑**——大半徑的搜尋成本呈平方成長，業務上通常也不需要（誰會關心 50 公里外的餐廳）。「用業務約束限制技術成本」是一個很有效的思路。

**面試回答方式**：給精確的瓶頸——成本與候選集大小成正比而非結果數，並用「市中心搜尋一公里可能候選數萬個但只回傳十個」說明。指出 `COUNT` 不減少計算除非用 `ANY`（代價是結果不保證最近）。加分點是與**單執行緒疊加的嚴重性**——一次慢搜尋阻塞所有請求，所以分片不只為了記憶體更為了控制候選集大小。收在思路：**用業務約束限制技術成本**（限制搜尋半徑，因為業務上也不需要 50 公里外的結果）。

### 位置資料的隱私該怎麼處理？

**核心答案**：三個原則。**最小精度**——不要存超過業務需要的精度；顯示「附近 500 公尺內有 3 位司機」不需要存到公分級。**保留期限**——歷史軌跡應該有明確的保留期並自動刪除（Redis 的 TTL 只能設在整個 key 上，所以分時間段存 key 是實用的做法）。**存取控制**——位置是敏感個資，查詢應該有授權檢查與稽核記錄。

**詳細解析**：「軌跡資料的敏感度遠高於單點位置」值得特別注意。單一時刻的位置只說明「此刻在這裡」，但一串軌跡能推斷出住家、工作地點、生活習慣、甚至社交關係——即使去除了身分識別，軌跡本身往往就足以重新識別出個人（研究顯示少數幾個時空點就能唯一識別多數人）。所以「匿名化的軌跡資料」通常不是真的匿名。 實務上的處理包括：**降低時間與空間解析度**、只保留聚合結果而非原始軌跡、以及**明確的資料生命週期管理**。在設計任何涉及位置的功能時，應該預設把資料當成高敏感度處理，而不是等到合規審查才回頭補。

**面試回答方式**：給三個原則（最小精度、保留期限、存取控制）並各配具體做法。真正的加分點是強調軌跡資料的敏感度遠高於單點位置——一串軌跡能推斷住家、工作地、生活習慣，而且少數幾個時空點就足以重新識別個人，所以「匿名化的軌跡」通常不是真的匿名。收在態度：設計涉及位置的功能時預設把資料當成高敏感度處理，而非等合規審查才補。

### 什麼時候該用專門的空間資料庫？

**核心答案**：三種需求。**複雜的空間關係查詢**——「這個點在不在這個多邊形（配送範圍）裡」「這兩個區域有沒有重疊」，Redis GEO 只支援圓形與矩形。**路網距離而非直線距離**——「開車 10 分鐘能到的範圍」需要路網資料與路徑演算法。**空間與屬性的複合查詢**——「附近三公里、評分四星以上、目前營業中的餐廳」，Redis 只能先做空間篩選再逐一過濾，而空間資料庫可以用複合索引一次完成。

**詳細解析**：「先空間篩選再過濾」的效率問題值得展開。用 Redis 做複合查詢時，通常是先 `GEOSEARCH` 取出附近所有店家（可能幾千個），再對每一個去查它的屬性並過濾——那是幾千次額外的查詢或一次大的 `MGET`。如果過濾條件很嚴格（只有 5 家符合），這個做法浪費了 99% 的工作。 PostGIS 這類資料庫可以用 GiST 索引結合屬性索引，在一次查詢中完成。判斷的訊號是「篩選後的結果遠小於候選集」——那代表過濾條件應該被下推到索引層，而 Redis 做不到這件事。實務上常見的折衷是用 Redis 做粗篩（快速排除大部分）、用資料庫做精確查詢，兩者各自發揮所長。

**面試回答方式**：給三種需求並各配具體例子。重點展開「先空間篩選再過濾」的效率問題——取出幾千個候選再逐一查屬性，過濾條件嚴格時浪費 99% 的工作，而空間資料庫可以用複合索引一次完成。給出判斷訊號：**篩選後結果遠小於候選集**，代表過濾應該下推到索引層。收在實務折衷：**Redis 做粗篩、資料庫做精確查詢**。
