# 題目

Jedis 與 Lettuce 差在哪？連線池該怎麼設定？

## 核心答案

Jedis 是同步阻塞的，且它的連線不是執行緒安全的——所以必須用連線池，每個執行緒借一條連線用完歸還。**Lettuce 基於 Netty，連線是執行緒安全的**，多個執行緒可以共用同一條連線（命令會被序列化到同一個 channel 上），**所以預設不需要連線池**；它同時支援同步、非同步與反應式三種 API。**Spring Boot 2 之後預設用 Lettuce。**

連線池的設定核心是「並行請求數 × 每個請求的 Redis 呼叫次數」——一個處理 200 並行請求、每個請求呼叫 3 次 Redis 的服務，理論上需要的並行連線遠少於 600（因為每次呼叫只佔用極短的時間），**實務上 `maxTotal` 設在 20 到 50 通常就夠**。設太大的壞處是每條連線在 Redis 端都佔用資源（`maxclients` 有上限、每個連線有輸出緩衝）。

**必須設定的是 `maxWaitMillis`**——借不到連線時等多久。**預設的無限等待是危險的**：Redis 慢的時候，所有請求執行緒會全部卡在等連線上，服務完全癱瘓而不是快速失敗。

## 詳細解析

「Lettuce 共用一條連線」有一個重要的例外：**阻塞命令**（`BLPOP`、`XREAD BLOCK`）與**交易**（`MULTI`／`EXEC`）會獨佔連線——一個執行緒在 `BLPOP` 上阻塞時，共用同一條連線的其他命令也會被卡住。所以用到這些命令時仍然需要專用連線或連線池。這是「Lettuce 不需要連線池」這個說法最常見的例外，也是實務上踩到的坑。

**Lettuce 的自動重連需要理解**。連線斷開時它會自動重連並重放（可設定）——**但重放的語意需要小心**：一個「已經送出但沒收到回應」的命令，重放後可能被執行兩次。`autoReconnect` 與 `cancelCommandsOnReconnectFailure` 這些選項控制了行為，預設值傾向可用性而非精確性。對於非冪等的命令（`INCR`、`LPUSH`），這個重放可能造成重複執行——所以關鍵的非冪等操作應該有自己的冪等保護。

逾時設定是最常被忽略的一項。連線逾時（建立連線多久算失敗）與命令逾時（送出命令後等回應多久）**都應該明確設定且不能太長**。預設的命令逾時（Lettuce 是 60 秒）在 Redis 卡住時會讓請求執行緒被佔用一分鐘——在高並行下這足以耗盡整個應用的執行緒池。合理的值應該是「Redis 正常回應時間的幾十倍」而非「一個保守的大數字」，因為超過那個範圍就代表 Redis 有問題，快速失敗比繼續等更好。

叢集模式下的客戶端還要維護拓撲。它需要知道哪個槽在哪個節點上，並在收到 `MOVED` 時更新。**拓撲的刷新策略要設定**——Lettuce 預設不會定期刷新，只在收到重導向時被動更新；在節點變動頻繁的環境下應該開啟定期刷新與自適應刷新（`ClusterTopologyRefreshOptions`），否則客戶端可能長時間持有過期的拓撲並不斷重導向。

## 面試回答方式

先給兩者的核心差別——Jedis 同步且連線非執行緒安全（必須用池），Lettuce 基於 Netty 且連線執行緒安全（預設不需要池），並指出 Spring Boot 2 之後預設用 Lettuce。給連線池設定的核心公式與實務值（`maxTotal` 20 到 50 通常夠），並強調 `maxWaitMillis` 必須設定——預設的無限等待在 Redis 慢時會讓所有請求執行緒卡住、服務完全癱瘓而非快速失敗。加分點有三個：「Lettuce 不需要連線池」的例外——阻塞命令與交易會獨佔連線，共用時會卡住其他命令，這是實務上最常踩的坑；命令逾時預設 60 秒在高並行下足以耗盡應用的執行緒池，合理值應該是正常回應時間的幾十倍而非一個保守的大數字；以及叢集模式下要設定拓撲刷新策略，否則客戶端可能長時間持有過期拓撲。

## 講稿

Jedis 是同步阻塞的，而且它的連線不是執行緒安全的，所以必須用連線池。Lettuce 基於 Netty，連線是執行緒安全的，多個執行緒可以共用同一條，所以預設不需要連線池。Spring Boot 2 之後預設用 Lettuce。

不過共用連線有一個重要的例外，阻塞命令跟交易會獨佔連線。一個執行緒卡在阻塞讀取上的時候，共用同一條連線的其他命令也會被卡住。所以用到這些命令時仍然需要專用連線。這是實務上最常踩的坑。

連線池的設定我用並行請求數乘以每個請求的呼叫次數來估，但實務上最大值設在二十到五十通常就夠，因為每次呼叫只佔用極短的時間。

必須設定的是取連線的等待逾時。預設的無限等待很危險，Redis 慢的時候所有請求執行緒會全部卡在等連線上，服務完全癱瘓而不是快速失敗。

命令逾時也常被忽略。Lettuce 預設是六十秒，在 Redis 卡住的時候會讓請求執行緒被佔用一分鐘，高並行下這足以耗盡整個應用的執行緒池。合理的值應該是正常回應時間的幾十倍，因為超過那個範圍就代表有問題，快速失敗比繼續等更好。

## 常見追問

### 連線池的指標該監控哪些？

**核心答案**：四個。**活躍連線數與閒置連線數**——活躍長期等於 `maxTotal` 表示池已飽和。**借用等待時間**——這是最直接的訊號，等待時間上升表示池不夠或 Redis 變慢。**借用失敗次數**（逾時取不到連線）——出現就代表已經在丟請求了。**連線建立與銷毀的次數**——頻繁的建立銷毀表示池的 `minIdle` 設得太低或 `maxIdle` 太小，每次都要重新握手。

**詳細解析**：「借用等待時間」與「命令執行時間」要分開量測，這與執行緒池那題的「排隊時間 vs 執行時間」是同一個道理。等待時間長表示連線不夠（加池或減少呼叫次數），執行時間長表示 Redis 慢（查 SLOWLOG 或網路）——兩者的處理方式完全不同，而只看「Redis 呼叫總耗時」無法區分。很多「Redis 變慢」的報告，實際上是連線池不足造成的排隊，而 Redis 端的指標完全正常。這類「觀察到的延遲不在被觀察的元件上」的問題，需要每一層都有自己的量測才能定位。

**面試回答方式**：給四個指標並各配判讀方式。重點強調「借用等待時間」與「命令執行時間」要分開量測——等待長是連線不夠、執行長是 Redis 慢，處理方式完全不同而只看總耗時無法區分。給出實務觀察：很多「Redis 變慢」的報告實際上是連線池不足造成的排隊，而 Redis 端指標完全正常。收在原則：觀察到的延遲不一定在被觀察的元件上，需要每一層都有自己的量測。

### 為什麼不建議把連線池設得很大？

**核心答案**：三個理由。**Redis 端的資源**——每個連線在 Redis 端佔用記憶體（輸入輸出緩衝區），`maxclients` 也有上限（預設 10000），大量應用實例乘以大池就可能撞到上限。**沒有收益**——Redis 是單執行緒的，一百條連線與二十條連線的吞吐上限是一樣的（都受限於那一個執行緒），更多連線只是更多排隊。**掩蓋問題**——池大了之後，「連線不夠」的症狀消失了，但根因（Redis 慢或呼叫次數太多）還在，只是變成了 Redis 端的排隊。

**詳細解析**：第二點是最反直覺也最重要的。在多執行緒的資料庫上，更多連線確實能提高並行度；但 Redis 的命令執行是單執行緒的，所有連線的請求最終都排在同一個佇列上。所以連線池的大小只需要「足以填滿那個佇列」，再多就純粹是浪費。 實務上二十到五十條連線已經足以讓 Redis 的單執行緒滿載。這個「瓶頸在下游的單一資源上時，上游加大並行沒有意義」的判斷，適用於很多場景——資料庫連線池、下游服務的並行呼叫、以及執行緒池的大小。認出瓶頸的位置，比調整任何參數都重要。

**面試回答方式**：給三個理由。重點展開第二點——Redis 是單執行緒的，一百條連線與二十條的吞吐上限一樣，所有連線的請求最終排在同一個佇列上，所以池只需要足以填滿那個佇列。加分點是把它一般化：瓶頸在下游的單一資源上時，上游加大並行沒有意義，這適用於資料庫連線池、下游並行呼叫、執行緒池大小。收在原則：認出瓶頸的位置比調整任何參數都重要。

### 客戶端該怎麼處理 Redis 短暫不可用？

**核心答案**：**快速失敗加降級**，而不是重試到底。具體是：**設短的命令逾時**（幾百毫秒到一兩秒）、有限次數的重試且只重試冪等操作、**加熔斷器**（連續失敗後直接短路一段時間，不再嘗試）、以及**明確的降級路徑**（快取讀不到就直接查資料庫、限流器不可用就本地限流或放行）。

**詳細解析**：「不加熔斷的重試會放大故障」是關鍵。Redis 慢的時候，每個請求都重試三次意味著**負載變成三倍**，而那正是 Redis 最不需要的時候。熔斷器讓系統在下游明顯故障時停止嘗試，給它恢復的空間——這與限流保護自己是互補的（一個限制輸入、一個限制輸出）。降級路徑的設計比熔斷本身更重要：熔斷之後做什麼？快取層可以直接回源（代價是資料庫壓力上升，所以資料庫也要有自己的保護）；而如果沒有降級路徑，熔斷只是把「慢」變成「錯」——那未必更好。所以引入熔斷時必須同時回答「斷開之後怎麼辦」，這個問題沒有答案的話，熔斷本身也沒有意義。

**面試回答方式**：給四個手段（短逾時、有限重試且只重試冪等、熔斷、降級路徑）。重點展開**不加熔斷的重試會放大故障**——每個請求重試三次讓負載變三倍，而那正是 Redis 最不需要的時候。真正的加分點是強調降級路徑的設計比熔斷本身更重要：熔斷之後做什麼？沒有降級路徑的話，熔斷只是把「慢」變成「錯」，未必更好。收在要求：引入熔斷時必須同時回答「斷開之後怎麼辦」。
