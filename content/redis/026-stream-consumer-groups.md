# 題目

Redis Stream 解決了什麼問題？它與 List 和 Pub/Sub 做訊息傳遞差在哪？

## 核心答案

Stream（Redis 5 引入）是一個**只追加的訊息日誌**，每筆訊息有一個單調遞增的 ID（預設是「毫秒時間戳 - 序號」）。它針對前兩種做法的缺陷而設計。

**相對於 Pub/Sub**：Pub/Sub 是**發送即忘**——沒有持久化、沒有 ack、訂閱者離線期間的訊息永遠丟失、也不知道有沒有人收到。Stream **持久化訊息**（隨 RDB/AOF 一起保存）、支援**從任意位置重新讀取**、並提供 **ack 機制**。

**相對於 List**：用 `LPUSH` 加 `BRPOP` 做佇列的問題是**訊息一被取走就從資料結構中消失**——消費者處理到一半崩潰，訊息就丟了；而且**多個消費者只能競爭同一批訊息，無法做「多組消費者各自消費全部」的廣播**。Stream 的**消費者群組**同時支援兩者：同一群組內的消費者分擔訊息（競爭），不同群組各自看到全部訊息（廣播）。

核心機制是 **PEL（Pending Entries List）**——訊息被 `XREADGROUP` 讀出後進入待處理清單，**直到 `XACK` 才移除**。消費者崩潰時，訊息還在 PEL 裡，可以用 `XPENDING` 查看、用 `XCLAIM` 或 `XAUTOCLAIM` 轉移給別的消費者。

## 詳細解析

**PEL 是 Stream 可靠性的核心，也是最需要理解的部分**。它記錄了「誰讀了哪些訊息、讀了多久、投遞了幾次」。**沒有 `XACK` 的訊息會一直留在 PEL 裡**——如果消費者有 bug 導致從不 ack，PEL 會無限成長並佔用記憶體。**所以必須有一個處理「卡住的訊息」的機制**：定期用 `XAUTOCLAIM` 把超過閒置時間的訊息轉給其他消費者，並對「投遞次數超過閾值」的訊息做死信處理（Redis 沒有內建死信佇列，要自己實作）。

**Stream 的長度需要主動管理**。它是只追加的，不會自動刪除舊訊息——**必須用 `XADD` 的 `MAXLEN` 或 `MINID` 參數修剪**（帶 `~` 的近似修剪效率更好，因為它只在節點邊界修剪）。**忘記修剪是 Stream 用法中最常見的記憶體問題**：一個每秒一千筆訊息的 Stream，一天就是八千多萬筆。

**與 Kafka 的差別要說清楚**。Stream 沒有**分區**（一個 Stream 就是一個有序的日誌，要並行只能靠消費者群組內的多個消費者，但那樣就失去了全域順序）、沒有**跨節點的複製保證**（Redis 的主從複製是非同步的，主節點故障可能丟失訊息）、也沒有**長期保留與重放的儲存設計**（Redis 是記憶體資料庫，保留大量歷史訊息成本很高）。**所以它適合的是「輕量、低延遲、量不大」的訊息場景**——任務佇列、事件通知、短期的變更流；**不適合作為系統的事實來源或需要長期保留的事件日誌**。

**選型的實用判準是「訊息丟失的後果」與「保留期需求」**。丟了會出事、或需要保留數天以上，就該用 Kafka 或 RabbitMQ；只是內部的任務分派且已經有 Redis，Stream 是一個成本很低的選擇——**不引入新的中介軟體本身就是一個實在的好處**。

## 面試回答方式

先給 Stream 的定位（只追加的訊息日誌、單調遞增 ID），再**分別對比 Pub/Sub 與 List**：前者發送即忘、離線就丟；後者訊息取走就消失、崩潰會丟，且無法做廣播。給出**消費者群組同時支援競爭與廣播**這個關鍵能力。然後把 **PEL 講成可靠性的核心**——訊息讀出後進入待處理清單直到 ack，消費者崩潰時可以用 `XCLAIM` 轉移。加分點有三個：**PEL 會無限成長**（消費者從不 ack 時），所以必須有 `XAUTOCLAIM` 加死信處理的機制；**Stream 必須主動修剪**，忘記是最常見的記憶體問題；以及**與 Kafka 的三個差別**（沒有分區、複製非同步可能丟訊息、不適合長期保留），由此給出判準：**丟了會出事或需要長期保留就用 Kafka，內部任務分派且已有 Redis 就用 Stream**。

## 講稿

Stream 是一個只追加的訊息日誌，每筆訊息有一個單調遞增的 ID。它針對前兩種做法的缺陷而設計。

相對於發布訂閱，那個是發送即忘，沒有持久化、沒有確認、訂閱者離線期間的訊息永遠丟失。Stream 會持久化，支援從任意位置重新讀取，而且有確認機制。

相對於用清單做佇列，問題是訊息一被取走就從資料結構中消失，消費者處理到一半崩潰訊息就丟了。而且多個消費者只能競爭同一批訊息，沒辦法做多組消費者各自消費全部的廣播。Stream 的消費者群組同時支援這兩種。

核心機制是待處理清單。訊息被讀出後進入這個清單，直到確認才移除。消費者崩潰的時候訊息還在裡面，可以查看並轉移給別的消費者。

有兩個實務上必須處理的事。第一，沒有確認的訊息會一直留著，所以要定期把超過閒置時間的訊息轉給其他消費者，並對投遞次數太多的做死信處理。第二，Stream 不會自動刪除舊訊息，必須主動修剪，忘記修剪是最常見的記憶體問題。

## 常見追問

### Stream 的訊息會丟失嗎？

**核心答案**：**會，在三種情況下**。**主從切換時**——Redis 的複製是非同步的，主節點確認了 `XADD` 但還沒複製到從節點就故障，那些訊息就丟了。**持久化的窗口**——AOF 的 `everysec` 策略最多丟一秒的資料，RDB 則可能丟更多。**記憶體不足被淘汰**——如果設定了 `maxmemory-policy` 為會淘汰資料的策略，Stream 也可能被淘汰（**應該用 `noeviction` 或確保 Stream 的鍵不會被選中**）。

**詳細解析**：**「Redis 的複製是非同步的」是所有可靠性討論的起點**。`WAIT` 命令可以要求「等待 N 個從節點確認」，但它**不是強一致的保證**——它只是等待，不會阻止已經寫入主節點的資料在故障時丟失（如果 N 個從節點都沒收到）。**所以用 Redis 做「絕對不能丟」的訊息傳遞，本質上是不合適的。** 務實的做法是：**接受可能丟失，並在業務層設計補償**（例如訊息的來源仍然是資料庫，Stream 只是加速通知；丟了的話定時任務會補上）。**這個「Redis 作為加速層而非事實來源」的定位，適用於 Redis 的幾乎所有用法。**

**面試回答方式**：給三種丟失情況（主從切換的非同步複製、持久化窗口、記憶體淘汰）。強調**「複製是非同步的」是所有可靠性討論的起點**，並澄清 `WAIT` 不是強一致保證。收在務實立場：**用 Redis 做絕對不能丟的訊息本質上不合適**，應該接受可能丟失並在業務層補償——而**「Redis 作為加速層而非事實來源」的定位適用於它的幾乎所有用法**。

### 消費者群組的訊息順序有什麼保證？

**核心答案**：**單一消費者內部有序，群組整體無序**。同一群組的多個消費者各自拿到不同的訊息並行處理，**完成的順序不確定**。所以「同一個實體的操作必須依序處理」這類需求，不能靠群組內的多消費者達成——**要嘛用單一消費者（犧牲吞吐），要嘛依鍵分流到多個 Stream**（每個 Stream 一個消費者，同鍵的訊息進同一個 Stream）。

**詳細解析**：**「依鍵分流」正是 Kafka 分區在做的事**，只是 Redis 需要自己實作——生產端用實體 ID 的雜湊決定寫進哪個 Stream（`stream:orders:0` 到 `stream:orders:7`），消費端每個 Stream 配一個消費者。**這樣同鍵有序、不同鍵並行**，是「有序並行處理」的標準解法。**要注意分流數一旦決定就難以改變**——增加 Stream 數會讓雜湊結果改變，同一個鍵可能落到不同的 Stream 而破壞順序。**這與 Kafka 增加分區的問題完全相同**，處理方式也一樣：一開始就開足夠多的分流，或者接受重新分流期間的短暫無序。

**面試回答方式**：給精確的保證範圍（單一消費者內有序、群組整體無序）與兩個解法（單一消費者、依鍵分流）。展開**依鍵分流正是 Kafka 分區在做的事**，並描述具體做法（生產端雜湊決定 Stream、消費端一對一）。加分點是指出**分流數難以改變**——增加會讓雜湊結果改變而破壞順序，這與 Kafka 增加分區的問題相同，處理方式也一樣。

### 什麼時候該用 Stream，什麼時候該用真正的訊息佇列？

**核心答案**：判準有三個。**訊息丟失的後果**——不能丟就不該用 Redis（非同步複製）。**保留期與資料量**——需要保留數天或數 TB 就不該用（記憶體成本）。**是否需要複雜的路由與投遞語意**——扇出、主題過濾、優先權、延遲投遞這些 Stream 都沒有內建。**三個都是「否」的話，Stream 是很好的選擇**，尤其在已經有 Redis 的系統裡。

**詳細解析**：**「不引入新中介軟體」的價值常被低估**。每個新的中介軟體都帶來維運成本（部署、監控、備份、升級、故障處理）、學習成本、以及一個新的故障點。**在團隊規模小或訊息量不大的情況下，用已有的 Redis 做 Stream 常常是正確的工程判斷**，即使 Kafka 在紙面上更「專業」。**反過來，當訊息成為系統的核心（事件驅動架構、事件溯源、需要重放歷史）時，用 Redis 硬撐的代價會迅速超過引入 Kafka 的成本。** **判斷的時機訊號是：開始需要自己實作死信、重放、分區管理、或監控消費延遲時**——那些都是專門的訊息系統已經解決的問題，自己重做一遍是明顯的訊號。

**面試回答方式**：給三個判準（丟失後果、保留期與資料量、路由與投遞語意的複雜度）。真正的加分點是**強調「不引入新中介軟體」的價值**——每個新元件帶來維運、學習、與新的故障點，團隊小或量不大時用已有的 Redis 常是正確判斷。收在切換的時機訊號：**開始需要自己實作死信、重放、分區管理、監控消費延遲時**，那些都是專門系統已解決的問題，自己重做一遍就是該換的訊號。
