# 題目

Redis 的預設設定有哪些安全風險？該怎麼加固？

## 核心答案

Redis 的設計前提是「**運行在可信的內部網路**」，所以預設幾乎沒有安全機制。主要風險有五類。

**無認證**——舊版本預設沒有密碼；即使有 `requirepass`，那也只是一個共享密碼，沒有使用者概念。**綁定所有介面**——設定不當時 Redis 監聽 0.0.0.0，任何能連到的人都能操作。**危險指令**——`FLUSHALL`（清空全部）、`KEYS`（阻塞）、`CONFIG`（改設定）、`DEBUG`、以及最危險的 `CONFIG SET dir` 加 `SAVE` 組合（可以把 RDB 寫到任意路徑，這是「未授權的 Redis 導致伺服器被入侵」的經典手法——寫入 SSH 授權金鑰或定時任務檔案）。沒有傳輸加密（Redis 6 才支援 TLS）。**Lua 腳本的能力**——腳本能執行任意 Redis 命令。

加固的核心措施：**保護模式**（Redis 3.2 起預設開啟，沒有設密碼且綁定所有介面時只接受本機連線）、**綁定內網位址**、**設定強密碼或用 ACL**、**重新命名或停用危險指令**（`rename-command`）、**開啟 TLS**、以及**網路層隔離**（安全群組或防火牆只允許應用伺服器連入）。

## 詳細解析

「未授權存取導致伺服器淪陷」的攻擊鏈值得完整理解，因為它說明了為什麼「只是一個快取」也需要認真保護。攻擊者連上沒有密碼的 Redis 後：`CONFIG SET dir /root/.ssh` 改變工作目錄、`CONFIG SET dbfilename authorized_keys` 改變檔名、`SET x "<公鑰>"` 寫入資料、`SAVE` 把它寫成檔案——於是攻擊者的 SSH 公鑰被寫進了目標主機的授權檔案。同樣的手法可以寫 crontab 或 web 目錄下的 webshell。這不是理論上的風險，是大量真實入侵事件的手法。

**ACL（Redis 6）是比 `requirepass` 大得多的進步**。它提供了多使用者、每個使用者的命令白名單／黑名單、以及鍵模式的限制——例如建立一個「只能對 `cache:*` 執行讀寫、不能執行任何管理命令」的應用專用使用者。這讓「最小權限原則」在 Redis 上第一次成為可能。 實務上應該為每個服務建立獨立的 ACL 使用者，而不是所有服務共用一個密碼——這樣既能限制權限，也能在稽核日誌中知道是誰做的。

重新命名危險指令的做法有其限制。`rename-command FLUSHALL ""` 可以停用它，`rename-command CONFIG a1b2c3` 可以改名。但這是一個模糊化的手段而非真正的權限控制——知道新名字的人仍然能用，而且它讓運維工具與監控可能失效。有了 ACL 之後，用權限限制比改名乾淨得多（`ACL SETUSER app -config -flushall`）。改名的做法主要留給無法升級到 Redis 6 的舊環境。

最重要的一層仍然是網路隔離。所有應用層的安全措施都可能被繞過或設定錯誤，而「Redis 只能被應用伺服器連到」是一個結構性的防護。在雲端環境用安全群組、在 Kubernetes 用 NetworkPolicy、在傳統機房用防火牆——這一層做對了，即使 Redis 本身的設定有疏漏，暴露面也被限制住了。縱深防禦的價值正在於此：不依賴任何單一層次的正確性。

## 面試回答方式

先指出 Redis 的設計前提是**運行在可信的內部網路**，所以預設幾乎沒有安全機制。給**五類風險**並把 **`CONFIG SET dir` 加 `SAVE` 的組合**特別展開——**完整說出攻擊鏈**（改工作目錄與檔名、寫入公鑰、`SAVE` 落檔，於是攻擊者的 SSH 金鑰進入授權檔案），並強調這不是理論風險而是大量真實入侵的手法，這說明了為什麼「只是一個快取」也要認真保護。給加固措施。加分點有三個：ACL 讓最小權限原則第一次在 Redis 上成為可能，應該為每個服務建立獨立使用者而非共用密碼；重新命名危險指令是模糊化而非權限控制，有 ACL 之後用權限限制更乾淨；以及**最重要的一層是網路隔離**——它是結構性的防護，不依賴任何單一層次的正確性正是縱深防禦的價值。

## 講稿

Redis 的設計前提是運行在可信的內部網路，所以預設幾乎沒有安全機制。

主要風險有五類。無認證、綁定所有介面、危險指令、沒有傳輸加密、還有腳本的能力。

其中最危險的是修改設定加上保存的組合，我想完整說一下這個攻擊鏈。攻擊者連上沒有密碼的 Redis 之後，先把工作目錄改成某個使用者的 SSH 目錄、把檔名改成授權金鑰檔、寫入自己的公鑰、然後執行保存。於是攻擊者的公鑰被寫進了目標主機的授權檔案，可以直接登入。同樣的手法可以寫定時任務或網頁目錄下的後門。這不是理論風險，是大量真實入侵事件的手法。所以就算只是一個快取，也需要認真保護。

Redis 6 的存取控制清單是很大的進步。它提供多使用者、每個使用者的命令白名單、還有鍵模式的限制。這讓最小權限原則第一次在 Redis 上成為可能。我會為每個服務建立獨立的使用者，而不是所有服務共用一個密碼。

不過最重要的一層仍然是網路隔離。所有應用層的措施都可能被繞過或設定錯誤，而 Redis 只能被應用伺服器連到是一個結構性的防護。

## 常見追問

### ACL 該怎麼設計權限？

**核心答案**：依**最小權限原則**，為每個服務建立獨立使用者並限制三件事：**能執行哪些命令**（用 `+@read +@write -@admin -@dangerous` 這類命令分類，比逐個列舉好維護）、**能存取哪些鍵**（用鍵模式 `~cache:*` 限制，這與命名規範直接相關）、以及**能訂閱哪些頻道**（`&channel:*`）。管理員操作應該用另一個獨立的使用者，並且不放在應用的設定裡。

**詳細解析**：**「命令分類」是 ACL 好用的關鍵**。Redis 把命令分成 `@read`、`@write`、`@admin`、`@dangerous`、`@slow` 等群組，用群組授權比列舉幾百個命令務實得多，而且新版本新增的命令會自動落入對應群組。**要特別注意 `@dangerous` 包含了 `KEYS`、`FLUSHALL`、`CONFIG` 這些**，應用使用者應該一律排除。另一個實務要點是「鍵模式限制與命名規範互相成就」——如果鍵沒有統一前綴，就無法用模式限制；有了 `svc-order:*` 這樣的前綴，ACL 的限制就自然可行。這是一個很好的例子說明「好的命名規範不只是可讀性，它讓後續的治理成為可能」——同樣的道理適用於資源標籤、日誌欄位、與指標命名。

**面試回答方式**：給最小權限原則與三項限制（命令、鍵模式、頻道），並強調**用命令分類比逐個列舉務實**，新增的命令會自動落入對應群組。指出 **`@dangerous` 包含 `KEYS`、`FLUSHALL`、`CONFIG`，應用使用者應一律排除**。真正的加分點是點出鍵模式限制與命名規範互相成就——沒有統一前綴就無法用模式限制，並收在觀點：好的命名規範不只是可讀性，它讓後續的治理成為可能。

### TLS 對 Redis 的效能影響有多大？

**核心答案**：**明顯但通常可接受**。TLS 增加了加解密的 CPU 成本與握手的延遲；實測上吞吐可能下降 30% 到 50%（依訊息大小與硬體而異，有 AES-NI 硬體加速時較好）。**握手的成本尤其要注意**——每次新連線都要完整握手（幾個往返加上非對稱加密運算），所以連線池與長連線在 TLS 下比明文更重要。

**詳細解析**：判斷要不要開 TLS 的關鍵是「流量會不會離開受信任的網路邊界」。同一個 VPC 內、有嚴格網路隔離的部署，多數團隊選擇不開（依賴網路層的隔離）；跨網路、跨可用區、或有合規要求（PCI DSS 等）時則必須開。中間方案是「只對特定連線開啟」——Redis 支援同時監聽明文與 TLS 埠，讓內網服務走明文、跨網路的走 TLS。這個「依風險分級施加保護」的思路比「一律加密」或「一律不加密」都務實，因為安全措施的成本應該與風險匹配。但要注意「內網是可信的」這個假設本身正在被挑戰（零信任架構主張不預設信任任何網路位置），所以在新建的系統上，預設開啟 TLS 是越來越常見的選擇。

**面試回答方式**：給量化影響（吞吐下降三到五成，有硬體加速時較好）並特別指出握手成本讓連線池與長連線在 TLS 下更重要。給判斷關鍵：流量會不會離開受信任的網路邊界，並提出中間方案（同時監聽明文與 TLS 埠，依來源分流）。收在思路：依風險分級施加保護比一律加密或一律不加密都務實，但補上零信任架構正在挑戰「內網可信」這個假設，所以新系統預設開 TLS 越來越常見。

### 除了設定，還有哪些營運面的安全措施？

**核心答案**：四項。**不要用預設埠**（6379 是掃描器的第一目標，改埠不是真正的防護但能大幅減少自動化掃描的命中）。**定期檢查暴露面**——用外部視角掃描自己的 IP 範圍，確認 Redis 沒有意外暴露到公網（雲端環境的安全群組設定錯誤是最常見的暴露原因）。**稽核與監控**——監控異常的命令（`CONFIG`、`FLUSHALL` 的執行）、異常的連線來源、以及認證失敗的次數。**最小化資料敏感度**——不要在 Redis 裡存明文的個資或密碼，即使被存取也降低損失。

**詳細解析**：「定期檢查暴露面」是最有效但最少被做的一項。設定在部署時是對的，但雲端環境的安全群組可能被後來的變更放寬（為了除錯臨時開放而忘記關、或者一個過於寬鬆的規則被套用到更多資源上）。所以「當時設定對了」不等於「現在仍然對」——需要持續的驗證而非一次性的檢查。**做法可以很簡單**：一個定期執行的腳本從外部嘗試連線並告警。這個「持續驗證而非一次性設定」的思路適用於所有安全控制——防火牆規則、權限設定、憑證有效期、以及備份的可恢復性，它們的共同特徵是「會隨時間悄悄失效，而失效時不會有任何跡象」。

**面試回答方式**：給四項營運措施。重點展開「定期檢查暴露面」最有效但最少被做——設定在部署時是對的，但安全群組可能被後來的變更放寬（臨時開放忘了關、寬鬆規則被套用到更多資源），所以「當時設定對了」不等於「現在仍然對」。給出簡單做法（定期從外部嘗試連線並告警）。收在通用思路：**持續驗證而非一次性設定**，適用於防火牆、權限、憑證、備份可恢復性，它們的共同特徵是會隨時間悄悄失效且失效時沒有跡象。
