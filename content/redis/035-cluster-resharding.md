# 題目

Redis Cluster 擴容時，資料是怎麼從舊節點搬到新節點的？遷移期間的請求怎麼處理？

## 核心答案

Redis Cluster 把鍵空間分成 **16384 個槽位**，每個節點負責一部分。擴容就是把一部分槽位從既有節點遷移到新節點——遷移的單位是槽位，而不是個別的鍵。

遷移一個槽位的流程是：目標節點標記該槽為 `IMPORTING`、來源節點標記為 `MIGRATING`、**然後逐批把鍵用 `MIGRATE` 命令搬過去**（`MIGRATE` 是原子的：序列化、傳送、在目標還原、在來源刪除）、全部搬完後通知所有節點更新槽位歸屬。

遷移期間的請求靠兩個重導向處理。`MOVED` 表示「這個槽已經不歸我管，去那個節點」——客戶端應該更新自己的槽位映射表。`ASK` 表示「這個槽正在遷移中，這個特定的鍵已經搬過去了，去問那個節點，但不要更新映射表」——因為槽位還沒完全遷移完。客戶端必須正確實作這兩者的區別，否則會在遷移期間出錯或反覆重導向。

**遷移是線上的、不停機的**，但它會佔用網路與 CPU，大 key 的遷移還可能造成明顯的阻塞（`MIGRATE` 是同步的）。

## 詳細解析

`MOVED` 與 `ASK` 的區別是理解叢集客戶端的關鍵。`MOVED` 是**永久性的資訊**（槽位歸屬變了），客戶端收到後應該更新本地的槽位映射，之後直接送到正確的節點。`ASK` 是**一次性的臨時重導向**（這個鍵剛好已經搬過去了，但槽還在遷移），客戶端應該先送 `ASKING` 命令再送實際命令，**而且不更新映射表**。把 `ASK` 當成 `MOVED` 處理會導致映射表被錯誤地更新，之後大量請求被送到還沒完成接管的節點。

**大 key 是重分片的主要障礙**。`MIGRATE` 會序列化整個鍵的值並傳送——一個 1GB 的 key 的遷移會讓來源與目標節點都阻塞數秒。而且 `MIGRATE` 有逾時，超過會失敗並留下一個中間狀態需要處理。所以在計劃擴容之前，應該先用 `--bigkeys` 掃描並處理大 key——這是擴容前的必要準備，卻常常被忽略直到遷移卡住。

**跨槽操作在叢集下受限**，這影響了應用的設計。`MGET`、`MSET`、交易、Lua 腳本都要求所有 key 在同一個槽。**解法是 hash tag**——鍵名中大括號內的部分決定雜湊（`{user:1000}:profile` 與 `{user:1000}:orders` 落在同一個槽）。**但過度使用 hash tag 會造成資料傾斜**：把大量鍵都塞進同一個 tag，那個槽會變得特別大，遷移它時成本極高，也讓負載無法均衡。所以 hash tag 應該用在「真的需要一起操作」的少數鍵上，而不是為了方便而大量使用。

**重分片的實務建議**：**在低峰時段進行**、**分批遷移**（一次遷移少量槽位，觀察影響後再繼續）、監控來源與目標節點的延遲與記憶體、以及**準備回滾方案**（遷移到一半可以停止，槽位歸屬會停在中間狀態但服務仍然正常）。`redis-cli --cluster reshard` 提供了互動式的操作，但生產環境應該用腳本控制批次與節奏，而不是手動一次遷移幾千個槽。

## 面試回答方式

先給**槽位是遷移的單位**（16384 個槽）與遷移流程（IMPORTING／MIGRATING 標記、逐批 `MIGRATE`、完成後更新歸屬）。接著把 `MOVED` 與 `ASK` 的區別講清楚——前者是永久資訊要更新映射表、後者是一次性臨時重導向不能更新映射表，並指出把 `ASK` 當 `MOVED` 處理會讓映射表被錯誤更新。加分點有三個：**大 key 是重分片的主要障礙**（`MIGRATE` 同步序列化整個值，1GB 的 key 讓兩端阻塞數秒），所以擴容前應該先掃描並處理大 key；**hash tag 過度使用會造成資料傾斜**——應該只用在真的需要一起操作的少數鍵上；以及**實務建議**：低峰時段、分批遷移、監控兩端、生產環境用腳本控制節奏而非手動一次遷移幾千個槽。

## 講稿

Redis Cluster 把鍵空間分成一萬六千多個槽位，每個節點負責一部分。擴容就是把一部分槽位從既有節點遷移到新節點，遷移的單位是槽位而不是個別的鍵。

流程是目標節點標記為匯入中、來源標記為遷移中，然後逐批把鍵搬過去，全部搬完後通知所有節點更新歸屬。

遷移期間的請求靠兩個重導向處理，這是理解叢集客戶端的關鍵。一個表示這個槽已經不歸我管，那是永久性的資訊，客戶端應該更新本地的映射表。另一個表示這個槽正在遷移中、這個特定的鍵已經搬過去了，那是一次性的臨時重導向，客戶端不應該更新映射表。把後者當成前者處理，會導致映射表被錯誤更新，之後大量請求被送到還沒完成接管的節點。

大 key 是重分片的主要障礙。遷移命令會序列化整個鍵的值並傳送，一個一 GB 的 key 會讓來源跟目標都阻塞數秒，而且遷移有逾時，超過會失敗並留下需要處理的中間狀態。所以計劃擴容之前應該先掃描並處理大 key，這是必要準備但常常被忽略，直到遷移卡住。

實務上我會在低峰時段分批遷移，一次少量槽位、觀察影響後再繼續。

## 常見追問

### 為什麼是 16384 個槽而不是更多？

**核心答案**：這是一個**權衡的結果**，作者的解釋是：節點之間的心跳訊息會攜帶槽位的位圖，16384 個位元是 2KB，而 65536 個位元是 8KB——在頻繁的心跳中，這個差別是可觀的頻寬。同時 16384 對於「Redis Cluster 實務上不會超過 1000 個節點」這個假設來說已經足夠——每個節點平均 16 個槽，分配的粒度夠細。

**詳細解析**：這個決定體現了「依實際的規模上限選參數」的思路。如果一開始就設計成支援十萬個節點，槽位數要大得多，而那個成本要由所有（實際上只有幾十個節點的）部署一起承擔。選擇一個「對目標規模夠用」的值，而不是「理論上最大」的值，是務實的工程判斷。 代價是它成為一個難以改變的常數——槽位數寫在協定裡，改它需要不相容的變更。這也提醒了一件事：早期的參數選擇會成為長期的約束，所以那些選擇應該基於明確的規模假設，並把假設記錄下來——這樣後來的人才知道「這個數字是怎麼來的、什麼情況下需要重新考慮」。

**面試回答方式**：給出作者的實際理由——心跳訊息攜帶槽位位圖，16384 位元是 2KB 而 65536 是 8KB，在頻繁心跳中差別可觀；同時對「不超過 1000 個節點」的假設已經足夠。真正的加分點是歸納思路：依實際的規模上限選參數，而非理論上最大。收在提醒：早期的參數選擇會成為長期約束（槽位數寫在協定裡難以改變），所以應該基於明確的規模假設並把假設記錄下來。

### 叢集下哪些操作受限？怎麼因應？

**核心答案**：所有**涉及多個 key 的操作**都要求那些 key 在同一個槽：`MGET`／`MSET`、`SUNION`／`ZUNIONSTORE` 這類多鍵運算、`MULTI` 交易、以及 Lua 腳本。因應方式有三個：**用 hash tag 把相關的鍵放進同一個槽**、**改用多次單鍵操作**（客戶端並行發送到不同節點再合併，多數叢集客戶端已經幫 `MGET` 做了這件事）、或**重新設計資料模型**讓跨鍵操作不再需要。

**詳細解析**：「重新設計資料模型」常常是最好的答案，卻最少被考慮。需要對五個 key 做交易，通常意味著那五個 key 在概念上是一個整體——那它們或許應該是一個 Hash 的五個欄位，那樣就在同一個 key 裡，完全沒有跨槽問題。叢集的限制其實在推動一個好的設計方向：讓「需要一起原子操作的資料」在物理上也在一起。 這與分散式系統中「聚合根（aggregate root）」的概念一致——交易邊界應該與資料的物理分佈邊界對齊。認出這一點，就會把叢集的限制看成一個設計提示而不只是一個麻煩。

**面試回答方式**：列出受限的操作類型與三個因應方式。真正的加分點是主張「重新設計資料模型」常是最好的答案卻最少被考慮——需要對五個 key 做交易通常意味著它們在概念上是一個整體，或許該是一個 Hash 的五個欄位。收在觀點：叢集的限制其實在推動一個好的設計方向——讓需要一起原子操作的資料在物理上也在一起，這與聚合根的概念一致，交易邊界應該與資料的物理分佈邊界對齊。

### 叢集的故障轉移是怎麼進行的？

**核心答案**：節點之間透過 **gossip 協定**互相探測（`PING`／`PONG`）。某個節點在 `cluster-node-timeout` 內沒有回應時，探測它的節點把它標記為 **PFAIL（疑似下線）**；當**超過半數的主節點**都報告某節點 PFAIL 時，它被標記為 **FAIL（確定下線）** 並廣播給整個叢集。此時該主節點的從節點會發起選舉，取得多數主節點的投票後晉升為新主節點，接管原本的槽位。

**詳細解析**：「需要多數主節點同意」是防止腦裂的關鍵——網路分割時，只有包含多數主節點的那一側能完成故障轉移，少數側無法產生新主節點。**但這不能完全消除資料丟失**：分割前寫入舊主節點但還沒複製出去的資料，在故障轉移後就丟了（複製是非同步的）。`cluster-require-full-coverage` 控制「部分槽位無人負責時整個叢集是否停止服務」——設成 no 可以讓其餘部分繼續服務，代價是應用可能拿到不完整的資料，這個取捨要依業務決定。另一個實務要點是 `cluster-node-timeout` 的設定：太短會在網路抖動時誤判並觸發不必要的故障轉移（那本身就是一次服務中斷），太長則真實故障時恢復慢。這是所有故障偵測系統的共同取捨——偵測的靈敏度與誤判率是同一個旋鈕的兩端。

**面試回答方式**：給流程（gossip 探測、PFAIL、多數主節點確認後 FAIL、從節點選舉需要多數投票）。強調「需要多數主節點同意」是防止腦裂的關鍵，但**不能消除資料丟失**因為複製是非同步的。加分點是 `cluster-require-full-coverage` 的取捨（繼續服務 vs 拿到不完整資料）與 `cluster-node-timeout` 的設定取捨——太短會誤判觸發不必要的轉移、太長則恢復慢。收在一般原則：偵測的靈敏度與誤判率是同一個旋鈕的兩端。
