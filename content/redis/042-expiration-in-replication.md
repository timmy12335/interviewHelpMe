# 題目

從節點會自己刪除過期的鍵嗎？讀從節點時會不會讀到已經過期的資料？

## 核心答案

**從節點不會自己刪除過期鍵**——刪除的決定完全由**主節點**做出。主節點透過惰性刪除（存取時檢查）或主動過期（週期取樣）發現鍵過期後，**會顯式地向從節點發送一個 `DEL`（Redis 6 之後是 `UNLINK`）命令**，從節點依此刪除。這個設計是為了**保證資料的一致性**：如果從節點各自決定刪除，主從之間會因為時鐘與執行時機的差異而不一致。

**代價是從節點上可能存在「邏輯上已過期但實體上還在」的鍵**——主節點還沒發現它過期（主動過期是取樣的，不保證及時），所以還沒發送刪除命令。

**但 Redis 在讀取時做了補償**：從節點回應讀取請求時**會檢查鍵的邏輯過期時間**，已過期的話**回傳 nil 而不刪除它**。所以**客戶端不會讀到過期的資料**（Redis 3.2 之後），只是那個鍵還佔著記憶體直到主節點下令刪除。

**唯一的例外是 `DEBUG` 或直接檢查資料庫大小時**——`DBSIZE` 與 `RANDOMKEY` 可能把尚未被刪除的過期鍵算進去。

## 詳細解析

**這個設計是「一致性優於即時性」的選擇**。讓從節點自己刪除會更及時，**但會引入不一致的窗口**：主從的時鐘不完全同步、主動過期的取樣時機不同，於是同一個鍵可能在從節點已經消失而在主節點還在。**對於「主從應該看到同樣的資料」這個基本期望，這是不可接受的**。所以 Redis 選擇讓刪除完全由主節點驅動，**讓複製流成為唯一的真相來源**。

**「讀取時檢查邏輯過期」這個補償很重要，但它有版本差異**。Redis 3.2 之前，**從節點會回傳已過期的資料**——這是一個真實的正確性問題，很多舊文章提到的「讀從節點可能讀到過期資料」就是指這個。**升級之後這個問題已經解決，但知道版本差異能避免引用過時的知識。**

**主動過期的取樣策略決定了記憶體的回收速度**。Redis 每 100 毫秒執行一次，**每次隨機取樣 20 個設了過期時間的鍵**，刪除其中已過期的；如果過期的比例超過 25%，**立刻再取樣一輪**（因為那暗示還有很多過期鍵）。**這個「取樣加自適應」的設計避免了掃描全部鍵的成本，但也意味著回收不是即時的**——大量鍵同時過期時，記憶體的下降會有延遲。

**在叢集下沒有額外的複雜度**（每個槽有明確的主節點，行為與主從相同），**但「大量鍵同時過期」的影響會被放大**——主節點的主動過期循環會佔用時間，而那是單執行緒的。**所以給 TTL 加隨機抖動不只是防雪崩，也是為了讓過期的工作分散開**，這是同一個手段解決兩個問題。

## 面試回答方式

先給核心事實——**從節點不會自己刪除，刪除完全由主節點驅動並透過複製流下發 `DEL`**，理由是**保證一致性**（各自刪除會因時鐘與時機差異而不一致）。給出代價：**從節點上可能有邏輯已過期但實體還在的鍵**。然後給補償機制：**讀取時檢查邏輯過期時間，已過期回傳 nil 但不刪除**，所以客戶端不會讀到過期資料。加分點有三個：**這是「一致性優於即時性」的選擇**，讓複製流成為唯一的真相來源；**Redis 3.2 之前從節點真的會回傳過期資料**，很多舊文章講的就是這個，知道版本差異能避免引用過時知識；以及**主動過期是取樣的**（每 100 毫秒取樣 20 個、過期比例超過 25% 就再來一輪），所以回收不即時，而**給 TTL 加隨機抖動同時解決雪崩與過期工作集中兩個問題**。

## 講稿

從節點不會自己刪除過期鍵，刪除的決定完全由主節點做出。主節點發現鍵過期之後，會顯式地向從節點發送刪除命令。

這個設計是為了保證一致性。如果從節點各自決定刪除，主從之間會因為時鐘跟執行時機的差異而不一致，而主從應該看到同樣的資料是一個基本期望。所以 Redis 讓複製流成為唯一的真相來源。

代價是從節點上可能存在邏輯上已經過期、但實體上還在的鍵，因為主節點還沒發現它過期。

但讀取時有補償。從節點回應讀取請求的時候會檢查鍵的邏輯過期時間，已過期就回傳空值而不刪除它。所以客戶端不會讀到過期資料，只是那個鍵還佔著記憶體。

要注意這是 Redis 3.2 之後的行為。在那之前從節點真的會回傳已過期的資料，很多舊文章提到的讀從節點可能讀到過期資料就是指這個。

還有一點，主動過期是取樣的。每一百毫秒隨機取樣二十個設了過期的鍵，過期比例超過四分之一就立刻再來一輪。所以回收不是即時的，大量鍵同時過期時記憶體的下降會有延遲。給過期時間加隨機抖動，同時解決雪崩跟過期工作集中兩個問題。

## 常見追問

### 大量鍵同時過期會造成什麼問題？

**核心答案**：三個。**主動過期循環佔用時間**——大量鍵過期時，取樣會反覆發現過期鍵並刪除，**而那是在主執行緒上執行的**，造成延遲上升。**複製流量突增**——每個過期都要向從節點發送一個刪除命令，**一百萬個鍵同時過期就是一百萬個複製指令**。**下游的雪崩**——大量快取同時失效導致請求全部穿透到資料庫。

**詳細解析**：**三個問題有同一個解法：給 TTL 加隨機抖動**（`ttl + random(0, ttl * 0.1)`）。這個做法通常只被當成防雪崩的手段，**但它同時解決了 Redis 自身的兩個問題**——過期工作分散、複製流量平滑。**這是一個「一個小改動解決三個問題」的例子**，而且成本幾乎為零。**要注意抖動的方向**：只往後加（延長）而不往前減，因為縮短可能讓資料比預期更早失效。**抖動的幅度**通常取 TTL 的 5% 到 20%——太小起不到分散作用，太大則讓實際過期時間的變異太大。**在批次寫入大量帶 TTL 的鍵時（例如一次預熱一百萬筆快取），加抖動是必須的而不是可選的。**

**面試回答方式**：給三個問題（主執行緒的過期循環、複製流量突增、下游雪崩）並各配具體數字。真正的加分點是指出**三個問題有同一個解法：給 TTL 加隨機抖動**，而這通常只被當成防雪崩手段，**它其實同時解決了 Redis 自身的兩個問題**——這是「一個小改動解決三個問題」的例子。收在實作細節：**只往後加不往前減**、幅度取 5% 到 20%、**批次預熱大量鍵時加抖動是必須而非可選**。

### 讀寫分離時還有哪些一致性問題？

**核心答案**：主要是**複製延遲**。寫入主節點後立刻讀從節點，可能讀到舊值——**這是非同步複製的必然結果**。典型的症狀是「使用者更新了個人資料，重新整理後看到的還是舊的」。三個處理方向：**寫後讀走主節點**（在一段時間內或在同一個 session 內強制讀主）、**用 `WAIT` 等待複製**（阻塞直到 N 個從節點確認，代價是延遲上升且不保證絕對）、或**接受並在 UI 上處理**（樂觀更新，前端先顯示新值）。

**詳細解析**：**「寫後讀走主節點」是最實用的方案**，但實作上有一個細節：**怎麼判斷「剛寫過」**。常見做法是寫入後在 session 或一個短 TTL 的標記裡記下時間戳，**後續讀取在該時間戳的一段時間內（例如複製延遲的 P99）強制走主節點**。**這比「所有讀都走主」精確得多**（後者等於放棄了讀寫分離的收益）。**更根本的問題是「讀寫分離真的需要嗎」**——它增加了一致性的複雜度，而收益是分擔讀取負載。**如果主節點的負載還有餘裕，不做讀寫分離是更簡單的選擇**；只有在讀取確實成為瓶頸時才引入，並明確接受它帶來的一致性成本。**「不要為了架構的完整性而引入複雜度」在這裡特別適用。**

**面試回答方式**：給根本原因（非同步複製）與典型症狀，再給三個處理方向。重點展開**「寫後讀走主節點」的實作細節**：用 session 或短 TTL 標記記下寫入時間戳，在複製延遲的 P99 內強制走主——**比「所有讀都走主」精確得多**。真正的加分點是往回問**「讀寫分離真的需要嗎」**——它增加一致性複雜度而收益是分擔讀取負載，**主節點還有餘裕時不做是更簡單的選擇**。收在原則：不要為了架構的完整性而引入複雜度。

### 為什麼過期不用一個定時器精確觸發？

**核心答案**：因為**成本太高**。為每個帶 TTL 的鍵維護一個定時器，意味著一個包含數千萬個項目的定時器結構——**插入、刪除、以及觸發都有成本，而且大量定時器同時到期會造成集中的處理高峰**。Redis 選擇了「惰性刪除加取樣式主動過期」的組合：**惰性刪除保證正確性**（存取時一定不會拿到過期資料），**主動過期負責回收記憶體**（盡力而為，不保證及時）。

**詳細解析**：**這是一個典型的「用近似換成本」的設計**，而且它的取捨很清楚：**正確性不打折**（惰性刪除保證了），**只有記憶體回收的即時性打折**。**理解這個劃分很重要**——很多人擔心「過期不及時會不會讀到舊資料」，實際上不會；真正的影響只是記憶體。**同樣的「保證正確性、放寬及時性」的設計思路在很多系統裡出現**：資料庫的空間回收（vacuum）、GC 的分代回收、以及各種背景整理任務。**它們的共同特徵是把「必須正確的部分」放在同步路徑上，把「只影響資源效率的部分」放在背景**——這是一個很值得學習的分工原則。

**面試回答方式**：給成本理由（數千萬個定時器的維護成本與集中到期的高峰）與 Redis 的組合方案（惰性刪除保證正確、主動過期負責回收）。真正的加分點是點清取捨的劃分：**正確性不打折，只有記憶體回收的即時性打折**——很多人擔心讀到舊資料，實際上不會。收在通用設計思路：**把必須正確的部分放在同步路徑、把只影響資源效率的部分放在背景**，並舉資料庫的空間回收與 GC 的分代回收作為同類。
