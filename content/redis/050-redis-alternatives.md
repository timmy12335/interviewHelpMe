# 題目

Redis 的授權變更之後有哪些替代方案？在什麼情況下該考慮它們？

## 核心答案

2024 年 Redis 從 BSD 改成 RSALv2 與 SSPLv1 雙授權——**不再是 OSI 認可的開源授權**，主要限制是「不能把 Redis 作為託管服務提供給第三方」。這對絕大多數**自用**的公司沒有影響，**但促成了社群的分叉**。

**Valkey** 是 Linux 基金會主導的分叉（由 AWS、Google、Oracle 等支持），**與 Redis 7.2 完全相容**、採用 BSD 授權、由社群治理。**對多數使用者而言它是一個直接的替代品**——協定相同、命令相同、客戶端不必改。

其他值得知道的方向：**DragonflyDB**（相容 Redis 協定但內部架構完全不同——多執行緒加分片，單機吞吐高得多，適合垂直擴展而非水平分片）、**KeyDB**（Redis 的多執行緒分叉，較早出現）、以及**回到基本問題**——**很多 Redis 的用途其實可以用更簡單的東西滿足**：純本地快取（Caffeine）、資料庫本身的快取、或者根本不需要快取。

**選型的判斷應該回到需求**：授權問題只影響「要不要提供託管服務」的公司；效能問題應該先確認瓶頸真的在 Redis；而**「已經在用且運作良好」本身就是一個很強的留下的理由**。

## 詳細解析

**授權變更的實際影響需要精確理解，而不是恐慌性反應**。RSALv2 與 SSPLv1 限制的是「提供 Redis 作為服務給第三方」——**自己的產品內部使用 Redis 完全不受影響**。所以絕大多數公司實際上不需要做任何事。**會受影響的是雲端服務商與提供 Redis 託管的公司**，而那正是這次變更針對的對象。**在評估時應該讓法務確認自己的使用情境，而不是憑技術部落格的摘要做決定**——授權條款的細節與具體的商業模式高度相關。

**Valkey 的價值在於「治理模式」而非技術差異**。它與 Redis 在功能上幾乎相同（分叉自 7.2），**真正的差別是它由 Linux 基金會治理、有多家公司共同投入、且採用永久的 BSD 授權**。**對於擔心「未來再次變更授權」的組織，這個治理保證比任何技術特性都重要。** 代價是生態需要時間跟上（客戶端函式庫、監控工具、雲端服務的支援），**但因為協定相容，這個成本比想像中低**。

**DragonflyDB 代表了另一種思路**：既然多核機器是常態，**為什麼不在單機上用多執行緒加內部分片**？它的架構讓單機吞吐比 Redis 高數倍，**適合「不想管理叢集但需要更高吞吐」的場景**。代價是：與 Redis 的行為有細微差異（某些命令的邊界情況、某些模組不支援）、生態較新、以及**它解決的是「垂直擴展」的問題，而如果你已經需要水平分片，它的優勢就有限**。

**最有價值的判斷往往是「回到需求」**。很多系統用 Redis 只是為了「快取幾個查詢結果」，**而那可能用應用內的 Caffeine 就夠了**（沒有網路往返、沒有序列化、沒有額外的元件）；有些用它做「跨實例共享的小量狀態」，**而那可能用資料庫的一張表加上短查詢就夠了**。**在討論替代方案之前，先確認「這個需求真的需要一個分散式的記憶體儲存嗎」，常常能省下整個技術選型的討論。**

## 面試回答方式

先**精確說明授權變更的影響**——限制的是「提供 Redis 作為服務給第三方」，**自用完全不受影響**，所以絕大多數公司不需要做任何事；受影響的是雲端服務商。給 **Valkey 的定位**：Linux 基金會治理、與 7.2 相容、BSD 授權，**價值在於治理模式而非技術差異**——對擔心未來再次變更的組織，治理保證比技術特性重要。給 **DragonflyDB 的思路**（單機多執行緒加內部分片、垂直擴展）與它的邊界（**如果已經需要水平分片，優勢有限**）。最有價值的部分放最後：**回到需求**——很多用途其實用應用內的 Caffeine 或資料庫的一張表就夠了，**在討論替代方案之前先確認「這個需求真的需要一個分散式的記憶體儲存嗎」**。並補一句：**「已經在用且運作良好」本身就是很強的留下理由**。

## 講稿

二零二四年 Redis 改成雙授權，不再是 OSI 認可的開源。但影響需要精確理解，而不是恐慌性反應。限制的是把 Redis 作為託管服務提供給第三方，自己的產品內部使用完全不受影響。所以絕大多數公司不需要做任何事，受影響的是雲端服務商。

Valkey 是 Linux 基金會主導的分叉，跟 Redis 7.2 完全相容、採用 BSD 授權。我認為它的價值在於治理模式而不是技術差異。功能上幾乎相同，真正的差別是有多家公司共同投入而且授權是永久的。

DragonflyDB 代表另一種思路。既然多核是常態，為什麼不在單機上用多執行緒加內部分片。它的單機吞吐高得多，適合不想管理叢集但需要更高吞吐的場景。但它解決的是垂直擴展，如果已經需要水平分片，優勢就有限。

我覺得最有價值的判斷是回到需求。很多系統用 Redis 只是為了快取幾個查詢結果，那可能用應用內的本地快取就夠了。在討論替代方案之前，先確認這個需求真的需要一個分散式的記憶體儲存，常常能省下整個選型討論。

## 常見追問

### 從 Redis 遷移到 Valkey 要注意什麼？

**核心答案**：**技術上幾乎沒有障礙**（協定與命令相同、RDB 格式相容、可以用主從複製平滑切換），**真正的工作在周邊**：確認客戶端函式庫支援（多數只是連線字串不變，不需改）、確認監控與維運工具支援（Prometheus exporter、管理介面）、以及確認雲端服務商是否提供託管的 Valkey。**驗證的方式與任何遷移相同**——在測試環境完整跑一遍，包括故障轉移與恢復。

**詳細解析**：**應該同時評估「不遷移的成本」**。留在 Redis 的成本是：未來的新版本採用新授權（如果你的使用情境不受限，這不是成本）、以及社群動能可能轉向 Valkey（影響長期的生態支援）。**遷移的成本是：一次遷移的工程時間、驗證的風險、以及短期內 Valkey 生態較新的不確定性。** **對多數自用的公司，這兩邊的成本都不大，所以「不急著決定」是合理的選擇**——觀察一到兩年，等生態明朗再決定。**技術決策不一定要立刻做，「主動選擇等待」與「拖延」是不同的**：前者有明確的觀察指標與重新評估的時間點，後者只是沒有討論。

**面試回答方式**：給技術上幾乎無障礙的事實與周邊需要確認的三項（客戶端、監控工具、雲端託管）。真正的加分點是**同時評估「不遷移的成本」**，並得出結論：**對多數自用公司兩邊成本都不大，所以「不急著決定」是合理的**。收在一個有價值的區分：**「主動選擇等待」與「拖延」不同**——前者有明確的觀察指標與重新評估的時間點，後者只是沒有討論。

### 什麼情況下 DragonflyDB 這類方案真的有優勢？

**核心答案**：**當「單機吞吐不夠但不想管理叢集」時**。典型的情境是：資料量能放進單機的記憶體（幾百 GB 以內）、但 QPS 已經打滿了 Redis 的單執行緒、而引入叢集會帶來跨槽操作的限制與維運複雜度。**DragonflyDB 用單機的多執行緒解決了這個中間地帶。** 反過來，如果資料量本來就超過單機、或者 QPS 還遠沒有打滿，它的優勢就不存在。

**詳細解析**：**要注意「相容 Redis 協定」不等於「行為完全相同」**。內部架構不同意味著某些邊界行為會有差異：**命令的原子性語意**（Redis 的單執行緒讓所有命令天然原子，多執行緒實作需要自己保證，通常是對的但需要驗證）、**慢命令的影響範圍**（Redis 裡一個慢命令阻塞全部，多執行緒下只影響部分——**這是優點，但也意味著行為與既有的心智模型不同**）、以及**模組與擴充的支援**。**所以遷移前應該用真實的工作負載做完整測試，特別是那些依賴原子性的邏輯**（分散式鎖、限流器、計數器）。**「協定相容」是遷移成本的下限而非全部**——這個判斷適用於所有「相容某個既有系統」的替代方案。

**面試回答方式**：給明確的適用區間——**單機吞吐不夠但不想管理叢集**，並劃出兩端的邊界（資料量超過單機、或 QPS 還沒打滿時優勢不存在）。真正的加分點是提醒**「相容協定」不等於「行為完全相同」**，並給三個具體的差異面向（原子性語意、慢命令的影響範圍、模組支援）。收在原則：**協定相容是遷移成本的下限而非全部**，這適用於所有「相容某個既有系統」的替代方案。

### 怎麼向團隊說明「我們暫時不需要換」？

**核心答案**：用**具體的影響評估**而非立場。三步：**確認授權變更對「我們的使用情境」有沒有實質影響**（多數自用公司沒有，讓法務給一個書面確認）、**列出留下與遷移各自的成本與風險**、**設定一個重新評估的觸發條件與時間點**（例如「一年後、或者雲端服務商停止提供 Redis 託管時」）。

**詳細解析**：**「設定重新評估的觸發條件」是這個回答的關鍵**，因為它把「暫時不換」從一個被動的現狀變成一個主動的決定。**沒有觸發條件的「暫時不換」會變成永遠不換**，直到某天被迫在壓力下做決定。**而有了明確的觸發條件，團隊就知道「什麼情況下要重新討論」，也不必反覆爭論同一件事。** **這個做法適用於所有「現在不做但將來可能要做」的技術決定**——技術債的償還、框架的升級、架構的重構。**把決定與它的前提一起記錄下來（例如寫成一份簡短的 ADR），是讓團隊的技術決策可累積而非反覆重來的最低成本做法。**

**面試回答方式**：給三步（確認實質影響並讓法務書面確認、列出兩邊的成本與風險、設定重新評估的觸發條件與時間點）。重點強調**第三步是關鍵**——它把「暫時不換」從被動現狀變成主動決定，**沒有觸發條件的「暫時不換」會變成永遠不換**直到被迫在壓力下決定。收在通用做法：**把決定與它的前提一起記錄（例如寫成簡短的 ADR）**，這適用於所有「現在不做但將來可能要做」的技術決定，是讓團隊決策可累積而非反覆重來的最低成本做法。
