# 題目

Redis 突然變慢了，你會怎麼排查？延遲可能來自哪些地方？

## 核心答案

先分清楚**是 Redis 慢還是整條鏈路慢**。用 `redis-cli --latency`（從客戶端量測往返時間）與 `redis-cli --intrinsic-latency`（量測伺服器本身的排程延遲，它不連線、只在本機測系統的固有延遲）對照——如果固有延遲就很高，問題在作業系統或虛擬化層而非 Redis。

Redis 側的延遲來源有六類。**慢命令**——用 `SLOWLOG GET` 查看，O(N) 命令在大集合上執行是最常見的原因。**fork 造成的阻塞**——`BGSAVE` 與 AOF 重寫要 fork，大記憶體實例的 fork 可能耗時數百毫秒到數秒（`INFO stats` 的 `latest_fork_usec`）。**過期與淘汰**——大量鍵同時過期時，主動過期的循環會佔用時間。**記憶體交換**——碎片率小於 1 就是這個問題。**網路與客戶端**——輸出緩衝區大、大量新連線、或客戶端本身慢。**持久化的磁碟 IO**——AOF 的 `always` 策略讓每次寫入都要等 fsync。

**`LATENCY MONITOR` 是專門的工具**：開啟後（`latency-monitor-threshold`）會記錄各類延遲事件的來源與時間，`LATENCY LATEST` 與 `LATENCY DOCTOR` 直接給出分析。

## 詳細解析

`--intrinsic-latency` 是最被低估的診斷工具。它在本機執行一個緊密迴圈量測「執行一個簡單操作實際花了多久」——如果這個數字就有幾毫秒，那表示作業系統的排程或虛擬化層有問題（CPU 被超賣、鄰居干擾、透明大頁的整理、或 CPU 節流），而不管怎麼優化 Redis 都沒用。在雲端或容器環境，這是應該最先排除的一項。

**fork 的成本與記憶體量成正比**。fork 本身不複製資料（寫時複製），但**它需要複製頁表**——一個 20GB 的實例，頁表可能有幾十 MB，複製它需要數百毫秒，**而這段時間主行程完全阻塞**。`latest_fork_usec` 直接給出上次 fork 的耗時。緩解方式有：降低單實例的記憶體量（分片）、減少持久化頻率、在從節點做持久化、或者關閉透明大頁（THP 會讓頁表更大且寫時複製的粒度變成 2MB，大幅放大成本——這是 Redis 官方明確建議關閉 THP 的原因）。

大量鍵同時過期是一個容易忽略的來源。Redis 的主動過期是一個週期性的取樣循環，如果大量鍵在同一秒過期，這個循環會反覆發現過期鍵並刪除，佔用可觀的時間。緩解方式是**給過期時間加隨機抖動**（`ttl + random(0, 300)`），把過期時間分散開——這與快取雪崩的防護是同一個手段。

**排查的順序應該由外而內**：先確認是不是網路或客戶端（比較 `--latency` 與伺服器端的 `INFO commandstats`）、再確認是不是系統層（`--intrinsic-latency`）、然後才看 Redis 內部（SLOWLOG、fork、過期、記憶體）。跳過前兩步直接調 Redis 參數是最常見的浪費——很多「Redis 慢」的案例，根因是客戶端的連線池不足或網路抖動。

## 面試回答方式

先給第一步——**分清楚是 Redis 慢還是整條鏈路慢**，用 `--latency` 與 `--intrinsic-latency` 對照，後者不連線、只測本機系統的固有延遲，如果它就很高就是作業系統或虛擬化層的問題。給**六類延遲來源**並各配一個診斷手段。加分點有三個：**fork 的成本與記憶體量成正比**（複製頁表，20GB 實例可能數百毫秒），而透明大頁會大幅放大這個成本，這正是官方建議關閉 THP 的原因；**大量鍵同時過期**會讓主動過期循環佔用時間，緩解是**給 TTL 加隨機抖動**（與快取雪崩防護同一個手段）；以及**排查順序要由外而內**——先網路與客戶端、再系統層、最後才是 Redis 內部，跳過前兩步直接調參是最常見的浪費。

## 講稿

我會先分清楚是 Redis 慢還是整條鏈路慢。用客戶端的延遲量測跟伺服器的固有延遲量測對照。後者不連線，只在本機測系統的排程延遲。如果固有延遲就有幾毫秒，那問題在作業系統或虛擬化層，可能是 CPU 被超賣或被節流，不管怎麼優化 Redis 都沒用。在雲端或容器環境，這是應該最先排除的一項。

Redis 側的來源有六類。慢命令、fork 造成的阻塞、大量鍵同時過期、記憶體被交換到磁碟、網路與客戶端、還有持久化的磁碟 IO。

fork 值得特別講。它本身不複製資料，但需要複製頁表。一個二十 GB 的實例，頁表可能有幾十 MB，複製它要數百毫秒，而這段時間主行程完全阻塞。而且透明大頁會讓頁表更大、寫時複製的粒度變成兩 MB，大幅放大這個成本。這正是官方明確建議關閉透明大頁的原因。

大量鍵同時過期也容易被忽略。主動過期是一個週期性的取樣循環，大量鍵在同一秒過期的話，這個循環會反覆發現並刪除，佔用可觀的時間。緩解方式是給過期時間加隨機抖動，跟快取雪崩的防護是同一個手段。

## 常見追問

### SLOWLOG 記錄的時間包含什麼？

**核心答案**：**只包含命令的實際執行時間**，不包含網路傳輸、不包含等待其他命令完成的排隊時間、也不包含 IO 執行緒的處理時間。**這是一個重要的限制**——一個在 `SLOWLOG` 裡只有 1 毫秒的命令，客戶端觀察到的延遲可能是 100 毫秒，因為它在佇列裡等了 99 毫秒（前面有一個慢命令在執行）。

**詳細解析**：**這正是「單執行緒的排隊效應」**：一個 100 毫秒的慢命令會讓後面所有命令的觀察延遲都增加，而那些命令自己在 `SLOWLOG` 裡完全乾淨。所以排查時要看的是「有沒有任何慢命令」而不是「哪個命令在 SLOWLOG 裡最多」——一個每分鐘執行一次的 `KEYS *` 就足以造成規律的延遲毛刺，而它在 SLOWLOG 裡只有一筆。這個「一個慢請求影響所有後續請求」的模式，在所有單執行緒或單佇列的系統上都存在（事件迴圈、單執行緒的訊息消費者、以及有全域鎖的系統），認出它能解釋很多「為什麼這個明明很快的操作有時候很慢」的現象。

**面試回答方式**：給精確的範圍——只包含執行時間，不含網路、排隊、IO 執行緒。展開最重要的推論：**單執行緒的排隊效應**——一個 100 毫秒的慢命令讓後面所有命令的觀察延遲都增加，而它們在 SLOWLOG 裡完全乾淨。給出排查建議：看「有沒有任何慢命令」而非「哪個最多」。收在一般化：這個模式在所有單執行緒或單佇列系統上都存在，能解釋很多「明明很快的操作有時候很慢」的現象。

### 持久化對延遲的影響有多大？

**核心答案**：取決於策略。RDB 的 `BGSAVE`——主要成本是 fork（與記憶體量成正比）加上子行程寫入期間主行程的寫時複製（寫入越頻繁，複製的頁越多，記憶體與 CPU 成本越高）。**AOF 的 `everysec`**——背景執行緒每秒 fsync，正常情況影響很小，但如果磁碟慢導致上一次 fsync 還沒完成，主執行緒會被阻塞等待。AOF 的 `always`——每個寫命令都等 fsync 完成，延遲直接受磁碟影響，在一般磁碟上會讓寫入延遲上升一個數量級。

**詳細解析**：`everysec` 的阻塞行為是最容易被誤解的。它「每秒同步一次」聽起來與主執行緒無關，但 Redis 會檢查上一次背景 fsync 是否完成——如果磁碟卡住（雲端磁碟的 IO 突發額度用完、或磁碟本身有問題），主執行緒在寫 AOF 緩衝時會被阻塞。症狀是「Redis 突然卡住幾秒」，而 SLOWLOG 裡什麼都沒有（因為時間花在寫緩衝而非命令執行）。`INFO stats` 的 `aof_delayed_fsync` 會統計這種延遲的次數，**它是一個應該被監控的指標**。更根本的緩解是「在從節點做持久化」——主節點只服務請求、不做 RDB 也不做 AOF，把持久化的成本完全隔離到從節點上。代價是主節點故障時可能丟失更多資料，這個取捨要依業務決定。

**面試回答方式**：給三種策略的成本並各配機制。重點展開 `everysec` 的阻塞行為最容易被誤解——它會檢查上次 fsync 是否完成，磁碟卡住時主執行緒被阻塞，症狀是 Redis 突然卡幾秒而 SLOWLOG 裡什麼都沒有。給出該監控的指標 `aof_delayed_fsync`。收在更根本的緩解：**在從節點做持久化**，把成本完全隔離，代價是主節點故障時可能丟更多資料。

### 客戶端側有哪些常見的延遲來源？

**核心答案**：四個。**連線池不足**——請求排隊等連線，症狀是「Redis 很快但應用觀察到的延遲高」。**沒有用 pipeline 或批次命令**——N 次往返而非 1 次，跨機房時特別明顯。**序列化成本**——存取大物件時，JSON 的序列化與反序列化可能比 Redis 的操作本身還慢。**客戶端的 GC 停頓**——Java 應用的 GC 停頓期間，Redis 的回應在 socket 緩衝裡等著，觀察到的延遲包含了那段停頓。

**詳細解析**：「連線池不足」的診斷方式是比較兩個數字：應用端量測的「取得連線加執行」的總時間，與 Redis 端 `INFO commandstats` 的平均執行時間。**差距大就是排隊**。連線池的大小應該依「並行請求數乘以每個請求的 Redis 呼叫次數」估算，而不是憑感覺設。最後一項（客戶端 GC）特別容易被誤判成 Redis 的問題——因為應用的監控顯示「Redis 呼叫很慢」，但那個時間其實花在 GC 上。區分的方法是把 Redis 呼叫的延遲與應用的 GC 日誌對照時間戳。這個「觀察到的延遲不一定發生在被觀察的元件上」的問題，在所有跨元件的效能排查中都存在——所以每一層都應該有自己的量測，而不是只依賴上游的觀察。

**面試回答方式**：給四個來源。展開**連線池不足的診斷方式**——比較應用端的總時間與 Redis 端的平均執行時間，差距大就是排隊，並給出連線池大小的估算方式。重點放在客戶端 GC 特別容易被誤判成 Redis 的問題，區分方法是把延遲與 GC 日誌對照時間戳。收在一般原則：觀察到的延遲不一定發生在被觀察的元件上，所以每一層都該有自己的量測。
