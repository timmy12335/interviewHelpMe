# 題目

Redis 的主從複製是怎麼工作的？全量複製和增量複製有什麼區別？

## 核心答案

主從複製是——一個主節點（master）的資料，複製到一個或多個從節點（slave/replica）。主節點負責寫（也可讀）、從節點負責讀（不能寫），實現「讀寫分離（Read-Write Splitting）」（分攤讀壓力）和「資料備份/高可用基礎」。複製分兩種——「全量複製」：從節點第一次連接主節點、或斷線太久無法增量時，主節點生成一份 RDB 快照發給從節點、從節點載入（把主的全部資料同步過來）；「增量複製（部分複製）」：從節點短暫斷線後重連，主節點只把「斷線期間積壓的那部分寫命令」補發給從節點（不用重新全量），透過「複製積壓緩衝區」和「複製偏移量」實現。增量複製避免了每次斷線都全量的巨大開銷。

## 詳細解析

**主從複製的作用**：

- **讀寫分離**——主節點寫、從節點讀，多個從節點分攤讀請求，提升讀的吞吐（適合讀多寫少）。
- **資料冗餘/備份**——資料在多個節點都有副本。
- **高可用的基礎**——配合哨兵，主節點掛了可以把從節點提升為新主（故障轉移）。

**全量複製（Full Resynchronization）**：

- 觸發——從節點「第一次」連接主節點、或「斷線太久」導致無法增量複製時。
- 過程——(1)從節點發送同步請求;(2)主節點執行 `BGSAVE` 生成一份 RDB 快照(fork 子進程),同時把「生成快照期間新產生的寫命令」記入緩衝區;(3)主節點把 RDB 檔案發給從節點;(4)從節點清空自己的資料、載入這個 RDB(得到主節點快照時刻的全部資料);(5)主節點再把「緩衝的那些新寫命令」發給從節點(補上快照之後的變更);(6)之後進入持續的增量複製(主節點的每個寫命令都即時傳給從節點)。
- 開銷大——要生成和傳輸整個 RDB(資料大時 fork 卡頓、網路傳輸耗時)。

**增量複製（Partial Resynchronization，Redis 2.8+）**：

- 觸發——從節點「短暫斷線後重連」,且斷線時間不長(斷線期間的寫命令還在主節點的「複製積壓緩衝區」裡)。
- 過程——從節點重連時,告訴主節點「我上次複製到的位置(複製偏移量 offset)」;主節點檢查「從這個 offset 到現在的寫命令,是否還在複製積壓緩衝區裡」——如果在,就只把「這段增量的寫命令」補發給從節點(不用全量);如果不在(斷線太久、緩衝區裡的舊命令已被覆蓋),就只能退回全量複製。
- 關鍵組件——「複製積壓緩衝區(repl backlog)」:主節點維護的一個固定大小的環形緩衝區,持續記錄最近的寫命令,供斷線重連的從節點做增量;「複製偏移量(offset)」:主從各自記錄複製到的位置,用於判斷從哪裡開始增量;「複製 ID(replid)」:標識一次複製的身份。

## 面試回答方式

先講主從複製的作用(讀寫分離、備份、高可用基礎)。全量 vs 增量是核心——講清楚「全量:第一次或斷線太久,主節點發 RDB + 緩衝命令,從節點載入」和「增量:短暫斷線重連,只補發斷線期間積壓的寫命令(靠複製積壓緩衝區 + 偏移量)」。要點出「增量避免了每次斷線都全量的巨大開銷」這個增量複製的價值。能講出增量複製的三個關鍵組件(複製積壓緩衝區、複製偏移量、複製 ID)和「斷線太久緩衝區被覆蓋就退回全量」,展現你理解增量複製的機制而非只知道有這回事。

## 常見追問

### 複製積壓緩衝區的大小為什麼重要？設太小會怎樣？

**核心答案**：複製積壓緩衝區(repl backlog)是主節點用來「暫存最近的寫命令」、供斷線重連的從節點做增量複製的環形緩衝區,它的大小決定了「從節點斷線多久還能做增量複製」。如果緩衝區設太小——它能容納的寫命令就少,一旦從節點斷線的時間稍長(斷線期間主節點的寫命令量超過了緩衝區大小、把緩衝區裡『從節點還沒複製的舊命令』覆蓋掉了),從節點重連時就「無法增量」(它要的那段命令已經被覆蓋、不在緩衝區了),只能退回「全量複製」——而全量複製開銷巨大(生成傳輸整個 RDB)。所以緩衝區太小會導致「稍微斷線久一點就觸發全量複製」,頻繁的全量複製會給主節點(fork、傳輸)和網路帶來很大壓力。應該根據「網路可能斷線的時長」和「主節點的寫入速率」把緩衝區設得足夠大(能容納預期斷線時間內的寫命令量)。

**詳細解析**：複製積壓緩衝區是「增量複製能不能成功」的關鍵。它是一個「固定大小的環形緩衝區」——主節點持續把寫命令寫進去,寫滿了就從頭覆蓋(環形)。它保存的是「最近的一段寫命令歷史」。當從節點斷線重連,它要「從自己上次複製到的位置(offset)開始的那段命令」;主節點檢查「這個 offset 對應的命令是否還在緩衝區裡」——在,就增量補發;不在(已被新命令覆蓋),就只能全量。所以緩衝區的大小 = 它能保存多長的「寫命令歷史」= 從節點「最多能斷線多久還能增量」。如果緩衝區太小(比如只能存幾秒的寫命令量),那從節點只要斷線超過幾秒、期間主節點的寫命令就把緩衝區填滿並覆蓋掉了從節點需要的舊命令,重連就得全量。而全量複製代價很大——主節點要 fork 生成 RDB(大資料集時卡頓)、傳輸整個 RDB(佔網路帶寬)、從節點要清空重載;如果因為緩衝區太小導致「動不動就全量」,對系統是很大的負擔。合理的設定是——根據「網路抖動/斷線的典型時長」和「主節點的寫入速率」估算:緩衝區大小要能容納「預期最長斷線時間內產生的寫命令量」(如預期最多斷線 60 秒、寫入速率是每秒 1MB,緩衝區至少設 60MB 以上留餘量)。理解緩衝區大小對增量複製的影響,展現你理解主從複製的一個重要調優點。

**面試回答方式**：講出「複製積壓緩衝區是環形緩衝、暫存最近寫命令供斷線重連做增量、大小決定從節點斷線多久還能增量」。説明「設太小——斷線稍久緩衝區就被新命令覆蓋、從節點要的舊命令沒了、只能退回全量、而全量開銷巨大(fork+傳輸整個 RDB)、頻繁全量拖累系統」。給出調優——「根據預期斷線時長和寫入速率設足夠大」。展現你理解這個重要調優點。

### 主從複製是同步的還是非同步的？這帶來什麼問題？

**核心答案**：Redis 的主從複製預設是「非同步」的——主節點執行完寫命令、「立即返回成功給客戶端」,然後才「非同步地」把這個寫命令傳播給從節點(不等從節點確認)。這帶來的問題是「資料可能丟失」和「主從短暫不一致」——(1)主節點寫成功後、還沒複製給從節點就宕機了,那麼這個「已經返回成功但沒複製出去」的寫入就丟失了(新主節點沒有這個資料);(2)主從之間有「複製延遲」,從節點的資料總是比主節點「慢一點」,所以「寫主節點後立即讀從節點」可能讀到舊值(讀寫分離時的一致性問題)。非同步複製是「效能」和「一致性」的取捨——非同步不用等從節點確認、主節點的寫入延遲低、吞吐高,代價是弱一致(可能丟少量資料、主從短暫不一致)。

**詳細解析**：這個「非同步複製」的特性是理解 Redis 主從一致性(以及前面分散式鎖（Distributed Lock）失效)問題的關鍵。非同步的含義——主節點處理一個寫命令的流程是:執行命令(改自己的資料)→ 立即回覆客戶端成功 → 之後(非同步地)把命令發給從節點。注意「回覆客戶端成功」發生在「複製給從節點」之前——所以「客戶端收到成功」不代表「資料已經複製到從節點」。這帶來兩個問題。**資料丟失**——如果主節點「回覆成功後、複製給從節點前」宕機了,這個寫入只存在於已宕機的主節點、沒傳到從節點;哨兵故障轉移後,新主(原從節點)沒有這個資料,於是這個「客戶端以為成功了」的寫入就永久丟失了。這也是前面分散式鎖在主從切換失效的根源。**主從不一致(複製延遲)**——因為複製是非同步的、有網路傳輸時間,從節點的資料總是比主節點延遲一點(複製延遲,通常很小但存在);所以做「讀寫分離」時,「剛寫入主節點、立即去讀從節點」可能讀到「還沒複製過來的舊值」,造成「讀不到自己剛寫的資料」的困惑。這是非同步複製的固有代價。為什麼 Redis 選非同步——因為「同步複製」(主節點要等從節點都確認才回覆客戶端)會大幅增加寫入延遲(每個寫都要等網路往返和從節點處理),抵銷 Redis 的高效能;非同步犧牲了一點一致性(可能丟少量資料、短暫不一致)換取了低延遲高吞吐。Redis 也提供了 `WAIT` 命令和 `min-replicas-to-write` 等配置,可以要求「寫入至少複製到 N 個從節點才算成功」來增強一致性（Strong Consistency）(半同步),但會犧牲效能。理解非同步複製及其帶來的資料丟失和主從不一致問題,展現你理解 Redis 主從的一致性本質。

**面試回答方式**：講出「預設非同步——主節點寫完立即回客戶端成功、之後才非同步複製給從節點(不等確認)」。講兩個問題——「資料丟失(主節點回覆成功後、複製前宕機、這個寫入丟了、也是分散式鎖失效的根源)、主從不一致(複製延遲、讀寫分離時剛寫主立即讀從可能讀到舊值)」。點出「非同步是效能和一致性的取捨(低延遲高吞吐 vs 弱一致)、可用 WAIT/min-replicas 增強一致但犧牲效能」。展現你理解 Redis 主從的一致性本質。

### 讀寫分離時，怎麼處理「從節點讀到舊資料」的問題？

**核心答案**：從節點因為複製延遲、資料比主節點舊,讀寫分離時可能讀到舊值,處理方法要看業務對一致性的要求——(1)**對一致性要求高的讀,直接讀主節點**:某些「必須讀到最新」的場景(如剛下單後查詢訂單、剛支付後查餘額),就不走從節點、直接讀主節點(犧牲讀寫分離的分攤效果、換強一致);(2)**接受最終一致**:對「舊一點沒關係」的場景(如瀏覽商品列表、看歷史資料),容忍從節點的短暫延遲(反正很快會同步過來);(3)**寫後讀主一段時間**:剛寫入的資料,在一小段時間內(複製延遲的預期時長內)相關的讀都走主節點,過了這段時間再走從節點;(4)**監控複製延遲**:如果某個從節點延遲過大(如網路問題),把它從讀的節點池裡摘掉。核心是——「根據每個讀操作對一致性的要求,決定它走主還是從」,而非一刀切。

**詳細解析**：讀寫分離的「從節點讀到舊資料」問題,本質是「用一致性換讀取的擴展性」——你把讀分攤到從節點提升了讀吞吐,但代價是從節點有複製延遲、可能讀到舊值。處理的核心思路是「按讀操作的一致性要求分類、區別對待」。**要求強一致的讀走主節點**——有些讀操作「必須是最新的」,典型是「寫後立即讀」(read-your-writes):使用者剛下了單、馬上查訂單列表,如果查從節點、訂單還沒複製過來、使用者看不到自己剛下的單,體驗很差;這種就該讀主節點,保證讀到自己剛寫的。**能容忍的讀走從節點**——大量的讀是「不要求絕對最新」的(瀏覽、統計、歷史查詢),這些走從節點、享受讀分攤,舊一點點無所謂。**寫後讀主的時間窗**——一個折衷:對某個使用者剛寫入後的一小段時間(如幾秒,覆蓋複製延遲),他的相關讀都走主(保證讀到自己剛寫的),過了這段時間認為已複製到從、再走從節點。**摘除延遲過大的從節點**——監控每個從節點的複製延遲(offset 差距),如果某個從節點因為網路或負載問題延遲很大(讀它會讀到很舊的資料),就暫時把它從讀池裡摘掉、不讓它服務讀請求,等它追上再放回。這些方法的共同點是「不一刀切、按需決定走主還是從」——這也是分散式系統中「一致性 vs 可擴展性」權衡的典型體現。理解按一致性要求區別對待讀操作,展現你能處理讀寫分離的實際一致性問題。

**面試回答方式**：講出「按讀操作的一致性要求區別對待——要求強一致的讀(如寫後立即讀、剛下單查訂單)走主節點、能容忍的讀(瀏覽、歷史)走從節點、寫後一小段時間內相關讀走主(覆蓋複製延遲)、監控並摘除延遲過大的從節點」。強調「核心是按需決定走主還是從、而非一刀切、是一致性 vs 可擴展性的權衡」。展現你能處理讀寫分離的實際一致性問題。
