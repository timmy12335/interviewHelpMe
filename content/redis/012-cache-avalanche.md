# 題目

什麼是快取雪崩（Cache Avalanche）？怎麼解決？

## 核心答案

快取雪崩是指——「大量的 key 在同一時間集中過期失效」，或「Redis 整個宕機不可用」，導致原本被快取擋著的海量請求「同時」全部打到資料庫，資料庫瞬間承受巨大壓力被壓垮（像雪崩一樣連鎖崩潰）。它和擊穿的區別是——擊穿是「單個熱點 key」過期、雪崩是「大量 key 同時失效或 Redis 整體掛掉」。解決方法——（1）**過期時間加隨機值**：避免大量 key 設相同的過期時間、集中過期（讓過期時間分散開）；（2）**Redis 高可用**：用主從 + 哨兵或叢集，避免 Redis 單點宕機導致全部快取失效；（3）**多級快取**：如本地快取 + Redis，一層失效還有另一層兜底；（4）**服務降級（Service Degradation）/熔斷/限流（Rate Limiting）**：資料庫壓力過大時，限流或降級保護資料庫。

## 詳細解析

**快取雪崩的兩種成因**：

1. **大量 key 集中過期**——如果在某個時刻（如系統啟動時、或某次批量操作）給大量 key 設了「相同的過期時間」，那麼到了那個時間點，這些 key 會「同時」過期失效，於是原本命中這些 key 的大量請求瞬間全部快取未命中、同時打到資料庫。
2. **Redis 整體宕機**——如果 Redis 服務整個掛了（或網路不通），那麼所有的快取都不可用，所有請求都直接打到資料庫，資料庫瞬間承受平時幾十倍的壓力。

**和擊穿的區別**：擊穿是「單個熱點 key」過期的瞬間並發、雪崩是「大量 key 同時失效 / Redis 整體不可用」——範圍不同（一個 vs 大量/整體）。

**解決方法**：

1. **過期時間加隨機值**——針對「集中過期」：給 key 設過期時間時，在基礎過期時間上「加一個隨機的偏移量」（如 `基礎時間 + random(0, 300)秒`），讓大量 key 的過期時間「分散」在一個範圍內，而不是集中在同一時刻，避免同時過期。這是最簡單有效的針對集中過期的手段。

2. **Redis 高可用**——針對「Redis 宕機」：用主從複製 + 哨兵（Sentinel）或 Redis Cluster 部署，保證 Redis 的高可用——主節點掛了能自動故障轉移到從節點，避免「Redis 單點故障導致全部快取失效」。

3. **多級快取**——加一層「本地快取」（如應用內的 Caffeine/Guava Cache）作為第一級、Redis 作為第二級：即使 Redis 失效或某些 key 過期，本地快取還能擋一部分請求，不會全部打到資料庫。

4. **服務降級、熔斷、限流**——作為最後防線：當偵測到資料庫壓力過大（或 Redis 不可用），透過限流（限制打到資料庫的請求量）、熔斷（暫時拒絕部分請求）、降級（返回預設值/舊資料/友善提示）來保護資料庫不被壓垮，犧牲部分請求的體驗換取整體系統不崩潰。

## 面試回答方式

先講清楚雪崩的「兩種成因」——大量 key 集中過期、或 Redis 整體宕機，並和擊穿區分（雪崩是大量/整體、擊穿是單個熱 key）。解法要對應成因講——過期加隨機（針對集中過期）、Redis 高可用（針對宕機）、多級快取（兜底）、限流降級熔斷（最後防線）。這題的關鍵是「解法要對症」——集中過期就用過期加隨機、Redis 宕機就用高可用。能把「成因 → 對應解法」清楚對應起來，並提到「限流降級作為最後防線保護資料庫」，展現你有系統性的防護思路而非零散的解法。

## 常見追問

### 過期時間加隨機值具體怎麼做？為什麼有效？

**核心答案**：做法很簡單——給 key 設過期時間時，不用一個固定值，而是「固定的基礎時間 + 一個隨機的偏移量」。例如原本想設 1 小時過期，改成「1 小時 + random(0 到 10 分鐘)」，這樣不同的 key 雖然大約都是 1 小時後過期，但實際過期時刻分散在「1 小時到 1 小時 10 分」這個範圍內、不會集中在同一秒。它有效的原因是——快取雪崩的一種成因是「大量 key 在同一時刻集中過期、同時打 DB」，而加隨機把這些 key 的過期時刻「打散」到一個時間範圍內，於是同一時刻過期的 key 就少了很多，重建快取的請求被分散到不同時刻、不會瞬間全湧向資料庫，資料庫的壓力就從「瞬間的尖峰」變成了「平緩的分佈」。

**詳細解析**：這是針對「集中過期型雪崩」最簡單、最直接有效的手段。理解它為什麼有效——問題的本質是「同一時刻大量 key 過期→大量請求同時 miss→同時打 DB→DB 尖峰壓力」。加隨機偏移打破了「同一時刻」這個關鍵——如果一萬個 key 都設「整整 1 小時」過期，那 1 小時後的那一秒，這一萬個 key 同時過期，對應的大量請求同時 miss、同時查 DB，DB 瞬間承受一萬個 key 重建的壓力尖峰。如果改成「1 小時 + random(0~600 秒)」，這一萬個 key 的過期時刻就均勻分散在了 10 分鐘的範圍內——平均每秒只有十幾個 key 過期，對應的重建請求也分散在 10 分鐘裡，DB 每一刻只需處理少量重建、壓力平緩，不會有尖峰。這個「加隨機打散過期時刻」的技巧成本極低(就是設過期時間時加個隨機數)、效果卻很好，是防集中過期雪崩的首選。要注意隨機範圍要合理——太小(如隨機幾秒)打散效果不夠、太大(如隨機幾小時)可能讓部分 key 過早或過晚過期影響快取效果，一般取基礎時間的一個合理比例。理解這個技巧的原理(打散過期時刻、把尖峰變平緩)，展現你理解防雪崩的核心思路之一。

**面試回答方式**：講出做法——「過期時間 = 固定基礎時間 + 隨機偏移(如 1 小時 + random(0~10 分))、讓 key 的過期時刻分散而非集中」。解釋有效原因——「打破了『同一時刻大量 key 過期』、把過期時刻打散到一個範圍、同一刻過期的 key 少了、重建請求分散、DB 壓力從尖峰變平緩」。能點出「成本極低效果好、是防集中過期雪崩的首選、隨機範圍要合理」，展現你理解這個技巧的原理。

### 多級快取（本地快取 + Redis）有什麼優缺點？

**核心答案**：多級快取是「在 Redis 之前再加一層本地快取(應用進程內的快取，如 Caffeine)」——請求先查本地快取、miss 再查 Redis、再 miss 才查 DB。優點——(1)更快(本地快取在應用進程內、無網路開銷，比查 Redis 還快);(2)減輕 Redis 壓力(熱點請求被本地快取擋掉、不用都打到 Redis);(3)防雪崩兜底(即使 Redis 整個掛了，本地快取還能擋一部分請求、不會全部打 DB)。缺點——(1)一致性更難(現在有本地快取和 Redis 兩層，資料更新時要讓兩層都失效/更新，多台應用機器各自的本地快取更難統一);(2)佔用應用的記憶體;(3)本地快取容量有限(只能放最熱的一小部分)。所以多級快取適合「有明確熱點資料、對一致性要求不是極致」的場景。

**詳細解析**：多級快取是應對高並發和防雪崩的一個進階手段，核心是「用多層快取分攤壓力、層層兜底」。它的優勢很實在——本地快取在應用進程內存(記憶體直接存取、沒有網路往返)，所以查本地快取比查 Redis 更快(Redis 再快也要一次網路 IO);而且熱點資料被本地快取擋住後，大量請求根本不會到 Redis，大幅減輕了 Redis 的壓力(對於極熱的 key，見熱 key 問題，本地快取是重要的緩解手段);最重要的是防雪崩兜底——萬一 Redis 整個掛了，本地快取還能擋住那些熱點請求，不至於所有請求都瞬間打到 DB。但多級快取的代價也不小——最大的挑戰是「一致性」:原本只有 Redis 一層，資料更新時讓 Redis 失效就好;現在多了本地快取，而且應用通常是多台機器(每台都有自己的本地快取)，資料更新時要讓「所有機器的本地快取 + Redis」都失效/更新，這很難做到即時和一致(通常本地快取只能設較短的過期時間、容忍短暫的不一致，或透過訊息廣播通知各機器失效本地快取)。此外本地快取佔應用記憶體、容量有限(只能放最熱的極少數 key)。所以多級快取是「用一致性的複雜度、換取更高的效能和更強的兜底」——適合有明確熱點、且能容忍本地快取短暫不一致的場景。理解多級快取的優缺點，展現你能權衡這個進階方案的取捨。

**面試回答方式**：講出「多級快取=本地快取(如 Caffeine)+ Redis、先查本地再查 Redis 再查 DB」，優點「更快(進程內無網路)、減輕 Redis 壓力、Redis 掛了本地兜底防雪崩」，缺點「一致性更難(多層+多機器的本地快取難統一，常靠短過期或訊息廣播失效)、佔應用記憶體、容量有限」。給出適用場景——「有明確熱點、對一致性要求不極致」。展現你能權衡這個進階方案的取捨。

### 快取雪崩時，為什麼限流和降級是「最後防線」？

**核心答案**：因為前面的手段(過期加隨機、高可用、多級快取)都是「盡量避免大量請求打到資料庫」，但它們不能 100% 保證——萬一還是有大量請求湧向資料庫(如遇到極端流量、或多個防護同時失效)，就需要一個「最後的保護資料庫、防止它被壓垮」的手段，這就是限流和降級。限流——限制「同時打到資料庫的請求數量」(超過的請求直接拒絕或排隊)，保證資料庫的負載在它能承受的範圍內、不被壓垮。降級——當資料庫壓力過大或不可用時，不再查資料庫，而是「返回一個預設值、舊資料、或友善的提示(如『系統繁忙請稍後』)」，犧牲這部分請求的完整體驗，換取「資料庫不崩潰、系統整體還能運作」。它們是「最後防線」是因為——它們不追求「讓所有請求都成功」，而是「在最壞情況下，犧牲部分請求、保住核心系統(資料庫)不崩潰」，是兜底的、保命的手段。

**詳細解析**：這題體現了「分層防禦、最後兜底」的系統設計思想。防快取雪崩是一個「多層防禦」的體系——第一層(過期加隨機)防集中過期、第二層(Redis 高可用)防 Redis 宕機、第三層(多級快取)兜底一部分、但這些都是「盡量減少打到 DB 的請求」，無法保證 DB 絕對不會過載(極端情況總可能發生:突發的超大流量、多個防護同時出問題、或有預料之外的熱點)。所以需要「最後一道防線」——直接保護資料庫這個「最脆弱、最不能崩的核心」。限流的邏輯是——資料庫有一個承載上限，超過就會崩;那我就在入口處「限制放行的請求數」，只讓資料庫能承受的量進去、多的拒絕(返回錯誤或排隊)，這樣資料庫始終在安全負載內、不會崩。降級的邏輯是——當實在扛不住時(資料庫壓力過大/掛了)，與其讓請求都卡死等待(甚至拖垮整個應用)，不如「快速返回一個降級的結果」(預設值、快取的舊資料、或提示)，讓使用者至少得到一個(可能不完整的)響應、系統不至於整體卡死。這兩者的共同哲學是——「在最壞情況下，寧可犧牲部分請求的完整性/成功率，也要保住核心系統不崩潰」，這是「可用性優先」的取捨(部分降級的可用 > 整體崩潰的不可用)。理解限流降級作為「保命的最後防線」以及背後「犧牲局部保全整體」的思想，展現你有系統性的高可用設計意識。

**面試回答方式**：講出「前面的手段(過期加隨機、高可用、多級快取)是盡量減少打 DB 的請求、但不能 100% 保證、極端情況仍可能大量打 DB」，所以需要限流降級作為「保護 DB 不崩潰的最後防線」。說明「限流——限制打到 DB 的請求數、保證 DB 在承受範圍內;降級——DB 壓力大時返回預設值/舊資料/提示、犧牲部分請求換 DB 不崩」。能提煉出「犧牲局部保全整體、可用性優先」的思想，展現你有系統性的高可用設計意識。
