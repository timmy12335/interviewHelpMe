# 題目

Redis 的 AOF 持久化是什麼？它怎麼工作？AOF 重寫是做什麼的？

## 核心答案

AOF（Append Only File，追加檔案）是 Redis 的另一種持久化方式——它記錄「每一個修改資料的寫命令」（以 Redis 協定格式追加到 AOF 檔案）。恢復時Redis 重新執行 AOF 檔案中的所有命令來還原資料。它的資料安全性比 RDB 高（可以配置每次寫命令或每秒同步到磁碟，丟失的資料很少），但檔案體積較大、恢復較慢。「AOF 重寫」是為了解決「AOF 檔案越來越大」的問題——它用一個更緊湊的方式重新生成 AOF（只保留「能還原當前資料的最少命令」，去掉冗餘的歷史命令），壓縮檔案體積。

## 詳細解析

**AOF 的工作原理**：

1. 每執行一個「修改資料的寫命令」（如 SET、DEL、LPUSH），Redis 就把這個命令追加到 AOF 緩衝區。
2. 根據 `appendfsync` 配置的策略，把緩衝區的命令同步（fsync）到磁碟的 AOF 檔案。
3. 恢復時——Redis 啟動載入 AOF 檔案，重新執行裡面的所有命令，一步步還原到最後的資料狀態。

**三種 fsync 同步策略（appendfsync）**：

- **`always`**：每個寫命令都立即 fsync 到磁碟。最安全（幾乎不丟資料），但最慢（每個命令都要等磁碟寫入）。
- **`everysec`（預設，推薦）**：每秒 fsync 一次。折衷——最多丟失 1 秒的資料，效能好。
- **`no`**：不主動 fsync，交給作業系統決定何時刷盤。最快但可能丟失較多資料（作業系統緩衝的資料在宕機時丟失）。

**AOF 重寫（rewrite）**：

- 問題——AOF 記錄每一個寫命令，隨著時間推移，檔案會越來越大，且有大量「冗餘」（例如對同一個 key `INCR` 了 100 次，AOF 裡就有 100 條 INCR 命令，但其實用 1 條 `SET key 100` 就能還原）。
- 解法——AOF 重寫：不是讀取和壓縮舊的 AOF，而是「根據當前記憶體中的資料狀態，直接生成一組『能還原當前資料的最少命令』」寫入新 AOF 檔案，替換舊的。這樣去掉了所有冗餘的歷史命令，大幅縮小檔案。
- 觸發——自動（`auto-aof-rewrite-percentage` 和 `auto-aof-rewrite-min-size`，當 AOF 增長到一定比例和大小時觸發）或手動（`BGREWRITEAOF`）。
- 重寫也是 fork 子進程做（不阻塞主進程）——子進程根據當前資料生成新 AOF，期間主進程新產生的寫命令會記到緩衝區，重寫完再追加到新 AOF，保證不丟資料。

## 面試回答方式

先講「AOF 記錄每個寫命令、恢復時重放這些命令」。三種 fsync 策略是必考——講清 always（最安全最慢）、everysec（預設、折衷、最多丟 1 秒）、no（最快最不安全），並說明 everysec 是推薦的平衡點。AOF 重寫是另一個重點——講清「問題是檔案越來越大且有冗餘、解法是根據當前資料生成最少命令的新 AOF」，尤其「重寫不是壓縮舊檔案而是按當前資料重新生成」這個關鍵。能對比 AOF 和 RDB 的安全性差異（AOF 更安全但檔案大恢復慢），展現你理解兩者的定位。

## 常見追問

### AOF 的三種同步策略該怎麼選？everysec 為什麼是推薦的？

**核心答案**：選擇取決於「對資料安全性和效能的權衡」。`always`（每命令 fsync）最安全但效能最差（每個寫命令都要等磁碟同步完成，大幅降低吞吐），只在「絕對不能丟任何資料」的極端場景用。`no`（不主動 fsync）效能最好但最不安全（可能丟失作業系統緩衝裡的較多資料，宕機時丟的量不可控），很少用。`everysec`（每秒 fsync）是推薦的——它在安全和效能之間取得了很好的平衡：最多只丟失 1 秒的資料（一個很小的、可接受的量），同時效能接近不同步（因為 fsync 每秒才做一次、且由後台執行緒做、不阻塞每個命令）。所以絕大多數場景用 everysec——用「最多丟 1 秒」這個小代價換取好效能，是最務實的選擇。

**詳細解析**：這三種策略本質是「持久化的即時性 vs 效能」的取捨光譜。`always` 在光譜的「最安全」端——每個寫命令都同步刷盤，保證命令一旦返回成功、資料就一定在磁碟上（宕機也不丟），但代價是每個寫都要等磁碟 IO（磁碟比記憶體慢幾個數量級），吞吐量大幅下降，把 Redis 的高效能優勢抵銷了大半。`no` 在「最快」端——完全不管刷盤、交給作業系統（作業系統通常會攢一批資料才刷一次），效能最好，但宕機時作業系統緩衝裡還沒刷盤的資料全丟了，而且丟多少不可控（取決於作業系統的刷盤時機，可能是幾十秒的資料）。`everysec` 在中間的甜蜜點——每秒刷一次盤，且這個 fsync 由後台執行緒非同步做（不阻塞主執行緒處理命令，所以對效能影響很小），代價只是「宕機時最多丟最近 1 秒還沒刷盤的資料」。對絕大多數應用，「最多丟 1 秒資料」是完全可以接受的（1 秒的資料量不大、且很多場景本身就允許少量丟失），而換來的是接近無同步的效能。所以 everysec 是「安全性夠用 + 效能夠好」的最佳平衡，是官方推薦和絕大多數場景的選擇。理解這個權衡光譜和為什麼 everysec 是甜蜜點，展現你能做務實的技術權衡。

**面試回答方式**：講出三種策略在「安全 vs 效能」光譜上的位置——「always 最安全最慢（每命令刷盤）、no 最快最不安全（丟量不可控）、everysec 是甜蜜點（每秒刷、後台做不阻塞、最多丟 1 秒）」。強調「everysec 用最多丟 1 秒的小代價換好效能、是務實的最佳平衡、絕大多數場景用它」。展現你能做務實的技術權衡。

### AOF 重寫時，主進程新產生的寫命令會丟失嗎？怎麼保證不丟？

**核心答案**：不會丟。AOF 重寫是 fork 子進程來做的（子進程根據 fork 那一刻的資料快照生成新 AOF），而重寫期間主進程仍在處理新的寫命令——為了不丟失這些新命令，Redis 用一個「AOF 重寫緩衝區」：重寫期間，主進程執行的每個新寫命令，除了正常寫入現有的 AOF，還會「額外追加到一個 AOF 重寫緩衝區」。當子進程完成新 AOF 的生成後，主進程再把「重寫緩衝區裡的這些新命令」追加到新 AOF 檔案的末尾，然後用新 AOF 替換舊的。這樣——新 AOF = 子進程根據 fork 時刻資料生成的部分 + 重寫期間累積的新命令，完整地包含了所有資料，不丟失任何重寫期間的寫入。

**詳細解析**：這個機制和 RDB 的 fork + COW 有異曲同工之處——都要解決「後台生成持久化檔案時、主進程還在改資料」的問題，但 AOF 重寫的解法不同（因為 AOF 是命令日誌而非資料快照）。問題是——子進程 fork 出來後，它看到的是 fork 那一刻的資料快照，它根據這個快照生成新 AOF；但主進程在子進程忙著生成的這段時間裡，還在處理新的寫命令、改變資料。如果不處理，這些新命令就不會出現在子進程生成的新 AOF 裡（子進程只知道 fork 時刻的資料），恢復時就會丟失這段時間的資料。Redis 的解法是「AOF 重寫緩衝區」——重寫期間主進程執行的每個寫命令，都額外複製一份到這個緩衝區暫存;等子進程生成完新 AOF（包含 fork 時刻的所有資料），主進程把緩衝區裡累積的這些「重寫期間的新命令」追加到新 AOF 末尾。這樣新 AOF 就 = 「fork 時刻的完整資料（子進程生成）」+「重寫期間的增量命令（緩衝區）」，涵蓋了直到重寫完成時刻的所有資料，一條不丟。理解這個「重寫緩衝區保證增量命令不丟」的機制，展現你對 AOF 重寫的完整理解。

**面試回答方式**：講出「不會丟——用 AOF 重寫緩衝區：重寫期間主進程的新寫命令額外追加到重寫緩衝區、子進程生成完新 AOF 後主進程把緩衝區的新命令追加到新 AOF 末尾、再替換舊的」。強調「新 AOF = fork 時刻資料（子進程生成）+ 重寫期間增量（緩衝區）、涵蓋所有資料不丟」。展現你對 AOF 重寫機制的完整理解。

### AOF 檔案損壞（如寫入一半宕機）能恢復嗎？

**核心答案**：通常能。AOF 是「追加寫」的——如果在追加一個命令的過程中宕機，導致 AOF 檔案末尾有一條「不完整的命令」，Redis 提供了 `redis-check-aof` 工具來修復：它會掃描 AOF、找到最後一條完整命令的位置、把後面那條不完整的殘缺命令截斷掉（用 `--fix` 選項），這樣 AOF 就恢復成「一組完整命令」可以正常載入（只丟失了最後那條沒寫完的命令，損失極小）。另外可以配置 `aof-load-truncated yes`（預設開啟），讓 Redis 載入 AOF 時如果遇到末尾不完整的命令，自動忽略它並繼續載入（而不是拒絕啟動）。所以 AOF 的損壞通常只影響「最後一條沒寫完的命令」，容易修復、損失很小。

**詳細解析**：AOF 損壞的常見情況是「寫入命令的過程中宕機/斷電」——因為 AOF 是不斷追加命令的，如果正在把一條命令追加到檔案時突然斷電，檔案末尾就會留下半條殘缺的命令。這種損壞和 RDB 的損壞不同——RDB 是一個整體的二進位快照，中間損壞可能導致整個檔案無法解析;AOF 是一條條獨立的命令，損壞通常只在末尾（最後一條沒寫完），前面的命令都是完整的。所以 AOF 的損壞恢復相對簡單——`redis-check-aof --fix` 掃描檔案、保留到「最後一條完整命令」為止、截斷掉末尾殘缺的部分，這樣就得到一個全是完整命令的 AOF，能正常載入，只損失了最後那條沒寫完的命令(通常是宕機瞬間那一條，損失極小)。`aof-load-truncated yes` 更是讓這個過程自動化——Redis 載入 AOF 時遇到末尾不完整的命令自動忽略、繼續啟動，不用手動修復。這也是 AOF 相比 RDB 在「損壞容忍度」上的一個優勢——命令日誌的結構讓部分損壞（末尾殘缺）容易處理，不會像快照那樣一損俱損。理解 AOF 損壞的特點(通常在末尾、易修復)和恢復方法，展現你對 AOF 可靠性的實務認識。

**面試回答方式**：講出「通常能——AOF 是追加寫、損壞通常只在末尾（最後一條沒寫完）、用 redis-check-aof --fix 截斷末尾殘缺命令、或 aof-load-truncated yes 自動忽略末尾不完整命令、只損失最後一條」。能對比「AOF 命令日誌結構讓末尾損壞易處理、不像 RDB 快照可能一損俱損」，展現你對 AOF 可靠性的實務認識。
