# 題目

什麼是快取擊穿？它和快取穿透有什麼區別？怎麼解決？

## 核心答案

快取擊穿是指——一個「熱點 key」（被大量並發請求存取的 key）在「快取過期的那一瞬間」，大量並發請求同時發現快取失效，於是「同時」全部穿透到資料庫去查詢並重建快取，造成資料庫瞬間承受巨大壓力（可能被壓垮）。它和快取穿透的區別是——穿透查的是「根本不存在的資料」（DB 也沒有），擊穿查的是「存在的熱點資料、只是快取剛好過期了」。解決方法主要有——（1）**互斥鎖**：快取失效時，只讓「一個」請求去查資料庫重建快取，其他請求等待或稍後重試（避免大量請求同時查 DB）；（2）**熱點資料不過期**（或邏輯過期）：對極熱的 key 不設過期時間，或用「邏輯過期」的方式後台非同步更新。

## 詳細解析

**快取擊穿的成因**：一個熱點 key（如首頁的熱門商品、爆款活動的資料）被非常多的並發請求存取。平時這些請求都命中快取、不壓資料庫。但當這個 key 的快取「過期失效」的那一刻——在快取被重建之前的極短時間裡，所有並發請求都會「快取未命中」，於是它們「同時」都去查資料庫、都想重建快取。這一瞬間，本來被快取擋著的大量請求全部湧向資料庫，資料庫可能瞬間被這波並發壓垮。

**和快取穿透的區別**：

- **穿透**——查的是「不存在的資料」（快取和 DB 都沒有），問題是「每次都穿透」（因為結果是空、不會被快取）。
- **擊穿**——查的是「存在的熱點資料」，問題是「快取過期的瞬間，大量並發同時重建」。
- 一個是「查不存在的」、一個是「熱點 key 過期瞬間的並發重建」。

**解決方法一：互斥鎖（Mutex Lock）**：

- 做法——當一個請求發現快取失效、要去查資料庫重建時，先「搶一把鎖」（如用 Redis 的 `SETNX` 分散式鎖）；搶到鎖的那「一個」請求去查資料庫、重建快取、然後釋放鎖；其他沒搶到鎖的請求，「等待一下再重試讀快取」（此時快取可能已被重建好、直接命中）。
- 效果——保證「只有一個請求去查資料庫」，其他請求等它重建好後直接命中快取，避免了大量並發同時打到資料庫。
- 注意——鎖要設過期時間（防止持鎖的請求掛了導致死鎖）、要處理等待/重試邏輯。

**解決方法二：熱點資料不過期 / 邏輯過期**：

- 「不設過期」——對極熱的 key 乾脆不設過期時間，讓它一直在快取裡（配合資料更新時主動更新快取）。
- 「邏輯過期」——不用 Redis 的真實過期，而是在 value 裡存一個「邏輯過期時間」欄位；請求讀到後，如果發現邏輯上過期了，就（用互斥鎖讓一個請求）「非同步」地後台更新快取，而當前請求先返回「舊資料」（可接受短暫的舊資料，換取不阻塞、不打 DB）。

## 面試回答方式

先清楚區分「擊穿 vs 穿透」——這是這題最容易混淆、也最該先講清的：穿透查不存在的資料、擊穿是熱點 key 過期瞬間的並發重建。然後講擊穿的成因（熱點 key 過期瞬間大量並發同時查 DB）。兩個解法——互斥鎖（只讓一個請求查 DB 重建、其他等待/重試）是最常考的，要講清楚機制；熱點不過期/邏輯過期作為補充。能講清「互斥鎖如何把『大量並發查 DB』變成『只有一個查、其他等結果』」，並提到鎖要設過期防死鎖，展現你理解解法的實作細節。

## 常見追問

### 用互斥鎖解決擊穿時，有什麼要注意的細節？

**核心答案**：幾個關鍵細節——（1）**鎖必須設過期時間**：搶到鎖的請求如果在重建快取的過程中掛了（沒釋放鎖），會導致其他請求永遠搶不到鎖（死鎖），所以鎖要設一個合理的過期時間作為兜底（見 [[014-distributed-lock.md]]）；（2）**沒搶到鎖的請求怎麼辦**：可以「短暫等待後重試讀快取」（此時快取可能已被重建、直接命中），要避免「沒搶到就直接查 DB」（那就失去了互斥的意義）；（3）**重建快取後要先釋放鎖還是先寫快取**：應該「先寫好快取、再釋放鎖」，保證釋放鎖時快取已就緒、等待的請求重試能命中；（4）**鎖的粒度**：鎖應該是「針對這個具體的 key」的（如鎖名包含 key），不同 key 的重建不應該互相阻塞。

**詳細解析**：互斥鎖解決擊穿看似簡單（只讓一個請求查 DB），但實作有不少要注意的坑。**鎖過期（防死鎖）**——最重要的一點：搶到鎖的請求負責查 DB 重建快取，但如果它在這個過程中崩潰了、或卡住了（沒能釋放鎖），那麼其他所有請求都會一直搶不到這把鎖、一直等待，形成死鎖。所以鎖必須設過期時間——即使持鎖者掛了，鎖過期後也能被其他請求獲取。但過期時間要設得合理（比重建快取的預期耗時長一些，否則重建還沒完鎖就過期了、別的請求又進來）。**沒搶到鎖的處理**——這些請求不能「沒搶到就自己去查 DB」（那就等於沒有互斥、還是大量請求打 DB）；正確做法是「短暫 sleep 一下再重試讀快取」——因為搶到鎖的那個請求正在重建快取，等一下快取就好了、重試讀就能命中。**寫快取和釋放鎖的順序**——先把快取寫好、再釋放鎖，這樣等待重試的請求在鎖釋放後讀快取能命中（如果先釋放鎖、還沒寫快取，等待的請求可能又都 miss 了）。**鎖粒度**——鎖應該針對具體的 key（鎖名如 `lock:product:1001`），這樣不同 key 的快取重建互不影響（如果用一把全域鎖，所有 key 的重建都要排隊、效能差）。理解這些細節，展現你不只知道「用互斥鎖」這個方向、還能正確地實作它。

**面試回答方式**：講出幾個關鍵細節——「鎖設過期時間防死鎖（持鎖者掛了要能自動釋放）、沒搶到鎖的請求應等待重試讀快取而非直接查 DB、先寫快取再釋放鎖（保證等待者重試能命中）、鎖粒度針對具體 key（不同 key 重建不互相阻塞）」。能點出「防死鎖是最重要的」，展現你能正確實作互斥鎖方案而非只知道方向。

### 「邏輯過期」方案相比「真實過期 + 互斥鎖」有什麼優劣？

**核心答案**：「邏輯過期」——不用 Redis 的真實過期（key 永不真的過期），而是在 value 裡存一個「邏輯過期時間」;請求讀到後檢查是否邏輯過期,過期了就（用鎖讓一個請求）非同步後台更新快取、當前請求先返回舊資料。優點是——「請求永遠不會阻塞、也永遠不會有大量請求打 DB」(因為 key 從不真的過期、讀永遠命中、更新是後台非同步做的),延遲最穩定。缺點是——「會返回舊資料」(在後台更新完成前,讀到的是過期的舊值,有短暫的資料不一致),且實作較複雜(要維護邏輯過期欄位、後台更新邏輯)。相比之下「真實過期 + 互斥鎖」——保證讀到的是新資料(重建後),但快取真過期的瞬間,沒搶到鎖的請求要「等待重試」(有短暫的延遲/阻塞)。所以取捨是——「能接受短暫舊資料、要求延遲穩定不阻塞」用邏輯過期;「要求資料及時、能接受過期瞬間的短暫等待」用真實過期+互斥鎖。

**詳細解析**：這兩個方案的核心差異在「過期瞬間怎麼處理」——是「讓請求等新資料(互斥鎖)」還是「先給舊資料、後台換新(邏輯過期)」。**真實過期 + 互斥鎖**——key 真的會過期,過期後第一批請求會 miss,然後互斥鎖讓一個去重建、其他等待重試。優點是「重建後大家拿到的是最新資料」(強調資料新鮮);缺點是「過期瞬間有短暫的阻塞」(等待重建的那些請求要 sleep 重試,延遲會有毛刺)。**邏輯過期**——key 永不真的過期(所以讀永遠命中、永不阻塞、永不 miss 打 DB),靠 value 裡的邏輯過期時間判斷「該更新了」,發現該更新就後台非同步更新、當前請求先返回舊值。優點是「延遲極其穩定(永遠命中快取、不阻塞)、DB 壓力極小(更新是後台一個請求做)";缺點是「返回舊資料(在後台更新完成前的這段時間,所有請求讀到的都是過期的舊值)、且實作複雜」。所以選擇取決於業務對「資料新鮮度」和「延遲穩定性」的偏好——像秒殺、金融這種要求資料及時準確的,可能傾向真實過期+互斥鎖(寧可短暫等待也要新資料);像首頁展示、排行榜這種「舊一點沒關係、但要求極致的低延遲和穩定」的,傾向邏輯過期(先給舊的、後台悄悄更新)。理解這兩個方案在「資料新鮮 vs 延遲穩定」上的取捨,展現你能根據業務需求選對快取更新策略。

**面試回答方式**：講出「邏輯過期(key 不真過期、存邏輯過期時間、過期就後台非同步更新、當前請求先返回舊資料)——優點延遲穩定不阻塞、DB 壓力小,缺點返回舊資料、實作複雜;真實過期+互斥鎖——優點資料及時(重建後是新的),缺點過期瞬間有短暫等待」。給出取捨——「能接受舊資料要延遲穩定用邏輯過期、要資料及時能接受短暫等待用真實過期+互斥鎖」。展現你能根據業務需求選對策略。

### 快取穿透、擊穿、雪崩三者怎麼區分？

**核心答案**：三者都是「快取相關的、導致大量請求打到資料庫」的問題,但成因不同——**穿透**：查詢「根本不存在的資料」(快取和 DB 都沒有),每次都穿透到 DB(因為空結果不快取),常見於惡意攻擊,解法是快取空值/布隆過濾器。**擊穿**：「單個熱點 key」在「過期的瞬間」,大量並發同時重建快取都打到 DB,解法是互斥鎖/熱點不過期。**雪崩**：「大量 key 在同一時間集中過期」(或 Redis 整個宕機),導致大量請求同時打到 DB,解法是過期時間加隨機、多級快取、Redis 高可用。一句話區分——穿透查「不存在的」、擊穿是「一個熱點 key 過期」、雪崩是「大量 key 同時過期/Redis 掛了」。

**詳細解析**：這三個概念極容易混淆,能清楚區分是這一組快取問題的核心。用「範圍和成因」來區分最清楚——**穿透(penetration)**:關鍵詞是「不存在」。查的是 DB 裡也沒有的資料,所以永遠無法被快取、每次都穿過快取打到 DB。它和 key 過不過期無關,是「資料本身不存在」導致的。防禦針對「擋掉對不存在資料的查詢」(布隆過濾器、快取空值)。**擊穿(breakdown)**:關鍵詞是「單個熱點 key 過期瞬間」。查的是存在的、很熱的資料,問題出在「這一個熱 key 過期的那一刻,大量並發同時去重建」。範圍是「單個(熱點)key」、時機是「它過期的瞬間」。防禦針對「讓熱 key 過期時只有一個請求重建」(互斥鎖)或「別讓熱 key 過期」(不過期/邏輯過期)。**雪崩(avalanche)**:關鍵詞是「大量 key 同時失效」。要嘛是「大量 key 恰好設了相同的過期時間、在同一時刻集中過期」,要嘛是「Redis 整個宕機、所有 key 都不可用」,導致海量請求同時打 DB。範圍是「大量 key / 整個 Redis」。防禦針對「避免集中過期(過期時間加隨機)、保證 Redis 可用(高可用架構)、多級快取兜底」。所以三者的層次是——穿透(資料不存在)、擊穿(一個熱 key 過期)、雪崩(大量 key 同時失效/Redis 掛)。理解這個清楚的區分,能避免面試中把三者搞混,也展現你對這組快取問題有系統性的掌握。

**面試回答方式**：用「一句話區分」清楚劃分——「穿透查『不存在的資料』(每次穿透)、擊穿是『單個熱點 key 過期瞬間』的並發重建、雪崩是『大量 key 同時過期或 Redis 宕機』」,並各配解法(穿透→布隆/空值、擊穿→互斥鎖/不過期、雪崩→過期加隨機/高可用/多級快取)。能點出三者的層次(資料不存在→一個熱key→大量key/Redis),展現你對這組問題的系統性掌握。
