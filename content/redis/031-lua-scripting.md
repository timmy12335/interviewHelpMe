# 題目

Redis 的 Lua 腳本為什麼是原子的？寫腳本時有哪些限制與陷阱？

## 核心答案

原子性來自**單執行緒**——腳本被當成**一個命令**執行，執行期間 Redis 不處理任何其他請求。所以腳本裡的多個操作之間**不可能有其他客戶端介入**，這讓「讀取後判斷再寫入」這類複合操作可以安全地完成，而不需要 `WATCH`／`MULTI` 的樂觀重試。

代價也來自同一件事：**腳本執行期間整個 Redis 被阻塞**。一個跑一秒的腳本會讓所有客戶端等一秒。`lua-time-limit`（預設 5 秒）只是「超過這個時間後開始回應其他客戶端 BUSY 錯誤」，**腳本本身不會被中止**；要中止只能 `SCRIPT KILL`（僅限沒有寫入過的腳本）或 `SHUTDOWN NOSAVE`（有寫入的話只能這樣，代價極大）。

主要限制有四個。**必須聲明所有 key**——用 `KEYS` 陣列傳入而非在腳本裡拼接，否則叢集模式無法判斷路由（**這是最常被違反的一條**）。**必須是確定性的**——不能用 `math.random`（除非先 `math.randomseed`）、不能依賴系統時間；因為腳本可能被複製到從節點重放。**不能執行阻塞命令**（`BLPOP` 等）。**沒有辦法呼叫外部系統**。

## 詳細解析

**「必須聲明所有 key」在叢集模式下是硬性要求**。Redis Cluster 依 key 的雜湊槽路由請求，**如果腳本存取了沒有在 `KEYS` 中聲明的 key，那個 key 可能不在當前節點上**——結果是錯誤或（更糟）操作了錯誤的資料。而且**所有 key 必須在同一個槽**，這通常需要用 **hash tag**（`{user:1000}:profile` 與 `{user:1000}:orders` 因為大括號內相同而落在同一個槽）。**單機開發時不聲明 key 也能運作，換到叢集就壞掉**——這是一個經典的「本機好好的、上線就爆」問題。

**腳本的複製方式在 Redis 5 之後改變了**。舊版本是**複製腳本本身**到從節點重放（所以要求確定性），Redis 5 起改為**複製腳本產生的實際寫入命令**（effects replication）——這放寬了確定性的要求，但**腳本仍然應該寫成確定性的**，因為它更容易推理，而且某些場景（AOF 重寫）仍然依賴這個性質。

**`EVALSHA` 與腳本快取的實務問題**：每次 `EVAL` 都傳完整腳本很浪費頻寬，所以客戶端通常用 `SCRIPT LOAD` 取得 SHA1 再用 `EVALSHA` 呼叫。**問題是 Redis 重啟或 `SCRIPT FLUSH` 之後快取就沒了**，`EVALSHA` 會回傳 `NOSCRIPT` 錯誤。**所以客戶端必須處理這個錯誤並自動退回 `EVAL`**——多數成熟的客戶端函式庫已經做了，但自己實作時很容易漏掉，症狀是「重啟後某些功能壞掉直到重新部署」。

**Redis 7 的 Function 是 Lua 腳本的演進版**。它把腳本組織成有名稱的函式庫、可以持久化（隨 RDB 保存，重啟不會消失）、也有更好的命名空間管理。**它解決了 `EVALSHA` 的持久性問題**，但生態採用還不普遍。**在新專案上值得考慮，既有專案則沒有急迫的遷移理由。**

## 面試回答方式

先給原子性的來源——**單執行緒，腳本被當成一個命令執行**，所以中間不可能有其他客戶端介入。立刻給出代價：**執行期間整個 Redis 被阻塞**，而 `lua-time-limit` 只是開始回應 BUSY，**腳本本身不會被中止**，有寫入的話只能 `SHUTDOWN NOSAVE`。給四個限制並把**「必須聲明所有 key」**放最前面——叢集模式依 key 路由，沒聲明的 key 可能不在當前節點，而且**單機開發能跑、換到叢集就壞**，是經典的上線才爆問題；還要提到 hash tag。加分點有兩個：**`EVALSHA` 在 Redis 重啟後會回傳 NOSCRIPT**，客戶端必須自動退回 `EVAL`，漏掉的症狀是「重啟後功能壞掉直到重新部署」；以及 **Redis 7 的 Function 解決了持久性問題**但生態採用還不普遍。

## 講稿

原子性來自單執行緒。腳本被當成一個命令執行，執行期間 Redis 不處理任何其他請求。所以腳本裡的多個操作之間不可能有其他客戶端介入，讀取後判斷再寫入這類複合操作可以安全完成。

代價也來自同一件事，腳本執行期間整個 Redis 被阻塞。一個跑一秒的腳本會讓所有客戶端等一秒。而且時間限制那個設定只是超過之後開始回應其他客戶端忙碌錯誤，腳本本身不會被中止。如果腳本已經寫入過資料，想中止只能整個關掉不保存，代價極大。

限制我認為最重要的是必須聲明所有的 key，用參數陣列傳進去而不是在腳本裡拼接。因為叢集依 key 的雜湊槽路由請求，沒有聲明的 key 可能根本不在當前節點上。而且所有 key 必須在同一個槽，通常需要用雜湊標籤。

這一條在單機開發時不遵守也能跑，換到叢集就壞掉，是經典的本機好好的上線就爆。

還有一個實務問題。用雜湊值呼叫快取的腳本很省頻寬，但 Redis 重啟之後快取就沒了，會回傳找不到腳本的錯誤。客戶端必須處理這個錯誤並自動退回完整傳送。漏掉的症狀是重啟後某些功能壞掉，直到重新部署才恢復。

## 常見追問

### 什麼時候該用 Lua 腳本，什麼時候不該？

**核心答案**：**該用**的情況是「多個操作必須原子完成，而 Redis 沒有現成的單一命令」——限流器（讀計數、判斷、遞增或拒絕）、分散式鎖的安全釋放（比對持有者再刪除）、庫存扣減（檢查餘量再扣）。**不該用**的情況是：**單一命令就能完成**（`INCR`、`SETNX`、`GETSET` 已經是原子的）、**邏輯複雜或耗時**（會阻塞整個 Redis）、以及**需要外部資料**（腳本無法呼叫外部系統）。

**詳細解析**：**「把業務邏輯搬進 Lua」是一個常見的過度使用**。腳本裡的邏輯**難以測試、難以除錯、難以版本控制、也沒有型別檢查**——一個五十行的 Lua 腳本是一段沒有 IDE 支援、沒有單元測試、出錯時只有一行錯誤訊息的程式碼。**所以腳本應該盡量短，只包含「必須原子」的那幾步**，其餘邏輯留在應用層。**判斷的方式是問：如果這一步不是原子的，會發生什麼錯誤？** 答不出具體錯誤的步驟就不該放進腳本。**這個「最小原子範圍」的原則與交易邊界的設計是同一個判斷**——範圍越大，阻塞越久、風險越高，而收益往往在前幾步就拿完了。

**面試回答方式**：給該用與不該用的具體情況。真正的重點是點名**「把業務邏輯搬進 Lua」是常見的過度使用**——腳本難測試、難除錯、沒有型別檢查，五十行的腳本是一段沒有 IDE 支援的程式碼。給出原則：**只包含必須原子的那幾步**，並提供判斷方式——**問「如果這一步不是原子的會發生什麼錯誤」，答不出來就不該放進去**。收在類比：這與交易邊界的設計是同一個判斷。

### 腳本執行太久造成阻塞，怎麼處理？

**核心答案**：**預防重於處理**，因為處理的手段都很糟。預防的三個做法：**限制腳本處理的資料量**（不要在腳本裡遍歷大集合，改成分批由客戶端驅動）、**在測試環境用真實資料量壓測腳本的執行時間**、以及**設定合理的 `lua-time-limit` 並監控 BUSY 錯誤**。真的發生時：沒有寫入過的腳本可以 `SCRIPT KILL`；**已經寫入過的只能 `SHUTDOWN NOSAVE`**（因為中止會留下不一致的狀態），那意味著丟失最後一次持久化之後的所有資料。

**詳細解析**：**「已寫入的腳本無法中止」這個設計是必然的**——腳本的原子性保證意味著它「要嘛全做、要嘛全不做」，而中止一個做了一半的腳本會破壞這個保證。**Redis 選擇了保護一致性而非可用性**，這是一個明確的取捨。**這也解釋了為什麼腳本必須短**：它是唯一一個「一旦開始就無法安全中止」的操作，而其他慢命令至少可以透過客戶端超時來緩解（雖然伺服器端仍然會跑完）。**在設計任何「原子且可能長時間執行」的機制時，都應該問：如果它卡住了，我有什麼手段？** 沒有好答案的話，就必須從源頭限制它的執行時間。

**面試回答方式**：強調**預防重於處理**並給三個預防做法。說明處理手段的殘酷現實：**已寫入的腳本只能 `SHUTDOWN NOSAVE`**，意味著丟失最後一次持久化後的所有資料。真正的加分點是解釋**這個設計是必然的**——中止做了一半的腳本會破壞原子性保證，**Redis 選擇保護一致性而非可用性**。收在通用問題：設計任何「原子且可能長時間執行」的機制時，都該問**如果它卡住了我有什麼手段**，沒有好答案就必須從源頭限制執行時間。

### Redis Function 相較於 EVAL 好在哪？

**核心答案**：三點。**持久性**——Function 隨 RDB/AOF 保存，重啟後仍然存在，不會有 `NOSCRIPT` 的問題。**組織性**——腳本被組織成有名稱的函式庫，可以有多個函式、共用的輔助函式、以及明確的註冊與升級流程（`FUNCTION LOAD REPLACE`）。**明確的介面**——註冊時宣告函式名與旗標（例如標記為唯讀，讓它可以在從節點執行）。

**詳細解析**：**「腳本成為伺服器狀態的一部分」是最大的概念轉變**。`EVAL` 的腳本是「客戶端每次帶來的東西」，Function 則是「部署到伺服器上的東西」——**這讓它更像資料庫的預存程序**，也帶來了同樣的問題：**版本管理與部署流程**。誰負責載入函式？升級時怎麼確保所有節點都更新？舊版本的客戶端呼叫新版本的函式會怎樣？**這些問題在 `EVAL` 模式下不存在（腳本跟著應用一起部署），在 Function 模式下必須明確處理。** 所以它不是單純的改進，**而是把一部分邏輯的生命週期從應用移到了資料庫**——這個取捨與「該不該用預存程序」是同一個爭論，而多數現代團隊傾向把邏輯留在應用層。**認出這個取捨，比列舉 Function 的功能更有價值。**

**面試回答方式**：給三點改進（持久性、組織性、明確介面）。真正的加分點是指出概念轉變：**腳本成為伺服器狀態的一部分，更像預存程序**，因而帶來版本管理與部署流程的問題（誰載入、怎麼確保所有節點更新、舊客戶端呼叫新版本會怎樣）——**這些在 `EVAL` 模式下不存在因為腳本跟著應用部署**。收在取捨：**它把一部分邏輯的生命週期從應用移到資料庫**，與「該不該用預存程序」是同一個爭論，而多數現代團隊傾向把邏輯留在應用層。
