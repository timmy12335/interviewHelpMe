# 題目

用 Redis 做訊息佇列有哪幾種方式？什麼時候該換成專門的訊息中介軟體？

## 核心答案

三種方式，能力遞增。**List 加 `BRPOP`**——最簡單，但**訊息取走就消失**，消費者崩潰就丟失；沒有 ack、沒有廣播、沒有消費進度。**Pub/Sub**——支援廣播，但**完全不持久化**，離線就丟。**Stream 加消費者群組**——有持久化、有 ack、有待處理清單、支援競爭與廣播兩種模式，**是 Redis 上唯一可以認真考慮的佇列方案**。

即使是 Stream，與專門的訊息中介軟體相比仍有三個結構性的差距。**複製是非同步的**——主節點確認後、複製前故障就會丟訊息，**這是 Redis 架構決定的，無法透過設定完全消除**。**沒有分區**——一個 Stream 是一個有序日誌，要並行只能靠群組內的多消費者（失去順序）或自己做分流。**記憶體儲存**——長期保留大量訊息的成本很高。

**換掉的時機訊號很具體**：開始需要自己實作**死信佇列、訊息重放、分區管理、或消費延遲監控**時——**那些都是專門系統已經解決的問題，自己重做一遍就是該換的訊號。**

## 詳細解析

**「不引入新中介軟體」的價值必須被認真計入**。每個新元件帶來部署、監控、備份、升級、故障處理的成本，以及一個新的故障點與一份新的知識需求。**在團隊規模小、訊息量不大、且已經有 Redis 的情況下，用 Stream 常常是正確的工程判斷**——即使 Kafka 在紙面上「更專業」。**技術選型應該把維運成本算進去，而不只比較功能表。**

**但要誠實面對「量不大」這個前提會變**。一個從每天一萬則長到每天一億則的系統，Stream 的記憶體成本與缺乏分區會變成硬約束。**所以採用 Stream 時應該同時想好「什麼指標超過多少就該遷移」**——例如「Stream 的記憶體超過總記憶體的 20%」或「消費延遲持續超過一分鐘」。**把遷移的觸發條件寫下來，比事後臨時決定好得多**，因為那時候通常已經在救火。

**混合方案是實務上常見且合理的**：**關鍵事件走 Kafka**（訂單、支付、需要重放與長期保留），**內部的輕量任務走 Redis Stream**（快取預熱、通知推送、統計上報）。**依訊息的重要性分流**，讓成本與保證匹配——不是所有訊息都值得付出 Kafka 的維運成本。

**用 List 做佇列的唯一合理場景**是「任務丟了也沒關係且不需要任何管理能力」——即使如此，**Stream 的成本也沒有高多少**，所以新專案沒有理由選 List。**如果既有系統用 List，遷移的優先順序取決於「丟過訊息沒有」**——沒出過事的話，這通常不是最該花時間的地方。

## 面試回答方式

先給**三種方式與能力遞增**，並明確指出 **Stream 是 Redis 上唯一可以認真考慮的佇列方案**。接著給與專門中介軟體的**三個結構性差距**（非同步複製會丟訊息且無法透過設定消除、沒有分區、記憶體儲存的保留成本）。給出**換掉的具體訊號**：開始需要自己實作死信、重放、分區管理、消費延遲監控時。加分點有三個：**「不引入新中介軟體」的價值必須認真計入**——技術選型要把維運成本算進去而不只比功能表；**採用時就該想好遷移的觸發條件**並寫下來（例如記憶體佔比或消費延遲的閾值），因為事後臨時決定時通常已經在救火；以及**混合方案是合理的**——關鍵事件走 Kafka、輕量任務走 Stream，依重要性分流讓成本與保證匹配。

## 講稿

三種方式，能力遞增。用清單加阻塞式取出最簡單，但訊息取走就消失，消費者崩潰就丟失，沒有確認也沒有消費進度。發布訂閱支援廣播但完全不持久化。Stream 加消費者群組有持久化、有確認、有待處理清單，是 Redis 上唯一可以認真考慮的佇列方案。

即使是 Stream，跟專門的訊息中介軟體比仍有三個結構性差距。複製是非同步的，主節點確認後、複製前故障就會丟訊息，這是架構決定的無法透過設定消除。沒有分區。還有記憶體儲存，長期保留大量訊息的成本很高。

換掉的時機訊號很具體。開始需要自己實作死信佇列、訊息重放、分區管理、或消費延遲監控的時候。那些都是專門系統已經解決的問題，自己重做一遍就是該換的訊號。

我也想強調，不引入新中介軟體的價值必須被認真計入。每個新元件帶來部署、監控、備份、升級的成本，還有一個新的故障點。團隊小、量不大、而且已經有 Redis 的話，用 Stream 常常是正確的工程判斷。

不過採用的時候應該同時想好什麼指標超過多少就該遷移，把觸發條件寫下來。因為事後臨時決定的時候，通常已經在救火了。

## 常見追問

### 用 List 做佇列具體會遇到什麼問題？

**核心答案**：四個。**訊息丟失**——`BRPOP` 取出後訊息就從 List 消失，消費者處理到一半崩潰，那則訊息永遠不見了。**沒有重試**——失敗了沒有機制讓它重來。**看不到積壓**——`LLEN` 只告訴你佇列長度，不知道「有多少正在處理中」也不知道消費延遲。**無法廣播**——多個消費者只能競爭，不能各自消費全部。

**詳細解析**：**針對訊息丟失有一個經典的補救：`RPOPLPUSH`（或 Redis 6.2 的 `LMOVE`）**——把訊息從待處理佇列原子地移到「處理中」佇列，處理完再從後者刪除。**消費者崩潰時訊息還在「處理中」佇列裡，可以被監控與重新投遞。** 這實際上是在手工實作 Stream 的待處理清單。**而一旦你開始實作這個，就應該問「為什麼不直接用 Stream」**——它已經內建了同樣的機制，加上投遞次數統計、閒置時間追蹤、與自動轉移。**「發現自己在重新實作某個現成元件的核心機制」是一個很好的重新評估訊號**，這在很多技術決定上都適用。

**面試回答方式**：給四個問題並各配後果。真正的加分點是介紹 **`RPOPLPUSH` 的補救模式**（原子地移到處理中佇列、崩潰時還在），並指出**這實際上是在手工實作 Stream 的待處理清單**。收在通用訊號：**發現自己在重新實作某個現成元件的核心機制，就該重新評估選型**。

### 消費延遲該怎麼監控？

**核心答案**：Stream 提供了需要的資訊。**`XINFO GROUPS`** 給出每個群組的 `lag`（未消費的訊息數）與 `last-delivered-id`；**`XPENDING`** 給出待處理訊息的數量、最舊的一筆、以及每個消費者各有多少。**兩個指標要一起看**：`lag` 大表示消費速度跟不上生產，`pending` 大且最舊的很舊表示有訊息卡住沒被 ack（消費者掛了或有 bug）。

**詳細解析**：**「訊息數的延遲」與「時間的延遲」是不同的指標，而後者通常更有意義**。積壓一萬則訊息，如果消費速度是每秒一萬則，那延遲只有一秒；如果是每秒一百則，那是一百秒。**業務關心的是「這件事多久之後會被處理」，而不是「積了幾則」。** Stream 的訊息 ID 內含毫秒時間戳，**所以可以用「當前時間減去最舊未消費訊息的 ID 時間戳」直接算出時間延遲**——這是比 `lag` 更好的告警指標。**同樣的原則適用於所有佇列系統**：告警應該設在「延遲時間」上而不是「佇列長度」上，因為長度的意義取決於處理速度，而那是會變的。

**面試回答方式**：給兩個命令與各自提供的資訊，並強調**兩個指標要一起看**（lag 大是跟不上、pending 舊是卡住）。真正的加分點是區分**「訊息數的延遲」與「時間的延遲」，後者更有意義**——業務關心的是「多久會被處理」而非「積了幾則」。給出具體做法：**Stream 的 ID 內含時間戳，可以直接算出時間延遲**。收在通用原則：**告警應該設在延遲時間上而非佇列長度上**。

### 已經用 Redis 做佇列的系統，什麼時候真的該遷移？

**核心答案**：三個具體訊號。**已經丟過訊息且造成業務影響**——這是最直接的訊號，而且通常會伴隨「我們加了補償邏輯」這種症狀。**Stream 的記憶體佔比持續上升**（超過總記憶體的 20% 到 30% 就該警覺），因為那意味著訊息保留與快取在競爭記憶體。**開始需要重放歷史訊息**——Redis 的記憶體成本讓長期保留不可行，而重放是事件驅動架構的核心能力。

**詳細解析**：**遷移應該是漸進的而非一次切換**。務實的路徑是：**新的訊息類型先用新系統**、**既有的訊息在需要大改時順便遷移**、**保留一段雙寫或雙讀的過渡期**以驗證新系統的正確性。**一次性切換的風險在於「新系統的未知問題會在最忙的時候暴露」**——而訊息系統的問題往往是資料丟失或重複，那是很難事後補救的。**另外要誠實評估遷移的總成本**：不只是換一個客戶端函式庫，還包括部署與維運新系統、團隊的學習、監控與告警的重建、以及過渡期的雙軌成本。**很多遷移之所以拖著沒做，是因為只估算了程式碼改動而低估了這些**——把它們一起列出來，決策才是誠實的。

**面試回答方式**：給三個具體訊號（丟過訊息且有業務影響、記憶體佔比持續上升、開始需要重放歷史）。強調**遷移應該漸進而非一次切換**並給出路徑（新類型先用新系統、既有的在大改時順便、保留雙寫或雙讀的過渡期），理由是**一次切換的風險在於新系統的未知問題會在最忙時暴露**，而訊息系統的問題往往是丟失或重複、很難事後補救。收在誠實評估：**遷移成本不只是換客戶端，還有部署維運、學習、監控重建、雙軌成本**——很多遷移拖著沒做正是因為低估了這些。
