# 題目

Redis 6 的客戶端快取（Client-side caching）解決什麼問題？它怎麼保證一致性？

## 核心答案

問題是**熱點資料的網路往返成本**。即使 Redis 本身只要幾十微秒，跨網路的往返可能是 0.5 到 1 毫秒——對於每個請求都要讀十次快取的應用，那是幾毫秒的純粹等待。如果應用能在本地記憶體裡快取這些值，就完全省掉了往返。

**難點在於失效**：本地快取怎麼知道 Redis 裡的值變了？Redis 6 的 **Tracking** 機制解決了這件事——客戶端用 `CLIENT TRACKING ON` 告訴伺服器「我要快取這些鍵」，伺服器記住哪個客戶端快取了哪些鍵，當那些鍵被修改時主動推送失效通知。這需要 **RESP3 協定**（它為推送訊息定義了獨立的型別，所以能在同一條連線上混合命令回應與推送）。

有兩種追蹤模式。**預設模式**——伺服器精確記錄每個客戶端關心的鍵（用一個全域的表），精確但**佔用伺服器記憶體**。**廣播模式（BCAST）**——伺服器不記錄個別客戶端，而是依**鍵的前綴**廣播失效通知給所有訂閱該前綴的客戶端，不佔記憶體但可能收到不需要的通知。

它本質上是「Redis 幫你做本地快取的失效廣播」，把原本要自己用 Pub/Sub 實作的機制內建了。

## 詳細解析

**兩種模式的取捨很清楚**。預設模式的伺服器端表（invalidation table）大小與「被追蹤的鍵數量乘以客戶端數量」相關，在鍵很多或客戶端很多時可能佔用可觀的記憶體；Redis 用 `tracking-table-max-keys` 限制它的大小，超過時會主動驅逐一些追蹤項並發送失效通知（保守但正確——寧可讓客戶端多失效一次）。廣播模式沒有這個成本，但客戶端會收到所有符合前綴的失效通知，包括它根本沒快取的鍵。**選擇取決於「鍵的分佈」**：熱點集中且鍵數不多時用預設模式，鍵很分散時用廣播模式加合適的前綴。

**它不保證強一致**。失效通知是**在鍵被修改之後**發送的，客戶端收到之前的那段時間，本地快取是髒的。這個窗口通常是次毫秒級，但不是零。 而且通知可能因為連線問題丟失（雖然 Redis 會在客戶端重連時發送 flush 通知讓它清空全部快取）。所以本地快取仍然應該設一個保底 TTL——這與用 Pub/Sub 做失效廣播的建議完全相同：**不要讓正確性依賴單一機制**。

「什麼資料適合本地快取」是採用前的關鍵判斷。適合的是：讀取極頻繁、變更很少、且能容忍次毫秒級的不一致——設定資料、字典表、功能開關、以及熱點的商品或使用者資料。**不適合的是**：頻繁變更（失效通知的成本超過收益，而且命中率低）、要求強一致（庫存、餘額）、以及**資料量大**（本地快取吃的是應用行程的記憶體，而那通常比 Redis 的記憶體更寶貴）。

實務上很多團隊用的是「應用層的兩級快取」而非 Redis Tracking——本地用 Caffeine，失效用 Pub/Sub 廣播或短 TTL。Tracking 的優勢是不需要自己實作失效邏輯，劣勢是需要 RESP3 支援、客戶端函式庫的支援程度不一、且增加了伺服器的複雜度。 在已經有成熟的兩級快取實作時，遷移到 Tracking 的收益不明顯。

## 面試回答方式

先給問題——**熱點資料的網路往返成本**（Redis 幾十微秒但往返 0.5 到 1 毫秒），與難點——**本地快取怎麼知道值變了**。給出 Tracking 的機制（伺服器記住誰快取了什麼、修改時主動推送失效）並指出它**需要 RESP3**（推送有獨立型別所以能與命令回應混在同一條連線）。給**兩種模式的取捨**：預設模式精確但佔伺服器記憶體、廣播模式不佔記憶體但會收到不需要的通知。加分點有三個：**它不保證強一致**，通知在修改之後發送，窗口雖小但不是零，**所以本地快取仍應設保底 TTL**（不要讓正確性依賴單一機制）；**適合與不適合的資料類型**，特別指出本地快取吃的是應用行程的記憶體而那通常比 Redis 的更寶貴；以及誠實指出很多團隊用應用層的兩級快取而非 Tracking，在已有成熟實作時遷移收益不明顯。

## 講稿

問題是熱點資料的網路往返成本。就算 Redis 本身只要幾十微秒，跨網路的往返可能是零點五到一毫秒。對於每個請求要讀十次快取的應用，那是幾毫秒的純粹等待。如果能在本地記憶體快取，就完全省掉了往返。

難點在於失效，本地快取怎麼知道 Redis 裡的值變了。Redis 6 的追蹤機制解決了這件事。客戶端告訴伺服器我要快取這些鍵，伺服器記住哪個客戶端快取了哪些鍵，那些鍵被修改的時候主動推送失效通知。這需要新版的協定，因為它為推送訊息定義了獨立型別，可以跟命令回應混在同一條連線上。

有兩種模式。預設模式精確記錄每個客戶端關心的鍵，精確但佔伺服器記憶體。廣播模式依鍵的前綴廣播，不佔記憶體但客戶端會收到不需要的通知。

要注意它不保證強一致。失效通知是在鍵被修改之後才發送的，客戶端收到之前那段時間本地快取是髒的。窗口通常是次毫秒級但不是零。所以本地快取仍然應該設一個保底過期時間，不要讓正確性依賴單一機制。

我也要誠實說，很多團隊用的是應用層的兩級快取而不是這個機制。在已經有成熟實作的情況下，遷移過去的收益不明顯。

## 常見追問

### 本地快取的記憶體成本該怎麼控制？

**核心答案**：必須有明確的容量上限與淘汰策略，因為本地快取吃的是應用行程的堆積記憶體——**無界的本地快取會直接導致 OOM**。用 Caffeine 這類有 `maximumSize` 或 `maximumWeight` 的實作，並依「熱點資料佔多少」而非「全部資料佔多少」來設定。**同時要監控命中率**：命中率低的本地快取只是浪費記憶體與 GC 壓力。

**詳細解析**：「本地快取的記憶體比 Redis 的記憶體貴」這個判斷很重要。應用行程的堆積要同時服務業務邏輯、請求處理、與快取；快取吃掉的每一 MB 都直接增加 GC 壓力並減少可用於處理請求的空間。而 Redis 的記憶體是專用的、可以獨立擴充的、也不受 GC 影響。所以本地快取應該只放「最熱的那一小部分」——經驗上是總資料的 1% 到 5%，但貢獻了大部分的存取。**判斷方式是看存取分佈**：如果前 100 個鍵佔了 80% 的存取，那本地快取 100 個鍵就拿到了 80% 的收益，而成本極小。如果存取是均勻分佈的，本地快取的價值就很低——這時應該直接放棄它而不是硬做。

**面試回答方式**：給明確要求（容量上限與淘汰策略，無界會直接 OOM）與監控命中率的必要性。真正的加分點是判斷：**本地快取的記憶體比 Redis 的貴**——它增加 GC 壓力並減少處理請求的空間，而 Redis 的記憶體是專用可獨立擴充的。給出設定原則：**只放最熱的 1% 到 5%**，並用存取分佈判斷（前 100 個鍵佔 80% 存取就拿到 80% 收益）。收在反面：存取均勻分佈時本地快取價值很低，應該放棄而不是硬做。

### Tracking 對伺服器的開銷有多大？

**核心答案**：主要是**失效表的記憶體**與**失效通知的網路開銷**。預設模式下，伺服器維護一個「鍵到關心它的客戶端集合」的映射，大小與被追蹤的鍵數量成正比；`tracking-table-max-keys` 限制它（預設 100 萬），超過時會驅逐追蹤項並發送失效通知——這是保守但正確的行為（寧可多失效一次）。廣播模式沒有這個記憶體成本，但每次符合前綴的修改都要廣播給所有訂閱者，寫入密集時網路開銷可觀。

**詳細解析**：「驅逐追蹤項時發送失效通知」這個設計值得注意——它保證了「客戶端永遠不會持有一個已經不被追蹤但實際上已變更的值」。代價是失效表滿的時候，客戶端會收到大量非必要的失效通知，本地快取的命中率驟降。 這形成一個負回饋：被追蹤的鍵越多，失效表越容易滿，本地快取越沒用。**所以 Tracking 適合「熱點集中」的場景**——追蹤的鍵數量遠小於總鍵數。在鍵很分散的場景下，預設模式會不斷驅逐，而廣播模式會不斷發送無關的通知，**兩種模式都失去價值**。認出「這個機制在什麼分佈下有效」比記住它的參數更重要。

**面試回答方式**：給兩類開銷（失效表記憶體、通知的網路開銷）與兩種模式各自的成本。真正的加分點是展開「驅逐時發送失效通知」的負回饋：被追蹤的鍵越多、表越容易滿、通知越多、本地快取命中率越低——**所以 Tracking 適合熱點集中的場景**，鍵很分散時兩種模式都失去價值。收在原則：認出「這個機制在什麼分佈下有效」比記住參數更重要。

### 兩級快取的一致性問題怎麼收斂？

**核心答案**：接受最終一致，並用三層機制縮短窗口。**主動失效**（Tracking 或 Pub/Sub 廣播）讓多數情況下的失效在毫秒內生效。**保底 TTL** 保證即使通知丟失，髒資料的存在時間有明確上界。**版本號或時間戳**在關鍵路徑上做最後檢查（讀本地快取後帶著版本去 Redis 確認，但那樣就沒省掉往返，所以只用在少數必須正確的地方）。

**詳細解析**：三層機制的角色不同，這一點值得說清楚：主動失效負責「快」、TTL 負責「有界」、版本檢查負責「這一次必須對」。**混淆它們會導致設計錯誤**——例如以為有了主動失效就不需要 TTL（一次通知丟失就是永久髒資料），或者以為 TTL 夠短就不需要主動失效（那樣失效延遲是整個 TTL）。更重要的是「哪些資料需要第三層」的判斷：絕大多數資料不需要（商品描述晚一秒更新沒關係），只有直接影響金錢或權限的才需要，而那些資料或許根本不該進本地快取。這個「依資料的正確性要求分層」的思路，比追求一個統一的一致性等級務實得多——不同的資料本來就有不同的要求，強求統一只會讓成本被最嚴格的那一項決定。

**面試回答方式**：給三層機制並明確說出**各自的角色不同**：主動失效負責快、TTL 負責有界、版本檢查負責這一次必須對。指出**混淆它們會導致設計錯誤**（以為有主動失效就不用 TTL、或以為 TTL 短就不用主動失效）。真正的加分點是**「哪些資料需要第三層」的判斷**——絕大多數不需要，只有直接影響金錢或權限的才需要，而那些資料或許根本不該進本地快取。收在思路：依資料的正確性要求分層，比追求統一的一致性等級務實得多。
