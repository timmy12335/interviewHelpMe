# 題目

什麼是熱 key 和大 key？它們有什麼危害？怎麼發現和解決？

## 核心答案

**熱 key（hot key）**是「被極高頻率存取的單個 key」（如爆款商品、熱門活動的資料）——危害是「單個 key 的所有請求都集中打到它所在的那一個節點，導致該節點負載過高、成為瓶頸甚至被壓垮（在叢集下無法透過分片分攤，因為它就一個 key、在一個節點）」。**大 key（big key）**是「單個 key 的 value 非常大」（如一個有百萬元素的 List/Hash、或一個很大的 String）——危害是「操作大 key 很慢（單執行緒下阻塞其他命令）、刪除大 key 慢、大 key 在網路傳輸和記憶體上都造成壓力、且在叢集下導致資料分佈不均」。解決——熱 key 用「本地快取、多副本分散」；大 key 用「拆分成多個小 key、用 UNLINK 非同步刪除」。

## 詳細解析

**熱 key 問題**：

- 定義——某個 key 被極高頻率地存取（QPS 遠高於其他 key）。
- 危害——在 Redis Cluster 中，資料按槽分片到不同節點，但「一個 key 只屬於一個槽、在一個節點」，所以熱 key 的海量請求全部集中在「它所在的那一個節點」，這個節點的負載遠高於其他節點、成為瓶頸（分片無法分攤單個 key 的壓力），嚴重時把該節點壓垮。
- 發現——用 `redis-cli --hotkeys`（基於 LFU 統計）、監控各 key 的存取頻率、或在客戶端/代理層統計。
- 解決——(1)**本地快取**：把熱 key 快取到應用本地(多級快取)、大量請求在本地就命中、不打到 Redis;(2)**多副本分散**：把熱 key 複製成多份(如 `hotkey_1`、`hotkey_2`...`hotkey_N`、分佈在不同節點)、請求隨機讀其中一份、把壓力分散到多個節點;(3)讀寫分離（Read-Write Splitting）、增加從節點分攤讀。

**大 key 問題**：

- 定義——單個 key 的 value 很大,如一個包含幾百萬元素的 Hash/List/Set/ZSet、或一個幾 MB 的 String。
- 危害——(1)**操作慢阻塞**：對大 key 的操作(如 HGETALL 一個百萬欄位的 Hash、LRANGE 一個超長 List)很耗時,而 Redis 單執行緒、慢操作會阻塞所有其他命令(見 [[003-single-thread-model.md]]);(2)**刪除慢**：DEL 一個大 key 要釋放大量記憶體、很慢、也會阻塞;(3)**網路和記憶體壓力**：讀取大 key 要傳輸大量資料(佔網路帶寬)、大 key 佔用大量記憶體;(4)**叢集分佈不均**：一個大 key 只在一個節點,導致該節點記憶體遠高於其他節點。
- 發現——`redis-cli --bigkeys`(掃描找出各類型最大的 key)、`MEMORY USAGE key`(看單個 key 佔用)、或分析 RDB 檔案。
- 解決——(1)**拆分**：把大 key 拆成多個小 key(如一個百萬欄位的 Hash 拆成多個 Hash、按欄位雜湊分到不同 key);(2)**用 UNLINK 刪除**：刪大 key 用 `UNLINK`(非同步釋放記憶體、不阻塞)而非 `DEL`;(3)**避免一次性操作整個大 key**：用 `HSCAN`/`SSCAN` 等漸進式地分批操作,而非 HGETALL 一次全取。

## 面試回答方式

分別講清「熱 key」和「大 key」——它們是兩個不同的問題(一個是『存取頻率高』、一個是『value 大』),不要混淆。熱 key：危害是「集中打一個節點、分片無法分攤」,解決用「本地快取、多副本分散」。大 key：危害是「操作/刪除慢阻塞(單執行緒)、網路記憶體壓力、分佈不均」,解決用「拆分、UNLINK 非同步刪除、漸進式操作」。發現方法各自提一下(--hotkeys / --bigkeys)。能把兩個問題的「定義、危害、發現、解決」都講清楚,並點出熱 key 的關鍵危害是「分片分攤不了單 key」、大 key 的關鍵危害是「單執行緒下阻塞」,展現你理解這兩個問題的本質。

## 常見追問

### 為什麼熱 key 在 Redis Cluster 下特別麻煩（分片解決不了）？

**核心答案**：因為 Redis Cluster 的分片是「以 key 為單位」的——每個 key 根據 `CRC16(key) mod 16384` 算出它屬於哪個槽、進而屬於哪個節點,「一個 key 只能在一個槽、一個節點上」。分片的本意是「把不同的 key 分散到不同節點、分攤壓力」,但這對「單個熱 key」無效——因為熱 key 就是「一個 key」,它只屬於一個槽、在一個節點上,所以對它的所有海量請求都會集中打到「這一個節點」,無論叢集有多少節點都分攤不了(其他節點幫不上忙、因為這個 key 不在它們那裡)。這就是熱 key 在叢集下的根本問題——分片能分攤「多個不同 key 的總壓力」,但無法分攤「單個 key 的集中壓力」。所以熱 key 需要「本地快取(在 Redis 前擋掉)」或「多副本(把這一個熱 key 複製成多個、分佈到不同節點)」這類專門手段,而不能指望分片。

**詳細解析**：這題的關鍵是理解「分片的粒度是 key」——這決定了分片能解決什麼、不能解決什麼。分片(sharding)的思路是「把資料集拆成多份、分到多個節點、每個節點負責一部分、從而分攤總負載」。對於「大量不同的 key」,分片很有效——不同的 key 算到不同的槽、分到不同節點,總的存取壓力就被分攤到了多個節點。但「單個熱 key」打破了這個——它是「一個 key」,分片的最小粒度就是 key,一個 key 沒法再被拆到多個節點(它的所有資料和所有請求都繫在這一個 key、一個節點上)。所以叢集裡即使有 100 個節點,一個熱 key 的壓力還是全壓在它所在的那 1 個節點上,其他 99 個節點對這個熱 key 的壓力毫無幫助。這就是為什麼「加節點、擴容叢集」解決不了熱 key 問題——熱 key 的瓶頸是「單節點對單 key 的處理能力」,擴容增加的是「節點數」,但單個節點的能力沒變、而熱 key 就繫在單個節點上。解決熱 key 必須用「不依賴分片」的手段——「本地快取」是在 Redis 之前加一層(讓大部分熱 key 請求在應用本地就命中、根本不到 Redis,從源頭削減打到那個節點的量);「多副本分散」是「人為地把一個熱 key 變成多個 key」(hotkey_0 到 hotkey_9,用不同的 key 名、會被分片到不同節點,請求隨機讀其中一個,這樣就把對「一個熱 key」的壓力分散成了對「多個副本 key」的壓力、分到了不同節點)。理解「分片以 key 為粒度、解決不了單熱 key」以及對應的專門手段,展現你理解熱 key 問題的本質。

**面試回答方式**：講出「分片以 key 為粒度——一個 key 只在一個槽一個節點、分片能分攤『多個不同 key 的壓力』但無法分攤『單個熱 key 的集中壓力』(它就一個 key、繫在一個節點、加多少節點都幫不上)」。給出專門手段——「本地快取(在 Redis 前擋掉大部分請求)、多副本分散(把一個熱 key 複製成多個 key 名、分到不同節點、請求隨機讀)」。能點出「擴容加節點解決不了熱 key(瓶頸是單節點對單 key 的能力)」,展現你理解熱 key 問題的本質。

### 大 key 為什麼要用 UNLINK 而不是 DEL 刪除？

**核心答案**：因為 `DEL` 是「同步刪除」——它會在「主執行緒」裡「同步地釋放這個 key 佔用的所有記憶體」,對於大 key(如佔幾 GB 記憶體的大 Hash),釋放這麼多記憶體很耗時,而 Redis 是單執行緒,這個耗時的釋放過程會「阻塞主執行緒、卡住所有其他命令」(見單執行緒下慢操作阻塞一切)。`UNLINK`(Redis 4.0+)是「非同步刪除」——它在主執行緒裡只做「把 key 從資料庫的字典裡移除(解除引用,這步很快 O(1))」,然後把「實際釋放記憶體」這個耗時的工作「交給後台執行緒非同步去做」,主執行緒立即返回、不被阻塞。所以刪除大 key 用 UNLINK,能避免「同步釋放大量記憶體阻塞主執行緒」的問題。

**詳細解析**：這題深入到大 key 刪除的機制,連結到 Redis 單執行緒的特性。刪除一個 key 分兩件事——「邏輯刪除(從字典裡移除這個 key,讓它不再可訪問)」和「實際釋放記憶體(把這個 key 的 value 佔用的記憶體歸還)」。對於小 key,這兩件事都很快、沒問題。但對於大 key——「實際釋放記憶體」這一步很耗時:一個有幾百萬元素的 Hash/List,要逐個釋放這幾百萬個元素佔用的記憶體,這是一個和元素數量成正比的耗時操作。`DEL` 把這兩件事都在主執行緒同步做——邏輯刪除 + 同步釋放全部記憶體,對大 key 來說,那個「同步釋放幾百萬元素記憶體」的過程會佔用主執行緒很久(可能幾百毫秒甚至更久),而 Redis 單執行緒,這期間所有其他命令都被阻塞、無法處理,造成明顯的卡頓甚至請求超時。`UNLINK` 的改進是「把耗時的記憶體釋放非同步化」——它在主執行緒只做「邏輯刪除(從字典移除 key,O(1) 很快)」,然後判斷「這個 key 的釋放成本是否值得非同步」(大 key 才非同步、小 key 直接同步釋放沒必要開後台),對大 key 就把「釋放記憶體」的工作丟給一個後台執行緒去慢慢做,主執行緒立即返回、繼續處理其他命令、不被阻塞。所以刪大 key 用 UNLINK——主執行緒只花 O(1) 解除引用、記憶體釋放在後台非同步進行、不阻塞。這也是為什麼 Redis 4.0 引入了 UNLINK 以及一系列「惰性刪除(lazy free)」的配置(可以讓過期刪除、淘汰刪除等也走非同步釋放)。理解 DEL(同步釋放阻塞)vs UNLINK(非同步釋放不阻塞)的區別,展現你把大 key 問題和單執行緒模型串起來理解。

**面試回答方式**：講出「DEL 同步刪除——在主執行緒同步釋放 key 的全部記憶體、大 key 釋放幾百萬元素記憶體很耗時、單執行緒下阻塞所有其他命令;UNLINK 非同步刪除——主執行緒只做邏輯刪除(從字典移除、O(1))、把實際釋放記憶體交給後台執行緒、主執行緒立即返回不阻塞」。能連結到「單執行緒下慢操作阻塞一切、所以大 key 的同步釋放是問題、UNLINK 用非同步釋放解決」,展現你把大 key 和單執行緒模型串起來理解。

### 怎麼設計 key 才能避免大 key 和熱 key？

**核心答案**：**避免大 key**——(1)控制單個集合類型(Hash/List/Set/ZSet)的元素數量,不要無限往一個 key 裡堆(如一個「使用者的所有訂單」不要用一個 List 存全部、而是分頁或按時間分成多個 key);(2)把大物件拆分(如一個大 Hash 按欄位雜湊拆成多個 Hash);(3)大的 String(如大 JSON)考慮是否真的需要整個存、能否拆分或壓縮;(4)給集合類型設計時就考慮上限、定期清理。**避免熱 key**——(1)識別可能的熱點(如爆款商品、熱門活動),對它們預先用本地快取或多副本;(2)業務設計上分散熱點(如把一個全域計數器拆成多個分片計數器最後匯總,類似 LongAdder 的思路);(3)避免「所有請求都讀同一個 key」的設計。核心是——在「設計 key 和資料結構時」就預判規模和存取模式、避免單個 key 過大或過熱,而非事後補救。

**詳細解析**：這題考的是「從設計上預防」而非「事後解決」,體現更成熟的工程思維。**大 key 的預防**在於「設計資料結構時就控制規模」——很多大 key 是「無節制地往一個 key 裡堆資料」造成的:比如用一個 List 存「某使用者的所有行為記錄」、越積越多變成大 key;正確做法是設計時就考慮「這個集合會長多大」,如果可能很大,就「分片」(按時間分成 `records:2026-01`、`records:2026-02`,或按 id 雜湊分到多個 key)或「限制大小」(只保留最近 N 條、用 LTRIM 定期裁剪)。**熱 key 的預防**在於「設計上分散存取」——有些熱 key 是設計導致的:比如用「一個全域 key 做計數器」(所有請求都 INCR 同一個 key),這個 key 必然成為熱點;可以借鑑 LongAdder 的分散思路(見 [[../java-concurrency/019-atomicinteger-vs-longadder.md]])——用多個分片 key 分別計數(`counter_0` 到 `counter_9`,請求隨機選一個 INCR)、需要總數時把它們加起來,把對一個 key 的集中寫入分散成對多個 key 的寫入。對於「業務上天然的熱點」(如爆款商品,無法從設計上消除),則要預先識別、用本地快取/多副本應對。這個「設計時預判規模和存取模式」的思維,比「等出了問題再用 --bigkeys/--hotkeys 發現、再拆分」要主動得多。當然,實務中兩者結合——設計時盡量預防、同時有監控(--bigkeys/--hotkeys、記憶體監控)及時發現漏網的、再補救。理解「從設計上預防大 key/熱 key」,展現你有前瞻性的工程設計思維。

**面試回答方式**：講出「避免大 key——設計時控制集合元素數量(分片如按時間/id 拆、或限制大小如 LTRIM 保留最近 N 條)、拆分大物件、大 String 考慮拆分壓縮」;「避免熱 key——預先識別熱點用本地快取/多副本、設計上分散(如計數器用多個分片 key 借鑑 LongAdder 思路、避免所有請求讀同一 key)」。強調「核心是設計 key 和資料結構時就預判規模和存取模式、預防勝於補救、同時有監控兜底」。能連結到 LongAdder 的分散思路,展現你有前瞻性的工程設計思維。
