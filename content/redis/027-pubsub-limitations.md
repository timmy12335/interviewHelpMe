# 題目

Redis 的 Pub/Sub 適合用在哪裡？它有哪些不能用來做的事？

## 核心答案

Pub/Sub 是**發送即忘的廣播**：發布者 `PUBLISH` 到一個頻道，**當下訂閱該頻道的所有客戶端**會收到；沒有訂閱者就直接丟棄，訊息不被儲存。

它的限制有四個，每一個都排除了一類用途。**沒有持久化**——訂閱者離線期間的訊息永遠丟失，重連後也拿不回來。**沒有 ack**——發布者不知道有沒有人收到、收了幾個。**沒有背壓**——訂閱者處理不過來時，訊息在伺服器的輸出緩衝區堆積，超過 `client-output-buffer-limit` 就**斷開連線**（於是丟失更多訊息）。**在叢集下的行為特殊**——訊息會廣播到所有節點（因為訂閱者可能連在任何節點上），這在大型叢集裡是可觀的網路開銷；Redis 7 的 `SSUBSCRIBE`（分片 Pub/Sub）針對這一點做了改善。

所以它適合的是「**丟了也沒關係的即時通知**」：本地快取的失效廣播、設定變更的通知、簡單的即時訊息推送。**不適合任何「不能丟」的場景**——那該用 Stream 或真正的訊息佇列。

## 詳細解析

**「本地快取失效廣播」是 Pub/Sub 最經典也最合適的用途**。多個應用實例各自有本地快取，資料變更時發布一則失效訊息，所有實例收到後清除本地快取。**丟一則訊息的後果只是某個實例的快取多存在一段時間，可以接受**——尤其是在同時設了保底 TTL 的情況下。**這正好符合它的能力邊界：廣播、低延遲、可以容忍丟失。**

**輸出緩衝區斷線的機制值得理解**。Redis 為每個客戶端維護一個輸出緩衝區；Pub/Sub 的訂閱者如果消費得慢（處理邏輯重、或網路慢），緩衝區會成長。`client-output-buffer-limit pubsub 32mb 8mb 60` 的意思是：**硬上限 32MB（超過立刻斷線）、軟上限 8MB 持續 60 秒（也斷線）**。**斷線之後客戶端通常會重連並重新訂閱，但那段時間的訊息全部丟失**——而且如果消費速度沒有改善，會陷入「連上、堆積、斷線、重連」的循環。**這個故障模式在「訂閱者做重活」時很常見**，解法是讓訂閱者只做極輕量的工作（把訊息放進本地佇列，由另一個執行緒處理）。

**沒有背壓是它與 Stream 最本質的差別**。Stream 的消費者主動 `XREAD` 拉取，速度由消費者決定；Pub/Sub 是伺服器推送，**消費者無法說「慢一點」**。**推送模型在消費者能跟上時延遲更低，跟不上時則會崩潰**——這是所有推送式系統的共同特性。

**Redis 7 的分片 Pub/Sub 解決的是叢集擴展性問題**。傳統的 Pub/Sub 在叢集下把每則訊息廣播到所有節點，**節點數越多開銷越大且與訊息量成正比**；`SSUBSCRIBE` 讓頻道依雜湊落到特定的槽位，訊息只在負責該槽的節點與其副本間傳遞。**代價是訂閱者必須連到正確的節點**，客戶端要理解拓撲。

## 面試回答方式

先給定位——**發送即忘的廣播**，沒有訂閱者就直接丟棄。給**四個限制**（沒有持久化、沒有 ack、沒有背壓、叢集下廣播到所有節點）並指出每一個排除了一類用途。給出適合的場景：**丟了也沒關係的即時通知**，特別是**本地快取失效廣播**——丟一則的後果只是某個實例的快取多存在一段時間，尤其在有保底 TTL 時可以接受。加分點有兩個：**輸出緩衝區超限會斷線**，訂閱者做重活時會陷入「連上、堆積、斷線、重連」的循環，解法是讓訂閱者只做極輕量的工作；以及**沒有背壓是它與 Stream 最本質的差別**——Stream 是拉取（速度由消費者決定），Pub/Sub 是推送（消費者無法說慢一點），**推送模型跟得上時延遲更低、跟不上時會崩潰**。

## 講稿

發布訂閱是發送即忘的廣播。發布到一個頻道，當下訂閱該頻道的所有客戶端會收到，沒有訂閱者就直接丟棄，訊息不被儲存。

限制有四個。沒有持久化，訂閱者離線期間的訊息永遠丟失。沒有確認，發布者不知道有沒有人收到。沒有背壓。還有在叢集下訊息會廣播到所有節點。

所以它適合的是丟了也沒關係的即時通知。最經典的用途是本地快取的失效廣播，多個實例各自有本地快取，資料變更時發布一則失效訊息。丟一則的後果只是某個實例的快取多存在一段時間，尤其在同時設了保底過期時間的情況下完全可以接受。

有一個故障模式要注意。Redis 為每個客戶端維護輸出緩衝區，訂閱者消費得慢的話緩衝區會成長，超過上限就斷線。斷線之後客戶端通常會重連重新訂閱，但那段時間的訊息全部丟失。如果消費速度沒改善，會陷入連上、堆積、斷線、重連的循環。所以訂閱者應該只做極輕量的工作，把訊息放進本地佇列由別的執行緒處理。

沒有背壓是它跟 Stream 最本質的差別。Stream 是消費者主動拉取，速度由消費者決定。

## 常見追問

### 用 Pub/Sub 做本地快取失效有什麼要注意的？

**核心答案**：三點。**必須有保底 TTL**——廣播可能丟失（訂閱者剛好在重連、訊息在緩衝區被截斷），所以本地快取仍要設一個過期時間作為最後防線。**要處理自己發的訊息**——發布者自己也訂閱時會收到自己的訊息，通常需要帶上實例 ID 並跳過。**要考慮啟動時的狀態**——新啟動的實例沒有收到之前的失效訊息，如果它從 Redis 載入了資料建立本地快取，那些資料的新鮮度是未知的。

**詳細解析**：**「必須有保底 TTL」體現了一個重要的設計原則：不要讓正確性依賴單一機制**。廣播是為了「快」（讓失效在毫秒內生效），TTL 是為了「對」（保證最終一致）。**兩者的角色不同，缺一不可**——只有廣播的話，一次丟失就是永久的髒資料；只有 TTL 的話，失效延遲是整個 TTL。**同樣的模式適用於很多場景**：主動推送加定期拉取、事件驅動加定時對帳、快取失效加版本檢查。**認出這個模式的價值在於：設計時就知道要問「如果這個機制失效了，還有什麼在保底」。**

**面試回答方式**：給三點注意事項（保底 TTL、跳過自己發的訊息、啟動時的狀態未知）。真正的加分點是把第一點提升成原則：**不要讓正確性依賴單一機制**——廣播負責快、TTL 負責對，角色不同缺一不可。舉同類模式（主動推送加定期拉取、事件驅動加定時對帳）並收在設計時該問的問題：**如果這個機制失效了，還有什麼在保底**。

### Pub/Sub 的訂閱連線有什麼特殊性？

**核心答案**：**進入訂閱模式後，該連線只能執行訂閱相關的命令**（`SUBSCRIBE`、`UNSUBSCRIBE`、`PING`、`QUIT`），不能執行 `GET`、`SET` 等一般命令。**所以訂閱需要一條專用的連線**，不能與一般的讀寫共用。這在使用連線池的客戶端上要特別注意——訂閱會**長期佔用一條連線**，池的大小要把它算進去。

**詳細解析**：**這個限制的原因是協定層面的**：訂閱模式下伺服器會主動推送訊息，而 Redis 的協定是請求-回應式的，**如果同一條連線上同時有命令回應與推送訊息，客戶端無法區分哪個回應對應哪個請求**。**RESP3 協定（Redis 6 引入）解決了這件事**——它為推送訊息定義了獨立的型別標記，所以在 RESP3 下同一條連線可以同時做一般命令與訂閱。**但要用到這個能力，客戶端函式庫必須支援 RESP3 並明確啟用**（`HELLO 3`）。**這也是客戶端快取（Tracking）能實作的基礎**——它需要伺服器主動推送失效通知，而那只在 RESP3 下才乾淨可行。

**面試回答方式**：給限制（訂閱模式下只能執行訂閱相關命令）與實務影響（需要專用連線、連線池大小要算進去）。真正的加分點是解釋**原因是協定層面的**——請求-回應式協定無法區分推送與回應，並指出 **RESP3 為推送定義了獨立型別標記因而解決了它**。收在延伸：這也是**客戶端快取（Tracking）能實作的基礎**，因為它需要伺服器主動推送失效通知。

### Pub/Sub 與 Stream 該怎麼選？

**核心答案**：一個問題就能決定——**丟失一則訊息會不會造成問題**。不會就用 Pub/Sub（更簡單、延遲更低、不佔記憶體）；會就用 Stream（持久化、可 ack、可重放）。**次要的判準是「需不需要知道消費進度」**——Pub/Sub 完全不記錄任何狀態，Stream 有消費者群組的位移與待處理清單，可以監控消費延遲。

**詳細解析**：**「不佔記憶體」是 Pub/Sub 一個容易被忽略的優點**。Stream 的訊息會一直存在記憶體裡直到被修剪，高吞吐的場景下這是持續的記憶體成本；Pub/Sub 則是零成本（除了輸出緩衝區）。**所以在「每秒數萬則的即時通知」這類場景，Pub/Sub 常常是唯一可行的選擇**——用 Stream 的話記憶體會被吃光。**這提醒我們選型時要同時看「功能」與「資源成本」**：更強的保證總是要付出代價，而在量很大時那個代價可能是決定性的。**實務上也常見兩者搭配**：關鍵事件走 Stream（保證不丟），高頻的通知走 Pub/Sub（接受丟失），依訊息的重要性分流。

**面試回答方式**：給決定性的問題（**丟失一則會不會造成問題**）與次要判準（需不需要知道消費進度）。真正的加分點是指出 **Pub/Sub「不佔記憶體」這個容易被忽略的優點**——Stream 的訊息會持續佔用記憶體，每秒數萬則的場景下 Pub/Sub 常是唯一可行選擇。收在通用觀點：**選型要同時看功能與資源成本**，更強的保證總要付代價而量大時那可能是決定性的；並提出實務上常見**依訊息重要性分流**的搭配用法。
