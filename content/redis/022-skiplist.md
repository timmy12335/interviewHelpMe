# 題目

跳躍表（Skip List）是什麼？它是怎麼實現高效查詢的？Redis 的 ZSet 為什麼用跳躍表而不是紅黑樹？

## 核心答案

跳躍表是一種「基於多層鏈結串列」的有序資料結構，透過「在有序鏈結串列上建立多層索引」來實現高效的查詢——底層是一個包含所有元素的有序鏈結串列，上面建立多層「稀疏的索引層」（每一層都是下一層的一部分元素、跳著取），查詢時「從最高層開始、能跳就跳、跳過大量元素、逐層向下逼近目標」，把查詢複雜度從普通鏈結串列的 O(n) 降到 O(log n)。它靠「隨機」決定每個元素建幾層索引，實現簡單。Redis 的 ZSet 用跳躍表（配合雜湊表）而非紅黑樹，主要因為——跳躍表實現更簡單、且天然支援「範圍查詢（ZRANGEBYSCORE 等）」（沿底層鏈結串列順序遍歷即可），這是 ZSet 的常見需求，而紅黑樹做範圍查詢較麻煩。

## 詳細解析

**普通有序鏈結串列的問題**：一個有序鏈結串列，查找一個元素要「從頭一個一個比較」，O(n)很慢。

**跳躍表的核心思想——多層索引**：

- **底層（第 0 層）**——一個包含「所有元素」的有序鏈結串列。
- **上層索引**——在底層之上建立多層索引，每一層都「跳著」取下一層的部分元素（如第 1 層取第 0 層的每隔一個、第 2 層取第 1 層的每隔一個……越上層越稀疏）。每個索引節點有指標指向「同層的下一個」和「下一層的對應節點」。
- **查詢過程**——從「最高層的頭部」開始，沿著當前層向右走：如果「下一個節點的值 ≤ 目標」就繼續向右（跳過中間的元素）；如果「下一個節點的值 > 目標」就「下降一層」（在更細的層繼續找）。這樣一路「能跳就跳、跳不動就下降」，逐層逼近目標，跳過了大量不需要比較的元素。

**為什麼是 O(log n)**：因為每一層索引大約是下一層的一半（稀疏一倍），所以層數大約是 log n；查詢時每一層平均只走幾步就下降，總的比較次數大約是 O(log n)。這和二分查找、平衡樹的複雜度一樣，但實現簡單得多。

**用「隨機」決定層數**：跳躍表不像平衡樹那樣要複雜地維護平衡——它用「隨機」決定每個新插入的元素「建幾層索引」（如拋硬幣：50% 機率建 1 層、25% 建 2 層……），這樣「概率上」形成了合理的層數分佈（越高層越稀疏），平均達到 O(log n)，而插入/刪除不需要複雜的旋轉調整（只需改幾個指標），實現簡單。

**Redis ZSet 為什麼用跳躍表而非紅黑樹**：

1. **實現簡單**——跳躍表用隨機層數、指標操作，比紅黑樹的旋轉、變色等平衡調整簡單很多，程式碼更易維護、更不易出錯。
2. **範圍查詢方便**——ZSet 常要做「範圍查詢」（ZRANGE、ZRANGEBYSCORE 取某個分數區間的元素）。跳躍表的底層就是有序鏈結串列，找到範圍的起點後「沿底層鏈結串列順序往後走」就能取到範圍內的所有元素，非常自然高效；紅黑樹做範圍查詢要中序遍歷、較麻煩。
3. **效能相當**——跳躍表和紅黑樹的查詢、插入、刪除都是 O(log n)，效能相當但跳躍表在範圍查詢和實現複雜度上有優勢。

（注：ZSet 實際是「跳躍表 + 雜湊表」——跳躍表保證按分數有序和範圍查詢 O(log n)、雜湊表保證按成員查分數 O(1)。）

## 面試回答方式

先講「普通有序鏈結串列查找 O(n) 慢」的問題，引出跳躍表的「多層索引」思想——底層全部元素、上層稀疏索引、查詢時從高層跳著找逐層下降。核心要講清「為什麼 O(log n)」（每層稀疏一倍、層數 log n、跳過大量元素）和「用隨機決定層數（避免平衡樹的複雜調整）」。「為什麼 ZSet 用跳躍表而非紅黑樹」是必考——講「實現簡單、範圍查詢方便（底層有序鏈結串列順序遍歷）、效能相當」，尤其「範圍查詢方便」是關鍵（ZSet 常做範圍查詢）。能講出跳躍表的原理和 ZSet 選它的理由，展現你理解這個 Redis 核心資料結構。

## 常見追問

### 跳躍表用「隨機層數」，會不會導致效能不穩定（退化）？

**核心答案**：理論上有極小的機率會退化（如果隨機得非常不巧、大量元素都只建了很少的層，跳躍表就接近普通鏈結串列、查詢變慢），但實際上這個機率極低、可以忽略。因為跳躍表的層數是「概率分佈」的——每個元素建 k 層的機率大約是 (1/2)^k，所以「大量元素都恰好只建很少層」這種導致退化的情況，概率上極其罕見（就像連續拋很多次硬幣都是同一面一樣不可能）。而且元素越多，概率分佈越穩定、越接近理想的層數分佈，查詢複雜度越穩定在 O(log n)。所以跳躍表雖然用隨機、理論上有退化可能，但實際上「概率保證」了它幾乎總是 O(log n) 的良好效能，這種「用簡單的隨機換取概率上的高效能」正是它相比平衡樹（用複雜的確定性調整保證嚴格平衡）的取捨。

**詳細解析**：這題考的是「理解跳躍表的概率性保證」。跳躍表和平衡樹（紅黑樹、AVL）的一個根本區別是——平衡樹用「確定性的、複雜的調整（旋轉、變色）」來「嚴格保證」樹的平衡、從而嚴格保證 O(log n)；跳躍表用「隨機」來「概率性地保證」層數的合理分佈、從而「概率上」保證 O(log n)。跳躍表的層數機制是——每個元素插入時，用類似拋硬幣的隨機過程決定它建幾層：一定有第 0 層，然後 50% 機率再上一層、再 50% 機率再上一層……所以建 k 層的機率約是 (1/2)^k（越高層越少元素）。這個概率分佈「期望上」形成了理想的稀疏索引（每層約為下層的一半），使查詢期望是 O(log n)。理論上的退化——需要「大量元素恰好都只建了很低的層」（使得高層索引很稀疏甚至沒有、查詢時跳不動、退化成接近線性掃描），但這需要「大量獨立的隨機拋硬幣結果都極端一致」，概率極低（元素越多越不可能，因為要求所有這些獨立隨機都不巧）。實際上對於任何有意義規模的資料，跳躍表的效能都穩定在 O(log n)，退化在實踐中不會發生。這種「用隨機的簡單性換取概率上的高效能、放棄嚴格保證但實際足夠好」的設計哲學，是跳躍表相比平衡樹的核心價值——它避免了平衡樹複雜的平衡維護邏輯（旋轉、變色的各種情況很容易寫錯），用簡單的隨機達到了實踐上一樣好的效能。理解跳躍表的概率性保證和它的設計哲學，展現你對這個資料結構有深入而非表面的理解。

**面試回答方式**：講出「理論上有極小機率退化(大量元素恰好都建很低層)、但實際概率極低可忽略——層數是概率分佈(建 k 層機率約 (1/2)^k)、大量獨立隨機都極端一致的概率極小、元素越多越穩定」。點出「跳躍表用隨機的概率保證 vs 平衡樹用複雜調整的嚴格保證、用簡單性換概率上足夠好的效能、避免了平衡樹複雜易錯的平衡維護」。展現你對跳躍表概率性保證和設計哲學的深入理解。

### 為什麼 ZSet 要同時用跳躍表和雜湊表兩個結構？

**核心答案**：因為 ZSet 有兩類常見操作，各自需要不同的結構來高效支援——(1)「按分數的有序操作」(如按分數排序取 top N、取某個分數區間 ZRANGEBYSCORE、查某成員的排名 ZRANK)需要「有序性和範圍查詢」，這靠「跳躍表」(按分數有序、範圍查詢 O(log n));(2)「按成員查它的分數」(如 ZSCORE member 直接查某個成員的分數)需要「按 key 快速查找」，這靠「雜湊表」(成員→分數的映射、O(1) 查找)。如果只用跳躍表，按成員查分數要遍歷跳躍表 O(n);如果只用雜湊表，按分數排序和範圍查詢又做不到。所以 ZSet 同時用兩個結構、各司其職——跳躍表管「有序和範圍」、雜湊表管「按成員查分數」，兩者存的是同一份資料(成員+分數)的兩種索引，用空間換取「兩類操作都高效」。

**詳細解析**：這題揭示了 ZSet 的完整底層實現(跳躍表 + 雜湊表的組合)，體現「用多個結構分別優化不同操作」的設計。ZSet 的資料本質是「一組(成員, 分數)對」，而對它的操作分兩大類、對資料結構有不同的要求。**按分數的有序操作**——「取分數最高的 10 個(ZREVRANGE)」「取分數在 100 到 200 之間的成員(ZRANGEBYSCORE)」「查某成員的排名(ZRANK)」，這些都需要「資料按分數有序、且能高效地做範圍查詢和排名」。跳躍表完美支援——它按分數維護有序、範圍查詢是 O(log n)(找到起點後沿底層鏈結串列走)、排名也能高效算(跳躍表節點可以記錄跨度來算排名)。**按成員查分數**——「查成員 X 的分數是多少(ZSCORE X)」，這需要「給定成員、快速找到它的分數」。如果用跳躍表做這個，要在跳躍表裡按成員找(跳躍表是按分數組織的、不是按成員)，只能遍歷 O(n)，很慢。所以 ZSet 額外用一個「雜湊表」存「成員→分數」的映射，ZSCORE 直接雜湊查找、O(1)。這兩個結構存的是「同一份資料的兩種索引」——跳躍表按分數索引(支援有序/範圍)、雜湊表按成員索引(支援 O(1) 查分數)，它們指向同一批(成員，分數)資料。這樣不管是「按分數的有序操作」還是「按成員查分數」，ZSet 都能高效支援，代價是「用了兩個結構、多佔一點記憶體」(空間換時間)。這種「同一份資料建多種索引以支援不同的高效查詢」的思想，在資料庫(一張表建多個索引)、其他系統中也很常見。理解 ZSet 用兩個結構各司其職，展現你理解這個複合資料結構的完整設計。

**面試回答方式**：講出「ZSet 有兩類操作各需不同結構——按分數的有序操作(排序取 top N、範圍查詢、排名)靠跳躍表(有序、範圍查詢 O(log n))、按成員查分數(ZSCORE)靠雜湊表(成員→分數、O(1))」。說明「只用跳躍表則按成員查分數要 O(n)、只用雜湊表則做不到有序和範圍、所以兩個結構各司其職、存同一份資料的兩種索引、空間換時間」。能連結到「同一份資料建多種索引支援不同查詢、和資料庫建多個索引同理」，展現你理解 ZSet 的完整設計。

### 跳躍表和 B+ 樹（資料庫索引用的）有什麼區別和相似？

**核心答案**：相似點——兩者都是「有序的、支援高效查找和範圍查詢的資料結構」，查找複雜度都是 O(log n)(或類似)，都支援「找到起點後順序遍歷做範圍查詢」。區別——(1)**結構**:跳躍表是「多層鏈結串列 + 隨機索引」、B+ 樹是「多路平衡樹(每個節點有多個子節點)」;(2)**適用場景**:跳躍表主要用於「記憶體中」的有序結構(如 Redis ZSet)，B+ 樹主要用於「磁碟儲存」(如資料庫索引)——B+ 樹的設計(每個節點存多個 key、對應一個磁碟頁)是專門為「減少磁碟 IO」優化的(一次讀一個節點/頁能拿到很多 key、樹很矮、磁碟 IO 次數少)，而跳躍表沒有這個磁碟優化(它是為記憶體設計的、不考慮磁碟頁);(3)**實現**:跳躍表用隨機、實現簡單，B+ 樹用確定性的分裂/合併維護平衡、實現較複雜。所以——記憶體中的有序結構常用跳躍表(簡單)，磁碟上的索引用 B+ 樹(為減少磁碟 IO 優化)。

**詳細解析**：這題把 Redis 的跳躍表和資料庫的 B+ 樹(見資料庫題)對比，體現「不同場景選不同的有序結構」。**相似**——它們解決的是同一類問題:「維護有序資料、支援高效的查找、插入、刪除、範圍查詢」。所以在「有序性、O(log n) 查找、範圍查詢(順序遍歷)」這些特性上是相似的。**關鍵區別在於「為記憶體還是為磁碟設計」**——這決定了結構的不同。跳躍表是「為記憶體設計」的——記憶體是隨機存取的、存取任何位置成本一樣，所以跳躍表用「多層鏈結串列」的結構、每個節點存一個元素、靠指標跳轉，這在記憶體裡很自然高效。B+ 樹是「為磁碟設計」的——磁碟 IO 是昂貴的(比記憶體慢幾個數量級)、且磁碟以「頁(block)」為單位讀取，所以 B+ 樹專門優化「減少磁碟 IO」:它是「多路」的(每個節點存很多個 key、對應一個磁碟頁，一次磁碟 IO 讀一個節點就能拿到很多 key)、樹很「矮胖」(因為每個節點分支多、所以很少的層數就能索引大量資料、查找時磁碟 IO 次數少)，且 B+ 樹把資料都放在葉子節點、葉子用鏈結串列相連(範圍查詢時沿葉子鏈結串列走)。這個「每個節點對應一個磁碟頁、樹矮以減少磁碟 IO」的設計是 B+ 樹的精髓，而跳躍表沒有這個(它不考慮磁碟、就是記憶體裡的多層鏈結串列)。所以選擇——Redis 是記憶體資料庫、ZSet 在記憶體裡，用跳躍表(簡單、適合記憶體);MySQL 的索引在磁碟上，用 B+ 樹(為減少磁碟 IO 優化)。理解跳躍表和 B+ 樹「都是有序結構、但分別為記憶體和磁碟優化」的區別，展現你能跨知識點(Redis 和資料庫)對比、理解資料結構選擇和儲存介質的關係。

**面試回答方式**：講出相似——「都是有序結構、O(log n) 查找、支援範圍查詢(順序遍歷)」;區別——「跳躍表是多層鏈結串列+隨機索引、為記憶體設計(Redis ZSet);B+ 樹是多路平衡樹、為磁碟設計(資料庫索引)——B+ 樹每個節點對應磁碟頁、樹矮胖以減少磁碟 IO，跳躍表沒這個磁碟優化;跳躍表用隨機實現簡單、B+ 樹用分裂合併維護平衡較複雜」。概括「記憶體用跳躍表(簡單)、磁碟用 B+ 樹(減少磁碟 IO)」。展現你能跨知識點對比、理解資料結構和儲存介質的關係。
