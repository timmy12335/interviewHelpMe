# 題目

用有序集合做排行榜有哪些設計問題？分數相同時怎麼處理？大量玩家時怎麼辦？

## 核心答案

有序集合天生適合排行榜：`ZADD` 更新分數、`ZREVRANGE` 取前 N 名、`ZREVRANK` 查某人的名次、`ZINCRBY` 增量更新——**全部都是 O(log N) 或 O(log N + M)**。

三個主要的設計問題。**分數相同的排序**——有序集合在分數相同時依成員名的字典序排，**這通常不是業務要的**（同分時應該先達成的排前面）。標準解法是**把時間戳編進分數**：用 `score * 10^10 + (最大時間戳 - 達成時間)` 這樣的複合分數，讓同分時較早達成的分數更高。**注意浮點精度**——有序集合的分數是 double，只有 53 位元的整數精度，複合分數必須控制在這個範圍內。

**大量成員的記憶體與延遲**——一億個玩家的有序集合是一個巨大的 key，記憶體與操作成本都成問題。解法是**只保留前 N 名**（用 `ZREMRANGEBYRANK` 定期修剪）——**排行榜通常只有前 1000 名有意義**，其餘玩家的名次可以另外估算或不提供。

**深分頁**——`ZREVRANGE key 100000 100010` 需要跳過十萬個成員，成本與偏移量成正比。**與資料庫的深分頁是同一個問題，解法也一樣：用「上一頁最後一筆的分數」當游標**（`ZREVRANGEBYSCORE key (lastScore -inf LIMIT 0 10`）。

## 詳細解析

**複合分數的位元分配需要仔細設計**。double 的整數精度是 2 的 53 次方（約 9 × 10^15）。如果分數上限是一百萬（需要 20 位元），剩下 33 位元給時間戳——**33 位元的秒級時間戳可以表示約 272 年，足夠**；但如果要毫秒級就不夠了。**超出精度的後果是靜默的錯誤**：兩個不同的複合分數在 double 裡變成同一個值，排序就亂了。**所以複合分數的設計必須先算清楚位元預算**，而且要寫測試驗證邊界值。

**「只保留前 N 名」的取捨要說清楚**。它解決了記憶體問題，但**失去了「查詢任意玩家名次」的能力**。實務上的處理是分層：**前 1000 名用精確的有序集合**、**其餘玩家用近似的名次**（依分數區間統計，回答「你在前 30%」而非「你是第 45231 名」）。**這正好符合業務現實**——排名靠後的玩家其實不在乎精確名次，而精確地維護一億人的名次成本極高。**「用業務上可接受的近似換取數量級的成本下降」是這類設計的核心思路。**

**時間窗口的排行榜（本週、本月）需要額外設計**。做法有兩種：**每個窗口一個獨立的有序集合**（`rank:week:202403`，過期後自動刪除，簡單但每次更新要寫多個 key），或**用 `ZUNIONSTORE` 合併多個較小的窗口**（存每天一個，本週由七天合併——但合併本身是 O(N) 的重操作，只適合定時預算而非即時查詢）。**前者在寫入量可接受時更簡單。**

**併發更新的正確性**：`ZINCRBY` 是原子的，所以「累加型」的分數不會有競態。**但「取最大值」型的更新（只有新分數更高才更新）需要 Lua 腳本**——`ZSCORE` 讀取、比較、`ZADD` 寫入這三步在併發下會互相覆蓋。**這是有序集合使用中最常見的正確性問題**。

## 面試回答方式

先給有序集合適合排行榜的原因（各種操作都是 O(log N)），再給**三個設計問題**。**分數相同的排序**要給具體解法——把時間戳編進複合分數，並提醒 **double 只有 53 位元整數精度，超出會靜默出錯**。**大量成員**的解法是只保留前 N 名，因為**排行榜通常只有前 1000 名有意義**。**深分頁**與資料庫是同一個問題，用「上一頁最後的分數」當游標。加分點有三個：**只保留前 N 名的取捨**——失去查詢任意玩家名次的能力，實務上分層處理（前 1000 名精確、其餘給近似的百分位），這符合業務現實；**時間窗口排行榜的兩種做法**（每窗口一個 key vs `ZUNIONSTORE` 合併）；以及**「取最大值」型的更新需要 Lua 腳本**，讀取比較寫入三步在併發下會互相覆蓋——**這是有序集合最常見的正確性問題**。

## 講稿

有序集合天生適合排行榜，更新分數、取前 N 名、查某人名次都是對數時間。

三個主要的設計問題。第一是分數相同的排序。有序集合在分數相同時依成員名的字典序排，這通常不是業務要的，同分應該先達成的排前面。標準解法是把時間戳編進分數，用一個複合分數讓同分時較早達成的排前面。但要注意浮點精度，分數是雙精度浮點，只有五十三位元的整數精度，複合分數必須控制在這個範圍內。超出的後果是靜默的錯誤，兩個不同的分數變成同一個值，排序就亂了。

第二是大量成員的記憶體與延遲。一億個玩家的有序集合是一個巨大的 key。解法是只保留前 N 名，因為排行榜通常只有前一千名有意義。代價是失去查詢任意玩家名次的能力，實務上我會分層，前一千名精確，其餘給近似的百分位。

第三是深分頁，跟資料庫是同一個問題，用上一頁最後一筆的分數當游標。

還有一個正確性問題。累加型的更新是原子的，但只有新分數更高才更新這種取最大值型的，需要用 Lua 腳本，否則讀取比較寫入三步在併發下會互相覆蓋。

## 常見追問

### 為什麼有序集合的分數是 double 而不是整數？

**核心答案**：因為 **double 能同時表達整數與小數，涵蓋更多使用場景**——時間戳、金額、評分、機率權重都可以直接用。代價是**整數精度只有 53 位元**（超過 2^53 的整數無法精確表示），以及**浮點比較的細微問題**。Redis 在解析時如果分數是整數且在安全範圍內會用整數表示，**但底層的比較與儲存仍然是 double 的語意**。

**詳細解析**：**53 位元的限制在實務上真的會踩到**。用毫秒時間戳（約 41 位元）當分數還安全，但**「分數乘以 10^13 再加時間戳」這類複合設計很容易超過**。而且**超出精度時不會報錯**——它靜默地把兩個不同的值變成同一個，症狀是「排序偶爾不對」而非明確的失敗。**防護方式是在寫入前檢查複合分數是否超過 2^53，超過就拒絕或改用其他方案**（例如把時間戳編進成員名而非分數，用字典序處理同分）。**這類「靜默的精度損失」是數值處理中最難查的一類問題**，因為它不觸發任何錯誤路徑——**所以邊界檢查應該是主動加上的，而不是等出錯才補。**

**面試回答方式**：給選擇 double 的理由（同時表達整數與小數、涵蓋更多場景）與代價（53 位元整數精度）。重點強調**53 位元的限制真的會踩到**，複合分數設計很容易超過，而且**超出時不報錯只是靜默地把兩個值變成同一個**，症狀是「排序偶爾不對」。給防護方式（寫入前檢查、或把時間戳編進成員名）。收在一般觀點：**靜默的精度損失是數值處理中最難查的一類問題**，所以邊界檢查應該主動加上。

### 排行榜的分數更新頻率很高怎麼辦？

**核心答案**：問題是**單一 key 成為熱點**——所有玩家的分數更新都打在同一個有序集合上，而 Redis 是單執行緒的。三個方向：**降低更新頻率**（不是每次得分都更新，而是累積到一定量或一定時間才寫）、**分片再合併**（依玩家 ID 分成 N 個有序集合，取排行榜時合併前 N 名——因為只要前 K 名，每個分片取前 K 名再合併就夠了）、以及**寫入與讀取分離**（更新寫進佇列由專門的消費者批次套用）。

**詳細解析**：**「分片再合併」的正確性值得說明**：要取全域前 100 名，只需要每個分片的前 100 名——**因為全域第 100 名在它所屬的分片裡至少是第 100 名**。所以合併 N 個分片各自的前 100 名（共 N×100 個）再排序取前 100，結果是精確的。**這是一個很優雅的性質，讓分片不必犧牲精確度。** 代價是取排行榜時要查 N 個 key 並在客戶端合併，**但排行榜的讀取通常可以快取幾秒**，所以這個成本被攤薄了。**同樣的「分片取 K、合併取 K」模式在分散式搜尋與分散式排序中普遍使用**——認出它就能把很多「全域 Top-K」的問題分解掉。

**面試回答方式**：給問題本質（單一 key 熱點加單執行緒）與三個方向。重點展開**分片再合併的正確性**：**全域第 100 名在它所屬的分片裡至少是第 100 名**，所以每個分片取前 100 再合併就是精確的——這讓分片不必犧牲精確度。指出代價（查 N 個 key）被排行榜可以快取幾秒攤薄。收在一般化：**「分片取 K、合併取 K」在分散式搜尋與排序中普遍使用**，認出它就能分解很多全域 Top-K 的問題。

### 排行榜的資料要不要持久化？

**核心答案**：**看它是不是事實來源**。如果分數的來源是資料庫（每次得分都記在資料庫，Redis 只是加速的排序索引），**那 Redis 的資料丟了可以重建**，持久化只是為了避免重建的成本。如果分數只存在於 Redis（純粹的即時排行，例如遊戲的當局排名），**那就是事實來源，必須持久化**——而且要考慮主從切換時的資料丟失。

**詳細解析**：**「可重建」是一個非常有價值的性質**，它讓很多決定變簡單：不必為了資料安全而犧牲效能、可以放心地做主從切換與重啟、遇到資料異常時有一個確定的修復路徑（重建）。**所以在設計時應該優先考慮「能不能讓它可重建」**——即使那意味著多寫一份到資料庫。**重建的成本要事先量測並準備好腳本**，否則「理論上可以重建」在真的需要時會變成「沒有人知道怎麼重建」。**這與備份的道理相同：沒有演練過的恢復方案等於沒有方案。** 實務上的做法是定期執行一次重建（在測試環境或用影子 key），驗證腳本仍然有效且時間在可接受範圍內。

**面試回答方式**：給判準——**它是不是事實來源**，可從資料庫重建的話持久化只是省下重建成本，只存在於 Redis 的就必須持久化並考慮主從切換的丟失。真正的加分點是強調**「可重建」是一個非常有價值的性質**，它讓效能、切換、修復的決定都變簡單，所以設計時應該優先考慮讓它可重建。收在實務要點：**重建成本要事先量測並準備好腳本，定期演練**——因為**沒有演練過的恢復方案等於沒有方案**。
