# 題目

要統計一個網站每天的獨立訪客數（UV），為什麼不用 Set？HyperLogLog 是怎麼做到只用 12KB 的？

## 核心答案

用 `Set` 存所有訪客 ID 是精確的，但**記憶體與基數成正比**——一千萬個 UV，即使每個 ID 只有 20 位元組，加上 Set 的節點開銷就是幾百 MB，**而且每天一個 Set**。

HyperLogLog 用 **12KB 的固定空間**估算任意大小的基數，標準誤差約 **0.81%**。它的原理是用「雜湊值前導零的最大長度」估算基數：一個均勻的雜湊值，出現 k 個前導零的機率是 2 的負 k 次方，所以如果觀察到最多 k 個前導零，元素數量大約是 2 的 k 次方。單一觀察的方差很大，所以 HLL 把雜湊值分成 **16384 個桶**（用前 14 位元決定桶），每個桶記錄自己看到的最大前導零數，最後用**調和平均**合併——分桶加平均把方差降到可用的程度。

Redis 的操作是 `PFADD`（加入元素）、`PFCOUNT`（估算基數）、`PFMERGE`（合併多個 HLL，這讓「本週 UV」可以由七天的 HLL 合併得出，而 Set 做這件事要真的做聯集）。

核心取捨是：用 0.81% 的誤差換取幾百 MB 到 12KB 的空間，而 UV 這類指標本來就不需要精確。

## 詳細解析

`PFMERGE` 是 HLL 最被低估的能力。它讓「任意時間範圍的去重計數」變成常數成本的合併操作——存每小時一個 HLL，就能算出任意小時區間的獨立數，而且合併是無損的（合併後的估算精度與直接統計相同）。用 Set 做這件事需要真的做聯集，成本與資料量成正比。這種「可合併性」是 HLL 適合分散式統計的根本原因：每個節點各自統計，最後合併即可，不需要把原始資料集中。

**它的限制要說清楚**。**只能算基數，不能查詢成員**——無法問「這個使用者今天來過嗎」（那要用 Bloom filter 或 Set）。**誤差在小基數時的行為特殊**——Redis 的實作在基數很小時會切換成**稀疏編碼**並用線性計數，此時是精確的；超過門檻才轉成稠密編碼並開始有誤差。這意味著小資料量時它比 12KB 小得多，也解釋了為什麼一個剛建立的 HLL 只佔幾十位元組。**不能刪除元素**——HLL 沒有 `PFREMOVE`，因為前導零的最大值無法被「減回去」。

選型時要與其他近似結構區分清楚：**HLL 回答「有幾個不同的」**、**Bloom filter 回答「這個在不在裡面」**（可能誤判為在）、**Count-Min Sketch 回答「這個出現幾次」**（可能高估）。三者都是用精確度換空間，但回答的問題完全不同——選錯的話再怎麼調參數也得不到想要的答案。

**實務上的使用建議**：**鍵的命名要帶時間粒度**（`uv:20240115:14` 表示某日某小時），這樣才能靈活合併。**注意 `PFCOUNT` 對單個 HLL 是 O(1) 但對多個 key 是 O(N)**（要先合併），高頻呼叫時應該把合併結果快取起來。

## 面試回答方式

先給對比——**Set 的記憶體與基數成正比**（一千萬 UV 就是幾百 MB，而且每天一個），HLL 用**固定 12KB、誤差 0.81%**。原理要講得直觀：用雜湊值前導零的最大長度估算基數（出現 k 個前導零的機率是 2 的負 k 次方），分成 16384 個桶再用調和平均降低方差。給出核心取捨：**用 0.81% 的誤差換幾百 MB 到 12KB**，而 UV 這類指標本來就不需要精確。加分點有三個：`PFMERGE` 讓任意時間範圍的去重計數變成常數成本的合併，而且合併無損，這也是它適合分散式統計的根本原因；它只能算基數不能查詢成員，也不能刪除；以及**與 Bloom filter、Count-Min Sketch 的區分**——三者都用精確度換空間但回答的問題完全不同。

## 講稿

用集合存所有訪客 ID 是精確的，但記憶體跟基數成正比。一千萬個獨立訪客，加上節點開銷就是幾百 MB，而且每天一個。

HyperLogLog 用十二 KB 的固定空間估算任意大小的基數，標準誤差大約百分之零點八。

原理是用雜湊值前導零的最大長度來估算。一個均勻的雜湊值，出現 k 個前導零的機率是二的負 k 次方，所以如果觀察到最多 k 個前導零，元素數量大約就是二的 k 次方。單一觀察的方差很大，所以它把雜湊值分成一萬六千多個桶，每個桶記錄自己看到的最大前導零數，最後用調和平均合併。分桶加平均把方差降到可用的程度。

我覺得最被低估的能力是合併。存每小時一個 HLL，就能算出任意小時區間的獨立數，而且合併是無損的。用集合做這件事需要真的做聯集，成本跟資料量成正比。這種可合併性也是它適合分散式統計的根本原因，每個節點各自統計最後合併就好。

限制也要說清楚。它只能算基數，不能查詢某個成員在不在裡面，那要用布隆過濾器。而且不能刪除元素，因為前導零的最大值無法減回去。

## 常見追問

### 0.81% 的誤差在什麼情況下不能接受？

**核心答案**：當這個數字被用來做需要精確的決定時。計費（依獨立使用者數收費）、對帳、以及法規要求的統計都不能接受估算值。而在觀測與趨勢分析上，0.81% 完全不影響結論——今天的 UV 是 100 萬還是 100.8 萬，對「比昨天成長了 20%」這個判斷沒有任何影響。

**詳細解析**：還有一個微妙的情況：小數字時的相對誤差感受不同。基數 100 時 0.81% 是不到一個人，但如果用它比較兩個相近的數字（A 組 1000 人、B 組 1005 人），估算誤差可能讓比較的方向都是錯的。所以 HLL 不適合用來比較相近的數值——那需要精確計數。判斷的方式是問：這個數字的用途，能容忍多大的相對誤差？ 趨勢分析容忍度高，A/B 測試的顯著性判斷容忍度低。這提醒了一件事：近似演算法的「誤差可接受」是相對於用途而言的，不是一個絕對的性質。

**面試回答方式**：給明確的分界（計費、對帳、法規需要精確；觀測與趨勢不受影響）並用具體數字說明。真正的加分點是提出微妙情況：比較兩個相近的數字時，估算誤差可能讓比較方向都錯，所以 HLL 不適合這種用途。收在判斷方式：問這個數字的用途能容忍多大相對誤差，並指出近似演算法的「誤差可接受」是相對於用途的，不是絕對性質。

### Bitmap 與 HLL 該怎麼選？

**核心答案**：看元素是不是可以映射成連續的小整數。如果使用者 ID 是連續的自增整數（1 到 1000 萬），Bitmap 用 1000 萬個位元（約 1.2MB）就能精確記錄誰來過——精確、可以查詢單一使用者、還能做位元運算（`BITOP` 算多天的交集或聯集）。如果 ID 是 UUID 或稀疏的（1 到 10 億但只有 100 萬個活躍），Bitmap 要開 10 億個位元（125MB）就不划算，**這時 HLL 的固定 12KB 明顯更好**。

**詳細解析**：Bitmap 的獨特能力是「既能算基數也能查詢成員，還能做集合運算」——`BITCOUNT` 算基數、`GETBIT` 查單一使用者、`BITOP AND` 算「連續兩天都來的人數」。**這些 HLL 都做不到**（HLL 沒有成員查詢，`PFMERGE` 只能做聯集不能做交集）。所以「留存率分析」這類需要交集的場景，Bitmap 是明顯的選擇。 代價是它要求 ID 是密集的小整數——實務上常見的做法是維護一個「使用者 ID 到序號」的映射（用一個自增計數器分配序號），把稀疏的 ID 轉成密集的。這增加了一層間接與維護成本，但換到了精確性與集合運算能力，在留存分析這類需求上通常划算。

**面試回答方式**：給核心判準（元素能不能映射成連續的小整數）並用具體數字對比（1000 萬連續 ID 是 1.2MB，10 億稀疏空間是 125MB）。展開 **Bitmap 的獨特能力**——既能算基數也能查詢成員還能做集合運算，特別是 `BITOP AND` 算留存，而 **HLL 只能做聯集不能做交集**。加分點是實務做法：維護「使用者 ID 到序號」的映射把稀疏轉密集，多一層間接換到精確性與集合運算能力。

### 這類近似資料結構還有哪些值得知道？

**核心答案**：四個。**Bloom Filter**——回答「在不在」，可能誤判為在、不會誤判為不在，適合快取穿透防護與去重的第一層過濾。**Count-Min Sketch**——回答「出現幾次」，可能高估，適合熱點偵測與頻率統計。**Top-K**——直接維護出現次數最多的 K 個元素，適合排行榜的近似版本。**t-digest**——估算分位數（P50、P99），適合延遲統計。Redis Stack 的 RedisBloom 模組提供了前三個與 t-digest 的實作。

**詳細解析**：它們有一個共同的設計思路：用固定或亞線性的空間，換取一個有界的誤差。而且**誤差的方向通常是單向的**——Bloom filter 只會誤判為「在」、Count-Min Sketch 只會高估、HLL 的誤差是雙向但有界。單向誤差很有價值，因為它讓使用方知道該怎麼補救：Bloom filter 說「不在」就一定不在（可以直接返回），說「在」則需要進一步確認。設計自己的近似方案時，「誤差是單向還是雙向」應該是一個明確的設計決定，因為它決定了使用方能不能安全地依賴某一個方向的答案。這比記住每個結構的實作細節有用得多。

**面試回答方式**：列出四個結構與各自回答的問題，並提到 RedisBloom 模組。真正的加分點是歸納共同思路：用固定或亞線性空間換有界誤差，而且**誤差通常是單向的**——Bloom 只誤判為在、CMS 只高估。說明單向誤差的價值在於讓使用方知道怎麼補救（說「不在」就一定不在可以直接返回）。收在設計建議：「誤差是單向還是雙向」應該是明確的設計決定，因為它決定了使用方能不能安全依賴某個方向的答案。
