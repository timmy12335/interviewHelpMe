# 題目

當 Redis 記憶體不足時會怎麼辦？有哪些記憶體淘汰策略？LRU 和 LFU 有什麼區別？

## 核心答案

當 Redis 記憶體達到 `maxmemory` 上限時，會根據配置的「淘汰策略（maxmemory-policy）」來刪除一些 key 以騰出空間。策略主要分幾類——**noeviction**（不淘汰，記憶體滿了就拒絕寫入、返回錯誤，預設）、**針對「設了過期時間的 key」淘汰**（volatile-lru/lfu/ttl/random）、**針對「所有 key」淘汰**（allkeys-lru/lfu/random）。LRU（Least Recently Used，最近最少使用）淘汰「最久沒被存取」的 key；LFU（Least Frequently Used，最不經常使用，Redis 4.0+）淘汰「存取頻率最低」的 key。LFU 通常比 LRU 更能保留真正的熱資料（LRU 可能被「偶爾存取一次的冷資料」誤導）。

## 詳細解析

**淘汰的觸發**：Redis 配置了 `maxmemory`（最大記憶體）後，當記憶體使用達到這個上限、且有新的寫入請求時，就根據淘汰策略刪除一些 key 騰出空間。

**八種淘汰策略**：

- **noeviction**（預設）：不淘汰任何 key，記憶體滿了時，寫入命令直接返回錯誤（讀命令仍可執行）。適合「不能丟資料」的場景（但要保證記憶體夠用，否則寫入會失敗）。
- **針對「設了過期時間的 key（volatile）」**：
  - `volatile-lru`：在設了過期時間的 key 中，淘汰最近最少使用的。
  - `volatile-lfu`：在設了過期時間的 key 中，淘汰使用頻率最低的。
  - `volatile-ttl`：在設了過期時間的 key 中，淘汰剩餘存活時間最短（最快過期）的。
  - `volatile-random`：在設了過期時間的 key 中，隨機淘汰。
- **針對「所有 key（allkeys）」**：
  - `allkeys-lru`：在所有 key 中，淘汰最近最少使用的。（做快取時最常用。）
  - `allkeys-lfu`：在所有 key 中，淘汰使用頻率最低的。
  - `allkeys-random`：在所有 key 中，隨機淘汰。

**LRU vs LFU**：

- **LRU（最近最少使用）**：以「最後一次被存取的時間」為依據，淘汰最久沒被存取的。缺點——會被「偶發的一次存取」誤導：一個平時沒人用的冷 key，剛好最近被存取了一次，LRU 就認為它「最近用過、不該淘汰」，可能誤留冷資料、淘汰掉真正的熱資料。
- **LFU（最不經常使用，Redis 4.0+）**：以「存取頻率」為依據，淘汰存取次數最少的。它更能反映「真正的熱度」——真正的熱資料是「頻繁被存取」的，LFU 保留它們、淘汰那些「總存取次數少」的，不會被偶發的一次存取誤導。

**做快取時的選擇**：純快取場景通常用 `allkeys-lru`（或 `allkeys-lfu`）——淘汰不常用的、保留熱資料，讓 Redis 作為一個「自動保留熱資料」的快取。

## 面試回答方式

先講「淘汰的觸發」（記憶體達 maxmemory 上限 + 有寫入時）。八種策略不用死背全部，講清楚「分類邏輯」——noeviction（不淘汰、拒絕寫入）、volatile-xxx（只淘汰設了過期的）、allkeys-xxx（淘汰所有 key），每類裡有 lru/lfu/random/ttl 幾種依據。LRU vs LFU 是核心考點——講清「LRU 看最後存取時間、會被偶發存取誤導；LFU 看存取頻率、更能保留真熱資料」。能給出「做快取常用 allkeys-lru/lfu」的實務建議，展現你理解策略選擇。

## 常見追問

### 為什麼說 LFU 通常比 LRU 更適合做快取淘汰？

**核心答案**：因為 LFU 更能準確地識別和保留「真正的熱資料」。LRU 的判斷依據是「最後一次存取的時間」——它假設「最近被存取的就是熱的」，但這個假設有漏洞：一個平時幾乎沒人用的冷資料，如果剛好最近被偶然存取了一次(如一次性的批量掃描、一個爬蟲的偶然存取),LRU 就會認為它「最近用過、是熱的」而保留它,反而可能淘汰掉那些「稍早存取過但其實一直很熱」的資料。LFU 的判斷依據是「存取的頻率(次數)」——真正的熱資料的特徵是「被頻繁地、反覆地存取」,LFU 統計每個 key 的存取頻率、淘汰頻率最低的,所以那個「只被偶然存取一次」的冷資料因為總頻率低仍會被淘汰、真正頻繁存取的熱資料被保留。所以 LFU 不會被「偶發的單次存取」誤導,能更準確地保留真熱資料、提高快取命中率。

**詳細解析**：這題的核心是理解 LRU 的一個經典缺陷——「對偶發存取敏感」。舉個具體場景説明——假設快取裡有兩個 key:A 是一個熱門商品的資料(每秒被存取幾百次、非常熱)、B 是一個冷門商品(平時幾乎沒人看)。現在有一個定時的資料同步任務,凌晨掃描了一遍所有商品(包括 B),於是 B「最近被存取過一次」。此時如果記憶體不足要淘汰,LRU 會看「最後存取時間」——B 剛在凌晨被掃到、A 可能上一次存取是幾秒前,如果恰好在這個時間點,LRU 可能認為 B「更近被存取」而保留 B、淘汰 A(那個真正的熱資料)!這顯然是錯的——A 才是該保留的熱資料,B 只是被偶然掃了一次。LFU 就不會犯這個錯——它看的是「存取頻率」:A 的頻率是每秒幾百次、B 的頻率極低(就凌晨那一次),所以 LFU 會淘汰 B、保留 A,正確地保留了真熱資料。這就是為什麼「LFU 通常比 LRU 更適合快取」——快取的目標是「保留最有價值(最常被存取)的資料以提高命中率」,而 LFU 的「按頻率」正好對準這個目標,不會被偶發存取干擾。當然 LFU 也有自己的考量(如需要處理「曾經熱、現在冷」的資料的頻率衰減,Redis 的 LFU 實現有衰減機制),但總體上對「識別真熱資料」更準。理解 LRU 對偶發存取敏感的缺陷,展現你理解兩種策略的本質差異和快取淘汰的目標。

**面試回答方式**：講出「LRU 看最後存取時間、會被偶發的單次存取誤導(如批量掃描讓一個冷 key 顯得最近很熱、可能淘汰真熱資料);LFU 看存取頻率、真熱資料是高頻存取的、不會被偶發單次存取干擾、能準確保留真熱資料」。用「熱門商品 A vs 被凌晨掃描偶然存取的冷門商品 B」的例子説明 LRU 可能誤淘汰 A。展現你理解兩種策略的本質差異和快取淘汰的目標。

### Redis 的 LRU 是「精確的 LRU」嗎？

**核心答案**：不是。Redis 實現的是「近似 LRU（approximate LRU）」,而非精確的 LRU。精確的 LRU 需要「維護一個按存取時間排序的完整鏈結串列」(每次存取都把 key 移到鏈結串列頭部、淘汰時取尾部),這需要為所有 key 維護這個鏈結串列、且每次存取都要調整,記憶體和效能開銷都很大。Redis 為了省開銷,用「近似 LRU」——它不維護完整的排序鏈結串列,而是給每個 key 記錄一個「最後存取時間戳」,淘汰時「隨機抽樣」若干個 key、從這個樣本中淘汰最久沒存取的那個。這是抽樣的近似,不保證淘汰的一定是全域最久沒存取的,但透過調整抽樣數量(maxmemory-samples)可以在「精確度」和「開銷」之間權衡,樣本越大越接近精確 LRU。

**詳細解析**：這又是一個「Redis 為了效能和記憶體做的近似取捨」的例子(類似前面過期策略的抽樣)。精確 LRU 的實現代價——要維護一個包含所有 key、按最後存取時間排序的雙向鏈結串列,每次存取一個 key 都要把它從鏈結串列中移到頭部(O(1) 但要操作指標)、淘汰時取尾部。問題是這個鏈結串列要為「所有 key」維護,在 key 數量巨大時,這些額外的指標(每個 key 要存前後指標)消耗大量記憶體,且每次存取都要調整鏈結串列。Redis 覺得這個代價不划算——它的目標是「大致淘汰掉不常用的」,不需要「精確地淘汰全域最久未用的那一個」。所以 Redis 用近似 LRU——每個 key 的物件頭裡記一個「最後存取時間(一個較粗的時鐘)」,淘汰時不看全域,而是隨機抽取 maxmemory-samples(預設 5)個 key,從這幾個樣本裡挑最久沒存取的淘汰。這樣不用維護全域鏈結串列(省記憶體)、每次淘汰只看幾個樣本(省時間),代價是「淘汰的不一定是全域最優的、只是樣本裡最優的」。透過調大 maxmemory-samples(如設為 10),抽樣更多、結果更接近精確 LRU,但也更耗 CPU——這是精度和開銷的權衡。LFU 也是類似的近似實現。理解 Redis 用近似 LRU 的原因(省維護全域排序的開銷),展現你理解 Redis「為效能和記憶體做務實近似」的一貫設計哲學。

**面試回答方式**：講出「Redis 是近似 LRU 不是精確 LRU——精確 LRU 要維護全域按存取時間排序的鏈結串列、開銷大;Redis 用抽樣——每個 key 記最後存取時間、淘汰時隨機抽樣若干個從中淘汰最久未用的」。說明「可透過 maxmemory-samples 調整精度和開銷(樣本越大越接近精確但越耗 CPU)」。能點出「這是 Redis 為省開銷做的務實近似、和過期抽樣、near-LRU 是一貫的設計哲學」,展現你理解 Redis 的設計取捨。

### 如果設定了 noeviction 且記憶體滿了，會發生什麼？

**核心答案**：如果淘汰策略是 `noeviction`(不淘汰)且記憶體達到 maxmemory 上限,那麼——所有「會增加記憶體使用的寫入命令」(如 SET、LPUSH、增加資料的命令)都會被拒絕,返回一個 OOM 錯誤(`OOM command not allowed when used memory > 'maxmemory'`);而「讀命令」和「不增加記憶體的操作」(如 GET、DEL 刪除資料反而釋放記憶體)仍然可以正常執行。所以 noeviction 下記憶體滿了,Redis 變成「唯讀(不能寫入新資料)」的狀態,直到有資料被刪除/過期釋放出空間、或調大 maxmemory。這適合「絕對不能丟失資料(不能被淘汰)」的場景,但代價是「記憶體滿了就無法寫入」,所以必須保證記憶體規劃充足、或有監控及時擴容。

**詳細解析**：noeviction 的行為體現了「寧可拒絕寫入、也不淘汰資料」的取捨,適合「資料不能丟」的場景(如 Redis 被用作重要的資料儲存而非純快取,淘汰任何 key 都不可接受)。它的邏輯是——既然不能淘汰任何資料,那記憶體滿了就只能拒絕新的寫入(因為寫入會讓記憶體超限)。具體——當記憶體超過 maxmemory,Redis 會拒絕執行那些「會增加記憶體」的命令(寫入類),返回 OOM 錯誤,提醒你「記憶體不夠了、我不能再寫、又不能淘汰、所以只能拒絕」;但讀命令(不增加記憶體)還能用,DEL 等釋放記憶體的命令也能用(反而幫助騰出空間)。這意味著 noeviction 下記憶體滿了會導致「服務部分不可用」(不能寫)——這對很多場景是不可接受的。所以用 noeviction 必須配套——嚴格的記憶體容量規劃(保證 maxmemory 設得足夠、資料量不會超)、以及記憶體使用的監控告警(在接近上限前就告警、及時擴容或清理),避免真的撞到「無法寫入」的狀態。反過來,如果是純快取場景(資料能從 DB 重建、淘汰無所謂),就該用 allkeys-lru 之類的淘汰策略,讓 Redis 自動淘汰冷資料、始終能接受新寫入。理解 noeviction 的行為和適用場景,展現你理解淘汰策略要根據「資料能否丟失」來選。

**面試回答方式**：講出「noeviction 記憶體滿時——寫入命令被拒絕返回 OOM 錯誤、讀命令和釋放記憶體的命令仍可用、Redis 變成不能寫入的狀態」。説明「適合資料不能丟的場景、但代價是記憶體滿了無法寫入、所以必須配套嚴格的容量規劃和監控告警」。能對比「純快取場景該用 allkeys-lru 自動淘汰冷資料」,展現你理解淘汰策略要根據資料能否丟失來選。
