# 題目

Redis 在各種故障下最多會丟失多少資料？怎麼設定才能把損失控制在可接受範圍？

## 核心答案

丟失量取決於**故障類型**與**持久化設定**的組合。

**行程崩潰（Redis 被殺、OOM）**——AOF 的 `everysec` 最多丟一秒（實際上因為背景 fsync 的機制，最壞可能接近兩秒）；`always` 幾乎不丟（每個寫入都等 fsync）；純 RDB 則丟到上次快照為止（可能是幾分鐘到幾小時）。

**機器斷電或核心崩潰**——與上面相同，因為 fsync 是唯一能保證資料到磁碟的機制；沒有 fsync 的寫入還在作業系統的 page cache 裡，斷電就沒了。

**主從切換**——**這是最容易被低估的一項**。複製是非同步的，主節點確認寫入後、複製到從節點前故障，那些資料就丟了。**丟失量等於「複製延遲」**，正常情況下是毫秒級，但在網路抖動或從節點負載高時可能是數秒。

**設定的判斷順序是**：先問「這些資料能不能從別的地方重建」——能的話（純快取）持久化的重要性大幅下降；不能的話，**用 AOF `everysec` 加上多個從節點**是實務上的平衡點，`always` 的效能代價通常不值得。

## 詳細解析

「主從切換的丟失」值得特別強調，因為它與持久化設定無關。即使設定了 AOF `always`（主節點的資料絕對安全），故障轉移後新的主節點是從節點，它只有複製到的那些資料——主節點磁碟上的資料在它恢復之前都用不到，而且如果它以從節點身分重新加入，還會被新主節點的資料覆蓋。所以「持久化」與「高可用」保護的是不同的失敗場景：持久化保護「整個叢集重啟」，複製保護「單節點故障」。兩者都需要，而且都不能保證零丟失。

**`WAIT` 命令提供的是「等待」而非「保證」**。`WAIT numreplicas timeout` 阻塞直到指定數量的從節點確認接收，**但它不是同步複製**——它不會回滾已經在主節點生效的寫入，只是讓客戶端知道複製的進度。如果逾時了，寫入仍然存在於主節點，只是沒有複製出去。 所以它能降低丟失的機率，但無法提供「要嘛成功複製、要嘛不生效」的原子語意。真正需要那種保證的系統應該用有共識協定的儲存（etcd、以及支援同步複製的資料庫）。

**AOF `always` 的效能代價要具體理解**。它讓每個寫命令都等待 fsync 完成——在一般 SSD 上 fsync 是零點幾毫秒，於是寫入的 QPS 上限大約降到幾千（相對於 `everysec` 的十萬級）。在有電池備援快取的企業級儲存上代價較小，在雲端的網路磁碟上則可能更糟。 所以它只適合「寫入量小但每一筆都極重要」的場景，而那類場景通常本來就該用資料庫。

**多層防護的思路**：AOF 保護單機重啟、複製保護節點故障、定期備份（RDB 檔案傳到物件儲存）保護邏輯錯誤與災難。**最後一項最常被忽略**——複製不能防護「有人執行了 `FLUSHALL`」或「應用的 bug 寫壞了資料」，那些錯誤會被忠實地複製到所有從節點。**只有離線的備份能救。**

## 面試回答方式

先給**故障類型 × 持久化設定**的組合，並具體給出各自的丟失量。把**主從切換**標為最容易被低估的一項——**它與持久化設定無關**，即使 AOF `always` 讓主節點的資料絕對安全，故障轉移後新主節點只有複製到的那些，而舊主節點以從節點身分回來時還會被覆蓋。給出關鍵區分：持久化保護「整個叢集重啟」、複製保護「單節點故障」，兩者都需要且都不保證零丟失。加分點有三個：`WAIT` 提供的是等待而非保證（逾時後寫入仍然生效，沒有原子語意）；AOF `always` 讓寫入 QPS 從十萬級降到幾千，只適合寫入量小但每筆極重要的場景，而那類場景通常該用資料庫；以及定期備份最常被忽略——複製不能防護 `FLUSHALL` 或應用 bug 寫壞資料，那些錯誤會被忠實地複製到所有從節點，只有離線備份能救。

## 講稿

丟失量取決於故障類型跟持久化設定的組合。

行程崩潰或斷電的話，AOF 的每秒同步策略最多丟一秒，永遠同步幾乎不丟，純快照則丟到上次快照為止。

主從切換是最容易被低估的一項，而且它跟持久化設定無關。複製是非同步的，主節點確認寫入之後、複製出去之前故障，那些資料就丟了。丟失量等於複製延遲。就算設定了永遠同步讓主節點的資料絕對安全，故障轉移之後新的主節點是從節點，它只有複製到的那些。而舊主節點以從節點身分回來的時候，還會被新主節點的資料覆蓋。

所以持久化跟高可用保護的是不同的失敗場景。持久化保護整個叢集重啟，複製保護單節點故障，兩者都需要而且都不保證零丟失。

還有一個常被忽略的層次，就是定期備份。複製不能防護有人執行了清空命令，或是應用的 bug 寫壞了資料，那些錯誤會被忠實地複製到所有從節點。只有離線的備份能救。

我的設定順序是先問這些資料能不能從別的地方重建。能的話持久化的重要性大幅下降。不能的話，每秒同步加上多個從節點是實務上的平衡點。

## 常見追問

### everysec 為什麼最壞可能丟兩秒？

**核心答案**：因為 fsync 由背景執行緒執行，而主執行緒不會無限等它。正常情況是每秒觸發一次 fsync；但如果上一次的 fsync 還沒完成（磁碟慢），主執行緒在寫 AOF 緩衝時會發現這件事，並選擇「延後最多兩秒」再強制等待。所以在磁碟慢的情況下，緩衝裡可能累積了接近兩秒的資料還沒落盤。

**詳細解析**：這個「延後兩秒」的設計是在資料安全與延遲之間的取捨——如果主執行緒每次都等 fsync 完成，磁碟一慢整個 Redis 就卡住（那等於變成 `always`）；完全不等則緩衝會無限成長。Redis 選擇了「盡量不阻塞，但有一個上界」。`INFO stats` 的 `aof_delayed_fsync` 計數器記錄了這種延後發生的次數，它持續增加表示磁碟跟不上，應該被監控。這個案例很好地說明了「持久性保證的細節取決於實作」——文件上的「最多丟一秒」是理想情況，實際的保證要看實作怎麼處理異常路徑。在評估任何持久性承諾時，都應該問「異常情況下呢」。

**面試回答方式**：給機制——fsync 由背景執行緒做，主執行緒發現上次未完成時會延後最多兩秒再強制等待。說明這個設計的取捨（每次都等會變成 `always` 讓磁碟一慢就卡住，完全不等則緩衝無限成長）。給出該監控的指標 `aof_delayed_fsync`。收在一般觀點：持久性保證的細節取決於實作，文件上的「最多丟一秒」是理想情況，評估任何持久性承諾時都應該問「異常情況下呢」。

### 備份該怎麼做才可靠？

**核心答案**：四個要素。**離線儲存**——備份必須在 Redis 之外（物件儲存、異地），否則同一次災難會一起消失。**定期驗證恢復**——沒有演練過的備份等於沒有備份，應該定期把備份還原到一個臨時實例並驗證資料完整。**保留多個版本**——只有最新的備份無法防護「昨天就已經寫壞了但今天才發現」。**記錄備份的時間點與內容**，讓恢復時知道會丟失哪一段。

**詳細解析**：「定期驗證恢復」是最常被跳過也最致命的一項。備份腳本可能因為權限、磁碟空間、或某次變更而靜默失敗，而沒有人會注意到，直到真的需要恢復的那一天。驗證應該是自動化的：定期還原、檢查鍵數量與幾個抽樣值、並把結果上報成指標。**同樣重要的是量測恢復時間**——一個 50GB 的 RDB 檔案，下載加載入可能需要十幾分鐘，這個數字必須被知道並納入 RTO 的規劃，否則事故時的「我們有備份」會變成「但要兩小時才能恢復」。「備份的價值在於恢復，而恢復的可行性必須被證明」是這題的核心。

**面試回答方式**：給四個要素。重點展開「定期驗證恢復」最常被跳過也最致命——備份腳本可能靜默失敗而沒有人注意，直到真的需要的那天；驗證應該自動化（定期還原、檢查鍵數與抽樣值、上報指標）。加分點是**量測恢復時間並納入 RTO 規劃**——50GB 的檔案可能要十幾分鐘，否則「我們有備份」會變成「但要兩小時才能恢復」。收在核心：備份的價值在於恢復，而恢復的可行性必須被證明。

### 怎麼向業務方說明「可能丟失一秒的資料」？

**核心答案**：用具體的業務後果而非技術術語。「丟失一秒的資料」對業務方沒有意義，「在機器斷電的情況下，最多有 50 筆訂單狀態需要重新同步」才有。所以應該把技術上的丟失量換算成業務語言：這一秒內大約有多少筆什麼樣的操作、丟失後會表現成什麼、有沒有補償機制。

**詳細解析**：更重要的是給出「選擇」而非「現狀」。與其說「我們可能丟一秒」，不如說「目前的設定下最多丟一秒，如果要降到接近零，寫入吞吐會從十萬降到幾千，成本是需要多開 N 台機器；或者我們可以把關鍵資料改存資料庫，只有那部分不會丟」。把技術取捨轉譯成「選項與代價」，讓業務方能參與決策——這比單方面決定或單方面告知都好。很多技術風險之所以沒有被妥善處理，是因為它們從來沒有以業務方能理解的形式被提出過。 而一旦提出來，業務方常常會說「那部分資料確實不能丟，值得多花錢」或者「那個場景我們可以接受，不用改」——兩種答案都比工程師自己猜好。

**面試回答方式**：給原則——用具體的業務後果而非技術術語，並示範換算（「最多有 50 筆訂單狀態需要重新同步」）。真正的加分點是提升一層：**給出「選項與代價」而非「現狀」**，讓業務方能參與決策。收在觀點：很多技術風險沒有被妥善處理，是因為從來沒有以業務方能理解的形式被提出過，而一旦提出，得到的答案通常比工程師自己猜好。
