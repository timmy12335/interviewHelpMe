# 題目

Redis 的事務是怎麼實現的？它和關聯式資料庫的事務有什麼區別？WATCH 是做什麼的？

## 核心答案

Redis 的事務用 `MULTI`（開始事務）、`EXEC`（執行事務）、`DISCARD`（取消事務）實現——`MULTI` 後，客戶端發送的命令不會立即執行，而是被「排隊」；`EXEC` 時，這些排隊的命令會被「依序、連續地」執行（單執行緒下不會被其他客戶端的命令打斷，保證了「隔離性」和批次執行的原子性）。但 Redis 事務和關聯式資料庫的事務有重大區別——它「不支援回滾」：如果事務中某條命令執行出錯，其他命令仍會照常執行（不會像 DB 那樣全部回滾）。`WATCH` 用於實現「樂觀鎖」——監視一個或多個 key，如果在 EXEC 之前這些 key 被其他客戶端修改了，事務就會被取消（EXEC 返回 nil），用於「檢查-修改」的並發控制。

## 詳細解析

**Redis 事務的基本命令**：

- `MULTI`——標記事務的開始。之後客戶端發的命令不立即執行、而是排入一個佇列。
- `EXEC`——執行事務:把佇列裡的命令「依序、連續地」全部執行。因為 Redis 單執行緒,EXEC 執行這批命令期間不會插入其他客戶端的命令(保證了這批命令的「隔離執行」)。
- `DISCARD`——取消事務,清空命令佇列、不執行。
- `WATCH key...`——在 MULTI 之前監視一些 key(樂觀鎖,見下)。

**Redis 事務的特點(和 DB 事務的區別)**：

1. **不支援回滾(最重要的區別)**——這是 Redis 事務和 DB 事務最大的不同。如果事務中的某條命令執行時出錯(如對一個 String 執行 List 的命令),Redis「不會回滾」已經執行的其他命令、也會繼續執行後面的命令——它沒有 DB 那種「要麼全成功要麼全回滾」的原子性。Redis 作者的理由是——Redis 的命令出錯通常是「程式設計錯誤(用錯了命令/類型)」、應該在開發階段就發現,不需要為這種錯誤設計複雜的回滾機制。
2. **命令入隊時的語法錯誤會導致整個事務不執行**——如果在入隊階段就發現命令有語法錯誤(如命令名拼錯),EXEC 時整個事務會被拒絕、都不執行(這是入隊時就能檢測的錯誤)。但「執行時才發現的錯誤(如類型不對)」不影響其他命令。
3. **有隔離性(單執行緒保證)**——EXEC 執行事務的命令期間不會被打斷,所以有隔離性。

**WATCH——樂觀鎖(CAS)**：

- 用途——實現「先檢查某個 key、根據它的值決定怎麼修改」的並發安全(check-then-act)。
- 機制——`WATCH key` 監視一個 key,然後 MULTI...EXEC;在 EXEC 執行時,Redis 檢查「被 WATCH 的 key 從 WATCH 到現在有沒有被其他客戶端修改過」——如果被改過,EXEC 就「放棄執行整個事務、返回 nil」(表示「我監視的 key 變了、我的操作可能基於過時的值、所以取消」);沒被改過才執行。這是一種樂觀鎖——不加鎖,而是「先假設沒衝突、執行前檢查有沒有衝突、有衝突就放棄重試」。
- 典型場景——如「扣庫存」:WATCH 庫存 key、讀庫存、判斷夠不夠、MULTI 扣減 EXEC;如果 EXEC 時庫存被別人改了(WATCH 檢測到),EXEC 失敗、重試。

## 面試回答方式

先講基本命令(MULTI 排隊、EXEC 依序執行、DISCARD 取消)和「單執行緒保證 EXEC 期間不被打斷(隔離性)」。最重要的考點是「Redis 事務不支援回滾」——這是和 DB 事務最大的區別,一定要講清「某命令出錯不影響其他命令、沒有全或無的原子性、作者認為命令出錯是程式 bug 應開發時發現」。WATCH 是另一個重點——講清它實現「樂觀鎖」:監視 key、EXEC 時如果 key 被改過就取消事務、用於 check-then-act 的並發控制(舉扣庫存的例子)。能講出「不回滾」和「WATCH 樂觀鎖」這兩個特點,展現你理解 Redis 事務的本質(和 DB 事務很不一樣)。

## 常見追問

### 為什麼 Redis 事務不支援回滾？這樣設計合理嗎？

**核心答案**：Redis 作者(antirez)的理由是——Redis 事務中命令執行時出錯,幾乎都是「程式設計錯誤」(如對錯誤的資料類型用了命令、命令參數用錯),這類錯誤應該在「開發和測試階段」就被發現和修復,而不是在生產環境靠回滾來補救;為這種「本不該發生的程式 bug」設計複雜的回滾機制,會增加 Redis 的複雜度和降低效能,不划算。而 DB 的回滾主要是為了應對「執行期的各種預期外情況(約束衝突、死鎖、系統故障等)」,那些是「運行時可能合理發生」的,需要回滾。所以是否合理取決於視角——從「Redis 是高效能的資料結構服務、命令出錯主要是程式 bug」的定位看,不支援回滾(保持簡單高效)是合理的取捨;但從「習慣了 DB 事務的開發者」的角度,這確實是個容易踩坑的差異(以為和 DB 一樣有回滾)。

**詳細解析**：這題考的是「理解一個有爭議的設計決策背後的邏輯」。DB 事務的回滾是其 ACID 中原子性的核心——「要麼全做、要麼全不做」,任何一步失敗都回滾到事務開始前。DB 需要這個是因為——DB 事務執行中可能遇到各種「運行時合理發生的問題」:違反唯一約束、外鍵約束、死鎖被選為犧牲者、磁碟滿了等,這些不是程式 bug、是運行時可能出現的情況,需要回滾來保證資料一致。Redis 作者的觀點是——Redis 的情況不同:Redis 命令執行時出錯的情況很少,主要就是「用錯了命令或類型」(如對一個是 String 的 key 執行 LPUSH),這種是「程式寫錯了」、是 bug,應該在開發測試時就發現修復,不是運行時合理會發生的;為了處理這種「本不該出現的 bug」而給 Redis 加上回滾機制(要記錄每個命令的反向操作、出錯時撤銷),會顯著增加複雜度、影響效能,而 Redis 的核心價值是「簡單、高效」,不值得為此犧牲。所以他選擇「不回滾」——命令出錯就出錯(那條命令失敗),其他命令照常,把「保證命令都正確」的責任交給開發者(在開發時就別寫錯)。這個決策確實有爭議——它讓 Redis 事務不能提供 DB 那種「原子性保證」,對習慣 DB 的人是個陷阱。但從 Redis 的定位(高效能資料結構服務、不是關聯式資料庫)看,這個「保持簡單、把正確性責任前移到開發階段」的取捨是自洽的。理解這個決策的邏輯和爭議,展現你能理解設計取捨、不簡單地用 DB 的標準評判 Redis。

**面試回答方式**：講出作者的理由——「Redis 命令執行出錯幾乎都是程式設計錯誤(用錯命令/類型)、應該開發測試時發現、不是運行時合理發生的、為此加回滾會增加複雜度降效能不划算;DB 的回滾是為了運行時合理的問題(約束衝突、死鎖)」。給出平衡評價——「從 Redis 高效能、命令出錯主要是 bug 的定位看不回滾是合理取捨、但對習慣 DB 事務的人是容易踩的差異」。展現你能理解設計取捨、不用 DB 標準簡單評判 Redis。

### WATCH 實現的樂觀鎖和 Redis 分散式鎖有什麼區別？

**核心答案**：兩者都能做並發控制,但機制和適用場景不同。**WATCH 樂觀鎖**——是「樂觀」的:不加鎖,而是「先執行、EXEC 時檢查監視的 key 有沒有被改、有改就放棄重試」,適合「衝突較少、check-then-act」的場景(如扣庫存:讀庫存、判斷、扣減,用 WATCH 保證扣的時候庫存沒被別人改過),它的粒度是「Redis 內部的、對某些 key 的操作」,且是「單次事務內」的。**分散式鎖**——是「悲觀」的:先搶鎖、搶到才能操作、操作完釋放鎖,適合「保護一段業務邏輯的臨界區、防止多個客戶端/進程同時執行」的場景(如保證某個定時任務只有一個節點執行),它的粒度是「一段業務程式碼」、跨越多個操作甚至多個系統。簡言之——WATCH 樂觀鎖適合「Redis 內部對 key 的 check-then-act 並發控制、衝突少」;分散式鎖適合「保護跨操作/跨系統的業務臨界區、需要互斥」。

**詳細解析**：這題區分兩種並發控制手段的定位。**WATCH(樂觀鎖/CAS)**的本質是「樂觀並發控制」——它不阻止並發、而是「先做、提交時檢查有沒有衝突(監視的 key 被改了就是衝突)、有衝突就放棄本次、重試」。它的特點是「輕量(不加鎖、不阻塞)、但衝突多時要反覆重試」,所以適合「衝突不頻繁」的場景。它作用的範圍是「Redis 內部,對被 WATCH 的 key 在一次 MULTI/EXEC 事務內的並發保護」——典型是「基於某個 key 的當前值來決定如何修改它」這種 check-then-act(如根據當前庫存決定扣多少)。**分散式鎖**的本質是「悲觀並發控制」——先獲取鎖(互斥),獲取到的才能執行臨界區、其他的等待或放棄,執行完釋放。它的特點是「重(要搶鎖、可能阻塞等待)、但能可靠地互斥」。它作用的範圍更大——是「保護一整段業務邏輯(可能涉及多個 Redis 操作、甚至操作資料庫或呼叫其他服務)的臨界區,保證同一時間只有一個客戶端/進程在執行這段邏輯」。舉例區分——如果需求是「原子地根據 Redis 裡的庫存值扣減庫存」,用 WATCH 樂觀鎖就很合適(輕量、且這就是個 check-then-act);如果需求是「保證一個部署在多台機器上的定時任務只有一台在執行」,那 WATCH 不適用(這不是對某個 key 的 check-then-act、而是要互斥一整段業務執行),要用分散式鎖。所以選擇取決於——「是 Redis 內部對 key 的 check-then-act(且衝突少)」用 WATCH、「是要互斥一段業務臨界區(跨操作/跨系統)」用分散式鎖。理解兩者的機制(樂觀 vs 悲觀)和適用範圍(key 級 check-then-act vs 業務臨界區),展現你能區分不同的並發控制手段。

**面試回答方式**：講出「WATCH 樂觀鎖——不加鎖、EXEC 時檢查監視的 key 有沒有被改、有改就放棄重試、適合 Redis 內部對 key 的 check-then-act 且衝突少(如扣庫存);分散式鎖——悲觀、先搶鎖才能操作、適合保護跨操作/跨系統的業務臨界區、互斥(如定時任務只一個節點執行)」。概括「WATCH 適合 key 級的 check-then-act、分散式鎖適合業務臨界區的互斥」。展現你能區分不同並發控制手段的機制和適用範圍。

### Redis 的 Lua 腳本和事務相比，有什麼優勢？

**核心答案**：Lua 腳本相比 MULTI/EXEC 事務,在「原子性、靈活性、效能」上都有優勢——(1)**原子性更強**:Lua 腳本在 Redis 中是「原子執行」的(單執行緒下、腳本執行期間不插入其他命令),和事務一樣有隔離性,但 Lua 腳本裡「可以有邏輯(if/else、迴圈、根據前一個命令的結果決定下一步)」,而 MULTI/EXEC 只是「把命令排隊依序執行」、無法根據中間結果做判斷;(2)**能實現複雜的原子操作**:很多「需要根據讀取的結果來決定寫入」的複雜原子操作(如「如果庫存夠就扣減、否則不扣」),用事務做不到(事務不能在中間根據結果判斷)、但用 Lua 腳本可以(在腳本裡讀取、判斷、寫入,整個原子完成)——這也是前面分散式鎖釋放用 Lua 的原因;(3)**減少網路往返**:複雜邏輯用 Lua 一次發送到服務端執行,而不是客戶端多次往返(讀一次、判斷、再寫一次)。所以現在很多需要「原子的複雜操作」的場景,更傾向用 Lua 腳本而非 MULTI/EXEC 事務。

**詳細解析**：這題比較 Redis 兩種「原子執行多個操作」的手段,Lua 腳本在多數場景下更強。**事務(MULTI/EXEC)的局限**——它只是「把一批命令排隊、然後依序執行」,關鍵限制是「命令之間無法有邏輯關聯」:你不能「先讀一個值、根據這個值決定接下來執行什麼命令」(因為 MULTI 階段命令只是入隊、還沒執行、拿不到結果;EXEC 才執行、但那時命令已經定死了)。所以事務只適合「一批固定的、不依賴中間結果的命令的批次原子執行」。**Lua 腳本的優勢**——它是「在服務端執行一段程式」,腳本裡可以有完整的邏輯:讀取 key 的值、用 if 判斷、迴圈、根據結果決定寫什麼,而整個腳本是原子執行的(單執行緒、期間不被打斷)。這讓 Lua 能做很多事務做不到的「原子的複雜操作」——最典型的是「check-then-act 的原子化」:如「原子地扣庫存(讀庫存→判斷夠不夠→夠就扣→返回結果)」,這需要「根據讀取的庫存值決定是否扣減」,事務做不到(不能在中間判斷)、WATCH 樂觀鎖可以但要重試,Lua 腳本則能在服務端一次原子地完成(讀、判斷、扣,全在腳本裡、原子)。分散式鎖的釋放(判斷是不是自己的鎖→是才刪)也是用 Lua 保證原子(見 [[014-distributed-lock.md]])。此外 Lua 減少網路往返——複雜邏輯一次發過去執行,不用客戶端和服務端多次來回。所以趨勢是——需要「原子的、有邏輯的複雜操作」時用 Lua 腳本(更強大),簡單的「一批固定命令原子執行」才用事務(且 Lua 也能做)。要注意 Lua 腳本要避免寫得太複雜/太慢(單執行緒下慢腳本會阻塞一切)。理解 Lua 相比事務的優勢(能有邏輯、實現複雜原子操作、減少往返),展現你理解 Redis 原子操作的進階手段。

**面試回答方式**：講出 Lua 相比事務的優勢——「原子性一樣但 Lua 能有邏輯(if/迴圈/根據前面結果決定下一步)、事務只是排隊依序執行無法根據中間結果判斷;所以 Lua 能做複雜的原子操作(如原子扣庫存:讀→判斷→扣、事務做不到)、也是分散式鎖釋放用 Lua 的原因;還減少網路往返」。點出「趨勢是複雜原子操作用 Lua、但要避免腳本太慢(單執行緒阻塞)」。展現你理解 Redis 原子操作的進階手段。
