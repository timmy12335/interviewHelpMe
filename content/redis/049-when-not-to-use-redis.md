# 題目

有哪些場景不適合用 Redis？你看過哪些誤用？

## 核心答案

五類不適合的場景。需要強一致與持久性保證的資料——複製是非同步的、持久化有窗口，訂單、餘額、庫存的事實來源應該是資料庫。**複雜查詢**——Redis 只能依鍵查詢，需要多條件、範圍、聚合、關聯時，用資料庫或搜尋引擎。**大量冷資料**——記憶體成本遠高於磁碟，存放很少被存取的歷史資料是浪費。**大物件**——單一鍵存幾百 MB 會造成延遲、複製、與叢集均衡的全方位問題。**需要事務語意的多步驟操作**——Redis 的 `MULTI` 沒有回滾（命令失敗不影響其他命令），Lua 有原子性但沒有隔離級別的概念。

實務上看過的誤用，最常見的三個是：**把 Redis 當成主資料庫**（資料只存在於 Redis，重啟或切換就丟）、**用 `KEYS` 掃描生產環境**（阻塞整個實例）、以及**沒有 TTL 的快取**（記憶體緩慢成長直到爆掉，而且沒有人知道那些鍵是誰放的）。

判斷的核心問題是：「如果 Redis 現在整個消失，會發生什麼？」 答案是「服務變慢但仍然正確」就是健康的用法；答案是「資料丟失」或「功能不可用」就要重新評估。

## 詳細解析

「如果 Redis 消失會怎樣」這個問題非常有診斷力。它強迫你釐清 Redis 在系統中的角色——**加速層還是事實來源**。健康的架構裡，Redis 是可以被移除的（代價是變慢）；而一旦有資料只存在於 Redis，它就成了一個沒有交易、沒有備份文化、沒有 schema 的資料庫，而那幾乎總是後續事故的來源。這個問題也適合用在架構審查中，因為它比「你們用 Redis 做什麼」更能揭露真實的耦合。

**「Redis 當主資料庫」的滑坡是漸進的**。一開始只是快取，然後有人把 session 放進去（可以接受，丟了就重新登入），然後是分散式鎖的狀態，然後是「反正已經在 Redis 了」的計數器、排行榜、購物車——每一步都很小，但累積起來 Redis 裡有了大量無法從別處重建的資料。**防護的方式是明確的規則**：任何寫入 Redis 的資料，都要能回答「它能不能重建、不能的話備援在哪」。

**大 key 的問題值得單獨列為誤用**，因為它極其常見且危害全面：**存取慢**（O(N) 命令在單執行緒上阻塞所有請求）、**刪除慢**（要用 `UNLINK`）、**複製放大**（修改可能導致整個 key 重傳）、**fork 的 COW 成本高**、以及**無法分片**（一個 key 只能在一個節點上，成為熱點且限制均衡）。它通常來自「用一個 Hash 存所有使用者」或「用一個 List 當無界佇列」這類設計，而修正它需要資料遷移——所以在設計時就避免，比事後修正便宜得多。

「用 Redis 取代訊息佇列」的誤用有其合理的邊界。內部的輕量任務用 Stream 是合理的；但把它當成系統的事件骨幹（需要重放、長期保留、嚴格不丟）就是誤用。判斷的訊號是「開始自己實作死信、重放、分區管理」——那些是專門系統已解決的問題。

## 面試回答方式

先給**五類不適合的場景**並各配一句理由。然後給實務上最常見的**三個誤用**（當成主資料庫、用 `KEYS` 掃生產、沒有 TTL 的快取）。真正的重點是給出核心的診斷問題：「如果 Redis 現在整個消失，會發生什麼？」——答案是「變慢但仍然正確」就健康，是「資料丟失」或「功能不可用」就要重新評估。加分點有三個：**「當主資料庫」的滑坡是漸進的**（快取、session、鎖狀態、計數器⋯⋯每一步都小但累積起來有大量無法重建的資料），防護是明確的規則「任何寫入都要能回答它能不能重建」；**大 key 的危害是全方位的**（存取慢、刪除慢、複製放大、fork 成本、無法分片），而修正需要資料遷移所以設計時避免更便宜；以及「取代訊息佇列」的誤用訊號是開始自己實作死信與重放。

## 講稿

五類不適合的場景。需要強一致與持久性保證的資料、複雜查詢、大量冷資料、大物件、還有需要事務語意的多步驟操作。

實務上我看過最常見的三個誤用是，把 Redis 當成主資料庫、用掃描全部鍵的命令在生產環境查東西、還有沒有設過期時間的快取。

我判斷的核心問題是這一句：如果 Redis 現在整個消失，會發生什麼？答案是服務變慢但仍然正確，那就是健康的用法。答案是資料丟失或功能不可用，那就要重新評估。這個問題很有診斷力，因為它強迫你釐清 Redis 在系統中的角色，是加速層還是事實來源。

當主資料庫的滑坡是漸進的。一開始只是快取，然後有人把 session 放進去，可以接受，丟了就重新登入。然後是分散式鎖的狀態，然後是反正已經在 Redis 了的計數器、排行榜、購物車。每一步都很小，但累積起來就有了大量無法從別處重建的資料。

防護方式是一條明確的規則。任何寫入 Redis 的資料，都要能回答它能不能重建、不能的話備援在哪。

大 key 我會單獨列為誤用，因為它極其常見而且危害全面，而修正需要資料遷移，所以設計時避免比事後修正便宜得多。

## 常見追問

### session 存在 Redis 裡算不算誤用？

**核心答案**：**不算，但要理解它的後果**。session 是典型的「只存在於 Redis」的資料，**丟失的後果是使用者被登出**——那是可以接受的降級（使用者重新登入即可），而不是資料損失。所以它符合「Redis 消失後服務仍然正確」的標準，只是體驗變差。真正該注意的是：session 裡不要放無法重建的重要資料（例如購物車的唯一副本、或者一個進行到一半的表單的唯一狀態）。

**詳細解析**：「可接受的降級」與「資料損失」的區別是關鍵。使用者被登出是可回復的（重新登入）、影響有限的（只有當下在線的使用者）、且有明確的使用者感知（他知道發生了什麼）。而購物車消失則是不可回復的、使用者可能不知道自己失去了什麼、也無法自行修復。 判斷一個資料能不能只存在於 Redis，應該問「丟失後使用者能不能自行恢復」——能的話可以接受，不能的話就需要持久的備援。這個框架比「重要不重要」精確得多，因為「重要」是主觀的而「能不能自行恢復」是可以客觀判斷的。

**面試回答方式**：明確回答不算誤用，並給理由——丟失的後果是使用者被登出，那是可接受的降級而非資料損失，符合「Redis 消失後服務仍然正確」的標準。給出真正該注意的：session 裡不要放無法重建的重要資料。真正的加分點是提出判斷框架：問「丟失後使用者能不能自行恢復」，而這比「重要不重要」精確得多，因為前者可客觀判斷而後者主觀。

### 分散式鎖用 Redis 有什麼根本的問題？

**核心答案**：Redis 的鎖無法提供互斥的保證，只能提供效率的最佳化。原因有三個：**複製是非同步的**（主節點上鎖成功但還沒複製就故障，新主節點上鎖是空的，兩個客戶端同時持有）、**GC 停頓或網路延遲**（持鎖者以為自己還持有，實際上鎖已經過期並被別人取得）、以及**時鐘假設**（鎖的過期依賴時間，而時鐘可能不同步）。

**詳細解析**：「效率最佳化而非互斥保證」這個定位決定了正確的用法：鎖用來**減少重複工作**（避免十個實例同時做同一件事），**而不是用來保證正確性**。正確性必須由被保護的操作本身提供——用資料庫的唯一約束、樂觀鎖的版本號、或者讓操作冪等。**這個區分在實務上非常重要**：很多系統用 Redis 鎖「保護」一個非冪等的操作，然後在某次網路抖動後出現了重複執行的資料問題，而排查時完全想不通「明明有鎖」。如果真的需要互斥的保證，應該用有共識協定的系統（etcd、ZooKeeper）——它們用 Raft 或 ZAB 保證了「同一時刻只有一個持有者」這個性質，代價是延遲更高、部署更複雜。而多數場景其實不需要那個保證，只需要「大部分時候不重複」加上「重複了也沒關係」的冪等設計。

**面試回答方式**：給明確的定位——Redis 的鎖是效率最佳化而非互斥保證，並給三個原因（非同步複製、GC 停頓與網路延遲、時鐘假設）。展開這個定位決定的正確用法：鎖用來減少重複工作，正確性必須由被保護的操作本身提供（唯一約束、版本號、冪等）。給出實務痛點：很多系統用它「保護」非冪等操作，出問題時**完全想不通「明明有鎖」**。收在選型：真正需要互斥保證該用 etcd 或 ZooKeeper，而多數場景其實只需要「大部分時候不重複」加冪等設計。

### 怎麼判斷一個新需求該不該用 Redis？

**核心答案**：依序問四個問題。**這個資料的事實來源在哪？** 如果答案是 Redis，先確認那是有意識的決定並有對應的持久化與備份。**存取模式是不是「依鍵取值」？** 需要複雜查詢就不該用。資料量與存取頻率的比例如何？ 大量冷資料放記憶體是浪費。如果 Redis 不可用，這個功能怎麼降級？ 沒有答案的話就是一個新的單點。

**詳細解析**：第四個問題最有價值，因為它逼出了「降級路徑」這個常被忽略的設計。多數需求討論會聚焦在「正常情況下怎麼運作」，而「異常情況下怎麼辦」往往被推遲到上線後才想——但那時候是在事故中臨時決定。在設計階段就回答它，成本很低而收益很高：可能發現這個功能其實不需要 Redis（直接查資料庫就夠快）、或者發現需要一個本地快取作為第二層、或者確認「這個功能在 Redis 掛掉時可以直接停用」。**三種答案都比「沒想過」好。** 這個「先問失敗時怎麼辦」的習慣，是區分「能設計出可運維系統的人」與「只考慮happy path 的人」的一個實際指標。

**面試回答方式**：給四個依序的問題。重點強調**第四個最有價值**——它逼出了降級路徑這個常被忽略的設計，而多數討論聚焦在正常情況、異常情況被推遲到事故中臨時決定。說明在設計階段回答它**成本很低收益很高**：可能發現不需要 Redis、需要第二層本地快取、或確認可以直接停用，**三種答案都比「沒想過」好**。收在觀點：「先問失敗時怎麼辦」是區分能設計可運維系統的人的實際指標。
