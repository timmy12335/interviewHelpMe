# 題目

`INFO memory` 裡的各項數字代表什麼？記憶體碎片率高該怎麼處理？

## 核心答案

關鍵的四個數字：`used_memory`（Redis 自己認為用了多少，也就是資料加上內部結構）、`used_memory_rss`（作業系統看到的常駐記憶體，也就是實際佔用的實體記憶體）、`mem_fragmentation_ratio`（前兩者的比值）、以及 **`maxmemory`**（設定的上限，淘汰策略的觸發點）。

**碎片率的解讀不是「越低越好」**：**大於 1**（例如 1.5）表示配置器保留了比實際需要更多的記憶體——常見成因是大量的刪除與寫入造成的外部碎片。**小於 1** 表示**部分記憶體被交換到磁碟（swap）**，這比碎片嚴重得多——Redis 的延遲會災難性地上升，因為記憶體存取變成了磁碟 IO。**理想值大致在 1.0 到 1.5 之間。**

處理碎片的手段：**啟用主動碎片整理**（`activedefrag yes`，jemalloc 提供的能力，Redis 會在背景把資料搬到更緊湊的位置）、**重啟**（最徹底但有服務中斷）、或**主從切換**（在從節點上重啟再切換，避免中斷）。

**注意 `used_memory` 不包含所有記憶體**——複製緩衝區、客戶端輸出緩衝區、以及 AOF 緩衝區在某些統計裡是分開的，容量規劃時要一併考慮。

## 詳細解析

**碎片的成因值得理解**。Redis 用 jemalloc 依大小分級配置記憶體（size class），一個 100 位元組的物件可能實際佔用 112 位元組——這是內部碎片，無法避免但可預測。外部碎片則來自「刪除留下的空洞無法被不同大小的新物件使用」——大量刪除或改寫變長的值時特別嚴重。所以「先寫入大量資料再刪除大部分」的使用模式會產生很高的碎片率，而這正是很多快取場景的實際模式。

**`activedefrag` 的代價是 CPU**。它在背景掃描並搬移資料，會佔用一定的 CPU 並輕微增加延遲。相關參數（`active-defrag-ignore-bytes`、`active-defrag-threshold-lower/upper`、`active-defrag-cycle-min/max`）控制觸發門檻與積極程度。保守的設定讓它只在碎片明顯時才工作，這通常是對的——碎片率 1.2 完全不值得付出 CPU 去整理。

`maxmemory` 應該明確設定，而且要留出餘裕。不設的話 Redis 會一直配置直到耗盡系統記憶體並被 OOM Killer 殺掉。設定值應該是「容器或機器記憶體」減去「非資料的記憶體」——複製緩衝區（`repl-backlog-size`）、客戶端緩衝區（連線數乘以每連線的緩衝）、AOF 重寫時的額外記憶體、以及 fork 時可能的寫時複製開銷。實務上留 25% 到 30% 的餘裕是常見的做法，而在寫入密集或 fork 頻繁的場景要留更多。

**記憶體使用的分析工具**：`MEMORY USAGE key` 看單一鍵的佔用、`MEMORY DOCTOR` 給出診斷建議、`--bigkeys` 與 `--memkeys`（redis-cli 的選項）掃描出最大的鍵。`MEMORY STATS` 給出最詳細的分解，包括資料、複製、客戶端、AOF 各佔多少——這是容量問題排查的起點。

## 面試回答方式

先給**四個關鍵數字**的意義，然後把**碎片率的解讀**講清楚：**不是越低越好**——大於 1 是配置器保留了多餘記憶體，小於 1 表示部分記憶體被交換到磁碟，那比碎片嚴重得多（延遲災難性上升）。給處理手段（`activedefrag`、重啟、主從切換）。加分點有三個：**碎片的成因**——內部碎片來自 size class 的向上取整、外部碎片來自刪除留下的空洞，而「先寫入大量資料再刪除大部分」正是很多快取的實際模式；`maxmemory` 要留 25% 到 30% 的餘裕給複製緩衝、客戶端緩衝、AOF 重寫與 fork 的寫時複製；以及排查用 `MEMORY STATS` 看資料、複製、客戶端、AOF 各佔多少。

## 講稿

關鍵有四個數字。Redis 自己認為用了多少、作業系統看到的常駐記憶體、兩者的比值也就是碎片率、還有設定的上限。

碎片率的解讀不是越低越好。大於一表示配置器保留了比實際需要更多的記憶體，常見成因是大量刪除與寫入造成的外部碎片。小於一則表示部分記憶體被交換到磁碟，這比碎片嚴重得多，因為記憶體存取變成了磁碟 IO，延遲會災難性地上升。理想值大致在一到一點五之間。

碎片的成因有兩種。內部碎片來自配置器依大小分級，一個一百位元組的物件可能實際佔一百一十二位元組。外部碎片來自刪除留下的空洞無法被不同大小的新物件使用。所以先寫入大量資料再刪除大部分的使用模式會產生很高的碎片率，而那正是很多快取場景的實際模式。

處理手段有主動碎片整理、重啟、或是在從節點重啟再切換。碎片整理的代價是 CPU，所以保守的設定讓它只在碎片明顯時才工作是對的，碎片率一點二完全不值得付出 CPU 去整理。

還有一點，上限一定要明確設定而且留出餘裕。因為複製緩衝區、客戶端緩衝區、還有重寫時的額外記憶體都不在資料的統計裡。我通常留兩到三成。

## 常見追問

### 為什麼碎片率小於 1 是嚴重問題？

**核心答案**：因為它表示部分記憶體已經被作業系統交換到磁碟（swap out）——`used_memory_rss`（實體記憶體）小於 `used_memory`（Redis 認為的用量），差額就在磁碟上。Redis 是記憶體資料庫，它的效能假設是「所有存取都是記憶體存取」；一旦有資料在 swap 上，存取那些資料會觸發磁碟 IO，延遲從微秒級變成毫秒級甚至更糟，而且因為是單執行緒，一次慢存取會阻塞所有請求。

**詳細解析**：**正確的做法是完全禁止 swap**（`vm.swappiness=0` 或在容器裡不配置 swap），讓記憶體不足直接表現為 OOM 而非靜默的效能崩潰。這聽起來反直覺——OOM 會讓行程被殺掉，而 swap 至少還能跑——但對 Redis 而言，一個因為 swap 而延遲百倍的實例，比一個乾脆掛掉並被重啟的實例更糟：它會拖垮所有依賴它的服務，而且問題極難診斷（監控上看起來還活著）。這是「快速失敗優於緩慢降級」原則的一個具體案例，同樣的思路適用於很多基礎設施元件。

**面試回答方式**：給精確的機制（RSS 小於 used_memory 表示差額在磁碟上）與後果（延遲從微秒變毫秒，且單執行緒下一次慢存取阻塞所有請求）。真正的加分點是主張**完全禁止 swap**，並解釋這個反直覺的選擇：一個因 swap 延遲百倍的實例，比乾脆掛掉被重啟的更糟——它拖垮所有依賴者且監控上看起來還活著。收在原則：**快速失敗優於緩慢降級**。

### 大 key 對記憶體管理有什麼影響？

**核心答案**：三方面。**配置與釋放的成本**——一個 1GB 的大 key，`DEL` 它需要釋放大量記憶體，在單執行緒上是幾百毫秒的阻塞（所以要用 `UNLINK` 交給背景執行緒）。**碎片**——大物件的配置與釋放留下大空洞，難以被重用。**複製與持久化的放大**——一個大 key 的任何修改都可能導致整個 key 被複製到從節點（取決於命令），而 fork 時它的寫時複製成本也很高。

**詳細解析**：「大 key 的危害是全方位的」是這題的重點——它不只佔記憶體，還影響延遲（存取與刪除都慢）、複製（頻寬與延遲）、持久化（fork 的 COW）、以及叢集（無法拆分，成為熱點且限制了分片的均衡）。所以發現大 key 應該當成一個需要修正的設計問題，而不是調參能解決的事。 常見的修正是**拆分**：一個裝了一百萬個欄位的 Hash 拆成一千個各裝一千個欄位的 Hash（用 `key:{hash(field) % 1000}` 分片）。代價是「取得全部」變成一千次查詢，但那個操作本來就不該存在。掃描大 key 用 `redis-cli --bigkeys`（取樣，開銷小）或 `--memkeys`（更精確但慢），應該納入例行巡檢。

**面試回答方式**：給三方面影響並各配具體數字或機制。強調**大 key 的危害是全方位的**——記憶體、延遲、複製、持久化、叢集均衡都受影響，所以它是設計問題而非調參能解決的事。給出修正方式（拆分成多個小 key）與誠實的代價（「取得全部」變成很多次查詢，但那個操作本來就不該存在）。收在可操作建議：**`--bigkeys` 納入例行巡檢**。

### 記憶體用量的容量規劃該怎麼做？

**核心答案**：分三部分估算。**資料本身**——用 `MEMORY USAGE` 量測代表性的鍵，乘以預期的鍵數量；注意 Redis 的每個鍵有約 50 到 100 位元組的固定開銷（鍵物件、值物件、字典項、過期字典項），小值的場景下這個開銷可能超過資料本身。**非資料部分**——複製積壓緩衝區、客戶端輸出緩衝區（連線數乘以緩衝上限）、AOF 緩衝。**餘裕**——fork 時的寫時複製（最壞情況接近資料量的一倍）、碎片、以及成長空間。

**詳細解析**：「每個鍵的固定開銷」常常被嚴重低估。存一百萬個 `user:123 -> "1"` 這樣的小鍵值對，資料本身只有幾 MB，**但實際佔用可能是 100MB 以上**——絕大部分是每個鍵的元資料。所以「用很多小鍵」是一個記憶體效率很差的模式，正確的做法是**用 Hash 聚合**（一個 Hash 存一千個欄位，共用一份鍵開銷），而且小 Hash 會用 ziplist/listpack 這種緊湊編碼，記憶體可能只有十分之一。這是 Redis 記憶體優化中投資報酬率最高的一項，也是為什麼「編碼」那題重要——知道什麼時候會用緊湊編碼，就知道怎麼設計鍵的結構。

**面試回答方式**：給三部分估算並強調 fork 的寫時複製最壞接近資料量的一倍。真正的加分點是展開每個鍵的固定開銷常被嚴重低估——一百萬個小鍵值對資料只有幾 MB 但實際佔用超過 100MB，絕大部分是元資料。給出解法：**用 Hash 聚合共用鍵開銷**，而且小 Hash 會用緊湊編碼記憶體可能只有十分之一。收在定位：這是 Redis 記憶體優化投資報酬率最高的一項。
