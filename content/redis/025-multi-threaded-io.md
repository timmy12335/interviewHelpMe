# 題目

Redis 6 引入了多執行緒，那「Redis 是單執行緒」還成立嗎？它多執行緒化了哪一部分？

## 核心答案

**命令的執行仍然是單執行緒的**——這一點沒有改變，也是 Redis 保持簡單與無鎖的基礎。多執行緒化的是 **IO 的讀寫與協定解析**：從 socket 讀取請求位元組、解析成命令、以及把回應序列化並寫回 socket，這些工作被分給多個 IO 執行緒。

原因是**瓶頸的位置變了**。在千兆網路與一般負載下，Redis 的瓶頸是網路 IO 與協定處理，不是命令執行本身（多數命令是 O(1) 的記憶體操作，只要幾百奈秒）。**單執行緒處理十萬 QPS 時，大部分時間花在讀寫 socket 上**——把這部分平行化，吞吐可以提升一到兩倍。

啟用方式是設定 `io-threads`（預設 1，也就是關閉），以及 `io-threads-do-reads yes`（預設只平行化寫出，開啟後讀取也平行化）。**官方建議執行緒數不超過 CPU 核心數，且四核以上的機器才值得開**。

**關鍵推論**：因為命令執行仍是單執行緒，**一個慢命令（`KEYS *`、大的 `SMEMBERS`）仍然會阻塞所有其他請求**——多執行緒 IO 完全沒有改善這一點。

## 詳細解析

**「單執行緒」這個說法一直都不精確**。Redis 從很早就有背景執行緒處理特定工作：`BGSAVE` 是 fork 出的子行程、`UNLINK` 的實際釋放與 `FLUSHALL ASYNC` 由 lazy-free 執行緒處理、AOF 的 fsync 也可以由背景執行緒做。**準確的說法是「命令執行是單執行緒的」**，這才是 Redis 無鎖、簡單、且行為可預測的來源。

**單執行緒執行命令的價值不只是簡單**。它讓每個命令天然是原子的——不需要鎖，也就沒有死鎖、沒有競態、沒有優先權反轉。**這也是 `INCR`、`SETNX`、以及各種原子操作能成為可靠的分散式原語的基礎。** 換成多執行緒執行命令的話，這些保證要靠鎖來維持，而那會引入 Redis 刻意避開的一整類複雜度。

**多執行緒 IO 的實際收益依場景而定**。它對「大量小請求」的場景效果最明顯（協定處理佔比高）；對「少量大請求」（例如取一個 1 MB 的值）幫助有限，因為瓶頸在記憶體複製與網路頻寬。**而且它增加了 CPU 使用率**——在 CPU 受限的容器裡開啟可能適得其反。**判斷的方式是量測：開啟前後比較吞吐與 CPU，而不是預設它一定更快。**

**更有效的優化通常在別處**：**用 pipeline 或 MGET 減少往返次數**（一次往返處理多個命令，這比任何伺服器端的優化都有效）、**避免大 key 與慢命令**、以及**用讀寫分離或叢集分散負載**。**多執行緒 IO 是一個邊際改善，不是架構層面的解方**——理解這個定位比記住怎麼開啟它更重要。

## 面試回答方式

先給最重要的區分：**命令執行仍然是單執行緒，多執行緒化的是 IO 讀寫與協定解析**。給出原因——瓶頸在網路 IO 與協定處理而非命令執行（多數命令只要幾百奈秒）。給啟用方式與官方建議（不超過核心數、四核以上才值得）。**關鍵推論要說出來**：因為執行仍是單執行緒，**慢命令仍然會阻塞所有請求，多執行緒 IO 完全沒有改善這一點**。加分點有三個：**「單執行緒」一直都不精確**（早就有 lazy-free、fsync、fork 的背景工作），準確說法是「命令執行是單執行緒的」；**單執行緒執行的價值是讓每個命令天然原子**，這是分散式原語的基礎；以及**更有效的優化通常在別處**（pipeline 減少往返、避免大 key），多執行緒 IO 是邊際改善而非架構解方。

## 講稿

命令的執行仍然是單執行緒的，這一點沒有改變。多執行緒化的是 IO 的讀寫跟協定解析，也就是從 socket 讀取請求位元組、解析成命令、把回應序列化寫回去。

原因是瓶頸的位置變了。在一般負載下，Redis 的瓶頸是網路 IO 跟協定處理，不是命令執行本身，因為多數命令是常數時間的記憶體操作，只要幾百奈秒。單執行緒處理十萬 QPS 的時候，大部分時間花在讀寫 socket 上。

有一個關鍵推論要說。因為命令執行仍然是單執行緒，一個慢命令，像是掃描全部鍵或取一個很大的集合，仍然會阻塞所有其他請求。多執行緒 IO 完全沒有改善這一點。

另外我想澄清，單執行緒這個說法一直都不精確。Redis 很早就有背景執行緒處理特定工作，像是延遲釋放跟持久化的同步。準確的說法是命令執行是單執行緒的。

而這個單執行緒執行的價值不只是簡單，它讓每個命令天然是原子的，不需要鎖。這是各種原子操作能成為可靠分散式原語的基礎。

## 常見追問

### 為什麼 Redis 不乾脆把命令執行也多執行緒化？

**核心答案**：因為**代價遠大於收益**。多執行緒執行命令需要對資料結構加鎖，而 Redis 的資料結構被高度優化過（緊湊編碼、共享物件、就地修改），**加鎖會破壞這些優化並引入可觀的常數成本**。更重要的是它會**破壞「每個命令天然原子」這個保證**——那是 Redis 被當成分散式原語（鎖、計數器、限流器）使用的基礎。

**詳細解析**：**橫向擴展是更好的答案**。需要更多執行能力時，開多個 Redis 實例（叢集或分片）比讓單個實例多執行緒化更簡單、更可預測、也更能利用多台機器。**這是一個「用架構解決而非用實作解決」的選擇**——Redis 選擇保持單實例的簡單，把擴展交給分片。**代價是分片帶來的複雜度**（跨槽操作受限、重新分片的成本、客戶端要理解拓撲）。**近年出現的 DragonflyDB 等專案則選了另一條路**——用多執行緒加分片的內部架構在單機上提供更高吞吐，代價是與 Redis 的行為有細微差異。**兩條路都成立，差別在於把複雜度放在哪一層。**

**面試回答方式**：給代價（需要加鎖、破壞資料結構的優化、**破壞每個命令天然原子這個保證**）並指出後者是分散式原語的基礎。真正的加分點是提出**橫向擴展是更好的答案**，這是「用架構解決而非用實作解決」的選擇，代價是分片的複雜度。收在對照：**DragonflyDB 選了另一條路**（單機多執行緒加內部分片），兩條路都成立，差別在把複雜度放在哪一層。

### 慢命令怎麼發現與避免？

**核心答案**：發現用 **`SLOWLOG`**（記錄執行時間超過 `slowlog-log-slower-than` 的命令，預設 10 毫秒）與 **`LATENCY MONITOR`**（記錄各類延遲事件的來源，包含 fork、過期、AOF 等）。避免的原則是**不要在生產環境執行 O(N) 且 N 很大的命令**：`KEYS`（用 `SCAN` 取代）、`SMEMBERS`／`HGETALL`／`LRANGE 0 -1`（用 `SSCAN` 系列或限制範圍）、以及對大 key 的 `DEL`（用 `UNLINK` 非同步釋放）。

**詳細解析**：**`SCAN` 系列的正確理解很重要**：它用游標分批遍歷，**保證「遍歷期間一直存在的元素一定會被回傳」，但不保證不重複**（重新雜湊期間同一個元素可能被回傳兩次），也**不保證看得到遍歷期間新增的元素**。使用方必須自己去重。**這是一個典型的「用弱保證換取不阻塞」的設計**——`KEYS` 給你完整一致的快照但阻塞整個伺服器，`SCAN` 給你較弱的保證但不影響其他請求。**在生產系統上，這個取捨幾乎總是該選 `SCAN`。** 另外要注意 `SCAN` 的 `COUNT` 只是提示而非精確的批次大小，而且**在大量鍵的情況下完整遍歷可能需要很多次往返**，要考慮總耗時。

**面試回答方式**：給發現的工具（`SLOWLOG` 與 `LATENCY MONITOR`）與避免的具體命令對照（`KEYS`→`SCAN`、`HGETALL`→`HSCAN`、`DEL`→`UNLINK`）。真正的加分點是解釋 **`SCAN` 的保證**：保證一直存在的元素會被回傳、不保證不重複、不保證看得到新增的，所以使用方要自己去重。收在取捨的本質：**用弱保證換不阻塞**，而在生產系統上這個取捨幾乎總是該選 `SCAN`。

### Pipeline 為什麼比多執行緒 IO 更有效？

**核心答案**：因為它消除的是**網路往返（RTT）**，而那通常是延遲的主要成分。一次跨機房的往返可能是 1 毫秒，而 Redis 執行一個命令只要幾百奈秒——**也就是說 99.9% 的時間花在等待網路上**。Pipeline 把 100 個命令一次送出、一次收回，往返從 100 次變成 1 次，**吞吐可以提升數十倍**，而多執行緒 IO 只能提升一到兩倍。

**詳細解析**：**這說明了一個通用的優化原則：先消除往返，再優化單次操作。** 同樣的思路出現在資料庫的批次插入、HTTP/2 的多工、以及 GraphQL 的一次請求取多個資源。**Pipeline 的限制是「命令之間不能有依賴」**——後一個命令的參數不能依賴前一個的結果，因為它們是一起送出的。需要依賴時可以用 **Lua 腳本**（在伺服器端執行，可以有邏輯與分支）。**要注意 pipeline 不是交易**——中間某個命令失敗不會影響其他命令，也沒有隔離性；而且**一次送太多命令會讓回應緩衝區膨脹**（客戶端輸出緩衝區有上限，超過會斷線），實務上一批 100 到 1000 個是合理的範圍。

**面試回答方式**：給核心原因——**消除網路往返，而往返佔了 99.9% 的時間**（1 毫秒 RTT vs 幾百奈秒的執行），並量化對比（數十倍 vs 一到兩倍）。把它提升成通用原則：**先消除往返、再優化單次操作**，並舉批次插入與 HTTP/2 多工作為同類。加分點是限制與注意事項：**命令之間不能有依賴**（需要依賴用 Lua）、**pipeline 不是交易**、以及一次送太多會讓緩衝區膨脹導致斷線，實務上一批 100 到 1000 個。
