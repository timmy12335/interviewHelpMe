# 題目

Redis 的備份該怎麼做？要把資料從一個實例遷移到另一個有哪些方式？

## 核心答案

**備份的基礎是 RDB 檔案**——它是一個自包含的二進位快照，可以直接複製到別處。做法是 `BGSAVE` 產生（或用既有的定期快照），把檔案傳到物件儲存，**保留多個版本**。AOF 檔案也能備份但體積大得多且恢復慢。

**備份必須滿足四個條件才算數**：**離線儲存**（在 Redis 之外，否則同一次災難一起消失）、**多版本保留**（防護「昨天就寫壞了今天才發現」）、**定期驗證恢復**（**沒有演練過的備份等於沒有備份**）、以及**已知的恢復時間**（納入 RTO 規劃）。

**遷移的方式有四種**，依情境選擇：**主從複製再切換**（最平滑，適合同版本、同架構的遷移——讓新實例成為舊實例的從節點，同步完成後提升為主）、**RDB 檔案搬移**（簡單但有停機窗口）、**`MIGRATE` 命令**（逐鍵搬移，適合部分資料或跨叢集）、以及**雙寫加校驗**（應用同時寫兩邊，讀取逐步切換，最靈活但要改應用）。

**跨大版本或跨架構（單機到叢集）時，主從複製可能不可用**，那時雙寫是最穩妥的方案。

## 詳細解析

**「主從複製再切換」為什麼最平滑**：新實例作為從節點完成全量同步後，**它與舊實例的資料是持續一致的**（只差複製延遲）；切換時只需要 `REPLICAOF NO ONE` 提升新實例並讓應用連過去，**停機窗口是秒級的**。**代價是它要求版本相容**（新版本可以作為舊版本的從節點，反之通常不行）與**架構相同**（單機到單機、叢集到叢集）。

**「雙寫加校驗」是跨架構遷移的標準做法**，值得詳細理解。流程是：**應用同時寫入新舊兩邊**（先寫舊、再寫新，新的失敗只記錄不影響主流程）、**背景任務把存量資料從舊搬到新**（用 `SCAN` 遍歷）、**持續校驗兩邊的一致性**（抽樣比對）、**讀取逐步切換**（先少量流量讀新的並比對結果，再逐步放大）、**最後停止雙寫**。**它的優勢是每一步都可回退，而且切換前就已經驗證了新環境的正確性。** 代價是需要改應用、過渡期較長、且雙寫本身有一致性的邊界情況（例如寫舊成功寫新失敗，需要靠背景校驗修補）。

**恢復時間必須被量測**。一個 20GB 的 RDB 檔案：從物件儲存下載（依頻寬可能幾分鐘）、Redis 載入（大約每 GB 幾秒到十幾秒）、加上服務切換的時間——**總計可能十幾分鐘**。**這個數字必須在事故發生前就知道**，因為它決定了業務能不能接受、以及要不要用其他手段（例如維持一個熱備實例）縮短它。**「我們有備份」與「我們能在 X 分鐘內恢復」是完全不同的兩件事**，而只有後者對業務有意義。

**遷移的驗證清單**：資料筆數比對（`DBSIZE` 或按前綴計數）、抽樣的值比對、**TTL 是否正確保留**（`MIGRATE` 與 RDB 都會保留，但自己寫的搬移腳本很容易漏掉）、以及**應用行為的驗證**（不只是資料對，還要確認應用在新環境下的功能正常）。**TTL 遺失是自訂遷移腳本最常見的錯誤**——資料看起來都對，但幾天後開始出現「快取永遠不過期」或「應該過期的資料還在」的問題。

## 面試回答方式

先給備份的基礎（RDB 檔案自包含、可直接複製）與**四個必要條件**（離線、多版本、定期驗證恢復、已知恢復時間），並強調**沒有演練過的備份等於沒有備份**。給**四種遷移方式**與各自的適用情境，指出**跨大版本或跨架構時主從複製可能不可用，雙寫最穩妥**。加分點有三個：**「雙寫加校驗」的完整流程**（雙寫、背景搬存量、持續校驗、讀取逐步切換、停止雙寫）與它的優勢——**每一步都可回退且切換前就驗證了正確性**；**恢復時間必須被量測**——20GB 的檔案總計可能十幾分鐘，**「我們有備份」與「我們能在 X 分鐘內恢復」是完全不同的兩件事**；以及**TTL 遺失是自訂遷移腳本最常見的錯誤**，資料看起來都對但幾天後開始出問題。

## 講稿

備份的基礎是快照檔案，它是自包含的二進位檔，可以直接複製到別處。但備份必須滿足四個條件才算數。離線儲存、多版本保留、定期驗證恢復、還有已知的恢復時間。其中定期驗證最常被跳過也最致命，沒有演練過的備份等於沒有備份。

遷移有四種方式。主從複製再切換最平滑，讓新實例成為舊實例的從節點，同步完成後提升為主，停機窗口是秒級的。但它要求版本相容而且架構相同。

跨架構的話，雙寫加校驗是標準做法。應用同時寫兩邊、背景任務搬存量資料、持續校驗一致性、讀取逐步切換、最後停止雙寫。它的優勢是每一步都可回退，而且切換前就已經驗證了新環境的正確性。

恢復時間必須被量測。一個二十 GB 的檔案，下載加載入加切換可能十幾分鐘。這個數字必須在事故發生前就知道，因為它決定了業務能不能接受。我們有備份跟我們能在幾分鐘內恢復，是完全不同的兩件事。

還有一個很常見的錯誤，自己寫的遷移腳本容易漏掉過期時間。資料看起來都對，但幾天後開始出現快取永遠不過期，或是該過期的資料還在。

## 常見追問

### 雙寫期間怎麼保證兩邊一致？

**核心答案**：**不保證強一致，而是靠「持續校驗加修補」達成最終一致**。雙寫必然有邊界情況：寫舊成功但寫新失敗、兩個並行的寫入在兩邊的順序不同、或者背景搬移與即時寫入的競態。**處理方式是：讓新的寫入失敗不阻塞主流程（只記錄），並由一個持續執行的校驗任務比對兩邊、修補差異。**

**詳細解析**：**校驗的設計是這件事的核心**。全量比對成本高，**實務上是「抽樣比對 + 針對記錄的失敗做定向修補」**：抽樣負責發現系統性的問題（例如某類鍵一直沒同步），定向修補處理已知的個別失敗。**還要處理「背景搬移與即時寫入的競態」**——搬移某個鍵時它剛好被更新，可能把舊值搬過去覆蓋了新值。**標準的解法是「搬移時用 `SETNX` 語意」**（只在新環境不存在時才寫入），因為即時寫入的值一定比存量的新。**這類遷移的正確性論證應該在動手前就完成**，而不是遇到不一致才想辦法——**「先想清楚有哪些交錯順序，再決定每一種怎麼處理」是資料遷移最重要的準備工作。**

**面試回答方式**：明確指出**不保證強一致而是最終一致**，靠持續校驗加修補。列出必然的邊界情況（寫舊成功寫新失敗、並行寫入順序不同、搬移與即時寫入競態）。展開**校驗的設計**：抽樣發現系統性問題、定向修補處理已知失敗。給出競態的標準解法：**搬移時用只在不存在時寫入的語意**，因為即時寫入的值一定比存量新。收在準備工作：**先想清楚有哪些交錯順序、再決定每一種怎麼處理**。

### RDB 檔案能跨版本使用嗎？

**核心答案**：**向後相容但不向前相容**——新版本的 Redis 能載入舊版本產生的 RDB，反之不行（RDB 有版本號，新版本可能引入舊版本不認識的編碼）。**所以升級是安全的，降級不是**——如果升級後發現問題想回滾，**新版本產生的 RDB 無法被舊版本載入**，必須有升級前的備份。

**詳細解析**：**這讓「升級前備份」變成硬性要求而非建議**。而且要注意**備份必須是升級前的版本產生的**——升級後才做的備份對回滾沒有幫助。**回滾計畫應該包含「用哪一份備份、恢復到哪裡、會丟失哪一段資料」三個明確的答案**。另一個相關的問題是**跨版本的行為差異**：即使資料能載入，某些命令的行為或預設值可能改變（例如前面提過的從節點回傳過期資料的行為在 3.2 改變）。**所以升級的驗證不能只確認「資料還在」，還要驗證應用的行為**。**「能載入」與「行為相同」是兩個不同的保證，而升級計畫需要同時確認兩者。**

**面試回答方式**：給明確答案（向後相容、不向前相容）與推論：**升級安全、降級不安全**，所以回滾必須有升級前的備份。強調**備份必須是升級前版本產生的**，升級後才做的對回滾沒有幫助。給出回滾計畫該有的三個明確答案（用哪份備份、恢復到哪、丟失哪一段）。收在更完整的觀點：**「能載入」與「行為相同」是兩個不同的保證**，升級驗證不能只確認資料還在，還要驗證應用行為。

### 雲端託管的 Redis 在備份上有什麼不同？

**核心答案**：託管服務通常提供**自動快照與時間點恢復**，省去了自己管理備份的工作。**但有三個要確認的**：**備份的保留期與頻率**（是否符合你的 RPO 需求）、**恢復的粒度與時間**（是恢復整個實例還是能選擇資料庫？恢復要多久？）、以及**能不能匯出到自己的儲存**（**如果只能在該雲端服務內恢復，那就是一種鎖定**，而且無法防護「帳號層級的問題」如誤刪或權限被撤銷）。

**詳細解析**：**「能不能匯出」是最容易被忽略但最重要的一項**。託管服務的自動備份保護了硬體故障與人為的資料錯誤，**但它保護不了「整個雲端帳號出問題」的場景**——帳單問題導致資源被停用、憑證外洩導致資源被刪除、或者服務本身的區域性故障。**真正的災難恢復需要備份存在於另一個信任邊界之外。** 實務上的做法是定期把 RDB 匯出到另一個帳號或另一個雲端的物件儲存，**即使託管服務已經有備份**。**這個「不要把所有雞蛋放在一個信任邊界裡」的原則，在雲端時代比在自建機房時代更重要**，因為雲端的便利讓「全部託管給一家」變成了預設選擇。

**面試回答方式**：給託管服務的優勢與**三個要確認的項目**。重點展開**「能不能匯出」最容易被忽略但最重要**——自動備份保護硬體故障與資料錯誤，**但保護不了整個雲端帳號出問題的場景**（帳單、憑證外洩、區域故障）。給出實務做法：定期匯出到另一個帳號或另一個雲端的物件儲存，即使託管已有備份。收在原則：**不要把所有雞蛋放在一個信任邊界裡**，這在雲端時代比自建時代更重要因為便利讓全部託管變成預設。
