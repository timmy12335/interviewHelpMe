# 題目

Redlock 演算法是什麼？它解決了什麼問題？為什麼有爭議？

## 核心答案

Redlock 是 Redis 作者提出的一種「更可靠的分散式鎖（Distributed Lock）」演算法，用來解決「單個 Redis（主從）分散式鎖在主從切換時可能失效」的問題（見 [[014-distributed-lock.md]]）。它的核心思想是——不依賴單一 Redis，而是用「多個（如 5 個）相互獨立、不互為主從的 Redis 主節點」，加鎖時要「向這多個節點都嘗試加鎖」，只有在「多數節點（如 5 個中的 3 個，N/2+1）都加鎖成功、且總耗時在鎖有效期內」時，才算加鎖成功。這樣即使少數節點宕機，鎖依然有效。但 Redlock 有爭議——分散式系統專家 Martin Kleppmann 質疑它在「時鐘跳變、GC 停頓、網路延遲」等情況下仍不可靠，引發了與 Redis 作者的著名辯論；結論是——Redlock 比單 Redis 鎖可靠，但仍不能提供「絕對」的正確性保證。

## 詳細解析

**Redlock 要解決的問題**：單個 Redis（即使有主從）的分散式鎖，在「主節點加鎖後、還沒複製給從節點就宕機、從節點被提升為新主」時，會導致鎖失效（兩個客戶端同時持鎖）。根源是主從複製的非同步性。

**Redlock 的方案（多節點多數決）**：

1. 準備 N 個（推薦 5 個）「相互獨立」的 Redis 主節點（它們不互為主從、各自獨立部署）。
2. 加鎖時——客戶端「依次向這 N 個節點」都嘗試加鎖（用相同的 key 和 unique value、設過期時間），並記錄總耗時。
3. 判斷加鎖成功的條件——「在『多數』節點（N/2+1，如 5 個中的 3 個）上加鎖成功」，且「加鎖的總耗時 < 鎖的有效期」。滿足才算真正加鎖成功。
4. 釋放鎖時——向「所有」N 個節點都發送釋放命令（不管當初在哪些節點加成功）。

**為什麼多數決能提高可靠性**：因為要「多數節點都加鎖成功」才算成功，所以即使「少數節點宕機或出問題」，只要多數還正常、鎖依然有效；且兩個客戶端不可能「同時在多數節點上都加鎖成功」（多數決保證了互斥）。這樣就不依賴單一節點、避免了單 Redis 的主從切換問題。

**Redlock 的爭議（Martin Kleppmann 的質疑）**：

- 著名的分散式系統專家 Martin Kleppmann 撰文質疑 Redlock 的正確性，主要論點——在「GC 停頓、進程暫停、時鐘跳變、網路延遲」等情況下，Redlock 仍可能失效。例如——客戶端加鎖成功後，發生了一次長時間的 GC 停頓（暫停期間鎖過期了、被別人搶走），GC 恢復後客戶端「以為自己還持有鎖」繼續操作，就和搶到鎖的另一個客戶端衝突了。這類問題的根源是——「基於過期時間的鎖」無法應對「持鎖者被暫停超過過期時間」的情況。
- Redis 作者 antirez 做了回應辯護。這場辯論很有名，結論性的共識是——**Redlock 比單 Redis 鎖更可靠，但沒有任何基於「時間/過期」的分散式鎖能提供絕對的正確性保證**；如果需要絕對的正確性（如涉及金錢），應該用「fencing token（單調遞增的令牌）」等額外機制，或用專門的一致性系統。

## 面試回答方式

先講 Redlock 要解決的問題（單 Redis 主從切換導致鎖失效）。然後講它的方案——「多個獨立 Redis 節點、多數決（N/2+1 都加鎖成功才算成功）」，並解釋為什麼多數決能避免單節點問題。爭議是這題的深度所在——講 Martin Kleppmann 的質疑（GC 停頓/時鐘跳變下仍可能失效、用一個 GC 停頓導致鎖過期被搶的例子）和結論（Redlock 更可靠但無絕對保證、需要絕對正確性要用 fencing token 或專門系統）。能講出這場著名辯論和「沒有基於時間的鎖能絕對可靠」的結論，展現你對分散式鎖的理解達到了很深的層次。

## 常見追問

### Martin Kleppmann 質疑 Redlock 的核心論點是什麼？用一個例子說明。

**核心答案**：核心論點是——Redlock（以及所有「基於過期時間」的分散式鎖）無法應對「持鎖的客戶端發生了長時間的暫停（如 GC 停頓、進程被作業系統掛起）」的情況。例子——客戶端 A 成功加鎖（鎖有效期 30 秒），然後 A 開始執行業務；但就在此時，A 發生了一次長達 40 秒的 Full GC 停頓（JVM 暫停了所有應用執行緒）；在這 40 秒裡，A 的鎖過期了（30 秒到期）、被自動釋放，客戶端 B 於是成功搶到了這把鎖、開始操作臨界資源；然後 A 的 GC 結束、恢復執行，A「以為自己還持有鎖」（它不知道自己暫停了 40 秒、鎖早過期了），繼續操作臨界資源——此時 A 和 B 同時在操作同一個臨界資源，鎖的互斥性被破壞了。這說明——鎖的「過期時間」和「持鎖者的實際執行」可能脫節（持鎖者被暫停超過過期時間時），而 Redlock 無法偵測和防止這種情況。

**詳細解析**：這個例子深刻地揭示了「基於時間/過期的鎖」的根本局限。問題的核心是——分散式鎖用「過期時間」來防死鎖（Deadlock）（持鎖者掛了鎖能自動釋放），但「過期時間」是按「真實時間」走的，而「持鎖的客戶端」可能因為各種原因被暫停（GC 停頓、作業系統把進程換出、虛擬機器被暫停、網路分區等），暫停期間客戶端「感知不到時間流逝」、也「感知不到自己的鎖已經過期」。於是就出現「鎖已經過期(按真實時間)、被別人搶走了，但原持鎖者恢復後還以為自己持有鎖」的危險情況。Kleppmann 的例子用 GC 停頓最典型——一次長 GC(尤其大堆的 Full GC)可能停頓幾秒甚至幾十秒，足以超過鎖的過期時間;GC 期間客戶端完全暫停(不知道鎖過期了)，別的客戶端搶到鎖開始工作，GC 恢復後原客戶端繼續它「以為還持有鎖」的操作，兩者衝突。這個問題 Redlock 解決不了(多節點多數決解決的是「單節點故障」，解決不了「持鎖者自身被暫停」)、任何基於過期時間的鎖都解決不了。Kleppmann 的結論是——如果鎖用於「效率」(避免重複工作，偶爾失效問題不大)，Redlock 夠用;但如果鎖用於「正確性」(絕對不能兩個客戶端同時操作，如涉及金錢)，就不能只靠這種鎖，需要額外的「fencing token」機制。理解這個例子和它揭示的根本局限，展現你對分散式鎖可靠性的理解達到了專家級的深度。

**面試回答方式**：講出核心論點——「基於過期時間的鎖無法應對持鎖者長時間暫停(GC 停頓等)」，並完整講這個例子——「A 加鎖(30 秒)、發生 40 秒 GC 停頓、期間鎖過期被 B 搶走、A 恢復後以為還持鎖繼續操作、和 B 衝突」。強調「鎖的過期時間和持鎖者的實際執行可能脫節、Redlock 和任何基於時間的鎖都解決不了」。展現你對分散式鎖可靠性的深度理解。

### 什麼是 fencing token？它怎麼解決這個問題？

**核心答案**：fencing token（隔離令牌）是 Martin Kleppmann 提出的、用來彌補分散式鎖局限的機制——每次成功加鎖時，鎖服務會頒發一個「單調遞增的令牌（token，一個不斷增大的數字）」給客戶端;客戶端在「操作被保護的資源(如寫入儲存)」時，要「帶上這個 token」;而被保護的資源(儲存服務)會「記住它見過的最大 token、拒絕任何 token 比它小的操作」。這樣——如果客戶端 A 加鎖拿到 token 33、然後 GC 停頓、鎖過期、客戶端 B 加鎖拿到 token 34(遞增的)、B 帶著 34 去寫資源(資源記下見過 34);之後 A 恢復、帶著舊的 token 33 去寫資源——資源發現 33 < 34(已見過的最大)、拒絕 A 的寫入。這樣即使 A 錯誤地以為自己還持鎖，它的過期操作也會被資源端用 token 擋掉，保證了正確性。

**詳細解析**：fencing token 的精妙之處在於——它「不試圖讓鎖本身變得完美」，而是「在被保護的資源端加一道防線、用單調遞增的令牌擋掉過期持鎖者的操作」。回顧前面的問題——A 加鎖後 GC 停頓、鎖過期被 B 搶走、A 恢復後帶著「過期的鎖認知」去操作資源。光靠鎖無法阻止 A 的這個操作(A 以為自己持鎖)。fencing token 的解法是「讓資源端能識別並拒絕過期的操作」——關鍵是「單調遞增」:每次加鎖頒發的 token 都比上一次大(如用一個全域遞增的計數器)，所以「後加鎖的人的 token 一定比先加鎖的人大」。資源端(如資料庫、儲存服務)維護「見過的最大 token」，只接受 token >= 已見最大的操作、拒絕更小的。時序——A 拿 token 33、B(後來搶到)拿 token 34;B 先帶 34 去寫、資源記下 34;A 恢復後帶 33 去寫、資源發現 33 < 34、拒絕。這樣 A 的過期操作被擋在資源端，即使 A 的鎖邏輯出了問題(以為還持鎖)，也無法真正破壞資源。fencing token 把「保證正確性」的責任從「不可能完美的分散式鎖」轉移到了「資源端的令牌校驗」，這是一個更可靠的設計。但它要求——鎖服務能頒發單調遞增的 token、且「被保護的資源」要支援 token 校驗(能記住最大 token、拒絕更小的)，這需要資源端的配合(不是所有資源都支援)。ZooKeeper 的 zxid、etcd 的 revision 等天然提供了這種單調遞增的令牌。理解 fencing token 如何「在資源端用遞增令牌擋過期操作」來彌補鎖的局限，展現你對分散式鎖正確性問題有專家級的完整理解。

**面試回答方式**：講出「fencing token 是單調遞增的令牌——每次加鎖頒發一個遞增的 token、客戶端操作資源時帶上它、資源端記住見過的最大 token、拒絕 token 更小的操作」。用例子説明——「A 拿 token 33、GC 停頓、B 搶鎖拿 34、B 帶 34 寫資源(記下 34)、A 恢復帶 33 寫、被資源拒絕(33<34)」。點出「它把保證正確性的責任轉移到資源端的令牌校驗、比不可能完美的鎖更可靠、但需要資源端支援(ZooKeeper zxid/etcd revision 天然提供)」。展現你對這個問題有專家級的完整理解。

### 那實務中到底該不該用 Redis 分散式鎖 / Redlock？

**核心答案**：要根據「鎖是用於效率還是正確性」來決定。如果鎖是用於「效率」——即「避免重複做同一件工作」(如避免多個節點同時重建同一個快取、同時發同一封郵件)，偶爾鎖失效(兩個節點同時做了)只是「多做了一次、浪費一點資源」、不會造成嚴重後果，那麼「單 Redis 分散式鎖」就足夠了(簡單、高效、夠用)，不需要 Redlock 的複雜度。如果鎖是用於「正確性」——即「絕對不能兩個客戶端同時操作」(如涉及金錢、庫存等，同時操作會導致資料錯誤)，那麼「任何基於時間的鎖(包括 Redlock)都不能提供絕對保證」，應該——用 fencing token(在資源端校驗)、或改用專門的強一致協調系統(ZooKeeper、etcd)，或在資料層加最終的保障(如資料庫唯一約束、樂觀鎖（Optimistic Lock）)。所以——效率場景用簡單的 Redis 鎖、正確性場景不能只靠 Redis 鎖。

**詳細解析**：這是對整個分散式鎖話題的實務總結，核心是「先分清鎖的用途，再選方案」。這個「效率 vs 正確性」的區分來自 Kleppmann——它決定了你能容忍多大的鎖失效風險。**效率用途**——鎖只是「優化」，目的是「盡量避免重複工作」。例如:一個定時任務部署在多個節點上，你不希望它們同時執行(重複做)，用鎖讓一個節點做;但萬一鎖失效、兩個節點都執行了，後果只是「這個任務被做了兩次」(可能浪費點資源、或需要任務本身冪等)，不會造成資料錯誤。這種場景，單 Redis 鎖(簡單、快)完全夠用，失效機率很低、失效了後果也輕，沒必要上 Redlock 的複雜度。**正確性用途**——鎖是「安全保障」，絕對不能有兩個客戶端同時進臨界區。例如:扣庫存、轉帳，如果兩個客戶端同時操作，可能超賣、餘額算錯，後果嚴重。這種場景，必須認識到「基於時間的鎖(Redis 鎖、Redlock)都可能因 GC 停頓等失效」，不能把正確性「只」壓在鎖上，而要——用 fencing token 在資源端擋過期操作、或用 ZooKeeper/etcd(基於一致性協定、更適合強一致的協調)、或在最終的資料層加保障(資料庫的唯一約束能防重複、樂觀鎖/悲觀鎖（Pessimistic Lock）能防並發修改)。所以實務的成熟做法是——「效率場景大膽用簡單的 Redis 鎖、正確性場景把鎖當『第一道優化』但在資料層有『最終的正確性保障』(不單純依賴鎖)」。理解這個「按用途選方案、正確性場景不單靠鎖」的實務判斷，展現你有成熟的分散式系統設計思維。

**面試回答方式**：講出「按鎖的用途分——效率用途(避免重複工作、偶爾失效只是多做一次、後果輕)用簡單的單 Redis 鎖就夠;正確性用途(絕對不能同時操作、如金錢庫存)不能只靠 Redis/Redlock(基於時間的鎖都可能因 GC 停頓失效)、要用 fencing token/ZooKeeper/etcd/或資料層保障(唯一約束、樂觀鎖)」。強調「效率場景大膽用 Redis 鎖、正確性場景要有資料層的最終保障、不單靠鎖」。展現你有成熟的分散式系統設計思維。
