# 題目

Redis 的 key 設定了過期時間，到期後是怎麼被刪除的？

## 核心答案

Redis 用「惰性刪除 + 定期刪除」兩種策略結合來刪除過期的 key。**惰性刪除**——當有請求存取一個 key 時，Redis 才檢查它是否過期，過期就刪除並返回 nil（「被存取到才刪」）。**定期刪除**——Redis 每隔一段時間（透過 serverCron）「隨機抽取」一部分設了過期時間的 key 檢查，把其中過期的刪除（「定期抽樣清理」）。兩者結合——惰性刪除保證「過期的 key 一旦被存取就會被清理」（但沒被存取的過期 key 不會清），定期刪除彌補了「那些過期了但一直沒被存取的 key」（定期抽樣清掉一部分），兩者互補，在「及時清理」和「不浪費 CPU」之間取得平衡。

## 詳細解析

**為什麼不用「定時刪除」（到期立刻刪）**：理論上最及時的是「為每個 key 設一個定時器、到期立刻刪」，但這需要為每個 key 維護定時器、且大量 key 同時到期時會佔用大量 CPU 做刪除，開銷太大。所以 Redis 不用這種方式。

**惰性刪除（Lazy Deletion）**：

- 機制——不主動檢查 key 是否過期，只有當「有命令要存取這個 key」時，才順便檢查它過不過期，過期就刪除（並當作 key 不存在處理）。
- 優點——對 CPU 友好（不主動做無謂的檢查、只在存取時順便查）。
- 缺點——如果一個過期的 key「一直沒被存取」，它就一直不會被刪除，白白佔用記憶體（記憶體洩漏（Memory Leak）風險）。

**定期刪除（Active/Periodic Deletion）**：

- 機制——Redis 的定時任務（serverCron，預設每秒執行 10 次）會「隨機抽取」一部分設了過期時間的 key 進行檢查，刪除其中已過期的。它不檢查所有 key（那樣太耗時），而是抽樣——每次抽一批、如果過期比例高就再抽一批，直到過期比例降到閾值以下或達到時間上限。
- 優點——能清理「過期了但沒被存取」的 key，彌補惰性刪除的不足。
- 平衡——抽樣而非全查、有時間限制，避免了清理本身佔用太多 CPU 阻塞命令處理。

**兩者結合**：惰性刪除保證「被存取的過期 key 及時清理、且不返回過期資料」，定期刪除保證「沒被存取的過期 key 也能被逐步清理、不會無限堆積」。結合起來在「記憶體及時釋放」和「CPU 開銷可控」之間取得平衡。（另外，如果記憶體不足，還有淘汰策略作為最後防線，見 [[009-eviction-policy.md]]。）

## 面試回答方式

先講「為什麼不用定時刪除」（每個 key 一個定時器開銷太大），引出 Redis 的「惰性 + 定期」結合方案。惰性刪除講「存取時才檢查、CPU 友好但沒存取就不刪」。定期刪除講「定時任務隨機抽樣檢查刪除、彌補惰性的不足」。核心是講清「兩者互補、在及時清理和 CPU 開銷間平衡」——惰性保證被存取的及時清、定期保證沒存取的也逐步清。能點出「定期刪除是抽樣而非全查（避免清理本身太耗 CPU）」和「還有淘汰策略作為記憶體不足時的最後防線」，展現你理解這套機制的完整設計。

## 常見追問

### 只有惰性刪除會有什麼問題？只有定期刪除呢？

**核心答案**：只有惰性刪除的問題——「過期但一直沒被存取的 key 永遠不會被刪除」，這些 key 白白佔用記憶體，如果有大量這種 key（如批量設定了過期時間但之後不再存取的 key），會導致記憶體被過期資料佔滿、造成記憶體洩漏。只有定期刪除的問題——定期刪除是「抽樣」的、不是每個過期 key 都能被及時掃到，所以可能存在「已過期但還沒被定期任務抽到、也還沒被存取」的 key 短暫存在；如果只靠定期刪除，且抽樣沒掃到某個過期 key，那麼在它被抽到之前，如果有請求存取它、就可能返回過期的資料（沒有惰性刪除來保證「存取時檢查過期」）。所以兩者必須結合——惰性刪除保證「存取時絕不返回過期資料」、定期刪除保證「沒被存取的過期 key 也能逐步清理」。

**詳細解析**：這題透過「單獨用一種會怎樣」來凸顯兩者互補的必要性。只有惰性刪除的致命問題是「記憶體洩漏」——考慮一個場景，你批量給一百萬個 key 設了 1 小時過期,1 小時後它們都過期了，但如果之後沒有任何請求存取這些 key，惰性刪除就永遠不會觸發(它只在存取時才檢查)，這一百萬個過期 key 就一直佔著記憶體不釋放。這對記憶體是嚴重浪費甚至可能耗盡記憶體。所以需要定期刪除來主動清理這些「過期但沒人存取」的 key。反過來，只有定期刪除的問題是「可能返回過期資料」——定期刪除是抽樣的、有時間限制的，不保證每個 key 過期的瞬間就被刪，所以在「某 key 過期了、但還沒被定期任務抽樣掃到」的這段時間裡，如果只有定期刪除、沒有惰性刪除，那麼此時存取這個 key 可能返回它過期的舊值(因為沒有「存取時檢查過期」的機制)。惰性刪除正是補上這一點——保證「任何時候存取一個 key、都會先檢查它過不過期、過期就當作不存在」，絕不返回過期資料。所以兩者缺一不可——惰性保證「正確性(不返回過期資料)」、定期保證「記憶體效率(清理沒人存取的過期 key)」。理解單獨用的缺陷，展現你理解為什麼要兩者結合。

**面試回答方式**：講出「只有惰性刪除——過期但沒被存取的 key 永不刪除、記憶體洩漏;只有定期刪除——抽樣不及時、可能在抽到前存取到過期資料(沒有存取時檢查的保證)」。強調「兩者互補缺一不可——惰性保證不返回過期資料(正確性)、定期保證清理沒人存取的過期 key(記憶體效率)」。展現你理解兩者結合的必要性。

### 定期刪除為什麼要「隨機抽樣」而不是掃描所有 key？

**核心答案**：因為「掃描所有設了過期時間的 key」在 key 數量巨大時會非常耗時，而 Redis 是單執行緒的——定期刪除的清理工作也在主執行緒做，如果每次都掃描全部過期 key，這個掃描本身就會佔用大量 CPU、長時間阻塞主執行緒處理正常的命令(回想單執行緒下慢操作阻塞一切)。所以定期刪除採用「隨機抽樣 + 時間限制」——每次只隨機抽取一小批 key 檢查、且整個定期刪除過程有時間上限(不能佔用太久)，這樣既能逐步清理過期 key、又不會因為清理本身耗時太久而阻塞命令處理。這是「清理效果」和「不阻塞主執行緒」之間的平衡。

**詳細解析**：這個「抽樣而非全掃」的設計直接源於 Redis 的單執行緒約束。定期刪除的清理工作是在主執行緒的定時任務(serverCron)裡做的——而主執行緒還要處理客戶端命令。如果定期刪除每次都「掃描所有設了過期的 key」，假設有幾百萬個這樣的 key，掃描一遍要花很久，這段時間主執行緒被這個掃描佔用、無法處理客戶端命令，就會造成明顯的卡頓(單執行緒下慢操作阻塞一切)。所以 Redis 的定期刪除很「克制」——採用抽樣策略:每次只從過期字典裡隨機抽一小批(預設 20 個)key 檢查、刪除其中過期的;如果這批的過期比例超過一定閾值(說明過期 key 較多、值得多清)，就再抽一批繼續;但整個過程有嚴格的時間上限(預設不超過一定的毫秒數)，一旦超時就停止、留到下次再清。這樣定期刪除每次只佔用主執行緒很短的時間、清理一部分過期 key，不會長時間阻塞命令處理，而多次執行下來(每秒 10 次)也能持續地把過期 key 清理掉。這體現了「在單執行緒約束下，後台維護工作必須克制、抽樣、限時，以不阻塞主線任務為前提」的設計原則。理解這個抽樣設計的原因，展現你把過期策略和單執行緒模型串起來理解。

**面試回答方式**：講出「因為單執行緒——定期刪除在主執行緒做、掃描所有過期 key 會佔用大量 CPU 長時間阻塞命令處理」，所以用「隨機抽樣(每次抽一小批)+ 時間限制(整個過程有上限)」來平衡清理效果和不阻塞主執行緒。能連結到「單執行緒下後台維護必須克制、以不阻塞主線為前提」，展現你把過期策略和單執行緒模型串起來理解。

### 主從複製時，從節點會自己刪除過期的 key 嗎？

**核心答案**：不會。在主從複製架構中，從節點「不會自己主動刪除過期的 key」——過期 key 的刪除統一由「主節點」負責。主節點刪除一個過期 key 後，會向所有從節點發送一個 `DEL` 命令，從節點收到後才刪除對應的 key。這樣設計是為了「保證主從資料的一致性」——如果從節點各自獨立地刪除過期 key，可能因為時鐘差異、刪除時機不同，導致主從節點在某個時刻對「某個 key 是否存在」的判斷不一致。統一由主節點刪除、再同步給從節點，保證了所有節點對過期 key 的處理是一致的。(注意——這也意味著從節點上可能短暫存在「已過期但主節點還沒發 DEL」的 key，為了正確性，從節點在被查詢時，對於邏輯上已過期的 key 會返回「不存在」，即使物理上還沒刪。)

**詳細解析**：這是過期策略在主從架構下的一個重要細節，關乎資料一致性。核心規則是「過期刪除以主節點為準、從節點被動接受」。為什麼不讓從節點自己刪——如果從節點各自根據自己的時鐘判斷 key 過期並刪除，會有一致性問題:主從節點的時鐘可能有微小差異、處理過期的時機也不同，可能出現「主節點認為某 key 還沒過期(還存在)、從節點認為過期了(已刪)」的不一致，這在讀從節點時會讀到和主節點不一致的結果。所以 Redis 讓過期刪除「集中由主節點決定」——主節點透過惰性/定期刪除刪掉一個過期 key 後，顯式地發一個 DEL 命令給從節點，從節點收到才刪。這保證了「主刪從也刪、時機由主統一控制」的一致性。但有個微妙之處——在「主節點已經判定某 key 過期、但還沒來得及發 DEL 給從節點」的短暫視窗裡，從節點上這個 key 物理上還存在;為了不返回過期資料，從節點在處理讀請求時，會對「邏輯上已經過期(超過了過期時間)」的 key 返回「不存在」(較新版本的 Redis 這樣處理)，即使它物理上還沒被主節點的 DEL 刪掉，保證讀到的結果符合過期語意。理解主從下過期刪除的一致性設計，展現你考慮到了分散式架構下的資料一致性細節。

**面試回答方式**：講出「從節點不自己刪過期 key、統一由主節點刪除後發 DEL 命令給從節點、從節點被動刪除」，原因是「保證主從一致性(避免各自刪除因時鐘/時機差異導致不一致)」。能補充「主已判定過期但還沒發 DEL 的視窗裡、從節點對邏輯已過期的 key 返回不存在、保證不返回過期資料」，展現你考慮到了分散式架構下的一致性細節。
