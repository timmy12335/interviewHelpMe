# 題目

要為一個新服務規劃 Redis 的容量，你會怎麼估算？什麼時候該分片？

## 核心答案

估算分四步。**第一，估資料量**——用 `MEMORY USAGE` 量測代表性的鍵，乘以預期的鍵數；**記得加上每個鍵約 50 到 100 位元組的固定開銷**，小值場景下這可能是主要成本。**第二，加上非資料的記憶體**——複製積壓緩衝、客戶端輸出緩衝（連線數乘以緩衝上限）、以及 AOF 緩衝。**第三，留出 fork 的餘裕**——寫入密集時可能要 30% 到 50%。**第四，加上成長空間**。實務上 `maxmemory` 設在機器記憶體的 60% 到 70% 是常見的起點。

**分片的觸發訊號有三個**，任何一個成立就該考慮：**記憶體超過單機的合理上限**（通常是 32GB 到 64GB——超過之後 fork 時間、備份時間、與故障恢復時間都會變得難以接受）、**單執行緒成為 CPU 瓶頸**（一個核心跑滿，而多執行緒 IO 已經開了）、以及**單點的可用性風險無法接受**。

**注意分片解決的是「容量與吞吐」，不是「熱點」**——一個熱點 key 分片之後仍然在同一個節點上，需要另外處理（本地快取、讀寫分離、或把那個 key 拆開）。

## 詳細解析

**「單機記憶體的合理上限」不是技術限制而是運維限制**。Redis 本身可以用幾百 GB，**但那會讓 fork 耗時數秒、RDB 檔案的傳輸與載入以十分鐘計、主從全量同步變成一場災難**。**故障恢復時間（RTO）是決定這個上限的關鍵**——問「這個實例掛了，多久能恢復服務」，如果答案是二十分鐘而業務只能接受兩分鐘，那實例就太大了。**這個「用恢復時間反推單元大小」的思路適用於所有有狀態的系統**，包括資料庫的分片與檔案系統的卷大小。

**分片方式的選擇**：**Redis Cluster**（官方方案，客戶端理解拓撲、自動故障轉移、支援線上重分片，但跨槽操作受限）、**代理層**（Twemproxy、Codis，對客戶端透明但多一跳延遲且代理本身要高可用）、**客戶端分片**（應用自己算雜湊，最簡單但擴容時要自己處理資料遷移）。**新專案應該直接用 Cluster**——它是官方維護的、生態支援最好、也不需要額外的元件。

**成本的維度常被忽略**。記憶體是雲端最貴的資源之一，**一個 64GB 的 Redis 實例的年成本可能相當於一個工程師幾週的時間**。所以「能不能少存一點」是一個有真實回報的問題：**縮短鍵名、用 Hash 聚合小值、設定合理的 TTL、把冷資料移出 Redis**——這些優化的收益是持續的。**在規劃時就把成本納入，比事後被財務追問好。**

**成長曲線的估計比當前用量更重要**。一個「現在 10GB、每月成長 20%」的服務，一年後是 90GB——**規劃時應該想的是「一年後的架構」而不是「現在夠不夠」**，因為架構的改變（從單機到叢集）需要時間與風險，而那不該在容量已經吃緊時才開始。**務實的做法是設定容量的告警閾值（例如 70%），並在觸發時啟動擴容或架構調整的流程**，而不是等到滿了才反應。

## 面試回答方式

先給**四步估算**（資料量含每鍵 50 到 100 位元組固定開銷、非資料記憶體、fork 餘裕、成長空間）與實務起點（`maxmemory` 設在機器記憶體的 60% 到 70%）。給**三個分片的觸發訊號**並解釋「單機記憶體的合理上限」**不是技術限制而是運維限制**——用**故障恢復時間反推單元大小**：問「這個實例掛了多久能恢復」，答案超過業務容忍就是太大了。明確指出**分片解決容量與吞吐、不解決熱點**。加分點有三個：**分片方式的選擇**（Cluster、代理層、客戶端分片）與新專案該直接用 Cluster；**成本維度常被忽略**——記憶體是雲端最貴的資源之一，縮短鍵名、Hash 聚合、合理 TTL 的收益是持續的；以及**成長曲線比當前用量重要**——規劃時該想「一年後的架構」，並設定 70% 的告警閾值啟動流程而非等滿了才反應。

## 講稿

估算我分四步。第一估資料量，用命令量測代表性的鍵再乘以預期鍵數，記得加上每個鍵五十到一百位元組的固定開銷，小值場景下這可能是主要成本。第二加上非資料的記憶體，複製緩衝、客戶端緩衝、還有持久化緩衝。第三留出 fork 的餘裕，寫入密集時可能要三到五成。第四加上成長空間。實務上我把上限設在機器記憶體的六到七成。

分片的觸發訊號有三個。記憶體超過單機的合理上限、單執行緒成為 CPU 瓶頸、還有單點的可用性風險無法接受。

單機記憶體的合理上限我認為不是技術限制而是運維限制。Redis 本身可以用幾百 GB，但那會讓 fork 耗時數秒、備份檔案的傳輸與載入以十分鐘計。真正決定上限的是故障恢復時間。問這個實例掛了多久能恢復服務，如果答案是二十分鐘而業務只能接受兩分鐘，那實例就太大了。

要注意分片解決的是容量跟吞吐，不是熱點。一個熱點 key 分片之後仍然在同一個節點上，需要另外處理。

最後，成長曲線的估計比當前用量更重要。規劃時應該想的是一年後的架構，因為架構的改變需要時間與風險，不該在容量已經吃緊時才開始。

## 常見追問

### 怎麼估算一個新服務的 Redis 用量？

**核心答案**：**用原型量測而非公式推算**。做法是：**寫一個小腳本，用真實形態的資料寫入一千筆或一萬筆**，用 `INFO memory` 前後的差值除以筆數得到「每筆的實際成本」——**這比任何理論計算都準確**，因為它包含了編碼選擇、對齊、與固定開銷。然後乘以預期的筆數並加上前述的其他部分。

**詳細解析**：**「用真實形態的資料」是關鍵**——編碼的選擇取決於資料的形態。一個有 50 個小欄位的 Hash 會用 listpack 編碼（很省），**超過 `hash-max-listpack-entries`（預設 128）之後轉成雜湊表，記憶體可能翻好幾倍**。**所以用 10 個欄位測出來的數字，不能直接外推到 200 個欄位的情況。** 同樣地，用短字串測的結果不能外推到長字串。**測試資料應該涵蓋實際的分佈（包含極端值），而不是一個「典型」的樣本。** 這也提醒了一個更一般的問題：**容量估算的誤差往往來自「用不具代表性的樣本外推」**，而那在資料形態有階躍變化（編碼切換、資料結構升級）時特別嚴重。

**面試回答方式**：給方法——**用原型量測而非公式推算**，寫真實形態的資料一萬筆、用 `INFO memory` 的差值除以筆數。重點強調**「真實形態」是關鍵**：編碼選擇取決於資料形態，超過門檻後從緊湊編碼轉成雜湊表**記憶體可能翻好幾倍**，所以 10 個欄位測的結果不能外推到 200 個欄位。收在一般問題：**容量估算的誤差往往來自用不具代表性的樣本外推**，在資料形態有階躍變化時特別嚴重。

### 擴容的時候怎麼避免影響服務？

**核心答案**：**縱向擴容（加記憶體）** 需要重啟，做法是「在從節點上完成、再故障轉移過去」——先讓從節點用新的設定重啟並完成同步，再手動觸發切換，**主節點的角色在幾秒內轉移，客戶端重連即可**。**橫向擴容（加節點）** 在 Cluster 下是線上的槽位遷移，**不需要重啟，但要控制節奏**（分批遷移、監控兩端的延遲與記憶體）。

**詳細解析**：**兩者的共同要求是「客戶端能正確處理拓撲變化」**。故障轉移時客戶端會遇到連線斷開與 `MOVED` 重導向，**如果客戶端沒有正確實作重連與拓撲更新，切換就會表現成一段時間的錯誤**。**所以擴容之前應該先在測試環境驗證客戶端的行為**——主動觸發一次故障轉移，觀察應用的錯誤率與恢復時間。**這個「先驗證恢復行為再做變更」的做法，是所有有狀態系統維運的基本功**，卻經常被跳過（因為「應該沒問題」）。**而真正的問題往往就出在那些「應該沒問題」的假設上**——例如某個客戶端函式庫的舊版本不處理拓撲刷新，或者連線池的設定讓重連風暴壓垮了新主節點。

**面試回答方式**：分別給縱向與橫向擴容的做法（在從節點完成再切換 vs 線上槽位遷移並控制節奏）。真正的重點是**兩者的共同要求：客戶端能正確處理拓撲變化**——沒有正確實作重連與拓撲更新的話，切換會表現成一段時間的錯誤。給出建議：**擴容前先在測試環境主動觸發故障轉移，觀察錯誤率與恢復時間**。收在觀點：**先驗證恢復行為再做變更是有狀態系統維運的基本功**，而問題往往就出在「應該沒問題」的假設上。

### 什麼時候該考慮把資料移出 Redis？

**核心答案**：三個訊號。**成本不成比例**——Redis 的記憶體成本遠高於磁碟型儲存，**存放冷資料或大量歷史資料在 Redis 裡是浪費**。**存取模式不匹配**——如果資料的存取是低頻的、或者需要複雜查詢，Redis 的優勢（低延遲的鍵值存取）發揮不出來。**資料量的成長不受控**——例如日誌型的資料，它只會越來越多，而 Redis 的容量是有硬上限的。

**詳細解析**：**「冷熱分離」是最實用的處理方式**：熱資料留在 Redis、冷資料移到成本低得多的儲存（資料庫、物件儲存），**用存取時間或存取頻率決定分界**。實作上可以用 TTL 自然淘汰（冷資料自動過期，需要時從冷儲存回填），這比主動遷移簡單得多。**要注意「回填的成本」**——如果冷資料被存取的頻率不低，回填會造成可觀的延遲與下游壓力，**那表示分界線畫錯了**。**判斷分界的方式是看存取的時間分佈**：如果 95% 的存取集中在最近 7 天的資料，那就是分界；如果存取是均勻分佈的，冷熱分離的收益就有限。**「先看資料的存取分佈再決定分層」比憑感覺設一個 TTL 有效得多。**

**面試回答方式**：給三個訊號（成本不成比例、存取模式不匹配、資料量成長不受控）。重點展開**冷熱分離的實用做法**——用 TTL 自然淘汰讓冷資料過期、需要時從冷儲存回填，比主動遷移簡單。指出要注意**回填成本**，回填頻繁表示分界線畫錯了。收在判斷方法：**看存取的時間分佈**——95% 集中在最近 7 天就是分界，均勻分佈則冷熱分離收益有限，**先看分佈再決定分層比憑感覺設 TTL 有效得多**。
