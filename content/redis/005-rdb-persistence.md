# 題目

Redis 的 RDB 持久化是什麼？它怎麼工作？有什麼優缺點？

## 核心答案

RDB（Redis Database）是 Redis 的「快照」持久化方式——在某個時間點，把記憶體中的「全部資料」以壓縮的二進位格式生成一個快照檔案（dump.rdb）存到磁碟。它透過 `fork` 出一個子進程來生成快照（子進程遍歷資料寫檔案，不阻塞主進程繼續處理命令）。優點是——檔案緊湊、恢復速度快（載入快照直接還原整個資料集）、對效能影響小（fork 後由子進程做）；適合做「定期備份」和「災難恢復」。缺點是——「可能丟失資料」（兩次快照之間宕機，這段時間的資料就沒了）、且大資料集 fork 時可能有短暫卡頓（fork 本身在大記憶體時有成本）。

## 詳細解析

**RDB 是什麼**：某個時刻記憶體資料的完整快照，以二進位形式存為一個檔案。恢復時，Redis 啟動時載入這個檔案就能還原到快照時的狀態。

**觸發方式**：

- **手動**——`SAVE`（在主執行緒同步做，會阻塞，生產不用）、`BGSAVE`（fork 子進程後台做，不阻塞主執行緒，常用）。
- **自動**——透過配置 `save` 規則觸發，如 `save 900 1`（900 秒內有至少 1 個 key 變化就觸發 BGSAVE）、`save 300 10`、`save 60 10000`，多個規則滿足任一個就觸發。

**工作原理（BGSAVE 的 fork 機制）**：

1. 主進程 `fork` 出一個子進程。fork 時，子進程「共享」父進程的記憶體資料（透過作業系統的「寫時複製 Copy-On-Write」，一開始不真的複製、共享同一份實體記憶體）。
2. 子進程負責「遍歷這份資料、寫入 RDB 檔案」——這個過程慢慢做，不影響主進程繼續處理客戶端命令。
3. 主進程繼續處理命令，如果期間修改了某些資料，「寫時複製」機制會為被修改的那部分複製一份新的（子進程仍看到 fork 那一刻的舊資料——保證快照是 fork 時刻的一致快照）。
4. 子進程寫完 RDB 檔案後，用新檔案替換舊的，退出。

**優點**：

- 檔案緊湊（二進位壓縮）、體積小，適合備份和傳輸。
- 恢復快——載入 RDB 直接還原整個資料集，比 AOF 重放命令快得多。
- 對主進程效能影響小——快照生成由子進程做，主進程只在 fork 那一刻有短暫停頓。

**缺點**：

- **會丟資料**——RDB 是「定期快照」，兩次快照之間的資料在宕機時會丟失（例如設定每 5 分鐘一次快照，宕機時最多丟 5 分鐘的資料）。
- **fork 的開銷**——資料集很大時，fork 本身（複製頁表等）會有短暫卡頓，且寫時複製在寫入密集時會消耗額外記憶體。

## 面試回答方式

先講「RDB 是全量資料的二進位快照」。工作原理的核心是 fork + 寫時複製——「fork 子進程、子進程共享父進程記憶體（COW）、子進程慢慢寫快照不阻塞主進程、主進程改資料時 COW 複製、保證快照是 fork 時刻的一致快照」，能講清這個機制是這題的關鍵深度。優缺點要對比清楚——優點（緊湊、恢復快、影響小）、缺點（會丟資料、大資料 fork 卡頓）。能點出「RDB 適合備份和災難恢復、但對資料完整性要求高的場景要配合 AOF」，展現你理解 RDB 的定位和它與 AOF 的互補。

## 常見追問

### fork 的「寫時複製（Copy-On-Write）」是怎麼保證快照一致性又不阻塞主進程的？

**核心答案**：fork 時，子進程並不真的立即複製父進程的全部記憶體，而是「共享」父進程的實體記憶體頁（透過作業系統的寫時複製機制）——父子進程一開始指向同一份實體記憶體，只是這些頁被標記為「唯讀」。子進程基於這份共享的記憶體慢慢遍歷、寫 RDB 檔案。當主進程在此期間「修改」某個資料時，作業系統偵測到對唯讀頁的寫入，會「複製一份這個頁」給主進程去改（Copy-On-Write），而子進程仍然看到原來那份（未被修改的）頁。這樣——子進程始終看到的是「fork 那一刻的資料快照」（因為主進程的修改都複製到新頁去了、不影響子進程看到的舊頁），保證了快照的一致性;同時主進程可以繼續自由地讀寫（改的部分 COW 複製、不用等子進程），不被阻塞。

**詳細解析**：這是 RDB「既能生成一致快照、又不阻塞主進程」的核心機制，非常精妙。關鍵矛盾是——生成快照需要「一個穩定不變的資料視圖」（否則寫到一半資料變了、快照就不一致），但主進程又要繼續處理命令（會不斷改資料）。如果簡單地「複製整份資料給子進程」，複製本身很慢很耗記憶體（資料集幾 GB 就要複製幾 GB）。寫時複製巧妙地解決了——fork 時父子進程「共享」實體記憶體（不真的複製，所以 fork 很快、不佔雙倍記憶體），只有當某個記憶體頁「真的被修改」時才複製那一頁。因為 Redis 運行中，兩次快照間被修改的資料通常只是一小部分（大部分資料是不變的），所以實際被 COW 複製的頁很少，記憶體開銷可控。而這個機制天然保證了「子進程看到的是 fork 時刻的快照」——主進程的所有修改都發生在「複製出來的新頁」上，子進程手裡的舊頁不受影響，所以子進程遍歷寫出的快照就是 fork 那一刻的一致狀態。理解 COW 如何同時解決「一致性」和「不阻塞」，展現你對 RDB 底層機制的透徹理解，也連結到作業系統的知識。

**面試回答方式**：講出「fork 時父子進程共享實體記憶體（COW、不真的複製所以快且省記憶體）、子進程基於共享記憶體寫快照、主進程修改資料時作業系統複製那一頁給主進程改、子進程仍看到舊頁」。強調它同時解決兩個問題——「子進程看到 fork 時刻的一致快照 + 主進程不被阻塞可繼續讀寫」。能連結到作業系統的 COW，展現你對這個精妙機制的透徹理解。

### fork 在大記憶體時為什麼會卡頓？如何緩解？

**核心答案**：fork 雖然用了寫時複製、不真的複製資料，但它仍然需要「複製父進程的頁表（page table）」——頁表是記錄「虛擬記憶體到實體記憶體映射」的資料結構，資料集越大、頁表越大，複製頁表的耗時就越長，這個複製是在 fork 的瞬間同步做的，會導致主進程短暫卡頓（fork 期間主進程無法處理命令）。資料集達到幾十 GB 時，fork 可能卡頓幾百毫秒甚至更久。緩解方法——（1）控制單個 Redis 實例的記憶體大小（不要讓單實例資料集過大，用叢集分片把資料分散）；（2）降低快照頻率（減少 fork 次數，但會增加丟資料的風險，要權衡）；（3）確保伺服器有足夠記憶體（避免 COW 期間因寫入多而記憶體不足觸發 swap）；（4）用支援大頁的相關優化、或關閉透明大頁（THP，它會加重 COW 的記憶體複製開銷）。

**詳細解析**：這個 fork 卡頓是 RDB（以及 AOF 重寫，也用 fork）在大實例上的一個真實痛點。fork 的「寫時複製」省去了複製資料本身，但省不了「複製頁表」——頁表是作業系統管理記憶體映射的結構，它的大小和進程使用的記憶體量成正比（記憶體越多、需要映射的頁越多、頁表越大）。fork 時要為子進程複製一份頁表（雖然指向的實體頁是共享的），這個複製是同步的、會短暫阻塞主進程。對於幾十 GB 的大實例，頁表可能有幾百 MB，複製它可能要幾百毫秒——這幾百毫秒內 Redis 卡住不響應，對延遲敏感的服務是問題。緩解的核心思路是「別讓單實例太大」——用 Redis 叢集把資料分片到多個實例，每個實例的資料量小、fork 快。其次是「減少 fork 頻率」（少做快照）但要權衡資料安全。還有作業系統層面——關閉「透明大頁（Transparent Huge Pages, THP）」是一個常見的 Redis 部署優化：THP 會讓 COW 時複製的記憶體單位變大（從 4KB 頁變成 2MB 大頁），加重 COW 的記憶體複製開銷和延遲，Redis 官方建議關閉它。理解 fork 卡頓的原因（複製頁表）和緩解方法，展現你有 Redis 生產部署的實戰知識。

**面試回答方式**：講出「fork 雖用 COW 不複製資料、但要複製頁表、資料集越大頁表越大、複製頁表的耗時導致主進程短暫卡頓」。給出緩解方法——「控制單實例大小（用叢集分片）、降低快照頻率（權衡資料安全）、確保記憶體充足避免 swap、關閉透明大頁 THP」。能點出「關閉 THP 是常見的 Redis 部署優化」，展現你有生產部署的實戰知識。

### RDB 檔案損壞了怎麼辦？

**核心答案**：Redis 提供了工具和機制來應對——（1）用 `redis-check-rdb` 工具檢查 RDB 檔案的完整性、發現損壞；（2）如果啟用了 RDB 的校驗和（`rdbchecksum yes`，預設開啟），Redis 載入時會校驗檔案完整性，發現損壞會拒絕載入並報錯（避免載入了損壞的資料）；（3）恢復手段——如果有多個備份（RDB 應該定期備份到別處），用一個未損壞的較舊備份恢復（會丟失較新的資料）；如果同時啟用了 AOF，可以用 AOF 恢復（AOF 通常資料更完整）。所以最佳實踐是——同時啟用 RDB 和 AOF（互補）、且定期把 RDB 備份到其他機器/儲存（單機的 RDB 也可能隨機器一起丟失）。

**詳細解析**：RDB 檔案損壞可能因為——磁碟故障、寫入過程中斷電/宕機、檔案傳輸出錯等。應對的關鍵是「預防（校驗和）+ 檢測（工具）+ 恢復（備份/AOF）」。校驗和（rdbchecksum）——RDB 檔案末尾有一個 CRC64 校驗和，Redis 載入時會重新計算並比對，不一致就說明檔案損壞、拒絕載入（這比「載入了損壞的資料、資料錯亂卻不自知」好得多——寧可啟動失敗讓你發現問題）。`redis-check-rdb` 工具可以主動檢查一個 RDB 檔案是否完整。恢復依賴「有沒有好的備份或 AOF」——這也是為什麼生產環境的最佳實踐是「RDB + AOF 都開 + 定期異地備份」：RDB 和 AOF 互為備份（一個壞了用另一個）、異地備份防止單機故障（本機的持久化檔案會隨機器故障一起丟失，所以要定期把備份傳到其他機器或物件儲存）。理解 RDB 損壞的檢測和恢復，以及背後「多重備份」的最佳實踐，展現你有資料可靠性的意識和實戰經驗。

**面試回答方式**：講出「用 redis-check-rdb 檢查、校驗和（rdbchecksum）在載入時檢測損壞並拒絕載入、恢復靠備份或 AOF」。強調最佳實踐——「RDB + AOF 都開（互補）、定期異地備份（防單機故障）」。能點出「校驗和讓 Redis 寧可啟動失敗也不載入損壞資料」，展現你有資料可靠性意識和實戰經驗。
