# 題目

Redis 和 Memcached 有什麼區別？該怎麼選？

## 核心答案

Redis 和 Memcached 都是記憶體快取，但 Redis 功能豐富得多：（1）**資料類型**——Memcached 只支援簡單的 key-value（value 是字串/二進位），Redis 支援 String/Hash/List/Set/ZSet 等豐富的資料結構；（2）**持久化**——Memcached 純記憶體、不支援持久化（重啟資料全丟），Redis 支援 RDB/AOF 持久化；（3）**高可用/分散式**——Redis 有主從、哨兵、Cluster 等完整方案，Memcached 沒有原生的（要靠客戶端分片）；（4）**功能**——Redis 還有事務、Lua 腳本、發布訂閱、過期、淘汰策略等豐富功能。Memcached 的優勢是——「多執行緒」（能更好利用多核，純 key-value 讀寫的極致吞吐可能略高）、且「純快取、簡單」。選擇——絕大多數場景用 Redis（功能全、生態好）；只有「純粹的、簡單的 key-value 快取、且追求多核下的極致吞吐」才可能考慮 Memcached。

## 詳細解析

**主要區別對比**：

| 面向 | Redis | Memcached |
|------|-------|-----------|
| 資料類型 | 豐富（String/Hash/List/Set/ZSet 等） | 只有簡單 key-value |
| 持久化 | 支援（RDB/AOF） | 不支援（純記憶體） |
| 高可用 | 主從/哨兵/Cluster | 無原生方案 |
| 執行緒模型 | 命令處理單執行緒（6.0 網路 IO 多執行緒） | 多執行緒 |
| 額外功能 | 事務、Lua、發布訂閱、過期、淘汰等 | 很少 |
| 記憶體管理 | 自己的記憶體管理 | Slab 分配（減少碎片） |

**Redis 的優勢**：

- 豐富的資料類型——不只是快取字串，還能用各種資料結構做排行榜、佇列、計數器、去重等，功能遠超單純快取。
- 持久化——資料能落盤，重啟不丟（Memcached 重啟資料全沒）。
- 高可用和分散式——有完整的主從、哨兵、Cluster 方案。
- 豐富功能——事務、Lua、發布訂閱、過期淘汰等。

**Memcached 的優勢**：

- 多執行緒——能更充分利用多核 CPU，對於「純粹的 key-value 讀寫」，多執行緒的吞吐可能略高於 Redis（Redis 命令處理單執行緒）。
- 純快取、簡單——如果需求就是「一個簡單的、大容量的 key-value 快取」，Memcached 的簡單性也是一種優勢。
- Slab 記憶體分配——對於固定大小的資料，能較好地控制記憶體碎片。

**選擇建議**：絕大多數情況用 Redis——它功能全面、生態成熟、能覆蓋 Memcached 的所有場景並提供更多能力。只有在「純粹簡單的 key-value 快取、且對多核下的極致吞吐有特殊要求」的少數場景，才可能考慮 Memcached。實務中 Redis 已經是快取的主流選擇。

## 面試回答方式

用對比的方式講清主要區別——資料類型（Redis 豐富 vs Memcached 只有 key-value）、持久化（Redis 有 vs Memcached 無）、高可用（Redis 完整方案 vs Memcached 無原生）、功能（Redis 事務/Lua/發布訂閱等 vs Memcached 少）。要「平衡」——也講 Memcached 的優勢（多執行緒、純快取簡單），避免給人「Redis 全面碾壓」的偏頗印象。最後給選擇建議——「絕大多數用 Redis（功能全生態好）、純簡單 key-value 追求極致吞吐才考慮 Memcached」。這是相對基礎的比較題，能全面客觀地對比並給出務實建議即可。

## 常見追問

### Memcached 是多執行緒的，Redis 是單執行緒的，為什麼 Redis 反而更流行？

**核心答案**：因為「多執行緒」帶來的吞吐優勢，在實際的快取場景中往往不是決定性的、且被 Redis 的其他優勢遠遠彌補了。首先——Redis 單執行緒配合記憶體操作和 IO 多路復用，效能已經非常高（單機幾萬到十幾萬 QPS），對絕大多數應用綽綽有餘，「多執行緒的更高吞吐」在多數場景用不到（不是瓶頸）。其次——Redis 用「豐富的資料類型、持久化、高可用、豐富功能」提供了遠超「純 key-value 快取」的價值，這些能力在實際開發中極其有用（排行榜、分散式鎖（Distributed Lock）、佇列、計數器等），是 Memcached 完全沒有的。再者——Redis 6.0 已經把「網路 IO」多執行緒化了，在網路 IO 密集場景也能利用多核。所以權衡下來——Memcached 的「多執行緒吞吐」優勢對多數場景不關鍵、而 Redis 的功能豐富性是實實在在的巨大價值，所以 Redis 成為了主流。

**詳細解析**：這題考的是「不要被單一指標（多執行緒/吞吐）誤導、要看整體價值」。表面上「多執行緒 > 單執行緒」（能用多核、吞吐高），但這個優勢在快取場景的實際重要性沒那麼大。原因——(1)**Redis 單執行緒已經夠快**：Redis 基於記憶體 + IO 多路復用，單執行緒就能達到單機幾萬到十幾萬 QPS，對絕大多數應用來說，快取根本不是瓶頸（瓶頸通常在別處，如資料庫、業務邏輯、網路），「Redis 能不能更快」對這些應用沒意義。(2)**Memcached 的吞吐優勢場景有限**：只有在「純粹的、超高並發的 key-value 讀寫、且 Redis 的單執行緒真的成了瓶頸」的極少數場景，Memcached 的多執行緒吞吐才可能有優勢；而這種場景很少見。(3)**Redis 的功能價值遠超吞吐差異**：實際開發中，Redis 的豐富資料類型和功能（用 ZSet 做排行榜、用 List 做佇列、用 String 的 INCR 做計數器、用它做分散式鎖、發布訂閱、持久化、高可用）解決了大量的實際問題，這些是 Memcached 給不了的——開發者用 Redis 能做的事情比 Memcached 多太多，這個「能力上的巨大差異」的價值遠遠超過「純 key-value 吞吐的一點差異」。(4)**Redis 6.0 補上了 IO 多執行緒**：即使在網路 IO 密集場景，Redis 6.0 也能用多執行緒處理網路 IO 了，進一步縮小了和 Memcached 在多核利用上的差距。所以「多執行緒 vs 單執行緒」這個看似 Memcached 佔優的點，實際上對主流場景不關鍵，而 Redis 在功能、生態、可用性上的全面優勢讓它成為了絕大多數場景的首選。理解「不能只看單一指標、要看整體價值和實際需求」，展現你有成熟的技術選型判斷。

**面試回答方式**：講出「多執行緒的吞吐優勢在實際快取場景不關鍵、被 Redis 其他優勢彌補——Redis 單執行緒配合記憶體+IO多路復用已經夠快(幾萬到十幾萬 QPS、多數應用快取不是瓶頸)、Redis 的豐富資料類型和功能(排行榜/佇列/計數器/分散式鎖/持久化/高可用)是 Memcached 沒有的巨大價值、6.0 還補上了 IO 多執行緒」。提煉「不能只看單一指標(吞吐)、要看整體價值和實際需求」。展現你有成熟的技術選型判斷。

### 什麼場景下 Memcached 可能仍是更好的選擇？

**核心答案**：Memcached 在少數特定場景下可能仍有優勢——(1)**純粹、簡單的大容量 key-value 快取**：如果需求就是「一個簡單的、只存字串、不需要任何複雜資料結構和功能的快取」（如純粹快取一些序列化的物件或頁面片段），Memcached 的簡單性和「多執行緒下純 key-value 的高吞吐」可能適合；(2)**多核下追求極致的 key-value 吞吐**：在超高並發的純快取讀寫、且單機多核資源充足、想充分利用多核的場景，Memcached 的多執行緒模型可能榨出比 Redis 更高的單機吞吐；(3)**已有的 Memcached 基礎設施**：如果一個系統已經在用 Memcached、運維成熟、且沒有需要 Redis 額外功能的需求，繼續用它也合理（沒必要為了用 Redis 而遷移）。但要強調——這些都是「特定的、較少見的」場景，絕大多數新專案會直接選 Redis（功能全、能覆蓋所有需求並提供更多）。

**詳細解析**：這題考的是「客觀地承認 Memcached 的適用場景、不盲目一邊倒」。雖然 Redis 是主流，但技術選型要客觀——Memcached 並非一無是處，在它擅長的場景仍可能是合理選擇。**純簡單 key-value 大容量快取**——Memcached 的定位就是「一個簡單、高效的分散式記憶體 key-value 快取」，它把這件事做得很專注、很好。如果你的需求恰好就是這個（不需要 Redis 的任何進階功能、就是要快取一堆字串/序列化物件、大容量、簡單），Memcached 的簡單性（少了很多 Redis 的複雜功能、運維和心智負擔更小）和純 key-value 的高效可能反而合適。**多核極致吞吐**——Memcached 的多執行緒能充分利用多核，對於「單機、超高並發、純 key-value」的場景，它的單機吞吐可能超過單執行緒命令處理的 Redis（雖然 Redis 6.0 的 IO 多執行緒縮小了差距，但命令執行還是單執行緒）。**已有基礎設施**——技術選型也要考慮現實：如果一個成熟系統已經在用 Memcached、跑得好好的、又沒有需要 Redis 功能的新需求，那「為了趕時髦而遷移到 Redis」是不必要的成本和風險（if it ain't broke, don't fix it）。但這些場景的共同點是「特定、較少見」——現實中，大部分應用或多或少會用到 Redis 的某些進階能力（哪怕只是持久化或某個資料結構），且 Redis 能覆蓋 Memcached 的所有純快取場景，所以新專案的預設選擇幾乎都是 Redis。理解「客觀承認 Memcached 的適用場景、但也認清 Redis 是主流」，展現你有不盲從、就事論事的技術選型態度。

**面試回答方式**：講出 Memcached 可能更好的場景——「純粹簡單的大容量 key-value 快取(不需 Redis 進階功能、簡單性是優勢)、多核下追求極致 key-value 吞吐(多執行緒榨多核)、已有成熟的 Memcached 基礎設施且無 Redis 功能需求(不必為遷移而遷移)」。強調「這些是特定較少見的場景、絕大多數新專案直接選 Redis(功能全、覆蓋所有需求)」。展現你有客觀、就事論事的技術選型態度。

### Redis 也能當資料庫用嗎？和傳統資料庫的區別？

**核心答案**：Redis 可以「在特定場景下」當資料庫用（作為主要的資料儲存，而非只做快取），但它和傳統資料庫（如 MySQL）的定位和能力有本質區別——(1)**Redis 是記憶體資料庫**：資料主要在記憶體（受記憶體容量限制、成本高），適合「資料量不太大、要求極高效能」的場景；傳統資料庫資料在磁碟（容量大、成本低），適合海量資料。(2)**一致性/持久化**：Redis 的持久化和主從是非同步的、最終一致、可能丟少量資料；傳統關聯式資料庫提供強一致的 ACID 事務、可靠持久化。(3)**查詢能力**：Redis 是 key-value/資料結構的、查詢方式有限（主要按 key）；關聯式資料庫有強大的 SQL、複雜查詢、多表關聯、二級索引等。所以——Redis 適合「作為高效能的、資料量可控的、對強一致要求不極致的資料儲存」（如 session、即時排行榜、計數器、某些高頻讀寫的狀態）；需要「海量資料、複雜查詢、強一致事務」的核心業務資料，還是要用傳統資料庫。實務中常「Redis + 傳統資料庫」配合——Redis 做快取和高頻資料、資料庫做持久的核心資料。

**詳細解析**：這題考的是「認清 Redis 的定位邊界——它強大但不是萬能的資料庫」。Redis 確實可以當「資料庫」用（有持久化、能作為資料的主要儲存），在一些場景這樣用很合適，但要清楚它和傳統資料庫的區別和邊界。**記憶體 vs 磁碟**——這是最根本的區別。Redis 資料主要在記憶體：優勢是快（記憶體存取），劣勢是「容量受限於記憶體、成本高」（記憶體比磁碟貴得多，存 TB 級資料在 Redis 不現實）。傳統資料庫資料在磁碟：能存海量資料、成本低，但存取比記憶體慢。所以 Redis 適合「資料量可控（能放進記憶體）、要求高效能」的資料，不適合海量資料。**一致性**——Redis 的持久化（RDB/AOF）和複製（主從）都有「可能丟少量資料」的特性（見前面的持久化和複製題），是最終一致；傳統關聯式資料庫提供強一致的 ACID 事務（真正的原子性、隔離性、持久性），對「絕對不能丟、不能錯」的資料（如帳戶餘額、訂單）更可靠。**查詢能力**——Redis 主要是「按 key 存取」（加上一些資料結構的操作），沒有 SQL 那種靈活的複雜查詢（多條件、關聯、聚合、範圍等）；關聯式資料庫的 SQL 和索引能支援各種複雜查詢。所以定位是——Redis 適合做「高效能的、資料量可控的、查詢模式簡單（按 key）的、對強一致要求不極致的」資料儲存（session、排行榜、計數器、實時狀態、佇列等），這些正是它擅長的；而「海量的、需要複雜查詢的、需要強一致的核心業務資料」（訂單、使用者、交易等）應該用傳統資料庫。實務中最常見的是「配合使用」——傳統資料庫存核心的持久資料（真相來源）、Redis 做快取（加速讀）和承載一些高頻的、適合它的資料（session、排行榜等），各自發揮所長。理解 Redis 當資料庫的適用邊界和它與傳統資料庫的配合，展現你對 Redis 定位有清醒、全面的認識。

**面試回答方式**：講出「Redis 能在特定場景當資料庫、但和傳統資料庫有本質區別——記憶體 vs 磁碟(Redis 快但容量受限成本高、適合資料量可控、傳統 DB 存海量)、一致性(Redis 最終一致可能丟少量、傳統 DB 強一致 ACID)、查詢能力(Redis 按 key、傳統 DB 有 SQL 複雜查詢)」。給出定位——「Redis 適合高效能、資料量可控、查詢簡單、強一致要求不極致的資料(session/排行榜/計數器);海量/複雜查詢/強一致的核心資料用傳統 DB;實務常配合(DB 存核心真相、Redis 做快取和高頻資料)」。展現你對 Redis 定位有清醒全面的認識。
