# 題目

Redis 的 Bitmap 適合解決什麼問題？它的記憶體使用有什麼陷阱？

## 核心答案

Bitmap **不是獨立的資料類型，它是字串上的位元操作**——`SETBIT key offset value` 把字串的第 offset 個位元設成 0 或 1。所以它繼承了字串的所有限制，包括 **512MB 的最大長度**（也就是最多約 42 億個位元）。

典型應用有四類：**簽到與活躍度**（每個使用者一個 key，每天一個位元，一年只要 46 位元組）、**使用者狀態標記**（每個功能一個 key，使用者 ID 當偏移量，`BITCOUNT` 算有多少人）、**留存分析**（用 `BITOP AND` 算「連續兩天都活躍的人數」）、以及**布隆過濾器的底層**。

**最大的陷阱是稀疏偏移量造成的記憶體浪費**。`SETBIT key 1000000000 1` 會**立刻配置 125MB**——因為字串必須是連續的，設定第十億個位元意味著前面十億個位元也要存在（即使全是 0）。**所以用稀疏的 ID（UUID 雜湊、或跳號很大的自增 ID）當偏移量是災難性的**。

**正確的用法要求偏移量是密集的小整數**，實務上常需要維護一個「業務 ID 到序號」的映射。

## 詳細解析

**`BITCOUNT` 與 `BITOP` 是它真正的價值所在**。單純存位元不稀奇，**能對整個位圖做高效的統計與集合運算才是關鍵**——`BITCOUNT` 用查表法（一次處理一個位元組或字組）算出 1 的個數，`BITOP AND/OR/XOR/NOT` 對多個位圖做位元運算。**「連續七天都簽到的使用者數」用七個 `BITOP AND` 加一次 `BITCOUNT` 就能算出**，而用資料庫要做七次 join 或一個複雜的聚合查詢。

**但這些操作的成本與位圖長度成正比**。一個 125MB 的位圖，`BITCOUNT` 要掃過 125MB 的記憶體——**在單執行緒上執行，這是幾十毫秒的阻塞**，會影響所有其他請求。**`BITCOUNT` 支援指定範圍**（`BITCOUNT key start end`），應該盡量用它限制掃描範圍。`BITOP` 的成本更高（要讀多個位圖並寫出結果），**大位圖的 `BITOP` 應該視為慢命令，避免在請求路徑上執行**——通常的做法是定時任務預先算好並存起來。

**兩種常見設計的取捨要分清**。**「一個使用者一個 key、天數當偏移量」**適合查詢單一使用者的歷史（`GETBIT` 或 `BITCOUNT` 都很快、記憶體極省），但**無法高效算出「某天有多少人活躍」**（要遍歷所有使用者的 key）。**「一天一個 key、使用者 ID 當偏移量」**則相反——算某天的活躍數是一次 `BITCOUNT`，算單一使用者的歷史則要查很多個 key。**選哪個取決於主要的查詢模式**，兩種都要的話就兩種都存（空間成本不高）。

**與其他方案的比較**：**HLL** 只能算基數但空間固定且不需要密集 ID；**Set** 精確且能查詢成員但記憶體與元素數成正比；**Bitmap** 在「ID 密集」的前提下同時擁有精確、可查詢、可集合運算、且記憶體極省的優點。**所以問題往往歸結為「能不能把 ID 變成密集的小整數」**——能的話 Bitmap 通常是最好的選擇。

## 面試回答方式

先指出 **Bitmap 是字串上的位元操作**而非獨立類型，因此繼承 512MB 上限。給四類典型應用並強調**簽到場景的記憶體優勢**（一年 46 位元組）。把**最大的陷阱**講清楚：**稀疏偏移量會立刻配置巨大的記憶體**（設第十億個位元就是 125MB），因為字串必須連續——**所以用 UUID 雜湊或跳號的 ID 當偏移量是災難性的**，正確用法要求密集的小整數。加分點有三個：**`BITCOUNT` 與 `BITOP` 才是真正的價值**（七天連續簽到用七次 AND 加一次 COUNT，而資料庫要七次 join）；**這些操作的成本與位圖長度成正比且在單執行緒上執行**，大位圖的 `BITOP` 應視為慢命令、用定時任務預先算好；以及**兩種設計方向的取捨**（一使用者一 key vs 一天一 key）取決於主要查詢模式。

## 講稿

Bitmap 不是獨立的資料類型，它是字串上的位元操作。所以它繼承了字串的所有限制，包括五百一十二 MB 的最大長度。

典型應用有四類。簽到與活躍度、使用者狀態標記、留存分析、還有布隆過濾器的底層。簽到的記憶體優勢很明顯，每個使用者一個 key、每天一個位元，一年只要四十六位元組。

最大的陷阱是稀疏偏移量造成的記憶體浪費。設定第十億個位元會立刻配置一百二十五 MB，因為字串必須是連續的，前面十億個位元也要存在，即使全是零。所以用 UUID 雜湊或跳號很大的 ID 當偏移量是災難性的。正確用法要求偏移量是密集的小整數。

真正的價值在於統計與集合運算。連續七天都簽到的使用者數，用七次位元且運算加一次計數就能算出，而用資料庫要做七次 join。

但這些操作的成本跟位圖長度成正比，而且在單執行緒上執行。一個一百多 MB 的位圖做一次計數是幾十毫秒的阻塞，會影響所有其他請求。所以大位圖的位元運算應該視為慢命令，用定時任務預先算好而不是在請求路徑上執行。

## 常見追問

### 怎麼把稀疏的業務 ID 變成密集的序號？

**核心答案**：維護一個**雙向映射**——用 Redis 的 Hash 存「業務 ID 到序號」與「序號到業務 ID」，配一個 `INCR` 的計數器分配新序號。第一次見到某個業務 ID 時分配一個序號並存進映射，之後查映射即可。**分配必須是原子的**（用 Lua 腳本或 `HSETNX` 加 `INCR` 的組合），否則併發下同一個 ID 可能拿到兩個序號。

**詳細解析**：**這個映射本身的成本要納入考量**——一千萬個使用者的雙向映射，每筆存 ID 字串與整數，可能要幾百 MB，**遠大於 Bitmap 本身**。**所以只有在「Bitmap 被大量重用」時這個投資才划算**：一個映射服務幾十個不同的位圖（每天一個、每個功能一個），成本被攤薄。**如果只有一個位圖，維護映射的成本可能超過直接用 Set。** 另一個考量是**映射的持久性**——序號一旦分配就不能改變（改了所有既有的位圖都作廢），所以它必須被可靠地持久化，通常應該存在資料庫而非只在 Redis 裡。**這讓「用 Bitmap 省記憶體」變成一個需要額外基礎設施的決定**，而不是一個純粹的資料結構選擇。

**面試回答方式**：給做法（雙向映射加 `INCR` 計數器）並強調**分配必須原子**否則併發下同一 ID 拿到兩個序號。真正的加分點是成本分析：**映射本身可能比 Bitmap 大得多**，所以只有在位圖被大量重用時才划算；只有一個位圖時維護映射可能超過直接用 Set。收在關鍵約束：**序號一旦分配不能改變**（改了所有既有位圖作廢），必須可靠持久化通常要存資料庫——**這讓它變成需要額外基礎設施的決定而非純粹的資料結構選擇**。

### 大位圖的操作怎麼避免阻塞？

**核心答案**：三個方向。**限制範圍**——`BITCOUNT key start end` 只掃描指定的位元組範圍，把一次大掃描拆成多次小掃描（配合客戶端累加）。**預先計算**——定時任務在低峰時段算好結果存成一般的鍵，請求路徑只讀那個結果。**分片**——把一個大位圖拆成多個小位圖（依 ID 範圍），每個操作只碰一片，並可以並行。

**詳細解析**：**「預先計算」是最實用也最常被採用的**，因為這類統計通常不需要即時。**關鍵是設計好「什麼時候算、算完存哪裡、過期怎麼處理」**——例如每小時算一次日活並存成 `stats:dau:20240115`，設一個較長的 TTL。**這讓請求路徑的成本從「掃描 125MB」變成「讀一個整數」**。**更一般地說，這是「把昂貴的計算從讀取路徑移到寫入或背景路徑」的模式**，在很多場景都適用——物化視圖、預聚合表、以及各種快取都是同一個思路。**判斷能不能這樣做的問題是：這個結果需要多即時？** 大多數統計指標容忍分鐘級的延遲，那就有充分的空間做預計算。

**面試回答方式**：給三個方向（限制範圍、預先計算、分片）。重點展開**預先計算最實用**——這類統計通常不需要即時，把請求路徑的成本從掃描 125MB 變成讀一個整數。把它提升成一般模式：**把昂貴的計算從讀取路徑移到寫入或背景路徑**，並舉物化視圖、預聚合表、快取作為同類。收在判斷問題：**這個結果需要多即時**，大多數統計容忍分鐘級延遲就有充分空間做預計算。

### 布隆過濾器為什麼可以用 Bitmap 實作？

**核心答案**：因為布隆過濾器的本質就是**一個位圖加上 k 個雜湊函式**。加入元素時用 k 個雜湊算出 k 個位置並設為 1；查詢時檢查那 k 個位置是否**全為 1**——有任何一個是 0 就確定不存在，全為 1 則「可能存在」（其他元素的位元可能碰巧覆蓋了這些位置，這就是誤判）。**所以它需要的原語只有「設某個位元」與「讀某個位元」，Bitmap 剛好提供。**

**詳細解析**：**自己用 Bitmap 實作與用 RedisBloom 模組的差別在於工程細節**：模組會依「預期元素數」與「可接受誤判率」自動計算最佳的位圖大小與雜湊函式數（有明確的數學公式），還支援**可擴充的布隆過濾器**（元素超過預期時自動加一層）。**自己實作的話這些都要自己算與處理，而且參數選錯的後果是誤判率遠高於預期。** **另一個實務差別是原子性**——自己實作時「設 k 個位元」需要 k 次 `SETBIT`，中間如果有其他操作介入會有一致性問題（雖然布隆過濾器對此相對寬容）；用 Lua 腳本或模組則是原子的。**所以「能用現成的就用現成的」在這裡特別成立**——自己實作省下的是一個依賴，付出的是參數計算、擴充處理、與原子性這三項工程成本。

**面試回答方式**：給出本質——**位圖加 k 個雜湊函式**，並精確描述加入與查詢的邏輯與誤判的來源。真正的加分點是說明**自己實作與用模組的差別在工程細節**：模組自動計算最佳位圖大小與雜湊數、支援可擴充布隆過濾器、且操作是原子的。收在判斷：**能用現成的就用現成的**，自己實作省下一個依賴但付出參數計算、擴充處理、原子性三項成本。
