# 題目

怎麼用 Redis 實現分散式鎖？有哪些要注意的點（原子性、防死鎖、防誤刪、鎖續期）？

## 核心答案

用 Redis 實現分散式鎖，核心是用 `SET key value NX EX seconds` 這一個原子命令——`NX`（key 不存在時才設定，實現「只有一個客戶端能搶到鎖」）、`EX`（設過期時間，防止持鎖者宕機導致死鎖）、`value`（設一個唯一標識，如 UUID，用於「釋放鎖時驗證是自己的鎖才刪」，防誤刪）。釋放鎖時，要用 Lua 腳本「原子地」判斷「value 是不是自己的」再刪除（防止刪掉別人的鎖）。此外還要考慮「鎖續期」——如果業務執行時間可能超過鎖的過期時間，要有機制自動延長鎖（如 Redisson 的看門狗）。生產環境通常直接用 Redisson（封裝好了這些細節）。

## 詳細解析

**基本實現——加鎖**：

- 用 `SET lock_key unique_value NX EX 30`——這一個命令原子地完成「如果 lock_key 不存在就設定它、值為 unique_value、過期 30 秒」。
- `NX` 保證「只有一個客戶端能設定成功（搶到鎖）」，其他客戶端設定失敗（沒搶到）。
- `EX 30` 設過期時間——防止「搶到鎖的客戶端宕機、沒能釋放鎖」導致這把鎖永遠不釋放（死鎖）。
- `unique_value`（如 UUID）——標識「這把鎖是誰的」，用於釋放時驗證。

**幾個關鍵注意點**：

1. **原子性（加鎖）**——必須用 `SET ... NX EX` 一個命令完成，不能分成「先 SETNX、再 EXPIRE」兩步（兩步之間如果宕機，鎖就沒有過期時間、可能死鎖）。
2. **防死鎖**——必須設過期時間（EX），保證持鎖者掛了鎖也能自動釋放。
3. **防誤刪（釋放鎖）**——釋放鎖時不能直接 `DEL lock_key`,而要「先驗證 value 是不是自己的、是才刪」。因為可能——你的鎖過期了、別人搶到了鎖,如果你直接 DEL、就把別人的鎖刪了。所以要用 Lua 腳本「原子地」做「比對 value + 刪除」(不能分成先 GET 比對、再 DEL 兩步,中間有並發問題)。
4. **鎖續期(自動延長)**——如果業務執行時間可能超過鎖的過期時間,鎖會在業務還沒做完時就過期、被別人搶走,造成問題。需要「鎖續期」機制——在持鎖期間,後台定期檢查、如果業務還在執行就延長鎖的過期時間。Redisson 的「看門狗(watchdog)」就是做這個。

**生產環境用 Redisson**：手動實現分散式鎖要正確處理上述所有細節,容易出錯。生產環境通常直接用 Redisson——它封裝好了原子加鎖、防死鎖、防誤刪、看門狗自動續期、可重入、公平鎖等,用起來就像 `lock.lock()`/`lock.unlock()`,可靠且方便。

## 面試回答方式

先講基本實現——`SET key uniqueValue NX EX seconds` 一個原子命令。然後逐一講四個關鍵注意點,這是這題的核心——原子性(一個命令、不能分兩步)、防死鎖(設過期)、防誤刪(釋放時 Lua 腳本驗證 value 再刪)、鎖續期(看門狗)。每一點都要講清「為什麼需要」(如防誤刪是因為鎖可能過期後被別人搶走、你會刪掉別人的鎖)。最後提「生產用 Redisson(封裝好這些細節)」。能把四個注意點及各自的「為什麼」講清楚,展現你不只會寫基本的鎖、還理解各種邊界情況,這是這題深度的體現。

## 常見追問

### 為什麼釋放鎖要用 Lua 腳本？直接先 GET 比對再 DEL 不行嗎？

**核心答案**：不行,因為「先 GET 比對、再 DEL」是兩個獨立的操作、不是原子的,中間可能被打斷導致誤刪。具體場景——你 GET 到 value、比對確認是自己的鎖(此時判斷通過);但就在你「準備 DEL」之前的這個間隙,你的鎖恰好過期了、並且另一個客戶端搶到了這把鎖(設了它自己的 value);然後你才執行 DEL——就把「別人剛搶到的鎖」刪掉了(因為 DEL 不管 value、直接刪 key)。用 Lua 腳本則能「原子地」完成「比對 value + 刪除」——Lua 腳本在 Redis 裡是原子執行的(單執行緒、腳本執行期間不會插入其他命令),所以「判斷是自己的鎖」和「刪除」之間不會被打斷,不會出現「判斷通過後、刪除前鎖被別人搶走」的情況,徹底避免了誤刪。

**詳細解析**：這題深入到「防誤刪」的正確實現。防誤刪的邏輯是「只刪自己的鎖」——需要「判斷 value 是不是自己的 + 是才刪」。問題是這兩個動作如果分開做(先 GET 比對、再 DEL),就有「判斷和刪除之間的並發窗口」。詳細時序——(1)你 GET lock_key,得到 value,和你自己的 uniqueValue 比對,一致(確認是你的鎖);(2)就在你「比對通過」到「執行 DEL」之間的這個間隙,你的鎖過期了(EX 時間到);(3)另一個客戶端 B 此時 SET NX 成功、搶到了這把鎖(設了 B 的 value);(4)你才執行 DEL lock_key——把 B 剛搶到的鎖刪了!(DEL 不驗證 value,直接刪 key)。結果 B 以為自己持有鎖、實際上鎖被你誤刪了,B 的臨界區保護就失效了。根本原因是「判斷」和「刪除」不原子、中間有窗口讓鎖易主。Lua 腳本解決這個——把「比對 value + 刪除」寫成一個 Lua 腳本(`if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end`),Redis 執行 Lua 腳本是原子的(單執行緒,腳本執行期間不處理其他命令),所以「判斷是自己的鎖」和「刪除」在一個原子操作裡完成,中間不可能插入別的客戶端搶鎖,徹底杜絕了誤刪。這也呼應了 Redis 單執行緒 + Lua 原子執行的特性。理解為什麼需要 Lua 腳本(原子地判斷+刪除、避免中間鎖易主),展現你理解分散式鎖的一個關鍵細節。

**面試回答方式**：講出「不行——先 GET 比對再 DEL 是兩步、不原子」,並講清誤刪時序——「GET 比對通過後、DEL 之前的間隙、你的鎖過期了、別人搶到鎖、你的 DEL 刪掉了別人的鎖」。説明「Lua 腳本原子地做『比對 value + 刪除』(Redis 執行 Lua 是原子的、期間不插入其他命令)、杜絕中間鎖易主」。能連結到「Redis 單執行緒 + Lua 原子執行」,展現你理解這個關鍵細節。

### 什麼是鎖續期（看門狗）？為什麼需要它？

**核心答案**：鎖續期是「在持有鎖期間、自動延長鎖的過期時間」的機制。需要它是因為——鎖設了過期時間(防死鎖),但如果「業務的實際執行時間」超過了「鎖的過期時間」,鎖會在業務還沒做完時就過期、被釋放,此時別的客戶端就能搶到這把鎖,導致「兩個客戶端同時進入臨界區」(鎖失效了)。鎖續期解決這個——在持鎖期間,一個後台任務(如 Redisson 的「看門狗 watchdog」)定期(如每隔過期時間的 1/3)檢查:如果業務還在執行(鎖還被持有),就把鎖的過期時間「續」上(重新延長),這樣只要業務還沒做完、鎖就不會過期。等業務做完、正常釋放鎖時,看門狗也停止續期。這樣既防了死鎖(業務正常時看門狗續期、掛了就不再續期、鎖自然過期釋放),又避免了「業務沒做完鎖就過期」。

**詳細解析**：鎖續期解決的是「鎖過期時間」的一個兩難——過期時間設短了,怕業務沒做完鎖就過期(鎖失效、多個客戶端進臨界區);設長了,怕持鎖者真的掛了、要等很久鎖才過期(死鎖時間長)。看門狗機制優雅地化解了這個兩難——它讓過期時間「動態地跟隨業務」:設一個合理的初始過期時間(如 30 秒),然後在持鎖期間,看門狗每隔一段時間(如 10 秒,過期時間的 1/3)就檢查一次——如果持鎖的客戶端還活著、業務還在執行,就把過期時間重新設回 30 秒(續期);如此循環,只要業務還在跑、鎖就一直被續期、不會過期。而如果持鎖的客戶端「掛了」(進程崩潰、宕機),看門狗也隨之停止(看門狗是這個客戶端進程的一部分),不再續期,那麼鎖就會在最後一次續期的 30 秒後自然過期、被釋放——避免了死鎖。所以看門狗實現了「業務正常執行時鎖不會過期(續期)、持鎖者掛了鎖能自動釋放(不再續期後過期)」的理想效果,兼顧了「不誤過期」和「防死鎖」。Redisson 的看門狗是自動的——你用 Redisson 的鎖時,如果加鎖不指定過期時間,它會啟動看門狗自動續期(預設 30 秒過期、每 10 秒續一次)。理解看門狗解決的兩難和它的機制,展現你理解分散式鎖在「鎖過期時間」上的深層考量。

**面試回答方式**：講出「鎖續期是持鎖期間自動延長過期時間、解決『業務執行時間超過鎖過期時間、鎖提前過期被別人搶走』的問題」。講清看門狗機制——「後台定期檢查(如每過期時間 1/3)、業務還在就續期、業務做完停止續期、持鎖者掛了看門狗也停(不再續期、鎖自然過期防死鎖)」。能點出它「兼顧不誤過期和防死鎖、化解了過期時間設長設短的兩難、Redisson 自動做」,展現你理解這個深層考量。

### Redis 分散式鎖在主從架構下有什麼問題？

**核心答案**：在「主從 + 哨兵」的 Redis 架構下,分散式鎖有一個「主從切換導致鎖失效」的問題。場景——客戶端 A 在「主節點」上加鎖成功(鎖資料寫在主節點);但主節點是「非同步」複製給從節點的,如果「主節點在把鎖資料複製給從節點之前就宕機了」,哨兵會把一個「還沒有這把鎖資料的從節點」提升為新主節點;此時客戶端 B 來加同一把鎖,在新主節點上「加鎖成功」(因為新主上沒有這把鎖)——結果 A 和 B 同時持有了「同一把鎖」,鎖的互斥性被破壞了。根本原因是——Redis 主從複製是非同步的、不保證「加鎖成功時鎖資料已經複製到從節點」,所以主從切換時可能丟失剛加的鎖。Redlock 演算法就是為了解決這個問題而提出的(見 [[015-redlock.md]]),但 Redlock 本身也有爭議。

**詳細解析**：這是 Redis 分散式鎖在「單 Redis(主從)」架構下的一個根本性問題,揭示了「基於單個 Redis(即使有從節點)的分散式鎖不是絕對可靠的」。問題的根源是 Redis 主從複製的「非同步」特性——客戶端在主節點加鎖成功(主節點寫入了鎖),主節點會「非同步地」把這個寫入複製給從節點,但「加鎖命令返回成功」和「複製完成」之間有時間差。如果主節點在這個時間差裡宕機了(鎖還沒複製到從節點),哨兵故障轉移、把一個從節點(它上面沒有這把鎖)升為新主;此時另一個客戶端來加同一把鎖,新主上沒有這把鎖、於是加鎖成功——現在兩個客戶端都認為自己持有這把鎖,互斥失效,可能導致嚴重的並發問題(兩個客戶端同時操作臨界資源)。這個問題在「主節點宕機 + 剛加的鎖還沒複製」這個特定但可能發生的時序下觸發。Redlock 演算法是 Redis 作者提出的解決方案——不依賴單個 Redis(主從),而是用「多個獨立的 Redis 主節點(不互為主從)」,在多數(N/2+1)個節點上都加鎖成功才算加鎖成功,這樣單個節點的故障不會導致鎖失效。但 Redlock 也有爭議(見下一題和 Redlock 專題)。實務中——對於「鎖偶爾失效可以容忍(用鎖只是優化、失效了業務層還有其他保障如唯一約束)」的場景,單 Redis 鎖夠用;對於「鎖絕對不能失效」的場景,要用 Redlock 或改用更適合做分散式協調的系統(如 ZooKeeper、etcd,它們基於一致性協定、主從資料強一致)。理解這個主從架構下的鎖失效問題,展現你認識到「Redis 分散式鎖不是絕對可靠的、要根據場景權衡」。

**面試回答方式**：講出「主從架構下的鎖失效問題——主從複製是非同步的、客戶端在主節點加鎖成功後、主節點還沒複製給從節點就宕機、哨兵把沒有這把鎖的從節點升為新主、另一個客戶端在新主上加同一把鎖也成功、導致兩個客戶端同時持鎖、互斥失效」。點出「根源是主從複製非同步、Redlock 想解決這個(但有爭議)、絕對不能失效的場景可用 ZooKeeper/etcd(強一致)」。展現你認識到 Redis 鎖不是絕對可靠、要按場景權衡。
