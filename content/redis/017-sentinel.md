# 題目

Redis 的哨兵（Sentinel）是做什麼的？它怎麼實現高可用（自動故障轉移）？

## 核心答案

哨兵（Sentinel）是 Redis 的「高可用方案」——它是一組獨立運行的進程，負責「監控」Redis 主從節點的健康、在「主節點宕機時自動故障轉移」（把一個從節點提升為新的主節點，並讓其他從節點改為複製新主、通知客戶端新主的位址）。它解決的是「主從複製架構中，主節點掛了需要人工干預切換」的問題——有了哨兵，主節點故障能被自動偵測和處理，實現無人值守的高可用。哨兵本身通常部署多個（如 3 個）組成哨兵集群，用「多數決」來判斷主節點是否真的故障、以及選舉由哪個哨兵來執行故障轉移，避免單個哨兵誤判。

## 詳細解析

**哨兵的主要職責**：

1. **監控（Monitoring）**——哨兵定期向主從節點發送心跳（PING），檢查它們是否正常回應、是否存活。
2. **故障偵測**——如果主節點沒有在規定時間內回應，哨兵先標記它為「主觀下線（SDOWN，單個哨兵認為它掛了）」;然後詢問其他哨兵、如果「多數哨兵都認為主節點掛了」，就標記為「客觀下線(ODOWN，大家一致認為掛了)」——用多數決避免單個哨兵的誤判(如網路抖動)。
3. **故障轉移(Failover)**——確認主節點客觀下線後，哨兵們選舉出一個「領頭哨兵」來執行故障轉移:從所有從節點中「選出一個最合適的」提升為新主節點、讓其他從節點改為複製這個新主、並更新配置。
4. **通知(Notification)**——把新主節點的位址通知給客戶端(客戶端透過哨兵獲取當前主節點是誰)，讓客戶端連到新主。

**主觀下線 vs 客觀下線**：

- **主觀下線(SDOWN)**——「單個」哨兵發現主節點沒回應、自己認為它掛了。但單個哨兵的判斷可能不準(可能是這個哨兵和主節點之間的網路問題，主節點其實是好的)。
- **客觀下線(ODOWN)**——「多數」哨兵都認為主節點掛了(達到配置的 quorum 數量)，才確認主節點「客觀地」故障了、可以觸發故障轉移。用多數決避免誤判。

**故障轉移的過程**：

1. 確認主節點客觀下線。
2. 哨兵之間選舉一個「領頭哨兵」(用 Raft 類似的選舉)來主導這次故障轉移。
3. 領頭哨兵從從節點中「選出最佳的一個」提升為新主——選擇依據包括:從節點的優先級(可配置)、複製偏移量(選資料最新的、複製最完整的)、runid 等。
4. 對選中的從節點執行 `SLAVEOF NO ONE`(讓它成為主節點)，讓其他從節點 `SLAVEOF 新主`(改為複製新主)。
5. 更新配置、通知客戶端新主的位址。

## 面試回答方式

先講哨兵的定位——「Redis 的高可用方案、監控主從、主節點掛了自動故障轉移」，解決「主節點故障需人工切換」的問題。四個職責(監控、故障偵測、故障轉移、通知)要能講清。核心考點是「主觀下線 vs 客觀下線」——講清「單個哨兵認為掛了(主觀)vs 多數哨兵一致認為掛了(客觀)、用多數決避免誤判」。故障轉移過程講「選領頭哨兵、從從節點選最佳的(依複製偏移量選資料最新的)提升為新主」。能點出「哨兵要部署多個組成集群、多數決」以及「選新主看複製偏移量(資料最完整)」，展現你理解哨兵的高可用機制。

## 常見追問

### 故障轉移時，怎麼從多個從節點中選出哪個當新主？

**核心答案**：領頭哨兵按幾個依據「過濾 + 排序」來選出最佳的從節點當新主——(1)先「過濾掉不健康的」:排除已下線的、長時間沒回應的、或和主節點斷開太久(資料太舊)的從節點;(2)然後按優先級排序:如果配置了 `replica-priority`(從節點優先級，數字越小優先級越高)，選優先級最高的;(3)優先級相同時，選「複製偏移量最大」的——複製偏移量越大代表它從主節點複製的資料越多、資料越新越完整，選它當新主能「丟失最少的資料」;(4)如果還相同，選 runid(一個唯一標識)最小的(一個確定性的最終決勝，保證選擇是確定的)。核心原則是——「選一個健康的、且資料最完整(複製偏移量最大)的從節點」，盡量減少故障轉移導致的資料丟失。

**詳細解析**：選新主的核心目標是「選一個能繼續服務、且資料損失最小的節點」。因為主從複製是非同步的(見 [[016-master-slave-replication.md]])，主節點宕機時，各個從節點複製到的進度可能不同——有的複製得快、資料較新，有的複製得慢、資料較舊。選新主時自然要選「資料最新最完整」的那個，這樣「主節點宕機時還沒複製出去的資料損失」最小。所以選擇過程是——先過濾:把明顯不能用的排除(已下線的、失聯太久的、和主斷開時間超過閾值的『資料太舊不可信』的);再按優先級:管理員可以透過 replica-priority 人為指定「優先選誰當主」(比如某個從節點在效能更好的機器上、想優先用它)，優先級高的先選;優先級相同時看複製偏移量:這是最關鍵的資料完整性指標——複製偏移量記錄了「從節點複製到主節點資料流的哪個位置」，偏移量越大說明它複製的資料越多越新，選它當主丟失的資料最少;最後如果偏移量也相同(理論上少見)，用 runid 做一個確定性的決勝(選最小的)，保證選擇是確定的、不會有歧義。理解這個「過濾不健康的 + 選資料最完整的(複製偏移量最大)」的選主邏輯，展現你理解故障轉移如何盡量減少資料損失，也連結到主從非同步複製的知識。

**面試回答方式**：講出選主的依據——「先過濾不健康的(下線、失聯太久、和主斷開太久資料太舊)、再按優先級(replica-priority)、優先級同看複製偏移量最大的(資料最新最完整、丟失最少)、還同用 runid 最小做確定性決勝」。強調核心原則「選健康且資料最完整的、盡量減少故障轉移的資料丟失」。能連結到「因為主從非同步複製、各從節點進度不同、選偏移量最大的丟失最少」，展現你理解選主邏輯和它與非同步複製的關係。

### 哨兵為什麼要部署多個（奇數個）？

**核心答案**：部署多個哨兵是為了「避免單個哨兵誤判、且能透過多數決做可靠的決策」。單個哨兵的問題——如果只有一個哨兵，它自己和主節點之間如果有網路問題，它會誤以為主節點掛了(其實主節點好好的)、觸發不必要的故障轉移;而且單個哨兵本身也可能掛掉(那就沒人監控了)。多個哨兵——用「多數決」判斷主節點是否真的客觀下線(要多數哨兵都認為掛了才確認)、以及選舉領頭哨兵執行故障轉移，避免單個哨兵的誤判或故障。部署「奇數個」(如 3、5 個)——是為了「多數決」能明確(奇數個容易形成明確的多數、不會平票)，且在容忍一定數量哨兵故障的前提下用最少的節點(如 3 個哨兵能容忍 1 個故障、仍有 2 個構成多數)。

**詳細解析**：這題考的是分散式系統中「多數決/法定人數(quorum)」的思想在哨兵上的應用。單哨兵的兩個致命問題——**誤判**:哨兵判斷主節點死活是靠「能不能 PING 通」，但「PING 不通」可能是「主節點真掛了」、也可能是「哨兵到主節點的網路斷了(主節點其實活著)」;單個哨兵無法區分這兩種，可能因為自己的網路問題誤判主節點掛了、觸發不必要的、甚至有害的故障轉移(把好好的主節點換掉、造成混亂)。**單點故障**:只有一個哨兵，這個哨兵自己掛了，就沒有高可用保障了。多哨兵 + 多數決解決這些——判斷主節點客觀下線要「多數哨兵都認為它掛了」，單個哨兵的誤判(它自己網路問題)不會被其他哨兵認同、不會達到多數、不會觸發故障轉移，避免了誤判;多個哨兵也不怕個別哨兵掛掉(還有其他的)。為什麼奇數個——「多數決」需要「超過半數」，奇數個(如 3)的「多數」是明確的(3 個裡的 2 個)，不會出現「剛好一半對一半」的平票僵局;而且從「容錯能力」看,3 個哨兵能容忍 1 個故障(剩 2 個仍是多數)、5 個能容忍 2 個故障，奇數個在「容忍 N 個故障」時比「偶數個」更划算(4 個哨兵也只能容忍 1 個故障——要 3 個構成多數，和 3 個哨兵的容錯力一樣、卻多用了一個節點)。這個「奇數個 + 多數決」的模式在很多分散式系統(ZooKeeper、etcd 的節點數)中都是一樣的。理解為什麼多個且奇數個哨兵，展現你理解分散式系統的多數決/容錯思想。

**面試回答方式**：講出「多個哨兵——避免單哨兵誤判(單哨兵和主節點的網路問題會誤判主掛了)、避免單點故障(哨兵自己掛了)、用多數決做可靠決策(多數哨兵認為掛了才確認客觀下線)」。講「奇數個——多數決明確(不平票)、容錯划算(3 個容忍 1 個、和 4 個一樣但省節點)」。能點出「這和 ZooKeeper/etcd 的奇數節點多數決是同一個思想」，展現你理解分散式系統的多數決容錯思想。

### 哨兵模式有什麼局限？和 Redis Cluster 的區別是什麼？

**核心答案**：哨兵模式的主要局限是——它只解決了「高可用(主節點故障自動轉移)」，但沒有解決「資料分片(水平擴展（Horizontal Scaling）)」的問題。哨兵架構下，所有資料還是存在「一個主節點」上(從節點只是副本、用於讀和備份)，所以「單個主節點的記憶體和寫入能力」就是整個系統的上限——資料量或寫入量超過單機能力時，哨兵模式無法擴展(不能把資料分散到多個主節點)。Redis Cluster(叢集)則同時解決了「高可用」和「資料分片」——它把資料「分片」到多個主節點(每個主節點只存一部分資料、各自有從節點做高可用)，既能水平擴展(加主節點分攤資料和寫入)、又有高可用(每個分片的主掛了、它的從頂上)。所以——資料量/寫入量不大、只需要高可用，用哨兵(簡單);資料量大、需要水平擴展，用 Cluster(見 [[018-redis-cluster.md]])。

**詳細解析**：這題釐清了 Redis 三種架構的定位——單機、主從+哨兵、叢集，解決的問題層層遞進。**單機**——最簡單，但沒有高可用(掛了就沒了)、也不能擴展。**主從 + 哨兵**——在單機基礎上加了「高可用」:主節點掛了哨兵自動把從節點提升為新主，服務不中斷;還能讀寫分離（Read-Write Splitting）分攤讀壓力。但它的根本局限是「所有資料在一個主節點」——從節點是「完整的副本」(不是分片)，所以整個系統的資料容量和寫入吞吐受限於「單個主節點的能力」，無法透過加節點來擴展資料量或寫入量(加從節點只能分攤讀、不能分攤寫和資料儲存)。當資料量大到單機記憶體裝不下、或寫入量大到單機扛不住時，哨兵模式就無能為力了。**Redis Cluster**——在高可用之上再加了「資料分片(水平擴展)」:它把整個資料集用「雜湊槽(hash slot)」分成多份，分散到多個主節點，每個主節點只負責一部分資料、且各自有從節點做高可用。這樣——資料容量 = 多個主節點記憶體之和(可透過加主節點擴展)、寫入吞吐 = 多個主節點之和(寫入分散到不同分片)、且每個分片有高可用。所以 Cluster 同時解決了容量/吞吐擴展和高可用，是資料量大時的方案。選擇——如果資料量和寫入量單機夠用、只需要「別掛」，用主從+哨兵(架構簡單、運維容易);如果資料量或寫入量超過單機、需要水平擴展，用 Cluster(架構複雜些、但能擴展)。理解三種架構的層次和哨兵的局限，展現你對 Redis 高可用/擴展方案有全局的認識。

**面試回答方式**：講出「哨兵的局限——只解決高可用、沒解決資料分片:所有資料在一個主節點、從節點是完整副本(不是分片)、系統容量和寫入受限於單個主節點、無法水平擴展」。對比「Redis Cluster 同時解決高可用和分片——資料用雜湊槽分到多個主節點、可加主節點擴展容量和寫入、每個分片有從節點高可用」。給出選擇——「單機夠用只需高可用用哨兵(簡單)、資料量大需擴展用 Cluster」。展現你對 Redis 高可用/擴展方案的全局認識。
