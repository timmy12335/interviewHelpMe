# 題目

Redis Cluster 是怎麼做資料分片的？為什麼用 16384 個雜湊槽？

## 核心答案

Redis Cluster 用「雜湊槽（hash slot）」做資料分片——整個叢集有固定的 16384 個雜湊槽，每個 key 透過「CRC16(key) mod 16384」計算出它屬於哪個槽，而每個主節點負責一部分槽（如 3 個主節點各負責約 5461 個槽）。這樣資料就被分散到了多個主節點。用槽做中間層的好處是——擴容/縮容時只需「遷移部分槽」（把某些槽從一個節點移到另一個節點），而不用重新計算所有 key 的位置，遷移靈活。之所以是 16384（2^14）——是在「槽數要足夠多以便均勻分片」和「節點間交換槽資訊的訊息大小要可控」之間的權衡（16384 個槽的位圖只要 2KB，節點間心跳交換這個資訊開銷小）。

## 詳細解析

**為什麼要分片**：主從+哨兵的所有資料在一個主節點,受限於單機容量和寫入能力。Cluster 透過分片把資料分散到多個主節點,實現水平擴展(容量和寫入吞吐 = 多個主節點之和)。

**雜湊槽分片機制**：

- 整個叢集固定有 16384 個槽(slot)。
- 每個 key 透過 `CRC16(key) mod 16384` 算出它屬於哪個槽(0~16383)。
- 每個主節點「負責一部分槽」——如 3 個主節點,可以是節點 A 負責 0~5460、節點 B 負責 5461~10922、節點 C 負責 10923~16383。
- 一個 key 存在「它所屬的槽所在的那個節點」上。

**為什麼用「槽」這個中間層(而非直接 key mod 節點數)**：

- 如果直接用「hash(key) mod 節點數」來分片,那麼「增減節點」時,節點數變了、幾乎所有 key 的歸屬都會變,要大規模遷移資料(災難)。
- 用「槽」做中間層——key 先固定映射到槽(這個映射不變)、槽再分配給節點。擴容時只需「把部分槽(連同其資料)從舊節點遷移到新節點」、調整「槽→節點」的分配,大部分槽的歸屬不變、遷移量可控。這是一種「一致性雜湊」思想的變體(用固定的槽做中間層解耦 key 和節點)。

**為什麼是 16384 個槽**：

- 槽數要「足夠多」——才能在多個節點間均勻分配(如果槽太少,節點多時就分不均)。
- 槽數又不能「太多」——因為 Cluster 的節點之間要透過心跳互相交換「每個節點負責哪些槽」的資訊(用一個位圖 bitmap 表示),槽越多這個位圖越大、心跳訊息越大、網路開銷越大。16384 個槽的位圖是 16384/8 = 2048 位元組(2KB),大小可控。
- 16384 = 2^14,是「均勻性」和「訊息大小」權衡的結果(作者 antirez 解釋過:16384 個槽對於他預期的叢集規模(不超過 1000 個節點)已經足夠均勻,且 2KB 的位圖大小合理)。

**客戶端怎麼找到 key 在哪個節點**：客戶端快取「槽→節點」的映射;訪問一個 key 時算出它的槽、直接連到負責這個槽的節點。如果連錯了節點(如映射過時),節點會返回「MOVED」重定向、告訴客戶端正確的節點,客戶端更新映射並重連。

## 面試回答方式

先講「為什麼分片」(突破單機容量/寫入限制、水平擴展)。核心是「雜湊槽機制」——16384 個槽、`CRC16(key) mod 16384` 定槽、每個主節點負責一部分槽。務必講清「為什麼用槽這個中間層」——「直接 key mod 節點數的話增減節點要遷移幾乎所有 key、用槽解耦後擴容只需遷移部分槽」,這是分片設計的精髓。「為什麼 16384」講「均勻性(要夠多)和心跳訊息大小(位圖 2KB、不能太多)的權衡」。能提到「MOVED 重定向」(客戶端連錯節點時的糾正機制)是加分。展現你理解分片的核心設計思想。

## 常見追問

### Redis Cluster 中，涉及多個 key 的操作（如 MSET、事務）有什麼限制？

**核心答案**：限制是——涉及多個 key 的操作,要求「這些 key 都在同一個槽(slot)」,否則會報錯(`CROSSSLOT` 錯誤)。因為不同的槽可能在不同的節點上,而 Redis 的多 key 操作(MSET、MGET、事務 MULTI/EXEC、Lua 腳本等)是在「單個節點」上執行的、無法跨節點,所以如果多個 key 分散在不同節點(不同槽),這些操作就無法完成。解決辦法——用「hash tag」:在 key 裡用大括號 `{}` 標記一部分作為「計算槽的依據」,如 `user:{1001}:name` 和 `user:{1001}:age`,Redis 只用 `{}` 裡的 `1001` 來算槽,所以這兩個 key 一定在同一個槽(同一節點),就能一起做多 key 操作了。所以在 Cluster 中,如果一組 key 需要一起操作(如同一個使用者的多個屬性、需要事務保證),要用 hash tag 把它們固定到同一個槽。

**詳細解析**：這是 Redis Cluster 一個重要的實際限制,源於「分片」和「多 key 原子操作」的矛盾。分片把資料分散到多個節點,但 Redis 的多 key 操作(MSET 一次設多個、事務要原子地操作多個、Lua 腳本操作多個 key)本質上是「在一個節點上原子執行」的——它無法跨節點做(跨節點就涉及分散式事務,Redis Cluster 不支援)。所以當你想 `MSET k1 v1 k2 v2`,如果 k1 和 k2 算出來屬於不同的槽、在不同節點,Redis 就沒法在一個節點上完成這個操作,直接報 CROSSSLOT 錯誤。hash tag 是解決這個的機制——它讓你「控制 key 的槽計算」:正常 key 用整個 key 算槽,但如果 key 裡包含 `{...}`,Redis 就「只用大括號裡的內容算槽」。所以 `order:{1001}:info`、`order:{1001}:items`、`order:{1001}:status` 這幾個 key,因為 `{}` 裡都是 `1001`,算出的槽相同、一定在同一節點,就能對它們做 MSET、事務、Lua 等多 key 操作。實務中——如果一組 key 有「需要一起原子操作」的關係(如一個訂單的多個相關 key、需要在事務裡一起改),設計 key 時就要用 hash tag 把它們綁到同一個槽。但也要注意——過度使用 hash tag 把大量 key 綁到同一個槽,會導致「資料分佈不均」(那個槽所在的節點資料特別多、成為熱點),要平衡。理解這個限制和 hash tag 解法,展現你了解 Cluster 的實際使用細節。

**面試回答方式**：講出「多 key 操作要求 key 都在同一個槽、否則 CROSSSLOT 錯誤——因為多 key 操作在單節點執行、無法跨節點、而不同槽可能在不同節點」。給出解法「hash tag——key 裡用 {} 標記算槽的依據(如 user:{1001}:name)、讓相關 key 固定到同一個槽、就能一起操作」。能點出「過度用 hash tag 會導致資料分佈不均、要平衡」,展現你了解 Cluster 使用的實際細節。

### MOVED 和 ASK 重定向有什麼區別？

**核心答案**：兩者都是 Cluster 中「客戶端連錯節點時,節點返回的重定向」,但語意不同——**MOVED** 表示「這個槽已經『永久地』屬於另一個節點了」:客戶端訪問一個 key、連到節點 A,但這個 key 的槽已經分配給節點 B(可能客戶端快取的槽映射過時了),A 返回 `MOVED 槽號 B的位址`,客戶端應該「更新自己的槽映射、之後訪問這個槽都直接連 B」。**ASK** 表示「這個槽『正在遷移中』、這個 key 可能已經移到目標節點了、但只是這一次去問問」:在槽遷移的過程中(槽從 A 遷到 B、遷了一部分),客戶端訪問 A、A 發現這個 key 已經遷到 B 了,返回 `ASK B的位址`,客戶端「這一次去 B 查詢(且要先發 ASKING 命令)、但不更新槽映射」(因為遷移還沒完成、這個槽暫時還算 A 的)。簡言之——MOVED 是「永久搬家、更新映射」、ASK 是「臨時的、遷移中的一次性重定向、不更新映射」。

**詳細解析**：這兩個重定向對應「槽的兩種狀態」——已經穩定分配、和正在遷移中。**MOVED(穩定狀態的重定向)**——當槽的分配是穩定的(某個槽明確屬於節點 B),但客戶端快取的「槽→節點」映射過時了(還以為這個槽在 A)、連到了 A,A 就返回 MOVED 告訴客戶端「這個槽是 B 的、以後直接找 B」,客戶端收到 MOVED 會「更新它的槽映射快取」,之後對這個槽的訪問都直接連 B、不會再連錯。這是「客戶端的映射需要修正」的情況。**ASK(遷移中的重定向)**——當一個槽「正在從 A 遷移到 B」的過程中(擴容或重新平衡時,槽的資料在一點點從 A 搬到 B),這個槽的狀態是「不確定」的:有些 key 還在 A、有些已經搬到 B 了。此時客戶端連到 A 訪問一個 key,如果這個 key 已經被搬到 B 了,A 返回 ASK——意思是「這個 key 暫時去 B 找一下(這一次)、但別更新你的映射(因為遷移還沒完成、這個槽官方上還是 A 的,等遷移完成 A 會發 MOVED 正式移交)」。所以客戶端收到 ASK 是「臨時去目標節點問一次(要先發 ASKING 命令表示我是被 ASK 來的)、不改變自己對槽歸屬的認知」。這個區分保證了「遷移過程中客戶端也能正確找到 key(不管它搬了沒)」、且「不會在遷移未完成時就錯誤地更新映射」。理解 MOVED(永久、更新映射)和 ASK(遷移中、臨時、不更新映射)的區別,展現你理解 Cluster 在擴縮容遷移時如何保證客戶端正確訪問。

**面試回答方式**：講出「MOVED——槽已永久屬於另一個節點、客戶端更新槽映射、以後直接連新節點;ASK——槽正在遷移中、這個 key 已搬到目標節點、客戶端這一次去目標節點查(先發 ASKING)、但不更新映射(遷移未完成)」。概括「MOVED 是永久搬家更新映射、ASK 是遷移中的臨時一次性重定向不更新映射」。能點出「這保證了遷移過程中客戶端也能正確找到 key」,展現你理解 Cluster 擴縮容遷移的機制。

### Redis Cluster 保證強一致性嗎？

**核心答案**：不保證強一致性,Redis Cluster 提供的是「最終一致性」(和主從複製一樣是非同步的)。原因和主從複製一樣——每個分片的主從之間是「非同步複製」的:主節點寫成功後立即返回、非同步複製給從節點,所以「主節點寫成功後、還沒複製給從節點就宕機」時,故障轉移到從節點會丟失這部分資料。此外 Cluster 在「網路分區」時也可能有一致性問題(如少數派的主節點在分區期間仍接受寫入、分區恢復後這些寫入可能丟失)。所以 Redis Cluster 是為「高效能、可用性、可擴展性」設計的,一致性上是「最終一致、可能丟少量資料」,不適合對強一致有絕對要求的場景(那種場景要用基於一致性協定的系統如 etcd、或在應用層加保障)。

**詳細解析**：這題把 Redis 的一致性本質(非同步複製→最終一致)延伸到了 Cluster。Cluster 本質是「多個『主從分片』的組合」——每個分片就是一個主從結構,所以它繼承了主從複製的所有一致性特性:非同步複製、可能丟資料、主從短暫不一致(見 [[016-master-slave-replication.md]])。具體的一致性風險——(1)故障轉移丟資料:某個分片的主節點寫成功後、還沒複製給它的從節點就宕機,故障轉移把從節點升為新主,那個沒複製出去的寫入就丟了(和單個主從一樣);(2)網路分區問題:如果發生網路分區,把叢集分成了「多數派」和「少數派」,少數派裡的主節點在分區期間如果仍接受寫入(在 `cluster-node-timeout` 之內),這些寫入在分區恢復、少數派主節點發現自己已被多數派故障轉移替換後,會被丟棄。所以 Redis Cluster 明確地選擇了「AP」傾向(在 CAP 中偏向可用性和分區容忍、犧牲強一致)——它優先保證「高可用和可擴展」,一致性上只做到「最終一致、極端情況可能丟少量資料」。這是 Redis 作為「高效能快取/資料結構服務」的定位決定的——它不是設計來做「需要強一致的關鍵資料儲存」(如訂單、帳戶的最終真相)的,那些應該放在支援強一致的資料庫或協調系統裡。理解 Cluster 不保證強一致、及其原因(繼承了非同步複製、AP 傾向),展現你對 Redis 一致性定位的清醒認識,也連結到 CAP 理論(系統設計題會深入)。

**面試回答方式**：講出「不保證強一致、是最終一致——因為每個分片的主從是非同步複製(繼承主從複製的特性)、故障轉移時主節點沒複製出去的寫入會丟、網路分區時少數派主節點的寫入可能被丟棄」。點出「Cluster 是 AP 傾向、優先高可用和可擴展、犧牲強一致、不適合對強一致絕對要求的場景(那用 etcd 或應用層保障)」。能連結到「這是 Redis 高效能定位決定的、CAP 中偏 AP」,展現你對 Redis 一致性定位的清醒認識。
