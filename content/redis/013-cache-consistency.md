# 題目

快取和資料庫的資料一致性怎麼保證？更新資料時，是先更新資料庫還是先更新快取？先刪快取還是先更新資料庫？

## 核心答案

快取與資料庫一致性是一個「無法做到強一致、只能盡量減少不一致視窗」的問題（因為更新快取和更新資料庫是兩個操作、無法原子）。最推薦的方案是「Cache-Aside（旁路快取）+ 先更新資料庫、再刪除快取」——讀時：先讀快取、miss 就讀 DB 並寫入快取；寫時：先更新資料庫、再刪除快取（而不是更新快取）。之所以「刪快取」而非「更新快取」——刪除更簡單、且避免了並發更新快取導致的髒資料；之所以「先更 DB 再刪快取」——相比「先刪快取再更 DB」，它在並發下產生不一致的機率更低。即便如此仍有極小的不一致視窗，可用「延遲雙刪」等手段進一步降低。

## 詳細解析

**為什麼無法強一致**：更新資料庫和操作快取是「兩個獨立的操作」，中間可能被打斷、可能有並發、可能一個成功一個失敗，無法保證兩者原子地同時生效。所以快取一致性只能「盡量減少不一致的時間視窗和機率」，而非追求強一致。

**Cache-Aside（旁路快取）模式（最常用）**：

- **讀**：先讀快取 → 命中就返回 → 未命中就讀資料庫 → 把結果寫入快取 → 返回。
- **寫**：先更新資料庫 → 再刪除快取（讓下次讀時 miss、從 DB 讀最新的重建快取）。

**為什麼寫時「刪快取」而非「更新快取」**：

1. **更簡單、避免無效計算**——如果每次寫都更新快取，但這個資料之後不一定會被讀，就白白算了；刪除則是「惰性」的，下次真被讀時才重建。
2. **避免並發更新快取的髒資料**——如果兩個並發的寫都去「更新快取」，可能因為執行順序問題導致快取裡是舊值（如寫 A 先更 DB、寫 B 後更 DB，但更快取時 B 先更、A 後更，快取就成了 A 的舊值）。刪除就沒這個問題。

**為什麼「先更 DB 再刪快取」而非「先刪快取再更 DB」**：

- 「先刪快取再更 DB」的問題——刪快取後、更 DB 前的這個間隙，如果有一個「讀請求」進來，它會 miss、去讀 DB（讀到的是「還沒更新的舊值」）、然後把這個舊值寫入快取；之後更 DB 完成，但快取裡已經是剛才寫入的舊值了，造成不一致（且這個不一致會持續到快取過期或下次更新）。
- 「先更 DB 再刪快取」——相對更安全。它也有理論上的不一致場景（見追問），但發生機率遠低於前者。

**延遲雙刪**：為了進一步降低不一致，可以在「更新 DB + 刪快取」之後，「延遲一小段時間、再刪一次快取」——目的是刪掉「在這段時間內可能被其他讀請求寫入的舊值」。

## 面試回答方式

先講清楚「無法強一致、只能減少不一致視窗」這個前提——這是理解整題的基礎，避免給人「快取能做到強一致」的錯誤印象。然後推薦「Cache-Aside + 先更 DB 再刪快取」這個主流方案。核心要能回答兩個「為什麼」——為什麼「刪」而非「更新」快取（簡單、避免並發髒資料）、為什麼「先更 DB 再刪」而非「先刪再更 DB」（後者的讀請求會把舊值寫回快取）。能講出「先刪再更 DB」的具體不一致場景，展現你真正理解而非背結論。延遲雙刪作為進階補充。

## 常見追問

### 「先更新資料庫、再刪除快取」就完全一致了嗎？有沒有不一致的場景？

**核心答案**：不是完全一致，仍有一個理論上的不一致場景，但機率極低。場景是——假設快取剛好失效（miss），一個「讀請求」進來讀 DB（讀到舊值 V1），正準備把 V1 寫入快取；就在這個「讀到 V1、還沒寫入快取」的間隙，一個「寫請求」進來，更新 DB 為新值 V2、並刪除快取（但此時快取本來就是空的，刪了也沒用）；然後那個讀請求才把它之前讀到的舊值 V1 寫入快取。結果——DB 是 V2、快取是 V1，不一致，且會持續到快取過期。這個場景要求「讀請求讀 DB 和寫入快取之間，恰好插入了一個完整的寫請求」，而通常「寫 DB + 刪快取」比「讀 DB + 寫快取」慢（寫操作更重），所以這個時序很難湊齊、機率極低。可以用「快取設過期時間」和「延遲雙刪」來兜底這種極小機率的不一致。

**詳細解析**：這題考的是「能不能看穿『先更 DB 再刪快取』也不是完美的」——它比「先刪再更 DB」好很多，但不是絕對一致。詳細分析這個罕見的不一致時序：前提是快取此刻是 miss 的（空的）。時間線——(1)讀請求 R 進來,快取 miss,去讀 DB,讀到當前值 V1;(2)就在 R「讀到 V1」之後、「把 V1 寫入快取」之前的這個極短間隙裡,寫請求 W 進來了;(3)W 更新 DB 為 V2、然後刪除快取(但快取現在是空的,刪除無效果);(4)現在 R 才繼續執行,把它之前讀到的 V1 寫入快取。最終——DB=V2(最新)、快取=V1(舊),不一致,且持續到快取過期或下次更新。這個場景成立的苛刻條件是——「一個讀請求讀完 DB 但還沒寫快取的極短間隙裡,恰好完整地插入了一個寫請求(更 DB + 刪快取)」。而現實中,「讀 DB 然後寫快取」這一串通常很快(尤其寫快取),而「寫 DB 然後刪快取」相對慢(寫 DB 是重操作),所以「寫請求的完整流程」要恰好卡在「讀請求讀完 DB 到寫快取的那個微小間隙」裡,時序上非常難湊齊,機率極低。所以「先更 DB 再刪快取」在實務中被認為是「足夠好」的方案(不一致機率極低),配合快取過期時間(即使不一致也最多持續到過期)和延遲雙刪(主動再刪一次兜底),能把不一致控制在可接受範圍。理解這個罕見場景,展現你對快取一致性的理解是嚴謹、不流於「背個結論」的。

**面試回答方式**：回答「不是完全一致、有一個極低機率的場景」,並講清時序——「快取 miss 時讀請求讀到舊值 V1、還沒寫快取的間隙裡、寫請求更 DB 為 V2 並刪快取(空的刪了無效)、然後讀請求才把 V1 寫入快取、導致 DB=V2 快取=V1」。強調「這要求苛刻的時序(寫請求恰好插在讀 DB 到寫快取的間隙)、而寫 DB 通常比寫快取慢、所以機率極低」,並用「快取過期 + 延遲雙刪兜底」。展現你對快取一致性理解的嚴謹。

### 延遲雙刪具體是怎麼做的？為什麼要「延遲」再刪一次？

**核心答案**：延遲雙刪是——更新資料時,「先刪一次快取、更新資料庫、然後延遲一小段時間(如幾百毫秒到幾秒)、再刪一次快取」。第一次刪是常規操作;「延遲後再刪一次」的目的是——清除掉「在第一次刪快取到延遲結束的這段時間裡,可能被其他讀請求寫入快取的舊值」。因為在你更新 DB 的過程中,可能有並發的讀請求讀到了舊值並寫入了快取(產生了髒的快取),延遲一段時間(讓這些可能的舊值寫入都完成)後再刪一次,就能把這些髒快取清掉,進一步降低不一致的機率和持續時間。「延遲」是為了「等那些可能寫入舊值的讀請求都完成後再刪」。

**詳細解析**：延遲雙刪是對「並發下讀請求可能寫入舊值到快取」這個問題的補救。核心問題還是——在你更新資料的過程中,並發的讀請求可能讀到舊值、並把舊值寫進快取,導致更新完成後快取裡卻是髒的舊值。單次刪除(不管先刪還是後刪)都無法完全避免這個(因為讀請求寫入舊值的時機可能在你刪除之後)。延遲雙刪的思路是——既然「讀請求寫入舊值」這件事可能發生在「你更新的前後一小段時間內」,那我就「等這段時間過去(延遲)、確保那些寫入舊值的操作都完成了、再刪一次快取」,把它們寫入的髒值清掉。具體時序——(1)刪快取(第一次);(2)更新 DB;(3)sleep 一小段時間(這段時間覆蓋「並發讀請求讀舊值並寫快取」可能發生的窗口);(4)再刪快取(第二次,清掉步驟 3 期間可能被寫入的舊值)。「延遲」的時長要「略大於一次讀請求(讀 DB + 寫快取)的耗時」,保證第二次刪除發生在「可能的髒寫入」之後。它的代價——延遲期間有短暫的不一致(第二次刪之前)、且延遲雙刪的第二次刪除通常「非同步做」(如丟到訊息佇列或用延遲任務,避免阻塞當前的寫請求)。延遲雙刪不能保證絕對一致(如果並發讀請求的舊值寫入發生在第二次刪之後,還是會有髒快取),但它進一步降低了不一致的機率和持續時間,是常用的加強手段。理解延遲雙刪的目的(清掉並發讀寫入的舊值)和「延遲」的原因(等舊值寫入完成),展現你理解這個進階手段的機制。

**面試回答方式**：講出做法——「刪快取、更新 DB、延遲一小段時間、再刪一次快取」,目的是「清掉在更新過程中並發讀請求可能寫入快取的舊值」。解釋「延遲」的原因——「等那些可能寫入舊值的讀請求都完成後再刪、才能清乾淨」,延遲時長「略大於一次讀請求耗時」。能點出「第二次刪常非同步做(避免阻塞寫請求)、且仍不能保證絕對一致、只是進一步降低不一致機率」,展現你理解這個進階手段的機制和局限。

### 如果要求更強的一致性，有什麼方案？

**核心答案**：如果 Cache-Aside 的「最終一致(有極小不一致視窗)」還不夠、要求更強的一致性,可以考慮——(1)**訂閱資料庫的 binlog**(如用 Canal 監聽 MySQL 的 binlog):資料庫一有變更,binlog 就記錄,一個訂閱服務讀取 binlog、據此去刪除/更新快取,這樣「快取的失效由 DB 的實際變更驅動」,更可靠(不依賴應用程式碼記得刪快取)、且能處理應用直接改 DB 繞過快取的情況;(2)**加分散式鎖**:更新時鎖住這個 key,序列化對它的讀寫,避免並發導致的不一致(代價是效能下降);(3)**接受「讀寫都走 DB、快取只做加速且容忍不一致」**:對強一致要求極高的資料乾脆不快取、或快取設極短過期。但要清醒——這些方案要嘛增加複雜度、要嘛犧牲效能,而且快取的本質決定了「絕對強一致」和「快取的高效能」是矛盾的,大多數場景應該接受「最終一致」、選擇 Cache-Aside 這種簡單高效的方案,只有真正需要強一致的關鍵資料才用更重的手段。

**詳細解析**：這題考的是「知道有更強一致的方案、但也清醒地知道它們的代價」。**binlog 訂閱(如 Canal)**是實務中較常用的加強方案——它的思路是「讓快取失效由資料庫的真實變更來驅動,而非由應用程式碼主動刪」。Canal 偽裝成 MySQL 的從節點、訂閱主節點的 binlog,任何對 DB 的變更都會產生 binlog,Canal 讀到後通知一個服務去刪除對應的快取。這比「應用更新 DB 後主動刪快取」更可靠——因為它不依賴「每個更新 DB 的地方都記得刪快取」(容易遺漏),而是統一由 binlog 驅動(只要改了 DB 就一定會觸發快取失效),還能覆蓋「有人直接改 DB 沒走應用」的情況。但它增加了架構複雜度(要部署 Canal、訂閱服務、處理 binlog 的順序和重試)。**分散式鎖**能序列化讀寫、避免並發不一致,但序列化意味著效能大幅下降(失去了快取並發讀的優勢),只在對一致性要求極高、能接受效能損失的關鍵場景用。**不快取/極短過期**是「乾脆放棄快取的一致性問題」——對強一致要求極高的資料(如帳戶餘額)可能就不用快取、直接走 DB,或快取極短時間。關鍵的清醒認識是——「快取的高效能」和「絕對強一致」本質上矛盾(快取就是用一份可能過時的副本換效能),追求強一致就要犧牲效能或加複雜度。所以正確的態度是——大多數場景接受最終一致(Cache-Aside,簡單高效)、只對真正需要強一致的少數關鍵資料用更重的手段,而非一律追求強一致。理解這些方案及其代價、以及「強一致 vs 高效能」的本質矛盾,展現你有成熟的權衡判斷。

**面試回答方式**：講出更強一致的方案——「binlog 訂閱(Canal 監聽 DB 變更驅動快取失效、更可靠、能覆蓋繞過應用改 DB 的情況、但增加複雜度)、分散式鎖(序列化讀寫、但犧牲效能)、不快取/極短過期(放棄快取一致性問題)」。強調清醒的取捨——「快取高效能和絕對強一致本質矛盾、大多數場景該接受最終一致(Cache-Aside)、只有關鍵資料才用更重手段」。展現你既知道方案又有成熟的權衡判斷。
