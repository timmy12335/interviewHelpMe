# 題目

Redis 的資料類型底層是怎麼實現的？同一個資料類型為什麼有多種底層編碼？編碼是怎麼轉換的？

## 核心答案

Redis 的「資料類型（如 List、Hash、ZSet）」是對外的邏輯類型，每種類型底層可以由「不同的資料結構（編碼）」實現，Redis 根據資料的「規模和內容」自動選擇最合適的編碼，並在條件變化時自動轉換。這樣設計是為了「在小資料時用緊湊省記憶體的結構、大資料時用高效的結構」，兼顧記憶體和效能。例如——Hash 在元素少且值短時用 `ziplist`/`listpack`（緊湊、省記憶體），元素多或值長時轉為 `hashtable`（查詢快）；ZSet 在小時用 `ziplist`/`listpack`大時用 `skiplist`（跳躍表）+ `hashtable`。這種「一個類型多種編碼、按需自動轉換」是 Redis 高效省記憶體的關鍵設計。

## 詳細解析

**設計思想——邏輯類型與底層編碼分離**：對外的資料類型（String/List/Hash/Set/ZSet）是「使用者看到的邏輯類型」，底層用什麼資料結構實現是「內部的編碼」，兩者分離。這讓 Redis 能「根據實際資料的規模和特徵，動態選擇最優的底層結構」——小資料用省記憶體的緊湊結構、大資料用高效的複雜結構。

**各類型的底層編碼**（新版 Redis 用 listpack 取代了部分 ziplist）：

- **String**：int（整數）、embstr（短字串）、raw（長字串）——見 [[001-data-types.md]]。
- **List**：早期是 ziplist（小）/ linkedlist（大），新版統一用 `quicklist`（一個由 listpack 節點組成的雙向鏈結串列，兼顧了 ziplist 的省記憶體和鏈結串列的靈活）。
- **Hash**：`listpack`（元素少、值短時，緊湊省記憶體）/ `hashtable`（元素多或值長時，O(1) 查詢）。
- **Set**：`intset`（全是整數且數量少時，緊湊有序的整數陣列）/ `listpack`（少量非整數時）/ `hashtable`（多時）。
- **ZSet**：`listpack`（小時）/ `skiplist`（跳躍表）+ `hashtable`（大時——跳躍表保證有序和範圍查詢 O(log n)、雜湊表保證按成員查分數 O(1)）。

**編碼轉換的觸發條件**：Redis 用配置的「閾值」判斷何時轉換——例如 Hash 有兩個閾值 `hash-max-listpack-entries`（元素數量，預設 128）和 `hash-max-listpack-value`（值的長度，預設 64 位元組），一旦元素數量超過 128 或某個值長度超過 64，就從 listpack 轉為 hashtable。ZSet、Set 等也有類似的閾值配置。轉換是「單向的」——從緊湊編碼轉為複雜編碼後，一般不會轉回去（即使刪除元素降到閾值以下也不轉回）。

## 面試回答方式

先講核心設計思想——「邏輯類型和底層編碼分離、按資料規模自動選最優編碼」，這是理解這題的關鍵。然後對幾個重點類型講清楚「小資料用什麼、大資料用什麼、為什麼」——尤其 Hash（listpack vs hashtable）、ZSet（listpack vs skiplist+hashtable）、List（quicklist）。要點出「轉換由閾值觸發、且是單向的（不轉回）」。能講出「這種設計是為了兼顧小資料的記憶體和大資料的效能」，展現你理解 Redis 這個核心設計的動機，而非死背哪個類型有哪些編碼。

## 常見追問

### 為什麼小資料用 ziplist/listpack、大資料才用 hashtable/skiplist？

**核心答案**：因為兩類結構各有優劣、適合不同規模。ziplist/listpack 是「緊湊的連續記憶體結構」——把元素緊密地存在一塊連續記憶體裡，非常省記憶體（沒有指標、雜湊表的額外開銷），但查詢是「線性掃描」（O(n)），只在元素少時快。hashtable/skiplist 是「有額外結構的高效結構」——雜湊表查詢 O(1)、跳躍表範圍查詢 O(log n)，但有指標、雜湊桶等額外的記憶體開銷。所以——資料量小時，元素少、線性掃描也很快，用緊湊的 ziplist/listpack 省記憶體最划算；資料量大時，線性掃描變慢、記憶體開銷相對佔比也小了，改用 hashtable/skiplist 換取查詢效能。這是「小資料優先省記憶體、大資料優先效能」的權衡。

**詳細解析**：這個權衡的本質是「記憶體開銷 vs 查詢效能」隨資料規模的變化。ziplist/listpack 的優勢是極致省記憶體——它把多個元素連續緊湊地存放，沒有指標（不像鏈結串列每個節點要存前後指標）、沒有雜湊桶（不像雜湊表要預留一堆桶），一塊連續記憶體存所有元素，記憶體利用率極高，且連續記憶體對 CPU 快取友好。它的劣勢是查詢要線性掃描（從頭找）——但在元素只有幾十個時，線性掃描其實很快（甚至因為快取友好可能比雜湊還快），所以小資料時劣勢不明顯、優勢（省記憶體）很突出。反過來，hashtable/skiplist 有額外開銷（雜湊表的桶、跳躍表的多層指標），在元素少時這些開銷「不划算」（為了幾十個元素維護一整套雜湊表/跳躍表，記憶體浪費）；但在元素多時，線性掃描會變得很慢，這時 O(1)/O(log n) 的查詢優勢就遠超那點額外的記憶體開銷了。所以 Redis 的策略是——用閾值劃分「小」和「大」，小的時候用緊湊結構省記憶體、大的時候用高效結構保效能，動態切換取兩者之長。理解這個「隨規模變化的權衡」，展現你理解編碼選擇背後的深層原因。

**面試回答方式**：講出「ziplist/listpack 緊湊省記憶體但查詢 O(n)、hashtable/skiplist 查詢高效但有額外記憶體開銷」，並解釋「小資料時線性掃描也快、省記憶體最划算；大資料時掃描變慢、額外開銷佔比小、換效能划算」。能提煉出「小資料優先記憶體、大資料優先效能」的權衡，展現你理解編碼選擇的深層原因。

### 編碼轉換為什麼是單向的（轉為 hashtable 後不轉回 listpack）？

**核心答案**：主要是為了「避免頻繁轉換的抖動和開銷」。編碼轉換本身有成本（要重建整個資料結構、遷移所有元素）。如果轉換是雙向的——當元素數量在閾值附近反覆增減時（例如反覆增刪讓元素數在 128 上下波動），資料結構就會頻繁地在 listpack 和 hashtable 之間來回轉換，每次轉換都要重建結構、遷移資料，開銷很大且效能抖動。設計成單向（升級後不降級）就避免了這種「臨界值抖動」——一旦升級到 hashtable，就穩定用它，不會因為刪了幾個元素又轉回去。這是一種「用少量的記憶體換取穩定性」的取捨（升級後即使元素變少、繼續用 hashtable 會比 listpack 多佔點記憶體，但避免了反覆轉換的開銷和抖動）。

**詳細解析**：這個「單向轉換」的設計和前面 JVM 中「鏈結串列轉紅黑樹的閾值上下不對稱（8 轉樹、6 轉回）」有點異曲同工——都是為了避免臨界值附近的頻繁轉換抖動，但 Redis 的做法更徹底（乾脆不轉回）。考慮如果雙向轉換——一個 Hash 元素數量在 127、128 之間反覆橫跳（不斷有元素增刪），每次跨過 128 就轉 hashtable、跌回 127 就轉 listpack，這種反覆轉換每次都要「把所有元素從一種結構搬到另一種結構」，開銷巨大且效能極不穩定。Redis 選擇單向——一旦因為某次增長超過閾值升級到 hashtable，就一直用 hashtable，即使後續刪除元素讓數量降回閾值以下也不轉回 listpack。代價是——一個曾經很大、後來變小的 Hash 會繼續用 hashtable（比用 listpack 多佔一些記憶體），但這個代價通常可以接受（且這種「大了又小」的情況不算常見），換來的是「不會有反覆轉換的抖動」。理解這個「單向轉換避免抖動」的設計，展現你理解 Redis 在效能穩定性上的考量。

**面試回答方式**：講出「單向是為了避免臨界值附近反覆轉換的抖動和開銷——轉換要重建結構遷移資料、雙向會導致元素數在閾值波動時頻繁來回轉」。能類比 JVM 鏈結串列轉紅黑樹的閾值不對稱（都是避免抖動），並點出「代價是曾大後小的結構會多佔點記憶體、但換來穩定性」，展現你理解這個設計的權衡。

### listpack 相比 ziplist 有什麼改進？

**核心答案**：listpack 是 Redis 7.0 起用來取代 ziplist 的新緊湊結構，主要改進是「解決了 ziplist 的『連鎖更新（cascade update）』問題」。ziplist 中每個節點會記錄「前一個節點的長度」（用於反向遍歷），這個長度欄位的大小是可變的（前節點短用 1 位元組記、長則用 5 位元組記）——問題是，如果某個節點的長度變化導致它的長度欄位從 1 位元組變成 5 位元組，可能連帶影響後一個節點記錄的「前節點長度」也要擴容，如此連鎖下去，最壞情況一次修改引發整個 ziplist 的連鎖更新（O(n) 甚至 O(n²) 的開銷）。listpack 重新設計了節點的編碼方式，讓每個節點的長度資訊「自包含」（不依賴記錄前一個節點的長度），從根本上消除了連鎖更新的問題，讓緊湊結構的修改更穩定高效。

**詳細解析**：這是 Redis 底層結構的一個重要演進。ziplist 的「連鎖更新」是一個著名的效能隱患——它為了支援反向遍歷，每個節點存了「前一個節點的長度（prevlen）」，而這個 prevlen 欄位是變長的（前節點小於 254 位元組用 1 位元組存、否則用 5 位元組存）。問題在於——假設一連串節點的 prevlen 都是 1 位元組（前節點都很小），現在在前面插入或修改了一個節點讓它變大（超過 254 位元組），那麼緊接著的節點的 prevlen 就要從 1 位元組擴成 5 位元組，而這個節點自己變大了 4 位元組後又可能超過 254，導致再後面的節點 prevlen 也要擴容……如此連鎖，一次修改可能引發大量節點的連鎖擴容（重新分配、資料搬移），最壞是 O(n²)。雖然實際觸發連鎖更新的機率不高（要恰好一連串節點的長度都在臨界值附近），但它是一個潛在的效能不確定性。listpack 重新設計——它讓每個節點記錄「自己的長度」而非「前一個節點的長度」，並把長度資訊放在節點的合適位置使得反向遍歷仍可行，但不再有「一個節點變化連累後續節點」的連鎖依賴，徹底消除了連鎖更新。理解 listpack 對 ziplist 連鎖更新問題的解決，展現你關注 Redis 底層結構的演進和其中的效能改進。

**面試回答方式**：講出「listpack（Redis 7.0）取代 ziplist、主要解決 ziplist 的連鎖更新問題——ziplist 每個節點記錄前節點長度（變長欄位）、一個節點變大可能連鎖導致後續節點的長度欄位都要擴容（最壞 O(n²)）」。說明「listpack 讓節點記錄自己的長度而非前節點、消除了連鎖依賴」。展現你關注 Redis 底層結構的演進和效能改進。
