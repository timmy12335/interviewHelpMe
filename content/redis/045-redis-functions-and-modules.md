# 題目

Redis 7 的 Function 與 Lua 腳本差在哪？模組（RedisJSON、RediSearch）值不值得引入？

## 核心答案

**Function 是 Lua 腳本的演進版**，主要改進三點：**持久化**（隨 RDB/AOF 保存，重啟後仍在，不會有 `EVALSHA` 找不到腳本的問題）、**組織成函式庫**（一個函式庫可以有多個函式與共用的輔助程式碼，用 `FUNCTION LOAD` 註冊與 `FUNCTION LOAD REPLACE` 升級）、以及**明確的中繼資料**（註冊時宣告函式名與旗標，例如標記為唯讀讓它能在從節點執行）。

**模組則是用 C 撰寫的原生擴充**，能新增資料類型與命令。主要的官方模組有 **RedisJSON**（原生的 JSON 型別，支援路徑查詢與部分更新，避免了「取出整個 JSON、在應用層改、再寫回」的往返與競態）、**RediSearch**（二級索引與全文檢索，讓 Redis 能依欄位查詢而不只是依鍵）、**RedisBloom**（Bloom filter、Cuckoo filter、Count-Min Sketch、Top-K）、以及 **RedisTimeSeries**。

**判斷值不值得的核心問題是「這個能力有沒有更合適的專門系統」**。需要全文檢索時，Elasticsearch 的功能與生態遠勝 RediSearch；需要複雜的 JSON 查詢時，MongoDB 或 PostgreSQL 的 JSONB 更成熟。**模組的價值在於「已經有 Redis 而需求不複雜」的場景**——省下一個新系統的維運成本。

## 詳細解析

**Function 帶來的最大轉變是「腳本成為伺服器狀態」**。`EVAL` 的腳本跟著應用一起部署（每次呼叫都帶著或用 SHA 引用），**Function 則是部署到 Redis 上的東西**——這讓它更像資料庫的預存程序，也繼承了同樣的問題：**誰負責部署？升級時怎麼確保所有節點都更新？舊版本的應用呼叫新版本的函式會怎樣？** 這些問題在 `EVAL` 模式下不存在。**所以 Function 不是單純的改進，而是把一部分邏輯的生命週期從應用移到了資料庫**——這個取捨與「該不該用預存程序」是同一個爭論。

**模組的引入成本要看得完整**。除了功能本身，還有：**部署複雜度**（模組必須在伺服器端載入，這排除了很多託管服務，或者限制了你只能用支援該模組的雲端方案）、**授權**（Redis Stack 的模組採用的授權條款不是完全開源的，商業使用要確認）、**升級耦合**（模組版本與 Redis 版本要匹配）、以及**除錯難度**（模組是 C 寫的原生程式碼，出問題時能查的資源遠少於核心功能）。**這些成本在評估時常常被忽略，因為功能展示總是很吸引人。**

**RedisJSON 的價值最容易被低估也最容易被高估**。它真正解決的問題是**部分更新的原子性與網路成本**——改一個大 JSON 物件的一個欄位，用字串存的話要取出整個物件（可能幾百 KB）、在應用層改、再寫回，**中間有競態且浪費頻寬**；用 RedisJSON 則是一個 `JSON.SET key $.field value`。**如果你的 JSON 很小或很少部分更新，這個價值就不存在**——用字串加應用層的序列化完全足夠。**判斷的方式是問：我是不是經常只改物件的一小部分？**

**RediSearch 的定位是「Redis 上的二級索引」**。Redis 原生只能依鍵查詢，**RediSearch 讓你能依欄位、範圍、全文查詢**——這在「已經把資料放在 Redis 裡、偶爾需要按條件找」的場景很有用。**但它不是 Elasticsearch 的替代品**：分析能力、聚合、以及大規模的水平擴展都不在同一個層級。**用它取代「把資料同步一份到 ES」是合理的簡化；用它承擔真正的搜尋業務則是誤用。**

## 面試回答方式

先給 **Function 的三點改進**（持久化、組織成函式庫、明確中繼資料）與**最大的轉變**：腳本成為伺服器狀態、更像預存程序，因而繼承了部署、升級、版本相容的問題——**這是把邏輯的生命週期從應用移到資料庫的取捨**。接著給主要模組與各自解決的問題。給出判斷的核心問題：**這個能力有沒有更合適的專門系統**，模組的價值在於「已經有 Redis 而需求不複雜」時省下一個新系統的維運。加分點有三個：**模組的引入成本要看完整**（部署複雜度排除了很多託管服務、授權條款、版本耦合、除錯資源少）；**RedisJSON 真正解決的是部分更新的原子性與網路成本**，JSON 很小或很少部分更新時價值就不存在；以及 **RediSearch 是「Redis 上的二級索引」而非 Elasticsearch 的替代品**，用它取代「同步一份到 ES」合理，用它承擔真正的搜尋業務則是誤用。

## 講稿

Function 是 Lua 腳本的演進版，主要改進三點。持久化，隨快照保存、重啟後仍在，不會有找不到腳本的問題。組織成函式庫，可以有多個函式跟共用的輔助程式碼。還有明確的中繼資料，比如標記為唯讀讓它能在從節點執行。

但我認為最大的轉變是腳本成為了伺服器狀態。用舊方式的腳本跟著應用一起部署，Function 則是部署到 Redis 上的東西，更像資料庫的預存程序，也繼承了同樣的問題。誰負責部署？升級時怎麼確保所有節點都更新？舊版本的應用呼叫新版本會怎樣？這些在舊模式下不存在。

模組方面，主要有原生的 JSON 型別、二級索引與全文檢索、還有各種近似資料結構。

判斷值不值得引入，我的核心問題是這個能力有沒有更合適的專門系統。需要真正的全文檢索，Elasticsearch 的功能跟生態遠勝。模組的價值在於已經有 Redis 而需求不複雜的場景，省下一個新系統的維運成本。

還有一個常被忽略的成本，模組必須在伺服器端載入，這排除了很多託管服務，或是限制了你只能用支援該模組的雲端方案。

## 常見追問

### RedisJSON 相較於用字串存 JSON，具體省了什麼？

**核心答案**：三樣。**網路頻寬**——只傳輸要改的欄位而非整個物件。**原子性**——`JSON.SET key $.status "PAID"` 是一個原子操作，而「取出、改、寫回」中間有競態（兩個並行的更新會互相覆蓋）。**應用層的序列化成本**——不需要把整個物件反序列化再序列化，那在物件大時是可觀的 CPU。

**詳細解析**：**「原子性」是最實質的收益，因為它解決的是正確性而非效能**。用字串存 JSON 時，兩個並行的部分更新必然有一個會丟失——**除非用鎖或 Lua 腳本，而那又回到了複雜度**。RedisJSON 讓部分更新變成一個原子命令，**這在「多個服務更新同一個文件的不同欄位」的場景下是必要的**。**但要注意它不提供跨欄位的交易**：改兩個欄位是兩個命令，中間仍可能有其他更新介入。**所以它解決的是「單一路徑的原子更新」，不是「多路徑的一致性」**——後者仍然需要應用層的設計。**釐清一個工具解決了問題的哪一部分，比籠統地說它「更好」重要得多。**

**面試回答方式**：給三樣收益並指出**原子性是最實質的，因為它解決正確性而非效能**——用字串存時兩個並行的部分更新必然有一個丟失。加分點是精確劃出邊界：**它不提供跨欄位的交易**，改兩個欄位是兩個命令中間仍可能被介入，**所以它解決的是「單一路徑的原子更新」而非「多路徑的一致性」**。收在原則：釐清一個工具解決了問題的哪一部分，比籠統說它更好重要。

### 模組會不會影響 Redis 的穩定性？

**核心答案**：**會，而且風險是真實的**。模組是載入到 Redis 行程裡的原生程式碼（C 動態函式庫），**它與 Redis 共享同一個位址空間與同一個執行緒**——模組的 bug 可能造成**記憶體損毀、崩潰、或阻塞整個 Redis**。而且模組的命令與核心命令一樣在單執行緒上執行，**一個慢的模組命令會卡住所有請求**。

**詳細解析**：**這與「應用層的函式庫」有本質差別**：一個有 bug 的 Java 函式庫最多讓你的應用出錯，一個有 bug 的 Redis 模組會影響**所有使用這個 Redis 的服務**。**所以模組的選擇應該比一般依賴更保守**——優先用官方維護的、有廣泛生產使用的模組，並在測試環境充分驗證（包括異常輸入與大資料量）。**另一個實務建議是「模組隔離」**：如果某個模組的用途與核心的快取用途無關（例如用 RediSearch 做搜尋），**把它放在獨立的 Redis 實例上**——這樣模組的問題不會影響核心的快取服務。**「把不同信任等級或不同故障影響的東西分開部署」是一個普遍適用的原則**，而它在這裡的成本很低（多一個實例）而收益很明確。

**面試回答方式**：明確回答會，並給機制——**模組與 Redis 共享位址空間與執行緒**，bug 可能造成記憶體損毀、崩潰、或阻塞所有請求。指出與應用層函式庫的**本質差別**：一個有 bug 的模組影響所有使用這個 Redis 的服務。給選擇建議（優先官方與有廣泛生產使用的、充分測試異常輸入與大資料量）。真正的加分點是提出**模組隔離**——把用途無關的模組放在獨立實例上，並收在普遍原則：**把不同信任等級或不同故障影響的東西分開部署**。

### 什麼時候該用 Function 而不是 EVAL？

**核心答案**：**當腳本是「基礎設施的一部分」而非「應用的一部分」時**。如果腳本實作的是一個跨多個應用共用的原語（例如統一的限流器、統一的分散式鎖），**把它做成 Function 並由基礎設施團隊維護是合理的**——所有應用共用同一份正確的實作。如果腳本只服務單一應用的特定邏輯，**跟著應用部署（`EVAL`）更簡單**，版本永遠與應用匹配。

**詳細解析**：**判準其實是「這段邏輯的變更節奏與誰綁在一起」**。跟著應用變的邏輯應該跟著應用部署；獨立演進的基礎能力才適合放在伺服器端。**這與「該不該用預存程序」是同一個判斷**——而歷史上預存程序的問題正是「業務邏輯放在資料庫裡之後，它的版本管理、測試、與部署都脫離了應用的流程」。**Function 需要一套自己的部署與版本管理流程，而多數團隊沒有為此準備。** 所以務實的建議是：**除非有明確的「多應用共用」需求，否則繼續用 `EVAL`**——它的唯一缺點（`EVALSHA` 的 `NOSCRIPT`）已經被成熟的客戶端函式庫自動處理了。

**面試回答方式**：給判準——**腳本是「基礎設施的一部分」還是「應用的一部分」**，跨應用共用的原語適合 Function，單一應用的邏輯跟著應用部署更簡單。真正的加分點是把判準精確化為**「這段邏輯的變更節奏與誰綁在一起」**，並連到「該不該用預存程序」的歷史教訓——業務邏輯放進資料庫後版本管理、測試、部署都脫離了應用流程。收在務實建議：**除非有明確的多應用共用需求否則繼續用 `EVAL`**，因為它的唯一缺點已被成熟客戶端自動處理。
