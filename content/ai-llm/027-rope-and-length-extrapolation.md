# 題目

RoPE 相比絕對位置編碼好在哪？訓練時是 4K，怎麼讓它支援 128K？

## 核心答案

**RoPE（旋轉位置編碼）的核心是「把位置資訊編碼成旋轉」**：**對 query 與 key 的向量按位置施加一個旋轉**——**於是兩個 token 的注意力分數只取決於它們的相對距離，而不是絕對位置**。**這比「把位置向量加到嵌入上」自然得多**，**因為注意力本來關心的就是相對關係**。

**它的三個優點**：**相對位置天然**（不需要額外的相對位置矩陣）、**不增加參數**（純粹的數學變換）、**以及可以在推理時調整**（**這正是長度外推的基礎**）。

**外推的主流方法是「調整旋轉的頻率」**。**位置內插（PI）**——**把位置索引除以一個係數，把 128K 的位置「壓縮」進 4K 的範圍**；簡單但會損失高頻的細粒度分辨力。**NTK-aware 縮放**——**只縮放低頻維度，保留高頻的局部分辨力**，效果更好。**YaRN**——**進一步分段處理不同頻率並校正注意力的溫度**，是目前效果最好的免訓練方法之一。

**而所有這些方法都建議「用少量長樣本微調」來補足**——**純外推不微調的效果通常有明顯衰減**。

## 詳細解析

**「為什麼直接外推會壞掉」值得說清楚**：RoPE 的旋轉角度是 `位置 × 頻率`——**訓練時模型只見過位置 0 到 4096 對應的角度範圍**，**而位置 100000 產生的角度組合完全在訓練分布之外**。**模型對這些從未見過的角度沒有正確的反應**，**表現為注意力分布崩壞、輸出變成重複或亂碼**。**所以外推的本質是「把新位置映射回模型見過的角度範圍」。**

**「高頻與低頻維度的分工」是理解 NTK 方法的關鍵**。RoPE 的不同維度使用不同的旋轉頻率——**高頻維度旋轉得快，負責分辨鄰近 token 的細微位置差異**；**低頻維度旋轉得慢，負責表達長距離的粗略位置**。**位置內插對所有維度統一縮放，於是高頻維度被壓縮得無法分辨相鄰 token**——**這正是它在短距離上表現退化的原因**。**NTK-aware 只縮放低頻、保留高頻**，**於是局部的分辨力不受影響而長距離被擴展**——**這個「按頻率分別處理」的洞察是這一系列方法的核心**。

**「支援長上下文」與「用得好長上下文」是兩件事**。即使技術上能吃 128K，**模型在長輸入中的「大海撈針」能力可能很差**——**典型的現象是中段的資訊被忽略（lost in the middle）**。**所以評估長上下文能力不能只看「能不能跑」，而要用檢索類的基準測試在不同位置放置關鍵資訊並檢查召回率**。

**成本也不能忽略**：**注意力的計算是序列長度的平方**——**128K 的一次前向計算量是 4K 的一千倍**；**而 KV Cache 的記憶體也隨長度線性成長**。**所以長上下文的實際限制往往是成本而非能力。**

## 面試回答方式

先給 RoPE 的核心——**把位置編碼成旋轉，讓注意力分數只取決於相對距離**，並給三個優點。給外推的三種方法（位置內插、NTK-aware、YaRN）並指出**都建議配合少量長樣本微調**。加分點有四個：**為什麼直接外推會壞掉**——**位置乘頻率產生的角度組合完全在訓練分布之外，模型沒有正確反應**，**所以外推的本質是把新位置映射回見過的角度範圍**；**高頻與低頻維度的分工**——**高頻分辨鄰近位置、低頻表達長距離**，**位置內插統一縮放讓高頻被壓縮到無法分辨相鄰 token，而 NTK 只縮放低頻**；**「支援長上下文」與「用得好」是兩件事**——**要用在不同位置放關鍵資訊的檢索基準測試**；以及**成本**——**注意力是長度的平方，128K 的計算量是 4K 的一千倍**。

## 講稿

旋轉位置編碼的核心是把位置資訊編碼成旋轉。對查詢跟鍵的向量按位置施加一個旋轉，於是兩個詞元的注意力分數只取決於它們的相對距離。這比把位置向量加到嵌入上自然得多，因為注意力本來關心的就是相對關係。

至於外推，要先理解為什麼直接外推會壞掉。旋轉的角度是位置乘上頻率，訓練時模型只見過某個角度範圍，而位置十萬產生的角度組合完全在訓練分布之外。模型對這些沒見過的角度沒有正確反應，表現為注意力崩壞、輸出變成重複或亂碼。

所以外推的本質是把新位置映射回模型見過的角度範圍。最簡單的是位置內插，把索引除以一個係數壓縮進去。但它有一個問題，不同維度的旋轉頻率是不一樣的，高頻負責分辨鄰近詞元的細微差異，低頻負責長距離。統一縮放會讓高頻被壓縮到無法分辨相鄰詞元。所以後來的方法只縮放低頻、保留高頻。

還有一點，能吃長上下文跟用得好長上下文是兩件事，要用大海撈針類的基準去驗證。

## 常見追問

### 絕對位置編碼、相對位置編碼與 RoPE 怎麼比較？

**核心答案**：**三個維度比**。**絕對位置編碼**（正弦或可學習）——**把位置向量加到輸入嵌入上**；簡單但**外推能力差**（可學習的完全不能外推，正弦的理論上可以但實測效果有限）。**相對位置編碼**（T5 的 bias、ALiBi）——**在注意力分數上加一個依距離的偏置**；**外推好但表達能力較弱**。**RoPE**——**在 query/key 上施加旋轉**；**兼顧相對性與表達能力，且可以在推理時調整，是目前的主流**。

**詳細解析**：**ALiBi 值得單獨提，因為它的外推能力最好而做法最簡單**：**直接在注意力分數上減去一個與距離成正比的懲罰**——**距離越遠懲罰越大**。**它的外推是天然的（訓練 1K 可以推到 8K 而幾乎不退化）**，**代價是它強制了一個「越遠越不重要」的歸納偏置**——**這對多數語言任務是合理的，但對「需要精確引用遠處資訊」的任務（例如長文檔問答）反而是限制**。**這是一個很好的例子說明「歸納偏置是雙面的」**：**它讓模型在符合假設的情況下學得更好、外推更穩，卻在假設不成立時成為天花板**。**而 RoPE 之所以勝出，部分原因正是它的偏置更弱、更依賴資料本身。**

**面試回答方式**：給三種方法在「相對性、外推能力、表達能力」上的比較。核心加分點是單獨展開 **ALiBi**：**做法最簡單（注意力分數減去與距離成正比的懲罰）而外推能力最好**，**代價是強制了「越遠越不重要」的歸納偏置**——**對多數語言任務合理，但對需要精確引用遠處資訊的任務是限制**。收在一般性的洞察：**歸納偏置是雙面的**，**它在符合假設時讓模型學得更好，卻在假設不成立時成為天花板**，**而 RoPE 勝出部分正是因為它的偏置更弱**。

### 長上下文為什麼會「中間遺失」？

**核心答案**：**兩個原因疊加**。**訓練資料的分布**——**長文本中的關鍵資訊往往出現在開頭或結尾（文章結構如此），於是模型學到了對這兩處更敏感**。**注意力的稀釋**——**序列越長，softmax 之後每個位置分到的注意力越少**，**中段的資訊需要更強的信號才能勝出**。

**詳細解析**：**「這是資料與機制共同造成的」意味著它不能只靠架構解決**。改善的方向有三：**訓練層面**——**刻意構造把關鍵資訊放在中段的長樣本**，讓模型學會均勻地檢索。**推理層面**——**把重要的內容放在提示的開頭或結尾**（**一個立刻可用的實務技巧**），**或者把長文檔改成檢索後只放入相關片段**。**評估層面**——**用「針在不同深度」的測試量化這個現象，而不是假設模型能均勻處理**。**而最務實的結論是「不要因為模型支援 128K 就把 128K 塞滿」**——**在多數應用中，先做檢索再放入 8K 的相關內容，效果比塞滿 128K 更好也更便宜**。**這個判斷比理解機制本身更有實用價值。**

**面試回答方式**：給兩個疊加的原因（訓練資料的位置分布、長序列下注意力的稀釋）。核心加分點是指出**這是資料與機制共同造成的所以不能只靠架構解決**，並給三個方向（訓練時構造中段關鍵的樣本、推理時把重要內容放頭尾、評估時用不同深度的針測試）。收在最務實的結論：**不要因為模型支援 128K 就塞滿**——**先檢索再放入 8K 相關內容，效果更好也更便宜**。

### 長上下文會取代 RAG 嗎？

**核心答案**：**不會完全取代，因為它們解決的問題只有部分重疊**。長上下文解決的是**「一次能處理多少內容」**；RAG 解決的是**「從海量資料中找出相關的部分」**——**當資料量是 GB 或 TB 級時，任何上下文長度都不夠**。**而且 RAG 還提供了長上下文沒有的能力**：**引用來源、即時更新、以及權限過濾**。

**詳細解析**：**成本是另一個決定性因素**：**把 100K token 放進上下文的成本，遠高於檢索出 5K 相關內容再處理**——**而且延遲也差很多**（**prefill 的計算量與長度成正比甚至平方**）。**所以即使長上下文技術上可行，在高頻的線上應用中 RAG 仍然是更經濟的選擇**。**真正的變化是「兩者的分工在移動」**：**長上下文讓 RAG 可以放入更多、更粗粒度的片段**（**不必為了省 token 而切得很細，而切得太細正是 RAG 品質問題的主要來源之一**）——**於是檢索的精度要求下降，整體品質反而提升**。**這是一個「新能力改善了舊方案」而非取代的例子**，**而能做出這個判斷比選邊站更有價值**。

**面試回答方式**：明確回答不會完全取代，並區分兩者解決的問題（**能處理多少 vs 從海量中找出相關的**），指出**RAG 還提供引用來源、即時更新、權限過濾**。加分點是**成本與延遲**：**100K 放進上下文遠貴於檢索 5K，而 prefill 的計算量與長度成正比甚至平方**。核心加分點是指出**真正的變化是分工在移動**：**長上下文讓 RAG 可以放入更粗粒度的片段，不必切得太細，而切得太細正是 RAG 品質問題的主要來源之一**——**這是「新能力改善了舊方案」而非取代**。
