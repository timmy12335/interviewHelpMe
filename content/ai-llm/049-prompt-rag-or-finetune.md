# 題目

同一個需求，用提示工程、RAG、還是微調？

## 核心答案

**判準是「你缺的是什麼」。**

**缺指令的清晰度** → **提示工程**。模型有能力也有知識，只是不知道你要什麼——**加範例、明確格式、拆解步驟**。**成本最低、迭代最快，永遠應該先試這一條。**

**缺知識** → **RAG**。模型不知道你的文檔、你的資料、或者最新的資訊——**檢索並放進上下文**。**適合會更新的、量大的、需要引用來源的知識。**

**缺行為的一致性或特定的能力** → **微調**。**輸出格式的穩定、專業領域的表達習慣、以及「怎麼使用提供的內容」這類行為**——**這些用提示要寫很長且仍不穩定，用微調則能內化。**

**而實務上最常見的答案是「組合」**：**提示定義任務、RAG 提供知識、微調調整行為**——**它們解決不同的問題，不是三選一。**

## 詳細解析

**「先試提示」不只是因為便宜，還因為它是診斷工具**：如果精心設計的提示（含幾個好範例）仍然做不到——**那通常說明模型能力不足或任務定義有問題**，**而那兩者都不是 RAG 或微調能解決的**。**反過來，如果提示能做到但不穩定，那正是微調的適用場景**。**所以「用提示能不能做到」這個實驗，本身就給出了下一步該往哪走的答案。**

**「用微調灌輸知識」是最常見的錯誤選擇**，它有三個具體的缺點：**知識更新要重新訓練**、**無法引用來源**、**而且模型對微調學到的知識同樣會產生幻覺**（**它學到的是統計關聯而非可查證的事實**）。**這三點都是 RAG 天然沒有的**——**所以除非知識極其穩定且量小，否則 RAG 幾乎總是更好的選擇**。

**「少樣本範例」是提示與微調之間的中間地帶**：**它用上下文中的例子達到類似微調的效果**——**代價是每次請求都要付那些範例的 token 成本**。**判斷的分界是「範例的成本 × 請求量」與「微調的一次性成本」的比較**：**高頻的應用中，把穩定的少樣本範例微調進模型能同時省下成本與延遲**。

**成本與時間的量級差異值得知道**：**提示工程是小時級**、**RAG 是天到週級**（要建立資料管線與評估）、**微調是週級**（要準備資料、訓練、評估、部署）。**這個差異意味著即使最終方案是微調，先用提示或 RAG 做出一個能用的版本並驗證需求，幾乎總是正確的順序。**

## 面試回答方式

先給判準——**你缺的是什麼**：缺指令清晰度用提示、缺知識用 RAG、缺行為一致性用微調，並強調**實務上最常見的答案是組合而非三選一**。加分點有四個：**先試提示不只因為便宜，還因為它是診斷工具**——**精心設計的提示仍做不到通常說明模型能力不足或任務定義有問題**，**而如果能做到但不穩定，那正是微調的適用場景**；**「用微調灌輸知識」是最常見的錯誤選擇**與它的三個缺點；**少樣本範例是中間地帶**——**判斷分界是「範例成本乘請求量」與「微調的一次性成本」的比較**；以及**三者的時間量級差異**（小時、天到週、週），**所以即使最終方案是微調，先用提示或 RAG 驗證需求幾乎總是正確的順序**。

## 講稿

我的判準是你缺的是什麼。

缺指令的清晰度就用提示工程。模型有能力也有知識，只是不知道你要什麼，那就加範例、明確格式、拆解步驟。缺知識就用檢索增強。缺行為的一致性或特定能力就用微調。

而實務上最常見的答案是組合，提示定義任務、檢索提供知識、微調調整行為。它們解決不同的問題，不是三選一。

先試提示不只是因為便宜，還因為它是一個診斷工具。如果精心設計的提示加上幾個好範例仍然做不到，那通常說明模型能力不足或者任務定義有問題，而那兩者都不是檢索或微調能解決的。反過來，如果提示能做到但不穩定，那正是微調的適用場景。所以這個實驗本身就給出了下一步該往哪走的答案。

還有一個最常見的錯誤選擇是用微調灌輸知識。它有三個缺點，知識更新要重新訓練、無法引用來源、而且對微調學到的知識同樣會產生幻覺。這三點都是檢索天然沒有的。

## 常見追問

### 提示工程有哪些真正有效的技巧？

**核心答案**：**按效益排序有五個**。**給範例**（少樣本）——**比任何文字描述都有效，尤其是格式與風格**。**明確輸出格式**——**用 schema 或範本，減少歧義**。**拆解步驟**——**複雜任務明確列出步驟，讓模型逐步執行**。**允許推理空間**——**要求先分析再結論，而不是直接給答案**。**明確邊界與失敗處理**——**告訴它「找不到就說找不到」，否則它會編**。

**詳細解析**：**「範例的品質比數量重要」**：三個精心挑選、覆蓋不同情況（包含邊界案例與該拒絕的案例）的範例，**勝過十個相似的**。**尤其重要的是「包含負面示範」**——**如果所有範例都是正常情況，模型不知道遇到異常輸入該怎麼辦**。**另一個常被忽略的是「範例的順序與位置」**：**模型對最後幾個範例的印象更深（近因效應）**，**所以最重要或最典型的範例應該放在最後**。**而那些流傳很廣但效果可疑的技巧**（例如承諾小費、威脅、扮演專家）——**在現代的指令微調模型上收益已經很小甚至為零**，**因為模型本來就被訓練成盡力回答**。**能區分「有機制解釋的技巧」與「經驗傳說」，比記住一堆咒語有價值得多。**

**面試回答方式**：給五個按效益排序的技巧。核心加分點是**範例的品質比數量重要**——**三個覆蓋不同情況的勝過十個相似的**，**尤其要包含負面示範，否則模型不知道遇到異常輸入該怎麼辦**；以及**範例的順序**——**近因效應讓最重要的應該放最後**。收在判斷力：**那些流傳很廣的技巧（承諾小費、威脅、扮演專家）在現代指令微調模型上收益已經很小**，**而能區分「有機制解釋的技巧」與「經驗傳說」比記住一堆咒語有價值得多**。

### 什麼時候該把提示邏輯改成程式碼？

**核心答案**：**當那部分是確定性的時候**。如果一段提示在教模型「怎麼一步步做一件有明確規則的事」——**那件事應該用程式碼寫**。**判斷的訊號是「這段提示的邏輯能不能寫成 if-else 或一段函式」**：**能的話，程式碼一定更可靠、更便宜、更快、也更好測試。**

**詳細解析**：**「用模型做確定性的事」是 LLM 應用最常見的浪費**：計算、排序、格式轉換、條件判斷——**這些交給程式碼是百分之百正確且幾乎零成本的**，**而交給模型則是機率性的且要付 token**。**正確的分工是「模型負責處理非結構化與模糊的部分，程式碼負責處理結構化與確定的部分」**——**而好的架構會讓兩者的邊界盡量清晰**。**一個實用的檢驗是「畫出資料流，標出每一步是模型還是程式碼」**：**如果模型出現在了不需要理解自然語言的地方，那就是可以優化的點**。**這個檢驗往往能同時降低成本、提升準確率、並讓系統變得可測試**——**是 LLM 應用最高效益的重構方向之一。**

**面試回答方式**：給判斷訊號（**這段提示的邏輯能不能寫成 if-else 或一段函式**）並指出**能的話程式碼一定更可靠、更便宜、更快、更好測試**。核心加分點是點名**「用模型做確定性的事」是最常見的浪費**並給正確的分工原則。收在實用檢驗：**畫出資料流標出每一步是模型還是程式碼**，**模型出現在不需要理解自然語言的地方就是可優化的點**——**這往往能同時降低成本、提升準確率、讓系統可測試**。

### 提示怎麼版本管理與測試？

**核心答案**：**把提示當成程式碼**：**放進 Git、經過 code review、有版本號、有測試**。**具體是三件事**：**提示與它的評估案例放在一起**、**每次改動在 CI 中跑評估集並比對基準**、**以及在生產中記錄「這次回應用的是哪個提示版本」**（**否則無法歸因問題**）。

**詳細解析**：**「把提示存在資料庫或後台讓非工程師隨時改」是一個誘人但危險的設計**：它讓迭代變快——**但也讓提示脫離了版本控制、脫離了測試、脫離了 code review**。**於是一次未經測試的修改可能在生產中造成大範圍的品質下降，而且沒有人知道是誰在什麼時候改的**。**折衷的做法是「後台可以編輯，但改動走一個帶評估的發布流程」**——**編輯者可以在沙盒中即時看到效果，但要發布到生產必須通過評估集**。**這保留了非工程師參與的價值，同時保住了工程上的紀律**——**而這個平衡在多數 LLM 產品團隊裡是一個真實的組織問題，不只是技術問題**。

**面試回答方式**：給核心原則（**把提示當程式碼**）與三件具體的事。核心加分點是點出**「存在資料庫讓非工程師隨時改」是誘人但危險的設計**——**它讓提示脫離版本控制、測試與 review，一次未經測試的修改可能造成大範圍品質下降且無法追溯**。收在折衷：**後台可編輯但發布走帶評估的流程，沙盒即時預覽、發布必須通過評估集**——**這在多數 LLM 產品團隊裡是一個真實的組織問題而不只是技術問題**。
