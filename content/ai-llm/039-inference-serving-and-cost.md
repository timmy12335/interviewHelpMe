# 題目

自建推理服務與呼叫 API 怎麼選？成本怎麼算？

## 核心答案

先算清楚兩邊的成本結構，因為它們完全不同。

**API**——按 token 計費，零固定成本，用多少付多少。適合流量小、流量波動大、或者需要最強模型的場景。缺點是單位成本較高、資料要送出去、以及受制於供應商的可用性與政策。

**自建**——固定的 GPU 成本（無論有沒有流量都在燒錢），**但邊際成本極低**。**只有在「利用率夠高」時才划算**——而利用率正是多數自建專案失算的地方。

**判斷的核心是「盈虧平衡點」**：把自建的月度總成本（GPU 租金 + 人力 + 運維）除以你能達到的月度 token 產出，**與 API 的單價比較**。多數團隊算出來會發現：除非持續高負載，API 更便宜——因為 GPU 閒置的時間也在計費，而 API 只在你用的時候收錢。

## 詳細解析

「利用率」是自建划不划算的唯一關鍵，而它常常被高估。**一張 H100 的月租可能是幾千美元**——如果你的流量只在工作時間有、而且尖峰與平均差五倍，那麼實際利用率可能只有 10% 到 20%。於是有效的單位成本是紙面計算的五到十倍。**改善的方式有三**：**混合部署**（訓練或批次任務填滿低谷）、**多租戶共用**（多個產品共用同一個推理叢集）、以及用 spot 實例跑可中斷的批次推理。

**「人力成本常被完全忽略」**：自建意味著要有人負責模型部署、版本升級、效能調校、故障處理、以及跟上推理框架的演進——這通常是至少半個到一個全職工程師。在多數地區，那個人力成本本身就相當於幾張 GPU 的租金。所以「自建更便宜」的計算如果沒有把人算進去，結論通常是錯的。

**混合策略往往是最優解**：用 API 服務尖峰與長尾請求，用自建處理穩定的基礎負載——或者反過來，用自建的小模型處理簡單請求、用 API 的大模型處理困難請求。後者（按難度路由）在成本與品質上的效益往往最高：如果 80% 的請求可以用便宜十倍的模型處理，總成本就降到原來的三成左右。

自建的正當理由往往不是成本：資料不能出境或不能給第三方、**需要微調過的專屬模型**、**需要極低且穩定的延遲**、或者需要不受供應商政策變動影響。**這些理由比「省錢」紮實得多**——而面試中能區分「真正的理由」與「以為的理由」是有說服力的。

## 面試回答方式

先給兩邊的成本結構（API 零固定成本按量計費，自建固定成本高但邊際成本極低）與判斷核心——**盈虧平衡點**，並給出結論：除非持續高負載，API 通常更便宜，因為 GPU 閒置也在計費。加分點有四個：**利用率常被高估**——流量只在工作時間、尖峰與平均差五倍時，實際利用率可能只有 10% 到 20%，有效單位成本是紙面的五到十倍，並給三個改善方式；**人力成本常被完全忽略**——至少半個到一個全職工程師，本身就相當於幾張 GPU 的租金；按難度路由的混合策略效益最高——80% 的請求用便宜十倍的模型，總成本降到三成；以及自建的正當理由往往不是成本而是資料、專屬模型、延遲穩定性與政策風險。

## 講稿

我會先算清楚兩邊的成本結構，因為它們完全不同。呼叫介面是按詞元計費、零固定成本。自建是固定的加速卡成本，無論有沒有流量都在燒，但邊際成本極低。

判斷的核心是盈虧平衡點。把自建的月度總成本除以你能達到的月度詞元產出，跟介面單價比。多數團隊算出來會發現，除非持續高負載，呼叫介面更便宜。因為加速卡閒置的時間也在計費，而介面只在你用的時候收錢。

這裡最常被高估的是利用率。如果流量只在工作時間有，而且尖峰跟平均差五倍，那實際利用率可能只有一兩成，有效的單位成本就是紙面計算的五到十倍。

第二個常被完全忽略的是人力。自建意味著要有人負責部署、升級、調校、故障處理，這通常是至少半個到一個全職工程師，那個成本本身就相當於幾張卡的租金。

而實務上最優的往往是混合。用自建的小模型處理簡單請求，用介面的大模型處理困難的。如果八成的請求可以用便宜十倍的模型，總成本就降到三成左右。

## 常見追問

### 量化能省多少？品質損失多大？

**核心答案**：int8 或 fp8 幾乎無損，int4 有可察覺但通常可接受的損失。收益是**顯存佔用等比例下降**（**fp16 的 70B 需要 140 GB，int4 只需要約 35 GB**）**與解碼速度提升**（讀的位元組變少，而解碼是記憶體受限的）。實務上 int4 讓「原本需要 2 張 80GB 卡的模型可以放進 1 張」——這個階躍式的成本變化往往比百分比的節省更重要。

**詳細解析**：「量化的損失不是均勻分布的」是一個重要的細節：對一般的對話與摘要幾乎看不出差異，而對數學推理、長鏈邏輯、與程式碼生成的影響明顯得多——因為這些任務對每一步的精確度更敏感，誤差會累積。所以評估量化模型必須用「你實際的任務」而非通用基準。技術上，現代的量化方法（GPTQ、AWQ、SmoothQuant）都做了「保護重要權重」的處理——因為權重的分布極不均勻，少數異常值（outlier）承載了大部分的資訊，粗暴地均勻量化會嚴重損害它們。理解這一點能解釋「為什麼有些量化方法比另一些好很多」，而那與位元數無關。

**面試回答方式**：給各精度的損失程度與收益，並指出 int4 讓「2 張卡變 1 張」這種階躍式的成本變化往往比百分比節省更重要。核心加分點是**量化的損失不是均勻分布的**——對話與摘要幾乎無感，而數學推理、長鏈邏輯與程式碼影響明顯，因為誤差會累積，所以評估必須用你實際的任務而非通用基準。收在技術洞察：權重分布極不均勻，少數異常值承載大部分資訊，現代量化方法都在保護它們，而這解釋了為什麼同樣位元數的方法效果差很多。

### 怎麼監控推理服務？

**核心答案**：**四類指標**。**延遲**——**TTFT 與 TPOT 分開看，都要 p50/p95/p99**。**吞吐**——每秒輸入與輸出的 token 數（不是請求數，因為請求大小差異巨大）。**資源**——顯存使用率、KV Cache 佔用率、以及正在服務的序列數。**品質與成本**——錯誤率、逾時率、每千次請求的成本、以及輸出長度的分布。

**詳細解析**：「用 token 數而非請求數」是這裡最重要的一條：**一個請求可能是 100 token 也可能是 100K token**——用請求數做容量規劃會完全失準。同樣的道理，限流也應該以 token 為單位而非請求數（**多數商業 API 正是這樣做的**）。另一個容易忽略的指標是「輸出長度的分布」：它直接決定成本與延遲，而它的異常上升往往是提示變更或模型行為改變的早期訊號——例如一次提示調整讓模型變得囉唆，帳單會在幾天後才反映出來，而輸出長度的指標當天就能看到。這類「先行指標」在成本控制上比事後的帳單分析有價值得多。

**面試回答方式**：給四類指標並強調 **TTFT 與 TPOT 要分開**。核心加分點是**用 token 數而非請求數**——一個請求可能是 100 也可能是 100K token，用請求數做容量規劃會完全失準，**限流也應該以 token 為單位**。第二個是**輸出長度的分布**這個容易忽略的指標：它直接決定成本與延遲，異常上升是提示變更或模型行為改變的早期訊號——帳單幾天後才反映，而這個指標當天就看得到。

### 模型版本怎麼管理與更新？

**核心答案**：把模型當成一個有版本的依賴：明確鎖定版本、有測試流程、有金絲雀發布、有回滾能力。尤其重要的是「不要用會自動更新的模型別名」——供應商更新模型可能改變輸出的風格、長度與行為，而你的提示是針對舊版本調校的。

**詳細解析**：「提示與模型版本是耦合的」是這個領域一個特有的困難：軟體的依賴升級有明確的 API 契約——而模型的「契約」是模糊的行為傾向，升級後所有提示都可能需要重新調校。所以升級的流程應該包含「用一組固定的評估案例跑新舊兩個版本並比較差異」——這相當於模型層面的回歸測試。建立這個評估集的成本不低，但它是唯一能讓你「安心升級」的東西：沒有它，每次模型更新都是一次盲目的賭博。而更根本的建議是「把提示與評估案例一起版本控制」——它們必須被當成一個整體來測試與發布，而不是提示在 Git 裡、模型版本在設定檔裡、評估在某個人的筆記本裡。

**面試回答方式**：給管理原則（鎖定版本、測試、金絲雀、回滾）並強調不要用會自動更新的模型別名。核心加分點是指出**提示與模型版本是耦合的**——軟體依賴有明確的 API 契約，而模型的契約是模糊的行為傾向，升級後所有提示都可能需要重新調校，所以升級流程要包含「固定評估案例跑新舊兩版比較」這個模型層面的回歸測試。收在根本建議：把提示與評估案例一起版本控制，它們必須被當成一個整體來測試與發布。
