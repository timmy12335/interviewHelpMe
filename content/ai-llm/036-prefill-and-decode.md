# 題目

LLM 推理為什麼要分成 prefill 與 decode？它們的效能瓶頸有什麼不同？

## 核心答案

**兩個階段的計算特性完全相反，這是理解推理效能的起點。**

**Prefill（預填充）**——**把整個提示一次送進模型，平行計算所有位置的表示並填滿 KV Cache**。**它是計算受限（compute-bound）**：**大量的矩陣乘法，GPU 的算力被充分利用**。**時間大致與提示長度成正比**，**對應使用者感受到的「首個 token 延遲」（TTFT）**。

**Decode（解碼）**——**一次只生成一個 token，每步都要讀取整個 KV Cache 與全部模型權重**。**它是記憶體頻寬受限（memory-bound）**：**計算量很小（只有一個 token），卻要把幾十 GB 的權重從顯存讀一遍**——**算力大量閒置**。**每步的時間幾乎與批次大小無關**，**這正是批次處理能大幅提升吞吐的原因**。

**兩者的差異決定了幾乎所有的推理優化方向**：**decode 階段的優化（批次、量化、推測解碼、GQA）收益遠大於 prefill。**

## 詳細解析

**「decode 是記憶體受限」是最重要的一個認知**。生成一個 token 需要讀取全部模型權重——**一個 70B 的 fp16 模型是 140 GB**，**而顯存頻寬假設是 2 TB/s，那麼每個 token 至少要 70 毫秒**——**這是硬性的下限，與你的算力有多強無關**。**這解釋了三件事**：**為什麼量化能直接提升解碼速度**（讀的位元組變少）、**為什麼增大批次幾乎不增加每步時間**（權重只讀一次，服務更多請求）、**以及為什麼小模型的生成速度快得多**。

**「批次處理的收益是不對稱的」**：對 decode 階段，**批次從 1 增加到 32，吞吐幾乎線性提升而延遲幾乎不變**——**因為瓶頸是讀權重，而權重只需要讀一次**。**對 prefill 階段則不然**——**它本來就把算力用滿了，增大批次只是排隊**。**所以推理服務的批次策略應該針對 decode 設計。**

**「prefill 與 decode 互相干擾」是生產服務的一個真實問題**：**一個長提示的 prefill 會佔住 GPU 幾百毫秒**——**在此期間所有正在 decode 的請求都被卡住，表現為「輸出突然停頓」**。**兩種緩解**：**分塊 prefill（chunked prefill）**——**把長提示切成小塊，與 decode 交錯執行**；**PD 分離**——**用不同的機器分別處理兩個階段**，**各自用最適合的配置**。**後者是近年大規模推理服務的趨勢**。

**指標上要分開看**：**TTFT（首 token 延遲）由 prefill 決定**，**TPOT（每個輸出 token 的時間）由 decode 決定**。**對話類產品對 TTFT 敏感（使用者盯著空白畫面），而對 TPOT 的要求只要「快過閱讀速度」即可**——**這個區分決定了優化的優先順序**。

## 面試回答方式

先給兩個階段的計算特性並強調**它們完全相反**：**prefill 計算受限、對應 TTFT；decode 記憶體頻寬受限、每步時間幾乎與批次無關**。指出**這個差異決定了幾乎所有優化方向**。加分點有四個：**用具體數字說明 decode 的硬性下限**——**70B 的 fp16 模型是 140 GB，2 TB/s 的頻寬意味著每個 token 至少 70 毫秒，與算力無關**，**這解釋了量化為何提速、批次為何幾乎不增加每步時間、小模型為何快**；**批次收益的不對稱**——**對 decode 幾乎線性提升吞吐而延遲不變，對 prefill 只是排隊**；**prefill 與 decode 互相干擾**——**長提示會讓正在解碼的請求「輸出突然停頓」**，緩解是分塊 prefill 或 PD 分離；以及**TTFT 與 TPOT 要分開看**，**TPOT 只要快過閱讀速度即可**。

## 講稿

兩個階段的計算特性完全相反，這是理解推理效能的起點。

預填充是把整個提示一次送進去，平行算出所有位置並填滿快取。它是計算受限的，算力被充分利用，時間跟提示長度成正比，對應使用者感受到的首個詞元延遲。

解碼是一次生成一個詞元，每步都要讀取整個快取跟全部模型權重。它是記憶體頻寬受限的，計算量很小卻要把幾十 GB 的權重讀一遍，算力大量閒置。

這個認知很重要，因為它有硬性的下限。一個七百億參數的半精度模型是一百四十 GB，顯存頻寬假設每秒兩 TB，那每個詞元至少七十毫秒，跟你的算力有多強無關。

這一句話解釋了三件事。為什麼量化能直接提升解碼速度，因為讀的位元組變少。為什麼增大批次幾乎不增加每步時間，因為權重只讀一次卻服務了更多請求。還有為什麼小模型的生成速度快得多。

所以推理優化的重點幾乎都在解碼階段，批次、量化、推測解碼、還有共享鍵值頭。

## 常見追問

### 為什麼 KV Cache 這麼佔記憶體？怎麼算？

**核心答案**：**KV Cache 的大小 = `2 × 層數 × KV頭數 × 頭維度 × 序列長度 × 批次 × 精度位元組`**。**「2」是 key 與 value 各一份**。**對一個 70B 模型、80 層、8 個 KV 頭（GQA）、頭維度 128、fp16**——**每個 token 約 `2×80×8×128×2 = 320 KB`**；**一個 8K 的對話就是 2.6 GB，而 32 個並發就是 84 GB**——**遠超模型權重本身在很多配置下的佔用**。

**詳細解析**：**這個計算解釋了「為什麼並發數上不去」**：顯存被 KV Cache 吃光，而不是被模型權重吃光。**三個降低的方向**：**GQA/MQA 減少 KV 頭數**（**上例從 64 頭降到 8 頭就是 8 倍**）、**量化 KV Cache**（**fp8 或 int8，直接減半或更多**）、**以及 PagedAttention 減少碎片浪費**（**傳統做法按最大長度預留，實際用不到就浪費了；分頁管理讓利用率接近 100%**）。**vLLM 的核心貢獻正是最後這一項，它讓實際可服務的並發數提升了好幾倍**——**而那不是靠更快的計算，只是靠更好的記憶體管理**。**這是一個很好的例子說明「系統層面的優化有時比演算法優化收益更大」。**

**面試回答方式**：給出完整的計算公式並用具體數字算一遍（**70B 模型每個 token 約 320 KB，8K 對話 2.6 GB，32 並發 84 GB**），指出**它遠超模型權重的佔用**。核心加分點是說明**這解釋了為什麼並發數上不去**，並給三個降低方向。收在 **PagedAttention**：**傳統按最大長度預留造成浪費，分頁管理讓利用率接近 100%**，**vLLM 靠這個讓可服務並發提升好幾倍**——**不是靠更快的計算，只是靠更好的記憶體管理**。

### 提示快取（prompt caching）是怎麼運作的？

**核心答案**：**把「相同前綴」的 KV Cache 存下來重複使用**。多輪對話中，**每一輪的提示都包含前面所有的內容**——**如果不快取，每輪都要重新 prefill 一遍**。**快取之後，只需要對新增的部分做 prefill**，**TTFT 與成本都大幅下降**。**系統提示、少樣本範例、與長文檔這類固定前綴的收益最大。**

**詳細解析**：**「前綴必須完全相同」是使用它的關鍵約束**：**只要有一個 token 不同，從那個位置之後的快取就全部失效**——**因為注意力的計算依賴前面所有內容**。**這帶來一個實用的提示設計原則：把固定的內容放前面，變動的放後面**。**很多人習慣把使用者的問題放在系統提示之前或中間，那會讓快取完全失效。** **另一個實務要點是「快取有存活時間與成本」**：**商業 API 的快取通常只保留幾分鐘，而寫入快取本身可能比普通輸入貴**——**所以它適合「同一個長前綴在短時間內被重複使用」的場景**（例如一個文檔的多輪問答），**而不適合每次都是全新內容的場景**。**能算清楚「重複幾次以上才划算」，是使用這個功能時最實際的判斷。**

**面試回答方式**：給機制（快取相同前綴的 KV，只 prefill 新增部分）與收益最大的場景。核心加分點是**「前綴必須完全相同」這個約束**——**一個 token 不同，之後的快取全部失效**，**由此導出提示設計原則：固定內容放前面、變動放後面**，並指出**很多人把使用者問題放在系統提示之前或中間，那會讓快取完全失效**。收在成本判斷：**快取有存活時間，寫入可能比普通輸入貴**，**所以要算清楚重複幾次以上才划算**。

### 怎麼降低首 token 延遲？

**核心答案**：**四個方向**。**縮短提示**——**最直接，用檢索取代把全部內容塞進去**。**提示快取**——**固定前綴不重複計算**。**分塊 prefill 與優先級調度**——**避免長請求阻塞短請求**。**以及流式輸出**——**嚴格說它不降低 TTFT，但讓使用者更早看到第一個字，感受上的改善很大**。

**詳細解析**：**「感知延遲」與「實際延遲」的區別在產品上非常重要**：**使用者對「等待」的容忍度取決於有沒有回饋**——**一個 3 秒才出現完整答案的介面，感覺比一個 1.5 秒開始逐字輸出、5 秒才寫完的介面慢**。**所以串流不只是技術選擇，它直接改變了可接受的延遲預算**。**進一步的技巧包括「先回應一個確認或思考中的提示」與「先返回檢索到的來源再開始生成」**——**都是用資訊填補等待**。**而在真正需要壓低 TTFT 的場景（例如自動補全），根本的做法是換一個更小的模型**——**因為 prefill 的時間與模型大小成正比，而小模型的品質在簡單任務上往往足夠**。**「按任務難度路由到不同大小的模型」是這裡最有效的架構決定。**

**面試回答方式**：給四個方向。核心加分點是區分**感知延遲與實際延遲**：**使用者對等待的容忍度取決於有沒有回饋**，**3 秒才出現完整答案感覺比 1.5 秒開始逐字輸出更慢**，**所以串流直接改變了可接受的延遲預算**。收在根本做法：**真正需要壓低 TTFT 時換一個更小的模型**（prefill 時間與模型大小成正比），**而「按任務難度路由到不同大小的模型」是這裡最有效的架構決定**。
