# 題目

什麼是「Function Calling（函式呼叫，或稱工具呼叫 Tool Use）」？它是怎麼運作的？為什麼這個能力對於讓大型語言模型能真正和外部世界（如即時資料、程式系統）互動，扮演如此關鍵的角色？

## 核心答案

Function Calling 是一種讓大型語言模型**在處理一個使用者請求的過程中，不只是單純地依靠自己在預訓練階段已經內化的知識直接生成文字回答，而是能夠主動地判斷「這個請求是否需要呼叫某個外部的、事先定義好的函式（工具）才能被妥善地回答」；如果判斷需要，就生成一個結構化的（通常是 JSON 格式）、指明要呼叫哪一個函式以及這個函式需要哪些具體參數的「呼叫請求」，再由實際執行這個系統的應用程式去真正地執行這個被指定的函式（例如查詢即時天氣資料庫、呼叫一個計算機函式，或是查詢某個內部系統的資料庫），把這個函式實際執行後得到的結果回傳給模型，讓模型能夠依照這個額外取得的、來自外部世界的即時或精確資訊，生成最終真正能夠回答使用者原本請求的回覆**的能力。這個能力之所以扮演關鍵角色，核心原因在於大型語言模型本身的知識**終究侷限於它在預訓練階段所見過的訓練資料**（存在知識截止日期、也不具備即時性；且對於需要精確計算，或是需要查詢特定私有系統、私有資料庫裡的具體資訊這類任務，模型單純依靠自己內化的知識天生就難以勝任）。Function Calling 讓模型能夠**把這些自己天生不擅長、或是無法直接勝任的任務，轉交給真正適合、專精處理這些任務的外部工具和系統來實際執行**，模型本身則專注在它真正擅長的部分——**理解使用者的意圖、判斷應該呼叫哪個工具，以及把工具回傳的結果整合組織成一個通順、易懂的最終回覆**。這種「模型負責理解和協調、外部工具負責實際執行專精任務」的分工合作模式，是讓大型語言模型能夠真正跳脫單純的文字生成，進一步發展成具備實際任務執行能力的「智能代理（Agent）」的關鍵基礎。

## 詳細解析

**Function Calling 的具體運作流程**：一個典型的 Function Calling 流程大致包含以下幾個步驟——**(1) 事先定義工具**——應用程式的開發者事先需要明確地定義好模型可以呼叫的每一個工具（函式）——包括這個工具的名稱、它具體是用來做什麼的（一段清楚的文字描述），以及它需要接收哪些參數（每個參數的名稱、型別、是否為必要參數等），這些定義通常會被整理成一份結構化的規格說明；**(2) 把這些工具的定義連同使用者的請求一起提供給模型**——模型在處理這個使用者請求時會同時參考這些可用工具的定義；**(3) 模型判斷是否需要呼叫工具、以及應該呼叫哪一個**——模型依照使用者請求的內容，以及它對各個可用工具的功能描述的理解，判斷這個請求是否需要藉助某個（或多個）外部工具才能被妥善地回答，如果判斷需要，模型會生成一個結構化的、明確指出要呼叫哪個工具以及這個工具需要哪些具體參數值的請求（而不是直接生成一段自然語言的文字回覆）；**(4) 應用程式實際執行這個被指定的函式**——這是在模型本身之外，由實際承載、運行這整個系統的應用程式負責的部分，應用程式依照模型生成的那個結構化的呼叫請求去真正地執行對應的程式碼（例如真正地去呼叫一個查詢天氣的 API，或者真正地去執行一段計算邏輯）；**(5) 把執行結果回傳給模型**——應用程式把這個函式實際執行後得到的結果（例如查到的即時天氣資料）重新提供回給模型；**(6) 模型依照這個額外取得的結果生成最終回覆**——模型這時候才依照這個額外取得的、來自外部工具的具體資訊，生成一段真正能夠回答使用者原本問題的、通順的自然語言回覆。

**Function Calling 和之前討論過的 RAG 之間的關聯與區別**：Function Calling 和之前已經深入討論過的 RAG（見 [[008-rag-architecture.md]]）某種程度上都是**讓模型能夠取得超越自己預訓練知識範圍的額外資訊**這個共同大方向下，兩種不同但可能互補的具體技術手段。兩者一個值得仔細釐清的核心區別是——**RAG 通常處理的是「檢索相對靜態、已經事先準備好的文件或知識庫內容」這類任務**（透過向量相似度搜尋找到語意上和使用者問題相關的既有文件片段）；而 **Function Calling 處理的範圍明顯更加廣泛、也更具備「主動執行」的特性**——它不只可以用來查詢資訊（某種程度上可以把「查詢一個即時的、會隨時間變動的資訊，例如即時天氣或股價」這種用法理解為一種比 RAG 更即時、更動態的「檢索」形式），還可以用來**真正地執行具備實際副作用的操作**（例如呼叫一個函式去真正地發送一封郵件、真正地在某個系統裡建立一筆訂單，或是真正地執行一段計算邏輯）。這種「不只是被動地檢索既有資訊，還能主動地執行具備實際後果的操作」的特性，是 Function Calling 相較於 RAG 一個更進一步、也更貼近「智能代理」這個概念核心精神的能力延伸。實務上一個功能完整的 AI 應用系統經常會**同時結合運用 RAG（用來讓模型能夠參照既有的知識庫文件）和 Function Calling（用來讓模型能夠查詢即時資訊，或是真正執行具備實際效果的操作）**，這兩種技術取長補短，共同讓這個系統具備更完整、更強大的整體能力。

**Function Calling 帶來的安全性考量**：因為 Function Calling 讓模型具備了**真正觸發執行具備實際副作用操作**的能力（而不再只是單純地生成一段文字），這也連帶地引入了一些額外需要被謹慎對待的安全性考量——尤其需要特別注意的是前面已經在其他章節反覆強調過的「Prompt Injection（提示注入）」這類風險（見下一題將詳細討論的 [[023-prompt-injection.md]]）——如果模型是依照某個**可能遭到惡意使用者、或是來自外部不受信任來源（例如模型在執行任務過程中讀取到的一份外部網頁內容）的惡意指令所污染影響**的判斷，而被誤導去呼叫某個具備實際破壞性後果的工具（例如被誤導去執行一個會刪除重要資料的函式，或是把敏感的私有資訊傳送給不應該收到這些資訊的外部對象），這種情況可能會帶來相當嚴重的實際損害。因應這種風險，實務上一個重要的防範原則是——針對那些**具備較高風險、或是會造成難以復原的實際後果**的工具（例如涉及金錢交易、刪除資料，或是發送對外的正式通訊這類操作），應該**額外設計一道明確的人工確認機制**（模型判斷需要呼叫這類高風險工具時並不會直接自動地執行，而是會先向實際的使用者呈現「即將要執行這個操作」這件事，明確地取得使用者的確認同意之後才真正地觸發執行這個操作）。這種**針對高風險操作額外設置人工把關確認**的設計原則，是實際在運用 Function Calling 這種具備實際執行能力的技術時需要被審慎納入考量的重要安全實務。

## 面試回答方式

先給出Function Calling的核心概念——「讓大型語言模型在處理使用者請求過程中，能主動判斷這個請求是否需要呼叫某個事先定義好的外部函式才能被妥善回答，如果需要就生成一個結構化的、指明要呼叫哪個函式和需要哪些參數的呼叫請求，由應用程式實際執行這個函式，再把執行結果回傳給模型，讓模型依照這個額外取得的資訊生成最終回覆」。可以清楚地把六個步驟講出來——「事先定義工具規格、把工具定義和使用者請求一起給模型、模型判斷是否及呼叫哪個工具、應用程式實際執行、把結果回傳給模型、模型依照結果生成最終自然語言回覆」。解釋為什麼這個能力重要——「模型自身的知識終究侷限於預訓練階段見過的訓練資料，存在知識截止日期、不具備即時性、也難以精確計算或查詢私有系統資料，Function Calling讓模型能把自己不擅長的任務轉交給真正專精的外部工具執行，自己專注在理解意圖、判斷該呼叫哪個工具、以及整合結果這件真正擅長的事情上」。可以主動比較和RAG的關係——「RAG通常處理檢索相對靜態、已準備好的文件內容，Function Calling的範圍更廣、更具備主動執行的特性，不只能查詢資訊還能真正執行具備實際副作用的操作，實務上功能完整的系統經常同時結合運用兩者」。一定要主動提到安全性考量——「針對具備較高風險或難以復原後果的工具操作，應該額外設計一道明確的人工確認機制，而不是讓模型自動觸發執行」，展現你對Function Calling不僅理解技術機制，也理解其實際部署時的安全考量。

## 常見追問

### 如果模型判斷一個請求需要同時呼叫好幾個不同的工具才能完整地回答，這種多工具協同呼叫的情境在實務上會面臨什麼樣的額外挑戰？

**核心答案**：多工具協同呼叫相較於單一工具呼叫，會額外面臨幾個層面的挑戰——**(1) 呼叫順序的依賴關係**——如果某個工具的呼叫需要依賴另一個工具先前執行後得到的結果（例如需要先呼叫一個工具查到某位使用者的帳號 ID，才能用這個 ID 去呼叫另一個工具查詢這位使用者的訂單紀錄），模型需要正確地判斷出這種**先後順序的依賴關係**，而不能錯誤地同時、或是以錯誤的順序去呼叫這些彼此存在依賴關係的工具；**(2) 中間結果的錯誤處理**——如果其中某一個工具的呼叫執行失敗、或是回傳了一個不符合預期的結果，模型需要能夠妥善地判斷應該如何因應這種中間環節的失敗（是否應該重試；是否應該改為呼叫另一個替代的工具；還是應該直接如實地告知使用者這個部分的請求無法被完成），而不是簡單地忽略這個失敗，或是基於一個實際上並不完整、正確的中間結果就貿然地繼續執行後續的步驟；**(3) 整體流程的效率考量**——如果多個工具的呼叫彼此之間並不存在前後依賴關係（可以被同時、平行地執行），一個設計良好的系統應該要能夠識別出這種情況，並**平行地**同時發起這些彼此獨立的工具呼叫（而不是不必要地依序一個接著一個逐一執行），來降低整體完成這個多工具協同任務所需要的總時間。

**詳細解析**：這題把 Function Calling 這個核心概念從「單一次呼叫」這種相對簡化的情境，延伸到更貼近實務上真正常見、也更複雜的「多工具協同」情境，考察是否理解這種更複雜的協同情境底下具體會浮現出來的實務挑戰。第一個挑戰——**呼叫順序的依賴關係**——是多工具協同場景裡最核心、也最需要被模型（或是承載這整個流程的應用程式框架）正確處理的問題。很多實際的複雜任務本質上是**由一連串彼此存在先後依賴關係的子步驟所組成**（就像前面舉的例子，「先查到帳號 ID，才能查詢訂單紀錄」這種依賴），要正確地完成這種多步驟、彼此存在依賴的任務，模型需要具備**類似於規劃一個多步驟計畫**的能力——先正確地識別出這整個任務實際上需要分解成哪幾個具體的子步驟、這些子步驟之間存在怎樣的先後依賴關係，再依照這個正確梳理出來的依賴關係，逐一按照正確的順序發起每一個工具呼叫（而不能錯誤地跳過某個必要的前置步驟，或是用錯誤的順序去執行這些彼此存在依賴的步驟）。這種「規劃、拆解多步驟任務並正確識別步驟間依賴關係」的能力，某種程度上也是讓一個基於大型語言模型的 Agent 系統能夠真正勝任複雜的、多步驟的實際任務（而不只是處理相對簡單、一步到位的單一請求）的一個關鍵能力。第二個挑戰——**中間結果的錯誤處理**——則觸及真實世界裡**任何一個涉及實際外部系統呼叫的流程都不可避免地存在一定機率的失敗風險**這個現實（外部 API 可能因為各種原因暫時無法回應；查詢的結果可能因為某些邊界狀況而不符合預期；等等）。一個穩健、可靠的多工具協同系統需要具備**妥善地識別和因應這種中間環節失敗**的能力（這某種程度上也呼應了前面在其他章節反覆強調過的「錯誤處理不應該被靜默地忽略，而應該被明確地處理」這個原則），而不是天真地假設每一個被呼叫的工具都一定會順利地回傳正確的結果。第三個挑戰——**整體流程的效率考量**——則是一個相對更偏向系統效能優化面向的考量——如果一個任務實際上可以被拆解成多個彼此並不互相依賴的獨立子任務，一個設計良好的系統應該主動地識別出這種可以被平行處理的機會（而不是一律保守地逐一依序執行每一個工具呼叫），透過適當地運用平行處理來縮短整體完成這個多工具協同任務所需要的總時間，帶給使用者更快速、更流暢的整體體驗。理解「多工具協同呼叫相較於單一工具呼叫，會額外面臨呼叫順序的依賴關係(需要正確識別哪些工具呼叫必須依照特定先後順序執行)、中間結果的錯誤處理(任何涉及實際外部系統呼叫的流程都不可避免存在失敗風險，需要妥善判斷如何因應而非天真假設每次都會順利成功)、以及整體流程的效率考量(識別彼此不互相依賴的獨立子任務，平行處理以縮短總完成時間)這幾個層面的額外挑戰，這些能力某種程度上也是讓一個基於大型語言模型的Agent系統能真正勝任複雜多步驟實際任務的關鍵能力」，展現你能把Function Calling這個核心概念，延伸到更貼近實務的多工具協同情境，並具體識別出其中的實務挑戰。

**面試回答方式**：先給出三個主要挑戰的框架——「多工具協同呼叫會額外面臨呼叫順序的依賴關係、中間結果的錯誤處理、以及整體流程的效率考量這幾個層面的挑戰」。逐一展開解釋——「呼叫順序方面，如果某個工具呼叫需要依賴另一個工具先前執行的結果，模型需要正確識別出這種依賴關係並按正確順序執行，這需要類似規劃多步驟計畫的能力;錯誤處理方面，任何涉及實際外部系統呼叫的流程都不可避免存在失敗風險，系統需要妥善判斷是否重試、改用替代工具、或如實告知使用者無法完成，而不是忽略失敗或基於不完整結果貿然繼續;效率方面，如果多個工具呼叫彼此不互相依賴，設計良好的系統應該識別出這種情況並平行處理，而非不必要地逐一依序執行」。可以總結——「這些能力某種程度上也是讓一個基於大型語言模型的Agent系統，能真正勝任複雜多步驟實際任務的關鍵能力，而不只是處理相對簡單的單一請求」。

### 模型是怎麼知道一個工具函式「需要哪些參數」，以及應該怎麼把使用者的自然語言請求轉換成這些結構化參數的？這個轉換過程可靠嗎？

**核心答案**：模型之所以能夠知道一個工具需要哪些參數，是因為在前面（見核心答案）已經提到的「事先定義工具」這個步驟裡，開發者會明確地提供一份**結構化的規格說明**（通常採用類似 JSON Schema 這樣的格式），清楚地列出這個工具需要哪些參數、每個參數的名稱、型別，以及一段文字描述。模型在處理使用者的請求時會同時參照這份規格說明，依照它對使用者請求內容的理解，去判斷應該從使用者的自然語言敘述裡**提取或推斷出哪些具體的參數值**來填入這個結構化的呼叫請求裡；然而這個「從自然語言轉換成結構化參數」的過程**並非百分之百可靠**——模型可能因為對使用者請求的理解有誤，或者使用者的請求本身就存在模糊不清、缺少必要資訊的情況，而生成不正確或者不完整的參數值，這是實務上運用 Function Calling 技術時需要額外透過適當的驗證機制（例如在應用程式實際執行這個函式呼叫之前，先對模型生成的參數做格式和合理性的檢查）來因應的一個重要環節。

**詳細解析**：這題深入探討 Function Calling 流程裡「模型如何把自然語言轉換成結構化參數」這個關鍵、但經常被視為理所當然而較少被深入追問的技術環節。回顧前面已經解釋的「事先定義工具」這個步驟——開發者需要提供一份明確的規格說明，這份規格說明本質上扮演了一種**「合約」**的角色——它明確地界定了「呼叫這個工具必須提供哪些資訊」。模型在實際運作時會把這份規格說明連同使用者的請求一起作為輸入，依照它在預訓練（以及可能額外針對這類結構化輸出格式所做的專門微調）過程中已經習得的能力，去**理解使用者自然語言敘述裡所蘊含的意圖，並把這些意圖對應到規格說明裡所要求的具體參數欄位上**——例如如果使用者說「幫我查一下台北明天的天氣」，模型需要正確地理解「台北」應該被填入這個查詢天氣工具裡代表地點的那個參數欄位；「明天」這個相對日期的描述需要被正確地轉換成這個工具實際需要的、可能是絕對日期格式的參數值。這種「自然語言理解以及轉換成結構化格式」的能力，某種程度上也是模型需要具備的一種相當細膩的語言理解和轉換能力；然而正因為這個過程本質上依賴模型對自然語言的**理解和推斷**，而不是一個機械式、可以被保證百分之百準確的規則轉換過程，這個環節**確實存在出錯的可能性**——可能的出錯情況包括模型誤解了使用者的意圖（例如把使用者實際上想要查詢的地點誤判成另一個發音或文字相近的地名）；或者使用者的原始請求本身就**缺少某個必要參數所需要的資訊**（例如使用者只說「幫我查一下天氣」，卻沒有指明是哪個地點的天氣，這種情況下一個設計良好的系統理想上應該要讓模型**主動地向使用者反問釐清**這個缺失的必要資訊，而不是貿然地自行猜測、或者用一個不正確的預設值去填補這個空缺）。因應這種「轉換過程並非百分之百可靠」的現實，實務上一個重要的做法是在應用程式真正地執行這個模型生成的函式呼叫請求之前**額外地加上一層驗證檢查的機制**（檢查這些被生成的參數值是否符合預期的格式、型別，以及一些基本的合理性判斷），如果這層額外的驗證發現有不符合預期或是明顯不合理的參數值，可以選擇拒絕執行這次的呼叫請求、或是要求模型重新嘗試理解和轉換，來作為因應這種轉換過程本身並非絕對可靠這個現實的一道額外防線。理解「模型是依照開發者事先提供的結構化規格說明(如JSON Schema)，去理解使用者自然語言敘述裡蘊含的意圖，並將這些意圖對應到規格說明所要求的具體參數欄位上，這個轉換過程本質上依賴模型對自然語言的理解和推斷，並非機械式、能保證百分之百準確的規則轉換，確實存在模型誤解使用者意圖、或使用者原始請求本身缺少必要資訊等出錯可能，因應這種不完全可靠的現實，實務上需要在應用程式真正執行這個函式呼叫之前，額外加上一層驗證檢查機制，對不符合預期或明顯不合理的參數值做出攔截」，展現你理解Function Calling裡從自然語言到結構化參數這個轉換環節，本質上的侷限性，以及對應的實務防範措施。

**面試回答方式**：先解釋模型如何知道需要哪些參數——「開發者會在事先定義工具的步驟裡，提供一份結構化的規格說明，通常是JSON Schema格式，清楚列出這個工具需要哪些參數、每個參數的名稱型別和描述，模型會參照這份規格說明，依照它對使用者請求的理解，去提取或推斷出具體的參數值」。明確指出這個轉換過程並非百分之百可靠——「這個從自然語言轉換成結構化參數的過程，本質上依賴模型對自然語言的理解和推斷，並非機械式、能保證百分之百準確的規則轉換，可能因為模型誤解使用者意圖、或使用者原始請求本身就缺少必要資訊，而生成不正確或不完整的參數值」。給出實務因應做法——「因應這種不完全可靠的現實，實務上需要在應用程式真正執行這個函式呼叫之前，額外加上一層驗證檢查機制，對格式、型別、合理性做出檢查，發現異常就拒絕執行或要求模型重新嘗試理解和轉換」。可以補充理想設計——「一個設計良好的系統，如果發現使用者請求缺少必要參數，理想上應該讓模型主動向使用者反問釐清，而不是貿然自行猜測或用不正確的預設值填補」。

### Function Calling 這個能力是怎麼被訓練出來的？是單純透過提示工程就能讓任何一個現有的語言模型具備這個能力，還是需要額外的專門訓練？

**核心答案**：雖然**單純透過精心設計的提示工程**（在提示裡清楚地描述可用工具的規格，並指示模型應該依照什麼樣的格式輸出結構化的呼叫請求）**確實可以在一定程度上，讓一個本身具備足夠通用語言理解能力的模型展現出一定程度的 Function Calling 能力**；但實務上要讓這個能力達到**真正穩定、可靠，能夠被實際應用在正式的產品系統裡**的水準，通常還是需要**額外的、專門針對「判斷是否需要呼叫工具」、「正確地選擇該呼叫哪個工具」，以及「精準地生成符合格式要求的結構化參數」這幾個面向所做的專門訓練（通常是監督式微調階段的一部分）**。也就是說，**這是一個「提示工程可以帶來一定程度的基礎能力，但額外的專門訓練能夠顯著地提升這個能力的穩定性和可靠性」的情況**——目前主流的、被廣泛提供 Function Calling 功能的大型語言模型通常都是經過這種**額外專門訓練**的模型，而不是單純僅僅依靠提示工程技巧就宣稱具備這個能力。

**詳細解析**：這題考察是否理解 Function Calling 這種看似只是一種「提示技巧」的能力，實際上背後通常涉及**額外的、專門的模型訓練工作**，而不是單純地只靠巧妙的提示設計就能被憑空「喚出來」的能力。理解這個問題需要回顧前面（見 [[021-chain-of-thought.md]]）已經討論過的一個類似的區分——就像 Zero-shot CoT 這種單純透過提示引導就能一定程度地激發出模型原本在預訓練過程中已經隱含具備的推理能力一樣，**單純的提示工程**確實可以在一定程度上激發出一個通用語言模型原本就具備的、和「依照指定格式輸出結構化內容」相關的一般性能力（語言模型在預訓練資料裡很可能見過大量類似 JSON 這種結構化格式的文字內容，因此具備一定程度的模仿、生成這類格式化內容的基礎能力），只透過在提示裡清楚地說明「請依照以下格式輸出你的回答」，確實可以在一定程度上引導模型展現出初步的 Function Calling 行為；但是要讓這個能力達到**能夠被實際可靠地應用在正式產品系統上**的水準，單純的提示工程通常**並不足夠**——實務上會發現單純依靠提示工程的模型在 Function Calling 這件事情上容易出現各種不夠穩定的行為（例如即使使用者的請求明明需要呼叫某個工具，模型卻沒有正確地判斷出這一點，反而直接嘗試用自己內化的、可能並不準確或並不即時的知識去回答；或者即使正確地判斷出需要呼叫某個工具，生成的結構化參數卻存在格式不夠精確、或是容易出現一些難以預期的錯誤）。因應這種「單純提示工程不夠穩定可靠」的現實，主流的大型語言模型供應商通常會額外地在**監督式微調**這個訓練階段裡（見 [[005-pretraining-finetuning.md]]）**特別地準備大量專門針對「判斷是否需要呼叫工具」、「正確選擇該呼叫哪個工具」，以及「精準地生成符合格式要求的結構化參數」這幾個面向所設計的訓練資料，讓模型透過這種針對性、專門的訓練過程更加穩固、可靠地習得這些能力**。這種「額外的專門訓練」讓模型在實際面對各種多樣、複雜的真實使用情境時，能夠展現出遠比單純依靠提示工程所能達到的更穩定、更可靠的 Function Calling 行為。理解「單純透過精心設計的提示工程，確實可以在一定程度上讓一個具備足夠通用語言理解能力的模型展現出一定程度的Function Calling行為，這是因為模型在預訓練資料裡已經見過大量類似JSON這種結構化格式的內容，具備一定的模仿生成能力，但要讓這個能力達到真正穩定可靠、能被實際應用在正式產品系統的水準，通常還是需要在監督式微調階段額外準備大量專門針對判斷是否需要呼叫工具、正確選擇該呼叫哪個工具、以及精準生成符合格式要求的結構化參數這幾個面向所設計的訓練資料，目前主流提供這個功能的大型語言模型，通常都是經過這種額外專門訓練的模型」，展現你理解Function Calling這個能力背後，通常涉及超越單純提示工程的專門模型訓練工作。

**面試回答方式**：先給出核心答案——「單純透過提示工程，確實可以在一定程度上讓模型展現出一定程度的Function Calling行為，但要讓這個能力達到真正穩定可靠、能被實際應用在正式產品系統的水準，通常還是需要額外的專門訓練」。解釋為什麼提示工程能帶來一定基礎能力——「這是因為模型在預訓練資料裡已經見過大量類似JSON這種結構化格式的內容，具備一定程度模仿生成這類格式化內容的基礎能力，就像Zero-shot CoT單純透過提示引導也能一定程度激發模型原本隱含具備的推理能力一樣」。指出單純提示工程的侷限——「實務上會發現單純依靠提示工程的模型，容易出現各種不穩定行為，例如該呼叫工具時沒有正確判斷、或生成的參數格式不夠精確」。給出業界的實際做法——「因應這種不足，主流大型語言模型供應商通常會在監督式微調階段額外準備大量專門訓練資料，針對判斷是否需要呼叫工具、正確選擇工具、精準生成結構化參數這幾個面向做專門訓練，讓模型的Function Calling行為更加穩固可靠」。
