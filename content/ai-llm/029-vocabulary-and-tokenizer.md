# 題目

詞表大小怎麼定？tokenizer 的選擇會影響什麼？

## 核心答案

**詞表大小是一個明確的取捨**。**大詞表**——**同樣的文字用更少的 token 表示**（序列變短、推理更快、上下文能裝更多內容），但嵌入層與輸出層的參數量隨詞表線性成長，**而輸出層的 softmax 計算也變貴**。**小詞表**——**參數少，但同樣的文字要更多 token**。**現代模型多在 32K 到 256K 之間**，近年有往大走的趨勢，因為推理成本比參數成本更值得優化。

**tokenizer 的影響遠比多數人以為的大**，**主要在四個地方**：**多語言的公平性**（中文、日文在英文為主的詞表下，一個字可能要 2 到 3 個 token，等於同樣的內容付 2 到 3 倍的錢）、**數字與程式碼的處理**（數字被切碎會直接損害算術能力）、**上下文的有效長度**（同樣 128K token 對不同語言意味著不同的實際文字量）、**以及邊界效應**（同一個詞在不同上下文可能被切成不同的 token 序列）。

## 詳細解析

「多語言的 token 效率差異」是一個有實際成本後果的問題。以英文為主的 BPE 詞表下，英文平均約 4 個字元一個 token，而中文常常是 1 個字甚至半個字一個 token——於是同樣資訊量的中文內容，token 數可能是英文的兩倍以上。這直接體現在 API 費用、延遲、與上下文佔用上。近年的模型（如 Llama 3、Qwen）擴大詞表並針對多語言優化，正是為了解決這個問題——而評估一個模型是否適合中文場景時，「token 效率」應該與「品質」一起被量測。

「數字的切分方式影響算術能力」是一個很具體的例子。如果 `12345` 被切成 `123` + `45`，模型看到的不是五個數字而是兩個任意的符號——進位、對齊這些算術操作變得極難學習。現代模型多半採用「數字逐位切分」或「固定三位一組」的策略，**實測能顯著改善算術表現**。這說明 tokenizer 不只是預處理，它決定了模型能看到什麼樣的結構。

「token 邊界效應」會造成一些難以理解的行為。同一個詞在句首與句中可能被切成不同的 token（**有無前導空格**）——於是模型對它們的處理可能不一致。這也是「提示的結尾不要留空格」這類玄學建議的真正原因：留了空格會讓下一個 token 的分布偏離模型熟悉的模式。

**詞表無法在微調時輕易擴充**。加入新 token 意味著嵌入層與輸出層要增加對應的列——新加的向量是隨機初始化的，需要足夠的資料才能訓練好。所以「為特定領域加入專有名詞」通常收益不如預期，除非有大量該領域的資料做繼續預訓練。

## 面試回答方式

先給詞表大小的取捨（大詞表序列短但參數與輸出層計算貴）與現代的區間及趨勢。給 tokenizer 影響的四個地方。加分點有四個：多語言的 token 效率差異有實際成本後果——同樣資訊量的中文 token 數可能是英文的兩倍以上，直接體現在費用、延遲與上下文佔用，所以評估模型是否適合中文時「token 效率」應與品質一起量測；數字的切分方式影響算術能力——被切成任意符號後進位與對齊極難學習，這說明 tokenizer 決定了模型能看到什麼結構；**token 邊界效應**是「提示結尾不要留空格」這類建議的真正原因；以及**詞表無法在微調時輕易擴充**，所以為領域加專有名詞的收益通常不如預期。

## 講稿

詞表大小是一個明確的取捨。大詞表讓同樣的文字用更少的詞元表示，序列變短、推理更快、上下文能裝更多，但嵌入層跟輸出層的參數隨詞表線性成長。現代模型多在三萬到二十幾萬之間，近年往大走，因為推理成本比參數成本更值得優化。

分詞器的影響遠比多數人以為的大。我覺得最有實際後果的是多語言的效率差異。以英文為主的詞表下，英文平均四個字元一個詞元，而中文常常一個字就一個詞元甚至更多。同樣資訊量的中文，詞元數可能是英文的兩倍以上。這直接體現在費用、延遲跟上下文佔用上。所以評估一個模型適不適合中文場景時，詞元效率應該跟品質一起被量測。

第二個是數字的切分會影響算術能力。如果一串數字被切成兩個任意的符號，模型看到的就不是數字結構，進位跟對齊極難學習。現代模型多半改成逐位或固定三位一組，實測有顯著改善。這說明分詞器不只是預處理，它決定了模型能看到什麼樣的結構。

## 常見追問

### BPE、WordPiece 與 SentencePiece 差在哪？

**核心答案**：演算法細節不同，但核心思路都是「從字元開始，反覆合併最常出現的相鄰單元」。**BPE** 按**出現頻率**合併；**WordPiece** 按合併後對語言模型似然的提升選擇（更有理論依據但更慢）；**SentencePiece** 是一個**實作框架**而非演算法——它的關鍵貢獻是「直接在原始文字上操作，不預先按空格切詞」，於是能處理中文、日文這類沒有空格分隔的語言。

**詳細解析**：「不預先按空格切詞」這一點對多語言至關重要：傳統做法先用空格把文字切成詞再做子詞切分——**這對中文完全不適用**。SentencePiece 把空格當成一個普通字元（通常編碼成 `▁`），**讓整個流程對語言無關**，而且切分結果是完全可逆的（能精確還原原文，包括空格）——後者對程式碼與格式敏感的內容很重要。現在多數模型用的是「SentencePiece 框架 + BPE 或 Unigram 演算法」的組合。**至於 Unigram**：它從一個大詞表開始逐步刪除貢獻最小的 token，與 BPE 的自底向上相反——實測在多語言上略優，但差距不大。

**面試回答方式**：先指出**三者的核心思路相近**（從字元開始反覆合併），再給各自的差別，並強調 **SentencePiece 是框架而非演算法**。核心加分點是「不預先按空格切詞」對多語言至關重要——**傳統做法對中文完全不適用**，而把空格當普通字元讓流程語言無關且切分完全可逆，後者對程式碼與格式敏感的內容很重要。收在補充：現在多數模型用的是 SentencePiece 框架加 BPE 或 Unigram 的組合。

### 為什麼模型數不清一個詞裡有幾個字母？

**核心答案**：**因為它看不到字母**。模型的輸入是 token 而非字元——`strawberry` 可能是兩三個 token，而模型從未直接觀察過構成它的字母序列。它對「這個詞有幾個 r」的知識只能來自訓練資料裡「有人討論過這件事」的間接資訊，**而那顯然不可靠**。

**詳細解析**：這個例子的價值在於它揭示了「模型的能力邊界往往來自表示層而非推理能力」——不是模型笨，是它拿到的輸入裡根本沒有那個資訊。同類的問題還有：反轉字串、押韻判斷、字元級的編輯——這些都需要字元級的視角，而 token 化把它抹掉了。實務上的處理很簡單：讓模型呼叫工具（寫一行程式碼去數），**而不是期待它直接算出來**。更廣的啟示是「遇到模型表現異常差的任務時，先問它是不是根本看不到需要的資訊」——這個診斷角度能省下大量無效的提示調整。

**面試回答方式**：給根本原因——模型的輸入是 token 而非字元，它從未直接觀察過構成詞的字母序列。核心加分點是提煉出原則：模型的能力邊界往往來自表示層而非推理能力——不是笨，是輸入裡根本沒有那個資訊，並舉同類問題（反轉字串、押韻、字元級編輯）。收在實務處理（**讓它呼叫工具去數**）與更廣的啟示：遇到模型表現異常差的任務時先問它是不是根本看不到需要的資訊，這個診斷角度能省下大量無效的提示調整。

### 怎麼估算一段文字會用掉多少 token？

**核心答案**：用官方的 tokenizer 實測，不要用經驗公式。粗略的參考是英文約 1 個 token 對 4 個字元、中文約 1 個 token 對 1 到 1.5 個字——**但不同模型的差異很大**，而成本估算錯一倍是很常見的。生產系統應該在請求前用 tokenizer 計算實際數量，用於預算控制、上下文截斷、與成本歸屬。

**詳細解析**：「在請求前計算」有三個實際用途：**避免超出上下文限制而失敗**（與其被 API 拒絕，不如自己先截斷或分段）、**成本預估與配額控制**（在昂貴的請求送出前就知道它多貴）、**以及選擇模型**（同一個請求在不同模型上的 token 數不同，成本比較必須基於實際數量而非字數）。另一個容易忽略的是「輸出 token 通常比輸入貴」——多數 API 的輸出定價是輸入的三到五倍，所以控制輸出長度（用 `max_tokens` 與提示中的長度要求）往往比壓縮輸入更能省錢。這個成本結構的認知，比任何提示優化技巧都更直接地影響帳單。

**面試回答方式**：主張**用官方 tokenizer 實測而非經驗公式**，給出粗略參考但強調差異很大。加分點是**在請求前計算的三個用途**（避免超限、成本預估與配額、模型選擇）。核心加分點是指出**輸出 token 通常比輸入貴三到五倍**——所以控制輸出長度往往比壓縮輸入更能省錢，而這個成本結構的認知比任何提示優化技巧都更直接地影響帳單。
