# 題目

RAG 系統有哪些典型的失敗模式？怎麼評估它？

## 核心答案

六個典型失敗模式，而它們分布在不同的環節。

**檢索沒召回**——正確片段根本沒進候選（切分或檢索問題）。**召回但排序太後**——在第 30 名而你只取前 5（需要重排）。**檢索到相關但不足以回答**——片段缺少關鍵細節（切分粒度問題）。**模型忽略了給的內容**——上下文裡有答案但模型用自己的先驗回答（尤其當檢索內容與模型的訓練知識衝突時）。**模型過度依賴檢索內容**——檢索到錯誤或過時的資訊，模型照單全收。**無法回答時仍然編造**——沒有「找不到就說不知道」的行為。

**評估要分層對應**。**檢索層**：召回率@K、MRR。**生成層**：**忠實度**（答案是否有出處支撐）、**答案相關性**、**以及「該拒答時有沒有拒答」**。RAGAS 這類框架提供了這幾個指標的自動化實作。

## 詳細解析

「模型忽略檢索內容」是最隱蔽也最危險的一種：外表看起來系統正常運作（有檢索、有回答），而答案其實來自模型的內部知識——於是你以為的「基於公司文檔的回答」實際上是模型在編。**檢測的方法是「忠實度評估」**：逐句檢查答案中的每個事實陳述能否在檢索到的片段中找到支撐——**這可以用另一個模型自動化**。而緩解的方式是在提示中明確要求「只根據提供的內容回答，找不到就說明」並要求引用出處——引用要求本身就是一種約束，它讓模型更難編造。

「該拒答時要拒答」是產品品質的關鍵而評估中常被遺漏。多數評估集只有「有答案的問題」——而真實使用中大量問題是文檔裡沒有的。所以評估集必須包含「知識庫中確實沒有答案」的問題，並檢查系統是否正確地說「我找不到相關資訊」。沒有這一類測試，你無法知道系統的幻覺率——而那往往是使用者最不能容忍的失敗。

「建立評估集」是 RAG 專案最值得的前期投入。做法是從真實的使用者問題中抽樣，人工標註出正確的答案與應該被檢索到的片段——幾十到一兩百條就足以支撐迭代。沒有它，所有的優化都是憑感覺：換一個切分策略，你根本不知道是變好還是變差。而有了它，每一次改動都能在幾分鐘內得到量化的回饋——這個從「憑感覺」到「有數字」的轉變，是 RAG 專案能不能持續改進的分水嶺。

**線上評估同樣重要**：記錄「使用者是否追問」「是否重新表述問題」「是否點擊了引用來源」——這些行為信號比任何離線指標更接近真實的滿意度。

## 面試回答方式

先給六個失敗模式並指出它們分布在不同環節，再給分層的評估指標。加分點有四個：「模型忽略檢索內容」最隱蔽也最危險——外表看起來正常，答案卻來自模型的內部知識，檢測靠逐句的忠實度評估，緩解靠明確要求只根據提供內容回答並引用出處，而引用要求本身就是一種讓模型更難編造的約束；「該拒答時要拒答」在評估中常被遺漏——評估集必須包含知識庫裡沒有答案的問題，否則你無法知道系統的幻覺率；建立評估集是最值得的前期投入——幾十到一兩百條就夠，沒有它所有優化都是憑感覺，而從「憑感覺」到「有數字」是能不能持續改進的分水嶺；以及線上的行為信號比離線指標更接近真實滿意度。

## 講稿

失敗模式我會分六種，而且它們分布在不同環節。檢索沒召回、召回但排序太後、檢索到相關但不足以回答、模型忽略了給的內容、模型對錯誤內容照單全收、還有無法回答時仍然編造。

其中我認為最隱蔽也最危險的是模型忽略檢索內容。外表看起來系統正常運作，有檢索也有回答，而答案其實來自模型的內部知識。於是你以為的基於公司文檔的回答，實際上是模型在編。

檢測的方法是忠實度評估，逐句檢查答案裡的每個事實陳述能不能在檢索到的片段中找到支撐。緩解的方式是明確要求只根據提供的內容回答，並且要求引用出處。引用要求本身就是一種約束，它讓模型更難編造。

另一個常被遺漏的是該拒答時要拒答。多數評估集只有有答案的問題，而真實使用中大量問題是文檔裡沒有的。評估集必須包含這一類，否則你根本不知道系統的幻覺率。

而最值得的前期投入是建立評估集。幾十到一兩百條就夠。沒有它，換一個切分策略你根本不知道是變好還是變差。

## 常見追問

### 怎麼低成本地建立評估集？

**核心答案**：**三步**。**一、從真實流量抽樣問題**（沒有流量就請領域專家寫，或者從文檔反向生成）。二、用強模型生成候選答案與應引片段，再由人工快速校對（**校對比從零撰寫快得多**）。**三、刻意加入負面案例**——知識庫裡沒有答案的問題、模糊的問題、以及應該拒絕的問題。

**詳細解析**：「從文檔反向生成問題」是冷啟動時最實用的技巧：讓模型讀一個片段並生成「這個片段能回答什麼問題」——於是你自動得到了「問題加正確片段」的配對，而那正是檢索評估需要的標註。它的限制是生成的問題往往比真實問題更「書面」、更貼近文檔的用詞——而真實使用者的提問更口語、更模糊。所以這種自動生成的評估集會系統性地高估檢索效果：因為問題與文檔的用詞太接近，檢索當然容易。緩解的做法是「讓模型用不同的口吻改寫問題」並混入真實流量的樣本。知道這個偏誤的存在，比擁有一個看起來很漂亮的評估分數重要得多。

**面試回答方式**：給三步流程並強調**校對比從零撰寫快得多**與**刻意加入負面案例**。核心加分點是**從文檔反向生成問題**這個冷啟動技巧與它的**系統性偏誤**：生成的問題用詞太貼近文檔，會高估檢索效果，而真實使用者的提問更口語更模糊。收在緩解與判斷：讓模型改寫口吻並混入真實樣本，而知道這個偏誤的存在比擁有一個漂亮的分數重要得多。

### 檢索到的內容互相矛盾怎麼辦？

**核心答案**：先在資料層解決，再在提示層處理。**資料層**——矛盾多半來自「過時的文檔沒有下架」，所以要有版本與有效期的元資料，並在檢索時過濾掉失效的。**提示層**——明確告訴模型「如果提供的內容互相矛盾，請指出矛盾並優先採用較新的版本」，並在每個片段上標註來源與日期讓它能判斷。

**詳細解析**：「讓模型看到元資料」是一個簡單卻常被忽略的做法：多數 RAG 實作只把片段的正文放進上下文——而如果同時附上「來源文件、章節、最後更新日期」，模型就有了判斷可信度與時效性的依據，也能在回答時給出更有用的引用。**成本只是每個片段多幾十個 token。** 更根本的是「矛盾往往是知識庫治理的問題而非檢索的問題」：同一件事在三份文檔裡有三種說法，那麼無論檢索多準，答案都不可靠。所以 RAG 專案的一部分價值其實是「暴露了知識庫本身的品質問題」——而處理它需要業務方參與，不是純技術能解決的。能指出這一點，通常表示真的落地過而不只是搭過 demo。

**面試回答方式**：給資料層與提示層的處理。核心加分點是**讓模型看到元資料**——附上來源、章節、最後更新日期讓它有判斷可信度與時效性的依據，**成本只是每個片段多幾十個 token**。真正的深度在最後：矛盾往往是知識庫治理的問題而非檢索的問題，同一件事有三種說法時無論檢索多準答案都不可靠，所以 RAG 的一部分價值是暴露了知識庫本身的品質問題，而處理它需要業務方參與。

### RAG 與微調怎麼配合？

**核心答案**：**RAG 提供知識，微調調整行為**——它們解決不同的問題，通常應該同時用。需要頻繁更新、需要引用來源、資料量大的知識用 RAG；輸出格式、專業術語的使用習慣、以及「怎麼使用檢索到的內容」這類行為用微調。一個常見且有效的組合是「微調模型讓它更擅長基於上下文回答與正確拒答，知識全部來自 RAG」。

**詳細解析**：「微調讓模型更會用 RAG」是一個容易被忽略的方向：通用模型並沒有專門訓練過「在提供的片段與自己的知識衝突時該信誰」——而用你的領域資料做一輪微調，明確示範「只用提供的內容、找不到就說明、並引用出處」，**能顯著降低幻覺率**。這比反覆調整提示更根本，因為它改變的是模型的預設行為而非每次都要提醒。 反過來，「用微調灌輸知識」通常是一個糟糕的選擇：知識更新意味著重新訓練、無法引用來源、而且模型對微調學到的知識同樣會產生幻覺——**這三個缺點都是 RAG 天然沒有的**。能清楚說出「用 RAG 管知識、用微調管行為」這條分工原則，比討論任何細節都更能展現判斷。

**面試回答方式**：給分工原則（**RAG 提供知識、微調調整行為**）與各自適用的內容。核心加分點是**微調讓模型更會用 RAG** 這個容易被忽略的方向——明確示範只用提供內容、找不到就說明、並引用出處，能顯著降低幻覺率，比反覆調整提示更根本，因為它改變的是預設行為。收在反面：**用微調灌輸知識通常很糟**——更新要重訓、無法引用來源、而且同樣會幻覺，**這三個缺點都是 RAG 天然沒有的**。
