# 題目

一個 LLM 應用該選哪個模型？怎麼控制成本？

## 核心答案

選型的順序應該是「先確定任務的難度下限，再往上找最便宜的能做到的」——而不是先選最強的再想辦法省錢。

**具體流程**：用最強的模型建立「品質上限」的參考（先確認任務本身可行）、再用你的評估集依序測試更便宜的模型、找到「品質仍可接受的最便宜那一個」。很多任務用便宜十倍的模型就能達到 95% 的品質——**而那 5% 的差距對產品未必重要**。

成本控制的四個槓桿，按效益排序。**一、模型路由**——按難度把請求分給不同的模型；**這通常是收益最大的一項**。**二、控制輸出長度**——**輸出 token 比輸入貴三到五倍**。**三、提示快取**——**固定前綴不重複計算**。**四、批次與非同步**——能接受延遲的任務用批次 API，通常便宜一半。

## 詳細解析

**「先確定難度下限」為什麼重要**：從最強模型開始的團隊往往就停在那裡了——**因為它能用，沒有動力再試**。而如果一開始就建立「用便宜模型測試」的流程，你會發現很多任務根本不需要旗艦模型。這個順序的差異，在規模化之後就是幾倍到幾十倍的成本差距。

「模型路由」的實作比想像中簡單：用一個小模型或分類器判斷請求的複雜度，簡單的走便宜模型、困難的走強模型。更省事的做法是「先用便宜模型試，不滿意再升級」（cascade）——用一個信心判斷或校驗步驟決定要不要重試。後者的好處是不需要事先分類，代價是困難請求要跑兩次。而收益的計算很直觀：如果 80% 的請求可以用便宜十倍的模型處理，總成本降到約 28%——這比任何提示層的優化都大一個數量級。

「小模型的能力邊界正在快速上移」是選型時要持續重估的事實。今天需要旗艦模型的任務，半年後可能中型模型就夠——所以選型不應該是一次性決定，而應該是一個定期重跑的評估流程。把評估集自動化的價值在這裡再次體現：換一個模型只需要跑一遍就知道行不行。

**「不要只看單價」**：便宜模型可能需要更長的提示（更多範例）、更多的重試、或者更多的後處理——實際的每次任務成本可能沒有便宜那麼多。正確的比較單位是「每完成一次任務的總成本」而非「每千 token 的價格」。

## 面試回答方式

先給選型的順序原則——先確定任務的難度下限，再往上找最便宜的能做到的，並給具體流程。給四個成本槓桿並指出**模型路由通常收益最大**。加分點有四個：**先確定難度下限為什麼重要**——從最強模型開始的團隊往往就停在那裡，因為它能用、沒有動力再試，而這個順序差異在規模化後就是幾倍到幾十倍；**路由的兩種實作**（事先分類 vs 級聯重試）與**收益計算**（80% 走便宜十倍的模型，總成本降到約 28%）；小模型的能力邊界在快速上移——選型應該是定期重跑的評估流程而非一次性決定；以及**不要只看單價**——正確的比較單位是「每完成一次任務的總成本」。

## 講稿

選型的順序應該是先確定任務的難度下限，再往上找最便宜的能做到的，而不是先選最強的再想辦法省錢。

這個順序很重要。從最強模型開始的團隊往往就停在那裡了，因為它能用，沒有動力再試。而如果一開始就建立用便宜模型測試的流程，你會發現很多任務根本不需要旗艦模型。這個差異在規模化之後就是幾倍到幾十倍的成本差距。

成本控制我認為收益最大的是模型路由。用一個小模型判斷請求的複雜度，簡單的走便宜模型，困難的走強模型。或者更省事的做法是先用便宜的試，不滿意再升級。收益的計算很直觀，如果八成的請求可以用便宜十倍的模型，總成本降到大約兩成八，這比任何提示層的優化都大一個數量級。

第二是控制輸出長度，因為輸出詞元比輸入貴三到五倍。第三是提示快取。第四是能接受延遲的任務走批次介面，通常便宜一半。

最後一點，不要只看單價。便宜模型可能需要更長的提示、更多重試、更多後處理。正確的比較單位是每完成一次任務的總成本。

## 常見追問

### 開源模型與商業 API 怎麼選？

**核心答案**：**看四個維度**。**能力差距**——在你的具體任務上實測，而不是看排行榜；很多垂直任務上開源模型已經足夠。**部署成本**——自建的盈虧平衡點取決於利用率。**資料與合規**——資料不能出境或不能給第三方時，開源自建是唯一選項。**可控性**——開源模型可以微調、可以固定版本、不受供應商政策變動影響。

**詳細解析**：「可控性」在生產環境的價值常被低估：商業 API 的模型會被更新或棄用——而你的提示是針對特定行為調校的，一次靜默的更新可能讓你的系統在毫無預警的情況下退化。開源模型讓你完全掌握「什麼時候升級」。但代價同樣真實：你要自己負責安全對齊、自己處理濫用防護、自己跟上推理框架的演進——**這些在商業 API 上是內建的**。所以判斷的關鍵不是「哪個更好」，而是「你的團隊願意承擔哪一類工作」：是願意付更高的單價換取免維運，還是願意投入工程換取控制權與更低的邊際成本。這個問題的答案取決於團隊規模與階段，而不是技術優劣。

**面試回答方式**：給四個維度並強調能力差距要在你的具體任務上實測而非看排行榜。核心加分點是**可控性的價值常被低估**——商業 API 的模型會被更新或棄用，而你的提示是針對特定行為調校的，一次靜默更新可能讓系統無預警退化。收在誠實的取捨：開源要自己負責安全對齊、濫用防護、跟上框架演進，所以關鍵不是哪個更好而是「你的團隊願意承擔哪一類工作」——這取決於團隊規模與階段而非技術優劣。

### 怎麼判斷一個任務「需要多強的模型」？

**核心答案**：**看三個特徵**。**推理深度**——需要幾步推導？單步的分類與抽取用小模型就夠，多步的規劃與數學需要強模型。**知識廣度**——需不需要模型內建的世界知識？如果知識都由 RAG 提供，模型的知識量就沒那麼重要。**輸出的精確度要求**——格式錯了就完全不能用，還是有點瑕疵也能接受。

**詳細解析**：「知識由 RAG 提供時可以用小得多的模型」是一個很實用的判斷：模型不需要記得所有事實，只需要有「讀懂提供的內容並組織成答案」的能力——而那個能力在中小模型上已經相當好。所以一個設計良好的 RAG 系統，往往可以用比預期小很多的模型達到滿意的效果——這是「用架構換模型能力」的典型例子。反過來，如果系統嚴重依賴模型的內建知識，那就只能用大模型，而且要承受幻覺的風險。這個連結說明了「架構選擇與模型選擇是耦合的」——不應該先定模型再設計架構，而應該一起考慮。

**面試回答方式**：給三個特徵（推理深度、知識廣度、輸出精確度要求）。核心加分點是知識由 RAG 提供時可以用小得多的模型——模型只需要「讀懂提供的內容並組織成答案」，而那個能力在中小模型上已經相當好，所以設計良好的 RAG 往往能用比預期小很多的模型。收在原則：這是「用架構換模型能力」的典型例子，而它說明架構選擇與模型選擇是耦合的，不應該先定模型再設計架構。

### 成本突然暴增怎麼排查？

**核心答案**：**按維度拆解**：請求數變了嗎？平均輸入長度變了嗎？平均輸出長度變了嗎？模型版本或路由比例變了嗎？ 最常見的原因是「輸出長度失控」與「重試風暴」——前者可能來自一次提示調整，後者來自下游錯誤導致的大量重試。

**詳細解析**：「重試風暴」在 LLM 應用中特別危險，因為每次重試都是真金白銀：一個解析失敗導致的自動重試，在下游持續故障時會變成無限循環的燒錢。所以必須有「每個請求的最大重試次數」與「全局的成本熔斷」——當某個時間窗內的花費超過閾值時直接停止或降級。這與傳統服務的限流是同一個思路，但代價更直接。 而預防的關鍵是「把成本納入日常監控並設定先行指標」：每千次請求的成本、平均輸出長度、重試率——這三個指標的異常都會在帳單反映之前幾天就出現。很多團隊只在月底看帳單，那時已經燒掉了幾週的錢——而建立這些指標的成本很低，回報卻是立即的。

**面試回答方式**：給拆解的維度並指出最常見的是輸出長度失控與重試風暴。核心加分點是說明重試風暴在 LLM 應用中特別危險，因為每次重試都是真金白銀——下游持續故障時會變成無限循環的燒錢，所以必須有最大重試次數與全局的成本熔斷。收在預防：把成本納入日常監控並設先行指標（每千次請求成本、平均輸出長度、重試率），它們都會在帳單反映之前幾天就出現異常——而很多團隊只在月底看帳單，那時已經燒掉幾週的錢。
