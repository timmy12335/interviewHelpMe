# 題目

為什麼 LLM 推理不能用傳統的靜態批次？continuous batching 解決了什麼？

## 核心答案

**傳統靜態批次的問題是「必須等最慢的那個」**：把 N 個請求湊成一批一起跑——**但每個請求的輸出長度不同**，**生成 10 個 token 的請求必須等生成 500 個 token 的那個跑完，整批才能返回**。**於是 GPU 有大量時間在為已經完成的請求做無意義的計算**，**而新來的請求只能排隊等下一批**。

**continuous batching（連續批次，又稱 in-flight batching）的做法是「以 token 為調度單位而非以請求」**：**每生成一步之後就檢查——完成的請求立刻返回並移出批次，等待中的請求立刻補進來**。**批次的組成是動態變化的。**

**收益非常大**：**實測吞吐提升往往是幾倍到十幾倍**，**同時平均延遲也下降**（因為請求不用等整批）。**這是現代推理框架（vLLM、TGI、TensorRT-LLM）的標配。**

## 詳細解析

**「為什麼能一邊完成一邊補入」需要 decode 階段的特性支撐**：解碼時每個請求各自維護自己的 KV Cache，**而模型的前向計算只是把這些請求的當前 token 拼成一個批次一起算**——**它們之間並沒有耦合**。**所以任意時刻加入或移出一個請求，對其他請求完全沒有影響**。**這個「請求之間獨立」的性質是連續批次成立的基礎。**

**排隊與搶佔是它必須處理的複雜性**。顯存有限——**當正在服務的請求佔滿了 KV Cache 空間，新請求只能等待**。**更棘手的是「已經在跑的請求需要更多空間」**（**每生成一個 token，KV Cache 就成長一點**）——**空間不足時必須搶佔某個請求**：**要嘛把它的 KV Cache 換出到 CPU 記憶體（swap），要嘛直接丟棄並在之後重算（recompute）**。**後者聽起來浪費，但因為 prefill 是計算受限而且很快，實測上往往比換出換入更划算**。

**「prefill 與 decode 的混合調度」是效能調校的關鍵**。純粹按到達順序處理會讓一個長提示的 prefill 阻塞所有解碼——**所以框架會做分塊 prefill，把它切成小塊與 decode 步驟交錯**。**調校的參數是「每步允許的 prefill token 預算」**：**設大則 TTFT 好但正在解碼的請求會卡頓，設小則相反**——**這是一個直接影響使用者體驗的取捨，應該按產品的特性決定**。

**吞吐與延遲的取捨仍然存在**：**增大最大批次能提高吞吐，但每步的計算量變大，單個請求的 TPOT 會略微變差**。**在容量規劃時應該明確目標**——**是要最大化每秒處理的 token 數（成本導向），還是要保證每個請求的生成速度（體驗導向）**。

## 面試回答方式

先給靜態批次的問題——**必須等最慢的那個，GPU 為已完成的請求做無意義計算，新請求只能等下一批**。給連續批次的核心（**以 token 為調度單位，完成就移出、等待的立刻補入**）與實測收益。加分點有四個：**為什麼能一邊完成一邊補入**——**解碼時請求之間沒有耦合，各自維護 KV Cache**，**這個獨立性是它成立的基礎**；**搶佔的處理**——**空間不足時換出到 CPU 或直接丟棄重算**，**而重算聽起來浪費但因為 prefill 快，實測往往更划算**；**prefill 與 decode 的混合調度**——**每步的 prefill token 預算是直接影響體驗的取捨**；以及**吞吐與延遲的取捨仍然存在**，**容量規劃要明確是成本導向還是體驗導向**。

## 講稿

傳統靜態批次的問題是必須等最慢的那個。把幾個請求湊成一批一起跑，但每個請求的輸出長度不同，生成十個詞元的請求必須等生成五百個的那個跑完。於是加速卡有大量時間在為已經完成的請求做無意義的計算，而新來的請求只能排隊等下一批。

連續批次的做法是以詞元為調度單位而不是以請求。每生成一步之後就檢查，完成的立刻返回並移出，等待中的立刻補進來。批次的組成是動態變化的。實測吞吐提升往往是幾倍到十幾倍，而且平均延遲也下降。

它能成立是因為解碼時請求之間沒有耦合。每個請求各自維護自己的快取，模型的前向只是把它們的當前詞元拼成一批一起算。所以任意時刻加入或移出對其他請求完全沒有影響。

它必須處理的複雜性是搶佔。顯存有限，而已經在跑的請求每生成一個詞元快取就成長一點。空間不足時要嘛把某個請求換出到主記憶體，要嘛直接丟棄之後重算。後者聽起來浪費，但因為預填充是計算受限而且很快，實測往往比換出換入更划算。

## 常見追問

### 怎麼設定最大批次與最大序列數？

**核心答案**：**由顯存決定，而算式是明確的**：**可用顯存 = 總顯存 − 模型權重 − 啟動值與框架開銷**；**剩下的除以「單個請求的 KV Cache 大小 × 預期序列長度」就是能並發的請求數**。**框架通常有一個 `gpu_memory_utilization` 參數控制預留比例**（**設太高會在尖峰時 OOM，設太低則浪費**），**0.85 到 0.9 是常見的起點**。

**詳細解析**：**「預期序列長度」是這個計算裡最不確定的一項**，**而它決定了策略**：**如果保守地按最大長度規劃，並發數會很低而多數時候顯存閒置**；**如果按平均長度規劃，偶爾會需要搶佔**。**PagedAttention 讓後者變得可行**——**因為它按需分配頁面而非預留整段**，**於是「按平均規劃、偶爾搶佔」成為更好的策略**。**另一個實用的建議是「量測而非估算」**：**用真實的流量分布做壓力測試，觀察吞吐與 p99 延遲隨並發數的曲線**——**曲線的拐點就是合理的上限**，**而那個數字往往與紙上計算有明顯差距**。

**面試回答方式**：給明確的算式（總顯存減權重減開銷，除以單請求的 KV Cache）與 `gpu_memory_utilization` 的合理起點。核心加分點是指出**「預期序列長度」最不確定且決定了策略**：**按最大長度規劃並發低、按平均規劃偶爾要搶佔**，**而 PagedAttention 讓後者可行因為它按需分配頁面**。收在建議：**量測而非估算**——**用真實流量分布壓測，看吞吐與 p99 延遲隨並發的曲線，拐點就是合理上限**，**而那往往與紙上計算有明顯差距**。

### 多個請求共享前綴時有額外的優化嗎？

**核心答案**：**有，叫做「前綴共享」或 automatic prefix caching**。如果多個請求都以同一個系統提示或少樣本範例開頭——**那段的 KV Cache 只需要計算並儲存一份，所有請求共用**。**這同時省下了 prefill 的計算與 KV Cache 的顯存**。**在「同一個系統提示服務大量請求」的場景（幾乎所有產品都是）收益非常顯著。**

**詳細解析**：**它的實作依賴 PagedAttention 的分頁機制**：**KV Cache 被切成固定大小的頁，相同內容的頁可以被多個請求引用**——**這與作業系統的寫時複製（copy-on-write）是完全一樣的思路**。**當請求開始分歧時，才各自分配新的頁**。**收益的量化很直觀**：**如果系統提示是 2000 token 而使用者輸入平均 100 token，那麼前綴共享省下了 95% 的 prefill 計算**。**這也給出一個提示設計的建議：把長而固定的內容盡量前置並保持穩定**——**每次微調系統提示都會讓所有快取失效**，**所以「頻繁 A/B 測試系統提示」的成本比想像中高**。

**面試回答方式**：給機制與收益場景。核心加分點是說明**實作依賴分頁機制，相同內容的頁被多個請求引用**，**與作業系統的寫時複製是完全一樣的思路**。給出量化（**系統提示 2000 token、使用者輸入 100 token 時省下 95% 的 prefill**）並收在設計建議：**把長而固定的內容前置並保持穩定**——**每次微調系統提示都會讓所有快取失效，所以頻繁 A/B 測試系統提示的成本比想像中高**。

### 推理服務怎麼做自動擴縮？

**核心答案**：**不能用 CPU 使用率，要用「佇列深度」或「等待中的請求數」**。GPU 的使用率在解碼階段本來就不高（記憶體受限）——**用它做擴縮信號會完全誤判**。**合理的指標是**：**排隊等待的請求數**、**TTFT 的 p95**、**或者「正在服務的序列數佔容量的比例」**。

**詳細解析**：**LLM 服務的擴縮有一個特殊困難：擴容非常慢**。**新實例要拉取一個幾十 GB 的模型映像、載入權重到顯存、預熱 CUDA 核心**——**整個過程可能是幾分鐘**。**所以反應式的擴縮幾乎來不及應對突發流量**。**實務上的做法是三管齊下**：**預留一定的緩衝容量**（接受平時的閒置）、**按流量規律預先擴容**（如果有日內模式）、**以及在容量不足時降級而非讓延遲爆炸**（**排隊並明確告知等待時間，或者路由到更小的模型**）。**「承認擴容慢並設計降級」比追求更快的擴縮更務實**——**而這與傳統無狀態服務的擴縮思路有本質區別**。

**面試回答方式**：先指出**不能用 GPU 使用率，因為解碼階段本來就記憶體受限**，給出合理的指標。核心加分點是說明**LLM 服務擴容非常慢**——**拉取幾十 GB 映像、載入權重、預熱核心，可能要幾分鐘**，**所以反應式擴縮幾乎來不及**。收在三管齊下的務實做法（預留緩衝、按規律預先擴容、容量不足時降級而非讓延遲爆炸），並指出**「承認擴容慢並設計降級」比追求更快的擴縮更務實**。
