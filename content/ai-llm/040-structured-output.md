# 題目

怎麼讓模型穩定地輸出合法的 JSON？約束解碼是什麼原理？

## 核心答案

**三個層次，可靠性遞增。**

**提示層**——**在提示中要求「只輸出 JSON」並給範例**。**最簡單，但沒有保證**——**模型仍可能加上前後的說明文字、漏掉引號、或者截斷**。

**校驗與重試層**——**解析失敗就把錯誤訊息回饋給模型並重試**。**顯著提升成功率，代價是延遲與成本**（**失敗的那次全部白費**）。

**約束解碼層**——**在每一步採樣時，用一個狀態機或語法把「不合法的 token」的機率直接設為零**——**於是輸出在語法上必然合法**。**這是唯一有保證的方法**，**也是各家 API 的「JSON mode」與「structured output」背後的機制**。

**而「語法合法」不等於「語意正確」**——**約束解碼保證你能解析，不保證欄位的值是對的**，**業務層的驗證仍然必要。**

## 詳細解析

**約束解碼的原理是「把 JSON Schema 編譯成一個有限狀態機」**：在生成的每一步，**狀態機知道「當前位置允許哪些字元」**——**例如在一個字串內部，除了跳脫序列以外的引號是不合法的**；**在一個列舉欄位上，只有那幾個預定義的值是合法的**。**把不合法的 token 的 logits 設為負無窮，softmax 之後它們的機率就是零**。**實作上的難點是「token 與字元的不對齊」**——**一個 token 可能跨越狀態機的多個狀態**，**所以要預先計算「每個狀態下哪些 token 是可行的」**，**這通常用前綴樹加快取來實作**。

**「約束會影響品質」是一個需要知道的副作用**：強制模型走某條路徑，**可能把它推離它本來想表達的內容**——**尤其當 schema 與模型的自然傾向衝突時**（例如強制它先輸出結論再輸出理由，而它需要先推理）。**緩解的做法是「讓 schema 的欄位順序符合推理順序」**——**把 `reasoning` 欄位放在 `answer` 之前**，**讓模型有機會先想再答**。**這個小調整對複雜任務的準確率影響很明顯，而它幾乎沒有成本。**

**「用工具呼叫還是結構化輸出」是一個常見的選擇**。**兩者的底層機制相近，區別在語意**：**工具呼叫表達「我要執行一個動作」，結構化輸出表達「我要回傳一份資料」**。**如果只是要一份結構化的結果，用 structured output 更直接**；**而如果需要模型在多個動作之間選擇，工具呼叫的語意更合適**。

**Schema 的設計本身影響成功率**：**過深的巢狀、過多的欄位、以及模糊的欄位名都會降低品質**。**實用的原則是「扁平優於巢狀、少量必填優於大量選填、欄位名要自我說明」**——**因為模型是靠欄位名理解要填什麼的，`t` 與 `transaction_type` 的差別很大**。

## 面試回答方式

先給三個層次（提示、校驗重試、約束解碼）與各自的保證程度，強調**約束解碼是唯一有保證的**，並補上**「語法合法不等於語意正確」**。加分點有四個：**約束解碼的原理**——**把 Schema 編譯成有限狀態機，每步把不合法 token 的 logits 設為負無窮**，**難點是 token 與字元的不對齊，要預先計算每個狀態下的可行 token**；**約束會影響品質**——**schema 與模型的自然傾向衝突時會把它推離**，**緩解是讓欄位順序符合推理順序，把 reasoning 放在 answer 之前**，**幾乎沒有成本卻明顯改善準確率**；**工具呼叫與結構化輸出的語意區別**；以及**Schema 設計影響成功率**——**扁平優於巢狀、欄位名要自我說明，因為模型是靠欄位名理解要填什麼**。

## 講稿

有三個層次，可靠性遞增。

第一層是在提示裡要求只輸出 JSON。最簡單但沒有保證，模型仍可能加上前後說明或者漏掉引號。第二層是解析失敗就把錯誤回饋給模型重試，成功率提升但失敗那次的成本全部白費。第三層是約束解碼，在每一步採樣時把不合法的詞元機率直接設為零，於是輸出在語法上必然合法。這是唯一有保證的方法。

原理是把結構描述編譯成一個有限狀態機。生成的每一步，狀態機知道當前位置允許哪些字元。實作的難點是詞元跟字元不對齊，一個詞元可能跨越多個狀態，所以要預先算出每個狀態下哪些詞元可行。

有一個副作用要知道。約束會影響品質，因為強制模型走某條路徑可能把它推離本來想表達的內容。緩解的方式是讓欄位順序符合推理順序，把推理欄位放在答案欄位前面，讓模型先想再答。這個調整幾乎沒有成本，但對複雜任務的準確率影響很明顯。

最後，語法合法不等於語意正確。約束解碼保證你能解析，不保證值是對的，業務層的驗證仍然必要。

## 常見追問

### 模型輸出的欄位值不對怎麼辦？

**核心答案**：**分三種情況處理**。**格式對但值錯**（例如日期格式對但日期是錯的）——**這是模型能力問題，要靠更好的提示、範例、或更強的模型**。**值不在允許範圍**——**用 enum 約束直接在解碼層排除**。**值前後不一致**（例如總額與明細對不上）——**用業務規則校驗並要求重新生成，或者乾脆不讓模型計算，改用程式碼算**。

**詳細解析**：**「不要讓模型做它不擅長的事」是最後那一項的核心**：**加總、日期計算、單位換算這些確定性的運算，交給程式碼比交給模型可靠一百倍**——**而模型應該負責的是「從非結構化文字中抽取出結構」這件它擅長的事**。**一個好的設計是「讓模型只輸出原始的抽取結果，所有衍生的計算由後續程式碼完成」**——**這同時提升了正確性與可除錯性（你能看到中間結果）**。**這個「劃清模型與程式碼的分工」的判斷，往往比任何提示技巧更能決定系統的可靠性**——**而它也是評估一個 LLM 應用設計好壞的一個實用切入點**。

**面試回答方式**：分三種情況給處理方式。核心加分點是**「不要讓模型做它不擅長的事」**——**加總、日期計算、單位換算這些確定性運算交給程式碼比交給模型可靠一百倍**，**模型應該負責的是從非結構化文字抽取結構**。收在設計原則：**讓模型只輸出原始抽取結果，衍生計算由程式碼完成**，**同時提升正確性與可除錯性**，**而這個劃清分工的判斷往往比任何提示技巧更能決定系統的可靠性**。

### 為什麼有時候加了 JSON mode 反而變差？

**核心答案**：**因為它剝奪了模型「先思考再回答」的空間**。純 JSON 輸出意味著**第一個 token 就是 `{`**——**模型沒有機會先寫下推理過程**。**而對需要推理的任務，那個推理過程正是準確率的來源**。**解法是在 schema 裡保留一個推理欄位，或者用兩階段：先自由生成推理，再要求結構化的最終答案。**

**詳細解析**：**這個現象再次印證了「生成的 token 就是模型的計算」**：**限制輸出格式等於限制了它能用的計算量**。**兩階段的做法（先推理、再抽取）在複雜任務上效果最好，代價是兩次呼叫的延遲與成本**；**而單次呼叫加推理欄位是一個很好的折衷**——**只要那個欄位在 schema 中排在答案之前**。**另一個實用的觀察是「不是所有任務都需要推理空間」**：**單純的資訊抽取（從一段文字中找出人名與日期）幾乎不受影響**，**而需要判斷或計算的任務影響很大**。**所以「要不要留推理欄位」應該按任務性質決定，而不是一概而論**——**而能做出這個區分，說明理解了背後的機制而不只是記住了現象**。

**面試回答方式**：給根本原因——**它剝奪了先思考再回答的空間，第一個 token 就是大括號**，並指出**對需要推理的任務，那個推理過程正是準確率的來源**。核心加分點是連結到**「生成的 token 就是模型的計算」**——**限制輸出格式等於限制了可用的計算量**。給兩種解法（兩階段、schema 內的推理欄位放在答案前）並收在區分：**單純的資訊抽取幾乎不受影響，需要判斷或計算的任務影響很大**，**所以應該按任務性質決定而非一概而論**。

### 多個欄位的輸出怎麼確保穩定性？

**核心答案**：**四個實務手段**。**用 schema 而非自然語言描述格式**（**明確的類型與必填標記**）。**給一到兩個完整的範例**（**比任何描述都有效**）。**欄位名用完整的英文單字而非縮寫**。**以及對每個欄位加上 description**（**多數 structured output API 支援，而模型確實會讀它**）。

**詳細解析**：**「description 被模型讀取」這一點常被忽略，而它是最便宜的品質提升手段**：在 schema 中為 `status` 欄位加上「訂單的當前狀態，只有在明確提到時才填寫，否則填 unknown」——**這比在系統提示裡寫一大段規則有效得多**，**因為它出現在模型正要填那個欄位的上下文中**。**這也是一個更普遍的原則：把指令放在它適用的位置附近，比集中在提示開頭有效**。**另一個穩定性手段是「用固定的欄位順序」**——**schema 的順序會影響生成順序，而讓依賴的欄位排在被依賴的之後（先分類再給該分類的細節）能讓模型的推理鏈條更自然**。**這些調整單獨看都很小，但累積起來對輸出穩定性的影響相當可觀。**

**面試回答方式**：給四個實務手段並強調**範例比任何描述都有效**。核心加分點是 **description 被模型讀取**這個常被忽略的點——**在欄位上加說明比在系統提示裡寫一大段規則有效得多，因為它出現在模型正要填那個欄位的上下文中**，並提煉出原則：**把指令放在它適用的位置附近，比集中在提示開頭有效**。收在**固定的欄位順序**：**讓依賴的欄位排在被依賴的之後，讓推理鏈條更自然**。
