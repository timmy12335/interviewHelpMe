# 題目

生產者的吞吐上不去，有哪些參數可以調？

## 核心答案

**四個關鍵參數，而它們共同構成「延遲換吞吐」的取捨。**

**`batch.size`**——**單個批次的位元組上限（預設 16KB）**；**批次越大，每條訊息攤到的網路與協定開銷越小**。

**`linger.ms`**——**批次未滿時願意等多久（預設 0，即不等）**；**設成 5 到 20 毫秒通常能顯著提升吞吐，因為它讓批次真的裝滿**。

**`compression.type`**——**批次層級的壓縮**；**文字類訊息通常能壓到三分之一以下**，**直接減少網路與磁碟的量**。

**`buffer.memory` 與 `max.in.flight.requests.per.connection`**——**前者是客戶端的緩衝上限，後者是同時在途的請求數**。

**而最容易被忽略的是「`linger.ms=0` 讓批次幾乎不生效」**：**預設值下，只要有一條訊息就立刻發送**——**於是「批次」這個機制在低到中等流量下形同虛設**。

## 詳細解析

**「linger.ms 的收益是非線性的」**：從 0 調到 5 毫秒——**吞吐可能提升數倍，而延遲只增加 5 毫秒**。**因為它把「一條訊息一個請求」變成「幾百條訊息一個請求」**——**協定開銷、網路往返、以及 broker 端的處理次數都成比例下降**。**而繼續往上調（例如 100 毫秒）的邊際收益快速遞減，延遲卻線性增加**。**所以 5 到 20 毫秒是多數場景的甜蜜點**——**而這是一個「幾乎免費的顯著提升」，卻經常因為預設值是 0 而被忽略**。

**「壓縮的選擇有明確的取捨」**：**gzip 壓縮率最高但 CPU 開銷大**、**lz4 與 snappy 速度快但壓縮率中等**、**zstd 在壓縮率與速度上取得了很好的平衡（較新版本的推薦）**。**判斷的依據是「瓶頸在網路還是 CPU」**——**跨機房或頻寬受限的場景值得用高壓縮率，而 CPU 吃緊的場景用快速的**。**另一個要點是「壓縮在生產者端完成，broker 直接儲存壓縮後的資料，消費者端解壓縮」**——**於是 broker 的 CPU 不受影響，而磁碟與網路都受益**。

**「in-flight 請求數與有序性的關係」是一個容易踩的坑**：**`max.in.flight.requests.per.connection > 1` 且開啟重試時，訊息可能亂序**（**第一個請求失敗重試，而第二個已經成功**）。**開啟冪等生產者（`enable.idempotence=true`）之後，Kafka 會在 broker 端保證順序，於是可以安全地設到 5**——**這是冪等生產者除了去重之外的一個重要好處**。

**「同步發送是吞吐的殺手」**：每發一條就 `future.get()` 等待——**吞吐會下降一到兩個數量級**。**正確的做法是非同步發送加上回呼處理錯誤**，**只在真的需要確認順序或結果時才等待。**

## 面試回答方式

先給四個關鍵參數並指出**它們共同構成「延遲換吞吐」的取捨**，強調**最容易被忽略的是 `linger.ms=0` 讓批次形同虛設**。加分點有四個：**linger.ms 的收益非線性**——**從 0 調到 5 毫秒吞吐可能提升數倍而延遲只增 5 毫秒**，**繼續往上邊際收益遞減而延遲線性增加**，**所以 5 到 20 毫秒是甜蜜點，是一個幾乎免費的顯著提升**；**壓縮演算法的取捨依據是瓶頸在網路還是 CPU**，並指出**壓縮在生產者完成、broker 直接存壓縮資料，所以 broker 的 CPU 不受影響**；**in-flight 大於 1 加重試會亂序**，**而冪等生產者能保證順序，這是它除了去重之外的重要好處**；以及**同步發送會讓吞吐下降一到兩個數量級**。

## 講稿

有四個關鍵參數，而它們共同構成延遲換吞吐的取捨。批次大小、等待時間、壓縮類型、還有緩衝與在途請求數。

最容易被忽略的是等待時間的預設值是零，也就是只要有一條訊息就立刻發送。於是批次這個機制在低到中等流量下形同虛設。

而它的收益是非線性的。從零調到五毫秒，吞吐可能提升數倍，而延遲只增加五毫秒。因為它把一條訊息一個請求變成幾百條訊息一個請求，協定開銷、網路往返、還有伺服器端的處理次數都成比例下降。繼續往上調的邊際收益快速遞減，延遲卻線性增加。所以五到二十毫秒是多數場景的甜蜜點，這是一個幾乎免費的顯著提升。

壓縮我會看瓶頸在網路還是 CPU。跨機房或頻寬受限就用高壓縮率的，CPU 吃緊就用快的。而壓縮是在生產者端完成、伺服器直接儲存壓縮後的資料，所以伺服器的 CPU 不受影響。

還有一個容易踩的坑，在途請求數大於一加上重試會導致亂序。開啟冪等生產者之後就能保證順序，這是它除了去重之外的重要好處。

## 常見追問

### 生產者發送失敗怎麼處理？

**核心答案**：**先區分可重試與不可重試**。**可重試**——leader 變更、網路逾時、broker 暫時不可用；**客戶端會自動重試（`retries` 預設是很大的值，由 `delivery.timeout.ms` 控制總時限）**。**不可重試**——訊息過大、序列化失敗、權限不足、topic 不存在；**這些重試一百次也一樣，必須在回呼中處理**（記錄、告警、或寫入本地的失敗佇列）。

**詳細解析**：**「回呼中的錯誤處理常被寫成一行 log 然後就沒了」是一個常見的可靠性漏洞**：非同步發送的失敗如果只是被記錄——**那條訊息就永久遺失了，而且沒有任何人知道**。**正確的處理應該至少包含：計數器（讓失敗率可監控）、以及一個明確的降級路徑**（寫入本地檔案或另一個佇列供後續補發）。**而更根本的問題是「生產者的緩衝區在客戶端當機時會丟失」**——**已經進入緩衝但還沒發送成功的訊息，隨著行程結束就沒了**。**所以「發送成功」的定義應該是「收到 broker 的確認」而非「呼叫了 send()」**——**而在關鍵的業務流程中，這意味著要嘛等待確認、要嘛用 Outbox 模式先落庫**。

**面試回答方式**：給可重試與不可重試的分類與各自的處理。核心加分點是指出**回呼中的錯誤處理常被寫成一行 log 然後就沒了**——**那條訊息永久遺失且沒有人知道**，**正確的處理應該有計數器與明確的降級路徑**。收在更根本的問題：**生產者的緩衝區在客戶端當機時會丟失**，**所以「發送成功」的定義是「收到 broker 確認」而非「呼叫了 send」**——**關鍵業務流程要嘛等待確認、要嘛用 Outbox 先落庫**。

### 訊息太大發不出去怎麼辦？

**核心答案**：**先確認三個地方的上限都調對了**：**生產者的 `max.request.size`**、**broker 的 `message.max.bytes`**、**以及 topic 級的 `max.message.bytes`**。**任何一處小於訊息大小都會失敗**。**但更根本的問題是「訊息本來就不該那麼大」**——**Kafka 的設計目標是高吞吐的小訊息，而大訊息會造成記憶體壓力、複製延遲、以及消費端的處理困難。**

**詳細解析**：**「引用而非內嵌」是處理大內容的標準模式**：**把大的內容（檔案、圖片、大型 JSON）存到物件儲存，訊息裡只放一個 URL 或 ID**——**訊息保持小而快，而消費者按需取得內容**。**這同時解決了「不是所有消費者都需要那個內容」的浪費**。**代價是引入了一個外部依賴與一致性問題**（**訊息到了但物件還沒寫完、或者物件被清理了但訊息還在**）——**處理的方式是「先寫物件、確認成功後才發訊息」並讓物件的保留期長於訊息的保留期**。**這個順序與「先落盤再確認」的原則一致：不可逆的引用應該建立在已經確定存在的東西上。**

**面試回答方式**：給三處上限的檢查，但強調**更根本的問題是訊息本來就不該那麼大**。核心加分點是**引用而非內嵌**這個標準模式——**大內容存物件儲存、訊息只放 URL**，**同時解決了「不是所有消費者都需要那個內容」的浪費**。收在一致性的處理：**先寫物件確認成功後才發訊息，並讓物件的保留期長於訊息的保留期**——**與「先落盤再確認」的原則一致，不可逆的引用應該建立在已確定存在的東西上**。

### 怎麼量測生產者的實際效能？

**核心答案**：**用客戶端的內建指標而非自己計時**。關鍵的幾個：**`record-send-rate`（每秒發送的訊息數）、`request-latency-avg`（請求延遲）、`batch-size-avg`（實際的批次大小）、以及 `record-error-rate`**。**其中 `batch-size-avg` 最能診斷「批次到底有沒有生效」**——**如果它遠小於 `batch.size` 設定值，那就是 `linger.ms` 太小或流量不足。**

**詳細解析**：**`buffer-available-bytes` 是一個容易忽略但很有診斷價值的指標**：如果它持續接近 0——**說明生產速度超過了發送速度，緩衝區在堆積**；**而緩衝滿了之後 `send()` 會阻塞（或者拋出例外，取決於 `max.block.ms`）**——**於是應用的業務執行緒被卡住**。**這種「訊息佇列的問題反向影響了業務服務」的情況很危險，而它的訊號正是這個指標**。**緩解的方式包括：增大緩衝、提升發送吞吐（批次與壓縮）、或者在應用層做背壓（發現緩衝吃緊時降低產生速度）**。**而最重要的認知是「生產者的緩衝不是無限的，它會反壓到應用」**——**很多團隊以為「非同步發送就不會影響業務」，直到緩衝滿的那一刻**。

**面試回答方式**：給關鍵指標並強調 **`batch-size-avg` 最能診斷批次有沒有生效**。核心加分點是 **`buffer-available-bytes` 的診斷價值**——**持續接近 0 說明生產快過發送，而緩衝滿了之後 send 會阻塞業務執行緒**，**這種「訊息佇列的問題反向影響業務服務」的情況很危險**。收在認知：**生產者的緩衝不是無限的，它會反壓到應用**——**很多團隊以為非同步發送就不會影響業務，直到緩衝滿的那一刻**。
