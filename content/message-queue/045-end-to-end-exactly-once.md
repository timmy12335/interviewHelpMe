# 題目

「精確一次」到底能做到什麼程度？

## 核心答案

**先把問題拆成三段，因為每一段的保證機制不同。**

**生產者到 broker**——**冪等生產者用「生產者 ID + 序號」讓 broker 去重**；**於是重試不會產生重複**。**這一段可以做到精確一次。**

**broker 內部的多個 topic**——**Kafka 交易讓「寫入多個分區」與「提交消費位移」成為一個原子操作**；**消費者用 `read_committed` 只讀已提交的訊息**。**這一段也可以。**

**broker 到外部系統**——**Kafka 無能為力**。**寫入資料庫、呼叫 API、發送郵件都不在它的交易範圍內。**

**所以「端到端的精確一次」的準確表述是**：**在純 Kafka 的管線中可以由 Kafka 保證**；**而跨出 Kafka 之後，必須由外部系統的冪等或交易來完成**——**沒有例外。**

## 詳細解析

**「冪等生產者的去重範圍是有限的」是一個必須知道的細節**：broker 為每個「生產者 ID + 分區」維護最近 5 個批次的序號——**於是它能偵測並丟棄重試造成的重複**。**但這個狀態不是永久的**：**生產者重啟後會拿到新的 PID（除非用了 `transactional.id`），於是舊的去重狀態失效**；**而 `transactional.id` 讓 PID 在重啟後保持穩定，這正是它除了交易之外的另一個作用**。**所以「開啟冪等就萬無一失」是不準確的**——**它防的是「客戶端內部重試造成的重複」，而不是「應用層重複發送同一個業務事件」**。

**「交易的效能代價」需要被量化**：交易引入了額外的協調（交易協調者、控制訊息、以及消費端的 `read_committed` 過濾）——**實測上吞吐下降可能在 10% 到 30% 之間，而端到端延遲增加**（因為消費者要等交易提交才能看到訊息）。**所以「不是所有管線都值得開交易」**——**在能用冪等解決的場景中，冪等更便宜。**

**「多數場景的正確答案是至少一次加冪等」**：因為**冪等在消費端本來就是必需的**（**任何重試都會產生重複**）——**而一旦有了冪等，精確一次的額外保證就沒有邊際價值**。**所以投入應該放在「把冪等做對」而非「開啟交易」**。**這是這個類別反覆出現的主線，而它在這裡達到了最明確的形式。**

**「業務層的精確一次」是另一個層次的問題**：即使傳輸層做到了精確一次——**如果使用者按了兩次提交按鈕，那是兩個不同的訊息**。**所以「業務的冪等鍵」（訂單號、請求 ID）是唯一能處理這一層的機制**——**而它與訊息佇列的保證完全無關**。**能區分這兩個層次，是理解這個問題的關鍵。**

## 面試回答方式

先把問題拆成三段（生產者到 broker、broker 內部、broker 到外部）並指出**前兩段可以而第三段 Kafka 無能為力**，給出準確的表述。加分點有四個：**冪等生產者的去重範圍有限**——**broker 維護的是最近幾個批次的序號，而生產者重啟後 PID 會變**，**`transactional.id` 讓 PID 穩定是它除了交易之外的另一個作用**，**所以它防的是客戶端重試而非應用層重複發送**；**交易的效能代價**（吞吐下降 10% 到 30%、延遲增加）；**多數場景的正確答案是至少一次加冪等**——**冪等本來就必需，有了它精確一次就沒有邊際價值**；以及**業務層的精確一次是另一個層次**——**使用者按兩次提交是兩個不同的訊息，只有業務冪等鍵能處理**。

## 講稿

我會先把問題拆成三段，因為每一段的保證機制不同。

生產者到伺服器這一段，冪等生產者用生產者編號加序號讓伺服器去重，可以做到。伺服器內部跨多個主題這一段，交易讓寫入多個分區跟提交位移成為一個原子操作，也可以。但伺服器到外部系統這一段，Kafka 完全無能為力，寫資料庫、呼叫介面都不在它的交易範圍內。

所以準確的表述是，純 Kafka 的管線中可以由 Kafka 保證，跨出去之後必須由外部系統的冪等或交易來完成，沒有例外。

而我認為多數場景的正確答案是至少一次加冪等。因為冪等在消費端本來就是必需的，任何重試都會產生重複。而一旦有了冪等，精確一次的額外保證就沒有邊際價值了。所以投入應該放在把冪等做對，而不是開啟交易。

還有一個層次要區分。即使傳輸層做到了精確一次，如果使用者按了兩次提交按鈕，那是兩個不同的訊息。所以業務的冪等鍵是唯一能處理那一層的機制，它跟訊息佇列的保證完全無關。

## 常見追問

### Kafka 交易具體怎麼運作？

**核心答案**：**由一個「交易協調者」（broker 中的一個角色）管理**。生產者用 `transactional.id` 註冊——**協調者為它分配一個 PID 與 epoch**；**交易期間的所有寫入被標記為屬於該交易**；**提交時協調者往每個涉及的分區寫入一個「控制訊息」標記交易已提交**；**而消費者在 `read_committed` 模式下會跳過未提交或已中止的訊息**。

**詳細解析**：**「epoch 用於處理殭屍生產者」是一個關鍵的設計**：如果一個生產者實例卡住了（GC 停頓、網路分割）而系統啟動了一個新的實例——**新實例用同一個 `transactional.id` 註冊時，協調者會遞增 epoch 並讓舊 epoch 的寫入全部被拒絕**。**這防止了「兩個實例同時以同一個交易身份寫入」的混亂**——**而它與 Kafka 的 leader epoch、以及分散式系統的柵欄令牌是完全相同的機制**。**這個「用單調遞增的號碼讓舊的持有者失效」的模式在整個分散式系統領域反覆出現**，**而能指出這個共通性，比記住 Kafka 的具體實作更能展現理解。**

**面試回答方式**：給運作機制（交易協調者、PID 與 epoch、控制訊息、`read_committed` 的過濾）。核心加分點是**epoch 用於處理殭屍生產者**——**新實例註冊時遞增 epoch 讓舊 epoch 的寫入全部被拒絕**，**防止兩個實例同時以同一個交易身份寫入**。收在共通性：**這與 leader epoch、以及分散式系統的柵欄令牌是完全相同的機制**，**「用單調遞增的號碼讓舊持有者失效」在整個領域反覆出現**。

### 消費者的 read_committed 模式有什麼影響？

**核心答案**：**延遲增加，因為訊息要等交易提交後才可見**。**如果一個交易持續 5 秒，那期間寫入的訊息對 `read_committed` 的消費者都不可見**——**於是端到端延遲至少增加那 5 秒**。**所以交易應該盡量短**。**另外，`read_committed` 的消費者會維護一個「已中止交易的位移列表」用於過濾，這帶來少量的記憶體與處理開銷。**

**詳細解析**：**「LSO（Last Stable Offset）」是這個機制的關鍵概念**：`read_committed` 的消費者只能讀到 LSO 之前的訊息——**而 LSO 是「最早的未完成交易的起始位移」**。**於是一個長時間未提交的交易會「卡住」LSO**，**讓所有後續的訊息都不可見**——**即使它們屬於已經提交的交易**。**這意味著「一個卡住的交易生產者會阻塞整個分區的消費」**，**而那是一個相當嚴重的影響**。**Kafka 用 `transaction.timeout.ms` 防止這個問題（超時的交易被自動中止）**——**但那個超時預設是 15 分鐘，在多數場景下應該調短**。**知道這個機制能解釋一類神秘的問題：「生產正常、消費者也正常，但就是收不到訊息」。**

**面試回答方式**：給影響（延遲增加、少量開銷）並指出**交易應該盡量短**。核心加分點是介紹 **LSO 的概念**：**`read_committed` 只能讀到最早的未完成交易的起始位移之前**，**於是一個長時間未提交的交易會卡住整個分區的消費，即使後面的訊息屬於已提交的交易**。收在防護與診斷價值：**`transaction.timeout.ms` 預設 15 分鐘，多數場景應該調短**，**而知道這個機制能解釋「生產正常、消費者正常，但就是收不到訊息」這類神秘問題**。

### 那到底什麼時候該用交易？

**核心答案**：**「消費 Kafka、處理、產出 Kafka」的純流式管線**——**在那裡交易能提供「輸入的位移與輸出的訊息原子地一起提交」，而自己實作這個保證非常困難**。**除此之外的場景，包括「消費後寫資料庫」與「單純的生產」**——**用冪等生產者加消費端冪等更簡單也更便宜。**

**詳細解析**：**「自己實作流式管線的精確一次有多難」值得說明**：需要「處理完成、輸出寫入、位移提交」三件事原子完成——**而它們涉及不同的分區甚至不同的 topic**。**沒有交易的話，任何一種順序都有失敗窗口**：**先輸出後提交位移會重複輸出，先提交後輸出會遺漏**。**而下游如果無法冪等（例如輸出是一個累加的聚合），重複輸出就是錯誤的結果**。**所以在流式聚合這類場景中，交易確實提供了難以替代的價值**。**而反過來，如果輸出是「可以被冪等覆蓋的」（例如按 key 寫入最新狀態）**——**那重複輸出無害，交易的價值就消失了**。**所以判斷的關鍵是「輸出是否可以冪等」而非「有沒有跨分區寫入」**——**這個判準比「用不用交易」的二分法精確得多。**

**面試回答方式**：給明確的適用場景（純 Kafka 的流式管線）與其餘場景的建議。核心加分點是說明**自己實作有多難**——**處理、輸出、提交位移三者原子完成，而任何順序都有失敗窗口**，**且下游若無法冪等（例如累加的聚合）重複輸出就是錯誤結果**。收在更精確的判準：**關鍵是「輸出是否可以冪等」而非「有沒有跨分區寫入」**——**輸出可以被冪等覆蓋的話交易的價值就消失了**。
