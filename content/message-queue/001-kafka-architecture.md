# 題目

Kafka 的核心概念有哪些？它和傳統的訊息佇列在架構上最大的差別是什麼？

## 核心答案

核心概念由外而內是：**叢集**由多個 **broker**（節點）組成；訊息按 **topic**（主題）分類；每個 topic 切成若干 **partition**（分區），分區是**平行處理與有序性的基本單位**；每個分區有多份 **replica**（副本）分散在不同 broker 上，其中一份是 **leader** 負責讀寫、其餘是 **follower** 負責同步。生產者把訊息**追加**到分區末端，消費者以**消費者群組**為單位訂閱，群組內每個分區只會被**一個**消費者處理。和傳統訊息佇列最大的架構差別是：**Kafka 是一個持久化的分散式日誌，而不是一個訊息的暫存區**。傳統佇列中訊息被消費後就移除，Kafka 則把訊息**按保留策略留在磁碟上**，消費者各自維護自己讀到哪裡（位移），所以**同一份資料可以被多個消費者群組獨立重複讀取**，也可以回溯重放。這個差別決定了它適合的場景——資料管線與事件溯源，而不只是任務分發。

## 詳細解析

**分區是理解 Kafka 的關鍵**：它同時決定了三件事——**平行度上限**（一個群組內最多只有分區數那麼多的消費者能同時工作）、**有序性範圍**（Kafka 只保證單一分區內有序，不保證跨分區）、以及**資料分布**（訊息依鍵的雜湊落到分區）。多數 Kafka 的設計問題最後都會回到「分區怎麼切」這件事上。

**位移由消費者維護，這是重複讀取的基礎**：Kafka 本身不記錄「誰讀過什麼」，只記錄每個消費者群組讀到哪個位移（存在一個內部的 topic 中）。所以新增一個群組就能從頭重讀全部歷史，這對於「新上線一個下游服務，需要處理過去的資料」的場景極為有用——傳統佇列做不到這件事，因為訊息已經被消費掉了。

**Leader 與 follower 的分工**：所有讀寫都走 leader，follower 只負責從 leader 拉取資料保持同步。**follower 不分擔讀取**（早期版本完全不行，後來才支援從最近的副本讀取以降低跨區流量），這與某些資料庫的讀寫分離不同，理解這一點才不會誤以為增加副本能提升讀取吞吐。副本的價值在**可用性**——leader 所在的 broker 掛掉時，從同步狀態良好的 follower 中選出新的 leader。

**控制器負責協調**：叢集中有一個 broker 擔任控制器，負責分區的 leader 選舉、感知 broker 的上下線、以及變更的傳播。早期依賴 ZooKeeper 保存中繼資料與協助選舉，新版本改用內建的共識機制移除了這個外部依賴，簡化了部署與運維——這是近年最重要的架構演進，值得知道。

**訊息的持久化方式是它高效能的根源**：Kafka 把每個分區實作成一個**只追加的日誌檔案**，寫入是**順序寫**（磁碟的順序寫遠快於隨機寫），讀取大量依賴**作業系統的頁快取**，並用**零拷貝**把資料直接從檔案送到網路。這三者的組合讓它在普通磁碟上也能達到很高的吞吐，而不是靠把資料放在記憶體裡。

## 面試回答方式

由外而內把五個概念串起來（broker、topic、partition、replica、消費者群組），並強調**分區是平行處理與有序性的基本單位**。接著給出最關鍵的架構差異：**Kafka 是持久化的分散式日誌而非訊息暫存區**——訊息消費後不刪除，位移由消費者維護，所以多個群組可以獨立重複讀取與回溯。這一句能直接說明它為什麼適合資料管線而不只是任務分發。加分點有三個：**follower 不分擔讀取**，所以增加副本不會提升讀取吞吐，它的價值在可用性；**控制器已從依賴 ZooKeeper 演進到內建共識**；以及高效能來自順序寫、頁快取與零拷貝，而不是把資料放記憶體。

## 常見追問

### 為什麼 Kafka 要分區？只有一個大 topic 不行嗎？

**核心答案**：不行，因為**單一分區的吞吐受限於單一 broker 的單一檔案**，無法水平擴展；而且**消費端的平行度也被鎖死**——一個分區在群組內只能被一個消費者處理，所以只有一個分區就等於只能有一個消費者在工作。分區讓寫入分散到多個 broker、讓消費可以平行進行，是 Kafka 水平擴展能力的來源。

**詳細解析**：代價是**有序性只能保證在分區內**。需要保證某一組訊息有序時（例如同一筆訂單的狀態變化），做法是**用同一個鍵讓它們落到同一個分區**，而不是追求全域有序——全域有序等於只能有一個分區，也就放棄了擴展能力。另一個代價是**分區數不容易減少**（增加相對容易，減少通常需要重建 topic），而且增加分區會改變鍵到分區的對應關係，導致**同一個鍵的新舊訊息落到不同分區**，破壞既有的順序保證。所以分區數是一個**要提前想清楚**的設計決定，這是它在實務上最容易踩的坑。

**面試回答方式**：給出兩個限制（單分區吞吐受限於單一節點、消費平行度被鎖死）說明為什麼要分區。接著給代價：有序性只在分區內，需要有序就用同一個鍵。加分點是指出分區數難以減少、且增加分區會破壞既有鍵的順序保證，所以是要提前想清楚的決定。

### 消費者群組的意義是什麼？

**核心答案**：它讓 Kafka 同時支援**兩種消費模式**。**同一個群組內**，每個分區只分配給一個消費者，所以群組整體是「**分工**」——這等同於傳統佇列的競爭消費模式，加消費者就能提升處理能力（上限是分區數）。**不同群組之間**互不影響，各自維護位移、各自讀取全部資料，所以是「**廣播**」——這等同於發布訂閱模式。用一套機制涵蓋兩種模式，是 Kafka 設計上很優雅的地方。

**詳細解析**：實務上要注意兩件事。**消費者數量超過分區數時，多出來的會閒置**——這是常見的浪費，擴容前要先確認分區數是否足夠。**群組 ID 決定了身分**，所以部署時如果不小心讓兩個不同用途的服務用了相同的群組 ID，它們會互相搶分區導致各自只收到部分訊息，症狀是「訊息隨機遺失」但其實是被另一個服務吃掉了——這是很典型且難查的設定錯誤。另外**新群組的起始位移**（從最早還是最新開始）也是要明確設定的，預設值不符合預期時會造成「上線後把歷史資料全部重跑一遍」或「漏掉上線前的訊息」。

**面試回答方式**：講清「群組內分工、群組間廣播」這一套機制同時涵蓋兩種模式。加分點是三個實務陷阱：消費者多於分區數會閒置、群組 ID 撞號會造成訊息像是隨機遺失、以及新群組的起始位移要明確設定。

### Kafka 移除 ZooKeeper 之後有什麼變化？

**核心答案**：中繼資料（topic 設定、分區分配、broker 成員）與控制器選舉改由 **Kafka 自己的共識機制**管理，不再需要外部的 ZooKeeper 叢集。好處是**部署與運維簡化**（少一套系統要維護與監控）、**中繼資料的擴展性提升**（原本大量分區時 ZooKeeper 會成為瓶頸）、以及**控制器故障切換更快**（不需要從外部重新載入全部中繼資料）。

**詳細解析**：這個演進的價值在大規模叢集上最明顯——分區數達到數十萬時，舊架構的中繼資料傳播與控制器重啟時間會變得難以接受。對中小型叢集來說，最直接的收益是**少一個必須高可用的依賴**，因為 ZooKeeper 本身的運維（磁碟、快照、連線數）也是實際負擔。遷移時要注意版本相容性與工具鏈的支援，某些依賴 ZooKeeper 介面的舊工具需要更換。面試中能講出「這解決的是中繼資料規模與運維複雜度」而不只是「移除了依賴」，會顯示你理解演進的動機。

**面試回答方式**：說明改由內建共識管理中繼資料與控制器選舉，並給三個好處（運維簡化、中繼資料擴展性、故障切換更快）。加分點是指出大規模叢集受益最明顯、中小型叢集的主要收益是少一個高可用依賴，並提醒遷移時舊工具的相容性。
