# 題目

分區鍵怎麼選？某個分區特別忙怎麼辦？

## 核心答案

分區鍵決定兩件事，而它們互相牽制：**順序保證的粒度**（同一個 key 的訊息一定在同一個分區因而有序）與**負載的分布**（key 的分布決定各分區的流量）。

選擇的原則是「選擇需要保序的最小粒度」：如果只需要「同一個訂單的事件有序」，就用訂單 ID 而非使用者 ID——因為粒度越細，key 的種類越多，分布越均勻。

**而傾斜的來源有兩類**。**key 的分布本身不均**——一個大客戶佔了平台一半的訂單；這是業務性質造成的，無法用雜湊函數解決。**key 的種類太少**——例如用「地區」作為 key 而只有五個地區；那麼再多的分區也只有五個被用到。

**處理傾斜的三個手段**：**加鹽**（key 後面加隨機後綴打散，代價是失去該 key 的順序保證）、**自訂分區器**（手動把熱點 key 分配到專屬分區）、以及在消費側加大該分區的處理能力。

## 詳細解析

「加鹽會破壞順序保證」這個代價必須被明確評估：加鹽的本質是「把一個 key 拆成多個」——於是它們散布在不同分區，順序不再保證。所以只有在「該 key 不需要嚴格順序」時才能用。如果順序是必需的，可行的替代是「把熱點 key 單獨路由到一個專屬分區並給那個分區更多的消費資源」——順序保住了，但那個分區的吞吐上限仍然是單消費者的能力。這是一個沒有完美解的取捨，而能清楚說出「順序與並行是對立的」比列舉手段更重要。

**「不指定 key 的行為」值得知道**：早期 Kafka 用輪詢（round-robin）——均勻但每次都換分區，批次效率差；**而 2.4 之後預設改成「黏性分區」（sticky partitioning）**：在一個批次內堅持用同一個分區，批次滿了才換——於是批次能裝滿，吞吐顯著提升而分布仍然均勻。這是一個「在不影響語義的前提下改善效能」的好設計，而知道它能解釋「為什麼升級之後吞吐變好了」。

「傾斜的診斷」應該分開看流量與訊息數：**某個分區的訊息數多**（key 分布不均）與**某個分區的位元組數多**（訊息本身較大）**是不同的問題**。前者可能需要調整 key，後者可能需要處理大訊息。而消費側的 LAG 分布則直接告訴你「哪個分區處理不過來」。

「一開始就規劃足夠的分區」比事後處理傾斜容易：因為增加分區會改變 key 到分區的映射——**於是既有的順序保證斷裂**。所以在設計階段就估算「key 的種類數」與「預期的最大吞吐」，並留出餘裕。

## 面試回答方式

先給分區鍵決定的兩件事（順序粒度與負載分布）與選擇原則（**選擇需要保序的最小粒度**）。給傾斜的兩類來源與三個處理手段。加分點有四個：**加鹽會破壞順序保證**——只有該 key 不需要嚴格順序時才能用，替代是把熱點 key 路由到專屬分區但吞吐上限仍是單消費者的能力，而「順序與並行是對立的」比列舉手段更重要；**黏性分區**——2.4 之後不指定 key 的預設從輪詢改成在批次內堅持同一分區，於是批次能裝滿而分布仍均勻；傾斜要分開看訊息數與位元組數，**它們是不同的問題**；以及一開始就規劃足夠的分區比事後處理容易，因為增加分區會讓既有的順序保證斷裂。

## 講稿

分區鍵決定兩件事，而它們互相牽制。順序保證的粒度，還有負載的分布。

選擇的原則是選需要保序的最小粒度。如果只需要同一個訂單的事件有序，就用訂單編號而不是使用者編號，因為粒度越細，鍵的種類越多，分布越均勻。

傾斜的來源有兩類。鍵的分布本身不均，比如一個大客戶佔了平台一半的訂單，這是業務性質造成的，換雜湊函數解決不了。另一類是鍵的種類太少，比如用地區作為鍵而只有五個地區，那再多的分區也只有五個被用到。

處理的手段有加鹽、自訂分區器、還有加大消費能力。但加鹽會破壞順序保證，因為它本質上是把一個鍵拆成多個。所以只有在該鍵不需要嚴格順序時才能用。如果順序是必需的，可行的替代是把熱點鍵單獨路由到一個專屬分區並給它更多消費資源，順序保住了但吞吐上限仍然是單消費者的能力。

## 常見追問

### 全域有序真的做得到嗎？

**核心答案**：做得到，代價是只能用一個分區——於是吞吐受限於單一分區的能力，而消費也只能有一個實例。這實際上放棄了 Kafka 的核心價值（水平擴展）。所以問題應該反過來問：「你真的需要全域有序嗎」——而絕大多數場景需要的只是「某個實體的事件有序」，那用分區鍵就能達成。

**詳細解析**：「需要全域有序」的需求往往來自對問題的誤解：例如「訂單狀態必須按順序處理」——實際需要的是「同一個訂單的狀態變更有序」，不同訂單之間完全不相關。**而「所有的財務流水必須有序」——**實際需要的可能是「同一個帳戶的流水有序」**。**所以第一步應該是「找出真正需要保序的邊界」**，**而那個邊界通常就是一個自然的實體 ID**。**如果真的無法縮小（例如需要一個全域單調的序號），那應該考慮「這個需求是不是可以用其他方式滿足」**——**例如在消費端用一個排序緩衝，或者用資料庫的序號而非依賴訊息的順序**。**把「排序的責任」從傳輸層移到需要它的那一層，往往是更好的設計。

**面試回答方式**：回答做得到但代價是放棄水平擴展，並主張**問題應該反過來問**。核心加分點是指出「需要全域有序」往往來自對問題的誤解並給兩個具體例子（訂單狀態、財務流水），實際需要的都是「某個實體的事件有序」。收在真的無法縮小時的替代：消費端的排序緩衝或用資料庫的序號——把排序的責任從傳輸層移到需要它的那一層往往是更好的設計。

### 消費端怎麼處理分區之間的順序？

**核心答案**：**接受它們之間沒有順序**。不同分區的訊息可以任意交錯——所以消費邏輯不應該依賴跨分區的順序。如果業務上確實需要（例如要等兩個不同實體的事件都到齊才能處理）——那應該在消費端用狀態機或緩衝來處理，而不是指望訊息按需要的順序到達。

**詳細解析**：「用狀態機處理亂序」是這類需求的標準解法：把「等待的條件」明確表達成狀態——收到 A 時記錄「A 已到」，收到 B 時檢查「A 是否已到」，**兩者齊備才觸發處理**。這需要一個持久化的狀態儲存（因為消費者可能重啟），而那本質上就是一個小型的流式 join。**Kafka Streams 這類框架提供了現成的實作**——如果需求複雜到需要多路 join 與時間窗口，用框架比自己寫可靠得多。而一個常被忽略的細節是「等待要有超時」：如果 B 永遠不來，那個狀態會永遠留著——所以必須定義「等多久之後放棄並走異常流程」，**否則狀態儲存會無限成長。**

**面試回答方式**：給原則（接受沒有順序，消費邏輯不應依賴跨分區的順序）與需要時的做法（狀態機或緩衝）。核心加分點是說明用狀態機處理亂序的具體形態（記錄已到的、檢查是否齊備、需要持久化狀態）並指出它本質上就是一個小型的流式 join，複雜時用框架比自己寫可靠。收在常被忽略的細節：**等待要有超時**——否則 B 永遠不來的話狀態會永遠留著，儲存無限成長。

### 用時間戳當分區鍵可以嗎？

**核心答案**：**幾乎總是錯的**。時間戳是單調遞增的——於是同一段時間的訊息會集中到同一個分區（如果直接雜湊），造成嚴重的熱點與其他分區的閒置。這與資料庫用時間作為分片鍵的問題完全一樣。

**詳細解析**：「單調遞增的值不適合作為分片或分區鍵」是一個跨系統的通用原則：時間戳、自增 ID、雪花 ID——它們的共同特徵是「新資料總是落在同一個地方」。而分區的目的正是「把負載分散」——**兩者直接衝突**。正確的做法是「用一個分布均勻的業務標識」（使用者 ID、訂單 ID）**或者「複合鍵」**（例如 `使用者ID + 日期` 用於需要按天分組的場景）。而如果確實需要「按時間查詢」的能力——那應該靠 Kafka 的 timeindex（按時間定位位移）而非靠分區，因為那是兩個不同的機制解決不同的問題。混淆「分區用於分散負載」與「索引用於快速定位」是這個錯誤的根源。

**面試回答方式**：明確回答幾乎總是錯的並說明機制（單調遞增讓同一段時間的訊息集中）。核心加分點是把它提升成通用原則：單調遞增的值不適合作為分片或分區鍵（時間戳、自增 ID、雪花 ID），因為它們讓新資料總是落在同一個地方，而分區的目的正是分散負載。收在根源：需要按時間查詢應該靠 timeindex 而非分區——混淆「分區用於分散負載」與「索引用於快速定位」是這個錯誤的根源。
