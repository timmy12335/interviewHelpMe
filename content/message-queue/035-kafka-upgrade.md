# 題目

Kafka 叢集怎麼升級？客戶端與 broker 的版本可以不一致嗎？

## 核心答案

**Kafka 的相容性設計相當寬鬆**：**broker 與客戶端可以跨版本運作**——新 broker 支援舊客戶端（向後相容），而 0.10.2 之後的客戶端也能與新 broker 通訊（向前相容）。這讓「先升 broker 再升客戶端」成為可行的順序。

滾動升級的標準流程有三個階段。**一、逐台升級 broker 的二進位檔**，但先在設定中把 `inter.broker.protocol.version` 與 `log.message.format.version` 固定在舊版本——於是 broker 之間仍用舊協定通訊，可以隨時回退。二、全部升級完成並驗證後，把 `inter.broker.protocol.version` 提升到新版本並再滾動一次。**三、最後才提升 `log.message.format.version`**（這一步之後就無法回退，因為磁碟上的格式變了）。

這個「先升程式、再升協定、最後升格式」的三段式，讓每一步都有回退的餘地。

## 詳細解析

**「為什麼要分三步」值得說清楚**：如果一次全部升級——升到一半發現問題時，已經升級的 broker 用新協定，未升級的用舊協定，無法互相通訊；而且新格式的資料寫進磁碟後，舊版本的 broker 讀不了。分段之後，第一階段的任何時候都可以把某台換回舊版本——**因為協定與格式都還是舊的**。這個「先讓新程式碼用舊行為運行，確認穩定後才啟用新行為」的模式，與應用系統的功能旗標是完全相同的思路。

「訊息格式的升級不可逆」需要特別謹慎：一旦有訊息以新格式寫入——**舊版本的 broker 就無法讀取那些 segment**。所以這一步應該在「新版本已經穩定運行一段時間」之後才做。而它的收益是「避免格式轉換的開銷」：如果 broker 的格式版本與客戶端的不一致，broker 需要在讀取時做格式轉換——而那會破壞零拷貝（因為要在使用者空間處理資料），顯著降低效能。所以「升級後長期不提升格式版本」是一個隱形的效能損失，值得在客戶端都升級後盡快完成。

「客戶端的升級順序」通常是「消費者先於生產者」：因為新版本的生產者可能使用新的協定特性——**而舊的消費者可能不認得**。先升消費者確保它們能處理新的格式與特性，再升生產者。

**「升級前的檢查清單」應該包含**：閱讀版本間的 release notes（尤其是不相容的變更）、**在測試環境完整演練一次**、確認監控在升級期間仍然工作、以及有明確的回退計畫與觸發條件。

## 面試回答方式

先給相容性的設計（broker 與客戶端可跨版本，新 broker 支援舊客戶端）與滾動升級的三個階段。加分點有四個：**為什麼分三步**——一次全升的話升到一半時新舊協定無法互通、新格式舊 broker 讀不了，而分段讓第一階段隨時可回退，這與應用系統的功能旗標是相同的思路；訊息格式的升級不可逆且要在穩定運行後才做；格式版本不一致會讓 broker 做轉換而破壞零拷貝，所以長期不提升格式版本是隱形的效能損失；以及客戶端的升級順序是消費者先於生產者。

## 講稿

Kafka 的相容性設計相當寬鬆，伺服器跟客戶端可以跨版本運作。新伺服器支援舊客戶端，而較新版本之後的客戶端也能跟新伺服器通訊。所以先升伺服器再升客戶端是可行的順序。

滾動升級的標準流程分三個階段。第一階段逐台升級二進位檔，但先在設定裡把節點間的協定版本跟訊息格式版本固定在舊版本，於是節點之間仍用舊協定，可以隨時回退。第二階段全部升完並驗證後，提升協定版本再滾動一次。第三階段最後才提升訊息格式版本，而這一步之後就無法回退了。

為什麼要分三步？如果一次全部升級，升到一半發現問題時，已升級的用新協定、未升級的用舊協定，無法互相通訊。分段之後第一階段的任何時候都可以把某台換回舊版本。這個先讓新程式碼用舊行為運行、確認穩定後才啟用新行為的模式，跟應用系統的功能旗標是完全相同的思路。

還有一點，如果格式版本跟客戶端不一致，伺服器要在讀取時做轉換，而那會破壞零拷貝顯著降低效能。所以長期不提升格式版本是一個隱形的效能損失。

## 常見追問

### 升級到 KRaft 模式要注意什麼？

**核心答案**：這比一般的版本升級複雜得多，因為它改變了中繼資料的儲存方式。流程是：先把叢集升級到支援遷移的版本、部署 KRaft controller 節點、啟用遷移模式（雙寫到 ZooKeeper 與 KRaft）、確認同步完成、然後逐台把 broker 切換到 KRaft 模式、最後移除 ZooKeeper。每一步都要驗證，而整個過程應該在測試環境完整演練過。

**詳細解析**：「遷移的過程中有一個雙寫階段」是這個設計能安全進行的關鍵：中繼資料同時寫入 ZooKeeper 與 KRaft 的 log——於是在確認 KRaft 側完全正確之前，ZooKeeper 仍然是可用的退路。而一旦完成切換並移除 ZooKeeper，就無法回退。所以「在雙寫階段停留足夠長的時間並充分驗證」是最重要的建議。另一個實務要點是「新叢集直接用 KRaft，不要為了統一而遷移既有的叢集」——如果既有叢集運行穩定且沒有遇到 ZooKeeper 帶來的問題，遷移的風險可能大於收益。而在需要擴展到大量 partition 或者頻繁遇到 controller 故障轉移慢的情況下，遷移才有明確的價值——這個「有具體的痛點才升級」的判斷，適用於幾乎所有的基礎設施變更。

**面試回答方式**：給遷移流程並強調**它比一般版本升級複雜得多**。核心加分點是**雙寫階段是安全進行的關鍵**——中繼資料同時寫兩邊，確認正確前 ZooKeeper 是退路，而移除之後無法回退，所以要在雙寫階段停留足夠長並充分驗證。收在判斷：新叢集直接用 KRaft，既有叢集運行穩定的話遷移風險可能大於收益——有具體痛點才升級，這適用於幾乎所有基礎設施變更。

### 升級過程中生產與消費會中斷嗎？

**核心答案**：單台 broker 重啟時，它上面的 leader partition 會短暫不可用直到 leader 切換完成（通常幾秒）。客戶端會自動重試並更新中繼資料，所以應用層通常感受不到——前提是「生產者的重試設定合理」與「副本數足夠」。而如果副本數只有 1，那重啟就是真正的中斷。

**詳細解析**：「優雅關閉」能顯著縮短這個窗口：Kafka 支援 `controlled.shutdown.enable`（預設開啟）——broker 在關閉前會主動把自己的 leadership 遷移到其他副本，於是切換是有序的而非等待故障偵測。這把不可用時間從「幾十秒（等偵測超時）」縮短到「幾秒（主動遷移）」。確認這個設定開啟並且關閉時給足夠的時間（不要直接 kill -9）是升級操作中很實際的一點。另一個要點是「一次只重啟一台並等它完全恢復」：**判斷恢復的標準是 `UnderReplicatedPartitions` 回到 0**——**而不是「行程起來了」**。急於進行下一台是升級事故最常見的原因，因為那會讓多個 partition 同時失去多個副本。

**面試回答方式**：給答案（短暫不可用但客戶端自動處理）與前提（重試設定合理、副本數足夠）。核心加分點是優雅關閉能把不可用時間從幾十秒縮短到幾秒——**broker 主動遷移 leadership 而非等待故障偵測**，**所以要確認設定開啟且不要 kill -9**。收在操作紀律：一次只重啟一台並等 `UnderReplicatedPartitions` 回到 0 而不是「行程起來了」——急於進行下一台是升級事故最常見的原因。

### 客戶端版本太舊有什麼風險？

**核心答案**：**三類**。**功能受限**——冪等生產者、交易、cooperative rebalance 這些都需要較新的客戶端。**效能損失**——舊的訊息格式讓 broker 做轉換，破壞零拷貝。**以及安全與 bug 修復缺失**——舊版本可能有已知的資料遺失或死鎖問題。

**詳細解析**：「客戶端的升級往往比 broker 難推動」是一個組織問題而非技術問題：broker 由平台團隊控制，而客戶端散落在幾十個應用中，由不同的團隊維護。於是常見的狀況是「broker 已經升到最新，而某些應用還在用三年前的客戶端」。**處理的方式有兩個層面**：技術上——用一個統一的內部 SDK 封裝 Kafka 客戶端，於是升級只需要改一個依賴版本；組織上——建立「支援的客戶端版本範圍」並定期通知即將淘汰的版本。而最有效的推動力是「量測並公開」：統計每個應用使用的客戶端版本並讓它可見——因為看得到落後的團隊比收到郵件通知的團隊更容易行動。這與依賴升級的一般問題是同構的，而在 Kafka 上它的後果更直接（效能與可靠性）。

**面試回答方式**：給三類風險。核心加分點是指出客戶端升級難推動是組織問題而非技術問題——broker 由平台團隊控制而客戶端散落在幾十個應用中，並給兩個層面的處理（統一的內部 SDK、支援版本範圍與淘汰通知）。收在最有效的推動力：量測並公開每個應用的客戶端版本——看得到落後的團隊比收到郵件通知的更容易行動。
