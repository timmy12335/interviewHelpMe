# 題目

消費一批訊息並寫入資料庫，交易邊界怎麼劃？

## 核心答案

**核心問題是「訊息的位移在 Kafka，業務資料在資料庫」——兩者不在同一個交易裡**。**所以無論怎麼設計，都存在一個窗口讓兩者不一致**。

**三種常見的順序，而它們的失敗模式不同。**

**先處理、後提交位移**（推薦）——**業務資料寫入成功後才提交位移**；**中間當機的話位移沒提交，訊息會被重新消費**——**於是需要冪等，但不會丟資料**。

**先提交位移、後處理**——**當機的話訊息已被視為消費但業務沒做完**；**這是資料遺失，通常不可接受。**

**把位移也存進資料庫**——**在同一個交易中寫入業務資料與位移**，**於是兩者原子地一致**；**消費者啟動時從資料庫讀取位移而非 Kafka**。**這能做到精確一次，代價是放棄了 Kafka 的位移管理與消費者群組的部分便利。**

## 詳細解析

**「批次的交易邊界」有兩種劃法**：**整批一個交易**——**簡單、效率高（一次批次寫入），但一條失敗就整批重來**；**每條一個交易**——**失敗隔離好，但效能差（N 次資料庫往返）**。**多數場景選前者**，**因為冪等讓「整批重來」是安全的**，**而效能的差距可能是一個數量級**。**而如果批次中有一條「怎麼重試都會失敗」的毒訊息（poison message）**——**整批就永遠卡住**；**處理方式是「失敗時降級為逐條處理，找出那一條並送進死信佇列」**——**於是常態走高效的批次路徑，只在異常時付出逐條的成本**。

**「位移存進資料庫」的實務考量**：它讓每個分區的位移成為業務資料庫中的一列——**而消費者需要在 rebalance 時正確地讀取新分配到的分區的位移**（在 `onPartitionsAssigned` 回呼中用 `seek()`）。**這個模式在需要嚴格精確一次的場景（財務、計費）是值得的**，**而在多數場景中「至少一次加冪等」更簡單且效果相同**——**因為冪等本來就是必需的**。

**「Kafka 的交易能保證什麼」需要說清楚**：`transactional.id` 加上讀寫交易能做到「Kafka 到 Kafka 的精確一次」——**例如流式處理中「消費、處理、產出」的原子性**。**但它不涵蓋外部系統**：**寫入資料庫的操作不在 Kafka 的交易範圍內**。**所以「Kafka 有交易所以我不用擔心」是一個常見的誤解**——**它的範圍是明確的，而跨出 Kafka 就需要別的機制。**

**「處理失敗的分級」是實務設計的一部分**：**暫時性失敗（下游不可用）→ 重試**；**永久性失敗（資料格式錯誤）→ 死信佇列**；**未知 → 有限次重試後進死信**。**沒有這個分級的話，一條格式錯誤的訊息會無限重試並阻塞整個分區。**

## 面試回答方式

先給核心問題（**位移在 Kafka、業務資料在資料庫，不在同一個交易裡**）與三種順序及各自的失敗模式，推薦**先處理後提交位移加冪等**。加分點有四個：**批次的交易邊界有兩種劃法**與**毒訊息的處理**（**失敗時降級為逐條，常態走高效路徑、異常才付逐條成本**）；**位移存進資料庫的實務考量**（rebalance 時要在回呼中 seek），**而多數場景「至少一次加冪等」更簡單且效果相同**；**Kafka 的交易只涵蓋 Kafka 到 Kafka**，**「有交易所以不用擔心」是常見的誤解**；以及**處理失敗要分級**，**否則一條格式錯誤的訊息會無限重試並阻塞整個分區**。

## 講稿

核心問題是位移在 Kafka、業務資料在資料庫，兩者不在同一個交易裡。所以無論怎麼設計，都存在一個窗口讓它們不一致。

我推薦的順序是先處理、後提交位移。業務資料寫入成功才提交位移，中間當機的話位移沒提交，訊息會被重新消費。於是需要冪等，但不會丟資料。反過來先提交後處理則是資料遺失，通常不可接受。

批次的交易邊界我會用整批一個交易，因為冪等讓整批重來是安全的，而效能差距可能是一個數量級。但要處理毒訊息，就是那種怎麼重試都會失敗的。整批就永遠卡住了。做法是失敗時降級為逐條處理，找出那一條送進死信佇列。於是常態走高效的批次路徑，只在異常時付出逐條的成本。

還有一個常見的誤解要澄清。Kafka 的交易能做到 Kafka 到 Kafka 的精確一次，但它不涵蓋外部系統，寫入資料庫的操作不在範圍內。所以有交易所以我不用擔心是錯的。

最後，處理失敗要分級。暫時性的重試、永久性的進死信、未知的有限次重試後進死信。沒有分級的話，一條格式錯誤的訊息會無限重試並阻塞整個分區。

## 常見追問

### 死信佇列的訊息後續怎麼處理？

**核心答案**：**必須有人看，否則死信佇列只是一個垃圾桶**。標準流程是：**告警（死信數量增長時通知）→ 人工或自動分析原因 → 修復後重放**。**而死信訊息應該帶上足夠的中繼資料**：**原始的 topic 與位移、失敗的次數、最後一次的錯誤訊息、以及第一次失敗的時間**——**沒有這些，事後根本不知道發生了什麼。**

**詳細解析**：**「死信佇列被建立但從來沒有人看」是最常見的失敗模式**：它讓團隊有一種「錯誤有被處理」的錯覺——**而實際上那些訊息就在那裡累積，直到某天有人發現半年前就開始丟資料了**。**所以「死信佇列的訊息數」必須是一個有告警的指標**，**而且應該有明確的責任人**。**另一個實務要點是「重放的機制要事先準備」**：**修好 bug 之後怎麼把死信重新處理一遍？** **如果沒有現成的工具，那個修復可能永遠不會發生**——**因為手動處理幾千條訊息的成本太高**。**準備一個「從死信 topic 讀取並重新投遞到原 topic」的工具，成本很低而它讓整個死信機制真正閉環。**

**面試回答方式**：給標準流程與死信訊息應帶的中繼資料。核心加分點是指出**「死信佇列被建立但從來沒有人看」是最常見的失敗模式**——**它給團隊「錯誤有被處理」的錯覺而訊息就在那裡累積**，**所以數量必須是有告警的指標且有明確責任人**。收在**重放機制要事先準備**——**沒有現成工具的話那個修復可能永遠不會發生，因為手動處理幾千條的成本太高**。

### 消費失敗要重試幾次？間隔多久？

**核心答案**：**看失敗的性質**。**暫時性的（下游逾時）**——**指數退避重試三到五次，總時長不超過幾十秒**；**再久就應該讓位給後面的訊息**。**而如果下游長時間不可用**——**繼續重試只是浪費，應該「暫停該分區的消費」等下游恢復**（用 `pause()`），**或者把訊息轉入延遲重試的 topic。**

**詳細解析**：**「在消費迴圈中長時間重試會阻塞整個分區」是這裡最重要的約束**：Kafka 的分區是嚴格有序消費的——**一條訊息卡住，後面的全部等待**。**所以「重試」不能像同步呼叫那樣想重試多久就多久**。**分層重試 topic 是一個常見的模式**：**主 topic 失敗 → 投遞到 `retry-5s` topic → 再失敗 → `retry-1m` → 再失敗 → `retry-10m` → 最後死信**。**每個 retry topic 由獨立的消費者處理並在對應的延遲後重試**——**於是主 topic 的消費完全不被阻塞**。**代價是訊息在重試路徑中失去了與其他訊息的順序關係**——**所以這個模式適用於「不要求嚴格順序」的場景，而那正是多數需要重試的場景。**

**面試回答方式**：給按失敗性質的判斷與短重試的建議。核心加分點是**在消費迴圈中長時間重試會阻塞整個分區**——**Kafka 的分區是嚴格有序消費的，一條卡住後面全部等待**，**所以重試不能像同步呼叫那樣想重試多久就多久**。收在**分層重試 topic** 這個常見模式（5 秒、1 分、10 分、死信）與它的代價：**訊息在重試路徑中失去順序關係，所以適用於不要求嚴格順序的場景**。

### 怎麼確保「處理過的訊息不會再處理一次」？

**核心答案**：**用一個持久化的去重表，key 是訊息的唯一 ID**。處理前檢查、處理後記錄——**而檢查與業務寫入應該在同一個交易中**，**否則仍有窗口**。**唯一 ID 的來源可以是「業務層的冪等鍵」（最好）或者「topic + 分區 + 位移」（通用但在重放場景下會失效）。**

**詳細解析**：**「用業務冪等鍵優於用位移」有一個具體的理由**：位移在重放、跨叢集複製、或者 topic 重建之後會改變——**於是同一條邏輯訊息可能有不同的位移，去重失效**。**而業務層的鍵（訂單 ID、事件 ID）是穩定的**——**無論訊息走了什麼路徑，它都代表同一件事**。**所以「事件應該帶一個全域唯一的事件 ID」是設計時就該做的決定**，**而不是消費端事後想辦法**。**至於去重表的成長**：**它會無限累積，所以需要一個保留策略**（例如只保留 7 天）——**而那意味著「7 天後的重複不會被擋下」**。**判斷這個保留期的依據是「重複可能在多久之後發生」**：**正常的重試在秒級、災難恢復的重放在小時到天級**——**所以 7 天通常足夠，而理解這個推導比記住一個數字重要。**

**面試回答方式**：給做法（持久化去重表、檢查與業務寫入在同一交易中）與 ID 的兩種來源。核心加分點是說明**業務冪等鍵優於位移**——**位移在重放、跨叢集複製、topic 重建後會改變而業務鍵是穩定的**，**所以「事件帶全域唯一 ID」是設計時就該做的決定**。收在去重表的保留策略：**依據是「重複可能在多久之後發生」**——**正常重試在秒級、災難重放在小時到天級**，**理解這個推導比記住一個數字重要**。
