# 題目

消費速度跟不上，怎麼提升？加執行緒有用嗎？

## 核心答案

**先理解 Kafka 的並行上限是分區數**：**一個 partition 在同一個消費者群組內只能被一個消費者實例消費**——**所以「消費者實例數超過分區數」時，多出來的實例完全閒置**。

**提升消費吞吐有三條路徑，順序上應該由簡到繁。**

**一、增加分區與消費者實例**——**最直接，但分區數只能增不能減，而且增加分區會改變 key 的分布（破壞既有的順序保證）**。

**二、單個消費者內部並行處理**——**拉取仍然是單執行緒，但把訊息交給一個執行緒池處理**；**吞吐提升但「位移提交」變複雜（不能簡單地提交最大位移，否則會丟訊息）**。

**三、優化單條訊息的處理時間**——**批次寫資料庫、非同步化外部呼叫、去掉不必要的處理**；**這往往是收益最大且風險最小的一條。**

## 詳細解析

**「內部並行的位移問題」是這裡最需要說清楚的**：訊息被交給執行緒池後亂序完成——**如果直接提交最大的位移，那些還沒處理完的訊息就被視為已消費**；**而如果它們之後失敗了，訊息就永久遺失**。**正確的做法有兩種**：**維護一個「已完成位移」的有序結構，只提交「連續完成的最大位移」**（實作較複雜但精確）；**或者「等一批全部完成才提交」**（簡單但吞吐略低）。**多數框架選擇後者，而理解為什麼不能簡單提交最大值，是這題的關鍵。**

**「先看瓶頸在哪」比盲目加並行重要**：如果消費者的處理是**等待外部服務**（資料庫、API）——**那增加執行緒有效**；**如果是 CPU 密集**——**加執行緒超過核心數就沒有收益**；**而如果瓶頸在下游的容量**（資料庫寫入慢）——**加消費者只會讓下游更擠**。**所以診斷應該先看「消費者的執行緒在等什麼」，而不是直接加並行**。

**「批次處理是最容易被忽略的優化」**：`poll()` 一次可能返回幾百條訊息——**而如果逐條寫入資料庫，那就是幾百次往返**；**改成批次寫入可能提升一個數量級**。**這個優化不需要任何額外的並行，也不影響位移的語義**（**整批完成後提交**）——**是收益與風險比最好的一項**。

**「消費者的參數也影響吞吐」**：`max.poll.records`（單次拉取的訊息數）、`fetch.min.bytes` 與 `fetch.max.wait.ms`（類似生產者的批次）、以及 `max.partition.fetch.bytes`。**而 `max.poll.interval.ms` 是一個容易出問題的參數**：**如果單次 poll 之後的處理時間超過它，消費者會被視為失效並觸發 rebalance**——**這是「處理慢導致反覆 rebalance」這個經典問題的成因**。

## 面試回答方式

先給並行上限（**分區數**）並指出**實例數超過分區數時多出來的完全閒置**。給三條路徑並指出**優化單條訊息的處理時間往往收益最大且風險最小**。加分點有四個：**內部並行的位移問題**——**亂序完成後直接提交最大位移會導致未完成的訊息被視為已消費**，並給兩種正確做法；**先看瓶頸在哪**——**等待外部服務加執行緒有效、CPU 密集超過核心數就沒收益、瓶頸在下游則加消費者只會讓下游更擠**；**批次處理是最容易被忽略的優化**——**逐條寫入變批次可能提升一個數量級且不影響位移語義**；以及 **`max.poll.interval.ms` 是「處理慢導致反覆 rebalance」的成因**。

## 講稿

先理解 Kafka 的並行上限是分區數。一個分區在同一個消費者群組內只能被一個實例消費，所以實例數超過分區數的話，多出來的完全閒置。

提升吞吐有三條路徑。增加分區與實例、單個消費者內部用執行緒池、還有優化單條訊息的處理時間。而第三條往往收益最大而且風險最小。

其中最容易被忽略的是批次處理。一次拉取可能返回幾百條訊息，如果逐條寫入資料庫那就是幾百次往返，改成批次可能提升一個數量級。而且它不需要額外的並行，也不影響位移的語義。

至於內部並行，有一個位移問題必須說清楚。訊息交給執行緒池之後是亂序完成的，如果直接提交最大位移，那些還沒處理完的就被視為已消費，之後失敗了就永久遺失。正確的做法是維護一個已完成位移的有序結構，只提交連續完成的最大值，或者等一批全部完成才提交。

還有一個經典問題的成因。如果單次拉取之後的處理時間超過了輪詢間隔上限，消費者會被視為失效並觸發重平衡。處理慢導致反覆重平衡就是這樣來的。

## 常見追問

### 分區數增加了，既有的順序保證會怎樣？

**核心答案**：**會被破壞**。訊息按 key 的雜湊值對分區數取模決定去哪個分區——**分區數變了，同一個 key 的雜湊結果也會落到不同的分區**。**於是「同一個 key 的訊息在同一個分區因而有序」這個保證，在擴容的那一刻斷開**：**新舊訊息分散在兩個分區，順序不再有保證**。

**詳細解析**：**「擴容的過渡期」需要被明確處理**：如果順序性是必需的——**做法是「等舊分區中該 key 的訊息全部被消費完，再開始寫入新的分區」**，**而那實際上意味著一段時間的暫停或雙寫**。**這個代價讓「分區數應該一開始就規劃足夠」變得很重要**——**因為事後擴容的成本不只是操作，還有這個順序性的斷裂**。**另一個避免的方式是「用自訂的分區器並保持映射穩定」**：**例如用一致性雜湊或者維護一個明確的 key 到分區的映射表**——**於是增加分區只影響一小部分 key**。**但那增加了複雜度，且需要生產者與可能的重分配邏輯配合**。**多數團隊的務實選擇是「一開始就設定比預期需要更多的分區」，接受一些閒置換取未來的彈性。**

**面試回答方式**：明確回答會被破壞並說明機制（取模的結果變了）。核心加分點是**擴容的過渡期需要明確處理**——**順序性必需時要等舊分區的該 key 訊息消費完才寫新的，實際上意味著暫停或雙寫**，**這讓「分區數應該一開始就規劃足夠」變得重要**。收在替代方案與務實選擇：**自訂分區器保持映射穩定能讓擴容只影響一小部分 key 但增加複雜度**，**而多數團隊選擇一開始就設定更多分區，接受閒置換彈性**。

### 消費者處理時間長怎麼避免 rebalance？

**核心答案**：**三個手段**。**調大 `max.poll.interval.ms`**——**最直接，但如果真的卡住了，故障偵測也變慢**。**減少 `max.poll.records`**——**每次拉少一點，處理時間自然短**。**以及「把處理非同步化」**——**poll 之後立刻把訊息交給處理池並返回，讓 poll 迴圈保持快速**；**但這需要處理前面提到的位移問題與背壓（處理池滿了要暫停拉取）**。

**詳細解析**：**「暫停與恢復分區」是非同步處理的關鍵配套**：Kafka 的消費者提供 `pause()` 與 `resume()`——**當處理池積壓時暫停拉取，處理完了再恢復**。**沒有這個機制，非同步化只是把積壓從 Kafka 移到了記憶體中，最終會 OOM**。**而心跳與 poll 的分離也值得知道**：**現代的 Kafka 客戶端用一個背景執行緒發送心跳**——**所以「消費者還活著」與「消費者還在處理」是分開判定的**：**心跳保持連線，而 `max.poll.interval.ms` 判定處理是否卡住**。**理解這個分離能解釋為什麼調 `session.timeout.ms` 對「處理慢」的問題沒有幫助**——**那兩個參數管的是不同的事**。

**面試回答方式**：給三個手段與各自的代價。核心加分點是**暫停與恢復分區是非同步處理的關鍵配套**——**沒有它，非同步化只是把積壓從 Kafka 移到記憶體中最終 OOM**。第二個是**心跳與 poll 的分離**：**背景執行緒發心跳保持連線，而 `max.poll.interval.ms` 判定處理是否卡住**——**理解這個分離能解釋為什麼調 session timeout 對「處理慢」沒有幫助**。

### 一個消費者要處理多個 topic 怎麼設計？

**核心答案**：**看它們的處理特性是否相近**。**相近的（處理時間、失敗處理、優先級都類似）可以訂閱在同一個消費者中**——**省資源且簡單**。**而差異大的應該分開**：**一個慢的 topic 會拖累同一個消費者中的其他 topic**（**因為 poll 迴圈是共用的**）。**尤其是「一個 topic 的訊息處理需要 5 秒，另一個需要 5 毫秒」這種情況，混在一起會讓快的那個也被拖慢。**

**詳細解析**：**「共用 poll 迴圈的耦合」是這個設計最需要注意的**：`poll()` 返回的是所有訂閱分區的訊息混在一起——**而處理它們是串行的**。**所以任何一個 topic 的處理變慢，都會延遲其他 topic 的訊息**。**這與「不要把不同重要性的工作放進同一個執行緒池」是同一個隔離原則**。**而分開的代價是更多的消費者實例與連線**——**在 topic 數量很多時這個成本不可忽略**。**折衷的做法是「按處理特性分組」**：**把處理時間相近、優先級相同的 topic 放在一組**——**於是既有隔離又不至於每個 topic 一個消費者**。**這與執行緒池的分組原則完全一致，而它是一個很好的「同一個原則在不同層次重複出現」的例子。**

**面試回答方式**：給判斷（處理特性相近可以合、差異大要分開）並說明理由（**poll 迴圈共用，慢的會拖累快的**）。核心加分點是把它連結到隔離原則：**與「不要把不同重要性的工作放進同一個執行緒池」是同一個道理**。收在折衷：**按處理特性分組**——**處理時間相近、優先級相同的放一組，既有隔離又不至於每個 topic 一個消費者**，**而這是「同一個原則在不同層次重複出現」的好例子**。
