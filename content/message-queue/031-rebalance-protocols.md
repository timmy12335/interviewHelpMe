# 題目

Kafka 的 rebalance 為什麼會讓所有消費者停頓？後來怎麼改善的？

## 核心答案

**舊的 eager 協定是「全部放棄、重新分配」**：任何一個成員加入或離開——**所有消費者先放棄自己的全部分區（stop-the-world），等新的分配方案下來後再重新開始**。**於是一個消費者的重啟，會讓整個群組停頓幾秒到幾十秒**。

**cooperative（增量式）協定改成「只移動需要移動的」**：**協調者計算出新的分配，只讓那些「分區歸屬改變了」的消費者釋放對應的分區**——**其他消費者完全不受影響，繼續消費**。**代價是需要兩輪 rebalance（第一輪釋放，第二輪分配），但停頓範圍從全部縮小到了一小部分。**

**靜態成員（static membership）則解決另一個問題**：**給消費者一個固定的 `group.instance.id`**——**於是短暫的重啟（滾動更新、Pod 重建）不會觸發 rebalance**，**協調者會等它在 `session.timeout.ms` 內回來並保留它原本的分區。**

## 詳細解析

**「eager 協定為什麼要全部放棄」有一個歷史原因**：分配演算法是在客戶端執行的（leader consumer 計算）——**而為了保證「不會有兩個消費者同時擁有同一個分區」，最簡單安全的做法就是先全部釋放**。**cooperative 的改進在於「協調者可以判斷哪些歸屬沒變」**——**於是那些分區不需要經過釋放與重新獲取的循環**。**這個改進的本質是「從粗粒度的全域同步變成細粒度的增量調整」**，**與很多系統從「全量重算」演進到「增量更新」是同一個模式。**

**「靜態成員的取捨」很明確**：它讓計畫內的重啟不觸發 rebalance——**但代價是「真正掛掉的消費者也要等 session timeout 才被發現」**。**所以 `session.timeout.ms` 需要設得比「正常的重啟時間」長，但又不能太長（否則故障恢復慢）**。**在 Kubernetes 的滾動更新場景中，這個功能非常有價值**——**因為每次部署會依序重啟所有 Pod，而在舊協定下那意味著 N 次全群組停頓**。

**「rebalance 期間位移的處理」是一個容易出錯的地方**：釋放分區前應該提交位移——**否則新的擁有者會從舊位移開始，造成重複消費**。**cooperative 協定提供了 `onPartitionsRevoked` 的回呼讓你做這件事**，**而如果處理不當（例如在回呼中做耗時的操作），會延長 rebalance 的時間。**

**「頻繁 rebalance 的診斷」有明確的順序**：**先看是不是 `max.poll.interval.ms` 超時**（處理太慢）、**再看是不是心跳超時**（GC 停頓或網路）、**然後看是不是消費者實例在反覆重啟**（OOM 或部署問題）。**這三者的日誌訊息不同，能直接區分**——**而盲目調參數通常只是把問題推遲。**

## 面試回答方式

先解釋 **eager 協定是「全部放棄、重新分配」的 stop-the-world**，再說明 **cooperative 只移動需要移動的、代價是兩輪但停頓範圍大幅縮小**，最後給**靜態成員解決的是另一個問題（短暫重啟不觸發 rebalance）**。加分點有四個：**eager 為什麼要全部放棄的歷史原因**——**分配在客戶端計算，全部釋放是保證不重疊最簡單安全的做法**，**而 cooperative 的本質是「從全域同步變成增量調整」**；**靜態成員的取捨**——**真正掛掉的也要等 session timeout 才被發現**，**而在 Kubernetes 滾動更新中它非常有價值**；**rebalance 期間要在回呼中提交位移**，**否則新擁有者會重複消費**；以及**頻繁 rebalance 的診斷順序**（poll 超時、心跳超時、實例反覆重啟），**三者的日誌不同能直接區分**。

## 講稿

舊的協定是全部放棄、重新分配。任何一個成員加入或離開，所有消費者先放棄自己的全部分區，等新的分配方案下來再重新開始。於是一個消費者的重啟會讓整個群組停頓幾秒到幾十秒。

它為什麼要全部放棄？因為分配演算法是在客戶端執行的，而為了保證不會有兩個消費者同時擁有同一個分區，最簡單安全的做法就是先全部釋放。

新的協作式協定改成只移動需要移動的。協調者計算出新分配後，只讓那些歸屬改變了的消費者釋放對應分區，其他人完全不受影響繼續消費。代價是需要兩輪，但停頓範圍從全部縮小到一小部分。這個改進的本質是從粗粒度的全域同步變成細粒度的增量調整。

還有一個叫靜態成員的功能解決另一個問題。給消費者一個固定的實例編號，於是短暫的重啟不會觸發重平衡，協調者會等它在超時時間內回來並保留原本的分區。這在滾動更新的場景特別有價值，因為每次部署會依序重啟所有實例，舊協定下那意味著很多次全群組停頓。

## 常見追問

### 分區分配策略有哪幾種？怎麼選？

**核心答案**：**四種常見的**。**Range**——**按 topic 逐個分配連續的分區範圍**；**簡單但在多 topic 時容易造成不均**（每個 topic 的前幾個分區都給了同一個消費者）。**RoundRobin**——**把所有分區輪流分配**；**更均衡但成員變化時移動量大**。**Sticky**——**在均衡的前提下盡量保持原有的分配**；**減少移動**。**CooperativeSticky**——**Sticky 加上增量式協定**，**是目前的推薦選擇**。

**詳細解析**：**「Range 在多 topic 下的不均」值得具體說明**：假設有 3 個 topic 各 3 個分區、2 個消費者——**Range 對每個 topic 獨立分配，於是 C1 拿到每個 topic 的分區 0 和 1（共 6 個），C2 只拿到分區 2（共 3 個）**。**這種偏斜在 topic 數量多時會很嚴重**，**而它是一個純粹由分配演算法造成的問題，與資料本身無關**。**RoundRobin 把所有 topic 的分區放在一起輪流分配，避免了這個問題**。**而 Sticky 的價值在於「減少不必要的移動」**：**每次 rebalance 後分區的重新獲取需要重建狀態（例如本地的快取或連線）**——**保持原有分配能避免那些成本**。**所以現代的選擇幾乎總是 CooperativeSticky：它同時獲得了均衡、少移動、與增量式的好處。**

**面試回答方式**：給四種策略與各自的特性，並指出 **CooperativeSticky 是目前的推薦**。核心加分點是用具體例子說明 **Range 在多 topic 下的不均**（3 個 topic 各 3 分區、2 個消費者的分布），並指出**這是純粹由演算法造成的偏斜，與資料無關**。收在 **Sticky 的價值是減少不必要的移動**——**重新獲取分區需要重建本地狀態，保持原有分配能避免那些成本**。

### rebalance 時正在處理的訊息怎麼辦？

**核心答案**：**在 `onPartitionsRevoked` 回呼中完成當前的處理並提交位移**——**這是 Kafka 給你的最後機會**。**如果處理需要很長時間，應該考慮「中止當前的處理並不提交」**（**於是新的擁有者會重新處理，前提是消費端冪等**）**而不是拖長 rebalance**。

**詳細解析**：**「回呼中的耗時操作會拖累整個群組」是一個實務上的陷阱**：eager 協定下，**所有消費者都在等最慢的那個完成 revoke**——**於是一個消費者在回呼中花 30 秒，整個群組就停頓 30 秒**。**cooperative 協定緩解了這個問題（只有相關的消費者受影響），但仍然應該讓回呼保持快速**。**而這再次指向同一個結論：消費端冪等是所有可靠性設計的終點**——**因為有了冪等，你可以在任何不確定的時候選擇「不提交、讓它重來」**，**而那是最簡單也最安全的處理**。**沒有冪等的話，每一個邊界情況都需要精確處理，而那在分散式環境中幾乎不可能做對。**

**面試回答方式**：給正確做法（在 revoke 回呼中完成處理並提交位移）與替代（中止不提交，前提是冪等）。核心加分點是**回呼中的耗時操作會拖累整個群組**——**eager 協定下所有人等最慢的那個**。收在結論的呼應：**消費端冪等是所有可靠性設計的終點**——**有了它你可以在任何不確定時選擇「不提交讓它重來」**，**而沒有冪等的話每個邊界情況都要精確處理，那在分散式環境中幾乎不可能做對**。

### 消費者數量該設幾個？

**核心答案**：**不超過分區數，而且要留一點餘裕**。**設成等於分區數時，每個消費者一個分區，並行度最大**——**但任何一個實例故障就有分區沒人消費，直到 rebalance 完成**。**設少一點（例如分區數的一半）讓每個消費者處理兩個分區**——**一個故障時它的分區被其他人接管，而它們還有處理餘力**。

**詳細解析**：**「一比一還是有餘裕」的判斷取決於延遲要求與資源成本**：一比一的並行度最高，適合追求極致吞吐——**但故障時的影響最大（那個分區完全停止直到 rebalance）**。**而有餘裕的配置在故障時只是其他消費者變忙一些，服務不中斷**。**這與服務容量規劃的 N+1 冗餘是同一個思路。** **另一個實務要點是「多出來的消費者實例不是完全無用」**：**它們作為熱備待命，一旦有實例故障，rebalance 會立刻把分區分給它們**——**於是恢復比「等待故障實例重啟」快得多**。**所以在對可用性要求高的場景，故意多開一兩個實例是一個便宜的保險**——**成本只是那些實例的資源，而收益是故障時的快速接管**。

**面試回答方式**：給上限（不超過分區數）與兩種配置的取捨。核心加分點是把它連結到 **N+1 冗餘的思路**——**一比一並行度最高但故障影響最大，有餘裕的配置在故障時只是其他人變忙**。收在**多出來的實例不是完全無用**：**它們作為熱備，故障時 rebalance 立刻把分區分給它們，比等待重啟快得多**——**所以高可用場景故意多開一兩個是便宜的保險**。
