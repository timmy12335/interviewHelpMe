# 題目

Kafka Streams 與 Flink 這類框架解決什麼問題？直接寫消費者不行嗎？

## 核心答案

直接寫消費者能處理「無狀態的逐條轉換」——而框架真正解決的是「有狀態的、跨訊息的計算」。

四類問題是自己寫會很痛苦的。**視窗聚合**——「每五分鐘的訂單總額」需要維護一個按時間分組的狀態，並處理視窗的觸發與清理。**流式 join**——把兩個 topic 按 key 關聯，需要緩衝一邊等待另一邊。**狀態的容錯**——消費者重啟後，那些累積的狀態怎麼恢復。**以及亂序與遲到資料**——事件時間與處理時間不一致時，視窗該什麼時候關閉。

**Kafka Streams 是一個嵌入應用的函式庫**（不需要獨立叢集，狀態存在本地 RocksDB 並備份到 Kafka 的 changelog topic）；Flink 是一個獨立的分散式運算框架（功能更完整、支援更複雜的作業，代價是要維運一個叢集）。

## 詳細解析

「狀態的容錯」是這些框架最核心的價值：一個累積了一小時聚合結果的消費者重啟——如果狀態只在記憶體裡，那一小時就白算了。**Kafka Streams 的做法很優雅**：本地狀態的每一次變更都寫入一個 changelog topic（壓實的）——**於是重啟時從那個 topic 重建狀態**。這讓「狀態的持久化」複用了 Kafka 本身的複製與持久化能力，而不需要另一套機制。理解這個設計，比記住 API 有價值得多。

「事件時間與水印」是流式處理最需要理解的概念：資料可能亂序到達（網路延遲、上游重試）——所以「五分鐘的視窗什麼時候可以關閉」不能單看時鐘。水印（watermark）是一個「我認為事件時間早於 T 的資料都到齊了」的宣告——它由框架根據觀察到的事件時間推進。而遲到超過水印的資料進入側輸出流或被丟棄。這個機制的本質是「在完整性與延遲之間做一個明確的取捨」——等越久越完整但延遲越高，而水印讓這個取捨變成一個可調的參數而非隱式的行為。

「什麼時候不需要框架」也要說清楚：**無狀態的轉換、過濾、路由**——直接寫消費者更簡單也更容易除錯。而「簡單的計數」如果可以用外部儲存（Redis 或資料庫）維護狀態——**那也不需要框架**，代價是每條訊息一次外部往返。判斷的分界是「狀態的規模與存取頻率」：小而低頻用外部儲存，大而高頻才值得引入框架的本地狀態。

**「Kafka Streams 與 Flink 的選擇」**：如果資料源與輸出都是 Kafka、作業不太複雜、且不想維運額外的叢集——**Kafka Streams 的簡單性很有價值**。而如果需要接多種資料源、需要更複雜的視窗與 join、或者需要更好的資源隔離與擴縮容——**Flink 更合適。**

## 面試回答方式

先給區分（直接寫消費者能處理無狀態的逐條轉換，框架解決有狀態的跨訊息計算）與四類痛苦的問題，再比較兩個框架的形態。加分點有四個：**狀態的容錯是最核心的價值**——Kafka Streams 把本地狀態的變更寫入壓實的 changelog topic 並在重啟時重建，這複用了 Kafka 本身的複製能力而不需要另一套機制；**事件時間與水印**——水印是「早於 T 的資料都到齊了」的宣告，本質是把「完整性與延遲的取捨」變成一個可調的參數；**什麼時候不需要框架**——判斷分界是狀態的規模與存取頻率；以及**兩個框架的選擇依據**。

## 講稿

直接寫消費者能處理無狀態的逐條轉換。而框架真正解決的是有狀態的、跨訊息的計算。

有四類問題是自己寫會很痛苦的。視窗聚合、流式關聯、狀態的容錯、還有亂序與遲到資料的處理。

其中我認為最核心的價值是狀態的容錯。一個累積了一小時聚合結果的消費者重啟，如果狀態只在記憶體裡就白算了。Kafka Streams 的做法很優雅，本地狀態的每一次變更都寫入一個壓實的變更日誌主題，重啟時從那裡重建。這讓狀態的持久化複用了 Kafka 本身的複製與持久化能力，不需要另一套機制。

## 常見追問

### 本地狀態與外部儲存怎麼選？

**核心答案**：**看存取頻率與狀態大小**。**本地狀態（RocksDB）**——每次存取是本地磁碟或記憶體，延遲微秒級；**適合高頻存取的大狀態**。**外部儲存（Redis、資料庫）**——每次存取是一次網路往返，延遲毫秒級；適合低頻或者需要被其他系統查詢的狀態。在每秒幾萬條訊息的處理中，這個差距是決定性的。

**詳細解析**：「本地狀態的代價是與分區綁定」：狀態按 key 分區存在對應的實例上——**於是 rebalance 時狀態需要遷移或重建**，**而那可能需要幾分鐘（從 changelog topic 重放）**。**Kafka Streams 用「standby replica」緩解這個問題**：在另一個實例上維護一份熱備狀態——**於是接管時不需要重建**。**代價是額外的儲存與網路**。而外部儲存沒有這個問題（任何實例都能存取任何 key）——這是它在「需要快速擴縮容」場景下的優勢。所以這個選擇不只是效能，還包含了運維特性：本地狀態快但擴縮容慢，外部儲存慢但無狀態實例可以自由伸縮。

**面試回答方式**：給選擇依據（存取頻率與狀態大小）並量化延遲差距。核心加分點是指出本地狀態的代價是與分區綁定——rebalance 時需要遷移或重建，可能幾分鐘，並介紹 **standby replica** 的緩解與代價。收在更完整的比較：這個選擇不只是效能還包含運維特性——本地狀態快但擴縮容慢，外部儲存慢但實例可以自由伸縮。

### 遲到的資料該怎麼處理？

**核心答案**：**三種策略，按業務需求選**。**丟棄**——最簡單，適合「遲到的資料不重要」（例如即時儀表板）。**更新已輸出的結果**——重新計算受影響的視窗並發出一個修正；需要下游能處理修正（冪等的更新而非累加）。**送入側輸出流**——交給一個單獨的流程處理（例如寫入一個「遲到資料」的 topic 供批次修正）。

**詳細解析**：「允許遲到多久」是一個明確的取捨參數（Kafka Streams 的 grace period、Flink 的 allowed lateness）：設得長——結果更完整，但視窗的狀態要保留更久（記憶體壓力）且最終結果的延遲更高；**設得短——快但可能遺漏**。**而判斷的依據應該來自實測**：觀察「事件時間與處理時間的差」的分布——如果 p99 是 30 秒，那 grace period 設一分鐘能覆蓋絕大多數。這比憑感覺設一個數字好得多。另一個實務要點是「遲到資料的比例應該被監控」：它突然上升通常意味著上游出了問題（重試、積壓、時鐘偏移）——而那是一個比「結果稍有偏差」更值得關注的訊號。

**面試回答方式**：給三種策略與各自的適用場景。核心加分點是「允許遲到多久」的取捨與判斷依據：觀察「事件時間與處理時間的差」的分布，p99 是 30 秒的話 grace period 設一分鐘——**比憑感覺設一個數字好得多**。收在監控：遲到資料的比例突然上升通常意味著上游出了問題（重試、積壓、時鐘偏移），而那是比「結果稍有偏差」更值得關注的訊號。

### 流式處理能做到精確一次嗎？

**核心答案**：**在「Kafka 到 Kafka」的範圍內可以**——用 Kafka 的交易把「消費的位移提交」與「產出的訊息寫入」放進同一個原子操作。於是重啟後不會重複產出也不會遺漏。但一旦輸出到外部系統（資料庫、API），就超出了這個保證的範圍——那需要外部系統自己的冪等或交易支援。

**詳細解析**：「精確一次是端到端的性質而非某個元件的性質」是最重要的認知：Kafka 的交易保證了它自己這一段——而整條鏈路的語義由最弱的那一環決定。所以「我們用了 Kafka 的精確一次」這句話需要被追問「端到端的哪一段」。實務上，多數系統的正確做法仍然是「至少一次加上外部系統的冪等」——因為它更簡單、效能更好、而且在跨系統的情況下本來就是唯一可行的。而 Kafka 交易真正有價值的場景是「純粹的流式處理管線」（消費 topic A、處理、產出 topic B）——在那裡它確實提供了自己實作很難達到的保證。能區分「哪一段用交易划算、哪一段用冪等」，比籠統地說「我們做到了精確一次」有價值得多。

**面試回答方式**：給範圍（Kafka 到 Kafka 可以，輸出到外部系統就超出保證）。核心加分點是精確一次是端到端的性質而非某個元件的性質——整條鏈路由最弱的那一環決定，所以「我們用了 Kafka 的精確一次」需要被追問是哪一段。收在實務判斷：多數系統仍是「至少一次加外部冪等」因為更簡單效能更好，而 Kafka 交易真正有價值的是純粹的流式管線。
