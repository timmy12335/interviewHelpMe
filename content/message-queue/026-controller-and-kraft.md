# 題目

Kafka 的 controller 負責什麼？為什麼要從 ZooKeeper 換成 KRaft？

## 核心答案

Controller 是叢集中的一個特殊角色，負責「中繼資料的管理與變更的協調」：**partition 的 leader 選舉**、**broker 上下線的偵測與處理**、**topic 的建立與刪除**、以及把中繼資料的變更廣播給所有 broker。

**舊架構的問題有三個**。**外部依賴**——需要獨立部署與維運一個 ZooKeeper 叢集，而它有自己的故障模式與調校需求。**擴展性瓶頸**——controller 啟動時要從 ZooKeeper 載入全部中繼資料，partition 數量大時這個過程可能要幾分鐘，期間叢集無法處理中繼資料變更。**一致性模型的縫隙**——中繼資料同時存在於 ZooKeeper 與 controller 的記憶體中，兩者之間的同步是一個額外的複雜度來源。

KRaft 把中繼資料本身做成一個 Kafka 的內部 topic，**用 Raft 協定在一組 controller 節點之間複製**——於是中繼資料的變更就是「往一個 log 追加」，而 broker 只需要消費那個 log。

## 詳細解析

「中繼資料變成一個 log」是這個設計最優雅的地方：broker 不再需要「被通知」——它只要記住自己讀到哪個位移，落後了就繼續讀。這讓「broker 重啟後怎麼追上中繼資料」變成一個已經被解決的問題（就是消費一個 topic），**而不需要另外設計同步機制**。**而 controller 的故障轉移也變快了**：新的 controller 只需要從 log 的最新快照加上後續的變更恢復狀態，而不是從 ZooKeeper 一次性載入全部。

「controller 是單一活躍的」在兩種架構下都成立：同一時間只有一個 controller 在做決策——這避免了多個節點同時做 leader 選舉造成的衝突。**KRaft 下這個「唯一性」由 Raft 的 leader 選舉保證**，**而舊架構靠 ZooKeeper 的臨時節點**。兩者都需要處理「舊 controller 還以為自己是 controller」的腦裂情況——Kafka 用 controller epoch（一個單調遞增的號碼）解決：broker 拒絕來自舊 epoch 的指令。這與分散式系統中的柵欄令牌是同一個機制。

**「效能提升的量級」值得知道**：官方的測試顯示 KRaft 下「controller 故障轉移」與「大量 partition 的叢集啟動」從幾分鐘降到幾秒——這對大規模叢集的運維體驗是質的改變。而 partition 數量的上限也從幾萬提升到百萬級。

**「遷移是漸進的」**：Kafka 提供了從 ZooKeeper 模式遷移到 KRaft 的路徑（雙寫過渡）——但它是一個需要謹慎規劃的操作，**而新叢集應該直接用 KRaft**。

## 面試回答方式

先給 controller 的職責（leader 選舉、broker 上下線、topic 管理、中繼資料廣播），再給舊架構的三個問題（外部依賴、擴展性瓶頸、一致性縫隙），最後說明 KRaft 把中繼資料做成一個 Kafka 內部 topic 用 Raft 複製。加分點有四個：**「中繼資料變成一個 log」最優雅**——broker 不再需要被通知，只要記住讀到哪個位移，於是重啟後追上中繼資料變成一個已解決的問題；**controller 的唯一性與腦裂處理**——用 controller epoch 讓 broker 拒絕舊 epoch 的指令，與柵欄令牌是同一個機制；**效能提升的量級**——故障轉移與叢集啟動從幾分鐘降到幾秒，partition 上限從幾萬到百萬級；以及遷移是漸進的但新叢集應該直接用 KRaft。

## 講稿

控制器負責中繼資料的管理與變更的協調。分區的領導者選舉、節點上下線的偵測、主題的建立刪除、還有把變更廣播給所有節點。

舊架構有三個問題。需要額外部署維運一個協調服務、控制器啟動時要一次載入全部中繼資料而分區多的時候要好幾分鐘、還有中繼資料同時存在兩個地方帶來的同步複雜度。

新的架構把中繼資料本身做成一個 Kafka 的內部主題，用共識協定在一組控制器節點之間複製。我覺得最優雅的地方是中繼資料變成了一個日誌。節點不再需要被通知，它只要記住自己讀到哪個位移，落後了就繼續讀。於是節點重啟後怎麼追上中繼資料，變成一個已經被解決的問題，就是消費一個主題而已。

控制器的唯一性在兩種架構下都要保證，而且都要處理舊控制器還以為自己是控制器的腦裂。Kafka 用一個單調遞增的紀元號解決，節點拒絕來自舊紀元的指令。這跟分散式系統裡的柵欄令牌是同一個機制。

效能上，故障轉移跟大叢集啟動從幾分鐘降到幾秒。

## 常見追問

### broker 怎麼知道自己該當某個 partition 的 leader？

**核心答案**：由 controller 決定並下發，而不是 broker 自己競選。controller 維護每個 partition 的 ISR 列表——當現任 leader 失效時，它從 ISR 中選一個新的 leader 並把決定寫進中繼資料；所有 broker 消費到這個變更後更新自己的角色。選擇的規則是「優先選 ISR 中的第一個（通常是最早加入的）」，而不是選擇資料最多的——因為 ISR 中的成員在定義上都是同步的。

**詳細解析**：「偏好 leader（preferred leader）」是一個容易忽略但影響負載均衡的機制：每個 partition 的副本列表中的第一個被視為偏好 leader——**Kafka 會週期性地嘗試把 leadership 遷回它**，**目的是讓 leader 均勻分布在所有 broker 上**。**因為 leader 承擔了所有的讀寫流量**（**follower 只做複製**）——如果 leadership 集中在少數 broker 上，那幾台會成為瓶頸。**所以「偏好 leader 選舉」預設是開啟的（`auto.leader.rebalance.enable`）**，而它的執行會造成短暫的分區不可用——這是一個「短暫的擾動換取長期的均衡」的取捨。知道這個機制能解釋一個常見的現象：叢集在沒有任何操作的情況下偶爾出現短暫的 leader 變更。

**面試回答方式**：給機制（**controller 決定並下發，broker 不自己競選**）與選擇規則（從 ISR 中選，因為 ISR 成員在定義上都是同步的）。核心加分點是**偏好 leader 機制**：副本列表的第一個是偏好 leader，Kafka 週期性把 leadership 遷回它以讓負載均勻，因為 leader 承擔所有讀寫而 follower 只做複製。收在它的副作用：執行時會造成短暫的分區不可用，而知道這個能解釋「叢集沒有任何操作卻偶爾出現短暫 leader 變更」這個現象。

### 中繼資料很大時客戶端會有問題嗎？

**核心答案**：**會**。客戶端需要知道「每個 topic 的每個 partition 的 leader 在哪個 broker」——一個有幾萬個 partition 的叢集，這份中繼資料本身就不小。問題表現為：客戶端啟動慢、中繼資料更新時的網路尖峰、以及大量客戶端同時刷新時對 broker 的壓力。緩解的方式是「只請求需要的 topic 的中繼資料」而非全叢集的（現代客戶端預設如此）。

**詳細解析**：「中繼資料的刷新時機」是一個容易產生問題的地方：客戶端在遇到 `NOT_LEADER_FOR_PARTITION` 之類的錯誤時會刷新中繼資料——而如果一次 leader 變更影響了很多 partition，所有客戶端會同時刷新，形成一個尖峰。**這是一個典型的「驚群」問題**，而緩解靠客戶端側的退避與抖動（`metadata.max.age.ms` 與重試的隨機化）。另一個實務要點是「不要建立過多的 partition」：partition 數量影響的不只是 broker 的檔案控制代碼與記憶體，還有每個客戶端要維護的中繼資料量——而後者在客戶端數量多的情況下是一個容易被忽略的放大效應。這也是「分區數怎麼定」這個問題需要考慮的一個維度。

**面試回答方式**：給問題的表現（啟動慢、更新時的網路尖峰、大量客戶端同時刷新的壓力）與緩解（只請求需要的 topic）。核心加分點是中繼資料的刷新時機容易產生驚群——一次 leader 變更影響很多 partition 時所有客戶端同時刷新，**緩解靠退避與抖動**。收在**partition 數量的影響不只在 broker 側**——每個客戶端都要維護中繼資料，而在客戶端數量多時這是被忽略的放大效應。

### KRaft 的 controller 節點該部署幾個？

**核心答案**：**奇數個，通常是 3 或 5**——**與任何 Raft 叢集一樣**。**3 個能容忍 1 個故障，5 個能容忍 2 個**。更多不會提升可用性反而降低寫入效能（**每次寫入要等多數派確認**）。而 controller 可以與 broker 混合部署（小叢集）或獨立部署（大叢集）——後者讓中繼資料的處理不受業務流量影響。

**詳細解析**：「獨立部署 controller」在大叢集是明確更好的選擇：broker 承擔了大量的 IO 與網路流量——而 controller 需要穩定的、低延遲的響應來維持 Raft 的心跳。混合部署時，一次業務流量的尖峰可能導致 controller 的心跳超時並觸發不必要的 leader 選舉——而那會造成中繼資料操作的短暫不可用。這與「不要把 etcd 與工作負載放在同一台機器」是完全相同的道理。至於 controller 節點的資源需求：CPU 與記憶體都不高，但對磁碟延遲敏感（**Raft 的寫入要落盤**）——所以應該用 SSD，而這一點與 broker 更需要吞吐的特性正好不同，**也是獨立部署的另一個理由**。

**面試回答方式**：給數量建議（奇數，3 或 5）與理由（更多不提升可用性反而降低寫入效能）。核心加分點是**大叢集應該獨立部署 controller**——broker 的流量尖峰可能導致 controller 心跳超時並觸發不必要的選舉，與「不要把 etcd 與工作負載放同一台機器」是相同的道理。收在資源特性的差異：controller 對磁碟延遲敏感（Raft 寫入要落盤）而 broker 更需要吞吐，**這是獨立部署的另一個理由**。
