# 題目

發到訊息佇列的訊息該怎麼設計？帶多少資訊？

## 核心答案

**先分清三種訊息的語義，因為它們的設計原則不同。**

**事件（event）**——**「某件事發生了」**（`OrderPlaced`）；**過去式、不指定誰處理、可以有多個消費者**。**這是訊息佇列最主要的用法。**

**命令（command）**——**「請做某件事」**（`SendEmail`）；**祈使句、有明確的目標處理者、通常只有一個消費者**。

**文件或狀態（document）**——**「這是當前的狀態」**（一個完整的訂單快照）；**用於同步而非通知。**

**而事件的內容設計有兩個極端**：**「薄事件」只帶 ID（消費者自己去查詳情）**——**耦合低但消費者要多一次查詢，而且查到的可能是已經變化的狀態**；**「胖事件」帶完整的資料**——**消費者自足且看到的是事件發生當時的狀態，但事件與生產者的資料模型耦合更緊。**

## 詳細解析

**「薄事件的時間錯位問題」常被低估**：消費者收到「訂單已建立」的事件後去查詢訂單——**而此時訂單可能已經被取消了**。**於是消費者處理的是「當前狀態」而非「事件發生時的狀態」**——**這在需要按事件順序處理的場景中是錯誤的**。**胖事件沒有這個問題，因為狀態被凍結在事件裡**。**所以「事件應該自足」在多數情況下是對的**——**而它的代價（與生產者資料模型的耦合）可以透過「明確定義事件的 schema 而非直接序列化內部物件」來緩解**。

**「事件不應該是資料庫變更的直接映射」是一個重要的設計判斷**：`UserTableRowUpdated` 這種事件洩漏了內部的儲存結構——**於是生產者的任何 schema 變更都會影響消費者**。**而 `UserEmailChanged` 表達的是業務含義**——**它與內部如何儲存無關**。**這個區別決定了「事件是一個穩定的契約」還是「一個隨時可能變的內部細節」**。**CDC 產生的正是前一種，所以它適合資料同步而不適合作為業務事件的來源**——**能區分這兩種用途，是設計事件驅動架構時的關鍵判斷。**

**「事件要帶什麼中繼資料」有幾個標準項**：**事件 ID（用於冪等）、事件類型與版本、發生時間（事件時間而非發送時間）、以及關聯 ID（trace ID，用於追蹤）**。**這些常被遺漏，而它們在排查問題時的價值極高**——**尤其是關聯 ID，它讓「這個事件是由哪個請求觸發的」變成一個可以直接查詢的問題**。

**「不要在事件中放不穩定的東西」**：內部的列舉值、資料庫的自增 ID、以及可能被重構的欄位名——**它們一旦出現在事件中就變成了公開契約的一部分**。**設計事件時應該問「我願意在未來三年裡維持這個欄位嗎」**。

## 面試回答方式

先分清三種訊息語義（事件、命令、文件）並指出**事件是最主要的用法**。給薄事件與胖事件的取捨。加分點有四個：**薄事件的時間錯位問題**——**消費者查到的是當前狀態而非事件發生時的狀態，在需要按序處理時是錯的**，**所以「事件應該自足」在多數情況下是對的**；**事件不應該是資料庫變更的直接映射**——**那洩漏內部儲存結構，而業務含義的事件與內部如何儲存無關**，**這也是 CDC 適合資料同步而不適合作為業務事件來源的原因**；**標準的中繼資料**（事件 ID、類型與版本、事件時間、關聯 ID）**常被遺漏而排查價值極高**；以及**不要在事件中放不穩定的東西**，**設計時要問「我願意在未來三年維持這個欄位嗎」**。

## 講稿

我會先分清三種語義。事件是某件事發生了，過去式、不指定誰處理、可以有多個消費者。命令是請做某件事，有明確的目標處理者。文件是這是當前的狀態，用於同步而不是通知。

事件的內容設計有兩個極端。薄事件只帶編號，消費者自己去查詳情。胖事件帶完整資料。

我傾向胖事件，因為薄事件有一個常被低估的問題，時間錯位。消費者收到訂單已建立的事件之後去查詢，而此時訂單可能已經被取消了。於是它處理的是當前狀態而不是事件發生時的狀態，這在需要按順序處理的場景中是錯的。胖事件沒有這個問題，因為狀態被凍結在事件裡。

還有一個重要的設計判斷，事件不應該是資料庫變更的直接映射。某某表的某一列被更新了這種事件洩漏了內部儲存結構，生產者的任何變更都會影響消費者。而使用者信箱已變更表達的是業務含義，跟內部怎麼存無關。這也是為什麼變更資料捕捉適合資料同步，但不適合作為業務事件的來源。

另外事件要帶事件編號、類型版本、事件時間、還有關聯編號。最後那個在排查時價值極高。

## 常見追問

### 事件驅動會不會讓系統變得難以理解？

**核心答案**：**會，這是它最真實的代價**。同步呼叫的流程可以從程式碼直接讀出來——**而事件驅動的流程分散在多個服務中，沒有一個地方能看到完整的鏈路**。**緩解的手段有三**：**完整的分散式追蹤**（讓一次業務流程的鏈路可視）、**明確的事件目錄**（記錄有哪些事件、誰產生、誰消費）、**以及在文件中維護關鍵流程的圖**。

**詳細解析**：**「事件目錄」是最容易做也最容易被忽略的一項**：一份記錄「事件名稱、schema、生產者、消費者、以及業務含義」的清單——**它讓「改這個事件會影響誰」變成一個可以查詢的問題**。**而沒有它，每次變更都要靠問人或搜尋程式碼**。**現代的做法是「從程式碼自動產生」**（**掃描註冊的生產者與消費者**）——**於是它不會過時**。**另一個有價值的觀察是「事件驅動的可理解性問題在小規模時被低估」**：**三個服務的時候一切都很清楚，而三十個服務的時候沒有人知道全貌**——**所以追蹤與目錄應該在規模還小的時候就建立，因為那時建立的成本最低而後續的回報持續累積**。

**面試回答方式**：誠實承認**這是它最真實的代價**並給三個緩解手段。核心加分點是**事件目錄最容易做也最容易被忽略**——**它讓「改這個事件會影響誰」變成可以查詢的問題**，**而現代做法是從程式碼自動產生所以不會過時**。收在時機的判斷：**可理解性問題在小規模時被低估**——**三個服務時一切清楚而三十個時沒人知道全貌**，**所以追蹤與目錄應該在規模還小時就建立，那時成本最低而回報持續累積**。

### 一個事件應該被多少個消費者處理？

**核心答案**：**事件的設計目標就是「不知道也不在乎有幾個消費者」**——**這正是它與命令的區別**。**生產者只負責「宣告這件事發生了」**；**新增一個消費者不需要生產者做任何改動**。**而如果你發現「加一個消費者需要改生產者」，那說明它實際上是一個命令而非事件。**

**詳細解析**：**「這個判準能診斷出很多設計問題」**：例如一個事件裡帶了「應該發送郵件」這樣的欄位——**那就是把命令偽裝成事件**，**於是生產者實際上知道並關心下游會做什麼**。**正確的做法是「生產者只說發生了什麼，由消費者決定要不要做以及做什麼」**。**這個區分的實質收益是「新增功能不需要改動既有的服務」**——**而那正是事件驅動架構聲稱的最大好處**。**如果一個系統宣稱是事件驅動但每次加功能都要改生產者，那它只是用訊息佇列做遠端呼叫，並沒有得到解耦的好處**——**而這種情況比想像中常見。**

**面試回答方式**：給核心設計目標（**不知道也不在乎有幾個消費者，這正是與命令的區別**）並給出診斷判準：**如果加一個消費者需要改生產者，那它實際上是命令而非事件**。核心加分點是舉例（事件裡帶「應該發送郵件」的欄位是把命令偽裝成事件）並指出**正確的做法是生產者只說發生了什麼**。收在判斷：**宣稱事件驅動但每次加功能都要改生產者的系統，只是用訊息佇列做遠端呼叫**，**而這比想像中常見**。

### 事件的版本怎麼管理？

**核心答案**：**在事件中帶版本號，並用 schema registry 的相容性檢查強制**。**多數變更應該是相容的（新增有預設值的欄位）**；**而不相容的變更應該「發布一個新的事件類型」而非修改既有的**——**例如 `OrderPlacedV2`，讓新舊消費者各自訂閱需要的版本，生產者在過渡期同時發布兩種。**

**詳細解析**：**「發布新事件類型而非修改舊的」比想像中乾淨**：它讓「誰還在用舊版本」變成一個可觀測的問題（看舊 topic 的消費者群組）——**而不是一個需要協調的猜測**。**過渡期結束的判斷也很明確：舊事件沒有活躍的消費者了就可以停止發布**。**代價是過渡期的雙寫成本與兩份 schema 的維護**。**而這個模式與 API 的版本化完全一致**——**只是在事件驅動中它更重要，因為消費者是解耦的、你可能不知道有誰在用**。**能把「事件的演進」與「API 的演進」對應起來，說明理解了它們共同的本質：一個被多方依賴的契約，其變更必須是漸進且可觀測的。**

**面試回答方式**：給做法（帶版本號、用相容性檢查強制、不相容時發布新事件類型）。核心加分點是說明**發布新類型比修改舊的乾淨**——**它讓「誰還在用舊版本」變成可觀測的問題而非需要協調的猜測**，**過渡期結束的判斷也很明確**。收在對應：**這與 API 的版本化完全一致，只是在事件驅動中更重要，因為消費者解耦而你可能不知道有誰在用**。
