# 題目

Pulsar 說自己是「儲存與運算分離」，這相對 Kafka 帶來什麼差別？

## 核心答案

**Kafka 的 broker 同時負責服務與儲存**——資料存在 broker 的本機磁碟上，所以擴容 broker 時必須**搬移分區資料**，資料量大時這個過程很慢且會影響線上流量。**Pulsar 把兩者拆開**——broker 只負責服務（無狀態），資料存在獨立的儲存層中。這帶來三個差別：**一、擴容更快**——增加 broker 不需要搬資料，它立刻就能服務任何分區；**二、故障恢復更快**——broker 掛掉時另一個 broker 直接接手，不必等待資料複製；**三、儲存與運算可以獨立擴展**——資料量大但吞吐不高時只加儲存節點，反之只加 broker。代價則是**架構更複雜**（多一個儲存系統要維運，加上協調服務）、**延遲路徑更長**（多一跳網路）、以及**生態系統相對小**（工具、整合、社群經驗都不如 Kafka 豐富）。所以選擇的判準通常不是效能，而是**運維模式與團隊能力**。

## 詳細解析

**Kafka 擴容的真實痛點**：新增 broker 之後，必須執行分區重新分配把資料搬過去，這個過程可能持續數小時甚至數天（取決於資料量與頻寬限制），期間會佔用網路與磁碟 IO 影響線上流量。所以 Kafka 叢集的擴容是一個**需要規劃與監控的專案**而非隨時可做的操作。這正是儲存分離架構想解決的問題。分層儲存（把舊資料移到物件儲存）在較新的版本中緩解了這一點，但熱資料仍在本機。

**Pulsar 的訂閱模型更靈活**：它在同一個主題上支援多種訂閱模式——**獨佔**、**故障轉移**、**共享**（多個消費者競爭同一個訂閱，類似傳統佇列）、**鍵共享**（依鍵分配但不綁定分區）。其中**共享模式**讓消費者數量不受分區數限制，這正是 Kafka 的一個明確限制。所以需要「任務分發的彈性」又要「日誌的持久性」時，Pulsar 的模型確實更貼合。

**多租戶是 Pulsar 的原生設計**：它有租戶與命名空間的層級，可以在其上設定隔離、配額與權限。Kafka 的多租戶需要靠外部治理與命名規範達成。在平台團隊要服務多個業務團隊的環境中，這個差異是實際的維運價值。

**選型不該只看架構優劣**：Kafka 的**生態系統成熟度**是實質的優勢——連接器、串流處理框架、監控工具、雲端託管服務、以及大量可查詢的實戰經驗。遇到問題時能不能快速找到答案，往往比架構是否優雅更影響專案成敗。所以除非有明確的痛點（擴容困難、需要儲存運算獨立擴展、需要原生多租戶），否則 Kafka 通常是更穩妥的選擇。

**託管服務改變了這個決策**：如果使用雲端的託管服務，擴容與運維的複雜度大部分由服務商承擔，「儲存分離帶來的運維優勢」對使用者的價值就下降了。此時選型的重點回到**功能需求與成本**，而非底層架構。這一點在現代的技術選型中越來越重要——**你要維運的東西才需要在意它的運維特性**。

## 面試回答方式

先把差別的**根源**講清楚——Kafka 的 broker 同時負責服務與儲存，所以擴容要搬資料；Pulsar 拆開之後 broker 無狀態，擴容與故障恢復都更快。給出三個具體差別（擴容快、恢復快、獨立擴展）與三個代價（架構複雜、多一跳延遲、生態較小）。加分點有三個：**Pulsar 的共享訂閱模式讓消費者數不受分區數限制**，這正是 Kafka 的明確限制；**Kafka 的生態成熟度是實質優勢**，遇到問題能不能快速找到答案往往比架構優雅更重要；以及**用託管服務時運維優勢的價值下降**，選型重點回到功能與成本——你要維運的東西才需要在意它的運維特性。

## 講稿

差別的根源是 Kafka 的 broker 同時負責服務跟儲存，資料存在本機磁碟上。所以擴容的時候必須搬移分區資料，量大的話可能好幾小時甚至幾天，期間還會影響線上流量。

Pulsar 把兩者拆開，broker 只負責服務、本身無狀態，資料存在獨立的儲存層。這帶來三個差別。擴容更快，增加 broker 不用搬資料就能服務任何分區。故障恢復更快，broker 掛了另一個直接接手。還有儲存跟運算可以獨立擴展。

代價是架構更複雜，多一個儲存系統要維運，延遲路徑也多一跳，而且生態系統相對小。

另外 Pulsar 的訂閱模型值得一提。它支援共享模式，消費者數量不受分區數限制，這正好是 Kafka 的一個明確限制。

不過我的立場是，除非有明確的痛點，像擴容真的很困難、或需要原生的多租戶，否則 Kafka 通常還是比較穩妥。因為它的生態成熟度是實質優勢，遇到問題能不能快速找到答案，常常比架構優不優雅更影響專案成敗。

還有一點，如果用雲端託管服務，運維複雜度大部分由服務商承擔，儲存分離的優勢對我的價值就下降了，選型重點會回到功能跟成本。

## 常見追問

### Kafka 的分層儲存解決了什麼問題？

**核心答案**：解決的是**冷資料佔用昂貴本機磁碟**的問題。啟用之後，較舊的日誌段會被移到物件儲存，本機磁碟只保留熱資料。好處是**可以用更長的保留期而不必等比增加本機磁碟**，也讓擴容時要搬移的資料量下降（只搬熱資料）。但它**沒有讓 broker 變成無狀態**——熱資料仍在本機，所以擴容仍需要搬移，只是規模變小。

**詳細解析**：使用時要注意**讀取冷資料的效能**——從物件儲存讀取的延遲遠高於本機磁碟，所以需要重放大量歷史資料的消費者會明顯變慢，而且可能影響其他消費者（佔用 broker 的資源）。所以它適合「**保留很久但很少讀取**」的資料，例如合規要求的保存或偶爾的回溯分析；不適合經常需要重讀歷史的場景。另外要評估**物件儲存的請求費用**——大量小請求的費用可能超出預期，所以段的大小與讀取模式都要納入成本估算。這類「新功能解決了一部分問題但帶來新的取捨」的分析，比單純說「有這個功能」有價值。

**面試回答方式**：說明它解決冷資料佔用本機磁碟的問題並帶來更長保留期，但明確指出它沒有讓 broker 無狀態、擴容仍需搬移熱資料。加分點是講讀取冷資料的延遲與對其他消費者的影響，以及物件儲存的請求費用需要納入成本估算。

### 什麼情況會讓你認真考慮從 Kafka 換到 Pulsar？

**核心答案**：三種情況。**擴容已經成為實際痛點**——資料量大到每次擴容都要花數天並影響線上，而業務成長速度讓這件事頻繁發生。**需要消費者數量不受分區數限制**——任務量波動極大的場景，希望能隨時增減消費者。**需要原生的多租戶隔離**——平台團隊服務多個業務方，希望有租戶層級的配額與權限而不是靠命名規範治理。除此之外，遷移的成本（重寫客戶端、重建監控、團隊學習曲線）通常高於收益。

**詳細解析**：即使符合上述情況，也應該先評估**有沒有更小的改動能解決**——擴容痛點可能靠分層儲存與更好的容量規劃緩解；消費彈性的需求可能靠拆分 topic 或改用不同的處理模型解決；多租戶可能靠更嚴格的命名與配額規範達成。**遷移訊息中介是高風險的工程**，因為它通常是系統的核心樞紐，牽動所有上下游。所以合理的決策順序是：先量化痛點的實際成本、再評估較小的改動能解決多少、最後才考慮遷移，並且要把遷移期間的雙跑成本算進去。能表達這個保守但有依據的態度，通常比熱情推薦新技術更受面試官認可。

**面試回答方式**：給三種明確的觸發情況並指出其他時候遷移成本高於收益。加分點是強調即使符合也要先評估更小的改動能否解決，並說明遷移訊息中介是高風險工程（牽動所有上下游），給出「量化痛點、評估小改動、最後才考慮遷移」的決策順序。

### 訊息中介的選型，除了技術特性還該考慮什麼？

**核心答案**：至少三項。**團隊的運維能力與既有經驗**——一個團隊熟悉的技術即使不是最優，通常也比不熟悉的最優解跑得更穩。**生態與整合**——需要的連接器、串流處理、監控工具是否現成，這直接決定了開發與維運的工作量。**託管服務的可得性**——如果雲端有成熟的託管選項，自建的運維成本可以省下，這常常是最大的成本項。

**詳細解析**：還有兩個容易被忽略的：**招募與知識傳承**——冷門技術的人才難找，而且團隊成員離開時知識流失的風險更高。**長期支援與社群活躍度**——專案是否持續維護、有沒有明確的版本支援政策，這決定了幾年後你是不是被困在一個沒人維護的版本上。這些「非技術」因素在多年期的系統中往往比效能差異更決定成敗。面試中能提出這些，會顯示你的思考尺度是產品生命週期而不只是當下的技術指標——這在資深職缺的評估中很有份量。

**面試回答方式**：給三項（團隊能力、生態整合、託管可得性）並各一句理由。加分點是補上兩個容易被忽略的因素：招募與知識傳承、以及長期支援與社群活躍度，並指出這些非技術因素在多年期系統中往往比效能差異更決定成敗。
