# 題目

生產者怎麼決定訊息要送到哪個分區？在什麼情況下會出現亂序？

## 核心答案

分區的決定有三種方式：**指定分區**（直接寫死，最少用）、**依鍵的雜湊**（有鍵時的預設行為，相同鍵必定落到相同分區，這是保證同鍵有序的基礎）、以及**無鍵時的分配策略**（新版預設會**黏著批次**——在一段時間內把訊息集中送到同一個分區直到批次填滿，這比逐條輪詢更能提升批次效率）。至於亂序，即使同鍵落在同一分區，仍可能因為**重試**而亂序：如果允許多個請求同時在途中（未確認），前一個批次失敗重試時，後一個批次可能已經寫入，於是順序顛倒。控制它的關鍵參數是單一連線上允許的未確認請求數——設為 1 可以嚴格保證順序但吞吐低；比較好的做法是**啟用冪等生產者**，它讓 broker 依序號去重與排序，即使允許多個未確認請求也能保證單分區內的順序，兼顧吞吐與正確性。

## 詳細解析

**鍵的選擇決定了一切**：鍵不只影響分區，也影響**熱點**與**順序保證的粒度**。選擇原則是「**業務上需要保序的最小單位**」——訂單狀態變更用訂單 ID、帳戶餘額變更用帳戶 ID。用太粗的鍵（例如整個商戶）會造成熱點，用太細的鍵（例如每則訊息一個唯一 ID）則等於沒有順序保證。這是設計時最值得花時間的決定。

**批次與延遲的取捨**：生產者會把訊息累積成批次再送出，由**批次大小**與**等待時間**兩個參數控制。等待時間設為 0 表示有訊息就送，延遲最低但吞吐最差（每次請求的固定開銷被放大）；設幾毫秒到幾十毫秒能顯著提升吞吐，代價是端到端延遲增加。判斷依據是**業務對延遲的實際要求**——多數資料管線可以接受幾十毫秒，即時通知類則不行。

**壓縮應該在生產端開啟**：壓縮是對**整個批次**進行的，所以批次越大壓縮率越好。生產端壓縮之後，broker 通常直接儲存壓縮後的資料，消費端才解壓——這意味著壓縮同時節省了**網路頻寬、磁碟空間與 broker 的處理**，收益是全鏈路的。代價是生產端與消費端的 CPU 開銷，但對多數文字類訊息（JSON）非常划算。

**訊息遺失的三個生產端來源**：**發送失敗未處理**（用了不等待回應的發送方式，錯誤回呼沒有處理）、**未等待足夠的副本確認**（確認策略設得太寬鬆，leader 寫入就回成功，leader 掛掉時資料還沒同步出去）、以及**緩衝區滿時的丟棄行為**（生產者的緩衝區滿了，依設定可能阻塞或拋錯，處理不當就會漏）。這三者要分別處理，只調確認策略是不夠的。

同步發送不是唯一的可靠做法：每條訊息都同步等待回應會讓吞吐極差。正確的做法是**非同步發送加上回呼處理**——在回呼中處理失敗（記錄、告警、或寫入本地補償佇列），既保留吞吐又不遺漏錯誤。這是實務上最常見的正確模式，而「為了可靠所以改成同步」是常見的過度反應。

## 面試回答方式

先給三種分區方式，並強調依鍵雜湊是保證同鍵有序的基礎。接著直接回答亂序的來源——**重試加上多個未確認請求**會讓順序顛倒，並給出兩種解法：把未確認請求數設為 1（安全但慢）或**啟用冪等生產者**（兼顧吞吐與順序，是實務上的正解）。加分點有三個：**鍵的選擇原則**是「業務上需要保序的最小單位」，太粗造成熱點、太細等於沒保證；**壓縮在生產端開啟**能同時省網路、磁碟與 broker 處理，收益是全鏈路的；以及**可靠不等於同步發送**，正確做法是非同步加回呼處理失敗。

## 講稿

分區的決定有三種方式。可以直接指定分區，但很少用。有鍵的時候依鍵的雜湊決定，相同的鍵必定落到相同分區，這是保證同鍵有序的基礎。沒有鍵的時候新版預設會黏著批次，在一段時間內集中送到同一個分區直到批次填滿，這比逐條輪詢更有效率。

鍵怎麼選我覺得是最值得花時間的決定。原則是選業務上需要保序的最小單位。訂單狀態變更就用訂單 ID。用太粗的鍵會造成熱點，用太細的等於沒有順序保證。

至於亂序，就算同鍵落在同一分區還是可能發生，來源是重試。如果我允許多個請求同時在途中，前一個批次失敗重試的時候，後一個批次可能已經寫進去了，順序就顛倒了。

控制它的參數是單一連線上允許的未確認請求數。設成一可以嚴格保證順序但吞吐很差。比較好的做法是啟用冪等生產者，它讓 broker 依序號去重跟排序，就算允許多個未確認請求也能保證單分區內有序。

另外我想澄清一點，可靠不等於同步發送。每條都同步等回應吞吐會很差。正確的做法是非同步發送加上回呼處理失敗。

## 常見追問

### 生產端在哪些情況會遺失訊息？

**核心答案**：三個來源。**發送失敗沒有被處理**——用非同步發送卻沒有實作錯誤回呼，失敗就靜默消失了。**確認策略太寬鬆**——只等 leader 寫入就視為成功，若 leader 所在的 broker 在同步給 follower 之前掛掉，資料就沒了。**緩衝區滿時的行為**——生產者本地緩衝區滿了之後，依設定會阻塞或拋出例外，若程式沒有處理這個例外就會漏掉訊息。

**詳細解析**：對應的處理分別是：**一定要處理回呼中的失敗**，並決定失敗後的行為（重試、寫入本地檔案、或告警並停止）；確認策略設為等待所有同步副本確認，並配合最小同步副本數的設定（否則只剩一個副本時仍然會回成功）；緩衝區滿時選擇阻塞而非丟棄，讓壓力往上傳遞而不是靜默遺失。最徹底的做法是在應用層引入**本地暫存加補償**——先寫入本地（資料庫或檔案），確認送達後再標記完成，這樣即使程式崩潰也不會遺失。這正是 outbox 模式的思路，代價是額外的儲存與複雜度。

**面試回答方式**：列出三個來源並各給對應的處理方式，重點是確認策略要搭配最小同步副本數才有意義。加分點是提出本地暫存加補償這個最徹底的做法，並指出它就是 outbox 模式的思路與其代價。

### 批次與延遲的參數該怎麼調？

**核心答案**：從**業務能接受的延遲**反推。等待時間設為 0 表示有訊息就送，延遲最低但每次請求的固定開銷被放大、吞吐最差；設成幾毫秒到幾十毫秒能顯著提升吞吐與壓縮率。批次大小則決定了單次請求最多累積多少，兩者是「先到者觸發」的關係——等待時間到了或批次滿了就送出。所以調整時要一起看，只調其中一個常常沒有效果。

**詳細解析**：實務上的判斷順序是：先確認目前是延遲問題還是吞吐問題。如果吞吐不足且延遲有餘裕，加大等待時間與批次通常立刻見效。如果延遲不足，那要看延遲花在哪裡——可能根本不在生產端而在消費端積壓或下游處理。另外要注意**壓縮與批次的關係**：壓縮是對整批進行的，批次太小壓縮率很差，所以開了壓縮卻沒調批次，效果會遠低於預期。最後，這些參數的調整應該**在真實流量下量測驗證**，因為最佳值與訊息大小、分區數、網路狀況都相關，照抄別人的設定通常不適用。

**面試回答方式**：說明兩個參數是「先到者觸發」的關係、要一起調。給出判斷順序：先確認是延遲問題還是吞吐問題。加分點是指出壓縮率依賴批次大小（開了壓縮沒調批次效果會差很多），以及參數要在真實流量下量測而非照抄。

### 為什麼說「用同步發送保證可靠」是過度反應？

**核心答案**：因為可靠性來自「確認機制與失敗處理」，不是來自「同步等待」。非同步發送同樣會收到 broker 的確認結果，只是透過回呼而非阻塞返回；只要在回呼中正確處理失敗，可靠性完全相同，而吞吐可能高出一個數量級。改成同步的真正效果是把吞吐壓到「每次往返只能送一條訊息」，這在高流量下往往直接成為瓶頸。

**詳細解析**：會出現這種誤解，通常是因為非同步的錯誤處理容易被忽略——回呼中的例外若沒有被妥善處理，失敗就靜默消失，於是有人得出「非同步不可靠」的結論。正確的做法是把回呼的失敗處理當成必要的實作而非可選項，並且**監控發送失敗的計數**。真正需要同步等待的情況是業務流程必須知道結果才能繼續（例如要在同一個交易中確認訊息已送出），但這種需求通常暗示應該改用 outbox 模式——先在本地交易中記錄，再由獨立的流程負責可靠投遞，這樣既保證一致性又不犧牲吞吐。

**面試回答方式**：核心是可靠來自確認與失敗處理而非同步等待，非同步同樣收得到結果。指出誤解來自回呼錯誤處理被忽略。加分點是說明真正需要同步的場景（業務必須知道結果）通常該改用 outbox 模式，兼顧一致性與吞吐。
