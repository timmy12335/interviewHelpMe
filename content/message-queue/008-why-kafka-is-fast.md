# 題目

Kafka 的資料是寫在磁碟上的，為什麼還能有這麼高的吞吐？

## 核心答案

因為它把每個瓶頸都換成了硬體最擅長的操作。**一、順序寫而非隨機寫**——每個分區是一個只追加的日誌檔案，寫入永遠在末端，磁碟的順序寫速度可以比隨機寫高出兩三個數量級，即使是傳統硬碟也能達到很高的吞吐。二、依賴作業系統的頁快取而非自行管理記憶體——寫入先進頁快取由作業系統決定何時落盤，讀取也優先從頁快取取得；這避免了在 JVM 堆積中維護大量快取所帶來的記憶體開銷與垃圾回收壓力，而且**行程重啟後快取仍然有效**（快取在作業系統手上）。**三、零拷貝**——把資料從檔案送到網路時，不必經過「檔案讀進使用者空間、再從使用者空間寫入通訊端」這兩次多餘的複製，直接在核心中完成，大幅減少 CPU 與記憶體頻寬的消耗。**四、批次與壓縮**——生產者累積成批再送、broker 原樣儲存壓縮後的批次、消費者取走時也是整批，讓每則訊息攤到的固定開銷極小。

## 詳細解析

**順序寫的價值常被低估**：多數人直覺認為「寫磁碟一定慢」，但慢的是**隨機**寫——磁頭尋道或快閃記憶體的寫入放大才是成本所在。只追加的日誌完全避開了這些，加上作業系統會把連續的寫入合併，實際落盤的效率很高。這個設計選擇也帶來一個副作用：**Kafka 不支援刪除單則訊息**，只能按時間或大小整段清理——這是「用功能換效能」的明確取捨。

**頁快取的兩個隱含好處**：一是不必為快取付出垃圾回收的代價，這對 JVM 應用意義重大——若把幾十 GB 的資料放在堆積中，垃圾回收停頓會難以接受。二是**重啟後快取仍在**，因為它屬於作業系統而非行程；重啟一個持有大量堆積內快取的服務，通常要花很久才能重新暖機，Kafka 沒有這個問題。代價是**broker 的記憶體規劃思路不同**——不應該把大部分記憶體配給 JVM 堆積，而應該留給作業系統做頁快取。

零拷貝的前提是資料不需要在使用者空間被處理：因為消費者拿到的就是儲存在檔案中的原始批次（含壓縮），broker 不需要解開來看，才能直接從檔案送到網路。這解釋了為什麼**broker 端不做訊息轉換**——一旦需要在 broker 上改動訊息內容（例如轉換格式），零拷貝就失效了，吞吐會明顯下降。理解這個依賴關係，才知道哪些功能在架構上是「便宜的」、哪些是「昂貴的」。

**批次是全鏈路的**：生產者批次送出、broker 以批次為單位儲存、消費者以批次為單位取走，壓縮也是對整批進行。所以批次大小同時影響網路、磁碟、CPU 與壓縮率，是最值得調整的參數之一。反過來，過度追求低延遲而把批次縮到極小，會讓所有這些優化同時失效。

**它不是萬用的「快」**：Kafka 的強項是**高吞吐的順序讀寫**，不是低延遲的隨機存取。需要「查詢某一則特定訊息」「按條件過濾」「單則訊息的毫秒級延遲」時，它並不是好選擇——那些需求應該用資料庫或專門的低延遲佇列。把它當成資料庫用是常見的誤用，這一點值得在面試中主動點出。

## 面試回答方式

用**四個機制**組織回答（順序寫、頁快取、零拷貝、批次與壓縮），每個一句話說清它換掉了什麼瓶頸。主動糾正一個直覺——**慢的是隨機寫不是寫磁碟**，只追加的日誌完全避開了尋道成本。頁快取的部分要講出兩個隱含好處：**不必付垃圾回收代價**、**重啟後快取仍在**，並補上「broker 的記憶體應該留給作業系統而非 JVM 堆積」這個實務結論。加分點有兩個：零拷貝的前提是 broker 不處理訊息內容，所以在 broker 上做轉換會讓它失效；以及誠實指出它的強項是高吞吐順序讀寫，**不適合當成可查詢的資料庫**，這是常見的誤用。

## 講稿

因為它把每個瓶頸都換成了硬體最擅長的操作，我覺得有四個。

第一是順序寫。每個分區是一個只追加的日誌檔案，寫入永遠在末端。很多人直覺認為寫磁碟一定慢，但慢的其實是隨機寫，尋道才是成本。順序寫的吞吐可以比隨機寫高兩三個數量級。

第二是依賴作業系統的頁快取，而不是自己在 JVM 堆積裡管理快取。這有兩個好處，不用付垃圾回收的代價，還有重啟之後快取仍然有效，因為它在作業系統手上。所以 broker 的記憶體規劃應該是留給頁快取，而不是把大部分配給堆積。

第三是零拷貝。把資料從檔案送到網路的時候，不用先讀進使用者空間再寫出去，直接在核心裡完成。這件事的前提是 broker 不需要處理訊息內容，消費者拿到的就是檔案裡原本的批次。所以如果在 broker 上做格式轉換，零拷貝就失效了。

第四是批次跟壓縮，而且是全鏈路的，生產者批次送、broker 批次存、消費者批次取。

不過我想補一句，它的強項是高吞吐的順序讀寫，不是低延遲的隨機查詢。把它當資料庫用是常見的誤用。

## 常見追問

### 資料寫進頁快取但還沒落盤，會不會遺失？

**核心答案**：單機層面會，所以 Kafka 靠副本而非落盤來保證可靠。寫入頁快取後若機器突然斷電，尚未落盤的資料確實會遺失。Kafka 的設計選擇是**不強制每次寫入都同步落盤**（那會嚴重影響吞吐），而是靠**多副本**——資料同步到多個 broker 的頁快取中，單一機器斷電時其他副本仍有資料。這是「用冗餘換效能」的取捨。

**詳細解析**：Kafka 也提供強制落盤的設定（依訊息數或時間間隔觸發），但通常不建議開啟——它會讓吞吐大幅下降，而收益有限，因為**同時斷電多台機器**的機率遠低於單機故障，而後者已經由副本涵蓋。真正該投資的是**副本的分布**（跨機架、跨可用區）與**電源的可靠性**，而不是強制落盤。這個判斷的通用形式是：面對故障要問「我要防禦哪種故障模式」，然後選擇針對該模式最有效的手段，而不是把所有可用的保護都打開。

**面試回答方式**：明確說單機會遺失，並說明 Kafka 靠副本而非落盤保證可靠，這是用冗餘換效能。加分點是指出強制落盤通常不建議（吞吐代價大而收益有限），該投資的是副本分布，並歸納出「先問要防禦哪種故障模式」這個通用判斷。

### 為什麼消費者從舊資料開始讀會變慢？

**核心答案**：因為**頁快取只涵蓋熱資料**。正常消費時消費者緊跟在寫入位置後面，讀取幾乎都命中頁快取，等同於記憶體速度。但如果消費者從很舊的位移開始（新群組從頭讀、或積壓嚴重），要讀的資料早已不在快取中，必須**從磁碟讀取**，速度差距很大；而且這些讀取還會**擠掉頁快取中的熱資料**，連帶影響其他正常的消費者。

**詳細解析**：這是實務上很典型的干擾——一個新上線的服務從頭重讀歷史資料，導致整個叢集的正常消費者延遲上升。緩解方式包括：**在低峰期做歷史重讀**、**限制該消費者的拉取速率**、或在有條件時把重讀的流量導到專門的副本或叢集。另外新版本支援從**最近的副本**讀取，可以把跨區的讀取流量與本地熱資料的競爭分開。監控上要注意「**讀取來源是快取還是磁碟**」這類指標——它能提前發現這種干擾，而單看吞吐往往看不出來。

**面試回答方式**：解釋頁快取只涵蓋熱資料，讀舊資料要落磁碟且會擠掉熱資料影響其他消費者。給出三種緩解（低峰期、限速、分流）。加分點是提到監控「讀取來自快取還是磁碟」能提前發現這種干擾，單看吞吐看不出來。

### 訊息很大（例如幾 MB）時該怎麼處理？

**核心答案**：**盡量不要讓大訊息進入 Kafka**。它的設計假設是大量的小訊息，大訊息會造成多重問題：批次效率下降、記憶體壓力上升（生產者、broker、消費者三端都要為單則訊息配置緩衝）、單則處理時間變長而容易觸發 rebalance、以及各層的大小上限都要調整（生產者、broker、topic、消費者拉取上限缺一不可）。標準做法是把大內容存到物件儲存，訊息中只放參照。

**詳細解析**：這個「**只傳參照不傳內容**」的模式（有時稱為 claim check）帶來額外的好處：訊息本身變小、Kafka 的保留成本下降、而且大內容可以有自己的生命週期管理。代價是**多一個依賴**與**一致性問題**——要確保消費者讀取時內容還在（物件儲存的清理策略要與訊息的保留策略協調），以及處理「訊息到了但物件還沒寫完」的時序（先寫物件再發訊息可以避免）。如果確實必須傳大訊息，那至少要**四層大小上限一起調**，並且**降低批次與拉取數量**避免記憶體爆掉——只調其中一層是最常見的錯誤，症狀是「小訊息正常、大訊息失敗」。

**面試回答方式**：先給結論——不要讓大訊息進 Kafka，並列出它造成的四類問題。給出參照模式的標準做法與它的額外好處。加分點是講清代價（多一個依賴、要處理時序與清理協調），以及若必須傳大訊息，四層上限要一起調、否則症狀是小訊息正常大訊息失敗。
