# 題目

冪等生產者解決什麼問題？Kafka 的交易能達成「精準一次」嗎？

## 核心答案

**冪等生產者**解決的是「**重試造成重複**」。生產者會被分配一個識別碼，並為每個分區的訊息編上遞增序號；broker 記住每個生產者在每個分區的最後序號，收到重複或亂序的序號就丟棄或拒絕。效果是**單一生產者、單一分區、單一工作階段內不重複也不亂序**，而且開銷很小，所以應該預設啟用。**交易**則提供更大的範圍——**跨多個分區與 topic 的原子性**，一組寫入要嘛全部可見、要嘛全部不可見；更重要的是它能把**消費位移的提交也納入同一個交易**，於是「讀取、處理、寫出」可以是原子的。這讓 **Kafka 到 Kafka 的串流處理**確實達成精準一次。但範圍到此為止——一旦處理過程中有**外部副作用**（寫資料庫、呼叫第三方），Kafka 的交易管不到那些系統，此時的精準一次必須靠**外部系統自身的冪等或交易**。所以務實的立場是：**用至少一次的傳輸加上消費端冪等**，效果等價而適用範圍廣得多。

## 詳細解析

**冪等生產者的三個邊界**：**單一分區**（跨分區不保證，那需要交易）、**單一工作階段**（生產者重啟後識別碼改變，去重狀態失效，需要交易提供的持久識別碼）、以及**broker 端記憶有限**（只記住最近若干個序號，落後太久的重試無法被識別）。理解這三個邊界才知道它解決了什麼、沒解決什麼——很多人以為開了它就萬無一失，其實只涵蓋了最常見的一種重複來源。

**交易的運作方式**：生產者向協調者宣告開始交易，寫入的訊息會被標記為交易的一部分；提交時協調者寫入標記，消費端在**只讀已提交**的隔離層級下才會看到這些訊息。中止的交易訊息仍然在日誌中但不會被讀取。這意味著交易 topic 的消費端**必須設定正確的隔離層級**，否則會讀到未提交甚至已中止的訊息——這是使用交易時最常見的設定遺漏。

**交易的代價**：吞吐下降（多了協調與標記的往返）、延遲上升（消費端要等交易提交才看得到訊息）、以及**運維複雜度**（交易逾時、掛起的交易會阻塞消費端的讀取進度，需要監控與處理）。所以它不該是預設選項，而是在確認需要跨分區原子性時才引入。

**外部副作用的正確處理**：真實的消費端幾乎都有外部副作用，所以與其追求協定層的精準一次，不如把**冪等做在資料層**。三種常見做法是：**業務唯一鍵加上唯一索引**（重複插入直接失敗）、**去重表記錄已處理的訊息識別**（要與業務寫入在同一個交易中，否則仍有窗口）、以及**讓操作本身冪等**（設定為某值而非增減、用條件更新比對版本）。第三種最乾淨，能設計成這樣就優先選它。

**「精準一次」這個詞容易誤導**：它在分散式系統中通常指的是「**效果上等同於恰好執行一次**」，而非「訊息在網路上只傳送一次」——後者在有故障的環境中不可能保證。理解這個定義之後就會發現，**至少一次加冪等**本來就是達成它的標準途徑，而不是次一等的替代方案。能講清楚這個概念，通常比背出交易的 API 更有價值。

## 面試回答方式

先分清**兩者的範圍**——冪等生產者是單分區單工作階段的去重，交易是跨分區的原子性並可綁定位移。接著明確界定精準一次的適用範圍：**Kafka 到 Kafka 可以，有外部副作用時 Kafka 管不到**。然後給出務實立場——**至少一次加消費端冪等**，並補上關鍵論點：**精準一次指的是「效果上恰好一次」而非「只傳一次」**，所以這本來就是達成它的標準途徑而非退而求其次。加分點有三個：冪等生產者的三個邊界（單分區、單工作階段、broker 記憶有限）；**交易 topic 的消費端必須設定只讀已提交**，這是最常見的設定遺漏；以及掛起的交易會阻塞消費進度，需要監控。

## 講稿

冪等生產者解決的是重試造成重複。生產者有一個識別碼，訊息帶遞增序號，broker 記住每個分區的最後序號，重複的就丟掉。它的保證範圍是單一生產者、單一分區、單一工作階段內不重複也不亂序。開銷很小，我會預設啟用。

但它有三個邊界。跨分區不保證，那需要交易。生產者重啟之後識別碼會變，去重狀態就失效了。還有 broker 只記最近若干個序號，落後太久的重試識別不出來。

交易的範圍更大，提供跨多個分區跟 topic 的原子性，而且可以把消費位移的提交也放進同一個交易。所以讀取、處理、寫出可以是原子的，Kafka 到 Kafka 的串流處理確實能做到精準一次。

但範圍就到這裡。一旦處理過程有外部副作用，寫資料庫或呼叫第三方，Kafka 的交易管不到那些系統。

所以我的立場是用至少一次的傳輸加上消費端冪等。而且我想澄清一個概念，精準一次指的是效果上等同於恰好執行一次，不是訊息在網路上只傳一次，後者在有故障的環境根本不可能保證。理解這個定義之後就會發現，至少一次加冪等本來就是達成它的標準途徑，不是次一等的替代。

## 常見追問

### 使用交易時消費端要注意什麼？

**核心答案**：**必須把隔離層級設成只讀已提交**。預設可能是讀取未提交的訊息，那樣會讀到還在交易中甚至最終被中止的訊息，造成下游處理了不該存在的資料。這是使用交易時最常見也最嚴重的設定遺漏——生產端做對了，消費端沒改，等於交易白做。

**詳細解析**：設定之後還有兩個影響要知道。**延遲增加**——消費端只能讀到已提交的位置，所以訊息要等交易提交才可見，長交易會顯著拉高端到端延遲。**掛起的交易會阻塞讀取進度**——如果某個生產者在交易進行中崩潰且未在逾時內被清理，消費端會卡在那個位置無法前進，症狀是「積壓一直增加但沒有任何錯誤」。所以使用交易的系統應該**監控掛起交易的數量與最舊的未完成交易時間**，並把交易逾時設得夠短。另外交易應該**盡量短**——把大批次拆成小交易，既降低延遲也減少掛起的影響範圍。

**面試回答方式**：明確指出必須設定只讀已提交，否則交易白做。接著給兩個影響：延遲增加、以及掛起的交易會阻塞讀取造成「積壓增加但無錯誤」的症狀。加分點是建議監控掛起交易與最舊未完成時間，並讓交易盡量短。

### 消費端冪等具體怎麼做？

**核心答案**：三種做法，優先序由高到低。**讓操作本身天然冪等**——用「設定為某值」取代「增減」、用條件更新比對版本號，這最乾淨且不需要額外儲存。**業務唯一鍵加唯一索引**——用訂單號、交易流水號當唯一約束，重複插入直接失敗即可忽略。**去重表**——記錄已處理的訊息識別，處理前先查；但它**必須與業務寫入在同一個交易中**，否則「業務寫了但去重紀錄沒寫」的窗口仍會造成重複。

**詳細解析**：去重表還有兩個常被忽略的問題。**清理策略**——不清理會無限成長，清理太早又可能讓晚到的重複訊息通過，保留期應該大於訊息可能延遲的最長時間。**識別的選擇**——用 Kafka 的 topic、分區、位移組合當識別在多數情況可行，但如果訊息會被重新產生（上游重放），位移會變而業務上其實是同一筆，此時應該用**業務層的識別**。這個選擇要看重放的可能性，選錯會讓冪等在重放時完全失效。整體而言，能設計成「天然冪等」的操作永遠是最好的，其他兩種都是補救。

**面試回答方式**：給三種做法並排優先序，強調天然冪等最乾淨。重點指出去重表必須與業務寫入同交易，否則仍有窗口。加分點是講去重表的清理策略與識別選擇（位移在重放時會變，應該用業務識別），並說明選錯會讓冪等在重放時失效。

### 什麼時候真的需要用 Kafka 交易？

**核心答案**：主要是 **Kafka 到 Kafka 的串流處理**——從一個或多個 topic 讀取、處理後寫入其他 topic，需要「寫出結果」與「提交位移」同時成功或同時失敗。沒有這個原子性時，故障可能造成「結果寫出去了但位移沒提交」（重啟後重複產出）或反之（結果遺失）。另一個場景是**需要跨多個 topic 原子寫入**的業務，例如一個事件必須同時進入兩個下游流。

**詳細解析**：值得注意的是，即使在串流處理場景，也**不一定要自己管理交易**——串流處理框架通常內建了這套機制，設定一個保證層級的參數即可，比手寫交易安全得多。手寫交易容易漏掉的細節包括：交易逾時與處理時間的關係、生產者識別碼在重啟後的延續、以及例外路徑上是否正確中止交易。所以實務建議是：**能用框架就用框架，不要自己組裝交易語意**。這個「用成熟實作而非自己組裝」的判斷，在涉及分散式一致性的功能上特別重要，因為錯誤往往只在罕見的故障時序下才顯現。

**面試回答方式**：給出兩個真正需要的場景（串流處理的原子性、跨 topic 原子寫入）。加分點是建議用串流框架內建的保證層級而非手寫交易，並列出手寫容易漏掉的細節，歸結為「涉及分散式一致性時用成熟實作而非自己組裝」。
