# 題目

一台 broker 掛了會發生什麼？磁碟壞了怎麼恢復？

## 核心答案

broker 掛掉時，controller 會偵測到（透過心跳或 session 超時）並為它上面的所有 leader partition 選出新的 leader——**通常在幾秒到幾十秒內完成**。這期間那些 partition 不可用，客戶端會重試並更新中繼資料。

恢復的路徑取決於資料是否還在。

資料完好（例如只是行程掛了或機器重啟）——broker 啟動後會做日誌恢復（檢查最後一個 segment 的完整性），然後作為 follower 從 leader 追平落後的部分；**追上之後重新加入 ISR。**

**資料遺失（磁碟損壞）**——用同樣的 broker ID 啟動一個空的 broker，它會從各個 leader 完整複製所有它應該持有的 partition；資料量大時這個過程可能很久，而期間叢集的複製流量會顯著上升。

而如果連 broker ID 都要換（例如換一台新機器）——需要執行分區重分配把原來的副本分配過去。

## 詳細解析

「非正常關閉後的日誌恢復」可能很慢：Kafka 在正常關閉時會寫一個乾淨關閉的標記——而如果是 kill -9 或斷電，啟動時必須掃描最後的 segment 驗證每條訊息的 CRC。partition 數量多時，這個過程可能持續數分鐘到數十分鐘。**`num.recovery.threads.per.data.dir` 可以調高來並行處理**——這是一個在故障恢復時很有價值但平時被忽略的參數。

「空 broker 重建的流量衝擊」需要被預期：一台持有 5TB 資料的 broker 重建——**意味著要從其他 broker 拉取 5TB**，而那個流量會與正常的生產消費競爭。**所以應該用 `replication.quota` 限制重建的頻寬**——代價是恢復更慢，但保住了正常服務。這與分區重分配的限流是同一個機制與同一個取捨。

「多磁碟的部分故障」是一個特殊情況：Kafka 支援多個 `log.dirs`——而較新的版本能處理「單個磁碟故障」而不讓整個 broker 下線（**只有那個磁碟上的 partition 離線**）。這降低了單一磁碟故障的影響範圍，但也意味著監控需要覆蓋「離線的 log dir」這個狀態——否則你會有一個「活著但少了三分之一分區」的 broker。

「什麼時候該直接換掉而非修復」：如果磁碟已經損壞、或者恢復的時間預期長於重建的時間——直接用新機器加入並重分配可能更快。判斷的依據是「這台機器的資料量與可用頻寬」——而在雲端環境中，換一台新機器通常比修復舊的快得多，也更可靠。

## 面試回答方式

先給故障時的行為（controller 偵測並重新選舉 leader、幾秒到幾十秒、客戶端重試）與**兩種恢復路徑**（資料完好則追平、資料遺失則完整重建）。加分點有四個：非正常關閉後的日誌恢復可能很慢——要掃描最後的 segment 驗證 CRC，partition 多時持續數分鐘到數十分鐘，而 recovery threads 是故障時很有價值但平時被忽略的參數；空 broker 重建的流量衝擊要用限流控制，與重分配是同一個機制與取捨；**多磁碟的部分故障**——較新版本能只讓那個磁碟的 partition 離線，但監控必須覆蓋「離線的 log dir」否則會有一個活著但少了分區的 broker；以及什麼時候該直接換掉而非修復的判斷依據。

## 講稿

節點掛掉時，控制器會偵測到並為它上面的所有領導者分區選出新的領導者，通常幾秒到幾十秒完成。這期間那些分區不可用，客戶端會重試並更新中繼資料。

恢復的路徑取決於資料在不在。如果資料完好，節點啟動後做日誌恢復，然後作為跟隨者追平落後的部分。如果磁碟壞了，用同樣的節點編號啟動一個空的，它會從各個領導者完整複製所有應該持有的分區。

這裡有兩個實務上的坑。第一，非正常關閉後的日誌恢復可能很慢。正常關閉會寫一個乾淨的標記，而被強制終止或斷電的話，啟動時必須掃描最後的區段驗證每條訊息的校驗碼。分區多的時候可能持續數十分鐘。恢復執行緒數這個參數可以調高來並行處理，它在故障時很有價值但平時被忽略。

第二，空節點重建的流量衝擊要預期。一台持有五 TB 資料的節點重建意味著要從其他節點拉五 TB，那個流量會跟正常服務競爭。所以要用複製配額限制頻寬，代價是恢復更慢但保住了正常服務。

## 常見追問

### 恢復期間的訊息會丟嗎？

**核心答案**：在 `acks=all` 加 `min.insync.replicas=2` 加 3 副本的標準配置下不會——因為每條已確認的訊息至少在兩個副本上，掛一台仍有一份。**而如果配置是 `acks=1` 或 `min.insync.replicas=1`**——leader 確認後還沒複製到 follower 就掛掉的那些訊息會遺失。所以「會不會丟」完全取決於配置而非故障本身。

**詳細解析**：**「acks=1 的遺失窗口比想像中大」**：leader 收到訊息後立刻確認——而 follower 的下一次 fetch 可能在幾十毫秒之後。在高吞吐下，那個窗口裡可能有幾千條訊息。於是一次 leader 故障可能丟掉幾千條——而且生產者已經收到了成功的確認，完全不知道發生了什麼。這種「靜默的遺失」是最危險的，因為沒有任何錯誤可以觸發告警。所以對於「不能丟」的資料流，`acks=all` 不是可選的優化而是必要條件——而它的效能代價（等待複製）在有 `linger.ms` 批次的情況下其實相當有限，這也是為什麼「用 acks=1 換效能」通常是一個不划算的取捨。

**面試回答方式**：給明確的答案（**標準配置下不會，acks=1 或 min.insync=1 則會**）並強調這完全取決於配置而非故障本身。核心加分點是**acks=1 的遺失窗口比想像中大**——leader 確認到 follower fetch 之間可能有幾千條訊息，而生產者已收到成功確認完全不知情，這種靜默遺失最危險因為沒有錯誤可以觸發告警。收在取捨：acks=all 的效能代價在有批次的情況下相當有限，**所以用 acks=1 換效能通常不划算**。

### 怎麼驗證恢復真的完成了？

**核心答案**：看 `UnderReplicatedPartitions` 回到 0 且該 broker 重新出現在所有應該持有的 partition 的 ISR 中。只看「行程起來了」或「沒有錯誤日誌」是不夠的——broker 可能已經在運行但還在追趕大量的落後資料，而此時叢集仍處於冗餘度不足的狀態。

**詳細解析**：「恢復是一個過程而非一個事件」是這裡最重要的認知：broker 啟動只是開始——真正的恢復是「所有分區重新達到完整的副本數」，**而那可能需要幾小時**。在這段時間內，叢集實際上仍然是脆弱的（少一份冗餘）——所以不應該在此期間進行其他的維護操作（例如重啟另一台）。這個「等前一個操作完全完成才做下一個」的紀律，是叢集運維中最常被違反也最容易造成事故的一條。**而具體的判斷指標就是 `UnderReplicatedPartitions`**——它是一個簡單但完整反映「叢集是否處於健康的完整冗餘狀態」的數字，值得在任何維護操作的前後都檢查。

**面試回答方式**：給明確的判斷指標並指出**只看行程起來了是不夠的**。核心加分點是恢復是一個過程而非一個事件——真正的恢復是所有分區重新達到完整副本數，可能需要幾小時，而這段時間叢集仍然脆弱所以不應該進行其他維護操作。收在紀律：「等前一個操作完全完成才做下一個」是最常被違反也最容易造成事故的一條，而 `UnderReplicatedPartitions` 是一個簡單但完整的判斷指標。

### 整個叢集掛了怎麼辦？

**核心答案**：先恢復 controller（或 ZooKeeper/KRaft 的多數派），再逐台啟動 broker。**順序很重要**：沒有 controller 的話 broker 無法完成註冊與分區分配。而啟動 broker 時應該逐台進行並等待每台完成日誌恢復——同時啟動所有節點會讓磁碟 IO 完全飽和，反而更慢。

**詳細解析**：「同時啟動所有 broker 反而更慢」是一個違反直覺但真實的現象：每台 broker 啟動時都要做日誌恢復（掃描與驗證）——**這是磁碟密集的操作**；而全部同時進行會讓共享的儲存（如果有）或網路飽和。更糟的是，它們同時開始互相複製追平——流量瞬間打滿**。**所以「逐台或分小批啟動」通常更快也更安全**。**另一個要點是「先確認資料的完整性再全面恢復服務」**：**如果是斷電導致的全叢集故障，某些 broker 的資料可能損壞**——**先啟動一台驗證，確認正常後再繼續**，**比全部起來之後發現問題要好處理得多**。**這個「小步驗證」的原則在災難恢復中比在正常運維中更重要，因為那時的錯誤代價更高。

**面試回答方式**：給順序（先 controller 再逐台 broker）並解釋沒有 controller 的話 broker 無法完成註冊與分配。核心加分點是**同時啟動所有 broker 反而更慢**——日誌恢復是磁碟密集的、而它們同時互相複製追平會讓流量瞬間打滿。收在災難恢復的原則：先啟動一台驗證資料完整性再繼續，比全部起來之後發現問題好處理得多——「小步驗證」在災難恢復中比正常運維更重要，因為錯誤代價更高。
