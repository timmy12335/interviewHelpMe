# 題目

發現消費邏輯有 bug，需要重新處理過去三天的訊息，怎麼做？

## 核心答案

**前提是「訊息還在」**——**保留期必須長於「你可能需要回溯的時間」**。**這正是「Kafka 的保留期設定不只是儲存成本問題，也是可修復性問題」**。

**標準流程有四步**。**一、修復並部署新版本的消費邏輯**（**先確保不會繼續產生錯誤資料**）。**二、決定重放的方式**：**用新的消費者群組從指定時間開始**（不影響現有消費）**或者停掉現有消費者並重設位移**。**三、處理「重複處理」的影響**——**冪等的話直接跑；不冪等的話需要先清理錯誤的資料或者設計一個修正的流程**。**四、驗證結果並監控。**

**而最重要的判斷是「重放會不會產生副作用」**：**如果消費邏輯會發送郵件、扣款、或呼叫外部 API**——**重放意味著那些副作用會再發生一次**，**必須先處理。**

## 詳細解析

**「副作用的重放」是這裡最危險的部分，而它常常被忽略**：一個「訂單完成後發送通知」的消費者——**重放三天的訊息意味著所有使用者會再收到一次通知**。**所以重放前必須盤點「這條處理鏈路上有哪些外部副作用」並決定怎麼處理**：**用一個旗標關閉通知、用去重表擋掉已發送的、或者只重放到一個隔離的環境驗證**。**這個盤點在複雜的處理鏈路中並不容易**——**而它正是「消費邏輯應該把副作用集中而非散布」這個設計原則的實際價值所在。**

**「用新群組而非重設位移」通常更好**：不需要停掉現有的消費者（服務不中斷）、**可以並行運行並比對結果**、**而且如果重放出問題，隨時可以停掉而不影響正常流程**。**代價是「重放與正常消費同時進行，下游要承受雙倍的寫入」**——**所以需要限速，而那可以透過控制重放消費者的並行度來達成。**

**「只重放受影響的部分」比全部重放好**：如果 bug 只影響某一類訊息——**在重放的消費者中加入過濾條件，只處理那一類**。**這降低了下游的壓力也降低了副作用的範圍。**

**「重放的結果需要被驗證」**：跑完之後怎麼知道修對了？——**應該事先準備好「驗證的查詢」**（例如「這三天內狀態為 X 的訂單數應該是多少」），**並在重放前後各執行一次比對**。**沒有驗證的修復，本質上只是「又跑了一次」而不知道結果對不對。**

## 面試回答方式

先給前提（**訊息還在，而保留期不只是儲存成本問題也是可修復性問題**）與四步流程，並強調**最重要的判斷是重放會不會產生副作用**。加分點有四個：**副作用的重放最危險且常被忽略**——**重放三天意味著所有使用者再收到一次通知**，**所以要盤點鏈路上的外部副作用並決定處理方式**，**而這正是「副作用應該集中而非散布」的實際價值**；**用新群組而非重設位移通常更好**（不中斷、可比對、可隨時停），**代價是下游承受雙倍寫入所以要限速**；**只重放受影響的部分**降低壓力與副作用範圍；以及**重放的結果需要被驗證**——**沒有驗證的修復只是「又跑了一次」**。

## 講稿

前提是訊息還在。保留期必須長於你可能需要回溯的時間。所以保留期的設定不只是儲存成本問題，也是可修復性問題。

流程上我會先修復並部署新版本，確保不會繼續產生錯誤資料。然後決定重放的方式。我通常用一個新的消費者群組從指定時間開始，而不是停掉現有的重設位移。因為這樣不中斷服務、可以並行比對結果、而且出問題隨時能停。代價是下游要承受雙倍寫入，所以要限速。

但最重要的判斷是重放會不會產生副作用。如果消費邏輯會發送郵件、扣款、或呼叫外部介面，重放意味著那些副作用會再發生一次。一個訂單完成後發通知的消費者，重放三天代表所有使用者會再收到一次。

所以重放前必須盤點這條鏈路上有哪些外部副作用，並決定怎麼處理。關掉通知的旗標、用去重表擋掉已發送的、或者只重放到隔離環境驗證。而這個盤點在複雜鏈路中並不容易，這正是消費邏輯應該把副作用集中而不是散布的實際價值。

最後，重放完要驗證。事先準備好驗證的查詢，前後各跑一次比對。

## 常見追問

### 保留期該設多久？

**核心答案**：**至少要覆蓋「發現問題到修復所需的時間」**。如果一個 bug 平均要三天才被發現、修復再要兩天——**那保留期至少要七天才有修復的餘地**。**而常見的預設值 7 天正是基於這個經驗**。**對關鍵的資料流可以更長（30 天），而對量大且可再生的可以更短。**

**詳細解析**：**「保留期與可修復性的關係」是一個很少被明確討論但很實在的取捨**：多數團隊按「儲存成本」設定保留期——**而更好的問法是「如果一個 bug 在 N 天後才被發現，我還能修嗎」**。**而如果答案是不能，那要嘛延長保留期，要嘛在上游保留一份原始資料**（**寫入物件儲存的成本遠低於 Kafka 的磁碟**）。**後者是一個很划算的模式**：**Kafka 保留 7 天供正常消費與短期修復，同時把所有訊息歸檔到便宜的物件儲存供長期回溯**——**於是既有了成本效率也有了完整的可修復性**。**這個「熱資料在 Kafka、冷資料在物件儲存」的分層，與資料庫的冷熱分層是同一個思路，而它在訊息系統上同樣適用。**

**面試回答方式**：給依據（**覆蓋「發現問題到修復」所需的時間**）與常見值。核心加分點是提出更好的問法：**「如果一個 bug 在 N 天後才被發現，我還能修嗎」**，並給出划算的模式：**Kafka 保留 7 天供正常消費，同時歸檔到便宜的物件儲存供長期回溯**——**既有成本效率也有完整的可修復性**。收在**這與資料庫的冷熱分層是同一個思路**。

### 重放時下游被壓垮怎麼辦？

**核心答案**：**限速**。重放的消費者應該有明確的速率控制——**而不是「全速跑完」**。**做法包括：減少並行度、在處理迴圈中加入延遲、或者用 `pause()` 週期性暫停**。**判斷速率的依據是「下游還有多少餘裕」**——**通常設在正常流量的 20% 到 50% 之間，於是重放與正常業務可以共存。**

**詳細解析**：**「重放的時間可以被計算」讓限速的決定有依據**：三天的訊息量除以重放速率就是預計的時間——**而如果那個時間長到不可接受，就需要在「更快」與「下游壓力」之間重新取捨**。**這比憑感覺調參數好得多**。**另一個實用的手段是「錯開時段」**：**在夜間低流量時全速重放，白天降速或暫停**——**於是總時間可能只比全速慢一點，而白天完全不受影響**。**這與批次任務的排程思路一致**。**而最根本的預防是「下游應該有背壓或限流」**——**如果它自己能拒絕過量的請求，那重放的速率控制就成了一個優化而非必需的保護**。

**面試回答方式**：給限速的三種做法與速率的判斷依據。核心加分點是**重放的時間可以被計算**——**訊息量除以速率就是預計時間，而那讓限速的決定有依據，比憑感覺調參數好得多**。收在兩個進階：**錯開時段（夜間全速、白天降速）讓總時間只慢一點而白天不受影響**；**最根本的預防是下游自己有背壓或限流**，**那樣重放的速率控制就成了優化而非必需的保護**。

### 訊息已經過期了還能修復嗎？

**核心答案**：**看有沒有其他的資料來源**。**上游的資料庫、應用的日誌、物件儲存的歸檔**——**任何一個保留了原始資訊的地方都可以作為重建的來源**。**而如果 Kafka 是唯一的真相來源且訊息已過期**——**那就無法完整修復，只能評估影響並在下游做修正**。

**詳細解析**：**「Kafka 是不是唯一的真相來源」應該是一個被明確回答的架構問題**：如果是——**那它的保留期、副本數、以及備份策略都應該按「不可再生的關鍵資料」的標準設定**；**而如果上游有持久化的來源**——**Kafka 就只是一個傳輸通道，設定可以寬鬆得多**。**很多團隊沒有明確回答這個問題，於是既沒有給 Kafka 足夠的保護，也沒有上游的備份**——**直到需要修復時才發現什麼都沒有**。**所以我會建議在設計資料流時就畫出「原始資料在哪、經過哪些轉換、每一步保留多久」**——**這張圖能同時回答可靠性、成本、與可修復性三個問題，而畫它的成本很低。**

**面試回答方式**：給判斷（**看有沒有其他資料來源**）並列出可能的來源。核心加分點是把它提升成架構問題：**「Kafka 是不是唯一的真相來源」應該被明確回答**——**是的話保護標準要按不可再生的關鍵資料設定，不是的話可以寬鬆得多**，**而很多團隊沒有回答這個問題，於是兩邊都沒有保護**。收在建議：**設計資料流時就畫出「原始資料在哪、經過哪些轉換、每一步保留多久」**——**這張圖同時回答可靠性、成本與可修復性，而畫它的成本很低**。
