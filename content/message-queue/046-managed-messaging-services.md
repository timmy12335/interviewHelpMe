# 題目

雲端的託管訊息服務與自建 Kafka 怎麼選？

## 核心答案

先看模型是否匹配，因為它們不都是 Kafka 的替代品。

**SQS（佇列模型）**——訊息被消費後就消失，沒有回放；沒有分區的概念，順序只在 FIFO 佇列中保證（且吞吐受限）；**擴展性極好且完全免維運**。**它適合「任務分發」而非「事件流」。**

**Pub/Sub 與 Kinesis（更接近日誌模型）**——Pub/Sub 支援訂閱與一定的回放（保留期內），Kinesis 有明確的分片概念與保留期——**兩者都比 SQS 更接近 Kafka 的定位。**

**判斷的核心問題有三個**：**需不需要回放**（需要就排除 SQS）、需不需要多個獨立的消費者讀同一份資料（發布訂閱）、**以及順序保證的粒度需求**。

而託管服務的共同優勢是「沒有叢集要維運」——這個價值在小團隊中往往超過任何功能上的差距。

## 詳細解析

「佇列模型與日誌模型的根本差異」是這個選型的核心，而它常被模糊：**佇列**——訊息是「工作項」，被某個消費者取走並處理後就消失；**多個消費者是為了分攤負載**。**日誌**——訊息是「事實記錄」，被保留一段時間，任意數量的消費者可以各自從任意位置讀取；多個消費者可能是為了不同的目的。所以「一份訂單資料要同時給計費、通知、與分析三個系統用」在日誌模型下是自然的，而在佇列模型下需要複製三份。這個差異決定了很多架構選擇，而它比任何功能清單的比較都更根本。

「託管的隱性成本」需要被算清楚：SQS 按請求次數計費——一個高頻輪詢的消費者可能產生大量的空請求費用（**用長輪詢能大幅降低**）。**Kinesis 按分片小時加上寫入量計費**——而分片數需要手動管理（雖然有隨需模式）。**Pub/Sub 按訊息量計費**。在高吞吐的場景中，這些費用可能遠超自建的成本——而在中低吞吐下，託管幾乎總是更便宜（因為自建的固定成本被攤在很少的訊息上）。所以「盈虧平衡點」是一個應該實際計算的數字。

**「鎖定」是另一個維度**：託管服務的 API 與語義各不相同——**遷移的成本很高**。緩解的方式是「在應用與訊息服務之間加一層抽象」——但那層抽象只能覆蓋共通的功能，而各家的特色功能（Kafka 的交易、SQS 的可見性逾時）就用不了。所以完全的可移植性是一個代價很高且收益不確定的追求——多數團隊的務實選擇是接受一定程度的鎖定。

「Kafka 也有託管版本」是一個常被忽略的選項：MSK、Confluent Cloud、以及各雲的託管 Kafka——它們提供 Kafka 的完整語義而不需要自己維運叢集。如果你需要 Kafka 的模型但不想維運，這往往是比「換一個不同模型的服務」更好的選擇。

## 面試回答方式

先指出**它們不都是 Kafka 的替代品**並區分 SQS 的佇列模型與 Pub/Sub、Kinesis 的日誌模型，給三個判斷問題。加分點有四個：佇列模型與日誌模型的根本差異——佇列的訊息是工作項、消費後消失，日誌的訊息是事實記錄、可被多方各自讀取，「一份資料給三個系統用」在日誌模型下自然而佇列模型下要複製三份；**託管的隱性成本**（SQS 的請求次數、Kinesis 的分片小時）**與盈虧平衡點應該實際計算**；**鎖定的緩解與它的限制**——抽象層只能覆蓋共通功能，完全可移植是代價高而收益不確定的追求；以及**Kafka 也有託管版本**，需要 Kafka 的模型但不想維運時它往往比換一個不同模型的服務更好。

## 講稿

我會先看模型是否匹配，因為它們不都是 Kafka 的替代品。

簡單佇列服務是佇列模型，訊息被消費後就消失，沒有回放，順序只在特定模式下保證。它適合任務分發而不是事件流。而發布訂閱服務跟串流服務比較接近日誌模型，有保留期跟一定的回放能力。

這個佇列模型跟日誌模型的差異是選型的核心。佇列的訊息是工作項，被某個消費者取走處理後就消失，多個消費者是為了分攤負載。日誌的訊息是事實記錄，被保留一段時間，任意數量的消費者可以各自從任意位置讀取。所以一份訂單資料要同時給計費、通知、分析三個系統用，在日誌模型下是自然的，在佇列模型下要複製三份。

託管的共同優勢是沒有叢集要維運，這個價值在小團隊中往往超過任何功能上的差距。

但要算清楚隱性成本。有些是按請求次數計費，高頻輪詢會產生大量空請求的費用。在高吞吐場景中這些費用可能遠超自建，而中低吞吐下託管幾乎總是更便宜。所以盈虧平衡點是一個應該實際計算的數字。

## 常見追問

### SQS 的可見性逾時是什麼？

**核心答案**：訊息被取出後不會立刻刪除，而是進入「不可見」狀態一段時間——消費者處理成功後主動刪除它，失敗或當機則在逾時後重新可見被其他消費者取得。這是佇列模型實現「至少一次」的機制：它把「取出」與「確認完成」分開，於是處理失敗的訊息不會遺失。

**詳細解析**：「逾時設得不對會造成重複處理」是最常見的問題：如果處理需要 60 秒而可見性逾時是 30 秒——訊息會在還在處理時就重新可見並被另一個消費者取走，**於是同一條訊息被處理兩次**。正確的做法是「逾時設得比最長的處理時間長」，或者在處理期間主動延長它（`ChangeMessageVisibility`）。**這與 Kafka 的 `max.poll.interval.ms` 面對的是同一類問題**——「系統怎麼知道消費者還在處理而不是掛了」，而兩者的解法都是「一個時限加上主動的延長機制」。能看出這個共通性，說明理解了問題的本質而不只是某個產品的參數。

**面試回答方式**：給機制（取出後不可見、成功才刪除、失敗則逾時後重新可見）並指出這是佇列模型實現「至少一次」的方式。核心加分點是逾時設得不對會造成重複處理與正確做法（設得比最長處理時間長、或主動延長）。收在共通性：**這與 Kafka 的 `max.poll.interval.ms` 是同一類問題**——「系統怎麼知道消費者還在處理而不是掛了」，兩者的解法都是一個時限加主動延長機制。

### 這些服務的順序保證怎麼樣？

**核心答案**：**普遍比 Kafka 弱或者有明確的代價**。**SQS 標準佇列不保證順序**；FIFO 佇列保證但吞吐上限低得多（每秒幾千條，而標準佇列幾乎無限）。**Pub/Sub 支援「按 ordering key 有序」但會降低吞吐**。Kinesis 在同一個分片內有序（與 Kafka 的分區類似）。所以如果順序是核心需求，Kinesis 的模型最接近 Kafka。

**詳細解析**：「順序保證的代價在所有系統中都存在」是一個值得指出的共通性：因為順序意味著「不能並行處理」——**無論是 Kafka 的分區、Kinesis 的分片、還是 SQS FIFO 的 message group**，它們本質上都是「把訊息分成若干個獨立有序的流」。而吞吐的上限就是「流的數量乘以單流的處理能力」。所以不同產品的差異主要在「單流的能力」與「流的數量上限」上，而非機制的根本不同。理解這一點之後，比較不同服務的順序能力就變成一個定量的問題——而不需要記住每個產品的宣傳說法。

**面試回答方式**：給各服務的順序能力與代價，並指出 **Kinesis 的模型最接近 Kafka**。核心加分點是提煉共通性：順序意味著不能並行，所以所有系統本質上都是「把訊息分成若干個獨立有序的流」，吞吐上限是流的數量乘以單流的能力。收在：理解這一點之後，比較不同服務就變成一個定量問題，而不需要記住每個產品的宣傳說法。

### 什麼情況下託管服務明顯更好？

**核心答案**：**三種情況**。團隊沒有專職的基礎設施人力——Kafka 的維運（升級、擴容、故障處理）需要真實的投入。**流量小或波動大**——託管的按量計費在低利用率下遠優於自建的固定成本。以及需要與雲端生態深度整合——例如 SQS 觸發 Lambda、Pub/Sub 觸發 Cloud Function 這類無伺服器的組合。

**詳細解析**：「無伺服器的整合」是託管服務一個被低估的優勢：SQS 加 Lambda 讓「處理一個佇列」變成「寫一個函式」——不需要管理消費者的部署、擴縮容、與健康檢查。在流量波動大的場景中，這個組合的成本與運維優勢都很明顯。而用 Kafka 達成同樣的效果需要自己維護消費者服務。**但要注意它的限制**：無伺服器函式的執行時間有上限、冷啟動有延遲、而且難以維護跨訊息的狀態——所以它適合「無狀態的、短時的處理」而非複雜的流式計算。這個「用對場景就非常好用、用錯就處處受限」的特性，讓「先確認處理邏輯的形態」成為選型時的第一步。

**面試回答方式**：給三種情況。核心加分點是無伺服器的整合是被低估的優勢——SQS 加 Lambda 讓「處理一個佇列」變成「寫一個函式」，不需要管理部署、擴縮容與健康檢查，在流量波動大時成本與運維優勢都明顯。收在限制與判斷：執行時間有上限、冷啟動有延遲、難以維護跨訊息狀態，**所以適合無狀態的短時處理**，而「先確認處理邏輯的形態」是選型的第一步。
