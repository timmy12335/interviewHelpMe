# 題目

訊息的格式怎麼定？欄位要改的時候怎麼辦？

## 核心答案

**訊息佇列的核心困難是「生產者與消費者是解耦的」**——**你無法讓它們同時升級**。**所以 schema 的演進必須向後或向前相容，而這需要工具支援而非靠約定。**

**Schema Registry 是標準做法**：**它集中儲存每個 topic 的 schema 版本，並在註冊新版本時檢查相容性**——**不相容的變更會被直接拒絕**。**訊息本體只帶一個 schema ID（幾個位元組），消費者用它去 registry 取得對應的 schema 來反序列化。**

**三種相容性模式**。**向後相容（BACKWARD）**——**新消費者能讀舊訊息**；**允許刪除欄位與新增有預設值的欄位**。**向前相容（FORWARD）**——**舊消費者能讀新訊息**；**允許新增欄位與刪除有預設值的欄位**。**完全相容（FULL）**——**兩者都要**。**預設通常是 BACKWARD，因為典型的升級順序是消費者先升。**

## 詳細解析

**「為什麼不用 JSON」是一個常見且合理的問題**：JSON 可讀、無需 registry、任何語言都能處理——**但它有三個實質的缺點**：**體積大**（欄位名在每條訊息中重複）、**沒有 schema 強制**（一個拼錯的欄位名不會被發現，直到下游解析失敗）、**以及型別鬆散**（數字可能是整數也可能是字串）。**在高吞吐或長期演進的場景中，這些缺點會累積成真實的問題**——**而 Avro、Protobuf 這類格式配合 registry 解決了全部三個**。**至於選 Avro 還是 Protobuf**：**Avro 的 schema 演進規則更完整（有明確的預設值與別名機制），Protobuf 的跨語言支援與工具鏈更成熟**——**兩者都是合理的選擇。**

**「相容性檢查在 CI 中執行」是最有價值的實踐**：讓 schema 的變更在合併前就被驗證——**而不是部署到生產才發現不相容**。**做法是把 schema 定義放進版本控制，並在 CI 中用 registry 的相容性檢查 API 驗證**。**這把一個運行期的風險轉換成一個編譯期的檢查，收益很大而成本很低。**

**「有些變更無論如何都不相容」需要明確的處理路徑**：改變一個欄位的型別、重新命名一個沒有別名的欄位、刪除一個沒有預設值的必填欄位——**這些無法透過相容性規則繞過**。**正確的做法是「新增一個新欄位並雙寫，等所有消費者遷移後再移除舊的」**——**這與資料庫的擴充收縮式遷移是完全相同的模式**。**而如果變更太大，建立一個新的 topic 並讓消費者逐步遷移，比在原 topic 上做破壞性變更更安全。**

**「registry 是一個關鍵依賴」需要被納入可用性設計**：如果 registry 掛了，新的消費者無法取得 schema——**雖然客戶端通常會快取，但重啟後就沒了**。**所以 registry 應該是高可用的，而客戶端應該有本地的快取與合理的重試。**

## 面試回答方式

先給核心困難（**生產者與消費者解耦，無法同時升級**）與 **Schema Registry 的機制**（集中儲存、註冊時檢查、訊息只帶 ID）。給三種相容性模式與**預設用 BACKWARD 的理由**。加分點有四個：**為什麼不用 JSON**——**體積大、沒有 schema 強制、型別鬆散**，**而在高吞吐或長期演進中這些會累積成真實問題**；**相容性檢查在 CI 中執行**——**把運行期的風險轉換成編譯期的檢查，收益大成本低**；**有些變更無論如何都不相容**，**正確的處理是新增欄位並雙寫再移除舊的，與資料庫的擴充收縮完全相同**；以及**registry 是一個關鍵依賴**，**需要高可用與客戶端快取**。

## 講稿

訊息佇列的核心困難是生產者跟消費者是解耦的，你沒辦法讓它們同時升級。所以格式的演進必須相容，而這需要工具支援而不是靠約定。

標準做法是用一個集中的結構描述註冊中心。它儲存每個主題的格式版本，並在註冊新版本時檢查相容性，不相容的變更會被直接拒絕。訊息本體只帶一個編號，消費者用它去取得對應的定義來反序列化。

相容性有三種模式。向後相容是新消費者能讀舊訊息，向前相容是舊消費者能讀新訊息，完全相容是兩者都要。預設通常用向後相容，因為典型的升級順序是消費者先升。

有一個實踐我覺得最有價值，就是把相容性檢查放進持續整合。讓格式的變更在合併前就被驗證，而不是部署到生產才發現。這把一個運行期的風險轉換成編譯期的檢查，收益很大而成本很低。

還有一點，有些變更無論如何都不相容，比如改型別、重新命名、刪除必填欄位。正確的做法是新增一個新欄位並雙寫，等所有消費者遷移後再移除舊的。這跟資料庫的擴充收縮式遷移是完全相同的模式。

## 常見追問

### 一個 topic 該只放一種訊息類型嗎？

**核心答案**：**多數情況是的，但有例外**。**單一類型**——schema 簡單、消費者不需要判斷類型、相容性檢查直接。**多種類型（例如「使用者的所有事件」放同一個 topic）**——**好處是「同一個實體的事件保持全域有序」**（因為在同一個分區），**代價是消費者需要處理多種格式且 schema 管理更複雜**。

**詳細解析**：**「事件的順序需求決定了這個選擇」**：如果「使用者建立」與「使用者更新」在不同的 topic——**消費者無法保證看到的順序正確**（可能先看到更新再看到建立）。**而放在同一個 topic 且用使用者 ID 作為 key，順序就有保證**。**所以「同一個實體的事件應該在同一個 topic」是一個有實質理由的模式**，**而不只是風格偏好**。**Schema Registry 支援這個模式**（用 `RecordNameStrategy` 而非預設的 `TopicNameStrategy` 註冊 schema）——**於是一個 topic 可以有多個 schema**。**而消費者的處理方式是「用 schema 的類型分派」**——**這與處理一個 sealed class 的多個子類是同構的**。**能說出「這個選擇由順序需求決定」，比籠統地說「看情況」有價值得多。**

**面試回答方式**：給兩種選擇與各自的取捨。核心加分點是指出**事件的順序需求決定了這個選擇**——**不同 topic 的話消費者無法保證看到「建立」在「更新」之前，而同一個 topic 加上實體 ID 作為 key 就有保證**，**所以「同一個實體的事件應該在同一個 topic」是有實質理由的模式而非風格偏好**。收在實作：**Schema Registry 支援一個 topic 多個 schema，而消費者用類型分派，與處理 sealed class 的多個子類同構**。

### 沒有 Schema Registry 的話怎麼辦？

**核心答案**：**用「自描述的格式加上嚴格的約定」**：**訊息中帶一個版本欄位**、**只做相容的變更（只新增有預設值的欄位）**、**以及在程式碼庫中集中管理 schema 定義並產生各語言的類別**。**這能運作但缺少強制**——**一個不小心的破壞性變更不會被任何機制攔下，直到消費者失敗。**

**詳細解析**：**「把 schema 定義放進一個共用的程式碼庫並產生類別」是最接近 registry 效果的替代**：**所有生產者與消費者依賴同一份定義**——**於是格式的變更會透過依賴的升級被看見**，**而不是靠文件溝通**。**再配合「相容性的單元測試」**（**用舊版本的序列化資料驗證新版本能否讀取**）——**就補上了大部分的強制**。**這個做法的成本是「需要一個跨團隊的共用程式碼庫並管理它的版本」**，**而那本身有組織上的協調成本**。**所以判斷是：topic 數量少、團隊少、變更不頻繁的情況下這個方案夠用**；**而規模上來之後，registry 的集中管理與運行期檢查的價值會超過它的維運成本。**

**面試回答方式**：給替代方案（版本欄位、只做相容變更、集中管理定義）並誠實指出**它缺少強制，破壞性變更不會被攔下直到消費者失敗**。核心加分點是**把 schema 放進共用程式碼庫並產生類別**——**格式變更透過依賴升級被看見而非靠文件溝通**，**再配合用舊資料驗證新版本的相容性測試就補上大部分強制**。收在判斷：**小規模夠用，而規模上來後 registry 的價值會超過維運成本**。

### 訊息格式的變更怎麼安全上線？

**核心答案**：**四步**。**一、在 registry 註冊新 schema 並確認相容性檢查通過**。**二、先升級消費者**（讓它們能處理新舊兩種格式）。**三、確認所有消費者實例都已升級**（**這一步最容易被跳過**）。**四、才升級生產者開始寫新格式。** **順序反了的話，還沒升級的消費者會遇到不認得的格式。**

**詳細解析**：**「確認所有消費者都已升級」在實務上比想像中難**：有些消費者可能是別的團隊的、可能是很久沒動的批次任務、可能是一個沒有人記得的內部工具——**而它們都會在生產者切換的那一刻失敗**。**所以 registry 提供的「哪些消費者用了哪個 schema 版本」的資訊很有價值**（部分實作支援），**而更務實的做法是「維護一份 topic 的消費者清單」**——**這聽起來很基礎，但很多團隊沒有，於是每次變更都是一次未知的風險**。**另一個保險是「保持向前相容一段時間」**：**即使升級了生產者，也不要立刻使用新欄位的新語義**——**給落後的消費者一個緩衝期**。**這與資料庫遷移的「擴充階段停留足夠久」是完全相同的紀律。**

**面試回答方式**：給四步順序並強調**第三步最容易被跳過**。核心加分點是說明**確認所有消費者都已升級在實務上很難**——**別的團隊的、很久沒動的批次任務、沒人記得的內部工具都會在切換那一刻失敗**，**所以「維護一份 topic 的消費者清單」聽起來基礎但很多團隊沒有，於是每次變更都是未知的風險**。收在保險：**保持向前相容一段時間、不要立刻使用新語義**——**與資料庫遷移的「擴充階段停留足夠久」是相同的紀律**。
