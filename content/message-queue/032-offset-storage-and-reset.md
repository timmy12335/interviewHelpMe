# 題目

消費位移存在哪裡？需要重新消費時怎麼操作？

## 核心答案

**位移存在一個特殊的內部 topic `__consumer_offsets` 中**——**它是一個壓實（compacted）的 topic**，key 是「群組 + topic + 分區」，value 是位移與中繼資料。壓實保證了每個 key 只保留最新的位移，於是這個 topic 不會無限成長。

這個設計取代了早期存在 ZooKeeper 的做法——因為位移的提交非常頻繁，而 ZooKeeper 不適合高頻寫入。存進 Kafka 自己則天然獲得了複製、持久化與高吞吐。

**重設位移用 `kafka-consumer-groups.sh --reset-offsets`**，**支援幾種模式**：`--to-earliest`（從頭）、`--to-latest`（跳到最新）、`--to-offset`（指定位移）、`--to-datetime`（按時間）、`--shift-by`（相對移動）。關鍵限制是「群組必須處於非活躍狀態」——所以要先停掉所有消費者實例。

## 詳細解析

「必須先停掉消費者」是一個容易在事故中被忽略的操作前提：如果消費者還在跑——它會繼續提交自己的位移，覆蓋你剛設的值。所以標準流程是「停消費者 → 重設位移 → 啟動消費者」。在 Kubernetes 環境中這意味著把 Deployment 縮到 0 再恢復——而這個停機時間應該被納入操作計畫。忘記這一步是重設位移最常見的失敗原因，而它的症狀很困惑：指令執行成功但位移沒有變。

「`auto.offset.reset` 只在沒有已提交位移時生效」是另一個常見的誤解：這個參數（`earliest` / `latest` / `none`）只決定「一個全新的消費者群組，或者已提交的位移已經過期時，該從哪裡開始」——它不會影響已經有位移的群組。所以「我設了 earliest 為什麼沒有從頭讀」的答案通常是「這個群組已經有位移了」。而 `latest` 作為預設值有一個危險：新部署的消費者群組會跳過所有既有的訊息——在資料處理場景中這可能造成靜默的資料遺失，所以應該明確設定而非依賴預設。

「位移過期」是一個容易忽略的機制：`offsets.retention.minutes`（預設 7 天）之後，**不活躍群組的位移會被刪除**——於是那個群組重新啟動時會按 `auto.offset.reset` 處理。對於「週期性運行的消費者」（例如每月跑一次的批次），這意味著它的位移可能已經沒了。知道這個能避免「為什麼我的批次任務重跑了所有歷史資料」這類困惑。

「用新的群組 ID 而非重設位移」是一個常見的替代做法：需要重新處理時——**換一個 group.id 並設 `auto.offset.reset=earliest`**，於是它作為全新的群組從頭開始。好處是不需要停掉原有的消費者、可以並行運行、而且原群組的進度完全不受影響。代價是要管理群組 ID 的生命週期（避免累積大量廢棄的群組）。

## 面試回答方式

先給儲存位置（`__consumer_offsets` 這個壓實的內部 topic）與**它取代 ZooKeeper 的理由**（提交頻繁而 ZooKeeper 不適合高頻寫入）。給重設的模式與**關鍵限制：群組必須非活躍**。加分點有四個：忘記停消費者是重設最常見的失敗原因，症狀很困惑（指令成功但位移沒變）；**`auto.offset.reset` 只在沒有已提交位移時生效**——「設了 earliest 為什麼沒從頭讀」的答案通常是「這個群組已經有位移了」，而 `latest` 作為預設值會讓新群組跳過所有既有訊息；**位移會過期**（預設 7 天），週期性運行的消費者可能因此重跑歷史資料；以及**用新的群組 ID 而非重設位移**這個常見的替代做法與它的優缺點。

## 講稿

位移存在一個特殊的內部主題裡，它是壓實的，鍵是群組加主題加分區，值是位移。壓實保證每個鍵只保留最新的，所以這個主題不會無限成長。

這個設計取代了早期存在協調服務的做法，因為位移的提交非常頻繁，而那個服務不適合高頻寫入。存進 Kafka 自己則天然獲得複製、持久化跟高吞吐。

重設位移用內建的工具，支援從頭、跳到最新、指定位移、按時間、相對移動幾種模式。關鍵限制是群組必須處於非活躍狀態，所以要先停掉所有消費者。忘記這一步是最常見的失敗原因，而症狀很困惑，指令執行成功但位移沒有變。因為消費者還在跑，它會繼續提交自己的位移覆蓋掉你設的值。

還有一個常見的誤解。自動重設參數只在沒有已提交位移時生效。所以我設了從頭為什麼沒有從頭讀，答案通常是這個群組已經有位移了。

實務上我更常用另一個做法，換一個新的群組編號並設定從頭開始。好處是不用停掉原有的消費者、可以並行跑、而且原群組的進度完全不受影響。

## 常見追問

### 自動提交與手動提交怎麼選？

**核心答案**：只有「處理失敗可以接受丟訊息」的場景才用自動提交。自動提交是按時間週期提交當前拉取到的最大位移——**而它不知道你有沒有處理完**：如果在提交之後、處理完成之前當機，那些訊息就遺失了。手動提交讓你控制「處理完成後才提交」，**是可靠處理的必要條件。**

**詳細解析**：「自動提交也可能造成重複而非只是遺失」：提交是週期性的（預設 5 秒）——如果在兩次提交之間當機，那段時間已處理的訊息會被重複消費。所以自動提交既不保證不丟也不保證不重——**它只是「大致上不會差太多」**。這對日誌收集、指標上報這類場景是可接受的，而對業務處理不是。**手動提交則分「同步」與「非同步」**：同步提交會阻塞直到確認（可靠但慢），非同步提交快但失敗時只有回呼知道。實務上的常見模式是「平時用非同步提交，在關閉前做一次同步提交」——兼顧了吞吐與最後一次的可靠性。

**面試回答方式**：給選擇標準（只有能接受丟訊息才用自動提交）並說明自動提交的機制問題。核心加分點是自動提交既不保證不丟也不保證不重——兩次提交之間當機會重複，提交後處理前當機會遺失，**它只是「大致上不會差太多」**。收在手動提交的模式：平時用非同步提交、關閉前做一次同步提交，兼顧吞吐與最後一次的可靠性。

### 怎麼查一個消費者群組的積壓？

**核心答案**：**用 `kafka-consumer-groups.sh --describe --group <name>`**——它會列出每個分區的「當前位移、日誌末端位移、以及兩者的差（LAG）」。**LAG 是最重要的健康指標**：持續增長表示消費跟不上生產，而某個分區的 LAG 特別大則表示分配不均或該分區的資料有問題。

**詳細解析**：「按分區看而非只看總和」是診斷的關鍵：總 LAG 一萬可能是「每個分區各一千」（均勻，需要整體擴容）——也可能是「一個分區九千九、其他都是零」（傾斜，需要看那個分區的 key 分布或處理邏輯）。這兩種情況的處理完全不同，而只看總和無法區分。另一個實用的觀察是「LAG 的變化趨勢比絕對值重要」：一個穩定在五千的 LAG 可能完全正常（批次處理的自然積壓），而一個從零漲到一千但持續上升的則是問題。所以告警應該基於「LAG 的增長率」或「LAG 對應的時間延遲」而非絕對的訊息數——後者尤其有意義，因為「落後 5 分鐘」比「落後 10 萬條」對業務更有解釋力。

**面試回答方式**：給指令與 LAG 的含義。核心加分點是**按分區看而非只看總和**——「每個分區各一千」與「一個分區九千九」的處理完全不同而只看總和無法區分。收在告警設計：**LAG 的變化趨勢比絕對值重要**，應該基於增長率或「對應的時間延遲」而非絕對訊息數——「落後 5 分鐘」比「落後 10 萬條」對業務更有解釋力。

### 位移提交失敗會怎樣？

**核心答案**：**訊息會被重複消費**——因為下次啟動時從舊的位移開始。這正是「至少一次」語義的來源，也是「消費端冪等」必要的根本原因。提交失敗的常見原因是：rebalance 期間分區已被撤銷、與協調者的連線中斷、或者消費者已被視為失效。

**詳細解析**：「提交失敗通常不需要重試」是一個反直覺但正確的處理：如果失敗是因為 rebalance——那個分區已經不屬於你了，重試提交會被拒絕；而如果是連線問題，下一次正常的提交會覆蓋它。所以非同步提交的回呼中，記錄與計數比重試更合適。真正需要注意的是「關閉時的最後一次提交」——那沒有下一次機會，所以應該用同步提交並處理失敗。而更根本的認知是：位移提交的可靠性不需要做到完美，因為它的失敗只導致重複而非遺失——**而重複由冪等處理**。這個「把可靠性的責任放在能可靠處理它的那一層」的分工，是這整個類別反覆出現的主線。

**面試回答方式**：給後果（重複消費）並指出這正是「至少一次」語義的來源與冪等必要的根本原因，列出常見失敗原因。核心加分點是**提交失敗通常不需要重試**這個反直覺的處理——rebalance 導致的重試會被拒絕，連線問題則下次提交會覆蓋，所以回呼中記錄與計數比重試合適，而關閉時的最後一次沒有下一次機會，要用同步提交。收在主線的呼應：位移提交的失敗只導致重複而非遺失，而重複由冪等處理。
