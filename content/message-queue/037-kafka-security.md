# 題目

Kafka 的安全該怎麼配置？

## 核心答案

三個獨立的層次，可以分別啟用。

**認證（誰是你）**——SASL/PLAIN（帳密，簡單但要配合 TLS）、SASL/SCRAM（雜湊挑戰，帳密不明文傳輸且可以存在 Kafka 中管理）、SASL/GSSAPI（Kerberos，企業環境）、以及 mTLS（雙向憑證）。SCRAM 是自建環境中最務實的選擇；雲端環境通常用 IAM 整合。

**授權（你能做什麼）**——ACL 定義「哪個 principal 對哪個資源（topic、group、cluster）能做哪些操作（讀、寫、建立、描述）」。**關鍵是「預設拒絕」**（`allow.everyone.if.no.acl.found=false`），否則沒有規則的資源對所有人開放。

**加密（傳輸中的保護）**——TLS 加密 broker 與客戶端之間、以及 broker 之間的流量。**注意「加密會破壞零拷貝」**——因為資料需要在使用者空間被加密，效能有明顯的下降。

## 詳細解析

「TLS 破壞零拷貝」是一個必須知道的效能影響：Kafka 快的一個原因是消費時能用 `sendfile` 把資料從頁快取直接送到網路——而 TLS 需要在使用者空間加密，這條路徑就走不通了。實測上，開啟 TLS 可能讓吞吐下降 20% 到 40%（取決於硬體的加密加速支援）。所以「哪些連線需要加密」值得分別考慮：**跨公網或跨機房的必須加密**；而同一個安全網段內的 broker 之間，有些團隊選擇不加密以保住效能——這是一個明確的安全與效能取捨，應該基於威脅模型決定而非一律開啟或一律關閉。

「ACL 的粒度與管理」在規模大時是一個負擔：每個應用對每個 topic 都需要規則——幾百個 topic 乘以幾十個應用就是大量的 ACL。**實用的做法是「用前綴匹配」**（`--resource-pattern-type prefixed`）——於是一個團隊的所有 topic 用一條規則覆蓋，**前提是 topic 的命名有紀律**（例如 `team-a.service-b.event-name`）。這讓「良好的命名規範」從一個風格問題變成一個有實質收益的治理工具。

「消費者群組也需要 ACL」是一個容易遺漏的點：不只是 topic 的讀取權限——**消費者還需要對它的 group ID 有 `Read` 權限**。而如果群組 ID 是動態產生的（例如帶上實例 ID），ACL 就無法預先設定——所以群組 ID 應該是穩定且可預測的，這也是靜態成員設計時要考慮的一點。

**「靜態資料的加密」Kafka 本身不提供**：磁碟上的訊息是明文的——需要的話應該用磁碟層的加密（LUKS、雲端的 EBS 加密）或者在生產者端加密訊息內容。後者的代價是 broker 無法做壓縮（加密後的資料壓不動）與無法做日誌壓實（如果 key 也加密了）。

## 面試回答方式

先給三個獨立的層次（認證、授權、加密）與各自的選項，並指出**授權的關鍵是預設拒絕**。加分點有四個：**TLS 破壞零拷貝**——消費時無法用 sendfile 直送網路，吞吐可能下降 20% 到 40%，所以哪些連線需要加密應該基於威脅模型分別決定；**ACL 用前綴匹配管理**——讓「良好的命名規範」從風格問題變成有實質收益的治理工具；**消費者群組也需要 ACL**，而動態產生的群組 ID 無法預先設定規則；以及**Kafka 不提供靜態資料加密**，在生產者端加密的代價是無法壓縮與無法日誌壓實。

## 講稿

有三個獨立的層次可以分別啟用。認證、授權、加密。

認證上自建環境我會用雜湊挑戰的方式，帳密不明文傳輸而且可以存在 Kafka 裡管理。雲端環境通常直接整合身分服務。

授權用存取控制列表，定義哪個主體對哪個資源能做哪些操作。關鍵是要設成預設拒絕，否則沒有規則的資源對所有人開放。

加密這裡有一個必須知道的效能影響。傳輸加密會破壞零拷貝。Kafka 快的一個原因是消費時能把資料從頁快取直接送到網路，而加密需要在使用者空間處理，這條路徑就走不通了。實測上吞吐可能下降兩到四成。所以哪些連線需要加密值得分別考慮，跨公網跨機房的必須加密，而同一個安全網段內的節點之間有些團隊選擇不加密以保住效能。這是一個明確的取捨，應該基於威脅模型而不是一律開啟或關閉。

還有一個管理上的實用技巧。存取規則可以用前綴匹配，於是一個團隊的所有主題用一條規則覆蓋。這讓良好的命名規範從風格問題變成有實質收益的治理工具。

## 常見追問

### 多租戶的 Kafka 怎麼隔離？

**核心答案**：**四個層次**。**命名與 ACL**——**用前綴劃分租戶並用 ACL 強制**。**配額**——用 `quota` 限制每個 client ID 或使用者的生產與消費頻寬，以及請求速率；這是防止一個租戶影響其他人的關鍵。**分區與 broker 的分布**——必要時把不同租戶的 topic 放到不同的 broker（用副本分配控制）。**以及獨立叢集**——當隔離要求高到前三者不足時。

**詳細解析**：「配額是多租戶最重要也最容易被忽略的一環」：ACL 防止「讀到不該讀的」——但它完全不防止「一個租戶把叢集的頻寬吃光」。**而 Kafka 的配額機制相當完整**：可以按使用者、按 client ID、或兩者組合設定生產頻寬、消費頻寬、以及請求處理時間的百分比。**最後那一項尤其有用**——它限制的是「這個客戶端佔用 broker 請求處理執行緒的比例」，能防止「大量小請求」這種不佔頻寬但佔處理能力的濫用。設定配額的方式是「先觀察正常的用量，設在合理的倍數上」——而配額被觸發時客戶端會被限速（延遲回應）而非拒絕，所以它的效果是漸進的降級而非硬性中斷。

**面試回答方式**：給四個層次並指出配額是防止一個租戶影響其他人的關鍵。核心加分點是**配額最重要也最容易被忽略**——ACL 防止讀到不該讀的但完全不防止吃光頻寬，並介紹 Kafka 配額的三個維度，尤其是請求處理時間的百分比能防止「大量小請求」這種不佔頻寬但佔處理能力的濫用。收在設定方式與效果：先觀察正常用量設在合理倍數，觸發時是限速而非拒絕，所以效果是漸進降級而非硬性中斷。

### ACL 設錯導致服務不可用怎麼排查？

**核心答案**：看客戶端的錯誤訊息與 broker 的授權日誌。客戶端會收到 `TopicAuthorizationException` 或 `GroupAuthorizationException`——**訊息中會說明是哪個資源**。**而 broker 端可以開啟 `kafka-authorizer` 的日誌**（**通常需要調整 log4j 設定到 DEBUG**）**看到每一次授權判斷的細節**：principal、資源、操作、以及結果。

**詳細解析**：「授權失敗最常見的三個原因」值得記住：**principal 的格式不符**（mTLS 下的 principal 是憑證的 DN，格式與你想像的可能不同）、**遺漏了群組的 ACL**（只設了 topic 的）、**以及遺漏了 `Describe` 權限**（**很多操作隱含需要它**）。**第一個尤其容易出錯**——用 `kafka-acls.sh --list` 看實際生效的規則，並與客戶端日誌中顯示的 principal 比對，**通常一眼就能發現不匹配**。而更根本的建議是「ACL 的變更應該與其他設定一樣走版本控制與審查」——因為它們是分散的、難以整體檢視的，而一個錯誤的規則可能讓某個服務在部署後才失敗。把 ACL 定義成程式碼（用工具從一份宣告產生）比手動執行指令可靠得多。

**面試回答方式**：給排查途徑（客戶端錯誤訊息、broker 的授權日誌）。核心加分點是**三個最常見的原因**：principal 格式不符（mTLS 下是憑證的 DN）、遺漏群組的 ACL、遺漏 Describe 權限，並給出快速比對的方法。收在治理建議：ACL 的變更應該走版本控制與審查——它們分散且難以整體檢視，而一個錯誤的規則可能讓服務在部署後才失敗，所以把 ACL 定義成程式碼比手動執行指令可靠。

### 訊息內容需要加密嗎？

**核心答案**：**看資料的敏感度與威脅模型**。傳輸加密（TLS）保護的是「網路上被竊聽」；而如果威脅包括「有權存取 broker 磁碟的人」或者「Kafka 的管理員不應該看到內容」——**那就需要端到端的訊息加密**（生產者加密、消費者解密，broker 只是搬運密文）。

**詳細解析**：「端到端加密的代價是失去了 Kafka 的幾個關鍵能力」：**壓縮失效**（加密後的資料熵很高，壓不動）、**日誌壓實失效**（如果 key 也被加密，broker 無法識別相同的 key）、以及無法在 broker 側做任何基於內容的處理。所以它應該只用於真正需要的欄位而非整條訊息——常見的做法是「只加密敏感欄位，其餘保持明文」，於是 key 可以用於分區與壓實，而壓縮對明文部分仍然有效。**另一個實務考量是「金鑰管理」**：生產者與消費者需要共享金鑰，而金鑰的輪換要考慮「舊訊息用舊金鑰加密」——所以訊息中應該帶上金鑰的版本標識。這些複雜度說明了「端到端加密不是一個開關，而是一個需要設計的方案」。

**面試回答方式**：給判斷依據（傳輸加密防竊聽，而威脅包括有磁碟存取權的人時才需要端到端）。核心加分點是說明端到端加密的代價是失去壓縮、日誌壓實、與 broker 側的內容處理，並給出務實的做法：只加密敏感欄位而非整條訊息，**於是 key 仍可用於分區與壓實**。收在金鑰管理：輪換要考慮舊訊息用舊金鑰，所以訊息要帶金鑰版本標識——這些複雜度說明它不是一個開關而是一個需要設計的方案。
