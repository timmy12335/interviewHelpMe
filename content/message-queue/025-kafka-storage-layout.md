# 題目

Kafka 的訊息實際上是怎麼存在磁碟上的？怎麼快速定位一條訊息？

## 核心答案

**一個 partition 對應磁碟上的一個目錄，目錄內是一組 segment 檔案**。**每個 segment 由三個檔案組成**：**`.log`（實際的訊息）、`.index`（位移到檔案位置的稀疏索引）、`.timeindex`（時間戳到位移的索引）**。**檔名是該 segment 的起始位移**（`00000000000000368769.log`）。

**定位一條訊息分三步**。**一、用二分搜尋在目錄的 segment 檔名中找到「起始位移小於等於目標」的那個 segment**。**二、在該 segment 的 `.index` 中二分搜尋找到「最接近但不超過目標位移」的索引項**——**得到一個檔案偏移量**。**三、從那個偏移量開始順序掃描 `.log` 直到找到目標**。

**索引是稀疏的**（**預設每 4KB 資料建一個索引項**）——**這讓索引檔小到可以完全放進記憶體**，**代價是最後那一小段順序掃描**。

## 詳細解析

**「稀疏索引」的取捨很值得說**：稠密索引（每條訊息一項）能一步定位——**但索引檔會與資料檔同一個量級，放不進記憶體**。**而稀疏索引小到能全部映射進記憶體，於是「二分搜尋在記憶體中完成，只有最後 4KB 的掃描碰磁碟」**——**而那 4KB 通常還在頁快取裡**。**這是一個「用少量的順序掃描換取索引全記憶體化」的經典設計，與資料庫的稀疏索引思路一致。**

**「segment 的滾動」由三個條件觸發**：**大小達到上限（預設 1GB）、時間達到上限（預設 7 天）、或者索引檔滿了**。**滾動的意義在於「刪除是以 segment 為單位的」**——**過期的資料只需要刪掉整個檔案，而不是在檔案中間挖洞**。**這正是為什麼 Kafka 的資料清理幾乎沒有成本**，**而傳統佇列的刪除需要維護複雜的空間回收**。

**「只追加寫」是效能的根本來源**：訊息只會被寫到當前 segment 的末尾——**沒有隨機寫、沒有原地更新、沒有頁的分裂與合併**。**磁碟的順序寫吞吐可以接近記憶體的隨機寫**——**這個特性讓 Kafka 能用便宜的機械硬碟達到很高的吞吐**。

**「訊息批次是儲存的基本單位」**：生產者發送的是一個 RecordBatch——**而它在磁碟上、在網路上、在頁快取中都保持同樣的格式**。**這讓「壓縮」可以在批次層級一次完成並全程保持壓縮狀態**，**而 broker 不需要解壓縮就能轉發**——**這是零拷貝能成立的前提之一。**

## 面試回答方式

先給檔案佈局（partition 目錄、segment 的三個檔案、以檔名為起始位移）與**三步定位流程**，並說明**索引是稀疏的**。加分點有四個：**稀疏索引的取捨**——**稠密索引放不進記憶體，而稀疏索引讓二分在記憶體中完成、只有最後 4KB 碰磁碟且通常還在頁快取裡**；**segment 滾動的意義是刪除以檔案為單位**——**過期資料直接刪整個檔案而不是在中間挖洞**，**這是 Kafka 資料清理幾乎沒有成本的原因**；**只追加寫是效能的根本來源**——**沒有隨機寫與頁分裂，順序寫吞吐接近記憶體的隨機寫**；以及**訊息批次在磁碟、網路、頁快取中格式一致**，**讓壓縮全程保持而 broker 不需解壓縮**，**這是零拷貝的前提之一**。

## 講稿

一個分區對應磁碟上一個目錄，目錄裡是一組區段檔案。每個區段有三個檔案，訊息本體、位移索引、還有時間索引。檔名就是該區段的起始位移。

定位一條訊息分三步。先用二分在檔名中找到起始位移小於等於目標的那個區段。再在該區段的索引中二分找到最接近但不超過目標的索引項，得到一個檔案偏移量。最後從那裡開始順序掃描直到找到。

索引是稀疏的，預設每四 KB 建一項。這個取捨很值得說。稠密索引能一步定位，但索引檔會跟資料檔同一個量級，放不進記憶體。而稀疏索引小到能全部映射進記憶體，於是二分在記憶體中完成，只有最後四 KB 的掃描碰磁碟，而那四 KB 通常還在頁快取裡。

區段滾動還有一個重要意義，刪除是以區段為單位的。過期的資料只需要刪掉整個檔案，而不是在檔案中間挖洞。這正是 Kafka 的資料清理幾乎沒有成本的原因，而傳統佇列的刪除需要維護複雜的空間回收。

## 常見追問

### 為什麼還需要 timeindex？

**核心答案**：**因為「從某個時間點開始消費」是一個常見需求**——而 `.index` 只支援按位移查找。**timeindex 記錄「時間戳到位移」的映射**，**讓 `offsetsForTimes` 這類 API 能先用時間找到位移，再用位移找到位置**。**典型場景是「重放昨天下午三點之後的所有訊息」**——**而沒有 timeindex 就只能從頭掃描。**

**詳細解析**：**時間索引依賴的時間戳有兩種語義**，**而選錯會導致查詢結果不符預期**：`CreateTime`（生產者產生訊息時的時間，預設）與 `LogAppendTime`（broker 寫入時的時間）。**前者反映業務時間但可能亂序（生產者的時鐘不同、重試導致延遲）**——**於是時間索引不是嚴格單調的，查詢結果只能是近似的**。**後者嚴格單調但不反映事件實際發生的時間**。**多數場景用 CreateTime 是對的（業務關心事件時間），但要理解「按時間定位是近似的」**——**這在資料修復與重放場景中需要留一點餘裕（往前多讀一些再自己過濾）**。

**面試回答方式**：給用途（**按時間定位，典型場景是重放某個時間之後的訊息**）與它與位移索引的配合。核心加分點是**兩種時間戳語義的差別**：**CreateTime 反映業務時間但可能亂序，於是時間索引不嚴格單調、查詢結果是近似的**；**LogAppendTime 嚴格單調但不反映事件實際時間**。收在實務建議：**多數場景用 CreateTime，但要理解按時間定位是近似的**，**所以重放時要往前多讀一些再自己過濾**。

### 日誌壓實（compaction）的檔案是怎麼處理的？

**核心答案**：**背景執行緒把舊的 segment 重寫成「每個 key 只保留最新一條」的新 segment**。過程是：**先掃描建立一個「key 到最新位移」的映射，再逐個讀取舊 segment 並只寫出那些是最新版本的訊息**。**壓實後的檔案位移不再連續**（中間的舊版本被跳過了）——**但這不影響消費，因為消費者是按位移順序讀取而不假設連續**。

**詳細解析**：**「壓實不會處理當前正在寫入的 segment」是一個重要的細節**：活躍的那個 segment 永遠不被壓實——**所以最新寫入的資料一定保留完整的歷史**，**而這正是「壓實的 topic 仍然可以有短期的變更流」的原因**。**另一個關鍵是「墓碑訊息」**：**刪除一個 key 用的是「value 為 null 的訊息」**——**壓實時它會保留一段時間（`delete.retention.ms`）讓所有消費者都有機會看到這個刪除，之後才真正移除**。**如果這個時間設得太短，一個離線很久的消費者恢復後可能永遠不知道某個 key 被刪了**——**這是分散式狀態同步中一個經典的取捨，與 CRDT 的墓碑回收面對的是同一個問題**。

**面試回答方式**：給壓實的機制（建立 key 到最新位移的映射、重寫 segment、位移不再連續但不影響消費）。加分點是**活躍 segment 永遠不被壓實**，所以最新資料保留完整歷史。核心加分點是**墓碑訊息**：**刪除用 null value 的訊息，保留一段時間讓所有消費者有機會看到再真正移除**，**設太短的話離線很久的消費者恢復後永遠不知道某個 key 被刪了**——**這與 CRDT 的墓碑回收是同一個問題**。

### 磁碟滿了會怎樣？

**核心答案**：**broker 會停止接受寫入並可能下線該 partition**——**而這是一個很難優雅恢復的狀態**。**預防的關鍵是「保留策略要與磁碟容量匹配」**：**保留 7 天且每天寫入 100GB 就需要至少 700GB 加上副本與餘裕**。**監控上要對「磁碟使用率」設早期告警（例如 75%），因為到 90% 時處理的時間窗口已經很小。**

**詳細解析**：**「清理是背景進行的且有延遲」讓磁碟告警需要提前**：即使保留策略設對了，**清理執行緒也是週期性運行的（預設 5 分鐘檢查一次）**——**而在流量突增時，寫入的速度可能快過清理的速度**。**所以緩衝空間必須足夠**。**緊急處理的手段有三**：**縮短某些 topic 的保留時間（立即生效，清理會在下個週期執行）**、**刪除不再需要的 topic**、**以及把部分 partition 遷移到其他 broker**。**而最不該做的是「手動刪除 log 檔案」**——**那會讓 broker 的索引與實際資料不一致，通常導致更嚴重的問題**。**這條「不要繞過系統直接動它的資料檔」的規則適用於幾乎所有的儲存系統。**

**面試回答方式**：給後果與預防（保留策略與容量匹配、75% 就告警）。加分點是**清理是背景週期性進行的且有延遲**——**流量突增時寫入可能快過清理**，所以緩衝要足夠。給三個緊急手段並收在禁忌：**最不該做的是手動刪除 log 檔案**——**那會讓索引與實際資料不一致並導致更嚴重的問題**，**而「不要繞過系統直接動它的資料檔」適用於幾乎所有儲存系統**。
