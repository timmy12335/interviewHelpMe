# 題目

訊息可能重複投遞，消費端要怎麼保證重複處理不會出錯？

## 核心答案

三種做法，優先序由高到低。**一、讓操作本身天然冪等**——把「餘額增加 100」改成「餘額設為 500」、把「狀態往前推進」改成「條件更新：當前狀態是 A 時才改成 B」。這最乾淨，不需要任何額外儲存，重複執行結果完全相同。**二、業務唯一鍵加上唯一索引**——用訂單號、交易流水號當資料庫的唯一約束，重複插入直接失敗、捕捉後忽略即可。**三、去重表**——記錄已處理的訊息識別，處理前先查詢；關鍵是**去重記錄與業務寫入必須在同一個資料庫交易中**，否則「業務寫了但去重紀錄沒寫」的窗口仍會造成重複。最重要的一點是：**冪等的範圍必須涵蓋所有副作用**，不只是資料庫寫入。如果處理還包含呼叫外部 API、發送通知、寫入快取，每一項都要各自考慮重複的後果——通知類的副作用最容易被漏掉，因為它們沒有天然的冪等機制。

## 詳細解析

**天然冪等的設計思路是「傳狀態而非傳差異」**：訊息攜帶「這筆訂單現在的完整狀態」而不是「把狀態改成下一步」，下游直接覆蓋即可，重複幾次結果都一樣。配合版本號或更新時間，還能同時解決亂序的問題（只接受版本更新的訊息）。這個設計把「順序保證」與「去重」兩個問題一起解決了，是最值得優先考慮的方向。

**唯一索引的限制**：它只能防止**插入**重複，對更新類的操作沒有幫助。而且捕捉重複例外時要小心——不能把所有的約束違反都當成「重複訊息」忽略，必須確認是預期的那個唯一鍵，否則會把真正的資料錯誤靜默吞掉。實作上應該檢查例外中的約束名稱而非籠統地捕捉。

**去重表的三個設計點**：**識別的選擇**——用訊息的 topic、分區、位移組合可行，但若上游會重放（位移改變而業務上是同一筆）就會失效，此時要用**業務層的識別**。**清理策略**——不清理會無限成長，保留期必須大於訊息可能延遲的最長時間。**與業務寫入的原子性**——必須同交易，否則有窗口。這三點缺一，去重表就只是看起來有效。

**外部呼叫的冪等要靠對方支援**：呼叫第三方 API 時，重複的後果取決於對方。成熟的 API 通常支援**冪等鍵**——由呼叫方產生唯一鍵一併送出，對方保證同一個鍵只執行一次。如果對方不支援，就只能自己在呼叫前後記錄狀態（先寫「準備呼叫」、成功後寫「已完成」），但這仍有窗口（呼叫成功但記錄失敗），只能降低機率而非消除。**誠實面對這個限制**比宣稱完全冪等重要。

**冪等不是萬能的，要注意「副作用的順序」**：如果處理包含資料庫寫入與外部呼叫，重試時資料庫可能已經寫過（被去重擋下）但外部呼叫失敗需要重來——此時要確保**去重的判定發生在所有副作用完成之後**，否則會出現「資料庫認為處理過了，但外部呼叫其實沒成功」的不一致。實務上的做法是把去重記錄的寫入放在最後，或設計成可以查詢實際完成狀態的形式。

## 面試回答方式

給**三種做法並排優先序**，強調天然冪等最乾淨且不需要額外儲存。展開第一種時提出「**傳狀態而非傳差異**」這個設計思路，並指出配上版本號能同時解決去重與亂序——這是最有價值的一點。去重表要主動說出**必須與業務寫入同交易**這個關鍵條件。最重要的加分點是：**冪等的範圍必須涵蓋所有副作用**，特別是**通知類副作用沒有天然冪等最容易被漏掉**；以及**外部呼叫的冪等要靠對方支援冪等鍵**，對方不支援時只能降低機率而非消除，誠實面對這個限制。

## 講稿

我會依三種做法排優先序。

第一種是讓操作本身天然冪等。把餘額增加一百改成餘額設為五百，把狀態往前推進改成條件更新，只有當前狀態是 A 的時候才改成 B。這最乾淨，不需要任何額外儲存。

這裡有個更根本的設計思路，傳狀態而不要傳差異。訊息帶的是這筆訂單現在的完整狀態，下游直接覆蓋。配上版本號之後，還能同時解決亂序，只接受版本比較新的訊息。這樣去重跟順序兩個問題一起解決了。

第二種是業務唯一鍵加唯一索引，重複插入直接失敗，捕捉之後忽略。但它只能防插入，對更新沒有幫助。而且捕捉例外的時候要確認是預期的那個唯一鍵，不然會把真正的資料錯誤靜默吞掉。

第三種是去重表，關鍵是去重記錄跟業務寫入必須在同一個交易裡，不然有窗口。

最後我想強調一件事，冪等的範圍必須涵蓋所有副作用，不只是資料庫。如果還會呼叫外部 API 或發通知，每一項都要考慮。通知類的最容易被漏掉，因為它沒有天然的冪等機制。

## 常見追問

### 呼叫第三方 API 時要怎麼保證冪等？

**核心答案**：**優先使用對方提供的冪等鍵**——由你產生一個唯一鍵（通常是業務識別加上操作類型）隨請求送出，對方保證同一個鍵只執行一次並回傳相同結果。多數成熟的支付與通訊 API 都支援。如果對方不支援，退而求其次的做法是**先查詢再執行**（呼叫前先查對方的狀態，已完成就跳過），但這仍有競態窗口，只能降低重複機率。

**詳細解析**：如果連查詢介面都沒有，就只能在自己這邊記錄狀態：呼叫前寫入「進行中」、成功後更新為「已完成」。這樣重試時看到「進行中」可以選擇等待或視為可能已完成。問題是**呼叫成功但記錄失敗**的窗口仍然存在，所以這不是保證而是緩解。此時應該**在業務上設計成可容忍重複**（例如重複發送的通知加上去重的顯示邏輯），或者**接受風險並建立事後對帳**來偵測與修正。誠實地說「這個環節無法完全保證，我們用對帳兜底」比宣稱做到冪等更專業——因為後者在事故發生時會失去信任。

**面試回答方式**：優先給冪等鍵這個標準做法，再給「先查詢再執行」的退路並指出它有競態窗口。加分點是誠實說明無法完全保證時的處理——業務上容忍重複或用事後對帳兜底，並指出誠實承認限制比宣稱完全冪等更專業。

### 去重表會不會成為效能瓶頸？

**核心答案**：**在高吞吐時會**。每則訊息都要查一次、寫一次去重表，等於把訊息量直接轉成資料庫的讀寫量。緩解方式有三個：**優先改用天然冪等的操作**（根本不需要去重表）、**用唯一索引取代顯式查詢**（讓資料庫在插入時直接判斷，省掉一次查詢）、以及**分表或分片**（依識別的雜湊分散壓力）。如果訊息量極大且必須去重，可以考慮用支援高吞吐的鍵值儲存取代關聯式資料庫，但要注意**它與業務寫入的原子性可能無法保證**。

**詳細解析**：最後這一點是關鍵的取捨——去重記錄放在外部快取（例如 Redis）雖然快，但**無法與業務的資料庫寫入放在同一個交易中**，於是「快取寫了但資料庫失敗」或反之的窗口就出現了。判斷是否可接受要看業務：如果重複的後果只是輕微的（多發一封通知），用快取去重是合理的；如果後果嚴重（重複扣款），就必須用同交易的方案並承擔效能成本。這個「用一致性換效能」的決定應該是明確的、被記錄下來的，而不是為了效能悄悄放寬。

**面試回答方式**：確認高吞吐時會成為瓶頸，並給三種緩解（改天然冪等、用唯一索引省查詢、分片）。重點展開用外部快取去重的取捨——快但無法與業務寫入同交易，並給出依後果嚴重程度判斷的原則，強調這個決定應該明確而非悄悄放寬。

### 訊息的識別該用什麼？

**核心答案**：**優先用業務層的唯一識別**（訂單號、交易流水號、事件 ID），而不是 Kafka 的 topic、分區、位移組合。原因是**位移在重放時會改變**——上游重新產生同一批事件時位移不同，用位移去重會完全失效，於是重放變成重複執行。業務識別則在重放後仍然相同，去重依然有效。

**詳細解析**：如果上游沒有提供業務識別，可以要求它在訊息中加上一個**產生時就決定的唯一 ID**（例如 UUID），並保證重放時沿用原本的 ID 而非重新產生——這是上游需要配合的設計約定，值得在介面規範中明確寫下來。另一個折衷是用**訊息內容的雜湊**當識別，但要小心內容中若含有時間戳記或隨機欄位，同一筆業務的雜湊會不同而失效。實務上最穩健的還是要求上游提供穩定的業務識別，這也符合「**事件應該自帶身分**」這個事件設計原則——一個沒有唯一識別的事件，在任何需要去重或追蹤的場景都會造成麻煩。

**面試回答方式**：明確主張用業務識別而非位移，並用「重放時位移改變」說明為什麼位移會失效。加分點是提出要求上游提供穩定 ID 並寫進介面規範、內容雜湊的陷阱（時間戳記讓雜湊不同），並歸納出「事件應該自帶身分」這個設計原則。
