# 題目

什麼是零拷貝？Java 裡有哪些方式可以達成，各自的代價是什麼？

## 核心答案

「零拷貝」指的是**減少資料在使用者態與核心態之間的複製次數**，不是真的一次都不複製。傳統的「讀檔案再送到 socket」要 **4 次複製與 4 次上下文切換**：磁碟到核心緩衝（DMA）、核心緩衝到使用者緩衝、使用者緩衝到 socket 緩衝、socket 緩衝到網卡（DMA）。中間那兩次「經過使用者態」是純粹的浪費——應用程式根本沒有讀那些位元組的內容。

Java 有三種主要做法。**`FileChannel.transferTo`**（底層是 `sendfile`）讓資料直接從檔案的核心緩衝送到 socket，**不進入使用者態**，複製降到 2 次（兩次都是 DMA）、切換降到 2 次。**`MappedByteBuffer`**（底層是 `mmap`）把檔案映射進行程的位址空間，讀寫記憶體就是讀寫檔案，省掉核心到使用者的那次複製。**`DirectByteBuffer`** 在堆積外配置記憶體，讓 IO 不必先把資料從 Java 堆積複製到一塊固定的原生記憶體。

## 詳細解析

**為什麼堆積上的 byte[] 不能直接做 IO**：GC 會移動物件，而系統呼叫執行期間位址必須固定。所以用 `byte[]` 做 IO 時，JDK 內部會先把資料複製到一塊臨時的直接記憶體再交給核心——**這次複製是隱形的，很多人不知道它存在**。`DirectByteBuffer` 就是把這塊記憶體變成長期持有的，省掉每次的複製。代價是**配置與釋放都很貴**（要走 `malloc` 與 `Cleaner`），而且不受堆積大小限制、只受 `-XX:MaxDirectMemorySize` 控制，**洩漏時 heap dump 上看不出來**——這是 Netty 這類框架要自己做記憶體池的原因。

**transferTo 的限制決定了它的適用範圍**：它要求**資料原封不動地轉發**，因為應用程式根本碰不到那些位元組。所以能用它的場景是靜態檔案伺服、檔案複製、以及 Kafka 把日誌段直接送給消費者——**Kafka 的高吞吐有很大一部分來自這裡**。反過來說，只要需要加解密、壓縮、修改內容，就必須把資料讀進使用者態，零拷貝就用不上了（TLS 就是這樣讓 `sendfile` 失效的，除非有支援 kTLS 的核心）。

**mmap 的代價常被低估**：它省掉一次複製，但帶來**缺頁中斷**（第一次存取每一頁都要觸發）、**無法控制的刷寫時機**（作業系統決定何時把髒頁寫回磁碟，程式崩潰時可能丟資料，要靠 `force()` 但那又是同步 IO）、以及 **JVM 無法及時解除映射**（`MappedByteBuffer` 沒有公開的 unmap 方法，要等 GC 回收，映射大檔案時可能撐爆虛擬位址空間）。所以 mmap 適合**大檔案的隨機讀取**，不適合順序串流（順序讀時預讀機制已經很有效，mmap 的收益有限而風險不小）。

**判斷值不值得的關鍵是「資料量與處理成本的比例」**：零拷貝省下的是每位元組的複製成本。如果每筆資料都要做複雜的業務處理，那點複製成本佔比極小，優化它毫無意義。它真正發光的場景是**資料量巨大而處理極少**——檔案轉發、日誌傳輸、代理伺服器。**在一般的 CRUD 應用裡談零拷貝，通常是把力氣用在錯的地方**。

## 面試回答方式

先精確定義——**減少使用者態與核心態之間的複製，不是完全不複製**，並把傳統路徑的 **4 次複製 4 次切換**拆解出來，指出中間兩次是純浪費。接著給三種做法與各自機制（`transferTo`／`sendfile`、`MappedByteBuffer`／`mmap`、`DirectByteBuffer`）。有兩個很能拉開差距的細節：**堆積上的 byte[] 做 IO 時 JDK 內部會隱形地複製一次到直接記憶體**（因為 GC 會移動物件而系統呼叫需要固定位址）；以及 **`transferTo` 要求資料原封不動轉發**，所以加密壓縮一介入就失效，這解釋了為什麼 Kafka 能用而一般應用不能。最後收在判斷準則：零拷貝省的是每位元組成本，只有在**資料量巨大而處理極少**時才值得，一般 CRUD 應用談它是用錯力氣。

## 講稿

零拷貝指的是減少資料在使用者態跟核心態之間的複製次數，不是真的一次都不複製。

傳統的讀檔案再送到 socket 要四次複製。磁碟到核心緩衝、核心緩衝到使用者緩衝、使用者緩衝到 socket 緩衝、最後送到網卡。中間那兩次經過使用者態是純粹的浪費，因為應用程式根本沒有讀那些位元組的內容。

Java 主要有三種做法。第一種讓資料直接從檔案的核心緩衝送到 socket，複製降到兩次，兩次都是 DMA。第二種是把檔案映射進位址空間，讀寫記憶體就是讀寫檔案。第三種是在堆積外配置緩衝。

有一個細節我覺得很多人不知道。用堆積上的位元組陣列做 IO 的時候，JDK 內部會先偷偷複製一份到直接記憶體，因為垃圾回收會移動物件，而系統呼叫期間位址必須固定。

最後講適用邊界。零拷貝要求資料原封不動地轉發，只要需要加密或壓縮就用不上了。它真正有價值的場景是資料量巨大而處理極少，像是靜態檔案伺服跟訊息佇列的日誌傳輸。

## 常見追問

### Kafka 是怎麼利用零拷貝的？

**核心答案**：Kafka 把訊息以**與網路傳輸完全相同的二進位格式**存在磁碟的日誌段檔案裡。消費者拉取時，broker 直接用 `FileChannel.transferTo` 把檔案的某個區間送進 socket——**訊息內容從頭到尾沒有進入 JVM 堆積**。這是它能在單機上做到極高吞吐的關鍵之一，也解釋了為什麼 Kafka 的 broker 記憶體需求相對低（大部分快取交給作業系統的 page cache）。

**詳細解析**：這個設計是**格式決定的**——正因為儲存格式與傳輸格式一致，才可能原封不動地轉發。如果 broker 需要解析每則訊息（例如做內容過濾或格式轉換），零拷貝立刻失效。這也是為什麼**開啟 TLS 之後 Kafka 的吞吐會明顯下降**：加密必須在使用者態進行，資料得完整讀進來加密再送出。同樣地，broker 端的壓縮轉換（生產者與消費者用不同壓縮格式時）也會讓它退回一般路徑。**Kafka 的效能故事其實是「用格式設計換取系統呼叫層級的最佳化」，而不是某個聰明的演算法**。

**面試回答方式**：關鍵是點出**儲存格式與傳輸格式一致**這個設計決定，零拷貝只是它的結果。然後給兩個會讓它失效的具體情況：TLS 加密與 broker 端壓縮轉換，並說明這解釋了開啟 TLS 後吞吐下降。收在一句總結：這是用格式設計換系統呼叫層級的最佳化，而不是演算法上的聰明。

### DirectByteBuffer 的記憶體什麼時候被釋放？

**核心答案**：它的原生記憶體**不由 GC 直接管理**。`DirectByteBuffer` 物件本身在堆積上，配置的原生記憶體則掛在一個 `Cleaner`（JDK 9 前）或 `Cleaner` API 的清理器上；**只有當那個 Java 物件被 GC 回收時，清理動作才會執行並釋放原生記憶體**。問題在於 `DirectByteBuffer` 物件很小，堆積壓力可能很久都不足以觸發 GC，於是**堆積看起來很空閒、原生記憶體卻已經爆了**。

**詳細解析**：這造成兩類實務問題。第一，**`OutOfMemoryError: Direct buffer memory`** 在堆積使用率很低時發生，讓人一頭霧水；預設上限是 `-Xmx` 的值，可以用 `-XX:MaxDirectMemorySize` 明確設定。第二，**診斷困難**——heap dump 裡看不到原生記憶體的用量，要靠 NMT（Native Memory Tracking）或 `BufferPoolMXBean` 才看得到。實務上的解法是**池化**：Netty 的 `PooledByteBufAllocator` 自己管理一塊大的直接記憶體並切分重用，配合引用計數明確釋放，不依賴 GC 的時機。**這是「把資源生命週期從 GC 手上拿回來」的典型案例**，也說明了為什麼高效能網路框架不能只依賴 Java 的自動記憶體管理。

**面試回答方式**：核心是「原生記憶體的釋放綁在 Java 物件被 GC 回收的時機上，而那個物件很小、不足以觸發 GC」。給出兩個具體後果：堆積很空卻拋 Direct buffer memory 的 OOM、heap dump 看不到用量要靠 NMT。收在解法與它的意義——Netty 用池化加引用計數把生命週期從 GC 手上拿回來。

### 虛擬執行緒與零拷貝有關係嗎？

**核心答案**：**沒有直接關係，它們解決的是不同層次的問題**。零拷貝減少的是**每位元組的資料搬運成本**，虛擬執行緒減少的是**每個並行任務的執行緒成本**。一個是資料平面的最佳化，一個是併發模型的最佳化。混淆兩者是常見的誤解——把虛擬執行緒當成「讓 IO 變快的東西」，但它讓 IO 阻塞變便宜，不讓 IO 本身變快。

**詳細解析**：兩者在高吞吐服務裡是**互補的**。虛擬執行緒讓「一個連線一個執行緒」的簡單寫法重新可行（阻塞時掛起虛擬執行緒而不佔用平台執行緒），零拷貝讓每個連線的資料搬運成本降低。但要注意虛擬執行緒有它自己的陷阱——**在 `synchronized` 區塊內阻塞會釘住（pin）平台執行緒**（JDK 21 的限制，後續版本改善），以及大量虛擬執行緒同時持有大緩衝時的記憶體壓力。**能清楚區分「哪一層的成本」是這題的核心價值**：面對效能問題時，先確認瓶頸在資料搬運、在執行緒排程、還是在演算法，再選工具。

**面試回答方式**：先明確否定關聯並給出區分——**零拷貝是資料平面、虛擬執行緒是併發模型**，一個省每位元組成本、一個省每任務成本。點出常見誤解（把虛擬執行緒當成讓 IO 變快）。然後說明兩者互補，並補一個虛擬執行緒的實務陷阱（在 `synchronized` 內阻塞會釘住平台執行緒）。收在方法論：先確認瓶頸在哪一層再選工具。
