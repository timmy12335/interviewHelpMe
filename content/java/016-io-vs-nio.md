# 題目

Java 的 BIO、NIO、AIO 有什麼差異？NIO 的三大核心元件是什麼？

## 核心答案

BIO（Blocking IO）是傳統的同步阻塞 IO——每個連線需要一個執行緒，讀寫時執行緒會阻塞等待，高並發下執行緒開銷巨大。NIO（Non-blocking IO，JDK 4 引入）是同步非阻塞 IO——透過「多路復用器 Selector」讓單一執行緒管理多個連線，只處理真正有資料的連線，大幅提升高並發能力。AIO（Asynchronous IO，JDK 7 引入）是非同步非阻塞 IO——發起 IO 操作後不等待，作業系統完成後透過回呼通知，理論上更進一步但實際應用較少。NIO 三大核心是 Channel（通道）、Buffer（緩衝區）、Selector（多路復用器）。

## 詳細解析

**BIO（同步阻塞）**：

- 一個連線一個執行緒，執行緒在讀寫時完全阻塞直到資料就緒。
- 問題：高並發下需要海量執行緒（例如一萬個連線就要一萬個執行緒），執行緒的建立、切換、記憶體開銷讓系統無法承受。
- 適用：連線數少、每個連線資料量大的場景。

**NIO（同步非阻塞 + 多路復用）**：

- 核心是「多路復用」——用一個 `Selector` 監聽多個 `Channel`，只有當某個 Channel 真的有資料可讀/可寫時才去處理它，一個執行緒就能高效管理成千上萬個連線。
- 「非阻塞」指的是：執行緒發起讀取時如果沒資料，會立即返回而非傻等，可以去處理其他 Channel。
- 適用：高並發、連線數多但每個連線資料量小的場景（如聊天伺服器、Netty 底層）。

**AIO（非同步非阻塞）**：

- 發起 IO 操作後立即返回，由作業系統在背景完成 IO，完成後透過回呼（CompletionHandler）通知應用程式。
- 應用程式完全不需要主動查詢或等待，是真正的「非同步」。
- 實際應用較少：Linux 對 AIO 的支援不如 Windows 完善，且 Netty 等主流框架基於 NIO 已能滿足絕大多數需求，所以 AIO 生態不成熟。

**NIO 三大核心元件**：

1. **Channel（通道）**：雙向的資料傳輸通道（可讀可寫），如 `SocketChannel`、`FileChannel`，取代 BIO 的單向 Stream。
2. **Buffer（緩衝區）**：資料的容器，NIO 的讀寫都是面向 Buffer 的（先讀進 Buffer 再處理，或先寫入 Buffer 再送出），有 position/limit/capacity 等狀態。
3. **Selector（多路復用器）**：一個執行緒用一個 Selector 監聽多個 Channel 的事件（連線、可讀、可寫），實現「一個執行緒管理多個連線」。

## 面試回答方式

用「同步/非同步、阻塞/非阻塞」這兩個維度來組織回答最清楚——BIO 是同步阻塞、NIO 是同步非阻塞（多路復用）、AIO 是非同步非阻塞。核心要講清楚 NIO 的價值是「多路復用讓一個執行緒管理海量連線」，這是它解決 BIO「一連線一執行緒」瓶頸的關鍵。三大核心元件（Channel/Buffer/Selector）要能說出各自角色，尤其 Selector 是多路復用的核心。如果能提到「Netty 基於 NIO」「AIO 因 Linux 支援不佳而少用」這些實務現況，會展現你對 IO 生態的真實認識。

## 常見追問

### NIO 的「非阻塞」和「多路復用」是同一件事嗎？

**核心答案**：不是同一件事，是兩個層次的概念。「非阻塞」指的是「單一 IO 操作（如讀取）在資料未就緒時立即返回而不傻等」；「多路復用」指的是「用一個 Selector 同時監聽多個 Channel、只在有事件時才處理對應的 Channel」。多路復用是建立在非阻塞之上、並依賴作業系統的 select/poll/epoll 機制來實現「一個執行緒高效管理多個連線」的更高層架構。

**詳細解析**：非阻塞只是「不傻等」——但如果只有非阻塞而沒有多路復用，你仍然需要不斷輪詢每個 Channel「有資料了嗎？」（忙輪詢）非常浪費 CPU。多路復用透過 Selector（底層對應作業系統的 epoll 等機制）解決了這個問題——你把多個 Channel 註冊到 Selector，然後呼叫 `selector.select()` 阻塞等待「任何一個 Channel 有事件」，作業系統會在有事件時喚醒你並告訴你「哪些 Channel 就緒了」，你只需處理這些就緒的 Channel，完全不需要輪詢那些沒事件的。所以完整的 NIO 高並發能力 = 非阻塞（單次操作不傻等）+ 多路復用（Selector 統一管理、只處理就緒的）。理解兩者是不同層次的概念，能展現你對 NIO 的理解不流於表面。

**面試回答方式**：明確區分「非阻塞是單次操作不傻等、多路復用是一個 Selector 管多個 Channel 只處理就緒的」，並點出「只有非阻塞沒有多路復用會導致忙輪詢浪費 CPU、多路復用靠 epoll 避免輪詢」，這種能拆解兩個常被混為一談的概念的回答，很能展現你對 NIO 底層機制的深入理解。

### NIO 的 Buffer 有哪些關鍵狀態？flip() 做了什麼？

**核心答案**：Buffer 有三個關鍵狀態——`capacity`（容量，Buffer 的總大小）、`position`（當前讀寫位置）、`limit`（讀寫的上限）。`flip()` 用於「從寫入模式切換到讀取模式」——它把 `limit` 設為當前的 `position`（標記「剛才寫到哪裡」作為讀取上限），再把 `position` 歸零（從頭開始讀），這樣就能把剛寫入的資料正確地讀出來。

**詳細解析**：NIO 的 Buffer 是「讀寫共用同一塊空間、靠狀態切換模式」的設計，這是新手最容易搞混的地方。寫入時`position` 隨著寫入不斷後移，`limit` 等於 `capacity`；當你寫完想讀時，直接讀是錯的（`position` 停在寫入的末尾、後面是空的），必須呼叫 `flip()`——它把 `limit` 定在「剛才寫入的末尾位置」（讀取不能超過這裡），把 `position` 拉回 0（從頭讀）。讀完後如果想再寫，用 `clear()`（position 歸零、limit 回到 capacity，覆蓋舊資料）或 `compact()`（保留未讀資料、繼續寫）。忘記 `flip()` 是 NIO 程式設計最常見的 bug 之一——寫完直接讀會讀到空資料或錯位資料。

**面試回答方式**：先講三個狀態（capacity/position/limit）的含義，再用「寫入後 position 在末尾、flip 把 limit 設到這末尾、position 歸零讓你從頭讀」清楚說明 flip 的作用。能點出「忘記 flip 是 NIO 常見 bug」展現你有實際寫過 NIO 程式碼，而不只是背概念。

### 為什麼像 Netty 這樣的框架選擇 NIO 而不是 AIO？

**核心答案**：主要原因是——Linux 對 AIO 的支援不成熟（Linux 的 AIO 實作有諸多限制，底層其實仍用 epoll 模擬，沒有真正的效能優勢），而伺服器絕大多數跑在 Linux 上；相比之下 NIO 的 epoll 機制在 Linux 上非常成熟高效，Netty 基於 NIO 已經能達到極高的並發效能，AIO 帶來的複雜度並沒有換來實質的效能提升，所以 Netty 甚至曾經加入 AIO 支援後又移除了。

**詳細解析**：理論上 AIO（非同步）比 NIO（同步非阻塞）更進一步——連「檢查哪些 Channel 就緒」都交給作業系統，應用只需等回呼。但實務上這個理論優勢在 Linux 上無法兌現：Linux 的原生 AIO（io_uring 出現之前）對網路 IO 的支援很弱，JDK 的 AIO 在 Linux 底層其實還是用 epoll 模擬非同步，並沒有比直接用 NIO 的 epoll 更快，反而多了一層封裝的複雜度。而 Windows 的 IOCP 雖然是真正高效的非同步，但伺服器很少用 Windows。Netty 團隊評估後認為 AIO 在主流的 Linux 伺服器上沒有實質收益，且維護兩套 IO 模型增加複雜度，所以專注於把基於 NIO（epoll）的實作做到極致。這也提醒我們——理論上更先進的技術，在特定平台的實作成熟度才是實務選型的決定因素。

**面試回答方式**：講出核心原因「Linux 的 AIO 支援不成熟、底層仍用 epoll 模擬沒有實質優勢，而伺服器主要跑 Linux」，並點出「Netty 曾加入 AIO 又移除」這個實例。能得出「理論先進性不等於實務優勢，平台實作成熟度才是關鍵」這個洞察，展現你對技術選型有超越紙面比較的務實判斷。
