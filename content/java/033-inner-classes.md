# 題目

內部類別與靜態巢狀類別差在哪？為什麼非靜態內部類別容易造成記憶體洩漏？

## 核心答案

差別只有一個，但後果很大：**非靜態內部類別持有一個指向外部實例的隱藏引用**（編譯後是一個名為 `this$0` 的合成欄位），靜態巢狀類別沒有。

這個隱藏引用帶來三個後果。第一，**建立方式不同**——非靜態內部類別必須先有外部實例（`outer.new Inner()`），靜態巢狀類別可以獨立建立。第二，**生命週期被綁住**——只要內部類別的實例還活著，外部實例就無法被回收；如果內部實例被交給一個長生命週期的物件（監聽器、執行緒、靜態集合、快取），整個外部物件連同它引用的所有東西都會被留住，這就是洩漏。第三，**序列化會連帶**——序列化內部類別實例會嘗試序列化外部實例。

實務規則很簡單：**巢狀類別預設加 static，只有真的需要存取外部實例狀態時才拿掉**。這是《Effective Java》明確的建議，也是靜態分析工具會檢查的項目。

## 詳細解析

**編譯後的樣子解釋了一切**：`Outer$Inner.class` 會多一個 `final Outer this$0` 欄位，建構子也多一個 `Outer` 參數。存取外部欄位其實是 `this$0.field`。JDK 11 之前甚至會為此生成合成的橋接方法（因為內部類別存取外部的私有成員在位元組碼層面是跨類別存取），JDK 11 的巢狀存取控制（Nest-Based Access Control）才讓同一個巢狀群組直接互相存取，消除了這些合成方法。

**洩漏的典型場景是「短命物件註冊到長命容器」**：在一個 Activity 或 Service 裡用非靜態內部類別寫一個回呼，把它註冊到全域的事件匯流排；即使那個外部物件早該被銷毀，事件匯流排仍持有回呼，回呼持有 `this$0`，於是外部物件與它引用的整棵物件圖都留在堆積裡。**同樣的機制也適用於匿名類別與非靜態的 lambda**——匿名類別一定捕獲外部實例；lambda 則只在**真的用到 `this` 或外部實例成員時**才捕獲，這是 lambda 比匿名類別安全的一個實際理由。

**匿名類別與 lambda 的差異不只是語法糖**：匿名類別編譯成一個獨立的 `.class` 檔（`Outer$1.class`），每次執行到都會 `new` 一個實例；lambda 編譯成 `invokedynamic`，由 `LambdaMetafactory` 在首次執行時生成實作，**無狀態的 lambda 還可以被重用同一個實例**。所以在熱路徑上大量建立回呼時，lambda 的配置壓力明顯較小。但 lambda 只能實作**函式介面**（單一抽象方法），需要多個方法或需要具名、需要持有狀態時仍然要用匿名類別或具名類別。

**區域類別與捕獲的變數必須是 effectively final**：這是為了避免「拷貝語意」造成的困惑——捕獲的是變數當下的值（對物件是引用的拷貝），如果允許之後修改，方法內外會看到不同的值。Java 選擇直接禁止而不是提供可變捕獲，理由與值傳遞一致：**寧可讓限制顯式，也不要讓語意隱晦**。需要可變狀態時該用陣列或 `AtomicReference` 包起來，但那通常是設計該調整的訊號。

## 面試回答方式

先給**唯一的差別**——非靜態內部類別有一個指向外部實例的隱藏欄位 `this$0`，並立刻帶出三個後果：建立方式、生命週期綁定、序列化連帶。洩漏的部分要給具體場景：**短命物件的回呼註冊到長命容器**，回呼持有外部實例，整棵物件圖被留住。接著給實務規則：**巢狀類別預設加 static**。兩個能拉開差距的補充：**lambda 只在真的用到外部成員時才捕獲**，匿名類別則一定捕獲，所以 lambda 在這件事上更安全；以及 lambda 走 `invokedynamic`、無狀態時可重用實例，匿名類別每次都要 new，熱路徑上配置壓力不同。

## 講稿

差別只有一個，但後果很大。非靜態內部類別持有一個指向外部實例的隱藏引用，編譯之後是一個合成欄位。靜態巢狀類別沒有這個東西。

這個隱藏引用帶來三個後果。建立的時候必須先有外部實例。生命週期被綁住，只要內部實例還活著，外部實例就回收不掉。還有序列化的時候會連帶把外部實例一起序列化。

洩漏最典型的場景是短命物件註冊到長命容器。用非靜態內部類別寫一個回呼，註冊到全域的事件匯流排，就算外部物件早該銷毀，匯流排還持有回呼，回呼持有外部實例，整棵物件圖都留在堆積裡。

所以我的規則很簡單，巢狀類別預設加 static，只有真的需要存取外部實例狀態的時候才拿掉。

補一個我覺得實用的差異。匿名類別一定會捕獲外部實例，lambda 只有在真的用到外部成員的時候才捕獲。這是 lambda 在這件事上比較安全的實際理由。

## 常見追問

### 為什麼捕獲的區域變數必須是 effectively final？

**核心答案**：因為捕獲的是**值的拷貝**，不是變數本身。內部類別或 lambda 的實例可能比方法的堆疊框架活得更久，所以它必須把用到的區域變數複製一份存進自己的欄位。如果允許之後修改原變數，就會出現「方法裡看到新值、內部類別裡還是舊值」的分裂狀態。Java 的選擇是**直接禁止修改，讓限制顯式**，而不是提供可變捕獲然後留下一個難以推理的語意。

**詳細解析**：其他語言選了不同的路。JavaScript 的閉包捕獲的是**變數本身**（透過作用域鏈），所以修改是共享的，代價是經典的「迴圈裡註冊回呼全部拿到最後一個值」問題。C# 也捕獲變數本身，並在 C# 5 特別修改了 foreach 迴圈變數的語意來避開同一個坑。**Java 用限制換掉了一整類 bug**，代價是需要可變狀態時得繞路——用長度為 1 的陣列、`AtomicInteger`，或者重新設計成不需要共享可變狀態。注意 effectively final 只約束**變數的重新賦值**，不約束它指向的物件：捕獲一個 `List` 之後仍然可以 `add`。

**面試回答方式**：核心是「**捕獲的是值的拷貝，而內部實例可能活得比堆疊框架久**」，若允許修改會出現值分裂。加分點是拿 JavaScript 與 C# 的閉包做對照，說明它們捕獲變數本身因而有迴圈變數的經典坑，Java 用一個限制換掉了一整類 bug。最後補一句精確的界線：約束的是重新賦值，不是被指向物件的內容。

### lambda 與匿名類別在效能上具體差在哪？

**核心答案**：三點。**類別數量**——每個匿名類別是一個獨立的 class 檔，大量使用會讓類別載入與 metaspace 佔用上升；lambda 由 `LambdaMetafactory` 在執行期生成，且相同的 lambda 站點共用。**物件配置**——匿名類別每次執行到都 `new` 一個；**無捕獲的 lambda 會被快取重用同一個實例**，有捕獲的才需要每次建立。**首次成本**——lambda 的 `invokedynamic` 在首次呼叫時要做連結（linkage），比匿名類別稍慢，之後就一樣。

**詳細解析**：實務上這些差異多半不是瓶頸，真正值得注意的是**捕獲造成的配置**。在熱迴圈裡寫 `list.forEach(x -> process(x, config))` 時，如果 `config` 是外部變數，每次進入這行都要建立一個新的 lambda 實例。JIT 的逃逸分析常常能消除它（因為 lambda 沒有逃出方法），但這不是保證。另一個常被忽略的成本是**堆疊追蹤**——lambda 在例外堆疊裡顯示為 `lambda$method$0` 這種合成名稱，而且中間夾著 `LambdaMetafactory` 的框架，除錯時比具名類別難讀。**在複雜或需要長期維護的邏輯上，具名類別的可讀性收益通常大於 lambda 的簡潔**。

**面試回答方式**：分三點給差異（類別數量、物件配置、首次連結成本），並明確指出**無捕獲的 lambda 會重用實例**這個具體事實。然後把重點轉到實務判斷：多數情況不是瓶頸，值得注意的是熱迴圈裡的捕獲配置，而逃逸分析常能消除但不保證。收在一個非效能的理由——lambda 的堆疊追蹤難讀，複雜邏輯用具名類別更好維護。

### 什麼情況下非靜態內部類別是正確的選擇？

**核心答案**：當內部類別**在概念上是外部物件的一部分，且離開外部實例就沒有意義**時。最典型的是**集合的迭代器**——`ArrayList` 的 `Itr` 必須存取外部的 `elementData`、`size` 與 `modCount`，而且一個迭代器天生就屬於某一個特定的清單。這種情況下隱藏引用不是負擔，而是正確表達了「這個物件依附於那個物件」的關係。

**詳細解析**：判斷的關鍵是**生命週期是否天然一致**。迭代器通常在一個方法或迴圈內用完就丟，不會比清單活得久，所以隱藏引用造成不了洩漏。反過來說，**只要內部實例可能被交給外部世界並長期持有**（監聽器、回呼、執行緒、快取的值），就該改成靜態巢狀類別加一個明確的弱引用或明確傳入需要的資料。這也給了一個更一般的原則：**隱藏引用的風險與「這個實例會流到哪裡」成正比**，而不是與類別本身有關。看到非靜態內部類別時該問的不是「它有沒有問題」，而是「它的實例會被誰持有多久」。

**面試回答方式**：用 `ArrayList` 的迭代器當正例，說明它必須存取外部的欄位而且天生屬於某個清單，隱藏引用在這裡是正確的表達。接著給判準——**生命週期是否天然一致**，並指出風險真正的來源是「實例會流到哪裡、被持有多久」，而不是類別形式本身。收在具體處理：會流到外部就改成靜態巢狀加明確傳入需要的資料。
