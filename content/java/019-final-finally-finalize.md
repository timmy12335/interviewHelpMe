# 題目

`final`、`finally`、`finalize` 這三個看起來相似的關鍵字/方法有什麼差異？

## 核心答案

三者除了名字相似外沒有關聯。`final` 是修飾符——修飾變數表示不可重新賦值（常數）、修飾方法表示不可被覆寫、修飾類別表示不可被繼承。`finally` 是例外處理的區塊——不管 try 區塊是否拋例外，`finally` 中的程式碼都會執行（用於資源清理）。`finalize()` 是 `Object` 的一個方法，在物件被 GC 回收前會被呼叫一次，但因為執行時機不確定、有效能與正確性問題，已在 JDK 9 被標記為過時（deprecated），不該再使用。

## 詳細解析

**final（修飾符）**：

- **修飾變數**：變數只能被賦值一次，之後不可改變。對基本型別是值不可變，對引用型別是「引用」不可變（但引用指向的物件內部仍可修改）。
- **修飾方法**：該方法不能被子類別覆寫（override）。
- **修飾類別**：該類別不能被繼承（如 `String`、`Integer` 都是 final 類別）。
- 好處：表達「不可變」的設計意圖、幫助編譯器優化、保證安全性（如不可變物件、常數）。

**finally（例外處理區塊）**：

- 配合 try-catch 使用，`finally` 中的程式碼「一定會執行」（除了 `System.exit()`、JVM 崩潰等極端情況）。
- 主要用途：釋放資源（關閉檔案、連線、鎖），保證清理邏輯無論如何都會執行。
- 現代更推薦用 `try-with-resources` 自動管理資源，取代手動 finally 關閉。

**finalize()（已廢棄的方法）**：

- 定義在 `Object`，物件被 GC 回收前會被呼叫一次，原意是給物件一個「臨終清理」的機會。
- 問題重重：執行時機完全不確定（取決於 GC 何時運行，可能很久甚至永遠不執行）、會拖慢 GC、可能導致物件「復活」、例外會被吞掉。
- JDK 9 起被標記為 `@Deprecated`，官方明確建議改用 `try-with-resources` 或 `Cleaner` 機制。實務中不該再使用 `finalize`。

## 面試回答方式

這題考的是「別被相似的名字騙了」——開門見山點出「三者除了名字像，本質毫無關聯」，然後逐一講清楚各自是什麼（final 是修飾符、finally 是例外區塊、finalize 是方法）。final 要能講出修飾變數/方法/類別三種情況。finally 講「一定執行、用於資源清理」。finalize 的關鍵是「已廢棄、不該用」——能講出它為什麼被廢棄（時機不確定、拖慢 GC、可能復活）會是加分點，展現你了解 Java 的演進而不是停留在舊知識。

## 常見追問

### final 修飾引用型別變數，物件內容還能改嗎？

**核心答案**：能。`final` 修飾引用型別變數時，限制的是「這個變數不能再指向別的物件」（引用/位址不可變），但它所指向的那個物件的「內部狀態」仍然可以被修改。例如 `final List<String> list = new ArrayList<>();`，你不能再讓 `list` 指向另一個 List（`list = new ArrayList<>()` 會編譯錯誤），但可以 `list.add("x")` 修改這個 List 的內容。

**詳細解析**：這是 `final` 一個常被誤解的點——`final` 保證的是「引用的不變」，不是「物件的不變」。對基本型別（`final int x = 5`），值本身不可變；但對引用型別，`final` 只鎖定了「變數持有的引用」，不鎖定「引用指向的物件」。這也是為什麼「不可變物件（immutable object）」需要的不只是把欄位宣告為 `final`——把欄位設為 final 只保證欄位引用不變，若欄位指向的是一個可變物件（如可變的 List），這個物件的內容仍可能被改動，破壞不可變性。真正的不可變物件還需要——欄位指向的也是不可變物件、或對外只提供防禦性複製（defensive copy）、不洩漏內部可變物件的引用。理解這個區別對設計執行緒安全的不可變物件很重要。

**面試回答方式**：明確回答「引用不可變，但物件內容可變」，並用 `final List` 能 add 但不能重新賦值的例子佐證。能延伸到「所以設計不可變物件光靠 final 不夠，還需要防禦性複製」，展現你理解 final 的精確語意以及它與真正不可變性的差距，這是很有深度的延伸。

### finally 中的 return 會發生什麼？

**核心答案**：如果 `finally` 區塊中有 `return`，它會「覆蓋」try 或 catch 中的 return 值——也就是最終返回的是 finally 的值，而不是 try 中原本要返回的值；更糟的是，如果 try 中拋出了例外，finally 中的 return 會「吞掉」這個例外（例外不會被拋出，方法正常返回 finally 的值）。因此 `finally` 中絕對不應該寫 `return`，這是公認的反模式。

**詳細解析**：執行流程是——當 try 中執行到 `return x` 時，會先把 x 的值準備好，然後執行 finally；如果 finally 中也有 `return y`，這個 return 會直接讓方法返回 y，try 中準備好的 x 就被丟棄了。更危險的情況是 try 中拋出例外，本應向上傳播，但如果 finally 中有 return，方法會因為這個 return 而「正常結束」，那個例外就被靜默吞掉了，呼叫方完全不知道發生過錯誤——這會造成極難排查的 bug（錯誤憑空消失）。所以最佳實踐是：`finally` 只用來做清理（關資源），絕不放 return、也不要在 finally 中拋出新例外（同樣會覆蓋原例外）。

**面試回答方式**：講清楚兩個後果——「覆蓋 try 的返回值」和「吞掉 try 拋出的例外」，尤其強調「吞例外導致錯誤憑空消失」的危險性，並給出結論「finally 不該有 return」。能點出這個反模式的具體危害，展現你不只知道語法行為還理解它在實務中會造成的隱蔽 bug。

### 既然 finalize 被廢棄了，物件的資源清理應該怎麼做？

**核心答案**：應該用 `try-with-resources`（配合 `AutoCloseable`）做確定性的資源清理——在使用資源的地方明確地、及時地釋放它，而不是依賴 GC 的不確定時機。對於「物件被回收時作為最後保險的清理」，JDK 9 引入了 `Cleaner` 機制作為 `finalize` 的替代（更安全、不阻塞 GC），但主要的資源管理仍應靠 `try-with-resources` 的顯式關閉。

**詳細解析**：`finalize` 的根本問題是「依賴 GC 的時機做清理」——而 GC 何時運行完全不確定，可能等很久，導致資源（如檔案句柄、連線）長時間得不到釋放，甚至如果物件一直沒被回收，`finalize` 永遠不執行。正確的思路是「確定性清理」——誰使用資源，誰就負責在用完後立即釋放，這正是 `try-with-resources` 做的事（離開 try 區塊就保證關閉）。`Cleaner` 是 JDK 9 提供的、比 finalize 更安全的「兜底」機制——它在物件變得不可達時執行清理動作，但用獨立執行緒、不阻塞 GC、且不會導致物件復活，適合作為「萬一使用者忘記關閉資源時的最後保險」，但它仍然有時機不確定的問題，所以只是輔助，主力仍是 `try-with-resources` 的顯式關閉。

**面試回答方式**：回答「主要靠 `try-with-resources` 做確定性的顯式清理，`Cleaner` 作為 JDK 9 後替代 finalize 的兜底機制」，並解釋核心思想「不依賴 GC 的不確定時機、誰用誰及時釋放」。能區分「主力（try-with-resources）」與「兜底（Cleaner）」的角色，展現你對現代 Java 資源管理的完整認識。
