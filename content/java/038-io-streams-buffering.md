# 題目

`InputStream` 與 `Reader` 的分界是什麼？為什麼不加 `BufferedInputStream` 會慢那麼多？

## 核心答案

分界是位元組與字元的差別，也就是編碼。`InputStream`／`OutputStream` 處理**原始位元組**，不做任何解釋；`Reader`／`Writer` 處理**字元**，中間必須有一個字元集把位元組序列解碼成字元。橋接兩者的是 `InputStreamReader` 與 `OutputStreamWriter`——它們是唯一該指定編碼的地方，**而且一定要明確指定**，不然會用平台預設編碼，同一份程式在不同機器上讀出不同結果（JDK 18 起預設改為 UTF-8，但舊版與舊程式碼仍是問題來源）。

緩衝的必要性來自**系統呼叫的成本**。沒有緩衝時，`read()` 每讀一個位元組就是一次系統呼叫——使用者態切到核心態、回來，一次大約幾百奈秒到一微秒。讀一個 1 MB 的檔案就是一百萬次切換。`BufferedInputStream` 內部有一個預設 8 KB 的陣列，**一次系統呼叫填滿它**，之後的 8192 次 `read()` 都只是從陣列取值。系統呼叫次數從一百萬降到一百二十八，這就是那個數量級的差距。

## 詳細解析

這一組類別是裝飾者模式的教科書案例：`new BufferedReader(new InputStreamReader(new FileInputStream(f), UTF_8))` 這串巢狀不是為了折磨人，而是把三個正交的職責分開——資料來源（檔案）、編碼轉換（位元組到字元）、緩衝策略。任何一層都可以替換：來源換成 socket、編碼換成 Big5、緩衝換成不緩衝。**代價是 API 的入門門檻很高**，這正是 `Files.readString`、`Files.lines` 這些便利方法存在的理由——它們把最常見的組合包成一行。

**BufferedWriter 的關鍵是 flush 與 close**：寫入時資料先進緩衝，只有緩衝滿了或明確 `flush()` 才真的寫出去。程式如果沒有正常關閉流（或用 try-with-resources），最後一段資料會留在緩衝裡永遠寫不出去——這是「檔案內容少了最後幾行」這類 bug 的標準成因。`close()` 會先 flush 再關閉，所以 try-with-resources 同時解決了兩件事。

**編碼問題有三個典型症狀**。**亂碼**——寫入端與讀取端用了不同編碼。**字元被切半**——用位元組流按固定長度分塊處理多位元組編碼（UTF-8 的中文是 3 個位元組），塊的邊界剛好切在字元中間；這是 `Reader` 存在的理由之一，它會處理跨塊的字元邊界。**BOM**——UTF-8 檔案開頭的三個位元組不會被 `InputStreamReader` 自動去掉，會變成第一行開頭一個看不見的字元，讓「為什麼第一欄的比對總是失敗」變成一個難查的問題。

現代寫法應該優先用 NIO.2 的便利方法：`Files.readString(path)`、`Files.writeString`、`Files.lines(path, UTF_8)`、`Files.newBufferedReader`（已經幫你組好緩衝與 UTF-8 預設）。它們更短、預設更安全、也不容易漏掉編碼參數。只有在需要精細控制（自訂緩衝大小、串接特殊的解壓縮流、處理超大檔案的分塊）時才手動組裝裝飾鏈。知道什麼時候不用手寫這串巢狀，比背得出巢狀順序更重要。

## 面試回答方式

先給分界——**位元組 vs 字元，中間隔著編碼**，並指出 `InputStreamReader` 是唯一該指定編碼的地方而且一定要明確指定。緩衝的部分要給**具體機制與量級**：沒緩衝時每次 `read()` 是一次系統呼叫、幾百奈秒，1 MB 就是一百萬次；`BufferedInputStream` 用 8 KB 陣列把它降到一百多次。接著把這組類別定位成**裝飾者模式**——來源、編碼、緩衝三個正交職責分離，代價是入門門檻高，所以才有 `Files.readString` 這些便利方法。加分點給三個具體的坑：沒 close 導致最後一段資料留在緩衝、用位元組流分塊會把多位元組字元切半、**UTF-8 的 BOM 不會被自動去掉**。收在建議：現代寫法優先用 NIO.2 的便利方法。

## 講稿

分界就是位元組跟字元的差別，中間隔著編碼。位元組流處理原始位元組不做任何解釋，字元流處理字元，所以必須有一個字元集負責解碼。橋接兩者的那個類別是唯一該指定編碼的地方，而且一定要明確寫出來，不然會用平台預設，同一份程式在不同機器上讀出不同結果。

緩衝的必要性來自系統呼叫的成本。沒有緩衝的時候，每讀一個位元組就是一次系統呼叫，使用者態切到核心態再回來，一次大概幾百奈秒。讀一個一 MB 的檔案就是一百萬次切換。

加上緩衝之後，內部有一個預設八 KB 的陣列，一次系統呼叫填滿它，之後的八千多次讀取都只是從陣列取值。系統呼叫從一百萬次降到一百多次，這就是那個數量級的差距。

有一個很常見的坑要提。寫入的時候資料先進緩衝，沒有正常關閉流的話，最後一段資料會留在緩衝裡永遠寫不出去。檔案內容少了最後幾行，通常就是這個原因。

## 常見追問

### 緩衝區大小該設多少？

**核心答案**：**預設的 8 KB 幾乎總是夠好**，調它通常是最沒有收益的最佳化。原因是收益曲線很快就平了：系統呼叫次數與緩衝大小成反比，從 1 位元組到 8 KB 是四個數量級的改善，從 8 KB 到 64 KB 只再減少 87%的剩餘呼叫，而那部分已經不是瓶頸了。真正該調的時機是單次讀取的資料本來就遠大於 8 KB（例如串流大型檔案），此時設成 64 KB 或與底層區塊大小對齊可能有小幅收益。

**詳細解析**：更值得注意的是**大緩衝的反效果**。每個緩衝都是一個堆積上的陣列，開太大又開很多（例如每個連線一個 1 MB 緩衝）會直接吃掉堆積並增加 GC 壓力。而且大於 CPU 快取的緩衝會讓資料在填充後就被逐出快取，處理時又要從主記憶體載回來，區域性反而變差。實務上真正有效的最佳化通常在別的層次：**改用 `transferTo`／`FileChannel.transferTo` 走零拷貝**（資料不經過使用者態）、或者**改變存取模式**（順序讀取比隨機讀取快數十倍，因為預讀機制生效）。

**面試回答方式**：先給結論——8 KB 幾乎總是夠好，並用收益曲線解釋為什麼（前四個數量級拿走了幾乎全部收益）。接著給反效果：大緩衝吃堆積、超過 CPU 快取後區域性變差。最後把注意力導向真正有效的方向——零拷貝的 `transferTo` 與順序存取模式，這顯示你知道最佳化該用在哪一層。

### 為什麼建議一律明確指定 UTF-8？

**核心答案**：因為不指定時用的是平台預設編碼，它會隨作業系統、地區設定與 JDK 版本改變。同一份程式在開發者的 macOS（UTF-8）上正確、在伺服器的某個地區設定下讀出亂碼，而且這種錯誤**不會拋例外**——解碼失敗的位元組被替換成問號字元，資料靜默損壞。JDK 18 起（JEP 400）把預設改成 UTF-8，但舊版本、舊程式碼、以及 `System.out` 這類仍受主控台編碼影響的地方，問題依然存在。

**詳細解析**：更嚴重的是**損壞不可逆**。一旦用錯的編碼讀入並替換成問號，原本的位元組資訊就沒了，之後再怎麼轉換都救不回來。所以編碼錯誤的處理原則是**在最早的入口擋住**：明確指定編碼，並在需要嚴格性時用 `CharsetDecoder` 搭配 `CodingErrorAction.REPORT`，讓非法位元組**拋例外而不是靜默替換**。這在處理外部上傳的檔案時特別重要——寧可讓一批資料匯入失敗並回報，也不要匯入一批帶問號的髒資料進資料庫。

**面試回答方式**：核心是「平台預設會變，而且解碼失敗不拋例外、靜默替換成問號」。強調**損壞不可逆**這一點——資訊丟了就救不回來，所以要在最早的入口擋住。加分點是提出 `CodingErrorAction.REPORT` 讓非法位元組拋例外，並用「寧可整批匯入失敗也不要匯入髒資料」說明這個選擇的實務理由。

### System.out.println 為什麼在大量輸出時特別慢？

**核心答案**：因為 `System.out` 是一個 **autoflush 開啟的 `PrintStream`**——每次遇到換行就 flush 一次，也就是每一行都是一次系統呼叫。加上它內部有同步（多執行緒印出不會交錯），以及主控台本身的渲染成本，在迴圈裡印十萬行會比寫檔慢上一兩個數量級。

**詳細解析**：解法是**自己包一層緩衝**：`var out = new PrintWriter(new BufferedWriter(new OutputStreamWriter(System.out, UTF_8)))`，最後記得 `flush()`。競賽程式與批次工具常這樣做，差距很明顯。但更重要的實務結論是生產程式不該用 `System.out` 輸出——該用日誌框架，它提供了級別過濾（不需要的訊息根本不會產生字串）、非同步 appender（寫入不阻塞業務執行緒）、以及結構化輸出。很多「日誌讓服務變慢」的案例，根本原因是用了同步輸出加上在熱路徑無條件拼接字串，而不是日誌本身貴。

**面試回答方式**：先給機制——autoflush 讓每一行都是一次系統呼叫，加上內部同步與主控台渲染。給出可立即使用的解法（自己包 `BufferedWriter` 並記得 flush）。然後把結論提升到實務層面：生產程式該用日誌框架，並指出「日誌拖慢服務」的常見真因是同步輸出加熱路徑無條件拼字串，而非日誌本身。
