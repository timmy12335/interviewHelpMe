# 題目

`java.io.File` 有哪些問題？NIO.2 的 `Path` 與 `Files` 改善了什麼？

## 核心答案

`File` 的問題可以歸成三類。**錯誤資訊丟失**——`delete()`、`mkdir()`、`renameTo()` 全都回傳 `boolean`，失敗時你只知道「失敗了」，不知道是權限不足、檔案不存在、還是跨檔案系統移動。**功能缺口**——沒有符號連結的處理、沒有檔案屬性（擁有者、權限、建立時間）的存取、沒有原子性的移動、目錄遍歷會把整個清單一次載入記憶體。**API 語意混亂**——`File` 同時代表路徑與檔案，`exists()` 為 false 時它到底是什麼並不清楚。

NIO.2（JDK 7）把它拆成兩個概念：**`Path` 只代表路徑**（純粹的語法物件，不需要對應真實檔案），**`Files` 提供所有操作**（靜態方法，失敗時拋帶有具體資訊的 `IOException` 子類別，例如 `NoSuchFileException`、`AccessDeniedException`）。這個拆分同時解決了語意混亂與錯誤資訊丟失。

## 詳細解析

**具體的例外型別讓錯誤處理變得可能**：`Files.delete(path)` 失敗時拋 `NoSuchFileException` 或 `DirectoryNotEmptyException`，呼叫方可以分別處理；`File.delete()` 只給一個 false，實務上大家就寫 `if (!f.delete()) log.warn("delete failed")` 然後永遠查不出原因。**如果不在意「不存在」這個情況，`Files.deleteIfExists` 提供了明確的語意**，比先 `exists()` 再 `delete()` 好——後者有 TOCTOU（檢查與使用之間狀態改變）的競爭問題。

**遍歷是差異最大的地方**：`File.listFiles()` 回傳一個陣列，**必須先把整個目錄讀完**——目錄有幾十萬個檔案時會直接吃掉大量記憶體。`Files.list(path)` 回傳一個惰性的 `Stream<Path>`，`Files.walk` 遞迴遍歷也是惰性的，可以配合 `limit`、`filter` 提早結束。**但這兩個方法回傳的串流持有作業系統資源，必須用 try-with-resources 關閉**，這是最常被漏掉的一點——漏了會累積開啟的目錄描述符，最終拋出「too many open files」。需要更多控制（例如處理遍歷中的錯誤、控制遞迴深度）時用 `Files.walkFileTree` 搭配 `FileVisitor`。

**原子性與跨檔案系統**：`Files.move` 可以指定 `StandardCopyOption.ATOMIC_MOVE` 要求原子性（同一個檔案系統內通常由 `rename` 系統呼叫保證），跨檔案系統時它會退化成複製加刪除且無法保證原子。`File.renameTo` 的行為則**完全依平台而定**，文件明說它「許多方面都與平台相關」，是最不該用的方法之一。**「先寫暫存檔再原子性改名」是安全寫入檔案的標準做法**，可以避免程式在寫到一半崩潰時留下半個檔案。

**判斷什麼時候還會遇到 File**：舊 API（`FileInputStream` 的建構子、許多第三方函式庫）仍然吃 `File`，所以 `Path.toFile()` 與 `File.toPath()` 這兩個轉換方法會一直用到。**新程式碼一律用 `Path`，只在邊界上轉換**，是務實的做法。

## 面試回答方式

把 `File` 的問題歸成**三類**（錯誤資訊丟失、功能缺口、語意混亂）而不是散列，然後給 NIO.2 的核心改變：**`Path` 只是路徑、`Files` 提供操作、失敗拋具體例外**。舉一個對照最有力：`Files.delete` 拋 `NoSuchFileException` 或 `DirectoryNotEmptyException` 可以分別處理，`File.delete` 只給 false，所以大家寫個 warn 就永遠查不出原因。接著講遍歷的差別——`listFiles` 一次載入整個目錄，`Files.list`／`walk` 是惰性串流，**但必須 try-with-resources 關閉，否則會累積目錄描述符**。加分點是**先寫暫存檔再原子性改名**這個安全寫入模式，以及 `File.renameTo` 行為依平台而定所以不該用。

## 講稿

File 的問題我會歸成三類。第一是錯誤資訊丟失，刪除、建目錄、改名全都只回傳布林值，失敗的時候你不知道是權限不足還是檔案不存在。第二是功能缺口，沒有符號連結處理、沒有檔案屬性存取、沒有原子性移動。第三是語意混亂，它同時代表路徑跟檔案。

NIO.2 把它拆成兩個概念。Path 只代表路徑，是純粹的語法物件。Files 提供所有操作，失敗的時候拋出帶有具體資訊的例外，像是檔案不存在或目錄不為空，呼叫方可以分別處理。

遍歷是差異最大的地方。舊的方法回傳陣列，必須先把整個目錄讀完，目錄有幾十萬個檔案就直接吃掉記憶體。新的方法回傳惰性串流，可以配合過濾跟限制筆數提早結束。

但有一個很容易漏的地方，那些串流持有作業系統資源，一定要用 try-with-resources 關閉。漏掉會累積開啟的描述符，最後拋出檔案開太多的錯誤。

## 常見追問

### 為什麼 Files.list 回傳的串流一定要關閉？

**核心答案**：因為它**持有一個開啟的目錄控制代碼**（directory stream），惰性地一邊走一邊回傳項目。串流用完不關，那個控制代碼就不會釋放。作業系統對每個行程的開啟檔案數有上限（Linux 上常見是 1024 或幾萬），累積到上限後**任何開檔、建立 socket 的操作都會失敗**，錯誤訊息是「too many open files」，而且通常爆在跟遍歷完全無關的地方。

**詳細解析**：這是「**惰性 API 讓資源生命週期變得不明顯**」的典型例子。一般的串流（`list.stream()`）不持有資源，所以大家習慣不關；但 `Files.list`、`Files.lines`、`Files.walk`、`Files.find` 都持有。判斷方式是看 API 文件有沒有說「必須在 try-with-resources 中使用」，或看回傳型別是不是繼承 `AutoCloseable`——`Stream` 本身就是 `AutoCloseable`，只是大多數串流的 `close` 什麼都不做。**排查這類洩漏可以用 `lsof -p <pid>` 看開啟的描述符**，如果看到大量同一個目錄的項目，答案就很明顯了。

**面試回答方式**：先給機制（持有目錄控制代碼、惰性遍歷）與後果（描述符耗盡，錯誤爆在無關的地方）。把它歸納成一個一般教訓：**惰性 API 讓資源生命週期變得不明顯**，並給出判斷方式——`Stream` 是 `AutoCloseable`，只是多數串流的 close 是空操作。加分點是給出排查手段 `lsof`。

### 怎麼安全地寫入一個檔案，避免寫到一半崩潰？

**核心答案**：**寫暫存檔再原子性改名**。先把內容完整寫進同一個目錄下的暫存檔（同目錄是為了確保在同一個檔案系統上），`flush` 並在需要強一致時 `force`／`fsync`，然後用 `Files.move(tmp, target, ATOMIC_MOVE, REPLACE_EXISTING)`。這樣讀取方在任何時刻看到的**要嘛是舊版完整檔案、要嘛是新版完整檔案**，永遠不會看到半個。

**詳細解析**：有兩個細節常被漏掉。**第一，暫存檔必須與目標同目錄**——跨檔案系統的 move 會退化成複製加刪除，失去原子性。**第二，只 flush 不 fsync 的話資料可能還在作業系統的 page cache 裡**，機器斷電仍會丟；要真正持久化需要對檔案 `force(true)`，嚴格的話連目錄項也要 sync（因為改名這個目錄操作本身也可能還沒落盤）。這個模式在資料庫、設定檔管理、快取檔案上到處可見，**它本質上是把「多步驟的寫入」壓縮成「一步原子的替換」**——同樣的思路也出現在藍綠部署與不可變基礎設施。

**面試回答方式**：給出完整步驟（同目錄暫存檔、寫完 flush／force、`ATOMIC_MOVE` 加 `REPLACE_EXISTING`），並說明它保證讀取方只會看到完整的舊版或新版。補兩個容易漏的細節：暫存檔必須同目錄、只 flush 不 fsync 斷電仍會丟。收在抽象層次——**把多步驟寫入壓縮成一步原子替換**，並指出藍綠部署是同一個思路。

### WatchService 可以用來監控檔案變化嗎？

**核心答案**：可以，它包裝了作業系統的檔案系統事件機制（Linux 的 inotify、macOS 的 FSEvents／kqueue、Windows 的 ReadDirectoryChangesW），比輪詢目錄有效率得多。但它有幾個實務限制：**macOS 的實作是輪詢的**（JDK 長期沒有用 FSEvents，延遲可達數秒）、**事件可能溢位**（大量變更時會收到 `OVERFLOW`，只能重新掃描）、**不遞迴**（要監控子目錄必須自己為每個子目錄註冊）。

**詳細解析**：更根本的問題是**檔案系統事件天生不可靠，不該當成資料流的唯一來源**。一個檔案可能在你收到事件之前又被刪除，一次寫入可能觸發多個事件（建立、多次修改、屬性變更），編輯器的「安全寫入」（寫暫存檔再改名）會表現成刪除加建立而不是修改。所以正確的用法是**把事件當成「該去檢查了」的提示，而不是「發生了什麼」的權威描述**——收到事件後重新讀取實際狀態。需要跨平台可靠性時，成熟的做法是用專門的函式庫（例如 commons-io 的 monitor 或 directory-watcher），或者退回到「低頻輪詢加上事件加速」的混合模式。

**面試回答方式**：先肯定它的定位（包裝 OS 事件、比輪詢有效率），再誠實給出三個限制（macOS 實作是輪詢、事件會溢位、不遞迴）。真正的加分點是提升到原則層次：**檔案系統事件不可靠，該當成「去檢查」的提示而不是「發生了什麼」的權威描述**，並舉編輯器的安全寫入會表現成刪除加建立作為例子。
