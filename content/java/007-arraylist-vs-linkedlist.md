# 題目

`ArrayList` 和 `LinkedList` 有什麼差異？各自適合什麼場景？

## 核心答案

`ArrayList` 底層是動態陣列，支援 O(1) 的隨機存取（依索引取值），但在中間插入/刪除元素需要搬移後續元素（O(n)），且容量不足時要擴容複製；`LinkedList` 底層是雙向鏈結串列，插入/刪除只需調整指標（找到位置後 O(1)），但隨機存取需要從頭或尾遍歷（O(n)）。實務上絕大多數場景 `ArrayList` 都更合適，`LinkedList` 較少用。

## 詳細解析

**ArrayList（動態陣列）**：

- 隨機存取快：依索引取值直接計算記憶體位址，O(1)。
- 尾端新增快：攤銷後 O(1)（偶爾擴容時 O(n)）。
- 中間插入/刪除慢：需要把插入點之後的所有元素往後/往前搬移，O(n)。
- 記憶體較緊湊：連續記憶體儲存，快取局部性好。

**LinkedList（雙向鏈結串列）**：

- 隨機存取慢：沒有索引直達，要從頭或尾一個一個走，O(n)。
- 插入/刪除快（前提是已經定位到位置）：只需改指標，O(1)；但「定位到位置」本身通常需要 O(n) 遍歷。
- 記憶體開銷大：每個節點除了資料還要存前後指標，且節點分散在記憶體各處，快取局部性差。

**為什麼實務上多用 ArrayList**：雖然理論上 `LinkedList` 的插入刪除是 O(1)，但那是「已經拿到節點引用」的前提下；實際使用中往往要先遍歷找到位置（O(n)），加上鏈結串列的快取不友善，實測效能常常比 `ArrayList` 還差。而 `ArrayList` 的隨機存取優勢、緊湊的記憶體、良好的快取局部性，在絕大多數場景下都勝出。`LinkedList` 唯一稍有優勢的場景是「頻繁在頭部插入/刪除」（可當作 Deque 用），但這種需求通常用 `ArrayDeque` 更好。

## 面試回答方式

用「底層資料結構決定操作複雜度」這個框架回答最清楚——`ArrayList` 是陣列所以隨機存取快、中間增刪慢；`LinkedList` 是鏈結串列所以增刪改指標快、但隨機存取慢。回答的加分點在最後的結論：主動指出「實務上絕大多數場景 `ArrayList` 更好，因為 `LinkedList` 的 O(1) 增刪要先 O(n) 定位、且快取不友善」，這個「理論 vs 實務」的洞察比單純背複雜度表更能展現你有實際判斷力。

## 常見追問

### ArrayList 的擴容機制是怎樣的？

**核心答案**：`ArrayList` 預設初始容量為 10（第一次新增元素時才真正分配），當元素數量超過目前容量時觸發擴容，擴容策略是「新容量 = 舊容量 × 1.5」（舊容量加上舊容量右移一位），建立一個更大的新陣列並把舊元素複製過去。因此如果已知會存大量元素，用建構子指定初始容量可以避免多次擴容複製。

**詳細解析**：`ArrayList` 底層的 `Object[]` 陣列容量固定，裝滿後必須換一個更大的陣列並複製。1.5 倍的擴容係數是「空間浪費」與「擴容頻率」的折衷——係數太大（如 2 倍）省了擴容次數但可能浪費較多空間，太小則擴容太頻繁。每次擴容的 `Arrays.copyOf` 是 O(n) 操作，所以雖然單次尾端新增攤銷後是 O(1)，但存入大量元素若從預設容量 10 開始會經歷多次擴容複製。實務上若預估要存 1000 個元素，直接 `new ArrayList<>(1000)` 一次分配到位，能避免這些中間的擴容成本。

**面試回答方式**：講出「預設 10、擴容 1.5 倍、擴容要複製」這些具體數字，並延伸「已知大小時指定初始容量避免多次擴容」的實務優化，展現你對這個最常用集合類的底層有實際掌握。

### 為什麼說 LinkedList 的 O(1) 插入在實務中往往名不副實？

**核心答案**：因為 `LinkedList` 真正 O(1) 的只有「已經持有目標節點引用時，改指標插入/刪除」這個動作；但實際使用中，你通常是用「索引」或「值」來指定插入/刪除位置（例如 `list.add(index, e)` 或 `list.remove(value)`），這時 `LinkedList` 必須先從頭或尾遍歷到那個位置（O(n)），所以整體操作其實是 O(n)，並沒有比 `ArrayList` 快，反而因為鏈結串列快取不友善而常常更慢。

**詳細解析**：這是一個「理論複雜度」與「實際使用模式」脫節的經典例子。教科書說「鏈結串列插入 O(1)」的前提是「你手上已經有那個位置的節點引用」，但這個前提在多數 API 使用場景中不成立——`list.add(5, element)` 要先走到第 5 個節點。加上現代 CPU 對連續記憶體（陣列）有強大的快取預取優化，而鏈結串列的節點散落在記憶體各處、每次跳轉都可能造成快取未命中，實測下來 `ArrayList` 即使有元素搬移，總體效能也常常勝過 `LinkedList`。這也是為什麼許多資深工程師和《Effective Java》都建議「預設用 `ArrayList`，除非有明確理由才考慮 `LinkedList`」。

**面試回答方式**：點出關鍵——「O(1) 的前提是已持有節點引用，但實際用索引/值定位時要先 O(n) 遍歷」，再補上「鏈結串列快取不友善所以實測常更慢」，這種能拆穿「教科書複雜度」與「真實效能」落差的回答，是展現實務深度的好機會。

### 如果需要頻繁在頭部插入/刪除，該用什麼？

**核心答案**：優先用 `ArrayDeque`（陣列實作的雙端佇列），而不是 `LinkedList`。`ArrayDeque` 用環形陣列實作，在頭尾兩端插入/刪除都是攤銷 O(1)，且因為是連續記憶體、快取局部性好，實測效能通常明顯優於 `LinkedList`，記憶體開銷也更小（不需要每個節點存前後指標）。

**詳細解析**：很多人一看到「頻繁頭部操作」就直覺選 `LinkedList`，但 `ArrayDeque` 在這個場景通常是更好的選擇。它底層是一個可以在兩端增長的環形陣列，透過頭尾兩個指標的移動實現兩端的高效增刪，避免了 `LinkedList` 那種節點分散、指標開銷大、快取不友善的問題。Java 官方文件也明確建議：作為堆疊（Stack）用時 `ArrayDeque` 優於 `Stack`，作為佇列（Queue）用時 `ArrayDeque` 優於 `LinkedList`。`LinkedList` 真正無可替代的場景其實非常少。

**面試回答方式**：直接推薦 `ArrayDeque` 而非 `LinkedList`，並說明原因（環形陣列、兩端 O(1)、快取友善、記憶體省），這種「打破 LinkedList 是雙端操作首選的直覺」的回答，能展現你對集合框架的選型有超越教科書的實務認識。
