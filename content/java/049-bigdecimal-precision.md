# 題目

為什麼 `0.1 + 0.2 != 0.3`？金額計算為什麼一定要用 `BigDecimal`，又有哪些容易踩的坑？

## 核心答案

因為 `double` 用的是 **IEEE 754 二進位浮點數**，而 0.1、0.2、0.3 在二進位下都是無限循環小數，只能取近似值儲存。兩個近似值相加的結果與 0.3 的近似值不同，於是比較為 false。**這不是 Java 的 bug，任何用 IEEE 754 的語言都一樣**。

金額必須用 `BigDecimal` 是因為它用**十進位的「未縮放值加標度」**表示（`unscaledValue × 10^-scale`），可以精確表示任何有限位數的十進位小數，而且能明確控制小數位數與捨入方式。

但它有三個非常容易踩的坑。**第一，一定要用字串建構子**——`new BigDecimal(0.1)` 會把 double 的誤差原封不動帶進來（結果是 0.1000000000000000055511151231257827…），必須寫 `new BigDecimal("0.1")` 或 `BigDecimal.valueOf(0.1)`。**第二，`equals` 會比較標度**——`new BigDecimal("1.0").equals(new BigDecimal("1.00"))` 是 false，比較數值要用 `compareTo() == 0`。**第三，除法可能拋例外**——除不盡時 `divide` 不指定標度與捨入模式會拋 `ArithmeticException`。

## 詳細解析

**第二個坑會延伸成一個更嚴重的問題**：`BigDecimal` 的 `equals` 與 `hashCode` 都包含標度，所以把它放進 `HashSet` 或當作 `HashMap` 的鍵時，1.0 與 1.00 是**兩個不同的鍵**。而 `TreeMap` 用 `compareTo`，兩者又是**同一個鍵**——同一組資料放進兩種容器會得到不同的結果。這正是「`equals` 與 `compareTo` 不一致」在 JDK 裡最有名的例子，文件明確警告過。實務上的做法是**在存入集合前統一標度**（`setScale(2, RoundingMode.HALF_UP)`）。

**捨入模式要明確選擇而不是用預設**：`RoundingMode.HALF_UP`（四捨五入）是直覺的選擇，但**金融領域常用 `HALF_EVEN`（銀行家捨入）**——遇到正好一半時捨到最近的偶數，這樣大量計算後的累積偏差趨近於零，而 `HALF_UP` 會系統性地偏大。選哪一個應該由業務規則決定並寫進文件，不是憑感覺。

**效能與可讀性的代價要誠實面對**：`BigDecimal` 的每次運算都會建立新物件（它是不可變的），比 `long` 的整數運算慢一到兩個數量級，而且 `a.add(b).multiply(c)` 遠不如 `a + b * c` 好讀。**所以另一條常見的路是「用最小單位的整數」**——金額以「分」為單位存成 `long`，計算全部用整數，只在顯示時除以 100。這在單一幣別、精度固定、且不需要複雜比例計算（利率、分攤）的系統裡很好用，效能也好得多。

**選擇的判準是「有沒有除法與比例計算」**：只有加減與整數倍的場景（一般電商訂單）用 `long` 分即可；有利率、匯率、分攤、稅率這類會產生除不盡結果的計算，就該用 `BigDecimal` 並明確定義每一步的捨入規則。**分攤問題還有一個經典陷阱**：把 100 元分給 3 個人，四捨五入後三份加起來是 99.99 或 100.02，必須有明確的「餘數給誰」規則，這是業務決策而不是技術細節。

## 面試回答方式

先解釋成因——**IEEE 754 二進位無法精確表示 0.1 這類十進位小數**，並強調這與語言無關。接著給 `BigDecimal` 的表示方式（未縮放值加標度）說明它為什麼能精確。然後把重點放在**三個實際會踩的坑**：字串建構子（`new BigDecimal(0.1)` 會把誤差帶進來）、`equals` 比較標度（1.0 不等於 1.00，要用 `compareTo`）、除法除不盡會拋例外。加分點有三個：`equals` 與 `compareTo` 不一致導致**同一組資料在 HashSet 與 TreeMap 有不同結果**；**金融常用 HALF_EVEN 而非 HALF_UP**，因為後者會系統性偏大；以及提出另一條路——**用最小單位的 long**，並給判準：只有加減用 long，有除法與比例計算才用 `BigDecimal`。

## 講稿

因為 double 用的是二進位浮點數，而零點一、零點二在二進位下都是無限循環小數，只能存近似值。兩個近似值相加的結果跟零點三的近似值不同，所以比較是 false。這不是 Java 的問題，任何用同一套標準的語言都一樣。

BigDecimal 用十進位的未縮放值加標度來表示，可以精確表示任何有限位數的十進位小數，而且能明確控制小數位數跟捨入方式。

但它有三個很容易踩的坑。第一，一定要用字串建構子，直接傳 double 會把誤差原封不動帶進來。第二，equals 會比較標度，一點零跟一點零零是不相等的，比較數值要用 compareTo。第三，除不盡的時候不指定捨入模式會拋例外。

第二個坑還會延伸。因為 equals 包含標度而 compareTo 不包含，同一組資料放進 HashSet 跟 TreeMap 會得到不同的結果。所以我的習慣是存進集合前先統一標度。

最後補一個選型。只有加減的場景，我會用最小單位的整數，把金額存成分。有利率、匯率、分攤這種會除不盡的計算，才用 BigDecimal 並明確定義每一步的捨入規則。

## 常見追問

### 為什麼金融領域常用 HALF_EVEN 而不是 HALF_UP？

**核心答案**：因為 `HALF_UP`（遇到正好一半就進位）在大量計算上會產生**系統性的向上偏差**。0.5、1.5、2.5 全部進位，長期累積下來總和會偏大。`HALF_EVEN`（銀行家捨入）在正好一半時捨到**最近的偶數**——0.5 進到 0、1.5 進到 2、2.5 進到 2——進位與捨去的機會各半，**累積偏差趨近於零**。在處理數百萬筆交易的系統裡，這個差別會累積成可觀的金額。

**詳細解析**：這也是 IEEE 754 的**預設捨入模式**（round half to even），所以 `double` 的運算本來就是這樣捨入的。要注意的是**捨入規則必須全系統一致**——如果對帳的兩端用了不同的捨入模式，差額會出現在無法解釋的地方，而且金額很小、難以追查。實務上應該把捨入規則寫進系統規格並在程式碼裡集中一處（例如一個 `MoneyMath` 工具類別），不要讓每個開發者各自呼叫 `setScale` 時選自己習慣的模式。**捨入是業務規則，不是技術細節**，這是這題最重要的判斷。

**面試回答方式**：核心是「`HALF_UP` 有系統性向上偏差、`HALF_EVEN` 讓偏差趨近於零」，並指出後者也是 IEEE 754 的預設。真正的加分點是把它提升成工程問題：**捨入規則必須全系統一致**，否則對帳差額會出現在難以追查的地方；所以規則應該集中在一處實作，而且它是業務規則不是技術細節。

### float 與 double 在什麼情況下仍然是對的選擇？

**核心答案**：當**輸入本身就是近似值、且誤差在可接受範圍內**時——物理量測、圖形座標、機器學習的權重、統計指標。這些場景的資料本來就有量測誤差，浮點數的相對誤差（`double` 大約 15 到 17 位有效數字）遠小於資料本身的不確定性。而且浮點運算有硬體支援，比 `BigDecimal` 快一到兩個數量級。**不該用的是「必須精確且會被人核對」的數字**——金額、計數、序號。

**詳細解析**：用浮點數時要遵守幾條紀律。**不要用 `==` 比較**，改用「差的絕對值小於容差」，而容差要依數值量級調整（相對誤差而非絕對誤差）。**避免大數與小數相加**——`1e16 + 1` 的結果仍是 `1e16`，小的那個被完全吃掉；累加大量數字時應該用 Kahan 補償求和或先排序。**注意 `NaN` 的特殊性**——它不等於自己，所以 `NaN` 出現在排序或集合裡會產生怪異行為，`Double.compare` 有特別處理但 `<` 運算子沒有。這些不是冷知識，**數值累加誤差在報表與監控指標上是真的會出事的**。

**面試回答方式**：給判準——**輸入本身是近似值就用浮點數，必須精確且被人核對就用精確型別**，並舉出各自的典型場景。然後給三條使用紀律：不要用 `==` 而用相對容差、避免大數加小數（`1e16 + 1` 等於 `1e16`）、注意 `NaN` 不等於自己。強調這些在報表與監控指標的累加上是真的會出事的，不是冷知識。

### 分攤金額時的餘數該怎麼處理？

**核心答案**：這是**業務決策而非技術問題**，但技術上必須確保**分攤後的總和等於原始金額**。常見的規則有三種：**餘數給第一個**（或最後一個）、**餘數依序分配**（每份多一分，直到餘數用完）、**依權重最大的優先**。無論選哪一種，實作上都應該**先算出每份的基礎金額，再把餘數明確分配掉**，而不是各自四捨五入後祈禱總和剛好。

**詳細解析**：具體做法是：用整數運算（以最小單位計）算 `base = total / n` 與 `remainder = total % n`，然後把 remainder 分給前 remainder 份。這樣總和必然精確等於 total，而且結果是確定的、可重現的、可對帳的。**「各自四捨五入」的做法在測試裡通常看不出問題**——用 90 分給 3 個人剛好整除，用 100 分給 3 個人就差了。這是典型的「常見輸入正確、邊界輸入錯誤」，所以測試必須刻意涵蓋除不盡的案例。另外**退款與部分退款會讓問題更複雜**：如果原始分攤有餘數分配，退款時必須依同樣的規則反向計算，否則會出現一分錢的殘留，而金額系統裡任何無法解釋的一分錢都會變成對帳工單。

**面試回答方式**：先定位成**業務決策**，但給出技術上的硬性要求——分攤後總和必須等於原始金額。給出具體做法（整數運算算基礎值與餘數，再明確分配餘數），並指出「各自四捨五入」在整除的測試資料上看不出問題。加分點是提出退款要依同樣規則反向計算，否則會留下一分錢殘留而變成對帳工單——這顯示你想過完整的生命週期。
