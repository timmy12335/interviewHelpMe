# 題目

文字區塊（Text Block）解決了什麼問題？JDK 11 之後 `String` 新增的方法有哪些值得知道？

## 核心答案

文字區塊（JDK 15 正式）用三個雙引號包住多行字串，解決三個具體問題：**跳脫地獄**（嵌入 JSON、SQL、HTML 時不必把每個引號寫成 `\"`）、**手動換行符**（不必寫 `\n` 與字串串接）、**縮排管理**（編譯器會自動移除共同的前導空白，讓字串在原始碼裡可以正常縮排而不影響內容）。

縮排的規則值得記清楚：編譯器取所有非空行與結尾定界符所在行的最小前導空白數，把它從每一行移除。這表示結尾的 `"""` 放在哪一欄會影響結果——放在內容的縮排位置就完全移除縮排，放在最左邊則保留全部縮排。需要精確控制時可以用 `\` 在行尾表示「不換行」，用 `\s` 表示「這裡有一個要保留的空白」。

JDK 11 之後值得知道的方法：`isBlank`（比 `trim().isEmpty()` 更正確，它認得全形空白與其他 Unicode 空白）、`strip`／`stripLeading`／`stripTrailing`（Unicode 感知版的 `trim`）、`lines()`（回傳 `Stream<String>`，不必自己 split）、`repeat(n)`、`formatted(...)`（`String.format` 的實例方法版，接在文字區塊後面很順）。

## 詳細解析

**trim 與 strip 的差別是一個真實的坑**：`trim()` 移除的是「碼點小於等於 U+0020」的字元，這是 1995 年的定義，它不認得全形空白（U+3000）、不斷行空白（U+00A0）等 Unicode 空白。處理使用者輸入時（尤其是中日韓輸入法或從網頁複製貼上的內容）常常出現「看起來有 trim 但還是有空白」的問題，換成 `strip()` 就對了。**新程式碼沒有理由再用 `trim`**。

**文字區塊不是「原始字串」**：它仍然處理跳脫序列，`\n`、`\t`、`\\` 都有效。這與某些語言的 raw string 不同，寫正規表達式時仍然要寫 `\\d`。另外它**沒有插值**——Java 至今沒有字串插值語法（字串模板曾以預覽功能出現後被撤回重新設計），所以要嵌入變數仍然得用 `formatted()` 或串接。

它最大的實務價值在可讀性審查：嵌在程式碼裡的 SQL 或 JSON，用傳統串接寫法時**很難在 code review 中看出是否正確**——引號、空格、換行全混在跳脫符號裡。文字區塊讓它們以原本的樣子呈現，錯誤一眼可見。但要注意**這不改變 SQL 注入的風險**：文字區塊裡用字串串接拼參數，跟以前一樣危險，仍然必須用參數化查詢。

行尾空白會被移除，這偶爾會咬人：文字區塊會**自動去掉每一行結尾的空白**（為了避免看不見的字元造成差異）。如果內容真的需要行尾空白（例如某些固定寬度格式），必須用 `\s` 明確標記。同樣地，**它一律使用 `\n` 作為換行符**，不管原始檔案是什麼行尾格式——這其實是好事，讓行為與平台無關。

## 面試回答方式

先給文字區塊解決的**三個具體問題**（跳脫地獄、手動換行、縮排管理），並把縮排規則說清楚——編譯器取所有非空行與結尾定界符行的最小前導空白後移除，所以結尾的三引號放在哪一欄會影響結果。這個細節能顯示是真的用過。接著給幾個值得知道的方法，重點放在 **`strip` 與 `trim` 的差別**：`trim` 是 1995 年的定義、不認得全形空白，處理使用者輸入時會出現「trim 過還是有空白」，所以新程式碼該一律用 `strip`。加分點有兩個：文字區塊**仍然處理跳脫序列**，不是 raw string，寫正則還是要雙反斜線；以及它**不改變 SQL 注入風險**，裡面串接參數一樣危險。

## 講稿

文字區塊解決三個具體問題。第一是跳脫地獄，嵌入 JSON 或 SQL 的時候不用把每個引號寫成反斜線引號。第二是不必手動寫換行符跟串接。第三是縮排管理，編譯器會自動移除共同的前導空白。

縮排規則有一個細節值得記。編譯器取所有非空行跟結尾定界符那一行的最小前導空白，把它從每一行移除。所以結尾的三個引號放在哪一欄，會影響最後的結果。

JDK 11 之後有幾個方法我覺得該知道。isBlank 比先 trim 再判斷是否為空更正確。strip 是 Unicode 感知的版本。還有 lines 直接回傳串流。

strip 跟 trim 的差別是一個真實的坑。trim 移除的是碼點小於等於空白字元的東西，這是很早以前的定義，它不認得全形空白。處理使用者輸入的時候常常出現 trim 過還是有空白的狀況。所以新的程式碼我一律用 strip。

最後要提醒一件事，文字區塊不改變 SQL 注入的風險。在裡面用串接拼參數，跟以前一樣危險。

## 常見追問

### 文字區塊會影響字串常數池的行為嗎？

**核心答案**：不會有特殊待遇。文字區塊在編譯期就被展開成一個普通的字串常數，所以它跟直接寫在原始碼裡的字面值完全一樣——會進入常數池、相同內容的兩個文字區塊會是同一個實例、可以用 `==` 比較（但不該這樣做）。位元組碼層面看不出它曾經是文字區塊。

**詳細解析**：這帶來一個實務上的推論：文字區塊裡的內容全部是編譯期常數，所以會被寫進 class 檔並常駐在常數池。放入很大的內容（例如一整份 HTML 範本）會讓 class 檔膨脹並佔用 metaspace 與字串池，而且無法在不重新編譯的情況下修改。大型範本應該放在資源檔裡用 `Files.readString` 或 `getResourceAsStream` 載入，文字區塊適合的是十幾行以內、與程式邏輯緊密相關的內容（一段 SQL、一個測試用的 JSON、一段錯誤訊息範本）。

**面試回答方式**：先給明確答案——編譯期展開成普通字串常數，位元組碼看不出差別。然後給有價值的推論：內容常駐常數池、改動要重新編譯，所以大型範本該放資源檔，文字區塊適合十幾行以內、與程式邏輯緊密相關的內容。這比只回答「沒有影響」有用得多。

### 為什麼 Java 到現在還沒有字串插值？

**核心答案**：因為 Java 想解決的不只是便利性，而是**安全性**。單純的插值（像 `"Hello ${name}"`）讓拼接變得太容易，而拼接正是 SQL 注入、XSS、命令注入的根源。Java 的字串模板（String Templates）設計刻意要求**指定一個處理器**（例如 `STR."..."` 或自訂的 `SQL."..."`），讓模板可以在組合前**檢查與轉義**每個嵌入值。這個提案在 JDK 21、22 以預覽功能出現後被撤回重新設計，因為 API 形狀還沒定案。

**詳細解析**：這反映了 Java 一貫的取捨——寧可晚一點、也要讓預設行為是安全的。同樣的思路出現在檢查例外（強迫處理錯誤）、泛型的型別檢查、以及模組系統的強封裝。代價是使用者要多等很多年，期間只能用 `String.format`、`formatted` 或串接。實務上的建議是：在等到語言支援之前，把「拼接不安全的字串」這件事交給專門的 API——SQL 用 `PreparedStatement`、HTML 用範本引擎的自動轉義、命令列用 `ProcessBuilder` 的參數陣列而不是 shell 字串。

**面試回答方式**：把答案定位在**安全性而非便利性**：Java 要的是能在組合前檢查與轉義的模板處理器，而不是單純的插值。誠實說明它預覽後被撤回重新設計。然後給實務結論——在語言支援到位之前，把不安全的拼接交給專門的 API（`PreparedStatement`、範本引擎、`ProcessBuilder`），這比等語言功能實際得多。

### String.format 與 formatted 有什麼差別？效能如何？

**核心答案**：功能相同，`formatted` 只是實例方法版本（JDK 15），讓 `"""...""".formatted(a, b)` 讀起來比 `String.format("""...""", a, b)` 順。**兩者的效能都不好**——格式字串每次呼叫都要重新解析，內部還會建立 `Formatter`、`StringBuilder` 與正規表達式相關的物件，比直接串接慢一個數量級以上。

**詳細解析**：所以在**熱路徑與日誌**上要特別注意。日誌框架的參數化寫法（`log.debug("user {} did {}", id, action)`）之所以重要，正是因為它在級別被過濾掉時完全不做格式化；用 `String.format` 或串接先算好再傳進去，就算這條日誌不會輸出，格式化成本也已經付了。對於真正的熱路徑，直接用 `StringBuilder` 或 `+`（編譯後走 `StringConcatFactory`，JDK 9 之後已經相當快）比 `format` 好得多。`format` 的價值在可讀性與國際化（`Locale` 敏感的數字與日期格式），不在速度——選它應該是因為需要那些能力，而不是順手。

**面試回答方式**：先說明兩者功能相同、只是實例方法版本更順。重點放在效能：**格式字串每次都要重新解析**，比串接慢一個數量級。然後給最有實務價值的推論——日誌一定要用參數化寫法，因為級別被過濾時完全不做格式化。收在定位：`format` 的價值在可讀性與國際化，不在速度。
