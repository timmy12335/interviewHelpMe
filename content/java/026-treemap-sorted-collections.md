# 題目

`TreeMap` 與 `HashMap` 該怎麼選？紅黑樹為什麼是有序 Map 的預設選擇？

## 核心答案

差別不在「哪個比較快」，而在**提供什麼能力**。`HashMap` 用雜湊，單點操作平均 O(1)，但**沒有順序**——不能問「大於 x 的最小鍵是什麼」，也不能取區間。`TreeMap` 用紅黑樹，所有操作 O(log n)，但它提供**有序性**：`firstKey`、`ceilingKey`、`headMap`、`subMap` 這些範圍與鄰近查詢，用 `HashMap` 得掃過全部元素才能做到。

所以選型的判準是：**只做單點存取就用 HashMap**（常數因子小很多，通常快 3 到 5 倍）；需要排序輸出、範圍查詢或找最接近的鍵就用 TreeMap。紅黑樹被選為實作是因為它是平衡二元搜尋樹裡插入與刪除成本最低的一種——它只要求「最長路徑不超過最短路徑的兩倍」這個較鬆的平衡條件，一次插入最多旋轉兩次、刪除最多三次；AVL 樹平衡更嚴格、查詢略快，但重新平衡的旋轉次數多得多，對寫入密集的通用容器不划算。

## 詳細解析

紅黑樹的平衡條件為什麼是「鬆」的：它用五條規則（根為黑、葉為黑、紅節點的子節點必為黑、任一節點到葉的路徑黑節點數相同等）保證最長路徑不超過最短路徑的兩倍，樹高上界是 2·log(n+1)。AVL 樹要求左右子樹高度差不超過 1，樹高上界約 1.44·log n——查詢稍微好一點，但維持這個條件需要更頻繁的旋轉。通用容器的工作負載是讀寫混合的，紅黑樹在兩者間取的平衡更適合當預設值；如果是幾乎唯讀的場景，AVL 或跳躍表可能更好。

**TreeMap 的 NavigableMap 介面才是它的價值所在**：`ceilingKey(k)` 回傳大於等於 k 的最小鍵、`floorKey(k)` 回傳小於等於 k 的最大鍵、`subMap(from, to)` 回傳一個**檢視**（view）而非拷貝。檢視這件事很重要——`subMap` 回傳的 Map 與原 Map 共用資料，改動任一邊會互相反映，而且它是懶的，不會因為區間很大就複製大量資料。這讓「找到最接近的閾值」這類需求（例如依流量區間套用不同費率、依時間區間找最近的快照）可以用 O(log n) 完成。

**排序來源有兩個且互斥**：`new TreeMap<>()` 用鍵的 `Comparable`；`new TreeMap<>(comparator)` 用傳入的比較器。一旦選定就決定了整個 Map 的相等語意——與 `TreeSet` 一樣，`containsKey` 判斷的是比較結果為 0，不是 `equals`。這也表示 `TreeMap` **不接受 null 鍵**（除非比較器特別處理），因為比較 null 會 NPE；`HashMap` 則允許一個 null 鍵。

**與 ConcurrentSkipListMap 的關係**：需要併發的有序 Map 時，JDK 給的不是「同步版的 TreeMap」而是 `ConcurrentSkipListMap`。原因是紅黑樹的旋轉是全域性的結構調整，很難做成無鎖；跳躍表的插入只影響局部的幾個指標，可以用 CAS 完成。這是一個有趣的設計取捨：單執行緒選紅黑樹（空間更省、常數更小），併發選跳躍表（可無鎖化）。Redis 的有序集合也是同樣的理由選了跳躍表。

## 面試回答方式

先把問題從「誰快」導回「**提供什麼能力**」：`HashMap` 是單點 O(1) 但無序，`TreeMap` 是 O(log n) 但有 `ceilingKey`、`subMap` 這些範圍與鄰近查詢。給明確判準——只做單點存取用 `HashMap`（常數因子小 3 到 5 倍），要排序輸出或範圍查詢才用 `TreeMap`。接著回答「為什麼是紅黑樹」：它的平衡條件較鬆，插入最多旋轉兩次、刪除三次，**適合讀寫混合的通用容器**；AVL 查詢略快但旋轉頻繁。兩個加分點：`subMap` 回傳的是共用資料的檢視而非拷貝；以及併發版本是 `ConcurrentSkipListMap` 而不是同步的 `TreeMap`，因為紅黑樹的旋轉是全域結構調整難以無鎖化。

## 講稿

我不會從誰比較快來談，而是從提供什麼能力。HashMap 用雜湊，單點操作平均是常數時間，但完全沒有順序。TreeMap 用紅黑樹，所有操作是對數時間，換到的是有序性。

有序性具體是什麼？是 ceilingKey 這種找大於等於某個鍵的最小鍵、是 subMap 這種取區間。這些用 HashMap 得掃過全部元素才做得到。所以判準很簡單，只做單點存取就用 HashMap，常數因子小很多。需要排序輸出、範圍查詢或找最接近的鍵，才值得付出對數時間。

至於為什麼是紅黑樹，因為它的平衡條件比較鬆，只要求最長路徑不超過最短路徑的兩倍，一次插入最多旋轉兩次。AVL 樹平衡更嚴格、查詢稍快，但旋轉頻繁很多，對讀寫混合的通用容器不划算。

補一個我覺得有意思的點。需要併發的有序 Map，JDK 給的是跳躍表而不是同步版的紅黑樹，因為旋轉是全域的結構調整，很難做成無鎖。

## 常見追問

### subMap 回傳的檢視有什麼要小心的地方？

**核心答案**：它與原 Map **共用底層資料**，所以有兩個陷阱。第一，**改動會互相反映**——往 `subMap` 放入元素會真的寫進原 Map；而且如果放入的鍵落在區間之外，會直接拋 `IllegalArgumentException`。第二，原 Map 被結構性修改後，檢視上的迭代會 fail-fast，拋 `ConcurrentModificationException`。要拿到一份獨立的快照，必須明確拷貝：`new TreeMap<>(map.subMap(from, to))`。

**詳細解析**：檢視的設計是刻意的，好處是**取區間不需要 O(k) 的複製成本**，只是記住兩個邊界並在遍歷時裁切。這在區間很大或只是想數個數（`subMap(...).size()`）時省很多。代價是生命週期綁定——把檢視存起來當作長期狀態、原 Map 卻持續被寫入，行為就會很難推理。實務原則是把檢視當成一次性的表達式使用（取完立刻遍歷或立刻拷貝），不要當成欄位存著。同樣的道理適用於 `Arrays.asList`、`List.subList` 與 `Map.keySet`，它們全都是檢視。

**面試回答方式**：先講「共用資料」這個本質，再給兩個具體陷阱：寫入區間外的鍵會拋例外、原 Map 被改動後迭代會 fail-fast。然後解釋設計理由——省掉 O(k) 的複製成本。收在可操作的原則：把檢視當一次性表達式用，需要長期持有就明確拷貝一份。

### 為什麼 HashMap 在雜湊衝突多時會轉成紅黑樹，而不是換一種雜湊？

**核心答案**：因為衝突多的成因常常是外部可控的。當鍵的 `hashCode` 是攻擊者能構造的（例如來自 HTTP 參數名、JSON 欄位名），對手可以刻意送出大量落在同一個桶的鍵，把 O(1) 退化成 O(n)，用少量請求打垮伺服器——這就是雜湊碰撞的阻斷服務攻擊。JDK 8 的樹化把**最壞情況**從 O(n) 壓到 O(log n)，是一個**保底**而不是最佳化。

**詳細解析**：換雜湊函式解決不了問題，因為 `hashCode` 由使用者的類別提供，`HashMap` 只能對它做擾動（把高位混入低位），無法阻止一個刻意寫壞的 `hashCode`。樹化的門檻設得很高——單一桶超過 8 個節點**且**表容量至少 64 才轉樹，容量不足時優先擴容。這個 8 的來源是泊松分布的估算：在雜湊均勻的前提下，一個桶累積到 8 個元素的機率大約是千萬分之一，也就是正常情況下這條路徑幾乎不會被走到。這正好說明它的定位是保險絲，不是常態路徑。

**面試回答方式**：把樹化定位成「**保底而非最佳化**」，並用雜湊碰撞攻擊說明最壞情況為什麼值得處理。接著指出換雜湊解決不了，因為 `hashCode` 是使用者提供的。最後用門檻的數字支撐論點：8 個節點且容量至少 64 才樹化，而 8 這個值來自泊松分布估算——正常情況幾乎不會觸發。

### 什麼情況下該用 LinkedHashMap 而不是 TreeMap 來取得順序？

**核心答案**：看要的是**哪一種順序**。`TreeMap` 給的是**鍵的大小順序**（依比較器排序）；`LinkedHashMap` 給的是**插入順序或存取順序**（它在雜湊表之外多維護一條雙向鏈結串列）。如果需求只是「輸出時維持放進去的順序」或「實作 LRU」，`LinkedHashMap` 是對的選擇——它保有 `HashMap` 的 O(1) 單點操作，只多付出每個節點兩個指標的記憶體。

**詳細解析**：兩者的成本結構完全不同。`LinkedHashMap` 的操作仍然是雜湊表的 O(1)，鏈結串列只是額外維護；`TreeMap` 的每次操作都要走 O(log n) 次比較，而比較字串或複合鍵的常數成本並不低。所以只要不需要範圍查詢，就不該為了「有序」而選 TreeMap。反過來，`LinkedHashMap` 完全無法回答「大於 x 的最小鍵」這類問題，因為它的鏈結串列順序與鍵的大小無關。實務上還有第三種選擇：資料量小且建好就不再改的話，直接排序一個 `List` 或用 `Map.Entry` 陣列，區域性比任何樹都好。

**面試回答方式**：先把「順序」拆成兩種——鍵的大小順序與插入／存取順序，然後對應到兩個容器。強調 `LinkedHashMap` 保有 O(1) 而 `TreeMap` 每次操作都要付 O(log n) 次比較，所以不需要範圍查詢就不該選 `TreeMap`。加分點是提出第三條路：資料量小且不再改動時，排好的陣列在區域性上勝過任何樹。
