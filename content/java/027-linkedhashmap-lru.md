# 題目

`LinkedHashMap` 是怎麼維持順序的？為什麼它可以用幾行程式碼實作 LRU 快取？

## 核心答案

`LinkedHashMap` 繼承 `HashMap`，把節點型別擴充成帶 before/after 指標的版本，在雜湊表之外額外維護一條貫穿所有節點的雙向鏈結串列。雜湊表負責 O(1) 定位，鏈結串列負責順序——兩者管的是同一批節點物件，不是兩份資料。

順序有兩種模式，由建構子的 `accessOrder` 參數決定：**false（預設）是插入順序**，新節點接到鏈尾，重複 put 同一個鍵不改變位置；**true 是存取順序**，每次 `get` 或 `put` 都把該節點移到鏈尾。後者正是 LRU 需要的語意——鏈頭永遠是最久沒被使用的元素。

再加上 `removeEldestEntry` 這個**保護方法**：`HashMap` 每次插入新節點後會呼叫它，回傳 true 就移除鏈頭。所以 LRU 快取只需要「以 accessOrder=true 建構，並覆寫 `removeEldestEntry` 回傳 `size() > capacity`」，容量控制與淘汰策略就都有了。這是模板方法模式的典型應用：框架決定流程（何時檢查、移除哪一個），使用方只填「要不要移除」這個決策點。

## 詳細解析

**兩份結構共用節點是關鍵**：如果用一個 `HashMap` 加一個獨立的 `LinkedList`，移動元素時得先在串列裡找到它，那是 O(n)。`LinkedHashMap` 的 `Entry` 本身就帶著前後指標，從雜湊表拿到節點後可以**直接**在串列裡把它摘下來重接，整個 `get` 仍然是 O(1)。手寫 LRU 之所以要「HashMap 存 key 到節點的映射，值是雙向串列的節點」，就是在重現這個結構。

accessOrder=true 的隱藏後果是 get 變成結構性修改：讀取會移動鏈結串列的指標，這表示**在迭代過程中呼叫 get 會拋 `ConcurrentModificationException`**，而且多執行緒下即使全都是讀取也不安全。這是很容易被忽略的點——大家直覺認為讀是安全的。用它做快取時一定要外部同步，或改用 Caffeine 這類專門的快取庫。

**removeEldestEntry 的時機很精確**：它在 `afterNodeInsertion` 裡被呼叫，也就是**新元素已經放進去之後**。所以判斷條件寫 `size() > capacity` 而不是 `>=`——插入後大小暫時是 capacity+1，移除一個回到 capacity。另外它**只在插入新鍵時觸發**，更新既有鍵不會觸發，這符合直覺（更新不增加元素）。

**這個實作的邊界在哪**：`LinkedHashMap` 的 LRU 是**嚴格 LRU**，每次存取都要改指標，在高併發下即使加了讀寫鎖，讀取也要拿寫鎖，會成為瓶頸。生產級快取（Caffeine、Guava）改用 **近似 LRU 或 W-TinyLFU**：把存取記錄先寫進一個環形緩衝，再批次套用到淘汰結構上，讀路徑就不必修改共享狀態。理解這個差異，比背出 LinkedHashMap 的三行程式碼更能顯示深度——它說明了「正確的資料結構」與「可用於高併發的快取」之間還有一段工程距離。

## 面試回答方式

先講**結構**：`LinkedHashMap` 在 `HashMap` 之上把節點加了 before/after 指標，多維護一條貫穿全部節點的雙向串列——**兩份結構共用同一批節點**，所以定位是 O(1)、移動也是 O(1)。接著講**兩種順序模式**與 `accessOrder=true` 對應 LRU 語意，再講 `removeEldestEntry` 這個模板方法：插入後被呼叫，回傳 true 就移除鏈頭，條件寫 `size() > capacity`。有兩個很能拉開差距的補充：**accessOrder=true 時 get 是結構性修改**，迭代中讀取會拋 CME、多執行緒下純讀也不安全；以及**生產級快取不用嚴格 LRU**，Caffeine 用環形緩衝加 W-TinyLFU 讓讀路徑不修改共享狀態。

## 講稿

LinkedHashMap 繼承 HashMap，把節點加上前後指標，在雜湊表之外多維護一條貫穿所有節點的雙向串列。重點是兩份結構共用同一批節點物件，不是兩份資料。所以從雜湊表定位到節點之後，可以直接在串列裡把它摘下來重接，整個操作還是常數時間。

順序有兩種模式。預設是插入順序，另一種是存取順序，每次讀取或寫入都把節點移到鏈尾。後者正是 LRU 要的，鏈頭永遠是最久沒被用到的。

再加上一個保護方法，每次插入新節點之後框架會呼叫它，回傳 true 就移除鏈頭。所以實作 LRU 只要用存取順序建構，然後覆寫它回傳大小超過容量就好。這是模板方法模式，框架決定流程，我只填要不要移除這個決策點。

有一個很容易被忽略的地方，存取順序模式下讀取也是結構性修改，會移動指標。所以迭代中讀取會拋例外，多執行緒下就算全部都是讀也不安全。

## 常見追問

### 為什麼生產級的快取不直接用 LinkedHashMap？

**核心答案**：因為嚴格 LRU 的讀路徑會修改共享狀態。每次 `get` 都要把節點移到鏈尾，這是寫操作，多執行緒下必須拿排他鎖——讀取密集的快取因此變成完全序列化，核心數再多也沒用。生產級快取（Caffeine、Guava Cache）改成讀取時只把存取事件寫進一個執行緒本地或環形緩衝，之後由某個執行緒批次套用到淘汰結構，讀路徑就不碰共享的串列了。

**詳細解析**：除了併發，**命中率**也是換掉純 LRU 的理由。LRU 對「掃描式存取」很脆弱——一次全表遍歷會把整個快取沖掉，即使那些資料只用一次。Caffeine 用的 W-TinyLFU 在 LRU 之外加了一個**頻率草圖**（用 count-min sketch 近似記錄每個鍵最近的存取次數），淘汰時同時考慮「多久沒用」與「用得多不多」，掃描進來的一次性資料因為頻率低而擋在門外。代價是多了一個近似結構的記憶體與維護成本，但在真實工作負載上命中率的提升通常遠超過這個成本。

**面試回答方式**：分兩條講——**併發**上，嚴格 LRU 的讀取是寫操作、會序列化，所以改成把存取事件寫進緩衝再批次套用；**命中率**上，LRU 對掃描式存取脆弱，一次全表遍歷就沖掉快取，所以用頻率草圖同時考慮最近性與頻率。收在取捨：多付一個近似結構的成本，換到讀路徑無鎖與更高的命中率。

### LinkedHashMap 比 HashMap 多花多少記憶體？

**核心答案**：每個節點多兩個引用欄位（before、after）。64 位元 JVM 開啟壓縮指標時每個引用 4 位元組，所以**每個 entry 多 8 位元組**；關閉壓縮指標則是 16 位元組。以 `HashMap.Node` 本身約 32 位元組（物件頭 12、hash 4、key 4、value 4、next 4，再對齊）來算，大約是**多 25% 的節點開銷**，加上 key 與 value 物件本身的話比例會更低。

**詳細解析**：這個開銷通常不是問題，真正該注意的是**它讓節點無法被 HashMap 的樹化重用**——`LinkedHashMap` 同時覆寫了 `newNode` 與 `newTreeNode`，樹化後的節點也要維持串列指標，所以樹節點更大。另外一個常被忽略的成本是**遍歷行為的差異**：`HashMap` 的迭代是掃過整個桶陣列（包含空桶），元素少而容量大時會掃很多空位；`LinkedHashMap` 直接走串列，遍歷成本與元素數成正比而與容量無關。所以在「容量開得很大但元素稀疏、又要頻繁遍歷」的情境，`LinkedHashMap` 反而更快。

**面試回答方式**：給出具體數字——每個 entry 多兩個引用、壓縮指標下是 8 位元組，約 25% 的節點開銷。接著把話題轉向一個更有意思的面向：**遍歷成本**。`HashMap` 要掃過整個桶陣列包含空桶，`LinkedHashMap` 直接走串列，所以稀疏又常遍歷的情境下它反而更快——這說明「多花記憶體」不等於「一定比較慢」。

### 用 LinkedHashMap 做本地快取，還缺哪些東西？

**核心答案**：至少缺四項。**執行緒安全**——它完全不同步，而且 accessOrder 模式下連讀取都不安全。**過期時間**——`removeEldestEntry` 只處理容量，不處理時效，資料可能無限期地舊。**載入與擊穿保護**——快取未命中時多個執行緒會同時去查後端，需要單飛（single-flight）機制。**可觀測性**——命中率、淘汰數、載入耗時，沒有這些就無法判斷快取到底有沒有用。

**詳細解析**：這四項每一項都能自己補，但補完就是重寫了一個快取庫，而且每一項都有不明顯的坑：過期要決定是惰性清除還是定時掃描（惰性會讓過期資料佔著記憶體，定時掃描要多一個執行緒）；單飛要小心第一個執行緒失敗時其他人的處理；統計本身在高併發下會成為爭用點（Caffeine 用 `LongAdder` 而不是 `AtomicLong` 就是為此）。所以務實的判斷是：需求只有「限制大小的簡單暫存、單執行緒使用」時 `LinkedHashMap` 剛好夠用，一旦出現併發或過期需求就該換成專門的庫，自己補會在細節上流血。

**面試回答方式**：列出四個缺口（執行緒安全、過期、擊穿保護、可觀測性），每個給一句為什麼重要。然後給明確的分界線：單執行緒、只要限制大小就用 `LinkedHashMap`；出現併發或過期需求就換專門的庫。加分點是舉一個細節說明「自己補會流血」——例如統計本身在高併發下會爭用，所以 Caffeine 用 `LongAdder`。
