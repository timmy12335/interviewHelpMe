# 題目

`Arrays.asList`、`List.of`、`Collections.unmodifiableList` 與 `new ArrayList<>(...)` 產生的清單有什麼不同？

## 核心答案

四者在**可變性**與**與來源的關係**這兩個維度上完全不同。

`Arrays.asList(a, b, c)` 回傳的是**陣列的固定大小檢視**——不能增刪（拋 `UnsupportedOperationException`），但**可以 set**，而且 set 會寫回原陣列。它與傳入的陣列共用資料。

`List.of(a, b, c)`（JDK 9）回傳**真正的不可變清單**——增刪改全部拋例外，而且**不接受 null 元素**（傳 null 直接 NPE），內容獨立於任何來源。

`Collections.unmodifiableList(list)` 回傳的是一個**唯讀包裝**——它自己不能改，但底層的原清單如果被改，包裝看得到。它是「不給你改」而不是「不可變」，這個區別在把清單傳出去時很關鍵。

`new ArrayList<>(source)` 是**完整拷貝**，可變且與來源脫鉤。

## 詳細解析

**Arrays.asList 的兩個陷阱**很常在面試出現。第一，它回傳的是 `java.util.Arrays$ArrayList`（一個私有內部類別），**不是 `java.util.ArrayList`**，所以只實作了固定大小的語意，`add` 與 `remove` 都會拋例外。第二，傳入**基本型別陣列**時行為完全不符直覺：`Arrays.asList(new int[]{1,2,3})` 會得到一個**只有一個元素的 `List<int[]>`**，因為可變參數要求物件型別，`int[]` 整個被當成一個物件。改用 `Integer[]` 或 `Arrays.stream(arr).boxed().toList()` 才是對的。

**List.of 的 null 檢查是刻意的設計決策**：JDK 9 的不可變集合家族（`List.of`、`Set.of`、`Map.of`）一律拒絕 null，理由是 null 在集合裡幾乎總是代表某種未完成的狀態，而且 `contains(null)` 這類操作在不可變集合上要額外分支處理。代價是從舊 API 遷移時可能出現非預期的 NPE——`Arrays.asList` 允許 null，換成 `List.of` 後同樣的資料就會炸。這是升級時容易踩到的相容性問題。

unmodifiableList 是包裝而非拷貝，這決定了它的安全邊界：如果一個方法回傳 `Collections.unmodifiableList(this.items)`，呼叫方確實不能改，但這個類別自己之後修改 items，呼叫方手上的清單內容就會跟著變。要提供真正的不可變快照必須拷貝：`List.copyOf(this.items)`。`List.copyOf` 還有一個最佳化——如果來源已經是不可變清單，它會直接回傳同一個實例而不複製。

**選型的簡單規則**：對外回傳用 `List.copyOf`（真快照、真不可變）；內部常數用 `List.of`；要傳給會修改清單的舊 API 就用 `new ArrayList<>(...)`；`Arrays.asList` 只在**明確想要陣列檢視**時才用，其他情況它帶來的意外多於便利。

## 面試回答方式

用**可變性**與**與來源的關係**兩個維度把四者拉開，不要一個個背行為。重點放在最容易錯的兩個：`Arrays.asList` 是**陣列檢視**，不能增刪但可以 set 且會寫回原陣列，而且傳基本型別陣列會得到只有一個元素的清單；`Collections.unmodifiableList` 是**唯讀包裝不是不可變**，底層被改就看得到，所以對外回傳快照要用 `List.copyOf`。再補一句 `List.of` 拒絕 null 是刻意設計，從舊 API 遷移時是常見的 NPE 來源。最後給一條選型規則：對外回傳用 `copyOf`、內部常數用 `of`、要交給會修改的 API 就用 `new ArrayList<>`。

## 講稿

這四種東西差在兩個維度，可不可變，以及跟來源有沒有關係。

Arrays 的 asList 回傳的是陣列的固定大小檢視。它不能增刪，但可以修改元素，而且改了會寫回原本的陣列。它還有一個很不直覺的地方，傳入基本型別陣列的時候，整個陣列會被當成單一物件，你會拿到一個只有一個元素的清單。

List 的 of 是真正的不可變，增刪改都拋例外，而且不接受 null。這是刻意的設計，從舊的 API 遷移過來的時候，常常會冒出非預期的空指標。

Collections 的 unmodifiableList 我覺得最容易誤解。它是唯讀包裝，不是不可變。拿到它的人不能改，但底層那份被改的話，包裝看得到。所以要對外提供真正的快照，應該用 List 的 copyOf。

我的選型規則是，對外回傳用 copyOf，內部常數用 of，要交給會修改清單的舊 API 就直接拷貝一份。

## 常見追問

### 為什麼 JDK 9 的不可變集合刻意不接受 null？

**核心答案**：因為 null 在集合裡幾乎總是表示某種尚未完成或缺失的狀態，而不可變集合的定位是「已完成的值」。技術上還有兩個理由：允許 null 會讓 `contains`、`indexOf` 這類方法需要額外的分支處理（不能直接用 `equals` 呼叫），以及不可變集合內部用了針對小尺寸最佳化的多種實作，null 會讓這些實作各自都要處理特例。

**詳細解析**：這個決策與 `Optional` 不接受 null、`Map.of` 不接受 null 值是同一套哲學：在 API 邊界把 null 擋掉，讓 null 只存在於明確允許它的地方。副作用是遷移成本——`Arrays.asList` 與 `Collections.unmodifiableList` 都允許 null，把它們換成 `List.of` 時，只要資料裡混進一個 null 就會在建立時炸掉。這其實是好事（問題暴露在建立時而不是在遙遠的下游），但升級時要有心理準備。需要允許 null 又想要不可變時，可以用 `Collections.unmodifiableList(new ArrayList<>(source))`。

**面試回答方式**：先給概念上的理由——不可變集合代表「已完成的值」，null 代表未完成；再給兩個技術理由（`contains` 需要額外分支、小尺寸特化實作要處理特例）。把它連到 `Optional` 與 `Map.of` 的同一套哲學，並老實指出遷移成本與繞道方案，會顯得判斷是完整的。

### List.of 回傳的清單在小尺寸時有什麼特別的實作？

**核心答案**：JDK 對元素數量做了**特化**。0、1、2 個元素分別用專門的類別（`ListN` 之外還有 `List12`），把元素直接存成欄位而不是陣列，省掉一次陣列物件的配置與一層間接存取。超過 2 個才用內部陣列的 `ListN`。`Set.of` 與 `Map.of` 也有同樣的處理，而且 `Set.of` 在多元素時用的是**開放定址**的探測表而非鏈結，因為不可變後不需要處理動態擴容。

**詳細解析**：這種特化的收益來自真實的使用分布——絕大多數 `List.of` 呼叫的元素數量是個位數，很多是 1 或 2（例如回傳單一結果、或一組鍵值）。省下的不只是記憶體，還有**指標追逐**：欄位直接內嵌時，讀取元素不必先載入陣列物件再索引。另外不可變集合還有一個安全設計——`Set.of` 與 `Map.of` 的迭代順序**在每次 JVM 啟動時會不同**（用了一個隨機的 SALT），刻意防止使用者依賴迭代順序。這是把「不保證的事情」主動變得可觀察，避免程式碼悄悄依賴實作細節。

**面試回答方式**：講出「依元素數量特化」這個具體事實與它的收益（省一次配置、少一層間接）。真正的加分點是後半段：`Set.of` 與 `Map.of` 的迭代順序每次 JVM 啟動都不同，這是刻意把不保證的行為變得可觀察，防止程式碼依賴實作細節——這種設計思路比背實作類別名稱有價值得多。

### 對外回傳集合時，該回傳不可變副本還是唯讀包裝？

**核心答案**：**預設回傳不可變副本**（`List.copyOf`）。唯讀包裝只擋住呼叫方的修改，擋不住自己後續的修改，於是呼叫方手上的清單會在他不知情的時候變化——這是**共享可變狀態**，正是最難除錯的那類問題。副本的代價是一次 O(n) 拷貝，只有在集合很大且回傳很頻繁時才值得考慮換掉。

**詳細解析**：真的需要避免拷貝時有兩條路。第一，讓內部狀態本身就是不可變的——每次修改都建立新的不可變清單存回欄位，回傳時直接把它交出去（零拷貝且完全安全），代價轉移到寫入端，適合讀多寫少。第二，**回傳串流或迭代器**而不是集合，讓呼叫方只能消費不能持有。要注意 `List.copyOf` 對已經不可變的來源會直接回傳原實例，所以第一條路搭配 `copyOf` 幾乎沒有額外成本。在 API 設計上，把「呼叫方能不能改」與「內容會不會變」分開思考，是這題的核心判斷。

**面試回答方式**：先給預設立場——回傳不可變副本，並說明唯讀包裝的問題是共享可變狀態而非「能不能改」。接著給兩條避免拷貝的路：內部狀態本身不可變（成本轉移到寫入端，適合讀多寫少），或回傳串流讓呼叫方無法持有。最後點出 `List.copyOf` 對不可變來源不複製，所以這個組合幾乎沒有額外成本。
