# 題目

要讓一個類別真正不可變需要滿足哪些條件？防禦性拷貝在什麼時候是必要的？

## 核心答案

真正不可變需要五個條件同時成立：**所有欄位 final 且私有**、**類別不可被繼承**（final 類別或建構子私有加靜態工廠）、不提供任何會修改狀態的方法、建構時對傳入的可變物件做防禦性拷貝、回傳可變欄位時也做防禦性拷貝。前三條大家都記得，後兩條才是實際會漏掉的地方。

漏掉防禦性拷貝的後果是「假的不可變」：`final List<Item> items` 保證的是**引用不變**，不是**內容不變**。如果建構子直接 `this.items = items`，呼叫方手上還握著同一個清單，之後 `add` 一筆就改到了「不可變」物件的內部狀態。同理，`getItems()` 直接回傳內部清單，任何拿到它的人都能修改。

`record` 也一樣——它自動生成的建構子與存取器都不做拷貝，元件是可變物件時 record 並不是不可變的。要修正得在緊湊建構子裡拷貝（`items = List.copyOf(items)`），存取器也要覆寫。這是 record 最常被誤解的地方。

## 詳細解析

類別不可被繼承這一條的理由是「子類別可以偽裝成可變」：即使父類別所有欄位都是 final，子類別可以新增可變欄位並覆寫方法回傳不一致的結果，而多型讓呼叫方拿到的仍然宣稱是父型別。所以不可變類別要嘛 final，要嘛把建構子設為私有並只透過靜態工廠建立——後者更有彈性（可以做快取、可以回傳子型別）。

防禦性拷貝的深度是一個判斷題：拷貝清單本身（淺拷貝）只保護清單結構，如果元素本身是可變的，別人還是能透過元素改變狀態。正確的做法通常是讓元素型別本身也不可變，而不是做深拷貝——深拷貝成本高、容易漏、遇到循環引用還會爆。「不可變性應該是遞迴的性質，靠型別保證而不是靠拷貝維持」是這題最重要的判斷。

不可變帶來的好處遠不只執行緒安全：可以自由共享而不必同步、可以安全地當作 Map 鍵（雜湊值永不失效）、可以放進 Set 而不會遺失、失敗時不會留下半修改的狀態（原子性）、以及**推理成本大幅下降**（看到一個引用就知道它的值永遠不會變，不必追蹤誰可能改它）。最後一項在大型程式碼庫裡的價值最高，也最難量化。

**代價是修改要建立新物件**：修改一個欄位就要複製整個物件，在高頻修改的場景會產生大量垃圾。緩解方式有三種：**用建造者模式做批次修改**（一次建立一個新物件而不是每個欄位一次）、**用持久化資料結構**（結構共享，改一個元素只複製路徑上的節點，Java 沒有內建但有第三方實作）、或者在明確界定的邊界內使用可變物件（例如方法內部用 `StringBuilder`，回傳時轉成 `String`）。最後一種是實務上最常用也最務實的做法——不可變是預設，可變是局部且經過論證的例外。

## 面試回答方式

先給**五個條件**，並指出前三條大家都記得、後兩條（建構時拷貝、回傳時拷貝）才是實際會漏的地方。用一句話點破核心誤解：`final` 保證引用不變，不保證內容不變。接著主動講 **record 也不例外**——自動生成的建構子與存取器都不拷貝，元件是可變物件時 record 並不是不可變的，要在緊湊建構子裡 `List.copyOf`。加分點有兩個：不可變性應該靠型別遞迴保證而不是靠深拷貝維持（深拷貝成本高、易漏、有循環引用問題）；以及好處不只執行緒安全，還有可安全當 Map 鍵、失敗不留半修改狀態、推理成本下降。最後誠實給代價與緩解——建造者做批次修改、局部使用可變物件（`StringBuilder` 內部用、回傳前轉字串）。

## 講稿

真正不可變需要五個條件。所有欄位 final 且私有、類別不可被繼承、不提供修改狀態的方法、建構時對傳入的可變物件做防禦性拷貝、回傳可變欄位時也做拷貝。前三條大家都記得，後兩條才是實際會漏的地方。

漏掉的後果是假的不可變。final 保證的是引用不變，不是內容不變。如果建構子直接把傳進來的清單存起來，呼叫方手上還握著同一個清單，之後加一筆就改到了所謂不可變物件的內部。

record 也一樣。它自動生成的建構子跟存取器都不做拷貝，所以元件是可變物件的時候，record 並不是不可變的。要修正得在緊湊建構子裡拷貝。這是 record 最常被誤解的地方。

還有一個判斷我覺得很重要。防禦性拷貝該做多深？我的答案是不要靠深拷貝，而是讓元素型別本身也不可變。深拷貝成本高、容易漏、遇到循環引用還會爆。不可變性應該是遞迴的性質，靠型別保證。

## 常見追問

### record 到底算不算不可變？

**核心答案**：record 保證的是**淺層不可變**——所有元件都是 final，沒有 setter，`equals`、`hashCode`、`toString` 都由元件推導。但它**不對元件做任何拷貝**，所以元件如果是 `List`、陣列、`Date` 這類可變型別，record 的狀態就能被外部改變。準確的說法是：**record 保證引用不變，不保證值不變**。

**詳細解析**：要讓 record 真正不可變，需要在**緊湊建構子**裡拷貝並在**存取器**上也拷貝：`record Order(List<Item> items) { Order { items = List.copyOf(items); } }`——注意緊湊建構子裡是對參數賦值而不是 `this.items`，這是 record 特有的語法。存取器如果回傳的是已經拷貝成不可變的清單就不必再覆寫（`List.copyOf` 的結果本身不可變）。陣列元件則沒有便宜的解法，`clone()` 每次呼叫都複製，而且 `equals` 對陣列是引用比較——**record 的元件用陣列幾乎總是錯的**，該換成 `List`。

**面試回答方式**：給準確的表述——淺層不可變、保證引用不變不保證值不變，不要籠統說「record 是不可變的」。接著給修正方法（緊湊建構子裡 `List.copyOf`，並指出那裡是對參數賦值而非 `this`）。加分點是點出**陣列元件幾乎總是錯的**：`clone` 每次都複製、`equals` 是引用比較，該換成 `List`。

### 不可變物件在什麼情況下反而是負擔？

**核心答案**：**大型物件的高頻小修改**。一個有五十個欄位的物件，每次改一個欄位就複製全部五十個引用，在迴圈裡跑十萬次就是十萬個垃圾物件。此外**建構期需要分步組裝**時（例如從多個來源逐步填入資料）也不適合，全 final 的物件無法分步建立。

**詳細解析**：緩解方式依成本排序。**建造者模式**最常用——在建造者裡累積修改，最後一次建立不可變物件，把 n 次拷貝降到 1 次。**with 方法**（`order.withStatus(PAID)`）適合單點修改，配合 record 很自然，但連續多個 with 仍然是多次拷貝。**持久化資料結構**用結構共享讓修改只複製路徑上的節點（例如把清單實作成樹），Java 沒有內建但 Vavr、Guava 的不可變集合部分提供類似能力。最務實的方案往往是**劃定可變的邊界**：方法內部用可變的建造者或 `StringBuilder`，跨越方法邊界時轉成不可變。逃逸分析也常常讓短命的中間物件根本不配置，所以「怕產生垃圾」在很多情況下是過慮，該量測而不是預設避開不可變。

**面試回答方式**：給出具體的負擔場景（大型物件高頻小修改、需要分步組裝），並用「五十個欄位改一個要複製全部」這種具體描述取代抽象說法。緩解方式依成本排序給出（建造者、with 方法、持久化資料結構、劃定可變邊界）。加分點是提醒逃逸分析常讓短命中間物件不配置，所以怕產生垃圾往往是過慮，應該量測。

### 不可變與執行緒安全的關係是什麼？

**核心答案**：不可變物件天然執行緒安全，但前提是它被安全發布。物件的欄位都是 final 時，JMM 提供 **final 欄位的特殊保證**——建構子完成後，任何看得到這個物件引用的執行緒都保證看得到 final 欄位的正確初始值，不需要額外同步。這是 JMM 少數幾個「不用 volatile 也保證可見性」的地方。但**非 final 的欄位沒有這個保證**，所以只是「不提供 setter」而欄位不是 final 的類別，在不安全發布時仍可能被別的執行緒看到未初始化的狀態。

**詳細解析**：安全發布還有一個常被忽略的漏洞——**建構子裡的 this 逃逸**。如果建構子把 `this` 註冊到某個監聽器、或啟動一個引用 `this` 的執行緒，其他執行緒就可能在物件**還沒建構完成**時看到它，final 欄位的保證此時不成立。所以不可變類別的建構子裡不該有任何形式的自我發布，需要註冊時用靜態工廠：先完整建構，再註冊。這也是為什麼《Java 並發編程實戰》把「不要讓 this 在建構期逸出」列為專門一節——它是少數會讓 final 保證失效的情況。

**面試回答方式**：先給關係與精確條件——不可變天然執行緒安全，但要靠 final 欄位的 JMM 特殊保證，而非 final 的欄位沒有這個保證。這比籠統說「不可變就安全」精確得多。加分點是 **this 在建構期逸出**會讓 final 保證失效，並給出正確做法：用靜態工廠先完整建構再註冊，不要在建構子裡自我發布。
