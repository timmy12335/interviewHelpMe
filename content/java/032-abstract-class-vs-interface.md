# 題目

介面有了預設方法之後，抽象類別還有什麼不可取代的地方？實務上該怎麼選？

## 核心答案

預設方法讓介面能提供**行為**，但它補不上抽象類別的兩件事：**狀態**與**建構過程**。介面不能有實例欄位（只能有 `public static final` 常數），也沒有建構子，所以任何需要「子類別共用一份可變狀態」或「在建立時做初始化與不變量檢查」的重用，只有抽象類別做得到。

還有一個結構性的差異：**介面可以多實作，抽象類別只能單繼承**。這決定了它們在型別系統中的角色——**介面描述「能做什麼」（能力），抽象類別描述「是什麼」（身分）**。一個型別可以同時具備多種能力，但只有一個身分。

實務選型的順序是：**先寫介面**定義契約；發現多個實作有大量重複的樣板時，再加一個抽象骨架類別（`AbstractXxx`）放共用實作；讓具體類別繼承骨架但**對外宣告的型別仍是介面**。JDK 自己就是這樣做的——`List` 是介面、`AbstractList` 是骨架、`ArrayList` 是實作。預設方法適合放**用其他方法就能推導出來的便利行為**（例如 `List.sort` 用 `Comparator`），不適合放需要狀態的邏輯。

## 詳細解析

**預設方法真正解決的問題是介面演進**：JDK 8 要在 `Collection` 上加 `stream()`，如果是抽象方法，全世界所有實作 `Collection` 的類別都會編譯失敗。預設方法讓介面**可以在不破壞既有實作的前提下新增方法**——這才是它被引入的動機，而不是「讓介面取代抽象類別」。理解這個動機，就不會把大量邏輯塞進預設方法裡。

**多重繼承的衝突是有規則的**：一個類別同時實作兩個都有同名預設方法的介面時會編譯錯誤，必須自己覆寫並用 `Interface.super.method()` 明確指定。解析順序是「**類別優先於介面、子介面優先於父介面**」——來自父類別的具體方法永遠贏過介面的預設方法。這是刻意的設計，讓引入預設方法不會改變既有類別的行為。

**抽象類別的建構子是它最被低估的價值**：它讓子類別**無法跳過**必要的初始化與參數檢查（`super(...)` 是強制的）。介面做不到這件事，實作者可以完全自由地建立一個違反不變量的物件。所以當「所有實作都必須持有某些欄位且必須被驗證」時，抽象類別是對的工具。但要小心**在建構子裡呼叫可被覆寫的方法**——子類別的欄位此時還沒初始化，會讀到 null 或 0，這是繼承的經典陷阱。

**繼承本身的成本要納入選型**：抽象類別把子類別綁進一個繼承鏈，父類別的任何改動都可能波及子類別（脆弱基底類別問題），而且用掉了唯一的繼承名額。所以**當共用的只是行為而非狀態時，優先考慮「介面 + 組合」而不是抽象類別**——把共用邏輯抽成一個獨立的協作物件，讓各實作持有它。這通常比繼承更有彈性，也更好測試。

## 面試回答方式

先精準指出預設方法補不上的兩件事——**狀態與建構過程**，這比籠統說「抽象類別可以有欄位」更有力。接著給型別系統上的定位：**介面是能力、抽象類別是身分**，能力可以有多個、身分只有一個。然後說出預設方法的真正動機是**介面演進**（JDK 8 要在 `Collection` 加 `stream` 而不破壞既有實作），由此推出「不該把大量邏輯塞進預設方法」。實務順序給清楚：先介面定契約，重複的樣板才抽 `AbstractXxx` 骨架，對外仍宣告介面型別，並舉 `List`／`AbstractList`／`ArrayList`。加分點是提醒**共用的只是行為時優先用組合而非繼承**，以及抽象類別建構子裡不要呼叫可被覆寫的方法。

## 講稿

預設方法讓介面能提供行為，但它補不上兩件事，狀態跟建構過程。介面不能有實例欄位，也沒有建構子。所以只要重用的內容涉及子類別共用一份可變狀態，或是需要在建立時做初始化跟不變量檢查，就只有抽象類別做得到。

另外一個結構上的差異是介面可以多實作，抽象類別只能單繼承。所以我會說介面描述能做什麼，是能力，抽象類別描述是什麼，是身分。一個型別可以有很多能力，但只有一個身分。

預設方法真正的動機其實是介面演進。JDK 8 要在集合介面上加串流方法，如果是抽象方法，全世界的實作都會編譯失敗。理解這個動機，就不會把大量邏輯塞進預設方法裡。

實務上我的順序是，先寫介面定義契約，發現多個實作有大量重複的樣板，再加一個抽象骨架類別放共用實作，但對外宣告的型別仍然是介面。JDK 自己就是這樣做的。

## 常見追問

### 同時實作兩個有同名預設方法的介面會怎樣？

**核心答案**：**編譯錯誤**，Java 不做任何隱式選擇。必須在類別裡覆寫該方法，並用 `Interface.super.method()` 明確指定要用哪一個，或者自己寫一份新的實作。整體的解析規則是三條優先序：**類別的具體方法 > 更具體的子介面 > 同層級的介面（衝突則報錯）**。

**詳細解析**：「類別優先」這條規則是相容性的關鍵——如果一個既有類別已經從父類別繼承了某方法，之後它實作的介面新增了同名預設方法，行為**不會改變**，因為類別的方法永遠勝出。這正是預設方法能安全引入的原因。而同層級衝突選擇報錯而非隱式挑一個，是為了避免 C++ 多重繼承那種「菱形問題」的隱晦行為——**Java 的一貫取向是讓歧義在編譯期暴露，而不是給一個看起來能動的預設值**。實務上如果經常遇到這種衝突，通常是介面切分得不好，應該回頭看是不是把太多不相關的能力放進同一組介面。

**面試回答方式**：先給結果（編譯錯誤）與解法（覆寫加 `Interface.super`），再給完整的三條優先序。重點放在解釋**為什麼「類別優先」**——它保證既有類別的行為不會因為介面新增預設方法而改變，這是相容性的關鍵。收在設計取向：Java 選擇讓歧義在編譯期暴露，而不是給一個看起來能動的預設值。

### 什麼時候該用組合取代抽象類別？

**核心答案**：當**共用的是行為而不是身分**時。判斷的問題是：「子類別真的是父類別的一種嗎，還是只是想借用它的程式碼？」如果答案是後者，就該把那段程式碼抽成一個獨立物件，讓各個實作持有它。繼承會用掉唯一的繼承名額、把子類別綁進父類別的演進，而組合只是多一個欄位。

**詳細解析**：有一個實用的檢查——**如果父類別新增一個方法，所有子類別是不是都應該擁有它？** 如果答案是「有些子類別會被迫繼承不想要的方法」，那就不是「是一種」的關係。這正是里氏替換與介面隔離兩個原則在講的事。另一個訊號是**子類別覆寫父類別方法時直接空實作或拋不支援例外**，那代表繼承層次選錯了。組合的代價是要多寫轉發方法（Java 沒有語言層級的委派語法），這在方法多的時候確實囉嗦，但可以用 IDE 生成，而且**轉發是顯式的資料流，比隱式繼承好讀**。

**面試回答方式**：給出一個可操作的判斷問句——「真的是一種，還是只是想借程式碼」。再給兩個具體訊號：父類別新增方法時有子類別被迫繼承不想要的行為；子類別覆寫成空實作或拋不支援例外。誠實承認組合的代價是要寫轉發方法，但指出那是顯式的資料流。連到里氏替換與介面隔離會讓回答更有結構。

### 介面裡的 private 方法與 static 方法各解決什麼問題？

**核心答案**：**private 方法（JDK 9）解決預設方法之間的重複**——多個預設方法有共同邏輯時，以前只能開一個 public 的輔助方法（汙染 API）或複製貼上，現在可以抽成介面內的私有方法。**static 方法（JDK 8）解決工具類別的歸屬**——以前 `Collections`、`Arrays` 這種伴生工具類別是因為介面不能放靜態方法才存在的，現在 `List.of`、`Comparator.comparing` 可以直接掛在介面上，**契約與其工廠方法住在一起**。

**詳細解析**：這兩個補充讓介面在 JDK 9 之後有了完整的封裝能力——公開契約（抽象方法）、公開預設實作、私有輔助邏輯、靜態工廠，一應俱全。但**能力變多不代表該把介面當抽象類別用**：介面仍然沒有實例狀態，一旦邏輯需要記住東西，就是換工具的訊號。實務上比較好的界線是：介面裡的預設與私有方法只做**從其他介面方法推導得出的計算**（例如 `Comparator.thenComparing` 用既有的 compare 組合出新的），不做需要外部資源或狀態的事情。

**面試回答方式**：一句話點出各自解決的問題（預設方法間的重複、工具類別的歸屬），並用 `Collections` 這類伴生類別的歷史成因說明 static 方法的價值。接著給一個界線：**介面的預設與私有方法只做能從其他介面方法推導出的計算**，一旦需要記住狀態就該換成抽象類別或組合。
