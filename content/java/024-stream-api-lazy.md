# 題目

Java Stream 的中間操作和終端操作有什麼差異？什麼是惰性求值（lazy evaluation）？

## 核心答案

Stream 的操作分兩類——「中間操作（intermediate）」如 `filter`、`map`、`sorted`，回傳一個新的 Stream，可以鏈式串接；「終端操作（terminal）」如 `collect`、`forEach`、`reduce`、`count`，會觸發整個 Stream 管線執行並產生最終結果。惰性求值指的是：中間操作不會立即執行，它們只是「記錄下要做什麼」，直到遇到終端操作才真正開始處理資料，且處理是「逐個元素流過整條管線」而非「每個操作處理完整個集合再傳給下一個」，這讓 Stream 能做短路優化、避免不必要的計算。

## 詳細解析

**中間操作 vs 終端操作**：

- **中間操作**：`filter`、`map`、`flatMap`、`sorted`、`distinct`、`limit`、`peek` 等，回傳 Stream，惰性（不立即執行）。
- **終端操作**：`collect`、`forEach`、`reduce`、`count`、`anyMatch`、`findFirst` 等，回傳非 Stream 的結果（或 void），觸發實際執行。
- 一個 Stream 只能有一個終端操作，執行後這個 Stream 就被消耗掉、不能再用。

**惰性求值的含義**：

- 中間操作只是「建構一個處理管線的描述」，不做任何實際處理。例如 `stream.filter(...).map(...)` 這兩行執行完，一個元素都還沒被處理。
- 只有當終端操作被呼叫，整條管線才開始執行。

**逐元素流動（而非分階段處理整個集合）**：這是惰性求值的關鍵優勢。Stream 不是「先對整個集合做完 filter，再對結果整個做 map」，而是「每個元素依次流過 filter→map→終端」，一個元素走完整條管線，下一個元素再開始。這帶來兩個好處：

1. **短路優化**：像 `findFirst`、`anyMatch`、`limit` 這類操作，一旦滿足條件就能立即停止，不需要處理剩餘元素。例如 `stream.filter(...).findFirst()` 找到第一個符合的就停，不會遍歷完整個集合。
2. **避免中間集合**：逐元素流動不需要在每個階段之間建立完整的中間集合，節省記憶體。

**範例說明惰性**：`list.stream().filter(x -> {print(x); return x > 2;}).map(...)` 如果沒有終端操作，那個 `print` 完全不會執行；加上 `.findFirst()` 後，元素才會逐個流過，且找到第一個 >2 的就停止。

## 面試回答方式

先清楚區分中間操作（回傳 Stream、惰性）和終端操作（觸發執行、產生結果），並強調「一個 Stream 只能有一個終端操作、用完即消耗」。惰性求值是這題的核心——要講兩個層次：一是「中間操作不立即執行、遇到終端才執行」，二是更關鍵的「逐元素流過整條管線、而非分階段處理整個集合」，後者才能解釋短路優化和避免中間集合這兩個好處。能用 `filter().findFirst()` 找到就停這個例子說明短路，展現你真正理解惰性求值的機制而非只知道這個詞。

## 常見追問

### Stream 的並行流（parallelStream）什麼時候用、什麼時候不該用？

**核心答案**：並行流適合「資料量大、每個元素的處理是 CPU 密集且互相獨立、且操作本身無狀態無順序依賴」的場景，能利用多核心加速。不該用的情況包括——資料量小（並行的拆分合併開銷超過收益）、操作涉及共享可變狀態（會有執行緒安全問題）、操作有順序依賴或本身是 IO 阻塞（並行不會加速反而可能因共用 ForkJoinPool 互相拖累）。

**詳細解析**：`parallelStream()` 底層用共用的 `ForkJoinPool.commonPool()` 把資料拆分成多段並行處理再合併。它的收益來自多核並行，但也帶來拆分、合併、執行緒協調的開銷。判斷是否該用的關鍵：一是資料量——太小的話並行開銷大於收益，反而更慢；二是每個元素處理的成本——處理越重（CPU 密集）越值得並行，如果只是輕量操作，並行不划算；三是操作的性質——必須是無狀態（不依賴其他元素）、無共享可變狀態（否則要處理執行緒安全，且往共享集合寫入會出錯）、不依賴順序（並行下順序不保證）。特別要避免的是——在並行流的 lambda 中修改外部的共享變數（如往普通 ArrayList 塞資料），這會產生難以重現的並發 bug；以及在並行流中做阻塞 IO，因為共用 commonPool 執行緒有限，會和其他並行任務互相搶佔。

**面試回答方式**：用「該用（大資料量、CPU 密集、獨立無狀態）vs 不該用（小資料、共享可變狀態、順序依賴、IO 阻塞）」的對比回答，並特別警告「lambda 中改共享變數會有並發 bug」「共用 commonPool 導致 IO 任務互相拖累」這兩個具體陷阱。這種能講出明確判斷準則和具體陷阱的回答，展現你有實際使用並行流的經驗和謹慎態度。

### 為什麼說 Stream 的中間操作 peek 不應該用於改變狀態？

**核心答案**：`peek` 的設計初衷是「觀察」流經的元素（主要用於除錯，如印出每個階段的中間值），而不是用來執行有副作用的操作（如修改外部狀態、收集元素）。因為 Stream 的惰性求值和可能的並行執行，`peek` 中的副作用執行時機和次數都不可靠——沒有終端操作時 peek 根本不執行、某些優化下 peek 可能被跳過、並行流中 peek 的執行順序也不確定，所以依賴 peek 做狀態改變會產生不可預測的行為。

**詳細解析**：這體現了 Stream「函數式、無副作用」的設計哲學。`peek` 接受一個 `Consumer`，但它的語意是「在不改變元素的前提下，對每個流經的元素執行一個觀察動作」，典型正當用途是 `.peek(x -> System.out.println("processing: " + x))` 來除錯。問題在於——因為惰性求值，如果沒有終端操作，整條管線包括 peek 都不會執行；某些 JVM 優化（如 Stream 判斷 count 不需要實際遍歷元素時）可能跳過 peek；並行流中 peek 對不同元素的執行是並發的、順序不定的。所以如果你用 peek 去修改一個外部集合、累加一個計數器、或執行有順序要求的副作用，結果會不可靠。正確的做法是——需要收集結果用 `collect`、需要累加用 `reduce`、需要對每個元素執行動作（終端）用 `forEach`，而不是濫用 peek 做這些有狀態的操作。

**面試回答方式**：講清楚「peek 是給觀察/除錯用的，不是給副作用用的」，並解釋「惰性求值 + 可能的優化跳過 + 並行的順序不定，讓 peek 的副作用不可靠」。給出正確替代（collect/reduce/forEach）。這種能講出「為什麼一個看似能做副作用的操作實際上不該這樣用」的回答，展現你理解 Stream 背後的函數式無副作用哲學。

### Stream 為什麼設計成「用完即消耗、不能重複使用」？

**核心答案**：因為 Stream 代表的是「一次性的資料處理管線」而非「可重複遍歷的資料集合」——它在終端操作執行時，會逐元素消耗底層的資料來源並流過管線，執行完這個「流」就結束了。這個設計讓 Stream 能支援惰性求值、逐元素流動、以及處理「無限流（Rate Limiting）」或「一次性資料來源」（如讀取一個檔案流），如果允許重複使用，這些能力就難以保證。想重複處理應該重新從資料來源建立一個新的 Stream。

**詳細解析**：Stream 和 Collection 的定位根本不同——Collection 是「儲存資料的容器」，可以反覆遍歷；Stream 是「對資料的一次性運算描述」，強調的是「處理過程」而非「儲存」。這個「一次性」的設計是有意的：一是支援惰性和短路——Stream 可以連接到一個「無限的資料來源」（如 `Stream.iterate` 生成無限序列）或「只能讀一次的來源」（如網路流、檔案流），對這些來源「重複使用」根本沒有意義或不可能；二是逐元素流動的執行模型下，元素被消耗後就不再保留，沒有「回到開頭重來」的狀態。所以 Stream 用終端操作後就標記為已消耗，再次操作會拋 `IllegalStateException`。如果確實需要對同一批資料做多次不同的 Stream 處理，正確做法是保留原始的資料來源（如 List），每次需要時 `list.stream()` 重新建立一個新的 Stream。

**面試回答方式**：抓住「Stream 是一次性的運算管線、不是可重複遍歷的容器」這個定位差異，並說明這個設計是為了支援「無限流、一次性來源、惰性求值」。點出「想重複處理就從資料來源重新建立 Stream」的正確做法。這種能從「Stream 與 Collection 的本質定位差異」來解釋設計決策的回答，展現你對 Stream 的理解上升到了設計哲學層面。
