# 題目

`parallelStream()` 在什麼條件下才會比循序快？為什麼在 Web 應用裡用它常常是錯的？

## 核心答案

平行串流要划算，需要四個條件同時成立：**資料量夠大**（通常至少上萬筆，實際門檻取決於每筆的處理成本）、**每筆的處理成本夠高**（否則拆分與合併的開銷吃掉全部收益）、**資料來源易於切分**（`ArrayList` 與陣列可以 O(1) 對半切，`LinkedList` 與 `Stream.iterate` 幾乎切不動）、操作彼此獨立且無共享可變狀態。

在 Web 應用裡它常常是錯的，理由不在單次請求的效能，而在所有平行串流預設共用同一個 `ForkJoinPool.commonPool`，執行緒數是 CPU 核心數減一。這代表：一個慢請求的平行任務會佔住共用池、影響其他請求；池裡如果混進阻塞操作（IO、鎖、資料庫查詢），整個 JVM 的平行串流都會被拖住。而且 Web 伺服器本來就已經用多執行緒同時處理多個請求，CPU 早就被餵飽了，再切分只是增加排程與快取失效的成本。

一句話的判斷：平行串流是為「單一使用者、大量 CPU 密集計算」設計的，不是為「大量並行請求」設計的。

## 詳細解析

**拆分能力由 Spliterator 決定**，這是最常被忽略的因素。`ArrayList` 與陣列的 spliterator 可以精確對半切（回報 `SIZED` 與 `SUBSIZED`），負載天然均衡；`HashMap` 可以依桶切分，還算可以；`LinkedList` 只能一邊走一邊切，`BufferedReader.lines()` 與 `Stream.iterate` 則幾乎無法有效拆分——對這些來源用 `parallel()` 通常會比循序更慢，因為主執行緒仍然要序列地走過資料，還多付了任務排程成本。

**共用池的問題有具體的表現**：`commonPool` 的並行度預設是 `可用處理器數 - 1`，在 4 核機器上只有 3 個工作執行緒。如果某個請求提交了一批帶有阻塞 IO 的平行任務，這 3 個執行緒全部被佔住，其他請求的平行串流會排隊等待——而它們甚至不知道自己在等誰。要隔離的話可以把串流操作提交到自訂的 `ForkJoinPool` 執行（`myPool.submit(() -> stream.parallel()...).get()`），這利用了「ForkJoinTask 在哪個池裡執行就用哪個池」的行為，但這是一個依賴實作細節的技巧，寫在程式碼裡需要註解說明。

共享可變狀態是最危險的錯誤：`stream.parallel().forEach(x -> list.add(x))` 會產生資料競爭，結果可能少元素、可能拋例外、也可能什麼事都沒有——在測試環境跑一百次都對，上線後偶爾錯。正確做法是用 `collect` 讓框架處理合併。同理，`forEach` 在平行時**不保證順序**，需要順序要用 `forEachOrdered`，但那會讓平行的收益打折。

**量測是唯一可靠的判斷方式**，而且要用 JMH 而不是 `System.nanoTime` 圍一圈——JIT 預熱、死碼消除、迴圈展開都會讓天真的量測得出完全錯誤的結論。實務上更常見的正確答案是：與其平行化一個串流，不如先看看演算法或資料結構有沒有更好的選擇。把 O(n²) 改成 O(n log n) 的收益遠大於在多核上平行一個爛演算法。

## 面試回答方式

先給**四個必要條件**（資料量、單筆成本、可切分性、無共享狀態），這比籠統說「資料大才用」精確。接著把重點放在 Web 場景的真正理由——共用 `ForkJoinPool.commonPool`：一個慢任務影響全 JVM、混入阻塞操作會拖垮所有平行串流，而且 Web 伺服器本來就用多執行緒把 CPU 餵飽了。用一句話定位：平行串流是為單一使用者的大量計算設計的，不是為大量並行請求設計的。加分點有三個：**Spliterator 決定拆分能力**（`LinkedList` 與 `Stream.iterate` 幾乎切不動）、共享可變狀態的錯誤**在測試環境測不出來**、以及量測要用 JMH。最後收在一個更高的判斷：先檢查演算法，改複雜度的收益遠大於平行化。

## 講稿

平行串流要划算，需要四個條件同時成立。資料量夠大、每筆的處理成本夠高、資料來源容易切分、還有操作彼此獨立沒有共享可變狀態。

可切分性最容易被忽略。陣列跟 ArrayList 可以精確對半切，負載天然均衡。但 LinkedList 只能一邊走一邊切，逐行讀檔更是幾乎切不動。對這些來源用平行，通常比循序還慢。

在 Web 應用裡我通常不用它，理由不是單次請求的效能。所有平行串流預設共用同一個池，執行緒數是核心數減一。一個慢任務會佔住整個池、影響其他請求，如果裡面混進阻塞的 IO，整個 JVM 的平行串流都會被拖住。

而且 Web 伺服器本來就用多執行緒同時處理很多請求，CPU 早就被餵飽了，再切分只是增加排程跟快取失效的成本。

我會這樣定位它。平行串流是為單一使用者的大量計算設計的，不是為大量並行請求設計的。真的要調效能，我會先看演算法，改複雜度的收益遠大於平行化。

## 常見追問

### 為什麼 forEach 在平行串流裡不保證順序？

**核心答案**：因為平行的本質就是各段獨立完成、完成時間不確定。`forEach` 的契約明確寫著它「顯式地不保證遵守遭遇順序（encounter order），因為那會犧牲平行的好處」。需要順序時用 `forEachOrdered`，它會強制按原順序處理——代價是後完成的段必須等前面的段，平行度被壓縮，在某些情況下甚至退化成接近循序。

**詳細解析**：更根本的問題是在串流裡做副作用本身就值得懷疑。`forEach` 帶副作用的寫法（寫入外部集合、印出、送請求）繞過了串流的設計意圖——串流是為了描述「資料怎麼變換」，最終結果應該由 `collect` 或 `reduce` 產生。用 `collect` 的話順序問題由框架處理（`toList` 保證遭遇順序），也不會有資料競爭。所以遇到「平行 forEach 順序不對」時，通常真正的解法是換成 collect，而不是換成 forEachOrdered。另外要注意：即使是循序串流，`forEach` 也只是「實務上」照順序，`forEachOrdered` 才是有契約保證的。

**面試回答方式**：先給契約層面的答案（`forEach` 明確不保證，`forEachOrdered` 保證但壓縮平行度），再把問題往上提一層：在串流裡做副作用本身就是設計訊號，真正的解法多半是換成 `collect` 讓框架處理順序與合併。最後補一個精確的細節：循序串流的 `forEach` 也只是實務上有序，沒有契約保證。

### 怎麼把平行串流跑在自訂的執行緒池裡？

**核心答案**：把整個串流操作包成一個任務提交給自訂的 `ForkJoinPool`：`pool.submit(() -> list.parallelStream().map(...).collect(...)).get()`。原理是 `ForkJoinTask` 在執行時會使用**當前所在的池**來 fork 子任務，所以串流的拆分會落在自訂池裡而不是 `commonPool`。用完記得關閉池，並處理 `get()` 的 `InterruptedException` 與 `ExecutionException`。

**詳細解析**：這個技巧有效但依賴的是實作行為而非公開契約，JDK 文件沒有承諾它，所以應該加註解說明並在升級 JDK 時驗證。更重要的是**它解決不了根本問題**——如果任務裡有阻塞 IO，ForkJoinPool 本來就不適合（它的工作竊取假設任務是 CPU 密集且不阻塞的；阻塞會讓工作執行緒閒置卻不釋放）。這種情況正確的工具是一般的 `ThreadPoolExecutor`（可以開比核心數多得多的執行緒）或虛擬執行緒。所以看到「想把平行串流放進自訂池」這個需求時，值得先確認任務到底是 CPU 密集還是 IO 密集，後者根本不該用平行串流。

**面試回答方式**：給出具體寫法與原理（ForkJoinTask 使用當前所在的池），並誠實標註它依賴實作行為而非公開契約。真正的加分點是把問題往回推：這個需求常常來自 IO 密集的任務，而那根本不該用平行串流——ForkJoinPool 的工作竊取假設任務不阻塞，該用一般執行緒池或虛擬執行緒。

### 平行串流的效能怎麼量才可信？

**核心答案**：用 **JMH**。天真的量測（`nanoTime` 前後夾一段程式碼）會被三件事破壞：**JIT 預熱**（前幾千次呼叫走解譯器，比穩態慢一個數量級）、**死碼消除**（結果沒被使用時 JIT 可能整段刪掉）、**常數摺疊**（輸入是常數時整段計算可能在編譯期完成）。JMH 用預熱迭代、黑洞（`Blackhole`）消費結果、與 `@State` 隔離輸入來處理這三件事。

**詳細解析**：即使用了 JMH，平行的量測仍有額外的陷阱。微基準測試獨佔整台機器，生產環境不會——基準測出 4 倍加速，但在同時處理 200 個請求的伺服器上可能是負收益，因為那時 CPU 早就飽和。所以平行的決策必須在接近生產的負載下驗證，或至少在基準裡模擬背景負載。另外要注意 GC 的影響：平行版本常常配置更多暫時物件（每段一個容器），在堆積吃緊時 GC 成本會蓋過平行收益，這在短促的基準測試裡看不出來。「基準快、線上慢」在平行化上特別常見，因為它改變的正是資源競爭的結構。

**面試回答方式**：先給 JMH 與它處理的三個問題（預熱、死碼消除、常數摺疊），這說明你知道天真量測為什麼不可信。然後給更關鍵的一層：微基準獨佔機器、生產環境不會，所以平行的決策必須在接近生產的負載下驗證。補上 GC 這個在短基準裡看不見的成本，收在一句話：平行化改變的是資源競爭結構，所以「基準快、線上慢」特別常見。
