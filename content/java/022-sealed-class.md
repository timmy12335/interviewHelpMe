# 題目

密封類別（sealed class）是什麼？它解決了什麼問題？和 final 有什麼不同？

## 核心答案

密封類別（JDK 17 正式）是一種「限制哪些類別可以繼承/實作它」的機制——用 `sealed` 修飾並透過 `permits` 明確列出允許的子類別，只有被列出的類別才能繼承它。它介於 `final`（完全禁止繼承）和普通類別（任何類別都能繼承）之間，讓你能「開放繼承但精確控制繼承的範圍」。主要價值是——建立一個「封閉的、已知全部子類別」的型別階層，配合 switch 的模式匹配能做到「窮盡檢查」，讓編譯器確保你處理了所有可能的子型別。

## 詳細解析

**基本語法**：

```java
public sealed interface Shape permits Circle, Rectangle, Triangle {}
public final class Circle implements Shape {}
public final class Rectangle implements Shape {}
public final class Triangle implements Shape {}
```

`Shape` 用 `sealed` 修飾並 `permits` 列出唯三允許的實作者，其他任何類別都不能實作 `Shape`。

**子類別的三種選擇**：被 permits 允許的子類別，必須明確宣告自己的「繼承開放程度」：

- `final`：不再允許被繼承（封閉這條分支）。
- `sealed`：繼續密封，再用 permits 列出自己允許的子類別。
- `non-sealed`：重新開放，任何類別都能繼承它（打破密封）。

**解決什麼問題**：

1. **精確控制型別階層**：以前只有「final（誰都不能繼承）」和「開放（誰都能繼承）」兩個極端，密封類別提供了中間選項——「只允許我指定的這幾個類別繼承」，適合表達一組「已知且封閉的變體」（如「圖形只有圓、矩形、三角形這三種」）。
2. **配合模式匹配的窮盡檢查**：因為編譯器知道 `Shape` 的所有可能子型別，在 switch 中對 Shape 做模式匹配時，如果你涵蓋了所有子型別，就不需要寫 `default` 分支；如果漏掉了某個，編譯器會報錯提醒——這種「窮盡性檢查」讓程式碼更安全。

**和 final 的差異**：`final` 是「完全禁止繼承」，密封類別是「允許繼承但限定範圍」。密封類別讓你能建立一個「可擴展但受控」的階層，而 final 直接關閉了擴展的可能。

## 面試回答方式

先講「是什麼」——用 sealed + permits 精確控制哪些類別能繼承。核心是把它定位在「介於 final（禁止繼承）和開放（任意繼承）之間的中間選項」，這個定位能一句話說清它的價值。接著講它最重要的應用——「配合 switch 模式匹配的窮盡檢查」，這是密封類別在現代 Java 中真正發光的地方（編譯器能確保你處理了所有子型別）。如果能提到子類別必須選擇 final/sealed/non-sealed 這個細節，展現你了解完整的機制。

## 常見追問

### 密封類別如何配合 switch 模式匹配實現窮盡檢查？

**核心答案**：因為密封類別的所有子型別是編譯期已知且封閉的，當你在 switch 中對一個密封型別做模式匹配（switch pattern matching，JDK 21 正式），如果你的 case 已經涵蓋了所有被 permits 的子型別，編譯器就認為這個 switch 是「窮盡的」，不需要寫 `default` 分支；反之如果你漏掉了某個子型別，編譯器會直接報錯，強制你處理所有情況。這讓「新增一個子型別後忘記在某處處理它」這類 bug 能在編譯期就被抓出來。

**詳細解析**：這是密封類別與模式匹配結合的殺手級應用。傳統上，對一個開放的型別階層做 switch/if-else 分派時，你必須寫 `default` 分支處理「未預期的型別」，但這個 default 往往掩蓋了「你其實漏處理了某個已知型別」的問題；而且當有人新增了一個子型別，所有處理這個階層的 switch 都可能默默地走進 default 而出錯，編譯器不會提醒。密封類別改變了這一切——因為子型別是封閉已知的，編譯器能檢查你的 switch 是否涵蓋了全部，涵蓋全部就不用 default，漏了就編譯錯誤。這帶來的好處是：當你未來給 `Shape` 新增一個 `Hexagon`，所有對 Shape 做窮盡 switch 的地方都會立刻編譯失敗，逼你去補上處理 Hexagon 的邏輯——這種「編譯器強制你處理所有情況」的安全性，是函數式語言（如 Scala、Rust）的代數資料型別（ADT）帶來的優勢，Java 透過 sealed + record + 模式匹配也達到了類似的能力。

**面試回答方式**：講清楚「子型別封閉已知 → 編譯器能檢查 switch 是否窮盡 → 涵蓋全部不用 default、漏了就編譯錯」這個機制，並強調它的價值——「新增子型別時，所有沒處理它的地方會編譯失敗、逼你補上」。能連結到「這是 Scala/Rust 的代數資料型別帶給 Java 的能力」，展現你有跨語言的視野，理解這個特性的設計淵源。

### sealed、final、non-sealed 三種修飾符分別代表什麼？

**核心答案**：對於一個密封類別 permits 的子類別，它必須從三者中選一個來宣告自己的繼承策略——`final` 表示「這條繼承分支到此為止，我不再被任何類別繼承」；`sealed` 表示「我繼續密封，再用 permits 指定我允許的下一層子類別」；`non-sealed` 表示「我打破密封，重新開放，任何類別都可以繼承我」。這三個選項讓你能精確控制型別階層每一層的開放程度。

**詳細解析**：Java 強制密封類別的子類別明確表態，是為了讓整個型別階層的「封閉性」是明確且可控的，不留模糊地帶。`final` 讓某個子型別成為葉節點，階層在此封閉。`sealed` 讓密封性向下延伸——你可以建立多層的密封階層（例如 `Shape` 密封為 `Polygon` 和 `Circle`，`Polygon` 再密封為 `Triangle` 和 `Rectangle`）。`non-sealed` 則是一個「逃生口」——當你希望某個子型別之下仍然開放給任意擴展（例如提供給第三方繼承）時使用，它主動放棄了密封帶來的窮盡檢查等好處，換取開放性。這三個選項的存在，讓密封機制既能建立嚴格封閉的階層，也能在需要時局部開放，具有很好的靈活性。

**面試回答方式**：清楚對應三者——final（封閉這條分支）、sealed（繼續向下密封、可多層）、non-sealed（重新開放給任意繼承）。能說明「Java 強制子類別表態是為了讓封閉性明確可控」以及「non-sealed 是需要局部開放時的逃生口」，展現你理解這個機制設計的完整性和靈活性。

### 密封類別和列舉（enum）在「表達封閉集合」上有什麼區別？

**核心答案**：兩者都能表達「一組封閉的、已知的變體」，但層次不同——`enum` 表達的是「固定的一組『實例』」（例如一週有七天，就是七個固定的列舉常數，是值層級的封閉）；密封類別表達的是「固定的一組『子型別』」（例如圖形只有圓/矩形/三角形這三種類別，每種類別還能各自有不同的欄位和無限多個實例，是型別層級的封閉）。當每個變體需要攜帶不同結構的資料時用密封類別，當變體只是一組固定的無狀態常數時用列舉。

**詳細解析**：關鍵區別在於「變體是否需要不同的資料結構」。`enum` 的每個常數本質上是同一個型別的固定實例，適合「星期幾」「訂單狀態」這種每個變體結構相同、只是不同的具名常數的場景。但如果每個變體需要攜帶不同的欄位——例如「圓形有半徑、矩形有長寬、三角形有三邊」——列舉就不適合了（列舉的所有常數是同型別，硬要塞不同欄位會很彆扭）。密封類別配合 record 就完美——`sealed interface Shape permits Circle, Rectangle`，`Circle` 有 radius、`Rectangle` 有 width/height，每個子型別有自己的結構，又是封閉的一組，還能做窮盡的模式匹配。所以判斷準則是：變體只是「一組固定的具名值」用 enum；變體是「一組結構各異但封閉的型別」用 sealed（通常配合 record）。

**面試回答方式**：用「enum 是封閉的一組『實例/值』、sealed 是封閉的一組『子型別』」這個層次區別回答，並用「圖形」例子說明「當每個變體要攜帶不同資料結構時該用 sealed 而非 enum」。能點出「sealed + record + 模式匹配」的組合，展現你理解這幾個現代 Java 特性如何協同表達代數資料型別，是很有深度的回答。
