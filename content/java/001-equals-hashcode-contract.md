# 題目

為什麼覆寫 `equals()` 時一定要一起覆寫 `hashCode()`？它們之間有什麼契約？

## 核心答案

Java 規定：如果兩個物件 `equals()` 相等，它們的 `hashCode()` 必須相同；反之則不強制（`hashCode()` 相同的兩個物件不一定 `equals()` 相等，這是允許的雜湊衝突）。如果只覆寫 `equals()` 而不覆寫 `hashCode()`，會導致「邏輯上相等的兩個物件有不同的雜湊碼」，使得它們在 `HashMap`、`HashSet` 這類基於雜湊的容器中無法被正確地當成同一個 key，出現「明明放進去了卻查不到」的 bug。

## 詳細解析

**兩條契約規則**：

1. **一致性**：如果 `a.equals(b)` 為 true，則 `a.hashCode() == b.hashCode()` 必須為 true。
2. **反向不強制**：`a.hashCode() == b.hashCode()` 時，`a.equals(b)` 不一定為 true（不同物件雜湊碼相同稱為雜湊衝突，是允許且必然會發生的）。

**只覆寫 equals 不覆寫 hashCode 的後果**：以 `HashMap` 為例，查找一個 key 的流程是「先用 `hashCode()` 定位到某個桶，再在桶內用 `equals()` 逐一比對」。如果兩個邏輯相等的物件雜湊碼不同，它們會被分配到不同的桶，`equals()` 根本沒有機會被呼叫來判斷相等，於是 `map.get(邏輯相等的另一個物件)` 會回傳 null，`set.contains(邏輯相等的物件)` 會回傳 false，即使你「明明放進去過」。

**為什麼反向不強制**：因為雜湊碼是把一個可能有無限多種值的物件，映射到有限的 int 範圍（約 42 億個值），根據鴿籠原理，不同物件必然會有雜湊碼相同的情況，這是雜湊本質上無法避免的。容器的設計已經考慮到這點——雜湊只負責快速縮小範圍（定位桶），最終的相等判斷仍然交給 `equals()`。

**實作建議**：`equals()` 中用到哪些欄位判斷相等，`hashCode()` 就應該用同一組欄位計算，才能保證一致性。現代 Java 通常用 `Objects.equals()` 與 `Objects.hash()` 輔助實作，或直接用 `record`（自動生成符合契約的 `equals`/`hashCode`）、IDE 生成、Lombok 的 `@EqualsAndHashCode` 等工具避免手寫出錯。

## 面試回答方式

先講清楚「契約是什麼」——用「equals 相等則 hashCode 必須相等，反之不強制」這一句話點出雙向的不對稱性，這是這題的核心。接著一定要用「HashMap 查找流程」這個具體例子說明「不遵守契約會發生什麼 bug」，因為面試官真正想確認的是你理解「為什麼」，而不只是背「要一起覆寫」這條規則。最後補一句實務做法（用 `record`、`Objects.hash()` 或 IDE 生成避免手寫出錯），展現你知道實際開發中怎麼正確落地。

## 常見追問

### 為什麼 hashCode() 相同但 equals() 不同是被允許的？

**核心答案**：因為雜湊碼是把物件映射到有限的 int 範圍（約 42 億個值），而物件的可能狀態是無限的，根據鴿籠原理，不同的物件必然會出現雜湊碼相同的情況（雜湊衝突），這是雜湊機制本質上無法避免的，因此契約只能要求「相等物件雜湊碼必須相同」，而不能反過來要求「雜湊碼相同的物件必須相等」。

**詳細解析**：如果契約反過來也強制（雜湊碼相同就必須相等），那等於要求雜湊函式是一個完美的、無衝突的映射，這在數學上對於無限輸入空間映射到有限輸出空間是不可能做到的。雜湊容器的設計正是建立在「衝突會發生」這個前提上——它用雜湊碼快速定位到一個桶（縮小搜尋範圍），桶內若有多個雜湊碼相同的元素，再用 `equals()` 精確比對。一個好的 `hashCode()` 實作目標不是「絕對無衝突」（做不到），而是「盡量讓元素均勻分散到各個桶」，減少單一桶內的衝突數量以維持查找效率。

**面試回答方式**：用「鴿籠原理」點出「無限映射到有限必然衝突」這個數學本質，再說明「容器設計本來就假設會衝突，所以用 equals 做最終判斷」，展現你理解雜湊的底層原理而不只是背契約條文。

### 如果 hashCode() 永遠回傳同一個常數，程式會出錯嗎？

**核心答案**：不會出錯（功能仍然正確），但效能會嚴重劣化。因為所有物件的雜湊碼都相同，它們會全部被分配到 `HashMap` 的同一個桶裡，使得雜湊表退化成一條長鏈結串列（或紅黑樹），查找複雜度從理想的 O(1) 退化到 O(n)（或 O(log n)），完全喪失了雜湊表的效能優勢。

**詳細解析**：回傳固定常數的 `hashCode()` 仍然滿足契約（相等的物件雜湊碼確實相同——因為全部都相同），所以 `HashMap`/`HashSet` 的正確性不受影響，放得進去也查得到。問題純粹在效能：雜湊表的核心價值是靠雜湊碼把元素均勻分散到不同桶，讓每個桶只有極少數元素，達到接近 O(1) 的查找；如果所有元素擠在同一個桶，就退化成線性搜尋。這也說明了「滿足契約」只是正確性的最低要求，一個「好的」`hashCode()` 還需要讓雜湊值盡量均勻分布，這是正確性之外的效能考量。

**面試回答方式**：先明確回答「不會出錯但效能會爆掉」，把「正確性」和「效能」兩個層面分開講，再解釋「所有元素擠同一個桶導致退化成 O(n)」的具體原因，這種能區分「滿足契約（正確）」與「良好實作（高效）」兩個層次的回答，比只說「會變慢」更有深度。

### 可變物件當作 HashMap 的 key 有什麼風險？

**核心答案**：如果一個可變物件被當成 `HashMap` 的 key 放入後，又修改了它參與 `hashCode()` 計算的欄位，會導致它的雜湊碼改變，使得後續用這個 key 去查找時，`HashMap` 根據新的雜湊碼定位到的桶，和當初存入時（用舊雜湊碼）所在的桶不一致，於是「查不到自己」，造成資料實質上遺失在 map 中。

**詳細解析**：`HashMap` 在存入 key-value 時，是根據存入當下 key 的雜湊碼決定它放在哪個桶；如果之後這個 key 物件的欄位被修改導致雜湊碼變了，`HashMap` 並不會自動把它搬到新雜湊碼對應的桶（`HashMap` 完全不知道 key 被改了）。於是這個 entry 依然物理上待在舊桶裡，但當你拿「已被修改的 key」去 `get()` 時，`HashMap` 用新雜湊碼去找新桶，找不到，回傳 null；而這個 entry 也很難再被正常存取到，形同記憶體洩漏（Memory Leak）。這就是為什麼強烈建議用不可變物件（如 `String`、`Integer`、或欄位都是 `final` 的物件）當作 `HashMap` 的 key——它們的雜湊碼在生命週期內恆定，不會發生這種問題。

**面試回答方式**：用「存入時用舊雜湊碼放桶、修改後用新雜湊碼找桶、兩者不一致所以查不到」這個因果鏈清楚說明風險，再給出「用不可變物件當 key」的最佳實踐，展現你不只知道規則，還理解可變性與雜湊容器之間的深層衝突。
