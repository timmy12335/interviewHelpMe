# 題目

Lambda 表達式編譯之後變成什麼？為什麼不直接編譯成匿名類別？

## 核心答案

Lambda **不會**在編譯期被轉成匿名類別。編譯器做兩件事：把 lambda 的主體抽成當前類別的一個**私有靜態（或實例）合成方法**（名字像 `lambda$main$0`），然後在原本的位置放一條 **`invokedynamic`** 指令，指向一個叫做 `LambdaMetafactory.metafactory` 的**引導方法（bootstrap method）**。

真正的實作類別是在**執行期首次執行到那條指令時**才由 `LambdaMetafactory` 動態生成的——它生成一個實作了目標函式介面的類別，其唯一方法轉呼叫那個合成方法。生成之後這個呼叫點被**連結（link）**起來，之後每次執行都直接走已連結的目標，成本與一般方法呼叫相當。

不直接編譯成匿名類別的理由有三個：**避免類別檔爆炸**（每個 lambda 一個 class 檔）、**保留實作策略的彈性**（生成方式可以在未來的 JDK 改進而不必重新編譯程式碼）、以及**允許最佳化**（無捕獲的 lambda 可以重用單一實例，不必每次配置）。

## 詳細解析

**invokedynamic 是這裡的關鍵機制**：它是 JDK 7 為動態語言引入的位元組碼指令，語意是「**第一次執行時呼叫引導方法決定要呼叫誰，之後就固定下來**」。這讓「呼叫點的具體目標」從編譯期決定改成執行期決定一次。Lambda 借用了它——編譯期只寫下「我要一個實作某函式介面的物件，行為在那個合成方法裡」，具體怎麼生成留給執行期。

**捕獲與否決定了配置行為**：無捕獲的 lambda（不引用任何外部變數與 `this`）是無狀態的，`LambdaMetafactory` 生成的類別會有一個單例實例，每次求值都回傳同一個物件。有捕獲的 lambda 則需要把捕獲的值存進實例欄位，所以**每次求值都要建立新實例**。這就是為什麼在熱迴圈裡寫有捕獲的 lambda 會產生配置壓力，而無捕獲的不會。**判斷方式是看 lambda 主體有沒有用到外部的東西**。

**方法引用比 lambda 更接近直接呼叫**：`String::length` 這類引用不需要生成一個轉呼叫的合成方法，`LambdaMetafactory` 可以直接把介面方法連到目標方法上，少一層間接。這在超熱的路徑上有可量測的差別，也是「能用方法引用就用方法引用」這條風格建議背後的技術理由（雖然主要理由仍是可讀性）。

**這個設計的代價出現在啟動時間與堆疊追蹤**：每個 lambda 呼叫點首次執行時都要跑一次引導、生成類別、連結，這在有數千個 lambda 的大型應用啟動時是可觀的成本——這正是 AOT 編譯與 CDS（類別資料共享）要解決的問題之一，GraalVM 原生映像檔則在建置期就把 lambda 具現化。另一個代價是**堆疊追蹤變髒**：例外堆疊裡會出現 `lambda$foo$0` 這類合成名稱，中間還可能夾著 `LambdaMetafactory` 生成的框架，除錯體驗不如具名類別。

## 面試回答方式

先破除最常見的誤解：**lambda 不是語法糖式的匿名類別**。給出兩步編譯結果——主體抽成合成方法、原位置放 `invokedynamic` 指向 `LambdaMetafactory`，實作類別在**執行期首次執行時**生成並連結。接著解釋 `invokedynamic` 的語意（第一次決定目標、之後固定），這是整段的關鍵。然後回答「為什麼不用匿名類別」：**類別檔爆炸、實作策略彈性、允許最佳化**。加分點放兩個具體事實：**無捕獲的 lambda 重用單例、有捕獲的每次新建**，這解釋了熱迴圈裡的配置壓力；以及**方法引用少一層間接**。最後誠實給出代價——首次連結的啟動成本與變髒的堆疊追蹤。

## 講稿

Lambda 不會在編譯期被轉成匿名類別，這是最常見的誤解。編譯器做兩件事，把 lambda 的主體抽成當前類別的一個私有合成方法，然後在原本的位置放一條 invokedynamic 指令，指向一個工廠的引導方法。

真正的實作類別是在執行期才生成的，第一次執行到那條指令的時候動態產生，生成之後呼叫點就連結起來，之後每次執行都直接走已連結的目標。

為什麼不直接編譯成匿名類別？三個理由。避免每個 lambda 都產生一個類別檔、保留實作策略的彈性讓未來的 JDK 可以改進、還有允許最佳化。

最實際的最佳化是這樣。沒有捕獲外部變數的 lambda 是無狀態的，工廠會重用同一個實例。有捕獲的才需要每次建立新物件。所以在熱迴圈裡寫有捕獲的 lambda 會有配置壓力，無捕獲的不會。

代價也要講。每個 lambda 呼叫點首次執行都要跑一次引導跟生成，大型應用啟動時是可觀的成本，這正是原生映像檔要解決的問題之一。

## 常見追問

### 什麼是函式介面？為什麼需要 @FunctionalInterface 註解？

**核心答案**：函式介面是**只有一個抽象方法**的介面（預設方法、靜態方法、以及覆寫自 `Object` 的 public 方法如 `equals`、`toString` 都不計入）。它是 lambda 的目標型別——編譯器靠「唯一的抽象方法」推導出 lambda 的參數與回傳型別。`@FunctionalInterface` **不是必要的**，任何符合條件的介面都能當 lambda 目標；它的作用是**讓編譯器強制檢查**，之後有人再加第二個抽象方法時立刻編譯失敗，而不是等到所有使用它的 lambda 都壞掉才發現。

**詳細解析**：這個註解的價值在**表達意圖**——它宣告「這個介面被設計成 lambda 目標，這是它契約的一部分」。沒有註解的話，介面作者可能不知道有人拿它當函式介面用，一次善意的擴充就會破壞下游。`Object` 的 public 方法不計入抽象方法數，是為了讓 `Comparator` 這種同時宣告了 `compare` 與 `equals` 的介面仍然算函式介面——因為任何類別都已經從 `Object` 繼承了 `equals` 的實作，它不是真正需要被實作的方法。**這個規則看起來像特例，其實是「抽象方法」定義的自然結果**。

**面試回答方式**：先給定義並精確說明哪些方法不計入。重點放在註解的作用是**強制檢查與表達意圖**而非必要條件，並說明沒有它的風險：介面作者不知情地加第二個抽象方法，會一次打壞所有下游的 lambda。加分點是解釋 `Object` 方法為什麼不計入，並用 `Comparator` 舉例——這顯示對規則背後理由的理解。

### 為什麼 lambda 不能修改捕獲的區域變數，卻可以修改捕獲的物件內容？

**核心答案**：因為捕獲的是**變數的值**，而對物件來說值就是引用。捕獲一個 `int` 時複製的是那個數字，之後改原變數不會影響已複製的那份，所以 Java 直接禁止修改以避免語意分裂；捕獲一個 `List` 時複製的是引用，**兩邊指向同一個物件**，所以 `add` 的效果雙方都看得到。這與方法參數的值傳遞是完全一樣的規則。

**詳細解析**：這個一致性是刻意的——Java 讓「捕獲」與「傳參」遵循同一套語意，就不必記兩套規則。但它帶來一個併發上的陷阱：**捕獲的可變物件是共享狀態**。把 lambda 交給平行串流或執行緒池時，如果它修改捕獲的 `ArrayList`，那就是多執行緒同時寫入一個非執行緒安全的容器，結果不可預期。編譯器不會警告，因為 effectively final 的檢查只看重新賦值。**所以「lambda 能通過編譯」離「lambda 在併發下正確」還有很遠**，這是實務上真正會出事的地方。

**面試回答方式**：先把規則統一成一句話——**捕獲的是值，物件的值就是引用**，並指出這與方法參數的值傳遞是同一套語意。然後把答案推進到真正有價值的地方：捕獲的可變物件是共享狀態，交給平行串流時就是多執行緒寫入非安全容器，而 effectively final 檢查完全看不到這件事。收在一句判斷：能通過編譯離併發正確還很遠。

### invokedynamic 除了 lambda 還用在哪裡？

**核心答案**：JDK 內部至少還有三處。**字串串接**（JDK 9 起）——`"a" + b` 不再編譯成 `StringBuilder` 的呼叫鏈，而是一條 `invokedynamic` 指向 `StringConcatFactory`，執行期依實際型別組合出最佳策略。**Record 的 equals、hashCode、toString**——編譯成 `invokedynamic` 指向 `ObjectMethods.bootstrap`，由執行期依元件清單生成實作，所以 record 的 class 檔裡看不到這三個方法的實際邏輯。**switch 的模式比對**（JDK 21）——型別測試的分派也走 `invokedynamic`。

**詳細解析**：這些用法有共同的模式：**把「怎麼做」的決定從編譯期推遲到執行期，讓 JDK 可以在不重新編譯使用者程式碼的前提下改進實作**。字串串接是最好的例子——JDK 9 換掉策略之後，用舊 JDK 編譯的程式碼在新 JVM 上跑不會變快，但重新編譯後就自動享受到新策略，而且未來再改進也不需要改編譯器。代價同樣是**首次執行的連結成本**與**除錯時多一層間接**，這也是為什麼有 `-Djava.lang.invoke.stringConcat=inline` 這類選項可以退回舊行為。**能講出這個「延後決定」的共同模式，比列舉三個使用處更有價值**。

**面試回答方式**：列出三個具體使用處（字串串接、record 的三個方法、模式比對分派），每個一句話。然後歸納出共同模式——**把實作策略的決定從編譯期推遲到執行期**，並用字串串接說明它的實際收益：JDK 換策略時使用者只要重新編譯就受惠，編譯器不必改。最後補上代價（首次連結、除錯多一層）以顯示判斷是雙面的。
