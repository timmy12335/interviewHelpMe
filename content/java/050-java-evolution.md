# 題目

Java 8 之後最重要的變化是什麼？如果要說服團隊從 8 升到 21，你會怎麼論證？

## 核心答案

演進有**四條主線**，理解它們比背版本號有用得多。

**第一條是「讓資料型別變便宜」**——`record`（16）、`sealed`（17）、模式比對（21）合起來讓「用型別表達領域概念」的成本大幅下降，配合窮盡性檢查把一整類遺漏從執行期移到編譯期。

**第二條是「讓併發變便宜」**——虛擬執行緒（21）讓「一個任務一個執行緒」的簡單寫法重新可行，不必為了擴展性改寫成回呼或反應式風格；結構化併發與作用域值繼續補上生命週期與上下文傳遞。

第三條是「讓 JVM 適應現代硬體與部署形態」——G1 成為預設、ZGC 與 Shenandoah 把停頓壓到毫秒以下且與堆積大小脫鉤、容器感知（正確讀取 cgroup 限制）、CDS 與 AOT 改善啟動。

**第四條是「把平台整理乾淨」**——模組化封住內部 API、移除過時元件、新的六個月發布節奏加上 LTS。

升級的論證應該落在**具體收益**而不是「版本比較新」：**JDK 8 已無公開更新**（安全性）、GC 停頓從數百毫秒降到個位數毫秒（延遲）、**同樣的硬體吞吐提升**（成本）、以及**虛擬執行緒讓程式碼變簡單**（維護性）。

## 詳細解析

相容性是 Java 最大的資產，也是升級成本的來源。JDK 8 到 9 的斷點主要是模組化封住內部 API——用了 `sun.misc.Unsafe`、`com.sun.*` 或依賴反射硬闖 JDK 內部的函式庫會壞掉。實際的升級障礙幾乎都在依賴而不是自己的程式碼：舊版的位元組碼操作函式庫（ASM、CGLIB、Javassist）不認得新的 class 檔版本，會在啟動時拋出難懂的錯誤。所以升級的第一步是**盤點並更新依賴**，而不是改自己的程式碼。

**JDK 17 是實務上最重要的一站**：它是 8 之後第一個被生態系廣泛採納的 LTS，Spring Boot 3 直接要求 17 起跳。從 8 升到 17 拿到的是 `record`、`sealed`、文字區塊、switch 表達式、`var`，以及 ZGC 與容器感知。從 17 再到 21 主要是為了虛擬執行緒與模式比對——如果服務是 IO 密集且用阻塞式寫法，虛擬執行緒的收益可以很大。

新的發布節奏改變了升級的心理成本：六個月一版、每兩到三年一個 LTS，每版的改動量小得多。這讓「持續小步升級」比「五年跳一次大版」便宜——後者要一次面對所有斷點，而且沒有中間狀態可以驗證。**預覽功能（preview features）** 也是這個節奏的一部分：語言功能先以預覽發布收集回饋（字串模板就是在預覽後被撤回重新設計的），正式版才穩定下來。

該誠實承認的是「並非每個新功能都該用」：`var` 用過頭會傷可讀性、模式比對用在該用多型的地方會讓型別檢查散落各處、虛擬執行緒在 CPU 密集任務上沒有收益還可能更差。升級的價值主要在平台層（GC、容器感知、安全更新），語言功能是附帶的——把論證建立在平台收益上比建立在語法糖上更站得住腳，也更容易說服非技術的決策者。

## 面試回答方式

不要背版本號，給**四條主線**：讓資料型別變便宜（record、sealed、模式比對加窮盡性檢查）、讓併發變便宜（虛擬執行緒）、讓 JVM 適應現代硬體與部署（ZGC、容器感知、CDS）、把平台整理乾淨（模組化、新發布節奏）。然後把升級論證落在**可量化的收益**——JDK 8 已無公開更新的安全風險、GC 停頓從數百毫秒降到個位數毫秒、同硬體吞吐提升、虛擬執行緒讓程式碼變簡單。加分點是務實的細節：升級障礙幾乎都在依賴而不是自己的程式碼（舊版 ASM／CGLIB 不認得新 class 檔版本），所以第一步是盤點依賴；**JDK 17 是最重要的一站**因為 Spring Boot 3 要求它。最後誠實說一句：價值主要在平台層，語言功能是附帶的，而且不是每個新功能都該用。

## 講稿

我會用四條主線來講，這比背版本號有用。

第一條是讓資料型別變便宜。record、密封類別、模式比對合起來，讓用型別表達領域概念的成本大幅下降，而且窮盡性檢查把一整類遺漏從執行期移到了編譯期。

第二條是讓併發變便宜。虛擬執行緒讓一個任務一個執行緒的簡單寫法重新可行，不必為了擴展性改寫成回呼或反應式風格。

第三條是讓 JVM 適應現代硬體跟部署形態。新的垃圾收集器把停頓壓到毫秒以下而且跟堆積大小脫鉤，還有容器感知，能正確讀取容器的資源限制。

第四條是把平台整理乾淨，模組化封住內部 API，還有新的發布節奏。

如果要說服團隊升級，我不會說版本比較新。我會講具體收益，JDK 8 已經沒有公開更新了這是安全風險、GC 停頓從數百毫秒降到個位數、同樣的硬體吞吐提升。而且實際的升級障礙幾乎都在依賴而不是自己的程式碼，第一步是盤點依賴。

## 常見追問

### 虛擬執行緒真的能取代反應式編程嗎？

**核心答案**：在大多數 IO 密集的服務裡可以，但不是全部。反應式編程解決兩個問題：**執行緒不足時的擴展性**與**背壓（backpressure）**。虛擬執行緒完全解決了第一個——阻塞變得便宜，一個請求一個執行緒可以撐到數十萬並行。但它**沒有解決背壓**：當下游處理不過來時，反應式的 `request(n)` 機制可以往上游傳遞壓力，虛擬執行緒需要靠信號量、有界佇列等傳統手段自己實現。

**詳細解析**：實務上的選擇取決於**團隊成本**。反應式的除錯體驗差（堆疊追蹤斷裂、上下文傳遞複雜）、學習曲線陡、與阻塞式函式庫混用容易出事，這些成本是持續的。虛擬執行緒讓程式碼回到直觀的順序寫法，堆疊追蹤完整，除錯與剖析工具都能正常運作。所以趨勢是新專案優先用虛擬執行緒加傳統阻塞寫法，只在真的需要串流式背壓的場景（例如處理無界的事件流）才用反應式。要注意虛擬執行緒目前的陷阱——在 `synchronized` 區塊內阻塞會釘住平台執行緒（後續 JDK 版本改善），以及 `ThreadLocal` 在數十萬執行緒下的記憶體成本（作用域值是為此設計的替代）。

**面試回答方式**：把問題拆成兩個維度——**擴展性與背壓**，指出虛擬執行緒解決前者但不解決後者，這比籠統回答「能」或「不能」精確得多。接著把選擇拉到團隊成本：反應式的除錯體驗與學習曲線是持續成本，虛擬執行緒讓堆疊追蹤與工具正常運作。收在具體建議與陷阱：新專案優先虛擬執行緒，真的需要串流式背壓才用反應式；並提醒 `synchronized` 內阻塞會釘住平台執行緒。

### 為什麼有些團隊卡在 JDK 8 這麼久？

**核心答案**：三個原因疊加。**依賴的斷點**——舊版的位元組碼函式庫、應用伺服器、以及不再維護的內部框架在 9 以上跑不起來，而更新它們可能牽動整個技術棧。**驗證成本**——升級 JVM 等於換掉執行時基礎，需要完整的回歸測試與效能驗證，而很多系統的測試覆蓋不足以支撐這種信心。**缺乏可量化的驅動力**——沒有出事的話，升級的收益（延遲、吞吐、安全）很難在排期會議上勝過功能開發。

**詳細解析**：突破點通常是**外部壓力**：安全稽核指出 JDK 8 已無公開更新、雲端供應商停止支援舊映像檔、或者某個必要的函式庫只支援 17 起跳（Spring Boot 3 就是很多團隊的觸發點）。務實的推進方式是先在非關鍵服務上做一次完整升級，把依賴問題、效能差異、與需要的改動全部記錄下來，形成一份可複用的升級手冊。這比一次推動全公司升級容易得多，也讓後續的排期有具體的工時估算依據。用「先做一個、量出成本」取代「先說服所有人」，是這類技術債議題最有效的推進方式。

**面試回答方式**：給三個疊加的原因（依賴斷點、驗證成本、缺乏可量化驅動力），這比歸咎於「團隊保守」有說服力。然後給推進方法：先在非關鍵服務做一次完整升級，形成可複用的升級手冊與工時估算，再推廣。收在一句可遷移的原則：技術債議題用「先做一個、量出成本」推進，比「先說服所有人」有效。

### 六個月發布節奏對開發者實際的影響是什麼？

**核心答案**：每個版本變小、預覽功能成為常態、LTS 之外的版本主要用於嘗鮮而非生產。實際的影響是：生產環境跟 LTS（8、11、17、21、25），開發者可以在非 LTS 版本上試用預覽功能並回饋。這改變了語言演進的模式——功能不再閉門設計數年後一次發布，而是先以預覽發布、依回饋調整、必要時撤回（字串模板就被撤回重新設計）。

**詳細解析**：對日常工作的影響有兩個。第一，要習慣「預覽功能不是穩定 API」——它需要 `--enable-preview` 且同一個版本編譯的位元組碼不能在其他版本執行，所以絕不該用在生產。第二，升級變成常規維護而不是專案：從 17 到 21 的改動量遠小於 8 到 17，如果團隊保持每個 LTS 都升，每次的成本都很低；跳過兩三個 LTS 則會累積成一個大專案。這與依賴管理是同一個道理——持續小步的維護成本遠低於間歇的大步遷移，而後者往往在最不方便的時候（安全事件、供應商停止支援）被迫發生。

**面試回答方式**：先給結構性影響（版本變小、預覽成常態、生產跟 LTS），並用字串模板被撤回重新設計說明預覽機制真的在發揮作用。接著給對日常工作的兩個影響：預覽功能的位元組碼不能跨版本執行所以絕不能上生產；升級變成常規維護而非專案。收在可遷移的原則：持續小步維護的成本遠低於間歇的大步遷移，而大步遷移往往在最不方便的時候被迫發生。
