# 題目

`var` 會讓 Java 變成動態型別嗎？什麼時候該用、什麼時候不該用？

## 核心答案

**不會**。`var` 只是把「宣告時寫出型別」這件事交給編譯器推導，變數的型別在編譯期就確定且不可改變——`var s = "hi"; s = 1;` 會編譯錯誤。它是**語法的省略**，不是型別系統的改變，位元組碼裡完全看不出差別。

它的適用範圍被刻意限制得很窄：只能用於區域變數、for 迴圈變數、與 try-with-resources 的資源。不能用於欄位、方法參數、回傳型別。理由是**這些位置是 API 的一部分**，型別必須明確寫出來給呼叫方看；區域變數則只影響方法內部，讀者通常能從幾行之內的上下文理解。

判斷該不該用的標準只有一個：讀者能不能在不看 IDE 提示的情況下知道型別。`var list = new ArrayList<String>()` 很清楚（右邊寫著）；`var result = process(data)` 就不清楚（要跳去看方法簽章）。在 code review 與 GitHub diff 上沒有 IDE，這才是真正的檢驗場景。

## 詳細解析

推導的是「宣告型別」而非「動態型別」，這帶來一個容易忽略的後果：`var x = new ArrayList<String>()` 推導出的是 `ArrayList<String>` 而不是 `List<String>`。明確寫 `List<String> list = new ArrayList<>()` 是一種**刻意面向介面編程**的表態，用 `var` 會失去它——之後如果有人在同一個方法裡呼叫了 `ArrayList` 特有的方法，換實作時就會編譯失敗。在區域變數的尺度上這個代價通常很小（影響範圍就在方法內），但知道差異在哪比較好。

有幾個地方會推出意外的型別。`var x = 1` 推出 `int` 而不是 `long`；`var d = 1.0` 推出 `double`。菱形運算子單獨用會退化——`var list = new ArrayList<>()` 推出 `ArrayList<Object>`，因為沒有任何資訊可以推導元素型別，這幾乎總是錯的。匿名類別搭配 `var` 會推出**不可命名的型別**（可以呼叫匿名類別新增的方法，但這個變數無法傳給任何方法），這是一個有趣但少用的能力。

`var` 真正發光的場景是型別名稱又長又沒有資訊量的時候：`var entry = map.entrySet().iterator().next()` 比寫出 `Map.Entry<String, List<Order>>` 好讀太多；巢狀泛型（`Map<String, Map<String, List<Item>>>`）也是。它的價值是把讀者的注意力從型別樣板移到變數名稱與邏輯上，這也提示了一個配套要求——**用了 `var` 就要把變數命名得更好**，因為名稱現在承擔了更多說明責任。

團隊需要一致的約定，而不是個人偏好：最實用的規則是「右邊的表達式已經表明型別就用 `var`，否則寫出型別」。這條規則涵蓋 `new`、明確的工廠方法（`List.of`）、以及帶有型別名稱的方法（`Files.newBufferedReader`），同時排除了泛用名稱的方法呼叫。把規則寫進團隊風格指南並用靜態分析檢查，比每次 review 爭論有效率。

## 面試回答方式

先明確否定「動態型別」的誤解，並給出證據——型別編譯期確定、重新賦值不同型別會編譯錯誤、位元組碼沒有差別。接著解釋**限制範圍的理由**：欄位、參數、回傳型別是 API 的一部分，必須明確；區域變數只影響方法內部。然後給唯一的判斷標準：讀者能不能在沒有 IDE 的情況下知道型別，並強調 code review 與 diff 才是真正的檢驗場景。加分點是幾個推導陷阱：`new ArrayList<>()` 會推出 `ArrayList<Object>`、`var x = 1` 是 `int` 不是 `long`、以及 `var` 推的是具體類別而非介面所以失去面向介面的表態。收在團隊層面：訂一條「右邊表明型別就用」的規則並用靜態分析檢查，比每次爭論有效率。

## 講稿

var 不會讓 Java 變成動態型別。它只是把宣告時寫出型別這件事交給編譯器推導，型別在編譯期就確定而且不能改變。位元組碼裡完全看不出差別。

它的適用範圍被刻意限制得很窄，只能用在區域變數、迴圈變數跟 try-with-resources 的資源。不能用在欄位、方法參數、回傳型別。理由是那些位置是 API 的一部分，型別必須明確寫給呼叫方看。

我判斷該不該用的標準只有一個。讀者能不能在沒有 IDE 提示的情況下知道型別。看到 var 等於 new ArrayList 很清楚，右邊就寫著。但看到 var 等於某個方法的回傳值就不清楚，得跳去看簽章。程式碼審查跟 diff 上沒有 IDE，那才是真正的檢驗場景。

有幾個推導陷阱要注意。單獨用菱形運算子會推出元素型別是 Object，那幾乎總是錯的。還有 var 推出來的是具體類別而不是介面，所以會失去面向介面編程的表態。

團隊層面我會訂一條規則，右邊的表達式已經表明型別就用 var，否則寫出來，然後用靜態分析檢查。

## 常見追問

### var 對編譯速度或執行效能有影響嗎？

**核心答案**：**執行效能完全沒有影響**——推導在編譯期完成，產生的位元組碼與明確寫出型別時一模一樣，JIT 看到的東西也完全相同。編譯速度理論上多一點推導工作，但那是微不足道的，實務上量不出來。任何說「`var` 比較慢」的說法都是把它與動態型別語言混淆了。

**詳細解析**：值得一提的是 `var` 與**其他推導機制的差異**。泛型的型別推導（菱形運算子、方法型別參數）是更早就有的，`var` 只是把同一套推導引擎用在區域變數的宣告型別上。而 lambda 的參數型別推導（`(a, b) -> ...`）則是從目標型別反推，方向相反。這三者都是編譯期的事，都不影響執行期。真正會影響效能的推導是在動態語言裡的執行期型別檢查與內聯快取，Java 完全沒有那個成本。

**面試回答方式**：直接給明確答案（執行期零影響、位元組碼相同），並指出「`var` 比較慢」的說法源自與動態型別語言的混淆。加分點是把它與泛型推導、lambda 參數推導放在一起，說明三者都是編譯期機制，並對比動態語言的執行期型別檢查成本——這顯示你理解推導發生在哪個階段。

### 為什麼不能用在欄位和方法參數上？

**核心答案**：因為**那些位置構成 API 的契約**。方法的參數與回傳型別是呼叫方唯一能依賴的東西，如果它們可以被推導，那推導的來源就落在實作裡——實作一改，API 就悄悄變了，而且呼叫方在編譯前完全看不出來。欄位也類似：它是類別狀態的一部分，子類別與同套件的程式碼都會依賴它。區域變數是唯一「作用域小到讀者能自己看出來」的位置。

**詳細解析**：這個界線也讓工具鏈的工作變得可行——產生 API 文件、做二進位相容性檢查、生成介面樁碼，都需要簽章是顯式的。有些語言（Kotlin、Scala、TypeScript）允許推導回傳型別，代價正是這些工具要做更多工作，而且**API 的變更更容易在無意間發生**（改一行實作就改了公開簽章）。Kotlin 的解法是提供編譯器選項要求公開 API 必須顯式標註（explicit API mode），等於承認了同一個問題。Java 選擇從一開始就不給這個選項，這與它「相容性優先」的整體取向一致。

**面試回答方式**：核心是「那些位置是 API 契約，推導會讓實作的改動悄悄改變契約」。補上工具鏈的理由（文件生成、相容性檢查需要顯式簽章）。加分點是拿 Kotlin 作對照：它允許推導回傳型別，但提供了 explicit API mode 要求公開 API 顯式標註，等於承認了同樣的問題——這說明 Java 的選擇不是保守，而是取捨的另一端。

### var 與泛型一起用時有哪些陷阱？

**核心答案**：三個。**菱形運算子失去資訊**——`var list = new ArrayList<>()` 推出 `ArrayList<Object>`，之後放任何東西都能編譯，錯誤延後到取出時才發現。**萬用字元被捕獲**——`var x = someListOfWildcard.get(0)` 推出的是捕獲型別，錯誤訊息會出現 `capture of ? extends ...` 這種難懂的東西。**推出具體類別而非介面**——這讓後續程式碼可能無意間依賴實作特有的方法。

**詳細解析**：第一個是最實際的問題，而且**編譯器不會警告**——`ArrayList<Object>` 是完全合法的型別。這類問題的一般模式是「推導總是給你一個答案，但不保證那是你想要的答案」。所以 `var` 的使用原則可以再精確一點：只在右邊表達式的型別完整且明確時使用。`new ArrayList<String>()` 完整，`new ArrayList<>()` 不完整；`List.of("a", "b")` 完整，`List.of()` 不完整（推出 `List<Object>`）。這條線比「右邊有沒有 new」更準確。

**面試回答方式**：給三個陷阱並指出第一個最實際——`ArrayList<Object>` 完全合法所以編譯器不警告，錯誤延後到取出時。歸納成一句原則：推導總是給你答案，但不保證是你要的答案。然後把使用規則精確化：只在右邊表達式的型別**完整且明確**時使用，並用 `new ArrayList<String>()` 對比 `new ArrayList<>()`、`List.of("a")` 對比 `List.of()` 說明界線。
