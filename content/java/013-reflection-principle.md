# 題目

什麼是反射（Reflection）？它的原理是什麼？有哪些應用場景和缺點？

## 核心答案

反射是 Java 讓程式在「執行期」動態地檢查與操作類別的能力——可以在不知道具體類別名的情況下，取得類別的欄位、方法、建構子等資訊，並動態建立物件、呼叫方法、存取欄位。它的原理是 JVM 在載入類別時，會在方法區為每個類別建立一個 `Class` 物件，這個物件包含了該類別的完整結構元資料，反射就是透過這個 `Class` 物件來存取類別資訊。反射是很多框架（Spring、Hibernate、JSON 函式庫）的基礎，但有效能開銷、破壞封裝、失去編譯期型別檢查等缺點。

## 詳細解析

**原理**：每個類別被 JVM 載入後，都會在方法區（元空間（Metaspace））產生一個對應的 `Class` 物件，儲存了這個類別的所有結構資訊（欄位、方法、建構子、註解、父類別、介面等）。反射 API 就是透過取得這個 `Class` 物件（`obj.getClass()`、`類別名.class`、`Class.forName("全類名")`），進而讀取和操作這些元資料。

**主要能力**：

- 取得類別資訊：`getFields()`、`getMethods()`、`getConstructors()`、`getAnnotations()` 等。
- 動態建立實例：`clazz.getDeclaredConstructor().newInstance()`。
- 動態呼叫方法：`method.invoke(obj, args)`。
- 存取/修改欄位：`field.get(obj)`、`field.set(obj, value)`配合 `setAccessible(true)` 甚至能存取私有成員。

**應用場景**：

- **框架的依賴注入**：Spring 用反射掃描註解、建立 Bean、注入依賴。
- **ORM 框架**：Hibernate/MyBatis 用反射把資料庫欄位對應到物件欄位。
- **序列化/反序列化**：Jackson/Gson 用反射讀寫物件的欄位。
- **註解處理**：執行期讀取註解並據此做對應處理。

**缺點**：

1. **效能開銷**：反射呼叫比直接呼叫慢（雖然現代 JVM 有優化，但仍有額外成本）。
2. **破壞封裝**：`setAccessible(true)` 能存取私有成員，繞過了封裝的保護。
3. **失去編譯期檢查**：方法名、欄位名用字串指定，拼錯只有執行期才會報錯。
4. **不利於 JVM 優化**：反射呼叫難以被 JIT 內聯等優化。

## 面試回答方式

先講「反射是什麼」（執行期動態檢查/操作類別的能力），再講「原理」（每個類別有一個 `Class` 物件承載元資料，反射透過它存取）。應用場景是這題的重點，一定要舉出框架的實際用法（Spring 依賴注入、ORM、序列化），說明反射是「框架魔法」背後的基礎，這能展現你理解反射的真實價值而不只是 API。最後客觀地講缺點（效能、破壞封裝、失去編譯期檢查），展現你知道反射是「強大但要謹慎使用」的工具。

## 常見追問

### 取得 Class 物件有哪幾種方式？它們有什麼差異？

**核心答案**：主要有三種——`類別名.class`（編譯期就確定，最快，不觸發類別初始化）、`物件.getClass()`（執行期從實例取得）、`Class.forName("全類名字串")`（執行期根據字串動態載入，會觸發類別初始化，常用於載入編譯期未知的類別如 JDBC 驅動）。三者取得的是同一個 `Class` 物件（同一類別的 Class 物件全域唯一），差別在使用時機和是否觸發初始化。

**詳細解析**：`String.class` 這種字面量方式在編譯期就確定型別，效能最好，且只載入類別不執行初始化（不執行靜態程式碼區塊）。`obj.getClass()` 需要先有一個實例，回傳這個實例「實際的」執行期型別（多型場景下很有用，能拿到子類別的 Class）。`Class.forName("com.mysql.Driver")` 最動態——它接受一個字串，在執行期才決定載入哪個類別，且預設會觸發類別的初始化（執行靜態區塊），這正是老式 JDBC 用 `Class.forName` 載入驅動的原因（驅動類別的靜態區塊會自我註冊）。理解三者差異的關鍵是「編譯期確定 vs 執行期動態」以及「是否觸發初始化」。

**面試回答方式**：列出三種方式並對比它們的「使用時機」與「是否觸發初始化」，尤其點出 `Class.forName` 會觸發初始化、常用於 JDBC 驅動載入這個經典應用，展現你不只會用還理解背後的類別載入行為。

### setAccessible(true) 做了什麼？有什麼風險？

**核心答案**：`setAccessible(true)` 關閉了 Java 的存取權限檢查，讓反射能夠存取和修改原本被 `private`、`protected` 保護的欄位或方法。它的風險是徹底破壞了封裝——可以讀寫別人設計成私有的內部狀態，繞過了類別作者刻意設下的保護邊界，可能破壞物件的不變性（invariant）、造成難以預料的錯誤，也帶來安全隱憂。

**詳細解析**：封裝的目的是讓類別作者能控制「哪些狀態可以被外部存取」，把內部實作細節隱藏起來。`setAccessible(true)` 相當於用反射強行撬開這道保護——你可以修改一個 `final` 欄位、呼叫一個私有方法、讀取一個本該隱藏的密碼欄位。雖然框架（如 Spring 注入私有欄位、序列化讀取私有狀態）合理地使用了這個能力，但在應用程式碼中濫用它是危險的：你可能破壞被存取物件所依賴的不變性（例如強行改掉一個本應唯讀的狀態），且這種依賴內部實作細節的程式碼非常脆弱（對方一改內部實作你就壞了）。現代 Java（JDK 9+ 的模組系統）也對 `setAccessible` 加了更多限制，反映了對這種「破壞封裝」能力的謹慎態度。

**面試回答方式**：講清楚「關閉存取檢查、能操作私有成員」這個作用，並強調風險——「破壞封裝、可能破壞不變性、依賴內部實作而脆弱」。能提到「框架合理使用但應用程式碼應謹慎」以及「JDK 9 模組系統加了限制」，展現你對這個強大但危險的能力有平衡的認識。

### 反射的效能開銷主要來自哪裡？現代 JVM 如何優化？

**核心答案**：反射的效能開銷主要來自——每次反射呼叫都要做存取權限檢查、參數的裝箱/拆箱與陣列封裝、以及反射呼叫難以被 JIT 編譯器內聯優化。現代 JVM 對反射做了優化，例如對頻繁呼叫的反射方法會動態生成專用的位元組碼（inflation 機制）來加速後續呼叫，使得反射的效能開銷比早期版本小很多，但仍然比直接呼叫慢。

**詳細解析**：直接的方法呼叫，JIT 可以內聯、可以做各種優化；而反射呼叫 `method.invoke(obj, args)` 需要：檢查存取權限、把參數包裝成 `Object[]` 陣列（基本型別還要裝箱）、動態分派到目標方法，這些額外步驟都是成本。JVM 的優化之一是「inflation」——`Method.invoke` 前幾次用較慢的 JNI 本地方法呼叫，當某個反射方法被呼叫達到一定次數後，JVM 會動態生成一個專門的位元組碼（Bytecode）類別來執行這個呼叫，之後就能享受接近直接呼叫的速度。此外，如果反射物件（如 `Method`）被快取重複使用（而非每次重新 `getMethod`），也能避免重複的查找開銷。實務上，效能敏感且高頻的反射呼叫，可以考慮用 `MethodHandle`（更輕量）或程式碼生成（如編譯期註解處理）來替代。

**面試回答方式**：講出開銷來源（權限檢查、參數裝箱封裝、難以內聯）和優化手段（inflation 生成專用位元組碼、快取反射物件），並提到「高頻場景可用 MethodHandle 或程式碼生成替代」，展現你對反射效能有具體而非籠統的理解，這在效能敏感的框架開發場景很有價值。
