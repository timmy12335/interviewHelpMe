# 題目

深拷貝和淺拷貝有什麼差異？Java 中怎麼實現深拷貝？

## 核心答案

淺拷貝（shallow copy）只複製物件本身和其中的基本型別欄位，對於引用型別的欄位只複製「引用」（位址），所以原物件和拷貝物件會共享同一個被引用的子物件——改動子物件會互相影響。深拷貝（deep copy）則會遞迴地複製物件及其所有引用的子物件，產生一個完全獨立的副本，原物件和拷貝物件互不影響。Java 的 `Object.clone()` 預設是淺拷貝，實現深拷貝需要手動遞迴複製、或透過序列化/反序列化、或用建構子逐層複製。

## 詳細解析

**淺拷貝**：複製後，新物件的基本型別欄位是獨立的值，但引用型別欄位仍指向和原物件相同的子物件。例如一個 `Person` 物件有一個 `Address` 欄位，淺拷貝後兩個 `Person` 共享同一個 `Address`——修改其中一個的 `Address`，另一個也會受影響。`Object.clone()` 預設就是淺拷貝。

**深拷貝**：複製後，連引用型別的子物件也一併複製一份，新物件擁有完全獨立的子物件。修改拷貝物件的任何部分都不會影響原物件。

**Java 中實現深拷貝的方式**：

1. **手動遞迴複製**：覆寫 `clone()`，在其中對每個引用型別欄位也呼叫其 `clone()`（或 new 一個新的）。缺點是物件層次深時要逐層處理，繁瑣易漏。
2. **序列化 + 反序列化**：把物件序列化成位元組流再反序列化還原，得到的是完全獨立的深拷貝（前提是所有涉及的類別都可序列化）。簡單通用但效能較差。
3. **透過建構子或工具**：用複製建構子、或第三方工具（如 Apache Commons 的 `SerializationUtils.clone()`、或 JSON 序列化再反序列化）。

**Cloneable 介面的問題**：`clone()` 機制設計得不好——`Cloneable` 是個沒有方法的標記介面、`clone()` 定義在 `Object` 且是 protected、預設淺拷貝又容易誤用，所以《Effective Java》建議「盡量不要用 clone，改用複製建構子或複製工廠方法」。

## 面試回答方式

用一個具體例子（Person 含 Address 欄位）來對比淺拷貝和深拷貝最清楚——淺拷貝後兩個 Person 共享同一個 Address（改一個影響另一個），深拷貝後各有獨立的 Address。核心是「淺拷貝只複製引用、深拷貝遞迴複製子物件」。實現深拷貝要能列出幾種方式（手動遞迴、序列化、建構子）。如果能主動提到「`Object.clone()` 預設是淺拷貝」和「《Effective Java》建議別用 clone、改用複製建構子」，展現你不只知道概念還了解 Java 這塊設計的爭議。

## 常見追問

### 為什麼 Object.clone() 的設計常被批評？

**核心答案**：`clone()` 機制的設計有幾個為人詬病的問題——`Cloneable` 是一個沒有任何方法的標記介面，卻要求你覆寫 `Object` 中的 `clone()`（違反了介面應該定義行為的常理）；`clone()` 是 protected 的，外部無法直接呼叫；預設的淺拷貝行為容易被誤用（以為複製了其實子物件還是共享的）；而且 `clone()` 不呼叫建構子，繞過了建構子中的初始化邏輯和 final 欄位的正常賦值。因此《Effective Java》明確建議用「複製建構子」或「複製工廠方法」取代 clone。

**詳細解析**：`Cloneable` 的怪異在於——它是標記介面（不含方法），但它的作用是「改變 `Object.clone()` 這個 protected 方法的行為」（實作了 Cloneable 才不會拋 `CloneNotSupportedException`），這種「透過標記介面影響另一個方法的行為」的設計非常反直覺。此外，`clone()` 建立物件時不走建構子——它直接複製記憶體，這意味著建構子中的驗證邏輯、副作用被跳過，`final` 欄位也無法在 clone 中被正常賦值（造成深拷貝 final 引用欄位時的困難）。相比之下，複製建構子 `public Person(Person other)` 或複製工廠 `static Person copyOf(Person other)` 語意清晰、走正常的建構流程、可以自由控制深淺拷貝、也不需要處理 `CloneNotSupportedException`，是更乾淨的做法。

**面試回答方式**：列出 clone 的幾個設計問題（Cloneable 是無方法標記介面卻影響方法行為、clone 是 protected、預設淺拷貝易誤用、繞過建構子），並給出替代方案（複製建構子/工廠方法）。能引用《Effective Java》的建議展現你讀過經典資料，這種對「語言既有機制的缺陷」有批判性認識的回答很有深度。

### 用序列化實現深拷貝有什麼優缺點？

**核心答案**：優點是——通用且省事，不管物件的引用層次有多深，序列化再反序列化能一次性得到完全獨立的深拷貝，不需要手動逐層複製。缺點是——效能較差（序列化/反序列化的開銷遠大於直接複製）、要求所有涉及的類別都實作 `Serializable`（否則會失敗）、且 `transient` 欄位不會被複製（會變成預設值）。

**詳細解析**：序列化深拷貝的原理是——把物件寫成位元組流時，會遞迴地把它引用的所有子物件也一併寫入，反序列化時再遞迴地全部重建，重建出來的是一套全新的、與原物件完全無關的物件圖，天然就是深拷貝。這個「一次搞定任意深度」的特性很方便，Apache Commons 的 `SerializationUtils.clone()` 就是這個原理。但代價明顯：序列化涉及大量的反射、位元組流讀寫，比手動 new 慢很多；且它繼承了 Java 序列化的所有限制——類別必須可序列化、`transient` 欄位會遺失、還有前面提到的安全與相容性考量。因此它適合「物件結構複雜、深拷貝不頻繁、對效能不敏感」的場景；效能敏感的熱路徑上應該用手寫的複製邏輯或複製建構子。

**面試回答方式**：對比優點（通用、任意深度一次搞定）和缺點（效能差、要求可序列化、transient 遺失），並說明適用場景（結構複雜、不頻繁、非效能熱點）。這種能權衡「方便 vs 效能」並指出適用邊界的回答，比單純說「可以用序列化做深拷貝」更能展現工程判斷。

### 深拷貝一定比淺拷貝好嗎？什麼時候該用淺拷貝？

**核心答案**：不一定，要看需求。深拷貝雖然安全（完全獨立、互不影響）但有成本（複製所有子物件的時間與記憶體開銷），而且如果子物件本身是不可變的（如 `String`、`Integer`），淺拷貝共享它們完全沒有風險（反正誰都改不了），此時做深拷貝是純粹的浪費。所以當「子物件是不可變的」或「就是需要共享同一個子物件」時，淺拷貝更合適、更高效。

**詳細解析**：拷貝的深淺選擇本質是「隔離性」與「成本」的權衡。深拷貝提供完全的隔離（改副本絕不影響原件），但要付出複製整個物件圖的代價；淺拷貝成本低（只複製一層）但原件和副本共享子物件。關鍵判斷點是「共享的子物件會不會被修改」——如果子物件是不可變的（String、包裝類別、或設計成 immutable 的值物件），那麼共享它完全安全，深拷貝這些不可變子物件是白費功夫；只有當子物件是可變的、且你不希望原件和副本互相影響時，才需要深拷貝。實務中一個常見的高效模式是「不可變欄位淺拷貝共享、可變欄位深拷貝隔離」的混合策略。這也呼應了「用不可變物件能簡化很多問題」這個 Java 設計哲學。

**面試回答方式**：回答「不一定，取決於子物件是否可變」——不可變子物件共享無風險、深拷貝它們是浪費，可變子物件才需要深拷貝隔離。能提出「不可變欄位淺拷貝、可變欄位深拷貝的混合策略」，展現你理解拷貝深淺是「按需選擇的權衡」而非「深拷貝總是更好」的教條，這種務實判斷很加分。
