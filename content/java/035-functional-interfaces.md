# 題目

`java.util.function` 裡為什麼有那麼多介面？什麼時候該自訂函式介面而不是重用既有的？

## 核心答案

那些介面其實只有**四種基本形狀**的組合：`Function`（一進一出）、`Consumer`（有進無出）、`Supplier`（無進有出）、`Predicate`（一進一個布林）。剩下的都是三個維度上的變體——**參數個數**（`BiFunction`、`BiConsumer`）、**基本型別特化**（`IntFunction`、`ToIntFunction`、`IntPredicate`⋯⋯）、**同型別簡寫**（`UnaryOperator` 是參數與回傳同型的 `Function`，`BinaryOperator` 對應 `BiFunction`）。

介面數量爆炸的主因是**基本型別特化**。泛型不能用基本型別，`Function<Integer, Integer>` 每次呼叫都要裝箱拆箱，在串流這種百萬次級的呼叫上成本可觀。JDK 因此為 `int`、`long`、`double` 手工展開了一整組特化介面——這是型別擦除與缺乏值型別泛型的直接代價，也是 Valhalla 專案想要解決的問題。

自訂的時機有三個：**需要拋出檢查例外**（既有介面都不宣告 `throws`）、**參數超過兩個**、或者**名稱本身就是文件**（`RetryPolicy`、`PriceCalculator` 比 `BiFunction<Order, Customer, BigDecimal>` 好讀太多）。第三點最常被低估，也最值得做。

## 詳細解析

檢查例外是既有介面最大的缺口：`Function.apply` 沒有 `throws`，所以 `list.stream().map(this::readFile)` 在 `readFile` 拋 `IOException` 時無法編譯，只能在 lambda 裡包 try-catch 轉成執行期例外——程式碼立刻變醜，而且把檢查例外偷偷換成未檢查例外。解法是自訂一個宣告了 `throws` 的函式介面，或提供一個把它包裝成標準介面的轉接方法。這個問題沒有語言層級的好解答，是檢查例外與函式式風格之間真實的摩擦，能誠實指出它比假裝沒問題好。

**特化介面的命名有規則可循**，知道規則就不必背：前綴的型別指**參數**（`IntPredicate` 吃 int）、`To` 前綴指**回傳**（`ToIntFunction<T>` 吃 T 回傳 int）、兩者都有就是 `IntToLongFunction`。`ObjIntConsumer<T>` 這種混合形狀則是為特定 API（如 `collect`）量身訂做的。選對特化介面是串流效能最容易拿到的分數——`mapToInt` 之後用 `IntStream` 而不是 `Stream<Integer>`，能省掉整條管線的裝箱。

**組合方法是這組 API 真正的價值**：`Function` 有 `andThen` 與 `compose`（順序相反，前者先自己後參數，後者相反），`Predicate` 有 `and`、`or`、`negate` 與靜態的 `not`，`Consumer` 有 `andThen`。這些讓小函式可以拼成大函式而不必寫巢狀呼叫。自訂函式介面時如果只寫一個抽象方法而不提供組合方法，就少了一半的價值——加上幾個預設方法通常只要幾行。

過度使用函式介面是另一種病：把所有東西都寫成 `Function` 會失去型別帶來的資訊。`Map<String, Function<Order, BigDecimal>>` 這種結構能動，但看不出每個函式代表什麼、有什麼前提、失敗會怎樣。當一個行為有自己的名字、有前後條件、可能有多個相關操作時，它該是一個具名介面甚至一個類別，不是一個匿名的 `Function`。判準是「這個東西在領域語言裡有沒有名字」。

## 面試回答方式

先把數量問題拆解掉——只有四種基本形狀，其餘是參數個數、基本型別特化、同型別簡寫三個維度的組合，這比逐一列舉有結構得多。接著指出爆炸的主因是**基本型別特化**，而它源自型別擦除與缺乏值型別泛型，是 Valhalla 要解的問題。然後給自訂的三個時機，把**檢查例外**放在最前面並具體說明摩擦（`map(this::readFile)` 無法編譯，只能包 try-catch 把檢查例外偷換成未檢查）。加分點是命名規則（前綴是參數、`To` 是回傳）與一句實務建議：自訂函式介面記得補上組合的預設方法。最後給一個反向的判斷——行為在領域語言裡有名字時就該用具名型別，別什麼都寫成 `Function`。

## 講稿

那些介面其實只有四種基本形狀。一進一出、有進無出、無進有出、還有回傳布林的判斷。剩下的都是三個維度上的變體，參數個數、基本型別特化、還有參數跟回傳同型的簡寫。

數量爆炸的主因是基本型別特化。泛型不能用基本型別，所以每次呼叫都要裝箱拆箱，在串流這種百萬次級的呼叫上成本很可觀。JDK 只好為整數、長整數、浮點數手工展開一整組介面。這是型別擦除的直接代價。

我會自訂函式介面的時機有三個。第一是需要拋出檢查例外，因為既有的介面都沒有宣告 throws。第二是參數超過兩個。第三是名稱本身就是文件，一個叫做重試策略的介面，比一個吃兩個參數回傳金額的泛型函式好讀太多。

檢查例外那個缺口值得多講一句。在串流裡呼叫一個會拋 IO 例外的方法沒辦法編譯，只能在 lambda 裡包 try-catch，把檢查例外偷偷換成未檢查例外。這是函式式風格跟檢查例外之間真實的摩擦。

## 常見追問

### andThen 與 compose 差在哪？

**核心答案**：執行順序相反。`f.andThen(g)` 是**先 f 再 g**，等價於 `x -> g(f(x))`；`f.compose(g)` 是**先 g 再 f**，等價於 `x -> f(g(x))`。`compose` 沿用數學上函數合成的慣例（右邊先算），`andThen` 則沿用自然語言的閱讀順序。實務上 `andThen` 用得多得多，因為它與程式碼由上而下的閱讀方向一致。

**詳細解析**：兩者的型別簽章也不同，這決定了能接什麼。`andThen` 的參數是 `Function<? super R, ? extends V>`——它接在後面，所以吃的是前一步的回傳型別；`compose` 的參數是 `Function<? super V, ? extends T>`——它接在前面，回傳的必須是自己的參數型別。看懂這兩個簽章就不必背順序，型別會告訴你誰接誰。另外 `Consumer.andThen` 的語意是「兩個都執行」而不是串接（因為 Consumer 沒有回傳值），如果第一個拋例外第二個就不會執行——這在用它組合多個副作用時要注意。

**面試回答方式**：直接給順序與等價寫法，並解釋兩個名字各自沿用的慣例（數學的函數合成、自然語言的閱讀順序）。加分點是指出**看型別簽章就能推出順序**，不必死背；以及 `Consumer.andThen` 的語意是「都執行」而非串接，第一個拋例外會讓第二個不執行。

### 為什麼串流的 map 之後要用 mapToInt？

**核心答案**：為了**消除裝箱**。`stream().map(Order::getQuantity)` 得到的是 `Stream<Integer>`，每個元素都是一個堆積上的 `Integer` 物件；後續的 `sum` 還要一個個拆箱。`mapToInt(Order::getQuantity)` 得到 `IntStream`，元素是原始的 int，整條管線不配置任何包裝物件。在百萬級的資料上這是數倍的差距，而且省下的不只是 CPU，還有 GC 壓力與快取失效。

**詳細解析**：`IntStream` 還多了一些只有數值才有意義的操作——`sum`、`average`、`summaryStatistics`，用 `Stream<Integer>` 得靠 `reduce` 或 `collect` 繞路。反過來要注意 `boxed()` 的成本：`IntStream.boxed().collect(toList())` 會把剛剛省下的裝箱又加回來，所以**只在真的需要物件時才 boxed**。還有一個容易忽略的點——`Integer` 快取只涵蓋 -128 到 127，超出這個範圍的裝箱每次都是新物件，所以資料的數值分布會影響裝箱的實際成本。這題的一般原則是：在泛型與基本型別的邊界上，型別選擇就是效能選擇。

**面試回答方式**：核心是「消除整條管線的裝箱」，並指出省下的是 CPU、GC 壓力與快取效率三者。補充 `IntStream` 獨有的數值操作作為第二個理由。加分點是反向提醒 `boxed()` 會把成本加回來，以及 `Integer` 快取只在 -128 到 127，資料分布會影響實際成本。收在一句原則：泛型與基本型別的邊界上，型別選擇就是效能選擇。

### 自訂函式介面時有哪些容易踩的坑？

**核心答案**：三個。忘記加 `@FunctionalInterface`——之後有人加第二個抽象方法就會悄悄破壞所有下游 lambda。沒有提供組合方法——只有一個抽象方法的介面用起來很生硬，加幾個 `andThen`、`or` 這類預設方法成本很低。**泛型邊界寫得太緊**——參數應該用 `? super T`、回傳用 `? extends R`（PECS），寫成不帶萬用字元會讓很多合理的 lambda 無法傳入。

**詳細解析**：還有一個更隱蔽的問題是**多載造成的推導歧義**。如果一個類別同時有 `execute(Runnable)` 與 `execute(Callable<?>)` 兩個多載，傳一個 `() -> foo()` 進去時編譯器可能無法決定要用哪個（尤其 `foo()` 有回傳值時兩者都符合），使用者被迫加型別轉型才能編譯。設計 API 時應該避免在同一個方法名上多載多個函式介面，改用不同的方法名（`execute` 與 `submit`）。JDK 自己在 `ExecutorService` 上就是這樣分的。另外自訂介面的抽象方法**名字要有意義**（`apply` 這種泛用名對具名介面沒有幫助），因為方法引用與除錯時都會出現它。

**面試回答方式**：給三個坑（缺註解、缺組合方法、泛型邊界太緊）並各配一句後果。真正的加分點是第四個更隱蔽的：不要在同一個方法名上多載多個函式介面，因為 lambda 的型別推導會歧義，並舉 `ExecutorService` 用 `execute` 與 `submit` 分開作為正例。最後補一句抽象方法要取有意義的名字，因為它會出現在方法引用與堆疊追蹤裡。
