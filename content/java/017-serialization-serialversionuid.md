# 題目

Java 序列化是什麼？`serialVersionUID` 有什麼作用？`transient` 關鍵字呢？

## 核心答案

序列化是把物件轉換成位元組序列（以便儲存到檔案或透過網路傳輸）的過程，反序列化則是反向還原成物件。一個類別要能被序列化必須實作 `Serializable` 介面。`serialVersionUID` 是序列化的「版本號」，用於在反序列化時驗證「序列化與反序列化用的類別版本是否相容」——如果不一致會拋出 `InvalidClassException`。`transient` 修飾的欄位不會被序列化（還原後是預設值），用於排除敏感或不需要持久化的欄位。

## 詳細解析

**序列化的用途**：把記憶體中的物件轉成位元組流，用於——持久化到磁碟、透過網路傳輸（RPC）、存入快取等。實作 `Serializable` 介面（一個沒有任何方法的標記介面）即可讓類別支援 Java 原生序列化。

**serialVersionUID 的作用**：

- 它是序列化機制用來驗證版本相容性的唯一識別碼。序列化時會把它寫入位元組流，反序列化時會比對「位元組流中的 UID」和「當前類別的 UID」是否一致。
- 如果不一致，拋出 `InvalidClassException`，代表「你正在用一個和序列化時不同版本的類別來還原物件」。
- 如果不手動宣告，編譯器會根據類別結構自動生成一個——但這很危險，因為只要類別結構有任何改動（加個欄位、改個方法），自動生成的 UID 就會變，導致舊資料無法反序列化。因此強烈建議手動宣告一個固定的 `private static final long serialVersionUID`。

**transient 的作用**：

- `transient` 修飾的欄位在序列化時會被忽略，反序列化後該欄位是其型別的預設值（物件為 null、int 為 0 等）。
- 用途：排除敏感資訊（如密碼欄位不該被序列化寫入磁碟）、排除可以由其他欄位重新計算的衍生欄位、排除不可序列化的欄位（避免序列化失敗）。

**Java 原生序列化的問題**：效能不佳、產生的位元組流較大、有安全漏洞（反序列化不可信資料可能導致遠端程式碼執行）、且是 Java 專用（跨語言不友善）。因此實務上常改用 JSON（Jackson/Gson）、Protobuf、Kryo 等替代方案。

## 面試回答方式

先講序列化的用途（物件↔位元組流，用於持久化/傳輸）和前提（實作 `Serializable`）。`serialVersionUID` 是重點——講清楚它是「版本相容性驗證碼」，並強調實務建議「手動宣告固定值，否則類別一改動自動生成的 UID 就變、舊資料無法還原」。`transient` 講「排除不需序列化的欄位（敏感資訊、衍生欄位）」。如果能主動提到「Java 原生序列化有效能、安全問題，實務多用 JSON/Protobuf 替代」，展現你不只知道機制還知道它的侷限與業界實務。

## 常見追問

### 如果不手動宣告 serialVersionUID 會有什麼風險？

**核心答案**：如果不手動宣告，編譯器會根據類別的結構（欄位、方法、介面等）自動計算一個 `serialVersionUID`。風險在於——只要類別結構發生任何改變（哪怕只是新增一個無關的方法或欄位），自動計算出的 UID 就會改變，導致「用舊版類別序列化的資料，無法用新版類別反序列化」（拋 `InvalidClassException`），造成舊的持久化資料或在途的網路資料突然無法還原。

**詳細解析**：自動生成的 UID 對類別結構非常敏感——它是根據類別的完整簽章（類別名、欄位、方法、實作的介面等）雜湊計算出來的，任何細微改動都會產生完全不同的值。這在實務中是個大坑：假設你把一批物件序列化存到了 Redis 快取或資料庫，之後給這個類別加了一個新欄位重新部署，此時自動生成的 UID 變了，那些已經存起來的舊資料在反序列化時就會因為 UID 不匹配而全部失敗。手動宣告一個固定的 `serialVersionUID` 能讓你「明確控制版本相容性」——只要你認為類別的改動是相容的（例如只是加了一個有預設值的欄位），就保持 UID 不變，舊資料仍能正常還原（新欄位用預設值）；只有當你認為改動是不相容的、必須拒絕舊資料時，才刻意改變 UID。

**面試回答方式**：講清楚「自動生成的 UID 對類別任何改動都敏感、一改就導致舊資料無法還原」這個風險，再說明手動宣告的價值是「讓你主動控制版本相容性」。舉一個「加欄位後 Redis 快取的舊資料全部反序列化失敗」的具體場景，展現你理解這不是理論問題而是真實會踩的坑。

### 父類別沒實作 Serializable，子類別實作了，序列化時父類別的欄位會怎樣？

**核心答案**：如果父類別沒有實作 `Serializable`，子類別實作了，那麼序列化時「只有子類別自己的欄位會被序列化，父類別的欄位不會」。反序列化時，父類別的欄位不是從位元組流還原，而是透過「呼叫父類別的無參建構子」重新初始化——因此父類別必須有一個可存取的無參建構子，否則反序列化會失敗（拋 `InvalidClassException`）。

**詳細解析**：序列化機制的規則是——只序列化「實作了 Serializable 的那部分繼承鏈」的欄位。父類別如果沒實作 Serializable，它的欄位就被排除在序列化之外；反序列化重建物件時，對於這些未被序列化的父類別部分，序列化機制會呼叫父類別的無參建構子來初始化它們（相當於重新 new 了父類別的那部分）。這帶來兩個後果：一是父類別欄位的值不會被保留（反序列化後是無參建構子設定的初始值，而非序列化當時的值）；二是父類別必須提供可存取的無參建構子，否則機制無法重建父類別部分而失敗。理解這個規則能幫你排查「為什麼反序列化後父類別的某些欄位變回了初始值」這類困惑。

**面試回答方式**：回答「父類別欄位不被序列化、反序列化時靠父類別無參建構子重新初始化、所以父類別必須有無參建構子」，這種能講出「未序列化部分如何被重建」以及「對無參建構子的要求」的回答，展現你對序列化機制的細節有超越「加個 Serializable 就好」的深入理解。

### 為什麼實務上多用 JSON、Protobuf 取代 Java 原生序列化？

**核心答案**：因為 Java 原生序列化有幾個明顯缺點——效能較差且產生的位元組流較大；有嚴重的安全漏洞（反序列化不可信的資料可能觸發遠端程式碼執行，是很多知名漏洞的根源）；且它是 Java 專用的，無法跨語言（其他語言的服務讀不懂 Java 序列化的位元組流）。JSON 可讀性好且跨語言通用，Protobuf/Kryo 則在效能和體積上遠優於原生序列化，因此實務中的持久化、RPC、快取多採用這些替代方案。

**詳細解析**：安全問題是最嚴重的——Java 原生反序列化會根據位元組流「重建任意類別的物件並呼叫其方法」，如果攻擊者能控制反序列化的輸入，就可能構造惡意的位元組流，利用類別路徑中某些類別的特殊行為（gadget chain）達成遠端程式碼執行，這類「反序列化漏洞」在歷史上造成過大量嚴重的安全事件。效能與體積上，原生序列化把大量類別元資料寫進位元組流，又慢又大；Protobuf 用預先定義的 schema 和緊湊的二進位編碼，體積小、速度快、還跨語言。JSON 雖然體積比 Protobuf 大，但人類可讀、除錯方便、生態成熟，適合對外 API。因此現代系統很少直接用 Java 原生序列化——對外用 JSON，內部高效能場景用 Protobuf/Kryo。

**面試回答方式**：列出三個缺點（效能/體積差、安全漏洞、無法跨語言），並特別強調「反序列化漏洞可導致遠端程式碼執行」這個安全風險（這是資深工程師最在意的點），再給出替代方案的定位（JSON 對外可讀、Protobuf 內部高效）。這種能從安全、效能、跨語言多角度批判原生序列化的回答，展現你有全面的工程判斷。
