# 題目

`HashMap` 的底層資料結構是什麼？put 和 get 的流程是怎樣的？JDK 8 做了什麼改進？

## 核心答案

JDK 8 的 `HashMap` 底層是「陣列 + 鏈結串列 + 紅黑樹」。陣列的每個位置稱為桶（bucket），put 時先用 key 的雜湊碼計算桶的索引，若該桶為空直接放入，若已有元素（雜湊衝突）就用鏈結串列串接；當一個桶內的鏈結串列長度超過 8 且陣列容量達到 64 時，鏈結串列會轉換成紅黑樹以把查找複雜度從 O(n) 降到 O(log n)。這是 JDK 8 相較 JDK 7（只有陣列 + 鏈結串列）的主要改進。

## 詳細解析

**資料結構**：核心是一個 `Node[] table` 陣列，每個元素是一個桶。發生雜湊衝突（不同 key 算出同一個桶索引）時，同一個桶內的多個 entry 用鏈結串列串接；當鏈結串列過長時轉為紅黑樹。

**put 流程**：

1. 用 key 的 `hashCode()` 經過擾動函式（高低位元互斥或）計算出雜湊值，再對陣列長度取模得到桶索引。
2. 若該桶為空，直接放入新節點。
3. 若桶不為空，遍歷桶內的鏈結串列（或紅黑樹）：找到 key 相等（`equals()`）的節點就覆蓋其 value；沒找到就把新節點加到鏈結串列尾端。
4. 若加入後鏈結串列長度超過閾值 8 且陣列長度 ≥ 64，把鏈結串列轉為紅黑樹。
5. 若元素總數超過「容量 × 負載因子（預設 0.75）」，觸發擴容（resize）。

**get 流程**：用 key 算出桶索引，定位到桶後，在桶內的鏈結串列或紅黑樹中用 `equals()` 找到 key 相等的節點回傳其 value。

**JDK 8 的改進——引入紅黑樹**：JDK 7 只有陣列 + 鏈結串列，當大量 key 雜湊衝突集中在同一個桶，鏈結串列會變得很長，查找退化成 O(n)（甚至可能被惡意構造雜湊碰撞攻擊）。JDK 8 在鏈結串列過長時轉為紅黑樹，把最壞情況的查找從 O(n) 改善到 O(log n)。

**擾動函式**：JDK 8 用 `(h = key.hashCode()) ^ (h >>> 16)` 把雜湊碼的高 16 位元和低 16 位元互斥或，讓高位元也能參與桶索引的計算，減少雜湊衝突（因為取模只用到低位元，若不擾動，高位元的差異就被浪費了）。

## 面試回答方式

這是高頻重點題，建議按「資料結構 → put/get 流程 → JDK 8 改進」的結構回答。資料結構先一句話點出「陣列 + 鏈結串列 + 紅黑樹」；流程講 put 時務必提到「雜湊衝突用鏈結串列、過長轉紅黑樹、超過負載因子擴容」這幾個關鍵；JDK 8 改進的核心是「引入紅黑樹把最壞查找從 O(n) 改善到 O(log n)」。如果能主動提到「擾動函式讓高位元參與計算減少衝突」這個細節，會是明顯的加分點，展現你讀過原始碼層級的設計。

## 常見追問

### 為什麼鏈結串列轉紅黑樹的閾值是 8，而且還需要陣列長度達到 64？

**核心答案**：閾值 8 是因為在雜湊分布均勻的理想情況下，單一桶內累積到 8 個元素的機率極低（符合帕松分布，機率約為千萬分之一），所以正常情況根本不會觸發樹化，一旦觸發通常代表雜湊確實有問題，此時才值得付出紅黑樹的維護成本；而「陣列長度需達 64」的條件是為了區分「是雜湊分布不均」還是「只是陣列太小」——如果陣列很小導致衝突，優先透過擴容（resize）來分散元素，而不是急著樹化。

**詳細解析**：紅黑樹雖然查找快，但維護成本（插入時的旋轉、平衡調整）比鏈結串列高，且樹節點佔用的記憶體約是普通節點的兩倍，所以樹化是「不得已才做」的優化。閾值設為 8 是基於統計——在負載因子 0.75 下，均勻雜湊時單桶元素數符合帕松分布，達到 8 的機率極小，正常使用幾乎不會樹化。而如果陣列長度還小於 64 就出現長鏈結串列，更可能的原因是「陣列太小導致大家擠在少數桶」而非「雜湊函式本身有問題」，這時透過擴容把元素重新分散到更多桶，比樹化更有效也更省成本，所以設計上優先擴容、達到 64 才允許樹化。

**面試回答方式**：分兩部分回答——閾值 8 講「統計上正常情況極少觸發、樹化有成本所以只在真正需要時才做」，容量 64 講「小陣列的衝突優先靠擴容解決而非樹化」。能區分這兩個條件各自的用意，展現你理解樹化是「有成本的最後手段」而非預設行為。

### HashMap 為什麼是執行緒不安全的？多執行緒下會發生什麼問題？

**核心答案**：`HashMap` 的 put、resize 等操作都沒有同步保護，多執行緒同時修改時可能發生資料覆蓋（兩個執行緒同時 put 到同一個桶，其中一個的寫入被另一個覆蓋而遺失）、以及在 JDK 7 的擴容過程中因為採用頭插法可能形成環狀鏈結串列導致後續 get 時無限迴圈（CPU 飆到 100%），JDK 8 改用尾插法避免了環化但仍可能有資料遺失。多執行緒場景應該用 `ConcurrentHashMap`。

**詳細解析**：JDK 7 的經典問題是——擴容時要把舊桶的鏈結串列搬移到新陣列，JDK 7 用頭插法（新節點插到鏈結串列頭部），多執行緒同時擴容時，鏈結串列的指標可能被交錯修改形成一個環（A→B→A），之後任何 get 操作遍歷到這個環就會陷入無限迴圈，是生產環境很難排查的嚴重故障。JDK 8 把擴容改成尾插法（保持原有順序），消除了環化問題，但多執行緒下仍然沒有同步，兩個執行緒同時 put 到同一位置仍可能互相覆蓋導致資料遺失。因此 `HashMap` 只適合單執行緒或唯讀共享，需要並行讀寫必須用 `ConcurrentHashMap`。

**面試回答方式**：先講「沒有同步導致資料覆蓋」這個根本問題，再補上「JDK 7 頭插法擴容會形成環導致 get 無限迴圈、JDK 8 尾插法修復了環化但仍有資料遺失」這個經典演進細節，最後給出「並行場景用 ConcurrentHashMap」的結論。能講出「環化死迴圈」這個具體故障是明顯的加分點，代表你了解這段著名的歷史問題。

### HashMap 的負載因子為什麼預設是 0.75？

**核心答案**：0.75 是「空間利用率」與「雜湊衝突機率」之間的折衷。負載因子越大，陣列填得越滿、越省空間，但衝突機率越高、查找越慢；負載因子越小，衝突越少、查找越快，但陣列越空、越浪費記憶體。0.75 是經過權衡後，讓大多數場景都能在時間與空間之間取得良好平衡的經驗值。

**詳細解析**：負載因子決定了「元素數量達到容量的多少比例時觸發擴容」。若設為 1.0，陣列要幾乎填滿才擴容，雖然省空間但衝突率高、鏈結串列變長；若設為 0.5，很快就擴容，衝突少但一半空間閒置、且頻繁擴容也有成本。0.75 在數學上（配合均勻雜湊的帕松分布分析）能讓單桶元素數維持在很低的水準，同時空間利用率也可接受，是 JDK 團隊綜合考量後選定的預設值。一般不建議隨意調整，除非有明確的、經過測量的特殊需求（例如極度在意記憶體可調高、極度在意查找速度可調低）。

**面試回答方式**：用「空間 vs 衝突機率的權衡」這個框架回答——講清楚調高和調低各自的代價，說明 0.75 是折衷的經驗值。這種把一個「魔術數字」還原成「兩個相互衝突的目標之間的平衡點」的回答方式，展現你理解設計背後的取捨，比只回答「就是預設值」深入得多。
