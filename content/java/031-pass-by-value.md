# 題目

Java 是值傳遞還是引用傳遞？為什麼在方法裡修改物件的欄位會影響呼叫方，交換兩個物件卻沒有效果？

## 核心答案

**Java 只有值傳遞**，沒有例外。混淆來自於「值」是什麼：基本型別傳遞的是**數值本身的拷貝**，物件傳遞的是**引用（位址）的拷貝**——拷貝的是那個指向物件的指標，不是物件本身。

這一條就能解釋全部現象。方法裡 `obj.setName("x")` 有效，因為拷貝來的引用指向**同一個物件**，順著它去改物件的內部狀態，呼叫方當然看得到。而 `swap(a, b)` 裡把兩個參數變數互換無效，因為改的只是**方法內那兩份引用拷貝**的指向，呼叫方的變數完全沒被碰到。

判斷的簡單方法是問：**這個操作改的是「變數指向誰」，還是「被指向的物件內部」？** 前者只影響方法內的拷貝，後者透過共用的物件影響雙方。真正的引用傳遞（例如 C++ 的 `&`）能讓方法內對參數的重新賦值直接改到呼叫方的變數，Java 做不到這件事。

## 詳細解析

**「Java 沒有引用傳遞」不是文字遊戲，它有可驗證的判準**：如果語言支援引用傳遞，就能寫出一個真正有效的 `swap` 方法。Java 寫不出來——這就是證明。C++ 的 `void swap(int& a, int& b)` 可以，C# 的 `ref` 參數也可以，Java 沒有對應的語法。

**String 的例子最常引起爭論**：方法裡對 `String` 參數重新賦值後呼叫方沒變，很多人歸因於「String 不可變」。這個歸因是錯的——即使是可變物件，重新賦值一樣不會影響呼叫方。真正的原因就是值傳遞。**不可變性是另一個獨立的性質**，它保證的是「就算你拿到同一個 String 也改不了它」，兩件事恰好都指向同一個結果，但機制不同。要驗證這一點，把 `String` 換成 `StringBuilder`：呼叫 `append` 有效（改物件內部），重新賦值無效（只改拷貝的引用）。

**陣列與集合也一樣，只是更容易誤導**：傳一個 `int[]` 進方法，`arr[0] = 5` 有效，因為陣列是物件、拷貝的引用指向同一塊；但 `arr = new int[10]` 無效。集合同理——`list.add(x)` 有效，`list = new ArrayList<>()` 無效。

**這個規則對 API 設計的實際影響是「別靠參數回傳結果」**：想讓方法回傳多個值時，Java 沒有 out 參數，該用的是回傳一個 record 或小型物件。有些程式碼用「傳一個大小為 1 的陣列或 `AtomicReference` 進去讓方法寫入」，那是在模擬引用傳遞——能動，但**把資料流藏在參數裡**，讀的人得追進方法才知道哪些參數會被寫入。回傳值把資料流寫在簽章上，永遠更清楚。

## 面試回答方式

先給明確結論——**Java 只有值傳遞**，然後立刻澄清爭議點：物件傳的是「引用的拷貝」，不是物件、也不是引用本身。用一個判準把話說死：**如果有引用傳遞，就能寫出有效的 swap；Java 寫不出來**。接著用「改變數指向誰 vs 改被指向的物件內部」這組對照解釋為什麼 `setName` 有效而互換無效。加分點有兩個：指出 **String 的例子與不可變性無關**（換成 `StringBuilder` 就能看出 append 有效、賦值無效，證明機制是值傳遞）；以及延伸到 API 設計——別用參數當出口，回傳 record 讓資料流寫在簽章上。

## 講稿

Java 只有值傳遞，沒有例外。混淆的地方在於值是什麼。基本型別傳的是數值本身的拷貝，物件傳的是引用的拷貝，也就是那個指向物件的位址被複製了一份，物件本身沒有被複製。

這一條就能解釋全部的現象。在方法裡改物件的欄位有效，因為拷貝來的引用指向同一個物件。但是把兩個參數互換沒有效果，因為改的只是方法內那兩份拷貝指向誰，呼叫方的變數根本沒被碰到。

我判斷的方法是問一句，這個操作改的是變數指向誰，還是被指向的物件內部。前者只影響方法內的拷貝，後者透過共用的物件影響雙方。

還有一個常見的誤解要澄清。字串在方法裡重新賦值不影響呼叫方，很多人說是因為字串不可變，這個歸因是錯的。換成 StringBuilder 就看得出來，呼叫 append 有效，重新賦值一樣無效。真正的原因就是值傳遞。

## 常見追問

### 那 Java 為什麼不提供引用傳遞？

**核心答案**：因為它會**讓呼叫端無法從程式碼判斷變數會不會被改**。在支援引用傳遞的語言裡，`foo(x)` 這一行看不出 `x` 會不會被方法重新賦值，必須去讀方法簽章甚至實作。Java 的設計取向是**盡量讓區域推理成立**——看著一段程式碼就能推斷它的行為，不必展開所有被呼叫的方法。統一成值傳遞讓「參數變數的指向永遠不會被方法改變」成為一條無例外的規則。

**詳細解析**：這個取捨在其他地方也一致：Java 沒有運算子多載（避免 `a + b` 藏著任意邏輯）、沒有巨集、預設不允許隱式型別轉換。代價是某些場景要多寫一點——需要回傳多個值時得定義一個型別，這在 `record` 出現之前確實囉嗦。C# 選了另一條路，用 `ref` 與 `out` 提供這個能力，但**強制呼叫端也要寫出關鍵字**（`foo(ref x)`），也就是把資訊補回呼叫點。這是同一個問題的兩種解法，Java 選了「不提供」，C# 選了「提供但要求標記」。

**面試回答方式**：把理由歸結到**區域推理**——呼叫端不必展開方法就能知道自己的變數不會被重新賦值。舉旁證說明這是一致的設計取向（沒有運算子多載、沒有巨集）。最後用 C# 的 `ref`/`out` 作對照：它提供了能力但強制呼叫端標記，說明這是同一個問題的兩種解法，而不是誰對誰錯。

### 傳入的物件在方法內被修改，怎麼防？

**核心答案**：三條路，成本由低到高。**第一，讓型別不可變**——沒有任何 setter，方法就算拿到引用也改不了，這是最徹底也最省事的做法。**第二，傳入前防禦性拷貝**——呼叫方自己 `new ArrayList<>(list)` 再傳進去，適合對方是不受控的第三方程式碼。**第三，傳入唯讀檢視**（`Collections.unmodifiableList`），但要記得它擋得住對方改、擋不住底層被自己改。

**詳細解析**：實務上更重要的是**在 API 契約裡把「會不會修改參數」講清楚**。JDK 自己就有兩種風格：`Collections.sort(list)` 就地修改，`list.stream().sorted()` 回傳新的。混用這兩種風格而不加說明是很多 bug 的來源。現代 Java 的傾向是**優先回傳新值而不是就地修改**，因為它讓資料流顯式、也讓程式碼更容易平行化與測試。就地修改仍然有它的位置——大型資料結構避免拷貝、效能關鍵路徑——但那應該是**經過量測的決定**，並且在方法名稱上表明（例如 `sortInPlace`）。

**面試回答方式**：給三條路並排出成本順序（不可變型別 > 防禦性拷貝 > 唯讀檢視），指出第三條的限制。然後把重點拉到 API 契約：`Collections.sort` 與 `stream().sorted()` 是兩種風格，混用而不說明是 bug 來源。收在一個立場：**預設回傳新值，就地修改要是量測後的決定並在命名上表明**。

### 值傳遞與 Java 的記憶體模型有什麼關係？

**核心答案**：關係在於**它決定了哪些東西是執行緒私有的**。方法的參數與區域變數存在該執行緒的**虛擬機器堆疊**裡，每個執行緒有自己的一份，所以參數變數本身天然沒有競爭問題。有競爭的是**它指向的堆積物件**——多個執行緒可以持有指向同一物件的引用拷貝，透過它同時讀寫物件的欄位。**值傳遞讓「變數」安全，但完全不保護「被指向的物件」**。

**詳細解析**：這解釋了為什麼併發問題總是集中在共享的可變物件上，也解釋了為什麼「盡量用區域變數與不可變物件」是最有效的併發策略——區域變數執行緒私有，不可變物件不會被寫入，兩者都不需要同步。逃逸分析更把這件事推進一步：JIT 若能證明某個物件從未逃出方法（沒有被存到欄位、沒有被回傳、沒有被傳給可能保存它的方法），就可以把它**拆解成純粹的區域變數**甚至完全不配置，同時省掉同步。**「值傳遞」與「執行緒私有」在這裡接上了**——理解這條線比單純背「Java 是值傳遞」有價值得多。

**面試回答方式**：把答案定位在「**哪些東西是執行緒私有的**」：參數與區域變數在各自的執行緒堆疊上、天然無競爭，被指向的堆積物件才是共享點。由此導出最有效的併發策略——多用區域變數與不可變物件。加分點是接上逃逸分析：JIT 證明物件沒有逃出方法就能拆解它甚至消除同步，這正好是同一條線的延伸。
