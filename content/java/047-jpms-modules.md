# 題目

模組系統要解決什麼問題？為什麼多數應用專案至今仍然不用它？

## 核心答案

它解決三個問題。**強封裝**——`public` 在模組化之前等於「全世界都能用」，即使那是一個 `internal` 套件；模組讓 `exports` 明確決定哪些套件對外可見，沒 export 的套件連反射都碰不到（除非 `opens`）。**可靠的依賴**——類別路徑是一個扁平的清單，缺了某個 JAR 要等到執行期 `NoClassDefFoundError` 才發現，模組的 `requires` 讓依賴在**啟動時就被驗證**，也能偵測到重複與循環。**可裁剪的執行環境**——`jlink` 可以只打包實際用到的模組，做出幾十 MB 的執行映像檔而不是整個 JDK。

多數應用不用它的理由也很實際：**收益主要落在函式庫與平台，成本主要落在應用**。應用要模組化必須所有依賴都模組化（否則得用自動模組這個過渡機制），而反射密集的框架（Spring、Hibernate、Jackson）需要大量 `opens` 宣告，寫完之後封裝其實已經破了大半。加上 Spring Boot 的胖 JAR 與容器化已經解決了「打包與隔離」的實務需求，**動機不足**。

## 詳細解析

**JDK 自身的模組化才是這件事最大的成果**：JDK 9 把整個平台拆成約 70 個模組，讓 `java.base` 這類核心與 `java.xml`、`java.sql` 分離。副作用是**內部 API 被真的封起來了**——`sun.misc.Unsafe`、`com.sun.*` 這些長期被函式庫濫用的東西不再可存取。這造成了 JDK 8 到 9 之間著名的升級陣痛，但它是必要的：**沒有封裝，JDK 就無法安全地演進內部實作**。今天能有 ZGC、虛擬執行緒這些大改動而不擔心打壞使用者程式，模組化是前提之一。

**automatic module 是為了讓遷移可行的過渡設計**：把一個非模組化的 JAR 放到 module path 上，它會變成一個「自動模組」——名稱由 JAR 檔名推導（或讀 `Automatic-Module-Name` 資訊清單屬性），**export 全部套件、require 所有其他模組**。它讓應用可以在依賴還沒模組化時先模組化自己，代價是封裝形同虛設。函式庫作者即使不完全模組化，**也應該在 MANIFEST 加上 `Automatic-Module-Name`**，因為那能固定模組名，避免下游因為檔名變動而編譯失敗。

**opens 與 exports 的區別是理解 JPMS 的關鍵**：`exports` 給的是**編譯期與執行期的一般存取**，`opens` 給的是**執行期的深度反射存取**（包含私有成員）。框架需要的是後者——Spring 要反射注入私有欄位、Jackson 要反射讀寫私有屬性。所以模組化的應用通常要寫 `opens com.example.model to com.fasterxml.jackson.databind;`。**寫得精確（限定 to 某個模組）還有意義，寫成 `open module` 就等於放棄封裝**。

**該不該用的判準是「你是不是在做函式庫或平台」**：函式庫作者用它可以明確劃出公開 API 與內部實作，防止下游依賴內部細節（這對維護長期相容性極有價值）。應用作者的收益小得多——應用的內部結構本來就不對外，而依賴驗證與裁剪已經有其他工具。**但 `jlink` 做出的小型執行映像檔在容器化場景仍有實際價值**，這是應用端最可能的動機。

## 面試回答方式

先給**三個目標**（強封裝、可靠依賴、可裁剪執行環境）並各配一句具體說明。然後誠實回答為什麼沒普及——**收益在函式庫與平台、成本在應用**，而反射密集的框架需要大量 `opens`，寫完封裝已破大半，加上胖 JAR 與容器已解決打包隔離需求。加分點放在三處：**JDK 自身模組化才是最大成果**（封住 `sun.misc.Unsafe` 等內部 API，是後來能安全推出 ZGC、虛擬執行緒的前提）；**`opens` 與 `exports` 的差別**（深度反射 vs 一般存取），這是理解 JPMS 的關鍵；以及**函式庫作者即使不模組化也該加 `Automatic-Module-Name`**，這是一個很具體的實務建議。收在判準：做函式庫或平台就值得，做應用主要是為了 `jlink`。

## 講稿

模組系統要解決三個問題。第一是強封裝。在模組化之前，public 等於全世界都能用，就算那是一個內部套件。模組讓你明確宣告哪些套件對外可見。

第二是可靠的依賴。類別路徑是扁平的清單，缺了某個 JAR 要等到執行期才發現。模組的依賴宣告會在啟動時就驗證，也能偵測重複跟循環。

第三是可裁剪的執行環境，可以只打包用到的模組，做出幾十 MB 的映像檔而不是整個 JDK。

至於為什麼多數應用不用，我覺得原因很實際。收益主要落在函式庫跟平台，成本主要落在應用。反射密集的框架需要大量的開放宣告，寫完之後封裝其實已經破了大半。加上胖 JAR 跟容器化已經解決了打包跟隔離的需求，動機不足。

不過我想強調，JDK 自己的模組化才是這件事最大的成果。它把內部 API 真的封起來了，所以後來才能安全地推出新的垃圾收集器跟虛擬執行緒這些大改動。

## 常見追問

### 類別路徑與模組路徑可以混用嗎？

**核心答案**：可以，這正是遷移策略的基礎。放在 class path 上的所有 JAR 會被合併進一個叫做 **unnamed module（未具名模組）** 的東西——它可以讀所有模組、export 所有套件，行為與 JDK 8 幾乎相同。放在 module path 上的具名模組**不能 require 未具名模組**（因為它沒有名字），這是唯一的硬限制，也是遷移必須「由下而上」的原因：依賴要先模組化，使用者才能模組化。

**詳細解析**：實務上的遷移路徑是**由上而下先用自動模組**：把應用自己模組化，依賴仍是非模組化的 JAR 但放到 module path 變成自動模組。這樣可以先享受到自己模組內的封裝與依賴宣告，等依賴逐步提供真正的 `module-info` 再切換。要注意**同一個套件不能同時出現在兩個模組**（split package），這在舊的函式庫上是常見的障礙——例如某些 JAR 把類別放在 `javax.annotation` 這種 JDK 也有的套件下，會直接衝突。診斷這類問題可以用 `jdeps` 分析依賴與偵測對內部 API 的使用。

**面試回答方式**：先給機制（class path 合併成未具名模組、具名模組不能 require 它），並指出這是遷移必須由下而上的根本原因。然後給實務路徑：先用自動模組讓應用自己模組化。加分點是提出 **split package 是常見障礙**（舊 JAR 用了與 JDK 相同的套件名會直接衝突），以及診斷工具 `jdeps`。

### jlink 產出的映像檔與容器映像檔的關係是什麼？

**核心答案**：兩者解決不同層次的問題但可以疊加。`jlink` 減少的是**執行環境本身的大小**——只包含用到的 JDK 模組，把 300 MB 以上的完整 JDK 縮到 40 到 60 MB。容器映像檔則是**整個檔案系統的封裝**。把 jlink 的產出放進一個 distroless 或 alpine 基底映像檔，可以做出一百 MB 以內的完整應用映像檔，冷啟動的拉取時間與攻擊面都明顯下降。

**詳細解析**：不過**它與 GraalVM 原生映像檔是競爭關係而非互補**。原生映像檔把應用 AOT 編譯成單一執行檔，啟動時間從秒級降到毫秒級、記憶體佔用降到幾分之一，代價是**建置時間長、反射需要顯式配置、無法用 JIT 的執行期最佳化所以峰值吞吐通常較低**。選擇的判準是工作負載形態：**短命、高頻擴縮的無伺服器函式適合原生映像檔；長時間執行、追求峰值吞吐的服務適合 jlink 加 JIT**。另外 CDS（類別資料共享）與 AppCDS 是第三條路——保留 JIT 但改善啟動，成本遠低於原生映像檔。

**面試回答方式**：先區分兩者的層次（執行環境大小 vs 檔案系統封裝）並說明疊加後的具體效果（一百 MB 以內、拉取時間與攻擊面下降）。真正的加分點是把 **GraalVM 原生映像檔定位成競爭方案**，給出它的取捨（啟動快、記憶體省、但建置久、反射要配置、峰值吞吐較低），並用工作負載形態給出選擇判準。最後補 AppCDS 作為成本更低的中間選項。

### 強封裝對測試有什麼影響？

**核心答案**：測試常需要存取被測類別的內部（套件私有成員、私有欄位），而模組的封裝會擋住這件事。標準解法有三個：**測試程式碼與被測程式碼放在同一個模組的同一個套件**（最乾淨，Maven 的 `src/test/java` 預設就是這樣）、**用 `--add-opens` 在測試執行時打開特定套件**（build 工具設定，不汙染正式的 `module-info`）、或者**用白箱模組修補**（`--patch-module` 把測試類別注入被測模組）。

**詳細解析**：這件事其實反映了一個更普遍的設計訊號：**需要大量存取私有成員才能測的程式碼，通常是設計耦合過緊的徵兆**。模組系統把這個成本顯性化了——以前用反射硬闖沒人擋，現在要在 build 設定裡寫一行 `--add-opens`，那行設定就是一個看得見的技術債標記。實務上比較健康的方向是**透過公開行為測試**（給定輸入、驗證輸出與副作用），只在真的必要時才打開封裝。至於函式庫的使用者遇到框架需要反射的情況，優先用**精確的 `opens ... to ...`** 而不是整個模組 open，讓開放範圍留下記錄。

**面試回答方式**：給三個標準解法並排出偏好順序（同模組同套件 > build 層的 `--add-opens` > `--patch-module`）。真正的加分點是把它讀成設計訊號：**需要大量存取私有成員才能測，通常代表耦合過緊**，而模組系統把這個成本顯性化成一行看得見的 build 設定。收在建議：優先透過公開行為測試，必要時用精確的 `opens ... to ...` 保留記錄。
