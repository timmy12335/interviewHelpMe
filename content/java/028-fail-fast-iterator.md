# 題目

為什麼在 for-each 迴圈裡刪除元素會拋 `ConcurrentModificationException`？fail-fast 是保證還是盡力而為？

## 核心答案

集合內部有一個 `modCount` 欄位，**每次結構性修改**（新增、刪除，但不含更新既有元素的值）就加一。建立迭代器時它會把當時的 `modCount` 記進 `expectedModCount`，之後每次 `next()` 都比對兩者；不相等就拋 `ConcurrentModificationException`。for-each 語法糖背後就是迭代器，所以在迴圈裡直接呼叫 `list.remove(x)` 會改到 `modCount` 卻沒改 `expectedModCount`，下一次迭代就爆。

關鍵在於 **fail-fast 是盡力而為（best-effort），不是保證**。`modCount` 沒有任何同步，多執行緒下對它的讀寫沒有可見性保證，所以不能靠這個例外來偵測併發問題。JDK 文件寫得很明白：「拋出這個例外的程式碼不應該依賴它來判斷正確性，它只是用來偵測 bug。」正確的做法是**用 `Iterator.remove()`**（它會同步更新 `expectedModCount`），或用 `removeIf`，或改用 `CopyOnWriteArrayList` 這類 fail-safe 的容器。

## 詳細解析

**「結構性修改」的定義很精確**：改變元素**數量**的操作才算，`list.set(i, v)` 或 `map.put` 到既有鍵都不算，所以在迭代中改值是合法的。這解釋了一個常見的困惑——為什麼有時候在迴圈裡動集合沒事。

倒數第二個元素的刪除是最惡名昭彰的陷阱：`ArrayList` 的迭代器判斷「還有沒有下一個」用的是 `cursor != size`。刪掉倒數第二個元素後 size 減一，`cursor` 剛好等於新的 size，於是 `hasNext()` 回傳 false、迴圈**正常結束**，`next()` 從來沒被呼叫，檢查也就沒發生。結果是沒有例外、但少處理了最後一個元素——這種靜默的錯誤比拋例外危險得多，也正好說明「盡力而為」的意思。

**fail-safe 容器走的是另一條路**：`CopyOnWriteArrayList` 的迭代器持有的是**建立當下那個陣列的快照**，之後的修改會產生新陣列而不動舊的，所以迭代永遠不會拋例外，但**看到的是舊資料**。`ConcurrentHashMap` 的迭代器是弱一致的（weakly consistent）——它保證不拋例外、保證每個元素最多回傳一次，但不保證看得到迭代開始後的修改。這兩者都是用「放棄即時性」換「不中斷」，適合讀多寫少且能容忍稍舊資料的場景。

選型的判準是「舊資料可不可以接受」：能接受就用 fail-safe 容器；不能接受就代表需要真正的同步，那該用鎖或 `ConcurrentHashMap` 的原子方法（`compute`、`merge`），而不是期待例外會幫你發現問題。把 CME 當成「有人寫錯了」的訊號，而不是併發控制機制，是這題最重要的判斷。

## 面試回答方式

先講**機制**：`modCount` 記錄結構性修改次數，迭代器建立時快照成 `expectedModCount`，每次 `next()` 比對。接著定義清楚「結構性修改」——只有改變元素數量才算，所以迭代中 `set` 值是合法的。然後把重點放在 **fail-fast 是盡力而為不是保證**，並用「刪除倒數第二個元素」這個例子證明：`hasNext` 用 `cursor != size` 判斷，刪掉後迴圈提前結束，**沒有例外但少處理一個元素**——靜默錯誤比例外危險。最後給選型：能容忍舊資料就用 `CopyOnWriteArrayList` 或 `ConcurrentHashMap` 的弱一致迭代器；不能容忍就要真的同步。收在一句判斷：把 CME 當成「有人寫錯了」的訊號，不要當成併發控制機制。

## 講稿

集合內部有一個計數器，每次結構性修改就加一。建立迭代器的時候會把當下的值記起來，之後每次取下一個元素都比對，不相等就拋例外。for-each 背後就是迭代器，所以在迴圈裡直接呼叫集合的刪除方法，計數器改了、迭代器記的沒改，下一輪就爆掉。

要注意結構性修改的定義很精確，只有改變元素數量才算。在迭代中修改某個元素的值是合法的，這解釋了為什麼有時候在迴圈裡動集合沒事。

我想強調的是，這個機制是盡力而為，不是保證。最好的例子是刪除倒數第二個元素。刪掉之後，判斷還有沒有下一個的條件剛好成立，迴圈正常結束，檢查根本沒被觸發。結果是沒有例外，但少處理了最後一個元素。這種靜默的錯誤比拋例外危險多了。

所以我的結論是，把這個例外當成有人寫錯了的訊號，不要把它當成併發控制機制。真的要併發安全，該用鎖或併發容器的原子方法。

## 常見追問

### removeIf 與在迴圈裡用 Iterator.remove 有什麼差別？

**核心答案**：語意相同、成本不同。`Iterator.remove()` 在 `ArrayList` 上每刪一個就要搬移後面全部元素，刪 k 個元素是 O(n·k)；`ArrayList.removeIf` 覆寫過，它先用一個位元集標記要刪的位置，再一次性壓縮陣列，總成本是 O(n)。所以要刪掉大量元素時 `removeIf` 明顯更快，而且意圖更清楚。

**詳細解析**：`removeIf` 還有一個正確性上的好處——它**在方法內部完成全部修改**，不存在「迭代到一半集合處於中間狀態」的視窗，也不會忘記用迭代器的 remove 而誤用集合的 remove。它同樣有 fail-fast 檢查：如果傳入的斷言（predicate）本身去修改了集合，方法結束時會偵測 `modCount` 不符並拋例外。另外要注意 `LinkedList` 上兩者差別不大，因為它的刪除本來就是 O(1)（拿到節點後改指標），瓶頸在遍歷而不在搬移。選 removeIf 的主要理由其實是可讀性與不易寫錯，效能是附帶的。

**面試回答方式**：先說語意相同、成本不同，再給具體複雜度對比：`ArrayList` 上迭代器刪除是 O(n·k)、`removeIf` 用位元集標記加一次壓縮是 O(n)。補充 `LinkedList` 上差別不大，因為刪除本來就是 O(1)。最後把主要理由放回可讀性與不易寫錯，避免給人「只會談效能」的印象。

### ConcurrentHashMap 的「弱一致」迭代器具體保證什麼？

**核心答案**：保證三件事——**不會拋 ConcurrentModificationException**、**每個元素最多回傳一次**、回傳的元素在迭代器建立時或之後的某個時刻確實存在於 Map 中。不保證的是：迭代開始後新增的元素**可能看到也可能看不到**，以及看到的不是某個一致的時間點的快照。也就是說它反映的是一段時間內的變化過程，而不是某一瞬間的狀態。

**詳細解析**：這個設計是必要的取捨。要提供強一致的快照，要嘛在迭代期間鎖住整個 Map（併發容器就失去意義），要嘛複製一份（`ConcurrentHashMap` 可能很大，複製成本無法接受）。弱一致讓迭代**不阻塞寫入**，代價是使用方必須知道自己看到的可能不完整。實務上的後果是：不要用迭代的結果做需要精確性的事，例如「遍歷算總和然後拿去對帳」；`size()` 也有同樣的問題（它是估計值，用 `LongAdder` 風格的計數累加，不是精確快照）。需要精確就要在應用層加序列化點，或者換一個能提供快照的資料結構。

**面試回答方式**：把「保證什麼」與「不保證什麼」分開講清楚，這比籠統說「弱一致」有說服力得多。接著解釋為什麼必須這樣設計——強一致要嘛鎖整個 Map、要嘛複製，兩條路在併發容器上都不可行。收在可操作的建議：不要拿遍歷結果做需要精確性的事，`size()` 同樣是估計值。

### 為什麼 modCount 沒有加 volatile？

**核心答案**：因為 fail-fast 從一開始就不是為併發設計的。`ArrayList`、`HashMap` 這些容器的契約就是「非執行緒安全」，`modCount` 的用途是幫**單執行緒**的使用者抓到「在迭代中修改集合」這個 bug。為這個目的加 `volatile` 會讓每一次新增與刪除都付出記憶體屏障的成本——在絕大多數不出錯的正常路徑上白付代價，去換一個本來就不該依賴的偵測能力。

**詳細解析**：這是一個很典型的 API 設計取捨：偵錯輔助不應該讓正常路徑變慢。同樣的思路可以在別處看到——斷言（assertion）預設關閉、`HashMap` 的樹化門檻設得很高、JIT 的去最佳化路徑不影響快路徑。反過來說，如果真的需要在併發下偵測誤用，正確的做法是用專門的工具（例如 `Collections.synchronizedList` 搭配外部同步、或靜態分析、或壓測時打開額外檢查），而不是把成本加在每一次寫入上。能把「為什麼不加」講成一個設計取捨而不是疏漏，是這題的加分點。

**面試回答方式**：直接指出這些容器的契約本來就是非執行緒安全，`modCount` 是給單執行緒使用者抓 bug 用的。然後把它提升成一個通用原則：偵錯輔助不該讓正常路徑變慢，並舉斷言預設關閉、樹化門檻很高當旁證。最後說明真要在併發下偵測誤用該用專門工具，而不是把成本壓在每次寫入上。
