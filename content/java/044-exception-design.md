# 題目

在分層架構裡，底層的例外該怎麼往上傳遞？什麼時候該包裝成自訂例外？

## 核心答案

判斷的核心是：每一層應該拋出「用該層的語言描述的錯誤」。資料存取層拋 `SQLException` 是合理的，但讓它穿透到服務層與控制器就不合理——上層被迫理解 SQL 的細節，而且換掉持久化技術時所有呼叫端都要改。所以邊界上要轉譯：`SQLException` 轉成 `OrderRepositoryException` 或更具語意的 `DuplicateOrderException`。

包裝時的三條規則。**第一，一定要保留原因**（`new XxxException(msg, cause)`）——丟掉 cause 等於丟掉除錯所需的全部資訊，這是最常見也最致命的錯誤。**第二，不要為了包裝而包裝**——如果上層對這個錯誤沒有不同的處理方式，多一層自訂例外只是增加噪音。**第三，訊息要包含定位資訊**（哪個訂單、哪個使用者、哪個外部系統），但**不能包含機密**（密碼、金鑰、完整的卡號）。

至於「該不該往上拋」，判準是這一層能不能做出有意義的處理。能重試、能降級、能補償就在這裡處理；只能記一行日誌然後繼續往上，那就直接往上拋——在每一層都 catch 再 rethrow 只會讓堆疊追蹤變長、日誌重複。

## 詳細解析

「catch 之後只記日誌」是最普遍的反模式：它讓錯誤在日誌裡出現三四次（每一層各記一次），真正的處理卻沒有發生，而且上層可能誤以為呼叫成功了。正確的做法是只在能處理的地方 catch，在最外層統一記錄（Web 應用就是全域例外處理器，批次程式就是主迴圈）。這樣每個錯誤在日誌裡只出現一次，而且帶著完整的堆疊。

檢查例外與未檢查例外的選擇有一個實用判準：呼叫方是否有合理的方式從中恢復。找不到檔案時呼叫方可以改用預設設定——那可以是檢查例外；資料庫連線設定錯誤時呼叫方什麼都做不了——那該是未檢查例外。現實中 Java 的檢查例外被大量濫用（`SQLException` 是檢查例外，但幾乎沒有呼叫方能從中恢復），導致到處都是空的 catch 區塊。現代框架的傾向是把持久化與遠端呼叫的例外一律轉成未檢查例外（Spring 的 `DataAccessException` 家族就是這樣做的），把「要不要處理」的決定交還給呼叫方。

**自訂例外的層級設計**：實務上有效的做法是**每個模組一個基底例外**（`OrderException`），底下再依處理方式（而不是依成因）分幾個子類別——`OrderNotFoundException`（對應 404）、`OrderConflictException`（對應 409）、`OrderProcessingException`（對應 500）。**依處理方式分類**讓例外處理器可以直接映射，而依成因分類會產生幾十個上層根本不區分的型別。

**例外不該用於流程控制**：`findUser` 找不到時該回傳 `Optional` 還是拋例外？如果「找不到」是**預期中的正常情況**（例如檢查使用者名稱是否可用），用 `Optional`；如果它代表**呼叫方的前提被違反**（例如用剛登入的 ID 查不到使用者），拋例外。例外的建立成本主要在填充堆疊追蹤，在高頻路徑上用例外做流程控制會有可觀的開銷（必要時可以覆寫 `fillInStackTrace` 建立無堆疊例外，但那應該是量測後的決定）。

## 面試回答方式

先給核心原則——每一層拋出用該層語言描述的錯誤，並用「換掉持久化技術時所有呼叫端都要改」說明讓底層例外穿透的代價。接著給包裝的三條規則，把「**一定要保留 cause**」放最前面並說明丟掉它等於丟掉除錯資訊。然後回答「該不該往上拋」：判準是這一層能不能做出有意義的處理，並主動點名最普遍的反模式——**catch 之後只記日誌**，它讓同一個錯誤在日誌出現三四次卻沒有真正處理。加分點有兩個：檢查例外的判準是「呼叫方能不能恢復」，而 Spring 把持久化例外全轉未檢查正是因為現實中沒人能恢復；以及自訂例外要依處理方式分類而非依成因分類，這樣才能直接映射到回應碼。

## 講稿

我判斷的核心是，每一層應該拋出用該層的語言描述的錯誤。資料存取層拋 SQL 例外是合理的，但讓它穿透到服務層跟控制器就不合理，上層被迫理解 SQL 的細節，而且換掉持久化技術的時候所有呼叫端都要改。

包裝的時候有三條規則。第一，一定要保留原因，丟掉它等於丟掉除錯所需的全部資訊。第二，不要為了包裝而包裝，上層如果沒有不同的處理方式，多一層只是噪音。第三，訊息要有定位資訊，但不能包含機密。

該不該往上拋，判準是這一層能不能做出有意義的處理。能重試、能降級、能補償就在這裡處理。只能記一行日誌然後繼續往上，那就直接往上拋。

我想特別點名一個最普遍的反模式，就是 catch 之後只記日誌。它讓同一個錯誤在日誌裡出現三四次，真正的處理卻沒有發生，而且上層可能誤以為呼叫成功了。正確的做法是只在能處理的地方 catch，在最外層統一記錄。

## 常見追問

### 自訂例外該繼承 Exception 還是 RuntimeException？

**核心答案**：**預設繼承 `RuntimeException`**，除非有明確理由要強迫呼叫方處理。判準是「呼叫方是否有合理的恢復方式」——多數業務例外沒有（找不到訂單時服務層能做的就是往上傳到控制器轉成 404），強迫每一層宣告 `throws` 只會讓簽章被汙染，並誘發空的 catch 區塊。少數真的需要呼叫方在當場做決定的情況（例如「額度不足，可以改用其他支付方式」），檢查例外能起到提醒作用。

**詳細解析**：檢查例外還有一個結構性問題——**它會傳染**。一個底層方法加上 `throws IOException`，整條呼叫鏈的簽章都要改，這讓它與 lambda、串流、以及各種函式介面嚴重衝突（`Function.apply` 不宣告 throws）。這是為什麼現代 Java 生態幾乎一致地選擇未檢查例外：Spring、Hibernate、以及大多數新的函式庫都是如此。但這不代表檢查例外是設計失誤——它強迫思考錯誤路徑的意圖是好的，問題出在 JDK 自己把太多「無法恢復」的情況做成檢查例外，稀釋了這個訊號。誠實地講出「概念好但用法失準」比一面倒地否定更有說服力。

**面試回答方式**：給明確的預設立場（繼承 `RuntimeException`）與判準（呼叫方能否恢復）。加上結構性理由——**檢查例外會傳染**，並與 lambda、串流的函式介面衝突，這解釋了為什麼整個現代生態都選未檢查。收在一個平衡的評價：檢查例外的意圖是好的，問題出在 JDK 把太多無法恢復的情況做成檢查例外而稀釋了訊號。

### 例外訊息裡該放什麼、不該放什麼？

**核心答案**：該放的是定位與判斷所需的資訊——哪個實體（訂單 ID）、哪個外部系統、哪個階段、以及期望值與實際值的對比（「期望狀態 PAID，實際 CANCELLED」）。**不該放的是機密與個資**（密碼、token、完整卡號、身分證號），以及**對使用者顯示的文案**——面向使用者的訊息應該在最外層依語系產生，例外訊息是給工程師看的。

**詳細解析**：一個實用的檢驗是問：只看這則訊息（不看程式碼、不看其他日誌），能不能知道下一步要查什麼？「更新失敗」不行，「訂單 12345 從 PAID 轉 SHIPPED 失敗，實際狀態為 CANCELLED」可以。另一個常被忽略的點是例外訊息會進入日誌，而日誌可能流向第三方系統（集中式日誌、監控 SaaS），所以個資的合規要求同樣適用。實務上可以在自訂例外的基底類別裡提供結構化欄位（`entityId`、`errorCode`）而不只是字串訊息，讓日誌能結構化輸出並被查詢——字串訊息適合人讀，結構化欄位適合機器查，兩者都需要。

**面試回答方式**：把該放與不該放各列清楚，並給出可操作的檢驗——只看這則訊息能不能知道下一步查什麼，配上「更新失敗」與具體訊息的對比。加分點是指出例外訊息會進入日誌並可能流向第三方系統，所以個資合規同樣適用；以及建議在基底例外裡提供結構化欄位，讓人讀與機器查兩種需求都被滿足。

### 為什麼說 finally 裡不該有 return？

**核心答案**：因為 **`finally` 的 return 會吞掉正在傳播的例外**，也會覆蓋 try 區塊的 return 值。方法看起來正常回傳，實際上錯誤憑空消失——這是極難除錯的一類 bug，因為沒有任何痕跡。同樣的道理適用於在 `finally` 裡 `break`、`continue`，或拋出新的例外。

**詳細解析**：`try-with-resources` 正是為了處理這類問題而設計的：它在資源關閉時如果又拋例外，會把關閉的例外**加為主例外的 suppressed 例外**而不是取代它，`printStackTrace` 會一併印出（標記為 `Suppressed:`）。手寫 try-finally 關閉資源時很難做到這件事，這是應該一律用 try-with-resources 的實際理由，而不只是為了少寫幾行。另外要注意 **`finally` 不是萬能的**——`System.exit`、JVM 崩潰、以及守護執行緒在 JVM 結束時都不會執行 `finally`，所以真正重要的清理（釋放外部鎖、回滾遠端交易）不能只靠它，需要在外部系統設超時或補償機制。

**面試回答方式**：先給機制與後果——`finally` 的 return 會吞掉傳播中的例外，錯誤憑空消失且沒有痕跡。然後用 `try-with-resources` 的 suppressed 例外機制說明 JDK 怎麼正確處理同一個問題，這是「該一律用它」的實際理由。加分點是提醒 `finally` 不是萬能的：`System.exit` 與 JVM 崩潰都不會執行它，所以跨系統的清理需要超時或補償機制。
