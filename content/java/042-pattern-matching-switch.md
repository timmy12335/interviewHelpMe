# 題目

switch 表達式與傳統 switch 差在哪？模式比對加上密封類別能達成什麼？

## 核心答案

switch **表達式**（JDK 14）與 switch **陳述式**有四個實質差異：**有回傳值**（可以直接賦值給變數）、**不會貫穿**（用 `->` 分支，不需要 `break`）、**必須窮盡**（編譯器要求涵蓋所有情況，否則編譯錯誤）、**多標籤合併**（`case A, B ->`）。前三點都在消除傳統 switch 的實際錯誤來源——忘記 `break` 造成的貫穿、漏掉分支造成的靜默失敗。

模式比對（JDK 21 正式）讓 `case` 標籤可以是**型別模式**（`case Circle c ->`，比對成功後直接得到已轉型的變數）與**記錄模式**（`case Point(int x, int y) ->`，解構出元件）。與**密封類別**組合起來威力最大：密封類別限定了子型別的集合，編譯器因此**知道所有可能的情況**，可以在漏掉某個子型別時直接報錯——這把「新增一個子類別後忘記更新某處 switch」這個經典 bug 從執行期移到編譯期。

## 詳細解析

**窮盡性檢查是整套設計的核心價值**。傳統的多型做法（把行為放進每個子類別的方法）也能避免遺漏，但它要求把所有行為都塞進資料型別裡——當行為屬於別的關注點（例如序列化、UI 渲染、報表產生）時，硬塞進領域物件會汙染它。**密封類別加模式比對讓「行為在外部、但仍然有窮盡性保證」成為可能**，這正好補上了物件導向與函式式在「表達式問題」上各自的弱點。

**null 的處理改變了**：傳統 switch 對 null 會拋 `NullPointerException`。新的 switch 允許寫 `case null ->` 明確處理；**如果沒有寫 `case null` 也沒有 `default`，仍然拋 NPE**（保持相容）。這是刻意的設計：讓 null 從「隱含的陷阱」變成「必須明確決定的分支」。搭配 `case null, default ->` 可以把兩者合併。

**守衛（guard）補上了條件判斷**：`case Integer i when i > 100 ->` 讓模式比對可以附加條件。要注意**守衛不參與窮盡性判斷**——加了守衛的分支不算涵蓋該型別，所以仍然需要一個沒有守衛的分支或 `default`。這常常讓人困惑，但邏輯是對的：編譯器無法證明 `when` 條件必然成立。

**順序變得有意義**：模式比對的 case 是**由上而下依序測試**，所以更具體的模式必須寫在更一般的模式前面。如果把 `case Object o ->` 寫在前面，後面的所有分支都變成無法到達——好消息是**編譯器會直接報錯**（dominance check），不會讓這個錯誤溜過去。這與 `catch` 區塊的順序規則是同一個道理。

**什麼時候還是該用多型**：如果行為天然屬於那個型別、且未來會頻繁新增子型別，多型仍然更好——新增子型別時只要實作方法，不必找出散落各處的 switch。**判準是「變化的方向」**：常新增型別就用多型，常新增操作就用密封類別加模式比對。這正是表達式問題的兩邊，而 Java 現在兩邊都支援。

## 面試回答方式

先給 switch 表達式的**四個實質差異**（有值、不貫穿、必須窮盡、多標籤），並指出前三點都在消除實際的錯誤來源。接著講模式比對與密封類別的組合，核心是**窮盡性檢查把「新增子類別後忘記更新某處 switch」從執行期移到編譯期**。真正拉開差距的是後半段：說明它補上了**表達式問題**的另一邊——傳統多型要求把所有行為塞進型別裡，密封類別加模式比對讓行為留在外部卻仍有窮盡性保證。再給兩個實務細節：**守衛不參與窮盡性判斷**（所以仍需要無守衛分支）、**case 由上而下測試但編譯器會擋掉被支配的分支**。收在選型判準：常新增型別用多型，常新增操作用模式比對。

## 講稿

switch 表達式跟傳統的陳述式有四個實質差異。它有回傳值可以直接賦值、用箭頭分支不會貫穿、必須窮盡所有情況、還可以多標籤合併。前三點都在消除真實的錯誤來源，像是忘記 break 造成的貫穿。

模式比對讓 case 標籤可以是型別模式或記錄模式，比對成功之後直接拿到已經轉型的變數，或是解構出元件。

跟密封類別組合起來威力最大。密封類別限定了子型別的集合，編譯器因此知道所有可能的情況，漏掉某個子型別就直接報錯。這把新增子類別之後忘記更新某處 switch 這個經典錯誤，從執行期移到了編譯期。

我覺得更深一層的價值在這裡。傳統的多型也能避免遺漏，但它要求把所有行為都塞進資料型別。當行為屬於別的關注點，像是序列化或報表產生，硬塞進領域物件會汙染它。密封類別加模式比對，讓行為留在外面卻仍然有窮盡性保證。

所以選型的判準是變化的方向。常新增型別就用多型，常新增操作就用模式比對。

## 常見追問

### 什麼是表達式問題（Expression Problem）？

**核心答案**：它指的是一個兩難：一個系統有**資料型別**與**操作**兩個維度，我們希望**新增任一維度時都不必修改既有程式碼**，但傳統的做法只能滿足一邊。**物件導向**（每個型別實作方法）容易新增型別（加一個類別即可），但新增操作要修改所有既有類別。**函式式／模式比對**（每個操作 switch 所有型別）容易新增操作（加一個函式即可），但新增型別要修改所有既有函式。

**詳細解析**：Java 的訪問者模式是對這個問題的一種回應——它把操作抽成訪問者介面，新增操作只要加一個實作，但**新增型別要改訪問者介面與所有實作**，代價很高而且樣板很多。密封類別加模式比對提供了一個更輕量的方案：新增操作只要寫一個新的 switch（不改任何既有程式碼），新增型別則會讓**所有相關的 switch 立刻編譯失敗**——雖然還是要改，但編譯器會精確地告訴你要改哪裡，這與「執行期才發現漏了一個分支」有本質差別。**它沒有解決表達式問題，而是讓其中一邊的代價從「靜默失敗」降到「編譯期指出」**，這在工程上已經是很大的改善。

**面試回答方式**：先精確定義兩個維度與兩難，並把物件導向與模式比對各自的強弱說清楚。然後用訪問者模式當對照，指出它的代價。收在最有價值的判斷：**密封類別加模式比對沒有解決表達式問題，而是把新增型別的代價從靜默失敗降到編譯期指出**——這個誠實的定位比宣稱它解決了問題更有說服力。

### 記錄模式的巢狀解構有什麼要注意的？

**核心答案**：可以寫成 `case Line(Point(var x1, var y1), Point(var x2, var y2)) ->` 這樣多層解構，很簡潔。要注意三點：**只能用於 record**（一般類別沒有標準的解構協定）、**元件型別必須匹配**（可以用 `var` 讓編譯器推導，但寫具體型別時會多一層型別測試）、以及**巢狀太深會嚴重傷害可讀性**，兩層通常已經是上限。

**詳細解析**：一個容易忽略的語意細節是**巢狀模式對 null 的處理**：`case Line(Point p1, Point p2)` 在 `p1` 為 null 時**比對失敗**（因為 `Point p1` 是型別模式，null 不匹配任何型別模式），會落到下一個 case。但頂層的 record 型別模式本身如果遇到 null，行為又不同（走 `case null` 或拋 NPE）。**這種「巢狀位置的 null 靜默地讓比對失敗」很容易造成漏處理**，尤其是當 record 的元件宣告成可為 null 的型別時。實務建議是**讓 record 的元件在建構時就拒絕 null**（緊湊建構子加 `Objects.requireNonNull`），把問題擋在源頭。

**面試回答方式**：給三個注意點（只能用於 record、型別必須匹配、深度別超過兩層）。真正的加分點是 null 的語意細節：**巢狀位置的 null 會讓比對靜默失敗落到下一個 case**，與頂層的 null 處理不同。收在可操作的建議——在 record 的緊湊建構子裡拒絕 null，把問題擋在源頭。

### 密封類別的 permits 該怎麼設計？

**核心答案**：`sealed interface Shape permits Circle, Square, Triangle` 明確列出允許的子型別；子型別必須是 `final`、`sealed`、或 `non-sealed`（明確放棄封閉）。設計時的關鍵判斷是**這個型別的變體集合是不是本質上封閉的**——`Shape` 在幾何上其實是開放的（隨時可能加新形狀），但一個「支付方式」或「訂單狀態」在業務上通常是封閉的（新增要經過產品決策），後者才是密封類別的好用武之地。

**詳細解析**：實務上有兩個常見錯誤。**第一，對本質開放的概念用密封**——每次新增變體都要改介面宣告，而且如果它是公開 API，下游無法擴充，等於把擴充點關掉了。**第二，把密封類別當成列舉的替代品**——如果變體沒有各自的資料，列舉更簡單也更省。密封類別的價值在於**變體各自攜帶不同的資料**（`record Cash()` 與 `record Card(String last4, String brand)`），這是列舉做不到的。另外要注意子型別必須與密封型別**在同一個模組或同一個套件**（未具名模組下），這個限制讓編譯器能確信自己看得到全部子型別，是窮盡性檢查成立的前提。

**面試回答方式**：先給語法要點（permits 與三種子型別修飾），再給核心判斷——**變體集合是不是本質封閉**，並用「幾何形狀是開放的、支付方式是封閉的」做對照。給兩個常見錯誤：對開放概念用密封會關掉擴充點、變體沒有各自資料時該用列舉。最後補上「子型別必須同模組或同套件」這個限制，並說明它為什麼是窮盡性檢查成立的前提。
