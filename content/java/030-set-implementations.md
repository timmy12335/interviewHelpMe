# 題目

三種 `Set` 實作各自的底層與適用場景是什麼？為什麼 `HashSet` 內部其實是一個 `HashMap`？

## 核心答案

三者的差異就是它們背後的 Map：`HashSet` 包 `HashMap`（無序、O(1)）、`LinkedHashSet` 包 `LinkedHashMap`（插入順序、O(1)、每個元素多兩個指標）、`TreeSet` 包 `TreeMap`（鍵的大小順序、O(log n)、支援範圍查詢）。

`HashSet` 內部持有一個 `HashMap`，把元素當作**鍵**，值統一放一個名為 `PRESENT` 的靜態空物件。這是**組合重用**的典型例子——Set 的語意（不重複、快速判斷存在）恰好就是 Map 的鍵集合語意，重寫一份雜湊表沒有任何好處，還多一份要維護與除錯的程式碼。代價是每個元素多存一個指向 `PRESENT` 的引用（壓縮指標下 4 位元組），這個空間換維護性的取捨在通用類別庫裡是划算的。

選型規則很直接：**預設用 `HashSet`**；需要「輸出順序等於放入順序」用 `LinkedHashSet`；需要排序輸出或範圍查詢才用 `TreeSet`。

## 詳細解析

**HashSet 的行為完全繼承自 HashMap 的鍵**，包括那些不明顯的部分：允許一個 null 元素、判斷重複靠 `hashCode` 加 `equals`（所以自訂型別放進 Set 前必須正確覆寫這兩個方法）、迭代順序取決於雜湊值與容量因此**擴容後順序會變**。最後這點常被誤解成「HashSet 有某種穩定順序」——實際上加入元素導致擴容時，既有元素的相對位置就可能重排。

**LinkedHashSet 的價值主要在確定性**：它讓輸出可重現，這對測試斷言、日誌比對、產生穩定的設定檔輸出都很重要。**「用 HashSet 但依賴它的迭代順序」是一種很難察覺的 bug**——在開發環境跑得好好的，換了資料量或 JDK 版本順序就變了。所以只要輸出順序會被人或程式讀取，就應該明確選 `LinkedHashSet` 而不是碰運氣。

**TreeSet 判斷重複用比較結果而非 equals**，這是與另外兩者最大的行為差異。`TreeSet` 認為 `compareTo` 回傳 0 的兩個元素是同一個，即使 `equals` 說不是。所以用只比較部分欄位的比較器建 `TreeSet` 時會靜默地吃掉資料。解法是**比較器鏈最後補一個唯一鍵**。它的回報是 `first`、`last`、`ceiling`、`floor`、`headSet`、`subSet` 這組導覽方法，這些用另外兩種 Set 都得掃全表。

**去重之外還有第三條路**：如果只是要「判斷有沒有看過」且能容忍極小的誤判率、資料量又非常大（億級），布隆過濾器的空間成本是 Set 的幾十分之一。而如果只是要對一個 `List` 去重並保持順序，`new LinkedHashSet<>(list)` 一行就夠，不必手寫迴圈——**知道什麼時候不需要寫程式，也是選型能力的一部分**。

## 面試回答方式

先用一句話把三者串起來：**它們就是三種 Map 的鍵集合**，所以底層、複雜度與順序特性可以直接對應過去。接著解釋 `HashSet` 包 `HashMap` 是**組合重用**——Set 的語意就是 Map 鍵集合的語意，值統一放一個靜態空物件，代價是每個元素多一個引用，這個空間換維護性在類別庫裡划算。然後給選型規則（預設 `HashSet`、要重現順序用 `LinkedHashSet`、要排序或範圍查詢用 `TreeSet`），並主動提兩個容易踩的點：**依賴 `HashSet` 的迭代順序是隱性 bug**（擴容後會重排），以及 **`TreeSet` 用比較結果判斷重複**，只比部分欄位的比較器會靜默吃掉資料。

## 講稿

這三種 Set 其實就是三種 Map 的鍵集合，所以底層、複雜度、順序特性可以直接對應過去。HashSet 包的是 HashMap，LinkedHashSet 包 LinkedHashMap，TreeSet 包 TreeMap。

HashSet 內部真的就持有一個 HashMap，元素當作鍵，值統一放一個靜態的空物件。這是組合重用，因為 Set 的語意恰好就是 Map 鍵集合的語意，重寫一份雜湊表沒有好處。代價是每個元素多存一個引用，這個空間換維護性的取捨在通用類別庫裡是划算的。

選型我會這樣講。預設用 HashSet。需要輸出順序等於放入順序，用 LinkedHashSet。需要排序輸出或範圍查詢，才用 TreeSet。

有兩個容易踩的點。第一，依賴 HashSet 的迭代順序是隱性的錯誤，擴容之後既有元素的相對位置就可能重排。第二，TreeSet 判斷重複看的是比較結果而不是 equals，所以只比較部分欄位的比較器會靜默吃掉資料。

## 常見追問

### 自訂型別放進 HashSet 前要注意什麼？

**核心答案**：必須同時正確覆寫 `hashCode` 與 `equals`，而且**參與計算的欄位在物件放進 Set 之後不能改變**。只覆寫 `equals` 的話，兩個相等的物件會落在不同的桶，Set 裡就會出現重複；只覆寫 `hashCode` 的話，同桶內用 `equals` 比對會失敗，同樣重複。而如果物件放進去之後修改了參與雜湊的欄位，它的桶位置就與實際雜湊值不符，`contains` 會找不到它，`remove` 也刪不掉——**元素等於永久洩漏在 Set 裡**。

**詳細解析**：這就是**建議用不可變物件當作 Set 元素或 Map 鍵**的實際理由：不可變物件的雜湊值永遠不會失效。做不到完全不可變時，退一步的做法是**只用不會變的欄位參與 hashCode 與 equals**（例如只用 ID），業務欄位不參與。Java 的 `record` 自動生成的 `equals` 與 `hashCode` 包含全部元件，所以 record 適合當鍵的前提是它的元件本身也是不可變的——**record 只保證欄位引用不變，不保證引用指向的物件不變**，欄位如果是一個可變的 `List`，同樣的問題還在。

**面試回答方式**：先講兩個方法必須成對覆寫，各給一句失敗後果。真正的重點放在第二個條件——**放進去之後不能改參與雜湊的欄位**，否則元素永久卡在 Set 裡刪不掉。收在建議：用不可變物件當元素，或至少只讓穩定欄位參與雜湊。加分點是指出 `record` 只保證引用不變，欄位是可變集合時問題依然存在。

### 要對一個大型 List 去重，怎麼做最有效率？

**核心答案**：看**要不要保持順序**與**資料量**。不需要順序就用 `new HashSet<>(list)`，一次 O(n)。需要保持首次出現順序用 `new LinkedHashSet<>(list)`，同樣 O(n)，只多一條串列的記憶體。**不要用 `stream().distinct()` 之後再收集**——它語意相同但多了一層串流管線的開銷，在大量資料上沒有優勢；也不要用巢狀迴圈或 `list.contains` 過濾，那是 O(n²)。

**詳細解析**：真正大的資料要考慮**記憶體**而不只是時間。`HashSet` 每個元素大約要 32 到 48 位元組的節點開銷（還不含元素本身），一億個元素就是好幾 GB。這時的選擇是：先排序再掃一遍相鄰去重（O(n log n) 時間但記憶體只要原資料），或者用布隆過濾器做第一層過濾（有極小的誤判率，會誤判為「已存在」而漏掉少數元素，所以只適合容忍近似的場景），或者外部化——分批雜湊到不同檔案再各自去重。**建構 HashSet 時預先給容量**（`new HashSet<>((int)(n / 0.75f) + 1)`）也能省掉多次擴容與重雜湊，這是最便宜的最佳化。

**面試回答方式**：先給兩條主線（要不要保順序），並明確反對 `distinct()` 與 `contains` 過濾這兩種常見寫法，說明理由。接著把問題升級到記憶體層面：給出每個元素幾十位元組的量級，再給三條路（排序後相鄰去重、布隆過濾器、分批外部化）。最後補一個立刻能用的建議：預先指定容量避免多次擴容。

### EnumSet 為什麼比 HashSet 快很多？

**核心答案**：因為它**根本不是雜湊表**。列舉型別的所有值在編譯期就固定且有序（`ordinal`），所以 `EnumSet` 用一個**位元向量**表示成員資格——列舉常數少於 64 個時就是一個 `long`，每個位元代表一個常數在不在集合裡。`add`、`contains`、`remove` 全都是單一的位元運算，`union`、`intersection` 這類集合運算則是一次 `或` 或 `且`，**完全沒有物件配置、沒有雜湊計算、沒有指標追逐**。

**詳細解析**：這是「**知道定義域就能換更好的表示法**」的經典例子。同樣的思路出現在 `EnumMap`（用陣列以 ordinal 為索引，取代雜湊表）、位元圖索引（資料庫對低基數欄位的處理）、以及點陣圖去重。代價是適用範圍窄——只能用於單一列舉型別，且新增列舉常數超過 64 個時內部會切換成 long 陣列（仍然很快，只是多一層索引）。**實務上的建議是：只要 Set 或 Map 的鍵是列舉，就用 `EnumSet` 與 `EnumMap`，沒有理由用 `HashSet`**，它們在時間、空間與迭代順序（依宣告順序，天然穩定）三方面都更好。

**面試回答方式**：核心是一句話——它不是雜湊表而是位元向量。給出關鍵推論：集合運算變成單一位元運算、零配置零雜湊。然後把它抽象成一個可遷移的原則：**知道定義域就能換更好的表示法**，並舉 `EnumMap` 與資料庫位元圖索引作為同一思路。收在可操作的建議：鍵是列舉就一律用 `EnumSet` 與 `EnumMap`。
