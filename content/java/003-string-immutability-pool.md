# 題目

為什麼 `String` 被設計成不可變（immutable）？字串常數池（String Pool）是什麼？

## 核心答案

`String` 內部用一個 `final` 的字元陣列儲存內容，且不對外提供任何修改這個陣列的方法，因此一旦建立就無法改變（所有看似「修改」的操作如 `substring`、`concat` 都是回傳新的 `String`）。不可變設計帶來執行緒安全、可安全共享、可作為 `HashMap` 的 key（雜湊碼恆定）、以及能夠透過「字串常數池」重複使用相同字面量以節省記憶體等好處。

## 詳細解析

**為什麼是不可變的**：`String` 類別本身用 `final` 修飾（不能被繼承後破壞其不可變性），內部儲存內容的字元陣列也是 `private final`，且沒有任何方法會修改這個陣列。所有 `replace`、`substring`、`toUpperCase` 等操作都是產生並回傳一個全新的 `String` 物件，原字串完全不變。

**不可變帶來的好處**：

1. **執行緒安全**：不可變物件天生就是執行緒安全的，多執行緒可以自由共享同一個 `String` 而不需要任何同步。
2. **可安全作為 HashMap 的 key**：因為內容不變，雜湊碼在生命週期內恆定，不會發生 [[001-equals-hashcode-contract.md]] 中提到的「可變 key 導致查不到」問題。而且 `String` 會快取自己的雜湊碼（第一次計算後存起來），重複使用時不需要重算。
3. **可以有字串常數池**：正因為不可變，多個地方引用同一個池中的字串才是安全的（沒人能改到它）。

**字串常數池（String Pool）**：JVM 維護一塊特殊的記憶體區域（在現代 JDK 中位於堆記憶體），用來存放字串字面量。當程式碼中出現字串字面量（如 `String s = "hello"`）時，JVM 會先檢查池中是否已有內容相同的字串——有就直接回傳池中那個物件的引用，沒有才建立並放入池中。因此 `String a = "hello"; String b = "hello";` 中 `a` 和 `b` 指向池中同一個物件（`a == b` 為 true），節省了記憶體。

**`new String("hello")` 的差異**：用 `new` 明確要求在堆上建立一個「新的」物件，所以 `new String("hello") == "hello"` 為 false（一個是新建的堆物件，一個是池中物件）。可以呼叫 `.intern()` 方法手動把字串放入池中或取得池中已有的引用。

## 面試回答方式

先講「不可變是怎麼實作的」（`final` 類別 + `private final` 字元陣列 + 無修改方法），再講「為什麼要這樣設計」——這是這題的重點，把執行緒安全、可作 key、可用字串池這幾個好處串起來講，展現你理解不可變性不是限制而是刻意的設計取捨。字串常數池的部分，一定要用 `String a = "x"; String b = "x"` 相等、但 `new String("x")` 不相等這組對比說明，並提到 `intern()`，這樣才完整。

## 常見追問

### String s = "a" + "b" + "c" 會建立幾個物件？

**核心答案**：如果 `"a" + "b" + "c"` 全部都是編譯期常數（字面量），編譯器會在編譯階段就直接把它們合併成 `"abc"`，因此執行時只會在字串池中有一個 `"abc"` 物件，不會產生中間的 `"ab"` 等臨時物件；但如果拼接中包含變數（如 `s + b``b` 是變數），則會在執行期透過 `StringBuilder` 動態拼接，產生額外的中間物件。

**詳細解析**：這題考的是「編譯期常數摺疊（constant folding）」這個編譯器優化。對於純字面量的拼接 `"a" + "b" + "c"`，編譯器知道結果是確定的，會直接優化成一個 `"abc"` 字面量放入字串池，執行時沒有任何拼接動作。但一旦拼接涉及執行期才能確定的變數，編譯器無法預先計算結果，就會把拼接轉換成 `new StringBuilder().append(...).append(...).toString()` 的形式在執行期進行，這會產生 `StringBuilder` 物件以及最終的 `String` 物件。這也是為什麼「在迴圈中用 `+` 拼接字串」效能差——每次迴圈都會 new 一個新的 `StringBuilder`，應該改用一個 `StringBuilder` 在迴圈外重複 `append`。

**面試回答方式**：先區分「純字面量拼接（編譯期摺疊成一個物件）」與「含變數拼接（執行期用 StringBuilder）」兩種情況分別回答，再延伸到「迴圈中拼接字串為什麼要用 StringBuilder」的實務建議，展現你理解編譯器優化並能連結到實際的效能最佳實踐。

### 字串池在 JDK 各版本中位置有什麼變化？

**核心答案**：JDK 7 之前，字串常數池位於「方法區」（永久代 PermGen）中；JDK 7 開始，字串池被移到了「堆記憶體」中；JDK 8 徹底移除了永久代（改用元空間 Metaspace 存放類別元資料），但字串池仍然留在堆中。

**詳細解析**：這個遷移的主要動機是永久代的空間有限且不易調整，把大量字串放在永久代容易導致 `OutOfMemoryError: PermGen space`。移到堆記憶體後，字串池能享受更靈活的空間管理與垃圾回收（不再被池化的字串可以被 GC 回收），也讓 `intern()` 的行為在 JDK 7+ 有所不同——JDK 7 之後 `intern()` 如果池中沒有該字串，會直接把堆中已存在的這個字串物件的引用放入池（而非複製一份到永久代），更節省記憶體。這也是為什麼理解 `String.intern()` 的行為需要區分 JDK 版本。

**面試回答方式**：能講出「JDK 7 前在永久代、JDK 7 起移到堆、JDK 8 移除永久代」這個演進脈絡，並說明遷移動機（避免永久代 OOM、享受堆的 GC）是加分點，展現你對 JVM 記憶體區域演進有整體認識，這也能自然銜接到 JVM 類別的相關題目。

### 為什麼 String 不可變反而對效能好，而不是浪費（每次都要新建物件）？

**核心答案**：雖然「修改」字串需要新建物件看似浪費，但不可變性換來的好處往往更划算——字串池讓大量重複的字面量共享同一個物件（節省記憶體）、雜湊碼可以被快取（`HashMap` 場景下省去重複計算）、多執行緒共享不需要任何同步或防禦性複製（省去鎖與複製開銷），而真正需要頻繁修改字串的場景，Java 提供了 `StringBuilder`/`StringBuffer` 這類可變的替代方案。

**詳細解析**：這是一個「設計取捨」的權衡題。不可變確實在「頻繁修改單一字串」這個特定場景下有新建物件的成本，但這正是 `StringBuilder` 存在的原因——把「需要頻繁修改」的場景交給專門的可變類別處理。而在字串最常見的使用場景（作為固定的鍵、常數、訊息、在多執行緒間傳遞）中，不可變帶來的共享、快取、免同步的好處遠遠超過偶爾新建物件的成本。這體現了「為最常見的使用情境優化，同時為特殊情境（頻繁修改）提供專門工具」的設計哲學。

**面試回答方式**：把這題當成「設計取捨」來回答——承認不可變在頻繁修改場景有成本，但強調它在最常見場景（共享、作 key、多執行緒）的收益更大，且頻繁修改有 `StringBuilder` 這個專門解法。這種能看到取捨兩面、並理解「為常見情境優化」設計思路的回答，比單純說「不可變比較安全」更成熟。
