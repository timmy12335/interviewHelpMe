# 題目

什麼是自動裝箱（autoboxing）與拆箱（unboxing）？`Integer` 快取是什麼？為什麼 `Integer a = 127, b = 127; a == b` 是 true 但 `128` 卻是 false？

## 核心答案

自動裝箱是編譯器自動把基本型別（如 `int`）轉換成對應的包裝類別（如 `Integer`），拆箱則是反向的自動轉換。`Integer` 內部有一個快取池，預設快取 `-128` 到 `127` 之間的值，這個範圍內的自動裝箱會回傳快取中同一個物件；超出範圍則每次都 `new` 一個新物件。所以 `127 == 127` 因為是同一個快取物件而為 true，`128 == 128` 因為是兩個不同的新物件而為 false。

## 詳細解析

**自動裝箱與拆箱**：

- 裝箱：`Integer i = 10;` 編譯器自動轉為 `Integer i = Integer.valueOf(10);`。
- 拆箱：`int n = i;` 編譯器自動轉為 `int n = i.intValue();`。

**Integer 快取機制**：`Integer.valueOf(int)` 的實作會先檢查值是否在快取範圍（預設 `-128` 到 `127`）內——是就回傳 `IntegerCache` 中預先建立好的物件，否則才 `new Integer()`。這個快取是為了讓小整數（最常用的範圍）能重複使用物件、節省記憶體與提升效能。

**為什麼 127 和 128 行為不同**：

- `Integer a = 127, b = 127;`：兩次裝箱都呼叫 `Integer.valueOf(127)`，127 在快取範圍內，回傳的是快取中同一個物件，所以 `a == b`（比較引用）為 true。
- `Integer c = 128, d = 128;`：128 超出快取範圍，兩次 `Integer.valueOf(128)` 各自 `new` 一個新物件，`c` 和 `d` 指向不同物件，所以 `c == d` 為 false。

**正確做法**：比較包裝類別的值一律用 `.equals()`，永遠不要用 `==`（除非你確實要比較是不是同一個物件引用）。這樣不管值在不在快取範圍都是正確的內容比較。

**拆箱的 NPE 陷阱**：如果一個 `Integer` 為 null，自動拆箱時（例如 `int n = someInteger;` 而 `someInteger` 為 null）會呼叫 `null.intValue()` 拋出 `NullPointerException`，這是很隱蔽的陷阱。

## 面試回答方式

先解釋自動裝箱/拆箱是「編譯器自動插入的型別轉換」，並點出它們對應的方法（`valueOf`/`intValue`）。接著講 `Integer` 快取——核心是「-128~127 用快取同一物件、超出範圍 new 新物件」，這解釋了 127/128 的差異。務必給出結論「包裝類別比較值一律用 `equals`」。如果能主動補上「拆箱可能對 null 拋 NPE」這個隱蔽陷阱，會展現你不只知道快取這個常考點，還了解自動裝箱的其他實務風險。

## 常見追問

### Integer 的快取範圍可以調整嗎？

**核心答案**：快取的上界可以透過 JVM 參數 `-XX:AutoBoxCacheMax=<size>` 調整（預設上界是 127），下界固定為 -128 不可調。調大上界可以讓更多的整數值享受快取（節省記憶體），但這是全域設定，一般不建議依賴它，因為它會改變程式行為且不易察覺。

**詳細解析**：`IntegerCache` 在類別初始化時會讀取這個 JVM 參數決定快取上界，所以如果把上界調到例如 1000，那麼 `Integer a = 1000, b = 1000; a == b` 就會變成 true。但正因為它是全域的、且會讓 `==` 的行為隨設定改變，依賴它是危險的——同一段程式碼在不同 JVM 參數下行為不同，非常容易造成隱蔽 bug。這個參數的存在主要是給「確實有大量特定範圍小整數、想省記憶體」的特殊場景微調用，日常開發不應該依賴它，而是應該堅持用 `equals()` 比較值，讓程式碼行為與快取設定完全無關。

**面試回答方式**：回答「上界可用 `-XX:AutoBoxCacheMax` 調、下界固定」，但務必強調「不該依賴它，因為會讓 `==` 行為隨設定改變」，這種「知道可以調但知道不該依賴」的回答，展現你有正確的工程判斷，而不是炫技式地記住一個冷門參數。

### 為什麼其他包裝類別（Long、Character）也有快取，但 Double 沒有？

**核心答案**：`Long`、`Short`、`Byte`、`Character` 都有類似 `Integer` 的快取（`Byte`、`Short`、`Long` 快取 -128~127，`Character` 快取 0~127），因為這些是離散的整數型別，小範圍的值使用非常頻繁，快取能有效重複使用；而 `Double`、`Float` 是浮點型別，值是連續的、幾乎無限多種可能，「快取特定幾個值」意義不大（命中率極低），所以沒有設計快取。

**詳細解析**：快取機制的價值在於「少數幾個值被高頻重複使用」。整數型別中，小整數（如 0、1、-1）出現的頻率極高，快取它們能顯著減少物件建立;但浮點數如 3.14、2.71 這種值，幾乎不會有「大量程式碼恰好都用同一個浮點值」的情況，快取的命中率會非常低，反而白白佔用記憶體維護一個沒用的快取，所以 `Double`/`Float` 的 `valueOf` 每次都直接 new 新物件。這也解釋了為什麼 `Double a = 1.0, b = 1.0; a == b` 恆為 false——浮點包裝類別沒有快取。

**面試回答方式**：用「整數型別小值高頻重複所以快取有價值，浮點值連續且幾乎不重複所以快取無意義」這個對比回答，展現你理解快取設計的判斷依據是「值的重複使用頻率」，而不是死記「哪些有快取哪些沒有」。

### 一段大量自動裝箱的迴圈程式碼有什麼效能陷阱？

**核心答案**：如果在迴圈中不小心把累加變數宣告成包裝類別（如 `Long sum = 0L`）而非基本型別（`long sum`）每次 `sum += i` 都會發生「拆箱→運算→裝箱」的過程，其中裝箱在超出快取範圍時會不斷 `new` 新的 `Long` 物件，在大量迴圈下產生海量臨時物件，造成嚴重的記憶體與 GC 壓力，效能可能比用基本型別慢一個數量級。

**詳細解析**：這是一個著名的隱蔽效能陷阱——`Long sum = 0L;` 這個小小的「用了包裝類別」的疏忽，會讓迴圈中每次累加都經歷「把 sum 拆箱成 long、加上 i、再把結果裝箱成新的 Long 物件」。在幾百萬次的迴圈中，這會建立幾百萬個臨時 `Long` 物件（因為累加結果早就超出 -128~127 的快取範圍），GC 疲於回收這些短命物件，效能急劇下降。修正方法極其簡單——把 `Long sum` 改成 `long sum`，用基本型別做累加，完全避免裝箱。這也提醒開發者：在效能敏感的數值運算中，優先用基本型別而非包裝類別。

**面試回答方式**：用「累加變數誤用包裝類別導致每次迴圈都裝箱 new 新物件」這個具體場景回答，並給出「改用基本型別」的簡單修正，這種能指出「一個微小的型別選擇造成數量級效能差異」的回答，很能展現你在效能細節上的敏感度。
