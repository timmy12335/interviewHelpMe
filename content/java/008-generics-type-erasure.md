# 題目

Java 泛型的型別擦除（Type Erasure）是什麼？它帶來了哪些限制？

## 核心答案

Java 泛型是「編譯期」的概念，編譯器用泛型資訊做型別檢查與自動轉型，但編譯完成後會把泛型型別參數「擦除」——`List<String>` 和 `List<Integer>` 在執行期都變成原始型別 `List`型別參數 `T` 被替換成它的邊界（無邊界時是 `Object`）。這是為了與早期沒有泛型的 Java 版本保持二進位相容。型別擦除帶來了不能 `new T[]`、不能 `instanceof List<String>`、無法在執行期取得泛型型別等限制。

## 詳細解析

**什麼是型別擦除**：泛型只存在於原始碼與編譯階段。編譯器利用泛型資訊確保型別安全（例如不讓你往 `List<String>` 塞 `Integer`），並自動插入轉型程式碼。但編譯後產生的位元組碼（Bytecode）中，泛型型別參數被移除——`List<String>`、`List<Integer>`、`List<Object>` 在執行期都是同一個原始型別 `List`它們的 `getClass()` 完全相同。

**為什麼要擦除**：泛型是 JDK 5 才引入的，為了讓新的泛型程式碼能和 JDK 5 之前的舊程式碼、舊的類別庫二進位相容（不需要重新編譯舊的 class 檔），Java 選擇了「擦除式」泛型——執行期不保留泛型資訊，讓泛型類別在位元組碼層面和原始型別相容。這與 C# 的「具體化泛型（reified generics，執行期保留型別資訊）」是不同的設計路線。

**型別擦除帶來的限制**：

1. **不能 `new T[]`**：因為執行期不知道 `T` 的真實型別，無法建立對應型別的陣列。
2. **不能用 `instanceof` 判斷泛型型別**：`obj instanceof List<String>` 不合法，因為執行期 `List<String>` 就是 `List`，無法區分。
3. **不能建立泛型型別的實例 `new T()`**：同樣因為執行期不知道 `T` 是什麼。
4. **靜態欄位/方法不能用類別的型別參數**：因為型別參數是實例層級的，而靜態成員是類別層級共享的。
5. **泛型型別的例外不能被 catch**：不能 `catch (MyException<String> e)`。

**橋接方法（Bridge Method）**：型別擦除會導致覆寫泛型方法時簽章不一致，編譯器會自動生成「橋接方法」來維持多型的正確性，這是擦除機制的一個底層補償。

## 面試回答方式

先講清楚核心概念——「泛型是編譯期的，執行期會被擦除成原始型別」，並用 `List<String>` 和 `List<Integer>` 執行期是同一個 `List` 這個具體例子佐證。接著講「為什麼擦除」（與舊版本二進位相容），這是理解 Java 泛型設計的關鍵，能對比 C# 的具體化泛型更好。最後列舉幾個由擦除導致的實際限制（不能 `new T[]`、不能 `instanceof` 泛型），用具體限制證明你真的理解擦除的後果，而不只是背定義。

## 常見追問

### 型別擦除後，執行期還能取得泛型的實際型別嗎？

**核心答案**：一般的泛型變數（如區域變數 `List<String>`）在執行期確實無法取得型別參數；但如果泛型資訊被保留在「類別定義、欄位、方法簽章、父類別/介面的泛型宣告」中，這些是會被寫入 class 檔的元資料，可以透過反射（Reflection）（如 `getGenericSuperclass()`、`getGenericParameterTypes()`）取得。這也是很多框架（如 Gson、Spring）用「匿名子類別 + `TypeReference`」技巧取得泛型型別的原理。

**詳細解析**：型別擦除擦掉的是「使用泛型的地方」的型別參數（例如 `new ArrayList<String>()` 中的 String），但「宣告泛型的地方」的資訊會保留在 class 檔的 Signature 屬性中。例如 `class MyList extends ArrayList<String>`這個 `String` 會被保留可以透過 `getGenericSuperclass()` 取得。這就是 Gson 的 `TypeToken`、Spring 的 `ParameterizedTypeReference` 的原理——它們讓你建立一個匿名子類別（如 `new TypeToken<List<User>>(){}`）把 `List<User>` 這個泛型資訊「錨定」在子類別的父類別宣告中，從而在執行期透過反射把它讀出來，繞過擦除的限制。

**面試回答方式**：先回答「一般變數不行，但保留在類別/欄位/方法簽章中的泛型可透過反射取得」，再舉出 Gson 的 `TypeToken` 這個實際框架應用，展現你不只理解擦除的限制，還知道業界如何巧妙繞過它，這種「知道限制也知道 workaround」的回答很有深度。

### 為什麼不能建立泛型陣列 new T[]？

**核心答案**：因為陣列在 Java 中是「具體化（reified）」的——陣列在執行期會記住並檢查自己的元素型別（存入錯誤型別會拋 `ArrayStoreException`），但泛型因為型別擦除在執行期不知道 `T` 的真實型別，兩者的機制根本上衝突，無法在執行期建立一個「知道自己元素型別是 T」的陣列。

**詳細解析**：這裡揭示了 Java 中「陣列」與「泛型」兩種機制的根本矛盾——陣列是協變（covariant）且執行期保留型別的，泛型是不變（invariant）且執行期擦除型別的。如果允許 `new T[]`，執行期的陣列型別檢查會失效（因為不知道 T 是什麼，無法檢查存入的元素型別是否正確），破壞了陣列的型別安全保證。實務中如果真的需要泛型陣列，常見的變通做法是建立 `Object[]` 再轉型（會有未檢查警告），或者改用 `List<T>` 這類泛型集合（集合本身是泛型的，不受陣列的限制），後者是更推薦的做法。

**面試回答方式**：點出核心矛盾——「陣列執行期保留型別、泛型執行期擦除型別，兩者機制衝突」，再給出「用 `List<T>` 取代泛型陣列」的實務解法，展現你理解這不是隨意的限制，而是兩種型別機制根本性的不相容。

### Java 的擦除式泛型和 C# 的具體化泛型有什麼本質差異？

**核心答案**：Java 是「擦除式泛型」——泛型資訊只在編譯期存在，執行期被擦除，`List<String>` 和 `List<Integer>` 在執行期是同一個型別；C# 是「具體化泛型」——泛型資訊在執行期完整保留，`List<string>` 和 `List<int>` 是兩個不同的執行期型別，可以用反射取得型別參數、可以 `new T()`、可以 `T[]`。Java 選擇擦除主要是為了與 JDK 5 之前的舊程式碼二進位相容。

**詳細解析**：這個差異源於兩種語言引入泛型時的不同處境與取捨。Java 在 JDK 5 引入泛型時，已經有海量的既有程式碼和類別庫，為了不破壞這些舊程式碼的二進位相容性（讓新舊程式碼能混用而不需重新編譯），選擇了擦除式——泛型類別在位元組碼層面退化成原始型別，與舊程式碼看到的一樣。C# 則是在 .NET 2.0 由執行環境（CLR）層級直接支援泛型，執行期保留完整型別資訊，因此沒有 Java 那些「不能 new T[]、不能 instanceof 泛型」的限制，但代價是這需要執行環境的原生支援。兩種設計沒有絕對優劣，是不同歷史約束下的合理選擇——Java 換來了相容性，C# 換來了執行期的型別能力。

**面試回答方式**：用「擦除 vs 具體化」這組對比清楚劃分兩者，並點出 Java 選擇擦除的歷史原因（相容舊程式碼），這種能跨語言比較並理解「設計是歷史約束下的取捨」的回答，能展現你對泛型的理解超越了單一語言的層次。
