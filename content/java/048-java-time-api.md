# 題目

`Date` 與 `Calendar` 有哪些設計問題？`java.time` 的核心型別該怎麼選？

## 核心答案

舊 API 的問題有四類。**可變**——`Date` 有 setter，把它放進 Map 當鍵或傳給別人都不安全。**執行緒不安全**——`SimpleDateFormat` 內部有可變狀態，多執行緒共用一個實例會產生錯誤結果（不是拋例外，是**靜默地解析錯**），這是最經典的生產事故來源之一。**設計錯誤**——月份從 0 開始、年份從 1900 起算、`Date` 名字叫日期卻是一個時間戳。**概念混淆**——沒有「只有日期」或「只有時間」的型別，所有東西都是時間戳加時區。

`java.time` 的型別選擇圍繞一個問題：**這個時間點需不需要時區**。`Instant` 是時間軸上的一個絕對點（機器時間，適合記錄事件發生時刻）。`LocalDate`／`LocalTime`／`LocalDateTime` **不帶時區**，表示的是「牆上時鐘的讀數」——生日、營業時間、會議的當地時刻。`ZonedDateTime` 是本地時間加時區規則，能正確處理日光節約時間。`OffsetDateTime` 只帶固定偏移量，適合 API 傳輸與資料庫儲存。

## 詳細解析

**選錯型別是實務上最常見的錯誤**，而且判斷方式其實很簡單：問「**如果使用者換了時區，這個值該不該變**」。生日不該變（用 `LocalDate`），訂單建立時間該顯示成當地時間但代表同一個瞬間（存 `Instant` 或 `OffsetDateTime`，顯示時轉時區）。**把所有時間都存成 `LocalDateTime` 是最典型的錯誤**——它丟失了時區資訊，跨時區的系統之後永遠無法還原真正的瞬間。

**日光節約時間造成兩類邊界情況**，`ZonedDateTime` 有明確定義的處理方式。**間隙（gap）**——時鐘往前跳時某些本地時間不存在（例如凌晨 2:30 直接變成 3:30），此時 `ZonedDateTime.of` 會把時間往後推一個偏移量。**重疊（overlap）**——時鐘往回撥時某些本地時間出現兩次，預設選較早的那個偏移量，可以用 `withEarlierOffsetAtOverlap` 與 `withLaterOffsetAtOverlap` 明確指定。**排程系統在這兩個邊界上出錯是每年固定會發生的事故**，知道 API 有明確定義並主動處理，比事後救火好。

**Duration 與 Period 的分工反映了時間的兩種語意**：`Duration` 是**精確的時間量**（以秒與奈秒計），`Period` 是**日曆上的量**（年、月、日）。「一天後」在有日光節約的時區裡不等於「24 小時後」——用 `plusDays(1)` 會維持相同的當地時刻（日曆語意），用 `plus(Duration.ofDays(1))` 會精確加 24 小時（物理語意）。**選錯會產生一小時的偏差**，而且只在一年兩天發生，測試幾乎抓不到。

**格式化改用 `DateTimeFormatter`，它是不可變且執行緒安全的**，可以安全地宣告成靜態常數——這正好修正了 `SimpleDateFormat` 最大的坑。另外要注意 `DateTimeFormatter.ISO_DATE_TIME` 這類預定義格式與 `ofPattern` 的差別，以及 `ofPattern` 的模式字母與舊 API 不完全相同（例如 `uuuu` 與 `yyyy` 在處理紀元時的差異）。

## 面試回答方式

先把舊 API 的問題歸成**四類**（可變、執行緒不安全、設計錯誤、概念混淆），並特別點出 `SimpleDateFormat` 的執行緒問題是**靜默解析錯而不是拋例外**，所以特別難查。接著給型別選擇的核心問題——**這個時間點需不需要時區**，並提供一個可操作的判斷：「**使用者換時區時這個值該不該變**」，生日不該變用 `LocalDate`，訂單時間該轉換所以存 `Instant` 或 `OffsetDateTime`。明確指出**把所有時間存成 `LocalDateTime` 是最典型的錯誤**。加分點給兩個：**日光節約的間隙與重疊** API 都有明確定義（`withEarlierOffsetAtOverlap` 等），排程系統每年固定在這裡出事；以及 **`Duration` 與 `Period` 的語意差別**——`plusDays(1)` 是日曆語意、`plus(Duration.ofDays(1))` 是物理語意，選錯會有一小時偏差且測試抓不到。

## 講稿

舊的 API 有四類問題。第一是可變，Date 有 setter，放進 Map 當鍵或傳給別人都不安全。第二是執行緒不安全，格式化類別內部有可變狀態，多執行緒共用一個實例會靜默地解析錯，不是拋例外，所以特別難查。第三是設計錯誤，月份從零開始、年份從一九零零起算。第四是概念混淆，沒有只有日期或只有時間的型別。

新的 API 型別選擇圍繞一個問題，這個時間點需不需要時區。我實際判斷的方式是問，如果使用者換了時區，這個值該不該變。生日不該變，所以用不帶時區的日期型別。訂單建立時間該顯示成當地時間但代表同一個瞬間，所以存絕對時間點，顯示的時候再轉。

最典型的錯誤是把所有時間都存成不帶時區的日期時間。它丟失了時區資訊，跨時區的系統之後永遠還原不了真正的瞬間。

還有一個很容易踩的坑。加一天跟加二十四小時在有日光節約的時區裡不一樣，一個是日曆語意一個是物理語意。選錯會有一小時偏差，而且一年只發生兩天，測試幾乎抓不到。

## 常見追問

### 資料庫該用什麼型別存時間？

**核心答案**：**存 UTC 的絕對時間點**，型別上用 `TIMESTAMP WITH TIME ZONE`（PostgreSQL 的 `timestamptz`）或者明確約定為 UTC 的 `TIMESTAMP`／`BIGINT` 毫秒數。Java 端對應 `Instant` 或 `OffsetDateTime`。**不要存本地時間而不記時區**——這是最常見也最難補救的錯誤，因為歷史資料無法還原（你不知道當時那個時間是哪個時區的）。

**詳細解析**：例外是**真正沒有時區語意的值**——生日、國定假日、營業時間表，這些該用 `DATE` 或 `TIME` 存，配 `LocalDate`／`LocalTime`。另外要注意 PostgreSQL 的 `timestamptz` **並不真的存時區**，它把輸入轉成 UTC 儲存、輸出時依連線的時區設定轉換；如果需要保留「使用者當時在哪個時區」這個資訊（例如顯示「當地時間下午三點」），必須**另外存一個時區 ID 欄位**。這個區分常被忽略：**存絕對時刻與存使用者的時區脈絡是兩件事**，需要同時顯示原始當地時間時兩者都要存。

**面試回答方式**：給明確主張——存 UTC 絕對時間點，並強調存本地時間而不記時區**無法補救**因為歷史資料還原不了。接著給例外（生日、營業時間用 `DATE`／`TIME`）。真正的加分點是指出 `timestamptz` 並不真的存時區，需要保留使用者時區脈絡時要另外存時區 ID——**絕對時刻與時區脈絡是兩件事**。

### 為什麼 SimpleDateFormat 不是執行緒安全的？

**核心答案**：因為它在 `format` 與 `parse` 過程中會把中間狀態寫進一個**實例欄位 `calendar`**。多執行緒同時呼叫時，A 執行緒設定好日曆之後、讀取結果之前，B 執行緒可能已經覆寫了同一個日曆——結果是 A 拿到 B 的資料。**症狀是偶發的錯誤日期或格式解析例外，在低併發下幾乎不會出現，壓測或流量高峰時才爆**，所以常常上線很久才被發現。

**詳細解析**：以前的緩解方式有三種：每次 `new`（配置成本高但正確）、用 `ThreadLocal` 快取（正確且省配置，但要小心執行緒池下的洩漏——執行緒長期存活時 ThreadLocal 的值不會被回收）、或加鎖（正確但成為瓶頸）。`DateTimeFormatter` 直接把問題消除了——**它是不可變的，格式化過程中的所有中間狀態都在區域變數裡**，所以可以安全地宣告成 `static final` 共用。這是「用不可變性取代同步」最乾淨的例子之一，也說明了為什麼新 API 從一開始就把不可變當作設計前提。

**面試回答方式**：先給精確機制——中間狀態寫進實例欄位 `calendar`，執行緒之間互相覆寫。強調症狀是**偶發錯誤而非例外**，低併發測不出來、高峰才爆。列出舊的三種緩解方式並指出 ThreadLocal 在執行緒池下的洩漏風險。收在對比：`DateTimeFormatter` 不可變、中間狀態全在區域變數，是「用不可變性取代同步」最乾淨的例子。

### 怎麼處理跨時區的排程需求？

**核心答案**：關鍵是分清楚**「每天當地時間 9 點」與「每 24 小時一次」是兩種不同的需求**。前者是日曆語意，必須存**時區 ID 加當地時刻**（例如 `Asia/Taipei` 加 `09:00`），每次執行時用 `ZonedDateTime` 重新計算下一次的絕對時刻——這樣日光節約調整後仍然是當地的 9 點。後者是物理語意，直接用固定間隔即可。**把日曆語意的排程存成絕對時間戳是錯的**，因為時區規則變更後就對不上了。

**詳細解析**：時區規則**會真的變更**——各國政府調整日光節約政策、甚至改變標準偏移量，這些變更透過 IANA 時區資料庫發布，JDK 靠 `tzdb` 更新。所以**存時區 ID（`Asia/Taipei`）而不是偏移量（`+08:00`）**：ID 是穩定的標識，偏移量只是它在某個時刻的取值。系統還需要有更新 tzdb 的機制（JDK 升級或用 `tzupdater`），否則新的規則生效後排程會偏移。另外在間隙與重疊的邊界上要有明確策略：**當地時間 2:30 在春季調整那天不存在**，排程系統必須決定是跳過、還是移到 3:30，這應該是產品決策而不是預設行為的意外結果。

**面試回答方式**：先把兩種需求區分清楚（日曆語意 vs 物理語意），並給出對應的存法——日曆語意存**時區 ID 加當地時刻**，每次重新計算絕對時刻。強調**存 ID 而非偏移量**，因為時區規則會真的變更，ID 才是穩定標識。加分點是提出 tzdb 更新機制的需求，以及間隙那天的當地 2:30 不存在，該跳過還是移到 3:30 是**產品決策**而非預設行為的意外。
