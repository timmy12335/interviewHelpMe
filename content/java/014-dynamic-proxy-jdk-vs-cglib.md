# 題目

什麼是動態代理？JDK 動態代理和 CGLIB 有什麼差異？Spring AOP 怎麼選用它們？

## 核心答案

動態代理是在執行期動態生成一個代理物件來包裝目標物件，在呼叫目標方法前後插入額外邏輯（如日誌、交易、權限），是 AOP 的核心實作技術。JDK 動態代理基於介面——要求目標類別實作介面，透過反射生成一個實作相同介面的代理類別；CGLIB 基於繼承——透過位元組碼技術生成目標類別的子類別作為代理，不需要介面。Spring AOP 預設「目標有介面就用 JDK 動態代理，沒有介面就用 CGLIB」。

## 詳細解析

**JDK 動態代理**：

- 基於介面：目標類別必須實作至少一個介面，代理類別實作相同的介面。
- 透過 `java.lang.reflect.Proxy.newProxyInstance()` 在執行期生成代理物件，所有介面方法的呼叫都會被轉發到一個 `InvocationHandler` 的 `invoke()` 方法，你在這裡插入前後邏輯並呼叫真正的目標方法。
- 限制：只能代理「介面中定義的方法」，無法代理沒有宣告在介面上的方法。

**CGLIB（Code Generation Library）**：

- 基於繼承：透過 ASM 位元組碼框架，在執行期動態生成目標類別的「子類別」作為代理，覆寫目標方法並插入增強邏輯。
- 不需要介面，可以代理普通類別。
- 限制：因為靠繼承，無法代理 `final` 類別（不能被繼承）和 `final` 方法（不能被覆寫）。

**兩者對比**：

| 面向 | JDK 動態代理 | CGLIB |
|------|-------------|-------|
| 實作機制 | 反射 + 介面 | 位元組碼生成 + 繼承 |
| 前提 | 目標需實作介面 | 目標不能是 final 類別 |
| 能代理的方法 | 介面中的方法 | 非 final 的方法 |
| 生成速度 | 較快 | 較慢（要生成位元組碼） |
| 呼叫速度 | 現代版本已相近 | 早期較快，現在差異小 |

**Spring AOP 的選擇**：

- 預設策略：目標類別有實作介面 → 用 JDK 動態代理；沒有介面 → 用 CGLIB。
- 可以透過設定 `proxyTargetClass=true` 強制全部使用 CGLIB。
- Spring Boot 從 2.x 起預設把 `proxyTargetClass` 設為 true，也就是預設都用 CGLIB（避免一些「只有介面方法能被代理」的困惑）。

## 面試回答方式

先講「動態代理是什麼、解決什麼」（執行期生成代理物件、在方法前後插邏輯、是 AOP 的基礎），這是理解後面比較的前提。接著把 JDK 代理（基於介面/反射）和 CGLIB（基於繼承/位元組碼）的機制與各自限制對比清楚——JDK 要求有介面、CGLIB 不能代理 final。最後講 Spring 的選擇策略（有介面用 JDK、無介面用 CGLIB，Boot 2.x 後預設 CGLIB），把理論連結到最常見的實際框架，展現你理解這不只是 API 知識而是 Spring AOP 的底層。

## 常見追問

### 為什麼 CGLIB 不能代理 final 類別和 final 方法？

**核心答案**：因為 CGLIB 的原理是「動態生成目標類別的子類別」來作為代理，而 `final` 類別不能被繼承（無法生成子類別）、`final` 方法不能被覆寫（子類別無法攔截它插入增強邏輯），所以 CGLIB 對 final 類別完全無法代理，對 final 方法則無法增強（該方法會直接執行原邏輯，不經過代理攔截）。

**詳細解析**：這是 CGLIB「基於繼承」機制的直接後果。代理的本質是「攔截方法呼叫、插入額外邏輯」，CGLIB 靠的是生成一個子類別、覆寫父類別的方法來實現攔截。`final` 在 Java 中的語意正是「禁止繼承/覆寫」——`final` 類別擋住了子類別的生成，`final` 方法擋住了覆寫。因此如果你想讓一個類別能被 Spring AOP 用 CGLIB 代理（例如加交易、日誌），就不能把它或它需要被增強的方法宣告為 final。這也是實務上一個容易踩的坑——把 Service 類別或方法宣告成 final，導致 AOP 增強「靜默失效」（不報錯但增強沒生效）。

**面試回答方式**：用「CGLIB 靠生成子類別代理，final 禁止繼承/覆寫所以無法代理」這個因果直接回答，並補上實務陷阱——「Service 方法宣告 final 會導致 AOP 靜默失效」，展現你能把機制連結到真實開發中會遇到的坑。

### Spring AOP 中，一個方法呼叫同類別的另一個被 AOP 增強的方法，增強會生效嗎？

**核心答案**：不會生效。這是 Spring AOP 著名的「自我呼叫（self-invocation）」失效問題——因為 AOP 增強是透過「代理物件」攔截外部呼叫來實現的，而類別內部方法 A 呼叫方法 B 時，用的是 `this.B()`（直接呼叫真實物件本身），完全繞過了代理物件，所以 B 上的 AOP 增強（如 `@Transactional`、`@Cacheable`）不會生效。

**詳細解析**：假設一個 Service 有方法 A 和方法 B，B 上標了 `@Transactional`。外部呼叫 `service.B()` 時，走的是 Spring 注入的代理物件，代理會攔截並開啟交易——正常生效。但如果外部呼叫 `service.A()`，而 A 內部呼叫 `this.B()`，這個 `this` 是真實的目標物件（不是代理物件），呼叫直接落到真實的 B 方法，完全沒經過代理的攔截，所以 B 的 `@Transactional` 就不會開啟交易。這是因為 AOP 的增強邏輯「住在代理物件裡」，而自我呼叫用的是真實物件的引用。解法包括：把 B 抽到另一個 Bean（讓呼叫經過代理）、或透過 `AopContext.currentProxy()` 取得代理物件再呼叫、或注入自己的代理引用。

**面試回答方式**：這是一個高頻的實戰陷阱題，回答時要講清楚「自我呼叫用的是 this（真實物件）而非代理物件，所以繞過了代理攔截、增強失效」這個核心原因，再給出解法（抽到別的 Bean、或用 AopContext）。能主動點出「`@Transactional`/`@Cacheable` 在自我呼叫時失效」這個具體現象，展現你有踩過或深入理解過這個經典坑。

### 除了 JDK 代理和 CGLIB，還有其他實現代理/增強的方式嗎？

**核心答案**：有。除了執行期的動態代理，還有「編譯期織入」和「載入期織入」等方式——例如 AspectJ 支援在編譯期（透過特殊編譯器）或類別載入期（透過 Java Agent）直接把增強邏輯織入到目標類別的位元組碼中，不需要生成代理物件，因此沒有 JDK/CGLIB 的介面限制或 final 限制，也沒有自我呼叫失效問題，功能更強大但配置更複雜。

**詳細解析**：Spring AOP 用的是「執行期動態代理」，優點是簡單、無需特殊編譯器，缺點是有前述的介面/final/自我呼叫等限制。而 AspectJ 的「編譯期織入（CTW）」在編譯階段就把切面邏輯直接編織進目標類別的位元組碼，「載入期織入（LTW）」則在類別被 JVM 載入時透過一個 Java Agent 動態修改位元組碼。這兩種方式因為是「直接改目標類別本身的位元組碼」而非「在外面包一層代理」，所以能增強任何方法（包括 final、private、自我呼叫），功能最完整，但需要額外的編譯器或啟動參數配置。Spring 也支援整合 AspectJ 的 LTW 來突破自身動態代理的限制。理解這個光譜（執行期代理 → 載入期織入 → 編譯期織入）能展現你對 AOP 實作技術的全局認識。

**面試回答方式**：能講出「除了執行期動態代理，還有 AspectJ 的編譯期織入和載入期織入」，並說明後者「直接改目標位元組碼、沒有代理的那些限制（能增強 final/private/自我呼叫）但配置更複雜」，展現你對 AOP 實作技術的認識超越了 Spring 預設的動態代理，是很有廣度的回答。
