# 題目

`enum` 編譯之後是什麼？為什麼《Effective Java》說單一元素的列舉是實作單例最好的方式？

## 核心答案

`enum` 編譯後是一個**繼承 `java.lang.Enum` 的 final 類別**，每個常數是一個 `public static final` 的實例，在**靜態初始化區塊中建立**。編譯器同時生成 `values()`（回傳一份陣列拷貝）與 `valueOf(String)`。因為實例在類別初始化時建立，而類別初始化由 JVM 保證**執行緒安全且只執行一次**，所以列舉常數天生就是安全發布的單例。

單一元素列舉之所以是最好的單例實作，是因為它**免費解決了三個問題**：**執行緒安全**（類別初始化的保證）、**序列化安全**（`Enum` 的序列化機制只寫名稱，反序列化時用 `valueOf` 取得既有實例，不會產生新物件，而且 `readObject` 被寫死無法被繞過）、**反射攻擊**（`Constructor.newInstance` 對列舉型別會直接拋 `IllegalArgumentException`）。傳統的雙重檢查鎖單例三個都要自己處理，而序列化那一項幾乎沒人記得。

## 詳細解析

列舉可以有欄位、建構子與方法，這是它比常數字串或整數常數強大的地方。`enum Status { PENDING("待處理", 0), PAID("已付款", 1); ... }` 讓顯示名稱、資料庫值與常數綁在一起，避免了「三個地方各維護一份對照」的漂移問題。**建構子必然是 private**（寫 public 會編譯錯誤），因為實例集合是封閉的。

常數專屬的方法主體（constant-specific method body）讓列舉可以有多型行為：每個常數後面接一個 `{ ... }` 覆寫抽象方法，編譯後每個常數其實是一個**匿名子類別**的實例。這讓「訂單狀態各自知道自己能轉移到哪些狀態」這種狀態機可以寫得很緊湊，而且新增狀態時編譯器會強迫實作抽象方法——遺漏會編譯失敗而不是執行期出錯。

**EnumMap 與 EnumSet 是列舉的專屬容器**，它們的效能遠勝一般容器：`EnumMap` 內部是以 `ordinal` 為索引的陣列，`EnumSet` 是位元向量。**只要鍵是列舉就該用它們**，沒有理由用 `HashMap`。但要注意 `ordinal()` **不該被序列化或存進資料庫**——它是宣告順序，在列舉中間插入一個新常數時所有後面的值都會位移，歷史資料就對不上了。存資料庫要存**名稱**或**明確定義的自訂碼**。

**列舉的限制也要知道**：它不能繼承其他類別（已經繼承 `Enum` 了），但可以實作介面——這是讓多個列舉共享行為的標準做法。它也**無法在執行期擴充**，需要「基礎行為固定但可被外部擴充」時，模式是定義一個介面，列舉實作它，外部再提供其他實作（JDK 的 `TimeUnit` 與 `ChronoUnit` 之間就是類似的關係）。

## 面試回答方式

先給編譯結果——繼承 `Enum` 的 final 類別，常數是靜態 final 實例，在靜態初始化區塊建立，並指出這正是執行緒安全的來源（類別初始化由 JVM 保證只執行一次）。然後回答單例的問題，關鍵是列出它免費解決的三件事：執行緒安全、序列化安全（只寫名稱、反序列化走 `valueOf`，`readObject` 無法被繞過）、反射攻擊（`newInstance` 對列舉直接拋例外），並強調傳統雙重檢查鎖三件都要自己處理，而序列化那一項幾乎沒人記得。加分點給三個：常數專屬方法主體編譯後是匿名子類別，讓狀態機的遺漏在編譯期被抓到；**`EnumMap`／`EnumSet` 用陣列與位元向量**，鍵是列舉就該用；以及 **`ordinal` 不可持久化**，插入新常數會讓歷史資料位移。

## 講稿

列舉編譯之後是一個繼承 Enum 的 final 類別，每個常數是一個靜態 final 實例，在靜態初始化區塊裡建立。因為類別初始化由 JVM 保證執行緒安全而且只執行一次，所以列舉常數天生就是安全發布的單例。

這也是為什麼單一元素的列舉是最好的單例實作。它免費解決三個問題。執行緒安全，來自類別初始化的保證。序列化安全，因為列舉的序列化只寫名稱，反序列化的時候用名稱去取既有實例，不會產生新物件，而且那段邏輯被寫死無法繞過。還有反射攻擊，對列舉型別呼叫建構子會直接拋例外。

傳統的雙重檢查鎖單例，這三件事都要自己處理，而序列化那一項幾乎沒有人記得。

另外我想提一個實務上很重要的細節。ordinal 不該被序列化或存進資料庫，因為它是宣告順序。在列舉中間插入一個新常數，後面的值全部位移，歷史資料就對不上了。要存就存名稱，或是自己定義一個明確的碼。

## 常見追問

### 列舉常數專屬的方法主體有什麼實際用途？

**核心答案**：實作**每個常數行為不同的多型**，最典型的是狀態機與策略。`enum Operation { PLUS { int apply(int a, int b) { return a + b; } }, MINUS { ... } }`——每個常數覆寫抽象方法，編譯後各自是一個匿名子類別。它的價值不只在簡潔，更在**編譯期強制完整性**：新增一個常數而忘記實作抽象方法會直接編譯失敗，不會留下一個執行期才發現的漏洞。

**詳細解析**：狀態機是最有價值的應用。把「允許的下一個狀態」定義成每個狀態常數的方法，狀態轉移的合法性檢查就集中在一個地方，而不是散在各個服務裡。相比之下，用 `switch` 在外部判斷有兩個問題：新增狀態時編譯器**不一定**提醒（除非用了密封類別或窮盡的 switch 表達式），而且同樣的 switch 可能散落好幾處。代價是行為被綁進列舉，當行為屬於別的關注點（例如 UI 顯示、報表格式）時就不該塞進來——那種情況用外部的 `EnumMap` 查表或 switch 表達式更合適。判準與抽象類別 vs 組合是同一個：行為是不是這個型別的本質。

**面試回答方式**：給出用途（每常數不同行為的多型）與最有價值的性質——新增常數而忘記實作會編譯失敗。用狀態機當主要例子，說明它把轉移規則集中在一處。然後給界線：行為屬於別的關注點時不該塞進列舉，改用 `EnumMap` 查表或外部的 switch 表達式，判準是「行為是不是這個型別的本質」。

### 列舉存進資料庫該用什麼形式？

**核心答案**：存名稱字串或自訂的穩定碼，絕對不要存 `ordinal()`。`ordinal` 是宣告順序，在中間插入常數或重新排序時全部位移，而歷史資料不會跟著改，結果是**靜默的資料錯亂**——訂單狀態突然從「已付款」變成「已取消」。名稱字串可讀性好、重構時 IDE 能幫忙找出引用；自訂碼（每個常數帶一個明確的 int 或 short code）則省空間且與名稱重構解耦。

**詳細解析**：JPA 的 `@Enumerated` 預設是 `ORDINAL`，**這是一個危險的預設值**，一定要明確寫成 `@Enumerated(EnumType.STRING)` 或用 `AttributeConverter` 映射自訂碼。用自訂碼時要記得**處理未知值**——資料庫裡可能有比目前程式碼更新的碼（灰度發布期間舊版程式讀到新版寫入的資料），此時應該有明確的策略：拋例外並拒絕處理，或映射到一個 `UNKNOWN` 常數並記錄。「反序列化遇到未知列舉值」是跨版本相容性最常見的破口之一，值得在設計時就決定策略而不是等它發生。

**面試回答方式**：明確反對存 `ordinal` 並說明後果是**靜默的資料錯亂**。指出 JPA 的 `@Enumerated` 預設就是 `ORDINAL`，這個危險預設值一定要覆寫。加分點是提出**未知值的處理策略**：灰度發布期間舊版程式會讀到新版寫入的碼，應該事先決定是拒絕還是映射到 UNKNOWN——這顯示你想過跨版本相容性。

### 為什麼有人說「不要用列舉表示會變動的業務概念」？

**核心答案**：因為列舉是編譯期常數，修改它需要重新編譯與部署。如果一個概念的變體由業務人員決定且會頻繁增減（商品分類、優惠券類型、行銷活動），做成列舉意味著每次新增都要走完整的發版流程。這類概念該存在資料庫裡當作資料，而不是寫在程式碼裡當作型別。

**詳細解析**：判準是**變更的頻率與變更的決策者**。變體由工程決定且穩定（訂單狀態、支付結果、HTTP 方法）就適合列舉——它換來編譯期檢查、`EnumMap` 的效能、以及 switch 的窮盡性保證。變體由業務決定且會變動就該是資料。**中間地帶是最難的**：例如支付方式，短期穩定但偶爾會加新的。這時可行的折衷是列舉表示「程式碼需要特別處理的種類」，資料庫表示「完整的清單」——大多數支付方式走通用流程（資料驅動），少數需要特殊邏輯的才在列舉裡有對應常數。這樣新增一般的支付方式不必發版，新增需要特殊處理的才需要。

**面試回答方式**：給判準——**變更頻率與決策者**，工程決定且穩定就用列舉，業務決定且會變就存資料庫。真正的加分點是處理中間地帶：列舉表示「需要特別處理的種類」、資料庫表示「完整清單」，用支付方式舉例說明新增一般種類不必發版、需要特殊邏輯的才需要。這顯示你能處理不是非黑即白的設計問題。
