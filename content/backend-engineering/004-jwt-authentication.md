# 題目

JWT（JSON Web Token）是怎麼運作的？相較於傳統的 Session 認證，有什麼優缺點？實務上使用 JWT 有哪些安全性要注意的地方？

## 核心答案

**JWT** 是一種將使用者身份和權限資訊，編碼成一個「自包含（Self-Contained）、可驗證簽章」的字串 Token 的標準格式，結構分成三段（以 `.` 分隔）：**Header**（描述簽章演算法等中繼資訊）、**Payload**（實際的聲明資料，如使用者 ID、角色、過期時間，用 Base64 編碼但**沒有加密**，任何人都能解碼看到內容）、**Signature**（伺服器用私鑰對前兩段內容做簽章，確保內容沒有被竄改）。伺服器在使用者登入成功後簽發 JWT，之後每次請求，客戶端在 Header 帶上這個 Token，伺服器只需要**驗證簽章是否合法**，就能確認這個 Token 裡的資訊（使用者身份、角色）沒有被竄改，**不需要查詢資料庫或任何共享儲存**，這是它相較於傳統 Session 認證最大的優勢——真正的無狀態、易於水平擴展（Horizontal Scaling）。缺點包括：**Payload 內容不加密**（不應該放敏感資訊）、**簽發後難以主動撤銷**（不像 Session 可以隨時從伺服器端刪除記錄）、以及需要謹慎處理 Token 的儲存位置以防範 XSS 竊取。

## 詳細解析

**JWT 與傳統 Session 認證的根本差異**：傳統的 Session 認證，伺服器在使用者登入後，會在伺服器端（記憶體或共享儲存如 Redis）建立一筆「Session 記錄」，並把一個隨機的 Session ID 回傳給客戶端（通常存在 Cookie），之後每次請求，伺服器都要「拿著這個 Session ID 去查詢對應的 Session 記錄」才能知道這個使用者是誰，這代表伺服器需要**額外的儲存和查詢成本**，且在多台伺服器的架構下，需要一個「共享的 Session 儲存」（如 Redis）讓所有伺服器都能查到同一份 Session 資料，否則容易出現「使用者這次請求被路由到 A 伺服器、下次被路由到沒有這筆 Session 記錄的 B 伺服器」導致認證失敗的問題。JWT 的設計哲學完全不同——它把「使用者是誰、有什麼權限」這些資訊**直接編碼進 Token 本身**，並用密碼學簽章保證這些資訊沒有被竄改，伺服器收到請求時，只需要「用密鑰驗證這個 Token 的簽章是否合法」，就能相信 Token 裡宣稱的內容（因為只有持有正確密鑵的伺服器才能生成合法的簽章，第三方無法偽造），**完全不需要查詢任何額外的儲存**，這讓 JWT 認證天然具備良好的水平擴展性——任何一台伺服器，只要持有驗證簽章所需的密鑰（或公鑰），都能獨立完成驗證，不需要依賴共享的 Session 儲存。

**JWT 的結構細節**：一個典型的 JWT 長這樣：`eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxMjM0NTY3ODkwIn0.dQw4w9WgXcQ...`，三段分別是——**Header**（如 `{"alg": "HS256", "typ": "JWT"}`，說明用什麼演算法簽章）、**Payload**（如 `{"sub": "1234567890", "role": "admin", "exp": 1700000000}`其中 `exp` 是這個 Token 的過期時間，是 JWT 標準裡的重要保留欄位）、**Signature**（伺服器用密鑰對「Header + Payload 的 Base64 編碼結果」做簽章運算得出的結果）。**必須理解的關鍵細節是——Header 和 Payload 只是用 Base64 編碼，不是加密**，任何人拿到這個 Token，都可以直接用 Base64 解碼看到 Payload 裡的實際內容（例如使用者 ID、角色），只是無法在不知道密鑰的情況下「竄改內容並生成一個新的、合法的簽章」，這是「防竄改」而不是「保密」，因此 **Payload 裡絕對不應該放置敏感資訊**（如密碼、身分證字號），因為它實質上是明文的，只是編碼過而已。

**JWT 難以主動撤銷的問題**：因為 JWT 的驗證完全基於「簽章是否合法」，一旦簽發出去，在它的 `exp` 過期時間到達之前，伺服器**無法主動讓某一個特定的 Token 立刻失效**（不像 Session 可以直接從資料庫或 Redis 裡刪除那筆記錄），這在「使用者登出」、「偵測到帳號被盜用需要立即撤銷所有 Token」這類場景下會是個問題。常見的緩解方案包括：**（1）設定較短的過期時間**（如 15-30 分鐘），搭配 **Refresh Token 機制**（另一個生命週期較長、但只能用來換取新的短期 Access Token 的憑證，Refresh Token 儲存在伺服器端資料庫中，可以被主動撤銷）；**（2）維護一個「黑名單」**，記錄已經被主動撤銷但尚未過期的 Token（通常存在 Redis，設定和 Token 剩餘有效期相同的 TTL），伺服器驗證時額外檢查這個黑名單，但這個做法某種程度上又引入了「需要額外查詢共享儲存」的成本，部分抵銷了 JWT 原本「完全無狀態」的優勢。

**安全性注意事項**：JWT 應該**只透過 HTTPS 傳輸**（避免在傳輸過程中被竊聽）；儲存在客戶端時，如果放在 `localStorage`，容易受到 **XSS 攻擊**（惡意腳本可以直接讀取 localStorage 的內容並竊取 Token），較安全的做法是放在 **HttpOnly 的 Cookie**（JavaScript 無法讀取，降低 XSS 竊取風險），但這樣又需要額外處理 **CSRF** 防護；伺服器端簽發 Token 時應該**驗證並限制簽章演算法**（曾經有一類經典的 JWT 漏洞，是攻擊者把 Token 的演算法欄位改成 `none`，如果伺服器驗證邏輯沒有嚴格檢查，可能誤判為合法，或利用非對稱演算法和對稱演算法混淆的漏洞，因此驗證邏輯應該明確指定「只接受哪一種演算法」而非信任 Token 本身宣稱的演算法）。

## 面試回答方式

先講清楚 JWT 的結構（Header/Payload/Signature）和核心工作原理（伺服器簽發、簽章驗證、無狀態）。對比 Session 認證，點出最核心的差異——「JWT 不需要伺服器端儲存和查詢，天然適合水平擴展；Session 需要共享儲存」。接著主動點出 JWT 的缺點——「Payload 不加密只是編碼、難以主動撤銷」，這是這題容易被忽略但很重要的部分，展現你不是只知道 JWT 的優點。最後補充安全性注意事項（HTTPS傳輸、儲存位置的 XSS/CSRF 權衡、演算法驗證）。這是一道基礎但很實務的題目，能講出「難以撤銷」這個核心限制和對應的緩解方案（短期 Token + Refresh Token），比只會背誦「JWT 無狀態、可擴展」這些優點更能展現深度。

## 常見追問

### Refresh Token 機制具體是怎麼運作的？為什麼 Refresh Token 可以撤銷，但 Access Token（JWT）卻難以撤銷？

**核心答案**：Refresh Token 機制的運作方式是——使用者登入成功後，伺服器同時簽發**兩個 Token**：一個**短期的 Access Token**（通常是 JWT，有效期 15-30 分鐘，用於實際的 API 請求認證）和一個**長期的 Refresh Token**（有效期可能是幾天到幾週，僅用來「換取新的 Access Token」，不直接用於一般 API 請求）。當 Access Token 過期後，客戶端用 Refresh Token 向專門的「換新端點」請求一個新的 Access Token（以及通常也會換發一個新的 Refresh Token），不需要使用者重新輸入帳密。Refresh Token **之所以可以被撤銷**，是因為它**必須被記錄在伺服器端的資料庫裡**（每次換發都要查詢資料庫驗證這個 Refresh Token 是否合法且未被撤銷），這個「查詢資料庫」的動作，讓伺服器有機會在查詢當下，主動判斷「這個 Refresh Token 是否已經被列入撤銷名單」，如果使用者登出或帳號被盜用需要緊急處理，只要在資料庫裡把這筆 Refresh Token 記錄標記為失效，之後任何用它換新 Token 的請求都會被拒絕；而 Access Token（JWT）本身的設計理念就是「不需要查詢任何儲存，只憑簽章驗證」，這個設計上的犧牲換來了效能優勢，但也代表它天生就沒有「查詢時順便檢查是否被撤銷」這個介入點。

**詳細解析**：這題深入 Access Token 和 Refresh Token 這一組合設計的核心分工邏輯，說明為什麼要用「兩個 Token、兩種不同的驗證機制」而不是單純依賴一個 JWT。這個雙 Token 設計的精妙之處，在於它試圖「兼顧 JWT 的效能優勢和 Session 的可撤銷優勢」——大部分的 API 請求（頻率高）用 Access Token 驗證，享受「不查資料庫、純簽章驗證」的高效能；而「需要撤銷」這個相對低頻的需求（換發新 Token 這個動作，頻率遠低於一般 API 呼叫，可能每 15-30 分鐘才發生一次，而不是每次 API 呼叫都要發生），交給 Refresh Token 這個「必須查詢資料庫」的機制來處理，用相對低頻的查詢成本，換取「撤銷能力」這個重要的安全特性。這個設計的關鍵洞察是——「撤銷」這個需求，其實不需要「每一次 API 呼叫都能立即感知」，只需要「在 Access Token 的有效期（通常設定得很短，如 15-30 分鐘）內生效即可」——即使使用者在某一刻登出、或帳號被盜用而被緊急撤銷，之前已經簽發、還沒過期的 Access Token，在最壞情況下也只會「多存活最多 15-30 分鐘」（直到它自然過期），這個時間窗口在多數業務場景下是可以接受的風險（用短暫的延遲換取整體系統的高效能），如果需要更即時的撤銷（例如金融交易這類極度敏感的場景），才需要考慮額外的黑名單機制（如前面提到的、把已撤銷但未過期的 Access Token 記錄到 Redis），犧牲一些效能換取更即時的撤銷能力。理解「Access Token 和 Refresh Token 是用不同的驗證機制（純簽章 vs 查詢資料庫），分別對應『高頻但可以接受短暫失效延遲』和『低頻但需要立即生效的撤銷』這兩種不同的需求」，展現你理解這個常見架構設計背後真正的權衡邏輯。

**面試回答方式**：講出雙 Token 的運作流程——「Access Token（JWT，短期,15-30分鐘，一般 API 請求用，純簽章驗證不查資料庫）+ Refresh Token（長期，只用於換新 Access Token，必須查詢資料庫驗證是否被撤銷）」。解釋核心設計邏輯——「Refresh Token 因為每次使用都要查資料庫，所以能在查詢當下判斷是否已被撤銷；Access Token 為了效能刻意不查資料庫，所以撤銷能力被犧牲，但用『設定較短過期時間』把這個風險限制在可接受的時間窗口內」。展現你理解這是「用 Refresh Token 的低頻查詢成本，換取整體系統對高頻 Access Token 驗證的效能優勢，同時保留撤銷能力」這個精妙的權衡設計。

### 如果把 JWT 存在 localStorage，容易被 XSS 竊取；存在 HttpOnly Cookie，又要處理 CSRF。這兩種儲存方式的權衡該怎麼選？

**核心答案**：**存在 `localStorage`**：優點是使用簡單、不會受到 CSRF 攻擊影響（因為 CSRF 的攻擊原理是利用瀏覽器「自動帶上 Cookie」的機制，如果 Token 不是存在 Cookie 而是需要 JavaScript 主動從 localStorage 讀取並手動加到請求 Header，瀏覽器不會自動代為附加，天然免疫 CSRF）；缺點是完全暴露在 **XSS（跨站腳本攻擊）** 風險下——只要網站存在任何一個 XSS 漏洞（惡意腳本能在頁面上下文執行)，攻擊者的腳本就能直接讀取 `localStorage` 竊取 Token。**存在 HttpOnly Cookie**：優點是設定了 `HttpOnly` 屬性後，JavaScript **完全無法讀取**這個 Cookie 的內容，即使頁面存在 XSS 漏洞，惡意腳本也無法直接竊取到 Token；缺點是瀏覽器會在每次請求時「自動」把這個網域底下的 Cookie 帶上，這正是 CSRF 攻擊的利用基礎（惡意網站誘導使用者的瀏覽器發出請求，瀏覽器自動帶上受害者的 Cookie，讓惡意請求看起來像是使用者本人發出的），需要額外搭配 **CSRF Token** 或 `SameSite` Cookie 屬性等機制來防範。實務上業界的普遍共識是——**HttpOnly Cookie 搭配完善的 CSRF 防護，通常被認為是相對更安全的選擇**，因為 XSS 一旦發生，攻擊者能做的事情往往遠不止竊取 Token（可以直接在使用者的瀏覽器上下文中做任何操作），而 CSRF 的防護手段（CSRF Token、`SameSite=Strict/Lax`）相對成熟且容易正確實作。

**詳細解析**：這題要求對兩種儲存方式的風險模型做精確比較，而不是簡單地說「兩種都有風險，看情況選」。理解這個權衡的關鍵，在於認識到 **XSS 和 CSRF 這兩種攻擊的本質差異**——XSS 是「攻擊者的惡意程式碼，在受害者的瀏覽器裡、以受害者的權限執行」，一旦 XSS 發生，攻擊者能做的事情極其廣泛（不只是竊取 Token，還能偽造使用者的任何操作、竊取頁面上顯示的任何敏感資訊、甚至進一步發起其他攻擊），可以說「XSS 一旦得逞，遊戲基本上已經結束」，Token 儲存方式頂多是「多一道防線或少一道防線」的差別，並不能從根本上防止 XSS 造成的其他傷害；而 CSRF 攻擊，雖然利用了「瀏覽器自動帶 Cookie」這個機制，但攻擊者「看不到」回應內容（CSRF 通常是「盲打」，讓使用者的瀏覽器發出一個惡意請求，但攻擊者無法讀取這個請求的回應結果，因為同源政策的限制），且業界已經發展出相對成熟、容易正確實作的防禦手段（如 `SameSite=Lax` 或 `Strict` 這個 Cookie 屬性，現代瀏覽器預設值已經是 `Lax`，大幅降低了傳統 CSRF 攻擊的可行性；再搭配傳統的 CSRF Token 雙重驗證，防禦效果相當可靠）。基於這個風險模型的比較——「把 Token 放在 localStorage，雖然規避了 CSRF，但完全暴露在 XSS 之下（而 XSS 本身的危害遠不只是竊取 Token 這麼簡單）」，相較於「把 Token 放在 HttpOnly Cookie，即使發生 XSS，至少 Token 本身不會被直接竊取（雖然攻擊者可能還是能透過其他方式，如誘導使用者在被 XSS 污染的頁面上執行敏感操作，達到類似的破壞效果，但至少 Token 這個關鍵憑證本身多了一層保護)，同時搭配相對成熟可靠的 CSRF 防禦手段」，多數安全實務的共識傾向於後者是相對更穩健的選擇。理解這個權衡不是簡單的「兩害相權取其輕」，而是要理解「XSS 的危害面遠大於單純的 Token 竊取，而 CSRF 有相對成熟可靠的獨立防禦手段」這個更細緻的風險評估邏輯，展現你的安全思維有紮實的風險模型作為判斷基礎，而不只是背誦兩種方案的優缺點清單。

**面試回答方式**：先列出兩種方式各自的優缺點——「localStorage 天然免疫 CSRF 但完全暴露在 XSS 下；HttpOnly Cookie 能防止 JavaScript 直接讀取 Token(即使 XSS 也讀不到)但需要額外處理 CSRF」。給出業界傾向的判斷並解釋原因——「多數傾向 HttpOnly Cookie + CSRF 防護，因為 XSS 一旦發生，危害遠不止竊取 Token(能做任何以使用者身份的操作)，而 CSRF 有相對成熟可靠的防禦手段(SameSite 屬性、CSRF Token)」。展現你的判斷建立在對兩種攻擊本質差異和危害範圍的精確風險評估上，而非簡單的優缺點羅列。

### 如果伺服器需要支援「多個服務各自獨立驗證 JWT」（微服務（Microservices）架構下，每個服務都要能驗證使用者身份，但不希望每個服務都呼叫認證服務去驗證)，應該怎麼設計簽章機制？

**核心答案**：應該使用**非對稱加密演算法（如 RS256、ES256）而非對稱加密演算法（如 HS256）** 來簽發 JWT——用一把只有**認證服務（Auth Service）自己持有的私鑰（Private Key）** 來簽發 Token，而把對應的**公鑰（Public Key）** 分發給所有需要驗證 Token 的其他微服務。因為非對稱加密的特性是「私鑰簽章、公鑰驗證」，各個下游微服務只需要持有公鑰（公鑰外洩不會造成安全問題，因為它只能用來「驗證」，不能用來「簽發」新的合法 Token），就能各自獨立完成 Token 驗證，完全不需要每次都呼叫認證服務，也不用擔心因為分享了「能簽發 Token 的密鑰」給多個服務而擴大了金鑰外洩的風險面。

**詳細解析**：這題考察在多服務架構下，JWT 簽章演算法選擇（對稱 vs 非對稱）這個常被忽略但至關重要的安全設計決策。如果使用像 HS256 這樣的**對稱加密演算法**，簽章和驗證用的是**同一把密鑰**——這意味著，如果要讓多個微服務都能獨立驗證 Token（不透過認證服務中轉），就必須把這把「用來簽章的密鑰」分發給每一個需要驗證的服務，但這帶來了嚴重的安全隱憂——**任何一個持有這把密鑰的服務，不只能「驗證」Token，同時也具備「簽發」任意合法 Token 的能力**（因為簽章和驗證用的是同一把鑰匙），如果這些微服務中的任何一個被入侵，攻擊者就能拿到這把「萬能密鑰」，偽造任意使用者身份的合法 Token，攻擊面因為密鑰被分散到多個服務而大幅擴大。改用**非對稱加密演算法（RS256 等）** 從架構上根本解決了這個問題——簽發 Token 只需要私鑰，這把私鑰可以被嚴格地限制只存在於認證服務（唯一真正需要「簽發」能力的地方），而驗證 Token 只需要對應的公鑰，公鑰可以被放心地分發給所有下游服務、甚至公開發布也沒有安全疑慮（這正是「公鑰」這個名稱的由來——它本來就被設計成可以公開的），因為單憑公鑰，無法反推出私鑰、也無法用公鑰偽造出一個能通過驗證的合法簽章。這樣一來，即使某個下游微服務被入侵，攻擊者頂多只能拿到「驗證用的公鑰」，這對攻擊者毫無用處（他們沒辦法用公鑰去偽造新的 Token），真正敏感、具備簽發能力的私鑰，始終被安全地限制在認證服務這一個地方，大幅縮小了「金鑰外洩導致偽造 Token」這個攻擊面。這個設計原則呼應了資訊安全裡「最小權限（Least Privilege）」的核心思想——「驗證」和「簽發」是兩種截然不同、風險程度也截然不同的能力，非對稱加密演算法讓我們能夠精確地把這兩種能力分開授予不同的角色（認證服務擁有簽發能力、其他服務只擁有驗證能力），而不是像對稱加密那樣「要嘛完全不給、要嘛給了就是兩種能力都給」。

**面試回答方式**：直接給出答案——「用非對稱加密演算法(如 RS256)而非對稱加密(HS256)」。解釋核心原因——「對稱加密簽章和驗證用同一把密鑰，分發給多個服務等於把『簽發能力』也一併分發出去，任何一個服務被入侵就能偽造任意 Token，攻擊面大幅擴大；非對稱加密可以把私鑰(簽發能力)嚴格限制在認證服務，只把公鑰(僅能驗證，無法偽造)分發給下游服務，即使某個服務被入侵，攻擊者也只拿到毫無用處的公鑰」。可以延伸提到這呼應了「最小權限原則」——把簽發和驗證這兩種風險程度不同的能力，精確地分開授予不同角色。展現你在多服務架構下，對金鑰管理和攻擊面控制有具體、正確的安全設計判斷。
