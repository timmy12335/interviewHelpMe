# 題目

Saga 模式的「編排式（Orchestration）」和「協同式（Choreography）」這兩種實作方式，具體怎麼運作？各自適合什麼場景？

## 核心答案

**編排式（Orchestration）**：有一個**中心化的編排器（Orchestrator）**，明確地知道整個 Saga 流程的所有步驟和順序，由編排器主動地依序呼叫每一個服務（「呼叫訂單服務建立訂單」→「呼叫庫存服務扣庫存」→「呼叫支付服務扣款」），並根據每一步的成功或失敗，決定接下來該繼續往下一步、還是觸發補償邏輯（依序呼叫之前已成功步驟的補償操作）。**協同式（Choreography）**：**沒有中心化的協調者**，每個服務各自訂閱自己關心的事件，完成自己的本地交易後，發布一個事件（如「訂單已建立」事件），下一個服務（如庫存服務）訂閱到這個事件後，自己觸發並完成自己的本地交易，再發布下一個事件，依此類推，形成一條由事件驅動（Event-Driven）、去中心化的鏈條；失敗時，同樣透過發布「失敗事件」，讓已經完成的上游服務各自訂閱到這個失敗事件並觸發自己的補償邏輯。編排式適合**流程複雜、步驟較多、需要清楚的可觀測性和除錯能力**的場景；協同式適合**流程相對簡單、服務數量少、希望盡量減少服務間耦合**的場景。

## 詳細解析

**編排式的具體運作**：以「下單」流程為例，編排式的做法是——建立一個「訂單 Saga 編排器」，這個編排器明確知道「下單」這個大流程需要依序執行「建立訂單」、「扣庫存」、「扣款」、「安排出貨」這幾個步驟，編排器主動呼叫訂單服務的 API 建立訂單，成功後主動呼叫庫存服務的 API 扣庫存，成功後主動呼叫支付服務的 API 扣款，依此類推；如果任何一步失敗（例如扣款失敗），編排器會依照**已經成功的步驟、以相反順序**主動呼叫對應的補償 API（先呼叫庫存服務的「釋放庫存」補償邏輯，再呼叫訂單服務的「取消訂單」補償邏輯）。這種方式的優點是——**整個業務流程的邏輯集中在編排器這一個地方**，任何人想要理解或除錯「下單這個完整流程到底涉及哪些步驟、目前卡在哪一步」，只需要查看編排器的程式碼和執行記錄，非常直觀；缺點是——各個被呼叫的服務(訂單、庫存、支付服務)，某種程度上「知道」自己是被一個編排器呼叫的（需要提供編排器能呼叫的 API），編排器本身也需要對每個涉及的服務有一定程度的了解（知道要呼叫哪些 API、以什麼順序），這種「中心化」的設計，某種程度上重新引入了一些耦合(雖然不像單體那麼緊密，但編排器確實對整個流程涉及的所有服務有較深的認識)。

**協同式的具體運作**：同樣以「下單」為例，協同式的做法是——訂單服務完成「建立訂單」的本地交易後，不主動呼叫任何其他服務，而是向一個共享的事件匯流排(訊息佇列（Message Queue）)發布一個「OrderCreated（訂單已建立）」事件；庫存服務**訂閱**了這個事件，一旦收到「OrderCreated」事件，自己主動執行「扣庫存」的本地交易，完成後發布「StockReserved（庫存已扣減）」事件；支付服務訂閱「StockReserved」事件，收到後執行扣款、發布「PaymentCompleted」事件，依此類推。如果某一步失敗（例如支付服務扣款失敗），支付服務發布一個「PaymentFailed」事件，**庫存服務和訂單服務分別各自訂閱這個失敗事件**，各自觸發自己的補償邏輯（庫存服務釋放庫存、訂單服務取消訂單）。這種方式的優點是——**服務之間完全不需要知道彼此的存在**（訂單服務只需要知道「我完成了，發布一個事件」，完全不需要知道「後面誰會處理這個事件」），耦合度最低，新增一個對「訂單已建立」這個事件感興趣的新服務，只需要讓它訂閱這個事件即可，完全不需要修改任何既有服務的程式碼；缺點是——**整個業務流程的邏輯，分散在各個服務各自的事件訂閱/發布邏輯裡**，沒有一個地方能讓人「一眼看到」完整的流程全貌，隨著涉及的服務數量增加，理解「這個事件會觸發哪些連鎖反應」、除錯「流程卡在哪一步、為什麼」變得越來越困難，這種分散帶來的可觀測性挑戰，是協同式 Saga 最常被詬病的問題。

**選擇的判斷依據**：流程涉及的**服務數量和步驟複雜度**是最直接的判斷依據——如果一個 Saga 流程只涉及兩三個服務、邏輯相對單純，協同式帶來的「去中心化、低耦合」優勢很吸引人，且流程本身不複雜，即使邏輯分散在各個服務裡，也不至於太難理解；但如果流程涉及五個、十個甚至更多服務，步驟之間有複雜的條件分支（例如「如果是海外訂單，多一個海關檢查步驟」），協同式會讓「整個流程到底長什麼樣子」變得極其難以掌握（沒有人能一眼看到全貌，只能一個一個服務去查它訂閱和發布了哪些事件，才能拼湊出完整的流程），這種情況下，編排式把邏輯集中在一個地方，雖然引入了一定程度的中心化耦合，但換來的「流程清晰、易於理解和除錯」的價值，通常更值得。實務上，很多團隊也會採用**混合方式**——核心的、複雜的業務流程用編排式（獲得清晰的流程視圖），而一些相對獨立、簡單的周邊反應（例如「訂單完成後，順便通知行銷系統統計數據」這種不影響核心流程正確性的旁支邏輯）用協同式（讓行銷系統自己訂閱事件，不需要驚動核心的編排器）。

## 面試回答方式

先用「下單」這個具體場景，分別講清楚編排式（中心化編排器主動依序呼叫各服務、失敗時依序觸發補償）和協同式（去中心化，每個服務完成後發布事件、下一個服務訂閱並觸發、失敗時透過失敗事件觸發連鎖補償）的具體運作方式。接著點出各自的核心優缺點——編排式「流程集中、易於理解除錯，但重新引入一定程度的中心化耦合」；協同式「服務間耦合最低，但流程邏輯分散、可觀測性和除錯難度隨服務數量增加而急劇上升」。給出判斷依據——「流程涉及的服務數量和複雜度」是核心考量，簡單流程適合協同式、複雜流程適合編排式。如果能提到「混合方式」（核心流程用編排式、周邊旁支邏輯用協同式），展現你對這兩種模式的實務權衡有更靈活、更貼近真實工程決策的理解。

## 常見追問

### 協同式 Saga 「可觀測性差、難以看到流程全貌」這個問題，有沒有辦法緩解，而不必完全放棄協同式改用編排式?

**核心答案**：常見的緩解方式包括：**（1）分散式追蹤（Distributed Tracing，見 [[020-distributed-tracing.md]]）**——透過在每個事件裡攜帶一個共同的「追蹤 ID（Trace ID）」，串聯起一整條由多個服務的事件觸發鏈組成的完整鏈路，即使邏輯分散在各個服務裡，依然能透過追蹤系統的視覺化介面，重建出「這一次特定的下單流程，實際上經過了哪些服務、哪些步驟、各自花了多少時間」的完整視圖；**（2）事件溯源與集中式事件日誌**——把所有服務發布過的事件，統一記錄到一個集中的、可查詢的事件日誌裡(例如利用 Kafka 這類訊息佇列本身具備的持久化特性)，即使各服務的處理邏輯是分散的，事後依然可以透過查詢這個集中的事件日誌，重建出完整的流程歷史；**（3）維護一份文件化的「事件流程圖」**，雖然不是程式碼層面的強制機制，但團隊可以人工維護一份清楚標示「哪個事件會觸發哪些服務的哪些反應」的架構文件，作為輔助理解的參考資料，只是這種方式需要持續人工維護，容易隨著系統演進而過時。

**詳細解析**：這題探討「在不放棄協同式帶來的低耦合優勢的前提下，怎麼緩解它最大的痛點(可觀測性差)」，考察是否理解「架構模式的選擇，不是非黑即白的二選一，很多痛點可以透過額外的工具和實踐來緩解，而不必因為某個缺點就完全放棄一個模式的其他優點」。分散式追蹤是目前業界最主流、也最有效的緩解手段——它的核心思路是，即使協同式 Saga 的「業務邏輯」確實分散在各個服務裡（這件事本身沒有改變)，但可以透過在「基礎設施/可觀測性」這個層面，額外注入一個橫跨所有服務的「關聯資訊」（Trace ID)，讓原本各自獨立、看似不相關的服務呼叫和事件處理記錄，能夠被追蹤系統根據這個共同的 ID 串聯起來，事後（甚至即時）在一個集中的追蹤系統介面裡，重建出「這一次特定的業務流程，實際上跨越了哪些服務、每個環節花了多少時間、哪個環節出了問題」的完整視圖，某種程度上是「用可觀測性工具，彌補了協同式架構本身『沒有一個地方能看到全貌』的先天缺陷」，讓開發者在需要除錯或理解特定一次流程執行狀況時，依然能有一個相對集中、視覺化的入口，而不需要真的手動去逐一翻閱每個服務各自的日誌，拼湊出完整的故事。集中式的事件日誌則從另一個角度提供類似的價值——因為協同式 Saga 本身高度依賴訊息佇列（事件的發布和訂閱），而許多訊息佇列（尤其是 Kafka）本身就具備把所有事件持久化保存一段時間的能力，這意味著「這個完整流程，曾經發生過哪些事件」這件事，其實已經自然地被記錄在訊息佇列裡了，只是需要額外的工具或介面，讓開發者能方便地依照某個追蹤 ID 或業務識別碼（如訂單 ID），查詢並重建出「這個特定訂單的完整事件歷史」，這某種程度上也是「利用既有的基礎設施能力（訊息佇列的持久化特性），彌補架構模式本身的可觀測性缺陷」。理解「協同式 Saga 的可觀測性痛點，主要透過『在基礎設施層面額外投入可觀測性工具(分散式追蹤、集中式事件查詢)』來緩解，而不是只能透過『放棄協同式、改用編排式』這種架構層面的根本改變」，展現你理解架構模式的選擇和可觀測性工具的投入，是可以相輔相成、獨立於彼此進行優化的兩個維度。

**面試回答方式**：給出核心緩解手段——「分散式追蹤，透過共同的 Trace ID 串聯起分散在各服務的事件觸發鏈，在追蹤系統的視覺化介面重建出完整流程視圖」。補充「集中式事件日誌」——「利用訊息佇列(如Kafka)本身的持久化特性，讓所有事件自然地被記錄下來，搭配查詢工具依照業務ID重建完整的事件歷史」。點出核心思路——「這些是在基礎設施/可觀測性層面額外投入工具，來彌補協同式架構本身『沒有一個地方能看到全貌』的先天缺陷，而不必因為這個痛點就完全放棄協同式帶來的低耦合優勢」。展現你理解架構模式選擇和可觀測性投入是兩個可以相輔相成、獨立優化的維度。

### 編排式 Saga 的「編排器」本身，是不是也需要考慮高可用性?如果編排器在流程執行到一半時當機了，會發生什麼事?

**核心答案**：是的，編排器本身**必須**被設計成具備高可用性和故障恢復能力，因為它是整個 Saga 流程的「大腦」——如果編排器在「已經呼叫了訂單服務建立訂單、正準備呼叫庫存服務扣庫存」的當下當機，重啟後的編排器，**必須能夠知道「這個特定的 Saga 流程，目前執行到了哪一步」**，才能正確地從中斷的地方繼續（而不是從頭重新開始，導致訂單被重複建立；也不是完全遺忘這個未完成的流程，導致它永遠卡在半完成的狀態）。實作上，編排器需要把「每一個 Saga 流程實例目前的執行狀態(目前完成到第幾步、每一步的結果是什麼)」**持久化到資料庫**，而不是只存在編排器的記憶體裡，這樣一來，即使編排器本身當機重啟（或者用多個編排器實例做水平擴展（Horizontal Scaling）、負載平衡（Load Balancing）），任何一個編排器實例，都能透過查詢這份持久化的狀態記錄，知道「這個流程目前執行到哪一步、接下來該做什麼」，從而正確地接續執行或觸發補償。

**詳細解析**：這題把「編排式 Saga 依賴一個中心化編排器」這個設計特點，延伸到「這個編排器本身要怎麼被正確、可靠地實作，才不會自己成為整個系統新的單點故障或不可靠環節」這個必須認真面對的實務問題。編排式 Saga 相較於協同式，一個經常被提及的缺點是「引入了中心化」，但這個「中心化」如果沒有被妥善地設計成高可用，反而會讓整個系統的可靠性，完全繫於這一個編排器元件的健康與否，如果編排器本身脆弱、容易當機、且當機後無法正確恢復，它反而成為比拆分之前的單體應用更嚴重的單點故障——因為現在，「所有」透過這個編排器執行的業務流程，都依賴這一個元件的持續正常運作。要讓編排器具備真正的高可用性和故障恢復能力，核心原則是——**編排器本身不應該是「有狀態」的（Stateless），它所管理的每一個 Saga 流程實例的執行狀態，必須被持久化到一個外部的、可靠的儲存(通常就是編排器自己的資料庫)，而不是只存在編排器程序的記憶體裡**——這樣一來，編排器程序本身變得可以隨意重啟、也可以水平擴展成多個實例（因為任何一個實例，只要能查詢到同一份持久化的狀態記錄，就能正確地知道並接續任何一個 Saga 流程的執行進度，不需要依賴「一定要是原本啟動這個流程的那個編排器程序才能繼續處理」這種脆弱的假設）。具體實作上，通常會為每一個 Saga 流程實例，維護一筆記錄(例如一張資料表，欄位包含「這個 Saga 實例的唯一 ID」、「目前執行到第幾個步驟」、「每個步驟目前的狀態(未開始/進行中/已完成/失敗)」)，每完成一個步驟（呼叫某個服務成功），就更新這筆記錄的狀態並持久化；如果編排器當機重啟，它（或者任何其他健康的編排器實例）可以掃描資料庫裡「還在進行中、但可能因為當機而卡住」的 Saga 實例記錄，判斷「這個實例上次執行到哪一步、那一步是否真的成功完成了(可能需要額外去確認，因為當機的時間點，也可能剛好是『呼叫某個服務的請求已經送出，但還沒收到回應』的曖昧時刻，這裡又回到了前面討論過的冪等性（Idempotency）設計的重要性——重新呼叫這一步時，如果這一步的操作本身具備冪等性，即使不確定上次是否真的成功，重新呼叫一次也不會造成錯誤的重複執行)，據此決定接下來是要繼續往下一步、還是要觸發補償」，正確地從中斷的地方恢復整個流程的執行。理解「編排式 Saga 的編排器，必須被設計成無狀態、且把每個流程實例的執行進度持久化到外部儲存，才能真正具備高可用性，否則編排器本身反而可能成為一個比原本單體應用更嚴重的單點故障」，展現你理解「引入一個中心化元件」這個架構決策，必須同時伴隨「這個中心化元件本身的高可用設計」這個配套責任，不能只享受中心化帶來的清晰視圖優勢，卻忽略了它同時帶來的可靠性責任。

**面試回答方式**：先肯定「是的，編排器本身必須具備高可用性，否則它會成為比單體應用更嚴重的單點故障」。給出核心設計原則——「編排器應該是無狀態的，每個 Saga 流程實例的執行狀態(目前完成到第幾步)必須持久化到資料庫，而不是只存在編排器的記憶體裡」。解釋恢復機制——「編排器當機重啟後(或任何健康的編排器實例)，透過查詢持久化的狀態記錄，就能知道每個流程目前執行到哪一步，正確地接續執行或觸發補償，而不是從頭重來或永遠遺忘這個未完成的流程」。可以延伸提到「重新呼叫上次可能已經執行、但結果不確定的那一步時，依賴這一步本身具備冪等性，即使重複呼叫也不會造成錯誤」。展現你理解「引入中心化編排器」這個決策必須同時配套「這個元件本身的高可用設計」這個責任。

### 如果 Saga 流程中的某一步，呼叫了一個第三方系統(例如呼叫外部的物流公司 API 安排出貨)，而這個第三方系統根本不提供「補償/取消」的 API，這種情況要怎麼設計 Saga 流程?

**核心答案**：如果某個步驟的操作，本質上**無法被撤銷**（第三方系統不提供取消機制，或者操作一旦執行，實質上的影響已經無法收回，例如物流已經開始實體的攬收動作），常見的設計策略是**把這類「不可逆的步驟」，安排在整個 Saga 流程的最後（或盡量靠後）的位置**——因為 Saga 流程的補償邏輯，是「依照已完成步驟的相反順序，依序執行補償」，如果一個不可逆的步驟排在最後，代表「當這一步真正被執行時，前面所有其他步驟都已經確定成功了」，理論上不太需要再對這一步本身做補償（因為它是流程真正意義上的終點，一旦走到這一步，通常代表整個業務流程已經接近完全成功）；如果因為業務邏輯的必然性，不可逆的步驟無法排到最後，另一種思路是**在呼叫這個不可逆操作之前，盡可能地先完成所有「相對容易補償撤銷」的步驟並確認它們都成功**，把「執行這個不可逆操作」當作整個 Saga 裡「風險最集中、最後才觸發」的關鍵環節，並且對於萬一之後真的需要「處理」這個已經無法撤銷的操作的情況，設計**人工介入的補救流程**（例如觸發客服人員的工單，由人工聯繫物流公司協調退貨或取消，而非期待系統能自動化地完美解決）。

**詳細解析**：這題觸及 Saga 補償機制的一個根本限制——**不是所有操作都能被程式邏輯自動化地撤銷**，考察是否能理解並提出面對這種「補償力所不及」的情況時，務實的架構設計思路。前面追問已經討論過「補償不總是簡單的反向操作」這個原則，這題進一步深入到「如果某個操作，連『語意上的抵銷』都做不到（第三方系統完全不提供任何形式的取消或撤銷機制，或者操作造成的物理世界影響已經不可逆轉）」這種更極端的情況。第一個策略「把不可逆步驟盡量排在流程最後」，其背後的邏輯是——Saga 流程的設計，本質上是在管理「執行到目前這一步為止，前面每一步都已經成功、但後面的步驟還不確定是否會成功」這種漸進式推進的風險，如果把「風險最高、一旦執行就無法回頭」的步驟，安排在盡可能靠後的位置，代表「當系統真正要去執行這個不可逆操作時，前面所有可能失敗、且相對容易處理(補償)的環節，都已經確定順利完成了」，這大幅降低了「執行了這個不可逆操作之後，卻發現流程的其他部分其實失敗了、需要回頭撤銷這個不可逆操作」這種最糟糕情況發生的機率——雖然沒辦法完全消除這種風險（例如即使前面步驟都成功，觸發物流出貨這個不可逆步驟本身也可能因為某些原因需要事後處理），但透過調整執行順序，把最不希望發生「需要撤銷但撤銷不了」情況的環節，放在整個流程「最有把握、最後確認」的位置，是一種務實地降低風險機率(雖然不是徹底消除)的設計手法。當這種順序調整因為業務上的必然依賴關係而無法做到時（例如「必須先扣款，才能觸發物流出貨，但物流出貨的補償能力有限」這種順序在業務邏輯上是無法顛倒的），就必須誠實地承認「純軟體自動化的補償機制，在這裡是有極限的」，轉而設計一套**人工介入的補救機制**——當系統偵測到「已經觸發了一個不可逆操作，但後續(或並行)的其他部分卻失敗了，導致整體流程處於一個異常、無法用自動化補償完全解決的狀態」，正確的做法不是假裝系統能夠優雅地自動解決一切，而是誠實地把這個異常情況，轉化成一個「需要人工介入處理」的工單或告警，由客服人員或維運人員，去和第三方系統(如物流公司)協調（例如聯繫要求攔截或退回已經出貨的包裹，這在現實世界中往往是可行的，只是無法透過純軟體 API 呼叫自動化完成，需要人為的溝通和協調）。理解「Saga 補償機制的能力邊界，終究受限於『這個操作在現實世界(或第三方系統的能力範圍)裡，是否真的存在某種形式的撤銷或抵銷手段』，當這個能力邊界被觸及時，成熟的系統設計不會假裝能夠純軟體自動化地解決一切，而是誠實地引入人工介入的補救流程，作為自動化補償機制的最後防線」，展現你對分散式事務（Distributed Transaction）和 Saga 模式的實務理解，已經超越了「理論上補償永遠能順利完成」這種過於理想化的假設，觸及到真實工程系統必須面對的、軟體自動化力所不及的現實限制。

**面試回答方式**：先承認限制——「有些操作根本無法被程式化地撤銷，補償機制在這裡是有極限的」。給出第一個策略——「盡量把這類不可逆的步驟排在 Saga 流程最靠後的位置，讓它執行時，前面所有相對容易補償的步驟都已經確定成功，降低『執行了不可逆操作卻發現需要撤銷』的風險機率」。給出第二個策略——「如果業務邏輯的順序無法調整，就要誠實地設計人工介入的補救流程(如觸發客服工單，由人工聯繫第三方協調處理)，而不是假裝系統能自動化地完美解決一切」。展現你理解 Saga 補償機制有其能力邊界，成熟的系統設計需要在自動化能力的極限處，務實地引入人工介入作為最後防線，而非過度理想化地假設一切都能被程式自動撤銷。
