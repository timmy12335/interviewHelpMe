# 題目

哪些 API 變更是相容的、哪些是破壞性的？怎麼在不停機的情況下演進契約？

## 核心答案

判斷相容性的原則是「舊的客戶端還能不能正常運作」與「舊的伺服器還能不能處理新的請求」——**兩個方向都要考慮**，因為部署期間新舊版本會並存。

**向後相容的變更**（安全）：**新增可選的請求欄位**、**新增回應欄位**、**新增一個新的端點**、**放寬輸入的驗證**、**新增列舉值**（但只有在客戶端會忽略未知值的前提下）。

**破壞性的變更**：**移除或重新命名欄位**、**改變欄位的型別或語意**、**把可選欄位變成必填**、**收緊驗證規則**、**改變預設值**、**改變錯誤碼的含義**。

最容易被誤判的是「新增列舉值」與「改變預設值」。前者在客戶端用 switch 窮舉處理時會炸；後者不改變任何簽章，**但改變了行為**——而那是最難被發現的一類破壞。

**演進的標準做法是 expand-contract**：**先擴充**（同時支援新舊兩種形式）、**再遷移**（讓所有客戶端改用新的）、**最後收縮**（移除舊的）——三個階段各自獨立部署，任何一步都可回退。

## 詳細解析

「改變預設值」的危險值得展開，因為它不會被任何相容性檢查工具抓到。一個 `pageSize` 的預設從 20 改成 50，**API 的形狀完全沒變**，但所有沒有明確指定的客戶端行為都改變了——可能造成效能問題、也可能讓依賴「一頁 20 筆」假設的邏輯出錯。同樣的問題出現在排序的預設順序、逾時的預設值、以及任何「不指定時會怎樣」的行為上。所以預設值應該被當成契約的一部分明確記錄，改動它要按破壞性變更處理。

**expand-contract 的關鍵在「第二步的可觀測性」**。從「擴充」到「收縮」之間，必須知道還有沒有客戶端在用舊的形式——否則移除的時機只能靠猜。做法是為舊的欄位或端點加上使用統計（記錄呼叫者的識別、頻率），**並在確認歸零後才移除**。沒有這個統計的話，expand-contract 的第三步永遠不敢做，於是系統累積了大量「不敢刪的舊東西」——而那正是很多 API 變得臃腫的原因。

「舊伺服器處理新請求」這個方向常被忽略。滾動部署期間，新版本的客戶端可能打到舊版本的伺服器（負載平衡不會等所有實例都更新完）。**所以「客戶端先部署」是危險的**——正確的順序通常是先部署伺服器（讓它同時支援新舊），再部署客戶端。而如果客戶端與伺服器由不同團隊在不同時間部署，這個順序約束必須被明確溝通並記錄在變更說明裡。

契約的形式決定了驗證的可行性。用 OpenAPI 或 Protobuf 明確定義契約，**就能用工具自動檢查相容性**（`buf breaking`、openapi-diff）——把「這個變更會不會破壞客戶端」從人工判斷變成 CI 的一個檢查。這是契約優先設計最實質的收益之一，而它需要契約真的是權威（而非從程式碼生成的、事後才有的文件）。

## 面試回答方式

先給判斷原則——「舊客戶端還能不能運作」與「舊伺服器還能不能處理新請求」兩個方向都要考慮，因為部署期間新舊並存。列出相容與破壞性的變更，並指出最容易被誤判的是「新增列舉值」與「改變預設值」——後者不改變任何簽章但改變了行為，是最難被發現的一類破壞。給演進的標準做法 **expand-contract** 與三階段獨立部署可回退的性質。加分點有三個：改變預設值不會被任何相容性工具抓到，所以預設值應該被當成契約的一部分明確記錄；**expand-contract 的關鍵在第二步的可觀測性**——沒有使用統計就永遠不敢做第三步，**那正是很多 API 變臃腫的原因**；以及「舊伺服器處理新請求」常被忽略，滾動部署時正確的順序是**先部署伺服器再部署客戶端**。

## 講稿

判斷相容性的原則是兩個方向都要看。舊的客戶端還能不能正常運作，還有舊的伺服器還能不能處理新的請求。因為部署期間新舊版本會並存。

向後相容的變更是新增可選的請求欄位、新增回應欄位、新增端點、放寬驗證。破壞性的是移除或重新命名欄位、改變型別或語意、把可選變必填、收緊驗證。

最容易被誤判的有兩個。新增列舉值，在客戶端用窮舉處理的時候會炸。還有改變預設值，它不改變任何簽章但改變了行為，而那是最難被發現的一類破壞。一個分頁大小的預設從二十改成五十，API 的形狀完全沒變，但所有沒有明確指定的客戶端行為都變了。所以預設值應該被當成契約的一部分明確記錄。

演進的標準做法是先擴充、再遷移、最後收縮。三個階段各自獨立部署，任何一步都可以回退。

關鍵在第二步的可觀測性。從擴充到收縮之間，必須知道還有沒有客戶端在用舊的形式，否則移除的時機只能靠猜。做法是為舊的欄位加上使用統計，確認歸零之後才移除。沒有這個統計的話，第三步永遠不敢做，於是系統累積大量不敢刪的舊東西。

## 常見追問

### 版本化該用哪種方式？

**核心答案**：三種常見形式各有取捨。**URL 路徑**（`/v1/users`）——最明顯、最容易路由與快取，但它讓「版本」成為資源識別的一部分（同一個資源有兩個 URL，語意上不夠純粹）。**標頭**（`Accept: application/vnd.example.v2+json`）——語意上更正確，但不易在瀏覽器或 curl 中測試、也不易做基於路徑的路由。**查詢參數**（`?version=2`）——簡單但容易被遺漏且不利於快取。實務上路徑版本最常見，因為它的可操作性最好。

**詳細解析**：更重要的判斷是「該不該發新版本」。每個版本都要維護、測試、與最終棄用，**成本是持續的**；而多數變更其實可以用相容的方式做（新增欄位、放寬驗證）。所以「發 v2」應該是最後手段，而不是每次改動的預設反應。 一個實用的原則是「只在無法用相容方式表達時才升版本」——而那通常意味著資源的模型本身改變了（例如從「一個使用者一個地址」變成「一個使用者多個地址」）。另外要注意「版本」與「棄用」是兩件事：可以在同一個版本內棄用某個欄位（標記為 deprecated 並持續統計使用量），**不必為了棄用而升版本**。很多 API 的版本膨脹，是因為把「棄用」誤當成「需要新版本」。

**面試回答方式**：給三種形式與取捨，並指出實務上路徑版本最常見因為可操作性最好。真正的重點是提出更重要的判斷：**該不該發新版本**——每個版本的維護成本是持續的，而多數變更可以用相容的方式做，**所以「發 v2」應該是最後手段**。給出原則（只在無法用相容方式表達時才升版本）並澄清**「版本」與「棄用」是兩件事**——可以在同一版本內棄用欄位，很多 API 的版本膨脹是把棄用誤當成需要新版本。

### 內部服務之間的 API 需要這麼嚴格嗎？

**核心答案**：**需要，但形式可以不同**。內部服務的優勢是「你能找到所有的呼叫方」——所以理論上可以協調同步升級。但實務上那個協調的成本比想像中高（跨團隊、跨時區、各自的發布節奏），而且一旦服務數量超過十幾個，同步升級就不可行了。所以相容性的紀律在內部同樣需要，只是可以省掉版本化的儀式（用相容的演進取代顯式的版本）。

**詳細解析**：內部 API 特有的風險是「以為可以協調所以不做相容」。一個團隊改了回應的欄位名並通知了「所有已知的呼叫方」，但漏掉了一個很少呼叫的批次作業——那個作業在下次執行時失敗，而可能幾天後才被發現。所以「能找到所有呼叫方」這個假設本身需要被驗證，而驗證的方式是**在 API 層記錄呼叫者的識別**（透過認證的服務身分或一個明確的 `User-Agent`）。有了這個資料，「誰在用這個端點」就從一個靠記憶回答的問題，變成一個可以查詢的事實。 這個投資的成本很低（一個標頭加上日誌），而它讓所有的演進決定都建立在事實而非假設上。

**面試回答方式**：給明確立場——**需要但形式可以不同**，內部可以省掉版本化的儀式但相容性的紀律同樣需要，因為協調同步升級的成本比想像中高、服務超過十幾個就不可行。真正的加分點是點出內部 API 特有的風險：**以為可以協調所以不做相容**，而通知「所有已知的呼叫方」時漏掉了很少呼叫的批次作業。給出解法：**在 API 層記錄呼叫者的識別**，讓「誰在用這個端點」從靠記憶回答變成可查詢的事實——成本很低而它讓所有演進決定建立在事實而非假設上。

### 契約測試（contract testing）解決什麼問題？

**核心答案**：解決「整合測試太慢太脆弱，但單元測試又測不到整合」這個中間地帶。消費者驅動的契約測試（Pact 是代表）讓消費者定義「我期望這個 API 長什麼樣、回傳什麼」，生成一份契約；提供者則用那份契約驗證自己的實作。於是雙方不需要同時運行就能驗證相容性——消費者的測試用 mock、提供者的測試用契約重放。

**詳細解析**：它最實質的價值是「破壞性變更在 CI 就被發現」——提供者改了回應格式，它的 CI 跑消費者的契約時就失敗了，而不是等到部署後消費者出錯。代價是需要維護契約與雙方的測試流程，而且契約只涵蓋「消費者實際使用的部分」（那既是優點——不會為沒人用的欄位維護測試，也是限制——新的消費者可能用到未被契約涵蓋的部分）。實務上的採用障礙常常是組織而非技術：它需要兩個團隊都投入並維護，而如果其中一方不配合，整套機制就失效。所以它在「同一個組織內、有共同的 CI 基礎設施」的環境下最容易成功，跨組織的 API 則較難。

**面試回答方式**：給定位——解決「整合測試太慢太脆弱、單元測試又測不到整合」的中間地帶，並說明消費者驅動的機制（消費者定義期望生成契約、提供者用它驗證），**於是雙方不需要同時運行**。給最實質的價值：破壞性變更在 CI 就被發現而非部署後。誠實給出限制（契約只涵蓋消費者實際用的部分）與採用障礙常常是組織而非技術——需要雙方投入，一方不配合整套就失效。
