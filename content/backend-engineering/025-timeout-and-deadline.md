# 題目

微服務的逾時該怎麼設？為什麼「每一層各自設一個逾時」是不夠的？

## 核心答案

每一層各自設逾時的問題是**它們互相不知道對方**。A 呼叫 B 設 3 秒、B 呼叫 C 設 5 秒——**B 還在等 C 的時候，A 已經放棄了**；於是 B 與 C 繼續花資源處理一個**沒有人在等的請求**。**這些「幽靈工作」在過載時會持續消耗資源，讓系統更難恢復**。

正確的做法是**截止時間傳遞（deadline propagation）**：**在入口設定一個總預算**（例如 2 秒），**每一層把「剩餘的時間」傳給下一層**（透過 gRPC 的 deadline 或 HTTP 的自訂標頭），下一層據此設定自己的逾時。**於是整條鏈路共享同一個截止時間，上游放棄時下游也會停止。**

**逾時值的設定原則是「基於實際的延遲分布」而非猜測**：取下游的 P99 或 P999 加上一點餘裕，**而不是「設個 30 秒總不會錯」**——過長的逾時等於沒有逾時，它讓故障時的資源被長時間佔用。

**還有一條容易被忽略的紀律：逾時必須小於上游的逾時**，否則你的逾時永遠不會觸發。

## 詳細解析

**「幽靈工作」在過載時的危害值得展開**。系統變慢 → 上游逾時放棄 → 但下游還在處理 → 上游重試 → 下游同時處理原本的與重試的 → **負載變成兩倍或三倍** → 更慢 → 更多逾時與重試。**這是一個正回饋，而它是很多「服務一旦過載就無法自行恢復」的根因**。截止時間傳遞打斷了這個回饋：**下游知道請求已經沒有意義，可以直接放棄並釋放資源**。

**逾時的層次要完整**。一次 HTTP 呼叫至少有四個逾時：**連線逾時**（建立 TCP 連線）、**TLS 握手逾時**、**寫入逾時**（送出請求）、**讀取逾時**（等待回應）。**只設「讀取逾時」是常見的不完整**——如果下游的連線佇列滿了，連線逾時才是會觸發的那一個。**而且還有「整體逾時」**（涵蓋重試在內的總時間），**它與單次呼叫的逾時是不同的東西**——設了單次 3 秒加上重試 3 次，最壞情況是 9 秒加上退避的時間。

**逾時與重試必須一起設計**。逾時觸發後要不要重試？重試幾次？**而總的時間預算必須涵蓋所有重試**——否則「逾時 3 秒、重試 3 次」實際上是 10 秒以上，而上游可能只給了 5 秒。**成熟的做法是把重試也納入截止時間的計算**：每次重試前檢查「剩餘時間夠不夠再試一次」，不夠就直接放棄。

**逾時的設定應該是可觀測的**。記錄「因逾時失敗的比例」與「實際耗時的分布」，**兩者一起看才能判斷逾時值合不合理**：逾時率高但耗時分布正常，表示逾時設得太緊；耗時分布的尾部很長，表示下游有問題而不是逾時的問題。**沒有這些資料的話，調整逾時值只是猜測。**

## 面試回答方式

先指出**每一層各自設逾時的問題是它們互相不知道對方**，用「A 設 3 秒、B 設 5 秒」的具體例子說明**幽靈工作**的產生。給出正確做法**截止時間傳遞**（入口設總預算、每層傳剩餘時間、整條鏈路共享同一個截止時間）。給逾時值的設定原則（**基於實際延遲分布而非猜測**，而**過長的逾時等於沒有逾時**）與一條紀律（**逾時必須小於上游的逾時**）。加分點有三個：**幽靈工作在過載時形成正回饋**——這是「服務一旦過載就無法自行恢復」的根因，而截止時間傳遞打斷了它；**逾時的層次要完整**（連線、TLS、寫入、讀取，而**只設讀取逾時是常見的不完整**）；以及**重試必須納入總預算**——「逾時 3 秒重試 3 次」實際上是 10 秒以上。

## 講稿

每一層各自設逾時的問題是它們互相不知道對方。A 呼叫 B 設三秒、B 呼叫 C 設五秒，B 還在等 C 的時候 A 已經放棄了，於是 B 跟 C 繼續花資源處理一個沒有人在等的請求。

這些幽靈工作在過載時的危害很具體。系統變慢、上游逾時放棄、但下游還在處理、上游重試、下游同時處理原本的跟重試的，負載變成兩三倍，然後更慢。這是一個正回饋，也是很多服務一旦過載就無法自行恢復的根因。

正確的做法是截止時間傳遞。在入口設定一個總預算，每一層把剩餘的時間傳給下一層，下一層據此設定自己的逾時。於是整條鏈路共享同一個截止時間，上游放棄的時候下游也會停止。

逾時值我會基於實際的延遲分布來設，取下游的 P99 加一點餘裕，而不是設個三十秒總不會錯。過長的逾時等於沒有逾時，它讓故障時的資源被長時間佔用。

還有兩點。逾時的層次要完整，連線、握手、寫入、讀取都要設，只設讀取逾時是常見的不完整。還有重試必須納入總預算，逾時三秒重試三次，實際上會超過十秒。

## 常見追問

### 怎麼在 HTTP 上實作截止時間傳遞？

**核心答案**：**用一個標準化的自訂標頭傳遞剩餘時間或絕對的截止時刻**。常見的做法是傳絕對時刻（例如 `X-Request-Deadline: 2024-01-15T10:30:45.123Z`）——**它不受各節點處理時間的影響**，但**要求各節點的時鐘同步**。傳剩餘毫秒數（`X-Request-Timeout-Ms: 1500`）則不依賴時鐘，**但每一跳都要扣掉自己的處理時間，累積誤差較大**。**gRPC 內建了 deadline 機制**（用相對時間傳遞並在每一跳重新計算），所以用 gRPC 時這件事是免費的。

**詳細解析**：**實作上的關鍵是「讓它自動而非靠每個人記得」**——把截止時間的讀取、扣減、與傳遞放進 HTTP 客戶端的攔截器或框架的中介軟體裡，**讓業務程式碼完全不必知道它的存在**。**如果需要每個呼叫點手動處理，那它遲早會有遺漏，而一個遺漏就打斷了整條鏈路的傳遞。** **這與追蹤上下文的傳遞是完全相同的問題**——兩者都應該由同一層基礎設施處理（Micrometer 的 Observation、OpenTelemetry 的 context propagation 都提供了掛載點）。**認出「這是同一個問題」能避免重複造兩套機制。**

**面試回答方式**：給兩種傳遞形式（絕對時刻不受處理時間影響但需要時鐘同步、相對毫秒不依賴時鐘但累積誤差）與 gRPC 內建的支援。真正的重點是實作關鍵：**讓它自動而非靠每個人記得**——放進客戶端攔截器或框架中介軟體，**一個遺漏就打斷整條鏈路**。收在洞見：**這與追蹤上下文的傳遞是完全相同的問題**，應該由同一層基礎設施處理，認出這點能避免重複造兩套機制。

### 逾時之後資源真的被釋放了嗎？

**核心答案**：**不一定，這是最容易被誤解的一點**。多數 HTTP 客戶端的逾時只是「不再等待回應」——**它不會通知伺服器端停止處理**。所以伺服器仍然在跑那個請求、仍然佔著執行緒與連線、仍然在查資料庫。**真正的釋放需要伺服器端也知道截止時間並主動放棄**——這正是截止時間傳遞的價值，它讓「取消」能夠傳到真正做事的那一端。

**詳細解析**：**在 Java 上，取消一個正在執行的請求需要協作**——執行緒不能被強制停止，所以業務程式碼必須在適當的位置檢查「是否已經超過截止時間」並主動退出。**這在框架層很難完全自動化**（框架不知道你的迴圈或迴圈裡的哪一步是安全的中止點），**所以長時間的操作應該自己加上檢查**。**Go 的 context 與 gRPC 的 deadline 在這方面設計得更好**——`ctx.Done()` 提供了一個統一的取消訊號，而標準庫的 IO 操作都會回應它。**這是一個「語言與框架的設計影響了工程實踐可行性」的例子**：在有統一取消機制的環境裡，「逾時真的釋放資源」是預設行為；在沒有的環境裡，它需要每個人記得處理。

**面試回答方式**：明確指出**逾時不一定釋放資源**——多數 HTTP 客戶端的逾時只是不再等待，**不會通知伺服器停止**。給出真正釋放的條件（伺服器端也知道截止時間並主動放棄）並指出**這正是截止時間傳遞的價值**。加分點是說明 **Java 上取消需要協作**（執行緒不能強制停止、業務程式碼要主動檢查），而 **Go 的 context 與 gRPC 的 deadline 設計得更好**。收在觀點：**語言與框架的設計影響了工程實踐的可行性**。

### 逾時值應該設在哪一層？

**核心答案**：**每一層都要有，但角色不同**。**應用層的呼叫逾時**（HTTP 客戶端）是最直接的一層，它保護的是呼叫方的執行緒。**基礎設施層的逾時**（服務網格的 sidecar、API 閘道、負載平衡器）提供了一個**不依賴應用程式碼正確性的保底**——即使某個服務忘了設逾時，網格層仍會切斷。**伺服器端的處理逾時**（例如 Tomcat 的 `connectionTimeout`、或應用自己的截止時間檢查）保護的是被呼叫方。

**詳細解析**：**「基礎設施層的保底」是服務網格最實質的價值之一**。應用層的逾時依賴每個服務都正確設定，**而在幾十個服務、多種語言、多個團隊的環境裡，那個假設幾乎必然會被打破**。網格層的逾時是統一配置、集中管理、且不需要改應用程式碼的。**代價是它的粒度較粗**（通常是按服務或按路由，難以做到按請求類型的差異化），**所以它是保底而非取代**。**這個「應用層做精確控制、基礎設施層做統一保底」的分層，在限流、重試、與熔斷上同樣適用**——認出這個模式，就能理解服務網格提供的能力與應用層的關係不是取代而是互補。

**面試回答方式**：給三層（應用呼叫逾時、基礎設施保底、伺服器端處理逾時）與各自保護的對象。重點展開**基礎設施層的保底是服務網格最實質的價值之一**——應用層的逾時依賴每個服務都正確設定，**而在多服務多語言多團隊的環境裡那個假設必然被打破**。誠實給出它的限制（粒度較粗、是保底而非取代）。收在通用分層：**應用層做精確控制、基礎設施層做統一保底**，這在限流、重試、熔斷上同樣適用。
