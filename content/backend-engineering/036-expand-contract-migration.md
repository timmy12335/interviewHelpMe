# 題目

expand-contract（parallel change）是什麼？它能用在哪些地方？

## 核心答案

它是一個把破壞性變更拆成一連串相容變更的通用模式，分三個階段：**擴充**（新增新的形式，舊的仍然可用——**此時系統同時支援兩種**）、**遷移**（把所有使用者從舊的切到新的）、**收縮**（確認沒有使用者之後移除舊的）。

核心價值是「每個階段都是可獨立部署且可回退的」——而破壞性變更一次做完的話，回退意味著要撤銷所有的東西，而那通常做不到。

**它的適用範圍遠不只資料庫 schema**：**API 的欄位與端點**（新增新欄位、雙寫、遷移客戶端、移除舊欄位）、**函式或方法的簽章**（新增多載、遷移呼叫方、移除舊的）、**設定的鍵名**（同時支援新舊鍵、遷移、移除）、**訊息的格式**（生產者同時發新舊、消費者遷移、停止發舊的）、**以及服務的拆分或合併**。

認出「這是同一個模式」的價值在於：遇到任何破壞性變更時，都知道有一條安全的路徑，而不必在「一次做完的風險」與「不做」之間二選一。

## 詳細解析

「遷移階段的可觀測性」是這個模式能否完成的關鍵。從擴充到收縮之間，必須知道還有沒有人在用舊的——否則移除的時機只能靠猜，**而猜錯的代價是生產故障**。所以擴充階段就應該加上使用統計（舊路徑被呼叫的次數、呼叫者的身分），並在收縮之前確認它歸零並維持了一段足夠長的時間（涵蓋所有的業務週期，例如月結或年度作業）。沒有這個統計的話，第三階段永遠不敢做——於是系統累積了大量「不敢刪的舊東西」，而那正是很多系統變得臃腫難以維護的原因。

「先讓它壞在可觀測的地方」是一個有用的過渡技巧。在真的刪除之前，先讓舊的路徑產生一個明顯的警告或錯誤（記一筆 WARN 日誌加上呼叫者資訊、或者在非生產環境直接拋例外）。這比靜默地等統計歸零更快也更確定——因為統計可能因為取樣或某些路徑沒有埋點而遺漏，而一個明確的錯誤會被立刻注意到。

這個模式的成本是「同時維護兩套」的期間。那段期間程式碼裡有雙份的邏輯、測試要覆蓋兩條路徑、而且如果遷移拖得太久，可能會忘記為什麼有兩套。所以每個 expand-contract 都應該有一個明確的完成期限與負責人——沒有期限的遷移會變成永久的雙軌，而那比原本的問題更糟。

它與「大爆炸式重構」的對比很有教育意義。大爆炸式的做法是「在一個分支上改完所有東西再合併」——看起來乾淨，但合併時的衝突、無法漸進驗證、以及回退的困難，讓它在大型系統上幾乎必然失敗。expand-contract 則讓每一步都在主線上、都能被驗證、也都能被回退——代價是總的步驟更多、耗時更長。這正是「持續整合」與「長命分支」之爭的具體形式，而業界的共識已經明確倒向前者。

## 面試回答方式

先給**三個階段**與核心價值：每個階段都可獨立部署且可回退，並對比破壞性變更一次做完時「回退意味著撤銷所有東西而那通常做不到」。**列出它的廣泛適用範圍**（不只 schema，還有 API、方法簽章、設定鍵、訊息格式、服務拆分）並指出**認出「這是同一個模式」的價值**。加分點有三個：遷移階段的可觀測性是能否完成的關鍵——沒有使用統計就永遠不敢做第三階段，那正是很多系統變臃腫的原因；「先讓它壞在可觀測的地方」比靜默等統計歸零更快也更確定；以及每個 expand-contract 都該有明確的完成期限與負責人——沒有期限的遷移會變成永久的雙軌，而那比原本的問題更糟。

## 講稿

它是一個把破壞性變更拆成一連串相容變更的通用模式，分三個階段。擴充是新增新的形式而舊的仍然可用，此時系統同時支援兩種。遷移是把所有使用者從舊的切到新的。收縮是確認沒有使用者之後移除舊的。

核心價值是每個階段都可以獨立部署而且可以回退。破壞性變更一次做完的話，回退意味著要撤銷所有東西，而那通常做不到。

它的適用範圍遠不只資料庫 schema。API 的欄位、方法簽章、設定鍵名、訊息格式，都可以用同一個模式。認出這一點的價值在於，遇到任何破壞性變更時都知道有一條安全的路徑。

關鍵是遷移階段的可觀測性。必須知道還有沒有人在用舊的，否則移除的時機只能靠猜。所以擴充階段就應該加上使用統計，並在收縮之前確認它歸零並維持了足夠長的時間。沒有這個統計的話，第三階段永遠不敢做，於是系統累積大量不敢刪的舊東西。

還有一個成本要說。同時維護兩套的期間，程式碼裡有雙份邏輯、測試要覆蓋兩條路徑。所以每個遷移都應該有明確的完成期限跟負責人，沒有期限的遷移會變成永久的雙軌，而那比原本的問題更糟。

## 常見追問

### 遷移拖太久怎麼辦？

**核心答案**：這是這個模式最常見的失敗模式。原因通常是：遷移的第二階段（讓所有使用者改用新的）依賴其他團隊或其他系統，而它們有自己的優先順序。**處理方式有三個**：**明確的期限與升級路徑**（超過期限就升級到管理層決定）、**降低遷移的成本**（提供自動化的工具或範例，讓對方改起來很快）、以及**主動施加壓力**（在舊路徑加上警告日誌、逐步降級舊路徑的效能或可用性——但那應該是最後手段且需要事先溝通）。

**詳細解析**：更根本的做法是「一開始就不要讓遷移依賴太多方」。如果一個變更需要十個團隊配合，**那個遷移幾乎必然會拖很久**；而如果能設計成「只需要自己這邊改」（例如在自己的服務裡做轉換層而非要求呼叫方改），完成的機率就高得多。**這是一個設計上的選擇**：**把相容的責任放在自己這邊**（多寫一層轉換）**而非推給使用者**。代價是自己多維護一層，收益是遷移能真的完成。 在有很多下游的服務上，這個交換幾乎總是划算的——因為協調十個團隊的成本遠高於維護一層轉換。

**面試回答方式**：先指出**這是最常見的失敗模式**與原因（第二階段依賴其他團隊而它們有自己的優先順序）。給三個處理方式並註明施加壓力應該是最後手段。真正的加分點是更根本的做法：一開始就不要讓遷移依賴太多方——需要十個團隊配合的遷移幾乎必然拖很久，設計成「只需要自己這邊改」（在自己的服務做轉換層）完成的機率高得多。收在交換：把相容的責任放在自己這邊而非推給使用者，在有很多下游的服務上這個交換幾乎總是划算的。

### 怎麼判斷「舊的已經沒人用了」？

**核心答案**：**用資料而非推理**。在舊路徑上加上明確的量測：**呼叫次數**（帶上呼叫者的識別——服務名、API key、或 User-Agent）、**最後一次呼叫的時間**。確認的標準是「歸零並維持了一個完整的業務週期」——而那個週期必須涵蓋最長的循環（月結、季報、年度作業）。**搜尋程式碼是不夠的**，因為動態的呼叫、外部的整合、以及報表工具都可能不在你的程式碼庫裡。

**詳細解析**：「呼叫者的識別」是這件事的關鍵，而它需要事先準備。如果 API 沒有記錄呼叫者，你只知道「還有人在用」但不知道是誰——於是無法去推動他們遷移，只能繼續等。所以「要求每個呼叫方提供身分」應該是 API 設計的基本要求（透過認證的服務身分、一個明確的 `User-Agent`、或一個 API key）。這個投資在平時看起來沒有價值，但在需要遷移或需要通知呼叫方時，它是決定性的。 同樣的道理適用於資料庫的存取——如果有外部團隊直接查你的資料庫，你完全無法知道他們用了哪些欄位，而那正是「不敢刪任何東西」的根源。所以「不要讓別人直接存取你的資料庫」除了封裝的理由，也有可演進性的理由。

**面試回答方式**：給明確的做法（用資料而非推理、記錄呼叫次數與呼叫者識別）與確認標準（歸零並維持一個完整的業務週期，涵蓋月結年度等最長循環），並指出搜尋程式碼不夠。真正的加分點是**「呼叫者的識別」需要事先準備**——沒有它就只知道還有人用而不知道是誰，於是無法推動遷移只能繼續等。收在延伸：同樣的道理適用於資料庫的直接存取——完全無法知道別人用了哪些欄位，所以「不要讓別人直接存取你的資料庫」也有可演進性的理由。

### 這個模式在單體應用內部也適用嗎？

**核心答案**：**適用，而且成本更低**。在單體內重構一個介面時，同樣可以「新增新的方法 → 遷移呼叫方 → 移除舊的」——差別是編譯器幫你找到所有呼叫方，所以第二階段快得多（IDE 的重構工具甚至能自動完成）。所以單體內部的破壞性變更可以更大膽，這正是它相對於分散式系統的一個實質優勢。

**詳細解析**：「編譯期能找到所有使用者」是單體最被低估的優勢。跨服務的變更需要協調、需要等待、需要相容期；同一個程式碼庫內的變更可以在一次提交裡完成，而編譯器保證沒有遺漏。這正是「不要過早拆分服務」這個建議的核心理由之一——在邊界還不穩定的時候，把它們放在同一個程式碼庫裡讓調整的成本低得多。反過來說，一旦拆成服務，那個邊界就變得昂貴（每次調整都是跨團隊的協調）。所以服務的邊界應該畫在「已經穩定、不太會變」的地方，而那通常需要先在單體裡演化一段時間才看得出來。這個判斷比任何微服務的技術細節都重要。

**面試回答方式**：給明確答案（適用且成本更低）與原因（編譯器幫你找到所有呼叫方，第二階段快得多），推出單體內部的破壞性變更可以更大膽。真正的加分點是把它提升成架構判斷：「編譯期能找到所有使用者」是單體最被低估的優勢，而這正是「不要過早拆分服務」的核心理由之一——邊界還不穩定時放在同一個程式碼庫讓調整成本低得多。收在結論：服務的邊界應該畫在已經穩定的地方，而那通常需要先在單體裡演化一段時間才看得出來。
