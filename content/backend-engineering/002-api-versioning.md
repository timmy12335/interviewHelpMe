# 題目

API 上線之後，業務需求變化導致介面需要修改，要怎麼做版本管理才不會破壞現有客戶端？常見的版本管理策略有哪些？

## 核心答案

API 版本管理的核心目標是「讓 API 能夠演進，同時不破壞正在使用舊版本的既有客戶端」。常見的版本表達策略有：**（1）URL 路徑版本**——如 `/v1/users`、`/v2/users`，最直觀、最容易理解，也最容易在瀏覽器直接測試；**（2）查詢參數版本**——如 `/users?version=2`，實作簡單但不夠語意化；**（3）HTTP Header 版本**——如自訂 `API-Version: 2` 標頭，或透過 `Accept` 標頭做內容協商（如 `Accept: application/vnd.myapi.v2+json`），優點是 URL 保持乾淨、資源的唯一識別碼不隨版本變化，缺點是不容易在瀏覽器網址列直接測試、除錯較不直觀。實務上更重要的原則是——**能不升版就不升版**，透過「向後相容的漸進式修改」（如新增可選欄位、新增端點）盡量避免破壞性變更，只有真正的破壞性變更（移除欄位、改變欄位語意、改變回應結構）才需要真正發一個新版本，並搭配明確的舊版本淘汰時程和溝通機制。

## 詳細解析

**三種版本表達方式的比較**：URL 路徑版本（`/v1/...`）是業界最常見、最直觀的做法，優點是版本資訊一目了然、方便直接在瀏覽器或工具測試，也方便在閘道層（API Gateway）或負載平衡器層面依照路徑做路由（把 `/v1/*` 導向舊版服務、`/v2/*` 導向新版服務）；缺點是從嚴格的 REST 語意角度看，「同一個資源不應該因為版本不同而有不同的 URI」（資源的識別碼理論上應該是穩定的），版本號出現在路徑裡某種程度上違反了這個原則。Header 版本管理（自訂標頭或透過 `Accept` 內容協商）更符合「資源 URI 保持穩定，只是回應的『表示形式（Representation）』隨著版本或協商結果而不同」這個 REST 的原始精神，但實務上因為不容易直接在瀏覽器測試、除錯需要額外查看標頭，開發體驗上不如 URL 版本直觀，很多團隊在權衡「理論純粹性」和「實務易用性」之後，還是選擇 URL 路徑版本。

**向後相容的漸進式修改（避免升版的技巧）**：多數 API 的變更，其實可以透過「相容性設計」完全避免升版，常見手法包括——**新增欄位而非修改既有欄位**（在回應 JSON 裡新增一個欄位，既有客戶端如果沒有讀取這個新欄位，完全不受影響，這符合「Postel 法則」，即「發送時保守、接收時寬容」的健壯性原則）；**新增可選的請求參數**（既有客戶端不傳這個參數，行為維持原樣，新客戶端可以選擇性使用新參數獲得新行為）；**新增全新的端點**（而非修改既有端點的行為）；**用「棄用（Deprecated）」標記＋緩衝期，取代直接刪除**（在回應標頭加上 `Deprecation` 和 `Sunset` 標頭，告知客戶端「這個欄位/端點將在某個時間點之後失效」，給客戶端充足時間遷移，而不是無預警直接移除）。只有真正無法相容的變更——例如「一個欄位的資料型別從字串改成物件」、「移除某個仍在被使用的欄位」、「改變某個操作的核心語意」——才真正需要發一個新的主版本號。

**版本淘汰的溝通與時程管理**：即使真的需要升版，也不代表舊版本應該立刻被關閉，妥善的做法是——公告一個明確的「舊版本淘汰時間表」（例如「v1 將在 6 個月後停止支援」）、在舊版本的回應中加入警告標頭提醒客戶端盡快遷移、提供詳細的遷移指南（Migration Guide）說明新舊版本的差異和遷移步驟、並在真正下線前透過監控觀察還有多少流量仍在使用舊版本（如果仍有重要客戶依賴舊版本，可能需要延後淘汰時程或主動聯繫溝通）。

## 面試回答方式

先給出版本管理的核心目標——「讓 API 能演進、又不破壞既有客戶端」。介紹三種版本表達方式（URL路徑、查詢參數、Header），並點出各自的優缺點取捨（URL版本直觀但不夠 RESTful、Header 版本更純粹但除錯不直觀）。更重要的是要強調「能不升版就不升版」這個原則，具體講出幾種向後相容的漸進式修改手法（新增欄位、新增端點、棄用標記+緩衝期）。最後提到版本淘汰需要有明確的時程和溝通機制。這道題如果只回答「有三種版本策略」而沒有提到「向後相容優先於升版」這個更重要的原則，會顯得對 API 演進的實務理解不夠深入。

## 常見追問

### 如果新增一個「必填」欄位到既有的請求體（Request Body）裡，這算是破壞性變更嗎？為什麼？

**核心答案**：是的，這是一個典型的**破壞性變更**——即使表面上看起來只是「新增」了一個欄位，但因為這個欄位被標記為「必填」，所有既有的客戶端（它們的程式碼是根據舊的 API 規格寫的，完全不知道有這個新欄位存在）在呼叫這個端點時，都不會帶上這個欄位，導致伺服器端的驗證邏輯拒絕這些原本合法的請求（回傳 400 錯誤），瞬間讓所有既有客戶端的呼叫全部失敗。正確的做法是——**新增的欄位應該是「可選（Optional）」的，並提供合理的預設值**，這樣既有客戶端不帶這個欄位時，伺服器套用預設值正常處理（維持向後相容），只有新版本的客戶端主動選擇提供這個欄位時，才會使用新的行為。

**詳細解析**：這題糾正一個常見的誤解——「新增」欄位聽起來像是「加法」，直覺上應該是安全、向後相容的操作，但「新增必填欄位」恰恰是最容易被忽略、卻極具破壞性的變更類型之一。破壞性變更的判斷標準不是「這是新增還是修改/刪除」，而是「既有客戶端（完全不知道這個變更存在）繼續按照原本的方式呼叫這個 API，是否還能正常運作」——如果新增的欄位是可選的，既有客戶端的行為完全不受影響（它們的請求裡沒有這個欄位，伺服器套用預設值，一切正常）；但如果新增的欄位被標記為必填，既有客戶端的請求因為缺少這個欄位而被伺服器拒絕，這就是實質上的破壞性變更，即使從 API 規格文件的角度看，這只是「加了一行」這麼簡單的改動。這個陷阱之所以容易被忽略，是因為開發者在修改 API 規格時，往往只從「新規格是否完整、是否涵蓋了新的業務需求」的角度思考，而沒有從「所有還在使用舊規格的既有客戶端，會發生什麼事」這個角度做逆向驗證。正確的相容性設計原則是——任何新增到請求體的欄位,都應該預設是可選的,並在伺服器端的處理邏輯裡,為「客戶端沒有提供這個欄位」的情況設計合理的預設行為(套用預設值、或維持舊有的行為邏輯)，只有在極少數「這個欄位缺失在業務邏輯上完全沒有合理預設值、必須由客戶端明確提供」的情況下，才應該考慮把它設為必填——但即使如此，也應該透過「先以可選欄位＋警告的方式上線一段緩衝期，觀察並敦促既有客戶端逐步遷移提供這個欄位，緩衝期結束後才正式轉為必填」這種漸進式的方式，而不是直接一次性地把新欄位設為必填、立即生效。

**面試回答方式**：明確回答「是,這是破壞性變更」。解釋原因——「判斷破壞性變更的標準不是新增/修改/刪除,而是『既有客戶端按原本方式呼叫,是否還能正常運作』；新增必填欄位會導致所有沒有帶這個欄位的既有請求被伺服器拒絕,實質上破壞了向後相容」。給出正確做法——「新增欄位應該預設可選、有合理預設值；如果真的必須轉為必填,應該用『先可選+警告緩衝期,再正式轉必填』的漸進方式,而非一次到位」。展現你能識破「表面上是新增、實質上是破壞性變更」這種容易被忽略的陷阱。

### 如果選擇用 URL 路徑做版本管理（如 /v1、/v2），在後端程式碼架構上，要怎麼組織才不會讓多個版本的程式碼變得難以維護？

**核心答案**：常見的組織方式包括：**（1）版本間共用核心業務邏輯，只在「介面層（Controller/Handler）」做版本差異化**——把實際的業務邏輯（如資料驗證、資料庫操作、核心運算）抽取成與版本無關的共用服務層，不同版本的 Controller 只負責處理「這個版本特有的請求/回應格式轉換」，呼叫底層共用的業務邏輯，避免業務邏輯在多個版本間重複維護；**（2）用「介面卡轉接（Adapter）」模式**，讓舊版本的請求先被轉換（adapt）成內部統一的新格式，再交給共用邏輯處理，回應時再轉換回舊版本期望的格式，這樣核心邏輯永遠只需要維護「最新」的一套，各版本只是薄薄一層轉接；**（3）明確的版本淘汰治理**——定期審視有多少流量還在使用舊版本，主動淘汰不再需要維護的舊版本程式碼，避免版本數量無限累積導致維護負擔持續增加。

**詳細解析**：這題從架構設計的角度，探討「多版本並存」這個實務上容易演變成技術債的問題。如果不謹慎設計，最常見的反模式是「每個版本的 Controller 都各自獨立實作一整套業務邏輯」，一開始可能因為省事而這樣做（複製貼上前一版的程式碼，稍微修改），但隨著版本數量增加（v1, v2, v3...），同樣的核心邏輯（例如「計算訂單總金額」這個規則）如果散落在好幾個版本的程式碼裡各自維護一份，一旦這個核心邏輯本身需要修正（例如發現一個計算 bug），開發者必須記得同步修改所有版本裡重複的邏輯，非常容易遺漏，也讓程式碼庫的維護成本隨著版本數量線性甚至超線性增長。正確的架構原則是「業務邏輯只寫一份、只維護最新的一套，版本差異只存在於『輸入輸出的格式轉換』這層薄薄的介面」——具體實現上，可以讓每個版本的 Controller，收到請求後，先把「這個版本特有的請求格式」轉換成一個內部統一、與版本無關的「標準請求物件」，這個標準物件交給共用的業務邏輯層處理（這個共用邏輯層完全不需要知道呼叫它的是 v1 還是 v2），業務邏輯處理完畢後，回傳一個「標準回應物件」，再由對應版本的 Controller，把這個標準物件轉換回「這個版本客戶端期望的回應格式」。這種「Adapter（轉接器）」模式的核心價值是——核心業務邏輯的變更（新功能、bug 修正）只需要在一個地方進行，所有版本自動受益（因為它們都是透過轉接層呼叫同一份核心邏輯），版本相關的程式碼複雜度被限制在「格式轉換」這個相對單純、變動頻率較低的範疇。除了架構設計，「主動治理」也很重要——版本不應該無限期地累積下去，團隊應該定期檢視「還有哪些客戶端在使用哪個舊版本」（透過監控實際流量），主動溝通並淘汰真正不再需要維護的舊版本，把技術債控制在可管理的範圍內，而不是讓 v1、v2、v3、v4...無止盡地並存下去。

**面試回答方式**：給出核心架構原則——「業務邏輯只維護一份共用的、與版本無關的核心層，各版本 Controller 只負責『這個版本特有格式』和『內部統一格式』之間的轉換（Adapter 模式），避免核心邏輯在多版本間重複維護、修 bug 要改好幾個地方」。補充「主動治理」——「定期監控各版本實際流量，主動淘汰不再需要的舊版本，避免版本數量無限累積成為技術債」。展現你不只知道「怎麼標示版本」，還理解多版本並存對程式碼架構和長期維護成本的實際影響，並有具體的應對設計。

### 如果 API 的消費者是「內部其他團隊自己維護的服務」而非「外部第三方開發者」，版本管理策略是否應該有所不同？

**核心答案**：應該有所不同——**內部服務之間**因為呼叫方和提供方通常屬於同一個組織、溝通成本較低、部署節奏可以協調，版本管理策略可以更「輕量」，例如採用「持續交付、盡量不做正式版本號升級，而是透過完善的自動化測試（尤其是消費者驅動的契約測試 Consumer-Driven Contract Testing）確保每次變更都不破壞消費者的既有整合」，並搭配「同時部署新舊版本一小段時間、逐步把流量從舊版本遷移到新版本」的灰度發布策略。相對地，**面向外部第三方開發者的公開 API**，因為呼叫方是完全不受你控制的外部開發者（可能有數千個獨立的應用程式依賴這個 API、且他們的更新節奏你完全無法掌控），必須採用更保守、更正式的版本管理（明確的版本號、長時間的向後相容保證、正式的棄用公告和緩衝期），因為任何破壞性變更造成的影響範圍和溝通成本都遠高於內部服務。

**詳細解析**：這題考察是否能根據「API 的消費者是誰」這個關鍵情境差異，調整版本管理的策略取捨，而非套用一套固定不變的做法。內部服務之間的 API（有時稱為「私有 API」或「東西向流量」）和面向外部開發者的公開 API（「北南向流量」），在版本管理上的核心差異點在於「呼叫方的可控性和溝通成本」——內部服務的呼叫方，本質上是同一個組織裡的其他團隊，你通常知道「有哪些服務依賴這個 API」（透過服務註冊、依賴關係圖或組織內部的溝通），也有能力主動聯繫這些消費團隊，協調升級步調（例如「我們下週要修改這個介面，麻煩你們在這之前完成遷移」），這種情況下，過度正式化的版本管理（每次修改都發一個新的 v2、v3）反而增加了不必要的溝通和維護開銷，更輕量、更依賴「自動化測試保障相容性」而非「正式版本號」的做法（例如契約測試——消費方團隊定義他們對這個 API 的「期望契約」，提供方團隊的每次變更都要跑過這些契約測試，確保沒有破壞任何消費者的既有假設）更適合這種內部協作場景，能加快迭代速度而不犧牲穩定性。反觀面向外部開發者的公開 API，你完全不知道「有多少開發者、用什麼方式在依賴這個 API」，也沒有直接的管道去「協調」他們的升級步調（你只能單方面公告、給緩衝期，但無法強制所有人立即遷移），任何未經充分緩衝就上線的破壞性變更，都可能瞬間讓大量素未謀面的第三方應用程式故障，帶來的商譽損失和支援成本都遠高於內部場景，因此必須採用更保守、更正式（明確版本號、長緩衝期、詳盡的遷移文件、正式的棄用公告流程）的版本管理策略。理解「版本管理策略的『正式程度』應該和『呼叫方的可控性、溝通成本、變更影響範圍』成正比」，展現你能根據實際情境（而非教條式地套用同一套規則）做出合理的工程判斷。

**面試回答方式**：明確回答「應該不同」。給出核心判斷依據——「差異在於呼叫方的可控性和溝通成本：內部服務可以主動協調、溝通成本低,適合更輕量的版本管理(如契約測試保障相容性、少發正式版本號、搭配灰度遷移)；外部公開 API 呼叫方完全不可控、無法強制升級,必須更保守正式(明確版本號、長緩衝期、正式棄用公告)」。展現你能因應「消費者是誰」這個關鍵情境差異,調整版本管理策略的正式程度，而非一套規則套用所有場景。
