# 題目

什麼是 RESTful API？設計 RESTful API 時有哪些核心原則？

## 核心答案

RESTful API 是一種基於 **HTTP 協定、以「資源（Resource）」為核心** 的 API 設計風格，遵循 Roy Fielding 提出的 REST（Representational State Transfer）架構約束。核心原則包括：**（1）資源導向的 URL**——URL 代表「名詞」（資源），而不是「動詞」（操作），例如用 `GET /users/123` 而不是 `GET /getUser?id=123`；**（2）用 HTTP 方法表達操作語意**——`GET`（讀取）、`POST`（建立）、`PUT`（完整更新/替換）、`PATCH`（部分更新）、`DELETE`（刪除），操作的動詞交給 HTTP 方法表達，而非塞進 URL；**（3）無狀態（Stateless）**——每個請求都必須包含伺服器處理這個請求所需的全部資訊，伺服器不應該在請求之間保存客戶端的會話狀態；**（4）使用標準的 HTTP 狀態碼**表達結果（200 成功、201 建立成功、400 客戶端錯誤、404 找不到資源、500 伺服器錯誤等）；**（5）統一介面**——用一致的方式表達集合和單一資源的巢狀關係（如 `GET /users/123/orders` 代表使用者 123 的所有訂單）。

## 詳細解析

**資源導向 vs 動作導向**：REST 風格的核心思維轉變，是把 API 設計的焦點從「這個 API 要做什麼動作」轉移到「這個 API 在操作哪個資源」。例如傳統 RPC 風格可能設計成 `POST /createUser`、`POST /deleteUser`、`POST /updateUserEmail` 這種「每個操作一個端點」的方式；RESTful 風格則統一成「使用者」這一個資源，透過不同的 HTTP 方法表達不同操作：`POST /users`（建立）、`DELETE /users/123`（刪除）、`PATCH /users/123`（更新使用者的部分欄位，如僅更新 email）。這種設計讓 API 的介面數量大幅減少（不是每個操作一個端點,而是「資源數量 × 固定的方法組合」），也讓 API 的可預測性大幅提升——只要知道資源的命名，就能推測出對應的操作端點。

**HTTP 方法的語意與冪等性**：`GET`、`PUT`、`DELETE` 都應該是**冪等的**（多次執行同一個請求，結果應該和執行一次相同，見 [[003-idempotency-design.md]]），例如 `DELETE /users/123` 執行一次和執行三次，最終結果都是「使用者 123 不存在」；而 `POST` 通常不是冪等的（每次呼叫 `POST /users` 都會建立一筆新的使用者記錄）。`GET` 還應該是**安全的（Safe）**——不會對伺服器狀態產生任何副作用，這也是為什麼瀏覽器和快取伺服器可以放心地重複發送、預先載入 GET 請求，卻不能對 POST 這麼做。

**巢狀資源的表達**：當資源之間有明確的從屬關係時，用 URL 路徑的巢狀結構表達，例如 `GET /users/123/orders/456` 代表「使用者 123 底下、編號 456 的訂單」；但巢狀不應該無限層疊下去（一般建議最多兩層），過深的巢狀會讓 URL 難以理解和維護，這種情況下通常改用查詢參數表達關聯（如 `GET /orders?userId=123`）或直接把資源視為頂層資源獨立處理。

**狀態碼的正確使用**：狀態碼不只是「成功或失敗」這麼簡單的二分法，而是應該精確地傳達「發生了什麼」——`200 OK`（一般成功）、`201 Created`（資源建立成功，通常搭配回傳新資源的位置於 `Location` 標頭）、`204 No Content`（成功但沒有回傳內容，如成功刪除後）、`400 Bad Request`（客戶端請求格式或參數錯誤）、`401 Unauthorized`（未認證）、`403 Forbidden`（已認證但無權限）、`404 Not Found`（資源不存在）、`409 Conflict`（請求和目前資源狀態衝突，如重複建立）、`422 Unprocessable Entity`（請求格式正確但語意上驗證失敗）、`500 Internal Server Error`（伺服器端未預期的錯誤）。精確使用狀態碼讓客戶端（以及開發者除錯時）能快速判斷問題的性質和責任歸屬。

## 面試回答方式

先給出核心定義——「REST 是以資源為核心的 API 設計風格,用 HTTP 方法表達操作、用 URL 表達資源」，並舉一個「動詞導向 vs 資源導向」的具體對比例子（如 `POST /createUser` vs `POST /users`）讓面試官感受到你理解這個設計轉變的本質。接著逐一講出核心原則——資源導向 URL、HTTP 方法的語意（含冪等性）、無狀態、標準狀態碼、巢狀資源表達。如果能提到「GET 的安全性和冪等性」這類細節，展現你不只是背誦口號，而是理解每個原則背後的實際意義。

## 常見追問

### 「無狀態（Stateless）」具體是什麼意思？如果 API 需要「使用者登入狀態」，這樣不就違反無狀態原則了嗎？

**核心答案**：「無狀態」指的是「伺服器不會在多次請求之間，於自己的記憶體或會話儲存中保存與特定客戶端相關的上下文狀態」——每一個請求都必須自帶「伺服器處理這個請求所需的全部資訊」（例如透過 `Authorization` 標頭帶上 Token），伺服器不需要依賴「這是同一個客戶端之前發過的請求」這個記憶來正確處理。這和「使用者需要登入」並不矛盾——登入驗證後產生的憑證（如 JWT Token 或 Session ID），本身就是「客戶端在每次請求中主動攜帶的資訊」，伺服器每次都是「憑當下這個請求攜帶的憑證」重新驗證身份，而不是「記得這個連線之前登入過」，這仍然符合無狀態的精神。真正違反無狀態的做法，是伺服器在記憶體裡「記住」某個客戶端上一次請求做了什麼，並根據這個記憶決定這次請求怎麼處理（例如傳統的 Session 儲存在單一伺服器記憶體裡,導致這個客戶端後續的請求都必須被路由回同一台伺服器,這種「黏性會話」的設計恰恰違反了無狀態，也是分散式系統中常見的擴展性問題）。

**詳細解析**：這題釐清「無狀態」這個經常被誤解的 REST 原則。無狀態的核心價值在於「可擴展性和可靠性」——如果每個請求都是自包含的，任何一台伺服器都能獨立處理任何一個請求，不需要「記得」這個客戶端之前發生過什麼，這讓水平擴展（加更多伺服器分擔流量）變得非常簡單，因為請求可以被隨意路由到任何一台伺服器處理，不需要考慮「這個客戶端的狀態存在哪台機器上」這個問題；也讓系統更具韌性——如果某一台伺服器當機，其他伺服器可以立刻無縫接手處理後續請求，不會因為「狀態只存在那台掛掉的機器上」而導致服務中斷。「登入狀態」這個常見的疑惑點，關鍵在於分清楚「狀態存在哪裡」——如果狀態（如「這個使用者是誰、有什麼權限」）是編碼在客戶端持有、每次請求主動攜帶的憑證裡（如 JWT，其本身包含了使用者身份和權限資訊、並用簽章防止竄改，伺服器只需要驗證簽章、不需要查詢任何額外的儲存），這完全符合無狀態原則，因為伺服器不需要記住任何東西，光憑這次請求攜帶的 Token 就能獨立完成驗證和授權判斷；但如果狀態是「Session ID，伺服器需要拿著這個 ID 去查詢儲存在伺服器端（記憶體或資料庫）的會話資料才能知道這個使用者是誰」，這種模式雖然也是「每次請求帶著憑證」，但因為需要伺服器端額外儲存和查詢「會話狀態」，嚴格來說更接近一種「有狀態」的設計，只是這個狀態可以被抽出到獨立的共享儲存（如 Redis）而不綁定在單一伺服器上，緩解但不完全消除擴展性上的顧慮。理解「無狀態關注的是『伺服器不依賴私有記憶去處理請求』，而不是『使用者不能有登入狀態這個概念』」，展現你對這個原則的精確理解。

**面試回答方式**：先精確定義——「無狀態是指伺服器不在私有記憶體/儲存中保留和特定客戶端相關的上下文，每個請求都要自帶處理所需的全部資訊」。解釋「登入狀態」為何不矛盾——「登入後拿到的憑證（Token）本身就是客戶端每次主動攜帶的資訊，伺服器每次都是憑當下的憑證重新驗證，不是靠記憶」。可以延伸區分「JWT（自包含、伺服器不用查儲存）vs Session ID（需要伺服器查詢共享儲存）」在無狀態程度上的差異。展現你能精確拆解這個容易望文生義的原則。

### 如果一個操作，語意上介於「建立」和「更新」之間（例如「如果不存在就建立、存在就更新」，即 upsert），應該用哪個 HTTP 方法？

**核心答案**：這種「upsert（更新或插入）」語意，通常適合用 **`PUT`**——因為 `PUT` 的語意本來就是「用請求內容『完整替換』某個指定 URI 所代表的資源狀態」，如果這個資源原本不存在，`PUT` 建立它（並回傳 `201 Created`）；如果已經存在，`PUT` 用請求內容完整覆蓋原本的內容（回傳 `200 OK` 或 `204 No Content`），這剛好符合「不存在就建立、存在就取代」的 upsert 語意，且 `PUT` 本身要求是冪等的，這和 upsert「執行多次結果相同」的特性也吻合。相對地，`POST` 通常不適合這種場景，因為 `POST /users` 這種呼叫方式，每次呼叫語意上代表「建立一筆新資源」，如果用 `POST` 做 upsert，語意上會產生混淆（呼叫方難以預期「這次呼叫到底是建立還是更新」）。

**詳細解析**：這題考察對 HTTP 方法語意細微差別的精確掌握，尤其是 `PUT` 和 `POST` 這兩個經常被混用、但語意設計上有明確區分意圖的方法。`PUT` 的正式定義是「將請求的內容，作為指定 URI 上資源的新狀態」，這個定義隱含了幾個重要特性——首先，呼叫方在使用 `PUT` 時，必須「知道並指定完整的目標 URI」（例如 `PUT /users/123`），這和 upsert 的使用情境天然吻合（呼叫方通常確實知道要操作的資源識別碼，例如「使用者 123 的個人資料」，不管這筆資料現在存不存在,都用同一個確定的 URI 操作）；其次，`PUT` 是「完整替換」語意，如果請求內容裡沒有包含某個欄位，正確行為應該是把該欄位重設為空值或預設值（而不是像 `PATCH` 那樣「只更新有帶的欄位」），這和「新建立」時所有欄位都需要有明確初始值的邏輯也一致。反觀 `POST` 的傳統語意是「向一個集合資源提交一筆新資料，由伺服器決定新資源的識別碼並生成」（例如 `POST /users`，伺服器自己生成新的 user id 並回傳），呼叫方在呼叫 `POST` 的當下，通常並不知道（也不指定）最終資源的 URI，這和 upsert 場景「呼叫方明確知道要操作哪個資源」的特性不吻合，如果硬要用 `POST` 表達 upsert，語意上會顯得混淆（這次呼叫的 URI 到底代表什麼，是集合還是特定資源？結果是新建立還是更新？呼叫方難以單從 HTTP 方法和 URL 判斷）。因此業界的共識是——當語意上是「呼叫方指定了明確的資源識別碼、且該資源可能存在也可能不存在」這種情境（典型的 upsert），用 `PUT` 是更符合 HTTP 語意設計的選擇。

**面試回答方式**：直接給出答案——「用 PUT，因為 PUT 的語意本來就是『用請求內容完整替換指定 URI 的資源狀態』，不存在就建立、存在就覆蓋，剛好符合 upsert 需求，且 PUT 要求冪等,和 upsert 特性吻合」。對比說明「POST 通常代表『向集合提交、由伺服器決定新資源識別碼』，呼叫方不預先指定 URI，這和 upsert『呼叫方明確知道要操作哪個資源』的情境不吻合,用 POST 做 upsert 會造成語意混淆」。展現你對 HTTP 方法設計意圖有精確掌握，而不只是死記「GET/POST/PUT/DELETE 分別對應 CRUD」這種粗略對應。

### 如果客戶端需要一次取得多個不同資源的資料（例如同時要使用者資料、訂單列表、通知），嚴格遵守「每個端點只回傳單一資源」的 REST 原則，會遇到什麼問題？有什麼常見的解法？

**核心答案**：嚴格遵守「單一資源」原則，會導致客戶端需要**發送多次獨立的 HTTP 請求**才能組裝出畫面需要的完整資料（例如分別呼叫 `GET /users/123`、`GET /users/123/orders`、`GET /notifications?userId=123`），這在行動網路延遲較高、或請求數量很多的情境下，會因為「多次網路往返（round trip）」而顯著拖慢頁面載入速度，也增加了客戶端組裝資料的複雜度。常見的解法包括：**（1）為特定畫面設計「聚合端點（Aggregation Endpoint）」**——後端提供一個專門的端點（如 `GET /dashboard`），內部一次性查詢並組裝多個資源，一次回應就包含畫面需要的全部資料；**（2）支援欄位/關聯的動態展開（Field Expansion）**——如 `GET /users/123?expand=orders,notifications` 這種讓客戶端指定要一併帶出哪些關聯資料的參數化設計；**（3）改用 GraphQL**——讓客戶端自己在單一請求中，精確描述需要哪些欄位和關聯資料，伺服器一次性回應，從根本上解決「多次請求組裝資料」的問題。

**詳細解析**：這題觸及嚴格 RESTful 設計在實務前端場景下的一個常見痛點，考察是否理解純粹的資源導向設計和實際使用者體驗需求之間可能存在的張力。嚴格的 REST 風格鼓勵「每個端點對應一個資源、保持簡單和一致性」，這個設計哲學在系統的「可維護性、可預測性」上有很大優勢，但當客戶端（尤其是行動裝置，網路延遲和連線數限制更明顯）需要組裝一個複雜畫面（例如電商 App 的訂單詳情頁，可能同時需要訂單基本資訊、使用者資訊、商品明細、物流狀態等多個原本分散在不同資源端點的資料）時，嚴格遵守「一個端點一個資源」會導致客戶端必須發起 4-5 次獨立請求，每次請求都有各自的網路延遲、TLS 交握（如果沒有連線重用）、以及伺服器處理開銷，多次請求疊加起來的總延遲，可能遠高於「一次性把所有需要的資料組裝好回傳」的方案。聚合端點是最直接的解法，但代價是「這個端點是為了特定畫面量身訂做的，缺乏通用性，畫面需求一變動，這個端點的回應結構或邏輯往往也要跟著調整」，如果聚合端點越來越多，可能導致後端 API 表面積迅速膨脹、難以維護。欄位展開（Field Expansion）是介於「純粹的單一資源端點」和「完全客製化聚合端點」之間的折衷——保留資源導向的核心結構，但允許客戶端透過查詢參數，選擇性地要求伺服器把相關聯的資源一併展開帶出，兼顧了通用性和減少請求次數的效益，但需要後端在實作上支援這種動態組裝的邏輯，複雜度比純粹的固定回應結構要高。GraphQL 則是從架構層面徹底解決這個問題的方案——它把「決定要回傳哪些欄位和關聯」這件事的主導權完全交給客戶端（客戶端在請求中用 Query 描述自己需要的資料形狀），伺服器根據這個 Query 動態解析並組裝回應，一次網路往返就能精確拿到所需的全部資料，不多不少，但代價是後端需要額外的 Schema 設計和 Resolver 實作複雜度，以及一些傳統 REST 生態（如 HTTP 快取、CDN 快取）在 GraphQL 上不容易直接沿用的挑戰。理解這三種方案分別代表「特化但簡單」、「通用但需要額外設計」、「最靈活但架構複雜度最高」的不同權衡位置，展現你能因應實際場景在「嚴格遵守 REST 原則」和「使用者體驗/效能」之間做出合理取捨。

**面試回答方式**：先指出問題——「嚴格單一資源端點,會導致客戶端要發多次請求組裝畫面需要的資料,在延遲敏感場景(尤其行動網路)造成體驗問題」。給出三個層次的解法——「聚合端點(針對特定畫面客製化,簡單但通用性差、API 表面積容易膨脹)」、「欄位展開參數(如 ?expand=orders,在保留資源結構的同時支援選擇性展開關聯資料)」、「改用 GraphQL(客戶端自己描述需要的資料形狀,一次請求精確取得,但架構複雜度和 HTTP 快取相容性上有取捨)」。展現你理解嚴格 REST 設計原則和實務效能/體驗需求之間的張力，並能給出分層次的解決方案。
