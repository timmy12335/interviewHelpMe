# 題目

多租戶系統有哪幾種隔離方式？各自的取捨是什麼？

## 核心答案

隔離的層次由淺到深有四種。**共用資料庫、共用 schema**（每張表加一個 `tenant_id` 欄位）——**成本最低、擴展最容易**，但**隔離最弱**（一個查詢漏了條件就是跨租戶洩漏）。**共用資料庫、獨立 schema**（每個租戶一組表）——隔離較好、可以按租戶備份，**但 schema 變更要對每個租戶執行**，租戶多時成為負擔。**獨立資料庫**——隔離強、可以按租戶調整資源與版本，**成本與維運複雜度高得多**。**獨立部署**（每個租戶一整套服務）——最強的隔離，成本最高，通常只給大型企業客戶。

選擇的核心問題不只是技術，而是「客戶要求什麼樣的隔離保證」——某些行業（金融、醫療）的合規要求可能直接排除共用資料庫。

多數 SaaS 從「共用資料庫共用 schema」開始是對的——它的成本結構最適合大量的小客戶，而隔離的不足可以用工程紀律彌補（見下）。

## 詳細解析

共用 schema 的核心風險是「漏加租戶條件」，而它必須用結構性的手段防護而非依賴紀律。**三層做法**：在資料存取層自動注入租戶條件（Hibernate 的 `@Filter`、MyBatis 的攔截器、或一個統一的 Repository 基底類別）——讓業務程式碼根本沒有機會忘記；**資料庫層的 row-level security**（PostgreSQL 支援，**即使應用有 bug 資料庫也會拒絕**）；以及**專門的跨租戶測試**（用租戶 A 的身分嘗試存取租戶 B 的資料，驗證被拒絕）。只靠「每個查詢都記得加條件」必然會失敗——一個遺漏就是資料洩漏，而那在正常測試中不會被發現（測試通常只用一個租戶的資料）。

「吵鬧的鄰居」是共用資源的固有問題。一個大租戶的重查詢會影響所有人——而在共用資料庫下，你甚至難以歸因（監控看到的是總量而非按租戶分解）。**處理方式有三層**：**按租戶的指標與配額**（讓「誰在消耗資源」可見並可以限制）、**分級部署**（大客戶用獨立的資料庫或實例，小客戶共用）、以及**限流與資源隔離**（每個租戶的並行請求數上限）。「按租戶分解的指標」是這些的前提——沒有它就無法歸因也無法設定合理的配額。

**混合模式在成熟的 SaaS 中很常見**：大多數小客戶共用一套、少數大客戶獨立部署。這讓成本結構與客戶價值對應——而且它自然地提供了一個升級路徑（客戶成長到一定規模就遷移到獨立部署）。代價是要維護兩套部署方式與遷移的工具，但那通常比「所有客戶都用最高規格的隔離」便宜得多。

**租戶的識別方式影響架構**。**子網域**（`acme.example.com`）——最常見，容易在閘道層路由與識別。**路徑**（`/t/acme/...`）——簡單但讓 URL 較醜且不利於按租戶做 CDN 快取。**從認證的 token 取得**——最安全（無法被偽造）但**需要在每一層傳遞**。**實務上通常是組合**：子網域或路徑用於路由，而實際的授權必須依賴 token 中的租戶宣告——因為 URL 中的租戶識別是使用者可控的，不能作為授權依據。

## 面試回答方式

先給**四種隔離層次**與各自的取捨，並指出選擇的核心問題不只是技術，而是客戶要求什麼樣的隔離保證（合規可能直接排除共用資料庫）。給實務建議（多數 SaaS 從共用 schema 開始是對的）。加分點有四個：共用 schema 的核心風險必須用結構性手段防護——資料存取層自動注入、資料庫的 row-level security、專門的跨租戶測試，「每個查詢都記得加條件」必然會失敗且遺漏在正常測試中不會被發現；「吵鬧的鄰居」在共用資料庫下難以歸因，而按租戶分解的指標是所有處理的前提；混合模式讓成本結構與客戶價值對應並自然提供升級路徑；以及URL 中的租戶識別是使用者可控的，不能作為授權依據，授權必須依賴 token 中的宣告。

## 講稿

隔離的層次由淺到深有四種。共用資料庫共用 schema，每張表加一個租戶欄位，成本最低但隔離最弱。共用資料庫獨立 schema，隔離較好但變更要對每個租戶執行。獨立資料庫，隔離強但成本高。還有獨立部署，最強的隔離但通常只給大型企業客戶。

選擇的核心問題不只是技術，而是客戶要求什麼樣的隔離保證。某些行業的合規要求可能直接排除共用資料庫。

共用 schema 的核心風險是漏加租戶條件，而它必須用結構性的手段防護而不是依賴紀律。我會用三層。在資料存取層自動注入租戶條件，讓業務程式碼根本沒有機會忘記。資料庫層的列級安全，即使應用有 bug 資料庫也會拒絕。還有專門的跨租戶測試，用一個租戶的身分嘗試存取另一個的資料。

只靠每個查詢都記得加條件必然會失敗，一個遺漏就是資料洩漏，而那在正常測試中不會被發現，因為測試通常只用一個租戶的資料。

還有一個安全上的要點。URL 中的租戶識別是使用者可控的，不能作為授權依據。授權必須依賴權杖中的租戶宣告。

## 常見追問

### 跨租戶的資料洩漏怎麼預防與偵測？

**核心答案**：預防用結構、偵測用測試與稽核。結構上，讓租戶條件在資料存取層自動加入（或用資料庫的 row-level security），**使業務程式碼無法繞過**。偵測上，**寫專門的負面測試**（用租戶 A 的身分呼叫每一個端點並嘗試存取租戶 B 的資源 ID，驗證都被拒絕），**並把它納入 CI**。稽核上，記錄「哪個租戶存取了哪些資源」，異常的跨租戶模式應該告警。

**詳細解析**：「負面測試」在這裡的價值特別高，因為正面測試完全測不到這個問題。一個只用單一租戶測試的套件，無論覆蓋率多高都不會發現跨租戶洩漏——因為那個場景根本沒有被執行。所以多租戶系統的測試策略必須明確包含「至少兩個租戶的資料」，而且每個涉及資料存取的測試都應該驗證「另一個租戶看不到」。這是一個「測試策略必須反映風險模型」的例子——覆蓋率是一個技術指標，而它與「有沒有測到真正危險的情況」是兩回事。很多系統的測試覆蓋率很高，卻從未驗證過最關鍵的安全屬性。

**面試回答方式**：給預防與偵測的分工（結構預防、測試與稽核偵測）並具體說明各自的做法。真正的重點是負面測試的價值特別高，因為正面測試完全測不到——只用單一租戶測試的套件無論覆蓋率多高都不會發現跨租戶洩漏，因為那個場景根本沒被執行。收在一般化：**測試策略必須反映風險模型**，覆蓋率與「有沒有測到真正危險的情況」是兩回事，很多系統覆蓋率很高卻從未驗證過最關鍵的安全屬性。

### 租戶的資料要怎麼遷移到獨立部署？

**核心答案**：這是**混合模式必須具備的能力**，而它與一般的資料遷移類似但多了「篩選」：**匯出該租戶的所有資料**（每張表依 `tenant_id` 過濾）、**匯入到新環境**、**驗證完整性**、**切換路由**、確認無誤後清理舊環境的資料。**關鍵是「切換期間的寫入」**——通常需要一個短暫的唯讀窗口，或者用雙寫加追趕的方式。

**詳細解析**：「這個能力應該在早期就被驗證」而非等到第一個大客戶要求時才做。原因是它會揭露設計上的問題：**有沒有哪張表忘了加 `tenant_id`**（那些資料無法被正確篩選）、有沒有跨租戶共用的資料（例如共用的字典表——那要複製一份還是保持共用）、以及有沒有租戶 ID 之外的隱含關聯（例如一個全域的序號，遷移後可能衝突）。這些問題在單一部署下完全不會顯現，而它們可能需要 schema 的變更才能修正——所以越早發現越好。務實的做法是「在測試環境定期演練一次租戶遷移」，把它當成一個持續驗證的能力而非一次性的專案。

**面試回答方式**：給遷移的步驟並指出**關鍵是切換期間的寫入**（唯讀窗口或雙寫追趕）。真正的加分點是主張這個能力應該在早期就被驗證而非等到第一個大客戶要求，並說明它會揭露的三類設計問題（忘了加租戶欄位的表、跨租戶共用的資料、租戶 ID 之外的隱含關聯）。收在：這些問題在單一部署下完全不會顯現且可能需要 schema 變更才能修正，所以在測試環境定期演練租戶遷移，把它當成持續驗證的能力。

### 多租戶下的快取要注意什麼？

**核心答案**：**快取鍵必須包含租戶識別**——這是最基本也最容易出錯的一點。一個沒有帶租戶的快取鍵意味著租戶 A 的資料會被租戶 B 讀到，而那是最嚴重的一類洩漏。**而且它的症狀是間歇性的**（只有在快取命中且剛好是另一個租戶的資料時才發生），**極難重現與發現**。

**詳細解析**：防護的方式與資料庫的租戶條件相同：結構而非紀律。在快取的抽象層自動加上租戶前綴（一個統一的 `CacheKeyBuilder` 或攔截器），讓業務程式碼寫的鍵自動被加上前綴。**這樣「忘記加」就不可能發生。** 另一個要注意的是「本地快取的租戶隔離」——如果應用實例服務多個租戶且有行程內的快取，**同樣要確保鍵包含租戶**；而如果是「每個租戶一個實例」的部署，本地快取就天然隔離了——這是獨立部署的一個附帶好處。**還有配額的問題**：一個大租戶可能佔滿共用的快取，**把其他租戶的資料擠出去**——按租戶的快取配額（或者至少是監控）在共用快取上是必要的。

**面試回答方式**：給最基本的要求（**快取鍵必須包含租戶識別**）並強調症狀是間歇性的、極難重現與發現。給防護方式：在快取抽象層自動加上租戶前綴，讓「忘記加」不可能發生。加分點是兩個延伸：**本地快取同樣要注意**（而每租戶一實例的部署天然隔離，是獨立部署的附帶好處），以及**配額問題**——一個大租戶可能佔滿共用快取把其他租戶擠出去，按租戶的配額或至少是監控在共用快取上是必要的。
