# 題目

什麼是熔斷器模式（Circuit Breaker）？它解決什麼問題？三種狀態（關閉/開啟/半開）分別代表什麼？

## 核心答案

熔斷器模式借用了電路系統裡「保險絲」的概念，用來解決微服務（Microservices）架構中**「呼叫一個已經故障或回應緩慢的下游服務，可能拖垮整個呼叫鏈」**的問題——如果服務 A 呼叫服務 B，而服務 B 因為某種原因（如資料庫掛了）回應極度緩慢或大量失敗，服務 A 如果繼續傻傻地一直發起請求並等待逾時，不僅浪費大量的執行緒/連線資源(這些資源被卡在等待一個注定會失敗或逾時的請求上)，還可能因為資源被耗盡，連帶讓服務 A 自己也垮掉，進而讓呼叫服務 A 的服務 C 也遭殃，造成「連鎖故障（Cascading Failure）」。熔斷器透過持續監控「呼叫下游服務的成功/失敗比例」，在偵測到失敗率超過門檻時，**主動「跳閘」**，之後一段時間內的請求直接快速失敗（不再真正發送到下游服務），給下游服務喘息恢復的空間，也保護呼叫方自己不被拖垮。三種狀態：**關閉（Closed）**——正常狀態，請求正常轉發到下游服務，同時持續監控失敗率；**開啟（Open）**——失敗率超過門檻後跳閘，一段時間內直接快速失敗、不再真正呼叫下游；**半開（Half-Open）**——開啟一段時間後，放行少量「試探性」請求去檢查下游服務是否已經恢復，恢復就轉回關閉狀態，還沒恢復就轉回開啟狀態繼續等待。

## 詳細解析

**連鎖故障的具體發生機制**：假設服務 A 每次呼叫服務 B 都設定了 5 秒逾時，正常情況下服務 B 幾十毫秒就回應完畢；但如果服務 B 因為資料庫連線池（Connection Pool）耗盡而變得極度緩慢，每次呼叫都要等到 5 秒逾時才失敗，這代表服務 A 每一個處理請求的執行緒，都會被「卡住 5 秒」等待這個注定失敗的呼叫，如果服務 A 的執行緒池（Thread Pool）（或連線池）本來就有限（例如只有 200 個執行緒），在高併發流量下，這些執行緒很快就會被大量「正在等待逾時」的請求佔滿，導致服務 A 連處理其他（可能根本不需要呼叫服務 B 的）正常請求的能力都喪失了——服務 A 從「一個健康的服務」變成「因為某個下游依賴故障，自己也跟著垮掉」，如果還有服務 C 依賴服務 A，這個故障會繼續向上傳播，這就是「連鎖故障」的典型場景。

**三種狀態的完整流轉邏輯**：
- **關閉（Closed）**：預設的正常狀態，所有請求都會被正常轉發到下游服務，熔斷器在背景持續統計「最近一段時間內（如過去 10 秒或最近 100 次請求）」的失敗比例。一旦失敗比例超過設定的門檻（如 50%），熔斷器「跳閘」，狀態切換為開啟。
- **開啟（Open）**：進入這個狀態後，之後一段時間內（如 30 秒的「休眠期」），**所有**發往這個下游服務的請求，都會被熔斷器直接攔截、立即回傳一個失敗結果（通常是一個預先定義好的錯誤，或觸發「降級（Fallback）」邏輯，見 [[008-service-degradation.md]]），**完全不會真正把請求送到下游服務**。這樣做的目的有兩個——保護呼叫方自己(不再把執行緒/連線資源浪費在注定失敗的呼叫上)，同時也給下游服務一個「喘息」的機會(不會繼續被大量請求疲勞轟炸，有機會自己恢復，例如資料庫連線池有機會慢慢釋放、重新建立健康連線)。
- **半開（Half-Open）**：休眠期結束後，熔斷器不會直接魯莽地切回「完全正常」，而是先進入半開狀態——只放行**少量**（如 1-5 個）試探性請求真正送到下游服務，觀察這些試探性請求的結果：如果都成功，代表下游服務可能已經恢復，熔斷器轉回關閉狀態，重新開始正常轉發所有請求；如果試探性請求仍然失敗，代表下游服務還沒恢復，熔斷器轉回開啟狀態，重新開始下一輪的休眠等待。

**熔斷器 vs 逾時 vs 限流（Rate Limiting）的分工**：這三種機制經常被放在一起討論、但解決的問題層次不同——**逾時（Timeout）** 解決「單一次呼叫，不能無限期地等下去」的問題，是最基本的防線；**熔斷器** 解決「持續且大量地呼叫一個已知正在故障的服務，是在浪費資源、且可能造成連鎖故障」的問題，是在偵測到「這個依賴目前不健康」之後，主動停止繼續嘗試，給故障方喘息空間；**限流** 解決的是「保護自己不被過量的『入站』流量壓垮」的問題(見 [[006-rate-limiting-algorithms.md]])，方向和熔斷器（保護自己不被『出站』呼叫的故障下游拖垮）恰好相反。三者往往在一個健壯的微服務架構裡同時存在、各司其職。

## 面試回答方式

先講清楚熔斷器解決的核心問題——「呼叫故障或緩慢的下游服務，可能因為執行緒/連線資源被大量佔用而拖垮呼叫方自己，進而造成連鎖故障」，用「服務 A 呼叫變慢的服務 B，執行緒池被逾時等待耗盡」這種具體場景說明。接著詳細講出三種狀態的流轉邏輯——關閉(正常+監控)、開啟(跳閘+快速失敗+保護下游喘息)、半開(試探性放行少量請求判斷是否恢復)。如果能延伸區分「熔斷器 vs 逾時 vs 限流」各自解決的問題層次，展現你對服務韌性設計的整體圖像有清晰理解，而不只是孤立地知道熔斷器這一個模式。

## 常見追問

### 熔斷器判斷「失敗率超過門檻」時，怎麼定義「失敗」？網路逾時和伺服器回傳 500 錯誤，算不算同一種失敗？

**核心答案**：熔斷器的「失敗」判斷，通常需要**謹慎地區分「值得觸發熔斷的失敗」和「不該觸發熔斷的失敗」**——網路逾時、連線被拒絕、伺服器回傳 5xx 系列錯誤（代表伺服器端本身出了問題），這些通常應該被計入熔斷器的失敗統計;但如果下游服務回傳的是 4xx 系列錯誤(例如 400 請求格式錯誤、404 資源不存在)，這通常代表「呼叫方自己的請求有問題」，而不是「下游服務本身不健康」，不應該被計入熔斷器的失敗統計裡——因為即使下游服務目前完全健康，只要呼叫方持續發送格式錯誤的請求，一樣會收到大量 4xx 錯誤，如果這也被算進失敗率，會導致熔斷器因為呼叫方自己的程式錯誤而誤跳閘，錯誤地阻斷了原本健康、正常運作的下游服務。

**詳細解析**：這題考察對「失敗」這個看似直觀、實則需要仔細拆解的判斷標準的理解深度。熔斷器機制的核心目的，是「偵測下游服務本身是否健康」，如果把「所有非 2xx 的回應」都籠統地算作失敗，會混淆了兩種本質完全不同的情況——一種是「下游服務本身出了問題」(伺服器當機、資料庫連不上、處理邏輯拋出未預期的例外導致 500)，這種情況確實應該觸發熔斷器，因為不管呼叫方怎麼調整自己的請求內容，下游服務目前就是無法正常處理任何請求;另一種是「呼叫方自己的請求有問題」(格式錯誤、認證失敗、請求了不存在的資源)，這種情況下，下游服務其實運作得很正常(它正確地識別出了這是一個有問題的請求、並回應了恰當的錯誤)，問題出在呼叫方自己，如果因為這類「呼叫方自己的錯誤」而觸發熔斷器跳閘，會導致一個荒謬的結果——因為某個客戶端一直傳送格式錯誤的請求(可能是這個客戶端自己的程式 bug)，導致熔斷器誤判「下游服務不健康」而跳閘，阻斷了所有其他呼叫方(它們的請求原本完全正常)對這個健康服務的正常存取，這是一種因為判斷標準不精確而產生的「誤傷」。正確的設計原則是——熔斷器應該只針對「能夠反映下游服務本身健康狀況」的訊號(逾時、連線失敗、5xx 錯誤)進行統計和判斷，而把「4xx 這類反映呼叫方自身問題」的錯誤排除在熔斷判斷的失敗統計之外(這些錯誤依然應該被記錄、監控，甚至可能觸發其他機制，如「這個特定客戶端請求品質太差，考慮限流或封鎖它」，但不應該和「下游服務健康與否」這件事混為一談)。理解「熔斷判斷的失敗定義，需要精確地對應到『這個訊號是否真的反映下游服務不健康』這個核心問題，而不是簡單地把『任何不成功的回應』都一視同仁地算作失敗」，展現你對熔斷器的設計原理有更精細、更貼近實務的理解。

**面試回答方式**：先給出核心區分原則——「應該只計入『反映下游服務本身不健康』的訊號(逾時、連線失敗、5xx錯誤)，排除『反映呼叫方自己問題』的訊號(4xx錯誤)」。用具體例子說明為什麼——「如果把 4xx 也算進失敗率，某個客戶端自己程式有 bug 一直發送格式錯誤的請求，可能導致熔斷器誤判下游服務不健康而跳閘，連帶阻斷了其他呼叫方對這個其實運作正常的服務的存取」。展現你理解「失敗」這個判斷標準需要對應到「是否真的反映依賴服務的健康狀況」這個核心目的，而非籠統地把所有非成功回應都一視同仁。

### 半開狀態下，如果同時有多個請求湧入，熔斷器要怎麼控制「只放行少量試探性請求」，而不是讓所有請求一擁而上？

**核心答案**：常見的實作方式是讓熔斷器維護一個**計數器或信號量（Semaphore）機制**——進入半開狀態時，設定一個「這個狀態下最多允許幾個試探性請求通過」的上限（如 5 個），每當有請求嘗試通過時，先檢查目前已經放行的試探性請求數量是否已達上限，如果還沒達到上限，就放行這個請求並讓計數器加一(該請求成為一次試探);如果已經達到上限，後續湧入的其他請求就直接被視為「熔斷仍然開啟」而快速失敗(不會真的被送到下游服務)，避免在還不確定下游服務是否真的恢復的情況下，一次湧入過多真實流量，可能反而在下游服務剛從故障恢復、還很脆弱的狀態下，又把它壓垮一次。

**詳細解析**：這題深入半開狀態實作的併發控制細節，這是一個容易被簡化理解、但實務上需要仔細設計的環節。半開狀態存在的意義，正是要在「完全不給下游服務任何機會(繼續維持開啟狀態，錯過下游已經恢復的時機)」和「毫無保留地立刻恢復完全正常(萬一下游其實還沒真正恢復，一下子湧入大量真實流量，可能讓剛從故障中緩過氣來、資源還很緊繃的下游服務，再次被壓垮，形成一種『熔斷器不斷跳閘-半開-又被壓垮-再跳閘』的震盪循環)」這兩個極端之間，找到一個謹慎、漸進的中間地帶——只放行「少量」試探性請求，用這一小撮請求的結果，作為「判斷是否應該恢復完全正常」的依據，如果這一小撮試探成功了，才有信心讓熔斷器完全轉回關閉狀態、開始正常轉發所有流量。要讓「只放行少量」這件事在高併發情境下真正被正確執行，需要一個能夠在多個並行執行緒(或多個處理請求的協程/事件迴圈)之間，正確協調「目前已經放行了幾個試探請求」這個共享狀態的機制——如果沒有適當的併發控制(例如簡單地用一個沒有加鎖保護的計數器變數，在多執行緒環境下可能出現競態條件，導致實際放行的試探請求數量，超過原本設計的上限)，可能在高併發流量湧入的瞬間，半開狀態「名不符實」地放行了遠超過預期數量的真實請求，這樣就完全違背了半開狀態「謹慎試探」的設計初衷。因此，正確的實作通常需要用具備原子性保證的計數機制(如信號量 Semaphore，或搭配鎖保護的計數器)，確保「檢查目前已放行數量是否達到上限」和「放行這個請求並讓計數器加一」這兩個動作，在併發情境下依然能被正確、原子性地執行，真正做到「只放行約定數量的試探性請求，其餘一律視為熔斷仍開啟」。

**面試回答方式**：給出核心機制——「用計數器或信號量，限制半開狀態下最多放行的試探性請求數量(如5個)，超過這個數量的請求視為熔斷仍開啟、直接快速失敗」。解釋設計動機——「半開狀態是在『完全不給機會』和『一次恢復全部流量，萬一下游還沒真正恢復可能再次壓垮它』之間的謹慎中間地帶，用少量試探結果決定是否完全恢復」。可以補充「這個計數機制在高併發下需要具備原子性保證(如用信號量)，否則沒有正確併發控制的簡單計數器，可能在高併發瞬間讓實際放行的試探請求數超過預期上限，違背半開狀態的設計初衷」。展現你理解半開狀態不只是一個抽象概念，還考慮到高併發下正確實作這個「謹慎放行」機制所需的併發控制細節。

### 如果一個服務同時依賴多個不同的下游服務(比如同時呼叫服務 B 和服務 C)，應該對每個依賴各自設置獨立的熔斷器，還是共用一個？

**核心答案**：應該對**每一個不同的下游依賴，各自設置獨立的熔斷器**,而不是共用一個。因為熔斷器的核心目的，是要精確地反映「某一個特定依賴目前是否健康」，如果多個不同的下游依賴共用同一個熔斷器，會導致「服務 B 故障，但因為和服務 C 共用同一個熔斷器，連帶讓對服務 C 的呼叫也被誤判為『不健康』而跳閘」——即使服務 C 本身其實運作得完全正常，這種「一個依賴出問題，拖累了其他完全不相關的健康依賴」的現象，恰恰是熔斷器原本想要防止的「連鎖故障」的一種變形，只是這次連鎖故障是因為熔斷器本身的粒度設計錯誤而造成的。

**詳細解析**：這題考察對熔斷器「粒度（Granularity）」設計原則的理解——熔斷器要發揮正確的保護作用，前提是它所監控和保護的「範圍」，必須精確對應到「一個獨立的、可能各自獨立故障的依賴單位」。如果把對服務 B 和服務 C 的呼叫，混在同一個熔斷器裡統計失敗率，會產生一個邏輯上的謬誤——熔斷器統計出來的「失敗率」，其實是「呼叫服務 B 的失敗次數」和「呼叫服務 C 的失敗次數」混合在一起計算的結果，這個混合後的數字，已經不再能準確代表「服務 B 本身是否健康」或「服務 C 本身是否健康」這兩個各自獨立的問題——想像一個極端情境:服務 B 完全故障(每次呼叫都失敗)、服務 C 完全健康(每次呼叫都成功)，如果共用熔斷器，混合統計出來的失敗率可能剛好落在門檻邊緣(取決於呼叫服務 B 和服務 C 的請求比例)，即使真的觸發了跳閘，跳閘之後「所有」發往這個共用熔斷器所覆蓋範圍的請求都會被拒絕，這意味著明明運作正常的服務 C，也會因為服務 B 的故障而被無辜地阻斷，這完全違背了熔斷器「精確定位問題依賴、只針對這個有問題的依賴進行保護性隔離，而不影響其他健康依賴」的設計初衷。正確的做法是——每一個外部依賴(不管是不同的微服務、還是同一個服務但呼叫其中不同的、可能有各自獨立故障模式的 API 端點)，都應該有屬於自己的、獨立的熔斷器實例，各自獨立地追蹤各自的失敗率、各自獨立地決定是否跳閘、各自獨立地經歷開啟-半開-關閉的狀態流轉，這樣才能確保「熔斷器的保護範圍，精確地對應到每一個獨立可能故障的依賴，一個依賴的故障，只會影響到『呼叫這個特定依賴』的部分，不會殃及其他完全不相關的健康依賴」。這個「按依賴粒度獨立設置熔斷器」的原則，也呼應了微服務架構裡「艙壁隔離模式(Bulkhead Pattern，見 [[019-bulkhead-pattern.md]])」的核心思想——把不同的資源和故障域（Failure Domain）彼此隔離，避免一個地方的問題，擴散影響到其他本來不相關的地方。

**面試回答方式**：明確給出答案——「應該各自獨立設置，不應該共用」。用具體反例說明共用的問題——「如果服務 B 故障、服務 C 健康，但共用同一個熔斷器，混合統計的失敗率可能觸發跳閘，導致明明運作正常的服務 C 也被無辜阻斷，這違背了熔斷器『精確定位問題依賴、只隔離有問題的部分』的設計初衷」。可以延伸連結「艙壁隔離模式」的概念——「這其實呼應了艙壁隔離的核心思想，把不同的故障域彼此隔離，避免一個地方的問題擴散影響到其他不相關的地方」。展現你理解熔斷器的「粒度」設計和它要精確對應到獨立故障單位這個重要原則。
