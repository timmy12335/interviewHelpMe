# 題目

JSON、Protobuf、Avro 該怎麼選？序列化格式的選擇影響什麼？

## 核心答案

三者的定位不同。**JSON**——**人可讀、無需 schema、生態最廣**，代價是體積大（欄位名重複出現在每筆資料裡）、解析慢、**且沒有型別保證**（數字精度、日期格式都靠約定）。**Protobuf**——**有 schema、二進位、體積小、解析快、跨語言的程式碼生成**，代價是需要 schema 檔案與生成流程、除錯時不可讀。**Avro**——**schema 隨資料一起或存在 registry**，**特別適合資料管線與長期儲存**，因為它的 schema 演進規則明確且支援讀寫 schema 不同的情況。

**選型的核心問題是「這個介面的使用者是誰」**。**對外的 API 用 JSON**（客戶端多樣、可讀性與生態的價值高於效能）；**內部服務之間用 Protobuf**（效能與型別安全的價值高於可讀性，而且雙方都在你的控制下）；**資料管線與事件流用 Avro 或 Protobuf**（schema 演進與長期相容性是核心需求）。

**最重要的判斷是「有沒有 schema」而非「二進位還是文字」**——schema 帶來的型別安全、程式碼生成、與相容性檢查，比體積與速度更有長期價值。

## 詳細解析

**「有 schema」的實質價值有四項**。**編譯期的型別安全**——欄位名打錯在生成程式碼時就發現，而不是執行期拿到 null。**自動生成的客戶端**——不必手寫序列化與反序列化，跨語言時尤其省事。**相容性檢查可以自動化**——`buf breaking` 這類工具能在 CI 中檢查「這個變更會不會破壞既有的客戶端」。**契約成為權威**——schema 檔案本身就是文件，而且它與實作不會不同步。**這四項的價值隨團隊規模與服務數量放大**，在單一服務的小專案上則不明顯。

**Protobuf 的相容性規則值得理解**。**欄位由編號識別而非名稱**——所以**重新命名欄位是相容的**（編號不變），**而改變編號或型別是破壞性的**。**新增欄位是相容的**（舊的解析器忽略未知欄位），**刪除欄位要保留編號**（用 `reserved` 標記，防止之後被重用而造成資料誤讀）。**這套規則讓「什麼是安全的變更」變得明確且可以被工具檢查**——相比之下 JSON 的相容性完全靠約定與人工判斷。

**JSON 的隱藏成本常被低估**。**數字的精度**——JavaScript 的 `Number` 是雙精度浮點，**超過 2 的 53 次方的整數會失去精度**，所以大的 ID 應該用字串傳輸（這是一個很常見的踩坑）。**日期格式沒有標準**——ISO 8601 是慣例但不是強制，而時區的表達方式多樣。**欄位名的重複**——一個有一百萬筆記錄的回應，每筆都帶著完整的欄位名，**體積可能是二進位格式的三到五倍**。**這些在小規模時無所謂，在大規模時是真實的成本。**

**格式的選擇會被生態鎖定**。用了 gRPC 就基本上是 Protobuf；用了 Kafka 加 Schema Registry 通常是 Avro；用了 GraphQL 則是 JSON。**所以「選格式」往往不是一個獨立的決定，而是「選框架」的附帶結果**——**認清這一點能讓討論回到真正的決定點上**（該不該用 gRPC、該不該引入 Schema Registry），而不是在格式本身打轉。

## 面試回答方式

先給三者的定位與各自的代價。給選型的核心問題：**這個介面的使用者是誰**——對外用 JSON、內部用 Protobuf、資料管線用 Avro 或 Protobuf。給最重要的判斷：**「有沒有 schema」比「二進位還是文字」更重要**，並展開 schema 的**四項實質價值**（編譯期型別安全、自動生成客戶端、相容性檢查可自動化、契約成為權威）。加分點有三個：**Protobuf 的欄位由編號識別**，所以重新命名相容而改編號破壞，**刪除欄位要用 `reserved` 保留編號防止之後被重用造成資料誤讀**；**JSON 的數字精度問題**——超過 2 的 53 次方的整數在 JavaScript 會失去精度，**所以大的 ID 應該用字串傳輸**；以及**格式的選擇往往是「選框架」的附帶結果**，認清這點能讓討論回到真正的決定點。

## 講稿

三者的定位不同。JSON 人可讀、無需 schema、生態最廣，代價是體積大跟沒有型別保證。Protobuf 有 schema、二進位、可以跨語言生成程式碼，代價是需要生成流程。Avro 則特別適合資料管線與長期儲存。

選型的核心問題是這個介面的使用者是誰。對外的 API 用 JSON，因為客戶端多樣。內部服務之間用 Protobuf，因為雙方都在你的控制下。資料管線用 Avro 或 Protobuf。

我認為最重要的判斷是有沒有 schema，而不是二進位還是文字。schema 帶來的型別安全、程式碼生成、跟相容性檢查，比體積與速度更有長期價值。

Protobuf 的相容性規則值得知道。欄位由編號識別而不是名稱，所以重新命名是相容的，改編號或型別則是破壞性的。刪除欄位要用保留標記把編號留住，防止之後被重用而造成資料誤讀。

還有一個常見的踩坑。JSON 的數字在 JavaScript 是雙精度浮點，超過二的五十三次方的整數會失去精度，所以大的 ID 應該用字串傳輸。

## 常見追問

### Schema Registry 解決什麼問題？

**核心答案**：解決**「生產者與消費者的 schema 版本不一致」**。在 Kafka 這類的場景中，**訊息可能被幾天甚至幾個月後才消費**——那時生產者的 schema 可能已經演進了。Schema Registry 讓每筆訊息帶著一個 schema ID（而非完整的 schema，省空間），**消費者用 ID 查出寫入時的 schema，再與自己的讀取 schema 做相容的轉換**。

**詳細解析**：**它還提供了「相容性檢查的強制執行點」**——註冊新版本的 schema 時，registry 會依配置的相容性模式（`BACKWARD`、`FORWARD`、`FULL`）檢查它與既有版本是否相容，**不相容就拒絕註冊**。**這把「不要做破壞性變更」從一個口頭約定變成了一個系統強制的規則。** **選擇哪種相容性模式取決於部署順序**：`BACKWARD`（新的讀取 schema 能讀舊資料）適合「先升級消費者」；`FORWARD`（舊的讀取 schema 能讀新資料）適合「先升級生產者」。**很多團隊沒有明確想過這個順序，於是選了預設值然後在某次部署時被擋住**——**而那個「被擋住」其實是系統在保護你**。

**面試回答方式**：給它解決的核心問題（訊息可能幾個月後才消費、那時 schema 已演進）與機制（帶 schema ID、消費者查出寫入 schema 做轉換）。真正的加分點是**它提供了相容性檢查的強制執行點**——把「不要做破壞性變更」從口頭約定變成系統強制的規則。展開**相容性模式的選擇取決於部署順序**（BACKWARD 適合先升消費者、FORWARD 適合先升生產者），並指出**很多團隊沒明確想過就選了預設然後被擋住，而那個「被擋住」其實是系統在保護你**。

### gRPC 與 REST 在實務上怎麼選？

**核心答案**：**看邊界的性質**。**對外的公開 API 用 REST 加 JSON**——瀏覽器、各種客戶端、以及第三方整合的生態都建立在 HTTP 加 JSON 上，gRPC 在瀏覽器需要 grpc-web 加代理，摩擦明顯。**內部服務之間用 gRPC**——強型別、程式碼生成、串流支援、以及內建的 deadline 傳遞都是實質的收益。**混合是常態**：閘道對外用 REST、對內轉成 gRPC。

**詳細解析**：**gRPC 內建的能力常被低估**：**deadline 傳遞**（前面談過的截止時間傳遞，gRPC 是免費的）、**串流**（雙向串流讓某些場景不必用 WebSocket）、**攔截器**（統一處理認證、追蹤、重試）、以及**負載平衡的整合**（客戶端側的負載平衡，避免 L4 負載平衡對長連線的不均衡問題）。**最後一項在 HTTP/2 的環境下特別重要**——因為 HTTP/2 的多工讓一條連線承載大量請求，**傳統的 L4 負載平衡會讓某個後端持續收到同一條連線的所有流量**。**這個問題在從 HTTP/1.1 遷移到 gRPC 時經常出現，而它的表現是「負載明顯不均」**——認出它就知道需要客戶端側的負載平衡或者一個懂 gRPC 的代理。

**面試回答方式**：給判準（對外 REST、對內 gRPC、混合是常態）。真正的加分點是列出 **gRPC 內建但常被低估的能力**（deadline 傳遞、串流、攔截器、客戶端側負載平衡），並展開最後一項：**HTTP/2 的多工讓一條連線承載大量請求，傳統 L4 負載平衡會讓某個後端持續收到同一條連線的所有流量**——**這在遷移到 gRPC 時經常出現，表現是負載明顯不均**，認出它就知道需要客戶端側負載平衡或懂 gRPC 的代理。

### 序列化的效能什麼時候真的重要？

**核心答案**：三種情況。**訊息量極大**（每秒數十萬筆的事件流，序列化的 CPU 佔比可觀）。**訊息體積大**（大的 payload 讓網路頻寬成為瓶頸，而二進位格式可能小三到五倍）。**延遲極度敏感**（微秒級的場景，JSON 的解析可能佔了可觀的比例）。**其餘情況下，序列化的成本相對於網路往返與業務處理是微不足道的**——**在那些場景下選 JSON 的可讀性優勢通常更有價值**。

**詳細解析**：**一個常見的誤判是「因為聽說 Protobuf 比較快所以用它」，而實際的瓶頸在別處**。**判斷的方式是量測**：一次呼叫的總延遲中，序列化與反序列化佔了多少？**如果是 1%，那把它優化到零也只省 1%。** **而選 Protobuf 的真正理由通常不是效能，是 schema 帶來的型別安全與相容性檢查**——**把理由說對很重要**，因為它決定了「什麼情況下這個選擇仍然成立」。**用效能當理由的話，一旦有人量測發現效能差別不大，這個選擇就失去了依據**；**用型別安全當理由則不會**。**這是一個「把決定建立在正確的理由上」的例子**，而它影響的是決定的穩定性與可辯護性。

**面試回答方式**：給三種真的重要的情況並指出**其餘情況下序列化成本相對於網路往返與業務處理微不足道**。真正的加分點是點出常見誤判（因為聽說快所以用）與判斷方式（量測序列化在總延遲中的佔比）。收在一個重要的觀點：**選 Protobuf 的真正理由通常不是效能而是 schema 帶來的型別安全與相容性檢查**——**把理由說對很重要**，因為用效能當理由的話，一旦有人量測發現差別不大這個選擇就失去依據。
