# 題目

微服務架構中，「服務發現（Service Discovery）」解決什麼問題？客戶端發現（Client-Side Discovery）和伺服器端發現（Server-Side Discovery）有什麼差異？

## 核心答案

在微服務架構下，每個服務通常有多個實例（Instance），且這些實例的網路位置（IP、Port）會因為擴縮容、部署更新、故障重啟而**動態變化**——服務發現機制解決的核心問題是「一個服務（呼叫方）要呼叫另一個服務時，怎麼知道『目前應該連到哪個具體的網路位置』，而不需要在程式碼裡寫死固定的 IP」。核心組成是一個**服務註冊中心（Service Registry）**——每個服務實例啟動時,向註冊中心「註冊」自己目前的網路位置(並定期發送心跳證明自己還活著),呼叫方需要呼叫某個服務時,先向註冊中心「查詢」這個服務目前有哪些健康的實例,再從中選一個發起實際呼叫。**客戶端發現**：呼叫方自己（或呼叫方旁邊的一個輔助元件）直接查詢註冊中心，取得可用實例清單，並自己執行負載平衡邏輯選一個實例呼叫，服務註冊中心之外不需要額外的中間層。**伺服器端發現**：呼叫方只需要呼叫一個固定的位址（如負載平衡器或 API 閘道），由這個中間層負責查詢註冊中心並把請求轉發到實際的服務實例，呼叫方完全不需要知道服務發現的細節。

## 詳細解析

**服務發現要解決的根本問題**：在傳統的單體應用或少數幾個固定伺服器的架構下，服務之間的網路位置通常是相對穩定的，可以直接把 IP 或主機名寫死在設定檔裡；但在微服務架構,尤其是搭配容器化和自動擴縮容（如 Kubernetes）的環境下，一個服務可能同時有幾十個實例在運作，這些實例會因為「自動擴容(流量增加,啟動更多實例)」、「自動縮容(流量減少,關閉部分實例)」、「滾動更新部署(逐步替換成新版本的實例)」、「實例故障被自動重啟」等原因，**網路位置持續、頻繁地變動**，如果還是依賴「寫死 IP」這種靜態的方式，服務之間幾乎不可能正常協作(隨時可能呼叫到一個已經不存在或已經被替換的舊實例)，服務發現機制正是為了讓「呼叫方永遠能找到目前健康且正確的服務實例」這件事,能夠自動化、動態地被處理，不需要人工介入去維護和更新這些位址資訊。

**客戶端發現（Client-Side Discovery）的運作方式與優缺點**：呼叫方（或一個和呼叫方同進程/同主機運行的輔助元件，如 Sidecar）在發起呼叫前，主動去查詢服務註冊中心（如 Eureka、Consul），取得「目前這個目標服務有哪些健康的實例」清單，然後由呼叫方自己（依照某種負載平衡策略，如輪詢、隨機、依回應時間加權）從中選一個實例，直接發起呼叫。**優點**是「架構相對簡單，少了一層額外的網路跳轉（呼叫方直接連到目標實例，沒有經過額外的中間代理）,延遲相對較低」；**缺點**是「服務發現的邏輯（查詢註冊中心、負載平衡演算法）需要在每一個呼叫方的程式碼裡實作或依賴一個共用的客戶端函式庫,如果系統用多種不同的程式語言開發,每種語言都需要各自實作或維護對應的服務發現客戶端邏輯,增加了跨語言協作的複雜度」。

**伺服器端發現（Server-Side Discovery）的運作方式與優缺點**：呼叫方完全不需要知道服務發現的存在，只需要把請求發往一個固定、穩定的位址（例如一個負載平衡器,或在 Kubernetes 中,一個穩定的 Service 名稱），由這個中間層（負載平衡器或 API 閘道）負責「查詢服務註冊中心、選擇一個健康的實例、把請求轉發過去」這整個服務發現的邏輯,對呼叫方而言完全透明。**優點**是「服務發現的邏輯集中在一個地方(中間層)實作和維護,呼叫方的程式碼完全不需要關心服務發現的細節,天然對多語言環境友善」；**缺點**是「多了一層額外的網路跳轉（呼叫方 → 負載平衡層 → 實際服務實例）,增加了一點延遲,且這個中間層本身需要有良好的高可用性設計(它如果掛了,會影響所有經過它的呼叫)」。**Kubernetes 的 Service 機制**是伺服器端發現的一個典型例子——`kube-proxy` 在每個節點上維護網路規則，讓呼叫方只需要呼叫一個穩定的 Service 名稱/虛擬 IP，實際的流量會被自動轉發到後面某個健康的 Pod 實例，呼叫方完全不需要感知底層 Pod 的動態變化。

**心跳與健康檢查**：服務發現機制要真正可靠，除了「註冊」之外，還需要持續的**健康檢查（Health Check）** 機制——服務實例需要定期向註冊中心發送「心跳」證明自己還活著且健康,如果某個實例在一段時間內沒有發送心跳（可能是當機、網路中斷、或處理過載無法正常回應）,註冊中心應該把這個實例從「可用清單」裡剔除，避免呼叫方繼續把流量導向一個已經不健康的實例。這通常搭配「主動健康檢查（註冊中心或負載平衡器主動去 ping/呼叫服務實例的健康檢查端點）」和「被動健康檢查（觀察實際請求的成功/失敗情況,動態調整）」兩種方式共同運作，確保「可用實例清單」盡量貼近實際情況。

## 面試回答方式

先講清楚服務發現解決的核心問題——「微服務實例的網路位置動態變化(擴縮容、部署更新、故障重啟),呼叫方不能依賴寫死的 IP,需要一個機制動態找到目前健康的實例」。介紹服務註冊中心的核心角色(實例註冊+心跳+查詢)。接著對比客戶端發現和伺服器端發現的具體運作方式和優缺點——客戶端發現(呼叫方自己查詢並選擇,少一層跳轉但每種語言都要實作服務發現邏輯) vs 伺服器端發現(呼叫方對服務發現無感知,邏輯集中在中間層,但多一層網路跳轉)。可以用 Kubernetes Service 作為伺服器端發現的具體實例。展現你不只知道「有服務發現這個東西」,還理解兩種模式各自的架構取捨。

## 常見追問

### 服務發現機制本身(服務註冊中心)如果掛了,會發生什麼事?這個註冊中心自己要怎麼設計才能有高可用性?

**核心答案**：如果服務註冊中心完全掛掉,理論上會影響「新的服務發現查詢」和「新實例的註冊」,但多數成熟的服務發現客戶端實作,都會在本地**快取上一次查詢到的可用實例清單**,即使註冊中心暫時無法連線,呼叫方依然可以憑藉本地快取的清單繼續運作(只是這份清單可能不是最新的,例如某個實例其實已經下線了,但因為快取還沒更新,呼叫方可能還會嘗試呼叫到它,這時候需要靠呼叫方自己的重試和熔斷機制來處理這種暫時性的不一致)。註冊中心本身的高可用性設計,通常採用**多節點叢集部署**,搭配像 Raft 或 Paxos 這類分散式共識演算法(如 Consul、etcd 底層都使用 Raft)來確保即使叢集中的部分節點故障,整個註冊中心叢集依然能持續正常運作、維持資料一致性。

**詳細解析**：這題考察對「基礎設施元件本身也需要高可用設計」這個容易被忽略的問題的認識——服務發現機制的目的,是要提升整體系統的韌性(讓服務呼叫能動態適應實例變化),但如果實現這個目的的元件(註冊中心)本身是一個單點故障(Single Point of Failure),那麼「服務發現」反而可能成為整個系統最脆弱的環節,一旦註冊中心掛了,理論上所有依賴它的服務呼叫都可能受影響。「本地快取」是緩解這個問題的第一道防線——大多數服務發現客戶端(不管是客戶端發現模式下,呼叫方直接整合的客戶端函式庫,還是伺服器端發現模式下,負載平衡層內部維護的清單),都不會每次呼叫都即時去問註冊中心,而是定期(例如每隔幾秒到幾十秒)拉取一次最新的可用實例清單,並在本地記憶體快取起來,實際發起呼叫時,直接使用這份本地快取的清單,不需要每次都即時查詢註冊中心,這樣一來,即使註冊中心短暫地不可用,呼叫方依然能憑藉快取繼續正常運作一段時間(當然,這份快取會漸漸「過時」,如果註冊中心持續長時間不可用,快取裡的資訊和實際情況的落差會越來越大,這是一個需要權衡的風險,但至少提供了短暫故障的緩衝能力)。而註冊中心本身的高可用設計,則回歸到經典的分散式系統高可用模式——**不依賴單一節點,而是部署一個由多個節點組成的叢集**,並透過像 Raft 這樣的共識演算法,讓叢集中的節點對「目前有哪些服務實例、它們的健康狀態」這份資料,維持一致的認知,即使叢集中一部分節點(通常是少數,例如 5 個節點中的 2 個)發生故障,只要還有超過半數的節點正常運作,整個叢集依然能持續對外提供服務、正確地處理新的註冊和查詢請求,不會因為單一節點的故障而導致整個服務發現機制癱瘓。理解「服務發現的可靠性,建立在『客戶端本地快取提供的短期緩衝』和『註冊中心本身透過分散式共識演算法達成的叢集高可用』這兩層防護之上」,展現你理解基礎設施元件本身也需要被納入高可用設計的考量範圍,而不是想當然地認為它「理所當然一直都在」。

**面試回答方式**：先講「客戶端本地快取」這第一道防線——「大多數服務發現客戶端會定期拉取並在本地快取可用實例清單,即使註冊中心短暫不可用,呼叫方依然能憑藉快取繼續運作一段時間,只是快取會漸漸過時」。再講「註冊中心自身的高可用設計」——「透過多節點叢集部署,搭配 Raft/Paxos 這類分散式共識演算法(如 Consul、etcd),即使部分節點故障,只要還有超過半數節點正常,整個叢集依然能持續正確運作」。展現你認識到「服務發現機制本身也是一個需要被納入高可用設計考量的基礎設施元件」,而非想當然地認為它不會出問題。

### 客戶端發現模式下,如果系統用多種程式語言開發(如 Java、Go、Python 各自開發不同的服務),每種語言都要各自實作服務發現和負載平衡邏輯,這個問題有沒有更好的解法？

**核心答案**：業界常見的解法是引入 **Service Mesh（服務網格，見 [[024-service-mesh.md]]）架構**,透過在每個服務實例旁邊部署一個獨立的**Sidecar 代理**（如 Envoy），把「服務發現、負載平衡、重試、熔斷」這些跨語言共通的網路通訊邏輯，統一下沉到這個和程式語言無關的 Sidecar 代理裡實作,應用程式本身（不管用什麼語言寫）只需要單純地和「本地的 Sidecar 代理」溝通(通常是呼叫 localhost 上的一個固定埠),完全不需要在應用程式碼裡整合任何服務發現的客戶端函式庫,實際的服務發現、負載平衡邏輯都由 Sidecar 代理透明地處理,這樣就從根本上解決了「每種程式語言都要各自實作一套服務發現邏輯」的重複勞動問題。

**詳細解析**：這題延伸到「客戶端發現模式在多語言環境下的痛點,以及 Service Mesh 這個架構如何系統性地解決這個問題」，是一個承先啟後、串聯到更進階架構主題的追問。客戶端發現模式的核心痛點,正是「服務發現的邏輯（如何查詢註冊中心、怎麼做負載平衡、失敗時怎麼重試）,需要被實作在『呼叫方的程式碼』裡」,如果一個組織的技術棧是多語言的（例如核心交易系統用 Java、資料處理管線用 Python、某些高效能元件用 Go），要嘛每種語言都要各自維護一套功能相當、但用不同語言實作的服務發現客戶端函式庫(重複開發、且不同語言版本之間的功能可能不一致、修 bug 或加新功能時要在好幾個地方分別處理),要嘛只能依賴少數幾種「有現成客戶端函式庫」的語言,限制了技術選型的彈性。Service Mesh 架構的核心洞察,是把「服務間通訊」這件事,徹底從「應用程式業務邏輯」中剝離出來，變成一個獨立的、與程式語言無關的**基礎設施層**——具體做法是,在每一個服務實例旁邊(通常是同一個 Pod 內,以容器的形式),額外部署一個「Sidecar 代理」，應用程式本身完全不直接和其他服務通訊，而是把所有要發出的請求，都先發給「自己旁邊的這個 Sidecar 代理」(透過 localhost，幾乎沒有額外的網路延遲)，由這個 Sidecar 代理去處理「這個請求實際上應該被路由到哪個服務實例(服務發現)、用什麼策略做負載平衡、如果失敗了要不要重試、要不要因為多次失敗而觸發熔斷」這一整套跨語言共通的邏輯,應用程式的開發者完全不需要在自己的程式碼裡處理這些事情，也感受不到底層服務發現機制的存在，不管這個應用程式是用 Java、Go、還是 Python 寫的，只要它能發出一個普通的網路請求給 localhost 上的 Sidecar，就能自動享有完整的服務發現、負載平衡、重試熔斷等能力，這些能力的實作和維護,全部集中在 Sidecar 代理這一個(語言無關的)地方，徹底終結了「每種程式語言各自重複實作一套服務發現邏輯」的問題。理解「Service Mesh 本質上是把客戶端發現模式裡『分散在每個呼叫方程式碼裡』的服務發現邏輯，統一下沉、集中到一個獨立於應用程式語言的 Sidecar 代理層」，展現你能看到從「客戶端發現的痛點」演化到「Service Mesh 這個更進階架構方案」背後的邏輯脈絡。

**面試回答方式**：直接給出解法——「引入 Service Mesh 架構,透過 Sidecar 代理把服務發現、負載平衡等邏輯統一下沉到一個和程式語言無關的獨立層」。解釋運作方式——「每個服務實例旁邊部署一個 Sidecar(如 Envoy),應用程式只需要單純地呼叫本地的 Sidecar(localhost),不需要在自己的程式碼裡整合任何服務發現客戶端函式庫,實際的服務發現、負載平衡、重試熔斷邏輯全部由 Sidecar 透明處理」。點出核心價值——「這從根本上終結了『每種程式語言各自重複實作一套服務發現邏輯』的問題,不管應用程式用什麼語言寫,都能透過和 Sidecar 溝通,自動享有完整的服務治理能力」。展現你能看到從客戶端發現的多語言痛點,自然演進到 Service Mesh 這個更進階架構方案的邏輯脈絡。

### 註冊中心裡的「健康檢查」,如果只是簡單地檢查「這個服務實例的連接埠有沒有開著(TCP 連線是否能建立)」，這樣夠嗎？有什麼更完善的健康檢查方式？

**核心答案**：單純檢查「連接埠是否能建立 TCP 連線」是不夠的,因為即使 TCP 連線能夠建立(代表這個服務的程序還活著、監聽埠還開著),這個服務實例的**內部邏輯可能已經處於不健康的狀態**（例如它依賴的資料庫連線池已經耗盡、記憶體幾乎滿了導致大部分請求都會失敗、或某個關鍵的初始化步驟還沒完成),這種情況下,雖然 TCP 層面連線正常,但這個實例實際上完全無法正常處理業務請求。更完善的健康檢查方式是**應用層級的健康檢查**——服務自己提供一個專門的健康檢查端點（如 `GET /health` 或 `/actuator/health`），這個端點的邏輯裡,實際去檢查「這個服務所依賴的關鍵資源（資料庫連線、快取連線、關鍵的下游依賴）目前是否都正常」，只有當這些依賴都健康時，才回傳「健康」的結果，讓註冊中心（或負載平衡器）依據這個更貼近「這個實例是否真的能正常服務」的判斷結果，決定是否把它留在可用清單裡。

**詳細解析**：這題深入健康檢查的「深度」問題——區分「這個程序還活著（Liveness）」和「這個程序目前是否真的能正常服務（Readiness）」這兩個容易被混淆、但意義完全不同的健康狀態。單純的 TCP 連線檢查，本質上只回答了一個很淺層的問題——「這個埠有沒有被監聽、作業系統層面的網路堆疊是否正常回應」，這確實能過濾掉「程序整個當機、伺服器完全沒有回應」這種最嚴重的故障情況，但完全無法偵測到「程序本身還在運行、埠也還開著,但因為某些內部狀態異常(如連不上資料庫、記憶體耗盡、某個關鍵的背景執行緒卡死),導致這個實例實際上已經沒有能力正常處理大部分業務請求」的情況——這類問題如果沒有被健康檢查機制正確偵測到，會導致「明明這個實例已經名存實亡（收到請求也只會失敗或逾時），但因為它在 TCP 層面看起來活著，註冊中心依然把它列為『可用』，持續有流量被導向這個實際上不健康的實例，使用者持續遇到失敗的請求」，這正是為什麼需要**應用層級的健康檢查**——讓服務自己主動地、有能力地去檢查「我依賴的關鍵資源，現在到底健不健康」，並誠實地把這個判斷結果，透過一個標準化的健康檢查端點，回報給外部的監控和服務發現機制。這也是 Kubernetes 裡「Liveness Probe（存活探測，用來判斷『這個容器是否需要被重啟』，檢查得比較粗淺，通常只確認程序沒有卡死）」和「Readiness Probe（就緒探測，用來判斷『這個容器目前是否應該接收流量』，檢查得比較深入,通常會涉及依賴資源的健康狀況)」這兩種探測機制分開設計的原因——它們回答的是不同層次的問題：Liveness 回答「要不要重啟這個容器」，Readiness 回答「現在該不該把流量導向這個容器」，一個實例完全可能「還活著（不需要重啟）」但「目前還沒準備好接收流量（例如啟動初期,還在做一些初始化，還沒連上資料庫）」，如果不區分這兩種探測，可能會出現「因為某個依賴暫時不可用而錯誤地重啟了本來運作正常的程序（浪費資源、且重啟本身也需要時間,可能讓故障持續更久）」，或者反過來「明明服務內部狀態已經不健康、無法正常服務,卻因為只做了淺層的存活檢查而繼續讓它接收流量」這些不同性質的問題。

**面試回答方式**：先指出淺層 TCP 檢查的不足——「只能偵測『程序整個當機』這種最嚴重的故障,無法偵測『程序還活著但內部依賴(資料庫連線、記憶體)已經不健康,導致實際上無法正常處理請求』的情況」。給出更完善的做法——「應用層級的健康檢查端點,由服務自己主動檢查關鍵依賴資源的健康狀況,誠實地回報是否真的準備好接收流量」。可以延伸連結 Kubernetes 的 Liveness Probe(決定要不要重啟) 和 Readiness Probe(決定要不要導流量)這兩種不同層次探測的區分,展現你理解「存活」和「就緒」是兩個需要分開判斷的不同問題。
