# 題目

回顧後端工程的各種技術，你認為系統的複雜度主要來自哪裡？

## 核心答案

主要來自三個地方，而它們的順序很重要。

**第一是狀態**。無狀態的運算容易理解、容易測試、容易水平擴展；複雜度幾乎全部集中在「有東西必須被記住」的地方——資料庫、快取、佇列、會話、以及分散在多處的同一份資料。一致性、失效、順序、重複——這些問題全都是狀態的問題。

**第二是分散**。一旦跨越行程邊界，「呼叫」就從二元的成功失敗變成三態：成功、失敗、以及**不知道**。冪等、重試、逾時、補償、追蹤——這些機制全部是為了處理那個「不知道」。

**第三是變更**。系統不是被建造出來就結束，它持續被修改——而多數的複雜度預算實際上花在「如何在不停機、不破壞相容性的前提下改變一個運行中的系統」：擴充收縮式遷移、版本化的 API、功能旗標、金絲雀。

而好的工程判斷，多半是在做「把複雜度放在哪裡」的選擇，而不是消除它。

## 詳細解析

**這三者會相乘而非相加**。有狀態 + 分散 = 分散式資料的一致性問題（這是後端最難的一類問題）。分散 + 變更 = 相容性與部署順序問題（你無法同時更新所有節點）。**有狀態 + 變更 = 資料遷移問題**（schema 改了，但舊資料還在）。三者俱全就是「線上系統的分散式資料遷移」——而那正是實務上最容易出事、最需要謹慎設計的場景。這也解釋了為什麼「無狀態的服務 + 集中的狀態」是一個如此常見的架構：它把三者相乘的區域壓縮到最小。

「消除複雜度」多數時候是幻覺，真正在做的是搬移。加一層快取，是把「查詢慢」的複雜度換成「失效與一致性」的複雜度。改成非同步，是把「回應慢」換成「順序、重複、與失敗處理」。拆微服務，是把「程式碼耦合」換成「網路與部署協調」。這不是說這些選擇是錯的——它們常常是對的——而是說「評估一個方案時要問它把複雜度搬到哪裡去了，以及那個位置是不是我們更能承受的」。 只計算收益不計算搬移成本，是架構決策最常見的錯誤。

最好的複雜度管理往往是「不要製造它」。能用一個資料庫解決的就不要用三個；**能同步的就不要非同步**；**能不快取的就不要快取**；**能不拆的就不要拆**。這聽起來保守，但它的理由是精確的：每一個被引入的元件都帶來它自己的失效模式、監控需求、以及運維負擔——而那些成本會持續存在，直到系統退役為止。引入的門檻應該是「現在的問題已經確實痛到值得那些成本」，而不是「未來可能會需要」。

**而「判斷力」正是這一切的核心**。技術知識告訴你有哪些選項與它們怎麼運作；判斷力告訴你在這個具體的情境下該選哪一個，以及什麼時候該選「都不要」。面試中真正有區辨力的問題幾乎都在問後者——而那也是為什麼「說得出取捨與失敗模式」比「說得出定義」更能證明能力。

## 面試回答方式

給三個來源並強調**順序**：**狀態**（一致性、失效、順序、重複全都是狀態的問題）、**分散**（呼叫從二元變三態，多了「不知道」，而冪等重試逾時補償全是為了處理它）、**變更**（多數複雜度預算花在「如何改變一個運行中的系統」）。加分點有三個：**三者相乘而非相加**——有狀態+分散=分散式一致性，分散+變更=相容性與部署順序，有狀態+變更=資料遷移，三者俱全就是線上分散式資料遷移，實務上最容易出事，而這解釋了為什麼「無狀態服務+集中狀態」如此常見；「消除複雜度」多數是幻覺，真正在做的是搬移——加快取是把「查詢慢」換成「失效與一致性」，評估方案要問它把複雜度搬到哪裡、那個位置是不是更能承受，只算收益不算搬移成本是最常見的錯誤；以及**最好的管理是不要製造它**——每個引入的元件都帶來自己的失效模式與運維負擔，而那會持續到系統退役，引入的門檻應該是「現在已經痛到值得」而非「未來可能需要」。

## 講稿

我認為主要來自三個地方，順序很重要。

第一是狀態。無狀態的運算容易理解、容易測試、容易水平擴展。複雜度幾乎全部集中在有東西必須被記住的地方。一致性、失效、順序、重複，這些全都是狀態的問題。

第二是分散。一旦跨越行程邊界，呼叫就從成功失敗兩態變成三態，多了一個不知道。冪等、重試、逾時、補償，這些機制全部是為了處理那個不知道。

第三是變更。系統不是建造完就結束，它持續被修改。多數的複雜度預算其實花在如何在不停機、不破壞相容性的前提下改變一個運行中的系統。

而這三者是相乘而不是相加。有狀態加分散，就是分散式資料的一致性。分散加變更，就是相容性與部署順序。三者俱全就是線上系統的分散式資料遷移，那是最容易出事的場景。

所以我的結論是，消除複雜度多數時候是幻覺，我們真正在做的是搬移。加一層快取是把查詢慢換成失效與一致性。評估一個方案時要問它把複雜度搬到哪裡去了，以及那個位置是不是我們更能承受的。

## 常見追問

### 那要怎麼判斷「現在是不是已經痛到值得」？

**核心答案**：用可量測的痛與可估計的成本做比較。痛的一側應該有數字——「這個查詢的 p99 是 800 毫秒，佔了整體延遲的六成」、「我們每週有兩次因為協調部署而延遲上線」。成本的一側包括：建置的時間、新的失效模式、監控與告警的增量、以及團隊的學習曲線。如果痛說不出數字，那通常表示還不夠痛。

**詳細解析**：「說不出數字」有兩種可能，而區分它們很重要：一種是**真的不痛**（那就不要做），另一種是**痛但沒有量測**（那第一件事應該是加上量測而非直接動手）。後者其實很常見，而它有一個附帶的好處：**量測本身往往會改變結論**——你以為慢的地方不是最慢的、你以為的瓶頸不是真的瓶頸。**另一個實用的判準是「可逆性」**：**可逆的決定應該快速地做**（加一個索引、開一個功能旗標），**不可逆的決定應該慢慢地做**（換資料庫、拆服務、選一個框架）——因為前者錯了可以退回，後者錯了要付出數個月的代價。

**面試回答方式**：給比較的兩側（**痛的一側要有數字**、成本的一側包含建置時間、新失效模式、監控增量、學習曲線）並給出判準：說不出數字通常表示還不夠痛。加分點是區分「說不出數字」的兩種可能——真的不痛（別做）vs 痛但沒量測（**第一件事是加量測而非動手**），並指出**量測本身往往會改變結論**。收在**可逆性**這個判準：可逆的決定快速做，不可逆的決定慢慢做。

### 這個框架對「該學什麼」有什麼啟示？

**核心答案**：優先學那些解釋「為什麼」的東西。具體技術（某個框架的 API、某個工具的參數）**會過時而且查得到**；而狀態、一致性、失敗模式、以及變更管理的原理不會——它們讓你在遇到一個沒學過的技術時，知道該問什麼問題。實用的順序是：先徹底理解一個資料庫、一個訊息系統、一個快取的內部原理，再橫向擴展——因為同類系統的問題與取捨高度相似。

**詳細解析**：「知道該問什麼問題」是這種學法最大的回報。看到一個新的儲存系統，你會自動地問：它的一致性模型是什麼？失敗時會怎樣？資料怎麼複製？延遲的分布如何？怎麼備份與恢復？ ——這幾個問題足以在半小時內判斷它適不適合你的場景，而那是任何教學文件都給不了的能力。反過來，只學 API 的人在面對新系統時只能重新學一次。**而這也是面試中「深度」的來源**：能回答「為什麼這樣設計」的人，通常也能回答「換一個場景該怎麼設計」，而後者才是面試官真正想知道的。

**面試回答方式**：給優先順序——**先學解釋「為什麼」的原理**（具體 API 會過時且查得到，狀態、一致性、失敗模式、變更管理的原理不會），並給實用的路徑（先徹底理解一個資料庫、一個訊息系統、一個快取的內部原理再橫向擴展，因為同類系統的取捨高度相似）。真正的加分點是說出回報：**知道該問什麼問題**——一致性模型、失敗行為、複製方式、延遲分布、備份恢復，這幾個問題足以在半小時內判斷一個新系統適不適合。收在面試的層面：能回答「為什麼這樣設計」的人也能回答「換一個場景該怎麼設計」，而後者才是面試官真正想知道的。

### 如果只能給一個後端工程師一條建議？

**核心答案**：「先讓它能被觀察，再讓它變快或變複雜。」 幾乎每一個難以處理的線上問題，根本困難都不是「不知道怎麼修」，**而是「不知道發生了什麼」**。而可觀測性是唯一能同時服務於除錯、容量規劃、效能優化、與架構決策的投資——其他每一項優化都只解決一個問題，只有它讓所有後續的判斷都建立在事實而非猜測上。

**詳細解析**：這條建議之所以排在第一，是因為它有一個罕見的性質：它讓其他所有決定變得更好。沒有量測的優化是猜測、沒有監控的架構變更是賭博、而沒有追蹤的分散式系統除錯是徒勞。**而它的成本相對低**——結構化日誌、幾個關鍵指標、一套追蹤，通常在幾天內就能建立起雛形，而它的回報會持續整個系統的生命週期。如果要再加一句，那會是：把「可觀測性」當成功能的一部分而非事後的補充——在寫一個新功能時就想好「它出問題時我要怎麼發現、怎麼定位」，那比事後補上便宜得多，也完整得多。

**面試回答方式**：給那一條建議——先讓它能被觀察，再讓它變快或變複雜，理由是幾乎每一個難以處理的線上問題，根本困難不是「不知道怎麼修」而是「不知道發生了什麼」。加分點是說明它罕見的性質：**它讓其他所有決定變得更好**（沒量測的優化是猜測、沒監控的架構變更是賭博、沒追蹤的分散式除錯是徒勞），而成本低、回報持續整個生命週期。收在具體的做法：把可觀測性當成功能的一部分而非事後補充——寫新功能時就想好「它出問題時我要怎麼發現、怎麼定位」。
