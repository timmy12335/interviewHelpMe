# 題目

常見的限流（Rate Limiting）演算法有哪些？令牌桶（Token Bucket）和漏桶（Leaky Bucket）的差異是什麼？

## 核心答案

常見的限流演算法有四種：**（1）固定視窗計數器（Fixed Window Counter）**——把時間切成固定長度的區間（如每分鐘），統計這個區間內的請求數，超過門檻就拒絕，實作最簡單但有「視窗邊界問題」（臨界時刻可能瞬間通過兩倍流量）；**（2）滑動視窗（Sliding Window）**——用更精細的方式追蹤「過去固定時間長度內」的請求數，而非依賴固定的時間切點，修正了固定視窗的邊界問題；**（3）漏桶（Leaky Bucket）**——把請求放進一個固定容量的「桶子」，並以**固定的速率**從桶底流出處理，不管流入速度多快多不均勻，流出的速率永遠平穩，桶滿了就直接拒絕新請求，核心特性是「強制平滑流量」；**（4）令牌桶（Token Bucket）**——系統以固定速率生成「令牌」放進桶子（桶子有容量上限），請求要處理必須先拿到一個令牌，令牌用完就拒絕（或排隊），核心特性是「允許一定程度的突發流量（Burst）」，只要桶子裡還有累積的令牌，可以短時間內快速消耗處理一波超出平均速率的請求。

## 詳細解析

**固定視窗計數器的邊界問題**：假設限流規則是「每分鐘最多 100 個請求」，固定視窗計數器會在每個整分鐘的邊界重置計數器。問題在於——如果請求集中在「上一分鐘的最後幾秒」和「下一分鐘的最初幾秒」，例如 59.9 秒送出 100 個請求（在上一個視窗內，通過），緊接著在 60.1 秒又送出 100 個請求（進入了新的視窗，計數器重置為 0，同樣通過），這樣一來，在「59.9 秒到 60.1 秒」這短短 0.2 秒的實際時間窗口內，系統實際上放行了 200 個請求，遠超過「每分鐘 100 個」這個限流規則原本想表達的平均限制,這就是固定視窗在邊界時刻可能出現流量突增兩倍的經典問題。

**滑動視窗如何修正邊界問題**：滑動視窗不依賴「整分鐘」這種固定的切點，而是持續地追蹤「以當前時刻為結尾、往前推固定時間長度（如 60 秒）」這個滑動範圍內的請求數。常見實作方式是「加權滑動視窗」——結合上一個固定視窗和目前視窗的計數，依照當前時刻在目前視窗中的位置比例，加權計算出一個近似的「過去 60 秒」請求總數（例如目前時刻是新視窗的第 10 秒，就用「上一視窗計數 × (50/60) + 目前視窗計數」這種加權方式估算），這種方式用相對簡單的計算量，大幅緩解了固定視窗的邊界突增問題，是很多實際系統（如 Cloudflare 的限流機制）採用的折衷方案。

**漏桶（Leaky Bucket）的核心特性——強制平滑**：可以想像成一個底部有一個固定大小小孔的水桶，不管上面倒水（請求流入）的速度多快多不規律，水從底部小孔流出（實際被處理）的速度永遠是固定的；如果倒水的速度超過流出的速度，水桶會逐漸積水（請求在佇列裡排隊等待處理），一旦水桶滿了（佇列滿了），繼續倒進來的水就會溢出（新請求被直接拒絕）。這個演算法的特性是——**不管輸入流量如何波動,輸出永遠是平滑、固定速率的**，這對於「後端處理能力有嚴格上限、必須被保護不能超載」的場景（如呼叫一個處理能力有限的下游服務）非常適合，因為它從根本上「削平了所有的突發流量」。

**令牌桶（Token Bucket）的核心特性——允許突發**：令牌桶則是反過來想——系統以固定速率（如每秒 10 個）持續生成令牌放進桶子，桶子有一個容量上限（如最多累積 100 個令牌）；一個請求要被處理，必須先從桶子裡拿走一個令牌，如果桶子是空的（令牌都被拿光了），這個請求就被拒絕（或者依實作選擇讓它排隊等待下一個令牌生成）。這個演算法的關鍵特性在於——**如果請求量長時間低於令牌生成速率，令牌會在桶子裡持續累積（直到桶子容量上限）**，一旦突然來了一波超出平均速率的突發流量，只要桶子裡還有累積的令牌，這些請求依然可以被立即處理（消耗掉累積的令牌），只有當累積的令牌也用完了，超額的部分才會被拒絕。這種「允許短時間內用累積的餘裕應付突發流量，長期平均速率仍受控」的特性，比漏桶「不管三七二十一,一律強制平滑」更貼近多數真實業務場景的需求（多數業務都能接受「偶爾一陣忙一陣閒」，只要長期平均沒有超載）,因此令牌桶是實務上更常被選用的限流演算法（例如 Google 的 Guava RateLimiter、許多 API Gateway 的預設限流實作都採用令牌桶或其變種）。

## 面試回答方式

先列出四種常見演算法的名稱（固定視窗、滑動視窗、漏桶、令牌桶），然後聚焦在題目問的「令牌桶 vs 漏桶」這組最容易混淆的對比。用具體的比喻幫助說明——「漏桶是固定速率流出、強制平滑,不管輸入多快輸出永遠穩定；令牌桶是固定速率生成令牌、但允許把令牌累積起來,一旦累積夠多可以應付突發流量」。強調兩者的核心差異在於「是否允許突發流量（Burst）」——這是這題的核心考點,能清楚說出這個差異點,並舉例說明「為什麼令牌桶在多數業務場景更受歡迎(能容忍偶爾的流量尖峰,只要長期平均可控)」,展現你不只是背誦兩個名詞的定義,而是理解它們適用場景的本質差異。

## 常見追問

### 如果一個系統同時需要限制「短時間內的突發流量上限」和「長期的平均速率上限」，該怎麼設計？

**核心答案**：這正是令牌桶演算法**天生就能滿足**的需求，只需要正確設定兩個參數——**令牌生成速率（Refill Rate）** 控制「長期平均速率」（例如每秒生成 10 個令牌，代表長期平均每秒最多處理 10 個請求）；**桶子容量（Bucket Capacity）** 控制「短時間內能承受的突發流量上限」（例如桶子容量設為 50，代表即使長期平均是每秒 10 個，只要之前累積了足夠的令牌，短時間內最多可以一口氣處理 50 個請求）。如果需要更精細地同時限制多個不同時間尺度的流量（例如「每秒最多 10 個、且每分鐘總數不能超過 300 個」這種多層限制），可以**疊加多個限流層（每一層用不同的令牌桶參數）**，一個請求必須同時通過所有層的限流檢查才會被放行。

**詳細解析**：這題考察是否理解令牌桶演算法的兩個參數（生成速率、桶容量）分別對應到「哪一種流量特性」，並能靈活運用這個機制去滿足更複雜、多層次的限流需求。令牌桶的巧妙之處，正是它用「兩個獨立可調的參數」把「長期平均速率」和「短期突發容忍度」這兩個原本可能互相衝突的需求,解耦成可以分別調整的旋鈕——如果只調高生成速率而不調桶容量，系統能承受的長期吞吐量提高了，但依然無法應付「瞬間湧入一大波請求」這種場景（因為桶子容量小,很快就被掏空）；如果只調高桶容量而不調生成速率,系統能承受的瞬間突發流量增加了，但長期平均速率的上限沒有變（令牌生成的速度沒有變快）。理解這兩個參數的獨立性，能讓工程師根據實際業務的流量特徵（例如電商大促銷活動,平時流量平穩但特定時刻會有短暫尖峰,適合「較低的長期速率+較大的桶容量」；或反過來,需要嚴格控制長期吞吐量、完全不能容忍突發,適合「長期速率和桶容量都設得比較接近」)去精細調校限流策略。對於「多層次限流」的需求（例如同時要限制「每秒峰值」和「每分鐘總量」這兩個不同時間尺度的上限,單一個令牌桶參數可能無法同時精確表達兩種限制,例如「每秒10個、桶容量50」這組參數,理論上允許一分鐘內最多通過 10×60=600 個請求,如果業務需求是「每分鐘總數不能超過300」,單一層令牌桶無法精確表達這個額外限制),常見的做法是**疊加多個獨立的限流層**,每一層各自維護自己的令牌桶（或其他限流演算法）、各自監控不同的時間尺度,一個請求必須同時滿足所有層的限制才會被放行,任何一層拒絕就整體拒絕。這種「分層限流」的設計模式,在真實的 API Gateway 或雲端服務的限流系統中很常見(例如「每秒請求數上限」和「每天總配額上限」同時存在的多層限流規則)。

**面試回答方式**：先指出「令牌桶天生就能滿足這個需求,兩個參數分別對應兩種流量特性——生成速率控制長期平均、桶容量控制短期突發容忍度」。給出具體調校邏輯——「調高生成速率提升長期吞吐量上限、調高桶容量提升瞬間突發承受能力,兩者可以獨立調整」。補充「如果需要同時精確限制多個不同時間尺度(如每秒峰值+每分鐘總量),可以疊加多層限流,一個請求要同時通過所有層才放行」。展現你能靈活運用令牌桶的兩個參數,並知道更複雜的多層限流設計模式。

### 在分散式系統中（多台伺服器同時處理請求），限流演算法要怎麼實作才能保證「全域限流」而不是「每台伺服器各自限流」？

**核心答案**：關鍵是把「令牌桶（或其他限流演算法）的狀態（如目前桶子裡有多少令牌、上次生成令牌的時間）」**存放在一個所有伺服器共享的中心化儲存**，最常見的做法是用 **Redis**——每次請求進來時，任何一台伺服器都對 Redis 裡的「這個限流規則」執行一次「檢查並扣減令牌」的操作（通常用 Redis 的 Lua 腳本或原子性指令,保證「檢查令牌是否足夠」和「扣減令牌」這兩個步驟具備原子性,避免在高並發下出現多個請求同時檢查到「令牌還夠」但實際上令牌只剩一個的競態問題）。如果不使用共享儲存,而是讓每台伺服器各自維護一份獨立的限流狀態（例如記憶體裡的計數器）,會導致「全域限流」名不符實——假設限流規則是「全域每秒最多 100 個請求」,但流量被負載平衡（Load Balancing）器分散到 10 台伺服器,如果每台伺服器各自獨立限流「每秒 100 個」,實際上整個系統會放行遠超過 100 個請求(最多可能到 1000 個),完全沒有達到「全域」限流的效果。

**詳細解析**：這題把限流演算法從「單機」的理論模型,延伸到「分散式、多伺服器」這個更貼近真實生產環境的實務場景,考察是否能識別出「狀態集中化」這個分散式系統設計中反覆出現的核心主題。理解這個問題的關鍵,在於認清「限流演算法的正確性,建立在對『目前狀態』(如令牌桶裡還有幾個令牌)有一個唯一、一致的認知」——如果這個狀態被分散地、獨立地維護在每一台伺服器自己的記憶體裡,每台伺服器各自「以為」自己看到的令牌數量就是全局唯一的正確狀態,但實際上,它們各自的認知是彼此獨立、互不知情的,加總起來,系統實際承受的總流量,是「每台伺服器各自允許的流量」的總和,遠超過原本設計時想要的全域上限。解決這個問題的核心思路,是把限流狀態從「每台伺服器各自的私有記憶體」搬到「所有伺服器都能存取的共享位置」,Redis 因為其高效能、支援原子性操作(尤其是搭配 Lua 腳本,能把「讀取目前令牌數、判斷是否足夠、扣減令牌、更新時間戳」這一整串邏輯,包裝成一個對 Redis 而言不可分割的原子操作,徹底避免高並發下的競態問題,見 [[../redis/README.md]] 相關單執行緒特性的討論),是業界實作分散式限流最常見的選擇。除了 Redis,一些更先進的分散式限流方案,還會考慮「避免每一次請求都要跨網路呼叫 Redis 帶來的延遲和 Redis 本身的壓力」,例如採用「本地預先申請一批配額(類似前面資料庫章節提到的號段模式思路),每台伺服器定期向中心化的 Redis 申請一小批令牌配額緩存在本地,大部分請求先消耗本地緩存的配額,只有配額用盡才需要再向 Redis 申請,用犧牲一些限流精確度(短時間內全域實際通過的流量,可能因為多台伺服器各自持有的緩存配額,略微超出精確的全域上限)換取顯著降低對中心化儲存的存取壓力和延遲」,這是在「絕對精確的全域限流」和「效能開銷」之間的一個常見工程折衷。

**面試回答方式**：先指出核心問題——「限流狀態如果各自存在每台伺服器的私有記憶體,會導致全域限流名不符實,實際放行流量是『單機限制 × 伺服器數量』,遠超原本的全域上限」。給出正確做法——「把限流狀態(令牌數、時間戳)集中存放在共享儲存如 Redis,每次請求用原子性操作(Lua 腳本)檢查並扣減,避免競態問題」。如果能延伸提到「本地緩存一批配額、減少每次都跨網路呼叫 Redis 的效能開銷」這種進階優化,展現你對分散式限流有更全面、包含效能權衡的實務理解。

### 限流之後,被拒絕的請求,應該怎麼回應客戶端比較好?有沒有相關的 HTTP 標準?

**核心答案**：被限流拒絕的請求,應該回傳 HTTP 狀態碼 **`429 Too Many Requests`**（這是專門為限流場景定義的標準狀態碼,而不是用 `403 Forbidden` 或其他容易讓客戶端誤解的狀態碼)。更完善的做法是搭配 **`Retry-After`** 標頭,明確告知客戶端「大約需要等待多久之後再重試會比較合適」(可以是具體秒數,也可以是一個明確的時間點)。此外,許多 API 服務會額外提供 **`X-RateLimit-Limit`**(這個時間窗口的請求上限)、**`X-RateLimit-Remaining`**(目前這個時間窗口還剩多少配額)、**`X-RateLimit-Reset`**(配額重置的時間)這幾個自訂標頭(雖然不是正式的 HTTP 標準,但已經是業界廣泛採用的慣例),讓客戶端不需要「盲目地重試碰運氣」,而是能主動根據這些資訊,合理地調整自己的請求節奏。

**詳細解析**：這題從「限流演算法怎麼實作」延伸到「限流之後,如何以對客戶端友善、符合標準的方式溝通」這個容易被忽略、但對 API 使用體驗有直接影響的細節。使用正確的狀態碼很重要,因為狀態碼是客戶端(以及開發它的工程師)判斷「發生了什麼、該怎麼應對」最直接的依據——如果限流回傳的是 `403 Forbidden`,客戶端(尤其是自動化的程式邏輯)可能會誤判為「這個請求在權限上被永久拒絕,重試也沒有意義」,而放棄重試;但實際上限流只是「暫時性」的拒絕(過一段時間、配額恢復後,同樣的請求應該就能成功),用 `429` 這個專門為此設計的狀態碼,能讓客戶端(以及遵循標準的 HTTP 客戶端函式庫)正確理解「這是暫時性的、值得稍後重試」的情境。`Retry-After` 標頭進一步把「應該等多久再重試」這個資訊明確地告知客戶端,而不是讓客戶端自己瞎猜(可能猜得太短,導致又立刻被拒絕、形成無謂的重試風暴;或猜得太長,浪費不必要的等待時間)。`X-RateLimit-*` 這組雖然不是官方標準(不同服務商對這組標頭的具體命名可能略有差異,如 GitHub API 用類似但略有不同的命名慣例)、但已經是業界高度一致的實務慣例的標頭,則提供了更主動、更精細的資訊——好的 API 客戶端,不需要等到真的被拒絕(收到 429)才知道自己快超額了,而是可以透過每次成功請求的回應裡附帶的 `X-RateLimit-Remaining`,提前得知「目前配額只剩下 5 個了」,主動地放慢自己發送請求的速度,避免真的觸發限流,這種「防患於未然」的體驗,遠比「一直發送直到被拒絕、再狼狽地處理 429 錯誤」要來得更加平順和專業。理解「限流不只是後端要正確實作演算法,回應給客戶端的方式(狀態碼、標頭)同樣是良好 API 設計和開發者體驗的一部分」，展現你對這個問題有從「後端實作」延伸到「API 契約與開發者體驗」的完整視角。

**面試回答方式**：給出正確的狀態碼——「429 Too Many Requests,而非 403,因為 429 明確傳達『暫時性拒絕,稍後重試有意義』的語意」。補充 `Retry-After` 標頭——「明確告知客戶端該等多久再重試,避免客戶端瞎猜導致重試過快(形成請求風暴)或過慢(浪費時間)」。介紹 `X-RateLimit-*` 系列標頭(Limit/Remaining/Reset)——「讓客戶端能主動監控自己的剩餘配額,防患於未然地放慢節奏,而不是一路衝到被拒絕才反應」。展現你認為「限流」不只是後端演算法問題,也是良好 API 契約設計和開發者體驗的一環。
