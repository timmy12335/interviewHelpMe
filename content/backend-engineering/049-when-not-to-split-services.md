# 題目

什麼情況下不應該拆微服務？拆分的真正判準是什麼？

## 核心答案

拆分的真正判準是組織而非技術。微服務解決的核心問題是「多個團隊要獨立地開發與部署」——當一個團隊為了上線必須協調另外三個團隊時，服務邊界能讓他們解耦。如果只有一個團隊，那個問題不存在，而微服務的成本卻全部存在。

**不該拆的情況有四類**。**團隊規模不足**——服務數量超過團隊數量時，每個人都要維護多個服務，那比單體更糟。**領域邊界還不清楚**——**拆錯的邊界比不拆更貴**，因為跨服務的邊界修改需要協調兩邊的部署。**基礎設施還不成熟**——沒有自動化部署、集中式日誌、分散式追蹤、與服務發現時，微服務的運維成本會壓垮團隊。**問題其實是效能或耦合**——**那些通常有更便宜的解法**（加索引、加快取、重構模組）。

「模組化的單體」在多數情況下是更好的起點：清楚的模組邊界、各自的資料表歸屬、透過介面而非直接呼叫——它保留了未來拆分的可能，但不需要現在付出分散式系統的代價。

## 詳細解析

微服務把「編譯期的問題」變成「執行期的問題」。單體裡改一個介面，編譯器會告訴你所有呼叫端壞了；拆開之後，它變成「上線後才發現對方沒跟上」。單體裡的一次函式呼叫要嘛成功要嘛拋例外；拆開之後，它多了「逾時」與「不確定成功與否」兩種狀態——而後者需要冪等、重試、與補償來處理。這些成本不會因為「我們用了好的框架」而消失，它們是分散式的本質。

**「拆錯邊界」的代價比想像中大**。判斷邊界的正確與否有一個實用的指標：「一個典型的需求變更需要改幾個服務」。如果多數變更都跨兩個以上的服務，那個邊界就是錯的——**它把高內聚的東西切開了**。修正這種錯誤比一開始就不拆貴得多：資料已經分散在不同的資料庫、團隊已經按服務劃分、而合併服務在政治上比拆分更困難。

**「效能」幾乎不是拆分的好理由**。**微服務通常讓效能變差**——一次函式呼叫變成一次網路往返，而原本一個交易能保證的一致性現在需要多次呼叫加上補償。唯一合理的效能理由是「某個部分的擴展需求與其他部分差異巨大」（例如影片轉檔需要 GPU 而 API 只需要 CPU）——那時拆開是為了讓資源配置獨立，而不是為了讓程式跑得快。

**「拆分不是全有全無」**。最務實的路徑是「從單體中拆出真正需要獨立的部分」：那個需要獨立擴展的、那個被另一個團隊擁有的、那個技術棧確實不同的。留下的單體仍然是單體，而那完全沒有問題。 Shopify、Stack Overflow、以及 Basecamp 都是在相當大的規模上仍以單體為主的例子——它們證明了「單體」與「規模」不是對立的，真正的對立是「單體」與「多團隊獨立部署」。

## 面試回答方式

先給真正的判準——**組織而非技術**：微服務解決的是「多個團隊要獨立開發與部署」，只有一個團隊時那個問題不存在，而成本全部存在。給四類不該拆的情況（團隊規模不足、領域邊界不清、基礎設施不成熟、問題其實是效能或耦合）並推薦**模組化的單體**作為起點。加分點有三個：微服務把編譯期的問題變成執行期的問題——一次函式呼叫多了「逾時」與「不確定成功與否」兩種狀態，而這些成本是分散式的本質，不會被好框架消除；判斷邊界對錯的實用指標是「一個典型變更需要改幾個服務」，多數變更跨兩個以上服務就是切錯了；以及**效能幾乎不是好理由**，唯一合理的是「某部分的擴展需求與其他部分差異巨大」。收在 Shopify、Stack Overflow 的例子：單體與規模不對立，真正對立的是單體與多團隊獨立部署。

## 講稿

拆分的真正判準是組織而不是技術。微服務解決的核心問題是多個團隊要獨立地開發與部署。當一個團隊為了上線必須協調另外三個團隊時，服務邊界能讓他們解耦。如果只有一個團隊，那個問題不存在，而微服務的成本卻全部存在。

我會強調一件事。微服務把編譯期的問題變成執行期的問題。單體裡改介面，編譯器會告訴你哪裡壞了。拆開之後，變成上線後才發現對方沒跟上。一次函式呼叫原本要嘛成功要嘛拋例外，拆開之後多了逾時、還有不確定成功與否這兩種狀態，而後者需要冪等、重試、補償來處理。

判斷邊界對不對有一個實用的指標，就是一個典型的需求變更需要改幾個服務。如果多數變更都跨兩個以上，那個邊界就是錯的，它把高內聚的東西切開了。

效能幾乎不是拆分的好理由，微服務通常讓效能更差。唯一合理的是某個部分的擴展需求跟其他部分差異巨大，那時拆開是為了讓資源配置獨立。

所以我的預設是模組化的單體，需要獨立的部分才拆出去。剩下的單體仍然是單體，那完全沒有問題。

## 常見追問

### 模組化的單體具體要怎麼做？

**核心答案**：**三個機制**。**明確的模組邊界**——每個模組有一個公開的介面（一組 facade 或 service 類別），模組之間只能透過那個介面互相呼叫。**資料的歸屬**——每張表屬於一個模組，其他模組不能直接查它，**只能透過擁有者的介面**。**依賴方向的強制**——用工具檢查（ArchUnit、模組系統、或建置階段的規則）**確保沒有人繞過邊界**。

**詳細解析**：「靠自律維持邊界」在幾個月內一定會失敗。有人趕時間、有人不知道規則、有人覺得「這次特別」——而每一次繞過都讓後續拆分的成本增加。所以自動化的檢查不是可選項而是核心機制：ArchUnit 的規則、Java 的模組系統、或者最簡單的——把每個模組放進獨立的建置模組，讓「編譯不過」成為邊界的守門員。**最容易被繞過的是資料庫**：跨模組的 JOIN 寫起來太方便，而它一旦存在，那兩個模組就永遠拆不開了。所以「禁止跨模組 JOIN」是模組化單體最重要也最難維持的一條規則。

**面試回答方式**：給三個機制（模組邊界、資料歸屬、依賴方向強制）。真正的重點是靠自律維持邊界在幾個月內一定會失敗，所以自動化檢查不是可選項而是核心機制（ArchUnit、模組系統、或把每個模組放進獨立的建置模組讓編譯不過來守門）。加分點是指出**最容易被繞過的是資料庫**——跨模組 JOIN 寫起來太方便，而一旦存在那兩個模組就永遠拆不開，所以那是最重要也最難維持的一條規則。

### 已經拆得太細了該怎麼辦？

**核心答案**：合併回去，而且要接受那在政治上比拆分困難。技術上的步驟是先合併程式碼（把兩個服務放進同一個部署單元但保留模組邊界）、再合併資料（如果它們本來就常一起查）。判斷該合併哪些的依據是「哪些服務總是一起改、一起部署、或者一個掛了另一個也沒用」——那些其實是同一個服務被切開了。

**詳細解析**：「政治上的困難」比技術上的更值得預先處理。合併服務往往意味著團隊的合併或責任的重新劃分，而那會被解讀成「我們之前做錯了」。有效的框架是把它描述成「架構隨著理解的深化而演進」而非「修正錯誤」——**因為那確實是真的**：拆分當時的領域理解不如現在，而根據新的理解調整邊界正是好的工程實踐。**另外，合併不必一次到位**：先把它們部署在一起（減少網路呼叫與運維成本）、保留獨立的模組，觀察一段時間再決定要不要合併資料——這與拆分時的漸進策略是對稱的。

**面試回答方式**：給技術步驟（先合併程式碼保留模組邊界、再視情況合併資料）與判斷依據（總是一起改、一起部署、一個掛了另一個也沒用的，其實是同一個服務被切開了）。加分點是主動處理政治上的困難比技術上更值得預先準備——把它描述成「架構隨理解深化而演進」而非「修正錯誤」，因為那確實是真的。收在漸進策略：先部署在一起、保留獨立模組、觀察後再決定資料，與拆分時對稱。

### 面試官說「我們公司就是要上微服務」怎麼回答？

**核心答案**：不要唱反調，而是問「要解決什麼問題」並據此給出拆分的順序。合理的回答是：「我認同方向，我會關心的是拆分的順序與前置條件。」 然後給**前置條件**（自動化部署、集中式日誌、分散式追蹤、服務發現、以及 API 版本策略）與**順序**（先拆真正需要獨立的、邊界最清楚的、與其他部分耦合最少的）。

**詳細解析**：這個追問測的其實是「你能不能在既定的方向下提出專業意見」。單純反對顯得不合作，全盤接受顯得沒有判斷——而好的答案是「接受目標，管理風險」。最有價值的具體建議是「先建基礎設施再拆服務」：很多失敗的微服務轉型不是因為方向錯，而是因為在沒有可觀測性的情況下拆了二十個服務，然後任何問題都查不出來。另一個值得提的是「拆分應該有明確的成功標準」——例如「部署頻率提升」「跨團隊協調的次數下降」——如果拆完之後這些指標沒有改善，那就該重新檢視邊界，而不是繼續拆。

**面試回答方式**：先給態度——不唱反調，接受目標並管理風險，用「我認同方向，我關心的是拆分的順序與前置條件」開場，然後給前置條件與順序。指出這個追問測的是「能不能在既定方向下提出專業意見」——單純反對顯得不合作，全盤接受顯得沒判斷。加分點是**先建基礎設施再拆服務**（很多失敗不是方向錯，而是在沒有可觀測性的情況下拆了二十個服務然後查不出任何問題）與**拆分應該有明確的成功標準**（部署頻率、跨團隊協調次數），沒改善就該重新檢視邊界而不是繼續拆。
