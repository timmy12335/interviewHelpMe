# 題目

容器的 CPU 與記憶體限制該怎麼設？設錯了會有什麼症狀？

## 核心答案

**記憶體的限制是硬性的**——超過就被 OOM Killer 殺掉（退出碼 137），**沒有降級的空間**。所以它必須設得足夠：應用的堆積 + 非堆積（執行緒堆疊、中繼資料、直接記憶體）+ 額外的餘裕。而 JVM 應用最常見的錯誤是把堆積設成容器限制的 100%——忘了非堆積的部分。

**CPU 的限制則是節流而非殺掉**。Kubernetes 的 `limits.cpu` 對應 CFS quota——超過配額的執行緒會被強制暫停到下一個週期（預設 100 毫秒）。症狀是週期性的延遲毛刺，而且在 CPU 使用率圖上看起來使用率不高（因為被節流的時間不算使用）。要看 `container_cpu_cfs_throttled_seconds_total` 這類專門的指標才發現得了。

**`requests` 與 `limits` 的區別很重要**：`requests` 用於排程（保證能拿到多少），`limits` 是上限。**兩者相等時 Pod 得到 Guaranteed 的 QoS 等級**（最不容易被驅逐）；**差距大時是 Burstable**（可以突發但可能被節流或驅逐）。

## 詳細解析

「CPU limit 該不該設」是一個有爭議但值得理解的問題。**設了的好處是可預測性**（不會因為某個 Pod 突發而影響鄰居）；壞處是即使節點有閒置的 CPU 也用不到，而且CFS 節流在多執行緒應用上的行為可能出乎意料——一個設定 1 core 的容器，如果應用開了 8 個執行緒，它們共享那 1 core 的配額，可能在週期的前 12.5 毫秒就用完然後被節流 87.5 毫秒。所以「多執行緒應用加上緊的 CPU limit」是延遲毛刺的常見組合。**有些團隊選擇「設 requests 但不設 limits」**——依賴 requests 提供的保證，讓突發能用到閒置資源，代價是失去了對鄰居的保護。

**JVM 與容器的互動需要特別注意**。**JDK 10 之後的容器感知**讓 JVM 讀取 cgroup 的限制而非主機的資源——但那只調整了預設值，不會幫你算非堆積的部分。而且 **`Runtime.availableProcessors()` 的值會影響一大堆東西**：GC 執行緒數、JIT 編譯執行緒、`ForkJoinPool.commonPool` 的大小、以及所有依它設定的應用層執行緒池。**一個 CPU limit 設成 0.5 的容器，`availableProcessors` 可能回傳 1**——**於是所有的並行度都變成 1**，而那可能不是預期的。

記憶體的估算要包含所有部分。JVM 應用的實際 RSS 是：堆積 + Metaspace + 程式碼快取 + 執行緒堆疊（執行緒數 × 每執行緒的實際使用）+ 直接記憶體 + GC 自身的結構 + 原生函式庫。實務上「容器限制 × 0.7 作為堆積上限」是一個合理的起點，而精確的做法是用 NMT 量測非堆積的實際用量。

**驅逐的優先順序值得知道**。節點記憶體不足時，Kubernetes 會依 QoS 等級驅逐 Pod：**BestEffort（沒設 requests 與 limits）最先、Burstable 次之、Guaranteed 最後**。**所以關鍵服務應該設成 Guaranteed**（requests 等於 limits），而那也意味著它們的資源被完整預留、不能超用。

## 面試回答方式

先給**記憶體是硬性限制、CPU 是節流**這個關鍵區別，並指出 JVM 應用最常見的錯誤是把堆積設成容器限制的 100%。展開 **CPU 節流的症狀**——週期性延遲毛刺，而在 CPU 使用率圖上看起來使用率不高，要看專門的節流指標才發現得了。給 `requests` 與 `limits` 的區別與 QoS 等級。加分點有三個：**「CPU limit 該不該設」是有爭議的**——設了可預測但用不到閒置資源，而多執行緒應用加緊的 limit 是延遲毛刺的常見組合（8 個執行緒共享 1 core 的配額，可能前 12.5 毫秒用完然後被節流 87.5 毫秒）；`availableProcessors` 影響 GC 執行緒、JIT、commonPool 與所有依它設定的池，limit 設 0.5 時可能全部變成 1；以及**驅逐的優先順序**——關鍵服務應該設成 Guaranteed。

## 講稿

記憶體的限制是硬性的，超過就被系統殺掉，沒有降級的空間。所以它必須設得足夠，包含堆積、非堆積、還有餘裕。JVM 應用最常見的錯誤是把堆積設成容器限制的百分之百，忘了非堆積的部分。

CPU 的限制則是節流而不是殺掉。超過配額的執行緒會被強制暫停到下一個週期。症狀是週期性的延遲毛刺，而且在 CPU 使用率圖上看起來使用率不高，因為被節流的時間不算使用。要看專門的節流指標才發現得了。

CPU 限制該不該設是一個有爭議的問題。設了的好處是可預測，不會因為某個 Pod 突發而影響鄰居。壞處是即使節點有閒置的 CPU 也用不到。而且多執行緒應用加上緊的限制是延遲毛刺的常見組合。一個設定一核的容器，如果應用開了八個執行緒，它們共享那一核的配額，可能在週期的前十幾毫秒就用完然後被節流剩下的時間。

還有一點，可用處理器數這個值會影響一大堆東西，GC 執行緒數、JIT 編譯執行緒、共用池的大小、還有所有依它設定的應用層執行緒池。限制設成零點五的容器，那個值可能回傳一，於是所有的並行度都變成一。

## 常見追問

### 怎麼判斷限制設得對不對？

**核心答案**：**看三組指標的關係**。**記憶體**——實際使用相對於限制的比例（**應該有 20% 到 30% 的餘裕**）、以及有沒有 OOM 的記錄。**CPU**——使用率、**節流的比例**（`throttled_periods / periods`——任何持續的節流都表示 limit 太緊或應用需要優化）、以及與延遲指標的相關性。**驅逐與重啟**——Pod 的重啟次數與原因，**退出碼 137 表示被 OOM Killer 殺掉**。

**詳細解析**：「節流的比例」是最直接但最少被監控的指標。多數團隊監控 CPU 使用率，**而使用率無法顯示節流**——一個持續被節流的容器，使用率可能穩定在 60% 而延遲卻很糟。所以應該把節流比例做成一個標準的儀表板項目與告警。另一個實用的做法是「用 VPA 的建議值作為參考」（Kubernetes 的 Vertical Pod Autoscaler 即使在「只建議不執行」的模式下，也會依實際使用量給出推薦的 requests 與 limits），**它比憑感覺設定有依據得多**。但要注意 VPA 的建議基於歷史使用量，它無法預測未來的成長或罕見的尖峰——**所以建議值是起點而非答案**。

**面試回答方式**：給三組指標（記憶體的餘裕與 OOM 記錄、CPU 的使用率與**節流比例**、重啟次數與退出碼）。重點強調「節流的比例」最直接但最少被監控——使用率無法顯示節流，一個持續被節流的容器使用率可能穩定在 60% 而延遲很糟，所以應該做成標準的儀表板項目與告警。加分點是提出**用 VPA 的建議值作為參考**（即使在只建議的模式下），並誠實指出它基於歷史使用量、無法預測未來成長或罕見尖峰，所以是起點而非答案。

### 記憶體限制設得太緊有什麼症狀？

**核心答案**：**最直接的是 OOM 被殺（退出碼 137）**，但在那之前還有幾個徵兆：**GC 頻率上升**（堆積不夠導致更頻繁的回收）、**GC 停頓變長**（因為存活率高）、**以及吞吐下降**（更多的 CPU 花在 GC 上）。所以「還沒 OOM 但 GC 時間佔比上升」就是限制太緊的早期訊號——**而它比 OOM 早得多，也更容易處理**。

**詳細解析**：JVM 有一個特別的失敗模式值得知道：`OutOfMemoryError: GC overhead limit exceeded`——它表示 JVM 花了超過 98% 的時間在 GC 卻只回收了不到 2% 的堆積，於是主動放棄。這個機制的價值在於它把「無限緩慢」變成「明確失敗」——沒有它的話，應用會進入一個「還活著但幾乎不動」的狀態，而那對監控與恢復都是最糟的情況（看起來還在但實際上不可用）。這與前面談過的「快速失敗優於緩慢降級」是同一個原則，只是由 JVM 自己執行。在容器裡還要注意「OOM Killer 殺掉的可能不是 JVM 的堆積問題」——直接記憶體、原生函式庫、或執行緒堆疊的成長同樣會撞到限制，而那些不會產生 JVM 的 OOM 錯誤或堆積轉儲，只留下一個退出碼 137。

**面試回答方式**：給最直接的症狀（OOM 被殺、退出碼 137）與**在那之前的早期訊號**（GC 頻率上升、停頓變長、吞吐下降），並指出「GC 時間佔比上升」比 OOM 早得多也更容易處理。加分點是介紹 **`GC overhead limit exceeded`** 這個機制與它的價值：把「無限緩慢」變成「明確失敗」，避免了「還活著但幾乎不動」這個對監控與恢復最糟的狀態。收在容器特有的注意事項：OOM Killer 殺掉的可能不是堆積問題（直接記憶體、原生函式庫、執行緒堆疊），那些不會產生 JVM 的 OOM 錯誤或堆積轉儲，只留下退出碼 137。

### 水平擴展與垂直擴展該怎麼選？

**核心答案**：**看瓶頸的性質**。如果是「單一請求需要更多資源」（一個大的記憶體計算、或者一個無法平行化的操作）——**垂直擴展**（給更大的實例）。**如果是「請求太多」**——**水平擴展**（更多實例）。**而水平擴展的前提是無狀態**，或者狀態能被外部化（session 放 Redis、檔案放物件儲存）。

**詳細解析**：「小而多」與「大而少」的取捨值得展開。**小而多的優勢**：故障的影響範圍小、擴縮的粒度細、部署時的滾動更新更平滑、而且更容易被排程到節點的碎片空間。**大而少的優勢**：每個實例的固定開銷（JVM 的基礎記憶體、連線池、快取的暖機）被攤薄、**本地快取的命中率更高**、以及對下游的連線數更少。在 JVM 應用上，「大而少」的優勢比在 Go 或 Node 應用上明顯得多——因為 JVM 的固定開銷（Metaspace、程式碼快取、GC 結構）在小實例上佔比很高。所以「多開幾個小實例」這個在 Go 上很自然的做法，在 JVM 上可能造成可觀的浪費。認出「執行時的特性影響了架構決定」是這題的深度所在。

**面試回答方式**：給判準（單一請求需要更多資源就垂直、請求太多就水平）與水平擴展的前提（無狀態或狀態外部化）。真正的加分點是展開**「小而多」與「大而少」的取捨**，並指出在 JVM 應用上「大而少」的優勢比在 Go 或 Node 上明顯得多——因為 JVM 的固定開銷在小實例上佔比很高，所以「多開幾個小實例」這個在 Go 上很自然的做法，在 JVM 上可能造成可觀的浪費。收在：認出「執行時的特性影響了架構決定」。
