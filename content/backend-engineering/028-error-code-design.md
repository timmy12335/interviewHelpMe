# 題目

API 的錯誤回應該包含什麼？錯誤碼該怎麼設計？

## 核心答案

錯誤回應應該包含四項。**HTTP 狀態碼**——表達錯誤的大類（4xx 是呼叫方的問題、5xx 是伺服器的問題），**這是給基礎設施（負載平衡、監控、重試邏輯）看的**。**穩定的業務錯誤碼**——一個不隨文案改變的字串（`ORDER_ALREADY_PAID`），**這是給呼叫方的程式碼看的**。**人可讀的訊息**——給開發者除錯用，**不一定適合直接顯示給終端使用者**。**追蹤識別碼**——讓使用者回報問題時能對應到日誌。

**最常被省略但最有價值的是「穩定的業務錯誤碼」**。呼叫方需要依錯誤類型做不同處理——重試、顯示特定提示、還是引導到別的流程；**依訊息文字判斷是脆弱的**（文案一改就壞、國際化後無解），**依 HTTP 狀態碼又太粗**（同樣是 400，可能是格式錯誤、業務規則不符、或額度不足）。

**錯誤碼的設計原則是「依呼叫方的處理方式分類，而非依成因分類」**——依成因會產生幾十個呼叫方根本不區分的碼。

## 詳細解析

**「依處理方式分類」的實際做法**是先問「呼叫方看到這個錯誤會做什麼」，把答案相同的歸為一類。典型的幾類是：**可重試的暫時性錯誤**（下游不可用、逾時、限流）、**需要修正請求的錯誤**（參數格式、驗證失敗）、**業務規則不允許**（狀態不對、額度不足、權限不足）、以及**確定失敗不必重試的錯誤**（資源不存在、衝突）。**每一類對應一種呼叫方的行為，而具體的碼在類別之內提供細節。**

**錯誤碼的命名應該穩定且有結構**。常見的做法是 `<領域>.<類型>.<細節>`（`order.state.already_paid`）或者簡單的大寫底線（`ORDER_ALREADY_PAID`）。**關鍵是它一旦發布就不能改**——改了等於破壞性變更。**所以定義新的錯誤碼時應該像定義 API 一樣謹慎**，而很多團隊把它當成隨手加的字串，**結果是幾百個不一致的碼且沒有人知道哪些還在用**。

**HTTP 狀態碼的選擇有幾個常見的爭議**。**驗證失敗用 400 還是 422**——400 表示請求格式錯誤（無法解析）、422 表示格式正確但語意不合法。**區分它們讓呼叫方能分辨「我送的東西壞了」與「我送的值不合規則」**，但實務上很多 API 一律用 400 也能運作。**業務規則不允許用 400 還是 409**——409（Conflict）更精確地表達「當前狀態不允許這個操作」。**沒有絕對的對錯，但同一個 API 內必須一致**，而一致性比選對更重要。

**錯誤回應的安全考量**：**不要洩漏內部資訊**（堆疊追蹤、SQL、內部類別名、框架版本）、**不要讓錯誤訊息成為列舉的工具**（登入失敗一律回同樣的訊息，不要區分「使用者不存在」與「密碼錯誤」）。**而詳細的資訊應該留在日誌裡並用追蹤 ID 關聯**——**這樣既保護了安全，也保留了除錯的能力。**

## 面試回答方式

先給錯誤回應的**四項內容**與**各自是給誰看的**（狀態碼給基礎設施、業務錯誤碼給呼叫方的程式碼、訊息給開發者、追蹤 ID 給使用者回報）。強調**最常被省略但最有價值的是穩定的業務錯誤碼**——依訊息文字判斷脆弱、依狀態碼太粗。給設計原則：**依呼叫方的處理方式分類而非依成因分類**，並列出典型的四類。加分點有三個：**錯誤碼一旦發布就不能改**，定義新碼應該像定義 API 一樣謹慎，**而很多團隊把它當成隨手加的字串**；**400 與 422、400 與 409 的爭議沒有絕對對錯但同一個 API 內必須一致**，**一致性比選對更重要**；以及**安全考量**——不洩漏內部資訊、不讓錯誤訊息成為列舉帳號的工具，**詳細資訊留在日誌並用追蹤 ID 關聯**。

## 講稿

錯誤回應我認為該包含四項，而且每一項是給不同對象看的。HTTP 狀態碼給基礎設施，讓負載平衡跟監控能理解。穩定的業務錯誤碼給呼叫方的程式碼。人可讀的訊息給開發者除錯。還有追蹤識別碼，讓使用者回報問題時能對應到日誌。

最常被省略但最有價值的是穩定的業務錯誤碼。呼叫方需要依錯誤類型做不同處理，重試、顯示特定提示、還是引導到別的流程。依訊息文字判斷很脆弱，文案一改就壞，國際化之後更是無解。依狀態碼又太粗，同樣是四百，可能是格式錯誤、業務規則不符、或額度不足。

設計原則我會說是依呼叫方的處理方式分類，而不是依成因分類。依成因會產生幾十個呼叫方根本不區分的碼。具體做法是先問呼叫方看到這個錯誤會做什麼，把答案相同的歸為一類。

還有一點要強調，錯誤碼一旦發布就不能改，改了等於破壞性變更。所以定義新的錯誤碼應該像定義 API 一樣謹慎。而很多團隊把它當成隨手加的字串，結果是幾百個不一致的碼，而且沒有人知道哪些還在用。

## 常見追問

### 什麼時候該回 5xx，什麼時候該回 4xx？

**核心答案**：判準是**「這個錯誤是誰造成的、以及重試會不會有用」**。**4xx 表示呼叫方的請求有問題**——重試同樣的請求不會成功（除非呼叫方修正）。**5xx 表示伺服器端的問題**——請求本身可能是對的，重試可能成功。**這個區分直接影響基礎設施的行為**：多數重試邏輯只對 5xx（與 429）重試，監控也通常只對 5xx 的比例告警。

**詳細解析**：**最常見的誤用是「把下游的失敗回成 4xx」**。你呼叫的支付服務逾時了，**那不是呼叫方的錯**——回 4xx 會讓呼叫方以為是自己的請求有問題而不重試，**而實際上重試是正確的行為**。正確的是 502／503／504。**反過來的誤用也存在**：把「業務規則不允許」回成 500，**於是監控上看起來錯誤率很高、告警一直響，而實際上系統運作正常**。**這類誤用的代價是「告警的訊噪比下降」**——當 5xx 裡混雜了大量正常的業務拒絕，真正的故障就被淹沒了。**所以狀態碼的選擇不只是語意的正確性，它直接決定了監控與告警的品質。**

**面試回答方式**：給判準——**這個錯誤是誰造成的、重試會不會有用**，並指出這個區分**直接影響基礎設施的行為**（重試邏輯與告警規則）。給兩個方向的誤用：**把下游失敗回成 4xx** 會讓呼叫方不重試而實際上該重試；**把業務拒絕回成 500** 會讓監控看起來錯誤率很高。收在關鍵洞見：**狀態碼的選擇不只是語意正確性，它直接決定了監控與告警的品質**——5xx 裡混雜正常的業務拒絕時，真正的故障就被淹沒了。

### 錯誤碼該由誰維護、放在哪裡？

**核心答案**：**應該有一個集中的定義**，而不是散落在各個拋出點。做法是用一個列舉或常數類別定義所有的錯誤碼與它們的 HTTP 狀態碼、預設訊息、以及是否可重試——**讓「有哪些錯誤碼」成為一個可以被檢視的清單**。**這個清單應該是 API 文件的一部分**，讓呼叫方知道要處理哪些情況。

**詳細解析**：**集中定義的價值不只是整理**，它讓幾件事成為可能：**自動生成文件**（從定義生成錯誤碼的說明表）、**編譯期檢查**（用列舉就不會打錯字串）、**一致的映射**（每個碼對應固定的狀態碼與可重試性，不會同一個錯誤在不同地方回不同的狀態）、以及**使用統計**（知道哪些碼實際上會發生、哪些從未觸發）。**最後一項特別有價值**——一個從未被觸發的錯誤碼可能表示那條路徑是死的（可以刪），也可能表示測試從未覆蓋它。**而如果錯誤碼是散落的字串，這些都做不到。** **「把散落的字串收斂成型別化的定義」是一個通用的改善模式**，同樣適用於事件名稱、指標名稱、設定鍵、以及功能開關。

**面試回答方式**：給明確主張——**集中定義而非散落在拋出點**，用列舉或常數類別定義碼、狀態碼、預設訊息、是否可重試，並讓它成為 API 文件的一部分。展開集中定義讓四件事成為可能（自動生成文件、編譯期檢查、一致的映射、使用統計），並指出**使用統計特別有價值**——從未觸發的碼可能表示路徑是死的或測試沒覆蓋。收在通用模式：**把散落的字串收斂成型別化的定義**，同樣適用於事件名、指標名、設定鍵、功能開關。

### 部分成功的請求該怎麼回應？

**核心答案**：**批次操作中「有些成功有些失敗」是一個必須明確設計的情況**。三種做法：**全有全無**（任一失敗則整批回滾，回 4xx／5xx——**語意最簡單但可能讓一個小錯誤浪費整批的工作**）、**回 207 Multi-Status**（HTTP 的多狀態回應，逐項給出結果——**語意精確但客戶端的處理較複雜**）、以及**回 200 加上結構化的結果清單**（每一項標明成功或失敗與原因——**實務上最常見**）。

**詳細解析**：**選擇的關鍵是「呼叫方需要知道什麼」**。如果呼叫方只關心「整批有沒有成功」，全有全無最簡單。**如果它需要對失敗的項目做特別處理（重試那幾筆、通知使用者哪幾筆有問題），就必須逐項回報。** **而一旦選了逐項回報，就必須決定「HTTP 狀態碼是什麼」**——回 200 表示「請求本身處理成功了（雖然部分項目失敗）」，**這在語意上是對的但會讓監控看不到那些失敗**。**解法是同時在指標層記錄「項目層級的失敗率」**，而不是只依賴 HTTP 狀態碼的統計。**這是一個「HTTP 的狀態碼粒度與業務的成功粒度不一致」的例子**，而它在批次 API 上普遍存在——**認出這一點就知道監控不能只看狀態碼**。

**面試回答方式**：給三種做法與各自的取捨。給選擇的關鍵：**呼叫方需要知道什麼**——只關心整批就用全有全無，需要對失敗項目特別處理就必須逐項回報。真正的加分點是指出**逐項回報時回 200 會讓監控看不到那些失敗**，解法是**同時在指標層記錄項目層級的失敗率**。收在一般化：**這是「HTTP 狀態碼粒度與業務成功粒度不一致」的例子**，在批次 API 上普遍存在，**認出它就知道監控不能只看狀態碼**。
