# 題目

線上事故發生時該怎麼處理？事後檢討要達成什麼？

## 核心答案

**事故處理的第一原則是「先恢復服務，再找根因」**。很多人的直覺是「先搞清楚為什麼」——**但那可能花幾十分鐘，而使用者在那段時間持續受影響**。**正確的順序是：止血（回滾、切流量、降級、擴容）→ 確認恢復 → 才開始調查。**

**角色要明確**。事故指揮（決策與協調，**不親自動手除錯**）、操作者（執行變更）、溝通者（對內外更新狀態）。**規模小時可以一人多角，但「誰在做決定」必須明確**——**沒有明確指揮的事故處理會變成幾個人各自嘗試不同的方向且互相干擾**。

**事後檢討的目的是「改善系統而非追究個人」**。無指責（blameless）不是為了讓大家舒服，**而是因為指責會讓人隱藏資訊**——**而事故的完整資訊是改善的前提**。真正該問的是「**什麼樣的系統或流程讓這個錯誤成為可能，以及為什麼它沒有被更早發現**」。

**行動項必須具體、有負責人、有期限**——**沒有這三項的檢討報告只是一份文件。**

## 詳細解析

**「先恢復再調查」有一個重要的例外**：**如果不理解問題就無法安全地恢復**。盲目重啟可能讓資料處於不一致的狀態、盲目回滾可能撞到已經變更的 schema。**所以正確的表述是「用最少的理解達成安全的恢復」**——**判斷「這個止血動作安全嗎」需要理解，但不需要理解根因**。**而這正是「事先準備 runbook」的價值**：常見故障的止血步驟已經被驗證過，**執行時不需要現場判斷**。

**「調查會破壞現場」是一個真實的取捨**。恢復服務（重啟、擴容、切流量）往往會清掉現場——**堆積轉儲、執行緒狀態、以及當時的日誌與指標**。**所以在恢復之前應該花幾十秒保留證據**：抓一份執行緒轉儲與堆積轉儲、記下當時的關鍵指標數值、確認日誌會被保留。**這幾十秒的成本遠低於「事後完全查不出原因」的代價**——而後者意味著同樣的事故會再發生。

**事故的嚴重性分級應該事先定義**。它決定了：**誰要被通知**（值班的人、還是整個團隊、還是管理層）、**回應的時效**（15 分鐘內、還是次日）、以及**要不要做正式的檢討**。**沒有分級的話，每個事故都要靠當下判斷，而那既慢又不一致。** **分級的依據應該是「使用者的影響」而非「技術的嚴重性」**——一個內部工具完全掛掉可能是 P3，而一個核心 API 的 1% 錯誤率上升可能是 P1。

**事後檢討最容易流於形式的部分是「行動項」**。常見的問題是：**太籠統**（「加強監控」——加什麼監控？）、**沒有負責人**（於是沒有人做）、**沒有期限**（於是無限期推遲）、以及**只治標**（只修那個具體的 bug 而不問「為什麼它能上線」）。**一個有價值的行動項應該能回答「如果同樣的情況再發生，這一項會讓結果有什麼不同」**——**答不上來的行動項應該被重新思考或刪掉**。

## 面試回答方式

先給第一原則——**先恢復服務再找根因**，並說明正確的順序（止血 → 確認恢復 → 才調查）。給角色的明確化並指出**「誰在做決定」必須明確**，否則會變成幾個人各自嘗試且互相干擾。給事後檢討的目的與**無指責的真正理由**：**不是為了讓大家舒服，而是因為指責會讓人隱藏資訊，而完整的資訊是改善的前提**。加分點有三個：**「先恢復再調查」的例外**——不理解就無法安全恢復，所以正確的表述是**「用最少的理解達成安全的恢復」**，而那正是 runbook 的價值；**恢復會破壞現場**，所以**在恢復前花幾十秒保留證據**（執行緒轉儲、關鍵指標、確認日誌保留），**成本遠低於「事後完全查不出原因」**；以及**行動項最容易流於形式**，一個有價值的行動項應該能回答「同樣情況再發生時，這一項會讓結果有什麼不同」。

## 講稿

事故處理的第一原則是先恢復服務再找根因。很多人的直覺是先搞清楚為什麼，但那可能花幾十分鐘，而使用者在那段時間持續受影響。正確的順序是止血、確認恢復、才開始調查。

不過有一個重要的例外。如果不理解問題就無法安全地恢復，盲目重啟可能讓資料不一致。所以更準確的表述是用最少的理解達成安全的恢復。而這正是事先準備手冊的價值，常見故障的止血步驟已經被驗證過，執行時不需要現場判斷。

還有一個真實的取捨。恢復服務往往會清掉現場，堆積轉儲、執行緒狀態、當時的指標。所以在恢復之前應該花幾十秒保留證據。這幾十秒的成本遠低於事後完全查不出原因的代價，因為那意味著同樣的事故會再發生。

角色要明確。指揮、操作者、溝通者。規模小時可以一人多角，但誰在做決定必須明確，否則會變成幾個人各自嘗試不同方向而且互相干擾。

事後檢討的目的是改善系統而不是追究個人。無指責不是為了讓大家舒服，而是因為指責會讓人隱藏資訊，而完整的資訊是改善的前提。

## 常見追問

### 根因分析該做到什麼程度？

**核心答案**：**追到「可以被系統性防止的那一層」**。「因為某個工程師改錯了設定」不是根因——**那是一個必然會偶爾發生的事**；真正的問題是「**為什麼那個錯誤的設定能通過審查並被部署到生產環境而沒有被任何檢查攔下**」。**所以「五個為什麼」的價值在於逼你穿過「人為疏失」這一層**，到達流程與系統的層面。

**詳細解析**：**但也不要無限地追下去**。追到「因為公司沒有足夠的工程資源」這種層次雖然可能是真的，**但它不可行動**。**實用的停止點是「我們能在合理的成本內改變的最深那一層」**——**而那通常是流程、工具、或架構**。**另一個常被忽略的是「為什麼沒有更早發現」這條線**：一個事故往往有兩個根因，**一個是「為什麼發生」，另一個是「為什麼過了兩小時才被發現」**——**後者的改善（監控與告警）常常比前者更有價值**，因為它縮短了所有未來事故的影響時間，而不只是防止這一種。

**面試回答方式**：給明確的標準——**追到「可以被系統性防止的那一層」**，並用「工程師改錯設定」的例子說明**那不是根因，真正的問題是為什麼它能通過審查並被部署**。指出**「五個為什麼」的價值在於逼你穿過「人為疏失」這一層**。加分點是給出停止點（**我們能在合理成本內改變的最深那一層**，通常是流程、工具、架構）與**「為什麼沒有更早發現」這條常被忽略的線**——**它的改善常常比防止這一種事故更有價值，因為它縮短了所有未來事故的影響時間**。

### 值班制度該怎麼設計？

**核心答案**：三個關鍵。**告警的品質**——**每個告警都應該對應一個明確的行動**，而**誤報會訓練值班的人忽略告警**，那是最嚴重的破壞。**輪值的可持續性**——輪值的頻率、每次的長度、以及**「被叫醒之後的補償」**（隔天可以晚到或休息）。**知識的可得性**——runbook、架構圖、以及**「找誰」的清單**，讓值班的人不必靠記憶。

**詳細解析**：**「告警的品質」是一切的基礎，而它需要持續維護**。做法是**把「告警的數量與處理結果」當成一個被追蹤的指標**：這一週響了幾次、其中幾次是真的問題、幾次採取了行動。**如果「無需行動」的比例超過一半，那個告警規則就該被修正或刪除。** **另一個實用的做法是「值班交接時檢視本輪的所有告警」**——**讓改善告警成為輪值的一部分而非額外的工作**。**這個小小的流程設計，讓「告警品質」從一個沒有人負責的事，變成每一輪都會被檢視的事。**

**面試回答方式**：給三個關鍵（告警品質、輪值可持續性、知識可得性）並強調**誤報會訓練值班的人忽略告警，那是最嚴重的破壞**。真正的加分點是**把「告警的數量與處理結果」當成被追蹤的指標**（響了幾次、幾次是真問題、幾次採取行動），**「無需行動」超過一半的告警規則就該修正或刪除**。收在流程設計：**值班交接時檢視本輪的所有告警**，**讓改善告警成為輪值的一部分而非額外工作**。

### 事故的對外溝通該怎麼做？

**核心答案**：**及時、誠實、且對受眾有用**。及時——**在確認影響之後盡快公告，不要等到完全查清楚**（「我們正在調查影響 X 功能的問題」比沉默好得多）。誠實——不淡化影響、不承諾還不確定的恢復時間。有用——**告訴使用者「什麼受影響、有沒有替代方案、下次更新是什麼時候」**，而不是技術細節。

**詳細解析**：**「下次更新是什麼時候」是最常被遺漏但最有價值的一項**。它讓使用者不必反覆查詢或聯絡支援——**而每一次「還沒好嗎」的詢問都是團隊在事故中額外的干擾**。**承諾一個具體的更新時間（「30 分鐘後更新，即使還沒解決」）並嚴格遵守**，比「解決了再說」好得多。**事後的公開檢討（public postmortem）則是另一個層次的溝通**——**它把一次事故從「信任的損失」轉化成「能力的證明」**：能誠實地分析自己的失敗並說明改善措施，比從未出過事更能建立信任。**Cloudflare 與 GitHub 的公開事故報告是很好的範例**，而它們的共同特徵是**技術細節充分、不推卸責任、並明確列出改善行動**。

**面試回答方式**：給三個原則（及時、誠實、對受眾有用）並具體說明各自的含義。真正的加分點是指出**「下次更新是什麼時候」最常被遺漏但最有價值**——它讓使用者不必反覆詢問，**而每次詢問都是團隊在事故中額外的干擾**；並主張**承諾具體的更新時間並嚴格遵守比「解決了再說」好**。收在更高的層次：**公開的事後檢討把一次事故從「信任的損失」轉化成「能力的證明」**，並舉 Cloudflare 與 GitHub 的報告為例。
