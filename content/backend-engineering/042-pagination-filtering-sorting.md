# 題目

列表 API 的分頁、篩選、排序該怎麼設計？

## 核心答案

**分頁有兩種形式**。**偏移式**（`?page=3&size=20`）——直觀、支援跳頁，但深分頁時效能隨頁碼線性下降，而且翻頁期間有新資料插入會導致重複顯示。**游標式**（`?cursor=xxx&limit=20`）——效能與頁碼無關、翻頁期間穩定，但不支援跳頁。面向使用者的列表通常該用游標式（配合「載入更多」或無限捲動），只有真的需要跳頁的管理後台才用偏移式，而且應該限制最大頁數。

篩選的設計原則是「明確的參數而非通用的查詢語言」。`?status=ACTIVE&created_after=2024-01-01` 比一個通用的 `?filter=...` DSL 好——因為明確的參數可以被驗證、可以對應到索引、也不會讓使用者寫出打垮資料庫的查詢。通用的篩選語言只在真的需要動態組合時才值得，而那個成本很高。

排序應該限制在「有索引支援的欄位」——支援哪些排序等於決定要建哪些索引。開放任意欄位排序是一個容易給出但代價高昂的承諾。

## 詳細解析

「游標該包含什麼」決定了它的能力與穩定性。最簡單的游標是「上一頁最後一筆的排序鍵」——**但排序鍵必須唯一**（否則邊界會重複或遺漏），所以通常要加上主鍵形成複合游標。游標應該編碼成不透明的字串（base64 的 JSON），理由是「讓伺服器保留改變內部表示的自由」——而不是為了安全（base64 不是加密）。

「總筆數」是分頁設計中最常見的產品需求衝突。傳統的分頁 UI 需要「共 N 頁」，而那需要一次 `COUNT(*)`，在大表上與主查詢一樣昂貴。**處理方式有三**：**改變 UI**（載入更多、無限捲動——**本來就更適合行動裝置**）、用估算值（資料庫的統計估算，或者一個近似的計數）、或者只在第一頁算一次並快取。很多時候正確的答案是第一種——「共 12345 筆」對使用者的價值，通常遠低於工程上為它付出的成本。

篩選參數的組合會產生索引的爆炸。支援 5 個可篩選的欄位意味著理論上有 31 種組合，而每種組合的最佳索引可能不同。務實的做法是「識別出真正常用的組合並為它們建索引」（用 API 層的使用統計），**而不是為每種組合都準備**。**罕見的組合可以接受較慢**，或者要求必須帶上某個有索引的條件（例如「必須指定時間範圍」），這既保護了資料庫也引導了合理的使用方式。

API 的回應應該包含分頁的中繼資料：**下一頁的游標**（或者 `hasNext` 的布林）、**本頁的實際筆數**。GraphQL 的 Relay 規範定義了一個完整的形式（`edges`、`pageInfo`、`hasNextPage`、`endCursor`），即使不用 GraphQL，那個形狀也值得參考——因為它明確地分開了「資料」與「分頁的位置資訊」。

## 面試回答方式

先給**兩種分頁形式**與各自的取捨，並明確建議**面向使用者的列表用游標式**、只有真的需要跳頁的後台才用偏移式且應限制最大頁數。給篩選的原則——明確的參數而非通用的查詢語言（可驗證、可對應索引、不會被寫出打垮資料庫的查詢）。給排序的限制（支援哪些排序等於決定要建哪些索引）。加分點有三個：**游標的排序鍵必須唯一**（通常要加主鍵形成複合游標）且應該編碼成不透明字串，理由是讓伺服器保留改變內部表示的自由而非為了安全；「總筆數」是最常見的產品需求衝突，而**很多時候正確答案是改變 UI**；以及篩選參數的組合會產生索引爆炸，務實的做法是用使用統計識別真正常用的組合並對罕見的組合要求必須帶有索引的條件。

## 講稿

分頁有兩種形式。偏移式直觀而且支援跳頁，但深分頁時效能隨頁碼線性下降，而且翻頁期間有新資料插入會導致重複顯示。游標式的效能跟頁碼無關而且翻頁期間穩定，但不支援跳頁。

我的建議是面向使用者的列表用游標式，配合載入更多或無限捲動。只有真的需要跳頁的管理後台才用偏移式，而且應該限制最大頁數。

篩選的原則是明確的參數而不是通用的查詢語言。明確的參數可以被驗證、可以對應到索引、也不會讓使用者寫出打垮資料庫的查詢。通用的篩選語言只在真的需要動態組合時才值得。

排序應該限制在有索引支援的欄位。支援哪些排序等於決定要建哪些索引，開放任意欄位排序是一個容易給出但代價高昂的承諾。

總筆數是最常見的產品需求衝突。傳統的分頁介面需要共幾頁，而那需要一次完整計數，在大表上跟主查詢一樣昂貴。很多時候正確的答案是改變介面，因為共一萬多筆這個資訊對使用者的價值，通常遠低於工程上為它付出的成本。

還有一點，篩選參數的組合會產生索引爆炸。我會用使用統計識別真正常用的組合，而不是為每種組合都準備。

## 常見追問

### 游標式分頁怎麼支援「上一頁」？

**核心答案**：**用同樣的機制但反向**——游標記錄「本頁第一筆的排序鍵」，查詢時用相反的比較方向與排序，**取到之後再把結果反轉回來**。所以回應應該同時提供 `nextCursor`（本頁最後一筆）與 `prevCursor`（本頁第一筆）。**Relay 規範的 `startCursor` 與 `endCursor` 正是這個設計。**

**詳細解析**：「上一頁」的實作有一個容易出錯的細節：反向查詢取到的結果是「離游標最近的 N 筆」，**它們的順序與正向的相反**，**必須在回傳前反轉**——忘記這一步會讓上一頁的內容順序是顛倒的。另一個細節是「是否還有上一頁」的判斷：與 `hasNext` 一樣，做法是**多取一筆**（要 20 筆就查 21 筆），**有第 21 筆就表示還有下一頁**，回傳時丟掉那一筆。這個「多取一筆判斷有沒有下一頁」的技巧比執行一次 `COUNT` 便宜得多，而且它是精確的（不像估算值）。

**面試回答方式**：給做法（游標記錄本頁第一筆、反向比較與排序、結果反轉）並提到 Relay 規範的對應設計。加分點是兩個容易出錯的細節：反向查詢的結果順序相反必須反轉（忘記會讓上一頁的順序顛倒）、以及**「多取一筆」判斷有沒有下一頁**——比執行一次 `COUNT` 便宜得多而且是精確的。

### 篩選條件複雜時該怎麼設計？

**核心答案**：**先確認「真的需要那麼複雜嗎」**。多數列表 API 的實際使用只有幾種固定的組合——用使用統計驗證這一點，而不是憑想像設計。**如果真的需要動態組合**，選項有：**結構化的查詢參數**（`?filter[status][eq]=ACTIVE&filter[amount][gte]=100`——**囉嗦但明確且可驗證**）、**POST 一個查詢物件**（適合非常複雜的條件，**代價是不再是可快取的 GET**）、或者 **GraphQL**（把查詢能力交給客戶端，代價是伺服器端的效能與安全控制變難）。

**詳細解析**：「把查詢能力開放給客戶端」的代價常被低估。GraphQL 或通用的篩選 DSL 讓客戶端能組合出任意的查詢——而其中某些組合可能沒有索引支援、或者觸發笛卡兒積、或者一次拉出過多資料。**防護需要額外的機制**：查詢複雜度的計算與上限、深度限制、以及每個欄位的成本標記。這些在 GraphQL 的生態中有成熟的方案，但它們是必須做的工作而非可選的——沒有它們的 GraphQL 端點等於把資料庫直接暴露給客戶端。所以「開放查詢能力」的決定應該連同「怎麼防護」一起做，而不是先開放再補防護。

**面試回答方式**：先建議確認「真的需要那麼複雜嗎」並用使用統計驗證。給三種選項與各自的代價。真正的加分點是展開「把查詢能力開放給客戶端」的代價常被低估——客戶端能組合出沒有索引支援或拉出過多資料的查詢，防護需要查詢複雜度上限、深度限制、欄位成本標記，而這些是必須做的工作而非可選的。收在：沒有防護的 GraphQL 端點等於把資料庫直接暴露給客戶端，所以開放查詢能力的決定應該連同防護一起做。

### 列表 API 的回應該包含多少資料？

**核心答案**：只包含列表視圖真正需要的欄位，而不是完整的實體。理由有三：**回應體積**（一百筆記錄各帶 30 個欄位是不必要的傳輸）、**查詢成本**（少取欄位可能達成覆蓋索引、也避免了關聯的載入）、以及**契約的穩定性**（列表視圖的欄位比完整實體穩定得多）。需要完整資料時，客戶端再對單一項目發一次請求。

**詳細解析**：這帶出「列表與詳情用不同的 DTO」這個設計，而它的價值不只是效能：**兩個視圖可以獨立演進**——詳情頁新增一個欄位不影響列表的效能，而列表新增一個彙總欄位也不影響詳情。**代價是多一組 DTO 與映射**，但那通常是划算的。**另一個常見的問題是「N+1 的請求」**——客戶端拿到列表後對每一筆各發一次詳情請求。處理方式是提供「批次取得」的端點（`?ids=1,2,3`）或者在列表中就包含常用的關聯資料。**GraphQL 的 DataLoader 正是為了解決這個問題**，**而在 REST 上它需要明確的 API 設計**——認出「客戶端會怎麼用這個 API」是避免這類問題的關鍵。

**面試回答方式**：給明確主張（只包含列表視圖需要的欄位）與三個理由（體積、查詢成本、契約穩定性）。展開「列表與詳情用不同的 DTO」的價值不只是效能——**兩個視圖可以獨立演進**。加分點是提出**客戶端的 N+1 請求問題**與處理方式（批次端點、或列表中包含常用關聯），並指出 GraphQL 的 DataLoader 正是為此而在 REST 上需要明確的 API 設計。收在：認出「客戶端會怎麼用這個 API」是避免這類問題的關鍵。
