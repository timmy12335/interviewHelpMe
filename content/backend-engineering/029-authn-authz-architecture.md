# 題目

在微服務架構下，認證與授權該放在哪一層？

## 核心答案

**認證（你是誰）應該集中在入口**——API 閘道或服務網格驗證憑證（JWT 的簽章、或 session 的有效性），把驗證過的身分傳給下游服務（透過標頭或 mTLS 的憑證身分）。理由是它是一個統一的、與業務無關的關注點，而且集中處理讓憑證的格式與驗證邏輯只有一份。

授權（你能不能做這件事）則必須分層。**粗粒度的路徑保護**（「只有管理員能存取 `/admin/*`」）可以在入口做；**但細粒度的業務授權**（「只能修改自己的訂單」「這個金額超過你的審批額度」）**必須在業務服務裡做**——因為只有那裡知道資料的擁有者與業務規則。

最重要的判斷是「不要只依賴入口的授權」。入口只是眾多入口之一——訊息佇列的消費、定時任務、以及服務之間的直接呼叫都不會經過它。所以業務服務必須自己驗證權限，而不能假設「能呼叫到我就表示有權限」。

**服務之間的呼叫也需要身分**。用 mTLS 或服務帳號的 token 讓每個服務有明確的身分，**而不是「內網就信任」**——那正是零信任架構要糾正的假設。

## 詳細解析

「傳遞已驗證的身分」有兩種常見形式，各有取捨。**繼續傳原始的 JWT**——下游可以自己驗證（不必信任閘道），但每個服務都要有驗證的邏輯與金鑰，而且 JWT 可能很大（每次呼叫都帶著）。閘道驗證後傳一個內部的簡化身分（例如一個標頭帶著 user id 與角色）——下游簡單，但它必須信任閘道，而且必須確保外部無法偽造那個標頭（閘道要主動剝除來自外部的同名標頭，這一步被遺漏就是一個嚴重的權限提升漏洞）。

「服務之間的信任」是零信任架構的核心。傳統的做法是「內網可信」——只要能連到就假設有權限；但一旦有任何一個服務被攻破，或者網路隔離設定錯誤，整個內網就暴露了。零信任的做法是**每次呼叫都驗證身分與權限**，用 mTLS 提供服務身分、用短期的 token 提供授權。**服務網格讓這件事變得可行**——它在 sidecar 層自動處理 mTLS 與策略檢查，**應用程式碼不必改**。這是服務網格最實質的價值之一，比流量管理更難用其他方式取代。

授權模型的選擇影響長期的可維護性。**RBAC**（角色為基礎）簡單直觀但表達力有限（無法表達「只能修改自己的資料」這類與資料相關的規則）。**ABAC**（屬性為基礎）用「主體、資源、動作、環境」的屬性組合規則，表達力強但複雜。**ReBAC**（關係為基礎，Google Zanzibar 的模型）用「誰與什麼有什麼關係」表達，特別適合有複雜共享與繼承的場景（文件的擁有者、編輯者、以及透過資料夾繼承的權限）。多數系統從 RBAC 開始是對的，而在「權限開始與資料綁定」時就該考慮後兩者。

授權的決定點與執行點應該分開。**PDP（策略決定點）**負責回答「這個主體能不能對這個資源做這個動作」，**PEP（策略執行點）**負責在業務流程中呼叫 PDP 並執行結果。分開的價值是策略可以集中管理與審計（例如用 OPA），而不是散落在幾百個 `if` 判斷裡。代價是每次授權檢查多一次呼叫（可以用本地快取或把策略下發到本地評估緩解）。這個分離在權限規則複雜或需要合規審計時特別有價值。

## 面試回答方式

先給認證集中在入口、授權必須分層的核心分工，並說明理由（認證是統一的與業務無關的關注點；細粒度授權只有業務服務知道資料擁有者與規則）。給最重要的判斷：**不要只依賴入口的授權**——訊息消費、定時任務、服務間直接呼叫都不經過它，所以不能假設「能呼叫到我就表示有權限」。加分點有三個：**傳遞身分的兩種形式與取捨**，特別是簡化身分時閘道必須主動剝除來自外部的同名標頭，遺漏這一步就是嚴重的權限提升漏洞；服務網格處理 mTLS 與策略檢查是它最實質的價值之一，比流量管理更難用其他方式取代；以及**授權模型的演進**——RBAC 開始是對的，在「權限開始與資料綁定」時就該考慮 ABAC 或 ReBAC。

## 講稿

我的分工是認證集中在入口、授權必須分層。

認證是你是誰，它是一個統一的、與業務無關的關注點，所以應該在 API 閘道或服務網格驗證憑證，把驗證過的身分傳給下游。

授權是你能不能做這件事。粗粒度的路徑保護可以在入口做，但細粒度的業務授權，比如只能修改自己的訂單，必須在業務服務裡做，因為只有那裡知道資料的擁有者跟業務規則。

最重要的判斷是不要只依賴入口的授權。入口只是眾多入口之一，訊息佇列的消費、定時任務、還有服務之間的直接呼叫都不會經過它。所以業務服務必須自己驗證權限，不能假設能呼叫到我就表示有權限。

傳遞身分有一個容易踩的坑。如果閘道驗證後傳一個簡化的內部標頭，那個標頭必須確保外部無法偽造，閘道要主動剝除來自外部的同名標頭。這一步被遺漏就是一個嚴重的權限提升漏洞。

還有服務之間的呼叫也需要身分，用雙向 TLS 或服務帳號的權杖，而不是內網就信任。那正是零信任架構要糾正的假設。

## 常見追問

### JWT 該不該在每個服務都驗證？

**核心答案**：**看信任模型**。如果閘道之後的網路是完全受控的（服務網格加 mTLS，外部絕對進不來），下游可以信任閘道的驗證結果，不必重複驗——省下每個服務的驗證成本與金鑰管理。**如果無法完全確保這一點**（例如有服務可以被內網的其他系統直接呼叫），**那每個服務都應該自己驗證**。

**詳細解析**：**「重複驗證的成本」比想像中低**——JWT 的簽章驗證是本地的密碼學運算（用非對稱簽章時是一次公鑰驗證），**不需要呼叫外部服務**，通常是微秒級。真正的成本是金鑰的分發與輪換：每個服務都要拿到公鑰、都要處理金鑰輪換（JWKS 端點與快取）。所以「集中驗證」省的主要是維運複雜度而非效能。 一個實用的折衷是「閘道驗證簽章與過期、下游驗證權限範圍」——下游不重複做密碼學驗證，但仍然檢查 token 裡的 scope 或 claim 是否允許這個操作。這樣既省了金鑰管理，又避免了「完全信任上游」的風險。

**面試回答方式**：給判準（信任模型是否完全受控）。真正的加分點是澄清成本——重複驗證的計算成本很低（本地的密碼學運算、微秒級），真正的成本是金鑰分發與輪換，所以集中驗證省的是維運複雜度而非效能。給出實用折衷：閘道驗證簽章與過期、下游驗證權限範圍，既省金鑰管理又避免完全信任上游。

### 服務之間的授權該怎麼做？

**核心答案**：兩個層次。**服務身分的授權**——「訂單服務可以呼叫支付服務的這個端點嗎」，這是服務網格的策略層可以處理的（依來源服務的身分決定是否允許）。**代表使用者的授權**——「這個請求代表的使用者能不能做這件事」，這需要把使用者的身分一路傳下去（token 傳遞或內部標頭），並在最終的業務服務判斷。

**詳細解析**：兩者混淆是一個常見的設計缺陷。只做服務身分的授權意味著「訂單服務能呼叫支付服務」就等於「任何使用者的訂單都能觸發支付」——**而那顯然不對**。只做使用者授權則失去了「限制哪些服務能呼叫哪些端點」的防護——一個被攻破的服務可以呼叫任何內部 API。兩者都需要，而且它們保護的是不同的攻擊面：服務身分防護「橫向移動」，使用者授權防護「越權存取」。OAuth2 的 token exchange 與 on-behalf-of 流程正是為了表達「服務 A 代表使用者 U 呼叫服務 B」這個組合——而理解它需要先分清這兩個層次。

**面試回答方式**：給兩個層次（服務身分的授權、代表使用者的授權）與各自的處理位置。真正的重點是指出**兩者混淆是常見的設計缺陷**——只做服務身分等於任何使用者都能觸發、只做使用者授權則被攻破的服務可以呼叫任何內部 API。強調**它們保護的是不同的攻擊面**：服務身分防橫向移動、使用者授權防越權存取。收在 OAuth2 的 token exchange 正是為了表達這個組合。

### 權限檢查的效能怎麼處理？

**核心答案**：三個方向。**把決定所需的資料帶在 token 裡**（角色、scope、租戶），**避免每次都查資料庫**——代價是 token 變大且權限變更要等 token 過期才生效。**在服務內快取權限資料**（使用者的角色與權限清單），**用短 TTL 加上主動失效**。**把權限條件下推到查詢**（`WHERE owner_id = :currentUser`）——**這同時解決了效能與正確性**，因為它讓「查不到」與「無權限」變成同一件事。

**詳細解析**：第三個方向最值得推薦，因為它不只是效能優化。傳統的做法是「先查出資料、再檢查權限、無權限就拒絕」——那意味著即使無權限也做了查詢的工作，而且如果檢查被遺漏，資料就洩漏了。把條件下推之後，無權限的資料根本不會被查出來——遺漏檢查的風險從「可能洩漏」變成「查不到」。這是「用結構讓錯誤不可能發生」而非「用檢查阻止錯誤」的具體應用，與前面談過的多租戶隔離、參數化查詢是同一個思路。代價是它把權限邏輯滲進了資料存取層，需要小心設計（例如用一個統一的 repository 基底類別自動加上租戶或擁有者條件）。

**面試回答方式**：給三個方向。重點推薦**把權限條件下推到查詢**，並說明它**不只是效能優化**——傳統做法即使無權限也做了查詢工作，而**遺漏檢查就會洩漏資料**；下推之後遺漏的風險從「可能洩漏」變成「查不到」。收在原則：用結構讓錯誤不可能發生，而非用檢查阻止錯誤，並連到多租戶隔離與參數化查詢的同一思路；誠實給出代價（權限邏輯滲進資料存取層，需要統一的基底類別）。
