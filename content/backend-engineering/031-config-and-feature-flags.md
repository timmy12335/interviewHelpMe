# 題目

設定該放在哪裡？功能開關與設定有什麼不同？

## 核心答案

**設定與功能開關的核心差別是「變更的頻率與目的」**。設定是**環境的差異**（資料庫位址、逾時值、執行緒池大小）——**它們在部署時決定，之後很少改**。功能開關是**行為的控制**（要不要啟用新功能、對哪些使用者啟用）——**它們在執行期改變，而且改變是常態**。

**這個差別決定了它們的儲存與更新方式**。設定適合放在**環境變數或設定檔**（跟著部署走、變更需要重新部署或至少重新載入）；功能開關需要**能即時生效的儲存**（設定中心、專門的功能開關服務）並且**不需要重新部署**。

**混淆它們是一個常見的問題**——把功能開關放進需要重啟才生效的設定，等於失去了它的主要價值（快速關閉出問題的功能）;把資料庫密碼放進可以被隨意修改的功能開關系統，則是安全風險。

**機密（密碼、金鑰）是第三類**——它們不該出現在設定檔或環境變數的明文中，**應該用專門的機密管理**（Vault、雲端的 Secret Manager、或 Kubernetes Secret 掛載成檔案）。

## 詳細解析

**功能開關的真正價值是「把部署與發布分開」**。程式碼可以先部署（開關關著、行為不變），**確認部署本身沒問題之後再打開開關**——**於是「部署的風險」與「功能的風險」被分離了**。而且出問題時**關掉開關比回滾部署快得多也安全得多**（不需要重新部署、不會影響同一次部署裡的其他變更）。**這是持續交付的核心實踐之一**，也是它相對於「用分支控制發布」的優勢。

**開關的類型不同，生命週期也不同**。**發布開關**（控制新功能的上線）——**應該是短命的**，功能穩定後就移除。**實驗開關**（A/B 測試）——生命週期是實驗的週期。**營運開關**（緊急降級、限流的開閉）——**長期存在**。**權限開關**（依客戶方案啟用功能）——**永久存在，實際上是產品功能而非技術開關**。**混淆它們會導致「開關債」**：發布開關沒有被移除，於是程式碼裡累積了大量的分支，**而每個分支都是一條需要測試的路徑**。**明確標記每個開關的類型與預期移除時間，是控制這個債務的基本做法。**

**開關的組合會產生測試的爆炸**。10 個獨立的布林開關有 1024 種組合，**而測試不可能覆蓋全部**。**務實的做法是「限制同時存在的開關數量」並「明確哪些組合是被支援的」**——多數開關在生產環境只有一個明確的狀態（都開或都關），**只有正在發布的那一兩個是真的在變動**。**這也是「發布開關應該短命」的另一個理由。**

**設定的驗證應該在啟動時做**。一個錯誤的設定值（負數的逾時、格式錯誤的位址）**如果只在第一次使用時才出錯，問題會出現在部署後的某個請求上**。**在啟動時驗證並直接失敗，讓錯誤發生在早且明確的地方**——這與前面談過的 `@ConfigurationProperties` 加 `@Validated` 是同一個原則。

## 面試回答方式

先給**核心差別**——設定是環境的差異（部署時決定、很少改），功能開關是行為的控制（執行期改變、改變是常態），並由此推出**儲存與更新方式的不同**。指出**混淆它們的兩種問題**（開關需要重啟就失去主要價值、機密放進可隨意修改的系統是安全風險）並補上**機密是第三類**。加分點有三個：**功能開關的真正價值是把部署與發布分開**——部署的風險與功能的風險被分離，而**關開關比回滾部署快也安全**；**開關的類型不同生命週期也不同**（發布開關該短命、營運開關長期存在），混淆導致**開關債**——每個殘留的分支都是一條需要測試的路徑；以及**開關的組合會產生測試爆炸**（10 個布林開關有 1024 種組合），務實的做法是限制數量並明確支援的組合。

## 講稿

設定跟功能開關的核心差別是變更的頻率與目的。設定是環境的差異，像是資料庫位址、逾時值，它們在部署時決定、之後很少改。功能開關是行為的控制，要不要啟用新功能、對哪些使用者啟用，它們在執行期改變而且改變是常態。

這個差別決定了儲存方式。設定適合放環境變數或設定檔，跟著部署走。功能開關需要能即時生效的儲存，而且不需要重新部署。混淆它們是常見的問題，把開關放進需要重啟才生效的設定，等於失去了它的主要價值。

功能開關的真正價值是把部署與發布分開。程式碼可以先部署、開關關著、行為不變，確認部署本身沒問題之後再打開。於是部署的風險跟功能的風險被分離了。而且出問題時關掉開關比回滾部署快得多也安全得多。

不過開關的類型不同，生命週期也不同。發布開關應該是短命的，功能穩定後就移除。營運開關則長期存在。混淆它們會導致開關債，程式碼裡累積大量分支，而每個分支都是一條需要測試的路徑。

還有一個實際的限制。十個獨立的布林開關有一千多種組合，測試不可能覆蓋全部。所以要限制同時存在的開關數量。

## 常見追問

### 功能開關該怎麼做灰度？

**核心答案**：三種常見的維度。**依比例**（隨機讓 x% 的請求走新路徑——**簡單但同一個使用者可能忽開忽關**，體驗不一致）。**依使用者雜湊**（用 user id 的雜湊決定，**同一個使用者的體驗一致**，這是多數情況下正確的做法）。**依屬性**（內部員工、特定地區、特定方案的客戶——**適合先讓可控的群體試用**）。**實務上通常是組合**：先開給內部員工、再開給 1% 的使用者、逐步放大。

**詳細解析**：**「同一個使用者體驗一致」這個要求比想像中重要**。忽開忽關不只是體驗問題——**如果新舊路徑寫入的資料格式不同，同一個使用者可能產生不一致的資料**。**而且它讓問題無法重現**（使用者回報的問題，你去看時剛好走了另一條路徑）。**所以「依使用者雜湊」應該是預設**，除非有明確的理由用純隨機。**另一個容易忽略的是「灰度的粒度應該與資料的一致性邊界對齊」**——如果一個功能涉及訂單，那應該依訂單而非依使用者灰度（同一個訂單的所有操作走同一條路徑）。**這與分區的設計是同一個判斷：一致性的邊界決定了切分的維度。**

**面試回答方式**：給三種維度並明確推薦**依使用者雜湊是預設**。展開理由：**忽開忽關不只是體驗問題**——新舊路徑寫入的資料格式不同時會產生不一致的資料，**而且讓問題無法重現**。真正的加分點是提出**灰度的粒度應該與資料的一致性邊界對齊**——涉及訂單的功能應該依訂單而非依使用者灰度，**這與分區的設計是同一個判斷：一致性的邊界決定切分的維度**。

### 設定變更該不該經過發布流程？

**核心答案**：**看它的影響範圍與可逆性**。**功能開關的切換應該可以立即執行**（那正是它的價值），但**應該有審計記錄**（誰在什麼時候改了什麼）。**基礎設施相關的設定**（連線池大小、逾時值、執行緒數）**應該經過與程式碼相同的審查流程**——因為它們的錯誤可能造成全面故障，而且沒有測試覆蓋。**折衷的做法是「分級」**：高風險的設定走 PR 流程、低風險的（日誌級別、功能開關）可以即時調整。

**詳細解析**：**「設定變更造成的事故」在事故統計中的比例很高，卻常常被歸類成「人為錯誤」而非「流程缺失」**。一個把連線池從 50 改成 5 的設定變更，**可能造成的損害與一個 bug 相當**——**但它通常不需要 code review、不需要測試、也不會被記錄在變更日誌裡**。**所以「設定即程式碼」（把設定放進版本控制並走相同的審查流程）是一個有價值的實踐**，尤其對基礎設施相關的設定。**代價是失去了即時調整的能力**——而那正是為什麼要分級：**把「需要即時調整」的與「需要審查」的分開存放與管理**，而不是用同一套流程處理所有設定。

**面試回答方式**：給判準（影響範圍與可逆性）與分級的折衷。真正的加分點是指出**「設定變更造成的事故」比例很高卻常被歸類成人為錯誤而非流程缺失**——把連線池從 50 改成 5 的損害與一個 bug 相當，**但它不需要 review、不需要測試、也不在變更日誌裡**。收在「設定即程式碼」的實踐與它的代價，以及**為什麼要分級：把需要即時調整的與需要審查的分開存放**。

### 開關債怎麼清理？

**核心答案**：三個做法。**建立時就設定過期時間**——每個發布開關在建立時就記錄「預期何時移除」，過期時自動告警或建立任務。**定期盤點**——列出所有開關與它們的狀態、最後修改時間、以及所有環境的取值，**「在所有環境都固定為同一個值超過三個月」就是移除的候選**。**把移除納入功能的完成定義**——功能上線並穩定後，移除開關是那個功能的最後一步而非一個獨立的任務。

**詳細解析**：**第三個做法最有效但最需要紀律**。「功能完成」的定義如果只是「上線了」，那開關的移除永遠排不進優先順序——**因為它沒有使用者可見的價值**。**把它納入完成定義，等於承認「留下開關的功能不算做完」**。**這與「文件更新」「監控加上」「舊程式碼移除」是同一類問題**——它們都是完成一項工作的必要部分，**但如果不被明確地包含在定義裡，就會被無限期推遲**。**而推遲的成本不是立即的，是累積的**：每個殘留的開關都增加了一點認知負擔與測試路徑，**幾十個之後系統就變得難以推理了**。

**面試回答方式**：給三個做法。重點展開**第三個最有效但最需要紀律**——「功能完成」如果只是「上線了」，開關的移除永遠排不進優先順序因為它沒有使用者可見的價值；**把它納入完成定義等於承認「留下開關的功能不算做完」**。收在一般化：**這與文件更新、監控加上、舊程式碼移除是同一類問題**，不被明確包含在定義裡就會被無限期推遲，**而推遲的成本是累積的**。
