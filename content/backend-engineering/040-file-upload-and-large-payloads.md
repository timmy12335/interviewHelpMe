# 題目

大檔案的上傳該怎麼設計？為什麼不該讓檔案經過應用伺服器？

## 核心答案

**不該經過應用伺服器的理由有四個**：**佔用應用的執行緒與記憶體**（一個 500MB 的上傳可能佔住一條連線幾分鐘）、**浪費頻寬**（資料進來又出去，應用只是一個中轉）、**限制了水平擴展**（上傳期間那個實例不能被關閉或重啟），以及**逾時與重試困難**（大檔案的傳輸中斷後要從頭開始）。

**標準的做法是「預簽名 URL」（presigned URL）**：**應用產生一個有時效與權限限制的 URL**，**客戶端直接把檔案上傳到物件儲存**（S3、GCS），**完成後再通知應用**。**於是檔案完全不經過應用伺服器**——應用只負責授權與記錄。

**大檔案還需要「分段上傳」（multipart upload）**：把檔案切成多塊分別上傳，**支援斷點續傳與並行上傳**，而且**單塊失敗只需要重傳那一塊**。物件儲存服務都內建了這個能力。

**下載同理**——用預簽名的下載 URL 或 CDN，**而不是讓應用讀取檔案再寫給客戶端**。

## 詳細解析

**「完成後通知應用」這一步有一個容易被忽略的可靠性問題**：客戶端上傳成功但通知失敗（網路中斷、客戶端關閉），**於是物件儲存裡有檔案但應用不知道**。**兩種處理**：**依賴物件儲存的事件通知**（S3 的 Event Notification 觸發 Lambda 或訊息，**這是可靠的**）、或者**定期掃描比對**（列出儲存中的物件與資料庫的記錄，找出孤兒）。**只依賴客戶端的通知是不可靠的**，而那正是很多系統累積孤兒檔案的原因。

**安全性需要仔細處理**。預簽名 URL **本身就是憑證**——拿到它的人就能上傳或下載，**所以它必須有短的有效期**（幾分鐘）、**限制方法與路徑**（只能 PUT 到那個特定的 key）、**並且對上傳限制大小與型別**（S3 的 policy 可以限制 `content-length-range` 與 `Content-Type`）。**沒有大小限制的預簽名 URL 意味著任何人拿到它就能上傳任意大的檔案，那是一個真實的成本攻擊面。**

**檔案的驗證必須在伺服器端做**。客戶端宣稱的 `Content-Type` 與副檔名**都不可信**——**必須在收到通知後檢查檔案的實際內容**（magic number、以及對圖片、PDF 等格式的解析驗證）。**「依副檔名判斷檔案類型」是一個經典的漏洞**——一個 `.jpg` 的檔案可能是任何東西，而如果之後被以錯誤的方式處理（例如放在能被執行的路徑下），就是遠端執行的風險。

**如果因為某些原因必須經過應用**（例如需要在傳輸過程中處理），**那必須用串流而非全部載入記憶體**。一個 500MB 的檔案讀成 `byte[]` 會直接吃掉 500MB 的堆積——**幾個並行的上傳就會 OOM**。**用 `InputStream` 分塊處理、並且明確限制單次請求的大小上限**（在框架層與反向代理層都設，**因為只在應用層設的話，資料已經被讀進來了才發現超限**）。

## 面試回答方式

先給**不該經過應用伺服器的四個理由**（佔用執行緒與記憶體、浪費頻寬、限制水平擴展、逾時與重試困難）。給標準做法**預簽名 URL** 與**分段上傳**，並指出下載同理。加分點有四個：**「完成後通知應用」的可靠性問題**——只依賴客戶端通知不可靠，應該用物件儲存的事件通知或定期掃描比對，**那正是很多系統累積孤兒檔案的原因**；**預簽名 URL 本身就是憑證**，必須有短有效期、限制方法與路徑、**並限制大小與型別**（沒有大小限制是真實的成本攻擊面）；**檔案驗證必須在伺服器端做實際內容的檢查**，「依副檔名判斷」是經典漏洞；以及**必須經過應用時要用串流**，並在**反向代理層也設大小上限**（只在應用層設的話資料已經被讀進來才發現超限）。

## 講稿

不該經過應用伺服器的理由有四個。佔用應用的執行緒與記憶體、浪費頻寬因為資料進來又出去、限制水平擴展因為上傳期間那個實例不能重啟、還有大檔案傳輸中斷後要從頭開始。

標準做法是預簽名 URL。應用產生一個有時效與權限限制的 URL，客戶端直接把檔案上傳到物件儲存，完成後再通知應用。於是檔案完全不經過應用伺服器，應用只負責授權與記錄。大檔案還要用分段上傳，支援斷點續傳而且單塊失敗只需要重傳那一塊。

有一個容易被忽略的可靠性問題。客戶端上傳成功但通知失敗，於是儲存裡有檔案但應用不知道。只依賴客戶端的通知是不可靠的，應該用物件儲存的事件通知，或者定期掃描比對找出孤兒。

安全性也要注意。預簽名 URL 本身就是憑證，拿到它的人就能上傳。所以它必須有短的有效期、限制方法與路徑、而且要限制大小與型別。沒有大小限制的預簽名 URL 意味著任何人拿到就能上傳任意大的檔案，那是一個真實的成本攻擊面。

還有檔案的驗證必須在伺服器端做實際內容的檢查。客戶端宣稱的型別跟副檔名都不可信。

## 常見追問

### 上傳的檔案要怎麼防止惡意內容？

**核心答案**：**多層防護**。**型別驗證**（檢查 magic number 而非副檔名，並用允許清單而非拒絕清單）。**大小限制**（在預簽名的 policy 與反向代理層都設）。**病毒掃描**（對使用者上傳的檔案，尤其是會被其他使用者下載的）。**隔離儲存**（上傳的檔案放在獨立的網域或 bucket，**設定 `Content-Disposition: attachment` 讓瀏覽器下載而非執行**，並且那個網域不應該有應用的 cookie）。

**詳細解析**：**「隔離網域」這一層最容易被忽略但最重要**。如果使用者上傳的 HTML 或 SVG 檔案能從你的主網域被存取，**那就是一個儲存型 XSS**——攻擊者上傳一個包含腳本的檔案，其他使用者存取時腳本在你的網域下執行並能讀取 cookie。**用一個獨立的網域（例如 `usercontent.example.com`）存放使用者上傳的內容，讓同源政策把它隔離開**——這正是 GitHub 用 `githubusercontent.com`、Google 用 `googleusercontent.com` 的原因。**這個防護不需要任何掃描或驗證，它是結構性的**——**而結構性的防護永遠比依賴檢查的防護可靠**。

**面試回答方式**：給多層防護（型別驗證用 magic number 與允許清單、大小限制、病毒掃描、隔離儲存）。重點展開**「隔離網域」最容易被忽略但最重要**——使用者上傳的 HTML 或 SVG 從主網域存取就是儲存型 XSS，**用獨立網域讓同源政策隔離**，並舉 GitHub 與 Google 的例子。收在原則：**這個防護是結構性的，不需要任何掃描或驗證，而結構性的防護永遠比依賴檢查的可靠**。

### 上傳進度與斷點續傳怎麼實作？

**核心答案**：**用物件儲存的分段上傳 API**。客戶端把檔案切塊、逐塊上傳、記錄已完成的塊；中斷後**查詢已上傳的塊清單並只重傳缺的**。進度就是「已完成的塊數除以總塊數」。**這些都在物件儲存的 SDK 裡，不需要自己實作**——**而自己實作的版本幾乎必然會漏掉某些邊界情況**（塊的順序、最後一塊的大小限制、以及未完成的分段上傳會佔用儲存空間並產生費用）。

**詳細解析**：**「未完成的分段上傳會持續產生費用」是一個真實但容易遺漏的成本**。使用者開始上傳一個大檔案然後放棄，**那些已上傳的塊會留在儲存中直到分段上傳被中止或完成**——**而它們不會出現在物件列表裡，所以不會被一般的清理腳本發現**。**S3 的解法是生命週期規則**（`AbortIncompleteMultipartUpload`，自動中止超過 N 天的未完成上傳），**這是一個應該預設設定的規則**。**這類「看不見的成本」在雲端服務上普遍存在**——未完成的上傳、舊版本的物件、以及各種中間狀態，**它們都需要明確的生命週期管理，而預設通常是「永遠保留」**。

**面試回答方式**：給做法（用物件儲存的分段上傳 API）並強調**不需要自己實作，而自己實作幾乎必然漏掉邊界情況**。真正的加分點是指出**未完成的分段上傳會持續產生費用**——那些塊不會出現在物件列表裡所以不會被一般清理腳本發現，**解法是生命週期規則自動中止，而那應該是預設設定**。收在一般化：**這類「看不見的成本」在雲端服務上普遍存在**，都需要明確的生命週期管理而**預設通常是「永遠保留」**。

### 大型的回應（下載、匯出）該怎麼處理？

**核心答案**：**不要在請求中同步產生**。一個需要跑 30 秒才能產生的匯出檔案，同步回應意味著：**佔住連線 30 秒、可能撞到各層的逾時（負載平衡、閘道、瀏覽器）、而且中斷後要從頭開始**。**正確的做法是「非同步產生 + 通知下載」**：請求觸發一個背景任務、立刻回傳一個任務 ID、任務完成後把檔案放到物件儲存並通知使用者（輪詢或推送），**使用者用預簽名 URL 下載**。

**詳細解析**：**「串流回應」是一個中間選項，但它有限制**。用 `Transfer-Encoding: chunked` 邊產生邊回傳，**避免了記憶體的問題也讓使用者更快看到開始**——**但它仍然佔住連線，而且中斷後無法續傳**（除非實作 Range 請求）。**更麻煩的是「錯誤發生在串流中途」**：HTTP 的狀態碼已經送出（200），**無法再改成 500**——**於是使用者收到一個不完整但看起來成功的回應**。**這是串流回應最需要注意的問題**，處理方式是在資料格式中包含一個明確的結束標記（例如 JSON 陣列的閉括號、或者一個 `"status":"complete"` 的尾部欄位），**讓客戶端能判斷收到的是否完整**。

**面試回答方式**：給明確主張——**不要在請求中同步產生**，並列出同步的三個問題（佔連線、撞到各層逾時、中斷要重來）。給正確做法（非同步產生加通知下載）。真正的加分點是**串流回應這個中間選項的限制**：仍然佔連線、無法續傳，**而最麻煩的是「錯誤發生在串流中途」**——狀態碼已送出無法改，**使用者收到不完整但看起來成功的回應**。給處理方式：**在資料格式中包含明確的結束標記讓客戶端能判斷完整性**。
