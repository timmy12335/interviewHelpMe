# 題目

微服務（Microservices）架構下，一個業務操作涉及多個服務各自的資料庫時，怎麼保證資料一致性？2PC、TCC、Saga 這三種分散式事務（Distributed Transaction）方案分別是什麼？各自的優缺點？

## 核心答案

微服務拆分後，一個業務操作(如「下單」同時涉及「訂單服務扣庫存」和「支付服務扣款」)，因為每個服務各自擁有獨立的資料庫，無法再用單一資料庫的本地交易來保證「要嘛全部成功、要嘛全部失敗」，需要專門的分散式事務方案：**2PC（兩階段提交）**——由一個協調者（Coordinator）主導，先讓所有參與者「預備（Prepare）」（鎖定資源、確認可以提交），所有參與者都回報準備好之後，協調者再發出「提交（Commit）」指令；優點是強一致性（Strong Consistency）、對業務程式碼侵入性低，缺點是**同步阻塞、參與者在整個過程中持有鎖、協調者是單點故障**，效能和可用性都不理想，較少在微服務架構中直接使用。**TCC（Try-Confirm-Cancel）**——把每個服務的操作拆成三個階段：Try（預留資源，如凍結庫存但不真正扣除）、Confirm（真正確認執行，如真正扣除凍結的庫存）、Cancel（如果任何一方失敗，釋放之前預留的資源），優點是不需要長時間鎖住資源、效能較好，缺點是**需要業務程式碼自己實作三個階段的邏輯，開發成本高**。**Saga**——把一個大的分散式交易，拆解成一連串本地交易，每個本地交易成功後觸發下一步，如果某一步失敗，透過執行一系列「補償操作（Compensating Transaction）」把之前已經成功的步驟依序復原，優點是**沒有長時間鎖定資源、擴展性好**，缺點是**只能做到最終一致性（Eventual Consistency）（中間存在其他人可能讀到不一致資料的視窗）、補償邏輯設計複雜**。

## 詳細解析

**2PC 的具體流程與問題**：協調者先向所有參與者（各個涉及的資料庫）發送「Prepare」請求，每個參與者執行實際的操作但**先不提交**，鎖定所需的資源，並回報「我準備好了，可以提交」或「我遇到問題，無法提交」;協調者收集完所有參與者的回應，如果全部都回報「準備好了」，就發送「Commit」指令讓所有參與者真正提交(釋放鎖定的資源、讓變更生效);只要有任何一個參與者回報「無法提交」，協調者就發送「Rollback」讓所有人回滾。這個機制的核心問題是——**在「Prepare」到「Commit/Rollback」這整段期間，所有參與者持有的資源鎖都不會被釋放**（因為隨時可能收到協調者的提交或回滾指令，參與者不能自行決定放棄），如果協調者本身在這期間當機（或網路分區導致協調者的指令無法送達），參與者會**一直卡在「已經 Prepare 但不知道最終結果」的懸而未決狀態**,持續持有鎖，可能導致大量資源被長時間佔用，嚴重影響系統的並行處理能力和可用性，這也是為什麼 2PC 在需要高吞吐量、高可用性的微服務場景下，較少被直接採用。

**TCC 如何避免長時間鎖定資源**：TCC 的核心思路是「不要在整個交易過程中，一直鎖著實際的資源」，而是把「鎖定」這個概念，轉化成「業務層面的預留」——以電商庫存為例，**Try 階段**不是「鎖住資料庫的某一行資料不讓別人動」，而是「把庫存數字裡的一部分，明確地標記/凍結成『已預留給這筆訂單，但還沒真正扣除』的狀態」（例如資料表裡除了「總庫存」，額外維護一個「已凍結庫存」欄位，Try 階段只是把這筆訂單需要的數量從「可用庫存」移動到「已凍結庫存」，這個動作本身是一個很快完成的本地資料庫交易，不需要長時間持有鎖）；**Confirm 階段**（所有參與者的 Try 都成功之後觸發），則是「把凍結的庫存，真正地扣除掉」（也是一個很快的本地操作）；**Cancel 階段**（如果任何一個參與者的 Try 失敗），則是「把凍結的庫存，重新釋放回可用庫存」。因為 Try、Confirm、Cancel 都只是各自獨立、快速完成的本地資料庫操作，不需要像 2PC 那樣「持有鎖、等待協調者的最終指令」，TCC 因此能達到比 2PC 好得多的並行效能，代價是——**這三個階段的具體邏輯，都需要開發者自己動手設計和實作**（不像 2PC 可以透過通用的交易協調機制自動處理，TCC 要求每個涉及的服務，都要為自己的操作，額外設計並開發對應的 Try/Confirm/Cancel 三段邏輯），開發和維護成本顯著提高。

**Saga 的兩種編排方式與補償機制**：Saga 把一個大的分散式交易，拆解成一系列的本地交易（例如「下單」拆成「訂單服務建立訂單」→「庫存服務扣庫存」→「支付服務扣款」→「物流服務安排出貨」這幾個各自獨立的本地交易），每一步成功後才觸發下一步；**如果某一步失敗**（例如支付失敗），需要依序（通常是反向）執行「補償操作」，把之前已經成功執行的步驟「復原」（例如把已經扣除的庫存加回去、把已經建立的訂單狀態改成「已取消」），補償操作本身也是一系列獨立的本地交易，而不是像資料庫交易那樣真正的「回滾（Rollback）」。Saga 的編排方式有兩種——**編排式（Orchestration）**，有一個中心化的「編排器（Orchestrator）」明確地知道整個流程的所有步驟，依序呼叫並協調各個服務，失敗時也由編排器決定並觸發對應的補償邏輯，邏輯集中、容易追蹤和除錯，但編排器本身可能演變成一個需要謹慎設計的核心元件；**協同式（Choreography）**，沒有中心化的協調者，每個服務各自訂閱自己關心的事件，完成自己的本地交易後，發布一個事件通知下一個服務接手，失敗時同樣透過發布/訂閱補償事件，讓相關的服務各自執行自己的補償邏輯，這種方式去中心化、服務之間耦合度較低，但整個流程的邏輯分散在各個服務裡，除錯和追蹤相對困難（不容易一眼看出「這個完整的業務流程，到底涉及哪些步驟」）。Saga 因為每一步都是「本地交易先提交生效」，中間過程中，其他人確實有可能讀到「已經執行了部分步驟，但整個大交易還沒完全結束(甚至最終會被補償撤銷)」的中間狀態，只能保證「最終」（所有步驟都成功，或者失敗後所有補償都執行完畢）達到一致，這是它相較於 2PC「強一致性」的明確取捨。

## 面試回答方式

先說明為什麼需要分散式事務——「微服務拆分後，每個服務各自有獨立資料庫，無法用單一本地交易保證跨服務操作的原子性」。依序講出三種方案——2PC(協調者主導兩階段、強一致但長時間鎖資源、協調者單點故障，較少在微服務直接用)、TCC(拆成Try凍結資源/Confirm真正扣除/Cancel釋放，不長時間鎖資源但需要業務自己實作三階段邏輯)、Saga(拆成一系列本地交易，失敗時用補償操作反向復原，擴展性好但只能最終一致、補償邏輯設計複雜)。可以用「下單同時扣庫存+扣款」這個具體場景，讓面試官看到你能把抽象的方案套用到實際情境。如果能延伸講出 Saga 的兩種編排方式(編排式vs協同式)，展現你對這個主題有更深入、更全面的理解。

## 常見追問

### TCC 的 Cancel 階段，如果「Try 階段根本從來沒有成功執行過」(例如網路問題導致 Try 請求根本沒有送達這個服務)，Cancel 操作要怎麼正確處理這種「空回滾」的情況?

**核心答案**：這種情況稱為「**空回滾（Empty Rollback）**」——因為 Try 從未真正執行，理論上 Cancel 應該「什麼都不用做」就直接視為成功(因為根本沒有東西需要被撤銷)。但要正確識別「這是一次空回滾，而不是『Try 明明執行過但因為某種原因需要撤銷』」，關鍵在於**每個服務需要記錄「這筆分散式交易的 Try 階段是否真的執行過」的狀態**(通常在本地資料庫額外維護一張交易狀態記錄表，記錄「這個全域交易 ID 對應的 Try 是否已經執行、目前狀態如何」)——當 Cancel 請求抵達時，先查詢這張狀態表，如果查無記錄(代表 Try 從來沒有被執行過)，直接把這次 Cancel 標記為成功(空操作)，並在狀態表裡也記錄下「這個交易 ID 已經被 Cancel，即使之後 Try 請求遲來抵達，也要能正確識別並拒絕執行」，避免「Cancel 先到、Try 後到」這種訊息亂序抵達，導致 Try 誤以為自己是第一次執行、實際上真正凍結了資源，但這筆交易其實早已被判定應該取消的更複雜問題(這種情況稱為「懸掛/空懸，Try 和 Cancel 出現亂序」)。

**詳細解析**：這題深入 TCC 模式在實務落地時，最容易被忽略、卻極其重要的邊界情況處理，這類細節往往是「紙上談兵地理解 TCC 概念」和「真正動手實作過 TCC 的工程師」之間的分水嶺。「空回滾」之所以會發生，是因為在分散式系統裡，一次完整的 TCC 流程涉及多個網路呼叫(呼叫 Try、可能呼叫 Confirm 或 Cancel)，這些網路呼叫彼此獨立，任何一個都可能因為逾時、網路問題而失敗或延遲，如果整體協調邏輯(通常由類似 Saga 編排器的角色負責)在「呼叫某個服務的 Try 逾時無法確定成功與否」的情況下，基於保守原則選擇對所有已經呼叫過 Try 的服務(以及，萬一無法確定 Try 是否成功的服務)都發起 Cancel(寧可錯殺不可錯放，確保最終不會有『資源被錯誤地永久凍結』的情況)，就可能出現「這個服務的 Try 請求，其實還在網路傳輸的路上，還沒有真正抵達並被執行，但 Cancel 請求卻先一步(透過另一條網路路徑或因為 Try 本身處理較慢)抵達了」這種訊息亂序的情況，如果 Cancel 邏輯天真地假設「一定是先 Try 成功、才會需要 Cancel」，可能會出現各種邏輯錯誤(比如試圖撤銷一個根本不存在的凍結記錄、或者更糟，如果稍後姍姍來遲的 Try 請求真的抵達並執行了，會錯誤地凍結了一筆資源，而這筆資源其實早就應該被視為「已取消」而永遠不該被凍結)。正確處理的核心原則，是讓每個服務，針對「這個特定的分散式交易(通常用一個全域唯一的交易 ID 來識別)」，維護一個明確的**狀態機記錄**——不管 Try、Confirm、Cancel 這幾個請求以什麼樣的順序、什麼樣的時間點抵達，服務都能透過查詢這個交易 ID 對應的狀態記錄，正確地判斷「目前應該怎麼處理這個請求」：如果 Cancel 請求抵達時，查無這筆交易的任何記錄(代表 Try 還沒抵達，或者根本永遠不會抵達)，就把這次的 Cancel 標記為成功，同時**在狀態表裡明確記錄下「這筆交易已經被判定要取消」**這個事實;之後如果姍姍來遲的 Try 請求終於抵達，它應該先查詢這個狀態表，發現「這筆交易早就已經被標記為要取消了」，就應該直接拒絕執行 Try 邏輯(不能傻乎乎地真的去凍結資源)，避免了「Cancel 先到、Try 後到，導致資源被錯誤地凍結，且再也沒有機會被正確撤銷」這種更嚴重的資源洩漏問題。理解「TCC 的正確實作，遠不只是『寫三個函式(Try/Confirm/Cancel)』這麼簡單，還必須額外設計一套能夠正確處理『請求亂序抵達』這類分散式系統固有不確定性的狀態記錄機制」，展現你對 TCC 這個模式的實務複雜度有深刻、紮實的理解，而不只是停留在教科書式的三階段概念描述。

**面試回答方式**：先給出「空回滾」的定義——「Try 從未真正執行過，Cancel 應該視為空操作直接成功」。給出正確的處理機制——「每個服務需要為每筆分散式交易維護一個狀態記錄(用全域交易ID識別)，Cancel 抵達時先查詢這個記錄，查無記錄就標記為空回滾成功，並且記下『這筆交易已被取消』,避免之後姍姍來遲的 Try 請求誤以為自己是第一次執行而真的凍結了資源」。可以點出更深層的問題——「這其實是在處理『Cancel 和 Try 可能以任意順序抵達』這種分散式系統固有的訊息亂序問題，這類邊界情況的正確處理，往往是紙上談兵理解 TCC 和真正實作過 TCC 的工程師之間的分水嶺」。展現你理解 TCC 實作遠比「寫三個函式」複雜，需要額外的狀態機設計來應對這些邊界情況。

### Saga 模式的「補償操作」，是不是簡單地把原本的操作「反過來做」就可以了?有沒有補償操作本身也可能失敗、或無法簡單反向操作的情況?

**核心答案**：補償操作**不總是簡單的「反向操作」**，有幾種情況會讓補償變得更複雜：**（1）補償操作本身也可能失敗**——如果補償操作(例如「把已經扣除的庫存加回去」)本身因為某種原因(如資料庫暫時連不上)執行失敗，需要有可靠的重試機制，確保補償最終一定會成功執行，否則系統會停留在一個「部分完成、且補償也失敗」的不一致狀態，無法恢復；**（2）某些操作根本無法簡單地反向撤銷**——例如「已經發送出去的 Email 通知」，沒辦法真正把它「收回來」，補償能做的頂多是「發送另一封『之前的通知作廢，請忽略』的說明信」，這是一種語意上的補償而非真正的撤銷；**（3）如果在補償開始之前，原本的操作結果已經被其他交易讀取並依賴，單純撤銷可能導致連鎖的不一致**——例如庫存被扣減後，另一筆交易緊接著讀到了「扣減後的庫存數字」並基於這個數字做了自己的業務決策，如果原本的扣減操作事後被撤銷(補償)，那個依賴了舊(已扣減)數字的交易，可能因此變得不再正確。

**詳細解析**：這題破除「補償操作就是簡單地把之前做的事情倒過來做一遍」這種過於簡化的理解，揭示 Saga 模式在實務設計中真正的難點所在。「補償操作本身可能失敗」這個問題，聽起來像是一個顯而易見的邊界情況，但如果沒有仔細設計，很容易被忽略——很多開發者在設計 Saga 流程時，把大部分注意力放在「正向流程怎麼一步步推進」，卻假設「補償操作一定會順利執行成功」，但補償操作本身，終究也是一次跨網路的呼叫、一次資料庫寫入操作，它一樣可能遇到網路問題、資料庫暫時不可用等各種故障，如果補償失敗且沒有可靠的重試機制，系統可能會卡在一個「有些步驟已經完成、有些步驟的補償也失敗了，整個業務流程既沒有成功完成、也沒有被完全撤銷回到一致狀態」的尷尬中間狀態，需要靠人工介入才能解決，這是 Saga 模式實務落地時，必須認真投入設計(通常需要補償操作也具備冪等性（Idempotency）、並搭配持久化的重試佇列或排程任務，確保補償請求最終一定會被送達並成功執行)的一環。「某些操作無法真正反向撤銷」這個問題，更是直指補償這個概念的本質局限——Saga 的補償，不是資料庫交易那種「精確地把資料還原到操作之前的位元組狀態」的真正回滾，而是「用一個新的、語意上代表『抵銷/作廢』的業務操作，去盡量抵銷掉之前操作造成的影響」，對於「發送通知」、「呼叫了一個外部第三方系統且對方已經根據這次呼叫採取了進一步行動(比如已經開始物理揀貨出貨)」這類操作，單純的「反向撤銷」在語意上根本不存在或不完整，補償設計者必須針對每一種具體操作，仔細思考「這個操作的影響，實際上能不能被抵銷、要怎麼抵銷、抵銷不了的部分要怎麼處理(例如接受這個影響已經造成，轉而透過人工客服或事後補償措施處理)」，這需要對每個涉及的業務環節有深入的理解，而不是套用一個通用的公式。第三種情況(其他交易已經依賴了尚未補償的中間狀態)則揭示了 Saga「最終一致性」這個特性帶來的更深層挑戰——因為 Saga 的每一步都是立即提交生效的本地交易(不像 2PC 那樣，在最終確認之前，其他人完全看不到任何中間狀態的變化)，這意味著「這筆訂單的庫存已經被扣減」這件事，一旦第一步的本地交易提交，就立即對系統的其他部分(甚至其他完全不相關的交易)可見了，如果之後因為某個後續步驟失敗而需要補償撤銷這次扣減，但這段期間已經有其他交易讀取並依賴了「扣減後」的庫存數字做出了自己的決策(例如另一筆訂單，看到扣減後的庫存還夠，所以也順利地完成了下單)，簡單地補償撤銷第一筆交易的扣減，理論上不會直接讓第二筆交易的資料「出錯」（因為第二筆交易讀到的是它讀取當下的真實數字，補償只是把庫存加回去，不會去修改第二筆交易已經產生的結果），但這確實反映了 Saga「中間狀態對外部可見」這個特性，可能帶來一些微妙的、需要在業務邏輯設計時謹慎考量的連鎖效應（是否需要額外的隔離機制，或者接受這種程度的「暫時性不精確」是業務可以容忍的）。理解「Saga 的補償操作，遠不只是簡單的『反向操作』,還需要考慮補償本身的可靠性(冪等重試)、某些操作在語意上根本無法真正撤銷(只能做語意上的抵銷)、以及中間狀態對外可見所帶來的連鎖效應」，展現你對 Saga 模式的實務複雜度有超越教科書定義的深刻理解。

**面試回答方式**：先破除「補償就是簡單反向操作」的誤解——「不是，有幾種情況會讓補償變得複雜」。列舉三種情況——「補償操作本身也可能失敗，需要可靠的重試機制(否則系統卡在既沒完成也沒撤銷的中間狀態)」、「某些操作根本無法真正反向撤銷(如已發送的Email，只能發送作廢說明，是語意上的抵銷而非真正撤銷)」、「Saga 每一步都立即提交生效，其他交易可能已經依賴了尚未補償的中間狀態，補償撤銷可能帶來需要謹慎考量的連鎖效應」。展現你對 Saga 補償機制的實務複雜度有超越「反向操作」這種簡化理解的深刻認識。

### 在什麼情況下，應該優先考慮「根本避免跨服務的分散式事務」，而不是在 2PC/TCC/Saga 之間選擇?

**核心答案**：最理想的情況是，在做微服務拆分和資料庫設計時，就**盡量把「經常需要在同一個交易裡一起變更的資料」放在同一個服務、同一個資料庫裡**，從架構設計的源頭上，避免產生「一個業務操作，必須跨越多個服務的資料庫邊界」這種需求，這樣一來原本可能需要分散式事務的操作，可以直接退回到單一資料庫的本地交易，享受本地交易天然、高效、強一致的保證，完全不需要引入 2PC、TCC 或 Saga 這類複雜的機制。這通常需要**重新審視服務拆分的邊界是否合理**(是否按照真正的業務領域/限界上下文(Bounded Context)劃分，而不是過度細碎地拆分，導致原本應該是一個整體的業務操作，被硬生生切割到多個服務裡)，或者採用**資料冗餘**(接受一定程度的資料重複，讓某個服務保有一份「唯讀的、最終一致的」其他服務資料副本，避免每次操作都需要跨服務同步呼叫)等設計手法，從根本上減少對分散式事務的依賴。

**詳細解析**：這題把視角從「怎麼在 2PC/TCC/Saga 這三個選項裡挑一個最合適的」，拉高到「是不是一開始就不應該讓自己陷入需要分散式事務的困境」這個更根本的架構設計層次，展現對這整個問題領域的成熟認識——分散式事務(不管選用哪一種方案)，本質上都是在為「微服務拆分」這個架構決策的某種副作用「擦屁股」，2PC 犧牲了效能和可用性、TCC 大幅提高了開發成本、Saga 犧牲了強一致性並帶來補償邏輯的複雜度，這三者沒有一個是「沒有代價的完美解法」，這意味著，最好的分散式事務，其實是「根本不需要用到分散式事務」。這引導我們反思一個更根本的問題——「為什麼這個業務操作，一開始就被拆分到了多個服務裡?」很多時候，這是因為服務拆分的邊界劃分不夠合理——例如，如果「訂單」和「庫存」這兩個概念，在業務語意上其實高度耦合(每次下單幾乎都同時涉及扣庫存，兩者很少被獨立地單獨操作)，把它們拆成兩個完全獨立的服務、各自擁有獨立的資料庫，可能是一個過早或過度的拆分決策，導致原本在單體架構下，一行 SQL 交易就能搞定的操作，現在需要引入複雜的分散式事務機制才能達到類似的效果，這種情況下，重新審視並可能合併這兩個服務的邊界(或者至少讓它們共用同一個資料庫)，可能是比「努力在 TCC 和 Saga 之間挑一個」更根本、更務實的解法——微服務架構的一個常見教訓是「拆分的粒度需要對應到真正獨立的業務能力(領域驅動設計裡的『限界上下文』概念)，而不是為了拆分而拆分，過度細碎的拆分，往往正是導致『到處都需要分散式事務』這種痛苦的根源」。「資料冗餘」是另一種務實的緩解手法——如果兩個服務之間，確實有著合理的業務邊界(不適合合併)，但又頻繁需要彼此的資料做業務判斷(例如訂單服務，在建立訂單時，需要知道使用者的等級以決定運費折扣，而使用者等級是使用者服務管理的資料)，與其每次都跨服務同步呼叫(增加耦合和呼叫失敗的風險)，可以考慮讓訂單服務，透過訂閱使用者服務發布的「使用者等級變更」事件，在自己的資料庫裡，維護一份「最終一致的、稍微有延遲但足夠新鮮」的使用者等級唯讀副本，訂單服務需要判斷運費折扣時，直接查詢自己本地的這份副本資料即可，不需要每次都發起一次跨服務的同步呼叫，這種手法某種程度上是用「接受一定程度的資料冗餘和最終一致性」，換取「大幅減少跨服務即時互動的必要性，進而減少對分散式事務的依賴」。理解「分散式事務的三種方案，都是有代價的權宜之計，更成熟、更根本的思路，是透過合理的服務邊界劃分和適度的資料冗餘設計，盡量從架構源頭上減少真正需要分散式事務的場景」，展現你對這整個問題領域，有超越「怎麼選方案」這個技術實作層次、上升到「架構設計本身」這個更高視角的成熟認識。

**面試回答方式**：先給出核心觀點——「最好的分散式事務，是根本不需要用到分散式事務，三種方案(2PC/TCC/Saga)沒有一個是沒有代價的完美解法」。給出具體做法——「重新審視服務拆分邊界是否合理(按照真正的業務領域/限界上下文劃分，而非過度細碎拆分)，把經常需要一起變更的資料放在同一個服務同一個資料庫，直接退回本地交易」。補充「資料冗餘」這個折衷手法——「如果服務邊界合理但確實需要頻繁互相依賴資料，可以透過訂閱事件維護一份最終一致的本地唯讀副本，減少跨服務同步呼叫的必要性，進而減少對分散式事務的依賴」。展現你對這個問題領域有超越「技術方案選型」、上升到「架構設計本身」這個更高視角的成熟認識。
