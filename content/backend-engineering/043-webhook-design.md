# 題目

要為外部開發者提供 Webhook，需要考慮哪些設計問題？

## 核心答案

Webhook 是「**把事件主動推送到使用者提供的 URL**」——它把「使用者輪詢」換成了「我們推送」，**代價是我們承擔了投遞的可靠性責任**。

必須設計的有五項。**簽章驗證**——接收方要能確認「這真的是你發的」，標準做法是用共享密鑰對 payload 做 HMAC 並放在標頭中，**同時包含時間戳以防重放**。**重試策略**——接收方可能暫時不可用，需要指數退避的重試（例如 1 分鐘、5 分鐘、30 分鐘、2 小時⋯⋯持續一到三天）。**冪等性支援**——每次投遞帶一個唯一的事件 ID，**讓接收方能去重**（因為重試意味著同一個事件可能被投遞多次）。**順序不保證**——明確告知接收方事件可能亂序到達，**並在事件中包含時間戳或序號讓他們能處理**。**可觀測性**——讓使用者能查看投遞的歷史、失敗的原因、並手動重發。

**最容易被低估的是「接收方是不受控的」**——它可能很慢、可能回傳錯誤的狀態碼、也可能在收到後才崩潰。

## 詳細解析

**「接收方不受控」帶來的風險必須被隔離**。一個很慢的接收端點會佔住投遞的工作者——**如果沒有隔離，一個壞掉的接收方會拖垮整個 Webhook 系統**。**處理方式是**：**嚴格的逾時**（幾秒）、**按接收方（或按客戶）的並行度限制**（艙壁隔離）、以及**自動停用持續失敗的端點**（連續失敗 N 次後暫停並通知客戶，**避免對一個已經廢棄的 URL 持續重試**）。

**簽章的實作有幾個容易出錯的細節**。**必須對「原始的位元組」而非「解析後再序列化的物件」計算簽章**——重新序列化可能改變欄位順序或空白而讓簽章不符。**必須用常數時間的比較**（避免時序攻擊）。**必須包含時間戳並拒絕過舊的請求**（防止重放），**而那要求接收方與發送方的時鐘大致同步**。**Stripe 的 Webhook 簽章設計是一個好的參考**——它把時間戳與簽章放在同一個標頭並明確定義了簽章的內容（時間戳加上點號加上 payload）。

**「重試造成的重複」是接收方最常遇到的問題**。發送方送出、接收方處理成功、但**回應在傳輸中丟失**——發送方認為失敗而重試，**接收方收到第二次**。**這是「至少一次」投遞的本質，無法透過任何技巧消除**。**所以文件必須明確要求接收方實作冪等**，並提供事件 ID 讓他們去重。**而很多整合的問題（重複的訂單、重複的通知）根因就是接收方沒有讀那段文件。**

**提供「查看與重發」的介面比想像中重要**。整合的過程中，接收方一定會遇到「我的端點當時掛了」「我處理錯了想重來」的情況——**如果沒有自助的重發功能，那些請求會變成支援工單**。**而一個能看到「這個事件送了幾次、每次的回應是什麼」的介面，讓接收方能自行診斷**，**大幅降低了整合的支援成本**。**這是「開發者體驗即產品」的具體體現**——Webhook 的使用者是開發者，而他們的體驗直接影響整合的成功率。

## 面試回答方式

先給 Webhook 的本質——**把輪詢換成推送，代價是我們承擔投遞的可靠性責任**。列出**五項必須設計的**（簽章、重試、冪等支援、順序不保證的告知、可觀測性）。指出**最容易被低估的是接收方不受控**。加分點有四個：**接收方的風險必須被隔離**——嚴格逾時、按接收方的並行限制、自動停用持續失敗的端點，否則**一個壞掉的接收方會拖垮整個系統**；**簽章要對原始位元組計算**（重新序列化會改變欄位順序而讓簽章不符）、用常數時間比較、並包含時間戳防重放；**「至少一次」的重複無法消除**，文件必須明確要求接收方實作冪等，**而很多整合問題的根因是接收方沒讀那段文件**；以及**提供「查看與重發」的介面大幅降低支援成本**——**這是「開發者體驗即產品」的具體體現**。

## 講稿

Webhook 是把事件主動推送到使用者提供的 URL，它把使用者輪詢換成了我們推送，代價是我們承擔了投遞的可靠性責任。

必須設計的有五項。簽章驗證讓接收方能確認這真的是我們發的。重試策略要用指數退避並持續一到三天。冪等性支援，每次投遞帶一個唯一的事件 ID 讓接收方能去重。明確告知順序不保證。還有可觀測性，讓使用者能查看投遞歷史跟手動重發。

最容易被低估的是接收方是不受控的。它可能很慢、可能回傳錯誤的狀態碼、也可能在收到後才崩潰。所以風險必須被隔離，用嚴格的逾時、按接收方的並行度限制、還有自動停用持續失敗的端點。否則一個壞掉的接收方會拖垮整個系統。

簽章有幾個容易出錯的細節。必須對原始的位元組計算而不是解析後再序列化，因為重新序列化可能改變欄位順序而讓簽章不符。要用常數時間比較避免時序攻擊。還要包含時間戳並拒絕過舊的請求以防重放。

還有一點我想強調，提供查看與重發的介面比想像中重要。沒有自助的重發功能的話，那些請求會變成支援工單。

## 常見追問

### Webhook 與輪詢該怎麼選？

**核心答案**：**Webhook 的優勢是即時性與效率**（不需要一直問「有新的嗎」），**代價是接收方要提供一個公開可達的端點並處理可靠性**。**輪詢的優勢是簡單與可控**（接收方決定何時取、取多少），**代價是延遲與浪費的請求**。**成熟的 API 通常兩者都提供**——Webhook 用於即時通知、輪詢（一個「取得自某個時間之後的事件」的端點）用於補償遺漏與初次同步。

**詳細解析**：**「兩者都提供」不只是為了選擇，更是為了互補**。Webhook 可能因為接收方的問題而遺漏某些事件——**而一個能「拉取歷史事件」的端點讓接收方可以自行補齊**，**這比要求他們開支援工單好得多**。**而且它讓接收方能在初次整合或重建資料時取得完整的歷史。** **這個「推送為主、拉取為輔」的組合與前面談過的「事件驅動為主、定時輪詢為輔」是同一個模式**——**推送負責即時性、拉取負責完整性**，兩者的角色不同因而缺一不可。**認出這個模式，就知道設計 Webhook 系統時應該一併設計那個拉取端點，而不是等使用者抱怨才補。**

**面試回答方式**：給兩者的優劣並主張**成熟的 API 通常兩者都提供**。真正的加分點是說明**「兩者都提供」不只是為了選擇，更是為了互補**——Webhook 可能遺漏事件，而拉取歷史的端點讓接收方自行補齊，**比要求他們開支援工單好得多**，也讓初次整合能取得完整歷史。收在模式的識別：**這與「事件驅動為主、定時輪詢為輔」是同一個模式**，推送負責即時性、拉取負責完整性，**所以設計 Webhook 系統時應該一併設計拉取端點**。

### 接收方一直失敗該怎麼處理？

**核心答案**：**分階段回應**。**短期失敗**（幾次）——正常的指數退避重試。**持續失敗**（例如連續 24 小時全部失敗）——**暫停對該端點的投遞並通知客戶**（郵件或後台的告警），**避免對一個已經廢棄的 URL 持續浪費資源**。**恢復機制**——客戶修好之後能手動重新啟用並補發積壓的事件（或者至少能拉取遺漏的）。

**詳細解析**：**「自動停用」的設計需要小心不要傷害正常的客戶**。一次區域性的網路問題可能讓所有投遞失敗——**如果那時候自動停用了所有端點，恢復後就是一場災難**。**所以停用的判斷應該區分「這個端點的問題」與「我們這邊的問題」**：如果同時間所有端點都失敗，**那多半是我們的問題，不該停用任何人**。**實作上可以用「該端點的失敗率相對於全域失敗率」來判斷**——只有明顯高於全域水準的才停用。**這個「區分局部故障與全域故障」的判斷在很多自動化的保護機制中都需要**（熔斷器、自動摘除節點、自動擴縮），**而缺少它的自動化在全域故障時會加劇問題**。

**面試回答方式**：給分階段的回應（短期退避重試、持續失敗暫停並通知、提供恢復與補發）。真正的加分點是指出**「自動停用」需要小心不要傷害正常客戶**——一次區域性網路問題會讓所有投遞失敗，**那時自動停用所有端點，恢復後就是災難**。給出判斷方式：**用「該端點的失敗率相對於全域失敗率」**，只有明顯高於全域水準才停用。收在一般化：**「區分局部故障與全域故障」在很多自動化保護機制中都需要**，缺少它的自動化在全域故障時會加劇問題。

### Webhook 的安全風險有哪些？

**核心答案**：**兩個方向**。**接收方的風險**——收到偽造的請求（**所以必須驗證簽章**）、以及重放攻擊（**所以簽章要包含時間戳**）。**發送方的風險**——**SSRF**：使用者提供的 URL 可能指向內部服務（`http://169.254.169.254/` 的雲端中繼資料端點、或內網的服務），**於是你的伺服器成了攻擊內網的跳板**。

**詳細解析**：**SSRF 是 Webhook 系統最嚴重也最容易被忽略的風險**。防護需要**在解析 DNS 之後、連線之前檢查目標 IP**——**因為僅檢查 URL 的主機名不夠**（攻擊者可以讓自己的網域解析到內網 IP，這叫 DNS rebinding）。**具體的做法是**：解析出 IP、檢查它不在私有網段（RFC 1918、loopback、link-local）、**然後直接連到那個 IP**（避免在檢查之後 DNS 又被改成別的）。**還要禁止重導向或者對重導向的目標重新檢查**。**更徹底的做法是「從一個隔離的網路環境發出 Webhook」**——一個只有對外網路存取權的專用子網或容器，**於是即使檢查有漏洞，它也連不到內部服務**。**這是「用結構隔離取代邏輯檢查」的又一個例子，而它在安全防護上通常更可靠。**

**面試回答方式**：給兩個方向（接收方要驗簽與防重放、發送方要防 SSRF）。重點展開 **SSRF 是最嚴重也最容易被忽略的**——使用者提供的 URL 可能指向雲端中繼資料端點或內網服務，**你的伺服器成了攻擊內網的跳板**。給具體防護：**在解析 DNS 之後、連線之前檢查 IP**（僅檢查主機名不夠，因為有 DNS rebinding）、直接連到檢查過的 IP、並禁止或重新檢查重導向。收在更徹底的做法：**從一個只有對外存取權的隔離網路環境發出 Webhook**，**這是「用結構隔離取代邏輯檢查」的又一個例子**。
