# 題目

什麼是 API 的冪等性（Idempotency）？為什麼「支付」、「下單」這類操作特別需要考慮冪等性設計？怎麼實作？

## 核心答案

**冪等性**指的是「同一個操作，不管執行一次還是執行多次（使用完全相同的輸入），最終產生的結果都相同」——執行多次不會產生額外的副作用或造成資料狀態的錯誤累積。「支付」、「下單」這類操作特別需要冪等性設計，是因為在分散式系統和不穩定的網路環境下，**客戶端無法百分之百確定一次請求是否真正成功**（例如客戶端發送了扣款請求，伺服器端實際上已經扣款成功，但回應在網路傳輸中遺失，客戶端誤以為請求失敗而重試），如果沒有冪等性保護，這種「因逾時而重試」的正常容錯機制，反而可能導致「重複扣款」、「重複下單」這類嚴重的業務錯誤。實作冪等性最常見的手法是**冪等鍵（Idempotency Key）**——客戶端在發起請求時，附上一個唯一的識別碼（通常是客戶端生成的 UUID），伺服器在處理請求前，先檢查這個冪等鍵是否已經處理過，如果已經處理過，直接回傳「上一次處理的結果」而不重複執行實際的業務邏輯（如再扣一次款）。

## 詳細解析

**為什麼網路環境下「重試」天然帶來重複執行的風險**：在分散式系統中，一次網路請求可能在「傳輸過程的任何一個環節」失敗——請求可能根本沒有送達伺服器（客戶端網路中斷）、也可能請求已經送達且伺服器已經處理完成，只是「回應」在傳回客戶端的路上遺失或逾時（例如伺服器扣款成功了，但回應封包因為網路問題沒有送回客戶端）。從客戶端的視角，這兩種情況「看起來完全一樣」——都是「發出請求後沒有收到成功的回應」，客戶端唯一合理的容錯反應就是「重試」，但如果是第二種情況（伺服器其實已經處理成功），重試就會導致「同一個業務操作被執行了兩次」，如果這個操作是「扣款」，使用者的帳戶就會被扣兩次錢，這是一個嚴重到不可接受的業務錯誤。

**冪等鍵（Idempotency Key）的實作機制**：
1. 客戶端在發起一個「有副作用、且擔心重複執行」的請求時（如支付請求），生成一個唯一的識別碼（通常是 UUID），作為這次業務意圖的「冪等鍵」，並在請求中攜帶這個鍵（通常放在 HTTP Header，如 `Idempotency-Key: abc-123`）。
2. 伺服器收到請求後，先用這個冪等鍵去查詢「這個鍵是否已經被處理過」（通常存在一張獨立的資料表或 Redis 裡，記錄「冪等鍵 → 處理結果」的映射）。
3. 如果這個鍵**還沒被處理過**，伺服器正常執行業務邏輯（如真正執行扣款），並把「這個鍵」和「處理結果」一起記錄下來（通常和實際的業務操作放在同一個資料庫交易裡，確保「業務操作」和「記錄冪等鍵」要嘛一起成功、要嘛一起失敗）。
4. 如果這個鍵**已經被處理過**（不管是剛好同時有另一個相同鍵的請求正在處理中,還是這是一次重試），伺服器**不再重複執行實際的業務邏輯**，而是直接把「當初記錄下來的處理結果」原樣回傳給客戶端，讓客戶端得到和「第一次成功執行」完全相同的回應，即使實際上業務邏輯只被真正執行了一次。

**冪等鍵需要考量的細節**：冪等鍵通常應該有一個**有效期限**（例如 24 小時），避免這張「已處理冪等鍵」的記錄表無限增長；冪等鍵的儲存和「業務操作的執行」必須具有**原子性**（避免出現「業務操作執行成功了，但記錄冪等鍵這個動作卻失敗，導致下次重試時系統誤判『這個鍵還沒處理過』而重複執行」的競態問題，通常透過同一個資料庫交易，或利用資料庫的唯一約束＋樂觀鎖機制來保證）；如果同一個冪等鍵的請求，攜帶的「請求內容」和第一次不同（例如同一個 `Idempotency-Key`，但這次請求的金額卻和上次不一樣），伺服器應該偵測到這個異常並拒絕請求（通常回傳 422 或類似的錯誤），避免呼叫方誤用冪等鍵導致的邏輯錯誤被靜默地忽略。

**GET/PUT/DELETE 天然冪等 vs POST 需要額外設計**：如前面提到的（見 [[001-restful-api-design.md]]），`GET`、`PUT`、`DELETE` 這類方法因為其語意設計，天然就應該是冪等的（`DELETE` 刪除一個已經不存在的資源，結果和刪除前一樣是「不存在」；`PUT` 用同樣的內容多次替換,結果都一樣）；但 `POST`（通常代表「建立一筆新資源」）天生就不是冪等的——每次呼叫都會產生新的資源，這也是為什麼「下單」、「支付」這類本質上是 POST 操作的場景，特別需要額外設計冪等鍵機制來補上「意外重試導致重複建立」這個 POST 語意上原本沒有的保護。

## 面試回答方式

先給出冪等性的定義——「同一操作執行一次或多次,結果相同,不會有額外副作用」。解釋為什麼支付/下單特別需要——「分散式系統中客戶端無法確定請求是否真的成功(可能是伺服器已處理但回應遺失),容錯的重試機制反而可能導致重複執行」，這是理解這題的核心動機。詳細講出冪等鍵的實作機制——生成唯一鍵、伺服器查詢是否已處理、已處理就直接回傳原結果而不重複執行業務邏輯。補充實作細節（有效期限、原子性保證、內容不一致的偵測）能展現你不只知道概念，還有實際落地的經驗。

## 常見追問

### 冪等鍵的儲存和「實際業務操作」要怎麼保證原子性？如果只是簡單地「先查詢冪等鍵表、沒有記錄就執行業務邏輯、再寫入冪等鍵表」，會有什麼問題？

**核心答案**：如果簡單地「先查詢、沒有就執行業務邏輯、再寫入」這三個步驟分開處理（沒有原子性保證），會出現**競態條件（Race Condition）**——如果兩個攜帶相同冪等鍵的請求，幾乎同時抵達伺服器（例如客戶端因為逾時重試，兩個請求前後間隔極短），兩個請求都可能在「查詢冪等鍵表」這一步驟時，發現「還沒有這個鍵的記錄」（因為第一個請求的業務邏輯還沒執行完、也還沒來得及寫入冪等鍵記錄），導致兩個請求都誤判「這是第一次處理」而各自執行了一次業務邏輯，冪等保護完全失效。正確的做法是利用**資料庫的唯一約束（Unique Constraint）**——在冪等鍵表的「冪等鍵」欄位上建立唯一索引，讓「插入這筆冪等鍵記錄」這個動作本身，和實際業務操作在**同一個資料庫交易**裡完成；當第二個併發的請求嘗試插入同樣的冪等鍵時，會因為違反唯一約束而失敗，伺服器捕捉到這個失敗，就能明確知道「已經有另一個請求正在處理（或已經處理完）這個冪等鍵」，進而選擇等待、重試查詢已完成的結果，或返回衝突提示，而不是重複執行業務邏輯。

**詳細解析**：這題深入冪等鍵實作中最容易被忽略、但實務上至關重要的併發正確性問題。「先查詢、再執行、再寫入」這種分成三個獨立步驟的天真實作，在單一請求循序執行的情境下看起來完全正確，但一旦考慮「兩個攜帶相同冪等鍵的請求幾乎同時抵達」這個真實會發生的併發場景（這正是冪等鍵機制原本要解決的核心情境——客戶端因為逾時而重試，導致同一個邏輯請求，實際上產生了兩次網路層面的 HTTP 請求，這兩次請求完全可能因為網路和伺服器排程的巧合，在極短的時間差內先後（甚至幾乎同時）抵達伺服器），「查詢-執行-寫入」這三個步驟之間就存在一個危險的「競態視窗」——如果查詢和寫入不是原子性的，兩個請求都可能在對方還沒來得及寫入記錄之前，各自查詢到「還沒有這個鍵」的結果，於是都各自認為自己是第一個、都去執行了一次業務邏輯，冪等保護在這個極端但完全可能發生的併發情境下失效。正確的解法是利用資料庫本身提供的、真正具有原子性保證的機制——「在冪等鍵欄位建立唯一索引，把『插入這筆冪等鍵記錄』和『執行業務邏輯』包在同一個資料庫交易裡」，這樣一來，即使兩個請求幾乎同時嘗試插入，資料庫本身的唯一約束機制（這是資料庫層面真正原子、由資料庫引擎保證絕對正確的操作,不會有應用層自己實作查詢-判斷邏輯時的競態漏洞）保證了「只有一個請求能成功插入這筆記錄」，另一個請求的插入操作會直接因為違反唯一約束而報錯,伺服器程式碼捕捉到這個特定的資料庫錯誤，就能可靠地判斷「這是一個重複的請求」，進而選擇適當的後續處理（查詢並回傳先前已完成的結果，或者如果先前的請求還在處理中,回傳一個「請稍後查詢結果」的提示）。理解「冪等性保護的正確性,最終要建立在資料庫或某種真正具備原子性保證的底層機制上,而不能只靠應用層『先查後寫』這種看似合理、實則有競態漏洞的邏輯」，展現你對併發正確性有紮實的理解，而不只是知道「冪等鍵」這個概念的表面說法。

**面試回答方式**：先指出天真實作的問題——「查詢、執行、寫入三步驟分開,存在競態視窗:兩個併發的相同冪等鍵請求都可能在對方寫入之前查到『還沒有記錄』,導致冪等保護失效、業務邏輯被執行兩次」。給出正確做法——「用資料庫的唯一約束(在冪等鍵欄位建唯一索引),把插入冪等鍵記錄和執行業務邏輯放在同一個資料庫交易裡,利用資料庫本身真正原子的唯一約束機制,讓第二個請求的插入直接因違反約束而失敗,藉此可靠地偵測重複請求」。展現你理解冪等性的正確性最終要靠資料庫這類真正原子的底層機制保證,而非應用層自己實作的查詢-判斷邏輯。

### 如果一個請求的冪等鍵記錄已經存在，但對應的業務操作「還在處理中、尚未完成」（例如第一個請求的處理耗時較長，第二個重試請求就已經抵達），伺服器應該怎麼回應第二個請求？

**核心答案**：伺服器不應該假裝「處理完成」並回傳一個編造的結果，而應該讓第二個（重複的）請求得知「這個操作正在處理中，請稍候」，常見做法是回傳一個特定的狀態（如 HTTP `409 Conflict` 或自訂的「處理中」狀態碼），並在冪等鍵記錄裡明確地維護一個「狀態欄位」（如 `pending`、`completed`、`failed`），讓伺服器在收到重複請求時，能根據這個狀態欄位判斷該怎麼回應——如果狀態是 `pending`（仍在處理中），告知客戶端稍後重試或提供查詢端點讓客戶端輪詢最終結果；如果狀態是 `completed`，才回傳當初記錄下來的成功結果；如果狀態是 `failed`（第一次處理最終失敗了），則允許客戶端可以放心地發起一次新的、真正的重試（因為第一次確實沒有成功，不存在「重複執行」的風險）。

**詳細解析**：這題深入冪等鍵狀態管理的細節，補上「業務操作本身可能需要一段時間才能完成」這個更貼近真實場景的複雜情況。前面討論的冪等鍵機制,隱含了一個簡化假設——「業務操作要嘛已經完成、要嘛還沒開始處理」，但真實世界裡,業務操作（尤其是涉及外部系統呼叫，如呼叫第三方支付閘道）往往需要一定的處理時間，這段「正在處理中」的中間狀態,如果沒有被正確地建模和處理，會產生新的問題——如果伺服器在「業務操作還在處理中」的當下，收到攜帶同一個冪等鍵的重複請求，如果只是簡單地回傳「還沒有結果，所以視為未處理」，可能導致第二個請求也去執行一次業務邏輯（回到了原本要避免的重複執行問題）；但如果簡單地回傳「已經處理完成」的假結果，這個結果其實還不存在（可能最終會失敗），這會給客戶端錯誤的資訊。正確的設計是把冪等鍵記錄本身,設計成一個具有明確狀態流轉的「小型狀態機」——`pending`（已經有一個請求開始處理這個冪等鍵，業務邏輯正在進行中）→ `completed`（業務邏輯執行成功，結果已經確定並記錄下來）或 `failed`（業務邏輯執行失敗，允許之後真正地重新處理）。當伺服器收到一個攜帶已存在冪等鍵的請求時，先查詢這個鍵目前的狀態——如果是 `pending`，代表「有另一個請求正在處理這個業務邏輯，且尚未有確定的結果」，此時最合適的回應不是猜測或等待（等待可能造成請求執行緒的資源浪費，尤其如果第一個請求耗時很長），而是明確告知客戶端「這個操作正在處理中」（例如回傳 `409 Conflict` 搭配訊息，或者更完善的設計是提供一個獨立的「查詢處理狀態」端點，讓客戶端可以之後主動輪詢最終結果，而不需要重新發起同樣的請求）；如果狀態已經是 `completed`，代表業務邏輯確實執行完成了，直接回傳當初記錄下來的最終結果；如果狀態是 `failed`（處理失敗了，例如第三方支付系統回報交易失敗），這種情況下「重複執行」反而不是問題（因為第一次確實沒有真正成功），可以考慮讓這次的重複請求真正地重新走一次業務邏輯（相當於給客戶端一次「真正的重試機會」），或者依業務規則決定是否允許自動重試。理解「冪等鍵不能只是簡單的『有沒有處理過』的二元狀態，而需要建模成包含『處理中』這個中間狀態的完整狀態機」，展現你對這個機制在真實、有延遲的業務場景下的完整設計有更周全的考慮。

**面試回答方式**：先指出核心問題——「業務操作可能需要一段時間才完成,冪等鍵記錄不能只是簡單的『有/沒有』二元狀態,需要包含『處理中(pending)』這個中間狀態」。給出狀態機設計——「pending(正在處理,回應 409 或提示稍候查詢) → completed(回傳當初記錄的成功結果) 或 failed(允許之後真正重新處理,因為第一次確實沒成功)」。展現你能考慮到「業務操作有處理時間」這個更貼近真實場景的複雜情況,而不只是簡化模型下的冪等設計。

### 除了支付、下單，還有哪些常見的場景特別需要考慮冪等性設計？

**核心答案**：常見還需要冪等性設計的場景包括：**（1）訊息佇列的消費者處理邏輯**——訊息佇列在大多數設計下提供的是「至少一次（At Least Once）」的投遞保證（見 [[012-message-delivery-semantics.md]]），意味著同一則訊息完全可能被消費者重複收到並處理，消費端的業務邏輯必須設計成冪等的，才能正確處理這種重複投遞；**（2）第三方 Webhook 回呼**——外部系統（如支付閘道、物流系統）發送給你的 Webhook 通知，同樣可能因為網路問題而重複發送同一個事件通知，接收端需要用類似冪等鍵的機制（如事件本身攜帶的唯一事件 ID）去重；**（3）定時任務/排程作業**——如果排程系統本身有「重複觸發」的可能性（例如分散式排程在某些故障情況下可能觸發同一個任務兩次），任務的執行邏輯也應該設計成冪等；**（4）庫存扣減、點數/積分發放**——任何涉及「數值增減」且不能容忍重複執行的業務操作，都需要類似的保護機制。

**詳細解析**：這題把冪等性設計的適用範圍，從最容易聯想到的「支付、下單」延伸到更廣泛的分散式系統場景，展現對這個問題本質的理解已經超越了具體的業務案例，觸及到更通用的系統設計原則。冪等性設計之所以在這些場景都同樣重要，根本原因是相通的——**在分散式系統中，任何跨越網路邊界的通訊（不管是客戶端到伺服器的 API 呼叫、訊息佇列的訊息投遞、還是第三方系統的 Webhook 回呼），都無法用簡單的方式保證「精確一次（Exactly Once）」的傳遞語意**，大多數實務系統為了簡化實作和保證訊息不遺失，寧可選擇「至少一次（At Least Once）」這種「寧可重複也不遺漏」的保證，把「處理重複」這個責任，轉嫁給接收方（消費者）自己用冪等設計來吸收。以訊息佇列為例，如果一個消費者處理完一則訊息、正準備向佇列確認（ack）已經處理完成，但恰好在這個確認訊息送出之前當機重啟，佇列因為沒有收到確認，會認為這則訊息還沒被成功處理，重新把它投遞給另一個（或重啟後的同一個）消費者，這種情況下，同一則訊息的業務邏輯就有可能被執行兩次，如果這則訊息代表的是「扣庫存」或「發放點數」，沒有冪等設計就會導致庫存被多扣一次、點數被多發一次。Webhook 回呼的情境類似——很多第三方服務（尤其是支付閘道）為了確保「重要的業務事件通知不會因為你的伺服器暫時無法接收而遺失」，會採用「如果沒有收到你明確的成功回應（如 HTTP 200），就在之後自動重試，可能重試好幾次」的策略，這意味著你的 Webhook 接收端點,同樣需要對「同一個事件被通知了不只一次」這件事有心理準備，並用事件本身攜帶的唯一識別碼做去重處理。理解「冪等性需求的根源在於『分散式系統無法簡單保證精確一次傳遞』這個通用限制，而不是『支付、下單』這幾個特定業務案例的巧合」，展現你能從具體案例中提煉出更普適的分散式系統設計原則。

**面試回答方式**：列舉延伸場景——「訊息佇列消費邏輯(至少一次投遞保證下,同一則訊息可能被重複處理)」、「第三方 Webhook 回呼(外部系統可能因為沒收到成功回應而重複發送同一事件)」、「排程任務(分散式排程某些故障情況下可能重複觸發)」、「庫存扣減/點數發放(任何不能容忍重複執行的數值增減操作)」。用一句話點出共通根源——「這些場景的共同點是,分散式系統裡任何跨網路邊界的通訊,都很難簡單地保證精確一次傳遞,大多數系統選擇『至少一次』並把『處理重複』的責任交給接收方的冪等設計來吸收」。展現你能把冪等性的必要性,提升到一個更普適的分散式系統設計原則層次來理解。
