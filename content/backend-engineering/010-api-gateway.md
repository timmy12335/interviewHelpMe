# 題目

微服務（Microservices）架構中，API 閘道（API Gateway）扮演什麼角色？為什麼需要它？

## 核心答案

API 閘道是微服務架構裡，位於「所有外部客戶端請求」和「內部各個微服務」之間的**統一入口和反向代理（Reverse Proxy）層**。它解決的核心問題是——如果沒有 API 閘道，客戶端（如手機 App、前端網頁）就必須直接知道並個別呼叫「每一個」微服務各自的網路位址，且每個微服務都要自己各自實作「認證、限流（Rate Limiting）、日誌記錄」這些**橫切關注點（Cross-Cutting Concerns）**，造成大量重複工作且客戶端邏輯複雜。API 閘道把這些共通職責集中處理：**（1）請求路由**——根據請求的路徑，把請求轉發到對應的內部微服務；**（2）統一認證與授權**——在閘道層統一驗證 Token 或 API Key，通過後才轉發給後端服務，後端服務不需要各自重複實作認證邏輯；**（3）限流與熔斷**——在閘道層統一實施流量控制；**（4）請求聚合**——把多個微服務的呼叫結果組裝成客戶端需要的單一回應；**（5）協定轉換**——例如把外部的 REST/HTTP 請求，轉換成內部微服務之間使用的 gRPC 呼叫。

## 詳細解析

**沒有 API 閘道時的問題**：假設一個電商系統拆分成「使用者服務」、「訂單服務」、「商品服務」、「支付服務」等多個微服務，如果客戶端（例如手機 App）要直接和這些服務溝通，會遇到幾個問題——**客戶端需要知道每個微服務的網路位址**（且這些位址可能因為服務發現（Service Discovery）機制而動態變化，見 [[009-service-discovery.md]]，客戶端很難自己直接處理這種動態性）；**認證邏輯需要在每個微服務裡重複實作**（每個服務都要各自驗證 Token 是否合法，造成程式碼重複，且如果認證邏輯需要調整，要同步修改所有服務）；**跨多個微服務的請求，需要客戶端自己發起多次呼叫並組裝結果**（增加客戶端複雜度和網路延遲，見 [[001-restful-api-design.md]] 討論過的類似問題）；**每個微服務都要各自處理限流、日誌記錄、監控埋點**這些和自己核心業務邏輯無關，但每個服務都需要的共通功能。

**API 閘道如何集中處理橫切關注點**：API 閘道作為所有外部流量的唯一入口，天然是實施這些共通職責最合適的位置——**認證**方面，閘道統一驗證客戶端攜帶的 Token（如 JWT，見 [[004-jwt-authentication.md]]），驗證通過後，可以把「已經驗證過的使用者身份資訊」透過內部的 Header 傳遞給後端服務，後端服務不需要重新驗證 Token 的合法性，只需要信任並使用閘道傳來的身份資訊即可（這個信任建立在「後端服務只能被閘道呼叫，不能被外部直接繞過」這個網路層面的隔離之上）；**限流**方面閘道可以依照客戶端身份、API 端點、甚至業務規則，統一實施限流策略(見 [[006-rate-limiting-algorithms.md]])，不需要每個微服務各自實作一套限流邏輯；**日誌和監控**方面，閘道天然能記錄「每一個進入系統的外部請求」的完整資訊（來源、時間、回應時間、狀態碼），提供一個系統層級、跨越所有微服務的統一觀測視角。

**請求聚合（Request Aggregation）**：當客戶端需要的資料分散在多個微服務時（例如「訂單詳情頁」需要同時呼叫訂單服務、使用者服務、商品服務），API 閘道可以在自己這一層，代替客戶端發起這幾次內部呼叫，把結果組裝成一個統一的回應再回傳給客戶端，客戶端只需要發一次請求、拿到一次完整的回應，不需要自己處理「發多次請求、等待多個回應、組裝結果」這種複雜邏輯（也減少了客戶端和伺服器之間的網路往返次數，尤其對行動網路延遲較高的場景很有價值）。這種聚合邏輯，有時候會被進一步演化成「BFF（Backend For Frontend）」模式——為不同的客戶端類型（如手機 App、桌面網頁）各自建立一個專門客製化的聚合層，因為不同客戶端需要的資料形狀和聚合邏輯可能差異很大。

**協定轉換**：外部客戶端通常使用標準的 HTTP/REST 或 GraphQL 溝通，但內部微服務之間，為了追求更高的效能，經常採用 gRPC（見 [[022-grpc-vs-rest.md]]）這類更高效但對外部客戶端不夠友善的協定，API 閘道可以承擔「協定轉換」的角色——對外用 REST 接受請求，內部轉換成 gRPC 呼叫實際的微服務，讓「外部友善的協定」和「內部高效的協定」能夠並存，互不衝突。

## 面試回答方式

先給出核心定義——「API 閘道是外部客戶端和內部微服務之間的統一入口和反向代理」。講清楚「沒有 API 閘道」會遇到的問題——客戶端要知道每個服務的位址、認證邏輯要在每個服務重複實作、跨服務請求要客戶端自己組裝。接著逐一講出 API 閘道集中處理的職責——路由、統一認證、限流、請求聚合、協定轉換。可以特別強調「認證」這個例子——閘道統一驗證後，把身份資訊透過內部 Header 傳給後端，後端不需要重新驗證，這是一個很具體、能展現理解深度的細節。如果能提到 BFF 模式或協定轉換，展現你對 API 閘道的應用場景有更全面的認識。

## 常見追問

### 如果 API 閘道統一做了身份驗證，並把驗證後的使用者資訊透過內部 Header 傳給後端服務，後端服務要怎麼確保這個 Header 是真的來自可信的閘道，而不是被偽造的?

**核心答案**：關鍵在於**網路層面的隔離**——後端微服務**不應該直接暴露在外部網路可以直接存取的範圍**,只允許來自 API 閘道所在的網路(如透過防火牆規則、內部網路的 VPC 隔離、或服務網格（Service Mesh）的存取控制)才能連線到後端服務，這樣一來唯一能夠對後端服務發起請求的路徑，就是「先經過閘道驗證，再由閘道轉發」，外部攻擊者無法繞過閘道直接偽造一個帶有身份資訊的 Header，直接打到後端服務。額外的防禦手段還包括——**後端服務可以驗證請求是否確實來自閘道**(例如透過雙向 TLS 憑證驗證，或閘道對每個轉發的內部請求額外附加一個只有閘道和後端服務知道的簽章/密鑰，後端驗證這個簽章)，確保即使網路隔離有疏漏，也有第二層防護。

**詳細解析**：這題觸及一個容易被忽略、但一旦疏忽會造成嚴重安全漏洞的架構前提——「閘道統一驗證、後端信任閘道傳來的身份資訊」這個模式，其安全性完全建立在「後端服務不可能被外部直接繞過閘道存取」這個假設上，如果這個假設不成立(例如後端服務的網路位址意外地可以被外部直接連線到)，整個信任模型就會崩潰——任何人只要知道後端服務的位址，都可以直接偽造一個「我是某個已驗證使用者」的 Header，完全繞過閘道原本應該做的身份驗證，後端服務因為「信任閘道傳來的資訊」，會毫不懷疑地接受這個偽造的身份聲明，造成嚴重的權限繞過漏洞。因此，「網路層面的隔離」是這個信任模型能夠成立的根本前提——透過雲端服務商提供的 VPC(虛擬私有網路)、安全群組規則、Kubernetes 的 NetworkPolicy 等機制，確保後端微服務所在的網路，只允許來自 API 閘道所在網段的連線，外部網際網路完全無法直接連到後端服務，唯一合法的存取路徑，就是先經過閘道(閘道會在轉發之前完成身份驗證)，再由閘道轉發到後端。這種設計某種程度上呼應了「縱深防禦(Defense in Depth)」的安全原則——即使網路隔離萬一因為設定疏漏或某種未預期的方式被繞過，額外加上「後端驗證請求真的來自閘道」這一層(例如透過雙向 TLS，讓閘道和每個後端服務之間，都用憑證互相驗證對方的身份，確保這條連線的兩端，確實是「合法的閘道」和「合法的後端服務」，而不是某個偽裝成閘道的惡意連線)，提供了第二層的保護，即使第一層(網路隔離)因為某種原因失效，依然有機會攔截住偽造的請求。理解「閘道與後端之間的信任關係，不是憑空存在的，而是建立在具體的網路架構隔離和/或密碼學驗證機制之上」，展現你對這類「集中式驗證、下游信任」架構模式背後的安全前提有清晰的認識，而不會想當然地認為「閘道說這是誰，後端就無條件相信」是理所當然、不需要額外考慮安全性的設計。

**面試回答方式**：先給出核心答案——「靠網路層面的隔離，後端服務不直接暴露給外部，只允許來自閘道的連線，外部攻擊者無法繞過閘道直接偽造身份 Header 打到後端」。補充第二層防護——「即使網路隔離有疏漏，也可以透過雙向 TLS 或閘道與後端之間共享的簽章機制，讓後端驗證這個請求確實來自合法的閘道」。點出這呼應「縱深防禦」原則——「不能只依賴單一層防護，網路隔離加上密碼學驗證的雙重保障更穩健」。展現你理解這類「集中式驗證、下游信任」架構的安全前提不是憑空成立的，需要具體的架構和機制去保障。

### API 閘道本身如果承擔太多職責(路由、認證、限流、請求聚合、協定轉換)，會不會變成一個「臃腫」的單體瓶頸，反而違背了微服務架構原本想要達到的目的?

**核心答案**：這確實是一個實務上真實存在的風險，通常稱為「閘道臃腫(Gateway Bloat)」問題——如果把太多業務相關的邏輯(而不只是純粹的橫切關注點)都塞進 API 閘道，閘道本身會逐漸演變成一個難以維護、修改一處可能影響全局、且成為單點故障和效能瓶頸的「新單體」，恰恰違背了微服務架構「拆分獨立、各自可以獨立演進部署」的初衷。緩解這個問題的做法包括：**（1）嚴格限制閘道只處理真正通用、與具體業務邏輯無關的橫切關注點**(認證、限流、路由、基礎的協定轉換)，任何和特定業務規則相關的邏輯，都應該下放到對應的微服務自己實作，不應該塞進閘道;**（2）採用分層閘道架構**——一個面向外部、相對輕量的「邊緣閘道(Edge Gateway)」，加上針對不同客戶端類型各自獨立的 BFF 層(如前面提到的 Backend For Frontend)，把「請求聚合」這類容易變得複雜、且因客戶端而異的邏輯，下放到各自獨立的 BFF，而不是全部集中在同一個閘道裡;**（3）確保閘道本身具備良好的水平擴展（Horizontal Scaling）能力和高可用設計**,避免它成為效能瓶頸和單點故障。

**詳細解析**：這題考察對「API 閘道」這個看似解決了很多問題的架構元件，是否也帶來了自己的新風險有辯證性的認識，而不是片面地認為「引入 API 閘道就是萬靈丹」。API 閘道的價值，在於「集中處理真正通用、與業務邏輯無關的橫切關注點」，但這個「集中」的優勢，如果被過度濫用——例如把「訂單狀態變更時，需要同時通知使用者服務更新積分、通知物流服務安排出貨」這類明顯屬於「業務邏輯編排(Orchestration)」的複雜規則，也塞進 API 閘道去實作——閘道就會從「一個純粹的、通用的基礎設施層」，逐漸演變成「一個承載了大量特定業務規則、和各個微服務的內部邏輯緊密耦合」的龐大元件，這帶來幾個嚴重的問題:首先是**耦合和維護性**,閘道的程式碼開始需要理解和維護各個不同業務領域的具體規則，任何一個業務規則的變動，都可能需要修改閘道，這和微服務架構「每個服務的變動，應該盡量侷限在這個服務自己內部，不應該牽連到其他不相關的元件」的核心目標背道而馳;其次是**單點故障和效能瓶頸**,因為所有外部流量都要經過這一個閘道，如果閘道本身變得臃腫、處理邏輯複雜(尤其如果做了很多同步的請求聚合，等待多個下游服務的回應)，它自己的回應時間和可靠性，會直接決定整個系統對外呈現的效能和可用性上限，如果閘道設計不當，反而會成為「一個新的、隱藏在『微服務』外表下的單體瓶頸」。緩解這個問題的核心原則，是嚴格劃分「什麼該放在閘道」和「什麼不該放在閘道」的界線——閘道應該只承載那些「對所有(或大部分)進入系統的請求都通用適用、且邏輯相對簡單穩定」的橫切關注點(認證、基礎的限流、路由這種相對機械化的職責)，任何涉及「特定業務規則、需要理解某個領域的具體邏輯」的部分，都應該堅持下放到對應的微服務(或專門的業務編排層)去實作，讓閘道保持「薄、通用、穩定」的特性。BFF 模式則是另一種緩解策略——透過為不同客戶端(手機、網頁、第三方開發者)各自建立獨立的聚合層，把原本可能集中在單一閘道裡、因客戶端而異、容易變得複雜的聚合邏輯，分散到各自獨立的 BFF 服務裡，讓核心閘道保持相對單純，同時仍然能滿足不同客戶端的客製化需求。理解「API 閘道本身也需要被謹慎地設計和治理，避免它在解決了『多個微服務各自為政』的問題之餘，自己又演變成一個新的、隱藏的單體瓶頸」，展現你對這個架構模式有辯證、全面而非片面推崇的理解。

**面試回答方式**：肯定這確實是真實存在的風險——「這稱為閘道臃腫問題，如果塞入太多業務邏輯，閘道會演變成新的單體瓶頸，違背微服務拆分的初衷」。給出緩解原則——「嚴格限制閘道只處理真正通用、與業務邏輯無關的橫切關注點(認證、限流、路由)，業務規則相關的邏輯應該下放到對應微服務」。補充「BFF 模式作為分層策略」——「為不同客戶端類型各自建立獨立的聚合層，把容易變複雜的聚合邏輯分散開，而非全部集中在單一閘道」。展現你對 API 閘道這個架構元件，有「它解決了什麼問題、但如果濫用又會帶來什麼新問題」的辯證認識，而非片面地認為它是沒有代價的萬能解法。

### 如果 API 閘道掛了，是不是代表整個系統的所有功能都不可用了?這算不算違反了微服務架構「避免單點故障」的原則?

**核心答案**：確實，如果只部署**單一個**閘道實例，它會是一個明顯的單點故障(Single Point of Failure)——一旦這個實例掛掉，所有需要經過它的外部流量都會受影響，實質上讓整個系統(至少是所有外部可存取的功能)變得不可用，這確實和微服務架構的高可用理念相悖。正確的做法是——**API 閘道本身也應該被設計成一個具備水平擴展和高可用能力的服務**,通常會部署**多個閘道實例**,前面再加上一層**負載平衡（Load Balancing）器**(這層負載平衡器通常設計得極度簡單、穩定，較少變動降低它自己成為故障點的機率)，讓流量分散到多個健康的閘道實例上，即使其中一個或幾個閘道實例故障，負載平衡器能自動把流量導向其他健康的實例，不會因為單一實例的故障而導致整個系統癱瘓。

**詳細解析**：這題直接點出「引入了一個『統一入口』的元件，這個元件本身如果沒有被同樣審慎地設計成高可用，反而會成為一個比拆分微服務之前更集中、更致命的單點故障」這個容易被忽略、但邏輯上顯而易見的風險，考察是否理解「任何被賦予『統一、集中』角色的元件，都必須用同等嚴謹的高可用標準來要求，否則這個集中化的角色本身，就會變成整個架構裡最脆弱的環節」這個通用原則。微服務架構的初衷之一，是透過拆分，避免「一個地方出問題，拖累整個系統」這種單體架構的脆弱性，但引入 API 閘道這個「所有外部流量的統一入口」，某種程度上是在架構裡重新引入了一個「集中化」的元素——如果不謹慎處理，這個閘道反而可能成為一個比原本單體應用更脆弱的單點，因為現在「所有」對外的功能，都依賴這唯一一個閘道實例是否正常運作，一旦它掛了，不只是某一個特定的業務功能受影響，而是「整個系統對外呈現的所有能力」都可能瞬間癱瘓，這種「爆炸半徑(Blast Radius)」反而比微服務拆分之前更大(拆分之前，如果單體應用某個模組壞了，可能還會拖累整個應用，但至少故障的原因是分散在應用內部的某個具體模組;現在如果閘道這個單一元件壞了，故障的影響範圍是「所有外部使用者」)。正確的解法，是把「這個元件需要高可用」這個要求，同樣嚴謹地應用到 API 閘道自己身上——閘道服務本身也應該是**無狀態、可以水平擴展**的(這通常不難做到，因為閘道的核心職責，如路由、驗證 Token、限流檢查，本質上都不需要在閘道實例之間共享太多狀態，頂多是限流相關的計數器需要依賴共享儲存，如前面限流章節討論過的)，部署多個閘道實例，並在這些閘道實例前面，再放一層負載平衡器(這一層負載平衡器，通常會選用相對成熟、穩定、經過長期驗證考驗的技術，如雲端服務商提供的負載平衡服務，或者像 Nginx、HAProxy 這類久經考驗的軟體，盡量降低這一層本身出問題的機率，因為理論上，不管閘道層本身部署得多麼具備高可用性，如果連「把流量分散到這些閘道實例」這一層都不可靠，整個系統依然會有單點故障的風險，高可用設計某種程度上是一層一層往下要求，直到最基礎的網路層)，讓外部流量能夠自動、透明地被分散導向目前健康的閘道實例，即使部分閘道實例故障，系統整體依然能持續正常運作。理解「任何被賦予『集中、統一』角色的架構元件(不只是 API 閘道，包括服務註冊中心、訊息佇列（Message Queue）的協調節點等)，都必須用同等嚴謹(甚至更嚴謹)的高可用標準來設計，否則這個集中化角色本身，反而會成為整個系統裡風險最集中、影響範圍最大的單點」，展現你對「集中化元件需要對應的高可用投入」這個貫穿整個分散式系統設計的通用原則有深刻認識。

**面試回答方式**：先坦承這個風險——「如果只部署單一閘道實例，確實是一個明顯的單點故障，和微服務架構的高可用理念相悖」。給出正確做法——「閘道本身也應該被設計成無狀態、可水平擴展的服務，部署多個實例，前面加一層負載平衡器，讓流量能自動分散並在部分實例故障時導向健康實例」。可以延伸強調「這呼應了一個更普適的原則——任何被賦予『集中、統一』角色的元件(不只是 API 閘道，還包括服務註冊中心等)，都必須用同等嚴謹甚至更嚴謹的高可用標準設計，否則這個集中化角色本身，反而會成為系統裡風險最集中的單點」。展現你能看穿「引入統一入口元件」本身潛藏的新風險，而不是只看到它解決舊問題的一面。
