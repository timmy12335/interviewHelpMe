# 題目

gRPC 相較於傳統的 REST/HTTP+JSON，有哪些技術上的優勢？什麼場景適合用 gRPC、什麼場景適合用 REST？

## 核心答案

gRPC 是 Google 開發的高效能 RPC（遠端程序呼叫）框架，相較於傳統 REST（通常搭配 HTTP/1.1 + JSON），核心技術優勢有：**（1）使用 Protocol Buffers（Protobuf）作為訊息序列化格式**——這是一種二進位格式，相較於 JSON 這種文字格式，序列化/反序列化的速度更快、產生的資料體積更小（省頻寬）；**（2）基於 HTTP/2 協定**——支援「多工（Multiplexing）」（同一條 TCP 連線上,可以同時並行傳輸多個請求和回應,不需要像 HTTP/1.1 那樣受限於連線數量或排隊等待）、支援「雙向串流（Bidirectional Streaming）」（客戶端和伺服器可以在同一個連線上,持續地互相傳送多筆訊息，而不只是一問一答）；**（3）強型別的介面定義（.proto 檔案）**——透過 Protocol Buffers 的 IDL（介面定義語言）明確定義服務的方法簽章和訊息結構，可以自動產生多種程式語言的客戶端和伺服器端程式碼（Code Generation），減少手動維護 API 文件和客戶端程式碼的工作。**適合 gRPC 的場景**——內部微服務（Microservices）之間的高頻通訊（效能和延遲要求高）、需要串流傳輸的場景（如即時資料推送）、多語言環境下需要強型別契約的場景。**適合 REST 的場景**——面向外部、需要廣泛相容性的公開 API（瀏覽器對 gRPC 的原生支援有限）、需要人類可讀、方便除錯的介面（JSON 比二進位格式更容易直接肉眼檢視）。

## 詳細解析

**Protobuf 相較於 JSON 的效能優勢**：JSON 是一種**文字格式**，每一個欄位名稱（如 `"user_id"`）都要完整地以字串形式包含在每一筆訊息裡，且數值、布林值等資料，也都要轉換成文字表示（例如整數 `12345`,在 JSON 裡就是字元 `1`、`2`、`3`、`4`、`5` 這五個位元組），這帶來了不小的冗餘開銷。Protobuf 是**二進位格式**——透過 `.proto` 檔案預先定義好訊息的結構（每個欄位有固定的編號和型別），實際傳輸時，不需要重複傳送欄位名稱這些文字（只需要傳送預先約定好的欄位編號），數值型別也直接用緊湊的二進位編碼表示（而不是轉換成冗長的文字），這使得 Protobuf 序列化後的資料體積，通常比等效的 JSON 小上好幾倍，序列化和反序列化的運算速度也快得多（因為不需要像解析 JSON 那樣,做複雜的文字掃描和型別推斷,而是可以直接按照預先定義好的固定結構,快速地讀取二進位資料）。

**HTTP/2 多工帶來的效能提升**：傳統 HTTP/1.1，即使搭配「持久連線（Keep-Alive）」讓多個請求可以重複使用同一條 TCP 連線，但同一條連線上的請求,依然需要**依序**處理（如果連線上的第一個請求還沒處理完，後面的請求需要等待，這稱為「線頭阻塞 Head-of-Line Blocking」），這也是為什麼很多瀏覽器,會對同一個網域,同時開啟多條並行的 TCP 連線來規避這個限制（但連線數量本身也有實務上的限制）。HTTP/2 引入的「多工」機制，讓**同一條 TCP 連線**，可以同時交錯傳輸多個獨立的請求/回應資料流（Stream），不需要依序排隊等待，也不需要為了並行而開啟多條連線，這對於「一次業務操作,需要同時發起多個獨立呼叫」的場景（例如微服務之間頻繁的內部呼叫），能顯著降低延遲、提升吞吐量。

**強型別契約與程式碼產生**：gRPC 的服務定義（`.proto` 檔案）明確地列出「這個服務有哪些方法、每個方法的輸入輸出訊息結構長什麼樣（每個欄位的名稱、型別、是否為必填）」，這份定義本身就是一份**嚴謹、機器可讀的契約**，可以透過工具鏈,自動產生對應程式語言（Java、Go、Python、C++ 等）的客戶端呼叫程式碼和伺服器端骨架程式碼，開發者不需要手動撰寫「怎麼組裝這次呼叫的請求、怎麼解析回應」這類繁瑣的樣板程式碼，且因為契約是強型別的，很多在傳統 REST + JSON 場景下,需要等到執行期（Runtime）才會發現的錯誤（例如「呼叫方傳了一個字串,但伺服器端預期的是整數」），在 gRPC 的架構下，可以在**編譯期（Compile Time）** 就被靜態型別檢查發現，提前攔截，減少執行期出錯的風險。

**gRPC 的限制與 REST 依然適用的場景**：gRPC 因為依賴 HTTP/2 和二進位的 Protobuf 格式，**瀏覽器的原生支援有限**（傳統瀏覽器的 JavaScript,無法直接、原生地發起標準的 gRPC 呼叫,通常需要額外的轉譯層,如 gRPC-Web，把瀏覽器的呼叫轉換成後端能理解的 gRPC 格式,增加了一層架構複雜度)，因此面向瀏覽器前端或需要被廣泛的外部第三方開發者呼叫的公開 API，REST（搭配標準的 HTTP/1.1 + JSON，任何程式語言、任何瀏覽器,幾乎都能無障礙地直接呼叫）依然是更務實、相容性更好的選擇。此外，JSON 這種文字格式,**對人類而言更容易閱讀和除錯**（可以直接用瀏覽器開發者工具或 `curl` 指令，肉眼檢視回應內容），而 Protobuf 的二進位資料,需要額外的工具才能解讀，在開發除錯的便利性上，REST + JSON 有其不可取代的優勢。因此，實務上很多系統採用「**內部微服務之間用 gRPC**（追求效能、強型別契約），**對外的 API 閘道層轉換成 REST/JSON**（提供給瀏覽器和外部開發者更友善、相容性更好的介面）」這種混合架構（見 [[010-api-gateway.md]] 討論過的 API 閘道協定轉換職責）。

## 面試回答方式

先給出 gRPC 的核心技術優勢——序列化格式(Protobuf二進位,比JSON更快更省頻寬)、傳輸協定(HTTP/2的多工和雙向串流)、強型別契約(.proto定義,自動產生程式碼,編譯期就能發現型別錯誤)。用具體的比較說明「為什麼Protobuf比JSON快」(不用重複傳欄位名稱、二進位編碼比文字編碼更緊湊)和「為什麼HTTP/2多工比HTTP/1.1好」(同一條連線可以並行傳輸多個請求,不需要排隊等待或開多條連線)。給出適用場景的判斷——「內部微服務通訊(效能優先)用gRPC,面向瀏覽器/外部開發者的公開API(相容性優先)用REST」,並提到gRPC對瀏覽器支援有限這個實務限制。可以延伸提到「API閘道做協定轉換,內部gRPC、對外REST」這種常見的混合架構,展現你對這兩種技術在真實系統裡如何協同運作有實務認識。

## 常見追問

### gRPC 的「雙向串流(Bidirectional Streaming)」具體是什麼意思?和傳統 REST 的「一次請求、一次回應」模式有什麼本質差異?適合什麼場景?

**核心答案**：傳統 REST 是嚴格的「請求-回應（Request-Response）」模式——客戶端發送一個完整的請求，等待伺服器處理完成後，回傳一個完整的回應，這一來一往就結束了這次互動。gRPC 的**雙向串流**，允許客戶端和伺服器,在**同一次呼叫建立的連線上**，**持續地、各自獨立地**傳送多筆訊息給對方（不需要像傳統模式那樣,每次都要重新發起一次新的請求），客戶端可以一邊持續發送訊息、一邊同時接收伺服器持續傳來的訊息，兩個方向的資料流是**獨立、非同步**的（不需要「客戶端傳一則、等伺服器回一則」這種嚴格交替的節奏）。這種模式特別適合**需要持續、雙向即時互動的場景**，例如即時聊天應用（雙方都可能隨時傳送新訊息）、即時協作編輯工具（多方的編輯操作需要即時同步給彼此）、或需要持續回報進度的長時間任務（伺服器端可以持續地、主動地推送進度更新給客戶端，不需要客戶端不斷地重複發起請求去輪詢查詢進度）。

**詳細解析**：這題深入 gRPC 相較於傳統 REST 模式,最具突破性的一個特性——串流通訊，考察是否理解這個特性帶來的架構可能性,和傳統請求-回應模式在互動模式上的本質差異。傳統 REST 的請求-回應模式,本質上是一種**同步的、單向發起**的互動——永遠是客戶端主動發起一次完整的請求,伺服器被動地處理並回傳一次完整的回應，這種模式非常適合「查詢一筆資料」、「提交一個表單」這類天然就是「一問一答」性質的互動，但如果業務場景本身,需要「雙方都可能隨時主動傳送新的資訊給對方」（例如即時聊天，雙方都可能在任何時刻打字送出新訊息，不存在誰先誰後的固定順序）,或者「伺服器需要在處理過程中,持續地、主動地回報中間進度」（例如一個需要花費較長時間的批次處理任務，伺服器希望能夠每完成一部分就立即通知客戶端目前的進度百分比，而不是讓客戶端一直乾等到整個任務完全結束才收到唯一一次的回應），傳統的請求-回應模式,要嘛完全無法自然地表達這種持續、雙向的互動(勉強要做的話，可能需要客戶端不斷地重複發起新的請求去「輪詢」詢問「現在的最新狀態是什麼」，這種輪詢的做法,不僅效率低下(浪費大量不必要的請求)，也天生就有「輪詢間隔造成的延遲」這個侷限,永遠不可能做到真正即時)。gRPC 的雙向串流，透過在單一次的呼叫（建立在 HTTP/2 的一個 Stream 之上)，讓客戶端和伺服器,能夠**各自獨立地、隨時**往這條「管道」裡傳送訊息（而不需要嚴格地按照「一問一答」的節奏交替），完美地契合了這類「持續、雙向、即時」的互動需求——客戶端傳送的訊息串流和伺服器傳送的訊息串流,是兩個獨立、平行進行的資料流,伺服器完全可以在還沒收到客戶端的下一則訊息之前，就主動傳送好幾則自己的訊息過去（例如持續地推送進度更新），反過來客戶端也可以持續傳送新訊息,不需要等待伺服器的回應。這種能力,某種程度上,填補了傳統「一次性請求-回應」和「完全獨立的、需要額外基礎設施(如 WebSocket)才能實現的持續連線」之間的一個空白地帶——它讓開發者能夠用一套相對統一、和其他 gRPC 呼叫方式(單次呼叫、伺服器串流、客戶端串流)一致的程式設計模型和工具鏈,來實現原本可能需要引入完全不同技術(如額外搭建 WebSocket 伺服器)才能達成的持續、雙向互動需求，大幅簡化了這類應用的架構設計和開發複雜度。理解「雙向串流打破了傳統『一次請求換一次回應』的互動模式,讓客戶端和伺服器能在同一個連線上,各自獨立、持續地互相傳送訊息,特別適合聊天、協作、進度回報這類需要持續雙向即時互動的場景」，展現你理解 gRPC 這個特性相較於傳統 REST 模式,帶來的架構可能性上的本質差異，而不只是把 gRPC 當成「一種更快的 REST 替代品」這種表面的理解。

**面試回答方式**：先給出本質差異——「傳統 REST 是嚴格的一問一答,gRPC 雙向串流讓客戶端和伺服器能在同一個連線上,各自獨立、持續地互相傳送訊息,不需要嚴格交替的節奏」。舉出適合的場景——「即時聊天(雙方隨時可能傳送新訊息)、即時協作編輯、需要持續回報進度的長時間任務(伺服器主動推送進度,不需要客戶端不斷輪詢查詢)」。點出這個特性的價值——「填補了傳統一次性請求-回應和需要額外基礎設施(如WebSocket)才能實現的持續連線之間的空白地帶,用統一的程式設計模型實現原本需要引入完全不同技術才能達成的持續雙向互動需求」。展現你理解雙向串流帶來的架構可能性,而不只是把 gRPC 當作「更快的 REST」這種表面理解。

### 如果一個團隊已經有大量既有的 REST API,想要逐步遷移到 gRPC,有沒有比較平滑、風險較低的遷移策略?

**核心答案**：常見的平滑遷移策略包括：**（1）先從內部服務間通訊開始遷移，保留外部對外的 REST API 不變**——因為 gRPC 對外部客戶端(尤其是瀏覽器)的相容性有限，優先把「微服務之間彼此呼叫」這類完全在內部控制範圍內、不涉及外部相容性顧慮的通訊，改用 gRPC，能在完全不影響外部使用者和第三方開發者的前提下，先享受到 gRPC 帶來的內部效能提升；**（2）透過 API 閘道做協定轉換，讓外部依然看到 REST 介面，但閘道背後,實際上是呼叫已經遷移成 gRPC 的內部服務**（見 [[010-api-gateway.md]] 討論過的協定轉換職責），這樣一來，遷移對外部客戶端而言完全透明，不需要要求任何外部依賴方修改自己的呼叫程式碼；**（3）漸進式地、逐一服務地遷移**，而不是試圖一次性地把整個系統的所有服務都改成 gRPC,優先選擇「呼叫頻率高、對效能最敏感」的服務先行遷移,驗證效益後再逐步擴大遷移範圍。

**詳細解析**：這題把「gRPC vs REST」這個技術比較，延伸到「一個已經有大量既有系統的團隊,實際上要怎麼在不造成劇烈震盪、不需要一次性大改的前提下,逐步採用新技術」這個更貼近真實工程決策的實務問題,考察是否理解技術遷移，尤其是在複雜、既有系統的背景下，通常需要漸進、務實的策略,而不是一次到位的推倒重來。「先從內部服務通訊開始遷移」這個策略的核心邏輯,是識別出「哪些呼叫關係,是完全在自己團隊/組織的控制範圍內,不涉及需要相容外部第三方或瀏覽器的顧慮」——微服務之間的內部呼叫，正是這樣一類「風險最低、收益最直接」的遷移對象，因為這些呼叫關係的雙方（呼叫方和被呼叫方），都是團隊自己開發和部署的服務，可以一起協調升級到 gRPC，不會受到「外部第三方開發者依然只能發送 REST/JSON 請求,無法直接呼叫 gRPC」這種外部限制的阻礙，同時,微服務之間的內部呼叫，往往也正是對效能和延遲最敏感、最能從 gRPC 的技術優勢中受益的場景（因為內部呼叫的頻率通常遠高於外部 API 呼叫，累積起來的效能提升會更顯著）。「透過 API 閘道做協定轉換」這個策略,則巧妙地利用了 API 閘道原本就承擔的「統一入口、屏蔽內部複雜度」這個職責——外部客戶端看到的，永遠是穩定不變的 REST/JSON 介面（因為這是它們唯一能夠、也習慣呼叫的方式），但這個介面「背後」實際對接的內部服務，可以在閘道層面被悄悄地替換成已經升級為 gRPC 的新實作，整個遷移過程對外部使用者而言完全無感，這種「透過一個中介層,把『外部看到的介面』和『內部實際的實作技術』解耦開來」的思路，是很多技術遷移和架構演進中都會用到的通用手法（本質上呼應了軟體工程裡「抽象層讓外部依賴穩定，內部實作可以自由演進」這個經典原則）。「漸進式地、逐一服務地遷移」則是任何大規模技術遷移都應該遵循的通用工程智慧——與其冒著「一次性把所有東西都改掉,萬一出問題,整個系統全面受影響」的巨大風險,不如選擇一小部分、影響範圍可控、且能夠帶來明確效益驗證的範圍先行嘗試(例如挑選一個呼叫頻率特別高、對效能特別敏感的內部服務),驗證這次遷移確實帶來了預期的效益（並且沒有引入非預期的問題）之後，再有信心地、逐步地擴大遷移的範圍到其他服務，這種「小步快跑、持續驗證」的漸進策略，比「畢其功於一役」的大改，在真實的工程實踐中往往更加穩健可靠。理解「技術遷移(尤其是在複雜既有系統的背景下)，通常需要考慮『從風險最低、收益最明確的範圍開始』、『用抽象層(如API閘道)把外部依賴和內部實作解耦,讓遷移對外透明』、『漸進式、逐步擴大範圍,而非一次到位』這幾個通用的遷移策略原則」，展現你不只知道 gRPC 和 REST 的技術差異，還理解在真實、複雜的既有系統背景下，怎麼務實、穩健地推動這類技術升級。

**面試回答方式**：給出三個漸進策略——「先從內部微服務通訊開始遷移(風險低、收益直接,不受外部相容性顧慮限制)」、「透過 API 閘道做協定轉換,外部看到的 REST 介面不變,閘道背後悄悄替換成已遷移的 gRPC 內部服務,對外部客戶端完全透明」、「漸進式逐一服務遷移,先挑呼叫頻率高、對效能敏感的服務驗證效益,再逐步擴大範圍,而非一次性全面改造」。展現你理解技術遷移在真實複雜既有系統背景下,需要的是務實、漸進、風險可控的策略,而非教條式地一次性推翻重來。

### gRPC 的強型別契約(.proto 檔案),如果需要修改一個訊息結構(比如新增或移除欄位),要怎麼確保不會破壞既有的、還沒更新的客戶端?

**核心答案**：Protocol Buffers 的設計，本身就內建了一套「向後相容」的欄位演進規則——**每個欄位都有一個固定的編號（Field Number）**，這個編號才是序列化/反序列化時真正用來識別欄位的依據（而不是欄位名稱），只要遵循幾個核心原則,就能安全地演進訊息結構：**（1）新增欄位時,使用一個全新的、之前沒有用過的欄位編號**——舊版本的客戶端(不認識這個新編號)會直接忽略它,不會因此出錯；新版本的客戶端能正確讀取到這個新欄位；**（2）絕對不要重複使用(重新指派)一個曾經被使用過、但後來被移除的欄位編號給一個新的、意義不同的欄位**——這會導致舊資料(用舊編號儲存的舊欄位資料)，被新版本的程式碼,誤判成是新欄位的資料，造成資料混淆的嚴重錯誤；**（3）移除一個欄位時,建議明確地把這個欄位編號標記為 `reserved`（保留）**，防止未來不小心又把這個編號重新分配給其他新欄位,造成前述的混淆問題。

**詳細解析**：這題深入 Protobuf 這個技術，在「API 版本演進、向後相容」這個之前已經在其他章節(見 [[002-api-versioning.md]])深入討論過的通用主題上,具體展現了什麼樣的機制設計，讓開發者能安全地演進訊息結構而不破壞既有客戶端。理解這裡的關鍵，在於認識到 Protobuf 序列化格式的一個核心設計決策——**訊息在被序列化成二進位資料時，並不會包含欄位的名稱（不像 JSON 那樣,每個欄位都要完整地攜帶自己的名稱字串），而是只使用一個緊湊的數字編號來代表每個欄位**（這也是前面提到 Protobuf 之所以比 JSON 更緊湊、更節省頻寬的原因之一），這意味著，「一個 .proto 檔案裡,某個欄位到底叫什麼名字」，這件事本身,只在「產生程式碼」和「開發者閱讀 .proto 定義檔」這個層面上有意義，實際傳輸的二進位資料裡，真正決定「這是哪個欄位」的依據，是這個欄位被指定的那個數字編號，而不是它的名稱。這個設計，直接帶來了向後相容演進的優雅特性——如果要新增一個欄位，只要確保這個新欄位使用一個「之前從來沒有被用過」的全新編號，那麼，一個「還沒有更新、不認識這個新編號代表什麼意思」的舊版本客戶端，在收到（反序列化）一筆包含這個新欄位的訊息時,會發現「這個編號,我不認識」，Protobuf 的標準行為是**直接忽略掉這個無法識別的欄位**（而不是報錯或拒絕解析整筆訊息），舊客戶端能夠正常地處理訊息裡它「認識」的其他欄位，完全不受這個新增欄位的影響，這正是向後相容的具體體現——新增欄位,對還沒更新的舊客戶端而言,是完全無害、可以安全忽略的操作。反過來，如果不小心「重複使用了一個曾經代表某個意義的欄位編號，賦予了完全不同的新意義」（例如原本編號 5 代表「使用者的暱稱（字串）」，這個欄位後來被移除了，但之後又有人不小心把編號 5 重新分配給了一個全新的、意義完全不同的欄位,例如「使用者的年齡（整數）」），這會造成非常危險的混淆——如果系統裡還存在著用「舊版本 .proto 定義」序列化、儲存下來的舊資料（這些舊資料，在編號 5 這個位置，儲存的是「暱稱」這個字串資訊），一旦被「新版本 .proto 定義」的程式碼讀取，會誤以為編號 5 位置儲存的資料是「年齡」，直接把一段字串資料，錯誤地解讀成整數,這會導致嚴重的資料錯誤甚至程式當機。因此，Protobuf 提供了明確的 `reserved` 關鍵字，讓開發者能夠在移除一個欄位時，明確地把這個欄位曾經使用過的編號，標記為「保留、不可再被重新使用」，這樣一來，即使之後有其他開發者想要新增欄位、不小心想要使用這個曾經被用過的編號，編譯工具會直接報錯提醒，從根本上避免了這種因為編號重複使用而導致的資料混淆風險。理解「Protobuf 之所以能夠優雅地支援向後相容的欄位演進,核心在於它用『固定的數字編號』而非『欄位名稱』作為序列化的真正依據,新增欄位對舊客戶端而言是安全可忽略的,但絕對不能重複使用曾經被賦予過不同意義的舊編號,並善用 reserved 關鍵字明確標記已棄用的編號防止誤用」，展現你對 Protobuf 這個具體技術的向後相容機制,有超越「知道它是二進位格式、比JSON快」這種表面認識的、更深入的技術細節理解。

**面試回答方式**：給出核心機制——「Protobuf 用固定的數字欄位編號、而非欄位名稱,作為序列化的真正依據,新增欄位時使用一個全新的編號,舊版本客戶端不認識這個編號會直接忽略它,不會出錯,這是向後相容的核心保證」。給出關鍵禁忌——「絕對不能重複使用一個曾經代表過不同意義的舊編號給新欄位,否則舊資料會被新程式碼誤讀,造成資料混淆的嚴重錯誤」。補充「移除欄位時應該用 reserved 關鍵字明確標記這個編號已棄用,防止未來被誤用」。展現你對 Protobuf 向後相容機制的具體技術細節有深入理解,而不只是知道它是「二進位格式,比JSON快」這種表面認識。
