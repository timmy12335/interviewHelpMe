# 題目

日誌該記什麼、用什麼格式？結構化日誌解決了什麼問題？

## 核心答案

**結構化日誌**（JSON 或鍵值對）取代純文字，**讓日誌可以被機器查詢與聚合**。純文字的 `"User 12345 failed to place order 67890: insufficient balance"` 只能用正規表達式或全文檢索去撈；結構化的 `{"event":"order_failed","user_id":12345,"order_id":67890,"reason":"insufficient_balance"}` **可以直接依欄位過濾與聚合**（「過去一小時因餘額不足失敗的訂單有幾筆、集中在哪些使用者」）。

該記的內容有五類。**追蹤識別碼**（trace ID、span ID，**這是把跨服務的日誌串起來的唯一方式**）。**業務識別碼**（使用者、訂單、租戶——**讓「這個使用者發生了什麼」可以被查詢**）。**事件名稱**（一個穩定的字串，讓同類事件可以被聚合）。**結果與原因**（成功或失敗、失敗的具體原因）。**關鍵的量測值**（耗時、筆數、大小）。

**不該記的是**：機密（密碼、token、完整卡號）、大量的重複資訊（每筆日誌都帶著完整的請求體）、以及**沒有人會看的日誌**。

## 詳細解析

**「日誌級別應該表達『這需不需要人來看』而非『這是不是錯誤』」是最有價值的一條紀律**。一個 API 每天有幾千次 404（使用者查詢不存在的資源）是完全正常的——**如果它們都記成 ERROR，告警規則就必須把閾值調高到失去意義的程度，或者乾脆被關掉**。**而那才是真正的損失**：當 ERROR 級別充滿了正常的業務情況，真正的故障就被淹沒了。**正確的分級是：ERROR 表示「有人需要看並可能需要行動」、WARN 表示「異常但系統自行處理了」、INFO 表示「重要的業務事件」、DEBUG 表示「除錯用的細節」。**

**日誌的成本比多數人以為的高**。它包含：**產生的 CPU**（字串格式化、序列化）、**IO**（寫入磁碟或網路）、**傳輸與儲存**（集中式日誌系統的成本按量計費）、以及**查詢的成本**。**在高吞吐的服務上，過度的日誌可能佔用可觀的資源**——而且**日誌本身可能成為瓶頸**（同步的 appender 讓每次寫入都等磁碟）。**所以「參數化的日誌」很重要**（`log.debug("user {} did {}", id, action)`）——**它在級別被過濾掉時完全不做字串格式化**，而用字串拼接先算好再傳進去，即使不輸出成本也已經付了。

**取樣是高吞吐場景的必要手段**。不是每一筆請求都需要完整的日誌——**可以只記錄失敗的、慢的、以及正常請求中的一小部分取樣**。**關鍵是「取樣的決定要一致」**：同一個 trace 的所有服務要嘛都記錄要嘛都不記錄，**否則會得到破碎的鏈路**。**這需要取樣的決定在鏈路開頭做並沿著追蹤上下文傳遞**——與追蹤的取樣是同一個機制。

**日誌、指標、追蹤的分工要清楚**。**指標**回答「有多少、多快、多少比例」（聚合的、便宜的、適合告警）。**追蹤**回答「這一個請求經過了哪些服務、每一段花了多久」（取樣的、適合分析單一請求）。**日誌**回答「當時具體發生了什麼」（詳細的、適合事後調查）。**用日誌做指標的工作（例如靠計算日誌行數得到 QPS）是昂貴且不可靠的**——**認清三者的分工能避免大量的浪費**。

## 面試回答方式

先給結構化日誌的**核心價值**——讓日誌可以被機器查詢與聚合，並用具體的對比說明（純文字只能用正規表達式撈、結構化可以直接依欄位過濾與聚合）。給該記的五類與不該記的三類。加分點有三個：**「日誌級別應該表達『需不需要人來看』而非『是不是錯誤』」**——每天幾千次 404 全記成 ERROR 會讓告警閾值失去意義或乾脆被關掉，**而那才是真正的損失**；**參數化的日誌在級別被過濾時完全不做字串格式化**，而字串拼接即使不輸出成本也已經付了；以及**日誌、指標、追蹤的分工**——指標回答有多少多快、追蹤回答經過哪些服務、日誌回答當時具體發生了什麼，**用日誌做指標的工作是昂貴且不可靠的**。

## 講稿

結構化日誌讓日誌可以被機器查詢與聚合。純文字的一行訊息只能用正規表達式去撈，而結構化的可以直接依欄位過濾，比如過去一小時因餘額不足失敗的訂單有幾筆、集中在哪些使用者。

該記的內容我會說五類。追蹤識別碼，那是把跨服務的日誌串起來的唯一方式。業務識別碼，讓這個使用者發生了什麼可以被查詢。穩定的事件名稱。結果與原因。還有關鍵的量測值。

有一條紀律我認為最有價值。日誌級別應該表達這需不需要人來看，而不是這是不是錯誤。一個 API 每天有幾千次找不到資源是完全正常的，如果都記成錯誤級別，告警規則就必須把閾值調高到失去意義，或者乾脆被關掉。而那才是真正的損失，因為真正的故障被淹沒了。

日誌的成本也比多數人以為的高，包含產生的 CPU、IO、傳輸與儲存、還有查詢。所以參數化的寫法很重要，它在級別被過濾掉的時候完全不做字串格式化。用拼接先算好再傳進去的話，即使不輸出成本也已經付了。

最後，日誌、指標、追蹤的分工要清楚。用日誌做指標的工作，比如靠計算日誌行數得到每秒請求數，是昂貴而且不可靠的。

## 常見追問

### 日誌裡不小心記了機密怎麼辦？

**核心答案**：**當成資安事件處理**——因為日誌通常會被複製到多個地方（集中式日誌系統、備份、可能還有第三方的分析服務），**「刪掉那一行」是做不到的**。正確的處理是：**輪換那個機密**（假設它已經洩漏）、**評估暴露範圍**（誰有日誌系統的存取權）、以及**修正產生它的程式碼**。

**詳細解析**：**預防比補救重要得多，而預防的方式是「結構化加上明確的欄位白名單」**。如果日誌是結構化的且每個欄位都是明確指定的，**就不會有「不小心把整個請求物件序列化進去」的情況**——而那正是機密洩漏最常見的路徑（`log.info("request: {}", request)` 而 request 裡有密碼欄位）。**另一層防護是在日誌框架加上遮罩**（依欄位名的模式自動遮蔽 `password`、`token`、`secret` 等），**但那只是保險而非主要防護**——因為它依賴命名的慣例，而一個叫 `pwd` 或 `authValue` 的欄位就漏掉了。**最根本的做法是「不要把包含機密的物件傳給日誌」**，而那需要在型別層面下功夫（例如讓機密欄位的型別覆寫 `toString` 回傳遮罩後的值）。

**面試回答方式**：先給處理方式（**當成資安事件**——輪換機密、評估暴露範圍、修正程式碼），並指出「刪掉那一行」做不到因為日誌已被複製到多處。重點放在預防：**結構化加上明確的欄位白名單**，避免「不小心把整個請求物件序列化進去」這個最常見的洩漏路徑。給第二層防護（框架的遮罩）並誠實指出它**只是保險而非主要防護**，因為依賴命名慣例。收在最根本的做法：**讓機密欄位的型別覆寫 `toString` 回傳遮罩值**，在型別層面下功夫。

### 日誌的保留期該怎麼定？

**核心答案**：**依用途分級**。**除錯用的詳細日誌**（DEBUG、以及大量的 INFO）——保留幾天到兩週就夠，因為問題通常在發生後不久被調查。**業務事件與稽核日誌**——保留期由合規要求或業務需求決定，可能是幾個月到幾年。**錯誤日誌**——中等（幾週到幾個月），足以支援「這個問題以前發生過嗎」的查詢。**分級的價值是成本**：詳細日誌的量最大而保留期最短，**兩者相乘之後總成本可控**。

**詳細解析**：**「分層儲存」是更精細的做法**——最近幾天的日誌放在可快速查詢的熱儲存（Elasticsearch），較舊的移到便宜的冷儲存（物件儲存的壓縮檔案），**需要時再載入或用專門的查詢引擎存取**。**這讓「保留很久」與「成本可控」同時成立**。**要注意的是「能查」與「查得快」是兩件事**——冷儲存的查詢可能要幾分鐘，**而那對事故調查是不夠的但對事後分析足夠**。**所以熱儲存的保留期應該覆蓋「典型的事故調查窗口」**（通常是幾天），而那個數字應該從實際的事故處理經驗中得出，**而不是憑感覺設。**

**面試回答方式**：給依用途分級的三類與各自的保留期，並指出**分級的價值是成本**（量最大的保留期最短）。加分點是**分層儲存**——熱儲存放最近幾天、冷儲存放較舊的，讓「保留很久」與「成本可控」同時成立。收在一個精確的區分：**「能查」與「查得快」是兩件事**，冷儲存對事故調查不夠但對事後分析足夠，**所以熱儲存的保留期應該覆蓋典型的事故調查窗口，而那個數字該從實際經驗得出**。

### 什麼樣的日誌是「好日誌」？

**核心答案**：**能讓不熟悉這段程式碼的人在事故中快速理解發生了什麼**。具體的檢驗是：**只看這一行日誌（加上它的結構化欄位），能不能知道「什麼操作、對什麼對象、結果如何、如果失敗是為什麼」**？**「處理失敗」不合格，「訂單 12345 的支付失敗：餘額不足，需要 500 元但只有 200 元」合格。**

**詳細解析**：**另一個檢驗是「這行日誌會讓人採取什麼行動」**。**如果答案是「什麼都不做」，那它可能不該存在**（或者級別太高）。**很多日誌是「寫的時候覺得可能有用」而從來沒有人看過**——它們持續消耗資源卻沒有價值。**定期檢視「哪些日誌從來沒有被查詢過」是一個有效的清理方式**（集中式日誌系統通常能提供這個資料）。**更根本的做法是「在寫日誌時就想清楚誰會在什麼情況下看它」**——**這個問題答不上來的日誌，通常就不該寫**。**這與「每個指標都該回答『什麼情況下我會看它』」是同一個原則**，而它適用於所有的可觀測性投資。

**面試回答方式**：給核心標準——**讓不熟悉這段程式碼的人在事故中快速理解發生了什麼**，並給具體的檢驗（什麼操作、對什麼對象、結果如何、失敗為什麼）與正反例。真正的加分點是第二個檢驗：**這行日誌會讓人採取什麼行動**——答案是「什麼都不做」就可能不該存在。給出清理方式（檢視哪些日誌從未被查詢）與更根本的做法：**在寫時就想清楚誰會在什麼情況下看它**。收在通用原則：**這與「每個指標都該回答什麼情況下我會看它」是同一個原則**。
