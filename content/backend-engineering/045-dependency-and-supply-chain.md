# 題目

第三方依賴帶來哪些風險？該怎麼管理？

## 核心答案

風險有四類。**已知漏洞**——依賴中的 CVE，**而且它可能藏在傳遞依賴裡**（你沒有直接引入但它在依賴樹上）。**惡意套件**——被入侵的維護者帳號、或者名稱相似的仿冒套件（typosquatting）。**維護中斷**——套件不再更新，漏洞永遠不會被修補。**授權風險**——某些授權（GPL、SSPL）對商業使用有限制。

管理的四個基本動作：**鎖定版本**（lockfile 確保每次建置的依賴完全相同）、**持續掃描**（Dependabot、Snyk、或 `npm audit` 這類工具在 CI 中檢查已知漏洞）、**產生 SBOM**（軟體物料清單，讓「我們用了哪些東西」成為可查詢的事實）、以及**定期升級**（小步持續 > 累積幾年後一次大升）。

**最需要理解的是「傳遞依賴才是主要的攻擊面」**——一個直接依賴可能帶進幾十個間接依賴，**而你從未審查過它們**。

## 詳細解析

**「持續小步升級」比「定期大升級」安全得多，卻常被推遲**。原因是它沒有立即可見的價值——**沒有人會因為「我們升級了依賴」而受益，但每個人都會因為「升級卡住了」而受苦**。**而累積的成本是非線性的**：一年不升級可能只是幾個小版本，三年不升級可能意味著跨越了破壞性變更、放棄支援的版本、以及互相不相容的依賴組合。**所以自動化的依賴更新（Dependabot 的自動 PR）加上足夠的測試覆蓋，是投資報酬率很高的實踐**——**它讓升級變成日常的小事而非偶爾的大工程**。

**「Spring Boot 這類的 BOM」大幅簡化了版本管理**。它定義了一組互相相容的依賴版本，**讓你不必自己判斷「Jackson 2.15 能不能配這個版本的 Spring」**。**代價是它限制了個別依賴的版本選擇**——想升級某一個依賴到 BOM 之外的版本時，要自己承擔相容性的驗證。**這是一個「用彈性換取確定性」的交換，而在多數專案上它是划算的。**

**惡意套件的防護需要多層**。**鎖定版本並驗證雜湊**（lockfile 中的 integrity 欄位）防止「同一個版本號但內容被換掉」。**用私有的依賴代理**（Nexus、Artifactory）讓所有依賴經過一個可控的入口並被掃描。**限制建置環境的網路存取**（建置時不該能連到任意的外部主機——**因為惡意的安裝腳本正是在那時執行的**）。**而「審查新增的依賴」應該是 code review 的一部分**——**一個新的依賴不只是一行 `package.json` 的改動，它是一次信任的授予**。

**「這個依賴值不值得」需要被明確評估**。判斷的維度有：**它解決的問題有多大**（一個 left-pad 等級的功能不值得一個依賴）、**維護的活躍度**（最後一次更新、issue 的回應速度、貢獻者數量）、**傳遞依賴的數量**（引入一個帶來五十個間接依賴的套件是一個大決定）、以及**移除的難度**（它滲透進多少程式碼）。**「先問能不能自己寫二十行」是一個健康的反射**——**但也不要走到另一個極端，把成熟的函式庫重寫一遍。**

## 面試回答方式

先給**四類風險**並指出**已知漏洞可能藏在傳遞依賴裡**。給四個基本動作（鎖定版本、持續掃描、SBOM、定期升級）。強調**傳遞依賴才是主要的攻擊面**——一個直接依賴帶進幾十個你從未審查過的間接依賴。加分點有四個：**「持續小步升級」比「定期大升級」安全得多卻常被推遲**，因為它沒有立即可見的價值，**而累積的成本是非線性的**；**BOM 是「用彈性換確定性」的交換**，多數專案划算；**惡意套件的防護要多層**，特別是**限制建置環境的網路存取**（惡意的安裝腳本正是在那時執行）；以及**新增依賴應該是 code review 的一部分**——**它不只是一行改動，是一次信任的授予**。

## 講稿

風險有四類。已知漏洞、惡意套件、維護中斷、還有授權風險。其中最需要理解的是傳遞依賴才是主要的攻擊面。一個直接依賴可能帶進幾十個間接依賴，而你從未審查過它們。

管理我會做四件事。鎖定版本讓每次建置的依賴完全相同、在 CI 中持續掃描已知漏洞、產生軟體物料清單讓我們用了哪些東西成為可查詢的事實、還有定期升級。

惡意套件的防護需要多層。鎖定版本並驗證雜湊、用私有的依賴代理讓所有依賴經過可控的入口、還有限制建置環境的網路存取，因為惡意的安裝腳本正是在那時執行的。

而審查新增的依賴應該是程式碼審查的一部分。一個新的依賴不只是一行設定的改動，它是一次信任的授予。

## 常見追問

### 掃描出一堆漏洞但都是傳遞依賴，怎麼處理？

**核心答案**：**先判斷「這個漏洞在我們的用法下能不能被觸發」**。很多 CVE 只在特定的功能路徑上有效——**而你的直接依賴可能根本沒有用到那個路徑**。**工具的報告是「這個版本有漏洞」，不是「你受影響」**。**所以第一步是評估可達性**（有些工具提供「reachability analysis」），第二步才是處理。

**詳細解析**：**處理的手段有三**：**升級引入它的直接依賴**（最乾淨，但可能還沒有修好的版本）、**強制覆寫傳遞依賴的版本**（Maven 的 `dependencyManagement`、npm 的 `overrides`、Gradle 的 `resolutionStrategy`——**有效但要驗證相容性**）、或者**明確記錄為「已評估、不受影響」並在工具中標記**（避免它持續出現在報告裡淹沒真正的問題）。**最後一項很重要卻常被忽略**——**如果掃描報告裡永遠有一百個未處理的項目，那麼新出現的第一百零一個就不會被注意到**。**「保持報告乾淨」是讓掃描持續有價值的前提**，而那需要每一項都被明確處置（修了、或者記錄了為什麼不修）。

**面試回答方式**：先給關鍵判斷——**「這個版本有漏洞」不等於「你受影響」**，很多 CVE 只在特定功能路徑上有效，**第一步是評估可達性**。給三種處理手段（升級直接依賴、強制覆寫版本、記錄為已評估）。真正的加分點是強調**最後一項常被忽略但很重要**：**如果報告裡永遠有一百個未處理項目，第一百零一個就不會被注意到**，**「保持報告乾淨」是讓掃描持續有價值的前提**。

### 內部的共用函式庫該怎麼管理？

**核心答案**：**它有外部依賴的所有問題，加上「你也是維護者」的責任**。關鍵的三件事：**語意化版本並認真對待**（破壞性變更就升主版本，**而不是「反正是內部的」就隨便改**）、**明確的棄用流程**（標記、通知、給遷移期）、以及**知道誰在用**（沒有這個資料就無法評估變更的影響也無法推動升級）。

**詳細解析**：**「內部的所以可以隨便改」是一個代價很高的誤解**。它假設「能找到所有使用方並協調升級」——**而那個假設在超過幾個服務之後就不成立了**（跨團隊、各自的發布節奏、以及沒有人記得的舊服務）。**結果是一次破壞性變更造成幾個團隊的計畫外工作，而那個成本不會出現在做變更的那個團隊的帳上。** **更根本的問題是「共用函式庫的版本分散」**——十個服務用著五個不同的版本，**於是修一個 bug 要發五次修補版本，或者要求五個團隊各自升級**。**所以「內部函式庫的版本收斂」應該是一個被主動管理的指標**，而不是放任它自然分散。**這也是「不要過早抽出共用函式庫」的一個理由**——重複的程式碼比錯誤的抽象容易修，**而一個被十個服務依賴的函式庫，改動的成本乘以十**。

**面試回答方式**：給三件關鍵的事（認真對待語意化版本、明確的棄用流程、知道誰在用）。重點展開**「內部的所以可以隨便改」是代價很高的誤解**——它假設能協調所有使用方，**而那個假設超過幾個服務就不成立**，且**成本不出現在做變更的那個團隊的帳上**。加分點是**版本分散的問題**（十個服務五個版本、修一個 bug 要發五次）與**「版本收斂應該是被主動管理的指標」**。收在：**這也是「不要過早抽出共用函式庫」的理由**——被十個服務依賴的函式庫，改動成本乘以十。

### 建置的可重現性為什麼重要？

**核心答案**：**因為「同樣的原始碼建置出同樣的產物」是所有除錯與稽核的前提**。如果建置的結果會因為時間而不同（依賴解析到了新版本、基底映像檔更新了），**那麼「這個版本在生產出問題」時，你無法在本地重現它**。**做法是**：lockfile 鎖定所有依賴的確切版本與雜湊、基底映像檔用摘要（digest）而非標籤（`:latest` 或甚至 `:1.2` 都可能指向不同的內容）、以及建置環境本身固定。

**詳細解析**：**「用 `:latest` 標籤」是最常見也最容易修的問題**。它讓「昨天能建置、今天壞了」成為可能——**而那個變化沒有任何記錄，因為你的程式碼與設定都沒變**。**用摘要（`image@sha256:...`）則保證了確定性**，代價是升級基底映像檔要明確地改那個摘要——**而那正是想要的：讓變更是顯式的**。**更進一步的是「可重現建置」（reproducible builds）**——同樣的輸入產生位元組層級完全相同的輸出，**這需要處理時間戳、檔案順序、以及各種嵌入的中繼資料**。**多數專案不需要走到那麼徹底，但「依賴與基底映像檔的版本固定」是最低限度，而它的成本幾乎為零。**

**面試回答方式**：給核心理由——**「同樣的原始碼建置出同樣的產物」是除錯與稽核的前提**，否則生產出問題時無法在本地重現。給三個做法（lockfile、基底映像檔用摘要、建置環境固定）。重點展開**用 `:latest` 是最常見也最容易修的問題**——「昨天能建置、今天壞了」而**那個變化沒有任何記錄**；用摘要則**讓變更是顯式的，而那正是想要的**。收在程度的判斷：**完整的可重現建置多數專案不需要，但「依賴與基底映像檔版本固定」是最低限度而成本幾乎為零**。
