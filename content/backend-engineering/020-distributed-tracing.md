# 題目

微服務（Microservices）架構下，為什麼需要「分散式追蹤」？它的核心概念（Trace、Span）是什麼？怎麼實作跨服務的鏈路串聯？

## 核心答案

在微服務架構下，一次使用者請求，往往會經過多個服務的層層呼叫（如「API 閘道 → 訂單服務 → 庫存服務 → 資料庫」），如果每個服務只各自記錄自己的日誌，開發者要排查「這次請求為什麼變慢、哪個環節出了問題」，需要手動地去每一個涉及的服務裡分別翻查日誌，再自己拼湊出完整的呼叫鏈路，這在服務數量多、呼叫關係複雜時極其困難。**分散式追蹤**解決的正是這個問題——透過在整個呼叫鏈路中，攜帶並傳遞一組共同的識別資訊，讓系統能夠自動地把「一次請求所經過的所有服務、所有步驟」串聯起來，呈現成一個完整、視覺化的呼叫鏈路圖。核心概念：**Trace（追蹤）**——代表「一次完整的請求，從進入系統到處理完成」的整個過程，用一個全域唯一的 **Trace ID** 標識；**Span（跨度）**——代表這個 Trace 裡的「一個具體的操作步驟」（例如「呼叫訂單服務的這一次呼叫」、「訂單服務內部查詢資料庫的這一次查詢」），每個 Span 有自己的 ID，並記錄「父 Span 是誰」，透過這種父子關係，能夠重建出整個呼叫鏈路的樹狀結構，以及每個環節各自花費的時間。

## 詳細解析

**跨服務串聯的實作機制——Context Propagation（上下文傳遳）**：要讓分散式追蹤系統能夠正確地把「橫跨多個獨立服務的呼叫」串聯成一個完整的 Trace，核心機制是——當服務 A 呼叫服務 B 時，服務 A 需要把「目前這個請求所屬的 Trace ID，以及『我這次呼叫，是作為哪一個 Span 發起的（用於服務 B 建立自己的 Span 時，能正確地記錄『我的父 Span 是誰』）』這些資訊，透過 HTTP Header（最常見的標準是 **W3C Trace Context**，定義了 `traceparent` 這個標準 Header 欄位）附加在這次呼叫請求裡一起傳遞給服務 B；服務 B 收到請求後，從這個 Header 裡讀取到 Trace ID 和父 Span 資訊，在處理這次請求時，建立一個新的 Span（記錄「我是誰、我的父親是誰、我什麼時候開始處理、什麼時候處理完成」），並繼續把這組追蹤資訊，透過同樣的方式，傳遞給它自己接下來呼叫的其他下游服務，依此類推。這整個「把追蹤上下文，持續地透過每一層的呼叫傳遞下去」的過程，稱為 **Context Propagation**，是分散式追蹤能夠跨越服務邊界、正確串聯整個鏈路的核心機制。

**Span 記錄的具體內容**：每個 Span 通常會記錄——**開始和結束時間**（藉此能計算出這個操作花費了多久）、**操作名稱**（例如「呼叫庫存服務的扣減庫存 API」）、**狀態**（成功或失敗，如果失敗，通常還會記錄錯誤訊息和堆疊追蹤)、以及一組**標籤（Tags/Attributes）**（可以是任意有助於除錯的額外資訊，例如這次 HTTP 呼叫的狀態碼、呼叫的具體 URL、資料庫查詢的 SQL 語句等）。當所有服務都正確地上報自己的 Span 資訊後（通常上報到一個集中的追蹤系統後端，如 Jaeger、Zipkin，或使用雲端服務商提供的追蹤服務），開發者可以在追蹤系統的視覺化介面裡，輸入一個 Trace ID（或透過其他條件篩選），看到這一次請求完整的「瀑布圖（Waterfall View）」——清楚地看到「這次請求先呼叫了訂單服務（耗時 50ms），訂單服務內部又呼叫了庫存服務（耗時 200ms，佔了整個請求的一大部分時間），庫存服務內部又執行了一次資料庫查詢（耗時 180ms，看起來是這個查詢特別慢，是整個請求延遲的主要瓶頸）」這種清晰的、跨服務的效能剖析視圖，大幅簡化了在複雜微服務架構下排查效能問題和錯誤根因的難度。

**OpenTelemetry 的角色**：早期不同的追蹤系統（如 Zipkin、Jaeger）各自有自己的資料格式和 SDK，導致應用程式的程式碼，如果要支援分散式追蹤，往往需要和特定的追蹤系統廠商綁定。**OpenTelemetry** 是目前業界廣泛採用的、**廠商中立（Vendor-Neutral）** 的可觀測性標準與工具集，它定義了統一的 API 和資料格式，讓應用程式的程式碼，只需要依照 OpenTelemetry 的標準方式，埋設追蹤的邏輯（產生 Span、傳遞上下文），之後可以自由地選擇要把收集到的追蹤資料，匯出（Export）到 Jaeger、Zipkin、或任何支援 OpenTelemetry 標準的商業可觀測性平台，不需要因為更換底層的追蹤系統，就重寫應用程式裡的追蹤埋點程式碼，大幅降低了廠商鎖定的風險。

**分散式追蹤和日誌、指標的關係——可觀測性三大支柱**：分散式追蹤通常被視為「可觀測性（Observability）」的三大支柱之一，與**日誌（Logs）**（記錄離散的事件細節）和**指標（Metrics）**（記錄聚合的數值型資料，如 QPS、錯誤率、延遲百分位數）相輔相成——指標告訴你「系統整體上是否健康、有沒有異常」（例如「錯誤率突然升高了」）、日誌提供「某個具體事件發生時的詳細上下文」、而追蹤則提供「一次特定請求，完整地跨越了哪些服務、每個環節各花了多少時間」這個橫跨整個呼叫鏈路的視角，三者結合，能讓開發者從「發現問題（指標）」到「定位問題發生在哪個環節（追蹤）」再到「深入了解這個環節具體發生了什麼（日誌）」，形成一套完整的問題排查流程。

## 面試回答方式

先講清楚分散式追蹤解決的核心問題——「微服務下一次請求跨越多個服務，單靠各自獨立的日誌很難拼湊出完整的呼叫鏈路和效能瓶頸」。介紹核心概念——Trace(代表一次完整請求的全域唯一標識)和 Span(代表其中一個具體操作步驟，有父子關係可以重建樹狀鏈路)。詳細解釋跨服務串聯的機制——「透過 Context Propagation，把 Trace ID 和父 Span 資訊，附加在服務間呼叫的 HTTP Header(如 W3C Trace Context 標準的 traceparent 欄位)裡層層傳遞」，這是理解分散式追蹤如何跨越服務邊界工作的核心機制。可以補充 OpenTelemetry 作為業界標準的角色，以及分散式追蹤和日誌、指標一起構成「可觀測性三大支柱」這個更完整的圖景，展現你對整個可觀測性領域有全面的認識，而不只是孤立地知道「分散式追蹤」這一個工具。

## 常見追問

### 如果某個服務，在轉發呼叫給下游服務時，「忘記」正確地傳遞追蹤上下文(比如自己寫的一個內部工具函式，沒有把 traceparent 這個 Header 帶上)，會發生什麼問題?

**核心答案**：如果某個服務在呼叫下游時，沒有正確地傳遞（透傳）追蹤上下文，下游服務因為收不到任何 Trace ID 資訊，通常會**認為自己是一個全新的、獨立的請求，自行產生一個全新的 Trace ID**，這會導致——原本應該是「同一次使用者請求」的完整鏈路，在這個環節被**意外地『斷開』成兩個(或更多)彼此獨立、沒有關聯的 Trace**，開發者在追蹤系統裡查看這次請求時，只能看到「斷點之前」的那一部分鏈路(例如只看到到某個服務為止)，完全看不到這個服務之後，實際上呼叫了哪些其他下游服務、那些下游服務各自花了多少時間，這種「追蹤鏈路斷裂」的問題，是分散式追蹤系統在實務落地時最常見、也最容易被忽略的陷阱之一，通常需要仰賴良好的框架整合(讓大多數常見的 HTTP 客戶端函式庫，自動地處理上下文傳遞，而不需要開發者手動記得每一次呼叫都要自己加上這個 Header)和團隊的程式碼審查，來降低這種疏漏發生的機率。

**詳細解析**：這題揭示分散式追蹤機制，一個看似簡單、但實務上極容易因為疏忽而失效的脆弱環節——整個追蹤鏈路能夠被正確地串聯起來，完全建立在「每一個呼叫下游服務的地方，都必須正確地把追蹤上下文傳遞下去」這個假設上，這個假設，只要在整條呼叫鏈路的**任何一個環節**被打破(哪怕只是某一個開發者，自己寫了一個簡便的內部 HTTP 呼叫工具函式，而這個工具函式沒有整合分散式追蹤框架的上下文傳遞邏輯)，就會導致從這個環節開始，之後的所有呼叫，都會被系統誤判為「一個全新開始的、獨立的請求」，因為下游服務，在沒有收到任何『這是延續自哪個 Trace』的資訊時，唯一合理的預設行為，就是「假設自己就是這次請求鏈路的起點，開啟一個全新的 Trace ID」，這種「靜默地開啟新 Trace」的行為，某種程度上比「明確地報錯，告知開發者『追蹤上下文缺失』」還要更難被察覺——因為系統不會因此而出現任何錯誤或警告，一切看起來『正常運作』，只是追蹤系統呈現出來的鏈路視圖，不完整地在某個環節被切斷了，如果開發者沒有特別留意「這次追蹤的鏈路，怎麼看起來比我預期的短、缺少了某些應該有的環節」，很可能完全沒有意識到這個問題的存在，直到某次真正需要仰賴完整鏈路排查一個棘手問題時，才發現「追蹤系統顯示的鏈路，竟然在某個環節莫名其妙地斷掉了，看不到後續發生了什麼」，這時候才回頭去檢查，往往才發現是某個角落裡，一個沒有正確整合追蹤框架的呼叫邏輯造成的。因應這個問題最有效的方式，是**盡量依賴框架層面自動化的整合**——現代的 HTTP 客戶端函式庫、RPC 框架（如各種語言生態裡，已經和 OpenTelemetry 整合的標準函式庫)，通常已經內建了「自動攔截每一次對外呼叫、自動把當前的追蹤上下文附加到請求 Header 裡」的邏輯，開發者只需要正確地使用這些標準函式庫發起呼叫，而不是自己手寫底層的網路請求邏輯(繞過了框架的自動處理)，就能大幅降低「忘記傳遞上下文」這種人為疏忽發生的機率；此外，團隊也可以透過**程式碼審查規範**（例如要求任何新增的、直接呼叫其他服務的程式碼，都必須確認有正確使用經過標準整合的 HTTP 客戶端，而不是自己憑空寫一個簡便但繞過了追蹤框架的呼叫方式）和**持續的鏈路完整性監控**(例如定期抽查追蹤系統裡的 Trace，確認鏈路的長度和涉及的服務數量，是否符合對這個業務流程的預期，如果發現異常地短或缺少了應該有的環節，及早排查是否有上下文傳遞被遺漏的地方)，來降低這類問題的發生機率並及早發現。理解「分散式追蹤的完整性，建立在『每一個環節都正確傳遞上下文』這個容易被疏忽打破的脆弱假設上，實務落地時，需要依賴框架層面的自動化整合和團隊的規範紀律，來降低這類人為疏忽造成鏈路斷裂的風險」，展現你對分散式追蹤系統的實務落地挑戰，有超越「理論上怎麼運作」的、更貼近真實工程實踐的理解。

**面試回答方式**：先給出核心後果——「下游服務收不到任何 Trace ID 資訊，會認為自己是一個全新獨立的請求，自行產生新的 Trace ID，導致原本應該是同一次請求的完整鏈路，在這個環節被意外斷開成互不相關的多個 Trace」。點出這個問題的隱蔽性——「系統不會因此報錯或有任何警告，一切看起來正常運作，只是追蹤鏈路視圖不完整地被切斷，很容易被忽略，直到真正需要仰賴完整鏈路排查問題時才被發現」。給出因應方式——「盡量依賴框架層面自動化的上下文傳遞整合(標準HTTP客戶端/RPC框架通常已內建)，搭配程式碼審查規範和持續的鏈路完整性監控，降低人為疏忽造成鏈路斷裂的風險」。展現你對分散式追蹤實務落地挑戰有貼近真實工程實踐的理解。

### 分散式追蹤如果對「每一次請求」都完整記錄所有 Span 的細節，會不會對系統效能和儲存造成很大的負擔?有沒有常見的緩解方式?

**核心答案**：確實，如果對系統裡「每一次」請求都毫無保留地完整記錄追蹤資訊，在高流量系統下，產生的追蹤資料量會非常龐大，對追蹤系統後端的儲存和查詢效能都會造成顯著壓力，同時追蹤資料的收集和上報本身，也會對應用程式增加一定的效能開銷（雖然通常經過良好優化，單次開銷很小，但在極高的請求量下累積起來依然可觀）。常見的緩解方式是**取樣（Sampling）**——不對每一次請求都完整記錄追蹤資訊，而是依照某種策略，只挑選其中一部分比例的請求（例如 1%，或使用更智慧的取樣策略）進行完整的追蹤記錄，其餘的請求則不記錄詳細的追蹤資料（或只記錄極簡化的摘要）。常見的取樣策略包括——**固定比例取樣**（如固定抽取 1% 的請求）、**基於優先權的取樣**（例如「所有出現錯誤或延遲異常高的請求，都優先完整記錄；正常、快速完成的請求，則依照較低的比例取樣」，確保「有問題的請求」不會因為取樣機制而漏掉，同時大幅降低「正常、沒有問題的大量請求」佔用的儲存和效能開銷）。

**詳細解析**：這題考察對分散式追蹤系統實務部署時，必須面對的「效能與儲存成本」這個現實考量，以及業界普遍採用的取樣機制，是否有全面的理解。分散式追蹤系統，雖然帶來了強大的除錯和效能剖析能力，但這個能力本身，並非沒有代價——每一次請求，如果都要在跨越的每一個服務裡，產生並記錄一個(或多個) Span，並把這些資訊上報到集中的追蹤系統後端，這個「產生、記錄、上報」的過程，本身就需要消耗一定的 CPU（序列化 Span 資料）、網路頻寬（把資料傳輸到追蹤後端）、以及最終在追蹤系統後端的儲存空間（如果系統的請求量是每秒數千甚至數萬次，且每次請求可能涉及十幾個 Span，累積起來的資料量會相當可觀，長期保存這些資料的儲存成本，可能遠超過實際的效益）。取樣機制正是為了在「保留分散式追蹤的核心價值(能夠對特定的、需要排查的請求，提供完整的鏈路視圖)」和「控制整體的效能開銷和儲存成本」之間，找到一個務實的平衡點——最簡單的固定比例取樣（例如「所有進來的請求，隨機抽取其中 1% 完整記錄追蹤」），雖然簡單容易實作，但有一個明顯的問題——如果系統裡真正出問題的請求，佔比本來就很低（例如整體錯誤率只有 0.1%），用固定 1% 的隨機取樣，很可能大部分被完整記錄下來的樣本，反而都是「正常、沒有問題」的請求，而真正有問題、開發者最迫切需要完整追蹤資訊去排查的那些請求，卻可能因為隨機性而沒有被抽樣到，錯過了寶貴的除錯資訊。因此，更智慧的取樣策略，通常會採用「基於優先權/尾端(Tail-Based)取樣」——不是在請求「一開始」就隨機決定「這次要不要記錄」，而是等到請求「已經完成」（已經知道這次請求的最終結果是成功還是失敗、耗時是正常還是異常地長）之後，才決定「這個已經完成的請求，值不值得被完整保留下來」——如果這次請求最終是失敗的、或者耗時明顯異常地長（超過某個閾值），優先、盡量地把它完整保留下來（即使正常情況下的取樣比例很低，這類「有問題」的請求，也應該用接近 100% 的比例保留）；如果請求是正常、快速完成的，則可以套用一個較低的取樣比例（例如維持在 1% 左右，主要用於統計性的效能分析，而非個別問題的排查），這種「尾端取樣」策略，能確保「真正有價值、需要被排查的異常請求」，不會因為隨機取樣的運氣不好而被錯過，同時整體上又能大幅降低「正常、大量、沒有排查價值」的請求所佔用的儲存和效能開銷，是目前業界(如很多商業可觀測性平台)普遍採用的更精細做法。理解「分散式追蹤的完整記錄，在高流量下會帶來顯著的效能和儲存開銷，取樣是業界普遍採用的緩解手段，而更精細的『尾端取樣』策略(基於請求最終結果決定是否保留)，能確保真正有問題的請求優先被完整保留，同時大幅降低正常請求的整體開銷」，展現你對分散式追蹤系統的實務部署考量，有涵蓋「效能成本」這個現實工程約束的全面理解。

**面試回答方式**：先坦承這個問題——「確實，對每一次請求都完整記錄，在高流量系統下會對儲存和效能造成顯著負擔」。給出核心緩解方式——「取樣機制，不對每次請求都完整記錄，只依照策略挑選部分比例完整追蹤」。給出兩種取樣策略並比較——「簡單的固定比例取樣(容易實作但可能錯過真正有問題的請求，因為隨機性可能剛好沒抽到那些少數異常的請求)」vs「更智慧的尾端取樣(等請求完成後，根據最終結果決定是否保留，確保失敗或延遲異常的請求優先接近100%保留，正常請求則維持低比例取樣，兼顧排查價值和整體開銷)」。展現你對分散式追蹤實務部署的效能與成本考量，以及業界更精細的取樣策略有全面理解。

### 如果一個效能問題，追蹤系統顯示「某個服務的 Span 耗時特別長」，但這個服務內部，實際上是在等待一個非同步的訊息佇列（Message Queue）處理完成(而不是單純的同步呼叫)，分散式追蹤要怎麼正確地呈現這種「非同步」的呼叫關係?

**核心答案**：對於非同步的訊息佇列場景，分散式追蹤需要把「發布訊息的服務」和「消費訊息的服務」，透過**同樣的上下文傳遞機制，把追蹤上下文(Trace ID 等資訊)附加在訊息本身的中繼資料(Metadata/Header)裡**，而不是像同步 HTTP 呼叫那樣附加在 HTTP Header 裡——生產者服務發布訊息時，把目前的追蹤上下文寫進訊息的 Header；消費者服務消費到這則訊息時，從訊息的 Header 讀取出追蹤上下文，並在自己的處理邏輯裡，建立一個新的 Span，明確標記「這個 Span 的父 Span，是生產者服務發布這則訊息時的那個 Span」，這樣一來，即使生產者和消費者之間，是透過非同步的訊息佇列間接關聯(而非直接的同步呼叫)，追蹤系統依然能夠正確地把這兩者串聯起來，並且通常會用一種特殊的 Span 關係（如「Follows-From」而非傳統同步呼叫的「Child-Of」）來標示「這是一個非同步、時間上可能有延遲的關聯關係，而不是像同步呼叫那樣『父 Span 必須等待子 Span 完成才能繼續』的關係」。

**詳細解析**：這題延伸到分散式追蹤在「非同步」場景下的特殊處理，考察是否理解「同步呼叫」和「非同步事件驅動（Event-Driven）」這兩種完全不同的呼叫模式，在追蹤語意上需要被區別對待，而不能生硬地套用同一套「父子」關係的思維。傳統同步呼叫的 Span 父子關係，隱含了一個重要的語意——「父 Span 發起了子 Span 代表的操作，並且『等待』這個子操作完成之後，才會繼續自己接下來的邏輯」，也就是「父 Span 的持續時間，天然地涵蓋了子 Span 的持續時間」（子 Span 一定是在父 Span 這個時間範圍之內發生的）。但非同步的訊息佇列場景，這個假設完全不成立——生產者服務，把一則訊息發布到佇列之後，通常會**立刻**認為自己這個操作已經完成(它的 Span 可能只花費了幾毫秒，就是「把訊息放進佇列」這個動作本身的耗時)，而消費者服務，真正去處理這則訊息，可能是幾秒鐘、甚至幾分鐘之後才發生的事情(取決於佇列的堆積程度、消費者的處理速度)——如果生硬地套用「父 Span 的時間範圍，必須涵蓋子 Span」這種同步呼叫的語意，會產生一個邏輯上很奇怪的結果："生產者的 Span"（可能只耗時 5 毫秒），卻要顯示自己的父 Span 底下，「涵蓋」了一個實際上晚了好幾秒鐘才開始執行的、屬於消費者的 Span，這在時間軸的呈現上會顯得非常不自然甚至產生誤導（例如追蹤系統的視覺化介面，可能會嘗試把子 Span 硬塞進父 Span 標示的很短的時間範圍內顯示，或者顯示出明顯超出父 Span 範圍的、令人困惑的時間軸），因此，業界的分散式追蹤標準(如 OpenTracing/OpenTelemetry 的規範)，特別定義了一種和傳統「Child-Of（子代自，隱含同步等待、時間包含關係）」不同的關聯類型——「**Follows-From（跟隨自）**」，用來表達「這兩個 Span 之間確實有邏輯上的因果關聯(消費者的處理，確實是因為生產者發布的這則訊息而觸發的)，但兩者之間不存在『父 Span 必須等待、且時間範圍涵蓋子 Span』這種同步呼叫特有的語意」，這樣一來，追蹤系統在呈現這種非同步關聯的 Span 時，能夠更準確地反映實際的時間軸(消費者的處理，確實可能發生在生產者的 Span 早已結束之後的某個時間點)，同時依然保留了「這兩者之間有因果關聯，可以被串聯追蹤」這個核心的追蹤能力，不會因為它們是非同步關聯，就完全失去被串聯起來的可能性。理解「分散式追蹤在處理非同步、事件驅動的呼叫關係時，需要透過把追蹤上下文附加在訊息本身的中繼資料裡進行傳遞，並使用類似 Follows-From 這種區別於傳統同步呼叫 Child-Of 關係的特殊標示方式，來正確地反映『有因果關聯但時間軸獨立、不存在等待關係』這種非同步呼叫特有的語意」，展現你對分散式追蹤的核心概念，有超越「只適用於同步 HTTP 呼叫」這種簡化理解的、更完整的認識。

**面試回答方式**：給出核心機制——「同樣透過上下文傳遞，只是這次是把追蹤上下文附加在訊息本身的中繼資料(Header)裡，消費者消費訊息時從中讀取並建立自己的 Span，標記父 Span 是生產者發布訊息時的那個 Span」。點出這種關聯需要用不同於同步呼叫的語意來標示——「用 Follows-From 而非傳統的 Child-Of 關係，因為非同步場景下，生產者的 Span 可能很快就結束了，消費者實際處理可能是很久之後才發生，不存在『父 Span 等待並涵蓋子 Span 時間範圍』這種同步呼叫特有的假設」。展現你理解分散式追蹤需要區分同步和非同步這兩種不同呼叫模式的語意差異，而非生硬地套用同一套父子關係思維。
