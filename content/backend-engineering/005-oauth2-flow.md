# 題目

OAuth 2.0 解決的核心問題是什麼？「授權碼流程（Authorization Code Flow）」的具體步驟是什麼？

## 核心答案

OAuth 2.0 解決的核心問題是——**讓使用者能夠授權「第三方應用程式」有限度地存取自己在「另一個服務（資源提供方）」上的資料，而不需要把自己的帳號密碼交給這個第三方應用程式**。例如使用者想讓一個第三方相片列印服務讀取自己 Google 相簿裡的照片，OAuth 讓使用者可以「直接在 Google 的頁面上登入並授權」，列印服務全程拿不到使用者的 Google 帳號密碼，只會拿到一個「範圍有限（比如只能讀取相簿、不能刪除）、可以被撤銷」的存取憑證（Access Token）。**授權碼流程**是最常見、最安全的 OAuth 2.0 流程，具體步驟：**（1）** 使用者點擊第三方應用（Client）上的「用 Google 登入」，被導向 Google 的授權頁面；**（2）** 使用者在 Google 的頁面登入並同意授權範圍；**（3）** Google 把使用者導回第三方應用指定的網址，並帶上一個一次性的「授權碼（Authorization Code）」；**（4）** 第三方應用的**後端**（不是瀏覽器前端）用這個授權碼，加上自己的 Client Secret，向 Google 的伺服器換取真正的 **Access Token**；**（5）** 第三方應用之後用這個 Access Token 代表使用者去呼叫 Google 的 API 存取資料。

## 詳細解析

**為什麼需要「授權碼」這個中間步驟，而不是直接把 Access Token 給前端**：授權碼流程刻意設計成「先給一個一次性、短期有效的授權碼，再由後端拿授權碼＋Client Secret 去換真正的 Access Token」，而不是「授權完成後直接把 Access Token 透過瀏覽器網址列傳回」，核心原因是**安全性**——如果 Access Token 直接出現在瀏覽器的網址列或重新導向的 URL 裡，會有洩漏風險（瀏覽器歷史紀錄、伺服器的存取日誌、Referer 標頭都可能意外記錄下這個敏感的網址，或是網路上的中間人有機會攔截)，而「授權碼」本身即使被攔截，因為換取 Access Token 這一步驟**必須同時提供 Client Secret**（只有第三方應用的後端才知道，前端瀏覽器和使用者都不知道），沒有 Client Secret 的第三方，即使拿到授權碼，也無法換出真正有效的 Access Token，加了這一層防護。

**四個核心角色**：**資源擁有者（Resource Owner）**——通常就是使用者本人，擁有資料的所有權；**客戶端（Client）**——想要存取使用者資料的第三方應用程式（如列印服務）；**授權伺服器（Authorization Server）**——負責處理使用者登入、授權確認、簽發 Access Token 的伺服器（如 Google 的 OAuth 伺服器）；**資源伺服器（Resource Server）**——實際存放使用者資料、接受 Access Token 驗證後回傳資料的伺服器（如 Google 相簿的 API）。理解這四個角色的分工，有助於理解整個流程「誰跟誰互動、交換了什麼」。

**PKCE（Proof Key for Code Exchange）擴充**：對於「無法安全保管 Client Secret」的客戶端類型（例如純前端的單頁應用 SPA、或手機 App，這些應用程式的程式碼或封包本身可能被反編譯，任何寫死在裡面的 Client Secret 都形同公開），OAuth 2.0 發展出 PKCE 這個擴充機制——客戶端在發起授權請求前，先自己生成一個隨機的「驗證碼（Code Verifier）」，並計算出它的雜湊值「Code Challenge」隨著授權請求一起發送；等到後續要用授權碼換 Access Token 時，客戶端要一併附上當初的「Code Verifier」原文，授權伺服器驗證「這個 Verifier 的雜湊值是否等於當初收到的 Code Challenge」，這樣即使授權碼在傳輸過程中被攔截，攻擊者沒有原始的 Code Verifier，依然無法換出 Access Token，某種程度上取代了 Client Secret 在這類「無法保密」的客戶端類型上的保護作用。

**Scope（授權範圍）的設計意義**：OAuth 授權請求中會指定 `scope` 參數（如 `scope=photos.read`），這代表「使用者只授權這個第三方應用做這麼有限的事情」，即使 Access Token 被竊取，攻擊者也只能在這個授權範圍內行動（例如只能讀取相片，不能刪除帳號或修改個人資料），這是 OAuth「最小權限」設計理念的具體體現，也是它相較於「把帳號密碼整個交出去」安全得多的關鍵原因——密碼一旦外洩，攻擊者能做任何事;Access Token 外洩，傷害被限制在授權範圍內，且可以被使用者隨時到授權伺服器的設定頁面主動撤銷。

## 面試回答方式

先給出 OAuth 解決的核心問題——「讓第三方應用有限度存取使用者資料，而不需要使用者把密碼交出去」，用一個具體場景（如第三方應用讀取 Google 相簿）幫助理解。接著按順序講出授權碼流程的五個步驟——導向授權頁、使用者登入授權、帶著授權碼導回、後端用授權碼+Client Secret 換 Access Token、用 Access Token 呼叫 API。一定要點出「為什麼需要授權碼這個中間步驟」——這是這題的核心考點，展現你理解這個設計背後的安全考量，而不只是背誦流程步驟。如果能延伸提到 PKCE 或 Scope 的設計意義，展現對 OAuth 生態更全面的理解。

## 常見追問

### 如果第三方應用是一個「純前端的單頁應用（SPA）」，沒有後端伺服器來安全保管 Client Secret，應該怎麼安全地使用 OAuth？

**核心答案**：這種情況下應該使用 **「授權碼流程 + PKCE（Proof Key for Code Exchange）」**，而不是傳統依賴 Client Secret 的授權碼流程，也不應該使用已經被官方棄用的「隱含流程（Implicit Flow，直接把 Access Token 透過 URL Fragment 回傳給前端）」。PKCE 的運作方式是：客戶端（前端 SPA）在發起授權請求前，本地生成一個隨機字串當作 **Code Verifier**，並計算它的 SHA-256 雜湊值作為 **Code Challenge**，隨著授權請求一起送給授權伺服器；使用者完成登入授權後，取得授權碼；接著客戶端（仍然是前端，沒有後端參與）用這個授權碼，**加上原始的 Code Verifier**（而非 Client Secret，因為前端根本不該有 Client Secret），向授權伺服器換取 Access Token；授權伺服器驗證「這次提供的 Code Verifier，計算雜湊值後是否等於當初收到的 Code Challenge」，驗證通過才發出 Access Token。這個機制讓「即使授權碼在傳輸過程中被攔截」，攻擊者因為不知道原始的 Code Verifier，依然無法換出真正的 Access Token。

**詳細解析**：這題考察對「不同客戶端類型需要不同 OAuth 流程」這個實務問題的理解，因為傳統的授權碼流程有一個隱含假設——「客戶端有能力安全保管一個 Client Secret」，這個假設在傳統的伺服器端 Web 應用（如用 Node.js/Java 寫的後端服務）是成立的（Secret 存在伺服器的環境變數或設定檔裡，使用者和攻擊者都碰不到），但對於**純前端的單頁應用**，情況完全不同——SPA 的所有程式碼（包含任何寫死的常數，如果真的把 Client Secret 寫進前端 JavaScript 程式碼）都會被完整下載到使用者的瀏覽器，任何人都可以打開瀏覽器的開發者工具直接看到這段程式碼，Client Secret 在這種情境下形同虛設（一點都不 Secret），如果依然照搬傳統的授權碼流程要求提供 Client Secret，這個 Secret 實際上是公開的，起不到任何安全防護作用。早期 OAuth 規範針對這類「無法保密的客戶端」設計了另一種簡化流程——「隱含流程（Implicit Flow）」，讓授權伺服器在使用者授權後，直接把 Access Token 附加在重新導向 URL 的 Fragment 部分回傳給前端（跳過了「用授權碼換 Token」這個步驟，因為反正沒有 Secret 可以用來做這個交換的驗證），但這個流程被證實有多個安全隱憂（Token 直接暴露在 URL 裡、瀏覽器歷史記錄、沒有辦法像授權碼流程那樣有一個「必須知道額外秘密才能兌換」的防護層），因此業界（包含 OAuth 官方最新的最佳實務指引）現在普遍建議**棄用隱含流程**，改用「授權碼流程 + PKCE」這個組合。PKCE 的精妙之處在於——它用「客戶端在本地臨時生成、只在這一次授權流程中使用、事後即丟棄的一次性驗證資料（Code Verifier/Challenge）」取代了「長期、固定不變的 Client Secret」，這個「一次性、動態生成」的特性，使得即使前端程式碼完全公開透明（沒有辦法藏住任何常數），這個機制依然能提供有效的安全防護——因為攻擊者即使攔截到授權碼，也無法憑空猜出「這次流程」對應的、隨機生成的 Code Verifier 原文，PKCE 巧妙地把「保密」的對象從「客戶端本身的固定密鑰」轉移到「每次授權流程中臨時產生、與這次流程綁定的一次性驗證資訊」，解決了純前端應用天生無法保管長期密鑰的根本困境。

**面試回答方式**：直接給出答案——「授權碼流程 + PKCE，不要用已被棄用的隱含流程」。解釋核心機制——「客戶端生成一次性的 Code Verifier 和對應的 Code Challenge，授權請求時送出 Challenge，換 Token 時提供原始 Verifier 讓伺服器驗證雜湊值是否吻合，取代了 Client Secret 的角色」。解釋為什麼傳統流程不適用——「前端所有程式碼都會被完整下載到瀏覽器，任何寫死的 Client Secret 形同公開，起不到保密作用」。展現你理解 PKCE 用「一次性、動態生成的驗證資料」取代「長期固定密鑰」這個巧妙的設計思路，解決了純前端應用的根本困境。

### 如果 Access Token 被使用者主動撤銷（例如在 Google 帳號設定裡取消對某個第三方應用的授權），已經在客戶端持有這個 Access Token 的第三方應用，會發生什麼事？

**核心答案**：這個第三方應用**下一次**用這個已經被撤銷的 Access Token 去呼叫資源伺服器（如 Google API）時，資源伺服器會拒絕這次請求（通常回傳 `401 Unauthorized`），因為資源伺服器每次收到 Access Token，都會（直接或間接）驗證這個 Token 目前是否仍然有效——如果 Access Token 是一個「不透明的隨機字串（Opaque Token）」，資源伺服器需要向授權伺服器查詢這個 Token 目前的狀態（是否已撤銷、是否過期），這個查詢動作讓撤銷可以立即生效；但如果 Access Token 本身是像 JWT 這種「自包含、只憑簽章驗證」的格式（見 [[004-jwt-authentication.md]]），資源伺服器可能只做本地的簽章驗證，不會即時查詢是否已被撤銷，這種情況下，「撤銷」要等到這個 Access Token 自然過期（因為 Access Token 通常設計成短期有效，如幾十分鐘）才會真正生效，撤銷動作實際上不是「立即生效」而是「阻止之後換發新的 Token」（因為刷新機制，如 Refresh Token，通常確實會被記錄並可即時撤銷）。

**詳細解析**：這題延伸到 OAuth 撤銷機制的實際生效時機，這其實和前面 JWT 討論過的「難以主動撤銷」問題（見 [[004-jwt-authentication.md]]）本質相通，只是換了一個 OAuth 授權情境來考察。理解這裡的關鍵，在於區分「Access Token 的具體實作格式」對撤銷即時性的影響——如果授權伺服器選擇讓 Access Token 是一個「不透明的隨機字串」（沒有任何自解釋的內容，只是一個可以拿去查詢的識別碼，這種設計常見於較早期或較保守的 OAuth 實作)，資源伺服器驗證這個 Token 時，勢必需要主動去問授權伺服器（或共享的儲存）「這個 Token 現在還有效嗎」，這個查詢動作雖然犧牲了一些效能（每次資源請求都要多一次驗證查詢)，但換來的好處是——授權伺服器可以在使用者撤銷授權的當下，立即在自己的資料庫裡把這個 Token 標記為失效，下一次資源伺服器來查詢時，立刻就能得知「這個 Token 已經被撤銷了」，撤銷因此可以做到接近即時生效。但如果 Access Token 選擇像 JWT 這種自包含格式（近年很多 OAuth 實作，尤其是搭配 OpenID Connect 的場景，傾向使用 JWT 格式的 Access Token，因為可以省去資源伺服器每次都要呼叫授權伺服器驗證的網路開銷，資源伺服器只要有公鑰就能自行完成驗證)，就會遇到和一般 JWT 完全相同的困境——資源伺服器為了追求效能，選擇「只驗證簽章、不查詢是否被撤銷」，這代表撤銷這個動作，對「已經簽發出去、還在有效期內」的 Access Token 而言，實際上是「延遲生效」的（要等到這個 Token 自然過期），真正立即生效的，是「授權伺服器內部維護的『這個使用者對這個第三方應用的授權關係』狀態，以及對應的 Refresh Token 記錄」——一旦撤銷，即使舊的 Access Token 還能在剩餘的短暫有效期內繼續被使用，但這個第三方應用之後想用 Refresh Token 換發新的 Access Token 時，這一步驟一定會因為授權關係已經被撤銷而失敗，所以撤銷的實際效果是「立即阻斷了未來繼續存取的能力，但可能有一個和 Access Token 剩餘有效期相當的短暫窗口，舊 Token 依然堪用」。理解這個「撤銷的即時性，取決於 Access Token 的實作格式，以及資源伺服器的驗證策略是否包含即時查詢」的細節，展現你不只是知道「OAuth 可以撤銷授權」這個表面概念，還理解不同實作方式下，撤銷生效的實際時間差異。

**面試回答方式**：先給出關鍵判斷依據——「取決於 Access Token 的實作格式:如果是不透明字串，資源伺服器每次驗證都要向授權伺服器查詢狀態，撤銷可以接近即時生效;如果是像 JWT 這種自包含格式，資源伺服器可能只做本地簽章驗證不查詢撤銷狀態，撤銷實際上要等到這個 Token 自然過期才完全生效」。補充「即使 Access Token 有短暫的『延遲失效』窗口，Refresh Token 通常會立即被撤銷，阻斷之後換發新 Token 的能力，所以撤銷的實際效果是『立即阻斷未來存取、但可能有一個和 Access Token 剩餘效期相當的短暫窗口舊 Token 仍然堪用』」。展現你理解撤銷即時性和 Token 實作格式之間的具體關聯，而不只是籠統地說「可以撤銷」。

### OAuth 2.0 和 OpenID Connect（OIDC）是什麼關係？為什麼常常看到這兩個名詞一起出現？

**核心答案**：**OAuth 2.0 本質上是一個「授權（Authorization）」協定**——它解決的問題是「讓第三方應用有限度地存取使用者的資源」，設計上並沒有標準化「如何確認使用者的真實身份」這件事（雖然實務上大家常常拿 OAuth 來做登入，但嚴格來說 OAuth 本身沒有規範「身份驗證」）。**OpenID Connect（OIDC）是建立在 OAuth 2.0 之上的一層擴充協定**，專門用來解決「身份驗證（Authentication）」這個問題——它在 OAuth 標準的授權流程基礎上，額外定義了一個標準化的 **ID Token**（同樣是 JWT 格式，但內容標準化為「這個使用者是誰」的身份聲明，如姓名、Email），讓第三方應用不只能拿到「存取資源的 Access Token」，還能拿到一個標準格式、可驗證的「這個使用者確實是誰」的身份證明。所以常聽到的「用 Google/Facebook 登入」這類第三方登入功能，實際上用的是 OIDC（建立在 OAuth 2.0 之上），而不是單純的 OAuth 2.0。

**詳細解析**：這題釐清一個業界極其常見的混淆——很多開發者（甚至一些文件）會不精確地說「用 OAuth 做登入」，但嚴格從協定設計的角度看，**OAuth 2.0 解決的是「Authorization（授權）」問題，OpenID Connect 解決的才是「Authentication（身份驗證）」問題**，這兩者雖然經常一起使用、流程也高度相似（甚至共用同一套授權碼流程的步驟），但在協定設計的原始意圖上是不同的概念。這個混淆的來源，某種程度上是「歷史的巧合」——早期很多開發者發現，既然 OAuth 授權流程完成後，第三方應用能透過 Access Token 呼叫資源伺服器的 API（例如呼叫 Google 的「取得使用者基本資料」API），拿回使用者的姓名、Email 等資訊，這個結果「間接地」也讓第三方應用知道了「這個使用者是誰」，於是很多應用就「借用」OAuth 的授權碼流程來實現登入功能——但這種做法有安全隱憂（OAuth 標準本身沒有規範「這個 Access Token 對應的資源擁有者身份聲明，必須用什麼標準格式表達、如何驗證其真實性和防止竄改」，不同的資源伺服器可能用完全不同、不一致的方式回應「使用者是誰」這個問題，第三方應用需要自己額外處理驗證邏輯，容易出現安全疏漏）。OpenID Connect 正是為了解決這個「借用 OAuth 做登入」時缺乏標準化身份驗證機制的問題而誕生的——它明確地在 OAuth 2.0 的授權流程之上，額外定義了標準化的 `openid` 授權範圍（scope）、標準化的 **ID Token**（一個 JWT，其中的欄位如 `sub`（使用者唯一識別碼）、`iss`（簽發者）、`aud`（預期的接收方）、`exp`（過期時間）都有明確的標準定義和驗證規則）、以及標準化的「使用者資訊端點（UserInfo Endpoint）」，讓「這個使用者是誰、如何驗證這個身份聲明的真實性」這件事，有了業界統一遵循的規範，不再是每個服務商各自發明一套不一致的做法。理解「OAuth 管『授權存取資源』、OIDC 管『驗證身份』，OIDC 是建立在 OAuth 之上的一層擴充」，展現你能精確區分這兩個經常被混為一談、但協定設計意圖截然不同的標準。

**面試回答方式**：精確地區分兩者——「OAuth 2.0 解決『授權』問題(讓第三方有限度存取資源)，OpenID Connect 建立在 OAuth 之上解決『身份驗證』問題(標準化地確認使用者是誰)」。解釋常見混淆的來源——「很多人借用 OAuth 授權流程間接推斷使用者身份(拿 Access Token 呼叫使用者資料 API)，但這種做法沒有標準化的身份驗證機制，OIDC 正是為了補上這個標準化的 ID Token 而誕生」。點出「用 Google/Facebook 登入通常實際上用的是 OIDC 而非單純 OAuth」。展現你能精確拆解這兩個經常被混用的協定各自的職責邊界。
