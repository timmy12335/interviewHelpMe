# 題目

滾動部署期間新舊版本的應用會同時存在，資料庫 schema 該怎麼變更才不會出問題？

## 核心答案

核心約束是「新舊版本的應用必須都能在同一個 schema 上運作」。滾動部署期間，舊版本還在跑而新版本已經上線——如果 schema 只相容其中之一，另一個就會壞掉。這排除了「改了 schema 再部署程式碼」這種一步到位的做法。

**標準的解法是 expand-contract（也叫 parallel change）**，分三次獨立的部署：**第一次「擴充」**——只加不刪（新增欄位、新增表、新增索引），**舊程式碼完全不受影響**。**第二次「遷移」**——部署新程式碼，讓它同時寫新舊兩處（或只寫新的、讀時兩處都看），並把存量資料補齊。**第三次「收縮」**——確認沒有程式碼再用舊的欄位之後，才移除它。

關鍵是每一步都可以獨立回退——而那正是它比「一次改完」安全的原因。

重新命名一個欄位是最典型的例子：不能直接 `RENAME`，要「加新欄位 → 雙寫 → 遷移存量 → 改讀取 → 停止寫舊的 → 刪除舊欄位」，**五到六次部署**。

## 詳細解析

「這麼麻煩值得嗎」是一個合理的質疑，而答案取決於停機的成本。如果系統可以接受幾分鐘的維護窗口，**「停機、改 schema、部署、啟動」簡單得多**——不要為了「零停機」的名號而付出五倍的工程成本。expand-contract 的價值在「不能停機」或「停機的協調成本很高」（例如全球服務、或者需要跨多個團隊協調）的場景。

**「雙寫」階段的正確性需要設計**。同時寫新舊兩處時，**如果其中一個失敗了怎麼辦**？三種處理：**同一個交易裡寫兩處**（最簡單，但要求兩處在同一個資料庫）、**以舊的為準、新的失敗只記錄**（然後靠背景任務補齊）、或者**以新的為準**（如果已經確信新的可靠）。同時需要一個「校驗與補齊」的背景任務——比對兩處的資料並修補差異，因為任何雙寫都會有失敗的情況。

「確認沒有程式碼再用舊欄位」這一步最容易被卡住。理論上可以搜尋程式碼，但動態的查詢、報表工具、以及其他團隊的直接資料庫存取都可能漏掉。務實的做法是「先讓它壞在可觀測的地方」：把舊欄位改名成 `old_xxx_deprecated`（任何還在用它的程式碼會立刻報錯而非靜默地讀到錯的值），觀察一段時間沒有錯誤之後才真的刪除。這個「用明顯的失敗取代靜默的錯誤」的技巧在所有的清理工作中都適用。

**遷移腳本本身需要能重跑**。部署可能失敗、可能回退、也可能因為某些原因被重複執行——**所以 schema 遷移應該是冪等的**（`ADD COLUMN IF NOT EXISTS`）或者由遷移框架追蹤已執行的版本（Flyway、Liquibase）。而資料遷移（把存量資料補齊）更需要能斷點續傳，因為它可能跑很久且中途會被中斷。

## 面試回答方式

先給**核心約束**——滾動部署期間新舊版本同時存在，**schema 必須同時相容兩者**，這排除了「改 schema 再部署」的一步到位做法。給 **expand-contract 的三次部署**與**每一步都可獨立回退**這個關鍵性質。用「重新命名欄位需要五到六次部署」說明它的實際成本。加分點有三個：**主動質疑「這麼麻煩值得嗎」**——如果可以接受維護窗口，停機做簡單得多，不要為了「零停機」的名號付出五倍的工程成本；「確認沒有程式碼再用舊欄位」最容易卡住，務實的做法是先改名讓它壞在可觀測的地方再刪除，這個「用明顯的失敗取代靜默的錯誤」的技巧在所有清理工作中都適用；以及**遷移腳本必須能重跑**，資料遷移更需要斷點續傳。

## 講稿

核心約束是滾動部署期間新舊版本的應用會同時存在，所以 schema 必須同時相容兩者。這排除了改了 schema 再部署程式碼這種一步到位的做法。

標準解法是分三次獨立的部署。第一次只加不刪，舊程式碼完全不受影響。第二次部署新程式碼，讓它同時寫新舊兩處，並把存量資料補齊。第三次確認沒有程式碼再用舊的之後，才移除它。關鍵是每一步都可以獨立回退。

重新命名一個欄位是最典型的例子，要五到六次部署才能完成。

不過我想主動質疑一下這麼麻煩值不值得。如果系統可以接受幾分鐘的維護窗口，停機改完再部署簡單得多。不要為了零停機的名號而付出五倍的工程成本。它的價值在不能停機、或是停機的協調成本很高的場景。

還有一步最容易卡住，就是確認沒有程式碼再用舊欄位。理論上可以搜尋程式碼，但動態查詢、報表工具、其他團隊的直接存取都可能漏掉。我的做法是先讓它壞在可觀測的地方，把舊欄位改名，任何還在用它的程式碼會立刻報錯而不是靜默讀到錯的值，觀察一段時間之後才真的刪除。

## 常見追問

### 遷移失敗了怎麼回退？

**核心答案**：**schema 的變更通常不能簡單回退**——`ALTER TABLE` 不在交易裡（MySQL），而且「加了欄位再刪掉」本身也是一次全表操作。所以正確的策略是「讓每一步都不需要回退」：擴充階段只加不刪（**加了不用不會壞任何東西**），收縮階段在確認無人使用後才做。真正需要回退的是應用程式碼，而那應該是獨立且快速的。

**詳細解析**：這是 expand-contract 最重要的設計意圖，卻常被誤解成只是「分步驟做」。它的本質是「讓 schema 的變更永遠是向前相容的，於是回退只需要回退程式碼」——而回退程式碼是部署系統本來就支援的操作。如果某一步的 schema 變更不是向前相容的，那一步就沒有安全的回退路徑，而那正是要避免的。資料遷移（把存量資料補齊）則需要另一種考量：它可能已經改了資料，回退程式碼不會把資料改回去。所以資料遷移應該盡量是「新增而非修改」（寫到新欄位而不是覆寫舊的），這樣舊程式碼仍然讀到它原本的資料。「向前相容的 schema 加上新增而非修改的資料遷移」是零停機遷移的核心原則。

**面試回答方式**：先給精確的事實——**schema 變更通常不能簡單回退**，所以策略是**讓每一步都不需要回退**（擴充只加不刪、收縮在確認無人使用後才做）。真正的加分點是點出這是 expand-contract 最重要的設計意圖卻常被誤解成只是分步驟——本質是讓 schema 變更永遠向前相容，於是回退只需要回退程式碼。收在資料遷移的原則：**盡量是「新增而非修改」**，這樣舊程式碼仍讀到原本的資料——「向前相容的 schema 加上新增而非修改的資料遷移」是核心原則。

### 遷移該由誰執行、在什麼時機？

**核心答案**：三種常見的模式。**應用啟動時自動執行**（Flyway 或 Liquibase 整合在應用裡）——**簡單但危險**：多個實例同時啟動時要處理併發（框架通常有鎖）、而且一個失敗的遷移會讓應用起不來。**部署流程中的獨立步驟**——在部署應用之前先跑遷移，**這是最常見也最推薦的做法**，因為它讓遷移的失敗與應用的部署分開處理。**手動執行**——適合高風險的大型變更（需要人在旁邊觀察與控制節奏）。

**詳細解析**：「應用啟動時自動執行」的問題在容器環境下被放大。Kubernetes 會同時啟動多個 Pod，**它們會競爭遷移的鎖**——拿不到鎖的要等待，而如果遷移跑很久，那些 Pod 可能觸發啟動探針的逾時而被重啟，形成循環。**用 initContainer 或 Job 執行遷移**（讓它在應用容器啟動之前完成）是容器環境下的正確做法。另一個常被忽略的是「遷移與應用版本的對應」——如果遷移是獨立執行的，必須確保「跑了哪個版本的遷移」與「部署了哪個版本的應用」是協調的，否則可能出現應用需要的欄位還沒建立。在 CI/CD 中把兩者綁在同一個流程裡並明確順序，是避免這類問題的基本做法。

**面試回答方式**：給三種模式與各自的取捨，並明確推薦**部署流程中的獨立步驟**（讓遷移的失敗與應用部署分開處理）。展開「啟動時自動執行」的問題在容器環境下被放大——多個 Pod 競爭鎖、遷移跑久會觸發啟動探針逾時而被重啟形成循環，**正確做法是用 initContainer 或 Job**。加分點是**遷移與應用版本的對應**——必須確保兩者協調，在 CI/CD 中把它們綁在同一個流程並明確順序。

### 大型的資料遷移該怎麼進行？

**核心答案**：**分批、可中斷、可觀測、可重跑**。分批（每次處理一千到一萬筆並提交）避免長交易；可中斷（記錄進度、隨時能停）讓它不影響線上；可觀測（進度、速率、預估剩餘時間、錯誤數）讓人知道它在做什麼；可重跑（冪等）讓失敗後能繼續。而且要能控制速度並在複製延遲上升時自動減速。

**詳細解析**：「與線上流量共存」是大型資料遷移最需要設計的部分。一個全速跑的遷移會佔滿 IO、拉高複製延遲、並讓線上查詢變慢——**而它通常不急**（可以跑幾天）。**所以主動的節流是必要的**：每批之間短暫休息、監控複製延遲並在超過閾值時暫停、以及在流量高峰時自動減速或停止。這個「利用空隙執行」的設計讓遷移從一個高風險的操作變成一個可以在營運時間安全進行的日常任務。 另一個實務要點是「先在影子環境跑一次」——用生產資料的副本完整執行一次遷移，量測它需要多久、確認結果正確、並發現那些只有在真實資料上才會出現的問題（空值、超長的字串、非預期的編碼）。這一步的成本遠低於在生產環境中途失敗的代價。

**面試回答方式**：給四個要求（分批、可中斷、可觀測、可重跑）並加上能控制速度並在複製延遲上升時自動減速。重點展開**「與線上流量共存」最需要設計**——遷移通常不急（可以跑幾天），所以主動節流是必要的，這讓它從高風險操作變成可以在營運時間安全進行的日常任務。加分點是先在影子環境用生產資料副本完整跑一次——量測時間、確認正確、並發現只有真實資料才會出現的問題，成本遠低於在生產環境中途失敗。
