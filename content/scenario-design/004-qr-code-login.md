# 題目

使用者在電腦瀏覽器打開網站，畫面出現一個 QR Code，用已登入的手機 App 掃描並按下確認後，電腦端就自動登入了。請說明這個流程背後的設計：QR Code 裡放了什麼、電腦怎麼知道手機已確認、以及如何防止被攻擊者利用。

## 核心答案

核心是一個有狀態的**一次性登入票據**。電腦端向伺服器申請一個隨機、短效的票據 ID（例如 2 分鐘有效），把它編進 QR Code，並持續以長輪詢或 WebSocket 等待狀態變化。票據狀態依序是「待掃描 → 已掃描 → 已確認 → 已使用」或「已過期／已取消」。手機 App 掃描後帶著**自己的登入憑證**向伺服器回報「已掃描」，使用者在手機上按下確認後，伺服器把票據綁定到該使用者，並為**電腦端另外簽發一組新的 Token**，電腦端在下一次輪詢時取得並完成登入。安全上的關鍵是：票據短效且只能使用一次、確認動作必須在手機上明確顯示登入的裝置與地點、以及 Token 只交給發起票據的那個電腦端連線。

## 詳細解析

**QR Code 裡放什麼**：只放一個不可猜測的票據 ID（或包含它的 URL），不放任何使用者資訊。伺服器在 Redis 以 `qr:<id>` 存放狀態、建立時間、發起端的資訊（IP、User-Agent、一個只有該瀏覽器知道的 secret），並設定 TTL。

**電腦端如何得知狀態**：最簡單的是短輪詢，每秒問一次，但浪費請求。常用長輪詢：請求掛在伺服器上最多 30 秒，狀態一變就立即回應。也可以用 WebSocket 或 Server-Sent Events 推送。由於登入頁的同時在線人數有限，長輪詢通常已足夠。

**手機端的兩步：掃描與確認**：掃描時，App 以自己的 Token 呼叫「掃描」介面，伺服器驗證 App 身分，把票據改為「已掃描」並記下使用者 ID，此時電腦端可顯示「請在手機上確認」。確認時，App 再呼叫「確認」介面，伺服器以條件更新把狀態從「已掃描」改為「已確認」，並為電腦端產生全新的 Session 或 Token。拆成兩步是為了讓使用者看到登入資訊再決定，避免一掃就登入。

**為什麼要為電腦另發 Token**：手機的 Token 綁定行動裝置，不能直接複製給電腦。另發 Token 可以獨立設定有效期、權限與裝置資訊，使用者也能在「已登入裝置」清單中單獨登出電腦端。

**防止被利用**：最主要的攻擊是「QR Code 劫持」：攻擊者在自己電腦上產生 QR Code，誘騙受害者掃描並確認，攻擊者的電腦就登入了受害者的帳號。防禦手段包括：確認頁明確顯示「將在某城市的某瀏覽器登入」、票據短效且一次性、偵測掃描端與發起端的地理位置差異過大時加強驗證，以及教育使用者不要掃描別人傳來的登入碼。此外，Token 只能由持有發起端 secret 的連線領取，即使票據 ID 外洩也無法被其他人領走 Token。

## 面試回答方式

用狀態機把流程講清楚：待掃描、已掃描、已確認、已使用、過期。接著說明三個角色（電腦、手機、伺服器）各自做什麼，並強調「手機帶自己的憑證證明身分」和「伺服器為電腦另發 Token」這兩個關鍵點。最後主動提出 QR Code 劫持這種社交工程攻擊和防禦手段，這是區分一般回答與資深回答的地方。

## 講稿

掃碼登入的核心，是伺服器上一張短效、只能用一次的登入票據。

流程是這樣的。電腦先向伺服器要一個隨機的票據 ID，把它做成 QR Code，然後用長輪詢等待結果。手機 App 掃描之後，帶著自己的登入憑證告訴伺服器：我掃了。這時電腦端顯示請在手機上確認。使用者在手機上按下確認，伺服器把票據綁到這個使用者，並且替電腦另外簽發一組新的 Token。電腦在下一次輪詢時拿到，就登入了。

這裡有兩個重點。第一，手機的 Token 不會直接給電腦，電腦有自己的憑證，可以單獨設定有效期，也能單獨登出。第二，掃描和確認要分兩步，讓使用者先看清楚是哪個裝置、在哪裡要登入。

安全上最要防的是 QR Code 劫持，也就是攻擊者把自己畫面上的碼騙你去掃。所以確認頁要清楚顯示登入地點，票據要短效、一次性，而且 Token 只交給發起票據的那條連線。

## 常見追問

### 為什麼用長輪詢而不是 WebSocket？兩者怎麼選？

**核心答案**：掃碼登入是一次性的、低頻的狀態通知，等待時間通常不超過兩分鐘，長輪詢實作簡單、穿透代理與防火牆的相容性好、不需要維護長連線基礎設施，已經足夠。WebSocket 更適合雙向、持續、高頻的互動，例如聊天或即時協作。

**詳細解析**：長輪詢的代價是每 30 秒左右重新建立一次 HTTP 請求，以及伺服器要能非阻塞地掛住請求（例如 Spring 的 `DeferredResult` 或非同步 Servlet）。在多實例部署下，狀態變化發生在處理手機請求的實例，而電腦的長輪詢可能掛在另一個實例上，所以需要透過 Redis Pub/Sub 或訊息佇列通知所有實例，或讓輪詢端每次醒來時直接查 Redis。WebSocket 也有同樣的跨實例問題，並且需要負載平衡器支援連線升級與黏性。若系統本來就有 WebSocket 推送通道，重用它也合理。

**面試回答方式**：先依通訊特性（一次性、單向、短時間）選長輪詢，再說明多實例下「狀態變化在 A、等待者在 B」的跨實例通知問題，展現你考慮過部署層面。

### 如果 QR Code 圖片被別人拍走，攻擊者能登入嗎？

**核心答案**：拍走的人如果用自己的 App 掃描，登入的是他自己的帳號到你的電腦上，而不是取得你的帳號。真正的風險是反過來：攻擊者把他電腦上的 QR Code 給你掃，你確認後他的電腦就登入了你的帳號。所以防禦重點是確認畫面清楚顯示登入裝置與地點，以及票據只能被發起端領取 Token。

**詳細解析**：票據 ID 本身不帶權限。被誰掃描，就綁定到誰的帳號。旁人拍照後掃描，結果只是把旁人的帳號登入到你的瀏覽器上，這頂多是騷擾，而且你會看到不是自己的帳號。危險的情境是受害者替攻擊者「授權」。除了顯示登入資訊，還可以比對手機與電腦的 IP 或地理位置，差距過大時要求額外驗證，或限制 QR Code 只能在同一區域網路內使用（部分企業內部系統會這麼做）。

**面試回答方式**：先釐清「誰掃描就登入誰的帳號」這個方向性，再指出真正的威脅是誘騙授權，最後給出顯示資訊與位置比對兩種防禦。

### 票據的狀態在多個伺服器實例之間怎麼保持一致？

**核心答案**：票據狀態集中存放在 Redis 等共享儲存，所有狀態轉移都用原子操作（Lua 腳本或比較後設定）完成，例如只有在狀態是「已掃描」且掃描者等於確認者時，才能改為「已確認」。長輪詢的實例透過 Pub/Sub 或定期查詢得知變化。

**詳細解析**：如果把狀態放在單一實例的記憶體裡，手機的請求和電腦的請求被負載平衡分到不同實例時就會失效。集中儲存解決了可見性，但還有競態問題：例如使用者在手機上同時按了確認與取消，或兩台手機掃了同一個碼。用 Lua 腳本把「讀取目前狀態、檢查前置條件、寫入新狀態」包成一步，就能保證狀態機只會依合法路徑前進。票據領取 Token 也要是原子的「已確認 → 已使用」轉移，確保 Token 只被領取一次。

**面試回答方式**：講「集中儲存 + 原子狀態轉移」兩件事，舉出兩台手機掃同一個碼的競態例子，並說明 Token 領取也必須是一次性的轉移。
