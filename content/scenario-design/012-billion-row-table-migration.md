# 題目

一張 MySQL 訂單表已經累積到 10 億筆，查詢與寫入都越來越慢，決定遷移到分庫分表的新叢集。業務要求不能停機、不能遺失資料。請說明你的遷移方案、每個階段如何驗證、以及出問題時如何回退。

## 核心答案

不停機遷移的標準流程是「全量同步 + 增量同步 + 校驗 + 灰度切讀 + 切寫 + **保留回退**」。先建立增量同步通道（訂閱舊庫 binlog 的 CDC，或應用層雙寫），記下起點後再做全量搬遷，這樣全量期間產生的變更不會遺漏；全量完成後增量追平，新舊兩邊持續同步。接著做**資料校驗**（筆數、按區段的總和雜湊、抽樣逐筆比對），通過後**灰度切讀**，先讓少量流量讀新庫並比對結果；穩定後**切寫**，以新庫為主，並建立反向同步把新庫的變更寫回舊庫，讓舊庫保持可回退狀態一段時間。每一步都由開關控制，可以秒級切回。

## 詳細解析

**增量同步方案選擇**：應用層雙寫（同時寫舊庫與新庫）實作直觀，但兩次寫入無法放在同一個交易，任一邊失敗都會不一致，還需要額外的補償與校驗；而且要修改所有寫入路徑，容易遺漏。基於 binlog 的 CDC（例如 Canal、Debezium）不侵入業務程式碼，能捕捉所有變更來源（包括人工修資料的 SQL），是較常見的選擇。關鍵是 binlog 格式要是 ROW，且保留時間要足以覆蓋全量搬遷的時長。

**全量搬遷**：依主鍵範圍分批讀取，例如每批 1 萬筆，以 `id > ? ORDER BY id LIMIT` 的游標方式推進，並記錄進度以便中斷續跑。讀取走唯讀副本、控制速率，避免影響線上。寫入新庫時依分片規則路由。10 億筆若每秒 2 萬筆，大約需要 14 小時，需要預估並安排在低峰期。全量與增量重疊的資料要用冪等寫入（以主鍵 upsert，並以更新時間判斷新舊）處理，避免舊資料覆蓋新資料。

**資料校驗**：分三層。粗粒度比對各分段的筆數；中粒度把主鍵區段內所有列的內容做雜湊後聚合比對，不一致的區段再細分；細粒度抽樣逐筆比對。增量期間資料持續變化，校驗要容忍「正在同步中」的短暫差異，對不一致的列延遲後再比一次。

**灰度切讀與切寫**：讀流量先切 1%，同時讀新舊兩邊比對結果並記錄差異（影子讀），確認後逐步放大到 100%。切寫是風險最高的一步：短暫停止寫入（秒級）或以版本號保證，確認增量已完全追平，再把寫入切到新庫，同時啟動新庫到舊庫的反向同步。

**回退設計**：切寫後保留反向同步至少數天到數週，期間若新庫發現問題，可以把讀寫切回舊庫，資料是完整的。只有在新庫穩定運行、對帳無誤後，才停掉反向同步並下線舊庫。沒有回退路徑的遷移，等於是單向的賭注。

## 面試回答方式

先給出完整的階段流程，讓面試官知道你有全貌。強調「先建增量通道再做全量」這個順序的理由，以及 CDC 相較於雙寫的優點。接著逐段講驗證：校驗的三層粒度、影子讀比對。最後重點放在回退：切寫後的反向同步是很多人會漏掉、但實際上最重要的保險。有數字估算（10 億筆約 14 小時）會更有說服力。

## 講稿

不停機遷移，我會照這個順序走：先建增量同步，再做全量搬遷，然後校驗、灰度切讀、切寫，最後保留回退。

順序很重要。我會先接上 binlog 的 CDC 同步，記下起點，再開始搬全量。這樣搬遷期間的新變更都不會漏掉。比起應用層雙寫，CDC 不用改業務程式碼，連人工修資料的 SQL 也抓得到。全量部分依主鍵分批、控制速率、記錄進度。十億筆以每秒兩萬筆來算，大概要十四個小時。

搬完之後要校驗。先比筆數，再比每個主鍵區段的雜湊，不一致的區段再細分，最後抽樣逐筆比。

接著灰度切讀。先切百分之一，同時讀新舊兩邊比對結果，沒問題再慢慢放大。切寫是風險最高的一步，要確認增量完全追平才切。

最重要的是回退。切寫之後，我會開一條從新庫寫回舊庫的反向同步，保留幾週。新庫出問題，隨時能切回去，資料也是完整的。

## 常見追問

### 為什麼要先建增量同步再做全量，反過來會怎樣？

**核心答案**：全量搬遷要花十幾個小時，期間舊庫持續有新增與修改。若先做全量再開始增量，全量開始到增量開始之間的變更就遺漏了。先記下 binlog 位置再搬全量，增量從那個位置開始重放，就能覆蓋全量期間的所有變更。

**詳細解析**：增量重放時會遇到「全量已經搬了較新的版本，增量又帶來較舊的事件」的情況，例如某列在全量讀取前已被更新兩次。所以增量寫入要冪等並能判斷新舊：以主鍵 upsert，並比較更新時間或版本號，只有較新的才覆蓋。刪除事件也要正確處理，否則被刪除的資料會在新庫中殘留。這也是為什麼 binlog 必須是 ROW 格式，因為需要完整的前後映像。

**面試回答方式**：用時間軸說明遺漏的區間，再補充重疊期間的冪等與新舊判斷，以及刪除事件的處理。

### 切寫的那一刻，如何保證不遺失、也不重複寫入？

**核心答案**：常見做法是一個極短的寫入凍結窗口：透過開關讓應用暫停寫入（或請求排隊、短暫回傳重試），等增量同步的延遲歸零、確認新舊資料一致後，切換寫入目標到新庫並啟動反向同步，再解除凍結。整個窗口控制在秒級。

**詳細解析**：如果不凍結，就會有一段時間兩邊都可能接受寫入，造成雙寫衝突。也可以用更精細的作法：按使用者或分片逐批切換，每批只凍結該批的寫入，降低單次影響範圍。不重複寫入的保證來自冪等：寫入以業務主鍵 upsert，同一筆資料被同步兩次不會產生兩列。切換開關本身要集中管理（例如配置中心），所有應用實例同時生效，並在切換前演練過。

**面試回答方式**：講出「短暫凍結、追平、切換、解凍」四步，說明不凍結會造成雙寫衝突，再提按分片逐批切換與冪等寫入兩個細節。

### 遷移到分庫分表後，原本依「使用者 ID」查詢訂單、也依「訂單號」查詢，分片鍵怎麼選？

**核心答案**：選查詢量最大且最需要高效的維度作為分片鍵，通常是使用者 ID（使用者查自己的訂單）。另一個維度則用**基因法**：讓訂單號內嵌使用者 ID 的分片資訊（例如末幾位），這樣依訂單號也能直接算出分片；或建立訂單號到使用者 ID 的映射表。商家維度的查詢則透過 CDC 同步到另一份以商家 ID 分片的副本或搜尋引擎。

**詳細解析**：分片鍵決定了哪些查詢能精準路由到單一分片，其他查詢會變成廣播到所有分片，延遲與資源消耗都很高。基因法的作法是：產生訂單號時，取使用者 ID 對分片數取模的結果嵌入訂單號末幾位，於是兩種 ID 計算出的分片相同。前提是分片數要預先規劃，未來擴容時取模基數要相容（例如以 2 的冪次擴容）。對於後台的多條件查詢與報表，不應強求從分片庫查詢，而是同步到 Elasticsearch 或資料倉儲處理。

**面試回答方式**：先說明分片鍵選擇的依據，再給出基因法並解釋原理，最後把多維度與報表查詢交給異構副本，展現你知道分庫分表不是萬能。
