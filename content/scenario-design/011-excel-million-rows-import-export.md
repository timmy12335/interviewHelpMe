# 題目

營運人員需要一次匯出 100 萬筆訂單成 Excel，也需要把一份 50 萬列的商品資料 Excel 匯入系統。目前的寫法一跑就記憶體溢位（OOM），或是 HTTP 請求逾時。你會怎麼改造？

## 核心答案

兩個問題的根源相同：**把所有資料一次載入記憶體**，以及**在同步請求中做長時間工作**。匯出要做到**串流**：資料庫用游標或依主鍵分頁分批讀取，寫 Excel 用 POI 的 `SXSSFWorkbook` 或 EasyExcel 這類只在記憶體保留少量列、其餘寫入暫存檔的寫法；單一工作表上限約 104 萬列，超過要分頁籤或分檔。匯入要用**事件驅動的逐列解析**（SAX 模式），每讀 1000 列就校驗並批次寫入資料庫，而不是先把整份檔案讀成 List。兩者都改成**非同步任務**：請求只建立任務並立即回傳任務 ID，背景執行完成後把檔案放到物件儲存，透過通知或任務列表提供下載與錯誤報告。

## 詳細解析

**為什麼會 OOM**：POI 的 `XSSFWorkbook` 會把整份 xlsx 解析成 DOM 物件樹，一個儲存格可能佔用上百位元組，100 萬列 × 20 欄就是 2000 萬個物件，輕易超過數 GB。再加上先 `SELECT *` 把 100 萬筆查回來放進 List，記憶體雙重爆炸。

**匯出的串流寫法**：讀取端不要用 `LIMIT offset, size`，因為深分頁越翻越慢；改用 `WHERE id > ? ORDER BY id LIMIT 5000` 的游標分頁，或 JDBC 的串流結果集（MySQL 需設定 `fetchSize = Integer.MIN_VALUE` 或使用游標模式）。寫入端用 `SXSSFWorkbook(100)`，只保留最近 100 列在記憶體，舊列寫入暫存檔。EasyExcel 在此基礎上做了更多記憶體優化並提供較簡潔的 API。如果使用者能接受，直接匯出 CSV 是最省資源的選擇。

**匯入的逐列解析與批次寫入**：EasyExcel 的 `ReadListener` 每解析一列就回呼一次，在回呼中累積到 1000 列時做校驗並 `batchInsert`，然後清空暫存。資料庫端開啟 JDBC 批次（MySQL 的 `rewriteBatchedStatements=true`），能把逐筆插入的速度提升一到兩個數量級。

**錯誤處理與可重入**：50 萬列中可能有幾百列格式錯誤。不要因為一列錯誤就整批失敗，應收集錯誤列（列號、欄位、原因）產生一份錯誤報告讓使用者下載修正後重新上傳。是否要「全部成功才生效」取決於業務：若需要原子性，先匯入暫存表、全部校驗通過後再一次搬到正式表；否則逐批提交並記錄進度，任務中斷時能從上次的位置繼續。

**非同步化與資源保護**：大檔處理動輒數分鐘，不能佔住 HTTP 請求與閘道逾時。用任務表記錄狀態（排隊、處理中、成功、部分失敗），由專門的工作者執行，並限制同時執行的任務數，避免十個人同時匯出把資料庫壓垮。匯出查詢最好走唯讀副本，不和線上交易搶資源。

## 面試回答方式

先診斷根因：全量載入記憶體與同步執行。然後分匯出與匯入兩部分，各講讀取端與寫入端的串流作法，記得點出深分頁的陷阱與 JDBC 批次參數這類實作細節。最後談非同步任務、錯誤報告、限制併發與唯讀副本，讓回答從「不 OOM」升級到「可營運的功能」。

## 講稿

這兩個問題的根源是一樣的。一是把所有資料一次載進記憶體，二是在同步請求裡做很久的事。

先看匯出。讀資料庫的時候，不要一次查一百萬筆放進 List，也不要用 offset 深分頁，越後面越慢。我會用主鍵當游標，每次往後拿五千筆。寫 Excel 的時候，用 SXSSF 或 EasyExcel 這種串流寫法，記憶體只留一百列左右，其他寫進暫存檔。另外要記得，單一工作表最多一百萬列出頭，超過要分頁籤。

再看匯入。不要先把整份檔案讀成物件。我會用事件驅動的方式逐列解析，每累積一千列就校驗一次，然後批次寫入。MySQL 要記得開 rewriteBatchedStatements，速度差很多。格式錯的列不要讓整批失敗，收集起來產生一份錯誤報告給使用者。

最後，兩者都改成非同步任務。請求只回傳任務 ID，背景做完把檔案放到物件儲存再通知。同時限制併發數，匯出查詢走唯讀副本，不跟線上交易搶資源。

## 常見追問

### 匯出 100 萬筆時，用 LIMIT offset 分頁有什麼問題？

**核心答案**：`LIMIT 900000, 5000` 會讓資料庫先掃描並丟棄前 90 萬筆，再回傳 5000 筆，越往後每一頁越慢，整體複雜度接近 O(n²)。改用以主鍵為游標的「延續查詢」`WHERE id > 上一批最大 id ORDER BY id LIMIT 5000`，每一頁都能直接從索引定位，速度穩定。

**詳細解析**：深分頁的問題在於 offset 沒辦法跳過，資料庫必須數過那些列（若還需要回表，成本更高）。游標分頁利用了 B+ 樹索引的有序性，`id > ?` 直接定位到起點。它的限制是只能依游標欄位順序前進，不能跳頁，但匯出本來就是循序讀取，完全適用。若排序條件不是唯一欄位（例如依建立時間），要用 `(created_at, id)` 的組合游標，避免同一時間的多筆資料被跳過或重複。

**面試回答方式**：說出「offset 必須掃描丟棄」的原理，給出游標分頁的 SQL，再補一句非唯一排序欄位要用組合游標。

### 匯入時如何避免同一份檔案被重複上傳造成資料重複？

**核心答案**：分兩層處理。檔案層，計算上傳檔案的雜湊值，同一份檔案在處理中或已成功時直接提示；資料層，依業務唯一鍵（例如商品編號）做 upsert 或唯一索引，讓重複的列更新而不是新增。後者才是根本保證，因為使用者可能修改一個字後重新上傳。

**詳細解析**：檔案雜湊只能擋住完全相同的檔案，屬於體驗優化。真正的冪等性來自資料本身：每一列都應該有一個業務上的唯一識別，資料庫以唯一索引保證，寫入時用 `INSERT ... ON DUPLICATE KEY UPDATE` 或先查後寫的合併邏輯。若業務資料沒有天然唯一鍵（例如流水帳），則要讓使用者在檔案中提供外部單號，或在任務層記錄「這個批次已匯入哪些列」，重試時跳過。

**面試回答方式**：區分檔案層與資料層兩種去重，並強調資料層的唯一鍵才是根本，最後提沒有天然唯一鍵時的作法。

### 為什麼建議匯出走唯讀副本？會有什麼問題？

**核心答案**：大量匯出會長時間佔用資料庫的 IO 與緩衝池，把熱資料擠出記憶體，影響線上交易的延遲；放到唯讀副本可以隔離這種影響。代價是主從延遲：副本上的資料可能落後主庫幾秒，所以匯出結果要註明資料時間點，對需要即時一致的對帳類匯出則要另外評估。

**詳細解析**：InnoDB 的緩衝池是以 LRU 的變形管理，雖然有防止全表掃描污染的機制（新讀入的頁先放在 old 區），但持續大量掃描仍會造成 IO 壓力與快取命中率下降。唯讀副本最好再區分用途，例如專門給報表與匯出的副本，避免和提供線上讀取的副本互相干擾。若匯出的資料量大到副本也吃不消，就應該考慮從資料倉儲或 CDC 同步出去的分析資料庫匯出，而不是從交易資料庫。

**面試回答方式**：說明緩衝池被擠壓的影響與隔離的好處，坦白提出主從延遲的代價，最後延伸到報表專用副本與資料倉儲。
