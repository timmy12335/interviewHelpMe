# 題目

系統裡有身分證字號、手機號碼、信用卡號、地址等敏感資料。主管要求「所有地方都要脫敏」。請說明你會在哪些環節做脫敏、各用什麼方式實作，以及要注意哪些容易漏掉的地方。

## 核心答案

脫敏不是單一功能，而是按資料流向在多個出口各自處理：**API 回應**依使用者角色做動態遮罩（例如手機顯示 `0912***678`），常用 Jackson 自訂序列化器加上欄位註解，讓規則集中宣告；**日誌**在輸出前統一遮罩，透過 Logback 的自訂轉換器或在 `toString()` 中排除敏感欄位；**非正式環境的資料**（測試、分析、外包）做靜態脫敏，在資料匯出時以假資料替換或做不可逆轉換，而不是只遮住顯示。容易漏掉的地方包括：例外訊息與堆疊追蹤、第三方 SDK 的請求日誌、匯出報表、前端埋點、訊息佇列中的訊息內容、以及快取中的資料。

## 詳細解析

**動態脫敏（API 回應）**：定義一個 `@Sensitive(type = PHONE)` 註解標在 DTO 欄位上，實作 Jackson 的 `JsonSerializer`，序列化時依類型套用遮罩規則。若要依角色決定是否遮罩（例如客服主管可看完整號碼），序列化器從安全上下文讀取目前使用者的權限。好處是規則集中在 DTO 宣告，不會散落在各個 Controller；要注意的是，回傳完整資料的「查看明文」操作應是獨立的、需要額外授權並記錄稽核的介面。

**遮罩規則的設計**：手機保留前四後三、身分證保留首字母與末兩碼、信用卡只顯示末四碼（這也是 PCI DSS 的要求）、姓名保留姓氏、地址只顯示到行政區。規則要統一，因為若不同頁面遮的位置不同，組合起來就能拼出完整資料。

**日誌脫敏**：最可靠的是源頭不印：DTO 的 `toString()` 排除敏感欄位（Lombok 的 `@ToString.Exclude`），不要直接 log 整個請求物件。第二道是 Logback 的自訂 `MessageConverter` 或 Log4j2 的 `RewritePolicy`，以正規表達式在輸出前替換符合身分證、手機格式的字串。正規表達式是補漏用的，有效能成本也可能誤判，不能當作唯一手段。

**靜態脫敏（非正式環境）**：測試環境需要「看起來真實」的資料，但絕不能是真實個資。常見做法是在匯出管線中替換：姓名換成隨機假名、手機換成同格式的假號碼、需要維持關聯的欄位（例如同一個使用者在多張表出現）用帶金鑰的確定性雜湊轉換，保持關聯但不可還原。只做遮罩（`0912***678`）不夠，因為遮罩後的資料仍可能透過其他欄位組合識別出個人。

**常被遺漏的出口**：例外訊息中帶入了參數（例如 `"user not found: " + idNumber`）；呼叫第三方金流、簡訊的 HTTP 客戶端開了完整請求日誌；客服匯出的 Excel；前端埋點把表單內容送到分析平台；Kafka 訊息中的完整個資被下游無權限的服務消費；Redis 中快取的完整使用者物件。脫敏要做資料流盤點，逐一確認每個出口。

## 面試回答方式

先釐清「脫敏」在不同環節有不同意思：顯示時遮罩、日誌中遮罩、非正式環境替換。然後各給一個具體實作（Jackson 註解序列化器、Logback 轉換器與 toString 排除、匯出管線的假資料替換）。最後列舉容易漏掉的出口，這一段最能展現實務經驗，也可以提一句「要先做資料流盤點」作為方法論。

## 講稿

我會先把脫敏拆開看，因為不同環節要做的事不一樣。

第一是 API 回應。我會定義一個敏感欄位的註解，標在 DTO 上，再寫一個 Jackson 序列化器，輸出時依類型遮罩。手機留前四後三，信用卡只留末四碼。要看完整資料，就走另一個需要額外授權、而且會留稽核的介面。

第二是日誌。最可靠的是一開始就不印出來。DTO 的 toString 排除敏感欄位，也不要直接把整個請求物件丟進日誌。再加一層 Logback 的轉換器，用正規表達式補漏，但它只是補漏，不能當成主要手段。

第三是測試或分析環境。這裡要的不是遮罩，而是替換成假資料。需要維持關聯的欄位，用帶金鑰的雜湊轉換，還原不回來。

最後，很多外洩都發生在沒想到的地方。像是例外訊息帶了身分證號、第三方 SDK 開了完整日誌、匯出的報表、前端埋點。所以我會先做一次資料流盤點，把每個出口都檢查一遍。

## 常見追問

### 用正規表達式在日誌輸出前統一脫敏，有什麼問題？

**核心答案**：有三個問題：效能（每一行日誌都要跑多個正規表達式）、誤判與漏判（格式不標準的資料抓不到，長得像身分證的訂單號卻被遮掉）、以及給人錯誤的安全感（開發者以為有兜底就隨意印物件）。它適合當作最後一道補漏，而不是主要防線。

**詳細解析**：高流量服務每秒可能輸出上萬行日誌，每行跑五六個正規表達式，CPU 成本明顯，尤其是寫得不好的正規表達式還可能出現回溯爆炸。誤判會讓排查問題時關鍵資訊被遮掉；漏判則是真正的風險，例如手機號中間有空格或破折號、或被放在 JSON 的跳脫字元裡。所以主要防線應是「源頭不印」，透過 DTO 設計、程式碼審查規則與靜態掃描工具（例如掃描 log 呼叫中是否直接傳入含敏感欄位的物件）來保證。

**面試回答方式**：條列三個問題並各給一個具體例子，最後給出「源頭不印為主，正規表達式補漏為輔」的定位。

### 脫敏和加密有什麼不同？什麼時候用哪個？

**核心答案**：加密是可逆的，持有金鑰就能還原，目的是保護儲存與傳輸中的資料，合法使用者仍需要完整資料；脫敏通常不可逆，目的是讓不需要完整資料的人或系統只看到必要的部分。兩者常同時使用：資料庫存密文，顯示時解密後再遮罩。

**詳細解析**：判斷依據是「接收方需不需要完整資料」。金流服務需要完整卡號，所以傳輸時加密；客服只需要確認末四碼，所以顯示遮罩；測試環境完全不需要真實資料，所以替換。還有一類是「假名化」（pseudonymization），用確定性的轉換替代識別資料，讓分析時仍能關聯同一使用者，但無法直接識別本人。法規（如 GDPR）對假名化資料與匿名化資料的要求不同：假名化資料仍屬個資，匿名化資料才可能不受規範。

**面試回答方式**：用「可逆與否」和「接收方需不需要完整資料」兩個維度區分，再舉卡號在不同環節的處理作為例子。

### 遮罩規則不一致為什麼會造成資料外洩？

**核心答案**：如果 A 頁面遮住手機的中間四碼、B 頁面遮住後四碼，有權限看兩個頁面的人把兩者拼起來就能得到完整號碼。所以遮罩規則必須全系統統一，由共用的元件產生，而不是由各頁面自行實作。

**詳細解析**：這種「組合洩漏」在大型系統中很常見，因為不同團隊各自實作遮罩，各自都覺得自己有遮。同理，匯出報表遮了姓名但保留了生日、郵遞區號與性別，這三者組合起來在很多地區就足以唯一識別一個人。所以脫敏不能只看單一欄位，要評估欄位組合的識別能力。統一的作法是把遮罩規則放在共用函式庫中，並在程式碼審查中檢查是否有自行實作的遮罩邏輯。

**面試回答方式**：用拼接手機號這個直觀例子說明，再延伸到準識別欄位組合的問題，最後給出「共用元件統一規則」的解法。
