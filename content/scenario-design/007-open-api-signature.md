# 題目

公司要把訂單查詢與建單能力開放給外部合作夥伴呼叫。你會如何設計這組對外 API 的安全機制？如何確認呼叫者身分、確保請求沒被竄改、防止請求被攔截後重複送出？

## 核心答案

典型做法是 **AppKey + AppSecret + HMAC 簽章**：平台為每個合作夥伴發放公開的 AppKey 與保密的 AppSecret；呼叫時，把請求方法、路徑、排序後的參數、請求主體的雜湊、**時間戳**與**隨機數（nonce）**組成待簽字串，用 AppSecret 做 HMAC-SHA256 得到簽章，放在標頭中。伺服器以相同規則重算簽章比對，即可同時確認**身分**（只有持有 Secret 的人算得出來）與**完整性**（任何參數被改，簽章就對不上）。**防重放**靠時間戳加 nonce：時間戳超過 ±5 分鐘的請求直接拒絕，5 分鐘內的 nonce 存進 Redis，重複出現就拒絕。外層一律走 HTTPS，並搭配 IP 白名單、權限範圍、按 AppKey 的限流與完整稽核日誌。

## 詳細解析

**為什麼不只用 HTTPS**：HTTPS 保護的是傳輸途中，但無法證明「是哪個合作夥伴」，也無法防止合作夥伴的系統或日誌外洩後請求被重送。簽章把身分與請求內容綁在一起，是應用層的保證。

**簽章字串的設計細節**：參數要按 key 排序並以固定格式串接，否則雙方序列化順序不同會導致簽章不一致；請求主體不直接放進字串，而是放它的 SHA-256 雜湊，避免大型 body 的處理成本；空值與編碼（URL encode 的大小寫）都要在文件中明確定義，這是串接時最常出錯的地方。比對簽章時要用常數時間比較，避免時序攻擊。

**防重放的兩個條件**：只有時間戳時，攻擊者在 5 分鐘內重送仍然有效；只有 nonce 時，要永久保存所有 nonce，儲存無限成長。兩者結合後，nonce 只需要保存時間窗口的長度（用 `SET nonce:<appKey>:<nonce> 1 NX EX 300`），超過窗口的請求已被時間戳擋掉。這也要求雙方時鐘大致同步。

**權限與配額**：每個 AppKey 綁定可呼叫的介面範圍（scope）與資料範圍（只能查自己的訂單），在閘道統一檢查。按 AppKey 限流，避免單一合作夥伴的程式錯誤拖垮平台。建單這類寫入介面，還要要求合作夥伴提供業務冪等鍵（例如外部訂單號），防止他們自己的重試造成重複建單。

**Secret 的生命週期**：Secret 只在建立時顯示一次，平台端加密儲存；支援同時存在兩把 Secret 以便無縫輪換；外洩時可立即停用。更高安全需求的場景會改用非對稱簽章（合作夥伴用私鑰簽、平台用公鑰驗），平台甚至不必保管對方的密鑰，或直接採用 mTLS 或 OAuth 2.0 的 client credentials 流程。

## 面試回答方式

把問題對應到三個安全目標：身分、完整性、防重放，然後一一說明 HMAC 簽章與時間戳加 nonce 各自解決哪一個。細節上要講出參數排序、body 用雜湊、常數時間比較、nonce 只需保存時間窗口，這些是實作過才知道的坑。最後補上權限範圍、按 AppKey 限流、冪等鍵與 Secret 輪換，讓回答從「簽章演算法」擴展到「開放平台設計」。

## 講稿

對外 API 的安全，我會對應到三個目標：確認是誰在呼叫、確保內容沒被改、防止請求被重送。

最常見的做法是 AppKey 加 AppSecret 再加 HMAC 簽章。平台發給每個合作夥伴一組 Key 和 Secret。呼叫時，把方法、路徑、排序過的參數、主體的雜湊，加上時間戳和隨機數，組成一個字串，用 Secret 算出簽章放在標頭。伺服器用同樣規則重算一次。對得上，就同時證明了身分和內容完整。

防重放要靠時間戳和隨機數一起用。時間差超過五分鐘直接拒絕。五分鐘內的隨機數存進 Redis，重複出現就擋掉。這樣隨機數只需要保存五分鐘，不會無限成長。

實作上有幾個坑。參數一定要排序，主體放雜湊就好，比對簽章用常數時間比較。最後別忘了外圍的配套：每個 Key 綁定權限範圍，按 Key 限流，建單介面要求冪等鍵，Secret 也要能輪換。

## 常見追問

### HMAC 簽章和 JWT 有什麼不同？為什麼開放平台多用簽章？

**核心答案**：JWT 是伺服器簽發給客戶端的身分令牌，證明「持有者是誰」，但它不綁定每一次請求的內容，令牌被截取後可以拿來發任意請求。HMAC 請求簽章則是對每一次請求的具體內容簽名，內容一變就失效，再搭配時間戳與 nonce，即使被截取也無法改寫或重送。

**詳細解析**：開放平台的呼叫方是伺服器對伺服器，雙方可以安全保存共享密鑰，所以逐請求簽章的成本可以接受，換來更強的完整性保證。JWT 適合使用者登入後的會話，客戶端是瀏覽器或 App，無法安全保存長期密鑰。兩者也可以組合：先用 OAuth 2.0 client credentials 換取短效 access token，再在高敏感介面上額外要求請求簽章。

**面試回答方式**：用「令牌證明身分」與「簽章證明這一次請求」的差別來回答，並從呼叫方類型（伺服器 vs 瀏覽器）解釋適用場景。

### 合作夥伴說他們的簽章一直驗證失敗，你會怎麼排查？

**核心答案**：讓平台在驗證失敗時，於日誌（不回傳給呼叫方）記錄伺服器端算出的待簽字串，請對方提供他們的待簽字串逐字比對。最常見的原因是參數排序、URL 編碼大小寫、空值處理、body 被框架重新序列化、以及時間戳單位（秒 vs 毫秒）不一致。

**詳細解析**：簽章本身是雜湊，看不出差在哪裡，只有比對原始待簽字串才能定位問題。對外回應只說「簽章無效」，不能回傳伺服器的待簽字串，否則會幫攻擊者除錯。最好的預防是提供官方 SDK 與一個沙箱環境的「簽章除錯工具」，讓合作夥伴輸入參數就能看到標準的待簽字串。文件中附上一組完整的範例輸入與預期簽章，也能大幅降低串接成本。

**面試回答方式**：講出「比對待簽字串」這個方法，列舉幾個常見原因，並強調不能把除錯資訊回傳給呼叫方，最後用 SDK 與除錯工具作為預防。

### 如果合作夥伴的 AppSecret 外洩了，怎麼處理才不會中斷他們的服務？

**核心答案**：平台應支援每個 AppKey 同時有兩把有效的 Secret。外洩時立即產生新 Secret，讓合作夥伴切換，切換完成後停用舊 Secret；若已確認被濫用，則直接停用舊 Secret，接受短暫中斷。同時根據稽核日誌追查外洩期間的可疑呼叫。

**詳細解析**：只允許一把 Secret 的設計，輪換時一定會有一段時間舊的已失效、新的還沒部署，造成服務中斷，結果大家都不願意輪換。雙 Secret 讓驗證時兩把都試，輪換就變成無痛的例行操作，甚至可以定期強制輪換。稽核日誌要記錄每次呼叫的 AppKey、來源 IP、介面與結果，才能在事後判斷影響範圍。若合作夥伴還綁定了 IP 白名單，即使 Secret 外洩，攻擊者也很難從其他位置成功呼叫，這是縱深防禦的價值。

**面試回答方式**：先給出雙 Secret 無縫輪換的設計，再說明緊急停用與事後稽核，最後提 IP 白名單降低外洩的影響。
