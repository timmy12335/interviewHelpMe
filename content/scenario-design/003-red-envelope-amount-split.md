# 題目

群組裡發一個 100 元、分成 10 份的拼手氣紅包。每份金額要隨機、每人至少 0.01 元、全部加起來剛好 100 元。你會怎麼設計拆分演算法？什麼時候拆：發紅包時一次拆好，還是搶的時候才即時計算？

## 核心答案

最常見的是**二倍均值法**：每次在 `[0.01, 剩餘金額 / 剩餘人數 × 2]` 之間隨機取一個值，最後一人拿走剩下的全部。它保證每份期望值相等、最小值有下限、總和精確。所有計算都要以「分」為單位的整數進行，避免浮點誤差。另一種是**線段切割法**：在 (0, 總金額) 上隨機選 n-1 個不重複的切點，排序後相鄰差值就是每份金額，分布更自然、可以出現極大值。至於何時拆，**預先拆好**存進 Redis List、搶的時候 `LPOP` 是較穩健的做法，搶紅包變成一個原子的出隊操作，也方便稽核。

## 詳細解析

**為什麼要以分為單位**：100 元等於 10000 分，整數運算沒有 `0.1 + 0.2 != 0.3` 的問題。若用 `double`，十份加總可能變成 99.99999，導致對帳不平。對外顯示時再除以 100。Java 裡也可以用 `BigDecimal`，但整數分在儲存和比對上最簡單。

**二倍均值法的推導**：設剩餘金額 M、剩餘人數 N，均值是 M/N。在 `[1, 2M/N)` 區間均勻取值，期望值剛好是 M/N，所以每個人的期望值都相同，先搶後搶不吃虧。同時上限 2M/N 保證剩下的人每人至少還能分到 1 分：取走最多不到 2M/N 後，剩 N-1 人的平均仍大於 0。缺點是每份金額不會超過當下均值的兩倍，分布偏集中，手氣王不會太誇張。

**線段切割法**：把 10000 分看成一條線段，隨機選 9 個 1 到 9999 之間不重複的整數作為切點，排序後計算相鄰差。只要切點不重複，每段至少 1 分。它允許某一份非常大，「驚喜感」較強，但實作要處理去重，且隨機數品質影響分布。

**預先拆分 vs 即時計算**：即時計算時，每次搶都要讀取剩餘金額與人數、計算、寫回，這三步要原子化（Lua 腳本），而且演算法改動會直接影響線上。預先拆分是在發紅包時就把 10 個金額算好放進 Redis List，搶的時候 `LPOP` 一個，天然原子、O(1)，而且整包的金額在發出那一刻就固定了，事後稽核也有依據。代價是要多佔一些記憶體，以及紅包過期時要把剩餘金額退回。

**搶與拆分離**：實務上常把「搶到資格」和「入帳」拆開：先在 Redis 用 Lua 腳本同時完成「檢查這人沒搶過」與「彈出一份金額」，再送訊息非同步記帳到資料庫。使用者幾毫秒內就知道結果，帳務寫入則可以削峰處理。

## 面試回答方式

先講約束條件：隨機、下限 0.01、總和精確，然後立刻說「以分為單位用整數」，這是最容易被扣分的細節。接著介紹二倍均值法並解釋期望值為什麼公平，再提線段切割法作為對比。最後回答架構面：預先拆好放 Redis List、搶時 LPOP，並用 Lua 腳本防止同一人重複搶。

## 講稿

我會先把三個約束講清楚：金額要隨機，每人至少一分錢，全部加起來剛好等於總額。

第一個細節是單位。我一律用分來算，一百元就是一萬分，用整數運算，避免浮點誤差讓帳對不平。

演算法最常用二倍均值法。每次在一分到剩餘均值的兩倍之間隨機取一個數，最後一個人拿走剩下的全部。因為區間的期望值剛好等於均值，所以先搶後搶，期望拿到的錢都一樣。上限是均值的兩倍，也保證後面的人至少還分得到一分。如果想要更有驚喜感，可以用線段切割法，在線段上隨機切九刀，每段就是一份。

至於什麼時候拆，我傾向發紅包時就全部算好，放進 Redis 的 List。搶的時候彈出一個，天然原子。再搭配 Lua 腳本確認這個人沒搶過，最後送訊息非同步入帳。

## 常見追問

### 二倍均值法下，越晚搶的人是不是越吃虧？

**核心答案**：不會。每一輪取值區間的期望值都等於當下的剩餘均值，而剩餘均值在期望上一直維持 M/N 不變，所以每個位置的期望金額都相同。只是後面的人金額的變異數會比較大，最後一人因為拿走全部剩餘，可能特別多或特別少。

**詳細解析**：設總額 M、人數 N。第一人期望拿 M/N，剩下的期望是 M(N-1)/N，分給 N-1 人，均值仍是 M/N。依此類推，每個位置的期望值都是 M/N。差別在分布形狀：越後面的人，其取值上限依賴前面所有人的隨機結果，波動累積下來，變異數較大。很多人覺得「最後一個比較多」，其實是記住了極端案例。如果產品希望分布更平均，可以縮小區間倍數（例如 1.5 倍），代價是隨機感變弱。

**面試回答方式**：用期望值的推導回答「不吃虧」，再補充變異數會變大這個細節，顯示你不只背結論，還理解分布。

### 同一個使用者連點兩次，怎麼避免他搶到兩份？

**核心答案**：把「檢查是否搶過」和「領取一份」放進同一支 Lua 腳本，以 Redis Set 或 Hash 記錄已搶使用者，原子地完成判斷與領取。資料庫的搶紅包記錄表上也要有 `(紅包ID, 使用者ID)` 的唯一索引作為最後防線。

**詳細解析**：如果先 `SISMEMBER` 判斷、再 `LPOP` 領取，兩個並發請求可能都通過判斷。Lua 腳本裡依序執行 `SISMEMBER`、`LPOP`、`SADD` 並一次回傳結果，就不會有中間狀態。即使 Redis 發生主從切換造成極少數重複，非同步入帳時資料庫的唯一索引會讓第二筆寫入失敗，這時把那份金額退回紅包即可。前端防抖只是體驗優化，不能當作正確性保證。

**面試回答方式**：講出「判斷與領取必須同一原子操作」，給出 Lua 裡的三個指令順序，最後提資料庫唯一索引兜底，層次分明。

### 紅包 24 小時沒被搶完，剩下的錢怎麼處理？

**核心答案**：發紅包時就登記一個 24 小時後到期的延遲任務。到期時把紅包狀態改為已過期（條件更新，避免與最後一次搶並發衝突），計算未領取的金額總和，退回發送者的餘額，並清除 Redis 裡剩下的資料。

**詳細解析**：退款金額不能用「總額減已領取」這種可能被並發影響的計算，應以 Redis List 中剩下的金額或資料庫裡未被領取的分份為準，且先把狀態切成「過期中」阻止新的領取。退款本身是帳務操作，要寫入流水並以紅包 ID 做冪等鍵，避免延遲任務重試時重複退款。延遲任務的實作可以沿用訂單逾時取消的方案，再加上每日掃表兜底。

**面試回答方式**：強調三件事：先封住領取、以剩餘份額計算退款、退款冪等。並指出這和訂單逾時取消是同一類延遲任務問題。
