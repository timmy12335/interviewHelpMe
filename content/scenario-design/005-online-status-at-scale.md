# 題目

一個有上億註冊使用者的 App，需要知道「某個使用者現在是否在線」，也需要知道「目前總共有多少人在線」以及「今天有多少人上線過」。你會怎麼設計？資料結構與記憶體成本大概是多少？

## 核心答案

先把需求拆成三個不同的問題，各用最適合的結構：**單人是否在線**靠心跳加過期時間判定，可用 Redis 的 key 加 TTL，或在 ZSet 裡以最後心跳時間為 score；**即時在線總數**是對「最近 N 秒有心跳的人」計數，用分片計數器或對 ZSet 做範圍計數；**當日上線人數**是去重計數，精確需求用 **Bitmap**（使用者 ID 當偏移量，1 億人約 12 MB），允許誤差用 **HyperLogLog**（固定 12 KB，誤差約 0.81%）。判定「在線」的依據是**心跳**而不是連線事件，因為行動網路斷線常常不會送出離線通知。

## 詳細解析

**為什麼靠心跳**：App 進入背景、切換網路、進電梯，TCP 連線可能沒有正常關閉，伺服器收不到斷線事件。所以「在線」的定義應該是「最近 T 秒內有心跳」，例如每 30 秒送一次心跳，超過 90 秒沒收到就視為離線（容忍兩次丟包）。

**單人在線查詢**：最簡單是 `SET online:<uid> 1 EX 90`，每次心跳續期，查詢就是 `EXISTS`。一億使用者若同時有一千萬人在線，就是一千萬個 key，每個 key 在 Redis 約佔 50 到 70 位元組，約 600 MB 左右，可接受但需要叢集分片。另一種是以使用者 ID 取模分成多個 Hash，field 是 uid、value 是最後心跳時間，查詢時比對時間是否在 90 秒內，記憶體更省，但過期要靠背景清理。

**即時在線總數**：最直接的是一個 ZSet，score 是最後心跳時間，`ZCOUNT online now-90 now` 即可得到總數，再定期 `ZREMRANGEBYSCORE` 清除舊成員。單一 ZSet 千萬成員會變成大 key，要按 uid 分成 N 個 ZSet 分別計數再加總。若只需要大致數字，也可以讓每台長連線閘道回報自己的連線數，彙總後就是在線總數，完全不碰使用者層級的資料。

**當日上線人數（去重）**：Bitmap 以 uid 為偏移量 `SETBIT dau:20261124 <uid> 1`，`BITCOUNT` 取得人數。一億個位元等於 12.5 MB，而且可以 `BITOP AND/OR` 計算連續登入、週活躍等。前提是 uid 是連續的整數；若是 UUID 或雪花 ID，要先映射成連續序號，否則稀疏的大偏移量會浪費記憶體。允許約 1% 誤差時，HyperLogLog 每天只要 12 KB，`PFADD` / `PFCOUNT` 即可，也支援 `PFMERGE` 合併多天。

**整體架構**：心跳不應直接打到 Redis。通常由長連線閘道或 API 閘道接收心跳，在本機先合併、批次寫入 Redis，降低寫入量；上下線的狀態變化（例如從離線轉在線）再發事件給需要的服務，例如好友上線提醒。

## 面試回答方式

這題的關鍵是先拆需求，因為「是否在線」「在線總數」「當日上線人數」需要的資料結構完全不同。先講心跳判定在線的原因，再依序給出三種需求的結構與記憶體估算，一定要把數字算出來（12.5 MB、12 KB），這是面試官最想看到的。最後補上心跳的批次寫入與分片，說明你考慮過寫入壓力與大 key。

## 講稿

這題我會先拆成三個問題，因為它們需要的資料結構完全不同。

第一，判斷某個人在不在線。我不靠連線斷開的事件，因為手機網路斷了常常沒有通知。所以用心跳，大約三十秒一次，超過九十秒沒收到就當離線。實作可以用 Redis 的 key 加過期時間，每次心跳續期，查詢就看 key 存不存在。

第二，現在總共多少人在線。可以用有序集合，分數放最後心跳時間，數一下最近九十秒內的成員。成員太多會變大 key，要按使用者 ID 分片再加總。只要概數的話，讓每台閘道回報連線數也行。

第三，今天有多少人上線過，這是去重計數。要精確就用 Bitmap，使用者 ID 當偏移量，一億人才十二點五 MB。可以接受百分之一左右的誤差，就用 HyperLogLog，一天只要十二 KB。

最後，心跳量很大，我會在閘道先合併，再批次寫進 Redis。

## 常見追問

### 使用者 ID 是雪花 ID 這種 64 位元的大數字，還能用 Bitmap 嗎？

**核心答案**：不能直接用。Bitmap 的記憶體由最大偏移量決定，64 位元的 ID 會讓偏移量大到不可能配置。需要先把使用者 ID 映射成從 0 開始連續的序號（例如註冊時分配一個自增的內部編號），或改用 Roaring Bitmap 這種針對稀疏資料壓縮的結構，或接受誤差改用 HyperLogLog。

**詳細解析**：`SETBIT key 2^40 1` 會讓 Redis 嘗試配置上百 GB 的字串，Redis 本身對單一字串有 512 MB 的上限，所以直接失敗。常見解法是維護一個 uid 到序號的映射表，在註冊時就分配好，這個序號也可以拿來做其他位元運算的統計。若使用者 ID 分布在幾個區段內，也可以按區段切成多個 Bitmap。Roaring Bitmap 把整數空間切成 65536 為一組的容器，稀疏時用陣列、稠密時用位圖，可以在 Redis 模組或應用層使用。

**面試回答方式**：說出「Bitmap 的成本由最大偏移量決定」這個原理，再給出序號映射、分段、Roaring Bitmap、HyperLogLog 四種出路，視精確度需求選擇。

### 心跳每 30 秒一次、一千萬人在線，Redis 撐得住嗎？

**核心答案**：一千萬人每 30 秒一次，大約每秒 33 萬次寫入。單一 Redis 節點大約每秒十萬級操作，所以需要叢集分片，或在閘道層先合併心跳再批次寫入（例如每 5 秒用 Pipeline 送一批），把對 Redis 的請求數降到原本的幾十分之一。

**詳細解析**：心跳的內容高度重複，真正需要的只是「最後心跳時間」。閘道可以在記憶體裡維護本機連線使用者的最後心跳時間，定期批次寫入。更進一步，閘道本身就知道哪些連線還活著，可以只在「狀態改變」時（新上線、超時下線）才寫入 Redis，平時完全不寫。代價是閘道故障時，它負責的使用者狀態會短暫不準，需要靠 TTL 自然過期來收斂。

**面試回答方式**：先算數字（每秒 33 萬），再提出批次寫入與「只在狀態變化時寫」兩個降量手段，並說明閘道故障時的收斂方式。

### 好友列表要顯示每個好友是否在線，怎麼查比較有效率？

**核心答案**：好友數通常在幾百以內，用一次批次查詢取得所有好友的狀態，例如 `MGET` 多個在線 key，或用 Pipeline 查 Hash，不要逐一呼叫。若好友上線需要即時提醒，則改為訂閱模式：使用者上線時通知其在線好友，而不是讓每個人輪詢。

**詳細解析**：在 Redis Cluster 下，`MGET` 的 key 若分散在不同槽位會報錯，需要用客戶端把 key 按槽位分組並行查詢，或用 hash tag 讓同一使用者的資料落在同一槽位（但好友的 key 本來就不同人，通常用前者）。推送模式下，上線事件會被放大到所有好友，名人帳號可能有上萬好友，此時要限制只推給在線好友，或改為使用者打開好友列表時才拉取。這和社群動態消息的推拉取捨是同一類問題。

**面試回答方式**：先給批次查詢的作法並點出叢集下跨槽位的問題，再談即時提醒的推拉取捨與名人帳號的放大效應。
