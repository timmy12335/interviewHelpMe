# 題目

限量商品開賣時，上萬個請求同時扣同一個商品的庫存。怎麼保證不會超賣（賣出比庫存多）？又怎麼避免少賣（明明還有貨卻賣不出去，或庫存被佔住遲遲不釋放）？

## 核心答案

**超賣**的根源是「先讀庫存、再判斷、再寫回」這三步不是原子的。解法是把判斷和扣減合成一個原子操作：資料庫層用 `UPDATE stock SET num = num - 1 WHERE sku = ? AND num >= 1` 的條件更新，高並發時把熱點庫存預熱到 Redis，用 Lua 腳本一次完成「檢查並扣減」，再非同步落庫。**少賣**則來自扣了庫存卻沒成單：下單失敗沒回補、未付款訂單佔住庫存、Redis 與資料庫不一致。解法是「預扣 + 逾時釋放 + 對帳」：扣減記錄要帶訂單號以便冪等回補，未付款訂單逾時就釋放，並定期比對 Redis 與資料庫的庫存。

## 詳細解析

**為什麼會超賣**：典型錯誤寫法是 `select num` 得到 1，判斷 `num > 0`，再 `update num = 0`。兩個執行緒同時讀到 1，都判斷通過，都寫回，賣出兩件。在單機加 `synchronized` 救不了多實例部署；加分散式鎖雖然正確，但把整個商品序列化，吞吐量直接崩掉。

**資料庫條件更新**：`UPDATE ... SET num = num - ? WHERE sku = ? AND num >= ?`，檢查與扣減在同一條語句裡由行鎖保證原子，影響行數為 0 就代表庫存不足。正確且簡單，但同一行的更新會在行鎖上排隊，單一熱點 SKU 大約只能撐到每秒幾百到上千次更新。

**Redis + Lua 預扣**：開賣前把庫存寫進 Redis，用 Lua 腳本 `if tonumber(redis.call('get', KEYS[1])) >= tonumber(ARGV[1]) then return redis.call('decrby', KEYS[1], ARGV[1]) else return -1 end`。Redis 單執行緒執行腳本，天然原子，單節點每秒可處理數萬次。扣成功後再送訊息讓訂單服務非同步建單、資料庫再做一次條件扣減作為最終真相。

**分桶分散熱點**：單一 key 仍是單點。可以把 1000 件庫存拆成 10 個子 key 各 100 件，請求隨機或依使用者雜湊打到某一桶，某桶售罄再嘗試其他桶。代價是尾端庫存可能分散在不同桶，需要一個「歸攏」機制避免少賣。

**少賣的三個來源與對策**：第一，Redis 扣成功但建單失敗，必須回補，且回補要以訂單號冪等，避免重複加回去造成超賣。第二，下單後不付款，靠逾時取消釋放庫存。第三，Redis 故障切換遺失了扣減紀錄，靠定期以資料庫訂單為準的對帳任務校正。三者都做到，才能說庫存是「賣得掉、也不會多賣」。

## 面試回答方式

先把問題拆成「超賣」與「少賣」兩半，這是很多人漏掉的。超賣部分要講出根因是「讀－判斷－寫」非原子，然後按並發量給出三層解法：資料庫條件更新、Redis Lua 預扣、分桶。少賣部分講回補冪等、逾時釋放、對帳校正。結尾可以補一句「Redis 負責扛流量，資料庫負責最終真相」，說明你清楚各層的角色。

## 講稿

超賣的根本原因，是讀庫存、判斷、寫回這三步不是原子的。兩個請求同時讀到剩一件，都覺得可以買，結果賣出兩件。

所以解法就是把檢查和扣減合成一步。量不大的時候，用資料庫的條件更新：庫存大於等於購買數量才扣，影響行數是零就代表賣完了。可是同一行會在行鎖上排隊，熱門商品撐不住。這時候我會把庫存預熱到 Redis，用 Lua 腳本一次做完檢查和扣減，扣成功再送訊息非同步建單。單一 key 還是太熱的話，就把庫存拆成多個桶分散壓力。

另一半常被忽略的是少賣。Redis 扣了，建單卻失敗，要用訂單號冪等地把庫存加回去。下單不付款，要靠逾時取消釋放。Redis 故障丟了資料，要靠定期對帳，以資料庫的訂單為準來校正。

一句話總結，Redis 扛流量，資料庫保存最終真相。

## 常見追問

### 用 Redis 的 DECR 直接扣，扣到負數再加回去，可以嗎？

**核心答案**：功能上勉強可行，但不建議。DECR 本身是原子的，扣成負數時回補也能讓最終數字正確；問題在於「負數的瞬間」其他讀取者會看到錯誤狀態，回補失敗時還會永久少賣，而且大量無效請求都會真的改寫一次庫存值。

**詳細解析**：先扣後判斷的做法，在售罄後每一個請求仍然會執行 DECR 再 INCR，等於把無效流量也變成兩次寫入。若程序在 DECR 之後、INCR 之前崩潰，那一件庫存就永遠被扣掉了，形成少賣。此外，前端或其他服務如果直接讀這個 key 來顯示剩餘庫存，會看到負數。用 Lua 腳本把「檢查再扣」包成一步，售罄後的請求只讀不寫，邏輯也更清楚。進一步還可以在本機放一個「已售罄」旗標，直接在應用層擋掉後續請求，連 Redis 都不用打。

**面試回答方式**：先承認 DECR 是原子的，再指出它的三個副作用：中間狀態可見、崩潰造成少賣、無效寫入放大。最後給出 Lua 檢查再扣加本機售罄旗標的改良方案。

### 資料庫用樂觀鎖（版本號）防超賣，和條件更新有什麼差別？

**核心答案**：樂觀鎖是「讀出版本號，更新時比對版本號」，衝突時整個請求要重試；條件更新是「直接以庫存數量為條件」，只要數量還夠就會成功。在搶購這種高衝突場景，樂觀鎖的重試率極高，大部分請求白白失敗，條件更新的效率好得多。

**詳細解析**：版本號方案中，100 個請求同時讀到 version=5，只有一個能把它更新成 6，其餘 99 個失敗後要重新讀取再試，形成大量重試風暴，甚至在庫存還很多時也大量失敗，這就是一種少賣。條件更新 `WHERE num >= 1` 不在乎別人有沒有改過，只在乎剩餘數量夠不夠，所以只要還有貨，排隊等行鎖的請求依序都能成功。樂觀鎖適合衝突少、且更新內容依賴讀取結果的情境，例如編輯文件；庫存這種可交換的計數更新，條件更新是更自然的選擇。

**面試回答方式**：說清楚兩者的判斷依據不同（版本是否變化 vs 數量是否足夠），再用「100 個請求只成功 1 個」的例子說明高衝突下樂觀鎖造成的重試與少賣。

### 為什麼不直接用分散式鎖鎖住商品再扣庫存？

**核心答案**：分散式鎖能保證正確，但它把同一商品的所有請求完全序列化，而且每次扣減要多兩次網路往返（加鎖、解鎖）。在秒殺場景吞吐量會被鎖的持有時間卡死，還要處理鎖逾時、續期、誤刪別人的鎖等問題，成本遠高於一個原子的 Lua 腳本。

**詳細解析**：分散式鎖的意義是保護「一段包含多個步驟、無法用單一原子指令表達」的臨界區。庫存扣減本身就能用條件更新或 Lua 表達成單一原子操作，沒有必要再包一層鎖。若硬要用鎖，鎖的持有時間包含了讀庫存、判斷、寫回、甚至查資料庫，假設每次 5 毫秒，單一商品每秒最多 200 次，遠低於 Redis 單 key 的處理能力。真正需要鎖的是更複雜的流程，例如同時扣多個 SKU 並校驗組合規則，那時也應優先考慮把邏輯搬進一支 Lua 腳本裡。

**面試回答方式**：點出「鎖是為了保護多步驟臨界區，而扣庫存可以是單步原子操作」，再用持有時間換算出吞吐上限，展現你會用數字判斷方案。
