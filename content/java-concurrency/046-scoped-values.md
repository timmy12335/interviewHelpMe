# 題目

作用域值（Scoped Values）要取代 `ThreadLocal` 的哪些用法？它為什麼更適合虛擬執行緒？

## 核心答案

它針對的是 `ThreadLocal` 最主要的用法——**在呼叫鏈中隱式傳遞上下文**（追蹤 ID、租戶、當前使用者、語系），而不是把這些參數一路傳下去汙染所有簽章。

`ThreadLocal` 在這個用途上有三個問題，作用域值逐一改掉。**可變**——任何程式碼在任何位置都能 `set`，導致上下文的來源無法從程式碼推理；作用域值**綁定後不可變**。**生命週期無界**——設了不 `remove` 就一直留著，在池化執行緒上造成殘留與洩漏；作用域值綁定在一個明確的 lambda 作用域內，離開自動解除，語法上不可能忘記清理。**每執行緒一份副本**——數十萬個虛擬執行緒就是數十萬份；作用域值讓子任務**共享父的綁定而不複製**。

形式是 `ScopedValue.where(KEY, value).run(() -> ...)`，值只在那個 lambda 及其呼叫的所有程式碼中可見。

## 詳細解析

「共享而不複製」是它對虛擬執行緒最關鍵的改進。`InheritableThreadLocal` 在建立子執行緒時會**複製整個 map**，如果一個請求 fork 出一千個子任務，就是一千次複製。作用域值的綁定是不可變的，所以子任務可以**直接引用父的綁定鏈**——沒有複製成本，記憶體只有一份。這在「每個子任務一個虛擬執行緒」的模型下是必要的設計。

**它與結構化併發配套**：只有在 `StructuredTaskScope` 中 fork 的子任務才會自動繼承綁定。這不是限制而是刻意的設計——繼承需要一個明確的父子關係，而結構化併發正好提供了它。相比之下，提交到任意執行緒池的任務沒有明確的父子關係，所以不繼承（要傳遞就得明確地在任務內重新綁定）。

不可變帶來的取捨要誠實面對：某些既有模式會需要重構。例如「中介軟體逐步累積上下文」——第一層設追蹤 ID、第二層加使用者、第三層加租戶——在 `ThreadLocal` 下是連續的 `set`，在作用域值下必須改成**巢狀的 where 綁定**（每一層開一個新作用域）或一次綁定一個包含全部欄位的物件。後者通常更好，因為它讓「上下文包含什麼」成為一個明確的型別而不是散落的鍵。

**它不能取代 ThreadLocal 的所有用法**。`ThreadLocal` 還被用來做**每執行緒的可重用緩衝**（例如每執行緒一個 `SimpleDateFormat` 或 `byte[]`），那是為了避免同步或重複配置，語意上是「執行緒本地的快取」而不是「上下文」。**作用域值不適合這個用途**——它的值是不可變的、生命週期綁在作用域上，而快取需要的正好相反。而且在虛擬執行緒下，每執行緒緩衝的模式本身就該重新考慮（數十萬個執行緒各一份緩衝是不可行的）。

## 面試回答方式

先界定它針對的是**上下文傳遞**這個用法，不是 `ThreadLocal` 的全部。然後給 `ThreadLocal` 的三個問題與作用域值的逐一對應（可變 → 不可變、生命週期無界 → 綁定在明確作用域且語法上不可能忘記清理、每執行緒一份副本 → 共享不複製）。把**共享而不複製**講清楚——`InheritableThreadLocal` 建立子執行緒時複製整個 map，一千個子任務就是一千次複製；作用域值的綁定不可變所以能直接引用父的綁定鏈。加分點有兩個：只有結構化併發 fork 的子任務才繼承，因為繼承需要明確的父子關係；以及誠實指出它不能取代每執行緒可重用緩衝那類用法（語意是快取而非上下文，需求正好相反），而且那個模式在虛擬執行緒下本來就該重新考慮。

## 講稿

它針對的是 ThreadLocal 最主要的用法，在呼叫鏈中隱式傳遞上下文，像是追蹤 ID、租戶、當前使用者，而不是把這些參數一路傳下去汙染所有簽章。

ThreadLocal 在這個用途上有三個問題。第一是可變，任何程式碼在任何位置都能設定，導致上下文的來源沒辦法從程式碼推理。第二是生命週期無界，設了不清就一直留著。第三是每個執行緒一份副本。

作用域值逐一改掉。綁定之後不可變。綁定在一個明確的 lambda 作用域內，離開自動解除，語法上不可能忘記清理。還有子任務共享父的綁定而不複製。

第三點對虛擬執行緒最關鍵。可繼承的 ThreadLocal 在建立子執行緒時會複製整個對映，一個請求分出一千個子任務就是一千次複製。作用域值因為綁定是不可變的，子任務可以直接引用父的綁定鏈，沒有複製成本。

不過我要誠實說，它不能取代 ThreadLocal 的所有用法。每執行緒一個可重用緩衝那種模式，語意上是快取而不是上下文，需求正好相反。而且那個模式在虛擬執行緒下本來就該重新考慮。

## 常見追問

### 為什麼不乾脆把上下文當參數明確傳遞？

**核心答案**：因為**它會汙染整條呼叫鏈的簽章**。一個追蹤 ID 要從控制器傳到最底層的資料存取，中間可能經過十幾層方法，每一層都要加一個參數——而其中大部分方法根本不使用它，只是負責轉發。這不只囉嗦，還讓那些方法變得不可重用（沒有上下文的呼叫者無法使用它們），而且新增一個上下文欄位就要改動所有簽章。

**詳細解析**：所以隱式傳遞是有真實價值的，問題只在於 `ThreadLocal` 的實作方式太不受控。作用域值的定位正是「保留隱式傳遞的便利，但把生命週期與可變性管起來」。要注意隱式傳遞本身仍有代價——呼叫者看不出被呼叫的方法需要什麼上下文，忘記綁定時會在執行期才失敗（作用域值未綁定時 `get()` 拋 `NoSuchElementException`，這比 `ThreadLocal` 回傳 null 好，至少會明確失敗）。務實的判斷是：真正橫切所有層的少數項目（追蹤、租戶、語系）用隱式傳遞，業務相關的資料一律明確傳參。 把業務資料塞進上下文是常見的濫用，它會讓資料流完全隱形。

**面試回答方式**：先肯定明確傳參的問題——汙染整條呼叫鏈，大部分方法只是轉發卻要加參數，還讓方法不可重用、新增欄位要改所有簽章。由此說明隱式傳遞有真實價值，作用域值的定位是保留便利但管起生命週期與可變性。誠實給出隱式傳遞的代價（呼叫者看不出需要什麼上下文，忘記綁定在執行期才失敗）。收在務實判斷：橫切所有層的少數項目用隱式，業務資料一律明確傳參。

### 作用域值的效能與 ThreadLocal 相比如何？

**核心答案**：讀取略慢、寫入（綁定）快得多、記憶體省得多。`ThreadLocal.get()` 是一次雜湊表查找，通常很快；作用域值需要沿著綁定鏈往上找，鏈很深時稍慢，但 JDK 為此加了**每執行緒的小快取**（最近使用的綁定），常見情況下差距不明顯。綁定則便宜得多——它只是把一個節點推入鏈，而 `InheritableThreadLocal` 的繼承要複製整個 map。

**詳細解析**：**記憶體才是真正的差距所在**。在數十萬個虛擬執行緒的場景下，`ThreadLocal` 的每執行緒一份副本是壓垮記憶體的直接原因；作用域值的綁定只有一份，所有子任務共享。這也是為什麼虛擬執行緒的官方指引明確建議**檢視並減少 `ThreadLocal` 的使用**。但要注意這個差距只在「大量執行緒」的前提下才顯著——平台執行緒只有幾百個時，`ThreadLocal` 的記憶體成本完全不是問題。所以遷移的動機應該是「我要用大量虛擬執行緒」，而不是「新的比較快」。

**面試回答方式**：給出三個維度的比較（讀取略慢、綁定快得多、記憶體省得多）並說明各自的機制。強調**記憶體才是真正的差距**，而且只在大量執行緒的前提下才顯著——平台執行緒只有幾百個時 `ThreadLocal` 的成本不是問題。收在遷移動機的判斷：因為要用大量虛擬執行緒才遷移，不是因為新的比較快。

### 現有系統要怎麼從 ThreadLocal 遷移？

**核心答案**：分三步。**第一，盤點用途並分類**——是上下文傳遞、每執行緒快取、還是為了避免傳參的懶惰？只有第一類該遷移。第二，把散落的上下文收斂成一個不可變的上下文物件——與其有五個 `ThreadLocal`，不如有一個 `RequestContext` record 包含全部欄位，這一步即使不遷移也是改善。**第三，在請求入口統一綁定**，並把「逐步 set」的模式改成「在需要時開新的巢狀作用域」。

**詳細解析**：實務上第二步的價值最大，也最獨立——它讓上下文包含什麼變成一個明確的型別，可以被檢視、被測試、被序列化，而不是散落在幾個靜態欄位裡。做完這一步之後，是否遷移到作用域值反而變成一個小改動。遷移的風險集中在第三方框架：日誌的 MDC、追蹤庫、安全框架都用了 `ThreadLocal`，它們沒有遷移之前，混用兩套機制會讓上下文只傳一半。所以現實的路徑通常是漸進的——自己的上下文先收斂成一個物件、框架的部分繼續用它們的機制、等生態跟上再統一。能給出「先收斂成型別、遷移是後續的小步」這個順序，比直接談 API 替換更有工程感。

**面試回答方式**：給三步（盤點分類、收斂成不可變上下文物件、入口統一綁定）。重點放在**第二步價值最大也最獨立**——讓上下文包含什麼變成明確的型別，可檢視可測試，做完後遷移反而是小改動。誠實指出風險集中在第三方框架（MDC、追蹤、安全框架），混用兩套會讓上下文只傳一半。收在現實路徑：漸進遷移，自己的先收斂、等生態跟上再統一。
