# 題目

什麼是「不安全發布」？把一個物件的引用賦值給共享變數，為什麼別的執行緒可能看到未初始化的狀態？

## 核心答案

**發布**指的是讓一個物件能被當前作用域之外的程式碼存取（賦值給公開欄位、放進共享容器、從非私有方法回傳、或傳給外部回呼）。**不安全發布**是指發布的過程沒有建立 happens-before 關係，於是**別的執行緒可能看到一個引用非 null、但物件的欄位還是預設值的狀態**。

原因是重排序：`obj = new Foo(5)` 在位元組碼層面是「配置記憶體 → 執行建構子 → 把引用賦給變數」三步，而 **JIT 與處理器可以把第三步提到第二步之前**（對單執行緒而言結果相同，符合 as-if-serial）。另一個執行緒讀到那個引用時，建構子可能還沒跑完。

安全發布有四種標準方式：**在靜態初始化器中初始化**（類別初始化由 JVM 保證同步）、**把引用存入 volatile 欄位或 AtomicReference**、**把引用存入由鎖保護的欄位**、**把引用存入執行緒安全容器**（`ConcurrentHashMap`、`BlockingQueue` 等，它們的內部同步提供了必要的順序保證）。**外加一個特例：所有欄位都是 final 的不可變物件，即使不安全發布也保證看得到正確的欄位值**。

## 詳細解析

**final 欄位的特殊保證是 JMM 少數幾個免費午餐**：建構子結束時有一道隱含的屏障，保證 final 欄位的寫入不會被重排到建構子之後。所以**完全不可變的物件可以自由地在執行緒間傳遞而不需要任何同步**——這是不可變設計最大的併發紅利。但它有一個前提：**`this` 不能在建構期間逸出**。如果建構子把自己註冊到監聽器或啟動了引用自己的執行緒，其他執行緒就可能在建構完成前拿到引用，保證失效。

**雙重檢查鎖之所以必須加 volatile，就是這個問題的具體案例**：沒有 volatile 時，第二個執行緒可能看到非 null 的 `instance` 卻讀到未初始化的欄位。volatile 阻止了那個重排序，也建立了寫入者與讀取者之間的 happens-before。

**「有效不可變」是一個實用的中間狀態**：物件本身有可變欄位，但發布之後**約定不再修改**（例如從資料庫載入設定物件，載入完成後只讀）。這種物件**必須安全發布**（不能靠 final 的保證），但發布之後就可以自由共享。實務上很多快取與設定物件就是這樣用的，代價是那個「不再修改」的約定沒有任何機制保證，只能靠紀律與文件。

**容器提供的保證常被忽略**：把物件放進 `ConcurrentHashMap` 再由別的執行緒取出，**是安全發布**——因為容器內部的同步在放入與取出之間建立了 happens-before。同樣地，`BlockingQueue` 的 put 與 take、`CountDownLatch` 的 countDown 與 await、`Future` 的完成與 `get`，都提供這個保證。**知道這一點可以避免很多不必要的額外同步**：資料經由執行緒安全的通道傳遞時，不需要再對物件本身加鎖。

## 面試回答方式

先定義「發布」與「不安全發布」，並用**三步重排序**解釋原因——配置、建構、賦值三步中，賦值可以被提前，所以另一個執行緒可能看到引用非 null 但欄位還是預設值。接著給**四種安全發布方式**（靜態初始化、volatile／AtomicReference、鎖保護的欄位、執行緒安全容器），再補上特例：**全 final 欄位的不可變物件即使不安全發布也保證看得到正確值**，但前提是 `this` 沒在建構期逸出。加分點有兩個：把**雙重檢查鎖需要 volatile** 定位成這個問題的具體案例；以及指出**執行緒安全容器本身就是安全發布通道**（放入與取出之間建立 happens-before），所以資料經由它傳遞時不需要再對物件加鎖——這能避免很多不必要的同步。

## 講稿

發布指的是讓一個物件能被當前作用域之外的程式碼存取。不安全發布是指這個過程沒有建立 happens-before 關係，於是別的執行緒可能看到引用不是 null，但物件的欄位還是預設值。

原因是重排序。建立物件在底層是三步，配置記憶體、執行建構子、把引用賦給變數。JIT 跟處理器可以把第三步提到第二步前面，因為對單執行緒來說結果是一樣的。另一個執行緒讀到那個引用的時候，建構子可能還沒跑完。

安全發布有四種標準方式。在靜態初始化器裡初始化、存進 volatile 欄位、存進由鎖保護的欄位、或是存進執行緒安全容器。

另外有一個特例。所有欄位都是 final 的不可變物件，就算不安全發布，也保證看得到正確的欄位值。這是不可變設計最大的併發紅利。但前提是 this 不能在建構期間逸出。

還有一件事很多人忽略。把物件放進併發容器再由別的執行緒取出，本身就是安全發布，因為容器內部的同步已經建立了順序關係。知道這點可以省掉很多不必要的額外同步。

## 常見追問

### 什麼叫「this 在建構期間逸出」？

**核心答案**：指的是在建構子還沒執行完的時候，`this` 引用就被外部程式碼拿到了。常見的三種形式：**在建構子裡把自己註冊到監聽器或事件匯流排**、**在建構子裡啟動一個引用 `this` 的執行緒**、以及**在建構子裡呼叫可被覆寫的方法**（子類別的覆寫實作會拿到一個父類別已初始化但子類別欄位還是預設值的 `this`）。

**詳細解析**：第三種最隱蔽，因為它不涉及任何併發程式碼就會出錯——父類別建構子呼叫的可覆寫方法在子類別建構子之前執行，子類別的 final 欄位此時還是 null 或 0。這是一個**單執行緒下也會出錯的設計問題**，併發只是讓它更難查。正確做法是：**建構子裡不呼叫可被覆寫的方法**（要嘛把方法設為 final 或 private，要嘛把初始化移到一個明確的 `init()`）；**需要註冊自己時用靜態工廠**——先完整建構、再註冊、最後回傳，這樣外部只會看到已完成的物件。

**面試回答方式**：給三種形式，並特別展開第三種——**在建構子裡呼叫可覆寫方法**，因為它連單執行緒下都會出錯（子類別欄位還是預設值），併發只是讓它更難查。給出兩個明確的做法：建構子裡不呼叫可覆寫方法；需要註冊自己時用靜態工廠先建構再註冊。

### 為什麼靜態初始化器不需要額外同步？

**核心答案**：因為 **JVM 保證類別初始化過程是執行緒安全的**。第一個觸發初始化的執行緒會取得該類別的初始化鎖並執行 `<clinit>`，其他執行緒會阻塞等待，直到初始化完成才繼續。這個機制由 JVM 規範保證，而且它建立了 happens-before——初始化中的所有寫入對之後看到該類別的所有執行緒都可見。

**詳細解析**：這正是**靜態內部類別（holder）單例模式**的原理：把實例放在一個靜態內部類別的靜態欄位裡，只有第一次存取那個內部類別時才觸發初始化，於是同時得到了**延遲載入**與**執行緒安全**，而且**沒有任何同步成本**（初始化完成後的存取就是普通的靜態欄位讀取）。它比雙重檢查鎖更簡單也更不容易寫錯。要注意的是**如果初始化過程拋出例外，該類別會被標記為錯誤狀態**，之後所有存取都直接拋 `NoClassDefFoundError`，而且**看不到原始的例外原因**——這讓靜態初始化的失敗特別難查，所以初始化邏輯應該盡量簡單且不依賴外部資源。

**面試回答方式**：給出 JVM 的保證機制（初始化鎖、其他執行緒阻塞等待、建立 happens-before）。然後連到最有價值的應用——**靜態內部類別 holder 單例**，同時得到延遲載入與執行緒安全且零同步成本，比雙重檢查鎖更簡單。加分點是誠實指出風險：初始化拋例外會讓類別進入錯誤狀態、之後只看得到 `NoClassDefFoundError` 而看不到原因，所以初始化邏輯要簡單且不依賴外部資源。

### 「有效不可變」與真正不可變差在哪？

**核心答案**：**真正不可變**由型別保證（全部欄位 final、沒有 setter、防禦性拷貝），編譯器與 JMM 都能利用這個事實，所以連不安全發布都是安全的。**有效不可變**只是**約定**——物件技術上可以修改，但發布之後大家同意不再改。它**必須安全發布**（volatile、鎖、或執行緒安全容器），因為沒有 final 欄位的保證可以依靠。

**詳細解析**：實務上有效不可變很常見，因為完全不可變有時做不到——物件由框架反射建立（需要無參建構子與 setter）、由 JSON 反序列化填入、或者要分階段從多個來源組裝。這些場景下的務實做法是**明確劃出一個「發布點」**：在那之前是單執行緒的建構階段（可以隨意修改），在那之後是共享的唯讀階段。**把這個界線寫進程式碼與文件是關鍵**——用一個 `volatile boolean published` 旗標加上斷言、或者把物件包在一個只暴露 getter 的介面後面。**沒有標示界線的有效不可變是最危險的，因為它看起來像可變物件，維護者不會知道自己不該改它。**

**面試回答方式**：講清楚差別的本質——**型別保證 vs 約定**，以及由此推出的實際後果：真正不可變連不安全發布都安全，有效不可變必須安全發布。說明為什麼有效不可變在實務上常見（框架反射建立、反序列化、分階段組裝）。收在最重要的建議：**必須明確標示發布點的界線**，否則它看起來就像可變物件，維護者不會知道不該改它。
