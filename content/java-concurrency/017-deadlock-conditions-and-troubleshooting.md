# 題目

死鎖產生需要滿足哪些條件？寫一個死鎖的例子。線上發生死鎖時該怎麼排查？

## 核心答案

死鎖需要同時滿足四個條件：互斥、持有並等待、不可搶佔、循環等待。最經典的例子是兩個執行緒以相反順序取得兩把鎖。排查死鎖最直接的方法是用 `jstack` 導出執行緒堆疊，JVM 會自動偵測並標示出死鎖的執行緒與鎖持有關係。

## 詳細解析

**死鎖的四個必要條件**：互斥條件、持有並等待、不可搶佔、循環等待。只要破壞其中任何一個條件，就能避免死鎖。

**經典死鎖範例**：執行緒 1 先取得鎖 A、再嘗試取得鎖 B；執行緒 2 先取得鎖 B、再嘗試取得鎖 A，雙方永久互相等待。

**如何預防死鎖**：統一鎖的取得順序、使用逾時機制（`tryLock`）、一次性取得所有需要的資源、縮小鎖的粒度與持有時間。

**線上排查步驟**：用 `jstack <pid>` 導出執行緒堆疊，若存在死鎖會有「Found one Java-level deadlock」的明確標示；也可用 `jconsole`、`VisualVM` 或 Arthas 的 `thread -b` 指令找出阻塞的執行緒。

## 面試回答方式

先背出四個必要條件（互斥、持有並等待、不可搶佔、循環等待），但不要只是背條件本身，緊接著用一句話串起來：「只要破壞其中任何一個就能避免死鎖」，這個補充讓四個條件從死知識變成可操作的預防原則。接著馬上用一個具體的雙鎖交叉範例說明死鎖怎麼發生，比空泛描述更容易讓面試官確認你真的理解。最後排查方法一定要提到 `jstack` 這個具體工具名稱與「Found one Java-level deadlock」這個關鍵輸出訊息，展現這不是紙上談兵而是有實際排查經驗。

## 常見追問

### 除了死鎖，還有哪些類似的並行問題？它們和死鎖有什麼不同？

**核心答案**：活鎖（Livelock）是指多個執行緒都在持續改變狀態試圖避讓對方，但因為互相反應反而誰都無法真正推進（不像死鎖是靜止不動，而是「動」但沒有進展）；饑餓（Starvation）是指某個執行緒因為排程或鎖分配策略的問題，長期甚至永久得不到需要的資源，即使系統整體並沒有卡死。

**詳細解析**：活鎖的經典比喻是「兩人在走廊相遇，同時往同一邊讓路，結果又撞在一起，反覆調整方向卻永遠錯身不了」——程式碼中常見於「偵測到衝突就退讓重試」的邏輯設計不當，導致多個執行緒不斷互相退讓卻沒人真正往前推進；解法通常是引入隨機退讓時間，打破這種同步性的互相反應模式。饑餓最常見的成因是使用非公平鎖時，某個執行緒運氣一直不好，總是被插隊的執行緒搶先，或是優先級排程策略下低優先級任務永遠排不到；解法可以是改用公平鎖（見 [[005-reentrantlock-fair-vs-unfair.md]]）或調整排程策略保證最低限度的執行機會。三者的共同點是「執行緒無法正常推進」，差異在於死鎖是完全靜止的循環等待，活鎖是持續變化但沒有實質進展，饑餓則是系統其他部分正常運作、只是某個特定執行緒被冷落。

**面試回答方式**：用「死鎖是靜止的循環等待、活鎖是動態但沒進展、饑餓是被冷落但系統正常」這組對比清楚區分三者，是這題最容易讓人印象深刻的回答方式，比逐一分別解釋更能展現你理解它們在同一個問題光譜上的不同位置。

### 為什麼「統一加鎖順序」在複雜系統中有時很難徹底落實？

**核心答案**：因為大型系統中鎖的取得順序往往橫跨多個模組、多個團隊維護的程式碼，甚至涉及第三方函式庫內部的鎖，單一開發者或團隊很難掌握系統中「所有」可能同時被持有的鎖，也就難以保證一個全域一致的加鎖順序規範被所有程式碼路徑遵守。

**詳細解析**：「統一加鎖順序」這個原則說起來簡單，但實務上的挑戰在於：系統可能隨著時間演進，新增的程式碼路徑不小心引入了新的鎖組合，卻沒有人意識到需要檢查它是否違反了既有的加鎖順序約定；不同團隊維護的模組之間，鎖的取得可能透過深層的方法呼叫鏈間接發生，很難單靠程式碼審查發現；第三方函式庫內部的鎖更是完全不受應用程式碼控制。實務上比較務實的做法是：盡量減少「需要同時持有多把鎖」的程式碼路徑（用更細粒度的鎖或無鎖資料結構降低這種需求）、對於真的無法避免的多鎖場景明確寫成文件與程式碼規範並搭配靜態分析工具檢查、以及優先使用帶逾時的 `tryLock` 而非無限期的 `lock`，讓即使順序不慎違反，系統也能透過逾時重試而非永久卡死來自我恢復。

**面試回答方式**：這題適合展現「工程實務中理想原則與現實複雜度的落差」這種務實視角，回答時不要只說「統一順序很重要」，而要具體講出為什麼在大型系統中做不到理想狀態，以及退而求其次的務實做法（逾時鎖、減少多鎖依賴），這種回答對資深職位特別加分。

### 資料庫層級的死鎖和 Java 應用層級的死鎖排查方式有何不同？

**核心答案**：資料庫（如 MySQL InnoDB）通常有內建的死鎖偵測機制，會自動選擇一個交易作為犧牲者回滾並拋出錯誤（不需要人工介入排查即可自動恢復），可以透過 `SHOW ENGINE INNODB STATUS` 查看最近一次死鎖的詳細資訊；Java 應用層級的死鎖，JVM 本身不會自動偵測並恢復，執行緒會永久卡住，必須靠人工用 `jstack` 等工具主動診斷，且需要重啟應用或手動介入才能恢復。

**詳細解析**：這個差異的根本原因在於資料庫的交易模型天生就需要處理並行衝突（這是資料庫系統設計的核心問題之一），因此資料庫實作了主動的死鎖偵測演算法（例如等待圖分析），一旦偵測到循環等待，會立刻主動打破僵局（回滾其中一個交易）讓系統自動恢復，只是這個過程對應用程式來說會體現為某個交易收到死鎖錯誤需要重試。相對地，JVM 對於應用程式碼中自行使用 `synchronized`/`ReentrantLock` 造成的死鎖，並沒有內建的自動偵測與打破機制（因為 JVM 無法安全地知道「回滾」哪個執行緒的操作才是安全的，這涉及業務邏輯），只能被動地讓執行緒永久等待，排查與恢復完全仰賴人工介入。

**面試回答方式**：用「資料庫會自動偵測並回滾恢復，Java 應用層只能人工排查且無法自動恢復」這組對比講清楚兩者的本質差異及背後原因（資料庫交易模型天生需要處理衝突），展現你對不同系統層級的死鎖處理哲學有全局理解，而不只是熟悉 Java 這一層。
