# 題目

非同步任務的例外跑去哪裡了？`CompletableFuture` 的逾時該怎麼設？

## 核心答案

非同步例外**不會傳播到提交它的執行緒**——它被記錄在 `CompletableFuture` 的內部狀態裡，只有在**有人去取結果**（`get`、`join`、或註冊了 `exceptionally`／`handle`）時才會浮現。所以「提交了但沒有人處理結果」的任務，**例外會完全靜默消失**。這是非同步程式碼最常見的失敗模式：功能沒有生效，日誌裡什麼都沒有。

處理例外有三個方法，語意不同：`exceptionally` 只在失敗時執行，把例外轉成一個替代值；`handle` 無論成敗都執行，同時拿到結果與例外；`whenComplete` 也是無論成敗都執行，但**不改變結果**（適合記錄日誌與清理，它會把原本的結果或例外原封不動往下傳）。

逾時方面，JDK 9 加了 **`orTimeout(n, unit)`**（逾時後以 `TimeoutException` 完成）與 `completeOnTimeout(value, n, unit)`（逾時後用預設值完成，適合降級）。但要注意逾時只是「不再等待結果」，並不會取消底層正在執行的工作——那個執行緒仍然佔著資源跑到結束。

## 詳細解析

**例外會被包成 `CompletionException`**，所以 `exceptionally` 拿到的是包裝過的例外，要用 `getCause()` 取出原始的。這在做「依例外型別分支處理」時特別容易踩到——判斷 `instanceof MyException` 會失敗，因為外面包了一層。寫一個統一的拆包工具方法是實務上必要的。

執行緒池的選擇是另一個大坑。不帶 `Async` 後綴的方法（`thenApply`）在前一階段完成的那個執行緒上執行——如果前一階段是在某個 IO 回呼執行緒上完成的，後續的業務邏輯就跑在那個執行緒上，可能阻塞了框架的事件迴圈。帶 `Async` 但不指定執行器的方法用的是 `ForkJoinPool.commonPool`，那是全 JVM 共用的、大小為核心數減一、且不適合阻塞操作的池。正確做法是永遠明確傳入自己的執行器，這是最容易做到也最容易被忽略的一條紀律。

**逾時不取消底層工作**這件事的後果是：設了 100 毫秒逾時的下游呼叫，在下游真的變慢時，執行緒仍然被佔用直到下游回應或連線逾時。所以逾時必須是**多層的**——`CompletableFuture` 的逾時只保護呼叫方的等待，真正釋放資源需要 HTTP 客戶端的連線逾時與讀取逾時、以及下游服務自己的處理逾時。只設最外層的逾時是一種常見的誤以為安全。

組合多個 Future 時的失敗語意要選擇：`allOf` 在任一失敗時整體失敗（但**其他任務仍會繼續執行**，不會被取消），`anyOf` 在任一完成時就完成（包括以例外完成）。實務上常需要「等全部完成，然後分別處理成功與失敗的部分」——這要用 `allOf` 搭配每個 Future 各自的 `handle`，把失敗轉成一個表示失敗的值，這樣 `allOf` 就永遠成功，再從各個結果中分揀。**這個模式比直接用 `allOf` 有用得多**，因為部分失敗在真實系統裡是常態。

## 面試回答方式

先給根本問題：非同步例外不會傳播到提交執行緒，沒有人取結果就完全靜默消失——功能沒生效、日誌什麼都沒有，這是非同步最常見的失敗模式。接著精確區分三個處理方法（`exceptionally` 只在失敗時、`handle` 成敗都執行且可改結果、`whenComplete` 成敗都執行但不改結果）。逾時部分給出兩個 API，並立刻補上關鍵限制：逾時只是不再等待，不會取消底層工作，執行緒仍被佔用，所以逾時必須是多層的（連線逾時、讀取逾時、下游處理逾時），只設最外層是一種誤以為安全。加分點有兩個：例外被包成 `CompletionException` 所以型別判斷會失敗，需要統一的拆包工具；以及永遠明確傳入自己的執行器——不帶 `Async` 會跑在前一階段的執行緒上，帶 `Async` 不指定則用全 JVM 共用且不適合阻塞的 `commonPool`。

## 講稿

非同步例外不會傳播到提交它的執行緒，它被記錄在 Future 的內部狀態裡，只有在有人去取結果的時候才會浮現。所以提交了但沒有人處理結果的任務，例外會完全靜默消失。功能沒有生效，日誌裡什麼都沒有。這是非同步程式碼最常見的失敗模式。

處理例外有三個方法，語意不同。一個只在失敗時執行，把例外轉成替代值。一個無論成敗都執行而且可以改結果。還有一個無論成敗都執行但不改結果，適合記錄日誌跟清理。

逾時方面有兩個方法，一個逾時後拋例外，一個逾時後用預設值完成適合降級。但要注意逾時只是不再等待結果，並不會取消底層正在執行的工作。那個執行緒仍然佔著資源跑到結束。所以逾時必須是多層的，還需要連線逾時、讀取逾時、跟下游自己的處理逾時。只設最外層是一種誤以為安全。

還有一個最容易被忽略的紀律。永遠明確傳入自己的執行器。不帶 Async 的方法會跑在前一階段完成的那個執行緒上，帶 Async 但不指定的話用的是全 JVM 共用的池。

## 常見追問

### allOf 遇到部分失敗時該怎麼處理？

**核心答案**：`allOf` 的預設語意是「任一失敗則整體失敗」，而且其他任務不會被取消，仍然繼續執行。實務上更常需要的是「等全部結束，再分別處理成功與失敗」。做法是先讓每個 Future 各自 `handle`，把例外轉成一個能表示失敗的結果型別（例如 `Result.success(v)` 或 `Result.failure(e)`），這樣它們永遠成功完成，`allOf` 也永遠成功，之後再從結果清單中分揀。

**詳細解析**：這個模式的價值在於**把「部分失敗」變成一等公民**。真實系統中，聚合五個下游服務的資料時，一個失敗通常不該讓整個請求失敗——應該回傳其他四個的資料並標記缺少哪一項。直接用 `allOf` 的失敗語意會讓這種降級無法表達。**要注意的是 `allOf` 回傳 `CompletableFuture<Void>`**，取結果要自己從原本的 Future 清單裡 `join`（此時它們都已完成，所以不會阻塞）。另外失敗的那些任務仍然消耗了資源——如果需要在第一個失敗時取消其他任務，得自己呼叫 `cancel`，而 `cancel` 對 `CompletableFuture` 只是把它標記為取消，**同樣不會中斷底層執行**。

**面試回答方式**：先給預設語意的兩個要點（任一失敗即整體失敗、其他任務不會被取消）。重點放在實務模式：每個 Future 先各自 `handle` 把例外轉成結果型別，讓 `allOf` 永遠成功再分揀。說明它的價值是**把部分失敗變成一等公民**，讓降級可以表達。加分點是提醒 `allOf` 回傳 `Void` 要自己 join，以及 `cancel` 同樣不會中斷底層執行。

### 非同步程式碼的堆疊追蹤為什麼沒用？

**核心答案**：因為堆疊是執行緒的屬性，而非同步的每一段跑在不同的執行緒上。當 `thenApply` 裡的程式碼拋出例外時，堆疊只顯示「這個執行緒從執行緒池的 run 方法開始，然後進到這個 lambda」——完全看不到是誰提交了這個任務、也看不到前面的階段。追蹤鏈路因此斷裂，這是非同步除錯最大的成本。

**詳細解析**：緩解方式有三種。**在提交點記錄上下文**——把追蹤 ID 傳遞下去（見上下文傳遞那題），讓日誌可以關聯即使堆疊不能。**在關鍵邊界補充例外資訊**——用 `whenComplete` 捕捉例外後，包一層帶有業務上下文的例外再往下傳（例如「處理訂單 12345 的第二階段失敗」），這比原始堆疊有用得多。用 `-Djdk.tracePinnedThreads` 之類的診斷選項或商業 APM 工具，它們會在提交時記錄堆疊並在例外時拼接。根本的改善來自結構化併發與虛擬執行緒——回到阻塞式的順序寫法後，堆疊自然是完整的，這正是它們相對於回呼式非同步最大的實務優勢，而且這個優勢常常比效能更重要。

**面試回答方式**：先給原因——堆疊是執行緒的屬性，非同步各段在不同執行緒上，所以看不到提交者與前面的階段。給三種緩解方式，重點在第二種：在邊界包一層帶業務上下文的例外比原始堆疊有用得多。真正的加分點是收在結構化併發與虛擬執行緒——回到順序寫法後堆疊自然完整，這是它們相對於回呼式非同步最大的實務優勢，**而且常常比效能更重要**。

### 逾時之後怎麼真正釋放資源？

**核心答案**：必須在**產生阻塞的那一層**設逾時。HTTP 呼叫要設連線逾時與讀取逾時（`HttpClient` 的 `connectTimeout` 與請求的 `timeout`）；資料庫要設查詢逾時（`Statement.setQueryTimeout`）與連線池的取得逾時；訊息佇列要設拉取逾時。`CompletableFuture.orTimeout` 只影響等待方，對執行方毫無作用——它甚至不知道自己被放棄了。

**詳細解析**：完整的做法是**逾時預算沿呼叫鏈遞減**：入口設定總預算（例如 2 秒），每一層扣掉已耗時後把剩餘預算傳給下一層，下一層據此設定自己的逾時。這樣不會出現「上游已經放棄、下游還在慢慢做」的浪費。gRPC 的 deadline 機制就是這個設計，HTTP 也可以用自訂標頭傳遞。沒有預算傳遞的系統會累積大量「沒有人在等的工作」，在過載時這些幽靈工作會持續消耗資源，讓系統更難恢復——這是過載後遲遲無法自愈的常見原因。能講出「逾時預算要沿鏈傳遞」比只回答「在每一層設逾時」深一層。

**面試回答方式**：先給明確原則——必須在產生阻塞的那一層設逾時，並列舉具體 API（連線／讀取逾時、查詢逾時、連線池取得逾時），強調 `orTimeout` 只影響等待方。真正的加分點是**逾時預算沿呼叫鏈遞減**：入口設總預算、每層扣除已耗時後傳遞剩餘，並舉 gRPC 的 deadline 為例。收在後果：沒有預算傳遞會累積「沒有人在等的工作」，過載時這些幽靈工作讓系統無法自愈。
