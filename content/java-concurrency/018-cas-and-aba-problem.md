# 題目

CAS 是什麼？它有什麼缺點？什麼是 ABA 問題，怎麼解決？

## 核心答案

CAS（Compare-And-Swap）是一種由 CPU 提供的原子指令：比較記憶體中某個位置的值是否等於預期值，若相等才更新為新值，整個「比較並更新」過程是原子的，不需要作業系統層級的鎖。它是一種樂觀鎖思路，缺點包括自旋開銷、只能保證單一變數的原子性、以及 ABA 問題；ABA 問題可以透過加上版本號（如 `AtomicStampedReference`）來解決。

## 詳細解析

**CAS 的工作原理**：CAS 操作包含三個運算元：記憶體位置 V、預期原值 A、要更新的新值 B。操作邏輯是「如果 V 目前的值等於 A，就把 V 更新為 B，並返回成功；否則不做任何更新，返回失敗」，整個比較加更新的過程由 CPU 的原子指令（如 x86 的 `CMPXCHG`）保證不會被其他執行緒打斷。Java 中 `Unsafe` 類別（及其上層的 `AtomicInteger` 等原子類別）就是透過呼叫這類底層原子指令實作的。

**樂觀鎖 vs 悲觀鎖**：`synchronized`、`ReentrantLock` 屬於悲觀鎖思路——假設一定會發生競爭，所以先加鎖阻止其他執行緒進入；CAS 屬於樂觀鎖思路——假設大多數時候不會發生競爭，先嘗試直接更新，失敗了再重試（通常搭配自旋迴圈：`do { 讀取舊值; 計算新值; } while (CAS 更新失敗)`）。在競爭不激烈的場景，CAS 通常比加鎖效能更好（省去執行緒阻塞、喚醒的上下文切換開銷）；但競爭非常激烈時，CAS 大量失敗重試反而會浪費 CPU（忙等）。

**CAS 的缺點**：

1. **自旋開銷**：高競爭下大量執行緒同時 CAS 失敗並重試，CPU 使用率會顯著升高。
2. **只能保證單一共享變數的原子性**：如果需要同時對多個變數做原子性的複合操作，CAS 無法直接勝任，通常還是要靠鎖，或者把多個欄位合併封裝進一個物件、用一次 CAS 更新這個物件的引用。
3. **ABA 問題**：見下方詳細說明。

**ABA 問題**：假設執行緒 1 讀到某個值是 A，準備做 CAS；在執行緒 1 真正執行 CAS 之前，執行緒 2 把值從 A 改成 B，然後又改回 A；此時執行緒 1 執行 CAS，發現目前值仍然是 A（符合預期），CAS 成功——但實際上這個值已經被修改過兩次，只是恰好又變回了原來的值。在大多數簡單計數場景下這不是問題，但如果 A 代表的是「某個節點的引用」（例如無鎖鏈結串列、無鎖堆疊的實作），中間發生的 B 狀態變化（例如節點被釋放又重新分配）可能導致資料結構被破壞而不自知。

**如何解決 ABA 問題**：使用 `AtomicStampedReference`，每次更新時除了比較值本身，還額外比較一個單調遞增的版本號（stamp）；即使值從 A 變 B 又變回 A，版本號也已經不同，CAS 就會偵測到「這期間發生過變化」而失敗，強制執行緒重新讀取最新狀態再決定如何處理。`AtomicMarkableReference` 則是用一個簡化的布林標記代替版本號，用於只需要知道「是否被修改過」而不需要精確版本號的場景。
