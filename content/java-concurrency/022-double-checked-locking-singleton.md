# 題目

實作執行緒安全的單例模式時，雙重檢查鎖定（Double-Checked Locking）寫法為什麼實例變數必須加 `volatile`？不加會有什麼問題？

## 核心答案

物件的建立在 JVM 層面並非單一原子操作，而是可以拆解成「分配記憶體」「初始化物件」「把引用指向記憶體位址」三個步驟，這三步在沒有 `volatile` 的情況下可能被指令重排。如果不加 `volatile`，另一個執行緒可能拿到一個「引用不為 null，但物件尚未初始化完成」的半成品物件。

## 詳細解析

**典型的雙重檢查鎖定寫法**：

```java
public class Singleton {
    private static volatile Singleton instance;
    public static Singleton getInstance() {
        if (instance == null) {
            synchronized (Singleton.class) {
                if (instance == null) {
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

**為什麼要「雙重檢查」**：第一次檢查避免每次呼叫都要進入 `synchronized`；第二次檢查防止多個執行緒都通過第一次檢查後重複建立實例。

**`new Singleton()` 為什麼不是原子操作**：分配記憶體、初始化欄位、引用賦值三步可能被重排——先把引用指向記憶體位址、才真正執行建構子。

**不加 `volatile` 的實際風險**：其他執行緒透過第一次檢查看到「引用不為 null」，直接返回一個「還沒初始化完成」的半成品物件。

**替代方案**：靜態內部類別持有者模式、或用 `enum` 實作單例。

## 面試回答方式

這題最容易的陷阱是只回答「因為要保證可見性」，這只答對了一半。完整的答法必須包含「建構過程可拆解成三步」「哪兩步可能被重排」「重排會導致什麼具體後果」這個完整因果鏈，最好搭配前面提供的程式碼片段逐行講解，讓面試官確認你不是背了一個結論而是真的理解機制。回答完機制之後，主動提一句「還有靜態內部類別持有者模式和 `enum` 這兩種替代方案可以完全避開這個問題」，展現你不只會除錯這個寫法，還知道有更簡潔的設計選擇。

## 常見追問

### 靜態內部類別持有者模式是怎麼利用類別載入機制保證執行緒安全的？

**核心答案**：把單例實例的建立放在一個獨立的靜態內部類別中，利用 JVM 保證「類別初始化過程本身是執行緒安全且只會執行一次」這個特性（類別載入鎖），讓多個執行緒同時第一次存取這個內部類別時，只有一個執行緒真正執行類別的靜態初始化區塊建立實例，其他執行緒會被阻塞直到初始化完成，且因為外部類別載入時不會觸發內部類別載入，天然達到了「延遲初始化」的效果。

**詳細解析**：具體寫法類似：外部類別 `Singleton` 不直接持有實例，而是定義一個 `private static class Holder { static final Singleton INSTANCE = new Singleton(); }``getInstance()` 直接回傳 `Holder.INSTANCE`。因為 Java 類別載入機制規定「一個類別的 `<clinit>`（類別初始化方法）在多執行緒環境下只會被執行一次，且執行期間其他嘗試載入同一個類別的執行緒會被阻塞等待」，這個保證完全由 JVM 規範層級提供，不需要開發者自己寫任何 `synchronized` 或 `volatile`，程式碼更簡潔且不容易出錯；同時因為 `Holder` 是一個獨立的內部類別，只有在第一次呼叫 `getInstance()` 觸發 `Holder` 類別載入時才會建立實例，達到了和雙重檢查鎖定一樣的延遲初始化效果，卻不需要處理指令重排的問題。

**面試回答方式**：講清楚「JVM 保證類別初始化只執行一次且執行緒安全」這個底層規範是這題的核心，並對比「不需要自己寫 `synchronized`/`volatile`，程式碼更簡潔」這個相對 DCL 的優勢，展現你知道為什麼業界更推薦這個寫法。

### 為什麼用 enum 實作單例能天然防止反序列化、反射（Reflection）攻擊破壞單例？

**核心答案**：因為 `enum` 常數的建立、反序列化行為都由 JVM 規範層級直接保證只會有一個實例——JVM 明確禁止透過反射呼叫 `enum` 的建構子建立額外實例（會直接拋出例外），且 `enum` 的反序列化機制是透過名稱查找既有的常數實例，而不是像一般物件那樣重新呼叫建構子建立新物件。

**詳細解析**：傳統的單例實作（不管是餓漢式、懶漢式還是雙重檢查鎖定）都只保證了「透過正常的 `getInstance()` 呼叫路徑」不會建立多個實例，但如果程式碼支援序列化（實作 `Serializable`），一個看似正確的單例在反序列化時預設會呼叫建構子重新建立一個新物件，導致實際上出現了兩個不同的實例，除非額外實作 `readResolve()` 方法手動返回既有實例；同樣地，透過 Java 反射 API 直接呼叫私有建構子（`Constructor.setAccessible(true)`）也能繞過 `private` 建構子的保護，強行建立額外的實例。`enum` 則完全避開了這兩個攻擊面：JVM 規範明確規定不允許反射建立 `enum` 實例（`Constructor.newInstance()` 呼叫 `enum` 建構子會直接拋出 `IllegalArgumentException`）反序列化 `enum` 也是透過 `Enum.valueOf()` 按名稱查找既有常數而非重新建構，這兩個保證都是 JVM 規範層級提供的，不需要開發者額外撰寫任何防禦程式碼。

**面試回答方式**：分別針對「反序列化」和「反射」兩個攻擊面說明傳統單例寫法各自的漏洞，再說明 `enum` 如何從 JVM 規範層級同時堵住這兩個漏洞，這種「先講問題、再講解法怎麼對症下藥」的結構，比只說「`enum` 比較安全」更有說服力，也展現你真正理解單例模式在實務中容易被破壞的具體方式。

### 如果單例類別本身很重，餓漢式和懶漢式該怎麼取捨？

**核心答案**：如果這個單例幾乎一定會被用到（不用白不用），或者建立成本雖高但可以接受在應用程式啟動時就付出這個成本，用餓漢式（類別載入時就直接建立）更簡單且天然執行緒安全；如果這個單例只在特定條件下才會被用到、且建立成本高到值得延遲到真正需要時才付出，才需要考慮懶漢式（雙重檢查鎖定或靜態內部類別持有者模式）換取啟動效能與資源節省。

**詳細解析**：餓漢式（例如 `private static final Singleton INSTANCE = new Singleton();`）的優勢是實作極其簡單、天然執行緒安全（因為靜態欄位的初始化本身由 JVM 保證安全），代價是不管這個單例最終會不會被用到，都會在類別載入時就付出建立成本，如果這個物件建構很重（例如需要載入大量設定、建立連線池（Connection Pool）等），且應用程式中某些啟動路徑根本不會用到它，就等於浪費了啟動時間與記憶體；懶漢式的優勢是真正做到「按需建立」，只有第一次呼叫 `getInstance()` 時才付出建立成本，適合建立成本高、且不確定是否一定會被使用的場景，代價是實作複雜度較高（需要正確處理執行緒安全，如前面討論的 DCL 或持有者模式）。實務上，多數應用中的單例建立成本並不高，餓漢式的簡單性往往勝過懶漢式的延遲優化，只有在明確有效能或啟動時間考量時才值得選擇懶漢式。

**面試回答方式**：不要直接說「懶漢式比較好因為節省資源」，而要點出「這是一個權衡，取決於這個單例的建立成本、以及是否一定會被使用」，並給出具體的判斷準則（建立成本高且不確定會被用到才選懶漢式），這種強調「權衡而非絕對優劣」的答法，更符合資深工程師實際做技術決策時的思考方式。
