# 題目

除了死鎖，還有哪些「活躍性」問題？活鎖與死鎖差在哪？

## 核心答案

活躍性（liveness）問題是指**程式無法繼續向前推進**，有三種形態。

**死鎖**——執行緒互相等待對方持有的資源，全部永久阻塞。特徵是所有相關執行緒都處於等待狀態，CPU 使用率為零，執行緒轉儲上一眼看得出來。

**活鎖**——執行緒沒有被阻塞，**一直在執行卻沒有進展**。經典比喻是兩個人在走廊上相遇，都往同一邊讓，於是再次擋住，重複下去。技術上的典型成因是「偵測到衝突就重試，而所有人的重試策略完全相同」——重試又撞在一起，無限循環。特徵是 **CPU 使用率很高但業務指標不動**，比死鎖難查得多。

**飢餓**——某些執行緒長期拿不到需要的資源。成因包括優先權設定不當、非公平鎖下的持續插隊、以及某個執行緒長期佔用資源不放。

活鎖的解法是**引入隨機性**：重試前等待一個隨機的時間（隨機退避），打破對稱性。這與網路的 CSMA/CD、以及分散式系統的重試退避是同一個思路。

## 詳細解析

死鎖與活鎖的診斷方式完全不同。死鎖用 `jstack` 就能直接看到「Found one Java-level deadlock」，JVM 會自動偵測監視器鎖形成的環（但**偵測不到 `ReentrantLock` 之外的邏輯死鎖**，例如兩個執行緒互相等對方的 `CountDownLatch`）。活鎖沒有任何自動偵測——它看起來就像系統很忙，只能靠**業務指標**發現：吞吐為零、佇列不動、日誌顯示同樣的重試訊息反覆出現。「CPU 高但沒有產出」是活鎖最可靠的訊號。

飢餓在非公平鎖下是設計取捨的結果。`ReentrantLock` 預設非公平，因為公平鎖的吞吐明顯較低——公平模式下每次釋放鎖都必須喚醒佇列頭的執行緒（一次上下文切換），而非公平模式允許正在執行的執行緒直接搶到（免去切換）。代價是佇列尾端的執行緒可能等很久。實務上這通常可以接受，因為多數場景在乎的是總吞吐而非個別請求的最壞延遲；但如果系統有尾延遲的服務品質目標（例如 P99 必須小於 200 毫秒），公平鎖或有逾時的取鎖才是對的選擇。

執行緒優先權在 Java 裡幾乎不可靠：`Thread.setPriority` 只是給作業系統的**提示**，不同平台的映射差異很大（Linux 上預設甚至完全忽略）。用優先權解決飢餓是錯誤的方向——正確的做法是用明確的機制：公平鎖、有界佇列加優先權佇列、或者把不同重要性的工作分到不同的執行緒池。

這三個問題有一個共同的預防原則：**縮短並簡化臨界區**。臨界區越短，持有鎖的時間越短，死鎖的窗口越小、飢餓的等待越短、衝突的機率也越低。而在鎖內呼叫外部程式碼（回呼、遠端呼叫、其他元件的方法）是最危險的模式——你無法知道那段程式碼會不會取得別的鎖、會不會阻塞很久。「不要在持有鎖時呼叫不受控的程式碼」是最有效的一條併發紀律。

## 面試回答方式

先給三種形態的定義與**最容易區分的特徵**：死鎖是「全部阻塞、CPU 為零」，活鎖是「一直在跑卻沒有進展、CPU 高但業務指標不動」，飢餓是「某些執行緒長期拿不到資源」。用走廊互相讓路的比喻解釋活鎖，並給出技術上的典型成因——**所有人的重試策略完全相同**。解法給明確：**隨機退避打破對稱性**，並連到網路的 CSMA/CD 與分散式重試。加分點有三個：死鎖可以被 `jstack` 自動偵測，活鎖完全不能，只能靠業務指標；非公平鎖是吞吐與尾延遲的取捨，有 P99 目標時該用公平鎖或有逾時的取鎖；以及 `Thread.setPriority` 在 Java 裡不可靠，不該用來解決飢餓。收在最有效的一條紀律：不要在持有鎖時呼叫不受控的程式碼。

## 講稿

活躍性問題是指程式無法繼續往前推進，有三種形態。

死鎖是執行緒互相等待對方持有的資源，全部永久阻塞。特徵是所有相關執行緒都在等待，CPU 使用率是零，執行緒轉儲上一眼看得出來。

活鎖是執行緒沒有被阻塞，一直在執行卻沒有進展。經典的比喻是兩個人在走廊上相遇，都往同一邊讓，於是再次擋住。技術上的典型成因是偵測到衝突就重試，而所有人的重試策略完全相同，重試又撞在一起。特徵是 CPU 很高但業務指標不動，比死鎖難查多了。

飢餓是某些執行緒長期拿不到需要的資源，成因包括非公平鎖下的持續插隊。

活鎖的解法是引入隨機性，重試前等一個隨機的時間打破對稱性。這跟網路協定的退避、分散式系統的重試退避是同一個思路。

最後我想說一條最有效的紀律，不要在持有鎖的時候呼叫不受控的程式碼。因為你無法知道那段程式碼會不會取得別的鎖、會不會阻塞很久。這一條同時降低了三種問題的風險。

## 常見追問

### JVM 能自動偵測哪些死鎖，不能偵測哪些？

**核心答案**：能偵測的是基於監視器鎖（`synchronized`）與 `java.util.concurrent.locks` 中可擁有同步器的環形等待——`jstack` 與 `ThreadMXBean.findDeadlockedThreads()` 會走訪「誰持有哪把鎖、誰在等哪把鎖」的關係圖找環。不能偵測的是所有不透過這些機制表達的等待：互相等對方的 `CountDownLatch`、互相等對方訊息的兩個佇列、資料庫層的鎖等待、以及跨行程或跨服務的循環依賴。

**詳細解析**：這些「偵測不到的死鎖」在真實系統裡反而更常見，尤其是**執行緒池的耗盡型死鎖**：池裡的任務提交了子任務到同一個池並等待結果，當所有執行緒都在等自己的子任務時，就沒有執行緒去執行那些子任務——這是一個完美的死鎖，但 JVM 看不到任何鎖，執行緒轉儲上只顯示大家都在 `Future.get()` 上等待。預防方式是「不要在池化任務中等待同一個池的其他任務」，需要分層時就用不同的池。這個問題在 `CompletableFuture` 混用 `commonPool` 與阻塞操作時特別容易發生。

**面試回答方式**：先精確劃出能與不能的界線（基於監視器與 AQS 可擁有同步器的環 vs 其他所有等待）。重點放在**執行緒池耗盡型死鎖**這個 JVM 看不到但實務常見的形態：任務等待同池的子任務，所有執行緒都在 `Future.get()` 上等。給出預防原則——不要在池化任務中等待同一個池的其他任務，需要分層就用不同的池。

### 公平鎖真的能保證公平嗎？

**核心答案**：`ReentrantLock` 的公平模式保證的是 **FIFO 的取鎖順序**——等待最久的執行緒先拿到鎖。但它**不保證執行緒的排程公平**：拿到鎖之後多久真正跑起來，取決於作業系統的排程器。所以它消除的是「鎖層面的插隊」，不是「端到端的延遲公平」。

**詳細解析**：而且公平的代價是可觀的吞吐損失——通常是數倍。原因是每次釋放鎖都必須喚醒佇列頭的執行緒並等它被排程上來，這段時間鎖是空閒的（沒有人在用）；非公平模式下，正在執行的執行緒可以直接拿走，**完全省掉一次上下文切換**，鎖的利用率高得多。所以正確的判斷是：公平鎖不是「更好」的鎖，而是「用吞吐換最壞延遲」的選擇。什麼時候值得？當臨界區很長（切換成本相對變小）、或者系統有明確的尾延遲目標、或者飢餓已經被觀測到。其餘情況預設用非公平是對的，這也是 JDK 選擇非公平作為預設值的理由。

**面試回答方式**：先精確界定公平的範圍——保證 FIFO 取鎖順序，不保證端到端延遲公平（排程仍由作業系統決定）。然後給代價與機制：公平模式下每次釋放都要喚醒並等待排程，這段時間鎖是空閒的，非公平則省掉一次上下文切換。收在判斷：公平鎖不是更好的鎖，是用吞吐換最壞延遲，只在臨界區長、有尾延遲目標、或已觀測到飢餓時才值得。

### 怎麼設計一個不會活鎖的重試機制？

**核心答案**：四個要素。**隨機化**——退避時間加上隨機抖動（jitter），打破多個重試者的同步性。**指數退避**——每次失敗後等待時間倍增，讓爭用自然降低。**上限**——退避時間有上界（避免等到天荒地老），重試次數也有上界（避免無限重試）。**區分可重試與不可重試**——業務錯誤重試多少次都一樣，只重試暫時性錯誤。

**詳細解析**：**抖動的形式比想像中重要**。純粹的指數退避在多個客戶端同時失敗時，它們的重試時間仍然同步（都是 1、2、4、8 秒），於是一起重試、一起失敗——這就是「重試風暴」。加上抖動之後才真正分散開。AWS 的經典建議是「**完全抖動**」：等待時間是 `random(0, min(cap, base * 2^n))`，而不是在固定值上下加減一點。另外要考慮**重試的整體預算**：分散式系統中每一層都重試三次，三層就是二十七倍的放大，足以把已經過載的下游徹底打垮。成熟的做法是給整條呼叫鏈一個共享的重試預算或截止時間，而不是每層各自決定。

**面試回答方式**：給四個要素（隨機化、指數退避、上限、區分錯誤類型）。重點展開**抖動的形式**——純指數退避在多客戶端下仍然同步、造成重試風暴，並給出「完全抖動」的具體公式。真正的加分點是**重試放大**：每層重試三次、三層就是二十七倍，足以打垮已過載的下游；成熟做法是給整條鏈一個共享的重試預算或截止時間，而不是每層各自決定。
