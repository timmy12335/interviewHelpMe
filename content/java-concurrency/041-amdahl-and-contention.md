# 題目

為什麼加了執行緒卻沒有更快？怎麼判斷一個系統的擴展性上限？

## 核心答案

**Amdahl 定律**給出了上限：如果程式中有比例 S 的部分必須序列執行，那麼無論用多少個處理器，加速比都不會超過 **1/S**。5% 的序列部分意味著上限是 20 倍——**即使有一千個核心**。這解釋了為什麼「加執行緒沒有更快」通常不是執行緒不夠，而是**序列部分佔比太高**。

更接近現實的是 **USL（通用擴展性定律）**，它在 Amdahl 之上多加一項**一致性成本**（執行緒之間協調的開銷，隨執行緒數的平方成長）。這一項讓曲線不只是趨於平緩，而是**過了某個點之後開始下降**——這正是實務中「加執行緒反而更慢」的模型解釋。

實務上該做的是**找出序列部分**：獨佔的鎖、單一的連線池、共享的計數器、下游的單點、以及看不見的協調（快取行爭用、GC 的 STW）。**優化的重點永遠是縮小 S，而不是增加處理器數**——把 5% 降到 1%，上限就從 20 倍變成 100 倍。

## 詳細解析

**「序列部分」比想像中多**，而且很多不在程式碼裡明顯可見。**GC 的停頓**是全域序列的（即使是併發收集器也有 STW 階段）。**單一的資料庫連線池**讓所有查詢在池的容量上序列化。**日誌的同步 appender** 讓所有執行緒在一個檔案鎖上排隊。**共享的計數器與統計**（監控指標本身）在高併發下是真實的爭用點。**JIT 的去最佳化與重新編譯**也會造成短暫的全域影響。列舉這些比只講鎖更能顯示實務理解。

**USL 的第二項為什麼是平方**：N 個執行緒之間兩兩協調的次數是 N(N-1)/2，隨 N 平方成長。快取一致性協定的訊息、鎖的喚醒與排隊、以及跨核的資料搬移都屬於這一項。**這解釋了為什麼把執行緒數設成核心數的十倍通常更慢**——多出來的執行緒不但沒有更多 CPU 可用，還增加了上下文切換與快取汙染。

**量測擴展性的正確方法是畫曲線而不是量單點**：固定總工作量，用 1、2、4、8、16 個執行緒各跑一次，畫出「執行緒數對吞吐」的曲線。**曲線的形狀直接告訴你問題所在**——線性上升代表還沒到瓶頸；提早趨平代表序列部分佔比高；**上升後下降代表協調成本已經超過並行收益**。單獨量一個執行緒數的結果無法區分這三種情況。

**最有效的最佳化往往不是併發技巧，而是減少工作量**。把 O(n²) 改成 O(n log n)、加一層快取避免重複計算、批次化減少往返次數——這些直接縮小了總工作量，收益不受 Amdahl 限制。**先窮盡「做得更少」的可能，再考慮「做得更平行」**，這個順序在實務上幾乎總是對的。

## 面試回答方式

先給 **Amdahl 定律**的結論並用具體數字說明——**5% 的序列部分讓上限停在 20 倍，即使有一千個核心**。接著引入 **USL 的一致性成本項**，說明它隨執行緒數平方成長（N 個執行緒兩兩協調是 N² 級），所以曲線**過了某點會下降**，這正是「加執行緒反而更慢」的模型解釋。然後把重點放在**找出序列部分**，並列舉那些不在程式碼裡明顯可見的：GC 停頓、單一連線池、同步日誌 appender、監控指標本身的爭用。給出量測方法——**畫「執行緒數對吞吐」的曲線而不是量單點**，曲線形狀直接區分三種情況（還沒到瓶頸、序列佔比高、協調成本超過收益）。收在最有價值的一句：**先窮盡「做得更少」再考慮「做得更平行」**，改演算法與加快取的收益不受 Amdahl 限制。

## 講稿

Amdahl 定律給出了上限。如果程式中有百分之五的部分必須序列執行，那不管用多少處理器，加速比都不會超過二十倍。就算有一千個核心也一樣。所以加了執行緒沒有更快，通常不是執行緒不夠，是序列部分佔比太高。

更接近現實的是通用擴展性定律，它多加了一項協調成本，隨執行緒數的平方成長。因為 N 個執行緒兩兩協調的次數就是 N 的平方級。這一項讓曲線不只是趨於平緩，而是過了某個點之後開始下降。這就是加執行緒反而更慢的模型解釋。

實務上我會去找序列部分，而且很多不在程式碼裡明顯可見。GC 的停頓是全域序列的。單一的資料庫連線池讓所有查詢在池的容量上序列化。同步的日誌 appender 讓所有執行緒在一個檔案鎖上排隊。連監控指標本身在高併發下都是真實的爭用點。

量測我會畫曲線而不是量單點。固定總工作量，用一、二、四、八、十六個執行緒各跑一次。曲線形狀直接告訴你問題在哪。

最後一句我覺得最重要。先窮盡做得更少的可能，再考慮做得更平行。改演算法跟加快取的收益不受這條定律限制。

## 常見追問

### 怎麼在生產環境找出序列瓶頸？

**核心答案**：三種互補的手段。**非同步剖析器**（async-profiler）的 lock 與 wall-clock 模式——前者直接顯示鎖等待時間的分布並指出是哪一把鎖，後者包含阻塞時間（一般的 CPU 剖析看不到等待）。**執行緒轉儲的取樣**——連續抓幾十次 `jstack`，統計執行緒最常停在哪個堆疊位置，這是最低成本的做法。**分散式追蹤的 span 分析**——看單一請求中各階段的耗時，找出「等待時間遠大於執行時間」的環節。

**詳細解析**：關鍵是**要看等待而不只是 CPU**。傳統的 CPU 剖析器只採樣正在執行的執行緒，而序列瓶頸的特徵恰恰是**大家都在等**——那些執行緒在 CPU 剖析裡完全不出現。這是為什麼很多人「剖析了半天看不出問題」：工具看的維度不對。**wall-clock 模式或 lock 模式才是對的工具。** 另外一個實用的信號是**利用率與飽和度的背離**：CPU 只有 30% 但延遲很高、佇列很深，這幾乎必然意味著存在某個非 CPU 的序列點（鎖、連線池、下游）。**這個「低利用率加高延遲」的組合是診斷序列瓶頸最可靠的宏觀訊號。**

**面試回答方式**：給三種手段並說明各自看到什麼。核心洞見放在中間：**要看等待而不只是 CPU**——序列瓶頸的特徵是大家都在等，那些執行緒在 CPU 剖析裡根本不出現，所以要用 wall-clock 或 lock 模式。加分點是給出宏觀訊號：**CPU 低但延遲高、佇列深**，這個組合幾乎必然意味著存在非 CPU 的序列點。

### 為什麼有時候減少執行緒數反而變快？

**核心答案**：因為越過了 USL 曲線的頂點。過多的執行緒帶來四種成本：**上下文切換**（每次切換要保存與恢復暫存器、還會刷掉 TLB 的部分條目）、**快取汙染**（每個執行緒有自己的工作集，太多執行緒讓 L1/L2 快取不斷被替換，命中率崩潰）、**鎖爭用加劇**（等待佇列變長、喚醒的執行緒可能又立刻被搶走鎖）、**記憶體壓力**（每個平台執行緒的堆疊預設 1 MB，一千個執行緒就是 1 GB 的虛擬位址）。

**詳細解析**：**快取汙染常常是最大但最不明顯的那一項**。一個執行緒的工作集如果是 256 KB，而 L2 只有 1 MB，那麼超過四個執行緒同時活躍就會開始互相踢出對方的資料，記憶體存取從幾個週期變成幾百個週期。**這在剖析工具上表現為「同樣的程式碼變慢了」，看不出任何原因**，要靠硬體效能計數器的快取失效率才能確認。實務上的推論是：**CPU 密集任務的執行緒數不該遠超核心數**，即使有幾個執行緒偶爾阻塞。虛擬執行緒改變了 IO 密集場景的計算，但**對 CPU 密集任務完全沒有幫助**——它的載體執行緒數仍然是核心數，而且虛擬執行緒之間的切換同樣會汙染快取。

**面試回答方式**：給四種成本，並特別展開**快取汙染**——它最大但最不明顯，工作集超過 L2 容量後記憶體存取從幾個週期變成幾百個，剖析工具上只表現為「莫名變慢」。給出推論：CPU 密集任務的執行緒數不該遠超核心數。加分點是澄清**虛擬執行緒對 CPU 密集任務沒有幫助**——載體執行緒數仍是核心數，切換同樣汙染快取。

### 微服務架構下 Amdahl 定律怎麼應用？

**核心答案**：把「序列部分」理解成**呼叫鏈上必須依序完成的環節**。一個請求要依序呼叫五個服務時，總延遲是五者之和，**其中最慢的那個決定了優化的天花板**——把其他四個都優化到零，總延遲也降不到最慢那個之下。所以優化應該從**關鍵路徑上最慢的環節**開始，而不是從最容易改的開始。

**詳細解析**：更有價值的應用是**把序列變成並行**：如果五個呼叫中有三個彼此不依賴，就應該並行發出（`CompletableFuture.allOf` 或結構化併發），總延遲從「三者之和」變成「三者之最大值」。**這是微服務中收益最大的單一優化**，而且不需要改動任何下游服務。要注意兩件事：並行呼叫會**同時增加下游的瞬時壓力**（原本錯開的請求變成同時到達），以及**錯誤處理變複雜**（其中一個失敗時，其他的要不要取消、部分結果能不能用）。結構化併發正是為了讓後者變得可控——它保證所有子任務在作用域結束前都完成或被取消，不會有洩漏的呼叫。

**面試回答方式**：先把「序列部分」對應到呼叫鏈上的依序環節，並給出關鍵推論——**最慢的環節決定優化天花板**，所以要從關鍵路徑最慢處而非最容易處開始。重點放在最有價值的應用：**把不相依的呼叫並行化**，延遲從「和」變成「最大值」，且不需改動下游。誠實補上兩個代價：下游瞬時壓力上升、錯誤處理變複雜，並指出結構化併發正是為了讓後者可控。
