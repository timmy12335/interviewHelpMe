# 題目

`Exchanger` 與 `Phaser` 各解決什麼問題？`Phaser` 比 `CyclicBarrier` 好在哪？

## 核心答案

`Exchanger` 是兩個執行緒之間的資料交換點：雙方各自呼叫 `exchange(item)`，先到的阻塞等待，配對成功後**同時拿到對方的物件**。典型場景是雙緩衝——生產者填滿緩衝 A 的同時消費者處理緩衝 B，兩邊都做完就交換，**省掉每筆資料的配置與複製**。它本質上是一個雙向的 `SynchronousQueue`。

`Phaser` 是 `CyclicBarrier` 與 `CountDownLatch` 的通用化，三個關鍵改進：**參與者數量可以動態增減**（`register`／`arriveAndDeregister`），而 `CyclicBarrier` 的數量在建構時就固定了；**支援多階段**並且每個階段有編號，可以問「現在是第幾階段」；**支援非阻塞的到達**（`arrive()` 到達但不等待，`arriveAndAwaitAdvance()` 才等待），讓執行緒可以先做別的事。

選擇上：固定數量、單純的柵欄用 `CyclicBarrier`（更簡單）；參與者會動態變化、或需要多階段協調時才用 `Phaser`。

## 詳細解析

`Phaser` 的動態註冊解決了一個真實問題：分治演算法中，任務執行到一半可能產生新的子任務，`CyclicBarrier` 的固定參與者數在這裡完全不適用——建構時根本不知道最終會有幾個。`Phaser` 讓新任務 `register()` 加入、完成的任務 `arriveAndDeregister()` 離開，**參與者集合隨計算過程演化**。

**`onAdvance` 是它的擴充點**：每個階段結束時被呼叫，回傳 true 表示終止 phaser。這相當於 `CyclicBarrier` 的 barrier action，但多了階段編號與當前參與者數兩個參數，可以實作「跑滿 N 輪就停」或「所有參與者都離開就終止」的邏輯。預設實作就是「參與者數為零時終止」，這讓分治任務自然收斂。

**它還支援樹狀階層**：一個 `Phaser` 可以有父 phaser，子 phaser 的參與者對父而言只算一個。這是為了**降低爭用**——參與者數量很大時（幾百個執行緒），所有人在同一個計數器上 CAS 會嚴重爭用，分成多層之後每層的爭用大幅下降。這與 `LongAdder` 的分格思路是同一個道理：把單點爭用改成分散再匯總。

這兩個工具的實際使用頻率都很低，該誠實承認。`Exchanger` 的場景（雙緩衝）在現代 Java 裡常被 `BlockingQueue` 加物件池取代；`Phaser` 的能力在多數應用中用 `CompletableFuture` 的組合或 `CountDownLatch` 就夠了。它們的價值更多在於「知道 JDK 提供了什麼」——遇到真的需要動態參與者或多階段協調時，不必自己用 wait/notify 手寫一個容易出錯的版本。 面試中能說清楚它們解決什麼問題、以及為什麼多數場景用不到，比背出所有方法有用。

## 面試回答方式

先各給一句定位：`Exchanger` 是**兩執行緒的雙向交換點**（本質是雙向的 `SynchronousQueue`），典型用途是雙緩衝以省掉配置與複製；`Phaser` 是 `CyclicBarrier` 與 `CountDownLatch` 的通用化。接著給 `Phaser` 的**三個關鍵改進**（動態參與者、多階段且有編號、非阻塞到達），並用分治演算法執行中產生新子任務這個具體場景說明為什麼固定參與者數不夠用。加分點是**樹狀階層降低爭用**，並把它連到 `LongAdder` 的分格思路——單點爭用改成分散再匯總。最後誠實說明兩者的實際使用頻率都低，多數場景用 `CompletableFuture` 或 `CountDownLatch` 就夠，它們的價值在於需要時不必自己手寫容易出錯的版本。

## 講稿

Exchanger 是兩個執行緒之間的資料交換點。雙方各自呼叫交換方法，先到的等待，配對成功之後同時拿到對方的物件。典型場景是雙緩衝，生產者填滿一個緩衝的同時消費者處理另一個，兩邊做完就交換，省掉每筆資料的配置跟複製。

Phaser 是 CyclicBarrier 跟 CountDownLatch 的通用化，有三個關鍵改進。參與者數量可以動態增減、支援多階段而且每個階段有編號、還有支援非阻塞的到達，執行緒可以先去做別的事。

動態註冊解決一個真實問題。分治演算法執行到一半可能產生新的子任務，固定參與者數在這裡完全不適用，因為建構的時候根本不知道最終會有幾個。

它還支援樹狀階層，子 phaser 的參與者對父而言只算一個。這是為了降低爭用，幾百個執行緒在同一個計數器上 CAS 會很嚴重。這跟 LongAdder 的分格是同一個思路。

不過我要誠實說，這兩個工具實際使用頻率都很低。多數場景用 CompletableFuture 或 CountDownLatch 就夠了。它們的價值在於真的需要的時候，不必自己手寫一個容易出錯的版本。

## 常見追問

### CountDownLatch 與 CyclicBarrier 到底差在哪？

**核心答案**：三個差異。**可重複性**——`CountDownLatch` 是一次性的，計數歸零後無法重置；`CyclicBarrier` 到達後自動重置，可以循環使用。**等待的對象**——`CountDownLatch` 是「一或多個執行緒等待另一組執行緒完成某些事」，等待者與倒數者是不同的角色；`CyclicBarrier` 是「**一組執行緒互相等待**」，每個參與者既是等待者也是到達者。**中斷語意**——`CyclicBarrier` 的任一參與者被中斷或逾時，會讓**所有其他參與者**拋出 `BrokenBarrierException`，因為柵欄已經無法達成。

**詳細解析**：最後一點常被忽略但很重要——**柵欄是全有或全無的**。這在實務上意味著使用 `CyclicBarrier` 時必須處理 `BrokenBarrierException`，而且要決定柵欄破損後的復原策略（`reset()` 重置，或整批放棄）。相比之下 `CountDownLatch` 沒有這個問題，倒數者失敗就是永遠不歸零，等待者會一直等——**所以 `await` 一定要用有逾時的版本**，否則失敗會表現成永久掛起而不是錯誤。這兩個「失敗模式」的差異，比功能差異更值得記住。

**面試回答方式**：給三個差異（可重複性、等待對象的角色、中斷語意）。重點放在第三個——**柵欄是全有或全無的**，任一參與者破壞會讓所有人拋例外，所以必須決定復原策略。然後對照 `CountDownLatch` 的失敗模式：倒數者失敗會讓等待者永久掛起，所以 `await` 一定要用有逾時的版本。收在一句：兩者的失敗模式差異比功能差異更值得記住。

### Exchanger 的實作為什麼比想像中複雜？

**核心答案**：因為它為了效能做了**多層槽位（slot）與退讓策略**。最簡單的實作是一個共享的交換點加鎖，但那在多對執行緒同時交換時會嚴重爭用。JDK 的實作用了一個**槽位陣列**，執行緒依雜湊落到不同槽位，只有同槽位的兩個執行緒才配對——這把爭用分散開了，代價是可能找不到配對而需要換槽重試。它還混用了**自旋、退讓與阻塞**三段策略：先自旋短暫等待（配對常常很快到來）、再 `Thread.yield`、最後才真正掛起。

**詳細解析**：這個「**分散槽位加分段等待**」的組合在 JDK 的併發工具裡反覆出現——`ConcurrentHashMap` 的分桶、`LongAdder` 的分格、`ForkJoinPool` 的每執行緒工作佇列，都是同一種「把單點爭用變成多點」的思路；而「先自旋再阻塞」則出現在 `AbstractQueuedSynchronizer`、偏向鎖與輕量級鎖的升級路徑上。理解這兩個模式，比記住任何單一工具的 API 都有價值，因為自己設計高併發元件時會不斷用到：爭用點要分散、等待要分段（短等待自旋比掛起便宜，長等待掛起比自旋便宜）。

**面試回答方式**：給出兩個機制（分散槽位、自旋到阻塞的分段等待）與各自的理由。真正的價值在後半段——把它們歸納成**兩個反覆出現的通用模式**：「把單點爭用變成多點」（分桶、分格、每執行緒佇列）與「等待分段」（短等待自旋、長等待掛起），並指出理解這兩個模式比記住任何單一 API 都有用。

### 這些同步器都基於 AQS 嗎？

**核心答案**：不完全是。`CountDownLatch`、`Semaphore`、`ReentrantLock`、`ReentrantReadWriteLock` 都用 AQS 的共享或獨佔模式實作。但 **`CyclicBarrier` 是用 `ReentrantLock` 加 `Condition` 實作的**（間接用到 AQS），**`Phaser` 與 `Exchanger` 則完全沒有用 AQS**——它們自己維護狀態並用 CAS 與 `LockSupport.park`／`unpark` 實作等待。

**詳細解析**：不用 AQS 的原因是它們的狀態模型不符合 AQS 的抽象。AQS 的核心是「一個 int 狀態 + 一個等待佇列 + 嘗試取得／釋放」，適合表達「資源可不可以被取得」。`Phaser` 的狀態要同時編碼階段號、參與者數與已到達數（打包在一個 long 裡），而且需要樹狀階層與動態增減；`Exchanger` 的語意是配對而不是取得資源。**硬套 AQS 反而會更複雜**。這給出一個有用的判斷：AQS 是一個很好的框架，但不是所有同步需求都適合套進它——自己實作同步器時，先確認「取得／釋放」這個抽象是否貼合，不貼合就用 `LockSupport` 直接做。

**面試回答方式**：先給準確的分類（哪些用 AQS、哪些不用），這比籠統說「都基於 AQS」正確。然後解釋原因——它們的狀態模型不符合 AQS「一個 int 狀態加取得釋放」的抽象，`Phaser` 要編碼階段、參與者與到達數還要支援樹狀階層，`Exchanger` 的語意是配對而非取得。收在可遷移的判斷：自己實作同步器時先確認「取得／釋放」的抽象貼不貼合，不貼合就用 `LockSupport` 直接做。
