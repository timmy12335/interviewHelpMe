# 題目

生產者消費者模型解決什麼問題？佇列該有界還是無界，滿了要怎麼處理？

## 核心答案

它解決三件事：**解耦**（生產與消費各自演進、各自調整速率）、**削峰**（突發流量進佇列而不是直接壓垮下游）、**並行化**（多個消費者從同一個佇列取，天然做到工作分配）。

**佇列必須有界**，這是最重要的判斷。無界佇列只是把「拒絕服務」推遲成「記憶體耗盡」——生產快於消費時佇列無限成長，最後 OOM，而且在此之前 GC 壓力上升、延遲惡化，整個服務在崩潰前先變得極慢。有界佇列讓壓力在正確的時間點顯現，也就是背壓。

滿了之後有四種選擇，必須明確決定：**阻塞生產者**（`put`，最自然的背壓，把壓力往上游傳）、**丟棄新任務**（`offer` 回傳 false，適合可丟的資料如監控指標）、**丟棄最舊的**（適合只關心最新狀態的場景）、**降級處理**（例如 `CallerRunsPolicy`，讓提交者自己執行，等於自動減速）。**沒有第五種選擇叫「不會滿」。**

## 詳細解析

**`BlockingQueue` 是標準實作**，關鍵是選對實作與方法。`ArrayBlockingQueue` 是有界的環形陣列，單一鎖保護；`LinkedBlockingQueue` 用兩把鎖（put 與 take 各一）所以並行度更好，但它的建構子不傳容量就是無界的——這正是 `Executors.newFixedThreadPool` 的隱患來源。`SynchronousQueue` 沒有容量，put 必須等到有人 take，適合「直接交手」的場景。方法要選對：**`put`／`take` 阻塞、`offer`／`poll` 立即回傳、`offer(e, timeout)`／`poll(timeout)` 限時等待**——用錯會讓背壓策略完全失效。

容量該設多少是一個容量規劃問題：佇列的作用是吸收**短暫**的突發，而不是長期的速率差。合理的估算是「可容忍的最大延遲 ÷ 單筆處理時間」——如果單筆處理 10 毫秒、可接受 2 秒延遲，佇列深度就是 200。設得比這個大只會讓排隊中的請求在完成前就已經逾時，浪費資源處理沒人要的結果。這也是為什麼「加大佇列」通常不是解決過載的正確方法。

**多消費者時要注意順序**：多個消費者從同一個佇列取，**全域順序就沒了**。需要「同一個實體的訊息依序處理」時，做法是**依鍵分片**——用實體 ID 雜湊到 N 個佇列，每個佇列一個消費者，這樣同鍵有序、不同鍵並行。這正是 Kafka 分區的設計，也是任何需要有序並行處理的通用解法。

優雅關閉需要毒丸或明確的訊號：消費者阻塞在 `take()` 上時，中斷是一種方式；另一種是放入約定的**毒丸物件**（poison pill）讓消費者看到就退出。毒丸的好處是保證佇列裡先前的任務都被處理完（它排在後面），中斷則會立刻放棄。有 N 個消費者就要放 N 顆毒丸，或者用一個消費者收到後負責再放一顆的接力方式。

## 面試回答方式

先給它解決的三件事（解耦、削峰、並行化），再把重點放在最關鍵的判斷——**佇列必須有界**，並給出理由：無界只是把拒絕服務推遲成記憶體耗盡，而且崩潰前服務會先因為 GC 壓力而變得極慢。接著列出滿了之後的**四種選擇**（阻塞、丟新、丟舊、降級），並強調**沒有第五種叫「不會滿」**。加分點有三個：**`LinkedBlockingQueue` 不傳容量就是無界**，這正是 `newFixedThreadPool` 的隱患；容量該用「可容忍延遲 ÷ 單筆處理時間」估算，設太大只會讓請求在完成前就逾時；以及多消費者會失去順序，需要有序就依鍵分片（Kafka 分區的思路）。最後補優雅關閉用毒丸能保證先前任務跑完。

## 講稿

這個模型解決三件事。解耦，讓生產跟消費各自演進。削峰，突發流量進佇列而不是直接壓垮下游。還有並行化，多個消費者從同一個佇列取，天然做到工作分配。

最重要的判斷是佇列必須有界。無界佇列只是把拒絕服務推遲成記憶體耗盡。生產快於消費的時候佇列無限成長，最後 OOM，而且在那之前 GC 壓力上升、延遲惡化，服務在崩潰前先變得極慢。有界佇列讓壓力在正確的時間點顯現，這就是背壓。

滿了之後有四種選擇，必須明確決定。阻塞生產者，這是最自然的背壓。丟棄新任務，適合監控指標這種可丟的資料。丟棄最舊的，適合只關心最新狀態。或是降級，讓提交者自己執行，等於自動減速。沒有第五種選擇叫做不會滿。

容量該設多少我會這樣估。可容忍的最大延遲除以單筆處理時間。設得比這個大，只會讓排隊中的請求在完成前就已經逾時，浪費資源處理沒人要的結果。

## 常見追問

### 為什麼 LinkedBlockingQueue 用兩把鎖會比較快？

**核心答案**：因為入隊與出隊操作的是鏈結串列的兩端，互不干擾。`ArrayBlockingQueue` 用單一鎖保護整個環形陣列，生產者與消費者互相排斥，即使一個在隊頭一個在隊尾。`LinkedBlockingQueue` 為 put 與 take 各設一把鎖（`putLock` 與 `takeLock`），**生產與消費可以真正並行**，在高吞吐場景下差別明顯。

**詳細解析**：代價有三個。**節點配置**——每次入隊都要 `new` 一個節點物件，GC 壓力比預先配置好的陣列大。**兩把鎖的協調成本**——佇列從空變非空或從滿變非滿時，需要跨鎖喚醒對方，這段邏輯（`signalNotEmpty`／`signalNotFull`）比單鎖複雜。元素數量用 `AtomicInteger` 維護，因為兩把鎖都要改它，這本身是一個爭用點。所以在低併發或佇列經常接近空的情況下，`ArrayBlockingQueue` 反而更快（沒有配置、快取區域性好）。選擇的判準是：高吞吐且佇列通常有一定深度用 Linked，低延遲且佇列通常很淺用 Array。

**面試回答方式**：先給核心機制——put 與 take 操作串列兩端、各用一把鎖所以能真正並行。接著誠實給三個代價：節點配置的 GC 壓力、跨鎖喚醒的協調複雜度、以及計數用的 `AtomicInteger` 本身是爭用點。收在具體判準：高吞吐且佇列有深度用 Linked，低延遲且佇列很淺用 Array——這比籠統說「Linked 比較快」準確。

### 什麼是背壓？在 Java 裡怎麼實作？

**核心答案**：背壓（backpressure）是下游把「我處理不過來」的訊號往上游傳遞，讓上游減速的機制。沒有背壓的系統只有兩種結局：緩衝無限成長直到崩潰，或者靜默丟棄資料。Java 裡最直接的實作就是**有界佇列加阻塞式 put**——生產者被阻塞就自然減速，壓力沿著呼叫鏈往上傳到最源頭。

**詳細解析**：更完整的形式是**請求式背壓**（Reactive Streams 的 `request(n)`）：消費者主動告訴生產者「我現在能處理 n 筆」，生產者最多送 n 筆。它比阻塞式更精確，也適合跨網路的場景（阻塞一個遠端的生產者做不到，但可以告訴它別再送）。在單機的執行緒模型裡，阻塞式背壓已經足夠而且簡單得多——這也是虛擬執行緒讓反應式框架的必要性下降的原因之一，阻塞變便宜後，用阻塞表達背壓就沒有成本問題了。要注意背壓必須一路傳到源頭才有效：如果中間某一層用了無界佇列或直接丟棄，訊號就斷了，上游會繼續全速發送。

**面試回答方式**：先定義背壓並指出沒有它只有兩種結局（無限成長或靜默丟棄）。給出 Java 最直接的實作（有界佇列加阻塞 put）並說明壓力如何沿呼叫鏈上傳。加分點是介紹請求式背壓與它的適用場景（跨網路），並指出虛擬執行緒讓阻塞變便宜，因而降低了反應式框架的必要性。最後強調**背壓必須一路傳到源頭**，中間任一層用無界佇列訊號就斷了。

### 消費者處理失敗的訊息該怎麼辦？

**核心答案**：要有明確的策略，而不是「記個日誌然後丟掉」。標準做法是三層：**重試**（區分可重試的暫時性錯誤與不可重試的資料錯誤，只重試前者，並用指數退避避免打垮下游）、**死信佇列**（重試耗盡後把訊息移到專門的佇列，保留原始內容與失敗原因，讓人可以事後檢查與補償）、**告警**（死信佇列的深度應該被監控，因為它代表有一批資料沒有被處理）。

**詳細解析**：關鍵的區分是**可重試與不可重試**。網路逾時、下游暫時不可用是可重試的；資料格式錯誤、業務規則不符合是重試多少次都一樣的。把不可重試的錯誤拿去重試，等於用滿一個佇列的容量去做注定失敗的事，而且會延遲後面所有正常的訊息。實務上這個判斷應該用例外型別表達（`RetryableException` 與 `PermanentException` 兩個基底類別），而不是在 catch 區塊裡判斷字串。另外要注意**重試會破壞順序**：一筆訊息被退回重試時，後面的訊息已經先處理了。需要嚴格順序的場景，失敗時只能停止該分區的消費並告警，這是順序性的實際代價。

**面試回答方式**：給三層策略（重試、死信佇列、告警）並強調死信佇列深度必須被監控。重點放在**可重試與不可重試的區分**——把不可重試的錯誤拿去重試等於浪費容量做注定失敗的事，還延遲後面的正常訊息；並建議用例外型別而非字串判斷來表達這個區分。加分點是指出**重試會破壞順序**，嚴格有序的場景失敗時只能停止該分區並告警。
