# 題目

`wait()`、`notify()`、`notifyAll()` 為什麼必須在 `synchronized` 區塊內呼叫？為什麼 `wait()` 通常要放在 `while` 迴圈而不是 `if` 裡？`Condition` 和它們有什麼關係？

## 核心答案

`wait`/`notify`/`notifyAll` 是 `Object` 類別的方法，操作的是這個物件對應的 Monitor 的等待集合，必須先持有這個物件的鎖才能呼叫，否則拋出 `IllegalMonitorStateException`。`wait()` 要放在 `while` 迴圈判斷條件，是為了防範「虛假喚醒」與「條件在喚醒後被其他執行緒再次改變」的情況。`Condition` 是 `Lock` 體系下的等價物，功能更強，支援一個鎖對應多組獨立的等待佇列。

## 詳細解析

**為什麼必須持鎖才能呼叫**：`wait()` 的語意是「釋放目前持有的鎖，並讓當前執行緒進入這個物件 Monitor 的等待集合中阻塞」；`notify()`/`notifyAll()` 是「從等待集合中喚醒一個/所有執行緒」，這些操作直接涉及 Monitor 內部狀態的變更，必須確保呼叫者當下正持有這把鎖。

**為什麼 `wait()` 要放在 `while` 而不是 `if`**：

```java
synchronized (lock) {
    while (!條件成立) {
        lock.wait();
    }
}
```

原因：虛假喚醒（JVM 規範允許）、`notifyAll()` 喚醒多個執行緒但條件只滿足一次、被喚醒後重新競爭鎖之前條件可能又被改變。

**`Condition` 是什麼**：透過 `lock.newCondition()` 建立，提供 `await()`/`signal()`/`signalAll()`。一個 `Lock` 可以建立多個獨立的 `Condition`，比只有單一等待集合的內建 Monitor 更精細。

## 面試回答方式

這題有三個子問題（為什麼要持鎖、為什麼用 while、Condition 是什麼），建議按這個順序逐一回答，每個子問題給一句核心結論再補細節，避免混在一起講讓邏輯顯得凌亂。「為什麼用 while」這部分是最容易被追問也最能展現細節理解的地方，務必把「虛假喚醒」和「notifyAll 喚醒多個但條件只滿足一次」這兩個原因都講到，只講一個會顯得不夠完整。最後用 `Condition` 帶出「一個鎖可以有多組等待佇列」這個相對內建 Monitor 的優勢收尾，自然銜接到更精細的生產者消費者實作。

## 常見追問

### notify() 和 notifyAll() 該怎麼選？

**核心答案**：大多數情況建議用 `notifyAll()`，除非能明確證明所有在等待集合中的執行緒的等待條件完全相同、喚醒任何一個都是安全的，才考慮用 `notify()` 換取效能（只喚醒一個，減少不必要的競爭）。

**詳細解析**：`notify()` 的風險在於：如果等待集合中有多個執行緒因為不同的原因在等待（例如生產者消費者模式中，既有等待「佇列非空」的消費者，也有等待「佇列非滿」的生產者，兩者共用同一個內建 Monitor 的等待集合），`notify()` 只會隨機喚醒其中一個，如果恰好喚醒了一個「條件其實還沒真正滿足」的執行緒（例如喚醒了一個生產者，但實際上是消費者該被喚醒的情境），這個執行緒被喚醒後透過 `while` 迴圈重新檢查條件會發現不滿足，只能再次進入等待，而真正該被喚醒的執行緒卻可能被遺漏，導致該執行緒永久等待（因為信號被「浪費」在了錯誤的執行緒身上）。用 `notifyAll()` 保守地喚醒所有等待者，讓每個執行緒自己重新檢查條件決定要不要真正繼續，雖然效能上會有更多不必要的喚醒與競爭，但能避免遺漏喚醒的正確性風險。只有在確定所有等待者的等待條件相同（例如都只是在等待同一個簡單的布林旗標）時，用 `notify()` 才是安全且更有效率的選擇。

**面試回答方式**：先給出「預設用 `notifyAll`，除非確定安全才用 `notify`」的明確結論，再用「等待集合中可能有不同等待原因的執行緒，`notify` 可能喚醒錯誤的對象導致遺漏喚醒」這個具體風險說明原因，這種「先講結論、再講為什麼」的結構是回答這類權衡取捨題最有效率的方式。

### 用 Condition 實作一個簡單的生產者消費者佇列的框架大致是什麼樣子？

**核心答案**：用一個 `ReentrantLock` 搭配兩個獨立的 `Condition`——`notFull`（佇列未滿時通知生產者可以繼續放入）與 `notEmpty`（佇列非空時通知消費者可以繼續取出），生產者在佇列滿時 `notFull.await()`，放入元素後呼叫 `notEmpty.signal()`；消費者在佇列空時 `notEmpty.await()`，取出元素後呼叫 `notFull.signal()`。

**詳細解析**：這個結構的核心優勢在於「精準喚醒」——用內建 Monitor 的 `wait`/`notify` 時，生產者和消費者只能共用同一個等待集合，喚醒時無法區分「該喚醒的是生產者還是消費者」，容易發生前一題提到的信號浪費問題；用兩個獨立的 `Condition` 後，生產者放入元素後只需要呼叫 `notEmpty.signal()` 精準喚醒等待消費的執行緒，不會誤喚醒同樣在等待但等待「佇列變不滿」的其他生產者，反之亦然。這正是為什麼標準函式庫的 `ArrayBlockingQueue`、`LinkedBlockingQueue` 底層都是用這種「一把鎖、兩個 Condition」的模式實作，而不是用內建的 `synchronized`/`wait`/`notify`。

**面試回答方式**：口頭描述這個框架時，強調「兩個 Condition 分別對應兩種不同的等待原因，各自精準喚醒」這個設計動機，並主動提到「這正是 JDK 內建阻塞佇列的實作方式」，把抽象的程式碼結構與實際標準函式庫的設計連結起來，展現理論與實務的呼應。

### LockSupport.park()/unpark() 和 wait()/notify() 有什麼本質差異？

**核心答案**：`LockSupport.park()`/`unpark()` 不需要先持有任何鎖就能呼叫，且沒有「先 park 後 unpark 才有效」的順序限制（`unpark()` 可以先於 `park()` 呼叫，並讓後續的 `park()` 直接返回不阻塞，稱為「許可」機制）；`wait()`/`notify()` 必須在持有對應物件鎖的情況下呼叫，且如果 `notify()` 在 `wait()` 之前呼叫，這個喚醒信號會直接遺失，之後的 `wait()` 仍然會照常阻塞。

**詳細解析**：`LockSupport` 的 `park`/`unpark` 是給每個執行緒關聯一個「許可（permit）」概念——`unpark(thread)` 讓目標執行緒獲得一個許可（如果該執行緒還沒有許可的話），`park()` 則是「如果目前有許可就消耗掉並立即返回，否則阻塞直到獲得許可」，這個許可最多只能累積一個（不會因為呼叫多次 `unpark` 就累積多個許可）。因為這個機制不依賴物件鎖，也沒有嚴格的呼叫順序要求（不像 `wait`/`notify` 那樣如果順序反了信號就遺失），`LockSupport` 更適合用來實作底層的同步工具（AQS 內部正是大量使用 `park`/`unpark` 來阻塞和喚醒等待佇列中的執行緒），因為底層框架程式碼往往無法保證呼叫順序，需要更寬容、更不容易出錯的喚醒機制。

**面試回答方式**：用「不需要持鎖」「有許可機制、不怕喚醒信號先到」這兩個關鍵差異點回答，並主動連結到「AQS 內部正是用 `park`/`unpark` 實作」（呼應 [[006-aqs-principle.md]]），展現你理解這是 Java 並行工具底層真正在用的機制，而不只是一個孤立的 API 知識點。
