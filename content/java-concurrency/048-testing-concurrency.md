# 題目

併發 bug 為什麼難以用一般測試發現？有哪些方法能提高發現率？

## 核心答案

難以發現的根本原因是**併發正確性是關於「所有可能的執行交錯」的性質，而測試只能取樣其中極少數**。一段程式碼有一千萬種可能的交錯，其中三種會出錯，跑一萬次測試可能一次都碰不到——**測試通過不能證明沒有競態**。

更糟的是三個放大因素。**執行環境掩蓋問題**——x86 的強記憶體模型讓許多缺少同步的程式碼「碰巧正確」，換到 ARM 才暴露。**測試環境併發度低**——本機四核跑不出生產環境上百並發的交錯。**JIT 改變行為**——測試跑幾百次都在解譯模式，而生產環境的 JIT 會做重排序與最佳化，行為並不相同。

提高發現率的方法有四類：**壓力測試加隨機延遲**（在關鍵位置插入 `Thread.yield` 或隨機 sleep，人為製造交錯）、**jcstress**（JDK 官方工具，窮舉並標記哪些結果違反規範）、**確定性測試**（用 `CountDownLatch` 精確編排執行順序，測試特定的交錯）、**靜態分析**（ErrorProne 的 `@GuardedBy` 檢查、SpotBugs 的併發規則）。

**但最有效的仍然是「減少需要測試的表面積」**——不可變、執行緒封閉、用現成的併發工具。

## 詳細解析

**確定性測試是最被低估的方法**。與其祈禱壓力測試碰到那個交錯，不如**用同步工具精確地製造它**：讓執行緒 A 執行到某個點後停下（`latch.await()`），讓執行緒 B 執行到另一個點，然後同時放行。這能把「檢查後執行」的競態變成一個**穩定重現的測試**。實作上可以用測試專用的鉤子（一個可注入的 `Runnable` 在關鍵位置呼叫），或用位元組碼工具在特定位置插入延遲。**它的價值在於一旦寫出來，這個測試就永遠守住這個 bug**，而壓力測試只是機率性的。

**jcstress 的工作方式值得理解**：它會生成大量的執行緒對、在極端條件下反覆執行一小段程式碼，記錄**所有觀察到的結果組合**，並依據 JMM 規範標記哪些是 `ACCEPTABLE`、哪些是 `FORBIDDEN`。**出現 FORBIDDEN 就是確定的 bug**；但某個可疑結果從未出現，並不代表安全——只代表這台機器這次沒觸發。**它適合測試小段的核心同步邏輯，不適合測整個應用。**

**壓力測試要做對才有意義**。單純把測試跑一萬次收效很低，因為每次的交錯模式相似。有效的做法是：**加入隨機性**（隨機的執行緒數、隨機的延遲、隨機的操作順序）、**在多種硬體上跑**（尤其是 ARM）、**開啟 `-XX:+UseParallelGC` 之類的不同設定製造不同的停頓模式**、以及**跑足夠長的時間**（併發 bug 的觸發常常是低機率事件，跑一分鐘與跑一小時的發現率差很多）。

**CI 上的「偶爾失敗」不該被當成 flaky test 忽略**。併發 bug 在 CI 上的典型表現正是偶發失敗——而常見的處理是加上重試或標記為 flaky，**這等於主動關掉了唯一發現它的管道**。正確的做法是保留失敗的證據（執行緒轉儲、日誌、種子值）並認真調查。**「偶發失敗的測試是併發 bug 最常見的第一個訊號」，這個認識比任何工具都重要。**

## 面試回答方式

先給根本原因——**併發正確性是關於「所有可能執行」的性質，測試只能取樣**，所以測試通過不能證明沒有競態。接著給三個放大因素（x86 掩蓋、測試環境併發度低、JIT 讓行為與測試時不同）。方法給四類並各配一句。**確定性測試要展開**——用 `CountDownLatch` 精確編排讓兩個執行緒在指定位置同時放行，把競態變成穩定重現的測試，**一旦寫出來就永遠守住這個 bug**，而壓力測試只是機率性的。加分點有兩個：**jcstress 出現 FORBIDDEN 就是確定的 bug，但沒出現不代表安全**；以及最重要的一句——**CI 上偶發失敗的測試往往是併發 bug 的第一個訊號，加重試或標記 flaky 等於關掉唯一發現它的管道**。收在根本策略：減少需要測試的表面積。

## 講稿

難以發現的根本原因是，併發正確性是關於所有可能執行交錯的性質，而測試只能取樣其中極少數。一段程式碼可能有一千萬種交錯，其中三種會出錯，跑一萬次可能一次都碰不到。所以測試通過不能證明沒有競態。

還有三個放大因素。x86 的強記憶體模型讓很多缺少同步的程式碼碰巧正確。測試環境的併發度遠低於生產。還有 JIT，測試跑幾百次可能都在解譯模式，跟生產環境的行為不一樣。

方法我分四類。壓力測試加隨機延遲、官方的 jcstress 工具、確定性測試、還有靜態分析。

我覺得最被低估的是確定性測試。與其祈禱壓測碰到那個交錯，不如用同步工具精確製造它。讓一個執行緒執行到某個點停下、另一個執行緒到另一個點，然後同時放行。這能把檢查後執行的競態變成穩定重現的測試。而且一旦寫出來，它就永遠守住這個問題。

最後一句我覺得最重要。CI 上偶爾失敗的測試往往是併發問題的第一個訊號。常見的處理是加重試或標記為不穩定，那等於主動關掉了唯一能發現它的管道。

## 常見追問

### 怎麼寫一個能穩定重現「檢查後執行」競態的測試？

**核心答案**：用**兩個 latch 精確編排**。讓執行緒 A 執行到「檢查完成、尚未執行」的位置後 `await` 一個 latch；主測試執行緒此時讓執行緒 B 完整執行一遍（改變了 A 檢查過的狀態）；然後 countDown 放行 A，讓它在過期的判斷上繼續執行。這樣就 100% 重現了那個交錯。關鍵是**需要一個可注入的暫停點**——生產程式碼裡放一個可覆寫的 protected 方法或一個可注入的 `Runnable`，預設是空實作。

**詳細解析**：有人會反對「為了測試修改生產程式碼」，但**這個注入點的成本極低（一個空方法呼叫，JIT 會直接消除），而收益是把一個機率性的 bug 變成確定性的測試**。替代方案是用位元組碼工具（如 Byteman）在執行期注入，不改動原始碼但增加了測試基礎設施的複雜度。**更好的思路往往是重構**：如果一段程式碼需要複雜的編排才能測試它的併發正確性，這通常說明它的同步邏輯過於分散，把「檢查與執行」收斂成一個原子操作（`compute`、`putIfAbsent`、或一把明確的鎖）之後，測試也就不需要了。**「難以測試」本身是設計訊號**。

**面試回答方式**：給出具體技術（兩個 latch 加可注入的暫停點）並說明編排步驟。回應「為測試改生產程式碼」的反對——**成本是一個會被 JIT 消除的空方法，收益是把機率性 bug 變成確定性測試**。真正的加分點是收在設計層面：**難以測試本身是設計訊號**，需要複雜編排才能測的同步邏輯通常過於分散，收斂成原子操作後測試也就不需要了。

### 靜態分析能抓到哪些併發問題？

**核心答案**：能抓的是**有明確模式的錯誤**：`@GuardedBy` 標註的欄位在沒有持鎖時被存取（ErrorProne）、雙重檢查鎖缺少 volatile、在 `synchronized` 上呼叫 `wait` 卻沒有用迴圈檢查條件、對可變靜態欄位的非同步存取、以及不一致的同步（同一個欄位有時加鎖有時不加）。抓不到的是**需要理解語意的問題**：跨物件的不變量、邏輯層面的競態、以及所有涉及外部系統的併發問題。

**詳細解析**：**`@GuardedBy` 的檢查是投資報酬率最高的一項**，因為它把「這個欄位需要哪把鎖」這個知識從註解變成了可強制執行的規則。缺點是**它需要程式碼先標註**，而既有程式碼補標註本身就是一次審查工作——不過那次審查往往就會發現問題。另一個實用的工具類別是**執行期檢查**：在開發模式下用斷言驗證「這個方法只能在某個執行緒上呼叫」（Android 的主執行緒檢查就是這樣），這抓到的是靜態分析看不出的動態違規。**靜態分析、執行期斷言、確定性測試、壓力測試四者互補，沒有任何一個能單獨解決問題。**

**面試回答方式**：把能抓與抓不到的界線劃清楚（有明確模式 vs 需要理解語意）。重點放在 **`@GuardedBy` 的投資報酬率最高**——它把知識變成可強制執行的規則，代價是既有程式碼要補標註，而那次審查本身就會發現問題。加分點是提出**執行期斷言**這個補充手段（驗證「只能在某執行緒上呼叫」），並收在四種手段互補、沒有單一銀彈。

### 生產環境發現併發 bug 後怎麼定位？

**核心答案**：優先保留三類證據。**執行緒轉儲**（連續抓數次，看執行緒卡在哪、有沒有 BLOCKED 的堆疊集中）、**堆積轉儲**（看資料結構是否處於不一致狀態，例如一個 `HashMap` 的 size 與實際節點數不符——那是併發寫入損壞的鐵證）、**應用日誌中的時序**（帶上執行緒名與精確時間戳，重建事件順序）。這些必須在問題發生時抓，事後重啟就沒了。

**詳細解析**：**最有力的證據往往是「不可能的狀態」**——一個被聲稱不變的欄位變了、一個計數器變成負數、一個 `List` 的 size 與內容不符。看到這些就可以確定是併發問題而不是邏輯錯誤，範圍立刻縮小到「哪些程式碼會寫這個狀態」。**所以在關鍵資料結構上加入不變量檢查（開發環境用斷言、生產環境用取樣檢查加告警）是很划算的**——它讓損壞在發生時就被發現，而不是在幾小時後表現成莫名其妙的業務錯誤。**併發 bug 的成本大部分來自「發現得太晚」，而不是「修起來太難」。**

**面試回答方式**：給三類必須在現場抓的證據（執行緒轉儲、堆積轉儲、帶執行緒名與時間戳的日誌）並強調重啟後就沒了。重點放在**「不可能的狀態」是最有力的證據**——計數器變負、`size` 與內容不符，看到就能確定是併發問題並立刻縮小範圍。收在可操作的建議：在關鍵資料結構上加不變量檢查（開發用斷言、生產用取樣加告警），因為**併發 bug 的成本大部分來自發現得太晚**。
