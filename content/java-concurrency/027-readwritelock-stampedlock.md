# 題目

讀寫鎖什麼時候才真的比互斥鎖快？`StampedLock` 又解決了讀寫鎖的什麼問題？

## 核心答案

`ReentrantReadWriteLock` 允許**多個讀取者同時持有**、寫入者獨佔。但它只在**讀遠多於寫、且臨界區夠長**時才划算——因為它的內部狀態比互斥鎖複雜（一個 int 拆成高 16 位的讀取計數與低 16 位的寫入計數），每次加解鎖的成本更高。**臨界區很短時，讀寫鎖往往比 `synchronized` 還慢**，因為省下的並行時間補不上多出來的協調成本。

它還有一個結構性問題：**寫入者飢餓**。非公平模式下讀取者可以持續插隊，寫入者可能長時間拿不到鎖。JDK 的實作有部分緩解（讀取者發現佇列頭是寫入者時會退讓），但在讀取極頻繁時仍會有明顯延遲。

`StampedLock`（JDK 8）的核心貢獻是**樂觀讀**：`tryOptimisticRead()` **完全不加鎖**，只取得一個版本戳記；讀完資料後用 `validate(stamp)` 檢查期間有沒有寫入發生，沒有就直接用，有就退回到悲觀讀重試。讀路徑因此**不修改任何共享狀態**，沒有 CAS、沒有快取行的爭用，在讀多寫少時吞吐遠勝讀寫鎖。

代價是它**不可重入、不支援 Condition，而且樂觀讀的程式碼必須寫成「先讀進區域變數、再驗證、驗證失敗才重試」的固定模式**，寫錯就會讀到不一致的資料。

## 詳細解析

**樂觀讀為什麼快，關鍵在「讀路徑不寫入」**。傳統讀寫鎖的讀取者要對共享的計數器做 CAS 遞增與遞減，多核之下那個快取行在核心之間來回彈跳（快取一致性協定的成本），讀取者越多爭用越嚴重——**看起來是並行的讀，實際上在一個計數器上序列化**。樂觀讀完全避開這件事，代價是可能白讀一次。

**樂觀讀的正確寫法有嚴格的紀律**：必須把讀到的欄位**先複製到區域變數**再驗證，不能邊讀邊用。原因是讀取期間可能有寫入者正在修改，讀到的可能是撕裂的中間狀態（例如 x 是新的、y 是舊的）——只要不拿它去做任何有副作用的事、驗證失敗就丟棄，就是安全的。**如果在驗證前就用讀到的值去查陣列索引或解引用，可能直接拋例外或讀到錯誤記憶體**，這是最容易寫錯的地方。

**不可重入是一個真實的限制**：`StampedLock` 的鎖不記錄持有者，同一個執行緒重複取寫鎖會**自我死鎖**。這讓它不適合放在會遞迴呼叫或呼叫外部程式碼的路徑上。它也**不支援 Condition**，所以需要等待某個條件的場景仍然要用 `ReentrantLock`。這些限制說明它的定位是**專門用於保護簡單資料結構的低階工具**，不是通用鎖的替代品。

**判斷該用哪一個的順序是**：先問「能不能不用鎖」——用不可變物件、`ConcurrentHashMap` 的原子方法、或 `AtomicReference` 加 CAS 通常更簡單也更快。不行的話，臨界區很短就用 `synchronized`（JIT 的偏向鎖與鎖粗化已經處理得很好），讀多寫少且臨界區有一定長度才考慮讀寫鎖，**只有在量測證明讀寫鎖的爭用是瓶頸時才上 `StampedLock`**。這個順序反映了一個原則：**複雜度應該由量測來驅動，不是由「聽起來比較快」來驅動**。

## 面試回答方式

先給讀寫鎖的成立條件——**讀遠多於寫且臨界區夠長**，並主動指出**臨界區很短時它比 `synchronized` 慢**，因為協調成本補不回來。再點出**寫入者飢餓**這個結構性問題。接著把 `StampedLock` 的貢獻講準：**樂觀讀完全不加鎖，讀路徑不修改任何共享狀態**——傳統讀寫鎖的讀取者要 CAS 一個共享計數器，那個快取行在多核之間彈跳，**看似並行的讀其實在計數器上序列化**。這是最有解釋力的一句。然後誠實給代價：不可重入（重複取寫鎖會自我死鎖）、不支援 Condition、樂觀讀必須「先複製到區域變數再驗證」否則可能讀到撕裂狀態。收在選型順序：先問能不能不用鎖，短臨界區用 `synchronized`，量測證明爭用才上 `StampedLock`。

## 講稿

讀寫鎖允許多個讀取者同時持有，寫入者獨佔。但它只在讀遠多於寫、而且臨界區夠長的時候才划算。臨界區很短的話，它往往比 synchronized 還慢，因為省下的並行時間補不上多出來的協調成本。

它還有一個結構性問題是寫入者飢餓，非公平模式下讀取者可以一直插隊。

StampedLock 的核心貢獻是樂觀讀。它完全不加鎖，只取得一個版本戳記，讀完資料再驗證期間有沒有寫入發生，沒有就直接用。

為什麼這樣快？關鍵在讀路徑不寫入。傳統讀寫鎖的讀取者要對一個共享計數器做 CAS，多核之下那個快取行在核心之間來回彈跳，讀取者越多爭用越嚴重。看起來是並行的讀，實際上在一個計數器上序列化了。

代價也很實在。它不可重入，同一個執行緒重複取寫鎖會自我死鎖。不支援條件變數。而且樂觀讀必須先把資料複製到區域變數再驗證，邊讀邊用可能讀到撕裂的中間狀態。

## 常見追問

### 為什麼讀寫鎖在短臨界區反而比 synchronized 慢？

**核心答案**：因為**協調成本是固定的，而並行收益與臨界區長度成正比**。讀寫鎖的加解鎖要操作一個更複雜的狀態（讀寫計數打包在同一個 int 裡）、要維護等待佇列、還要處理讀寫轉換的公平性判斷。臨界區只有幾條指令時，這些成本可能比臨界區本身還大。`synchronized` 則有 JIT 的多層最佳化——偏向鎖（早期版本）、輕量級鎖的 CAS 快路徑、以及**鎖粗化與鎖消除**，在低爭用下幾乎沒有開銷。

**詳細解析**：更關鍵的是**逃逸分析帶來的鎖消除**：JIT 若能證明某個物件不會被其他執行緒看到，會直接把 `synchronized` 移除。這對 `ReentrantReadWriteLock` 完全不適用，因為它是一個明確的物件、有明確的方法呼叫，JIT 無法證明它可以省略。**這是「內建語法比函式庫更容易被最佳化」的一個具體例子**——同樣的道理適用於 `synchronized` 對比 `ReentrantLock`（後者在低爭用下也未必更快，它的優勢在可中斷、可逾時、可公平、支援多個 Condition）。所以選鎖時該問的是「我需要哪些能力」，而不是「哪個比較快」。

**面試回答方式**：核心是「**協調成本固定、並行收益隨臨界區長度成正比**」。加分點是指出 JIT 對 `synchronized` 的最佳化——尤其是**逃逸分析的鎖消除對函式庫鎖完全不適用**，因為 JIT 無法證明一個明確的物件呼叫可以省略。收在選型原則：選鎖該問「需要哪些能力」（可中斷、可逾時、多 Condition），而不是「哪個比較快」。

### StampedLock 的鎖升級與降級怎麼用？

**核心答案**：它提供 `tryConvertToWriteLock(stamp)` 與 `tryConvertToReadLock(stamp)`。典型模式是：先樂觀讀或悲觀讀，發現需要修改時嘗試升級成寫鎖；**升級可能失敗**（期間有別人拿到寫鎖），失敗時要釋放當前鎖、重新取得寫鎖、並且**重新檢查條件**，因為狀態可能已經改變。降級（寫鎖轉讀鎖）則通常會成功，用於「修改完之後還要讀一段時間但不想擋住其他讀取者」。

**詳細解析**：升級的重試迴圈是最容易寫錯的地方——常見錯誤是升級失敗後直接取寫鎖，卻**忘了重新驗證條件**，於是在一個已經被別人改過的狀態上執行修改。正確的骨架是一個 `for(;;)` 迴圈，每一輪都重新讀取狀態、判斷是否需要修改、嘗試升級、失敗就繼續下一輪。**這與 CAS 的重試迴圈是同一個模式**：樂觀地嘗試、失敗就從頭再來，而「從頭」必須包含重新讀取狀態。`ReentrantReadWriteLock` 則**完全不支援升級**（會死鎖），只支援降級，這是它與 `StampedLock` 的一個實質差異。

**面試回答方式**：給出兩個轉換方法與典型模式，重點放在**升級可能失敗，失敗後必須重新檢查條件**這個最容易寫錯的地方。把正確骨架描述成一個重試迴圈，並指出它與 **CAS 的重試模式相同**——樂觀嘗試、失敗就從頭，而「從頭」必須包含重新讀取狀態。加分點是對比 `ReentrantReadWriteLock` 完全不支援升級（會死鎖）。

### 什麼時候該用不可變快照取代讀寫鎖？

**核心答案**：當**寫入頻率低、資料整體不大、且讀取需要一致的視圖**時。做法是把共享資料放在一個 `volatile` 的不可變物件引用裡：讀取直接讀那個引用（**零同步成本**），寫入則建立一份新的完整資料並原子地換掉引用。`CopyOnWriteArrayList` 就是這個模式的具體實作。

**詳細解析**：它的優勢是讀路徑完全沒有協調成本，而且**讀到的一定是某個時刻的完整一致快照**——連 `StampedLock` 的樂觀讀都做不到這點（樂觀讀可能讀到撕裂狀態）。代價是每次寫入要複製全部資料，資料量大或寫入頻繁時成本無法接受。**判斷的量化方式是「複製成本 × 寫入頻率」對比「鎖協調成本 × 讀取頻率」**——這兩個數字通常差了好幾個數量級，所以答案往往很明顯，不需要精細量測。中間地帶可以用**分片**：把資料切成 N 份，每份獨立做寫時複製，寫入只複製受影響的那一份。這與 `ConcurrentHashMap` 的分段思路一致。

**面試回答方式**：給出成立條件與做法（volatile 引用 + 整體替換），並指出它的獨特優勢——**讀到的一定是完整一致的快照**，連樂觀讀都做不到。給出量化判斷：「複製成本乘寫入頻率」對比「協調成本乘讀取頻率」，並說明兩者通常差好幾個數量級所以不需精細量測。加分點是提出分片作為中間地帶，並連到 `ConcurrentHashMap` 的分段思路。
