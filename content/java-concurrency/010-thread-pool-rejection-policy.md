# 題目

`ThreadPoolExecutor` 內建哪些拒絕策略？生產環境該如何選擇或自訂拒絕策略？

## 核心答案

JDK 內建 4 種拒絕策略：`AbortPolicy`（預設，直接拋例外）、`CallerRunsPolicy`（讓提交任務的執行緒自己執行）、`DiscardPolicy`（靜默丟棄）、`DiscardOldestPolicy`（丟棄佇列中最舊的任務再嘗試提交）。生產環境通常不會直接用內建策略，而是自訂拒絕策略，至少要記錄日誌／告警，避免任務被靜默丟棄導致問題難以排查。

## 詳細解析

**四種內建策略**：

1. **`AbortPolicy`**（預設）：直接拋出 `RejectedExecutionException`，呼叫方需要自行捕捉處理。優點是問題不會被隱藏；缺點是如果呼叫方沒有正確處理例外，可能導致呼叫鏈路異常中斷。
2. **`CallerRunsPolicy`**：由提交任務的執行緒（通常是業務執行緒，例如 Web 容器的請求執行緒）親自執行這個任務。這是一種「反壓」機制——因為提交執行緒被佔用去執行任務，暫時無法再提交新任務，間接降低了任務提交速度，給執行緒池喘息空間。缺點是可能拖慢呼叫方（例如拖慢 HTTP 請求回應時間）。
3. **`DiscardPolicy`**：靜默丟棄被拒絕的任務，不拋出任何例外、不留任何紀錄。**生產環境幾乎不該直接使用**，因為任務憑空消失且毫無感知，出問題時很難排查。
4. **`DiscardOldestPolicy`**：丟棄佇列中排隊最久的任務，然後重新嘗試提交目前這個任務。同樣有靜默丟棄任務的風險，且會讓「最先提交、可能最重要」的任務被犧牲。

**生產環境建議**：

- 大多數場景**自訂拒絕策略**，實作 `RejectedExecutionHandler` 介面，至少做到：記錄詳細日誌（任務資訊、執行緒池目前狀態：活躍數、佇列積壓量）、上報監控告警、必要時降級處理（例如寫入訊息佇列稍後重試，或直接返回「系統繁忙」給使用者而非讓執行緒卡死）。
- 選擇拒絕策略本質是業務決策：能不能接受任務被丟棄？能不能接受呼叫方被拖慢？這需要結合任務的重要程度與 SLA 來決定，不是單純的技術選型問題。

## 常見追問

- 如果拒絕策略選 `CallerRunsPolicy`，在 Web 服務中會有什麼風險（可能因為業務執行緒被佔用執行任務而導致請求逾時）？
- 如何在任務被拒絕時實現「降級到訊息佇列非同步重試」？
- 執行緒池的監控指標應該包含哪些（佇列長度、活躍執行緒數、拒絕次數、平均任務執行時間）？
