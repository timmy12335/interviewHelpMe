# 題目

`ThreadPoolExecutor` 內建哪些拒絕策略？生產環境該如何選擇或自訂拒絕策略？

## 核心答案

JDK 內建 4 種拒絕策略：`AbortPolicy`（預設，直接拋例外）、`CallerRunsPolicy`（讓提交任務的執行緒自己執行）、`DiscardPolicy`（靜默丟棄）、`DiscardOldestPolicy`（丟棄佇列中最舊的任務再嘗試提交）。生產環境通常不會直接用內建策略，而是自訂拒絕策略，至少要記錄日誌／告警，避免任務被靜默丟棄導致問題難以排查。

## 詳細解析

**四種內建策略**：

1. **`AbortPolicy`**（預設）：直接拋出 `RejectedExecutionException`，呼叫方需要自行捕捉處理。優點是問題不會被隱藏；缺點是如果呼叫方沒有正確處理例外，可能導致呼叫鏈路異常中斷。
2. **`CallerRunsPolicy`**：由提交任務的執行緒親自執行這個任務。這是一種「反壓」機制，缺點是可能拖慢呼叫方（例如拖慢 HTTP 請求回應時間）。
3. **`DiscardPolicy`**：靜默丟棄被拒絕的任務，不拋出任何例外、不留任何紀錄。**生產環境幾乎不該直接使用**。
4. **`DiscardOldestPolicy`**：丟棄佇列中排隊最久的任務，然後重新嘗試提交目前這個任務。同樣有靜默丟棄任務的風險。

**生產環境建議**：

- 大多數場景**自訂拒絕策略**，實作 `RejectedExecutionHandler` 介面，至少做到：記錄詳細日誌、上報監控告警、必要時降級處理。
- 選擇拒絕策略本質是業務決策：能不能接受任務被丟棄？能不能接受呼叫方被拖慢？這需要結合任務的重要程度與 SLA 來決定。

## 面試回答方式

先把四種內建策略快速過一遍（一句話一個），但不要平均用力——花最多時間講清楚「為什麼 `DiscardPolicy` 和 `DiscardOldestPolicy` 生產環境不該用」，因為這是最能展現風險意識的部分。接著直接說結論「生產環境通常自訂拒絕策略」，並具體講出自訂策略至少要做到哪三件事（記日誌、告警、降級）。如果面試官是資深工程師，可以主動補一句「選哪個策略本質是業務決策，不是純技術問題」，展現你有把技術選型和業務需求連結起來思考的習慣。

## 常見追問

### 如果拒絕策略選 CallerRunsPolicy，在 Web 服務中會有什麼風險？

**核心答案**：因為業務執行緒（例如處理 HTTP 請求的執行緒）被迫去執行本該由執行緒池處理的任務，可能導致這個請求的回應時間明顯拉長，甚至可能連鎖影響到 Web 容器本身的請求處理執行緒池被大量佔用。

**詳細解析**：`CallerRunsPolicy` 的反壓設計立意良好——讓提交速度自然被拖慢，給執行緒池喘息空間，但這個「拖慢」的代價是由呼叫方承擔的。在 Web 服務中，如果呼叫方剛好是處理使用者請求的執行緒（例如 Tomcat 的請求處理執行緒），這個執行緒被迫執行一個可能耗時的非同步任務，等同於把原本應該非同步處理的邏輯變成同步阻塞，使用者會感受到明顯的回應延遲；如果這種情況大量發生，甚至可能把 Web 容器自己的執行緒池也拖慢甚至耗盡，變成一種連鎖反應式的效能劣化，反而放大了問題而非緩解問題。因此 `CallerRunsPolicy` 更適合用在「呼叫方不是使用者請求執行緒、可以承受被拖慢」的場景，例如背景批次處理系統。

**面試回答方式**：這題最好舉出「使用者請求被拖慢，甚至連鎖影響 Web 容器自己的執行緒池」這個具體因果鏈，展現你能預見一個看似合理的機制在特定場景下反而會放大問題，這種風險預判能力是資深工程師的重要訊號。

### 如何在任務被拒絕時實現降級到訊息佇列非同步重試？

**核心答案**：在自訂的 `RejectedExecutionHandler` 實作中，捕捉到任務被拒絕時，不直接拋出例外或丟棄，而是把任務資訊序列化後發送到訊息佇列（如 Kafka、RabbitMQ），由消費端稍後非同步重新處理。

**詳細解析**：具體做法是自訂一個實作 `RejectedExecutionHandler` 介面的類別，在 `rejectedExecution(Runnable r, ThreadPoolExecutor executor)` 方法中，把這個被拒絕的任務轉換成一個可序列化的訊息物件（包含任務的必要參數，而不是 `Runnable` 物件本身，因為 `Runnable` 通常無法直接序列化），推送到訊息佇列的一個「重試」主題。另外需要有一個消費端服務或排程任務，定期從這個重試主題拉取訊息並重新嘗試執行，通常還會搭配重試次數上限與死信佇列（多次重試仍失敗的訊息單獨存放供人工排查），避免無限重試造成資源浪費。這個模式本質上是把「同步的執行緒池過載」轉換成「非同步的訊息佇列緩衝」，用犧牲即時性換取系統的韌性。

**面試回答方式**：回答時強調「任務資訊要序列化成訊息，而不是直接丟 `Runnable` 物件」這個實作細節，並補充「需要搭配重試上限與死信佇列」，展現你考慮到了這個方案的完整生命週期，而不只是「丟到 MQ 裡」這麼簡單的一句話。

### 執行緒池的監控指標應該包含哪些？

**核心答案**：佇列長度（判斷是否積壓）、活躍執行緒數與執行緒池大小（判斷是否接近飽和）、拒絕次數（判斷是否已經在丟任務）、平均任務執行時間（判斷是否有任務執行變慢拖累整體吞吐）。

**詳細解析**：這四類指標分別對應執行緒池健康狀況的不同面向：佇列長度反映「上游提交速度是否超過處理速度」；活躍執行緒數／執行緒池大小的比值反映「執行緒池是否接近或已達到滿載」；拒絕次數是最直接的「系統已經扛不住」的信號，一旦這個數字不為零就代表有任務真的沒被執行；平均任務執行時間則能幫助判斷問題根源是「任務本身變慢了」（例如下游依賴變慢）還是「單純提交量暴增」。把這些指標定期上報到監控系統並設定告警閾值，能讓團隊在系統真正出問題（大量請求逾時、記憶體暴漲）之前就先發現異常趨勢並介入處理，這也呼應了前面提到的「拒絕策略至少要能被監控到」的原則。

**面試回答方式**：不要只列出指標名稱，針對每個指標補一句「這個指標異常代表什麼問題」，展現你理解監控的目的是「儘早發現問題根源」而不只是「收集數據」。
