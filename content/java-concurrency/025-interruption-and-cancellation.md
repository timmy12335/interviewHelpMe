# 題目

`Thread.interrupt()` 到底做了什麼？為什麼捕捉 `InterruptedException` 之後只印堆疊是錯的？

## 核心答案

`interrupt()` **不會停止執行緒**，它只是把該執行緒的**中斷旗標設為 true**。這是一個**協作式**的機制——被中斷的執行緒必須自己檢查旗標或在可中斷的阻塞點被喚醒，然後決定要怎麼回應。Java 沒有安全的強制停止機制（`Thread.stop` 早已廢棄，因為它會在任意位置拋例外，留下破損的不變量與未釋放的鎖）。

回應中斷有兩條路徑。**在可中斷的阻塞方法裡**（`sleep`、`wait`、`join`、`BlockingQueue.take`、`Lock.lockInterruptibly`）會拋出 `InterruptedException`，而且拋出前會把中斷旗標清掉。**在計算迴圈裡**則要自己輪詢 `Thread.currentThread().isInterrupted()`。

「捕捉之後只印堆疊」之所以錯，正是因為**旗標已經被清掉了**——這等於把「有人要求你停下來」這個訊息吞掉，上層再也看不到。正確的做法只有兩種：**往上拋**（讓呼叫方決定），或者**恢復旗標**（`Thread.currentThread().interrupt()`）之後再結束當前工作。

## 詳細解析

旗標被清除這件事是整題的關鍵。JDK 這樣設計是為了讓「處理中斷」與「傳遞中斷」成為兩個明確的選擇，而不是預設就一直帶著。代價是只要有人吞掉例外，中斷請求就永遠消失了——執行緒池裡的任務吞掉之後，`shutdownNow` 發出的中斷完全沒有效果，關閉會卡住直到逾時。

輪詢的頻率決定了取消的延遲：長計算迴圈裡如果每一百萬次才檢查一次，取消請求就要等那麼久。實務上的做法是在**迴圈的自然邊界**檢查（每處理完一批、每讀完一個檔案），這樣延遲有上界又不會付出太多檢查成本。**注意 `isInterrupted()` 與 `interrupted()` 的差別**——後者是靜態方法，**會清除旗標**，寫錯了會意外吞掉中斷。

不可中斷的阻塞是實務上的難題：傳統的 socket IO（`InputStream.read`）、`synchronized` 的鎖等待、以及 `Lock.lock()`（相對於 `lockInterruptibly`）都**不回應中斷**。要讓這些能被取消，只能靠**關閉底層資源**——關閉 socket 會讓阻塞中的 read 拋出 `SocketException`。這是為什麼有些框架把「取消」實作成「關閉連線」而不是「中斷執行緒」。

**Future.cancel 的兩個參數語意要分清**：`cancel(true)` 會中斷正在執行的任務執行緒，`cancel(false)` 只會阻止尚未開始的任務執行、對已在跑的不做任何事。**選 false 通常更安全**——除非任務明確設計成可中斷的，否則中斷一個沒有處理中斷的任務只是把旗標設起來然後什麼都沒發生，反而讓呼叫方誤以為取消成功了。

## 面試回答方式

先破除最大的誤解：`interrupt` 不會停止執行緒，只是設一個旗標，Java 沒有安全的強制停止（`Thread.stop` 廢棄的理由是會在任意位置留下破損的不變量與未釋放的鎖）。接著給關鍵事實——拋出 `InterruptedException` 之前旗標會被清掉，所以「捕捉後只印堆疊」等於吞掉中斷請求，上層再也看不到。給出唯二正確的處理方式：往上拋，或恢復旗標後結束工作。加分點有三個：吞掉之後 `shutdownNow` 會完全沒效果、關閉卡到逾時；**`interrupted()` 是靜態方法且會清旗標**，與 `isInterrupted()` 容易寫混；以及不可中斷的阻塞（socket read、synchronized）只能靠關閉底層資源來取消。

## 講稿

中斷不會停止執行緒，它只是把中斷旗標設成 true。這是一個協作式的機制，被中斷的執行緒必須自己檢查旗標，或是在可中斷的阻塞點被喚醒，然後決定怎麼回應。Java 沒有安全的強制停止，那個方法早就廢棄了，因為它會在任意位置拋例外，留下破損的不變量跟沒釋放的鎖。

有一個關鍵事實很多人不知道。可中斷的阻塞方法拋出中斷例外之前，會先把旗標清掉。所以捕捉之後只印堆疊，等於把有人要求你停下來這個訊息完全吞掉，上層再也看不到。

正確的做法只有兩種。往上拋，讓呼叫方決定。或是恢復旗標之後再結束當前的工作。

吞掉的後果很具體。執行緒池裡的任務吞掉之後，關閉時發出的中斷完全沒有效果，關閉會一直卡到逾時。

還有一個實務上的難題。傳統的 socket 讀取跟 synchronized 的鎖等待都不回應中斷。要取消這些，只能靠關閉底層資源，讓阻塞中的讀取拋出例外。

## 常見追問

### 為什麼 Thread.stop 被廢棄了？

**核心答案**：因為它會在**任意的執行位置**拋出 `ThreadDeath`——可能正好在一個物件更新到一半、不變量暫時被破壞的時候。更嚴重的是它會釋放該執行緒持有的所有監視器鎖，於是其他執行緒立刻看到一個處於不一致狀態的物件，而且完全沒有跡象顯示發生過什麼。這種損壞無法用 try-catch 防禦，因為例外可能在任何一行拋出。

**詳細解析**：`suspend` 與 `resume` 也基於相同的理由被廢棄——`suspend` 掛起執行緒時**不釋放鎖**，如果掛起的執行緒持有某個鎖而喚醒它的執行緒又需要那個鎖，就是必然的死鎖。這些 API 的共同問題是它們從外部改變了執行緒的執行狀態，而執行緒內部的程式碼對此毫無準備。協作式中斷的設計正好相反：中斷點是程式碼自己選的，可以確保在安全的位置回應。這個「狀態改變必須發生在程式碼準備好的位置」的原則，在 GC 的安全點（safepoint）設計上也看得到，是同一種思路。

**面試回答方式**：核心是「在任意位置拋例外**並釋放所有鎖**」，讓其他執行緒看到不一致的狀態且無從防禦。補上 `suspend` 的對照——它掛起時**不釋放鎖**所以會死鎖，說明這一族 API 的共同問題是從外部改變執行狀態而程式碼沒有準備。加分點是把它連到 GC 安全點的設計：狀態改變必須發生在程式碼準備好的位置。

### 執行緒池裡的任務被中斷後，會發生什麼？

**核心答案**：取決於任務怎麼回應。`shutdownNow()` 會對所有**正在執行**的工作執行緒呼叫 `interrupt()`，並回傳尚未開始的任務清單。如果任務正阻塞在可中斷的方法上，它會拋 `InterruptedException`；如果任務吞掉例外或根本不檢查旗標，**它會繼續跑到自然結束**，`shutdownNow` 對它毫無作用。這是「關閉時卡住」最常見的原因。

**詳細解析**：另一個容易忽略的細節是**任務拋出的例外會被吞掉**。用 `submit` 提交的任務，例外會被包進 `Future`——如果沒有人呼叫 `get()`，例外就永遠不會被看到，任務靜默失敗。用 `execute` 提交則會走到執行緒的 `UncaughtExceptionHandler`。所以池化任務一定要在任務內部自己 try-catch 並記錄，不要依賴外層。至於關閉的正確流程：先 `shutdown()`（停止接受新任務、讓已提交的跑完）、再 `awaitTermination` 等一段合理的時間、逾時後才 `shutdownNow()`、最後再等一次確認。這四步缺一不可，只呼叫 `shutdown()` 而不等待等於沒有關閉。

**面試回答方式**：先說明取決於任務怎麼回應，並點出任務不檢查旗標時 `shutdownNow` 毫無作用是關閉卡住的常見原因。加分點是提出另一個獨立的坑：`submit` 的例外會被包進 `Future`，沒人 `get` 就靜默失敗，所以池化任務要自己 try-catch。最後給出關閉的四步流程並強調缺一不可。

### 怎麼設計一個可以被取消的長時間任務？

**核心答案**：三個要素。第一，在自然邊界輪詢中斷旗標——每處理完一批資料、每完成一個階段就檢查一次，讓取消延遲有明確上界。第二，所有阻塞操作都用可中斷的版本——`lockInterruptibly` 而非 `lock`、`BlockingQueue.poll(timeout)` 而非無限等待、NIO 的 `InterruptibleChannel` 而非傳統 socket。**第三，取消時要能清理**——用 try-finally 確保已配置的資源釋放、已寫入的部分結果被回滾或標記為不完整。

**詳細解析**：還有一個設計層面的建議：把「取消」與「逾時」統一成同一條路徑。逾時本質上就是「時間到了就取消」，如果兩者用不同機制實作，會出現「逾時了但任務還在跑」這種難以推理的狀態。實務上可以讓任務接受一個表示截止時間的參數，在每個檢查點同時判斷中斷旗標與是否超過截止時間。**另外要考慮取消的可見性**——任務被取消後，呼叫方要能知道結果是「完成」「被取消」還是「失敗」，而不是收到一個看起來正常但其實不完整的結果。這通常意味著回傳型別要能表達這三種狀態。

**面試回答方式**：給三個要素（自然邊界輪詢、可中斷的阻塞版本、try-finally 清理）並各配具體 API。加分點是兩個設計層面的建議：把取消與逾時統一成同一條路徑（否則會出現「逾時了但還在跑」的狀態），以及回傳型別要能區分完成、取消、失敗三種狀態，避免呼叫方收到看似正常但不完整的結果。
