# 題目

`scheduleAtFixedRate` 與 `scheduleWithFixedDelay` 差在哪？為什麼定時任務會「突然不跑了」？

## 核心答案

`scheduleAtFixedRate` 是**固定頻率**——下一次的預定時間是「上一次的預定開始時間 + 週期」，與這次跑多久無關。如果某次執行超過一個週期，**下一次會立刻開始（不會併發執行同一個任務，但會連續跑以追上進度）**。`scheduleWithFixedDelay` 是**固定間隔**——下一次在「上一次**結束**之後」再等一個間隔，所以實際頻率會隨執行時間變動。

「突然不跑了」的原因幾乎總是同一個：**任務拋出了未捕捉的例外**。`ScheduledThreadPoolExecutor` 的契約是**週期任務一旦拋出例外就被取消，後續所有執行都不再發生**，而例外被包進 `ScheduledFuture` 裡——**沒有人呼叫 `get()` 就永遠看不到它**。於是表現是：任務靜默停止，日誌裡什麼都沒有。

解法只有一個且必須做：**在任務主體的最外層整段包 try-catch**，捕捉 `Throwable`（不只是 `Exception`，`Error` 同樣會終止任務），記錄後不再往外拋。

## 詳細解析

**這個「靜默停止」的坑之所以特別危險，是因為它的症狀不在定時任務本身**：資料沒有同步、快取沒有更新、報表沒有產生——問題出現在下游，而排查的人往往要繞很久才想到去看那個從不出聲的定時任務。**監控的做法是讓任務每次執行都更新一個「最後成功時間」指標，並對它設告警**，這樣任務停止會在幾分鐘內被發現，而不是等業務方反映。

**`scheduleAtFixedRate` 的追趕行為要特別注意**：如果任務因為某次特別慢而落後了十個週期，它**不會跳過那十次，而是連續執行十次**去追進度。對於「每分鐘同步一次」這種冪等的任務，追趕沒問題；對於「每小時發一次摘要郵件」，追趕就會連發十封。**需要「錯過就跳過」的語意時，`ScheduledExecutorService` 沒有內建支援**，要自己在任務裡判斷「距離預定時間是否已經超過容忍範圍」，或改用 Quartz 這類支援 misfire 策略的排程框架。

**它的執行緒模型也有限制**：`ScheduledThreadPoolExecutor` 使用**無界的延遲佇列**（`DelayedWorkQueue`），所以**它的 `maximumPoolSize` 完全無效**——池永遠不會超過 core size，因為佇列永遠不會滿。這表示如果 core size 是 1 而某個任務跑很久，**所有其他定時任務都會被延遲**。多個定時任務混在同一個池裡時，一個慢任務會拖垮全部，這是實務上很常見的問題。**解法是依任務特性分池**，或者讓定時任務只負責提交工作到另一個執行池。

**單機定時任務在多實例部署下會重複執行**：服務擴到三個實例，同一個定時任務就跑三次。解法是**分散式鎖**（用 Redis 或資料庫搶一個租約）或**專門的排程系統**（Quartz 叢集模式、XXL-Job、或雲端的排程服務）。**這是從單機走向叢集時最容易被忽略的一件事**，因為在開發與測試環境（單實例）永遠不會顯現。

## 面試回答方式

先精確區分兩個方法——**固定頻率是以「上次預定開始時間」為基準，固定間隔是以「上次結束時間」為基準**。接著把重點放在「突然不跑了」：**未捕捉例外會讓週期任務被永久取消，而例外被包進 Future 沒人看得到**，所以是靜默停止。給出唯一解法：最外層整段 try-catch 且要捕捉 `Throwable`。加分點有三個：**`scheduleAtFixedRate` 落後時會連續追趕**（每小時的摘要郵件會連發十封），需要「錯過就跳過」得自己判斷或換 Quartz；**`maximumPoolSize` 完全無效**因為用的是無界延遲佇列，所以一個慢任務會拖垮同池的所有定時任務；以及**多實例部署會重複執行**，需要分散式鎖或專門的排程系統，而這在單實例的開發環境永遠測不出來。

## 講稿

固定頻率的下一次是以上一次的預定開始時間加週期來算，跟這次跑多久無關。固定間隔則是等上一次結束之後再等一個間隔，所以實際頻率會隨執行時間變動。

至於為什麼定時任務會突然不跑了，原因幾乎總是同一個，任務拋出了未捕捉的例外。契約就是週期任務一旦拋例外就被取消，後續全部不再執行。而那個例外被包進 Future 裡，沒有人去取就永遠看不到。所以表現是靜默停止，日誌裡什麼都沒有。

解法只有一個而且必須做，在任務主體的最外層整段包 try-catch，而且要捕捉 Throwable，因為 Error 一樣會終止任務。

還有兩個實務上的坑。第一，這種池用的是無界的延遲佇列，所以最大執行緒數完全無效。如果核心數是一而某個任務跑很久，其他定時任務全部被延遲。我會依任務特性分池。

第二，服務擴到三個實例，同一個定時任務就跑三次。這在單實例的開發環境永遠測不出來，需要分散式鎖或專門的排程系統。

## 常見追問

### 定時任務的執行時間漂移該怎麼處理？

**核心答案**：先確認需求是「**固定頻率**」還是「**固定間隔**」。要求「每小時整點執行」屬於固定頻率，且不能容忍漂移——`scheduleAtFixedRate` 雖然以預定時間為基準而不累積漂移，但它**不對齊時鐘**（從第一次執行的時刻起算），所以要對齊整點必須自己計算首次延遲。要求「上次做完休息五分鐘再做」屬於固定間隔，漂移是預期內的。

**詳細解析**：需要**對齊真實時鐘且處理時區與日光節約**時，`ScheduledExecutorService` 就不夠了——它基於 `System.nanoTime` 的相對時間，完全不知道日曆。這時該用 cron 風格的排程（Spring 的 `@Scheduled(cron = ...)`、Quartz），它們用 `ZonedDateTime` 計算下一次的絕對時刻。**但要注意 cron 排程在日光節約的間隙那天可能跳過一次執行、在重疊那天可能執行兩次**，這需要明確的策略。另外，長時間執行的 JVM 中 `nanoTime` 是單調的（不受系統時間調整影響），這對相對排程是好事，但也意味著**手動調整系統時間不會影響 `ScheduledExecutorService`**，而會影響 cron 排程——這個差異在處理時間相關的問題時值得知道。

**面試回答方式**：先把需求分成固定頻率與固定間隔兩類，並指出 `scheduleAtFixedRate` **不對齊時鐘**，要對齊整點得自己算首次延遲。接著給出界線：需要對齊日曆、處理時區與日光節約時就該換 cron 排程。加分點是提醒 cron 在日光節約的間隙與重疊那天會跳過或重複執行，以及 `nanoTime` 單調所以不受系統時間調整影響——這個差異在排查時間問題時很有用。

### 為什麼說「一個慢任務會拖垮同池的所有定時任務」？

**核心答案**：因為 `ScheduledThreadPoolExecutor` 的**執行緒數固定在 core size**（無界佇列讓 max size 失效）。如果池只有 1 個執行緒而某個任務跑了十分鐘，這十分鐘內**所有到期的其他任務都只能在佇列裡等**，它們的實際執行時間會全部延後。即使 core size 設成 5，只要同時有 5 個慢任務就會發生同樣的事。

**詳細解析**：這是**共享資源的典型故障傳播**，處理方式也是通用的：**隔離**。做法有兩種。第一，**依特性分池**——快而頻繁的任務一個池、慢而稀疏的任務另一個池，讓故障不跨池傳播。第二，**讓定時任務只負責觸發**，實際工作提交到另一個有界的工作池並立即返回；這樣定時執行緒永遠不會被業務邏輯佔用，但要處理「上一次還沒做完、下一次又觸發」的重入問題（用一個 `AtomicBoolean` 或信號量做互斥，並在跳過時記錄）。**第二種通常更好**，因為它讓「排程」與「執行」兩個關注點分離，也讓工作池的容量可以獨立調整。

**面試回答方式**：先給機制（無界佇列讓 max size 失效、執行緒數固定在 core size）與後果。然後把它歸類成**共享資源的故障傳播**，並給出兩種隔離做法。明確推薦第二種——**定時任務只負責觸發、實際工作提交到另一個有界池**，因為它分離了排程與執行兩個關注點；同時誠實指出它需要處理重入（用旗標或信號量互斥並在跳過時記錄）。

### 分散式環境下怎麼保證定時任務只執行一次？

**核心答案**：三種層次的方案。**分散式鎖**——每個實例執行前先搶一個帶 TTL 的鎖（Redis 的 `SET NX EX` 或資料庫的唯一約束），搶到才執行。**排程框架的叢集模式**——Quartz 用資料庫的行鎖協調，XXL-Job 用中心排程器主動派發。**外部觸發**——用 Kubernetes CronJob 或雲端排程服務定時呼叫一個 API，應用本身完全不排程。

**詳細解析**：分散式鎖的方案最輕量但有**兩個必須處理的細節**：鎖的 TTL 要大於任務的最長執行時間（否則任務還在跑鎖就過期了，另一個實例會開始執行），而且**不能只靠鎖保證不重複**——網路分割或 GC 停頓可能讓持鎖者失去鎖而不自知。所以**任務本身應該盡量設計成冪等的**，鎖只是減少重複的機率而不是消除它。這與分散式系統中「鎖不能提供互斥保證，只能提供效率最佳化」的普遍認識一致。**外部觸發的方案最乾淨**——排程的可靠性交給專門的系統、應用只是一個無狀態的 HTTP 端點，也更容易手動重跑與觀察。

**面試回答方式**：給三個層次的方案並排出輕重。重點放在分散式鎖的兩個細節：**TTL 必須大於最長執行時間**、以及**不能只靠鎖**（網路分割或 GC 停頓會讓持鎖者失去鎖而不自知）。由此推出關鍵結論——**任務本身要設計成冪等的，鎖只是降低重複機率而非消除**。收在推薦外部觸發：排程可靠性交給專門系統，應用只是無狀態端點，也更好手動重跑與觀察。
