# 題目

用 `ThreadLocal` 存的追蹤 ID，為什麼提交到執行緒池之後就不見了？有哪些解法？

## 核心答案

因為 `ThreadLocal` 的值**綁在執行緒物件上**（每個 `Thread` 有一個 `ThreadLocalMap` 欄位）。提交到執行緒池後，任務在**另一個執行緒**上執行，那個執行緒的 map 裡沒有你放的值——所以取到 null。日誌框架的 MDC 就是基於 `ThreadLocal`，這正是「非同步之後日誌沒有追蹤 ID」的成因。

解法有四層。**`InheritableThreadLocal`** 讓**新建立的子執行緒**繼承父執行緒的值，但**對執行緒池無效**——池裡的執行緒是很久以前建立的，繼承的是當時那個建立者的上下文，反而更危險（拿到過期的錯誤資料）。**手動捕獲與還原**——提交任務前抓下當前上下文，在任務開頭設定、結尾清除，這是最可靠但最囉嗦的做法。**包裝執行器**——把上述邏輯封裝進一個 `ExecutorService` 的裝飾器（阿里的 TransmittableThreadLocal、Micrometer 的 `ContextSnapshot`、Spring 的 `TaskDecorator` 都是這條路）。**作用域值（Scoped Values，JDK 21 預覽）**——語言層級的新機制，值只在一個明確的作用域內有效，配合結構化併發自動傳遞給子任務。

**實務上的正確答案幾乎總是第三層**：用框架已經提供的裝飾器，不要自己在每個提交點手動處理。

## 詳細解析

**`InheritableThreadLocal` 對執行緒池「無效」的說法要更精確**：它其實有效，但**繼承發生在執行緒建立的那一刻**，而池中的執行緒是在第一次需要時建立的。所以某個請求 A 觸發了執行緒建立，那個執行緒就永久帶著 A 的上下文；之後請求 B、C、D 的任務跑在同一個執行緒上時，看到的仍是 A 的追蹤 ID。**這比拿到 null 更糟——它會產生看起來合理但完全錯誤的日誌關聯**，排查時會把兩個不相干的請求串在一起。

**手動還原的關鍵是「一定要在 finally 清除」**：執行緒池的執行緒會被重複使用，任務結束時沒有清乾淨的話，下一個任務會看到殘留的上下文。這與 `ThreadLocal` 的記憶體洩漏是同一個根源——**池化執行緒的生命週期遠長於任務，所以任務層級的狀態必須顯式清理**。

**傳遞的內容要慎選**：追蹤 ID、租戶 ID、語系這類**小而穩定的識別資訊**適合放上下文；使用者的完整物件、資料庫連線、大型物件則不適合——它們會被非預期地跨執行緒共享（可能不是執行緒安全的），而且在虛擬執行緒場景下每個執行緒一份會撐爆記憶體。**上下文應該只放「識別」不放「資源」。**

**作用域值是為虛擬執行緒設計的**。`ThreadLocal` 有三個問題在數十萬個虛擬執行緒下被放大：**無界的生命週期**（設了不清就一直在）、**可變**（任何程式碼都能改）、**每執行緒一份副本的記憶體成本**。作用域值把這三點都改掉：**不可變、綁定在一個明確的作用域內、子任務共享父的值而不複製**。它的形式是 `ScopedValue.where(KEY, value).run(() -> ...)`——值只在那個 lambda 裡有效，離開就自動消失，**不可能忘記清理**。

## 面試回答方式

先給根本原因——**`ThreadLocal` 的值綁在執行緒物件上**，池化後任務跑在別的執行緒上所以取不到，MDC 就是基於它。接著給四層解法，並特別把 **`InheritableThreadLocal` 的陷阱講清楚**：它不是無效，而是繼承發生在執行緒建立的那一刻，於是池中執行緒永久帶著第一個請求的上下文——**這比拿到 null 更糟，會產生看起來合理但完全錯誤的日誌關聯**。實務答案給明確：用框架提供的執行器裝飾器（`TaskDecorator`、TransmittableThreadLocal、Micrometer 的 ContextSnapshot），不要在每個提交點手動處理，並強調**一定要在 finally 清除**因為池化執行緒會重複使用。加分點有兩個：**上下文只放識別不放資源**；以及**作用域值為虛擬執行緒設計**——不可變、綁定明確作用域、子任務共享不複製，形式上不可能忘記清理。

## 講稿

因為 ThreadLocal 的值是綁在執行緒物件上的，每個執行緒有自己的一份對映。提交到執行緒池之後，任務在另一個執行緒上執行，那個執行緒的對映裡沒有你放的值。日誌框架的 MDC 就是基於這個機制，所以非同步之後日誌就沒有追蹤 ID 了。

有一個陷阱要特別講。可繼承的版本看起來能解決，但它的繼承發生在執行緒建立的那一刻。池裡的執行緒是很久以前建立的，所以它永久帶著當時那個請求的上下文。之後其他請求跑在同一個執行緒上，看到的還是最早那個追蹤 ID。這比拿到 null 更糟，因為它會產生看起來合理但完全錯誤的日誌關聯。

實務上的正確做法是用框架提供的執行器裝飾器，在提交時捕獲上下文、執行前設定、結束後清除。關鍵是一定要在 finally 清除，因為池化的執行緒會被重複使用，沒清乾淨下一個任務就會看到殘留。

還有一個原則。上下文只放識別，不要放資源。追蹤 ID、租戶 ID 這種小而穩定的可以，連線或大型物件不行。

## 常見追問

### ThreadLocal 的記憶體洩漏具體是怎麼發生的？

**核心答案**：`ThreadLocalMap` 的 key 是**對 `ThreadLocal` 物件的弱引用**，value 則是**強引用**。當 `ThreadLocal` 物件本身沒有其他強引用時，key 會被 GC 回收變成 null，但 **value 仍然被 map 強引用著**——形成一個 key 為 null、value 取不到卻回收不掉的 entry。在池化執行緒中，這個 map 隨執行緒長期存活，entry 就一直累積。

**詳細解析**：JDK 有部分緩解——`get`、`set`、`remove` 時會**順帶清理一些 key 為 null 的 entry**（探測式清理），但它只清理探測路徑上遇到的，不保證全部清掉。所以**唯一可靠的做法是用完呼叫 `remove()`，而且放在 finally 裡**。典型的洩漏場景是：`ThreadLocal` 存了一個大物件（例如整個使用者的資料）、`ThreadLocal` 變數本身是區域變數或被重新賦值、然後任務結束沒有 remove——那個大物件就跟著執行緒活到服務重啟。**排查方式是 heap dump 之後看 `ThreadLocalMap$Entry` 的數量與它們持有的物件**，如果某個池化執行緒上有幾百個 entry，答案就很明顯。

**面試回答方式**：先給精確的機制——**key 是弱引用、value 是強引用**，key 被回收後 value 仍被 map 強引用且再也取不到。指出 JDK 的探測式清理只是部分緩解，不保證清乾淨。給出唯一可靠的做法：**finally 裡 remove**。加分點是描述典型洩漏場景（存大物件、任務結束沒 remove、跟著池化執行緒活到重啟）與排查方式（heap dump 看 `ThreadLocalMap$Entry` 的數量）。

### 作用域值與 ThreadLocal 的具體差別是什麼？

**核心答案**：三個關鍵差別。**不可變**——`ScopedValue` 綁定後在該作用域內不能改，任何人拿到的都是同一個值，消除了「誰在什麼時候改了它」這類問題。**作用域明確**——用 `ScopedValue.where(KEY, v).run(...)` 綁定，離開 lambda 自動解除，**在語法上不可能忘記清理**。**共享而非複製**——子執行緒（尤其是結構化併發下的子任務）**共享父的綁定而不複製一份**，所以數十萬個虛擬執行緒不會產生數十萬份副本。

**詳細解析**：這三點合起來解決的正是 `ThreadLocal` 在虛擬執行緒時代的三個問題：無界生命週期、可變、記憶體成本。**設計上的取捨是失去了靈活性**——不能在任意位置設定或修改，必須在明確的作用域邊界綁定。這對某些既有的使用模式（例如中介軟體在請求處理過程中逐步累積上下文）需要重構。**但這個「限制」正是它的價值**：`ThreadLocal` 之所以難用，就是因為它太靈活——任何程式碼在任何時候都能改，導致上下文的來源與生命週期完全無法從程式碼推理。**用限制換取可推理性，是很多現代 API 設計的共同方向**（`final`、不可變集合、結構化併發都是同一類）。

**面試回答方式**：給三個差別（不可變、作用域明確、共享而非複製）並對應到 `ThreadLocal` 的三個問題。誠實指出取捨——失去靈活性，逐步累積上下文的既有模式需要重構。真正的加分點是把限制重新詮釋成價值：**`ThreadLocal` 難用正是因為太靈活**，任何程式碼都能改導致無法推理；**用限制換可推理性是現代 API 設計的共同方向**，並舉不可變集合與結構化併發作為同類。

### 分散式追蹤的上下文怎麼跨服務傳遞？

**核心答案**：跨執行緒靠上下文機制，**跨服務則靠協定的標頭**。業界標準是 **W3C Trace Context**（`traceparent` 與 `tracestate` 兩個 HTTP 標頭），OpenTelemetry 的實作會在**出站呼叫時注入**（inject）標頭、在**入站時擷取**（extract）並放進當前執行緒的上下文。訊息佇列則放在訊息的標頭或屬性裡。

**詳細解析**：完整的鏈路需要**每一個環節都不斷鏈**，而最常斷的三個地方是：**非同步邊界**（提交到執行緒池、`CompletableFuture` 的回呼）、**訊息佇列**（生產者沒注入或消費者沒擷取）、以及**沒有被檢測的第三方元件**。實務上的檢查方法是**刻意產生一條跨越所有元件的請求，看追蹤系統裡的鏈路是否完整**，而不是假設它會自動運作。另外要注意**取樣**：全量追蹤的成本很高，通常會取樣（例如 1%），**但取樣決定必須在鏈路開頭做並沿著標頭傳遞**，否則會出現「一半的服務記錄了、另一半沒記」的破碎鏈路。錯誤與慢請求則常用「尾部取樣」——先全部收集，在鏈路結束後才決定要不要保留，這樣不會漏掉真正需要的樣本。

**面試回答方式**：先區分兩個層次——跨執行緒用上下文機制、跨服務用協定標頭（W3C Trace Context 的 `traceparent`），並說明注入與擷取的流程。重點放在**最常斷鏈的三個地方**（非同步邊界、訊息佇列、未檢測的第三方）與驗證方法：刻意產生一條跨全元件的請求檢查鏈路完整性。加分點是取樣的兩個要點：**取樣決定要在鏈路開頭做並沿標頭傳遞**（否則鏈路破碎），以及尾部取樣讓錯誤與慢請求不會被漏掉。
