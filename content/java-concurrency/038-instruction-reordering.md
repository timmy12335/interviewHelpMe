# 題目

誰會重排序指令？既然重排序會造成併發問題，為什麼不乾脆禁止它？

## 核心答案

重排序發生在**三個層次**，而且它們是獨立的。**編譯器重排序**——javac 與 JIT 在不改變單執行緒語意的前提下調整順序（例如把迴圈不變的計算提到迴圈外）。**處理器指令級重排序**——現代 CPU 亂序執行，把後面不依賴前面結果的指令先執行。**記憶體系統重排序**——存放緩衝區（store buffer）與失效佇列讓寫入不立即對其他核心可見，看起來像是順序被調換了。

不禁止它的原因是**效能損失無法接受**。順序執行意味著每次記憶體存取都要等待完成、每次分支都要等待結果、CPU 的多個執行單元大部分時間閒置——**現代處理器的效能有很大一部分正是來自亂序執行與快取**，禁止之後可能損失一個數量級。

真正的設計是**「預設允許重排序，需要順序時明確要求」**：as-if-serial 保證單執行緒下結果不變，跨執行緒的順序則要透過 happens-before 規則（volatile、synchronized、final、以及執行緒的啟動與結束）明確建立。**成本只在需要的地方付出**，這是整個 JMM 的核心設計取捨。

## 詳細解析

**as-if-serial 只保證單執行緒**，這是最關鍵的界線。它的規則是「有資料依賴的操作不能重排」——`a = 1; b = a + 1;` 不會被調換。但 `a = 1; b = 2;` 這種沒有依賴的可以任意調換，而在多執行緒下，另一個執行緒可能看到 `b == 2` 卻 `a == 0`。**單執行緒的正確性與多執行緒的可見性是兩個完全不同的問題，as-if-serial 只管前者。**

**記憶體屏障是實作 happens-before 的手段**。JMM 定義了四種概念性的屏障：`LoadLoad`、`StoreStore`、`LoadStore`、`StoreLoad`，其中 **`StoreLoad` 最昂貴**（它要求把存放緩衝區排空，等待寫入真正可見）。volatile 寫入之後、讀取之前都需要 `StoreLoad`，這也是 volatile 寫比普通寫貴得多的原因。在 x86 上，處理器本身已經提供了較強的順序保證（只允許 StoreLoad 重排），所以 JVM 只需要在 volatile 寫入後插入一條 `lock addl` 之類的指令；在 ARM 這種弱記憶體模型的架構上，需要插入的屏障多得多——**同一段 Java 程式碼在不同架構上的併發成本差異可能很大**。

**弱記憶體模型的實務意義**：在 x86 上跑得好好的併發程式碼，換到 ARM（Apple Silicon、AWS Graviton）上可能暴露出隱藏的競態。因為 x86 的強順序「意外地」修正了一些缺少同步的錯誤。**這是近年真實發生的事**——很多團隊在遷移到 ARM 伺服器時才發現長年潛伏的併發 bug。所以**不能用「在我們的機器上跑了三年沒問題」來論證併發正確性**，正確性必須來自對 happens-before 的推理，不是來自經驗。

**JMM 的價值在於它是一份與硬體無關的契約**：只要按照 happens-before 規則寫，程式在任何符合規範的 JVM 與任何架構上都正確。**這是 Java 相對於 C++11 之前的一大優勢**——那時 C++ 沒有語言層級的記憶體模型，跨平台的併發程式碼只能依賴平台特定的知識。

## 面試回答方式

先給**三個獨立的重排序層次**（編譯器、處理器亂序執行、存放緩衝區造成的記憶體系統重排序），這比籠統說「會重排序」有結構。接著回答「為什麼不禁止」——**現代處理器的效能有很大一部分來自亂序執行與快取，禁止可能損失一個數量級**，所以設計是「預設允許、需要時明確要求」，成本只在需要的地方付出。然後劃出關鍵界線：**as-if-serial 只保證單執行緒**，`a=1; b=2;` 可以任意調換，跨執行緒的順序必須靠 happens-before 建立。加分點有兩個：**`StoreLoad` 是最昂貴的屏障**，這解釋了 volatile 寫為什麼特別貴；以及**x86 的強順序會意外掩蓋缺少同步的錯誤，遷移到 ARM 時才暴露**——所以「跑了三年沒問題」不能用來論證併發正確性。

## 講稿

重排序發生在三個層次，而且是獨立的。編譯器在不改變單執行緒語意的前提下調整順序。處理器亂序執行，把後面不依賴前面結果的指令先做。還有記憶體系統，存放緩衝區讓寫入不立即對其他核心可見，看起來也像順序被調換。

為什麼不乾脆禁止？因為效能損失無法接受。順序執行意味著每次記憶體存取都要等完成、每次分支都要等結果，現代處理器的效能有很大一部分正是來自亂序執行跟快取。

所以真正的設計是預設允許重排序，需要順序的時候明確要求。單執行緒的結果由 as-if-serial 保證，跨執行緒則要透過 happens-before 規則建立。成本只在需要的地方付出。

這裡有一條關鍵界線。as-if-serial 只管單執行緒。兩個沒有資料依賴的賦值可以任意調換，而在多執行緒下另一個執行緒可能看到第二個已經寫了、第一個還沒。

還有一件實務上真的發生的事。x86 的順序保證比較強，意外地掩蓋了一些缺少同步的錯誤。很多團隊遷移到 ARM 伺服器的時候，才發現潛伏多年的併發問題。所以跑了三年沒事不能用來論證併發正確性。

## 常見追問

### happens-before 到底是什麼關係？它保證了什麼？

**核心答案**：它是一個**偏序關係**，定義在「操作」之間。如果操作 A happens-before 操作 B，那麼 **A 的所有寫入結果對 B 都是可見的，而且 A 在 B 之前的順序是確定的**。要注意它**不是「時間上更早」**——時間上更早但沒有 happens-before 關係的兩個操作，彼此的結果可能互相看不到。它是一個**語意上的保證**，不是時鐘上的先後。

**詳細解析**：核心規則有六條：**程式順序**（同一執行緒內按程式碼順序）、**監視器鎖**（解鎖 happens-before 之後對同一把鎖的加鎖）、**volatile**（寫 happens-before 之後的讀）、**執行緒啟動**（`start()` happens-before 新執行緒的任何操作）、**執行緒終止**（執行緒的所有操作 happens-before 其他執行緒從 `join()` 返回）、**傳遞性**（A→B 且 B→C 則 A→C）。**傳遞性是最有用的一條**——它讓「用 volatile 旗標發布一批普通變數的寫入」成立：先寫普通變數、再寫 volatile 旗標，讀取端先讀旗標、再讀普通變數，透過傳遞性就保證看得到全部。這正是很多無鎖模式的基礎。

**面試回答方式**：先給精確定義並強調它**不是「時間上更早」而是語意保證**——這是最常見的誤解。列出六條核心規則。真正的加分點是展開**傳遞性的實際用途**：先寫普通變數、再寫 volatile 旗標，讀取端反過來讀，透過傳遞性就能安全發布一整批寫入——這是很多無鎖模式的基礎，比逐條背規則有價值得多。

### 為什麼 volatile 的寫比讀貴這麼多？

**核心答案**：因為兩者需要的屏障不同。**volatile 讀**只需要在讀之後插入 `LoadLoad` 與 `LoadStore` 屏障，在 x86 上這些**不需要任何額外指令**（處理器本身就保證），所以 volatile 讀的成本幾乎等於普通讀。**volatile 寫**則需要在寫之後插入 **`StoreLoad`** 屏障——這是唯一一個 x86 也不保證的重排序方向，必須用一條實際的指令（`lock addl $0, (%rsp)` 或 `mfence`）強制排空存放緩衝區並等待完成，成本是數十個週期。

**詳細解析**：這個不對稱有實際的設計意義：**volatile 適合「一寫多讀」的場景**——狀態旗標、設定物件的引用、單次初始化的結果。讀取端幾乎不付成本，寫入端的成本只在稀少的更新時付出。反過來，**高頻寫入的 volatile 變數會成為明顯的瓶頸**（例如用 volatile 計數器統計 QPS），這種情況該用 `LongAdder`。**理解「讀便宜寫貴」比記住 volatile 的兩個保證更有實務價值**，因為它直接指導了什麼資料適合用 volatile。另外要注意 volatile 寫的成本還包括**使其他核心的快取失效**，所以爭用越多、成本越高，這與偽共享是同一個機制。

**面試回答方式**：給出不對稱的具體原因——讀只需要 x86 本來就保證的屏障、寫需要 `StoreLoad` 這個唯一不被保證的方向，必須用實際指令排空存放緩衝區。然後給實務推論：**volatile 適合一寫多讀**（旗標、設定引用），**高頻寫入會成為瓶頸**（該用 `LongAdder`）。加分點是指出寫的成本還包括使其他核心快取失效，所以爭用越多成本越高——與偽共享是同一個機制。

### 怎麼驗證一段併發程式碼真的沒有記憶體可見性問題？

**核心答案**：**不能靠測試，只能靠推理加上專門工具**。一般的壓力測試在 x86 上幾乎測不出可見性問題（強記憶體模型掩蓋了大部分），而且競態的觸發機率極低。正確的方法有三層：**第一，用 happens-before 規則做論證**——寫下「哪個寫入透過什麼關係對哪個讀取可見」；**第二，用 jcstress**（JDK 官方的併發壓力測試工具），它會生成極端的交錯、在弱記憶體模型上測試、並窮舉所有可能的結果；**第三，在 ARM 機器上跑**，因為它的弱順序會暴露 x86 掩蓋的問題。

**詳細解析**：jcstress 的價值在於它**列舉所有觀察到的結果並標記哪些是規範允許的**——如果出現了規範不允許的結果，就確定有 bug；如果某個「可疑但合法」的結果從未出現，也不代表安全（只是這台機器沒觸發）。**這正好說明了併發正確性的本質：它是一個關於「所有可能執行」的性質，而測試只能取樣其中極少數。** 所以工程實務上更重要的是**降低需要推理的表面積**——多用不可變物件、多用 JDK 提供的併發工具、把共享可變狀態集中在少數幾個經過仔細審查的類別裡。**「不需要推理的程式碼」永遠比「推理正確的程式碼」可靠。**

**面試回答方式**：先給明確立場——**不能靠測試**，x86 的強順序會掩蓋問題且觸發機率極低。給三層方法（happens-before 論證、jcstress、在 ARM 上測）並說明 jcstress 的機制（列舉結果並標記規範是否允許）。真正的加分點是點出併發正確性的本質——**它是關於「所有可能執行」的性質，測試只能取樣**，因此工程上更重要的是**降低需要推理的表面積**：多用不可變、多用現成工具、把共享狀態集中在少數經審查的類別裡。
