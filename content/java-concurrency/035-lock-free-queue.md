# 題目

`ConcurrentLinkedQueue` 是怎麼在沒有鎖的情況下保證正確的？無鎖一定比有鎖快嗎？

## 核心答案

它實作的是 **Michael-Scott 無鎖佇列**：一個單向鏈結串列，`head` 與 `tail` 都是 volatile 引用，所有更新都用 CAS。核心技巧是**把「入隊」拆成兩個獨立的 CAS**——先 CAS 尾節點的 `next` 指標把新節點掛上去，再 CAS 移動 `tail`。

關鍵在於**第二步允許失敗且允許被別人代勞**：`tail` 可能暫時落後於真正的尾端，任何執行緒發現這件事時都會**幫忙推進它**再繼續自己的操作。這就是**無等待的協助機制（helping）**——不需要「誰負責修好它」，任何看到不一致中間狀態的執行緒都有義務先把它推進到一致。這讓演算法即使在某個執行緒被作業系統掛起的情況下，整體仍然能繼續前進。

**無鎖不等於更快**。它保證的是**系統整體有進展**（lock-free：至少有一個執行緒能完成操作），而不是每個操作更快。高爭用下 CAS 會大量失敗重試，**浪費的 CPU 可能比阻塞掛起還多**；而且無鎖結構的 `size()` 通常是 O(n) 且不精確。

## 詳細解析

**「允許中間狀態」是無鎖設計的核心思想**。有鎖的資料結構在鎖內部可以有任意的中間狀態，因為別人看不到；無鎖結構沒有這個保護，所以它必須設計成**每個中間狀態對其他執行緒都是可辨識且可修復的**。Michael-Scott 佇列的做法是讓 `tail` 落後最多一個節點，任何人看到都知道該怎麼修。**這個「狀態機的每一步都對外可見且合法」的要求，是無鎖演算法難寫的根本原因。**

**ABA 問題在這裡被 Java 的 GC 化解了**。C 語言實作 Michael-Scott 佇列必須用帶版本號的指標，因為節點記憶體被釋放後可能被重新配置到同一個位址，CAS 會誤判成沒變過。Java 有 GC——**只要有執行緒還持有某個節點的引用，那塊記憶體就不會被重用**，所以位址相同必然代表是同一個節點。**GC 在這裡不只是方便，它是演算法正確性的一部分**，這是一個很少被提及但很有意思的點。

**`size()` 是 O(n) 而且不精確**：它要走過整條串列數，而走的過程中別人還在改。文件明確建議**不要用它做流程控制**，判斷是否為空要用 `isEmpty()`（只看 head，是 O(1)）。這是無鎖結構的通性——**全域性的資訊（大小、總和）與局部無鎖的設計本質衝突**，要精確的全域資訊就要某種形式的同步。

**它是無界的**，這在實務上是最需要注意的一點。`ConcurrentLinkedQueue` 沒有容量限制、也沒有阻塞方法（沒有 `put`／`take`），所以**它不能用來實作背壓**——生產快於消費就是無限成長到 OOM。需要有界與阻塞時應該用 `ArrayBlockingQueue` 或 `LinkedBlockingQueue`。**它的正確定位是「高吞吐、消費者能跟上、且不需要阻塞語意」的場景**，例如事件的收集與轉發。

## 面試回答方式

先講機制：**Michael-Scott 佇列把入隊拆成兩個 CAS**，先掛節點再推 `tail`，而**第二步允許失敗並由任何執行緒代勞**——這個「協助機制」是整個演算法的關鍵。接著給無鎖設計的核心思想：**每個中間狀態都必須對其他執行緒可辨識且可修復**，這是它難寫的根本原因。然後主動澄清最大的誤解——**無鎖不等於更快**，它保證的是系統整體有進展，高爭用下 CAS 大量重試浪費的 CPU 可能比掛起還多。加分點是 **ABA 問題被 GC 化解**：只要還有人持有引用記憶體就不會被重用，所以位址相同必然是同一節點，**GC 在這裡是演算法正確性的一部分**。最後給實務定位：它**無界且無阻塞方法，不能用來做背壓**，適合消費者跟得上的高吞吐轉發場景。

## 講稿

它實作的是 Michael-Scott 無鎖佇列。核心技巧是把入隊拆成兩個獨立的 CAS，先把新節點掛到尾節點後面，再移動尾指標。

關鍵在於第二步允許失敗，而且允許被別人代勞。尾指標可能暫時落後於真正的尾端，任何執行緒發現這件事的時候都會幫忙把它推進，然後才繼續自己的操作。這就是協助機制。這讓演算法就算某個執行緒被作業系統掛起，整體還是能繼續前進。

我覺得無鎖設計的核心思想是允許中間狀態。有鎖的結構在鎖裡面可以有任意中間狀態，因為別人看不到。無鎖沒有這個保護，所以每個中間狀態都必須對其他執行緒是可辨識而且可修復的。這是它難寫的根本原因。

有一個有意思的點。ABA 問題在這裡被垃圾回收化解了。C 語言的實作必須用帶版本號的指標，因為記憶體釋放後可能被重新配置到同一個位址。Java 有 GC，只要還有人持有引用那塊記憶體就不會被重用。所以 GC 在這裡是演算法正確性的一部分。

最後提醒，它是無界的而且沒有阻塞方法，所以不能用來做背壓。

## 常見追問

### 無鎖、無等待、無阻塞這幾個詞有什麼區別？

**核心答案**：三個層次的漸強保證。**無阻塞（obstruction-free）**最弱——單獨執行時任一執行緒都能在有限步驟內完成（但多個執行緒可能互相干擾導致誰都完不成）。**無鎖（lock-free）**保證**系統整體有進展**——任何時刻至少有一個執行緒能完成操作，但個別執行緒可能一直重試失敗（飢餓）。**無等待（wait-free）**最強——**每個執行緒都能在有限步驟內完成**，沒有飢餓，但實作代價很高。

**詳細解析**：`ConcurrentLinkedQueue` 是無鎖但不是無等待——某個倒楣的執行緒可能一直 CAS 失敗。實務上**無等待的資料結構很少見**，因為要達成它通常需要「協助機制」的完整版本（每個執行緒不只修復狀態，還要幫別人完成整個操作），複雜度與常數成本都高得多。**這三個詞真正的價值在於描述「最壞情況的保證」**：無鎖保證系統不會整體卡住（不會死鎖），無等待額外保證公平性。選擇資料結構時該問的是「我的場景在乎的是整體吞吐還是最壞延遲」——在乎最壞延遲（即時系統、交易系統的尾延遲）才值得付出無等待的代價。

**面試回答方式**：把三個層次由弱到強講清楚，各給一句精確的保證內容。指出 `ConcurrentLinkedQueue` 是無鎖但不是無等待（個別執行緒可能飢餓）。加分點是說明無等待為什麼罕見（需要完整的協助機制，複雜度與常數成本高），並給出選擇的判準：**在乎整體吞吐用無鎖就好，在乎最壞延遲（尾延遲敏感的系統）才值得付出無等待的代價**。

### 什麼時候該用有鎖的資料結構而不是無鎖的？

**核心答案**：三種情況。**高爭用**——CAS 失敗重試會白燒 CPU，而阻塞會讓執行緒讓出處理器給別人用；爭用嚴重時有鎖反而吞吐更高。**臨界區長**——無鎖要求每個操作是單一的 CAS 或可重試的短序列，複雜的多步驟更新根本寫不成無鎖。**需要複合操作的原子性**——「檢查後執行」跨多個資料結構時，無鎖結構各自的原子性拼不出整體的原子性，必須用鎖。

**詳細解析**：還有一個常被忽略的維度是**可讀性與可維護性**。無鎖程式碼的正確性論證非常困難，一個看似無害的修改就可能引入極難重現的競態。**團隊中能正確審查無鎖程式碼的人通常很少**，這讓它的長期成本遠高於初始的效能收益。務實的原則是：**優先用 JDK 提供的併發資料結構（它們已經被驗證過），不要自己寫無鎖結構**；真的需要時，先確認有鎖版本經過量測確實是瓶頸，並準備好完整的併發測試（jcstress 這類工具）。**「不要自己寫無鎖資料結構」在絕大多數團隊裡是正確的建議**，這比討論任何技術細節都實用。

**面試回答方式**：給三種技術情況（高爭用、臨界區長、需要跨結構的複合原子性）並各配一句理由。然後補上最實用的一個維度——**可讀性與可維護性**：無鎖的正確性論證極困難、能審查的人很少，長期成本高於初始收益。收在一條明確的建議：**優先用 JDK 已驗證的結構，不要自己寫無鎖**，真的要寫先量測確認瓶頸並準備 jcstress 這類併發測試。

### CAS 的重試迴圈要注意什麼？

**核心答案**：三點。**每一輪都必須重新讀取當前值**——用上一輪讀到的舊值去計算新值，就是典型的錯誤。**要有退讓機制**——高爭用下純粹的忙迴圈會讓所有執行緒互相干擾，加入 `Thread.onSpinWait()`（JDK 9，提示處理器這是自旋）或有限次數後改為阻塞，能明顯改善。**要考慮迴圈不終止的風險**——理論上某個執行緒可能永遠失敗，實務上如果觀察到某些操作的延遲極長，這就是嫌疑之一。

**詳細解析**：`AtomicReference.updateAndGet` 與 `AtomicInteger.accumulateAndGet` 這類方法已經封裝了正確的重試迴圈（包括重新讀取），**能用它們就不要自己寫**。要注意傳入的函式**必須是純函式且無副作用**——它可能被呼叫多次（每次重試一次），如果裡面有計數、日誌或外部呼叫，就會重複執行。這是一個很容易踩的坑：程式碼看起來只執行一次，實際上在高爭用下可能執行了十次。**同樣的注意事項適用於 `ConcurrentHashMap.compute` 與 `merge` 的重映射函式**，它們也可能被重試。

**面試回答方式**：給三點（重新讀取、退讓機制、不終止風險），並具體提到 `Thread.onSpinWait`。真正的加分點是後半段：**能用 `updateAndGet` 這類封裝好的方法就不要自己寫迴圈**，但要注意傳入的函式**可能被呼叫多次**，所以必須是純函式無副作用——裡面有計數、日誌或外部呼叫就會重複執行。並指出 `ConcurrentHashMap.compute` 與 `merge` 有同樣的注意事項。
