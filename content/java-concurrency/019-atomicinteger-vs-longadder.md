# 題目

高並發計數場景下，為什麼 `LongAdder` 通常比 `AtomicLong`/`AtomicInteger` 效能更好？它的原理是什麼？

## 核心答案

`AtomicInteger`/`AtomicLong` 用單一個變數配合 CAS 自旋更新，高並發下大量執行緒會集中競爭同一個記憶體位置，CAS 失敗率隨並發數上升而急遽增加。`LongAdder` 用「分段累加」的思路，把熱點資料拆分成多個 `Cell` 槽位，不同執行緒盡量寫入不同的槽位分散競爭，最後需要總和時才把所有槽位加總，大幅降低了高並發下的 CAS 競爭衝突。

## 詳細解析

**`AtomicInteger` 的瓶頸**：`incrementAndGet()` 是 CAS 自旋迴圈，並發執行緒增加時 CAS 失敗率上升，吞吐量無法隨執行緒數線性提升。

**`LongAdder` 的分段累加設計**：內部維護一個 `base` 值加上一個 `Cell[]` 陣列。沒有競爭時對 `base` 做 CAS 累加；一旦偵測到競爭，就分散到 `Cell[]` 陣列中的某個槽位。需要總和時（`sum()`）才把 `base` 與所有 `Cell` 加總，這是一個近似值而非即時精確值。

**為什麼適合「高並發寫入、低頻率讀取總和」的場景**：空間換時間、分散熱點，犧牲一點記憶體與讀取即時精確性，換取寫入在高並發下幾乎不會互相競爭。

**偽共享（False Sharing）的處理**：`Cell` 類別做了記憶體填充，確保不同 `Cell` 不會落在同一個 CPU 快取行。

**如何選擇**：低並發且需要絕對精確即時值用 `AtomicLong`；高並發寫入、偶爾讀總和用 `LongAdder`。

## 面試回答方式

這是這批題目中理論密度最高的一題，建議用「問題 → 解法 → 代價」的結構回答：先講清楚 `AtomicInteger` 在高並發下的瓶頸是什麼（CAS 競爭同一記憶體位置），再講 `LongAdder` 怎麼解決（分段累加、分散熱點），最後主動點出代價（`sum()` 只是近似值、犧牲一點記憶體）。「偽共享」是這題很容易被追問、也是最容易展現深度的細節，建議主動提一句「`Cell` 有做記憶體填充避免偽共享」，即使面試官沒問，這種主動補充細節的答法很容易讓人留下深刻印象。

## 常見追問

### 什麼是偽共享（False Sharing）？除了 LongAdder，還有哪裡也用到了類似的快取行填充技巧？

**核心答案**：偽共享是指多個執行緒各自修改邏輯上互不相關的變數，但這些變數剛好被分配在同一個 CPU 快取行（cache line，通常是 64 位元組）內，導致 CPU 的快取一致性協定（如 MESI）誤判為「這些變數互相衝突」，頻繁地讓其他核心的快取失效並重新載入，造成不必要的效能損耗；除了 `LongAdder` 的 `Cell` 類別，JDK 中的 `ConcurrentHashMap` 的計數器 `CounterCell`、`Exchanger` 內部的槽位陣列，以及 Disruptor 這類高效能框架的環形緩衝區實作，都用了類似的記憶體填充技巧。

**詳細解析**：CPU 讀寫記憶體是以快取行為單位進行的，即使兩個變數在程式邏輯上完全獨立，只要它們的記憶體位址剛好落在同一個 64 位元組區塊內，一個 CPU 核心修改其中一個變數，就會讓持有這個快取行副本的其他核心，即使它們關心的是另一個變數，也必須讓自己的快取失效並重新從主記憶體或其他核心同步這個快取行，這個過程對高頻寫入的並行程式而言是顯著的效能損耗。解法是在資料結構中刻意加入填充欄位（padding），讓每個真正需要獨立存取的變數各自佔滿一整個快取行，確保不同執行緒操作的變數實體上不會共享快取行。

**面試回答方式**：先用「CPU 讀寫是以快取行為單位」這個硬體背景解釋為什麼會有偽共享問題，再舉出「填充欄位讓每個變數獨佔一個快取行」的解法，最後列出一兩個除了 `LongAdder` 之外也用到這個技巧的例子（如 Disruptor），展現你的知識面不局限在單一 API。

### LongAdder.sum() 為什麼不是強一致的？在什麼場景下這種弱一致性是可以接受的？

**核心答案**：因為 `sum()` 執行的過程是「依序讀取 `base` 和每個 `Cell` 的當前值再加總」，這個讀取過程本身不是原子操作，如果在加總的同時，其他執行緒仍在對某些 `Cell` 進行寫入，得到的總和可能無法反映「絕對某一個時間點」上的精確值；這種弱一致性在只需要「大致趨勢」而非「絕對精確瞬時值」的統計監控場景是完全可以接受的，例如接口呼叫次數統計、QPS 監控指標。

**詳細解析**：這種弱一致性本質上是用「一致性強度」換取「並發寫入效能」的典型取捨，和前面提到的 `CopyOnWriteArrayList`（見 [[015-copyonwritearraylist.md]]）用弱一致性換取無鎖讀取是同一種設計哲學。在實務場景中，像 QPS、呼叫次數這類監控指標的價值在於觀察**趨勢與量級**（例如「這個接口這一分鐘大概被呼叫了 10 萬次」），而不是要求「精確到某一奈秒的絕對數字」，因此偶爾讀到的總和比實際值略有出入（在高並發下差距通常極小）完全不影響這類指標的實用價值；但如果場景是「銀行帳戶餘額」這種要求絕對精確、且必須反映某一時刻確切狀態的資料，就完全不適合用 `LongAdder` 這種弱一致性的工具，應該用 `synchronized`、`ReentrantLock` 或資料庫交易保證強一致性。

**面試回答方式**：用「監控指標關心趨勢、帳務資料要求精確」這組對比清楚劃出 `LongAdder` 適用與不適用的邊界，這種能明確指出「什麼時候不該用」的回答，往往比只講「什麼時候該用」更能展現成熟的技術判斷力。

### LongAccumulator 和 LongAdder 有什麼關係？

**核心答案**：`LongAdder` 是 `LongAccumulator` 針對「加法運算」的特化版本；`LongAccumulator` 是更通用的分段累加工具，可以透過建構子傳入任意的 `LongBinaryOperator`（二元運算函式）自訂累加邏輯，不限於加法，例如可以用來做分段累加取最大值、取最小值等場景。

**詳細解析**：`LongAdder` 內部其實可以視為 `LongAccumulator` 在「運算子固定為加法、初始值固定為 0」情境下的簡化實作（雖然兩者在 JDK 原始碼中是各自獨立實作，共用同一個抽象基底類別 `Striped64` 提供分段累加的核心機制，但概念上 `LongAdder` 就是 `LongAccumulator` 的一個特例）。當需求不只是「累加次數」，而是例如「記錄目前為止觀察到的最大延遲時間」這種需要自訂合併邏輯的統計場景，`LongAccumulator` 允許傳入 `(x, y) -> Math.max(x, y)` 這樣的運算子，同樣享受分段累加減少競爭的效能優勢，但適用範圍比只能做加法的 `LongAdder` 更廣。

**面試回答方式**：直接點出「`LongAdder` 是 `LongAccumulator` 的加法特化版本，兩者共用 `Striped64` 這個分段累加的抽象基底」，並舉一個 `LongAccumulator` 用於「取最大值」而非單純計數的例子，展現你知道這一整個家族工具的設計脈絡，而不只認識最常用的那一個類別。
