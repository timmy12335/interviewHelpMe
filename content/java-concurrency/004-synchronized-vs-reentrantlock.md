# 題目

`synchronized` 和 `ReentrantLock` 有什麼差異？什麼情況該選哪一個？

## 核心答案

兩者都提供互斥鎖語義且都支援可重入，但 `ReentrantLock` 是 API 層級（`java.util.concurrent.locks`）的顯式鎖，功能更豐富（可中斷、可設定逾時、可實作公平鎖、支援多個 `Condition`），需要手動 `lock()/unlock()`；`synchronized` 是 JVM 層級的關鍵字，由編譯器與 JVM 自動管理加解鎖，語法更簡潔且不會忘記釋放鎖。

## 詳細解析

**共同點**：

- 都是可重入鎖（同一執行緒可重複取得同一把鎖）。
- 都能保證互斥與（配合 JMM）可見性。

**差異點**：

| 面向 | synchronized | ReentrantLock |
|------|---------------|----------------|
| 鎖釋放 | JVM 自動釋放，即使拋出例外也會釋放 | 必須手動在 `finally` 中呼叫 `unlock()`，否則死鎖 |
| 可中斷 | 不支援，執行緒阻塞後無法被中斷 | 支援 `lockInterruptibly()`，等待鎖過程中可回應中斷 |
| 逾時等待 | 不支援 | 支援 `tryLock(timeout, unit)` |
| 公平性 | 不保證公平（重量級鎖狀態下由 OS 排程） | 可選擇公平鎖或非公平鎖（建構子參數） |
| 條件變數 | 只有一組隱式的 wait-set | 可透過 `newCondition()` 建立多組等待佇列，做更精細的執行緒喚醒 |
| 效能 | JDK 6 後鎖升級機制優化了低競爭場景效能，目前與 ReentrantLock 差異不大 | 基於 AQS 實作，高競爭下表現穩定 |

**選型建議**：

- 大多數簡單同步場景，優先用 `synchronized`：語法簡潔、不會忘記釋放鎖、JVM 已充分優化。
- 需要「嘗試取鎖但不阻塞」「可設定逾時」「可回應中斷」「需要公平鎖語意」「需要多組等待條件（例如生產者/消費者用不同 Condition 區分佇列滿/空）」時，選 `ReentrantLock`。

**踩坑提醒**：使用 `ReentrantLock` 時，必須把 `unlock()` 放在 `finally` 區塊，且 `lock()` 呼叫要放在 `try` 之前（不能放進 `try` 裡），否則加鎖失敗時仍會嘗試釋放一把沒有持有的鎖，拋出 `IllegalMonitorStateException`。

## 面試回答方式

這是一題「二選一比較題」，最好的結構是「先講共同點、再用表格式的差異點逐項比較、最後給選型建議」。共同點只要一句話帶過（都可重入、都保證互斥）即可，不用花時間；差異點挑 3-4 個最實務的維度講（可中斷、逾時、公平鎖、Condition），比背出全部差異更聚焦。最重要的是最後一定要給出「什麼情況選哪個」的具體建議，因為這才是面試官真正想確認的——你是否有能力做技術選型，而不只是背 API 差異。如果時間夠，補一句 `unlock()` 要放 `finally` 的踩坑提醒，會顯示你有實戰經驗而非只讀過文件。

## 常見追問

### ReentrantLock 的公平鎖是如何實作的？

**核心答案**：公平鎖在嘗試取鎖前，會先呼叫 AQS 的 `hasQueuedPredecessors()` 檢查等待佇列中是否已經有排在自己之前的執行緒，如果有就不搶佔、乖乖排隊；非公平鎖則省略這個檢查，直接嘗試 CAS 搶鎖。

**詳細解析**：這題的完整分析在 [[005-reentrantlock-fair-vs-unfair.md]] 中有詳細說明。核心是：`ReentrantLock` 的公平性差異只體現在「取鎖那一刻要不要檢查佇列」這一行程式碼的差異，其餘的排隊、阻塞、喚醒邏輯完全共用同一套 AQS 機制。這也是為什麼理解 AQS 之後，很多看似複雜的同步工具行為差異，其實都能歸結成「`tryAcquire` 這個方法裡多了哪一行判斷」。

**面試回答方式**：能講出 `hasQueuedPredecessors()` 這個具體方法名稱，會比只說「公平鎖會排隊、非公平鎖會搶」更有說服力，代表你真的看過原始碼而非只讀過概念文章。

### ReentrantReadWriteLock 解決了什麼問題？

**核心答案**：解決「讀多寫少」場景下，普通互斥鎖讓多個只讀操作也必須互相排隊等待的效能浪費問題——讀鎖之間可以共享（多個執行緒同時持有讀鎖），寫鎖仍然是互斥的（且與讀鎖互斥）。

**詳細解析**：`ReentrantReadWriteLock` 內部維護一組讀鎖與一組寫鎖，語意是「讀-讀不衝突、讀-寫互斥、寫-寫互斥」。它同樣基於 AQS 實作，巧妙地用同一個 `state` 的高 16 位表示讀鎖持有數量、低 16 位表示寫鎖的重入次數，用位元運算拆分同一個狀態值來同時管理兩種鎖語意。適合「讀取頻繁、寫入極少」的共享資料場景（例如快取、設定檔），比起把所有存取都用一把互斥鎖保護，能大幅提升讀取的並行度。若讀寫都很頻繁，或者需要更細緻的樂觀讀取，可以考慮 JDK 8 引入的 `StampedLock`。

**面試回答方式**：先用一句話點出「讀讀不衝突、讀寫互斥」這個核心語意，再視情況延伸到底層用 `state` 的高低位拆分實作，最後可以主動提一句 `StampedLock` 作為更進階的替代方案，展現你知道技術的演進脈絡。

### 為什麼公平鎖通常吞吐量比非公平鎖低？

**核心答案**：因為公平鎖強制所有執行緒按順序排隊，即使鎖已經釋放、新來的執行緒有機會立即搶佔並開始工作，也必須讓路給佇列中排隊更久的執行緒，這中間會有喚醒延遲導致的鎖閒置時間。

**詳細解析**：這題與 [[005-reentrantlock-fair-vs-unfair.md]] 中「非公平鎖為什麼吞吐量更高」是同一個問題的兩種問法。核心邏輯是：執行緒被喚醒到真正重新開始執行之間存在 CPU 排程延遲，這段時間鎖其實是空閒的；非公平鎖允許新來的執行緒直接搶佔這段空窗期，減少鎖閒置時間；公平鎖為了保證順序，寧可讓鎖空閒也要等排隊中的執行緒被正式喚醒，因此吞吐量較低，但换來了執行緒不會被餓死的公平性保證。

**面試回答方式**：如果之前已經完整回答過公平鎖與非公平鎖的機制題，這裡可以直接說「本質上和剛剛講的是同一個機制，換個角度問」，然後用一句話重申結論即可，不需要重複整段解釋，展現你能辨識出問題背後是同一個知識點。
