# 題目

`ArrayBlockingQueue`、`LinkedBlockingQueue`、`SynchronousQueue`、`PriorityBlockingQueue` 有什麼差異？各自適合什麼場景？

## 核心答案

`ArrayBlockingQueue` 是有界佇列，底層陣列，一把鎖控制存取；`LinkedBlockingQueue` 預設無界，底層鏈結串列，讀寫可用兩把鎖分離提升並行度；`SynchronousQueue` 本身不儲存任何元素，每個 `put` 必須配對一個 `take` 才能完成；`PriorityBlockingQueue` 是無界的優先級佇列，元素按照優先級出列而非先進先出。

## 詳細解析

**`ArrayBlockingQueue`**：底層固定大小陣列，讀寫共用同一把鎖，同一時間只能有一個執行緒在存取。適合需要明確控制記憶體上限的場景。

**`LinkedBlockingQueue`**：底層鏈結串列，讀鎖與寫鎖分開（`takeLock`、`putLock`），並行度比 `ArrayBlockingQueue` 高。若不指定容量預設等同無界，需注意 OOM 風險。

**`SynchronousQueue`**：本質上是「執行緒對執行緒」的直接交接點，不是真正的儲存容器。`Executors.newCachedThreadPool()` 就是用它。

**`PriorityBlockingQueue`**：底層用二元堆實作，元素出列順序由 `Comparable`/`Comparator` 決定，而非先進先出。

**選型速查表**：需要嚴格控制記憶體用 `ArrayBlockingQueue`；高吞吐讀寫分離（Read-Write Splitting）用 `LinkedBlockingQueue`；需要立即交接用 `SynchronousQueue`；需要按優先級處理用 `PriorityBlockingQueue`。

## 面試回答方式

四選一比較題最容易講成流水帳，建議先用一句話點出核心差異軸——「有沒有容量上限」「鎖的粒度」「排隊順序」，再逐一對應到四個實作類別上。每個實作講完立刻補一個典型使用場景（尤其 `SynchronousQueue` 一定要提到它是 `newCachedThreadPool` 的底層佇列，這個連結很容易被追問），最後用選型速查表收尾。這種「先給框架、再填內容、最後給決策依據」的結構，是回答任何「多選一比較題」的通用模板。

## 常見追問

### SynchronousQueue 有公平模式和非公平模式，兩者實作機制有何不同？

**核心答案**：非公平模式（預設）底層用一個棧（stack）結構管理等待的執行緒，後到的等待者會先被配對（後進先出）；公平模式底層改用佇列（queue）結構，讓等待的執行緒按照先來後到的順序被配對（先進先出）。

**詳細解析**：這個差異的原因和資料結構的存取特性有關：非公平模式選擇棧是因為它在某些情境下能提供更好的快取局部性與更低的競爭（最近加入的執行緒最有可能還在 CPU 快取中），犧牲了公平性換取吞吐量，這與 `ReentrantLock` 非公平鎖的設計哲學是一致的；公平模式選擇佇列則是為了保證嚴格的先進先出順序，避免某些等待者被無限期跳過而飢餓。這也再次印證了「公平性 vs 吞吐量」這個貫穿整個並行工具集的核心取捨主題，在不同的工具裡用不同的底層資料結構實現，但背後的權衡邏輯是相通的。

**面試回答方式**：能具體講出「非公平用棧、公平用佇列」這組對應關係，並主動連結到「這和 `ReentrantLock` 公平/非公平鎖的取捨邏輯是同一件事」，展現你能把不同工具的類似設計決策串連起來理解，而不是把每個工具當成孤立的知識點背誦。

### LinkedBlockingQueue 的讀寫分離鎖為什麼在佇列為空或為滿時仍需要額外同步？

**核心答案**：因為當佇列從「空」變成「非空」，或從「非空」變成「非滿」時，原本在等待的消費者或生產者需要被喚醒，而喚醒動作牽涉到跨越讀鎖和寫鎖的邊界情況——例如剛新增一個元素讓佇列從空變成有一個元素，這時候需要喚醒可能正在等待的消費者，這個「新增（寫鎖範圍）」與「喚醒消費者（原本屬於讀鎖語意的等待者）」的協調，需要額外的同步處理，不能完全用兩把獨立無關的鎖處理。

**詳細解析**：具體來說，`LinkedBlockingQueue` 用兩個 `Condition`（分別關聯 `takeLock` 和 `putLock`）管理「佇列非空」和「佇列非滿」的等待喚醒，並額外用一個 `AtomicInteger count` 追蹤目前元素數量（這個計數器的存取需要能同時被讀寫兩側正確地看到，本身就帶有一定的同步考量）。當 `put` 操作把元素數量從 0 增加到 1 時，除了完成插入，還需要額外呼叫 `signalNotEmpty()` 喚醒可能在 `takeLock` 對應的 `notEmpty` 這個 `Condition` 上等待的消費者執行緒——這個喚醒動作跨越了原本讀寫分離的邊界，是這個資料結構中少數需要特別處理的邊界情況，設計者透過 `count` 這個共享的原子計數器加上精確的訊號喚醒時機，讓兩把鎖之間的協調保持正確又盡量減少互相阻塞。

**面試回答方式**：這題偏底層細節，回答時抓住「元素數量從 0 變 1，或從滿變不滿，這種邊界跨越需要通知另一側的等待者」這個核心邏輯講清楚即可，不需要背出每一行原始碼，展現理解「為什麼需要協調」比背誦「怎麼協調」更重要。

### DelayQueue 是如何實現延遲任務排程的？

**核心答案**：`DelayQueue` 內部用一個 `PriorityQueue`（優先佇列）依照元素的「到期時間」排序，只有當佇列頭部元素的延遲時間已經到期（`getDelay() <= 0`），`take()` 才會真正把它取出，否則呼叫執行緒會被阻塞等待到最近一個元素到期為止。

**詳細解析**：放入 `DelayQueue` 的元素必須實作 `Delayed` 介面，提供 `getDelay(TimeUnit)` 方法回傳距離到期還剩多久。內部的優先佇列會依照到期時間排序，永遠讓「最快到期」的元素排在佇列頭部。當執行緒呼叫 `take()` 時，會先檢查頭部元素是否已到期：若已到期就直接取出返回；若還沒到期，執行緒會用 `Condition.awaitNanos()` 精確地睡眠到這個元素的到期時間點再重新檢查（而不是忙碌輪詢）。這個機制常被用來實作簡單的延遲任務佇列，例如訂單超時未支付自動取消、快取項目到期清理等需要「在未來某個時間點才處理」的場景。

**面試回答方式**：能講出「底層是優先佇列依到期時間排序」加上「用 `Condition.awaitNanos()` 精確睡到到期時間而不是輪詢」這兩個關鍵機制，會比只回答「用來做延遲任務」更展現你理解它是如何有效率地實現「等待到特定時間點」這件事，而不是暴力輪詢。
