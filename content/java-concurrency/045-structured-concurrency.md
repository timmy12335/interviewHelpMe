# 題目

什麼是結構化併發？它與直接用執行緒池加 `Future` 差在哪？

## 核心答案

結構化併發的核心主張是：**併發任務的生命週期應該被限制在一個明確的語法作用域內**，就像區域變數的生命週期被限制在區塊內一樣。作用域結束時，**所有在其中啟動的子任務保證都已完成或被取消**，不會有洩漏出去的執行緒。

與執行緒池加 `Future` 的差別在**誰負責善後**。用 `Future` 時，任務的生命週期與提交它的程式碼完全脫鉤——方法回傳了，任務可能還在跑；某個子任務失敗了，其他子任務不會自動被取消，會繼續消耗資源做沒有人要的工作；例外沒有人取就靜默消失。**這些都是「結構」缺失的症狀**。

`StructuredTaskScope`（JDK 21 預覽）用 try-with-resources 表達這個結構：在作用域內 `fork` 子任務、`join` 等待全部完成、離開作用域時自動關閉。搭配兩種常用策略——`ShutdownOnFailure`（任一失敗就取消其餘，適合「全部都需要」）與 `ShutdownOnSuccess`（任一成功就取消其餘，適合「任一即可」的競速）。

**它的前提是虛擬執行緒**——每個子任務一個執行緒的模型只有在執行緒便宜時才成立。

## 詳細解析

**「取消要能傳播」是最實際的收益**。聚合三個下游服務的資料時，如果第一個就失敗了，另外兩個應該立刻停止——否則它們會繼續佔用連線、繼續等待逾時，而結果根本不會被使用。用 `CompletableFuture.allOf` 做不到這件事（失敗時其他任務照跑），要自己一個個 `cancel`，而且 `cancel` 對 `CompletableFuture` 只是標記、不會中斷底層。**結構化併發把這件事變成預設行為。**

**堆疊追蹤與可觀測性也被修復了**。子任務在 `fork` 時記錄了父作用域，所以執行緒轉儲可以顯示樹狀的任務結構（JDK 的 `jcmd Thread.dump_to_file -format=json` 就會呈現這個階層）。**這是回呼式非同步最難處理的問題**——那裡的任務關係完全存在於閉包裡，工具看不到。

**它與作用域值天然配對**：作用域值的綁定會被結構化併發的子任務**繼承但不複製**，於是「請求上下文自動傳給所有子任務」變成語言層級的能力，不必再用執行器裝飾器手動搬運。**這兩個特性是一起設計的**，分開看會低估它們的價值。

**限制也要說清楚**。它是**預覽功能**，API 在 JDK 21 到 25 之間有過調整，不該用在生產。它**只處理「作用域內的併發」**，跨請求的長生命週期任務（背景排程、常駐的消費者）仍然需要執行緒池。而且**它不會讓程式變快**——它解決的是正確性與可維護性問題（洩漏、取消、上下文、可觀測性），效能與手寫的正確版本相同。**把它定位成「讓正確的寫法變成最簡單的寫法」，比說它更快準確得多。**

## 面試回答方式

先給核心主張——**併發任務的生命週期被限制在明確的語法作用域內，作用域結束時所有子任務保證完成或被取消**，用「就像區域變數」這個類比讓它立刻可理解。接著把差別聚焦在**誰負責善後**，並列出 `Future` 模型缺失結構的三個症狀：方法回傳了任務還在跑、一個失敗其他不會被取消、例外沒人取就靜默消失。給出 `StructuredTaskScope` 的形式與兩種策略。加分點有三個：**取消傳播是最實際的收益**（第一個下游失敗時另外兩個立刻停止，`allOf` 做不到）；**執行緒轉儲能顯示樹狀任務結構**，這是回呼式非同步最難處理的；以及**它與作用域值是一起設計的**，上下文繼承變成語言能力。最後誠實定位：**它不會讓程式變快，它讓正確的寫法變成最簡單的寫法**。

## 常見追問

### 為什麼說結構化併發的前提是虛擬執行緒？

**核心答案**：因為它的模型是「**每個子任務一個執行緒**」。如果執行緒是稀缺的平台執行緒（每個約 1 MB 堆疊、建立成本高），那麼在每個作用域裡為每個子任務開一個執行緒是不可行的——必須回到共用執行緒池，而共用池就帶回了「生命週期與提交者脫鉤」的問題。**虛擬執行緒讓執行緒變成可以隨用隨拋的東西，結構化的模型才成立。**

**詳細解析**：這是一個典型的**「底層能力改變後，上層設計才變得可行」**的例子。在虛擬執行緒之前，Java 的併發設計被「執行緒昂貴」這個約束主導：所以有執行緒池、有非同步回呼、有反應式框架——**它們本質上都是在少數執行緒上多工，代價是把順序的控制流打散**。虛擬執行緒移除了這個約束，於是可以回到「一個任務一個執行緒」的直觀模型，而結構化併發是在這個模型上建立的紀律。**Go 的 goroutine 與 Kotlin 的協程走的是同一條路**，只是 Java 走得晚一些但保留了與既有阻塞式 API 的相容。

**面試回答方式**：給出模型上的依賴——**每個子任務一個執行緒，只有執行緒便宜時才可行**，否則必須回到共用池而共用池又帶回生命週期脫鉤的問題。真正的加分點是把它提升成一般觀察：**底層能力改變後上層設計才變得可行**——虛擬執行緒之前的所有併發設計（執行緒池、回呼、反應式）本質上都在少數執行緒上多工、代價是打散控制流。並指出 Go 與 Kotlin 走的是同一條路。

### ShutdownOnFailure 與 ShutdownOnSuccess 各適合什麼場景？

**核心答案**：`ShutdownOnFailure` 適合「**全部都需要**」——聚合多個下游的資料組成一個回應，任一失敗整體就無法完成，所以其餘的應該立刻取消。`ShutdownOnSuccess` 適合「**任一即可**」的競速——向多個副本或多個供應商同時發請求，最快回來的就用，其餘取消。後者是降低尾延遲的經典手段（對沖請求，hedged request）。

**詳細解析**：兩者之外還有更多需求，所以 API 允許**自訂策略**（覆寫 `handleComplete`）。實務上常見的第三種是「**盡力而為**」——等全部結束，成功的用、失敗的降級，不取消任何東西。這在儀表板類的聚合中很常見（某個模組載入失敗就顯示佔位符）。**選擇的關鍵是問「部分失敗時這個請求還有沒有意義」**：沒有意義就 fail-fast 並取消其餘（省資源），有意義就收集全部結果再分揀。要注意**對沖請求會放大下游負載**（一個請求變成 N 個），所以通常只對「已經超過 P95 延遲」的請求才發出對沖，而不是一律並發。

**面試回答方式**：給兩者的適用場景並用「全部都需要」與「任一即可」概括。指出 `ShutdownOnSuccess` 對應**對沖請求**這個降低尾延遲的經典手段。加分點是提出第三種常見需求——**盡力而為**（等全部結束、成功的用、失敗的降級），並給出選擇的關鍵問句：「部分失敗時這個請求還有沒有意義」。最後補上對沖請求會放大下游負載，所以通常只對超過 P95 的請求才發。

### 沒有結構化併發時，怎麼自己維持這個紀律？

**核心答案**：三條可以立刻實行的規則。**第一，每個提交點都要有對應的等待點**——不要「發射後不管」，提交了就要在同一個方法（或明確的下游）處理它的完成與失敗。**第二，用 try-finally 保證取消**——聚合多個 Future 時，在 finally 裡對尚未完成的呼叫 `cancel`。**第三，永遠明確指定執行器並設定逾時**，不要用 `commonPool`、不要無限等待。

**詳細解析**：更根本的做法是**把這些規則封裝成一個小工具**，而不是靠每個人記得。例如寫一個 `parallel(List<Supplier<T>>, Duration)` 方法，內部處理執行器選擇、逾時、失敗時取消其餘、以及結果收集——**讓正確的用法變成唯一便利的用法**。這正是結構化併發在語言層做的事，只是自己在應用層做一個簡化版。**「用 API 設計消除犯錯的可能，而不是用文件要求大家小心」是這題最值得帶走的原則**——它適用於併發，也適用於資源管理、權限檢查、以及任何「容易忘記」的紀律。

**面試回答方式**：給三條可立即實行的規則（提交點對應等待點、try-finally 保證取消、明確執行器加逾時）。真正的加分點是提升一層：**把規則封裝成一個小工具**（例如帶逾時與失敗取消的 `parallel` 方法），讓正確用法成為唯一便利的用法。收在可遷移的原則：**用 API 設計消除犯錯可能，而不是用文件要求大家小心**——這適用於併發，也適用於資源管理與權限檢查。
