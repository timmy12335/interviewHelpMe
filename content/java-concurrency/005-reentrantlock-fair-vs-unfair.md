# 題目

`ReentrantLock` 的公平鎖與非公平鎖有什麼差異？為什麼預設是非公平鎖？

## 核心答案

公平鎖嚴格按照執行緒請求鎖的先後順序分配鎖（先到先得），非公平鎖允許後來的執行緒「插隊」直接嘗試搶鎖。`ReentrantLock` 預設是非公平鎖，因為非公平鎖能減少執行緒喚醒的空窗期，吞吐量通常明顯優於公平鎖。

## 詳細解析

**實作差異（基於 AQS）**：

- **非公平鎖**：執行緒呼叫 `lock()` 時，會先直接嘗試 CAS 搶佔鎖狀態（`state` 從 0 改為 1），搶佔成功就直接持有鎖，完全不管 AQS 等待佇列中是否已有其他執行緒在排隊；只有搶佔失敗才會進入佇列排隊。
- **公平鎖**：執行緒呼叫 `lock()` 時，會先呼叫 `hasQueuedPredecessors()` 檢查 AQS 佇列中是否已經有排在自己前面的等待者，若有，就乖乖去排隊，不搶佔。

**為什麼非公平鎖吞吐量更高**：假設執行緒 A 剛釋放鎖，此時佇列頭部的執行緒 B 還在被喚醒的過程中（喚醒有 CPU 排程延遲），若這時新來的執行緒 C 呼叫 `lock()`：

- 非公平鎖：C 可以直接搶到鎖並執行，不需要等 B 被喚醒完成上下文切換，減少了「鎖空閒但無人持有」的時間窗口。
- 公平鎖：C 必須排隊等待，即使 B 還沒真正開始執行，鎖资源在這段喚醒延遲期間完全閒置。

**代價**：非公平鎖可能導致某些執行緒長時間搶不到鎖（「飢餓」），公平鎖能避免飢餓，但吞吐量較低、上下文切換次數較多。

**面試延伸**：這個「插隊 vs 排隊」的權衡本質上是**吞吐量與公平性的取捨**，和作業系統排程、資料庫鎖等待佇列的設計思路是相通的，回答時可以類比說明展現系統性思維。

## 面試回答方式

先用「插隊 vs 排隊」這個生活化比喻破題，讓面試官立刻理解語意差異，再補上底層機制（CAS 搶佔 vs `hasQueuedPredecessors()` 檢查）證明你懂實作，最後一定要講「為什麼預設非公平」並點出「吞吐量 vs 公平性」這個取捨——這是這題真正的考點，很多人只答得出「一個排隊一個插隊」但講不出背後的效能原因。如果還有餘裕，可以主動類比到作業系統排程或資料庫鎖等待佇列，展現這是你理解的「一類問題」而不是孤立的知識點。

## 常見追問

### synchronized 有公平鎖選項嗎？

**核心答案**：沒有。`synchronized` 的鎖分配完全由 JVM 與作業系統排程決定，沒有提供任何 API 讓開發者指定公平或非公平語意。

**詳細解析**：`synchronized` 在鎖升級為重量級鎖後，等待執行緒會被放入 Monitor 的 `_EntryList` 中，喚醒順序取決於底層作業系統的執行緒排程策略與實作細節，Java 語言層級完全沒有暴露任何介面讓開發者干預這個順序。如果業務場景必須保證「先請求先取得」的嚴格順序（例如某些需要保證處理順序的佇列消費場景），就必須改用 `ReentrantLock` 並指定 `true` 建立公平鎖，這也是 `synchronized` 相較 `ReentrantLock` 功能較少的具體例子之一。

**面試回答方式**：直接回答「沒有」，然後立刻補一句「這正是 `ReentrantLock` 比 `synchronized` 更靈活的地方之一」，把這個追問轉化成呼應前一題（[[004-synchronized-vs-reentrantlock.md]]）選型比較的機會，展現回答的連貫性。

### 什麼場景必須用公平鎖？

**核心答案**：需要嚴格保證「先請求先服務」順序的場景，例如某些限流演算法要求依請求到達順序處理、或需要避免任何執行緒被長期餓死的關鍵任務排程系統。

**詳細解析**：多數高吞吐量的業務系統（如一般的 Web 請求處理）並不特別要求嚴格的鎖分配順序，此時非公平鎖的效能優勢更重要。但在某些場景下，「順序」本身就是業務邏輯的一部分，例如：交易系統中同一帳戶的操作需要嚴格按照送達順序處理以保證帳務正確、批次任務排程系統需要保證公平地讓每個任務都有機會執行而不會被持續搶佔資源的任務餓死。這類場景犧牲一些吞吐量、換取確定性的處理順序與公平性是合理的取捨。

**面試回答方式**：舉一到兩個具體業務場景（例如交易順序、任務排程公平性）會比抽象地說「需要公平性的時候」更有說服力，展現你能把技術選型連結到實際業務需求。

### AQS 的等待佇列資料結構是什麼？

**核心答案**：CLH（Craig, Landin, and Hagersten）鎖演算法的變種，是一個雙向鏈結串列（doubly linked list）結構的 FIFO 佇列。

**詳細解析**：原始的 CLH 鎖是單向佇列且只用於自旋鎖；AQS 對其做了改造，變成雙向鏈結串列，讓佇列中的節點可以在逾時或被中斷時，方便地從佇列中間移除自己（單向鏈結串列做不到，因為找不到前驅節點）。每個等待的執行緒被包裝成一個 `Node`，包含指向前驅與後繼節點的指標，以及該節點的等待狀態；持有鎖的執行緒釋放鎖時，會找到佇列頭部的下一個有效節點並喚醒它。

**面試回答方式**：能講出「CLH 鎖的變種」與「雙向鏈結串列」這兩個關鍵詞，並補一句「改成雙向的原因是為了支援逾時和取消時能直接移除節點」，會比只回答「佇列」更顯示出你真的了解 AQS 原始碼層級的設計考量。
