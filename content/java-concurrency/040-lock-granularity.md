# 題目

鎖的粒度該怎麼選？「分段鎖」為什麼有效，又有什麼限制？

## 核心答案

粒度的取捨是**爭用**與**複雜度**之間的權衡。**粗粒度**（一把大鎖保護整個物件）簡單、不會死鎖、容易推理，但所有操作序列化。**細粒度**（每個部分一把鎖）並行度高，但代價是：可能死鎖（多把鎖就有順序問題）、跨部分的操作需要同時持有多把鎖、以及**每把鎖本身都有記憶體與快取成本**。

**分段鎖**是細粒度的一種結構化做法：把資料依某個鍵**分成 N 段，每段一把鎖**。同一段內序列、不同段並行，於是理論並行度變成 N。JDK 7 的 `ConcurrentHashMap` 用 16 個 Segment 就是這個設計。

它的限制有三個。**分佈不均時失效**——熱點鍵集中在一段的話，並行度回到 1。**跨段操作很貴**——`size()` 要取得所有段的鎖或做多次不加鎖的嘗試。**N 的選擇是固定的**——太小並行度不足，太大則每段的資料太少、記憶體開銷佔比上升。

JDK 8 之所以放棄 Segment 改成「**每個桶一把鎖**」（用桶頭節點當作鎖物件），正是因為那是**最細的自然粒度**，而且不需要預先決定 N。

## 詳細解析

**「先粗後細」是正確的順序**。從一把大鎖開始，程式碼簡單且必然正確；只有在**量測證明鎖爭用是瓶頸**之後才細化。判斷爭用的方式：執行緒轉儲中大量執行緒 `BLOCKED` 在同一個監視器上、或用非同步剖析器（async-profiler）的 lock 模式直接看鎖等待時間的分布。**憑感覺細化鎖是併發 bug 最主要的來源之一**。

**細化的順序也有講究**。第一步不是分段，而是**縮小臨界區**——把不需要保護的計算（尤其是 IO、日誌、格式化）移出鎖外，這通常能拿到大部分收益而且零風險。第二步是**拆分不相關的狀態**——一個類別如果保護了兩組互不相關的欄位，用兩把鎖是安全且直接的。第三步才是分段。**這個順序的原則是：收益遞減、風險遞增。**

**多把鎖必須有全域的取得順序**，否則必然死鎖。實務做法是**依某個固定的屬性排序**（例如物件的 `identityHashCode`、或業務上的 ID），永遠按同樣的順序取。轉帳這個經典例子就是如此：`transfer(a, b)` 與 `transfer(b, a)` 同時發生時，若各自按參數順序取鎖就會死鎖；改成按帳號 ID 排序後取，就不可能形成環。

**分段的思路遠不只用在鎖上**。`LongAdder` 的分格、資料庫的分庫分表、Kafka 的分區、快取的分片——**都是「把單點爭用變成多點，最後再匯總」**。它們也共享同樣的限制：**熱點鍵會讓分片失效**。所以分片方案幾乎總是要配套一個熱點處理策略（熱點鍵單獨拆出、加一層本地快取、或在鍵上加隨機後綴打散）。**能看出這是同一個模式，比記住 `ConcurrentHashMap` 的實作細節更有價值。**

## 面試回答方式

先把取捨講清楚——**爭用 vs 複雜度**，並具體列出細粒度的三個代價（死鎖風險、跨部分操作要持多把鎖、每把鎖本身的記憶體與快取成本）。接著解釋分段鎖的原理與 JDK 7 的 16 個 Segment，然後給它的三個限制（分佈不均失效、跨段操作貴、N 固定）。**JDK 8 改成每個桶一把鎖**的理由要說出來：那是最細的自然粒度且不必預先決定 N。加分點有兩個：給出**細化的正確順序**——先縮小臨界區（把 IO 與日誌移出鎖外，零風險且收益大）、再拆分不相關的狀態、最後才分段，原則是收益遞減風險遞增；以及指出**分段是一個通用模式**（`LongAdder`、分庫分表、Kafka 分區都是），它們共享「熱點鍵會讓分片失效」這個限制，所以分片方案幾乎總要配套熱點處理策略。

## 講稿

粒度的取捨是爭用跟複雜度之間的權衡。粗粒度就是一把大鎖保護整個物件，簡單、不會死鎖、容易推理，但所有操作序列化。細粒度並行度高，代價是可能死鎖、跨部分的操作要同時持有多把鎖、而且每把鎖本身都有記憶體跟快取成本。

分段鎖是把資料依某個鍵分成 N 段，每段一把鎖。同一段內序列、不同段並行。JDK 7 的併發雜湊表用十六個段就是這個設計。

它有三個限制。分佈不均的時候失效，熱點鍵集中在一段，並行度就回到一。跨段操作很貴。還有段數是固定的，太小並行度不足，太大則每段資料太少。所以 JDK 8 改成每個桶一把鎖，因為那是最細的自然粒度，而且不必預先決定段數。

實務上我的順序是先粗後細。而且細化的第一步不是分段，是縮小臨界區，把 IO、日誌、格式化這些不需要保護的東西移出鎖外。這通常能拿到大部分收益而且零風險。第二步是拆分不相關的狀態，第三步才是分段。原則是收益遞減、風險遞增。

## 常見追問

### 為什麼多把鎖一定要有取得順序？

**核心答案**：因為**循環等待是死鎖的四個必要條件之一**，而固定的全域取得順序能直接消除它。如果所有執行緒都按同一個順序取鎖，就不可能形成「A 等 B 持有的鎖、B 等 A 持有的鎖」這種環——先取到順序較前那把鎖的執行緒必然能繼續往下取。**這是四個條件裡最容易在工程上強制執行的一個。**

**詳細解析**：實作上的關鍵是**順序必須是全域一致且穩定的**。用物件的 `hashCode` 有風險（可能碰撞，兩個不同物件的值相同時順序不確定），實務做法是先比 `System.identityHashCode`，相同時再用一把「加時賽鎖」（tie-breaking lock）序列化這種罕見情況。用業務 ID 排序則更清楚也更穩定，只要 ID 是不可變的。**另一個常被忽略的來源是隱含的鎖**——呼叫某個框架方法時它可能內部取了鎖，而你不知道順序。這正是「不要在持有鎖時呼叫不受控的程式碼」這條紀律的另一個理由：**你無法為看不見的鎖安排順序。**

**面試回答方式**：先給原理——**固定順序直接消除循環等待這個必要條件**，並說明它是四個條件裡最容易工程強制的。接著給實作細節：`hashCode` 可能碰撞所以要有加時賽鎖，用不可變的業務 ID 排序更穩定。加分點是點出**隱含的鎖**：框架方法內部可能取鎖而你不知道順序，這正是「不要在持有鎖時呼叫不受控程式碼」的另一個理由——你無法為看不見的鎖安排順序。

### 縮小臨界區具體要移出哪些東西？

**核心答案**：四類。**IO 操作**——資料庫查詢、遠端呼叫、檔案讀寫，它們的延遲不受控，在鎖內做等於把不確定的等待時間變成所有人的等待。**日誌**——尤其是同步 appender，一次磁碟寫入可能是毫秒級。**字串格式化與物件建立**——看起來便宜，但在熱路徑上累積可觀，而且可能觸發 GC。**不依賴共享狀態的計算**——先算好再進鎖，或者在鎖內只讀出需要的值、出鎖後再計算。

**詳細解析**：標準的重構模式是「**進鎖只讀、出鎖計算、必要時再進鎖寫**」，但這會引入「讀與寫之間狀態可能改變」的問題，所以寫回時需要**檢查前提是否仍然成立**（版本號或條件檢查），這本質上就是樂觀併發控制。**這也解釋了為什麼縮小臨界區不是免費的**——它把「持續持有鎖」換成「檢查與重試」，適合衝突率低的場景。衝突率高時，反而是持續持鎖更有效率（重試的成本超過等待）。**判斷方式是量測衝突率**：重試次數佔總操作的比例超過一定程度（例如 10%）就該考慮回到粗粒度。

**面試回答方式**：列出四類要移出的東西並各給一句理由，重點放在 IO（不受控的延遲變成所有人的等待）與日誌（同步 appender 是毫秒級）。加分點是給出重構模式「進鎖只讀、出鎖計算、再進鎖寫」，並誠實指出它**不是免費的**——需要檢查前提是否仍成立，本質是樂觀併發控制，只適合衝突率低的場景。收在量測建議：重試比例超過一成就該考慮回到粗粒度。

### 熱點鍵讓分片失效時該怎麼辦？

**核心答案**：三種做法。**打散**——在鍵上加一個隨機或輪詢的後綴，讓一個熱點鍵變成 N 個子鍵分散到不同分片，讀取時聚合 N 個子鍵的結果。適合計數器這類可聚合的資料。**本地快取**——在分片之前加一層行程內快取，熱點的讀取根本到不了分片層。適合讀多寫少。**單獨處理**——把識別出的熱點鍵放進專門的結構（例如獨立的無鎖計數器或專屬的分片），與其他鍵分開。

**詳細解析**：三者都要先**識別熱點**，而識別本身需要取樣統計（完整統計每個鍵的存取次數本身就是熱點）。常見做法是用 count-min sketch 這類近似結構做低成本的頻率估計，或者取樣（每 100 次操作記錄 1 次）。**熱點是動態的**——今天的熱點鍵明天可能是冷的，所以識別與應對應該是自動且持續的，而不是寫死一份清單。**這也是為什麼成熟的快取庫（Caffeine）內建了頻率統計**：它不只用來淘汰，也是熱點感知的基礎。**能指出「識別熱點本身也有成本、而且熱點會漂移」，比只列舉三種解法更顯示實務經驗。**

**面試回答方式**：給三種做法（打散、本地快取、單獨處理）並各配適用場景。真正的加分點是後半段——**識別熱點本身需要成本**（完整統計每個鍵就是新的熱點），所以要用近似結構或取樣；而且**熱點會漂移**，識別與應對應該自動且持續而非寫死清單。用 Caffeine 內建頻率統計作為佐證。
