# 題目

什麼是虛擬執行緒的「釘住」（pinning）？怎麼發現與避免它？

## 核心答案

虛擬執行緒的核心機制是：阻塞時把自己從載體執行緒（carrier thread，一個平台執行緒）上卸下，讓載體去跑別的虛擬執行緒。**釘住**是指某些情況下它無法卸下——阻塞時**整個載體執行緒跟著被佔住**，於是虛擬執行緒的擴展性優勢完全消失。

JDK 21 有兩種釘住來源。在 `synchronized` 區塊或方法內阻塞——因為監視器鎖與載體執行緒綁定，卸下會破壞鎖的語意（JDK 24 的 JEP 491 已經解決了這一項）。執行原生方法或外部函式時阻塞——JVM 無法卸下位於原生堆疊上的執行緒。

後果很具體：載體執行緒池預設只有核心數那麼多，幾個被釘住的虛擬執行緒就能讓所有載體被佔滿，此時整個應用的虛擬執行緒全部停擺，表現為吞吐驟降但 CPU 很低。

診斷靠 **`-Djdk.tracePinnedThreads=full`**（印出釘住時的堆疊）或 **JFR 的 `jdk.VirtualThreadPinned` 事件**（生產環境更合適，開銷低）。

## 詳細解析

避免釘住在 JDK 21 上的主要做法是把 `synchronized` 換成 `ReentrantLock`。JUC 的鎖是用 `LockSupport.park` 實作的，而 `park` 對虛擬執行緒是「卸下」而不是「阻塞平台執行緒」，所以完全不會釘住。**這個替換不改變語意**（可重入、互斥都一樣），只是要注意 `ReentrantLock` 必須手動 `unlock`（放 finally），而且它不支援 `synchronized` 的鎖粗化等 JIT 最佳化，低爭用下可能略慢。

風險最大的是第三方函式庫裡的 `synchronized`——自己的程式碼可以改，JDBC 驅動、連線池、日誌框架裡的就改不了。這正是遷移到虛擬執行緒時最需要驗證的地方：不能只看自己的程式碼，要用 `tracePinnedThreads` 實際跑一輪壓測看有沒有釘住。好消息是主流函式庫（HikariCP、驅動程式、Netty）都已經陸續處理過這個問題，而 JDK 24 之後這個顧慮基本消失。

**釘住不是唯一的坑，還有兩個**。`ThreadLocal` 的記憶體放大——每個虛擬執行緒一份副本，數十萬個執行緒會撐爆堆積，這是作用域值存在的理由。連線池成為真正的並行度上限——十萬個虛擬執行緒同時要資料庫連線而池只有 20 個，那 20 才是實際並行度，其餘在等待；此時的問題不再是執行緒不夠，而是等待連線的排隊與逾時策略。

**虛擬執行緒不適合 CPU 密集任務**，這一點值得主動說明。它的價值在於「阻塞很便宜」，而 CPU 密集任務不阻塞——開十萬個虛擬執行緒跑計算，載體執行緒仍然只有核心數，反而多了排程與快取汙染的成本。CPU 密集仍然該用固定大小的執行緒池或 ForkJoinPool。

## 面試回答方式

先給機制——虛擬執行緒阻塞時**從載體執行緒卸下**，而釘住是無法卸下、整個載體被佔住。給出 JDK 21 的**兩種來源**（`synchronized` 內阻塞、原生方法阻塞）並說明第一項在 JDK 24 已解決。後果要具體：載體池只有核心數那麼多，幾個釘住就能讓所有虛擬執行緒停擺，表現是吞吐驟降但 CPU 很低。診斷給兩個工具（`-Djdk.tracePinnedThreads` 與 JFR 事件，後者適合生產）。加分點有三個：風險最大的是第三方函式庫裡的 `synchronized`，所以遷移時要實際壓測驗證而非只看自己的程式碼；`ThreadLocal` 的記憶體放大與連線池成為真正的並行度上限這兩個獨立的坑；以及主動說明虛擬執行緒不適合 CPU 密集任務，那仍該用固定執行緒池。

## 講稿

虛擬執行緒的核心機制是，阻塞的時候把自己從載體執行緒上卸下，讓載體去跑別的虛擬執行緒。釘住是指某些情況下它卸不下來，阻塞的時候整個載體執行緒跟著被佔住，擴展性優勢就完全消失了。

JDK 21 有兩種來源。在 synchronized 區塊裡阻塞，因為監視器鎖跟載體執行緒綁定。還有執行原生方法時阻塞，因為 JVM 無法卸下位於原生堆疊上的執行緒。第一項在 JDK 24 已經解決了。

後果很具體。載體執行緒池預設只有核心數那麼多，幾個被釘住的虛擬執行緒就能把所有載體佔滿，這時候整個應用停擺，表現是吞吐驟降但 CPU 很低。

診斷可以開一個系統屬性印出釘住時的堆疊，生產環境則用 JFR 的事件，開銷比較低。

避免的做法是把 synchronized 換成 ReentrantLock，因為 JUC 的鎖是用 park 實作的，對虛擬執行緒是卸下而不是阻塞。但風險最大的是第三方函式庫裡的 synchronized，那個改不了。所以遷移的時候一定要實際壓測驗證，不能只看自己的程式碼。

## 常見追問

### 虛擬執行緒的載體執行緒池可以調整嗎？

**核心答案**：可以，用 `-Djdk.virtualThreadScheduler.parallelism`（並行度，預設等於可用處理器數）與 `-Djdk.virtualThreadScheduler.maxPoolSize`（上限，預設 256）。**但調它通常不是正確的解法**——需要調大並行度，往往代表有釘住或有大量在原生方法中阻塞的操作，那應該去修根因而不是加載體。

**詳細解析**：載體池本身是一個 `ForkJoinPool`（FIFO 模式，與平行串流用的不同實例）。它的設計前提是虛擬執行緒不會長時間佔用載體——阻塞時卸下、計算時佔用短暫。如果應用有大量 CPU 密集的虛擬執行緒，它們會持續佔用載體，其他虛擬執行緒得不到執行機會，**表現得很像釘住但成因不同**（不是無法卸下，而是根本沒有阻塞點可以卸）。這種情況下正確的做法是把 CPU 密集的工作移到獨立的執行緒池，讓虛擬執行緒專門處理 IO 密集的工作。能區分「釘住」與「CPU 佔用」這兩種症狀相似但成因不同的問題，是這題的深度所在。

**面試回答方式**：給出兩個系統屬性與預設值，但立刻指出**調它通常不是正確解法**——需要調大往往代表有釘住或原生阻塞，該修根因。加分點是區分兩種相似症狀：釘住是無法卸下，CPU 密集是根本沒有阻塞點可卸，後者表現得很像釘住但解法完全不同（把 CPU 工作移到獨立執行緒池）。

### 遷移到虛擬執行緒要檢查哪些地方？

**核心答案**：五項。**釘住**——壓測時開 `tracePinnedThreads` 或 JFR 事件驗證。`ThreadLocal` 用量——盤點並減少，尤其是存大物件的。連線池與其他資源池的大小——它們成為真正的並行度上限，可能需要重新調整。背壓機制——`newVirtualThreadPerTaskExecutor` 沒有佇列也沒有上限，必須自己用信號量或有界佇列限制並行。固定大小執行緒池的隱含限流——原本靠「執行緒池只有 50 個」限制了對下游的並發，換成虛擬執行緒後這個限制消失，下游可能被打垮。

**詳細解析**：最後一項是最容易忽略也最危險的。很多系統從未明確設定過對下游的限流，而是靠執行緒池的大小意外地達成了——換成虛擬執行緒之後，原本每秒 50 個並發請求變成每秒五千個，下游立刻崩潰。所以遷移不只是換一個執行器，而是要把原本隱含的限制變成明確的限制（信號量、速率限制器、或下游客戶端的並發上限）。這是一個很好的例子說明「隱含的約束在移除時才會被發現」——這類約束在架構變更時是主要的風險來源。

**面試回答方式**：列出五項檢查點。重點放在最後一項最容易忽略也最危險：原本靠執行緒池大小意外達成的下游限流，換成虛擬執行緒後消失，並發從每秒 50 變成五千。給出解法——**把隱含限制變成明確限制**（信號量、速率限制器）。收在一般教訓：隱含的約束在移除時才會被發現，這是架構變更的主要風險來源。

### 怎麼判斷一個服務值不值得用虛擬執行緒？

**核心答案**：問三個問題。**是不是 IO 密集？** 大部分時間花在等待下游、資料庫、檔案的服務才有收益；CPU 密集的沒有。目前是不是被執行緒數限制住？ 執行緒池滿載、佇列堆積、但 CPU 使用率不高，這是典型的訊號。**是不是用阻塞式寫法？** 如果已經改成反應式，收益主要是「可以改回簡單寫法」而不是效能。

**詳細解析**：收益最大的場景是「原本考慮改反應式但還沒改」的服務——虛擬執行緒讓它們用簡單的阻塞寫法拿到接近反應式的擴展性，省下了整個重寫的成本與後續的除錯痛苦。收益最小的是已經跑得很好的服務：如果目前的執行緒池從未滿載、延遲也達標，換過去只會帶來遷移風險而沒有實際好處。這個判斷的一般形式是：新技術的價值等於「它解決的問題」乘以「你有多少那個問題」——沒有那個問題時，再好的技術也是負收益。能明確說出「我們的服務不需要」也是一種有價值的判斷。

**面試回答方式**：給三個判斷問題（IO 密集嗎、被執行緒數限制住了嗎、用阻塞寫法嗎）並說明各自的訊號。點出收益最大的場景是「原本考慮改反應式但還沒改」的服務，收益最小的是已經跑得好的服務。收在一般形式：新技術的價值等於「它解決的問題」乘以「你有多少那個問題」，並強調能說出「我們不需要」也是有價值的判斷。
