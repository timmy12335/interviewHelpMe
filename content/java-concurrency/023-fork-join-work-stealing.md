# 題目

Fork/Join 框架解決了什麼問題？工作竊取（work-stealing）演算法是怎麼運作的？

## 核心答案

Fork/Join 框架（JDK 7 引入）用於把一個大任務遞迴拆分成多個可以並行執行的小任務（分治法），充分利用多核 CPU。其核心是工作竊取演算法：每個工作執行緒維護自己的雙端佇列（deque），優先處理自己佇列裡的任務；當自己的佇列任務用完時，會去「偷」其他執行緒佇列尾端的任務來執行，藉此讓所有執行緒盡量保持忙碌、減少因任務分配不均導致的閒置。

## 詳細解析

**適用場景（分治演算法）**：Fork/Join 適合能夠遞迴拆解成獨立子問題、子問題可以並行求解、最後再合併結果的計算密集型任務，經典例子包括大陣列求和、排序、矩陣運算等。使用時通常繼承 `RecursiveTask<V>`（有返回值）或 `RecursiveAction`（無返回值），在 `compute()` 方法中判斷任務規模是否小於閾值：小於閾值就直接計算，否則呼叫 `fork()` 把任務拆成多個子任務並行送出，最後用 `join()` 等待並合併子任務結果。

**工作竊取演算法的運作方式**：

1. `ForkJoinPool` 內部為每個工作執行緒分配一個獨立的雙端佇列（deque），而不是像傳統執行緒池那樣所有執行緒共用一個佇列。
2. 執行緒呼叫 `fork()` 產生子任務時，會把子任務放入**自己**佇列的**頭部（head）**；執行緒平常從自己佇列的**頭部**取出任務執行（後進先出，類似棧，有利於局部性——最近拆分出的子任務通常和目前處理的資料在快取上更接近）。
3. 當某個執行緒自己的佇列空了（沒有任務可做），它不會閒置等待，而是隨機挑選其他執行緒的佇列，從對方佇列的**尾部（tail）**「偷」一個任務來執行。
4. 從佇列尾部竊取（而不是頭部），是為了盡量減少與佇列擁有者本身的操作（擁有者從頭部取，竊取者從尾部取）發生競爭衝突，並且偷到的通常是「最早被拆分出來、顆粒度較大」的任務，減少頻繁竊取的次數。

**為什麼比傳統執行緒池更適合分治任務**：如果所有執行緒共用一個任務佇列，任務分配不均時，某些執行緒可能會頻繁地在同一把鎖上競爭以取得下一個任務；而工作竊取讓每個執行緒優先處理自己的任務（無鎖或低競爭），只有在真正閒置時才需要處理跨執行緒的協調，大幅減少了任務排程本身的同步開銷，讓大量細粒度並行任務的整體效率更高。

**`ForkJoinPool.commonPool()`**：JDK 8 之後，`Stream` 的 `parallelStream()` 以及 `CompletableFuture` 預設的非同步方法，都使用同一個全域共用的 `ForkJoinPool.commonPool()`。這意味著如果系統中大量使用 `parallelStream()` 或 `CompletableFuture` 的非同步方法且其中有任務執行時間很長或會阻塞（例如做 I/O），可能會互相搶佔 `commonPool` 的執行緒資源，導致彼此拖慢，這也是為什麼建議 I/O 密集或耗時的非同步任務應該使用自訂的 `Executor`，而不是依賴共用的 `commonPool`。

## 常見追問
