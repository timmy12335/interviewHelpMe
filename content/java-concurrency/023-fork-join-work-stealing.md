# 題目

Fork/Join 框架解決了什麼問題？工作竊取（work-stealing）演算法是怎麼運作的？

## 核心答案

Fork/Join 框架用於把一個大任務遞迴拆分成多個可以並行執行的小任務（分治法），充分利用多核 CPU。其核心是工作竊取演算法：每個工作執行緒維護自己的雙端佇列，優先處理自己佇列裡的任務；當自己的佇列任務用完時，會去「偷」其他執行緒佇列尾端的任務來執行，藉此讓所有執行緒盡量保持忙碌。

## 詳細解析

**適用場景**：能遞迴拆解成獨立子問題、可並行求解、最後再合併結果的計算密集型任務。繼承 `RecursiveTask<V>`（有返回值）或 `RecursiveAction`（無返回值），在 `compute()` 判斷規模是否小於閾值。

**工作竊取演算法的運作方式**：每個工作執行緒有獨立的雙端佇列；`fork()` 產生的子任務放入自己佇列的**頭部**；執行緒從自己佇列的**頭部**取出執行；佇列空了就隨機挑選其他執行緒的佇列，從對方佇列的**尾部**偷任務。

**為什麼比傳統執行緒池（Thread Pool）更適合分治任務**：避免大量細粒度並行任務在共用佇列上競爭同一把鎖，只有真正閒置時才需要跨執行緒協調。

**`ForkJoinPool.commonPool()`**：`parallelStream()` 和 `CompletableFuture` 預設非同步方法都用同一個全域共用池，長時間或阻塞任務可能互相搶佔。

## 面試回答方式

先講「解決什麼問題」（分治任務、充分利用多核），再講「工作竊取怎麼運作」，這裡務必講清楚「自己從頭部取、竊取者從尾部偷」這個雙端佇列的巧妙設計，這是這題最核心也最容易被追問細節的地方。最後主動提一句 `ForkJoinPool.commonPool()` 被 `parallelStream()` 和 `CompletableFuture` 共用的風險，這個連結能自然銜接到前面 `CompletableFuture` 相關題目（[[013-completablefuture-composition.md]]），展現你的知識點是連貫成一張網而不是孤立的碎片。

## 常見追問

### parallelStream() 什麼時候不適合使用？

**核心答案**：任務量太小（拆分與合併的協調開銷可能超過並行帶來的效益）、任務之間有共享可變狀態（並行執行可能導致競態條件，因為 `parallelStream` 不會幫你處理執行緒安全）、依賴任務執行順序（例如需要依序輸出或依序處理有前後依賴關係的資料）、以及任務內部包含阻塞式 I/O 操作（因為預設共用 `ForkJoinPool.commonPool()`，容易與其他也在使用共用池的任務互相拖累）。

**詳細解析**：`parallelStream()` 的效益來自於「把運算工作分散到多核心平行執行」，如果資料量很小（例如只有幾十個元素），拆分任務、分配給不同執行緒、再合併結果的協調開銷，很可能比單執行緒直接循序處理還要慢，這是最常見的誤用場景——看到 `parallelStream` 就直覺覺得「並行一定比較快」而不評估任務規模。另一個常見陷阱是在 `parallelStream` 的 lambda 內部修改外部的共享可變變數（例如往一個普通 `ArrayList` 裡塞資料），因為多個執行緒同時執行這段邏輯，會產生典型的執行緒安全問題，這類 bug 往往只在高並發或大資料量時才會偶發出現，非常難以重現與除錯。如果任務內部涉及網路呼叫或資料庫查詢這類阻塞式 I/O，因為預設使用的是全域共用的 `ForkJoinPool.commonPool()`，執行緒數量有限，容易和系統中其他同樣使用 `parallelStream`/`CompletableFuture` 的邏輯互相競爭執行緒資源，導致效能不升反降。

**面試回答方式**：列出「小資料量」「共享可變狀態」「順序依賴」「阻塞式 I/O」這四個具體的不適用場景，每個都補一句「為什麼不適合」的原因，這種列舉具體反例的答法，比籠統地說「不是所有情況都適合」更能展現你真的踩過或深入思考過這些陷阱。

### fork()/join() 和普通執行緒池的 submit()/Future.get() 有什麼本質差異？

**核心答案**：`fork()`/`join()` 是設計給「執行緒池內部的工作執行緒」使用的，當一個任務在 `ForkJoinPool` 的工作執行緒中執行時呼叫 `join()` 等待子任務結果，這個工作執行緒不會真正阻塞閒置，而是會利用工作竊取機制去執行佇列中其他待處理的任務，善用這段等待時間；普通執行緒池的 `submit()`/`Future.get()` 中，呼叫 `get()` 等待結果的執行緒（不管是不是執行緒池內部的執行緒）就是單純阻塞，不會主動去做其他任何工作。

**詳細解析**：這個差異是 Fork/Join 框架效能優勢的核心來源——在遞迴分治的場景中，一個任務往往需要 `fork()` 出多個子任務再 `join()` 等待它們全部完成才能合併結果，如果這個「等待子任務完成」的過程和普通執行緒池一樣是單純阻塞，那麼工作執行緒在等待期間就完全被浪費了；`ForkJoinPool` 特別設計了「在 `join()` 等待時，如果目前的工作執行緒發現自己閒置，就去佇列裡（自己的或偷別人的）找其他任務來做」這個機制，讓遞迴分治產生的大量細粒度任務能夠持續填滿所有工作執行緒的閒置時間，這正是工作竊取演算法真正發揮威力的地方，也是它和一般執行緒池在「等待」語意上的根本不同。

**面試回答方式**：用「`join()` 等待時工作執行緒不會真正閒著，而是去偷其他任務做；普通 `get()` 等待就是單純阻塞」這個對比講清楚，這正是 Fork/Join 框架為什麼特別適合遞迴分治任務的核心原因，能把這個機制講清楚會是這批追問題中最展現深度理解的一題。

### 工作竊取演算法如何避免在竊取過程中和佇列擁有者發生資料競爭？

**核心答案**：因為佇列擁有者永遠從佇列的頭部存取（單執行緒操作，不需要同步），而竊取者永遠從佇列的尾部存取，兩者操作的是雙端佇列的不同兩端，大幅降低了實際發生衝突的機率；即使真的同時發生（佇列裡只剩最後一個任務，擁有者和竊取者剛好同時嘗試取走），底層仍然需要透過 CAS 等輕量級同步機制解決這個邊界衝突，但因為這種情況相對少見，整體上的同步開銷遠低於「每次存取佇列都要加鎖」的傳統做法。

**詳細解析**：這種「一端給擁有者、一端給竊取者」的設計是雙端佇列在工作竊取演算法中被選用的關鍵原因——大多數時候擁有者存取頭部、竊取者存取尾部完全不會互相干擾，不需要任何鎖或同步機制；只有在佇列裡任務數量很少（極端情況下只剩一個）時，頭部和尾部實質上指向同一個任務，這時才真正需要透過 CAS 這類原子操作來仲裁到底是擁有者還是某個竊取者成功取得了這個任務，確保不會被重複執行或遺失。這種「大部分時候無鎖、極少數邊界情況才需要輕量同步」的設計思路，與前面提到的 `ConcurrentHashMap`（見 [[014-concurrenthashmap-internals.md]]）先嘗試 CAS 無鎖插入、只在真正衝突時才加鎖的思路是高度一致的，都是「樂觀地假設大部分情況不衝突，只在真正衝突時才付出同步成本」這個並行程式設計的通用哲學。

**面試回答方式**：用「頭尾分離存取、大部分時候無需同步、只有邊界情況才需要 CAS 仲裁」這個結構回答，並主動連結到 `ConcurrentHashMap` 類似的樂觀無鎖設計思路，展現你能辨識出不同並行資料結構背後共通的設計哲學，而不是把每個資料結構當成孤立的知識點記憶。
