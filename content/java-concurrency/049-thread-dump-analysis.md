# 題目

拿到一份執行緒轉儲，你會怎麼看？各種執行緒狀態分別代表什麼？

## 核心答案

判讀的順序是先看整體分布、再看熱點堆疊、最後看鎖關係。

**整體分布**——各狀態的執行緒各有幾個。大量 `BLOCKED` 指向鎖爭用；大量 `WAITING`／`TIMED_WAITING` 在同一個位置通常是正常的（執行緒池閒置、等待佇列），但如果那個位置是業務邏輯（例如 `Future.get`），就代表在等某個不會來的東西；大量 `RUNNABLE` 而 CPU 不高，往往是**卡在 socket 讀取**（Java 把阻塞的網路 IO 標成 RUNNABLE，這是最常被誤解的一點）。

**熱點堆疊**——把所有執行緒的堆疊頂端聚合統計，出現次數最多的位置就是嫌疑點。這比逐個看幾百個執行緒有效得多。

**鎖關係**——每個 `BLOCKED` 的執行緒會顯示 `waiting to lock <0x...>`，持有者則顯示 `locked <0x...>`。用位址比對就能找出「誰擋住了所有人」。JVM 也會自動偵測並印出 `Found one Java-level deadlock`。

**單次轉儲只是一張快照**，要判斷是「卡住」還是「正在跑」，必須**連抓三到五次比對**——堆疊沒變的才是真的卡住。

## 詳細解析

`RUNNABLE` 不等於在用 CPU，這是判讀時最大的陷阱。Java 的執行緒狀態是 JVM 層級的概念，阻塞在原生方法（socket read、檔案 IO）的執行緒仍然是 RUNNABLE，因為 JVM 不知道原生方法內部在做什麼。所以看到幾百個 RUNNABLE 執行緒不代表 CPU 爆滿——要對照實際的 CPU 使用率。堆疊頂端是 `socketRead0` 或 `epollWait` 這類原生方法時，那就是在等 IO。

**`BLOCKED` 與 `WAITING` 的區別很精確**：`BLOCKED` 是在**等待進入 `synchronized`**（等監視器鎖）；`WAITING` 是呼叫了 `Object.wait`、`Thread.join`、`LockSupport.park`（包括所有 JUC 的鎖與佇列）而主動等待。**這表示 `ReentrantLock` 的等待顯示為 `WAITING` 而不是 `BLOCKED`**——如果只看 BLOCKED 的數量，會完全漏掉 JUC 鎖的爭用。要靠堆疊裡的 `AbstractQueuedSynchronizer` 相關幀來識別。

執行緒名稱的價值在這裡體現：預設的 `pool-2-thread-7` 什麼也說明不了；改成 `order-async-7`、`payment-callback-3` 之後，看到「三十個 payment-callback 執行緒全部卡在同一個位置」就立刻知道是哪個功能出問題。自訂 `ThreadFactory` 的成本是幾行程式碼，收益在每一次排查時兌現。

**與其他證據配合才能定位**。轉儲告訴你「在哪裡」，但不告訴你「為什麼」。搭配的做法是：用 `top -H` 找出 CPU 最高的原生執行緒 ID，轉成十六進位後在轉儲裡用 `nid=` 比對，就能找出真正吃 CPU 的那個執行緒；或者搭配 GC 日誌排除 GC 停頓；或者搭配應用日誌確認那個時間點在處理什麼請求。單看轉儲能解決的問題有限，它的價值在於快速縮小範圍。

## 面試回答方式

先給**三步判讀順序**（整體分布、熱點堆疊、鎖關係）而不是一開始就講狀態定義。整體分布要說出各狀態的含義，並主動點出最大的陷阱：`RUNNABLE` 不等於在用 CPU，阻塞在 socket read 的執行緒仍是 RUNNABLE，要對照實際 CPU 使用率與堆疊頂端的原生方法名。接著給 `BLOCKED` 與 `WAITING` 的精確區別，並指出關鍵推論——`ReentrantLock` 的等待顯示為 `WAITING`，只看 BLOCKED 會完全漏掉 JUC 鎖的爭用。強調單次轉儲只是快照，要連抓三到五次比對才能區分「卡住」與「正在跑」。加分點是兩個實務技巧：自訂執行緒名稱讓問題一眼可辨；以及 `top -H` 找出 CPU 最高的執行緒、轉十六進位後用 `nid=` 在轉儲裡比對。

## 講稿

我的判讀順序是先看整體分布、再看熱點堆疊、最後看鎖關係。

整體分布就是各狀態各有幾個執行緒。大量 BLOCKED 指向鎖爭用。大量等待狀態如果集中在執行緒池閒置那通常正常，但如果在業務邏輯上，就代表在等某個不會來的東西。

這裡有一個最大的陷阱要講。RUNNABLE 不等於在用 CPU。阻塞在 socket 讀取的執行緒仍然是 RUNNABLE，因為 JVM 不知道原生方法內部在做什麼。所以看到幾百個 RUNNABLE 不代表 CPU 爆滿，要對照實際的使用率跟堆疊頂端的方法名。

還有一個精確的區別。BLOCKED 專指在等待進入 synchronized 區塊，而 JUC 的鎖走的是 park，顯示成 WAITING。所以只看 BLOCKED 的數量，會完全漏掉 JUC 鎖的爭用。

另外單次轉儲只是一張快照。要判斷是卡住還是正在跑，必須連抓三到五次比對，堆疊沒變的才是真的卡住。

最後一個實用技巧，用 top 加 H 找出 CPU 最高的原生執行緒，轉成十六進位之後在轉儲裡比對，就能找出真正吃 CPU 的那個。

## 常見追問

### 執行緒轉儲會不會影響線上服務？

**核心答案**：`jstack` 需要 JVM 走到**安全點**才能抓取所有執行緒的堆疊，所以它會造成一次短暫的 STW 停頓。對大多數應用來說這個停頓是**毫秒級**，抓幾次完全可以接受。真正需要小心的是**執行緒數極多**（幾千個）或**堆疊很深**的應用，此時單次抓取可能到數百毫秒。

**詳細解析**：實務上的建議是：**排查時不要吝於抓轉儲**——它的成本遠小於「猜不出原因而讓故障延長」的成本。但要避免**在自動化腳本裡高頻抓取**（例如每秒一次），那會累積成可觀的停頓。虛擬執行緒的轉儲是另一回事——`jcmd Thread.dump_to_file` 專門處理它，**不需要安全點**（虛擬執行緒的堆疊在堆積上），所以幾乎沒有停頓，而且輸出可以是 JSON 格式包含任務的樹狀結構。這是虛擬執行緒在可觀測性上的一個實際優勢，值得提及。

**面試回答方式**：給明確答案——需要安全點所以有 STW，但通常是毫秒級，抓幾次可接受；執行緒極多或堆疊很深時才需小心。給實務建議：排查時不要吝於抓，但別在腳本裡高頻抓。加分點是指出虛擬執行緒的轉儲不需要安全點（堆疊在堆積上），幾乎沒有停頓且可輸出含任務樹狀結構的 JSON——這是它在可觀測性上的實際優勢。

### 看到大量執行緒在 park 上等待，怎麼判斷正不正常？

**核心答案**：看**堆疊的下一幀是誰**。如果是 `ThreadPoolExecutor.getTask` 或 `LinkedBlockingQueue.take`，那是執行緒池的閒置執行緒在等任務，完全正常。如果是 `AbstractQueuedSynchronizer` 的 `acquire` 相關幀，那是**在等一把 JUC 鎖**，需要進一步找持有者。如果是 `CompletableFuture.waitingGet` 或 `Future.get`，那是**在等一個非同步結果**——這常常是問題所在（等待的東西可能永遠不會來）。

**詳細解析**：最需要警覺的是「大量執行緒等在 `Future.get` 上」，因為它常常意味著執行緒池耗盡型死鎖：池裡的任務提交了子任務到同一個池並等待結果，而所有執行緒都在等自己的子任務。這種死鎖 JVM 偵測不到（沒有監視器鎖形成環），轉儲上只顯示大家都在等待，需要靠「等待者與被等待者在同一個池」這個線索識別。判斷方法是看執行緒名稱——如果等待的執行緒與應該執行子任務的執行緒屬於同一個池，就是這個問題。

**面試回答方式**：給出判斷方式——**看堆疊的下一幀**，並列出三種典型情況（池閒置正常、AQS 是鎖爭用、`Future.get` 常是問題）。重點放在大量執行緒等在 `Future.get` 上這個訊號，說明它常意味著執行緒池耗盡型死鎖，而 JVM 偵測不到（沒有監視器鎖環）。給出識別線索：看執行緒名稱，等待者與應執行子任務者屬於同一個池就是這個問題。

### 除了 jstack，還有哪些工具值得知道？

**核心答案**：四類。**`jcmd`**——功能比 `jstack` 更全（`Thread.print`、`GC.heap_info`、`VM.native_memory`、虛擬執行緒的 `Thread.dump_to_file`），是現在的推薦入口。**非同步剖析器（async-profiler）**——不需要安全點所以沒有偏差，支援 CPU、alloc、lock、wall-clock 多種模式，`wall` 模式能看到等待時間，這是 `jstack` 取樣做不到的。**JFR（Java Flight Recorder）**——低開銷的持續記錄，適合生產環境常駐開啟，事後可以回溯問題發生時的完整狀態。**APM 工具**——提供跨服務的視角，適合定位「哪個服務慢」而非「哪一行慢」。

**詳細解析**：選擇的關鍵是「你要回答的是哪一層的問題」。跨服務的延遲用 APM、單一服務的宏觀行為用 JFR、CPU 或鎖的熱點用 async-profiler、當下卡住的狀態用 jcmd。最常見的錯誤是用錯層次的工具——例如用 CPU 剖析器去找一個「大家都在等」的問題（那些執行緒在 CPU 剖析裡根本不出現）。先判斷症狀屬於哪一類（CPU 高、等待多、記憶體漲、跨服務慢），再選工具，比熟悉任何單一工具都重要。

**面試回答方式**：給四類工具並各配一句能力說明，特別指出 **async-profiler 的 wall 模式能看到等待時間**、**JFR 適合生產常駐**。真正的加分點是收在方法論：選工具的關鍵是「你要回答哪一層的問題」，並點出最常見的錯誤是用錯層次——用 CPU 剖析器找「大家都在等」的問題，那些執行緒根本不出現。
