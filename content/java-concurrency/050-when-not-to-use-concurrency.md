# 題目

什麼情況下不該引入併發？如果一定要用，怎麼把複雜度控制住？

## 核心答案

不該引入併發的情況有四種。**工作量本身不大**——處理一百筆資料的迴圈，平行化的協調成本可能比計算本身還高。**序列部分佔比高**——受 Amdahl 定律限制，優化上限有限，不如先縮小序列部分。**有更簡單的方案**——改演算法、加快取、批次化，這些直接減少工作量，收益不受併發的限制且沒有正確性風險。**團隊無法維護**——併發程式碼的正確性論證困難、bug 難以重現、能審查的人少，長期成本可能遠超收益。

真的需要時，控制複雜度的原則有三條，按優先順序：**第一，消除共享**——不可變物件、執行緒封閉、訊息傳遞（把共享狀態換成傳遞副本）。沒有共享就沒有併發問題。**第二，收斂共享**——把必須共享的可變狀態集中在少數幾個經過仔細設計與審查的類別裡，其餘程式碼完全不碰同步。**第三，用現成的工具**——JUC 的併發集合、`CompletableFuture`、結構化併發都經過大量驗證，自己寫同步邏輯的錯誤率高得多。

## 詳細解析

**「消除共享」有三種具體形態，值得分開理解**。**不可變**——資料建立後不變，讀取者可以任意共享。**執行緒封閉**——資料只被一個執行緒存取，天然不需要同步。**訊息傳遞**——執行緒之間傳遞資料的副本或所有權而不是共享引用，這是 Actor 模型與 Go 的 channel 哲學（「不要透過共享記憶體來通訊，要透過通訊來共享記憶體」）。**三者的共同點是把「同步」從執行期的協調變成設計期的約束**——約束在編譯期或架構上成立，就不需要在執行期驗證。

**「收斂共享」的實際做法是劃出一個小的併發核心**。整個系統只有少數幾個類別涉及共享可變狀態（例如一個狀態管理器、一個計數聚合器），它們被仔細設計、有完整的併發測試、有明確的 `@GuardedBy` 標註；其餘幾萬行業務程式碼完全是單執行緒語意。**這比「每個類別都稍微考慮一點執行緒安全」可靠得多**——後者的實際結果是每個類別都有一點點沒考慮到的地方。

**引入併發前該問的三個問題**：**現在的效能真的不夠嗎**（有沒有量測，還是憑感覺）？**瓶頸真的在 CPU 或延遲嗎**（很多時候是 IO 或下游，加執行緒沒用）？**有沒有非併發的方案**（快取、批次、演算法、預先計算）？**三個問題都是「是」才動手**，而實務上多數情況會停在前兩個。

**併發是一種借貸**：它用**永久的複雜度**換取**當下的效能**。利息以「更難的除錯、更慢的新功能開發、更高的事故風險」的形式持續支付。**所以決定引入併發時，應該像決定引入任何架構複雜度一樣，明確說出換到了什麼、以及這個交換為什麼划算**——說不出具體數字時，通常代表還沒到該用它的時候。

## 面試回答方式

先給**四種不該引入的情況**（工作量小、序列佔比高、有更簡單的方案、團隊無法維護），並特別把最後一項講實在——正確性論證困難、bug 難重現、能審查的人少，長期成本可能超過收益。接著給**三條控制複雜度的原則並排出優先順序**：消除共享（不可變、執行緒封閉、訊息傳遞）、收斂共享（劃出一個小的併發核心）、用現成工具。**「消除共享」要展開**——三種形態的共同點是**把同步從執行期的協調變成設計期的約束**。「收斂共享」的價值要對比說明：**少數幾個仔細設計的類別，比每個類別都稍微考慮一點可靠得多**。最後給引入前的三個問題（效能真的不夠嗎、瓶頸真的在這裡嗎、有沒有非併發方案），並用一個定位收尾：**併發是用永久的複雜度換當下的效能，說不出具體數字就代表還沒到該用它的時候**。

## 講稿

不該引入併發的情況我會講四種。工作量本身不大的時候，協調成本可能比計算還高。序列部分佔比高的時候，受定律限制上限有限。有更簡單的方案的時候，改演算法或加快取直接減少工作量，收益不受限制而且沒有正確性風險。還有團隊無法維護的時候，併發的正確性論證困難、問題難以重現、能審查的人很少。

真的需要的話，我控制複雜度有三條原則，而且有優先順序。

第一是消除共享。不可變、執行緒封閉、訊息傳遞。這三種的共同點是把同步從執行期的協調變成設計期的約束。約束在編譯期或架構上成立，就不需要在執行期驗證。

第二是收斂共享。整個系統只有少數幾個類別涉及共享可變狀態，它們被仔細設計、有完整測試、有明確標註。其餘幾萬行業務程式碼完全是單執行緒語意。這比每個類別都稍微考慮一點可靠得多，因為後者的實際結果是每個類別都有一點沒考慮到。

第三是用現成的工具，自己寫同步邏輯的錯誤率高得多。

最後我想說，併發是一種借貸，用永久的複雜度換當下的效能。說不出具體換到多少，通常代表還沒到該用它的時候。

## 常見追問

### 訊息傳遞真的比共享記憶體好嗎？

**核心答案**：**它把問題換成了另一種形式，不是消除了問題**。訊息傳遞確實消除了資料競爭（沒有共享的可變狀態就沒有競態），但帶來了新的問題：**訊息順序**（多個發送者的訊息順序不確定）、**背壓**（收件匣滿了怎麼辦）、**死鎖的新形態**（兩個 actor 互相等對方的回覆）、以及**除錯困難**（因果關係散在訊息流中而不在堆疊上）。

**詳細解析**：所以它的優勢是**問題的形態變了，而新的形態更容易推理**。資料競爭是「在某個奈秒級的時間窗口裡兩個執行緒同時碰了同一塊記憶體」，而訊息死鎖是「A 在等 B 的回覆、B 在等 A 的回覆」——後者可以在架構圖上看出來，前者不能。**這正是它的真正價值：把不可見的執行期問題變成可見的結構問題。** 代價是效能（複製訊息而非共享引用）與延遲（訊息傳遞有排隊）。**判斷的方式是問：這個系統的併發複雜度主要來自「共享狀態的協調」還是「元件間的互動」？** 前者用訊息傳遞會有大改善，後者不會。

**面試回答方式**：先明確指出它**把問題換成另一種形式而非消除**，並列出新問題（訊息順序、背壓、新形態的死鎖、除錯困難）。真正的洞見放在中間：**新形態更容易推理**——資料競爭是奈秒級窗口裡的不可見事件，訊息死鎖是架構圖上看得見的循環等待。收在判準：問系統的併發複雜度主要來自共享狀態協調還是元件互動，前者才會有大改善。

### 怎麼向團隊論證「不要用併發」？

**核心答案**：用**數字與替代方案**，不要用「太複雜」這種主觀理由。具體做法是：**先量測**——證明目前的瓶頸不在需要併發的地方（例如 CPU 只有 30%、延遲來自下游）。**再給替代方案的預估收益**——「加一層快取可以砍掉 60% 的下游呼叫，比平行化那 5% 的計算收益大得多」。**最後才談成本**——併發的維護成本、事故風險、以及過去類似改動的實際經驗。

**詳細解析**：**論證的順序很重要**。從「太複雜」開始會被聽成保守與抗拒改變；從數據開始則是在同一個框架下討論。而且**提出替代方案是關鍵**——反對一個方案而不給出更好的路徑，很難說服人。如果替代方案的收益確實不如併發，那就該誠實承認並轉向「怎麼把併發做對」（劃出核心、加測試、安排審查）。**技術決策的說服力來自「我算過而且我有更好的方案」，不是來自「我覺得風險高」。** 這個溝通模式適用於所有引入複雜度的提案，不只是併發。

**面試回答方式**：給三步順序（先量測、再給替代方案的預估收益、最後才談成本）並強調**順序很重要**——從「太複雜」開始會被聽成抗拒改變。點出**提出替代方案是關鍵**，反對而不給出更好的路徑很難說服人；如果替代方案確實不如併發，就誠實轉向「怎麼把併發做對」。收在可遷移的原則：**說服力來自「我算過而且有更好的方案」，不是「我覺得風險高」**。

### 既有的併發程式碼難以維護時，怎麼重構？

**核心答案**：分四步，**每一步都要能獨立驗證**。**第一，補上可觀測性**——加入指標與日誌，先弄清楚它實際的行為（哪些路徑真的併發、爭用在哪、有沒有已經在發生的異常狀態）。**第二，補上不變量檢查**——用斷言把「應該成立的條件」寫進程式碼，讓潛在的損壞立刻暴露。**第三，縮小共享面**——把不需要共享的狀態改成區域變數或不可變物件，這通常能砍掉大部分同步程式碼。**第四，替換同步機制**——把手寫的 wait/notify 換成 JUC 的工具，把散落的鎖收斂成一個明確的併發核心。

**詳細解析**：**順序不能顛倒**。直接跳到第四步替換同步機制是最危險的做法——在不了解實際行為、也沒有不變量檢查的情況下改動同步邏輯，很可能引入新的競態而且測不出來。**前兩步的價值在於建立「改動是否安全」的判斷依據**：有了指標與斷言，重構之後至少能觀察到行為是否改變。另外**每一步都應該獨立提交與部署**，讓問題能被歸因到具體的改動——併發問題往往在部署後幾天才顯現，一次改十處會讓歸因變得不可能。**這與所有高風險重構的原則相同：小步、可觀測、可回退。**

**面試回答方式**：給四步並強調**順序不能顛倒**——直接替換同步機制最危險，因為不了解實際行為又沒有不變量檢查，引入的新競態測不出來。說明前兩步的價值是**建立「改動是否安全」的判斷依據**。加分點是強調**每一步獨立提交與部署**，因為併發問題往往幾天後才顯現，一次改十處會讓歸因不可能。收在通用原則：小步、可觀測、可回退。
