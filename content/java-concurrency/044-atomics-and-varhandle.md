# 題目

`java.util.concurrent.atomic` 提供了哪些工具？`VarHandle` 又補上了什麼？

## 核心答案

原子類別分成四組。**基本型別**（`AtomicInteger`、`AtomicLong`、`AtomicBoolean`）——CAS 保證的原子讀改寫。**引用**（`AtomicReference`，以及帶版本戳的 `AtomicStampedReference` 與帶布林標記的 `AtomicMarkableReference`，用來解決 ABA）。**陣列**（`AtomicIntegerArray` 等，對單一元素做原子操作，比整個陣列一把鎖細得多）。**欄位更新器**（`AtomicIntegerFieldUpdater` 等，用反射對普通的 volatile 欄位做原子操作，**省掉每個物件一個 Atomic 包裝物件的記憶體**）。

`VarHandle`（JDK 9）是欄位更新器與 `sun.misc.Unsafe` 的正式替代品，它補上兩件事。**安全的低階存取**——不需要反射的執行期成本，也不需要用內部 API。**明確的記憶體順序模式**——`getPlain`（無任何保證）、`getOpaque`（保證原子性但無順序）、`getAcquire`／`setRelease`（單向屏障）、`getVolatile`／`setVolatile`（全屏障）。**這讓「只需要原子性但不需要全屏障」的場景可以省掉昂貴的 `StoreLoad`。**

一般應用幾乎用不到 `VarHandle`；它的價值在於**寫高效能函式庫時，不必再依賴 `Unsafe` 這種隨時可能被封的內部 API**。

## 詳細解析

**欄位更新器解決的是記憶體問題**。一個有一百萬個實例的類別若用 `AtomicInteger` 欄位，就是一百萬個額外的物件（每個至少 16 位元組）。改用 `volatile int` 加一個**靜態的** `AtomicIntegerFieldUpdater`，記憶體回到一個 int。代價是欄位必須是 `volatile` 且非私有（更新器要能存取），而且**每次操作有反射檢查的開銷**。`VarHandle` 在這一點上更好——它在初始化時完成檢查，之後的操作可以被 JIT 內聯成與直接存取相同的指令。

**記憶體順序模式的區別是這題的深度所在**。`volatile` 給的是最強的保證（全序），但很多場景不需要那麼強。例如**只是想原子地讀一個計數器用於統計**，不需要它與周圍的讀寫建立任何順序關係——用 `getOpaque` 就夠了，可以省掉屏障。**acquire／release 則對應了「發布與訂閱」的典型模式**：寫入端用 `setRelease` 確保之前的寫入都可見，讀取端用 `getAcquire` 確保之後的讀取不會提前。這比 volatile 的雙向全屏障便宜，而且**表達的語意更精確**——程式碼明確說出了「我需要的是哪個方向的順序」。

**`Unsafe` 為什麼要被取代**：它是 `sun.misc` 下的內部 API，卻被幾乎所有高效能框架（Netty、Kafka、Hazelcast、各種序列化庫）依賴。這讓 JDK **無法自由修改內部實作**，也讓那些框架在模組化之後面臨破壞。`VarHandle` 加上 `MethodHandles.Lookup` 提供了同等能力的**受支援的公開 API**，讓 JDK 能逐步收回 `Unsafe`。**這是「內部 API 被廣泛依賴」這個問題的標準解法：提供正式的替代品，再逐步關閉舊路徑。**

**實務上的建議是：一般業務程式碼用原子類別就好**。`VarHandle` 的 API 冗長（要用 `MethodHandles.lookup().findVarHandle(...)` 取得，型別在執行期檢查）、錯誤訊息不友善、而且用錯記憶體模式的後果是難以重現的競態。**它的存在是為了讓函式庫作者不必用 `Unsafe`，不是為了讓應用程式碼更快。**

## 面試回答方式

先把原子類別分成**四組**（基本型別、引用含解 ABA 的變體、陣列、欄位更新器）並說明欄位更新器解決的是**記憶體問題**——百萬實例時省掉百萬個包裝物件。接著給 `VarHandle` 補上的兩件事：**安全的低階存取**與**明確的記憶體順序模式**。後者是深度所在，要展開：`volatile` 是最強的全序保證，但很多場景不需要——只讀計數器用 `getOpaque` 就夠、發布訂閱模式用 `setRelease`／`getAcquire` 這對單向屏障，**比 volatile 便宜且語意更精確**。加分點是說明 **`Unsafe` 被取代的理由**：它是內部 API 卻被所有高效能框架依賴，讓 JDK 無法自由演進，`VarHandle` 是「提供正式替代品再逐步關閉舊路徑」的標準解法。收在務實建議：一般業務程式碼用原子類別就好，`VarHandle` 是給函式庫作者的。

## 講稿

原子類別我分成四組。基本型別、引用、陣列、還有欄位更新器。

欄位更新器解決的是記憶體問題。一個有一百萬個實例的類別，如果用 AtomicInteger 欄位，就是一百萬個額外物件。改用 volatile 整數加一個靜態的更新器，記憶體就回到一個整數。

VarHandle 是欄位更新器跟內部不安全 API 的正式替代品，它補上兩件事。第一是安全的低階存取，不需要反射的執行期成本。第二是明確的記憶體順序模式，這個比較有意思。

volatile 給的是最強的全序保證，但很多場景不需要那麼強。比如只是要原子地讀一個計數器做統計，不需要它跟周圍的讀寫建立任何順序關係，用最弱的那個模式就夠，可以省掉屏障。而發布訂閱這種模式用單向屏障就好，寫入端確保之前的寫入可見，讀取端確保之後的讀取不會提前。這比雙向全屏障便宜，而且語意更精確。

不過我要說，一般業務程式碼用原子類別就好。VarHandle 的 API 很冗長、用錯記憶體模式的後果是難以重現的競態。它的存在是為了讓函式庫作者不必用內部 API，不是為了讓應用程式碼更快。

## 常見追問

### AtomicStampedReference 怎麼解決 ABA？

**核心答案**：它把「引用」與「一個整數戳記」**打包成一對，用一次 CAS 同時比較兩者**。每次修改都遞增戳記，所以即使引用從 A 變成 B 又變回 A，戳記已經從 1 變成 3，CAS 會發現不一致而失敗。內部實作是一個不可變的 `Pair` 物件加上 `AtomicReference`——**用「換掉整個 Pair」把兩個值的原子性合成一個**。

**詳細解析**：`AtomicMarkableReference` 是簡化版，只帶一個布林標記（「這個節點是否已被邏輯刪除」），用在無鎖鏈結串列的刪除演算法中。**要注意 ABA 不是所有場景都需要處理**——如果程式邏輯只在乎「當前值是不是 A」而不在乎「中間有沒有變過」，那 ABA 根本不是問題。**典型需要處理的是「引用指向的物件會被回收重用」的場景**（無鎖堆疊的節點池、C 語言的手動記憶體管理），而 Java 有 GC，只要還持有引用記憶體就不會重用，所以**純 Java 的無鎖結構往往不需要戳記**。這也解釋了為什麼 `ConcurrentLinkedQueue` 沒有用它。

**面試回答方式**：先給機制——**引用與戳記打包成不可變的 Pair，用一次 CAS 同時比較**，修改時遞增戳記。真正的加分點是後半段：**ABA 不是所有場景都需要處理**，只在乎當前值時它不是問題；典型需要處理的是物件會被回收重用的場景，而 **Java 有 GC 所以純 Java 的無鎖結構往往不需要戳記**，這正是 `ConcurrentLinkedQueue` 沒用它的原因。

### getAcquire 與 setRelease 對應什麼使用模式？

**核心答案**：**發布與訂閱**——寫入端準備好一批資料後，用 `setRelease` 寫入一個「就緒」標記，保證**之前的所有寫入都不會被重排到這個寫入之後**；讀取端用 `getAcquire` 讀那個標記，保證**之後的所有讀取都不會被重排到這個讀取之前**。兩者配對就建立了 happens-before，讀取端讀到標記為真時，必然看得到寫入端準備的全部資料。

**詳細解析**：這比 volatile 便宜的原因是**它只約束一個方向**。volatile 寫需要 `StoreLoad`（最貴的屏障，要排空存放緩衝區），而 release 寫只需要 `StoreStore`（確保之前的寫不越過），在 x86 上甚至不需要任何指令。**代價是它不保證「全域一致的順序」**——多個 acquire／release 對之間的相對順序不像 volatile 那樣有全序保證，所以需要多個變數之間有全域順序時（例如 Dekker 演算法那類），仍然必須用 volatile。**判斷的方式是問：我需要的是「這一對之間的順序」還是「所有執行緒對所有變數看到相同的順序」？** 前者用 acquire／release，後者用 volatile。

**面試回答方式**：用**發布與訂閱**模式說明兩者的配對關係與各自約束的方向，並指出配對後建立 happens-before。給出便宜的原因——**只約束一個方向**，release 寫只需要 `StoreStore` 而非最貴的 `StoreLoad`。誠實給出代價：不保證全域一致順序。收在判準：**需要「這一對之間的順序」用 acquire／release，需要「所有執行緒看到相同全序」用 volatile**。

### 為什麼 JDK 要花這麼大力氣取代 Unsafe？

**核心答案**：因為 `sun.misc.Unsafe` 讓 **JDK 的內部實作變成了事實上的公開 API**。幾乎所有高效能框架都依賴它，於是 JDK 一旦修改相關的內部結構，整個生態就會壞掉——**這等於 JDK 失去了演進自己內部實作的自由**。同時它也是安全風險：它能繞過所有型別檢查與存取控制，直接讀寫任意記憶體。

**詳細解析**：解法遵循一個標準路徑：**先提供功能對等的正式 API**（`VarHandle` 取代原子操作與欄位存取、`MemorySegment`／FFM API 取代堆外記憶體操作、`MethodHandles` 取代部分反射技巧），**再逐步限制舊路徑**（模組化封裝、預設警告、最終移除）。這個過程走了十年以上，因為生態遷移需要時間。**這件事的一般教訓是：任何被廣泛依賴的東西都會變成 API，不管你怎麼命名它**（`sun.misc`、`internal`、加底線前綴都攔不住）。真正有效的是**提供夠好的正式替代品**，讓大家沒有理由用內部 API。**能把這個案例講成一個 API 設計與生態演進的教訓，比背出 `VarHandle` 的方法名有價值得多。**

**面試回答方式**：核心是「**內部實作被廣泛依賴後就變成事實上的公開 API，JDK 因此失去演進自由**」，並補上安全風險（繞過所有型別檢查與存取控制）。給出標準解法路徑：先提供功能對等的正式 API，再逐步限制舊路徑，並說明這走了十年以上。收在一般教訓：**被廣泛依賴的東西都會變成 API，命名攔不住**，真正有效的是提供夠好的正式替代品。
