# 題目

什麼是偽共享？為什麼兩個執行緒各自更新自己的變數也會互相拖慢？

## 核心答案

CPU 快取的最小交換單位不是位元組而是**快取行**（cache line，主流架構是 64 位元組）。如果兩個執行緒各自更新的變數**恰好落在同一條快取行上**，即使它們在邏輯上完全獨立，硬體的快取一致性協定仍會認為這條行被爭用——核心 A 寫入時會使核心 B 的那份快取失效，核心 B 下次讀取自己的變數就要重新從記憶體或另一個核心取回。這就是**偽共享**：沒有真正的資料共享，卻付出了共享的代價。

它的影響可以很大。多執行緒更新相鄰陣列元素的情境下，加上填充讓每個元素獨佔一條快取行，吞吐提升數倍是常見的結果。

解法有兩種。**手動填充**——在變數前後加上足夠的無用欄位把快取行撐開（傳統做法，但可能被 JIT 的欄位重排最佳化掉）。**`@Contended` 註解**（JDK 8，`jdk.internal.vm.annotation.Contended`）——由 JVM 負責填充，需要 `-XX:-RestrictContended` 才能在使用者程式碼中生效。JDK 內部的 `LongAdder`、`ConcurrentHashMap` 的計數格子都用了它。

## 詳細解析

**`LongAdder` 是理解偽共享最好的例子**。`AtomicLong` 在高爭用下慢，不只因為 CAS 失敗重試，更因為所有執行緒都在同一條快取行上競爭。`LongAdder` 把計數拆成一個 `Cell` 陣列，每個執行緒依雜湊落到不同格子，而每個 `Cell` 都標了 `@Contended` 讓它獨佔快取行。少了這個註解，格子雖然分開了但仍擠在同幾條快取行上，分散的效果會大打折扣。「拆分資料」與「拆分快取行」是兩件必須同時做的事，這是這題最有價值的認識。

**判斷是否遇到偽共享很困難**，因為它不會出現在任何 Java 層級的指標上——沒有鎖爭用、沒有 GC、CPU 使用率還很高（因為忙著等快取）。診斷需要硬體效能計數器：Linux 的 `perf c2c` 專門用來偵測快取行的跨核爭用，`perf stat` 的快取失效率也是線索。在 Java 層面最實用的線索是「增加執行緒數卻不增加吞吐、甚至下降」，而且沒有明顯的鎖爭用。

它不是普遍問題，只在特定形態出現：高頻寫入的**相鄰**變數、被多個執行緒各自更新的陣列元素、以及並排存放的計數器。唯讀的共享資料完全不受影響（多個核心可以同時持有同一條行的唯讀副本），所以「共享」本身不是問題，「共享 + 寫入」才是。這解釋了為什麼不可變資料在多核上擴展得那麼好。

**不要預先最佳化**：填充會浪費記憶體（每個變數佔 64 到 128 位元組），也讓程式碼變得難懂。只有在量測確認吞吐無法隨核心數擴展、且排除了鎖與 GC 之後，才值得往這裡查。反過來說，寫高併發資料結構（佇列、計數器、環形緩衝）時，把它當成設計階段就要考慮的因素是合理的——Disruptor 的高效能有一部分正是來自對快取行的細緻安排。

## 面試回答方式

先給機制——快取的最小單位是 64 位元組的快取行，兩個獨立變數落在同一行時，一方寫入會使另一方的快取失效，於是沒有邏輯共享卻付出了共享的代價。用 `LongAdder` 當主例子，並給出最有價值的一句：拆分資料與拆分快取行是兩件必須同時做的事——格子分開但擠在同幾條行上，分散效果會大打折扣。接著誠實講診斷困難：它不出現在任何 Java 層指標上，線索是「加執行緒不加吞吐且沒有鎖爭用」，確認要靠 `perf c2c` 這類硬體計數器。最後給界線：**唯讀共享完全不受影響**，是「共享加寫入」才有問題，這也解釋了不可變資料為什麼擴展性好；而且不該預先最佳化，除非量測排除了鎖與 GC。

## 講稿

CPU 快取的最小交換單位不是位元組，是六十四位元組的快取行。如果兩個執行緒各自更新的變數剛好落在同一條快取行上，就算它們邏輯上完全獨立，硬體的一致性協定還是會認為這條行被爭用。一邊寫入會讓另一邊的快取失效，對方下次讀自己的變數就要重新取回。

這就是偽共享。沒有真正的資料共享，卻付出了共享的代價。

最好的例子是 LongAdder。它慢的原因不只是 CAS 重試，更因為所有執行緒都在同一條快取行上競爭。LongAdder 把計數拆成一個格子陣列，但關鍵是每個格子都做了填充讓它獨佔快取行。少了這一步，格子雖然分開但還是擠在同幾條行上，分散的效果會大打折扣。

我想強調的是，拆分資料跟拆分快取行是兩件必須同時做的事。

診斷很困難，因為它不會出現在任何 Java 層級的指標上。沒有鎖爭用、沒有 GC、CPU 使用率還很高。最實用的線索是增加執行緒卻不增加吞吐，而且找不到明顯的鎖爭用。

## 常見追問

### 為什麼唯讀的共享資料不會有偽共享問題？

**核心答案**：因為快取一致性協定（MESI 這類）允許多個核心同時持有同一條快取行的「共享」狀態副本——大家都可以讀，不需要任何協調。只有當某個核心要**寫入**時，它必須先把該行轉成「獨佔／修改」狀態，這會使其他核心的副本失效。沒有寫入就沒有狀態轉換，也就沒有失效與重新取得的成本。

**詳細解析**：這正是不可變資料在多核上擴展性極佳的硬體層原因，比「不需要同步」這個軟體層理由更根本。同樣的道理解釋了幾個實務現象：讀多寫少的快取效能好、把設定資料做成不可變的全域物件不會成為瓶頸、以及把「熱寫入的欄位」與「常讀的欄位」放在不同物件裡是有意義的最佳化（避免頻繁寫入的計數器讓旁邊的唯讀設定不斷失效）。最後這一點在設計高併發物件時很實用：依「讀寫模式」而不是依「邏輯歸屬」分組欄位。

**面試回答方式**：先給硬體層的答案——一致性協定允許多核同時持有唯讀副本，只有寫入才觸發狀態轉換與失效。然後把它連到一個更有價值的推論：這是不可變資料擴展性好的硬體層原因，比「不用同步」更根本。加分點是給出可操作的設計建議：依讀寫模式而非邏輯歸屬分組欄位，把熱寫入的計數器與常讀的設定分開存放。

### @Contended 為什麼預設對使用者程式碼無效？

**核心答案**：因為它的代價是**記憶體膨脹**——一個標了 `@Contended` 的欄位會被填充到獨佔至少一條快取行（實務上常是 128 位元組，因為某些處理器會預取相鄰的行）。如果使用者隨手到處加，物件大小會暴增、快取容量被浪費、GC 壓力上升。JDK 因此要求明確加上 `-XX:-RestrictContended` 才對使用者程式碼生效，等於要求使用者主動確認自己知道代價。

**詳細解析**：它在 JDK 9 之後移到 `jdk.internal.vm.annotation` 套件並被模組系統封裝，所以應用程式碼要用還需要 `--add-exports`。這個逐步加高的門檻反映了 JDK 的態度：這是給函式庫作者與 JDK 內部用的工具，不是給一般應用的。應用層若真的遇到偽共享，更務實的做法是**調整資料結構**——把熱點欄位分散到不同物件、或用陣列時刻意留出間隔（例如只用索引 0、8、16…），這些做法不依賴內部 API 也不受 JDK 版本影響。能提出「不用註解也能解決」的替代方案，比背出註解名稱更有價值。

**面試回答方式**：先給理由——**記憶體膨脹**，一個欄位可能被填充到 128 位元組，隨手加會讓物件暴增並浪費快取。指出 JDK 9 後還被模組系統封裝，門檻逐步加高，反映它是給函式庫作者的工具。真正的加分點是提出不依賴內部 API 的替代方案：把熱點欄位分散到不同物件，或用陣列時刻意留出索引間隔。

### Disruptor 為什麼比 BlockingQueue 快？

**核心答案**：三個層次的差別。**資料結構**——它用預先配置的**環形緩衝**，元素在建構時就全部建立好，執行期不配置也不回收物件，GC 壓力接近零；`ArrayBlockingQueue` 雖然也是陣列，但仍要處理鎖與條件變數。**同步機制**——它用序號加 CAS 而不是鎖，消費者用忙等或退讓策略而不是條件變數的掛起喚醒，**省掉了上下文切換**。**記憶體佈局**——生產者與消費者的序號各自做了快取行填充，避免偽共享。

**詳細解析**：代價同樣明確。**忙等策略會持續消耗 CPU**——在核心數充裕、追求極低延遲的場景（金融交易）這是划算的交換，在一般的 Web 服務上則是浪費（那些 CPU 可以拿去服務其他請求）。**環形緩衝的大小固定**，滿了就必須阻塞或丟棄，不像無界佇列能吸收突發。而且它的程式設計模型（事件處理器、依賴關係圖）與一般的佇列消費差異不小，團隊的學習與維護成本是真實的。所以它的適用範圍很窄：單機、極低延遲、可以獨佔 CPU 的場景；一般的服務用 `ArrayBlockingQueue` 或 `LinkedBlockingQueue` 就夠了。

**面試回答方式**：把差別分成資料結構、同步機制、記憶體佈局三層，每層一句具體說明（預配置環形緩衝零 GC、序號加 CAS 省掉上下文切換、序號做快取行填充）。然後誠實給代價：忙等消耗 CPU、緩衝大小固定無法吸收突發、程式設計模型的學習成本。收在適用範圍——單機、極低延遲、可獨佔 CPU，一般服務用普通阻塞佇列就夠。
