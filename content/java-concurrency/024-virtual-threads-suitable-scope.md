# 題目

Java 21 正式發布的虛擬執行緒（Virtual Threads）解決了什麼問題？它是不是可以完全取代傳統的執行緒池？

## 核心答案

虛擬執行緒是 JDK 用非常輕量的方式實作的使用者態執行緒，由少量的平台執行緒（載體執行緒）承載，數量可以輕鬆達到百萬級，特別適合「大量、高並發、以阻塞式 I/O 為主」的場景，能大幅簡化高並發程式碼（不需要再用複雜的非同步回呼）。但它不是萬能的：CPU 密集型運算、需要限制真實並行度的場景、或大量使用 `synchronized` 進行長時間阻塞的舊程式碼，仍然更適合傳統執行緒池或需要額外調整。

## 詳細解析

**虛擬執行緒解決的核心問題**：傳統的 Java 執行緒（平台執行緒）是作業系統執行緒的一對一封裝，建立成本高（預設棧空間約 1MB）、數量受系統資源限制（通常幾千個就是上限）。在「每個請求綁定一個執行緒、執行緒大部分時間在等待 I/O（資料庫查詢、呼叫下游服務）」的傳統同步阻塞式架構下，高並發場景很容易把執行緒池耗盡。虛擬執行緒讓我們可以繼續寫簡單直觀的同步阻塞式程式碼（不需要 `CompletableFuture` 鏈式回呼那種心智負擔），但底層由 JVM 自動把「阻塞在 I/O」的虛擬執行緒與載體執行緒解綁，載體執行緒可以去執行其他虛擬執行緒，等 I/O 完成後再重新排程回來，實現用少量作業系統執行緒支撐海量並發任務。

**運作機制簡述**：虛擬執行緒不直接綁定作業系統執行緒，而是由 JVM 排程到一小組載體執行緒（predominantly 使用 `ForkJoinPool`）上執行；當虛擬執行緒執行到會阻塞的操作（如網路 I/O、`java.util.concurrent` 中支援虛擬執行緒的阻塞方法），JVM 會自動把它從載體執行緒上「卸載」，讓載體執行緒去執行其他虛擬執行緒，等阻塞操作完成後，虛擬執行緒會被重新排程到某個載體執行緒上繼續執行。

**適用場景**：I/O 密集、需要大量並發連線（例如每個 HTTP 請求都用一個獨立虛擬執行緒處理）、目前用複雜非同步框架只是為了突破執行緒數限制的場景，改用虛擬執行緒能大幅簡化程式碼且提升可維護性。

**不適用或需要注意的場景**：

1. **CPU 密集型運算**：虛擬執行緒的優勢在於「大量執行緒等待 I/O」，如果任務本身是持續佔用 CPU 運算（沒有阻塞等待），虛擬執行緒再多也受限於實體 CPU 核心數，這種場景用 Fork/Join 或普通執行緒池配合合理的並行度反而更直接。
2. **`synchronized` 區塊內的長時間阻塞操作（JDK 21 之前的限制）**：早期版本中，虛擬執行緒若在 `synchronized` 區塊內執行阻塞操作，會導致載體執行緒被一併「釘住（pinned）」無法卸載，喪失虛擬執行緒的優勢（JDK 24 已經改進了這個限制，但升級前的環境仍需注意）。
3. **需要嚴格限制真實併發存取數量的場景**：例如限制同時對某個下游服務的並行呼叫數，這時候用 `Semaphore` 顯式限流仍然是必要的，虛擬執行緒的「輕量」不代表「不需要限流」——反而因為建立虛擬執行緒幾乎沒有成本，更容易不小心對下游造成過大瞬間壓力。
4. **需要執行緒本地變數（`ThreadLocal`）大量長期快取昂貴資源的舊模式**：因為虛擬執行緒數量巨大且生命週期通常較短，過去「執行緒池固定幾十個執行緒、每個執行緒的 `ThreadLocal` 快取一個昂貴連線」的模式不再適用，需要改用 JDK 21 引入的 `ScopedValue` 或重新設計資源管理方式。

**面試回答要點**：不要只說「虛擬執行緒更快更輕量」，而要說清楚它解決的具體問題（I/O 密集場景下執行緒數量瓶頸）、底層機制（載體執行緒 + 卸載重新排程），以及它**不是**用來加速 CPU 密集運算、也不能替代限流機制，這樣的回答才顯得有實際理解而非死記硬背關鍵字。
