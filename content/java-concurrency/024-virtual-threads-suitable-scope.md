# 題目

Java 21 正式發布的虛擬執行緒（Virtual Threads）解決了什麼問題？它是不是可以完全取代傳統的執行緒池（Thread Pool）？

## 核心答案

虛擬執行緒是 JDK 用非常輕量的方式實作的使用者態執行緒，由少量的平台執行緒（載體執行緒）承載，數量可以輕鬆達到百萬級，特別適合「大量、高並發、以阻塞式 I/O 為主」的場景。但它不是萬能的：CPU 密集型運算、需要限制真實並行度的場景、或大量使用 `synchronized` 進行長時間阻塞的舊程式碼，仍然更適合傳統執行緒池或需要額外調整。

## 詳細解析

**虛擬執行緒解決的核心問題**：傳統平台執行緒建立成本高、數量受限。在「每個請求綁定一個執行緒、大部分時間在等待 I/O」的傳統同步阻塞式架構下，高並發場景容易把執行緒池耗盡。虛擬執行緒讓開發者能繼續寫同步阻塞式程式碼，底層由 JVM 自動把「阻塞在 I/O」的虛擬執行緒與載體執行緒解綁。

**運作機制**：虛擬執行緒由 JVM 排程到一小組載體執行緒上執行；執行到會阻塞的操作時，JVM 自動把它從載體執行緒上「卸載」，等阻塞操作完成後重新排程回某個載體執行緒。

**不適用或需要注意的場景**：CPU 密集型運算（受限於實體核心數）；早期版本 `synchronized` 區塊內長時間阻塞會導致載體執行緒被「釘住（pinned）」；需要嚴格限流（Rate Limiting）的場景（虛擬執行緒建立幾乎沒有成本，更容易對下游造成過大瞬間壓力）；過去依賴 `ThreadLocal` 長期快取昂貴資源的模式需要改用 `ScopedValue`。

## 面試回答方式

這題最容易的陷阱是把虛擬執行緒講成「無腦升級、全面取代執行緒池」，這會讓面試官覺得你只知道表面的行銷話術。正確答法是先講清楚「它解決的具體問題」（I/O 密集場景下傳統執行緒數量受限），再講「底層機制」（載體執行緒 + 卸載重新排程），最後務必花時間講「不適用的場景」——尤其是「CPU 密集運算不會變快」和「仍然需要限流」這兩點，這是這題真正的加分關鍵，展現你有能力批判性地評估一個新技術的適用邊界，而不是盲目追捧。

## 常見追問

### 虛擬執行緒和傳統執行緒池的執行緒在 jstack/監控工具中觀察起來有什麼不同？

**核心答案**：虛擬執行緒數量可能極其龐大（成千上萬甚至更多），傳統的 `jstack` 全量導出所有執行緒堆疊在虛擬執行緒場景下會產生海量且難以閱讀的輸出，因此 JDK 提供了專門的工具與指令（例如 `jcmd <pid> Thread.dump_to_file` 搭配新的執行緒傾印格式，或直接觀察載體執行緒的數量與狀態）來更有效地觀察虛擬執行緒的運作狀況，而不是沿用傳統對「幾十到幾千個」平台執行緒設計的排查思路。

**詳細解析**：傳統執行緒池的監控思路建立在「執行緒數量有限、每個執行緒都值得單獨關注」的假設上——例如逐一檢查每個執行緒卡在哪個鎖上；但虛擬執行緒的數量級完全不同，逐一檢視每個虛擬執行緒既不現實也沒有意義，真正該關注的往往是「載體執行緒的數量與利用率」「有多少虛擬執行緒因為 `synchronized` 而被釘住」這類聚合層級的指標，而不是單一虛擬執行緒的狀態。JDK 也相應提供了新的診斷能力（例如 JDK Flight Recorder 中新增了虛擬執行緒相關的事件類型），讓開發者能用適合虛擬執行緒規模的方式進行觀測，而不是把舊工具直接套用在新模型上。

**面試回答方式**：先指出「舊的 `jstack` 逐一檢視執行緒的排查思路在虛擬執行緒的數量級下不再適用」這個核心差異，再提到需要關注的重點轉移到「載體執行緒利用率」「釘住次數」這類聚合指標，展現你理解新技術帶來的不只是效能提升，也伴隨著監控排查方法論的轉變。

### 為什麼虛擬執行緒的引入讓「執行緒池應該設多大」這類經驗公式在 I/O 密集場景下變得不再重要？

**核心答案**：因為傳統的執行緒池大小估算公式（如「CPU 核心數 × (1 + 等待時間/運算時間)」）本質上是在解決「有限的平台執行緒資源該如何分配才能兼顧吞吐量與資源消耗」這個問題；而虛擬執行緒的建立與維護成本極低、數量可以輕鬆達到數十萬甚至更多，在 I/O 密集場景下開發者可以近乎「每個任務都用一個新的虛擬執行緒」而不需要像過去那樣精打細算地控制執行緒數量上限，因為底層真正稀缺的資源（少量的載體執行緒與 CPU 核心）由 JVM 自動排程管理，不再需要開發者手動調校一個「固定大小的執行緒池」。

**詳細解析**：這並不代表「資源限制」這個問題本身消失了——下游資源（例如資料庫連線數、下游服務的處理能力）仍然是有限的，仍然需要透過 `Semaphore` 等機制顯式限流；但「執行緒池本身該設多大」這個特定問題確實變得不再是核心考量，因為執行緒（虛擬執行緒）本身不再是稀缺、昂貴的資源。這個轉變的本質是「把資源限制的關注點，從『執行緒數量』轉移到『真正的下游依賴容量』」，這也呼應了前面提到的「虛擬執行緒仍然需要限流」這個重點——限流的對象變了，但限流本身仍然必要。

**面試回答方式**：強調「不是資源限制消失了，而是限制的對象從『執行緒數量』轉移到『真正的下游依賴容量』」這個轉變本質，避免讓面試官誤以為你認為虛擬執行緒讓所有資源管理問題都消失了，這是這題很容易讓人講過頭、需要特別謹慎表達的地方。

### ScopedValue 相較於 ThreadLocal 在虛擬執行緒場景下解決了什麼問題？

**核心答案**：`ScopedValue`（JDK 21 引入的預覽功能）提供的是「不可變、有明確作用域邊界」的執行緒上下文傳遞方式——值只在明確定義的程式碼區塊內有效，區塊結束後自動失效並釋放，不需要像 `ThreadLocal` 那樣手動呼叫 `remove()` 來清理，天然避免了忘記清理導致的記憶體洩漏（Memory Leak）或資料污染問題，且更適合虛擬執行緒這種數量龐大、生命週期短暫的場景。

**詳細解析**：`ThreadLocal` 的設計是「與執行緒的整個生命週期綁定」，在傳統執行緒池場景下已經有記憶體洩漏風險（見 [[008-threadlocal-memory-leak.md]]），這個風險在虛擬執行緒場景下會被進一步放大——虛擬執行緒數量龐大，如果每個虛擬執行緒都疏忽大意地建立 `ThreadLocal` 資料卻沒有清理，即使單一虛擬執行緒佔用的記憶體不多，乘以龐大的數量後累積起來的影響也不容小覷。`ScopedValue` 從設計上就是不可變的、且透過 `ScopedValue.where(...).run(...)` 這種明確的「作用域」語法，讓值的生命週期與程式碼區塊的執行範圍完全綁定，區塊執行完畢後這個值自動失效，開發者無法（也不需要）像 `ThreadLocal` 那樣手動 `set` 之後忘記清理，從語言層級的 API 設計上就排除了洩漏的可能性。

**面試回答方式**：對比「`ThreadLocal` 綁定執行緒整個生命週期、需要手動清理」與「`ScopedValue` 綁定明確的程式碼作用域、自動失效」這組差異，並點出這個問題在虛擬執行緒數量級下會被放大，展現你理解為什麼虛擬執行緒的引入會連帶推動這種新 API 的設計，而不是把兩者當成無關的獨立知識點。
