# 題目

JUC 提供了哪些併發集合？面對一個場景要怎麼選？

## 核心答案

按**用途**分成四類會比按名稱背誦清楚得多。

**映射與集合**：`ConcurrentHashMap`（通用首選，分桶鎖加 CAS）、`ConcurrentSkipListMap`／`Set`（需要排序或範圍查詢時的併發版本，跳躍表可無鎖化）、`CopyOnWriteArraySet`（極少寫、常遍歷的小集合）。

**清單**：`CopyOnWriteArrayList`（讀遠多於寫、且遍歷不能被中斷，典型是監聽器清單）。**JUC 沒有通用的併發 List**，因為按索引存取的語意在併發下本身就難以定義。

**佇列（阻塞）**：`ArrayBlockingQueue`（有界、單鎖、無配置）、`LinkedBlockingQueue`（雙鎖並行度高，**不傳容量就是無界**）、`SynchronousQueue`（無容量，直接交手）、`PriorityBlockingQueue`（有優先權，**無界**）、`DelayQueue`（延遲到期才能取）。

**佇列（非阻塞）**：`ConcurrentLinkedQueue`／`Deque`（無鎖、無界、無阻塞方法）。

選型的第一個問題永遠是：**需不需要背壓？** 需要就選有界且有阻塞方法的；不需要再談效能。

## 詳細解析

「無界」是選型時最容易忽略的風險。`LinkedBlockingQueue` 不傳容量、`PriorityBlockingQueue`、`DelayQueue`、`ConcurrentLinkedQueue` 都是無界的——它們在生產快於消費時會靜默地把記憶體吃光。`Executors.newFixedThreadPool` 的問題正是它用了無界的 `LinkedBlockingQueue`，所以任務堆積不會觸發拒絕策略，而是堆到 OOM。看到任何佇列，先確認它有沒有界，是最有價值的一個習慣。

**`ConcurrentHashMap` 的原子方法比 `putIfAbsent` 更值得記**：`compute`、`computeIfAbsent`、`computeIfPresent`、`merge` 讓「讀取後修改」變成原子操作，這是它相對於 `synchronizedMap` 的核心價值。但有一個重要限制——這些方法的重映射函式在執行期間會持有該桶的鎖，所以裡面絕對不能做耗時操作、也不能修改同一個 map（會死鎖或造成不可預期的行為）。這在用 `computeIfAbsent` 做快取載入時特別危險：載入函式若去查資料庫，就是在持鎖時做 IO。

`CopyOnWriteArrayList` 的適用範圍比大家以為的窄：每次寫入都複製整個陣列，所以只適合元素少、寫入極稀少的場景。監聽器清單是標準用例（註冊在啟動時完成、之後只有遍歷）。用它裝幾千個元素並頻繁增刪，效能會災難性地差，而且每次寫入產生的舊陣列都是垃圾。

**沒有 `ConcurrentArrayList` 是有原因的**：`get(i)` 與 `set(i, v)` 這種按索引的操作，在其他執行緒可能同時插入或刪除的情況下語意無法定義——你拿到的索引在下一刻可能指向完全不同的元素。這說明了併發資料結構的一個普遍原則：不是所有單執行緒的介面都能有意義地併發化，有些需要重新設計介面（例如改用佇列或映射）而不是加鎖。

## 面試回答方式

按**四類用途**組織答案（映射與集合、清單、阻塞佇列、非阻塞佇列）而不是逐個背名稱。給出選型的第一個問題：**需不需要背壓**——需要就選有界且有阻塞方法的，這比先談效能重要。接著主動點名**無界的陷阱**：`LinkedBlockingQueue` 不傳容量、`PriorityBlockingQueue`、`DelayQueue`、`ConcurrentLinkedQueue` 全是無界的，而 `newFixedThreadPool` 的問題正源於此。加分點有兩個：`ConcurrentHashMap` 的 `compute`／`merge` 系列在執行重映射函式時持有桶鎖，所以裡面不能做 IO 也不能改同一個 map，這在用 `computeIfAbsent` 做快取載入時特別危險；以及沒有併發 List 是因為按索引的語意在併發下無法定義，這說明不是所有單執行緒介面都能有意義地併發化。

## 講稿

我會按用途分成四類。映射跟集合、清單、阻塞佇列、非阻塞佇列。

映射的通用首選是 ConcurrentHashMap。需要排序或範圍查詢就用跳躍表的版本。清單只有寫時複製那個，適合讀遠多於寫的監聽器清單。阻塞佇列有陣列版、鏈結版、直接交手版、優先權版、延遲版。非阻塞佇列則是無鎖的鏈結佇列。

選型我問的第一個問題永遠是需不需要背壓。需要就選有界而且有阻塞方法的，不需要再談效能。

無界是最容易忽略的風險。鏈結佇列不傳容量、優先權佇列、延遲佇列、還有無鎖佇列，這些全都是無界的。固定執行緒池的問題正是它用了無界佇列，所以任務堆積不會觸發拒絕，而是堆到記憶體耗盡。看到任何佇列先確認有沒有界，是我覺得最有價值的習慣。

還有一個很重要的細節。ConcurrentHashMap 的 compute 那一系列方法，在執行你傳進去的函式時會持有那個桶的鎖。所以裡面絕對不能做耗時操作，用它做快取載入去查資料庫，就是在持鎖的時候做 IO。

## 常見追問

### computeIfAbsent 用來做快取有什麼問題？

**核心答案**：兩個問題。第一，載入函式在持有桶鎖時執行——如果載入要查資料庫或呼叫遠端，這段 IO 期間該桶的所有其他操作都會阻塞，而且在 JDK 8 早期版本還可能因為函式內部修改同一個 map 而死鎖。**第二，它不處理過期與容量**——快取需要的淘汰、TTL、以及載入失敗的處理它都沒有，這些自己補會逐漸長成半個快取庫。

**詳細解析**：它的正確用途是「純計算的記憶化」——輸入到輸出的映射是確定的、計算是本地的、且結果永遠有效。例如把字串解析成編譯好的正規表達式、把類別映射到它的反射中繼資料。這些場景沒有 IO、沒有過期需求，`computeIfAbsent` 是完美的選擇。需要 IO 載入或過期時就該用專門的快取庫（Caffeine 的 `LoadingCache`），它處理了單飛（多個執行緒請求同一個鍵時只載入一次）、非同步載入、以及載入失敗不會污染快取這些細節。判斷的關鍵是問「載入是純計算還是有副作用」。

**面試回答方式**：給兩個問題並具體說明第一個的機制（持桶鎖時做 IO 阻塞整個桶）。然後給出正確用途——**純計算的記憶化**，並舉具體例子（編譯正規表達式、反射中繼資料）。收在明確的判準：問「載入是純計算還是有副作用」，有 IO 或過期需求就該用專門的快取庫，並列出它多處理的細節（單飛、非同步載入、失敗不污染快取）。

### ConcurrentSkipListMap 為什麼用跳躍表而不是紅黑樹？

**核心答案**：因為跳躍表的修改是局部的，可以用 CAS 做成無鎖。插入一個節點只需要修改幾個相鄰指標；紅黑樹的插入可能觸發從葉到根的旋轉與重新著色，那是**全域的結構調整**，很難在不加鎖的情況下保持一致。所以單執行緒的有序映射用紅黑樹（更省空間、常數更小），併發的有序映射用跳躍表。

**詳細解析**：跳躍表的另一個好處是**它天然支援併發的範圍查詢**——遍歷只是沿著底層串列走，不需要像樹那樣維護遍歷路徑上的狀態。代價是**空間開銷較大**（每個節點平均有兩個指標層級，比紅黑樹多）以及**依賴隨機化**（層數由隨機決定，最壞情況理論上可能退化，雖然機率極低）。Redis 的有序集合也選了跳躍表，理由完全相同——實作簡單、範圍查詢自然、且容易併發化。能指出「資料結構的選擇往往由『能不能併發化』決定，而不只是漸進複雜度」，是這題最有價值的認識：兩者都是 O(log n)，選擇的依據完全在別的地方。

**面試回答方式**：核心是「跳躍表的修改是局部的可以 CAS，紅黑樹的旋轉是全域結構調整」。補上跳躍表的附帶好處（範圍查詢自然）與代價（空間較大、依賴隨機化）。舉 Redis 有序集合作為同樣選擇的旁證。真正的加分點是歸納：兩者漸進複雜度相同，選擇的依據是「能不能併發化」而非複雜度——這說明資料結構選型有複雜度以外的維度。

### 什麼時候併發集合反而不如加鎖的普通集合？

**核心答案**：當**需要跨多個操作的原子性**時。併發集合保證單一操作原子，但「檢查後執行」「同時更新兩個 map」「遍歷時保持一致快照」這些都需要外部同步——而一旦要在外面加鎖，內部的併發機制就成了純粹的額外開銷。這種情況下用 `HashMap` 加一把 `ReentrantLock` 反而更快也更容易推理。

**詳細解析**：另外兩種情況也適合普通集合加鎖：**低併發**（只有兩三個執行緒偶爾存取，併發集合的複雜度換不到收益）與**寫入極頻繁**（`ConcurrentHashMap` 的優勢在讀多寫少，全寫入時桶鎖的爭用與普通鎖差別不大，卻多了 CAS 重試的成本）。判斷的核心問題是：我的原子性邊界在哪裡？ 如果邊界剛好落在單一集合操作上，用併發集合；如果邊界跨越多個操作或多個資料結構，那就必須有一把涵蓋整個邊界的鎖，此時集合本身的併發能力沒有意義。這個「先確定原子性邊界，再選工具」的順序，比記住每個集合的特性更重要。

**面試回答方式**：給出核心情況——需要跨操作原子性時，外面加了鎖，內部的併發機制就成了純額外開銷。補上另外兩種（低併發、寫入極頻繁）。真正的加分點是把它提升成方法論：先確定原子性邊界在哪裡，再選工具——邊界落在單一操作上就用併發集合，跨多個操作就需要涵蓋整個邊界的鎖，此時集合的併發能力沒有意義。
