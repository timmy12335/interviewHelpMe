# 題目

Disruptor 為什麼能比 `BlockingQueue` 快一個數量級？它的代價是什麼？

## 核心答案

差別來自四個設計決策，每一個都針對佇列的一項成本。

**預先配置的環形緩衝**——所有事件物件在啟動時就建立好並重複使用，執行期**零配置零回收**，GC 壓力接近消失。傳統佇列每筆訊息都是一個新物件，高吞吐下 young GC 極其頻繁。

**序號加 CAS 取代鎖**——生產者用 CAS 取得一個遞增序號作為寫入位置，消費者追蹤自己的序號。沒有 `ReentrantLock`、沒有 `Condition` 的掛起與喚醒，**省掉了大量的上下文切換**。

**快取行填充**——生產者序號、消費者序號、環形緩衝的欄位都做了填充，避免偽共享。這在高頻更新的序號上影響巨大。

**批次消費**——消費者一次可以取得「到目前為止的所有可用序號」，攤平了每筆的協調成本。

代價同樣明確：**等待策略若用忙等會持續燒 CPU**、緩衝大小固定無法吸收長時間的突發、程式設計模型（事件處理器與依賴關係圖）與一般佇列差異大，學習與維護成本真實存在。

## 詳細解析

**「機械同理心」（mechanical sympathy）是它的設計哲學**：理解硬體如何運作，然後順著它設計。環形緩衝用陣列而非鏈結串列是為了**記憶體連續與預取友善**；容量取 2 的次方是為了用位元遮罩取代取模；填充快取行是為了避免核心間的無謂通訊。這些單獨看都是小最佳化，疊加起來才有數量級的差距——這也說明為什麼「換個佇列實作」拿不到同樣的效果。

等待策略是使用時最重要的選擇。`BusySpinWaitStrategy` 延遲最低但獨佔一個 CPU 核心；`YieldingWaitStrategy` 自旋一段後讓出；`BlockingWaitStrategy` 用鎖與條件變數，CPU 友善但延遲高（退化成類似佇列的行為）；`SleepingWaitStrategy` 介於中間。選擇取決於「有沒有多餘的核心可以燒」——交易系統願意獨佔核心換微秒級延遲，一般 Web 服務不願意。

它的多消費者模型是另一個價值點：多個消費者可以**各自獨立消費全部事件**（廣播），也可以組成**依賴關係圖**（例如日誌與複製並行處理，兩者都完成後才交給業務處理）。傳統佇列做廣播要複製多份或用多個佇列，做依賴要自己協調。這種「一份資料、多個處理階段、明確依賴」的模型，是它在交易系統中被採用的重要原因，不只是快。

**什麼時候不該用它**：需要無界或很大緩衝的場景（環形緩衝固定大小）、消費速率長期低於生產速率的場景（滿了就阻塞，Disruptor 幫不上忙）、以及團隊不熟悉且沒有延遲壓力的場景。「我們的服務延遲要求是 100 毫秒」這種情況下，佇列的幾微秒差距完全不重要，引入它只會增加複雜度。判斷的門檻是：只有當協調成本佔總延遲的可觀比例時，這些最佳化才有意義。

## 面試回答方式

把差距拆成**四個設計決策**，每個對應佇列的一項成本：預配置環形緩衝（零 GC）、序號加 CAS（省上下文切換）、快取行填充（避免偽共享）、批次消費（攤平協調成本）。強調它們單獨都是小最佳化，疊加才有數量級差距——這解釋了為什麼換個佇列實作拿不到同樣效果。接著給設計哲學「**機械同理心**」並舉三個具體例子（陣列而非串列、容量取 2 的次方用遮罩、填充快取行）。然後誠實給代價：忙等燒 CPU、緩衝固定、程式設計模型的學習成本。加分點是指出它的價值不只是快——多消費者的廣播與依賴關係圖模型是傳統佇列難以表達的。最後給判斷門檻：只有協調成本佔總延遲可觀比例時這些最佳化才有意義，100 毫秒的服務不需要在意幾微秒。

## 講稿

差別來自四個設計決策，每一個都針對佇列的一項成本。

第一，預先配置的環形緩衝。所有事件物件在啟動時就建立好並重複使用，執行期零配置零回收，GC 壓力幾乎消失。傳統佇列每筆訊息都是新物件，高吞吐下年輕代回收極其頻繁。

第二，用序號加 CAS 取代鎖，省掉大量的掛起喚醒跟上下文切換。

第三，快取行填充。生產者跟消費者的序號都做了填充避免偽共享，這在高頻更新的序號上影響很大。

第四，批次消費。消費者一次取得目前所有可用的序號，攤平每筆的協調成本。

我想強調的是，這些單獨看都是小最佳化，疊加起來才有數量級的差距。所以換一個佇列實作拿不到同樣的效果。

代價也很明確。忙等策略會持續燒 CPU、緩衝大小固定無法吸收長時間突發、程式設計模型跟一般佇列差異很大。我的判斷門檻是，只有協調成本佔總延遲可觀比例的時候，這些最佳化才有意義。

## 常見追問

### 為什麼環形緩衝的容量要是 2 的次方？

**核心答案**：為了用**位元遮罩取代取模運算**。序號要映射到陣列索引時，`sequence % capacity` 在容量是 2 的次方時等價於 `sequence & (capacity - 1)`——一次位元與運算，遠快於整數除法（除法在現代處理器上仍然要十幾到幾十個週期，而位元運算是一個週期）。在每筆訊息都要算一次索引的熱路徑上，這個差別是可量測的。

**詳細解析**：同樣的技巧在 `HashMap` 的擴容與索引計算上也用到，那裡的容量也強制是 2 的次方。它還有一個附帶好處：序號可以無限遞增而不必回繞，因為遮罩自動處理了。用一個 `long` 序號，即使每秒十億次也要幾百年才溢位，所以實務上不需要處理環繞問題——這讓「序號單調遞增」成為一個可以依賴的不變量，消費者可以用序號的大小關係判斷進度，程式碼因此簡單很多。這是「選對表示法讓後續邏輯變簡單」的好例子，比單純的速度收益更有價值。

**面試回答方式**：先給直接理由（位元遮罩取代取模，除法十幾到幾十週期 vs 位元運算一週期），並指出 `HashMap` 用同樣的技巧。真正的加分點是附帶好處：**序號可以單調遞增不必回繞**（long 序號每秒十億次也要幾百年才溢位），這讓「序號單調」成為可依賴的不變量，消費者用大小關係判斷進度、程式碼因此簡單很多——這比速度收益更有價值。

### Disruptor 的生產者怎麼避免覆蓋還沒被消費的資料？

**核心答案**：靠**序號的距離檢查**。生產者要寫入序號 n 的位置時，必須確認最慢的消費者已經處理到 n - capacity 之後——否則那個位置還有未消費的資料。生產者會追蹤所有消費者序號中的最小值（稱為 gating sequence），距離不足時就依等待策略等待。這等價於有界佇列的「滿了就阻塞」，只是用序號比較實作而非計數器。

**詳細解析**：多生產者的情況更複雜——它們要先 CAS 一個共享的序號取得寫入位置，然後各自填資料，但填完的順序可能與序號順序不同。所以還需要一個「已發布」的標記（`availableBuffer`）讓消費者知道某個序號是否真的可讀，消費者只能消費到**連續已發布**的最大序號。這使得多生產者模式明顯慢於單生產者模式，官方也建議盡量設計成單生產者（例如用一個執行緒統一收集後寫入）。這是一個通用的教訓：把多寫者收斂成單寫者，往往比優化多寫者的協調更有效——同樣的思路出現在 Kafka 的分區、資料庫的單一寫入節點、以及事件溯源的單一寫入序列。

**面試回答方式**：先給機制——生產者追蹤最慢消費者的序號（gating sequence），距離不足就等待，並指出這等價於有界佇列的「滿了就阻塞」。加分點是展開多生產者的複雜度：CAS 取位置後填資料的順序可能亂，需要已發布標記，消費者只能讀到連續已發布的最大序號，因此明顯較慢。收在通用教訓：把多寫者收斂成單寫者，往往比優化多寫者的協調更有效，並舉 Kafka 分區與事件溯源作為同一思路。

### 一般的業務系統可以借鑑 Disruptor 的哪些思路？

**核心答案**：三個可以直接遷移的思路，都不需要引入這個框架。**物件重用**——在高頻路徑上重用緩衝與臨時物件（例如每執行緒一個 `StringBuilder`），減少 GC 壓力。**批次處理**——把逐筆的協調成本攤平，這適用於資料庫寫入、日誌刷新、遠端呼叫的合併。**單寫者原則**——把對共享狀態的寫入收斂到單一執行緒，讀取則可以無鎖並行。

**詳細解析**：**單寫者原則的收益常被低估**。當只有一個執行緒寫入時，寫入端完全不需要同步（不需要 CAS、不需要鎖），讀取端只要一個 volatile 引用或序號就能安全讀到。這比任何精巧的無鎖演算法都簡單，而且更快。實務上的落地方式是：把「命令」放進佇列由單一執行緒處理（actor 模型的核心思想）、或用事件溯源把所有變更序列化。代價是那個單寫者成為吞吐上限，所以要確保它的工作足夠輕——重活（IO、計算）應該移到它之外，讓它只做狀態更新。這正是 LMAX 交易所的架構：所有業務邏輯在單一執行緒上跑，因為狀態全在記憶體、每筆處理只要幾微秒。

**面試回答方式**：給三個可直接遷移的思路（物件重用、批次處理、單寫者原則）並各給一個一般系統的應用場景。重點展開**單寫者原則**——寫入端完全不用同步、讀取端一個 volatile 就夠，比任何精巧的無鎖演算法都簡單且更快。給出落地方式（命令佇列加單執行緒、事件溯源）與代價（單寫者是吞吐上限，所以重活要移出去），並用 LMAX 的架構作為實例。
