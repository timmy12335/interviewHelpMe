# 題目

`@Scheduled` 的三種觸發方式有什麼不同？多實例部署時怎麼避免重複執行？

## 核心答案

三種方式：**`fixedRate`**（固定頻率，以**上次開始時間**為基準）、**`fixedDelay`**（固定間隔，以**上次結束時間**為基準）、**`cron`**（依日曆時間，支援時區）。前兩者用相對時間、與時鐘無關；`cron` 對齊真實時間，適合「每天凌晨兩點」這類需求。

預設的執行緒池只有一個執行緒——這是最常被忽略的一點。所有 `@Scheduled` 方法共用它，一個慢任務會延遲所有其他任務。應該明確設定 `spring.task.scheduling.pool.size` 或提供自訂的 `TaskScheduler`。

多實例部署時，同一個定時任務會在每個實例上各執行一次。這在單實例的開發環境完全測不出來，是從單機走向叢集時最常被忽略的問題之一。解法有三層：**分散式鎖**（ShedLock 是最輕量的方案，用資料庫或 Redis 搶一個帶 TTL 的鎖）、**專門的排程系統**（Quartz 叢集模式、XXL-Job）、或**外部觸發**（Kubernetes CronJob 呼叫一個 API，應用本身不排程）。

另一個必做的事是任務主體整段 try-catch——未捕捉的例外會讓**週期任務被永久取消**，之後再也不執行，而且沒有任何錯誤訊息。

## 詳細解析

「拋例外後永久停止」是定時任務最陰險的失敗模式。它的症狀不在任務本身——資料沒同步、報表沒產生、快取沒更新，問題出現在下游，而排查的人往往要繞很久才想到去看那個從不出聲的定時任務。監控的做法是讓每次成功執行都更新一個「最後成功時間」指標並對它設告警，這樣停止會在幾分鐘內被發現而不是等業務方反映。

`fixedRate` 的追趕行為要注意：某次執行特別慢而落後了幾個週期時，它不會跳過，而是連續執行去追進度。對冪等的同步任務沒問題，對「每小時發一次摘要」則會連發好幾封。需要「錯過就跳過」的語意時，`@Scheduled` 沒有內建支援——要自己在任務裡判斷「距離預定時間是否已超過容忍範圍」，或改用支援 misfire 策略的 Quartz。

分散式鎖的兩個細節容易做錯。鎖的 TTL 必須大於任務的最長執行時間——否則任務還在跑鎖就過期了，另一個實例會開始執行。**而且不能只靠鎖保證不重複**：網路分割或 GC 停頓可能讓持鎖者失去鎖而不自知。所以任務本身應該盡量設計成冪等的，鎖只是降低重複的機率而不是消除它。 這與分散式系統中「鎖提供的是效率最佳化而非互斥保證」的普遍認識一致。

**外部觸發是最乾淨的方案**。用 Kubernetes CronJob 或雲端排程服務定時呼叫一個受保護的 API，應用本身完全不排程。好處是：排程的可靠性交給專門的系統（有重試、有歷史記錄、有告警）、**應用保持無狀態**、以及**手動重跑變得容易**（呼叫一次 API 即可）。代價是多一個外部元件與網路呼叫的可靠性問題（要處理逾時與重複觸發，這又回到冪等性）。在容器化的環境下，這通常是最值得考慮的方向。

## 面試回答方式

先精確區分三種觸發方式的基準時間（開始時間、結束時間、日曆時間）。接著點出預設執行緒池只有一個執行緒這個最常被忽略的事實——一個慢任務會延遲所有其他任務。然後給多實例的問題：同一個任務在每個實例各執行一次，而這在單實例開發環境完全測不出來，並給三層解法（分散式鎖、專門排程系統、外部觸發）。強調**任務主體必須整段 try-catch**——未捕捉例外會讓週期任務永久停止且沒有錯誤訊息。加分點有三個：監控用「最後成功時間」指標加告警，讓停止在幾分鐘內被發現；`fixedRate` 落後時會連續追趕，冪等任務沒問題但摘要郵件會連發好幾封；以及分散式鎖不能保證不重複（網路分割、GC 停頓），**任務本身仍應設計成冪等的**。

## 講稿

三種方式的差別在基準時間。固定頻率以上次開始時間為基準，固定間隔以上次結束時間為基準，cron 則對齊真實的日曆時間。

有一個最常被忽略的事實，預設的執行緒池只有一個執行緒。所有定時任務共用它，一個慢任務會延遲所有其他任務。應該明確設定池大小。

多實例部署的時候，同一個定時任務會在每個實例上各執行一次。這在單實例的開發環境完全測不出來，是從單機走向叢集時最容易忽略的問題之一。

解法有三層。用分散式鎖搶一個帶過期時間的鎖、用專門的排程系統、或是外部觸發，讓平台的定時任務去呼叫一個 API，應用本身完全不排程。容器化環境下我通常推薦最後一種。

還有一件必做的事，任務主體要整段 try-catch。未捕捉的例外會讓週期任務被永久取消，之後再也不執行，而且沒有任何錯誤訊息。

這種失敗最陰險的地方是症狀不在任務本身，是資料沒同步、報表沒產生，問題出現在下游。所以我會讓每次成功執行都更新一個最後成功時間的指標，並對它設告警。

## 常見追問

### cron 表達式在時區與日光節約上有什麼問題？

**核心答案**：`@Scheduled(cron = "...", zone = "Asia/Taipei")` 可以指定時區，**不指定時用的是 JVM 的預設時區**——這在容器裡通常是 UTC，與開發者的預期不同，是「任務在錯誤的時間執行」最常見的原因。日光節約則帶來兩個邊界：春季調整那天某些本地時間不存在（例如凌晨 2:30 直接跳到 3:30，排在那個時間的任務可能被跳過），秋季調整那天某些時間出現兩次（任務可能執行兩次）。

**詳細解析**：這些邊界情況一年只發生兩天，測試幾乎不可能覆蓋到，所以必須靠設計來避開。實用的做法有兩個：把任務排在不會受影響的時間（凌晨 4 點以後，避開常見的日光節約調整窗口），以及**讓任務冪等**（即使執行兩次也不會產生錯誤結果）。如果任務必須「精確地每天一次」，更穩健的做法是用 UTC 排程並在任務內部處理當地時間的邏輯——這樣排程本身完全不受日光節約影響。「把時間處理的複雜度集中在一個地方」比讓它散落在排程設定與業務邏輯兩處好。

**面試回答方式**：先給時區問題——不指定時用 JVM 預設，容器裡通常是 UTC，這是「任務在錯誤時間執行」最常見的原因。給日光節約的兩個邊界（不存在的時間可能被跳過、重複的時間可能執行兩次）並指出一年只兩天、測試幾乎不可能覆蓋。給出兩個實用做法（排在不受影響的時間、讓任務冪等），並提出更穩健的方案：用 UTC 排程、在任務內部處理當地時間邏輯，把時間複雜度集中在一處。

### ShedLock 是怎麼運作的？

**核心答案**：它在任務執行前嘗試在共享儲存（資料庫表或 Redis）中插入或更新一筆帶有「鎖到期時間」的記錄，插入成功才執行任務，失敗（表示別人持有）就跳過。關鍵是它用 `lockAtMostFor`（鎖的最長持有時間，防止實例崩潰後鎖永遠不釋放）與 `lockAtLeastFor`（鎖的最短持有時間，防止任務執行得太快導致其他實例也搶到）兩個參數。

**詳細解析**：`lockAtLeastFor` 這個參數解決了一個不明顯的問題：如果任務執行只要 10 毫秒，而各實例的時鐘有幾百毫秒的偏差，實例 A 執行完釋放鎖之後，實例 B 的排程時間才到並成功搶到鎖，於是任務被執行了兩次。設定 `lockAtLeastFor` 讓鎖至少持有一段時間（例如排程間隔的一半），就能避開這個窗口。這是一個很好的例子說明「分散式環境下時鐘偏差是真實的」——單機的直覺（做完就釋放）在多機下會出錯。要注意 ShedLock 的定位是「防止重複執行」而不是「保證執行」——如果持鎖的實例崩潰，那一次執行就是丟失了，不會有別的實例補上。需要「保證執行」要靠任務本身的補償邏輯或專門的排程系統。

**面試回答方式**：給機制（共享儲存插入帶到期時間的記錄、成功才執行）與兩個關鍵參數。重點展開 `lockAtLeastFor` 解決的不明顯問題：任務執行很快加上時鐘偏差，A 釋放後 B 才到時間並搶到鎖，任務被執行兩次——這說明分散式環境下時鐘偏差是真實的。加分點是澄清定位：**ShedLock 防止重複執行但不保證執行**，持鎖實例崩潰時那次執行就丟失了。

### 什麼時候該從 @Scheduled 換成專門的排程系統？

**核心答案**：四個訊號。**任務之間有依賴**（A 完成後才能跑 B）——`@Scheduled` 只能各自獨立排程，靠時間差來「希望」順序正確，這很脆弱。**需要執行歷史與重跑**——`@Scheduled` 不記錄任何歷史，出問題時無法知道上次成功是什麼時候、也無法手動重跑某一次。**需要動態調整排程**——改 cron 要改設定並重啟。**任務量大需要分片**——把一個大任務拆給多個實例並行處理。

**詳細解析**：「執行歷史」這一項的價值常被低估。定時任務的問題往往是「某一次沒跑」或「某一次跑錯了」，沒有歷史記錄的話這些問題無從診斷。專門的排程系統（XXL-Job、Airflow、或雲端的工作流服務）提供了執行記錄、日誌、狀態、以及重跑按鈕——這些在出事時的價值遠超它們的維運成本。中間方案是自己記錄執行歷史：在任務的開始與結束寫一筆記錄到資料庫（任務名、開始時間、結束時間、狀態、錯誤訊息），這幾行程式碼就解決了大部分的診斷需求，**而且不需要引入新的元件**。在決定引入排程系統之前，先做這個低成本的改善通常很划算。

**面試回答方式**：給四個訊號（任務依賴、需要歷史與重跑、需要動態調整、需要分片）。重點展開**「執行歷史」的價值常被低估**——定時任務的問題往往是某次沒跑或跑錯了，沒有歷史就無從診斷。真正的加分點是提出**低成本的中間方案**：自己在任務開始與結束寫一筆記錄到資料庫，幾行程式碼解決大部分診斷需求且不引入新元件，在決定引入排程系統之前先做這個通常很划算。
