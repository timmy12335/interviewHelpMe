# 題目

Spring 應用怎麼優雅關閉？bean 的銷毀順序是怎麼決定的？

## 核心答案

優雅關閉的目標是：停止接受新請求 → 讓進行中的請求完成 → 才釋放資源。Spring Boot 用 `server.shutdown=graceful` 開啟——內嵌伺服器收到關閉訊號後停止接受新連線，並在 `spring.lifecycle.timeout-per-shutdown-phase`（預設 30 秒）內等待進行中的請求完成。

bean 的銷毀順序是**建立順序的反向**——依賴者先銷毀、被依賴者後銷毀。這是正確的：一個服務要先停止，它使用的連線池才能安全關閉。銷毀的回呼有三種形式：`@PreDestroy`、實作 `DisposableBean`、或在 `@Bean` 上指定 `destroyMethod`。

**更精細的控制用 `SmartLifecycle`**——它有 `getPhase()` 決定啟動與停止的階段順序（**啟動時 phase 小的先、停止時 phase 大的先**），還有非同步的 `stop(Runnable callback)` 讓需要時間的關閉可以被等待。訊息消費者、排程器這類需要「先停止接收、再處理完手上的」的元件，應該實作它而不是只用 `@PreDestroy`。

最容易被忽略的是與平台的時間預算對齊：Kubernetes 送出 SIGTERM 後預設等 30 秒才 SIGKILL，而應用的關閉流程（下線傳播 + 請求排空 + 資源關閉）總和必須小於它。

## 詳細解析

「停止接受新請求」不等於「上游不再送請求過來」。應用停止接受連線的那一刻，負載平衡器可能還不知道——在它更新之前送過來的請求會直接失敗。所以完整的關閉流程要多一步：收到 SIGTERM 後先讓 readiness 探針變成不健康，等待一段時間讓上游摘除，才開始真正的關閉。Kubernetes 的 `preStop` hook（在 SIGTERM 之前執行）睡個幾秒是常見做法。

**`@PreDestroy` 不保證一定執行**。JVM 被 `kill -9`、容器被 SIGKILL、或 JVM 崩潰時，關閉流程根本不會開始。所以任何「必須發生」的清理（釋放分散式鎖、通知外部系統、回滾遠端交易）都不能只依賴它——外部系統應該有超時或補償機制。這與 Java 核心裡「不要把資源正確性建立在 GC 上」是同一個原則的延伸：不要把正確性建立在「關閉流程一定會跑」上。

銷毀順序的反向規則有一個例外要注意：原型作用域（prototype）的 bean **不會被容器銷毀**——容器只負責建立，之後就不再持有引用，所以 `@PreDestroy` 不會被呼叫。如果原型 bean 持有資源，必須由使用方負責關閉。這是 prototype 作用域一個容易踩到的陷阱。

關閉時的資源釋放順序需要明確設計。典型的正確順序是：停止接收（Web 伺服器、訊息消費者、定時任務）→ 等待進行中的工作完成 → 關閉執行緒池 → 關閉外部連線（資料庫、Redis、HTTP 客戶端）→ 上報關閉事件。Spring 的依賴反向規則通常會給出正確的順序，但只在依賴關係被正確表達的前提下——如果某個元件透過靜態欄位或服務定位器取得連線而非注入，容器不知道這個依賴，順序就可能出錯。這是「顯式依賴」除了可測試性之外的另一個實際好處。

## 面試回答方式

先給優雅關閉的**三步目標**與 Spring Boot 的開啟方式，再給 bean 銷毀順序是**建立順序的反向**及其理由。介紹 **`SmartLifecycle`** 作為更精細的控制——`getPhase` 決定順序（啟動時小的先、停止時大的先）、`stop(Runnable)` 支援非同步等待，並指出訊息消費者與排程器應該實作它。加分點有三個：「停止接受新請求」不等於「上游不再送」，所以要先讓 readiness 變不健康並等待傳播（`preStop` hook）；`@PreDestroy` 不保證執行（SIGKILL、崩潰時根本不跑），所以必須發生的清理要靠外部的超時或補償，這是「不要把正確性建立在關閉流程一定會跑上」；以及原型作用域的 bean 不會被容器銷毀，持有資源時要由使用方負責關閉。最後強調與平台時間預算對齊——總和必須小於 K8s 的 grace period。

## 講稿

優雅關閉的目標是三步。停止接受新請求、讓進行中的請求完成、才釋放資源。Spring Boot 有一個設定可以開啟，內嵌伺服器收到關閉訊號後停止接受新連線，並在設定的逾時內等待進行中的請求完成。

bean 的銷毀順序是建立順序的反向，依賴者先銷毀、被依賴者後銷毀。這是正確的，一個服務要先停止，它使用的連線池才能安全關閉。

更精細的控制用生命週期介面，它有階段編號決定順序，啟動時編號小的先、停止時編號大的先。訊息消費者、排程器這類需要先停止接收再處理完手上的元件，應該實作它。

有一個很容易被忽略的地方。停止接受新請求不等於上游不再送請求過來。應用停止接受連線的那一刻，負載平衡器可能還不知道，在它更新之前送過來的請求會直接失敗。所以要先讓就緒探針變成不健康，等待一段時間讓上游摘除，才開始真正的關閉。

還有一點，銷毀回呼不保證一定執行。被強制終止或 JVM 崩潰的時候，關閉流程根本不會開始。所以任何必須發生的清理，像是釋放分散式鎖或通知外部系統，都不能只依賴它，外部系統應該有超時或補償機制。

## 常見追問

### SmartLifecycle 的 phase 該怎麼設計？

**核心答案**：把元件依「誰依賴誰」分層，**越底層（被依賴的）phase 越小**。例如連線池 phase 0、資料存取層 phase 100、業務服務 phase 200、訊息消費者 phase 300、Web 伺服器 phase `Integer.MAX_VALUE`（Spring Boot 的內嵌伺服器就用這個）。啟動時由小到大，**確保依賴先就緒**；停止時由大到小，**確保使用者先停止**。

**詳細解析**：留出間隔（用 100 而非 1、2、3）是實用的做法——之後要在中間插入一個元件時不必重新編號。**要注意 `isAutoStartup()` 預設是 true**，所以實作了 `SmartLifecycle` 的 bean 會在上下文重新整理時自動啟動；如果你希望手動控制，要覆寫成 false。另一個容易忽略的是 `stop(Runnable callback)` 這個非同步版本——如果你的關閉需要時間（等待消費者處理完手上的訊息），應該實作它並在完成後呼叫 callback，容器會等待（最多等 `timeout-per-shutdown-phase`）。只實作同步的 `stop()` 而在裡面阻塞也能運作，但那會佔用關閉的執行緒且無法被逾時控制。

**面試回答方式**：給分層原則（越底層 phase 越小）與具體的數字範例，說明啟動與停止的方向。加分點是三個實務細節：**留出間隔方便日後插入**、**`isAutoStartup` 預設 true**、以及用非同步的 `stop(Runnable)` 讓需要時間的關閉能被容器等待與逾時控制，而只實作同步版本在裡面阻塞會佔用關閉執行緒且無法被逾時控制。

### 關閉時進行中的訊息消費怎麼處理？

**核心答案**：目標是**不丟失也不重複處理**。做法是：**先停止拉取新訊息**（Kafka 的 consumer 停止 poll、RabbitMQ 停止 basicConsume）、**處理完已經拉取的**、**提交位移或 ack**、**才關閉連線**。Spring 的 `MessageListenerContainer` 實作了 `SmartLifecycle`，關閉時會走這個流程——**但前提是給它足夠的時間**，逾時被強制關閉時仍可能有未提交的訊息。

**詳細解析**：「未提交的訊息會被重新投遞」是這個設計的安全網——所以**訊息處理必須是冪等的**，這比任何關閉流程的優化都重要。如果處理不冪等，那麼無論關閉多優雅，只要有一次強制終止（SIGKILL、節點故障、OOM）就會產生重複處理。 實務上的做法是在處理端做冪等控制（用訊息 ID 去重、或者用資料庫的唯一約束），把正確性建立在冪等而非「關閉一定優雅」上。這與前面說的「不要把正確性建立在關閉流程一定會跑上」是同一個原則，而且它在分散式系統中反覆出現：任何依賴「正常流程一定會完成」的設計，在有故障的環境下都會失敗。

**面試回答方式**：給出四步流程與 Spring 的 `MessageListenerContainer` 已實作 `SmartLifecycle`，但強調**前提是給足時間**。真正的重點是後半段：未提交的訊息會被重新投遞是安全網，所以訊息處理必須冪等，這比任何關閉優化都重要——不冪等的話，一次強制終止就會產生重複處理。收在原則：把正確性建立在冪等而非「關閉一定優雅」上，並指出這在分散式系統中反覆出現。

### 怎麼驗證優雅關閉真的有效？

**核心答案**：用測試而不是靠設定就相信它。做法是：在持續發送請求的情況下觸發關閉（送 SIGTERM 給行程或用 `kubectl delete pod`），**觀察有沒有請求失敗**。成功的標準是：關閉期間所有已建立的請求都完成、新請求被路由到其他實例、且沒有 5xx 或連線重置。這個測試應該在 CI 或部署前的驗證中自動化，因為關閉行為很容易在設定改動時悄悄退化。

**詳細解析**：**常見的失敗點有四個**，可以逐一檢查：**readiness 沒有及時變成不健康**（上游還在送）、**等待時間不足**（長請求被截斷）、**時間預算超過平台的 grace period**（被 SIGKILL 打斷）、以及**某個元件沒有參與關閉流程**（自己起的執行緒、第三方函式庫的背景任務）。**最後一項最隱蔽**——一個用 `new Thread()` 起的背景執行緒不受 Spring 管理，關閉時它可能還在跑，如果它是非守護執行緒，甚至會讓 JVM 無法退出。「所有背景工作都應該由容器管理」是一條值得堅持的紀律，因為它讓關閉、監控、與診斷都有一個統一的入口。

**面試回答方式**：給明確立場——**用測試驗證而非相信設定**，並描述測試方法（持續發送請求時觸發關閉、觀察有無失敗）與成功標準。強調**應該自動化**因為關閉行為容易在設定改動時悄悄退化。給四個常見失敗點並展開最隱蔽的一個：自己 `new Thread()` 起的背景執行緒不受管理，關閉時還在跑，非守護的話甚至讓 JVM 無法退出。收在紀律：所有背景工作都應該由容器管理，這讓關閉、監控、診斷有統一入口。
