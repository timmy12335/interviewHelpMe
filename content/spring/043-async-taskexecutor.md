# 題目

`@Async` 怎麼運作？預設的執行緒池有什麼問題？

## 核心答案

`@Async` 是**基於 AOP 的非同步呼叫**：標註的方法被代理，呼叫時把實際執行提交到一個 `TaskExecutor` 並立刻返回。回傳型別必須是 `void`、`Future`、`CompletableFuture` 或 `ListenableFuture`——**回傳普通型別會拿到 null 而不會報錯**，這是一個沉默的錯誤。

**預設執行緒池的問題很嚴重**。如果沒有明確定義 `TaskExecutor` bean，Spring Boot 會用 `SimpleAsyncTaskExecutor`——**它為每個任務建立一個新執行緒，完全不重用、也沒有任何上限**。流量一大就會建立數千個執行緒，記憶體耗盡或觸發作業系統的執行緒上限。**Spring Boot 從 3.2 起若啟用虛擬執行緒會用它，情況好一些，但仍然沒有並行度上限。**

所以第一件事永遠是**明確定義一個 `ThreadPoolTaskExecutor`**，設定核心數、最大數、佇列容量、執行緒名前綴、以及拒絕策略。而且**應該依用途分池**（`@Async("emailExecutor")`），不要所有非同步任務共用一個。

三個容易踩的坑：**自呼叫失效**（同 `@Transactional`）、**例外會消失**（`void` 回傳時例外不會傳到呼叫方，要設定 `AsyncUncaughtExceptionHandler`）、以及**上下文不會自動傳遞**（追蹤 ID、安全上下文、租戶資訊在新執行緒上都不見了）。

## 詳細解析

**「例外會消失」是最危險的一個**。`@Async void` 方法拋出的例外，呼叫方完全不知道——它已經返回了。預設情況下這個例外會被記錄（透過 `SimpleAsyncUncaughtExceptionHandler`），但**如果日誌沒有被監控，等於功能靜默失敗**。**正確做法是實作 `AsyncConfigurer` 提供自訂的 `AsyncUncaughtExceptionHandler`**，在裡面記錄完整上下文並上報指標。回傳 `CompletableFuture` 時例外會被包在裡面，**但呼叫方如果不 `get` 或不註冊 `exceptionally`，同樣靜默消失**。

**上下文傳遞需要明確處理**。`ThreadLocal` 綁在執行緒上，`@Async` 的任務跑在池的執行緒上，所以 MDC 的追蹤 ID、`SecurityContextHolder` 的認證資訊、以及任何自訂的上下文都不會跟著走。**解法是用 `TaskDecorator`**——在 `ThreadPoolTaskExecutor` 上設定一個裝飾器，它在提交時捕獲當前上下文、在執行時設定、執行後清除。**這是一次性的基礎設施投資，做完之後所有 `@Async` 都受益**，比在每個任務裡手動傳遞可靠得多。

**分池的理由與執行緒池那題相同**：一個慢的非同步任務（例如呼叫一個變慢的外部服務）會佔滿共用池，讓完全無關的任務（例如寄信）也被阻塞。**依「下游是誰」與「失敗會不會互相影響」分組**是實用的原則。

**`@Async` 與交易的互動要特別小心**。非同步方法**在新的執行緒上執行，所以不在呼叫方的交易裡**——它看不到未提交的資料，也不會被呼叫方的回滾影響。**常見的錯誤是「在交易裡非同步地處理剛寫入的資料」**：非同步任務可能在交易提交之前就開始執行，查詢時找不到那筆資料。**正確做法是用 `@TransactionalEventListener(phase = AFTER_COMMIT)` 讓非同步處理在提交之後才觸發。**

## 面試回答方式

先給機制（AOP 代理、提交到 `TaskExecutor`、回傳型別限制）並指出**回傳普通型別會拿到 null 而不報錯**這個沉默錯誤。接著把**預設執行緒池的問題**講清楚——`SimpleAsyncTaskExecutor` 為每個任務建新執行緒、不重用、沒有上限，流量一大就耗盡資源，所以**第一件事永遠是明確定義 `ThreadPoolTaskExecutor` 並依用途分池**。給三個坑，並把**例外會消失**單獨展開：`void` 方法的例外呼叫方完全不知道，回傳 `CompletableFuture` 時不 `get` 也一樣靜默消失，解法是實作 `AsyncConfigurer` 提供自訂處理器。加分點有兩個：**用 `TaskDecorator` 一次性解決上下文傳遞**，比每個任務手動傳可靠；以及 **`@Async` 不在呼叫方的交易裡**，「在交易裡非同步處理剛寫入的資料」會找不到那筆資料，正確做法是用 `@TransactionalEventListener(AFTER_COMMIT)`。

## 講稿

它是基於 AOP 的非同步呼叫。標註的方法被代理，呼叫時把實際執行提交到執行器並立刻返回。回傳型別必須是空、Future 或它的變體，回傳普通型別會拿到 null 而不會報錯，這是一個沉默的錯誤。

預設執行緒池的問題很嚴重。沒有明確定義執行器的話，Spring 會用一個為每個任務建立新執行緒的實作，完全不重用也沒有上限，流量一大就會建立數千個執行緒。所以第一件事永遠是明確定義一個執行緒池，並且依用途分池。

三個容易踩的坑是自呼叫失效、例外會消失、還有上下文不會自動傳遞。

例外消失最危險。標註為空回傳的非同步方法拋出例外，呼叫方完全不知道，因為它已經返回了。預設會被記錄，但如果日誌沒有被監控，等於功能靜默失敗。回傳 Future 的話例外被包在裡面，但呼叫方不去取也一樣消失。

上下文傳遞我會用裝飾器解決。提交時捕獲當前上下文、執行時設定、結束後清除。這是一次性的投資，做完之後所有非同步方法都受益。

最後一個坑，非同步方法不在呼叫方的交易裡。在交易裡非同步處理剛寫入的資料，可能在提交之前就開始執行而找不到那筆資料。

## 常見追問

### @Async 與訊息佇列該怎麼選？

**核心答案**：判準是**任務丟失的後果**。`@Async` 的任務在**行程記憶體裡**——實例重啟、崩潰、或被 Kubernetes 驅逐時，佇列裡等待的任務全部消失，而且沒有任何記錄。訊息佇列則**持久化任務**，消費失敗可以重試、可以進死信佇列、也可以由另一個實例接手。**所以「丟了也沒關係」的用 `@Async`（記錄非關鍵日誌、更新快取、發送可有可無的通知），「不能丟」的用訊息佇列（訂單處理、扣款、對外通知）。**

**詳細解析**：**還有一個維度是「處理能力的解耦」**。`@Async` 的處理能力綁在同一個行程裡——要擴充非同步處理，只能擴充整個服務。訊息佇列讓生產者與消費者可以獨立擴充，也可以用不同的技術實作。**代價是引入了一個外部依賴與它的維運成本。** **一個常被忽略的中間選項是「持久化到資料庫再由排程處理」**——用一張任務表加上定時掃描，它有持久性但不需要引入訊息中介軟體，適合任務量不大但不能丟的場景（例如 Outbox 模式）。**認出這個中間選項，能避免「不是 `@Async` 就是 Kafka」的二分思維。**

**面試回答方式**：給核心判準——**任務丟失的後果**，並具體說明 `@Async` 的任務在行程記憶體裡、重啟就全部消失且沒有記錄。給出對應的場景分類。加分點是第二個維度**處理能力的解耦**（`@Async` 綁在同一行程、佇列可獨立擴充），以及**中間選項：持久化到資料庫再由排程處理**（Outbox 模式），適合任務量不大但不能丟的場景——這避免了「不是 `@Async` 就是 Kafka」的二分思維。

### 虛擬執行緒對 @Async 有什麼影響？

**核心答案**：Spring Boot 3.2 起，設定 `spring.threads.virtual.enabled=true` 之後，`@Async` 的預設執行器會改用虛擬執行緒（每個任務一個）。**好處是不再需要精算執行緒池大小**——IO 密集的非同步任務可以大量並行。**但它不是萬靈丹**：沒有並行度上限意味著**對下游的壓力沒有限制**，一萬個並行的非同步任務同時打一個外部 API 會直接壓垮它。

**詳細解析**：**所以「限流」的責任從執行緒池轉移到了明確的機制**——用信號量限制同時進行的下游呼叫數、用限流器控制速率、或者仍然用有界的佇列。**這是一個典型的「移除了一個隱含限制，就必須補上一個明確限制」的情況**：原本執行緒池大小 50 意外地限制了下游並發，換成虛擬執行緒後那個限制消失了。**而且 CPU 密集的非同步任務不該用虛擬執行緒**——它們不阻塞，虛擬執行緒沒有好處，反而多了排程與快取汙染。**所以即使啟用了虛擬執行緒，仍然應該為 CPU 密集的任務保留一個固定大小的平台執行緒池，並用 `@Async("cpuBoundExecutor")` 明確指定。**

**面試回答方式**：給出啟用方式與好處（不必精算池大小），然後給關鍵限制：**沒有並行度上限意味著對下游的壓力沒有限制**，一萬個並行任務會壓垮外部 API。把它歸納成一個模式：**移除了一個隱含限制就必須補上一個明確限制**（原本池大小 50 意外地限制了下游並發）。加分點是指出 **CPU 密集任務不該用虛擬執行緒**，應該保留固定大小的平台執行緒池並用 `@Async("...")` 明確指定。

### 怎麼測試 @Async 的方法？

**核心答案**：兩種策略。**同步化測試**——在測試設定中提供一個 `SyncTaskExecutor`（在呼叫執行緒上直接執行），這樣測試變成同步的、確定的、不需要等待。這適合驗證**業務邏輯**。**真正非同步的測試**——用 `Awaitility` 這類工具輪詢等待條件成立（`await().atMost(5, SECONDS).until(...)`），適合驗證**非同步行為本身**（有沒有真的在另一個執行緒、有沒有正確處理例外）。**絕對不要用 `Thread.sleep`**——它讓測試又慢又不穩定。

**詳細解析**：**還要注意 `@Async` 在測試中可能根本沒生效**。如果測試沒有載入包含 `@EnableAsync` 的設定，或者被測的 bean 是直接 `new` 出來的而非從容器取得，那個註解完全沒有作用——**測試會通過，但它測的是同步版本**。**這類「測試通過但測的不是真的東西」的問題，在所有基於 AOP 的功能上都存在**（`@Transactional`、`@Cacheable`、`@PreAuthorize` 都一樣）。**防護方式是至少寫一個測試明確驗證代理有生效**——例如斷言注入的 bean 是一個代理（`AopUtils.isAopProxy`），或者驗證方法確實在不同的執行緒上執行。

**面試回答方式**：給兩種策略與各自適用的目標（同步化測業務邏輯、Awaitility 測非同步行為），並明確反對 `Thread.sleep`。真正的加分點是提出**測試中 `@Async` 可能根本沒生效**——沒載入 `@EnableAsync` 或 bean 是直接 new 的，測試會通過但測的是同步版本。指出這類問題在所有 AOP 功能上都存在，並給防護：**至少寫一個測試驗證代理有生效**（斷言是 AOP 代理，或驗證在不同執行緒上執行）。
