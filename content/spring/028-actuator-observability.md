# 題目

Actuator 提供哪些能力？健康檢查該怎麼設計才對 Kubernetes 有意義？

## 核心答案

Actuator 把應用的**內部狀態暴露成 HTTP 端點或 JMX**，主要有四類。**健康檢查**（`/health`）——聚合各個 `HealthIndicator` 的結果（資料庫、磁碟、自訂）。**指標**（`/metrics`、`/prometheus`）——透過 Micrometer 暴露 JVM、HTTP、資料庫連線池等指標。**診斷資訊**（`/env`、`/configprops`、`/beans`、`/mappings`、`/conditions`）——實際生效的設定、註冊的 bean、路由表、自動配置的判定結果。**操作端點**（`/loggers` 動態調整日誌級別、`/threaddump`、`/heapdump`）。

健康檢查對 Kubernetes 有意義的關鍵是**區分三種探針**。**liveness**（活著嗎）——失敗會**重啟容器**，所以**絕對不能包含外部依賴**：資料庫掛了不該重啟應用（重啟解決不了，只會讓所有實例一起重啟）。**readiness**（能服務嗎）——失敗會**從負載平衡摘除但不重啟**，這裡才該檢查關鍵依賴。**startup**——給啟動慢的應用更長的初始寬限期。

Spring Boot 提供 `/health/liveness` 與 `/health/readiness` 兩個群組，並且會在關閉流程開始時自動把 readiness 標成不健康，讓流量先被摘除。

## 詳細解析

「liveness 不該檢查外部依賴」是最重要也最常被違反的一條。把資料庫檢查放進 liveness 的後果是：資料庫短暫故障 → 所有應用實例的 liveness 失敗 → **全部被 Kubernetes 重啟** → 重啟後仍然連不上資料庫 → 進入 CrashLoopBackOff → 資料庫恢復後應用還在退避等待中。一個下游的短暫故障被放大成全站的長時間中斷，這是真實發生過很多次的事故模式。

**readiness 該檢查什麼也需要判斷**。原則是「沒有它就無法正確服務任何請求」——主資料庫算，一個只影響次要功能的下游不算。把所有依賴都放進 readiness 會讓服務過度敏感：某個非關鍵的下游抖動就導致全部實例被摘除，變成沒有實例可用。更好的做法是讓非關鍵依賴的故障走降級路徑（回傳部分結果或快取值）而不是讓整個實例不可用。

**端點的安全性必須處理**。`/env`、`/configprops`、`/heapdump` 會洩漏設定值（可能含機密）與完整記憶體內容。**預設只有 `/health` 與 `/info` 對外暴露是對的**，其餘應該：只在管理埠（`management.server.port`）上開啟、限制在內網、並加上認證。把 Actuator 完全暴露在公網是一個經典的資安漏洞。

指標的價值取決於有沒有人看。暴露幾百個指標而沒有儀表板與告警，等於沒有。務實的做法是先定義少數幾個關鍵指標（請求延遲分布、錯誤率、飽和度指標如佇列深度與連線池使用率），建立告警，之後再依需要擴充。Micrometer 的 `@Timed` 與 Observation API 讓自訂業務指標的成本很低，但每個新指標都應該回答「什麼情況下我會看它」。

## 面試回答方式

先給 Actuator 的**四類能力**（健康檢查、指標、診斷資訊、操作端點）。健康檢查的部分要把**三種探針的語意**講清楚，並把最重要的一條放在前面：**liveness 絕對不能包含外部依賴**，並用完整的事故鏈說明後果——資料庫短暫故障導致所有實例被重啟、進入 CrashLoopBackOff、資料庫恢復後應用還在退避，一個下游的短暫故障被放大成全站長時間中斷。接著給 readiness 的判準（沒有它就無法正確服務任何請求）並指出把所有依賴都放進去會讓服務過度敏感，非關鍵依賴應該走降級路徑。加分點是**端點的安全性**（`/env`、`/heapdump` 會洩漏機密與記憶體，應該只在管理埠與內網開啟）以及指標的價值取決於有沒有人看——每個新指標都該回答「什麼情況下我會看它」。

## 講稿

Actuator 把應用的內部狀態暴露成 HTTP 端點，主要有四類。健康檢查、指標、診斷資訊像是實際生效的設定跟路由表、還有操作端點比如動態調整日誌級別。

健康檢查對 Kubernetes 有意義的關鍵是區分三種探針。存活探針失敗會重啟容器，就緒探針失敗只會從負載平衡摘除，啟動探針給啟動慢的應用更長的寬限期。

最重要也最常被違反的一條是，存活探針絕對不能包含外部依賴。把資料庫檢查放進去的後果是這樣。資料庫短暫故障，所有實例的存活探針失敗，全部被重啟。重啟之後仍然連不上，進入崩潰回圈退避。等資料庫恢復了，應用還在退避等待中。一個下游的短暫故障，被放大成全站的長時間中斷。

就緒探針該檢查什麼也需要判斷。原則是沒有它就無法正確服務任何請求。主資料庫算，一個只影響次要功能的下游不算。把所有依賴都放進去會讓服務過度敏感，某個非關鍵下游抖動就導致全部實例被摘除。

還有安全性，環境端點跟堆積轉儲會洩漏設定值跟完整記憶體，應該只在管理埠跟內網開啟。

## 常見追問

### 自訂 HealthIndicator 要注意什麼？

**核心答案**：三點。**必須有逾時**——健康檢查若阻塞在一個沒有回應的下游上，探針本身會逾時，而 Kubernetes 會把「探針逾時」視為失敗，等於讓一個慢的依賴變成實例不可用。**必須輕量**——探針會被高頻呼叫（預設每 10 秒），做一次全表掃描或複雜查詢是不可接受的。**要分類到正確的群組**——用 `management.endpoint.health.group.readiness.include` 明確指定哪些指標屬於 readiness，不要讓自訂的指標預設出現在 liveness 裡。

**詳細解析**：還有一個設計上的判斷：健康檢查應該反映「能不能服務」而不是「一切正常」。一個依賴的降級狀態（例如快取失效但仍能直接查資料庫）不該讓 readiness 失敗——服務仍然能正確回應，只是慢一點。把這類狀態放進健康檢查會導致不必要的摘除。更好的表達方式是用指標與告警：健康檢查回答二元的「能不能服務」，指標描述連續的「服務品質如何」。混淆這兩者是健康檢查設計最常見的問題——把所有想監控的東西都塞進健康檢查，結果是探針既不穩定又不精確。

**面試回答方式**：給三個技術要點（必須有逾時、必須輕量、要分類到正確群組）並說明各自的後果。真正的加分點是設計判斷：健康檢查應該反映「能不能服務」而非「一切正常」，降級但仍能服務的狀態不該讓 readiness 失敗。收在職責劃分：健康檢查回答二元的能不能，指標描述連續的服務品質如何，混淆兩者是最常見的設計問題。

### 為什麼關閉時 readiness 要先變成不健康？

**核心答案**：因為負載平衡器需要時間才能感知到實例下線。如果應用收到 SIGTERM 後立刻停止接受連線，在負載平衡器更新之前送過來的請求會直接失敗——使用者看到 502 或連線重置。正確的流程是：收到 SIGTERM → **readiness 立刻變成不健康** → 等待負載平衡器摘除（通常是探針間隔的兩到三倍）→ 才開始關閉並排空進行中的請求。

**詳細解析**：Spring Boot 支援這個流程：`server.shutdown=graceful` 讓內嵌伺服器在關閉時停止接受新請求並等待進行中的完成（`spring.lifecycle.timeout-per-shutdown-phase` 控制等待時間），而 `management.endpoint.health.probes.enabled=true` 加上 Kubernetes 的探針設定會讓 readiness 在關閉開始時自動變成 `OUT_OF_SERVICE`。但等待傳播的那段時間需要自己配置——Kubernetes 的 `preStop` hook 睡個幾秒是常見做法，因為它在 SIGTERM 之前執行。整個關閉的時間預算（傳播等待 + 請求排空 + 資源關閉）必須小於 `terminationGracePeriodSeconds`，否則會被 SIGKILL 打斷。這個時間預算的對齊是「優雅關閉沒有真的優雅」最常見的原因。

**面試回答方式**：給出根本原因——負載平衡器需要時間感知下線，立刻停止接受連線會讓傳播完成前的請求直接失敗。給出正確的四步流程。加分點是具體的設定項（`server.shutdown=graceful`、探針啟用）並指出等待傳播的那段時間要自己配置（`preStop` hook 睡幾秒）。收在最常見的問題：**整個關閉時間預算必須小於 `terminationGracePeriodSeconds`**，否則會被 SIGKILL 打斷，這是「優雅關閉沒有真的優雅」的常見原因。

### /conditions 端點在什麼時候有用？

**核心答案**：排查自動配置為什麼生效或沒生效的時候。它列出所有的條件判定：哪些自動配置類別被套用（positive matches）、哪些被跳過以及原因（negative matches）、哪些被明確排除。當「我加了依賴但那個功能沒出現」或「我不想要的 bean 被自動建立了」時，這個端點直接給出答案，而不必去猜或翻原始碼。

**詳細解析**：常見的判定原因有幾類：`@ConditionalOnClass` 找不到某個類別（依賴沒引入或版本不對）、`@ConditionalOnMissingBean` 因為使用者已經定義了同型別的 bean 而跳過（這是最容易誤解的一種——你自己定義的 bean 讓自動配置退讓了）、以及 `@ConditionalOnProperty` 的屬性沒設。`--debug` 啟動參數會在主控台印出同樣的報告，適合在啟動階段就看。這個端點體現了 Spring Boot 自動配置的一個重要設計：它是可解釋的——每個決定都有明確的條件與記錄，而不是黑箱。評價一個「約定優於配置」的框架時，「當約定不符合預期時能不能查出原因」是關鍵指標，Spring Boot 在這一點上做得相當好。

**面試回答方式**：給出使用場景（排查自動配置為什麼生效或沒生效）與它列出的三類資訊。加分點是常見判定原因，特別是 `@ConditionalOnMissingBean` 因為你自己定義了 bean 而讓自動配置退讓——這是最容易誤解的一種。收在一個評價：這體現了自動配置的「可解釋性」，每個決定都有明確記錄；而評價「約定優於配置」的框架時，「約定不符預期時能不能查出原因」是關鍵指標。
