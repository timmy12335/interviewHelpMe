# 題目

什麼情況下該用 WebFlux 而不是 Spring MVC？虛擬執行緒出現後這個答案有什麼變化？

## 核心答案

WebFlux 的價值在用少量執行緒處理大量並行連線。傳統的 Servlet 模型是「一個請求一個執行緒」，執行緒在等待 IO 時被佔用；WebFlux 用事件迴圈加非阻塞 IO，等待時執行緒可以去處理別的請求，所以幾個執行緒就能撐住數萬個連線。

適用場景有三類：**高並行且以 IO 等待為主**（大量的下游呼叫聚合）、**長連線**（SSE、WebSocket、串流回應）、以及**需要串流式背壓**（處理無界的資料流，下游處理不過來時要能讓上游減速）。

代價很實在：**整條鏈路必須全部非阻塞**——只要一個阻塞呼叫（JDBC、傳統 HTTP 客戶端、任何 `synchronized` 的等待）出現在事件迴圈執行緒上，就會阻塞整個事件迴圈、拖垮所有請求。**除錯體驗差**（堆疊追蹤斷裂、上下文傳遞複雜）、**學習曲線陡**、**與現有生態的整合成本高**（JPA 是阻塞的，要用 R2DBC）。

虛擬執行緒改變了第一項的計算：阻塞變便宜之後，「一個請求一個執行緒」的簡單寫法也能撐住大量並行。所以現在選 WebFlux 的理由主要剩下第二與第三類——長連線與串流式背壓，而純粹為了並行度的場景，虛擬執行緒是成本低得多的選項。

## 詳細解析

「整條鏈路必須非阻塞」是最容易被低估的約束。一個看似無害的呼叫——記錄日誌到同步的 appender、讀一個設定檔、呼叫一個第三方 SDK——都可能是阻塞的。而問題的症狀不是那個請求變慢，是整個服務的吞吐崩塌，因為事件迴圈執行緒只有幾個。**這讓 WebFlux 的正確性要求遠高於 MVC**：MVC 裡一個慢呼叫只影響那一個執行緒，WebFlux 裡它影響全部。Reactor 提供了 `BlockHound` 這類工具在測試時偵測阻塞呼叫，在採用 WebFlux 時應該把它加進測試流程。

背壓是 WebFlux 相對於虛擬執行緒真正無法被取代的能力。虛擬執行緒讓阻塞變便宜，但它沒有提供「告訴上游減速」的機制——阻塞式的背壓只能透過有界佇列與阻塞來實現，那在跨網路的串流場景（例如從 Kafka 消費並轉發、或處理一個很長的 SSE 流）不夠用。Reactive Streams 的 `request(n)` 是一個明確的、可以跨越網路邊界傳遞的需求訊號。判斷是否需要它的問題是：資料來源是不是無界且速率不受你控制？ 是的話，背壓是必要的。

除錯成本是採用時最常被低估的一項。堆疊追蹤只顯示反應式框架的內部框架，看不到「是誰觸發了這個操作」；上下文（追蹤 ID、使用者資訊）不能用 `ThreadLocal` 傳遞，要用 Reactor Context 並在每個操作符之間明確傳遞。這些成本在寫的時候不明顯，在半夜排查生產問題時全部浮現。 團隊經驗不足時，這往往是採用失敗的主因，而不是技術本身的問題。

**混用是可行但要小心的**。Spring 允許在同一個應用裡同時有 MVC 與 WebFlux 的元件（雖然不能同時作為主要的 Web 堆疊），也允許在 MVC 裡用 `WebClient`（非阻塞的 HTTP 客戶端）。**後者是一個很划算的組合**——用 MVC 的簡單模型，但下游呼叫用非阻塞的客戶端加 `CompletableFuture` 聚合，拿到部分的並行收益而不必全面改寫。

## 面試回答方式

先給 WebFlux 的核心價值（少量執行緒處理大量並行連線）與**三類適用場景**（高並行 IO 等待、長連線、串流式背壓）。接著給代價，並把 「整條鏈路必須全部非阻塞」放在最前面——一個阻塞呼叫就會拖垮整個事件迴圈，症狀不是那個請求變慢而是整個服務吞吐崩塌，所以正確性要求遠高於 MVC，應該用 BlockHound 在測試時偵測。然後給出最重要的判斷：虛擬執行緒改變了第一項的計算，純粹為了並行度的場景現在有成本低得多的選項，所以選 WebFlux 的理由主要剩下長連線與串流式背壓。加分點有兩個：背壓是虛擬執行緒無法取代的能力，判斷問題是「資料來源是不是無界且速率不受你控制」；以及**混用是划算的中間路線**——MVC 的簡單模型加上 `WebClient` 的非阻塞下游呼叫。

## 講稿

WebFlux 的價值在用少量執行緒處理大量並行連線。傳統的模型是一個請求一個執行緒，執行緒等待 IO 的時候被佔用。WebFlux 用事件迴圈加非阻塞 IO，等待的時候執行緒可以去處理別的請求。

適用場景有三類。高並行且以 IO 等待為主、長連線像是串流回應、還有需要串流式背壓。

代價很實在，而且最容易被低估的是整條鏈路必須全部非阻塞。只要一個阻塞呼叫出現在事件迴圈執行緒上，症狀不是那個請求變慢，是整個服務的吞吐崩塌，因為事件迴圈執行緒只有幾個。所以 WebFlux 的正確性要求遠高於 MVC。

虛擬執行緒改變了第一項的計算。阻塞變便宜之後，一個請求一個執行緒的簡單寫法也能撐住大量並行。所以現在選 WebFlux 的理由主要剩下長連線跟串流式背壓。

背壓是虛擬執行緒無法取代的。它讓阻塞變便宜，但沒有提供告訴上游減速的機制。我判斷需不需要的問題是，資料來源是不是無界而且速率不受你控制。

還有一個划算的中間路線，用 MVC 的簡單模型，但下游呼叫改用非阻塞的客戶端，拿到部分並行收益而不必全面改寫。

## 常見追問

### 反應式的上下文傳遞為什麼困難？

**核心答案**：因為 **`ThreadLocal` 在反應式模型下完全不可靠**——一個請求的處理鏈會在多個執行緒之間切換（每個操作符可能在不同的執行緒上執行），`ThreadLocal` 的值不會跟著走。Reactor 提供了 **Reactor Context**——一個附加在訂閱上的不可變鍵值映射，它隨著訂閱鏈傳遞而不是隨著執行緒。取值要用 `Mono.deferContextual` 或 `contextWrite`。

**詳細解析**：問題在於整個生態都建立在 `ThreadLocal` 上：MDC（日誌的追蹤 ID）、Spring Security 的 `SecurityContextHolder`、以及大量第三方函式庫。**Reactor 與 Micrometer 提供了橋接機制**（`ContextPropagation`），在關鍵的邊界上把 Reactor Context 的值寫進 `ThreadLocal` 再清掉，讓既有的函式庫能運作——但這個橋接需要在正確的地方啟用，漏掉就會出現「有些日誌有追蹤 ID、有些沒有」的破碎狀態。這正是「新模型與既有生態的阻抗不匹配」的具體例子，而這類成本在評估技術選型時經常被忽略。

**面試回答方式**：給根本原因——`ThreadLocal` 綁在執行緒上，而反應式鏈會在多個執行緒間切換，所以要用隨訂閱傳遞的 Reactor Context。真正的加分點是指出整個生態建立在 `ThreadLocal` 上（MDC、SecurityContextHolder、第三方函式庫），需要橋接機制而漏掉就會出現破碎的追蹤狀態。收在觀點：這是「新模型與既有生態的阻抗不匹配」的具體例子，這類成本在技術選型時經常被忽略。

### R2DBC 相較於 JDBC 有哪些限制？

**核心答案**：三類。**功能覆蓋較少**——JDBC 有二十多年的生態，R2DBC 的驅動、連線池、以及 ORM 支援都年輕得多。**沒有完整的 ORM**——Spring Data R2DBC 是輕量的資料映射，沒有延遲載入、沒有關聯的自動抓取、沒有一級快取（因為這些機制本質上依賴同步的存取模式）。**交易的表達不同**——宣告式交易在反應式下要用 `TransactionalOperator` 或 `@Transactional` 搭配反應式交易管理器，語意與傳統的 ThreadLocal 綁定不同。

**詳細解析**：「沒有完整 ORM」對很多團隊是決定性的——習慣了 JPA 的關聯導覽與延遲載入之後，改用手動的查詢與映射會顯著增加工作量。**但這也可以看成好事**：JPA 的延遲載入是 N+1 問題與 `LazyInitializationException` 的來源，明確的查詢反而更可控。真正的判斷是團隊願不願意接受這個轉變的成本。 另外要注意**資料庫本身可能成為瓶頸**——反應式的應用層能處理數萬並行，但資料庫的連線數與處理能力沒有變，非阻塞只是讓等待更便宜，不會讓資料庫更快。這是反應式改造中最常見的期望落差。

**面試回答方式**：給三類限制並展開「沒有完整 ORM」——沒有延遲載入、關聯自動抓取、一級快取，因為它們本質上依賴同步存取模式。給出平衡的評價：這也可以看成好事，因為延遲載入正是 N+1 與 `LazyInitializationException` 的來源。真正的加分點是指出**資料庫本身可能成為瓶頸**——非阻塞只讓等待更便宜，不會讓資料庫更快，這是反應式改造中最常見的期望落差。

### 已經用了 WebFlux 的專案，該不該改回去？

**核心答案**：看它是否真的用到了 WebFlux 的獨特能力。如果是為了長連線或串流式背壓，那沒有替代品，繼續用。如果只是為了並行度，而團隊在除錯與維護上持續付出成本，那麼在虛擬執行緒可用的前提下，改回阻塞式模型是合理的——但改寫本身有成本與風險，應該評估「持續的維護成本」與「一次性的改寫成本」哪個大。

**詳細解析**：**務實的做法通常是漸進的**：新的端點用 MVC 加虛擬執行緒寫、既有的端點在需要大改時順便遷移，而不是一次全部重寫。Spring 允許兩種模型在不同的服務中共存（雖然同一個應用不能同時作為主要 Web 堆疊，但可以拆成不同的服務）。更重要的是誠實評估「持續成本」是多少——如果團隊已經熟悉了反應式、工具鏈也配好了，那個成本可能沒有想像中高；如果每次排查生產問題都要花好幾倍的時間，那就是實質的損失。技術債的償還與否應該基於量測而不是偏好，而「每次排查問題多花多少時間」是可以粗略量測的。

**面試回答方式**：給判準——**是否真的用到獨特能力**（長連線、串流背壓沒有替代品；只為並行度則虛擬執行緒是更低成本的選項）。給出務實做法：**漸進遷移**，新端點用新模型、既有的在需要大改時順便遷移。真正的加分點是強調**誠實評估持續成本**：如果團隊已熟悉且工具鏈配好，成本可能不高；如果每次排查都多花好幾倍時間，那是實質損失。收在原則：技術債的償還應該基於量測而非偏好，而排查時間是可以粗略量測的。
