# 題目

要為團隊做一個共用的 starter，該怎麼設計？有哪些容易做錯的地方？

## 核心答案

一個 starter 通常拆成**兩個模組**：`xxx-spring-boot-autoconfigure`（放自動配置類別與設定屬性）與 `xxx-spring-boot-starter`（只有依賴宣告，把 autoconfigure 與必要的第三方依賴聚合起來）。**分開的理由是讓不想要自動配置的使用者可以只依賴前者**，或者反過來只引入依賴而自己寫配置。

自動配置類別的三個要素：**`@AutoConfiguration`**（Spring Boot 3；2.x 用 `@Configuration`）標註類別；**條件註解**決定何時生效（`@ConditionalOnClass`、`@ConditionalOnProperty`、以及最重要的 **`@ConditionalOnMissingBean`**）；**註冊到 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`**（Boot 3；2.x 用 `spring.factories`）。

**`@ConditionalOnMissingBean` 是設計的核心**——它讓使用者只要自己定義了同型別的 bean，你的預設就自動退讓。**這是「提供預設但不強加」的實現方式**，也是 Spring Boot 整個自動配置生態的基礎規則。

最容易做錯的三件事：**沒有加 `@ConditionalOnMissingBean`**（使用者無法覆寫）、**沒有提供關閉的開關**（`@ConditionalOnProperty` 加一個 `enabled` 屬性）、以及**在自動配置裡做耗時或會失敗的初始化**（讓所有引入者的啟動變慢或變脆弱）。

## 詳細解析

**命名規範要遵守**：官方的 starter 叫 `spring-boot-starter-xxx`，**第三方的應該叫 `xxx-spring-boot-starter`**——這不只是禮貌，它讓使用者一眼看出這不是 Spring 官方維護的。同樣地，設定屬性的前綴不該用 `spring.`，那是保留給框架的。

**條件的順序與粒度需要設計**。`@ConditionalOnClass` 應該檢查**真正會被用到的類別**，這樣使用者沒有引入對應依賴時整個配置類別會被跳過而不是在載入時拋錯。**`@AutoConfiguration` 的 `before`／`after` 屬性控制配置之間的順序**——如果你的配置依賴另一個自動配置產生的 bean（例如 `DataSource`），必須宣告在它之後，否則條件判定時對方還不存在。**這類順序問題的症狀是「有時候生效有時候不生效」，非常難查。**

**設定屬性的設計決定了使用體驗**。用 `@ConfigurationProperties` 定義一個型別化的設定類別、加上 `spring-boot-configuration-processor` 產生中繼資料（讓 IDE 有自動完成）、**並為每個屬性寫 Javadoc**（它會變成 IDE 的提示文字）。**這一步的邊際成本很低但對使用者的體驗差別很大**，卻經常被跳過。

**最重要的設計原則是「零配置可用、有需要時可調、必要時可完全接管」**。零配置可用意味著加入依賴就能運作（用合理的預設值）；可調意味著常見的變化透過屬性完成；可完全接管意味著使用者定義自己的 bean 時你完全退讓。**三個層次都提供，才是一個好的 starter**——只做到第一層會讓使用者被綁死，只做到第三層則失去了 starter 的意義。

## 面試回答方式

先給**兩個模組的拆分**與拆分的理由（讓使用者可以只要依賴或只要配置）。接著給自動配置類別的三個要素，並把 **`@ConditionalOnMissingBean` 定位成設計核心**——它讓使用者自己定義同型別 bean 時你的預設自動退讓，這是「提供預設但不強加」的實現方式，也是整個自動配置生態的基礎規則。給出最容易做錯的三件事（沒有 `@ConditionalOnMissingBean`、沒有關閉開關、在自動配置裡做耗時或會失敗的初始化）。加分點有兩個：**`@AutoConfiguration` 的 before／after 順序問題**，症狀是「有時候生效有時候不生效」非常難查；以及**為每個設定屬性寫 Javadoc**（會變成 IDE 提示），邊際成本低但體驗差別大。收在核心原則：**零配置可用、有需要時可調、必要時可完全接管**，三層都要有。

## 講稿

我會拆成兩個模組。一個放自動配置類別跟設定屬性，另一個只有依賴宣告，把前者跟必要的第三方依賴聚合起來。分開的理由是讓不想要自動配置的使用者可以只依賴前者。

自動配置類別有三個要素。用註解標註類別、用條件註解決定何時生效、還有註冊到指定的中繼資料檔案讓框架掃描得到。

設計的核心是「當使用者沒有定義同型別 bean 時才生效」這個條件。它讓使用者只要自己定義了，你的預設就自動退讓。這是提供預設但不強加的實現方式，也是整個自動配置生態的基礎規則。

## 常見追問

### Boot 3 為什麼把 spring.factories 換成新的檔案？

**核心答案**：因為 `spring.factories` **把所有種類的擴充點混在同一個檔案裡**——自動配置、監聽器、初始化器、失敗分析器都用它，而且格式是一個很長的 properties 行（用反斜線續行），**難讀、難維護、也難以增量處理**。Boot 3 把自動配置獨立出來放進 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`，**一行一個類別名，格式簡單得多**。

**詳細解析**：更實質的動機是**啟動效能與 AOT**。舊格式需要在啟動時讀取所有 JAR 的 `spring.factories`、解析、合併，而新格式的每一類擴充點有自己的檔案，**可以只載入需要的那一類**。對 AOT 與原生映像檔而言，**明確、簡單的格式讓建置期的分析更可靠**。`spring.factories` 在 Boot 3 中仍然支援其他擴充點，只有自動配置被搬走了——**這種「逐步遷移而非一次全換」的做法本身也值得注意**，它讓生態有時間跟上。

**面試回答方式**：先給表面理由（混在同一個檔案、格式難讀難維護），再給更實質的動機——**啟動效能與 AOT**：分開的檔案可以只載入需要的那一類，而明確簡單的格式讓建置期分析更可靠。加分點是指出**只有自動配置被搬走，其他擴充點仍用 `spring.factories`**，這種逐步遷移而非一次全換的做法讓生態有時間跟上。

### 自訂 starter 怎麼測試？

**核心答案**：用 **`ApplicationContextRunner`**——它是 Spring Boot 專門為測試自動配置提供的工具，可以在**不啟動完整應用**的情況下模擬各種條件組合。典型的測試包括：**預設情況下 bean 被建立**、**使用者定義了同型別 bean 時自動配置退讓**、**關閉開關生效**、**缺少某個類別時配置被跳過**、以及**設定屬性正確綁定**。

**詳細解析**：`ApplicationContextRunner` 的價值在於它讓**條件邏輯本身變成可測試的**。條件註解的組合很容易出錯（順序、AND/OR 語意、classpath 狀態），而這些錯誤在整合測試裡不一定顯現——因為整合測試通常只覆蓋一種條件組合。**`withClassLoader(new FilteredClassLoader(SomeClass.class))` 可以模擬「某個類別不在 classpath 上」**，這是驗證 `@ConditionalOnClass` 的唯一實際方法。**「為擴充點的條件邏輯寫測試」是自訂 starter 與隨手寫的自動配置之間最大的差別**——沒有這些測試，starter 在使用者的各種環境下的行為是未知的。

**面試回答方式**：給出工具（`ApplicationContextRunner`）與五種典型測試場景。真正的加分點是說明它的價值——**讓條件邏輯本身變成可測試的**，而條件錯誤在整合測試裡不一定顯現（只覆蓋一種組合）。給出具體技巧 `FilteredClassLoader` 模擬類別不在 classpath 上。收在判斷：**為條件邏輯寫測試是正式 starter 與隨手寫的自動配置之間最大的差別**。

### 什麼情況下不該做 starter？

**核心答案**：三種。**只有一兩個地方會用**——直接寫一個 `@Configuration` 類別放進共用模組就好，starter 的樣板與維護成本不值得。**邏輯會頻繁變動**——starter 一旦被多個服務依賴，改動的擴散成本很高，每次都要各服務升級版本。**沒有明確的「預設值」可言**——如果每個使用者的設定都完全不同，自動配置提供不了價值，只是多一層間接。

**詳細解析**：**還有一個常被忽略的成本：版本管理**。一個被十個服務依賴的 starter，發布新版本後要追蹤誰升級了、誰還在舊版；出現 bug 時要判斷影響範圍；而且它會**把自己的傳遞依賴強加給所有使用者**，可能造成版本衝突。**這些成本在「內部共用函式庫」上普遍存在，不只是 starter。** 務實的判斷是：**先讓程式碼在兩三個服務裡各自存在一段時間，等模式穩定了再抽成 starter**。過早抽象的代價是抽錯了方向，而修正一個已被廣泛依賴的抽象比修正重複的程式碼貴得多。**「重複三次再抽象」在共用函式庫上尤其適用。**

**面試回答方式**：給三種不該做的情況並各配理由。加分點是提出**版本管理的成本**——追蹤誰升級了、判斷 bug 影響範圍、以及把傳遞依賴強加給所有使用者可能造成版本衝突。收在務實判斷：**先讓程式碼在兩三個服務裡各自存在，等模式穩定了再抽**，因為修正一個被廣泛依賴的錯誤抽象比修正重複程式碼貴得多。
