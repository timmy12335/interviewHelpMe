# 題目

`@Value` 與 `@ConfigurationProperties` 該怎麼選？後者有哪些好處？

## 核心答案

`@Value("${app.timeout}")` 是**逐個屬性注入**，適合只需要一兩個值的簡單情況。`@ConfigurationProperties(prefix = "app")` 是**把一整組屬性綁定到一個型別化的物件**上，適合有結構的設定。

`@ConfigurationProperties` 的好處有五個。**型別安全與結構化**——設定變成一個有欄位的類別，IDE 能自動完成、編譯器能檢查。**支援複雜型別**——巢狀物件、`List`、`Map`、`Duration`、`DataSize` 都能自動轉換，`@Value` 只能處理簡單值。**支援 Bean Validation**——加 `@Validated` 之後可以用 `@NotNull`、`@Min` 在**啟動時**就驗證設定，而不是在使用時才發現值是錯的。**寬鬆綁定**（relaxed binding）——`app.readTimeout`、`app.read-timeout`、`APP_READ_TIMEOUT` 都能綁到同一個欄位，這讓環境變數的命名慣例能被支援。**中繼資料**——配合 `spring-boot-configuration-processor` 可以生成設定的自動完成提示。

**實務建議是預設用 `@ConfigurationProperties`**，`@Value` 只留給真正的單一值場景。

## 詳細解析

**「啟動時驗證」是最被低估的好處**。一個錯誤的設定值（負數的逾時、空字串的端點）如果只在第一次使用時才出錯，**問題會出現在部署後的某個請求上**，而且錯誤訊息通常是遠處的 NPE 或連線失敗。用 `@Validated` 加約束註解，**應用會在啟動時直接失敗並明確指出是哪個屬性不合法**——這是「讓失敗發生在早且明確的地方」這個原則的具體應用。

**寬鬆綁定的規則值得知道**：Spring Boot 會嘗試多種形式（camelCase、kebab-case、snake_case、大寫底線）對應到同一個欄位。**這解決了一個真實的痛點**——環境變數在多數系統上只能用大寫與底線，而 Java 欄位是 camelCase。**建議在設定檔中一律使用 kebab-case**（`read-timeout`），因為它是官方推薦且在所有來源中都能正確對應。

**建構子綁定讓設定物件可以不可變**：用 `@ConfigurationProperties` 搭配建構子（Spring Boot 2.2 起，配合 `@ConstructorBinding` 或在 3.x 中自動偵測）可以把設定綁到一個 `record` 或全 final 欄位的類別上。**這比可變的 POJO 好——設定在啟動後不該被修改，用不可變型別把這個約束表達在型別系統裡**，也避免了「某段程式碼意外改了設定物件」這種難查的問題。

**兩者在解析時機上也有差別**。`@Value` 支援 SpEL（`#{...}`），可以做簡單的運算與引用其他 bean；`@ConfigurationProperties` 只做屬性綁定，**不支援 SpEL**。所以需要「依另一個屬性計算出來的值」時，`@Value` 反而是唯一選擇——**但那通常是設計訊號**，更好的做法是在設定類別裡提供一個計算方法，把邏輯放在 Java 而不是字串裡。

## 面試回答方式

先給定位差別（逐個屬性 vs 整組綁定到型別化物件），再給 `@ConfigurationProperties` 的**五個好處**（型別安全、複雜型別、Bean Validation、寬鬆綁定、中繼資料）。把**啟動時驗證**單獨強調——錯誤設定若只在使用時才出錯，問題會出現在部署後的某個請求上且錯誤訊息是遠處的 NPE，加 `@Validated` 讓應用在啟動時直接失敗並指出是哪個屬性。加分點有三個：**寬鬆綁定解決了環境變數只能大寫底線的真實痛點**，建議設定檔一律用 kebab-case；**建構子綁定讓設定物件不可變**，把「啟動後不該修改」表達在型別系統裡；以及 **`@Value` 支援 SpEL 而 `@ConfigurationProperties` 不支援**，但需要 SpEL 通常是設計訊號。

## 講稿

一個是逐個屬性注入，適合只需要一兩個值的簡單情況。另一個是把一整組屬性綁定到一個型別化的物件上，適合有結構的設定。

型別化綁定的好處有五個。型別安全跟結構化、支援巢狀物件跟集合這些複雜型別、支援驗證、寬鬆綁定、還有可以生成自動完成的中繼資料。

我覺得最被低估的是啟動時驗證。一個錯誤的設定值，比如負數的逾時或空字串的端點，如果只在第一次使用的時候才出錯，問題會出現在部署後的某個請求上，而且錯誤訊息通常是遠處的空指標或連線失敗。加上驗證註解之後，應用會在啟動時直接失敗，並明確指出是哪個屬性不合法。

寬鬆綁定解決的是一個真實痛點。環境變數在多數系統上只能用大寫跟底線，而 Java 欄位是駝峰命名。我的建議是設定檔一律用連字號形式，因為它是官方推薦而且在所有來源中都能正確對應。

還有建構子綁定，可以把設定綁到 record 或全 final 欄位的類別上。設定在啟動後不該被修改，用不可變型別把這個約束表達在型別系統裡比較好。

## 常見追問

### 設定的驗證應該做到什麼程度？

**核心答案**：**能在啟動時檢查的都應該檢查**。基本的約束用 Bean Validation 註解（`@NotBlank`、`@Min`、`@Max`、`@Pattern`）；跨欄位的約束（「開始時間必須早於結束時間」「啟用 A 時必須設定 B」）用 `@AssertTrue` 標註的方法或自訂的驗證器；**外部資源的可達性**（資料庫連得上、端點回應）則不該在設定驗證裡做——那屬於健康檢查，混在一起會讓啟動失敗的原因難以區分。

**詳細解析**：**驗證失敗的訊息品質決定了它的價值**。Spring Boot 的設定綁定失敗會產生一段相當長的錯誤，但關鍵資訊（哪個屬性、期望什麼、實際是什麼）都在裡面。**自訂驗證時應該在訊息中包含這三項**，否則使用者只知道「設定錯了」卻不知道要改什麼。另外有一個實用的技巧：**為設定類別寫測試**——用 `@SpringBootTest` 搭配不同的屬性值，驗證合法值能綁定成功、非法值會在啟動時失敗。**這類測試很少見，但它把設定當成程式碼的一部分來對待**，而設定確實是程式碼的一部分——它決定了系統的行為。

**面試回答方式**：給三個層次（基本約束用註解、跨欄位用 `@AssertTrue`、外部資源可達性不該放這裡而屬於健康檢查）並說明理由。加分點是強調**驗證失敗的訊息品質決定價值**——要包含哪個屬性、期望什麼、實際是什麼。收在一個少見但有價值的實踐：**為設定類別寫測試**，驗證合法值能綁定、非法值會啟動失敗，這體現了「設定是程式碼的一部分」的態度。

### 為什麼建議用 record 當設定類別？

**核心答案**：因為設定天生就是**不可變的值物件**——啟動時綁定一次，之後只讀。`record` 精確地表達了這個語意：全部欄位 final、自動生成 `equals`、`hashCode`、`toString`、沒有 setter。Spring Boot 3 對 record 的建構子綁定是自動支援的，不需要額外註解。**它比一個有 getter/setter 的 POJO 少寫大量樣板，而且型別系統直接排除了「有人改了設定物件」這種問題。**

**詳細解析**：有兩個實務細節要注意。**第一，`toString` 會印出全部欄位**——設定裡如果有密碼或金鑰，一次日誌就洩漏了；解法是覆寫 `toString` 遮罩敏感欄位，或者根本不把機密綁進設定物件（改用專門的機密來源）。**第二，巢狀的 record 要能被正確綁定**，需要每一層都是 record 或有對應的建構子；混用 record 與可變 POJO 時綁定行為會不一致。**另外要注意 record 的元件如果是 `List`，Spring 綁定後給的是不可變清單，但 record 本身不會阻止你把一個可變清單傳進去**——所以「record 就是不可變」在有集合元件時需要額外注意，這與 Java 核心類別裡討論的 record 淺層不可變是同一件事。

**面試回答方式**：核心是「**設定天生是不可變的值物件，record 精確表達了這個語意**」並列出它省掉的樣板。真正的加分點是兩個實務細節：**`toString` 會印出全部欄位**，設定裡有機密時一次日誌就洩漏（解法是覆寫遮罩或不把機密綁進來）；以及 **record 是淺層不可變**，集合元件仍需注意，這與 Java 核心的 record 問題是同一件事。

### @Value 什麼時候仍然是對的選擇？

**核心答案**：三種情況。**只需要單一個值且沒有相關的其他設定**——為了一個屬性建立一個設定類別是過度設計。**需要 SpEL 表達式**——`@Value("#{systemProperties['user.region'] ?: 'default'}")` 這類動態邏輯，`@ConfigurationProperties` 不支援。**在測試或原型階段快速取值**——不需要為臨時的東西建立正式結構。

**詳細解析**：**但要注意 `@Value` 的幾個陷阱**。**找不到屬性時的行為**——沒有預設值就啟動失敗（這是好的），但寫成 `@Value("${a.b:}")` 會得到空字串而非 null，這常常不是預期的。**在 `@Bean` 方法的參數上使用時，屬性解析的時機與一般欄位不同**，某些情況下會拿不到值。**而且它散落在各處**——一個屬性被三個類別用 `@Value` 注入時，改名字要找三個地方，而 `@ConfigurationProperties` 只有一處。**這個「散落」的成本會隨專案成長而放大**，所以即使一開始只有一個值，若預期會增加相關設定，直接用 `@ConfigurationProperties` 比較好。

**面試回答方式**：給三種仍然適用的情況（單一值、需要 SpEL、測試或原型）。加分點是列出 `@Value` 的陷阱：**`${a.b:}` 得到空字串而非 null**、在 `@Bean` 方法參數上解析時機不同、以及**它散落在各處**——改名字要找多處而 `@ConfigurationProperties` 只有一處。收在建議：預期會增加相關設定時，即使一開始只有一個值也直接用結構化綁定。
