# 題目

一個 HTTP 請求參數的字串，是怎麼變成方法參數上的 `LocalDate` 或自訂型別的？

## 核心答案

靠 **`ConversionService`** 這個統一的轉換抽象。它管理一組 **`Converter<S, T>`**（單純的型別轉換）與 **`Formatter<T>`**（帶地區設定的字串與物件互轉，適合日期、數字這類需要格式化的型別）。Spring MVC 在綁定請求參數、Spring Boot 在綁定設定屬性、SpEL 在求值時，用的都是同一套機制。

流程是：拿到來源值與目標型別 → `ConversionService` 查找能處理這對型別的轉換器 → 執行轉換。**查找支援繼承與泛型**，所以一個 `Converter<String, Enum>` 能處理所有列舉型別。

自訂型別的支援方式有三種，由簡到繁：**該型別有一個 `String` 參數的建構子或靜態 `valueOf`／`of` 方法**（Spring 會自動使用）、**註冊一個 `Converter<String, MyType>` bean**（最常用）、**實作 `Formatter<MyType>`**（需要地區敏感的格式化時）。

**舊的 `PropertyEditor` 機制仍然存在但不建議使用**——它是有狀態的（非執行緒安全，每次要建立新實例）、只支援 String 與物件的互轉、而且是 JavaBeans 時代的遺留。`ConversionService` 在各方面都更好。

## 詳細解析

**「統一的轉換服務」的價值在於一致性**。註冊一個 `Converter<String, PhoneNumber>` 之後，**它在 HTTP 參數綁定、設定屬性綁定、`@Value` 注入、SpEL 求值中全部生效**——不必在每個使用點各自處理。這正是把橫切關注點抽象成服務的收益。

**日期時間的轉換有幾個常見坑**。預設情況下 Spring 對 `LocalDate` 期望 ISO 格式（`2024-01-15`）；要接受其他格式需要 `@DateTimeFormat(pattern = "yyyy/MM/dd")` 標註參數或欄位，或者註冊一個全域的 `Formatter`。**`@DateTimeFormat` 與 Jackson 的 `@JsonFormat` 作用在不同的路徑上**——前者用於表單參數與路徑變數的綁定，後者用於 JSON 的序列化與反序列化。**同一個 DTO 同時被兩種方式使用時，兩個註解都要加**，這是一個常見的困惑來源。

**資料綁定的安全性需要注意**。`@ModelAttribute` 的綁定會**把請求參數映射到物件的所有可寫屬性上**，如果那個物件包含了不該被使用者設定的欄位（`isAdmin`、`price`、`status`），就是一個權限提升漏洞。**這就是所謂的批量賦值（mass assignment）問題。** 防護方式有三種：**用專門的 DTO** 而不是直接綁定領域物件（最推薦）、用 `@InitBinder` 加 `setAllowedFields`／`setDisallowedFields` 白名單、或者用 `@JsonIgnore` 之類的註解排除。**「用專門的 DTO」之所以最好，是因為它把安全性變成型別問題而不是設定問題**——DTO 裡沒有那個欄位，就沒有辦法被賦值。

**轉換失敗的錯誤處理值得設計**。預設會拋 `MethodArgumentTypeMismatchException` 或綁定錯誤，若沒有處理就變成 400 加上一段對使用者無意義的訊息。**應該用 `@ControllerAdvice` 統一處理，轉成有意義的錯誤回應**（哪個欄位、期望什麼格式、收到了什麼），這對 API 的可用性影響很大。

## 面試回答方式

先給 **`ConversionService`** 這個統一抽象與它管理的兩類元件（`Converter` 單純轉換、`Formatter` 帶地區設定），並強調**一致性的價值**：註冊一次，在 HTTP 參數綁定、設定屬性、`@Value`、SpEL 中全部生效。給出自訂型別的三種支援方式（String 建構子或 valueOf、註冊 `Converter`、實作 `Formatter`）。加分點有三個：**`@DateTimeFormat` 與 `@JsonFormat` 作用在不同路徑**（前者表單與路徑變數、後者 JSON），同一個 DTO 兩種用法都有時兩個註解都要加；**批量賦值漏洞**——`@ModelAttribute` 會綁定到所有可寫屬性，包含不該被使用者設定的欄位，**用專門的 DTO 最好因為它把安全性變成型別問題而非設定問題**；以及轉換失敗應該用 `@ControllerAdvice` 轉成有意義的錯誤回應。

## 講稿

靠一個統一的轉換服務。它管理一組轉換器跟格式化器，前者做單純的型別轉換，後者處理需要地區設定的日期跟數字。Spring MVC 綁定請求參數、Spring Boot 綁定設定屬性、SpEL 求值，用的都是同一套。

這個統一的價值在於一致性。註冊一個字串轉自訂型別的轉換器之後，它在請求參數綁定、設定屬性綁定、注入、SpEL 求值中全部生效，不必在每個使用點各自處理。

自訂型別的支援方式由簡到繁有三種。該型別有一個字串參數的建構子或靜態工廠方法、註冊一個轉換器 bean、或是實作格式化器。

有一個常見的困惑我想提。表單綁定用的日期格式註解，跟 JSON 序列化用的格式註解，作用在不同的路徑上。同一個 DTO 同時被兩種方式使用的時候，兩個註解都要加。

還有一個安全問題。把請求參數直接綁定到領域物件上，會映射到所有可寫的屬性，包含不該被使用者設定的欄位，這就是批量賦值漏洞。防護最好的方式是用專門的 DTO，因為它把安全性變成型別問題而不是設定問題，DTO 裡沒有那個欄位就沒辦法被賦值。

## 常見追問

### Converter 與 Formatter 該選哪個？

**核心答案**：**需要地區敏感的格式化就用 `Formatter`，否則用 `Converter`**。`Converter<S, T>` 是純粹的型別轉換，兩個方向要各寫一個；`Formatter<T>` 專門處理「物件與字串的雙向轉換」，而且 `parse` 與 `print` 都接受 `Locale` 參數——所以同一個 `Formatter` 能依使用者的地區產生不同的表示（金額的千分位符號、日期的順序）。

**詳細解析**：實務上大多數自訂型別用 `Converter` 就夠了——一個電話號碼、一個訂單編號、一個列舉的別名，它們的字串表示與地區無關。**`Formatter` 的必要性主要出現在面向終端使用者的顯示層**（金額、日期、百分比），而現代的做法往往是**把格式化交給前端**（API 回傳 ISO 格式或原始數值，前端依使用者地區呈現）。**這讓 `Formatter` 在純 API 的服務上用得越來越少。** 判斷的問題是：**這個格式化的目標是機器還是人？** 機器用固定格式（ISO），人才需要地區敏感的格式化——而「給人看」這件事在前後端分離的架構下通常不在後端。

**面試回答方式**：給明確判準（需要地區敏感就用 `Formatter`）與兩者的介面差異。真正的加分點是實務觀察：**現代做法是把格式化交給前端**（API 回傳 ISO 格式或原始數值），所以 `Formatter` 在純 API 服務上用得越來越少。收在判斷問題：**這個格式化的目標是機器還是人**——機器用固定格式，而「給人看」在前後端分離下通常不在後端。

### 批量賦值漏洞在真實系統裡怎麼發生？

**核心答案**：典型的路徑是**直接把請求綁定到 JPA 實體**。一個 `updateUser(@ModelAttribute User user)` 的端點，使用者只要在表單或 JSON 裡多送一個 `role=ADMIN` 或 `id=其他人的id`，就可能改到不該改的欄位。**它之所以危險，是因為程式碼看起來完全正常**——沒有任何一行寫著「允許修改角色」，那個能力是綁定機制自動提供的。

**詳細解析**：**同樣的問題也出現在 JSON 反序列化上**——Jackson 預設會把 JSON 裡的所有欄位映射到物件的對應屬性。防護的層次有三：**型別層**（用只包含允許欄位的 DTO，最徹底）、**設定層**（`@InitBinder` 白名單、Jackson 的 `@JsonIgnoreProperties`）、**驗證層**（在服務層檢查使用者有沒有權限改這些欄位）。**三層都做才穩妥，但如果只能做一層，選型別層**——因為它不依賴任何人記得加註解或設定。**這體現了一個安全設計原則：讓不安全的事情在型別上不可能，而不是靠檢查去阻止。** 同樣的思路出現在用參數化查詢防 SQL 注入（不是去過濾危險字元，而是讓資料永遠不會被當成程式碼）。

**面試回答方式**：給出典型路徑（直接綁定到 JPA 實體，多送一個 `role=ADMIN`）並強調**它危險在程式碼看起來完全正常**——沒有一行寫著允許修改角色。給三層防護並主張**只能做一層就選型別層**，因為它不依賴任何人記得加設定。收在安全設計原則：**讓不安全的事在型別上不可能，而不是靠檢查阻止**，並用參數化查詢作為同一思路的例子。

### 綁定失敗的錯誤回應該怎麼設計？

**核心答案**：回傳的資訊要讓呼叫方**知道怎麼修**：**哪個欄位**、**期望什麼**、**收到了什麼**（注意不要把敏感值原樣回傳）。結構上建議用一個統一的錯誤格式（例如 RFC 7807 的 Problem Details，Spring 6 有內建支援），包含錯誤類型、標題、以及一個欄位層級的錯誤清單。**用 `@ControllerAdvice` 統一處理 `MethodArgumentNotValidException` 與 `MethodArgumentTypeMismatchException`**，不要讓每個控制器各自處理。

**詳細解析**：**兩個常被忽略的細節**。**第一，不要洩漏內部資訊**——預設的錯誤訊息可能包含類別名、堆疊追蹤片段或內部欄位名，這既無助於呼叫方也可能洩漏實作細節。**第二，多個錯誤要一次回傳**——只回報第一個錯誤會讓呼叫方需要來回多次才能修好所有問題；Bean Validation 預設會收集全部違規，應該把它們全部回傳。**還有一個 API 設計層面的判斷：驗證失敗回 400 還是 422？** 400 表示請求格式錯誤（無法解析），422 表示格式正確但語意不合法（欄位驗證失敗）——**區分它們讓呼叫方能區分「我送的東西壞了」與「我送的值不合規則」**，雖然實務上很多 API 一律用 400 也能運作。

**面試回答方式**：給出三項必要資訊（哪個欄位、期望什麼、收到什麼）與結構建議（RFC 7807 Problem Details，Spring 6 內建），並強調用 `@ControllerAdvice` 統一處理。加分點是兩個容易忽略的細節：**不要洩漏內部類別名與實作細節**、**多個錯誤要一次回傳**（否則呼叫方要來回多次）。收在 API 設計判斷：**400 是格式錯誤、422 是語意不合法**，區分它們讓呼叫方能分辨兩種情況。
