# 題目

什麼是 N+1 查詢問題？在 Spring Data JPA 裡有哪些解法？

## 核心答案

N+1 是指：查出 N 筆主資料（1 次查詢），**然後為每一筆各查一次關聯資料（N 次查詢）**，總共 N+1 次。它幾乎總是由**延遲載入**造成——查出訂單清單後遍歷它們存取 `order.getCustomer()`，每次存取都觸發一次查詢。**症狀是「資料量少時沒事、資料量一大就慢得離譜」**，而且它在日誌裡表現為大量結構相同的 SQL。

解法有四種，各有適用場景。**`JOIN FETCH`**（在 JPQL 裡明確要求一起查出來）——最直接，但**一次只能 fetch 一個集合**（多個會產生笛卡兒積）。**`@EntityGraph`**（宣告式地指定要抓取的關聯）——與 Spring Data 的方法名推導相容，可讀性好。**批次抓取**（`@BatchSize` 或 `hibernate.default_batch_fetch_size`）——把 N 次查詢合併成 N/batchSize 次的 `IN` 查詢，**不改變程式碼就能大幅改善**，是最容易採用的一種。**投影**（用 DTO 或介面投影只查需要的欄位）——從根本上避免載入整個實體圖。

**最重要的判斷是：預設用延遲載入，在需要時明確地一起抓**——把 `fetch = EAGER` 設在實體上是錯的方向，那會讓每個查詢都拖著一堆用不到的資料。

## 詳細解析

**「資料量小時看不出來」是這個問題最危險的特性**。開發環境的十筆測試資料產生 11 次查詢，感覺不出差別；生產環境的一千筆就是 1001 次查詢，而每次查詢都有網路往返。**所以它必須靠工具而非感覺來發現**：開啟 SQL 日誌（`spring.jpa.show-sql` 或更好的 `logging.level.org.hibernate.SQL=DEBUG`）、用 datasource-proxy 或 p6spy 統計每個請求的查詢次數、**或者在測試中斷言查詢次數**（這是最可靠的做法——寫一個測試驗證「這個操作應該只產生 2 次查詢」，回歸時立刻發現）。

**`JOIN FETCH` 的分頁問題是一個經典陷阱**。對集合關聯做 `JOIN FETCH` 加分頁時，Hibernate **無法在資料庫層面正確分頁**（因為 join 之後的列數與實體數不對應），它會把**全部資料載入記憶體再分頁**，並印出一條警告日誌（`HHH000104: firstResult/maxResults specified with collection fetch; applying in memory`）。**資料量大時這是一個記憶體災難。** 解法是分兩步：先分頁查出 ID，再用 `IN` 查詢加 `JOIN FETCH` 取完整資料。

**批次抓取是投資報酬率最高的一項**。設定 `hibernate.default_batch_fetch_size=100` 之後，Hibernate 會把「載入 100 個代理」合併成一次 `WHERE id IN (...)` 查詢。**它不需要改任何程式碼，對整個應用全面生效**，而且對「無法預先知道要抓什麼」的動態場景特別有用。**多數專案應該預設開啟它**，然後才針對熱點用 `JOIN FETCH` 或投影精細優化。

**投影是最徹底但也最需要改動的解法**。用一個只包含需要欄位的介面或 record，讓 Hibernate 只查那些欄位——**沒有實體、沒有代理、沒有延遲載入，也就沒有 N+1**。而且它避免了「查出整個實體只用兩個欄位」的浪費。**代價是失去了實體的行為與變更追蹤**，所以只適合唯讀場景。**在讀多寫少的系統裡，把讀取路徑改成投影是很划算的**——這也是 CQRS 思路的一個輕量應用。

## 面試回答方式

先給定義與成因（延遲載入加遍歷），並強調**症狀是「資料量少時沒事、一大就慢得離譜」**，所以必須靠工具而非感覺發現——**最可靠的是在測試中斷言查詢次數**。給出四種解法並標出各自定位：`JOIN FETCH` 最直接但一次只能 fetch 一個集合、`@EntityGraph` 宣告式且與方法名推導相容、**批次抓取投資報酬率最高**（不改程式碼、全面生效）、投影最徹底但只適合唯讀。給出核心判斷：**預設延遲載入、需要時明確一起抓**，把 `EAGER` 設在實體上是錯的方向。加分點是 **`JOIN FETCH` 加分頁的陷阱**——Hibernate 無法在資料庫層分頁，會把全部載入記憶體再分頁並印出警告，資料量大時是記憶體災難，解法是先分頁查 ID 再用 `IN` 加 fetch。

## 講稿

N+1 是指查出 N 筆主資料用了一次查詢，然後為每一筆各查一次關聯資料，總共 N 加一次。它幾乎總是由延遲載入造成，查出訂單清單之後遍歷存取關聯物件，每次存取都觸發一次查詢。

最危險的特性是資料量小時看不出來。開發環境十筆測試資料產生十一次查詢，感覺不出差別。生產環境一千筆就是一千零一次查詢。所以它必須靠工具發現，我認為最可靠的是在測試中斷言查詢次數，寫一個測試驗證這個操作應該只產生兩次查詢，回歸的時候立刻發現。

解法有四種。明確要求一起查出來、用註解宣告要抓取的關聯、批次抓取、還有投影。

其中批次抓取的投資報酬率最高。設定一個批次大小之後，Hibernate 會把載入一百個代理合併成一次 IN 查詢。它不需要改任何程式碼，對整個應用全面生效。多數專案應該預設開啟它，然後才針對熱點做精細優化。

還有一個經典陷阱要提。對集合關聯做關聯抓取加分頁的時候，Hibernate 無法在資料庫層面正確分頁，它會把全部資料載入記憶體再分頁。資料量大時這是記憶體災難。

## 常見追問

### 為什麼不乾脆把關聯都設成 EAGER？

**核心答案**：因為 **EAGER 是一個全域決定，而需求是逐查詢的**。設成 EAGER 之後，**每一個查詢這個實體的地方都會拖著關聯資料**——即使那個場景根本不需要。結果是原本簡單的查詢變成多表 join、資料量膨脹、而且**你失去了「不載入」這個選項**（EAGER 無法在單次查詢中被覆寫成 LAZY，反過來則可以）。

**詳細解析**：更糟的是 **EAGER 會傳染**：實體 A EAGER 關聯 B，B 又 EAGER 關聯 C，一次查詢 A 就把整棵圖拉出來。**在複雜的領域模型裡這可能是幾十張表的 join**。而且 EAGER 也**不能解決 N+1**——Hibernate 對 EAGER 的集合關聯在某些查詢路徑（例如 JPQL 查詢而非 `find`）下仍然會產生額外查詢。**所以正確的預設是全部 LAZY，然後在需要的查詢上明確指定要抓什麼。** 這體現了一個通用原則：**預設應該是保守的（少做事），額外的工作由呼叫端按需求要求**——因為呼叫端知道自己需要什麼，而定義端不知道。

**面試回答方式**：核心是「**EAGER 是全域決定而需求是逐查詢的**」，並指出它讓你失去「不載入」的選項（EAGER 無法被覆寫成 LAZY，反之可以）。加分點是 **EAGER 會傳染**（A→B→C 一次拉出整棵圖）以及 **EAGER 也不能解決 N+1**（JPQL 查詢路徑下仍會產生額外查詢）。收在通用原則：**預設應該保守，額外工作由呼叫端按需求要求**，因為呼叫端知道自己需要什麼而定義端不知道。

### 開放式的 session 模式（OSIV）是好是壞？

**核心答案**：`spring.jpa.open-in-view` 預設是 **true**，它讓 Hibernate session 在整個 HTTP 請求期間保持開啟——好處是**在控制器或視圖層存取延遲載入的關聯不會拋 `LazyInitializationException`**。壞處有三個：**資料庫連線被佔用到請求結束**（即使早就不需要了，在高並行下會耗盡連線池）、**N+1 更容易發生且發生在意想不到的地方**（序列化 JSON 時觸發載入）、以及**它掩蓋了設計問題**（讓開發者不必思考「這個查詢該抓什麼」）。

**詳細解析**：**Spring Boot 在啟動時會印出一條 WARN 提醒這個預設值**，因為社群普遍認為它應該預設關閉。**關閉之後的正確做法是：在服務層（有交易的地方）就把需要的資料全部抓好，回傳 DTO 而不是實體。** 這強迫你明確地決定每個使用場景需要什麼資料——**囉嗦一點，但查詢行為變得可預測**。**這是一個典型的「便利 vs 可預測性」的取捨**：OSIV 讓寫的時候輕鬆，代價是執行期的行為難以推理。**在小型應用上它的代價可以接受，在高並行或複雜領域模型上應該關閉。**

**面試回答方式**：給出預設值、好處與三個壞處，特別強調**連線被佔用到請求結束**在高並行下會耗盡連線池、以及**序列化 JSON 時觸發 N+1** 這種意想不到的位置。指出 **Spring Boot 會印 WARN 提醒**因為社群認為它該預設關閉。給出關閉後的正確做法（服務層抓好、回傳 DTO）。收在取捨：**便利 vs 可預測性**，小型應用可接受、高並行或複雜模型應該關閉。

### 什麼時候該放棄 JPA 改用直接 SQL？

**核心答案**：三種情況。**複雜的報表與聚合查詢**——JPQL 的表達力有限，而且結果本來就不是實體；用 JdbcTemplate、jOOQ 或 MyBatis 寫原生 SQL 更清楚也更好調優。**需要資料庫特有功能**——視窗函數、CTE、全文檢索、JSON 操作，這些 JPQL 支援有限。**批次寫入**——JPA 的逐筆持久化在大量資料時效能很差，直接用批次 SQL 或 `COPY` 快幾個數量級。

**詳細解析**：**混用是完全正常的，不必二選一**。JPA 適合「以實體為中心的 CRUD 與領域邏輯」，SQL 適合「以查詢為中心的讀取與批次操作」。**Spring 讓兩者共用同一個 `DataSource` 與交易管理器，所以混用沒有技術障礙**——要注意的是 JPA 的一級快取不知道你用原生 SQL 改了什麼，**混用時可能讀到過期的快取資料**，必要時要 `flush` 或 `clear`。**判斷的方式不是「哪個更好」而是「這段程式碼的中心是實體還是查詢」**。強行用 JPA 表達複雜報表，與強行用 SQL 表達領域邏輯，都是把工具用在不擅長的地方。

**面試回答方式**：給三種情況並各配理由。真正的重點是**混用是正常的、不必二選一**——JPA 適合以實體為中心的 CRUD 與領域邏輯，SQL 適合以查詢為中心的讀取與批次。加分點是提醒**混用時 JPA 的一級快取不知道原生 SQL 改了什麼**，可能讀到過期資料，必要時要 flush 或 clear。收在判準：**不是「哪個更好」而是「這段程式碼的中心是實體還是查詢」**。
