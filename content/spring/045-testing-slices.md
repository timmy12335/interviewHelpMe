# 題目

`@SpringBootTest` 與各種切片測試（`@WebMvcTest`、`@DataJpaTest`）差在哪？為什麼測試會越跑越慢？

## 核心答案

`@SpringBootTest` **載入完整的應用上下文**——所有 bean、所有自動配置。切片測試則**只載入相關的那一層**：`@WebMvcTest` 只載入 MVC 相關的元件（控制器、轉換器、過濾器），不載入服務與資料層；`@DataJpaTest` 只載入 JPA 相關的（實體、Repository、內嵌資料庫），並預設把每個測試包在會回滾的交易裡。

**切片的價值不只是快，更是聚焦**——`@WebMvcTest` 搭配 `@MockitoBean`（舊版 `@MockBean`）模擬服務層，測試就只驗證「HTTP 層的行為」：路由、參數綁定、驗證、序列化、狀態碼。**服務層的邏輯留給純單元測試**，那不需要 Spring 上下文，快上百倍。

測試越跑越慢的主因是**上下文快取被打破**。Spring 會快取應用上下文並在多個測試類別間重用——**快取的鍵是「上下文的配置」**（哪些類別、哪些屬性、哪些 profile、有哪些 mock bean）。**任何一項不同就是一個新的上下文，要重新啟動一次**。一個專案裡如果有二十種不同的配置組合，測試就要啟動二十次上下文。

**所以最有效的測試提速手段，通常是「減少上下文配置的種類」而不是優化單個測試。**

## 詳細解析

**`@MockitoBean` 會打破快取，這是最常見的原因**。每個不同的 mock 組合都產生一個新的上下文鍵——`@MockitoBean OrderService` 與 `@MockitoBean PaymentService` 是兩個不同的上下文。**所以在幾十個測試類別裡零散地 mock 不同的 bean，會產生幾十個上下文。** 緩解方式是**把常用的測試配置抽成少數幾個共用的基底類別或 `@TestConfiguration`**，讓大多數測試共用同一組配置。

**`@DirtiesContext` 應該盡量避免**——它明確標記「這個測試污染了上下文」，導致測試後上下文被銷毀並在下次重建。**一個 `@DirtiesContext` 可能讓整個測試套件多花幾十秒**。需要它通常代表測試修改了共享狀態（改了一個 bean 的內部狀態、改了靜態變數），**更好的做法是讓測試不要污染狀態**，或者在測試的清理階段還原。

**測試的分層應該對應成本**。**純單元測試**（不載入 Spring，直接 `new` 物件並注入 mock）——毫秒級，應該佔絕大多數。**切片測試**——百毫秒級，驗證框架整合的部分。**完整整合測試**——秒級，驗證端到端的關鍵路徑，數量應該很少。**很多專案的問題是「所有測試都是 `@SpringBootTest`」**——因為那樣寫最省事，代價是測試套件從幾秒變成幾分鐘，而慢的測試套件會被跳過，最終等於沒有測試。

**Testcontainers 改變了整合測試的取捨**。以前用內嵌資料庫（H2）做整合測試，快但**行為與生產的資料庫不同**（SQL 方言、鎖行為、型別）——測試通過不代表生產沒問題。Testcontainers 用真實的資料庫映像檔，**行為一致但啟動較慢**。Spring Boot 3.1 的 `@ServiceConnection` 與可重用容器讓這個成本大幅下降，**現在的最佳實務傾向用真實的容器而非內嵌資料庫**。

## 面試回答方式

先給差別（完整上下文 vs 只載入相關層），並強調**切片的價值不只是快、更是聚焦**——`@WebMvcTest` 只驗證 HTTP 層的行為，服務邏輯留給純單元測試。接著解釋測試變慢的主因：**上下文快取的鍵是「配置的組合」，任何一項不同就要重新啟動一次**，所以最有效的提速手段是**減少配置種類**而非優化單個測試。加分點有三個：**`@MockitoBean` 會打破快取**，零散地 mock 不同 bean 會產生幾十個上下文，應該抽成少數共用配置；**`@DirtiesContext` 一個就可能讓套件多花幾十秒**，需要它通常代表測試污染了共享狀態；以及**測試分層應該對應成本**——純單元測試佔絕大多數，「所有測試都是 `@SpringBootTest`」會讓套件從幾秒變幾分鐘，而慢的套件會被跳過等於沒有測試。

## 講稿

完整的那個會載入所有 bean 跟所有自動配置。切片測試只載入相關的那一層，比如只載入 MVC 相關的元件，不載入服務跟資料層。

切片的價值我認為不只是快，更是聚焦。搭配模擬的服務層，測試就只驗證 HTTP 層的行為，路由、參數綁定、驗證、序列化、狀態碼。服務層的邏輯留給純單元測試，那不需要 Spring 上下文，快上百倍。

測試越跑越慢的主因是上下文快取被打破。Spring 會快取應用上下文並在多個測試類別間重用，而快取的鍵是上下文的配置。任何一項不同就是一個新的上下文，要重新啟動一次。

最常見的原因是模擬 bean。每個不同的模擬組合都產生一個新的上下文鍵，所以在幾十個測試類別裡零散地模擬不同的 bean，會產生幾十個上下文。緩解方式是把常用的測試配置抽成少數幾個共用的基底類別。

所以最有效的提速手段通常是減少上下文配置的種類，而不是優化單個測試。

還有一點，測試分層應該對應成本。純單元測試應該佔絕大多數。很多專案的問題是所有測試都用完整上下文，因為那樣寫最省事，代價是套件從幾秒變成幾分鐘，而慢的套件會被跳過，最終等於沒有測試。

## 常見追問

### 怎麼確認上下文快取有沒有生效？

**核心答案**：開啟 `logging.level.org.springframework.test.context.cache=DEBUG`，它會印出**快取的統計**（大小、命中數、未命中數）與每次建立新上下文的原因。看到「未命中數」與測試類別數接近，就代表快取幾乎沒有作用。另一個線索是測試日誌中出現多次 Spring Boot 的啟動橫幅——**每一次都是一個新的上下文**。

**詳細解析**：**診斷之後的改善方向有三個**：把 mock 的組合收斂（用一個共用的 `@TestConfiguration` 提供所有需要的 mock，而不是每個測試類別各自 `@MockitoBean`）、**把測試屬性統一**（`@TestPropertySource` 的不同組合也會產生不同的鍵）、以及**檢查有沒有不必要的 `@DirtiesContext`**。**還有一個容易忽略的點：預設的快取上限是 32 個上下文**（`spring.test.context.cache.maxSize`），超過之後會用 LRU 淘汰——**在配置種類很多的專案裡，這意味著上下文會被反覆建立與銷毀**，而那是最糟的情況。**這個現象只有在看了快取統計之後才會發現。**

**面試回答方式**：給出開啟方式與該看的統計（命中數、未命中數、建立原因），並補上一個直觀線索：**測試日誌出現多次啟動橫幅**。給三個改善方向。加分點是指出**預設快取上限是 32 個上下文**，超過會 LRU 淘汰導致上下文被反覆建立與銷毀——**這只有看了統計才會發現**。

### @MockitoBean 與 Mockito 的 @Mock 差在哪？

**核心答案**：**`@Mock` 只是建立一個 mock 物件**，需要手動注入到被測物件（或用 `@InjectMocks`）；**`@MockitoBean` 是把 mock 放進 Spring 上下文並取代原本的 bean**——所以所有依賴那個 bean 的元件都會拿到 mock。前者不涉及 Spring，適合純單元測試；後者需要 Spring 上下文，適合整合或切片測試。**關鍵差別是 `@MockitoBean` 會影響上下文快取，而 `@Mock` 不會。**

**詳細解析**：**這個差別直接對應了「該用哪種測試」的判斷**。如果被測的是一個純粹的服務類別，**用 `@Mock` 加建構子注入寫純單元測試**——不需要 Spring、毫秒級、也不影響快取。**只有在測試需要框架行為時**（AOP 的交易、快取、安全、或 MVC 的綁定與序列化）才需要 Spring 上下文，那時才用 `@MockitoBean`。**「用建構子注入」讓純單元測試變得容易**，這是偏好建構子注入而非欄位注入的一個實際理由——欄位注入的類別在測試中無法用 `new` 加參數建立，必須靠反射或 Spring。**測試的難易度是設計品質的一個訊號**，這個連結值得指出。

**面試回答方式**：給機制差別（建立 mock vs 取代上下文中的 bean）與關鍵影響（`@MockitoBean` 會打破快取）。真正的加分點是把它連到測試選型：**純服務類別用 `@Mock` 加建構子注入寫純單元測試**，只有需要框架行為（AOP、MVC 綁定）時才用 Spring 上下文。並指出**建構子注入讓純單元測試變容易**，這是偏好它而非欄位注入的實際理由——收在「測試的難易度是設計品質的訊號」。

### Testcontainers 值得引入嗎？

**核心答案**：**在需要驗證資料庫行為的測試上，值得**。用 H2 這類內嵌資料庫的問題是**它與生產資料庫的行為不同**——SQL 方言、索引行為、鎖與隔離級別、型別轉換、以及各種特有功能（PostgreSQL 的 JSONB、視窗函數）。**測試在 H2 上通過但在生產的 PostgreSQL 上失敗，是一個真實且常見的問題。** Testcontainers 用真實的資料庫映像檔，消除了這個落差。

**詳細解析**：**成本主要在啟動時間**，但有幾個緩解方式：**可重用容器**（`testcontainers.reuse.enable=true`，跨測試執行重用同一個容器）、**Spring Boot 3.1 的 `@ServiceConnection`**（自動把容器的連線資訊注入設定，省掉大量樣板）、以及**在整個測試套件共用一個容器**（用 static 欄位而非每個測試類別各起一個）。**這些做法讓啟動成本從「每個測試類別幾十秒」降到「整個套件一次幾十秒」**，那通常是可以接受的。**要注意 CI 環境需要能執行 Docker**，這在某些受限的 CI 上是障礙。**判斷的問題是：這個測試驗證的是「我的程式碼邏輯」還是「我的程式碼與資料庫的互動」？** 前者用 mock 或純單元測試，後者才需要真實的資料庫。

**面試回答方式**：給明確立場（需要驗證資料庫行為時值得）與 H2 的核心問題——**行為與生產資料庫不同**（方言、鎖、型別、特有功能），測試通過但生產失敗是真實常見的問題。給三個降低成本的做法（可重用容器、`@ServiceConnection`、套件共用一個容器）並量化效果。誠實指出 CI 需要能跑 Docker。收在判準：**這個測試驗證的是程式碼邏輯還是程式碼與資料庫的互動**。
