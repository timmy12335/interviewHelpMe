# 題目

`@ControllerAdvice` 怎麼運作？一個 API 的錯誤回應該包含什麼？

## 核心答案

`@ControllerAdvice`（或回傳 JSON 的 `@RestControllerAdvice`）是一個**跨控制器的橫切元件**，裡面的 `@ExceptionHandler` 方法會處理所有控制器拋出的對應例外。它還能承載 `@InitBinder`（自訂綁定行為）與 `@ModelAttribute`（為所有請求加入共用的模型資料）。可以用 `basePackages`、`assignableTypes`、`annotations` 限制作用範圍。

方法的匹配是依例外型別的最近繼承關係——處理 `RuntimeException` 的方法會接住所有沒有更精確處理器的執行期例外。**多個 `@ControllerAdvice` 之間用 `@Order` 決定順序**，這在有多層（框架層、應用層）處理器時很重要。

錯誤回應應該包含四項：**穩定的錯誤代碼**（機器可讀，不隨文案改變）、**人可讀的訊息**（給開發者除錯，不一定給終端使用者看）、**欄位層級的細節**（驗證失敗時哪些欄位錯了）、以及**追蹤識別碼**（讓使用者回報問題時能對應到日誌）。Spring 6 內建了 **RFC 7807 Problem Details** 的支援，提供一個標準的結構。

最重要的原則是：不要洩漏內部資訊——堆疊追蹤、SQL 語句、內部類別名、以及框架的預設錯誤訊息都不該出現在回應裡。

## 詳細解析

「穩定的錯誤代碼」是最常被省略但最有價值的一項。呼叫方（尤其是前端與其他服務）需要依錯誤類型做不同處理——重試、顯示特定提示、還是引導使用者去別的流程。**依訊息文字判斷是脆弱的**（文案一改就壞、國際化後更是無解），依 HTTP 狀態碼又太粗（同樣是 400，可能是格式錯誤、業務規則不符、或額度不足）。一個穩定的字串代碼（`ORDER_ALREADY_PAID`）讓呼叫方可以可靠地分支，而且它在日誌與監控中也是很好的分群依據。

追蹤識別碼把使用者回報與日誌連起來。使用者說「我剛剛下單失敗了」時，有沒有一個 ID 決定了排查是幾分鐘還是幾小時。做法是把當前的 trace ID 放進錯誤回應，並確保日誌中也有它。這幾乎沒有成本，但很多 API 沒有做。

**例外處理器的粒度需要設計**。太粗（只有一個 `handle(Exception e)`）會讓所有錯誤變成同一種回應，失去了區分的價值；太細（每個業務例外一個方法）則產生大量重複的樣板。務實的做法是定義少數幾個「錯誤類別」的基底例外（找不到、衝突、權限不足、外部依賴失敗、內部錯誤），各自對應一種 HTTP 狀態與處理方式，具體的業務例外繼承它們。這正好對應了前面在 Java 例外設計裡說的「依處理方式分類而非依成因分類」。

未預期例外的處理要特別小心。落到 `handle(Exception e)` 的例外代表**有一個沒被預期的情況**——這時應該：回傳一個泛用的 500 錯誤（不洩漏細節）、**以 ERROR 級別記錄完整堆疊**、並確保它會觸發告警。「靜默地把所有例外轉成漂亮的錯誤訊息」是一個危險的反模式——它讓系統看起來運作正常，實際上錯誤從未被人看到。

## 面試回答方式

先給 `@ControllerAdvice` 的機制（跨控制器的橫切元件、依例外型別最近繼承匹配、可用 `@Order` 排序多個 advice）。錯誤回應的**四項內容**要說清楚，並把**穩定的錯誤代碼**單獨強調——依訊息文字判斷脆弱、依 HTTP 狀態碼太粗，一個穩定的字串代碼讓呼叫方能可靠分支，也是日誌與監控的分群依據。加分點有三個：**追蹤識別碼**幾乎沒成本卻決定了排查是幾分鐘還是幾小時；**處理器的粒度**應該定義少數幾個「錯誤類別」的基底例外（找不到、衝突、權限、外部失敗、內部錯誤）讓業務例外繼承，這對應「依處理方式分類而非依成因分類」；以及未預期例外要記完整堆疊並觸發告警，「靜默地把所有例外轉成漂亮訊息」是危險的反模式——系統看起來正常但錯誤從未被人看到。

## 講稿

它是一個跨控制器的橫切元件，裡面的處理方法會接住所有控制器拋出的對應例外。匹配是依例外型別的最近繼承關係，所以處理執行期例外的方法會接住所有沒有更精確處理器的。多個之間可以用順序註解決定優先權。

錯誤回應我認為該包含四項。穩定的錯誤代碼、人可讀的訊息、欄位層級的細節、還有追蹤識別碼。

穩定的錯誤代碼是最常被省略但最有價值的。呼叫方需要依錯誤類型做不同處理，而依訊息文字判斷很脆弱，文案一改就壞掉，國際化之後更是無解。依 HTTP 狀態碼又太粗，同樣是 400 可能是格式錯誤、業務規則不符、或額度不足。

追蹤識別碼則是把使用者回報跟日誌連起來。使用者說我剛剛下單失敗了，有沒有一個 ID 決定了排查是幾分鐘還是幾小時。這幾乎沒有成本，但很多 API 沒有做。

最後我想點名一個危險的反模式，就是靜默地把所有例外轉成漂亮的錯誤訊息。落到通用處理器的例外代表有一個沒被預期的情況，應該記完整堆疊並觸發告警。不然系統看起來運作正常，實際上錯誤從來沒有被人看到。

## 常見追問

### 為什麼有些例外沒有被 @ControllerAdvice 接住？

**核心答案**：因為它只能接住控制器方法執行過程中拋出的例外。發生在更早或更晚的錯誤不會經過它：**過濾器（Filter）中拋出的例外**（Filter 在 DispatcherServlet 之前，Spring MVC 的例外處理還沒開始）、**Spring Security 的認證與授權失敗**（在過濾器鏈裡處理，有自己的 `AuthenticationEntryPoint` 與 `AccessDeniedHandler`）、回應已經開始寫出之後的錯誤（無法再改變狀態碼）、以及非同步處理中在另一個執行緒拋出的例外。

**詳細解析**：過濾器的例外是最常見的困惑來源。一個自訂的 JWT 解析過濾器拋出例外時，使用者看到的是容器的預設錯誤頁而不是你精心設計的 JSON 錯誤——因為那時候還沒進到 Spring MVC。**解法有兩個**：在過濾器裡自己捕捉並直接寫出回應（要自己序列化 JSON），或者把例外儲存到請求屬性中、放行到一個專門的錯誤處理端點。**Spring Security 的做法是後者的變形**——它提供了 `AuthenticationEntryPoint` 與 `AccessDeniedHandler` 兩個擴充點讓你自訂認證失敗與授權失敗的回應。要讓錯誤格式在整個應用中一致，這兩個地方必須各自配置成與 `@ControllerAdvice` 相同的格式，這一步很常被漏掉，結果是同一個 API 有兩種錯誤格式。

**面試回答方式**：給出根本界線——只能接住控制器方法執行中的例外，並列出四種不會經過它的情況。重點展開**過濾器的例外**：使用者看到容器預設錯誤頁而非你設計的 JSON，並給兩個解法。真正的加分點是指出 Spring Security 的 `AuthenticationEntryPoint` 與 `AccessDeniedHandler` 必須各自配置成相同格式，這一步常被漏掉，結果是同一個 API 有兩種錯誤格式。

### 錯誤回應該不該包含堆疊追蹤？

**核心答案**：**生產環境絕對不該**。堆疊追蹤會洩漏內部套件結構、使用的框架與版本、以及程式碼路徑——這些都是攻擊者用來尋找已知漏洞的資訊。而且它對呼叫方沒有任何價值（他們無法依它做任何處理）。開發環境可以開啟以方便除錯，但**必須用設定控制且預設關閉**，避免忘記在部署時關掉。

**詳細解析**：**Spring Boot 的預設行為值得檢查**：`server.error.include-stacktrace` 預設是 `never`（較新的版本），但 `include-message` 與 `include-binding-errors` 的預設在不同版本有變化。依賴預設值是有風險的，應該明確設定。 另外要注意錯誤訊息本身也可能洩漏資訊——「使用者不存在」與「密碼錯誤」的區別能讓攻擊者列舉有效帳號，所以登入失敗應該一律回傳同樣的訊息。「錯誤訊息的資訊量」是一個需要刻意設計的安全維度：對合法使用者要夠有幫助，對攻擊者要夠沒有用，而這兩個目標常常衝突——折衷方式是回應中只給穩定代碼與泛用訊息，詳細資訊留在日誌裡並用追蹤 ID 關聯。

**面試回答方式**：給明確立場（生產絕對不該）與理由（洩漏套件結構、框架版本、程式碼路徑供攻擊者尋找已知漏洞；對呼叫方沒有價值）。加分點是指出應該明確設定而非依賴預設值（預設在不同版本有變化），以及**錯誤訊息本身也會洩漏資訊**（「使用者不存在」與「密碼錯誤」的區別能讓攻擊者列舉帳號）。收在折衷方式：回應只給穩定代碼與泛用訊息，詳細資訊留在日誌並用追蹤 ID 關聯。

### 錯誤處理與可觀測性怎麼配合？

**核心答案**：三件事。**分類記錄**——預期內的業務錯誤（找不到、驗證失敗）用 WARN 或 INFO，未預期的錯誤用 ERROR，讓 ERROR 級別的告警不會被業務錯誤淹沒。**指標化**——依錯誤代碼或錯誤類別打點（`http.server.requests` 的 `outcome` 與 `status` 標籤，或自訂的錯誤計數器），讓錯誤率能被監控與告警。**關聯追蹤**——錯誤日誌與回應中都帶追蹤 ID。

**詳細解析**：「不要讓預期內的錯誤產生 ERROR 日誌」是一條很實用的紀律。一個 API 每天有幾千次 404（使用者查詢不存在的資源）是完全正常的，如果它們都記成 ERROR，告警規則就必須把閾值調高到失去意義的程度，或者乾脆被關掉——而那才是真正的損失。日誌級別應該表達「這需不需要人來看」而不是「這是不是錯誤」。 同樣的道理適用於指標：把預期內的業務失敗與系統故障分開計數，才能對後者設有意義的告警。這個「區分預期與非預期」的思路，是可觀測性設計中最重要的一條原則之一。

**面試回答方式**：給三件事（分類記錄、指標化、關聯追蹤）。重點展開紀律：不要讓預期內的錯誤產生 ERROR 日誌——每天幾千次 404 是正常的，全記成 ERROR 會讓告警閾值失去意義或乾脆被關掉。給出關鍵原則：日誌級別應該表達「這需不需要人來看」而不是「這是不是錯誤」。收在一般化：區分預期與非預期是可觀測性設計中最重要的原則之一。
