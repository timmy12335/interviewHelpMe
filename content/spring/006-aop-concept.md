# 題目

什麼是 AOP？它解決什麼問題？Spring AOP 的底層是怎麼實現的？

## 核心答案

AOP（Aspect-Oriented Programming，面向切面程式設計）是一種把「橫切關注點（cross-cutting concerns）」——那些散落在多個模組中、和核心業務無關但又必須處理的通用邏輯（如日誌、交易、權限、快取）——從業務程式碼中抽離出來、集中管理的程式設計思想。它解決的是「橫切邏輯散落各處、重複、和業務耦合」的問題。Spring AOP 的底層是「動態代理（Dynamic Proxy）」——透過 JDK 動態代理（目標有介面）或 CGLIB（目標無介面）在執行期生成代理物件，在目標方法前後織入橫切邏輯。

## 詳細解析

**AOP 解決的問題**：像日誌、交易、權限檢查這類邏輯，它們「橫切」很多業務方法——幾乎每個 Service 方法都要記日誌、開交易、檢查權限。如果把這些邏輯直接寫在每個業務方法裡，會導致——大量重複程式碼、業務邏輯被這些非業務程式碼淹沒、修改通用邏輯要改很多地方。AOP 把這些橫切邏輯抽成「切面」，宣告式地「織入」到目標方法，讓業務程式碼保持乾淨、通用邏輯集中維護。

**AOP 的核心概念**：

- **切面（Aspect）**：橫切關注點的模組化（如「交易切面」），包含切入點和通知。
- **連接點（Join Point）**：程式執行中可以織入切面的點（Spring AOP 中就是方法呼叫）。
- **切入點（Pointcut）**：定義「哪些連接點」要被織入（用表達式匹配，如「所有 Service 的方法」）。
- **通知（Advice）**：在切入點「做什麼」以及「何時做」（前置、後置、環繞等，見 [[007-aop-advice-types.md]]）。
- **織入（Weaving）**：把切面應用到目標物件、生成代理的過程。

**Spring AOP 的底層——動態代理**：

- Spring AOP 是「執行期」的動態代理（不是編譯期或載入期織入）。
- 如果目標類別實作了介面，預設用「JDK 動態代理」（生成一個實作相同介面的代理）；如果沒有介面，用「CGLIB」（生成目標類別的子類別作為代理）。（Spring Boot 2.x 起預設都用 CGLIB。）
- 代理攔截目標方法的呼叫，在方法前後執行通知邏輯，再呼叫真正的目標方法。詳見 Java 核心的 [[../java/014-dynamic-proxy-jdk-vs-cglib.md]]。

## 面試回答方式

先講「AOP 解決什麼問題」——橫切關注點（日誌、交易、權限）散落各處、重複、和業務耦合，AOP 把它們抽離集中。這個「為什麼需要 AOP」是理解的基礎。接著講核心概念（切面、切入點、通知、織入），但不用死背術語，能說清楚「切入點定義在哪織入、通知定義做什麼」即可。底層實作要點出「Spring AOP 是執行期動態代理（JDK 代理 or CGLIB）」，並能連結到動態代理題。能舉一個具體的橫切例子（如交易）說明 AOP 的價值，展現你理解 AOP 不只是概念而是解決真實問題的工具。

## 常見追問

### Spring AOP 和 AspectJ 有什麼區別？

**核心答案**：主要區別在「織入時機和能力」——Spring AOP 是「執行期」的動態代理織入（在 Bean 建立時生成代理），實現簡單、無需特殊編譯器，但只能代理「Spring 容器管理的 Bean 的方法呼叫」、且有自我呼叫失效等限制；AspectJ 是更強大、更底層的 AOP 框架，支援「編譯期織入（CTW）」和「載入期織入（LTW）」，直接修改目標類別的位元組碼（Bytecode），能織入任何方法（包括 final、private、建構子、欄位存取、非 Spring 管理的物件），功能完整但配置更複雜。Spring AOP 適合大多數常見場景（且 Spring AOP 借用了 AspectJ 的註解和切入點表達式語法），需要更強能力時才用 AspectJ 的織入。

**詳細解析**：這是一個容易混淆的點——Spring AOP「使用了 AspectJ 的註解」（如 `@Aspect`、`@Before`、切入點表達式），但它的「織入機制」不是 AspectJ 的，而是自己的動態代理。所以說「Spring AOP 用了 AspectJ 的語法、但用自己的代理實現」。兩者的能力差異源於織入時機——Spring AOP 在執行期用代理「從外面包一層」，所以只能攔截「透過代理的方法呼叫」，這帶來限制（見自我呼叫失效題）：無法攔截同類別內部的方法呼叫（self-invocation）、無法代理 final 類別/方法、只能作用於 Spring 管理的 Bean。AspectJ 的編譯期/載入期織入是「直接改目標類別的位元組碼」，把切面邏輯真正嵌進去，所以沒有這些限制——能織入任何方法、任何物件、任何連接點（甚至欄位讀寫）。實務上——絕大多數業務場景（給 Service 方法加交易、日誌）Spring AOP 足夠，且更輕量；只有需要突破 Spring AOP 限制（如攔截 self-invocation、代理非 Spring 物件）時才引入 AspectJ 的織入。理解「Spring AOP 借用 AspectJ 語法但用自己的代理、兩者織入機制和能力不同」，展現你對 AOP 實現有清晰的區分。

**面試回答方式**：講出核心區別——「Spring AOP 執行期動態代理（簡單、但有 self-invocation/final 等限制、只作用於 Spring Bean）、AspectJ 編譯期/載入期織入位元組碼（強大、能織入任何方法但複雜）」。務必澄清「Spring AOP 借用了 AspectJ 的註解和切入點語法、但織入機制是自己的代理」這個容易混淆的點，展現你對兩者關係的精確理解。

### Spring AOP 中，一個類別內部方法 A 呼叫方法 B（B 有 AOP），B 的增強會生效嗎？

**核心答案**：不會生效。這是 Spring AOP 著名的「自我呼叫（self-invocation）」失效問題——因為 AOP 增強靠代理物件攔截「外部進來的呼叫」，而類別內部 `A` 呼叫 `B` 用的是 `this.B()``this` 是原始的目標物件（不是代理物件），這個呼叫直接落在真實物件上、完全繞過了代理，所以 B 上的 AOP 增強（如 `@Transactional`、`@Cacheable`）不會被觸發。

**詳細解析**：這個坑的根源是「AOP 增強邏輯住在代理物件裡，而自我呼叫用的是原始物件」。詳細機制見 Java 核心的 [[../java/014-dynamic-proxy-jdk-vs-cglib.md]]。具體場景——外部呼叫 `service.A()` 時走的是代理，代理攔截後呼叫真實物件的 A；A 內部執行 `this.B()` 時，這個 this 就是真實物件本身（代理在呼叫真實物件的 A 時，A 裡的 this 指向真實物件而非代理），於是 B 的呼叫直接在真實物件上執行，沒經過代理的攔截，B 的 `@Transactional` 就不會開啟交易、`@Cacheable` 就不會走快取。這在實務中非常容易踩——例如你以為給某個方法加了 `@Transactional` 就有交易，但如果它是被同類別的另一個方法內部呼叫的，交易根本沒生效（而且不報錯，是靜默失效，很難發現）。解法包括——把 B 抽到另一個 Bean（讓呼叫經過代理）、透過 `AopContext.currentProxy()` 拿到代理再呼叫、或注入自己的代理引用（自注入）。理解這個坑及其解法，是 Spring AOP 實戰中極重要的知識。

**面試回答方式**：明確回答「不會生效」，並講清原因——「自我呼叫用 this（原始物件）、繞過了代理、所以 B 的增強失效」。舉出具體後果「@Transactional/@Cacheable 靜默失效、不報錯很難發現」，並給出解法（抽到另一個 Bean、AopContext.currentProxy、自注入）。能主動點出這個高頻實戰坑，展現你有真實的 Spring AOP 使用經驗。

### 為什麼 Spring Boot 2.x 之後預設用 CGLIB 而不是 JDK 動態代理？

**核心答案**：Spring Boot 2.x 起把 AOP 的預設代理方式設為 CGLIB（`spring.aop.proxy-target-class=true`），主要是為了「減少困惑和避免一類問題」——JDK 動態代理只能代理介面中定義的方法、且注入時必須用介面型別接收（不能用實作類別型別接收，否則會拋轉型異常，因為 JDK 代理生成的是實作介面的物件、不是實作類別的子類別）。這對開發者是個容易踩的坑。改用 CGLIB（生成目標類別的子類別作為代理）後，代理是目標類別的子類別，可以用「介面型別」或「實作類別型別」接收，更符合直覺、減少了「用實作類別型別注入導致轉型異常」這類困惑。

**詳細解析**：這個預設值的改變是 Spring 團隊為了「開發者體驗」做的權衡。JDK 動態代理的一個容易踩的坑是——如果一個 Bean 被 JDK 代理，那麼它的代理是「實作了同樣介面的物件」，但這個代理和原始實作類別「不是同一種型別」（代理不是 `XxxServiceImpl` 的子類別）。所以如果你用實作類別型別去注入（`@Autowired XxxServiceImpl service`），會失敗——因為容器裡放的是代理（實作了介面但不是 XxxServiceImpl），無法賦值給 XxxServiceImpl 型別的欄位（轉型失敗）。這讓一些開發者困惑「明明有這個 Bean 為什麼注入不了」。CGLIB 因為生成的代理是「目標類別的子類別」，既是介面型別、也是實作類別型別，所以不管你用介面還是實作類別型別注入都能成功。Spring Boot 為了讓「注入行為更符合直覺、減少這類困惑」，預設改用 CGLIB。代價是 CGLIB 有它自己的限制（不能代理 final 類別/方法）、且生成子類別的開銷略大於 JDK 代理，但這些在多數場景不是問題。理解這個預設值變化的動機，展現你了解 Spring 的演進以及背後對開發者體驗的考量。

**面試回答方式**：講出「Spring Boot 2.x 預設 CGLIB 是為了避免 JDK 代理的一個坑——JDK 代理生成的是實作介面的物件、不是實作類別的子類別、所以用實作類別型別注入會轉型失敗、讓人困惑」。說明 CGLIB 的代理是子類別、介面和實作類別型別都能注入、更符合直覺。能點出這是「為開發者體驗做的權衡」，展現你理解這個演進的動機。
