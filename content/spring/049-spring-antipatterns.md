# 題目

你在 Spring 專案裡看過哪些反模式？各自的代價是什麼？

## 核心答案

六個最常見的。**欄位注入**（`@Autowired` 直接標在欄位上）——無法用 `new` 建立物件所以難以寫純單元測試、隱藏了依賴數量（一個有十五個 `@Autowired` 欄位的類別，職責顯然過多，但用建構子注入時十五個參數會刺眼得多）、也無法宣告 `final`。

**貧血的服務層加萬能的 Service 類別**——所有邏輯堆在 `XxxService` 裡，領域物件只有 getter 與 setter。結果是幾千行的服務類別、大量重複的邏輯、以及難以測試的糾纏。

**在控制器裡寫業務邏輯**——業務規則被綁在 HTTP 這一個入口上，訊息佇列或定時任務要用同樣的邏輯時只能複製。

**過度使用 `@Transactional`**——標在所有服務方法上（包含唯讀查詢），拉長交易時間、佔用連線；更糟的是**在交易裡呼叫外部 API**，讓遠端的延遲直接變成資料庫鎖的持有時間。

**用例外做流程控制**——業務的正常分支拋例外，成本高且讓程式碼難以推理。

**設定散落**——`@Value` 散布各處而非集中在 `@ConfigurationProperties`。

## 詳細解析

**欄位注入的問題值得展開，因為它是最普遍的一個**。除了測試困難，它最大的代價是**隱藏了設計問題**：建構子注入時，一個類別需要八個依賴會產生一個八參數的建構子，那個醜陋本身就是一個訊號——**「這個類別做太多事了」**。欄位注入把這個訊號藏起來了，於是類別可以無聲地長到十五個依賴。**好的設計工具應該讓壞的設計看起來很醜**，而欄位注入正好相反。

**「在交易裡呼叫外部 API」是危害最具體的一個**。交易期間資料庫連線被佔用、相關的列被鎖住；如果那個外部 API 平常 50 毫秒但偶爾 5 秒，**那 5 秒內鎖一直握著**，其他請求排隊，連線池耗盡，最後整個服務癱瘓——**一個外部依賴的抖動被放大成資料庫層面的故障**。正確做法是把外部呼叫移到交易之外，或者用「先在交易裡寫入待處理記錄、提交後再呼叫」的模式（Outbox）。

**過度使用 `@Transactional` 還有一個隱性成本**：它讓「哪些操作真的需要交易」變得不明顯。**當所有方法都標了它，這個註解就不再傳遞任何資訊。** 更好的做法是只在真正需要原子性的地方標註（涉及多次寫入的操作），唯讀查詢用 `@Transactional(readOnly = true)` 或根本不標。

**這些反模式有一個共同的根源：它們都讓「省事」勝過了「表達意圖」。** 欄位注入省了寫建構子、萬能 Service 省了設計領域模型、控制器寫邏輯省了分層、到處標交易省了思考。**每一次省事的代價都是把一個決定推遲給後來的維護者，而那時候上下文已經丟失了。** 這是判斷反模式的一個通用標準：**它現在讓誰輕鬆、之後讓誰困難？**

## 面試回答方式

先列出六個反模式並各給一句代價。展開**欄位注入**——除了測試困難，它最大的問題是**隱藏了設計訊號**：建構子注入時八個依賴會產生醜陋的八參數建構子，而那個醜陋本身就在說「這個類別做太多事」，**好的設計工具應該讓壞的設計看起來很醜**。再展開**在交易裡呼叫外部 API**：外部服務偶爾 5 秒時鎖握著 5 秒，其他請求排隊、連線池耗盡，**一個外部依賴的抖動被放大成資料庫故障**，正確做法是移出交易或用 Outbox 模式。加分點是指出**過度標註 `@Transactional` 讓這個註解不再傳遞任何資訊**。收在共同根源：**它們都讓「省事」勝過「表達意圖」，而每次省事的代價是把決定推遲給後來的維護者**——判斷反模式的通用標準是「它現在讓誰輕鬆、之後讓誰困難」。

## 講稿

我會列六個。欄位注入、貧血服務層加萬能的 Service 類別、在控制器裡寫業務邏輯、過度使用交易註解、用例外做流程控制、還有設定散落各處。

欄位注入最普遍，值得展開。除了難以寫純單元測試，它最大的代價是隱藏了設計問題。用建構子注入的話，一個類別需要八個依賴會產生一個八參數的建構子，那個醜陋本身就是訊號，說這個類別做太多事了。欄位注入把這個訊號藏起來，於是類別可以無聲地長到十五個依賴。我認為好的設計工具應該讓壞的設計看起來很醜。

危害最具體的是在交易裡呼叫外部 API。交易期間連線被佔用、相關的列被鎖住。如果那個 API 平常五十毫秒但偶爾五秒，那五秒內鎖一直握著，其他請求排隊、連線池耗盡，整個服務癱瘓。一個外部依賴的抖動被放大成資料庫層面的故障。

這些反模式有一個共同的根源，它們都讓省事勝過了表達意圖。每一次省事的代價都是把一個決定推遲給後來的維護者，而那時候上下文已經丟失了。所以我判斷反模式的標準是，它現在讓誰輕鬆、之後讓誰困難。

## 常見追問

### 為什麼建構子注入比欄位注入好？

**核心答案**：四個具體理由。**可測試**——可以直接 `new` 出物件並傳入 mock，不需要 Spring 上下文或反射。**不可變**——依賴可以宣告成 `final`，保證建立後不被替換。**顯式**——依賴的數量與型別寫在簽章上，過多時立刻可見。**啟動時就能發現循環依賴**——建構子注入的循環依賴會直接讓應用啟動失敗（**這是好事**），欄位注入則會被三級快取「解決」而讓問題留到執行期。

**詳細解析**：**最後一項很有意思**：Spring 的三級快取能解決欄位或 setter 注入的循環依賴，**但那是在掩蓋一個設計問題**——兩個類別互相依賴通常代表職責劃分有誤，或者應該抽出第三個元件。**Spring Boot 2.6 之後預設禁止循環依賴**（`spring.main.allow-circular-references` 預設 false），正是因為社群認為「能解決」不代表「應該解決」。**這是一個很好的例子說明「框架的能力與好的設計不總是一致」**——框架提供某個能力不代表你該用它，而框架後來把預設值改成禁止，等於承認了這一點。

**面試回答方式**：給四個理由（可測試、不可變、顯式、啟動時發現循環依賴）。真正的加分點是展開最後一項：**三級快取能解決循環依賴但那是在掩蓋設計問題**，而 **Spring Boot 2.6 之後預設禁止循環依賴**，正是因為「能解決」不代表「應該解決」。收在觀點：**框架的能力與好的設計不總是一致**，而框架後來改了預設值等於承認了這一點。

### 什麼是貧血領域模型，它一定是壞的嗎？

**核心答案**：貧血領域模型是指**領域物件只有資料（getter/setter）而沒有行為**，所有邏輯放在服務層。它**不一定是壞的**——判斷取決於系統的複雜度。**簡單的 CRUD 應用用貧血模型完全合理**：業務邏輯本來就少，強行放進實體只是增加間接。**問題出現在複雜的業務規則上**——當一個訂單的狀態轉移規則、金額計算規則、折扣規則全部散在幾個服務類別裡時，它們就無法被一起理解與維護。

**詳細解析**：**判斷的訊號是「同一條規則出現在多個地方」**。如果「訂單只有在 PENDING 狀態才能取消」這條規則寫在三個服務方法裡，那它應該屬於訂單物件本身（`order.cancel()` 內部檢查狀態）。**把規則放進領域物件的價值在於：它變成一個入口，所有想取消訂單的路徑都必須經過它，規則因此不可能被繞過。** 相反地，如果規則只有一個使用點且很簡單，放在服務裡完全沒問題。**所以正確的問題不是「該不該用領域模型」而是「這條規則有沒有多個入口、會不會被繞過」**——這比抽象地爭論貧血與充血有用得多。

**面試回答方式**：先給定義並明確表態**不一定是壞的**——簡單 CRUD 用它完全合理，問題出現在複雜業務規則上。給出判斷訊號：**同一條規則出現在多個地方**。說明把規則放進領域物件的價值：**它變成唯一入口，所有路徑都必須經過，規則不可能被繞過**。收在問題的重新表述：**不是「該不該用領域模型」而是「這條規則有沒有多個入口、會不會被繞過」**。

### 怎麼在既有專案裡逐步改善這些問題？

**核心答案**：**不要大重構，用「碰到就改」的策略**。具體做法是：**新程式碼一律用好的做法**（建構子注入、DTO、明確的交易邊界）、**修改既有程式碼時順便改善那一部分**（改一個方法時把那個類別的欄位注入換成建構子注入）、以及**用工具擋住退化**（靜態分析規則禁止欄位注入、ArchUnit 測試強制分層）。

**詳細解析**：**「用工具擋住退化」是最關鍵的一步**，因為沒有它的話，改善的速度趕不上新增的速度。**ArchUnit 這類架構測試可以把架構約束寫成測試**——「控制器不能直接依賴 Repository」「領域層不能依賴 Spring 的註解」「所有服務方法的交易邊界必須明確」。**這讓架構決策從「文件與口頭約定」變成「會失敗的測試」**，而後者才真正有效。**引入時的做法是先允許既有的違規**（大多數工具支援凍結現狀的基準檔），只擋住新的——這樣不需要一次修完所有問題就能開始受益。**「凍結現狀、只擋新增」是所有技術債治理中最實用的一個模式**，它把一個看起來不可能的大工程變成可以立刻開始的小步驟。

**面試回答方式**：給「碰到就改」的三步策略。重點強調**「用工具擋住退化」最關鍵**——沒有它改善速度趕不上新增速度。展開 ArchUnit 的價值：**把架構約束寫成會失敗的測試**，讓架構決策從文件與口頭約定變成強制。真正的加分點是引入方式：**先凍結現狀只擋新增**，不需要一次修完就能開始受益，並指出這是**技術債治理中最實用的模式**——把不可能的大工程變成可以立刻開始的小步驟。
