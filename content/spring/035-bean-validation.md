# 題目

`@Valid` 與 `@Validated` 差在哪？什麼時候需要分組驗證？

## 核心答案

`@Valid` 是 **Jakarta Bean Validation 規範的註解**，標註在方法參數上觸發對該物件的驗證，也可以標註在欄位上做**巢狀驗證**（驗證集合中的每個元素或關聯物件）。`@Validated` 是 **Spring 自己的註解**，它多了兩個能力：**支援驗證分組**（可以指定 `@Validated(Create.class)`）、以及在類別上標註時啟用方法級別的驗證（透過 AOP 代理驗證任意 Spring bean 的方法參數與回傳值，不限於控制器）。

分組驗證解決的是「同一個物件在不同情境下的驗證規則不同」。最典型的是建立與更新：建立時 `id` 必須為 null、更新時 `id` 必須存在；建立時密碼必填、更新時可以不改。用兩個 DTO 也能解決，而且通常更清楚——分組的價值在於欄位重疊度很高、只有少數規則不同的情況。

實務上的預設選擇是：**控制器參數用 `@Valid`**（簡單、符合規範）、需要分組或要在服務層驗證時用 `@Validated`。

## 詳細解析

方法級驗證是 `@Validated` 最實用但最少被用的能力。在一個 `@Service` 類別上加 `@Validated`，就可以在它的方法參數上用 `@NotNull`、`@Min` 等註解，違規時拋 `ConstraintViolationException`。這讓「參數前置條件」變成宣告式的，取代大量的 `if (x == null) throw ...` 樣板。代價是它透過 AOP 實現，所以同類別內部的方法呼叫不會被驗證——這與 `@Transactional` 的自呼叫問題完全相同。

驗證應該發生在哪一層是一個設計問題。控制器層驗證「輸入格式是否合法」（必填、長度、格式），服務層驗證「業務規則是否滿足」（庫存是否足夠、狀態是否允許轉移）。把業務規則塞進 Bean Validation 註解是常見的過度使用——它們往往需要查詢資料庫或依賴其他物件的狀態，而註解式驗證不適合表達這種邏輯。判準是：驗證需不需要外部資訊？ 不需要（只看這個物件本身）就適合註解，需要就該是服務層的明確檢查。

自訂約束的成本很低但常被忽略。實作 `ConstraintValidator<MyAnnotation, MyType>` 加上一個註解，就能把重複的驗證邏輯（統一編號的檢查碼、密碼強度規則、業務代碼的格式）變成可重用的宣告。它的價值不只是少寫程式碼，更在於錯誤訊息的一致性與可國際化——訊息定義在一處，所有使用點自動一致。

**巢狀驗證需要明確標註**。一個 DTO 裡有 `List<ItemDto> items`，如果不在欄位上加 `@Valid`，清單裡每個元素的約束完全不會被檢查——外層驗證通過但內層的非法資料進入了系統。這是一個沉默的失效，很容易在測試中被漏掉（因為外層的正例測試會通過）。Jakarta Validation 也支援 `List<@NotNull ItemDto>` 這種容器元素的約束語法。

## 面試回答方式

先給兩者的歸屬與能力差別——`@Valid` 是規範註解，`@Validated` 是 Spring 的且多了**分組**與**方法級驗證**兩個能力。給出分組解決的問題（同一物件在不同情境規則不同，典型是建立 vs 更新）並誠實指出**用兩個 DTO 通常更清楚**，分組的價值在欄位重疊度高、只有少數規則不同時。加分點有三個：方法級驗證讓「參數前置條件」變成宣告式的，取代大量 if-throw 樣板，但它透過 AOP 實現所以同類別內部呼叫不會被驗證（與 `@Transactional` 的自呼叫問題相同）；驗證分層的判準是「需不需要外部資訊」——不需要用註解、需要就該是服務層的明確檢查；以及**巢狀驗證不加 `@Valid` 會沉默失效**，外層通過而內層非法資料進入系統，測試很容易漏掉。

## 講稿

一個是規範的註解，標註在參數上觸發驗證，也可以標在欄位上做巢狀驗證。另一個是 Spring 自己的，多了兩個能力，支援驗證分組，還有在類別上標註時啟用方法級別的驗證。

分組驗證解決的是同一個物件在不同情境下規則不同。最典型的是建立跟更新，建立時 ID 必須為空、更新時必須存在。不過我要說，用兩個 DTO 也能解決而且通常更清楚，分組的價值在欄位重疊度很高、只有少數規則不同的情況。

方法級驗證是最實用但最少被用的能力。在服務類別上標註之後，就可以在方法參數上用約束註解，違規時直接拋例外。這讓參數的前置條件變成宣告式的，取代大量的判空拋例外樣板。但它透過 AOP 實現，所以同類別內部的方法呼叫不會被驗證，跟交易註解的自呼叫問題完全一樣。

還有一個很容易漏掉的坑。一個 DTO 裡有一個清單欄位，如果不在那個欄位上加驗證註解，清單裡每個元素的約束完全不會被檢查。外層驗證通過但內層的非法資料進了系統。這是沉默的失效，測試很容易漏掉，因為外層的正例測試會通過。

## 常見追問

### 驗證的錯誤訊息怎麼國際化？

**核心答案**：約束註解的 `message` 屬性支援**訊息鍵**的語法（`{my.constraint.message}`），對應到 `ValidationMessages.properties` 或 Spring 設定的 `MessageSource`。Spring Boot 預設會把 `MessageSource` 接進驗證器，所以可以用 `messages_zh_TW.properties` 這類標準的國際化檔案。訊息裡也可以用 `{min}`、`{max}` 這類佔位符引用約束的屬性值。

**詳細解析**：實務上的難點不在機制而在維護。訊息鍵散落在幾十個 DTO 的註解裡，而翻譯檔在另一個地方——兩者不同步時（新增了約束卻沒加訊息）會直接顯示原始的鍵，看起來像是 bug。緩解方式有兩個：用測試驗證所有訊息鍵都有對應的翻譯（掃描註解、比對 properties 檔），以及為每個約束提供合理的預設訊息（`message = "{app.user.name.notBlank}"` 找不到時退回一個英文預設）。這類「設定與程式碼分離造成的不同步」問題在國際化、設定、以及 API 文件上普遍存在，用自動化檢查比靠紀律可靠。

**面試回答方式**：給出機制（訊息鍵語法、`MessageSource`、佔位符）。真正的加分點是指出**難點在維護而非機制**：訊息鍵與翻譯檔不同步時會直接顯示原始鍵、看起來像 bug。給兩個緩解方式（用測試驗證所有鍵都有翻譯、提供合理預設）。收在一般觀察：設定與程式碼分離造成的不同步問題普遍存在，用自動化檢查比靠紀律可靠。

### 什麼樣的規則不該用 Bean Validation 表達？

**核心答案**：**需要外部資訊的規則**。「使用者名稱不能重複」要查資料庫、「訂單金額不能超過額度」要查帳戶、「狀態轉移是否合法」要看當前狀態——**這些都不該寫成約束註解**。技術上可以做到（在 `ConstraintValidator` 裡注入 Repository），但它有三個問題：**驗證變成有副作用的**（會查資料庫）、錯誤訊息難以表達完整的業務語意、以及同一個檢查在服務層還是要再做一次（因為驗證與實際操作之間有時間差，有競態）。

**詳細解析**：**「唯一性檢查」是最典型的例子**。即使在驗證時查到名稱可用，到實際插入之間仍然可能有另一個請求插入了同名的資料——所以資料庫的唯一約束是不可省略的，而既然有了它，前面那次查詢只是為了提供更好的錯誤訊息（提早告訴使用者），**不是為了保證正確性**。這個區分很重要：驗證是為了「早一點給出好的錯誤訊息」，正確性必須由更底層的機制保證。 誤把驗證當成正確性保證，是分散式與併發場景下許多資料問題的來源。

**面試回答方式**：給明確判準（需要外部資訊的規則）與三個問題（驗證有副作用、訊息難表達業務語意、服務層還是要再做一次）。重點展開**唯一性檢查**：驗證與插入之間有競態，所以資料庫唯一約束不可省略，前面的查詢只是為了更好的錯誤訊息。收在關鍵區分：驗證是為了早一點給出好的錯誤訊息，正確性必須由更底層的機制保證，誤把驗證當成正確性保證是許多併發資料問題的來源。

### 分組驗證與多個 DTO，實務上怎麼選？

**核心答案**：**預設用多個 DTO**。它們更明確（看型別就知道這個端點接受什麼）、更安全（`CreateUserRequest` 裡沒有 `id` 欄位，就不可能被批量賦值）、也更容易演進（更新請求要加欄位不影響建立請求）。分組的適用場景是「欄位幾乎完全相同、只有兩三條規則不同」，此時維護兩個高度重複的 DTO 反而是負擔。

**詳細解析**：**多個 DTO 的代價是映射的樣板**——要寫 DTO 到領域物件的轉換，欄位多時很囉嗦。緩解方式有 MapStruct 這類編譯期生成映射的工具（比反射式的映射器安全且快），或者用 record 讓 DTO 本身很短。但要注意「用映射工具消除樣板」不該變成「所有 DTO 都自動映射到實體」——那等於繞回了批量賦值的問題，映射應該明確列出哪些欄位會被複製。這裡有一個一般的取捨：明確帶來安全與可讀性，但也帶來重複；工具可以消除重複，但要小心不要順便消除了明確性。 好的做法是用工具生成程式碼（可以被閱讀與審查），而不是在執行期做反射式的自動映射。

**面試回答方式**：明確主張**預設用多個 DTO**並給三個理由（更明確、更安全因為欄位不存在就無法被賦值、更容易演進），劃出分組的適用場景（欄位幾乎相同、只有兩三條規則不同）。誠實給出多 DTO 的代價（映射樣板）與緩解（MapStruct、record）。收在取捨：明確帶來安全與可讀但也帶來重複，工具可以消除重複但不要順便消除明確性——用生成程式碼優於執行期反射式自動映射。
