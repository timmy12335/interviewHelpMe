# 題目

Spring 框架中運用了哪些設計模式？舉例說明。

## 核心答案

Spring 大量運用了設計模式，常見的有：**工廠模式**（BeanFactory/ApplicationContext 用工廠模式建立和管理 Bean）、**單例模式**（Bean 預設單例）、**代理模式**（AOP 用動態代理實現）、**模板方法模式**（JdbcTemplate、RestTemplate 等 XxxTemplate，把固定流程封裝、可變部分留給使用者）、**觀察者模式**（事件機制 ApplicationEvent/Listener）、**適配器模式**（HandlerAdapter 適配不同形式的 Controller）、**裝飾器模式**（如各種 Wrapper）、**策略模式**（如多種 ViewResolver、各種可替換的策略介面）等。這些模式的運用讓 Spring 靈活、可擴展、易維護。

## 詳細解析

**主要設計模式及在 Spring 中的體現**：

1. **工廠模式（Factory）**：`BeanFactory`/`ApplicationContext` 本質是工廠——負責建立、管理、提供 Bean，把物件的建立集中封裝。`FactoryBean` 也是（封裝複雜物件的建立）。

2. **單例模式（Singleton）**：Bean 預設是單例作用域，容器保證每個 Bean 在容器中只有一個實例（不過是「容器管理的單例」，和經典的單例模式實現方式不同）。

3. **代理模式（Proxy）**：AOP 的核心——透過 JDK 動態代理或 CGLIB 為 Bean 生成代理，在方法前後織入橫切邏輯（交易、日誌等）。

4. **模板方法模式（Template Method）**：`JdbcTemplate`、`RestTemplate`、`RedisTemplate` 等——把「固定的流程骨架」（如 JDBC 的獲取連線、執行、處理異常、關閉連線）封裝在模板裡，把「可變的部分」（如具體的 SQL、結果處理）透過回呼留給使用者。使用者不用管重複的樣板程式碼。

5. **觀察者模式（Observer）**：事件機制——`ApplicationEventPublisher` 發布事件、`ApplicationListener`/`@EventListener` 監聽事件，發布者和監聽者解耦（見 [[021-spring-events.md]]）。

6. **適配器模式（Adapter）**：`HandlerAdapter` 適配不同形式的 Handler，讓 DispatcherServlet 能統一呼叫（見 [[012-dispatcherservlet-components.md]]）；`AdvisorAdapter` 適配不同的 Advice。

7. **策略模式（Strategy）**：很多可替換的策略——多種 `ViewResolver`、多種 `HandlerMapping`、`PlatformTransactionManager` 的不同實作等，都是「同一介面、可替換的不同策略」。

8. **裝飾器模式（Decorator）**：如 `BeanWrapper`、各種對原始物件增強的 Wrapper。

## 面試回答方式

這題考的是「廣度 + 能舉例」。不用把所有模式都講，挑幾個最有代表性、最能說清楚的重點講——工廠（BeanFactory）、代理（AOP）、模板方法（JdbcTemplate）、觀察者（事件機制）、適配器（HandlerAdapter）。每個模式一定要配「在 Spring 哪裡用到、解決什麼」的具體例子，這是這題的關鍵（光說模式名沒用，要能對應到 Spring 的實際運用）。能講清楚「模板方法在 JdbcTemplate 的應用（封裝固定流程、回呼處理可變部分）」這種有深度的例子，比泛泛列舉更能展現理解。

## 常見追問

### 模板方法模式在 JdbcTemplate 中是怎麼體現的？

**核心答案**：`JdbcTemplate` 用模板方法模式把「JDBC 操作的固定樣板流程」封裝起來——每次做 JDBC 操作都要重複的步驟（獲取資料庫連線、建立 Statement、執行、處理 SQL 異常、關閉 ResultSet/Statement/Connection 釋放資源）被封裝在 JdbcTemplate 的方法裡（這是「固定的流程骨架」），而「每次不同的部分」（具體的 SQL 語句、如何把 ResultSet 對應成物件）透過「回呼介面」（如 `RowMapper`、`PreparedStatementSetter`）留給使用者實現。使用者只需提供 SQL 和結果處理邏輯，不用寫那些重複又容易出錯的資源管理樣板程式碼（尤其是 finally 中關閉資源），JdbcTemplate 保證資源被正確釋放。

**詳細解析**：這是模板方法模式解決「重複樣板 + 可變邏輯」問題的典範。原生 JDBC 的痛點是——每個查詢都要寫一大堆重複的樣板：try 裡獲取連線、建 statement、執行、遍歷 ResultSet，finally 裡一層層關閉資源（且關閉本身還可能拋異常要處理），真正「業務相關」的只有 SQL 和結果對應那幾行，卻被淹沒在樣板裡，而且很容易忘記關閉資源導致連線洩漏。JdbcTemplate 用模板方法把這個固定流程（連線管理、異常處理、資源釋放）封裝成「模板」，把可變部分（SQL、結果對應）抽象成「回呼」——例如 `jdbcTemplate.query(sql, rowMapper)`，你提供 SQL 和一個 RowMapper（告訴它怎麼把一行 ResultSet 轉成物件），JdbcTemplate 負責其餘所有樣板（拿連線、執行、遍歷、每行呼叫你的 rowMapper、關閉資源）。這樣你的程式碼只剩業務邏輯、資源管理由模板保證正確。這正是模板方法「把固定的流程骨架封裝在父類別/模板、把可變的步驟留給子類別/回呼」的思想。理解 JdbcTemplate 的例子，展現你能把設計模式和 Spring 的實際 API 深入連結。

**面試回答方式**：講出「JdbcTemplate 用模板方法封裝 JDBC 的固定樣板（連線管理、異常處理、資源釋放）、把可變部分（SQL、結果對應）透過回呼（RowMapper）留給使用者」。強調它解決的痛點——「原生 JDBC 樣板重複、容易忘記關資源導致洩漏、JdbcTemplate 保證資源正確釋放、使用者只寫業務」。這種能深入一個具體 API 講清模式應用的回答，比列舉模式名有深度得多。

### AOP 用到的代理模式和你知道的其他代理有什麼關係？

**核心答案**：Spring AOP 用的是「動態代理」——在執行期動態生成代理物件（JDK 動態代理或 CGLIB），這是代理模式的一種實現。代理模式的核心思想是「用一個代理物件包裝目標物件、在存取目標的前後插入額外邏輯、控制對目標的存取」。除了 AOP 的動態代理，代理模式還有「靜態代理」（手寫一個代理類別、編譯期就確定）等形式。動態代理相比靜態代理的優勢是——不用為每個目標類別手寫代理（靜態代理要一個個寫），而是執行期動態地為任意類別生成代理，一套代理邏輯（如交易攔截）能作用於所有需要的 Bean，這正是 AOP 能「無侵入地把橫切邏輯應用到大量方法」的基礎。

**詳細解析**：這題把 Spring AOP 的代理和代理模式的通用概念連結起來（也呼應 Java 核心的動態代理題）。代理模式的本質是「中間人」——不直接存取目標物件，而是透過一個代理，代理可以在轉發請求給目標的前後做額外的事（存取控制、延遲載入、記錄日誌、遠端呼叫等）。它有兩種主要形式——「靜態代理」是你手寫一個代理類別（實作和目標相同的介面、內部持有目標、在方法裡加額外邏輯再呼叫目標），編譯期就寫死，缺點是每個要代理的類別都要手寫一個代理、且橫切邏輯散落在各代理裡。「動態代理」是執行期動態生成代理（JDK 用反射生成實作介面的代理、CGLIB 生成子類別），不用手寫、一套增強邏輯（如 InvocationHandler 裡的交易邏輯）能應用於任意類別。Spring AOP 選動態代理，正是因為它要「把交易/日誌等橫切邏輯無侵入地應用到成百上千個 Bean 方法」——如果用靜態代理，要為每個 Bean 手寫代理，完全不現實；動態代理讓一套切面邏輯能被容器自動應用到所有匹配的 Bean。理解動態代理相對靜態代理的優勢，展現你把設計模式、AOP、動態代理串起來理解。

**面試回答方式**：講出「AOP 用動態代理（JDK/CGLIB 執行期生成代理）、是代理模式的一種實現、代理模式核心是用代理包裝目標、在前後插入邏輯」。對比靜態代理（手寫、編譯期、每類一個）和動態代理（執行期動態生成、一套邏輯應用於任意類別）。能點出「動態代理讓 AOP 能無侵入地把橫切邏輯應用到大量 Bean、靜態代理做不到」，展現你理解為什麼 AOP 選動態代理。

### 為什麼說 Spring 本身就是設計模式的「活教材」？

**核心答案**：因為 Spring 作為一個成熟的大型框架，為了實現「靈活、可擴展、可維護、對使用者友好」這些目標，在各個層面都恰當地運用了大量設計模式——而且這些運用都是「為了解決真實問題」而非為用而用。例如用工廠模式集中管理物件建立、用代理模式實現無侵入的 AOP、用模板方法消除重複樣板、用策略模式讓各種組件可替換、用觀察者模式解耦事件的發布和處理。研究 Spring 如何運用這些模式，能學到「設計模式在真實工程中如何恰當地解決問題」，比看教科書上孤立的模式範例更有價值——這也是為什麼很多人透過閱讀 Spring 源碼來學習設計模式的實際應用。

**詳細解析**：這題其實是在考「你是否理解設計模式的本質是解決問題、而 Spring 是很好的學習範本」。設計模式的價值不在於「記住有哪些模式」，而在於「理解每種模式解決什麼問題、在什麼場景用」。Spring 恰恰提供了大量「模式解決真實問題」的範例——它面臨的問題（如何靈活管理海量物件、如何無侵入地加橫切邏輯、如何讓組件可替換、如何消除重複程式碼、如何解耦事件處理）正是設計模式擅長解決的，所以它自然地運用了對應的模式。而且 Spring 的運用往往是「教科書級別」的恰當——例如模板方法用在 JdbcTemplate（消除 JDBC 樣板）就是模板方法最經典的應用場景。所以研究 Spring 源碼是學習「設計模式實戰」的好途徑——你能看到「這個模式在真實框架中為了解決什麼問題、如何被運用」，這比背模式的定義和 UML 圖有價值得多。面試中能表達這個認識，展現你對設計模式的理解是「以解決問題為導向」的成熟視角，而非「會背幾個模式名」。

**面試回答方式**：講出「Spring 為了靈活/可擴展/易維護，在各層面恰當運用了大量模式、且都是為解決真實問題（管理物件用工廠、無侵入 AOP 用代理、消除樣板用模板方法、可替換用策略、解耦事件用觀察者）」。點出「研究 Spring 源碼是學設計模式實戰的好途徑、比教科書孤立範例有價值」。這種「以解決問題為導向理解設計模式」的視角，展現你對設計模式的理解是成熟的。
