# 題目

Spring Boot 3 升級到 4 要注意什麼？它和當年 2 升 3 的難點一樣嗎？

## 核心答案

不一樣，而這個對比本身就是答案的重點。2 升 3 的痛點是**命名空間**——`javax.*` 改成 `jakarta.*`，機械但波及每一個檔案（見 [[025-spring-boot-3-migration.md]]）。3 升 4 的痛點是**依賴結構**：**模組被拆細了，而 Jackson 換了大版本**。

**四個主要斷點**：

**模組拆分**——原本的大 jar 被拆成 `spring-boot-<技術>` 的細模組。沒有透過 starter 而是直接依賴的專案，升上去會發現類別找不到，要自己補上對應的依賴；Flyway、Liquibase 這類現在各自需要專屬的 starter。官方提供 `spring-boot-starter-classic` 當過渡。

**Jackson 3**——groupId 從 `com.fasterxml.jackson` 換成 `tools.jackson`，`@JsonComponent` 改名 `@JacksonComponent`，設定屬性重新分組到 `spring.jackson.json.read` 與 `.write`。Jackson 2 仍以廢棄的形式提供，而 `spring.jackson.use-jackson2-defaults=true` 可以先保留舊的行為。

**移除的東西**——Undertow（與 Servlet 6.1 不相容）、Spock 整合、`@MockBean` 與 `@SpyBean`（改用 `@MockitoBean`、`@MockitoSpyBean`）。

**基線**——Java 17 起跳（官方強烈建議 21 或 25）、Spring Framework 7、Jakarta EE 11 與 Servlet 6.1、Kotlin 2.2、原生映像檔要 GraalVM 25。

## 詳細解析

**升級順序和上一次一樣重要**：先升到最新的 3.5.x 把廢棄警告清乾淨，再動 4。因為 4 移除的正是 3.x 標記為廢棄的那些 API——在 3.5 上修完，等於把大部分的錯誤提前到一個還能編譯的版本上處理。跳過這一步的話，你會同時面對「編譯不過」與「不知道該改成什麼」。

模組拆分的動機是那個 jar 長太大了：`spring-boot-autoconfigure` 在 1.0 時是 182 KB，到 3.5 已經超過 2 MB——裡面裝著 Kafka、MongoDB、Neo4j、LDAP、Flyway 等每一種它支援的技術的自動配置，而你的專案可能只用到其中兩三個。拆細之後只有實際引入的模組會進來，收益是可維護性、容器映像檔的體積、以及 GraalVM 原生映像檔的可達性分析。理解這個動機，就知道為什麼官方願意承擔一次破壞性的重構。

**Jackson 3 的 groupId 變更是最容易漏的一項**：因為它不是 Spring 的類別，編譯錯誤會出現在你自己寫的序列化器或設定類別上，而錯誤訊息不會提示「這是 Jackson 換版了」。掃一遍專案裡所有 `com.fasterxml.jackson` 的匯入，是升級前值得先做的一件事。

**新功能可以晚點再用**：HTTP 介面客戶端（宣告一個 Java 介面就能呼叫 REST 服務）、API 版本控制、OpenTelemetry starter——這些是升上去之後的收益，不該和遷移混在一起做。先讓舊功能在新版本上跑起來，再分批採用新特性，是降低歸因難度的標準做法。

## 面試回答方式

先做對比：2 升 3 難在命名空間、3 升 4 難在依賴結構——這句話就展示了你分得清兩次升級的性質不同。接著給四個斷點（模組拆分、Jackson 3、移除項、基線）。加分點有四個：**先升到 3.5.x 清廢棄警告**，因為 4 移除的正是 3.x 廢棄的那些；模組拆分的動機是原生映像檔與啟動速度；**Jackson 的 groupId 變更最容易漏**，錯誤訊息不會提示是它；以及**遷移與採用新特性要分開做**。

## 講稿

這兩次升級的難點性質不一樣，我覺得這是回答的重點。

二升三痛在命名空間，javax 改成 jakarta，很機械但波及每個檔案。三升四痛在依賴結構。

主要有四個斷點。第一是模組拆分，原本的大 jar 被拆成細模組。沒有透過 starter 而是直接依賴的專案，升上去會發現類別找不到。Flyway 這類現在需要專屬的 starter。

第二是 Jackson 換到三，groupId 從 com.fasterxml 換成 tools.jackson。這一項最容易漏，因為編譯錯誤會出現在你自己寫的序列化器上，訊息不會提示是 Jackson 換版了。

第三是移除的東西，Undertow、Spock 整合、還有 MockBean 改成 MockitoBean。第四是基線，Java 十七起跳但建議二十一或二十五，Spring Framework 七，Jakarta EE 十一。

升級順序跟上次一樣重要。先升到最新的 3.5 把廢棄警告清乾淨再動四，因為四移除的正是三點五標記為廢棄的那些。

## 常見追問

### 模組拆得這麼細，是不是讓依賴管理變麻煩了？

**核心答案**：用 starter 的專案幾乎無感，直接依賴的專案才會痛。starter 的職責就是把一組模組打包起來——所以 `spring-boot-starter-web` 仍然一行搞定。痛的是那些為了「不要拉進不需要的東西」而繞過 starter、直接列出個別依賴的專案，它們現在要自己補齊被拆出去的部分。

**詳細解析**：這考察「抽象層存在的理由要在它改變時才看得出來」——starter 平常看起來只是一組依賴的別名，直到底層重構時你才發現它吸收了這次變更。繞過 starter 直接依賴的做法，在平時省下一點傳遞依賴，在升級時付出全部的代價；這是一個「用一點便利換取未來的耦合」的典型例子。而官方提供 `spring-boot-starter-classic` 讓你先升上去再慢慢拆，正是承認這個成本真實存在。能指出「這次升級懲罰的是繞過抽象層的專案」，比列舉模組名稱有洞察得多。

**面試回答方式**：給明確的區分（**用 starter 幾乎無感、直接依賴才痛**）並說明 starter 吸收了這次變更。核心加分點是點出抽象層的價值要在它改變時才看得出來，以及繞過它是「用一點便利換未來的耦合」。收在觀察：官方提供 classic starter，正是承認這個成本真實存在。

### 該現在就升 4 嗎？

**核心答案**：看你在不在支援期內，而不是看新功能吸引不吸引人。Spring Boot 3.5 已於 2026-06-30 結束支援——還在 3.5 或更舊的版本上就有安全更新的風險，那是升級的實質理由。而如果你在 3.4（仍在支援），可以按自己的節奏規劃；純粹為了 HTTP 介面客戶端這類新特性而升，通常排不進優先順序。

**詳細解析**：這考察「升級的驅動力應該是風險而非功能」（見 [[../behavioral/036-selling-tech-debt-work.md]]）——新功能很難排進優先順序，因為它要和產品需求競爭；而「這個版本不再收到安全修補」是一個管理層無法忽視的論述。所以提案時該給的是支援期的時間表而非特性清單。而更務實的做法是「把版本升級變成常態而非事件」——每個小版本都跟，於是大版本的落差永遠只有一個台階；累積三年不升，那次升級就會變成一個需要專案化的大工程。這個「持續小步升級比一次跳一大步便宜」的判斷，在 Spring 改成短支援週期之後更成立。

**面試回答方式**：給判準（**看支援期而非新功能**）並指出 3.5 已於 2026-06-30 EOL。核心加分點是升級的驅動力應該是風險而非功能——安全修補是管理層無法忽視的論述，而新功能要和產品需求競爭。收在做法：把版本升級變成常態而非事件，累積三年不升會讓它變成需要專案化的大工程。

### Jackson 3 除了改名還有什麼要注意的？

**核心答案**：行為預設值可能變了，而那比改名危險。改名編譯期就會爆，好處理；而序列化行為的差異（日期格式、null 的處理、未知欄位的容忍度）是執行期才顯現的，可能悄悄改變 API 的輸出。官方提供 `spring.jackson.use-jackson2-defaults=true` 先鎖住舊行為，正是為了讓這兩類問題可以分開處理。

**詳細解析**：這考察「編譯期錯誤是好消息，執行期的行為差異才是壞消息」這個升級時的通則——編譯不過會逼你處理，而一個悄悄改變的 JSON 欄位格式可能到下游系統報錯才被發現。所以升級的驗證重點應該放在**「輸出的比對」而非「編譯通過」**：把升級前後同一組請求的回應存下來做差異比對，是成本不高但能抓到這類問題的做法（這正好就是前面提過的特徵測試，見 [[../behavioral/010-taking-over-legacy-system.md]]）。先用相容旗標升上去、確認功能正常、再逐項關掉旗標處理行為差異，把一次大變更拆成兩個可以各自驗證的步驟。

**面試回答方式**：給重點（行為預設值的變化比改名危險）並說明為什麼（編譯期 vs 執行期）。核心加分點是通則：編譯期錯誤是好消息，執行期的行為差異才是壞消息，於是驗證重點該放在輸出的比對而非編譯通過。收在做法：先用相容旗標升上去、確認正常、再逐項關掉，把一次大變更拆成兩個可各自驗證的步驟。
