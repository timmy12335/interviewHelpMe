# 題目

Spring 提供了那麼多擴充點，它們背後有什麼一致的設計原則？

## 核心答案

歸納起來有五條，而且它們互相支撐。

第一，分階段的生命週期加上每階段的鉤子。容器的啟動被切成明確的階段（環境準備、定義載入、定義後處理、實例化、實例後處理、就緒），每個階段都有對應的擴充介面。這讓使用者能在正確的時間點介入，而框架也能保證階段之間的不變量。

**第二，提供預設但允許覆寫**。`@ConditionalOnMissingBean` 是這條原則的核心實現——使用者一旦提供自己的實作，框架的預設就自動退讓，不需要任何額外設定。

**第三，宣告優於繼承**。從 `WebSecurityConfigurerAdapter` 到 `SecurityFilterChain` bean、從 `WebMvcConfigurerAdapter` 到有預設方法的介面——框架不佔用使用者的繼承名額，也讓多段設定可以組合。

**第四，客製化器（Customizer）模式**。當使用者只想調整一點點時，提供一個作用在框架建立過程中的回呼，而不是逼他接管整個物件的建立。

**第五，可診斷性**。`/actuator/conditions`、`--debug` 報告、`FailureAnalyzer`——當約定不符合預期時，能查出原因。

## 詳細解析

「提供預設但允許覆寫」是整個生態的基礎規則。它讓數百個 starter 能安全地共存於同一個 classpath 上——每個都提供合理的預設，而使用者的明確宣告永遠優先。這條規則的價值在於它把「加一個依賴」的風險降到很低：最壞的情況是多了一些用不到的 bean，而不是行為被意外改變。設計自己的函式庫時，這是最值得複製的一條。

「可診斷性」是最容易被忽略但決定採用成敗的一條。約定優於配置的框架有一個固有風險——當約定不符合預期時，使用者不知道發生了什麼。Spring Boot 用條件報告解決了這件事：每個自動配置為什麼生效或不生效，都有明確的記錄。沒有這個機制的話，自動配置就是黑箱魔法，而黑箱魔法在出問題時會摧毀使用者的信任。這給出一個判斷框架品質的標準：它的「魔法」能不能被解釋。

擴充點的數量本身是有成本的。Spring 的擴充點多到成為學習曲線的一部分——`BeanPostProcessor`、`BeanFactoryPostProcessor`、`BeanDefinitionRegistryPostProcessor`、`ApplicationContextInitializer`、`EnvironmentPostProcessor`、`SmartLifecycle`⋯⋯選錯一個就會遇到「東西還不存在」或「已經太晚」的問題。**這是「彈性」的代價**：每個擴充點都對應一個真實的需求，但它們合起來形成了一個需要理解整個生命週期才能正確使用的體系。設計自己的框架時，應該優先減少擴充點的數量，而不是增加。

這些原則的共同底層是「讓使用者的程式碼保持普通」。Spring 的擴充點大多是**介面加註解**，使用者的類別仍然是普通的 Java 類別——不繼承框架的基底類別、不實作大量的框架介面、也能在沒有框架的情況下被測試。這正是 Spring 相對於早期 EJB 的核心優勢，也是它能存活二十年的原因。 框架應該是**一個可以被移除的東西**，而不是滲透進每一行程式碼的東西。

## 面試回答方式

先給**五條原則**（分階段生命週期加鉤子、提供預設但允許覆寫、宣告優於繼承、客製化器模式、可診斷性）並各配一句說明。把「提供預設但允許覆寫」定位成整個生態的基礎規則——它讓數百個 starter 能安全共存，把「加一個依賴」的風險降到最壞只是多了用不到的 bean，這是設計自己的函式庫時最值得複製的一條。接著把**可診斷性**講成決定採用成敗的一條：約定優於配置有固有風險——約定不符預期時使用者不知道發生什麼，沒有條件報告的話自動配置就是黑箱魔法，而黑箱魔法在出問題時會摧毀信任。加分點是誠實指出**擴充點的數量本身是成本**，選錯就會遇到「東西還不存在」或「已經太晚」。收在共同底層：**讓使用者的程式碼保持普通**——不繼承框架基底類別、能在沒有框架的情況下被測試，框架應該是一個可以被移除的東西。

## 講稿

我歸納成五條。分階段的生命週期加上每階段的鉤子、提供預設但允許覆寫、宣告優於繼承、客製化器模式、還有可診斷性。

提供預設但允許覆寫是整個生態的基礎規則。使用者一旦提供自己的實作，框架的預設就自動退讓，不需要任何額外設定。這條規則的價值在於它把加一個依賴的風險降到很低，最壞的情況是多了一些用不到的 bean，而不是行為被意外改變。設計自己的函式庫時，這是最值得複製的一條。

可診斷性則是最容易被忽略但決定採用成敗的一條。約定優於配置的框架有一個固有風險，當約定不符合預期時，使用者不知道發生了什麼。Spring Boot 用條件報告解決這件事，每個自動配置為什麼生效或不生效都有明確記錄。沒有這個機制的話，自動配置就是黑箱魔法，而黑箱魔法在出問題的時候會摧毀使用者的信任。

我也想誠實說，擴充點的數量本身是有成本的。Spring 的擴充點多到成為學習曲線的一部分，選錯一個就會遇到東西還不存在或已經太晚的問題。

這些原則的共同底層是讓使用者的程式碼保持普通。框架應該是一個可以被移除的東西，而不是滲透進每一行程式碼的東西。

## 常見追問

### 為什麼說「框架應該可以被移除」？

**核心答案**：因為它決定了你的業務邏輯是不是被鎖在某個技術上。如果領域類別繼承了框架的基底類別、實作了框架的介面、方法簽章裡有框架的型別，那麼**換框架等於重寫**，而且那些類別無法在沒有框架的情況下被測試。反過來，如果它們是普通的 Java 類別，框架只是透過註解與設定把它們組裝起來，**那框架就只是一層外殼**。

**詳細解析**：這在實務上的價值不是「真的會換框架」（多數專案不會），而是三件更常發生的事：**測試變得容易**（不需要啟動容器）、**升級變得容易**（框架的破壞性變更影響的是組裝層而非業務邏輯）、以及**理解變得容易**（讀業務類別時不必先理解框架）。Spring 相對於早期 EJB 的核心優勢正是這個——EJB 要求元件實作特定介面、繼承特定類別，於是業務邏輯與容器綁死；Spring 用依賴注入加註解讓元件保持普通。這也是六角形架構（ports and adapters）的核心主張：把框架、資料庫、訊息中介軟體都當成可替換的適配器，領域邏輯不知道它們的存在。判斷一個專案有沒有做到這件事的簡單測試是：領域類別的 import 裡有沒有框架的套件。

**面試回答方式**：給根本理由——決定業務邏輯是不是被鎖在某個技術上。真正的重點是修正動機：價值不是「真的會換框架」而是三件更常發生的事——測試容易、升級容易、理解容易。用 EJB 與 Spring 的對比說明歷史脈絡，並連到六角形架構的核心主張。收在一個可操作的檢查：領域類別的 import 裡有沒有框架的套件。

### 設計自己的框架或內部函式庫時，該學什麼、避免什麼？

**核心答案**：該學的是「預設加覆寫」與「可診斷性」——提供合理的預設讓使用者零配置可用，同時保證他能覆寫任何一項；並且在行為不如預期時能查出原因（日誌、診斷端點、清楚的錯誤訊息）。**該避免的是擴充點的擴散**——每多一個擴充點就多一個使用者需要理解的概念，而且擴充點之間的互動會產生組合爆炸。

**詳細解析**：一個實用的原則是「先解決具體問題，不要先設計擴充點」。內部函式庫最常見的失敗模式是：預期了十種使用方式、設計了五個擴充點，結果實際只用到一種，而那五個擴充點成為永遠要維護的表面積。正確的順序是先讓兩三個使用者跑起來，等真的出現「我需要在這裡改一下」的需求時，再加對應的擴充點。 這與「重複三次再抽象」是同一個判斷。另一個值得學的是 Spring 的「失敗要清楚」——為你的函式庫常見的設定錯誤提供明確的錯誤訊息（甚至自訂 `FailureAnalyzer`），這件事的成本是幾十行程式碼，收益乘以所有使用者與所有次數。

**面試回答方式**：給該學的兩項（預設加覆寫、可診斷性）與該避免的一項（擴充點擴散）。真正的加分點是實用原則：先解決具體問題、不要先設計擴充點——常見失敗是預期十種用法設計五個擴充點、結果只用到一種而那五個成為永遠的維護表面積。給出正確順序（先讓幾個使用者跑起來、真的出現需求再加）並連到「重複三次再抽象」。收在低成本高回報的一項：為常見設定錯誤提供明確的錯誤訊息。

### Spring 有哪些設計現在看來是失誤的？

**核心答案**：三個可以誠實談的。**`spring.factories` 把所有擴充點混在一個檔案**——難讀難維護，Boot 3 已經開始拆分。XML 設定時代的過度靈活——幾乎所有東西都能在 XML 裡表達，結果是設定與程式碼分離到難以追蹤；註解與 Java 設定的轉向承認了這一點。循環依賴的三級快取——它「解決」了一個本該被視為設計問題的東西，讓使用者不必面對職責劃分的錯誤；Boot 2.6 把預設值改成禁止，等於承認了這個判斷。

**詳細解析**：這些「失誤」有一個共同模式：都是在早期為了解決真實問題而做的選擇，但隨著使用方式的演變成為負擔。 XML 的靈活性在 2004 年是相對於 EJB 的巨大進步；三級快取在大量使用欄位注入的年代確實讓很多專案跑起來了。評價一個設計決定，必須放回它被做出的脈絡。 更有價值的觀察是**Spring 願意改**——廢棄舊 API、改變預設值、拆分檔案格式，同時用足夠長的過渡期保護既有使用者。這種「承認錯誤但不粗暴地破壞相容」的能力，可能比任何單一的設計決定都更決定一個框架的長期壽命。

**面試回答方式**：誠實給出三個例子（`spring.factories` 混雜、XML 時代的過度靈活、循環依賴的三級快取）並各說明後來怎麼修正。真正的加分點是後半段：這些都是早期為解決真實問題而做的選擇，隨使用方式演變成為負擔，所以評價設計決定必須放回它被做出的脈絡。收在更有價值的觀察：Spring 願意改，同時用足夠長的過渡期保護既有使用者，而這種「承認錯誤但不粗暴破壞相容」的能力，可能比任何單一設計決定更決定框架的長期壽命。
