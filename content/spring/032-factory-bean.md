# 題目

`FactoryBean` 是什麼？為什麼取它要加 `&` 前綴？

## 核心答案

`FactoryBean<T>` 是一個特殊的 bean，它的職責是生產另一個 bean。容器在注入時會做一個特殊處理：發現某個 bean 實作了 `FactoryBean`，就呼叫它的 `getObject()` 並注入回傳值，而不是注入 `FactoryBean` 本身。所以宣告一個名為 `myThing` 的 `FactoryBean<Thing>`，`@Autowired Thing thing` 拿到的是 `Thing`。

`&` 前綴是取得工廠本身的逃生門：`applicationContext.getBean("&myThing")` 回傳的才是 `FactoryBean` 實例。這個設計是因為「同一個名稱指向兩個不同的東西」需要一個消歧義的方式，而 Spring 選了一個特殊字元前綴。

它有三個方法：`getObject()`（生產實例）、`getObjectType()`（回傳產品的型別，讓容器能在不實例化的情況下做型別比對）、`isSingleton()`（產品是否為單例）。**`getObjectType()` 特別重要**——如果它回傳 null，容器就必須真的建立一次物件才知道型別，這會破壞延遲初始化並可能造成初始化順序問題。

## 詳細解析

`FactoryBean` 與 `@Bean` 方法的核心差別是「工廠本身是不是一個 bean」。`@Bean` 方法只是設定類別裡的一段程式碼；`FactoryBean` 是一個真正的 bean，所以它可以被注入依賴、有完整的生命週期、能被 `BeanPostProcessor` 處理、也能被動態註冊。這讓它適合「建立邏輯複雜且本身需要協作者」的場景。

**`getObjectType()` 回傳 null 的後果值得展開**。容器在做「依型別自動裝配」時需要知道每個 bean 的型別；對 `FactoryBean` 而言，這個資訊由 `getObjectType()` 提供。回傳 null 時容器只能提前實例化該產品來確定型別——這會讓一個本該延遲初始化的 bean 提前建立，可能在其他 post processor 尚未準備好時就完成，導致它沒有被正確地代理或增強。這是「延遲初始化被意外破壞」的常見來源之一，症狀與前面提過的 post processor 提前實例化問題相同。

**`isSingleton()` 的語意容易混淆**：它指的是**產品**是不是單例，而不是工廠本身。回傳 true 時容器會快取 `getObject()` 的結果；回傳 false 則每次注入都呼叫一次。要注意的是，即使產品不是單例，`FactoryBean` 本身仍然是容器管理的單例。

**實務上什麼時候會遇到它**：多數開發者不會自己寫 `FactoryBean`，但會**間接使用**——MyBatis 的 `MapperFactoryBean`、Spring 的 `ProxyFactoryBean`、以及各種整合套件的工廠。**知道它存在的價值在於除錯**：當 `getBean("xxx")` 拿到的型別與預期不符、或者注入的物件是一個代理而你想拿到工廠時，`&` 前綴就是答案。這是一個「平時用不到但遇到時省下數小時」的知識。

## 面試回答方式

先給定義與最關鍵的行為——注入時給的是 `getObject()` 的結果而非工廠本身，並解釋 `&` 前綴是消歧義的逃生門（同一個名稱指向兩個東西，需要一個取得工廠本身的方式）。列出三個方法並特別強調 `getObjectType()`：它讓容器能在不實例化的情況下做型別比對，回傳 null 會迫使容器提前建立產品，破壞延遲初始化並可能讓該 bean 錯過後續的代理與增強。接著給與 `@Bean` 方法的核心差別：**工廠本身是不是一個 bean**——是的話就能被注入依賴、有生命週期、能被動態註冊。收在實務定位：多數人不會自己寫但會間接使用（MyBatis 的 Mapper、各種整合套件），**知道它的價值在於除錯**——注入型別與預期不符時，`&` 前綴就是答案。

## 講稿

FactoryBean 是一個特殊的 bean，它的職責是生產另一個 bean。容器發現某個 bean 實作了這個介面，注入的時候會呼叫它的生產方法並注入回傳值，而不是注入工廠本身。

所以要取得工廠本身，需要在名稱前加一個 & 符號。這個設計是因為同一個名稱指向兩個不同的東西，需要一個消歧義的方式。

它有三個方法，生產實例、回傳產品型別、還有產品是不是單例。其中回傳產品型別這個特別重要，因為容器做依型別自動裝配的時候需要知道型別。如果它回傳 null，容器就必須真的建立一次物件才知道型別，這會破壞延遲初始化，而且可能讓那個 bean 在其他處理器還沒準備好的時候就建立，結果沒有被正確代理。

跟配置方法的核心差別是，工廠本身是不是一個 bean。配置方法只是設定類別裡的一段程式碼，而 FactoryBean 是真正的 bean，可以被注入依賴、有完整生命週期、也能被動態註冊。

多數人不會自己寫它，但會間接用到，像是 MyBatis 的 Mapper。知道它存在的價值主要在除錯，當取得的型別跟預期不符的時候，那個前綴就是答案。

## 常見追問

### 什麼時候該用 FactoryBean 而不是 @Bean 方法？

**核心答案**：三種情況。建立邏輯需要依賴其他 bean 且邏輯複雜——把它放進一個有狀態的類別比放進一個 `@Bean` 方法清楚。**需要動態註冊**——`@Bean` 方法是編譯期寫死的，無法在執行期產生，而 `FactoryBean` 的定義可以被動態註冊。**產品的型別在編譯期未知**——例如為使用者的介面生成代理。**除此之外一律用 `@Bean` 方法**，它更簡單、更直觀、也更容易被讀者理解。

**詳細解析**：`@Bean` 方法其實已經能處理大部分「複雜建立邏輯」的需求——它可以有參數（容器會注入）、可以呼叫其他方法、可以有條件分支。所以「邏輯複雜」本身通常不足以構成用 `FactoryBean` 的理由。真正的分界線是「這個工廠需不需要自己是一個被管理的物件」——需要生命週期回呼（初始化時建立連線、銷毀時釋放）、需要被其他 bean 注入、或需要被 post processor 處理時，才必須是 bean。這個判斷方式比「邏輯複不複雜」精確得多，因為後者是主觀的。

**面試回答方式**：給三種情況並明確主張**除此之外一律用 `@Bean` 方法**。真正的加分點是修正判準：「邏輯複雜」本身不足以構成理由，因為 `@Bean` 方法已經能處理大部分複雜建立邏輯（可以有參數、分支、呼叫其他方法）。給出更精確的分界線：這個工廠需不需要自己是一個被管理的物件（需要生命週期回呼、被注入、被 post processor 處理）。

### FactoryBean 產生的物件能被 AOP 代理嗎？

**核心答案**：**可以，但時機與一般 bean 不同**。`getObject()` 的回傳值會經過 `BeanPostProcessor`，所以 AOP 的自動代理創建器有機會包裝它。但如果 `FactoryBean` 本身在很早的階段就被實例化（例如被某個 `BeanFactoryPostProcessor` 依賴），那時候 AOP 的 post processor 可能還沒註冊，**產品就不會被代理**。

**詳細解析**：這個問題的一般形式是「bean 的實例化順序決定了它會被哪些 post processor 處理」。Spring 對此有部分防護——它會偵測到「某個 bean 被提前實例化而錯過了 post processor」並印出 INFO 級別的日誌（訊息大意是 bean 不符合被所有 BeanPostProcessor 處理的資格）。這條日誌非常容易被忽略，但它是一個重要的警告訊號：出現它代表有某個 bean 沒有被完整處理，可能沒有 AOP 代理、沒有屬性注入的增強。排查「`@Transactional` 或 `@Async` 沒生效」時，第一件事就是去啟動日誌裡搜尋這類訊息——它常常直接指出問題所在。

**面試回答方式**：先給答案（可以，但時機不同）與失效條件（`FactoryBean` 被提前實例化時 AOP 的 post processor 還沒註冊）。真正的加分點是把它一般化：bean 的實例化順序決定了它會被哪些 post processor 處理，並指出 **Spring 會印出 INFO 級別的警告日誌**說某個 bean 不符合被所有 post processor 處理的資格。收在可操作的建議：排查「`@Transactional` 沒生效」時，第一件事是去啟動日誌搜尋這類訊息。

### 為什麼 Spring 用 & 這個奇怪的前綴？

**核心答案**：因為它需要一個在 bean 名稱中不會自然出現的字元來表達「我要工廠本身」。`&` 在 Java 識別字與大多數命名慣例中都不合法，所以不會與真實的 bean 名稱衝突。這是一個典型的**帶內訊號（in-band signaling）** 設計——用資料本身的一部分來傳遞控制資訊，而不是另外開一個參數或方法。

**詳細解析**：帶內訊號的優點是**不必改變介面**（`getBean(String)` 的簽章不動就多了一種能力），缺點是**它讓資料的解析變得有特例**，而且如果將來需要更多種控制訊號，字元前綴會越加越多且難以組合。Spring 在其他地方也用了同樣的手法：資源位置的 `classpath:`、`file:` 前綴、以及 SpEL 的 `#{}` 與屬性佔位符的 `${}`。這些設計的共同特徵是：用字串攜帶結構化資訊，換取 API 的簡潔。 代價是這些規則必須被記住或查文件，IDE 也難以提供協助。更現代的 API 設計傾向用型別表達這類區別（例如提供一個 `getFactoryBean(String)` 方法），但 Spring 的這些設計早於那個潮流，而且相容性讓它們無法更改。

**面試回答方式**：給出直接理由——需要一個在 bean 名稱中不會自然出現的字元。真正的加分點是把它識別成**帶內訊號**的設計模式：用資料本身傳遞控制資訊，優點是不必改介面、缺點是解析有特例且難以組合。舉 Spring 的其他同類設計（`classpath:` 前綴、`#{}` 與 `${}`）並歸納共同特徵：用字串攜帶結構化資訊換取 API 簡潔，代價是規則要記且 IDE 難以協助。
