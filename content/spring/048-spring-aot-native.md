# 題目

Spring 的 AOT 處理做了什麼？為什麼 Spring 需要它才能跑原生映像檔？

## 核心答案

原生映像檔要求**封閉世界假設**——建置時必須知道所有會被載入的類別、所有反射目標、所有動態代理。而 Spring 的核心機制**大量依賴執行期的動態性**：掃描 classpath 找元件、用反射建立 bean 與注入欄位、用 JDK 動態代理實作 AOP、用條件註解在執行期決定配置。**這兩者直接衝突**。

Spring AOT 的工作是把這些執行期的決定搬到建置期。它在建置時執行一次「模擬的容器啟動」：評估所有條件、確定最終有哪些 bean、它們的依賴關係與建立方式，然後**生成 Java 原始碼**（`__BeanDefinitions` 類別）直接註冊這些 bean，同時生成 GraalVM 需要的反射、代理、資源配置檔。

結果是：執行期不再需要掃描與條件評估，啟動路徑變成一連串明確的方法呼叫。這帶來兩個收益——**在 JVM 上也能加快啟動**（AOT 不一定要配原生映像檔），以及**讓原生映像檔成為可能**。

代價是**失去執行期的動態性**：條件在建置時就固定了，某些依賴執行期反射的功能需要額外配置或無法使用。

## 詳細解析

「AOT 不一定要配原生映像檔」是一個常被忽略的點。`spring-boot-maven-plugin` 的 `process-aot` 目標可以單獨使用，產生的程式碼在普通 JVM 上執行也能省下掃描與條件評估的時間——這是一個成本較低的中間選項，適合想改善啟動但不願承擔原生映像檔完整代價的專案。

AOT 生成的是可讀的 Java 原始碼，這是一個重要的設計選擇。相較於位元組碼操作或執行期魔法，生成原始碼讓結果可以被閱讀、被除錯、被版本控制檢視。當某個 bean 沒有被正確註冊時，可以直接去看生成的程式碼確認發生了什麼——這對一個本質上「把動態變靜態」的機制來說，可診斷性是關鍵。

**測試策略需要調整**。AOT 處理的結果與一般執行不同，所以必須在 AOT 模式下也跑一次測試（Spring Boot 提供了相關的測試支援）。常見的問題是：某個只在特定條件下才註冊的 bean，在建置時的條件評估中被排除了，於是原生映像檔裡沒有它——而這只有在 AOT 模式的測試中才會發現。「多一種建置模式就多一種需要驗證的組合」是採用 AOT 的隱藏成本。

判斷該不該用的標準與原生映像檔相同：啟動時間與記憶體是不是核心痛點。無伺服器函式、需要秒級擴容的服務、以及大量小型實例的部署，收益明顯；長時間執行的服務則收益有限而成本實在（建置時間變長、除錯變難、某些函式庫不支援）。先用 AOT 加 JVM 量測收益，再決定要不要走到原生映像檔，是一個風險較低的路徑。

## 面試回答方式

先講清楚**衝突的本質**——原生映像檔要求封閉世界假設，而 Spring 的核心機制（掃描、反射、動態代理、執行期條件）都依賴動態性。接著給 AOT 的工作：在建置時執行一次模擬的容器啟動，評估所有條件、確定最終的 bean 清單，然後生成 Java 原始碼直接註冊它們，同時生成 GraalVM 需要的反射與資源配置。給出兩個收益（JVM 上也能加快啟動、讓原生映像檔成為可能）與代價（失去執行期動態性）。加分點有三個：**AOT 不一定要配原生映像檔**，單獨用是成本較低的中間選項；**生成的是可讀的 Java 原始碼**而非位元組碼魔法，這讓結果可被閱讀與除錯，對「把動態變靜態」的機制來說可診斷性是關鍵；以及**必須在 AOT 模式下也跑測試**，因為條件評估的差異只有那裡才會發現。

## 講稿

原生映像檔要求封閉世界假設，建置時必須知道所有會被載入的類別、所有反射目標、所有動態代理。而 Spring 的核心機制大量依賴執行期的動態性，掃描 classpath 找元件、用反射建立 bean、用動態代理實作 AOP、用條件註解在執行期決定配置。這兩者直接衝突。

AOT 的工作就是把這些執行期的決定搬到建置期。它在建置時執行一次模擬的容器啟動，評估所有條件、確定最終有哪些 bean 跟它們的依賴關係，然後生成 Java 原始碼直接註冊這些 bean，同時生成映像檔需要的反射跟資源配置檔。

結果是執行期不再需要掃描跟條件評估，啟動路徑變成一連串明確的方法呼叫。

有一個常被忽略的點，AOT 不一定要配原生映像檔。單獨用它，生成的程式碼在普通 JVM 上執行也能省下掃描跟條件評估的時間。這是一個成本較低的中間選項。

我覺得生成可讀的 Java 原始碼是一個重要的設計選擇。相較於位元組碼操作或執行期魔法，生成原始碼讓結果可以被閱讀、被除錯。對一個本質上把動態變靜態的機制來說，可診斷性是關鍵。

## 常見追問

### AOT 之後哪些 Spring 功能會受限？

**核心答案**：**依賴執行期動態性的功能**。具體有四類：**執行期才決定的條件**（參與 `@ConditionalOnProperty` 判定的屬性在建置時就固定了，部署時改它不會生效）、**執行期產生的代理**（某些動態代理需要在建置時就宣告介面）、**未被靜態分析發現的反射**（例如用字串拼出類別名再 `Class.forName`）、以及**動態載入的類別或外掛**。

**詳細解析**：**Spring 對第一類提供了部分緩解**：某些條件被標記為「執行期可評估」，讓常見的設定切換仍然有效。但開發者需要知道哪些屬性是建置期固定的，這是一個新增的心智負擔。第三類最麻煩，因為它不會在建置時報錯——建置成功、啟動成功，直到某個罕見路徑第一次執行時才拋 `ClassNotFoundException`。防護方式是完整的測試覆蓋加上 GraalVM 的追蹤代理（跑一次應用記錄實際用到的反射），但追蹤代理只能記錄跑到的路徑，測試覆蓋不足就會漏。所以「AOT 的可靠性直接取決於測試覆蓋率」——這是採用它之前應該誠實評估的前提。

**面試回答方式**：給四類受限功能。重點展開**第三類最麻煩**——未被靜態分析發現的反射不會在建置時報錯，直到罕見路徑第一次執行才拋例外。給防護方式（完整測試加追蹤代理）並指出追蹤代理只能記錄跑到的路徑。收在關鍵前提：AOT 的可靠性直接取決於測試覆蓋率，這是採用前該誠實評估的。

### Spring Boot 3 的原生映像檔實務上成熟嗎？

**核心答案**：**核心框架與主流 starter 相當成熟**——Spring 官方為自家模組提供了完整的 AOT 支援與 GraalVM 中繼資料。**風險集中在第三方依賴**：一個沒有提供 GraalVM 中繼資料的函式庫，需要你自己寫反射配置，而那往往要深入它的原始碼才知道要配什麼。**GraalVM 的可達性中繼資料倉庫**（社群維護的常見函式庫配置）覆蓋了不少熱門依賴，但不是全部。

**詳細解析**：評估的方法是先做一次概念驗證：把應用建置成原生映像檔並跑完整的測試，把遇到的每個問題與解法記錄下來，這份清單就是「採用成本」的具體估算。**常見的問題類型**是：某個函式庫用了未宣告的反射、某個資源檔沒被包含、以及某個功能在原生下行為不同（例如日期時區資料庫需要明確包含）。要注意成本不只是初次採用，還有持續維護——每次升級依賴都可能引入新的反射需求，所以原生映像檔的建置與測試必須進 CI，不能是一次性的手動驗證。這個持續成本是決定要不要採用的關鍵因素，卻常常在評估時被忽略。

**面試回答方式**：分開評估——核心框架與主流 starter 成熟，風險集中在第三方依賴，並提到 GraalVM 可達性中繼資料倉庫覆蓋了不少但非全部。給出評估方法：先做概念驗證並記錄每個問題與解法，那份清單就是採用成本的估算。真正的加分點是強調成本不只是初次採用還有持續維護——每次升級依賴都可能引入新的反射需求，所以建置與測試必須進 CI；而這個持續成本常在評估時被忽略。

### 除了 AOT，還有哪些改善 Spring 啟動的方法？

**核心答案**：由低成本到高成本有五個。**移除不需要的依賴**——每個 starter 都帶來自動配置與類別載入，清理未使用的依賴是最便宜的改善。**縮小元件掃描範圍**——明確指定 `basePackages` 而非掃描整個根套件。**延遲初始化**（`spring.main.lazy-initialization=true`）——把 bean 建立推遲到第一次使用。**AppCDS**——預存類別解析結果，不改任何程式碼。**AOT 與原生映像檔**。

**詳細解析**：**前兩項的效果常被低估**。一個依賴了二十個 starter 的應用，可能有數百個自動配置類別需要評估，而其中大半對應的功能根本沒在用。用 `--debug` 的自動配置報告檢視「哪些配置生效了但我其實不需要」，往往能找到可以移除的依賴。 延遲初始化則要謹慎——它把成本移到第一次請求，而且會讓「啟動時就該發現的錯誤」（設定錯誤、bean 建立失敗）延後到執行期。在需要快速擴容的場景，延遲初始化可能是負收益：新實例看起來就緒了但第一批請求很慢。所以正確的目標是「從啟動到能穩定服務的時間」而非「啟動時間」，這兩者在 readiness probe 的設計上直接體現。

**面試回答方式**：給五個方法並按成本排序。強調**前兩項的效果常被低估**，並給出可操作的診斷：用 `--debug` 的自動配置報告找出「生效了但其實不需要」的配置。真正的加分點是對延遲初始化的平衡評價：它把成本移到第一次請求，且讓啟動時該發現的錯誤延後到執行期，在需要快速擴容時可能是負收益。收在目標的修正：「從啟動到能穩定服務的時間」而非「啟動時間」。
