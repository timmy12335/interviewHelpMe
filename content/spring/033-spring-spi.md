# 題目

Spring 怎麼發現分散在各個 JAR 裡的擴充？它與 Java 原生的 SPI 差在哪？

## 核心答案

Spring 的做法是**掃描 classpath 上所有 JAR 的特定中繼資料檔案**，把裡面列出的類別名收集起來。Boot 2.x 用 `META-INF/spring.factories`（一個 properties 檔，key 是介面名、value 是逗號分隔的實作類別名）；**Boot 3 把自動配置獨立成 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`**，一行一個類別名。

與 Java 原生 SPI（`ServiceLoader` 加 `META-INF/services`）的差別有四點。**實例化方式**——`ServiceLoader` 用無參建構子直接建立，Spring 則可以把它們變成受管理的 bean（能注入依賴、有生命週期）。**排序**——Spring 支援 `@Order` 與 `Ordered` 介面決定執行順序，`ServiceLoader` 沒有順序保證。**條件**——Spring 的自動配置可以用 `@Conditional` 決定是否生效，`ServiceLoader` 載入了就是載入了。**多種擴充點共用一個檔案**（spring.factories 的設計，也是它被拆分的原因）。

**核心價值都一樣：讓「誰提供了實作」這件事由 classpath 決定，而不是由使用方的程式碼決定**——這正是外掛式架構的基礎。

## 詳細解析

**「約定的檔案位置」是這類機制的共同基礎**。JAR 是獨立打包的，彼此不知道對方存在；**唯一能讓它們協作的方式，是約定一個位置放中繼資料，由框架在啟動時把所有 JAR 的那個位置掃過一遍**。`classpath*:` 前綴（掃描所有符合的資源，而非只找第一個）正是實現這件事的機制。理解這一點，就理解了 Java 生態裡幾乎所有「加一個依賴就多一個功能」的原理。

**條件化是 Spring 相對於原生 SPI 最大的優勢**。原生 SPI 一旦被載入就會建立實例，而 Spring 的自動配置可以宣告「**只有在 classpath 有某個類別、且使用者沒有自己定義同型別 bean、且某個屬性為 true 時才生效**」。**這讓一個 starter 可以安全地存在於 classpath 上而不強加任何東西**——這正是 Spring Boot 生態能有數百個 starter 共存的原因。

**代價是啟動時的掃描成本**。每個 JAR 都要被檢查、每個候選類別都要被載入以評估條件、每個條件都要被求值。一個依賴很多的應用可能有數百個自動配置類別需要評估，**這是 Spring Boot 啟動慢的主要來源之一**。Boot 3 的檔案拆分、以及 AOT 在建置期就把條件求值完成，都是針對這個成本的優化。

**自訂擴充點時要考慮的問題**：擴充的順序是否重要（要不要支援 `@Order`）、能不能被關閉（提供 `enabled` 屬性）、多個實作同時存在時的語意（全部執行、只取第一個、還是報錯）。**最後一項最容易被忽略**——如果語意是「只取第一個」，那必須有明確的排序規則，否則行為會依 classpath 的順序而定，**而 classpath 順序在不同環境可能不同**，這會造成極難重現的問題。

## 面試回答方式

先給機制——**掃描 classpath 上所有 JAR 的約定位置檔案**，並指出 Boot 3 把自動配置獨立成新檔案。接著給與原生 SPI 的**四點差別**（實例化成受管理的 bean、支援排序、支援條件、多種擴充點共用檔案）。把**條件化定位成最大的優勢**：原生 SPI 載入了就建立，而 Spring 可以宣告「classpath 有某類別、使用者沒自己定義、屬性為 true 時才生效」——**這讓 starter 能安全地存在於 classpath 上而不強加任何東西，正是數百個 starter 能共存的原因**。加分點有兩個：**代價是啟動時的掃描與條件求值成本**，這是 Boot 啟動慢的主要來源，AOT 在建置期完成求值就是針對它；以及自訂擴充點時**「多個實作同時存在的語意」最容易被忽略**——若是「只取第一個」就必須有明確排序，否則行為依 classpath 順序而定，而那在不同環境可能不同。

## 講稿

Spring 的做法是掃描 classpath 上所有 JAR 的一個約定位置的中繼資料檔案，把裡面列出的類別名收集起來。Boot 3 把自動配置獨立成一個專門的檔案，一行一個類別名。

跟 Java 原生 SPI 的差別有三點。實例化方式不同，原生的用無參建構子直接建立，Spring 可以把它們變成受管理的 bean。Spring 支援排序。Spring 支援條件。

我認為條件化是最大的優勢。原生 SPI 一旦被載入就會建立實例，而 Spring 的自動配置可以宣告只有在 classpath 有某個類別、使用者沒有自己定義同型別 bean、而且某個屬性為真的時候才生效。這讓一個 starter 可以安全地存在於 classpath 上而不強加任何東西，這正是數百個 starter 能共存的原因。

代價是啟動時的掃描成本，每個候選類別都要被載入以評估條件，這是啟動慢的主要來源之一。

自訂擴充點的時候，我覺得最容易忽略的是多個實作同時存在的語意。如果語意是只取第一個，就必須有明確的排序規則，否則行為會依 classpath 順序而定，而那在不同環境可能不同。

## 常見追問

### 自動配置的順序怎麼控制？

**核心答案**：用 `@AutoConfiguration` 的 **`before`／`after`／`beforeName`／`afterName`** 屬性（Boot 3；2.x 用 `@AutoConfigureBefore`／`@AutoConfigureAfter`／`@AutoConfigureOrder`）。順序重要的原因是**條件的求值依賴於當時已有的 bean 定義**——如果你的配置用 `@ConditionalOnBean(DataSource.class)`，而 `DataSource` 的自動配置排在你後面，判定時它還不存在，你的配置就被跳過了。

**詳細解析**：**`@ConditionalOnBean` 與 `@ConditionalOnMissingBean` 對順序特別敏感**，這也是官方建議「**在自動配置以外的地方不要用 `@ConditionalOnBean`**」的原因——在使用者的 `@Configuration` 類別裡用它，順序完全不可預測。**更穩健的做法是用 `@ConditionalOnClass` 這類不依賴 bean 定義狀態的條件**，它只看 classpath，結果是確定的。**這是一個有價值的一般原則：條件應該盡量基於「靜態且確定的事實」（classpath、屬性值），而不是「動態且順序相關的狀態」（有沒有某個 bean）。** 前者的行為可預測，後者會產生「在某些依賴組合下才出錯」的問題。

**面試回答方式**：給出控制屬性與**順序重要的根本原因**——條件求值依賴於當時已有的 bean 定義，順序錯了條件就判定錯。真正的加分點是官方建議「**自動配置以外不要用 `@ConditionalOnBean`**」及其理由（順序不可預測），並提升成一般原則：**條件應該基於靜態確定的事實（classpath、屬性值）而非動態順序相關的狀態（有沒有某個 bean）**。

### AOT 怎麼優化這個機制？

**核心答案**：把**條件求值從執行期移到建置期**。AOT 處理在建置時就知道 classpath 的完整內容與設定值（在允許的範圍內），因此可以先評估所有條件，**只把真正會生效的配置與 bean 定義寫進生成的程式碼**。啟動時不必再掃描 JAR、載入候選類別、求值條件——直接執行生成好的註冊程式碼。這對啟動時間的改善很明顯，也是原生映像檔的前提。

**詳細解析**：**代價是失去了執行期的動態性**。AOT 處理過的應用，**條件在建置時就固定了**——不能在部署時透過改一個屬性來啟用不同的自動配置（如果那個屬性參與了條件判定）。Spring 對此的處理是把**部分條件標為「建置期可評估」、部分保留到執行期**，但這增加了心智負擔：開發者需要知道哪些設定在 AOT 下仍然有效。**這是所有 AOT 方案的共同取捨——用動態性換啟動速度**，而 Spring 的做法是盡量保留常用的動態性、只把明顯靜態的部分提前。**能講出「這不是免費的優化，而是一個取捨」，比只說 AOT 讓啟動變快更準確。**

**面試回答方式**：給出核心機制——**條件求值從執行期移到建置期**，只把會生效的配置寫進生成程式碼。真正的加分點是誠實給出代價：**失去執行期的動態性**，參與條件判定的屬性在建置時就固定了，開發者需要知道哪些設定在 AOT 下仍有效。收在定位：**這是所有 AOT 方案的共同取捨——用動態性換啟動速度**，而不是免費的優化。

### 這種「掃描 classpath」的機制有什麼風險？

**核心答案**：三個。**行為依賴 classpath 的內容**——加一個看似無關的依賴可能意外啟用某個自動配置，改變應用行為。**衝突難以預期**——兩個 JAR 提供了同型別的 bean 時，誰生效取決於順序與條件，而那可能不明顯。**安全風險**——classpath 上的任何 JAR 都能註冊擴充並在啟動時執行程式碼，**這意味著依賴供應鏈的信任邊界很寬**。

**詳細解析**：**第三項在近年的供應鏈攻擊背景下值得認真對待**。一個惡意或被入侵的依賴，只要出現在 classpath 上，就能透過 `spring.factories` 註冊一個 `ApplicationContextInitializer` 或 `EnvironmentPostProcessor` 並在啟動最早期執行任意程式碼——**不需要應用主動呼叫它的任何 API**。防護的方向是依賴管理層面的：**鎖定版本（lockfile）、驗證校驗和、使用私有的依賴代理並掃描已知漏洞、以及定期審查新增的傳遞依賴**。**這說明「方便的擴充機制」與「安全邊界」天生存在張力**——凡是能讓依賴自動生效的機制，也就讓惡意依賴自動生效。

**面試回答方式**：給三個風險（行為依賴 classpath 內容、衝突難預期、安全風險）。重點展開第三項：**classpath 上的任何 JAR 都能註冊擴充並在啟動最早期執行任意程式碼，不需要應用主動呼叫它**。給出防護方向（鎖定版本、驗證校驗和、私有代理加漏洞掃描、審查傳遞依賴）。收在洞見：**方便的擴充機制與安全邊界天生存在張力**——能讓依賴自動生效的機制，也讓惡意依賴自動生效。
