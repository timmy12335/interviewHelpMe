# 題目

什麼是 IoC（控制反轉）？什麼是 DI（依賴注入）？兩者是什麼關係？Spring 為什麼要用 IoC？

## 核心答案

IoC（Inversion of Control，控制反轉）是一種設計思想——把「建立物件、管理物件之間依賴關係」的控制權從程式碼本身反轉交給一個外部容器。DI（Dependency Injection，依賴注入）是實現 IoC 的一種具體手段——由容器在建立物件時，主動把它所依賴的其他物件「注入」進來，而不是物件自己去 new。兩者的關係是——IoC 是思想/目標，DI 是實現這個思想的方式。Spring 用 IoC 是為了「解耦」——物件不再自己負責建立和查找依賴，降低了物件之間的耦合、提升了可測試性和可維護性。

## 詳細解析

**傳統做法（控制權在自己手上）**：一個物件如果需要用到另一個物件，通常自己 `new` 它——例如 `UserService` 內部 `this.userDao = new UserDaoImpl()`。這樣 `UserService` 就和具體的 `UserDaoImpl` 緊密耦合，換實作要改程式碼、也難以在測試時替換成 mock。

**IoC（控制反轉）**：把「建立和組裝物件」的控制權「反轉」交給容器。物件不再自己 new 依賴，而是宣告「我需要一個 UserDao」，由容器負責建立好 UserDao 並提供給它。控制權從「應用程式碼」反轉到了「容器」，這就是「控制反轉」的字面含義。

**DI（依賴注入）**：是實現 IoC 的具體手段。容器在建立一個 Bean 時，發現它依賴其他 Bean，就主動把那些依賴「注入」進來。注入方式有三種——建構子注入、Setter 注入、欄位注入（`@Autowired`）。

**IoC 帶來的好處**：

1. **解耦**：物件依賴的是抽象（介面），具體實作由容器注入，換實作不用改依賴方的程式碼。
2. **可測試性**：測試時可以輕鬆注入 mock 物件，不需要真的建立依賴。
3. **統一管理**：容器統一管理所有物件的生命週期、依賴關係、配置，程式碼更清晰。
4. **便於橫切關注點**：容器管理物件後，可以在建立過程中織入 AOP（如交易、日誌）。

**「反轉」反轉的是什麼**：反轉的是「依賴物件的取得方式」——傳統是「主動去建立/查找依賴（正向控制）」，IoC 是「被動地等待容器注入依賴（反向）」。有個生動的說法叫「好萊塢原則：Don't call us, we'll call you」——你別主動找依賴，容器會把依賴給你。

## 面試回答方式

先講清楚「IoC 是思想、DI 是實現手段」這個關係，這是這題最容易混淆也最能展現理解的點——很多人把兩者當成一回事。用「傳統自己 new 依賴（耦合）vs IoC 由容器注入依賴（解耦）」的對比說明「反轉」反轉的是什麼（依賴取得的控制權）。好處要能講出核心的「解耦」和「可測試性」。如果能用「好萊塢原則」這個生動的比喻，或點出「容器接管物件後才能織入 AOP」，展現你理解 IoC 不只是個名詞而是 Spring 整個體系的基石。

## 常見追問

### 依賴注入有哪幾種方式？各有什麼優缺點？該用哪種？

**核心答案**：三種——建構子注入（透過建構子參數注入）、Setter 注入（透過 setter 方法注入）、欄位注入（直接在欄位上 `@Autowired`）。現在官方和社群普遍推薦「建構子注入」，因為它能保證依賴不可變（欄位可設 final）、保證物件建立時依賴就已齊備（不會出現半初始化狀態）、且便於測試（不依賴 Spring 容器就能 new 出來傳入 mock）。欄位注入雖然寫起來最簡潔，但有隱藏依賴、無法設 final、脫離容器難以測試等缺點，逐漸不被推薦。

**詳細解析**：三種方式的取捨——**建構子注入**：依賴透過建構子傳入，可以把欄位宣告為 `final`（不可變、更安全）、且物件一旦建立依賴就一定齊全（不會有「注入到一半」的狀態），測試時直接 `new XxxService(mockDao)` 即可，不需要 Spring 容器。缺點是依賴多時建構子參數會很長（但這其實是一個「這個類別依賴太多、該拆分」的信號）。**Setter 注入**：適合「可選依賴」或「需要在建立後重新配置」的場景，但依賴是可變的、且可能出現「還沒 set 就被使用」的問題。**欄位注入**：`@Autowired` 直接標在欄位上，最簡潔，但問題最多——依賴被隱藏（從建構子看不出這個類別依賴什麼）、無法宣告 final、且脫離 Spring 容器就無法注入（測試時要用反射（Reflection）或容器）。Spring 官方文件現在推薦建構子注入，很多團隊也把它作為規範。

**面試回答方式**：列出三種方式，重點論述「為什麼推薦建構子注入」——不可變（final）、依賴齊備、易測試，並對比欄位注入的缺點（隱藏依賴、不可 final、難測試）。能提到「建構子參數過長其實是類別依賴過多的信號」，展現你不只知道注入方式，還理解背後的設計原則。

### IoC 容器初始化的大致流程是什麼？

**核心答案**：大致流程是——讀取配置（XML、註解、Java Config）解析成 BeanDefinition（Bean 的「定義/藍圖」，記錄類別、作用域、依賴、初始化方法等元資料）→ 把 BeanDefinition 註冊到容器 → 對於單例且非延遲載入的 Bean，容器在初始化時就實例化它們（實例化 → 屬性填充/依賴注入 → 初始化回呼如 `@PostConstruct`/`InitializingBean`，中間穿插 BeanPostProcessor 的處理，AOP 代理也在此織入）→ 容器就緒可以對外提供 Bean。

**詳細解析**：這個流程的核心是「BeanDefinition 是 Bean 的藍圖，容器先收集所有藍圖、再根據藍圖建立 Bean」。分兩大階段——**容器啟動/BeanDefinition 註冊階段**：掃描配置來源（`@ComponentScan` 掃描註解、解析 `@Configuration` 的 `@Bean` 方法、讀 XML），把每個 Bean 的定義封裝成 BeanDefinition 註冊到容器（此時還沒建立實例）；期間 `BeanFactoryPostProcessor` 可以修改這些定義。**Bean 實例化階段**：對單例非延遲的 Bean，容器逐個建立——實例化（呼叫建構子）→ 屬性填充（依賴注入）→ 執行 `Aware` 回呼、`BeanPostProcessor` 的前置處理、初始化方法（`@PostConstruct`/`InitializingBean.afterPropertiesSet`/自訂 init）、`BeanPostProcessor` 的後置處理（AOP 代理通常在這裡生成）。理解這個流程是理解 Bean 生命週期、循環依賴、AOP 織入時機的基礎，這些後續題目都建立在它之上。

**面試回答方式**：分「BeanDefinition 註冊」和「Bean 實例化」兩階段講，點出「BeanDefinition 是藍圖、先收集藍圖再造 Bean」這個核心。能提到 BeanFactoryPostProcessor（改定義）和 BeanPostProcessor（處理實例、織入 AOP）的介入時機，展現你對容器啟動流程的整體掌握，也為後續生命週期、AOP 等題目鋪墊。

### 為什麼有了 IoC 容器，AOP 才容易實現？

**核心答案**：因為 AOP 需要「在目標物件的方法前後織入橫切邏輯（如交易、日誌）」，而織入的方式是「用一個代理物件包裝目標物件」——關鍵在於「呼叫方拿到的必須是代理物件而非原始物件」。IoC 容器統一負責建立和提供所有物件，於是容器就能在建立 Bean 的過程中「偷偷把原始 Bean 換成代理 Bean」再提供給呼叫方，讓 AOP 對使用者透明。如果沒有容器、物件都是自己 new 的，就沒有一個統一的地方能把物件替換成代理，AOP 就難以無侵入地實現。

**詳細解析**：這揭示了 IoC 和 AOP 的深層關係——IoC 是 AOP 的基礎設施。AOP 的本質是動態代理（見 Java 核心的動態代理（Dynamic Proxy）題），而動態代理要生效，必須保證「使用者實際拿到並呼叫的是代理物件」。在 IoC 容器中，這件事自然而然就能做到——因為所有 Bean 都由容器建立和注入，容器在建立某個需要 AOP 的 Bean 時（透過 `BeanPostProcessor`），可以生成它的代理物件、並把代理註冊到容器，於是任何地方 `@Autowired` 注入到的都是代理物件，方法呼叫自動經過代理的攔截。這一切對開發者完全透明——你以為注入的是 `UserService`，實際上是它的代理。如果沒有容器、`UserService` 是各處自己 `new` 的，就沒有統一的攔截點能把它換成代理，AOP 就只能靠手動包裝（侵入式）。所以「容器統一管理物件」正是 AOP 能無侵入織入的前提。理解這層關係，展現你把 Spring 的兩大核心（IoC 和 AOP）串起來理解。

**面試回答方式**：講出核心邏輯——「AOP 靠代理、代理要生效必須讓呼叫方拿到代理物件、而容器統一建立和提供物件所以能把 Bean 換成代理、對使用者透明」。強調「沒有容器就沒有統一的替換點、AOP 難以無侵入實現」。能把「IoC 是 AOP 的基礎設施」這個關係點出來，展現你對 Spring 兩大核心的關聯有深刻理解。
