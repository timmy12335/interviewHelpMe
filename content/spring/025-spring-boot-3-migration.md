# 題目

Spring Boot 2 升級到 3 的主要斷點是什麼？為什麼 `javax` 要改成 `jakarta`？

## 核心答案

最大的斷點是**命名空間從 `javax.*` 改成 `jakarta.*`**。原因是 Oracle 把 Java EE 捐給 Eclipse 基金會成立 Jakarta EE 時，**保留了 `javax` 這個商標**——新的規範版本不得繼續使用它。所以 `javax.servlet`、`javax.persistence`、`javax.validation` 全部變成 `jakarta.*`。**這是一次純粹因為法律因素造成的破壞性變更**，技術上沒有任何必要，但它影響了每一個用到 Servlet、JPA 或 Bean Validation 的檔案。

其餘三個主要斷點：**最低 JDK 17**（Spring Framework 6 全面採用 Java 17 的語言特性）、**移除大量已廢棄的 API**（`WebSecurityConfigurerAdapter`、`antMatchers`、`RestTemplate` 的部分用法）、以及**可觀測性的重構**——原本分散的 Micrometer 指標與 Sleuth 追蹤統一成 **Micrometer Observation API**，Spring Cloud Sleuth 併入 Micrometer Tracing。

遷移的實際順序是：**先升級到 Spring Boot 2 的最後一個版本**（讓廢棄警告全部浮現並修完）、**再升 JDK 到 17**、**最後才換 Spring Boot 3**——一次跳過中間步驟會讓錯誤難以歸因。

## 詳細解析

**命名空間變更的機械性讓工具可以處理**：OpenRewrite 的遷移配方或 IDE 的全域取代能完成大部分工作。**真正的麻煩在第三方依賴**——如果某個函式庫還沒發布支援 jakarta 的版本，你就卡住了。**這是升級時間表的主要不確定性來源**，應該在評估階段就把所有依賴掃過一遍。少數情況可以用 Eclipse Transformer 之類的工具在建置時轉換位元組碼，但那是應急手段。

**Spring Security 的變更幅度特別大**。`WebSecurityConfigurerAdapter` 被移除，改成宣告 `SecurityFilterChain` 這個 bean；`authorizeRequests` 改成 `authorizeHttpRequests`；`antMatchers` 改成 `requestMatchers`。**這些不只是改名，而是設計方向的轉變**——從「繼承一個基底類別覆寫方法」改成「宣告設定物件」，與 Spring 整體從繼承轉向組合的方向一致。**遷移時要一併理解新的心智模型，否則只是機械地改名字，之後仍然不會用。**

**可觀測性的統一是升級的實質收益之一**。以前指標（Micrometer）與追蹤（Sleuth）是兩套獨立的機制，要在兩邊各自埋點；**Observation API 讓一次埋點同時產生指標與追蹤 span**，並且能自動關聯。這減少了樣板也讓資料更一致。**但它要求重新設定既有的追蹤配置**，這部分的遷移成本常被低估。

**升級的收益要能說清楚**：Spring Boot 2.7 已於 2023 年結束開源支援（商業支援也有期限），繼續留在舊版意味著**沒有安全修補**。加上虛擬執行緒支援（Boot 3.2 起）、原生映像檔支援、以及 JDK 17 的效能改善。**把「不升級的風險」講成安全與支援問題，比談新功能更能推動決策。**

## 面試回答方式

先給最大的斷點——**`javax` 改 `jakarta`**，並說明它是**純粹因為商標的法律因素**，技術上沒有必要卻影響每一個用到 Servlet、JPA、Validation 的檔案。接著給其餘三個斷點（JDK 17 起跳、移除廢棄 API、可觀測性重構成 Observation API）。給出遷移順序：**先升到 Boot 2 最後一版修完廢棄警告 → 再升 JDK 17 → 最後換 Boot 3**，強調一次跳過會讓錯誤難以歸因。加分點有三個：**真正的麻煩在第三方依賴**有沒有 jakarta 版本，這是時間表的主要不確定性；**Spring Security 的變更是設計方向轉變**（從繼承基底類別改成宣告設定 bean），只機械改名之後仍然不會用；以及推動決策要講**安全與支援**而非新功能。

## 講稿

最大的斷點是命名空間從 javax 改成 jakarta。原因是 Oracle 把 Java EE 捐給 Eclipse 基金會的時候保留了 javax 這個商標，新的規範版本不能繼續用。所以 Servlet、JPA、Validation 這些全部要改。這是一次純粹因為法律因素造成的破壞性變更，技術上沒有任何必要，但它影響每一個用到這些的檔案。

其餘三個斷點是，最低 JDK 十七、移除大量已廢棄的 API、還有可觀測性重構，原本分開的指標跟追蹤統一成一套觀測 API。

我的遷移順序是，先升到 Spring Boot 2 的最後一個版本讓廢棄警告全部浮現並修完，再升 JDK 到十七，最後才換 Boot 3。一次跳過中間步驟會讓錯誤難以歸因。

命名空間的變更很機械，工具可以處理大部分。真正的麻煩在第三方依賴，如果某個函式庫還沒發布支援新命名空間的版本，你就卡住了。這是升級時間表最主要的不確定性來源。

還有 Spring Security 的變更幅度特別大，而且不只是改名，是從繼承基底類別覆寫方法，改成宣告設定物件。要一併理解新的心智模型，不然只是機械改名，之後還是不會用。

## 常見追問

### 為什麼 Spring Security 要從繼承改成宣告 bean？

**核心答案**：因為**繼承的擴充模型有結構性問題**。`WebSecurityConfigurerAdapter` 要求使用者繼承並覆寫方法，這帶來三個限制：**只能有一條設定路徑**（一個類別只能繼承一次，多套安全規則要用複雜的內部類別技巧）、**父類別的改動會波及所有子類別**（脆弱基底類別）、以及**設定的組合困難**（無法把幾段設定拼起來）。改成宣告 `SecurityFilterChain` 這個 bean 之後，**可以宣告多條鏈並用 `@Order` 決定順序**，每條鏈負責不同的路徑模式。

**詳細解析**：這是 Spring 整體方向的一部分——**從「繼承框架提供的類別」轉向「宣告設定物件」**。同樣的轉變出現在 `WebMvcConfigurerAdapter` 變成 `WebMvcConfigurer` 介面（有預設方法所以不必繼承）、以及各種 `Customizer` 介面的普及。**好處是使用者的類別不被框架佔用繼承名額、多個設定可以組合、而且框架可以在不破壞使用者程式碼的情況下演進。** 代價是設定的表達從「覆寫哪個方法」變成「宣告哪些 bean」，**對不熟悉的人來說可發現性較差**——不知道該宣告什麼型別的 bean，也不知道有哪些可選項。這正是為什麼文件與 IDE 支援對這種設計特別重要。

**面試回答方式**：給繼承模型的**三個結構性限制**（只能一條路徑、脆弱基底類別、無法組合），再說明新模型如何解決（可宣告多條鏈並用 `@Order` 排序）。加分點是把它放進 Spring 的整體方向——**從繼承框架類別轉向宣告設定物件**，並舉 `WebMvcConfigurer` 的預設方法與 `Customizer` 介面作為同類。誠實給出代價：**可發現性較差**，不知道該宣告什麼型別的 bean，所以文件與 IDE 支援特別重要。

### 遷移時怎麼處理還沒支援 jakarta 的依賴？

**核心答案**：按優先順序有四條路。**升級到支援的版本**——多數主流函式庫已經發布，先確認是不是自己的版本太舊。**尋找替代品**——某些不再維護的函式庫可能有活躍的分支或替代方案。**建置期位元組碼轉換**——用 Eclipse Transformer 或 Apache Tomcat 的 migration tool 把 JAR 裡的 `javax` 改寫成 `jakarta`，**這是可行但脆弱的應急手段**（轉換後的 JAR 沒有經過原作者測試）。**隔離**——把用到該函式庫的功能拆成一個獨立的服務，留在舊版。

**詳細解析**：**評估階段就該把這件事做完**，而不是遷移到一半才發現。做法是列出所有直接與傳遞依賴（`mvn dependency:tree` 或 `gradle dependencies`），逐一確認有沒有支援 jakarta 的版本。**傳遞依賴特別容易漏**——自己的程式碼沒有直接用到，但某個框架內部用了。**這個盤點的結果直接決定了升級的可行性與時程**，應該在提出升級計畫之前就完成。如果發現有無法解決的依賴，**誠實地把它列為阻礙並提出解法選項**，比樂觀估計然後中途卡住好得多。

**面試回答方式**：給四條路並排出優先順序，對位元組碼轉換給出平衡評價（可行但脆弱，轉換後的 JAR 未經原作者測試）。真正的重點是流程建議：**評估階段就要把依賴盤點做完**，包含傳遞依賴（自己沒直接用但框架內部用了，特別容易漏），而這個盤點的結果**直接決定升級的可行性與時程**。收在態度：發現無法解決的依賴要誠實列為阻礙並提出選項。

### Observation API 相較於原本的做法好在哪？

**核心答案**：**一次埋點，同時產生指標與追蹤**。以前要在同一段程式碼裡分別用 Micrometer 記指標、用 Sleuth 開 span，兩套 API、兩份樣板、而且容易不一致（指標的標籤與 span 的屬性各自維護）。Observation API 把「一次可觀測的操作」抽象成一個概念，**由它同時產生 timer 指標與 tracing span**，標籤共用，也自動處理上下文傳遞。

**詳細解析**：更實質的價值是**慣例的統一**。Spring 內部的所有元件（HTTP 客戶端與伺服器、資料庫存取、訊息傳遞、快取）都改用同一套 Observation，所以**指標的命名、標籤、以及與追蹤的關聯方式在整個框架裡是一致的**——這讓儀表板與告警規則可以跨元件重用。**自訂的業務觀測也能接進同一套約定**，不必自己發明命名規則。代價是**遷移期間兩套機制可能並存**（舊的 Sleuth 設定與新的 Micrometer Tracing），需要明確地完成切換而不是長期共存，否則會出現「有些鏈路有追蹤、有些沒有」的破碎狀態。

**面試回答方式**：核心是「**一次埋點同時產生指標與追蹤**」，並說明以前兩套 API 容易不一致的問題。真正的加分點是提出更實質的價值——**慣例的統一**：框架內所有元件用同一套約定，讓儀表板與告警規則可跨元件重用，自訂業務觀測也能接進同一套命名。誠實給出代價：遷移期兩套機制並存會造成破碎的追蹤鏈路，需要明確完成切換。
