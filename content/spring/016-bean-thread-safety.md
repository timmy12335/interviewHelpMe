# 題目

Spring 的單例 Bean 是執行緒安全的嗎？為什麼？如何保證執行緒安全？

## 核心答案

Spring 的單例 Bean「本身不保證執行緒安全」——是否安全取決於這個 Bean 有沒有「可變的共享狀態」。如果 Bean 是「無狀態的」（只有方法邏輯、沒有可變的實例成員欄位，或成員都是唯讀的），那麼即使被多執行緒共享也是安全的（每個執行緒呼叫方法時用的是各自的棧幀、參數、區域變數，互不干擾）。但如果 Bean 有「可變的實例成員欄位」並在方法中讀寫它，多執行緒共享這個單例就會有執行緒安全問題（資料串號）。所以絕大多數 Spring Bean（Service、DAO、Controller）設計成無狀態的，正是為了在單例共享下保持安全。

## 詳細解析

**為什麼單例本身不保證執行緒安全**：Spring 只負責「建立和管理」Bean，不會為你的 Bean 加任何同步。單例意味著「全應用共享同一個實例」——多個執行緒（如處理不同 HTTP 請求的執行緒）會同時呼叫這同一個 Bean 的方法。這本身有沒有問題，取決於這些執行緒有沒有「共享並修改」同一份可變狀態。

**無狀態 Bean 是安全的**：一個典型的 Service——

```java
@Service
class UserService {
    @Autowired UserDao userDao;  // 注入的無狀態 Bean
    User getUser(Long id) {       // id 是方法參數（每個執行緒棧幀各一份）
        return userDao.findById(id);  // 用的是區域變數和參數
    }
}
```

這個 Service 沒有可變的成員欄位（`userDao` 是注入的、實際不變的引用），方法用的都是參數和區域變數（執行緒隔離），所以多執行緒共享它完全安全。

**有可變狀態的 Bean 不安全**：

```java
@Service
class BadService {
    private User currentUser;   // 可變的成員欄位！危險
    void process(User u) {
        this.currentUser = u;   // 多執行緒會互相覆蓋
        // ... 用 this.currentUser 做事，可能已被別的執行緒改了
    }
}
```

多個請求並發呼叫 `process`，A 執行緒設的 currentUser 可能被 B 執行緒覆蓋，導致 A 後續用到的是 B 的資料——串號。

**如何保證執行緒安全**：

1. **首選：保持 Bean 無狀態**——不要有可變的成員欄位，需要的狀態放方法參數、區域變數。這是最好的做法（也是為什麼 Spring 敢用單例）。
2. **如果必須有狀態**：用 `ThreadLocal` 讓狀態執行緒隔離、或用同步機制（synchronized/鎖）保護、或改用 prototype/request 作用域讓每個執行緒/請求有自己的實例、或用 `Atomic`/並發容器保證原子性。

## 面試回答方式

先給明確結論——「單例 Bean 本身不保證執行緒安全，取決於有沒有可變的共享狀態」。這個「取決於」是關鍵，不能簡單說安全或不安全。用「無狀態 Service（安全）vs 有可變成員欄位的 Service（串號）」的對比說清楚。務必強調「絕大多數 Bean 設計成無狀態、所以單例共享沒問題」這個實務事實。保證安全的方法首推「保持無狀態」，其他（ThreadLocal、同步、改作用域）作為必須有狀態時的手段。能講清「為什麼無狀態就安全（參數/區域變數執行緒隔離）」，展現你理解執行緒安全的本質而非死記結論。

## 常見追問

### 為什麼無狀態的 Bean 即使被多執行緒共享也是安全的？

**核心答案**：因為無狀態 Bean 的方法在執行時，用到的資料都是「執行緒私有」的——方法參數和區域變數存在於每個執行緒各自的「虛擬機器棧」的棧幀裡（棧是執行緒私有的，見 JVM 記憶體結構題），不同執行緒呼叫同一個方法時，各有各的棧幀、各有各的參數和區域變數副本，完全不會互相干擾。而無狀態 Bean 沒有「可變的實例成員欄位」這種「多執行緒共享的資料」，所以不存在「多執行緒同時讀寫同一份資料」的競爭，自然就安全。安全的根源是「沒有共享的可變狀態」——共享的（Bean 實例本身）是不變的邏輯、可變的（參數/區域變數）是執行緒私有的。

**詳細解析**：這題把 Spring 執行緒安全和 JVM 記憶體模型串起來了。理解的關鍵是「什麼是共享的、什麼是私有的」——單例 Bean 實例本身是「共享的」（多執行緒都用這一個物件），但這個物件如果只有「方法邏輯」（方法的位元組碼（Bytecode）是唯讀的、共享沒問題）和「不變的引用欄位」（如注入的 DAO），就沒有「可變的共享狀態」。而方法執行時的參數、區域變數，是存在執行緒各自的棧幀裡的（棧是執行緒私有記憶體），A 執行緒呼叫 `getUser(1)` 和 B 執行緒呼叫 `getUser(2)`，它們的 `id` 參數、方法內的區域變數是各自獨立的、互不可見。所以雖然它們用的是同一個 UserService 實例，但實例本身沒有會被修改的共享狀態，方法執行又各用各的棧，就不會有競爭。執行緒安全問題只會發生在「多執行緒共享並修改同一份資料」時——無狀態 Bean 恰好沒有這種「共享的可變資料」，所以安全。理解這個「共享的不可變、可變的私有」的分析，展現你對執行緒安全和 JVM 記憶體模型的深入理解。

**面試回答方式**：講出核心——「無狀態 Bean 沒有可變的共享成員欄位、方法用的參數和區域變數在各執行緒私有的棧幀裡、不同執行緒互不干擾、所以沒有共享可變狀態的競爭」。能連結到「棧是執行緒私有的（JVM 記憶體結構）」，展現你把 Spring 執行緒安全和 JVM 記憶體模型串起來理解，是很有深度的回答。

### 如果 Service 需要保存請求相關的狀態，該怎麼辦？

**核心答案**：不應該把請求相關的狀態放到單例 Service 的成員欄位（會串號）。正確做法有幾種——（1）**透過方法參數傳遞**：把狀態作為參數在方法之間傳遞，不存到成員欄位（最簡單直接）；（2）**用 ThreadLocal**：如果狀態需要在一次請求的多個方法調用鏈中共享、又不想層層傳參，用 ThreadLocal 存放（執行緒隔離，每個請求執行緒各有一份），但務必在請求結束時 remove（見 ThreadLocal 記憶體洩漏（Memory Leak）題）；（3）**用 request 作用域的 Bean**：把這些請求狀態封裝到一個 `@Scope("request")` 的 Bean 裡，每個請求有自己的實例；（4）**Spring 內建的請求上下文**：如 `RequestContextHolder`、或安全上下文 `SecurityContextHolder`（底層也是 ThreadLocal）。

**詳細解析**：這是一個實務中常見的需求——「我需要在一次請求處理中共享一些狀態（如當前登入使用者、traceId、請求級的快取）」。錯誤的做法是放到單例 Service 的成員欄位（多請求並發會串號）。正確的思路都是「讓狀態的作用域和生命週期正確」——要嘛用參數顯式傳遞（狀態的生命週期就是方法調用，最清晰但可能要層層傳參）；要嘛用 ThreadLocal（狀態綁定到當前執行緒/請求，避免傳參，這也是 Spring 很多機制的做法——`RequestContextHolder` 存當前請求、`SecurityContextHolder` 存當前使用者、事務管理器用 ThreadLocal 存連線，都是這個模式），但要注意 ThreadLocal 在執行緒池（Thread Pool）場景必須 remove 避免洩漏和串號（見 [[../java-concurrency/008-threadlocal-memory-leak.md]]）；要嘛用 request 作用域 Bean（把請求狀態封裝成一個每請求一實例的 Bean，注入到需要的地方，透過 scoped proxy 路由到當前請求的實例）。核心原則是「絕不把請求級的可變狀態放到單例的成員欄位」。理解這幾種正確做法，展現你既知道單例的坑、又知道實務中如何正確處理請求狀態。

**面試回答方式**：先強調「不能放單例成員欄位（串號）」，再給出正確做法——「方法參數傳遞、ThreadLocal（記得 remove）、request 作用域 Bean、或用 Spring 的 RequestContextHolder/SecurityContextHolder」。能點出「Spring 自己很多機制（請求上下文、安全上下文、事務連線）都用 ThreadLocal 這個模式」，展現你理解正確處理請求狀態的方法及其在框架中的應用。

### Controller、Service、DAO 都是單例，這樣的分層架構為什麼沒有執行緒安全問題？

**核心答案**：因為在標準的分層架構中，Controller、Service、DAO 這些 Bean 都被設計成「無狀態」的——它們之間只有「注入的引用關係」（Controller 注入 Service、Service 注入 DAO，這些注入的引用在啟動後就不變了），而處理請求時的所有資料（請求參數、查詢結果、業務物件）都是透過「方法參數和返回值」在各層之間傳遞的，存在於各執行緒私有的棧幀中，不存到任何 Bean 的成員欄位。所以雖然這些 Bean 都是單例、被所有請求執行緒共享，但因為它們沒有可變的共享狀態、資料都在執行緒私有的調用棧裡流動，多執行緒並發處理不同請求時完全互不干擾，天然安全。

**詳細解析**：這題把單例、無狀態、分層架構串起來，揭示了為什麼「Spring 的分層架構敢全用單例」。標準分層的資料流是——請求進來，Controller 方法接收參數（棧幀私有），呼叫 Service 方法並傳參（新棧幀私有），Service 呼叫 DAO 傳參（又是私有棧幀），DAO 查詢返回結果（沿調用鏈返回，每層的返回值也在各自棧幀）。整個過程中，資料是「沿著方法調用鏈以參數/返回值的形式流動」的，全程待在執行緒私有的棧記憶體裡，從不寫入任何單例 Bean 的成員欄位。而各層 Bean 之間的關係（Controller 有一個 Service 引用、Service 有一個 DAO 引用）是啟動時注入好的、之後不變的唯讀引用。所以這些單例 Bean 都是「無狀態的處理器」——它們提供處理邏輯（方法），但不持有任何請求相關的可變狀態。多個請求並發時，就像多個執行緒同時呼叫一組無狀態的工具方法，各算各的、互不影響。這正是「無狀態 + 單例」這個組合的威力——既省了大量物件建立（單例共享），又天然執行緒安全（無狀態）。理解這個，展現你理解 Spring 分層架構執行緒安全的整體原理。

**面試回答方式**：講出「各層 Bean 都無狀態、之間只有不變的注入引用、請求資料全程以參數/返回值在調用鏈的私有棧幀中流動、不寫入任何成員欄位、所以單例共享也天然安全」。能提煉出「無狀態 + 單例 = 省物件建立又天然安全」這個組合的價值，展現你對 Spring 分層架構執行緒安全的系統性理解。
