# 題目

Spring Boot 的設定來源有哪些？它們的優先順序是怎麼決定的？

## 核心答案

Spring Boot 從**十幾個來源**讀取設定並合併成一個 `Environment`，**後面的來源覆蓋前面的**。由低到高的主要順序是：**打包在 JAR 裡的 `application.properties`／`yml`** → **JAR 裡的 profile 專屬設定**（`application-{profile}.yml`）→ **JAR 外部的 `application.yml`**（同目錄或 `config/` 子目錄）→ **JAR 外部的 profile 專屬設定** → **作業系統環境變數** → **Java 系統屬性**（`-D`）→ **命令列參數**（`--key=value`）→ **測試中的 `@TestPropertySource` 與 `properties` 屬性**。

**這個順序的設計意圖是「越接近部署現場的來源優先權越高」**——打包時寫死的預設值最低，部署時注入的環境變數與命令列參數最高。這讓同一個成品（artifact）可以部署到不同環境而不必重新打包，**是十二要素應用（Twelve-Factor App）原則在 Spring 裡的體現**。

`@Profile` 則控制**哪些 bean 會被註冊**，與設定值的覆蓋是兩件不同的事——前者決定「有沒有這個元件」，後者決定「這個值是多少」。

## 詳細解析

**優先序最常見的誤解是「外部檔案一定覆蓋內部」**。實際上還要看是不是 profile 專屬的——**JAR 外部的非 profile 設定，優先權低於 JAR 外部的 profile 專屬設定**，但兩者都高於 JAR 內部的對應項。排查「為什麼我的設定沒生效」時，最可靠的方法是用 Actuator 的 `/actuator/env` 端點，**它會顯示每個屬性的最終值與它來自哪個來源**。

**Profile 的濫用是一個常見問題**。用 `@Profile("prod")` 標註 bean 意味著**不同環境跑的是不同的程式碼路徑**——測試環境驗證過的東西，在生產環境可能根本沒被執行。**更好的做法是「同樣的程式碼、不同的設定值」**：一個 bean 讀取一個設定屬性來決定行為，而不是兩個 bean 各自實作。`@Profile` 應該保留給真正需要不同實作的情況（例如本機用記憶體佇列、生產用 Kafka），而且要清楚意識到它降低了測試覆蓋的代表性。

**設定的來源應該與敏感度匹配**。**非敏感的環境差異**（日誌級別、功能開關、逾時值）放設定檔或環境變數即可；**機密**（資料庫密碼、API 金鑰）**不該出現在設定檔或環境變數的明文中**——應該用 Kubernetes Secret（掛載成檔案）、Vault、或雲端的機密管理服務。**環境變數看起來安全但其實會出現在行程列表、崩潰轉儲與某些日誌裡**，這是一個常被忽略的洩漏面。

**設定的可觀測性也值得設計**：啟動時記錄關鍵設定的**來源與值**（機密要遮罩），能省下大量「為什麼這個環境行為不同」的排查時間。Spring Boot 的 `--debug` 會印出自動配置的判定報告，那是另一個很有價值但很少被用的診斷輸出。

## 面試回答方式

先給**優先序的原則**——「**越接近部署現場的來源優先權越高**」，這比背誦十幾個來源的順序有用得多，然後列出主要的幾層（JAR 內設定 → JAR 內 profile → JAR 外設定 → JAR 外 profile → 環境變數 → 系統屬性 → 命令列）。指出設計意圖是**同一個成品部署到不同環境不必重新打包**，是十二要素原則的體現。加分點有三個：排查「設定沒生效」用 **`/actuator/env` 看每個屬性的最終值與來源**；**`@Profile` 的濫用讓不同環境跑不同程式碼路徑**，降低測試覆蓋的代表性，更好的做法是「同樣的程式碼、不同的設定值」；以及**環境變數不適合放機密**——它會出現在行程列表、崩潰轉儲與某些日誌裡。

## 講稿

Spring Boot 從十幾個來源讀取設定並合併，後面的覆蓋前面的。我記的不是完整順序，而是背後的原則，越接近部署現場的來源優先權越高。

打包在 JAR 裡的設定最低，然後是 JAR 外部的設定檔，再來是環境變數、系統屬性，最高的是命令列參數。這個設計讓同一個成品可以部署到不同環境而不必重新打包。

排查設定沒生效的時候，最可靠的方法是用 Actuator 的環境端點，它會顯示每個屬性的最終值跟它來自哪個來源。

我想特別講一個常見問題，就是 Profile 的濫用。用 Profile 標註 bean 意味著不同環境跑的是不同的程式碼路徑，測試環境驗證過的東西，生產環境可能根本沒被執行。

更好的做法是同樣的程式碼、不同的設定值。一個 bean 讀取設定屬性來決定行為，而不是兩個 bean 各自實作。Profile 應該保留給真正需要不同實作的情況。

還有一點，環境變數看起來安全但其實會出現在行程列表跟崩潰轉儲裡，所以機密應該用專門的機密管理，而不是環境變數。

## 常見追問

### 設定變更要不要重啟才生效？

**核心答案**：**預設要**。`@Value` 與 `@ConfigurationProperties` 綁定的值在 bean 建立時就固定了，之後修改設定來源不會反映。要做到動態刷新有三條路：**Spring Cloud Config 加 `@RefreshScope`**（收到刷新事件時重建被標註的 bean）、**用 `Environment` 或 `ConfigurationProperties` 的 `getter` 每次讀取**（自己實作動態）、或者**外部的設定中心搭配監聽**（Nacos、Apollo 等）。

**詳細解析**：**動態刷新的複雜度常被低估**。`@RefreshScope` 是透過代理實現的——每次呼叫都檢查 bean 是否需要重建，這意味著**該 bean 的所有依賴關係都要重新建立**，如果它持有連線或執行緒池，重建的副作用可能很大。**而且刷新不是原子的**：多個 bean 的重建有先後，中間可能出現「一半新設定一半舊設定」的狀態。**所以務實的原則是：只讓真正需要動態的設定可刷新**（功能開關、限流閾值、日誌級別），基礎設施相關的設定（連線字串、執行緒池大小）寧可重啟。**在有滾動更新的環境下，重啟的成本其實不高，而動態刷新的正確性風險是持續存在的。**

**面試回答方式**：先給明確答案（預設要重啟）與三條動態化的路。重點放在**動態刷新的複雜度**：`@RefreshScope` 會重建整個依賴鏈、持有連線或執行緒池時副作用大、而且**刷新不是原子的**可能出現一半新一半舊。收在務實原則：**只讓真正需要動態的設定可刷新**（功能開關、限流閾值、日誌級別），基礎設施設定寧可重啟——在有滾動更新的環境下重啟成本不高，而動態刷新的正確性風險持續存在。

### 多個 profile 同時啟用時怎麼合併？

**核心答案**：`spring.profiles.active=a,b` 會**依序套用**，**後面的覆蓋前面的**。所以 `application-b.yml` 的值會蓋掉 `application-a.yml` 的同名屬性。Spring Boot 2.4 之後還引入了 `spring.config.activate.on-profile`（取代舊的多文件 `spring.profiles`）與 `spring.profiles.group`（把多個 profile 組成一組，啟用組名等於啟用全部）。

**詳細解析**：**2.4 的變更曾造成不少混亂**，因為它同時改變了設定檔的處理順序（從「profile 專屬的一律最後套用」改成「依文件出現順序」）。**升級時如果依賴了舊的覆蓋行為，可能靜默地讀到不同的值**——這是一個沒有錯誤訊息的破壞性變更。可以用 `spring.config.use-legacy-processing=true` 暫時回到舊行為（該選項已在後續版本移除），但正確的做法是理解新規則並調整。**這個案例的一般教訓是：設定的合併規則是框架的隱性契約，改變它的影響難以被測試發現**——所以升級時對設定行為的驗證應該包含「印出關鍵屬性的最終值並與升級前比對」。

**面試回答方式**：給合併規則（依序套用、後蓋前）與 2.4 之後的新語法。真正的加分點是指出 **2.4 的變更是一個沒有錯誤訊息的破壞性變更**——處理順序改變，依賴舊覆蓋行為的應用會靜默讀到不同的值。收在一般教訓：**設定的合併規則是隱性契約，改變它的影響難以被測試發現**，所以升級時應該印出關鍵屬性的最終值並與升級前比對。

### 設定應該放多少東西？

**核心答案**：判準是**「這個值會不會因環境而不同，或需要在不重新編譯的情況下調整」**。會的放設定（環境差異、功能開關、閾值、外部端點）；不會的**不要放**（業務規則、演算法參數、只有一種正確值的東西）。**過度設定化是一個真實的反模式**——每個常數都做成可設定的，結果是幾百個屬性沒有人知道該設什麼，預設值散落各處，而且大部分從未被改過。

**詳細解析**：過度設定化的成本很具體：**每個設定項都是一個需要文件、需要驗證、需要在各環境維護的東西**，而且它讓程式碼變得難讀（看不出實際會走哪條路）。更糟的是**它把設計決策推遲給了維運**——「這個值該設多少」如果連開發者都不知道，維運更不會知道。**好的預設值加上「必要時才可覆寫」比「什麼都可設」好得多。** 判斷一個設定項該不該存在，可以問：**過去一年有人改過它嗎？如果要改，誰知道該改成什麼？** 兩個問題都答不上來的設定項應該刪掉，把值寫死在程式碼裡並附上為什麼是這個值的註解。

**面試回答方式**：給明確判準（會不會因環境而不同、需不需要不重新編譯就調整）並點名**過度設定化是真實的反模式**。展開它的成本：每個設定項都要文件、驗證、跨環境維護，讓程式碼難讀，而且**把設計決策推遲給了維運**。收在兩個可操作的檢查問題：**過去一年有人改過它嗎？要改的話誰知道該改成什麼？** 都答不上來就該刪掉並寫死在程式碼裡附註解。
