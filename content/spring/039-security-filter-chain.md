# 題目

Spring Security 是怎麼運作的？請求進來之後經過哪些環節？

## 核心答案

它的本質是**一條 Servlet 過濾器鏈**，掛在 `DispatcherServlet` 之前。入口是一個註冊到 Servlet 容器的 **`DelegatingFilterProxy`**，它把請求委派給 Spring 容器裡名為 `springSecurityFilterChain` 的 bean——**這個間接讓安全過濾器能享有 Spring 的依賴注入與生命週期**，而不是被 Servlet 容器直接管理。

該 bean 是 **`FilterChainProxy`**，它持有多條 **`SecurityFilterChain`**，每條有自己的路徑匹配規則與過濾器清單。**請求進來時依序比對，只有第一條匹配的鏈會被執行**——這是最重要也最常被誤解的一點：**不會執行多條鏈**。

單條鏈裡的過濾器按固定順序執行，主要環節是：**`SecurityContextPersistenceFilter`**（從 session 或其他儲存恢復認證資訊）→ **各種認證過濾器**（表單登入、HTTP Basic、JWT 等，成功時把 `Authentication` 放進 `SecurityContextHolder`）→ **`ExceptionTranslationFilter`**（捕捉後續的認證與授權例外並轉成回應）→ **`AuthorizationFilter`**（依規則檢查當前使用者能不能存取這個路徑）。

## 詳細解析

**「只有第一條匹配的鏈被執行」造成了大量的設定困惑**。宣告兩條鏈，一條 `securityMatcher("/api/**")` 另一條沒有限定（匹配全部），如果後者的 `@Order` 較小，**它會搶先匹配所有請求，第一條永遠不會執行**。**排查方式是開啟 `logging.level.org.springframework.security=DEBUG`**，它會印出每個請求被哪條鏈處理、經過哪些過濾器、以及授權決策的結果——**這是排查 Security 問題最有效的單一手段**，卻經常被忽略。

**`SecurityContextHolder` 預設用 `ThreadLocal` 儲存當前的認證資訊**。這帶來兩個實務後果：**非同步執行緒拿不到它**（要用 `DelegatingSecurityContextExecutor` 或設定 `MODE_INHERITABLETHREADLOCAL`），以及**它必須在請求結束時被清除**（框架會做，但自訂的執行緒使用要注意）。**在反應式堆疊裡則完全不同**——用的是 Reactor Context 而非 ThreadLocal。

**認證與授權是兩個獨立的階段，混淆它們是常見的設計錯誤**。認證回答「你是誰」，產生一個 `Authentication` 物件（含身分與權限清單）；授權回答「你能不能做這件事」，依 `Authentication` 的權限與設定的規則做決策。**401 與 403 的區別正對應這兩者**——401 是「我不知道你是誰（或憑證無效）」，403 是「我知道你是誰，但你沒有權限」。**很多 API 把兩者都回 401 或都回 403，讓呼叫方無法判斷該重新登入還是該放棄。**

**過濾器鏈之外還有方法級的安全**（`@PreAuthorize`、`@PostAuthorize`），它透過 AOP 實現。**兩者的分工是：過濾器鏈做粗粒度的路徑保護，方法級做細粒度的業務授權**（例如「只能修改自己的訂單」）。**只用路徑保護是不夠的**——同一個端點的不同資料可能有不同的權限，那必須在業務層判斷。

## 面試回答方式

先給本質——**一條 Servlet 過濾器鏈**，入口是 `DelegatingFilterProxy` 把請求委派給 Spring 容器裡的 bean，**這個間接讓安全過濾器能享有依賴注入**。接著給 `FilterChainProxy` 持有多條鏈，並把最重要也最常被誤解的一點放前面：**只有第一條匹配的鏈會被執行，不會執行多條**，並給出排查手段——**開 `org.springframework.security=DEBUG`**，它會印出每個請求被哪條鏈處理、經過哪些過濾器、授權決策結果。列出單條鏈的主要環節（恢復上下文 → 認證 → 例外轉換 → 授權）。加分點有兩個：**認證與授權是兩個獨立階段**，401 與 403 正對應它們，而很多 API 混用讓呼叫方無法判斷該重新登入還是放棄；以及**過濾器鏈做粗粒度路徑保護、方法級做細粒度業務授權**，只用路徑保護不夠因為同一端點的不同資料可能有不同權限。

## 講稿

它的本質是一條 Servlet 過濾器鏈，掛在前端控制器之前。入口是一個註冊到容器的委派代理，把請求交給 Spring 容器裡的安全過濾器鏈 bean。這個間接讓安全過濾器能享有依賴注入跟生命週期。

那個 bean 持有多條安全過濾器鏈，每條有自己的路徑匹配規則。請求進來時依序比對，只有第一條匹配的鏈會被執行。這是最常被誤解的一點，不會執行多條。

所以如果宣告了兩條鏈，一條限定某個路徑、另一條匹配全部，而後者的順序比較前面，它會搶先匹配所有請求，第一條永遠不會執行。

排查這類問題最有效的手段是把 Security 的日誌級別開到 DEBUG。它會印出每個請求被哪條鏈處理、經過哪些過濾器、還有授權決策的結果。這一招很有效但經常被忽略。

單條鏈裡主要有四個環節，恢復認證上下文、認證、例外轉換、然後是授權。

還有一點，認證跟授權是兩個獨立階段。401 是我不知道你是誰，403 是我知道你是誰但你沒有權限。很多 API 兩者都回同一個，讓呼叫方無法判斷該重新登入還是放棄。

## 常見追問

### 自訂的過濾器該加在哪個位置？

**核心答案**：用 `addFilterBefore`、`addFilterAfter`、`addFilterAt` 相對於某個既有過濾器定位。**位置的選擇取決於它依賴什麼**：如果需要已認證的使用者資訊，必須加在認證過濾器**之後**；如果它自己做認證（例如 JWT 解析），應該加在 `UsernamePasswordAuthenticationFilter` 的位置或之前；如果它只是記錄或修改請求，可以加在最前面。

**詳細解析**：**最常見的錯誤是把 JWT 過濾器加錯位置**——加得太後面（在授權過濾器之後）會導致授權時還沒有認證資訊，一律被拒絕；加得太前面（在 `SecurityContextPersistenceFilter` 之前）則可能被後續的上下文恢復覆蓋掉。**正確的位置通常是 `UsernamePasswordAuthenticationFilter` 之前。** 另一個要點是**自訂過濾器應該繼承 `OncePerRequestFilter`**——它保證在一次請求中只執行一次，避免了轉發（forward）與非同步分派造成的重複執行。**「一個過濾器被執行了兩次」是很難察覺的問題**，因為它通常不會報錯，只是做了兩次工作（例如記錄兩筆日誌、扣了兩次額度）。

**面試回答方式**：給定位方法與**依賴決定位置**的原則（需要認證資訊就在認證之後、自己做認證就在認證過濾器之前）。重點展開最常見的錯誤：**JWT 過濾器加太後面會導致授權時沒有認證資訊而一律被拒**。加分點是**自訂過濾器應該繼承 `OncePerRequestFilter`**，避免轉發與非同步分派造成重複執行——而「被執行兩次」很難察覺，因為它不報錯只是做了兩次工作。

### 為什麼要有 DelegatingFilterProxy 這一層？

**核心答案**：因為 **Servlet 容器管理的過濾器不是 Spring bean**——它由容器直接實例化，無法注入依賴、無法享有 Spring 的生命週期、也無法被 AOP 處理。`DelegatingFilterProxy` 是一個由容器管理的**薄殼**，它在初始化時從 Spring 的 `WebApplicationContext` 裡查找同名的 bean，之後把每個請求委派給它。**這讓真正的安全邏輯完全活在 Spring 的世界裡。**

**詳細解析**：**這是一個通用的橋接模式**——凡是「外部框架要求你提供一個由它建立的物件，但你希望那個物件是 Spring bean」的場景，都可以用同樣的手法。**其他例子包括 `HandlerInterceptor` 的註冊、以及各種訊息中介軟體的監聽器適配**。**認出這個模式的價值在於：遇到「這個第三方框架的擴充點不支援依賴注入」時，知道可以自己寫一個委派層解決**，而不是把依賴變成靜態欄位或服務定位器。**它也解釋了為什麼 Spring 能與各種容器和框架整合得這麼好**——大量的整合其實就是這一層薄薄的委派。

**面試回答方式**：給出直接理由——**容器管理的過濾器不是 Spring bean，無法注入依賴與享有生命週期**，`DelegatingFilterProxy` 是一個由容器管理的薄殼，委派給 Spring 裡的 bean。真正的加分點是認出這是**通用的橋接模式**，並舉其他例子（HandlerInterceptor 註冊、訊息監聽器適配）。收在實用價值：遇到「第三方擴充點不支援依賴注入」時，知道可以自己寫委派層，而不是退回靜態欄位或服務定位器。

### 方法級授權的 SpEL 表達式有什麼要注意的？

**核心答案**：三點。**它在執行期求值，錯誤只在被呼叫時才發現**——一個打錯字的屬性名不會在啟動時報錯，而是在某個請求上拋例外（或更糟，靜默地回傳 false 導致拒絕存取）。**效能**——複雜的表達式（尤其是呼叫其他 bean 的方法查資料庫）在每次方法呼叫時都執行。**它是 AOP 實現的，所以同類別內部呼叫不生效**——與 `@Transactional` 完全相同的限制。

**詳細解析**：**「表達式錯誤在執行期才發現」是用字串表達邏輯的共同代價**。緩解方式有兩個：**為授權規則寫測試**（用不同角色的使用者呼叫，驗證允許與拒絕的行為），以及**把複雜邏輯抽成一個 bean 的方法**（`@PreAuthorize("@orderSecurity.canModify(#orderId, authentication)")`），這樣邏輯是 Java 程式碼（有編譯檢查、可以單元測試、IDE 能重構），表達式只負責分派。**後者是實務上很推薦的做法**——它保留了註解的宣告性，同時把邏輯放回型別安全的世界。**這是一個通用的技巧：當宣告式機制需要複雜邏輯時，讓宣告只做分派，邏輯放在程式碼裡。**

**面試回答方式**：給三點（執行期求值、效能、AOP 的自呼叫限制）。重點展開第一點並給出解法：**為授權規則寫測試**、以及**把複雜邏輯抽成 bean 方法**讓表達式只負責分派——這樣邏輯有編譯檢查、可單元測試、IDE 能重構。收在通用技巧：**宣告式機制需要複雜邏輯時，讓宣告只做分派、邏輯放在程式碼裡**。
