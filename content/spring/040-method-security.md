# 題目

`@PreAuthorize` 與 `@Secured` 差在哪？權限模型該怎麼設計？

## 核心答案

`@Secured` 是舊的、只支援**角色清單**的註解（`@Secured("ROLE_ADMIN")`），語意是「使用者具有這些角色之一」。`@PreAuthorize` 支援**完整的 SpEL 表達式**，可以引用方法參數（`#orderId`）、當前的 `authentication` 物件、以及任意的 bean 方法——**表達能力強得多**，所以是現在的預設選擇。另外還有 `@PostAuthorize`（在方法執行後依**回傳值**決定是否放行，適合「只能看自己的資料」這類需要先查出來才能判斷的情況）與 `@PreFilter`／`@PostFilter`（過濾集合中的元素）。

權限模型的核心設計判斷是**「角色」與「權限」要分開**。角色（`ROLE_ADMIN`）是**給人看的分組**，權限（`order:write`）是**程式碼實際檢查的細粒度能力**。**程式碼應該檢查權限而不是角色**——這樣新增一個角色或調整角色的能力範圍時，不必修改任何程式碼。角色到權限的映射放在資料或設定裡。

**只檢查角色是最常見的設計問題**：`@PreAuthorize("hasRole('ADMIN')")` 散落各處之後，新增一個「只能看報表的管理員」就必須改動所有相關的註解。

## 詳細解析

**`@PostAuthorize` 的代價要理解**：它在方法**執行完之後**才檢查，所以**方法的副作用已經發生了**。用它保護一個會修改資料的方法是錯的（資料已經改了才發現沒權限，而且如果沒有交易包住，改動不會被回滾）。**它只適合唯讀的查詢**，而且要注意「查出來才發現不能看」在資料量大時是浪費。**更好的做法通常是把權限條件下推到查詢裡**（`WHERE owner_id = :currentUserId`），這樣既安全又不浪費。

**細粒度授權經常需要「這筆資料是不是他的」**，這無法只靠角色與權限表達。做法有三種：**在查詢時加上擁有者條件**（最推薦，安全且高效）、**用 `@PostAuthorize` 檢查回傳值**（簡單但有前述問題）、**用 Spring Security 的 ACL 模組**（功能完整但複雜度高，維護一張物件層級的權限表）。**大多數系統用第一種就夠了**，ACL 只在真的有複雜的物件層級分享需求時才值得。

**權限檢查應該放在哪一層是一個設計判斷**。放在控制器層貼近入口、容易看出端點的保護；放在服務層則能保護所有呼叫路徑（包含來自訊息佇列、定時任務、以及其他服務的呼叫）。**推薦放在服務層**——因為控制器只是眾多入口之一，把安全放在只有一個入口會保護到的地方是脆弱的。**這與「驗證放哪一層」是同一類判斷：安全檢查應該放在所有路徑都會經過的地方。**

**測試授權規則是常被跳過的一步**。Spring Security 提供了 `@WithMockUser` 與 `@WithSecurityContext` 讓測試可以模擬不同身分，**應該為每個受保護的方法至少寫一個「有權限」與一個「無權限」的測試**。**授權是少數「沒有測試就等於沒有保證」的功能**——它的失效不會造成錯誤，只會安靜地放行不該放行的請求，而那可能很久都沒有人發現。

## 面試回答方式

先給兩者的差別（`@Secured` 只支援角色清單、`@PreAuthorize` 支援完整 SpEL 因而是預設選擇）並補上 `@PostAuthorize` 與過濾註解。接著把重心放在**權限模型的核心設計判斷：角色與權限要分開**——角色是給人看的分組、權限是程式碼實際檢查的細粒度能力，**程式碼應該檢查權限**，這樣新增角色時不必改程式碼。指出**只檢查角色是最常見的設計問題**並用「新增一個只能看報表的管理員」說明後果。加分點有三個：**`@PostAuthorize` 在方法執行後才檢查，副作用已經發生**，只適合唯讀且大資料量時浪費，**更好的做法是把權限條件下推到查詢裡**；**權限檢查該放服務層而非控制器層**，因為控制器只是眾多入口之一；以及**授權是「沒有測試就等於沒有保證」的功能**——失效不會報錯，只會安靜地放行。

## 講稿

舊的那個只支援角色清單，語意是使用者具有這些角色之一。新的支援完整的表達式，可以引用方法參數、當前的認證物件、還有任意 bean 的方法，表達能力強得多，所以是現在的預設選擇。

權限模型我認為核心的設計判斷是角色跟權限要分開。角色是給人看的分組，權限是程式碼實際檢查的細粒度能力。程式碼應該檢查權限而不是角色，這樣新增一個角色或調整角色的能力範圍時，不必修改任何程式碼。

只檢查角色是最常見的設計問題。角色判斷散落各處之後，新增一個只能看報表的管理員，就必須改動所有相關的註解。

還有一個容易誤用的地方。方法執行後才檢查的那個註解，是在方法跑完之後才判斷，所以副作用已經發生了。用它保護會修改資料的方法是錯的。它只適合唯讀查詢，而且資料量大的時候是浪費。更好的做法通常是把權限條件下推到查詢裡。

權限檢查我會放在服務層而不是控制器層，因為控制器只是眾多入口之一，還有訊息佇列跟定時任務。把安全放在只有一個入口會經過的地方是脆弱的。

## 常見追問

### 為什麼 Spring Security 的角色要加 ROLE_ 前綴？

**核心答案**：因為它內部**用同一個機制表示角色與權限**——都是 `GrantedAuthority` 的字串。`hasRole('ADMIN')` 實際上檢查的是 `ROLE_ADMIN` 這個 authority，**前綴是用來區分「這是一個角色」與「這是一個細粒度權限」的慣例**。`hasAuthority('ROLE_ADMIN')` 與 `hasRole('ADMIN')` 完全等價。

**詳細解析**：**這個設計造成了大量混淆**——使用者常常在資料庫裡存了 `ADMIN` 卻用 `hasRole('ADMIN')` 檢查，結果永遠不通過（因為框架去找 `ROLE_ADMIN`）。**前綴可以透過 `GrantedAuthorityDefaults` bean 修改，但更好的做法是理解它並保持一致。** 更深層地看，**這個「用命名慣例區分兩種概念」的設計不理想**——如果一開始就把角色與權限做成兩個不同的型別，就不會有這個問題。**但它反映了一個真實的權衡：統一的表示讓授權檢查的實作簡單（只要比對字串集合），代價是語意上的區分只能靠慣例維持。** 認出這種「為了實作簡潔而犧牲型別區分」的取捨，在設計自己的權限系統時很有參考價值。

**面試回答方式**：給出機制——**內部用同一個機制表示角色與權限，前綴是區分的慣例**，並指出 `hasRole('ADMIN')` 等價於 `hasAuthority('ROLE_ADMIN')`。給出最常見的混淆（資料庫存 `ADMIN` 卻用 `hasRole` 檢查而永遠不通過）。加分點是評價這個設計：**用命名慣例區分兩種概念不理想**，但它反映了「統一表示讓實作簡單、代價是語意區分只能靠慣例」的真實權衡。

### 多租戶系統的授權該怎麼設計？

**核心答案**：核心是**把租戶識別碼變成每一次資料存取的隱含條件**，而不是靠每個查詢自己記得加 `WHERE tenant_id = ?`。做法有三層：**在認證階段把租戶 ID 放進 `Authentication` 的細節或安全上下文**、**在資料存取層自動套用租戶過濾**（Hibernate 的 `@Filter`、MyBatis 的攔截器、或資料庫的 row-level security）、**在必要時加上明確的檢查**（跨租戶操作的白名單）。

**詳細解析**：**「靠每個查詢自己記得」是必然會失敗的策略**——只要有一個查詢忘了加條件，就是跨租戶的資料洩漏，而這種漏洞在正常測試中不會被發現（因為測試通常只用一個租戶的資料）。**防護必須在一個所有查詢都會經過的地方**，這與「安全檢查放在所有路徑都經過的地方」是同一個原則。**資料庫層級的 row-level security 是最徹底的**——即使應用程式碼有錯，資料庫也會拒絕。代價是它與連線池的互動需要處理（連線是共用的，每次借出時要設定當前租戶）。**測試上應該有專門的「跨租戶存取」測試**：用租戶 A 的身分嘗試存取租戶 B 的資料，驗證被拒絕。**這類負面測試是多租戶系統的必要投資。**

**面試回答方式**：給核心原則——**把租戶識別碼變成每次資料存取的隱含條件**，而非靠每個查詢記得加。給三層做法。重點強調**「靠每個查詢自己記得」必然失敗**：一個遺漏就是跨租戶洩漏，而正常測試不會發現（只用一個租戶的資料）。加分點是提出**資料庫層級的 row-level security 最徹底**（應用有錯資料庫也會拒絕）與它的代價（連線池共用時要每次設定當前租戶），以及**專門的跨租戶負面測試是必要投資**。

### 授權規則多了之後怎麼維護？

**核心答案**：三個做法。**集中定義權限常數**——不要在註解裡散落字串，用一個 `Permissions` 類別的常數（或列舉），這樣重新命名時 IDE 能處理、也能看出總共有哪些權限。**把複雜規則抽成 bean 方法**——`@PreAuthorize("@orderSecurity.canModify(#id, authentication)")`，邏輯回到型別安全的 Java。**建立權限清單的文件或測試**——列出所有權限、哪些角色有它、以及哪些端點需要它。

**詳細解析**：**「權限矩陣的可見性」是大型系統的真實痛點**。當授權規則散落在幾百個註解裡時，回答「誰能做什麼」需要通讀程式碼——而這個問題在稽核、權限調整、以及安全審查時經常被問到。**一個有效的做法是寫一個測試或工具掃描所有 `@PreAuthorize` 註解並生成矩陣**，把它輸出成文件的一部分。**這讓權限模型從「散落在程式碼裡的隱性知識」變成「可檢視的資產」。** 同樣的思路適用於 API 端點清單、設定項清單、以及事件類型清單——**凡是散落在程式碼裡卻需要整體檢視的東西，都值得用工具生成一份總覽**。

**面試回答方式**：給三個做法（集中常數、複雜規則抽成 bean 方法、建立權限清單）。真正的加分點是點出**「權限矩陣的可見性」是大型系統的真實痛點**——散落在幾百個註解裡時，回答「誰能做什麼」要通讀程式碼，而稽核與安全審查經常問這個。給出解法：**寫工具掃描所有註解生成矩陣**，讓權限模型從隱性知識變成可檢視的資產。收在一般化：凡是散落在程式碼裡卻需要整體檢視的東西，都值得用工具生成總覽。
