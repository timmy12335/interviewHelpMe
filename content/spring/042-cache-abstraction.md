# 題目

`@Cacheable` 是怎麼運作的？有哪些容易踩的陷阱？

## 核心答案

它是**基於 AOP 的宣告式快取**：方法被代理，呼叫時先用鍵去 `CacheManager` 查，命中就直接回傳、不執行方法；未命中則執行方法並把結果放進快取。相關註解還有 `@CachePut`（一定執行方法並更新快取）、`@CacheEvict`（清除）、以及 `@Caching`（組合多個）。

陷阱有五個，每一個都很常見。**自呼叫失效**——同類別內部呼叫不經過代理，快取完全不生效，與 `@Transactional` 完全相同的問題。**鍵的生成**——預設的 `SimpleKeyGenerator` 用所有參數組成鍵，**參數是物件時依賴它的 `equals` 與 `hashCode`**，沒有正確實作就會出現詭異的命中或不命中。**null 值的處理**——預設會快取 null，這通常是好的（避免快取穿透），但要意識到它；`unless = "#result == null"` 可以關掉。**沒有 TTL**——Spring 的抽象**不提供統一的過期設定**，必須在具體實作（Caffeine、Redis）的設定裡指定。**交易的互動**——`@CacheEvict` 預設在方法**返回時**執行，如果交易之後回滾了，快取已經被清掉（或更糟，`@CachePut` 已經寫進了未提交的值）。

## 詳細解析

**「Spring 的快取抽象不管過期」是最需要理解的一件事**。這個抽象只定義了 `get`、`put`、`evict` 這幾個操作，**TTL、最大容量、淘汰策略全部是實作特有的**。所以用 Caffeine 時要在 `spring.cache.caffeine.spec` 裡寫 `maximumSize=1000,expireAfterWrite=10m`，用 Redis 則在 `RedisCacheConfiguration` 裡設。**忘記設定的後果是快取無限成長或永不過期**——前者導致記憶體問題，後者導致資料永遠不更新。**「加了 `@Cacheable` 但沒設過期」是一個很常見的生產問題。**

**交易與快取的互動需要明確決定**。預設情況下 `@CacheEvict` 在方法返回時立即執行；如果那個方法在一個交易裡而交易之後回滾，**快取已經被清除，下一次查詢會從資料庫載入舊值再放進快取**——結果是快取與資料庫暫時不一致（雖然這種不一致通常會自癒）。更危險的是 `@CachePut` 寫入了一個未提交的值，回滾之後**快取裡是一筆根本不存在的資料**。**解法是設定 `beforeInvocation` 或使用交易感知的 `CacheManager`（`TransactionAwareCacheManagerProxy`），讓快取操作延遲到交易提交之後。**

**快取鍵的設計比想像中重要**。用 `key = "#user.id"` 這類 SpEL 明確指定，比依賴預設的生成器可靠得多——**預設生成器在方法簽章改變時（多一個參數）會產生完全不同的鍵，導致快取靜默失效**。而且明確的鍵讓「這個快取存了什麼」在程式碼裡可讀。**在分散式快取（Redis）上還要注意鍵的命名空間**，避免不同服務或不同版本的資料互相衝突。

**最根本的判斷是「這個資料適不適合快取」**。適合的是：**讀多寫少、可以容忍短暫過期、計算或查詢成本高**。不適合的是：**寫入頻繁（快取不斷失效，維護成本超過收益）、要求強一致（快取天生是弱一致的）、或者資料量大而命中率低**（快取只是浪費記憶體）。**在加快取之前先量測「這個查詢真的是瓶頸嗎」與「預期命中率是多少」**——很多快取加上去之後命中率只有 20%，帶來的複雜度遠超收益。

## 面試回答方式

先給機制（AOP 代理、命中就不執行方法）與相關註解。接著給**五個陷阱**，每個一句：自呼叫失效、鍵的生成依賴 `equals`／`hashCode`、null 值預設會被快取、**沒有統一的 TTL 設定**、以及交易回滾與快取操作的時序問題。把 **「抽象不管過期」單獨強調**——TTL、容量、淘汰策略全是實作特有的，**忘記設定會導致快取無限成長或永不過期**，這是很常見的生產問題。加分點有兩個：**交易回滾後 `@CachePut` 可能讓快取裡存著根本不存在的資料**，解法是用交易感知的 `CacheManager`；以及**用 SpEL 明確指定鍵**比依賴預設生成器可靠——後者在方法簽章改變時會產生不同的鍵導致快取靜默失效。最後給根本判斷：**加快取前先量測這個查詢是不是瓶頸、預期命中率多少**。

## 講稿

它是基於 AOP 的宣告式快取。方法被代理，呼叫時先用鍵去查，命中就直接回傳不執行方法，未命中才執行並把結果放進快取。

陷阱有五個。自呼叫失效，同類別內部呼叫不經過代理，跟交易註解完全一樣的問題。鍵的生成，預設用所有參數組成，參數是物件時依賴它的 equals 跟 hashCode。null 值預設會被快取。沒有統一的過期設定。還有交易的互動。

我覺得最需要理解的是這個抽象不管過期。它只定義了取、放、清除這幾個操作，過期時間、最大容量、淘汰策略全部是實作特有的。所以忘記設定的後果是快取無限成長或永不過期。加了註解但沒設過期，是很常見的生產問題。

交易的互動也要明確決定。清除快取預設在方法返回時就執行，如果交易之後回滾了，快取已經被清掉。更危險的是更新快取的註解寫入了一個未提交的值，回滾之後快取裡是一筆根本不存在的資料。解法是用交易感知的快取管理器，讓快取操作延遲到提交之後。

最後我想說，加快取之前要先量測這個查詢真的是瓶頸嗎、預期命中率是多少。很多快取加上去命中率只有兩成，複雜度遠超收益。

## 常見追問

### 快取與資料庫的一致性該怎麼處理？

**核心答案**：**接受最終一致並縮短不一致的窗口**，而不是追求強一致。常見的策略是 **Cache-Aside**（讀時未命中就查庫並回填、寫時更新資料庫並刪除快取）。**刪除而非更新**是重要的細節——更新快取需要與資料庫的寫入保持順序（併發下可能出現舊值覆蓋新值），而刪除是冪等的、順序無關的，下次讀取自然會載入新值。

**詳細解析**：**「先更新資料庫再刪快取」與「先刪快取再更新資料庫」都有競態窗口**，但前者的窗口小得多（只在「讀取到舊值」與「寫回快取」之間），所以是主流選擇。**要進一步縮短窗口可以用延遲雙刪**（更新後隔一小段時間再刪一次）或**訂閱資料庫的變更日誌**（binlog 或 CDC）來驅動快取失效——後者是最可靠的，因為它保證了「資料庫變了、快取一定會被通知」，而不依賴應用程式碼記得刪。**判斷用哪一種取決於「不一致能容忍多久」**：幾秒可以接受就用簡單的 cache-aside，要求近即時就上 CDC。**而如果答案是「完全不能不一致」，那就不該用快取**——強一致與快取在本質上是衝突的。

**面試回答方式**：給明確立場——**接受最終一致並縮短窗口**，並說明 Cache-Aside 的流程。重點解釋**為什麼是刪除而非更新**：更新需要與資料庫寫入保持順序（併發下舊值可能覆蓋新值），刪除是冪等且順序無關的。加分點是給出縮短窗口的手段（延遲雙刪、CDC 驅動失效）並指出 **CDC 最可靠因為它不依賴應用記得刪**。收在判斷：容忍幾秒用簡單方案、要求近即時上 CDC、**完全不能不一致就不該用快取**。

### 為什麼 Spring 的 Cache 抽象這麼薄？

**核心答案**：因為**各家快取實作的差異太大，能被統一的只有交集**。本地快取（Caffeine）與分散式快取（Redis）在過期精度、淘汰策略、原子操作、批次能力、以及失敗語意上都完全不同——**強行統一這些會產生一個在每個實作上都不完整的介面**。Spring 選擇只統一最核心的操作，其餘交給實作特有的設定。

**詳細解析**：**代價是「可替換性」其實有限**。理論上換掉 `CacheManager` 就能從 Caffeine 換成 Redis，但**實際上兩者的行為差異大到程式碼可能需要調整**——本地快取的存取是奈秒級且不會失敗，Redis 是毫秒級且可能逾時或連線失敗；本地快取每個實例一份（不一致但快），Redis 共享（一致但有網路成本）。**所以「用抽象換取可替換性」在這裡是打折的**——真正的價值反而是**統一的程式設計模型**（不管底層是誰，宣告式快取的寫法一樣）與**測試時可以換成簡單實作**。**認出「這個抽象的真實價值是什麼」比預設它提供了完整的可替換性重要**，因為後者會讓人在切換時措手不及。

**面試回答方式**：給根本原因——**各家實作差異太大，能統一的只有交集**，強行統一會產生在每個實作上都不完整的介面。真正的加分點是誠實評估**可替換性其實有限**：本地快取奈秒級不會失敗、Redis 毫秒級可能逾時，行為差異大到程式碼可能要調整。收在重新定位抽象的真實價值：**統一的程式設計模型與測試時可換簡單實作**，而不是完整的可替換性——認清這點才不會在切換時措手不及。

### 多級快取該怎麼設計？

**核心答案**：典型是**本地快取（L1）加分散式快取（L2）**：讀取先查本地、未命中查 Redis、再未命中才查資料庫，並逐層回填。好處是**熱點資料的存取完全不走網路**，大幅降低延遲與 Redis 的負載。**核心難題是本地快取的失效**——每個實例有自己的一份，資料變更時必須通知所有實例。

**詳細解析**：**通知機制有三種**：**訊息廣播**（用 Redis 的 pub/sub 或訊息佇列，資料變更時廣播失效訊息，所有實例收到後清除本地快取）、**短 TTL**（本地快取設一個很短的過期時間如 30 秒，接受最多 30 秒的不一致，最簡單）、**版本號**（本地快取存版本，每次讀取時檢查 Redis 的版本，變了就重新載入——但這樣就沒省掉網路往返）。**實務上「短 TTL」的性價比最高**——它不需要任何額外機制，而多數場景能接受幾十秒的不一致。**只有在「不一致的代價很高」且「熱點集中」時，才值得引入廣播機制的複雜度。** 要注意廣播本身也不可靠（訊息可能丟失、實例可能剛好在重啟），**所以即使有廣播，也應該同時設一個保底的 TTL**——這是「不要讓正確性依賴單一機制」的一般原則。

**面試回答方式**：給架構（L1 本地 + L2 分散式、逐層回填）與好處，並點出**核心難題是本地快取的失效**。給三種通知機制並明確推薦：**短 TTL 性價比最高**，不需額外機制且多數場景能接受幾十秒不一致。收在一個重要提醒：**廣播本身也不可靠**（訊息會丟、實例會重啟），所以即使有廣播也應該同時設保底 TTL——這是「不要讓正確性依賴單一機制」的一般原則。
