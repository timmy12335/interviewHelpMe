# 題目

TypeScript 7 用 Go 重寫了編譯器。這對日常開發實際上改變了什麼？

## 核心答案

**它改的是速度，不是型別系統**。型別檢查的語意與 6.0 相容——**同樣的程式碼、同樣的錯誤**；變的是那些錯誤出現得多快。

**實測的量級是八到十二倍**：VS Code 自身的專案快 11.9 倍、Sentry 8.9 倍、Bluesky 8.7 倍，記憶體同時降了 6% 到 26%。**編輯器裡的感受最直接**——VS Code 開一個有錯誤的檔案從 17.5 秒降到 1.3 秒以內。

**速度來自三件事**：從 JavaScript 換成原生程式碼、共享記憶體的多執行緒（解析、型別檢查、產出可以並行）、以及重寫過的檔案監看。

而代價相當具體，升級前必須先確認：Vue、Svelte、Astro、MDX、Angular 樣板這些「把 TS 嵌在別的語言裡」的工具還不能用（它們依賴的程式化 API 要到 7.1 才有）；**移除了 ES5 目標、AMD/UMD 模組、classic 模組解析**；JavaScript 的支援也重做過，不再支援 Closure 風格的註解語法。

**用法沒變**——仍然是 `npm install -D typescript` 加 `npx tsc`。

## 詳細解析

**6.0 是為了 7.0 而存在的過渡版**，理解這一點才知道升級路徑該怎麼走。6.0 仍然是 JavaScript 寫的，但它把預設值改成現代的樣子（`strict` 預設開、`module` 預設 `esnext`、`target` 預設 `es2025`、`types` 預設空陣列），並把 7.0 要移除的選項標成廢棄。所以正確的順序是 5.x → 6.0 把警告清乾淨 → 7.0，官方還提供了 `ts5to6` 這個工具處理設定的機械調整。直接從 5.x 跳 7.0，會把「預設值變了」與「選項不存在了」兩類問題混在一起。

「嵌入式語言的工具還不支援」是這次升級最現實的阻擋點。如果你的專案是 Vue 或 Svelte，那不論編譯器多快都還輪不到你——而這類框架佔前端專案的比例不低。所以評估時第一件事不是跑效能測試，是確認你的框架在不在支援清單上。

十倍的意義在超過某個門檻之後會質變。型別檢查從三十秒降到三秒，不只是省下二十七秒——它讓「存檔就檢查」從不可行變成可行，於是錯誤在寫的當下就出現而不是在 CI 上。這和前面談過的回饋週期是同一件事（見 [[043-frontend-testing-layers.md]]）：速度跨過某個界線時，改變的是工作方式而不只是等待時間。

但它不會讓你的建置整體快十倍。型別檢查只是建置的一部分，打包、轉譯、壓縮各有自己的成本（見 [[027-bundling-and-code-splitting.md]]）——而很多專案早就用 esbuild 或 SWC 跳過了 tsc 的產出、只把它當型別檢查器用。那些專案感受到的是 CI 檢查與編輯器變快，而不是產出變快。

## 面試回答方式

先講清楚**它改的是速度而非型別系統**——語意與 6.0 相容，同樣的程式碼同樣的錯誤。給實測量級（八到十二倍、記憶體降兩成上下）並用編輯器的體感說明。加分點有四個：**6.0 是為 7.0 存在的過渡版**，所以順序是 5.x → 6.0 清警告 → 7.0；**嵌入式語言的工具還不支援**是最現實的阻擋點，Vue、Svelte 專案還輪不到；**速度跨過門檻會質變**——存檔就檢查從不可行變成可行；以及**它不會讓整體建置快十倍**，因為很多專案早就只把 tsc 當型別檢查器。

## 講稿

它改的是速度，不是型別系統。型別檢查的語意跟六點零相容，同樣的程式碼、同樣的錯誤，變的是錯誤出現得多快。

實測大概八到十二倍。VS Code 自己的專案是十一點九倍，記憶體同時降了兩成左右。編輯器裡的感受最直接，開一個有錯誤的檔案從十七秒半降到一點三秒以內。

快的原因有三個。從 JavaScript 換成原生程式碼、共享記憶體的多執行緒、還有重寫過的檔案監看。

但代價很具體。Vue、Svelte、Astro 這些把 TypeScript 嵌在別的語言裡的工具還不能用，因為它們依賴的程式化 API 要到七點一才有。所以評估時第一件事不是跑效能測試，是確認你的框架在不在支援清單上。

升級路徑我會走五點 x 到六點零再到七點零。六點零是為了七點零而存在的過渡版，它把預設值改成現代的樣子，並且把七要移除的選項標成廢棄。在六點零把警告清乾淨再跳，比直接跳過去好歸因。

## 常見追問

### 型別檢查快十倍，對團隊實際的收益在哪？

**核心答案**：在回饋週期，而不在等待時間的總和。最大的收益是**編輯器**——在大型專案裡，型別提示與錯誤標示原本會延遲好幾秒甚至卡住，那讓人傾向不看它；變快之後型別系統才真正在「寫的當下」發揮作用。**其次是 CI**：型別檢查那一關從幾分鐘變成幾十秒，讓 PR 的回饋更快。

**詳細解析**：這考察**「工具的速度會改變人的行為」**這個常被低估的效應——慢到某個程度的檢查，人會繞過它（跳過 pre-commit hook、不等 CI 就切去做別的事、把型別錯誤留到最後一起處理）；而快到某個程度，它就變成無感的背景動作。所以效能改善的價值不能只用「省下的秒數乘上次數」來估算，那會嚴重低估它。**同樣的道理適用於測試套件**：跑十分鐘的測試沒有人在本機跑，跑十秒的每次存檔都會跑——而後者抓到問題的時機早得多。能把工具效能連到行為改變而不只是時間節省，是這題比較有深度的答案。

**面試回答方式**：給兩個收益（編輯器、CI）並指出收益在回饋週期而非等待時間的總和。核心加分點是**工具的速度會改變人的行為**——慢到某個程度人會繞過檢查，快到某個程度它變成無感的背景動作，所以不能只用「秒數乘次數」估算。收在類比：測試套件也一樣，跑十分鐘沒人在本機跑，跑十秒的每次存檔都會跑。

### 用 Go 重寫，會不會有行為不一致的風險？

**核心答案**：有，但團隊用「照著移植而不是重新設計」的方式把風險壓到最低。整個程式碼庫是結構與邏輯逐段對應地移植過去的，不是拿規格重寫一個新編譯器——所以差異來自移植的疏漏而非設計的分歧，這類問題容易被大規模的實測比對抓出來。官方也把「與 6.0 的行為相容」當成明確的目標。

**詳細解析**：這考察「重寫的兩種策略風險完全不同」——**照著移植**保留了原本累積的所有邊界情況處理，缺點是也繼承了原本的設計限制；**重新設計**能修正舊決策，但等於要把十年份的邊界情況重新踩一遍。編譯器這種「行為的細節就是規格」的軟體，幾乎一定該選前者——因為它的正確性定義就是「和舊版一樣」。這個判斷可以推廣：當既有系統的行為本身就是契約時，重寫要優先保證等價而非優先改善設計（見 [[../behavioral/010-taking-over-legacy-system.md]]）。**而驗證的方式也隨之確定**：拿大量真實專案跑新舊兩版比對輸出，而不是寫新的測試。

**面試回答方式**：給答案（有風險，但照著移植把它壓到最低）並說明差異來自移植疏漏而非設計分歧。核心加分點是重寫的兩種策略風險完全不同——照著移植 vs 重新設計各自繼承什麼，而編譯器這種「行為的細節就是規格」的軟體幾乎一定該選前者。收在推廣：當既有行為本身就是契約時，重寫要優先保證等價，而驗證方式是新舊比對而非寫新測試。

### 現在該升嗎？

**核心答案**：先確認三件事，任何一件不過就先不要。**你的框架支不支援**（Vue、Svelte、Astro、Angular 樣板目前還不行）；**有沒有用到被移除的設定**（ES5 目標、AMD/UMD、classic 模組解析）；**有沒有工具依賴程式化 API**（自訂的 lint 規則、程式碼產生器——那要等 7.1）。三件都過的話，升級的成本其實很低，因為型別檢查的行為沒變。

**詳細解析**：這考察「大版本升級的評估該從阻擋點開始而非從收益開始」——收益是已知的（快十倍），所以真正要花時間確認的是「有沒有東西擋著」；先算收益再發現被擋住，那個評估就白做了。而這三項的檢查成本都很低：看框架的支援公告、掃一遍 `tsconfig.json`、盤點依賴 TypeScript API 的工具，加起來大概一個小時。這個「先花一小時確認可行性，再決定要不要花一週」的順序，在任何升級評估中都適用——而它也對應到前面談過的「先確認阻擋點」這個習慣（見 [[049-frontend-tech-selection.md]]）。

**面試回答方式**：給三個要先確認的阻擋點（框架支援、被移除的設定、程式化 API），並指出三項都過的話成本很低因為行為沒變。核心加分點是評估該從阻擋點開始而非從收益開始——收益已知，先算收益再發現被擋住等於白做。收在通用做法：先花一小時確認可行性，再決定要不要花一週。
