# 題目

樂觀更新怎麼實作？失敗與衝突要怎麼處理？

## 核心答案

樂觀更新是「先假設成功並立刻更新畫面，等伺服器確認或失敗再修正」——它的價值是消除等待，讓按讚、勾選、拖曳排序這類操作感覺是瞬間的。

**實作的四個步驟**：**取消進行中的相關請求**（避免它們回來覆蓋你的樂觀值）、**保存當前的快取快照**、**寫入樂觀的值**、在失敗時用快照回滾並提示使用者。

**適合的操作有共同特徵**：**成功率高**、**失敗的後果可以被回滾**、而且使用者能理解回滾發生了什麼。不適合的是付款、不可逆的刪除、以及結果依賴伺服器計算的操作（例如「送出後才知道分配到哪個位置」）。

最容易被忽略的是「失敗時的溝通」——畫面默默地變回去而沒有任何提示，比一開始就等待更讓人困惑；所以回滾必須伴隨明確的訊息與（可能的）重試選項。

## 詳細解析

「取消進行中的請求是最容易漏的一步」：如果一個背景的重新獲取正在進行——它回來時會用伺服器的舊值覆蓋你剛寫入的樂觀值，畫面就會閃一下變回去再變回來；所以在寫入樂觀值之前要先取消相關的查詢。這個 bug 的症狀很特殊（畫面短暫地跳回舊值），認得它能快速定位。

「多個樂觀更新的疊加」需要小心：使用者快速點了三次——每次都保存快照並寫入樂觀值，如果第二次失敗，回滾到它的快照會連第三次的更新也抹掉；處理的方式是用「重新計算」而非「回滾到快照」：失敗後重新從伺服器取得真值，並重新套用仍在進行中的樂觀操作。

**「衝突與失敗是不同的問題」**：失敗是操作沒成功（網路錯誤、驗證不過）——衝突是操作成功了但基於過期的資料（你編輯的版本已經被別人改過）；前者回滾即可，後者需要決定「誰的版本勝出」：最後寫入勝出（簡單但會靜默丟失資料）、拒絕並要求重新編輯（安全但打斷流程）、或者呈現差異讓使用者選擇（最好但最貴）。

**「協作場景需要不同的模型」**：多人同時編輯同一份文件——樂觀更新加衝突處理已經不夠；需要 CRDT 或 OT 這類能自動合併的資料結構。而它們的複雜度很高，所以在需要之前不該引入；判斷的訊號是「多人同時編輯同一個欄位是常態還是例外」。

## 面試回答方式

先給定義與價值，再給實作的四個步驟並強調**取消進行中的請求**這一步。接著給適合與不適合的判準。加分點有四個：**取消請求漏掉的症狀很特殊**（畫面短暫跳回舊值）；**多個樂觀更新的疊加**需要用重新計算而非回滾到快照；**衝突與失敗是不同的問題**並給出三種衝突策略；以及**協作場景需要 CRDT 或 OT**，而判斷的訊號是「多人同時編輯同一個欄位是常態還是例外」。

## 講稿

樂觀更新是先假設成功立刻更新畫面，等伺服器確認或失敗再修正。它的價值是消除等待，讓按讚、勾選、拖曳排序這類操作感覺是瞬間的。

實作有四步。先取消進行中的相關請求、保存當前快取的快照、寫入樂觀值、失敗時用快照回滾。

第一步最容易漏。如果有一個背景的重新獲取正在進行，它回來的時候會用伺服器的舊值覆蓋你剛寫的樂觀值，畫面就會閃一下。這個 bug 的症狀很特殊，畫面短暫跳回舊值，認得它就能快速定位。

適合的操作有共同特徵，成功率高、失敗能回滾、而且使用者能理解回滾發生了什麼。付款跟不可逆的刪除我不會用。

還有一件常被忽略的事，失敗時的溝通。畫面默默變回去而沒有提示，比一開始就等待更讓人困惑。所以回滾一定要配明確的訊息跟重試選項。

另外衝突跟失敗是兩件事。失敗是沒成功，衝突是成功了但基於過期的資料，後者要決定誰的版本勝出。

## 常見追問

### 拖曳排序怎麼做才不會出錯？

**核心答案**：用小數或者字串的排序鍵而非連續的整數索引。如果用整數索引，每次移動都要更新受影響的所有項目——而用兩個相鄰項目的中間值（例如在 1.0 和 2.0 之間插入 1.5）只要更新一筆；字串鍵（fractional indexing）能避免浮點數精度用盡的問題。

**詳細解析**：「整數索引在協作時特別容易出錯」：兩個人同時移動不同的項目——各自計算出的新索引序列會互相衝突，結果是順序錯亂；而中間值的方案讓每次移動只影響一筆記錄，衝突的機率大幅降低。浮點數的問題是連續在同一個位置插入約五十次後精度就用盡了——所以生產環境應該用字串的分數索引（在字元空間中取中間值，例如 'a' 和 'b' 之間是 'am'）；**它可以無限細分**。而無論用哪種，都需要一個「重新平衡」的機制以防鍵變得過長——**通常是低頻的背景任務**。這是一個「看起來簡單的功能實際上有成熟的解法」的好例子。

**面試回答方式**：給核心做法（用中間值而非連續整數，字串鍵避免精度問題）。核心加分點是說明整數索引在協作時特別容易出錯與中間值方案如何降低衝突，以及**浮點數約五十次後精度用盡**這個具體的限制。收在完整性：字串的分數索引可以無限細分，但仍需要一個低頻的重新平衡機制。

### 離線時的操作怎麼處理？

**核心答案**：把操作排入佇列並在恢復連線後重放。要處理的關鍵問題有三個：**順序**（操作之間可能有依賴）、**冪等**（重放時不能造成重複的效果）、**以及失敗的處理**（如果第三個操作失敗了，後面的還要不要送）。

**詳細解析**：「離線佇列的難點在於重放時的狀態已經不同」：你在離線時編輯了一筆記錄——而在你離線期間別人已經刪除了它；重放時該怎麼辦沒有通用的答案，需要按業務決定（跳過並告知、恢復該記錄、或者存成草稿讓使用者處理）。所以完整的離線支援成本很高——而多數應用需要的其實只是「離線時能讀取快取的內容」加上「操作時明確告知需要連線」；這個較輕的版本成本低得多而覆蓋了大部分的實際需求。在面試中能區分「離線讀取」與「離線寫入」的成本差異，展示的是務實的判斷——因為許多團隊在低估後者的複雜度之後才發現做不完。

**面試回答方式**：給做法（**排入佇列並在恢復後重放**）與三個關鍵問題。核心加分點是**重放時的狀態已經不同**這個難點並用具體的例子說明它沒有通用答案。收在務實判斷：區分「離線讀取」與「離線寫入」的成本差異——多數應用需要的只是離線讀取加上明確的告知，而許多團隊低估了離線寫入的複雜度。

### 怎麼讓使用者知道資料還沒真正儲存？

**核心答案**：用細微但明確的狀態指示，而不是阻塞式的載入畫面。常見的做法是：在項目旁顯示一個小的同步中圖示、用略微降低的透明度表示未確認、以及在頁面層級顯示「所有變更已儲存」或「儲存中」；關鍵是讓使用者能一眼看出狀態而不需要中斷操作。

**詳細解析**：「離開頁面前的提示是必要的保險」：如果還有未同步的變更——**`beforeunload` 能提示使用者確認**；但要注意瀏覽器對它的限制越來越嚴格（必須有使用者互動、訊息內容無法自訂），**而且它在行動裝置上不可靠**。所以更穩健的做法是「盡快同步而非依賴離開時的提示」——把變更的延遲送出時間縮短、在頁面隱藏時（`visibilitychange`）主動送出、並用 `navigator.sendBeacon` 送出最後的變更（它能在頁面卸載時仍然完成請求）。這個組合能讓「使用者關掉分頁而變更遺失」的情況大幅減少；而完全依賴使用者看到並回應提示，在實務中的成功率不高。

**面試回答方式**：給指示的做法並強調**不要用阻塞式的載入畫面**。核心加分點是離開頁面前的提示是必要的保險但限制很多（需要互動、訊息無法自訂、行動裝置不可靠）。收在更穩健的做法：**盡快同步而非依賴提示**——縮短延遲、在頁面隱藏時主動送出、用 `sendBeacon` 送出最後的變更；因為完全依賴使用者看到並回應提示，成功率不高。
