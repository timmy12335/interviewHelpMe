# 題目

XSS 和 CSRF 的攻擊原理差在哪？各自要怎麼防？

## 核心答案

兩者利用的信任方向相反。**XSS 是「網站信任了使用者的輸入」**——攻擊者把腳本注入頁面，讓它在受害者的瀏覽器中以該網站的身分執行，於是可以讀取 Cookie、竄改畫面、以使用者身分發請求。**CSRF 是「網站信任了瀏覽器自動附上的憑證」**——攻擊者誘導已登入的使用者的瀏覽器發出請求，因為 Cookie 會自動帶上，伺服器誤以為是使用者本人的操作。防禦方向也因此不同：**XSS 靠輸出時的正確編碼**（不是輸入時的過濾）、避免 `innerHTML` 這類直接注入 HTML 的操作、以及 **CSP** 這道獨立的防線。**CSRF 靠驗證請求的來源**——`SameSite` Cookie（現代瀏覽器預設 `Lax`，已擋掉大部分情境）、**CSRF token**（伺服器發一個攻擊者拿不到的隨機值，要求請求帶上）、以及檢查 `Origin` 標頭。要記住的是：**XSS 可以繞過所有 CSRF 防護**，因為腳本已經在頁面內執行，讀得到 token——所以 XSS 是更根本的問題。

## 詳細解析

**XSS 的三種類型**：**儲存型**最嚴重——惡意內容存進資料庫，每個看到這則內容的使用者都會中招（留言、暱稱、商品描述）。**反射型**透過 URL 參數，需要誘導使用者點擊特製連結。**DOM 型**完全發生在前端，伺服器沒有參與——例如把 `location.hash` 的內容直接塞進 `innerHTML`，這類最容易被後端的防護漏掉。

**防禦的正確位置是「輸出」而非「輸入」**：同一份資料在不同情境下的安全編碼方式不同——放在 HTML 內文、放在屬性值、放在 `<script>` 內、放在 URL 參數，各自需要不同的轉義。在輸入時過濾會同時造成兩個問題：可能破壞合法資料（使用者的暱稱裡有 `<`），也擋不住所有情境。所以正確做法是**照原樣儲存，在輸出到特定情境時做該情境的編碼**。

**框架的自動轉義與它的漏洞**：React、Vue 這類框架預設會轉義插值內容，這擋掉了絕大多數 XSS。但仍有幾個逃生口必須小心：`dangerouslySetInnerHTML`／`v-html`（直接注入 HTML）、把使用者輸入放進 `href`（`javascript:` 協定可以執行腳本）、以及動態產生的樣式或事件處理器。**需要渲染富文本時一定要先用成熟的消毒函式庫處理**，不要自己寫黑名單——黑名單永遠有繞過方式。

**CSP 是縱深防禦的一層**：內容安全政策透過回應標頭限制哪些來源的腳本可以執行，即使有注入也無法載入外部腳本或執行內聯腳本。有效的設定要避免 `unsafe-inline`，改用 **nonce** 或雜湊授權必要的內聯腳本。CSP 不能取代正確的編碼，但它能把「一個注入漏洞」的後果從「完全淪陷」降到「攻擊失敗」。

**CSRF 防禦的層次**：`SameSite=Lax` 是目前的預設，擋掉了跨站的 `POST` 與大部分情境，但**跨站的 `GET` 導航仍會帶上 Cookie**——所以**有副作用的操作絕對不能用 `GET`**，這是最基本的原則。CSRF token 的關鍵是攻擊者讀不到它（因為同源政策擋住了讀取回應）。另外檢查 `Origin` 或 `Referer` 標頭是輕量的補強，但要處理標頭缺失的情況。

## 面試回答方式

用「**信任方向相反**」把兩者一次講清楚——XSS 是網站信任了使用者輸入，CSRF 是網站信任了瀏覽器自動附上的憑證。接著各給防禦重點，並強調 **XSS 的防禦位置在輸出而不是輸入**，說明同一份資料在不同情境需要不同編碼。CSRF 講三層：`SameSite`、CSRF token、檢查 `Origin`，並點出**有副作用的操作不能用 `GET`**。最重要的加分點是主動說出**XSS 可以繞過所有 CSRF 防護**，因為腳本在頁面內執行讀得到 token——這句話顯示你理解兩者的關係而不只是分別背了防禦清單。另外提 CSP 作為縱深防禦，並說明要避免 `unsafe-inline`。

## 講稿

這兩個利用的信任方向剛好相反。

XSS 是網站信任了使用者的輸入。攻擊者把腳本注入頁面，讓它在受害者的瀏覽器裡以這個網站的身分執行，於是可以讀 Cookie、竄改畫面、以使用者的身分發請求。

CSRF 是網站信任了瀏覽器自動附上的憑證。攻擊者誘導已登入的使用者發出請求，Cookie 會自動帶上，伺服器就以為是本人操作。

所以防禦方式不同。XSS 我會在輸出的時候做編碼，不是在輸入的時候過濾。因為同一份資料放在 HTML 內文、放在屬性、放在 script 裡面，需要的轉義方式都不一樣，輸入時過濾既擋不全又會破壞合法資料。

CSRF 則是驗證請求來源。SameSite 現在預設是 Lax，已經擋掉大部分情境，再加 CSRF token，因為攻擊者讀不到那個值。另外有副作用的操作絕對不能用 GET，這是最基本的。

最後我想強調一件事，XSS 可以繞過所有 CSRF 防護，因為腳本已經在頁面裡執行，token 它讀得到。所以 XSS 是更根本的問題，CSP 這種縱深防禦也值得加上。

## 常見追問

### React 已經自動轉義了，還會有 XSS 嗎？

**核心答案**：**會**。自動轉義只涵蓋「把值當文字插入」這個最常見的情況，仍有幾個逃生口：**`dangerouslySetInnerHTML`**（直接注入 HTML）、**把使用者資料放進 `href` 或 `src`**（`javascript:` 這類協定可以執行腳本）、**動態產生的事件處理器或樣式**、以及**伺服器端渲染時把資料注入到 `<script>` 標籤中**（需要額外處理 `</script>` 這類序列的轉義）。

**詳細解析**：`href` 的問題特別容易被忽略——把使用者提供的網址直接渲染成連結，若對方填的是 `javascript:alert(1)`，使用者點擊就會執行腳本。正確做法是**驗證協定白名單**（只允許 `http`、`https`、`mailto`），不合的就不渲染成連結。至於富文本，唯一可靠的做法是用成熟的消毒函式庫，並採**白名單**方式（只允許已知安全的標籤與屬性），因為黑名單永遠有新的繞過方式。伺服器端渲染注入初始狀態時也要小心，要對輸出做 JSON 的安全序列化而不是直接字串插值。

**面試回答方式**：明確說會，並列出四個逃生口。重點展開 `href` 的 `javascript:` 協定問題與協定白名單的解法。加分點是強調富文本必須用成熟函式庫且採白名單，以及伺服器端渲染注入狀態時要做安全序列化。

### CSP 要怎麼設定才實用？

**核心答案**：關鍵是**避免 `unsafe-inline` 與 `unsafe-eval`**，否則等於沒設。內聯腳本改用 **nonce**（每次回應產生隨機值，只有帶對 nonce 的內聯腳本能執行）或**雜湊**授權。導入時先用 **`Content-Security-Policy-Report-Only`** 模式蒐集違規回報，確認不會誤擋正常功能，再切換成強制模式。

**詳細解析**：實務上最大的阻力是**第三方腳本**——分析工具、廣告、客服元件常常需要 `unsafe-inline` 或動態載入其他網域，導致政策被迫放寬。務實的做法是逐步收緊：先限制 `object-src` 與 `base-uri` 這些低風險但高價值的項目，再處理 `script-src`。另外 `frame-ancestors` 可以防止頁面被嵌入到其他站（點擊劫持），這是很划算的一條。要注意 CSP 是**縱深防禦而非主要防線**——它降低漏洞被利用的後果，但不能取代正確的輸出編碼。把它當成「即使我們寫錯了一個地方，攻擊也難以得手」的保險。

**面試回答方式**：核心是避免 `unsafe-inline` 並改用 nonce 或雜湊，以及先用 Report-Only 模式導入。點出第三方腳本是最大阻力，建議逐步收緊。加分點是提到 `frame-ancestors` 防點擊劫持，並強調 CSP 是縱深防禦不能取代輸出編碼。

### 如果 token 放在 localStorage，被 XSS 之後會怎樣？

**核心答案**：**token 會被完整竊取**，攻擊者可以在自己的環境用它冒充使用者，直到 token 過期為止。相對地，`HttpOnly` Cookie 中的 token 讀不到，攻擊者只能在受害者的瀏覽器中發請求（仍然危險，但**無法把憑證帶走**），影響範圍與持續時間都小得多。這個差別是選擇儲存位置時最實際的考量。

**詳細解析**：不過要誠實看待：有 XSS 的情況下，即使用 `HttpOnly` Cookie，攻擊者仍可在頁面內以使用者身分執行任意操作（轉帳、改密碼、竊取畫面上的資料），所以**不能把 `HttpOnly` 當成 XSS 的解方**——它只是限縮了損害。真正的縱深防禦組合是：正確的輸出編碼（根本）、CSP（限制注入後能做什麼）、`HttpOnly` Cookie（限制憑證外洩）、短存活期的 token 加更新機制（限制被竊後的有效時間）、以及對敏感操作要求**二次驗證**（改密碼、大額轉帳時重新輸入密碼或多因素驗證）。最後一項常被忽略，但它是防止「已被入侵的工作階段造成不可逆損害」的最後一道關卡。

**面試回答方式**：先給明確差別——`localStorage` 的 token 會被帶走，`HttpOnly` 的只能在受害者瀏覽器內被濫用。接著誠實說明 `HttpOnly` 不是 XSS 的解方，只是限縮損害。加分點是給出完整的縱深防禦組合，特別點出敏感操作的二次驗證是最容易被忽略的一層。
