# 題目

Core Web Vitals 的三個指標分別衡量什麼？各自該用什麼手段優化？

## 核心答案

三個指標分別對應使用者體驗的三個面向。**LCP（最大內容繪製）**衡量**載入速度**——視窗內最大的圖片或文字區塊何時渲染完成，目標 2.5 秒內。**CLS（累積版面位移）**衡量**視覺穩定性**——內容有沒有在使用者閱讀或點擊時突然跳動，目標 0.1 以下。**INP（互動到下次繪製）**衡量**互動回應**——使用者操作後畫面何時反映出變化，目標 200 毫秒內，它在 2024 年取代了原本的 FID。優化手段各不相同：**LCP** 靠減少關鍵資源的載入時間（預載主要圖片、內聯關鍵 CSS、移除阻塞渲染的資源、用伺服器端渲染讓內容更早出現）；**CLS** 靠為圖片與影片**指定明確尺寸**、為動態插入的內容**預留空間**、以及避免在既有內容上方插入元素；**INP** 靠**減少主執行緒的長任務**——拆分長運算、減少不必要的重新渲染、把重運算移到 Web Worker。關鍵是先量測確認哪個指標不好，再選對應手段。

## 詳細解析

**LCP 的常見瓶頸不只是圖片大小**：實際上它常受制於**資源發現的時間**——如果主圖是由 JavaScript 動態插入的，瀏覽器要等 JS 下載執行完才知道要載入它，比寫在 HTML 中晚很多。解法是把首屏主圖直接寫在 HTML 並加上 `fetchpriority="high"`，或用 `preload`。另外**字體載入**也常影響 LCP——若最大元素是文字，字體未載入完可能導致文字不顯示，`font-display: swap` 可以讓文字先用備用字體顯示。

**CLS 最常見的四個來源**：沒有尺寸的圖片（載入後把下方內容推開）、動態插入的橫幅或廣告、**字體切換造成的行高變化**（備用字體與正式字體的度量不同）、以及在使用者已經看到內容後才載入的資料改變了版面。要注意**動畫不一定造成 CLS**——用 `transform` 的動畫不計入，因為它不影響版面。

**INP 的實際成因**：使用者點擊後的延遲由三段組成——**輸入延遲**（主執行緒忙碌，事件回呼排不進去）、**處理時間**（回呼本身執行多久）、**呈現延遲**（渲染更新畫面）。在前端框架中最常見的是第二與第三段：一次點擊觸發大量元件重新渲染。優化方向是**縮小更新範圍**（正確的記憶化與狀態切分）、**把非緊急的更新延後**（例如把搜尋結果的更新標記為低優先權），以及避免在事件處理器中做重運算。

量測要分實驗室資料與真實使用者資料：開發工具與 Lighthouse 給的是**實驗室資料**（固定的裝置與網路條件），適合開發時的迭代與比較；但真實使用者的裝置與網路差異極大，最終要看**真實使用者監控**的資料。兩者常常不一致，這時應該相信真實資料——因為它才反映實際體驗。

**優化的順序**：先量測、找出主導因素、再處理。常見的錯誤是憑印象優化——花大量時間壓縮 JavaScript，但真正的瓶頸是一張沒壓縮的首屏大圖，或是一個阻塞渲染的第三方腳本。**用資料決定優先順序**是這題最重要的方法論。

## 面試回答方式

先把三個指標各自衡量什麼講清楚（載入速度、視覺穩定、互動回應）並給目標值，這是基本盤。接著**分別給對應的手段**，強調三者的成因不同、手段不能互換。最重要的方法論要主動說出：先量測確認是哪個指標不好，再選手段，並舉一個憑印象優化錯方向的例子。加分點有三個：LCP 常受制於**資源發現時間**（JS 動態插入的圖片會晚很多），解法是寫進 HTML 並加 `fetchpriority`；CLS 有一個容易忽略的來源是**字體切換造成的行高變化**；以及 INP 的延遲由輸入延遲、處理時間、呈現延遲三段組成，框架應用多半卡在後兩段。

## 講稿

三個指標對應三個不同的體驗面向。

LCP 是載入速度，看視窗裡最大的圖片或文字區塊什麼時候渲染完，目標兩秒半。CLS 是視覺穩定性，看內容會不會在你正要點的時候跳掉，目標零點一以下。INP 是互動回應，看你操作之後畫面多久反映出來，目標兩百毫秒。

手段完全不同，不能互換。LCP 要減少關鍵資源的載入時間。這裡有個常被忽略的點，LCP 常常卡在資源發現的時間，如果主圖是 JavaScript 動態插入的，瀏覽器要等 JS 下載執行完才知道要載它。所以我會把首屏主圖直接寫在 HTML，加上高優先權。

CLS 主要靠給圖片明確尺寸、為動態內容預留空間。有個容易漏的來源是字體切換，備用字體跟正式字體的度量不一樣，換過去的時候行高會變。

INP 則是減少主執行緒的長任務。它的延遲分三段，輸入延遲、處理時間、呈現延遲，框架應用通常卡在後面兩段，也就是一次點擊觸發太多元件重新渲染。

最重要的是先量測確認是哪個指標不好，不要憑印象優化。

## 常見追問

### Lighthouse 分數很高但使用者還是覺得慢，可能是什麼原因？

**核心答案**：因為 Lighthouse 給的是**實驗室資料**——固定的裝置效能、固定的網路節流、而且通常是**冷啟動的單次載入**。真實使用者的情況差異極大：低階手機、不穩定的行動網路、已有快取的重複造訪、以及**載入之後的互動體驗**（Lighthouse 對 INP 的模擬有限）。另一個常見落差是 Lighthouse 只測了首頁，而使用者實際卡住的是某個資料密集的內頁。

**詳細解析**：正確的做法是**同時看兩種資料**。實驗室資料適合在開發階段做可重現的比較（改了一個東西前後差多少），真實使用者監控適合判斷實際體驗與決定優先順序。看真實資料時要看**分佈而非平均**——第 75 百分位或第 95 百分位才反映「體驗最差的那群人」，而平均值會被大量快速的重複造訪拉低。另外要**依裝置與地區切分**，常見的情況是整體看起來不錯，但低階 Android 裝置的體驗差很多。這種分群分析往往比任何優化技巧更能找到真正的問題。

**面試回答方式**：先解釋實驗室資料與真實資料的差異來源（裝置、網路、快取狀態、只測首頁）。接著給方法：兩種都看，各有用途。加分點是強調要看分佈的第 75 或 95 百分位而非平均，以及依裝置與地區切分找出真正受影響的群體。

### 打包產物太大要怎麼處理？

**核心答案**：**先分析再切分**。用打包工具的分析報告找出體積來源——通常是幾個大型函式庫、重複打包的相依套件、或不小心引入了整個函式庫（例如引入整個工具庫只用了一個函式）。處理手段依序是：**移除不需要的相依**、**改用更輕量的替代品**、**確保 tree shaking 生效**（使用具名匯入、確認套件標示為無副作用）、**路由層級的程式碼分割**（每個頁面只載入自己需要的）、以及**延後載入**非首屏必要的功能（圖表、編輯器、彈窗內容）。

**詳細解析**：實務上收益最大的往往是**程式碼分割與延後載入**，因為它直接減少首屏需要下載與解析的量。要注意 JavaScript 的成本不只是下載——**解析與執行**在低階裝置上可能比下載還久，所以減少體積的收益是雙重的。另一個常被忽略的是**重複的相依**：不同套件依賴同一函式庫的不同版本，導致打包了兩份，用分析工具可以看出來，通常靠版本收斂解決。最後要建立**體積預算與 CI 檢查**——設定門檻，超過就讓建置失敗，否則體積會隨著時間無聲地膨脹，而膨脹是一次一點累積起來的，事後很難回頭處理。

**面試回答方式**：給出「先分析再切分」的順序與五個手段。強調程式碼分割與延後載入收益最大，並指出 JS 的成本包含解析與執行、在低階裝置上更明顯。加分點是提到重複相依這個常見來源，以及建立體積預算與 CI 檢查防止無聲膨脹。

### 圖片優化有哪些具體手段？

**核心答案**：**格式、尺寸、載入時機**三個方向。**格式**用現代格式（WebP 或 AVIF）並保留回退，體積通常比 JPEG 小三到五成。**尺寸**用 `srcset` 與 `sizes` 讓不同螢幕載入合適大小的版本，避免手機下載桌面尺寸的圖。**載入時機**——首屏主圖用 `fetchpriority="high"` 提前，非首屏用 `loading="lazy"` 延後。同時務必**指定寬高或 `aspect-ratio`**，這是避免 CLS 的關鍵。

**詳細解析**：容易被忽略的細節有三個。一是**佔位策略**——用低解析度的模糊縮圖或純色佔位，能顯著改善感知速度，比空白等待好得多。二是 `loading="lazy"` **不該用在首屏圖片**，那會延後 LCP 元素的載入，反而讓指標變差。三是**背景圖無法用這些屬性**——CSS 背景圖不支援 `srcset` 也不會被預載掃描器發現，首屏的重要視覺應該用 `<img>` 而不是背景圖。另外如果有影像處理服務，讓它依請求參數即時產生合適的尺寸與格式，比預先產生一堆版本更好維護。

**面試回答方式**：用格式、尺寸、載入時機三個方向組織，並強調指定寬高是避免 CLS 的關鍵。加分點是三個容易忽略的細節：佔位策略改善感知速度、`loading="lazy"` 不能用在首屏圖片、以及首屏重要視覺不該用 CSS 背景圖因為預載掃描器發現不了。
