# 題目

JavaScript 是單執行緒的，為什麼還能處理非同步？`setTimeout` 和 `Promise.then` 誰先執行？

## 核心答案

單執行緒指的是**只有一個呼叫堆疊**，非同步能力來自**執行環境**（瀏覽器或 Node）——計時器、網路請求、事件監聽都由環境負責，完成後把回呼放進佇列，等主執行緒空了才取出執行。這個取出的機制就是 **Event Loop**。關鍵規則是：**每執行完一個巨任務，就把微任務佇列「清空」，然後才進入下一個巨任務**。`Promise.then`、`queueMicrotask`、`MutationObserver` 是**微任務**；`setTimeout`、`setInterval`、I/O、UI 事件是**巨任務**。所以 `Promise.then` 一定比 `setTimeout` 先執行，即使 `setTimeout` 的延遲是 0。更重要的推論是：**微任務會在渲染之前全部跑完**，所以在微任務裡遞迴地產生新微任務會讓頁面永遠無法更新——這是「頁面卡死但 CPU 沒滿」的典型原因。

## 詳細解析

**完整的一輪流程**：執行一個巨任務 → 清空微任務佇列（過程中新產生的微任務也會在這一輪被執行完）→ 執行渲染相關工作（`requestAnimationFrame` 回呼、樣式計算、版面配置、繪製）→ 進入下一個巨任務。理解「微任務清空在渲染之前」這一點，能解釋很多實務現象，例如為什麼連續修改 DOM 只會觸發一次繪製。

**async/await 就是 Promise 的語法糖**：`await` 之後的程式碼相當於放進 `.then` 裡，所以是**微任務**。一個常見的考題是「函式裡 `await` 前的程式碼是同步執行的」——呼叫 async 函式時，函式體會**同步執行到第一個 `await`**，之後才交出控制權。這個細節在推導執行順序時經常決定答案。

**setTimeout(fn, 0) 不是立刻執行**：規範規定巢狀超過五層的計時器最小延遲會被限制在 4 毫秒左右，而且它只是「**至少**經過這麼久之後才有資格被排入佇列」，實際執行時間取決於主執行緒何時空閒。如果主執行緒被一段長運算佔住，計時器會被無限期推遲——這是動畫掉幀與輸入延遲的常見來源。

**requestAnimationFrame 的定位**：它既不是微任務也不是一般巨任務，而是排在**渲染前**執行的回呼，頻率跟著螢幕刷新率（通常每 16.7 毫秒一次），而且分頁在背景時會暫停。所以動畫應該用它而不是 `setTimeout`——後者會在背景分頁繼續累積、也無法和刷新對齊，造成撕裂與掉幀。

**Node.js 的差異**：Node 的 Event Loop 分成多個階段（timers、pending callbacks、poll、check、close），`setImmediate` 在 check 階段、`setTimeout` 在 timers 階段，兩者在主模組中的先後**不確定**（取決於行程啟動耗時），但在 I/O 回呼裡 `setImmediate` 必定先於 `setTimeout`。另外 Node 有 `process.nextTick`，它的優先權**高於**所有其他微任務。這些差異在全端職缺常被問到。

## 面試回答方式

先把「單執行緒」的意思講精確——只有一個呼叫堆疊，非同步能力來自執行環境，這一句就避開了最常見的誤解。接著給核心規則：**一個巨任務結束後清空整個微任務佇列，再進入下一個巨任務**，並分類哪些是微任務、哪些是巨任務。回答「誰先執行」時直接給結論並補上原因。加分點有三個：一是點出**微任務在渲染之前清空**，所以遞迴產生微任務會讓頁面卡死；二是說明 `await` 之前的程式碼是同步執行的；三是說明 `requestAnimationFrame` 排在渲染前、跟著刷新率，所以動畫該用它而不是 `setTimeout`。

## 講稿

單執行緒指的是只有一個呼叫堆疊，不是不能處理非同步。真正做事的是執行環境，計時器、網路請求、事件監聽都是瀏覽器或 Node 在管，完成之後把回呼丟進佇列，等主執行緒空了才取出。

取出的規則就是 Event Loop。核心只有一句話，執行完一個巨任務之後，把微任務佇列整個清空，然後才進入下一個巨任務。

Promise 的 then、queueMicrotask 這些是微任務。setTimeout、I/O、UI 事件是巨任務。所以 then 一定比 setTimeout 先跑，就算延遲寫零也一樣。

有個推論我覺得更重要。微任務是在渲染之前清空的，所以如果我在微任務裡不斷產生新的微任務，這一輪就永遠結束不了，畫面完全不會更新。

另外 await 之後的程式碼等於放進 then 裡，所以是微任務。但 await 之前是同步執行的，呼叫 async 函式當下就會跑到第一個 await 才交出控制權。推順序的時候這個細節常常決定答案。

動畫我會用 requestAnimationFrame，因為它排在渲染前、跟著螢幕刷新率，而且分頁在背景會暫停。

## 常見追問

### 為什麼一段長時間的同步運算會讓整個頁面卡住？

**核心答案**：因為**渲染和事件處理都排在同一個主執行緒上**。當一段同步程式碼佔住呼叫堆疊，Event Loop 無法進入下一輪，所以計時器不會觸發、點擊事件的回呼進不了佇列、樣式計算與繪製也不會執行——使用者看到的是完全凍結的畫面，連捲動與輸入游標都沒有反應。

**詳細解析**：解法有三個方向。**切片**：把長任務拆成小塊，每塊之間用 `setTimeout` 或 `scheduler.yield` 讓出控制權，讓瀏覽器有機會渲染與處理輸入。**移出主執行緒**：把純運算搬到 Web Worker，它有自己的執行緒，不會阻塞 UI，代價是只能透過訊息傳遞溝通、且無法存取 DOM。**減少工作量**：虛擬捲動只渲染可見範圍、用索引結構取代線性搜尋、把運算移到伺服器。實務上判斷準則是任務時長——超過 50 毫秒的任務就會被視為長任務並影響互動延遲，這也是 INP 這個核心指標在量測的東西。

**面試回答方式**：核心是渲染與事件處理共用主執行緒，堆疊被佔住就全部停擺。接著給三個方向：切片讓出、移到 Web Worker、減少工作量。加分點是給出 50 毫秒這個長任務門檻，並連結到 INP 指標。

### for 迴圈裡的 setTimeout 為什麼印出來的都是同一個值？

**核心答案**：這是 **`var` 的函式作用域**造成的，不是 Event Loop 的問題。用 `var` 宣告的迴圈變數在整個函式中只有**一份**，所有回呼閉包捕獲的是同一個變數；等到回呼真正執行時（迴圈早已結束），那份變數的值已經是最終值。改用 `let` 就正常，因為 `let` 在**每一輪迭代都建立一個新的綁定**，每個回呼捕獲的是不同的變數。

**詳細解析**：在 `let` 出現之前的解法是用**立即執行函式**建立新的作用域，把當前的值當參數傳進去。理解這題的關鍵是分清兩件事：**閉包捕獲的是變數本身而不是值的快照**，以及**回呼在迴圈結束後才執行**。兩者疊加才產生這個現象。同一個原理也出現在 React 的 hooks 中——`useEffect` 裡的閉包捕獲的是那一次渲染的變數，依賴陣列漏了東西就會讀到過期的值，本質上是同一類問題。能把這兩個場景連起來，比只會答「用 let」有深度。

**面試回答方式**：先明確指出根因是 `var` 的函式作用域而非 Event Loop，並解釋 `let` 為什麼可以（每輪迭代建立新綁定）。點出兩個疊加的前提：閉包捕獲變數本身、回呼在迴圈後才執行。加分點是連結到 React hooks 的過期閉包，說明它是同一類問題。

### Promise 裡的程式碼是同步還是非同步執行的？

**核心答案**：**傳給 `new Promise` 的執行器函式是同步執行的**，只有 `.then`、`.catch`、`.finally` 裡的回呼才是非同步（微任務）。所以 `new Promise(resolve => { console.log('A'); resolve(); }).then(() => console.log('B')); console.log('C')` 的輸出順序是 A、C、B——A 在建構當下就印出來了。

**詳細解析**：這個細節常被用來考「你是不是真的理解，還是只記得 Promise 是非同步的」。相關的另一個重點是 **`resolve()` 只是改變狀態，不會中斷函式執行**——`resolve()` 之後的程式碼仍然會跑完，這常導致意料外的副作用。另外要注意 `.then` 註冊的回呼**必定非同步執行**，即使 Promise 已經是完成狀態：對一個已完成的 Promise 呼叫 `.then`，回呼仍然被放進微任務佇列而不是立即執行。這個一致性是規範刻意設計的，目的是讓程式碼的執行順序可預測，不會因為 Promise 完成的時機而改變。

**面試回答方式**：直接給結論——執行器同步、then 的回呼非同步，並用具體的輸出順序示範。補充 `resolve()` 不會中斷後續程式碼這個常見陷阱。加分點是說明對已完成的 Promise 呼叫 `.then` 仍然是非同步的，並解釋這個一致性是刻意設計來讓順序可預測。
