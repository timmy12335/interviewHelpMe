# 題目

瀏覽器把 HTML 變成畫面經過哪些階段？「重排」和「重繪」差在哪，為什麼要避免？

## 核心答案

主要階段是：解析 HTML 建 **DOM 樹** → 解析 CSS 建 **CSSOM** → 合併成**渲染樹**（只包含要顯示的節點）→ **版面計算**（layout，算出每個元素的位置與大小）→ **繪製**（paint，決定每個像素的顏色）→ **合成**（composite，把各圖層組合起來上螢幕）。**重排（reflow）指的是重新執行版面計算**，因為幾何屬性變了（寬高、位置、字體大小、增刪節點）；**重繪（repaint）是只重新繪製**，因為外觀變了但幾何沒變（顏色、陰影、背景）。**重排一定會導致重繪，反之不然**，所以重排成本高得多——它可能影響整棵樹的後續元素。最理想的是**只觸發合成**：`transform` 與 `opacity` 的改變可以完全跳過版面計算與繪製，直接由合成器處理（甚至在 GPU 上），這就是動畫應該只用這兩個屬性的技術原因。

## 詳細解析

**強制同步版面計算是最常見的效能殺手**：瀏覽器會把多次 DOM 修改**批次處理**，等到需要時才一次算完。但如果你在修改之後**立刻讀取**幾何屬性（`offsetHeight`、`getBoundingClientRect`、`scrollTop`），瀏覽器為了給出正確的值必須**當場強制執行版面計算**。在迴圈中反覆「寫、讀、寫、讀」就會造成版面計算抖動，效能急遽下降。解法是**先批次讀取、再批次寫入**，把讀寫分離。

**離線修改再一次插入**：要對 DOM 做大量修改時，可以先把節點取下（`display: none` 或移出文件）、修改完再放回，這樣中間的修改只觸發一次重排。`DocumentFragment` 是同樣的思路——在記憶體中組好整段結構，再一次插入文件。

**為什麼 `transform` 比改 `left` 好**：改 `left` 屬於幾何變化，觸發版面計算加繪製加合成；`transform` 只影響該圖層在合成階段的變換矩陣，跳過前兩步。同理 `opacity` 也是。要注意**建立圖層本身有記憶體成本**——`will-change` 可以提示瀏覽器提前建立圖層，但濫用會消耗大量記憶體反而更慢，正確用法是**在動畫開始前加上、結束後移除**。

**CSS 與 JavaScript 對解析的阻塞**：`<script>` 預設會**阻塞 HTML 解析**（因為它可能修改 DOM），所以要放在底部或加上 `defer`／`async`。CSS 會**阻塞渲染**（因為沒有樣式就無法正確繪製），所以關鍵樣式要盡早載入，非關鍵的用媒體查詢或動態載入延後。這兩件事直接影響首次內容繪製的時間。

**選擇器與樣式計算的成本通常被高估**：現代引擎對選擇器匹配已經高度優化，過度糾結選擇器效率的收益很小。真正值得關注的是**受影響元素的數量**——修改根元素上的 class 導致整頁重新計算樣式，比選擇器寫得複雜嚴重得多。優化的方向應該是**縮小影響範圍**，例如把變動限制在單一子樹、使用 `contain` 屬性告訴瀏覽器某個子樹的變化不會影響外部。

## 面試回答方式

先把六個階段講出來（DOM、CSSOM、渲染樹、版面計算、繪製、合成），這給了後面所有討論一個框架。接著定義重排與重繪的差別，並強調**重排一定導致重繪**、成本更高。然後給最重要的實務結論：**動畫只用 `transform` 與 `opacity`**，因為它們可以跳過版面計算與繪製直接由合成器處理。加分點有三個：**強制同步版面計算**（修改後立刻讀取幾何屬性）與讀寫分離的解法；`will-change` 應該在動畫前加、結束後移除，因為圖層有記憶體成本；以及選擇器效率通常被高估，真正要優化的是**受影響元素的數量**。

## 講稿

流程大致是解析 HTML 建 DOM，解析 CSS 建 CSSOM，合併成渲染樹，然後算版面、繪製，最後合成上螢幕。

重排是重新算版面，因為幾何變了，像寬高、位置、增刪節點。重繪是只重新畫，幾何沒變只是外觀變了，像顏色、陰影。重排一定會導致重繪，反過來不會，所以重排貴很多，因為它可能影響後面一整串元素。

最理想的其實是連重繪都跳過，只觸發合成。transform 跟 opacity 就是這樣，它們只影響圖層在合成階段的變換，前面兩步都不用做。所以動畫我只會動這兩個屬性，改 left 或 width 就會一路重算。

實務上最常見的效能殺手是強制同步版面計算。瀏覽器本來會把多次修改批次處理，但如果我改完馬上讀 offsetHeight 或 getBoundingClientRect，它為了給正確的值就得當場算一次。在迴圈裡反覆寫讀寫讀，效能會掉得很誇張。解法是先批次讀完再批次寫。

另外 will-change 可以提示瀏覽器提前建圖層，但建圖層本身有記憶體成本，濫用反而更慢。我會在動畫開始前加、結束後拿掉。

## 常見追問

### 為什麼 `transform` 動畫可以跑在 GPU 上？

**核心答案**：因為 `transform` 與 `opacity` 的變化**不改變元素的內容像素**，只改變它**如何被組合到畫面上**。瀏覽器可以把該元素提升為獨立的**合成層**，把它的內容繪製成一張紋理交給 GPU，之後每一幀只需要對這張紋理做矩陣變換或改變透明度——這正是 GPU 擅長的操作，而且完全不需要主執行緒參與。所以即使主執行緒忙碌，這類動畫仍然流暢。

**詳細解析**：這也解釋了為什麼有些動畫「看起來很順但頁面卡住」——動畫在合成器執行緒上跑，不受主執行緒阻塞影響。要注意合成層不是免費的：**每一層都佔用記憶體**（寬乘高乘四位元組），大面積元素提升為圖層可能消耗數十 MB；層數過多也會增加合成的成本。觸發圖層提升的條件除了 `will-change`，還包括 3D 變換、`position: fixed`、`video`、`canvas` 等。實務上可以用開發工具的圖層面板檢視實際建立了多少層，這比猜測有效。另外要注意的是，**動畫 `transform` 不會觸發重排，但改變 `width` 造成的視覺效果類似卻完全不同**——需要縮放效果時應該用 `transform: scale` 而不是改寬高。

**面試回答方式**：核心是這兩個屬性不改變內容像素、只改變如何組合，所以能繪成紋理交給 GPU 每幀做矩陣變換。點出它在合成器執行緒執行，不受主執行緒阻塞。加分點是講圖層的記憶體成本與層數過多的問題，並建議用開發工具的圖層面板實際檢視。

### 首屏渲染慢，你會怎麼排查？

**核心答案**：先分辨慢在**網路**還是**渲染**。用開發工具的網路面板看關鍵資源的載入時間與瀑布圖——是不是有阻塞渲染的 CSS 或同步腳本、是不是有請求瀑布（一個請求完才發下一個）、資源體積是否過大。再用效能面板看主執行緒——是不是有長任務佔住、樣式計算與版面計算是否過重。這兩個方向的解法完全不同，先分清楚才不會亂優化。

**詳細解析**：網路側的常見手段是：**關鍵 CSS 內聯**（避免額外的往返）、腳本加 `defer`、**預載入**首屏的字體與主要圖片、以及**壓縮與分割**打包產物讓首屏只載入必要的程式碼。渲染側的手段是：減少首屏需要渲染的節點數（長列表用虛擬捲動）、避免在首屏執行大量同步運算、以及對圖片指定明確尺寸避免載入後造成版面位移。要注意**優化的目標指標不同解法也不同**——LCP 通常受最大圖片或文字區塊的載入時間主導，CLS 受版面位移主導，INP 受長任務主導。**先確認是哪個指標不好，再選對應的手段**，是這題最重要的方法論。

**面試回答方式**：先給分辨網路與渲染這個第一步，並說明各自用哪個面板看什麼。接著分別列出兩側的手段。加分點是強調方法論——先確認是 LCP、CLS 還是 INP 不好，因為三者的主導因素完全不同，選錯手段等於白做。

### `display: none` 和 `visibility: hidden` 在渲染上差在哪？

**核心答案**：**`display: none` 的元素不進入渲染樹**，完全不佔空間，切換它會觸發**重排**。**`visibility: hidden` 仍在渲染樹中並佔據原本的空間**，只是不繪製，切換它只觸發**重繪**（成本較低）。第三個選項 `opacity: 0` 更輕——它可以只觸發合成，而且元素仍然可以接收滑鼠事件（前兩者不行）。

**詳細解析**：選擇的判準是**要不要保留空間**與**切換頻率**。需要頻繁顯示隱藏且不希望版面跳動的（例如提示框、下拉選單的動畫），用 `opacity` 加 `pointer-events` 控制最順；需要完全移除佔位的用 `display: none`。要注意無障礙的差異：`display: none` 與 `visibility: hidden` 的內容**不會被螢幕閱讀器讀出**，但 `opacity: 0` 的內容**仍然會被讀出且可以被鍵盤聚焦**——這會造成「看不見但可以 Tab 到」的困擾，所以用 `opacity` 隱藏時必須同時處理 `aria-hidden` 與焦點管理。這個細節在面試中提出來，會顯示你考慮的不只是效能。

**面試回答方式**：給出三者在渲染樹、佔位、觸發層級上的差異，並給選擇判準（要不要保留空間、切換頻率）。加分點是主動提無障礙的差異——`opacity: 0` 的內容仍會被螢幕閱讀器讀出且可聚焦，需要額外處理，展現你考慮的不只效能。
