# 題目

前端專案長大之後，程式碼該怎麼組織？

## 核心答案

**核心原則是「按功能領域組織而非按檔案類型」**——**把 `components/`、`hooks/`、`utils/` 各放一堆的結構，在小專案中沒問題**；**但當專案長大，一個功能的修改要跨越五個目錄，而且沒有人知道某個元件還有沒有人用。**

**更好的結構是「每個功能一個資料夾，內部包含它自己的元件、hooks、型別與測試」**——**於是功能的邊界是可見的**；**而真正跨功能共用的東西才放到共享的層級。**

**依賴的方向要明確**：**功能可以依賴共享層，共享層不能依賴功能，而功能之間應該盡量不互相依賴**（要協作時透過明確的介面或者上層的組合）；**這個規則可以用工具（ESLint 的匯入規則）強制執行，而不是靠約定。**

**最重要的判斷是「什麼時候該抽出共用」**——**過早抽象會產生一個需要滿足所有情況的元件，而它最後會有十五個 props**；**等到第三次出現相同的需求再抽，通常是更好的時機。**

## 詳細解析

**「用工具強制依賴規則」是這件事能持續的關鍵**：純粹的約定會在時間壓力下被打破——**而一個 ESLint 規則（禁止從 `features/a` 匯入 `features/b`）會在當下就阻止它**；**而例外可以明確標記並被審查**。**沒有強制的架構規則，在六個月後通常已經不成立。**

**「共用的層級應該很薄」**：如果共享層變得很大——**那通常表示邊界劃錯了**（本應屬於某個功能的東西被放進了共享）；**一個檢查是「這個共享的模組被幾個功能使用」——只有一個的話，它應該回到那個功能裡**。

**「元件的抽象程度要與它的位置相稱」**：共享的元件應該只知道自己的呈現而不知道業務——**而功能內的元件可以直接使用該功能的資料與邏輯**；**混淆這一點會產生「共享元件裡有訂單相關的判斷」這種難以維護的結構**。

**「檔案的組織要讓刪除變容易」**：好的結構讓「移除一個功能」等於刪掉一個資料夾——**而如果那個功能的程式碼散落在各處，就沒有人敢刪**；**於是死程式碼會不斷累積**。**用「刪除的難易度」來檢驗結構，是一個簡單而有效的判準。**

## 面試回答方式

先給核心原則（**按功能領域而非按檔案類型**）並說明後者在專案長大後的問題，再給依賴方向的規則與抽出共用的時機。加分點有四個：**用工具強制依賴規則**——**純粹的約定在六個月後通常已經不成立**；**共用的層級應該很薄**與檢查方法（只被一個功能使用就該回去）；**元件的抽象程度要與它的位置相稱**；以及**用「刪除的難易度」檢驗結構**——**好的結構讓移除一個功能等於刪掉一個資料夾**。

## 講稿

核心原則是按功能領域組織而不是按檔案類型。把元件、hooks、工具各放一堆的結構在小專案沒問題，但專案長大之後，一個功能的修改要跨越五個目錄，而且沒有人知道某個元件還有沒有人用。

更好的做法是每個功能一個資料夾，裡面包含它自己的元件、hooks、型別跟測試。真正跨功能共用的才放到共享層。

依賴的方向我會明確規定。功能可以依賴共享層，共享層不能依賴功能，功能之間盡量不互相依賴。而這個規則我會用 ESLint 的匯入規則去強制，不是靠約定。因為純粹的約定會在時間壓力下被打破，而沒有強制的架構規則，六個月後通常已經不成立了。

另外什麼時候該抽出共用，我的判斷是等到第三次出現相同需求再抽。過早抽象會產生一個要滿足所有情況的元件，最後有十五個 props。

還有一個簡單的檢驗方法，看刪除容不容易。好的結構讓移除一個功能等於刪掉一個資料夾。

## 常見追問

### 元件該拆多細？

**核心答案**：**按「變化的原因」拆而非按行數拆**。一個三百行但只做一件事的元件，比五個互相纏繞的六十行元件好——**而如果一個元件同時處理資料獲取、業務判斷與呈現，那它有三個變化的原因，值得拆**；**這正是單一職責原則在元件上的應用。**

**詳細解析**：**「過度拆分的成本是可見性」**：把一個表單拆成十五個檔案——**要理解整體的行為就得在檔案之間跳來跳去**；**而「一個功能能不能在一個螢幕內被理解」是一個實用的檢驗**。**所以拆分的動機應該是「這部分會被複用」或者「這部分的變化原因不同」，而不是「檔案太長了」**。**而在實務上，一個常見的良好結構是「一個容器元件負責資料與協調、幾個呈現元件負責畫面」**——**這個兩層的劃分覆蓋了大部分的情況而不會過度**；**再往下拆通常要有具體的理由。**

**面試回答方式**：給判準（**按變化的原因拆而非按行數**）並用具體的例子說明。核心加分點是**過度拆分的成本是可見性**與實用的檢驗（**一個功能能不能在一個螢幕內被理解**），並指出拆分的動機不該是「檔案太長」。收在實務結構：**一個容器負責資料與協調、幾個呈現元件負責畫面**——**這兩層覆蓋大部分情況，再往下拆要有具體理由**。

### 共用的邏輯該用 hook 還是工具函式？

**核心答案**：**需要用到 React 的能力（state、effect、context）才用 hook，純計算用普通函式**。把一個不需要 state 的計算包成 hook，只是讓它變得無法在元件外使用且更難測試——**而純函式可以在任何地方呼叫、測試也不需要渲染環境。**

**詳細解析**：**「hook 的可測試性比普通函式差」**：測試 hook 需要一個渲染環境（`renderHook`）——**而純函式直接呼叫就好**；**所以把邏輯盡量抽成純函式、讓 hook 只負責「連接 React 的生命週期」，能讓大部分的邏輯用最簡單的方式測試**。**這個分離也讓邏輯可以在非 React 的環境重用**（伺服器端、Web Worker、或者未來換框架時）。**而一個實用的檢驗是「這段邏輯如果搬到 Node 腳本裡能不能跑」**——**能的話它就該是純函式**；**這個問題能快速地把「本質的業務邏輯」與「框架的膠水」區分開。**

**面試回答方式**：給判準（**需要 React 的能力才用 hook**）並說明過度包成 hook 的代價。核心加分點是**hook 的可測試性比普通函式差**與分離的好處（邏輯可在非 React 環境重用）。收在檢驗方法：**這段邏輯如果搬到 Node 腳本裡能不能跑**——**能的話就該是純函式**，**這個問題能快速區分本質的業務邏輯與框架的膠水**。

### 多人協作時怎麼避免結構走樣？

**核心答案**：**把約定變成工具與模板**。ESLint 的匯入邊界規則、資料夾結構的產生器（新功能用指令產生標準骨架）、以及在程式碼審查中對結構的明確檢查——**這三者比一份沒有人讀的架構文件有效得多。**

**詳細解析**：**「新人的第一週決定了他們之後的寫法」**：人會模仿他們看到的既有程式碼——**所以如果程式碼庫中同時存在三種寫法，新人會隨機挑一種並讓混亂延續**；**而一個乾淨的範例加上一個產生器，能讓多數人自然地走上正確的路徑**。**這也意味著「清理既有的不一致」的收益比看起來大**——**因為它不只修正了那幾個檔案，還改變了未來的產出**。**而在面試中能指出「架構的維持靠的是降低正確做法的阻力而非提高錯誤做法的懲罰」，展示的是對團隊實際運作方式的理解**；**因為在時間壓力下，人總是會選阻力最小的路徑。**

**面試回答方式**：給三個具體的手段並指出它們比架構文件有效。核心加分點是**新人的第一週決定了他們之後的寫法**——**人會模仿看到的既有程式碼，而三種並存的寫法會讓混亂延續**，並推論**清理既有的不一致收益比看起來大**。收在洞察：**架構的維持靠的是降低正確做法的阻力而非提高錯誤做法的懲罰**——**因為在時間壓力下人總是會選阻力最小的路徑**。
