# 題目

實驗室的效能測試和真實使用者的體驗常常不一致，該怎麼衡量？

## 核心答案

**兩種資料要一起用**：**實驗室資料**（Lighthouse、合成監控）——環境可控、可重現、適合在 CI 中偵測退步；**真實使用者資料（RUM）**——反映實際的裝置、網路與使用模式，是判斷「使用者的體驗到底如何」的唯一依據。

**兩者不一致的原因很具體**：實驗室通常用固定的網路與 CPU 設定（而真實使用者分布很廣）、**測的是冷啟動**（而真實使用者有快取）、**以及測的是首頁**（而真實流量可能集中在別的頁面）。

**RUM 要看的是分布而非平均**：平均值會被少數極端值拉高或者掩蓋問題——**應該看第 75 或第 95 百分位**；Core Web Vitals 的官方定義本身就是「第 75 百分位」。

而最有價值的分析是「按維度切分」：按裝置類型、網路狀況、地區、以及頁面類型分別看——因為一個看起來還好的整體數字，可能掩蓋了「所有 Android 使用者的體驗都很糟」這個事實。

## 詳細解析

「用 `web-vitals` 函式庫而非自己測量」：Core Web Vitals 的定義有很多細節（LCP 在使用者互動後就停止更新、CLS 只計算沒有使用者輸入的位移、INP 取的是特定的百分位）——自己實作幾乎一定與 Google 的定義不一致；而不一致的話，你的數字與搜尋排名的依據就對不上。

**「INP 取代 FID 的意義」**：FID 只測第一次互動的延遲——而 INP 測整個訪問期間所有互動的回應時間並取接近最差的值；這讓「首次很快但之後越來越卡」的應用無所遁形。改善 INP 的主要方向是「減少長任務」與「讓渲染的工作量與互動的規模相稱」（例如輸入時不要重新渲染整個列表）。

「歸因資料比數字本身更有行動價值」：知道 LCP 是 4 秒沒有告訴你該做什麼——而知道「LCP 元素是那張主視覺圖，其中 2.8 秒花在等待資源開始下載」就指向了明確的行動（提高優先權或預載）；現代的 RUM 工具能提供這類歸因，而它把監控從「知道有問題」變成「知道改什麼」。

**「取樣與成本的權衡」**：對高流量網站，收集每一次瀏覽的完整資料成本很高——而取樣（例如百分之十）通常足以看出趨勢；但要注意取樣可能讓罕見但嚴重的問題不可見，所以常見的做法是「一般資料取樣、錯誤與極端值全收」。

## 面試回答方式

先說明兩種資料的用途與不一致的三個具體原因，再強調**看分布而非平均**與**按維度切分**。加分點有四個：**用 `web-vitals` 函式庫而非自己測量**——否則你的數字與搜尋排名的依據對不上；**INP 取代 FID 的意義**——它讓「首次很快但之後越來越卡」無所遁形；歸因資料比數字本身更有行動價值；以及**取樣與成本的權衡**，做法是一般資料取樣、錯誤與極端值全收。

## 講稿

兩種資料要一起用。實驗室資料環境可控、可重現，適合在 CI 中偵測退步。真實使用者資料反映實際的裝置跟網路，是判斷體驗到底如何的唯一依據。

而它們不一致的原因很具體。實驗室用固定的網路跟 CPU 設定，測的是冷啟動，而且通常測首頁。真實使用者的分布很廣、有快取、流量也可能集中在別的頁面。

看 RUM 我一定看分布不看平均。平均會被少數極端值拉高，或者反過來掩蓋問題。Core Web Vitals 的官方定義本身就是第七十五百分位。

而最有價值的分析是按維度切分。按裝置、網路、地區、頁面類型分別看。因為一個看起來還好的整體數字，可能掩蓋了所有 Android 使用者體驗都很糟這個事實。

另外我會用官方的 web-vitals 函式庫而不是自己測量。那些指標的定義有很多細節，自己實作幾乎一定跟 Google 的不一致，而不一致的話你的數字跟搜尋排名的依據就對不上。

## 常見追問

### 效能預算怎麼在 CI 中執行？

**核心答案**：用合成測試在每次 PR 上跑並比較與基準的差異。可以檢查的包括：**打包產物的體積**（最穩定、最適合當硬性門檻）、**Lighthouse 的分數**（波動較大，適合看趨勢或者設寬鬆的門檻）、**以及關鍵頁面的載入指標。**

**詳細解析**：**「體積比分數更適合當門檻」**：因為打包體積是確定性的——同樣的程式碼永遠產出同樣的大小；而 Lighthouse 的分數在同一個提交上跑兩次可能差好幾分（受執行環境的負載影響）。所以常見的做法是「體積設硬門檻、分數設趨勢告警」。而更重要的是「門檻被超過時的流程」——如果只是印一個警告，那它會被忽略；而如果直接擋下合併卻沒有例外的機制，團隊會因為緊急需求而把整個檢查關掉。折衷是「擋下但允許明確標記例外並記錄原因」——於是每次超標都是一個有意識的決定而非默默的累積；這個模式在任何品質門檻上都適用。

**面試回答方式**：給可檢查的三類並指出體積比分數更適合當硬性門檻與原因（確定性 vs 環境波動）。核心加分點是**門檻被超過時的流程**——只印警告會被忽略，直接擋下沒有例外機制會讓團隊乾脆關掉檢查。收在折衷：擋下但允許明確標記例外並記錄原因，於是每次超標都是有意識的決定而非默默的累積。

### 怎麼判斷一次效能改善是真的有效？

**核心答案**：看 RUM 資料在發布前後的分布變化，並確認樣本足夠。單看發布後一天的數字可能受流量組成變化影響（週末的裝置分布與平日不同）——**而更嚴謹的做法是 A/B 測試**：讓一部分使用者拿到新版本，直接比較同時期的兩組資料。

**詳細解析**：「效能改善要連結到業務指標才有說服力」：「LCP 從 3.2 秒降到 2.1 秒」是技術指標——而「同時期的跳出率下降了百分之四、轉換率上升了百分之一點五」才是決策者關心的；而建立這個連結的方法正是 A/B 測試，因為它能排除其他因素。多個大型網站公開過這類數據（載入時間每減少 100 毫秒帶來的轉換率提升），而那些數字是效能工作能持續獲得投資的原因。所以在做效能專案時，一開始就設計好「怎麼證明它有效」，比事後補一個報告有用得多——因為事後你可能已經失去了對照組。

**面試回答方式**：給做法（看發布前後的分布並確認樣本，更嚴謹的是 A/B 測試）並說明單看一天的數字為什麼不可靠。核心加分點是效能改善要連結到業務指標才有說服力並對比技術指標與業務指標，指出 A/B 測試是建立連結的方法。收在建議：一開始就設計好「怎麼證明它有效」——因為事後你可能已經失去了對照組。

### 前端的可觀測性和後端的有什麼不同？

**核心答案**：執行環境不受控，而且資料要靠使用者的裝置回傳。後端的環境是你的——可以裝任何代理、記錄任何細節；而前端跑在千百種裝置與網路上，收集的資料本身會消耗使用者的流量與電力，還要處理隱私規範與廣告攔截器的阻擋。

**詳細解析**：「資料回傳的可靠性是一個特有的問題」：使用者關閉分頁時，未送出的資料會遺失——而 `navigator.sendBeacon` 或 `fetch` 的 `keepalive` 能在頁面卸載時仍然完成請求；這對「離開時的最終指標」（例如 CLS 的最終值）特別重要。而廣告攔截器會阻擋常見的分析網域——於是你的資料會系統性地缺少某一群使用者（而那群人往往是技術傾向較高的）；用自己網域的路徑代理（first-party）能減少這個偏差。理解「你收到的資料本身就是有偏差的樣本」，是正確解讀前端監控數據的前提——而這個偏差在後端監控中幾乎不存在。

**面試回答方式**：給兩個根本差異（**環境不受控、資料靠裝置回傳**）並列出前端特有的限制。核心加分點是**資料回傳的可靠性**（`sendBeacon` 與 `keepalive` 對離開時的最終指標特別重要）與廣告攔截器造成的系統性缺失。收在洞察：你收到的資料本身就是有偏差的樣本——這是正確解讀前端監控數據的前提，而這個偏差在後端幾乎不存在。
