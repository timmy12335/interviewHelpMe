# 題目

ESM 和 CommonJS 有什麼實際的差別？為什麼混用會出問題？

## 核心答案

**最根本的差別是「靜態 vs 動態」**。**ESM 的 import 是靜態的**——**在程式碼執行之前，依賴關係就已經確定**；**於是打包工具能做 tree shaking（分析哪些匯出沒被用到並移除）**。**CommonJS 的 require 是執行期的函式呼叫**——**可以放在條件式裡、路徑可以是變數**；**於是無法在編譯期確定依賴。**

**第二個差別是「載入的時機」**：**ESM 是非同步的且有明確的解析、實例化、求值三個階段**；**CommonJS 是同步的、執行到 require 那一行才載入。**

**第三個是「繫結的語意」**：**ESM 匯出的是「活的繫結」**（原模組改了值，引用方會看到新值）；**CommonJS 匯出的是「當下的值」的複製。**

**混用出問題的核心原因是「預設匯出的對應不明確」**——**CommonJS 的 `module.exports` 該對應到 ESM 的什麼，沒有唯一正確的答案**；**於是不同的工具做了不同的選擇，而 `import x from 'cjs-module'` 有時拿到的是整個物件、有時是 `.default`。**

## 詳細解析

**「循環依賴的行為不同」是一個實際的差異**：CommonJS 中，循環依賴會讓其中一方拿到「部分初始化」的模組（那些還沒執行到的匯出是 `undefined`）——**而 ESM 因為有提升（hoisting）的階段，函式宣告可以正常運作但變數仍然可能在暫時死區**；**兩者都會出問題，但症狀不同**。**而真正的解法是消除循環依賴而非依賴某個載入器的行為。**

**「tree shaking 的實際效果比預期弱」**：它要求模組是 ESM、沒有副作用、而且打包工具能證明移除是安全的——**而許多函式庫在頂層有副作用（修改全域、註冊 polyfill），於是整個模組無法被搖掉**；**`package.json` 的 `sideEffects: false` 就是在告訴打包工具「我保證沒有副作用」**。**所以「換成 ESM 就會變小」常常不成立，需要實際測量。**

**「Node 的雙套件問題」值得知道**：同一個套件如果同時提供 CJS 與 ESM 版本——**可能在同一個程序中被載入兩次（一個經由 require、一個經由 import）**；**於是模組層級的狀態（單例、快取、`instanceof` 檢查）會出錯**。**`exports` 欄位的條件式匯出是為了處理這個問題，但它也讓套件的設定變複雜。**

**「瀏覽器原生支援 ESM 但仍然需要打包」**：因為每個 import 都是一次網路請求——**幾百個模組意味著幾百次請求，即使有 HTTP/2 的多工，往返延遲仍然是成本**；**所以打包不是為了相容性而是為了減少請求數與最佳化載入順序。**

## 面試回答方式

先給三個根本差別（**靜態 vs 動態、載入時機、繫結語意**）與混用出問題的核心原因。加分點有四個：**循環依賴的行為不同**且**真正的解法是消除它而非依賴載入器的行為**；**tree shaking 的實際效果比預期弱**——**它要求沒有副作用，而 `sideEffects: false` 是那個保證**；**Node 的雙套件問題**與模組層級狀態的錯誤；以及**瀏覽器原生支援 ESM 但仍需打包**——**因為打包是為了減少請求數而非相容性**。

## 講稿

最根本的差別是靜態跟動態。ESM 的 import 是靜態的，在程式碼執行之前依賴關係就確定了，所以打包工具能做 tree shaking。CommonJS 的 require 是執行期的函式呼叫，可以放在條件式裡，路徑可以是變數，所以沒辦法在編譯期確定。

第二個差別是載入時機，ESM 是非同步而且分成解析、實例化、求值三個階段，CommonJS 是同步的。第三個是繫結語意，ESM 匯出的是活的繫結，原模組改了值引用方會看到，CommonJS 匯出的是當下的值的複製。

混用會出問題，核心原因是預設匯出的對應不明確。CommonJS 的 module.exports 該對應到 ESM 的什麼，沒有唯一正確的答案，所以不同工具做了不同選擇。

還有一點我覺得常被誤解。換成 ESM 不一定會讓打包變小，因為 tree shaking 要求模組沒有副作用。很多函式庫在頂層修改全域，那整個模組就搖不掉。

## 常見追問

### 動態 import 是什麼？它和靜態 import 怎麼配合？

**核心答案**：**`import()` 是一個回傳 Promise 的表達式**——**它讓你在執行期按需載入模組**；**而打包工具會把它當成一個分割點，把那個模組與它的依賴打包成獨立的檔案**。**典型的用途是路由層級的分割、以及只在特定條件下才需要的重量級功能**（圖表函式庫、編輯器、PDF 產生器）。

**詳細解析**：**「分割的粒度需要權衡」**：切得太細會產生大量的小檔案（每個都有請求開銷與執行開銷）——**而切得太粗則失去了按需載入的意義**；**實務上的常見做法是「按路由分割」加上「把幾個特別大的函式庫單獨分出來」**。**而一個容易被忽略的細節是「載入的時機」**：**在使用者點擊時才開始載入，會有明顯的等待**——**而在滑鼠移到按鈕上時就開始預載（`<link rel="prefetch">` 或者手動呼叫 `import()`），能讓感知延遲幾乎消失**；**這個「用意圖的訊號提前載入」的技巧，成本很低而效果明顯**。

**面試回答方式**：說明 `import()` 是回傳 Promise 的表達式與打包工具如何處理它，並給典型的用途。核心加分點是**分割的粒度需要權衡**與實務的常見做法（按路由加上單獨分出大函式庫）。收在技巧：**載入的時機**——**在滑鼠移到按鈕上時就開始預載，能讓感知延遲幾乎消失**；**用意圖的訊號提前載入，成本低而效果明顯**。

### 為什麼有些套件要求「必須用 import 不能用 require」？

**核心答案**：**因為它們是純 ESM 套件**（`package.json` 中 `"type": "module"` 且沒有提供 CJS 的進入點）。**而純 ESM 無法被同步的 `require` 載入**——**因為 ESM 的求值是非同步的**；**所以在 CommonJS 環境中只能用動態 `import()`，而那會讓呼叫方也變成非同步。**

**詳細解析**：**「這個限制造成了生態的分裂」**：許多知名的套件在近年轉為純 ESM——**而使用 CommonJS 的專案要嘛整個遷移，要嘛把那個相依改成動態載入並處理非同步的傳染**；**後者在測試工具、設定檔、以及 CLI 中特別麻煩**。**而「非同步的傳染」是這裡的關鍵詞**：**一旦某個模組必須用 `await import()` 載入，呼叫它的函式就要變成 async，而它的呼叫者也是**；**這個傳播可能一路影響到程式的進入點**。**理解這個機制，能解釋為什麼「只是升級一個套件」有時候會引發大範圍的重構**——**而在評估升級時把這一點納入考量，可以避免一個看起來簡單的變更變成兩週的工作。**

**面試回答方式**：說明純 ESM 套件與為什麼 `require` 載不了（**ESM 的求值是非同步的**）。核心加分點是**這個限制造成了生態的分裂**與**「非同步的傳染」**這個關鍵機制——**一旦某個模組要 `await import()`，呼叫鏈上的每一層都要變 async**。收在實用價值：**理解它能解釋為什麼「只是升級一個套件」有時會引發大範圍重構**。

### 打包工具在做的事，能不能簡單描述？

**核心答案**：**四件事**：**解析依賴圖**（從進入點出發，遞迴地找出所有 import）、**轉換**（TypeScript、JSX、以及舊語法的降級）、**優化**（tree shaking、壓縮、常數折疊、模組合併）、**以及輸出**（決定分成幾個檔案、如何命名以配合快取、產生 source map）。

**詳細解析**：**「新一代工具的差異主要在開發時的策略」**：Webpack 在開發時也會打包整個應用——**而 Vite 在開發時直接用瀏覽器原生的 ESM 提供未打包的模組（只做即時轉換），於是啟動時間與模組數量無關**；**這是啟動速度差異的根本原因，而非「用 Go 或 Rust 寫的所以比較快」**（雖然那也有影響）。**而正式建置時，多數工具仍然會打包**——**因為前述的請求數問題**。**理解「開發時不打包、正式時打包」這個策略，比記住工具的名稱有用**；**它也解釋了為什麼有些問題只在正式建置時出現**（開發時每個模組獨立，而打包後的模組合併可能暴露出副作用的順序問題）。

**面試回答方式**：給四件事並簡述各自在做什麼。核心加分點是指出**新一代工具的差異主要在開發時的策略**——**Vite 在開發時直接用原生 ESM，於是啟動時間與模組數量無關**，並澄清這比語言的選擇更關鍵。收在實用推論：**「開發時不打包、正式時打包」解釋了為什麼有些問題只在正式建置時出現**。
