# 題目

客戶端路由是怎麼實作的？它有哪些容易踩的坑？

## 核心答案

**實作的核心是 History API**：**`pushState` 改變網址而不觸發頁面載入**、`popstate` 事件接住瀏覽器的上一頁與下一頁、而路由庫攔截所有連結的點擊、阻止預設行為、改用 `pushState` 加上重新渲染。

**伺服器端的必要配合**：**任何路徑都要回傳同一份 HTML**（否則使用者直接輸入或重新整理 `/users/123` 會拿到 404）；這是單頁應用部署時最常見的問題。

**四個容易踩的坑**：**捲動位置**（切換頁面後應該回到頂部，而按上一頁時應該回到原本的位置——後者需要主動保存）；**焦點與螢幕閱讀器的宣告**（客戶端導航不會自動處理）；**離開頁面的確認**（有未儲存的變更時要攔截，但攔截 `pushState` 的導航和攔截關閉分頁是兩套機制）；**以及切換時的載入狀態**（如果新頁面需要載入資料，不處理的話畫面會空白一段時間）。

**而 hash 路由（`#/path`）與 history 路由的差別**，主要在於前者不需要伺服器配置但網址較醜且對 SEO 不利。

## 詳細解析

**「捲動的恢復需要主動處理」**：瀏覽器對傳統導航有內建的捲動恢復——**而客戶端路由要自己實作**：在離開一個頁面時記下捲動位置（存在 history 的 state 中），在 `popstate` 回到它時恢復；**而對於新的導航則捲到頂部**。`history.scrollRestoration = 'manual'` 可以關掉瀏覽器的預設行為以免衝突。

「導航期間的狀態設計影響感受」：如果新頁面需要載入資料——立刻切換到一個空的骨架，和停在舊頁面直到資料準備好，兩者的感受不同；後者（React 的 transition 支援的模式）在資料很快回來時體驗更好，因為避免了「閃一下骨架」；而如果超過一個門檻仍未回來，再顯示載入狀態。這個「延遲顯示載入指示」的做法能明顯減少畫面的閃動。

**「預取是低成本的體驗改善」**：在連結進入視窗或滑鼠移上去時，就預先載入那個路由的程式碼與資料——**於是點擊時幾乎立即完成**；代價是可能載入使用者不會去的頁面，所以要考慮流量（可以用 `navigator.connection` 在省流量模式下停用）。

「路由參數的型別與驗證」常被忽略：`/users/:id` 中的 id 是字串且可能是任何東西——直接拿去用可能造成錯誤的請求或者 XSS；在路由層做一次解析與驗證（用 schema），比在每個使用處防禦更可靠。

## 面試回答方式

先給實作核心（**History API 的三件事**）與伺服器端的必要配合，再列出四個坑。加分點有四個：**捲動的恢復需要主動處理**並說明新導航與上一頁的不同處理；**導航期間的狀態設計**——延遲顯示載入指示能減少畫面閃動；**預取是低成本的體驗改善**與它的流量考量；以及**路由參數的型別與驗證**應該在路由層做一次而非在每個使用處防禦。

## 講稿

核心是 History API。pushState 改變網址但不觸發頁面載入，popstate 接住瀏覽器的上一頁，而路由庫攔截連結的點擊，阻止預設行為，改用 pushState 加上重新渲染。

伺服器端要配合，任何路徑都回傳同一份 HTML。否則使用者直接輸入網址或重新整理會拿到 404。這是單頁應用部署時最常見的問題。

容易踩的坑我覺得有四個。第一個是捲動位置。切換到新頁面應該回到頂部，但按上一頁應該回到原本的位置，而後者要自己保存，瀏覽器不會幫你做。第二個是焦點跟螢幕閱讀器的宣告，客戶端導航不會自動處理。第三個是有未儲存變更時的離開確認，攔截前端導航跟攔截關閉分頁是兩套機制。第四個是切換時的載入狀態。

關於載入狀態有一個小技巧。如果資料很快回來，立刻顯示骨架反而會閃一下。我的做法是延遲一個門檻再顯示載入指示，這樣能明顯減少畫面閃動。

## 常見追問

### 為什麼有些網站切換路由時網址變了但內容沒更新？

**核心答案**：通常是元件沒有對參數的變化做出反應。React 中如果同一個元件在兩個路由間被重用（例如 `/users/1` 到 `/users/2`）——元件不會卸載重建，於是在 mount 時執行的資料載入不會再跑一次；解法是把參數放進 effect 的依賴，或者給元件一個以參數為值的 key 強制重建。

**詳細解析**：「用 key 強制重建是一個簡單但有代價的解法」：它保證了乾淨的狀態——但也丟掉了所有的內部狀態並重新掛載整棵子樹（包括重新執行所有的 effect 與動畫）；而如果只是需要重新取資料，用依賴陣列更精準也更有效率。判斷的依據是「切換參數時，元件的內部狀態應該保留還是重置」——例如一個編輯表單在切換到另一個使用者時應該重置（用 key 合適），而一個帶有展開狀態的列表可能希望保留。這個問題也是 React 中「同一個位置的同一個元件型別會被重用」這個核心規則的直接後果——理解那條規則，這類 bug 就從神秘變成可預期。

**面試回答方式**：給原因（元件被重用所以 mount 時的載入不再執行）與兩個解法。核心加分點是**用 key 強制重建有代價**——丟掉所有內部狀態並重新執行所有 effect，並給出判斷依據（切換參數時內部狀態應該保留還是重置）。收在根源：這是 React「同一個位置的同一個元件型別會被重用」這條規則的直接後果——理解它，這類 bug 就從神秘變成可預期。

### 巢狀路由解決什麼問題？

**核心答案**：**讓 URL 的結構對應到 UI 的巢狀結構**。`/settings/profile` 中，`/settings` 對應外層的版面與側邊欄、`profile` 對應內容區——於是切換內容時外層不需要重新渲染或重新取資料；而如果用扁平的路由，每個頁面都要自己重複整個版面。

**詳細解析**：「巢狀路由讓資料載入可以並行」：知道了完整的路由結構之後——框架可以同時發起外層與內層需要的請求，而不是等外層渲染完才發現內層還要載入；這消除了單頁應用中常見的「請求瀑布」（一層渲染觸發一層請求）。這是 Remix 與 React Router 的資料 API 帶來的主要收益，而它的前提正是「路由的結構在渲染前就已知」。理解這一點能解釋為什麼這些框架要求把資料載入宣告在路由上而非寫在元件裡——那不是風格的偏好，而是讓並行載入成為可能的必要條件；而請求瀑布往往是單頁應用感覺慢的主要原因之一。

**面試回答方式**：給核心價值（URL 結構對應 UI 巢狀結構，切換內層時外層不重新渲染）。核心加分點是巢狀路由讓資料載入可以並行——它消除了「一層渲染觸發一層請求」的瀑布，並指出這是 Remix 與 React Router 資料 API 的主要收益。收在推論：這解釋了為什麼那些框架要求把資料載入宣告在路由上而非寫在元件裡——那是讓並行成為可能的必要條件。

### 路由層級的權限控制怎麼做？

**核心答案**：在路由的載入階段檢查並重導向，但要記得前端的檢查只是體驗而非安全。做法是在進入路由前判斷（載入器或守衛），沒有權限就導向登入或無權限頁——而真正的防護必須在後端的每個 API 上；因為使用者可以直接呼叫 API，完全不經過你的前端。

**詳細解析**：「前端權限控制的真正目的是避免無意義的操作與資訊洩漏」：不顯示使用者無權使用的按鈕，避免他點了才被拒絕——**這是體驗**；而不在前端載入他無權看的資料，避免資料出現在網路面板中——這其實需要後端配合，因為如果 API 回了資料，前端「不顯示」是無效的。所以一個常見的錯誤是「後端回傳完整資料，前端根據角色決定顯示什麼」——那等於把資料公開給任何會打開開發者工具的人；正確的做法是後端根據呼叫者的權限決定回傳什麼。在面試中能指出這個區分，展示的是你理解「前端沒有秘密」這個基本事實。

**面試回答方式**：給做法（在路由載入階段檢查並重導向）並強調**前端檢查只是體驗而非安全**。核心加分點是說明**前端權限控制的真正目的**（避免無意義的操作），並點出常見的錯誤：後端回傳完整資料、前端決定顯示什麼——那等於把資料公開給任何會開開發者工具的人。收在原則：正確的做法是後端根據呼叫者的權限決定回傳什麼，而理解「前端沒有秘密」是基本事實。
