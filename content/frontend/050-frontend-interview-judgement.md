# 題目

前端的知識面很廣，準備面試時深度該放在哪裡？

## 核心答案

分成三層來準備，而它們的深度要求不同。

**一、不會過時的基礎要真的懂**：**JavaScript 的執行模型**（事件迴圈、閉包、原型）、**瀏覽器的渲染流程**、**HTTP 與快取**、**以及 CSS 的排版模型**——這些十年沒有太大變化，而它們是判斷其他一切的基礎；這一層的標準是「能解釋為什麼」而不只是「知道是什麼」。

二、當前主流框架的心智模型要清楚：不是背 API——而是理解「它什麼時候重新渲染」「狀態放在哪裡」「副作用怎麼被管理」；因為框架會換，但這些問題在每個框架中都存在。

**三、工程實踐要有具體的經驗**：效能怎麼測量與改善、錯誤怎麼被發現、測試怎麼分層、以及一個變更怎麼安全地上線——這一層區分了「會寫功能」與「能負責一個產品」。

而最能拉開差距的，是能對一個常見說法給出更精確的修正——「虛擬 DOM 不一定比較快」「SSR 改善的是內容可見時間而非互動可用時間」；這類回答證明了你理解到了原理而非停在結論。

## 詳細解析

「深度的檢驗是能不能回答第三層追問」：說得出防抖與節流的差別是第一層——能說出「防抖在連續輸入時可能一直不觸發，所以搜尋建議需要一個最大等待時間」是第二層；而能說出「這其實是延遲與資源消耗的取捨，而正確的參數取決於使用者的打字速度分布」是第三層。準備時對每個主題自問三次「所以呢」，能有效地找出自己的深度上限。

「廣度的價值在於能判斷該用什麼」：知道有 Web Worker、SSE、容器查詢、`content-visibility` 這些工具存在——在遇到對應的問題時就能想到它們；而不知道的話，會用更笨拙的方式解決或者根本不知道有問題。所以廣度不需要深入，但需要「知道它解決什麼問題」。

**「用實際做過的東西展示深度」**：一個真正優化過首屏的人，能說出「我們發現 LCP 的元素是主視覺圖，而它在字型載入完成後才開始下載，因為……」——**這種具體性無法靠背誦模擬**；所以在準備時，把自己做過的每一件事整理成「問題、診斷、行動、結果」的形式，比多讀十篇文章有用。

**「誠實地標記自己的邊界」**：前端的範圍太廣，沒有人樣樣精通——而「這一塊我用過但沒有深入，我理解的是……」比不懂裝懂好得多；因為面試官幾乎一定會追問到你不會的地方，那是探測深度的正常做法而非刁難。

## 面試回答方式

先給三層的劃分與各自的深度要求，並指出最能拉開差距的是能對常見說法給出更精確的修正。加分點有四個：深度的檢驗是能不能回答第三層追問，而準備時自問三次「所以呢」能找出自己的上限；廣度的價值在於能判斷該用什麼——不需要深入但要知道它解決什麼問題；**用實際做過的東西展示深度**，把經歷整理成「問題、診斷、行動、結果」；以及**誠實地標記自己的邊界**。

## 講稿

我會分三層準備，而它們的深度要求不同。

第一層是不會過時的基礎。JavaScript 的執行模型、瀏覽器的渲染流程、HTTP 快取、還有 CSS 的排版模型。這些十年沒有太大變化，而且是判斷其他一切的基礎。這一層的標準是能解釋為什麼，不只是知道是什麼。

第二層是當前框架的心智模型。不是背 API，而是理解它什麼時候重新渲染、狀態放在哪裡、副作用怎麼被管理。因為框架會換，但這些問題在每個框架裡都存在。

第三層是工程實踐。效能怎麼測量、錯誤怎麼被發現、測試怎麼分層。這一層區分了會寫功能跟能負責一個產品。

而我覺得最能拉開差距的，是能對一個常見說法給出更精確的修正。比如虛擬 DOM 不一定比較快，或者伺服器端渲染改善的是內容可見時間而不是互動可用時間。這類回答證明你理解到了原理而不是停在結論。

檢驗自己深度的方法很簡單，對每個主題自問三次所以呢。

## 常見追問

### 該不該把時間花在演算法題上？

**核心答案**：**看目標公司的流程**。大型科技公司的前端職位通常仍有演算法關——而多數的中小型公司更看重實作能力與框架的理解；所以應該先確認流程再分配時間，而不是預設所有面試都一樣。

**詳細解析**：「前端面試的實作題有它自己的類型」：手寫防抖與節流、實作一個 Promise、實作深拷貝、用原生 JS 做一個可拖曳的元件、或者在四十分鐘內做一個有互動的小介面——這些比純演算法題更常出現在前端面試中；而它們考的是「對語言與平台的熟練度」而非「解題技巧」。所以如果時間有限，練這一類的投資報酬率通常高於刷演算法。**而準備的方式也不同**：演算法靠模式的識別，而這一類靠實際寫過——因為它們的難點在細節（防抖的 this 綁定、深拷貝的循環引用、拖曳的邊界處理）而非思路。

**面試回答方式**：給判準（看目標公司的流程，不要預設所有面試都一樣）。核心加分點是指出前端面試的實作題有自己的類型並列舉，說明它們考的是**對語言與平台的熟練度**而非解題技巧。收在準備方式的差別：演算法靠模式識別，而這一類靠實際寫過——**因為難點在細節而非思路**。

### 沒有大型專案經驗怎麼展示能力？

**核心答案**：**用深度取代規模**。把一個小專案做到有測試、有效能考量、有錯誤處理、有部署流程——比列舉三個功能堆砌的專案更有說服力；而能說出「我在這裡遇到什麼問題、怎麼診斷、最後怎麼解決」的具體過程，是規模無法取代的。

**詳細解析**：「面試官在找的是思考的品質而非履歷的規模」：一個能把「為什麼我的列表在一千筆時變慢、我怎麼確認瓶頸、我試了什麼、最後用了什麼」講清楚的人——展示的能力和一個在大公司但只做過表單的人完全不同；而後者的專案規模再大也無法補上這個。所以準備的重點是「找出自己做過的東西中最有深度的一兩個點並把它們挖到底」——包括那些你當時繞過去但事後想想有更好解法的地方；主動說出「我當時用了 A，後來我理解到 B 會更好，因為……」是很強的信號，因為它證明了你的學習沒有停在專案結束的那一天。

**面試回答方式**：給策略（**用深度取代規模**）並說明什麼樣的敘述有說服力。核心加分點是面試官在找的是思考的品質而非履歷的規模並用具體的對比說明。收在準備重點：找出最有深度的一兩個點挖到底，包括當時繞過去但事後有更好解法的地方——主動說出「我當時用了 A，後來理解到 B 更好」證明了你的學習沒有停在專案結束那天。

### 前端變化這麼快，怎麼避免學到過時的東西？

**核心答案**：**把時間分配給「變化慢的東西」**。瀏覽器的渲染機制、網路協定、JavaScript 的語言核心、以及使用者體驗的原則——**這些的半衰期是十年**；而具體框架的 API 半衰期可能是兩年；所以在基礎上的投入，回報期長得多。

**詳細解析**：「用『它解決什麼問題』的角度學新東西」：如果你理解了「hydration 的成本從哪裡來」——那伺服器元件、islands、以及未來任何新的方案，你都能快速地判斷它們在解決同一個問題的哪一部分；而只記得 API 的人，每次都要重新學一遍。所以學習新框架時，最有價值的問題是「它與前一代相比，改變了什麼假設」——因為那個改變才是知識，而 API 只是它的表面。這個習慣也讓你在面試中談論新技術時，能給出判斷而非只是描述；**而判斷正是資深與否的分界。**

**面試回答方式**：給策略（**把時間分配給變化慢的東西**）並用半衰期的對比說明。核心加分點是用「它解決什麼問題」的角度學新東西——理解了 hydration 的成本從哪來，就能快速判斷任何新方案在解決哪一部分，而只記 API 的人每次都要重學。收在方法：學新框架時最有價值的問題是「它改變了什麼假設」——那個改變才是知識，而 API 只是表面。
