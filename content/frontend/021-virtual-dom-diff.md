# 題目

虛擬 DOM 為什麼能提升效能？它一定比直接操作 DOM 快嗎？

## 核心答案

**不一定，而且單就速度而言通常更慢**——虛擬 DOM 多了「建立虛擬樹、比對、再套用到真實 DOM」這幾步，手寫的精準 DOM 操作永遠更快。它真正的價值是**用宣告式的心智模型換取可維護性**：你只描述「資料長這樣時畫面應該長什麼樣」，不必自己追蹤「哪些地方變了、要改哪幾個節點」——而後者正是手寫 DOM 操作最容易出錯、也最難維護的部分。效能上它提供的是**下限保證**而非上限：它把大量零散的 DOM 操作**批次合併**成一次更新，避免了新手最常見的效能陷阱（在迴圈中反覆讀寫 DOM 造成版面計算抖動）。所以正確的說法是：**虛擬 DOM 讓「寫得好」的成本大幅降低，而不是讓程式跑得比手寫最佳解更快**。理解這一點才能解釋為什麼有些框架（Svelte、Solid）選擇不用虛擬 DOM，改在編譯期就算出要更新哪些節點。

## 詳細解析

**diff 的三個假設讓它從 O(n³) 降到 O(n)**：完整的樹比對演算法是立方複雜度，不可用。React 用三個啟發式假設把它降到線性——**不同型別的元素會產生完全不同的樹**（所以型別一變就整棵重建，不再往下比）、**同層級的比對不跨層移動**（節點換到別的父層下就是刪掉再建立）、以及**開發者可以用 `key` 提示哪些子元素在不同渲染間是同一個**。這三個假設在絕大多數真實 UI 中成立，代價是少數情況會多做一些工作。

**key 的作用與代價**：沒有 `key` 時，框架只能依索引比對——在列表開頭插入一個項目會導致後面每一項都被判定為「內容變了」，於是全部更新。有了穩定的 `key`，框架能認出「這些是同一批元素只是位置變了」，只做移動。用**索引當 key** 等同於沒有 key 的效果，而且在有元件內部狀態（輸入框的值、展開狀態）時會造成**狀態錯位**——這是實務上最常見的 bug 之一。

**批次更新是效能收益的主要來源**：多次狀態變更會被合併成一次重新渲染與一次 DOM 更新。這避免了「改一次 DOM、讀一次幾何屬性」造成的強制同步版面計算。手寫程式碼要達到同樣效果需要自行設計批次機制，而多數人不會這麼做——這才是虛擬 DOM 在實務上「比較快」的真正原因。

**不用虛擬 DOM 的路線**：Svelte 在**編譯期**分析出哪些狀態影響哪些節點，直接產生精準的更新程式碼；Solid 用**細粒度的響應式系統**，狀態變更直接觸發對應節點的更新，不需要比對。兩者的共同點是**把找出差異的工作從執行期移到編譯期或訂閱關係上**，因此執行期的成本更低、打包體積也更小。代價是編譯期方案對動態性的支援受限、且需要特定的編譯工具鏈。

**虛擬 DOM 的額外價值常被忽略**：它讓渲染目標**可抽換**——同一套元件邏輯可以渲染到瀏覽器 DOM、原生行動介面、canvas、甚至測試用的假樹。這種跨平台能力是虛擬 DOM 這層抽象的副產品，也是它在大型生態系中的重要價值。

## 面試回答方式

第一句就直接糾正前提——**虛擬 DOM 不一定比較快，單就速度而言通常更慢**，這比順著問題講「它很快」有辨識度得多。接著給它真正的價值：用宣告式模型換可維護性，並提供效能的**下限保證**（批次合併避免零散操作）。diff 的部分要講出**三個啟發式假設**如何把 O(n³) 降到 O(n)。`key` 要主動展開，特別是**用索引當 key 會造成狀態錯位**這個實務 bug。加分點是講不用虛擬 DOM 的路線（Svelte 編譯期、Solid 細粒度響應式）以及它們的共同思路，再補一句虛擬 DOM 讓渲染目標可抽換這個常被忽略的價值。

## 講稿

我會先說一件可能跟預期相反的話，虛擬 DOM 不一定比較快，單論速度它通常更慢，因為多了建虛擬樹、比對、再套用這幾步。手寫的精準 DOM 操作永遠更快。

它真正的價值是心智模型。我只要描述資料長這樣時畫面該長什麼樣，不用自己追蹤哪裡變了要改哪幾個節點，而那正是手寫最容易出錯也最難維護的部分。

效能上它給的是下限保證，不是上限。它把大量零散的 DOM 操作批次合併成一次更新，避免了在迴圈裡反覆讀寫 DOM 造成的版面計算抖動。所以與其說它快，不如說它讓寫得好的成本大幅降低。

diff 本身如果做完整的樹比對是立方複雜度，不可用。React 用三個假設把它降到線性，型別不同就整棵重建、同層級比對不跨層移動、還有用 key 提示哪些是同一個元素。

key 我想特別講。用索引當 key 等於沒有 key，而且如果元件有內部狀態，像輸入框的值，在列表開頭插入一項就會造成狀態錯位。這是我看過最常見的 bug 之一。

## 常見追問

### 為什麼用索引當 key 會出問題？

**核心答案**：因為索引**不跟著資料走**。在列表開頭插入一項後，原本索引 0 的資料變成索引 1，但框架看到的是「索引 0 的內容變了、索引 1 的內容變了……」，於是把所有項目都判定為內容更新而非位置移動。如果元件有內部狀態（輸入框的值、勾選狀態、展開收合），那些狀態會**留在原本的位置**上，導致資料與狀態錯位——使用者在第一列輸入的內容，插入新項目後出現在第二列。

**詳細解析**：這個問題只有在**列表順序會變動**（插入、刪除、排序）且**項目有內部狀態或昂貴的重新渲染**時才顯現，所以在靜態列表上用索引不會出錯——這也是為什麼它容易被忽略，測試時看不出問題，上線後才被使用者發現。正確的 key 應該是**資料本身穩定且唯一的識別**（通常是後端給的 ID）。如果資料真的沒有 ID，可以在載入時產生一次並保存在資料中，而不是每次渲染都產生新的（那會讓每次都完全重建）。另外要注意 key 只需要在**同一個父層的兄弟之間唯一**，不需要全域唯一。

**面試回答方式**：核心是索引不跟著資料走，導致移動被誤判成內容變更、狀態留在原位。用「在第一列輸入後插入新項目」這個具體場景說明。加分點是指出這個 bug 只在順序變動且有內部狀態時顯現，所以測試時容易漏掉，以及 key 只需在兄弟之間唯一。

### React 的 memo 和 useMemo 什麼時候該用？

**核心答案**：**量測到問題之後才用**。兩者都不是免費的——記憶化本身要比較依賴、佔用記憶體，對輕量的元件與運算，成本可能高於它省下的。合理的使用時機是：**元件重新渲染的成本明顯**（渲染大型列表、複雜圖表）、**依賴很少變動**、以及**父元件頻繁重新渲染而子元件的 props 實際上沒變**。反過來，對一個只渲染幾個文字節點的元件加 `memo`，通常是淨損失。

**詳細解析**：更關鍵的認知是 **`memo` 常常無效**——只要父元件傳下來的 props 中有每次渲染都新建的物件、陣列或函式，淺比較就會失敗，`memo` 形同虛設。所以用 `memo` 通常要連帶處理傳入的 props（用 `useCallback` 與 `useMemo` 穩定參照），這讓程式碼變複雜。實務上更有效的做法往往是**結構性的調整**：把狀態下移到真正需要它的元件（縮小重新渲染的範圍）、把不變的部分作為 children 傳入（children 的參照不變就不會重新渲染）。這些調整不需要記憶化就能解決問題，而且更容易維護。能提出結構性解法而不是一律加 `memo`，是這題最能拉開差距的地方。

**面試回答方式**：先給原則——量測到問題才用，並說明記憶化本身有成本。重點指出 `memo` 常因為 props 中的新建物件而失效，所以要連帶穩定參照，程式碼會變複雜。加分點是提出結構性解法（狀態下移、把不變的部分作為 children 傳入）優先於記憶化。

### 為什麼 Svelte 說自己「沒有虛擬 DOM」？

**核心答案**：因為它在**編譯期**就分析出「哪個狀態影響哪些 DOM 節點」，直接產生精準的更新程式碼——狀態變更時執行的是「把這個文字節點的內容改成新值」這種具體指令，不需要在執行期建立虛擬樹再比對。結果是**執行期沒有比對成本、也不需要把框架的執行期程式碼全部送給瀏覽器**，打包體積更小。

**詳細解析**：這條路線的代價是**動態性受限**——編譯期需要能靜態分析出依賴關係，所以某些高度動態的模式會比較難表達或需要額外標註。另外它需要專屬的編譯步驟，元件不是純粹的 JavaScript。Solid 走的是另一條路——執行期的**細粒度響應式**，狀態與使用它的 DOM 節點之間建立訂閱關係，變更時直接通知，同樣不需要比對整棵樹。兩者的共同觀念是：**找出「什麼變了」這件事，不一定要在每次更新時重新算，可以事先建立好對應關係**。這個觀念也正在影響 React 的發展方向（例如編譯器自動插入記憶化）。能講出這條共同脈絡，比比較個別框架的優劣更有價值。

**面試回答方式**：說明 Svelte 在編譯期產生精準更新程式碼，所以執行期沒有比對成本且體積更小。誠實給出代價（動態性受限、需要編譯步驟）。加分點是把 Solid 的細粒度響應式並列，並歸納共同觀念——事先建立對應關係取代每次重算，並指出這個方向也在影響 React。
