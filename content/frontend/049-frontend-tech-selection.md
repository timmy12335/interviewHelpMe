# 題目

一個新的前端專案，你會怎麼決定技術選型？

## 核心答案

**先從約束而非從偏好開始**。要確認的有五項：**產品的性質**（內容型網站、後台工具、還是高互動的應用——這決定了渲染模式）、**SEO 與首屏的重要性**、**團隊已有的技能**、**維護的年限與人員的流動性**、**以及部署的環境限制**（能不能跑 Node、有沒有 CDN）。

**這五項通常已經把選項收斂到一兩個**——**而剩下的差異往往沒有想像中重要。**

**幾個具體的對應**：**內容型且重視 SEO** → **靜態生成或伺服器端渲染的框架**；**登入後的後台工具** → **純客戶端渲染就夠，不需要 SSR 的複雜度**；**高互動且需要離線** → **考慮 PWA 與本地優先的資料架構。**

**而最重要的判斷是「你的團隊能不能長期維護它」**——**一個技術上更優但團隊不熟悉、社群小、且只有一個人懂的選擇，在那個人離開時會變成負債**；**這個因素的權重通常應該高於技術指標本身。**

## 詳細解析

**「選型的可逆性應該被納入考量」**：換一個 UI 元件庫是幾週的工作——**而換一個框架可能是重寫**；**所以在不確定性高的部分應該選更容易替換的，而在確定的部分可以接受更深的耦合**。**具體的做法是「把框架特有的東西集中在少數地方」**——**業務邏輯用純函式，於是它們在任何框架中都能用。**

**「社群規模的實際影響常被低估」**：一個小眾框架在遇到問題時，你可能是第一個遇到的人——**而在主流框架中，多數問題搜尋一下就有答案**；**這個差別在專案的整個生命週期中累積起來是巨大的**。**同樣地，招募的難易度也是一個真實的成本。**

**「不要用一個專案來學新技術」**：如果團隊都不熟悉某個框架——**那專案的前三個月會同時付出學習成本與錯誤決策的成本**；**而正確的做法是先在一個小的、低風險的專案上試用**。**在面試中能說出這個判斷，展示的是你會為結果負責而非追求新鮮感。**

**「注意『我們可能需要』的陷阱」**：為了「未來可能需要 SSR」而現在就引入它的複雜度——**常常是不划算的**；**因為多數的「可能需要」不會發生，而發生時的改造成本往往低於一直背負的複雜度**。**判斷的方法是估算「現在做的成本」與「事後補做的成本乘上發生的機率」。**

## 面試回答方式

先給五項要確認的約束並指出**它們通常已經把選項收斂到一兩個**，再給幾個具體的對應，最後強調**團隊能不能長期維護**這個最重要的判斷。加分點有四個：**選型的可逆性**與「把框架特有的東西集中在少數地方」；**社群規模的實際影響常被低估**（包括招募成本）；**不要用一個專案來學新技術**；以及**「我們可能需要」的陷阱**與估算的方法。

## 講稿

我會先從約束開始而不是從偏好開始。

要確認五件事。產品的性質是內容型、後台工具、還是高互動的應用，這決定渲染模式。SEO 跟首屏有多重要。團隊已有的技能。維護的年限跟人員流動。還有部署環境的限制。

這五項通常已經把選項收斂到一兩個，剩下的差異往往沒有想像中重要。

而我認為最重要的判斷是團隊能不能長期維護它。一個技術上更優但團隊不熟、社群小、只有一個人懂的選擇，在那個人離開時會變成負債。這個因素的權重通常應該高於技術指標本身。

另外有一個陷阱我會特別注意，就是我們可能需要。為了未來可能需要伺服器端渲染而現在就引入複雜度，常常不划算。因為多數的可能需要不會發生，而真的發生時的改造成本往往低於一直背負的複雜度。

我的估算方法是比較現在做的成本，跟事後補做的成本乘上發生的機率。

## 常見追問

### 該不該用最新的框架版本或功能？

**核心答案**：**看它解決的問題是否是你當下真的有的**。新版本常常帶來實質的改善——**但也可能有未成熟的邊界情況、不完整的生態支援、以及還在變動的 API**；**所以判斷的方式是「這個功能解決的痛點，我現在痛不痛」而非「它是不是更先進」。**

**詳細解析**：**「早期採用的成本主要在生態而非核心」**：一個新的框架功能本身可能很穩定——**但你依賴的十個函式庫可能還沒支援它**；**於是你會花大量時間在整合的邊緣問題上，而那些問題在半年後會自動消失**。**所以「等一兩個小版本」通常是划算的策略**——**除非那個功能解決的正是你當下的主要痛點**。**而一個實用的做法是「在非關鍵的部分先試用」**——**例如在一個內部工具或者一個新的小功能上，於是你能累積實際的經驗而風險有限**；**這比在主要產品上豪賭，或者完全不碰新技術，都是更好的中間路線。**

**面試回答方式**：給判準（**這個功能解決的痛點我現在痛不痛**）而非新舊。核心加分點是**早期採用的成本主要在生態而非核心**——**核心可能很穩定但依賴的函式庫還沒支援，而那些問題半年後會自動消失**。收在中間路線：**在非關鍵的部分先試用**，**這比在主要產品上豪賭或完全不碰新技術都更好**。

### 如果接手一個技術棧很舊的專案呢？

**核心答案**：**先評估它「還能不能安全地運作」而非急著現代化**。要看的是：**有沒有已知的安全漏洞**（相依的版本）、**能不能正常建置與部署**、**以及團隊改動它的效率**；**如果這三項都還可以，那全面重寫通常不是最好的投資。**

**詳細解析**：**「漸進的現代化幾乎總是優於重寫」**：重寫需要在很長一段時間內維護兩套系統且沒有新功能產出——**而在那段期間，業務不會停下來等你**；**這是重寫專案失敗率高的結構性原因**。**可行的漸進路徑包括**：**先升級能安全升級的相依**、**在新功能中使用新的模式**（讓新舊共存）、**用一個嚴格的邊界把新的部分隔開**、**以及在修改既有程式碼時順手改善它**。**而如果真的必須替換整個框架，「絞殺者模式」（新舊並存並逐頁遷移）比一次切換風險低得多**——**代價是過渡期的複雜度**；**這個取捨在面試中能說清楚，展示的是你處理過真實的遺留系統而非只做過新專案。**

**面試回答方式**：給評估的三項並指出**如果都還可以，全面重寫通常不是最好的投資**。核心加分點是**漸進的現代化幾乎總是優於重寫**與它的結構性原因（**重寫期間業務不會停下來等你**），並列出可行的漸進路徑。收在方法：**絞殺者模式比一次切換風險低得多**，**而能說清楚這個取捨展示的是你處理過真實的遺留系統**。

### 選型錯了怎麼辦？

**核心答案**：**先確認是「選錯了」還是「還沒熟悉」**。許多被歸咎於技術的痛苦，實際上來自不熟悉它的慣用做法——**而換一個技術會讓學習曲線重來一次**；**所以在決定更換之前，值得先確認問題是否能透過調整用法解決。**

**詳細解析**：**「真正該換的訊號比較明確」**：框架已經停止維護且有安全問題、需要的功能它本質上不支援（而非只是麻煩）、或者社群已經大規模遷移導致生態萎縮——**這些是結構性的問題**；**而「寫起來不順」「不如某個新框架優雅」通常不是**。**而即使確定要換，也應該量化「換的成本」與「不換每年的成本」**——**因為前者是一次性的而後者是持續的，兩者的比較才是決策的依據**。**在面試中能展示這個「用成本而非偏好做技術決策」的思考方式，往往比你選了哪個技術更能得分**；**因為前者可以遷移到任何新的技術情境，而後者會過時。**

**面試回答方式**：給第一步（**確認是選錯了還是還沒熟悉**）並指出換技術會讓學習曲線重來。核心加分點是**真正該換的訊號比較明確**並列出三個結構性問題，對比「寫起來不順」這類非結構性的抱怨。收在決策方法：**量化「換的成本」與「不換每年的成本」**——**前者一次性後者持續**；**而這個「用成本而非偏好做決策」的方式可以遷移到任何新的技術情境**。
