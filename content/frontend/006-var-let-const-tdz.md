# 題目

`var`、`let`、`const` 差在哪？「提升」到底提升了什麼？

## 核心答案

三個維度：**作用域**、**提升行為**、**能否重新賦值**。`var` 是**函式作用域**，在 `if` 或 `for` 區塊裡宣告仍然屬於整個函式；`let` 與 `const` 是**區塊作用域**，只在最近的 `{}` 內有效。提升的部分最容易被誤解——**三者都會提升**，差別在於 `var` 提升後會被**初始化為 `undefined`**（所以宣告前存取得到 `undefined`），而 `let` 與 `const` 提升後**沒有初始化**，在執行到宣告那一行之前處於**暫時死區**（TDZ），存取會直接拋出 `ReferenceError`。這個設計是刻意的：讓「宣告前使用」變成明確的錯誤，而不是拿到 `undefined` 之後在別的地方才炸掉。`const` 的限制是**不能重新賦值綁定**，不是「值不可變」——`const arr = []` 之後 `arr.push(1)` 完全合法，要真正凍結物件得用 `Object.freeze`（而且它只凍結第一層）。

## 詳細解析

**var 的兩個實際問題**：一是**變數洩漏出區塊**——在 `if` 裡宣告的變數在區塊外仍然存在，容易造成意外的覆蓋。二是**迴圈中的共享變數**——`for (var i = 0; ...)` 中的 `i` 整個函式只有一份，所有在迴圈中建立的閉包捕獲的是同一個變數，於是非同步回呼全部讀到最終值。`let` 在**每輪迭代建立新的綁定**，所以每個閉包各自捕獲不同的變數，這是它最實用的差異。

**暫時死區的價值**：它把一類隱蔽的 bug 變成明確的錯誤。用 `var` 時，宣告前存取得到 `undefined`，程式繼續執行，錯誤可能在幾行之後才以「無法讀取 undefined 的屬性」的形式出現，離真正的原因很遠。TDZ 讓錯誤在**發生的當下**就拋出，除錯成本低得多。這是「**盡早失敗**」原則在語言設計上的體現。

函式宣告與函式運算式的提升不同：`function foo(){}` 這種函式宣告會**連同函式體一起提升**，所以可以在定義前呼叫；而 `const foo = function(){}` 或箭頭函式屬於變數宣告，遵守 `const` 的 TDZ 規則，宣告前呼叫會拋錯。這個差異常被拿來出題。

**實務上的選擇順序**：預設用 `const`，需要重新賦值才用 `let`，不使用 `var`。這個順序的價值不在於強制不可變，而在於**傳達意圖**——看到 `const` 就知道這個綁定不會改變，閱讀時少一件要追蹤的事。多數 lint 規則會強制這個慣例。

**const 與不可變的區別要講清楚**：`const` 保證的是**綁定不會指向另一個值**，物件內部仍然可以修改。要真正的不可變需要 `Object.freeze`（淺層）、遞迴凍結（深層）、或使用不可變資料結構函式庫。在 React 這類依賴參照比較來判斷是否更新的框架中，理解這個差別特別重要——直接修改物件內部不會改變參照，元件就不會重新渲染。

## 面試回答方式

用三個維度組織回答：作用域、提升、能否重新賦值。**提升那一段要講精確**——三者都提升，差別在 `var` 提升後初始化為 `undefined`、`let` 與 `const` 沒有初始化所以進入暫時死區。並說明 TDZ 是刻意設計，讓錯誤在當下就拋出而不是延後爆炸。`const` 的部分要主動澄清**它限制的是綁定不是值**，並舉 `const arr` 仍可 `push` 為例。加分點有兩個：`let` 在迴圈中每輪建立新綁定，這是閉包捕獲行為的關鍵；以及函式宣告會連同函式體一起提升，但箭頭函式賦值給 `const` 不會。

## 講稿

我從三個維度看，作用域、提升、還有能不能重新賦值。

var 是函式作用域，寫在 if 或 for 裡面也還是屬於整個函式。let 跟 const 是區塊作用域，只在最近的大括號裡有效。

提升這件事我想講精確一點。三個其實都會提升，差別在提升之後有沒有被初始化。var 提升之後會被初始化成 undefined，所以宣告前存取拿得到 undefined。let 跟 const 提升之後沒有初始化，在執行到宣告那一行之前是暫時死區，存取會直接拋錯。

這個設計我覺得是好的。用 var 的時候，宣告前拿到 undefined，程式會繼續跑，錯誤可能在好幾行之後才以另一種形式炸出來，離真正的原因很遠。暫時死區讓錯誤在當下就發生。

const 我要澄清一下，它限制的是綁定不能指向另一個值，不是值不可變。const 宣告一個陣列之後，push 是完全合法的。要真的不可變得用 Object.freeze，而且它只凍結第一層。

還有一個很實用的差異，let 在迴圈裡每一輪都會建立新的綁定，所以每個閉包捕獲到的是不同的變數。用 var 的話全部共用同一個。

## 常見追問

### 為什麼 let 在迴圈中每輪建立新綁定？

**核心答案**：這是規範對 `for` 迴圈的**特別規定**——當迴圈變數用 `let` 宣告時，每次迭代都會建立一個新的詞法環境，並把上一輪的值複製進來。所以每一輪的迴圈體（包括其中建立的閉包）看到的是**屬於那一輪的變數**。這個設計正是為了解決 `var` 時代必須用立即執行函式才能達到的效果。

**詳細解析**：要注意這個特殊處理**只適用於 `for` 迴圈的宣告部分**。如果你在迴圈體內用 `let` 宣告變數，那本來就是每輪一個新變數（區塊作用域的自然結果），不需要特殊規定。另外 `for...of` 與 `for...in` 也有同樣的行為。實務上這個差異最常在**非同步操作**中顯現——迴圈中發起多個請求並在回呼中使用索引，用 `var` 會全部拿到最終值。理解這一點也有助於理解 React hooks 的閉包行為，因為兩者的本質相同：閉包捕獲的是變數，而變數屬於哪個環境決定了你看到什麼值。

**面試回答方式**：說明這是規範對 `for` 迴圈的特別規定——每次迭代建立新環境並複製上一輪的值。點出它取代了過去必須用立即執行函式的做法。加分點是澄清這個特殊處理只針對迴圈宣告部分，以及把它連結到 React hooks 的閉包行為是同一個本質。

### Object.freeze 能做到真正的不可變嗎？

**核心答案**：**只能凍結第一層**。`Object.freeze(obj)` 之後不能新增、刪除或修改 `obj` 的直接屬性，但如果某個屬性的值是物件，**那個巢狀物件仍然可以修改**。要深層凍結必須遞迴地對每個物件屬性呼叫 `freeze`。另外要注意在非嚴格模式下，對凍結物件賦值會**靜默失敗**而不是拋錯，這讓 bug 更難發現——ES 模組預設嚴格模式，所以現代程式碼會拋錯。

**詳細解析**：實務上很少對整個資料結構做深層凍結，因為遞迴凍結有效能成本，而且凍結是不可逆的。更常見的做法是在開發環境凍結以偵測意外的修改，正式環境不凍結，或者根本不依賴凍結，而是用**不可變的更新模式**——每次修改都建立新物件（展開運算子、`map`、`filter`），這樣既保證了參照的變化（框架能偵測到更新），也避免了共享狀態被意外修改。這個模式在 React 與 Redux 中是強制的慣例，理解「為什麼需要新的參照」比記住語法重要。

**面試回答方式**：明確說只凍結第一層，並說明深層需要遞迴。主動提非嚴格模式下會靜默失敗這個陷阱。加分點是給出實務做法——開發環境凍結來偵測、正式環境靠不可變更新模式，並解釋為什麼框架需要新的參照。

### 「暫時死區」在實務上會怎麼被踩到？

**核心答案**：最常見的是在同一個作用域中，於宣告之前使用了同名變數——特別是當外層作用域有同名變數時，你可能以為讀到的是外層的值，實際上內層的 `let` 宣告已經讓這個名字在整個區塊中被遮蔽，於是拋出 `ReferenceError` 而不是讀到外層的值。另一個場景是 **`typeof` 也會拋錯**——對 TDZ 中的變數用 `typeof` 不像對未宣告變數那樣安全地回傳 `'undefined'`。

**詳細解析**：這個「遮蔽整個區塊」的行為是理解 TDZ 的關鍵——`let` 的宣告在**進入區塊時就生效**（變數已存在但未初始化），而不是執行到那一行才生效。所以區塊內從頭到宣告之間的整段都是死區。實務上要避免這類問題，最好的習慣是把宣告放在使用之前、且盡量靠近使用處，這本來就是可讀性上的好做法。另外在 `switch` 語句中特別容易踩到，因為所有 `case` 共用同一個區塊作用域——在一個 `case` 裡用 `let` 宣告的變數，在其他 `case` 中也存在（且可能在死區裡），解法是為每個 `case` 加上獨立的大括號。

**面試回答方式**：給出最常見的場景——內層宣告遮蔽外層同名變數，導致宣告前存取拋錯而不是讀到外層值。補充 `typeof` 在 TDZ 中也會拋錯這個細節。加分點是提到 `switch` 的所有 case 共用區塊作用域這個實際陷阱，以及用獨立大括號解決。
