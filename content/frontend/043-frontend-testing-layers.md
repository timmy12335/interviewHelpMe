# 題目

前端該測什麼？各層測試的比例怎麼分配？

## 核心答案

判準是「這個測試在什麼情況下會失敗」——好的測試只在行為真的壞掉時失敗；而測試實作細節（內部 state、私有方法、DOM 結構）的測試，會在重構時失敗而在真的壞掉時通過。

**分層與各自的用途**：**單元測試**——純函式、格式化、複雜的計算與狀態轉換邏輯；**快、穩定、定位精確**。**元件測試**——**用使用者的視角操作元件**（用可見的文字與角色查詢，而非類名或測試 ID）；這一層的投資報酬率通常最高。**端到端測試**——**只覆蓋最關鍵的少數流程**（登入、結帳、核心的建立流程）；它最接近真實但也最慢最脆弱。

比例的實際建議是「元件測試為主」而非傳統的金字塔——因為前端的邏輯多數存在於元件的互動中，而現代的元件測試工具已經足夠快；端到端測試維持在十幾條關鍵路徑即可。

## 詳細解析

「用使用者能感知的方式查詢元素」是這一層的核心原則：`getByRole('button', { name: '送出' })` 比 `container.querySelector('.btn-primary')` 好——因為前者在改了類名後仍然通過，而在按鈕文字錯了或者角色不對時會失敗；這正好對應了「使用者能不能找到並使用它」。而這個查詢方式的副作用是它同時檢驗了無障礙——找不到角色的元素，螢幕閱讀器也找不到。

**「不要測試框架本身」**：測試「點了按鈕之後 state 變成 true」是在測 React——而測試「點了按鈕之後畫面出現了確認訊息」才是在測你的行為；前者在重構成別的狀態管理方式時會失敗，而使用者的體驗根本沒變。

**「模擬網路要在正確的層級」**：直接模擬你的 API 客戶端函式，會讓「請求的網址或參數寫錯」這類 bug 逃過測試——而在網路層攔截（MSW 這類工具）能讓測試涵蓋整個請求的組裝；而且同一套模擬可以在開發環境重用。

**「視覺回歸測試的定位」**：它抓的是單元與元件測試抓不到的問題（版面錯位、樣式衝突、跨瀏覽器的差異）——**但它也最容易產生誤報**（字型的細微差異、動畫的時間點）；所以應該用在少數穩定且重要的畫面上，而非全面覆蓋。

## 面試回答方式

先給核心判準（**只在行為真的壞掉時失敗**）並指出測試實作細節的問題，再給三層的用途與比例建議（**元件測試為主**）。加分點有四個：用使用者能感知的方式查詢元素，而它的副作用是同時檢驗了無障礙；**不要測試框架本身**並給出具體的對比；**模擬網路要在正確的層級**——在網路層攔截能涵蓋請求的組裝且可在開發環境重用；以及**視覺回歸測試的定位**與它容易誤報的特性。

## 講稿

我的判準是這個測試在什麼情況下會失敗。好的測試只在行為真的壞掉時失敗。而測試實作細節的測試，會在重構時失敗，卻在真的壞掉時通過，那是最糟的組合。

分層上，單元測試我用在純函式、格式化、複雜的計算。元件測試是用使用者的視角操作元件，我覺得這一層的投資報酬率最高。端到端只覆蓋最關鍵的少數流程。

## 常見追問

### 端到端測試很不穩定怎麼辦？

**核心答案**：多數的不穩定來自等待的方式錯了。用固定時間的 `sleep` 必然在慢的環境失敗——**而應該等待明確的條件**（某個元素出現、某個請求完成、某個文字改變）；現代的測試工具（Playwright）內建了自動等待，但仍需要正確地選擇等待的對象。

**詳細解析**：「不穩定的測試比沒有測試更糟」：因為團隊會開始習慣性地重跑——而一旦「失敗了就重跑」變成慣例，真正的問題也會被重跑掉；這是測試套件失去信任的典型路徑。所以處理不穩定的測試應該有明確的政策：連續不穩定的測試先隔離（標記為 quarantine 並不阻擋合併）但必須有人負責修，而不是永久地忽略它。而其他常見的不穩定來源包括：**測試之間共用狀態**（資料庫沒清乾淨、前一個測試留下的登入狀態）、**動畫尚未結束就開始互動**、**以及依賴外部服務**；每一種都有對應的解法，但共同的前提是「把不穩定當成 bug 來處理而非當成噪音來容忍」。

**面試回答方式**：給主因（**等待的方式錯了**）與正確的做法。核心加分點是不穩定的測試比沒有測試更糟——「失敗了就重跑」變成慣例後真正的問題也會被重跑掉，並給出政策（隔離但必須有人負責修）。收在其他來源：共用狀態、動畫未結束、依賴外部服務，而共同前提是把不穩定當成 bug 而非噪音。

### 測試覆蓋率該定多少？

**核心答案**：覆蓋率是一個有用的下限指標而不是目標。它能告訴你「哪些程式碼完全沒被執行過」——**但高覆蓋率不代表測得好**（一個執行了所有行卻沒有斷言的測試也是百分之百）；所以更有意義的做法是對關鍵路徑要求高覆蓋，對整體只設一個防退步的下限。

**詳細解析**：「用差異覆蓋率而非總覆蓋率」是一個實用的做法：要求新增與修改的程式碼有較高的覆蓋——而不要求為既有的程式碼補測試；於是覆蓋率會隨著程式碼的更新自然提升，而不需要一次投入大量的補測試工作。這個做法的另一個好處是它把測試的討論放在程式碼審查中——「這段新邏輯沒有測試」是一個具體的、當下可以處理的意見；而「我們的覆蓋率是 62%」則沒有人知道該怎麼行動。把一個整體的指標轉成每次變更的門檻，是讓品質要求真正生效的常見模式。

**面試回答方式**：給定位（**有用的下限指標而非目標**）並說明高覆蓋率不代表測得好。核心加分點是**用差異覆蓋率而非總覆蓋率**——只要求新增與修改的程式碼，於是覆蓋率隨更新自然提升，並指出它把討論放進程式碼審查。收在模式：把整體指標轉成每次變更的門檻，是讓品質要求真正生效的常見做法。

### 元件庫或設計系統該怎麼測？

**核心答案**：行為用元件測試、外觀用視覺回歸、而使用方式用型別與文件。因為元件庫的使用者是其他開發者——所以「介面的穩定性」比內部實作更重要；測試應該圍繞公開的 props 與可觀察的行為，而不是內部的結構。

**詳細解析**：「元件庫的測試還要涵蓋無障礙」：因為一個有障礙的基礎元件會把問題複製到所有使用它的地方——而在元件庫這一層修正，收益是乘數的；所以在元件測試中加入自動的無障礙檢查（axe 這類工具）是高投資報酬率的做法。而另一個特有的需求是「跨版本的相容性」——元件庫的破壞性變更會影響所有使用者，所以需要明確的版本策略與棄用流程（先標記棄用並提供遷移指引，數個版本後才移除）。這些讓元件庫的維護比一般應用更接近函式庫開發——而理解這個差別，是決定「要不要抽出一個共用元件庫」時應該納入的成本。

**面試回答方式**：給三個面向的對應方式並指出介面的穩定性比內部實作更重要。核心加分點是元件庫的測試還要涵蓋無障礙——在這一層修正的收益是乘數的，以及**跨版本的相容性**需要明確的棄用流程。收在判斷：這讓元件庫的維護更接近函式庫開發，而理解這個差別是決定「要不要抽出共用元件庫」時應該納入的成本。
