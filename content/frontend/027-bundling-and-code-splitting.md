# 題目

前端的打包產物該怎麼優化？分割的判斷依據是什麼？

## 核心答案

**先確認瓶頸在哪，因為「檔案太大」有三種不同的問題**：**下載時間**（頻寬受限，壓縮與減量有效）、**解析與執行時間**（CPU 受限，這在低階手機上常常是真正的瓶頸）、**以及阻塞渲染**（載入的順序與優先權問題）。**沒有先測量就開始分割，常常優化了不是瓶頸的那一項。**

**分割的三個常見維度**：**按路由**（最自然，使用者不會同時需要所有頁面）、**按互動**（點開才需要的對話框、編輯器、圖表）、**以及把長期不變的相依單獨分出**（讓它們的快取不被業務程式碼的更新打掉）。

**而快取的關鍵是「檔名中的雜湊要對應內容」**——**內容不變則檔名不變，於是瀏覽器能長期快取**；**這裡有一個常見的陷阱：模組 ID 的變動會讓沒改過的檔案雜湊也改變**，**現代的打包工具多數已經處理，但值得驗證。**

**最後要記得「第三方腳本常常是最大的問題」**——**分析、廣告、客服元件加起來可能超過你自己的全部程式碼**；**而它們往往不在打包分析的視野裡。**

## 詳細解析

**「解析與執行的成本容易被忽略」**：一個壓縮後 300KB 的 JavaScript，在高階手機上解析加執行可能是 300 毫秒，在低階手機上可能是一秒以上——**而這段時間頁面是無回應的**；**所以「減少 JavaScript 的量」的收益，在低階裝置上遠大於下載時間的節省**。**用實際的裝置或者 CPU 降速的模擬測試，比在開發機上看數字誠實得多。**

**「共用相依的分割要小心過度」**：把每個共用的模組都抽成獨立檔案，會產生大量的小請求與複雜的載入圖——**而現代的做法是設一個最小體積門檻，小於它的就內聯進使用它的檔案**；**這是「請求數」與「重複程式碼」之間的權衡，而沒有普適的最佳解。**

**「快取的分層」值得設計**：不常變的框架與函式庫放一個檔案（快取一年）、業務程式碼按路由分（每次發布更新）、而 HTML 不快取（它引用了帶雜湊的資源）——**這個結構讓一次發布只讓少數檔案失效**；**而如果把所有東西打成一個檔案，每次發布使用者都要重新下載全部。**

**「打包分析要看的是實際的內容而非總數」**：用視覺化工具打開產物，常常會發現意外的東西——**整個 `moment.js` 的語系檔、被完整引入的圖示庫、或者同一個函式庫的兩個版本**；**這類發現的修復成本通常很低而收益很大**，**而它們幾乎不可能靠猜測找到。**

## 面試回答方式

先指出**「檔案太大」有三種不同的問題**並強調要先測量，再給分割的三個維度與快取的關鍵。加分點有四個：**解析與執行的成本在低階裝置上常常是真正的瓶頸**；**共用相依的分割要小心過度**，**現代做法是設最小體積門檻**；**快取的分層設計**讓一次發布只讓少數檔案失效；以及**打包分析要看實際內容**——**常會發現整個語系檔、完整引入的圖示庫、或同一函式庫的兩個版本**。最後補上**第三方腳本常常是最大的問題**。

## 講稿

我會先確認瓶頸在哪，因為檔案太大其實是三種不同的問題。下載時間、解析執行時間、還有阻塞渲染。沒有先測量就開始分割，常常會優化到不是瓶頸的那一項。

而在低階手機上，真正的瓶頸通常是解析跟執行。壓縮後三百 KB 的 JavaScript，在高階機上大概三百毫秒，在低階機可能超過一秒，而那段時間頁面是無回應的。所以我會用 CPU 降速去測，不看開發機的數字。

分割我用三個維度。按路由、按互動、還有把長期不變的相依單獨分出來，讓它們的快取不被業務程式碼的更新打掉。

快取的關鍵是檔名的雜湊要對應內容。內容不變檔名就不變，瀏覽器才能長期快取。

另外有一件事很容易被漏掉。第三方腳本常常是最大的問題，分析、廣告、客服元件加起來可能超過我自己的全部程式碼，而它們通常不在打包分析的視野裡。

## 常見追問

### 首屏應該載入多少 JavaScript？

**核心答案**：**沒有絕對的數字，但一個常被引用的參考是「壓縮後 150KB 以內」**——**這大致對應在中階手機上一秒內完成解析與執行**；**而更有意義的做法是直接測量目標裝置上的互動可用時間，並用它來反推可接受的體積。**

**詳細解析**：**「用預算而非目標」是讓這件事持續有效的方法**：在 CI 中設定體積上限並在超過時讓建置失敗——**否則體積只會隨時間單向增長**；**因為每個功能都只增加一點點，而沒有人會為了「大概多了 20KB」擋下一個 PR**。**而預算應該分層設定**（首屏、每個路由、第三方）**並且在超過時要求明確的說明而非自動放行**。**這個機制的價值不在於精確的數字，而在於它讓「體積」變成一個必須被討論的維度**——**而多數團隊的問題不是選錯了門檻，而是根本沒有門檻。**

**面試回答方式**：給參考數字（**壓縮後 150KB**）與它對應的執行時間，並指出更有意義的是測量目標裝置。核心加分點是**用預算而非目標**——**在 CI 中設上限並在超過時讓建置失敗**，並解釋為什麼（**每個功能只增加一點點，沒有人會為了 20KB 擋下 PR**）。收在洞察：**多數團隊的問題不是選錯門檻，而是根本沒有門檻**。

### 伺服器端渲染會讓 JavaScript 的量變小嗎？

**核心答案**：**不會，它改變的是「什麼時候看得到內容」而非「要下載多少程式碼」**。SSR 讓使用者更早看到畫面——**但為了讓它可互動，仍然要下載並執行同樣的 JavaScript（hydration）**；**而在 hydration 完成前，頁面看得到但點不動，那個落差有時比純客戶端渲染更讓人困惑。**

**詳細解析**：**「真正減少 JavaScript 的是伺服器元件與部分 hydration」**：React Server Components 讓某些元件的程式碼完全不進入客戶端——**而 islands 架構（Astro 等）只對真正需要互動的區塊 hydrate**；**這兩者改變的是「哪些程式碼需要送到客戶端」，那才是量的減少**。**理解「SSR 改善的是感知而非總量」這個區分很重要**——**因為許多團隊在導入 SSR 之後發現互動可用時間沒有改善甚至更差，原因就是他們期待的是總量的減少**；**而如果目標是減少 JavaScript，該做的是重新檢視哪些互動真的必要，而不是換一個渲染模式。**

**面試回答方式**：給明確的答案（**不會，它改變的是何時看得到內容**）並說明 hydration 前「看得到但點不動」的落差。核心加分點是指出**真正減少 JavaScript 的是伺服器元件與部分 hydration**並說明它們改變了什麼。收在常見的誤解：**許多團隊導入 SSR 後發現互動可用時間沒改善，原因是他們期待的是總量的減少**。

### 怎麼找出可以刪掉的程式碼？

**核心答案**：**用覆蓋率工具加上靜態分析**。瀏覽器開發者工具的 Coverage 面板能顯示載入了但沒執行的程式碼比例——**而 knip 或 ts-prune 這類工具能找出沒有被任何地方引用的匯出**；**兩者結合能找出大部分的死程式碼。**

**詳細解析**：**「覆蓋率報告要小心解讀」**：「載入但未執行」不等於「可以刪除」——**那可能是錯誤處理的分支、只在特定條件下才走的路徑、或者尚未被使用者觸發的功能**；**所以它應該被當成「值得檢查的清單」而非「刪除清單」**。**而更可靠的訊號是靜態分析找出的「完全沒有引用」**——**那幾乎確定可以刪**（除非有動態的引用，例如用字串組出的路徑）。**一個實用的漸進做法是「先加上日誌而非直接刪除」**：**在懷疑沒用的程式碼路徑上記錄一筆，觀察一個月**；**如果完全沒有觸發，那時再刪就很安心**——**這個做法把「我覺得沒人用」變成了「我知道沒人用」。**

**面試回答方式**：給兩類工具（覆蓋率、靜態分析）與各自能找到什麼。核心加分點是**覆蓋率報告要小心解讀**——**「載入但未執行」不等於可刪除**，並指出靜態分析的「完全沒有引用」是更可靠的訊號。收在漸進做法：**先加上日誌觀察一個月再刪**——**它把「我覺得沒人用」變成「我知道沒人用」**。
