# 題目

什麼是閉包？它為什麼會造成記憶體無法回收？

## 核心答案

閉包是**函式加上它被定義時所在的詞法環境**。當內層函式引用了外層函式的變數，即使外層函式已經回傳，那些變數也不會被回收——因為內層函式還持有對那個環境的參照。這不是 JavaScript 的特殊機制，而是**作用域鏈加上垃圾回收規則**自然產生的結果：變數只要還被引用就不會被回收。閉包解決的核心問題是**在函式呼叫之間保存狀態**，同時**不污染全域**——計數器、防抖節流的計時器 ID、模組的私有變數、React 的 hooks，本質上都靠它。所謂的「記憶體洩漏」其實是**非預期的持有**：如果閉包捕獲了一個大物件（例如整個 DOM 節點或大陣列）而這個閉包被長期持有（掛在全域、事件監聽器、計時器上），那個大物件就永遠不會被釋放。關鍵不是閉包本身有問題，而是**它的生命週期比你以為的長**。

## 詳細解析

**作用域鏈是編譯期決定的**：JavaScript 是**詞法作用域**——一個變數要去哪裡找，取決於程式碼**寫在哪裡**，而不是**從哪裡被呼叫**。這是它和 `this` 最大的差別（`this` 由呼叫方式決定）。理解這一點就能解釋為什麼把函式傳來傳去，它仍然存取得到原本定義位置的變數。

**閉包捕獲的是變數而不是值**：這是最常見的誤解來源。多個閉包引用同一個變數時，它們看到的是**同一份**，任何一個修改其他都會看到。經典的 `for` 加 `var` 加 `setTimeout` 印出相同值，就是因為所有回呼共享同一個變數；`let` 之所以能修正，是因為它在每輪迭代建立新的綁定。

**實際的洩漏場景**：最常見的三種是——**事件監聽器沒有移除**（監聽器持有的閉包捕獲了元件的狀態，元件卸載後仍然存活）、**計時器沒有清除**（`setInterval` 的回呼會一直被持有）、**在閉包裡捕獲 DOM 節點**（節點從畫面移除了，但 JavaScript 仍持有參照，整棵子樹都無法回收）。React 的 `useEffect` 要回傳清理函式，正是為了處理前兩種。

**只捕獲你需要的東西**：如果閉包只需要一個大物件的某個欄位，就在建立閉包時先取出那個欄位，而不是捕獲整個物件。這是很實用的優化——引擎的優化程度不一，不能假設它會幫你裁剪。

**閉包的效能代價通常被高估**：現代引擎對閉包做了大量優化，多數情況下它的開銷可以忽略。真正需要注意的是**在熱路徑中大量建立閉包**（例如在每次渲染或每個陣列元素上建立新函式），那會增加垃圾回收壓力。但這屬於量測到問題之後才處理的優化，不該預先為此犧牲可讀性。

## 面試回答方式

先給精確的定義——函式加上它被定義時的詞法環境，並強調它是**作用域鏈與垃圾回收規則的自然結果**，不是特殊機制。接著講它解決什麼問題：在呼叫之間保存狀態且不污染全域，並舉幾個真實用途（防抖的計時器 ID、模組私有變數、React hooks）。談記憶體時要把話講準：**閉包本身不是洩漏，非預期的長期持有才是**，並列出三個實際場景（事件監聽器、計時器、捕獲 DOM 節點）。加分點是主動說明**閉包捕獲的是變數不是值**，並用 `var` 與 `let` 在迴圈中的差異示範。

## 講稿

閉包就是函式加上它被定義的時候所在的環境。當內層函式引用了外層的變數，就算外層已經回傳了，那些變數也不會被回收，因為還有東西在引用它。

我覺得重點是，這不是什麼特殊機制，而是作用域鏈加上垃圾回收規則自然的結果。變數只要還被引用就不會被回收，如此而已。

它解決的問題是在多次呼叫之間保存狀態，而且不用把東西放到全域。防抖節流裡面存計時器的 ID、模組的私有變數、React 的 hooks，本質上都靠它。

至於記憶體問題，我覺得說閉包造成洩漏不太精確。真正的問題是非預期的長期持有。如果一個閉包捕獲了很大的東西，比如一整棵 DOM 子樹，而這個閉包又掛在全域、事件監聽器或者計時器上，那個東西就永遠不會被釋放。所以實務上最常見的三種就是監聽器沒移除、計時器沒清掉、還有在閉包裡抓著 DOM 節點。

還有一個很重要的細節，閉包捕獲的是變數本身，不是當下的值。所以多個閉包引用同一個變數的時候，看到的是同一份。迴圈裡用 var 印出相同的值就是這個原因。

## 常見追問

### 閉包和一般的函式在記憶體上差在哪？

**核心答案**：差在**是否讓外層的環境存活**。一般函式執行完，它的區域變數就可以被回收；如果內層函式被保留下來並引用了外層變數，那個環境就必須繼續存在，直到內層函式本身也不再被引用為止。所以閉包的記憶體成本不是函式本身，而是**它讓一個本該死掉的環境活了下來**。

**詳細解析**：現代引擎會做**環境裁剪**——只保留閉包實際用到的變數，而不是整個外層環境，但這個優化的程度因引擎與情境而異，尤其在有 `eval` 或 `with` 的情況下無法進行。所以實務建議仍然是主動控制：只捕獲需要的欄位、在不需要時解除引用（把變數設為 null）、以及確保長期存活的閉包（監聽器、計時器、快取）在生命週期結束時被清理。要診斷這類問題，可以用瀏覽器開發工具的堆積快照比對前後的物件數量，找出應該被回收卻仍存活的節點——這比猜測有效得多。

**面試回答方式**：核心是閉包讓本該回收的環境存活下來，成本在環境而非函式。接著說明引擎會做環境裁剪但不能依賴。加分點是給出診斷方法——用堆積快照比對前後，找出該回收卻存活的物件。

### 立即執行函式現在還有用嗎？

**核心答案**：在**模組系統普及之後，用途大幅減少**。它原本的兩個主要用途是——建立獨立作用域避免污染全域，以及在 `let` 出現前於迴圈中捕獲當前值。前者現在由 ES 模組解決（模組有自己的作用域），後者由 `let` 解決。目前還會用到的情況主要是**需要立即執行的初始化邏輯**、以及在不支援模組的環境（例如注入的腳本片段）中隔離作用域。

**詳細解析**：另一個仍然常見的形態是**塊級作用域的替代**——不過在有 `let` 與 `const` 之後，直接用一個 `{}` 區塊就能達到相同效果，更清楚。至於「模組模式」（用立即執行函式回傳一個包含公開方法的物件來實現私有變數），現在有更好的選擇：ES 模組本身、或 class 的 `#` 私有欄位。理解這個演變的價值在於，看到舊程式碼裡的立即執行函式時，你知道它原本在解決什麼問題，也知道現在該用什麼取代它——這比單純批評舊寫法有用。

**面試回答方式**：說明它的兩個原始用途都已被模組與 `let` 取代，只在少數情況仍需要。接著說明模組模式現在可以用 ES 模組或 class 私有欄位取代。加分點是把重點放在「知道舊寫法在解決什麼問題，才知道用什麼取代」，展現對演變的理解。

### React 的 hooks 和閉包有什麼關係？

**核心答案**：**hooks 完全建立在閉包上**。每次渲染都會產生一組新的函式，這些函式捕獲的是**那一次渲染時的 props 與 state**。所以 `useEffect` 或事件處理器裡讀到的值，是**它被建立的那一次渲染的值**，而不是最新的值。這解釋了為什麼依賴陣列漏了某個變數會讀到過期的資料——不是 React 有 bug，而是閉包如實地保留了當時的環境。

**詳細解析**：理解這一點之後，幾個常見問題就有了統一的解釋：`setInterval` 裡的回呼永遠讀到初始 state（因為它只在第一次渲染時建立過一次）、事件處理器讀到舊值（因為依賴陣列讓 effect 沒有重新建立）、以及為什麼 `setState` 的函式形式（`setCount(c => c + 1)`）比直接用變數安全（因為它拿到的是最新值而不是閉包裡的值）。解法通常有三種：把變數加進依賴陣列、用 `useRef` 保存一個跨渲染穩定的容器、或改用函式形式的更新。能把這三種解法對應到「為什麼」，比背規則有用得多。

**面試回答方式**：核心是每次渲染產生新函式、捕獲那次渲染的值，所以讀到的是當時的環境而非最新值。用這一句統一解釋 interval 讀到舊 state、事件處理器讀到舊值等現象。加分點是給出三種解法（加依賴、用 ref、函式形式更新）並說明各自對應到什麼原因。
