# 題目

React 的受控與非受控元件怎麼選？表單驗證該放在哪幾層？

## 核心答案

**受控元件**（值由 state 控制）——**需要即時回應輸入時使用**（即時驗證、輸入格式化、聯動的欄位）；**代價是每次按鍵都觸發重新渲染，在大表單上可能有效能問題。**

**非受控元件**（值由 DOM 自己持有，用 ref 或表單提交時讀取）——**適合大型表單與只在提交時才需要值的情況**；**現代的表單函式庫多數採用這個模型並只在需要時訂閱特定欄位，於是同時得到效能與功能。**

**驗證要分三層而且每層的目的不同**：**HTML 原生屬性**（`required`、`type`、`pattern`——零成本、在 JS 載入前就有效、且自帶無障礙）；**客戶端的邏輯驗證**（即時回饋、跨欄位的規則）；**伺服器端驗證**（唯一真正可信的一層，因為客戶端的任何檢查都可以被繞過）。

**最常見的錯誤是「把客戶端驗證當成安全機制」**——**它是使用者體驗的功能而非防護**；**任何請求都可以直接用工具送出，繞過整個前端。**

## 詳細解析

**「驗證的時機影響體驗很大」**：在使用者還在輸入時就顯示「格式錯誤」很惱人——**而常見的良好做法是「離開欄位時才驗證，但一旦顯示過錯誤就改成即時更新」**；**這樣既不會在輸入中途打擾，又能讓修正時立刻看到已經正確**。**這個細節在多數表單函式庫中對應到 `onBlur` 加上 `onChange` 的混合模式。**

**「錯誤訊息要說怎麼修而不只是說錯了」**：「密碼不符合規則」不如「密碼需要至少 8 個字元，目前是 5 個」——**後者讓使用者知道確切要做什麼**；**而把規則在輸入前就顯示出來（而非等錯了才說），能減少大部分的錯誤。**

**「無障礙的關聯是必要的而非加分」**：`<label for>` 或包裹式的 label、錯誤訊息用 `aria-describedby` 關聯到欄位、以及 `aria-invalid` 標記狀態——**沒有這些，螢幕閱讀器的使用者不知道哪個欄位錯了、錯在哪**；**而這幾個屬性的成本極低。**

**「防止重複提交」是常被漏掉的一項**：使用者連點兩次送出——**如果沒有在提交後立刻禁用按鈕或者用一個提交中的狀態，可能產生兩筆訂單**；**而更完整的做法是後端用冪等鍵處理，因為前端的防護在網路重試或者使用者重新整理時仍然可能失效。**

## 面試回答方式

先給受控與非受控各自的適用情況與代價，並指出**現代表單函式庫多採非受控加選擇性訂閱**。再給驗證的三層與各自的目的，強調**客戶端驗證不是安全機制**。加分點有四個：**驗證的時機**——**離開欄位時才驗證，顯示過錯誤後改成即時**；**錯誤訊息要說怎麼修**，**而把規則在輸入前就顯示能減少大部分錯誤**；**無障礙的關聯是必要而非加分**；以及**防止重複提交**，**而完整的做法需要後端的冪等鍵**。

## 講稿

受控元件是值由 state 控制，需要即時回應輸入的時候用，比如即時驗證或者聯動欄位。代價是每次按鍵都會觸發重新渲染，大表單上可能有效能問題。

非受控是值由 DOM 自己持有，適合大型表單跟只在提交時才需要值的情況。現代的表單函式庫多數採用這個模型，只在需要時訂閱特定欄位，所以效能跟功能兩邊都拿到。

驗證我會分三層。HTML 原生屬性是零成本的，在 JavaScript 載入前就有效而且自帶無障礙。客戶端的邏輯驗證負責即時回饋跟跨欄位規則。伺服器端驗證是唯一真正可信的一層。

這裡有一個常見的錯誤，把客戶端驗證當成安全機制。它是體驗功能不是防護，任何請求都可以用工具直接送出。

體驗上還有一個細節。我的做法是離開欄位時才驗證，但一旦顯示過錯誤就改成即時更新。這樣輸入中途不會被打擾，修正的時候又能立刻看到已經正確。

## 常見追問

### 大型表單的效能怎麼優化？

**核心答案**：**避免「一個欄位改變導致整張表單重新渲染」**。具體的做法包括：**用非受控加上函式庫的欄位級訂閱**、**把表單拆成獨立的子元件並用 memo 隔離**、**或者把每個欄位的 state 放在自己的元件裡**；**而最有效的通常是第一種，因為它從根本上讓渲染的範圍等於改變的範圍。**

**詳細解析**：**「先確認效能問題是真的」**：一個五十個欄位的表單在現代裝置上，即使全部重新渲染也可能只有幾毫秒——**而過早地引入複雜的優化，會讓程式碼難以維護且可能引入 bug**；**用 React DevTools 的 Profiler 確認每次輸入實際花了多久，是決定要不要優化的前提**。**而如果確實有問題，常見的真正原因往往不是欄位數量而是「某個昂貴的計算或元件被包在表單裡一起重新渲染」**——**例如一個複雜的預覽區塊或者一張圖表**；**這時把那個部分隔離出來，效果遠大於優化欄位本身**。**這是一個「找出真正的熱點比套用通用優化更有效」的典型例子。**

**面試回答方式**：給核心目標（**避免一個欄位改變導致整張表單重新渲染**）與三個做法。核心加分點是**先確認效能問題是真的**——**五十個欄位全部重渲染可能只有幾毫秒**，並指出真正的原因往往是**某個昂貴的元件被包在表單裡一起重新渲染**。收在通則：**找出真正的熱點比套用通用優化更有效**。

### 多步驟表單的狀態該放哪？

**核心答案**：**看是否需要在重新整理後保留**。純前端的暫存用一個共用的 state 或 context 就好——**而如果使用者可能中途離開再回來（長表單、上傳流程、結帳），那需要持久化**：**存在 URL（步驟編號）加上 sessionStorage 或者後端的草稿。**

**詳細解析**：**「把步驟放進 URL」帶來幾個免費的好處**：瀏覽器的上一頁能回到前一步（否則會直接離開整個表單，那是常見的體驗災難）、可以分享或書籤特定的步驟、以及重新整理不會回到第一步。**而資料本身通常不該放進 URL**（太長、可能含敏感資訊）——**所以常見的組合是「步驟在 URL、資料在 sessionStorage 或後端」**。**而如果表單很長且有價值（例如貸款申請），把草稿存到後端是最可靠的**——**因為它跨裝置有效且不受瀏覽器清理的影響**；**判斷的依據是「使用者填到一半的資料，遺失的代價有多大」**。

**面試回答方式**：給判準（**是否需要在重新整理後保留**）與兩種情況的做法。核心加分點是**把步驟放進 URL**的三個免費好處，特別是**上一頁能回到前一步**（否則會直接離開整個表單）。收在組合與判斷：**步驟在 URL、資料在 sessionStorage 或後端**，**而依據是「使用者填到一半的資料，遺失的代價有多大」**。

### 檔案上傳有什麼要注意的？

**核心答案**：**進度、失敗處理、以及大檔案的分塊**。要處理的包括：**顯示上傳進度**（否則使用者不知道是不是卡住了）、**允許取消**、**失敗後能重試而不用重選檔案**、**在客戶端先檢查大小與格式**（節省無謂的上傳，但伺服器端仍要檢查）、**以及大檔案用分塊上傳並支援續傳。**

**詳細解析**：**「直傳到儲存服務」是大檔案的標準做法**：讓後端簽發一個有時效的上傳網址，前端直接把檔案傳給物件儲存——**於是檔案不經過應用伺服器，省下頻寬與記憶體，也避免了請求體積的限制**；**而後端只需要在完成後收到一個通知並驗證**。**這個模式的安全要點是「簽發的網址要限制大小、類型與有效期」**——**否則等於開放了一個任意上傳的端點**。**而在使用者體驗上，一個常被忽略的細節是「上傳完成不等於處理完成」**——**影片轉碼、圖片壓縮、病毒掃描都需要時間**；**所以介面上要區分「已上傳」與「可使用」這兩個狀態，否則使用者會以為完成了卻發現檔案還不能用。**

**面試回答方式**：列出五個要處理的項目。核心加分點是**直傳到儲存服務**這個大檔案的標準做法與它的好處，以及安全要點（**簽發的網址要限制大小、類型與有效期**）。收在體驗細節：**上傳完成不等於處理完成**——**介面要區分「已上傳」與「可使用」，否則使用者會以為完成了卻發現檔案還不能用**。
