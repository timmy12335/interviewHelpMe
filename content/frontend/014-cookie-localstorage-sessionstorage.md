# 題目

三種前端儲存差在哪？登入的 token 應該放哪裡？

## 核心答案

差別在四個維度：**生命週期**、**容量**、**是否自動隨請求送出**、**能否被 JavaScript 讀取**。**Cookie** 容量最小（約 4KB）、**會自動附加在每個同網域的請求上**（這是它的核心特性也是效能負擔）、可以設定過期時間，而且能加上 **`HttpOnly`** 讓 JavaScript 讀不到。**localStorage** 約 5MB、**永久保存**直到明確清除、只能由 JavaScript 存取、不會自動送出。**sessionStorage** 同 localStorage 但**限於單一分頁**，關閉分頁就消失。至於 token 放哪裡——最安全的做法是 **`HttpOnly` + `Secure` + `SameSite` 的 Cookie**，因為 XSS 攻擊讀不到它；放在 `localStorage` 的 token 只要頁面上有任何 XSS 漏洞就會被完整竊取。代價是 Cookie 需要處理 CSRF，但 `SameSite=Lax` 或 `Strict` 已經擋掉了大部分情境，加上 CSRF token 就相當完整。

## 詳細解析

**Cookie 自動送出的兩面**：好處是伺服器不需要前端配合就能識別身分，跨分頁也天然共用。壞處是**每個請求都會帶上**——包括圖片、CSS、字體這些完全不需要身分的請求，在 Cookie 較大時形成可觀的頻寬浪費。解法是把靜態資源放在**不同的網域**（不會帶上主網域的 Cookie），這是大型網站普遍的做法。

**SameSite 的三個值**：`Strict` 完全不在跨站請求中送出（連從外部連結點進來都不帶，會導致使用者看起來像未登入）；`Lax` 是現代瀏覽器的預設值，在跨站的 `GET` 導航中會送出、其他情境不送，平衡了安全與可用性；`None` 才會在所有跨站情境送出，但**必須同時加上 `Secure`**。理解這三者是處理第三方嵌入與跨站登入問題的基礎。

**localStorage 的兩個實際限制**：一是**同步 API**——讀寫會阻塞主執行緒，存放大量資料時會造成卡頓，不適合放大型結構。二是**只能存字串**——物件要自己序列化，而 `JSON.parse` 失敗時要有防護，否則一筆壞掉的資料會讓應用崩潰。需要存放結構化的大量資料時該用 **IndexedDB**，它是非同步的、容量大得多、也支援索引查詢。

**sessionStorage 的分頁隔離常被誤解**：它是**每個分頁各自獨立**的，同一個網站開兩個分頁有兩份不同的 `sessionStorage`；但「重新整理」和「在同一分頁內導航」會保留，透過 `target="_blank"` 開新分頁在部分情況下會複製一份。這個特性適合放**與這次瀏覽流程相關的暫時狀態**，例如多步驟表單的中間資料。

**所有前端儲存都不可信任**：使用者可以隨意修改這些值，所以**任何權限判斷都必須在伺服器端做**。前端存的角色、權限旗標只能用來決定 UI 顯示什麼，絕不能當成授權依據。這是面試中很值得主動點出的原則。

## 面試回答方式

用四個維度（生命週期、容量、是否自動送出、JS 能否讀取）把三者一次講清楚，比逐一介紹有條理。**token 放哪裡**要給明確立場：`HttpOnly` Cookie 最安全，因為 XSS 讀不到；`localStorage` 的 token 一旦有 XSS 就整個外洩。同時誠實講代價——Cookie 要處理 CSRF，但 `SameSite` 加 CSRF token 已相當完整。加分點有三個：Cookie 會附加在**所有**請求上包括靜態資源，所以大站把資源放在不同網域；`localStorage` 是**同步 API** 會阻塞主執行緒，大量結構化資料該用 IndexedDB；以及**所有前端儲存都不可信任**，權限判斷必須在伺服器端。

## 講稿

我從四個維度看，生命週期、容量、會不會自動送出、還有 JavaScript 能不能讀。

Cookie 大概四 KB，最小，但它會自動附加在每個同網域的請求上。這是核心特性也是負擔，因為圖片、CSS 這些不需要身分的請求也會帶，所以大型網站會把靜態資源放到另一個網域。它可以設 HttpOnly，讓 JavaScript 讀不到。

localStorage 大概五 MB，永久保存，不會自動送出。sessionStorage 一樣，但限單一分頁，關掉就沒了。

token 我會放在 HttpOnly 加 Secure 加 SameSite 的 Cookie。理由是只要頁面上有任何 XSS 漏洞，放在 localStorage 的 token 就會被完整偷走，而 HttpOnly 的讀不到。代價是要處理 CSRF，但 SameSite 設 Lax 已經擋掉大部分情境，再加 CSRF token 就相當完整。

另外兩件事我會注意。localStorage 是同步 API，會阻塞主執行緒，大量結構化資料應該用 IndexedDB。還有前端儲存都不可信任，使用者可以隨便改，權限判斷一定要在伺服器端做。

## 常見追問

### 用 HttpOnly Cookie 之後，前端要怎麼知道使用者登入了？

**核心答案**：**不從 token 判斷，而是問伺服器**。標準做法是提供一個「取得目前使用者」的端點，前端在啟動時呼叫一次，回 200 就是已登入並拿到使用者資料，回 401 就是未登入。另一個做法是搭配一個**非 `HttpOnly` 的輔助 Cookie**（只存無敏感資訊的旗標，例如登入狀態或顯示名稱），讓前端能立刻渲染，真正的驗證仍由 `HttpOnly` 的 token 負責。

**詳細解析**：兩種做法各有取捨。呼叫端點的方式最單純且永遠正確，代價是首屏多一次往返，可能造成短暫的「未登入閃爍」——這可以用伺服器端渲染或骨架畫面緩解。輔助 Cookie 的方式沒有額外往返，但要小心兩者**可能不同步**（例如 token 過期了但輔助 Cookie 還在），所以前端仍必須能處理任何請求回 401 的情況，統一導向登入。實務上不論用哪種，**攔截所有 401 回應並集中處理**都是必要的，因為 token 可能在任何時刻失效。

**面試回答方式**：給出兩種做法並比較取捨（多一次往返 vs 可能不同步）。強調不論哪種，都必須攔截 401 集中處理，因為 token 可能隨時失效。加分點是提到未登入閃爍可以用伺服器端渲染或骨架畫面緩解。

### 需要在多個分頁之間同步狀態該怎麼做？

**核心答案**：用 **`storage` 事件**或 **`BroadcastChannel`**。`localStorage` 被其他分頁修改時會在本分頁觸發 `storage` 事件（注意：**修改的那個分頁自己不會收到**），適合同步登入登出這類狀態。`BroadcastChannel` 更直接——同源的分頁之間可以直接互相發送訊息，不需要透過儲存，語意也更清楚。

**詳細解析**：典型的應用是**登出的同步**——使用者在一個分頁登出，其他分頁應該立刻反映而不是繼續顯示已登入的畫面。另一個是**避免重複的請求**，例如多個分頁同時要刷新 token 時，可以透過通道協調只讓一個分頁執行。要注意 `storage` 事件的限制：它只在 `localStorage` 與 `sessionStorage` 變動時觸發，而且傳遞的資料要自行序列化。`BroadcastChannel` 沒有這些限制，但需要注意瀏覽器支援度與**訊息只在同源之間傳遞**這個邊界。若需要與 Service Worker 協調，`BroadcastChannel` 也能涵蓋。

**面試回答方式**：給出兩個機制並說明各自的適用性，特別點出 `storage` 事件不會通知修改者自己這個容易踩的細節。用登出同步與 token 刷新協調兩個實際場景說明價值。加分點是提到 `BroadcastChannel` 也能與 Service Worker 協調。

### localStorage 存滿了會發生什麼事？

**核心答案**：**寫入時拋出例外**（配額超出的錯誤），而不是靜默失敗。所以任何寫入 `localStorage` 的地方都應該包在 `try/catch` 中——否則一個寫入失敗可能讓整段流程中斷。容量上限各瀏覽器不同（多半 5 到 10MB），而且**無痕模式下可能極小或直接不可用**，這是實際會遇到的情境。

**詳細解析**：除了容量，還有兩種情況會讓存取失敗：**使用者停用了網站資料**（存取時直接拋錯）、以及**某些嵌入情境下的第三方 Cookie 限制**。所以健全的做法是把儲存封裝成一層薄薄的工具函式，內部處理例外並在失敗時退回記憶體中的暫存，讓應用程式不會因為儲存不可用而崩潰。至於容量管理，實務上應該**主動控制寫入的資料量**——只存必要的，並為快取類的資料加上過期時間定期清理，而不是等到滿了才處理。需要大量儲存時應該直接選 IndexedDB。

**面試回答方式**：明確說會拋例外而非靜默失敗，所以寫入要包 `try/catch`。補上無痕模式與停用網站資料這兩種存取失敗的情境。加分點是建議把儲存封裝成一層工具函式、失敗時退回記憶體暫存，並主動控制寫入量與設定過期清理。
