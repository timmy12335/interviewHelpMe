# 題目

防抖和節流差在哪？搜尋輸入框、視窗縮放、無限捲動各該用哪一個？

## 核心答案

**防抖（debounce）是「等你停下來才做」**——每次觸發都重設計時器，只有在停止觸發超過指定時間後才真正執行一次。**節流（throttle）是「固定頻率做」**——不管觸發多密集，每隔固定時間最多執行一次。判斷準則是問：我需要的是最後那一次的結果，還是過程中的持續更新？要最後結果用防抖，要持續更新用節流。所以**搜尋輸入框用防抖**（使用者還在打字時不需要送出請求，停下來才查）；**視窗縮放用節流**（縮放過程中版面就要跟著調整，等停下來才調會很卡）；**無限捲動用節流**（捲動過程中要持續檢查是否接近底部）。另外兩個常見的是按鈕防連點用節流的首次執行版本（立刻執行一次、之後的忽略），**表單自動儲存用防抖**（停止編輯後才存）。實作上兩者都要處理**清理**——元件卸載時要清除待執行的計時器，否則會對已卸載的元件操作。

## 詳細解析

**防抖的兩種模式**：**尾部觸發**（trailing，預設）是停止後才執行，適合搜尋；**首部觸發**（leading）是第一次立刻執行、之後在冷卻期內的都忽略，適合防止按鈕連點。有些實作支援兩者同時開啟。選錯模式會造成體感問題——搜尋用首部觸發會查到只輸入一個字的結果，按鈕用尾部觸發會讓使用者覺得沒反應。

**節流的實作有兩種思路**：**時間戳記法**（記錄上次執行時間，距離夠久才執行）會立刻執行第一次但可能漏掉最後一次；**計時器法**（設定計時器，執行後清除）會延遲第一次但保證最後一次會執行。成熟的實作通常兩者結合並提供選項。這個差別在「捲動到底部載入更多」的情境會顯現——漏掉最後一次可能導致捲到底了卻沒觸發載入。

**在 React 中要用 useMemo 或 useRef 保存**：直接在元件中呼叫 `debounce(fn, 300)` 會在每次渲染都建立新的防抖函式，計時器根本不會累積，防抖完全失效。正確做法是用 `useMemo` 或 `useRef` 讓它跨渲染保持同一個實例，並在 `useEffect` 的清理函式中取消待執行的呼叫。這是實務上最常見的錯誤，也是很好的追問點。

**現代的替代方案**：捲動偵測不一定要用節流——**`IntersectionObserver`** 是更好的選擇，它由瀏覽器在非主執行緒判斷元素是否進入視窗，不需要監聽捲動事件，效能更好也更簡潔。同理，元素尺寸變化可以用 **`ResizeObserver`** 取代監聽 resize。搜尋輸入除了防抖，還可以配合 `AbortController` 取消過期的請求，避免慢的舊請求覆蓋快的新結果。

取消過期回應是防抖不能解決的問題：即使做了防抖，仍可能發出兩個請求而先發的後到，導致舊資料覆蓋新資料。解法有兩種：**取消**（用 `AbortController` 中止前一個請求）或**忽略**（記錄請求序號，只採用最新那一次的結果）。這是搜尋功能實作中很容易漏掉的正確性問題，而不只是效能問題。

## 面試回答方式

先給一句話定義——防抖是等你停下來才做，節流是固定頻率做。然後給**判斷準則**：要最後那一次的結果用防抖，要過程中的持續更新用節流，並用搜尋框、視窗縮放、無限捲動三個例子套一遍。接著主動講實作細節：防抖有首部與尾部兩種模式、選錯會造成體感問題；節流的兩種實作在「最後一次會不會執行」上有差異。加分點有三個：React 中要用 `useMemo` 或 `useRef` 保存否則防抖完全失效；捲動偵測改用 `IntersectionObserver` 更好；以及搜尋要配合取消或序號忽略，處理舊回應覆蓋新結果的正確性問題。

## 講稿

防抖是等你停下來才做，每次觸發都重設計時器。節流是固定頻率做，不管觸發多密集，每隔一段時間最多執行一次。

我判斷用哪個就問一句話，我要的是最後那一次的結果，還是過程中的持續更新。要最後結果用防抖，要持續更新用節流。

所以搜尋框用防抖，使用者還在打字的時候不需要送請求。視窗縮放用節流，因為縮放過程中版面就要跟著調整，等停下來才調會很卡。無限捲動也是節流，捲動過程要持續檢查有沒有接近底部。

實作上有個細節，防抖有首部跟尾部兩種模式。搜尋要用尾部，停下來才執行。按鈕防連點要用首部，第一次立刻執行、後面的忽略，不然使用者會覺得按了沒反應。

在 React 裡面我一定會用 useMemo 或 useRef 保存這個函式。如果直接在元件裡呼叫 debounce，每次渲染都會建立一個新的，計時器根本累積不起來，防抖完全失效。這是我看過最常見的錯誤。

還有一件事防抖解決不了，就是舊的請求比新的晚回來，把新資料蓋掉。這要用 AbortController 取消，或者記請求序號只採用最新的。

## 常見追問

### 手寫一個防抖函式要注意什麼？

**核心答案**：三件事。**保存計時器 ID 在閉包中**，每次呼叫先清除舊的再設新的。**保留 `this` 與參數**——用一般函式接收並用 `apply` 轉發，或直接用箭頭函式配剩餘參數，否則在物件方法或事件處理器中會丟失上下文。**提供取消方法**——回傳的函式上掛一個 `cancel`，讓使用者能在元件卸載時清除待執行的呼叫。

**詳細解析**：進階的實作還要處理**回傳值**。防抖函式的呼叫和實際執行不同步，所以無法直接回傳結果——常見做法是回傳一個 Promise，在實際執行時解析。但這會帶來新問題：被取消掉的那些呼叫的 Promise 該怎麼處理（永遠不解析會造成記憶體累積，拒絕又會產生大量未捕捉的拒絕）。這也是為什麼多數場景直接用回呼而不強求回傳值。另一個細節是 **`leading` 與 `trailing` 同時開啟時**，只觸發一次的情況不應該執行兩次，實作時要記錄「冷卻期內有沒有再次觸發」。

**面試回答方式**：給出三個必要點（閉包保存計時器、保留 this 與參數、提供 cancel）。加分點是討論回傳值的難題——被取消的呼叫的 Promise 該怎麼處理，說明為什麼多數實作用回呼。以及 leading 與 trailing 同時開啟時不該重複執行。

### 節流和 requestAnimationFrame 怎麼選？

**核心答案**：和畫面更新有關的用 `requestAnimationFrame`，其他用節流。捲動時移動一個元素、視差效果、跟隨滑鼠的動畫，這些的更新頻率應該對齊螢幕刷新率，用 `rAF` 最自然——它保證在下一次繪製前執行、分頁在背景時自動暫停、也不會出現和刷新不同步造成的抖動。而發送請求、記錄分析事件、觸發資料載入這些與繪製無關的操作，用固定時間的節流更合適。

**詳細解析**：兩者也可以結合——用 `rAF` 當節流的時間基準，確保每一幀最多執行一次。要注意 `rAF` 的回呼**只執行一次**，需要持續更新必須在回呼中再次註冊，忘記註冊是常見的動畫停住的原因；反過來，忘記在不需要時取消註冊會造成永不停止的迴圈，浪費電力。另外 `rAF` 在分頁不可見時不會執行，這通常是好事（省電），但如果你依賴它做計時就會出錯——計時應該用實際的時間戳記差值而不是假設每幀 16.7 毫秒。

**面試回答方式**：給出判準——與畫面更新有關用 `rAF`，其他用節流，並各舉例子。說明 `rAF` 的三個優勢（對齊繪製、背景暫停、不抖動）。加分點是提到兩者可以結合，以及 `rAF` 在背景不執行時不能拿來計時，要用時間戳記差值。

### 搜尋框防抖的延遲時間該設多少？

**核心答案**：沒有標準答案，但常見範圍是 200 到 500 毫秒，取捨是**回應速度**與**請求數量**。太短（低於 150 毫秒）會在正常打字的字間空隙就觸發，浪費請求；太長（超過 600 毫秒）使用者會覺得遲鈍。實務上更好的做法不是猜一個數字，而是**量測**——看實際使用者的打字節奏與請求量，再調整。中文輸入法還要額外處理**組字階段**，在使用者還在選字時不該觸發查詢。

**詳細解析**：中文輸入的處理是這題最實際的細節：`input` 事件在注音或拼音的組字過程中也會觸發，這時的內容是無意義的中間狀態。正確做法是監聽 `compositionstart` 與 `compositionend`，在組字期間暫停查詢。這個問題在只用英文測試時完全不會出現，是本地化前端很典型的坑。另外**體感優化**比調整延遲更有效——立刻顯示載入指示、保留上一次的結果而不是清空、以及對常見查詢做前端快取，都能讓相同的延遲感覺更快。

**面試回答方式**：給出範圍與兩端的取捨，並強調應該量測而不是猜。重點放在中文輸入法的組字處理（`compositionstart` 與 `compositionend`），這是很有辨識度的實務細節。加分點是指出體感優化（載入指示、保留舊結果、前端快取）比調整延遲數字更有效。
