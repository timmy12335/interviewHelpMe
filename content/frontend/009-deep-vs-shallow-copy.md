# 題目

淺拷貝和深拷貝差在哪？前端開發中什麼時候真的需要深拷貝？

## 核心答案

**淺拷貝只複製第一層**——展開運算子、`Object.assign`、`Array.prototype.slice` 都是淺拷貝，巢狀的物件仍然是**共用同一個參照**，所以修改巢狀屬性會同時影響原本的物件。**深拷貝**則遞迴複製所有層級，得到完全獨立的結構。實務上的關鍵認知是：**多數情況不需要深拷貝**。現代前端的資料流建立在**不可變更新**上——修改巢狀資料時，只沿著要改動的那條路徑建立新物件，其他分支繼續共用參照。這樣既保證了「有變動的地方參照會改變」（框架才偵測得到），又避免了複製整棵結構的成本。真的需要深拷貝的場景其實有限：**要保存一份快照**（例如編輯前的原始資料以支援取消）、要把資料交給不受控的第三方程式碼、以及**跨執行緒傳遞**。現代環境優先用 `structuredClone`，不要用 `JSON.parse(JSON.stringify())`。

## 詳細解析

**淺拷貝的實際陷阱**：`const copy = {...original}` 之後修改 `copy.user.name`，`original.user.name` 也會變——因為 `user` 這個物件本身沒有被複製。這在 React 中造成的典型 bug 是：修改了狀態的巢狀屬性，但因為外層參照沒變，元件不會重新渲染；或者反過來，本以為改的是複本卻污染了原始資料。

**不可變更新的正確寫法**：要更新 `state.user.profile.name`，正確做法是逐層展開——建立新的 state、新的 user、新的 profile，只有 name 是新值，其餘的兄弟分支保持原參照。層級深時這種寫法很囉嗦，所以實務上常用 Immer 這類函式庫，它讓你用看似直接修改的語法寫，底層產生正確的不可變更新。理解底層在做什麼，才知道為什麼它比深拷貝有效率。

**JSON 方法的具體問題**：會丟失 `undefined` 與函式（物件中直接消失、陣列中變成 `null`）、把 `Date` 變成字串、`Map` 與 `Set` 變成空物件、`NaN` 與 `Infinity` 變成 `null`、遇到循環參照直接拋錯、以及**丟失原型**（類別實例變成普通物件）。它唯一的優點是無所不在，但在支援 `structuredClone` 的環境沒有理由再用它。

**structuredClone 的限制**：無法複製**函式**（會拋錯）、**DOM 節點**、**原型鏈**（類別實例會變成普通物件，但屬性保留）。它支援循環參照、`Map`、`Set`、`Date`、`RegExp`、`ArrayBuffer` 等。所以選擇前要先問：這個結構裡有沒有函式或類別實例。

**效能考量**：深拷貝的成本與資料量成正比，對大型結構（幾千筆列表資料）在每次更新時深拷貝會造成明顯卡頓。不可變更新的成本則只與**變動路徑的深度**成正比，與資料總量無關——這是它在效能上的根本優勢，也是 React 與 Redux 選擇這個模式的原因。能講出這個複雜度的差別，比列舉方法有價值得多。

## 面試回答方式

先講清楚差別（只複製第一層 vs 遞迴複製），並用一個具體的 bug 說明淺拷貝的陷阱。接著給最重要的判斷：**多數情況不需要深拷貝**，現代前端用的是**不可變更新**——只沿變動路徑建立新物件，其他分支共用參照。這裡要點出**複雜度的差別**：深拷貝的成本與資料總量成正比，不可變更新只與變動路徑深度成正比，這是效能上的根本優勢。真正需要深拷貝的場景要列出來（快照、交給第三方、跨執行緒）。加分點是列出 `JSON` 方法的具體缺陷，並說明 `structuredClone` 也無法處理函式與原型。

## 講稿

淺拷貝只複製第一層，巢狀的物件還是共用同一個參照。所以展開之後改巢狀屬性，原本的物件也會跟著變。在 React 裡這會產生兩種 bug，一種是改了但外層參照沒變所以不重新渲染，另一種是以為改的是複本結果污染了原始資料。

但我想強調的是，多數情況其實不需要深拷貝。現代前端用的是不可變更新，要改巢狀的某個值，我只沿著那條路徑逐層建立新物件，其他分支繼續共用原本的參照。

這樣做有兩個好處。有變動的地方參照會改變，框架偵測得到。而且成本只跟變動路徑的深度有關，跟資料總量無關。深拷貝的成本則是跟資料量成正比，幾千筆的列表每次更新都深拷貝就會明顯卡。這個複雜度的差別我覺得是重點。

真正需要深拷貝的情況其實不多，大概是要保存一份快照支援取消、要把資料交給不受控的第三方，或者跨執行緒傳遞。

方法上我會用 structuredClone，不會用 JSON 那一套。JSON 會丟掉 undefined 跟函式、把 Date 變成字串、遇到循環參照直接拋錯，而且原型也沒了。

## 常見追問

### 不可變更新的巢狀寫法太囉嗦，有什麼解法？

**核心答案**：用 **Immer** 這類函式庫。它讓你用**看似直接修改**的語法撰寫（`draft.user.profile.name = 'x'`），底層透過代理記錄你碰過哪些路徑，然後只在那些路徑上建立新物件，產出正確的不可變結果。Redux Toolkit 內建了它，所以現在寫 reducer 可以直接用修改語法。

**詳細解析**：它的原理值得理解——用 `Proxy` 攔截讀寫，建立一份「草稿」，記錄哪些節點被修改過（結構共享），最後產生新的樹。沒被碰過的分支直接沿用原參照，所以效能等同於手寫的不可變更新，但可讀性好得多。要注意的限制是：在草稿上不能做非同步操作後再修改（草稿有生命週期）、以及**不能把草稿本身存到外部**（離開產生函式後就失效）。另一個方向是**扁平化資料結構**——把巢狀的資料正規化成以 ID 為鍵的表，深層更新自然變成淺層更新，這在管理大量關聯資料時比任何工具都有效。

**面試回答方式**：介紹 Immer 的用法與它解決的問題，並說明底層原理是 Proxy 加結構共享，所以效能等同手寫。點出兩個限制（草稿有生命週期、不能存到外部）。加分點是提出扁平化資料結構這個更根本的解法——把巢狀正規化成 ID 表，深層更新變成淺層更新。

### React 為什麼要求狀態不可變？

**核心答案**：因為它用**參照比較**判斷是否需要重新渲染。如果你直接修改物件內部，參照沒有改變，React 的比較會認為「沒有變化」而跳過更新，畫面就不會反映新資料。不可變更新保證了「有變動就有新參照」，讓這個廉價的比較是可靠的——比較兩個參照是 O(1)，深度比較整棵資料樹則昂貴得多。

**詳細解析**：這個設計的收益不只在渲染判斷。**`memo` 與 `useMemo` 的依賴比較**同樣依賴參照穩定，不可變更新讓「沒變的部分保持同一個參照」，於是沒受影響的子元件可以安全跳過重新渲染。此外不可變資料讓**時間旅行除錯**（保留每次狀態的歷史快照）成為可能，因為舊的狀態不會被後續的修改污染。要注意的是**不可變不等於深拷貝**——保持沒變的分支共用參照，正是這套機制能高效運作的前提；如果每次更新都深拷貝整棵樹，反而會讓所有子元件都以為自己變了，效能更差。

**面試回答方式**：核心是參照比較——直接修改不會改變參照，React 就跳過更新。強調參照比較是 O(1)，深度比較昂貴。加分點是延伸到 memo 的依賴比較與時間旅行除錯，並澄清不可變不等於深拷貝，全樹深拷貝反而讓所有子元件誤以為變了。

### structuredClone 遇到類別實例會怎樣？

**核心答案**：**屬性會被複製，但原型會遺失**——複製出來的是一個普通物件，不再是原本類別的實例，方法也跟著不見（因為方法在原型上）。如果類別實例中包含函式屬性（定義在實例上而非原型的方法），`structuredClone` 會直接拋出錯誤。

**詳細解析**：這意味著 `structuredClone` 適合複製**純資料**，不適合複製**有行為的物件**。需要複製類別實例時，比較可靠的做法是在類別上實作自己的 `clone` 方法，明確控制哪些欄位要複製、要不要建立新的實例。這也符合一個更廣的設計原則：盡量讓需要傳遞與複製的資料是純資料，把行為放在處理這些資料的函式裡，而不是綁在資料物件上。這個原則讓序列化、快取、跨執行緒傳遞、以及狀態管理都變得單純——在前端架構上，這是選擇「純資料加函式」而非「充血物件」的實際理由之一。

**面試回答方式**：明確說屬性複製但原型遺失、實例上的函式屬性會拋錯。接著給替代做法——在類別上自己實作 clone。加分點是把它上升到設計原則：讓要傳遞的資料保持純資料，行為放在函式裡，這讓序列化與跨執行緒傳遞都變單純。
