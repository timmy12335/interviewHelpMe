# 題目

前端要接收即時更新，該用哪一種方式？

## 核心答案

**依「方向」與「頻率」選擇。**

**輪詢**——**前端定時發請求**；**最簡單、與現有的 HTTP 基礎設施完全相容、易於除錯**；**適合更新頻率低（幾十秒以上）或者延遲不敏感的場景**。**它的缺點是大量的空回應浪費。**

**Server-Sent Events（SSE）**——**伺服器單向推送，走的仍是 HTTP**；**瀏覽器內建自動重連與事件 ID 續傳**；**適合通知、進度更新、以及串流的文字回應**（大型語言模型的逐字輸出是典型用途）。

**WebSocket**——**全雙工、低開銷**；**適合雙向且高頻的場景**（協作編輯、遊戲、即時交易）；**代價是需要獨立的伺服器支援、自己處理重連與心跳、而且無法直接享用 HTTP 的快取與中介設施。**

**選擇的原則是「從簡單的開始」**——**多數需求用輪詢或 SSE 就夠，而 WebSocket 的營運複雜度（連線狀態、擴展、代理相容性）常常被低估。**

## 詳細解析

**「SSE 被嚴重低估」**：它自帶重連、支援 `Last-Event-ID` 讓伺服器補送斷線期間的訊息、走標準 HTTP 於是能通過大部分的代理與防火牆——**而這些在 WebSocket 上都要自己實作**；**唯一的主要限制是單向（客戶端要送資料仍然用一般的請求，但那通常沒問題）**。**HTTP/1.1 下每個網域的連線數限制曾經是它的痛點，但在 HTTP/2 之後已經不是問題。**

**「WebSocket 的重連要自己設計」**：連線會因為網路切換、代理逾時、伺服器重啟而斷開——**而需要的是指數退避的重連、心跳偵測（因為 TCP 連線可能「假死」：看起來還在但實際上收不到資料）、以及重連後的狀態同步**（斷線期間錯過的訊息怎麼補）。**「重連後如何補齊資料」是最容易被忽略的部分**——**沒有它的話，使用者在短暫斷網後會看到不一致的畫面。**

**「長輪詢是一個過渡方案」**：伺服器收到請求後不立即回應而是等到有資料——**它比定時輪詢即時且比 WebSocket 簡單**；**但它佔用連線且在多數場景下已經可以被 SSE 取代**。

**「即時不等於必須推送」**：很多「即時」的需求其實可以用「在使用者操作時重新獲取」加上「視窗聚焦時刷新」達成——**而那完全不需要任何長連線**；**在導入即時通訊之前，先確認「使用者真的需要在沒有操作的情況下看到更新嗎」，能省下大量的複雜度。**

## 面試回答方式

先給三種方式各自的特性與適用場景，再給選擇原則（**從簡單的開始**）。加分點有四個：**SSE 被嚴重低估**——**它自帶重連、支援斷線補送、且能通過代理，而這些在 WebSocket 上都要自己做**；**WebSocket 的重連要自己設計**，**而「重連後如何補齊資料」是最容易被忽略的部分**；**長輪詢是過渡方案，多數場景已可被 SSE 取代**；以及**即時不等於必須推送**——**先確認使用者是否真的需要在沒有操作時看到更新**。

## 講稿

我會依方向跟頻率來選。

輪詢最簡單，跟現有的 HTTP 基礎設施完全相容，也容易除錯。更新頻率低或者延遲不敏感的用它就夠。

SSE 是伺服器單向推送，走的仍然是 HTTP。我覺得它被嚴重低估。它自帶重連，支援 Last-Event-ID 讓伺服器補送斷線期間的訊息，而且能通過大部分的代理跟防火牆。這些在 WebSocket 上都要自己實作。它唯一的主要限制是單向，但客戶端要送資料用一般請求就好，通常沒問題。

WebSocket 適合雙向而且高頻的場景，像協作編輯或者遊戲。但它的營運複雜度常被低估，連線狀態、擴展、代理相容性都要處理。重連也要自己設計，包括指數退避跟心跳，因為連線可能假死。

而重連之後怎麼補齊斷線期間的資料，是最容易被忽略的部分。

另外我會先問一件事，使用者真的需要在沒有操作的情況下看到更新嗎。很多即時需求其實用聚焦時刷新就夠了。

## 常見追問

### WebSocket 的擴展有什麼問題？

**核心答案**：**連線是有狀態的，所以無法像 HTTP 那樣隨意地負載平衡**。每個連線綁在特定的伺服器實例上——**於是「發訊息給某個使用者」需要知道他連在哪台機器**；**常見的解法是用一個發布訂閱層（Redis、NATS）讓所有實例都能廣播，而每個實例只把訊息送給自己持有的連線。**

**詳細解析**：**「連線數的成本主要在記憶體而非 CPU」**：每個連線需要維持緩衝區與狀態——**單機幾萬到十幾萬連線是常見的量級，而超過之後需要橫向擴展**；**而擴展時的難點是「重啟部署會斷開所有連線」**——**幾萬個客戶端同時重連會形成驚群效應打垮剛啟動的實例**；**所以需要在客戶端加入隨機抖動的退避，並在伺服器端做優雅的排空（逐步斷開而非一次全斷）**。**這類營運上的細節是「WebSocket 比看起來複雜」的主要來源**；**而它們在示範程式碼中永遠不會出現，卻在正式環境中決定成敗**。

**面試回答方式**：說明**連線有狀態所以無法隨意負載平衡**與常見的解法（發布訂閱層）。核心加分點是**連線數的成本主要在記憶體**與擴展時的難點：**重啟部署會斷開所有連線，幾萬個客戶端同時重連形成驚群效應**，並給出解法（客戶端隨機抖動退避、伺服器優雅排空）。收在洞察：**這類細節在示範程式碼中永遠不會出現，卻在正式環境中決定成敗**。

### 前端怎麼處理訊息的順序與重複？

**核心答案**：**用序號或版本號，並在客戶端做去重與排序**。網路重連、伺服器重送、以及多路徑都可能造成亂序或重複——**而讓每個訊息帶一個單調遞增的序號，客戶端就能丟棄已處理的、並偵測到缺口（需要補齊）**；**這比假設傳輸層保證順序可靠得多。**

**詳細解析**：**「偵測到缺口之後的處理策略」有兩種**：**請求補送遺漏的那幾筆**（需要伺服器保留一段歷史）——**或者直接重新獲取完整狀態**；**後者簡單但成本高，適合狀態不大的情況**。**而一個實用的混合是「小缺口補送、大缺口重取」**。**這個設計的核心觀念是「把即時推送當成一種優化而非唯一的資料來源」**——**基準狀態仍然透過一般的 API 取得，推送只是讓它更新得更快**；**於是任何推送的失敗都只造成延遲而非資料錯誤**。**這個架構上的定位，比任何具體的實作細節都更能決定系統的穩健程度。**

**面試回答方式**：給做法（**序號加上客戶端去重與排序**）並指出不該假設傳輸層保證順序。核心加分點是**偵測到缺口之後的兩種策略**與實用的混合（小缺口補送、大缺口重取）。收在架構觀念：**把即時推送當成優化而非唯一的資料來源**——**基準狀態仍透過一般 API 取得，於是推送的失敗只造成延遲而非資料錯誤**。

### 串流的文字回應（例如 AI 輸出）前端怎麼處理？

**核心答案**：**用 SSE 或 fetch 的 ReadableStream 逐塊接收並增量渲染**。要注意的是：**不要每收到一個字就重新渲染整個內容**（用增量的方式追加）、**處理串流中斷後的續接**、**以及在使用者離開時取消請求**（否則伺服器端的生成會繼續消耗資源）。

**詳細解析**：**「渲染的節流比想像的重要」**：如果每收到一個 token 就觸發一次 React 的重新渲染——**在長回應中會產生數千次渲染而讓介面卡頓**；**用 `requestAnimationFrame` 或者一個小的時間窗（例如每 50 毫秒）批次更新，能讓效能大幅改善而視覺上幾乎沒有差別**。**而如果回應中包含 Markdown 或程式碼，增量解析會更複雜**——**因為一個未完成的程式碼區塊在解析時是無效的**；**常見的處理是「對未完成的部分用純文字渲染，收到完整的結構後再切換成格式化的版本」**。**這些細節決定了串流輸出是感覺流暢還是感覺閃爍**；**而它們在功能可用之後才會浮現，所以值得提前知道。**

**面試回答方式**：給機制（SSE 或 ReadableStream 逐塊接收）與三個注意事項。核心加分點是**渲染的節流比想像的重要**——**每個 token 一次渲染會產生數千次而讓介面卡頓，用時間窗批次更新效能大幅改善而視覺幾乎無差別**。收在進階細節：**Markdown 與程式碼的增量解析更複雜**，**常見處理是未完成的部分用純文字、收到完整結構後再切換**。
