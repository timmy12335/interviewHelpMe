# 題目

響應式的斷點該怎麼定？容器查詢改變了什麼？

## 核心答案

斷點應該由「版面在哪裡壞掉」決定，而不是由裝置的尺寸決定——追著 iPhone 或 iPad 的尺寸設斷點，在下一代裝置出來時就過時了；正確的做法是把視窗慢慢拉寬，在版面開始擁擠或者行長過長的地方設一個斷點。

容器查詢改變的是「依據什麼判斷」：媒體查詢看的是視窗——而容器查詢看的是元件的父容器寬度；於是同一個卡片元件放在窄的側邊欄與寬的主內容區，可以自動用不同的排版。這讓元件真正可複用，因為它不再需要知道自己被放在頁面的哪裡。

**流體排版（`clamp()`）減少了斷點的需求**：`font-size: clamp(1rem, 0.9rem + 0.5vw, 1.5rem)` 讓字級隨視窗連續變化並有上下限——於是不需要在三個斷點各設一次；**間距與容器寬度同樣適用。**

而優先順序上，先用內建的彈性（flex-wrap、grid 的 auto-fit、百分比）解決，斷點只用在「版面結構需要真正改變」的地方——因為每個斷點都是後續維護的成本。

## 詳細解析

「行長是一個被低估的斷點依據」：一行文字超過大約 75 個字元後，閱讀的舒適度明顯下降——所以內容區的最大寬度應該由行長決定（`max-width: 65ch`）而非由視窗寬度決定；這一條規則能解決很多「在大螢幕上看起來很空洞」的問題。

**「`auto-fit` 與 `auto-fill` 的差別值得知道」**：`repeat(auto-fit, minmax(200px, 1fr))` 會讓現有的項目填滿可用空間——**而 `auto-fill` 會保留空的欄位軌道**；在項目數量少時兩者的視覺結果差異很大（auto-fit 會讓兩個項目各佔一半，auto-fill 會讓它們維持原本的寬度靠左）。這一個關鍵字的選擇，常常是「為什麼我的網格看起來怪怪的」的答案。

**「行動優先不只是寫法的順序」**：從最小的版面開始寫並用 `min-width` 逐步增強——好處是預設的樣式最簡單，而複雜度隨螢幕變大遞增；這通常比從桌面往下砍容易維護。而它也符合「行動裝置的資源較少，應該給它最少的樣式」這個原則。

**「不要只測寬度」**：橫向的手機、視窗只佔一半的桌面瀏覽器、以及有大字級設定的使用者——這些情況下高度或者相對尺寸才是限制；用 `dvh` 而非 `vh` 能處理行動瀏覽器網址列造成的高度變化，**那是一個很常見的體驗問題。**

## 面試回答方式

先給核心原則（斷點由版面在哪裡壞掉決定而非由裝置尺寸決定），再說明容器查詢改變了什麼與流體排版如何減少斷點需求，最後給優先順序。加分點有四個：**行長是被低估的斷點依據**（`max-width: 65ch`）；**`auto-fit` 與 `auto-fill` 的差別**與它造成的常見困惑；**行動優先不只是寫法順序**；以及**不要只測寬度**，而 `dvh` 能處理行動瀏覽器網址列造成的高度變化。

## 講稿

斷點應該由版面在哪裡壞掉決定，不是由裝置尺寸決定。追著某一代手機的尺寸設斷點，下一代出來就過時了。我的做法是把視窗慢慢拉寬，在版面開始擁擠或者行長過長的地方設一個。

而行長是一個被低估的依據。一行文字超過大概七十五個字元之後，閱讀舒適度明顯下降。所以內容區的最大寬度應該由行長決定，用 ch 這個單位。這一條能解決很多在大螢幕上看起來很空洞的問題。

容器查詢改變的是依據什麼判斷。媒體查詢看視窗，容器查詢看元件的父容器寬度。所以同一個卡片放在窄的側邊欄跟寬的主內容區可以自動用不同排版。這讓元件真正可複用，因為它不需要知道自己被放在頁面的哪裡。

另外 clamp 這類流體的寫法能減少斷點的需求，字級隨視窗連續變化並且有上下限。

而優先順序上，我會先用內建的彈性解決，斷點只用在版面結構真的需要改變的地方。

## 常見追問

### 為什麼行動瀏覽器上 100vh 會出問題？

**核心答案**：因為網址列會隨捲動收合，而 `vh` 對應的是「網址列收起時」的最大高度——於是 `height: 100vh` 的元素在網址列展開時會超出可視範圍，底部的按鈕被切掉。解法是用 `dvh`（動態視窗高度，會隨網址列變化）或者 `svh`（最小的視窗高度，保守但穩定）。

**詳細解析**：**「三個新單位各有適用場景」**：`svh` 是網址列展開時的高度（最小）——適合「一定要完整可見」的元素，例如全螢幕的對話框；**`lvh` 是網址列收起時的高度（最大）**；**`dvh` 會即時變化**——適合背景或者不介意跟著調整的版面，但要注意它變化時會觸發重排，用在動畫中可能造成抖動。所以常見的建議是「關鍵的互動元素用 `svh` 保證可見，裝飾性的區塊用 `dvh`」。這個問題是行動網頁最常見的版面 bug 之一——而在 2022 年之前只能用 JavaScript 測量並設定 CSS 變數來繞過，那個 hack 至今仍在很多程式碼庫裡。

**面試回答方式**：說明成因（`vh` 對應網址列收起時的最大高度）與後果（底部按鈕被切掉），給出 `dvh` 與 `svh` 的解法。核心加分點是**三個新單位各有適用場景**並說明各自對應什麼與注意事項（`dvh` 變化時觸發重排，用在動畫中可能抖動）。收在實務建議：關鍵互動元素用 `svh`，裝飾性區塊用 `dvh`。

### 響應式圖片和響應式版面怎麼配合？

**核心答案**：`sizes` 屬性要反映圖片在版面中的實際顯示寬度。如果一張圖在手機上佔滿寬度、在桌面上佔三分之一——那 `sizes="(min-width: 1024px) 33vw, 100vw"`；寫錯的話瀏覽器會選錯尺寸，可能下載了三倍大的圖。

**詳細解析**：「`sizes` 是最容易寫錯也最少被檢查的部分」：因為它是一段「重複描述版面規則」的字串——版面改了但 `sizes` 忘記跟著改，是很常見的情況；而它不會有任何錯誤提示，只是靜靜地浪費頻寬。驗證的方法是在開發者工具中查看圖片的 `currentSrc`，確認選中的尺寸是否合理。而更根本的解法是「用容器查詢單位或者讓建置工具生成 `sizes`」——部分框架的圖片元件已經能根據版面自動推導；如果沒有，那至少應該把 `sizes` 和版面的斷點定義放在一起，讓它們更可能被同步修改。

**面試回答方式**：說明 `sizes` 要反映實際顯示寬度並給出一個具體的例子與寫錯的後果。核心加分點是它是最容易寫錯也最少被檢查的部分——版面改了但它忘記跟著改，而且沒有任何錯誤提示，並給出驗證方法（**查看 `currentSrc`**）。收在根本解法：用框架的圖片元件自動推導，或至少把它和斷點定義放在一起。

### 該不該做獨立的行動版網站？

**核心答案**：**現在幾乎都不該**。維護兩套程式碼的成本高、內容容易不同步、SEO 需要額外處理、而且裝置的界線越來越模糊（平板、折疊機、桌面上的窄視窗）——響應式的單一程式碼庫在絕大多數情況下是正確的選擇。

**詳細解析**：「例外是使用場景真的不同的時候」：例如一個複雜的後台管理系統——行動版可能只需要提供查看與少數的快速操作，而非完整功能的縮小版；這時「同一套程式碼但不同的功能集」比「同一套 UI 硬塞進小螢幕」合理得多。關鍵的區分是「不同的版面」與「不同的產品」——前者用響應式，後者可能需要不同的介面設計但仍然可以共用底層的邏輯與 API。而在實務上，多數團隊高估了「行動版需要不同功能」的程度——使用者的期待通常是「我在手機上也能做同樣的事」；所以在決定砍掉行動版的功能前，值得先看實際的使用數據。

**面試回答方式**：給明確的答案（**現在幾乎都不該**）並列出理由。核心加分點是說明例外是使用場景真的不同的時候並用後台系統舉例，同時給出關鍵區分：「不同的版面」用響應式，「不同的產品」可以共用底層邏輯但用不同的介面設計。收在實務提醒：多數團隊高估了「行動版需要不同功能」的程度，砍功能前值得先看實際的使用數據。
