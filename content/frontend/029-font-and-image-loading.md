# 題目

Web 字型與圖片怎麼載入才不會拖慢頁面或造成版面跳動？

## 核心答案

字型的核心問題是「載入期間顯示什麼」——**`font-display` 控制這件事**：`block`（先隱藏文字，可能造成看不見文字的閃爍）、`swap`（先用備援字型，載完再換，可能造成明顯的字型跳動）、`fallback` 與 `optional`（更保守，超時就直接放棄自訂字型）。多數情況 `swap` 是合理的預設，而 `optional` 適合裝飾性的字型。

減少字型跳動的關鍵是「讓備援字型的度量接近自訂字型」——用 `size-adjust`、`ascent-override` 這些描述符調整備援字型的尺寸；做對之後換字時幾乎看不出版面移動。

**圖片的三個要點**：一定要有明確的寬高或 `aspect-ratio`（否則載入完成時會推開下方的內容，那是 CLS 的最大來源）、首屏的主要圖片用 `fetchpriority="high"` 並且不要 lazy load、**其餘的用 `loading="lazy"`**。

而格式與尺寸的選擇往往比載入策略影響更大——送一張 4000 像素寬的圖給一個 375 像素的螢幕，任何載入優化都救不回來。

## 詳細解析

**「字型的預載要謹慎使用」**：`<link rel="preload">` 會讓字型以高優先權下載——但如果預載了實際上不會用到的字重或字集，那是純粹的浪費且會排擠更重要的資源；所以只預載首屏確定會用到的那一兩個檔案。而子集化（只包含實際用到的字元）對中文字型特別重要——完整的中文字型可能是幾 MB，而子集化後可能只有幾十 KB。

**「響應式圖片的兩個維度」**：`srcset` 加 `sizes` 處理「不同螢幕密度與寬度該給多大的圖」——而 `<picture>` 加 `<source type>` 處理「支援的格式不同該給哪種」；**兩者常常需要一起用**。而一個常見的錯誤是寫了 `srcset` 但 `sizes` 不正確，於是瀏覽器選了過大的圖。

**「CLS 的來源不只圖片」**：動態插入的廣告或橫幅、字型換置、以及在載入後才出現的元素——**都會造成版面移動**；而預留空間（用固定高度的佔位或者 `min-height`）是通用的解法。在面試中能指出「CLS 主要不是圖片問題而是『尺寸未知的內容』問題」，展示的是理解而非記憶。

**「現代格式的實際收益」**：AVIF 通常比 JPEG 小百分之三十到五十——但編碼慢、部分舊瀏覽器不支援；**WebP 是更安全的預設**。而用 `<picture>` 提供多種格式的回退，是零風險的做法；如果有圖片 CDN，格式協商可以交給它自動處理。

## 面試回答方式

先給字型的核心問題（**載入期間顯示什麼**）與 `font-display` 的選項，再給減少跳動的關鍵（**調整備援字型的度量**）。圖片給三個要點並強調**格式與尺寸的選擇影響更大**。加分點有四個：預載要謹慎，只預載首屏確定會用到的，而子集化對中文字型特別重要；**響應式圖片的兩個維度**與 `sizes` 寫錯的常見問題；CLS 主要是「尺寸未知的內容」問題而非圖片問題；以及現代格式的實際收益與回退策略。

## 講稿

字型的核心問題是載入期間顯示什麼。font-display 控制這件事。block 是先隱藏文字，swap 是先用備援字型載完再換，optional 是超時就放棄。多數情況我用 swap，裝飾性的字型用 optional。

而減少換字時的版面跳動，關鍵是讓備援字型的度量接近自訂字型。用 size-adjust 這些描述符去調，做對之後換字幾乎看不出移動。

中文的話子集化特別重要。完整的中文字型可能好幾 MB，子集化之後可能只剩幾十 KB。

圖片有三個要點。一定要有明確的寬高或 aspect-ratio，否則載完會推開下方內容。首屏的主圖用 fetchpriority high 而且不要 lazy load。其他的用 lazy。

不過我覺得格式跟尺寸的選擇影響更大。送一張四千像素寬的圖給三百七十五像素的螢幕，任何載入優化都救不回來。

還有一點，版面跳動主要不是圖片問題，是尺寸未知的內容的問題。動態插入的橫幅跟字型換置都會造成。

## 常見追問

### 圖示應該用什麼方式？

**核心答案**：**看數量與使用方式**。少量且需要動態改色的用內聯 SVG（可以用 CSS 控制、無額外請求）；大量的用 SVG sprite 或者按需匯入的元件；**而圖示字型（icon font）現在不推薦**——它有無障礙問題（螢幕閱讀器可能讀出奇怪的字元）、載入失敗時顯示方塊、而且無法多色。

**詳細解析**：**「按需匯入的圖示庫容易失控」**：`import { IconA } from 'icon-library'` 看起來只匯入了一個——但如果那個函式庫的匯出方式不利於 tree shaking，實際打包的可能是全部幾千個圖示；這是打包分析中最常見的意外之一。驗證的方法是打包後看那個模組的實際大小，而不是相信 import 的寫法。而更根本的做法是「只把實際用到的圖示放進專案」——用一個腳本掃描程式碼中引用的圖示名稱並產生一個只含它們的 sprite；這雖然多一個建置步驟，但它讓體積與圖示庫的總量完全脫鉤。

**面試回答方式**：按數量與使用方式給建議，並說明**圖示字型現在不推薦**的三個理由（無障礙、載入失敗、無法多色）。核心加分點是**按需匯入的圖示庫容易失控**——看起來只匯入一個但可能打包全部，並給出驗證方法（看打包後的實際大小而非相信 import 的寫法）。收在更根本的做法：用腳本掃描實際引用並產生只含它們的 sprite。

### 背景圖片和 img 標籤怎麼選？

**核心答案**：內容性的圖片用 `<img>`，裝飾性的用 CSS 背景。這不只是慣例——`<img>` 有 alt 文字（無障礙與 SEO）、能被瀏覽器提早發現並優先載入（預載掃描器會看 HTML 但不會執行 CSS）、也支援 `srcset` 的響應式選擇；而 CSS 背景圖的載入時機較晚，因為它要等 CSS 解析並且元素實際被渲染。

**詳細解析**：「預載掃描器」是一個值得理解的機制：瀏覽器在主解析器被阻塞時，會用一個輕量的掃描器提前掃描 HTML 找出資源並開始下載——於是寫在 HTML 中的 `<img src>` 能很早開始載入；而 CSS 中的背景圖、JavaScript 動態插入的圖片，都錯過了這個機會。這解釋了為什麼「把首屏的主圖從 CSS 背景改成 `<img>`」有時能顯著改善 LCP；而如果因為版面需要必須用背景圖，可以用 `<link rel="preload" as="image">` 補回那個提早發現的效果。理解這個機制，能讓你在遇到「圖片載入太晚」時知道該往哪裡找原因。

**面試回答方式**：給選擇的原則（內容性用 `<img>`、裝飾性用背景）並列出 `<img>` 的三個優勢。核心加分點是解釋**預載掃描器**這個機制——它會提前掃描 HTML 但看不到 CSS 中的背景圖，並用它解釋為什麼改成 `<img>` 有時能顯著改善 LCP。收在替代方案：必須用背景圖時可以用 `preload as="image"` 補回提早發現的效果。

### 影片該怎麼處理？

**核心答案**：不要自動播放帶聲音的影片，而背景影片要考慮流量與電力。技術上的要點是：**`preload="metadata"` 而非 `auto`**（避免下載整支）、**提供 `poster` 圖**（在影片載入前顯示）、**用 `playsinline` 避免行動裝置全螢幕接管**、**以及尊重 `prefers-reduced-motion`。**

**詳細解析**：**「背景影片的成本常常被低估」**：一支十秒的循環背景影片可能是 2 到 5MB——在行動網路上那是幾秒的等待與可觀的流量；而它對使用者的實際價值通常遠低於那個成本。一個常見的替代是「用一張高品質的靜態圖加上細微的 CSS 動畫」——**視覺效果接近而成本是幾十 KB**。**而如果一定要用影片，那應該**：只在寬螢幕且非省流量模式下載入（用 `matchMedia` 與 `navigator.connection` 判斷）、**並且提供靜態圖作為預設**；這個「預設輕量、有條件升級」的模式，比「預設重量、有條件降級」安全得多——因為前者的失敗模式是少了裝飾，後者的失敗模式是頁面不可用。

**面試回答方式**：給四個技術要點。核心加分點是**背景影片的成本常常被低估**（十秒循環可能 2 到 5MB）與用靜態圖加細微 CSS 動畫的替代方案。收在模式：**預設輕量、有條件升級**，並對比它與「預設重量、有條件降級」的失敗模式差異——前者是少了裝飾，後者是頁面不可用。
