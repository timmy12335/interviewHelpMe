# 題目

四種渲染模式各自的取捨是什麼？一個電商網站的不同頁面該分別用哪一種？

## 核心答案

差別在**HTML 在哪裡產生、什麼時候產生**。**CSR**（客戶端渲染）伺服器只給空殼，內容由瀏覽器執行 JS 後產生——首屏最慢、SEO 最差，但後續互動不需要往返伺服器。**SSR**（伺服器端渲染）每次請求都在伺服器產生完整 HTML——首屏內容立即可見、SEO 好，代價是伺服器負擔與每次請求的延遲。**SSG**（靜態產生）在**建置時**就把 HTML 產好——最快也最便宜（可以完全由 CDN 提供），但內容更新必須重新建置。**ISR**（增量靜態再生）是 SSG 加上「過期後在背景重新產生」，兼顧靜態的速度與內容的新鮮度。電商的分配通常是：**商品詳情頁用 ISR**（內容變動不頻繁但要保持更新，且需要 SEO）、**首頁與分類頁用 SSG 或 ISR**、**搜尋結果與購物車用 CSR**（個人化且不需要 SEO）、**結帳流程用 CSR**（純互動）。判準是三個問題：需不需要 SEO、內容多久變一次、是不是個人化的。

## 詳細解析

**SSR 不等於快**：它讓**內容更早可見**（改善 LCP），但**互動可用的時間不一定更早**——HTML 出來之後仍要下載並執行 JS 完成水合（hydration），在此之前按鈕點了沒反應。這個「看得到但按不動」的空窗在低階裝置上很明顯，有時體驗比 CSR 的載入指示更糟，因為使用者以為壞了。所以選 SSR 的理由主要是 **SEO 與首屏內容可見**，不是籠統的「比較快」。

**水合的成本與新方向**：傳統水合要在客戶端把整棵樹重新建立一次並附上事件處理器，成本與頁面複雜度成正比。近年的方向是減少這個成本——**串流式伺服器端渲染**讓 HTML 分段送出、先送先顯示；**選擇性水合**讓使用者互動的區域優先水合；**伺服器元件**讓不需要互動的部分完全不送 JS 到客戶端。這些的共同目標是只為真正需要互動的部分付出 JS 成本。

**SSG 的限制與 ISR 的解法**：SSG 的問題在於**頁面數量多時建置時間爆炸**（十萬個商品頁全部預先產生要很久），以及**內容一改就要重建**。ISR 解決兩者——可以只預先產生熱門頁面，其餘在第一次被請求時產生並快取；設定重新驗證的時間讓內容自動更新。代價是首次請求該頁的使用者可能等待較久，以及快取失效的行為需要理解清楚才不會給出過期資料。

**個人化內容不適合靜態**：任何依使用者不同而不同的內容（購物車、推薦、會員價）都不能放進共用的靜態頁面，否則會發生**快取污染**——A 使用者的資料被快取後回給 B。實務上的做法是頁面主體靜態、個人化的部分在客戶端補上，或用邊緣運算依請求動態組合。這是設計快取策略時最容易出錯的地方，值得主動提。

**SEO 的實際考量**：搜尋引擎現在能執行 JavaScript，但**執行是延後且有預算限制的**，內容量大或更新頻繁的站點不能依賴它。對社群分享的預覽卡片而言更關鍵——多數社群平台的爬蟲**完全不執行 JavaScript**，所以 meta 標籤必須在伺服器端就產生好。

## 面試回答方式

用「**HTML 在哪裡產生、什麼時候產生**」把四種模式一次分清。接著給**三個判準問題**：需不需要 SEO、內容多久變一次、是不是個人化的，並用電商的不同頁面示範怎麼分配——這比逐一介紹模式更能展現判斷力。主動糾正一個常見誤解：**SSR 不等於快**，它改善的是內容可見時間，但水合完成前按鈕是不能用的。加分點有三個：講水合成本與串流、選擇性水合、伺服器元件這條演進線；指出 SSG 在頁面數量大時建置時間會爆炸而 ISR 如何解決；以及個人化內容混進靜態頁面會造成快取污染這個實際的安全問題。

## 講稿

差別在 HTML 在哪裡產生、什麼時候產生。

CSR 是伺服器只給空殼，瀏覽器執行 JS 之後才有內容。SSR 是每次請求都在伺服器產生完整 HTML。SSG 是建置的時候就產好，可以完全由 CDN 提供。ISR 是 SSG 加上過期之後在背景重新產生。

我選的時候問三個問題，需不需要 SEO、內容多久變一次、是不是個人化的。

以電商來說，商品詳情頁我會用 ISR，因為要 SEO、內容變動不頻繁但要保持更新。首頁跟分類頁類似。搜尋結果跟購物車用 CSR，因為個人化而且不需要 SEO。結帳流程也是純互動，用 CSR。

我想澄清一個常見的誤解，SSR 不等於快。它讓內容更早可見，但互動可用的時間不一定更早，因為 HTML 出來之後還要下載跟執行 JS 完成水合。這個看得到但按不動的空窗在低階裝置上很明顯，有時候比載入指示還糟，因為使用者以為壞了。

還有一個實務上很容易出錯的地方，個人化的內容不能混進靜態頁面，不然會發生快取污染，A 使用者的資料被快取之後回給 B。正確做法是主體靜態、個人化的部分在客戶端補。

## 常見追問

### 水合是什麼？為什麼它會造成問題？

**核心答案**：水合是在伺服器產生的 HTML 上「接回」JavaScript 的過程——框架在客戶端重新建立元件樹、比對既有的 DOM、附上事件處理器，讓靜態的 HTML 變成可互動的應用。問題有兩個：**成本**（要下載完整的 JS 並在客戶端重新執行一次渲染邏輯，複雜頁面可能造成長任務阻塞互動）與**不匹配**（伺服器與客戶端渲染出的結果不同時會產生警告甚至畫面錯亂）。

**詳細解析**：不匹配的常見來源是在渲染中使用了兩端不一致的值——`Date.now()`、隨機數、`window` 或 `localStorage` 的內容、以及依使用者時區格式化的時間。解法是把這類邏輯移到副作用中（渲染後才執行），或明確標記該區塊只在客戶端渲染。至於成本，近年的解法方向是**減少需要水合的範圍**：伺服器元件讓純展示的部分完全不送 JS；島嶼架構只對互動區塊水合；選擇性水合則依使用者互動的位置決定優先順序。這條演進線的核心觀念是——過去我們預設整頁都需要互動，現在改成只為真正需要的部分付費。

**面試回答方式**：先定義水合並指出兩個問題（成本與不匹配）。給出不匹配的常見來源與解法。加分點是講出減少水合範圍的演進線（伺服器元件、島嶼架構、選擇性水合），並把核心觀念總結為「只為真正需要互動的部分付費」。

### 什麼情況下 CSR 反而是正確選擇？

**核心答案**：**登入後的應用程式**——後台管理、儀表板、編輯器、內部工具。這些頁面**不需要 SEO**（搜尋引擎看不到也不該看到）、**內容完全個人化**（無法快取共用）、而且使用者通常長時間停留在單一應用中反覆互動，此時 CSR 的優勢（後續導航不需往返伺服器、狀態保留在客戶端）完全發揮，而首屏慢一點的代價相對可以接受。

**詳細解析**：即使選 CSR，仍應該處理首屏體驗——用骨架畫面取代空白、把路由層級的程式碼分割做好讓首屏只載入必要的 JS、以及預先載入使用者最可能前往的下一個頁面。另一個值得注意的是**混合策略**：同一個站台可以公開頁面用 SSG 或 SSR、登入後的區域用 CSR，現代框架都支援逐頁選擇渲染模式。**不需要整站統一**這件事本身就是重要的認知——把渲染模式當成每個頁面的決定而非架構的全域選擇，才能拿到各自的好處。

**面試回答方式**：明確給出登入後應用這個場景並說明三個理由（不需 SEO、完全個人化、長時間互動）。加分點是提到即使選 CSR 也要處理首屏（骨架畫面、程式碼分割、預先載入），以及強調渲染模式是逐頁決定而非全站統一。

### ISR 的內容更新有延遲，怎麼處理需要立即生效的情況？

**核心答案**：用**按需重新驗證**——在內容變更時由後端主動觸發特定頁面的重新產生，而不是等時間到期。多數支援 ISR 的框架都提供這個機制（透過 API 或 webhook）。典型的流程是：內容管理系統發布更新 → 呼叫重新驗證的端點 → 該頁面在下次請求時提供新版本。這樣既保有靜態的速度，又能在需要時立即更新。

**詳細解析**：實務上要注意三件事。**觸發端點必須有驗證**，否則任何人都能觸發大量重新產生造成資源消耗。**要處理相依頁面**——改一個商品可能同時影響商品頁、分類頁與首頁的推薦區塊，需要一併重新驗證，通常用標籤式的失效（為頁面標上標籤，依標籤批次失效）比逐一列出 URL 好維護。**CDN 層的快取也要一併處理**，否則來源已經更新但 CDN 仍回舊版。這三點是「內容更新了但使用者還看到舊的」這類問題最常見的成因，能主動列出來會顯示你實際維運過。

**面試回答方式**：給出按需重新驗證這個機制與典型流程。重點放在三個實務注意事項：端點要驗證、相依頁面用標籤式失效、CDN 快取也要處理。加分點是把這三點連結到「更新了但看到舊的」這類實際問題的成因。
