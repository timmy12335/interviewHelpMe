# 題目

前端做國際化時，有哪些容易低估的問題？

## 核心答案

**最容易低估的是「翻譯不只是換字串」**。實際要處理的包括：**複數規則**（不同語言的複數形式數量不同，中文一種、英文兩種、俄文三種、阿拉伯文六種）、**語序**（「你有 3 則新訊息」在不同語言中變數的位置不同，所以不能用字串拼接）、**日期時間與數字格式**（分隔符號、小數點、曆法、時區）、**以及文字長度的變化**（德文常常比英文長百分之三十，版面會被撐爆）。

**技術上的關鍵決定有三個**：**翻譯資源怎麼載入**（全部打包會讓體積翻倍，按語言分割並按需載入是常見做法）、**語言怎麼決定**（URL 路徑、子網域、Cookie，還是瀏覽器設定——影響 SEO 與可分享性）、**以及翻譯的鍵怎麼命名**（用完整的英文句子還是結構化的鍵）。

**而最實際的建議是「用 `Intl` 內建 API 而非自己實作格式化」**——**`Intl.NumberFormat`、`Intl.DateTimeFormat`、`Intl.RelativeTimeFormat`、`Intl.PluralRules` 都是瀏覽器內建的**；**自己寫的格式化幾乎一定在某些語言上是錯的。**

## 詳細解析

**「不要用字串拼接組出句子」**：`"你有 " + count + " 則訊息"` 在其他語言中語序完全不同——**正確的做法是用帶佔位符的完整模板（ICU MessageFormat）讓譯者能調整語序**；**而複數也應該在模板中表達（`{count, plural, ...}`）而非用 if 判斷。**

**「語言決定的方式影響 SEO」**：如果所有語言共用同一個 URL 而用 Cookie 切換——**搜尋引擎只會索引到一個版本**；**而用路徑（`/zh-TW/about`）或子網域讓每個語言有獨立的 URL，配合 `hreflang` 標籤，才能被正確地索引**。**這個決定在專案早期做比後期改容易得多。**

**「RTL 語言需要的不只是文字方向」**：阿拉伯文與希伯來文需要整個版面鏡像——**而現代 CSS 的邏輯屬性（`margin-inline-start` 而非 `margin-left`）讓這件事幾乎自動**；**在專案一開始就用邏輯屬性，比日後全面替換省事非常多**。**但圖示的方向、動畫的方向、以及混合了數字與文字的段落，仍然需要個別處理。**

**「翻譯的維護流程比技術實作更容易失控」**：開發者新增了一個鍵但譯者還沒翻——**顯示什麼（回退到預設語言、顯示鍵名、還是空白）需要決定**；**而長期下來，沒有人知道哪些鍵還在用**。**所以需要一個機制掃描程式碼中實際使用的鍵並標出孤兒與缺失**，**否則翻譯檔會不斷膨脹。**

## 面試回答方式

先指出**最容易低估的是翻譯不只是換字串**並列出四類實際問題，再給三個技術決定，最後強調**用 `Intl` 內建 API**。加分點有四個：**不要用字串拼接組句子**，**複數也應該在模板中表達**；**語言決定的方式影響 SEO**，**而這個決定早期做比後期改容易**；**RTL 需要的不只是文字方向**，**而邏輯屬性讓它幾乎自動**；以及**翻譯的維護流程比技術實作更容易失控**。

## 講稿

我覺得最容易低估的是翻譯不只是換字串。

要處理的有複數規則，中文一種形式、英文兩種、俄文三種、阿拉伯文六種。還有語序，你有三則新訊息這句話，變數在不同語言中的位置不同，所以絕對不能用字串拼接。另外是日期數字的格式，還有文字長度的變化，德文常常比英文長三成，版面會被撐爆。

技術上我會用 ICU 的訊息格式，帶佔位符的完整模板，讓譯者能調整語序，複數也在模板裡表達，不要用 if 判斷。

格式化的部分我一律用瀏覽器內建的 Intl。數字、日期、相對時間、複數規則都有。自己寫的格式化幾乎一定在某些語言上是錯的。

另外語言怎麼決定會影響 SEO。如果所有語言共用同一個網址而用 Cookie 切換，搜尋引擎只會索引到一個版本。用路徑或子網域配合 hreflang 才能被正確索引。這個決定早期做比後期改容易得多。

## 常見追問

### 翻譯資源怎麼載入才不會拖慢首屏？

**核心答案**：**按語言與按頁面雙重分割，只載入當前需要的**。把所有語言打包進主檔案，會讓體積乘上語言數——**而正確的做法是每個語言一個檔案（甚至每個頁面一組），在確定語言後動態載入**；**而伺服器端渲染的情況下，首屏所需的翻譯可以直接內嵌在 HTML 中避免額外的往返。**

**詳細解析**：**「翻譯載入的時序會造成閃爍」**：如果元件先渲染再等翻譯到達——**使用者會看到鍵名或英文閃一下**；**避免的方式是在路由層級把翻譯當成該頁面的資料一起載入（於是它與其他資料並行且在渲染前備妥）**。**這正是「把資料需求宣告在路由上」這個模式的另一個受益者**。**而對於伺服器端渲染，把首屏的翻譯內嵌進 HTML 是最乾淨的做法**——**代價是 HTML 略大，但省下了一次往返且完全沒有閃爍**；**這個取捨在首屏體驗優先的場景中幾乎總是划算的。**

**面試回答方式**：給做法（**按語言與頁面雙重分割，SSR 時內嵌首屏翻譯**）。核心加分點是**翻譯載入的時序會造成閃爍**與避免的方式（**在路由層級把翻譯當成該頁面的資料一起載入**），並指出這是「把資料需求宣告在路由上」的另一個受益者。收在取捨：**SSR 內嵌的代價是 HTML 略大但省下往返且完全沒有閃爍**。

### 時區該怎麼處理？

**核心答案**：**後端一律存 UTC，前端在顯示時轉成使用者的時區**。而關鍵的判斷是「這個時間的語意是什麼」——**「事件發生的瞬間」該用 UTC 存並在當地顯示**；**而「某人的生日」或者「每天早上九點的提醒」是一個當地的日期或牆上時間，存 UTC 會在跨時區或日光節約時出錯。**

**詳細解析**：**「日光節約時間是最常見的錯誤來源」**：某些當地時間在一年中會出現兩次或者完全不存在——**於是「在當地時間 2:30 執行」的排程可能被跳過或執行兩次**；**而用固定的偏移量（例如 +8）而非時區名稱（`Asia/Taipei`）儲存，會在規則變更時全部錯誤**（各國的時區規則確實會改變）。**所以正確的做法是「存 UTC 時間戳加上時區的 IANA 名稱」而非偏移量**。**而在前端，`Intl.DateTimeFormat` 能正確處理這些**——**手動用偏移量計算的程式碼幾乎一定在某些日期上是錯的**；**這是一個「不要自己算」的典型領域**。

**面試回答方式**：給基本原則（**後端存 UTC、前端轉當地**）並指出關鍵判斷是**這個時間的語意是什麼**，區分「事件的瞬間」與「牆上時間」。核心加分點是**日光節約是最常見的錯誤來源**（某些當地時間出現兩次或不存在）與**用時區名稱而非固定偏移量**。收在建議：**`Intl` 能正確處理，而手動用偏移量計算的程式碼幾乎一定在某些日期上是錯的**。

### 如果只做兩三種語言，需要完整的 i18n 方案嗎？

**核心答案**：**需要基本的結構，但可以省略進階的功能**。最低限度是：**所有的字串集中在資源檔而非散落在程式碼中**、**用帶佔位符的模板而非拼接**、**以及用 `Intl` 做格式化**；**這些的成本很低而它們讓日後增加語言變成一件小事。**

**詳細解析**：**「事後補做 i18n 的成本高得不成比例」**：字串散落在幾百個元件中——**要找出全部並替換是一項枯燥且容易遺漏的工作**；**而漏掉的那些會在上線後被使用者發現**。**所以即使當下只有一種語言，把字串集中管理仍然是划算的**——**它的額外成本大約是每個字串多一次查表，而收益是「未來的選項被保留了」**。**這是一個「低成本保留可逆性」的典型例子**——**與其在需要時付出高昂的改造成本，不如在一開始就付一點點**；**判斷這類投資值不值得的標準是「事後補做的成本除以現在做的成本」，而在 i18n 上這個比值通常在十倍以上**。

**面試回答方式**：給最低限度的三項並指出**它們的成本很低而讓日後增加語言變成小事**。核心加分點是**事後補做的成本高得不成比例**——**字串散落在幾百個元件中，要找出全部枯燥且容易遺漏**。收在通則：**這是「低成本保留可逆性」的典型例子**，**而判斷標準是「事後補做的成本除以現在做的成本」，在 i18n 上這個比值通常在十倍以上**。
