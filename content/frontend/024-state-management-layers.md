# 題目

什麼時候需要全域狀態管理？為什麼說「不要把伺服器資料放進全域 store」？

## 核心答案

多數狀態管理的混亂來自**沒有把不同性質的狀態分開**。實務上至少有四種：**伺服器狀態**（來自後端的資料——它在別處也會被修改、需要快取、需要重新驗證、有載入與錯誤狀態）、**客戶端狀態**（純前端的 UI 狀態——側邊欄開合、目前的主題、多步驟表單的暫存）、**URL 狀態**（篩選條件、排序、分頁、目前分頁籤——應該放在網址中，因為使用者期待能複製連結分享、能用上一頁）、以及**表單狀態**（欄位值與驗證，通常交給表單函式庫）。把伺服器資料放進全域 store 的問題是：**你等於自己實作了一套快取**——要處理過期、重新取得、多處同步、競態條件、以及載入與錯誤狀態，而這些正是資料查詢函式庫（React Query、SWR 這類）已經做好的事。所以「需不需要全域狀態管理」的正確問法是：**扣掉伺服器狀態與 URL 狀態之後，還剩下多少真正跨元件共用的客戶端狀態**——通常比想像中少很多。

## 詳細解析

**URL 狀態最常被忽略**：把篩選與分頁放在元件的 state 裡，會讓使用者無法分享連結、重新整理後回到初始狀態、上一頁的行為也不符預期。放進查詢參數之後，這些問題自動消失，而且**狀態變成可分享、可書籤、可回溯的**。判準很簡單：**如果使用者會期待「這個畫面能被連結描述」，那它就是 URL 狀態**。

**伺服器狀態的難點在同步而非儲存**：同一份資料可能被多個畫面使用、被其他使用者修改、在背景過期。資料查詢函式庫提供的能力包括：**快取與去重**（同一份資料同時被多處請求只發一次）、**背景重新驗證**（先給快取再更新）、**失效管理**（更新後讓相關查詢重新取得）、以及**樂觀更新與回滾**。自己用全域 store 加手動的請求邏輯重寫這些，是大量重複的工作且容易出錯。

**真正需要全域客戶端狀態的情況不多**：登入使用者的基本資訊（但這其實常常是伺服器狀態）、主題與語言偏好、以及少數跨頁面的 UI 狀態（例如全域的通知佇列）。其餘多半可以用**狀態下移**或**組合**解決。過早引入全域 store 的代價是所有狀態都被拉到最上層，反而讓重新渲染範圍變大、也讓元件難以獨立測試。

**選擇工具的順序**：先用 React 自身的 state 與 context；跨元件共用但變動頻繁時，context 的「所有消費者一起重新渲染」會成為問題，這時才引入細粒度訂閱的狀態庫（Zustand、Jotai 這類）；伺服器資料用查詢函式庫；篩選排序放 URL。**依需求逐步升級，而不是一開始就套完整方案**，是這題最重要的立場。

**狀態的來源要唯一**：同一份資料如果同時存在於 store 與元件 state，就必然出現不同步。常見的錯誤是把伺服器回傳的資料複製一份到本地 state 再修改，導致兩份資料分歧。正確做法是**衍生而非複製**——需要變形的資料在渲染時計算，需要編輯的資料維持單一來源並在提交後讓查詢失效重新取得。

## 面試回答方式

先把**四種狀態分清楚**（伺服器、客戶端、URL、表單），這個分類本身就是這題的核心答案。接著解釋為什麼伺服器資料不該放進全域 store——**那等於自己實作一套快取**，要處理過期、去重、競態、失效，而查詢函式庫已經做好了。主動點出 **URL 狀態最常被忽略**，並給判準：使用者會不會期待這個畫面能被連結描述。談工具時給**逐步升級的順序**（本地 state、context、細粒度狀態庫、查詢函式庫），並明確反對一開始就套完整方案。加分點是講**狀態來源要唯一**——把伺服器資料複製到本地 state 再修改是分歧的根源，應該衍生而非複製。

## 講稿

我覺得多數狀態管理的混亂，來自沒有把不同性質的狀態分開。

我至少會分四種。伺服器狀態是從後端來的資料，它在別處也會被改、需要快取跟重新驗證。客戶端狀態是純前端的 UI 狀態，像側邊欄開合、主題。URL 狀態是篩選、排序、分頁，這些應該放在網址裡。還有表單狀態，通常交給表單函式庫。

伺服器資料不該放進全域 store，因為那等於我自己實作了一套快取。我要處理過期、重新取得、多處同步、競態，還有載入跟錯誤狀態，而這些正是查詢函式庫已經做好的事。

URL 狀態是我覺得最常被忽略的。篩選條件放在元件 state 裡，使用者就沒辦法分享連結，重新整理會回到初始狀態，上一頁的行為也不對。我的判準是，如果使用者會期待這個畫面能被連結描述，那它就是 URL 狀態。

所以要不要用全域狀態管理，正確的問法是扣掉伺服器狀態跟 URL 狀態之後，還剩多少真正跨元件共用的客戶端狀態。通常比想像中少很多。

工具我會逐步升級，先用本地 state 跟 context，變動頻繁再換細粒度訂閱的，不會一開始就套完整方案。

## 常見追問

### context 什麼時候會成為效能問題？

**核心答案**：當 **context 的值頻繁變動且消費者很多**時。context 值一變，**所有使用它的元件都會重新渲染**，而且 `memo` 擋不住——因為 context 的訂閱繞過了 props 比較。所以把「使用者資訊」（很少變）與「目前的捲動位置」（一直變）放進同一個 context，會讓所有讀取使用者資訊的元件跟著高頻重新渲染。

**詳細解析**：解法有三個層次。**拆分 context**——依變動頻率把值分開，讓消費者只訂閱自己需要的部分，這是最直接也最常用的。**穩定傳入的值**——如果傳入的物件每次渲染都新建，等於每次都變更，要用 `useMemo` 包起來。**改用細粒度訂閱的狀態庫**——Zustand、Jotai 這類允許元件只訂閱 store 中的特定欄位，只有那個欄位變才重新渲染，從根本解決這個問題。判斷要不要升級的準則是：**拆分 context 之後還是不夠**，那才值得引入額外的相依。

**面試回答方式**：先給成因（值頻繁變動加消費者多，且 `memo` 擋不住）並用具體的混放例子說明。接著給三個層次的解法並排出順序。加分點是給出升級的判準——拆分 context 之後還不夠才引入狀態庫，展現你不會過早引入相依。

### 樂觀更新要怎麼做才安全？

**核心答案**：三個步驟——**快照當前狀態、立刻套用預期的結果、失敗時回滾並提示**。關鍵是**回滾必須確實**，而且要讓使用者知道操作失敗了，不能靜默還原（那會讓人以為自己看錯了）。成熟的查詢函式庫都提供這個流程的封裝：在變更前取消進行中的相關查詢、保存快照、套用樂觀值、失敗時用快照還原、無論成功失敗最後都讓相關查詢失效以取得伺服器的真實狀態。

**詳細解析**：適用的場景是**成功率高且失敗代價低**的操作——按讚、加入收藏、標記已讀、拖曳排序。不適合的是**失敗代價高或結果無法預測**的操作——付款、下單、任何需要伺服器計算結果的動作（例如產生的 ID、庫存扣減後的餘量），因為你無法預先知道正確的結果。還有一個容易忽略的細節是**多個樂觀更新同時進行**時的順序問題：如果使用者快速點擊多次，回滾的順序與快照的選擇要謹慎，否則可能還原到錯誤的中間狀態。實務上對高頻操作可以搭配防抖，只送出最後一次。

**面試回答方式**：給出三步驟並強調回滾要確實、失敗要提示不能靜默還原。接著給適用與不適用的場景各三個例子，判準是失敗代價與結果可否預測。加分點是提到多個樂觀更新並行時的回滾順序問題，以及用防抖處理高頻操作。

### 一份資料需要在多個頁面共用，你會怎麼設計？

**核心答案**：**先確認它是伺服器狀態還是客戶端狀態**。如果是從後端來的，用**查詢函式庫加上共同的查詢鍵**——多個頁面用同一個鍵請求，函式庫會自動去重與共用快取，根本不需要「共用」的設計。如果是純客戶端的，才考慮放進 context 或狀態庫。這個判斷順序能避免大量不必要的全域狀態。

**詳細解析**：實務上很多「需要跨頁共用」的需求，本質上是**不想重複請求**——而那正是查詢快取解決的問題，不是狀態管理的問題。誤把它當成狀態管理來解，就會寫出「在某個頁面請求資料放進 store、其他頁面從 store 讀」的設計，接著要自己處理「資料什麼時候該重新取得」「使用者在別的分頁改了怎麼辦」這些難題。用查詢快取的話，這些都由設定（過期時間、重新驗證時機、失效規則）表達，語意清楚得多。真正需要全域客戶端狀態的例子其實很有限——主題、語言、通知佇列、以及少數的跨頁 UI 狀態。

**面試回答方式**：給出「先分辨是伺服器還是客戶端狀態」這個判斷順序，並說明伺服器狀態用共同查詢鍵就自動共用。重點指出很多共用需求本質上是「不想重複請求」，用狀態管理來解會衍生一堆自己要處理的難題。加分點是列出真正需要全域客戶端狀態的有限例子。
