# 題目

前端的錯誤怎麼收集？有哪些容易漏掉的地方？

## 核心答案

**要捕捉的入口有四個，而少了任何一個都會有盲區**：**`window.onerror`**（同步的執行期錯誤）、**`unhandledrejection`**（沒有 catch 的 Promise，這是現代應用最常見的漏洞）、**框架的錯誤邊界**（React 的 Error Boundary 會攔截渲染錯誤，於是它們不會到達 `window.onerror`）、**以及資源載入失敗**（要在捕獲階段監聽 `error` 事件，因為它不冒泡）。

**收集到之後最重要的是「還原現場」**：**source map**（沒有它，堆疊只是壓縮後的亂碼）、**使用者的操作軌跡**（前幾步做了什麼）、**環境資訊**（瀏覽器、版本、網路狀況）、**以及發生的頻率與影響的使用者數。**

**而最容易被忽略的是「噪音的處理」**：瀏覽器擴充功能造成的錯誤、跨域腳本的 `Script error.`、以及使用者網路中斷造成的請求失敗——**這些會淹沒真正的問題**；**沒有分類與過濾的錯誤監控，最後會變成沒有人看的儀表板。**

## 詳細解析

**「Script error.」是一個經典的問題**：跨域載入的腳本發生錯誤時，出於安全考量瀏覽器只給出這個沒有資訊的訊息——**解法是在 script 標籤加上 `crossorigin="anonymous"` 並讓 CDN 回應正確的 CORS 標頭**；**這個設定漏掉的話，你的錯誤監控對所有從 CDN 載入的程式碼都是瞎的**。**而這正是「以為有監控其實沒有」的典型情況。**

**「source map 的處理有安全考量」**：把 source map 公開部署，等於公開原始碼——**而正確的做法是在建置時上傳到監控服務，不隨產物一起發布**（或者用 `sourceMappingURL` 指向一個需要驗證的位置）；**這樣既能還原堆疊又不洩漏程式碼**。

**「影響範圍比錯誤次數重要」**：一個錯誤發生一萬次但都來自同一個使用者（可能是一個迴圈），和發生一百次但來自一百個使用者——**後者嚴重得多**；**所以按「受影響的使用者數」排序，比按發生次數排序更能指出優先順序**。

**「錯誤要能連到使用者的實際體驗」**：許多被記錄的錯誤其實不影響使用者（背景的重試最終成功了、一個非關鍵的分析請求失敗）——**而分辨它們需要在記錄時就帶上「這個錯誤導致了什麼」的資訊**；**否則團隊會花時間在無害的錯誤上，而真正讓使用者卡住的問題埋在噪音裡**。

## 面試回答方式

先給四個捕捉入口並強調**少了任何一個都有盲區**，特別點出 `unhandledrejection` 與錯誤邊界。再給還原現場需要的四項資訊。加分點有四個：**`Script error.` 的成因與 `crossorigin` 的設定**——**漏掉它等於對 CDN 載入的程式碼完全是瞎的**；**source map 的安全處理**（上傳而非公開部署）；**按受影響的使用者數排序而非發生次數**；以及**要能分辨錯誤是否真的影響體驗**。最後補上**噪音的處理**。

## 講稿

要捕捉的入口有四個，少了任何一個都會有盲區。window.onerror 抓同步錯誤，unhandledrejection 抓沒有 catch 的 Promise，這在現代應用是最常見的漏洞。框架的錯誤邊界會攔截渲染錯誤，所以那些不會到 onerror。還有資源載入失敗，要在捕獲階段監聽，因為它不冒泡。

有一個經典的坑是 Script error 這個沒有資訊的訊息。原因是跨域載入的腳本出於安全考量不給細節。解法是在 script 標籤加上 crossorigin，並且讓 CDN 回應正確的標頭。這個設定漏掉的話，你對所有從 CDN 載入的程式碼都是瞎的。這是以為有監控但其實沒有的典型情況。

另外我會按受影響的使用者數排序，不是按發生次數。一個錯誤發生一萬次但都來自同一個人，可能只是一個迴圈。發生一百次但來自一百個人，那嚴重得多。

還有噪音要處理。擴充功能造成的錯誤跟網路中斷會淹沒真正的問題。

## 常見追問

### 錯誤邊界該放在哪一層？

**核心答案**：**多層，而不是只在最外面包一個**。最外層防止整頁白畫面——**但如果只有那一層，一個側邊欄的錯誤會讓整個應用消失**；**正確的做法是在有意義的區塊邊界各放一個（每個路由、每個獨立的面板、每個列表項），於是一個區塊壞掉時其他部分仍然可用。**

**詳細解析**：**「降級的體驗要設計而非只顯示錯誤」**：一個好的錯誤邊界不只是顯示「出錯了」——**它應該提供重試、保留使用者已輸入的資料、並說明哪些功能仍然可用**；**而如果那個區塊是非關鍵的（例如推薦區塊），直接隱藏它可能比顯示錯誤訊息更好**。**這個判斷取決於「使用者在這裡的主要任務是什麼」**——**擋住主要任務的錯誤要明顯，而周邊功能的錯誤應該安靜地降級**。**另外要注意 React 的錯誤邊界不會捕捉事件處理器、非同步程式碼與 SSR 中的錯誤**——**那些仍然需要 try/catch 或者全域的處理器**；**以為錯誤邊界能捕捉一切，是一個常見的誤解。**

**面試回答方式**：給明確的做法（**多層，在有意義的區塊邊界各放一個**）並說明只有最外層的問題。核心加分點是**降級的體驗要設計**——**提供重試、保留輸入、說明哪些仍可用，而非關鍵區塊可以直接隱藏**，並給出判斷依據。收在常見誤解：**錯誤邊界不捕捉事件處理器、非同步程式碼與 SSR 中的錯誤**。

### 怎麼處理只在特定使用者身上出現的問題？

**核心答案**：**靠會話重播與詳細的環境資訊**。無法重現的問題通常來自特定的環境（舊瀏覽器、擴充功能、特殊的螢幕尺寸、關閉的 cookie、企業的網路代理）——**而會話重播能直接看到使用者的操作與畫面**；**如果不能用重播，那至少要在錯誤中帶上足夠的環境指紋以便分群。**

**詳細解析**：**「分群比個案更有價值」**：與其追一個使用者的問題——**不如檢查「有沒有一群共同特徵的使用者都遇到了」**；**例如「所有 Safari 16 的使用者」或者「所有從某個網域來的使用者」**。**這個分析能把一個看起來隨機的問題變成一個明確的相容性問題**。**而在導入會話重播時要注意隱私**——**輸入框的內容、個人資訊、以及可能的付款資料都必須被遮蔽**；**多數工具有預設的遮蔽規則但那通常不夠，需要針對自己的應用明確標記敏感區域**；**而這個設定應該在導入時就做，因為一旦錄到敏感資料，清理的成本很高。**

**面試回答方式**：給兩個手段（會話重播、環境指紋）並說明無法重現的問題通常來自哪些環境。核心加分點是**分群比個案更有價值**並給出具體的分群方式。收在隱私：**輸入內容與個資必須遮蔽，預設規則通常不夠**，**而這個設定應該在導入時就做，因為錄到之後清理的成本很高**。

### 前端該記錄哪些非錯誤的事件？

**核心答案**：**能幫助診斷的關鍵路徑節點**：**API 請求的耗時與狀態**、**路由的切換**、**重要的使用者操作**（提交、付款、上傳）、**以及效能指標**（Core Web Vitals 的實際值）。**而要避免的是記錄一切**——**因為量會很快變成成本問題，而且真正有用的訊號會被稀釋。**

**詳細解析**：**「記錄的設計應該從『我會想回答什麼問題』倒推」**：例如「付款失敗率是不是在某個瀏覽器上特別高」——**那就需要在付款流程的每一步記錄狀態與環境**；**而漫無目的地記錄一堆事件，在真的出問題時常常發現缺了關鍵的那一項**。**這個「先定義問題再決定記錄什麼」的順序，比「先記錄再說」有效得多**。**而另一個實用的原則是「記錄結果與轉換而非每一次點擊」**——**知道「一百個人開始付款、八十個完成、二十個在第三步離開」，比知道每個人點了哪些按鈕更能指出問題**；**前者是漏斗，而漏斗幾乎總是比原始事件流更有行動價值。**

**面試回答方式**：給該記錄的四類並指出**要避免記錄一切**與原因。核心加分點是**從「我會想回答什麼問題」倒推**這個設計順序，並用付款失敗率的例子說明。收在原則：**記錄結果與轉換而非每一次點擊**——**漏斗幾乎總是比原始事件流更有行動價值**。
