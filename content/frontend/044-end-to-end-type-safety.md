# 題目

前後端的介面怎麼管理才不會在改動時靜默地出錯？

## 核心答案

**核心問題是「契約散落在兩邊的程式碼與人的記憶中」**——**後端改了一個欄位名稱，前端要等到執行期才發現**；**而如果那個欄位在不常走的路徑上，可能上線很久才被使用者發現。**

**解決的方向是「單一來源加上自動化的驗證」，有幾種層次**：**從規格生成**（OpenAPI 或 GraphQL schema 生成兩邊的型別）、**從程式碼推導**（tRPC 這類方案讓前端直接取得後端的型別，適合同一個儲存庫）、**以及契約測試**（Pact 這類工具，讓兩邊的假設被明確驗證）。

**而無論用哪一種，執行期的驗證仍然必要**——**因為型別只在編譯期存在，而部署的不同步、快取的舊回應、以及中介層的改寫都可能讓實際的資料不符**。

**最實際的最小方案是**：**用 schema 工具在 API 邊界解析回應**（同時得到型別與執行期驗證）、**並在 CI 中檢查前端的型別與後端的規格是否一致**；**這兩件事的成本不高而它們涵蓋了大部分的風險。**

## 詳細解析

**「破壞性變更的溝通比技術方案更重要」**：即使有完美的型別生成——**如果後端在週五下午改了一個欄位而前端還沒部署，使用者仍然會遇到錯誤**；**所以需要的是流程上的約定**：**新增欄位是安全的、移除或改名要先標記棄用並等前端遷移、而回應的格式改變要用版本或者新的端點**。**這個「只做向後相容的變更」原則，比任何工具都更能減少事故。**

**「GraphQL 解決了一部分問題但帶來新的」**：它讓前端精確地要求需要的欄位（避免了過度獲取），而 schema 是強制的契約——**但它也讓快取變複雜、讓後端的查詢效能難以預測（N+1 問題）、而且錯誤處理的模型與 HTTP 狀態碼不對齊**；**所以它是一個取捨而非普遍的升級。**

**「錯誤回應也是契約的一部分」**：多數團隊仔細定義了成功的回應格式——**卻讓錯誤回應是各種形狀（有時是字串、有時是物件、有時是 HTML 的錯誤頁）**；**於是前端的錯誤處理充滿了防禦性的判斷**。**統一錯誤的格式（一個 code、一個給使用者看的訊息、一個給開發者的細節）是低成本高收益的改善。**

**「契約測試的價值在於它跑在兩邊」**：前端寫下「我期待這個端點回傳這樣的資料」——**而後端的 CI 驗證它真的會**；**於是後端在合併前就知道自己會不會破壞前端**，**而不是等到整合時才發現**。

## 面試回答方式

先指出核心問題（**契約散落在兩邊**）與後果，再給三種層次的方案並強調**執行期驗證仍然必要**，最後給最小的實際方案。加分點有四個：**破壞性變更的溝通比技術方案更重要**與「只做向後相容的變更」原則；**GraphQL 解決一部分問題但帶來新的**（快取、N+1、錯誤模型）；**錯誤回應也是契約的一部分**——**多數團隊定義了成功格式卻讓錯誤是各種形狀**；以及**契約測試的價值在於它跑在兩邊**。

## 講稿

核心問題是契約散落在兩邊的程式碼跟人的記憶裡。後端改了一個欄位名稱，前端要到執行期才發現。而如果那個欄位在不常走的路徑上，可能上線很久才被使用者發現。

解決的方向是單一來源加上自動化驗證。可以從 OpenAPI 或 GraphQL 的 schema 生成兩邊的型別，或者在同一個儲存庫裡用 tRPC 這類方案讓前端直接拿到後端的型別。

但無論哪一種，執行期的驗證仍然必要。因為型別只在編譯期存在，而部署不同步、快取的舊回應、中介層改寫都可能讓實際資料不符。

不過我覺得比技術方案更重要的是流程上的約定。新增欄位是安全的，移除或改名要先標記棄用並等前端遷移，格式改變要用新的端點。這個只做向後相容變更的原則，比任何工具都更能減少事故。

另外錯誤回應也是契約的一部分。很多團隊仔細定義了成功的格式，卻讓錯誤回應是各種形狀，於是前端的處理充滿防禦性判斷。

## 常見追問

### API 版本該怎麼管理？

**核心答案**：**盡量避免版本，用向後相容的演進取代**。因為每個版本都是一份要維護的程式碼——**而在有數個版本並存時，一個 bug 要修好幾次**；**所以優先的順序是：新增欄位（安全）、標記棄用並遷移（需要溝通）、最後才是新版本（成本最高）。**

**詳細解析**：**「棄用需要一個可觀測的流程」**：標記某個欄位為棄用之後——**你需要知道「還有誰在用」才能安全地移除**；**做法是在後端記錄該欄位被請求的次數與來源，觀察到歸零後再移除**。**沒有這個觀測，棄用就只是一個註解而永遠不敢真的刪**；**於是 API 只會不斷膨脹**。**這也是為什麼「先加上使用追蹤、再宣告棄用、觀察、最後移除」這個順序很重要**——**它把一個靠溝通與信任的過程，變成一個有數據支撐的過程**；**而在對外的 API 上，這幾乎是唯一可行的做法，因為你無法確認所有的使用者是否已經遷移。**

**面試回答方式**：給優先順序（**新增 → 棄用遷移 → 新版本**）並說明為什麼避免版本。核心加分點是**棄用需要一個可觀測的流程**——**要知道「還有誰在用」才能安全移除，做法是記錄該欄位的請求次數與來源**，並指出沒有觀測的棄用只是一個註解。收在順序：**先加追蹤、再宣告棄用、觀察、最後移除**，**而在對外 API 上這幾乎是唯一可行的做法**。

### BFF 模式解決什麼問題？

**核心答案**：**它在前端與多個後端服務之間加一層，負責聚合與裁剪**。解決的是：**前端需要呼叫五個服務才能組出一個畫面**（往返太多）、**後端的通用 API 回傳了前端不需要的大量欄位**、**以及不同的客戶端（網頁、行動、電視）需要不同形狀的資料。**

**詳細解析**：**「BFF 的擁有權應該歸前端團隊」**：這是這個模式的關鍵——**如果 BFF 由後端團隊維護，那前端要改一個欄位仍然需要跨團隊協調，問題只是被搬了個位置**；**而由前端團隊擁有時，畫面需求的變化可以在同一個團隊內完成**。**代價是前端團隊要承擔一個服務的營運責任**（部署、監控、擴展）——**所以它適合有能力承擔這些的團隊，而不是所有情況**。**而一個較輕的替代是「用 GraphQL 或者在框架的伺服器端層做聚合」**（Next.js 的路由處理器、Remix 的 loader）——**它們提供了類似的聚合能力而不需要獨立的服務**；**在多數規模下，這個較輕的方案已經足夠**。

**面試回答方式**：說明 BFF 在做什麼與它解決的三類問題。核心加分點是**BFF 的擁有權應該歸前端團隊**——**否則問題只是被搬了個位置**，並誠實給出代價（承擔服務的營運責任）。收在較輕的替代：**用框架的伺服器端層做聚合**，**在多數規模下已經足夠**。

### 前端該不該直接連資料庫？

**核心答案**：**在有適當授權層的前提下可以，但要非常清楚它的前提**。Firebase、Supabase 這類方案讓前端直接查詢——**而安全性完全依賴於資料庫的列級安全規則寫得正確**；**規則寫錯就是資料外洩，而規則的測試比 API 的測試更容易被忽略。**

**詳細解析**：**「它把授權邏輯從程式碼搬到了規則」**：好處是少了一整層的樣板程式碼且迭代很快——**代價是那些規則成為安全的唯一防線，而它們的表達能力有限、除錯困難、也不容易做程式碼審查**；**複雜的業務規則（例如「只有在訂單未出貨且使用者是建立者或管理員時才能取消」）用規則語言表達會非常難讀**。**所以常見的實務是「簡單的讀取直連、有業務邏輯的操作走伺服器端函式」**——**這個混合讓兩邊的優勢都能用上**。**而在面試中能指出「這個選擇的關鍵在於你的授權規則有多複雜」，展示的是超越工具偏好的判斷。**

**面試回答方式**：給條件式的答案（**可以，但要清楚前提**）並指出安全完全依賴列級規則。核心加分點是**它把授權邏輯從程式碼搬到了規則**與那個代價（表達能力有限、除錯困難、不易審查），並用一個複雜規則的例子說明。收在實務做法：**簡單讀取直連、有業務邏輯的操作走伺服器端函式**，**而關鍵在於你的授權規則有多複雜**。
