# 題目

在瀏覽器輸入網址按下 Enter 之後，到頁面顯示出來，中間經過哪些步驟？

## 核心答案

大致分成六段：**一、解析網址與檢查快取**——瀏覽器先判斷輸入的是網址還是搜尋詞，接著查詢各層快取（記憶體快取、磁碟快取、Service Worker），命中就可能直接回傳。**二、DNS 解析**——把網域轉成 IP，依序查瀏覽器快取、作業系統快取、路由器、ISP 的 DNS 伺服器。**三、建立連線**——TCP 三次握手，HTTPS 還要再做 TLS 握手交換金鑰（HTTP/3 改用 QUIC，把兩者合併以減少往返）。**四、發送請求與接收回應**——伺服器可能回傳 200 或各種重新導向與快取相關的狀態碼。**五、解析與渲染**——建 DOM 與 CSSOM、合成渲染樹、版面計算、繪製、合成，過程中遇到子資源（CSS、JS、圖片、字體）會發起新的請求。**六、執行 JavaScript 與後續互動**。這題的價值不在背步驟，而在你能從哪一段切入談優化與排查——面試官通常會挑一段往下深問。

## 詳細解析

**DNS 的優化手段**：`dns-prefetch` 可以提前解析第三方網域的 DNS，`preconnect` 更進一步連 TCP 與 TLS 都先建立好。這對「頁面載入後才會用到的第三方資源」（分析工具、字體、CDN）特別有效，能省下數百毫秒。但要節制——每個 `preconnect` 都佔用連線資源，過多反而拖慢。

**HTTPS 的握手成本與優化**：TLS 握手需要額外的往返，這在高延遲的行動網路上很明顯。優化手段包括 **TLS 1.3**（把握手從兩次往返縮成一次，且支援 0-RTT 恢復）、**連線重用**（HTTP/2 對同一網域只開一條連線並多工傳輸）、以及 **HSTS**（讓瀏覽器直接用 HTTPS，省下一次從 HTTP 到 HTTPS 的重新導向）。

**HTTP/1.1、2、3 的差別**：HTTP/1.1 有**隊頭阻塞**——同一條連線上的請求必須依序回應，所以瀏覽器要對同一網域開六條左右的連線。HTTP/2 引入**多工**，一條連線可以同時傳多個串流，解決了應用層的隊頭阻塞，但TCP 層的封包遺失仍會阻塞所有串流。HTTP/3 改用基於 UDP 的 QUIC，每個串流獨立，徹底解決這個問題，而且連線建立更快、支援連線遷移（切換網路不斷線）。

**解析階段的阻塞行為**：HTML 解析遇到 `<script>` 會**暫停解析**去下載並執行（除非有 `defer` 或 `async`）；CSS 不阻塞解析但**阻塞渲染**，而且會**阻塞後面的腳本執行**（因為腳本可能查詢樣式）。這解釋了為什麼 CSS 要放頭部、腳本要放底部或加 `defer`。瀏覽器有**預載掃描器**會提前掃描後續的資源開始下載，減緩阻塞的影響。

**這題的正確答法是「有深有淺」**：完整背出所有細節反而顯得零散。好的做法是先用一分鐘給出六段的骨架，然後說「這裡面我對某一段特別熟，可以展開講」——把主導權交出去讓面試官挑，同時展示你知道每一段可以深到什麼程度。

## 面試回答方式

先用一分鐘給出**六段骨架**（快取檢查、DNS、連線、請求回應、解析渲染、執行 JS），不要一開始就鑽細節。接著主動說「這幾段裡我對某一段比較熟」邀請對方選擇，這比自顧自講十分鐘有效。被追問時每一段都要能給出**優化手段**：DNS 用 `preconnect`、連線用 TLS 1.3 與 HTTP/2 多工、解析用 `defer` 與關鍵 CSS。加分點是講清楚 **HTTP/1.1 到 3 的演進解決了什麼**（應用層隊頭阻塞 → TCP 層隊頭阻塞），以及CSS 會阻塞渲染也阻塞後面的腳本執行這個常被忽略的行為。

## 講稿

我分六段來講。

第一段是解析網址跟查快取。瀏覽器先判斷輸入的是網址還是搜尋詞，然後依序查記憶體快取、磁碟快取、Service Worker，命中的話可能就直接回了。

第二段 DNS 解析，把網域轉成 IP，一樣是逐層查快取。第三段建立連線，TCP 三次握手，HTTPS 還要 TLS 握手。HTTP/3 用 QUIC 把這兩件事合併，減少往返。

第四段發請求收回應，第五段是解析跟渲染，建 DOM 跟 CSSOM、合成渲染樹、算版面、繪製、合成。過程中遇到子資源會再發請求。第六段是執行 JavaScript 跟後續互動。

這裡面每一段都可以往下深挖。比如解析階段有個常被忽略的行為，CSS 不阻塞 HTML 解析，但它阻塞渲染，而且會阻塞後面的腳本執行，因為腳本可能會查詢樣式。這就是為什麼 CSS 放頭部、腳本要加 defer。

不過我不確定你想聽哪一段比較細，網路那邊還是渲染那邊我都可以展開。

## 常見追問

### HTTP/2 已經解決隊頭阻塞了，為什麼還需要 HTTP/3？

**核心答案**：因為 HTTP/2 只解決了**應用層**的隊頭阻塞，**TCP 層的仍然存在**。HTTP/2 在一條 TCP 連線上多工傳輸多個串流，但 TCP 保證按序交付——只要有一個封包遺失，**所有**串流的資料都得等它重傳完成才能繼續處理。在封包遺失率高的網路（行動網路、擁塞的 Wi-Fi）上，HTTP/2 的表現可能反而不如開多條連線的 HTTP/1.1。

**詳細解析**：HTTP/3 的解法是**換掉傳輸層**——改用基於 UDP 的 QUIC，在其上自行實作可靠傳輸與擁塞控制，讓每個串流獨立處理遺失與重傳，一個串流卡住不影響其他。QUIC 還帶來兩個額外好處：**握手更快**（把傳輸層與加密握手合併，通常一次往返就能開始傳資料，恢復連線甚至可以 0-RTT）、以及**連線遷移**（用連線 ID 而非 IP 加通訊埠識別連線，手機從 Wi-Fi 切到行動網路不會斷線）。代價是 UDP 在部分網路環境會被封鎖或降速，所以實務上仍需保留 HTTP/2 的回退路徑。

**面試回答方式**：核心是分清應用層與 TCP 層的隊頭阻塞，並說明 TCP 的按序交付為什麼讓一個封包遺失卡住所有串流。接著給 HTTP/3 的解法（QUIC 讓串流獨立）。加分點是補上握手更快與連線遷移兩個好處，以及 UDP 可能被封鎖需要回退這個實務考量。

### defer 和 async 差在哪？該用哪個？

**核心答案**：兩者都**不阻塞 HTML 解析**，差別在**執行時機與順序**。`async` 是**下載完就立刻執行**（可能中斷解析），多個 `async` 腳本的執行**順序不保證**。`defer` 是**等 HTML 解析完成後、`DOMContentLoaded` 之前才執行**，且**保證按文件中的順序執行**。所以有依賴關係或需要操作完整 DOM 的腳本用 `defer`；完全獨立、越早執行越好的（例如分析腳本）用 `async`。

**詳細解析**：實務上 `defer` 是更安全的預設值——多數應用程式的腳本彼此有依賴，用 `async` 會產生難以重現的順序問題。要注意兩者**只對外部腳本有效**，內聯腳本會被忽略。另外 `type="module"` 的腳本**預設就有 defer 的行為**，所以現代的模組化前端通常不需要顯式加上。還有一個容易忽略的點：`defer` 保證在 `DOMContentLoaded` 之前執行，所以在 `defer` 腳本裡註冊 `DOMContentLoaded` 監聽器是有效的；但在 `async` 腳本裡註冊就可能已經錯過了那個事件。

**面試回答方式**：用「執行時機」與「順序保證」兩個維度講清差別，並給選擇判準（有依賴或要操作 DOM 用 defer，獨立的用 async）。加分點是提到模組腳本預設有 defer 行為、以及在 async 腳本裡註冊 `DOMContentLoaded` 可能已經錯過這個實際陷阱。

### 頁面白屏了，你會怎麼排查？

**核心答案**：**由外而內逐層排除**。先看**網路面板**——HTML 文件本身回來了嗎（狀態碼是什麼）、關鍵的 JS 與 CSS 有沒有 404 或被 CORS 擋掉。再看**主控台**——有沒有未捕捉的錯誤讓整個應用崩潰（單頁應用中一個渲染期錯誤就足以白屏）。再看 **DOM**——根節點裡有沒有內容，沒有的話代表框架根本沒掛載成功。最後看**樣式**——是不是有全域樣式讓內容不可見（高度為零、`display: none`、顏色與背景相同）。

**詳細解析**：分辨的關鍵是**內容在不在 DOM 裡**——在但看不到是樣式問題，不在則是 JS 或資料問題。單頁應用最常見的原因是**執行期錯誤中斷了渲染**，防禦手段是加上錯誤邊界，讓局部錯誤不至於讓整頁空白。另一類常見原因是**環境相關**：正式環境的路徑設定錯誤導致資源 404、CDN 快取了壞掉的版本、或是某些瀏覽器不支援用到的新語法而打包時沒有正確降級。這類問題在本地開發完全看不到，所以排查時要**先確認能不能重現**，不能重現就從錯誤監控的紀錄與使用者的環境資訊下手。

**面試回答方式**：給出由外而內的四層排查順序（網路、主控台、DOM、樣式），並給出分辨關鍵——內容在不在 DOM 裡。加分點是提到單頁應用的渲染期錯誤與錯誤邊界，以及環境相關問題（路徑、CDN 快取、語法降級）在本地看不到，要靠錯誤監控排查。
