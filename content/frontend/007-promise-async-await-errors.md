# 題目

`async/await` 的錯誤要怎麼處理才不會漏？`Promise.all` 中有一個失敗會怎麼樣？

## 核心答案

`async` 函式的錯誤處理有兩種形式：**函式內用 `try/catch`**，或**呼叫端用 `.catch`**。關鍵認知是 **`async` 函式永遠回傳 Promise**，所以裡面拋出的錯誤會變成**被拒絕的 Promise**，而不是同步的例外——這代表**外層的同步 `try/catch` 抓不到它**，必須 `await` 或接 `.catch`。最常漏掉的是**沒有被 await 的 async 呼叫**（例如在 `forEach` 裡呼叫 async 函式），它的拒絕沒有人處理，變成未捕捉的 Promise 拒絕。至於 `Promise.all`：只要有一個拒絕，整體立刻拒絕，而且**其他 Promise 不會被取消**（它們仍在執行，只是結果被丟棄）。需要「全部都跑完並拿到各自的成功或失敗」時要用 **`Promise.allSettled`**；需要「任何一個成功就好」用 **`Promise.any`**；需要「最快有結果的那個，不管成功失敗」用 **`Promise.race`**。

## 詳細解析

**try/catch 的涵蓋範圍**：`try { await fn() } catch(e) {}` 能抓到 `fn` 回傳的 Promise 被拒絕的情況，也能抓到 `fn` 同步拋出的錯誤。但如果寫成 `try { fn() } catch(e) {}`（沒有 `await`），拒絕就抓不到——因為 `try` 區塊在 Promise 完成之前就結束了。這個「**少寫一個 await 導致錯誤逃逸**」是最常見的實務問題，多數 lint 規則都有對應的檢查。

**迴圈中的非同步處理**：`forEach` **不會等待** async 回呼，所以在 `forEach` 裡用 `await` 完全無效——迴圈會立刻跑完，所有的 Promise 都沒有被等待。要循序執行用 `for...of` 配 `await`；要並行執行用 `map` 產生 Promise 陣列再 `Promise.all`。選擇的判準是**任務之間有沒有依賴**與**要不要控制並行數**——大量並行請求可能打爆對方的服務或觸發速率限制，這時需要分批或用並行限制。

**未捕捉的拒絕會怎樣**：瀏覽器會觸發 `unhandledrejection` 事件並在主控台印出警告；Node.js 在較新的版本會**直接終止行程**。所以在正式服務中一定要有全域的處理器記錄這類錯誤，但那是最後防線而不是正常的處理方式。

**錯誤要在哪一層處理**：原則是**在能做出決定的那一層處理**。底層的資料存取函式通常應該讓錯誤往上拋（或轉換成有意義的錯誤型別），因為它不知道要重試、要顯示什麼訊息、還是要靜默失敗；UI 層才知道該怎麼呈現。中間層盲目 `catch` 然後回傳 `null` 是常見的反模式——它讓錯誤消失，上層無法區分「沒有資料」與「請求失敗」。

**finally 與資源清理**：`try/catch/finally` 中的 `finally` 無論成功或失敗都會執行，適合用來收起載入狀態、關閉連線。Promise 也有對應的 `.finally`。要注意 `finally` 裡如果拋出錯誤會**覆蓋原本的錯誤**，所以清理邏輯本身要盡量不會失敗。

## 面試回答方式

先講最關鍵的認知——`async` 函式永遠回傳 Promise，所以裡面的錯誤是拒絕而不是同步例外，外層的同步 `try/catch` 抓不到。接著點出最常見的漏接：少寫一個 `await`、以及在 `forEach` 裡用 async 回呼（它不會等待）。`Promise.all` 的部分要講兩件事：**一個失敗就整體失敗**、以及**其他 Promise 不會被取消仍在執行**，然後給出 `allSettled`、`any`、`race` 各自的適用場景。加分點是講**錯誤該在哪一層處理**——在能做決定的那一層，並批評中間層 catch 之後回傳 null 這個反模式，因為它讓上層分不出「沒資料」和「失敗」。

## 講稿

最關鍵的一件事是，async 函式永遠回傳 Promise。所以裡面拋出的錯誤會變成被拒絕的 Promise，不是同步的例外。這代表外層用同步的 try catch 是抓不到的，一定要 await 或者接 catch。

最常漏掉的就是少寫一個 await。try 裡面呼叫了 async 函式但沒有 await，try 區塊在 Promise 完成前就結束，錯誤就逃掉了。

另一個是在 forEach 裡用 async 回呼。forEach 不會等待，裡面的 await 完全沒有效果。要循序執行我會用 for of 配 await，要並行就用 map 產生 Promise 陣列再交給 Promise.all。

Promise.all 有兩件事要注意。只要有一個拒絕，整體立刻拒絕。而且其他的 Promise 不會被取消，它們還在跑，只是結果被丟掉。

所以我依需求選。要全部跑完各自拿結果用 allSettled，任何一個成功就好用 any，要最快有結果的那個用 race。

還有一個原則，錯誤要在能做決定的那一層處理。底層應該讓錯誤往上拋，中間層抓到就回傳 null 是很糟的做法，上層會分不出沒資料跟失敗。

## 常見追問

### 要怎麼限制並行的請求數量？

**核心答案**：**分批**或**用並行池**。分批最簡單——把任務切成每組 N 個，用 `for...of` 逐組 `await Promise.all(batch)`，缺點是每一批要等最慢的那個完成才進入下一批。並行池更有效率：維持 N 個正在執行的任務，任何一個完成就立刻補上下一個，可以用一個索引配合 N 個工作者迴圈實作，或直接用成熟的函式庫。

**詳細解析**：需要限制並行的原因有三個：**對方的速率限制**（超過會被拒絕或封鎖）、**自己的資源限制**（瀏覽器對同一網域的並行連線數本來就有上限，超過只是排隊）、以及**避免瞬間打爆下游服務**。實務上還要搭配**重試與退避**——失敗後等待逐漸增加的時間再重試，並加上隨機抖動避免所有客戶端同時重試造成尖峰。另外要注意**取消機制**：如果使用者離開頁面或切換了篩選條件，未完成的請求應該用 `AbortController` 取消，否則會浪費頻寬並可能用過期的回應覆蓋新的資料。

**面試回答方式**：給出分批與並行池兩種做法並比較效率差異。說明需要限流的三個原因。加分點是延伸到重試退避加抖動、以及用 `AbortController` 取消過期請求避免舊回應覆蓋新資料。

### await 會不會阻塞主執行緒？

**核心答案**：**不會**。`await` 只是暫停**當前這個 async 函式**的執行，把控制權交回給 Event Loop，主執行緒可以繼續處理其他任務——包括渲染、事件回呼、其他的非同步流程。真正會阻塞主執行緒的是**同步的長運算**，不是 `await`。這是常見的誤解，因為 `await` 的寫法看起來像同步程式碼。

**詳細解析**：不過有一個實務上的效能陷阱：**不必要的循序 await**。如果兩個請求彼此獨立，寫成 `const a = await fetchA(); const b = await fetchB();` 會讓總時間變成兩者相加；正確做法是 `const [a, b] = await Promise.all([fetchA(), fetchB()])`，總時間是較慢的那一個。這不是阻塞問題而是**沒有善用並行**。判斷方式很簡單：後面的請求有沒有用到前面的結果，沒有就該並行。這個檢查在瀑布式請求（元件層層等待資料）造成的載入緩慢中特別重要。

**面試回答方式**：明確否認會阻塞，並解釋 `await` 只暫停當前函式、控制權交回 Event Loop。接著主動提出真正的陷阱——不必要的循序 await，並給出用 `Promise.all` 並行的做法與判準（後面有沒有用到前面的結果）。

### 為什麼 Promise.all 失敗時其他請求不會被取消？

**核心答案**：因為 **Promise 本身沒有取消機制**——它只是一個「最終會有結果」的容器，一旦開始執行就無法中止。`Promise.all` 只是在其中一個拒絕時**提早給出它自己的結果**，但它對其他 Promise 沒有任何控制權。要真正取消底層的操作（例如網路請求），必須用該操作提供的取消機制，也就是 `fetch` 搭配 **`AbortController`**。

**詳細解析**：這個設計是刻意的——Promise 被定位為「結果的代理」而非「任務的控制器」，取消屬於任務層級的責任。實務上的完整做法是：建立一個 `AbortController`，把它的 signal 傳給所有 `fetch`，在任何一個失敗時呼叫 `abort()` 取消其餘的。`AbortController` 現在也被許多其他 API 支援（事件監聽器、串流），成為標準的取消慣例。要注意被中止的 `fetch` 會以 `AbortError` 拒絕，處理時要區分它與真正的錯誤——因為使用者主動取消不該顯示錯誤訊息，這是實務上容易忽略的細節。

**面試回答方式**：核心是 Promise 是結果的代理而非任務的控制器，沒有取消能力。接著給正確做法——用 `AbortController` 並在失敗時 abort 其餘請求。加分點是提到 `AbortController` 已是跨 API 的標準慣例，以及要區分 `AbortError` 與真正的錯誤，避免對使用者顯示不該有的錯誤訊息。
