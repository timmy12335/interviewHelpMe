# 題目

微前端解決什麼問題？它的代價是什麼？

## 核心答案

它解決的是「組織問題」而非技術問題——當多個團隊要在同一個前端應用上獨立開發與部署時，單一的程式碼庫會讓他們互相阻塞（共用的建置、共同的發布時程、以及一個團隊的錯誤影響全部）。

**它的代價相當高**：共用相依的重複載入或版本衝突（兩個微前端各帶一份 React）、**跨應用的狀態與路由協調**、**樣式的隔離**、**整體的效能下降**（更多的請求與更大的總體積）、**以及除錯的困難**（問題可能跨越多個獨立部署的部分）。

判斷是否值得的核心問題是「你的團隊真的被彼此阻塞嗎」——如果只有兩三個團隊而發布並不頻繁，那 monorepo 加上清楚的模組邊界通常是更好的答案；微前端的複雜度只有在「多團隊、獨立發布節奏、且技術棧可能不同」時才划算。

最常見的失敗模式是「為了技術新鮮感導入，結果得到了分散式單體」——各部分仍然緊密耦合、必須一起發布，卻承擔了所有分散的成本。

## 詳細解析

「模組聯邦讓共用相依成為可能但也是複雜度的來源」：它允許在執行期共享模組（例如所有微前端共用同一份 React）——但需要版本協商，而不相容的版本會在執行期才爆炸；而「singleton」的設定錯誤會造成兩份 React 同時存在，於是 hooks 直接失效。這類錯誤的訊息通常很難懂，而它們只在整合後才出現。

**「路由的所有權需要明確定義」**：容器應用負責頂層的路由分發——而每個微前端在自己的路徑前綴下有完整的控制；沒有這個約定的話，兩個微前端可能互相搶奪同一個路徑或者干擾彼此的歷史記錄。

「共用的部分應該是契約而非程式碼」：如果所有微前端都依賴同一個共用的元件庫，並且需要同步升級——那你已經失去了獨立部署的能力；更可行的做法是共用設計 token（純 CSS 變數）與少數穩定的介面，而各自實作。這犧牲了一些一致性換取獨立性，而那個交換正是微前端的核心取捨。

**「先做垂直切分而非水平」**：按功能領域切（訂單、商品、帳戶各是一個微前端）比按層次切（一個負責頁首、一個負責內容）好得多——因為前者的邊界對應到團隊的職責，而後者會讓每個功能的變更都跨越多個部分；這正好對應了微服務中「按業務能力切分」的原則。

## 面試回答方式

先指出它解決的是組織問題而非技術問題並說明是什麼組織問題，再列出五項代價與判斷的核心問題。加分點有四個：**模組聯邦的版本協商問題**——singleton 設定錯誤會讓兩份 React 同時存在而 hooks 直接失效；**路由的所有權需要明確定義**；共用的部分應該是契約而非程式碼，否則已經失去獨立部署的能力；以及**先做垂直切分而非水平**。最後點出最常見的失敗模式是分散式單體。

## 講稿

它解決的是組織問題而不是技術問題。當多個團隊要在同一個前端應用上獨立開發跟部署時，單一程式碼庫會讓他們互相阻塞。

但代價相當高。共用相依會重複載入或版本衝突，兩個微前端各帶一份 React。還有跨應用的狀態跟路由協調、樣式隔離、整體效能下降、以及除錯困難，因為問題可能跨越多個獨立部署的部分。

所以我的判斷是先問一句，你的團隊真的被彼此阻塞嗎。如果只有兩三個團隊而發布也不頻繁，那 monorepo 加上清楚的模組邊界通常是更好的答案。

我看過最常見的失敗模式是為了技術新鮮感導入，結果得到一個分散式單體。各部分仍然緊密耦合、必須一起發布，卻承擔了所有分散的成本。

還有一點很關鍵，共用的部分應該是契約而不是程式碼。如果所有微前端都依賴同一個元件庫而且需要同步升級，那你已經失去了獨立部署的能力。共用設計 token 而各自實作，是比較可行的做法。

## 常見追問

### iframe 是不是更簡單的方案？

**核心答案**：**隔離最徹底但整合體驗最差**。iframe 提供了完整的 JavaScript、CSS 與 DOM 隔離——這解決了樣式衝突與全域污染的所有問題；但代價是路由與歷史記錄難以同步、彈窗無法超出邊界、尺寸需要手動協調、無障礙與鍵盤焦點跨框架不順、以及每個 iframe 都是一個完整的文件（記憶體與載入成本高）。

**詳細解析**：**「它適合的場景很明確」**：整合完全不受你控制的第三方應用、或者需要強安全隔離的內容（例如使用者提供的程式碼預覽）——**這時 iframe 的隔離正是你要的**；而如果目標是「讓多個團隊的介面看起來像同一個產品」，那 iframe 幾乎一定會在體驗上留下明顯的接縫。**而現代的替代是 Web Components 加上 Shadow DOM**——它提供了樣式隔離而保留在同一個文件中；代價是 JavaScript 仍然共用全域環境，而 Shadow DOM 的樣式穿透與表單整合有各自的複雜度。選擇的依據是「你需要的隔離是為了防止意外還是為了防止惡意」——**前者用 Shadow DOM 就夠，後者才需要 iframe**。

**面試回答方式**：說明 iframe 的隔離優勢與五項體驗代價。核心加分點是**它適合的場景很明確**（不受控的第三方、需要強安全隔離的內容）並指出用它做產品整合會留下明顯接縫。收在判斷依據：你需要的隔離是為了防止意外還是防止惡意——**前者用 Shadow DOM 就夠，後者才需要 iframe**。

### monorepo 和微前端的關係是什麼？

**核心答案**：它們解決不同的問題，而且可以組合。monorepo 是程式碼的組織方式（所有專案在同一個儲存庫）——微前端是執行期的組合方式（各部分獨立部署並在瀏覽器中組裝）；一個 monorepo 可以產出多個獨立部署的微前端，也可以只產出一個單體應用。

**詳細解析**：「多數團隊真正需要的是 monorepo 而非微前端」：因為痛點通常是「共用程式碼難以管理」與「跨專案的變更要開好幾個 PR」——**而這些正是 monorepo 解決的**；而「獨立部署」的需求往往被高估（多數團隊實際上是每天或每週發布，並不需要每個團隊各自的發布節奏）。所以正確的順序是「先用 monorepo 加上模組邊界與建置快取，遇到真正的部署阻塞時再考慮微前端」——**而不是反過來**。在面試中能給出這個順序判斷，比列舉微前端的技術方案更有價值；因為架構決策最常見的錯誤不是選錯方案，而是解決了一個還不存在的問題。

**面試回答方式**：給清楚的區分（**程式碼的組織 vs 執行期的組合**）並指出它們可以組合。核心加分點是多數團隊真正需要的是 monorepo 而非微前端——痛點通常是共用程式碼與跨專案變更，而「獨立部署」的需求往往被高估。收在順序判斷：先用 monorepo 加模組邊界，遇到真正的部署阻塞再考慮微前端；因為架構決策最常見的錯誤是解決了一個還不存在的問題。

### 如果已經導入了微前端但很痛苦，怎麼收回來？

**核心答案**：**漸進地合併而非一次重寫**。可行的路徑是：先把最緊密耦合的幾個部分合併回一個（那些本來就必須一起發布的）、把共用的相依統一到同一個版本、**再逐步把剩下的併入**；而在過程中保持每一步都可上線，是避免變成一個長期分支的關鍵。

**詳細解析**：「先解決痛點而非追求架構的純粹」：如果最大的痛苦是「版本衝突」——那統一相依版本可能就解決了八成的問題，而不需要真的合併；如果最大的痛苦是「除錯跨越多個部分」，那改善可觀測性（統一的追蹤 ID、集中的錯誤收集）可能比架構調整更快見效。先明確列出「具體哪些事情很痛」並逐項評估最小的解法，比宣告「我們要回到單體」有效得多——因為後者是一個大專案，而大專案在有其他優先事項時很容易被擱置。這個「把架構問題拆成一組具體的痛點」的做法，也讓你更容易獲得投入的許可。

**面試回答方式**：給漸進的路徑並強調**保持每一步都可上線**。核心加分點是先解決痛點而非追求架構的純粹——版本衝突可能統一版本就解決八成，除錯困難可能改善可觀測性更快見效。收在策略：把架構問題拆成一組具體的痛點並逐項評估最小的解法，比宣告「我們要回到單體」有效，也更容易獲得投入的許可。
