# 題目

為什麼 `setInterval` 裡的回呼永遠讀到初始的 state？依賴陣列該怎麼處理才對？

## 核心答案

根因是每次渲染都會產生一組新的函式，而每組函式捕獲的是那一次渲染的 props 與 state。`setInterval` 若只在掛載時設定一次（依賴陣列為空），它的回呼就永遠是第一次渲染時建立的那個閉包，裡面的 state 永遠是初始值。這不是 React 的 bug，而是閉包如實地保留了當時的環境。三種正確解法各有適用場景：**一、把依賴填齊**，讓 effect 在值變更時重新建立（計時器會被清除並重設，語意上可能不是你要的）。**二、用函式形式更新**（`setCount(c => c + 1)`），完全不需要讀取當前值，這對計數器類的場景最乾淨。**三、用 `useRef` 保存最新值**——ref 的參照跨渲染穩定但內容可變，在 effect 中透過 ref 讀取就永遠是最新的。判斷準則是：能用函式形式就用它，需要讀取多個最新值時用 ref，語意上真的該重建時才填依賴。

## 詳細解析

**「快照」是理解 hooks 的核心心智模型**：每次渲染都是一次獨立的快照——那次的 props、state、以及基於它們建立的所有函式，構成一個封閉的世界。事件處理器讀到的是點擊當下那次渲染的值；`setTimeout` 回呼讀到的是設定時那次的值。用這個模型可以統一解釋所有「讀到舊值」的現象，不必逐一背誦。

**依賴陣列不是效能優化開關**：很多人把它當成「填少一點可以少執行幾次」的調節鈕，這是誤解。它的正確語意是「**這個 effect 依賴哪些值**」，填錯就是宣告了錯誤的依賴關係，行為自然不對。lint 規則應該開啟並遵守；當它提示要加某個依賴而你覺得不該加時，通常代表**設計需要調整**（該用 ref、該用函式形式、或這件事根本不該用 effect），而不是該把 lint 關掉。

**useRef 的兩種用途要分清**：一是**存取 DOM 節點**，二是保存跨渲染的可變值且不觸發重新渲染。第二種用途正是解決閉包陷阱的工具——把最新的 state 同步到 ref（在每次渲染時或在一個 effect 中賦值），需要時從 ref 讀取。要注意在渲染過程中讀寫 ref 是不安全的（違反純渲染的要求，並在並行特性下可能出問題），賦值應該放在 effect 中。

**自訂 hook 是最好的封裝方式**：像「最新值的 ref」「可變間隔的計時器」這類模式應該封裝成自訂 hook，一次寫對之後到處重用，避免每個使用處都要重新推理閉包行為。這也是 hooks 設計的核心價值——**把有狀態的邏輯抽出來重用**，而不是像高階元件那樣包裝元件層級。

**清理函式的重要性**：effect 回傳的清理函式在**每次重新執行前**與**元件卸載時**都會被呼叫。忘記清理計時器、事件監聽器、訂閱、或未完成的請求，會造成記憶體洩漏與「對已卸載元件操作」的警告。在依賴會變的 effect 中尤其關鍵——每次重新執行都會建立新的訂閱，沒清理的話會累積。

## 面試回答方式

先給根因並用「**快照**」這個心智模型講清楚——每次渲染產生一組新函式，各自捕獲那次的值，這一句能統一解釋所有讀到舊值的現象。接著給**三種解法與各自的適用場景**，並明確表態優先順序：能用函式形式就用它、要讀多個最新值用 ref、語意上真的該重建才填依賴。主動糾正一個常見誤解：**依賴陣列不是效能開關**，填少一點不是優化而是宣告了錯誤的依賴。加分點有三個：`useRef` 的賦值應該放在 effect 中而非渲染過程；把這類模式封裝成自訂 hook；以及清理函式在每次重新執行前也會被呼叫，訂閱類的 effect 沒清理會累積。

## 講稿

根因是每次渲染都會產生一組新的函式，而每組函式捕獲的是那一次渲染的 props 跟 state。

所以如果 setInterval 只在掛載的時候設一次，它的回呼就永遠是第一次渲染建立的那個閉包，裡面的 state 永遠是初始值。這不是 React 的 bug，是閉包如實保留了當時的環境。

我覺得最好用的心智模型是快照。每次渲染都是一次獨立的快照，那次的 props、state、還有基於它們建立的所有函式，構成一個封閉的世界。事件處理器讀到的是點擊當下那次的值，setTimeout 讀到的是設定時那次的值，用這個模型可以統一解釋。

解法有三種。第一是把依賴填齊，讓 effect 在值變的時候重新建立，但計時器會被清掉重設，語意上不一定是我要的。第二是用函式形式更新，完全不需要讀當前值，計數器這種最乾淨。第三是用 useRef 保存最新值，ref 的參照跨渲染穩定但內容可變。

我的優先順序是能用函式形式就用，要讀多個最新值才用 ref。

## 常見追問

### useRef 和 useState 該怎麼選？

**核心答案**：問一句話——這個值改變時畫面需不需要更新。需要就用 `useState`（它會觸發重新渲染），不需要就用 `useRef`（改變它不會引起任何渲染）。典型的 ref 用途包括：保存計時器 ID、記錄前一次的值、存放 DOM 節點、以及任何「邏輯上需要但不影響畫面」的可變資料。

**詳細解析**：常見的誤用是用 `useState` 存放不影響畫面的東西（例如捲動位置的中間值），導致每次變動都重新渲染整棵子樹。反過來也有誤用 `useRef` 存放應該影響畫面的值，結果資料變了但畫面不更新——因為 ref 的改變不會通知 React。還有一個中間情況值得知道：需要在渲染中讀取但不想觸發渲染的值，正確做法通常是重新思考資料流，而不是硬用 ref——在渲染中讀 ref 會讓渲染變得不純，在並行特性下可能產生不一致的畫面。這個「純渲染」的要求是 React 並行能力的前提，值得主動提及。

**面試回答方式**：給出「值改變時畫面需不需要更新」這個一句話判準，並列出典型的 ref 用途。接著給兩個方向的誤用各一個例子。加分點是指出在渲染中讀 ref 會破壞純渲染、影響並行特性，說明這是判斷的底線而非風格偏好。

### 什麼時候該用 useCallback？

**核心答案**：當這個函式會成為別人的依賴時——傳給 `memo` 過的子元件當 props、或出現在另一個 hook 的依賴陣列中。這兩種情況下，函式參照每次渲染都變會讓 `memo` 失效或讓 effect 反覆執行。除此之外，單純為了「避免每次建立新函式」而用 `useCallback` 通常是淨損失，因為它本身也有比較依賴與佔用記憶體的成本。

**詳細解析**：實務上 `useCallback` 常常**用了也沒效果**——因為它自己的依賴每次都在變，或者接收它的子元件根本沒有 `memo`。所以使用前應該確認整條鏈都成立：函式穩定、子元件有記憶化、其他 props 也穩定。這條鏈很容易斷，維護成本高，這也是為什麼結構性解法（狀態下移、children 傳入）通常更值得優先考慮。另外值得知道的是 React 的編譯器方向——讓編譯器自動插入這些記憶化，開發者不必手動處理。理解「手動記憶化是當前的權宜之計」這個脈絡，比熟練地到處加 `useCallback` 更符合現況。

**面試回答方式**：給出明確的使用條件（成為別人的依賴時），並說明其他情況通常是淨損失。重點指出它常常用了沒效果，因為整條鏈很容易斷。加分點是提到 React 編譯器自動記憶化的方向，把手動記憶化定位為當前的權宜之計。

### 自訂 hook 有什麼設計原則？

**核心答案**：三個原則。一、只封裝有狀態的邏輯，不封裝畫面——回傳資料與操作函式，讓使用它的元件決定怎麼呈現。**二、命名以 `use` 開頭**，這不只是慣例，lint 規則依賴它判斷 hooks 的呼叫規則。**三、回傳的介面要穩定**——回傳物件時注意參照穩定性（否則使用它的元件的依賴陣列會一直變），回傳函式時用 `useCallback` 或用函式形式的更新避免依賴。

**詳細解析**：好的自訂 hook 應該像一個**獨立的功能單元**：明確的輸入、明確的輸出、內部管理自己的副作用與清理。判斷抽取時機的準則是同樣的有狀態邏輯出現第二次——第一次不急著抽，因為還看不出正確的抽象邊界。要避免的是**過度抽象**：把太多不相關的功能塞進一個 hook，導致使用者被迫接受不需要的行為與重新渲染。另外要注意 hooks 的呼叫必須是**無條件且順序固定**的，所以自訂 hook 內部不能有條件式的 hook 呼叫——這個限制來自 React 用呼叫順序來對應狀態的實作方式，理解原因比記住規則更能避免踩雷。

**面試回答方式**：給三個設計原則並解釋各自的理由，特別是回傳介面的參照穩定性。接著給抽取時機的準則（出現第二次才抽）與過度抽象的風險。加分點是解釋 hooks 不能有條件呼叫的原因——React 用呼叫順序對應狀態，說明你理解機制而非背規則。
