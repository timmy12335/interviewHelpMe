# 題目

前端要不要做權限控制？它和後端的權限檢查是什麼關係？

## 核心答案

要做，但它的目的是體驗而非安全——不顯示使用者無權使用的按鈕，避免他點了才被拒絕；而真正的防護必須在後端的每一個端點上，因為任何人都能直接呼叫 API，完全不經過你的前端。

最常見也最嚴重的錯誤是「後端回傳完整資料，前端根據角色決定顯示什麼」——那等於把資料公開給任何會打開開發者工具的人；正確的做法是後端根據呼叫者的權限決定回傳什麼欄位、什麼筆數。

**前端該做的三層**：**路由層**（沒權限就不進入該頁面）、**元件層**（隱藏或禁用無權的操作）、**以及請求失敗時的處理**（收到 403 時要有合理的提示而非泛用的錯誤）。

**而權限資訊本身也要小心**：把角色寫在前端可讀的 token 中沒問題（那只是用來決定顯示），但絕對不能讓前端「宣稱」自己的角色再由後端信任它。

## 詳細解析

「隱藏與禁用的選擇有體驗上的差別」：完全隱藏會讓使用者不知道有這個功能存在——而禁用並附上原因（「此功能需要管理員權限」）讓他知道該去申請什麼；判斷的依據是「知道這個功能存在會不會造成問題」（例如洩漏組織結構或未發布的功能）。

**「前端的權限資料會過期」**：使用者的角色在他登入期間被改變了——而前端持有的是登入時的快照；於是他可能看到已經無權使用的按鈕（點了會失敗）或者看不到新獲得的功能。處理的方式是「在關鍵操作前重新確認」或者「用較短的 token 有效期」；而後端的檢查永遠是即時的，所以安全性不受影響。

「多租戶的資料隔離要在查詢層強制」：如果每個 API 都要記得加上「且 tenant_id 等於當前使用者的租戶」——那漏掉一次就是一次跨租戶的資料洩漏；正確的做法是在資料存取層強制注入這個條件（或者用資料庫的列級安全性），讓「忘記加」在結構上不可能發生。

「JWT 中放什麼」是一個常見的設計問題：放太多資訊會讓 token 變大且無法即時撤銷——而放太少則每次請求都要查資料庫；常見的平衡是放使用者 ID 與少數穩定的角色，細粒度的權限在後端查詢並快取。

## 面試回答方式

先給明確的定位（**目的是體驗而非安全**）與理由，再點出**最常見也最嚴重的錯誤**：後端回傳完整資料由前端決定顯示。接著給前端該做的三層。加分點有四個：**隱藏與禁用的選擇**及其判斷依據；**前端的權限資料會過期**與處理方式；多租戶的資料隔離要在查詢層強制，讓「忘記加」在結構上不可能發生；以及 **JWT 中放什麼**的權衡。

## 講稿

要做，但它的目的是體驗不是安全。不顯示使用者無權使用的按鈕，避免他點了才被拒絕。真正的防護必須在後端的每一個端點上，因為任何人都能直接呼叫 API，完全不經過前端。

而我看過最嚴重的錯誤是後端回傳完整資料，前端根據角色決定顯示什麼。那等於把資料公開給任何會打開開發者工具的人。正確的做法是後端根據呼叫者的權限決定回傳什麼。

前端我會做三層。路由層不讓進入、元件層隱藏或禁用、還有收到 403 時要有合理的提示。

隱藏跟禁用我會分情況。完全隱藏會讓使用者不知道有這個功能，禁用並說明原因讓他知道該去申請什麼。判斷依據是知道這個功能存在會不會造成問題。

另外多租戶的隔離要在查詢層強制。如果每個 API 都要記得加租戶條件，漏一次就是一次資料洩漏。應該在資料存取層強制注入，讓忘記加在結構上不可能發生。

## 常見追問

### token 該存在哪裡？

**核心答案**：存取權杖放在記憶體、更新權杖放在 HttpOnly 的 Cookie，是目前較被接受的組合。放在 `localStorage` 的 token 能被任何 XSS 讀取——**而 HttpOnly 的 Cookie JavaScript 讀不到**；**但 Cookie 需要防範 CSRF（用 SameSite 屬性加上 CSRF token）**。兩種方案各有攻擊面，沒有絕對安全的選擇。

**詳細解析**：**「如果有 XSS，多數防護都會失效」**：即使 token 在 HttpOnly 的 Cookie 中——攻擊者仍然可以用受害者的瀏覽器發出帶著 Cookie 的請求（他不需要讀到 token，只需要用它）；所以「token 存哪裡」的討論，實際上是在降低損害而非消除風險。**真正的重點應該放在「不要有 XSS」**：嚴格的內容安全政策、對所有插入的 HTML 做消毒、以及避免 `dangerouslySetInnerHTML` 這類逃生口。在面試中能指出「這個問題的前提是已經被 XSS，而那時我們已經輸了大半」，展示的是對威脅模型的理解而非只記得幾條建議。

**面試回答方式**：給目前較被接受的組合並說明各自的攻擊面（localStorage 怕 XSS、Cookie 怕 CSRF）。核心加分點是指出**如果有 XSS，多數防護都會失效**——攻擊者不需要讀到 token，只需要用受害者的瀏覽器發請求。收在重點轉移：**真正的重點是不要有 XSS**（CSP、消毒、避免逃生口），而能指出「這個問題的前提是已經被 XSS」展示的是對威脅模型的理解。

### 前端該怎麼處理 token 過期？

**核心答案**：用攔截器在收到 401 時自動嘗試更新並重試原請求。要處理的細節有三個：多個請求同時遇到過期時只更新一次（否則會發出多個更新請求且可能互相作廢）、更新失敗時導向登入並保留原本要去的頁面、以及避免更新請求本身也觸發攔截器造成無限迴圈。

**詳細解析**：「並行請求的去重是最容易出錯的部分」：頁面同時發出五個請求而 token 剛好過期——如果每個都各自去更新，可能造成更新權杖被輪替五次而其中四次失效；正確的做法是「第一個發起更新，其餘的等待同一個 Promise」。這個模式在多數 HTTP 客戶端的攔截器範例中都有，但自己實作時很容易漏掉。而另一個常被忽略的是「使用者體驗上的無縫」——更新與重試應該對使用者完全不可見，如果過程中閃過登入頁或者顯示錯誤，那就失去了自動更新的意義；驗證的方法是刻意把 token 的有效期設得很短，然後正常使用一段時間看看有沒有異常。

**面試回答方式**：給做法（**攔截器在 401 時自動更新並重試**）與三個細節。核心加分點是並行請求的去重是最容易出錯的部分——每個各自更新可能讓更新權杖被輪替多次而失效，並給出正確的模式。收在驗證方法：刻意把有效期設得很短然後正常使用一段時間，因為更新與重試應該對使用者完全不可見。

### 功能開關和權限控制有什麼不同？

**核心答案**：權限是「這個人能不能做」，功能開關是「這個功能現在開不開」——兩者常常在程式碼中長得很像但目的不同；混在一起管理會讓兩邊都難以推理。權限的來源是使用者的角色，功能開關的來源是發布策略、實驗分組或者營運決定。

**詳細解析**：「功能開關也不該只在前端判斷」：如果一個未發布的功能只是在前端隱藏——它的程式碼仍然在打包產物中，而對應的 API 可能已經可用；於是有心人能提前發現甚至使用它（這在上市前的產品中曾造成過真實的洩漏）。所以真正未發布的功能應該在後端也關閉，或者連程式碼都不部署。而功能開關的另一個常被忽略的成本是「清理」——每個開關都是一個分支，累積下來會讓程式碼路徑爆炸；所以應該在建立時就記下移除的條件與負責人，而定期清理已經全開或全關的開關，是維護健康的必要工作。

**面試回答方式**：給清楚的區分（**能不能做 vs 現在開不開**）與各自的來源，並指出混在一起會讓兩邊都難以推理。核心加分點是功能開關也不該只在前端判斷——程式碼仍在產物中而 API 可能已可用，這曾造成真實的上市前洩漏。收在成本：每個開關都是一個分支，累積下來讓路徑爆炸，所以建立時就該記下移除的條件與負責人。
