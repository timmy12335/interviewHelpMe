# 題目

事件的傳播機制是什麼？事件委派解決什麼問題？React 的合成事件有什麼不同？

## 核心答案

**傳播分三階段**：**捕獲**（從 window 往下到目標）、**目標**、**冒泡**（從目標往上到 window）。`addEventListener` 的第三個參數決定監聽在哪個階段（預設 false 是冒泡）；而 `stopPropagation` 停止繼續傳播、`preventDefault` 取消瀏覽器的預設行為，兩者是不同的事情。

**事件委派**是把監聽器放在共同的祖先上，用 `event.target` 判斷實際被點的是誰——好處是動態新增的子元素不需要重新綁定、記憶體佔用少、以及在大量元素時效能明顯較好；**這在長列表中特別有價值。**

**React 的合成事件**：**它在根容器上做委派**（React 17 之前是掛在 document 上，之後改為掛在 React 樹的根節點）——於是所有的 onClick 其實共用少數幾個真實的監聽器；而合成事件包裝了原生事件以抹平瀏覽器差異，並提供一致的介面。

最常見的坑是「原生事件與 React 事件的執行順序」——因為 React 的處理器在根節點觸發，所以一個掛在子元素上的原生監聽器會先執行；在混用第三方函式庫時這會造成困惑。

## 詳細解析

「有些事件不冒泡」是委派時的陷阱：`focus`、`blur`、`mouseenter`、`mouseleave` 不冒泡——**所以無法直接委派**；替代方案是用會冒泡的對應事件（`focusin`/`focusout`、`mouseover`/`mouseout`）或者在捕獲階段監聽。這一點在實作「點擊外部關閉」或者焦點追蹤時常常踩到。

「`stopPropagation` 的副作用比想像的大」：它會讓所有依賴事件冒泡的機制失效——包括其他元件的「點擊外部關閉」、分析工具的點擊追蹤、以及框架自己的委派；所以應該優先考慮「在處理器中判斷 target 是否相關」而非阻止傳播。這是一個「局部的方便造成全域的問題」的典型例子。

**「被動監聽器改善捲動效能」**：`{ passive: true }` 告訴瀏覽器「這個處理器不會呼叫 `preventDefault`」——於是瀏覽器不需要等待它執行完才開始捲動；現代瀏覽器對 `touchstart` 與 `wheel` 預設就是被動的，而如果真的需要阻止預設行為，必須明確設為 `passive: false`。

「事件的清理」是記憶體洩漏的常見來源：忘記移除監聽器，而處理器閉包捕獲了大物件——**那個物件就無法被回收**；在框架中這對應到 effect 的清理函式，而 `AbortController` 提供了一個乾淨的批次移除方式（一個 signal 傳給多個 `addEventListener`，abort 一次全部移除）。

## 面試回答方式

先給三階段與兩個方法的區分，再說明事件委派的好處與 React 合成事件的機制，並點出**原生事件與 React 事件的執行順序**這個常見的坑。加分點有四個：**有些事件不冒泡**與替代方案；**`stopPropagation` 的副作用比想像的大**——它是「局部方便造成全域問題」的典型；**被動監聽器改善捲動效能**；以及**事件的清理與 `AbortController` 的批次移除**。

## 講稿

傳播分三階段，捕獲、目標、冒泡。addEventListener 的第三個參數決定監聽在哪一階段。而 stopPropagation 停止繼續傳播，preventDefault 取消預設行為，這是兩件不同的事。

事件委派是把監聽器放在共同的祖先上，用 target 判斷實際被點的是誰。好處是動態新增的子元素不用重新綁定，記憶體也省。

React 的合成事件本身就是在根容器上做委派，所有的 onClick 共用少數幾個真實監聽器。這裡有一個常見的坑，掛在子元素上的原生監聽器會先於 React 的處理器執行，因為 React 的是在根節點觸發的。混用第三方函式庫時這會造成困惑。

還有兩件事我覺得值得注意。第一是有些事件不冒泡，像 focus、blur、mouseenter，所以沒辦法直接委派，要用對應的會冒泡的版本。

第二是 stopPropagation 的副作用比想像的大。它會讓其他元件的點擊外部關閉、分析工具的追蹤都失效。所以我會優先在處理器裡判斷 target，而不是阻止傳播。

## 常見追問

### 「點擊外部關閉」怎麼實作才可靠？

**核心答案**：在 document 上監聽，並判斷事件的目標是否在元件內部。要注意的細節包括：用 `mousedown` 而非 `click`（避免在按下時內容變化導致 click 沒有觸發）、處理 Portal 渲染的內容（它在 DOM 上不在元件內部，需要額外判斷）、以及同時支援 Escape 鍵關閉。

**詳細解析**：「多層彈窗的關閉順序」是這個功能最容易出錯的地方：一個對話框裡開了一個下拉選單——點擊外部應該只關掉下拉而不是連對話框一起關；如果每個元件都獨立監聽 document，它們會同時觸發。解法是維護一個「當前開啟的浮層堆疊」，只讓最上層的回應；這正是無頭元件庫做的事情之一。而這也解釋了為什麼「自己寫一個下拉選單」看起來簡單但實際上有很多邊界情況——焦點陷阱、捲動鎖定、多層堆疊、以及行動裝置上的觸控行為，每一項都不難但加起來的複雜度很可觀；這是「用成熟函式庫」在這類元件上通常是正確選擇的原因。

**面試回答方式**：給實作方式與三個細節（`mousedown`、Portal、Escape）。核心加分點是**多層彈窗的關閉順序**這個最容易出錯的地方與它的解法（維護一個浮層堆疊，只讓最上層回應）。收在判斷：焦點陷阱、捲動鎖定、多層堆疊、觸控行為每一項都不難但加起來複雜度可觀——這是「用成熟函式庫」通常是正確選擇的原因。

### 為什麼有時候 React 的事件處理器裡拿到的是舊的 state？

**核心答案**：因為閉包捕獲了那次渲染時的值。每次渲染產生新的函式，而綁定的處理器捕獲的是當時的 state——如果那個處理器是在一個空依賴的 effect 裡註冊的（例如原生 `addEventListener`），它會永遠拿到第一次渲染的值；解法是把 state 放進依賴並重新註冊，或者用 ref 保存最新值。

**詳細解析**：「這是閉包陷阱在事件監聽上的具體表現」：React 自己的 onClick 通常沒有這個問題——因為每次渲染都會用新的函式重新綁定；而手動 `addEventListener` 加上空依賴陣列，就會固定在第一次的閉包。**兩種解法各有適用**：重新註冊簡單直接但頻繁的話有開銷（每次值變都要移除再加）；用 ref 保存最新值（在每次渲染時更新 ref，處理器讀 ref）避免了重新註冊，代價是多一層間接。而 React 官方提出的 `useEffectEvent` 正是為了系統性地解決這個模式——它讓你在 effect 中讀到最新的值而不必把它列入依賴；理解這個問題的形狀，比記住某個解法更重要，因為它會以很多變體出現。

**面試回答方式**：給原因（**閉包捕獲了那次渲染的值**）並說明為什麼手動註冊的監聽器特別容易中招。核心加分點是對比**兩種解法的取捨**（重新註冊簡單但有開銷、ref 避免重註冊但多一層間接），並提到 **`useEffectEvent` 是為了系統性解決這個模式**。收在建議：理解這個問題的形狀比記住某個解法更重要，因為它會以很多變體出現。

### 自訂事件什麼時候有用？

**核心答案**：在需要跨越框架邊界或者解耦元件通訊時。`CustomEvent` 加上 `dispatchEvent` 讓任意的 DOM 節點都能發出事件——於是一個 Web Component 可以通知外面的 React 應用、或者兩個沒有共同父元件的部分可以通訊；而在同一個框架內部，用框架自己的機制（props、context、狀態管理）通常更清楚。

**詳細解析**：「用 DOM 事件做應用內的通訊是一種倒退」：它繞過了框架的資料流——於是資料的來源變得不可追蹤（誰發的、誰在聽，都要靠搜尋字串找）；而型別安全也完全失去（事件的 detail 是 any）。所以它應該被限制在真正的邊界上：微前端之間、Web Component 與宿主之間、或者與無法修改的第三方腳本互動時。而在那些場景中，它的價值是「不需要共享任何 JavaScript 模組或執行期」——兩邊只要同意事件的名稱與資料格式；這種「用平台的機制做整合」的做法，在跨技術棧的整合中比共享程式碼可靠得多。

**面試回答方式**：給適用場景（**跨越框架邊界、解耦通訊**）並指出框架內部用框架自己的機制更清楚。核心加分點是說明用 DOM 事件做應用內通訊是一種倒退——繞過資料流讓來源不可追蹤，型別安全也完全失去。收在真正的價值：在邊界上它不需要共享任何模組或執行期，兩邊只要同意事件名稱與格式——這種「用平台的機制做整合」在跨技術棧時比共享程式碼可靠。
