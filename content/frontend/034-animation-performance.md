# 題目

為什麼有些動畫很順、有些會卡？該怎麼選擇動畫的屬性？

## 核心答案

**關鍵在於「這個屬性的變化會觸發渲染流程的哪一階段」**。渲染分四步：**樣式計算、版面（layout）、繪製（paint）、合成（composite）**——**改動的屬性越晚進入流程，成本越低。**

**只觸發合成的屬性**（`transform`、`opacity`）——**可以完全在合成執行緒上處理，不佔用主執行緒**；**於是即使主執行緒忙碌，動畫仍然流暢**；**這是為什麼位移應該用 `transform: translate` 而非改 `left`。**

**觸發繪製的**（`background-color`、`box-shadow`、`border-radius`）——**需要重畫但不需要重算版面，成本中等。**

**觸發版面的**（`width`、`height`、`top`、`margin`、`font-size`）——**最貴，因為可能影響大量其他元素的位置**；**動畫這些屬性幾乎一定會掉幀。**

**而 `will-change` 能提前建立合成層，但不該濫用**——**每個合成層都佔用記憶體，過多的層反而讓效能變差。**

## 詳細解析

**「合成執行緒獨立於主執行緒」是流暢的關鍵**：如果動畫只涉及 `transform` 與 `opacity`——**即使主執行緒正在執行一段很重的 JavaScript，動畫也不會卡**；**而如果動畫需要主執行緒參與（例如用 JS 每幀改變 `left`），那主執行緒的任何阻塞都會讓動畫掉幀**。**這解釋了為什麼「CSS 動畫比 JS 動畫順」這個常見的說法在特定條件下成立而不是普遍真理**——**真正的差別在於是否需要主執行緒。**

**「Web Animations API 兼具兩者」**：它用 JavaScript 控制但動畫本身交給瀏覽器執行——**於是可以動態地建立與控制動畫，同時保有合成執行緒的優勢**；**這比用 `requestAnimationFrame` 手動每幀計算好得多**。

**「動畫進入與離開的差別」**：進入的動畫（元素出現）可以直接播放——**而離開的動畫需要延遲元素的移除，這在框架中需要額外的處理**（React 的 transition 群組、Vue 的 transition）；**忘記處理的話，元素會瞬間消失而動畫來不及播**。

**「尊重 `prefers-reduced-motion`」不只是無障礙的要求**：對某些使用者，視差捲動與大幅度的移動會引發不適甚至暈眩——**而正確的做法不是關掉所有動畫，而是用淡入淡出取代位移**；**保留了狀態變化的提示而去掉了引起不適的部分**。

## 面試回答方式

先給核心框架（**渲染的四階段，屬性越晚進入流程成本越低**）並分三類列出屬性。加分點有四個：**合成執行緒獨立於主執行緒**——**這解釋了「CSS 動畫比較順」在什麼條件下成立**；**Web Animations API 兼具動態控制與合成優勢**；**進入與離開的動畫需要不同的處理**；以及**尊重 `prefers-reduced-motion` 的正確做法是用淡入取代位移而非關掉所有動畫**。最後補上 **`will-change` 不該濫用**。

## 講稿

關鍵在於這個屬性的變化會觸發渲染流程的哪一階段。渲染分四步，樣式計算、版面、繪製、合成。改動的屬性越晚進入流程，成本越低。

只觸發合成的是 transform 跟 opacity，這兩個可以完全在合成執行緒上處理，不佔用主執行緒。所以位移應該用 transform 的位移而不是改 left。

觸發繪製的像背景色、陰影，需要重畫但不用重算版面，成本中等。觸發版面的像寬高、top、margin，最貴，因為可能影響大量其他元素的位置，動畫這些幾乎一定掉幀。

而合成執行緒獨立這件事，是流暢的關鍵。如果動畫只涉及那兩個屬性，即使主執行緒正在跑一段很重的 JavaScript，動畫也不會卡。這也解釋了為什麼 CSS 動畫比 JS 動畫順這個說法只在特定條件下成立。真正的差別是需不需要主執行緒。

另外 will-change 能提前建立合成層，但不該濫用。每個層都佔記憶體，太多反而更慢。

## 常見追問

### 長列表的捲動卡頓怎麼解決？

**核心答案**：**虛擬化（只渲染可見範圍內的項目）是根本的解法**。一萬筆資料全部渲染成 DOM，光是節點數就會讓每次的樣式計算與版面變得很慢——**而虛擬化把渲染的節點數固定在幾十個**；**代價是需要處理捲動位置、變高的項目、以及頁內搜尋失效等問題。**

**詳細解析**：**「不定高的項目是虛擬化最麻煩的部分」**：因為要計算捲動條的總高度與每個項目的位置——**而在測量之前你不知道它們多高**；**常見的做法是先用一個預估值，在項目實際渲染後測量並修正**，**而那個修正可能造成捲動位置的跳動**。**現代的函式庫（TanStack Virtual 等）處理了這些細節，所以自己實作通常不划算**。**而在決定用虛擬化之前，值得先確認幾件事**：**分頁或無限捲動是不是更適合的產品設計**（使用者真的需要一次看一萬筆嗎）、**以及 `content-visibility: auto` 是不是已經足夠**——**後者只要一行 CSS 且沒有虛擬化的副作用**；**先試簡單的方案，是這類效能問題的正確順序。**

**面試回答方式**：給根本解法（虛擬化）與它的代價。核心加分點是**不定高的項目是最麻煩的部分**與常見的處理（預估後測量修正、可能造成跳動），並指出現代函式庫已處理這些細節。收在順序：**先確認分頁或無限捲動是否更適合，以及 `content-visibility: auto` 是否已經足夠**——**先試簡單的方案是這類問題的正確順序**。

### 為什麼有時候動畫在開發機很順但在手機上很卡？

**核心答案**：**因為開發機的 CPU、GPU 與記憶體都遠優於中低階手機**。而具體的瓶頸可能不同：**合成層過多造成記憶體壓力**（手機的可用記憶體少得多）、**主執行緒被 JavaScript 佔滿**（手機的單核效能可能只有開發機的三分之一）、**或者過大的繪製區域**（高解析度螢幕上填滿整個畫面的模糊或漸層特別貴）。

**詳細解析**：**「用 CPU 降速與真實裝置測試是唯一可靠的方法」**：Chrome DevTools 的 4x 或 6x CPU 降速能模擬中低階裝置——**而效能面板的火焰圖能顯示每一幀的時間花在哪**；**尋找的是超過 16 毫秒的幀以及它們的成因**。**而 `backdrop-filter` 與大面積的 `box-shadow` 是行動裝置上特別常見的兇手**——**它們在每一幀都需要昂貴的繪製，而在高解析度螢幕上像素數是四倍**。**一個實用的檢查是「把那個效果暫時拿掉看看幀率有沒有改善」**——**這種二分法比猜測快得多**；**而如果確實是它，通常可以用一張預先算好的圖片或者更小的模糊半徑取代。**

**面試回答方式**：給根本原因（開發機硬體遠優於中低階手機）並列出三種可能的瓶頸。核心加分點是**用 CPU 降速與真實裝置測試**並說明在火焰圖中要找什麼，以及點名 **`backdrop-filter` 與大面積陰影是行動裝置上常見的兇手**。收在方法：**把效果暫時拿掉看幀率有沒有改善**——**這種二分法比猜測快得多**。

### 該用 CSS 動畫還是動畫函式庫？

**核心答案**：**簡單的狀態轉換用 CSS，複雜的編排用函式庫**。CSS 的 transition 與 animation 覆蓋了大部分的懸停、展開、淡入淡出——**而多元素的序列、基於物理的彈簧效果、以及需要中途打斷並平滑接續的動畫，用函式庫（Framer Motion、GSAP）會簡單很多。**

**詳細解析**：**「可中斷性是函式庫最大的價值之一」**：純 CSS 的動畫在中途改變目標時會有跳動——**而好的動畫函式庫會從當前的實際位置與速度平滑地過渡到新目標**；**這在互動密集的介面中差別非常明顯**（例如快速地反覆懸停一個元素）。**而彈簧模型的動畫之所以感覺自然，正是因為它用速度而非時間定義過渡**——**於是被打斷時能保持動量**。**代價是函式庫的體積（幾十 KB）與學習成本**；**所以判斷的依據是「這個介面的動畫是裝飾還是核心體驗」**——**對前者，CSS 就夠了；對後者（例如一個以動畫為賣點的產品），函式庫的投資是值得的**。

**面試回答方式**：給選擇的分界（**簡單狀態轉換用 CSS，複雜編排用函式庫**）並各列適用情況。核心加分點是**可中斷性是函式庫最大的價值之一**——**純 CSS 中途改變目標會跳動，而函式庫能從當前的位置與速度平滑過渡**，並解釋彈簧模型自然的原因（**用速度而非時間定義過渡，被打斷時保持動量**）。收在判斷依據：**這個介面的動畫是裝飾還是核心體驗**。
