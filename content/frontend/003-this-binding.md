# 題目

`this` 的值是怎麼決定的？箭頭函式的 `this` 為什麼不一樣？

## 核心答案

一般函式的 `this` 由**呼叫方式**決定，不是由定義位置決定。優先順序由高到低是：**`new` 呼叫**（`this` 是新建立的物件）、**顯式綁定**（`call`、`apply`、`bind` 指定的物件）、**方法呼叫**（`obj.fn()` 的 `this` 是 `obj`）、**預設綁定**（嚴格模式下是 `undefined`，非嚴格模式下是全域物件）。箭頭函式完全不適用這套規則——它沒有自己的 `this`，而是沿著**作用域鏈**去找外層的 `this`，也就是說它的 `this` 在**定義時就固定了**，`call`、`apply`、`bind` 都改不了。這正是為什麼在回呼裡用箭頭函式能解決「`this` 跑掉」的問題。最常見的踩雷是**把方法拆出來單獨呼叫**——`const fn = obj.method; fn()` 會失去 `obj`，因為 `this` 看的是呼叫時的形式而不是函式來自哪裡。

## 詳細解析

「誰呼叫的」是判斷的第一個問題：看到 `this` 就先問「這個函式是怎麼被呼叫的」。`obj.fn()` 的 `this` 是 `obj`；`fn()` 的 `this` 是 `undefined` 或全域；`arr.map(obj.fn)` 因為傳的是函式本身、呼叫時沒有接收者，所以 `this` 會丟失。這個「**傳遞函式會丟失接收者**」的現象是回呼中 `this` 出錯的主要來源。

**箭頭函式沒有 this、arguments、super、new.target**：它不只是語法簡潔，而是刻意不建立自己的執行上下文相關綁定。因此它也**不能當建構函式**（`new` 會拋錯），也不該用來定義物件的方法——`{ name: 'a', getName: () => this.name }` 裡的 `this` 指向的是模組或全域，不是這個物件。這是初學者最常見的誤用。

**class 的方法為什麼要綁定**：class 的方法不會自動綁定實例，所以把方法當回呼傳出去（例如 React 的 `onClick={this.handleClick}`）就會丟失 `this`。三種解法是：在建構函式中 `this.handleClick = this.handleClick.bind(this)`、用**類別欄位加箭頭函式**（`handleClick = () => {}`，定義在實例上且 `this` 固定）、或在傳遞時包一層箭頭函式。第二種最常用，代價是每個實例各有一份函式（而不是共用原型上的一份）。

**bind 的細節**：`bind` 回傳的是**新函式**，原函式不變；而且綁定過的函式無法再被重新綁定——再 `bind` 一次不會生效。但有一個例外：**`new` 的優先權高於 `bind`**，對綁定過的函式使用 `new`，`this` 仍然是新物件。這個優先順序常被拿來考。

**this 在不同環境的預設值**：嚴格模式下獨立呼叫的函式 `this` 是 `undefined`，非嚴格模式下是全域物件（瀏覽器是 `window`）。ES 模組**預設就是嚴格模式**，所以現代前端程式碼裡的 `this` 通常是 `undefined` 而不是 `window`——這個差異在除錯時會造成困惑，值得知道。

## 面試回答方式

先給總原則——一般函式的 `this` 由**呼叫方式**決定而不是定義位置，這一句就把整題定調。接著按優先順序列出四種綁定（`new`、顯式、方法、預設），並強調箭頭函式完全不在這套規則裡，它沿作用域鏈取外層的 `this`、定義時就固定、`bind` 也改不了。主動舉出最常見的踩雷：把方法拆出來單獨呼叫會丟失接收者。加分點有三個：箭頭函式不能當建構函式也不該當物件方法；class 方法的三種綁定解法與各自代價；以及 ES 模組預設嚴格模式，所以現代程式碼裡獨立呼叫的 `this` 是 `undefined` 而不是 `window`。

## 講稿

一般函式的 this 是由呼叫方式決定的，不是由它寫在哪裡決定。這是關鍵。

優先順序由高到低，new 呼叫的話 this 是新建立的物件，接著是 call、apply、bind 顯式指定的，再來是 obj 點 fn 這種方法呼叫，this 就是 obj，最後是預設綁定，嚴格模式下是 undefined。

所以我看到 this 的第一個問題永遠是，這個函式是怎麼被呼叫的。最常踩到的是把方法拆出來單獨呼叫，或者當成回呼傳出去。傳的是函式本身，呼叫的時候沒有接收者，this 就丟了。

箭頭函式完全不在這套規則裡。它沒有自己的 this，是沿著作用域鏈去找外層的，所以定義的時候就固定了，連 bind 都改不了。這就是為什麼在回呼裡用箭頭函式可以解決 this 跑掉的問題。

但反過來，箭頭函式不能當建構函式，也不該拿來定義物件的方法，因為那個 this 會指到模組或全域，不是那個物件。

還有一個容易困惑的地方，ES 模組預設就是嚴格模式，所以現在的前端程式碼裡，獨立呼叫的 this 是 undefined 而不是 window。

## 常見追問

### call、apply、bind 三者的差別是什麼？

**核心答案**：`call` 和 `apply` 都是**立刻執行**，差別只在參數形式——`call` 逐個傳，`apply` 傳一個陣列。`bind` 則**不執行**，而是回傳一個 `this` 已經固定的新函式，之後才呼叫。所以選擇的判準是：現在就要跑用 `call` 或 `apply`，之後才跑（例如當成回呼傳出去）用 `bind`。

**詳細解析**：`apply` 在展開運算子出現後用途減少了——以前用 `Math.max.apply(null, arr)` 求陣列最大值，現在寫 `Math.max(...arr)` 更清楚。不過 `apply` 在**參數個數不定且來自陣列**時仍然有用，而且對超大陣列使用展開運算子可能超出呼叫堆疊限制，這時 `apply` 也有同樣問題，正確做法是改用 `reduce` 分批處理。另外 `bind` 還可以**預先綁定部分參數**（偏函式應用）——`fn.bind(null, a)` 回傳一個已經固定第一個參數的新函式，這在需要產生一組相似回呼時很方便。

**面試回答方式**：用「立刻執行 vs 回傳新函式」與「參數形式」兩個維度把三者分清楚，並給出選擇的判準。加分點是提到 `apply` 的用途因展開運算子而減少、以及 `bind` 可以做偏函式應用預綁參數。

### 為什麼箭頭函式不能當建構函式？

**核心答案**：因為 `new` 的運作需要函式**能建立自己的 `this`**——`new` 會建立一個新物件、把函式的 `this` 指向它、執行函式體、最後回傳這個物件。箭頭函式**沒有自己的 `this` 綁定**，也沒有 `prototype` 屬性，所以 `new` 這一整套流程無法進行，引擎會直接拋出錯誤。

**詳細解析**：這也解釋了箭頭函式的其他限制——它沒有 `arguments`（要用剩餘參數 `...args` 取代）、沒有 `super`、沒有 `new.target`。設計上這是刻意的取捨：箭頭函式被定位為**輕量的函式運算式**，專門用在需要「繼承外層 `this`」的場景，例如回呼與陣列方法。理解這個定位就知道該用哪一種：需要自己的 `this`（物件方法、建構函式、需要動態綁定的函式）用一般函式；需要沿用外層 `this`（回呼、內層的輔助函式）用箭頭函式。這個判準比「箭頭函式比較新所以都用它」可靠得多。

**面試回答方式**：從 `new` 的四個步驟解釋為什麼箭頭函式做不到（沒有自己的 `this`、沒有 prototype）。接著列出它的其他限制並說明這是刻意的定位取捨。加分點是給出實用的選擇判準——需要自己的 `this` 用一般函式，需要沿用外層用箭頭函式。

### this 在事件處理器裡是什麼？

**核心答案**：用 `addEventListener` 註冊的**一般函式**，`this` 是**綁定事件的那個元素**（等同於 `event.currentTarget`）。但如果用**箭頭函式**，`this` 會是外層作用域的值，通常不是元素——這是最常見的困惑點。要注意 `currentTarget`（綁定監聽器的元素）和 `target`（實際觸發事件的元素）不同，事件冒泡時兩者常常不一樣。

**詳細解析**：在框架中這個問題被進一步包裝。React 的合成事件系統中，事件處理器的 `this` 取決於你怎麼定義（類別元件要自行綁定，函式元件根本沒有 `this` 的問題）。實務上比較穩健的做法是**不依賴 `this` 取得元素**，而是用 `event.currentTarget`——它語意明確、在箭頭函式裡也正確、而且重構時不會因為函式形式改變而壞掉。這個建議背後的原則是：盡量減少對隱式上下文的依賴，讓程式碼的行為只取決於明確傳入的東西。這個原則也適用於其他情境，是很值得表達的工程觀點。

**面試回答方式**：先給一般函式與箭頭函式的差別，並釐清 `currentTarget` 與 `target` 的不同。加分點是給出實務建議——用 `event.currentTarget` 取代 `this`，並把它上升到「減少對隱式上下文的依賴」這個通用原則。
