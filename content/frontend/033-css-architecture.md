# 題目

CSS Modules、Tailwind、CSS-in-JS 這些方案各自解決什麼？怎麼選？

## 核心答案

它們解決的是同一組問題的不同面向：**全域命名空間的衝突**、**不知道哪些樣式還在被使用**、**以及樣式與元件的距離。**

**CSS Modules**——用編譯期的類名雜湊解決衝突；保持標準 CSS 的寫法、零執行期成本、工具支援好；**它是最保守也最安全的選擇。**

**Tailwind（原子化 CSS）**——用預定義的工具類別避免寫新的 CSS；優點是不會產生新的命名問題、樣式表大小趨於收斂、且天然地約束在設計系統的值域內；代價是 HTML 變得冗長、以及對複雜的狀態組合支援較弱。

**CSS-in-JS**——樣式與元件同在一處、可以用 props 動態計算；代價是執行期成本（部分方案）與伺服器端渲染的複雜度；而近年零執行期的方案（編譯期抽出 CSS）緩解了主要的缺點。

選擇的實際依據往往不是技術優劣，而是「團隊的熟悉度」與「是否有設計系統」——有設計 token 的團隊用哪一種都能寫出一致的樣式，沒有的話用哪一種都會亂。

## 詳細解析

「原子化 CSS 的收斂性是它最被低估的優點」：傳統 CSS 的檔案會隨功能線性增長——而原子化的樣式表大小會趨於平緩，因為新頁面多半在複用已有的類別；在大型專案中這個差別很明顯。而它的另一個隱性收益是「刪除功能時 CSS 自然被移除」——因為類別寫在 HTML 裡，元件刪了樣式就跟著消失，不會留下沒人敢刪的孤兒 CSS。

**「CSS-in-JS 的執行期成本值得量化」**：執行期方案要在渲染時生成樣式並插入——在大量元件的頁面上這是可測量的開銷，尤其在伺服器端渲染時；而它也讓元件的重新渲染可能觸發樣式的重新計算。Meta 與其他大型團隊轉向編譯期方案，主要原因就是這個。

**「原生 CSS 已經補上了很多缺口」**：CSS 變數（動態主題不再需要 JS）、`:has()`（父選擇器）、巢狀語法、以及 `@layer`（明確控制層疊優先權）——這些讓「必須用預處理器或 CSS-in-JS」的理由減少了；而在新專案中，先評估原生 CSS 加上 CSS Modules 是否已經足夠，往往能省下不少複雜度。

「設計 token 是比方案選擇更重要的決定」：把顏色、間距、字級、圓角定義成有限的一組變數——於是無論用什麼方案，樣式都被約束在一致的值域內；沒有這一層的專案，最後會有二十七種灰色。

## 面試回答方式

先指出它們解決的是同一組問題的不同面向並列出那三個問題，再逐一給各方案的優點與代價。加分點有四個：**原子化 CSS 的收斂性**與**刪除功能時 CSS 自然被移除**這個隱性收益；**CSS-in-JS 的執行期成本值得量化**，而大型團隊轉向編譯期方案正是因為它；**原生 CSS 已經補上很多缺口**（變數、`:has()`、巢狀、`@layer`）；以及設計 token 是比方案選擇更重要的決定。

## 講稿

我覺得它們解決的是同一組問題的不同面向。全域命名衝突、不知道哪些樣式還在用、還有樣式跟元件的距離。

CSS Modules 用編譯期的類名雜湊解決衝突，保持標準寫法、零執行期成本，是最保守也最安全的選擇。

Tailwind 這類原子化的方案，優點是不會產生新的命名問題，而且樣式表大小會趨於收斂。傳統 CSS 會隨功能線性增長，原子化的會平緩下來，因為新頁面多半在複用已有的類別。它還有一個隱性的好處，刪除功能的時候 CSS 自然就跟著消失，不會留下沒人敢刪的孤兒樣式。

CSS-in-JS 的優點是樣式跟元件同在一處而且能用 props 動態計算。但執行期的方案要在渲染時生成樣式並插入，那是可測量的開銷，伺服器端渲染時特別明顯。所以近年很多團隊轉向編譯期抽出 CSS 的方案。

不過我認為比方案選擇更重要的是有沒有設計 token。沒有那一層的專案，最後會有二十七種灰色。

## 常見追問

### !important 什麼時候是可以接受的？

**核心答案**：覆蓋你無法控制的第三方樣式時，以及在工具類別中刻意提升優先權時。而在自己的程式碼裡用它來解決優先權問題，通常表示選擇器的設計出了問題——因為它會讓後續的覆蓋更困難，形成 `!important` 的軍備競賽。

**詳細解析**：**「`@layer` 提供了更好的解法」**：層疊層讓你明確宣告優先權的順序（例如 `@layer reset, base, components, utilities`）——於是後面的層無論選擇器多簡單都能覆蓋前面的層；這正是過去只能用 `!important` 或者堆疊選擇器來達成的效果。它對整合第三方樣式特別有用——把第三方的 CSS 放進一個低優先權的層，你的樣式就能自然地覆蓋它而不需要提高特異性。理解 `@layer` 之後，多數 `!important` 的使用場景都有了更乾淨的替代；而在面試中提到它，展示的是你在追蹤 CSS 的現代發展而非停留在幾年前的實踐。

**面試回答方式**：給兩個可接受的場景並指出在自己的程式碼裡用它通常表示選擇器設計有問題。核心加分點是介紹 **`@layer` 提供了更好的解法**——它讓你明確宣告優先權順序，後面的層無論選擇器多簡單都能覆蓋前面的，並說明它對整合第三方樣式特別有用。收在價值：多數 `!important` 的場景都有了更乾淨的替代。

### 深色模式怎麼實作比較好？

**核心答案**：用 CSS 變數定義完整的淺色調色盤，然後在深色的條件下只重新定義那些變數。要支援三種狀態：**跟隨系統**（`prefers-color-scheme`）、**明確選淺色**、**明確選深色**——所以需要一個資料屬性或類別來覆蓋媒體查詢的結果。

**詳細解析**：「避免閃爍需要在渲染前就決定主題」：如果主題的選擇存在 `localStorage` 而讀取它的 JavaScript 在頁面渲染後才執行——使用者會看到淺色閃一下再變深色；解法是在 `<head>` 中放一小段同步的腳本，在任何內容渲染前就把類別加到 `<html>` 上。這是少數「阻塞渲染的內聯腳本是正確做法」的場景。而在設計上，深色模式不應該只是把顏色反轉——純黑背景加純白文字的對比過強會造成光暈效應，而陰影在深色下幾乎不可見，需要改用邊框或者更亮的表面色來表達層次；這些是把深色模式做得好看與只是「能用」的差別。

**面試回答方式**：給實作方式（**CSS 變數加上三種狀態的處理**）。核心加分點是避免閃爍需要在渲染前決定主題——在 `<head>` 放一小段同步腳本，這是少數「阻塞渲染的內聯腳本是正確做法」的場景。收在設計層面：**深色模式不是把顏色反轉**——純黑白對比過強會造成光暈，陰影在深色下幾乎不可見需改用邊框或更亮的表面色。

### CSS 的效能問題通常出在哪？

**核心答案**：主要不在選擇器的複雜度而在觸發的重排範圍。現代瀏覽器的選擇器匹配非常快——而真正的問題是「一個樣式變更影響了多大的範圍」：改變會影響版面的屬性（寬高、位置、字級）會觸發重排，而重排的成本取決於受影響的元素數量。

**詳細解析**：**「`contain` 與 `content-visibility` 能限制影響範圍」**：`contain: layout` 告訴瀏覽器「這個元素內部的版面變化不會影響外部」——**於是重排被限制在子樹內**；而 `content-visibility: auto` 讓螢幕外的內容跳過渲染，在長列表上效果顯著。這兩個屬性是少數「加一行就有明顯效果」的優化，但要注意 `content-visibility` 會影響頁內搜尋與捲動位置的準確性（需要配合 `contain-intrinsic-size` 給出預估高度）。而更常見的效能殺手其實是「在 JavaScript 中交錯地讀取與寫入版面屬性」——每次讀取都會強制瀏覽器完成前面的寫入，形成布局抖動；批次地先讀完再寫，是這類問題的標準解法。

**面試回答方式**：糾正常見的假設（主要不在選擇器複雜度而在觸發的重排範圍）。核心加分點是介紹 `contain` 與 `content-visibility` 這兩個「加一行就有明顯效果」的優化與它們的注意事項。收在更常見的殺手：在 JavaScript 中交錯讀寫版面屬性造成的布局抖動——每次讀取都強制完成前面的寫入，而批次地先讀完再寫是標準解法。
