# 題目

`==` 和 `===` 差在哪？為什麼 `[] == false` 是 `true`？

## 核心答案

`===` 是**嚴格相等**：型別不同直接回傳 `false`，型別相同才比較值。`==` 是**寬鬆相等**：型別不同時會先做**型別轉換**再比較，而轉換規則相當複雜——這正是它容易出錯的原因。核心規則有四條：**`null == undefined` 為真，但兩者與其他任何值比較都是假**；**數字與字串比較時，字串轉數字**；**布林值先轉成數字**（`false` 變 0、`true` 變 1）；**物件與原始值比較時，物件先透過 `valueOf` 或 `toString` 轉成原始值**。`[] == false` 之所以為真，就是這幾條疊在一起：`false` 轉成 `0`，`[]` 透過 `toString` 變成空字串 `""`，空字串再轉成數字也是 `0`，於是 `0 == 0` 成立。實務結論很簡單：**預設一律用 `===`**，唯一值得用 `==` 的場合是 `x == null`（同時檢查 `null` 與 `undefined`）。

## 詳細解析

**`NaN` 不等於自己**：`NaN === NaN` 是 `false`，這是浮點數標準的規定。要判斷是不是 `NaN` 要用 `Number.isNaN`（而不是全域的 `isNaN`，後者會先做型別轉換，導致 `isNaN('abc')` 回傳 `true`）。`Object.is` 也能正確處理 `NaN`，而且它還能區分 `+0` 與 `-0`——這是它和 `===` 的兩個差異。

**`+0` 與 `-0`**：兩者用 `===` 比較是相等的，但 `Object.is(+0, -0)` 是 `false`。實務上會踩到的情境是除以零的方向（`1/+0` 是正無限、`1/-0` 是負無限），在數值計算或排序時偶爾造成困惑。

**物件轉原始值的順序**：多數物件會先呼叫 `valueOf`，如果回傳的不是原始值再呼叫 `toString`；`Date` 則相反，預設先用 `toString`。這解釋了為什麼 `[] + {}` 與 `{} + []` 在某些情境下結果不同——前者是字串串接，後者的 `{}` 可能被解析成程式區塊。這類題目在面試中出現時，重點不是背結果，而是能講出「**加號在有字串參與時是串接，否則是數值相加**」以及「**物件會先轉成原始值**」這兩條規則。

**空陣列與空物件的真值判斷**：`[]` 和 `{}` 在布林轉換中都是 **truthy**（所有物件都是），但 `[] == false` 卻是 `true`——這個看似矛盾的組合是因為兩者走的是不同的轉換路徑：`if ([])` 用的是 `ToBoolean`，`==` 用的是 `ToPrimitive` 加 `ToNumber`。能講清楚這個區別，就抓到了這類題目的核心。

**判斷空值的實務寫法**：檢查是否為 `null` 或 `undefined` 用 `x == null` 或 `x ?? default`；檢查是否為空字串要小心 `0` 與空字串都是 falsy，如果 `0` 是合法值就不能用 `if (!x)`，要明確寫 `if (x === undefined)` 或用 `??` 而不是 `||`。這是 `??`（空值合併）與 `||` 最重要的差別：`||` 會把 `0` 與 `''` 也當成需要替換的值。

## 面試回答方式

先給定義差異，然後**直接示範 `[] == false` 的推導過程**——布林轉數字、陣列轉字串再轉數字，一步一步走完。能當場推導比背下結果有說服力得多。接著給實務結論：**預設用 `===`，唯一例外是 `x == null`**。加分點有三個：`NaN` 不等於自己且要用 `Number.isNaN`（不是全域的 `isNaN`）；`ToBoolean` 與 `ToPrimitive` 是不同的轉換路徑，所以 `[]` 是 truthy 但 `[] == false` 為真；以及 `??` 與 `||` 的差別——`||` 會把 `0` 和空字串也替換掉，這是實務上真正會造成 bug 的地方。

## 講稿

三個等號是嚴格相等，型別不同直接回傳 false。兩個等號會先做型別轉換再比較，規則相當複雜，這就是它容易出錯的原因。

我直接推一次那個經典的例子。左邊是空陣列，右邊是 false。第一步布林值先轉成數字，false 變成零。第二步物件要跟數字比較，陣列先透過 toString 變成空字串。第三步空字串再轉成數字，也是零。所以最後是零等於零，成立。

有趣的是空陣列在 if 判斷裡是 true，因為所有物件都是 truthy。看起來矛盾，其實是走了不同的轉換路徑，if 用的是布林轉換，兩個等號用的是先轉原始值再轉數字。

我的實務結論很單純，預設一律用三個等號。唯一會用兩個等號的地方是判斷 null，因為它可以同時涵蓋 null 跟 undefined。

另外有兩個容易踩的。NaN 不等於它自己，要判斷得用 Number.isNaN，不能用全域那個 isNaN，因為它會先做轉換。還有空值合併跟邏輯或不一樣，邏輯或會把零跟空字串也當成要被替換的值，如果零是合法的資料就會出錯。

## 常見追問

### `??` 和 `||` 該怎麼選？

**核心答案**：**`||` 在左側是任何 falsy 值時取右側**（`0`、`''`、`false`、`NaN`、`null`、`undefined`），**`??` 只在左側是 `null` 或 `undefined` 時取右側**。所以當 `0` 或空字串是合法的資料值時，必須用 `??`——用 `||` 會把使用者輸入的 0 或刻意設定的空字串當成「沒有值」而替換掉，這是真實會發生的 bug。

**詳細解析**：典型的踩雷場景是設定值的預設處理——`const timeout = config.timeout || 3000` 在使用者明確設定 `timeout: 0`（代表不逾時）時會變成 3000，完全違反意圖。同樣的問題出現在數量、價格、分數這些 0 有意義的欄位。反過來，如果空字串確實應該被視為「沒填」，那 `||` 才是對的。**判準是：0 和空字串對這個欄位而言是不是合法的值**。另外要注意 `??` 不能直接和 `||`、`&&` 混用（語法錯誤），必須加括號明確表示優先順序，這是規範刻意的設計，避免歧義。

**面試回答方式**：明確給出兩者的觸發條件差異，並用 `timeout: 0` 這個具體的 bug 場景說明。給出判準——0 和空字串對這個欄位是不是合法值。加分點是提到 `??` 不能與 `||`、`&&` 直接混用，必須加括號。

### 怎麼可靠地判斷一個值的型別？

**核心答案**：**分情況用不同工具**。基本型別用 `typeof`（但要記得 `typeof null` 是 `'object'` 這個歷史 bug，而且 `typeof` 對陣列與物件都回傳 `'object'`）。陣列用 **`Array.isArray`**。要精確區分內建型別（`Date`、`RegExp`、`Map`）用 **`Object.prototype.toString.call(x)`**，它會回傳像 `[object Date]` 的字串。自訂類別用 `instanceof`，但要注意跨執行環境會失效。

**詳細解析**：實務上還有幾個常見需求。判斷是否為**純粹物件**（不是陣列、不是 null、不是類別實例）沒有內建方法，通常組合 `typeof x === 'object' && x !== null && Object.getPrototypeOf(x) === Object.prototype`。判斷是否為**可迭代**看有沒有 `Symbol.iterator`。判斷是否為**函式**用 `typeof x === 'function'`（這是 `typeof` 最可靠的用途之一）。TypeScript 環境下更好的做法是用**型別守衛函式**把這些判斷封裝起來，讓型別系統也能收窄，而不是在各處散落 `typeof` 判斷。

**面試回答方式**：分情況給工具（`typeof`、`Array.isArray`、`toString.call`、`instanceof`），並主動提 `typeof null` 這個歷史 bug。加分點是給出判斷純粹物件的組合寫法，以及在 TypeScript 中應該封裝成型別守衛讓型別系統能收窄。

### 為什麼 `0.1 + 0.2 !== 0.3`？

**核心答案**：因為 JavaScript 的數字是 **IEEE 754 雙精度浮點數**，用二進位表示。0.1 和 0.2 在二進位下是**無限循環小數**，儲存時必須截斷，於是相加的結果是 0.30000000000000004 而不是精確的 0.3。這不是 JavaScript 的缺陷，所有使用相同浮點數標準的語言都一樣。

**詳細解析**：處理方式依場景不同。**比較**時用誤差範圍：判斷兩數差的絕對值小於一個極小值（可以用 `Number.EPSILON`）。**金額計算**絕對不要用浮點數——標準做法是**以最小單位（分）儲存成整數**，或使用高精度的十進位函式庫。**顯示**時用 `toFixed` 控制小數位數，但要注意它回傳字串且有自己的進位行為。另外要知道 JavaScript 的整數安全範圍是 `Number.MAX_SAFE_INTEGER`（約 9 千兆），超過就會失去精度——處理大整數 ID 時要用 `BigInt` 或直接以字串傳遞，這在後端回傳雪花演算法 ID 時是真實會遇到的問題。

**面試回答方式**：先講根因是二進位無法精確表示這些十進位小數，並強調這不是 JavaScript 特有的。接著分場景給解法：比較用誤差範圍、金額用整數分或十進位函式庫、顯示用 `toFixed`。加分點是提到安全整數上限與大整數 ID 要用字串傳遞這個真實場景。
