# 題目

什麼工作該放到 Web Worker？它的限制是什麼？

## 核心答案

判準是「這段工作會不會阻塞主執行緒超過幾十毫秒」——因為主執行緒同時負責 JavaScript、版面、繪製與事件回應；一段執行兩百毫秒的計算，意味著兩百毫秒內點擊沒有反應、動畫停住、輸入框打不出字。

**適合搬到 Worker 的**：**大量資料的解析與轉換**（大型 JSON、CSV、試算表）、**加密與壓縮**、**影像處理**、**複雜的搜尋與排序**、**以及需要持續運行的計算**（模擬、語法分析）。

**Worker 的限制**：**沒有 DOM 存取**（它看不到 document）、與主執行緒只能透過訊息通訊、而訊息傳遞預設是結構化複製（大物件的複製本身就有成本）；所以「搬過去」不一定變快，要看計算與傳輸的比例。

**真正的加速來自兩點**：**主執行緒被釋放**（即使總時間不變，介面仍然流暢）；**以及可轉移物件（Transferable）避免複製**——`ArrayBuffer` 可以被轉移而非複製，成本接近零。

## 詳細解析

**「不是所有慢都該用 Worker」**：如果瓶頸是等待網路或者是渲染大量 DOM——**Worker 沒有幫助**（前者本來就是非同步的，後者只能在主執行緒做）；**Worker 解決的專門是「CPU 密集的 JavaScript 計算」**。先用效能面板確認時間花在哪，比直接搬程式碼有效。

**「通訊的成本要納入計算」**：結構化複製一個 50MB 的物件可能要幾百毫秒——而那個複製發生在主執行緒上，等於你為了避免阻塞而製造了阻塞；所以對大資料要用可轉移物件，或者讓 Worker 直接去取資料（Worker 內可以用 fetch）而不是由主執行緒傳過去。**後者往往是更好的設計。**

**「SharedArrayBuffer 需要特定的標頭」**：它允許多個執行緒共享同一塊記憶體（真正的零複製）——但因為 Spectre 類的攻擊，它需要跨來源隔離的標頭（COOP 與 COEP）才能啟用；而開啟那些標頭會影響嵌入的第三方資源，**所以導入的門檻不低。**

「Worker 的除錯與錯誤處理要另外設計」：Worker 中的錯誤不會自動出現在主執行緒——需要監聽 `onerror` 與 `onmessageerror` 並轉發到監控系統；而堆疊追蹤也指向 Worker 的檔案，source map 的設定要涵蓋它。

## 面試回答方式

先給判準（會不會阻塞主執行緒超過幾十毫秒）與主執行緒的職責，再列出適合的工作與 Worker 的限制。加分點有四個：**不是所有慢都該用 Worker**——它專門解決 CPU 密集的 JS 計算，對網路等待與 DOM 渲染沒有幫助；**通訊的成本要納入計算**，而讓 Worker 自己去取資料往往是更好的設計；SharedArrayBuffer 需要跨來源隔離的標頭，門檻不低；以及**Worker 的錯誤監控要另外設計**。

## 講稿

判準是這段工作會不會阻塞主執行緒超過幾十毫秒。因為主執行緒同時負責 JavaScript、版面、繪製跟事件回應。一段跑兩百毫秒的計算，意味著那兩百毫秒內點擊沒反應、動畫停住、輸入框打不出字。

適合搬過去的是大量資料的解析、加密壓縮、影像處理、還有複雜的搜尋排序。

但有一點很重要，不是所有慢都該用 Worker。如果瓶頸是等網路或者是渲染大量 DOM，Worker 完全沒有幫助。它專門解決的是 CPU 密集的 JavaScript 計算。所以我會先用效能面板確認時間花在哪。

另外通訊的成本要算進去。結構化複製一個五十 MB 的物件可能要幾百毫秒，而那個複製發生在主執行緒上，等於為了避免阻塞而製造了阻塞。

所以對大資料我會用可轉移物件，ArrayBuffer 可以轉移而不是複製。或者更好的做法是讓 Worker 自己去 fetch 資料，不要由主執行緒傳過去。

## 常見追問

### Service Worker 和 Web Worker 有什麼不同？

**核心答案**：**目的完全不同**。Web Worker 是為了把計算搬離主執行緒——**生命週期跟著頁面**；**Service Worker 是一個網路代理**，它攔截頁面發出的請求並決定從快取還是網路回應，生命週期獨立於頁面（頁面關了它仍可能被喚醒處理推播或背景同步）。它們共用「在主執行緒之外運行」這個特性，但解決的問題不重疊。

**詳細解析**：「Service Worker 的更新機制是最容易出問題的部分」：新版本的 Service Worker 安裝後會進入等待狀態——要等所有使用舊版的分頁都關閉才會啟用；於是使用者可能長時間停留在舊版本。`skipWaiting` 能強制立即接管，但那可能讓已載入的頁面與新的 Service Worker 版本不匹配（頁面請求的是舊的資源檔名而新的快取裡沒有）；所以常見的做法是「偵測到新版本後提示使用者重新載入」而非靜默地強制更新。而一個部署失誤的 Service Worker 可能把錯誤的內容快取給所有使用者且難以撤回——這是它被稱為「最容易搞砸的 Web API」的原因；所以務必實作一個能遠端停用它的機制。

**面試回答方式**：說明兩者的目的與生命週期完全不同。核心加分點是Service Worker 的更新機制是最容易出問題的部分——新版本要等舊分頁全關才啟用，而 `skipWaiting` 可能造成頁面與版本不匹配，並給出常見做法（提示使用者重新載入）。收在風險：部署失誤的 Service Worker 可能把錯誤內容快取給所有人且難以撤回，所以務必實作能遠端停用的機制。

### 有沒有更簡單的方式避免阻塞？

**核心答案**：**有幾個成本低得多的手段**：把長任務切成小塊並在中間讓出控制權（用 `scheduler.yield()` 或者 `setTimeout` 分批）、**用 `requestIdleCallback` 把非緊急的工作排到空檔**、以及用 `IntersectionObserver` 讓工作只在需要時發生。這些不需要 Worker 的複雜度，而在很多情況下已經足夠。

**詳細解析**：「讓出控制權的關鍵是頻率而非總時間」：把一個 500 毫秒的任務切成十段每段 50 毫秒——總時間可能因為調度開銷而略增；但使用者的輸入能在每段之間被處理，於是介面感覺是回應的。而 `scheduler.yield()` 比 `setTimeout(0)` 更好的地方在於它保留了任務的優先權——`setTimeout` 會把剩餘的工作排到佇列末端，可能被其他任務插隊。這個「切分並讓出」的模式，是處理「必須在主執行緒做但很耗時」的工作（例如渲染大量 DOM）的標準方法；**因為那類工作根本無法搬到 Worker**。

**面試回答方式**：給三個成本較低的手段並指出**它們在很多情況下已經足夠**。核心加分點是讓出控制權的關鍵是頻率而非總時間——切分後總時間可能略增但介面感覺是回應的，並說明 **`scheduler.yield()` 比 `setTimeout(0)` 更好在保留了任務優先權**。收在適用範圍：這是處理「必須在主執行緒做但很耗時」的工作的標準方法——**因為那類工作根本無法搬到 Worker**。

### WebAssembly 和 Worker 怎麼配合？

**核心答案**：**常常一起用**。WebAssembly 提供接近原生的計算速度——而把它放在 Worker 中執行，就同時得到「快」與「不阻塞」；典型的組合是影像/影片處理、加密、以及把既有的 C++ 或 Rust 函式庫帶到瀏覽器。

**詳細解析**：**「WebAssembly 的收益取決於工作的類型」**：它在數值計算密集的工作上可能比 JavaScript 快數倍——但在頻繁與 JavaScript 互動或者大量操作字串與物件的場景中，跨邊界的轉換成本可能吃掉優勢；所以它適合「一次送進去一大塊資料、算完再一次送出來」的模式。而它最實際的價值往往不是速度而是「複用既有的程式庫」——把一個成熟的 C 函式庫編譯到瀏覽器，比用 JavaScript 重寫並確保行為一致划算得多（影像編解碼、PDF 渲染、資料庫引擎都是這樣的例子）。在面試中能指出「複用生態常常比效能更是導入的理由」，展示的是實務的判斷。

**面試回答方式**：說明兩者常一起用與典型的組合。核心加分點是**WebAssembly 的收益取決於工作類型**——數值密集時快數倍，但頻繁跨邊界互動時轉換成本可能吃掉優勢，於是它適合「一次進一大塊、算完一次出來」。收在實務洞察：它最實際的價值往往不是速度而是複用既有的程式庫，並舉出影像編解碼、PDF 渲染這類例子。
