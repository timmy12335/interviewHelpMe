# 題目

同源政策擋的到底是什麼？什麼情況會觸發預檢請求？

## 核心答案

同源政策的核心是：**瀏覽器會發出請求，但會擋住 JavaScript 讀取回應**。這是最常被誤解的一點——跨域的請求通常**已經送到伺服器並執行了**，只是回應被瀏覽器攔下不給前端程式碼讀。同源的定義是**協定、網域、通訊埠三者完全相同**，差一個就是跨域。**CORS** 是伺服器用回應標頭告訴瀏覽器「我允許這個來源讀取」的機制，關鍵標頭是 `Access-Control-Allow-Origin`。請求分兩類：**簡單請求**直接送出，瀏覽器收到回應後才檢查標頭決定要不要放行；**非簡單請求**會先送一個 `OPTIONS` 的**預檢請求**問伺服器允不允許，通過了才送真正的請求。觸發預檢的條件是：方法不是 `GET`、`POST`、`HEAD`，或帶了自訂標頭（例如 `Authorization`、`X-Request-Id`），或 `Content-Type` 是 `application/json` 以外的三種以外的值。實務上「送 JSON 就會預檢」是最常遇到的情況。

## 詳細解析

**「請求已經送到了」的安全含意**：因為簡單請求會實際抵達伺服器，所以**同源政策不能當成伺服器端的防護**。一個沒有 CSRF 防護的 `POST` 端點，即使前端讀不到回應，副作用（扣款、刪除資料）已經發生了。這就是為什麼 CSRF 需要獨立的防護機制，而不是靠 CORS。

**帶憑證的請求有更嚴格的規則**：需要送出 Cookie 時要設 `credentials: 'include'`，而伺服器端有兩個額外要求——必須回 `Access-Control-Allow-Credentials: true`，而且 **`Access-Control-Allow-Origin` 不能是萬用字元 `*`**，必須是具體的來源。這是刻意的限制，避免任意網站都能帶著使用者的 Cookie 讀取資料。實務上要用白名單依請求的 `Origin` 動態回應，而不是無條件回顯——無條件回顯等於完全開放。

**預檢請求的快取**：`Access-Control-Max-Age` 可以讓瀏覽器快取預檢結果，避免每個請求都多一次往返。在 API 呼叫頻繁的應用中這個設定對延遲的影響很明顯。要注意各瀏覽器對這個值有各自的上限。

**前端能讀到哪些回應標頭**：預設只能讀取幾個基本標頭，自訂標頭（例如分頁總數 `X-Total-Count`）必須由伺服器用 **`Access-Control-Expose-Headers`** 明確列出才讀得到。很多人以為標頭有回但前端讀不到是 bug，其實是漏了這個設定。

**開發環境的代理不是解法**：開發時用 dev server 的代理把請求轉發到後端，這樣就變成同源、不會有 CORS 問題。這很方便，但它會**掩蓋正式環境的設定問題**——正式環境是真的跨域，如果後端沒設好 CORS，上線才會爆。所以代理是開發便利，不是 CORS 的解決方案。

## 面試回答方式

第一句就把最常見的誤解糾正——**同源政策擋的是 JavaScript 讀取回應，不是擋請求送出**，請求通常已經到達伺服器並執行了。接著給同源的定義與 CORS 的角色。分清簡單請求與非簡單請求，並直接說出**觸發預檢的三個條件**，特別點出「送 JSON 就會預檢」這個最常遇到的情況。加分點有三個：因為請求已經送達，所以 **CORS 不能取代 CSRF 防護**；帶憑證時 `Allow-Origin` **不能用萬用字元**且不該無條件回顯 `Origin`；以及自訂回應標頭要用 `Expose-Headers` 才讀得到。

## 講稿

我想先糾正一個很常見的誤解。同源政策擋的不是請求送出，而是 JavaScript 讀取回應。跨域的請求其實通常已經送到伺服器、也已經執行了，只是回應被瀏覽器攔下來不給前端讀。

這件事有個安全含意，就是同源政策不能當成伺服器端的防護。一個沒有 CSRF 防護的 POST 端點，就算前端讀不到回應，扣款或刪資料的副作用已經發生了。所以 CSRF 要另外處理。

CORS 就是伺服器用回應標頭告訴瀏覽器我允許這個來源讀。請求分兩種，簡單請求直接送，收到回應才檢查標頭。非簡單請求會先送一個 OPTIONS 預檢，問過才送真正的請求。

觸發預檢的條件是方法不是 GET、POST、HEAD，或者帶了自訂標頭像 Authorization，或者 Content-Type 是 JSON。實務上送 JSON 就會預檢，這是最常遇到的。

另外帶 Cookie 的時候規則更嚴，伺服器要回 Allow-Credentials 為 true，而且 Allow-Origin 不能用星號，必須是具體的來源。這時候要用白名單，不能無條件把 Origin 回顯回去，那等於完全開放。

## 常見追問

### 為什麼帶憑證時 Access-Control-Allow-Origin 不能用萬用字元？

**核心答案**：因為那等於允許**任何網站**帶著使用者的 Cookie 去讀取你的 API。使用者只要登入過你的站，之後造訪任何惡意網站，那個網站的 JavaScript 就能以使用者的身分發請求並讀到回應——等於帳號資料完全外洩。所以規範強制：一旦 `Allow-Credentials` 為 `true`，`Allow-Origin` 必須是**具體的單一來源**。

**詳細解析**：實務上的正確做法是**維護允許來源的白名單**，收到請求時檢查 `Origin` 是否在白名單中，是才回顯該來源，並記得加上 `Vary: Origin`（否則 CDN 或代理可能把針對 A 來源的回應快取後回給 B 來源，造成快取污染）。常見的錯誤實作是**無條件回顯 `Origin`**——這在功能上「能動」，但安全性等同於萬用字元加憑證，是相當嚴重的漏洞。另一個要注意的是子網域：如果白名單用了寬鬆的比對（例如只檢查結尾），攻擊者註冊一個結尾相同的網域就能繞過，比對必須是精確的。

**面試回答方式**：用具體的攻擊路徑說明——使用者登入過，之後任何網站都能以其身分讀資料。接著給正確做法：白名單加回顯，並且要加 `Vary: Origin` 防快取污染。加分點是指出無條件回顯 `Origin` 這個「能動但等於全開」的常見錯誤，以及子網域比對要精確。

### 除了 CORS，還有哪些跨域方案？

**核心答案**：現在的答案基本上就是 **CORS**，其他多半是歷史方案或特定用途。**JSONP** 利用 `<script>` 不受同源限制，但只支援 `GET`、無法處理錯誤、而且有嚴重的安全風險（等於執行對方給的任意程式碼），已經不該使用。**反向代理**（由自己的伺服器轉發請求）在架構上把跨域變成同源，適合整合第三方 API 且需要隱藏金鑰的場景。**`postMessage`** 用於不同來源的視窗或 iframe 之間通訊，是正規且安全的做法，但要嚴格檢查來源。

**詳細解析**：選擇的判準是**你控制得了哪一端**。如果後端是自己的，就設定 CORS，最直接。如果第三方 API 不支援 CORS（或需要隱藏 API 金鑰、需要加上速率限制），就用自己的伺服器代理。如果是嵌入第三方頁面並要與它互動，就用 `postMessage`。使用 `postMessage` 時最常見的漏洞是**沒有驗證 `event.origin`** 就處理訊息，等於接受任何網站的指令；發送時也應該指定明確的目標來源而不是用萬用字元。

**面試回答方式**：直接說現在就是 CORS，其他各有特定用途。給出 JSONP 為什麼該淘汰、代理適合什麼場景、`postMessage` 用在視窗間通訊。加分點是給選擇判準（你控制得了哪一端），以及點出 `postMessage` 必須驗證 `event.origin` 這個常見漏洞。

### 預檢請求會拖慢效能嗎？怎麼優化？

**核心答案**：會，每個非簡單請求都多一次完整的往返，在高延遲網路上影響明顯。優化方式有三個：**設定 `Access-Control-Max-Age`** 讓瀏覽器快取預檢結果（同一個端點與方法組合在有效期內不再預檢）；**減少自訂標頭**（能放在請求主體或作為簡單標頭的就不要自訂）；以及**同源部署**——把 API 放在同一個網域下的路徑（例如 `/api`），透過反向代理轉發，從根本上不需要 CORS。

**詳細解析**：實務上第三個方案往往最有效，尤其對首屏就要發多個 API 請求的應用。要注意 `Max-Age` 的快取是**依 URL 加方法**區分的，所以對許多不同端點的應用，快取的效益有限——這時同源部署的價值更高。另外要留意的是**預檢失敗的錯誤訊息不明顯**：瀏覽器只會在主控台顯示 CORS 錯誤，網路面板中真正的請求根本不會出現，這常讓人誤以為請求沒送出。排查時要**先看有沒有 OPTIONS 請求以及它的回應標頭**，這是最快定位問題的方式。

**面試回答方式**：確認會拖慢並說明是多一次往返。給三個優化手段，並指出同源部署往往最有效。加分點是提到 `Max-Age` 依 URL 加方法快取所以對多端點應用效益有限，以及排查時要先看 OPTIONS 請求本身，因為預檢失敗時真正的請求不會出現在網路面板。
