# 題目

`Cache-Control` 和 `ETag` 各自解決什麼問題？前端打包產物的快取策略該怎麼設計？

## 核心答案

HTTP 快取分兩層。**強快取**由 `Cache-Control: max-age` 控制——在有效期內瀏覽器**完全不發請求**，直接用本地副本，這是最快的路徑。**協商快取**在強快取過期後生效——瀏覽器帶著 `If-None-Match`（對應伺服器給的 `ETag`）或 `If-Modified-Since`（對應 `Last-Modified`）去問伺服器，內容沒變就回 **304 Not Modified**，只傳標頭不傳內容。兩者的差別是**發不發請求**：強快取零往返，協商快取仍有一次往返但省下傳輸量。前端打包產物的標準策略是**內容雜湊加長期強快取**——把檔名加上內容雜湊（`app.a1b2c3.js`），設 `Cache-Control: max-age=31536000, immutable`，內容變了檔名就變，天然沒有失效問題；而 **HTML 入口檔則設為不快取或極短快取**（`no-cache`），因為它負責引用那些帶雜湊的檔名，必須每次都拿到最新的。

## 詳細解析

**no-cache 與 no-store 完全不同**：`no-cache` 是「**可以存但每次都要驗證**」——仍然會用協商快取，內容沒變就回 304。`no-store` 才是「**完全不要存**」，適合真正敏感的內容。這兩個名稱極容易混淆，而選錯會造成效能或安全問題。

**ETag 的兩種形式**：**強驗證**（`"abc"`）表示位元組完全相同，**弱驗證**（`W/"abc"`）表示語意等價即可（例如壓縮方式不同但內容相同）。多台伺服器的環境要注意 `ETag` 的產生方式必須一致——如果基於檔案的 inode 產生，不同伺服器會給出不同的 `ETag`，導致快取永遠命中不了。實務上建議基於**內容雜湊**產生。

**Last-Modified 的精度限制**：它只精確到秒，所以一秒內的多次修改偵測不到；而且它反映的是檔案時間而非內容，重新部署時檔案時間改變但內容相同也會造成不必要的傳輸。`ETag` 沒有這些問題，所以在兩者都可用時優先用 `ETag`。

**CDN 與瀏覽器快取要分開設定**：`s-maxage` 只對共用快取（CDN、代理）生效，可以設得比 `max-age` 長——讓 CDN 保留久一點、瀏覽器短一點，這樣需要更新時只要清 CDN 的快取，不必等使用者的瀏覽器過期。另外 `stale-while-revalidate` 允許先回傳過期的內容給使用者、同時在背景更新，兼顧速度與新鮮度，非常適合變動不頻繁的 API 回應。

**Service Worker 是另一層完全獨立的快取**：它在網路層之前攔截請求，可以完全自訂策略（快取優先、網路優先、過期後重新驗證）。它的強大之處在於**可程式化**與**支援離線**，代價是**更新機制複雜**——舊的 Service Worker 會持續控制頁面直到所有分頁關閉，處理不好會讓使用者長期停留在舊版本。這是漸進式網頁應用最常見的坑。

## 面試回答方式

先用「**發不發請求**」這個判準把強快取與協商快取分開，這比逐一介紹標頭清楚。接著給打包產物的標準策略：**帶內容雜湊的資源設一年強快取，HTML 入口設 no-cache**，並解釋為什麼這個組合天然沒有失效問題。主動澄清 **`no-cache` 不是不快取**而是每次驗證，`no-store` 才是完全不存——這是最常見的混淆。加分點有三個：`ETag` 在多台伺服器環境要基於內容雜湊產生否則永遠命中不了；`s-maxage` 讓 CDN 與瀏覽器可以設不同的存活時間；以及 Service Worker 是獨立的一層，強在可程式化但更新機制容易出錯。

## 講稿

我用一個判準把它分兩層，就是發不發請求。

強快取是 Cache-Control 的 max-age，在有效期內瀏覽器完全不發請求，直接用本地的。協商快取是過期之後，瀏覽器帶著 If-None-Match 去問伺服器，內容沒變就回 304，只傳標頭不傳內容。所以強快取是零往返，協商快取還是有一次往返，但省下傳輸量。

前端打包產物我的策略是內容雜湊加長期強快取。檔名帶上內容雜湊，設一年的 max-age 加 immutable。內容變了檔名就變，天然沒有失效的問題。而 HTML 入口檔要設 no-cache，因為它負責引用那些帶雜湊的檔名，必須每次拿最新的。

這裡我想澄清一個很常見的混淆，no-cache 不是不快取，它是可以存但每次都要驗證，還是會走協商快取。真正完全不存的是 no-store。

另外多台伺服器的環境要注意 ETag 的產生方式。如果是基於檔案的 inode 產生，不同機器給出的 ETag 不一樣，快取就永遠命中不了。我會用內容雜湊產生。

CDN 那邊我會用 s-maxage 設得比瀏覽器長，這樣要更新只要清 CDN，不用等使用者的瀏覽器過期。

## 常見追問

### 使用者反映「改了但沒生效」，可能是哪裡的快取？

**核心答案**：**由近到遠逐層排查**——瀏覽器記憶體與磁碟快取、Service Worker 快取、CDN 或反向代理快取、以及應用層自己的快取（例如前端的資料快取或後端的查詢快取）。判斷方式是看**回應標頭**：`age` 顯示在 CDN 中存了多久、`x-cache` 之類的自訂標頭顯示是否命中、以及狀態碼是 200（來自快取或來源）還是 304。

**詳細解析**：最容易被忽略的是 **Service Worker**，因為它在網路面板中的表現不明顯，而且即使強制重新整理也可能仍由它回應。排查時可以在開發工具中停用 Service Worker 再測一次。另一個常見來源是 **HTML 被快取了**——如果入口檔被 CDN 或瀏覽器快取，那麼即使新的 JS 已經部署，使用者拿到的 HTML 仍然指向舊的檔名。這正是「HTML 不要強快取」這條規則存在的原因。預防勝於排查：部署流程中應該**自動清除 CDN 對 HTML 的快取**，並確保資源檔名帶內容雜湊。

**面試回答方式**：給出由近到遠的四層排查順序，並說明看哪些回應標頭判斷。重點指出兩個容易忽略的來源：Service Worker（網路面板表現不明顯）與被快取的 HTML 入口檔。加分點是把結論導向預防——部署時自動清 HTML 的 CDN 快取。

### stale-while-revalidate 適合用在什麼場景？

**核心答案**：適合**變動不頻繁、但過期一小段時間可以接受**的內容——設定檔、商品分類、使用者的個人資料、以及多數的列表頁。它的行為是：在 `max-age` 內直接用快取；超過 `max-age` 但在 `stale-while-revalidate` 的時間窗內，**先立刻回傳過期的內容給使用者，同時在背景發請求更新快取**。使用者感受到的永遠是快取的速度，而資料最多落後一次請求的時間。

**詳細解析**：它不適合**強一致性要求**的內容——帳戶餘額、庫存數量、權限設定，這些顯示過期資料會造成實際問題。實務上同樣的模式也存在於前端資料層（SWR、React Query 這類函式庫的名稱就來自這個策略），差別在於一個發生在 HTTP 層、一個在應用層。應用層的版本更靈活，可以在拿到新資料時觸發 UI 更新，讓使用者看到內容「先出現再刷新」；HTTP 層的則對整個站台一致生效、不需要程式碼配合。兩者可以並用，判斷的關鍵是**這份資料過期一分鐘會不會造成問題**。

**面試回答方式**：說明它的行為（先回過期內容、背景更新）與適合的內容類型，並明確排除強一致性需求的資料。加分點是指出前端資料函式庫用的是同一個策略，比較 HTTP 層與應用層的差異，並給出判準——過期一分鐘會不會造成問題。

### 為什麼有些請求即使有快取還是會重新發送？

**核心答案**：常見原因有四個。**請求方法不是 GET**（POST 等有副作用的方法預設不快取）。**帶了不同的查詢參數或請求標頭**（快取的鍵包含完整 URL，多一個時間戳記參數就是不同的資源；`Vary` 標頭指定的請求標頭不同也會分開快取）。**使用者強制重新整理**（會帶上 `Cache-Control: no-cache` 略過本地快取）。**回應本身標明不可快取**或缺少必要的快取標頭。

**詳細解析**：`Vary` 是最容易造成困惑的一個——例如伺服器設了 `Vary: Accept-Encoding`，那麼支援不同壓縮格式的客戶端會有各自的快取項目，這是正確的；但如果誤設成 `Vary: User-Agent`，快取就會依瀏覽器版本切分成無數份，命中率趨近於零。另一個實務上的細節是**前端主動加時間戳記參數破壞快取**——這是有效但粗暴的手段，比較好的做法是用內容雜湊，因為時間戳記讓每次都是新資源，完全放棄了快取的好處。能指出這個差別，會顯示你理解快取設計而不只是會用。

**面試回答方式**：列出四個常見原因並各給一句說明。重點放在 `Vary` 的誤用（例如 `Vary: User-Agent` 讓命中率歸零）。加分點是比較「加時間戳記破快取」與「內容雜湊」的差別，指出前者等於放棄快取。
