# 題目

React 元件什麼時候會重新渲染？「重新渲染」等於「更新 DOM」嗎？

## 核心答案

**不等於**——這是理解 React 效能最重要的區分。「重新渲染」指的是**執行元件函式產生新的元素樹**，「更新 DOM」是 diff 之後才發生的實際變動。一個元件重新渲染但產生的結果和上次相同時，**DOM 完全不會被碰**。所以「重新渲染很多次」本身不一定是效能問題，真正的問題是**渲染函式本身很貴**或**連帶觸發大量子元件重新渲染**。觸發重新渲染的原因只有三個：**自身的 state 變更**、**接收到新的 props（實際上是父元件重新渲染）**、以及**使用的 context 值變更**。要注意第二點的真正含意——**父元件重新渲染時，子元件預設一律跟著重新渲染**，不管 props 有沒有變；`memo` 才會加上 props 的淺比較。理解這三個來源，就能解釋幾乎所有「為什麼這個元件一直在渲染」的疑問。

## 詳細解析

**狀態放的位置決定重新渲染的範圍**：把狀態放在越上層，重新渲染的範圍越大。一個常見的效能問題是把輸入框的值放在頁面層級的元件，導致每打一個字整頁重新渲染。解法是**把狀態下移**到真正需要它的最小範圍——通常這比加 `memo` 更有效也更簡單，因為它從根源縮小了範圍而不是事後阻擋。

**children 的參照穩定性是一個被低估的技巧**：如果一個會頻繁重新渲染的元件把不變的內容當作 `children` 傳入，那部分不會重新渲染——因為 `children` 是在**外層**建立的元素，參照沒變。這讓你不必用 `memo` 就能隔離重新渲染，是很優雅的結構性解法。

**context 會讓所有消費者重新渲染**：context 值一變，**所有使用它的元件都會重新渲染**，而且 `memo` 擋不住（context 的訂閱繞過了 props 比較）。所以把頻繁變動的值與穩定的值放進同一個 context 是常見的效能陷阱，解法是**拆分成多個 context**，讓消費者只訂閱自己需要的部分。另外傳入 context 的物件如果每次渲染都新建，等於每次都變更，要用 `useMemo` 穩定。

**批次更新的範圍**：在同一個事件處理器中多次呼叫 `setState` 會被合併成一次重新渲染。較新的 React 版本把批次擴大到非同步的情境（`setTimeout`、Promise 回呼中也會批次）。這意味著在同一個回合中讀取剛設定的 state 仍然是舊值——要基於前一個值計算時應該用函式形式，這也是避免過期閉包的標準做法。

**開發模式的重複渲染是刻意的**：嚴格模式下元件會被渲染兩次、副作用會被執行兩次再清理，目的是暴露不純的渲染與缺少清理的副作用。這在正式建置中不會發生，所以看到「渲染了兩次」不必急著優化，先確認是不是開發模式的行為。這個細節能避免大量無謂的排查。

## 面試回答方式

第一句就給出關鍵區分——**重新渲染不等於更新 DOM**，渲染結果相同時 DOM 完全不會被碰。接著列出觸發重新渲染的三個來源，並特別強調**父元件渲染時子元件預設一律跟著渲染**，這是最多人誤解的地方。談優化時**優先給結構性解法**：把狀態下移縮小範圍、把不變的內容當 children 傳入，這兩招不需要記憶化就能解決多數問題。加分點有三個：context 一變所有消費者都渲染且 `memo` 擋不住，解法是拆分 context；批次更新讓同回合讀到的是舊值，所以要用函式形式；以及嚴格模式的重複渲染是刻意的，不要誤判成效能問題。

## 講稿

我想先講一個很關鍵的區分，重新渲染不等於更新 DOM。重新渲染是執行元件函式產生新的元素樹，更新 DOM 是 diff 之後才發生的。如果產生的結果跟上次一樣，DOM 完全不會被碰。

所以渲染很多次本身不一定是問題。真正的問題是渲染函式本身很貴，或者連帶觸發一大堆子元件跟著渲染。

觸發的原因只有三個，自己的 state 變了、收到新的 props，還有用到的 context 變了。第二點要講清楚，父元件重新渲染的時候，子元件預設一律跟著渲染，不管 props 有沒有變。要加 memo 才會做 props 的淺比較。

不過我優化的第一選擇不是 memo，是結構性的調整。最常見的是把狀態下移，比如輸入框的值放在頁面層級，每打一個字整頁都渲染，把它移到真正需要的地方就解決了。另一招是把不變的內容當 children 傳進去，因為 children 是在外層建立的，參照不會變。

還有一件事要注意，context 一變所有消費者都會渲染，而且 memo 擋不住。所以頻繁變動的值不要跟穩定的值放在同一個 context。

## 常見追問

### `useEffect` 的依賴陣列該怎麼填？

**核心答案**：**填上 effect 中用到的所有外部值**——state、props、以及從它們衍生的函式與物件。這不是形式主義，而是因為 effect 是一個閉包，**捕獲的是那一次渲染的值**；漏掉依賴代表 effect 不會在該值變更時重新建立，於是它會一直讀到舊值。lint 規則能自動檢查，應該開啟並遵守它。

**詳細解析**：常見的困難是**依賴填齊之後 effect 執行太頻繁**——因為某個依賴是每次渲染都新建的物件或函式。這時的正確解法不是把它從依賴中刪掉（那是把 bug 藏起來），而是**穩定那個依賴**：用 `useCallback` 包函式、用 `useMemo` 包物件、或把不需要響應的值放進 `useRef`。另一個更根本的檢查是**這件事真的需要 effect 嗎**——依 props 計算出的值應該在渲染中直接算（或用 `useMemo`），回應使用者操作應該寫在事件處理器中，這兩類都不需要 effect。實務上很多 effect 相關的困難，根源是用 effect 做了不該用它做的事。

**面試回答方式**：先講原則（填齊所有用到的外部值）與原因（effect 是閉包，捕獲那次渲染的值）。接著處理「填齊後執行太頻繁」這個真實困難，強調解法是穩定依賴而非刪掉依賴。加分點是反問「這件事真的需要 effect 嗎」，並給出兩類不需要 effect 的情況。

### 為什麼 `setState` 之後立刻讀取還是舊值？

**核心答案**：因為 **state 在一次渲染中是固定的快照**。`setState` 是**排程一次更新**，不是立即修改變數；當前渲染的閉包中，那個 state 變數的值永遠是這一次渲染時的值。要基於前一個值計算，應該用**函式形式**（`setCount(c => c + 1)`），React 會把最新的值傳給你——這在連續多次更新時尤其重要，用直接的值會讓後面的覆蓋前面的。

**詳細解析**：理解「快照」這個心智模型能解釋一整族問題。事件處理器中讀到的值是**點擊當下那次渲染的值**；`setTimeout` 回呼中讀到的是**設定計時器時那次渲染的值**；`setInterval` 只註冊一次的話會永遠讀到第一次渲染的值。這些都不是 bug 而是閉包的正確行為。需要跨渲染讀到最新值的場景（例如在計時器中讀取當前狀態），正確工具是 `useRef`——它提供一個**參照穩定但內容可變**的容器，不受快照限制。能把這幾個現象用同一個「快照」模型統一解釋，比逐一記住現象有價值得多。

**面試回答方式**：用「state 是這次渲染的快照」一句話解釋，並給函式形式作為解法，強調連續多次更新時尤其重要。加分點是用快照模型統一解釋事件處理器、`setTimeout`、`setInterval` 讀到舊值的現象，並指出跨渲染讀最新值該用 `useRef`。

### 一個列表元件在輸入時很卡，你會怎麼排查？

**核心答案**：**先用開發者工具的分析器確認是誰在渲染、渲染多久**，不要憑猜測優化。常見的三種成因與對應解法是：**輸入框的狀態放太上層**導致整個列表跟著渲染（把狀態下移或用非受控元件）、**列表項目本身渲染昂貴**（用 `memo` 加穩定的 props，或簡化項目的渲染邏輯）、以及**列表太長**（用虛擬捲動只渲染可見範圍）。

**詳細解析**：如果資料量很大，**虛擬捲動幾乎是唯一有效的解法**——渲染一萬個 DOM 節點無論怎麼優化都會慢，只渲染可見的二十個才是根本解。另一個常被忽略的方向是**把更新標記為非緊急**：輸入框的值要立即反映（緊急），但依據輸入過濾的列表可以稍晚（非緊急），React 的並行特性提供了對應的機制讓輸入保持流暢。最後要檢查的是**每次輸入是否觸發了不必要的重新計算**——在渲染中做排序或過濾大陣列而沒有記憶化，是很常見的隱藏成本。排查順序建議是：先分析器定位、再判斷是範圍問題還是單項成本問題、最後才考慮虛擬化。

**面試回答方式**：強調先用分析器定位而非憑猜測，並給出三種成因與對應解法。指出資料量大時虛擬捲動是根本解。加分點是提到把過濾更新標記為非緊急以保持輸入流暢，以及檢查渲染中是否有未記憶化的大陣列運算。
