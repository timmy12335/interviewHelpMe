# 題目

前端的資料該怎麼快取？什麼時候該讓它失效？

## 核心答案

**核心的模型是「快取的資料有兩個維度：新鮮度與存在性」**。**新鮮（fresh）的資料直接用**；**過期（stale）但存在的資料可以先顯示再背景更新**（stale-while-revalidate）；**不存在的才需要等待載入。**

**這個模型讓多數的載入畫面消失**——**因為使用者第二次訪問同一個頁面時，看到的是快取的內容而更新在背景進行**；**這是 TanStack Query、SWR 這類函式庫的核心價值。**

**失效的四種觸發**：**時間到期**（設定的 staleTime）、**視窗重新聚焦**（使用者切回分頁時）、**網路重新連線**、**以及變更操作後的明確失效**（送出一筆訂單後讓訂單列表失效）。

**最需要判斷的是「staleTime 該設多久」**——**依資料的變化頻率與過期的代價而定**：**幾乎不變的設定資料可以很長、會被別人修改的協作資料要短、而涉及金額或庫存的可能不該快取**。

## 詳細解析

**「不要把伺服器資料放進客戶端的全域狀態」**：把 API 回應複製進 Redux 或 Zustand——**你就要自己處理快取、失效、重試、以及多個元件同時請求的去重**；**而那些正是資料獲取函式庫已經解決的問題**。**這個「伺服器狀態與客戶端狀態分開管理」的區分，是近年前端狀態管理最重要的觀念轉變。**

**「請求的去重與競態」是容易被忽略的正確性問題**：兩個元件同時要同一筆資料應該只發一次請求——**而如果使用者快速切換篩選條件，先發的請求可能後回來並覆蓋掉正確的結果**；**這個競態在手寫的 fetch 中很常見，而函式庫用「以最新的請求為準」或者 AbortController 處理它**。

**「快取的鍵設計決定了失效的粒度」**：如果所有的使用者資料都用同一個鍵——**那更新一個使用者要讓全部失效**；**而如果鍵包含了查詢的參數（`['users', { page: 2, filter: 'active' }]`），就能精確地失效相關的部分**。**設計鍵的原則是「讓它反映資料的依賴關係」。**

**「離線與持久化」是另一層決定**：把快取寫進 `localStorage` 或 IndexedDB 讓重新整理後仍然有內容——**但要處理版本不相容（結構變了的舊快取）與敏感資料（不該持久化的個人資訊）**；**而快取的持久化也意味著使用者可能看到很舊的資料，所以要搭配明確的更新提示。**

## 面試回答方式

先給核心模型（**新鮮度與存在性兩個維度**）與它帶來的體驗改變，再列出失效的四種觸發與 staleTime 的判斷依據。加分點有四個：**不要把伺服器資料放進客戶端全域狀態**——**這是近年最重要的觀念轉變**；**請求的去重與競態**是正確性問題而非只是效能；**快取的鍵設計決定失效的粒度**；以及**離線與持久化**的額外考量（版本不相容、敏感資料、很舊的資料）。

## 講稿

核心模型是快取的資料有兩個維度，新鮮度跟存在性。新鮮的直接用，過期但存在的可以先顯示再背景更新，不存在的才需要等待。

這個模型讓多數的載入畫面消失，因為使用者第二次進同一個頁面時看到的是快取內容，更新在背景進行。

失效我會用四種觸發。時間到期、視窗重新聚焦、網路重新連線、還有變更操作之後的明確失效。比如送出一筆訂單就讓訂單列表失效。

而我覺得最重要的觀念是不要把伺服器資料放進客戶端的全域狀態。把 API 回應複製進 Redux，你就要自己處理快取、失效、重試、還有多個元件同時請求的去重。那些正是資料獲取函式庫已經解決的問題。

另外有一個容易被忽略的正確性問題，就是競態。使用者快速切換篩選條件的時候，先發的請求可能後回來覆蓋掉正確的結果。手寫 fetch 很常見這個問題。

## 常見追問

### staleTime 和 cacheTime 有什麼不同？

**核心答案**：**staleTime 是「多久之後算過期」，cacheTime（或 gcTime）是「沒有元件使用之後保留多久才回收」**。前者控制何時觸發背景更新——**後者控制記憶體**；**兩者常被混淆但作用完全不同。**

**詳細解析**：**「典型的搭配是 staleTime 短而 cacheTime 長」**：例如 staleTime 設 30 秒、cacheTime 設 5 分鐘——**於是使用者離開頁面再回來時，仍然能立刻看到之前的內容（因為還在快取中），同時因為已經過期所以觸發背景更新**；**這正是「即時顯示加上背景刷新」的體驗來源**。**而如果 cacheTime 太短，離開再回來就會看到載入畫面**——**那就失去了快取的主要價值**。**理解這個搭配之後，調整這兩個值就從試錯變成有依據的決定**；**而一個實用的起點是「staleTime 依資料的變化頻率設定，cacheTime 設成使用者可能在幾分鐘內回來的時間」**。

**面試回答方式**：給清楚的定義區分（**何時算過期 vs 沒人用之後保留多久**）並指出兩者常被混淆。核心加分點是**典型的搭配是 staleTime 短而 cacheTime 長**並說明它產生的體驗（**離開再回來立刻看到內容同時觸發背景更新**），以及 cacheTime 太短的後果。收在起點建議：**staleTime 依變化頻率、cacheTime 設成使用者可能回來的時間**。

### 分頁與無限捲動的快取怎麼處理？

**核心答案**：**把每一頁當成獨立的快取項，但保留頁與頁之間的關係**。分頁時，切換到第二頁不該讓第一頁的快取消失——**於是回到第一頁時是即時的**；**而無限捲動則是把多頁的結果串接成一個邏輯上的清單，新增的頁面追加進去。**

**詳細解析**：**「分頁切換時的閃爍有一個好解法」**：切到下一頁時如果直接顯示載入狀態，版面會塌陷再撐開——**而「保留上一頁的資料直到新資料到達」（TanStack Query 的 placeholderData 或 keepPreviousData）能讓過渡平順**；**只需要加一個「更新中」的視覺提示**。**這個小改動對體驗的影響很大**。**而無限捲動的難點在於「資料變更後的一致性」**——**如果中間插入或刪除了一筆，後續頁面的偏移就錯了（可能重複或遺漏）**；**用游標分頁（cursor-based）而非偏移分頁（offset-based）能避免這個問題**，**而這是一個需要後端配合的決定**。

**面試回答方式**：給處理原則（**每頁獨立快取但保留關係**）並說明分頁與無限捲動的不同。核心加分點是**分頁切換時保留上一頁資料直到新資料到達**這個小改動與它對體驗的影響，以及**無限捲動的難點是資料變更後的一致性**——**偏移分頁在中間插入或刪除時會重複或遺漏**。收在解法：**用游標分頁而非偏移分頁，這需要後端配合**。

### 多個分頁同時開著時怎麼同步？

**核心答案**：**用 `BroadcastChannel` 或 `storage` 事件在分頁之間廣播**。當一個分頁執行了變更操作——**它廣播一個訊息讓其他分頁的相關快取失效**；**而登出這類操作尤其需要同步，否則使用者在一個分頁登出後，另一個分頁仍然顯示已登入的介面。**

**詳細解析**：**「不同步造成的問題往往是安全或正確性的」**：登出後其他分頁還能操作、在一個分頁改了設定而另一個分頁用舊的設定送出請求、或者在兩個分頁編輯同一份資料造成互相覆蓋——**這些不只是體驗問題**；**所以「哪些狀態必須跨分頁一致」值得明確列出**（認證狀態、權限、以及正在編輯的資源）。**而實作上，`BroadcastChannel` 比 `storage` 事件乾淨**（後者是 localStorage 的副作用且不會在同一個分頁觸發）；**但要注意它不跨來源也不跨瀏覽器設定檔**。**對於編輯衝突，更完整的做法是在後端用版本號或 ETag 檢查**——**因為跨分頁的同步無法涵蓋跨裝置的情況**。

**面試回答方式**：給機制（`BroadcastChannel` 或 `storage` 事件）並用登出這個例子說明必要性。核心加分點是指出**不同步造成的問題往往是安全或正確性的**並列出三類，以及**「哪些狀態必須跨分頁一致」值得明確列出**。收在限制：**跨分頁同步無法涵蓋跨裝置**，**所以編輯衝突更完整的做法是後端用版本號或 ETag 檢查**。
