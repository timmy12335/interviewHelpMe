# 題目

樣式沒生效的時候，你會怎麼判斷是哪一條規則贏了？

## 核心答案

決定哪條規則生效的順序是：來源與重要性 → 選擇器優先權 → 出現順序。**優先權**用三組數字比較——**ID 選擇器**、**class 與屬性選擇器與偽類**、**元素選擇器與偽元素**，由左到右依序比較，前面大的直接贏，**不會進位**（十個 class 也贏不過一個 ID）。行內樣式高於任何選擇器，`!important` 又高於行內樣式。優先權完全相同時，**後出現的贏**。實務上排查的方法很單純：**打開開發工具看樣式面板**——被覆蓋的規則會被劃掉，往上找到生效的那一條，就知道是誰贏了。真正該記住的不是怎麼贏過別人，而是盡量讓所有規則保持在相近的低優先權——大量使用 ID 選擇器與 `!important` 會讓樣式系統變成優先權的軍備競賽，每個新需求都要用更高的優先權才蓋得過，最後無法維護。

## 詳細解析

**!important 是最後手段而非工具**：它會跳過正常的層疊規則，導致後續任何人要覆蓋它都得再用一次 `!important`。少數合理的使用場景是**覆蓋無法修改的第三方樣式**，以及某些**工具類樣式**刻意要贏過元件樣式。除此之外出現 `!important` 通常代表選擇器設計出了問題。要注意的例外是：在**動畫的關鍵影格**中 `!important` 會被忽略，而**使用者樣式表**的 `!important` 優先權高於作者樣式（無障礙考量）。

**:is()、:where() 對優先權的影響不同**：`:where()` 的優先權**永遠是零**，裡面放什麼都不影響，非常適合寫預設樣式或重置——因為使用者的任何規則都能輕易覆蓋它。`:is()` 則採用**參數中優先權最高的那一個**。這對差異在設計元件庫時很有用：用 `:where()` 提供預設值，讓使用者不必和你比優先權。

**現代的層疊層讓優先權可控**：`@layer` 允許明確宣告樣式層的順序（例如重置、第三方、元件、工具），層的順序優先於選擇器優先權——後面的層永遠贏過前面的層，不管選擇器多具體。這從根本上解決了「第三方樣式的選擇器太具體，我必須寫得更具體」的問題，是目前最值得採用的樣式組織方式。

繼承與預設值不參與優先權比較：只有**直接套用到該元素**的規則才比優先權。父元素繼承下來的樣式永遠輸給任何直接套用的規則，即使父元素的選擇器很具體。這解釋了一個常見困惑：明明在父層寫了很具體的顏色規則，卻被子元素上一個簡單的元素選擇器蓋掉。

**方法論比規則重要**：實務上避免優先權問題的做法是**扁平化選擇器**——用單一 class 描述元件的狀態（例如 BEM 這類命名慣例，或 CSS Modules、CSS-in-JS 這類作用域方案），讓幾乎所有規則的優先權都是「一個 class」。這樣層疊就退化成單純的「後面的贏」，容易預測也容易維護。

## 面試回答方式

先給判定順序（來源與重要性、優先權、出現順序），再說明優先權的三組數字**不會進位**——十個 class 也贏不過一個 ID。實務排查直接說用開發工具看樣式面板，被劃掉的就是輸的，這比背規則實際。接著把重點轉向**方法論**：真正該做的是讓所有規則維持在相近的低優先權，避免優先權的軍備競賽。加分點有三個：`:where()` 的優先權永遠為零，適合寫可被輕易覆蓋的預設樣式；`@layer` 讓層的順序優先於選擇器優先權，從根本解決第三方樣式難以覆蓋的問題；以及繼承來的樣式永遠輸給直接套用的規則。

## 講稿

判定順序是先看來源跟重要性，再看選擇器優先權，最後才看出現順序。

優先權是三組數字，ID 一組、class 跟屬性跟偽類一組、元素跟偽元素一組，由左往右比。重點是不會進位，十個 class 也贏不過一個 ID。行內樣式又高於選擇器，important 再高於行內。

不過實務上我不會用算的。我直接打開開發工具看樣式面板，被覆蓋的規則會劃掉，往上找到沒被劃掉的那一條就知道是誰贏了。

我覺得真正該記的不是怎麼贏過別人，而是盡量讓所有規則保持在差不多的低優先權。大量用 ID 選擇器跟 important，會讓樣式變成優先權的軍備競賽，每個新需求都要更高的優先權才蓋得過，最後就沒辦法維護了。

所以我的做法是扁平化選擇器，用單一 class 描述元件跟它的狀態，讓幾乎所有規則都是一個 class 的優先權，層疊就退化成單純的後面贏，好預測也好維護。

現在還有兩個工具很有用。where 這個偽類的優先權永遠是零，很適合寫預設樣式。還有層疊層，可以明確宣告層的順序，而且層的順序優先於選擇器優先權。

## 常見追問

### 為什麼有時候寫了樣式在開發工具裡完全看不到？

**核心答案**：代表這條規則**根本沒有套用到這個元素**，而不是被覆蓋。常見原因有四個：**選擇器沒有匹配到**（拼字錯誤、結構與想像的不同、動態加上的 class 名稱不符）、**CSS 檔案沒有被載入**（路徑錯誤、建置沒有包含）、語法錯誤導致整條規則被丟棄（前一條規則少了分號或大括號會影響後續）、以及**屬性名稱或值不合法**（開發工具通常會標示無效的宣告）。

**詳細解析**：排查順序建議是：先在元素上確認 class 是否真的存在（動態 class 特別容易出錯）、再用開發工具搜尋該選擇器確認檔案有載入、最後檢查該規則區塊前後是否有語法問題。另一類容易忽略的原因是**作用域方案改寫了 class 名稱**——CSS Modules 會把 class 編譯成帶雜湊的名稱，如果你在別處硬寫原始名稱就不會匹配。同樣地，某些 CSS-in-JS 方案產生的樣式是動態插入的，順序可能與你預期的不同。理解你所用的工具**實際產生了什麼**，是這類問題最根本的排查能力。

**面試回答方式**：先區分「沒套用」與「被覆蓋」這兩種完全不同的狀況，並列出四個常見原因。給出具體的排查順序。加分點是提到作用域方案改寫 class 名稱、以及 CSS-in-JS 的插入順序，強調要理解工具實際產生了什麼。

### @layer 實務上要怎麼分層？

**核心答案**：常見的分法是由低到高：**`reset`**（瀏覽器預設值的重置）、**`base`**（元素層級的基礎樣式，例如標題與段落）、**`third-party`**（引入的第三方樣式）、**`components`**（自己的元件）、**`utilities`**（工具類，需要贏過元件）。順序在第一次宣告 `@layer` 時就決定，之後往任何一層追加樣式都不影響層的排序。

**詳細解析**：這個機制最大的價值是**把第三方樣式關進一層**——不管它的選擇器寫得多具體，只要它在較低的層，你的元件層就能用簡單的 class 覆蓋它，不必再打優先權戰爭。要注意兩個細節：**未分層的樣式優先權最高**（在所有具名層之上），所以遷移時要留意還沒分層的舊樣式會蓋過新的層；以及 **`!important` 在分層下的順序會反轉**——帶 `!important` 的宣告中，**較低的層反而優先**，這是刻意的設計，讓重置層能用 `!important` 強制某些基礎規則。這個反轉很反直覺，是實際使用時的主要陷阱。

**面試回答方式**：給出五層的典型分法與順序決定的時機。重點說明它解決第三方樣式難覆蓋的問題。加分點是點出兩個陷阱：未分層的樣式優先權最高（影響遷移）、以及 `!important` 在分層下順序反轉這個反直覺的設計。

### CSS-in-JS 和原生 CSS 你會怎麼選？

**核心答案**：看**團隊規模與樣式的動態程度**。CSS-in-JS 的優勢是**天然的作用域**（不會有全域命名衝突）、**與元件同生共死**（刪元件時樣式一起走，不會累積死樣式）、以及**能用 JavaScript 的值決定樣式**。代價是**執行期成本**（部分方案要在瀏覽器中產生樣式）與**打包體積**。原生 CSS 加上 CSS Modules 這類作用域方案能拿到大部分好處而沒有執行期成本，是目前很務實的選擇。

**詳細解析**：這個領域近年的趨勢是**往零執行期成本移動**——編譯期就把樣式抽成靜態 CSS 檔案的方案（以及原子化 CSS 工具）逐漸取代執行期產生樣式的做法，因為後者對伺服器端渲染與 Core Web Vitals 都有負擔。選擇時值得問三個問題：樣式需不需要依賴執行期的值（多數情況用 CSS 變數就能解決）、**團隊對命名慣例的紀律如何**（紀律好的話原生 CSS 加慣例就夠）、以及**伺服器端渲染的需求**（執行期方案在這裡最麻煩）。能把選擇連結到這三個具體問題，比表達個人偏好有說服力。

**面試回答方式**：給出雙方的優勢與代價，並推薦 CSS Modules 這類零執行期成本的折衷。加分點是指出趨勢往編譯期方案移動的原因（伺服器端渲染與效能負擔），並給出三個決策問題，避免變成偏好之爭。
