# 題目

在幾乎所有人都開著 JavaScript 的今天，漸進增強還有意義嗎？

## 核心答案

**有，但理由變了**。它現在的價值不是「支援關閉 JavaScript 的使用者」——**而是「當 JavaScript 還沒載入、載入失敗、或者執行出錯時，頁面仍然可用」**；**而這三種情況在真實世界中相當常見**（網路不穩、CDN 故障、瀏覽器擴充功能衝突、以及一個未捕捉的錯誤讓整個應用白畫面）。

**具體的實踐是「讓核心功能建立在平台的原生能力上，再用 JavaScript 增強」**：**表單用 `<form action method>` 讓它在沒有 JS 時也能提交**、**連結用 `<a href>` 讓它能被右鍵開新分頁與被爬蟲跟隨**、**而 JavaScript 負責攔截並提供更好的體驗**（不重整頁面、即時驗證、樂觀更新）。

**這個做法的額外收益很大**：**更好的無障礙**（原生元素自帶語意）、**更好的 SEO**、**更快的首次可用時間**、**以及在錯誤發生時的優雅降級。**

**而它不適用的場景也很明確**——**本質上需要 JavaScript 的應用**（繪圖工具、線上遊戲、即時協作編輯器）；**在那些情況下應該做的是清楚的錯誤處理而非勉強降級。**

## 詳細解析

**「Remix 與 Next.js 的 Server Actions 讓這件事重新變得容易」**：過去在單頁應用中要做漸進增強很麻煩——**而這些框架讓表單天然地在伺服器端有一個對應的處理器，JavaScript 載入後才升級為非同步提交**；**於是漸進增強從「額外的工作」變成「預設的行為」**。**這是一個很好的例子說明「框架的預設值決定了大部分專案的品質」。**

**「JavaScript 失敗的機率比想像的高」**：有研究指出約有百分之一的頁面瀏覽中 JavaScript 沒有正確執行——**原因包括網路逾時、企業代理的改寫、瀏覽器擴充功能的干擾、以及舊裝置上的語法不支援**；**在一個有百萬次瀏覽的網站上，那是一萬次失敗的體驗**。**這個數字讓「反正大家都有 JS」這個假設站不住腳。**

**「錯誤邊界是漸進增強的現代形式」**：讓一個元件的錯誤不影響整個頁面——**這和「JS 失效時頁面仍可用」是同一個思路的不同層次**；**共同的原則是「不要讓單點失敗導致全面失敗」**。

**「不要為了漸進增強犧牲主要體驗」**：如果為了支援無 JS 的情況而讓有 JS 的體驗變差——**那就本末倒置了**；**正確的做法是「基礎版本可用，增強版本優秀」，而非「兩個版本都平庸」**。

## 面試回答方式

先給明確的答案（**有，但理由變了**）並說明新的理由與三種常見的失敗情況，再給具體的實踐與額外收益，最後說明不適用的場景。加分點有四個：**現代框架讓它從「額外的工作」變成「預設的行為」**，**而框架的預設值決定了大部分專案的品質**；**JavaScript 失敗的機率約百分之一**——**在百萬次瀏覽上是一萬次失敗的體驗**；**錯誤邊界是漸進增強的現代形式**；以及**不要為了漸進增強犧牲主要體驗**。

## 講稿

有意義，但理由變了。它現在的價值不是支援關掉 JavaScript 的使用者，而是當 JavaScript 還沒載入、載入失敗、或者執行出錯的時候，頁面仍然可用。

而這三種情況在真實世界中相當常見。有研究指出大概百分之一的頁面瀏覽中 JavaScript 沒有正確執行，原因包括網路逾時、企業代理改寫、擴充功能干擾。在一個有百萬瀏覽的網站上，那是一萬次失敗的體驗。這個數字讓反正大家都有 JS 這個假設站不住腳。

具體的實踐是讓核心功能建立在平台的原生能力上。表單用原生的 action 跟 method，連結用 a 加 href，然後 JavaScript 負責攔截並提供更好的體驗。

而這樣做的額外收益很大。原生元素自帶語意所以無障礙更好，SEO 更好，首次可用時間也更快。

不過它不適用於本質上需要 JavaScript 的應用，像繪圖工具或者即時協作編輯器。那些情況該做的是清楚的錯誤處理而不是勉強降級。

## 常見追問

### 沒有 JavaScript 時表單怎麼運作？

**核心答案**：**瀏覽器會用 `action` 指定的網址與 `method` 指定的方法送出，然後導航到回應的頁面**。所以伺服器端需要一個能處理一般表單提交（`application/x-www-form-urlencoded`）並回傳完整 HTML 的路徑——**而在有 JavaScript 時，前端攔截提交並改用 fetch 送出，處理回應後更新畫面而不導航。**

**詳細解析**：**「同一個端點服務兩種模式」是關鍵的設計**：伺服器端根據請求的標頭（`Accept` 或者一個自訂的標記）決定回傳 HTML 還是 JSON——**於是只需要維護一套業務邏輯與驗證**；**而如果分成兩個端點，那驗證規則會漸漸不一致**。**這正是 Remix 的 action 與 Next.js 的 Server Actions 在做的事**。**而錯誤的處理也要對應**：**無 JS 時錯誤透過重新渲染的頁面呈現（帶著使用者剛才輸入的值，這一點常被忘記）**；**有 JS 時則在原地顯示**。**保留使用者輸入這個細節，是無 JS 降級能不能真的可用的分水嶺**——**因為讓使用者重填整張表單，實際上等於不可用**。

**面試回答方式**：說明原生表單提交的機制與伺服器端需要提供什麼。核心加分點是**同一個端點服務兩種模式**——**根據請求標頭決定回傳 HTML 還是 JSON，於是只維護一套邏輯與驗證**。收在細節：**無 JS 時錯誤要帶著使用者剛才輸入的值重新渲染**——**這是降級能不能真的可用的分水嶺，因為讓使用者重填整張表單等於不可用**。

### 這和「行動優先」是同一種思路嗎？

**核心答案**：**是，都是「從最受限的情況開始，再往上增強」**。行動優先從最小的螢幕開始加樣式——**漸進增強從最基本的能力開始加功能**；**共同的優點是「基礎的情況一定被照顧到」，而反過來（先做完整版再往下砍）常常會在受限的情況下留下破洞。**

**詳細解析**：**「這個模式在很多地方重複出現」**：資料庫的預設值設計（先定義最小可用的資料，額外的欄位可選）、API 的設計（先定義最小的必要參數）、以及功能的發布（先上最小可用版本再迭代）——**共同的結構是「讓退化的路徑是預設的，而增強是可選的疊加」**；**於是任何一層的失敗都只損失那一層的價值而非全部**。**這在系統設計中對應到「優雅降級」的原則**——**而它與「先做完整版再砍」的差別在於，前者的每一層都被獨立驗證過是可用的，後者則只驗證了完整版**。**理解這個共通的結構，能讓你在遇到新問題時知道該從哪個方向設計。**

**面試回答方式**：給明確的答案（**是，都是從最受限的情況開始**）並對比兩者的具體做法與共同優點。核心加分點是指出**這個模式在很多地方重複出現**並列舉（資料庫預設值、API 參數、功能發布），抽象出共同結構：**讓退化的路徑是預設的，增強是可選的疊加**。收在關鍵差別：**每一層都被獨立驗證過是可用的，而「先做完整版再砍」只驗證了完整版**。

### 伺服器端渲染就等於漸進增強嗎？

**核心答案**：**不等於**。SSR 讓內容更早出現——**但如果所有的互動都依賴 JavaScript（按鈕是綁 onClick 的 div、連結是 JS 導航）**，**那在 JS 失效時使用者只能看不能用**；**而漸進增強要求的是「互動也有原生的退路」。**

**詳細解析**：**「看得到但點不動」其實比什麼都看不到更令人困惑」**：至少一個空白頁或者錯誤訊息會讓使用者知道出問題了——**而一個看起來完整卻毫無反應的頁面，會讓人反覆點擊並認為是自己的問題**；**所以 SSR 加上「hydration 完成前禁用互動元素並顯示載入狀態」，是比放任更誠實的做法**。**而真正的漸進增強會讓那些按鈕在 hydration 前就能用（因為它們是真的表單提交或連結）**——**這個差別在慢速網路上非常明顯**。**在面試中能區分「SSR 解決了什麼」與「漸進增強解決了什麼」，展示的是對這兩個常被混為一談的概念的清楚理解。**

**面試回答方式**：給明確的區分（**SSR 讓內容更早出現，但互動仍依賴 JS**）。核心加分點是**「看得到但點不動」比什麼都看不到更令人困惑**——**使用者會反覆點擊並認為是自己的問題**，並給出誠實的中間做法（hydration 完成前禁用並顯示載入狀態）。收在真正的差別：**漸進增強讓那些按鈕在 hydration 前就能用，因為它們是真的表單或連結**——**這在慢速網路上非常明顯**。
