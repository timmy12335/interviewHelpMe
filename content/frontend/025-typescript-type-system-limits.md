# 題目

TypeScript 能防止哪些錯誤？哪些它其實防不了？

## 核心答案

**它擋得住的是「編譯期能推導出來的不一致」**——**傳錯參數、存取不存在的屬性、忘記處理某個聯合型別的分支、以及重構時漏改的呼叫點**；**這些是它最大的價值來源，而重構的安全性往往比寫新程式碼時的提示更重要。**

**它擋不住的有四類，而且都很常見**：**執行期進來的資料**（API 回應、`localStorage`、URL 參數——你宣告了型別但沒有人驗證它）；**`any` 與型別斷言**（`as` 會直接關掉檢查）；**空值以外的邏輯錯誤**（型別對但語意錯，例如把 `userId` 傳給 `orderId`，兩者都是 `string`）；**以及第三方型別定義與實際行為不符。**

**所以最重要的判斷是「型別安全的邊界在哪」**——**在邊界上做執行期驗證**（用 Zod 之類的 schema 工具），**邊界內才能真正信任型別**；**沒有這一層的專案，型別給的是一種虛假的安心。**

## 詳細解析

**「API 回應是最大的漏洞」**：`const user: User = await res.json()` 這一行沒有任何檢查——**`json()` 回傳的是 `any`，而你只是給它貼了一個標籤**；**於是後端改了欄位名稱，前端會在使用時才炸掉，而且錯誤訊息通常離現場很遠**。**用 schema 驗證在邊界上解析，能讓錯誤在進入的那一刻就被抓到並帶著清楚的訊息**；**這個改變的成本不高而它消除了整整一類的線上問題。**

**「品牌型別解決語意混淆」**：`type UserId = string & { readonly __brand: 'UserId' }`——**於是把 `OrderId` 傳給需要 `UserId` 的地方會被拒絕**；**這個技巧在有多種識別碼的系統中價值很高**，**代價是需要一個轉換函式來建立它**。

**「`as` 應該被當成一個警訊而非工具」**：每個型別斷言都是「我告訴編譯器相信我」——**而多數的斷言其實可以用型別守衛（`is` 函式）或者更好的型別設計取代**；**在程式碼審查中把 `as` 當成需要解釋的東西，是一個有效的慣例。**

**「嚴格模式的設定值決定了實際的保護力」**：關掉 `strictNullChecks` 的 TypeScript，防不住最常見的一類執行期錯誤——**而 `noUncheckedIndexedAccess` 這類較少開啟的選項，能抓到陣列存取的越界假設**；**所以「用了 TypeScript」和「型別安全」之間，隔著一份設定檔。**

## 面試回答方式

先分兩邊回答（擋得住編譯期的不一致、擋不住四類問題）並各給具體的例子，然後收在核心判斷：**型別安全的邊界在哪，而邊界上需要執行期驗證**。加分點有四個：**API 回應是最大的漏洞**——**`json()` 回傳 `any`，你只是貼了標籤**；**品牌型別解決語意混淆**；**`as` 應該被當成警訊而非工具**；以及**嚴格模式的設定值決定實際的保護力**，**「用了 TypeScript」和「型別安全」之間隔著一份設定檔**。

## 講稿

它擋得住的是編譯期能推導出來的不一致。傳錯參數、存取不存在的屬性、還有重構時漏改的呼叫點。而我覺得重構的安全性，價值比寫新程式碼時的提示更大。

它擋不住的有四類。第一類是執行期進來的資料，這是最大的漏洞。你寫 const user 冒號 User 等於 await res.json，這一行沒有任何檢查。json 回傳的是 any，你只是給它貼了一個標籤。後端改了欄位名稱，前端會在使用的時候才炸，而且錯誤離現場很遠。

第二類是 as 跟 any，型別斷言會直接關掉檢查。第三類是型別對但語意錯，比如把訂單編號傳給需要使用者編號的地方，兩個都是字串。第四類是第三方的型別定義跟實際行為不符。

所以我覺得最重要的判斷是型別安全的邊界在哪。在邊界上用 schema 做執行期驗證，邊界內才能真正信任型別。沒有這一層的專案，型別給的是一種虛假的安心。

## 常見追問

### 型別體操寫到很複雜值得嗎？

**核心答案**：**多數情況不值得**。複雜的條件型別與遞迴型別能表達很精巧的約束——**但它們的可讀性差、編譯速度慢、錯誤訊息幾乎無法閱讀**；**而如果只有作者看得懂，那份型別的維護成本會超過它防止的錯誤。**

**詳細解析**：**「判斷的標準是誰會讀到那個錯誤訊息」**：一個複雜的泛型在型別不符時，可能產生三十行的錯誤訊息——**而使用者要花十分鐘才能看懂哪裡錯了**；**這時候一個簡單的型別加上執行期檢查，體驗反而更好**。**而例外是函式庫的作者**——**因為那個成本由少數人承擔而收益由所有使用者享受**；**在應用程式碼裡，這個投資報酬率通常是反過來的**。**一個實用的原則是「應用程式碼裡的型別應該是描述性的而非證明性的」**——**它的工作是說明資料長什麼樣，而不是在型別系統裡證明某個不變式**。

**面試回答方式**：給明確的判斷（**多數情況不值得**）並列出代價（可讀性、編譯速度、錯誤訊息）。核心加分點是**判斷的標準是誰會讀到那個錯誤訊息**，並指出函式庫作者是例外（**成本由少數人承擔而收益由所有使用者享受**）。收在原則：**應用程式碼裡的型別應該是描述性的而非證明性的**。

### 為什麼 TypeScript 的型別在執行期完全消失？

**核心答案**：**因為它的設計目標是「不改變 JavaScript 的執行語意」**——**型別只在編譯期存在，編譯後被完全擦除**；**這讓它能無縫地與現有的 JavaScript 生態共存，代價是無法在執行期做型別檢查（沒有 `if (x instanceof MyInterface)`）。**

**詳細解析**：**「擦除的實際後果」有幾個要注意的地方**：**泛型的型別參數在執行期不可用**（所以無法寫 `new T()`）；**`instanceof` 只對 class 有效而對 interface 無效**；**以及裝飾器或依賴注入這類需要執行期型別資訊的場景，需要額外的機制**（例如 `reflect-metadata`）。**而這個設計選擇的好處在生態上是決定性的**——**任何 JavaScript 函式庫都能被使用，編譯輸出是乾淨的 JavaScript，而移除 TypeScript 不會改變行為**；**相對地，一個會改變執行語意的型別系統，會把使用者鎖進整個工具鏈**。**理解這個取捨，能解釋 TypeScript 幾乎所有看起來奇怪的設計。**

**面試回答方式**：給設計目標（**不改變 JavaScript 的執行語意**）與代價。核心加分點是列出**擦除的實際後果**（泛型參數不可用、`instanceof` 對 interface 無效、需要執行期型別資訊的場景要額外機制）。收在取捨：**這個選擇在生態上是決定性的**——**任何 JS 函式庫都能用、輸出乾淨、移除不改變行為**；**而理解它能解釋 TypeScript 幾乎所有看起來奇怪的設計**。

### 前後端怎麼保持型別一致？

**核心答案**：**用單一來源生成而非手動維護兩份**。可行的方式包括**從 OpenAPI 規格生成前端型別**、**用 GraphQL 的 schema 生成**、**在單一儲存庫中共享型別定義**、**或者用 tRPC 這類直接從後端的型別推導出前端的方案**；**手寫兩份一定會漂移，那只是時間問題。**

**詳細解析**：**「生成的型別仍然需要執行期驗證」是一個容易被忽略的點**：即使型別是從後端生成的——**執行期收到的資料仍然可能不符**（部署順序不同步、快取的舊回應、代理層改寫）；**所以生成解決的是「兩邊的定義一致」，而驗證解決的是「實際的資料符合定義」**，**兩者不能互相取代**。**而一個實用的做法是「在開發與測試環境開啟嚴格的驗證並記錄不符，在正式環境用寬鬆的模式（記錄但不中斷）」**——**這樣能發現契約漂移而不至於因為一個多餘的欄位就讓頁面壞掉**；**這個「嚴格偵測、寬鬆執行」的模式在契約管理中很實用**。

**面試回答方式**：給幾種單一來源的方案並指出**手寫兩份一定會漂移**。核心加分點是**生成的型別仍然需要執行期驗證**——**生成解決「定義一致」而驗證解決「資料符合定義」，兩者不能互相取代**，並列出仍會不符的原因。收在實用做法：**開發環境嚴格驗證、正式環境記錄但不中斷**——**這個「嚴格偵測、寬鬆執行」的模式在契約管理中很實用**。
