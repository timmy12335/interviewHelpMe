# 題目

HPA 按 CPU 擴縮不夠用時該怎麼辦？擴縮抖動怎麼處理？

## 核心答案

**CPU 不夠用的原因是「它常常不是真正的瓶頸」**——**一個等待下游回應的服務 CPU 很低但已經飽和**，**一個記憶體吃緊的服務 CPU 也不高**。**這時要用能反映真實負載的指標**。

**三種指標來源**。**Resource**（CPU、記憶體，內建）。**Pods / Object**（自訂指標，例如每個 Pod 的 QPS、佇列長度——**需要 metrics adapter 把 Prometheus 的指標暴露給 HPA**）。**External**（叢集外的指標，例如雲端佇列的訊息數）。**佇列長度是最直觀且最常用的自訂指標**——**它直接反映積壓**。

**擴縮抖動用 `behavior` 欄位處理**（1.18 之後）：**分別為 `scaleUp` 與 `scaleDown` 設定 `stabilizationWindowSeconds` 與速率上限**。**縮容的穩定窗口預設是 300 秒**（取這段時間內的最大建議值），**擴容則預設 0 秒**——**這個不對稱是刻意的：擴容要快，縮容要慢。**

## 詳細解析

**「擴容快、縮容慢」這個不對稱值得展開，因為它體現了成本與可用性的不對稱**。**擴晚了會掉請求，縮晚了只是多花一點錢**——**所以預設值把風險放在成本那一側是正確的**。**調校時應該保持這個方向**：**擴容可以設得更激進（一次翻倍），縮容則應該更保守（每分鐘最多減少 10%）**。**能主動說出這個原則，比背出參數名稱更能證明理解。**

**HPA 的計算公式是簡單的比例**：`期望副本數 = ceil(當前副本數 × (當前指標值 / 目標值))`。**理解它能解釋兩個常見現象**：**副本數少時擴縮幅度很粗**（2 個副本的下一步只能是 3 或 1，變化 50%），**以及「目標值設太低會導致頻繁擴縮」**（因為指標的正常波動就足以跨越門檻）。**還有一個容差**：**指標與目標的差距在 10% 以內時 HPA 不動作**，**這是內建的防抖動機制**。

**HPA 與 requests 的關係是初學者最常踩的坑**：**CPU 使用率是相對於 requests 而非 limits 或節點容量計算的**。**如果 requests 設得太低，即使實際用量很少，使用率也會顯得很高，導致 HPA 過度擴容**——**反之亦然**。**所以「調 HPA 之前先確認 requests 設得合理」是必要的前置步驟**。

**HPA 對突發流量的反應天然有延遲**：**指標採集週期（15 秒）+ HPA 檢查週期（15 秒）+ Pod 啟動時間（可能幾十秒）**——**加起來可能是一分鐘以上**。**所以真正的突發流量無法靠 HPA 扛住**，**必須靠預留容量、預測式擴容（按歷史流量曲線提前擴）、或者請求排隊**。

## 面試回答方式

先說明 **CPU 常常不是真正的瓶頸**（等待下游的服務 CPU 低但已飽和），再給三種指標來源並指出**佇列長度是最直觀常用的自訂指標**。給 `behavior` 的調校並強調**擴容預設 0 秒、縮容預設 300 秒這個不對稱是刻意的**。加分點有四個：**這個不對稱體現成本與可用性的不對稱**——**擴晚了掉請求，縮晚了只多花錢**，**所以調校要保持這個方向**；**HPA 的計算公式是簡單比例**，**它解釋了副本少時擴縮幅度粗、以及目標值太低導致頻繁擴縮**，**另有 10% 的容差作為內建防抖**；**CPU 使用率是相對於 requests 計算的**，**requests 設太低會導致過度擴容**，**所以調 HPA 前要先確認 requests 合理**；以及**HPA 對突發流量天然有一分鐘以上的延遲**，**真正的突發必須靠預留容量、預測式擴容或請求排隊**。

## 講稿

按 CPU 擴縮不夠用，是因為 CPU 常常不是真正的瓶頸。一個等待下游回應的服務 CPU 很低但已經飽和了。

所以要換成能反映真實負載的指標。最直觀也最常用的是佇列長度，它直接反映積壓。用自訂指標需要一個轉接器把監控系統的指標暴露給水平擴縮器。

抖動的部分用行為欄位處理，可以分別為擴容跟縮容設定穩定窗口跟速率上限。這裡有一個預設值我覺得很值得說。縮容的穩定窗口預設三百秒，擴容預設零秒。這個不對稱是刻意的，因為擴晚了會掉請求，縮晚了只是多花一點錢。所以調校時應該保持這個方向，擴容可以激進，縮容要保守。

還有一個很常踩的坑。CPU 使用率是相對於請求量計算的，不是相對於限制或節點容量。所以請求量設太低的話，即使實際用量很少，使用率也會顯得很高，導致過度擴容。調擴縮器之前要先確認請求量設得合理。

最後，擴縮器對突發流量天然有一分鐘以上的延遲，真正的突發扛不住，得靠預留容量或預測式擴容。

## 常見追問

### 縮容時把正在處理請求的 Pod 殺掉怎麼辦？

**核心答案**：**這不是 HPA 的問題，而是優雅終止的問題**。HPA 只是調整副本數——**具體哪個 Pod 被刪、怎麼刪，由 ReplicaSet 與 kubelet 處理**。**保證不掉請求需要三件事**：**preStop 鉤子先睡幾秒讓流量摘除**、**足夠的 `terminationGracePeriodSeconds`**、**以及應用能處理 SIGTERM 並拒絕新請求但完成既有的**。

**詳細解析**：**ReplicaSet 選擇刪除哪個 Pod 是有規則的，而知道它有實務價值**：優先刪除**未就緒的**、**在 Pod 數較多的節點上的**、**建立時間較晚的**。**所以「新起來的 Pod 更容易被縮掉」**——**這在擴縮頻繁時會造成 Pod 不斷地生生滅滅**。**如果某些 Pod 特別不希望被刪（例如正在處理長任務），可以用 `controller.kubernetes.io/pod-deletion-cost` 註解標記**，**成本高的會後被刪**——**這是一個知道的人不多但很實用的機制**。**對於長任務，更根本的做法是「不要用 Deployment 跑長任務」**——**把它拆成 Job 或者用佇列讓任務可以被中斷與重試**，**因為任何依賴「Pod 不會被刪」的設計在 K8s 裡都是脆弱的**。

**面試回答方式**：先澄清**這不是 HPA 的問題而是優雅終止的問題**，給三個必要條件（preStop 睡眠、足夠的 grace period、應用處理 SIGTERM）。加分點是說明 **ReplicaSet 的刪除規則**（優先刪未就緒的、Pod 較多節點上的、建立較晚的），**所以新起來的 Pod 更容易被縮掉**，並給出 **`pod-deletion-cost` 註解**這個少人知道但實用的機制。收在根本建議：**不要用 Deployment 跑長任務**，**任何依賴「Pod 不會被刪」的設計在 K8s 裡都是脆弱的**。

### HPA 與 VPA 能一起用嗎？

**核心答案**：**同一個指標上不能，不同指標上可以**。**如果 VPA 調整 CPU requests，而 HPA 按 CPU 使用率擴縮**——**兩者會互相干擾**：VPA 調高 requests 導致使用率下降，HPA 縮容；縮容後負載集中，VPA 又調高……**形成震盪**。**安全的組合是「VPA 管記憶體，HPA 按 CPU 或自訂指標」**，**或者 HPA 用完全獨立的指標（QPS、佇列長度）**。

**詳細解析**：**VPA 還有一個獨立於 HPA 的問題：它需要重啟 Pod 才能套用新的 requests**（原地調整資源在較新的版本才逐步支援）。**所以 VPA 在生產環境的常見用法其實是「推薦模式」**——**只計算建議值不自動套用，由人或 CI 週期性地檢視並更新資源宣告**。**這樣既獲得了 VPA 的分析能力，又不會有意外的重啟**。**而這其實反映了一個更廣的取捨：自動化調整資源的收益（更好的利用率）通常不如它帶來的不確定性（意外重啟、與其他機制的互動）**——**所以「用工具給建議、由人做決定」在資源調校上往往是更務實的模式**。

**面試回答方式**：明確回答**同一指標上不能、不同指標上可以**，並描述震盪的機制（VPA 調高 requests 使使用率下降、HPA 縮容、負載集中、VPA 再調高）。給安全的組合。核心加分點是指出 **VPA 需要重啟 Pod 才能套用新 requests**，**所以生產上常見的用法其實是推薦模式**——**只計算建議值由人週期性檢視**。收在更廣的取捨：**自動調整資源的收益通常不如它帶來的不確定性**，**「用工具給建議、由人做決定」在資源調校上往往更務實**。

### 擴容時節點不夠怎麼辦？

**核心答案**：**HPA 加 Cluster Autoscaler 的組合，但要理解它們的延遲是疊加的**。HPA 增加副本 → 新 Pod Pending → Cluster Autoscaler 偵測到並新增節點 → **節點啟動、加入叢集、拉取映像、Pod 啟動**——**整條鏈路可能是三到五分鐘**。**對延遲敏感的服務必須用「預留容量」的手段縮短它**。

**詳細解析**：**「暫停 Pod」（pause pods）是解決這個問題的經典技巧**：**部署一批低優先級、只佔資源不做事的 Pod 作為「佔位」**——**真正的工作負載需要擴容時，高優先級的 Pod 直接搶佔它們，立刻就能排上去**，**而被搶佔的暫停 Pod 進入 Pending 觸發 Cluster Autoscaler 新增節點**。**這把「等節點」變成了「先用預留的空間，節點在背景補上」**——**擴容延遲從幾分鐘降到幾秒**。**代價是常態性地多付一部分閒置資源的錢**，**而那正是「用成本換延遲」的明確交易**。**另一個做法是「按時間表預先擴容」**——**如果流量有明顯的日內規律（例如每天早上九點暴增），用 CronJob 在八點五十就把副本數拉上去**，**這比任何反應式的機制都有效，而且幾乎沒有技術複雜度**。

**面試回答方式**：給組合並強調**延遲是疊加的**，把整條鏈路拆開說明（HPA 增副本、Pod Pending、CA 偵測、節點啟動加入、拉映像、Pod 啟動），**三到五分鐘**。核心加分點是**暫停 Pod 的技巧**：**低優先級的佔位 Pod 被搶佔後立刻讓出空間，節點在背景補上**，**擴容延遲從幾分鐘降到幾秒**，**代價是常態多付閒置資源的錢——一個明確的成本換延遲的交易**。收在最簡單有效的手段：**流量有日內規律時用排程預先擴容**，**比任何反應式機制都有效且幾乎沒有技術複雜度**。
