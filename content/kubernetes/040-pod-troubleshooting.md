# 題目

一個 Pod 起不來，你的排查流程是什麼？

## 核心答案

先看狀態，因為狀態直接告訴你該往哪個方向查。

**`Pending`** ——**還沒被排到節點**。查 `describe pod` 的 Events：資源不足、taint 未容忍、選擇器無匹配、PVC 綁不上。

**`ImagePullBackOff` / `ErrImagePull`** ——**映像拉不下來**。查映像名稱、認證、倉庫可達性、速率限制。

**`CrashLoopBackOff`** ——**容器啟動後崩潰並反覆重試**。**這時要看的是「上一次」的日誌**（`kubectl logs --previous`），因為當前的容器可能還沒產生輸出。

**`Running` 但 `0/1 Ready`** ——**容器在跑但探針沒過**。查 readiness 探針的設定與應用的健康端點。

**`Init:...`** ——**卡在某個 init 容器**。用 `kubectl logs <pod> -c <init-container>` 看它的輸出。

**`Terminating` 不消失** ——**通常是 finalizer 或 grace period 的問題**。

## 詳細解析

`kubectl logs --previous` 是排查 CrashLoopBackOff 的關鍵，而很多人不知道它。容器崩潰後 kubelet 會重建它——當你執行 `kubectl logs` 時看到的是新容器（可能還沒輸出任何東西，或者又崩潰了）。加上 `--previous` 才能看到上一次崩潰前的完整輸出，而那裡才有真正的錯誤訊息。

`describe` 的 Events 區段是資訊密度最高的地方，但它有一個限制：Events 預設只保留一小時——所以排查一個「昨天發生的問題」時 Events 可能已經沒了。這時要靠日誌系統裡保存的 Event 記錄（如果有收集的話），**或者從 Pod 的 `status` 欄位推斷**。這也是一個「應該收集 Event 到日誌系統」的理由——它是成本很低但在事後排查時價值極高的資料。

**`kubectl debug` 是處理「無 shell 映像」的標準工具**（1.25 之後穩定）。**distroless 映像裡沒有 shell，`kubectl exec` 根本進不去**——`kubectl debug -it <pod> --image=busybox --target=<container>` 會在同一個 Pod 裡起一個臨時容器並共享目標容器的行程命名空間，**讓你能檢視它的檔案與行程**。知道這個工具能解決一整類「想除錯但進不去」的困境。

**Exit code 有明確的含義**：**`0` 正常退出**、**`1` 應用錯誤**、**`137` 是 SIGKILL（通常是 OOMKilled 或 grace period 超時）**、**`143` 是 SIGTERM（正常終止）**、**`139` 是段錯誤**。看到 137 應該立刻去查記憶體，而不是先讀應用日誌。

## 面試回答方式

先給方法論——先看狀態，因為狀態直接告訴你該往哪個方向查，然後把各狀態對應的排查方向列一遍。加分點有四個：`kubectl logs --previous` 是排查 CrashLoopBackOff 的關鍵而很多人不知道——容器崩潰後重建，直接 logs 看到的是新容器可能還沒輸出；**Events 預設只保留一小時**，所以排查昨天的問題時可能已經沒了，這是「應該收集 Event 到日誌系統」的理由——成本很低但事後價值極高；**`kubectl debug` 處理 distroless 映像沒有 shell 的困境**，起臨時容器並共享目標容器的行程命名空間；以及**exit code 的含義**——137 是 SIGKILL 通常是 OOM 或 grace period 超時，看到它應該立刻查記憶體而不是先讀應用日誌。

## 講稿

我會先看狀態，因為狀態直接告訴你該往哪個方向查。

待處理就是還沒被排到節點，去看事件，資源不足、汙點沒容忍、選擇器沒匹配、或儲存綁不上。映像拉取失敗就查名稱、認證、倉庫可達性。反覆崩潰重啟就看日誌。執行中但未就緒就查就緒探針跟應用的健康端點。

這裡有一個關鍵技巧很多人不知道。查反覆崩潰的時候要加上前一個容器的參數。因為容器崩潰之後元件會重建它，你直接看日誌看到的是新容器，可能還沒輸出任何東西。加上那個參數才能看到上一次崩潰前的完整輸出，錯誤訊息在那裡。

另外退出碼是有明確含義的。一三七是被強制終止，通常是記憶體超限或者優雅終止超時。看到它應該立刻去查記憶體，而不是先讀應用日誌。

還有一個工具值得知道。最小化的映像裡沒有殼層，直接進不去。除錯指令可以在同一個 Pod 裡起一個臨時容器，並共享目標容器的行程命名空間，讓你能檢視它的檔案跟行程。

## 常見追問

### Pod 卡在 Terminating 刪不掉怎麼辦？

**核心答案**：**兩個常見原因**。**Finalizer 未被清理**——某個控制器在 `metadata.finalizers` 裡登記了清理動作但沒有完成（可能該控制器已經掛了），於是物件永遠不會被真正刪除。**節點失聯**——**kubelet 無法回報 Pod 已終止，API server 就一直等**。**應急手段是 `kubectl patch` 移除 finalizer 或 `--force --grace-period=0`**，但要理解那只是刪除 API 物件，實際的容器可能還在跑。

**詳細解析**：**`--force` 的危險性值得強調**：它讓 API server 認為 Pod 已消失，於是 StatefulSet 會在別的節點建立一個同名的 Pod——如果原節點只是網路分割而容器仍在運行並持有磁碟或寫入資料，**就會出現兩個實例同時運行**。對有狀態應用這可能導致資料損壞。 所以正確的做法是先確認原節點的狀態（節點真的掛了嗎？還是只是失聯？），確認容器確實不在了再強制刪除。這是一個「便捷指令背後有嚴重後果」的典型例子——而知道這一點與只知道指令，是完全不同層次的理解。

**面試回答方式**：給兩個常見原因（finalizer 未清理、節點失聯）與應急手段，並指出強制刪除只是刪 API 物件，實際容器可能還在跑。核心加分點是說明 **`--force` 的危險**：**API server 認為 Pod 消失後 StatefulSet 會在別處建同名 Pod**，如果原節點只是網路分割而容器仍在運行並持有磁碟，就會有兩個實例同時運行，對有狀態應用可能導致資料損壞。收在正確做法：先確認節點是真的掛了還是只是失聯，這是「便捷指令背後有嚴重後果」的典型例子。

### 應用在本機正常但在 K8s 裡不行，怎麼縮小範圍？

**核心答案**：**按「環境差異」逐項排除**。最常見的五類：**設定**（環境變數、ConfigMap 是否正確注入——`kubectl exec` 進去 `env` 一下）、**網路**（能不能連到依賴——用臨時容器測試）、**權限**（以非 root 執行時的檔案權限問題）、**資源**（本機沒有記憶體限制而容器有）、**以及依賴的可達性**（本機連的是本地資料庫，容器裡連的是遠端）。

**詳細解析**：「以非 root 執行」造成的問題特別隱蔽：本機開發時是 root 或自己的使用者，而容器裡可能是 UID 1000 的非特權使用者——於是「寫入某個目錄」失敗、「綁定 1024 以下的端口」失敗。**後者尤其常見**：很多應用預設聽 80 端口，而非 root 使用者無權綁定——解法是改成聽 8080 並讓 Service 做端口映射，**而不是把容器跑成 root**。另一個常被忽略的差異是「時區與語系」：容器映像通常是 UTC 且沒有語系設定，這會讓時間顯示與字串排序的行為與本機不同——症狀往往不是崩潰，而是資料悄悄地錯了，**那比崩潰更難發現**。

**面試回答方式**：給五類環境差異的檢查清單與各自的驗證方法。核心加分點是以非 root 執行造成的問題特別隱蔽：寫入目錄失敗、綁定 1024 以下端口失敗，而後者的解法是改聽 8080 讓 Service 做映射而不是把容器跑成 root。第二個是**時區與語系的差異**：容器映像通常是 UTC 且沒有語系設定，症狀往往不是崩潰而是資料悄悄地錯了，那比崩潰更難發現。

### 怎麼查一個間歇性的問題？

**核心答案**：間歇性問題的關鍵是「保留現場」，因為你無法在它發生時剛好在看。三個手段：**收集 Events 到日誌系統**（不然一小時後就沒了）、**保留崩潰前的日誌**（日誌收集要能捕捉到容器重啟前的輸出）、以及在探針失敗時自動抓取診斷資訊（用 preStop 或 sidecar 在終止前 dump 執行緒堆疊與堆積）。

**詳細解析**：「在終止前自動抓 dump」是一個投入不大但回報極高的做法：在 `preStop` 鉤子裡執行 `jstack` 或 `jmap` 並把結果寫到一個持久化的位置——於是每一次意外終止都留下了現場。沒有這個機制的話，你只能等下一次發生並希望剛好在看，而間歇性問題可能幾天才出現一次。另一個有效的做法是「提高該工作負載的可觀測性密度」：暫時把日誌等級調高、增加指標的取樣頻率、或者對它開啟持續剖析——用一段時間的額外開銷換取抓到問題的機會。這是一個明確的取捨，而在間歇性問題上它幾乎總是划算的，因為「查不出來」的成本會一直累積。

**面試回答方式**：先給核心認知——間歇性問題的關鍵是保留現場，因為你無法在它發生時剛好在看，並給三個手段。核心加分點是**在終止前自動抓 dump**：在 preStop 裡執行 jstack 或 jmap 寫到持久化位置，讓每一次意外終止都留下現場，否則只能等下一次並希望剛好在看，而間歇性問題可能幾天才出現一次。收在**提高可觀測性密度**這個明確的取捨：用一段時間的額外開銷換抓到問題的機會，在間歇性問題上幾乎總是划算的，因為「查不出來」的成本會一直累積。
