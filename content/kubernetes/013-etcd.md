# 題目

etcd 在 Kubernetes 裡負責什麼？為什麼它的節點數建議是奇數？備份 etcd 等於備份整個叢集嗎？

## 核心答案

**etcd 是整個叢集唯一的真實來源（single source of truth）**——所有資源的期望狀態與實際狀態都存在裡面：Deployment 的定義、Pod 的排程結果、Service 與 Endpoints、ConfigMap 與 Secret、RBAC 規則。其他元件**都不直接讀寫 etcd**，一律經過 kube-apiserver，所以 apiserver 是 etcd 的唯一守門人。

**節點數要奇數是因為 Raft 的多數決**：etcd 用 Raft 達成一致性，任何寫入都要**超過半數**節點確認。3 個節點能容忍 1 個失敗（需要 2 個），4 個節點也只能容忍 1 個（需要 3 個）——**多一個節點沒有提升容錯能力，卻多了一份寫入延遲與網路開銷**，還增加了腦裂風險。所以偶數是純粹的浪費，實務上用 3 或 5。

**備份 etcd 幾乎等於備份整個叢集的「設定」，但不等於備份「資料」**——PV 裡的應用資料、容器映像檔都不在 etcd 裡。所以完整的災難復原計畫必須是 etcd 快照加上持久卷的備份。

## 詳細解析

**watch 機制是 K8s 運作的基礎**：控制器不是輪詢 etcd，而是透過 apiserver 對資源建立 **watch**，資源一變就收到事件。etcd 原生支援這種變更通知，這正是它被選中而非一般資料庫的原因——整個「宣告期望狀態、控制器持續校正」的模型都建立在高效的變更推播上。

**寫入放大與效能特性**：每次寫入都要經過 Raft 複製到多數節點並落盤，所以 etcd 對**磁碟延遲極度敏感**，官方建議用 SSD 並獨立於其他 I/O 負載。它也不適合存放大量或高頻變動的資料——單一物件有大小上限（預設 1.5MB），總容量預設配額約 2GB 到 8GB。這解釋了為什麼「大量 Completed 的 Job Pod 不清理」會成為真實問題，也是為什麼不該把大型設定檔硬塞進 ConfigMap。

**Secret 預設是明文存放**：etcd 裡的 Secret 只做了 base64 編碼。**拿到 etcd 備份就等於拿到所有 Secret**，所以備份檔本身必須被當成最高機密保護，並且應該啟用靜態加密（EncryptionConfiguration，GKE 上是以 Cloud KMS 金鑰做 Application-layer Secrets Encryption）。

**託管叢集裡你碰不到 etcd**：在 GKE、EKS 這類託管服務中，控制平面由雲端供應商管理，etcd 的備份、升級、擴容都不是使用者的責任，也無法直接存取。這時「備份叢集」的做法改為備份**資源定義**——用 Velero 或直接把 YAML 存進 Git（GitOps 天然就達成了這件事），加上 PV 的快照。

**etcd 失去多數就整個叢集唯讀**：如果 3 個節點壞了 2 個，Raft 無法形成多數，etcd 進入**唯讀**狀態。此時已經在跑的 Pod **不受影響**（kubelet 與容器執行環境不依賴 etcd 持續運作），但任何變更都做不了——不能部署、不能擴縮、故障的 Pod 也不會被重建。理解這個界線很重要：控制平面掛掉不等於服務中斷，但叢集失去了自我修復能力。

## 面試回答方式

第一句就定調——etcd 是唯一真實來源，而且所有元件都經過 apiserver 存取它，不直接連。奇數節點的問題要用 Raft 多數決算給面試官看：3 個容忍 1 個、4 個也只容忍 1 個，多的那個只增加延遲不增加容錯。備份那一問要拆開回答：etcd 存的是**設定**，PV 裡的**資料**不在裡面，完整方案要兩者兼具。實務加分點三個：etcd 的容量與物件大小限制解釋了為什麼要清理 Completed Pod、不該把大檔塞 ConfigMap；Secret 在 etcd 裡是明文，備份檔等同最高機密；以及「失去多數只是唯讀」——現有 Pod 繼續跑，但叢集失去自我修復能力。

## 講稿

etcd 是整個叢集唯一的真實來源。所有東西都存在裡面：Deployment 的定義、Pod 排到哪個節點、Service 跟 Endpoints、ConfigMap、Secret、RBAC 規則。而且其他元件都不直接讀寫它，一律經過 kube-apiserver。

為什麼節點數要奇數？因為 etcd 用 Raft，任何寫入都要超過半數節點確認。三個節點能容忍一個失敗。四個呢？需要三個才算多數，還是只能容忍一個。多的那一個沒有提升容錯，卻多了一份寫入延遲。所以偶數是純浪費，實務上用三個或五個。

備份要拆開講。備份 etcd 幾乎等於備份整個叢集的設定，但不等於備份資料。PV 裡的應用資料、容器映像檔都不在裡面。完整的災難復原要 etcd 快照加上持久卷備份。

有個界線值得記住。etcd 失去多數會進入唯讀，這時已經在跑的 Pod 完全不受影響，因為 kubelet 不需要持續依賴它。但你什麼都改不了，掛掉的 Pod 也不會被重建。控制平面掛掉不等於服務中斷，但叢集失去了自我修復能力。

## 常見追問

### etcd 掛掉的話，正在跑的服務會受影響嗎？

**核心答案**：**短期內不會**。kubelet 已經知道自己該跑哪些 Pod，容器執行環境也持續運作，既有的 Pod 照常服務流量，kube-proxy 節點上的轉發規則也還在。真正失去的是**變更能力與自我修復能力**——不能部署、不能擴縮，而且 Pod 掛掉之後**不會被重建**，Node 故障也不會觸發重新排程。

**詳細解析**：所以影響是**漸進累積**的，而不是立刻爆炸。第一分鐘可能毫無感覺，但只要有任何 Pod 因為 OOM 或節點問題死掉，那份容量就永久少掉，服務會慢慢降級。這個特性有兩面：好的一面是它給了修復控制平面的時間窗，不必恐慌；壞的一面是監控如果只看應用層的健康度，可能很久都沒發現控制平面已經死了。所以控制平面的健康必須獨立監控，不能靠「服務還通」來推論。另外要注意 Service 與 Endpoints 的更新也停了，所以滾動更新做到一半時 etcd 掛掉，可能會停在新舊版本並存的中間狀態。

**面試回答方式**：先回答短期不受影響並解釋為什麼（kubelet 與容器執行環境不需要持續連 etcd）。重點放在「漸進累積」這個特性——不是立刻爆炸，而是隨著 Pod 自然損耗慢慢降級。加分點是指出監控只看應用層會漏掉控制平面已死，必須獨立監控。

### 為什麼不建議把大型設定檔或大量資料放進 ConfigMap？

**核心答案**：因為 ConfigMap 最終存在 **etcd** 裡，而 etcd 有明確的限制——單一物件預設上限約 1.5MB，整個資料庫也有配額（常見是幾 GB）。更關鍵的是 etcd 的每次寫入都要經過 Raft 複製到多數節點並落盤，**大物件會放大寫入成本、拖慢整個控制平面**，影響的不只是你自己的 ConfigMap，而是所有 API 操作。

**詳細解析**：除了大小，**變更頻率**同樣要注意。etcd 會保留歷史版本供 watch 使用，高頻更新的物件會快速累積修訂版本，需要定期壓縮與碎片整理，否則容量會不斷成長直到觸發配額而讓叢集進入唯讀。這也是為什麼大量 Completed 的 Job Pod 不清理會成為真實問題——不是佔了多少空間，而是物件數量與修訂版本拖累了整體效能。替代方案很直接：大型靜態檔案放物件儲存（GCS）由應用啟動時下載，或直接打進映像檔；需要頻繁變更的設定放專門的設定中心。判準是「這份資料需不需要參與 K8s 的宣告式協調」，不需要的話就不該進 etcd。

**面試回答方式**：先給具體限制（單物件約 1.5MB、資料庫配額），再講更關鍵的原因——Raft 複製讓大物件放大寫入成本、拖慢**所有** API 操作。加分點是提到變更頻率與修訂版本累積，並把它和「Completed Pod 要清理」串起來。最後給判準：這份資料需不需要參與宣告式協調。

### 在 GKE 上要怎麼備份叢集？

**核心答案**：GKE 的 etcd 由 Google 管理，**使用者無法直接存取或做 etcd 快照**。所以做法改成備份**資源定義**與**持久資料**兩部分：資源定義用 Backup for GKE 或 Velero 匯出，或更根本地——採用 GitOps 讓所有 YAML 本來就在 Git 裡；持久資料則用 PV 的磁碟快照，或應用層自己的備份機制（資料庫的邏輯備份通常比磁碟快照更可靠）。

**詳細解析**：GitOps 在這件事上有結構性優勢——如果叢集的所有資源都由 Git 裡的宣告產生，那麼「重建叢集」就只是建一個新叢集再讓 GitOps 工具同步一次，完全不需要備份還原的流程，而且這條路徑平常就在被驗證（每次部署都在走）。相對地，備份還原的流程往往只在災難時第一次被真正執行，那正是最不該遇到意外的時刻。要注意的是即使用 GitOps，仍有一些東西不在 Git 裡：由 controller 動態產生的資源、外部密鑰服務同步進來的 Secret、以及 PV 的實際資料，這些要各自有對應方案。實務上建議定期做一次「從零重建到可服務」的演練，那是唯一能證明備份策略有效的方法。

**面試回答方式**：先說明 GKE 上碰不到 etcd，所以要換思路。給出資源定義與持久資料兩條線。重點放在 GitOps 的結構性優勢——重建就是同步一次，而且這條路徑平常就在被驗證，對比備份還原只在災難時第一次執行。加分點是指出 GitOps 也有涵蓋不到的部分，以及建議做重建演練。
