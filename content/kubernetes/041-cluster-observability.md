# 題目

一個 K8s 叢集該收集哪些可觀測性資料？分別怎麼收？

## 核心答案

**四類資料，來源與用途都不同。**

**資源指標**——CPU、記憶體的實際用量，**由 metrics-server 提供給 `kubectl top` 與 HPA**。注意它只保留最近的值，不是監控系統——要看歷史必須另外用 Prometheus 之類的系統。

**叢集狀態指標**——**kube-state-metrics 把 K8s 物件的狀態轉成指標**（有幾個 Pod 處於 Pending、Deployment 的期望與實際副本數差多少、PVC 的容量）。這一類最常被遺漏，卻是「叢集健康度」告警的基礎。

**日誌**——容器的 stdout/stderr 由容器執行期寫到節點磁碟，再由 DaemonSet 形式的收集器（Fluent Bit、Vector）送到集中儲存。應用不該自己寫檔案或直接送到後端——那讓日誌與 Pod 生命週期綁死，Pod 消失就查不到了。

**Event**——K8s 自己產生的事件記錄（排程失敗、拉取映像、探針失敗）。預設只保留一小時，必須主動收集才能事後排查。

## 詳細解析

「kube-state-metrics 與 metrics-server 的差別」是一個常見的混淆點。**metrics-server 回答「這個 Pod 用了多少 CPU」**（來自 kubelet 的 cAdvisor，**是資源用量**）；kube-state-metrics 回答「這個 Deployment 期望 3 個副本但只有 2 個可用」（來自 API server，**是物件狀態**）。它們是互補的，而後者才是「叢集是不是健康」這類問題的答案來源。

最有價值的叢集級告警多半來自 kube-state-metrics：**Pod 長時間 Pending**、Deployment 的可用副本數低於期望超過 N 分鐘、**Pod 反覆重啟**、**Job 失敗**、**PVC 使用率過高**、**節點 NotReady**。這些告警的共同特徵是「它們指向一個明確的行動」——**而那正是好告警的定義**。

日誌收集的節點級模式有一個重要優勢：它能收集到「Pod 已經消失」之後的日誌——因為日誌檔案還在節點上，收集器有機會讀完再讓它被輪替掉。而如果讓應用自己送日誌，Pod 崩潰的瞬間最後幾行往往就丟了——**而那幾行常常正是最關鍵的**。

結構化日誌在容器環境裡尤其重要：因為所有 Pod 的日誌會被混在一起，靠自由文字很難篩選。輸出 JSON 並帶上 trace ID，讓收集器能自動附加 Pod、namespace、node 的標籤——這讓「查某一次請求在所有服務裡的軌跡」變成可能。

## 面試回答方式

先給四類資料（資源指標、叢集狀態指標、日誌、Event）與各自的來源。加分點有四個：**metrics-server 與 kube-state-metrics 的差別**——前者回答「用了多少」來自 cAdvisor，後者回答「期望與實際差多少」來自 API server，而後者才是叢集健康度的答案來源；最有價值的叢集級告警多半來自 kube-state-metrics，並舉出具體規則，它們的共同特徵是指向明確的行動，而那正是好告警的定義；日誌收集的節點級模式能收到 Pod 消失後的日誌——應用自己送的話崩潰瞬間最後幾行往往就丟了，而那常常正是最關鍵的；以及Event 預設只保留一小時，必須主動收集才能事後排查。

## 講稿

我會分成四類。

資源指標是實際的 CPU 跟記憶體用量，由指標伺服器提供給頂端指令跟自動擴縮器。但要注意它只保留最近的值，不是監控系統，看歷史要另外用時序資料庫。

第二類最常被遺漏，叢集狀態指標。它把 K8s 物件的狀態轉成指標，比如某個部署期望三個副本但只有兩個可用。這一類才是叢集健康度告警的基礎，而它跟第一類是互補的，一個回答用了多少，一個回答期望跟實際差多少。

第三類是日誌。容器的標準輸出由執行期寫到節點磁碟，再由每節點一份的收集器送到集中儲存。這個節點級模式有一個重要優勢，它能收集到 Pod 已經消失之後的日誌，因為檔案還在節點上。如果讓應用自己送，Pod 崩潰的瞬間最後幾行往往就丟了，而那幾行常常正是最關鍵的。

第四類是 K8s 自己產生的事件。它預設只保留一小時，所以必須主動收集，否則事後完全查不到。

## 常見追問

### 應該監控哪些叢集級的黃金指標？

**核心答案**：**分成三層各看幾項**。**控制平面**——**API server 的請求延遲與錯誤率**、**etcd 的寫入延遲與資料庫大小**、**scheduler 的排程延遲**。**節點**——**NotReady 的節點數**、各節點的資源配置率（requests 佔 allocatable 的比例）、**磁碟與 PID 壓力**。**工作負載**——**Pending 超時的 Pod**、**重啟頻率**、**可用副本數與期望的差距**。

**詳細解析**：「資源配置率」比「實際使用率」更適合作為容量告警的依據：**因為排程是按 requests 進行的**——配置率到 90% 時新 Pod 就快排不進來了，即使實際使用率只有 40%。這個指標能在「擴容失敗」發生之前給出預警，而只看使用率的團隊會被「明明還很空為什麼排不進去」搞糊塗。**etcd 的指標同樣值得特別關注**：**它是整個叢集的單點**，而它的效能問題（寫入延遲上升、資料庫接近容量上限）會表現成「所有 kubectl 指令都變慢」這種難以歸因的症狀。知道要先看 etcd，能在這類事故中省下大量時間。

**面試回答方式**：分三層給出具體指標。核心加分點是資源配置率比實際使用率更適合作為容量告警依據——排程按 requests 進行，配置率到 90% 時新 Pod 就快排不進來了即使實際使用率只有 40%，只看使用率的團隊會被「明明還很空為什麼排不進去」搞糊塗。第二個是**etcd 是整個叢集的單點**，它的效能問題會表現成「所有 kubectl 都變慢」這種難以歸因的症狀，知道要先看它能省下大量時間。

### 日誌量太大成本失控怎麼辦？

**核心答案**：在來源側減量，而不是在儲存側壓縮。四個手段：**調整應用的日誌等級**（**生產環境不該輸出 DEBUG**）、**取樣**（成功請求的日誌只保留 1%，錯誤全留）、**分級保留**（熱儲存 7 天、冷儲存 30 天、之後歸檔或刪除）、**以及過濾**（在收集器層丟棄已知無用的雜訊，例如健康檢查的存取日誌）。

**詳細解析**：「健康檢查的存取日誌」常常佔了驚人的比例：每個 Pod 每秒被探測一到兩次，一千個 Pod 就是每秒兩千行——而它們幾乎沒有任何診斷價值。在收集器層過濾掉它們往往能立刻砍掉三成以上的量，**是投入最小的一項優化**。至於取樣，關鍵是「按 trace 取樣而非按行取樣」：如果隨機丟棄日誌行，一次請求的軌跡會變得殘缺不全——正確的做法是決定「這條 trace 要不要留」，然後留下它的全部日誌。這讓保留下來的資料仍然是完整可用的，而不是一堆孤立的片段。

**面試回答方式**：主張在來源側減量而非儲存側壓縮並給四個手段。加分點是指出健康檢查的存取日誌常佔驚人比例——一千個 Pod 每秒兩千行且幾乎沒有診斷價值，過濾掉往往能立刻砍掉三成以上，是投入最小的優化。核心加分點是取樣的正確方式：**按 trace 取樣而非按行取樣**——隨機丟棄日誌行會讓請求的軌跡殘缺不全，正確做法是決定這條 trace 要不要留然後留下它的全部，這讓保留的資料仍然完整可用而不是一堆孤立片段。

### 怎麼把應用的指標接進來？

**核心答案**：應用暴露一個 `/metrics` 端點，Prometheus 透過 ServiceMonitor 或 PodMonitor 自動發現並抓取。**關鍵是「標籤的設計」**：指標要帶上足夠的維度（service、endpoint、status）供切分，但絕不能放高基數的值（user_id、request_id）——那會讓時間序列數量爆炸並拖垮監控系統。

**詳細解析**：「K8s 環境讓高基數風險更高」值得指出：**Prometheus 的抓取會自動附加 pod、namespace、node 等標籤**——而 Pod 名稱本身就是變動的（每次重新部署都是新的名稱）。於是一個指標的時間序列數量會隨著部署次數不斷累積（舊的序列在保留期內仍佔用記憶體與索引）。這是 K8s 環境特有的一種基數膨脹，而它在頻繁部署的團隊裡特別明顯。 緩解的方式是「在記錄規則裡聚合掉 pod 標籤」——大多數告警與儀表板關心的是服務層級而非個別 Pod，所以預先聚合成服務級的指標既降低了查詢成本，也讓儀表板不受重新部署的影響。

**面試回答方式**：給接入方式（暴露 `/metrics`、用 ServiceMonitor 自動發現）並強調標籤設計的關鍵是有足夠維度但不能放高基數的值。核心加分點是指出**K8s 環境讓高基數風險更高**：抓取會自動附加 pod 標籤，而 Pod 名稱每次部署都變，於是時間序列數量隨部署次數累積，在頻繁部署的團隊裡特別明顯。收在緩解方式：**在記錄規則裡聚合掉 pod 標籤**——多數告警與儀表板關心的是服務層級，預先聚合既降低查詢成本也讓儀表板不受重新部署影響。
