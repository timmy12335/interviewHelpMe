# 題目

什麼情況下 K8s 是錯的選擇？有哪些替代方案？

## 核心答案

K8s 的價值是「用一套統一的抽象管理大量異質的工作負載」——而它的成本是那套抽象本身的學習與維運。當工作負載的數量與異質性不足以攤平這個成本時，它就是錯的選擇。

**四類不該用的情況**。**團隊規模太小**——沒有專職或半專職的人維護叢集時，K8s 的運維負擔會直接吃掉開發時間。**工作負載太簡單**——三個無狀態服務加一個資料庫，用 PaaS 或容器服務就完全夠了。需求是「跑一個東西」而非「編排很多東西」——單一應用、批次任務、或者一個定時腳本，K8s 是巨大的過度設計。**團隊沒有容器化的基礎**——應用還沒有做到無狀態、設定外部化、優雅終止時，上 K8s 只會把問題放大。

**替代方案按複雜度**：**PaaS**（Heroku、Render、Fly.io）、**雲端容器服務**（Cloud Run、App Runner、ECS Fargate）、**無伺服器函數**、**以及最樸素的「虛擬機加 systemd」**。

## 詳細解析

「K8s 的複雜度是持續的而非一次性的」是最常被低估的一點。它不只是「學會怎麼用」——還包括版本升級（一年兩到三次）、第三方元件的相容性維護、安全修補、以及每一次故障時需要的診斷能力。這些是持續投入，而它不會隨著你熟悉了就消失。所以評估時該問的不是「我們學得會嗎」，而是「我們願意每年投入多少人力在這上面」。

Cloud Run 這類服務是最常被低估的替代品：它給你容器、自動擴縮（包括縮到零）、流量分割、以及零維運——對「一組無狀態的 HTTP 服務」這個最常見的場景，它幾乎在所有維度上都優於自建 K8s。選 K8s 而非它的正當理由通常是：需要非 HTTP 的工作負載、需要更細的資源控制、需要跑有狀態的元件、或者需要避免供應商鎖定。

**「反正以後會需要」不是好理由**。過早採用 K8s 的成本是立即的，而收益是假設性的——而多數團隊的規模成長不如預期，或者成長時的需求與當初的設想不同。更好的策略是「保持應用是容器化且無狀態的」——**那讓未來遷移到 K8s 變得容易**，而在那之前不必付出叢集的維運成本。這是「保留選項而非提前行使」的思路。

**但也要公平地說 K8s 的獨特價值**：當你有幾十個服務、多個團隊、以及混合的工作負載（線上服務、批次、有狀態元件）時，沒有其他東西能提供同等的統一性——而那時每個團隊各自用不同的部署方式帶來的混亂，成本遠高於學習 K8s。

## 面試回答方式

先給價值與成本的框架——K8s 的價值是用統一抽象管理大量異質工作負載，成本是抽象本身的學習與維運，數量與異質性不足以攤平成本時它就是錯的選擇。給四類不該用的情況與替代方案的階梯。加分點有四個：K8s 的複雜度是持續的而非一次性的——升級、相容性維護、安全修補、診斷能力都是持續投入，所以該問的不是「學得會嗎」而是「願意每年投入多少人力」；**Cloud Run 這類服務最常被低估**——對一組無狀態 HTTP 服務這個最常見的場景，它幾乎在所有維度上優於自建；**「反正以後會需要」不是好理由**——**成本立即而收益假設性**，更好的策略是保持應用容器化且無狀態，那是「保留選項而非提前行使」；以及**公平地說 K8s 的獨特價值**：幾十個服務加多團隊加混合工作負載時，沒有其他東西提供同等的統一性。

## 講稿

我會先講價值跟成本的框架。K8s 的價值是用一套統一的抽象管理大量異質的工作負載，而它的成本是那套抽象本身的學習與維運。當工作負載的數量跟異質性不足以攤平這個成本時，它就是錯的選擇。

具體有四類不該用。團隊規模太小、工作負載太簡單、需求是跑一個東西而不是編排很多東西、還有團隊連容器化的基礎都還沒有。

最常被低估的一點是它的複雜度是持續的而不是一次性的。不只是學會怎麼用，還包括一年兩三次的版本升級、第三方元件的相容性、安全修補、以及每次故障時需要的診斷能力。所以評估時該問的不是我們學得會嗎，而是我們願意每年投入多少人力在這上面。

另外，反正以後會需要不是好理由。過早採用的成本是立即的，而收益是假設性的。更好的策略是保持應用容器化且無狀態，那讓未來遷移變得容易，而在那之前不必付叢集的維運成本。這是保留選項而不是提前行使。

但我也要公平地說，當你有幾十個服務、多個團隊、混合的工作負載時，沒有其他東西能提供同等的統一性。

## 常見追問

### 已經上了 K8s 但發現太複雜，怎麼辦？

**核心答案**：先分清是「K8s 太複雜」還是「你們的用法太複雜」。多數團隊的痛苦來自後者：自建了太多元件（自己跑 Prometheus、Ingress、cert-manager、service mesh）、寫了太多自訂的 YAML、或者過早引入了 Operator 與 CRD。簡化的第一步是「用託管的替代自建的」——託管的 K8s、託管的監控、雲端的負載平衡器。

**詳細解析**：**「service mesh 是最常見的過早採用」**：它解決的是大量服務之間的可觀測性、加密、與流量控制——而在十個服務以內，這些需求都可以用更簡單的方式滿足（應用層的追蹤函式庫、TLS 終止在 Ingress、以及重試邏輯寫在客戶端）。引入它的成本是一整套新的抽象、額外的資源開銷、以及一類全新的疑難雜症（sidecar 的啟動順序、mTLS 的憑證問題、以及流量被靜默丟棄）。如果要退，退掉 mesh 通常是收益最大的一步。更一般的原則是「每個引入的元件都要能說出它解決了哪個具體的、已經發生的問題」——說不出來的就是候選的移除對象。

**面試回答方式**：先做區分——「K8s 太複雜」還是「你們的用法太複雜」，並指出**多數痛苦來自後者**（自建太多元件、太多自訂 YAML、過早的 Operator 與 CRD），給出第一步（用託管的替代自建的）。核心加分點是**service mesh 是最常見的過早採用**：十個服務以內那些需求都能用更簡單的方式滿足，而它的成本是一整套新抽象加一類全新的疑難雜症。收在原則：每個引入的元件都要能說出它解決了哪個具體的、已經發生的問題，說不出來的就是候選的移除對象。

### 有狀態的東西該放進 K8s 嗎？

**核心答案**：**能用託管服務就用託管服務**。資料庫、訊息佇列、快取——雲端的託管版本已經處理了備份、高可用、升級、監控，而自己在 K8s 裡跑一套等於接手這些責任。**放進去的正當理由只有三個**：**沒有可用的託管服務**、**大規模下成本確實划算**、**或者需要跨雲的一致性**。

**詳細解析**：「因為我們已經有 K8s 了」是最常見但最站不住腳的理由——編排能力與運維能力是兩回事。跑一個生產級的資料庫需要的是懂它的人、驗證過的備份還原流程、以及處理故障的經驗——這些不會因為它跑在 K8s 上而變得更容易。而如果決定要跑，成熟的 Operator 是必要的（它把運維知識編碼進來），同時要接受「你現在是自己的 DBA」這個事實。值得補充的是「K8s 對有狀態的支援確實在進步」（CSI、StatefulSet、成熟的 Operator），**所以這個判斷會隨時間變化**——但變化的是可行性，不是「你的團隊有沒有能力承擔」這個問題。

**面試回答方式**：主張**能用託管就用託管**並列出三個正當理由。核心加分點是指出「因為我們已經有 K8s 了」最常見但最站不住腳——編排能力與運維能力是兩回事，跑生產級資料庫需要的是懂它的人、驗證過的備份還原、與處理故障的經驗，這些不會因為跑在 K8s 上而變容易。收在一個公允的補充：K8s 對有狀態的支援確實在進步，所以這個判斷會隨時間變化——但變化的是可行性，不是「你的團隊有沒有能力承擔」這個問題。

### 面試官說「我們正在導入 K8s」，該怎麼回應？

**核心答案**：接受方向並談前置條件與順序，而不是質疑決定。合理的回答結構是：「我認同這個方向，我會關心的是導入的順序。」 然後給**前置條件**（應用要無狀態、設定外部化、健康檢查與優雅終止到位、CI 能產出容器映像）與**順序**（先遷無狀態的、風險低的服務；有狀態的留在託管服務；最後才考慮要不要把它們也遷進來）。

**詳細解析**：這個追問測的是「你能不能在既定方向下提出專業意見」——單純附和顯得沒有判斷，直接反對顯得不合作。最有價值的具體建議是「先把應用改造好再遷」：很多失敗的導入不是因為 K8s 難，而是因為把一個依賴本地檔案、啟動要五分鐘、且無法優雅關閉的應用直接搬進去——於是每一個 K8s 的正常行為（重新排程、滾動更新、探針重啟）都變成一次事故。另一個值得提的是「導入應該有可衡量的目標」：部署頻率、環境一致性、資源利用率——如果遷完之後這些沒有改善，那就該檢視是哪裡出了問題，而不是繼續往前推。

**面試回答方式**：給態度——接受方向並談前置條件與順序，用一句話開場，然後給前置條件與遷移順序。核心加分點是指出很多失敗的導入不是因為 K8s 難，而是把一個依賴本地檔案、啟動要五分鐘、無法優雅關閉的應用直接搬進去，於是每一個 K8s 的正常行為都變成一次事故。收在**導入應該有可衡量的目標**（部署頻率、環境一致性、資源利用率），沒改善就該檢視哪裡出問題而不是繼續往前推。
