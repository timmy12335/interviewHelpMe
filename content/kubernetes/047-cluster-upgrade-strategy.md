# 題目

K8s 版本升級要注意什麼？怎麼降低升級的風險？

## 核心答案

**K8s 的發布節奏是每年三個小版本，每個版本支援約 14 個月**——**這意味著「不升級」不是一個選項，落後太多會失去安全修補**。

**升級的三個硬性規則**。**順序**——**先控制平面再工作節點**（**kubelet 可以比 API server 舊最多兩個小版本，但不能更新**）。**逐版**——**不能跳版，1.28 到 1.31 必須經過 1.29 與 1.30**。**API 棄用**——**每個版本都有 API 被移除，升級前必須確認沒有資源還在用它們**。

**降低風險的四件事**：**用 `kubectl deprecations` 或 Pluto 掃描棄用的 API**、**先在非生產叢集完整走一遍**、**用 surge 模式升級節點（先建新的再 drain 舊的）**、**以及確認所有 PDB 的設定不會讓 drain 卡死**。

**而最容易被忽略的是「第三方元件的相容性」**——**CNI、CSI 驅動、Ingress controller、Operator 都有各自的版本相容矩陣**。

## 詳細解析

**「API 棄用」是升級失敗最常見的原因，而它的隱蔽之處在於「舊的資源仍在運行」**。**API 被移除後，既有的資源物件通常會被自動轉換成新版本繼續運作**——**真正壞掉的是「你的 CI 或 Helm chart 裡寫的舊 API 版本」**：**下一次部署時 `kubectl apply` 會直接失敗**。**所以掃描不能只掃叢集裡現有的資源，還要掃你的 Git 倉庫裡的 YAML 與 chart**——**而後者更容易被遺漏**。

**「第三方元件」的風險常常大於 K8s 本身**。一個沒有跟上的 CSI 驅動可能在新版本上完全無法掛載磁碟；**一個舊的 Ingress controller 可能不認得新的 API 版本**。**所以升級的檢查清單應該包含「列出所有叢集級元件並確認它們支援目標版本」**——**這一步比升級 K8s 本身更耗時，卻更常出問題**。**實務上的順序通常是「先升級第三方元件到同時支援新舊版本的版本，再升級 K8s」**。

**託管服務讓升級變簡單但不是變沒有**。GKE、EKS 會自動處理控制平面，**但節點升級仍然會驅逐你的 Pod**——**所以 PDB、優雅終止、與副本數的設定仍然決定了你會不會掉請求**。**而託管服務的自動升級（例如 GKE 的 release channel）意味著「升級會在你沒有準備的時候發生」**——**這通常是好事（強迫保持在支援的版本上），但必須配合維護窗口的設定與充分的自動化測試**。

**升級的頻率是一個取捨**。**跟得緊**——每次的變化小、風險低、但頻繁地投入時間。**跟得鬆**——**幾個版本一起升，累積的變化多，風險反而更高**。**實務上「一年升兩次、始終保持在支援期內」是多數團隊的平衡點**。

## 面試回答方式

先給版本節奏與**「不升級不是一個選項」**的結論。給三個硬性規則（順序、逐版、API 棄用）與四件降低風險的事。加分點有四個：**API 棄用的隱蔽之處**——**既有資源會被自動轉換繼續運作，真正壞掉的是 CI 與 chart 裡寫的舊 API 版本**，**所以掃描不能只掃叢集，還要掃 Git 倉庫裡的 YAML 與 chart，而後者更容易被遺漏**；**第三方元件的風險常大於 K8s 本身**——**檢查清單要列出所有叢集級元件並確認支援目標版本**，**這一步比升級 K8s 本身更耗時卻更常出問題**；**託管服務讓升級變簡單但節點升級仍會驅逐 Pod**，**自動升級意味著升級會在你沒準備的時候發生**；以及**升級頻率的取捨**——**跟得鬆時累積的變化多、風險反而更高**。

## 講稿

K8s 每年三個小版本，每個版本支援大約十四個月。所以不升級不是一個選項，落後太多會失去安全修補。

有三個硬性規則。先控制平面再工作節點，因為節點元件可以比 API 伺服器舊最多兩個小版本但不能更新。不能跳版，要逐版升。還有每個版本都有介面被移除，升級前必須確認沒有東西還在用。

介面棄用是升級失敗最常見的原因，而它的隱蔽之處在於既有的資源仍在運行。介面被移除之後，既有的物件通常會被自動轉換成新版本繼續運作，真正壞掉的是你的持續整合腳本或部署套件裡寫的舊版本，下一次部署就直接失敗。所以掃描不能只掃叢集裡現有的資源，還要掃你的程式碼倉庫裡的設定檔，而後者更容易被遺漏。

還有一個常被忽略的，第三方元件的相容性。網路外掛、儲存驅動、入口控制器、操作器都有各自的相容矩陣。實務上的順序是先把它們升到同時支援新舊版本的版本，再升 K8s。

## 常見追問

### 怎麼知道哪些 API 要被移除了？

**核心答案**：**三個來源**。**官方的棄用指南**（Deprecated API Migration Guide 列出每個版本移除了什麼）。**API server 的警告**——**使用棄用 API 時 `kubectl` 會顯示警告，而 API server 也會記錄 `apiserver_requested_deprecated_apis` 指標**。**掃描工具**——Pluto、kubent 能掃描叢集與檔案。

**詳細解析**：**`apiserver_requested_deprecated_apis` 這個指標是最實用的一個，因為它反映的是「實際還有誰在用」**——**包括那些你不知道存在的控制器與腳本**。**掃描 YAML 檔案只能發現你知道的地方**，**而這個指標會抓到「某個第三方 Operator 內部還在呼叫舊 API」這種你完全看不到的情況**。**把它做成告警（「有人在使用即將移除的 API」）能讓問題在升級前幾個月就浮現**，**而不是升級當天才發現**。**這是一個典型的「用可觀測性取代靜態分析」的例子**——**因為靜態分析只能看到程式碼，而指標能看到實際行為**。

**面試回答方式**：給三個來源。核心加分點是強調 **`apiserver_requested_deprecated_apis` 指標最實用**——**它反映實際還有誰在用，包括你不知道存在的控制器與腳本**，**而掃描 YAML 只能發現你知道的地方**。舉出具體價值：**能抓到「某個第三方 Operator 內部還在呼叫舊 API」這種完全看不到的情況**。收在做法與原則：**把它做成告警讓問題在升級前幾個月浮現**，**這是「用可觀測性取代靜態分析」的典型例子**。

### 升級到一半失敗怎麼辦？

**核心答案**：**控制平面的升級基本上不可回滾**——**因為 etcd 中的資料可能已經被新版本轉換過**。**所以策略必須是「前進而非後退」**：**修復問題並完成升級**。**節點的升級則可以回滾**（**用舊版本的節點池替換**），**這也是「用新節點池而非原地升級」的另一個好處**。

**詳細解析**：**「控制平面不可回滾」這個事實應該直接影響準備工作的深度**：**因為沒有退路，所以驗證必須在升級前完成**——**在一個與生產配置相同的非生產叢集完整走一遍，是唯一可靠的準備**。**而「與生產配置相同」是關鍵**：**如果非生產叢集少了某個 Operator 或用了不同的 CNI，那次演練的價值就大打折扣**。**另外，etcd 的備份在升級前是必須的**——**它是最壞情況下唯一的退路（重建叢集並還原資料）**，**雖然那個過程本身很痛苦**。**能主動說出「我會先備份 etcd 並確認備份可還原」，通常表示真的做過生產升級。**

**面試回答方式**：明確指出**控制平面升級基本不可回滾**（etcd 資料可能已被轉換），**所以策略是前進而非後退**；節點可以回滾，**而這是「用新節點池而非原地升級」的另一個好處**。核心加分點是說明這個事實應該影響準備的深度：**沒有退路所以驗證必須在升級前完成**，**在一個與生產配置相同的非生產叢集完整走一遍是唯一可靠的準備**，**而「配置相同」是關鍵**。收在最壞情況的退路：**升級前備份 etcd 並確認可還原**。

### 應用需要為升級做什麼準備？

**核心答案**：**確保它能承受「隨時被重啟並在別的節點重建」**。具體是四件事：**多副本**、**正確的 PDB**（**不要嚴到讓 drain 卡死**）、**優雅終止**（**preStop 加足夠的 grace period**）、**以及沒有本地狀態依賴**（**不要把重要的東西寫在容器的可寫層或未持久化的 emptyDir**）。

**詳細解析**：**這份清單有一個有趣的性質：它與「應用是否雲原生」的檢查清單幾乎完全重合**——**因為升級只是把「Pod 隨時可能被重建」這個 K8s 的基本假設集中地驗證了一次**。**所以「為升級做準備」其實不是一項獨立的工作，而是「應用有沒有正確地適應 K8s」的體檢**。**如果一次叢集升級會導致你的應用出問題，那麼一次節點故障、一次自動擴縮、或一次重新排程也會**——**只是那些發生得更不可預期**。**能做出這個連結，比逐條列出準備事項更能展現理解**：**它把升級從「一件可怕的事」重新定位成「一次計畫中的、可控的韌性驗證」。**

**面試回答方式**：給四件事（多副本、正確的 PDB、優雅終止、無本地狀態依賴）。核心加分點是做出連結：**這份清單與「應用是否雲原生」的檢查清單幾乎完全重合**，**因為升級只是把「Pod 隨時可能被重建」這個基本假設集中驗證了一次**。收在重新定位：**如果升級會讓應用出問題，那節點故障、自動擴縮、重新排程也會，只是那些更不可預期**——**所以升級其實是一次計畫中的、可控的韌性驗證**。
