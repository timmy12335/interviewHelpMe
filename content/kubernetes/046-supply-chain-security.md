# 題目

怎麼確保叢集裡跑的是「你打算跑的東西」？

## 核心答案

**問題的本質是「從程式碼到執行中的容器，中間有多個環節可以被替換」**——**依賴套件、基底映像、建置流程、映像倉庫、以及部署設定**。**供應鏈安全就是在每個環節建立可驗證的來源。**

**四個核心實踐**。**簽章**——**用 Sigstore/cosign 對映像簽章，並在 admission 階段驗證簽章**（Kyverno 或 Connaisseur）；**沒有有效簽章的映像不准部署**。**SBOM**——**產生軟體物料清單記錄映像裡有哪些套件與版本**，**讓「某個 CVE 影響我們哪些服務」變成一次查詢而非一場考古**。**來源證明（provenance）**——**記錄「這個映像由哪個 CI、從哪個 commit、用什麼流程建置」**，SLSA 框架定義了它的等級。**倉庫限制**——**admission 政策只允許從信任的倉庫拉取**。

## 詳細解析

**「SBOM 的價值在事故當下才會顯現」**。Log4Shell 那次事件裡，**多數團隊花了好幾天才回答出「我們哪些服務用了受影響的版本」**——**而有 SBOM 的團隊在幾分鐘內就有答案**。**這個差距不是技術能力的差距，而是「有沒有預先建立索引」的差距**。**所以 SBOM 的投入應該被理解成「為未來的緊急事件預付成本」**——**它在平時完全沒有用，而那正是它容易被砍掉的原因**。

**簽章驗證的關鍵是「在 admission 階段強制」而非「在 CI 階段檢查」**。CI 的檢查可以被繞過（**直接 `kubectl apply` 一個不同的映像**）——**而 admission 是所有進入叢集的請求都必須經過的關卡**。**這體現了一個一般性的原則：控制點應該放在「無法繞過的地方」**，**而在 K8s 裡那就是 admission**。

**「只允許信任的倉庫」是投入最小、效果最直接的一條**。它擋掉的是一整類問題：**開發者不小心用了公開倉庫的同名映像**（typosquatting）、**測試用的映像跑到生產**、**以及被入侵後從外部倉庫拉取惡意映像**。**一條 admission 規則就能建立這道防線**，**而它幾乎不影響正常的開發流程**。

**依賴層面的防護同樣重要**：**鎖定版本（lock file）並提交進 Git**、**用私有的套件代理而非直接連公開倉庫**、**以及對依賴更新做自動化的掃描與測試**。**「基底映像自動重建」在這裡也適用**——**大部分映像漏洞來自基底，定期重建比逐個修補有效得多**。

## 面試回答方式

先給問題的本質——**從程式碼到執行中的容器，中間有多個環節可以被替換**，並列出那些環節。給四個核心實踐（簽章加 admission 驗證、SBOM、來源證明、倉庫限制）。加分點有四個：**SBOM 的價值在事故當下才顯現**——**Log4Shell 時多數團隊花好幾天回答「哪些服務受影響」而有 SBOM 的幾分鐘就有答案**，**所以它應該被理解成「為未來的緊急事件預付成本」**；**簽章驗證必須在 admission 而非 CI 強制**——**CI 可以被繞過而 admission 是所有請求的必經關卡**，**體現了「控制點要放在無法繞過的地方」這個原則**；**「只允許信任的倉庫」投入最小效果最直接**，擋掉 typosquatting、測試映像跑到生產、以及被入侵後拉取惡意映像；以及**基底映像自動定期重建比逐個修補有效**。

## 講稿

問題的本質是從程式碼到執行中的容器，中間有多個環節可以被替換。依賴套件、基底映像、建置流程、映像倉庫、還有部署設定。供應鏈安全就是在每個環節建立可驗證的來源。

我會做四件事。對映像簽章並且在准入階段驗證、產生軟體物料清單、記錄建置的來源證明、還有用政策限制只能從信任的倉庫拉取。

這裡有一個原則我想強調。簽章驗證必須在准入階段強制，而不是在持續整合階段檢查。因為持續整合的檢查可以被繞過，有人直接套用一個不同的映像就行了。而准入是所有進入叢集的請求都必須經過的關卡。控制點應該放在無法繞過的地方。

還有物料清單的價值，它在事故當下才會顯現。上次那個廣泛的日誌函式庫漏洞爆發時，多數團隊花了好幾天才回答出我們哪些服務用了受影響的版本，而有清單的團隊幾分鐘就有答案。這不是技術能力的差距，是有沒有預先建立索引的差距。所以它應該被理解成為未來的緊急事件預付成本。

## 常見追問

### cosign 的 keyless 簽章是怎麼運作的？

**核心答案**：**用「短期憑證加透明日誌」取代長期私鑰**。CI 用它的 OIDC 身份（例如 GitHub Actions 的 token）向 Fulcio 換取一張**只有幾分鐘有效期的簽章憑證**，**用它簽章後把記錄寫入 Rekor 這個公開的透明日誌**。**驗證時檢查「這個簽章對應的身份是不是預期的 CI 工作流程」**——**而不是檢查某把私鑰**。

**詳細解析**：**它解決的是「金鑰管理」這個長期難題**：**傳統簽章需要保管一把私鑰，而那把鑰匙的洩漏、輪換、與存取控制都是持續的負擔**。**keyless 的做法讓「誰簽的」由身份系統回答**——**於是驗證政策可以寫成「必須由 `github.com/myorg/myrepo` 的 main 分支工作流程簽章」**，**這比「必須由某把公鑰驗證通過」表達力強得多，也更符合實際想表達的信任關係**。**透明日誌則提供了不可否認性**：**任何人都可以查詢某個映像的簽章記錄**，**而攻擊者無法悄悄地簽一個惡意映像然後刪除記錄**。**這套設計是近年供應鏈安全最重要的進展之一。**

**面試回答方式**：給機制（OIDC 身份換短期憑證、簽章後寫入透明日誌、驗證時檢查身份而非私鑰）。核心加分點是說明**它解決的是金鑰管理這個長期難題**，並指出**驗證政策可以寫成「必須由某個 repo 的 main 分支工作流程簽章」**，**這比「必須由某把公鑰驗證」表達力強得多也更符合實際想表達的信任關係**。收在透明日誌提供的不可否認性：**任何人都能查詢簽章記錄，攻擊者無法悄悄簽一個惡意映像然後刪除記錄**。

### 漏洞掃描的結果該怎麼處理？

**核心答案**：**按「可利用性」而非「CVSS 分數」排序**。一個高分的 CVE 如果**存在於一個你根本沒有引入的程式碼路徑，或者需要本地存取才能利用**，**它的實際風險遠低於一個中等分數但能遠端觸發的漏洞**。**所以優先處理：有已知在野利用的、能遠端觸發的、以及影響對外服務的。**

**詳細解析**：**「可達性分析」是這個領域近年的重要進展**：**新一代的掃描工具能判斷「這個有漏洞的函式是否真的被你的程式碼呼叫到」**——**而實測上，一個映像報出的上百個 CVE 中，實際可達的往往只有個位數**。**這把「無法處理的清單」變成「幾個明確的待辦」**，**是讓漏洞管理從形式主義變成實質工作的關鍵**。**另一個實務原則是「區分阻擋與追蹤」**：**阻擋發布的門檻應該很高（有在野利用且可達），其餘進入一個有負責人與期限的追蹤清單**——**因為把門檻設得太低會讓團隊學會繞過檢查，而那比沒有檢查更糟**。

**面試回答方式**：主張**按可利用性而非 CVSS 分數排序**並給出優先順序。核心加分點是**可達性分析**：**新一代工具能判斷有漏洞的函式是否真的被呼叫到，而實測上上百個 CVE 中實際可達的往往只有個位數**，**這把「無法處理的清單」變成「幾個明確的待辦」**。收在原則：**區分阻擋與追蹤**——**阻擋的門檻要很高，因為設得太低會讓團隊學會繞過檢查，而那比沒有檢查更糟**。

### 開發者的體驗會不會被這些管控拖垮？

**核心答案**：**會，如果設計成「事後攔截」的話**。**正確的做法是把檢查左移並自動化**：**簽章在 CI 自動完成（開發者不需要知道）**、**掃描結果直接在 PR 上顯示**、**政策違規在本地就能用 CLI 檢查**。**目標是「符合規範是預設路徑」而不是「符合規範需要額外的工作」。**

**詳細解析**：**「預設安全的黃金路徑」是平台工程在這裡的核心產出**：**提供一套標準的 CI 模板與部署模板，用了它就自動滿足所有政策**——**於是絕大多數團隊根本不需要理解那些政策的細節**。**而只有需要偏離標準的少數情況才需要走例外流程**。**這比「寫一份安全規範然後期待每個團隊遵守」有效得多**，**因為它把「做對的事」變成阻力最小的路徑**。**反過來，如果符合規範需要每個團隊各自研究與實作，那麼實際的合規率會很低，而且會隨團隊變動而退化**——**這不是紀律問題，是流程設計問題**。

**面試回答方式**：誠實回答**會，如果設計成事後攔截的話**，並給正確做法（檢查左移、簽章在 CI 自動完成、掃描結果顯示在 PR、政策能在本地檢查），給出目標：**符合規範是預設路徑而非額外工作**。核心加分點是**預設安全的黃金路徑**：**提供標準的 CI 與部署模板，用了就自動滿足所有政策，絕大多數團隊根本不需要理解細節**。收在判斷：**「寫規範然後期待遵守」的合規率很低且會隨團隊變動退化**——**這不是紀律問題，是流程設計問題**。
