# 題目

「宣告期望狀態、控制器持續校正」這句話具體是怎麼運作的？為什麼說 K8s 是宣告式而不是命令式？

## 核心答案

核心是 **Reconcile 迴圈**：每個控制器持續比對「期望狀態」與「實際狀態」，發現差異就執行動作把實際拉向期望，然後再比對，永不停止。

以 Deployment 為例：你宣告 `replicas: 3`，這是期望狀態，存在 etcd 裡。ReplicaSet controller 透過 watch 得知這個期望，去數實際有幾個 Pod——只有 2 個就建 1 個，有 4 個就刪 1 個。**沒有人下「建立 Pod」這個指令**，是控制器自己算出差異後採取的行動。

這和命令式的差別在於**誰負責維持**。命令式是「執行這個動作」，執行完就結束，之後狀態飄移了沒人管；宣告式是「維持這個狀態」，控制器會**持續**校正，所以你手動刪掉一個 Pod 它會自己長回來，節點掛了它會在別處重建。

這也帶來一個重要性質：**動作必須是冪等的**。Reconcile 可能因為重試、重啟、事件重送而執行很多次，每一次都必須是「看現況、算差異、補上不足」，而不是「無條件再做一次」。

## 詳細解析

**控制器不是輪詢**：它透過 apiserver 建立 **watch**，資源變更時收到事件並放進工作佇列，再由 worker 取出執行 reconcile。同時也有定期的全量重新同步，作為漏掉事件的保險。這個「事件驅動 + 定期兜底」的組合，是所有控制器的共同結構。

**期望狀態在 spec，實際狀態在 status**：這是 K8s 資源的通用結構。使用者寫 `spec`，控制器讀 `spec` 並回寫 `status`。理解這個分工就能解釋為什麼不該手動改 `status`——那是控制器的輸出，你改了下一次 reconcile 就被覆蓋。

**控制器是分層的**：Deployment controller 不直接管 Pod，它管的是 **ReplicaSet**；ReplicaSet controller 才管 Pod。滾動更新的實作就是 Deployment controller 建立新的 ReplicaSet、逐步把新 RS 的副本數往上調、舊 RS 往下調。這也解釋了為什麼回滾很快——舊的 ReplicaSet 還留著，只要把副本數調回去即可。

Reconcile 是「向著期望前進一步」而不是「一次到位」：控制器每次執行不必把所有事情做完，只要讓狀態更接近期望，下一輪繼續即可。這讓控制器可以寫得很簡單，也讓它天然容忍中斷——寫到一半掛掉，重啟後重新比對現況繼續做就好，不需要記住上次做到哪。

**這個模式可以被使用者延伸**：CRD 加上自訂控制器（也就是 Operator）用的是完全同一套機制——定義新的資源型別表達期望，寫一個控制器持續校正。理解 reconcile 就理解了 K8s 擴充性的全部基礎。

## 面試回答方式

用 Deployment 的具體例子講 reconcile，比抽象定義有效——宣告 3 個副本，控制器去數實際有幾個，少了就補、多了就刪，沒有人下「建立 Pod」這個指令。接著用**誰負責維持**切開宣告式與命令式：命令式執行完就結束、之後飄移沒人管；宣告式會持續校正，所以手動刪 Pod 會自己長回來。一定要提到**冪等性**的要求，並解釋原因——reconcile 會因重試與重啟執行很多次。加分點：控制器是事件驅動加定期兜底，不是輪詢；spec 是期望、status 是控制器輸出，所以不該手動改 status；以及 Deployment 管 ReplicaSet、ReplicaSet 才管 Pod 這個分層，能順帶解釋為什麼回滾很快。

## 講稿

核心是一個永不停止的迴圈：比對期望狀態跟實際狀態，有差異就採取動作把實際拉向期望，然後再比對。

用 Deployment 舉例最清楚。你宣告 replicas 等於三，這是期望狀態。ReplicaSet controller 透過 watch 知道這件事，去數實際有幾個 Pod，只有兩個就建一個，有四個就刪一個。注意這裡沒有人下過「建立 Pod」這個指令，是控制器自己算出差異之後採取的行動。

宣告式跟命令式的差別，關鍵在誰負責維持。命令式是執行這個動作，跑完就結束，之後飄走了沒人管。宣告式是維持這個狀態，所以你手動刪掉一個 Pod 它會自己長回來。

這個模式帶來一個要求：動作必須是冪等的。因為重試、重啟、事件重送都會讓 reconcile 跑很多次，每一次都必須是看現況、算差異、補上不足，而不是無條件再做一次。

還有個巧妙處。Reconcile 是向著期望前進一步，不是一次到位。所以它天然容忍中斷，寫到一半掛掉，重啟後重新比對現況繼續做就好。

## 常見追問

### 為什麼手動刪掉一個 Pod，它會自己長回來？

**核心答案**：因為 Pod 是被 **ReplicaSet 擁有**的。刪掉之後 ReplicaSet controller 的下一輪 reconcile 發現實際副本數少於 `spec.replicas`，就會建立一個新的補上。這正是宣告式的體現——你刪的是「實際狀態」，但「期望狀態」沒變，控制器的職責就是把兩者拉回一致。

**詳細解析**：控制器靠 Pod 的 `ownerReferences` 知道哪些 Pod 屬於自己，所以它數的是「帶有我的 ownerReference 且符合我的 selector 的 Pod」。要真正移除就必須改變期望——縮減副本數或刪掉 Deployment。刪掉 Deployment 時，垃圾回收會依 `ownerReferences` 連帶刪除 ReplicaSet 與 Pod，這叫級聯刪除；如果用 `--cascade=orphan` 則會留下孤兒 Pod，它們不再被任何控制器管理，死了也不會重建。另外要注意「新建的 Pod 是全新的」——名稱、IP 都不同，任何硬記 Pod IP 的呼叫方都會斷線，這也是為什麼要透過 Service 尋址。

**面試回答方式**：用「你刪的是實際狀態，期望狀態沒變」這句話回答，直指宣告式的本質。補充 `ownerReferences` 是控制器認得自己 Pod 的依據。加分點是講級聯刪除與 `--cascade=orphan` 的差別，以及新 Pod 是全新 IP 所以要透過 Service 尋址。

### 為什麼 Deployment 回滾可以那麼快？

**核心答案**：因為 Deployment 管理的是 ReplicaSet，而舊的 ReplicaSet 沒有被刪除，只是副本數被調成 0。滾動更新的實作就是「新 RS 副本數往上加、舊 RS 往下減」，所以回滾只是把這個過程反過來——把舊 RS 調回去、新 RS 調成 0，不需要重新拉映像檔、重新建立任何定義。

**詳細解析**：保留幾份歷史由 `revisionHistoryLimit` 控制（預設 10），設成 0 就無法回滾，這是個容易誤設的參數。要注意**回滾的是 Pod template，不是所有東西**——ConfigMap、Secret 的內容不會跟著回滾，如果新版同時改了設定，回滾 Deployment 之後應用可能拿到新設定配舊程式碼，行為難以預期。這是「設定與程式碼要一起版本化」的實務理由，也是為什麼很多團隊把設定的雜湊放進 Pod template 的 annotation——這樣設定變更本身就會產生新的 revision，回滾時自然一起回去。另外資料庫 schema 的遷移通常不可逆，回滾程式碼不等於回滾資料，這要靠向前相容的遷移設計來解決。

**面試回答方式**：核心是「舊 ReplicaSet 還在，只是副本數為 0」，回滾只是調整數字。點出 `revisionHistoryLimit` 設成 0 會無法回滾。加分點是講清楚回滾只回 Pod template，ConfigMap 不跟著回，並給出把設定雜湊放進 annotation 的解法，以及提醒資料庫遷移不可逆。

### 自己寫控制器時，reconcile 函式要注意什麼？

**核心答案**：最重要的是**冪等**——同一個 reconcile 對同一個狀態執行一次和執行十次，結果必須相同。因為事件可能重送、程式可能重啟、佇列可能重試，你無法假設它只跑一次。實作上的正確心態是「**看現況、算差異、補上不足**」，而不是「收到事件所以做一個動作」。

**詳細解析**：其次是**不要在 reconcile 裡阻塞**。它應該快速返回，需要等待的事情用「返回並要求稍後重試」的方式表達（多數框架提供 requeue 機制），而不是在函式裡 sleep——阻塞會佔住 worker，影響其他物件的處理。第三是**謹慎處理錯誤與重試**：外部呼叫失敗應該返回錯誤讓框架用指數退避重試，而不是自己吞掉；但也要避免對永久性錯誤無限重試，那會塞爆佇列。第四是用 status 記錄觀察結果、用 events 記錄重要動作，讓使用者能理解控制器在做什麼——一個沉默的控制器在出問題時極難排查。最後是**owner reference 要設對**，這決定了資源的級聯刪除是否正確，設錯會留下清不掉的孤兒資源。

**面試回答方式**：把冪等放在第一位並解釋原因（事件重送、重啟、重試），給出「看現況算差異」的正確心態。接著列出不要阻塞、錯誤用退避重試但避免無限重試、用 status 與 events 讓行為可觀察、owner reference 要設對。加分點是指出沉默的控制器極難排查。
