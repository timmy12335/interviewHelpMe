# 題目

Helm 與 Kustomize 的差異是什麼？多環境設定該怎麼管？

## 核心答案

根本差異是「模板」與「疊加」兩種思路。

**Helm 是模板引擎加套件管理**：用 Go template 把 YAML 參數化，用 values 檔提供不同環境的值，**並且管理發布的版本與相依**（可以 rollback、可以依賴其他 chart）。**優點是分發能力強**——第三方元件用 Helm chart 安裝已經是事實標準；缺點是模板化的 YAML 可讀性差，除錯時要先 `helm template` 渲染出來才知道真正送出去的是什麼。

**Kustomize 是無模板的疊加**：**base 是一份完全合法的 YAML，overlay 用 patch 修改它**。優點是每一份檔案都是可以直接 apply 的合法 YAML，**沒有模板語法，可讀性好**；缺點是複雜的參數化很笨拙，也沒有套件分發與版本管理的概念。

實務上的常見組合是「用 Helm 安裝第三方元件，用 Kustomize 管自己的應用」——**各取所長。**

## 詳細解析

「Helm 的複雜度來自它試圖同時做三件事」：模板、套件管理、以及發布狀態追蹤。**第三件事是很多問題的來源**——Helm 把發布狀態存在 Secret 裡，而當一次升級中途失敗時，狀態可能停在 `pending-upgrade` 而讓後續操作全部被拒絕。這種「工具自己的狀態損壞」是 Helm 最令人挫折的失敗模式，而 Kustomize 完全沒有這個問題，因為它只是產生 YAML，狀態完全在叢集裡。

**Helm 的 hook 機制解決了順序問題**（`pre-install`、`pre-upgrade`、`post-install`）——**這是 Kustomize 沒有的能力**，而它在「升級前先跑資料庫遷移」這類需求上很有用。**但 hook 的失敗處理很粗糙**，而且它與 GitOps 的宣告式模型不太相容——**這也是為什麼 Argo CD 有自己的 sync hook 機制**。

「Kustomize 的 patch 在複雜情況下會變難維護」是一個真實的限制。**strategic merge patch 對列表的處理不直觀**（修改容器陣列裡的某一項需要靠名稱匹配），而 JSON patch 雖然精確但寫起來很囉唆且脆弱（**依賴索引位置**）。當 overlay 的層數超過兩層時，「最終產生的到底是什麼」會變得很難推理——這時應該用 `kubectl kustomize` 渲染出來檢查，而不是靠腦補。

共同的最佳實踐是「渲染後的結果要能被審查」：無論用哪個工具，CI 都應該產生最終的 YAML 並讓它出現在 PR 的 diff 裡——因為人審查的應該是「實際會套用什麼」，而不是「模板長什麼樣」。

## 面試回答方式

先給根本差異——**模板 vs 疊加**，並說明各自的優缺點（Helm 分發能力強但模板化 YAML 可讀性差；Kustomize 每份都是合法 YAML 但複雜參數化笨拙且無套件管理）。給實務組合（**Helm 裝第三方、Kustomize 管自己的應用**）。加分點有四個：Helm 的複雜度來自它同時做三件事，而發布狀態追蹤是很多問題的來源——升級中途失敗會讓狀態卡在 pending 讓後續操作全被拒絕，**而 Kustomize 沒有這問題因為它只產生 YAML**；Helm 的 hook 解決順序問題但失敗處理粗糙且與 GitOps 不相容；**Kustomize 的 patch 在超過兩層 overlay 後很難推理**，**應該渲染出來檢查而非腦補**；以及共同的最佳實踐是讓渲染後的結果出現在 PR 的 diff 裡——人審查的應該是實際會套用什麼。

## 講稿

根本差異是模板跟疊加兩種思路。

Helm 是模板引擎加套件管理，用模板語法把設定檔參數化，還管理發布版本跟相依。它的分發能力很強，第三方元件用它安裝已經是事實標準。缺點是模板化之後的設定檔可讀性差，除錯要先渲染出來才知道真正送出去的是什麼。

Kustomize 是無模板的疊加。基底是一份完全合法的設定檔，覆蓋層用修補去改它。每一份檔案都能直接套用，可讀性好。缺點是複雜的參數化很笨拙，也沒有套件分發的概念。

我實務上的組合是用 Helm 裝第三方元件，用 Kustomize 管自己的應用。

還有一點值得提。Helm 的複雜度來自它同時做三件事，模板、套件管理、還有發布狀態追蹤。第三件是很多問題的來源，一次升級中途失敗的話，狀態可能卡住讓後續操作全被拒絕。而 Kustomize 完全沒有這個問題，因為它只是產生設定檔，狀態全在叢集裡。

## 常見追問

### 多環境的差異該怎麼組織？

**核心答案**：**把「結構」與「值」分開**。**結構相同的部分放 base**（Deployment、Service、以及所有環境都一樣的欄位）；環境差異只放真正不同的東西——副本數、資源大小、映像標籤、以及環境特定的設定值。如果 overlay 裡開始出現整段的資源定義，那通常表示 base 的抽象不對。

**詳細解析**：「環境之間應該盡可能相同」是一條比工具選擇更重要的原則。每一個環境特有的設定都是一個「在測試環境不會被驗證到」的東西——於是「測試通過但生產失敗」的機率上升。所以理想的差異只有三類：規模（副本數與資源）、外部端點（資料庫位址、API 網址）、以及功能旗標。而「生產有而測試沒有」的元件（例如只在生產啟用的快取層或限流）是最危險的一類差異——它意味著那條程式碼路徑從未在部署前被執行過。能主動指出「差異本身就是風險」，比熟練使用任何工具更能展現判斷。

**面試回答方式**：給組織原則（結構放 base、只有真正不同的值放 overlay）並給出檢驗：overlay 裡出現整段資源定義通常表示 base 的抽象不對。核心加分點是主張「環境之間應該盡可能相同」比工具選擇更重要——每個環境特有的設定都是「測試環境不會被驗證到」的東西，理想的差異只有規模、外部端點、功能旗標三類。收在最危險的一類：生產有而測試沒有的元件意味著那條程式碼路徑從未在部署前被執行過。

### Helm chart 該自己寫還是用社群的？

**核心答案**：第三方元件用社群的，自己的應用用一個內部統一的模板。社群 chart 的價值是它封裝了那個元件的運維知識（正確的探針、合理的預設、必要的資源）——自己重寫等於重新踩一遍別人踩過的坑。但要注意「社群 chart 的品質參差不齊」：選擇前應該看維護活躍度、下載量、以及它的 values 是否暴露了你需要的參數。

**詳細解析**：「用社群 chart 但不要盲目升級」是一個實務要點：chart 的新版本可能改變預設值、重新命名 values 的鍵、或者引入新的資源——**而 `helm upgrade` 會忠實地套用這些變化**。所以升級前應該先 `helm diff`（一個很有價值的外掛）看實際會改什麼。至於自己的應用，寫一個「內部通用 chart」比每個服務各寫一份好得多：把探針、資源、標籤、安全上下文的標準做法固化在裡面，**各服務只提供少量的 values**——這讓平台團隊的最佳實踐能被自動套用到所有服務，而不是靠文件與提醒。這是「用工具固化標準」勝過「用文件傳達標準」的典型例子。

**面試回答方式**：給分工（第三方用社群、自己的用內部統一模板）並說明社群 chart 的價值是**封裝了那個元件的運維知識**，但要看維護活躍度與 values 是否暴露所需參數。加分點是**不要盲目升級**——新版可能改預設值、改鍵名、引入新資源，**升級前用 `helm diff` 看實際會改什麼**。核心加分點是**內部通用 chart**：把探針、資源、標籤、安全上下文的標準固化在裡面，各服務只提供少量 values，讓最佳實踐被自動套用而不是靠文件與提醒——這是「用工具固化標準」勝過「用文件傳達標準」的典型例子。

### 怎麼確保 YAML 的正確性？

**核心答案**：**四層驗證，越早越好**。**語法與 schema**——`kubeconform` 或 `kubectl apply --dry-run=server`（**後者會經過 admission webhook，能抓到政策違規**）。**政策**——OPA/Gatekeeper 或 Kyverno 的規則（**例如必須設 resources、必須非 root**）。**最佳實踐掃描**——kube-linter、Polaris。**實際部署驗證**——**在測試叢集真的套用一次**。

**詳細解析**：**`--dry-run=server` 與 `--dry-run=client` 的差別值得知道**：client 只做本地的 schema 驗證，server 則真的送到 API server 走完整的驗證與 admission 鏈但不持久化——所以只有後者能抓到「違反了叢集政策」或「引用了不存在的資源」這類問題。**在 CI 裡用 server dry-run 需要能連到一個叢集**，這是它的代價，但也是它能抓到的問題遠多於本地驗證的原因。另一個實用的建議是「把政策檢查左移到本地」：**同一套 Kyverno 規則可以用 CLI 在本地跑**——讓開發者在提交前就知道會不會被擋，而不是等到 CI 或部署時。這個「同一套規則在多個階段執行」的模式，比在每一層各寫一套檢查可靠得多。

**面試回答方式**：給四層驗證。核心加分點是 **`--dry-run=server` 與 `client` 的差別**：只有 server 會走完整的驗證與 admission 鏈，能抓到政策違規與引用不存在的資源，**代價是 CI 需要能連到叢集**。第二個是**把政策檢查左移到本地**：同一套規則用 CLI 在本地跑，讓開發者提交前就知道會不會被擋，而這個「同一套規則在多個階段執行」的模式比每層各寫一套檢查可靠得多。
