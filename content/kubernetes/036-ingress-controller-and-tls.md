# 題目

Ingress Controller 怎麼選？憑證管理該怎麼做？

## 核心答案

**Ingress 資源本身只是一份宣告**——**真正處理流量的是 Ingress Controller**，而不同的 controller 對同一份 Ingress 的行為可能不同（尤其是 annotation 的部分，**那是各家自訂的擴充**）。

**選型的三個維度**。**功能**——需要的重寫、限流、認證、金絲雀是否原生支援。**效能與資源**——Nginx Ingress 成熟穩定；Envoy 系（Contour、Emissary）的動態設定更新不需要 reload；HAProxy 效能好。**與環境的整合**——雲端託管的 Ingress（GKE Ingress、AWS ALB Controller）直接使用雲端負載平衡器，省去自己維運資料平面，但功能受限於該雲端提供的能力。

**TLS 管理的標準答案是 cert-manager**：它把憑證表達成 K8s 資源（Certificate、Issuer），自動向 Let's Encrypt 或內部 CA 申請、自動續期、並把結果寫進 Secret 供 Ingress 使用——把「憑證到期忘記換」這個經典事故變成不會發生的事。

## 詳細解析

「annotation 的可攜性很差」是使用 Ingress 最大的痛點。同一個「重寫路徑」的需求，Nginx 用 `nginx.ingress.kubernetes.io/rewrite-target`，其他 controller 用完全不同的寫法——**於是換 controller 幾乎等於重寫所有 Ingress**。**Gateway API 正是為了解決這個問題**：它把常見的進階功能（分流、標頭操作、跨命名空間路由）標準化成正式的 API 欄位而非 annotation，**並且把角色分離**（基礎設施團隊管 Gateway，應用團隊管 HTTPRoute）。**新專案值得直接評估 Gateway API。**

憑證續期的失敗是一個必須被監控的事。cert-manager 會自動續期，**但續期可能失敗**（DNS 驗證的記錄被改、ACME 的速率限制、網路問題）——而失敗是靜默的，直到憑證真的到期。所以必須對「憑證剩餘有效天數」設告警（例如少於 14 天就告警），**而不是信任自動化一定成功**。這是「自動化了但沒有監控」這類問題的典型案例——自動化降低了故障頻率，卻讓故障變得更難察覺。

**TLS 終止的位置是一個架構決定**。**在 Ingress 終止**——最常見，後端用明文，簡單但叢集內流量未加密。**穿透到 Pod**——後端自己處理 TLS，適合合規要求端到端加密的場景。**在 Ingress 終止後重新加密**——兼顧了「Ingress 能看到七層資訊做路由」與「內部流量加密」，**是零信任架構的常見選擇**，**而 service mesh 的 mTLS 能自動化這一層**。

**一個 Ingress Controller 還是多個？** **按暴露面分開通常是對的**：對外的與對內的用不同的 controller 與不同的負載平衡器——這讓「內部服務意外對外暴露」在架構上就不可能發生，**比依賴設定正確可靠得多**。

## 面試回答方式

先澄清Ingress 只是宣告，真正處理流量的是 controller，而 annotation 是各家自訂的擴充所以行為可能不同。給選型的三個維度並提到雲端託管 Ingress 的取捨。給 **cert-manager 作為 TLS 的標準答案**並說明它把「憑證到期忘記換」變成不會發生的事。加分點有四個：**annotation 的可攜性很差**——**換 controller 幾乎等於重寫所有 Ingress**，而 Gateway API 正是為解決這個問題把進階功能標準化成正式欄位並分離角色；**憑證續期失敗是靜默的**，**必須對剩餘有效天數告警**，這是「自動化了但沒有監控」的典型案例——自動化降低了故障頻率卻讓故障更難察覺；**TLS 終止位置的三個選擇**與零信任下的重新加密；以及**對外與對內用不同的 controller**，讓「內部服務意外對外暴露」在架構上就不可能發生。

## 講稿

首先要澄清一點，入口資源本身只是一份宣告，真正處理流量的是控制器，而不同控制器對同一份宣告的行為可能不同，尤其是註解的部分，那是各家自訂的擴充。

選型我會看三個維度，需要的功能是否原生支援、效能與資源開銷、還有跟環境的整合。雲端託管的入口直接用雲端的負載平衡器，省去自己維運資料平面，但功能受限於那朵雲提供的能力。

用入口資源最大的痛點是註解的可攜性很差。同一個路徑重寫的需求，不同控制器的寫法完全不同，換控制器幾乎等於重寫所有設定。閘道介面正是為了解決這個問題，它把常見的進階功能標準化成正式的欄位而不是註解，而且把角色分離，基礎設施團隊管閘道，應用團隊管路由。

憑證管理我會用專門的控制器自動申請跟續期。但有一點要特別注意，續期失敗是靜默的，直到憑證真的到期。所以一定要對憑證剩餘有效天數設告警。這是自動化了但沒有監控的典型案例，自動化降低了故障頻率，卻讓故障變得更難察覺。

## 常見追問

### Ingress、LoadBalancer Service 與 Gateway API 怎麼選？

**核心答案**：**按需求的複雜度往上走**。**LoadBalancer Service**——單一服務直接暴露，每個服務一個雲端負載平衡器，成本高但最簡單，適合少量服務或需要四層的場景。**Ingress**——多個服務共用一個負載平衡器並按主機名或路徑路由，是七層場景的預設選擇。**Gateway API**——需要進階路由、跨命名空間、或者要在多個 controller 間保持可攜時。

**詳細解析**：成本常常是被忽略的決定因素：每個 LoadBalancer Service 在雲端都是一個獨立的負載平衡器，月費從幾十美元起跳——二十個服務就是一筆可觀的固定成本，而用一個 Ingress 承載它們可能只需要一個。這個計算在小團隊裡經常決定了架構選擇。至於 Gateway API 的角色分離，它解決的是一個真實的組織問題：Ingress 把「TLS 憑證、負載平衡器設定」與「應用的路由規則」混在同一個資源裡——於是應用團隊需要能修改涉及基礎設施的欄位。Gateway API 把它們拆成 Gateway（平台團隊擁有）與 HTTPRoute（應用團隊擁有），**讓權限邊界與職責邊界對齊**——這比任何單一功能的改進都更有價值。

**面試回答方式**：按複雜度給三者的適用場景。加分點是指出**成本常被忽略**：每個 LoadBalancer Service 都是一個獨立的雲端負載平衡器，月費幾十美元起跳，二十個服務就是可觀的固定成本，**而一個 Ingress 可能只需要一個**。核心加分點是說明 Gateway API 的角色分離解決的是真實的組織問題：Ingress 把 TLS 與負載平衡器設定跟應用路由混在同一個資源，於是應用團隊需要能改基礎設施欄位，而 Gateway 與 HTTPRoute 的拆分讓權限邊界與職責邊界對齊。

### 憑證存在 Secret 裡安全嗎？

**核心答案**：預設不夠安全，因為 Secret 只是 base64 編碼而非加密。**改善的三個層次**：**開啟 etcd 的靜態加密**（`EncryptionConfiguration`，讓 Secret 在 etcd 中是密文）、**用 RBAC 嚴格限制誰能讀 Secret**（尤其要注意「能在該 namespace 建立 Pod 的人就能掛載該 namespace 的 Secret」）、**以及用外部密鑰管理系統**（Vault、雲端 KMS）配合 CSI driver 或 External Secrets Operator。

**詳細解析**：「能建立 Pod 就能讀 Secret」這個提權路徑最常被忽略：RBAC 可以禁止某人 `get secrets`，但如果他能建立 Pod，他就能建立一個掛載該 Secret 並把內容印出來的 Pod——**於是限制形同虛設**。真正的隔離需要 namespace 級的分離加上對 Pod 建立權限的控制，或者用 admission 政策限制哪些 ServiceAccount 能掛載哪些 Secret。至於外部密鑰管理，它的核心價值不只是加密，**而是「輪換」與「審計」**：密鑰在 Vault 中可以被定期輪換並記錄每一次存取，**而 K8s Secret 本身沒有這些能力**。所以選擇它的理由通常是合規而非單純的安全性提升。

**面試回答方式**：明確指出**Secret 只是 base64 編碼而非加密**，給三個改善層次。核心加分點是**「能建立 Pod 就能讀 Secret」這個提權路徑**：RBAC 禁止 get secrets 但能建立 Pod 的人可以掛載它並印出來，於是限制形同虛設，真正的隔離需要 namespace 分離加上對 Pod 建立權限的控制。收在外部密鑰管理的真正價值：**不只是加密，而是輪換與審計**——K8s Secret 本身沒有這些能力，所以選擇它的理由通常是合規。

### 怎麼做藍綠或金絲雀發布？

**核心答案**：**Ingress 層的分流是最直接的方式**。Nginx Ingress 支援 `canary` 系列 annotation（按權重、標頭、或 cookie 分流）；**Gateway API 則用 HTTPRoute 的 `weight` 欄位原生表達**。**更完整的方案是 Argo Rollouts 或 Flagger**——它們接管部署過程，自動地逐步調整權重並在指標劣化時回滾。

**詳細解析**：「自動分析」是這些工具的核心價值，而非分流本身。手動調權重誰都會——難的是「怎麼知道新版本是好的」：Flagger 會在每一步之後查詢 Prometheus，比對新舊版本的錯誤率與延遲，達標才繼續、不達標就回滾。這把發布從「人盯著儀表板」變成「系統自己判斷」——而後者更快、更一致、也不受人的疲勞影響。設定它的關鍵是「選對指標與閾值」：指標要能在觀察窗口內收集到足夠樣本（低流量服務可能需要很長的窗口才有統計意義），閾值要嚴到能抓住問題但寬到不會被正常波動觸發。這個調校往往需要幾次真實發布才能穩定，所以初期應該保留人工確認的關卡。

**面試回答方式**：給 Ingress 層分流的做法（Nginx 的 canary annotation、Gateway API 的 weight）與更完整的工具。核心加分點是指出這些工具的核心價值是自動分析而非分流本身——**難的是知道新版本是好的**，Flagger 每一步後查詢指標比對新舊版本，達標才繼續、不達標就回滾，把發布從「人盯儀表板」變成「系統自己判斷」。收在調校的難處：指標要能在觀察窗口內收集到足夠樣本（低流量服務需要很長窗口）、閾值要嚴到抓得住又寬到不誤觸，所以初期應該保留人工確認的關卡。
