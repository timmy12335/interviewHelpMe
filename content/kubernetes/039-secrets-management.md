# 題目

K8s 的 Secret 到底安不安全？外部密鑰管理該怎麼整合？

## 核心答案

**Secret 預設只是 base64 編碼，不是加密**——**任何能讀取它的人或能存取 etcd 的人都能拿到明文**。**它與 ConfigMap 的真正差別只有三個**：**存取有獨立的 RBAC 資源類型**、**掛載時預設用 tmpfs（不落到節點磁碟）**、**以及不會被印在某些 `kubectl` 的輸出裡**。

**要讓它真的安全需要三層**。**靜態加密**——設定 API server 的 `EncryptionConfiguration`，**讓 Secret 在 etcd 中是密文**（**理想是用 KMS provider，讓加密金鑰本身也不在叢集裡**）。**存取控制**——**嚴格的 RBAC，並且注意「能建立 Pod 的人就能讀該 namespace 的 Secret」這條提權路徑**。**外部化**——**用 Vault、雲端 Secret Manager 加上 External Secrets Operator 或 CSI Secret Store driver**。

**外部化的核心價值不只是加密，而是「輪換」與「審計」**——**這兩件事原生 Secret 完全做不到**。

## 詳細解析

**「能建立 Pod 就能讀 Secret」這條路徑必須被理解**：RBAC 可以禁止某人 `get secrets`，**但如果他能在該 namespace 建立 Pod，他就能建立一個掛載該 Secret 並把內容送出去的 Pod**——**於是讀取限制形同虛設**。**真正的隔離需要 namespace 級的分離**，**或者用 admission 政策限制「哪些 ServiceAccount 能掛載哪些 Secret」**。**這個認知會改變你對「namespace 邊界」的看法：它不只是命名的分組，而是一個實質的安全邊界。**

**環境變數注入比檔案掛載危險**。**環境變數會出現在 `/proc/<pid>/environ`、可能被錯誤堆疊或除錯輸出印出來、而且子行程會繼承它**。**更重要的是：環境變數在容器啟動時就固定了，密鑰輪換後必須重啟 Pod 才會生效**；**而檔案掛載的 Secret 會被 kubelet 定期同步更新**（**預設約一分鐘**），**應用可以監聽檔案變化而不重啟**。**所以「用檔案掛載」同時改善了安全性與可運維性**。

**輪換是外部化最實質的理由**。**原生 Secret 的輪換意味著：手動產生新值、更新 Secret、重啟所有使用它的 Pod**——**這個流程手動且容易遺漏**，**於是實務上密鑰經常幾年不換**。**Vault 這類系統支援動態密鑰**（**每個應用取得一組短期有效的憑證，到期自動失效**）——**這把「密鑰洩漏」的影響時間從無限變成幾小時**，**是安全性上的質變而非量變**。

**不要把密鑰放進 Git**，**即使 repo 是私有的**。**Sealed Secrets 或 SOPS 讓加密後的密文可以安全地進 Git**（**只有叢集內的私鑰能解密**），**這在 GitOps 流程中是必要的一環**。

## 面試回答方式

先明確指出**Secret 只是 base64 編碼不是加密**，並說出它與 ConfigMap 的三個真正差別。給三層改善（靜態加密、存取控制、外部化）並強調**外部化的核心價值是輪換與審計，那是原生 Secret 完全做不到的**。加分點有四個：**「能建立 Pod 就能讀 Secret」的提權路徑**——**它改變你對 namespace 邊界的看法：那不只是命名分組，而是實質的安全邊界**；**環境變數注入比檔案掛載危險**——**會出現在 proc、可能被堆疊印出、子行程會繼承，而且輪換後必須重啟才生效**，**檔案掛載則會被 kubelet 定期同步**；**動態密鑰把洩漏的影響時間從無限變成幾小時，是質變而非量變**；以及**GitOps 流程需要 Sealed Secrets 或 SOPS**。

## 講稿

首先要說清楚，Secret 預設只是 base64 編碼，不是加密。它跟設定圖的真正差別只有三個，獨立的存取控制資源類型、掛載時用記憶體檔案系統、以及不會被印在某些輸出裡。

要讓它真的安全需要三層。開啟靜態加密讓它在 etcd 裡是密文、嚴格的存取控制、還有外部化到專門的密鑰管理系統。

這裡有一條提權路徑必須理解。存取控制可以禁止某人讀取 Secret，但如果他能在那個命名空間建立 Pod，他就能建一個掛載該 Secret 並把內容送出去的 Pod，於是讀取限制形同虛設。這會改變你對命名空間邊界的看法，它不只是命名的分組，而是一個實質的安全邊界。

還有一個實務建議。用檔案掛載而不要用環境變數注入。環境變數會出現在行程資訊裡、可能被錯誤堆疊印出來、子行程還會繼承。更重要的是它在容器啟動時就固定了，密鑰輪換之後必須重啟才生效，而檔案掛載會被 kubelet 定期同步更新。所以用檔案同時改善了安全性跟可運維性。

## 常見追問

### External Secrets Operator 與 CSI Secret Store 怎麼選？

**核心答案**：**前者「同步成 K8s Secret」，後者「直接掛載進 Pod」**。**External Secrets Operator** 從外部系統讀取並建立對應的 K8s Secret——**優點是相容所有既有的用法（環境變數、掛載、imagePullSecrets），缺點是密鑰仍然以 Secret 的形式存在於 etcd**。**CSI Secret Store** 則在 Pod 掛載時直接從外部系統取值寫進 tmpfs——**密鑰完全不進 etcd，但只支援檔案掛載這一種用法**。

**詳細解析**：**多數團隊選 External Secrets Operator，因為相容性的價值通常大於「不進 etcd」的收益**——**尤其在已經開啟了 etcd 靜態加密的情況下，那個收益進一步縮小**。**而 CSI Secret Store 的一個實用特性是它可以同時做兩件事**：**掛載進 Pod，並且選擇性地同步成 K8s Secret 供需要的地方使用**——**所以它其實可以涵蓋兩種模式**。**選型時真正該問的是「輪換後應用怎麼感知」**：**兩者都能更新掛載的檔案，但應用如果不重新讀取檔案就沒有意義**——**所以無論選哪個，應用側都需要支援熱重載，否則整套機制只是把手動輪換變成了自動更新一個沒有人讀的檔案**。

**面試回答方式**：給核心差別（同步成 Secret vs 直接掛載）與各自的優缺點。加分點是指出**多數團隊選 External Secrets Operator，因為相容性的價值通常大於「不進 etcd」**，**尤其在已開啟靜態加密時那個收益進一步縮小**，並補充 **CSI Secret Store 其實可以同時做兩件事**。收在真正該問的問題：**輪換後應用怎麼感知**——**應用如果不重新讀取檔案，整套機制只是把手動輪換變成自動更新一個沒有人讀的檔案**。

### 怎麼防止密鑰被意外提交到 Git？

**核心答案**：**三層防線**。**開發者本機**——pre-commit hook 跑 gitleaks 或 detect-secrets。**CI**——**每次 push 掃描，發現就阻擋合併**。**倉庫層**——**GitHub 的 secret scanning 或等價功能，能在推送時直接拒絕已知格式的密鑰**。**而一旦真的洩漏，唯一正確的處理是「立即輪換該密鑰」**——**從 Git 歷史中刪除是次要的，因為你無法確定沒有人已經複製走**。

**詳細解析**：**「輪換優先於清理歷史」這個順序很重要，卻常常被搞反**。團隊發現洩漏後往往先花幾小時 rewrite history、force push、協調所有人重新 clone——**而在那段時間裡，那個密鑰仍然有效**。**正確的順序是：先輪換（幾分鐘內讓舊密鑰失效）、再考慮清理歷史（如果需要）**。**而清理歷史本身的價值有限**：**公開倉庫的內容可能已經被爬取、fork、或快取**，**歷史清乾淨了也無法收回**。**這個認知也應該影響預防的設計：把重點放在「讓密鑰短期有效」而非「絕對不洩漏」**——**動態密鑰讓一次洩漏的影響自動衰減，而那比任何掃描工具都可靠**。

**面試回答方式**：給三層防線（本機 hook、CI 掃描、倉庫層攔截）。核心加分點是**「輪換優先於清理歷史」這個常被搞反的順序**：**團隊往往先花幾小時 rewrite history，而那段時間密鑰仍然有效**，**正確順序是幾分鐘內先輪換再考慮清理**。收在更深的認知：**清理歷史的價值有限，公開倉庫可能已被爬取、fork 或快取**，**所以預防的重點應該是「讓密鑰短期有效」而非「絕對不洩漏」**——**動態密鑰讓一次洩漏的影響自動衰減，比任何掃描工具都可靠**。

### ServiceAccount token 也是 Secret，它怎麼管理？

**核心答案**：**1.24 之後預設不再自動建立長期有效的 token Secret**。**現在用的是「投影的 token」**（projected token）——**kubelet 向 API server 申請一個有時效、有受眾（audience）、且綁定該 Pod 的 token 並掛載進去**，**到期前自動輪換**。**這比舊的模式安全得多**：**舊的 token 永不過期，一旦洩漏就永久有效，而且可以在任何地方使用**。

**詳細解析**：**「綁定 Pod」這個性質值得強調**：**投影 token 的有效性與那個 Pod 的存在綁定**——**Pod 被刪除後 token 立即失效**，**這大幅縮小了洩漏的影響**。**而 `audience` 欄位讓 token 只能用於特定的接收方**——**這正是雲端工作負載身份（Workload Identity）的基礎**：**Pod 用一個 audience 為雲端 IAM 的 token 去換取雲端的存取憑證**，**整個過程不需要任何長期密鑰**。**這是 K8s 安全模型近年最重要的改進之一**，**而它的實務意義是：在雲端環境裡，「把服務帳號金鑰檔案放進 Secret」這種做法已經完全沒有必要**——**能指出這一點，通常表示跟上了近幾個版本的演進**。

**面試回答方式**：說明 **1.24 之後預設不再自動建立長期 token**，改用**有時效、有受眾、綁定 Pod 且自動輪換的投影 token**，並對比舊模式（永不過期、洩漏就永久有效、任何地方可用）。核心加分點是**「綁定 Pod」讓 token 在 Pod 刪除後立即失效**，以及 **`audience` 是雲端工作負載身份的基礎**：**Pod 用一個 audience 為雲端 IAM 的 token 去換取存取憑證，全程不需要長期密鑰**。收在實務意義：**在雲端環境裡「把服務帳號金鑰檔案放進 Secret」已經完全沒有必要**。
