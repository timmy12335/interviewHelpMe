# 題目

K8s 的網路模型有哪些硬性要求？CNI 外掛實際上做了什麼？

## 核心答案

K8s 定義了三條硬性要求，但不規定怎麼實作——**這正是 CNI 存在的理由**。三條要求是：**所有 Pod 可以不經 NAT 互相通訊**、節點上的 agent 可以不經 NAT 與該節點上的 Pod 通訊、以及 Pod 看到的自己的 IP 與別人看到的是同一個。

「不經 NAT 的扁平網路」是最關鍵的一條——它讓 Pod 之間的通訊就像在同一個區域網路裡，應用不需要知道自己在容器裡。

**CNI 外掛負責兩件事**：**給 Pod 分配 IP（IPAM）**、以及設定網路讓封包能到達目的地。**實作路線主要有兩條**：**Overlay**（VXLAN、IPIP——把 Pod 的封包封裝在節點之間的封包裡，不需要底層網路知道 Pod 網段，通用但有封裝開銷）與 **Routed / Native**（BGP 或雲端 VPC 的原生路由——底層網路直接知道怎麼送到 Pod IP，效能好但需要底層網路配合）。

**常見選擇**：Calico（支援兩種模式，網路政策強）、Cilium（eBPF，效能與可觀測性突出）、Flannel（簡單）、以及各雲端的原生 CNI。

## 詳細解析

**「Overlay vs Routed」的取捨是這題的核心**。Overlay 的封裝讓每個封包多出 50 個位元組左右的標頭——在 MTU 1500 的網路裡這會降低有效吞吐，而且如果 MTU 沒設好會導致封包分片或神秘的連線失敗。「MTU 設錯」是 overlay 網路最經典的疑難雜症：症狀是小封包正常、大封包卡住，表現為「TLS 握手成功但傳輸大 body 時 hang 住」——知道這個症狀能省下幾小時的排查。

雲端的原生 CNI 有一個常被忽略的限制：Pod IP 直接從 VPC 子網取得，而每個節點能掛載的網卡與 IP 數量有上限——所以「一個節點能跑幾個 Pod」不只受資源限制，也受 IP 數量限制。在大規模叢集裡這會成為實際的瓶頸，也讓子網規劃變成一個需要提前算清楚的事（子網太小會導致叢集無法擴容，而修改子網通常需要重建叢集）。

**eBPF 路線正在取代 iptables**。傳統的 kube-proxy 用 iptables 實作 Service 的轉發——規則數量隨 Service 數線性成長，而 iptables 的匹配是 O(n)，幾千個 Service 時規則更新與封包處理都會顯著變慢。IPVS 模式改善了匹配效率（雜湊表），而 eBPF 更進一步：在核心的封包路徑上直接執行程式，繞過大部分 netfilter 的處理——同時獲得更好的效能與更豐富的可觀測性。

跨節點的封包路徑值得能講清楚：Pod A 發出封包 → 經 veth pair 到節點的網路命名空間 → CNI 設定的路由決定下一跳 → overlay 則封裝後送到目標節點解封裝，routed 則直接按路由表送出 → 目標節點的 veth → Pod B。

## 面試回答方式

先給三條硬性要求並指出K8s 不規定實作，這正是 CNI 存在的理由，強調「不經 NAT 的扁平網路」讓應用不需要知道自己在容器裡。給 CNI 的兩件工作與**Overlay 與 Routed 兩條路線**的取捨。加分點有四個：**MTU 設錯是 overlay 最經典的疑難雜症**——症狀是小封包正常、大封包卡住，表現為 TLS 握手成功但傳輸大 body 時 hang 住；**雲端原生 CNI 的 IP 數量限制**——一個節點能跑幾個 Pod 也受網卡與 IP 上限約束，子網太小會導致叢集無法擴容而修改通常要重建；**eBPF 正在取代 iptables**——**iptables 規則隨 Service 數線性成長且匹配是 O(n)**，eBPF 在核心封包路徑直接執行，效能與可觀測性都更好；以及**能講清楚跨節點的封包路徑**。

## 講稿

K8s 定義了三條硬性要求但不規定怎麼實作，這正是網路外掛介面存在的理由。三條要求是所有 Pod 可以不經位址轉換互相通訊、節點上的代理可以直接跟該節點的 Pod 通訊、還有 Pod 看到的自己的位址跟別人看到的是同一個。

第一條最關鍵。不經位址轉換的扁平網路讓 Pod 之間的通訊就像在同一個區域網路裡，應用不需要知道自己在容器裡。

外掛負責分配位址跟設定路由。實作路線主要兩條。覆蓋網路把封包封裝在節點之間的封包裡，不需要底層網路知道 Pod 網段，通用但有封裝開銷。原生路由則讓底層網路直接知道怎麼送到 Pod，效能好但需要底層配合。

覆蓋網路有一個最經典的疑難雜症值得提，就是最大傳輸單元設錯。封裝會讓每個封包多出五十個位元組左右的標頭，如果沒調整，症狀是小封包正常但大封包卡住，表現成握手成功但傳輸大內容時就卡在那裡。知道這個症狀能省下幾小時的排查。

## 常見追問

### Service 的虛擬 IP 是怎麼運作的？

**核心答案**：它不存在於任何網路介面上，只是 iptables 或 IPVS 規則裡的一個匹配目標。封包送往 ClusterIP 時，節點上的規則把目的地址改寫成某個實際的 Pod IP（DNAT），**回程再改回來**。**所以 ClusterIP 是 ping 不通的**（沒有東西會回應 ICMP），這是一個常讓人困惑但完全正常的現象。

**詳細解析**：這個設計解釋了幾個常見行為。Service 的負載平衡是在「連線建立時」決定的——一旦選定了後端 Pod，這條連線的所有封包都去同一個 Pod；**所以長連線（HTTP/2、gRPC）不會被重新平衡**，這正是 gRPC 在 K8s 裡負載不均的根本原因，要靠客戶端側負載平衡或 service mesh 解決。**另一個是「Service 沒有健康檢查」**——它完全依賴 Endpoints 的內容，而 Endpoints 由 readiness 探針決定。所以「Service 把流量送到壞掉的 Pod」永遠是 readiness 探針的問題，不是 Service 的問題——能做出這個歸因是排查這類問題的關鍵。

**面試回答方式**：給核心機制——ClusterIP 不存在於任何介面上，只是規則裡的匹配目標，封包經 DNAT 改寫到實際 Pod IP，並指出**它 ping 不通是完全正常的**。核心加分點是用這個設計解釋兩個常見行為：負載平衡在連線建立時決定，所以長連線不會被重新平衡——這正是 gRPC 在 K8s 裡負載不均的根本原因；Service 沒有健康檢查，完全依賴 Endpoints 而 Endpoints 由 readiness 決定——所以流量送到壞掉的 Pod 永遠是探針的問題。

### Pod 之間網路不通怎麼排查？

**核心答案**：**從內往外分層驗證**。**一、同一個 Pod 內** `curl localhost` 確認應用真的在聽。**二、同節點的另一個 Pod** 用 Pod IP 直連——**排除 CNI 的節點內轉發問題**。**三、跨節點**用 Pod IP 直連——這一步失敗通常是 CNI 或底層網路（安全群組、路由）的問題。**四、用 Service 名稱**——**這一步才失敗就是 DNS 或 Endpoints 的問題**。

**詳細解析**：這個分層的價值在於「每一步失敗都指向一組明確的原因」——而跳過分層直接猜測往往浪費很多時間。實務上第三步（跨節點）失敗最常見的原因是雲端的安全群組或防火牆規則沒有放行 Pod 網段，尤其在 overlay 模式下需要放行封裝用的端口（VXLAN 是 UDP 8472）。第四步失敗則要進一步分：`nslookup` 能解析但連不上 → Endpoints 是空的（Pod 沒 Ready 或標籤選擇器寫錯）；連解析都失敗 → CoreDNS 的問題。而「標籤選擇器寫錯」是一個非常常見卻很隱蔽的錯誤——因為它不會報錯，只是 Endpoints 一直是空的，**用 `kubectl get endpoints <svc>` 一眼就能確認**。

**面試回答方式**：給四層驗證流程並說明每一步失敗都指向一組明確的原因，強調跳過分層直接猜測會浪費很多時間。加分點是給出各層的典型原因：第三步失敗最常見的是安全群組沒放行 Pod 網段，overlay 模式還要放行封裝端口；第四步要分「能解析但連不上」（Endpoints 空的）與「解析就失敗」（CoreDNS）。收在一個隱蔽的錯誤：標籤選擇器寫錯不會報錯，只是 Endpoints 一直是空的，**用 `kubectl get endpoints` 一眼就能確認**。

### NetworkPolicy 為什麼有時候沒生效？

**核心答案**：**最常見的原因是 CNI 不支援**。**NetworkPolicy 是 K8s 的 API，但實際執行它的是 CNI 外掛**——Flannel 這類簡單的外掛完全不實作它，於是政策物件建立成功卻毫無效果，也不會有任何錯誤訊息。第二個常見原因是「政策的疊加邏輯」：多條政策之間是聯集（OR）而非交集——加一條更嚴格的政策不會讓權限變小。

**詳細解析**：「建立成功但無效果」是這個 API 最危險的性質——團隊以為已經隔離了，實際上網路完全開放。**驗證的唯一方式是實際測試**：建立政策後從一個應該被擋的 Pod 發起連線，確認它真的失敗。把這個測試自動化（在 CI 或定期的合規檢查中）是唯一可靠的保證。 至於疊加邏輯，正確的心智模型是「預設全通，一旦有任何政策選中某個 Pod，該 Pod 就變成預設全擋，然後所有選中它的政策的允許規則取聯集」——所以要收緊權限必須修改既有政策或移除過寬的那一條，而不是新增一條嚴格的。這個「不能靠新增來收緊」的性質與防火牆規則的直覺相反，是最常見的誤解來源。

**面試回答方式**：給最常見的原因——CNI 不支援，政策建立成功卻毫無效果也沒有錯誤訊息，並指出這是這個 API 最危險的性質：團隊以為已經隔離，實際上網路完全開放。給驗證方式（實際從應該被擋的 Pod 發起連線並自動化這個測試）。第二個加分點是**疊加邏輯**：正確的心智模型是「一旦有政策選中某 Pod 就變成預設全擋，然後所有選中它的政策取聯集」，**所以不能靠新增政策來收緊**——這與防火牆規則的直覺相反，是最常見的誤解來源。
