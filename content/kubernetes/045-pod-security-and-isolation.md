# 題目

容器的隔離有多強？Pod Security Standards 在防什麼？

## 核心答案

**容器不是虛擬機**——它是同一個核心上的行程隔離（namespace 隔離視圖，cgroup 限制資源）。所以「容器逃逸」的本質是「利用核心漏洞或錯誤的設定跨越那層隔離」，而多數成功的逃逸不是靠 0-day，而是靠設定太寬鬆。

**Pod Security Standards 定義三級**。**Privileged**——不設限。**Baseline**——**禁止已知的明顯危險**：特權容器、hostNetwork、hostPID、大部分 hostPath、危險的 capabilities。**Restricted**——進一步要求非 root 執行、唯讀根檔案系統、丟棄所有 capabilities、以及 seccomp 設為 RuntimeDefault。

**最危險的四個設定**：**`privileged: true`**（幾乎等於節點的 root）、**`hostPath` 掛載敏感路徑**（掛 `/` 或 docker socket 就是完全接管節點）、**`hostNetwork` / `hostPID`**（**看得到節點的網路與行程**）、**以及 `CAP_SYS_ADMIN`**（**權限之大幾乎等於特權模式**）。

## 詳細解析

**「掛載 docker socket 或 containerd socket」是最常見的自我毀滅**。CI 的建置任務、日誌收集器、監控代理——很多工具的文件會叫你這樣做，而它的實際含義是「這個容器可以建立任意容器，包括一個特權容器掛載節點根目錄」——等於完全放棄了節點的安全邊界。**替代方案有很多**（Kaniko、Buildah 這類不需要 daemon 的建置工具；用 CRI 的唯讀介面而非 socket），而知道要避免它比知道任何一條安全規則都重要。

**「非 root 執行」的實際效果被低估了**：即使發生了應用層的入侵，非特權使用者能做的事情有限——無法安裝套件、無法修改系統檔案、無法綁定低端口。**配合唯讀根檔案系統（`readOnlyRootFilesystem: true`）**，入侵者連寫入一個惡意執行檔都做不到——這兩個設定加起來能擋掉絕大多數自動化的攻擊腳本，**而它們的實作成本只是幾行 securityContext**。

**Pod Security Admission 有三種模式**：**`enforce`（拒絕）、`audit`（記錄）、`warn`（提示）**——**可以同時設定不同等級**。推行的正確順序是「先用 audit 與 warn 觀察現況，處理掉違規的工作負載，最後才開 enforce」——直接開 enforce 會讓現有部署大量失敗。這與其他政策工具的推行策略是一樣的。

強隔離的執行期是另一個層次的答案：**gVisor**（用使用者態核心攔截系統呼叫）與 **Kata Containers**（每個 Pod 一個輕量虛擬機）**提供接近虛擬機的邊界**——代價是效能損耗與部分系統呼叫的相容性問題。適合跑不受信任的程式碼（例如使用者提交的任務）。

## 面試回答方式

先建立正確的心智模型——容器不是虛擬機，是同一個核心上的行程隔離，所以多數成功的逃逸不是靠 0-day 而是靠設定太寬鬆。給 Pod Security Standards 三級與最危險的四個設定。加分點有四個：**掛載 docker/containerd socket 是最常見的自我毀滅**——很多工具的文件會叫你這樣做，而它的實際含義是這個容器能建立特權容器掛載節點根目錄，知道要避免它比知道任何一條安全規則都重要；非 root 加唯讀根檔案系統能擋掉絕大多數自動化攻擊腳本，**而成本只是幾行 securityContext**；**推行順序要先 audit 與 warn 再 enforce**，直接開會讓現有部署大量失敗；以及**gVisor 與 Kata 提供接近虛擬機的邊界**，適合跑不受信任的程式碼。

## 講稿

首先要建立正確的心智模型。容器不是虛擬機，它是同一個核心上的行程隔離。所以容器逃逸的本質是利用核心漏洞或錯誤的設定跨越那層隔離，而多數成功的逃逸不是靠零時差漏洞，是靠設定太寬鬆。

最危險的幾個設定是特權模式、掛載敏感的主機路徑、共用主機的網路或行程命名空間、還有系統管理權限。

其中我覺得最常見的自我毀滅是掛載容器執行期的通訊端。很多工具的文件會叫你這樣做，而它的實際含義是這個容器可以建立任意容器，包括一個特權容器掛載節點根目錄。那等於完全放棄節點的安全邊界。替代方案很多，知道要避免它比知道任何一條安全規則都重要。

反過來，效果被低估的是非 root 執行加上唯讀根檔案系統。即使發生了應用層入侵，非特權使用者無法安裝套件、無法修改系統檔案，配合唯讀之後連寫入一個惡意執行檔都做不到。這兩個設定能擋掉絕大多數自動化的攻擊腳本，而成本只是幾行安全上下文。

## 常見追問

### seccomp 與 AppArmor 在做什麼？

**核心答案**：都是「限制容器能做什麼」的核心層機制，但角度不同。**seccomp** 過濾**系統呼叫**——`RuntimeDefault` 設定檔封鎖了約 40 個危險的系統呼叫（例如 `mount`、`reboot`、以及各種能操作核心模組的呼叫）。**AppArmor**（或 SELinux）則基於**路徑與能力的存取控制**——限制容器能讀寫哪些檔案、能用哪些網路能力。

**詳細解析**：`seccompProfile: RuntimeDefault` 是投入報酬比最高的安全設定之一：一行設定，封鎖大量攻擊面，而且對絕大多數應用完全無感（那些被封鎖的系統呼叫本來就不該被一般應用使用）。**它從 1.25 開始在 Restricted 等級中是必需的**。**自訂 seccomp 設定檔則要謹慎**——過度限制會讓應用在某些少見的程式碼路徑上突然失敗，而那種失敗極難診斷（表現為莫名的 EPERM）。實務建議是「先用 RuntimeDefault，只有在明確的威脅模型下才寫自訂設定檔」，而寫自訂檔時要先用 audit 模式收集實際使用的系統呼叫清單。

**面試回答方式**：給兩者的角度差異（seccomp 過濾系統呼叫、AppArmor 基於路徑與能力的存取控制）。核心加分點是指出 `RuntimeDefault` 是投入報酬比最高的安全設定之一——一行設定封鎖大量攻擊面且對絕大多數應用完全無感。收在自訂設定檔的謹慎：過度限制會讓應用在少見的程式碼路徑上突然失敗，表現為莫名的 EPERM 極難診斷，所以要先用 audit 模式收集實際使用的系統呼叫清單。

### 怎麼在既有叢集推行安全基線？

**核心答案**：**分階段且提供遷移路徑**。**第一階段**：對所有 namespace 開 `warn` 與 `audit`，產出一份「哪些工作負載違規、違反哪一條」的清單。**第二階段**：**按團隊溝通並協助修改**——多數違規只是「沒設 securityContext」而非真的需要特權。**第三階段**：**新建的 namespace 預設 enforce，既有的逐個切換**。特殊需求走例外流程並記錄理由與到期時間。

**詳細解析**：「例外要有到期時間」是這個流程裡最重要的設計：**沒有到期的例外會永遠存在**——於是幾年後你有一份沒有人記得為什麼存在的例外清單，而安全基線形同虛設。加上到期時間強迫定期重新評估，而多數例外在重新評估時會發現「其實已經不需要了」（原因可能是應用已經改版或該功能已下線）。另一個實務要點是「先讓新的符合標準比修好舊的更重要」：存量的問題可能永遠改不完，但如果新增的都符合標準，違規的比例會隨時間自然下降——而反過來（先花半年清存量但新增的仍然放行）是徒勞的。

**面試回答方式**：給三階段的推行流程並指出多數違規只是沒設 securityContext 而非真的需要特權。核心加分點是**例外要有到期時間**：沒有到期的例外會永遠存在，幾年後變成一份沒人記得為什麼的清單而基線形同虛設，加上到期強迫重新評估，而多數例外重新評估時會發現已經不需要了。收在推行策略：先讓新的符合標準比修好舊的更重要——存量可能永遠改不完，但新增的都合規時違規比例會隨時間自然下降。

### 執行期的威脅偵測該怎麼做？

**核心答案**：**用 eBPF based 的執行期安全工具**（Falco、Tetragon）**監控系統呼叫層的異常行為**：容器內啟動 shell、寫入敏感路徑、非預期的外連、以及提權嘗試。它與 Pod Security 的差別是「事前預防」與「事中偵測」——前者防止危險的設定，後者發現正在發生的異常。

**詳細解析**：執行期偵測的最大挑戰是誤報：「容器內啟動 shell」在正常運維中也會發生（有人在 exec 除錯）——於是規則不調整的話會產生大量噪音，而噪音會讓所有告警都被忽略。務實的起點是「只對高置信度的行為告警」：在生產容器裡執行套件管理器、修改 `/etc/passwd`、或者從一個不該有網路存取的 Pod 發出外連——**這些幾乎不會是正常行為**。另一個實用的做法是「把偵測結果先接到日誌而非告警」：觀察一段時間，看清楚正常行為的基線之後，再挑選少數規則升級成告警——這與任何監控系統的推行是同一個模式：先觀察、再定義正常、最後才告警。

**面試回答方式**：給工具類型與監控的行為，並明確區分Pod Security 是事前預防、執行期偵測是事中發現。核心加分點是指出**最大的挑戰是誤報**——容器內啟動 shell 在正常運維中也會發生，噪音會讓所有告警都被忽略，並給出**只對高置信度行為告警**的起點（生產容器裡跑套件管理器、改 `/etc/passwd`、不該有網路的 Pod 發外連）。收在推行模式：先接到日誌觀察一段時間看清正常基線，再挑少數規則升級成告警。
