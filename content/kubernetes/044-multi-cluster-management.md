# 題目

一個大叢集還是多個小叢集？多叢集要怎麼管理？

## 核心答案

先回答「為什麼要多叢集」，因為它的成本是實實在在的：每個叢集都需要獨立的控制平面、監控、升級、與存取管理——十個叢集的運維負擔遠超一個十倍大的叢集。

**拆分的正當理由有四個**。**故障隔離**——叢集是一個爆炸半徑邊界，控制平面或 CNI 出問題時影響範圍限於一個叢集。**地理分布**——跨區域的低延遲需求或資料落地法規。**環境隔離**——生產與非生產分開，這是最基本也最沒有爭議的一條。**合規與租戶隔離**——當 namespace 級的隔離不足以滿足要求時。

**不該拆的理由**：**「團隊隔離」**（用 namespace 加 RBAC 加配額就夠）、**「怕互相影響」**（那該用資源限制與網路政策解決）、**以及「叢集太大了」**（K8s 的官方上限是 5000 節點，多數團隊遠遠碰不到）。

## 詳細解析

「叢集是一個爆炸半徑邊界」是拆分最強的理由，而它值得具體化：etcd 損壞、API server 過載、CNI 的錯誤設定、一次失敗的叢集升級——這些故障的影響範圍就是整個叢集。如果所有生產流量都在一個叢集裡，那麼這些就是全站中斷的單點。而拆成三個區域各一個叢集，同樣的故障只影響三分之一。這個論證比任何規模上的理由都紮實，因為它針對的是「控制平面本身是共用的」這個無法用 namespace 隔離的事實。

多叢集帶來的最大複雜度是「跨叢集的服務通訊」。同一個叢集裡 Service 就能解決——跨叢集則需要：DNS 的跨叢集解析、網路的可達性（VPC peering 或 mesh 的閘道）、以及流量的故障轉移策略。**Istio 的多叢集網格或 Cilium Cluster Mesh 能提供這些**，但它們本身就是一套需要理解與維運的複雜系統。所以「跨叢集頻繁互相呼叫的服務」是一個設計上的警訊——它們可能本來就該在同一個叢集裡。

管理的關鍵是「不要手動管理每一個」。**叢集的建立用 IaC（Terraform、Cluster API）**，**叢集內的資源用 GitOps 的 ApplicationSet**，存取控制與政策用集中的身份提供者加上一致的 RBAC 宣告。任何需要「登入到每個叢集做一次」的操作，在叢集數量成長後都會變成事故的來源。

**升級策略要分批**。先升一個非生產叢集，觀察；再升一個生產叢集，觀察；最後才是其餘的——這讓多叢集從「N 倍的升級工作」變成「一次逐步驗證的推進」，而那其實是多叢集的一個隱藏好處。

## 面試回答方式

先強調**成本是實實在在的**（每個叢集都要獨立的控制平面、監控、升級、存取管理），再給四個正當理由與三個不該拆的理由。加分點有四個：「叢集是爆炸半徑邊界」是最強的理由，並具體化（etcd 損壞、API server 過載、CNI 設定錯誤、失敗的升級，影響範圍就是整個叢集），它針對的是「控制平面共用」這個無法用 namespace 隔離的事實；最大的複雜度是跨叢集服務通訊，而「跨叢集頻繁互相呼叫的服務」是設計警訊——它們可能本來就該在同一個叢集；管理的關鍵是不要手動管理每一個，任何需要逐叢集操作的事在數量成長後都會變成事故來源；以及升級分批讓多叢集從「N 倍工作」變成「逐步驗證的推進」，那其實是一個隱藏好處。

## 講稿

我會先問為什麼要多叢集，因為它的成本是實實在在的。每個叢集都需要獨立的控制平面、監控、升級跟存取管理，十個叢集的運維負擔遠超一個十倍大的叢集。

正當的理由有四個。故障隔離、地理分布、環境隔離、還有合規或租戶隔離。而不該拆的理由包括團隊隔離，那用命名空間加權限加配額就夠了。還有覺得叢集太大，但官方上限是五千節點，多數團隊遠遠碰不到。

我認為最強的理由是故障隔離，因為它針對的是控制平面共用這個無法用命名空間解決的事實。etcd 損壞、API 伺服器過載、網路設定錯誤、一次失敗的升級，這些故障的影響範圍就是整個叢集。

而多叢集最大的複雜度是跨叢集的服務通訊。同一個叢集裡用服務就解決了，跨叢集要處理跨叢集的名稱解析、網路可達性、還有故障轉移策略。所以我會把跨叢集頻繁互相呼叫的服務視為一個設計警訊，它們可能本來就該在同一個叢集裡。

## 常見追問

### 多租戶用 namespace 還是獨立叢集？

**核心答案**：**看隔離要求的強度**。**namespace 級的軟隔離**（RBAC、ResourceQuota、NetworkPolicy、Pod Security）足以應付「互相信任的內部團隊」；而「租戶之間互不信任」或「有合規要求」的場景需要更強的隔離——因為 namespace 共用同一個核心與同一個控制平面，容器逃逸或核心漏洞可以跨越 namespace。

**詳細解析**：「共用核心」是軟隔離的根本限制：所有容器共用節點的作業系統核心——一個核心層的漏洞讓 namespace 的邊界失效。中間的選項是「共用叢集但獨立節點池」（用 taint 把不同租戶分到不同節點，**至少不共用核心**），**或者用強隔離的執行期**（gVisor、Kata Containers——用使用者態核心或輕量虛擬機提供更強的邊界，代價是效能與相容性）。所以選擇不是二元的，而是一個「隔離強度與成本」的光譜：軟隔離、獨立節點、強隔離執行期、獨立叢集——應該按實際的威脅模型挑最低夠用的那一級，而不是預設選最強的。

**面試回答方式**：先給判準（**看隔離要求的強度**）並指出軟隔離適用於互相信任的內部團隊。核心加分點是說明「共用核心」是軟隔離的根本限制——**核心層的漏洞讓 namespace 邊界失效**。真正的深度是給出**光譜而非二元選擇**：軟隔離、獨立節點池、強隔離執行期、獨立叢集，並主張按實際的威脅模型挑最低夠用的那一級而不是預設選最強的。

### 跨叢集的服務發現怎麼做？

**核心答案**：**三種層次**。**DNS 層**——在每個叢集配置對其他叢集的 DNS 轉發，簡單但沒有健康感知與故障轉移。**服務網格**——Istio 的多叢集或 Cilium Cluster Mesh 把遠端服務的端點同步進本地，讓跨叢集呼叫看起來與本地一樣，並支援優先本地、故障時轉移。**外部負載平衡器**——服務透過公開或內部的負載平衡器互相呼叫，最簡單也最通用，代價是多一跳與失去叢集內的優化。

**詳細解析**：「優先本地、故障時跨叢集」是多叢集最有價值的能力：正常情況下請求留在本叢集（低延遲、無跨區費用），而本叢集的該服務全部不可用時自動轉到其他叢集——這讓多叢集真正提供了可用性收益，而不只是隔離。但它需要小心設定「什麼算不可用」：設得太敏感會在小抖動時把流量全部甩到遠端，反而放大問題。另一個要注意的是「跨叢集呼叫的可觀測性」：分散式追蹤必須能跨越叢集邊界（**trace context 要在網格的閘道間正確傳遞**），否則排查跨叢集的問題會非常困難——而這一點在設計階段就要驗證，不要等出事才發現追蹤斷在閘道上。

**面試回答方式**：給三個層次與各自的取捨。核心加分點是「優先本地、故障時跨叢集」是多叢集最有價值的能力——它讓多叢集真正提供可用性收益而不只是隔離，但要小心「什麼算不可用」的設定，太敏感會在小抖動時把流量全甩到遠端反而放大問題。收在一個容易被忽略的點：跨叢集呼叫的追蹤必須能跨越邊界，而這要在設計階段驗證，不要等出事才發現追蹤斷在閘道上。

### 叢集的建立與設定怎麼標準化？

**核心答案**：用 IaC 定義叢集本身，用 GitOps 定義叢集內容，並把兩者接起來。**Terraform 或 Cluster API 建立叢集與節點池**；叢集建立完成後自動安裝 GitOps 控制器（bootstrap）；控制器再從設定倉庫拉取這個叢集該有的所有東西（監控、日誌、政策、以及應用）。目標是「建立一個新叢集是一個 PR 加一次自動化流程」，而不是一份操作手冊。

**詳細解析**：「bootstrap 那一步」是最容易變成手動的地方，而它一旦手動就會讓整條鏈路失去可重現性。成熟的做法是用 Cluster API 或雲端的叢集 API 在建立時就注入 GitOps 控制器的安裝——或者用一個「管理叢集」來建立與管理其他叢集（Cluster API 的核心模式：叢集本身也是一個 K8s 資源）。後者的優雅之處是「管理叢集的 GitOps 控制器同時管理了叢集的建立與叢集的內容」——整個基礎設施變成一個統一的宣告式系統。代價是管理叢集本身成為一個關鍵單點，需要額外的保護與備份。這個取捨本身就是一個好的面試討論點。

**面試回答方式**：給分工（IaC 定義叢集、GitOps 定義內容、bootstrap 接起來）並給出目標：建立新叢集是一個 PR 加一次自動化流程而非一份操作手冊。核心加分點是指出 bootstrap 最容易變成手動，而一旦手動整條鏈路就失去可重現性，並給出 Cluster API 的核心模式：叢集本身也是一個 K8s 資源，用管理叢集來建立與管理其他叢集。收在取捨：優雅之處是整個基礎設施變成統一的宣告式系統，代價是管理叢集成為關鍵單點需要額外保護與備份。
