# 題目

K8s 叢集的成本從哪裡來？怎麼降低？

## 核心答案

最大的浪費幾乎總是「requests 設得遠高於實際用量」。排程按 requests 分配，所以宣告 2 核實際用 0.2 核的 Pod 佔用了十倍的容量——叢集看起來滿了，實際 CPU 使用率只有 15%。這是絕大多數 K8s 叢集的真實狀況。

降低成本的五個手段，按效益排序。**一、修正 requests**——**用實際用量的 p95 到 p99 作為依據**，這通常一次就能釋放三到五成的容量。**二、用 spot / 搶佔式節點**——**可中斷的工作負載省 60% 到 90%**。**三、節點自動縮容**——確保 Cluster Autoscaler 真的能縮，而不是被某些 Pod 卡住。**四、選對機型**——根據工作負載的 CPU 記憶體比例挑機型，避免一種資源用完另一種閒置。**五、關掉不用的東西**——**非生產環境下班後縮到零。**

## 詳細解析

「修正 requests」之所以排第一，是因為它幾乎沒有風險且效果立竿見影。做法是用歷史指標（VPA 的推薦模式或 Prometheus 的查詢）算出每個工作負載的實際用量分布，**然後把 requests 設在 p95 附近**，**limits 設在能容忍的峰值**。**注意「不要把 requests 設成平均值」**——那會讓 Pod 在正常的流量波動中就開始爭搶資源。

Cluster Autoscaler 縮不下去是一個非常常見的隱形成本。它只有在「節點上的所有 Pod 都能被搬到別處」時才會移除該節點——**而以下任何一個都會阻止它**：**使用了本地儲存的 Pod**、**沒有控制器管理的裸 Pod**、**PDB 不允許驅逐**、以及 kube-system 裡沒有設定允許驅逐註解的 Pod。結果是「叢集擴上去之後就再也縮不回來」——而這個問題完全不會有任何告警，**只會體現在帳單上**。檢查 Cluster Autoscaler 的日誌（它會明確說出「因為某個 Pod 所以不能縮這個節點」）是排查的第一步。

「機型的 CPU 與記憶體比例」值得注意：如果你的工作負載普遍是記憶體密集的（例如 JVM 應用），用標準機型會導致 CPU 大量閒置——換成記憶體優化的機型能顯著提升配置密度。這個調整不需要改任何應用，只是換節點池。

**成本歸屬要靠標籤**。namespace、標籤、以及節點池的標記讓成本工具（Kubecost、雲端的成本分析）能算出「哪個團隊花了多少」——而沒有歸屬的成本永遠不會被優化，因為沒有人覺得那是自己的問題。

## 面試回答方式

先給最大的浪費——**requests 遠高於實際用量**，並具體化（宣告 2 核用 0.2 核就佔了十倍容量，叢集看起來滿了但實際使用率只有 15%），指出這是絕大多數叢集的真實狀況。給五個手段並按效益排序。加分點有四個：修正 requests 排第一是因為幾乎沒有風險且立竿見影，用 p95 而非平均值，因為平均值會讓 Pod 在正常波動中就爭搶資源；**Cluster Autoscaler 縮不下去是常見的隱形成本**——**本地儲存、裸 Pod、PDB、kube-system 的 Pod 都會阻止縮容**，而這完全沒有告警只體現在帳單上，**查它的日誌是第一步**；**機型的 CPU 記憶體比例**——記憶體密集的工作負載用標準機型會讓 CPU 大量閒置，換節點池就能改善且不需要改應用；以及沒有歸屬的成本永遠不會被優化。

## 講稿

最大的浪費幾乎總是請求量設得遠高於實際用量。排程是按請求量分配的，所以宣告兩核實際只用零點二核的 Pod 佔用了十倍容量。叢集看起來滿了，實際使用率只有一成五。這是絕大多數叢集的真實狀況。

所以效益最高的手段是修正請求量，用實際用量的九十五百分位作為依據，通常一次就能釋放三到五成的容量。要注意不能設成平均值，那會讓 Pod 在正常的流量波動中就開始爭搶資源。

第二是可中斷的工作負載用搶佔式節點，省六到九成。第三是確認自動縮容真的能縮。

第三點值得展開，因為它是一個很常見的隱形成本。縮容只有在節點上所有 Pod 都能被搬到別處時才會發生，而使用本地儲存的 Pod、沒有控制器管理的裸 Pod、或者中斷預算不允許驅逐，任何一個都會阻止它。結果是叢集擴上去之後就再也縮不回來，而這完全不會有告警，只會體現在帳單上。查自動縮容元件的日誌是排查的第一步，它會明確說出因為哪個 Pod 所以不能縮。

## 常見追問

### 怎麼安全地使用 spot 節點？

**核心答案**：**四個配套**。**只放可中斷的工作負載**（用 taint 加 toleration 確保關鍵服務不會被排上去）。**跨多個機型與可用區**（**降低同時被回收的機率**）。**處理回收通知**（雲端會提前 30 秒到 2 分鐘通知，用它觸發優雅終止）。**混合節點池**（關鍵服務跑在按需節點，其餘跑 spot）。

**詳細解析**：「單一機型的 spot 池」是最常見的錯誤：當那個機型在該區域供應緊張時，你的所有 spot 節點會同時被回收——而那正是流量高峰的時候（因為別人也在搶）。用多個機型組成的節點池能大幅降低這個相關性風險。另一個要點是「不要讓 spot 的比例超過你能承受的損失」：如果 100% 的容量都在 spot 上，一次大規模回收就是服務中斷——常見的配置是「基礎容量用按需或預留實例，彈性的部分用 spot」。這與投資組合的思路是一樣的：用穩定的部分保底，用波動的部分提高效率——而關鍵是先確定「保底需要多少」，再把其餘的交給 spot。

**面試回答方式**：給四個配套並強調**用 taint 確保關鍵服務不會被排上 spot**。核心加分點是指出單一機型的 spot 池是最常見的錯誤——該機型供應緊張時所有節點同時被回收，而那正是流量高峰的時候，用多機型組成的池能大幅降低相關性風險。收在配置原則：不要讓 spot 比例超過你能承受的損失，基礎容量用按需或預留、彈性部分用 spot——先確定保底需要多少，再把其餘交給 spot。

### 非生產環境的成本怎麼降？

**核心答案**：**按時間縮容是最有效的一招**。開發與測試環境在下班後與週末基本上沒有人用——一週 168 小時裡真正需要的可能只有 50 小時。用 CronJob 或 KEDA 在固定時間把 Deployment 縮到零、把節點池縮到最小，能直接砍掉六成以上的非生產成本，**而且幾乎沒有副作用**。

**詳細解析**：「縮到零」的阻力通常不是技術而是習慣：有人會擔心「早上第一個人要等啟動」——而那可以用「上班前半小時自動擴回」解決。更深的阻力是「某些環境被當成了半個生產環境」（例如展示用的環境、或者某個團隊依賴它做整合測試）——這時該做的是把那些環境明確地標記出來並排除，而不是因為有例外就放棄整個做法。另一個實用的措施是「臨時環境的自動過期」：為每個 PR 建立的預覽環境設定 TTL，超時自動刪除——**否則它們會無限累積**，而那是一個安靜但持續增長的成本。

**面試回答方式**：給按時間縮容並量化（一週 168 小時真正需要的可能只有 50 小時，能砍掉六成以上非生產成本）。加分點是指出**阻力通常不是技術而是習慣**：「早上第一個人要等」可以用上班前自動擴回解決，而「某些環境被當成半個生產」該做的是明確標記並排除，而不是因為有例外就放棄整個做法。收在另一項措施：**臨時環境設 TTL 自動過期**，否則會無限累積成一個安靜但持續增長的成本。

### 怎麼讓成本優化持續下去？

**核心答案**：讓成本可見、可歸屬、且有人負責。**可見**——按 namespace 或標籤的成本報表，定期發給團隊。**可歸屬**——強制所有工作負載帶上團隊與服務的標籤（用 admission 政策）。**有人負責**——把「資源效率」納入服務的健康指標，**與延遲、錯誤率並列**。

**詳細解析**：「與延遲、錯誤率並列」這個做法值得強調：它把成本從**財務部門的事**變成**工程團隊的事**——而只有工程團隊能真正改變它。具體的指標可以是「requests 與實際用量的比值」（**效率**）**或「每千次請求的成本」**（**單位經濟**）。後者尤其有價值，因為它區分了「因為業務成長而增加的成本」（正常）與「因為效率下降而增加的成本」（問題）——而只看總金額的報表無法做出這個區分。最後，優化需要一個週期性的機制而非一次性的專案：每季檢視一次資源效率報表，處理最差的幾個——因為新的浪費會持續產生，而一次性的清理只能維持幾個月。

**面試回答方式**：給三個要素（可見、可歸屬、有人負責）。核心加分點是把資源效率與延遲、錯誤率並列——它把成本從財務部門的事變成工程團隊的事，而只有工程團隊能真正改變它。給出具體指標並強調「每千次請求的成本」尤其有價值，因為它區分了業務成長帶來的成本（正常）與效率下降帶來的成本（問題），而只看總金額無法做出這個區分。收在機制：需要週期性檢視而非一次性專案，**因為新的浪費會持續產生**。
