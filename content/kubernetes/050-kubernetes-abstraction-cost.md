# 題目

回顧整個 K8s，你認為它最核心的設計思想是什麼？它的代價在哪裡？

## 核心答案

**最核心的思想是「宣告式 + 控制迴圈」**：**你描述期望狀態，控制器持續地把實際狀態推向它**——**而不是執行一串命令**。**這一個模式解釋了 K8s 幾乎所有的行為**：**為什麼刪掉的 Pod 會自己回來、為什麼設定改了要等一下才生效、為什麼幾乎所有功能都是一個「控制器加自訂資源」。**

**它帶來三個真實的收益**：**自我修復**（實際狀態偏離就自動糾正）、**可擴充**（**CRD 加 Operator 讓你用同一個模式表達自己的領域**）、**以及可宣告的基礎設施**（**於是 GitOps 成為可能**）。

**而代價有三層**。**認知代價**——**你必須理解一整套新的概念與它們的互動，而排錯時要在多個抽象層之間切換**。**運維代價**——**叢集本身成為一個需要被維護的系統**。**間接性的代價**——**「為什麼我的請求失敗了」可能要穿過 Ingress、Service、EndpointSlice、探針、與排程五層才能回答**。

## 詳細解析

**「宣告式的代價是失去了確定的時序」**。命令式的部署你知道每一步何時發生；**宣告式的部署只保證「最終會收斂」**——**而中間發生了什麼、花多久、以及是否卡住，都需要另外觀察**。**這是很多困惑的來源**：**「我 apply 了為什麼沒生效」的答案往往是「控制器還沒處理」或「某個前置條件不滿足」**。**理解這一點會改變你的排錯方式**：**不要問「我的指令有沒有執行成功」，而要問「哪個控制器該做這件事，它的狀態是什麼」**。

**K8s 把「應用的假設」變成了硬性要求**。Pod 隨時可能被重建、IP 隨時會變、本地磁碟隨時消失——**這些不是 K8s 帶來的新問題，而是它把分散式系統本來就有的性質變得無法迴避**。**一個在虛擬機上「碰巧沒出過事」的應用，搬進 K8s 之後會頻繁地暴露它的脆弱**——**這常常被誤解成「K8s 讓事情變複雜了」，實際上是「K8s 讓既有的脆弱變得可見」**。

**最有價值的判斷是「哪些複雜度該暴露給應用團隊」**。K8s 提供了大量的旋鈕——**而讓每個團隊都去理解 taint、PDB、securityContext、與資源模型是不現實的**。**平台工程的核心產出正是「一組安全的預設值與少數幾個需要團隊決定的參數」**——**讓 90% 的服務只需要填「映像、副本數、資源、以及環境變數」**，**其餘由平台的模板與政策處理**。**這比培訓每個人成為 K8s 專家實際得多。**

**而最終的立場是：K8s 是一個平台的建構材料，而不是平台本身。** **直接把裸 K8s 交給應用團隊，是把一堆材料交給需要房子的人**——**平台團隊的工作是用它蓋出那個房子。**

## 面試回答方式

先給核心思想——**宣告式加控制迴圈**，並指出**這一個模式解釋了 K8s 幾乎所有的行為**（刪掉的 Pod 會回來、設定改了要等一下、所有功能都是控制器加自訂資源）。給三個收益與三層代價。加分點有四個：**宣告式的代價是失去確定的時序**——**只保證最終收斂，中間發生什麼要另外觀察**，**而這會改變排錯方式：不問「指令有沒有成功」而問「哪個控制器該做這件事、它的狀態是什麼」**；**K8s 把應用的假設變成硬性要求**——**它不是帶來新問題，而是讓既有的脆弱變得可見**；**最有價值的判斷是「哪些複雜度該暴露給應用團隊」**，**平台工程的核心產出是一組安全的預設值加少數幾個參數**，**比培訓每個人成為專家實際得多**；以及收在立場：**K8s 是平台的建構材料而非平台本身**。

## 講稿

最核心的思想是宣告式加控制迴圈。你描述期望狀態，控制器持續地把實際狀態推向它，而不是執行一串命令。這一個模式就解釋了 K8s 幾乎所有的行為，為什麼刪掉的 Pod 會自己回來、為什麼設定改了要等一下、為什麼幾乎所有功能都是一個控制器加自訂資源。

它的收益是自我修復、可擴充、還有基礎設施能被宣告，於是 GitOps 才成為可能。

而代價有三層。認知的、運維的、還有間接性的。最後那個最痛，一個請求為什麼失敗，可能要穿過入口、服務、端點、探針、排程五層才能回答。

我還想說一個常被誤解的地方。K8s 把應用的假設變成了硬性要求。Pod 隨時可能被重建、位址隨時會變、本地磁碟隨時消失。這些不是 K8s 帶來的新問題，而是它讓分散式系統本來就有的性質變得無法迴避。一個在虛擬機上碰巧沒出過事的應用搬進來之後會頻繁暴露脆弱，那常被誤解成 K8s 讓事情變複雜，實際上是它讓既有的脆弱變得可見。

## 常見追問

### CRD 與 Operator 為什麼是 K8s 最重要的擴充點？

**核心答案**：**因為它讓「同一個模式」可以表達任何領域的運維知識**。你定義一個 CRD 描述「我想要一個什麼樣的東西」（一個 Redis 叢集、一個 CI 流水線、一個資料庫備份），**再寫一個控制器持續地讓現實符合它**——**於是你的領域知識變成了與內建資源同等地位的一等公民**，**能被 kubectl 操作、被 RBAC 管理、被 GitOps 部署。**

**詳細解析**：**「Operator 是把運維手冊變成程式」這個描述值得展開**：一份運維手冊寫著「如果主節點掛了，就把某個從節點提升為主，更新設定，然後重啟其他節點」——**Operator 把這段邏輯寫成一個 reconcile 函數，讓它在每次狀態變化時自動執行**。**收益不只是自動化，還有一致性**：**手冊會被不同的人以不同的方式執行，而程式每次都一樣**。**但寫一個好的 Operator 很難**：**reconcile 必須是冪等的（可能被重複呼叫）、必須能從任何中間狀態恢復（不能假設上次執行到哪裡）、而且要處理所有的部分失敗**。**這些要求與寫一個分散式系統的難度相當**——**所以「能用現成的成熟 Operator 就不要自己寫」是一條務實的建議**。

**面試回答方式**：給核心價值——**同一個模式可以表達任何領域的運維知識，讓你的領域知識變成與內建資源同等地位的一等公民**。核心加分點是展開**「Operator 是把運維手冊變成程式」**：**收益不只是自動化還有一致性，手冊會被不同的人以不同方式執行而程式每次都一樣**。收在難度：**reconcile 必須冪等、必須能從任何中間狀態恢復、要處理所有部分失敗**，**與寫一個分散式系統的難度相當**，**所以能用現成的成熟 Operator 就不要自己寫**。

### 平台團隊該提供什麼、不該提供什麼？

**核心答案**：**該提供「安全的預設路徑」，不該提供「所有可能的選項」**。具體是：**一組標準的部署模板**（涵蓋探針、資源、標籤、安全上下文）、**自助式的環境與資源申請**、**統一的可觀測性接入**、**以及清楚的例外流程**。**不該做的是「幫每個團隊寫 YAML」**——**那讓平台團隊成為瓶頸，而且無法擴展**。

**詳細解析**：**「黃金路徑」的判準是「用它的人不需要理解 K8s」**：填幾個欄位就能得到一個符合所有標準的部署——**而理解 Deployment 與 Service 的細節應該是選修而非必修**。**這不是把人當笨蛋，而是承認「認知預算是有限的」**：**應用團隊的認知預算應該花在業務邏輯上**。**而平台的成功指標不是「叢集有多穩定」，而是「應用團隊交付的速度與品質」**——**一個技術上完美但沒有人願意用的平台是失敗的**。**判斷平台好不好的一個實用問題是：一個新工程師從零開始，把一個服務部署到生產需要多久、需要問幾個人？** **這個數字比任何架構圖都能說明問題。**

**面試回答方式**：給該提供與不該提供的清單，並指出**幫每個團隊寫 YAML 會讓平台團隊成為瓶頸且無法擴展**。核心加分點是**黃金路徑的判準是「用它的人不需要理解 K8s」**，並說明理由：**這不是把人當笨蛋，而是承認認知預算有限，應用團隊的預算該花在業務邏輯上**。收在成功指標：**平台的指標不是叢集多穩定而是應用團隊的交付速度與品質**，**而一個實用的問題是「新工程師從零把服務部署到生產要多久、要問幾個人」**——**這個數字比任何架構圖都能說明問題**。

### 準備 K8s 面試最該掌握什麼？

**核心答案**：**掌握「一個請求與一個 Pod 的完整生命週期」，其餘的都能從中推導**。**請求的路徑**：外部 → 負載平衡器 → Ingress → Service → EndpointSlice → kube-proxy 的規則 → Pod。**Pod 的生命週期**：apply → API server 驗證與 admission → etcd → scheduler 綁定 → kubelet 拉映像與啟動 → 探針 → 加入 Endpoints → 終止時的 SIGTERM 與摘除。**這兩條線串起了 K8s 的絕大部分元件與絕大部分面試題。**

**詳細解析**：**「能講完整條線」與「知道每個名詞」是完全不同的層次**：**前者讓你能回答任何「哪裡可能出問題」的追問**，**因為你知道有哪些環節**；**後者只能回答「這個是什麼」。** **而幾乎所有的 K8s 排錯題本質上都是「這條線上的某一環斷了」**——**Pod 起不來是生命週期的前半段，流量不通是請求路徑的某一跳，滾動更新掉請求是兩條線交會的地方（終止與摘除的時序）**。**所以與其背誦各種資源的欄位，不如把這兩條線徹底講清楚並在每個環節問自己「這裡可能怎麼壞」**——**這個準備方式的效率遠高於逐個主題複習。**

**面試回答方式**：給兩條線——**請求的路徑**與**Pod 的生命週期**，並完整列出各自的環節，指出**這兩條線串起了絕大部分元件與面試題**。核心加分點是區分層次：**「能講完整條線」讓你能回答任何「哪裡可能出問題」的追問，而「知道每個名詞」只能回答「這個是什麼」**。收在具體的映射：**Pod 起不來是生命週期的前半段、流量不通是請求路徑的某一跳、滾動更新掉請求是兩條線交會處的時序問題**，**所以與其背欄位，不如把兩條線講清楚並在每個環節問「這裡可能怎麼壞」**。
