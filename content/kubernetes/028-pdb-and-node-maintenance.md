# 題目

PodDisruptionBudget 解決什麼問題？設定不當會有什麼後果？

## 核心答案

PDB 解決的是「自願中斷時一次不要動太多副本」。當節點被 drain、叢集升級、或自動擴縮容要縮減節點時——這些操作會驅逐 Pod，而 PDB 讓驅逐者在動手前先問「這樣做會不會讓可用副本數低於底線」。

**兩種表達方式**：`minAvailable`（至少要保留幾個或幾成可用）與 `maxUnavailable`（最多可以有幾個或幾成不可用）。**用百分比比用絕對數字好**，因為副本數會隨 HPA 變動，絕對數字很快就不合適。

**「自願」這兩個字是關鍵**：**PDB 只對走 Eviction API 的驅逐生效**。節點突然斷電、kubelet 崩潰、或者直接 `kubectl delete pod` 都繞過它——它是一個協作式的機制，不是強制的保護。

設定不當最典型的後果是叢集升級卡死：`minAvailable` 等於副本數時**一個 Pod 都不能被驅逐**，drain 會無限等待。

## 詳細解析

「PDB 讓升級卡死」是一個非常常見的生產問題，而它有兩種形態。**明顯的一種**是 `minAvailable: 3` 配上 3 個副本——**數學上就不可能滿足**。**隱蔽的一種**是設定看起來合理（`minAvailable: 2` 配 3 個副本），**但新 Pod 因為資源不足而起不來**——於是可用副本停在 2，永遠達不到「驅逐一個後仍有 2 個可用」的條件。後者的排查要看「被驅逐的 Pod 有沒有成功在別處重建」，而不是只看 PDB 的設定。

**單副本的服務不該設 PDB**（或者說，設了就等於宣告它不能被維護）。正確的處理是先把它變成多副本——如果因為某些原因（例如需要獨佔的鎖或本地狀態）做不到，那應該接受「維護時它會短暫中斷」，並在維護窗口安排。用 PDB 阻止驅逐並不會讓單副本變得高可用，只會讓維護無法進行。

**PDB 與 HPA 的互動要注意**。如果 HPA 在低流量時把副本縮到 2，而 PDB 要求 `minAvailable: 2`——那麼在那段時間裡完全無法驅逐。**用百分比（`maxUnavailable: 25%`）能避免這個問題**，**因為它會隨副本數自動調整**。

PDB 保護的是「副本數」而非「服務健康」。它不知道那些副本是不是真的能服務——如果三個副本裡有兩個雖然 Ready 但實際上有問題，PDB 仍然認為驅逐第三個是安全的。真正的保障來自 readiness 探針的正確性：PDB 的判斷完全建立在 Ready 狀態上，而一個總是回傳成功的 readiness 探針會讓 PDB 形同虛設。

## 面試回答方式

先給它解決的問題——自願中斷時一次不要動太多副本，並列出典型的自願中斷（drain、升級、節點縮減）。給兩種表達方式並建議用百分比而非絕對數字，因為副本數會隨 HPA 變動。強調**「自願」是關鍵**：PDB 只對走 Eviction API 的驅逐生效，斷電、崩潰、直接 delete 都繞過它，**它是協作式而非強制的保護**。加分點有四個：**升級卡死的兩種形態**——明顯的（minAvailable 等於副本數）與隱蔽的（新 Pod 因資源不足起不來，可用數永遠達不到門檻）；**單副本服務不該設 PDB**，**設了等於宣告它不能被維護**；**PDB 與 HPA 的互動**——縮容後可能完全無法驅逐，用百分比可避免；以及PDB 保護的是副本數而非服務健康，一個總是回傳成功的 readiness 探針會讓它形同虛設。

## 講稿

中斷預算解決的是自願中斷時一次不要動太多副本。節點排空、叢集升級、自動縮減節點這些操作會驅逐 Pod，而它讓驅逐者動手前先問一句，這樣做會不會讓可用副本低於底線。

自願這兩個字是關鍵。它只對走驅逐介面的操作生效。節點突然斷電、元件崩潰、或者直接刪除 Pod 都繞過它。它是協作式的機制，不是強制的保護。

設定不當最典型的後果是叢集升級卡死，而這有兩種形態。明顯的一種是最小可用數等於副本數，數學上就不可能滿足。隱蔽的一種是設定看起來合理，但新 Pod 因為資源不足起不來，於是可用副本停在門檻上，永遠達不到條件。後者要看被驅逐的 Pod 有沒有成功在別處重建，而不是只看設定。

還有一點我覺得很重要。中斷預算保護的是副本數而不是服務健康。它完全建立在就緒狀態上，所以一個總是回傳成功的就緒探針會讓它形同虛設。

## 常見追問

### 升級叢集時完整的流程是什麼？

**核心答案**：先控制平面、再工作節點，一次一個節點。控制平面升級由雲端託管服務處理（或用 kubeadm 逐個升級）；工作節點的標準流程是：cordon → drain → 升級或替換節點 → uncordon。託管服務（GKE、EKS）通常提供自動的節點池升級，它就是在做這件事，**並用 `maxSurge` 與 `maxUnavailable` 控制節奏**。

**詳細解析**：**「Surge 升級」比「原地升級」安全得多**：先建立一個新版本的節點，等它就緒後才 drain 舊節點——這樣整個過程中的總容量不會下降。原地升級則會在升級期間少一個節點的容量，如果叢集本來就接近滿載，drain 出來的 Pod 會無處可去。所以升級前的檢查清單應該包含「叢集有沒有足夠的剩餘容量吸收一個節點的工作負載」。另一個必查項是「版本偏差（version skew）政策」：kubelet 可以比 apiserver 舊最多兩個小版本，但不能更新——所以必須先升控制平面再升節點，順序反了會出問題。而跨多個小版本升級必須逐版進行，不能跳版。

**面試回答方式**：給標準流程（**先控制平面再工作節點，cordon、drain、升級、uncordon**）與託管服務的自動化。核心加分點是**Surge 升級比原地升級安全**——先建新節點就緒後才 drain 舊的，總容量不下降，而原地升級在接近滿載時會讓 drain 出來的 Pod 無處可去，所以**升級前要檢查剩餘容量**。第二個是**版本偏差政策**：kubelet 最多比 apiserver 舊兩個小版本但不能更新，**所以必須先升控制平面**，而且跨多版本要逐版升不能跳。

### 為什麼 drain 之後服務還是掉了請求？

**核心答案**：因為 Pod 終止與流量摘除不是原子的。Pod 收到 SIGTERM 的同時，Endpoints 的更新、kube-proxy 的規則同步、以及 Ingress 或雲端負載平衡器的後端摘除都是非同步的——在那個時間差裡，流量仍然會被送到正在關閉的 Pod。**解法是 `preStop` 鉤子裡先 sleep 幾秒**，**讓摘除先完成，再開始關閉。**

**詳細解析**：這個「sleep 幾秒」的做法看起來很土，但它是官方文件也承認的標準做法——因為 K8s 沒有提供「等待所有流量來源都完成摘除」的信號。時間長度取決於最慢的那個環節：純叢集內的 Service 通常 1 到 2 秒就夠，而經過雲端負載平衡器的可能要 15 到 30 秒。另一個必要的配套是 `terminationGracePeriodSeconds` 要大於「preStop 的睡眠時間加上應用真正關閉所需的時間」——否則 Pod 會在還沒處理完既有請求時被 SIGKILL。這兩個參數是配套的，只調一個沒有用。 而最徹底的驗證方式是在持續施加流量的情況下做一次滾動更新，觀察是否有錯誤——這是一個成本很低但幾乎沒有團隊做的檢驗。

**面試回答方式**：給根本原因——**Pod 終止與流量摘除不是原子的**，Endpoints 更新、kube-proxy 同步、負載平衡器摘除都是非同步的。給解法（**preStop 先 sleep 讓摘除完成**）並指出這是官方也承認的標準做法，因為 K8s 沒有提供「摘除完成」的信號。加分點是**時間長度取決於最慢的環節**（叢集內 1 到 2 秒，經過雲端負載平衡器可能 15 到 30 秒）與**必須配套調大 terminationGracePeriodSeconds**，**只調一個沒有用**。收在驗證：在持續施加流量下做一次滾動更新看有沒有錯誤——**成本很低但幾乎沒有團隊做**。

### 有哪些中斷是 PDB 完全管不到的？

**核心答案**：**所有非自願的中斷**。**節點硬體故障或斷電**、**核心 panic**、**節點的網路分割**、**kubelet 崩潰**、**節點記憶體耗盡導致的 OOM 驅逐**、**以及直接 `kubectl delete pod`**。這些都不走 Eviction API，PDB 沒有任何機會介入。

**詳細解析**：認識這個邊界很重要，因為它決定了你的可用性策略該放在哪裡。PDB 只能讓「計畫中的操作」變得安全——而生產環境的多數意外中斷都不是計畫中的。所以真正的可用性來自：足夠的副本數、跨可用區的分散、快速的故障偵測與重建、以及應用本身能容忍副本消失。 PDB 只是這套體系裡最外圍的一層。 另一個值得指出的是「節點記憶體壓力導致的驅逐」：**它由 kubelet 直接執行，不經過 API server 的 eviction 流程**——所以一個記憶體洩漏的鄰居 Pod 可以在幾秒內連帶害死同節點上的其他 Pod，**而 PDB 完全無能為力**。防這個要靠正確的 requests/limits 設定與 QoS 等級，那是另一套機制。

**面試回答方式**：列出非自願中斷的清單（硬體故障、核心 panic、網路分割、kubelet 崩潰、OOM 驅逐、直接 delete）並指出**它們都不走 Eviction API**。核心加分點是說明這個邊界決定了可用性策略該放在哪裡：PDB 只讓計畫中的操作變安全，而生產環境的多數意外中斷都不是計畫中的，真正的可用性來自足夠副本、跨區分散、快速偵測重建、以及應用能容忍副本消失。收在一個具體例子：節點記憶體壓力的驅逐由 kubelet 直接執行不經過 eviction 流程，一個記憶體洩漏的鄰居能在幾秒內害死同節點的其他 Pod，而 PDB 完全無能為力。
