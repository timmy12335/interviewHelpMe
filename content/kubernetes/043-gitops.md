# 題目

GitOps 與傳統的 CI/CD push 模式差在哪？有什麼實際好處？

## 核心答案

**核心差異是方向：push 變成 pull**。傳統模式是 **CI 跑完後拿著叢集憑證去 `kubectl apply`**；GitOps 則是叢集內的控制器持續比對「Git 裡宣告的狀態」與「叢集的實際狀態」，發現差異就自動收斂。

這個方向的翻轉帶來四個實質好處。**憑證不外流**——CI 系統不需要叢集的寫入權限，攻破 CI 不等於攻破叢集。**漂移自動修正**——有人手動改了叢集，控制器會把它改回來，**於是「Git 是真相」不只是一句口號**。**審計與回滾天然存在**——每一次變更都是一個 commit，回滾就是 revert。**多叢集一致**——同一份宣告可以被多個叢集拉取。

**代表工具是 Argo CD 與 Flux**，兩者的模型相近，差別主要在 UI 與擴充方式。

## 詳細解析

「漂移自動修正」是 GitOps 最被低估的價值。傳統模式下，有人在半夜緊急改了一個設定但忘了同步回 Git——於是 Git 與現實不一致，而下一次部署會靜默地把那個緊急修復覆蓋掉。**GitOps 讓這種偏離立刻可見**（**控制器報告 OutOfSync**），**而 `selfHeal` 開啟時會直接改回去**。代價是「緊急手動修改變得不可能」——**這在事故中可能很痛苦**，所以實務上常見的折衷是「允許手動改但保留 OutOfSync 的告警」，**強迫事後補上 commit**。

「應用倉庫」與「設定倉庫」應該分開。應用的程式碼變更與部署的宣告變更有不同的節奏與審查者——混在一起會讓每次程式碼提交都觸發部署宣告的 diff。標準流程是：CI 建置映像並推送 → CI 更新設定倉庫裡的映像標籤 → GitOps 控制器偵測到並部署。中間那一步的自動化（image updater）是連接兩者的關鍵。

**Secret 是 GitOps 的經典難題**——因為「所有東西都在 Git 裡」與「密鑰不能進 Git」直接衝突。**三個解法**：**Sealed Secrets**（加密後的密文可以進 Git，只有叢集的私鑰能解）、**SOPS**（用 KMS 加密欄位）、**以及 External Secrets Operator**（Git 裡只放「去哪裡取密鑰」的引用）。第三種最乾淨，因為 Git 裡完全沒有密文。

GitOps 不解決「部署順序」與「漸進式發布」。控制器只是讓實際狀態趨向宣告狀態——它不知道「先跑遷移再更新應用」或「先給 5% 流量觀察十分鐘」。**這些需要 sync wave、hook、或者搭配 Argo Rollouts 這類工具**。

## 面試回答方式

先給核心差異——push 變成 pull，叢集內的控制器持續比對並收斂，並給四個實質好處（憑證不外流、漂移自動修正、審計與回滾天然存在、多叢集一致）。加分點有四個：漂移自動修正是最被低估的價值——傳統模式下半夜的緊急修改會被下次部署靜默覆蓋，而代價是緊急手動修改變得不可能，所以常見折衷是允許手動改但保留 OutOfSync 告警強迫事後補 commit；**應用倉庫與設定倉庫要分開**，並說明標準流程與 image updater 的角色；**Secret 是經典難題**與三個解法，其中 External Secrets 最乾淨因為 Git 裡完全沒有密文；以及GitOps 不解決部署順序與漸進式發布，需要 sync wave 或 Argo Rollouts。

## 講稿

核心差異是方向，推變成拉。傳統模式是持續整合跑完之後，拿著叢集憑證去套用。而這個模式是叢集裡的控制器持續比對 Git 宣告的狀態跟叢集的實際狀態，發現差異就自動收斂。

這個翻轉帶來四個好處。憑證不外流，持續整合系統不需要叢集寫入權限。漂移會自動修正。審計跟回滾天然存在，回滾就是撤銷一個提交。還有多叢集一致。

我覺得最被低估的是漂移自動修正。傳統模式下有人半夜緊急改了設定但忘了同步回 Git，於是 Git 跟現實不一致，而下一次部署會靜默地把那個緊急修復覆蓋掉。這個模式讓偏離立刻可見。代價是緊急手動修改變得不可能，在事故中可能很痛苦，所以常見的折衷是允許手動改但保留不同步的告警，強迫事後補上提交。

另外有兩件事它不解決。密鑰不能進 Git，這需要額外的方案。還有部署順序跟漸進式發布，控制器只是讓實際狀態趨向宣告狀態，它不知道要先跑遷移再更新應用。

## 常見追問

### 多叢集怎麼管理？

**核心答案**：用「應用集合」的抽象把同一份宣告展開到多個叢集。Argo CD 的 ApplicationSet 支援按叢集清單、按 Git 目錄、或按標籤自動生成 Application——新增一個叢集只需要註冊它，所有該部署的應用會自動同步過去。**差異用每叢集的 overlay 或 values 表達**。

**詳細解析**：「哪些差異是合理的」是多叢集管理裡最重要的治理問題：規模（不同區域的副本數）、端點（區域特定的資料庫）、以及功能旗標（漸進式開通）是合理的；而「某個叢集跑的是不同版本的應用」則應該是暫時狀態而非常態——因為那讓「一個 bug 在哪些叢集存在」變成一個需要逐一查詢的問題。實務上的做法是「用 GitOps 讓版本推進成為一個可見的流程」：設定倉庫裡明確記錄每個叢集當前的版本，**推進就是一個 PR**——於是「哪個叢集跑什麼」永遠可以從 Git 讀出來，而不需要去叢集裡查。這正是「單一真相來源」在多叢集場景下的具體收益。

**面試回答方式**：給 ApplicationSet 的機制（按叢集清單、目錄或標籤自動生成，新增叢集只需註冊）。核心加分點是把它提升到治理層面：**哪些差異是合理的**——規模、端點、功能旗標合理，而「不同叢集跑不同版本」應該是暫時狀態而非常態，因為那讓「一個 bug 在哪些叢集存在」變成需要逐一查詢的問題。收在具體收益：設定倉庫明確記錄每個叢集的版本、推進就是一個 PR，於是「哪個叢集跑什麼」永遠能從 Git 讀出來。

### 同步失敗或部署錯誤怎麼處理？

**核心答案**：**GitOps 的回滾就是 revert commit**——控制器會偵測到並把叢集改回去。但要注意「revert 不一定等於回到原狀」：如果那次變更包含了資料庫遷移或不可逆的外部副作用，revert 只還原了 K8s 資源。所以「能安全 revert」的前提與傳統部署一樣，是變更本身向後相容。

**詳細解析**：Argo CD 的 `syncPolicy` 是一個需要謹慎設定的地方：`automated` 加 `selfHeal` 意味著「Git 一改就立刻部署，而且叢集偏離就立刻修正」——這在開發環境很好，但在生產環境意味著「一個錯誤的 merge 會在幾秒內生效」。常見的做法是「生產環境用手動 sync」：控制器偵測到差異並顯示 OutOfSync，由人按下同步——保留了 GitOps 的所有好處，同時加上一道人工關卡。另一個要點是「sync 失敗時的可見性」：**Argo CD 的健康狀態會顯示為 Degraded 或 Progressing**，但如果沒有把它接到告警系統，失敗可能好幾個小時沒有人發現——因為 GitOps 的部署是背景進行的，沒有人在盯著一個 CI 的紅燈。

**面試回答方式**：給回滾方式（revert commit）並指出**revert 不一定等於回到原狀**——資料庫遷移與外部副作用不會被還原，所以「能安全 revert」的前提仍然是變更向後相容。核心加分點是 **`syncPolicy` 的設定**：automated 加 selfHeal 在生產意味著錯誤的 merge 幾秒內生效，所以常見做法是生產用手動 sync，保留所有好處並加一道人工關卡。收在可見性：GitOps 的部署是背景進行的，沒有人在盯著 CI 的紅燈，所以 sync 失敗必須接到告警系統，否則可能好幾個小時沒人發現。

### GitOps 有什麼不適合的場景？

**核心答案**：**三類**。需要頻繁、細粒度動態調整的東西——例如按流量即時調整的參數，**走 Git 提交的節奏太慢**。**大量由系統自動生成的資源**——例如每個租戶動態建立的 namespace，把它們都塞進 Git 會讓倉庫變成一個低效的資料庫。**以及高度互動的除錯過程**——事故中需要快速嘗試不同的設定時，GitOps 的流程是阻力。

**詳細解析**：第二類值得展開，因為它涉及一個常見的誤用：GitOps 適合管理「人決定的期望狀態」，不適合管理「系統推導出的狀態」。如果一個資源是由另一個控制器根據業務邏輯建立的（例如 Operator 為每個租戶建立的資源），那它本來就不該在 Git 裡——**Git 裡該有的是那個 Operator 與它的設定**。混淆這兩者會導致「Git 與叢集永遠 OutOfSync」的困境，因為控制器一直在建立 Git 裡沒有的東西。Argo CD 的 `ignoreDifferences` 與資源排除設定就是為了處理這類邊界，而需要大量使用它們通常是一個訊號：邊界畫錯了。

**面試回答方式**：給三類不適合的場景。核心加分點是展開第二類的原則：GitOps 適合管理「人決定的期望狀態」，不適合管理「系統推導出的狀態」——Operator 為每個租戶建立的資源本來就不該在 Git 裡，Git 裡該有的是那個 Operator 與它的設定。收在一個實用的訊號：**混淆兩者會導致永遠 OutOfSync**，而需要大量使用 `ignoreDifferences` 通常表示邊界畫錯了。
