# 題目

一個 Java 物件在記憶體中的佈局是怎樣的？物件頭裡存了什麼？

## 核心答案

一個物件在堆記憶體中的佈局分三部分：物件頭（Header）、實例資料（Instance Data）、對齊填充（Padding）。物件頭又分兩部分——Mark Word（存放物件的執行時資料：雜湊碼、GC 分代年齡、鎖狀態標誌、偏向鎖執行緒 ID 等，會隨鎖狀態變化）和類型指標（Klass Pointer，指向方法區中該物件所屬類別的元資料）。實例資料是物件真正儲存的欄位內容。對齊填充是為了讓物件的總大小是 8 位元組的整數倍（HotSpot 要求物件起始位址 8 位元組對齊）。

## 詳細解析

**三部分佈局**：

1. **物件頭（Object Header）**：
   - **Mark Word**：存放物件執行時的動態資料，64 位元 JVM 中通常是 8 位元組。它的內容會隨鎖狀態複用——無鎖時存雜湊碼和 GC 年齡，偏向鎖時存執行緒 ID，輕量級鎖時存指向鎖記錄的指標，重量級鎖時存指向 Monitor 的指標。這種「複用同一塊空間存不同資訊」的設計是為了節省空間（見 Java 併發的 synchronized 鎖升級）。
   - **類型指標（Klass Pointer）**：指向方法區/元空間中該類別的元資料，JVM 靠它知道這個物件是哪個類別的實例。開啟指標壓縮（`-XX:+UseCompressedOops`，預設開啟）時是 4 位元組，否則 8 位元組。
   - （陣列物件的物件頭還會多一塊記錄陣列長度的空間。）

2. **實例資料（Instance Data）**：物件真正的欄位內容（包括從父類別繼承的欄位）。JVM 會對欄位做重排以優化記憶體對齊（相同寬度的欄位排在一起）。

3. **對齊填充（Padding）**：不是必需的，僅起佔位作用——HotSpot 要求物件的起始位址必須是 8 位元組的整數倍，所以如果物件大小不是 8 的倍數，會填充到 8 的倍數。

**為什麼要 8 位元組對齊**：CPU 存取對齊的記憶體更高效（一次讀取就能拿到完整資料，不用跨快取行），對齊也簡化了記憶體管理。

## 面試回答方式

用「三部分」的結構回答——物件頭、實例資料、對齊填充。重點講物件頭的兩部分：Mark Word（存執行時資料、且隨鎖狀態複用，連結到 synchronized 鎖升級）和類型指標（指向類別元資料、涉及指標壓縮）。這兩個是最容易深挖的點。實例資料和對齊填充各一句帶過即可。能講出「Mark Word 隨鎖狀態複用同一塊空間存不同資訊」以及「對齊是為了 CPU 存取效率」，展現你理解佈局設計背後的空間和效能考量，而非只背三部分名稱。

## 常見追問

### 一個空物件 new Object() 佔多少位元組？

**核心答案**：在 64 位元 JVM、開啟指標壓縮（預設）的情況下，一個 `new Object()` 佔 16 位元組——Mark Word 8 位元組 + 類型指標 4 位元組（壓縮後）= 12 位元組的物件頭，但因為要 8 位元組對齊，填充 4 位元組湊到 16 位元組。`Object` 沒有實例欄位，所以實例資料是 0。

**詳細解析**：這個計算是理解物件佈局的一個好練習。拆解——Mark Word 固定 8 位元組；類型指標在開啟壓縮指標（`UseCompressedOops`，堆小於 32GB 時預設開啟）時是 4 位元組；`Object` 沒有任何欄位所以實例資料 0 位元組；物件頭合計 12 位元組不是 8 的倍數，所以填充 4 位元組對齊到 16。如果關閉指標壓縮，類型指標變 8 位元組，物件頭就是 16 位元組（剛好對齊），也是 16 位元組。所以無論是否壓縮，`new Object()` 通常都是 16 位元組。理解這個計算，能讓你在需要估算物件記憶體佔用（如評估快取容量、排查記憶體問題）時有基本的判斷依據，也展現你對物件佈局的細節有量化的掌握。

**面試回答方式**：給出「16 位元組」並拆解計算過程（Mark Word 8 + 壓縮類型指標 4 = 12、填充 4 到 16）。能說明「開不開壓縮指標結果都是 16」以及「這對估算物件記憶體佔用有用」，展現你不只知道佈局結構還能實際計算，這種量化能力很加分。

### 什麼是指標壓縮（Compressed Oops）？為什麼能節省記憶體？

**核心答案**：指標壓縮（Compressed Ordinary Object Pointers）是把原本 64 位元（8 位元組）的物件引用壓縮成 32 位元（4 位元組）來儲存，從而節省記憶體。它的原理是——因為物件都是 8 位元組對齊的，物件位址的最後 3 位元恆為 0，可以不儲存這 3 位元，於是 32 位元就能定址 `2^(32+3) = 2^35 = 32GB` 的空間。所以當堆小於 32GB 時，JVM 預設開啟指標壓縮，把物件頭中的類型指標、以及物件之間的引用都用 4 位元組儲存，顯著減少記憶體佔用（尤其引用密集的資料結構）。

**詳細解析**：在 64 位元 JVM 上，如果所有指標都用完整的 8 位元組，相比 32 位元 JVM 會多消耗大量記憶體（每個引用都翻倍），這是 64 位元 JVM 的「記憶體稅」。指標壓縮巧妙地利用「8 位元組對齊使位址低 3 位恆為 0」這個特性——既然低 3 位總是 0，儲存時就把位址右移 3 位（丟掉那 3 個 0）壓成 32 位元，使用時再左移 3 位還原。這讓 32 位元的壓縮指標能覆蓋 32GB 的堆（超過 32GB 就無法壓縮、必須用完整 64 位元指標，這也是為什麼建議堆大小要嘛明顯小於 32GB、要嘛遠大於 32GB，卡在 32GB 附近反而因為關閉壓縮而「用更大的堆卻能存更少的物件」）。理解指標壓縮能解釋很多記憶體相關的現象和調優建議。

**面試回答方式**：講出「把 64 位元引用壓成 32 位元、利用 8 位元組對齊低 3 位恆為 0、右移 3 位後 32 位元能覆蓋 32GB」。能點出「所以堆超過 32GB 會關閉壓縮、卡在 32GB 附近不划算」這個實務調優建議，展現你理解指標壓縮的原理及其對堆大小設定的實際影響。

### Mark Word 為什麼要設計成隨鎖狀態複用同一塊空間？

**核心答案**：因為物件頭的空間非常寶貴——每個物件都有物件頭，如果為「雜湊碼、GC 年齡、鎖資訊、偏向執行緒 ID、鎖記錄指標、Monitor 指標」等各種資訊都分配獨立的空間，會讓每個物件的物件頭變得很大，在物件數量巨大時浪費大量記憶體。Mark Word 的設計是——用同一塊固定大小（8 位元組）的空間，根據物件當前的鎖狀態（無鎖/偏向鎖/輕量級鎖/重量級鎖）「複用」來存放不同的資訊，並用最後幾個位元作為「鎖狀態標誌」來標示當前存的是哪種資訊。這是典型的「用時間換空間」——存取時要先判斷狀態，但省下了大量記憶體。

**詳細解析**：這個設計和 Java 併發中 synchronized 的鎖升級是同一件事的兩面。無鎖狀態下 Mark Word 存雜湊碼和 GC 分代年齡；一旦物件被作為鎖使用並發生偏向，就複用這塊空間存偏向執行緒 ID；升級到輕量級鎖時存指向棧幀中鎖記錄的指標；升級到重量級鎖時存指向 Monitor（ObjectMonitor）的指標。JVM 靠 Mark Word 末尾的 2-3 個位元（鎖標誌位）來區分當前是哪種狀態、該如何解讀這塊空間。這種複用的代價是——某些操作需要先讀鎖標誌位判斷狀態（例如一個物件一旦升級到重量級鎖，它原本存在 Mark Word 的雜湊碼就被 Monitor 指標覆蓋了，需要存到 Monitor 中）。理解這個設計，能把「物件記憶體佈局」和「synchronized 鎖升級」兩個知識點打通，展現你對 JVM 底層設計的整體理解。

**面試回答方式**：講出「物件頭空間寶貴、物件數量巨大、為各種資訊都留獨立空間太浪費、所以用同一塊空間隨鎖狀態複用、用鎖標誌位區分」。能連結到 synchronized 的鎖升級（無鎖存雜湊碼、偏向存執行緒 ID、重量級存 Monitor 指標），展現你把物件佈局和鎖機制打通理解，這是很有深度的回答。
