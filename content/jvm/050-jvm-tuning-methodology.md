# 題目

如果一個服務的延遲不達標，你會怎麼系統地排查與調優？

## 核心答案

順序是先定義目標、再量測現狀、再定位瓶頸、最後才調整——而且調整的優先順序是**應用層優於 JVM 參數**。

**第一步，定義可量測的目標**：是 P99 延遲、吞吐、還是資源成本？沒有明確目標的「調優」會變成無止境的參數嘗試。**第二步，建立基準**：延遲分布、吞吐、GC 停頓與頻率、分配速率、CPU 與記憶體用量，並確認這些數字在穩定狀態下量得。

**第三步，定位瓶頸**——關鍵是先確認**是不是 JVM 的問題**。GC 日誌的停頓時間與延遲毛刺對得上嗎？CPU 高不高？如果 CPU 低、GC 停頓短、而延遲仍然差，那瓶頸在下游或鎖，不在 JVM。**很多「JVM 調優」的需求其實是誤診。**

**第四步，依序處理**：**降低分配速率**（應用層，收益最大也最持久）→ **修正資料結構與演算法** → **調整堆積大小與分代比例** → **換收集器** → **調細部參數**。這個順序反映了「收益遞減、風險遞增」。

## 詳細解析

「先確認是不是 JVM 的問題」這一步最常被跳過，也最常導致浪費。典型的誤診是：延遲毛刺 → 假設是 GC → 開始調 GC 參數 → 沒有改善 → 換收集器 → 還是沒改善。而真正的原因可能是容器的 CPU 節流、下游的尾延遲、或某個鎖的爭用。 判斷的方法很直接：把 GC 日誌的時間戳與延遲毛刺的時間戳對齊比對，對不上就不是 GC。

**降低分配速率為什麼排第一**：它同時改善多個維度——GC 頻率下降、每次回收的工作量下降、晉升減少、CPU 開銷下降、快取效率提升。而且它是應用層的改動，效果確定且不依賴特定的 JVM 版本或收集器。相比之下，調參只是在既定的工作量下重新分配成本，天花板低得多。找出高分配點的工具是配置剖析（async-profiler 的 alloc 模式或 JFR 的配置事件），通常前幾個熱點就佔了大部分。

**調參應該一次一個並量測**。同時改五個參數然後效能好了 10%，你不知道哪個有效、哪些是無效或有害的。這聽起來慢，但它產生的是可累積、可解釋的知識——下一次遇到類似問題時，那些知識還在。大量從網路抄來的參數組合是相反的做法：它產生一個沒有人能推理的設定，而且會被一代代地傳下去。

最後一個判斷：什麼時候該停止調優。 當「再改善 10% 的成本」超過「那 10% 的價值」時就該停。實務上更常見的正確答案是**橫向擴展或改架構**——加一台機器、加一層快取、或把同步呼叫改成非同步，收益往往遠大於任何 JVM 調參。能說出「這個問題不該用調優解決」也是調優能力的一部分。

## 面試回答方式

先給**四步順序**（定義目標、建立基準、定位瓶頸、依序調整）並強調**應用層優於 JVM 參數**。第三步要展開最重要的一句：**先確認是不是 JVM 的問題**——把 GC 日誌的時間戳與延遲毛刺對齊比對，對不上就不是 GC，而**很多「JVM 調優」的需求其實是誤診**（真因常是容器 CPU 節流、下游尾延遲、或鎖爭用）。第四步給出**優先順序**（降低分配速率 → 修資料結構與演算法 → 調堆積與分代 → 換收集器 → 調細部參數）並說明它反映「收益遞減、風險遞增」。加分點有兩個：**分配速率為什麼排第一**（同時改善多個維度、應用層改動效果確定、不依賴特定 JVM 版本）；以及**調參要一次一個並量測**，因為那產生可累積可解釋的知識。收在一個成熟的判斷：能說出「這個問題不該用調優解決」也是調優能力的一部分。

## 講稿

我的順序是先定義目標、再量測現狀、再定位瓶頸、最後才調整。而且調整的優先順序是應用層優於 JVM 參數。

第一步是定義可量測的目標。是 P99 延遲、吞吐、還是資源成本？沒有明確目標的調優會變成無止境的參數嘗試。第二步建立基準，延遲分布、GC 停頓與頻率、分配速率、CPU 跟記憶體。

第三步我覺得最關鍵，先確認是不是 JVM 的問題。把 GC 日誌的時間戳跟延遲毛刺的時間對齊比對，對不上就不是 GC。很多所謂的 JVM 調優需求其實是誤診，真正的原因可能是容器的 CPU 節流、下游的尾延遲、或某個鎖的爭用。

第四步依序處理。先降低分配速率，再修資料結構跟演算法，然後才是調堆積大小、換收集器、調細部參數。這個順序反映的是收益遞減、風險遞增。

降低分配速率排第一，因為它同時改善多個維度，而且是應用層的改動，效果確定也不依賴特定的收集器。調參只是在既定的工作量下重新分配成本，天花板低得多。

最後一個判斷是什麼時候該停。很多時候正確的答案是橫向擴展或改架構，而不是繼續調參。

## 常見追問

### 怎麼判斷延遲問題是 GC 造成的？

**核心答案**：**時間戳對齊**是唯一可靠的方法。把 GC 日誌（帶絕對時間戳）與應用的延遲指標放在同一條時間軸上，看毛刺是否與 GC 停頓重合。**三種結果對應三種結論**：完全重合且停頓時長與毛刺相當，就是 GC；重合但毛刺遠大於停頓，說明還有安全點到達時間或其他因素疊加；完全不重合，就不是 GC。

**詳細解析**：「毛刺遠大於停頓」這個情況特別值得注意，它通常指向**安全點到達時間**（某個執行緒卡在沒有安全點的長迴圈裡讓所有人等待）或**排隊效應**——GC 停頓 50 毫秒期間到達的請求全部排隊，停頓結束後它們的處理時間仍然包含了等待，所以觀察到的延遲遠大於 50 毫秒。排隊效應在高吞吐服務上會顯著放大 GC 的影響：每秒一萬個請求時，50 毫秒的停頓意味著 500 個請求排隊，最後一個的額外延遲遠超 50 毫秒。這解釋了為什麼「GC 停頓看起來不長但影響很大」——影響量取決於停頓時間乘以到達速率。

**面試回答方式**：給出時間戳對齊的方法與**三種結果對應的三種結論**。重點展開「毛刺遠大於停頓」的情況，並給出最有價值的解釋：**排隊效應**——每秒一萬請求時 50 毫秒停頓意味著 500 個請求排隊，最後一個的額外延遲遠超停頓本身。收在一句公式化的認識：GC 的影響量取決於停頓時間乘以到達速率，這解釋了為什麼「停頓看起來不長但影響很大」。

### 調優時最常見的錯誤有哪些？

**核心答案**：五個。**沒有目標就開始調**——不知道要達到什麼，就不知道何時該停。**沒有基準**——改了之後不知道有沒有效。**一次改很多**——無法歸因。**抄別人的參數**——版本與工作負載都不同。**只調 JVM 不看應用**——把力氣用在天花板最低的地方。

**詳細解析**：還有一個更隱蔽的錯誤：在錯誤的環境量測。開發機的四核與生產的三十二核、測試環境的空載與生產的高併發、以及容器限制的有無——這些差異會讓量測結論完全不同。典型的例子是在本機量測發現某個參數有效，上了生產卻沒有效果甚至更糟，因為本機沒有 CPU 節流也沒有真實的並發爭用。所以效能相關的結論必須在盡可能接近生產的環境下取得，而這往往意味著要有一個專門的壓測環境或在生產上做小流量的 A/B 驗證。「量測環境的代表性」是效能工作中最容易被忽略卻最影響結論正確性的一項。

**面試回答方式**：給五個常見錯誤（無目標、無基準、一次改多個、抄參數、只調 JVM）。真正的加分點是提出第六個更隱蔽的：**在錯誤的環境量測**——開發機與生產的核心數、負載、容器限制都不同，本機有效的參數上生產可能無效甚至更糟。收在一句：量測環境的代表性是效能工作中最容易被忽略卻最影響結論正確性的一項，所以需要接近生產的壓測環境或生產上的小流量驗證。

### 什麼情況下應該接受現狀而不繼續調優？

**核心答案**：三種。**已經達到目標**——繼續調優是浪費，而且每個非預設參數都是未來的維護負擔。**邊際成本超過邊際收益**——再改善 5% 需要兩週的工程時間，而加一台機器只要幾百塊，那就加機器。**瓶頸不在自己手上**——延遲主要來自下游服務或網路，本地調優無論如何都碰不到那部分。

**詳細解析**：還有一種常被忽略的情況：調優會讓系統更脆弱。 一個高度調校的設定往往只在特定的工作負載下最優——流量模式改變、資料量成長、或換一批機器，它可能反而更差。預設值的價值在於它對各種情況都不會太差，而高度特化的設定是在犧牲穩健性換取當前的最優。所以在流量模式會變化的系統上，適度保守的設定往往比極致調優更好。 這與過度擬合的概念是同一回事：針對當前觀測最佳化到極致，通常會損害對未來變化的適應力。能提出這一點，通常比展示調參技巧更能顯示工程判斷的成熟度。

**面試回答方式**：給三種情況（已達目標、邊際成本超過收益、瓶頸不在自己手上）並各配一句具體判斷。真正的加分點是第四種：**調優會讓系統更脆弱**——高度調校的設定只在特定工作負載下最優，流量或資料變化後可能更差，而預設值的價值在於對各種情況都不會太差。收在類比：這與過度擬合是同一回事，針對當前觀測最佳化到極致會損害對未來變化的適應力。
