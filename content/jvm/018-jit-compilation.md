# 題目

什麼是 JIT 即時編譯？Java 既然是「解釋執行」，為什麼還能跑得快？

## 核心答案

Java 採用「解釋執行 + 即時編譯（JIT）」的混合模式。程式一開始由「解釋器」逐條解釋執行位元組碼（Bytecode）（啟動快、無需編譯等待）；同時 JVM 會偵測「熱點程式碼」（被頻繁執行的方法或迴圈），把這些熱點程式碼透過「JIT 編譯器」在執行期編譯成高度優化的本地機器碼並快取起來，之後直接執行機器碼（快得多）。這種「一邊執行一邊把熱點編譯成機器碼」的方式，讓 Java 兼顧了「啟動快（解釋執行）」和「執行快（熱點編譯）」，是 Java 性能能接近 C/C++ 的關鍵。

## 詳細解析

**為什麼是混合模式**：

- **純解釋執行**：逐條解釋位元組碼，啟動快（不用等編譯）、但執行慢（每條指令都要解釋）。
- **純編譯執行**：啟動時就把全部程式碼編譯成機器碼，執行快、但啟動慢（要等編譯）、且無法根據執行期資訊做優化。
- **混合模式（Java 採用）**：解釋器負責啟動和執行不頻繁的程式碼（快速啟動），JIT 把熱點程式碼編譯成機器碼（執行高效），兼顧兩者優點。

**熱點探測**：JVM 怎麼知道哪些是熱點？用「基於計數器的熱點探測」——為每個方法維護「方法呼叫計數器」和「迴圈回邊計數器」，當計數超過閾值（如方法被呼叫很多次、或迴圈執行很多次），就判定為熱點，觸發 JIT 編譯。

**分層編譯（Tiered Compilation）**：現代 JVM 用分層編譯，結合多個編譯器——

- C1（Client Compiler）：編譯快、優化較少，用於較早期的熱點。
- C2（Server Compiler）：編譯慢、優化激進，用於最熱的核心程式碼。
- 分層讓程式碼從解釋執行 → C1 編譯 → C2 編譯逐步升級，平衡編譯開銷和執行效能。

**JIT 的優化**：因為 JIT 在執行期編譯，能利用執行期的真實資訊做「靜態編譯器做不到」的優化——方法內聯（把小方法直接嵌入呼叫處）、逃逸分析（Escape Analysis）（棧上分配、標量替換、鎖消除）、去虛擬化、迴圈優化、分支預測等。這些執行期資訊驅動的優化是 JIT 相比 C/C++ 靜態編譯的獨特優勢。

## 面試回答方式

先破除「Java 慢因為解釋執行」的誤解——講清楚 Java 是「解釋 + JIT 混合模式」，用「解釋器負責快速啟動、JIT 把熱點編成機器碼負責高效執行」概括。接著講熱點探測（計數器）和分層編譯（C1/C2）。JIT 的優化是加分點——強調「JIT 能利用執行期真實資訊做靜態編譯做不到的優化（內聯、逃逸分析、去虛擬化）」，這是 Java 性能的核心也是它相比 C++ 靜態編譯的獨特之處。能講出這層，展現你理解 Java 性能的真正來源而非停留在「解釋執行很慢」的刻板印象。

## 常見追問

### 方法內聯（Inlining）是什麼？為什麼重要？

**核心答案**：方法內聯是 JIT 的一項核心優化——把一個被呼叫的（通常較小的）方法的程式碼「直接嵌入」到呼叫它的地方，消除方法呼叫本身的開銷（壓棧、跳轉、返回等）。它重要是因為——一是直接消除了方法呼叫的固定開銷（在高頻呼叫的小方法上累積起來很可觀）；二是更關鍵的，內聯後原本分散在多個方法裡的程式碼被合併到一起，為後續的其他優化（如逃逸分析、常數傳播、死程式碼消除）創造了更大的優化範圍——很多優化只有在「能看到完整的程式碼上下文」時才能進行，內聯正是把上下文打通。

**詳細解析**：內聯被稱為「優化之母」，因為它是很多其他優化的前提。想像一個 getter `getX()` 被高頻呼叫——不內聯的話每次呼叫都有方法呼叫開銷；內聯後`getX()` 的程式碼（`return this.x`）直接出現在呼叫處，不僅省了呼叫開銷，而且如果呼叫處還有 `getX() + getY()` 這樣的運算，內聯後 JIT 能看到完整運算式、可能進一步優化（如常數摺疊）。更重要的是逃逸分析——一個物件是否逃逸，往往要跨方法邊界才能判斷，內聯把方法邊界消除後，逃逸分析才能看清這個物件的完整生命週期、判斷它能否棧上分配。所以內聯不只是省一次呼叫，而是「打通優化的視野」。JIT 會根據方法大小（太大的不內聯，避免程式碼膨脹）、呼叫頻率等決定是否內聯，這也是為什麼「小方法」對 JIT 友好、過大的方法反而可能因無法內聯而失去很多優化機會。

**面試回答方式**：講出內聯是「把被呼叫方法的程式碼嵌入呼叫處、消除呼叫開銷」，並強調它更深層的價值——「打通方法邊界、為逃逸分析等後續優化創造完整視野，是優化之母」。能點出「小方法對 JIT 友好、過大方法無法內聯」的實務啟示，展現你理解內聯不只是省呼叫而是優化的前提。

### 為什麼有時候程式碼「跑一段時間後才變快」（預熱 warm-up）？

**核心答案**：因為 JIT 是「即時編譯」——程式剛啟動時，熱點程式碼還沒被識別和編譯，所有程式碼都在解釋執行（較慢）；隨著程式運行，熱點程式碼的計數器累積達到閾值，JIT 才把它們編譯成優化的機器碼，之後這些程式碼才變快。所以 Java 程式有一個「預熱（warm-up）」過程——運行一段時間、熱點被充分編譯優化後，才達到最佳效能。這也是為什麼做 Java 性能測試（benchmark）時必須先預熱，否則測到的是「還在解釋執行、未充分優化」的失真效能。

**詳細解析**：這個「預熱」現象是 JIT 混合模式的直接後果，理解它對正確做性能測試至關重要。剛啟動時——熱點未識別、解釋執行，慢；運行一段時間後——熱點被 C1 編譯，變快；持續運行——最熱的程式碼被 C2 用激進優化編譯，達到峰值效能。所以如果你在 Java 程式剛啟動就測量某段程式碼的效能，測到的是解釋執行的失真結果，遠低於它「熱」了之後的真實效能。這正是為什麼專業的 Java benchmark 工具（如 JMH，Java Microbenchmark Harness）會強制要求「預熱階段（warm-up iterations）」——先跑若干輪讓 JIT 充分編譯優化，再開始正式測量。這也影響一些實務決策——例如對啟動速度敏感的 serverless 場景，JIT 的預熱開銷是個痛點（剛啟動就要處理請求卻還沒優化好），這推動了 AOT 編譯（提前編譯，如 GraalVM Native Image）等技術的發展。

**面試回答方式**：講出「剛啟動熱點未編譯所以慢、運行一段時間熱點被 JIT 編譯後才快、所以有預熱過程」，並強調「做 benchmark 必須預熱（用 JMH）否則測到失真的解釋執行效能」。能延伸到「JIT 預熱開銷推動了 AOT/GraalVM Native Image 等技術」，展現你理解預熱現象的成因、對測試的影響、以及相關的技術演進。

### 什麼是「去優化（Deoptimization）」？JIT 為什麼需要它？

**核心答案**：去優化是指 JIT 把一段已經編譯優化的機器碼「退回」到解釋執行的過程。JIT 需要它是因為——JIT 的很多優化是基於「執行期觀察到的情況做的假設性優化（激進優化）」，例如「假設某個方法呼叫總是走某個具體實作」而做了去虛擬化和內聯；但如果之後執行期的情況變了（例如載入了新的類別、出現了之前沒見過的型別），這些假設不再成立，繼續用基於錯誤假設編譯的機器碼會導致錯誤，此時 JIT 就「去優化」——放棄這段機器碼、退回解釋執行，保證正確性，之後可能再根據新情況重新編譯。

**詳細解析**：去優化是 JIT「激進優化」得以安全進行的保障機制。JIT 為了極致效能，會做很多「賭一把」的優化——例如觀察到一個介面呼叫在執行期一直只有一個實作類別，就大膽地去虛擬化並內聯這個實作（省掉動態分派）；或者根據分支的歷史走向做分支預測優化。這些優化都建立在「執行期觀察到的模式會持續」的假設上，但假設可能被打破（後來載入了介面的第二個實作、分支突然走了另一邊）。如果沒有去優化，這些激進優化就是不安全的（假設破滅就出錯）。有了去優化，JIT 可以放心地激進——「先按當前觀察到的情況做最激進的優化，一旦假設被打破就去優化退回解釋執行、保證正確」。這種「樂觀假設 + 失敗回退」的模式讓 JIT 能在保證正確性的前提下追求極致效能。理解去優化，能讓你明白 JIT 的優化為什麼敢那麼激進、以及為什麼 Java 能在動態性（執行期載入類別、多型）和高效能之間取得平衡。

**面試回答方式**：講出「去優化是把已編譯的機器碼退回解釋執行，因為 JIT 的激進優化基於執行期假設（如去虛擬化假設只有一個實作），假設被打破時需要退回保證正確」。能提煉出「樂觀假設 + 失敗回退，讓 JIT 敢於激進優化又保證正確」這個核心思想，展現你對 JIT 優化哲學的深入理解，是很強的加分回答。
