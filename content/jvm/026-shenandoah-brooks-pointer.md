# 題目

Shenandoah 與 ZGC 的目標相同，做法差在哪？「轉發指標」解決了什麼問題？

## 核心答案

兩者的目標一致——**停頓時間與堆積大小無關**，做法的差別在用什麼機制讓使用者執行緒在物件移動期間仍能正確存取物件。

Shenandoah 早期用 **Brooks 轉發指標**：**每個物件都多一個指標欄位**，正常情況指向自己，物件被移動後就指向新位址。所有存取都先經過這個間接跳轉，於是即使物件已經被搬走，舊引用仍然能找到它。ZGC 則用**著色指標**——把中繼資訊放進指標的閒置高位，不需要每個物件多一個欄位。

轉發指標的代價是每個物件多 8 位元組（在物件普遍很小的 Java 堆積裡，這可能是 10% 到 20% 的額外記憶體），以及**每次存取多一次間接跳轉**。所以 Shenandoah 後續版本改用了**基於引用的讀屏障**（把轉發資訊放在物件頭的 mark word 裡，只在物件真的被移動時才需要處理），大幅降低了常態開銷。

實務上兩者的定位幾乎重疊，選擇往往取決於**發行版**：Shenandoah 由 Red Hat 主導、在 OpenJDK 建置中通常可用；ZGC 由 Oracle 主導、是 Oracle JDK 的重點。

## 詳細解析

**「併發移動物件」為什麼困難**：移動的瞬間，可能有使用者執行緒正拿著舊引用讀寫這個物件。如果不做任何處理，就會出現「兩個副本各被寫入一半」的資料損壞。解法只有兩類——要嘛讓舊引用仍然能找到新位址（轉發指標）、要嘛在每次讀取時就修正引用（著色指標加讀屏障）。理解這一點，就能看出所有低停頓收集器的設計都在這兩條路上。

**Shenandoah 的區域劃分與 G1 類似**（把堆積切成大小相等的區域），但**回收階段是併發的**：併發標記、併發疏散（evacuation，把存活物件搬到新區域）、併發更新引用。G1 的疏散是在 STW 中做的，這正是它停頓時間隨存活物件量成長的原因。Shenandoah 把最耗時的那一步併發化了，代價與 ZGC 相同——讀屏障的吞吐損失。

**兩者都不能消除所有停頓**。初始標記與最終標記仍然是 STW，而且如果分配速率超過回收速率，仍然會發生退化——ZGC 會出現配置停頓，Shenandoah 會退回到 STW 的完整回收。低停頓收集器的保證是「正常情況下停頓極短」，不是「永遠不會有長停頓」，這個區別在設定服務品質目標時很重要。

**選擇的實務建議**：先確認 JDK 發行版支援哪一個（有些建置只帶其中之一），再看堆積大小與延遲目標。兩者之間的差異，通常遠小於「從 G1 換到任一個」的差異——所以不必在它們之間糾結太久，把力氣放在量測與驗證上更有價值。

## 面試回答方式

先指出**目標相同、差別在機制**，然後給兩種機制的對照：Shenandoah 早期用 **Brooks 轉發指標**（每個物件多一個指標欄位，移動後指向新位址，所有存取先經過間接跳轉），ZGC 用**著色指標**（資訊放在指標高位，不必每個物件多欄位）。給出轉發指標的兩個代價（每物件多 8 位元組、每次存取多一次跳轉），並說明 Shenandoah 後來改用基於引用的讀屏障降低常態開銷。**最有解釋力的一句**是：併發移動的解法只有兩類——讓舊引用能找到新位址，或在讀取時修正引用，所有低停頓收集器都在這兩條路上。加分點是誠實指出**兩者都不能消除所有停頓**，分配速率超過回收速率時仍會退化，所以保證是「正常情況下極短」而非「永遠不長」。

## 講稿

兩者的目標一致，都是讓停頓時間跟堆積大小無關。差別在用什麼機制，讓使用者執行緒在物件移動期間還能正確存取物件。

Shenandoah 早期用轉發指標。每個物件多一個指標欄位，正常情況指向自己，被移動之後就指向新位址。所有存取都先經過這個間接跳轉，所以就算物件已經搬走，舊引用還是找得到它。

ZGC 則是把中繼資訊放進指標的閒置高位，不需要每個物件多一個欄位。

轉發指標的代價是每個物件多八位元組。Java 的物件普遍很小，所以這可能是百分之十到二十的額外記憶體。加上每次存取多一次跳轉。所以 Shenandoah 後來改用了基於引用的讀屏障，大幅降低常態開銷。

我覺得最有解釋力的一句是這樣。併發移動物件的解法只有兩類，要嘛讓舊引用能找到新位址，要嘛在每次讀取的時候修正引用。所有低停頓收集器都在這兩條路上。

還有一點要誠實說。兩者都不能消除所有停頓。如果分配速率超過回收速率，仍然會退化。它們的保證是正常情況下停頓極短，不是永遠不會有長停頓。

## 常見追問

### 為什麼 G1 的停頓會隨存活物件量成長？

**核心答案**：因為 G1 的疏散（把存活物件複製到新區域）是在 STW 中做的。一次年輕代回收要複製所有存活的年輕物件，複製的成本與**存活量**成正比。所以物件存活率高（例如快取類應用、或年輕代設得太小導致物件來不及死亡）時，停頓就會拉長。這也解釋了為什麼 G1 的停頓目標是「盡力而為」而非保證——它靠選擇回收哪些區域來控制工作量，但如果所有區域的存活率都高，就無法把工作量壓到目標之內。

**詳細解析**：G1 的 `-XX:MaxGCPauseMillis` 是給收集器的**提示**：它會根據歷史資料預測「回收 N 個區域需要多久」，然後選擇能在目標內完成的區域數量。設得太小的副作用是每次回收的區域太少，導致回收頻率上升、總吞吐下降，而且可能跟不上分配速率最終觸發完整回收——那是一次真正的長停頓。所以調 `MaxGCPauseMillis` 不是「設得越小越好」，而是要與實際的分配速率一起看。實務上的做法是先觀察 GC 日誌中的「預測 vs 實際」偏差與回收頻率，再逐步調整。

**面試回答方式**：核心是「疏散在 STW 中進行，複製成本與存活量成正比」，並推出 G1 的停頓目標是盡力而為而非保證。加分點是說明 `MaxGCPauseMillis` 的機制（依歷史預測選擇區域數量）與**設太小的副作用**：回收頻率上升、吞吐下降、可能跟不上分配速率而觸發完整回收這個真正的長停頓。收在建議：要與分配速率一起看，先觀察日誌中的預測偏差與回收頻率。

### 低停頓收集器什麼時候會退化？

**核心答案**：當分配速率持續超過併發回收的速率時。併發回收與使用者執行緒同時進行，如果應用產生垃圾的速度比 GC 清理的速度快，堆積會逐漸填滿——此時 ZGC 會讓分配執行緒**停下來等待**（allocation stall），Shenandoah 會退回**STW 的完整回收**。兩者都表現為「原本次毫秒的停頓突然變成數百毫秒甚至數秒」。

**詳細解析**：常見的觸發原因有三個：**堆積設得太小**（GC 沒有足夠的空間週轉，需要更頻繁地回收）、**分配速率突然暴增**（流量尖峰、或某段程式碼在迴圈裡建立大量物件）、**GC 的 CPU 資源不足**（併發回收要佔用 CPU，在 CPU 已經滿載的機器上 GC 執行緒搶不到時間片）。最後一項在容器裡特別容易發生——CPU 限制設得緊時，GC 與業務執行緒競爭同一份配額。**預防的方式是留出餘裕**：堆積不要設到剛好夠用、CPU 限制要考慮 GC 的開銷、並監控「併發回收週期的耗時」與「分配速率」這兩個指標的比例。

**面試回答方式**：先給退化條件（分配速率持續超過併發回收速率）與兩種收集器各自的表現（配置停頓 vs 退回 STW 完整回收）。給三個觸發原因，並特別點出在容器裡 CPU 限制太緊會讓 GC 執行緒搶不到時間片這個容易忽略的情況。收在預防：堆積與 CPU 都要留餘裕，並監控「併發回收週期耗時」與「分配速率」的比例。

### 如果不能換收集器，還能怎麼降低停頓？

**核心答案**：從**減少 GC 的工作量**下手，這往往比換收集器更有效。**減少配置**——重用物件（緩衝、`StringBuilder`）、避免在熱路徑上裝箱、用基本型別集合取代包裝型別集合。**減少存活量**——縮短物件的生命週期，讓它們在年輕代就死亡；檢查是否有不必要的長期持有（快取沒有上限、集合只增不減）。**減少跨代引用**——長期存活的物件持有大量短命物件的引用會增加寫屏障與記憶集的負擔。

**詳細解析**：「分配速率」是最值得先看的指標——它可以從 GC 日誌算出來（每次年輕代回收之間釋放的空間除以間隔時間）。降低分配速率的收益是全面的：GC 頻率下降、每次回收的工作量下降、CPU 開銷下降。而且它通常是應用層的改動，效果比調 JVM 參數確定得多。實務上最常見的高分配來源是：日誌的字串拼接（尤其是被級別過濾掉卻仍然拼接的）、序列化與反序列化、以及在迴圈裡建立集合或串流。先用配置剖析（async-profiler 的 alloc 模式）找出前幾大的分配點，通常改幾處就有明顯效果。

**面試回答方式**：把重點放在減少 GC 的工作量比換收集器更有效，並給三個方向（減少配置、減少存活量、減少跨代引用）。特別指出 「分配速率」是最值得先看的指標，可以從 GC 日誌算出，而降低它的收益是全面的且屬於應用層改動、效果比調參確定。加分點是列舉最常見的高分配來源（被過濾掉卻仍拼接的日誌、序列化、迴圈裡建集合）與工具（async-profiler 的 alloc 模式）。
