# 題目

APM 工具（SkyWalking、Arthas）是怎麼在不改程式碼的情況下加入監控的？

## 核心答案

靠 **Java Agent 加位元組碼增強**。JVM 提供 `java.lang.instrument` API，讓一個 agent 在類別被載入時**攔截它的位元組碼並修改**——在方法的入口與出口插入計時、記錄、追蹤上下文的程式碼，然後把修改後的位元組碼交給 JVM 載入。應用完全不知道自己被改過。

Agent 有兩種掛載方式。**啟動時掛載**（`-javaagent:xxx.jar`）——agent 的 `premain` 方法在主程式之前執行，可以註冊 `ClassFileTransformer` 攔截**所有後續載入的類別**。**執行期掛載**（Attach API）——用 `VirtualMachine.attach(pid)` 動態附加到一個正在執行的 JVM，呼叫 agent 的 `agentmain`，這是 Arthas 這類診斷工具的做法。

執行期掛載的限制是「已載入的類別要重定義」：JVM 支援 `retransformClasses` 重新轉換已載入的類別，但**不能改變類別的結構**（不能加欄位、加方法、改繼承關係），只能改方法體。這是 HotSwap 的根本限制，也是為什麼熱部署工具（JRebel）需要更深的技巧。

實際修改位元組碼一般用 **ASM**（最底層、最快）、**Byte Buddy**（API 友善，主流選擇）或 **Javassist**（可以用類似 Java 原始碼的語法）。

## 詳細解析

**「無侵入」是一個相對的說法**。Agent 確實不需要改應用程式碼，但它有真實的成本：**啟動變慢**（每個類別載入都要經過轉換）、**執行期開銷**（插入的程式碼本身要執行，通常 3% 到 10%）、**除錯變複雜**（堆疊追蹤裡出現不存在於原始碼的方法、行號可能對不上）。而且多個 agent 同時存在時可能互相衝突（兩個 agent 都想改同一個方法）。在效能問題排查時，要記得 agent 本身也是變因。

**Attach API 的安全考量**：能附加到一個 JVM 就等於能在裡面執行任意程式碼。所以它要求**同一個使用者身分**，而且 JDK 9 之後預設**禁止自我附加**（一個 JVM 附加到自己），要用 `-Djdk.attach.allowAttachSelf=true` 開啟。在生產環境，能夠 attach 是一個需要控制的權限——Arthas 這類工具好用，但它也能修改執行中的程式碼與讀取任何記憶體。

類別重定義的限制解釋了熱部署的難度。改一個方法的實作可以熱替換；加一個欄位、改一個方法簽章、加一個介面都不行——因為那會改變物件的記憶體佈局與虛擬方法表，而已經存在的實例無法遷移。JVM 選擇不支援這件事，是因為要正確處理「舊實例與新類別共存」在語意上幾乎不可能。 JRebel 的做法是在編譯時就為每個類別預留擴充的間接層，用空間與效能換取熱替換能力。

**Agent 的實務用途遠不只 APM**：程式碼覆蓋率工具（JaCoCo 用它插入探針）、Mock 框架（Mockito 的 inline mock maker 用它改寫 final 方法）、以及各種安全防護（RASP，在危險操作的入口插入檢查）。理解這個機制，能解釋很多「這怎麼做到的」的疑問。

## 面試回答方式

先給機制——Java Agent 在類別載入時攔截並修改位元組碼，在方法入口出口插入程式碼，應用不知情。給兩種掛載方式（`premain` 啟動時、`agentmain` 執行期 Attach）並指出後者是 Arthas 的做法。接著給**執行期掛載的核心限制**：`retransformClasses` **不能改變類別結構**（不能加欄位、加方法、改繼承），只能改方法體——這是 HotSwap 的根本限制。加分點有三個：**「無侵入」是相對的**，agent 有啟動變慢、3% 到 10% 執行開銷、堆疊追蹤變複雜的成本，排查效能問題時 agent 本身也是變因；**Attach 是一個需要控制的權限**，能附加就等於能執行任意程式碼；以及類別重定義的限制解釋了熱部署的難度——改結構會改變記憶體佈局與虛擬方法表，舊實例無法遷移。

## 講稿

靠 Java Agent 加位元組碼增強。JVM 提供一組介面，讓 agent 在類別被載入的時候攔截它的位元組碼並修改，在方法的入口跟出口插入計時、記錄、追蹤上下文的程式碼，然後把改過的位元組碼交給 JVM 載入。應用完全不知道自己被改過。

掛載有兩種方式。啟動時用參數指定，agent 的方法在主程式之前執行。或是執行期動態附加到一個正在跑的 JVM，這是診斷工具的做法。

執行期掛載有一個核心限制。已載入的類別可以重新轉換，但不能改變類別的結構，不能加欄位、加方法、改繼承關係，只能改方法體。這是熱替換的根本限制。

原因是改結構會改變物件的記憶體佈局跟虛擬方法表，而已經存在的實例無法遷移。JVM 選擇不支援，是因為要正確處理舊實例跟新類別共存，在語意上幾乎不可能。

還有一點我想強調，無侵入是相對的說法。Agent 有真實成本，啟動變慢、執行期開銷通常百分之三到十、堆疊追蹤裡會出現原始碼裡沒有的方法。所以排查效能問題的時候，要記得 agent 本身也是變因。

## 常見追問

### ClassFileTransformer 的實作要注意什麼？

**核心答案**：三點。第一，不要對所有類別都做轉換——每個類別載入都要走一次轉換邏輯，對 JDK 內部類別（`java/*`、`sun/*`）與無關的套件應該直接跳過，否則啟動時間會明顯拉長。**第二，轉換失敗要優雅降級**——拋出例外會讓類別載入失敗，整個應用起不來；正確的做法是捕捉例外、記錄、然後回傳 null 表示「不修改」。第三，注意類別載入器的可見性——agent 插入的程式碼如果引用了 agent 自己的類別，那些類別必須對目標類別的載入器可見（通常要放進 bootstrap classpath）。

**詳細解析**：**第三點是最容易踩的坑**。Agent 的 JAR 由 system class loader 載入，而被增強的類別可能由 Tomcat 或 Spring Boot 的自訂載入器載入——子載入器看得到父載入器的類別，反過來不行。所以 agent 要插入的輔助類別（例如追蹤上下文的持有者）必須用 `Instrumentation.appendToBootstrapClassLoaderSearch` 放到最上層，才能被所有載入器看到。這正好是雙親委派模型的一個實際應用場景——理解載入器的層級關係，才能寫出能在各種容器裡運作的 agent。

**面試回答方式**：給三點注意事項並各配後果。重點展開第三點——agent 的 JAR 由 system class loader 載入，被增強的類別可能由自訂載入器載入，而子看得到父、父看不到子，所以輔助類別要放進 bootstrap classpath。指出這正好是雙親委派模型的實際應用場景，理解載入器層級才能寫出跨容器可用的 agent。

### Arthas 這類工具能做到什麼，靠的是什麼機制？

**核心答案**：它結合了三種機制。**Attach API** 動態附加到目標 JVM。**Instrumentation 的重定義**——`watch`、`trace`、`stack` 這些命令是即時把目標方法的位元組碼改寫成「插入了記錄邏輯的版本」，用完再改回來。**JVMTI 與 MXBean** 取得執行緒轉儲、記憶體資訊、類別載入資訊。所以它能做到「不重啟、不改程式碼、即時觀察任意方法的入參與回傳值」。

**詳細解析**：這個能力的代價與風險都要知道。**代價是被觀察的方法會變慢**（插入的邏輯要執行、而且重定義會讓該方法的 JIT 編譯結果失效，退回解譯再重新編譯）——所以不該對超熱的方法長時間開啟 trace。**風險是它能執行任意程式碼**：`ognl` 命令可以呼叫任意方法、讀取任意物件，等同於在生產環境有一個 shell。所以在生產環境使用它應該有審計與權限控制，而不是讓任何人都能 attach。能主動提到「它的風險與代價」，比只列舉它的功能更能顯示工程判斷。

**面試回答方式**：給三種機制與它們各自提供的能力。真正的加分點是主動講代價與風險：**被觀察的方法會變慢**（插入邏輯加上 JIT 結果失效退回解譯），所以不該對超熱方法長時間 trace；以及**它能執行任意程式碼**，等同於生產環境有一個 shell，應該有審計與權限控制。

### 位元組碼增強與 AOP 代理有什麼區別？

**核心答案**：**攔截的層次不同**。Spring AOP 用**動態代理**——建立一個代理物件包裝目標物件，只能攔截**透過代理呼叫的方法**（所以「同類別內部的方法呼叫不會被攔截」是它的經典限制），而且只能攔截 public 的介面方法或可被覆寫的方法。位元組碼增強直接改寫目標類別本身——攔截範圍不受限制，private 方法、靜態方法、建構子、內部呼叫都能攔截。

**詳細解析**：代價是複雜度與風險。動態代理是標準的、可預測的、在原始碼層面可理解的；位元組碼增強則是**在編譯結果上動手術**，出問題時難以推理。所以兩者的定位不同：應用層的橫切關注點（交易、快取、權限）用 AOP 代理就夠了，而且它與框架的生命週期整合得更好；基礎設施層的觀測（APM、覆蓋率、安全防護）才需要位元組碼增強，因為它們必須覆蓋所有程式碼包括第三方函式庫。**AspectJ 的編譯期織入（compile-time weaving）是中間路線**——在編譯階段就改寫位元組碼，兼具無限制的攔截範圍與「結果是確定的、可以反編譯檢查」的可預測性，代價是需要特殊的編譯流程。

**面試回答方式**：核心是**攔截層次不同**——代理只能攔截透過代理的呼叫（內部呼叫不被攔截是經典限制），位元組碼增強直接改寫類別本身、範圍不受限。給出定位差異：應用層橫切關注點用 AOP 代理、基礎設施層觀測用位元組碼增強，理由是後者必須覆蓋第三方函式庫。加分點是提出 **AspectJ 的編譯期織入是中間路線**——兼具無限制範圍與可預測性，代價是特殊的編譯流程。
