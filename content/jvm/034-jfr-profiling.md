# 題目

JFR 是什麼？它與傳統的剖析器差在哪，為什麼能在生產環境常駐？

## 核心答案

JFR（Java Flight Recorder）是**內建在 JVM 裡的事件記錄框架**。它不是外掛的剖析器，而是 JVM 各個子系統（GC、JIT、類別載入、執行緒、鎖、IO、例外）在關鍵位置**主動發出事件**，JFR 把這些事件寫入一個環形緩衝，需要時再匯出成檔案。

它能常駐生產的原因有三個。**開銷極低**——預設設定的開銷通常在 1% 以下，因為事件是 JVM 內部本來就知道的資訊，只是多寫幾個位元組到緩衝。**沒有安全點偏差**——傳統的取樣剖析器用 `jstack` 或 JVMTI 取樣，只能在安全點取到堆疊，導致熱點被歸因到錯誤的位置（safepoint bias）；JFR 的方法剖析用的是不需要安全點的機制。**環形緩衝設計**——固定大小的緩衝持續覆寫，隨時可以「把最近 N 分鐘的記錄匯出」，適合「問題發生後才想看」的場景。

它涵蓋的範圍比純 CPU 剖析器廣得多——**GC 的每個階段、每次物件配置的取樣、鎖爭用、IO 等待、例外拋出頻率、以及執行緒狀態的時間分布**，全部在同一份記錄裡帶著時間軸。

## 詳細解析

**「安全點偏差」值得展開，因為它讓很多剖析結論是錯的**。JVM 只在安全點（方法返回、迴圈回邊等）才能可靠地走訪堆疊，所以基於安全點的取樣**只會取到安全點附近的位置**。一段沒有安全點的熱迴圈（JIT 常常省略計數迴圈內的安全點檢查）**完全不會出現在剖析結果裡**，熱點被歸給了下一個安全點所在的方法。**這解釋了為什麼有時候剖析結果與直覺嚴重不符。** JFR 與 async-profiler 都用了不依賴安全點的取樣機制（前者用 JVM 內部介面、後者用 `AsyncGetCallTrace` 加訊號），結果可信得多。

**JFR 與 async-profiler 的分工**：JFR 的強項是**廣度與時間軸**——它把 GC、鎖、IO、配置放在同一條時間線上，適合回答「這個時間點發生了什麼」。async-profiler 的強項是**深度與火焰圖**——它的 CPU、配置、鎖剖析更精細，wall-clock 模式能看到等待時間，火焰圖的視覺化更直接。**實務上兩者互補**：JFR 常駐收集，發現問題後用 async-profiler 深入。

**JFR 的兩個預設設定**：`default`（開銷約 1%，適合常駐）與 `profile`（開銷約 2% 到 5%，取樣更密、事件更多，適合排查期間短時間開啟）。**啟動時用 `-XX:StartFlightRecording=settings=default,disk=true,maxsize=200M,dumponexit=true`**，或用 `jcmd JFR.start` 在執行期開啟——**JFR 可以執行期開啟是它相對於 NMT 的重要優勢**。

**它的限制**：JFR 的事件是**JVM 層級的**，看不到原生函式庫內部發生的事；配置剖析是取樣的，小量但頻繁的配置可能被低估；而且**分析工具（JDK Mission Control）的學習曲線不低**，事件種類繁多，不熟悉的人容易在資料裡迷路。**這是它普及度不如簡單工具的實際原因。**

## 面試回答方式

先定位它**不是外掛的剖析器，而是 JVM 內建的事件記錄框架**——各子系統主動發事件，寫入環形緩衝。給出能常駐生產的三個理由（開銷 1% 以下、**沒有安全點偏差**、環形緩衝隨時可匯出最近 N 分鐘）。**安全點偏差要展開**：基於安全點的取樣只取得到安全點附近的位置，沒有安全點的熱迴圈完全不出現在結果裡，**這解釋了為什麼有些剖析結果與直覺嚴重不符**。接著給 **JFR 與 async-profiler 的分工**——前者是廣度與時間軸、後者是深度與火焰圖，實務上互補。加分點是 **JFR 可以執行期開啟**（相對於 NMT 必須啟動時開啟的重要優勢），以及誠實給出限制：看不到原生層、配置剖析是取樣的、分析工具學習曲線陡。

## 講稿

JFR 不是外掛的剖析器，它是內建在 JVM 裡的事件記錄框架。各個子系統在關鍵位置主動發出事件，寫進一個環形緩衝，需要的時候再匯出。

它能常駐生產有三個原因。開銷極低，通常在百分之一以下，因為事件是 JVM 本來就知道的資訊，只是多寫幾個位元組。環形緩衝設計，隨時可以匯出最近幾分鐘的記錄，適合問題發生後才想看的場景。還有一個我覺得最重要的，沒有安全點偏差。

這一點值得展開。JVM 只在安全點才能可靠走訪堆疊，所以基於安全點的取樣只取得到安全點附近的位置。一段沒有安全點的熱迴圈完全不會出現在剖析結果裡，熱點被歸給了下一個安全點所在的方法。這解釋了為什麼有時候剖析結果跟直覺嚴重不符。

實務上我會把 JFR 跟非同步剖析器搭配。JFR 的強項是廣度跟時間軸，把 GC、鎖、IO、配置放在同一條時間線上，適合回答這個時間點發生了什麼。非同步剖析器的強項是深度跟火焰圖。常駐用 JFR，發現問題後用剖析器深入。

## 常見追問

### JFR 的哪些事件最值得看？

**核心答案**：五類。**GC 事件**——每次回收的類型、耗時、回收前後的用量，以及分配速率。**執行緒狀態的時間分布**——每個執行緒花多少時間在執行、等待、阻塞，這直接指出瓶頸的性質。**鎖爭用（Java Monitor Blocked）**——誰在等哪把鎖等了多久。**TLAB 與配置事件**——找出配置最多的呼叫點，這是降低 GC 壓力的直接依據。**例外拋出頻率**——大量拋出的例外（尤其是被吞掉的）是隱藏的效能問題與邏輯問題。

**詳細解析**：**「例外拋出頻率」是最被低估的一項**。用例外做流程控制的程式碼在功能上正確，但每次拋出都要填充堆疊追蹤（成本可觀），高頻路徑上可能佔用可觀的 CPU。JFR 會統計每個例外型別的拋出次數與位置，**常常能找到「每秒拋出幾千次卻沒有人知道」的情況**。另外**執行緒狀態的時間分布是判斷「該加執行緒還是該優化程式碼」的直接依據**——大量時間在等待就是加執行緒或修下游，大量時間在執行就是優化程式碼。**這比看 CPU 使用率精確得多，因為它按執行緒分解了時間去向。**

**面試回答方式**：給五類事件並各配一句用途。重點展開兩項：**例外拋出頻率是最被低估的**（填充堆疊成本可觀，常能找到每秒幾千次卻沒人知道的情況）；以及**執行緒狀態的時間分布是判斷「加執行緒還是優化程式碼」的直接依據**，比看 CPU 使用率精確，因為它按執行緒分解了時間去向。

### 火焰圖該怎麼讀？

**核心答案**：橫軸是**樣本數的比例**（不是時間順序），縱軸是**呼叫堆疊的深度**。每個方框的寬度代表「這個方法出現在多少比例的樣本裡」——**寬的方框就是熱點**。讀的方法是**由下往上找出寬的分支**，然後看它上方的子方框判斷時間花在哪個子呼叫上。**平頂的方框（上面沒有子方框）代表時間真的花在這個方法自己身上**，那是最直接的優化目標。

**詳細解析**：兩個常見的誤讀。**第一，橫軸不是時間**——左右相鄰的方框沒有先後關係，只是按字母排序，所以看不出「先做這個再做那個」。**第二，寬度大不代表有問題**——一個佔 60% 樣本的方法如果是應用的核心邏輯，那很正常；要看的是「這個寬度符不符合預期」。另外**差分火焰圖（differential flame graph）** 在比較兩個版本或兩個時段時特別有用：它用顏色標示哪些方法變寬了、哪些變窄了，**直接回答「這次改動讓什麼變慢了」**，比並排看兩張圖有效得多。

**面試回答方式**：給出兩個軸的含義與讀法（由下往上找寬分支、平頂方框是最直接的優化目標）。加分點是兩個常見誤讀：**橫軸不是時間**（左右相鄰沒有先後關係）、**寬度大不代表有問題**（要看符不符合預期）。收在**差分火焰圖**——比較兩個版本時用顏色標示變寬變窄，直接回答「這次改動讓什麼變慢了」。

### 生產環境剖析要注意什麼？

**核心答案**：三點。**開銷要先驗證**——在壓測環境確認剖析開啟後的吞吐與延遲變化，不要直接在生產開啟未知開銷的工具。**避免影響正常流量**——剖析單一實例而非全部，並把該實例的流量權重調低（或選在低流量時段）。**資料要能帶得走**——記錄檔案要能自動上傳或匯出，不要留在可能隨時被重建的容器裡。

**詳細解析**：還有一個容易忽略的問題：**剖析結果的代表性**。單一實例的剖析可能不代表整體——如果負載平衡不均、或不同實例處理不同類型的請求（例如某些實例被分到大量的批次請求），剖析到的熱點可能是那個實例特有的。**做法是在多個實例上分別剖析並比對**，一致的熱點才可信。另外**剖析的時間窗口要涵蓋完整的行為週期**——如果應用有每分鐘的定時任務或每小時的批次作業，只剖析三十秒可能完全錯過它們。**「取樣的代表性」是所有基於取樣的診斷的共同弱點**，多次、多實例、跨時段的取樣是唯一的補救。

**面試回答方式**：給三點實務注意（先驗證開銷、只剖析單一低流量實例、資料要能帶走）。真正的加分點是提出**代表性問題**：單一實例可能不代表整體（負載不均、請求類型不同），要在多個實例剖析並比對；時間窗口要涵蓋完整行為週期（定時任務、批次作業）。收在通用弱點：**取樣的代表性是所有取樣式診斷的共同弱點，多次多實例跨時段是唯一補救**。
