# 題目

GC 日誌該開哪些選項？拿到一份日誌，你會先看什麼？

## 核心答案

JDK 9 之後用**統一日誌框架**：`-Xlog:gc*:file=gc.log:time,uptime,level,tags:filecount=5,filesize=20M`——`gc*` 開啟所有 GC 相關標籤、`time` 讓每行帶絕對時間戳（**與應用日誌對照時必要**）、輪替設定避免檔案無限成長。**生產環境應該預設開啟**，它的開銷極低（不到 1%），而沒有它就無法回答任何 GC 相關的問題。

拿到日誌先看四件事，順序有意義。**第一，停頓時間的分布**——最大值、P99、以及是否有異常長的單次停頓。**第二，回收頻率**——年輕代回收的間隔，太密集代表年輕代太小或分配速率太高。**第三，分配速率**——用「每次回收前後的年輕代用量差」除以「兩次回收的間隔」算出，這是最有診斷價值的衍生指標。**第四，晉升速率與老年代成長趨勢**——老年代如果持續成長且完整回收後也降不下來，那是記憶體洩漏的訊號。

**單看一次停頓沒有意義，要看趨勢與分布**。

## 詳細解析

**分配速率為什麼最有價值**：它直接連結到「應用做了什麼」與「GC 要做多少工作」。分配速率高會同時導致回收頻率上升、晉升增加、以及併發收集器跟不上——**一個指標解釋了多個症狀**。而且它是應用層可以改善的（減少物件建立），改善的效果確定且全面。相比之下，調 GC 參數只是在既定的工作量下重新分配成本。

**「Full GC」的出現要區分成因**。`System.gc()` 呼叫（日誌會標明）、Metaspace 不足、老年代不足、以及併發模式失敗——四者的處理方式完全不同。**尤其是 `System.gc()`，它常常來自第三方函式庫**（某些 NIO 的直接記憶體管理、RMI 的分散式 GC 會定期呼叫），可以用 `-XX:+DisableExplicitGC` 停用，但要先確認沒有元件真的依賴它（直接記憶體的釋放可能需要）。

**要注意「時間」有三個**：`user`（所有 GC 執行緒的 CPU 時間總和）、`sys`（核心時間）、`real`（實際經過的牆鐘時間）。**`real` 遠大於 `user/執行緒數` 是一個重要訊號**——代表 GC 執行緒沒有拿到足夠的 CPU（機器過載、或容器 CPU 限制太緊），或者發生了作業系統層級的等待（記憶體交換、磁碟 IO）。**`sys` 異常高則常常指向記憶體問題**（大量的頁面錯誤、透明大頁的整理）。這組數字經常被略過，但它們能直接區分「GC 本身慢」與「環境讓 GC 慢」。

**與應用指標對照才能得到結論**。GC 日誌說「這次停頓 200 毫秒」，但那 200 毫秒有沒有影響使用者，要看應用的延遲指標。**常見的錯誤是花大量時間優化一個從未影響業務的 GC 行為**——先確認 GC 停頓確實出現在請求延遲的尾部，再投入優化。

## 面試回答方式

先給**具體的開啟參數**並強調 `time`（與應用日誌對照必要）與輪替設定，並指出**生產環境應該預設開啟**因為開銷不到 1%。接著給**四件事的檢視順序**（停頓分布、回收頻率、分配速率、老年代趨勢），並特別說明**分配速率為什麼最有診斷價值**——一個指標解釋多個症狀，而且是應用層可改善的。加分點有三個：**Full GC 要區分四種成因**（顯式呼叫、Metaspace、老年代、併發模式失敗），其中顯式呼叫常來自第三方函式庫；**`user`／`sys`／`real` 三個時間的意義**，`real` 遠大於 `user` 除以執行緒數代表 GC 沒拿到足夠 CPU（容器限制太緊），`sys` 高指向記憶體問題；以及**必須與應用延遲指標對照**，否則可能在優化一個從未影響業務的行為。

## 講稿

JDK 9 之後用統一日誌框架，我會開啟所有 GC 標籤，帶絕對時間戳，再加上檔案輪替。時間戳很重要，因為要跟應用日誌對照。生產環境應該預設開啟，開銷不到百分之一，沒有它就無法回答任何 GC 相關的問題。

拿到日誌我先看四件事。第一是停頓時間的分布，最大值、P99、有沒有異常長的單次停頓。第二是回收頻率，太密集代表年輕代太小或分配速率太高。第三是分配速率，用每次回收前後的用量差除以間隔算出來。第四是老年代的成長趨勢，如果完整回收之後也降不下來，那是洩漏的訊號。

我認為分配速率最有診斷價值，因為它直接連結應用做了什麼跟 GC 要做多少工作。分配速率高會同時造成回收變頻繁、晉升增加、併發收集器跟不上，一個指標解釋多個症狀。而且它是應用層可以改善的。

還有一組常被略過的數字，就是使用者時間、系統時間、跟實際經過時間。實際時間遠大於使用者時間除以執行緒數，代表 GC 執行緒沒拿到足夠的 CPU，可能是容器限制太緊。這能直接區分是 GC 本身慢，還是環境讓 GC 慢。

## 常見追問

### 怎麼從 GC 日誌判斷有沒有記憶體洩漏？

**核心答案**：看**完整回收（或 G1 的混合回收）之後老年代的使用量**。正常的應用，這個數字應該在某個範圍內波動；**洩漏的特徵是它單調上升**——每次完整回收後的基線都比上一次高，最終逼近堆積上限並導致回收越來越頻繁、每次回收釋放的空間越來越少，最後 OOM。**關鍵是看「回收後」的值而不是「回收前」**，回收前的值只反映分配量。

**詳細解析**：這個模式在圖上非常明顯——把每次完整回收後的老年代用量畫成時間序列，洩漏是一條上升的直線或曲線。**要注意觀察窗口必須夠長**：有些洩漏很慢（每小時幾 MB），觀察十分鐘看不出來。另一個容易混淆的情況是**快取的正常成長**——一個有上限的快取在暖機期間也會讓老年代上升，但它會在達到上限後穩定下來。**區分方式是看它有沒有收斂**。確認洩漏之後，下一步是抓堆積轉儲並比對兩個時間點的差異（哪個類別的實例數持續增加），這比單看一份轉儲有效得多。

**面試回答方式**：給出關鍵判準——**看完整回收之後的老年代用量，單調上升就是洩漏**，並強調要看「回收後」而非「回收前」。加分點是兩個實務細節：**觀察窗口要夠長**（慢洩漏每小時幾 MB，十分鐘看不出來），以及**要與快取的正常暖機成長區分**（後者會收斂）。收在下一步：抓兩個時間點的堆積轉儲比對實例數增長，比單看一份有效得多。

### 停頓時間看起來正常，但服務的 P99 延遲很差，可能是什麼？

**核心答案**：GC 只是延遲的來源之一，而且**平均停頓正常不代表沒有 GC 問題**。要檢查三件事：**停頓的分布而非平均**（平均 20 毫秒但 P999 是 800 毫秒，那 800 毫秒就落在尾延遲上）、**停頓的頻率**（每次 20 毫秒但每秒發生五次，累計影響很大）、以及 **STW 之外的延遲**（併發階段搶佔 CPU、安全點的到達時間、以及 JIT 去最佳化）。

**詳細解析**：**安全點的到達時間常被忽略**。GC 停頓的日誌通常只記錄「停頓本身」，但在此之前 JVM 必須等所有執行緒到達安全點——**如果某個執行緒正在執行一個很長的計數迴圈（JIT 可能省略了迴圈內的安全點檢查），其他執行緒要一直等它**。這段時間可以用 `-Xlog:safepoint` 觀察，有時候比 GC 本身還長。另一個來源是**時間到安全點（time to safepoint）與 GC 無關的操作**——偏向鎖撤銷、去最佳化、以及 `jstack` 本身都要走安全點。**所以「GC 日誌看起來正常但延遲差」時，安全點日誌是下一個該看的地方。**

**面試回答方式**：先指出**平均正常不代表沒問題**，要看分布與頻率。真正的加分點是第三項——**STW 之外的延遲**，尤其是**安全點的到達時間**：某個執行緒卡在長計數迴圈時所有人都要等它，而 GC 日誌只記錄停頓本身不記錄等待。給出觀察手段 `-Xlog:safepoint`，並補上其他走安全點的操作（偏向鎖撤銷、去最佳化、`jstack`）。

### 生產環境開 GC 日誌需要注意什麼？

**核心答案**：三點。**輪替設定必須有**（`filecount` 與 `filesize`），否則日誌會無限成長最終填滿磁碟——**磁碟滿導致的服務中斷比 GC 問題更常見**。**寫入不能阻塞業務**——日誌寫在 GC 停頓期間，如果磁碟很慢（例如網路儲存），會直接延長停頓；應該寫在本機磁碟而非網路掛載。**保留期要夠長**——問題往往在事後才被調查，只保留一小時的日誌等於沒有。

**詳細解析**：還有一個容器環境特有的問題：**容器重啟後日誌就沒了**。如果 GC 日誌寫在容器的臨時檔案系統上，而問題正好導致 OOM 重啟，那份最關鍵的日誌就消失了。**解法是寫到掛載的持久磁碟，或者把日誌輸出到 stdout 讓日誌收集系統帶走**（統一日誌框架支援輸出到 stdout，但要注意它會與應用日誌混在一起）。**同樣的道理適用於堆積轉儲**——`-XX:+HeapDumpOnOutOfMemoryError` 加上 `-XX:HeapDumpPath` 指向持久儲存，否則 OOM 時產生的轉儲會隨容器一起消失，而那正是最需要它的時候。

**面試回答方式**：給三點（輪替、不要寫網路儲存、保留期夠長），並指出**磁碟滿導致的中斷比 GC 問題更常見**。真正的加分點是容器特有的問題：**重啟後日誌消失，而 OOM 重啟正是最需要那份日誌的時候**。給出解法（持久磁碟或輸出到 stdout），並延伸到堆積轉儲——`HeapDumpPath` 也必須指向持久儲存。
