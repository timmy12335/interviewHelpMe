# 題目

除了 GC，還有哪些原因會讓 Java 應用出現延遲毛刺？

## 核心答案

至少有六類，**而 GC 只是其中之一**。

**安全點的到達時間**——JVM 要做 STW 操作前必須等所有執行緒到達安全點；如果某個執行緒卡在沒有安全點檢查的長迴圈裡，**其他執行緒要一直等它**。這段時間不計入 GC 停頓，卻真實地影響延遲。

**GC 之外的 STW 操作**——偏向鎖撤銷、去最佳化、類別重定義、`jstack`、堆積轉儲，全都要走安全點。

**JIT 的編譯與去最佳化**——新的熱點被編譯、或樂觀假設被打破而退回解譯，都會造成局部的速度下降。

**作業系統層級**——CPU 排程延遲、CFS 節流（容器）、記憶體交換、透明大頁的整理、以及 NUMA 的跨節點存取。

**IO 與下游**——磁碟寫入的抖動（尤其是同步日誌）、網路重傳、下游服務的尾延遲。

**應用自身**——鎖爭用、快取失效後的批次重建、以及定時任務的干擾。

**排查的第一步是「先確認是不是 GC」**，用 GC 日誌的時間戳與延遲毛刺的時間比對；不是的話再依序排除其他類別。

## 詳細解析

**安全點問題值得展開，因為它最隱蔽**。JIT 為了效能，會在「可數迴圈」（counted loop，用 int 計數且邊界確定的迴圈）中**省略安全點檢查**——編譯器認為它會很快結束。但如果迴圈體很重（例如每次迭代做一次複雜計算），這個迴圈可能執行數百毫秒，**期間 JVM 無法進入任何 STW 操作**。症狀是「GC 日誌顯示停頓只有 5 毫秒，但應用的延遲毛刺是 300 毫秒」。用 `-Xlog:safepoint` 可以看到「time to safepoint」這個數字，它與停頓本身是分開統計的。**解法是把 int 計數改成 long**（long 迴圈不被視為可數迴圈，會保留安全點檢查），或者把大迴圈拆小。

**偏向鎖撤銷在 JDK 15 之前是一個真實的停頓來源**。當一個原本被單執行緒使用的物件開始被多執行緒存取時，JVM 要撤銷偏向——這需要 STW。在某些工作負載下（大量使用 `synchronized` 的集合、然後被多執行緒存取）撤銷會很頻繁。**JDK 15 之後偏向鎖預設關閉、JDK 18 移除，正是因為它的維護複雜度與這類停頓超過了它帶來的收益。**

**透明大頁（THP）的整理**是作業系統層級最常被忽略的一項。Linux 的 THP 在背景整理記憶體以組成大頁，這個整理可能造成應用執行緒的停頓（數十到數百毫秒）。**很多低延遲系統的部署指南會建議關閉 THP 或設成 `madvise` 模式**，這是一個成本極低但收益明顯的調整。

**排查方法的關鍵是「時間戳對齊」**。把 GC 日誌、安全點日誌、應用的延遲指標、以及系統指標放在同一條時間軸上比對——**毛刺與哪一類事件對得上，答案就出來了**。這也是為什麼所有日誌都應該帶絕對時間戳（而非相對的 uptime），否則無法對齊。

## 面試回答方式

先明確表態 **GC 只是六類原因之一**，並把六類列出來。接著展開最隱蔽的**安全點到達時間**：JIT 在可數迴圈中省略安全點檢查，重迴圈可能執行數百毫秒而 JVM 無法進入任何 STW——症狀是「GC 日誌顯示 5 毫秒但實際毛刺 300 毫秒」。給出觀察手段（`-Xlog:safepoint` 的 time to safepoint）與**具體解法：把 int 計數改成 long**。加分點有兩個：**偏向鎖撤銷是 JDK 15 之前的真實停頓來源**，這正是它被關閉與移除的原因；以及**透明大頁的整理**是作業系統層級最常被忽略的一項，低延遲系統通常建議關閉。收在排查方法：**所有日誌帶絕對時間戳、放在同一條時間軸上對齊比對**。

## 講稿

除了 GC 至少還有六類原因，而 GC 只是其中之一。

第一類是安全點的到達時間，這個最隱蔽。JVM 要做停止全世界的操作之前，必須等所有執行緒到達安全點。而 JIT 為了效能，會在可數迴圈中省略安全點檢查，因為編譯器認為它會很快結束。但如果迴圈體很重，這個迴圈可能執行數百毫秒，期間 JVM 無法進入任何停頓操作。

症狀就是 GC 日誌顯示停頓只有五毫秒，但應用的延遲毛刺是三百毫秒。用安全點日誌可以看到到達安全點的時間，它跟停頓本身是分開統計的。解法是把整數計數改成長整數，因為長整數迴圈不被視為可數迴圈，會保留安全點檢查。

其他幾類是，GC 之外的停止全世界操作、JIT 的編譯與去最佳化、作業系統層級的排程延遲跟容器節流、IO 與下游、還有應用自身的鎖爭用。

排查方法的關鍵是時間戳對齊。把 GC 日誌、安全點日誌、應用的延遲指標、系統指標放在同一條時間軸上比對，毛刺跟哪一類事件對得上，答案就出來了。所以所有日誌都應該帶絕對時間戳。

## 常見追問

### 什麼是安全點，為什麼需要它？

**核心答案**：安全點是**程式執行中「JVM 能夠可靠描述整個執行狀態」的位置**——在這些點上，所有物件引用的位置都是已知且準確的（哪些暫存器與堆疊槽存著引用），因此 GC 可以安全地走訪與移動物件。JIT 編譯的程式碼在任意指令處的狀態是不完整的（暫存器可能存著中間值），所以必須等到安全點。

**詳細解析**：安全點通常插在**方法返回前**與**非可數迴圈的回邊**——這兩個位置的密度足以保證執行緒能在合理時間內到達，又不至於因為檢查太頻繁而影響效能。**到達安全點的機制是「輪詢」**：編譯後的程式碼在安全點處讀取一個特定的記憶體頁，JVM 要求停頓時就把那個頁設成不可讀，於是讀取觸發訊號，執行緒進入停頓流程。**這個設計很巧妙——正常情況下的成本只是一次記憶體讀取，幾乎為零。** 另外還有**安全區域（safe region）** 的概念，處理「執行緒正在阻塞或執行原生方法」的情況：那些執行緒的狀態本來就穩定，JVM 不必等它們。

**面試回答方式**：給定義並強調關鍵——**在這些點上所有物件引用的位置是已知準確的**，而 JIT 程式碼在任意指令處狀態不完整。說明安全點插在哪裡（方法返回前、非可數迴圈的回邊）與為什麼是這個密度。加分點是描述**輪詢機制**：讀一個特定記憶體頁，要停頓時把它設成不可讀觸發訊號——**正常情況的成本只是一次記憶體讀取，幾乎為零**。補上安全區域處理阻塞與原生方法的執行緒。

### 為什麼偏向鎖被移除了？

**核心答案**：因為**它的收益前提已經不成立，而維護成本很高**。偏向鎖是為了優化「一個物件只被單一執行緒使用」的情況（省掉 CAS），這在早期大量使用同步集合（`Vector`、`Hashtable`、`StringBuffer`）的程式碼裡收益明顯。但現代程式碼普遍使用非同步的集合與 JUC 的工具，**這個模式越來越少見**；而偏向鎖的**撤銷需要 STW**、實作橫跨 JVM 多個子系統、且與新的併發功能（例如虛擬執行緒）互相干擾。

**詳細解析**：JEP 374 的說明很直白：偏向鎖讓 JVM 的同步子系統變得複雜，**阻礙了其他改進**（例如把物件頭變小、實作更輕量的鎖）。**這是一個好的技術決策案例：一個曾經正確的最佳化，在環境改變後成為負債，於是被移除。** 同樣的模式在 JDK 裡出現過多次——CMS 收集器被移除、`Applet` API 被移除、`finalize` 被廢棄。**能把「移除一個功能」理解成正常的演進而非退步，是一個成熟的技術觀點**；很多團隊在自己的系統裡累積了大量「曾經需要但現在只是負債」的程式碼，正是因為缺少這種判斷。

**面試回答方式**：給出兩個理由——**收益前提不成立**（現代程式碼少用同步集合）與**維護成本高**（撤銷需要 STW、橫跨多個子系統、干擾新功能）。引用 JEP 374 的核心論點：它阻礙了物件頭變小與更輕量鎖的實作。真正的加分點是把它提升成觀點：**一個曾經正確的最佳化在環境改變後成為負債而被移除，這是正常的演進**，並指出很多團隊的系統裡累積了大量「曾經需要但現在只是負債」的程式碼，正是因為缺少這種判斷。

### 怎麼系統地排查延遲毛刺？

**核心答案**：**由外而內，逐層排除**。**第一層，確認毛刺的形狀**——是週期性的（指向定時任務、GC、CFS 節流）還是隨機的（指向鎖爭用、下游）？影響所有請求還是特定端點？**第二層，排除環境**——CPU 節流指標、記憶體交換、鄰居干擾（共享主機）。**第三層，排除 JVM**——GC 日誌、安全點日誌、JIT 編譯事件。**第四層，才是應用**——鎖爭用、下游延遲、快取失效。

**詳細解析**：**「毛刺的形狀」這一步最有價值卻最常被跳過**。週期性的毛刺幾乎必然對應某個週期性的事件，把週期算出來（例如每 100 毫秒一次對應 CFS 週期、每 30 秒一次對應某個定時任務、每幾分鐘一次對應 GC）就已經縮小到少數幾個嫌疑。**這比一開始就抓剖析資料有效得多。** 另外要注意**尾延遲往往是多個小因素疊加的結果**——GC 停頓 10 毫秒、加上一次鎖等待 20 毫秒、加上下游的一次重試 50 毫秒，單獨看每一項都不嚴重。**所以「找到唯一的元兇」有時是不存在的目標，正確的做法是列出所有貢獻並依大小處理。**

**面試回答方式**：給四層由外而內的排除順序。重點強調**第一層「確認毛刺的形狀」最有價值卻最常被跳過**——週期性的毛刺把週期算出來就縮小到少數嫌疑（100 毫秒對應 CFS、幾分鐘對應 GC），這比一開始抓剖析資料有效得多。收在一個重要的認識：**尾延遲往往是多個小因素疊加**，「找到唯一元兇」有時是不存在的目標，正確做法是列出所有貢獻並依大小處理。
