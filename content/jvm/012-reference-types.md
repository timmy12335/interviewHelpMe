# 題目

Java 的四種引用（強引用、軟引用、弱引用、虛引用）有什麼區別？各自的應用場景是什麼？

## 核心答案

四種引用的回收強度從強到弱：**強引用**（普通的 `new`，只要引用存在物件絕不被回收，是 OOM 的常見來源）、**軟引用（SoftReference）**（記憶體充足時保留、記憶體不足即將 OOM 時才回收，適合做記憶體敏感的快取）、**弱引用（WeakReference）**（只要發生 GC 就被回收，不管記憶體是否充足，適合做規範化映射如 `WeakHashMap`、`ThreadLocalMap` 的 key）、**虛引用（PhantomReference）**（最弱，無法透過它取得物件，唯一作用是在物件被回收時收到一個通知，用於追蹤物件回收、做資源清理）。

## 詳細解析

**強引用（Strong Reference）**：

- 就是最普通的引用，如 `Object o = new Object()`。
- 只要強引用還存在（可從 GC Roots 到達），垃圾收集器就絕不會回收被引用的物件，寧可拋 OOM。
- 大部分記憶體洩漏都是「本該釋放的物件仍被某個強引用持有」導致的。

**軟引用（SoftReference）**：

- 用 `SoftReference<T>` 包裝。物件在「記憶體充足時保留、記憶體不足（即將發生 OOM）時被回收」。
- 典型場景：記憶體敏感的快取——快取的資料在記憶體充足時保留以加速存取，記憶體吃緊時自動被回收讓路，避免快取撐爆記憶體。

**弱引用（WeakReference）**：

- 用 `WeakReference<T>` 包裝。物件只要發生下一次 GC 就會被回收，不管記憶體是否充足。
- 典型場景：規範化映射——`WeakHashMap` 的 key 是弱引用，當 key 不再被外部強引用時，這個 entry 會自動被清除；`ThreadLocalMap` 的 key 也用弱引用（見 Java 併發 ThreadLocal 記憶體洩漏題）。

**虛引用（PhantomReference）**：

- 用 `PhantomReference<T>` 包裝，且必須配合一個引用佇列（ReferenceQueue）。
- 無法透過虛引用取得物件（`get()` 永遠返回 null），它唯一的作用是——當被引用的物件被回收時，這個虛引用會被加入引用佇列，程式可以據此得知「物件已被回收」並執行後續的清理動作（如釋放堆外記憶體）。
- 是 `finalize` 的更安全替代（`Cleaner` 底層就用虛引用實現）。

## 面試回答方式

用「回收強度從強到弱」這條主線串起四種引用最清晰——強（絕不回收）、軟（記憶體不足才回收）、弱（下次 GC 就回收）、虛（無法取得、僅通知回收）。每種引用一定要配一個典型應用場景（軟引用做快取、弱引用做 WeakHashMap/ThreadLocal key、虛引用做回收追蹤/資源清理），這是這題的加分關鍵——展現你知道這些引用「拿來做什麼」而不只是背它們的回收時機。能連結到 ThreadLocal 記憶體洩漏（弱引用 key）展現知識串聯。

## 常見追問

### 軟引用和弱引用在做快取時該怎麼選？

**核心答案**：軟引用更適合做「記憶體敏感的快取」——它在記憶體充足時盡量保留快取資料（提高命中率），只在記憶體不足時才被回收，能在「盡量快取」和「不撐爆記憶體」之間自動平衡。弱引用則太「弱」了，只要一次 GC 就被回收，做快取的話快取項存活時間太短、命中率很低，通常不用弱引用做主快取，而是用在「物件還在就順便用、被回收也無所謂」的規範化映射或臨時關聯場景。

**詳細解析**：兩者的關鍵區別在「回收的積極程度」。軟引用是「不到記憶體危急關頭不回收」，所以快取項能存活較久、命中率高，同時又保證了記憶體壓力大時能自動釋放，是「有彈性的快取」的理想選擇。弱引用是「見到 GC 就回收」，過於積極，若用它做快取，快取項可能剛放進去下一次 Minor GC 就沒了，快取形同虛設。所以弱引用的定位不是「快取」而是「不影響物件生命週期的附屬引用」——例如你想給某個物件關聯一些額外資訊，但不希望這個關聯阻止物件被回收（用 `WeakHashMap`，物件被回收時關聯資訊自動清除，避免記憶體洩漏）。實務中做快取常見的其實是用專門的快取庫（如 Caffeine、Guava Cache）配合大小限制和過期策略，而非直接用軟/弱引用，但理解兩者的區別能幫你判斷什麼時候用哪種引用。

**面試回答方式**：講出「軟引用適合記憶體敏感快取（記憶體足就留、不足才回收、命中率高）、弱引用太積極不適合做主快取（一次 GC 就沒、適合不影響生命週期的附屬關聯）」。能點出「實務快取常用專門的快取庫而非直接用軟/弱引用」，展現你既理解兩者區別又了解實務做法。

### 為什麼 ThreadLocalMap 的 key 用弱引用，這解決了什麼、又帶來了什麼問題？

**核心答案**：`ThreadLocalMap` 的 key（即 `ThreadLocal` 物件）用弱引用，解決的是「當 `ThreadLocal` 物件本身不再被外部強引用時，能讓它被 GC 回收」——避免 `ThreadLocal` 物件本身洩漏。但它帶來一個問題——key 被回收後變成 null，但對應的 value 仍是強引用不會被自動回收，如果執行緒長期存活（如執行緒池）且不呼叫 `remove()`，這些 key 為 null 的 value 會一直堆積造成記憶體洩漏。所以用弱引用 key 是「兩害相權取其輕」，並非完全解決洩漏，仍需開發者主動 `remove()`。

**詳細解析**：這題完整連結到 Java 併發的 [[../java-concurrency/008-threadlocal-memory-leak.md]]。核心邏輯是——如果 key 用強引用，那麼只要執行緒還活著，`ThreadLocalMap` 就一直強引用著 `ThreadLocal` 物件，即使程式其他地方早已不用這個 `ThreadLocal` 了，它也無法被回收，洩漏更嚴重。用弱引用 key 至少保證「`ThreadLocal` 物件本身能被回收」（當外部不再強引用它時）。但這只解決了 key 的洩漏，value 因為是強引用仍然會殘留，這就是為什麼強烈建議「用完 ThreadLocal 一定要 remove」。理解這個設計，能看到弱引用在實際框架中如何被用來「盡量減少洩漏」，也理解它的局限——弱引用不是萬能藥，它只能讓「弱引用指向的東西」被回收，管不了那個東西關聯的其他強引用資料。

**面試回答方式**：講出「弱引用 key 讓 ThreadLocal 物件本身能被回收（避免它洩漏），但 value 是強引用仍會殘留，是兩害相權取其輕，仍需 remove」。能連結到 ThreadLocal 記憶體洩漏的完整分析，展現你把 JVM 的引用機制和併發的實務問題打通理解。

### 虛引用和 finalize 都能在物件回收時做清理，虛引用好在哪？

**核心答案**：虛引用（配合引用佇列）比 `finalize` 更安全可控——`finalize` 的執行時機完全不確定、可能導致物件「復活」、執行緒優先級低可能長時間不執行、且例外會被吞掉；虛引用則是「物件確定被回收後」才把虛引用放入佇列通知你（不會讓物件復活）、你可以用專門的執行緒主動輪詢佇列來及時處理清理、行為更可預測。JDK 9 的 `Cleaner` 機制就是基於虛引用實現，作為 `finalize` 的官方替代。

**詳細解析**：`finalize` 的根本問題是它把清理邏輯「掛在物件的臨終方法上」，由 JVM 的 Finalizer 執行緒在不確定的時機呼叫，這帶來一系列不可控（見 Java 核心 [[../java/019-final-finally-finalize.md]]）。虛引用的模型完全不同——它不在物件上定義清理方法，而是「當物件被回收後，系統把對應的虛引用塞進你指定的引用佇列」，你用自己的執行緒去 `poll` 這個佇列，取到虛引用就知道「對應的物件已被回收」，然後執行你要的清理（例如釋放這個物件關聯的堆外記憶體 DirectByteBuffer、關閉某些系統資源）。這個模型的優勢是——清理邏輯由你自己的程式碼主動控制（不依賴 JVM 何時呼叫 finalize）、物件無法在清理過程中復活（虛引用 get 永遠是 null，你根本碰不到物件）、且不會像 finalize 那樣拖慢 GC。這正是 `Cleaner` 的實現方式，也是管理堆外記憶體（如 NIO 的 DirectBuffer）的標準做法。

**面試回答方式**：對比 finalize 的問題（時機不定、可能復活、拖慢 GC、吞例外）和虛引用的優勢（物件確定回收後才通知、無法復活、自己主動處理佇列、可控）。能點出「Cleaner 基於虛引用、是管理堆外記憶體的標準做法」，展現你理解虛引用的實際價值和它與 finalize 的本質區別。
