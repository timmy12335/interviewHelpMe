# 題目

什麼情況會發生 `StackOverflowError`？它和 `OutOfMemoryError` 有什麼區別？

## 核心答案

`StackOverflowError` 發生在「執行緒請求的棧深度超過了虛擬機器棧允許的最大深度」時——最常見的原因是無限遞迴（或遞迴層數過深），每次方法呼叫都壓入一個棧幀，遞迴不終止就會不斷壓棧直到超過棧容量。它和 `OutOfMemoryError` 的區別是——`StackOverflowError` 是「單個執行緒的棧深度超限」（棧空間不足以再壓入新棧幀），而 OOM 通常是「堆記憶體不足以分配新物件」；一個是棧的問題、一個是堆（或其他區）的問題。

## 詳細解析

**虛擬機器棧與棧幀**：每個執行緒有自己的虛擬機器棧，每呼叫一個方法就壓入一個「棧幀」（存放這次方法呼叫的區域變數、運算元棧、返回位址等），方法返回時彈出棧幀。棧的大小由 `-Xss` 控制（預設幾百 KB 到 1MB）。

**StackOverflowError 的成因**：

- **無限遞迴**：最常見。遞迴沒有正確的終止條件，方法無限地呼叫自己，棧幀不斷壓入永不彈出，很快超過棧深度上限。
- **遞迴層數過深**：即使遞迴有終止條件，但如果層數非常深（如處理一個很深的樹或很長的鏈結串列用遞迴），也可能超過棧容量。
- **方法呼叫鏈過長 / 棧幀過大**：極端情況下方法呼叫層次太深、或單個棧幀因為區域變數太多而過大，也可能觸發。

**與 OutOfMemoryError 的區別**：

| | StackOverflowError | OutOfMemoryError |
|---|---|---|
| 區域 | 虛擬機器棧（執行緒私有） | 堆、元空間、直接記憶體等 |
| 成因 | 棧深度超限（多為遞迴） | 記憶體不足以分配（洩漏/容量/大物件） |
| 範圍 | 單個執行緒 | 通常是整個 JVM 的記憶體 |

**注意**：兩者都是 `Error`（不是 `Exception`），都代表嚴重問題，一般不應該用 try-catch 去「處理」它們（雖然技術上 StackOverflowError 可以被 catch），而是應該修復根因（如修正遞迴邏輯、調整演算法為迭代）。

## 面試回答方式

這是基礎題，核心是講清楚「StackOverflowError = 棧深度超限，最常見是無限遞迴」。用「每次方法呼叫壓入棧幀、遞迴不終止就不斷壓棧直到超限」這個機制解釋成因。與 OOM 的區別要抓住「棧 vs 堆」「單執行緒棧深度 vs 整個 JVM 記憶體」這兩個維度。能補充「兩者都是 Error、不該 try-catch 處理而該修根因」以及「遞迴太深可改成迭代」的實務建議，展現你不只知道現象還知道怎麼解決。

## 常見追問

### 遞迴導致 StackOverflowError 怎麼解決？

**核心答案**：最根本的解法是——把遞迴改寫成迭代（用迴圈 + 顯式的棧或佇列資料結構來模擬遞迴），因為迭代用的是堆上的資料結構（如 `ArrayDeque` 當棧）而不是佔用有限的虛擬機器棧，能處理深得多的層數。如果邏輯上必須遞迴，可以——確保遞迴有正確的終止條件（避免無限遞迴）、或用「尾遞迴」形式（不過 Java 目前不做尾遞迴優化，所以在 Java 中尾遞迴幫助不大）、或適當調大 `-Xss`（但這只是治標，不能根治深度問題）。

**詳細解析**：遞迴的本質是用「虛擬機器棧」來隱式地保存每一層的狀態，而虛擬機器棧空間有限（`-Xss` 通常 1MB 左右），所以遞迴深度受限。把遞迴改成迭代，就是「用一個顯式的、分配在堆上的棧/佇列資料結構」來手動保存每一層的狀態，堆空間大得多（`-Xmx` 可能幾 GB），所以能處理極深的層數。例如遞迴遍歷一棵很深的樹容易 SOF，改用一個 `ArrayDeque` 顯式管理待處理節點的迭代遍歷就沒問題。調大 `-Xss` 只是讓棧能容納更多層，但無法根本解決「深度不確定或非常大」的問題（而且調大 Xss 會讓每個執行緒佔用更多記憶體，執行緒多時反而可能導致別的問題）。要注意 Java 不像某些函數式語言會做尾遞迴優化（把尾遞迴自動轉成迴圈），所以在 Java 中「寫成尾遞迴形式」並不能避免 SOF，還是要真正改成迭代。

**面試回答方式**：講出根本解法「遞迴改迭代（用堆上的顯式棧/佇列取代有限的虛擬機器棧）」，並說明「調大 -Xss 只是治標、Java 不做尾遞迴優化所以尾遞迴形式沒用」。能舉「遞迴遍歷深樹改成用 ArrayDeque 迭代」的例子，展現你理解遞迴與棧的關係以及正確的根治方法。

### 每個執行緒的棧是獨立的，那大量執行緒和 -Xss 設定有什麼關係？

**核心答案**：因為每個執行緒都有自己獨立的虛擬機器棧，`-Xss` 設定的是「單個執行緒棧的大小」，所以執行緒數量越多、`-Xss` 越大，總的棧記憶體消耗就越大（總棧記憶體 ≈ 執行緒數 × `-Xss`）。這帶來一個權衡——`-Xss` 設大能容納更深的方法呼叫（減少 SOF），但在需要建立大量執行緒的場景下，過大的 `-Xss` 會消耗大量記憶體，甚至可能導致「無法建立新執行緒」的 OOM（`unable to create new native thread`）。所以高並發、多執行緒的場景反而可能需要適當調小 `-Xss`。

**詳細解析**：這揭示了 `-Xss` 設定的一個容易被忽略的權衡。棧記憶體是「每執行緒獨立」的，且棧空間來自作業系統為執行緒分配的記憶體（不在 `-Xmx` 控制的堆內）。假設 `-Xss` 設為 1MB，1000 個執行緒就要 1GB 的棧記憶體；如果為了避免某些深遞迴而把 `-Xss` 調到 10MB，1000 個執行緒就要 10GB——這很可能導致系統記憶體不足、無法再建立新執行緒。所以在「需要大量執行緒」的場景（如某些每連線一執行緒的舊式伺服器），反而傾向於把 `-Xss` 調小以容納更多執行緒。這也是虛擬執行緒（見 Java 併發）的一大優勢——虛擬執行緒的「棧」很輕量且能動態伸縮，不像平台執行緒每個都要預留固定的 `-Xss` 大小，所以能輕鬆建立百萬級執行緒。理解這個權衡，展現你把棧記憶體、執行緒數、`-Xss` 這幾個因素串起來考量。

**面試回答方式**：講出「每執行緒獨立棧、總棧記憶體 ≈ 執行緒數 × -Xss、所以多執行緒場景 -Xss 過大會導致無法建立新執行緒的 OOM」。能點出「這也是虛擬執行緒的優勢（棧輕量可伸縮、不用每個預留固定 Xss）」，展現你把 JVM 記憶體和併發模型串起來的整體理解。

### StackOverflowError 可以被 catch 嗎？該這樣做嗎？

**核心答案**：技術上可以被 catch（它是 `Error` 的子類別，而 `catch (Throwable)` 或 `catch (StackOverflowError)` 能捕捉到它），但一般不應該這樣做。因為 `StackOverflowError` 代表程式已經處於一個異常狀態（通常是遞迴邏輯有 bug），catch 它並繼續執行往往治標不治本、甚至可能讓程式處於不確定的狀態；正確的做法是修復導致棧溢位的根因（如修正遞迴終止條件、改成迭代）。`Error` 這一類本就設計為「代表嚴重的、通常無法透過程式邏輯恢復的問題」，不建議像處理業務例外那樣捕捉處理。

**詳細解析**：`Error` 和 `Exception` 都繼承自 `Throwable`，所以語法上 `Error` 是可以被 catch 的，但設計語意上——`Error` 代表「JVM 層級的嚴重問題，應用通常無力回天」（見 Java 核心的例外體系題）。`StackOverflowError` 雖然相對「輕微」（catch 後棧會恢復，理論上還能繼續運行），但它的出現說明程式碼有 bug（不當的遞迴），catch 掉它讓程式「假裝沒事繼續跑」是一種掩蓋問題的做法——真正的問題（遞迴邏輯錯誤）沒有解決，可能在別處以更難排查的形式再次出現，或者留下不完整的執行狀態。極少數情況下（例如一個框架要防禦性地處理使用者可能寫出的無限遞迴），可能會 catch 它並做降級處理，但這是特例。一般原則是——把 `StackOverflowError` 當成「程式碼有 bug 的信號」去修復根因，而不是當成「可以捕捉處理的業務例外」。

**面試回答方式**：回答「技術上可以 catch（是 Error 子類別）但不應該」，並解釋原因——「它代表程式碼有 bug（不當遞迴）、catch 掉是掩蓋問題、正確做法是修根因」。能連結到「Error 設計上代表無法透過程式邏輯恢復的嚴重問題、不該當業務例外處理」，展現你理解 Error 的設計語意和正確的處理態度。
