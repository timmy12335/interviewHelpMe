# 題目

原生映像檔（Native Image）與傳統 JVM 差在哪？什麼場景值得用？

## 核心答案

原生映像檔用 **AOT（提前編譯）** 把 Java 應用編譯成一個獨立的作業系統可執行檔——**不需要 JVM、沒有 JIT、沒有類別載入**。收益非常明確：**啟動時間從秒級降到毫秒級**（快 50 到 100 倍）、**記憶體佔用降到幾分之一**（沒有 JIT、沒有中繼資料、堆積可以很小）、**映像檔小**（幾十 MB 而非幾百 MB）。

代價同樣明確。**封閉世界假設**——建置時必須知道所有會被載入的類別、所有反射的目標、所有動態代理，因為執行期無法再載入新東西；反射、動態代理、序列化、資源檔都需要**顯式配置**（或由框架提供的中繼資料）。**峰值吞吐通常較低**——沒有 JIT 就沒有基於執行期剖析的最佳化（單型內聯、分支預測），長時間執行的高吞吐服務上，JIT 的優勢仍然明顯。**建置時間長**——一個中型應用可能要幾分鐘到十幾分鐘。**除錯與可觀測性較弱**——傳統的 JVM 工具（jstack、JFR、heap dump）大多不適用或功能受限。

判斷準則很清楚：短命、高頻啟動、記憶體受限的場景（無伺服器函式、CLI 工具、大量小型微服務實例）用原生映像檔；長時間執行、追求峰值吞吐的服務用 JVM。

## 詳細解析

封閉世界假設是所有麻煩的根源，也是所有收益的來源。因為建置時就知道整個程式的範圍，AOT 編譯器可以做**全程式分析**——移除所有不可達的程式碼（這是映像檔小的原因）、把靜態初始化在建置時就跑完（這是啟動快的原因）、精確地佈局記憶體。代價是任何「執行期才決定」的機制都要事先宣告。Spring Boot 3 與 Quarkus 的原生支援，本質上是在建置階段分析框架的用法並自動生成這些配置——這也是為什麼「用框架的原生支援」遠比「自己寫配置」實際。

峰值吞吐的差距值得精確理解。AOT 編譯器可以做靜態最佳化，但它**無法知道執行期的行為**：哪個分支常走、哪個介面實作實際上只有一個、哪些物件不會逃逸。GraalVM 提供 **PGO（剖析導引最佳化）**——先跑一次收集剖析資料，再用它指導 AOT 編譯，能縮小差距但需要額外的建置步驟與代表性的工作負載。所以差距不是「AOT 一定慢」，而是「沒有執行期資訊時的最佳化上限較低」。

**GC 的選擇也不同**。原生映像檔預設用 Serial GC（社群版）或 G1（企業版），**沒有 ZGC 這類低停頓收集器**。對於記憶體小、生命週期短的無伺服器函式這完全不是問題；但如果想用原生映像檔跑一個大堆積的長期服務，GC 反而成為短板。**這進一步印證了它的定位。**

選型的實際考量還包括團隊成本。原生映像檔的問題往往在**建置期**才顯現（某個反射沒配置到），而且錯誤訊息不如 JVM 友善；生產環境的診斷手段也少。在團隊沒有相關經驗時，這些成本可能超過啟動時間的收益——除非啟動時間確實是核心痛點（無伺服器的冷啟動計費、或需要秒級擴容）。

## 面試回答方式

先給機制（AOT 編譯成獨立執行檔，無 JVM、無 JIT、無類別載入）與**三個明確收益**（啟動快 50 到 100 倍、記憶體降到幾分之一、映像檔小）。接著給四個代價，並把**封閉世界假設**放在核心位置——它既是所有麻煩的根源也是所有收益的來源：因為建置時知道整個程式範圍，才能做全程式分析、移除不可達程式碼、把靜態初始化提前跑完。給出明確的判斷準則（短命高頻啟動記憶體受限用 AOT，長時間高吞吐用 JVM）。加分點有三個：峰值吞吐的差距源自「沒有執行期資訊」而非 AOT 本身慢，PGO 能縮小差距；**沒有 ZGC 這類低停頓收集器**，進一步印證定位；以及**團隊成本**——問題在建置期才顯現、錯誤訊息不友善、生產診斷手段少。

## 講稿

原生映像檔用提前編譯把應用做成一個獨立的可執行檔，不需要 JVM、沒有 JIT、沒有類別載入。收益很明確，啟動時間從秒級降到毫秒級、記憶體佔用降到幾分之一、映像檔也小很多。

代價同樣明確。最核心的是封閉世界假設，建置的時候必須知道所有會被載入的類別、所有反射的目標、所有動態代理。因為執行期無法再載入新東西。

我覺得這個假設既是所有麻煩的根源，也是所有收益的來源。正因為建置時知道整個程式的範圍，編譯器才能做全程式分析，移除所有不可達的程式碼，這是映像檔小的原因。把靜態初始化在建置時就跑完，這是啟動快的原因。

第二個代價是峰值吞吐通常較低。但要精確理解，不是提前編譯一定慢，而是沒有執行期資訊時的最佳化上限比較低。哪個分支常走、哪個介面實際上只有一個實作，這些 JIT 知道而提前編譯不知道。GraalVM 有剖析導引最佳化可以縮小差距。

所以判斷準則很清楚。短命、高頻啟動、記憶體受限的場景用原生映像檔。長時間執行、追求峰值吞吐的服務用 JVM。

## 常見追問

### 反射在原生映像檔裡要怎麼處理？

**核心答案**：必須在建置時顯式宣告會被反射存取的類別、方法與欄位，透過 `reflect-config.json` 或註解（`@RegisterForReflection`）告訴編譯器保留它們。沒有宣告的話，那些成員會被當成不可達而被移除，執行期呼叫就拋 `ClassNotFoundException` 或 `NoSuchMethodException`。同樣的要求適用於動態代理、JNI、資源檔與序列化。

**詳細解析**：手寫這些配置在真實應用裡是不可行的——一個 Spring 應用可能反射存取數千個類別。實務上有三條路：**框架提供中繼資料**（Spring Boot 3 的 AOT 處理、Quarkus 的建置期擴充，它們在建置階段分析程式碼自動生成配置，這是主流做法）、**追蹤代理**（用 `-agentlib:native-image-agent` 跑一次應用，記錄實際用到的反射並生成配置，**但它只能記錄跑到的路徑**，測試覆蓋不足就會漏）、**GraalVM 可達性中繼資料倉庫**（社群維護的常見函式庫配置）。「追蹤代理只能記錄跑到的路徑」是最需要注意的一點——它讓問題從編譯期移到了「某個罕見路徑第一次被走到時」，那可能是上線後才發生。

**面試回答方式**：給出要求（顯式宣告反射目標，否則被當成不可達移除）並列出同樣需要處理的機制（動態代理、JNI、資源、序列化）。指出手寫不可行，給三條實務路徑並標出主流（框架的 AOT 處理）。真正的加分點是點出追蹤代理只能記錄跑到的路徑，測試覆蓋不足就會漏，讓問題從編譯期移到「罕見路徑第一次被走到時」——那可能是上線後才發生。

### 為什麼原生映像檔的靜態初始化行為與 JVM 不同？

**核心答案**：因為 AOT 編譯器會在建置時執行部分類別的靜態初始化，並把結果直接寫進映像檔的初始堆積——這正是啟動快的關鍵之一。但這帶來語意差異：在建置機器上取得的值被固定進映像檔。例如一個靜態欄位存了 `new Date()`、機器的主機名、或者一個開啟的檔案控制代碼，那些值會是**建置當時**的，而不是執行時的。

**詳細解析**：更嚴重的是資源類的物件不能被建置期初始化——一個在靜態初始化中建立執行緒池、開啟 socket、或載入原生函式庫的類別，如果被提前初始化，映像檔裡會存著一個無效的物件。GraalVM 因此提供了 `--initialize-at-build-time` 與 `--initialize-at-run-time` 兩個開關讓開發者明確指定。排查這類問題的難點在於症狀很奇怪——不是拋例外，而是「某個值莫名其妙是錯的」或「連線池裡的連線全部無效」。這是原生映像檔最需要小心的一類語意差異，而且它在傳統 JVM 上完全不會發生，所以很難靠既有經驗預期。

**面試回答方式**：先給機制——建置時執行靜態初始化並把結果寫進初始堆積，這是啟動快的關鍵之一，但會把建置當時的值固定住。舉具體例子（`new Date()`、主機名）。重點放在資源類物件不能被建置期初始化（執行緒池、socket、原生函式庫），並給出兩個控制開關。加分點是描述症狀的詭異之處：不是拋例外而是「值莫名其妙是錯的」，很難靠既有 JVM 經驗預期。

### 有沒有介於兩者之間的方案？

**核心答案**：有幾種。**AppCDS**——把類別的解析結果預存成共享歸檔，啟動時直接映射，省 10% 到 30% 的啟動時間，**保留完整的 JVM 能力**，成本極低。**JVM 的分層編譯調整**——短命行程用 `TieredStopAtLevel=1` 只用 C1。**Project Leyden**（進行中）——JDK 官方的方向，目標是提供一個「靜態程度可選」的光譜，讓應用可以在啟動速度與動態能力之間選擇位置，而不是二選一。**CRaC（Coordinated Restore at Checkpoint）**——把預熱完成的 JVM 狀態做成檢查點，之後從檢查點恢復，啟動時間也是毫秒級但保留 JIT。

**詳細解析**：**CRaC 是很有意思的一條路**——它繞過了「重新預熱」這個問題，直接把預熱後的狀態存下來。代價是檢查點包含了開啟的檔案、socket、以及時間相關的狀態，恢復時需要應用配合（實作回呼在檢查點前關閉資源、恢復後重建）。這條路的哲學與原生映像檔相反：原生映像檔是「放棄動態能力換取靜態最佳化」，CRaC 是「保留全部動態能力，只把啟動成本預先付掉」。能指出「這是一個光譜而不是二選一」，比評價任何單一方案更有價值——實際的選擇取決於應用在啟動速度、峰值吞吐、記憶體、與開發成本這四個維度上的權重。

**面試回答方式**：列出幾種中間方案，並特別展開 **CRaC**——把預熱後的 JVM 狀態做成檢查點再恢復，啟動毫秒級但保留 JIT，代價是需要應用配合處理資源。給出它與原生映像檔**哲學相反**的對比（放棄動態能力 vs 只把啟動成本預先付掉）。收在最有價值的判斷：**這是一個光譜而不是二選一**，選擇取決於應用在啟動速度、峰值吞吐、記憶體、開發成本四個維度上的權重。
