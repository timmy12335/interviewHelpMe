# 題目

Java 的執行緒與作業系統執行緒是什麼關係？一個執行緒佔多少資源？

## 核心答案

HotSpot 用的是 **一對一模型**：每一個 `java.lang.Thread` 對應一個**作業系統的原生執行緒**（Linux 上是一個 task）。建立、銷毀、排程、上下文切換全部由作業系統負責，JVM 只是包了一層 API。這也意味著 Java 無法控制執行緒的排程——`Thread.setPriority` 只是給 OS 的提示，`Thread.yield` 也只是建議。

一個平台執行緒的成本有三部分：**堆疊**（預設 1 MB 虛擬位址，用 `-Xss` 設定；實際佔用的實體記憶體依使用深度而定，通常遠小於 1 MB）、**核心的 task 結構**（幾 KB）、以及**建立與銷毀的成本**（涉及系統呼叫，約幾十微秒）。**上下文切換的成本約 1 到 10 微秒**，加上快取失效的間接成本可能更高。

**虛擬執行緒改變了這個模型**：它是 JVM 自己排程的使用者態執行緒，多對一地映射到少數載體執行緒上（載體數預設等於核心數）。它的堆疊在**堆積上**而非固定的原生堆疊，可以從幾百位元組成長到需要的大小——這是它能開到數十萬個的根本原因。

## 詳細解析

一對一模型的取捨是「簡單與整合」對上「成本」。好處是 Java 執行緒能直接享受作業系統的排程器（包括多核調度、優先權、以及與其他行程的公平競爭），阻塞的系統呼叫也自然運作。代價是每個執行緒都很重，數量受限於記憶體與排程開銷——幾千個平台執行緒就會讓上下文切換成為明顯的成本。

堆疊大小的設定是一個容易誤解的地方。`-Xss1m` 設的是**虛擬位址空間**的保留量，Linux 的按需分頁讓實際使用的頁面才佔實體記憶體。所以「一千個執行緒 = 1 GB 記憶體」是不準確的——實體佔用通常小得多。但虛擬位址空間仍然是有限的資源（32 位元系統上尤其明顯），而且在容器的記憶體核算裡，某些設定下 RSS 的成長仍然會反映出來。`-Xss` 設太小的後果是 `StackOverflowError`，設太大則浪費位址空間並可能讓能建立的執行緒數下降。

虛擬執行緒的「堆疊在堆積上」有幾個重要後果。**堆疊可以按需成長**，不必預先保留 1 MB。**掛起與恢復是複製堆疊片段**（stack chunk），這比作業系統的上下文切換便宜得多。但它也意味著虛擬執行緒的堆疊會被 GC 掃描——數十萬個虛擬執行緒的堆疊都是堆積上的物件，這對 GC 是新的負擔（也是為什麼 ZGC 與虛擬執行緒的搭配特別被強調）。

**執行緒數的實際上限**由幾個因素共同決定：可用記憶體、作業系統的 `threads-max` 與 `pid_max`、容器的 pids limit、以及排程開銷。在容器裡忘記調高 pids limit 而導致「無法建立新執行緒」是一個常見但容易誤診的問題——錯誤訊息是 `OutOfMemoryError: unable to create native thread`，看起來像記憶體問題，實際上是行程數限制。

## 面試回答方式

先給模型——一對一，每個 Java 執行緒對應一個 OS 原生執行緒，排程完全由作業系統負責，所以 `setPriority` 只是提示。給出三部分成本（堆疊 1 MB 虛擬位址、核心 task 結構幾 KB、建立銷毀幾十微秒）與上下文切換的量級（1 到 10 微秒）。接著說明**虛擬執行緒改變了模型**：JVM 自己排程、多對一映射到載體、**堆疊在堆積上可按需成長**——這是能開數十萬個的根本原因。加分點有三個：`-Xss` 設的是虛擬位址而非實體記憶體，所以「一千個執行緒 = 1 GB」不準確；**虛擬執行緒的堆疊會被 GC 掃描**，這對 GC 是新負擔；以及 `OutOfMemoryError: unable to create native thread` 常常是容器的 pids limit 而非記憶體問題，這是容易誤診的一個。

## 講稿

HotSpot 用的是一對一模型，每一個 Java 執行緒對應一個作業系統的原生執行緒。建立、銷毀、排程、上下文切換全部由作業系統負責，JVM 只是包了一層 API。這也意味著 Java 無法控制排程，設定優先權只是給作業系統的提示。

一個平台執行緒的成本有三部分。堆疊預設一 MB 的虛擬位址、核心的結構幾 KB、還有建立跟銷毀涉及系統呼叫大約幾十微秒。上下文切換大概一到十微秒，加上快取失效的間接成本可能更高。

有一個容易誤解的地方。堆疊參數設的是虛擬位址空間的保留量，按需分頁讓實際使用的頁面才佔實體記憶體。所以一千個執行緒等於一 GB 記憶體這個說法不準確，實體佔用通常小得多。

虛擬執行緒改變了這個模型。它是 JVM 自己排程的使用者態執行緒，多對一映射到少數載體執行緒上。它的堆疊在堆積上而不是固定的原生堆疊，可以按需成長，這是它能開到數十萬個的根本原因。

不過這也意味著虛擬執行緒的堆疊會被垃圾回收掃描，數十萬個執行緒的堆疊都是堆積上的物件，這對 GC 是新的負擔。

## 常見追問

### 「unable to create native thread」一定是記憶體不足嗎？

**核心答案**：**不一定，而且常常不是**。這個錯誤表示作業系統拒絕建立新執行緒，可能的原因有四個：**記憶體不足**（無法為堆疊保留位址空間）、**達到作業系統的執行緒上限**（`/proc/sys/kernel/threads-max`、`pid_max`）、**達到使用者的 `ulimit -u` 限制**、以及**容器的 pids cgroup limit**。在容器環境下，最後一項是最常見的原因，而錯誤訊息裡的「OutOfMemoryError」會把人引向錯誤的方向。

**詳細解析**：診斷方式是先確認實際的執行緒數（`ls /proc/<pid>/task | wc -l`）與各項限制（`cat /proc/sys/kernel/threads-max`、`ulimit -u`、`cat /sys/fs/cgroup/pids/pids.max`），比對就知道撞到哪一個。如果執行緒數異常高（例如幾萬個），那本身就是問題——通常是執行緒池設定錯誤、或者某處在迴圈裡建立執行緒而沒有重用。這個錯誤的價值在於它幾乎總是指向一個設計問題：正常的服務不該需要幾萬個執行緒。所以在調高限制之前，應該先問「為什麼需要這麼多」。

**面試回答方式**：明確否定「一定是記憶體不足」，給出四個可能原因並指出**容器的 pids limit 是最常見的**，而錯誤訊息裡的 OutOfMemoryError 會誤導。給出診斷方式（比對實際執行緒數與各項限制的具體路徑）。收在一個重要判斷：這個錯誤幾乎總是指向設計問題，正常服務不該需要幾萬個執行緒，所以調高限制之前應該先問為什麼需要這麼多。

### -Xss 該設多少？

**核心答案**：**多數應用用預設值（Linux x64 上是 1 MB）就好**，不需要調。調小的理由是「執行緒非常多且遞迴淺」（可以省虛擬位址空間，讓能建立的執行緒數上升）；調大的理由是「有深遞迴或大量區域變數」（避免 `StackOverflowError`）。調整前應該先確認實際的堆疊使用深度，而不是憑感覺。

**詳細解析**：深遞迴的正確解法通常不是調大堆疊，而是改成迭代。遞迴深度依賴輸入時（例如解析深度巢狀的 JSON、遍歷可能很深的樹），調大堆疊只是把崩潰的門檻推高——攻擊者或異常資料仍然可以構造出更深的結構，這在處理外部輸入時是一個真實的安全問題（堆疊溢位造成的阻斷服務）。所以處理不受信任的輸入時，正確的做法是明確限制深度並在超過時拋出業務例外，而不是依賴堆疊大小。JSON 與 XML 解析器通常都提供深度限制的設定，那是應該打開的。

**面試回答方式**：給預設值與調整的兩個方向，強調**調整前先量測實際堆疊深度**。真正的加分點是後半段：深遞迴的正確解法通常是改成迭代而非調大堆疊，因為調大只是推高門檻，處理外部輸入時攻擊者仍可構造更深的結構——這是真實的阻斷服務風險。收在具體建議：處理不受信任輸入時明確限制深度並拋業務例外，並打開解析器提供的深度限制設定。

### 虛擬執行緒之後，平台執行緒還有什麼用？

**核心答案**：三種場景仍然需要平台執行緒。**CPU 密集的計算**——虛擬執行緒的價值在於「阻塞便宜」，不阻塞的任務用它沒有好處，而且切換仍然會汙染快取；固定大小的執行緒池或 ForkJoinPool 更合適。需要作業系統排程特性的場景——設定執行緒親和性（affinity）、即時優先權、或需要與其他行程公平競爭時。執行原生方法或需要與原生程式碼互動——虛擬執行緒在原生方法中會釘住載體，沒有優勢。

**詳細解析**：還有一類是**長期存活的基礎設施執行緒**——事件迴圈、GC 執行緒、監控與心跳執行緒。這些執行緒的數量固定且很少，用平台執行緒沒有成本問題，而且它們往往需要穩定的排程特性。所以正確的心智模型不是「虛擬執行緒取代平台執行緒」，而是「任務用虛擬執行緒、基礎設施用平台執行緒」——前者數量多、生命週期短、以阻塞等待為主；後者數量少、長期存活、需要可預測的排程。能給出這個劃分，比籠統地說「虛擬執行緒更好」準確得多。

**面試回答方式**：給三種仍需平台執行緒的場景並各配理由。加分點是補上第四類——**長期存活的基礎設施執行緒**（事件迴圈、監控、心跳），數量固定且需要穩定排程。收在正確的心智模型：不是取代關係，而是「任務用虛擬執行緒、基礎設施用平台執行緒」——前者數量多、短命、以阻塞為主，後者數量少、長存活、需要可預測排程。
