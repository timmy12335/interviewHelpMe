# 題目

G1 收集器的回收流程是怎樣的？Remembered Set 解決了什麼問題？

## 核心答案

G1 把堆劃分成許多大小相等的 Region，回收流程包括：Young GC（回收新生代 Region）、並發標記週期（初始標記、並發標記、最終標記、清理）、以及 Mixed GC（同時回收新生代和部分價值最高的老年代 Region）。Remembered Set（記憶集）解決的是「跨 Region 引用」問題——當回收某些 Region 時，需要知道有哪些其他 Region 的物件引用了它們（否則這些引用者也算 GC Roots 的一部分），RSet 記錄了這些跨 Region 的引用關係，讓 G1 可以只回收部分 Region 而不用掃描整個堆。

## 詳細解析

**Region 化基礎**：堆被分成幾千個大小相等的 Region（1MB~32MB），每個 Region 動態地扮演 Eden、Survivor、Old 或 Humongous（存放大物件）的角色。這讓 G1 能靈活地「挑選」要回收哪些 Region。

**回收的三種活動**：

1. **Young GC（Minor GC）**：當 Eden Region 用滿，STW 地回收所有新生代 Region，把存活物件複製到 Survivor 或晉升到 Old Region。
2. **並發標記週期**：當老年代佔用達到閾值（`-XX:InitiatingHeapOccupancyPercent`，預設 45%）觸發，包含——初始標記（短 STW，標記 GC Roots 直接引用的物件，通常搭著一次 Young GC 做）、並發標記（與應用並發，遍歷整個物件圖）、最終標記（短 STW，處理並發標記期間的變動，用 SATB）、清理（統計各 Region 的存活情況，為 Mixed GC 做準備）。
3. **Mixed GC**：並發標記完成後，G1 進行 Mixed GC——回收所有新生代 Region 加上一部分「回收價值最高（垃圾最多）」的老年代 Region，用複製把存活物件搬到空 Region、消除碎片。

**Remembered Set（RSet）**：

- 問題：G1 要「只回收部分 Region」，但一個 Region 中的物件可能被其他 Region 的物件引用。如果不知道這些跨 Region 引用，回收時就無法正確判斷哪些物件還存活（總不能為了回收一個 Region 而掃描整個堆找引用它的地方）。
- 解法：每個 Region 維護一個 RSet，記錄「哪些其他 Region 的物件引用了本 Region 的物件」。回收某個 Region 時，除了 GC Roots，還把 RSet 中記錄的引用者也作為額外的根，這樣就能在不掃描整個堆的情況下正確判斷存活性。
- 維護 RSet 靠「寫屏障（write barrier）」——應用每次修改物件引用時，執行一小段程式碼更新相關的 RSet。這是 G1 的一項額外開銷。

## 面試回答方式

先講 Region 化這個基礎（堆分成小塊、動態扮演角色），這是理解 G1 一切的前提。接著講三種回收活動（Young GC、並發標記週期、Mixed GC），重點是 Mixed GC「回收新生代 + 部分高價值老年代 Region」這個 G1 的招牌能力。RSet 是這題最容易深挖的點——一定要講清楚它解決的問題（跨 Region 引用讓「只回收部分 Region」成為可能）和維護方式（寫屏障）。能把「為什麼只回收部分 Region 需要 RSet」的邏輯講通，展現你真正理解 G1 而非背流程。

## 常見追問

### G1 中的 Humongous 物件是什麼？為什麼要特殊處理？

**核心答案**：Humongous（巨型）物件指大小超過單個 Region 一半的大物件。G1 用專門的 Humongous Region 來存放它們（一個大物件可能佔用多個連續的 Humongous Region），而不是放在普通的 Eden Region。特殊處理是因為——大物件如果按正常流程在 Eden 分配、再隨 GC 在 Region 之間複製，成本很高；直接用專門的 Region 存放並特殊管理（例如可以在並發標記週期就直接回收不再被引用的 Humongous Region），能避免大物件反覆複製的開銷。

**詳細解析**：巨型物件對 G1 是個麻煩——它可能大到一個 Region 裝不下（需要多個連續 Region）、複製成本高、且容易導致 Region 碎片（找不到足夠的連續 Region 分配大物件時會觸發 GC）。G1 對它們的特殊處理包括：直接在老年代性質的 Humongous Region 分配（跳過新生代）、在標記階段結束後如果發現某個 Humongous 物件已不可達就直接回收整個 Humongous Region（快速釋放大塊空間）。但 Humongous 物件仍然是 G1 調優時要注意的點——過多或過大的 Humongous 物件會導致頻繁的 GC 和 Region 分配困難，有時需要透過調大 Region 大小（`-XX:G1HeapRegionSize`）讓這些物件不再算作 Humongous 來優化。理解 Humongous 的處理，能幫你排查「大物件頻繁分配導致 G1 GC 異常」這類問題。

**面試回答方式**：講出「超過半個 Region 的大物件、用專門的 Humongous Region 存放、避免反覆複製的開銷」，並延伸「過多 Humongous 物件是調優隱患、可透過調大 Region 大小緩解」，展現你不只知道這個概念，還了解它對實際調優的影響。

### G1 如何做到「可預測的停頓時間」？

**核心答案**：G1 為每個 Region 維護「回收它需要的成本」和「能回收多少垃圾」的統計資料，形成一個「回收效益模型」。當要做 Mixed GC 時，G1 根據使用者設定的目標停頓時間（`-XX:MaxGCPauseMillis`）作為預算，用這個模型貪心地挑選「在預算內能回收最多垃圾」的一組 Region 來回收。因為每次只回收「挑選出的、數量可控的」一部分 Region，且有歷史統計來估算回收這些 Region 大概要多久，所以能把單次停頓控制在目標時間附近，實現可預測。

**詳細解析**：這是 G1 相比傳統收集器最大的賣點。傳統收集器回收整個新生代或整個老年代，停頓時間由「要處理的資料量」決定、不可控（堆越大停頓越長）。G1 的 Region 化 + 效益模型讓它把 GC 變成一個「在停頓時間預算內最大化回收效益」的最佳化問題——它知道回收每個 Region 大概花多少時間（基於歷史)、能回收多少垃圾，於是像背包問題一樣挑選 Region。設定的目標停頓時間越短，G1 每次挑選的 Region 就越少（回收的垃圾也越少，可能需要更頻繁地 GC）；目標越寬鬆，每次能回收更多。要注意——這是「盡力達成」的軟目標而非硬保證，設得太離譜（如 1ms）G1 也做不到。理解這個「用效益模型在停頓預算內挑選 Region」的機制，是理解 G1 可預測停頓的核心。

**面試回答方式**：講出核心機制——「為每個 Region 統計回收成本和垃圾量、根據目標停頓時間作為預算挑選性價比最高的 Region 回收」，並說明「這是盡力達成的軟目標、設太小也做不到、且會導致更頻繁 GC」。能把它類比成「背包問題/最佳化問題」，展現你對這個機制的理解上升到了演算法層面。

### 什麼場景下 G1 不如 Parallel 或需要調優？

**核心答案**：在「追求極致吞吐量、不在意停頓時間」的批次運算場景，Parallel 可能比 G1 更好——因為 G1 為了控制停頓，付出了額外的開銷（維護 RSet 的寫屏障、並發標記佔用 CPU、更複雜的記憶體管理），這些開銷會略微降低吞吐量。此外，G1 在小堆（幾百 MB）上的優勢不明顯（Region 化的管理開銷相對佔比高），且若目標停頓時間設得不合理、或有大量 Humongous 物件、或 RSet 過大，都可能需要專門調優。

**詳細解析**：沒有「一個收集器適合所有場景」——G1 是「低延遲和吞吐的平衡者」，但這個平衡有代價。對於離線批次處理、大數據運算這類「跑得越快越好、GC 停頓長一點無所謂」的場景，Parallel 收集器把全部精力放在吞吐、不為低停頓付出額外開銷，反而更合適。G1 的甜蜜點是「大堆（幾 GB 到幾十 GB）+ 對延遲有要求（希望停頓可控）」的線上服務。調優 G1 時常見的關注點包括——目標停頓時間設定是否合理（太小導致頻繁 GC 和吞吐下降）、Humongous 物件是否過多、並發標記是否來得及（IHOP 閾值）、RSet 和寫屏障的開銷等。理解「G1 不是萬能、它的平衡有代價」能展現你有成熟的收集器選型判斷。

**面試回答方式**：回答「追求極致吞吐的批次場景 Parallel 可能更好、小堆 G1 優勢不明顯」，並說明原因——「G1 為控制停頓付出了 RSet/並發標記等額外開銷、略降吞吐」。點出 G1 的甜蜜點（大堆+延遲敏感的線上服務）和常見調優點，展現你理解收集器選型是「按場景權衡」而非「越新越好」。
