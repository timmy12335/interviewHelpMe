# 題目

年輕代回收時，怎麼知道有哪些老年代物件引用了年輕代物件？

## 核心答案

如果不做任何處理，每次年輕代回收都必須掃描整個老年代才能找出跨代引用——那樣分代就完全沒有意義了（分代的價值正是「只處理一小部分堆積」）。

解法是用空間換時間，額外記錄跨代引用的位置。經典的做法是**卡表（card table）**：把老年代切成一張張固定大小的「卡片」（HotSpot 是 512 位元組），用一個位元組陣列標記每張卡片是否「髒」——只要有引用寫入落在這張卡片上，就把對應位元組標為髒。年輕代回收時只需要掃描髒卡片對應的那些記憶體區域，而不是整個老年代。

維護卡表的機制是**寫屏障**：每次執行「把引用寫入物件欄位」時，額外執行一小段程式碼把對應的卡片標髒。這是一個**常態成本**——每次引用寫入都要付，換取每次年輕代回收時的大幅節省。

G1 因為是按區域（region）回收而非按代，需要更精細的結構：**記憶集（remembered set）**，每個區域記錄「有哪些其他區域的物件引用了我」。它比卡表精確但**記憶體開銷大得多**（可能佔堆積的百分之幾到十幾）。

## 詳細解析

卡表的粒度是一個典型的取捨。卡片設小（例如 128 位元組）則掃描時要看的區域少，但卡表本身變大、且寫屏障要處理的邊界情況變多；設大則卡表小但每次掃描的區域大。**512 位元組是 HotSpot 權衡後的選擇**，它讓卡表大小約為堆積的 1/512（8 GB 堆積約 16 MB）。

「卡表汙染」是一個真實的效能問題。多個執行緒同時寫入落在同一張卡片上時，它們會反覆寫同一個位元組——這造成**偽共享**（那個位元組所在的快取行在核心之間彈跳）。HotSpot 的緩解方式是 `-XX:+UseCondCardMark`：先讀取，只有在卡片還不是髒的時候才寫入。多一次讀取，但避免了重複寫入造成的快取行爭用，在多核多執行緒的場景下是淨收益。

**G1 的記憶集為什麼那麼貴**：它需要記錄「哪個區域的哪張卡片引用了我」，而區域數量可能上千。實作上是一個多層結構（稀疏、細粒度、粗粒度三種表示，依引用數量自動升級）。當跨區域引用非常多時，記憶集會膨脹到佔用大量記憶體，而且維護它的併發精煉（concurrent refinement）執行緒會消耗可觀的 CPU。這正是 ZGC 與 Shenandoah 選擇不維護記憶集（改用併發標記整個堆積）的理由之一——它們用「每次掃全堆」換掉了「持續維護記憶集」的成本。

這一組機制解釋了一個實務現象：把大量物件放進長期存活的集合（快取、靜態 Map）會顯著增加 GC 成本，不只因為它們佔記憶體，更因為它們持有的引用不斷產生跨代／跨區域引用，讓寫屏障、卡表與記憶集的負擔上升。「老年代物件持有大量年輕物件」是一個值得警惕的模式，典型的例子是一個長期存活的快取不斷放入新建立的物件。

## 面試回答方式

先講清楚**問題本身**：不做處理的話每次年輕代回收都要掃整個老年代，分代就失去意義了。接著給**卡表**的機制（老年代切成 512 位元組的卡片、位元組陣列標髒、只掃髒卡片），並點出維護它的是**寫屏障**——這是每次引用寫入都要付的常態成本，換取回收時的大幅節省。然後給 **G1 的記憶集**：按區域記錄「誰引用了我」，更精確但記憶體開銷可能佔堆積的百分之幾到十幾。加分點有三個：**卡表汙染造成偽共享**，`UseCondCardMark` 用「先讀再寫」緩解；**ZGC 與 Shenandoah 不維護記憶集**，用「每次掃全堆」換掉持續維護的成本；以及最有實務價值的一句——長期存活的集合不斷放入新物件會持續產生跨代引用，讓寫屏障與記憶集的負擔上升，這是快取設計時值得警惕的模式。

## 講稿

如果不做任何處理，每次年輕代回收都必須掃描整個老年代才能找出跨代引用，那分代就完全沒有意義了，因為分代的價值正是只處理一小部分堆積。

解法是用空間換時間。經典的做法是卡表，把老年代切成一張張五百一十二位元組的卡片，用一個位元組陣列標記每張卡片是不是髒的。只要有引用寫入落在這張卡片上就標髒。年輕代回收的時候只掃髒卡片對應的區域。

維護卡表靠寫屏障，每次把引用寫入物件欄位的時候，額外執行一小段程式碼把卡片標髒。這是常態成本，每次引用寫入都要付。

G1 因為按區域回收而不是按代，需要更精細的記憶集，每個區域記錄有哪些其他區域引用了我。它比卡表精確但記憶體開銷大得多，可能佔堆積的百分之幾到十幾。

這一組機制解釋了一個實務現象。把大量物件放進長期存活的集合，比如快取或靜態的 Map，會顯著增加 GC 成本。不只因為佔記憶體，更因為它們持有的引用不斷產生跨代引用，讓寫屏障跟記憶集的負擔上升。所以老年代物件持有大量年輕物件是一個值得警惕的模式。

## 常見追問

### 寫屏障的成本大概是多少？

**核心答案**：單次的成本很小（幾條指令），但它出現在每一次引用欄位的寫入上，所以總成本取決於應用的寫入密集程度。粗略地說，簡單的卡表寫屏障對整體吞吐的影響通常在 1% 到 5%；**G1 的寫屏障複雜得多**（要判斷跨區域、要把卡片放進佇列給精煉執行緒處理），影響可能到 10% 以上——這是 G1 在小堆積上吞吐不如 Parallel 收集器的主要原因之一。

**詳細解析**：值得注意的是寫屏障只作用於引用型別的欄位寫入，基本型別的寫入完全不受影響。所以「把大物件拆成基本型別欄位」或「用陣列存基本型別而非包裝物件」除了省記憶體之外，還能減少寫屏障的觸發次數。另外 **JIT 會做一些最佳化**：如果能證明寫入的目標是新配置且尚未逃逸的物件（不可能有跨代引用），寫屏障可以省略。這說明了逃逸分析的價值不只是棧上分配與鎖消除，它也影響 GC 屏障的成本——這是一個少被提及的連結。

**面試回答方式**：給出量級（簡單卡表屏障 1% 到 5%、G1 的複雜屏障可能 10% 以上）並指出這是 G1 在小堆積上吞吐不如 Parallel 的原因之一。加分點是兩個具體事實：寫屏障只作用於引用寫入，基本型別完全不受影響（所以用基本型別集合有雙重好處）；以及 JIT 能對未逃逸的新物件省略寫屏障，這說明逃逸分析也影響 GC 屏障成本。

### G1 的記憶集什麼時候會失控？

**核心答案**：當**跨區域引用非常多**時。典型的觸發模式是「一個大型的長期存活結構持有分散在各區域的大量物件」——例如一個裝了幾百萬個物件的快取，它的引用會遍布整個堆積。此時每個區域的記憶集都很大，總記憶體開銷可能達到堆積的 10% 以上，而且維護它的併發精煉執行緒會持續消耗 CPU。

**詳細解析**：G1 有一組參數控制精煉的積極程度（`G1ConcRefinementThreads`、`G1RSetUpdatingPauseTimePercent`），但調參只能移動成本，不能消除它——精煉做得少，停頓時就要處理更多累積的卡片。**根本的解法在應用層**：減少長期存活物件對大量分散物件的引用。具體做法包括把快取的值改成更緊湊的表示（例如存序列化後的位元組陣列而非物件圖）、限制快取大小、或者把資料移到堆外。「用一個大物件取代一百萬個小物件」在 GC 的角度上是巨大的改善，因為記憶集記錄的是引用而不是位元組。

**面試回答方式**：給出觸發模式（大型長期存活結構持有分散在各區域的大量物件）與後果（記憶集佔堆積 10% 以上、精煉執行緒持續耗 CPU）。指出**調參只能移動成本不能消除**——精煉做得少，停頓時就要處理更多累積卡片。收在應用層的根本解法：更緊湊的表示、限制快取大小、移到堆外，並給出關鍵洞見——記憶集記錄的是引用而非位元組，所以用一個大物件取代一百萬個小物件是巨大的改善。

### 為什麼 ZGC 不需要記憶集？

**核心答案**：因為它**不做分代式的部分回收**（JDK 21 之前）——每次回收都併發地掃描整個堆積，所以不需要「哪些外部區域引用了我」這個資訊。它用**併發標記加讀屏障**取代了「維護跨區引用記錄」這條路：反正整個堆積都要走一遍，就不必記錄誰引用誰。

**詳細解析**：這是一個徹底的取捨——用「每次的總工作量較大」換掉「持續的屏障與記憶集維護成本」。因為工作是併發的，總工作量大不直接轉成停頓，只轉成 CPU 開銷。但這個取捨在分配速率高時會出問題：每輪都掃全堆意味著回收週期較長，而週期越長越容易被分配速率追上——這正是 JDK 21 引入分代 ZGC 的動機。分代 ZGC 因此**又需要記錄跨代引用**了（它用了一種基於指標著色的方案而非傳統卡表）。這個來回很說明問題：分代假設的價值太大，即使是為了避免記憶集而放棄分代的設計，最終還是繞回來了。

**面試回答方式**：先給直接原因——不做分代式部分回收，每次併發掃全堆，所以不需要跨區引用資訊。說明這是「用總工作量大換掉持續屏障與記憶集成本」的徹底取捨，而工作是併發的所以不轉成停頓。真正的加分點是後半段：這個取捨在分配速率高時會出問題（週期長容易被追上），這正是 JDK 21 引入分代 ZGC 的動機，而分代版本又需要記錄跨代引用了——這個來回說明分代假設的價值太大，繞了一圈還是回來了。
