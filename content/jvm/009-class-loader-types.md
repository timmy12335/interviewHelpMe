# 題目

JVM 有哪些類別載入器？如何自訂一個類別載入器？什麼場景需要自訂？

## 核心答案

JVM 內建三層類別載入器：啟動類別載入器（Bootstrap，載入核心類別庫，C++ 實作）、擴展/平台類別載入器（Extension/Platform，載入擴展模組）、應用類別載入器（Application，載入 classpath 上的應用類別）。自訂類別載入器通常繼承 `ClassLoader`、覆寫 `findClass()` 方法（在其中讀取位元組碼（Bytecode）並呼叫 `defineClass()`），而不是覆寫 `loadClass()`（覆寫 findClass 能保留雙親委派（Parent Delegation））。自訂載入器的常見場景包括：從特殊來源（加密檔案、網路、資料庫）載入類別、實現類別隔離、熱部署/熱替換等。

## 詳細解析

**三層內建載入器**：

1. **Bootstrap ClassLoader**：載入 JVM 核心（`java.lang`、`java.util` 等），由 C++ 實作、沒有對應的 Java 物件（在 Java 中取得它會是 null）。
2. **Extension / Platform ClassLoader**：JDK 8 叫擴展類別載入器（載入 `jre/lib/ext`），JDK 9 模組化後改叫平台類別載入器（載入平台模組）。
3. **Application ClassLoader**：載入應用 classpath 上的類別，是程式預設使用的載入器（`ClassLoader.getSystemClassLoader()` 返回它）。

**自訂類別載入器的正確做法**：

- 繼承 `java.lang.ClassLoader`。
- **覆寫 `findClass()`**（而不是 `loadClass()`）：在 `findClass` 中實現「如何取得類別的位元組碼」（例如從加密檔案讀取並解密、從網路下載），拿到位元組陣列後呼叫 `defineClass(name, bytes, 0, bytes.length)` 把位元組碼轉成 Class 物件。
- 為什麼覆寫 `findClass` 而非 `loadClass`：`loadClass` 中實現了雙親委派的邏輯（先委派父載入器、失敗才呼叫 `findClass`），如果直接覆寫 `loadClass` 容易破壞雙親委派；覆寫 `findClass` 則能在保留雙親委派的前提下，只自訂「父載入器載不了時，自己怎麼載入」的邏輯。

**常見自訂場景**：

1. **從非標準來源載入**：類別位元組碼存在加密檔案、資料庫、網路上，需要自訂載入器讀取並（解密後）defineClass。
2. **類別隔離**：像 Tomcat 為每個應用用獨立載入器實現隔離。
3. **熱部署 / 熱替換**：用新的類別載入器載入更新後的類別（因為同一個載入器無法重複載入同名類別，換一個載入器就能載入新版本），實現不重啟 JVM 就更新程式碼。
4. **位元組碼加密保護**：對 class 檔加密，用自訂載入器解密後載入，防止反編譯。

## 面試回答方式

先列出三層內建載入器（Bootstrap/Platform/Application）及各自載入的範圍。自訂載入器的重點是「覆寫 `findClass` 而非 `loadClass`」以及「為什麼」——因為 loadClass 含雙親委派邏輯、覆寫 findClass 能保留委派。這個細節很能區分是否真的寫過自訂載入器。常見場景要能舉出幾個（非標準來源載入、隔離、熱部署、加密），尤其「熱部署靠換載入器來載入同名新類別」這個點展現你理解類別載入器的隔離特性如何被實際利用。

## 常見追問

### 為什麼自訂載入器要覆寫 findClass 而不是 loadClass？

**核心答案**：因為 `ClassLoader.loadClass()` 方法內部已經實現了完整的雙親委派邏輯——先檢查類別是否已載入、再委派給父載入器嘗試、父載入器失敗後才呼叫 `findClass()` 讓子類別自訂載入。如果你直接覆寫 `loadClass()`，就要自己重新實現這套委派邏輯，一不小心就會破壞雙親委派（例如忘了先委派父載入器，導致核心類別被自己錯誤載入）。覆寫 `findClass()` 則只需專注於「自己如何取得和定義類別」這一部分，雙親委派由父類別的 `loadClass` 自動保留，更安全、更符合設計意圖。

**詳細解析**：這體現了「模板方法模式」——`loadClass()` 是模板方法，定義了「檢查已載入 → 委派父載入器 → 自己載入」的固定流程，其中「自己載入」這一步呼叫 `findClass()` 作為擴展點留給子類別。設計者的意圖是——讓你只覆寫 `findClass` 這個擴展點來注入「如何載入」的自訂邏輯，而保持整個委派流程不變。如果你越過這個設計、直接覆寫 `loadClass`，就繞過了模板方法的保護，需要自己承擔維持委派正確性的責任。當然，如果你的目的正是「刻意打破雙親委派」（如 Tomcat 的 WebAppClassLoader 需要優先載入自己的類別），那才會去覆寫 `loadClass` 並小心地重新實現委派邏輯。所以規則是——想保留雙親委派就覆寫 `findClass`，想刻意打破才覆寫 `loadClass`。

**面試回答方式**：講出「loadClass 已含雙親委派邏輯、覆寫 findClass 能保留委派、覆寫 loadClass 要自己維持委派容易出錯」，並點出這是「模板方法模式，findClass 是留給子類別的擴展點」。能補充「刻意要打破雙親委派時才覆寫 loadClass」，展現你理解兩種覆寫方式對應的不同意圖。

### 熱部署/熱替換是怎麼靠類別載入器實現的？

**核心答案**：因為「同一個類別載入器無法重複載入同一個全限定名的類別」（第二次會直接返回快取的舊 Class），所以要實現「用新版本替換舊版本的類別」，就不能用原來的載入器，而是「建立一個新的類別載入器實例去載入更新後的類別」——由於「類別載入器 + 全限定名」決定類別的唯一性，新載入器載入的新版本類別和舊載入器載入的舊版本是「不同的類別」，於是就實現了在不重啟 JVM 的情況下用新版本替換舊版本。舊的載入器和它載入的舊類別在不再被引用後會被 GC 回收。

**詳細解析**：熱部署的核心技巧是利用類別載入器的隔離特性。假設有一個 `Plugin` 類別需要熱更新——第一次用 loader1 載入 Plugin，運行一段時間後 Plugin 的程式碼更新了，你不能用 loader1 再載入（會返回舊的快取），而是建立 loader2 去載入新的 Plugin.class，然後用 loader2 載入的新 Plugin 替換掉正在使用的舊 Plugin。當所有對舊 Plugin 和 loader1 的引用都斷開後，loader1 及其載入的所有類別會被 GC 回收（類別的卸載條件之一就是其載入器被回收）。這正是很多外掛系統、熱部署框架（如 JRebel、部分應用伺服器的熱部署）的底層原理。要注意——這需要小心管理引用，避免舊載入器因為某些殘留引用（如被 ThreadLocal、靜態變數持有）而無法被回收，造成「類別載入器洩漏（ClassLoader Leak）」，這是熱部署常見的記憶體洩漏（Memory Leak）來源。

**面試回答方式**：講出核心原理——「同一載入器不能重複載入同名類別，所以用新載入器載入新版本、利用載入器隔離實現替換、舊載入器和舊類別待回收」。能點出「類別卸載需要其載入器被回收、殘留引用會導致 ClassLoader 洩漏」這個實務陷阱，展現你理解熱部署不只是「換載入器」還涉及記憶體管理的細節。

### 類別在什麼條件下才會被卸載？

**核心答案**：一個類別要被卸載（從方法區/元空間（Metaspace）清除），需要同時滿足三個條件——該類別的所有實例都已被回收（堆中沒有這個類別的任何物件）、載入該類別的類別載入器已被回收、該類別對應的 `java.lang.Class` 物件沒有任何地方被引用（無法透過反射（Reflection）存取）。因為條件苛刻（尤其「類別載入器被回收」很難達成，Bootstrap/App 載入器在整個 JVM 生命週期都存在），所以由系統載入器載入的類別實際上幾乎不會被卸載，只有自訂載入器載入的類別才有卸載的可能。

**詳細解析**：類別卸載的苛刻條件是為了安全——只要還有一絲可能用到這個類別（有實例、載入器還在、Class 物件可達），就不能卸載它。這也解釋了為什麼——由 Bootstrap 和 Application 載入器載入的核心類別和應用類別基本上「一旦載入就常駐到 JVM 結束」（因為這些載入器本身不會被回收）。只有自訂類別載入器載入的類別，當這個自訂載入器連同它載入的所有類別的實例、Class 物件都不再被引用時，才可能整體被回收卸載——這正是前面熱部署場景中「舊載入器被回收、舊類別被卸載」的依據。理解類別卸載的條件，能幫你理解為什麼「頻繁用自訂載入器動態載入類別卻不釋放引用」會導致元空間/永久代（PermGen） OOM（類別越積越多卸載不掉），這是動態載入場景的一個重要陷阱。

**面試回答方式**：列出三個卸載條件（無實例、載入器被回收、Class 物件不可達），並強調「載入器被回收這個條件很難達成、所以系統載入器載入的類別幾乎不卸載、只有自訂載入器的類別可能卸載」。能連結到「動態載入不釋放引用會導致元空間 OOM」的實務陷阱，展現你理解類別卸載對記憶體管理的實際意義。
