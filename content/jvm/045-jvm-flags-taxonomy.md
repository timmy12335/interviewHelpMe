# 題目

`-X` 與 `-XX` 參數有什麼不同？怎麼知道一個 JVM 目前實際生效的參數？

## 核心答案

參數分三類。**標準參數**（`-version`、`-classpath`、`-D`）——所有 JVM 實作都必須支援，穩定不會變。**非標準參數**（`-X` 開頭，如 `-Xmx`、`-Xss`、`-Xlog`）——HotSpot 特有但相對穩定，不保證跨實作。**進階參數**（`-XX` 開頭）——實作細節，可能在任何版本被改變或移除，其中又分為 product（正式支援）、experimental（需要 `-XX:+UnlockExperimentalVMOptions` 解鎖）、與 diagnostic（需要 `-XX:+UnlockDiagnosticVMOptions`）。

查詢實際生效的參數有三個層次。**`java -XX:+PrintFlagsFinal -version`**——印出所有參數的最終值（包含 JVM 依環境自動推導的），這是最完整的清單。`jcmd <pid> VM.flags`——看一個執行中的 JVM 明確設定的參數；加 `-all` 則印出全部。**`java -XX:+PrintCommandLineFlags -version`**——只印出 JVM 自動設定的那些（例如它選了哪個收集器、堆積大小推導成多少）。

「我以為設了但沒生效」是調優時最常見的問題，而 `PrintFlagsFinal` 就是驗證的方法——它顯示每個參數的值以及來源標記（`default`、`command line`、`ergonomic`）。

## 詳細解析

`ergonomic`（自動推導）標記最值得注意。JVM 會依機器的 CPU 數與記憶體自動決定一堆參數：預設收集器、堆積初始與最大值、GC 執行緒數、TLAB 大小、以及 JIT 的編譯閾值。在容器裡，這些推導的正確性完全依賴容器感知是否運作——如果 JVM 誤讀了主機資源，所有推導出來的值都會錯，而且它們不會出現在命令列上，只能靠 `PrintFlagsFinal` 才看得到。

**參數之間的互動常常被忽略**。設定 `-XX:+UseG1GC` 會改變一批相關參數的預設值；設定 `-Xmx` 會影響 `MaxDirectMemorySize`（預設等於它）；設定 `MaxRAMPercentage` 與 `-Xmx` 同時存在時後者優先。所以「加了一個參數但行為沒變」有時是因為它被另一個參數覆蓋，或它只在某些條件下生效。 `PrintFlagsFinal` 的輸出是判斷這件事的唯一可靠依據。

實驗性與診斷參數的風險要理解。它們可以在下一個版本消失或改變語意，用了之後升級 JDK 可能直接無法啟動（無法識別的 `-XX` 參數會讓 JVM 拒絕啟動，除非加 `-XX:+IgnoreUnrecognizedVMOptions`）。在生產環境使用實驗性參數前，應該記錄「為什麼需要它」與「升級時要檢查什麼」，否則幾年後沒有人知道那行參數的用途，也不敢移除。

調參的實務原則是「少而有理由」。每一個非預設的參數都應該能回答「解決了什麼可量測的問題」。大量從網路上抄來的參數組合是常見的反模式——它們可能互相衝突、可能對應舊版本的 JDK、也可能掩蓋了真正的問題。預設值是經過大量工作負載驗證的，偏離它需要證據。

## 面試回答方式

先給**三類參數**與各自的穩定性承諾，特別指出 `-XX` 參數可能在任何版本被改變或移除，且分 product／experimental／diagnostic 三種。接著給**三個查詢層次**（`PrintFlagsFinal` 看最終值、`jcmd VM.flags` 看執行中的、`PrintCommandLineFlags` 看自動設定的），並強調 `PrintFlagsFinal` 的來源標記（default／command line／ergonomic）是驗證「我以為設了但沒生效」的方法。加分點有三個：`ergonomic` 推導在容器裡的正確性完全依賴容器感知，誤讀主機資源時所有推導值都錯且不會出現在命令列上；參數之間會互動（`-Xmx` 影響 `MaxDirectMemorySize`、`MaxRAMPercentage` 被 `-Xmx` 覆蓋）；以及實驗性參數會讓升級 JDK 時無法啟動。收在原則：少而有理由，每個非預設參數都要能回答「解決了什麼可量測的問題」。

## 講稿

參數分三類。標準參數所有 JVM 實作都支援。減 X 開頭的是非標準參數，HotSpot 特有但相對穩定。減 XX 開頭的是進階參數，屬於實作細節，可能在任何版本被改變或移除。

查詢實際生效的參數我會用三個層次。印出所有參數的最終值，這是最完整的清單。對執行中的 JVM 用 jcmd 看明確設定的參數。還有只印出 JVM 自動推導的那些。

我覺得最有價值的是第一個，因為它會顯示每個參數的來源標記，是預設值、命令列設定、還是 JVM 自己推導的。我以為設了但沒生效，是調優時最常見的問題，而這就是驗證的方法。

自動推導這一類特別值得注意。JVM 會依機器的 CPU 數跟記憶體自動決定收集器、堆積大小、GC 執行緒數這些。在容器裡，這些推導的正確性完全依賴容器感知是否運作。如果誤讀了主機資源，所有推導出來的值都會錯，而且它們不會出現在命令列上。

最後講原則。調參要少而有理由，每一個非預設的參數都應該能回答它解決了什麼可量測的問題。從網路上抄一大串參數是常見的反模式。

## 常見追問

### 為什麼不建議直接抄網路上的 JVM 參數組合？

**核心答案**：四個理由。**版本不匹配**——很多流傳的參數是為 JDK 8 的 CMS 寫的，在 JDK 17 的 G1 上要嘛無效要嘛有害。**工作負載不同**——參數的最佳值取決於堆積大小、分配速率、存活率，別人的最佳值對你可能是最差值。**互相衝突**——抄來的參數組合可能包含互相覆蓋或矛盾的設定。**掩蓋真正的問題**——把 GC 停頓從 200 毫秒調到 150 毫秒，可能掩蓋了「分配速率過高」這個真正該修的問題。

**詳細解析**：更根本的問題是「沒有基準就無法判斷有沒有效」。加了十個參數之後效能好了 10%，你不知道是哪一個有效、哪些是無效的、哪些其實是有害的但被其他的補償了。正確的方法是一次改一個並量測，這聽起來慢，但它產生的是可累積的知識而不是一團無法推理的設定。實務上更有效的順序是：先確認預設值下的實際行為（GC 日誌）、找出瓶頸、優先在應用層改善（降低分配速率、修正資料結構）、最後才調 JVM 參數。 應用層的改善通常收益更大也更持久。

**面試回答方式**：給四個理由（版本不匹配、工作負載不同、互相衝突、掩蓋真正問題）。真正的加分點是提升到方法論：沒有基準就無法判斷有沒有效，加十個參數之後不知道哪個有用；正確方法是一次改一個並量測，產生可累積的知識。收在優先順序：先看預設值下的實際行為、找瓶頸、優先在應用層改善、最後才調參。

### 哪些參數是幾乎每個生產服務都該設的？

**核心答案**：五類，都不是「效能調優」而是「可診斷性」。**GC 日誌**（`-Xlog:gc*:file=...` 加輪替設定）。**OOM 時的堆積轉儲**（`-XX:+HeapDumpOnOutOfMemoryError` 加指向持久儲存的 `HeapDumpPath`）。**OOM 時的動作**（`-XX:+ExitOnOutOfMemoryError` 或 `-XX:OnOutOfMemoryError`，讓行程確定地結束並被重啟，而不是半死不活地繼續處理請求）。**堆積上下限一致**（`-Xms` 等於 `-Xmx`）。**明確的非堆積上限**（`MaxMetaspaceSize`、`MaxDirectMemorySize`）。

**詳細解析**：`ExitOnOutOfMemoryError` 這一項特別值得強調。堆積 OOM 之後的 JVM 處於不確定狀態——某些執行緒死了、某些資料結構可能不一致、而它仍然接受請求並返回錯誤或錯誤的結果。在有編排系統（Kubernetes）自動重啟的環境下，快速失敗並重啟遠比苟延殘喘好。這是「快速失敗」原則在 JVM 層面的具體應用。這五類參數的共同點是：它們不讓系統變快，但讓系統在出事時可診斷、可恢復——而那通常比幾個百分點的效能更有價值。

**面試回答方式**：列出五類並強調它們都不是效能調優而是可診斷性。重點展開 `ExitOnOutOfMemoryError`：OOM 後的 JVM 處於不確定狀態卻仍接受請求，在有自動重啟的環境下快速失敗遠比苟延殘喘好。收在共同點：它們不讓系統變快，但讓系統出事時可診斷可恢復，而那通常比幾個百分點的效能更有價值。

### 怎麼知道一個參數在新版 JDK 還存不存在？

**核心答案**：三個方法。`java -XX:+PrintFlagsFinal -version | grep <name>`——最直接，在目標版本上跑一次就知道。JDK 的發行說明與 JEP——重大參數的移除會有明確的公告與遷移建議。`-XX:+IgnoreUnrecognizedVMOptions`——讓 JVM 忽略不認識的參數而非拒絕啟動，這在升級的過渡期很有用，但不該長期開啟（它會讓打錯字的參數靜默失效）。

**詳細解析**：升級 JDK 時的參數清理應該是一個明確的步驟，而不是等到啟動失敗才處理。實務做法是：在升級前用新版本跑一次 `PrintFlagsFinal` 比對現有參數、逐一確認每個參數在新版本的存在與語意、並趁機移除那些「不知道為什麼在這裡」的參數。這是一個很好的技術債清理時機——升級本來就需要驗證，順便把累積的參數清乾淨的邊際成本很低。反過來，如果每次升級都只是「讓它能啟動」，參數清單只會越來越長且越來越沒有人理解。

**面試回答方式**：給三個方法，並對 `IgnoreUnrecognizedVMOptions` 給出平衡的評價——過渡期有用但不該長期開啟，因為它會讓打錯字的參數靜默失效。真正的加分點是把它變成流程建議：升級 JDK 時的參數清理應該是一個明確步驟，用新版本跑 `PrintFlagsFinal` 比對、逐一確認、並移除「不知道為什麼在這裡」的參數。收在對比：如果每次升級都只是讓它能啟動，參數清單只會越來越長且沒人理解。
