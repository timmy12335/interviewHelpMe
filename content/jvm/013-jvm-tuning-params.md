# 題目

你知道哪些常見的 JVM 調優參數？調優時通常關注哪些指標？

## 核心答案

常見參數分幾類：堆大小（`-Xms` 初始堆、`-Xmx` 最大堆，通常設成相等避免動態擴縮容的抖動）、新生代（`-Xmn` 新生代大小、`-XX:SurvivorRatio` Eden/Survivor 比例）、元空間（`-XX:MetaspaceSize`、`-XX:MaxMetaspaceSize`）、棧（`-Xss` 執行緒棧大小）、收集器選擇（`-XX:+UseG1GC` 等）、GC 目標（`-XX:MaxGCPauseMillis` 目標停頓）、以及 GC 日誌與 OOM 時 dump（`-XX:+HeapDumpOnOutOfMemoryError`）。調優關注的核心指標是——吞吐量、GC 停頓時間、GC 頻率、記憶體佔用。

## 詳細解析

**堆相關**：

- `-Xms` / `-Xmx`：初始堆 / 最大堆大小。生產環境通常設成相等，避免堆在運行中動態擴容/縮容帶來的效能抖動和 Full GC。
- `-Xmn`：新生代大小。新生代大則 Minor GC 頻率低但單次時間長、晉升老年代慢；小則相反。
- `-XX:SurvivorRatio`：Eden 與單個 Survivor 的比例，預設 8（Eden:S0:S1 = 8:1:1）。

**元空間相關**（JDK 8+）：

- `-XX:MetaspaceSize`：元空間初始大小（觸發首次 Full GC 的閾值）。
- `-XX:MaxMetaspaceSize`：元空間最大大小，防止類別元資料無限增長耗盡本地記憶體。

**棧相關**：

- `-Xss`：每個執行緒的棧大小，預設幾百 KB 到 1MB。設太大浪費記憶體（執行緒多時）、設太小容易 StackOverflowError。

**收集器與 GC 目標**：

- `-XX:+UseG1GC` / `-XX:+UseZGC` 等：選擇收集器。
- `-XX:MaxGCPauseMillis`：G1 的目標停頓時間（軟目標）。

**診斷相關**：

- `-XX:+HeapDumpOnOutOfMemoryError` + `-XX:HeapDumpPath`：OOM 時自動 dump 堆快照，供事後分析。
- GC 日誌參數（如 `-Xlog:gc*`，JDK 9+ 統一的日誌框架）：記錄 GC 詳情供調優分析。

**調優關注的指標**：吞吐量（應用運行時間佔比）、延遲（GC 停頓時間，尤其 Full GC）、GC 頻率、記憶體佔用（堆使用率）。調優本質是在這幾個相互制約的目標之間取平衡。

## 面試回答方式

按類別組織參數（堆、新生代、元空間、棧、收集器、診斷），不用背全部，講出每類最核心的幾個即可。重點是展現「理解參數的作用和權衡」而非死背——例如「`-Xms` 和 `-Xmx` 設成相等避免動態擴縮容抖動」「新生代大則 Minor GC 少但單次長」這種帶權衡的說明。最後點出調優關注的核心指標（吞吐、停頓、頻率、記憶體）以及「調優是在這些相互制約的目標間取平衡」，展現你理解調優是系統性的權衡而非套用固定參數。

## 常見追問

### 為什麼建議把 -Xms 和 -Xmx 設成相等？

**核心答案**：因為如果 `-Xms`（初始堆）小於 `-Xmx`（最大堆），JVM 啟動時只分配初始大小，運行中隨著記憶體需求增長會逐步擴容堆（向作業系統申請更多記憶體），而堆的擴容和縮容都可能伴隨 Full GC、且會帶來效能抖動和不可預測的停頓。把兩者設成相等，JVM 啟動時就一次性分配好全部堆記憶體，運行中堆大小恆定，避免了動態調整的開銷和抖動，讓效能更穩定可預測——這在生產環境的服務中尤其重要。

**詳細解析**：堆的動態擴縮容看似「按需分配、節省記憶體」，但對追求穩定的生產服務是弊大於利——擴容時要向 OS 申請記憶體、可能觸發 Full GC 來重新規劃空間；縮容同理。這些動作發生的時機不可控，可能在業務高峰期突然來一下，造成延遲尖刺。設成相等後，記憶體在啟動時就固定下來（雖然啟動時佔用的記憶體立即達到最大值），換來運行期的穩定。這也是為什麼容器化部署時，通常會根據容器的記憶體限制把 `-Xms` 和 `-Xmx` 設成一個固定值（且要預留堆外記憶體的空間，避免容器 OOM 被殺）。理解這個建議背後的「穩定性優先於記憶體節省」的取捨，展現你有生產環境的調優意識。

**面試回答方式**：講出「不相等會導致運行中動態擴縮容、伴隨 Full GC 和效能抖動；相等則啟動時一次分配、運行穩定可預測」。能延伸到「容器化部署也建議固定、且要預留堆外記憶體」，展現你理解這個建議的權衡（穩定性換記憶體）和實務場景。

### 新生代設定過大或過小分別有什麼影響？

**核心答案**：新生代設過大——Minor GC 頻率降低（因為 Eden 更大、更久才裝滿），但單次 Minor GC 時間變長（要掃描的物件多）、且老年代相對變小可能導致 Full GC 更頻繁；新生代設過小——Minor GC 非常頻繁（Eden 很快裝滿）、物件容易因為 Survivor 放不下而過早晉升到老年代（加速老年代填滿、Full GC 增多）。所以新生代大小要根據物件的生命週期分布來平衡 Minor GC 的頻率和單次時間、以及晉升速度。

**詳細解析**：新生代大小是一個典型的權衡參數。它直接影響「物件在新生代能待多久」——新生代大，物件有更多時間在新生代「自然死亡」（在晉升前就變垃圾被 Minor GC 回收），減少晉升到老年代的物件量，這對「大量短命物件」的應用是好的；但新生代大也意味著老年代小，長命物件的空間受限、Full GC 可能更頻繁。新生代小則相反——Minor GC 太頻繁、且 Survivor 也小，容易觸發「動態年齡判斷」或「空間分配擔保」讓物件過早晉升，把本該在新生代死掉的物件塞進老年代，反而加重老年代負擔。調優時通常要結合 GC 日誌觀察——如果發現大量物件過早晉升、Full GC 頻繁，可能是新生代太小；如果 Minor GC 單次時間過長，可能是新生代太大。理解這個權衡，展現你能根據實際 GC 行為來調整而非盲目設定。

**面試回答方式**：對比過大（Minor GC 少但單次長、老年代小 Full GC 可能多）和過小（Minor GC 頻繁、物件過早晉升加重老年代）的影響，並點出「要結合 GC 日誌看晉升情況和 GC 時間來調整」。這種能講出雙向影響並連結到「看日誌調優」的回答，展現你理解調優是觀察驅動的權衡。

### JVM 調優的一般流程和原則是什麼？

**核心答案**：一般流程是——先明確目標（是追求低延遲還是高吞吐？可接受的停頓時間是多少？）、然後建立監控收集 GC 日誌和關鍵指標（停頓時間、頻率、吞吐、記憶體）、分析瓶頸（是 Full GC 太頻繁？單次停頓太長？記憶體不足？）、有針對性地調整參數、再觀察效果並迭代。核心原則是——「先監控分析、再有依據地調整」，不要盲目套用網上的參數；且「大部分應用用預設配置加上合理的堆大小就足夠，不需要過度調優」。

**詳細解析**：調優最忌諱的是「不看實際情況、直接套一堆網上抄來的參數」——每個應用的物件生命週期、負載模式、延遲要求都不同，適合別人的參數未必適合你。正確的流程是資料驅動的——先問清楚「要優化什麼」（沒有目標的調優是盲目的），再透過 GC 日誌、監控工具（見 [[014-gc-troubleshooting.md]]）看清楚「當前的瓶頸是什麼」，然後針對這個瓶頸調整對應的參數，最後驗證是否真的改善。而且要有一個清醒的認識——現代 JVM（尤其 G1）的預設配置已經相當好，大部分應用只需要設定合理的堆大小（`-Xms`/`-Xmx`）就能跑得不錯，過度調優（調一堆細節參數）往往收益很小甚至幫倒忙。真正需要深度調優的是那些對延遲/吞吐有嚴苛要求、或遇到明確 GC 問題的場景。理解「調優是資料驅動的、且不要過度」，展現你有成熟務實的工程態度。

**面試回答方式**：講出流程（定目標 → 監控 → 分析瓶頸 → 針對性調整 → 迭代驗證）和核心原則（資料驅動、不盲目套參數、不過度調優）。特別強調「大部分應用設好堆大小就夠、預設配置已經很好」，這種務實不炫技的態度，往往比背一堆參數更能贏得資深面試官的認可。
