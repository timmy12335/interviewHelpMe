# 題目

方法區、永久代、元空間三者是什麼關係？JDK 8 為什麼用元空間取代永久代？

## 核心答案

「方法區」是 JVM 規範中定義的一個「邏輯概念」——存放類別的元資料、執行時常數池、靜態變數等。「永久代（PermGen）」和「元空間（Metaspace）」是 HotSpot 虛擬機器對「方法區」這個規範概念的兩種具體「實作」——JDK 7 及之前用永久代（在 JVM 堆記憶體中、大小固定）實作方法區，JDK 8 起改用元空間（在本地記憶體中、可動態擴展）實作。改用元空間主要是為了解決永久代「大小固定容易 OOM、不易調優」的問題。

## 詳細解析

**三者的關係**：

- **方法區**：是《JVM 規範》定義的一個抽象概念（規範只說「有這麼一塊區域存類別元資料等」，不規定怎麼實作）。
- **永久代 / 元空間**：是 HotSpot 對「方法區」的具體實作。就像「介面」和「實作類別」的關係——方法區是規範（介面），永久代和元空間是不同版本的實作。

**永久代（PermGen，JDK 7 及之前）**：

- 位於 JVM 堆記憶體中，大小由 `-XX:PermSize` / `-XX:MaxPermSize` 控制、固定。
- 問題：大小固定且預設偏小，動態載入大量類別（反射、動態代理、熱部署、大型應用）容易撐爆，拋 `OutOfMemoryError: PermGen space`；且它的 GC 效率不高、與堆的 GC 耦合。

**元空間（Metaspace，JDK 8 起）**：

- 移到本地記憶體（native memory），不再佔用 JVM 堆。
- 大小預設只受可用實體記憶體限制，能動態擴展（可用 `-XX:MaxMetaspaceSize` 設上限）。
- 好處：大幅降低了 `PermGen space` 這類 OOM、記憶體管理更靈活。

**為什麼要改**：

1. 永久代大小固定、預設偏小，容易 OOM 且調優麻煩；元空間用本地記憶體、可動態擴展，緩解了這個問題。
2. Oracle 合併 HotSpot 和 JRockit（JRockit 沒有永久代概念），統一實作時傾向於去掉永久代。
3. 永久代的 GC 與堆耦合、效率不高，移到元空間後解耦。

**注意**：元空間用本地記憶體不代表不會 OOM——如果無限制載入類別（如 classloader 洩漏），仍會耗盡本地記憶體拋 `OutOfMemoryError: Metaspace`。

## 面試回答方式

先講清楚「三者的層次關係」——這是這題最容易搞混也最能展現理解的點：方法區是規範概念（介面），永久代和元空間是它的兩種實作（實作類別）。用「介面 vs 實作」的類比一句話說清楚。接著講從永久代到元空間的改變（堆內固定 → 本地記憶體可擴展）和原因（永久代易 OOM、難調優）。務必補一句「元空間也會 OOM（classloader 洩漏時）」避免給人「換了就沒問題」的錯覺，展現你理解這個改動的邊界。

## 常見追問

### 什麼場景容易導致元空間 OOM？

**核心答案**：元空間存放類別元資料，所以「載入了過多的類別」就會導致元空間 OOM，典型場景包括——大量使用動態代理/CGLIB（每個代理都動態生成一個新類別）、頻繁的反射生成類別、大量使用動態語言/腳本（如動態編譯生成類別）、以及最嚴重的「類別載入器洩漏（ClassLoader Leak）」（自訂載入器或熱部署場景中，舊的載入器和它載入的類別無法被回收、越積越多）。這些場景讓類別的數量持續增長、載入的類別卸載不掉，最終耗盡元空間。

**詳細解析**：元空間 OOM 的根源和堆 OOM 類似——要嘛是「正常需求就是大」（載入的類別本來就多，調大 `MaxMetaspaceSize` 即可），要嘛是「洩漏」（類別只增不減）。動態生成類別的框架是常見的「合理但量大」的來源——例如某些 ORM、AOP、序列化框架會為每個實體/切面/型別動態生成類別，用得多元空間就大。而 ClassLoader 洩漏是最隱蔽的「洩漏型」原因——回想類別卸載的苛刻條件（載入器要被回收，見 [[009-class-loader-types.md]]），如果一個自訂載入器因為某些殘留引用（被 ThreadLocal、靜態變數、執行緒持有）無法被回收，它載入的所有類別就都卸載不掉；在反覆熱部署或反覆建立自訂載入器的場景，這些卸載不掉的類別會不斷累積，最終元空間 OOM。排查元空間 OOM 通常要看「載入了哪些類別、類別數量是否異常增長、是否有大量重複的動態生成類別、是否有載入器洩漏」。

**面試回答方式**：列出常見場景（動態代理/CGLIB 生成類別、反射、動態編譯、ClassLoader 洩漏），並區分「合理但量大（調 MaxMetaspaceSize）」和「洩漏型（ClassLoader 洩漏、類別只增不減）」兩類。能連結到「類別卸載需要載入器被回收、載入器洩漏導致類別卸載不掉」，展現你把元空間 OOM 和類別載入/卸載機制串起來理解。

### 為什麼字串常數池從永久代移到了堆？

**核心答案**：JDK 7 把字串常數池從永久代移到了堆記憶體，主要原因是——永久代大小固定且偏小，如果大量呼叫 `String.intern()` 把字串放入永久代的字串池，容易撐爆永久代導致 `PermGen space` OOM；移到堆後，字串池能享受堆更大更靈活的空間和更好的 GC（不再被使用的池化字串可以被回收），也讓 `intern()` 的行為更合理（JDK 7 後 intern 如果池中沒有，會直接放堆中已存在字串的引用而非複製一份）。

**詳細解析**：這題連結到 Java 核心的字串池題（[[../java/003-string-immutability-pool.md]]）。字串池的遷移是「永久代問題」的一個具體體現——永久代空間有限，而字串（尤其大量 intern 的動態字串）可能很多，放在永久代容易 OOM。JDK 7 把字串池移到堆後，字串池就和普通物件一樣受堆的 GC 管理，不再有「永久代放不下」的問題，且沒有被引用的池化字串能被正常回收。這也順帶改變了 `intern()` 的實作——JDK 6 的 intern 如果池中沒有這個字串，會把字串「複製」一份放進永久代的池；JDK 7 之後，因為池在堆中，intern 如果池中沒有，會直接把「堆中已存在的這個字串物件的引用」放入池（不複製），更省記憶體。理解這個遷移，能把 JVM 記憶體區域的演進和字串的行為變化串起來。

**面試回答方式**：講出「永久代固定偏小、大量 intern 容易撐爆、移到堆後享受更大空間和 GC」，並連結到「intern 行為的變化（JDK 7 後放引用而非複製）」。能把它和永久代→元空間的整體演進、以及字串池題串起來，展現你對 JVM 記憶體演進有連貫的理解。

### 方法區裡除了類別元資料，還存了什麼？

**核心答案**：方法區（永久代/元空間）主要存放——類別的元資料（類別結構、欄位/方法資訊、存取修飾符等）、執行時常數池（class 檔常數池載入後的執行期形態，存放字面量和符號引用）、靜態變數（JDK 7 前 static 變數在永久代，JDK 7 後移到了堆）、以及即時編譯器編譯後的程式碼快取等。需要注意隨版本演進，一些東西的位置有變化——如靜態變數和字串常數池在 JDK 7 都移到了堆。

**詳細解析**：方法區是「類別層級」資訊的存放地，核心是類別的元資料和常數池。幾個容易混淆的點——一是「執行時常數池」，它是 class 檔中「常數池」這部分在類別載入後進入方法區的形態，存放編譯期生成的各種字面量（如字串、數值常數）和符號引用（類別/方法/欄位的符號描述，在解析階段轉為直接引用）；二是「靜態變數」的位置變化——JDK 7 之前靜態變數存在方法區（永久代），JDK 7 開始移到了堆（和字串池一起遷移），這是個容易答錯的細節；三是元空間時代，類別元資料在本地記憶體的元空間，但靜態變數和字串池在堆。理解「方法區存什麼、以及哪些東西隨版本遷移了位置」，能幫你答對關於記憶體區域的細節題，也展現你對 JVM 記憶體佈局演進的精確掌握。

**面試回答方式**：列出方法區存的東西（類別元資料、執行時常數池、JIT 程式碼快取），並主動點出「靜態變數和字串常數池在 JDK 7 已經移到堆了」這個容易答錯的細節。能區分「類別元資料在元空間、靜態變數和字串池在堆」，展現你對記憶體區域演進的精確理解。
