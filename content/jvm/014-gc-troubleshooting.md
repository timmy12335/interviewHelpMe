# 題目

線上遇到 GC 頻繁、記憶體洩漏或 CPU 飆高等問題，你會用哪些工具、怎麼排查？

## 核心答案

常用命令列工具：`jps`（查 Java 行程）、`jstat`（監控 GC 統計，如 GC 次數/耗時/各區使用率）、`jmap`（產生堆快照 heap dump、看物件統計）、`jstack`（產生執行緒堆疊快照，排查死鎖/CPU 飆高/執行緒阻塞）、`jinfo`（查看/修改 JVM 參數）。圖形化/進階工具：`jvisualvm`、`JMC`（Java Mission Control）、`Arthas`（阿里開源的線上診斷神器）、`MAT`（Memory Analyzer，分析 heap dump 找記憶體洩漏）。排查方法是——先用監控定位問題類型（GC 問題 / 記憶體洩漏 / CPU 問題），再用對應工具深入分析。

## 詳細解析

**核心命令列工具**：

- **`jps`**：列出當前的 Java 行程和 PID，排查的第一步（找到目標行程）。
- **`jstat`**：即時監控 GC 統計資料，如 `jstat -gcutil <pid> 1000` 每秒輸出各記憶體區使用率、YGC/FGC 次數和耗時。用來快速判斷「是不是 GC 有問題」（如 Full GC 頻繁、老年代持續增長不下降）。
- **`jmap`**：`jmap -histo <pid>` 看堆中物件的數量和大小統計（快速找出佔用最多的物件）；`jmap -dump:format=b,file=heap.hprof <pid>` 產生完整堆快照供 MAT 分析。
- **`jstack`**：`jstack <pid>` 產生所有執行緒的堆疊快照，用來排查死鎖（會自動標示 deadlock）、CPU 飆高（結合 top 找到高 CPU 的執行緒再對應到堆疊）、執行緒大量阻塞等問題。
- **`jinfo`**：查看和動態修改部分 JVM 參數。

**進階/圖形化工具**：

- **`jvisualvm` / `JMC`**：圖形化監控 JVM 的記憶體、執行緒、GC、CPU，能即時觀察和取樣分析。
- **`Arthas`**：阿里開源的線上診斷工具，能在不重啟服務的情況下——查看方法呼叫耗時、監控方法參數/返回值、反編譯類別、查看類別載入情況、追蹤呼叫鏈路等，是線上排查的利器。
- **`MAT`（Memory Analyzer Tool）**：分析 heap dump 的專業工具，能找出「佔用記憶體最多的物件」、「可疑的記憶體洩漏（Leak Suspects）」、以及物件的引用鏈（找出「為什麼這個物件沒被回收」）。

**排查思路（按問題類型）**：

1. **GC 頻繁 / Full GC 多**：用 `jstat` 確認 GC 情況 → 用 `jmap -histo` 或 heap dump 看是什麼物件在堆積 → 分析是記憶體不足還是有洩漏。
2. **記憶體洩漏（OOM）**：配置 `-XX:+HeapDumpOnOutOfMemoryError` 自動 dump → 用 MAT 分析 dump，找出佔用大且不該存在的物件及其引用鏈。
3. **CPU 飆高**：`top` 找到高 CPU 的行程和執行緒 → 把執行緒 ID 轉成十六進位 → 在 `jstack` 的輸出中找到對應執行緒的堆疊，看它在執行什麼。
4. **執行緒阻塞 / 死鎖**：`jstack` 看執行緒狀態和鎖持有關係（見 Java 併發死鎖題）。

## 面試回答方式

先按「工具分類」列出核心工具（命令列 jps/jstat/jmap/jstack + 進階 Arthas/MAT），並簡述各自用途。更重要的是展現「排查思路」——按問題類型（GC 頻繁 / OOM / CPU 飆高 / 死鎖）講對應的排查步驟，尤其「CPU 飆高怎麼用 top + jstack 定位到具體執行緒和程式碼」這個經典流程一定要能完整說出，這是最能展現實戰經驗的部分。能提到 Arthas 這個線上診斷利器和 MAT 分析 heap dump，展現你有實際的線上排查經驗而非只知道工具名稱。

## 常見追問

### CPU 飆高怎麼定位到具體是哪段程式碼？

**核心答案**：標準流程是——先用 `top` 找到 CPU 佔用高的 Java 行程 PID；再用 `top -Hp <pid>`（或 `top -H`）找到這個行程內 CPU 佔用高的「執行緒」的 ID；把這個執行緒 ID（十進位）轉換成十六進位；然後用 `jstack <pid>` 產生執行緒堆疊快照，在其中搜尋這個十六進位的執行緒 ID（在 `nid=0x...` 欄位），找到對應的執行緒堆疊，就能看到這個高 CPU 執行緒當前正在執行哪個方法、哪一行程式碼。

**詳細解析**：這是一個非常經典且高頻的線上排查流程，能完整說出來是實戰經驗的直接證明。關鍵細節——`jstack` 輸出中每個執行緒有一個 `nid`（native thread id），它是十六進位的；而 `top -Hp` 看到的執行緒 ID 是十進位的，所以中間要做一次進制轉換（`printf "%x" <十進位ID>`）才能對應上。找到堆疊後，如果這個執行緒卡在某個業務方法的迴圈裡，就定位到了「CPU 被什麼程式碼吃掉」。常見的高 CPU 原因包括——死迴圈、頻繁的 GC（此時高 CPU 的會是 GC 執行緒）、大量計算、正則回溯爆炸等。現在用 Arthas 的 `thread -n <top N>` 指令可以更方便地直接列出最耗 CPU 的執行緒及其堆疊，不用手動做進制轉換，是更現代的做法。

**面試回答方式**：完整講出「top 找行程 → top -Hp 找執行緒 → 進制轉換 → jstack 搜 nid 對應堆疊」這個流程，強調「執行緒 ID 要從十進位轉十六進位才能對應 jstack 的 nid」這個關鍵細節。能補一句「Arthas 的 thread -n 更方便」，展現你既懂經典手法又了解現代工具。

### 怎麼判斷是記憶體洩漏還是記憶體不足（容量問題）？

**核心答案**：關鍵看「GC 後記憶體能不能降下來」——用 `jstat` 或 GC 日誌觀察，如果每次 Full GC 後老年代使用率能明顯下降、回到一個穩定的低水位，那通常是「記憶體不足/容量問題」（只是堆設得太小、或瞬時負載大）；如果 Full GC 後老年代使用率降不下來、呈現「持續上漲、每次 GC 只回收一點點、最終趨向 100%」的趨勢，那就是「記憶體洩漏」（有物件本該被回收卻一直被引用著回收不掉）。確認洩漏後，用 heap dump + MAT 分析找出洩漏的物件和它的引用鏈。

**詳細解析**：這個判斷是排查記憶體問題的分水嶺，因為兩者的解法完全不同——容量問題調大堆或優化瞬時負載即可，洩漏問題則要找到並修復「不該持有的引用」。判斷的核心是觀察老年代使用率隨時間和 GC 的變化趨勢：健康的應用，老年代使用率會在一個範圍內波動（漲上去、Full GC 後降下來、再漲、再降）；洩漏的應用，老年代使用率呈現鋸齒狀但整體持續上升的趨勢（每次 Full GC 回收的越來越少，因為越來越多物件被洩漏的引用鎖住無法回收），最終逼近上限觸發 OOM。確認是洩漏後，MAT 的價值在於——它能分析 heap dump，透過「Dominator Tree」找出佔用最多記憶體的物件、透過「Leak Suspects」報告直接指出可疑的洩漏點、並能查看物件的「incoming references（引用鏈）」回答「這個物件為什麼沒被回收」（找到那個不該存在的強引用）。

**面試回答方式**：講出核心判斷依據——「Full GC 後老年代能降下來是容量問題、降不下來且持續上漲是洩漏」，並說明兩者解法不同（容量問題調堆、洩漏找引用）。能講出「確認洩漏後用 MAT 的 Dominator Tree / Leak Suspects / 引用鏈找出洩漏物件」，展現你有完整的從判斷到定位的排查能力。

### Arthas 相比傳統的 jstack/jmap 有什麼優勢？

**核心答案**：Arthas 的核心優勢是「動態、線上、無侵入」——它能在服務正常運行、不重啟、不改程式碼的情況下，即時地做很多傳統工具做不到或很麻煩的事：例如 `watch` 動態觀察某個方法的入參和返回值、`trace` 追蹤方法內部各步驟的耗時找出效能瓶頸、`monitor` 統計方法的呼叫次數和成功率、`jad` 反編譯線上正在運行的類別確認程式碼版本、`redefine` 甚至能熱替換類別。這些能力讓它在「問題只在線上特定條件下出現、無法在本地重現」的場景下特別有價值。

**詳細解析**：傳統工具（jstack/jmap/jstat）主要是「拍快照」——抓一個瞬間的執行緒/堆狀態來分析，是靜態的。Arthas 則是「動態觀測」——它透過 Java Agent 和位元組碼增強技術，能在執行期動態地插入觀測邏輯，讓你像用偵錯器一樣觀察線上運行的方法行為，卻不需要暫停服務或加日誌重新部署。典型場景——線上某個介面偶爾返回錯誤結果，但本地無法重現、加日誌又要重新部署很慢，這時用 Arthas 的 `watch` 直接觀察這個方法在線上的真實入參和返回值，往往幾分鐘就定位問題。它把「排查線上問題」從「加日誌 → 重新部署 → 等問題重現 → 看日誌」這種漫長的循環，變成了「即時觀測」。理解 Arthas 的動態觀測能力，展現你了解現代線上診斷的高效手段。

**面試回答方式**：講出核心優勢「動態、線上、無侵入——不重啟不改碼就能觀察方法入參返回值、追蹤耗時、反編譯線上類別」，並用一個具體場景（線上偶發問題本地無法重現，用 watch 直接觀察真實入參返回值）說明它的價值。能對比「傳統工具是靜態快照、Arthas 是動態觀測」，展現你理解它帶來的排查方式的變革。
