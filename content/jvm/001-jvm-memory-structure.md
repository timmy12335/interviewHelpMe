# 題目

JVM 執行時的記憶體區域分成哪幾塊？各自存放什麼、是執行緒共享還是私有？

## 核心答案

JVM 執行時資料區主要分五塊：堆（Heap）、方法區（Method Area，JDK 8 後由元空間 Metaspace 實作）、虛擬機器棧（JVM Stack）、本地方法棧（Native Method Stack）、程式計數器（Program Counter Register）。其中「堆」和「方法區」是所有執行緒共享的；「虛擬機器棧、本地方法棧、程式計數器」是每個執行緒私有的。堆存放物件實例，是 GC 的主要區域；棧存放方法呼叫的棧幀（區域變數、運算元棧等）。

## 詳細解析

**執行緒共享區域**：

1. **堆（Heap）**：存放幾乎所有的物件實例和陣列，是垃圾回收（Garbage Collection）管理的主要區域，通常被分為新生代和老年代。堆是 JVM 記憶體中最大的一塊，`-Xms`/`-Xmx` 控制其初始/最大大小。
2. **方法區（Method Area）**：存放類別的元資料——類別結構、欄位/方法資訊、執行時常數池、靜態變數等。JDK 7 及之前用「永久代（PermGen）」實作，JDK 8 起改用「元空間（Metaspace）」，且元空間使用本地記憶體（不再佔用堆）。

**執行緒私有區域**：

3. **虛擬機器棧（JVM Stack）**：每個執行緒有自己的棧，每呼叫一個方法就壓入一個「棧幀（Stack Frame）」，棧幀中包含區域變數表、運算元棧、動態連結、方法返回位址。方法執行完棧幀彈出。`-Xss` 控制棧大小。棧過深會拋 `StackOverflowError`。
4. **本地方法棧（Native Method Stack）**：與虛擬機器棧類似，但服務於 native（本地）方法的呼叫（用 C/C++ 實作的方法）。
5. **程式計數器（PC Register）**：記錄當前執行緒正在執行的位元組碼（Bytecode）指令位址，是唯一一個不會發生 `OutOfMemoryError` 的區域。執行緒切換後靠它恢復到正確的執行位置。

**為什麼這樣劃分**：共享區（堆、方法區）存放的是「所有執行緒都可能存取的資料」（物件、類別資訊），所以需要共享並考慮並發安全；私有區（棧、PC）存放的是「每個執行緒各自執行狀態」的資料（方法呼叫鏈、當前執行位置），天然應該隔離，也因此不需要同步。

## 面試回答方式

用「共享 vs 私有」這個維度來組織回答最清晰——先講共享的堆和方法區（存物件、存類別元資料），再講私有的棧、本地方法棧、程式計數器（存執行狀態）。核心要能說出「堆存物件是 GC 主戰場、棧存方法呼叫的棧幀」。如果能主動點出「為什麼這樣劃分」（共享區存跨執行緒資料、私有區存各自執行狀態），以及「JDK 8 方法區從永久代改成元空間、且用本地記憶體」這個演進，會展現你不只背區域名稱還理解設計邏輯。

## 常見追問

### 為什麼 JDK 8 要把永久代改成元空間？

**核心答案**：主要原因是永久代的大小是在 JVM 啟動時就固定分配的（受 `-XX:MaxPermSize` 限制），容易因為載入太多類別而發生 `OutOfMemoryError: PermGen space`，且不易調優；元空間改用「本地記憶體（native memory）」，大小預設只受可用實體記憶體限制、能動態擴展，大幅降低了這類 OOM 的風險，也讓類別元資料的記憶體管理更靈活。

**詳細解析**：永久代把類別元資料放在 JVM 堆的一個固定大小區域，這帶來兩個問題——一是大小固定且預設偏小，動態載入大量類別的應用（如大量使用反射（Reflection）、動態代理（Dynamic Proxy）、或熱部署的應用伺服器）很容易撐爆永久代；二是永久代的 GC 效率不高且與堆的 GC 耦合。元空間把類別元資料移到本地記憶體後，不再受固定的 JVM 堆大小限制，預設能用到的空間大得多（受實體記憶體限制），並可透過 `-XX:MaxMetaspaceSize` 設上限。這個改動也是 Oracle 合併 HotSpot 和 JRockit 兩個 JVM 的產物（JRockit 沒有永久代概念）。不過要注意——元空間用本地記憶體不代表不會 OOM，如果無限制地載入類別（如 classloader 洩漏），仍會耗盡本地記憶體拋 `OutOfMemoryError: Metaspace`。

**面試回答方式**：講清楚「永久代固定大小易 OOM、元空間用本地記憶體可動態擴展」這個核心改進，並補充「元空間仍可能因 classloader 洩漏而 OOM」避免給人「換了就沒問題」的錯覺，展現你理解這個改動的動機與它的邊界。

### 堆和棧最本質的區別是什麼？

**核心答案**：堆是執行緒共享的、存放物件實例、由 GC 管理生命週期、空間大且分配相對慢；棧是執行緒私有的、存放方法呼叫的棧幀（區域變數、部分基本型別值、物件引用）、隨方法呼叫壓入和彈出、生命週期跟隨方法、空間小但分配和回收極快（就是移動棧頂指標）。簡言之——堆存「資料本體（物件）」且需要 GC，棧存「執行狀態和引用」且自動隨方法進出。

**詳細解析**：這個區別對理解 Java 的記憶體行為很關鍵。當你 `Object o = new Object()``new Object()` 建立的物件實例在「堆」上，而變數 `o`（這個引用）在當前方法棧幀的「區域變數表」中（棧上）。堆上的物件需要 GC 判斷何時回收（因為多個執行緒、多個地方可能引用它，生命週期複雜）；棧上的區域變數則在方法執行完、棧幀彈出時自動消失，不需要 GC。棧的分配/回收極快（本質是棧頂指標的移動），但空間有限（`-Xss` 通常幾百 KB 到 1MB），遞迴太深會 `StackOverflowError`；堆空間大但分配較慢（要找合適的記憶體塊、可能觸發 GC）。理解「引用在棧、物件在堆」也是理解值傳遞、逃逸分析（Escape Analysis）等進階主題的基礎。

**面試回答方式**：用「堆存物件本體需 GC、棧存執行狀態隨方法自動進出」概括本質區別，並用 `Object o = new Object()` 這個例子點出「引用 o 在棧、物件在堆」，這個具體例子能證明你真正理解兩者的分工，而不只是背「一個共享一個私有」。

### 一個 Java 物件從建立到回收，涉及哪些記憶體區域？

**核心答案**：類別資訊（元資料）在「方法區/元空間」；`new` 出來的物件實例在「堆」（通常先在新生代的 Eden 區分配）；指向這個物件的引用變數在「虛擬機器棧」的棧幀中；建立物件時執行的位元組碼指令位址由「程式計數器」追蹤。物件不再被引用後，由 GC 在堆中回收。所以一次物件的生命週期幾乎串起了所有主要記憶體區域。

**詳細解析**：以 `User u = new User("Tom")` 為例——首先 JVM 檢查方法區/元空間是否已載入 `User` 類別（沒有就觸發類別載入）；然後在堆的 Eden 區為 `User` 實例分配記憶體並初始化（涉及物件記憶體佈局：物件頭、實例資料、對齊填充）；`new` 表達式返回這個物件的引用位址，賦值給區域變數 `u``u` 這個引用存在當前方法棧幀的區域變數表中；執行這些動作的位元組碼指令由程式計數器逐條追蹤。之後如果 `u` 所在的方法執行完、或 `u` 被重新賦值導致物件不再有任何引用，這個物件就成為 GC 可回收的垃圾，在下次 GC 時（若一直存活則可能晉升到老年代）被回收。這個過程完整地展示了各記憶體區域如何協同工作。

**面試回答方式**：用一個具體的 `new` 例子把流程串起來——方法區載入類別、堆分配物件、棧存引用、PC 追蹤指令、GC 回收，這種「用一個物件的一生串起所有區域」的回答方式，能有力地證明你對記憶體結構的理解是連貫的整體而非孤立的區域定義。
