# 題目

JVM 怎麼判斷一個物件是不是垃圾（可以回收）？為什麼不用引用計數法？什麼是 GC Roots？

## 核心答案

JVM 用「可達性分析（Reachability Analysis）」判斷物件是否可回收——從一組稱為「GC Roots」的根物件出發，沿著引用鏈往下搜尋，能被搜尋到（可達）的物件是存活的，搜尋不到（不可達）的物件就是垃圾、可以回收。不用引用計數法是因為它無法解決「循環引用」問題（兩個互相引用但整體已無用的物件，計數永遠不為 0）。GC Roots 包括虛擬機器棧中引用的物件、靜態變數引用的物件、常數引用的物件、本地方法棧引用的物件等。

## 詳細解析

**引用計數法的問題**：引用計數法給每個物件維護一個「被引用的次數」計數器，引用它就 +1、引用失效就 -1，計數為 0 就回收。它的優點是簡單、即時，但有一個致命缺陷——**無法處理循環引用**：物件 A 引用 B、B 引用 A，如果外部不再引用 A 和 B，它們理應被回收，但因為互相引用，兩者的計數都不為 0，永遠無法被回收，造成記憶體洩漏（Memory Leak）。因此主流 JVM 不用引用計數法。

**可達性分析**：從 GC Roots 這組「一定存活」的根物件出發，遍歷所有能通過引用鏈到達的物件，這些是存活物件；剩下無法從任何 GC Root 到達的物件就是垃圾。這個方法天然解決了循環引用問題——A、B 互相引用但如果整體都無法從 GC Roots 到達，它們就會一起被判為不可達、被回收。

**哪些物件可以作為 GC Roots**：

1. **虛擬機器棧中引用的物件**：當前各執行緒方法棧幀中的區域變數所引用的物件。
2. **方法區中靜態變數引用的物件**：類別的 static 欄位引用的物件。
3. **方法區中常數引用的物件**：如字串常數池中的引用。
4. **本地方法棧中 JNI 引用的物件**：native 方法引用的物件。
5. **JVM 內部引用**：如系統類別載入器（ClassLoader）、基本資料型別對應的 Class 物件、常駐的例外物件等。
6. **被同步鎖持有的物件**、**JMXBean/JVMTI 中註冊的回呼**等。

**共同點**：GC Roots 都是「當前一定在被使用、或 JVM 運行必需」的引用起點，從它們出發能到達的物件自然都還在被使用。

## 面試回答方式

先講「用什麼方法判斷垃圾」——可達性分析（從 GC Roots 出發，不可達的就是垃圾）。接著一定要講「為什麼不用引用計數」——用循環引用這個具體反例說明引用計數的致命缺陷，這是這題最常考的對比點。GC Roots 能列出主要幾類（棧中區域變數、靜態變數、常數、native 引用）即可，不用全背關鍵是點出它們的共同本質——「都是當前一定在使用的引用起點」。這樣回答展現你理解可達性分析的原理而非死記 GC Roots 清單。

## 常見追問

### 一個物件被判定為不可達後，一定會立刻被回收嗎？

**核心答案**：不一定。一個物件被可達性分析判為不可達後，還會經歷「兩次標記」的過程才真正被回收——第一次標記後，會檢查這個物件是否有必要執行 `finalize()` 方法（是否覆寫了 finalize 且尚未執行過），如果有，物件會被放入一個佇列等待執行 finalize，在 finalize 中物件有最後一次「自救」的機會（重新讓自己被某個 GC Root 引用）；如果自救成功就不會被回收，失敗才真正回收。不過因為 `finalize` 已被廢棄且不可靠，實務上不應該依賴這個機制。

**詳細解析**：這個「緩刑」機制的存在是為了給 `finalize()` 一個執行機會，但它問題重重——`finalize` 的執行時機不確定（由一個優先級很低的 Finalizer 執行緒處理，可能很久才執行）、可能因為 finalize 執行緩慢而導致物件遲遲不被回收甚至佇列堆積、而且「自救」這種讓已死物件復活的行為會讓程式邏輯極難理解。正因如此`finalize` 在 JDK 9 被標記為 deprecated，官方明確建議用 `try-with-resources` 或 `Cleaner` 替代（見 Java 核心的 [[019-final-finally-finalize.md]]）。理解「不可達不等於立刻回收、中間還有 finalize 的緩刑」能讓你更完整地理解 GC 的判定流程，但實務上不該寫任何依賴 finalize 自救的程式碼。

**面試回答方式**：回答「不是立刻回收，還有兩次標記、finalize 的緩刑和自救機會」，但務必強調「finalize 已廢棄、不該依賴這個機制」，展現你既知道 GC 判定的完整流程細節，又有正確的實務判斷不去濫用這個過時特性。

### 什麼是「引用」的四種強度？它們如何影響 GC？

**核心答案**：Java 有四種引用強度——強引用（Strong）、軟引用（Soft）、弱引用（Weak）、虛引用（Phantom）。強引用是普通的 `Object o = new Object()`，只要強引用存在物件就絕不會被回收；軟引用在「記憶體不足時」才會被回收，適合做快取；弱引用在「下一次 GC 時」不管記憶體是否充足都會被回收，適合做規範化映射（如 `ThreadLocalMap` 的 key）；虛引用最弱，無法透過它取得物件，僅用於在物件被回收時收到一個系統通知（做資源清理追蹤）。

**詳細解析**：這四種引用強度讓開發者能更精細地控制物件與 GC 的關係，完整說明見 [[012-reference-types.md]]。核心是——可達性分析中的「可達」其實有強弱之分：透過強引用可達的物件絕不回收；只透過軟引用可達的物件，在記憶體吃緊時可回收（給了快取「記憶體不夠就讓路」的能力）；只透過弱引用可達的物件，下次 GC 就回收（適合「物件還在就用、被回收就算了」的場景）。這讓 GC 不再是簡單的「可達就留、不可達就收」的二元判斷，而是能配合不同引用強度做更有彈性的回收決策，是實作記憶體敏感快取、避免記憶體洩漏的重要工具。

**面試回答方式**：簡述四種引用的回收時機（強-絕不、軟-記憶體不足時、弱-下次 GC、虛-僅通知），並點出它們的典型用途（軟引用做快取、弱引用做規範化映射如 ThreadLocalMap key），展現你理解可達性分析中「可達」是有強弱層次的，這比只知道「強引用不回收」更全面。

### 可達性分析在 GC 時需要「Stop The World」嗎？為什麼？

**核心答案**：需要（至少在關鍵的標記階段需要短暫的 STW）。因為可達性分析要從 GC Roots 出發遍歷整個物件引用圖，這個過程中如果應用執行緒繼續運行、不斷改變物件之間的引用關係，就可能導致「本來可達的物件被漏標記成垃圾」或「引用關係在遍歷過程中變化導致分析結果不一致」，所以在確定 GC Roots（列舉根節點）等關鍵時刻必須暫停所有應用執行緒（STW），保證分析基於一個一致的物件圖快照。

**詳細解析**：STW 是 GC 繞不開的問題——為了正確性，某些階段必須凍結應用。但完全 STW 地做完整個可達性分析（尤其堆很大時遍歷耗時很長）會造成很長的停頓，這是不可接受的。所以現代收集器（CMS、G1、ZGC）花了大量精力去縮短 STW——例如用「三色標記法」配合「增量更新」或「原始快照（SATB）」等技術，讓大部分的標記工作可以和應用執行緒並發進行，只在初始標記（列舉 GC Roots）和最終重新標記等少數關鍵點做短暫 STW。ZGC、Shenandoah 更是把 STW 壓到亞毫秒級。理解「可達性分析需要 STW 保證一致性、而現代收集器努力用並發標記縮短 STW」是理解 GC 演進方向的關鍵。

**面試回答方式**：回答「需要 STW 保證物件圖一致性，否則會漏標或分析不一致」，並延伸「現代收集器用三色標記+並發標記把 STW 壓到只剩少數關鍵點」，展現你理解 STW 的必要性以及 GC 收集器演進的核心目標（縮短停頓），這能自然銜接到收集器的話題。
