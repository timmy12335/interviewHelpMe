# 題目

JVM 在容器裡有哪些特有的問題？容器感知（container awareness）解決了什麼？

## 核心答案

問題的根源是**JVM 早期會讀取「主機」的資源而非「容器」的限制**。一台 64 核 256 GB 的主機上，一個限制為 2 核 1 GB 的容器裡，JVM 會看到 64 個處理器與 256 GB 記憶體，於是：**預設堆積設成主機記憶體的 1/4（64 GB）**——遠超容器限制，一分配就被 OOM Killer 殺掉；**GC 執行緒數、ForkJoin commonPool 大小、以及各種依 `availableProcessors()` 決定的池**全都按 64 核設定，在 2 核的配額下造成嚴重的排程爭用。

**容器感知**（JDK 8u191 與 JDK 10 之後預設開啟）讓 JVM 讀取 cgroup 的限制：記憶體上限、CPU 配額（`cpu.cfs_quota_us` 除以 `cpu.cfs_period_us`）、以及 CPU 集合。於是 `Runtime.availableProcessors()` 回傳的是容器的有效核心數，預設堆積也依容器限制計算。

**但它不是萬靈丹**：CPU 限制若用 `cpu.shares`（相對權重）而非 quota，JVM 的推斷可能不準；而**堆積之外的記憶體仍然需要手動留出**——容器感知只調整堆積的預設值，不會幫你算 Metaspace、執行緒堆疊與直接記憶體。

## 詳細解析

**`availableProcessors()` 的影響範圍比想像中大**：GC 執行緒數、JIT 編譯執行緒數、`ForkJoinPool.commonPool` 的並行度、以及**所有依它設定大小的應用層執行緒池與函式庫**（Netty 的 event loop 數量、連線池的預設值）。在容器裡讀到錯誤的值，會讓整個系統的並行度設定全部錯位。**這也是為什麼「容器感知」不只是記憶體的問題**。

**CPU 限制的兩種形式行為不同**。Kubernetes 的 `limits.cpu` 對應 CFS quota——**超過配額的執行緒會被強制節流（throttled）**，表現為週期性的停頓（每 100 毫秒的週期內用完配額後就被暫停到下一個週期）。`requests.cpu` 對應 shares，只是排程權重，不會節流。**CFS 節流是容器裡延遲毛刺最常見的原因之一**，而且它在 CPU 使用率圖上看起來使用率不高（因為被節流的時間不算使用），需要看 `container_cpu_cfs_throttled_seconds_total` 這類指標才看得到。

**GC 執行緒與 CPU 配額的互動要特別注意**。GC 執行緒也消耗配額——一次年輕代回收啟動多個平行執行緒，可能瞬間用光整個週期的配額，導致**業務執行緒在 GC 結束後還被節流一段時間**。這讓 GC 的實際影響大於 GC 日誌顯示的停頓。**在 CPU 配額緊的容器裡，明確設定 `-XX:ParallelGCThreads` 與 `-XX:ConcGCThreads` 為較小的值，往往比讓 JVM 自己推斷更穩定。**

**設定的實用起點**：`-XX:MaxRAMPercentage=70`（而非寫死 `-Xmx`，讓它隨容器限制自動調整）、明確設定 `-XX:MaxMetaspaceSize` 與 `-XX:MaxDirectMemorySize`、`-XX:+HeapDumpOnOutOfMemoryError` 加上指向持久卷的路徑、以及 GC 日誌輸出到能被收集的位置。**這幾項的共同目的是：讓資源問題以可診斷的方式失敗，而不是被 OOM Killer 靜默殺掉。**

## 面試回答方式

先給根源——**JVM 早期讀主機資源而非容器限制**，並用具體數字說明後果（64 核 256 GB 主機上的 2 核 1 GB 容器，預設堆積被設成 64 GB）。強調影響**不只是記憶體**：`availableProcessors()` 決定了 GC 執行緒、JIT 執行緒、commonPool、以及所有依它設定的應用層池。接著說明容器感知讀取 cgroup 限制，並誠實指出它的邊界——**堆積之外的記憶體仍需手動留出**。加分點有兩個：**CFS 節流是容器裡延遲毛刺最常見的原因之一**，而且在 CPU 使用率圖上看不出來（要看 throttled 指標）；以及 **GC 執行緒也吃配額**，一次回收可能用光整個週期導致業務執行緒被連帶節流，所以配額緊時該明確設定 GC 執行緒數。收在設定清單並點出共同目的：**讓資源問題以可診斷的方式失敗**。

## 講稿

問題的根源是 JVM 早期會讀主機的資源而不是容器的限制。一台六十四核兩百五十六 GB 的主機上，一個限制兩核一 GB 的容器裡，JVM 會看到六十四核跟兩百五十六 GB。預設堆積設成主機記憶體的四分之一，一分配就被系統殺掉。

而且影響不只是記憶體。可用處理器數決定了 GC 執行緒數、JIT 編譯執行緒數、共用池的並行度，還有所有依它設定大小的應用層執行緒池跟函式庫。讀到錯誤的值，整個系統的並行度設定全部錯位。

容器感知讓 JVM 讀取 cgroup 的限制，這在 JDK 10 之後是預設開啟的。但它不是萬靈丹，堆積之外的記憶體仍然要手動留出。

我想特別講一個容器特有的問題。CPU 限制對應的是配額，超過配額的執行緒會被強制節流，表現為週期性的停頓。這是容器裡延遲毛刺最常見的原因之一，而且在 CPU 使用率圖上看起來使用率不高，因為被節流的時間不算使用。要看專門的節流指標才看得到。

還有 GC 執行緒也吃配額。一次回收可能瞬間用光整個週期，導致業務執行緒在 GC 結束後還被節流一段時間。

## 常見追問

### 為什麼 CFS 節流在 CPU 使用率圖上看不出來？

**核心答案**：因為使用率的計算方式是「**實際使用的 CPU 時間除以經過的時間**」，而被節流期間執行緒是**被暫停的**——那段時間既不算使用也不算等待 IO，只是消失了。所以一個被嚴重節流的容器可能顯示 50% 的 CPU 使用率，實際上它每 100 毫秒的週期裡有一半時間完全無法執行。要看的指標是 `container_cpu_cfs_throttled_periods_total` 與 `container_cpu_cfs_throttled_seconds_total`。

**詳細解析**：節流造成的延遲有一個特徵：**它是週期性的且與 CFS 週期對齊**（預設 100 毫秒）。所以延遲分布會出現「多數請求很快，少數請求恰好慢了幾十毫秒」的雙峰形態。**這與 GC 停頓造成的毛刺很像，容易混淆**——區分方式是看 GC 日誌的時間戳是否對得上，以及看節流指標。**常見的誤解是「多執行緒應用被節流是因為執行緒太多」**——實際上節流看的是**總 CPU 時間**，一個執行緒跑滿 200 毫秒與二十個執行緒各跑 10 毫秒，消耗的配額相同。所以減少執行緒數不能解決節流，只能減少總計算量或提高配額。

**面試回答方式**：先給計算方式的原因——**被節流的時間既不算使用也不算等待，只是消失了**。給出該看的指標名稱。加分點是描述節流延遲的特徵（週期性、與 100 毫秒週期對齊、雙峰分布）以及它**容易與 GC 毛刺混淆**的區分方式。最後澄清常見誤解：**節流看的是總 CPU 時間，減少執行緒數不能解決**，只能減少總計算量或提高配額。

### 為什麼建議用 MaxRAMPercentage 而不是寫死 -Xmx？

**核心答案**：因為它讓同一份映像檔**能在不同記憶體限制的環境下自動適應**——開發環境給 512 MB、正式環境給 4 GB，同一個容器映像檔不必改參數。寫死 `-Xmx` 則需要為每個環境維護不同的設定，而且很容易在調整容器限制時忘記同步調整 JVM 參數——**那正是 OOM Killer 事件最常見的成因**。

**詳細解析**：要注意 `MaxRAMPercentage` 的百分比是**相對於容器的記憶體限制**，所以留給非堆積的空間也是按比例的。**這在小容器上可能不夠**——512 MB 的容器留 30%（150 MB）給非堆積可能剛好，但 4 GB 的容器留 30%（1.2 GB）就過多了。**非堆積的用量並不與堆積成正比**：Metaspace、程式碼快取、執行緒堆疊主要取決於應用的複雜度與執行緒數，不是堆積大小。所以精確的做法是**用 NMT 量出非堆積的實際用量，再用固定值而非百分比留出空間**（例如 `-Xmx = 限制 - 500MB`）。**百分比是好的預設，量測之後的固定值才是最佳解。**

**面試回答方式**：先給主要理由——**同一份映像檔自動適應不同環境**，避免調整容器限制時忘記同步調 JVM 參數（那是 OOM Killer 事件最常見的成因）。加分點是指出它的限制：**非堆積用量不與堆積成正比**（取決於應用複雜度與執行緒數），所以百分比在小容器上可能不夠、大容器上過多。收在更精確的做法：用 NMT 量出實際非堆積用量，改用固定值留出空間。

### 容器裡的 JVM 啟動時間怎麼改善？

**核心答案**：三個層次。**類別資料共享（CDS／AppCDS）**——把類別的解析結果預先存成共享檔案，啟動時直接映射而不必重新解析，通常能省 10% 到 30% 的啟動時間，成本極低。**分層編譯的調整**——啟動階段主要跑 C1 編譯的程式碼，`-XX:TieredStopAtLevel=1` 可以讓短命的行程完全不做 C2 編譯（適合 CLI 工具，不適合長期執行的服務）。**AOT 或原生映像檔**——GraalVM 把啟動時間降到毫秒級，代價是建置時間、反射配置、以及較低的峰值吞吐。

**詳細解析**：**在 Kubernetes 環境下，啟動時間的重要性常被低估**。它影響擴容的反應速度（流量尖峰時新實例要多久才能服務）、滾動更新的總時長、以及節點故障後的恢復時間。**而且啟動慢的服務往往要設較長的 readiness probe 初始延遲，這又拉長了整個部署週期。** 實務上 AppCDS 是投資報酬率最高的一項——它不改變任何程式碼與執行期行為，只需要在建置流程中多一步產生歸檔檔案。**JDK 19 之後的自動 CDS（`-XX:+AutoCreateSharedArchive`）讓這件事更簡單**，第一次執行時自動產生，之後就自動使用。

**面試回答方式**：給三個層次並標出投資報酬率——**AppCDS 最高**（不改程式碼與執行期行為，只在建置多一步）。說明為什麼容器裡啟動時間重要：**影響擴容反應速度、滾動更新時長、故障恢復時間**，而且啟動慢會逼你設更長的 readiness 延遲，進一步拉長部署週期。加分點是提到 JDK 19 之後的自動 CDS 讓這件事更簡單。
