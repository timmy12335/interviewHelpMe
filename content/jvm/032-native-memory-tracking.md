# 題目

Java 行程的記憶體用量遠大於 `-Xmx`，多出來的是什麼？怎麼查？

## 核心答案

JVM 的常駐記憶體（RSS）由**堆積**與**七類非堆積用量**組成：**Metaspace**（類別中繼資料）、**程式碼快取**（JIT 編譯的機器碼）、**執行緒堆疊**（每個平台執行緒約 1 MB）、**GC 自身的資料結構**（卡表、記憶集、標記位圖，G1 可能佔堆積的 10%）、**直接記憶體**（NIO 的 `DirectByteBuffer`，預設上限等於 `-Xmx`）、**編譯器與符號表**、以及原生函式庫自己配置的記憶體（JNI、壓縮庫、加密庫）。

診斷的第一個工具是 **NMT（Native Memory Tracking）**：啟動時加 `-XX:NativeMemoryTracking=summary`，之後用 `jcmd <pid> VM.native_memory summary` 查看各分類的 reserved 與 committed。它能把「多出來的記憶體」歸類到上述七項之一，這一步就排除掉大部分的猜測。

**NMT 看不到的是「JVM 之外」的配置**——JNI 呼叫的原生函式庫用 `malloc` 配置的記憶體不在 NMT 的統計裡。這種情況要靠 `pmap`、`jemalloc` 的剖析、或 `perf` 等系統層工具。「NMT 加起來與 RSS 差很多」本身就是一個有用的訊號，它指向原生函式庫。

## 詳細解析

`reserved` 與 `committed` 的區別很重要：reserved 是保留的虛擬位址空間（不佔實體記憶體），committed 是實際承諾的記憶體。看 RSS 相關的問題要看 committed，看 reserved 會被巨大的數字誤導（JVM 通常保留遠大於實際使用的位址空間）。

直接記憶體是最常見的堆外洩漏來源。`DirectByteBuffer` 的原生記憶體由 `Cleaner` 在該 Java 物件被 GC 時釋放——但那個物件很小，堆積壓力可能長期不足以觸發 GC，於是堆外記憶體持續累積。症狀是「堆積使用率很低，但行程記憶體不斷成長，最後被 OOM Killer 殺掉或拋出 Direct buffer memory 的 OOM」。明確設定 `-XX:MaxDirectMemorySize` 讓它以可診斷的方式失敗，並用 `BufferPoolMXBean` 或 NMT 的 Internal 分類監控用量。

Metaspace 洩漏的典型成因是類別載入器洩漏：動態產生類別（代理、腳本引擎、熱部署）而舊的類別載入器沒有被回收——類別載入器持有它載入的所有類別，一個未被回收的載入器就是一整批類別留在 Metaspace 裡。診斷方式是看 Metaspace 用量與「已載入類別數」的趨勢（`jcmd VM.classloader_stats` 或 JFR），持續上升且完整回收後不下降就是洩漏。

**排查的整體順序是「由粗到細」**：先確認 RSS 的成長趨勢（是持續成長還是階梯式）、再用 NMT 定位到分類、再依分類選工具（堆積用 heap dump、Metaspace 用類別載入器統計、直接記憶體用 BufferPool 指標、原生用 jemalloc 剖析）。跳過前兩步直接抓堆積轉儲是最常見的浪費時間方式——如果問題在堆外，堆積轉儲裡什麼都看不到。

## 面試回答方式

先把**非堆積的七類用量**列出來，這本身就顯示了完整的心智模型。接著給 NMT 作為第一個工具（`-XX:NativeMemoryTracking=summary` 加 `jcmd VM.native_memory summary`），並強調它能把問題歸類到某一項，排除掉大部分猜測。誠實指出它的盲區——JNI 原生函式庫的 `malloc` 不在統計裡，而「NMT 總和與 RSS 差很多」本身就是指向原生函式庫的訊號。加分點有三個：`reserved` 與 `committed` 的區別（看 RSS 問題要看 committed）；直接記憶體是最常見的堆外洩漏，因為 `DirectByteBuffer` 物件太小不足以觸發 GC，症狀是「堆積很低但行程記憶體不斷成長」；以及**排查順序要由粗到細**，跳過前兩步直接抓堆積轉儲是最常見的時間浪費。

## 講稿

Java 行程的記憶體除了堆積，還有七類非堆積用量。中繼空間、程式碼快取、執行緒堆疊、GC 自己的資料結構、直接記憶體、編譯器與符號表、還有原生函式庫自己配置的記憶體。

診斷的第一個工具是原生記憶體追蹤。啟動時加一個參數，之後用 jcmd 查看各分類的保留量跟承諾量。看 RSS 相關的問題要看承諾量，保留量只是虛擬位址空間，會被巨大的數字誤導。

這一步就能把多出來的記憶體歸類到某一項，排除掉大部分猜測。

它的盲區是 JNI 呼叫的原生函式庫自己配置的記憶體不在統計裡。所以追蹤的總和跟實際 RSS 差很多，本身就是一個指向原生函式庫的訊號。

最常見的堆外洩漏來源是直接記憶體。它的原生記憶體要等對應的 Java 物件被回收才釋放，但那個物件很小，堆積壓力可能長期不足以觸發回收。症狀是堆積使用率很低，但行程記憶體不斷成長。

最後講排查順序，要由粗到細。先看 RSS 趨勢、再用追蹤定位分類、再依分類選工具。跳過前兩步直接抓堆積轉儲是最常見的時間浪費，因為問題在堆外的話那裡什麼都看不到。

## 常見追問

### 怎麼確認是不是類別載入器洩漏？

**核心答案**：看兩個指標的趨勢——**Metaspace 使用量**與**已載入類別數**。正常的應用在暖機後這兩個數字會穩定；洩漏的特徵是它們持續上升且完整回收後不下降。進一步確認用 `jcmd <pid> GC.class_stats` 或 `VM.classloader_stats`，如果看到**同一個類別被載入了很多次**（不同的載入器各載入一份），那就確定了。

**詳細解析**：典型的成因有三類。**熱部署與動態語言**——每次重新部署或編譯腳本都建立新的載入器，舊的因為某個殘留引用（`ThreadLocal`、快取、監聽器註冊）而無法回收。**動態代理與位元組碼生成**——框架為每個代理類別建立類別，如果代理是為每個實例而非每個型別生成的，數量會失控。**第三方函式庫的靜態快取**——某些函式庫用靜態 Map 快取 `Class` 物件，而 `Class` 持有它的載入器，載入器又持有它載入的所有類別——一個靜態引用可以留住一整棵物件圖。診斷的關鍵動作是抓堆積轉儲後查找「類別載入器實例的數量」，正常應該是個位數。

**面試回答方式**：給出兩個趨勢指標與判準（持續上升且完整回收後不下降），再給確認工具與最有力的證據——同一個類別被不同載入器載入了很多次。加分點是三類典型成因，特別是第三類：靜態快取持有 `Class` 物件，而 `Class` 持有載入器、載入器持有所有它載入的類別，一個靜態引用留住一整棵物件圖。收在關鍵動作：抓堆積轉儲後查類別載入器實例的數量。

### 堆積很低但行程記憶體一直漲，最可能是什麼？

**核心答案**：按可能性排序有四個。**直接記憶體**（NIO、Netty、以及使用它們的任何框架）——最常見。**原生函式庫**（壓縮、加密、影像處理、以及各種 JNI 綁定）——它們的記憶體完全在 JVM 管理之外。**執行緒數失控**——每個平台執行緒約 1 MB，執行緒洩漏會直接反映在 RSS 上。**glibc 的記憶體碎片**——多執行緒下 `malloc` 的 arena 機制可能保留大量未歸還給作業系統的記憶體。

**詳細解析**：最後一項容易被忽略但真實存在。glibc 的 malloc 為每個執行緒分配獨立的 arena（最多 8 × CPU 核心數），每個 arena 保留自己的空閒記憶體不歸還——執行緒數多的 Java 應用可能因此多佔用幾百 MB。緩解方式有兩個：設定環境變數 `MALLOC_ARENA_MAX=2` 限制 arena 數量，或者改用 jemalloc／tcmalloc（它們的碎片行為更好，而且 jemalloc 內建剖析功能可以直接找出誰在配置）。在容器裡這個差異可能決定會不會被 OOM Killer 殺掉，是一個成本極低的調整。

**面試回答方式**：按可能性排序給四項。真正的加分點是最後一項——**glibc 的 arena 機制**：每執行緒獨立 arena（最多 8 倍核心數）、各自保留空閒記憶體不歸還，執行緒多的應用可能多佔幾百 MB。給出兩個緩解方式（`MALLOC_ARENA_MAX=2` 或換 jemalloc）並指出 jemalloc 內建剖析可以直接找出配置者。收在實務價值：在容器裡這可能決定會不會被 OOM Killer 殺掉，而調整成本極低。

### NMT 的開銷有多大？可以在生產環境常駐嗎？

**核心答案**：`summary` 模式的開銷約 **5% 到 10% 的記憶體**（用來記錄統計）與很小的 CPU 開銷；`detail` 模式更高（要記錄呼叫堆疊）。`summary` 模式在生產環境常駐通常是可以接受的——它的價值在問題發生時能立刻定位，而不必等到重啟並加上參數之後再等問題重現。注意 NMT 必須在啟動時開啟，無法在執行期打開，這正是「事後才想開」會失敗的原因。

**詳細解析**：這帶出一個更普遍的維運原則：診斷能力必須在問題發生之前就準備好。GC 日誌、NMT、JFR、`HeapDumpOnOutOfMemoryError` 都屬於這一類——它們的共同特徵是開銷小、但只有預先開啟才有用。相比之下，`jstack`、`jcmd`、堆積轉儲是隨時可以執行的，不需要預先準備。把前一類都預設開啟，是一個投資報酬率很高的維運決策：平時付出百分之幾的開銷，換取問題發生時不必「等它再發生一次」。很多故障排查時間的浪費，來自於第一次發生時沒有留下足夠的證據。

**面試回答方式**：給出具體開銷（summary 約 5% 到 10% 記憶體）與明確建議（summary 可常駐），並指出關鍵限制——NMT 必須啟動時開啟，無法執行期打開。真正的加分點是提升成維運原則：診斷能力必須在問題發生前準備好，並區分「必須預先開啟」的一類（GC 日誌、NMT、JFR、OOM 時的堆積轉儲）與「隨時可執行」的一類。收在一句：很多排查時間的浪費來自第一次發生時沒有留下足夠證據。
