# 題目

`.class` 檔裡有什麼？「常數池」在其中扮演什麼角色？

## 核心答案

類別檔是一個嚴格定義的二進位格式，主要包含：**魔數**（`0xCAFEBABE`，用來確認這是類別檔）、**版本號**（決定哪個 JDK 能載入它，版本太新會拋 `UnsupportedClassVersionError`）、**常數池**、**存取旗標**、**類別與父類別索引**、**介面清單**、**欄位表**、**方法表**（每個方法的位元組碼在這裡）、以及**屬性表**（行號、區域變數表、註解、內部類別資訊等）。

**常數池是整個檔案的「符號表」**，其他所有部分都用索引指向它。它存放兩類東西：**字面值**（字串、整數、浮點數常數）與**符號引用**（類別的全名、欄位的名稱與描述子、方法的名稱與描述子）。

它的關鍵作用是**讓編譯期不必知道實際的記憶體位址**。編譯 `foo.bar()` 時，編譯器只寫下「呼叫常數池第 27 項所描述的方法」；**真正的位址要等執行期的解析階段**，由 JVM 依符號引用找到實際的方法。**這正是 Java 能做到「編譯一次、到處執行」與「動態連結」的基礎。**

## 詳細解析

**「符號引用轉直接引用」是類別載入解析階段的核心工作**。它可以是**急切的**（載入時就全部解析）或**惰性的**（第一次用到時才解析），HotSpot 選擇惰性——這讓啟動更快，也讓「引用了某個不存在的類別但從未用到」不會導致失敗。**這解釋了一個常見現象**：一個依賴缺失可能在服務跑了幾小時後、某個罕見路徑第一次被走到時才拋 `NoClassDefFoundError`。

**方法描述子是理解位元組碼的關鍵**。`(Ljava/lang/String;I)V` 表示「吃一個 String 與一個 int，回傳 void」。**描述子包含回傳型別，這解釋了為什麼 JVM 層面允許「只有回傳型別不同」的方法共存**——雖然 Java 語言不允許這樣多載，但編譯器可以利用這一點實作橋接方法（泛型擦除後為了維持多型而生成的合成方法）。

**常數池在執行期會變成「執行時常數池」**，放在 Metaspace 中。**字串常數是特例**——它們在解析時會被放進**字串常數池**（JDK 7 之後在堆積裡），這是 `intern()` 與字串字面值共享的機制所在。

**看懂類別檔的實用價值**：用 `javap -c -p -v` 可以檢視位元組碼與常數池，這在幾個場景很有用——**確認編譯器實際做了什麼**（字串串接編譯成什麼、Lambda 變成了什麼、switch 用的是 tableswitch 還是 lookupswitch）、**排查版本不相容**（看 major version）、以及**理解框架的位元組碼增強做了什麼**。**它不是日常工作需要的技能，但在「編譯器到底做了什麼」這類問題上是唯一的直接證據。**

## 面試回答方式

先列出類別檔的主要組成部分，然後把重點放在**常數池是整個檔案的符號表**——其他部分都用索引指向它，它存放字面值與符號引用。給出它的關鍵作用：**讓編譯期不必知道實際位址**，編譯 `foo.bar()` 時只寫下「常數池第 27 項所描述的方法」，位址等執行期解析——**這是「編譯一次到處執行」與動態連結的基礎**。加分點有三個：**HotSpot 的解析是惰性的**，這解釋了「依賴缺失可能在跑了幾小時後才拋 `NoClassDefFoundError`」；**方法描述子包含回傳型別**，所以 JVM 層面允許只有回傳型別不同的方法共存，編譯器藉此實作泛型的橋接方法；以及 **`javap -c -v` 是「編譯器到底做了什麼」這類問題的唯一直接證據**。

## 講稿

類別檔是一個嚴格定義的二進位格式。開頭是魔數用來確認檔案類型，然後是版本號、常數池、存取旗標、類別與父類別索引、介面清單、欄位表、方法表、還有屬性表。

常數池是整個檔案的符號表，其他所有部分都用索引指向它。它存兩類東西，字面值跟符號引用。符號引用就是類別的全名、欄位跟方法的名稱與描述子。

它的關鍵作用是讓編譯期不必知道實際的記憶體位址。編譯一個方法呼叫的時候，編譯器只寫下呼叫常數池第幾項所描述的方法。真正的位址要等執行期的解析階段，由 JVM 依符號引用找到實際的方法。這正是編譯一次到處執行跟動態連結的基礎。

有一個實務上的推論。HotSpot 的解析是惰性的，第一次用到才解析。所以一個依賴缺失可能在服務跑了幾小時之後，某個罕見路徑第一次被走到的時候，才拋出找不到類別的錯誤。

還有一個細節我覺得有意思。方法描述子包含回傳型別，所以 JVM 層面允許只有回傳型別不同的方法共存。Java 語言不允許這樣多載，但編譯器利用這一點來實作泛型擦除後的橋接方法。

## 常見追問

### 什麼是橋接方法，為什麼需要它？

**核心答案**：橋接方法是**編譯器自動生成的合成方法，用來在泛型擦除後維持多型**。例如 `class StringBox implements Comparable<String>` 實作了 `compareTo(String)`，但擦除後介面上的方法簽章是 `compareTo(Object)`——**兩者簽章不同，虛擬方法表對不上**。編譯器因此生成一個 `compareTo(Object)` 的橋接方法，內部做型別轉換後呼叫真正的 `compareTo(String)`。

**詳細解析**：橋接方法的存在有幾個可觀察的後果。**反射會看到它們**——`getDeclaredMethods()` 會回傳兩個 `compareTo`，其中一個標記為 `isBridge()` 與 `isSynthetic()`，寫反射程式碼時必須過濾掉，否則會出現「找到兩個方法不知道用哪個」的情況。**堆疊追蹤裡可能出現它們**。而且**橋接方法內部的型別轉換是隱含的 `checkcast`**——這正是「泛型擦除後仍然型別安全」的實作方式：如果有人透過原始型別傳入了錯誤的物件，`ClassCastException` 會在橋接方法裡拋出，而不是在使用值的地方，**這讓錯誤訊息的位置有時令人困惑**。

**面試回答方式**：給出定義與最清楚的例子（`Comparable<String>` 擦除後介面方法是 `compareTo(Object)`，簽章對不上所以要橋接）。加分點是三個可觀察後果：**反射會看到兩個方法**（要用 `isBridge()` 過濾）、堆疊追蹤裡會出現、以及**橋接方法內的隱含 `checkcast` 正是泛型擦除後仍型別安全的實作方式**，但它讓 `ClassCastException` 的位置有時令人困惑。

### 為什麼會出現 UnsupportedClassVersionError？

**核心答案**：因為類別檔的 **major version 高於當前 JVM 支援的版本**——也就是「用新 JDK 編譯的類別，拿到舊 JVM 上跑」。版本號的對應是 JDK 8 對應 52、JDK 11 對應 55、JDK 17 對應 61、JDK 21 對應 65（規律是 JDK 版本加 44）。錯誤訊息會直接寫出「class file version 65.0，this version of the Java Runtime only recognizes up to 61.0」。

**詳細解析**：**JVM 只做向後相容，不做向前相容**——新 JVM 能跑舊類別檔，舊 JVM 不能跑新的。這是刻意的：新版本可能引入新的位元組碼指令或屬性，舊 JVM 無法理解。**實務上這個錯誤最常見的成因是建置環境與執行環境的 JDK 版本不一致**（本機用 JDK 21 編譯、容器映像檔卻是 JDK 17），或者某個依賴的 JAR 是用更新的 JDK 編譯的。**解法有兩個層次**：對齊環境版本，或用 `--release` 編譯選項（它不只設定目標版本，還會限制只能使用該版本存在的 API——這比 `-source`／`-target` 正確得多，後者不檢查 API 的可用性，會產生「編譯通過但執行期 `NoSuchMethodError`」的問題）。

**面試回答方式**：給出成因與版本號對應規律（JDK 版本加 44）。指出 **JVM 只向後相容不向前相容**及其理由。真正的加分點是解法的兩個層次，特別是 **`--release` 比 `-source`／`-target` 正確**——後者不檢查 API 可用性，會產生「編譯通過但執行期 `NoSuchMethodError`」，這是很多人不知道的區別。

### javap 在什麼情況下真的用得上？

**核心答案**：四種。**確認編譯器的實際行為**——字串串接在 JDK 9 之後編譯成 `invokedynamic` 而非 `StringBuilder`、Lambda 編譯成什麼、`switch` 用 `tableswitch`（密集）還是 `lookupswitch`（稀疏）。**排查看似不可能的問題**——原始碼與行為不符時，位元組碼是唯一的事實來源（可能是舊的 class 檔沒被重新編譯）。**理解框架的位元組碼增強**——AOP 代理、ORM 的懶載入、覆蓋率工具都會改動位元組碼。**驗證某個最佳化是否發生**——例如常數摺疊、死碼消除。

**詳細解析**：**「原始碼與行為不符」這個場景最能體現它的價值**。典型的情況是建置系統的增量編譯出錯、或者 classpath 上有兩個版本的同一個類別（一個從 JAR 來、一個從編譯輸出來），此時**讀原始碼永遠找不到答案**。用 `javap` 反編譯實際載入的類別（可以用 `-verbose:class` 確認載入來源），一比對就清楚了。**這說明了一個更普遍的除錯原則：當推理與觀察矛盾時，要去驗證「你以為在執行的東西，是不是真的在執行」**——同樣的原則適用於「改了設定但沒生效」「部署了但版本沒更新」這類問題。

**面試回答方式**：給四種場景並各配具體例子。重點展開**「原始碼與行為不符」**——增量編譯出錯或 classpath 上有兩個版本時，讀原始碼永遠找不到答案，要用 `-verbose:class` 確認載入來源再反編譯比對。收在通用除錯原則：**推理與觀察矛盾時，先驗證「你以為在執行的東西是不是真的在執行」**，這也適用於「改了設定沒生效」「部署了版本沒更新」。
