# 題目

執行 `java MyApp` 之後到 `main` 方法被呼叫之間，JVM 做了哪些事？

## 核心答案

大致分六個階段。**第一，啟動器解析參數**——`java` 這個執行檔解析命令列，區分 JVM 參數與應用參數，並依 ergonomics 推導未指定的參數。**第二，建立 JVM**——透過 JNI 的 `JNI_CreateJavaVM` 建立虛擬機器：配置堆積（依 `-Xms` 保留位址空間）、初始化 GC 的資料結構、建立 JIT 編譯執行緒與 GC 執行緒。

**第三，載入核心類別**——bootstrap 類別載入器載入 `java.lang.Object`、`Class`、`String` 等最基礎的類別，這些有雞生蛋問題（載入類別需要 `Class` 物件，而 `Class` 本身也是類別），JVM 用特殊的初始化順序處理。第四，建立初始執行緒與類別載入器體系——建立主執行緒的 `Thread` 物件、初始化 platform 與 application 類別載入器。

**第五，載入並初始化主類別**——用 application 類別載入器載入 `MyApp`，執行連結（驗證、準備、解析）與初始化（執行 `<clinit>`，包括靜態欄位賦值與靜態區塊）。**第六，呼叫 main**——透過反射呼叫 `public static void main(String[])`。

啟動慢的成本主要落在第三與第五階段——類別載入涉及大量的檔案 IO、解析與驗證。

## 詳細解析

類別載入的成本是啟動時間的主要來源。一個 Spring Boot 應用可能載入上萬個類別，每個都要：從 JAR 讀取（IO）、解析類別檔格式、**驗證位元組碼**（確保型別安全，這一步的成本不低）、準備靜態欄位、以及解析符號引用。`-Xverify:none` 曾經被用來跳過驗證以加快啟動，但它在 JDK 13 之後被廢棄並在後續移除——因為跳過驗證會讓 JVM 失去記憶體安全的保證，這個代價太大。

**AppCDS 正是針對這一段的最佳化**：把類別的解析結果預先存成一個記憶體映射檔，啟動時直接映射進來而不必重新解析與驗證。收益通常是 10% 到 30% 的啟動時間，而且它同時省下記憶體（多個 JVM 實例可以共享同一份唯讀的歸檔）。**JDK 19 之後的 `-XX:+AutoCreateSharedArchive` 讓它幾乎零配置**——第一次執行自動產生，之後自動使用。

靜態初始化的順序是一個容易出錯的地方。類別初始化是**惰性的**——只在第一次「主動使用」時觸發（建立實例、存取靜態欄位、呼叫靜態方法、反射）。而存取一個 `static final` 的編譯期常數不會觸發初始化（那個值在編譯期就被內聯到使用點了）。這解釋了幾個常見的困惑：為什麼有時候靜態區塊沒有執行、以及為什麼改了常數的值而不重新編譯依賴方會導致舊值繼續生效。

類別初始化的鎖是死鎖的一個隱蔽來源：初始化 A 時觸發初始化 B，而 B 又需要 A——單執行緒下 JVM 用「當前執行緒已持有」的判斷避免遞迴死鎖（結果是看到部分初始化的 A），但兩個執行緒各自初始化 A 與 B 且互相依賴時，會形成真正的死鎖。這種死鎖 `jstack` 能看到（執行緒卡在類別初始化上），但成因很不直觀。解法是避免類別初始化之間的循環依賴。

## 面試回答方式

先給**六個階段**（參數解析與 ergonomics 推導、建立 JVM、載入核心類別、建立初始執行緒與載入器體系、載入並初始化主類別、反射呼叫 main），並指出啟動慢的成本主要在類別載入。展開類別載入的五個步驟（IO、解析、驗證、準備、符號解析），並提到 `-Xverify:none` 已被移除因為跳過驗證會失去記憶體安全保證。接著把 AppCDS 定位成針對這一段的最佳化——預存解析結果、直接映射、10% 到 30% 收益、且多實例可共享唯讀歸檔。加分點有兩個：存取 `static final` 編譯期常數不觸發類別初始化（值在編譯期被內聯），這解釋了「靜態區塊沒執行」與「改了常數不重新編譯依賴方就無效」；以及類別初始化的循環依賴在多執行緒下會造成真正的死鎖，`jstack` 看得到但成因不直觀。

## 講稿

大致分六個階段。第一，啟動器解析命令列參數，並依機器資源推導沒有指定的參數。第二，建立虛擬機器，配置堆積、初始化 GC 的資料結構、建立編譯執行緒。

第三，載入核心類別。這裡有雞生蛋的問題，載入類別需要 Class 物件，而 Class 本身也是類別，JVM 用特殊的初始化順序處理。第四，建立主執行緒物件跟類別載入器體系。第五，載入並初始化主類別，執行驗證、準備、解析，然後執行靜態初始化。第六，透過反射呼叫 main。

啟動慢的成本主要落在類別載入。一個 Spring Boot 應用可能載入上萬個類別，每個都要從 JAR 讀取、解析格式、驗證位元組碼、準備靜態欄位。

類別資料共享正是針對這一段的最佳化，把解析結果預先存成記憶體映射檔，啟動時直接映射進來不必重新解析驗證。通常能省一到三成的啟動時間，而且多個實例可以共享同一份唯讀歸檔。

還有一個容易困惑的點。存取一個編譯期常數不會觸發類別初始化，因為那個值在編譯期就被內聯到使用點了。這解釋了為什麼有時候靜態區塊沒有執行。

## 常見追問

### 什麼情況會觸發類別初始化？

**核心答案**：JVM 規範定義了六種「主動使用」：**建立實例**（`new`）、**存取或修改靜態欄位**（編譯期常數除外）、**呼叫靜態方法**、**反射呼叫**（`Class.forName` 且 `initialize` 為 true）、初始化子類別時先初始化父類別、以及**作為 JVM 啟動的主類別**。除此之外都是「被動使用」，不觸發初始化——例如透過子類別存取父類別的靜態欄位、宣告一個陣列型別、或存取編譯期常數。

**詳細解析**：**`Class.forName` 與 `ClassLoader.loadClass` 的差別在這裡體現**：前者預設會初始化（除非用三參數版本傳 false），後者只載入不初始化。這在 JDBC 驅動的註冊上有實際意義——舊式的 `Class.forName("com.mysql.jdbc.Driver")` 之所以能註冊驅動，正是因為它觸發了驅動類別的靜態區塊執行 `DriverManager.registerDriver`。JDBC 4.0 之後用 SPI（`META-INF/services`）自動發現，這行程式碼就不需要了——但它在很多舊程式碼裡仍然存在，成為「不知道為什麼在這裡但不敢刪」的典型。能講出這個歷史脈絡，比背出六種主動使用更有價值。

**面試回答方式**：列出六種主動使用並舉幾個被動使用的例子（透過子類別存取父類別靜態欄位、宣告陣列型別、存取編譯期常數）。真正的加分點是用 **JDBC 驅動註冊**串起整個脈絡：`Class.forName` 觸發靜態區塊執行註冊，而 JDBC 4.0 之後用 SPI 自動發現讓這行不再需要——但它在舊程式碼裡成為「不知道為什麼在這裡但不敢刪」的典型。

### 靜態初始化裡不該做什麼？

**核心答案**：四類。**耗時操作**——它發生在第一次使用該類別時，可能是在一個延遲敏感的請求路徑上，而且會阻塞所有等待這個類別的執行緒。**可能失敗的操作**——初始化拋例外會讓類別進入永久的錯誤狀態，之後所有存取都拋 `NoClassDefFoundError` 且看不到原始原因，極難診斷。依賴外部資源——讀設定檔、連資料庫、呼叫遠端，這些在啟動順序上難以控制且失敗時後果嚴重。建立需要清理的資源——執行緒池、連線，因為靜態物件的生命週期是整個 JVM，沒有明確的釋放時機。

**詳細解析**：**第二項的診斷困難值得強調**。第一次觸發初始化的執行緒會看到真正的例外（`ExceptionInInitializerError` 包著原因），但之後所有執行緒只會看到 `NoClassDefFoundError: Could not initialize class X`，完全沒有原因資訊。如果第一次的例外被吞掉或發生在啟動的早期而沒有被注意到，後續的排查會非常困難。實務上的建議是：靜態初始化保持簡單且不可能失敗；需要複雜初始化時用明確的 `init()` 方法或依賴注入容器管理，那樣失敗會發生在可控的時機並有完整的錯誤資訊。

**面試回答方式**：給四類並各配一句後果。重點展開第二項——第一次觸發的執行緒看到真正例外，之後所有執行緒只看到 `NoClassDefFoundError` 且沒有原因，如果第一次的例外被吞掉或發生在啟動早期，後續排查極其困難。收在建議：靜態初始化保持簡單且不可能失敗，複雜初始化用明確的 `init()` 或依賴注入容器管理，讓失敗發生在可控時機並有完整錯誤資訊。

### 怎麼量測與改善啟動時間？

**核心答案**：先分解再優化。**量測分解**——用 `-Xlog:class+load=info` 看載入了多少類別與載入耗時、用 `-verbose:class` 或 JFR 的啟動事件、Spring Boot 則有 `spring-boot-actuator` 的 startup 端點顯示每個 bean 的初始化耗時。**常見的三大來源**是：類別載入（數量本身）、靜態初始化與 bean 建立（應用邏輯）、以及外部連線的建立（資料庫、註冊中心）。

**詳細解析**：改善的順序應該從「減少工作量」開始——延遲初始化非必要的 bean（Spring 的 `spring.main.lazy-initialization`）、移除不用的依賴（每個 starter 都會帶來自動配置與類別載入）、以及避免在啟動時就建立所有連線（連線池可以延遲到第一次使用時再建立，代價是第一個請求較慢）。之後才是 AppCDS 這類技術手段。要注意「延遲初始化」是把成本移到第一次請求而非消除它——在需要快速擴容的場景這可能不划算（新實例看起來就緒了但第一批請求很慢）。所以正確的目標不一定是「啟動時間最短」，而是「從啟動到能穩定服務的時間最短」，這兩者的差別在 Kubernetes 的 readiness probe 設計上直接體現。

**面試回答方式**：給量測分解的工具與三大來源。改善順序**從減少工作量開始**（延遲初始化非必要 bean、移除不用的依賴、避免啟動時建立所有連線），之後才是 AppCDS。真正的加分點是指出延遲初始化是把成本移到第一次請求而非消除，快速擴容時可能不划算。收在目標的修正：不是「啟動時間最短」而是「從啟動到能穩定服務的時間最短」，這在 readiness probe 的設計上直接體現。
