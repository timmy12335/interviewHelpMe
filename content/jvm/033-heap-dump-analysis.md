# 題目

拿到一份堆積轉儲，怎麼找出記憶體被誰佔用了？「支配樹」是什麼？

## 核心答案

分析的核心概念是**保留大小（retained size）**與**淺層大小（shallow size）**的區別。淺層大小是物件本身佔的位元組；保留大小是「如果這個物件被回收，總共能釋放多少記憶體」——也就是它獨佔持有的整棵物件圖。找洩漏要看的是保留大小，因為一個 `HashMap` 本身可能只有幾十位元組，但它保留的可能是幾百 MB。

計算保留大小靠**支配樹（dominator tree）**：如果所有從 GC Roots 到物件 B 的路徑都必須經過 A，那麼 **A 支配 B**——A 被回收 B 就一定會被回收。支配樹把物件圖轉成一棵樹，每個節點的子樹總大小就是它的保留大小。這是 MAT（Memory Analyzer Tool）最核心的能力。

實務的分析順序是：**看支配樹的頂層節點**（誰保留最多）→ **看那個物件的內容與引用鏈**（為什麼它還活著）→ **找出「到 GC Root 的最短路徑」**（誰在持有它）。MAT 的「Leak Suspects」報告會自動做前兩步。

## 詳細解析

「到 GC Root 的路徑」是回答「為什麼它沒被回收」的唯一方式。一個物件佔了 500 MB 不代表有問題——問題在於它為什麼還被引用著。MAT 的「Path to GC Roots」功能會顯示引用鏈，通常一眼就能看出是誰持有（一個靜態 Map、一個 ThreadLocal、一個註冊了卻沒解除的監聽器）。查看時要排除弱引用與軟引用（MAT 有選項），因為它們不阻止回收。

比對兩份轉儲比分析一份有效得多。單一轉儲告訴你「現在什麼佔記憶體」，但很多佔用是正常的（快取、連線池）。在間隔一段時間的兩個時間點各抓一份，比對哪些類別的實例數與保留大小顯著增加，增長的那些才是嫌疑犯。MAT 支援這種比較，這是找慢洩漏最可靠的方法。

**轉儲很大時的實務問題**：幾十 GB 的轉儲無法在筆電上開啟。做法有三個：用 `jmap -histo`（不需要完整轉儲，只給每個類別的實例數與總大小）先做粗略判斷；在有足夠記憶體的機器上跑 MAT 的命令列版本產生報告再下載；或者用 `-XX:HeapDumpPath` 加上壓縮與傳輸的自動化流程。注意抓轉儲會觸發一次完整回收並停止應用數秒到數分鐘（取決於堆積大小），在生產環境要有心理準備並選在低流量時段。

常見的洩漏模式有五種，認得它們能大幅加速排查：**無上限的快取**（`HashMap` 只增不減）、**未解除的監聽器與回呼**（註冊了但物件銷毀時沒有取消註冊）、**`ThreadLocal` 未清理**（池化執行緒上累積）、類別載入器洩漏（動態產生類別而載入器無法回收）、以及內部類別隱含持有外部實例（見 Java 類別的相關題目）。看到支配樹頂層是這五種之一時，答案通常就在那裡。

## 面試回答方式

先給**保留大小與淺層大小的區別**，並用「一個 `HashMap` 本身幾十位元組但保留幾百 MB」說明為什麼要看前者。接著解釋**支配樹**的定義（所有從根到 B 的路徑都經過 A，則 A 支配 B）與它為什麼能算出保留大小。給出分析順序：看支配樹頂層 → 看內容 → 找到 GC Root 的路徑。加分點有三個：比對兩份轉儲比分析一份有效得多，因為單份無法區分「正常佔用」與「持續增長」；抓轉儲會觸發完整回收並停止應用數秒到數分鐘，生產環境要有準備；以及**五種常見洩漏模式**（無上限快取、未解除的監聽器、ThreadLocal 未清、類別載入器洩漏、內部類別持有外部實例），認得它們能大幅加速排查。

## 講稿

分析的核心概念是保留大小跟淺層大小的區別。淺層大小是物件本身佔的位元組。保留大小是如果這個物件被回收，總共能釋放多少記憶體，也就是它獨佔持有的整棵物件圖。找洩漏要看保留大小，因為一個 HashMap 本身可能只有幾十位元組，但它保留的可能是幾百 MB。

計算保留大小靠支配樹。如果所有從根到某個物件的路徑都必須經過另一個物件，那後者就支配前者。支配樹把物件圖轉成一棵樹，每個節點的子樹總大小就是它的保留大小。

我的分析順序是，先看支配樹的頂層誰保留最多，再看那個物件的內容，最後找出它到 GC Root 的最短路徑，也就是誰在持有它。

不過我想強調，比對兩份轉儲比分析一份有效得多。單一轉儲告訴你現在什麼佔記憶體，但很多佔用是正常的，像是快取跟連線池。在間隔一段時間的兩個時間點各抓一份，比對哪些類別的實例數顯著增加，增長的那些才是嫌疑犯。

還有一個實務提醒。抓轉儲會觸發一次完整回收並停止應用數秒到數分鐘，在生產環境要選低流量時段。

## 常見追問

### 為什麼有些物件的保留大小很小，但它確實是洩漏的原因？

**核心答案**：因為支配關係要求「所有路徑都經過它」。如果一個洩漏的物件同時被兩個地方引用（例如既在一個快取裡、也在一個佇列裡），那麼**兩個持有者誰都不支配它**——它會被算在共同的祖先底下，兩個持有者的保留大小都不包含它。這讓「真正的元兇」在支配樹上看起來無害。

**詳細解析**：MAT 對這種情況提供了幾個補救的視角。**「Group by class」看實例數量**——不看大小而看數量，數量異常的類別會浮現。**「Merge Shortest Paths to GC Roots」** 把大量同類物件的引用路徑合併，能看出「這一百萬個物件都是透過同一條路徑被持有的」。**還有「不可達物件」的統計**——如果轉儲中有大量不可達但尚未被回收的物件，那說明問題可能是 GC 跟不上而非洩漏。這說明支配樹是主要工具但不是唯一工具，多個視角互相印證才可靠。

**面試回答方式**：先給精確原因——支配要求「所有路徑都經過」，被兩處引用的物件誰都不支配它，所以真正的元兇在支配樹上看起來無害。給出補救視角（按類別看實例數量、合併最短路徑、不可達物件統計）。收在方法論：支配樹是主要工具但不是唯一，多個視角互相印證才可靠。

### 抓堆積轉儲有哪些方式，各有什麼影響？

**核心答案**：三種。**`jmap -dump:live,format=b,file=...`**——`live` 選項會先觸發一次完整回收只轉儲存活物件，檔案小但**停頓長**；不加 `live` 則包含尚未回收的垃圾，檔案大但**更能看出真實狀態**（例如大量待回收物件說明 GC 跟不上）。**`-XX:+HeapDumpOnOutOfMemoryError`**——OOM 發生時自動轉儲，**這是最有價值的一個設定**，因為 OOM 現場往往無法重現。**JFR 或 `jcmd GC.heap_dump`**——功能類似 `jmap`。

**詳細解析**：**選 `live` 與否是一個實際的判斷**。排查洩漏時用 `live`（只看真正存活的，訊號更乾淨）；排查「GC 跟不上」或「分配速率過高」時不用 `live`（要看到垃圾的量）。另一個常被忽略的點是**轉儲檔案本身的大小**——它大致等於堆積的已用量，32 GB 的堆積會產生 20 到 30 GB 的檔案，寫入這個檔案需要磁碟空間與時間，在容器裡尤其要注意（臨時檔案系統可能放不下，而且容器重啟後檔案就沒了）。**`HeapDumpPath` 一定要指向持久卷**，否則 OOM 時產生的轉儲會隨容器消失。

**面試回答方式**：給三種方式，並把 **`live` 選項的取捨**講清楚——排查洩漏用 `live`（訊號乾淨），排查「GC 跟不上」不用（要看到垃圾量）。強調 `HeapDumpOnOutOfMemoryError` 是最有價值的設定因為 OOM 現場無法重現。加分點是提醒轉儲檔案大小約等於堆積已用量，容器裡要有磁碟空間、而且 `HeapDumpPath` 必須指向持久卷否則隨容器消失。

### 除了找洩漏，堆積轉儲還能看出什麼？

**核心答案**：三類有價值的資訊。**記憶體浪費的模式**——大量空的或幾乎空的集合（每個 `HashMap` 即使沒有元素也佔幾十位元組，一百萬個就是幾十 MB）、重複的字串（同樣內容的多個 `String` 實例，可以用 `intern` 或字串去重解決）、以及過度包裝（`Integer` 陣列 vs `int` 陣列）。**物件的實際大小**——驗證自己對記憶體佔用的估算是否正確。**類別載入的狀況**——載入了哪些類別、哪些載入器存在。

**詳細解析**：「重複字串」在很多應用裡是可觀的浪費——從資料庫讀出的欄位名、列舉值、狀態碼，同樣的字串可能存在幾十萬份。MAT 有專門的分析可以量化這個浪費。JVM 也提供 `-XX:+UseStringDeduplication`（G1 支援）在 GC 時自動去重，通常能省下堆積的百分之幾到十幾。這說明堆積分析不只在出事時有用，它也是一個定期健檢的工具——每季度抓一次轉儲看看有沒有明顯的浪費模式，往往能找到低成本的改善機會。把診斷工具用在「還沒出事」的時候，是成熟團隊與救火團隊的差別之一。

**面試回答方式**：給三類資訊（浪費模式、實際大小驗證、類別載入狀況），並展開**重複字串**這個具體且常見的浪費——同樣的欄位名與狀態碼可能存在幾十萬份，`UseStringDeduplication` 通常能省百分之幾到十幾。收在一個有價值的立場：堆積分析不只在出事時有用，也是定期健檢的工具，而把診斷工具用在還沒出事的時候，是成熟團隊與救火團隊的差別。
