# 題目

當執行 `new Object()` 時，JVM 內部經歷了哪些步驟？物件的記憶體是怎麼分配的？

## 核心答案

`new` 一個物件大致經歷：類別載入檢查（確認類別已載入，沒有則先載入）、分配記憶體（在堆中為物件劃分空間，用指標碰撞或空閒列表）、初始化零值（把分配到的記憶體設為零值）、設定物件頭（Mark Word、類型指標等）、執行 `<init>()` 建構子（按程式碼賦真正的初始值、執行建構邏輯）。記憶體分配還涉及並發安全（用 CAS 或 TLAB 保證多執行緒分配不衝突）。

## 詳細解析

**完整步驟**：

1. **類別載入檢查**：JVM 遇到 `new` 指令時，先檢查這個類別是否已被載入、連結、初始化，如果沒有，先執行類別載入流程（見 [[007-class-loading-process.md]]）。
2. **分配記憶體**：類別載入後，物件所需的記憶體大小就已確定，JVM 從堆中劃分一塊空間。分配方式有兩種——
   - **指標碰撞（Bump the Pointer）**：如果堆記憶體是規整的（用過的和空閒的各在一邊，中間有一個指標分界），分配就是把指標往空閒方向挪動物件大小的距離。適合有整理功能的收集器（如 Serial、G1）。
   - **空閒列表（Free List）**：如果堆記憶體不規整（有碎片），JVM 維護一個記錄空閒塊的列表，分配時從中找一塊夠大的。適合標記清除類的收集器（如 CMS）。
3. **並發安全處理**：多執行緒同時分配時要避免「兩個執行緒分到同一塊記憶體」。解法有兩種——CAS 加失敗重試（保證指標更新的原子性），或 TLAB（Thread Local Allocation Buffer，每個執行緒預先在 Eden 分一小塊私有緩衝區，執行緒在自己的 TLAB 中分配不需要同步）。
4. **初始化零值**：把分配到的記憶體空間（不含物件頭）初始化為零值，這保證了物件的實例欄位在不賦初值時能直接用（如 int 是 0）。
5. **設定物件頭**：在物件頭中填入這個物件是哪個類別的實例、雜湊碼、GC 分代年齡、鎖狀態等資訊。
6. **執行 `<init>()`**：執行建構子，按程式碼把實例變數賦予真正的初始值、執行建構邏輯。到這一步物件才真正「準備好」。

## 面試回答方式

按步驟講——類別載入檢查 → 分配記憶體 → 並發處理 → 初始化零值 → 設定物件頭 → 執行建構子。重點講清楚兩個容易被追問的細節：一是「記憶體分配的兩種方式（指標碰撞 vs 空閒列表）以及它們對應什麼收集器」；二是「並發分配的兩種保證方式（CAS vs TLAB）」。這兩個點是這題的深度所在。能區分「初始化零值（分配時 JVM 做）」和「賦真正的值（建構子 <init> 做）」，展現你理解物件建立的完整流程和各步驟的分工。

## 常見追問

### 指標碰撞和空閒列表分別在什麼情況下使用？

**核心答案**：取決於堆記憶體是否「規整」，而這由使用的垃圾收集器決定。如果收集器帶「整理（compact）」功能（回收後把存活物件緊湊排列，堆是規整的、空閒空間連續），就用「指標碰撞」——分配只需移動指向空閒區起點的指標。如果收集器用「標記清除」（回收後有碎片、堆不規整），就用「空閒列表」——JVM 維護一個記錄空閒塊的列表，分配時從中挑一塊夠大的。所以 Serial、ParNew、G1 這類有整理的收集器用指標碰撞，CMS 這類標記清除的用空閒列表。

**詳細解析**：這個區別直接連結到前面 GC 演算法的知識——收集器選擇的回收演算法決定了回收後堆的形態，而堆的形態決定了分配方式。指標碰撞效率更高（只是移動指標）但要求空閒空間連續；空閒列表更靈活（能利用碎片）但分配時要查找合適的塊、效率略低。這也是「標記清除產生碎片」的又一個代價——不僅可能導致分配大物件失敗，還讓分配方式退化成較慢的空閒列表。理解這個連結能讓你把「GC 演算法 → 堆形態 → 分配方式」串成一條完整的因果鏈，展現對記憶體管理的系統性理解。

**面試回答方式**：講出「取決於堆是否規整、由收集器決定」，並對應——「有整理功能的收集器（G1/Serial）用指標碰撞、標記清除的收集器（CMS）用空閒列表」。能把它連結到「這是標記清除產生碎片的又一代價」，展現你能把 GC 演算法和物件分配串起來理解。

### TLAB 是什麼？它解決了什麼問題？

**核心答案**：TLAB（Thread Local Allocation Buffer，執行緒本地分配緩衝）是 JVM 為每個執行緒在 Eden 區預先分配的一小塊私有記憶體區域。它解決的是「多執行緒並發在堆上分配物件時的同步開銷」問題——如果所有執行緒都直接在共享的 Eden 上分配（透過移動同一個指標），就需要用 CAS 等同步機制避免衝突，高並發下同步開銷大。有了 TLAB，每個執行緒在自己的私有緩衝區中分配物件（移動自己 TLAB 的指標）完全不需要同步，只有當 TLAB 用完需要申請新的 TLAB 時才需要一次同步，大幅減少了分配時的競爭。

**詳細解析**：物件分配是極其高頻的操作（程式不停地 new 物件），如果每次分配都要和其他執行緒競爭同一個 Eden 指標，同步開銷會成為效能瓶頸。TLAB 的思路是「空間換時間 + 分散競爭」——給每個執行緒一塊私有的小地盤，執行緒在自己的地盤內分配（快速、無鎖），只有地盤用完了才去共享的 Eden 申請新的一塊 TLAB（這一步才需要同步，但頻率低得多）。這和前面 Java 併發中 `LongAdder` 的「分段累加、分散熱點」是同一種設計思想——把對共享資源的高頻競爭，轉化為對私有資源的無競爭操作。TLAB 預設開啟（`-XX:+UseTLAB`），大小可調。理解 TLAB 能解釋為什麼「絕大多數物件分配其實非常快、幾乎無同步開銷」。

**面試回答方式**：講出 TLAB 是「每執行緒在 Eden 的私有分配緩衝、讓分配無需同步、只在 TLAB 用完時才同步申請新的」，並點出它和 `LongAdder` 的「分散熱點」是同一種設計思想。能連結到「這解釋了為什麼物件分配通常很快」，展現你理解 TLAB 對分配效能的實際意義以及它體現的通用並發設計思路。

### 物件分配一定在堆上嗎？有例外嗎？

**核心答案**：不一定。透過「逃逸分析（Escape Analysis）」，如果 JVM 判斷一個物件不會「逃逸」出方法（即這個物件只在方法內部使用、不會被外部引用），就可能做「棧上分配（scalar replacement / stack allocation）」的優化——把物件的欄位拆解成基本型別直接分配在棧上（標量替換），物件隨方法棧幀彈出而自動消失，完全不需要在堆上分配、也不需要 GC 回收。這能減輕堆的分配壓力和 GC 負擔。

**詳細解析**：這是 JIT 編譯器的一項重要優化，完整說明見 [[019-escape-analysis.md]]。核心是——「物件必須在堆上」其實是一個常見的誤解，JVM 在確定物件不逃逸的前提下會做優化，最常見的是「標量替換」：把一個不逃逸的物件的各個欄位當成獨立的區域變數（標量）直接放在棧上，等於根本沒有建立這個「物件」，也就無所謂堆分配和 GC。這對減少短命小物件的 GC 壓力很有幫助。要注意逃逸分析是 JVM 的自動優化，開發者無法直接控制（但可以透過寫「不讓物件逃逸」的程式碼來讓 JVM 更容易優化）。理解「物件不一定在堆上」能修正一個常見誤解，也展現你了解 JVM 的即時優化能力。

**面試回答方式**：回答「不一定，靠逃逸分析判斷物件不逃逸時可做棧上分配（標量替換）」，並簡述原理——「把不逃逸物件的欄位拆成棧上的區域變數、隨棧幀消失、無需 GC」。能點出「這修正了『物件必在堆上』的常見誤解」，展現你了解 JVM 的進階優化，能自然銜接到逃逸分析的深入話題。
