# 題目

分代回收建立在什麼假設上？什麼樣的應用會讓這個假設失效？

## 核心答案

分代回收建立在**弱分代假設**：絕大多數物件在很年輕的時候就死亡。實測上，典型的 Java 應用有 90% 以上的物件在第一次年輕代回收時就已經不可達。這讓「複製存活物件」這個策略極其划算——複製的成本與存活量成正比，而存活量極小，所以一次年輕代回收只需要處理堆積的很小一部分。

還有一個**強分代假設**（老物件很少引用新物件），它讓跨代引用的記錄（卡表、記憶集）保持稀疏，維護成本可控。

假設失效的場景有三類。**大型長期快取**——快取裡的物件會存活很久並持續被更新，導致晉升率高、老年代快速成長，而且「老物件引用新物件」極其常見（快取的值不斷被替換），讓寫屏障與記憶集的負擔大增。**批次處理與串流**——一批資料在整個處理過程中都存活，年輕代回收時它們全部要被複製，複製成本與資料量成正比而非與垃圾成正比。**物件池**——刻意讓物件長期存活，直接違反假設。

## 詳細解析

「存活率高」是分代失效的統一表徵。年輕代回收的成本 ≈ 存活物件的複製成本；存活率從 5% 上升到 50%，成本就是十倍。症狀是年輕代回收的耗時明顯偏長（正常應該是幾毫秒到幾十毫秒），而且**晉升量大**（每次回收後老年代明顯成長），最終導致老年代回收（成本高得多）變頻繁。

批次處理的正確處理方式是調整分代比例而非對抗它。如果一批資料本來就要活到處理結束，與其讓它們在年輕代被反覆複製再晉升，不如讓它們盡快進入老年代——調小年輕代或調低晉升閾值（`-XX:MaxTenuringThreshold`）。反過來，如果批次的生命週期短於一次年輕代回收的間隔，調大年輕代讓它們在年輕代就死亡才對。判斷依據是「資料的生命週期與 GC 週期的相對長短」，這個判斷比任何通用建議都重要。

物件池在現代 JVM 上通常是反效果。它的動機是「避免配置成本」，但 JVM 的配置成本極低——TLAB 讓配置只是移動一個指標（幾個機器指令），而年輕代的回收成本只與存活量有關，**短命物件幾乎是「免費」的**。物件池反而讓物件長期存活、增加跨代引用、並引入了池本身的同步成本。唯一仍然合理的池化對象是「配置成本遠高於記憶體成本」的資源——資料庫連線、執行緒、大型直接緩衝區，而不是普通的 Java 物件。

分代假設對其他系統也成立，這說明它不只是 JVM 的技巧。作業系統的頁面替換（LRU 假設最近用過的還會被用）、CPU 快取（時間與空間區域性）、資料庫的緩衝池、CDN 的快取——它們共享同一個洞見：存取模式是有偏的，而不是均勻的。分代回收之所以有效，正是因為它把這個偏斜結構化地利用起來了。能把這個聯繫講出來，比背誦分代的實作細節更能顯示理解深度。

## 面試回答方式

先給**弱分代假設**與它的實測依據（90% 以上的物件在第一次年輕代回收時就不可達），並解釋為什麼這讓複製策略划算——複製成本與存活量成正比而存活量極小。補上**強分代假設**讓跨代引用記錄保持稀疏。接著給三類失效場景（大型長期快取、批次與串流、物件池），並用一句統一它們：「存活率高」是分代失效的統一表徵，成本隨存活率線性上升。加分點有兩個：批次處理的正確處理是調整分代比例而非對抗，判斷依據是「資料生命週期與 GC 週期的相對長短」；以及物件池在現代 JVM 上通常是反效果（TLAB 讓配置只是移動指標，短命物件幾乎免費），只有配置成本遠高於記憶體成本的資源才值得池化。收在一個聯繫：分代假設與作業系統頁面替換、CPU 快取、資料庫緩衝池共享「存取模式是有偏的」這個洞見。

## 講稿

分代回收建立在弱分代假設上，絕大多數物件在很年輕的時候就死亡。實測上典型應用有九成以上的物件，在第一次年輕代回收時就已經不可達。

這讓複製存活物件這個策略極其划算。因為複製的成本跟存活量成正比，而存活量極小，所以一次年輕代回收只需要處理堆積的很小一部分。

失效的場景有三類。大型長期快取、批次處理、還有物件池。它們的統一表徵是存活率高。存活率從百分之五上升到百分之五十，年輕代回收的成本就是十倍。

批次處理我的處理方式是調整分代比例而不是對抗它。如果一批資料本來就要活到處理結束，與其讓它們在年輕代被反覆複製再晉升，不如讓它們盡快進入老年代。反過來如果生命週期短於一次回收的間隔，就調大年輕代讓它們在那裡死掉。判斷依據是資料的生命週期跟 GC 週期的相對長短。

物件池在現代 JVM 上通常是反效果。TLAB 讓配置只是移動一個指標，短命物件幾乎是免費的。池化反而讓物件長期存活、增加跨代引用、還引入同步成本。只有配置成本遠高於記憶體成本的資源才值得池化。

## 常見追問

### 怎麼判斷分代設定該調大還是調小年輕代？

**核心答案**：看**晉升率**與**年輕代回收的耗時**。**晉升率高**（每次回收後老年代明顯成長）代表物件在年輕代還沒死就被晉升了——這時該**調大年輕代**（給它們更多時間死亡）或**調高晉升閾值**。**年輕代回收耗時長**代表存活量大——這時調大年輕代反而更糟（每次要複製更多），該考慮**調小**或接受它們的長生命週期。兩個指標指向相反方向時，說明工作負載混合了兩種模式，此時分代調整能做的有限。

**詳細解析**：「晉升率」的計算方式是：每次年輕代回收後老年代增加的量除以時間，可以直接從 GC 日誌算出。它是分代調優最重要的單一指標——理想情況下晉升率應該接近零（所有年輕物件都在年輕代死亡），實際上有一個穩定的低值是正常的。晉升率突然上升通常對應應用行為的變化（新增了一個快取、批次任務開始跑、或流量模式改變）。**要注意 G1 的分代是動態的**——它會依停頓目標自動調整年輕代大小，所以手動設定 `-Xmn` 會關閉這個自適應，通常不建議（除非有明確證據顯示自適應的選擇不好）。

**面試回答方式**：給兩個指標（晉升率、年輕代回收耗時）與各自指向的調整方向，並指出兩者指向相反時說明工作負載混合了兩種模式。加分點是說明**晉升率的計算方式**（回收後老年代增量除以時間）並定位它是分代調優最重要的單一指標，理想接近零。最後提醒 **G1 的分代是動態的**，手動設 `-Xmn` 會關閉自適應，通常不建議。

### 為什麼說物件池在現代 JVM 上通常是反效果？

**核心答案**：因為配置已經非常便宜，而池化的成本被低估了。TLAB 讓每個執行緒有自己的配置緩衝，配置一個物件只是把指標往前移（幾個機器指令，無需同步）。年輕代回收的成本只與存活量有關——死掉的物件完全不需要處理，它們的空間直接被整片回收。所以短命物件的總成本接近零。而物件池引入了：**同步成本**（借出與歸還要協調）、**長期存活的物件**（增加老年代壓力與跨代引用）、**狀態污染的風險**（歸還時忘記重置）、以及**複雜度**。

**詳細解析**：「歸還時忘記重置」是池化最陰險的 bug 來源——一個帶著上一次使用殘留狀態的物件被借出，症狀是「偶爾出現別人的資料」，在多租戶系統裡甚至是資安問題。這類 bug 極難重現，因為它取決於借出的順序。 還有一個常被忽略的點：池化的物件通常需要是可變的（要重置狀態），這與「優先使用不可變物件」的設計方向相衝突。所以池化的決策應該問三個問題：這個物件的配置成本真的高嗎（量測過嗎）？它的狀態重置真的可靠嗎？值得放棄不可變性嗎？ 三個都是「是」的情況很少見。

**面試回答方式**：先給配置便宜的機制（TLAB 讓配置只是移動指標、死物件不需要處理），再列出池化被低估的四項成本。重點展開**「歸還時忘記重置」**——症狀是偶爾出現別人的資料、在多租戶系統裡是資安問題、且極難重現因為取決於借出順序。加分點是指出池化物件通常必須可變，與「優先不可變」的方向衝突。收在三個判斷問題（配置成本真的高嗎、重置真的可靠嗎、值得放棄不可變性嗎）。

### 有沒有不分代的收集器？它們怎麼處理這個問題？

**核心答案**：有。**Epsilon**（不回收，用於測試與極短命的批次）、**原版的 ZGC 與 Shenandoah**（不分代，每次併發掃描整個堆積）。它們處理的方式是**用併發換掉分代**——既然回收與應用同時進行、不造成長停頓，那麼「每次都掃全堆」的高總工作量就不直接轉成延遲，只轉成 CPU 開銷。

**詳細解析**：但這個取捨在分配速率高時會失效——掃全堆的週期較長，越長越容易被分配速率追上，導致配置停頓或退化。這正是 ZGC 在 JDK 21 引入分代版本的原因，Shenandoah 也在推進分代支援。這個「先放棄分代、後來又加回來」的過程很有說服力地證明了分代假設的價值：即使是為了低停頓而重新設計的收集器，最終還是需要它。一般的教訓是：一個經過幾十年驗證的假設，即使新的架構暫時繞過了它，通常最後還是要回頭利用它——因為那個假設反映的是工作負載的本質特性，而不是某個實作的限制。

**面試回答方式**：列出不分代的收集器並說明它們的策略——**用併發換掉分代**，高總工作量不轉成延遲只轉成 CPU。重點放在這個取捨在分配速率高時失效，這正是 ZGC 在 JDK 21 引入分代版本的原因。真正的加分點是把這個「先放棄後加回」的過程當成論證：它證明了分代假設反映的是工作負載的本質特性而非實作限制，即使新架構暫時繞過，最終還是要回頭利用它。
