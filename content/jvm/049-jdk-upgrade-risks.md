# 題目

從 JDK 8 升級到 17 或 21，會遇到哪些相容性問題？怎麼系統地評估風險？

## 核心答案

風險分四類。**強封裝**——JDK 9 的模組化封住了內部 API（`sun.misc.Unsafe` 的部分方法、`com.sun.*`），JDK 16 之後預設拒絕非法反射存取。受影響的主要是依賴而非自己的程式碼：舊版的位元組碼函式庫（ASM、CGLIB、Javassist）不認得新的 class 檔版本，會在啟動時拋出難懂的錯誤。

**移除的元件**——JDK 11 移除了 Java EE 模組（JAXB、JAX-WS、CORBA）與 Applet，需要改用獨立的依賴；JDK 14 移除 CMS 收集器，用了 `-XX:+UseConcMarkSweepGC` 的服務會**直接無法啟動**。

**行為變更**——預設收集器從 Parallel 變 G1（吞吐可能略降、停頓改善）、預設字元集在 JDK 18 變成 UTF-8（讀寫檔案的行為可能改變）、`String` 的內部表示改變（Compact Strings）。

**參數變更**——大量 `-XX` 參數被移除或改名，而無法識別的參數會讓 JVM 拒絕啟動。

評估的方法是 **`jdeps --jdk-internals`** 掃描對內部 API 的依賴，加上在新版本上跑完整的測試套件與壓測。

## 詳細解析

「問題在依賴而非自己的程式碼」是最重要的認識。實務上的升級順序應該是：先升級所有依賴到支援新 JDK 的版本（這通常是最大的工作量，而且可能牽動 Spring Boot 這種核心框架的大版本升級），**再切換 JDK**。反過來做會遇到一堆難以歸因的錯誤——因為錯誤發生在函式庫內部，堆疊追蹤指向的位置與真正的原因無關。

測試套件的覆蓋率決定了升級的信心。升級 JDK 改變的是**執行時的基礎**，影響面極廣但大多不可見（GC 行為、JIT 決策、預設值）。單元測試能抓到 API 層面的問題，但抓不到效能與行為的變化——那需要壓測與生產流量的比對。實務上的做法是：先在非關鍵服務升級並觀察一段時間、比對關鍵指標（延遲分布、GC 停頓、記憶體用量、CPU），再推廣。

行為變更的排查最困難，因為它不會報錯。預設收集器改變後吞吐略降、預設字元集改變後某個檔案讀出亂碼、時區資料庫更新後某個日期計算的結果不同——**這些都是靜默的**。**降低風險的方式是「明確化」**：把依賴預設值的地方改成明確指定（明確指定收集器、明確指定字元集、明確指定時區），這樣升級時預設值的變化就影響不到你。這也是一個更普遍的原則：依賴預設值讓系統更簡潔，但也讓它更容易被環境變化影響。

升級的收益要說清楚才推得動：安全更新（JDK 8 已無公開更新）、GC 停頓改善、容器感知、以及能使用新版本的框架（Spring Boot 3 要求 17 起跳）。把「不升級的風險」量化成安全與供應商支援的問題，比談新語法有說服力得多。

## 面試回答方式

先給**四類風險**（強封裝、移除的元件、行為變更、參數變更）並各配一個具體例子，特別點出用了 `UseConcMarkSweepGC` 的服務在 JDK 14 之後直接無法啟動這種硬失敗。接著給最重要的認識：問題在依賴而非自己的程式碼，所以升級順序應該是**先升級所有依賴、再切換 JDK**——反過來做會遇到堆疊追蹤指向錯誤位置的難解錯誤。給出評估工具 `jdeps --jdk-internals`。加分點有兩個：行為變更最難排查因為它不會報錯（收集器變了吞吐略降、字元集變了讀出亂碼），降低風險的方式是**「明確化」**——把依賴預設值的地方改成明確指定；以及推動升級時要把「不升級的風險」量化成安全與供應商支援問題，比談新語法有說服力。

## 講稿

風險我分四類。強封裝、移除的元件、行為變更、還有參數變更。

強封裝這一類，受影響的主要是依賴而不是自己的程式碼。舊版的位元組碼函式庫不認得新的 class 檔版本，會在啟動時拋出難懂的錯誤。移除元件的部分，用了 CMS 收集器參數的服務在 JDK 14 之後會直接無法啟動，因為無法識別的參數會讓 JVM 拒絕啟動。

所以我的升級順序是先把所有依賴升級到支援新 JDK 的版本，再切換 JDK。反過來做會遇到一堆難以歸因的錯誤，因為錯誤發生在函式庫內部，堆疊追蹤指向的位置跟真正的原因無關。

最難排查的是行為變更，因為它不會報錯。預設收集器改變之後吞吐略降、預設字元集改變之後某個檔案讀出亂碼，這些都是靜默的。

降低這類風險的方式是明確化，把依賴預設值的地方改成明確指定。明確指定收集器、明確指定字元集、明確指定時區。這樣升級的時候預設值的變化就影響不到你。

## 常見追問

### jdeps 能發現哪些問題，不能發現哪些？

**核心答案**：**能發現的是靜態的依賴關係**——`jdeps --jdk-internals` 掃描 class 檔中對 JDK 內部 API 的引用，`jdeps --multi-release` 檢查多版本 JAR，並能列出每個依賴用到哪些模組。**不能發現的是動態的存取**——透過反射呼叫內部 API（字串形式的類別名在位元組碼裡只是常數，靜態分析看不出它會被拿去 `Class.forName`）、以及執行期才載入的類別。

**詳細解析**：這個限制很關鍵，因為反射正是框架存取內部 API 的主要方式。所以 `jdeps` 的乾淨結果**不代表升級沒問題**——它只排除了靜態依賴這一類。補足的方式是**實際執行**：在新 JDK 上跑完整的測試套件與壓測，並開啟 `--illegal-access=debug`（JDK 9 到 16）或觀察 `InaccessibleObjectException`。這也帶出一個普遍的認識：靜態分析與動態驗證各有盲區，兩者都需要。 靜態分析能覆蓋所有程式碼路徑但看不到動態行為；動態驗證能看到真實行為但只覆蓋跑到的路徑。升級這種高風險變更應該兩者都做。

**面試回答方式**：清楚劃出能與不能的界線（靜態依賴 vs 反射與執行期載入），並強調反射正是框架存取內部 API 的主要方式，所以 `jdeps` 乾淨不代表沒問題。給出補足方式（在新 JDK 上跑完整測試與壓測、觀察相關例外）。收在普遍認識：靜態分析覆蓋所有路徑但看不到動態行為，動態驗證看到真實行為但只覆蓋跑到的路徑，高風險變更兩者都要做。

### 升級後效能變差了，怎麼歸因？

**核心答案**：分三個可能層次逐一排除。**GC**——預設收集器可能改變了（8 的 Parallel 到 9 之後的 G1），先比對 GC 日誌的停頓分布與吞吐；如果是吞吐敏感的批次應用，明確指定 Parallel 可能就恢復了。**JIT**——新版本的編譯策略與內聯決策不同，用 JFR 或 `PrintCompilation` 比對熱點方法是否被同樣地最佳化。**函式庫實作變更**——某個 JDK 類別的實作改變了（例如 `String` 的 Compact Strings 讓非 ASCII 字串的處理多一次轉換）。

**詳細解析**：歸因的前提是有升級前的基準。如果沒有在舊版本上量測過同樣的指標，「變差了」本身就無法確認——可能是流量變了、可能是資料量長了。所以升級的第一步應該是在舊版本上建立基準（延遲分布、吞吐、GC 停頓、記憶體、CPU），升級後用同樣的方法量測比對。這聽起來理所當然，但實務上經常被跳過，結果是升級後出現任何問題都無法判斷是不是升級造成的，只能靠猜測或回滾。「先建立基準再改變」適用於所有的基礎設施變更，不只是 JDK 升級。

**面試回答方式**：給三個層次（GC、JIT、函式庫實作）與各自的比對方法。真正的重點放在前提：**歸因需要升級前的基準**，沒有基準連「變差了」都無法確認（可能是流量或資料量變了）。指出這一步實務上經常被跳過，結果是任何問題都無法歸因只能猜測或回滾。收在通用原則：**先建立基準再改變**，適用於所有基礎設施變更。

### 大版本跳躍（8 直接到 21）與逐步升級哪個好？

**核心答案**：逐步升級（8 → 11 → 17 → 21）在風險上更好，但總成本可能更高。逐步的好處是每一步的變更面小、問題容易歸因、可以在每個穩定版本上驗證後再前進；壞處是要做四次升級的驗證與部署，總工時更多，而且中間版本可能沒有實質收益（例如 11 對很多團隊只是過渡）。

**詳細解析**：實務上的折衷是「一次跳躍但分階段驗證」——在開發環境直接升到 21、依序解決編譯與啟動問題，但**在部署上分階段推進**（先非關鍵服務、再次要服務、最後核心服務），每一階段觀察足夠長的時間。這樣拿到了「一次做完」的效率，又保留了「逐步驗證」的風險控制。 關鍵的判斷是：風險應該在部署維度上分散，而不一定要在版本維度上分散。另外要注意依賴的升級路徑可能不允許跳躍——某些函式庫的大版本升級有自己的遷移步驟，那部分可能必須逐步做。所以答案往往是「JDK 一次跳、依賴逐步升、部署分階段」的組合。

**面試回答方式**：先給兩者的取捨（逐步風險低但總成本高、跳躍效率高但變更面大）。真正的加分點是提出折衷：**一次跳躍但分階段驗證**——開發環境直接升到目標版本，部署上依服務重要性分階段推進。給出核心判斷：風險應該在部署維度上分散，不一定要在版本維度上分散。最後補上依賴的升級路徑可能不允許跳躍，所以答案往往是「JDK 一次跳、依賴逐步升、部署分階段」的組合。
