# 題目

什麼是雙親委派模型？它有什麼好處？有哪些破壞雙親委派的例子？

## 核心答案

雙親委派模型是類別載入器的一種工作機制——當一個類別載入器收到載入類別的請求時，它不會自己先嘗試載入，而是先把請求「向上委派」給父載入器，父載入器再委派給它的父載入器，直到最頂層的啟動類別載入器；只有當父載入器表示自己無法載入（在它的搜尋範圍內找不到）時，子載入器才會嘗試自己載入。好處是保證了類別載入的一致性和安全性——同一個類別不會被不同載入器重複載入，且核心類別庫（如 `java.lang.Object`）總是由頂層載入器載入，無法被使用者偽造的同名類別替換。

## 詳細解析

**類別載入器的層次**：

- **啟動類別載入器（Bootstrap ClassLoader）**：載入 JVM 核心類別庫（如 `java.lang.*`、`rt.jar` 或 JDK 9+ 的核心模組），由 C++ 實作，是最頂層。
- **擴展類別載入器（Extension/Platform ClassLoader）**：載入擴展類別庫。
- **應用類別載入器（Application ClassLoader）**：載入應用程式 classpath 上的類別，是預設的類別載入器。
- 使用者還可以自訂類別載入器。

**委派流程**：載入請求先自底向上委派（App → Platform → Bootstrap），Bootstrap 嘗試載入，載入不了就退回給下一層（Platform）嘗試，還載不了才由最初的 App 自己載入。

**好處**：

1. **避免類別重複載入**：一個類別只會被載入一次（由委派鏈中能載入它的最高層載入器載入），保證了類別在 JVM 中的唯一性。
2. **保護核心類別庫安全**：即使使用者寫了一個 `java.lang.Object` 同名類別，因為委派給 Bootstrap 而 Bootstrap 會載入真正的 Object，使用者偽造的版本永遠不會被載入，防止核心 API 被惡意替換。

**類別的唯一性由「類別載入器 + 全限定名」共同決定**：兩個類別即使全限定名相同，只要是被不同的類別載入器載入的，JVM 也會認為它們是「不同的類別」（`equals`、`instanceof` 都會失敗）。這是理解類別載入器隔離的關鍵。

**破壞雙親委派的例子**：

1. **JDBC/SPI（ServiceLoader）**：核心的 JDBC 介面由 Bootstrap 載入，但具體的驅動實作在 classpath 上（該由 App 載入器載入），Bootstrap 無法向下載入 App 的類別，於是引入「執行緒上下文類別載入器（Thread Context ClassLoader）」讓核心程式碼能反過來用 App 載入器載入實作，打破了自底向上的委派。
2. **Tomcat 等 Web 容器**：為了讓多個 Web 應用能各自載入自己版本的類別庫（相互隔離、允許同名不同版本共存），每個應用有自己的 WebAppClassLoader，且優先載入自己的類別（而非先委派給父載入器），打破了雙親委派。
3. **OSGi、熱部署**：為了實現模組化和動態替換類別，也採用了更複雜的、非嚴格雙親委派的載入機制。

## 面試回答方式

先講「委派流程」——收到請求先向上委派給父載入器、父載入不了才自己載入。接著講「好處」，這是核心：避免重複載入 + 保護核心類別庫（用「使用者偽造 java.lang.Object 也無效」這個例子最有說服力）。一定要提「類別的唯一性由『載入器 + 全限定名』共同決定」這個關鍵點。破壞雙親委派的例子（JDBC/SPI、Tomcat）是進階加分點，能舉出來展現你理解這個模型不是死規則、實務中有合理的打破場景。

## 常見追問

### 為什麼 JDBC 的 SPI 機制會破壞雙親委派？它怎麼解決？

**核心答案**：因為 JDBC 的核心介面（如 `java.sql.Driver`）由 Bootstrap 類別載入器載入，但具體的資料庫驅動實作（如 MySQL 的 Driver）在應用的 classpath 上，該由 Application 類別載入器載入。問題是——Bootstrap 載入的核心程式碼需要建立/使用驅動實作類別，但按雙親委派，Bootstrap 只能向上委派、無法向下讓 App 載入器去載入這些實作類別。解決方案是引入「執行緒上下文類別載入器（Thread Context ClassLoader）」，它預設是 App 類別載入器，讓核心的 SPI 程式碼能透過它「反向」使用 App 載入器來載入驅動實作，從而打破了自底向上的委派方向。

**詳細解析**：這是一個「上層程式碼需要載入下層（classpath）的實作」的典型矛盾。雙親委派的方向是「子委派給父」，適合「下層程式碼使用上層核心類別」的正常情況；但 SPI 場景反過來了——上層的核心介面需要載入下層的具體實作，這是雙親委派無法直接支援的（父載入器看不到子載入器的搜尋範圍）。Java 用「執行緒上下文類別載入器」這個機制打破僵局——`Thread.currentThread().getContextClassLoader()` 預設返回 App 類別載入器，SPI 的核心程式碼（如 `DriverManager`、`ServiceLoader`）用這個上下文載入器去載入實作類別，相當於讓 Bootstrap 載入的程式碼「借用」了 App 載入器的能力。這是一個為了現實需求而對純粹雙親委派模型做的務實妥協。理解這個例子能讓你明白雙親委派是一個「預設的合理機制」而非「不可違背的鐵律」。

**面試回答方式**：講清楚矛盾——「核心介面由 Bootstrap 載入、但實作在 classpath 該由 App 載入、Bootstrap 無法向下載入」，再給出解法——「用執行緒上下文類別載入器讓核心程式碼反向借用 App 載入器」。能說出 `ServiceLoader`/`Thread Context ClassLoader` 這些具體機制，展現你理解 SPI 破壞雙親委派的技術細節。

### 為什麼 Tomcat 要為每個 Web 應用使用獨立的類別載入器？

**核心答案**：為了實現多個 Web 應用之間的「類別隔離」——不同的 Web 應用可能依賴同一個類別庫的不同版本（例如應用 A 用 Spring 5、應用 B 用 Spring 6），如果都用同一個類別載入器，同名類別只能載入一份、會版本衝突。Tomcat 給每個應用一個獨立的 WebAppClassLoader，讓它們各自載入自己的類別庫版本、互不干擾（因為「類別載入器 + 全限定名」決定唯一性，不同載入器載入的同名類別是隔離的）。而且 WebAppClassLoader 通常「優先載入自己的類別」（而非先委派給父），這打破了標準的雙親委派。

**詳細解析**：這是「隔離性」需求驅動的設計。在一個 Tomcat 中可能部署多個 Web 應用，它們理應像獨立的程式一樣互不影響，但它們共享同一個 JVM。如果用標準雙親委派、共享類別載入器，那麼同一個類別（如某個工具類）全 JVM 只能有一份，多個應用就無法各用自己的版本。Tomcat 的解法是每個應用一個 WebAppClassLoader，利用「不同載入器載入的同名類別是不同類別」這個特性實現隔離。同時為了讓應用能優先使用自己打包的類別庫版本（而非 Tomcat 或 JDK 提供的版本），WebAppClassLoader 對於應用自己的類別採用「優先自己載入、找不到才委派」的策略（不過對於 JDK 核心類別仍然委派給上層，保證核心安全）。這種「部分打破雙親委派以實現隔離」是應用伺服器的通用做法。理解它能幫你排查「同一個類別在不同 Web 應用行為不同」或「ClassCastException：同名類別卻不相容」這類問題。

**面試回答方式**：講出核心需求——「多應用隔離、允許同名不同版本共存」，並解釋機制——「每應用一個 WebAppClassLoader、利用不同載入器隔離、優先載入自己的類別」。能點出「這也是為什麼有時會遇到同名類別卻 ClassCastException」的實務現象，展現你理解類別載入器隔離的實際影響。

### 兩個全限定名相同的類別一定是同一個類別嗎？

**核心答案**：不一定。JVM 中判斷兩個類別是否「相同」的依據是「類別載入器 + 全限定名」兩者的組合，而不僅僅是全限定名。也就是說，即使兩個類別的全限定名完全相同（如都是 `com.example.User`），只要它們是被「不同的類別載入器」載入的，JVM 就會認為它們是兩個不同的類別——它們的 `Class` 物件不相等、`instanceof` 判斷為 false、互相賦值會拋 `ClassCastException`。

**詳細解析**：這是類別載入器隔離的核心規則，也是很多詭異問題的根源。「類別載入器 + 全限定名」共同構成類別在 JVM 中的唯一標識，這正是 Tomcat 等容器能用不同載入器隔離同名類別的原理。但這也會導致一些容易困惑的問題——例如一個物件在 Web 應用 A 中建立（用 A 的載入器載入的 User 類別），傳到共享程式庫中被轉型成 User（用另一個載入器載入的 User 類別），就會拋 `ClassCastException: com.example.User cannot be cast to com.example.User`（兩個看起來一模一樣的類別名，因為載入器不同而不相容，錯誤訊息會讓人一頭霧水）。理解這個規則，能幫你排查這類「同名類別卻不相容」的疑難雜症，也能更深刻地理解類別載入器不只是「載入類別的工具」，還是「類別命名空間隔離的邊界」。

**面試回答方式**：明確回答「不一定，判斷依據是『類別載入器 + 全限定名』」，並舉出那個經典的詭異錯誤——「ClassCastException: User cannot be cast to User（同名但載入器不同）」，展現你理解類別載入器作為「命名空間隔離邊界」的深層作用，這種能解釋詭異現象的回答很有說服力。
