# 題目

什麼是分層編譯？為什麼 Java 應用剛啟動時特別慢？

## 核心答案

HotSpot 有兩個 JIT 編譯器：**C1（client）** 編譯快、最佳化少、產生的程式碼中等；**C2（server）** 編譯慢、最佳化激進、產生的程式碼快得多。分層編譯讓程式碼**依熱度逐級晉升**，兼顧啟動速度與峰值效能。

五個層級：**Level 0** 解譯執行（最慢，但立刻可用）；**Level 1** C1 完全最佳化但不收集剖析資料（用於不會再變熱的方法）；**Level 2** C1 加基本計數；**Level 3** C1 加完整剖析（收集分支機率、型別資訊等）；**Level 4** C2 用那些剖析資料做激進最佳化。典型路徑是 **0 → 3 → 4**——先解譯、快速編譯成帶剖析的 C1 程式碼、累積足夠資料後再用 C2 重新編譯。

**啟動慢的原因**就在這條路徑上：初期全部在解譯執行（比編譯後慢 10 到 100 倍），編譯需要時間也需要 CPU（編譯執行緒與業務執行緒競爭），而 C2 的激進最佳化必須等**足夠的剖析資料累積**才能做。**所以「預熱」不是玄學，它是等待這條晉升路徑走完。**

## 詳細解析

**剖析資料是 C2 最佳化的基礎**，這解釋了為什麼 C2 不能一開始就編譯。它的核心最佳化——**內聯、去虛擬化、分支預測、逃逸分析**——全都依賴「實際執行時的行為模式」。例如一個介面呼叫，如果剖析顯示它 99% 的時候都是同一個實作，C2 就可以**單型內聯**（直接內聯那個實作並加一個型別檢查），這是巨大的收益；但沒有剖析資料時它只能保守地留一個虛擬呼叫。

**編譯是樂觀的，所以需要去最佳化**。C2 基於「目前為止的觀察」做假設（這個分支從沒走過、這個型別總是同一個），假設被違反時就**去最佳化**——丟棄編譯後的程式碼、退回解譯執行、重新收集剖析資料再編譯。**這意味著預熱不是一次性的**：一個新的請求類型走了從未走過的分支，可能觸發去最佳化與重新編譯，造成延遲毛刺。**這是壓測時「暖機後仍偶爾有毛刺」的常見原因。**

**程式碼快取滿了會停止編譯**。JIT 產生的機器碼放在程式碼快取（預設上限可能是 240 MB），滿了之後 JVM 會停止編譯並印出警告，**所有新的熱點都只能解譯執行，效能斷崖式下降**。長時間執行的大型應用（尤其是大量使用動態代理、Lambda、腳本引擎的）可能撞到這個上限。**監控 `code cache` 的使用率是一項值得做但常被忽略的事。**

**針對啟動優化的手段**：`-XX:TieredStopAtLevel=1` 讓短命行程只用 C1（省掉 C2 的編譯成本，適合 CLI 工具與測試，**不適合長期服務**）；**AppCDS** 省掉類別解析；**AOT／原生映像檔**徹底繞過 JIT。**而在服務端最實用的往往是「預熱流量」**——上線後先送一批合成流量把熱路徑跑熱，再放真實流量進來，這在 Kubernetes 裡可以透過 readiness probe 的邏輯實現。

## 面試回答方式

先給 **C1 與 C2 的分工**（編譯快最佳化少 vs 編譯慢最佳化激進），再給五個層級與典型路徑 **0 → 3 → 4**。啟動慢的原因要三點齊全：**解譯比編譯後慢 10 到 100 倍、編譯本身消耗 CPU、C2 必須等剖析資料累積**。接著展開**為什麼 C2 需要剖析資料**——內聯、去虛擬化、分支預測都依賴實際行為，例如介面呼叫 99% 是同一個實作時可以單型內聯，這是巨大收益。加分點有三個：**編譯是樂觀的，假設被違反會去最佳化並退回解譯**，所以預熱不是一次性的，新的請求類型可能觸發重新編譯造成毛刺；**程式碼快取滿了會停止編譯導致效能斷崖**，值得監控；以及服務端最實用的手段是**預熱流量**而非調參。

## 講稿

HotSpot 有兩個 JIT 編譯器。C1 編譯快、最佳化少。C2 編譯慢、最佳化激進、產生的程式碼快得多。分層編譯讓程式碼依熱度逐級晉升，兼顧啟動速度跟峰值效能。典型路徑是先解譯執行、再快速編譯成帶剖析的 C1 程式碼、累積足夠資料之後再用 C2 重新編譯。

啟動慢的原因就在這條路徑上。初期全部在解譯，比編譯後慢十到一百倍。編譯本身需要時間也需要 CPU，編譯執行緒跟業務執行緒競爭。而且 C2 的激進最佳化必須等足夠的剖析資料累積。

為什麼 C2 需要剖析資料？因為它的核心最佳化全都依賴實際執行的行為。比如一個介面呼叫，如果剖析顯示九成九的時候都是同一個實作，C2 就可以直接內聯那個實作再加一個型別檢查，收益很大。沒有資料的話它只能保守地留一個虛擬呼叫。

還有一點很重要，編譯是樂觀的。假設被違反的時候會去最佳化，丟棄編譯後的程式碼退回解譯。所以預熱不是一次性的，一個新的請求類型走了從沒走過的分支，可能觸發重新編譯造成延遲毛刺。

## 常見追問

### 什麼是去最佳化？它什麼時候發生？

**核心答案**：去最佳化（deoptimization）是**丟棄已編譯的機器碼、把執行狀態轉回解譯器繼續執行**的過程。它發生在 JIT 的樂觀假設被違反時：**未走過的分支第一次被走到**（uncommon trap）、**單型內聯的呼叫點出現了第二種型別**、**類別階層改變**（載入了一個新的子類別，讓原本的去虛擬化失效）、以及**空值或例外的假設被打破**。

**詳細解析**：去最佳化的成本不只是「退回解譯」——它需要**重建解譯器的堆疊框架**（從編譯後的暫存器狀態還原出解譯器需要的區域變數表），這個過程要在安全點進行，而且該方法之後要重新累積剖析資料才能再次被 C2 編譯。**在延遲敏感的系統上，去最佳化造成的毛刺是真實的**。可以用 `-XX:+PrintCompilation` 或 JFR 的編譯事件觀察它的發生頻率。**實務上的緩解是「讓熱路徑的行為穩定」**——避免在熱路徑上出現罕見的分支、避免同一個呼叫點處理多種型別（多型分派過多會導致無法內聯）、以及在預熱時盡量涵蓋所有的請求類型。

**面試回答方式**：先給定義與四種觸發情況。加分點是說明**成本不只是退回解譯**——還要重建解譯器堆疊框架、要在安全點進行、之後要重新累積剖析資料。給出觀察手段（`PrintCompilation` 或 JFR 編譯事件）。收在可操作的緩解：**讓熱路徑的行為穩定**（避免罕見分支、避免同一呼叫點多型過度、預熱涵蓋所有請求類型）。

### 為什麼有些方法無法被內聯？

**核心答案**：四個常見原因。**方法太大**——超過 `-XX:MaxInlineSize`（預設 35 位元組碼）的非熱方法、或超過 `FreqInlineSize`（預設 325）的熱方法不會被內聯。**呼叫點是多型的**——同一個呼叫點出現了三種以上的實作型別（megamorphic），JIT 無法選一個內聯。**遞迴太深**或**內聯後總大小超過限制**。**方法是原生的或含有無法處理的位元組碼**。

**詳細解析**：**內聯是 JIT 最重要的最佳化，因為它是其他最佳化的前提**——內聯之後，跨方法的常數傳播、逃逸分析、死碼消除才成為可能。所以「方法無法內聯」的影響遠大於一次呼叫的開銷。**這給出一個實用的編碼建議：熱路徑上的方法要小**，把大方法拆成「一個小的熱路徑方法 + 一個大的冷路徑方法」（JIT 可以內聯前者），這是 JDK 內部大量使用的模式（例如很多方法把慢路徑抽成 `xxxSlow()`）。**多型的問題則提示：在極熱的路徑上，過度的介面抽象是有成本的**——不是說不該用介面，而是知道這個成本存在，並在量測顯示它是瓶頸時考慮調整。

**面試回答方式**：給四個原因並帶上具體的參數與預設值。真正的加分點是指出**內聯是其他最佳化的前提**（常數傳播、逃逸分析、死碼消除都要先內聯），所以無法內聯的影響遠大於一次呼叫開銷。收在兩個可操作的建議：**熱路徑方法要小**（把慢路徑抽成獨立方法，這是 JDK 內部的常用模式），以及**極熱路徑上的過度介面抽象有成本**，量測顯示是瓶頸時才調整。

### 怎麼為服務做預熱？

**核心答案**：目標是**在真實流量進來之前，讓熱路徑走完 0 → 3 → 4 的晉升**。做法有三種。**合成流量**——啟動後對自己發送一批代表性的請求（涵蓋主要的端點與分支），跑到編譯穩定後才把 readiness probe 標成就緒。**流量漸進**——先接收少量真實流量（負載平衡器的慢啟動或權重漸增），讓它自然預熱。**AppCDS 加 AOT**——減少需要預熱的量，但無法完全取代預熱（C2 的剖析仍然需要真實執行）。

**詳細解析**：**預熱流量的品質比數量重要**。跑一萬次同一個簡單請求，只會讓那一條路徑變熱；真正需要的是**涵蓋主要分支與型別組合**的代表性流量，否則上線後遇到未涵蓋的路徑仍然會有毛刺與去最佳化。實務上可以錄製一段生產流量作為預熱腳本。**要注意預熱也有成本**——它延長了實例就緒的時間，在需要快速擴容的場景下可能是負面的。**所以預熱的程度應該與「啟動慢造成的損失」對比決定**：如果擴容是為了應對突發流量，過長的預熱反而讓擴容跟不上。**這個「預熱時間 vs 擴容反應速度」的取捨，是雲原生環境下 JVM 應用的一個真實難題**，也是原生映像檔在無伺服器場景勝出的原因。

**面試回答方式**：給三種做法並說明目標是走完晉升路徑。重點放在**預熱流量的品質比數量重要**——要涵蓋主要分支與型別組合，否則上線後遇到未涵蓋路徑仍會毛刺；實務上可錄製生產流量。真正的加分點是指出**預熱本身有成本**：它延長就緒時間，在需要快速擴容時是負面的，所以**「預熱時間 vs 擴容反應速度」是雲原生下的真實取捨**，也是原生映像檔在無伺服器場景勝出的原因。
