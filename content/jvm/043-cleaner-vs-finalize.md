# 題目

`finalize()` 為什麼被廢棄？`Cleaner` 是怎麼運作的，該怎麼用？

## 核心答案

`finalize` 的問題有五個，任何一個單獨看都足以讓它不可用。**執行時機不確定**——只保證在物件被回收前執行，但不保證何時、甚至**不保證會執行**（JVM 退出時可能根本不跑）。**讓物件多活一輪**——有 `finalize` 的物件在第一次被判定不可達時不會被回收，而是放進佇列等待 finalizer 執行緒處理，至少要經過兩次 GC 才能真正回收。**單一 finalizer 執行緒**——所有物件的 finalize 排隊執行，一個慢的或卡住的會拖住全部，造成記憶體無法回收。**例外被吞掉**——finalize 拋出的例外會被忽略，物件可能處於半清理狀態。**物件復活**——finalize 裡可以把 `this` 存到某個靜態欄位讓物件重新可達，這讓 GC 的語意變得極其複雜。

`Cleaner`（JDK 9）是替代品：它基於**幻象引用（PhantomReference）**，註冊一個「當某個物件變得不可達時要執行的清理動作」。關鍵設計是清理動作不能持有被監控物件的引用（否則它永遠不會不可達）——這在 API 上強制了「清理邏輯與物件狀態分離」。

但兩者的正確答案都是「不要依賴它們」——資源釋放應該用 `try-with-resources` 明確進行，`Cleaner` 只是**最後的安全網**。

## 詳細解析

**「安全網」這個定位是關鍵**。`Cleaner` 的正確用法是：類別實作 `AutoCloseable` 讓使用者用 try-with-resources 明確關閉（正常路徑），同時註冊一個 Cleaner 以防有人忘記關（兜底）。JDK 自己就是這樣做的——`DirectByteBuffer`、`FileInputStream`（JDK 9 之前用 finalize，之後改用 Cleaner）都是這個模式。單靠 Cleaner 的問題與 finalize 相同：時機不確定，資源可能長時間不被釋放。

**幻象引用為什麼適合這件事**：它是四種引用中最弱的一種，**`get()` 永遠回傳 null**——所以持有幻象引用不可能意外地讓物件復活。它的用途純粹是「被通知物件已經不可達」：當物件變得只有幻象引用可達時，JVM 把該引用放進註冊的 `ReferenceQueue`，清理程式從佇列取出並執行動作。這個設計直接消除了 finalize 的「物件復活」問題。

**Cleaner 的實作細節值得知道**：每個 `Cleaner` 實例有自己的執行緒（而 finalize 是全 JVM 共用一個），所以一個慢的清理動作只影響自己的 Cleaner。而且它的執行緒是守護執行緒——**JVM 退出時不保證清理會執行**，這一點與 finalize 相同。所以「進程結束時必須做的清理」不能靠它，要用 shutdown hook（而 shutdown hook 在 `kill -9` 或 JVM 崩潰時同樣不會執行——沒有任何機制能保證清理一定發生）。

這個主題的一般教訓是：不要把資源的正確性建立在 GC 上。GC 管的是記憶體，而檔案控制代碼、socket、原生記憶體、資料庫連線都是**與記憶體無關的資源**，它們的生命週期應該由明確的作用域控制。try-with-resources 之所以重要，正是因為它把資源的生命週期綁在語法結構上，而不是綁在記憶體壓力上。

## 面試回答方式

先給 `finalize` 的**五個問題**（時機不確定且不保證執行、讓物件多活一輪至少兩次 GC、單一執行緒排隊、例外被吞、物件可復活），任何一個都足以讓它不可用。接著給 `Cleaner` 的機制——**基於幻象引用**，而幻象引用的 `get()` 永遠回傳 null，所以**不可能讓物件意外復活**，這直接消除了 finalize 最麻煩的問題。強調 API 上的強制：清理動作不能持有被監控物件的引用。然後給最重要的定位：兩者的正確答案都是「不要依賴」——正常路徑用 try-with-resources 明確關閉，Cleaner 只是防止有人忘記的安全網，JDK 自己就是這個模式。收在一般教訓：不要把資源的正確性建立在 GC 上，GC 管記憶體而檔案控制代碼與連線是與記憶體無關的資源。

## 講稿

finalize 有五個問題，任何一個單獨看都足以讓它不可用。執行時機不確定，甚至不保證會執行。有 finalize 的物件至少要經過兩次垃圾回收才能真正被回收。所有物件的 finalize 排在同一個執行緒上，一個卡住就拖住全部。拋出的例外會被吞掉。還有物件可以在 finalize 裡把自己存回靜態欄位而復活。

Cleaner 是替代品，它基於幻象引用。幻象引用的取值方法永遠回傳 null，所以持有它不可能意外讓物件復活，這直接消除了最麻煩的那個問題。它的用途純粹是被通知物件已經不可達。

而且 API 上有一個強制的設計，清理動作不能持有被監控物件的引用，否則那個物件永遠不會變成不可達。這在介面上就強制了清理邏輯跟物件狀態分離。

但我想強調，兩者的正確答案都是不要依賴它們。正常路徑應該用 try-with-resources 明確關閉，Cleaner 只是防止有人忘記的安全網。JDK 自己就是這個模式。

一般的教訓是，不要把資源的正確性建立在垃圾回收上。垃圾回收管的是記憶體，而檔案控制代碼、連線這些是跟記憶體無關的資源。

## 常見追問

### 四種引用各自的適用場景是什麼？

**核心答案**：**強引用**是預設，物件可達就不回收。**軟引用**在記憶體不足時才被回收，理論上適合快取但實務上不建議（見下一題）。**弱引用**在下一次 GC 就被回收，適合「快取的鍵」與「不想阻止物件被回收的關聯」——`WeakHashMap` 用它，`ThreadLocalMap` 的 key 也用它。**幻象引用**的 `get()` 永遠是 null，唯一用途是被通知物件已不可達以執行清理。

**詳細解析**：弱引用的典型正確用法是「附加資訊」——想為某些物件附加中繼資料（例如一個 `Map<Object, Metadata>`），但不希望這個 Map 阻止那些物件被回收。用 `WeakHashMap` 就能做到：物件被回收時對應的條目自動消失。但要注意 `WeakHashMap` 的值仍是強引用——如果值直接或間接引用了鍵，那個鍵就永遠不會被回收，這是一個經典的洩漏陷阱（解法是把值也包成弱引用，或確保值不引用鍵）。這個「弱鍵強值造成洩漏」的細節，是判斷一個人有沒有實際用過弱引用的好問題。

**面試回答方式**：給四種引用的回收時機與適用場景。重點展開弱引用的正確用法是「附加資訊」，用 `WeakHashMap` 為物件附加中繼資料而不阻止回收。加分點是指出經典陷阱：`WeakHashMap` 的值仍是強引用，值若引用了鍵則鍵永遠不會被回收，解法是把值也包成弱引用或確保值不引用鍵。

### 為什麼不建議用軟引用做快取？

**核心答案**：因為回收時機完全由 JVM 決定，而它的策略與快取的需求不符。軟引用在「記憶體不足時」被回收，但這個判斷是全域的、粗糙的——它會**一次清掉大量軟引用**（因為記憶體壓力是全域狀態），而不是按快取的價值（最近使用、命中頻率）選擇性淘汰。結果是**快取要嘛全滿要嘛被清空**，命中率極不穩定。

**詳細解析**：還有兩個具體問題。**它會延後 OOM 但讓 GC 更頻繁**——JVM 在拋 OOM 前必須先清掉所有軟引用，這意味著每次接近記憶體上限時都要做一次完整回收加軟引用清理，成本很高且發生在系統已經吃緊的時候。**回收行為與收集器相關**——不同的收集器對軟引用的處理策略不同，換收集器可能讓快取行為完全改變。正確的做法是用有明確容量與淘汰策略的快取（Caffeine 的 `maximumSize` 或 `maximumWeight`），讓快取的大小是一個可預測、可監控的設計決策，而不是 GC 的副作用。這也讓容量規劃成為可能——軟引用快取的實際大小是無法預測的。

**面試回答方式**：核心是回收時機由 JVM 決定且策略與快取需求不符——它一次清掉大量軟引用而非按價值淘汰，導致命中率極不穩定。加分點是兩個具體問題：清理發生在系統已經吃緊時且成本很高、**行為與收集器相關**換收集器就變。收在正確做法：用有明確容量與淘汰策略的快取，讓快取大小是可預測可監控的設計決策而不是 GC 的副作用，這也讓容量規劃成為可能。

### 資源洩漏怎麼排查？

**核心答案**：依資源類型選工具。**檔案控制代碼與 socket**——`lsof -p <pid>` 看開啟的描述符，數量持續成長且集中在同一類就是洩漏；也可以用 `-XX:+PrintGCDetails` 之外的作業系統層指標監控。**資料庫連線**——連線池的指標（活躍數、等待數）是最直接的證據，連線池通常也提供「洩漏偵測」（HikariCP 的 `leakDetectionThreshold` 會在連線被持有超過閾值時印出取得它的堆疊）。**原生記憶體**——NMT 加 jemalloc 剖析。

**詳細解析**：HikariCP 的洩漏偵測是一個值得學習的設計：它在借出連線時記錄堆疊，超過閾值還沒歸還就把那個堆疊印出來——直接告訴你「是這段程式碼借了連線沒還」，而不是只說「連線不夠了」。這個「在取得資源時記錄來源，在超時時報告」的模式可以用在任何池化資源上，**成本只在異常時才付**（正常歸還就丟棄記錄）。更根本的預防是讓資源無法被忘記——用 try-with-resources、用「借出即回調」的 API 形式（`template.execute(conn -> ...)` 而非 `getConnection()`），**讓使用者沒有機會忘記歸還**。這與前面說的「用 API 設計消除犯錯可能」是同一個原則。

**面試回答方式**：按資源類型給工具（`lsof`、連線池指標與洩漏偵測、NMT）。重點展開 **HikariCP 洩漏偵測的設計**——借出時記錄堆疊、超時就印出來，直接指出是哪段程式碼沒歸還，而且**成本只在異常時才付**。收在更根本的預防：**讓資源無法被忘記**——try-with-resources 與「借出即回調」的 API 形式（`template.execute(conn -> ...)` 而非 `getConnection()`），這是「用 API 設計消除犯錯可能」的同一個原則。
