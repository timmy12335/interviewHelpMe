# 題目

MVCC（多版本並發控制）是什麼？它是怎麼實現「讀不加鎖、寫不阻塞讀」的？

## 核心答案

MVCC 是 InnoDB 實現「高並發下讀寫互不阻塞」的核心機制——它讓每一行資料保留「多個歷史版本」（透過 undo log 形成版本鏈），不同的交易根據自己的「時間點」，讀取「屬於自己應該看到的那個版本」，而不是都搶著讀同一份「當前最新資料」。這樣一來，「讀（快照讀，如普通 SELECT）」完全不需要加鎖——它只是去讀某個歷史版本，不會和正在進行的「寫」操作衝突；「寫」也不會被「讀」阻塞。實現的核心組件是——每行資料的隱藏欄位（記錄交易 ID、指向 undo log 的指標）、undo log 形成的**版本鏈**、以及每個交易開始時建立的 **ReadView**（記錄「當前有哪些交易還沒提交」，用來判斷某個版本對自己是否可見）。

## 詳細解析

**每行資料的隱藏欄位**：InnoDB 的每一行資料除了使用者定義的欄位，還有幾個隱藏欄位——`DB_TRX_ID`（記錄最後一次修改這行資料的交易 ID）、`DB_ROLL_PTR`（回滾指標，指向這行資料在 undo log 中的「上一個版本」）。

**版本鏈**：每次修改一行資料，舊版本不會被直接覆蓋丟棄，而是被記錄到 undo log，並透過 `DB_ROLL_PTR` 把「新版本」和「舊版本」串起來，形成一條「版本鏈」——從最新版本，透過指標一路連到最舊的版本。

**ReadView（讀視圖）**：每個交易在「需要讀取資料」的某個時刻（可重複讀級別下是交易開始時、讀已提交級別下是每次 SELECT 時），會建立一個 ReadView——它記錄了「當前系統中，有哪些交易 ID 是『活躍的』（還沒提交）」。有了這個 ReadView，交易讀取某一行資料時，就可以判斷「這行資料的哪個版本，是我應該看到的」——規則大致是：如果某個版本是由「已經提交、且是在我的 ReadView 建立之前就已提交」的交易修改的，這個版本對我可見；如果是「還沒提交、或是在我的 ReadView 之後才開始的交易」修改的，這個版本對我不可見，要沿著版本鏈往前找更舊的版本，直到找到一個「可見」的。

**為什麼能「讀不加鎖、寫不阻塞讀」**：因為「讀」（快照讀）只是「沿著版本鏈找一個屬於自己的歷史版本」，這個過程完全不需要和「正在寫」的交易競爭同一把鎖——寫交易繼續修改它的（產生新版本），讀交易讀它認為該讀的舊版本，兩者互不干擾。這就是 MVCC 相比「用鎖保護讀寫」的巨大優勢——大幅提升了並發讀寫的效能。

## 面試回答方式

先講「MVCC 要解決的問題」——傳統用鎖保護讀寫、讀寫會互相阻塞、並發效能差，MVCC 用「多版本」讓讀寫不衝突。核心要講清三個組件——「隱藏欄位(交易ID+回滾指標)、版本鏈(undo log 串起的歷史版本)、ReadView(判斷哪個版本對我可見)」。能講出「讀是沿版本鏈找屬於自己的歷史版本、不用和寫競爭鎖」這個核心原理。這是一道深度題，能講清楚版本鏈和 ReadView 如何配合判斷可見性，展現你理解 MVCC 不是抽象概念而是有具體機制支撐的。

## 常見追問

### 可重複讀和讀已提交在 MVCC 的實現上有什麼具體差異？

**核心答案**：核心差異在「ReadView 的建立時機」——**讀已提交（RC）**：「每一次 SELECT」都重新建立一個新的 ReadView，所以每次讀取都是基於「當下最新的活躍交易列表」判斷可見性，這就是為什麼 RC 下同一交易內多次讀取可能得到不同結果（因為每次讀的 ReadView 不同、能看到的已提交資料範圍也不同）。**可重複讀（RR）**：只在「交易第一次讀取資料時（第一次執行查詢語句時）」建立一次 ReadView，之後這個交易內的所有查詢都「複用」這同一個 ReadView，所以不管中間有多少其他交易提交了修改，這個交易看到的始終是「它第一次查詢時那一刻的快照」，保證了同一交易內多次讀取結果一致（可重複讀）。

**詳細解析**：這題把「隔離級別的行為差異」和「MVCC 的具體機制」精確地對應起來，是這批題目中很能展現深度的一環。理解的關鍵是——ReadView 本質上是「一份『此刻誰還沒提交』的快照名單」，這份名單一旦建立，就決定了「接下來用這份名單判斷可見性時，能看到哪個時間點之前的已提交資料」。RC 級別選擇「每次查詢都重新拍一張快照」——這意味著每次查詢，都會用「當下最新」的已提交資料狀態去判斷可見性，如果兩次查詢之間，有其他交易提交了修改，第二次查詢的 ReadView 是全新的、會把這個新提交的修改也算作「可見」，於是讀到了不同的結果（不可重複讀（Non-Repeatable Read））。RR 級別選擇「只在交易一開始（更精確地説，是交易內第一次執行查詢時）拍一張快照，之後就一直用這張舊快照」——這意味著不管交易執行過程中外面發生了什麼提交，這個交易的視角始終「凍結」在它第一次查詢的那個時間點，所以同一交易內反覆讀同一行資料，結果永遠一致（因為判斷可見性用的是同一份 ReadView）。這個「快照建立一次 vs 每次都建立」的差異，正是 RC 和 RR 在 MVCC 實現上的根本區別，也精確地解釋了「為什麼 RR 能保證可重複讀、RC 不能」這個行為差異的技術原因，而不只是停留在「RR 級別更高」這種表面理解。

**面試回答方式**：講出「核心差異是 ReadView 的建立時機——RC 每次 SELECT 都重建 ReadView(每次都用最新的活躍交易名單判斷可見性、所以能看到中途提交的修改、導致不可重複讀)；RR 只在交易第一次查詢時建一次 ReadView、之後整個交易複用這同一份(視角凍結在那一刻、所以多次讀結果一致)」。展現你能把隔離級別的行為差異精確對應到 MVCC 的具體實現機制，而非停留在表面描述。

### MVCC 能完全避免加鎖嗎？什麼時候還是需要加鎖？

**核心答案**：不能完全避免——MVCC 只解決了「快照讀（普通的 SELECT，不帶 FOR UPDATE/LOCK IN SHARE MODE）」不用加鎖的問題；但「當前讀」（如 `SELECT ... FOR UPDATE`、`SELECT ... LOCK IN SHARE MODE`、以及所有的 `UPDATE`、`DELETE`、`INSERT`）仍然需要加鎖——因為這些操作的語意是「要讀取或修改『當前最新』的資料，並確保這個過程中不會有其他交易同時修改它」，這和 MVCC「讀一個歷史快照」的思路是矛盾的（你不能修改一個歷史版本，必須基於最新資料操作，且操作期間要防止別人插手）。所以完整的圖像是——「快照讀」用 MVCC（不加鎖、高並發）、「當前讀」用「鎖 + MVCC 配合」（如 next-key lock 防止幻讀（Phantom Read），同時也要讀到最新的、一致的資料）。

**詳細解析**：這題澄清一個常見的誤解——「用了 MVCC 就完全不用鎖了」。實際上 MVCC 和鎖是「互補」的機制，各自解決不同場景的問題。快照讀（Snapshot Read）——就是普通的 `SELECT ... `，這種讀取的語意是「給我看資料、我不打算修改它」，MVCC 完美適用：讀交易只需要沿著版本鏈找到自己該看的版本，全程不需要和任何其他交易競爭鎖，這是 MVCC 帶來的核心效能提升。當前讀（Current Read）——包括 `SELECT ... FOR UPDATE`（讀取並準備修改，通常用於「先查詢再更新」的業務邏輯，需要鎖住這行防止別人插手）、`UPDATE`、`DELETE`（修改操作，必須基於「當前最新」的資料值進行修改，如果基於一個舊快照去修改，會導致修改結果和其他並發修改衝突或覆蓋丟失）、`INSERT`（插入新行，某些情況下也涉及間隙鎖（Gap Lock）檢查唯一性約束）。這些操作因為涉及「修改」或「明確要求讀到最新值並鎖定它」，必然需要加鎖——鎖住相關的行（記錄鎖）甚至範圍（間隙鎖，防止幻讀），確保在這個交易完成修改之前，其他交易不能同時修改或插入衝突的資料。所以完整理解是——MVCC 解決了「大量的、不涉及修改的普通查詢」的並發效能問題（這在實務中佔絕大多數的資料庫操作），但涉及「修改」或「明確要鎖定資料防止併發修改」的操作，仍然依賴傳統的鎖機制，兩者是互補配合、共同構成 InnoDB 完整並發控制方案的兩個支柱。

**面試回答方式**：講出「不能完全避免——快照讀(普通 SELECT)用 MVCC 不加鎖；當前讀(SELECT FOR UPDATE、UPDATE、DELETE、INSERT)仍要加鎖，因為要基於『當前最新』資料操作、且要防止其他交易同時修改」。強調「MVCC 和鎖是互補的兩個支柱——MVCC 解決大量普通查詢的並發效能、鎖解決涉及修改的場景」。展現你理解 MVCC 的適用邊界，不誤以為它能替代所有鎖機制。

### 為什麼説 MVCC 解決不了幻讀（在快照讀場景），要靠鎖來解決？

**核心答案**：因為 MVCC 的快照讀，是「基於一個固定的、過去某個時間點的版本快照」讀取資料——在這個機制下，「快照讀」本身其實根本不會產生「幻讀」的困擾（因為它每次讀到的都是那個凍結時刻的一致視圖，不管別的交易插入了多少新資料，快照讀根本看不到這些新插入的、是在快照建立之後才提交的資料，所以快照讀角度看是「一致」的，沒有幻讀問題）。真正會遇到幻讀問題的，是「當前讀」——如果你先做了一次「當前讀」的範圍查詢（如 `SELECT ... FOR UPDATE` 查詢某範圍），接著另一個交易在這個範圍內插入了新行並提交，你再做一次同樣的「當前讀」查詢，就會看到多出來的「幻影行」——這種場景下，MVCC（基於歷史版本）幫不上忙（因為當前讀就是要讀「當前最新」狀態，不能用舊快照），必須靠「鎖」（specifically 是 next-key lock 的間隙鎖部分）去「阻止」其他交易插入新行，從物理上防止幻影行的產生，而不是靠「讀哪個版本」的邏輯手段。

**詳細解析**：這題釐清一個容易混淆的地方——「MVCC 能不能解決幻讀」這個問題要分場景討論，快照讀和當前讀的答案不同。在「快照讀」場景下，MVCC 本身就自然地避免了幻讀的困擾——因為你的每一次查詢，只要是在同一個交易內、且隔離級別是 RR（複用同一個 ReadView），看到的永遠是「同一個凍結時刻」的資料快照，這個快照裡「有多少行符合條件」是固定不變的，不會因為外面有新交易插入資料而變化（因為那些新資料，根本不在你這個舊快照的可見範圍內）。所以嚴格來説，「快照讀」場景下的 RR 級別，透過 MVCC 就已經自然地避免了幻讀（這也是為什麼很多資料庫教材説「MySQL 的 RR 解決了幻讀」，指的主要是快照讀場景）。但「當前讀」場景不同——當你做 `SELECT ... FOR UPDATE` 這類操作，語意上要求你「必須看到當前最新、真實的資料狀態」（因為你接下來可能要基於這個結果做修改），這時候不能用「舊快照」搪塞過去，必須真的去讀「當前」有哪些行符合條件。而如果只是「讀」了一下（哪怕是當前讀），沒有任何機制阻止「你讀完之後、你準備做後續操作之前，別的交易插入了新行」，那麼你如果基於「讀到的行數」做了某種判斷或後續操作，就可能因為這個「後來插入的幻影行」而出錯——這種情況下，唯一的解法是「鎖住這個範圍，不讓任何交易在這期間插入」，這正是 next-key lock（間隙鎖）的作用，是「物理上阻止」而非「邏輯上選擇看哪個版本」。理解「快照讀靠 MVCC 的邏輯隔離自然避免幻讀、當前讀必須靠鎖的物理阻止」這個場景區分，展現你對幻讀問題的理解達到了精確、不含糊的程度。

**面試回答方式**：講出「快照讀場景下、RR 級別複用同一個 ReadView、看到的永遠是凍結時刻的一致快照、根本不會有幻讀問題(MVCC 自然避免)；但當前讀(FOR UPDATE 等)語意上要求讀到最新真實狀態、不能用舊快照、如果沒有機制阻止別人插入、還是可能遇到幻影行、必須靠 next-key lock 的間隙鎖物理上阻止插入」。強調「區分快照讀(邏輯隔離自然避免)和當前讀(必須物理鎖定阻止)」。展現你對幻讀問題的理解精確而不含糊。
