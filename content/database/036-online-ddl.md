# 題目

在一張上億列的表上加一個欄位或索引，該怎麼做？

## 核心答案

MySQL 5.6 之後有**原生的 Online DDL**，它把變更分成三種演算法：**INSTANT**（8.0 起，只改中繼資料，例如在表尾加一個欄位——**幾乎瞬間完成**）、**INPLACE**（在原表上重建索引或資料，**不阻塞讀寫但仍要掃描全表**，期間會產生大量 IO 與 redo）、**COPY**（建立新表、複製全部資料、再改名，**期間阻塞寫入**——這是最差的情況）。

用 `ALTER TABLE ... , ALGORITHM=INPLACE, LOCK=NONE` 可以強制要求：如果 MySQL 無法用不阻塞的方式完成，它會直接報錯而不是靜默地降級成 COPY。這是執行大表 DDL 時必須加的保護——否則你可能以為是線上變更，實際上鎖了半小時。

**但原生 Online DDL 仍有兩個問題**：它會產生**大量的 IO 與複製延遲**（從庫要重放整個變更）、而且一旦開始就難以中止或控制速度。所以生產環境的大表變更普遍使用**外部工具**：**gh-ost** 或 **pt-online-schema-change**。

它們的做法是：建立一張新結構的影子表、把存量資料分批複製過去、同時捕捉變更並套用、最後原子地改名切換。優勢是可以隨時暫停、可以控制速度、也可以在切換前中止。

## 詳細解析

gh-ost 與 pt-osc 的關鍵差別在「怎麼捕捉變更」。**pt-osc 用觸發器**——在原表上建立 INSERT／UPDATE／DELETE 的觸發器，把變更同步寫到影子表。問題是觸發器在原表的寫入交易中同步執行，直接增加了線上寫入的延遲，而且觸發器與應用的鎖競爭可能造成死鎖。**gh-ost 則讀取 binlog**——它偽裝成一個從庫，從 binlog 中解析變更並套用到影子表。這讓它對原表的寫入路徑完全沒有影響，也讓它可以動態調節速度（發現複製延遲上升就自動減速）。**gh-ost 是現在的主流選擇。**

「最後的切換」是整個過程風險最集中的一刻。切換需要一個短暫的排他鎖（改名兩張表），如果此時有長交易持有原表的鎖，切換會等待——而它自己也持有鎖，可能造成連鎖阻塞。gh-ost 的做法是設定切換的逾時與重試，並且在切換前檢查是否有長交易。實務上應該在低峰時段切換，並事先確認沒有長時間執行的查詢。

新增欄位與新增索引的成本完全不同。在表尾新增一個有預設值的可為空欄位，8.0 可以用 INSTANT 演算法——只改中繼資料，瞬間完成。但新增索引必須掃描全表並建立索引結構，那是真正的重活。所以「加欄位」與「加索引」在評估時不該被一視同仁——很多人以為所有 DDL 都很危險，實際上 INSTANT 的變更可以隨時做。知道哪些變更是 INSTANT 的（`ALGORITHM=INSTANT` 明確指定，不支援就報錯）能省下大量不必要的謹慎。

**回滾計畫必須事先想好**。DDL 通常不能回滾（`ALTER TABLE` 不在交易裡），所以「加了索引發現效能更差」的補救是「再刪掉它」，而那又是一次全表操作。真正的防護是在測試環境用相近的資料量驗證——包含變更本身的耗時、變更後的查詢計畫、以及變更期間對線上的影響。

## 面試回答方式

先給**三種演算法**與各自的代價（INSTANT 只改中繼資料、INPLACE 不阻塞但要掃全表、COPY 阻塞寫入）。**強調必須加 `ALGORITHM=INPLACE, LOCK=NONE`**——它讓 MySQL 在無法用不阻塞的方式完成時直接報錯，而不是靜默降級成 COPY，這是執行大表 DDL 時必須的保護。接著給外部工具的做法（影子表、分批複製、捕捉變更、原子改名）與優勢（可暫停、可控速、可中止）。加分點有三個：gh-ost 用 binlog 而 pt-osc 用觸發器，後者在原表的寫入交易中同步執行、直接增加線上延遲，所以 gh-ost 是現在的主流；「最後的切換」是風險最集中的一刻，長交易會讓它卡住並造成連鎖阻塞；以及加欄位與加索引的成本完全不同——表尾加欄位在 8.0 可以是 INSTANT 的，知道這件事能省下大量不必要的謹慎。

## 講稿

MySQL 有原生的線上 DDL，分三種演算法。瞬間完成的只改中繼資料，比如在表尾加一個欄位。原地執行的不阻塞讀寫但仍要掃描全表，會產生大量 IO。複製表的則會阻塞寫入，那是最差的情況。

有一個必須加的保護。明確指定演算法跟鎖等級的話，如果 MySQL 無法用不阻塞的方式完成，它會直接報錯而不是靜默地降級成複製表。否則你可能以為是線上變更，實際上鎖了半小時。

但原生的方式仍有兩個問題，會產生大量複製延遲，而且一旦開始就難以中止或控制速度。所以生產環境的大表變更普遍用外部工具。它們建立一張新結構的影子表、分批複製存量、同時捕捉變更並套用、最後原子地改名切換。優勢是可以隨時暫停、控制速度、也可以在切換前中止。

兩種主流工具的關鍵差別在怎麼捕捉變更。一種用觸發器，但觸發器在原表的寫入交易中同步執行，直接增加線上寫入的延遲。另一種讀取 binlog，偽裝成一個從庫，對原表的寫入路徑完全沒有影響，還可以發現複製延遲上升就自動減速。後者是現在的主流。

還有一點，加欄位跟加索引的成本完全不同，不該被一視同仁。

## 常見追問

### DDL 對複製延遲的影響有多大？

**核心答案**：**可能非常大**。原生的 INPLACE DDL 在主庫執行完之後**才寫進 binlog 成為一個事件**，從庫要**完整重放一次同樣的變更**——一個在主庫跑了半小時的索引建立，從庫也要跑半小時，而期間它無法處理後續的任何變更。於是複製延遲會累積到半小時以上。

**詳細解析**：這是外部工具最重要的優勢之一。gh-ost 的分批複製是**普通的 `INSERT` 語句**，它們在 binlog 中是一批批的小事件，從庫可以逐批重放而不會被卡住；而且 gh-ost 會主動監測從庫的延遲並在超過閾值時暫停，等追上了再繼續。這讓「變更大表」從一個會造成複製中斷的高風險操作，變成一個可以在營運時間安全執行的日常操作。 對於讀寫分離的架構，複製延遲直接等於「從庫讀到的資料有多舊」——半小時的延遲意味著所有讀請求都拿到半小時前的資料，那在業務上通常是不可接受的。所以在有讀寫分離的系統上，DDL 的複製影響往往比它對主庫的影響更重要，而這一點很容易被忽略。

**面試回答方式**：給機制——INPLACE DDL 在 binlog 中是一個事件，從庫要完整重放同樣的時間，期間無法處理後續變更，於是延遲累積到與執行時間相當。展開這是**外部工具最重要的優勢之一**：分批複製是普通 INSERT、可逐批重放，而且工具會主動監測延遲並暫停。收在一個容易被忽略的判斷：在讀寫分離的架構下，複製延遲直接等於「讀到的資料有多舊」，所以 DDL 的複製影響往往比它對主庫的影響更重要。

### 哪些變更可以用 INSTANT 演算法？

**核心答案**：MySQL 8.0 支援的 INSTANT 變更包括：**在表的最後新增欄位**（8.0.29 之後也支援在中間新增）、**新增或刪除虛擬產生欄位**、**修改欄位的預設值**、修改列的 `ENUM`／`SET` 定義（只在末尾追加值）、**重新命名表**、以及**修改索引的可見性**。驗證的方式是明確寫 `ALGORITHM=INSTANT`——不支援的話會直接報錯，這比查文件可靠。

**詳細解析**：**INSTANT 新增欄位有一個累積的代價**：它不重寫既有的列，而是在中繼資料中記錄「這個欄位是第 N 次 instant 變更加的、預設值是什麼」，讀取舊列時動態補上。所以每次 INSTANT 加欄位都會增加一層這樣的記錄，而且有數量上限（超過就必須重建表）。這意味著 INSTANT 不是完全免費的——它把成本推遲了。了解這一點的實務意義是：不要因為 INSTANT 很快就頻繁地加欄位，累積之後仍然需要一次重建。這也是一個通用模式的例子：「即時完成」的操作往往是把工作推遲而非消除，而推遲的部分終究要付。 同樣的思路出現在延遲刪除、寫時複製、以及各種懶惰求值的設計裡。

**面試回答方式**：列出支援的變更類型，並給出最可靠的驗證方式：明確寫 `ALGORITHM=INSTANT`，不支援會直接報錯，比查文件可靠。真正的加分點是指出 INSTANT 新增欄位有累積代價——它在中繼資料記錄變更而不重寫既有列，有數量上限、超過就必須重建表。收在通用模式：「即時完成」的操作往往是把工作推遲而非消除，推遲的部分終究要付，並舉延遲刪除與寫時複製作為同類。

### 大表變更的完整流程該怎麼安排？

**核心答案**：六步。第一，在測試環境用相近的資料量驗證——量測耗時、確認變更後的執行計畫、觀察對線上查詢的影響。**第二，確認回滾方案**（通常是「反向的 DDL」，並知道它同樣需要時間）。**第三，選低峰時段**並確認沒有長交易與大批次作業在跑。**第四，用外部工具執行並監控**（複製延遲、主庫負載、工具的進度）。**第五，切換前再次確認**沒有長交易。**第六，切換後驗證**——查詢計畫、應用行為、以及一段時間的效能觀察。

**詳細解析**：「在測試環境用相近的資料量」是最常被打折的一步，也是最不該打折的。用一萬列的測試表跑三秒，不能告訴你一億列會跑多久——**而且非線性的因素很多**（索引建立的排序可能溢出到磁碟、緩衝池的命中率完全不同、鎖的爭用程度不同）。如果無法準備相同規模的測試資料，至少應該用「資料量的比例」做保守的外推並乘以安全係數。 另一個常被忽略的是「切換後的觀察期」——新的索引可能改變了其他查詢的執行計畫（最佳化器有了新的選擇），**有時候會變差**。所以變更後應該觀察一段時間的整體查詢效能，而不是只確認目標查詢變快了。 「一個變更的影響不限於它的目標」是效能工作中反覆出現的教訓。

**面試回答方式**：給六步流程。重點強調第一步最常被打折也最不該打折——一萬列跑三秒不能告訴你一億列會跑多久，而且**非線性因素很多**（排序溢出磁碟、緩衝池命中率不同、鎖爭用程度不同）；無法準備相同規模時至少要保守外推並乘安全係數。真正的加分點是**切換後的觀察期**——新索引可能改變其他查詢的執行計畫、有時會變差，所以要觀察整體效能而非只確認目標查詢變快。收在教訓：一個變更的影響不限於它的目標。
