# 題目

資料庫有哪些交易隔離級別？各自解決什麼問題？MySQL 預設是哪個級別？

## 核心答案

SQL 標準定義了四種隔離級別（從低到高）：**讀未提交（Read Uncommitted）**——能讀到其他交易「未提交」的修改，會有髒讀（Dirty Read）；**讀已提交（Read Committed）**——只能讀到其他交易「已提交」的修改，解決了髒讀，但同一交易內兩次讀取可能得到不同結果（不可重複讀（Non-Repeatable Read））；**可重複讀（Repeatable Read）**——同一交易內多次讀取同一資料結果一致，解決了不可重複讀，MySQL 的 InnoDB 預設用這個級別（且透過 next-key lock 在一定程度上解決了幻讀（Phantom Read），見追問）；**序列化（Serializable）**——最高級別，交易完全序列化執行（如同一個個排隊），沒有並發問題，但效能最差。級別越高、一致性越強、並發效能越差，是一個取捨。

## 詳細解析

**四種隔離級別及對應解決的問題**：

1. **讀未提交（Read Uncommitted）**——最低級別。一個交易可以讀到另一個交易「尚未提交」的修改（髒讀）。如果那個交易之後回滾了，你讀到的資料就是從沒真正存在過的「髒資料」。實務中幾乎不用。

2. **讀已提交（Read Committed，RC）**——一個交易只能讀到「其他交易已經提交」的修改，解決了髒讀。但存在「不可重複讀」——同一個交易內，先後兩次讀同一行資料，如果中間有另一個交易修改並提交了這行資料，兩次讀到的結果會不一樣（因為每次讀都是讀「當前已提交的最新版本」）。Oracle、SQL Server 預設用這個級別。

3. **可重複讀（Repeatable Read，RR）**——同一個交易內，多次讀同一行資料，結果保持一致（不會因為其他交易的提交而改變）。解決了不可重複讀。**MySQL InnoDB 的預設隔離級別**。理論上這個級別仍可能有「幻讀」（見追問），但 InnoDB 透過 next-key lock 在很大程度上緩解了幻讀。

4. **序列化（Serializable）**——最高級別，強制交易「序列化執行」（讀寫都會加鎖，衝突的交易要排隊），完全避免髒讀、不可重複讀、幻讀，但並發度最低、效能最差。

**級別越高、效能越低的取捨**：級別越高，資料庫為了保證一致性要做的工作越多（更多的鎖、更少的並發），所以吞吐量會下降。實務中根據業務對一致性的要求選擇合適的級別，不是越高越好——大多數應用用 RC 或 RR 就足夠，只有對一致性要求極高、又能接受效能損失的場景才用 Serializable。

## 面試回答方式

按四個級別從低到高逐一講，每個都要講清楚「解決了什麼問題、還存在什麼問題」——讀未提交(有髒讀)→讀已提交(解決髒讀、但有不可重複讀)→可重複讀(解決不可重複讀、理論上還有幻讀)→序列化(全解決但效能最差)。務必記得「MySQL InnoDB 預設是可重複讀」這個具體事實。能點出「級別越高、一致性越強、並發效能越差」這個核心取捨，並提到「InnoDB 的可重複讀透過 next-key lock 緩解了幻讀」作為加分（這是這批題目中最容易被深挖的細節，見下一題)。

## 常見追問

### 什麼是髒讀、不可重複讀、幻讀？分別舉例説明。

**核心答案**：**髒讀**——讀到了「其他交易還沒提交、甚至可能會回滾」的資料。例如交易 A 把某商品庫存改成 0（還沒提交），交易 B 這時候讀到庫存是 0（髒讀），如果 A 之後回滾了、庫存其實還是 100，但 B 已經基於「庫存是 0」做了錯誤的判斷（如告訴使用者無貨）。**不可重複讀**——同一個交易內，兩次讀同一行資料，結果不一樣（因為中間別的交易修改並提交了）。例如交易 A 第一次查詢某商品價格是 100 元、還沒結束交易，這時交易 B 把價格改成 120 元並提交，A 在同一個交易裡再查一次，變成 120 元了——同一個交易裡兩次讀到不同結果。**幻讀**——同一個交易內，兩次執行「相同條件的範圍查詢」，第二次查出來的「行數」比第一次多（或少）了（多出來的行像是「幻影」一樣冒出來）。例如交易 A 查詢「年齡大於 20 歲的使用者」得到 10 條，這時交易 B 新插入了一個 21 歲的使用者並提交，A 在同一交易裡再查一次同樣的條件，變成 11 條——多出來的這一條就是「幻讀」出來的行。

**詳細解析**：這三個概念是理解隔離級別的基礎，經常被拿來考察是否真的理解各級別解決的具體問題，而不只是背誦級別名稱。三者的核心區別在於「異常發生的層次」——**髒讀**是讀到了「根本不該存在」的資料（因為來源交易還沒提交、甚至會回滾，這份資料在邏輯上可能從未真正「發生」過），這是最嚴重的問題，因為你的判斷可能完全建立在虛假的資料上。**不可重複讀**是針對「同一行資料」，關注的是「這一行的值前後不一致」——問題出在「更新（UPDATE）」導致的，即別的交易改了某一行的內容並提交。**幻讀**是針對「一個範圍/一批資料」，關注的是「這批資料的『數量/行的集合』前後不一致」——問題出在「插入（INSERT）或刪除（DELETE）」導致符合條件的行集合發生了變化，即使你查詢的每一行內容都沒變，但「一共有幾行符合條件」這件事本身變了。理解這個「行的值 vs 行的集合」的區分，是分清「不可重複讀」和「幻讀」的關鍵——很多人容易把這兩個搞混，記住「改值是不可重複讀、改行數是幻讀」就能清楚區分。

**面試回答方式**：用具體例子逐一説明三者——「髒讀：讀到別人還沒提交甚至會回滾的資料(可能基於虛假資料做判斷)；不可重複讀：同交易兩次讀同一行、因為別人 UPDATE 並提交、內容變了；幻讀：同交易兩次執行同樣的範圍查詢、因為別人 INSERT/DELETE 並提交、符合條件的行數變了」。提煉區分口訣——「不可重複讀是改值(同一行內容變)、幻讀是改行數(範圍查詢的行集合變)」。展現你能清楚區分這三個容易混淆的並發異常。

### 為什麼説 MySQL 的可重複讀「透過 next-key lock 在很大程度上解決了幻讀」？

**核心答案**：因為標準的可重複讀（快照讀場景）在「當前讀」（如 `SELECT ... FOR UPDATE`、`UPDATE`、`DELETE` 這類會加鎖的操作）中仍可能遇到幻讀——如果只用「行鎖」鎖住已經查詢到的那幾行，其他交易仍然可以在這些行「之間的間隙」插入新的符合條件的行，導致幻讀。InnoDB 用 **next-key lock**（記錄鎖 + 間隙鎖的組合）解決這個——它不只鎖住「已存在、符合條件的行」，還鎖住這些行「之間的間隙（gap）」，讓其他交易「無法在這個範圍內插入新行」，從根本上阻止了「幻影行」的產生，所以在 InnoDB 的可重複讀級別下，透過鎖定範圍（間隙）而非只鎖定行，很大程度上避免了幻讀（雖然理論上快照讀場景下，某些特殊情況仍可能有輕微的幻讀現象，但當前讀場景下基本被 next-key lock 消除了）。

**詳細解析**：這題深入到 InnoDB 對標準隔離級別的「加強實現」，是一個經常被深挖的細節。標準的四種隔離級別是 SQL 標準定義的「理論行為」，但具體資料庫的實現可以「做得更好」（提供比標準要求更強的保證）。標準的可重複讀（RR）理論上不保證解決幻讀（只有序列化才完全保證），但 InnoDB 在「當前讀」的場景下，透過 next-key lock 這種「鎖住行 + 鎖住行之間間隙」的機制，實際上已經很大程度上避免了幻讀。具體機制是——普通的行鎖只能鎖住「已經存在的、符合條件的具體行」，但幻讀的產生正是因為「有新行插進來」，行鎖鎖不住「還不存在的行」；InnoDB 的間隙鎖（Gap Lock）就是為了解決這個——它鎖定的是「兩個索引記錄之間的間隙」，讓其他交易無法在這個間隙裡插入新的資料。Next-key lock 是「記錄鎖（鎖住行本身）+ 間隙鎖（鎖住行前面的間隙）」的組合，這樣不僅鎖住了已有的符合條件的行，也鎖住了它們之間、以及範圍邊界的間隙，使得其他交易的 INSERT 操作如果會落在這個被鎖定的範圍內，就會被阻塞，等到當前交易提交或回滾釋放鎖後才能繼續，從而防止了「幻影行」的插入。理解「行鎖鎖不住不存在的行、間隙鎖補上了這個漏洞」，是理解 InnoDB 如何超越標準隔離級別要求、提供更強一致性（Strong Consistency）保證的關鍵。

**面試回答方式**：講出「標準 RR 理論上不保證解決幻讀、但 InnoDB 在當前讀場景用 next-key lock(記錄鎖+間隙鎖)加強實現——行鎖只能鎖已存在的行、鎖不住『還沒插入的新行』、間隙鎖補上這個漏洞(鎖住行之間的間隙、阻止其他交易在這個範圍插入新行)、所以能防止幻讀」。展現你理解 InnoDB 的實現超越了標準定義、以及間隙鎖解決幻讀的具體機制。

### 隔離級別是怎麼設定的？換一個更高的隔離級別，程式碼需要改嗎？

**核心答案**：隔離級別是「連線/會話級別」或「全域」的設定，透過 `SET SESSION TRANSACTION ISOLATION LEVEL ...`（只影響當前連線的後續交易）或 `SET GLOBAL TRANSACTION ISOLATION LEVEL ...`（影響全域預設，需要有相應權限，且通常需要重新連線才生效）來設定，也可以在資料庫設定檔（如 MySQL 的 `my.cnf` 的 `transaction_isolation`）裡配置預設值。它是「資料庫層面」的設定，一般情況下切換隔離級別「不需要修改應用程式碼」（SQL 語句本身不用變）——因為隔離級別控制的是「資料庫在背後怎麼加鎖、怎麼決定讀取哪個版本」，這對應用程式碼是透明的。但需要注意——切換隔離級別可能「改變程式的實際行為」（例如原本在 RR 級別下不會出現的不可重複讀，切到 RC 後可能出現），所以雖然不用改程式碼語法，但要重新評估業務邏輯是否還能正確運作（尤其是那些「依賴同一交易內多次讀取結果一致」的邏輯，切到更低的隔離級別可能會出問題）。

**詳細解析**：這題釐清「隔離級別是資料庫配置、不是程式碼邏輯」這個定位，以及切換隔離級別的實際影響範圍。隔離級別的本質是「告訴資料庫，在處理並發交易時，用什麼樣的鎖策略和讀取規則」——這是資料庫內部的行為調整，你寫的 SQL 語句（SELECT、UPDATE 等）本身完全不需要因為隔離級別不同而改變寫法，資料庫會根據當前生效的隔離級別，自動決定「這個 SELECT 是走快照讀還是要加鎖」、「這個 UPDATE 要鎖住多大範圍」等。所以從「程式碼語法」的角度看，切換隔離級別確實「不需要改程式碼」。但這不代表切換隔離級別「沒有風險」——因為隔離級別實際上是在「一致性保證的強度」上做出承諾，如果你的業務邏輯是「假設了某種一致性保證」寫出來的（例如你依賴「同一個交易內，多次查詢庫存的結果一定一樣」這個可重複讀的保證來做判斷），一旦把隔離級別降低（比如降到讀已提交），這個假設就不再成立了，可能導致業務邏輯出現意料之外的錯誤（即使程式碼一行沒改）。所以正確的認知是——「改變隔離級別，語法上不需要改程式碼，但語意上可能改變程式的實際行為，必須重新審視業務邏輯對一致性的假設是否還成立」。這提醒我們，隔離級別的選擇是一個需要謹慎對待的架構決策，不能隨意切換而不評估影響。

**面試回答方式**：講出「隔離級別是連線/會話或全域的資料庫配置(SET SESSION/GLOBAL TRANSACTION ISOLATION LEVEL)、不是程式碼邏輯——SQL 語法不用變」。強調「但要注意——切換級別會改變背後的一致性保證、如果業務邏輯依賴某種一致性假設(如可重複讀)、降低隔離級別可能讓假設不成立、導致邏輯出錯，雖然程式碼沒改但行為變了」。展現你理解隔離級別是架構層面的決策、切換需要謹慎評估對業務邏輯的實際影響。
