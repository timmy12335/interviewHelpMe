# 題目

InnoDB 的 change buffer 解決什麼問題？為什麼它只對非唯一的二級索引有效？

## 核心答案

問題是**二級索引的寫入需要隨機 IO**。更新一列時，除了聚簇索引（依主鍵有序，寫入相對連續），還要更新每個二級索引——**而二級索引的順序與主鍵無關，所以要修改的頁面散落在磁碟各處**。如果那些頁不在 Buffer Pool 裡，就必須先把它們讀進來，**一次寫入變成多次隨機讀**。

change buffer 的做法是：**當要修改的二級索引頁不在記憶體中時，把「這個修改」先記在 change buffer 裡而不讀取頁面**；等到那個頁面因為別的原因被讀進記憶體時（或由背景執行緒定期合併），**再把累積的修改一次套用上去**（這個動作叫 merge）。**於是多次隨機讀被合併成一次，寫入吞吐大幅提升。**

**它只對非唯一索引有效，原因很直接**：唯一索引的插入必須**檢查是否已存在相同的值**，而檢查就必須讀取那個頁面——**既然頁面反正要讀進來，就沒有延後的餘地了**。所以 `UNIQUE` 索引的寫入無法受益於 change buffer。

## 詳細解析

**這個機制解釋了一個實務上的設計判斷：不必要的唯一約束是有寫入成本的**。很多欄位被加上 `UNIQUE` 是「順便」的（例如某個業務編號，實際上應用層已經保證唯一），**但它讓那個索引的每一次寫入都必須讀取頁面**。**在寫入密集的大表上，這個差別可以很明顯。** 反過來說，**真正需要唯一性保證時仍然應該用唯一約束**——用它換來的正確性遠比寫入效能重要，只是要知道這個成本存在並且是有意識地付出的。

**change buffer 的收益與「頁面在不在記憶體」直接相關**。如果表很小或 Buffer Pool 很大，二級索引頁本來就都在記憶體裡——**那 change buffer 幾乎沒有作用**。它真正發光的場景是**大表加上寫入密集，且資料量遠大於記憶體**。`innodb_change_buffer_max_size`（預設 25%，表示 change buffer 最多佔 Buffer Pool 的比例）可以調整，**寫多讀少的場景可以調高，讀多寫少的則該調低甚至關閉**（`innodb_change_buffering=none`），因為它佔用的緩衝池空間本來可以用來快取資料頁。

**merge 的時機決定了它的風險**。merge 發生在：頁面被讀入時、背景執行緒定期執行時、以及 InnoDB 正常關閉時。**這意味著崩潰後恢復需要重放 change buffer 的內容**——所以 change buffer 的修改也是寫進 redo log 的，崩潰不會丟失。**但「累積了大量未 merge 的修改」會讓崩潰恢復變慢**，這是它的一個隱藏成本。

**它與 LSM Tree 的思路有共通之處**：都是**把隨機寫轉成順序寫或延後寫**，用「讀取時多做一點工作」換「寫入時少做很多工作」。**差別在於 LSM 是整個儲存引擎的設計，change buffer 只是 B+ 樹引擎上的一個局部優化。** 認出這個共通點，就能理解為什麼寫入密集的系統會傾向 LSM——**它把這個思路貫徹到了底**。

## 面試回答方式

先給問題——**二級索引的寫入需要隨機 IO**，因為它的順序與主鍵無關、要改的頁散落各處。給出機制：**頁面不在記憶體時把修改記在 change buffer，等頁面因別的原因被讀進來時一次套用**，於是多次隨機讀合併成一次。**唯一索引無效的理由要說得直接**：插入必須檢查是否重複，檢查就必須讀頁面，**既然反正要讀就沒有延後的餘地**。加分點有三個：**不必要的唯一約束是有寫入成本的**——很多欄位「順便」加了 `UNIQUE`，但那讓每次寫入都要讀頁面；**收益與「頁面在不在記憶體」直接相關**，小表或大緩衝池時它幾乎沒作用，讀多寫少時甚至該關閉；以及**它與 LSM Tree 思路共通**——都是把隨機寫轉成延後寫，而 LSM 把這個思路貫徹到底。

## 講稿

問題是二級索引的寫入需要隨機 IO。更新一列的時候，除了聚簇索引，還要更新每個二級索引。而二級索引的順序跟主鍵無關，所以要修改的頁面散落在磁碟各處。如果那些頁不在記憶體裡，就必須先讀進來，一次寫入變成多次隨機讀。

change buffer 的做法是，當要修改的頁不在記憶體時，把這個修改先記下來而不讀取頁面。等到那個頁因為別的原因被讀進記憶體時，再把累積的修改一次套用上去。多次隨機讀就被合併成一次。

它只對非唯一索引有效，原因很直接。唯一索引的插入必須檢查是否已經存在相同的值，而檢查就必須讀取那個頁面。既然頁面反正要讀進來，就沒有延後的餘地了。

這解釋了一個實務上的設計判斷，不必要的唯一約束是有寫入成本的。很多欄位被加上唯一約束是順便的，但它讓那個索引的每一次寫入都必須讀取頁面。當然，真正需要唯一性保證的時候仍然應該用，只是要知道這個成本存在。

還有一點，它的收益跟頁面在不在記憶體直接相關。表很小或緩衝池很大的話，二級索引頁本來就都在記憶體裡，那它幾乎沒有作用。讀多寫少的場景甚至該關掉它。

## 常見追問

### 為什麼聚簇索引的寫入不需要 change buffer？

**核心答案**：因為**聚簇索引是按主鍵有序的**，而主鍵通常是自增或有序的——**新插入的資料集中在最後一個頁面上，而那個頁面幾乎必然已經在 Buffer Pool 裡**（剛剛才被寫過）。所以聚簇索引的插入是「順序寫」，不需要隨機讀取頁面。**這正是「主鍵應該用有序值」這條建議的核心理由之一。**

**詳細解析**：**用 UUID 當主鍵會摧毀這個性質**。隨機的 UUID 讓插入位置散落在整棵 B+ 樹上，**每次插入都可能要讀取一個不在記憶體的頁面，還會造成頁分裂與碎片**——寫入效能可能差幾倍到一個數量級。**而且它會放大到所有二級索引**：InnoDB 的二級索引葉節點存的是主鍵值，**主鍵越大，每個二級索引就越大**——16 位元組的 UUID 對比 8 位元組的 bigint，所有二級索引的體積幾乎翻倍。**所以主鍵的選擇不只影響聚簇索引，它影響整張表的所有索引**，這是一個影響面遠超直覺的決定。**需要 UUID 的全域唯一性時，應該用有序的變體**（UUIDv7、ULID）——它們保留了唯一性但前綴含時間戳，因此是遞增的。

**面試回答方式**：給原因（主鍵有序、新資料集中在最後一頁、那個頁必然在記憶體裡），並指出這是「主鍵應該用有序值」的核心理由之一。展開 **UUID 主鍵的兩層危害**：插入位置散落造成隨機讀與頁分裂；以及**二級索引葉節點存主鍵值，所以主鍵越大所有二級索引越大**——16 位元組 UUID 對比 8 位元組 bigint 讓所有二級索引體積幾乎翻倍。收在解法：**需要全域唯一時用有序的變體**（UUIDv7、ULID），前綴含時間戳所以是遞增的。

### change buffer 對讀取有什麼影響？

**核心答案**：**有負面影響，但通常可接受**。當一個頁面被讀入時，如果 change buffer 裡有它的未合併修改，**必須先執行 merge 才能返回正確的資料**——這讓那一次讀取變慢。而且 change buffer 佔用的緩衝池空間，**本來可以用來快取更多資料頁**。所以在讀多寫少的工作負載上，它是淨損失。

**詳細解析**：**這是一個典型的「寫入優化以讀取為代價」的設計**，而判斷它划不划算的方式是看工作負載的讀寫比。**`innodb_change_buffering` 支援細緻的控制**：`all`（預設，緩衝插入、刪除標記與刪除）、`inserts`、`deletes`、`changes`、`purges`、`none`。**寫入密集的表可以用 `all`，讀取密集的可以設 `none`**。**要注意這是全域設定而非按表設定**——所以在一個既有寫入密集又有讀取密集表的實例上，只能取一個折衷。**這也是「把不同工作負載的表分開部署」的一個理由**：全域參數無法為不同的表分別最佳化，而這類參數在 MySQL 裡並不少（緩衝池、redo log、隔離級別的預設值都是實例層級的）。

**面試回答方式**：明確指出**有負面影響**——merge 讓那次讀取變慢，而且它佔用的緩衝池本來可以快取資料頁，所以讀多寫少時是淨損失。給出調整方式（`innodb_change_buffering` 的幾個等級）。真正的加分點是指出**這是全域設定而非按表設定**，混合工作負載的實例只能取折衷——**這也是「把不同工作負載的表分開部署」的一個理由**，因為這類實例層級的參數在 MySQL 裡並不少。

### 這類「延後寫入」的優化還有哪些？

**核心答案**：資料庫裡至少有四種同源的設計。**redo log 的 WAL**——先順序寫日誌、再非同步刷資料頁，把隨機寫轉成順序寫。**髒頁的延後刷新**——修改先在記憶體累積，由背景執行緒批次刷回。**LSM Tree**——所有寫入先進記憶體表與順序的 WAL，再分層合併。**doublewrite buffer**（雖然是為了防止頁面撕裂，但也是先順序寫一份再寫到最終位置）。

**詳細解析**：**它們的共同思路是「利用順序 IO 比隨機 IO 快幾個數量級」這個硬體事實**。機械硬碟上隨機讀寫要尋道（毫秒級），順序讀寫則接近頻寬上限；**SSD 上差距縮小但仍然存在**（隨機寫還有寫入放大與垃圾回收的成本）。**所以幾乎所有儲存系統的核心優化都是同一個形狀：把隨機的、分散的、小的寫入，轉換成順序的、批次的、大的寫入。** 代價一致地落在讀取端（要合併多個來源）與空間（要存中間狀態）。**認出這個模式，就能理解為什麼「日誌結構」的設計在儲存系統中如此普遍**——從檔案系統到資料庫到訊息佇列，它們都在做同一件事。

**面試回答方式**：列出四種同源設計並各給一句機制。真正的加分點是歸納共同思路：**利用「順序 IO 比隨機 IO 快幾個數量級」這個硬體事實**，並精確說明 SSD 上差距縮小但仍存在（寫入放大與垃圾回收）。收在通用形狀：**把隨機、分散、小的寫入轉成順序、批次、大的寫入，代價一致地落在讀取端與空間上**，這解釋了日誌結構設計在儲存系統中為何如此普遍。
