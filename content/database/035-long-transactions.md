# 題目

長交易會造成哪些問題？怎麼發現與治理？

## 核心答案

五類危害。**undo 無法清理**——purge 執行緒不能清理「還有活躍 read view 需要」的版本，於是 undo 表空間持續膨脹、版本鏈變長、連帶讓一致性讀變慢。**鎖持有時間長**——增加阻塞與死鎖的機率。**複製延遲**——大交易在主庫執行完才寫 binlog，從庫要重放整個交易，延遲會突然跳高。**回滾成本高**——中斷或失敗時，回滾可能比執行還久且期間不釋放鎖。**連線與資源佔用**——交易期間連線不能被歸還給連線池。

最陰險的是「長交易不一定是慢查詢」——一個交易可能執行了一個很快的 `SELECT` 然後就開著不動（應用在等外部 API、或者連線沒有正確關閉），它在慢查詢日誌裡完全不會出現。

發現的手段是 **`information_schema.innodb_trx` 的 `trx_started`**（找出開始時間很久的交易）與 **`SHOW ENGINE INNODB STATUS` 的 History list length**（尚未 purge 的 undo 記錄數）。後者是一個應該被監控的指標，它比任何查詢層面的指標都更早反映長交易的存在。

## 詳細解析

長交易最常見的成因不是「查詢慢」而是「交易邊界畫錯」。四個典型的模式：**在交易裡呼叫外部 API**（遠端的延遲直接變成鎖持有時間，這是最危險的一種）、**交易裡有使用者互動或等待**（例如「開啟交易 → 顯示確認畫面 → 等使用者按確定」）、**框架的自動交易範圍過大**（`@Transactional` 標在一個做了很多事的方法上）、以及**連線洩漏**（交易開始後因為例外路徑沒有提交或回滾，連線被歸還到池裡但交易還開著——**這是最難查的一種**）。

「連線歸還但交易未結束」值得特別注意。多數連線池在歸還連線時會呼叫 `rollback()` 或檢查交易狀態（HikariCP 有相關設定），但如果沒有正確配置，一個未提交的交易可能隨著連線被重複使用而持續存在。症狀是 History list length 持續上升卻找不到對應的慢查詢。防護方式是確保連線池的 `autoCommit` 與歸還時的清理行為正確設定，並在 `innodb_trx` 中定期檢查是否有異常久的交易。

**治理的措施分三層**。**應用層**——交易邊界盡量小、絕對不在交易裡做外部呼叫、用明確的交易範圍而非讓框架推斷。**資料庫層**——設定合理的 `innodb_lock_wait_timeout`（5 到 10 秒而非預設 50）、對 `SELECT` 用 `MAX_EXECUTION_TIME`、監控 History list length 並告警。**流程層**——把「交易裡不能有外部呼叫」寫進 code review 的檢查項，因為這是一個靠工具很難自動檢測但靠紀律可以避免的問題。

**MySQL 8 提供了 `information_schema.innodb_trx` 之外更好的觀測**：`performance_schema.events_transactions_current` 給出每個執行緒當前交易的狀態與時長。把「最長交易的持續時間」做成一個持續的監控指標，比事後查 `innodb_trx` 有效得多——因為長交易往往在你去查的時候已經結束了。

## 面試回答方式

先給**五類危害**並各配機制。把「長交易不一定是慢查詢」講成重點——執行一個很快的查詢然後開著不動，慢查詢日誌完全看不到。給發現的手段（`innodb_trx` 的 `trx_started`、History list length）並指出後者應該被監控，它比任何查詢層面的指標都更早反映問題。加分點有三個：最常見的成因是「交易邊界畫錯」而非查詢慢，給四個典型模式並把「交易裡呼叫外部 API」標為最危險；「連線歸還但交易未結束」是最難查的一種，症狀是 History list length 上升卻找不到慢查詢；以及把「最長交易持續時間」做成持續的監控指標比事後查有效得多，因為長交易往往在你去查的時候已經結束了。

## 講稿

五類危害。undo 無法清理導致表空間膨脹跟版本鏈變長、鎖持有時間長增加阻塞跟死鎖、複製延遲突然跳高、回滾成本高而且期間不釋放鎖、還有連線被佔住不能歸還。

最陰險的是長交易不一定是慢查詢。一個交易可能執行了一個很快的查詢然後就開著不動，應用在等外部 API，或者連線沒有正確關閉。它在慢查詢日誌裡完全不會出現。

發現的手段是查詢正在執行的交易表看開始時間，還有引擎狀態裡的歷史清單長度，也就是尚未清理的 undo 記錄數。後者是我一定會監控的指標，它比任何查詢層面的指標都更早反映長交易的存在。

最常見的成因不是查詢慢，是交易邊界畫錯。四個典型模式是在交易裡呼叫外部 API、交易裡有使用者互動、框架的自動交易範圍過大、還有連線洩漏。第一個最危險，因為遠端的延遲直接變成鎖的持有時間。

連線洩漏那種最難查。交易開始後因為例外路徑沒有提交或回滾，連線被歸還到池裡但交易還開著。症狀是歷史清單長度持續上升卻找不到對應的慢查詢。

我會把最長交易的持續時間做成一個持續的監控指標，因為長交易往往在你去查的時候已經結束了。

## 常見追問

### 為什麼長交易會讓複製延遲突然跳高？

**核心答案**：因為 binlog 是在交易提交時才整批寫入的——一個執行了十分鐘的大交易，它的所有變更在第十分鐘才一次寫進 binlog。從庫收到之後要重放整個交易，而重放同樣需要可觀的時間（單執行緒重放時尤其）。於是延遲的曲線不是平滑上升，而是在大交易提交的那一刻突然跳高，然後隨著從庫追上而下降。

**詳細解析**：MySQL 5.7 之後的並行複製（基於 group commit 或 WRITESET）改善了整體吞吐，但對「單一大交易」沒有幫助——一個交易在從庫上仍然是由一個執行緒完整重放的，無法被拆開並行。所以「拆小交易」不只對主庫有好處，對複製延遲的平滑度也是必要的。 另一個常被忽略的點是「大交易讓從庫的延遲監控失真」：`Seconds_Behind_Master` 在從庫開始重放一個大交易時會持續上升，但那不表示從庫落後了那麼久的資料，只表示它正在處理一個很久以前開始的交易。用 GTID 的位置差或自訂的心跳表來量測延遲，比 `Seconds_Behind_Master` 準確得多——後者的定義有幾個已知的失真情況，這是複製監控中一個常見的誤讀來源。

**面試回答方式**：給機制——binlog 在提交時才整批寫入，從庫要重放整個交易，所以延遲曲線不是平滑上升而是在提交那一刻跳高。加分點是指出並行複製對單一大交易沒有幫助（一個交易仍由一個執行緒完整重放），所以拆小交易對複製延遲的平滑度是必要的。真正的深度在於`Seconds_Behind_Master` 會失真——它上升不表示落後那麼多資料，只表示正在處理一個很久前開始的交易；用 GTID 位置差或心跳表量測更準確。

### 怎麼在框架層面控制交易範圍？

**核心答案**：三個原則。**明確而非推斷**——用顯式的交易範圍（程式化的 `TransactionTemplate` 或明確標註的方法），而不是讓一個大方法被整個包在交易裡。**分離讀寫**——唯讀操作用 `readOnly = true`（或根本不開交易），只有真正需要原子性的寫入才開交易。**外部呼叫移出交易**——如果一個流程需要「寫資料庫、呼叫外部 API、再寫資料庫」，應該拆成兩個交易，中間的外部呼叫在交易之外。

**詳細解析**：第三點會引出「那中間失敗怎麼辦」這個真正的問題——而答案是**接受最終一致並設計補償**，而不是用一個大交易硬撐。**標準的模式是 Outbox**：第一個交易寫入業務資料與一筆「待發送」記錄，提交後由一個獨立的流程讀取待發送記錄並呼叫外部 API，成功後標記完成。這樣資料庫的交易保持極短，而「一定要發出去」由重試機制保證。 它的代價是引入了非同步與最終一致，好處是把「跨系統的原子性」這個不可能的需求，換成了「本地原子性加上可靠的重試」這個可實現的需求。 認出「跨系統的原子性做不到，只能用本地原子性加補償逼近」是這類設計的核心判斷。

**面試回答方式**：給三個原則（明確而非推斷、分離讀寫、外部呼叫移出交易）。重點展開第三點引出的問題「中間失敗怎麼辦」，並給出 **Outbox 模式**的完整流程。說明它的價值：資料庫交易保持極短，而「一定要發出去」由重試保證。收在核心判斷：跨系統的原子性做不到，只能用本地原子性加補償逼近，而 Outbox 正是把不可能的需求換成可實現的需求。

### 批次作業的交易該怎麼設計？

**核心答案**：**分批提交而非一個大交易**。處理一百萬列時，不要用一個交易——而是**每一千或一萬列提交一次**。這樣單次交易短、鎖持有時間短、undo 可以被及時清理、複製延遲平滑、而且中斷時已完成的部分不必回滾。**代價是失去了整批的原子性**——所以需要**斷點續傳的設計**（記錄處理到哪裡）與**冪等性**（重跑不會產生錯誤結果）。

**詳細解析**：「批次大小」的選擇是一個實測問題。太小則提交的開銷（每次提交要寫 binlog、可能要 fsync）佔比過高；太大則回到長交易的問題。經驗上一千到一萬列是常見的起點，但應該依實際的列寬與寫入量調整。 還有一個容易忽略的細節：批次之間應該有短暫的間隔（幾十毫秒），讓其他交易有機會取得鎖、也讓複製有機會追上——否則一個連續跑的批次作業會持續佔用資源，把線上查詢的延遲推高。這種「主動讓出」的設計在所有背景批次作業中都適用，而且它讓批次作業從「與線上業務競爭」變成「利用空隙執行」。很多批次作業造成的線上事故，根因就是它跑得太快太滿。

**面試回答方式**：給**分批提交**的做法與五個好處（交易短、鎖時間短、undo 及時清理、複製平滑、中斷不必全部回滾），並誠實給出代價（失去整批原子性，需要斷點續傳與冪等）。加分點是**批次大小是實測問題**（太小提交開銷佔比高、太大回到長交易），一千到一萬是起點。真正的深度是**批次之間應該有短暫間隔**讓其他交易取得鎖、讓複製追上——這種「主動讓出」讓批次作業從「與線上競爭」變成「利用空隙執行」，而很多批次造成的線上事故根因就是它跑得太快太滿。
