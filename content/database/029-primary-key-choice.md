# 題目

主鍵該用自增整數還是 UUID？各自的代價是什麼？

## 核心答案

**自增整數**的優勢是**寫入友善**（新資料集中在 B+ 樹的最右端，順序寫、頁面必在記憶體、不會頁分裂）與**體積小**（8 位元組的 bigint）。劣勢是**可預測**（洩漏業務量、也讓 ID 可被枚舉）、**分散式環境下需要協調**（分庫分表時不能各自自增）、以及**在寫入極高時尾端成為熱點**（所有插入競爭同一個頁面的鎖）。

**UUID（v4，隨機）**的優勢是**全域唯一、無需協調、不可預測**。劣勢很嚴重：**插入位置隨機**導致隨機 IO、頁分裂、與嚴重的頁面碎片；**體積大**（16 位元組二進位，如果存成 36 字元的字串更是災難）；而且因為 **InnoDB 的二級索引葉節點存主鍵值**，主鍵變大會讓所有二級索引一起變大。

現在的正確答案通常是「有序的全域唯一 ID」——UUIDv7、ULID、或 Snowflake。它們**前綴是時間戳所以整體遞增**（保留了寫入友善），同時**保有全域唯一與無需協調**的性質。這是一個「兩者的優點都要」的方案，沒有明顯的取捨損失，所以新專案沒有理由再選隨機 UUID。

## 詳細解析

「主鍵影響所有二級索引」這一點值得展開，因為它的影響面遠超直覺。InnoDB 的二級索引葉節點存的是「索引欄位 + 主鍵值」——所以一張有 5 個二級索引的表，主鍵從 8 位元組換成 16 位元組，等於每一列在 5 個地方各多了 8 位元組。在千萬列的表上就是幾百 MB 的額外空間，而那些空間會擠壓 Buffer Pool 能快取的資料量。 如果主鍵是 36 字元的 UUID 字串（`char(36)`），情況更糟——**幾乎是 bigint 的四到五倍**。

**存 UUID 的正確形式是 `BINARY(16)` 而非字串**。字串形式浪費空間、比較更慢、而且如果用了不區分大小寫的 collation 還會有正確性風險。MySQL 8 提供了 `UUID_TO_BIN` 與 `BIN_TO_UUID`，而且 `UUID_TO_BIN(uuid, 1)` 的第二個參數會交換時間戳的位元組順序，讓 UUIDv1 變成有序的——這是在沒有 UUIDv7 之前的一個實用技巧。

自增主鍵的熱點問題在極高寫入下才會顯現。所有插入都在 B+ 樹的最右端，它們競爭同一個頁面的鎖與同一個自增計數器的鎖（`innodb_autoinc_lock_mode` 控制後者的粒度）。每秒幾萬次插入時這會成為瓶頸，此時的解法通常是分表（不同的表有各自的自增序列）而非改主鍵形式。在絕大多數系統上這不是問題——不要為了一個不存在的瓶頸而放棄自增的其他好處。

業務主鍵與代理主鍵的選擇是另一個維度。用「訂單編號」這種有業務意義的值當主鍵，好處是不必額外一個欄位、查詢時直接用；壞處是業務規則變化時主鍵要跟著變（而主鍵被所有二級索引與外鍵引用，改動代價極高）。主流做法是用無意義的代理主鍵（自增或有序 ID），業務編號另外開一個有唯一索引的欄位——這讓「識別」與「業務含義」分開，兩者可以獨立演進。

## 面試回答方式

先給**自增與 UUID 各自的優劣**，並把 **UUID 的劣勢講具體**：隨機插入導致隨機 IO 與頁分裂、體積大、而且因為二級索引葉節點存主鍵值，主鍵變大會讓所有二級索引一起變大。給出現在的正確答案——**有序的全域唯一 ID**（UUIDv7、ULID、Snowflake），前綴是時間戳所以遞增，兩者的優點都要且沒有明顯損失。加分點有三個：用具體數字說明主鍵大小的放大效應（5 個二級索引、千萬列，8 位元組的差異就是幾百 MB，而那擠壓了 Buffer Pool）；**存 UUID 要用 `BINARY(16)` 而非字串**，並提到 `UUID_TO_BIN` 的第二個參數能讓 UUIDv1 變有序；以及**業務主鍵 vs 代理主鍵**——主流做法是代理主鍵加上業務編號的唯一索引，讓識別與業務含義分開、可以獨立演進。

## 講稿

自增整數的優勢是寫入友善跟體積小。新資料集中在 B+ 樹的最右端，是順序寫，頁面必定在記憶體裡，也不會頁分裂。劣勢是可預測、分散式環境下需要協調、還有在寫入極高的時候尾端會成為熱點。

隨機 UUID 的優勢是全域唯一、無需協調、不可預測。但劣勢很嚴重。插入位置隨機導致隨機 IO 跟頁分裂，體積大，而且因為 InnoDB 的二級索引葉節點存的是主鍵值，主鍵變大會讓所有二級索引一起變大。

這一點的影響面遠超直覺。一張有五個二級索引的表，主鍵從八位元組換成十六位元組，等於每一列在五個地方各多了八位元組。千萬列就是幾百 MB，而那些空間會擠壓緩衝池能快取的資料量。

所以現在的正確答案通常是有序的全域唯一 ID，像是 UUIDv7 或雪花演算法。它們的前綴是時間戳所以整體遞增，保留了寫入友善，同時保有全域唯一跟無需協調。這是兩者的優點都要，沒有明顯的取捨損失。

另外我想提一個獨立的維度。用有業務意義的值當主鍵，業務規則變化時主鍵要跟著變，而主鍵被所有二級索引跟外鍵引用，改動代價極高。主流做法是用無意義的代理主鍵，業務編號另外開一個唯一索引的欄位。

## 常見追問

### UUIDv7 與 Snowflake 該怎麼選？

**核心答案**：**UUIDv7 更標準、Snowflake 更緊湊**。UUIDv7 是 RFC 標準（前 48 位元是毫秒時間戳、其餘是隨機），16 位元組、不需要任何協調、也不需要分配機器 ID——這讓它在部署上極其簡單。Snowflake 是 8 位元組（`bigint` 就能存），**體積只有一半**，但需要**分配並管理機器 ID**，而且**依賴時鐘**（回撥要處理）。

**詳細解析**：選擇的關鍵通常是「體積是不是重要」。8 位元組的差距在小表上無所謂，在十億列且有多個二級索引的大表上則是幾十 GB 的差別。反過來，Snowflake 的機器 ID 分配在容器化的環境下是一個真實的麻煩——**Pod 是動態的，機器 ID 要從哪裡拿？** 常見的做法是啟動時從 Redis 或 ZooKeeper 申請一個，但那引入了一個啟動時的外部依賴，而且要處理「申請到的 ID 在異常時沒有被歸還」的問題。**UUIDv7 完全繞過了這個問題**，代價只是多 8 位元組。在容器化、實例動態伸縮的環境下，UUIDv7 通常是更務實的選擇。

**面試回答方式**：給兩者的核心差異（UUIDv7 標準且無需協調、Snowflake 緊湊但需要機器 ID 與時鐘）。給出選擇關鍵：**體積是不是重要**——8 位元組在十億列多索引的表上是幾十 GB。真正的加分點是指出 Snowflake 的機器 ID 分配在容器化環境是真實的麻煩（Pod 動態、要從外部申請、還要處理沒歸還的情況），**而 UUIDv7 完全繞過這個問題**，所以在實例動態伸縮的環境下通常更務實。

### 主鍵能不能修改？

**核心答案**：**技術上可以，實務上幾乎不該**。InnoDB 的聚簇索引以主鍵組織，修改主鍵等於「刪除一列再插入一列」——資料要搬到新的位置，而且**所有二級索引都要更新**（因為它們存的是主鍵值）。加上外鍵引用、應用層的快取、以及可能的外部系統引用，**代價與風險都很高**。

**詳細解析**：這正是「不要用業務值當主鍵」的實際理由——業務值會變（客戶要求改編號、合併帳號、修正輸入錯誤），而技術上的識別碼不該變。如果已經用了業務主鍵而現在需要改，務實的路徑是：新增一個代理主鍵欄位並填值、逐步把外鍵與應用引用改成指向它、最後才切換主鍵——這是一個需要分階段進行的遷移，不能一次完成。更一般的原則是「識別碼應該是不可變的」——這適用於資料庫主鍵、API 的資源 ID、以及分散式系統中的實體識別。可變的識別碼會讓所有引用它的地方都需要同步更新，而那在分散式環境下幾乎不可能做對。

**面試回答方式**：給技術上的代價（等於刪除再插入、所有二級索引要更新、加上外鍵與外部引用）。指出這正是「不要用業務值當主鍵」的實際理由——業務值會變而技術識別碼不該變。給出已經踩到時的遷移路徑（新增代理主鍵、逐步改引用、最後切換）。收在一般原則：**識別碼應該是不可變的**，適用於主鍵、API 資源 ID、分散式實體識別，因為可變識別碼會讓所有引用處都需要同步更新，那在分散式環境下幾乎不可能做對。

### 分庫分表時主鍵該怎麼設計？

**核心答案**：兩個要求同時成立——**全域唯一**（不同分片的 ID 不能重複）與**分片友善**（能從 ID 推出或至少不妨礙分片鍵的計算）。常見的方案有三種：**全域有序 ID**（Snowflake 或 UUIDv7，最通用）、**每個分片一段自增區間**（分片 1 用 1 到 1000 萬、分片 2 用 1000 萬到 2000 萬，簡單但擴容時要重新規劃）、以及**自增步長**（N 個分片各自以 N 為步長，第 i 個分片從 i 開始——同樣有擴容的問題）。

**詳細解析**：「分片鍵與主鍵是不是同一個」是一個獨立且更重要的決定。如果主鍵就是分片鍵（例如用 `user_id` 分片且 `user_id` 是主鍵），查詢時可以直接路由；如果不是（例如用 `user_id` 分片但主鍵是訂單 ID），那麼「依訂單 ID 查詢」就必須廣播到所有分片——這是分庫分表最常見的痛點。處理方式是建立「訂單 ID 到分片」的映射表（一個額外的查詢）或者把分片鍵編進主鍵（讓訂單 ID 的某幾位是使用者 ID 的雜湊，於是從訂單 ID 就能推出分片）。後者是基因法，很優雅但讓 ID 的格式與分片策略耦合——分片數改變時 ID 的解讀也要改，這是它的代價。這個「查詢維度與分片維度不一致」的問題，是分庫分表設計中最需要提前想清楚的一件事。

**面試回答方式**：給兩個要求與三種方案。真正的重點是提出「分片鍵與主鍵是不是同一個」這個更重要的獨立決定——不同的話「依主鍵查詢」就要廣播到所有分片，這是分庫分表最常見的痛點。給兩種處理方式（映射表、把分片鍵編進主鍵的基因法）並誠實指出基因法的代價：ID 格式與分片策略耦合，分片數改變時 ID 的解讀也要改。收在判斷：這是分庫分表設計中最需要提前想清楚的一件事。
