# 題目

分散式鍵值儲存的單一節點內部，寫入與讀取分別經過哪些步驟？為什麼寫入要先進 commit log 與記憶體，而不是直接寫到最終的資料檔？這種設計讓讀取付出了什麼代價、又如何補救？

## 核心答案

**寫入路徑**：請求先**追加寫入 commit log**（純順序寫，用於崩潰後重放復原），接著更新**記憶體中的 memtable**（有序結構，如跳表）此時即可回應成功。當 memtable 達到門檻，就整批**刷寫成一個不可變的 SSTable 檔案**（Sorted String Table，鍵有序排列）落到磁碟，並開啟新的 memtable 繼續接收寫入。**讀取路徑**：先查 memtable（最新資料在此），未命中則由新到舊逐一查詢各個 SSTable。這個設計把寫入變得極快——**全部都是順序寫、且不需要在寫入當下做任何排序或原地更新**，但代價是**讀取變複雜**：同一個鍵可能散落在 memtable 與多個歷史 SSTable 中，最壞情況要查遍所有檔案。補救手段有三：**（1）bloom filter**——為每個 SSTable 建立一個記憶體中的機率性集合，先廉價判斷「這個鍵**一定不在**這個檔案裡」，直接跳過絕大多數無謂的磁碟存取；**（2）稀疏索引**——記錄每個 SSTable 中部分鍵的位移，讓查找能直接跳到大致位置再局部掃描；**（3）壓實（compaction）**——背景把多個 SSTable 合併成更少、更大的檔案，同時丟棄被覆蓋的舊值與已刪除的鍵，減少讀取需要查找的檔案數量。

## 詳細解析

**這是一次刻意的「寫入優化、讀取補救」取捨**：傳統 B+ 樹（見 [[001-btree-index.md]]）在寫入時就維持全域有序——資料被寫到它該在的位置，因此讀取可以直接定位、效率極高且穩定。代價是寫入必須**原地更新磁碟上的特定位置**，這在機械磁碟上意味著隨機 I/O，即使在 SSD 上也會造成寫入放大（Write Amplification）與頁面改寫。LSM 的思路完全相反：**寫入時什麼都不整理，只管追加**把整理工作全部推遲到背景的壓實階段。這使得寫入路徑上不存在任何隨機 I/O 與讀取-修改-寫回的循環，寫入吞吐可以大幅提高，特別適合寫入密集的工作負載。但「不整理」的帳最終要還——讀取因此必須面對散落在多處的資料，這就是後面所有補救機制存在的理由。理解這個取捨的方向性很重要：**LSM 不是「更好的 B+ 樹」，而是把成本從寫入端搬到讀取端與背景維護的另一種分配方式**，選哪一種取決於工作負載是寫多還是讀多。

**commit log 與 memtable 的分工**：兩者看似都在「記錄剛寫入的資料」，職責卻完全不同。commit log 是**為了持久性**——記憶體中的 memtable 在斷電時會消失，若沒有 commit log，已經回應「成功」的寫入就會遺失，違反了對使用者的承諾；它是純追加的順序寫，因此極快且內容不需要有序（只要能重放即可）。memtable 是**為了服務讀取與後續的有序刷寫**——它必須是有序結構，這樣讀取能高效查找，刷成 SSTable 時也能直接順序輸出而不需要排序。理解這個分工可以回答一個常見疑問：「既然都寫了 commit log，為什麼還要 memtable？」——因為 commit log 是為了復原而設計的，它按寫入時間排列、可能包含同一個鍵的多個版本，完全不適合用來服務查詢。

**SSTable 為什麼要不可變**：一旦刷寫完成，SSTable 檔案就不再被修改，更新與刪除都是**寫入新的版本到新的檔案**（刪除寫入一個墓碑標記）。不可變帶來幾個關鍵好處：**讀取完全不需要加鎖**（檔案內容永遠不會變，多執行緒可以自由並行讀）、**壓實可以在背景安全進行**（合併時讀取舊檔案不影響正在服務的讀取，合併完成後原子地切換）、**快取極為友善**（快取的內容永不失效）。代價是空間放大（Space Amplification）——同一個鍵的多個歷史版本會同時存在於不同檔案中，直到壓實把它們合併掉，這也是為什麼壓實不只是效能優化，更是**回收空間的必要機制**。

**讀取補救的三個機制各自解決不同層面的問題**：bloom filter 解決的是「**要不要碰這個檔案**」——它以極小的記憶體代價（每個鍵約數位元）提供「一定不存在」的確定答案與「可能存在」的機率答案，讓大部分不含目標鍵的 SSTable 被直接跳過，完全不產生磁碟 I/O；它會有偽陽性（誤判為可能存在）但絕不會有偽陰性，因此不會漏掉資料（見 [[../redis/024-bloom-filter.md]]）。稀疏索引解決的是「**在這個檔案的哪個位置**」——完整索引每個鍵會佔用太多記憶體，只索引每隔一段距離的鍵，就能把查找範圍縮小到一個小區塊再局部掃描，用少量額外掃描換取大幅減少的索引記憶體。壓實解決的是「**檔案數量本身**」——前兩者都是在既定的檔案數量下優化單次查找，只有壓實能從根本上減少需要查找的檔案數，同時回收空間。三者是不同層次的補救，缺一都會讓讀取效能明顯劣化。

## 面試回答方式

先把兩條路徑各自的步驟講清楚（寫入：commit log → memtable → 刷成 SSTable；讀取：memtable → 由新到舊查 SSTable），再用一句話點出設計的本質——「這是一次刻意的取捨：寫入路徑上完全沒有隨機 I/O 與原地更新，代價是把整理工作推遲到背景，讀取因此要面對散落在多處的資料」。與 B+ 樹對比能大幅提升說服力——「B+ 樹在寫入時就維持有序，讀取直接定位但寫入是隨機 I/O；LSM 反過來，寫入只管追加，成本被搬到讀取端與背景壓實，**LSM 不是更好的 B+ 樹，而是成本的另一種分配方式**，選哪個看工作負載是寫多還是讀多」。接著回答容易被追問的「既然有 commit log 為什麼還要 memtable」——「兩者職責不同：commit log 為了持久性，純追加、按時間排列、只為重放而存在；memtable 為了服務讀取與有序刷寫，必須是有序結構」。談讀取補救時，把三個機制**按層次**說明而非平行列舉——bloom filter 決定「要不要碰這個檔案」、稀疏索引決定「在檔案的哪個位置」、壓實從根本上減少「檔案的數量」。最後補上 SSTable 不可變帶來的好處（讀取免鎖、壓實可安全背景進行、快取永不失效）與代價（空間放大，所以壓實也是回收空間的必要機制）。

## 常見追問

### 刪除一筆資料時，LSM 為什麼不能直接把它移除？墓碑（tombstone）會帶來什麼問題？

**核心答案**：因為要刪除的資料**可能存在於多個不可變的 SSTable 中**，而這些檔案依設計不能被修改——若只在最新的檔案裡「移除」，讀取時仍會在更舊的檔案中找到它，刪除等於無效。因此 LSM 的刪除是**寫入一個墓碑標記**（記錄「這個鍵已被刪除」），讀取時由新到舊查找，一旦先遇到墓碑就判定該鍵不存在，正確地遮蔽了舊檔案中的殘留值。墓碑帶來的問題有三：**（1）空間無法立即回收**——被刪除的資料仍佔用磁碟，直到壓實把墓碑與它遮蔽的所有舊版本一起清除；**（2）讀取效能受影響**——大量墓碑會讓查找過程需要走訪更多資料，在「刪除很多但很少新增」的場景尤其明顯；**（3）墓碑本身不能太早清除**——必須確認它遮蔽的所有舊版本都已被合併掉，否則清除墓碑會讓舊值「復活」。

**詳細解析**：這題考察是否理解**不可變性這個設計選擇的連鎖後果**。不可變帶來了讀取免鎖、快取友善、壓實安全等好處，但它也剝奪了「就地移除」這個最直觀的刪除方式，迫使刪除必須用「新增一筆記錄來表達否定」這種間接手法。這是一個很有代表性的權衡——**當你選擇讓資料不可變，所有的變更就都只能表現為追加，包括「否定」**。而以追加表達否定，必然導致資料量在短期內不減反增（刪除操作反而寫入了新資料），空間回收被推遲到壓實階段。墓碑清除時機的問題尤其微妙，值得展開：假設鍵 K 的舊值在 SSTable-1，墓碑在 SSTable-3，如果壓實時只處理 SSTable-3 而把墓碑當作「已無用」清掉，那麼下次讀取 K 時，查找會一路走到 SSTable-1 並找到那個本該被刪除的舊值——**資料復活**。因此墓碑只有在壓實過程**同時涵蓋了所有可能含有該鍵舊版本的檔案**時，才能被安全丟棄，這給壓實策略施加了額外的約束。在分散式環境中這個問題還會更嚴重：如果某個副本在墓碑被清除後才收到修復，可能因為看不到墓碑而把舊值重新散播回去，因此分散式儲存通常會為墓碑設定一個**明顯長於預期修復週期的保留期限**，確保所有副本都已經知道這次刪除之後，才允許清除。理解「不可變性剝奪了就地移除，迫使刪除以追加一筆否定記錄來表達，因此刪除反而先增加資料量、空間回收被推遲到壓實；墓碑不能早於它所遮蔽的全部舊版本被清除，否則舊值會復活，這對壓實策略構成額外約束；分散式環境下還必須讓墓碑的保留期長於修復週期，否則落後的副本可能把舊值散播回來」，展現你能追蹤一個設計選擇引發的多層後果。

**面試回答方式**：先給出無法直接移除的根本原因——「要刪的資料可能散落在多個不可變的 SSTable 裡，只在最新檔案裡移除，讀取仍會在更舊的檔案找到它」。說明墓碑的運作——「寫入一個刪除標記，讀取由新到舊查找，先遇到墓碑就判定不存在」。把它提升到設計原則層次——「這體現了一個代表性的權衡：選擇讓資料不可變，所有變更就只能表現為追加，**包括否定**所以刪除反而先增加了資料量」。逐一給出三個問題，其中把墓碑清除時機講具體最能加分——「假設舊值在 SSTable-1、墓碑在 SSTable-3，壓實時若只處理 SSTable-3 就把墓碑清掉，下次讀取會一路走到 SSTable-1 找到那個本該被刪的值，資料就復活了；所以墓碑只有在壓實同時涵蓋所有可能含該鍵舊版本的檔案時才能安全丟棄」。最後補分散式的加碼——「墓碑保留期還必須長於修復週期，否則落後的副本可能因為沒看到墓碑而把舊值散播回來」。

### 壓實（compaction）有哪些策略？它們的取捨是什麼？

**核心答案**：主要有兩大類。**分層壓實（Leveled）**——把 SSTable 組織成多個層級，每一層內的檔案**鍵範圍互不重疊**，且每層容量按倍數遞增；新資料從上層逐步合併下沉。優點是**讀取效能好且穩定**（每層最多只需查一個檔案，因為層內無重疊）、空間放大低（同一鍵的重複版本少）；缺點是**寫入放大高**（同一筆資料在下沉過程中會被反覆重寫多次）。**大小分層壓實（Size-Tiered）**——把大小相近的 SSTable 湊在一起合併成更大的檔案。優點是**寫入放大低**（合併次數少）；缺點是**讀取可能需要查很多檔案**（同層檔案的鍵範圍會重疊）且**空間放大高**（合併前同一鍵的多個版本並存，且合併瞬間需要接近兩倍的暫時空間）。選擇取決於工作負載：**讀多寫少選分層**，**寫多讀少選大小分層**。這實際上是「寫入放大、讀取放大、空間放大」三者無法同時最佳化的取捨。

**詳細解析**：這題考察是否理解儲存引擎領域的一個核心命題——**RUM 取捨（讀取放大、更新放大、記憶體/空間放大三者難以兼得）**，以及壓實策略正是在這個三角上選擇位置的旋鈕。理解的關鍵在於看清每一種放大的來源。寫入放大來自**同一筆資料被重寫的次數**：分層壓實中，一筆資料從最上層下沉到最底層，沿途每一次合併都要把它重寫一遍，層數越多、放大越嚴重；大小分層只在同量級檔案累積到一定數量時才合併，重寫次數少得多。讀取放大來自**一次查詢需要檢查的檔案數**：分層壓實因為層內鍵範圍不重疊，每層最多命中一個檔案，總數約等於層數，可預測且較小；大小分層同層檔案範圍重疊，可能每個都得查（雖有 bloom filter 大幅緩解，但仍不如前者穩定）。空間放大來自**同一鍵的過期版本存活多久**：分層壓實持續且積極地合併，過期版本很快被清除；大小分層等到累積足夠檔案才合併，期間重複版本一直佔用空間，而且合併大檔案時需要額外的暫時空間。認識到這三者由不同機制驅動、且改善其一往往惡化其二，就能理解為什麼不存在「最好的壓實策略」——只有「最適合這個工作負載的策略」。這也解釋了實務上常見的做法：許多儲存引擎允許**依 column family 或表分別設定壓實策略**，讓同一個系統中讀多與寫多的資料各自採用合適的方案，而非全域統一。理解「壓實策略是在寫入放大、讀取放大、空間放大這個三角上選位置的旋鈕；寫入放大來自資料被重寫的次數、讀取放大來自需檢查的檔案數、空間放大來自過期版本存活的時間；分層壓實讀取穩定空間小但寫入放大高，大小分層相反；不存在最好的策略只有最適合工作負載的策略，因此實務上常允許不同資料各自設定」，展現你掌握這個領域的核心取捨框架。

**面試回答方式**：先給出兩大類策略與各自的組織方式（分層：層內鍵範圍不重疊、容量倍增、逐層下沉；大小分層：大小相近的檔案湊在一起合併）。接著把取捨放進一個明確的框架，這比零散列舉優缺點有力得多——「這本質上是寫入放大、讀取放大、空間放大三者無法兼得的取捨，壓實策略就是在這個三角上選位置的旋鈕」。逐一說明每種放大的來源——「寫入放大來自同一筆資料被重寫幾次，分層壓實沿途每層都重寫一遍所以高；讀取放大來自一次查詢要檢查幾個檔案，分層因層內不重疊所以每層最多一個、可預測；空間放大來自過期版本存活多久，大小分層要等累積足夠檔案才合併所以高，而且合併大檔案時還需要接近兩倍的暫時空間」。給出選擇準則（讀多寫少選分層、寫多讀少選大小分層），最後補實務做法——「許多引擎允許不同的表或 column family 各自設定策略，而不是全域統一」。

### memtable 還沒刷寫就發生節點崩潰，資料會遺失嗎？commit log 要多久清理一次？

**核心答案**：**不會遺失**，這正是 commit log 存在的目的——節點重啟後，會**重放 commit log 中尚未被刷寫的部分**，重建崩潰前的 memtable 狀態，那些已經回應成功但還在記憶體中的寫入因此被復原。至於 commit log 的清理時機：一段 log 只有在**它所涵蓋的所有寫入都已經隨 memtable 刷寫成 SSTable 並落盤之後**才能安全刪除，因為在那之後這些資料已經有了持久的家。實務上通常把 commit log 切成多個區段輪替，每當一次 memtable 刷寫完成，就把對應的舊區段標記為可回收。需要注意的是，若 commit log 的寫入本身沒有真正落到磁碟（例如只寫進作業系統的頁快取而未 fsync），崩潰時仍可能遺失——因此**持久性的強度實際上取決於 fsync 的策略**：每次寫入都 fsync 最安全但最慢，定期批次 fsync 較快但會有一個小的遺失視窗，這是另一個明確的取捨。

**詳細解析**：這題考察是否理解崩潰復原的完整鏈條，以及「寫入成功」這個承諾的實際強度取決於什麼。理解的關鍵在於看清 commit log 與 memtable 構成的是一組**互補的持久性保證**：memtable 提供快速的讀取服務但不持久，commit log 提供持久性但不適合查詢，兩者合起來才讓「寫入立即回應成功」這件事既快速又安全。復原流程之所以正確，依賴於一個嚴格的順序約束——**必須先確保 commit log 寫入成功，才能回應客戶端成功**，如果順序反過來（先回應、再寫 log），崩潰時就會出現「使用者以為寫成功了，但系統毫無記錄」的情況，這是最嚴重的持久性違約。清理時機的約束同樣體現了這種嚴格性：只有當資料在**兩個地方之一**（commit log 或已落盤的 SSTable）確實存在時才算安全，因此清理 log 必須等到刷寫完成並落盤，任何提早清理都會製造出一個資料只存在於記憶體的危險窗口。而 fsync 這個細節則揭示了一個常被忽略的層次——**「寫入檔案」與「資料真的在磁碟上」之間還隔著作業系統的頁快取**，程式呼叫 write 成功只代表資料交給了作業系統，若此時整台機器斷電，頁快取中的內容一樣會消失。因此嚴格的持久性必須顯式呼叫 fsync 強制落盤，而 fsync 是昂貴的操作，這就形成了「持久性強度對上寫入延遲」的取捨：多數系統提供可設定的策略，允許在「絕對不丟」與「可能丟失最近數毫秒」之間依業務需求選擇。理解「commit log 與 memtable 是互補的持久性保證，復原正確性依賴『先確保 log 寫入成功才回應客戶端』這個嚴格順序；log 只能在其涵蓋的寫入都已刷寫落盤後清理，提早清理會製造只存在於記憶體的危險窗口；而 write 成功不等於資料在磁碟上，中間隔著作業系統頁快取，真正的持久性取決於 fsync 策略，這構成持久性強度與寫入延遲的取捨」，展現你能追究到持久性保證的實際邊界而非停在概念層。

**面試回答方式**：先直接回答「不會遺失，重啟時重放 commit log 中尚未刷寫的部分，重建 memtable」。點出保證成立所依賴的嚴格順序，這是關鍵——「前提是必須先確保 commit log 寫入成功才回應客戶端；如果順序反過來，崩潰時就會出現使用者以為寫成功、系統卻毫無記錄的最嚴重違約」。回答清理時機時給出安全條件——「一段 log 只有在它涵蓋的所有寫入都已隨 memtable 刷寫成 SSTable 並落盤後才能刪除，提早清理會製造出資料只存在於記憶體的危險窗口」，並補實務做法（分區段輪替，刷寫完成即標記舊區段可回收）。最後主動挖到更深一層，這最能展現深度——「而且 write 成功不等於資料真的在磁碟上，中間隔著作業系統的頁快取，整機斷電一樣會丟；真正的持久性強度取決於 fsync 策略：每次寫入都 fsync 最安全但最慢，定期批次 fsync 較快但留下一個小的遺失視窗」。
