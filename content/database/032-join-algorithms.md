# 題目

資料庫怎麼執行 JOIN？MySQL 8 的 Hash Join 解決了什麼問題？

## 核心答案

三種主要演算法。**巢狀迴圈連接（Nested Loop Join）**——對驅動表的每一列，去被驅動表查找匹配的列。如果被驅動表的連接欄位有索引，這是很好的演算法（每次查找是 O(log n)）；**沒有索引就退化成 O(n×m) 的災難**。

**區塊巢狀迴圈（Block Nested Loop）**——MySQL 8 之前在沒有索引時的做法：把驅動表的多列讀進 `join_buffer`，一次掃描被驅動表就能匹配緩衝區裡的所有列，把掃描次數從 n 次降到 n/緩衝區容量 次。它只是減輕了災難，沒有解決它。

**雜湊連接（Hash Join）**——MySQL 8.0.18 引入：先掃描較小的表建立雜湊表（build 階段），再掃描較大的表逐列探測（probe 階段）。總成本是 O(n+m)，這才是「沒有索引時」的正確演算法。

所以 MySQL 8 的 Hash Join 解決的是「連接欄位沒有索引時的效能懸崖」——以前這種查詢可能慢一千倍，現在只是慢一點。但它不改變一個事實：有索引的巢狀迴圈通常仍然更快（尤其在只需要少數結果時）。

## 詳細解析

**「驅動表的選擇」是 JOIN 效能的關鍵**。巢狀迴圈的成本大致是「驅動表的列數 × 在被驅動表查找一次的成本」——所以應該用結果集較小的表當驅動表。最佳化器會嘗試決定順序，但在有多個表 JOIN 且統計不準時可能選錯。`EXPLAIN` 的輸出順序就是連接順序，**第一行是驅動表**。`STRAIGHT_JOIN` 可以強制順序，但與其他 hint 一樣是最後手段。

**Hash Join 的記憶體限制要注意**。build 階段的雜湊表放在 `join_buffer_size` 裡；**放不下時會溢出到磁碟**（分批處理，把兩個表都依雜湊值分成多個檔案，再逐批在記憶體中連接）。**溢出會顯著變慢**，所以 `join_buffer_size` 在有大 JOIN 的系統上值得調整——**但要記得它是每連線分配的**，設太大加上高連線數會吃掉大量記憶體。

**JOIN 的數量本身是一個設計訊號**。一個 JOIN 了七八張表的查詢，即使每一步都走索引，最佳化器要考慮的連接順序組合也是階乘級的（MySQL 有 `optimizer_search_depth` 限制搜尋深度，超過就用貪心）。這意味著大型 JOIN 的執行計畫穩定性較差，而且難以推理。實務上的處理是：拆成多個查詢在應用層組合、或者用反正規化減少 JOIN、或者為報表類的複雜查詢建立專門的物化視圖。

分散式資料庫下 JOIN 的代價完全不同。跨分片的 JOIN 需要在節點之間搬移資料（廣播小表、或者依連接鍵重分佈），**網路成本遠超本地的 CPU 成本**。所以分庫分表之後，「盡量避免跨分片 JOIN」成為一個硬性的設計約束——這通常意味著要調整分片鍵（讓經常一起查詢的資料落在同一分片）或者接受反正規化。

## 面試回答方式

先給**三種演算法**與各自的成本特性，並強調巢狀迴圈在有索引時很好、沒索引時是 O(n×m) 的災難，而 **Block Nested Loop 只是減輕災難沒有解決它**。給出 Hash Join 的定位——它解決的是「連接欄位沒有索引時的效能懸崖」，但有索引的巢狀迴圈通常仍然更快（尤其只需要少數結果時）。加分點有三個：**驅動表的選擇是關鍵**（成本是驅動表列數乘以單次查找成本，所以該用結果集小的當驅動），`EXPLAIN` 的第一行就是驅動表；Hash Join 的記憶體放不下會溢出到磁碟並顯著變慢，而 `join_buffer_size` 是每連線分配的、設太大會吃掉大量記憶體；以及 **JOIN 的數量本身是設計訊號**——七八張表的連接順序組合是階乘級的，計畫穩定性差，實務上該拆查詢、反正規化、或建物化視圖。

## 講稿

三種主要演算法。巢狀迴圈是對驅動表的每一列，去被驅動表查找匹配的列。如果被驅動表的連接欄位有索引，這是很好的演算法。沒有索引就退化成兩個表相乘的災難。

區塊巢狀迴圈是 MySQL 8 之前在沒有索引時的做法，把驅動表的多列讀進緩衝區，一次掃描被驅動表就能匹配緩衝區裡的所有列。但它只是減輕了災難，沒有解決它。

雜湊連接是 MySQL 8.0.18 引入的。先掃描較小的表建立雜湊表，再掃描較大的表逐列探測，總成本是兩個表的和。這才是沒有索引時的正確演算法。

所以 Hash Join 解決的是連接欄位沒有索引時的效能懸崖。以前這種查詢可能慢一千倍，現在只是慢一點。但它不改變一個事實，有索引的巢狀迴圈通常仍然更快，尤其在只需要少數結果的時候。

驅動表的選擇是 JOIN 效能的關鍵。成本大致是驅動表的列數乘以在被驅動表查找一次的成本，所以應該用結果集較小的表當驅動表。執行計畫的第一行就是驅動表。

最後我想說，JOIN 的數量本身是一個設計訊號。連接七八張表的話，最佳化器要考慮的順序組合是階乘級的，執行計畫的穩定性會很差。

## 常見追問

### 什麼時候該用反正規化避免 JOIN？

**核心答案**：當**JOIN 的成本是真實的瓶頸**且冗餘資料的維護成本可以接受時。判斷的兩個問題是：**這個 JOIN 出現在熱路徑上嗎**（一天跑一次的報表不值得反正規化）、以及**被冗餘的欄位變動頻繁嗎**（`user_name` 這種很少改的適合冗餘，`order_status` 這種頻繁改的則會讓同步成為負擔）。

**詳細解析**：反正規化的真正代價是「一致性的維護責任從資料庫轉移到了應用」。正規化的設計下，使用者改名字只要改一個地方；反正規化之後，所有冗餘了 `user_name` 的表都要同步更新——而如果漏了一處，或者更新過程中崩潰，資料就不一致了。**處理方式有三種**：在同一個交易裡一起更新（簡單，但擴大了交易範圍）、用事件驅動非同步更新（最終一致，需要處理失敗與重試）、或者接受不一致並定期修補（適合非關鍵欄位）。選哪一種取決於「不一致多久是可接受的」。還有一個常被忽略的選項：把冗餘做成「快照」而非「複本」——訂單裡存的是「下單當時的商品名稱與價格」，那本來就該是不變的歷史記錄，**於是根本沒有同步問題**。很多看似需要反正規化的場景，其實是把「當時的值」誤當成「當前的值」。

**面試回答方式**：給兩個判斷問題（是不是熱路徑、被冗餘的欄位變動頻不頻繁）。展開真正的代價是一致性維護責任從資料庫轉移到應用，並給三種同步方式與選擇依據。真正的加分點是提出常被忽略的選項：**把冗餘做成「快照」而非「複本」**——訂單存的是下單當時的商品名稱與價格，那本來就是不變的歷史記錄、根本沒有同步問題；很多看似需要反正規化的場景，其實是把「當時的值」誤當成「當前的值」。

### 為什麼 LEFT JOIN 有時候比 INNER JOIN 慢很多？

**核心答案**：因為 **`LEFT JOIN` 限制了連接順序**。`INNER JOIN` 的兩個表可以互換（結果相同），最佳化器能自由選擇更好的驅動表；`LEFT JOIN` 則必須以左表為驅動——如果左表很大而右表很小，那就是最差的選擇。而且 `LEFT JOIN` 無法把右表的過濾條件下推（那會改變語意），所以右表可能要處理更多列。

**詳細解析**：一個常見的錯誤是「用了 `LEFT JOIN` 但在 `WHERE` 裡對右表加條件」——`LEFT JOIN t2 ON ... WHERE t2.status = 'A'` 實際上等價於 `INNER JOIN`（因為 `WHERE` 會把右表為 NULL 的列過濾掉），但最佳化器不一定能識別並轉換，於是白白承受了 `LEFT JOIN` 的限制。正確的寫法是要嘛改成 `INNER JOIN`（如果那是本意），要嘛把條件放進 `ON` 子句（如果本意是「保留左表全部、只是右表的匹配要符合條件」）。這是一個 `ON` 與 `WHERE` 語意差異造成的經典錯誤——它同時是正確性問題與效能問題，而且寫出來的人通常沒有意識到自己改變了語意。

**面試回答方式**：給主要原因——**`LEFT JOIN` 限制了連接順序**（必須以左表驅動），而 `INNER JOIN` 讓最佳化器能自由選擇。真正的加分點是點出常見錯誤：`LEFT JOIN` 加上 `WHERE` 裡對右表的條件實際上等價於 `INNER JOIN`，但白白承受了限制。給出正確寫法（改成 `INNER JOIN`，或把條件放進 `ON`）並指出這是 **`ON` 與 `WHERE` 語意差異的經典錯誤**——同時是正確性與效能問題，而寫的人通常沒意識到改變了語意。

### 分庫分表之後 JOIN 怎麼處理？

**核心答案**：四種做法，依成本排序。**避免**——調整分片鍵讓經常一起查詢的資料落在同一分片（**這是最好的答案**）。**廣播小表**——維度表（省份、分類）在每個分片都存一份，JOIN 變成本地操作。**應用層組合**——分別查兩個表再在應用層合併（要注意分頁與排序在這種模式下很難做對）。**反正規化**——把需要的欄位冗餘到同一張表。

**詳細解析**：**「應用層組合」的陷阱值得展開**：分別查兩張表再合併，在有分頁與排序時幾乎無法正確實作——要取「按時間排序的第 100 到 110 筆」，你不知道要從每個分片各取多少筆才夠。正確但昂貴的做法是每個分片各取前 110 筆再全域排序取第 100 到 110（這就是「分片取 K、合併取 K」模式），成本隨頁碼線性上升，深分頁時完全不可行。所以分庫分表的系統應該從一開始就避免深分頁——改用游標式分頁（用「上一頁最後一筆的排序鍵」當起點），它不需要跳過前面的資料，成本與頁碼無關。這個約束應該在設計分片方案時就被提出，而不是等產品要求「跳到第 500 頁」時才發現做不到。

**面試回答方式**：給四種做法並指出**「避免」是最好的答案**（調整分片鍵讓常一起查的資料同片）。重點展開應用層組合在有分頁與排序時的陷阱——不知道每個分片要取多少筆，正確做法是各取前 N 筆再全域排序，成本隨頁碼線性上升、深分頁完全不可行。收在設計建議：分庫分表的系統應該從一開始就避免深分頁，改用游標式分頁，而這個約束該在設計分片方案時就提出，不是等產品要求「跳到第 500 頁」才發現。
