# 題目

PostgreSQL 與 MySQL 在架構上有哪些關鍵差異？選型時該考慮什麼？

## 核心答案

四個層面的差異最重要。

**MVCC 的實作**——**InnoDB 把舊版本放在 undo log 裡**（資料頁只存最新版），**PostgreSQL 則把每個版本都存在資料頁裡**（舊版本標記為死元組，由 VACUUM 清理）。**這帶來完全不同的維運特性**：InnoDB 需要擔心 undo 膨脹與版本鏈變長，PostgreSQL 則需要擔心表膨脹與 VACUUM 跟不上（以及著名的事務 ID 回繞問題）。

**索引結構**——InnoDB 是**聚簇索引**（資料按主鍵組織，二級索引存主鍵值），PostgreSQL 是**堆表加獨立索引**（所有索引都存實體位置 ctid）。**所以 PostgreSQL 沒有「二級索引要回表」的概念，但它的 UPDATE 可能要更新所有索引**（HOT 更新是針對這一點的優化）。

**功能廣度**——PostgreSQL 有**部分索引、表達式索引、多種索引類型（GiST、GIN、BRIN）、豐富的資料型別（陣列、範圍、JSONB、地理）、CTE 與視窗函數的完整支援、以及可擴充的型別與函式系統**。MySQL 在這些方面明顯較弱。

**生態與運維**——MySQL 的複製與分片生態更成熟、雲端託管更普及、社群資源更多；PostgreSQL 近年追趕迅速但在超大規模的分片方案上仍較少見。

## 詳細解析

**MVCC 實作差異的實務後果值得展開**。PostgreSQL 的 UPDATE 實際上是「插入一個新版本並把舊版本標記為死」——**所以一個頻繁更新的表會快速膨脹**，而且**每個索引都要新增一項指向新版本**。**HOT（Heap-Only Tuple）更新是關鍵的優化**：如果更新不涉及任何索引欄位且同一頁有空間，新版本可以放在同一頁並由舊版本指向它，**索引不必更新**。**所以「留出 fillfactor（頁面的預留空間）」在 PostgreSQL 上是一個有意義的調優**，而在 InnoDB 上沒有對應的概念。

**VACUUM 是 PostgreSQL 特有的維運負擔**。它負責回收死元組並更新可見性映射；**跟不上時表會持續膨脹，查詢因為要跳過大量死元組而變慢**。autovacuum 通常夠用，**但在寫入極密集或有長交易的情況下可能跟不上**——而長交易在 PostgreSQL 上的危害與 MySQL 類似（阻止清理），只是表現形式不同（表膨脹而非 undo 膨脹）。**事務 ID 回繞**是更嚴重的問題：PostgreSQL 的事務 ID 是 32 位元的，**接近回繞時資料庫會強制進入唯讀模式以防資料損毀**——這需要監控 `age(datfrozenxid)`。

**「PostgreSQL 的功能更豐富」在實務上意味著什麼**：**部分索引**讓稀疏欄位的索引只有百分之一大；**表達式索引**讓 `WHERE lower(email) = ?` 能走索引；**JSONB 加 GIN 索引**讓半結構化資料的查詢真正可行；**BRIN 索引**讓「按時間追加的超大表」用極小的索引支援範圍查詢。**這些不是錦上添花，而是能改變架構決定的能力**——例如有了 JSONB 與部分索引，某些原本需要引入 MongoDB 或 Elasticsearch 的需求可以留在 PostgreSQL 裡。

**選型的實務建議**：**新專案在沒有特殊限制時，PostgreSQL 通常是更好的預設**（功能更完整、標準相容性更好、擴充性更強）。**選 MySQL 的正當理由是**：團隊已有深厚經驗、需要成熟的分片方案（Vitess）、或者雲端環境對它的支援更好。**「我們一直用 MySQL」本身也是一個真實的理由**——遷移的成本與風險常常超過功能上的收益。

## 面試回答方式

給**四個層面的差異**並把 **MVCC 實作**放在最前面——**InnoDB 用 undo log、PostgreSQL 把版本存在資料頁裡**，由此推出完全不同的維運特性（undo 膨脹 vs 表膨脹與 VACUUM）。給**索引結構**的差異（聚簇 vs 堆表加獨立索引）與它的後果。加分點有三個：**HOT 更新與 fillfactor** 是 PostgreSQL 特有的調優點，在 InnoDB 上沒有對應概念；**事務 ID 回繞**是 PostgreSQL 特有的嚴重問題，接近時會強制唯讀，需要監控；以及**「功能更豐富」在實務上意味著能改變架構決定**——有了 JSONB 加 GIN、部分索引，某些原本需要引入 MongoDB 或 Elasticsearch 的需求可以留在 PostgreSQL 裡。收在選型：**新專案在沒有特殊限制時 PostgreSQL 通常是更好的預設**，而**「我們一直用 MySQL」本身也是真實的理由**。

## 講稿

我認為四個層面的差異最重要。

第一是多版本併發控制的實作。InnoDB 把舊版本放在 undo log 裡，資料頁只存最新版。PostgreSQL 則把每個版本都存在資料頁裡，舊版本標記為死元組由清理程序回收。這帶來完全不同的維運特性，一個要擔心 undo 膨脹跟版本鏈變長，另一個要擔心表膨脹跟清理跟不上。

第二是索引結構。InnoDB 是聚簇索引，二級索引存主鍵值。PostgreSQL 是堆表加獨立索引，所以沒有回表的概念，但它的更新可能要更新所有索引。

第三是功能廣度。PostgreSQL 有部分索引、表達式索引、多種索引類型跟豐富的資料型別。這些不是錦上添花，而是能改變架構決定的能力。有了 JSONB 加上對應的索引，某些原本需要引入文件資料庫的需求可以留在 PostgreSQL 裡。

第四是生態與運維，MySQL 的複製與分片生態更成熟。

選型上，新專案在沒有特殊限制的時候，PostgreSQL 通常是更好的預設。而我一直用 MySQL 本身也是一個真實的理由，遷移的成本跟風險常常超過功能上的收益。

## 常見追問

### PostgreSQL 的 VACUUM 該怎麼監控與調優？

**核心答案**：監控三件事。**表膨脹率**（實際大小對比「如果沒有死元組會是多大」，用 `pgstattuple` 或 `pg_stat_user_tables` 的 `n_dead_tup` 估算）。**autovacuum 的執行頻率與耗時**（`pg_stat_user_tables` 的 `last_autovacuum` 與 `autovacuum_count`）。**最舊事務的年齡**（`age(datfrozenxid)`，接近 `autovacuum_freeze_max_age` 就要警覺回繞問題）。

**詳細解析**：**調優的核心是「讓 autovacuum 跟得上」**。預設的觸發閾值（`autovacuum_vacuum_scale_factor` 預設 0.2，表示死元組達到表的 20% 才觸發）**在大表上意味著要累積大量死元組才啟動**——一億列的表要等兩千萬個死元組。**所以大表應該單獨設定更小的 scale factor**（例如 0.01）或者用絕對值閾值。另外 **`autovacuum_vacuum_cost_delay` 控制它的積極程度**——預設值相當保守，在寫入密集的系統上應該調低（讓它跑得更快）。**這個「預設值是為小型部署設計的、大型部署需要調整」的模式在 PostgreSQL 上很常見**，也是它「開箱即用但需要調優」這個評價的來源。

**面試回答方式**：給三個監控項並特別點出**最舊事務的年齡**與回繞問題。展開調優核心：**預設的 scale factor 0.2 在大表上意味著要累積兩千萬個死元組才觸發**，所以大表應該單獨設定更小的值。加分點是提到 `autovacuum_vacuum_cost_delay` 的預設相當保守。收在觀察：**「預設值是為小型部署設計的」這個模式在 PostgreSQL 上很常見**，也是它「開箱即用但需要調優」評價的來源。

### 兩者的 JSON 支援差多少？

**核心答案**：差距很大。MySQL 的 JSON 型別支援路徑查詢與部分更新，**但索引只能透過「產生欄位加索引」間接達成**——每個要查詢的路徑都要一個產生欄位。PostgreSQL 的 **JSONB 加 GIN 索引**可以**對整個文件建立一個索引**，支援 `@>`（包含）、`?`（鍵存在）等運算子的任意路徑查詢，**不需要事先知道要查哪個欄位**。

**詳細解析**：**這個差距決定了「半結構化資料能不能留在關聯式資料庫」**。如果查詢模式固定（只查幾個特定路徑），MySQL 的產生欄位完全夠用；**如果查詢模式是動態的（使用者可以依任意屬性篩選），MySQL 就做不到，而 PostgreSQL 可以**。**後者正是「原本要引入 MongoDB 的需求」**——而能留在 PostgreSQL 裡意味著少一個系統、少一份維運、以及交易與關聯查詢的能力仍在。**要注意 GIN 索引的代價**：它比 B-tree 大得多、寫入更慢（尤其是 `gin_pending_list_limit` 的批次更新機制）、而且**對於高基數的鍵可能效果不如預期**。**所以「PostgreSQL 能做」不等於「應該用它做所有事」**——當半結構化資料成為核心且量很大時，專門的文件資料庫仍有它的位置。

**面試回答方式**：給精確的差距——MySQL 只能靠產生欄位間接索引（要事先知道查哪個路徑），**PostgreSQL 的 JSONB 加 GIN 可以對整個文件建索引、支援任意路徑查詢**。展開這個差距的意義：**它決定了半結構化資料能不能留在關聯式資料庫**，而查詢模式動態時 MySQL 做不到。誠實給出 GIN 的代價（索引大、寫入慢、高基數鍵效果有限）並收在判斷：**「能做」不等於「應該用它做所有事」**。

### 從 MySQL 遷移到 PostgreSQL 的主要障礙是什麼？

**核心答案**：四類。**SQL 方言差異**——`LIMIT` 語法相近但分頁、字串函式、日期函式、以及 `GROUP BY` 的嚴格程度都不同（PostgreSQL 要求 `SELECT` 的非聚合欄位必須在 `GROUP BY` 裡，MySQL 預設較寬鬆）。**資料型別映射**——`TINYINT`、`ENUM`、`UNSIGNED` 在 PostgreSQL 沒有直接對應。**大小寫敏感性**——PostgreSQL 的識別碼預設轉小寫且字串比較預設區分大小寫，**MySQL 的預設定序不區分**，這會改變查詢結果。**應用層的依賴**——ORM 的方言設定、原生 SQL、以及任何依賴 MySQL 特定行為的邏輯。

**詳細解析**：**「大小寫敏感性」是最容易造成靜默錯誤的一類**。MySQL 預設的 `utf8mb4_0900_ai_ci` 讓 `WHERE name = 'John'` 也能匹配 `'john'`；**遷移到 PostgreSQL 之後那個查詢會找不到資料**——而它不會報錯，只是回傳空結果。**這類「行為改變但不報錯」的差異，比會報錯的語法差異危險得多**，因為它們要靠測試覆蓋才能發現。**所以遷移的驗證重點應該放在「行為比對」而非「能不能跑起來」**：用相同的輸入在兩邊執行相同的查詢並比對結果，**而那需要一套完整的測試資料與自動化的比對工具**。**很多遷移失敗的根因是「跑起來了就以為完成了」**，而行為差異在上線後才逐漸暴露。

**面試回答方式**：給四類障礙。重點展開**「大小寫敏感性」最容易造成靜默錯誤**——MySQL 預設不區分而 PostgreSQL 預設區分，同樣的查詢**不會報錯只是回傳空結果**。給出關鍵判斷：**「行為改變但不報錯」的差異比會報錯的語法差異危險得多**。收在驗證重點：**放在「行為比對」而非「能不能跑起來」**——用相同輸入在兩邊執行並比對結果，**而很多遷移失敗的根因是「跑起來了就以為完成了」**。
