# 題目

分區表（partitioning）與分庫分表（sharding）差在哪？各自適合什麼場景？

## 核心答案

**最根本的差別是「有沒有跨越機器」**。**分區表是單一資料庫實例內的物理拆分**——邏輯上仍是一張表，SQL 完全不變，資料庫負責把查詢路由到正確的分區。**分庫分表是把資料分散到多個資料庫實例**——需要應用層或中介軟體處理路由、跨庫查詢、以及分散式交易。

**所以它們解決的問題不同**。**分區表解決的是「單表太大」造成的管理與查詢問題**：可以只掃描相關的分區（分區裁剪）、可以按分區做維護（刪除舊資料變成 `DROP PARTITION`，瞬間完成）、也可以把不同分區放在不同的磁碟。**但它不解決「單機的容量與吞吐上限」**——所有分區仍在同一個實例上。

**分庫分表解決的才是容量與吞吐**，代價是巨大的複雜度：跨庫 JOIN、分散式交易、全域唯一 ID、以及重分片的困難。

**判斷的順序應該是：先分區、再考慮分庫分表**——因為前者的成本低得多，而且很多「表太大」的問題用分區就解決了。

## 詳細解析

**分區最有價值的場景是「按時間的資料生命週期管理」**。日誌、訂單、事件這類資料通常按時間分區（每月一個分區），**於是「刪除三個月前的資料」變成 `ALTER TABLE ... DROP PARTITION p202401`——瞬間完成、不產生 undo、不影響其他分區**。相比之下 `DELETE FROM ... WHERE created_at < ?` 是一個要跑幾小時、產生大量 undo 與 binlog、還會造成複製延遲的操作。**這個差別大到足以單獨構成使用分區的理由。**

**分區裁剪的前提是「查詢條件包含分區鍵」**。按 `created_at` 分區的表，`WHERE created_at BETWEEN ? AND ?` 只掃描相關分區；**但 `WHERE user_id = ?` 必須掃描所有分區**——**那可能比不分區還慢**（因為要開啟多個分區的檔案）。**這是分區最常見的誤用**：分區鍵的選擇必須配合主要的查詢模式，**而不是「按時間分區看起來很自然」**。

**MySQL 分區的限制要知道**：**主鍵與唯一索引必須包含分區鍵**（否則無法保證全域唯一，因為每個分區的索引是獨立的）——**這個限制常常決定了分區方案的可行性**。另外分區數有上限、外鍵不支援、而且**分區表的查詢在某些情況下無法使用某些優化**。**這些限制加起來，讓分區在 MySQL 上的適用範圍比在 PostgreSQL 或 Oracle 上窄。**

**分庫分表的真正成本在「之後」而非「當下」**。切分本身是一次性的工程，**但之後的每一個新需求都要面對「這個查詢跨不跨庫」**：跨庫的聚合、跨庫的交易、跨庫的分頁、以及重分片時的資料遷移。**所以「什麼時候該分庫分表」的答案通常是「比你以為的更晚」**——先窮盡單機的優化（索引、快取、讀寫分離、分區、以及垂直拆分成多個服務各自的庫），**因為單機的能力比多數人以為的高得多**（現代硬體上單一 MySQL 實例處理幾 TB 資料與數萬 QPS 是可行的）。

## 面試回答方式

先給**最根本的差別**——有沒有跨越機器，並由此推出**它們解決的問題不同**：分區解決「單表太大」的管理與查詢，**但不解決單機的容量與吞吐上限**；分庫分表才解決後者，代價是巨大的複雜度。給判斷順序：**先分區、再考慮分庫分表**。加分點有三個：**分區最有價值的場景是按時間的生命週期管理**——`DROP PARTITION` 瞬間完成，相比 `DELETE` 要跑幾小時並造成複製延遲，**這個差別大到足以單獨構成使用分區的理由**；**分區裁剪的前提是查詢條件包含分區鍵**，否則要掃描所有分區、**可能比不分區還慢**，這是最常見的誤用；以及 **MySQL 的限制（主鍵必須包含分區鍵）常常決定方案的可行性**。收在判斷：**「什麼時候該分庫分表」的答案通常是「比你以為的更晚」**。

## 講稿

最根本的差別是有沒有跨越機器。分區表是單一實例內的物理拆分，邏輯上仍是一張表，SQL 完全不變。分庫分表是把資料分散到多個實例，需要應用層或中介軟體處理路由跟跨庫查詢。

所以它們解決的問題不同。分區解決單表太大造成的管理與查詢問題，可以只掃描相關分區、可以按分區做維護。但它不解決單機的容量與吞吐上限，所有分區仍在同一個實例上。分庫分表解決的才是容量與吞吐。

分區最有價值的場景是按時間的資料生命週期管理。刪除三個月前的資料變成刪除一個分區，瞬間完成、不產生 undo、不影響其他分區。而用條件刪除是一個要跑幾小時、產生大量日誌、還會造成複製延遲的操作。這個差別大到足以單獨構成使用分區的理由。

但有一個最常見的誤用要注意。分區裁剪的前提是查詢條件包含分區鍵。按時間分區的表，用使用者 ID 查詢就必須掃描所有分區，那可能比不分區還慢。所以分區鍵的選擇必須配合主要的查詢模式，而不是按時間分區看起來很自然。

最後，什麼時候該分庫分表，我的答案通常是比你以為的更晚。先窮盡單機的優化，因為單機的能力比多數人以為的高得多。

## 常見追問

### 分區鍵該怎麼選？

**核心答案**：**必須同時滿足三個條件**：**出現在主要的查詢條件裡**（否則無法分區裁剪）、**能被包含在主鍵與唯一索引裡**（MySQL 的硬性限制）、以及**分佈相對均勻**（否則某些分區特別大，失去了拆分的意義）。**時間欄位通常是最好的候選**，因為它同時滿足前兩者且天然遞增。

**詳細解析**：**「必須包含在主鍵裡」這個限制的影響常被低估**。一張以 `id` 為主鍵的表要按 `created_at` 分區，**主鍵必須改成 `(id, created_at)` 的複合主鍵**——這改變了聚簇索引的結構、讓每個二級索引都變大（存的是完整的複合主鍵）、**而且如果應用依賴「主鍵只有 id」的假設（例如 ORM 的設定），那也要改**。**所以分區不是一個「加上去就好」的變更，它會影響表的整體結構。** **在既有的大表上導入分區，實際上是一次完整的表重建**，成本與風險應該按那個等級評估。

**面試回答方式**：給三個必須同時滿足的條件並指出**時間欄位通常是最好的候選**。真正的加分點是展開**「主鍵必須包含分區鍵」的影響常被低估**——主鍵要改成複合的，這改變聚簇索引結構、讓所有二級索引變大、還可能影響應用的假設。收在判斷：**分區不是「加上去就好」的變更，在既有大表上導入實際上是一次完整的表重建**，成本與風險應該按那個等級評估。

### 分庫分表之後怎麼做全域查詢？

**核心答案**：四種做法。**廣播查詢加合併**（查所有分片再在中介層合併，**成本高且分頁難做對**）。**異構索引**（維護一張「非分片鍵到分片」的映射表，先查映射再精確路由）。**同步到搜尋引擎或資料倉儲**（用 CDC 把資料同步到 Elasticsearch 或 ClickHouse，**複雜查詢與聚合都在那裡做**）。**冗餘一份按另一個維度分片的資料**（例如訂單同時按使用者分片與按商家分片各存一份）。

**詳細解析**：**「同步到專門的查詢系統」是大型系統最常見的答案**，因為它同時解決了幾個問題：複雜查詢（搜尋引擎的能力遠超分片後的 MySQL）、聚合分析（列式儲存快幾個數量級）、以及**不影響線上的交易庫**。**代價是引入了資料同步的延遲與一致性問題**——那個系統的資料總是稍舊，而且同步管線本身需要維護與監控。**這個架構的本質是「讀寫分離的極致版本」**：交易走分片的 MySQL、查詢走專門的系統，**兩者用 CDC 連接**。**認出這個模式很重要，因為它是幾乎所有大型系統最終的形狀**——而理解它讓你在設計初期就能為這條路留下空間（例如一開始就用 ROW 格式的 binlog）。

**面試回答方式**：給四種做法。重點展開**「同步到專門的查詢系統」是大型系統最常見的答案**，並說明它同時解決的三個問題（複雜查詢、聚合分析、不影響交易庫）與代價（同步延遲、管線的維護）。真正的加分點是把它定位成**「讀寫分離的極致版本」**——交易走分片 MySQL、查詢走專門系統、用 CDC 連接，並指出**這是幾乎所有大型系統最終的形狀**，理解它讓你在設計初期就能留下空間。

### 什麼訊號表示該分庫分表了？

**核心答案**：四個。**單表的資料量讓維護操作變得不可行**（`ALTER` 要跑一天、備份要跑幾小時、恢復時間超出 RTO）。**單機的寫入吞吐達到上限**（磁碟 IOPS 飽和、或 redo log 的刷新跟不上）。**單機的容量接近上限**（且垂直擴展已經到頂或成本不合理）。**單點的故障影響範圍無法接受**（所有業務共用一個庫）。

**詳細解析**：**要注意這四個訊號中，前三個都有「先試試其他辦法」的空間**。維護操作慢可以用線上變更工具與分區解決；寫入吞吐可以用批次化、減少索引、調整刷新策略改善；容量可以用歸檔冷資料、壓縮、以及型別優化緩解。**第四個（故障影響範圍）則往往是最正當且最難用其他方式解決的理由**——而它其實不需要「分庫分表」這種按資料切分的方案，**用「垂直拆分」（不同的業務用不同的庫）就能達成，而那的複雜度低得多**。**所以「我們需要分庫分表」這個結論，應該先被追問「是水平切還是垂直切」**——很多情況下垂直拆分就夠了，而它不引入跨庫查詢的所有問題。

**面試回答方式**：給四個訊號。真正的重點是指出**前三個都有「先試試其他辦法」的空間**並各給一個替代方案。展開**第四個（故障影響範圍）往往最正當**，但**它不需要水平分片，用垂直拆分就能達成而複雜度低得多**。收在關鍵追問：**「我們需要分庫分表」應該先被追問「是水平切還是垂直切」**——很多情況下垂直拆分就夠了，而它不引入跨庫查詢的所有問題。
