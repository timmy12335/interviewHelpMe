# 題目

資料庫有哪些鎖類型？共享鎖、排他鎖、意向鎖分別是什麼？行鎖和表鎖有什麼區別？

## 核心答案

按「鎖的相容性」分——**共享鎖（S 鎖，Shared Lock）**：多個交易可以同時持有同一份資料的共享鎖（用於「讀」，如 `SELECT ... LOCK IN SHARE MODE`），共享鎖之間不衝突（大家都只是讀），但和排他鎖衝突；**排他鎖（X 鎖，Exclusive Lock）**：同一時間只能有一個交易持有（用於「寫」，如 UPDATE/DELETE 及 `SELECT ... FOR UPDATE`），排他鎖和任何其他鎖（包括共享鎖）都衝突。按「鎖的粒度」分——**表鎖**：鎖住整張表，粒度粗、開銷小但並發度低；**行鎖**：只鎖住涉及的具體行，粒度細、並發度高但開銷相對大（InnoDB 主要用行鎖，MyISAM 只支援表鎖）。**意向鎖（Intention Lock）**是為了「高效判斷表級鎖和行級鎖是否衝突」而引入的一種「表級別的標記鎖」——在對某些行加行鎖之前，先在表級別加一個對應的意向鎖，表明「這個表裡有些行被鎖了」，這樣其他交易想加表級鎖時，只需檢查這個意向鎖標記，不用去掃描表裡每一行看有沒有被鎖，大幅提高判斷效率。

## 詳細解析

**共享鎖（S）與排他鎖（X）——按操作類型分**：

- 共享鎖（S）——多個交易可以同時持有同一資料的 S 鎖（大家都只是「讀」，互不影響）。
- 排他鎖（X）——同一時間只能有一個交易持有 X 鎖，且持有 X 鎖時，其他任何交易都不能再持有這行的 S 鎖或 X 鎖（因為要修改資料，必須獨佔）。
- 相容性——S 和 S 相容（都能讀）、S 和 X 不相容、X 和 X 不相容。

**表鎖與行鎖——按鎖定粒度分**：

- 表鎖——鎖住整張表，加鎖/解鎖開銷小（只需判斷一次），但並發度低（即使兩個交易只是想改表裡完全不同的兩行，也要排隊，因為鎖的是整張表）。MyISAM 引擎只支援表鎖。
- 行鎖——只鎖住涉及的具體行，並發度高（不同行的操作可以並行），但加鎖本身開銷相對大（要精確判斷、管理每一行的鎖狀態）。InnoDB 主要用行鎖（透過索引實現，如果 WHERE 條件沒用上索引，行鎖可能退化成鎖住掃描過的所有行、甚至升級為表鎖）。

**意向鎖——解決「行鎖和表鎖如何高效共存」的問題**：

- 問題背景——如果一個交易對錶裡的某些行加了行級 X 鎖，這時另一個交易想對「整張表」加一個表級鎖（如某些 DDL 操作、或想確保沒有行鎖衝突），資料庫需要判斷「這張表裡有沒有行被鎖住」——如果沒有意向鎖，只能「掃描表裡所有行」逐一檢查有沒有鎖，效率很低。
- 意向鎖的解法——當一個交易要對某些行加 S 鎖或 X 鎖之前，會先在「表級別」加一個對應的意向鎖（意向共享鎖 IS、意向排他鎖 IX），表明「這個表裡『有』某些行被加了 S/X 鎖」（但不記錄具體是哪些行）。之後其他交易想加表級鎖，只需要檢查這個表級的意向鎖標記（一次快速的檢查），就能知道「這張表目前有沒有行級鎖存在」，不需要掃描每一行，大幅提升了判斷效率。

## 面試回答方式

先按兩個維度分類講——「按操作類型：共享鎖(讀、可共享) vs 排他鎖(寫、獨佔)」和「按粒度：表鎖(粗、開銷小並發低)vs 行鎖(細、開銷大並發高)」。意向鎖是這題的深度考點——要講清「它解決的問題」(高效判斷表級鎖和行級鎖是否衝突、不用掃描全表)，這是意向鎖存在的核心動機，很多人只知道有意向鎖這個名詞、講不出它解決什麼問題。能講清這幾種鎖的相容關係和意向鎖的具體作用，展現你理解資料庫鎖機制的設計思路而非死記名詞。

## 常見追問

### 為什麼 InnoDB 的行鎖是「透過索引實現」的？這意味著什麼？

**核心答案**：InnoDB 的行鎖，本質是「鎖在索引記錄（B+ 樹的葉子節點）上」，而不是直接鎖在「行的實體資料」上。這意味著——**如果查詢條件沒有用上索引（走全表掃描）**，InnoDB 沒辦法精確地只鎖住「符合條件的那幾行」，而是要「鎖住掃描過程中檢查到的每一行」（實際上可能鎖住了整張表的所有行，效果上退化成類似表鎖），因為它必須逐行掃描判斷是否符合條件、並鎖住檢查過的行以保證一致性。這也是「索引對於併發控制效能的另一個重要意義」——不只是加速查詢，還直接影響「行鎖能鎖多精確、並發度有多高」；如果一個 UPDATE 語句因為沒用上索引而導致鎖住了大量無關的行，會嚴重降低系統的並發能力，造成大量交易互相等待。

**詳細解析**：這題揭示了「索引和鎖機制之間的深層關聯」，是很多人容易忽略的一點——大家往往只從「查詢效能」的角度理解索引的重要性，卻沒意識到索引也直接決定了「鎖定的精確度」。原理是——InnoDB 的行鎖實作是在遍歷 B+ 樹索引、定位到具體記錄的過程中，對這些「被存取到的索引記錄」加鎖。如果查詢用上了合適的索引（如 `WHERE id = 5` 用了主鍵索引），資料庫能精確地只走到 id=5 這一條索引記錄、只鎖住這一行，其他行完全不受影響，並發度很高。但如果查詢條件沒有索引可用（如 `WHERE name = 'Tom'` 但 name 沒建索引），InnoDB 只能做全表掃描——它會「逐行掃描整張表」來判斷每一行是不是 `name = 'Tom'`，而在這個掃描過程中，為了保證資料一致性（防止掃描到一半，其他交易插入或修改了資料導致結果不一致），InnoDB 實際上會給「掃描過程中經過的每一行」都加上鎖，即使最終只有一行真正符合 `name='Tom'` 這個條件，但掃描路徑上的所有行都被鎖住了——這在效果上幾乎等同於鎖住了整張表，導致其他想操作這張表任何一行的交易都要排隊等待，並發效能急劇下降。這是一個非常實務的教訓——UPDATE 或 DELETE 語句如果 WHERE 條件沒有索引支援，不只是查詢慢的問題，還會嚴重拖累整個系統的並發能力（引發大量的鎖等待、甚至看起來像死鎖或系統卡死）。理解「行鎖依賴索引來實現精確鎖定、沒索引會退化成全表鎖定範圍」，展現你把索引和鎖這兩個知識點串聯起來理解，這是資料庫效能問題排查中一個常見但容易被忽視的關鍵點。

**面試回答方式**：講出「InnoDB 行鎖鎖在索引記錄上、如果查詢沒用上索引(全表掃描)、無法精確只鎖符合條件的行、只能鎖住掃描過程中檢查到的每一行、效果上退化成類似鎖全表」。強調「這是索引的另一個重要意義——不只加速查詢、還決定鎖定的精確度和並發能力、UPDATE/DELETE 沒索引不只是慢、還會嚴重拖累系統並發」。展現你把索引和鎖串聯理解，這是實務排查鎖等待/效能問題的關鍵知識點。

### 什麼是死鎖？資料庫層級的死鎖和應用程式層級（如 Java 的鎖）的死鎖有什麼相似和不同？

**核心答案**：資料庫層級的死鎖，和應用程式層級的死鎖，本質原理是完全相同的——都是「兩個或多個交易/執行緒，各自持有一部分資源（鎖）、又互相等待對方持有的資源，形成循環等待，永遠無法繼續」（見 Java 併發的死鎖題）。相似點——都需要滿足「互斥、持有並等待、不可搶佔、循環等待」這四個條件，預防思路也相通（統一加鎖順序、用逾時機制）。不同點主要在「偵測和處理機制」——資料庫（如 MySQL InnoDB）通常有「內建的自動死鎖偵測機制」，會主動偵測循環等待，發現死鎖後「自動選擇一個代價較小的交易作為犧牲者，回滾它並釋放鎖」，讓另一個交易能繼續，這個過程是資料庫自動完成的，應用程式只需要「捕捉到死鎖被回滾的錯誤、決定要不要重試」；而應用程式層級的死鎖（如 Java 的 synchronized 死鎖），JVM 本身通常沒有自動偵測和打破死鎖的機制，只能靠人工排查（jstack 分析）和修復程式碼。

**詳細解析**：這題把資料庫死鎖和 Java 併發的死鎖（已在 Java 併發類別詳細講過）做對比，既複習了共通的原理，又點出資料庫層級的一個重要優勢——「自動偵測和自我修復」。資料庫死鎖的典型場景——交易 A 先鎖住了行 1（想要行 2）、交易 B 先鎖住了行 2（想要行 1），兩者互相等待，這正是經典的死鎖四條件（互斥、持有並等待、不可搶佔、循環等待）在資料庫場景的體現，和 Java 中兩個執行緒交叉鎖定兩個物件的情況邏輯完全一樣。但資料庫（尤其 InnoDB）通常內建了「等待圖（wait-for graph）」的死鎖偵測演算法——它會定期或即時分析「誰在等誰的鎖」，一旦發現形成了循環，就判定為死鎖，並主動介入——選擇其中一個交易（通常是「持有鎖較少、或代價較小」的那個）作為犧牲者，強制回滾它、釋放它持有的鎖，讓另一個交易能夠繼續執行下去。這個過程完全是資料庫自動完成的，應用程式收到的是一個「因死鎖被回滾」的錯誤（如 MySQL 的 `Deadlock found when trying to get lock`），應用程式需要做的只是「捕捉這個特定的錯誤、決定是否要重新發起這個交易（通常重試是合理的，因為回滾後鎖的狀態已經改變，重試很可能成功）」。相較之下，Java 這種通用程式語言層級的死鎖（見 [[../java-concurrency/017-deadlock-conditions-and-troubleshooting.md]]），JVM 沒有這種自動偵測和打破死鎖的機制（因為在通用程式邏輯層面，「隨便回滾哪個執行緒的操作」可能是不安全的、不像資料庫交易那樣有明確的「回滾」語意），所以只能依賴人工用 jstack 排查、修改程式碼裡的加鎖順序來從根本上避免。理解這個「資料庫有自動死鎖偵測回滾、通用程式語言沒有」的差異，展現你能把不同層級的死鎖問題放在一起比較，理解各自的處理方式和背後的原因（資料庫交易天生就有「回滾」這個安全的補救手段，而通用程式碼沒有）。

**面試回答方式**：講出「原理相同——都是循環等待、四個死鎖條件」，差異在「處理機制——資料庫(InnoDB)有內建的自動死鎖偵測(等待圖分析)、發現後自動選一個交易犧牲回滾、應用程式只需捕捉錯誤決定是否重試；Java 等通用程式語言沒有這種自動機制、只能人工用 jstack 排查改程式碼」。點出「根本原因是資料庫交易天生有安全的回滾語意、可以自動打破死鎖，通用程式碼沒有這個安全的補救手段」。展現你能對比不同層級死鎖問題的處理方式，並理解背後的原因。

### 樂觀鎖和悲觀鎖在資料庫層面是怎麼實現的？

**核心答案**：**悲觀鎖**——假設一定會有並發衝突，所以在讀取資料時就「先加鎖」（如 `SELECT ... FOR UPDATE`，用資料庫的排他鎖），阻止其他交易同時修改，直到當前交易提交或回滾才釋放鎖，其他交易的相同操作要排隊等待。**樂觀鎖**——假設衝突較少，不預先加鎖，而是「先讀取資料（連同一個版本標記，如版本號 version 或最後修改時間 update_time）、修改時用 UPDATE 語句附加『版本號沒變』的條件（`UPDATE ... SET version=version+1 WHERE id=? AND version=?`），如果更新時發現版本號已經被別人改了（UPDATE 影響的行數是 0），説明有並發衝突，本次更新失敗，應用層決定是重試還是報錯」。悲觀鎖適合「衝突頻繁」的場景（提前鎖定避免浪費）、樂觀鎖適合「衝突較少」的場景（避免鎖的開銷，衝突了再處理）。

**詳細解析**：這題把「樂觀鎖 vs 悲觀鎖」這個在 Redis 分散式鎖題目中也出現過的概念（WATCH 樂觀鎖），對應到關聯式資料庫的具體實現方式，展現跨知識點的融會貫通。悲觀鎖的實現直接依賴資料庫本身的鎖機制——`SELECT ... FOR UPDATE` 會對查詢到的行加上排他鎖（X 鎖），這行資料在這個交易提交或回滾之前，其他任何想要修改（或用 FOR UPDATE 讀取）這行資料的交易都會被阻塞、排隊等待，這保證了「從讀取到修改」這整個過程是獨佔的、不會有其他交易插手，但代價是「並發度降低（大家要排隊）」。樂觀鎖的實現則完全不依賴資料庫的鎖，而是「用一個額外的版本欄位（version）+ 應用層的邏輯」實現——核心技巧是把「你以為的版本」作為 UPDATE 語句的 WHERE 條件的一部分：`UPDATE product SET stock = stock - 1, version = version + 1 WHERE id = 100 AND version = 5`（假設你之前讀到的版本是 5），如果在你讀取之後、執行這個 UPDATE 之前，沒有其他交易修改過這行資料（版本仍是 5），這個 UPDATE 會成功執行（影響 1 行），並把版本推進到 6；但如果中間有其他交易搶先修改了這行資料（版本已經變成 6），你的這個 UPDATE 因為 WHERE 條件裡的 `version = 5` 不再匹配任何行，會「影響 0 行」——應用層檢查到「影響行數是 0」，就知道發生了並發衝突，可以選擇「重新讀取最新資料再重試」或「直接告知使用者操作失敗」。理解這兩種鎖的具體 SQL 實現方式（悲觀鎖用資料庫原生的 FOR UPDATE、樂觀鎖用「版本號 + 條件 UPDATE + 檢查影響行數」的應用層技巧），展現你不只知道概念、還能寫出具體的實現。

**面試回答方式**：講出「悲觀鎖——用 SELECT ... FOR UPDATE 加資料庫的排他鎖、其他交易排隊等待、適合衝突頻繁；樂觀鎖——用版本號欄位、UPDATE 時帶上 WHERE version=讀到的值、影響行數為 0 就代表有並發衝突需要重試、不依賴資料庫鎖、適合衝突較少」。給出具體的樂觀鎖 SQL 示例(UPDATE ... SET version=version+1 WHERE id=? AND version=?)。能連結到「這和 Redis 的 WATCH 樂觀鎖是同一種思路(先做、提交時檢查衝突)」，展現你能跨知識點理解樂觀鎖的通用思想在不同系統中的具體落地方式。
