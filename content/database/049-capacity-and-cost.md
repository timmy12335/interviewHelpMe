# 題目

怎麼為資料庫做容量規劃？資料一直長大該怎麼辦？

## 核心答案

規劃要估四個維度。**資料量**——每張表的列數乘以平均列寬（記得加上索引，索引的總大小常常超過資料本身）與成長速率。**IOPS**——寫入的頻率乘以每次寫入涉及的頁數（一次插入要更新聚簇索引加上每個二級索引）。**記憶體**——理想是「熱資料集能放進 Buffer Pool」。**連線與 CPU**——並行的查詢數與每個查詢的成本。

「資料一直長大」的處理有四個層次，按成本遞增。**刪除**——真正不需要的資料（過期的 session、暫存記錄、超過保留期的日誌），**用分區讓刪除變成 `DROP PARTITION`**。歸檔——把冷資料移到便宜的儲存（另一個資料庫、物件儲存、或資料倉儲），主庫只留熱資料。壓縮——InnoDB 的頁面壓縮或表壓縮，**用 CPU 換空間**。**擴展**——垂直或水平。

最有效的往往是前兩層，而它們最常被跳過——因為「刪除資料」需要業務決定保留期，而那個對話沒有人主動發起。

## 詳細解析

「索引的總大小常常超過資料本身」是容量估算中最常被低估的一項。一張有五六個索引的表，索引的總和可能是資料的一到兩倍——尤其是在主鍵較大（UUID）或索引欄位較寬時。估算時應該分別列出每個索引的大小（用 `information_schema.TABLES` 的 `INDEX_LENGTH` 對比 `DATA_LENGTH`），**而不是只估資料**。這也是「不必要的索引有持續成本」的具體體現——一個從未被使用的索引不只拖慢寫入，還佔用了本來可以快取資料的記憶體。

「找出從未使用的索引」是一個高投資報酬率的清理。`performance_schema.table_io_waits_summary_by_index_usage` 記錄了每個索引被使用的次數——`count_star = 0` 且已經運行足夠久的索引就是候選。要注意的是「足夠久」必須涵蓋所有的業務週期（月結、年度報表可能一年才用一次某個索引），所以刪除前應該確認並保留恢復的能力（記下索引的定義，必要時能快速重建）。

資料生命週期應該在設計時就決定，而不是等到容量吃緊。每張表都應該能回答：這些資料要保留多久？超過之後是刪除還是歸檔？誰有權決定？ **沒有答案的表會永遠成長**，直到某天成為問題。把「保留期」寫進 schema 的文件（甚至用表的註解記錄），讓它成為設計的一部分而非事後的補救。

成本的維度在雲端環境變得直接可見。儲存、IOPS、記憶體、以及備份都是按量計費的——一個從未被清理的日誌表可能每月花掉可觀的費用，而沒有人注意到。把「每張表的儲存成本」做成一個可見的指標（大小乘以單價），能讓「該不該保留這些資料」從一個抽象的討論變成一個有數字的決定。很多資料被無限期保留，只是因為刪除它的價值從來沒有被量化過。

## 面試回答方式

先給**四個估算維度**並特別強調索引的總大小常常超過資料本身，估算時應該分別列出每個索引。給「資料長大」的**四個處理層次**（刪除、歸檔、壓縮、擴展）並指出最有效的往往是前兩層而它們最常被跳過——因為刪除需要業務決定保留期，**而那個對話沒有人主動發起**。加分點有三個：**用 `performance_schema` 找出從未使用的索引**是高報酬的清理，但「足夠久」必須涵蓋所有業務週期（年度報表可能一年才用一次）；資料生命週期應該在設計時決定——每張表都要能回答「保留多久、超過之後怎麼辦、誰有權決定」，沒有答案的表會永遠成長；以及把「每張表的儲存成本」做成可見指標，讓「該不該保留」從抽象討論變成有數字的決定——很多資料被無限期保留，只是因為刪除它的價值從來沒被量化過。

## 常見追問

### 歸檔的資料要放在哪裡？

**核心答案**：依「還會不會被查詢」決定。**偶爾會查**——放在另一個較便宜的資料庫實例（規格較低、可以用機械硬碟），應用在查不到時回退到那裡。**幾乎不查但要能查**——放在資料倉儲（ClickHouse、BigQuery）或物件儲存加上查詢引擎（Parquet 加 Athena／Trino），**成本低一到兩個數量級**。**只為了合規保留**——直接壓縮後放物件儲存的冷儲存層，需要時再解壓。

**詳細解析**：歸檔的難點不在「搬過去」而在「應用要怎麼查」。如果應用需要無縫地查詢冷熱資料，就需要一個能跨兩邊查詢的抽象層——那是一個真實的工程成本。務實的做法是「讓冷資料的查詢是一個明確不同的功能」：正常的查詢只查熱資料（快、簡單），需要歷史資料時走一個明確的「歷史查詢」功能（慢、有明確的等待提示）。這把「無縫」的需求換成了「明確分離」，而後者的實作成本低得多、行為也更可預測。 很多歸檔專案卡住，是因為堅持要無縫——而使用者其實能接受「查三年前的資料需要等一下」。

**面試回答方式**：給三種去處與對應的判準（偶爾查、幾乎不查但要能查、只為合規）。真正的加分點是指出難點不在搬過去而在應用要怎麼查——無縫查詢需要跨兩邊的抽象層，那是真實的工程成本。給出務實做法：讓冷資料的查詢是一個明確不同的功能，把「無縫」換成「明確分離」。收在觀察：很多歸檔專案卡住是因為堅持要無縫，而使用者其實能接受「查三年前的資料需要等一下」。

### 壓縮值得用嗎？

**核心答案**：**看瓶頸在哪**。如果瓶頸是**儲存空間或 IO 頻寬**，壓縮通常划算——壓縮後的頁面更小，一次 IO 能讀進更多邏輯資料，而且 Buffer Pool 能快取更多。如果瓶頸是 **CPU**，壓縮會讓情況更糟（每次讀寫都要解壓縮）。InnoDB 的頁面壓縮（透明頁面壓縮）依賴檔案系統的稀疏檔案支援，而表壓縮（`ROW_FORMAT=COMPRESSED`）則有較高的 CPU 與緩衝池管理成本。

**詳細解析**：**壓縮率高度依賴資料的性質**——文字與 JSON 通常能壓到三分之一以下，而已經壓縮過的資料（圖片、影片、加密後的內容）幾乎壓不動。所以評估前應該先取樣測試實際的壓縮率，而不是假設一個通用的比例。另一個常被忽略的是「壓縮後的表在緩衝池中同時存在壓縮與未壓縮兩份」（InnoDB 的表壓縮實作），這讓記憶體的使用變得更複雜——理論上省了磁碟但可能沒省記憶體。這是一個「優化在一個維度上有效但在另一個維度上有代價」的典型例子，而評估時必須把所有維度都看過，不能只看它宣稱要解決的那一個。

**面試回答方式**：給判準（瓶頸在儲存或 IO 就划算、在 CPU 就更糟）與兩種壓縮方式的差別。加分點是指出**壓縮率高度依賴資料性質**，已壓縮過的內容幾乎壓不動，所以要先取樣測試實際壓縮率。真正的深度是表壓縮在緩衝池中同時存在壓縮與未壓縮兩份——理論上省了磁碟但可能沒省記憶體。收在通用教訓：優化在一個維度有效但在另一個維度有代價，評估時必須把所有維度看過。

### 怎麼預測未來的容量需求？

**核心答案**：用歷史趨勢外推，但要區分「線性成長」與「成長率變化」。取過去 6 到 12 個月的每日資料量，畫出趨勢並看它是線性、指數、還是有階躍（新功能上線、行銷活動）。**線性成長最好預測**；指數成長則意味著現在的架構會在某個明確的時間點失效，而那個時間點應該被算出來並成為規劃的依據。

**詳細解析**：比預測更重要的是「設定觸發閾值並自動告警」。預測總是會錯（業務變化、新功能、非預期的使用模式），而一個「容量使用率超過 70% 就告警」的規則不需要預測準確，它只需要在問題發生前給出足夠的反應時間。關鍵是「足夠的反應時間」要涵蓋整個應對流程——不只是「加磁碟」的時間，還包括評估、決策、採購或申請、測試、以及執行的時間。如果擴容需要兩週，那閾值就必須設在「兩週後才會滿」的位置。這個「從應對所需的時間反推告警閾值」的思路，比憑感覺設一個百分比有依據得多，而它同樣適用於所有的資源告警。

**面試回答方式**：給方法（歷史趨勢外推、區分線性與指數與階躍）並指出指數成長意味著現在的架構會在某個明確時間點失效，而那個時間點應該被算出來。真正的重點是比預測更重要的是設定觸發閾值並自動告警——它不需要預測準確，只需要在問題前給出足夠反應時間。收在關鍵：「足夠的反應時間」要涵蓋整個應對流程（評估、決策、採購、測試、執行），如果擴容要兩週，閾值就必須設在「兩週後才會滿」的位置——這個從應對時間反推閾值的思路適用於所有資源告警。
