# 題目

`LIMIT 1000000, 10` 這種深分頁（Deep Pagination）查詢為什麼會很慢？有哪些常見的優化方式？

## 核心答案

`LIMIT offset, count` 的深分頁慢，是因為 MySQL 的實作方式是「先掃描並丟棄前面 offset 筆資料、再取接下來的 count 筆」——也就是說 `LIMIT 1000000, 10` 實際上要先讀取（並丟棄）前面 100 萬筆資料，才能拿到第 100 萬零 1 到 100 萬零 10 筆，offset 越大，需要掃描和丟棄的資料量就越大，效能隨 offset 線性惡化。常見優化方式包括：**（1）子查詢延遲關聯**——先用覆蓋索引（Covering Index）快速定位出符合條件的主鍵 ID（只掃索引不用回表（Bookmark Lookup），速度快），再用這些 ID 去關聯查詢完整資料，減少大量資料的隨機 I/O；**（2）記錄上次查詢的最後一筆資料的排序欄位值（游標/Seek 分頁）**，下次查詢用 `WHERE id > 上次最後的id ORDER BY id LIMIT 10` 代替 offset，避免掃描已經翻過的資料；**（3）如果業務允許，限制使用者只能翻到有限的頁數**（多數場景使用者也不會真的翻到第 10 萬頁）。

## 詳細解析

**問題根源**：MySQL 執行 `SELECT * FROM articles ORDER BY id LIMIT 1000000, 10` 時，即使有索引，執行流程是——按照 id 索引的順序，依序讀取資料（如果 SELECT * 需要非索引欄位，每讀一筆就要回表一次），讀到第 1 筆到第 1000000 筆都直接丟棄（因為 offset 是 1000000），只有第 1000001 到 1000010 筆才是真正要回傳的結果。也就是說，資料庫做了「100 萬次無謂的讀取（可能還帶著 100 萬次回表的隨機 I/O）」，只為了最終拿到 10 筆資料，offset 越大，這種浪費就越嚴重，這是深分頁慢的根本原因，而不是「MySQL 不會用索引」。

**優化方式一：子查詢延遲關聯（Deferred Join）**：核心想法是「先只用索引欄位（不觸發回表）快速定位出目標的主鍵 ID 範圍，再拿這些少量的 ID 去做一次關聯查詢，取得完整資料」。例如：
```sql
SELECT a.* FROM articles a
JOIN (SELECT id FROM articles ORDER BY id LIMIT 1000000, 10) b
ON a.id = b.id;
```
子查詢 `SELECT id FROM articles ORDER BY id LIMIT 1000000, 10` 因為只查 id（如果 id 是主鍵或有索引），可以直接走覆蓋索引，完全不用回表，掃描 100 萬筆的成本大幅降低（純索引掃描比帶回表的掃描快很多）；子查詢先篩出 10 個 id 後，外層再用這 10 個 id 去關聯查詢完整資料，只需要 10 次回表，而不是 100 萬次。這個方法能顯著減少 I/O，但仍然要「掃描」100 萬筆索引記錄（只是不回表），offset 極端大時效果仍會遞減。

**優化方式二：游標分頁（Seek Method / Keyset Pagination）**：不再用「第幾頁」的 offset 概念，而是「記住上一頁最後一筆資料的排序欄位值」，下一頁查詢直接用 `WHERE id > 上次最後的id ORDER BY id LIMIT 10`。因為有索引，`WHERE id > X` 可以直接透過 B+ 樹索引「跳到」大於 X 的位置開始讀，完全不需要像 offset 那樣「先掃過再丟棄」，效能和頁碼大小無關（不管翻到第幾頁，查詢成本都差不多）。缺點是「不能直接跳到任意頁碼」（比如沒辦法直接跳到第 500 頁），只能「上一頁 / 下一頁」這種連續翻頁，適合資訊流、無限捲動這類場景，不適合需要「跳頁」的傳統分頁 UI。

**優化方式三：業務層面限制**：多數真實場景中，使用者很少會真的翻到很深的頁數（大部分流量集中在前幾頁），可以直接在產品設計上限制「最多只能翻到第 N 頁」（超過提示使用者改用篩選/搜尋縮小範圍），從根本上避免深分頁的效能問題，是最簡單直接、性價比很高的方案。

## 面試回答方式

先講深分頁慢的根本原因（LIMIT offset, count 的實作是「掃描並丟棄前面所有資料」，offset 越大浪費的讀取和回表越多）。接著給出至少兩種優化方案——子查詢延遲關聯（讓分頁的掃描階段走覆蓋索引避免回表）和游標分頁（用上一頁最後的排序值取代 offset，讓查詢成本和頁碼無關）。如果能補充「業務層限制翻頁深度」這種產品設計層面的解法，展現你不只會寫 SQL 技巧，還有從整體系統設計角度解決問題的思維。

## 常見追問

### 游標分頁（Seek Method）除了不能跳頁，還有什麼限制或需要注意的地方？

**核心答案**：游標分頁還有幾個限制——**（1）排序欄位必須唯一（或加上主鍵作為次要排序鍵）**，否則排序欄位有重複值時，可能導致翻頁時漏掉或重複某些資料；**（2）如果排序欄位在翻頁過程中被修改或刪除**（比如按 `updated_at` 排序、但某筆資料在使用者翻頁的過程中被更新了 `updated_at`），可能導致這筆資料的位置「跳動」，出現漏看或重複看到的情況；**（3）游標值需要由前端或呼叫方在每次請求時攜帶上一頁最後一筆的排序值**，這比單純傳一個頁碼參數要複雜一些，前後端的 API 設計需要相應調整。

**詳細解析**：這題深入游標分頁的邊界情況和實務注意事項。第一點「排序欄位需要唯一」——如果只用一個可能重複的欄位排序（比如 `created_at`，多筆資料可能有相同的建立時間戳），`WHERE created_at > 上次的值` 這個條件，當有多筆資料的 `created_at` 剛好等於「上次最後一筆」的值時，可能會漏掉這些「並列」的資料（因為條件是嚴格大於，不包含等於的情況），正確做法是用「排序欄位 + 唯一鍵（如主鍵 id）」的組合作為游標（例如 `WHERE (created_at, id) > (上次的created_at, 上次的id)`），保證排序的唯一性和翻頁的正確性。第二點「資料在翻頁過程中變化」——這是游標分頁相比 offset 分頁的一個特性差異：offset 分頁是「基於位置」的（不管資料怎麼變，永遠是第幾行到第幾行），游標分頁是「基於值」的（永遠找『比上次游標值更大』的資料），如果排序欄位的值在使用者翻頁過程中被修改，可能導致這筆資料的相對順序改變，出現「這一頁少看了一筆」或「下一頁又看到一次」的情況——這其實在多數場景下是可以接受的（甚至某些情況下更符合預期，比如資訊流場景，新的變動理應被看到），但需要在設計時意識到這個行為差異。第三點是純粹的實作複雜度考量——API 需要傳遞「游標」（通常編碼成一個 opaque token）而非簡單的頁碼整數，前端需要相應地儲存和傳遞這個游標值。

**面試回答方式**：列舉三個限制——排序欄位需要唯一（否則要加上主鍵做複合排序鍵，避免漏資料）、資料在翻頁過程中變化可能導致順序跳動（游標分頁是「基於值」而非「基於位置」，這是和 offset 分頁的本質差異）、以及 API 設計需要傳遞游標值而非簡單頁碼（複雜度增加）。展現你不只知道游標分頁的優點，還理解它在邊界情況下的實務限制。

### 子查詢延遲關聯的優化方式，在 offset 特別特別大（比如 offset = 1000 萬）時，還有效嗎？

**核心答案**：效果會大幅遞減——雖然子查詢延遲關聯避免了「回表」的隨機 I/O，但子查詢本身仍然需要「掃描」這 1000 萬筆索引記錄（只是不用回表，純粹讀索引葉節點），offset 越大，這個純索引掃描的成本仍然線性增長，只是比「帶回表的掃描」快很多倍（因為避免了隨機 I/O），但終究不是「常數時間」的操作。在 offset 極端大的情況下（比如千萬級別），游標分頁（Seek Method）是更根本的解法，因為它透過索引直接「跳到」目標位置附近開始讀，成本和 offset 大小基本無關（只和 `LIMIT` 的筆數有關）。

**詳細解析**：這題釐清「子查詢延遲關聯」和「游標分頁」這兩種優化方式在效果上的本質差異，避免面試者誤以為子查詢延遲關聯是萬能解法。子查詢延遲關聯的優化收益，主要來自「把大量的隨機 I/O（回表）換成少量的隨機 I/O（只針對最終需要的少數幾筆資料回表）」，但「掃描 offset 筆索引記錄」這個動作本身還是存在的——只是掃描索引（尤其是覆蓋索引、資料是連續存放在 B+ 樹葉節點上）遠比「每掃一筆就額外做一次回表隨機讀取」要快得多，所以在 offset 是幾萬到幾十萬這個量級時，子查詢延遲關聯通常已經能帶來數量級的效能提升，是一個「用起來簡單、SQL 改動小、收益顯著」的實用優化。但當 offset 繼續增長到百萬甚至千萬級別，即使是純索引掃描，掃過這麼多筆記錄本身也需要時間（線性增長），這時候子查詢延遲關聯的效果就會「摸到天花板」。游標分頁之所以能做到「和 offset 大小基本無關」，是因為它完全不做「掃描並丟棄」這件事——透過 `WHERE id > X` 這個條件，B+ 樹索引可以直接用類似二元搜尋的方式，直接定位到「大於 X」的第一筆資料開始讀取，不管 X 對應的是第 10 筆還是第 1000 萬筆，這個「定位」操作的成本都差不多（B+ 樹的搜尋是對數時間複雜度）。所以正確的認知是——子查詢延遲關聯是「治標」（大幅減少每筆的處理成本，但沒有解決『要處理 offset 筆』這個根本問題），游標分頁是「治本」（從根本上避免了『需要處理 offset 筆』這件事）。

**面試回答方式**：先講清楚子查詢延遲關聯的優化本質——「把回表的隨機 I/O 換成純索引掃描，減少每筆的處理成本，但仍要線性掃描 offset 筆索引記錄」，所以在 offset 極端大時效果會遞減。對比游標分頁的本質——「用 B+ 樹的索引定位（近似二元搜尋）直接跳到目標位置附近，完全不掃描已翻過的資料，成本和 offset 大小基本無關」。用「治標 vs 治本」的說法總結兩者差異，展現你理解不同優化手段解決問題的層次深淺。

### 如果業務需求就是要支援「跳到任意頁碼」（如第 500 頁），同時又要顧慮深分頁的效能問題，有沒有折衷的做法？

**核心答案**：常見的折衷做法是**限制實際能跳頁的深度、超過就強制改用其他瀏覽方式**——例如產品設計上只允許「跳頁」跳到前面固定的頁數範圍內（如前 100 頁，這部分 offset 不算太大，用子查詢延遲關聯就能有不錯的效能），超過這個範圍，UI 上就不再提供「輸入頁碼跳轉」的功能，改為引導使用者使用「篩選條件縮小範圍」或「切換成連續捲動、不能跳頁的資訊流模式」。另一種做法是**預先建立頁碼到游標值的對照表（索引表）**——系統背景定期（或在資料寫入時）計算並記錄「第 N 頁對應的游標起始值是什麼」，使用者要跳到第 500 頁時，直接查這張對照表拿到對應的游標值，再用游標分頁的方式高效地查詢該頁資料，兼顧了「跳頁」的產品需求和游標分頁的效能優勢，代價是需要額外維護這張對照表（資料變動時要考慮更新成本）。

**詳細解析**：這題探討當「跳頁」這個產品需求和「深分頁效能」這個技術限制產生衝突時，怎麼找到務實的折衷方案，而不是簡單地說「這兩個需求沒辦法同時滿足」。第一種方案「限制可跳頁的深度」承認了一個現實——多數使用者實際上很少會真的跳到很深的頁數，把「能跳到任意頁」這個需求限縮成「能跳到合理範圍內的頁數」，在產品體驗上的犧牲通常很小，卻能完全避開深分頁的效能問題，是成本效益最高的折衷（也呼應了核心答案裡提到的「業務層面限制」這個思路，只是在這裡進一步結合了「部分支援跳頁」的細節）。第二種方案「預建頁碼到游標值的對照表」則是一個更精巧的工程解法——它的核心想法是「跳頁的效能瓶頸在於『不知道第 500 頁的起點在哪裡、只能用 offset 硬算』，但如果我們『提前算好』每一頁的起點游標值，存起來備用，之後真正要跳頁時，就不需要再現場硬算了」，這有點類似「用空間換時間」的預先計算（precomputation）策略，適合資料相對穩定（不會頻繁插入刪除、導致頁碼對照關係經常變動）的場景，例如季度報表、歷史資料查詢等場景；如果資料是高頻寫入的（如即時的貼文列表），這張對照表需要頻繁更新，維護成本可能會抵銷掉它帶來的效能收益，需要視實際情況權衡是否值得導入。

**面試回答方式**：給出兩個折衷方案——「限制實際可跳頁的深度，超過就引導使用者改用篩選或連續捲動」（成本最低、多數場景夠用）和「預先計算並維護頁碼到游標值的對照表，跳頁時查表取得起點再用游標分頁」（更精巧但需要額外維護成本，適合資料相對穩定的場景）。點出「這是產品需求和技術限制之間的權衡取捨，沒有完美無代價的方案，要根據實際資料變動頻率選擇」，展現你能在業務需求和技術限制衝突時提出務實方案，而不是簡單回答「魚與熊掌不可兼得」。
