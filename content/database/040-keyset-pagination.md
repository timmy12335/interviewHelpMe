# 題目

`LIMIT 100000, 20` 為什麼慢？游標分頁怎麼解決它，又有什麼限制？

## 核心答案

`LIMIT offset, n` 慢的原因是**資料庫必須先產生並丟棄前 offset 筆**——它沒有辦法「直接跳到第十萬筆」，因為那需要知道前面有多少筆符合條件，而那本身就是掃描。**所以成本與 offset 成正比**，第一頁瞬間、第五千頁要幾秒。

**游標分頁（keyset pagination）** 的做法是**用「上一頁最後一筆的排序鍵」當起點**：`WHERE (created_at, id) < (?, ?) ORDER BY created_at DESC, id DESC LIMIT 20`。**因為條件可以走索引定位，直接跳到起點，成本與頁碼完全無關**——第一頁與第一萬頁一樣快。

**限制有三個**。**不能跳頁**——只能「下一頁」與「上一頁」，無法直接跳到第 500 頁（**但那個功能的實際使用率極低，值得質疑它是不是真的需要**）。**排序鍵必須唯一**——否則相同值的邊界會出現重複或遺漏，**所以通常要加上主鍵當最後的排序鍵**。**排序條件不能任意變**——每種排序方式都需要對應的索引。

## 詳細解析

**「排序鍵必須唯一」這個要求容易被忽略而造成資料遺漏**。只用 `created_at` 當游標時，如果有多筆記錄的時間完全相同，**跨頁的邊界就會出問題**：`WHERE created_at < ?` 會跳過與邊界值相同的其他記錄，`<=` 則會重複。**加上主鍵形成複合條件 `(created_at, id) < (?, ?)` 才是正確的**——它定義了一個全序，不會有並列。**要注意 MySQL 支援這種列值比較（row value comparison）並且能正確使用複合索引**，而有些人會展開成 `created_at < ? OR (created_at = ? AND id < ?)`——**那個寫法在某些版本上無法有效使用索引**，應該優先用列值比較的形式。

**分頁期間資料變動的行為也不同**。offset 分頁在「翻頁期間有新資料插入」時會**重複顯示某些記錄**（因為後面的記錄被往後推了）；游標分頁則**天然穩定**——它的起點是一個具體的值，新插入的資料不會影響已經翻過的頁。**這是游標分頁除了效能之外的一個實質優勢**，在即時性強的列表（訊息、動態、日誌）上尤其明顯。

**「總筆數」是游標分頁最常遇到的產品需求衝突**。傳統的分頁 UI 需要顯示「共 1234 頁」，**而那需要一次 `COUNT(*)`，在大表上同樣昂貴**。**處理方式有三種**：**改變 UI**（用「載入更多」或無限捲動，那本來就更適合行動裝置）、**用估算值**（`EXPLAIN` 的 `rows` 估算，或維護一個近似的計數）、或**只在第一頁算一次並快取**。**很多時候正確的答案是第一種**——「共 12345 筆」這個資訊對使用者的價值，通常遠低於工程上為它付出的成本。

**深分頁在分庫分表下更嚴重**。取第 100 頁需要**每個分片各取前 100 頁再全域排序**——成本是單庫的 N 倍且隨頁碼線性上升。**所以分庫分表的系統應該從設計階段就排除深分頁**，改用游標；**而這個約束應該在設計分片方案時就提出**，而不是等產品要求「跳到第 500 頁」時才發現做不到。

## 面試回答方式

先給慢的**根本原因**——**資料庫必須先產生並丟棄前 offset 筆**，沒辦法直接跳過去，所以成本與 offset 成正比。給游標分頁的做法與**成本與頁碼完全無關**這個關鍵性質。給三個限制並對「不能跳頁」加一句判斷：**那個功能的實際使用率極低，值得質疑是不是真的需要**。加分點有三個：**「排序鍵必須唯一」容易被忽略而造成資料遺漏**，要加主鍵形成複合條件，而且**該用列值比較的形式而非展開成 OR**（後者在某些版本無法有效使用索引）；**游標分頁在資料變動時天然穩定**，而 offset 分頁會重複顯示——這是效能之外的實質優勢；以及**「總筆數」是最常見的產品需求衝突**，而**很多時候正確答案是改變 UI**，因為「共 12345 筆」的價值通常遠低於為它付出的成本。

## 講稿

慢的原因是資料庫必須先產生並丟棄前面那些筆。它沒有辦法直接跳到第十萬筆，因為那需要知道前面有多少筆符合條件，而那本身就是掃描。所以成本跟偏移量成正比。

游標分頁的做法是用上一頁最後一筆的排序鍵當起點。因為條件可以走索引定位，直接跳到起點，成本跟頁碼完全無關，第一頁跟第一萬頁一樣快。

限制有三個。不能跳頁、排序鍵必須唯一、排序條件不能任意變。第一個限制值得多說一句，跳到第五百頁這個功能的實際使用率極低，值得質疑它是不是真的需要。

排序鍵必須唯一這一點容易被忽略而造成資料遺漏。只用時間當游標的話，多筆記錄時間完全相同時，跨頁的邊界會跳過或重複。要加上主鍵形成複合條件才正確。而且應該用列值比較的形式，不要展開成或的條件，那個寫法在某些版本上無法有效使用索引。

還有一個效能之外的優勢。翻頁期間有新資料插入時，偏移量分頁會重複顯示某些記錄，而游標分頁天然穩定，因為它的起點是一個具體的值。

最後，總筆數是最常遇到的產品需求衝突。很多時候正確的答案是改變介面，用載入更多取代頁碼。

## 常見追問

### 如果一定要支援跳頁怎麼辦？

**核心答案**：三種折衷。**限制最大頁數**——只允許跳到前 N 頁（例如前 100 頁），超過就要求使用者加上更精確的篩選條件。**這是最務實的做法**，因為「翻到第 500 頁」通常表示搜尋條件不夠精確，而不是真的要看那一頁。**預先計算頁碼邊界**——定期為熱門的排序方式建立「第 N 頁的起始鍵」對照表，跳頁時查表得到起點再用游標查詢。**用搜尋引擎**——Elasticsearch 這類系統對深分頁同樣有限制（`from + size` 有上限），但它的 `search_after` 就是游標分頁，而且能處理更複雜的排序。

**詳細解析**：**「限制最大頁數」需要與產品溝通，而溝通的方式很重要**。與其說「技術上做不到」，不如**提出資料**：「目前 99.9% 的使用者不會翻超過 10 頁，而支援深分頁需要 X 的成本並讓所有查詢變慢」——**把它變成一個成本與收益的討論，而不是技術限制的宣告**。**很多時候產品方並不堅持那個功能，只是沒有人問過**。**這個「用資料把技術限制轉成產品取捨」的做法，比單方面說做不到有效得多**，也讓工程與產品的討論建立在同一個基礎上。

**面試回答方式**：給三種折衷並指出**「限制最大頁數」最務實**——翻到第 500 頁通常表示搜尋條件不夠精確。真正的加分點是**溝通的方式**：與其說技術上做不到，不如提出資料（99.9% 的使用者不會翻超過 10 頁、支援它的成本是多少），**把它變成成本與收益的討論而非技術限制的宣告**。收在觀察：**很多時候產品方並不堅持那個功能，只是沒有人問過**。

### 游標的值該怎麼傳給前端？

**核心答案**：**編碼成一個不透明的字串**（例如把 `(created_at, id)` 序列化後 base64），**而不是直接暴露欄位值**。三個理由：**避免前端依賴內部結構**（之後改排序方式時不必改 API 契約）、**避免使用者手動構造游標**（可能繞過權限或造成非預期的查詢）、以及**方便加入版本或簽章**（未來可以在游標裡加更多資訊而不破壞相容）。

**詳細解析**：**這與 GraphQL 的 Relay 分頁規範是同一個設計**——它的 `cursor` 就是不透明字串，而 `pageInfo` 提供 `hasNextPage` 等中繼資料。**「不透明」本身就是一個有價值的 API 設計原則**：它讓伺服器保留改變內部表示的自由。**但要注意「不透明」不等於「安全」**——base64 不是加密，使用者可以解碼看到內容。**如果游標裡包含了不該暴露的資訊（例如內部 ID 或權限相關的欄位），需要真正的加密或簽章**。**這是一個常見的誤解：把編碼當成保護。** 同樣的錯誤出現在把 base64 當成密碼保護、或把 JWT 的 payload 當成機密（**JWT 是簽章不是加密，payload 是明文可讀的**）。

**面試回答方式**：給做法（編碼成不透明字串）與三個理由。加分點是連到 **GraphQL Relay 分頁規範的同一設計**，並指出**「不透明」本身是有價值的 API 設計原則**——讓伺服器保留改變內部表示的自由。真正的深度是澄清**「不透明」不等於「安全」**——base64 不是加密，需要保護就要真的簽章或加密；並指出這是常見誤解，**同樣的錯誤出現在把 JWT 的 payload 當成機密**。

### 排序欄位不在索引裡怎麼辦？

**核心答案**：**游標分頁的前提就是「排序鍵有索引」**——沒有索引的話，每次查詢都要全表掃描加排序，游標分頁的優勢完全消失。**所以支援哪些排序方式，等於決定要建哪些索引**。實務上的處理是：**只支援少數幾種排序**（每種對應一個索引），而不是讓使用者對任意欄位排序。

**詳細解析**：**「讓使用者對任意欄位排序」是一個常見但代價高昂的需求**——N 個可排序欄位意味著可能需要 N 個索引，**而每個索引都有寫入與空間成本**。**務實的處理是分級**：常用的兩三個排序方式建索引並支援游標分頁；罕見的排序方式**限制結果數量**（例如只允許在已經篩選到一千筆以內的結果上排序），那時候記憶體排序完全可以接受。**這個「常見路徑優化、罕見路徑限制」的分級思路，比「所有路徑都要一樣快」務實得多**——後者的成本往往集中在那些幾乎沒人用的路徑上。**判斷的依據應該是實際的使用統計**，而那需要在 API 層記錄「使用者實際用了哪些排序方式」——**很多團隊沒有這個資料，於是只能猜。**

**面試回答方式**：給明確的前提——**游標分頁需要排序鍵有索引**，否則優勢完全消失，所以**支援哪些排序等於決定建哪些索引**。真正的加分點是**分級的思路**：常用的兩三種建索引並支援游標分頁，罕見的則限制結果數量後在記憶體排序。收在原則：**「常見路徑優化、罕見路徑限制」比「所有路徑一樣快」務實**，並指出判斷依據應該是實際使用統計——**而很多團隊沒有這個資料，於是只能猜**。
