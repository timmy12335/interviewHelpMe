# 題目

MySQL 的 InnoDB 和 MyISAM 這兩種儲存引擎有什麼主要差異？為什麼現在幾乎都預設用 InnoDB？

## 核心答案

兩者最核心的差異在於：**（1）交易支援**——InnoDB 支援交易（ACID）、支援 COMMIT/ROLLBACK，MyISAM 完全不支援交易；**（2）鎖粒度**——InnoDB 支援行級鎖（並實作了 MVCC，讀寫互不阻塞），MyISAM 只支援表級鎖（任何寫入都會鎖住整張表，並行寫入效能差）；**（3）索引結構**——InnoDB 用聚簇索引（Clustered Index）（資料和主鍵索引存在一起，見 [[003-clustered-index.md]]），MyISAM 的索引和資料是分開儲存的（索引檔存的是「指向資料檔案的位址」，屬於非聚簇結構）；**（4）崩潰恢復能力**——InnoDB 有 redo log（WAL）保證崩潰後能恢復到一致狀態，MyISAM 沒有這種機制，異常關閉容易造成資料損毀甚至遺失；**（5）外鍵約束**——InnoDB 支援外鍵，MyISAM 不支援。正因為現代應用幾乎都需要交易保證和高並行寫入能力，MySQL 5.5 之後就把 InnoDB 設為預設儲存引擎，MyISAM 目前只在極少數「純唯讀、對交易完全沒有需求」的場景才會被考慮。

## 詳細解析

**交易支援的差異影響**：InnoDB 完整支援 ACID 交易，意味著一系列相關的資料庫操作可以被包裝成一個「原子單位」，要嘛全部成功、要嘛全部回滾，這對於任何「一次業務操作涉及多個資料變更」的場景（例如轉帳同時扣一個帳戶、加另一個帳戶）都是必要的保障。MyISAM 完全沒有交易的概念——每一條 SQL 語句執行完就直接生效，無法「回滾」，如果一個業務邏輯涉及多個 SQL、中間某一步失敗了，前面已經執行的操作沒有辦法自動撤銷，需要應用程式自己想辦法處理這種「部分失敗」的異常情況，複雜且容易出錯。

**鎖粒度的差異影響**：MyISAM 的表級鎖意味著「同一時間，一張表只能有一個寫入操作在進行，且寫入時所有讀取也會被阻塞（或反過來，視鎖類型而定）」，在高並行寫入的場景下，這會造成嚴重的效能瓶頸——大量的寫入請求必須排隊依序執行，無法真正並行。InnoDB 的行級鎖搭配 MVCC（見 [[009-mvcc.md]]），使得「讀取操作幾乎不會被寫入操作阻塞（讀已提交的快照版本）」、「不同行的寫入操作之間也可以並行執行（只要不是修改同一行資料）」，這對現代高並發應用（大量並行的讀寫請求）的效能表現有本質性的差異。

**崩潰恢復能力的差異**：InnoDB 透過 redo log（見 [[012-redo-log.md]]）實現「先寫日誌、後寫資料（WAL）」的機制，即使資料庫在寫入資料檔案的過程中異常當機，重啟後也能透過重放 redo log，把資料恢復到「應該達到的、一致的狀態」，不會出現資料損毀或遺失已提交交易的情況。MyISAM 沒有這類機制，如果在寫入過程中發生異常關閉（如斷電、程序被強制終止），資料檔案很可能處於「損毀」的狀態（索引和資料檔案不一致，甚至檔案本身結構被破壞），往往需要手動執行 `REPAIR TABLE` 之類的修復操作，且不保證能完全恢復，資料遺失風險遠高於 InnoDB。

**MyISAM 目前仍可能被考慮的場景**（雖然非常少見）：因為 MyISAM 的資料結構相對簡單（不需要維護 MVCC 版本鏈、不需要交易日誌），在「純粹唯讀、不需要交易、且對某些特定操作（如 `COUNT(*)` 無 WHERE 條件時，MyISAM 因為在表的元資料裡直接快取了總行數，可以 O(1) 回傳，而 InnoDB 因為 MVCC 的關係，不同交易看到的行數可能不同，無法簡單快取，必須實際掃描計算）有極致效能要求」的場景，MyISAM 理論上仍有一些優勢，但這些場景在現代架構下通常會用其他手段解決（如維護一個獨立的計數快取），實務上幾乎不會為了這點優勢選擇犧牲交易支援和資料安全性。

## 面試回答方式

用一個清晰的對比表格式的口頭陳述，涵蓋這幾個維度——交易支援（有 vs 無）、鎖粒度（行鎖+MVCC vs 表鎖）、索引結構（聚簇 vs 非聚簇）、崩潰恢復（redo log vs 無保護）、外鍵支援（有 vs 無）。最後總結「因為現代應用幾乎都需要交易和高並行寫入，所以 InnoDB 是預設且幾乎唯一的選擇，MyISAM 只在極少數純唯讀場景才被考慮」。這是一道基礎題，考察你對 MySQL 儲存引擎架構的基本認識是否紮實，回答時盡量具體(講出「行鎖+MVCC」而非只說「效能較好」)，展現你不是死記硬背的表面認知。

## 常見追問

### 為什麼 MyISAM 的 COUNT(*) 比 InnoDB 快？這對實務上統計總數有什麼啟示？

**核心答案**：MyISAM 在表的元資料裡直接維護並快取了「這張表目前的總行數」，因為 MyISAM 不支援交易和 MVCC，「總行數」這個概念在任何時刻對所有人來說都是唯一確定的，所以可以簡單地在每次 INSERT/DELETE 時增減這個計數器，`COUNT(*)`（無 WHERE 條件）時直接回傳這個快取值，時間複雜度是 O(1)。InnoDB 因為支援 MVCC，同一時刻不同的交易可能因為隔離級別和各自交易開始的時間點不同，「看到」的行數本來就可能不一樣（比如交易 A 開始時表有 100 行，交易 B 在這之後插入了一行，但交易 A 因為可重複讀隔離級別，看到的還是 100 行），所以 InnoDB 無法簡單維護一個「全域唯一」的行數快取，`COUNT(*)` 必須老實地掃描（雖然可以走覆蓋索引（Covering Index）優化，掃最小的索引而不是主表資料，但仍然是線性掃描）。實務上如果需要頻繁取得「大約」的總數統計（如商品總數、使用者總數展示），比較好的做法是「額外維護一個獨立的計數表或快取（如 Redis 計數器），在資料變化時同步更新這個計數，避免每次都對大表做 COUNT(*) 全表掃描」。

**詳細解析**：這題延伸解釋兩種引擎在 `COUNT(*)` 效能上差異的根本原因，並給出實務的替代方案。核心的差異點在於「MVCC 帶來的多版本可見性」——InnoDB 為了支援交易隔離（尤其是可重複讀這種預設隔離級別），必須讓「同一張表，不同交易在同一時刻查詢，可能看到不同的行數（取決於各自的可見性判斷、即各自的 ReadView）」成為可能，這意味著「總行數」根本不是一個可以簡單快取的、全域唯一的值，InnoDB 只能透過「實際掃描每一行，並根據當前交易的可見性規則判斷這一行是否應該被計入」來得出準確的 `COUNT(*)` 結果，這個掃描過程雖然可以優化（比如選擇資料量最小的索引來掃描，而不是掃描資料量更大的主表資料，這樣至少能減少讀取的資料量），但終究是線性時間複雜度，隨表的資料量增長而變慢。反觀 MyISAM 因為完全沒有交易和 MVCC 這個包袱，任何時刻「這張表有幾行」就是一個簡單、確定、唯一的數字，直接在插入/刪除時同步增減這個計數器即可，讀取時直接回傳，是 O(1) 操作。這個差異對實務工作的具體啟示是——如果一個系統對「總數展示」的即時性和精確性要求不高（比如網站底部顯示的「目前已有 XX 位使用者加入」這種展示性質的數字，稍微有點延遲或誤差通常無傷大雅），與其每次都對 InnoDB 的大表做效能較差的 `COUNT(*)` 掃描，更好的做法是維護一個獨立的計數器（可以是資料庫裡的一張小表、也可以是 Redis 裡的一個計數鍵），在每次新增/刪除資料時，同步（或非同步）地更新這個計數器，把「取得總數」這個操作的複雜度也降到 O(1)，用一點點資料同步的複雜度，換取查詢效能的巨大提升。

**面試回答方式**：先解釋根本原因——「MyISAM 沒有 MVCC，總行數是唯一確定值，可以簡單快取；InnoDB 支援 MVCC，不同交易可能看到不同行數，無法簡單快取，必須實際掃描（可以走覆蓋索引優化但仍是線性掃描）」。給出實務啟示——「對即時性要求不高的總數展示場景，維護獨立的計數器（資料庫小表或 Redis 計數鍵）取代直接 COUNT(*) 大表」。展現你不只知道這個效能差異的表象，還理解背後的原理並能給出可落地的替代方案。

### 如果一個已經上線的系統，發現某些舊的表還在用 MyISAM 引擎，要怎麼安全地把它轉換成 InnoDB？

**核心答案**：可以直接用 `ALTER TABLE table_name ENGINE=InnoDB;` 這個 SQL 語句進行轉換，MySQL 會在背景重建整張表（把資料按照 InnoDB 的儲存格式重新組織，包括建立聚簇索引），這個操作本質上是「複製一份新格式的表、資料填充完成後替換舊表」，對於大表而言可能耗時較長、且在早期版本的 MySQL 中會鎖表（阻塞其他讀寫操作）。實務上對於「大表」或「線上不能長時間鎖表」的場景，需要謹慎規劃執行時機（如選擇離峰時段）、或使用支援線上 DDL（Online DDL，減少鎖表時間）的 MySQL 版本和工具（如 `pt-online-schema-change`），並且轉換前務必先在測試環境驗證、備份資料，轉換後要重新檢視原本依賴 MyISAM 特性（如全文索引在舊版 MySQL 中曾經是 MyISAM 獨有、或依賴表鎖的某些特殊行為）的應用邏輯是否受影響。

**詳細解析**：這題從理論轉向實務操作，考察對「引擎轉換」這個看似簡單但實際上需要謹慎規劃的維運操作的理解。`ALTER TABLE ... ENGINE=InnoDB` 這個語句表面上很簡單，但背後的實作是「建立一張新的、InnoDB 格式的臨時表，把舊表的所有資料逐行讀出並寫入到這張新表（同時建立 InnoDB 需要的聚簇索引結構），完成後用新表替換舊表，並刪除舊的 MyISAM 表」，這個過程對於資料量很大的表，可能需要相當長的時間（因為要重新組織全部資料並建立新的索引結構），且在傳統的實作方式下，這個重建過程需要對原表加鎖，期間會阻塞其他對這張表的讀寫操作，如果是一張仍在被線上系統頻繁存取的大表，直接執行這個操作可能導致長時間的服務不可用。因應這個問題，比較新版本的 MySQL 引入了「線上 DDL（Online DDL）」的能力，對某些類型的表結構變更（不一定包含所有情境下的引擎轉換）能做到「不完全鎖表、允許並行的讀寫繼續進行」，另外業界也有專門的工具（如 Percona 的 `pt-online-schema-change`）透過「建立一張新結構的影子表、用觸發器同步增量變化、資料複製完成後原子性地切換表名」的方式，實現幾乎不停機的大表結構變更（包括引擎轉換），這類工具在處理大表的線上結構變更時是業界的標準做法。除了執行方式的規劃，轉換前後還需要考慮「這張表原本依賴 MyISAM 特有行為的地方是否會受影響」——比如較舊版本的 MySQL，全文索引（FULLTEXT）曾經只有 MyISAM 支援（InnoDB 從 5.6 版本之後才支援全文索引），如果應用依賴這個功能，轉換引擎前要先確認 InnoDB 版本是否已經支援；另外表級鎖和行級鎖在某些依賴「整張表在寫入時完全鎖住」這種（不良）程式邏輯的舊系統裡，可能被意外地當作一種簡易的並行控制手段使用，轉換成行級鎖的 InnoDB 後，這類隱含依賴表鎖行為的邏輯可能需要重新檢視。

**面試回答方式**：先給出直接的方法——`ALTER TABLE ... ENGINE=InnoDB`。點出這個操作背後是「重建整張表」，對大表可能耗時長、可能鎖表，所以要規劃離峰時段執行，或使用線上 DDL / `pt-online-schema-change` 這類工具減少鎖表影響。補充「轉換前要備份、測試環境先驗證，轉換後要檢視原本是否有依賴 MyISAM 特性(如舊版全文索引、或誤用表鎖做並行控制)的邏輯」。展現你對這類看似簡單但實務上需要謹慎規劃的維運操作有具體的執行經驗和風險意識。

### MySQL 除了 InnoDB 和 MyISAM，還有其他儲存引擎可以選擇嗎？什麼情況下會用到？

**核心答案**：MySQL 支援多種儲存引擎，除了預設的 InnoDB，常見的還有：**Memory（記憶體引擎）**——資料完全存放在記憶體中，讀寫速度極快，但資料庫重啟或當機後資料會完全遺失，適合存放「臨時性、可重建、對速度要求極高」的資料（如某些暫存的統計中間結果、Session 資料）；**Archive（歸檔引擎）**——高壓縮比、只支援 INSERT 和 SELECT（不支援 UPDATE/DELETE），適合存放「只寫入、幾乎不修改、需要長期保存以節省空間」的歷史歸檔資料（如日誌歸檔）；**CSV 引擎**——直接以逗號分隔的純文字檔案格式儲存資料，方便和外部系統做資料交換。實務上，絕大多數的業務資料表仍然應該使用 InnoDB（因為交易和資料安全性的保證），其他引擎只在非常特定、明確知道自己需求（且能接受相應限制）的場景下才會被選用。

**詳細解析**：這題延伸 MySQL 儲存引擎的完整生態，考察是否知道除了兩個最常被拿來比較的引擎之外，還有其他針對特定場景設計的選項，並理解各自的取捨考量。Memory 引擎最大的特點是「速度」——因為完全不涉及磁碟 I/O，所有的讀寫都在記憶體中完成，效能遠高於任何需要持久化到磁碟的引擎，但這個優勢的代價是「資料完全不持久化」，一旦資料庫程序重啟（哪怕是正常的重啟，而非當機），Memory 引擎裡的所有資料都會消失，因此它只適合那些「就算資料不見了也無所謂、可以重新計算或重新產生」的場景，例如某些應用會用 Memory 引擎的表來存放「暫存的排行榜計算中間結果」或「短期有效的驗證碼」，比起額外引入 Redis 這類專門的記憶體資料庫，直接用 MySQL 內建的 Memory 引擎有時候在架構簡單性上有一定優勢（不需要額外維護一套 Redis），但需要清楚意識到它「不持久化」這個根本限制。Archive 引擎的設計目標則完全不同——它犧牲了「隨機讀寫的靈活性」（不支援 UPDATE/DELETE，只能 INSERT 新資料和 SELECT 查詢），換取了「極高的資料壓縮比」，適合那些「資料一旦產生就不會再被修改，但基於法規或稽核需求需要長期保留」的場景，例如企業內部的操作日誌、歷史交易記錄的長期歸檔，用 Archive 引擎儲存這類「只增不減」的歷史資料，能顯著降低儲存成本。CSV 引擎則更多是為了「資料交換的便利性」而非效能考量，讓 MySQL 的表能直接對應到作業系統上一個標準的 CSV 純文字檔案，方便和不支援直接資料庫連線、但能處理 CSV 檔案的外部系統或工具做資料交換。理解「MySQL 的儲存引擎架構本身是可插拔的（Pluggable Storage Engine），不同引擎針對不同的資料特性和使用場景做了取捨」這個更宏觀的架構設計理念，並能舉出至少一兩個 InnoDB/MyISAM 之外的具體引擎和其適用場景，展現你對 MySQL 的整體生態有更全面而非片面的認識。

**面試回答方式**：介紹 Memory 引擎（純記憶體、速度極快但不持久化，適合可重建的臨時資料）和 Archive 引擎（高壓縮比、只能 INSERT/SELECT，適合只寫不改的歷史歸檔資料），可以補充 CSV 引擎（方便和外部系統資料交換）。強調「MySQL 的儲存引擎是可插拔架構，不同引擎針對不同資料特性做取捨，但絕大多數業務資料仍應該用 InnoDB，其他引擎只在明確知道自己需求的特定場景下才選用」。展現你對 MySQL 儲存引擎生態的全面認識，而不只侷限在 InnoDB vs MyISAM 這組最常見的對比。
