# 題目

`IN` 子查詢與 `EXISTS` 差在哪？什麼時候該改寫成 JOIN？

## 核心答案

在現代 MySQL（5.6 之後）上，這三者的差別遠比傳說中小——最佳化器會把大部分的 `IN` 子查詢**半連接化**（semi-join），改寫成內部的連接操作並選擇合適的策略。所以「`EXISTS` 一定比 `IN` 快」這類說法是過時的經驗。

**真正需要理解的是語意差別**。`IN (子查詢)` 是「值在這個集合裡」；`EXISTS (子查詢)` 是「這個相關子查詢有結果」。**最重要的差異在 NULL**：`NOT IN` 的子查詢結果中只要有一個 NULL，整個 `NOT IN` 就永遠不成立（因為 `x NOT IN (1, NULL)` 是 `x != 1 AND x != NULL`，而後者是 UNKNOWN）。**`NOT EXISTS` 沒有這個問題**——這是實務上最容易踩到的一個坑，症狀是「查詢明明應該有結果卻回傳空」。

**改寫成 JOIN 的時機**：當你需要**用到子查詢裡的欄位**時（`IN`／`EXISTS` 只能判斷存在性，取不到值）。而如果只是判斷存在性，**用 `EXISTS` 或 `IN` 通常更清楚**，因為 JOIN 可能產生重複列而需要 `DISTINCT`——**而 `DISTINCT` 又帶來排序或雜湊的成本**。

## 詳細解析

`NOT IN` 的 NULL 陷阱值得完整說明，因為它是正確性問題而非效能問題。`SELECT * FROM a WHERE id NOT IN (SELECT b_id FROM b)`——如果 `b.b_id` 有任何一列是 NULL，**這個查詢回傳零列**，即使 `a` 裡明明有不在 `b` 中的 id。原因是三值邏輯：`x != NULL` 的結果是 UNKNOWN 而非 TRUE，**而 `NOT IN` 需要所有比較都為 TRUE**。**防護方式有三種**：改用 `NOT EXISTS`（推薦，語意最清楚且沒有這個問題）、在子查詢加 `WHERE b_id IS NOT NULL`、或者讓那個欄位設為 `NOT NULL`。這個坑之所以危險，是因為它在測試資料沒有 NULL 時完全不會顯現。

**相關子查詢（correlated subquery）的成本要注意**。`SELECT ... WHERE EXISTS (SELECT 1 FROM b WHERE b.a_id = a.id)` 中的子查詢**引用了外層的欄位**，理論上要對外層的每一列執行一次。最佳化器通常能把它轉成半連接（一次性的連接操作），但在複雜的情況下可能轉不了——此時就是真的逐列執行，成本是外層列數乘以子查詢成本。**`EXPLAIN` 裡出現 `DEPENDENT SUBQUERY` 就是這個訊號**，看到它應該考慮改寫。

`IN (常數列表)` 與 `IN (子查詢)` 是完全不同的東西。前者是簡單的值比對（大列表時 MySQL 會排序後二分查找），後者才涉及半連接的優化。**要注意超大的常數列表**（幾千個值）會讓 SQL 文字很長、解析變慢、也可能撞到 `max_allowed_packet`——那通常表示應該改成把值放進臨時表或用 JOIN。

改寫的一般原則是「讓意圖最清楚的寫法優先」。現代最佳化器對這幾種形式的處理已經相當好，所以除非量測顯示有問題，應該選最能表達意圖的寫法：判斷存在用 `EXISTS`、判斷不存在用 `NOT EXISTS`、需要取值用 JOIN、需要聚合用 JOIN 加 `GROUP BY`。為了「聽說比較快」而選一個較難讀的寫法，通常是錯的優化。

## 面試回答方式

先破除過時的經驗——在 MySQL 5.6 之後最佳化器會把大部分 `IN` 子查詢半連接化，所以「`EXISTS` 一定比 `IN` 快」是過時的。把重點轉到**語意差別**，特別是 **`NOT IN` 的 NULL 陷阱**：子查詢結果只要有一個 NULL，整個 `NOT IN` 就永遠不成立，症狀是「明明該有結果卻回傳空」，而且在測試資料沒有 NULL 時完全不會顯現。給改寫成 JOIN 的時機（需要用到子查詢裡的欄位時）並提醒 JOIN 可能產生重複列而需要 `DISTINCT`，那又帶來排序成本。加分點有兩個：`EXPLAIN` 出現 `DEPENDENT SUBQUERY` 表示半連接優化沒生效，是真的逐列執行；以及一般原則是「讓意圖最清楚的寫法優先」——為了「聽說比較快」而選較難讀的寫法通常是錯的優化。

## 講稿

我想先破除一個過時的經驗。在 MySQL 5.6 之後，最佳化器會把大部分的 IN 子查詢半連接化，改寫成內部的連接操作。所以 EXISTS 一定比 IN 快這類說法已經不成立了。

真正需要理解的是語意差別，最重要的是 NULL 的處理。NOT IN 的子查詢結果中只要有一個 NULL，整個條件就永遠不成立。因為某個值不等於 NULL 的結果是未知而不是真，而 NOT IN 需要所有比較都為真。

所以會出現查詢明明應該有結果卻回傳空的狀況。這個坑特別危險，因為它在測試資料沒有 NULL 的時候完全不會顯現。防護方式是改用 NOT EXISTS，語意最清楚而且沒有這個問題。

改寫成 JOIN 的時機是當你需要用到子查詢裡的欄位。如果只是判斷存在性，用 EXISTS 通常更清楚，因為 JOIN 可能產生重複列而需要去重，而去重又帶來排序的成本。

還有一個訊號要注意。執行計畫裡出現相依子查詢，表示半連接優化沒有生效，是真的對外層的每一列各執行一次子查詢，那時候就該考慮改寫。

我的一般原則是讓意圖最清楚的寫法優先。為了聽說比較快而選一個較難讀的寫法，通常是錯的優化。

## 常見追問

### 三值邏輯還在哪些地方會咬人？

**核心答案**：四個常見的地方。**`WHERE col != 'x'` 不會回傳 `col IS NULL` 的列**——因為 `NULL != 'x'` 是 UNKNOWN 而非 TRUE。**聚合函式忽略 NULL**——`COUNT(col)` 不算 NULL，而 `COUNT(*)` 算；`AVG(col)` 的分母也不含 NULL 的列。**`GROUP BY` 把所有 NULL 當成同一組**（雖然 `NULL = NULL` 是 UNKNOWN，但分組時它們被視為相同）。**`UNIQUE` 索引允許多個 NULL**（在 MySQL 與多數資料庫中），因為 NULL 之間不算重複。

**詳細解析**：「`!=` 不包含 NULL」是最常造成資料遺漏的一個。想查「狀態不是已取消的訂單」，寫 `WHERE status != 'CANCELLED'` 會漏掉所有 `status IS NULL` 的訂單——而那些訂單在業務上顯然應該被包含。正確的寫法是 `WHERE status != 'CANCELLED' OR status IS NULL`，或者更好的做法是讓那個欄位 `NOT NULL` 並用一個明確的預設值。這指向一個設計原則：能避免 NULL 就避免——用 `NOT NULL DEFAULT ''` 或一個明確的哨兵值，讓三值邏輯的複雜度從一開始就不進入系統。NULL 應該保留給真正表示「未知」或「不適用」的語意，而不是「還沒填」或「沒有值」。

**面試回答方式**：給四個地方並各配精確的行為。重點展開 `!=` 不包含 NULL 是最常造成資料遺漏的，用「查狀態不是已取消的訂單會漏掉狀態為 NULL 的」這個具體例子。給出正確寫法與更好的做法。收在設計原則：能避免 NULL 就避免，用 `NOT NULL` 加明確預設值讓三值邏輯的複雜度不進入系統，NULL 應保留給真正表示「未知」或「不適用」的語意。

### 什麼是半連接優化，它做了什麼？

**核心答案**：半連接（semi-join）是「**只判斷存在性、不產生重複列**」的連接。`WHERE id IN (SELECT ...)` 在語意上是半連接——外層的每一列最多輸出一次，不管子查詢裡有幾筆匹配。最佳化器把它轉成內部的半連接操作後，可以選擇多種執行策略：**Duplicate Weedout**（先做普通連接再去重）、**FirstMatch**（找到第一個匹配就停止繼續掃描）、**Loose Scan**（利用索引的有序性跳過重複值）、**Materialization**（把子查詢結果物化成臨時表再連接）。

**詳細解析**：「有多種策略可選」正是半連接優化的價值——最佳化器可以依統計資訊選最合適的。FirstMatch 在「子查詢匹配很多但只需要知道有沒有」時效果極好（找到一個就停）；Materialization 在「子查詢結果很小且被重複使用」時最好（算一次，之後都用臨時表）。**`EXPLAIN` 的 `Extra` 會顯示用了哪一種**（例如 `FirstMatch(t1)`、`Start temporary`／`End temporary` 表示 Duplicate Weedout）。知道這些名字的價值在於：看到執行計畫時能理解最佳化器做了什麼決定，而不是只看到一堆看不懂的字串——而理解了才可能判斷那個決定合不合理。

**面試回答方式**：給半連接的定義（只判斷存在性、外層每列最多輸出一次）與最佳化器可選的多種策略。真正的加分點是說明「有多種策略可選」正是它的價值，並各給一個最適合的場景（FirstMatch 適合匹配多但只需知道有沒有、Materialization 適合結果小且重複使用）。收在實用價值：**`EXPLAIN` 的 `Extra` 會顯示用了哪一種**，知道這些名字讓你能理解最佳化器的決定而非只看到看不懂的字串。

### SELECT 星號在子查詢裡有問題嗎？

**核心答案**：**在 `EXISTS` 子查詢裡沒有問題**——`EXISTS (SELECT * FROM ...)` 與 `EXISTS (SELECT 1 FROM ...)` 完全等價，最佳化器根本不取欄位，只判斷有沒有列。**寫 `SELECT 1` 是一個沒有效果的習慣**（但也無害）。**在 `IN` 子查詢裡則會出錯**——`IN` 需要單一欄位，`SELECT *` 回傳多欄位會直接報錯。

**詳細解析**：**真正該注意 `SELECT *` 的是外層查詢**，而理由有三個：破壞覆蓋索引（取了不必要的欄位就必須回表）、傳輸多餘的資料（尤其有大的 text 或 blob 欄位時）、以及對 schema 變更脆弱（新增一個欄位就改變了結果的形狀，而應用可能依賴欄位順序或數量）。第三點在 ORM 與手寫 SQL 混用的系統裡特別容易出事。所以「不要用 `SELECT *`」是對的建議，但理由應該說清楚——很多人以為是「效能」，而「破壞覆蓋索引」與「對 schema 變更脆弱」才是更實質的理由。

**面試回答方式**：先給精確的答案（`EXISTS` 裡完全等價、`IN` 裡會報錯），並指出寫 `SELECT 1` 是沒有效果但無害的習慣。把重點轉到**外層查詢**，給三個理由（破壞覆蓋索引、傳輸多餘資料、對 schema 變更脆弱）。收在澄清：「不要用 `SELECT *`」是對的但理由常被說錯——不只是效能，破壞覆蓋索引與對 schema 變更脆弱才是更實質的理由。
