# 題目

NULL 在 SQL 裡有哪些特殊行為？它對索引與查詢有什麼影響？

## 核心答案

NULL 的核心是**三值邏輯**——比較的結果不是 TRUE／FALSE 而是 TRUE／FALSE／UNKNOWN，**而 `WHERE` 只保留 TRUE 的列**。這帶來一連串反直覺的行為。

**`NULL = NULL` 是 UNKNOWN 而非 TRUE**——所以要用 `IS NULL`。`col != 'x'` 不會回傳 `col IS NULL` 的列——這是最常造成資料遺漏的一個。`NOT IN (子查詢)` 只要子查詢結果有一個 NULL 就永遠不成立。**聚合函式忽略 NULL**——`COUNT(col)` 不算 NULL 而 `COUNT(*)` 算，`AVG` 的分母也不含 NULL 的列。**`GROUP BY` 把所有 NULL 當成同一組**，`ORDER BY` 在 MySQL 中把 NULL 排在最前（升序時）。**唯一索引允許多個 NULL**——因為 NULL 之間不算重複。

**索引方面：InnoDB 的索引「包含」NULL**（B+ 樹裡有 NULL 的項），所以 `WHERE col IS NULL` 是可以走索引的——這與「NULL 不走索引」這個常見的誤傳相反。但可為空的欄位需要額外的 NULL 標記位，而且它讓最佳化器的選擇性估算更複雜。

## 詳細解析

「`!=` 不包含 NULL」值得完整說明，因為它是正確性問題。想查「狀態不是已取消的訂單」，寫 `WHERE status != 'CANCELLED'` 會**漏掉所有 `status IS NULL` 的訂單**——而那些在業務上顯然應該被包含。正確的寫法是 `WHERE status != 'CANCELLED' OR status IS NULL`，**或者用 `WHERE NOT (status <=> 'CANCELLED')`**（MySQL 的 `<=>` 是 NULL 安全的相等比較）。但最好的做法是讓那個欄位 `NOT NULL` 並用一個明確的預設值——問題從源頭消失。

「NULL 應該表示什麼」是一個設計問題。它的正確語意是**「未知」或「不適用」**——例如「使用者還沒填生日」（未知）、「這筆訂單沒有取消原因因為它沒被取消」（不適用）。不該用它表示「零」「空字串」「預設值」或「還沒處理」——那些都有更明確的表達方式。很多 NULL 造成的麻煩，根源是它被用來表達了不該用它表達的東西。

唯一索引允許多個 NULL 是一個常被利用也常被誤解的行為。它讓「已刪除的記錄保留但不佔用唯一鍵」這種軟刪除模式成為可能（把 `deleted_at` 之外再加一個 `active` 欄位，刪除時設為 NULL），但也意味著「唯一」的保證在 NULL 上不成立。要注意這個行為在不同資料庫間不一致——SQL Server 的唯一索引只允許一個 NULL，PostgreSQL 與 MySQL 允許多個。跨資料庫的應用不能依賴這個行為。

NULL 對統計資訊與最佳化器的影響：可為空的欄位讓選擇性估算更複雜（NULL 的比例可能很高而分佈極不均勻），**而直方圖能改善這一點**。另外 **`NOT NULL` 讓某些優化成為可能**——例如在 `NOT NULL` 欄位上，`COUNT(col)` 可以直接用 `COUNT(*)` 的路徑；某些 JOIN 的改寫也需要 `NOT NULL` 的保證。所以「盡量 `NOT NULL`」除了語意上的清楚，也有實際的效能理由。

## 面試回答方式

先給**三值邏輯**這個核心（比較結果是 TRUE／FALSE／UNKNOWN，而 `WHERE` 只保留 TRUE），再列出一連串反直覺的行為並把 **`!=` 不包含 NULL** 標為最常造成資料遺漏的。**主動澄清「NULL 不走索引」是誤傳**——InnoDB 的索引包含 NULL，`IS NULL` 可以走索引。加分點有三個：**「NULL 應該表示什麼」是設計問題**——它的正確語意是「未知」或「不適用」，很多麻煩的根源是它被用來表達不該用它表達的東西；唯一索引允許多個 NULL 的行為在不同資料庫間不一致（SQL Server 只允許一個），跨資料庫的應用不能依賴；以及 **`NOT NULL` 有實際的效能理由**——某些優化與 JOIN 的改寫需要這個保證。

## 講稿

NULL 的核心是三值邏輯。比較的結果不是真或假，而是真、假、未知，而 WHERE 只保留為真的列。這帶來一連串反直覺的行為。

NULL 等於 NULL 是未知而不是真，所以要用 IS NULL。不等於某個值的條件不會回傳值為 NULL 的列，這是最常造成資料遺漏的一個。NOT IN 的子查詢結果只要有一個 NULL 就永遠不成立。聚合函式忽略 NULL。唯一索引允許多個 NULL。

我想澄清一個常見的誤傳，很多人說 NULL 不走索引。實際上 InnoDB 的索引是包含 NULL 的，所以判斷是否為空的查詢可以走索引。

不等於那一條值得完整說明，因為它是正確性問題。想查狀態不是已取消的訂單，寫不等於已取消會漏掉所有狀態為 NULL 的訂單，而那些在業務上顯然應該被包含。最好的做法是讓那個欄位不可為空並用一個明確的預設值，問題從源頭消失。

還有一個設計層面的判斷。NULL 的正確語意是未知或不適用，不該用它表示零、空字串、或還沒處理。很多 NULL 造成的麻煩，根源是它被用來表達了不該用它表達的東西。

## 常見追問

### 軟刪除的設計該怎麼處理唯一約束？

**核心答案**：問題是「刪除後同樣的值要能再次使用」與「未刪除的記錄之間必須唯一」這兩個需求。三種做法：**用 NULL 的特性**（加一個 `active` 欄位，未刪除時填一個固定值、刪除時設為 NULL，唯一索引建在 `(name, active)` 上——**利用「多個 NULL 不算重複」**）、**把刪除時間編進唯一鍵**（唯一索引建在 `(name, deleted_at)`，未刪除時 `deleted_at` 是 0 或一個哨兵值）、或**用部分索引**（PostgreSQL 支援 `CREATE UNIQUE INDEX ... WHERE deleted_at IS NULL`，**這是最乾淨的做法但 MySQL 不支援**）。

**詳細解析**：更值得問的是「真的需要軟刪除嗎」。軟刪除的動機通常是「怕誤刪」或「需要保留歷史」，但它讓每一個查詢都要記得加 `WHERE deleted_at IS NULL`——而忘記的那一次就是 bug，且那類 bug 很難被測試發現（測試資料通常沒有已刪除的記錄）。替代方案有兩個：**真的刪除但有可靠的備份與 PITR**（處理「誤刪」的需求）、或者把已刪除的記錄移到歷史表（處理「保留歷史」的需求，而且讓主表保持乾淨與快速）。「用一個欄位標記狀態」看似最簡單，但它把複雜度分散到了每一個查詢——而分散的複雜度是最難管理的一種。

**面試回答方式**：給三種處理唯一約束的做法並指出 **PostgreSQL 的部分索引最乾淨但 MySQL 不支援**。真正的加分點是往回問**「真的需要軟刪除嗎」**——它讓每個查詢都要記得加條件，忘記的那一次就是 bug 且很難被測試發現。給兩個替代方案（真刪除加可靠備份、移到歷史表）並收在判斷：「用一個欄位標記狀態」看似簡單但把複雜度分散到每一個查詢，而分散的複雜度是最難管理的一種。

### 為什麼有人主張「完全不用 NULL」？

**核心答案**：因為 NULL 引入的三值邏輯讓所有涉及該欄位的查詢都要額外考慮一種情況，而那個考慮很容易被遺漏。主張者認為：「未知」與「不適用」這兩種語意應該用不同的方式表達——「未知」用一個明確的哨兵值或一個獨立的「是否已知」欄位，「不適用」則表示 schema 設計有問題（那個欄位不該屬於這張表，應該拆出去）。

**詳細解析**：「不適用意味著該拆表」是這個主張中最有價值的部分。一張 `users` 表如果有 `company_name`、`company_tax_id` 這些「只有企業使用者才有」的欄位，**個人使用者的那些欄位就是 NULL**——而正確的設計是把企業相關的資訊拆到 `company_profiles` 表。這樣不只消除了 NULL，還讓「哪些欄位是一組的」變得明確。 但完全不用 NULL 在實務上很難堅持——外連接必然產生 NULL、聚合函式在空集合上回傳 NULL、而且與既有系統整合時無法控制。所以務實的立場是「盡量避免但理解它」：在自己設計的 schema 中盡量 `NOT NULL`，同時清楚知道 NULL 的所有行為以便處理無法避免的情況。

**面試回答方式**：給主張的理由（三值邏輯讓每個查詢都要多考慮一種情況且容易遺漏）與兩種語意的分開處理。真正的加分點是展開**「不適用意味著該拆表」**，用 `users` 表裡的企業欄位舉例，並指出這樣不只消除 NULL，還讓「哪些欄位是一組的」變得明確。誠實指出完全不用在實務上難以堅持（外連接、空集合的聚合、既有系統整合）。收在務實立場：**盡量避免但理解它**。

### 索引裡的 NULL 對效能有什麼實際影響？

**核心答案**：主要影響選擇性的估算與索引的大小。如果一個欄位有 90% 是 NULL，**索引裡就有 90% 的項是 NULL** ——查 `WHERE col = 'x'` 時索引仍然有效（NULL 的部分被跳過），但查 `WHERE col IS NULL` 會命中 90% 的列，**那時候全表掃描通常更快**。最佳化器需要知道 NULL 的比例才能做對這個判斷，而基數統計不記錄這個資訊——**直方圖才記錄**。

**詳細解析**：一個常見的優化是「不要為大量 NULL 的欄位建立索引」，或者建立部分索引只涵蓋非 NULL 的部分（PostgreSQL 的 `WHERE col IS NOT NULL`，MySQL 沒有直接支援但可以用產生欄位模擬）。**這在「稀疏欄位」上收益很大**——例如一個只有 1% 的訂單有值的 `coupon_code` 欄位，索引只需要涵蓋那 1%，大小是完整索引的百分之一。MySQL 缺少部分索引是一個實質的功能差距，而繞道的方式（產生欄位加索引）在可讀性與維護性上都較差。知道這個差距，在「該用哪個資料庫」的討論中是一個具體的論據，而具體的功能差異比籠統的偏好更有說服力。

**面試回答方式**：給主要影響（選擇性估算與索引大小）並用「90% 是 NULL」的具體例子說明查詢的差異。指出基數統計不記錄 NULL 比例，直方圖才記錄。真正的加分點是提出**部分索引**的優化——稀疏欄位上索引只涵蓋非 NULL 的部分，大小可能只有百分之一；並誠實指出 MySQL 缺少部分索引是實質的功能差距，繞道方式（產生欄位）可讀性較差。收在觀點：具體的功能差異比籠統的偏好更有說服力。
