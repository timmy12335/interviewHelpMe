# 題目

SQL 注入是怎麼發生的？為什麼「參數化查詢（Prepared Statement）」能有效防範？

## 核心答案

SQL 注入發生的根本原因是「應用程式把使用者輸入的內容，直接用字串拼接的方式組成 SQL 語句」，導致使用者可以透過精心構造的輸入（例如在輸入框裡輸入 `' OR '1'='1`），改變這條 SQL 語句原本的邏輯結構，讓資料庫執行「攻擊者想要的查詢」而非「開發者原本預期的查詢」（例如繞過登入驗證、竊取或竄改資料）。**參數化查詢（Prepared Statement）**能有效防範的原理是——它把「SQL 語句的結構（哪裡是欄位、哪裡是條件）」和「使用者輸入的實際資料值」徹底分開處理：先把帶有佔位符（如 `?`）的 SQL 語句範本送給資料庫「預編譯」，資料庫先確定好這條語句的語法結構和執行計畫，之後再單獨把使用者輸入的值當作「純粹的資料」填入這些佔位符——因為資料庫在填值階段，完全不會把這些值當作「SQL 語法的一部分」重新解析，即使使用者輸入的內容裡包含類似 SQL 語法的特殊字元，也只會被當成單純的字串值處理，不可能改變原本已經固定下來的語句結構，從根本上杜絕了注入的可能性。

## 詳細解析

**SQL 注入的攻擊範例**：假設一個登入功能的後端程式碼，用字串拼接的方式組出查詢語句：
```java
String sql = "SELECT * FROM users WHERE username = '" + username + "' AND password = '" + password + "'";
```
如果攻擊者在「username」欄位輸入 `admin' -- `（後面加上 SQL 的註解符號 `--`），拼接後的語句會變成：
```sql
SELECT * FROM users WHERE username = 'admin' -- ' AND password = '...'
```
`--` 之後的內容全部被當成註解忽略，這條語句實際執行的邏輯變成「只要 username 是 admin 就回傳結果，完全不檢查密碼」，攻擊者就能在不知道密碼的情況下，繞過驗證直接以 admin 身分登入。更進階的攻擊還能透過 `UNION SELECT` 這類手法，讓查詢結果洩漏出原本不該被查詢到的其他資料表內容。

**參數化查詢為什麼能防範**：使用參數化查詢時，程式碼會寫成：
```java
String sql = "SELECT * FROM users WHERE username = ? AND password = ?";
PreparedStatement stmt = connection.prepareStatement(sql);
stmt.setString(1, username);
stmt.setString(2, password);
```
這裡的關鍵差異是——`sql` 這個字串（包含 `?` 佔位符的語句結構）在呼叫 `prepareStatement` 時，就已經被送到資料庫「預先編譯」，資料庫在這個階段就已經完全確定了這條語句的語法結構（有幾個條件、用什麼比較運算子等），並且可能已經生成了對應的執行計畫。之後呼叫 `setString` 填入實際的使用者輸入值時，這些值是透過「資料傳輸協定」直接傳給資料庫、填入已經編譯好的佔位符位置，資料庫執行時，這些值「只會被當成純粹的字串資料」去做比較（比如「username 欄位的值是否等於這個字串」），即使這個字串裡包含 `' OR '1'='1` 這樣的內容，資料庫也不會把它「重新解析成 SQL 語法的一部分」，而是老老實實地把整個字串（包括其中的單引號等字元）當成一個完整的資料值去比對，攻擊者輸入的特殊字元完全失去了「改變語句結構」的能力，注入攻擊因此失效。

**其他防範措施**：除了參數化查詢這個最核心、最根本的防禦手段，實務上通常還會搭配：**輸入驗證**（在應用層面對輸入格式做基本檢查，如電話號碼欄位只允許數字，雖然不能完全依賴這個作為唯一防線，但能過濾掉明顯不合理的輸入）、**最小權限原則**（應用程式連線資料庫使用的帳號，只賦予其業務所需的最小權限，例如唯讀查詢的功能就不該給予這個帳號 DROP TABLE 的權限，即使真的發生注入，也能限制損害範圍）、**ORM 框架**（如 MyBatis、Hibernate 等，其標準用法底層都是基於參數化查詢實作，只要正確使用框架提供的參數綁定方式而非手動拼接 SQL 字串，天然就能規避注入風險）。

## 面試回答方式

先用一個具體的攻擊範例（如 `' OR '1'='1` 或註解符號繞過密碼驗證）具體地展示 SQL 注入是怎麼發生的，讓面試官感受到你不是死記硬背概念。接著解釋參數化查詢的防範原理——關鍵是「語句結構先被固定下來（預編譯），使用者輸入的值之後才被當成純資料填入，不會被重新解析成語法」，這是理解「為什麼有效」的核心。最後補充其他防禦層次（輸入驗證、最小權限、ORM 框架正確使用），展現你有「縱深防禦（defense in depth）」的安全思維，而不只依賴單一防線。

## 常見追問

### 如果團隊裡有人堅持要用字串拼接的方式組 SQL（比如因為要動態組合複雜的查詢條件），有沒有安全的做法？

**核心答案**：即使需要「動態組合」查詢的結構（例如根據前端傳來的篩選條件，決定 WHERE 子句要包含哪些條件），仍然可以在「結構」和「數值」分離的原則下實現——**動態拼接的部分應該只限於「SQL 的結構性元素」**（如欄位名稱、要不要加上某個 WHERE 條件、排序方向 ASC/DESC 這類「有限選項、可以用白名單驗證」的部分），而「實際的使用者輸入值」（如使用者填的搜尋關鍵字、篩選的具體數值），永遠都應該透過參數化查詢的佔位符傳遞，絕不能直接拼接進 SQL 字串。多數 ORM 框架（如 MyBatis）針對這種「動態 SQL」需求，提供了專門的語法（如 MyBatis 的 `<if>`、`<where>` 動態標籤），讓開發者可以優雅地根據條件組合出不同的 SQL 結構，同時底層仍然對所有的實際數值使用參數化查詢，兼顧靈活性和安全性。

**詳細解析**：這題釐清一個常見的誤解——「動態 SQL」和「字串拼接注入風險」不是同一回事，動態組合查詢邏輯本身是合理的業務需求（不同的篩選條件組合，理應產生結構不同的 SQL），問題只出在「把使用者輸入的實際數值也一起用字串拼接的方式塞進去」。正確的做法是嚴格區分兩種「變動的部分」——一種是「結構性的變動」，比如「這次查詢要不要加上『依照建立時間排序』這個 ORDER BY 子句」、「要用哪個欄位做排序」，這類選項通常是有限的、可以列舉的（比如只允許依照 `created_at` 或 `updated_at` 排序），對這類結構性的動態內容，可以安全地做「白名單驗證」（檢查傳入的排序欄位名稱，是否在事先定義好的合法欄位清單裡，只有在清單內才允許拼接進 SQL，否則拒絕或使用預設值），因為這類值不是「任意的使用者輸入」，而是「從一組已知的、安全的選項中選擇」；另一種是「純粹的數值型變動」，比如使用者在搜尋框裡打的關鍵字、篩選的具體日期範圍，這類「真正任意、不可預期」的輸入，無論如何都必須透過參數化查詢的佔位符機制傳遞，絕對不能直接拼接。以 MyBatis 為例，它透過 `#{}` 語法（底層對應到 JDBC 的 PreparedStatement 參數綁定，即參數化查詢）和 `${}` 語法（純粹的字串替換，直接拼接，有注入風險）明確區分了這兩種用法，並提供 `<if test="...">` 這類動態 SQL 標籤，讓開發者可以根據條件「動態地決定要不要加入某個 WHERE 子句」，但子句裡涉及的實際數值，仍然是透過 `#{}` 做參數化綁定，這樣就能同時滿足「查詢結構需要動態變化」和「防止 SQL 注入」這兩個看似衝突、實則可以並存的需求。回答這題的重點是清楚傳達「區分『結構的動態』和『數值的動態』,只有前者可以在嚴格白名單驗證下考慮拼接，後者永遠必須參數化」這個核心原則。

**面試回答方式**：先破除迷思——「動態 SQL 本身沒問題，問題只在於把使用者的實際輸入值也拼接進去」。給出解法——「區分『結構性的動態』(如排序欄位、要不要加某個條件,這類可以用白名單驗證後安全拼接) 和『數值的動態』(使用者實際輸入的值,永遠必須參數化)」。舉 MyBatis 的 `#{}` (參數化) 和 `${}` (直接拼接,有風險) 的區分作為具體例子。展現你對「動態 SQL」和「注入防範」並不衝突有清晰、可落地的理解。

### 除了 SQL 注入，NoSQL 資料庫（如 MongoDB）是不是就完全沒有類似的注入風險？

**核心答案**：不是——NoSQL 資料庫同樣存在類似性質的「注入」風險，只是攻擊的具體形式和 SQL 注入不同，通常稱為 **NoSQL 注入**。以 MongoDB 為例，如果應用程式直接把使用者輸入「未經檢查地」當作查詢條件的一部分（尤其是當查詢條件用 JSON 物件表示、且應用程式直接把使用者傳入的 JSON 結構原樣傳給資料庫驅動程式時），攻擊者可以透過傳入特殊的「運算子物件」（如 MongoDB 的 `$ne`、`$gt`、`$where` 這類查詢運算子），改變原本查詢的邏輯（例如把「密碼必須完全相等」的條件，偷換成「密碼不等於任何不可能的值（$ne: null）」這種恆為真的條件），效果和 SQL 注入的「繞過驗證」類似。防範方式的核心原則相通——**永遠不要把使用者的原始輸入，未經檢查地直接當成查詢邏輯的一部分**，應該嚴格限制使用者輸入只能被當作「純數值」使用，而不能被解讀成查詢運算子或程式碼；多數現代的 NoSQL 資料庫官方驅動程式和 ODM 框架（如 Mongoose），也提供了相應的輸入清理和型別檢查機制來降低這類風險。

**詳細解析**：這題把「注入攻擊」這個安全概念，從 SQL 特有的問題，延伸到更廣泛的「未經檢查地信任並執行使用者輸入」這個通用安全原則，展現更全面的安全意識。NoSQL 注入之所以能發生，根源和 SQL 注入完全一致——都是「應用程式沒有嚴格區分『查詢的邏輯結構』和『使用者提供的資料值』，讓使用者有機會透過精心構造的輸入，去操縱原本不該由他們控制的邏輯部分」。以 MongoDB 為具體例子，假設一個登入驗證的程式碼寫成類似 `db.users.find({ username: req.body.username, password: req.body.password })` 這樣直接把 HTTP 請求的內容當成查詢條件，如果應用程式（或使用的框架）沒有對輸入做型別檢查，攻擊者可以構造請求，讓 `password` 欄位的值不是一個普通字串，而是一個 JSON 物件 `{ "$ne": null }`（即「不等於 null」這個 MongoDB 查詢運算子），這樣一來，查詢會被解讀成「密碼不等於 null 就符合條件」，而任何實際存在的密碼欄位當然都不等於 null，導致這個條件恆為真，攻擊者完全不需要知道正確密碼就能通過驗證，這個攻擊手法俗稱「運算子注入（Operator Injection）」，是 NoSQL 注入最常見的形式之一。這個例子清楚地展現了「注入攻擊」的通用本質——不管底層是關聯式資料庫的 SQL 語法、還是 NoSQL 資料庫的查詢運算子 DSL，只要應用程式讓「使用者的輸入」有機會被解讀成「查詢邏輯的一部分（而非單純的資料）」，就存在被注入攻擊的風險。防範的核心原則因此也是通用的——嚴格驗證輸入的型別（例如明確要求 `password` 欄位必須是字串型別，如果收到的是物件就直接拒絕，而不是原樣傳給資料庫）、絕不盲目地把整個請求內容不做檢查地轉發給資料庫查詢層。理解「注入攻擊是一個跨越 SQL/NoSQL 的通用安全概念，核心都是『邏輯結構和資料值沒有被嚴格分離』」，展現你的安全知識能夠超越單一技術棧、觸類旁通。

**面試回答方式**：先明確回答「不是，NoSQL 同樣有類似風險，稱為 NoSQL 注入」。用 MongoDB 的 `$ne` 運算子注入具體舉例（使用者傳入 `{"$ne": null}` 這種運算子物件而非普通字串，繞過密碼驗證）。點出通用防範原則——「嚴格驗證輸入型別、絕不把使用者輸入未經檢查地直接當成查詢邏輯的一部分」，這和 SQL 注入防範的核心原則（結構與資料分離）本質相通。展現你對「注入攻擊」這個安全概念有超越單一資料庫技術的、更本質的理解。

### 儲存過程（Stored Procedure）是不是就能完全避免 SQL 注入？

**核心答案**：不是——儲存過程本身**不能**保證完全避免 SQL 注入，關鍵仍然在於「儲存過程內部，是怎麼組合和執行 SQL 的」。如果儲存過程內部是「正確地使用參數（把外部傳入的值當作參數綁定使用，而非用字串拼接組成動態 SQL）」，那麼儲存過程確實能提供和參數化查詢相同的防護效果；但如果儲存過程內部圖方便，用「字串拼接」的方式動態組出一條 SQL 語句再執行（例如使用 `EXECUTE IMMEDIATE` 或類似機制執行一段拼接出來的 SQL 字串），即使外面包了一層「儲存過程」的外殼，內部的字串拼接漏洞完全沒有被解決，一樣存在被注入的風險。所以「使用儲存過程」本身不是防止注入的充分條件，真正的關鍵永遠是「SQL 的組成方式是否正確地把結構和數值分離」。

**詳細解析**：這題破除一個常見的安全迷思——「只要用了儲存過程，就自動安全」。這個誤解的來源，可能是因為儲存過程確實常被當作一種「資料庫存取的封裝層」，開發者只需要呼叫預先定義好的儲存過程、傳入參數，不需要在應用程式端直接手寫 SQL，這種「間接」的存取方式，給人一種「比較安全」的錯覺。但事實上，儲存過程內部仍然是用 SQL（或資料庫廠商提供的過程式擴充語言，如 Oracle 的 PL/SQL、MySQL 的儲存過程語法）寫成的程式碼，如果撰寫儲存過程的開發者，在儲存過程內部依然用「字串拼接」的方式組出一條動態的 SQL 語句（這在需要處理「動態排序欄位」、「動態 WHERE 條件組合」這類需求時，有時候會被偷懶地這樣實作），並透過資料庫提供的「執行動態 SQL」的機制（如 SQL Server 的 `sp_executesql` 搭配不當使用、或 Oracle 的 `EXECUTE IMMEDIATE`）去執行這段拼接出來的字串，那麼這個儲存過程本質上仍然是把「使用者輸入的值」當成了「SQL 語法的一部分」去執行，注入攻擊的原理和風險完全沒有改變，唯一的差別只是「拼接 SQL 這個危險的動作，發生在資料庫的儲存過程內部，而不是應用程式的程式碼裡」，這只是換了一個地方犯同樣的錯誤，並沒有解決根本問題。反過來說，如果儲存過程內部正確地使用「參數」（例如 `CREATE PROCEDURE GetUser(IN p_username VARCHAR(50)) BEGIN SELECT * FROM users WHERE username = p_username; END`，這裡的 `p_username` 是一個真正的參數，資料庫在執行這個儲存過程時，會把傳入的值當作參數綁定，而不是重新解析成 SQL 語法），那麼這個儲存過程確實能提供和應用程式端使用參數化查詢完全相同的防護效果——因為底層的防禦機制（結構與數值分離）是一致的，只是這次是在資料庫的儲存過程層面實現，而非應用程式層面。這題的核心啟示是——「防止 SQL 注入的關鍵，永遠是『SQL 語句的組成方式』本身，任何試圖用『架構上多包一層』（無論是儲存過程、ORM 框架、還是其他中介層）來規避這個核心問題，如果內部實作沒有真正做到參數化，這層包裝就只是虛假的安全感，不能取代對『結構與數值分離』這個根本原則的正確實踐」。

**面試回答方式**：先明確回答「不是,儲存過程本身不保證防注入,關鍵仍在於儲存過程內部怎麼組合 SQL」。舉例說明——「如果儲存過程內部正確使用參數綁定,效果等同參數化查詢,能防注入；但如果儲存過程內部用字串拼接組出動態 SQL 再執行(如 EXECUTE IMMEDIATE),同樣的注入風險完全沒有解決,只是換了個地方犯錯」。用一句話總結核心原則——「防注入的關鍵永遠是『結構與數值是否被正確分離』,任何包裝(儲存過程、ORM、中介層)本身都不是充分條件,内部實作正確才是關鍵」。展現你不會被表面的架構包裝迷惑，能看穿安全防護的本質所在。
