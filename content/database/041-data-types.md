# 題目

選資料型別時該考慮什麼？為什麼「能小就小」是一個原則？

## 核心答案

原則是「用能正確表達語意的最小型別」，理由有三層。**空間**——每一列省下的位元組乘以列數，在千萬列的表上是可觀的。**索引效率**——索引項越小，一個頁能放的越多、樹越矮、快取的命中率越高。**記憶體**——更小的資料意味著 Buffer Pool 能快取更多列。

具體的選擇要點：整數用能容納範圍的最小型別（`TINYINT` 到 `BIGINT`，而 `INT(11)` 的括號數字只影響顯示寬度、不影響儲存，這是一個普遍的誤解）。**時間用 `DATETIME` 或 `TIMESTAMP`**（`TIMESTAMP` 4 位元組但範圍到 2038 年且受時區影響；`DATETIME` 5 到 8 位元組、無時區），**不要用字串存時間**。**金額用 `DECIMAL`**，不要用 `FLOAT`／`DOUBLE`。變長字串用 `VARCHAR` 並設定合理的長度上限。

**最重要的一條是「盡量 `NOT NULL`」**——可為空的欄位需要額外的 NULL 標記位、讓索引與查詢的處理更複雜、而且引入三值邏輯的各種陷阱。

## 詳細解析

`VARCHAR` 的長度宣告不影響磁碟儲存（只存實際長度加 1 到 2 位元組的長度前綴），但影響記憶體。排序與臨時表在某些情況下會依宣告的最大長度分配空間——所以 `VARCHAR(255)` 存一個 10 字元的值，在排序時可能佔用 255 字元的空間。這讓「反正不影響磁碟就設大一點」變成一個真實的成本，尤其是在有大量排序或臨時表的查詢上。合理的做法是依業務的實際上限設定，而不是一律 255。

**`CHAR` 與 `VARCHAR` 的選擇有明確的界線**：**長度固定且短的用 `CHAR`**（例如國碼 `CHAR(2)`、MD5 `CHAR(32)`）——它沒有長度前綴、更新時不會因為長度變化而造成頁分裂。**長度變化大的用 `VARCHAR`**。**要注意 `CHAR` 會去除尾部空白**（讀取時），這在某些場景會造成非預期的行為。

`ENUM` 的取捨值得知道。它在儲存上很省（內部是整數），查詢時也快；但新增一個值需要 DDL（8.0 之後在末尾追加是 INSTANT 的，在中間插入則不是），而且它的值與順序耦合（`ORDER BY enum_col` 是按定義順序而非字面值排序，這常常出乎意料）。所以它適合「值的集合非常穩定」的場景（性別、是非），**不適合會變動的業務分類**——那應該用關聯表或一個有明確碼值的欄位。

**JSON 型別的定位要清楚**。MySQL 5.7 之後的原生 JSON 型別支援路徑查詢與部分更新，**而且可以用產生欄位加索引**（`ALTER TABLE ... ADD COLUMN x INT AS (json_col->>'$.x') STORED, ADD INDEX(x)`）。它適合「結構不固定或很少查詢的附加資料」——例如記錄一個事件的原始 payload。不適合的是「經常被查詢與過濾的核心欄位」——那應該是正式的欄位，因為 JSON 的查詢與索引仍然比原生欄位貴，而且失去了 schema 的約束與文件價值。

## 面試回答方式

先給原則「用能正確表達語意的最小型別」與**三層理由**（空間、索引效率、記憶體）。給具體要點，並主動澄清 `INT(11)` 的括號只影響顯示寬度不影響儲存這個普遍的誤解。強調**「盡量 `NOT NULL`」是最重要的一條**。加分點有三個：`VARCHAR` 的長度宣告不影響磁碟但影響記憶體——排序時可能依宣告的最大長度分配，所以「反正不影響磁碟就設大一點」是真實的成本；`ENUM` 的值與順序耦合（`ORDER BY` 是按定義順序），適合非常穩定的集合而不適合會變動的業務分類；以及 JSON 型別適合「結構不固定或很少查詢的附加資料」，不適合核心欄位——因為那**失去了 schema 的約束與文件價值**。

## 講稿

原則是用能正確表達語意的最小型別，理由有三層。空間、索引效率、還有記憶體。索引項越小，一個頁能放的越多、樹越矮、快取命中率越高。

具體的要點是，整數用能容納範圍的最小型別。這裡有一個普遍的誤解，整數型別括號裡的數字只影響顯示寬度，不影響儲存。時間不要用字串存。金額用定點數不要用浮點數。

最重要的一條是盡量不可為空。可為空的欄位需要額外的標記位、讓索引跟查詢的處理更複雜、而且引入三值邏輯的各種陷阱。

有一個細節值得知道。變長字串的長度宣告不影響磁碟儲存，只存實際長度加一個長度前綴。但它影響記憶體，排序跟臨時表在某些情況下會依宣告的最大長度分配空間。所以反正不影響磁碟就設大一點，是一個真實的成本。

列舉型別的取捨也值得提。它儲存很省，但新增值需要變更結構，而且它的值跟順序耦合，排序是按定義順序而不是字面值，這常常出乎意料。所以它適合值的集合非常穩定的場景，不適合會變動的業務分類。

JSON 型別我的定位是，適合結構不固定或很少查詢的附加資料，不適合經常被查詢與過濾的核心欄位。

## 常見追問

### 為什麼金額不能用 FLOAT？

**核心答案**：因為 IEEE 754 浮點數無法精確表示大多數十進位小數——`0.1` 在二進位下是無限循環，只能存近似值。**累加之後誤差會放大**，而金額的計算通常涉及大量的加總與比較。`DECIMAL(m, n)` 用定點的方式儲存（內部是整數加上小數位數的中繼資料），能精確表示指定位數的十進位值。這是正確性問題而非效能問題。

**詳細解析**：另一條同樣正確的路是「用整數存最小單位」——金額以「分」為單位存成 `BIGINT`，計算全部用整數，顯示時再除以 100。**它比 `DECIMAL` 更快也更省空間**（`DECIMAL` 的運算是軟體實作的，比整數慢），適合「單一幣別、精度固定、且不需要複雜比例計算」的系統。需要利率、匯率、分攤這類會產生除不盡結果的計算時，`DECIMAL` 的明確捨入控制更合適。**這個選擇應該是有意識的**——而很多系統的做法是「因為習慣所以用 `DECIMAL`」或「因為省事所以用 `DOUBLE`」，後者是明確的錯誤，前者則只是沒有想過。

**面試回答方式**：給根本原因——IEEE 754 無法精確表示大多數十進位小數，累加後誤差放大，並強調這是**正確性問題而非效能問題**。真正的加分點是提出另一條同樣正確的路：用整數存最小單位（以分為單位存 `BIGINT`），它更快更省空間、適合單一幣別精度固定的系統；而有除不盡計算時 `DECIMAL` 的捨入控制更合適。收在態度：**這個選擇應該是有意識的**，而很多系統只是「因為習慣」或「因為省事」。

### 該用 TIMESTAMP 還是 DATETIME？

**核心答案**：**看是否需要時區轉換**。`TIMESTAMP` 內部存的是 UTC 的秒數，讀寫時依連線的時區設定自動轉換——這讓「同一個時刻對不同時區的使用者顯示不同的本地時間」變得自動。代價是**範圍只到 2038 年**（32 位元的秒數）與**行為依賴連線的時區設定**（設定不一致會讀到不同的值）。`DATETIME` 存的是字面的日期時間，**不做任何轉換**，範圍到 9999 年。

**詳細解析**：現代的主流做法是「用 `DATETIME` 存 UTC，轉換在應用層做」——理由是它讓資料庫的行為完全可預測（不受連線設定影響），而時區轉換本來就是展示層的責任。`TIMESTAMP` 的自動轉換看似方便，但它讓「同一筆資料在不同連線下讀出不同的值」成為可能，那在除錯與資料匯出時是麻煩的來源。2038 年問題也不再遙遠——一個現在寫入「20 年後到期」的合約日期就已經超出範圍。這是一個「便利的自動行為在長期是負擔」的例子：明確而笨拙的做法（存 UTC、明確轉換）比隱含而聰明的做法更容易維護。

**面試回答方式**：給兩者的機制差別（`TIMESTAMP` 存 UTC 秒數並依連線時區自動轉換、`DATETIME` 存字面值不轉換）與各自的限制。真正的加分點是給出現代主流做法：用 `DATETIME` 存 UTC、轉換在應用層做，理由是**資料庫行為完全可預測**，而 `TIMESTAMP` 的自動轉換讓「同一筆資料在不同連線下讀出不同值」成為可能。收在觀點：便利的自動行為在長期是負擔，明確而笨拙比隱含而聰明更容易維護。

### schema 設計時還有哪些容易後悔的決定？

**核心答案**：四個。**用可變的業務值當主鍵**（前面談過，改動代價極高）。**欄位命名不一致**（`user_id` 與 `userId` 與 `uid` 混用，讓 JOIN 與工具處理都變麻煩）。過早地把所有東西正規化到極致（大量的小表與 JOIN，查詢複雜且慢）或**過早反正規化**（同步成本與不一致的風險）。沒有預留擴充空間的列舉或狀態欄位（用 `TINYINT` 存狀態碼但沒有留出未定義的區間）。

**詳細解析**：最難修正的是「命名與結構的不一致」，因為它不會造成任何錯誤，只是持續增加每個人的認知負擔——而正因為它不報錯，永遠沒有一個明確的時機去修。防護方式是在專案早期就訂立並執行 schema 規範：主鍵一律叫 `id`、外鍵一律叫 `<表名>_id`、時間欄位一律 `created_at`／`updated_at`、布林欄位一律 `is_<形容詞>`。這些規則的價值不在於哪一種寫法更好，而在於「一致」本身——一致的 schema 讓工具（ORM、遷移工具、文件生成）能依約定運作，也讓新人能從一張表推測其他表的結構。「約定的價值在於它省下的每一次思考」，而那個節省乘以團隊人數與時間，遠大於制定它的成本。

**面試回答方式**：給四個容易後悔的決定。真正的重點是指出最難修正的是命名與結構的不一致——它不報錯所以永遠沒有明確的時機去修，只是持續增加認知負擔。給出防護（早期訂立並執行 schema 規範）與具體的規則例子。收在原則：規則的價值不在於哪種寫法更好而在於「一致」本身，它讓工具能依約定運作、讓新人能從一張表推測其他表，而「約定省下的每一次思考」乘以團隊人數與時間遠大於制定它的成本。
