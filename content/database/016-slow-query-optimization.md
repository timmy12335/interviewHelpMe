# 題目

線上資料庫出現慢查詢時，你會怎麼排查和優化？請描述完整的流程。

## 核心答案

排查慢查詢的標準流程是：**（1）定位**——開啟並查看 **slow query log**（慢查詢日誌，記錄執行時間超過 `long_query_time` 閾值的 SQL），搭配 `pt-query-digest` 或類似工具，把大量的慢查詢記錄依「相同的 SQL 模式」歸類、統計出現次數和總耗時，找出「影響面最大」的少數幾條 SQL（而非逐一處理每一條）；**（2）分析**——對鎖定的目標 SQL 執行 `EXPLAIN`，檢查是否走了預期的索引、有沒有全表掃描（`type=ALL`）、有沒有 `Using filesort`、`Using temporary` 等警示訊號；**（3）優化**——根據分析結果，對症下藥：補充或調整索引、改寫 SQL（如避免 `SELECT *`、避免在索引欄位上做函式運算、拆分複雜的多表 JOIN）、必要時做分頁優化或引入快取；**（4）驗證**——優化後重新執行 `EXPLAIN` 確認執行計畫改善，並在實際環境觀察慢查詢日誌確認該 SQL 不再出現或耗時明顯下降。

## 詳細解析

**第一步：定位問題 SQL**。開啟 slow query log（設定 `slow_query_log = ON`、`long_query_time` 設定一個合理的閾值，比如 0.5 秒或 1 秒），MySQL 會把執行時間超過閾值的 SQL 連同執行時間、掃描行數等資訊記錄下來。實務上慢查詢日誌往往累積了大量記錄，直接肉眼看效率很低，通常搭配 `pt-query-digest`（Percona Toolkit 的工具）之類的分析工具，把「參數不同但結構相同的 SQL」（比如 `WHERE id = 1` 和 `WHERE id = 2` 視為同一類）自動歸類統計，依「總耗時」或「出現頻率」排序，優先處理影響面最大（而不一定是單次最慢）的那幾類查詢——因為一條「單次耗時 2 秒但一天只跑一次」的 SQL，和一條「單次耗時 0.1 秒但每秒跑 1000 次」的 SQL，後者對系統整體的影響其實更大。

**第二步：用 EXPLAIN 分析執行計畫**。針對鎖定的目標 SQL 執行 `EXPLAIN`（或 `EXPLAIN ANALYZE` 取得實際執行的行數和耗時），重點檢查幾個欄位：`type`（存取類型，`ALL` 代表全表掃描是最需要關注的警訊，理想情況應該是 `ref`、`range`、`const` 等有索引輔助的類型）、`key`（實際用到的索引，如果是 `NULL` 代表沒用上任何索引）、`rows`（預估需要掃描的行數，數字異常大時代表索引選擇性不好或沒有合適索引）、`Extra`（`Using filesort` 代表需要額外排序、`Using temporary` 代表需要建立臨時表，通常出現在複雜的 GROUP BY/ORDER BY/DISTINCT 場景，都是效能瓶頸的常見來源）。

**第三步：針對性優化**。常見的優化手段包括：
- **索引層面**：新增缺少的索引、調整複合索引的欄位順序（讓區分度高、常用作等值查詢的欄位排前面）、避免在索引欄位上使用函式或做隱式類型轉換（會導致索引失效，見 [[005-index-invalidation.md]]）。
- **SQL 改寫**：避免 `SELECT *`（只查需要的欄位，也有助於命中覆蓋索引）、把複雜的巢狀子查詢改寫成 JOIN（有些情況下優化器對子查詢的優化不如 JOIN）、大的 IN 清單考慮拆分或改用臨時表關聯。
- **結構性優化**：對深分頁使用游標分頁或延遲關聯（見 [[015-paging-optimization.md]]）、對高頻查詢引入快取（Redis）減少直接打到資料庫的次數、必要時考慮讀寫分離或分庫分表分散壓力。

**第四步：驗證效果**。優化後，重新用 `EXPLAIN` 確認執行計畫確實改善了（比如 `type` 從 `ALL` 變成 `range`、`rows` 大幅下降、`Extra` 不再顯示 `Using filesort`），並持續觀察慢查詢日誌，確認優化後的 SQL 執行時間穩定下降，同時留意優化措施（尤其是新增索引）有沒有對其他查詢或寫入效能造成負面影響。

## 面試回答方式

按「定位 → 分析 → 優化 → 驗證」四步驟的完整流程來組織回答，展現系統化的排查方法而非零散的技巧堆疊。第一步要提到慢查詢日誌和歸類分析工具（找出影響面最大的 SQL，而非逐條處理）；第二步要具體講出 EXPLAIN 裡要看哪些關鍵欄位（type、key、rows、Extra）及其代表的意義；第三步分索引、SQL 改寫、結構性優化三個層次給出具體手段；第四步強調優化後要驗證效果、留意副作用。這是一道綜合性很強的題目，能完整、有條理地講出這個流程，比單純羅列「加索引、避免 SELECT *」這些零散技巧更能展現實戰經驗。

## 常見追問

### EXPLAIN 顯示的 rows 是實際掃描的行數嗎？和 EXPLAIN ANALYZE 有什麼差別？

**核心答案**：`EXPLAIN` 裡的 `rows` 是優化器根據**統計資訊估算**出來的「預期需要掃描的行數」，並不是真正執行後的實際行數——因為 `EXPLAIN` 本身並不會真正執行這條 SQL，只是生成執行計畫並根據統計資訊做估算，估算值和實際值可能有落差（尤其是統計資訊過時，或資料分佈不均勻時）。`EXPLAIN ANALYZE`（MySQL 8.0.18+ 支援）則會**真正執行這條 SQL**，並回報「實際」的執行時間和實際掃描/回傳的行數，能更準確地反映真實的執行情況，但因為它會真的跑一次查詢，對於本來就很慢或有副作用（如涉及鎖）的 SQL，要謹慎使用（尤其是在生產環境上）。

**詳細解析**：這題釐清 `EXPLAIN` 和 `EXPLAIN ANALYZE` 這兩個相似但本質不同的診斷工具。傳統的 `EXPLAIN` 屬於「靜態分析」——它問優化器「如果要執行這條 SQL，你打算怎麼做（用哪個索引、預計掃描幾行）」，優化器基於表的統計資訊（透過 `ANALYZE TABLE` 收集，包含資料分佈的抽樣估計）做出這個判斷並回報，但整個過程並沒有真的去讀取資料、執行查詢，所以 `rows` 這個數字只是「預估值」。這帶來一個實務上的陷阱——如果統計資訊過時（比如表的資料量或分佈自上次 `ANALYZE TABLE` 以來發生了很大變化），`EXPLAIN` 顯示的預估行數可能和實際情況差很多，導致排查時的誤判（比如以為某個索引選擇性很好，實際上因為統計過時，真實情況並非如此）。`EXPLAIN ANALYZE` 解決了這個問題——它會「真正跑一次查詢」，在執行過程中同步記錄「每個步驟實際掃描/回傳了多少行、花了多少時間」，並在最後把「優化器原本預估的（estimated）」和「實際發生的（actual）」兩者並列展示，讓你可以直接比較「預估和實際的落差有多大」，這個落差本身也是一個很有用的診斷資訊（落差很大，通常暗示統計資訊需要更新，即執行 `ANALYZE TABLE`）。使用上的注意事項是——因為它會真的執行查詢，如果這條 SQL 本身是個高成本或有副作用的操作（比如涉及大量資料的 UPDATE、或可能觸發鎖等待），在生產環境直接跑 `EXPLAIN ANALYZE` 有實際的效能和鎖風險，通常建議先在測試/預發環境驗證，或搭配 `LIMIT`、時間窗口等方式謹慎使用。

**面試回答方式**：清楚點出「EXPLAIN 是靜態分析、基於統計資訊估算、不會真正執行查詢，所以 rows 是預估值」，「EXPLAIN ANALYZE 會真正執行查詢、回報實際的行數和耗時，並列出預估 vs 實際的對比」。補充「預估和實際的落差可以用來判斷統計資訊是否過時（需要 ANALYZE TABLE）」，並提醒「EXPLAIN ANALYZE 因為會真的執行，在生產環境對高成本或有副作用的 SQL 要謹慎使用」。展現你對這兩個工具的本質差異和適用場景有清楚的認識。

### 如果一條 SQL 的 EXPLAIN 顯示用到了索引、rows 也不多，但實際執行還是很慢，可能是什麼原因？

**核心答案**：這種「執行計畫看起來沒問題，但實際很慢」的情況，常見原因包括：**（1）鎖等待**——這條 SQL 本身執行很快，但因為要等待其他交易持有的鎖（行鎖、間隙鎖，或表級別的 metadata lock）而卡住，實際的「等待時間」被算進了總耗時，但 EXPLAIN 完全反映不出鎖等待這件事；**（2）伺服器資源瓶頸**——CPU、記憶體（Buffer Pool 太小導致大量磁碟 I/O）、磁碟 I/O 或網路本身出現瓶頸，導致即使執行計畫合理，實際執行仍然受硬體資源限制而變慢；**（3）統計資訊過時導致 EXPLAIN 的預估失真**（如前題所述，實際掃描的行數遠比 EXPLAIN 顯示的多）；**（4）連線層面的問題**，例如連線池耗盡、DNS 解析慢等和這條 SQL 本身無關的外部因素。

**詳細解析**：這題考察面試者是否能跳出「只看 EXPLAIN」的單一視角，理解慢查詢的成因可能在資料庫執行計畫之外。EXPLAIN 只能告訴你「優化器打算怎麼做、預期效率如何」，但完全不涵蓋「這條 SQL 在真正執行時，有沒有被其他事情卡住」——最典型的就是鎖等待：假設有另一個長交易持有了這張表某些行（甚至因為索引失效導致的間隙鎖鎖住了一大片範圍）的鎖，這條 SQL 即使自己的執行計畫再合理，也必須先排隊等鎖釋放，這段等待時間會完整計入這條 SQL 的總執行時間，讓它看起來「很慢」，但 EXPLAIN 完全看不出這一點（需要用 `SHOW ENGINE INNODB STATUS` 或 `performance_schema` 裡的鎖等待資訊來診斷）。另一個常見盲點是「硬體/系統資源層面的瓶頸」——如果資料庫伺服器本身 CPU 已經跑滿、或者 Buffer Pool 太小導致大量本該命中記憶體快取的資料都要從磁碟讀（產生大量隨機 I/O）、或磁碟本身 I/O 效能不足，這些都會讓「看似合理」的查詢實際執行變慢，這類問題需要搭配作業系統層面的監控（CPU、記憶體、iostat）才能發現，而非只盯著 SQL 本身。回答這題時，展現「排查慢查詢不能只依賴 EXPLAIN，還要有『鎖等待』和『系統資源』這兩個額外的排查方向」的全局思維，是區分初級和資深工程師的常見考點。

**面試回答方式**：先強調「EXPLAIN 只反映執行計畫本身的效率，不反映實際執行中的鎖等待和系統資源瓶頸」，列舉鎖等待（用 `SHOW ENGINE INNODB STATUS` 或 performance_schema 排查）和系統資源瓶頸（CPU/記憶體/磁碟 I/O）這兩個 EXPLAIN 看不到的常見原因。能補充「統計資訊過時導致 EXPLAIN 預估失真」作為第三個角度。展現你排查問題時有多個維度的思考，而非只依賴單一工具。

### 除了事後查慢查詢日誌，有沒有辦法在上線前就主動發現潛在的慢查詢風險？

**核心答案**：常見的事前預防手段包括：**（1）SQL 審核（Code Review 環節加入 SQL 檢查）**——在程式碼合併前，人工或透過自動化工具（如 SQL Lint 工具）檢查新增或修改的 SQL，留意是否有明顯的反模式（如沒有 WHERE 條件的全表查詢、在大表上沒有索引輔助的 JOIN、SELECT * 等）；**（2）在測試/預發環境用接近生產規模的資料量做效能測試**——很多慢查詢問題在開發環境資料量很小時完全不會顯現，只有資料量達到一定規模後才會暴露，所以用真實或模擬的大量資料做壓測，能提前發現這類「資料量增長後才會變慢」的查詢；**（3）資料庫層面設定 SQL 執行時間或掃描行數的告警閾值**，即使還沒到「慢查詢」的門檻，也能提前對「掃描行數異常大」的查詢示警，防患於未然。

**詳細解析**：這題把視角從「事後補救（查日誌）」轉移到「事前預防」，考察對慢查詢治理的完整流程理解。慢查詢日誌的本質是「事後諸葛」——問題已經在生產環境發生、被記錄下來之後才被發現和處理，這種被動的排查模式雖然必要，但如果能在問題影響到使用者之前就攔截下來，顯然是更理想的狀態。SQL 審核是最直接的第一道防線——很多慢查詢的根源，其實在寫程式碼的當下就已經能被有經驗的工程師（或自動化的 lint 規則）識別出來，例如「這個查詢完全沒有 WHERE 條件、卻查了一張可能有百萬筆資料的表」、「這個 JOIN 涉及的表沒有在關聯欄位上建索引」，這類明顯的反模式如果能在 Code Review 階段就被攔下並要求修正，就完全不需要等到它真的在生產環境變慢、才透過慢查詢日誌被動地發現。第二個手段「用接近生產規模的資料量做測試」，是為了彌補「開發/測試環境資料量太小，很多查詢效能問題被資料量小這個假象掩蓋」的常見陷阱——一個沒有索引的查詢，在只有幾百筆測試資料的情況下可能瞬間執行完畢，完全看不出問題，但同樣的查詢邏輯，一旦線上資料量成長到百萬甚至千萬筆，效能就會急劇惡化，如果能在上線前，用貼近真實規模的資料集做效能驗證（例如定期把生產環境資料的脫敏副本同步到預發環境），就能提前捕捉到這類「資料量相關」的效能地雷。第三個手段是把「監控告警」的門檻前移——不只是在 SQL 真正變慢（超過 `long_query_time`）之後才記錄，而是主動監控「掃描行數異常大」這類即使當下執行時間還可接受、但已經顯露出「效率不佳、未來資料量再成長就會變慢」跡象的查詢，提前介入優化。

**面試回答方式**：給出三個事前預防手段——「SQL 審核，在 Code Review 階段用人工或自動化工具攔截明顯的反模式（無 WHERE 的全表查詢、無索引 JOIN 等）」、「用接近生產規模的資料量做效能測試，避免開發環境資料量小掩蓋了真實的效能問題」、「監控告警門檻前移，即使還沒到慢查詢標準,也對掃描行數異常大的查詢提前示警」。用「從事後補救轉向事前預防」這個框架總結，展現你對慢查詢治理有完整、系統化的流程思維，而不只是「查日誌、下 EXPLAIN」這種被動反應。
