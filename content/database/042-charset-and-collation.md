# 題目

MySQL 的 `utf8` 與 `utf8mb4` 差在哪？定序（collation）會影響什麼？

## 核心答案

MySQL 的 `utf8` 是一個歷史遺留的錯誤命名——它最多只支援 3 位元組的字元，無法儲存需要 4 位元組的字元（表情符號、部分中日韓罕用字、以及一些數學符號）。`utf8mb4` 才是真正完整的 UTF-8。插入 4 位元組字元到 `utf8` 欄位的後果依 SQL 模式而定：嚴格模式下報錯，非嚴格模式下**靜默截斷**——後者會造成資料損壞且沒有任何提示。

**MySQL 8 已經把 `utf8mb4` 設為預設**，而 `utf8` 成為 `utf8mb3` 的別名並被標記為棄用。**新專案沒有理由用 `utf8`。**

定序決定了「字串怎麼比較與排序」。`utf8mb4_general_ci` 是舊的、快但不完全正確的實作；`utf8mb4_unicode_ci` 遵循 Unicode 的排序規則；`utf8mb4_0900_ai_ci`（MySQL 8 的預設）基於 Unicode 9.0，是現在的正確選擇。後綴的含義是：`ci` 不區分大小寫、`cs` 區分、`bin` 按二進位比較、`ai` 不區分重音、`as` 區分。

定序影響的不只是 `ORDER BY`，還有 `WHERE` 的相等比較與唯一索引的判定——`ci` 定序下，`'ABC'` 與 `'abc'` 被視為相同，**這可能不是你要的**。

## 詳細解析

「唯一索引在 `ci` 定序下的行為」是一個真實會出事的地方。使用者名稱欄位用 `ci` 定序加唯一索引時，`'John'` 與 `'john'` 無法同時存在——**這通常正是想要的**（避免混淆的帳號名）。但如果那是一個區分大小寫的識別碼（例如 base64 編碼的 token、或者區分大小寫的外部系統 ID），`ci` 定序會錯誤地認為兩個不同的值重複。這類欄位應該明確使用 `bin` 或 `_as_cs` 定序。

**定序不一致會讓索引失效**。JOIN 兩張表的字串欄位時，如果它們的定序不同，MySQL 必須做隱式轉換，而那會讓索引無法使用——症狀是「明明兩邊都有索引但 JOIN 極慢」。這在「舊表用 `utf8_general_ci`、新表用 `utf8mb4_0900_ai_ci`」的混合環境中很常見。排查的方式是 `SHOW CREATE TABLE` 比對兩邊的定序，而預防的方式是在資料庫層級統一設定並確保所有新表繼承它。

**字元集的設定有四個層級**：伺服器、資料庫、表、欄位——**下層繼承上層，但可以覆寫**。還有一個容易被忽略的第五層：連線（`character_set_client`／`connection`／`results`）。連線的字元集設錯會造成亂碼，而且症狀很迷惑——資料在資料庫裡是正確的，只是傳輸過程中被錯誤地解讀。JDBC 的連線字串應該明確指定 `characterEncoding=utf8`（或依驅動版本使用對應的參數），不要依賴預設。

從 `utf8` 遷移到 `utf8mb4` 有一個索引長度的問題。InnoDB 的索引鍵前綴有長度上限（舊版本是 767 位元組），而 `utf8mb4` 的每個字元最多 4 位元組——所以 `VARCHAR(255)` 的索引需要 1020 位元組，超過了限制。MySQL 5.7 之後預設啟用 `DYNAMIC` 列格式讓上限提升到 3072 位元組，問題基本消失；但在舊版本或舊表格式上遷移時仍會遇到，處理方式是縮短欄位長度、只索引前綴、或者升級列格式。

## 面試回答方式

先給最重要的事實——MySQL 的 `utf8` 是歷史遺留的錯誤命名，只支援 3 位元組，無法存表情符號等 4 位元組字元，而非嚴格模式下會靜默截斷造成資料損壞。指出 MySQL 8 已把 `utf8mb4` 設為預設。接著給定序的作用與後綴的含義，並強調它影響的不只是排序，還有相等比較與唯一索引的判定。加分點有三個：`ci` 定序下唯一索引會把大小寫不同的值視為重複，區分大小寫的識別碼應該用 `bin` 或 `_as_cs`；**定序不一致會讓 JOIN 的索引失效**，症狀是「兩邊都有索引但 JOIN 極慢」，這在新舊表混合的環境中很常見；以及連線的字元集是容易被忽略的第五層，設錯造成的亂碼很迷惑——資料在庫裡是對的，只是傳輸時被錯誤解讀。

## 講稿

MySQL 的 utf8 是一個歷史遺留的錯誤命名，它最多只支援三位元組的字元，無法儲存表情符號這類需要四位元組的字元。而且在非嚴格模式下會靜默截斷，造成資料損壞且沒有任何提示。utf8mb4 才是真正完整的 UTF-8，MySQL 8 已經把它設為預設。

定序決定了字串怎麼比較與排序。後綴的含義是不區分大小寫、區分、按二進位比較、不區分重音這些。

我想強調，定序影響的不只是排序，還有相等比較跟唯一索引的判定。不區分大小寫的定序下，大寫的 ABC 跟小寫的 abc 被視為相同。使用者名稱這樣通常是對的，但如果是一個區分大小寫的識別碼，比如 base64 的 token，那就會錯誤地認為兩個不同的值重複。那類欄位應該明確用二進位或區分大小寫的定序。

還有一個很實際的坑。JOIN 兩張表的字串欄位時，如果它們的定序不同，MySQL 必須做隱式轉換，而那會讓索引無法使用。症狀是明明兩邊都有索引但 JOIN 極慢。這在舊表跟新表用不同定序的混合環境中很常見。

最後，連線的字元集是容易被忽略的一層，設錯造成的亂碼很迷惑，因為資料在庫裡其實是正確的。

## 常見追問

### 已經用了 utf8 的表要怎麼遷移？

**核心答案**：用 `ALTER TABLE ... CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci`——它會轉換所有字串欄位並重寫資料。這是一個**重建表的操作**，在大表上應該用 gh-ost 這類工具執行。**遷移前要檢查三件事**：索引長度是否超限（舊列格式下 `VARCHAR(255)` 的完整索引會超過 767 位元組）、應用的連線字元集是否也已更新、以及**是否有依賴 `ci` 定序行為的邏輯**（定序從 `utf8_general_ci` 換到 `utf8mb4_0900_ai_ci` 時，某些字元的排序與相等判定會改變）。

**詳細解析**：第三點最容易被忽略且後果最隱蔽。`utf8mb4_0900_ai_ci` 遵循更新的 Unicode 規則，某些原本被視為不同的字元變成相同（或反之）——這可能讓唯一索引在遷移時衝突（發現了原本不算重複的重複），或者讓某些查詢的結果改變。遷移前應該在測試環境用真實資料跑一次轉換，看有沒有唯一約束衝突。 更一般地說，任何改變「相等」定義的變更都需要檢查唯一約束——這包含定序變更、大小寫規則變更、以及去除空白規則的變更。「相等的定義變了」是一類容易被低估的破壞性變更，因為它不改變 schema 的形狀，只改變語意。

**面試回答方式**：給遷移指令並指出它是**重建表的操作**，大表要用線上變更工具。給三個遷移前的檢查點。真正的加分點是展開**第三點最隱蔽**——新定序遵循更新的 Unicode 規則，某些字元的相等判定改變，可能讓唯一索引在遷移時衝突或讓查詢結果改變，所以要在測試環境用真實資料跑一次。收在一般化：任何改變「相等」定義的變更都需要檢查唯一約束，而那是一類容易被低估的破壞性變更——**它不改變 schema 的形狀，只改變語意**。

### 為什麼有些系統選 bin 定序？

**核心答案**：因為它**行為最簡單且最可預測**——按位元組比較，沒有任何語言相關的規則。三個典型的理由：**需要區分大小寫**（識別碼、token、路徑）、避免定序規則變更帶來的意外（Unicode 版本升級可能改變比較結果）、以及**效能**（位元組比較比 Unicode 的排序規則快）。

**詳細解析**：代價是排序結果不符合人的直覺——`bin` 定序下，大寫字母全部排在小寫之前（因為 ASCII 的 `'Z'` 小於 `'a'`），而非英文字元的排序完全依碼點順序，與任何語言的字典序都不一致。所以它適合「機器讀的識別碼」而不適合「給人看的名稱」。 實務上的做法是依欄位的用途分別選擇：識別碼類的欄位用 `bin`、面向使用者的名稱用 `_ai_ci`。「同一張表的不同欄位可以有不同的定序」這件事常被忽略——很多人以為定序是表層級的統一設定，實際上它可以精確到欄位，而那正是正確的做法。

**面試回答方式**：給三個選 `bin` 的理由（需要區分大小寫、避免規則變更的意外、效能）。誠實給出代價：**排序不符人的直覺**（大寫全排在小寫前、非英文依碼點順序），所以適合機器讀的識別碼而非給人看的名稱。真正的加分點是指出同一張表的不同欄位可以有不同的定序——很多人以為它是表層級的統一設定，實際上可以精確到欄位，而那正是正確的做法。

### 排序的結果為什麼在不同環境不一致？

**核心答案**：**因為定序不同**。同一組資料在 `utf8mb4_general_ci` 與 `utf8mb4_0900_ai_ci` 下的排序可能不同（尤其是非英文字元與特殊符號）；而如果應用在拿到資料後又在程式碼裡排序一次，那又是另一套規則（Java 的 `String.compareTo` 是按碼點、`Collator` 則依語系）。症狀是「資料庫排出來的順序與前端顯示的不一樣」或「開發環境與生產環境的順序不同」。

**詳細解析**：根本的處理原則是「排序只在一個地方做」——要嘛全部在資料庫（那就統一定序），要嘛全部在應用層（那資料庫的順序就不重要）。**混合兩者是問題的來源**。而如果排序的結果會被使用者看到並且需要跨環境一致（例如分頁的游標依賴排序），那麼定序必須被明確指定並記錄成 schema 的一部分——不要依賴伺服器或資料庫的預設，因為那可能在遷移或升級時改變。這是一個「隱含依賴造成環境差異」的典型案例：程式碼裡沒有任何地方寫著「依賴這個定序」，但行為確實依賴它，於是換一個環境就出錯而沒有人知道為什麼。

**面試回答方式**：給原因（定序不同、以及應用層又排一次是另一套規則）與典型症狀。真正的重點是原則：**排序只在一個地方做**，混合兩者是問題來源。加分點是指出如果排序結果會被看到且需要跨環境一致，定序必須明確指定並記錄成 schema 的一部分，不要依賴預設。收在觀點：這是「隱含依賴造成環境差異」的典型案例——程式碼裡沒寫著依賴它但行為確實依賴，換環境就出錯而沒人知道為什麼。
