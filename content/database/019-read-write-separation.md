# 題目

讀寫分離架構下，「寫入主庫後立刻讀取，卻讀不到剛寫入的資料」這個問題是怎麼發生的？有哪些解決方案？

## 核心答案

這個問題發生的原因是 MySQL 主從複製通常是**非同步**的——寫入操作在主庫上完成、提交成功之後，是透過非同步的方式（binlog 傳輸 + 從庫重放）把變更同步到從庫的，這個同步過程需要時間（即「主從延遲」）。如果應用程式的架構是「寫入走主庫、讀取走從庫」，剛寫入完成後（可能只過了幾毫秒到幾百毫秒）立刻去讀從庫，這時候從庫可能還沒完成這次變更的同步重放，讀到的仍然是舊資料，造成「明明剛寫入卻讀不到」的體驗問題。常見解決方案包括：**（1）強制讀主庫**——對「剛寫入、需要立即讀取確認」的這類操作，直接指定走主庫查詢，跳過從庫；**（2）延遲讀取**——在寫入後，讓讀取請求延遲一小段時間（大於預期的主從延遲）再去讀從庫；**（3）根據業務容忍度分流**——只有「強一致性要求」的讀取（如使用者自己剛提交的操作結果）走主庫，其他不那麼敏感的讀取仍走從庫；**（4）使用支援讀寫延遲感知的中介軟體**，自動判斷是否需要路由到主庫。

## 詳細解析

**問題的本質**：讀寫分離的目的是把「讀取流量」分散到多個從庫，減輕主庫的壓力（因為多數應用場景「讀多寫少」）。但這個架構的前提是「主從複製存在延遲」——延遲可能只有幾毫秒（正常情況下），但在網路波動、從庫負載高、或主庫寫入量突然暴增等情況下，延遲可能拉長到幾秒甚至更久。這種「最終一致（Eventually Consistent）」的模型，對大多數「讀別人寫的資料」場景沒有太大影響（使用者通常不會在意「別人剛發的貼文，我晚個幾百毫秒才看到」），但對「自己剛寫入、立刻要看到自己寫入結果」的場景（如使用者提交表單後，頁面立刻跳轉到「顯示剛提交的資料」的頁面），如果這次讀取剛好落在還沒同步到最新資料的從庫上，就會出現「我剛提交的東西，怎麼系統顯示沒有」的困惑體驗，這種場景在技術上稱為需要「讀寫一致性（Read-Your-Writes Consistency）」。

**解決方案一：強制讀主庫**：這是最直接、最保險的做法——在應用程式的路由邏輯裡，對「使用者剛完成寫入、緊接著需要讀取確認」這類特定的請求（例如「提交訂單後導向訂單詳情頁」），直接指定走主庫查詢，完全繞過從庫，也就不存在延遲不一致的問題。缺點是這部分讀取流量沒有被分擔到從庫，如果這類「寫後立即讀」的場景本身佔比很高，主庫的負擔仍然吃重，讀寫分離的效果打折扣。

**解決方案二：延遲讀取（Sleep 一小段時間）**：在寫入完成後，讓後續的讀取請求「刻意等待」一小段時間（比如 100-500 毫秒，依實際觀測到的主從延遲設定）再去讀從庫，賭「這段等待時間足夠讓從庫完成同步」。這個方法簡單粗暴，但不夠可靠——如果實際的主從延遲超過了設定的等待時間（比如從庫突然變慢），還是會讀到舊資料；而且「無論實際延遲多少，一律等待固定時間」也會拖慢正常情況下的回應速度，不是一個精細的解法。

**解決方案三：業務層面分流，區分一致性要求**：根據業務場景的實際需求，精細地決定「哪些讀取必須是強一致（走主庫）、哪些可以容忍最終一致（可以走從庫）」——例如電商場景，「使用者查看自己剛提交的訂單詳情」需要強一致（走主庫），但「瀏覽商品列表、查看他人評論」這類場景可以容忍些微延遲（走從庫）。這種方案需要在應用架構設計時，明確劃分不同讀取路徑的一致性需求，是相對精細但也最考驗架構設計能力的做法。

**解決方案四：路由中介軟體的延遲感知**：一些更成熟的資料庫代理層方案（如某些分庫分表中介軟體），會主動監測每個從庫「目前同步到主庫的哪個 binlog 位置（或 GTID）」，寫入操作完成後記錄「這次寫入對應的 binlog 位置」，後續讀取請求時，中介軟體會檢查「候選的從庫是否已經同步到（或超過）這個位置」，只有確認同步完成的從庫才會被選為這次讀取的目標，否則路由到主庫或等待。這是相對自動化、精確的解法，但需要中介軟體本身支援這個機制，實作複雜度較高。

## 面試回答方式

先講清楚問題的根源——主從複製是非同步的，存在「主從延遲」，讀寫分離架構下，寫後立即讀從庫可能讀到舊資料，這種一致性模型叫「最終一致性」，具體到這個場景叫「讀寫一致性（Read-Your-Writes）」需求沒被滿足。接著給出至少 2-3 種解決方案，並說明各自的權衡（強制讀主庫最簡單但犧牲讀寫分離的效果、延遲讀取不夠可靠、業務分流最精細但需要架構設計投入、中介軟體自動路由最先進但實作複雜）。展現你不只知道「有這個問題」，還能針對不同場景給出合適的解法選擇。

## 常見追問

### 「讀寫一致性（Read-Your-Writes）」和資料庫交易的「隔離性（Isolation）」是同一回事嗎？

**核心答案**：不是同一回事，兩者處理的是完全不同層次的一致性問題。**交易隔離性**處理的是「同一個資料庫實例內，多個並行交易之間互相看到彼此中間狀態的問題」（如髒讀、不可重複讀、幻讀，見 [[008-transaction-isolation.md]]），是單機、同步的問題。**讀寫一致性（Read-Your-Writes）**處理的是「分散式系統中（比如主從複製的多個節點），使用者自己剛完成的一次寫入，在後續的讀取請求中，能不能保證看到這次寫入的結果」，這是分散式系統的「複製一致性」範疇，和單機交易隔離級別完全是兩個不同維度的概念，即使把主庫本身的隔離級別設到最高的 `SERIALIZABLE`，也完全不能解決「讀從庫讀不到剛寫入主庫的資料」這個問題。

**詳細解析**：這題容易讓面試者混淆兩個都叫「一致性」但完全不同層次的概念，能清楚區分展現紮實的理論基礎。交易隔離性討論的場景，是「同一個資料庫伺服器上，同時有多個交易在跑，交易 A 看不看得到交易 B 還沒提交（或剛提交）的變更」，這完全發生在單一資料庫實例內部，由資料庫的鎖機制和 MVCC 機制保證（見 [[009-mvcc.md]]），和「這個資料庫實例的資料，有沒有同步到另外一台伺服器（從庫）」完全無關。讀寫一致性討論的場景，是「資料已經在主庫上正確地、按照交易隔離的規則提交完成了，但這個已經提交的資料，透過非同步複製傳播到其他節點（從庫）需要時間，在這段傳播的時間差裡，如果你去讀從庫，讀到的是『從庫尚未跟上的舊狀態』」，這是一個發生在「多個資料庫實例之間」的問題，屬於分散式系統理論裡「複製一致性模型」的範疇（讀寫一致性只是其中一種具體的一致性保證，其他還有單調讀一致性、因果一致性等）。這兩個問題是完全正交的——你可以有一個隔離級別很嚴格（SERIALIZABLE）但主從延遲很嚴重的系統（交易隔離做得很好，但讀寫一致性很差），也可以有一個隔離級別較寬鬆（READ COMMITTED）但因為沒有讀寫分離、所有讀寫都在同一個節點上，完全不存在讀寫一致性問題的系統。回答這題的關鍵是清楚地指出「兩者的作用範圍不同——一個是單機內的並行交易可見性問題，一個是多機之間的複製延遲問題」，避免把兩個概念混為一談。

**面試回答方式**：明確區分——「交易隔離性是單一資料庫實例內、多個並行交易之間的可見性問題（髒讀/不可重複讀/幻讀），由鎖和 MVCC 保證」；「讀寫一致性是分散式系統裡、多個資料庫節點之間的複製延遲問題，屬於分散式一致性模型的範疇」。強調「兩者完全正交，提高隔離級別完全無法解決主從延遲導致的讀寫不一致問題」。展現你能清楚區分這兩個容易混淆但本質不同的一致性概念。

### 如果從庫延遲一直很嚴重（比如持續好幾秒），除了應用層的應對方案，資料庫或架構層面可以怎麼優化？

**核心答案**：資料庫/架構層面的優化方向包括：**（1）從庫使用平行複製（Parallel Replication）**——MySQL 5.7+ 支援從庫用多個執行緒並行地重放 binlog（而非傳統單執行緒依序重放），大幅提升從庫追趕主庫的速度；**（2）優化網路和硬體**——確保主從之間的網路頻寬充足、從庫的硬體規格（尤其是磁碟 I/O 能力）不低於主庫，避免從庫成為效能瓶頸；**（3）減少主庫的寫入壓力**——如果主庫寫入量本身就非常大（導致 binlog 產生速度快、從庫追趕不上），考慮透過分庫分表分散寫入壓力，從根本上降低單一主庫的 binlog 產生速率；**（4）監控與告警**——建立主從延遲的即時監控（如透過 `SHOW SLAVE STATUS` 的 `Seconds_Behind_Master`），一旦延遲超過閾值就告警，讓維運能及時介入排查根因（如某個從庫硬體異常、或某條大交易阻塞了複製）。

**詳細解析**：這題把視角從「應用層怎麼繞過延遲問題」轉移到「怎麼從根本上減少延遲本身」，考察對主從複製效能優化的系統性理解。傳統 MySQL 複製中，從庫的 SQL 執行緒是「單執行緒」依序重放主庫傳來的 binlog 事件——這意味著即使從庫的硬體資源（CPU、I/O）很充裕，重放的速度也受限於單執行緒的處理能力，如果主庫的寫入是多執行緒並行完成的（吞吐量很高），單執行緒的從庫很容易追趕不上，延遲越積越多。MySQL 5.7 引入的平行複製（基於「同一個交易群組提交」的資訊，判斷哪些交易之間沒有依賴關係、可以安全地並行重放）大幅改善了這個瓶頸，讓從庫也能用多執行緒重放，追趕速度顯著提升，這是解決「持續性延遲」的一個關鍵資料庫層面優化。網路和硬體層面的優化也很直觀——如果從庫的磁碟 I/O 效能明顯低於主庫（比如從庫用了較便宜的儲存），即使複製協定本身沒問題，從庫寫入重放資料的速度也會被硬體拖累，確保從庫硬體規格對等（甚至更好，因為從庫除了重放寫入還要應付讀取查詢的負載）是基本要求。如果延遲的根因是「主庫寫入壓力太大」（binlog 產生速度太快，任何從庫的重放速度都追不上），單純優化從庫這一側是治標不治本的，需要考慮從根源減少主庫的寫入壓力，比如透過分庫分表把寫入流量分散到多個獨立的主庫，或是評估是否有不必要的高頻寫入可以透過批次合併、非同步佇列削峰等方式緩解。最後，建立完善的監控（`Seconds_Behind_Master` 或基於 GTID 的更精確延遲指標）是所有優化措施的前提——沒有監控，維運甚至不知道延遲已經惡化到需要處理的程度，也無從判斷優化措施是否真的有效。

**面試回答方式**：從「治標」到「治本」分層次回答——先講從庫平行複製（MySQL 5.7+，多執行緒重放提升追趕速度）這個直接針對複製瓶頸的優化；再講網路/硬體對等（避免從庫成為效能瓶頸）；如果根因是主庫寫入壓力過大，講到分庫分表分散寫入壓力這個更根本的解法；最後強調監控告警（`Seconds_Behind_Master`）是能及時發現和處理延遲問題的前提。展現你能從「應用層繞過」延伸到「資料庫架構層面根本優化」的完整思考層次。

### 除了「讀寫一致性（Read-Your-Writes）」，還有哪些常見的分散式一致性模型？它們之間的強弱關係是什麼？

**核心答案**：常見的分散式一致性模型（由強到弱）包括：**強一致性（Strict/Linearizability）**——任何時刻、任何節點讀取，都能立即看到最新的寫入結果，如同系統裡只有一份資料一樣；**順序一致性 / 因果一致性（Causal Consistency）**——保證「有因果關係的操作」的順序被所有節點一致地觀察到（例如你看到某則留言的回覆，一定不會比看到原留言本身更早）；**讀寫一致性（Read-Your-Writes）**——只保證「使用者自己剛完成的寫入，自己後續一定讀得到」，但不保證能立即看到「別人」的寫入；**單調讀一致性（Monotonic Reads）**——保證「同一個使用者」連續讀取時，不會發生「這次讀到的資料，比上次讀到的還要舊」（也就是讀取結果不會時光倒流）；**最終一致性（Eventual Consistency）**——只保證「如果沒有新的寫入，經過足夠長的時間後，所有節點最終會收斂到相同的資料狀態」，是最弱的一致性保證。這些模型之間，前面提到的通常比後面的保證更強（實現成本也更高）。

**詳細解析**：這題把「讀寫一致性」放進更完整的分散式一致性模型光譜裡，考察是否對這個領域有更系統性的知識框架，而不只是孤立地知道一個名詞。強一致性（Linearizability）是最嚴格的保證，效果上要求整個分散式系統「表現得就像只有一台機器、一份資料」，任何寫入一旦完成，之後任何節點的任何讀取都必須立即反映這個變化，這種保證的實現成本非常高（往往需要類似 Paxos/Raft 這樣的共識演算法，或犧牲可用性來換取），在讀寫分離、跨地域部署這類天生就有網路延遲和資料副本的架構下，幾乎不可能低成本地達成。因果一致性是一個相對務實的折衷——它不要求「所有操作都有全域一致的順序」，只要求「有因果依賴關係的操作」順序被保持（例如社群媒體場景，你不會在還沒看到別人的原始貼文之前，就先看到別人對這則貼文的回覆，因為「回覆」在因果上依賴於「原始貼文」），這類保證的實現成本比完全的強一致性低很多，卻能滿足很多實際場景「邏輯順序不能顛倒」的核心需求。讀寫一致性和單調讀一致性都是「以單一使用者的視角」出發的保證，兩者的差別是——讀寫一致性關注的是「我自己寫的東西，我自己要看得到」；單調讀一致性關注的是「我自己連續讀取的過程中，不會發生倒退」（比如第一次讀取剛好命中了一個同步較快的從庫、看到了最新資料，但第二次讀取剛好命中另一個同步較慢的從庫、反而看到了更舊的資料，這種「時光倒流」的體驗即使不涉及「自己剛寫的東西」，也會讓使用者感到困惑，單調讀一致性就是為了避免這種情況）。最終一致性是最寬鬆的保證，只承諾「總有一天會一致」，不對「多久之後」做任何具體保證，適合對即時性完全沒有要求、只在意最終資料正確性的場景。理解這個完整的一致性光譜，並能講出「保證越強、實現成本和對可用性/效能的犧牲通常越大」這個核心的權衡關係，展現你對分散式系統理論有結構性的認識，而非只記得幾個孤立的名詞。

**面試回答方式**：按「強到弱」列出一致性模型光譜——強一致性（任何時刻任何節點都看到最新結果，成本最高）、因果一致性（保證有因果關係的操作順序不顛倒）、讀寫一致性（自己寫的自己要讀得到）、單調讀一致性（自己連續讀取不會倒退）、最終一致性（只保證最終會收斂，最寬鬆）。強調「這是一個光譜，越強的保證通常需要越高的實現成本、可能犧牲可用性或效能，讀寫分離架構本質上提供的是弱於強一致性的保證」。展現你有完整的分散式一致性理論框架，而非只孤立地知道「讀寫一致性」這一個概念。
