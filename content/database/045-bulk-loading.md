# 題目

要匯入一億筆資料，怎麼做最快？批次寫入有哪些優化手段？

## 核心答案

**單筆 `INSERT` 的成本主要不在寫入本身，而在每一次的往返、解析、與交易提交**。所以優化的方向是**批次化**：把一千筆合併成一個 `INSERT ... VALUES (...), (...), ...`，**往返從一千次降到一次、交易提交從一千次降到一次**——通常能快十倍以上。

**更快的是 `LOAD DATA INFILE`**——它跳過了 SQL 解析，直接從檔案讀取並批次寫入，**通常比批次 `INSERT` 再快數倍**。這是大量匯入的標準工具。

其他有效的手段：**匯入前刪除二級索引、匯入後重建**（避免每筆插入都維護所有索引；重建索引是批次排序後一次建立，快得多）、**依主鍵順序匯入**（讓聚簇索引的插入是順序的、避免頁分裂）、**調大 `bulk_insert_buffer_size` 與 redo log**、以及**暫時關閉唯一性檢查與外鍵檢查**（`SET unique_checks=0, foreign_key_checks=0`——**但只有在資料確定乾淨時才安全**）。

**分批提交而非一個大交易**——每一萬到十萬筆提交一次，避免長交易的所有問題。

## 詳細解析

**「刪除索引再重建」的收益需要正確理解**。逐筆插入時，每一筆都要在每個二級索引裡找到位置並插入——**那是隨機的 B+ 樹操作**。而重建索引是**掃描全表、排序、再依序建立**——後者可以充分利用順序 IO 與批次排序。**收益隨索引數量與資料量成正比**，在有五六個索引的大表上可能是數倍的差別。**但要注意重建期間表是不可用的**（除非用線上 DDL），**所以這個手法適合初次匯入或可以停機的場景**，不適合線上的持續寫入。

**依主鍵順序匯入的重要性常被低估**。隨機順序的插入會讓 B+ 樹不斷分裂與重組，**產生大量碎片並讓最終的表體積可能大 30% 以上**；而順序插入則是持續在最右端追加，**幾乎沒有分裂**。**如果來源資料無序，先排序再匯入通常是划算的**——排序的成本（尤其是外部排序）遠低於隨機插入造成的損失。**這與「主鍵應該用有序值」是同一個道理的兩個面向。**

**「關閉唯一性檢查」的風險必須明確**。`unique_checks=0` 讓 InnoDB **不檢查唯一索引的重複**——如果資料真的有重複，**索引會處於不一致的狀態且不會報錯**，之後的查詢可能得到錯誤的結果。**所以它只能用在「資料來源已經保證唯一」的情況**，而且應該在匯入後執行一次一致性檢查。**這是一個典型的「用安全性換效能」的選項，而它的失敗模式是靜默的**——這讓它比大多數效能選項都危險。

**線上的持續批次寫入需要不同的策略**。無法刪除索引、無法關閉檢查、也不能長時間佔用資源。**此時的重點是「控制節奏」**：分批（每批一千到一萬筆）、批次之間有短暫間隔（讓其他交易取得鎖、讓複製追上）、以及**監控複製延遲並在超過閾值時自動減速**。**一個跑得太快太滿的批次作業是線上事故的常見來源**，而「主動讓出」的設計讓它從「與線上競爭」變成「利用空隙執行」。

## 面試回答方式

先給批次化的**根本理由**——單筆插入的成本主要在往返、解析、與交易提交，批次把這三者都降下來。給 **`LOAD DATA INFILE` 是最快的**（跳過 SQL 解析）。列出其他手段並對「關閉唯一性檢查」加上明確的警告。加分點有三個：**「刪除索引再重建」的收益來自「隨機 B+ 樹操作」變成「批次排序後依序建立」**，但**重建期間表不可用**，所以適合初次匯入而非線上寫入；**依主鍵順序匯入**能避免分裂與碎片，**最終表體積可能差 30% 以上**，來源無序時先排序通常划算；以及**線上的持續批次寫入需要完全不同的策略**——重點是控制節奏、批次之間留間隔、監控複製延遲並自動減速，**因為跑得太快太滿的批次作業是線上事故的常見來源**。

## 講稿

單筆插入的成本主要不在寫入本身，而在每一次的往返、解析、跟交易提交。所以優化的方向是批次化，把一千筆合併成一個語句，往返跟提交都從一千次降到一次，通常能快十倍以上。

更快的是從檔案批次載入，它跳過了 SQL 解析，通常比批次插入再快數倍，是大量匯入的標準工具。

其他手段有匯入前刪除二級索引、匯入後重建。因為逐筆插入時每一筆都要在每個索引裡做隨機的樹操作，而重建索引是掃描、排序、再依序建立，可以充分利用順序 IO。但重建期間表是不可用的，所以這適合初次匯入或可以停機的場景。

還有依主鍵順序匯入。隨機順序會讓樹不斷分裂重組，產生碎片，最終的表體積可能大三成以上。來源資料無序的話，先排序再匯入通常是划算的。

關閉唯一性檢查這個選項我要特別警告。如果資料真的有重複，索引會處於不一致的狀態而且不會報錯，之後的查詢可能得到錯誤結果。它的失敗模式是靜默的，這讓它比大多數效能選項都危險。

線上的持續批次寫入則需要完全不同的策略，重點是控制節奏，分批、批次之間留間隔、監控複製延遲並自動減速。

## 常見追問

### 批次的大小該怎麼選？

**核心答案**：**實測，但有明確的權衡邊界**。太小則每批的固定成本（往返、交易提交、日誌刷新）佔比過高；太大則單次交易變長（鎖持有久、undo 累積、複製延遲跳高），而且**可能撞到 `max_allowed_packet` 的上限**。**經驗上一千到一萬筆是常見的起點**，但應該依列寬調整——**每批的位元組數比筆數更有意義**，通常控制在幾 MB 以內。

**詳細解析**：**「批次大小」的收益曲線是快速遞減的**：從 1 筆到 100 筆可能快十倍，從 100 到 1000 再快兩倍，從 1000 到 10000 可能只快 10%——**而風險（交易時長、鎖範圍、記憶體）是線性上升的**。**所以最佳點通常在收益曲線變平的地方，而不是「越大越好」。** **實測時應該同時量測三個指標**：總吞吐、單批的耗時分布（P99）、以及對線上查詢的影響。**只看總吞吐會選出一個對線上傷害很大的設定**——這是批次作業調優中最常見的錯誤，**因為批次作業的成功標準往往被定義成「多久跑完」，而忽略了「跑的期間對其他人的影響」**。

**面試回答方式**：給權衡的兩端與起點範圍，並指出**每批的位元組數比筆數更有意義**。真正的加分點是描述**收益曲線快速遞減而風險線性上升**——所以最佳點在曲線變平處而非越大越好。收在調優建議：**同時量測總吞吐、單批耗時分布、以及對線上查詢的影響**，並指出**只看總吞吐會選出對線上傷害很大的設定**——這是最常見的錯誤，因為批次作業的成功標準常被定義成「多久跑完」而忽略了期間對其他人的影響。

### 匯入失敗要怎麼恢復？

**核心答案**：**設計成可重跑的**。三個要素：**記錄進度**（處理到哪一批、哪個主鍵，存在一張進度表或檔案裡）、**冪等**（重跑已處理的部分不會產生錯誤結果，用 `INSERT ... ON DUPLICATE KEY UPDATE` 或先刪除該範圍再插入）、以及**分批提交**（讓已完成的部分不必回滾）。**「一次性的大交易」在失敗時只能全部重來，而那在一億筆的規模上是不可接受的。**

**詳細解析**：**冪等的實作方式取決於資料的性質**。有自然唯一鍵的資料用 `ON DUPLICATE KEY UPDATE` 或 `REPLACE`（**注意 `REPLACE` 是「刪除再插入」，會改變自增 ID 並觸發外鍵的級聯**，語意與 `ON DUPLICATE KEY UPDATE` 不同）。沒有自然唯一鍵的則需要**在匯入前先刪除該批次的範圍**（例如依 `import_batch_id` 標記）。**「先刪除再插入」的做法讓每一批都是原子且冪等的**，代價是多一次刪除操作。**這個「用批次標記讓重跑安全」的模式在所有 ETL 與資料同步中都適用**，而它的關鍵是**在寫入時就記錄「這批資料是哪一次匯入產生的」**——沒有這個標記，事後就無法安全地重跑。

**面試回答方式**：給三個要素（記錄進度、冪等、分批提交）並指出**一次性大交易在失敗時只能全部重來**。展開冪等的實作方式並提醒 **`REPLACE` 是刪除再插入，會改變自增 ID 並觸發外鍵級聯**，語意與 `ON DUPLICATE KEY UPDATE` 不同。收在通用模式：**用批次標記讓重跑安全**，關鍵是**在寫入時就記錄「這批資料是哪一次匯入產生的」**，沒有標記事後就無法安全重跑。

### 大量刪除該怎麼做？

**核心答案**：**分批刪除而非一次 `DELETE`**。一次刪除幾千萬列會產生巨大的交易、大量的 undo、長時間的鎖、以及複製延遲的跳高。做法是 `DELETE ... WHERE ... LIMIT 10000` 配合迴圈，**每批之間短暫休息**。**如果是刪除整張表或大部分資料，`TRUNCATE` 或「建新表再改名」快得多**——因為它們不產生逐列的 undo 與 binlog。

**詳細解析**：**分批刪除有一個容易踩的效能陷阱**：如果條件是 `WHERE created_at < ?`，**每一批都要重新從頭掃描找到符合的列**——已刪除的部分雖然不見了但索引的遍歷成本仍在（尤其是有大量 undo 版本時）。**更好的做法是「依主鍵範圍分批」**：先找出要刪除的主鍵範圍，然後 `WHERE id BETWEEN ? AND ? AND created_at < ?` 逐段處理，**每一段的掃描範圍是確定且不重疊的**。**另一個常被忽略的是「刪除不會回收磁碟空間」**——InnoDB 的頁面被標記為可重用但不歸還給作業系統，**表的檔案不會縮小**。要真的回收需要 `OPTIMIZE TABLE`（重建表，是一個重操作）或者在建立時就用分區表讓「刪除舊資料」變成「刪除一個分區」。

**面試回答方式**：給分批刪除的做法與一次刪除的四個問題，並指出**刪除大部分資料時「建新表再改名」快得多**。真正的加分點是**分批刪除的效能陷阱**：依時間條件分批時每批都要重新掃描，**更好的是依主鍵範圍分批**讓每段的掃描確定且不重疊。收在另一個常被忽略的點：**刪除不回收磁碟空間**，表的檔案不會縮小，要真的回收需要重建表或者用分區表讓「刪除舊資料」變成「刪除一個分區」。
