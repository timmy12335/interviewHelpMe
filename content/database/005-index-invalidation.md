# 題目

哪些常見寫法會導致索引失效（用不上索引）？該怎麼避免？

## 核心答案

常見的索引失效場景包括：（1）**在索引欄位上使用函式或運算**（如 `WHERE YEAR(create_time) = 2026`、`WHERE age + 1 = 20`）——索引存的是欄位原始值，用函式/運算後值已經變了，索引無法直接匹配；（2）**隱式型別轉換**（如欄位是字串型別，查詢時傳數字 `WHERE phone = 13800000000` 而非字串，MySQL 會做隱式轉換、可能導致索引失效）；（3）**`LIKE` 以萬用字元開頭**（如 `LIKE '%abc'`，無法利用索引的有序性，`LIKE 'abc%'` 前綴匹配則可以）；（4）**`OR` 連接的條件中有欄位沒索引**（一個 OR 條件如果有任何一邊沒有索引，可能導致整個查詢放棄索引、走全表掃描）；（5）**聯合索引（Composite Index）不符合最左前綴（Leftmost Prefix）**（見前一題）；（6）**優化器判斷全表掃描更划算**（如索引選擇性低）。避免方法——把函式運算移到值的一側（不動欄位）、保持型別一致、避免 `%` 開頭的模糊查詢、統一用索引欄位加 OR 或改寫成 UNION。

## 詳細解析

**1. 對索引欄位使用函式/運算**：

- 錯誤示範——`WHERE YEAR(create_time) = 2026`（對欄位用了 YEAR 函式）、`WHERE age + 1 = 20`（對欄位做了運算）。
- 為什麼失效——索引裡存的是 `create_time`、`age` 的「原始值」，資料庫要判斷某一行是否符合條件，需要「先對索引裡的每個值都算一次函式/運算」才能比較，這樣索引的有序性就沒用了（等於要對每個值都重新計算），只能退化成全表掃描。
- 正確寫法——把運算/函式移到「常數值」那一側，讓欄位保持原樣：`WHERE create_time >= '2026-01-01' AND create_time < '2027-01-01'`（代替 YEAR 函式）、`WHERE age = 19`（代替 age+1=20）。

**2. 隱式型別轉換**：

- 如果欄位是 `VARCHAR` 型別（如手機號），查詢時寫 `WHERE phone = 13800000000`（傳了數字而非字串），MySQL 會按規則做隱式轉換——這種轉換可能發生在「索引欄位一側」（等同於對索引欄位做了運算 `CAST(phone AS SIGNED) = 13800000000`），導致索引失效。
- 正確寫法——保持查詢值的型別和欄位型別一致：`WHERE phone = '13800000000'`。

**3. LIKE 以萬用字元開頭**：

- `WHERE name LIKE '%明'`（前面有 %）——因為索引是按「字首」排序的，"%明" 要求「以明結尾」，索引的有序性（按第一個字母排）幫不上忙（可能是張明、李明、王明，字首完全不同），只能全表掃描（或全索引掃描）。
- `WHERE name LIKE '明%'`（後面有 %，前綴匹配）——可以利用索引，因為索引就是按字首排序的，能快速定位到「明」開頭的一段連續範圍。

**4. OR 連接的條件**：

- `WHERE a = 1 OR b = 2`——如果 a 有索引、b 沒索引，這個 OR 查詢可能無法有效利用 a 的索引（因為即使 a 條件能用索引快速定位，b 條件那部分還是要全表掃描，優化器可能乾脆整體放棄索引）。
- 優化——確保 OR 兩邊的欄位都有索引；或改寫成 `UNION`（分別對 a=1 和 b=2 走各自的索引查詢，再合併結果）。

## 面試回答方式

用列舉的方式講清幾種常見失效場景——函式/運算在索引欄位上、隱式型別轉換、LIKE 前置萬用字元、OR 連接無索引欄位、不符合最左前綴。每種都要能講出「為什麼失效」（不只是背現象）——核心邏輯是「索引的價值在於『有序性』，任何讓資料庫『無法直接用原始索引值比較、必須先做轉換或計算』的寫法，都會讓有序性失效」。給出對應的正確寫法（函式移到值一側、型別保持一致、LIKE 用前綴匹配、OR 兩邊都建索引或用 UNION）。能講清「為什麼」而非死背清單，展現你理解索引失效的本質原因。

## 常見追問

### 為什麼隱式型別轉換會導致索引失效？

**核心答案**：因為當「欄位型別」和「查詢值的型別」不一致時，資料庫需要「轉換」其中一方以便比較——而 MySQL 的轉換規則決定了，很多情況下是「把索引欄位的值轉換成查詢值的型別」，這相當於「對索引欄位的每一個值都做了一次函式運算（型別轉換）」，就和「對索引欄位用函式」的失效原理一樣——索引存的是原始型別的值，一旦要先轉換才能比較，索引的有序排列就沒用了，只能全表掃描逐行轉換比較。具體例子——`phone` 欄位是 `VARCHAR`，查詢 `WHERE phone = 13800000000`（傳整數），MySQL 會把 `phone` 隱式轉換成數字再比較（等同於 `CAST(phone AS SIGNED) = 13800000000`），這樣就是「對索引欄位做了轉換運算」，索引失效。

**詳細解析**：這題深入到隱式轉換為什麼在本質上「等同於對欄位用了函式」。MySQL 的型別轉換規則（何時轉換哪一方）比較複雜，但一個常見且容易踩的規律是——當「字串欄位」和「數字」比較時，MySQL 傾向於「把字串轉換成數字」（而不是把數字轉換成字串）。這意味著在 `WHERE phone = 13800000000` 這個查詢中，MySQL 實際執行的邏輯類似「對 phone 欄位的每一個值，都先轉換成數字，再和 13800000000 比較」——這就是為什麼它等同於「對索引欄位用了函式（CAST）」：索引裡存的是原始的字串值、按字串排序，但查詢卻要求「先轉換成數字再比較」，資料庫沒辦法利用「字串索引的有序性」去快速定位符合「轉換成數字後等於某值」的行，只能退化成「取出每一行，轉換，比較」的全表掃描。這個坑很隱蔽——因為 SQL 語法上完全合法（不會報錯，只是「悄悄地」變慢），很多人不知道自己寫的查詢因為型別不匹配而失去了索引加速，直到效能出問題才發現。避免的方法很簡單——養成「查詢值和欄位定義的型別保持一致」的習慣（字串欄位查詢時用引號括起來、數字欄位不用引號），這是一個容易被忽視但影響很大的實務細節。

**面試回答方式**：講出「型別不一致時 MySQL 要轉換其中一方以便比較、常見規律是把字串欄位轉成數字、這等同於對索引欄位每個值都做了一次轉換運算(如同用了函式)、索引的有序性(按字串排)就用不上了、只能全表掃描」。用具體例子(phone 是 VARCHAR、查詢傳整數)説明。強調「這個坑很隱蔽——語法合法不報錯、只是悄悄變慢、養成型別一致的習慣是關鍵」。展現你理解隱式轉換失效的本質原因和它的隱蔽性。

### 已經避免了函式和隱式轉換，為什麼查詢還是很慢？

**核心答案**：如果已經排除了函式/運算、隱式轉換這些明顯的索引失效原因，查詢仍慢可能是——(1)**優化器判斷全表掃描更划算**(見前面聚簇索引（Clustered Index）題的追問——索引選擇性低、或篩選出的資料佔全表比例大，優化器主動放棄索引);(2)**回表（Bookmark Lookup）次數太多**(查詢用了二級索引、但需要的欄位不在索引裡、每一行都要回表、如果符合條件的行很多，大量的回表 IO 累加起來就很慢，即使索引本身查找很快);(3)**資料量本身就很大、且查詢返回的結果集也很大**(即使索引查找是 O(log n)，但如果要返回和處理的資料量本身就是幾十萬行，這部分的網路傳輸和處理耗時也不容忽視);(4)**沒有用上最合適的索引**(可能有索引、但 MySQL 選擇了另一個效率較低的索引，需要用 EXPLAIN 檢查實際用了哪個索引、必要時用 FORCE INDEX 提示);(5)**鎖等待**(如果查詢因為和其他交易的鎖衝突而等待，看起來慢但其實是在排隊而非查詢本身慢)。核心是——查詢慢的原因是多方面的，索引失效只是其中一種，要用 EXPLAIN 分析實際的執行計劃（Execution Plan）來定位真正的原因(見 [[006-explain.md]])。

**詳細解析**：這題提醒「索引失效只是查詢慢的原因之一，不能一概而論」，要有系統性的排查思路。實務中查詢慢的原因往往是多方面的組合——即使欄位定義、查詢寫法都沒有明顯的索引失效問題，仍可能因為「回表次數多」(尤其在符合條件的行數很多時，每行都要回表，這個開銷是累加的，即使索引查找本身很快)、「返回結果集本身就很大」(資料傳輸和處理的固有成本，和索引無關)、「選錯了索引」(有多個可用索引，優化器的選擇不一定是最優的，這時可能需要用 `FORCE INDEX` 提示，或分析為什麼統計資訊導致優化器誤判)、「鎖等待」(交易之間的鎖衝突導致查詢排隊等待，這其實不是查詢本身慢，而是在等鎖，需要透過查看鎖狀態、慢查詢（Slow Query）日誌來區分)而變慢。所以排查查詢效能問題不能只停留在「檢查有沒有索引失效」這一個角度，而要系統性地——用 `EXPLAIN` 看實際的執行計劃(用了哪個索引、掃描了多少行、是否有回表)、看實際返回的資料量、檢查是否有鎖等待、對比資料量和硬體資源是否匹配。理解「索引失效只是眾多可能原因之一、需要系統性排查」，展現你有更全面的資料庫效能診斷思路，避免「一看到查詢慢就只想到索引失效」這種片面的思考方式。

**面試回答方式**：講出「查詢慢不只是索引失效——優化器判斷全表掃描更划算(選擇性低)、回表次數太多(符合條件的行多、每行都要回表)、結果集本身很大(傳輸處理成本)、選錯索引(要 FORCE INDEX 或分析統計資訊)、鎖等待(其實是排隊不是查詢慢)」。強調「要用 EXPLAIN 系統性分析、而非只想到索引失效這一個角度」。展現你有全面的資料庫效能診斷思路。

### 為什麼「範圍查詢右邊的欄位」和「LIKE 前後都有萬用字元」都會導致索引失效？它們的本質原因一樣嗎？

**核心答案**：本質原因是一樣的——都是「破壞了利用索引『有序性』快速定位一段連續範圍」的能力。**範圍查詢右邊的欄位**（如 `INDEX(a,b,c)`、`WHERE a=1 AND b>2 AND c=3` 裡的 c）——因為 b 是範圍條件，在「a=1 且 b>2」這個範圍內，資料只是按 b 有序、c 在這個範圍內並不是整體有序的（c 只有在 a、b 都固定為某個具體值時才有序），所以 c 這個條件無法再用索引的有序性快速定位（只能在這個範圍內逐一檢查，見索引下推的部分優化）。**LIKE 前面有萬用字元**（如 `'%abc'`）——索引是按「字串的字首」排序的，"以 abc 結尾" 這個條件和「字首」毫無關係（字首可能是任何字母），索引的有序排列（按字首）完全幫不上忙，只能全表/全索引掃描逐一檢查每個值是否以 abc 結尾。兩者的共同本質是——索引只能高效支援「能透過『前綴』或『排序中連續一段』來定位」的查詢，一旦查詢條件不再符合「利用索引現有排序方式定位一段連續範圍」，索引就退化成「需要逐一檢查」，效率大打折扣。

**詳細解析**：這題把兩個看似不相關的索引失效場景（範圍查詢右側欄位、LIKE 萬用字元開頭）統一到「索引有序性能否被有效利用」這個共同原理下，展現更本質的理解。索引的核心價值在於「有序」——B+ 樹按索引定義的規則（單欄位按值排序、聯合索引按欄位順序依次排序、字串按字典序排序）把資料排列好，這讓「查找某個值」或「查找某個連續範圍」都能透過「在有序結構中定位」而非「逐一檢查」來完成。但這個「有序性」是有「特定維度」的——聯合索引是「先按 a 排、a 相同再按 b 排」的有序，字串索引是「按字首排」的有序。一旦查詢的需求「和索引的排序維度不匹配」，有序性就用不上了。範圍查詢右側欄位的情況——`b>2` 這個範圍條件下，資料確實還是按 b 排序的（在 a=1 這個前提下），但排序到 b 這一層之後，c 就沒有整體的排序保證了（c 的排序只在「a 和 b 都固定為某個值」時才成立，一旦 b 是一個範圍而非固定值，c 在這個範圍內的多個 b 值之間是打亂的），所以無法用有序性定位 c。LIKE 萬用字元開頭的情況——索引是按「字首」的字典序排的，"%abc" 要求的是「後綴」匹配，這和「字首排序」完全是不同的維度，索引的排序對「後綴匹配」毫無幫助。所以雖然表面上看是兩個不同的「失效規則」，但本質都是「查詢的比對方式，和索引實際的排序維度不匹配，導致無法用有序性快速定位、只能退化為逐一檢查」。理解這個統一的本質原理，能幫你舉一反三地判斷「其他不熟悉的查詢寫法會不會導致索引失效」，而不是死記每一條具體規則。

**面試回答方式**：講出「本質相同——都是查詢的比對方式和索引實際的排序維度不匹配、無法利用有序性快速定位、只能退化成逐一檢查」。分別解釋——「範圍查詢右側欄位：b 是範圍、在這個範圍內 c 沒有整體排序保證(c 只在 a、b 都固定值時才有序)；LIKE 前置萬用字元：索引按字首排序、後綴匹配和字首排序是不同維度、完全用不上」。強調「理解這個統一原理能舉一反三判斷其他情況、而非死背具體規則」。展現你能提煉出索引失效背後更本質、更通用的原理。
