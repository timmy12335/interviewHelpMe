# 題目

什麼是聯合索引（Composite Index）？最左前綴（Leftmost Prefix）原則是什麼？聯合索引的欄位順序該怎麼設計？

## 核心答案

聯合索引（複合索引）是「在多個欄位上共同建立的一個索引」（如 `INDEX(a, b, c)`），而不是為每個欄位各自建一個獨立索引。它的底層仍是一棵 B+ 樹，但「排序規則」是——先按第一個欄位（a）排序，a 相同時再按第二個欄位（b）排序，以此類推。「最左前綴原則」是指——查詢時，只有「從索引的最左邊欄位開始、連續使用」的條件，才能有效利用這個聯合索引（如 `INDEX(a, b, c)` 能加速 `WHERE a=1`、`WHERE a=1 AND b=2`、`WHERE a=1 AND b=2 AND c=3`，但不能加速「只用 b」或「跳過 a 直接用 b、c」的查詢）。設計聯合索引的欄位順序時，通常把「等值查詢、選擇性高」的欄位放前面，「範圍查詢」的欄位放後面（且範圍查詢欄位之後的欄位無法再利用索引排序）。

## 詳細解析

**聯合索引的結構**：`INDEX(a, b, c)` 的 B+ 樹裡，資料按 `(a, b, c)` 這個組合排序——先比較 a，a 相同再比較 b，b 也相同再比較 c。這意味著——如果只看 b 或 c 這兩個欄位，它們在索引中「並沒有整體有序」（只有在 a 相同的一小段範圍內，b 才是有序的）。

**為什麼有「最左前綴」的限制**：因為索引的排序是「按 a 優先」的，如果查詢條件不包含 a（或者 a 不是從最左邊開始連續使用），資料庫就無法利用這個「先按 a 排序」的特性快速定位——就像一本按照「姓氏、名字」排序的電話簿，你可以快速查「姓王的所有人」（用姓氏，最左前綴）、也可以快速查「姓王且叫小明的」（姓氏+名字），但沒法快速查「所有叫小明的人」（跳過了姓氏這個排序的第一層，只知道名字沒用，因為姓王的小明和姓李的小明在這本電話簿裡離得很遠）。

**最左前綴原則的具體規則**：

- `INDEX(a, b, c)` 能被以下查詢有效利用——`WHERE a=1`、`WHERE a=1 AND b=2`、`WHERE a=1 AND b=2 AND c=3`、`WHERE a=1 AND c=3`（能用上 a，但 c 用不上，因為跳過了 b）。
- **不能**被有效利用——`WHERE b=2`（沒有 a）、`WHERE b=2 AND c=3`（缺 a）。
- **範圍查詢會「中斷」後續欄位的排序利用**——`WHERE a=1 AND b>2 AND c=3`：a 能用（等值）、b 能用（範圍），但因為 b 是範圍查詢（不是等值），在 b 這個範圍內，c 就不再是有序的了（c 只有在 a、b 都固定為某個值時才有序），所以 c 這個條件無法再利用索引的排序（雖然 InnoDB 有一些優化如「索引下推」能部分緩解，見追問）。

**聯合索引的欄位順序設計原則**：

- **選擇性高、常作等值查詢的欄位放前面**——這樣能透過最左前綴快速縮小範圍。
- **範圍查詢的欄位放後面**——因為範圍查詢會中斷後續欄位的排序利用，放在最後對索引效率影響最小。
- 一個設計良好的聯合索引，能同時支援「多種查詢組合」（覆蓋 `a`、`a+b`、`a+b+c` 這幾種查詢），減少需要建立的索引總數。

## 面試回答方式

先講「聯合索引是什麼」——多欄位共同建一個索引、B+ 樹按欄位順序依次排序。最左前綴原則要用「電話簿姓氏+名字」這個比喻講清楚——為什麼「只查後面的欄位」用不上索引。務必講清「範圍查詢會中斷後續欄位的排序利用」這個細節（很多人只知道最左前綴、不知道範圍查詢會截斷），並給出「等值放前、範圍放後」的欄位順序設計建議。能講清最左前綴的具體規則（哪些查詢能用、哪些不能）並用具體例子（INDEX(a, b, c) 對各種 WHERE 條件的效果），展現你不只背口訣還理解背後的排序邏輯。

## 常見追問

### 什麼是索引下推（Index Condition Pushdown, ICP）？它怎麼緩解最左前綴的限制？

**核心答案**：索引下推是 MySQL 5.6+ 的優化——在「聯合索引因為最左前綴限制、某些欄位條件無法直接利用索引排序定位」的情況下，讓 MySQL「在遍歷索引的過程中，就順便檢查這些用不上排序定位的條件（用索引裡已有的欄位值判斷），過濾掉不符合的，減少需要回表（Bookmark Lookup）的次數」，而不是「先用索引找到一批候選、把它們全部回表取出完整資料後、才在伺服器層過濾這些條件」。它並不能讓「用不上最左前綴」的欄位變得「像最左前綴欄位一樣快速定位」，但能減少不必要的回表操作，仍是一個實質的效能提升。

**詳細解析**：舉例説明——`INDEX(a, b, c)`查詢 `WHERE a=1 AND b>2 AND c=3`。因為 b 是範圍查詢，c 在索引裡（相對於這個範圍）不是有序的，所以「c=3」這個條件，按傳統做法（沒有 ICP），MySQL 只能用 `a=1 AND b>2` 透過索引定位到一批候選行（這些候選行的主鍵值），然後「把這些候選行都回表取出完整資料」，再在伺服器層（拿到完整行資料後）檢查每一行是否滿足 `c=3`，過濾掉不滿足的。這意味著——即使很多候選行最終不滿足 c=3 而被過濾掉，它們也都經歷了「回表」這個相對昂貴的操作（多一次 B+ 樹查找）。索引下推的優化是——在「遍歷 `INDEX(a, b, c)` 這個索引本身」的過程中（此時還沒回表，只是在索引的 B+ 樹葉子節點上遍歷），就用「索引裡已經有的 c 值」去檢查 `c=3` 這個條件，如果不滿足，直接跳過、不用回表；只有真正滿足所有能在索引裡檢查的條件的行，才需要真正回表取完整資料。這樣雖然「c=3」這個條件本身無法像 a、b 那樣利用排序快速定位（還是要遍歷 a=1、b>2 範圍內的所有索引項），但能省去大量「不符合 c=3 條件、卻還是要回表」的無謂回表操作，減少了 IO。理解索引下推的作用（在索引遍歷階段就過濾、減少不必要的回表），展現你對聯合索引優化有更深入的理解。

**面試回答方式**：講出「索引下推是在遍歷索引(還沒回表)的過程中、就用索引裡已有的欄位值(如例子中的 c)檢查條件、過濾掉不符合的、減少不必要的回表次數」。強調「它不能讓用不上最左前綴的欄位變得能快速定位、但能省去大量無謂的回表 IO」。用 `INDEX(a, b, c)` + `a=1 AND b>2 AND c=3` 的具體例子説明。展現你對聯合索引優化機制有更深入的理解。

### 如果查詢條件的順序和索引定義的順序不一致，索引還會生效嗎？

**核心答案**：會生效——查詢優化器會「自動調整」條件的判斷順序，不要求你寫 SQL 時「WHERE 後面的條件順序」和「索引定義的欄位順序」完全一致。例如 `INDEX(a, b, c)`你寫 `WHERE b=2 AND a=1`（b 寫在前面），優化器仍然能識別出「這裡有 a 和 b 的等值條件」，按索引的實際順序（先 a 後 b）去利用索引，效果和寫成 `WHERE a=1 AND b=2` 是一樣的。這是因為 SQL 的 WHERE 子句在邏輯上是「條件的集合」（用 AND 連接，不講究書寫順序），優化器會分析這些條件、判斷能不能匹配到某個索引的最左前綴，而不是機械地按你書寫的順序去匹配索引。

**詳細解析**：這題澄清一個常見的誤解——不少人以為「SQL 裡寫 WHERE 條件的順序要和索引定義的欄位順序一模一樣」，其實不然。SQL 的查詢優化器在處理 WHERE 子句時，會先把所有用 AND 連接的條件解析成一個「條件集合」（在邏輯上，`a=1 AND b=2` 和 `b=2 AND a=1` 是完全等價的），然後優化器會分析「這個條件集合裡，有哪些欄位、是什麼類型的比較（等值/範圍）」，再去匹配資料庫中已有的各個索引，看看「哪個索引的最左前綴能被這個條件集合滿足」。這個匹配過程是基於「條件集合」和「索引欄位順序」的比對，和你在 SQL 裡「按什麼順序書寫」這些條件沒有關係——不管你寫 `a=1 AND b=2` 還是 `b=2 AND a=1`，優化器分析出來的都是「這裡有 a 和 b 的等值條件」，然後都能匹配到 `INDEX(a, b, c)` 的最左前綴（a, b）。所以「最左前綴」講的是「索引欄位定義的順序」（決定了 B+ 樹的排序方式），而不是「你寫 SQL 時 WHERE 條件的順序」——這兩者是不同的概念，不要混淆。這也是為什麼寫 SQL 時不用刻意糾結「條件要按索引定義的順序寫」，只要「使用的欄位組合」符合最左前綴（即包含索引中連續的、從最左開始的欄位），順序怎麼寫都可以。

**面試回答方式**：明確回答「會生效——優化器把 WHERE 條件解析成邏輯上的條件集合(AND 連接、順序無關)、再去匹配索引的最左前綴、不要求 SQL 書寫順序和索引定義順序一致」。澄清「最左前綴講的是索引欄位定義的順序(決定 B+ 樹排序)、不是你寫 SQL 條件的書寫順序、這是兩個不同概念」。展現你對這個常見誤解有清晰的認識。

### 一個表已經有 INDEX(a, b) 這個聯合索引，還需要再單獨建 INDEX(a) 嗎？

**核心答案**：通常不需要——因為 `INDEX(a, b)` 這個聯合索引，本身「已經隱含支援」了「只用 a」這種查詢（最左前綴原則：`INDEX(a, b)` 對 `WHERE a=1` 這種查詢完全能有效利用，因為 a 就是這個聯合索引的第一個欄位）。所以如果你已經有 `INDEX(a, b)`，再單獨建一個 `INDEX(a)` 是「冗餘」的——它不會帶來額外的查詢效能（`WHERE a=1` 用 `INDEX(a, b)` 和用單獨的 `INDEX(a)` 效果一樣），卻會多佔用儲存空間、且拖慢寫入（多維護一個索引）。所以設計索引時，應該檢查「已有的聯合索引的前綴」，避免建立「已經被某個聯合索引的前綴覆蓋」的冗餘單欄位索引。

**詳細解析**：這題考的是「理解最左前綴原則後、能推導出索引設計的實務優化——避免冗餘索引」。核心邏輯是——`INDEX(a, b)` 這棵 B+ 樹本身就是「先按 a 排序、a 相同再按 b 排序」，如果你只用 a 做查詢條件（`WHERE a = 某值`），完全可以直接利用這棵樹「按 a 排序」的這個特性快速定位（不需要管 b），效果和一個「單獨只按 a 排序」的索引是一模一樣的。所以「INDEX(a, b) 的存在已經天然地包含了 INDEX(a) 的所有查詢能力」——任何能被 INDEX(a) 加速的查詢，INDEX(a, b) 也能同樣加速（因為最左前綴）。既然如此，如果你已經建了 INDEX(a, b)，再額外建一個 INDEX(a)，這個 INDEX(a) 除了徒增儲存空間和維護開銷（每次寫入要多維護一份索引）之外，沒有任何查詢效能上的額外好處（不會有任何查詢因為多了這個 INDEX(a) 而變得更快，因為 INDEX(a, b) 已經能滿足）。所以資料庫設計和優化的一個常見檢查點是——盤點現有的索引，看有沒有「某個索引是另一個聯合索引的前綴子集」這種冗餘關係，如果有，冗餘的那個（更短的、被前綴覆蓋的）通常可以刪除，以減少不必要的儲存和寫入開銷。這也提醒我們設計索引時要有「整體規劃」的思維——先看清楚已有哪些聯合索引及其前綴能覆蓋哪些查詢，再決定是否需要新建索引，而不是每個查詢需求都獨立地建一個新索引。

**面試回答方式**：講出「不需要——INDEX(a, b) 已經隱含支援 WHERE a=1 這種查詢(最左前綴、a 是這棵樹的第一排序欄位)、額外建 INDEX(a) 是冗餘、只會多佔空間拖慢寫入、不帶來查詢效能提升」。給出實務建議——「設計索引要整體規劃、檢查是否已有聯合索引的前綴能覆蓋需求、避免建立被覆蓋的冗餘單欄位索引」。展現你能從最左前綴原則推導出實務的索引設計優化。
