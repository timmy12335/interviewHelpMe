# 題目

InnoDB 怎麼處理死鎖？拿到一份死鎖日誌你會怎麼看？

## 核心答案

InnoDB 有**主動的死鎖偵測**：它維護一個「誰在等誰」的等待圖，每次有交易進入等待時檢查是否形成環，發現環就選一個「回滾成本最小」的交易當犧牲者（依它修改的列數與持有的鎖估算），回滾它並回傳 `ERROR 1213 Deadlock found`。**另一個交易則繼續執行**——所以死鎖不會讓系統卡死，它表現為「某些交易偶發失敗」。

看死鎖日誌（`SHOW ENGINE INNODB STATUS` 的 `LATEST DETECTED DEADLOCK` 段落，或開啟 `innodb_print_all_deadlocks` 記進錯誤日誌）要看四件事：**兩個交易各自在執行什麼 SQL**、**各自持有什麼鎖**（`HOLDS THE LOCK(S)`）、**各自在等什麼鎖**（`WAITING FOR THIS LOCK`）、以及**哪一個被回滾**。

關鍵是從「持有」與「等待」推出加鎖的順序——死鎖幾乎總是因為兩個交易以相反的順序取得同一組鎖。

## 詳細解析

**死鎖日誌只保留最後一次**，這是一個實務上的限制——所以應該開啟 `innodb_print_all_deadlocks` 把每一次都記進錯誤日誌，否則你只能看到最後那一次，而它未必是最有代表性的。這個設定的開銷極小，值得預設開啟。

**最常見的死鎖模式有四種**。**加鎖順序不一致**——交易 A 先鎖使用者 1 再鎖使用者 2，交易 B 反過來。**解法是統一順序**（例如永遠按主鍵由小到大加鎖）。**間隙鎖造成的死鎖**——在 RR 隔離級別下，兩個交易的插入意圖鎖與間隙鎖互相衝突，這類死鎖的 SQL 看起來完全不相關，最難理解。**唯一索引的插入衝突**——兩個交易插入相同的唯一鍵，一個等另一個提交才知道結果。**索引不足導致鎖範圍過大**——沒有合適索引時 InnoDB 可能鎖住大量列（甚至退化成鎖整張表的效果），**大幅提高衝突機率**。

「加索引減少死鎖」是一個不直覺但重要的洞見。InnoDB 的行鎖是**加在索引記錄上的**——沒有索引時，查詢要掃描更多列，就會鎖住更多列。所以一個 `UPDATE ... WHERE non_indexed_col = ?` 可能鎖住整張表的所有列，與任何其他交易都會衝突。加上合適的索引讓鎖的範圍縮到最小，是減少死鎖最有效的手段之一——而很多人只想到「調整加鎖順序」。

死鎖不一定要消除，但必須被處理。少量的死鎖在高併發系統中是正常的，應用層應該捕捉 `ERROR 1213` 並重試（死鎖是暫時性的，重試通常會成功）。但重試必須是安全的——交易要麼冪等、要麼從頭重新執行整個交易（不能只重試失敗的那一句，因為整個交易已經被回滾了）。「死鎖率上升」則是一個應該告警的指標，因為它通常意味著併發模式或資料分佈變了。

## 面試回答方式

先給 InnoDB 的**主動偵測機制**（維護等待圖、進入等待時檢查環、選回滾成本最小的當犧牲者）並指出死鎖表現為「某些交易偶發失敗」而非系統卡死。給看日誌的四件事，並強調關鍵是從「持有」與「等待」推出加鎖順序——死鎖幾乎總是兩個交易以相反順序取得同一組鎖。加分點有三個：**死鎖日誌只保留最後一次**，應該開啟 `innodb_print_all_deadlocks`（開銷極小，值得預設開啟）；「加索引減少死鎖」這個不直覺的洞見——行鎖加在索引記錄上，沒有索引時查詢掃描更多列就鎖住更多列，一個 `UPDATE ... WHERE 未索引欄位` 可能鎖住整張表，而很多人只想到調整加鎖順序；以及死鎖不一定要消除但必須被處理——應用層捕捉並重試，但必須重試整個交易而非失敗的那一句。

## 講稿

InnoDB 有主動的死鎖偵測。它維護一個誰在等誰的等待圖，每次有交易進入等待時檢查是否形成環，發現環就選一個回滾成本最小的交易當犧牲者。另一個交易繼續執行。所以死鎖不會讓系統卡死，它表現為某些交易偶發失敗。

看死鎖日誌我會看四件事。兩個交易各自在執行什麼 SQL、各自持有什麼鎖、各自在等什麼鎖、還有哪一個被回滾。關鍵是從持有跟等待推出加鎖的順序，因為死鎖幾乎總是兩個交易以相反的順序取得同一組鎖。

有一個實務限制要注意，死鎖日誌只保留最後一次。所以應該開啟記錄所有死鎖的設定，把每一次都寫進錯誤日誌。這個設定的開銷極小，值得預設開啟。

還有一個不直覺但很重要的洞見，加索引可以減少死鎖。因為 InnoDB 的行鎖是加在索引記錄上的，沒有索引的時候查詢要掃描更多列，就會鎖住更多列。一個依據未索引欄位的更新，可能鎖住整張表的所有列，跟任何其他交易都會衝突。很多人只想到調整加鎖順序，其實加索引常常更有效。

最後，死鎖不一定要消除但必須被處理。應用層要捕捉並重試，而且必須重試整個交易，不能只重試失敗的那一句。

## 常見追問

### 死鎖與鎖等待逾時差在哪？

**核心答案**：死鎖是循環等待，會被主動偵測並立刻回滾其中一個（`ERROR 1213`）；鎖等待逾時是單向等待超過了 `innodb_lock_wait_timeout`（預設 50 秒），沒有形成環，只是對方持有太久（`ERROR 1205`）。兩者的根因完全不同：死鎖是加鎖順序問題，逾時是長交易或熱點行的爭用問題。

**詳細解析**：`innodb_lock_wait_timeout` 的預設 50 秒對多數線上服務都太長——一個 HTTP 請求等 50 秒早就逾時了，而那條連線與交易還佔著資源。實務上設成 5 到 10 秒更合理，讓失敗快速發生並被重試或回報。但要注意這個參數是「等待單一個鎖的時間」而非「整個交易的時間」——一個交易可能連續等待多個鎖，每個都不到逾時但總和很長。真正限制交易總時長需要應用層的逾時或 MySQL 8 的 `MAX_EXECUTION_TIME`（只對 `SELECT` 有效）。 這個「參數限制的是哪一段時間」的區分，在設定所有逾時類參數時都要弄清楚——否則會以為設了保護但實際上沒有覆蓋到真正的風險。

**面試回答方式**：給精確的區分（循環等待被主動偵測 vs 單向等待超時）與不同的根因（加鎖順序 vs 長交易或熱點爭用）。加分點是指出**預設 50 秒對線上服務太長**，實務上 5 到 10 秒更合理。真正的深度在於澄清這個參數限制的是「等待單一個鎖的時間」而非「整個交易的時間」，一個交易可能連續等多個鎖、每個都不到逾時但總和很長。收在通用提醒：設定所有逾時類參數時都要弄清楚它限制的是哪一段時間。

### 間隙鎖造成的死鎖為什麼特別難懂？

**核心答案**：因為**衝突的 SQL 看起來毫無關係**。在 RR 隔離級別下，`SELECT ... FOR UPDATE` 或 `UPDATE` 一個不存在的值會加**間隙鎖**（鎖住一段範圍，防止其他交易插入造成幻讀）；而 `INSERT` 需要**插入意圖鎖**。兩個交易分別鎖了不同的間隙，然後各自要往對方的間隙插入，就形成死鎖——而日誌上顯示的是兩句完全不同的 SQL，操作的也是不同的值。

**詳細解析**：典型的場景是「先查詢是否存在，不存在就插入」（`SELECT ... FOR UPDATE` 加 `INSERT`）。兩個交易查不同的值都不存在（各自鎖了一段間隙），然後都要插入——如果它們的值落在對方鎖住的間隙裡，就死鎖了。**解法有三個**：**用 `INSERT ... ON DUPLICATE KEY UPDATE` 或 `INSERT IGNORE`**（一步完成，不需要先查）、降到 RC 隔離級別（RC 沒有間隙鎖，代價是可能有幻讀）、或者接受死鎖並重試。第一種是最好的——它把「檢查再插入」這個天然有競態的模式，換成了一個原子操作。「用資料庫提供的原子操作取代『先查再寫』」是一個普遍適用的建議，因為那個模式在任何併發環境下都是錯的。

**面試回答方式**：給原因——**衝突的 SQL 看起來毫無關係**，因為間隙鎖鎖的是範圍而非具體的列。用「先查詢是否存在、不存在就插入」這個典型場景說明形成過程。給三個解法並指出**第一種最好**：`INSERT ... ON DUPLICATE KEY UPDATE` 一步完成，把天然有競態的「檢查再插入」換成原子操作。收在普遍建議：用資料庫提供的原子操作取代「先查再寫」，因為那個模式在任何併發環境下都是錯的。

### 怎麼從根本上減少死鎖？

**核心答案**：四個方向，依有效性排序。**縮短交易**——交易越短，持有鎖的時間越短，衝突窗口越小；特別是交易裡絕對不要有外部呼叫。**統一加鎖順序**——多筆更新時按固定順序（例如主鍵排序）處理。**加合適的索引**——縮小鎖的範圍。**降低隔離級別**——RC 沒有間隙鎖，死鎖大幅減少（代價是可能有幻讀，而多數業務並不需要 RR 的保證）。

**詳細解析**：「降到 RC」這個選項常被忽略，但它可能是收益最大的一個。MySQL 的預設是 RR（與 SQL 標準不同，多數其他資料庫預設 RC），而 RR 的間隙鎖是大量死鎖的來源。**多數業務邏輯其實不需要 RR**——它們不會在一個交易裡對同一個範圍查詢兩次並期待結果相同。PostgreSQL、Oracle、SQL Server 的預設都是 RC 或類似的級別，而它們的應用運作良好，這本身就是一個佐證。 但切換隔離級別是一個需要謹慎評估的變更：要確認沒有邏輯依賴 RR 的可重複讀、也要注意在 RC 下 binlog 必須是 ROW 格式（STATEMENT 格式在 RC 下不安全）。這是一個「預設值不一定適合你」的例子——MySQL 選 RR 有歷史原因（早期的複製依賴它），而那個原因對現在的系統未必成立。

**面試回答方式**：給四個方向並依有效性排序，強調**交易裡絕對不要有外部呼叫**。重點展開「降到 RC」常被忽略但可能收益最大——MySQL 預設 RR 與 SQL 標準不同，而**間隙鎖是大量死鎖的來源**，多數業務不需要 RR 的保證；並用「其他主流資料庫預設 RC 而應用運作良好」作為佐證。誠實給出切換的前提（確認沒有邏輯依賴可重複讀、binlog 必須是 ROW 格式）。收在觀點：這是「預設值不一定適合你」的例子，MySQL 選 RR 的歷史原因對現在的系統未必成立。
