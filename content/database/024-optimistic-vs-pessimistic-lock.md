# 題目

樂觀鎖（Optimistic Lock）和悲觀鎖（Pessimistic Lock）有什麼差異？資料庫層面通常怎麼實作樂觀鎖？

## 核心答案

**悲觀鎖**假設「衝突很可能發生」，所以在操作資料之前就先把資料「鎖起來」（例如用 `SELECT ... FOR UPDATE` 對讀取到的行加上排他鎖（Exclusive Lock）），確保這段期間沒有其他交易能修改這筆資料，直到目前的交易完成才釋放鎖，其他想要修改同一筆資料的交易必須排隊等待。**樂觀鎖**假設「衝突很少發生」，所以操作時不預先加鎖，而是在真正要「提交更新」的那一刻，才去檢查「這筆資料在我讀取之後、到現在準備更新之前，有沒有被別人修改過」，如果沒有就正常更新，如果發現已經被別人修改過，就拒絕這次更新（回報衝突，讓應用程式決定重試或提示使用者）。資料庫層面最常見的樂觀鎖實作方式是**版本號機制**——在表裡加一個 `version` 欄位，更新時執行 `UPDATE table SET data=?, version=version+1 WHERE id=? AND version=舊版本號`，如果這筆資料的版本號在讀取後已經被其他交易修改過（version 已經不是預期的舊值），這條 UPDATE 語句會因為 WHERE 條件不匹配而影響 0 行，應用程式據此判斷發生了併發衝突。

## 詳細解析

**悲觀鎖的運作方式**：以 `SELECT * FROM accounts WHERE id = 1 FOR UPDATE` 為例，這條語句在讀取這一行資料的同時，就對它加上排他鎖（X 鎖，見 [[010-lock-types.md]]），在目前這個交易提交或回滾之前，其他任何想要修改（甚至某些隔離級別下想要讀取）這一行的交易，都必須等待鎖被釋放。悲觀鎖的優點是「保證正確性、不會有衝突被遺漏」，缺點是「鎖住的期間，其他交易被迫等待，如果持鎖交易執行時間較長，會顯著降低系統的並行處理能力，甚至可能引發鎖等待逾時或死鎖（Deadlock）」。

**樂觀鎖（版本號機制）的具體流程**：
1. 應用程式讀取資料時，一併讀出當前的 `version` 值（假設讀到 `version = 5`）。
2. 應用程式在記憶體中對資料做修改（這段時間完全不持有任何資料庫鎖）。
3. 準備寫回資料庫時，執行：
```sql
UPDATE accounts SET balance = 新餘額, version = version + 1
WHERE id = 1 AND version = 5;
```
4. 如果在「讀取」和「這次更新」之間，沒有其他交易修改過這筆資料（version 仍然是 5），這條 UPDATE 會成功執行，影響 1 行並把 version 更新為 6。
5. 如果中間有其他交易搶先修改並提交了這筆資料（version 已經變成 6），這條 UPDATE 的 WHERE 條件 `version = 5` 就不會匹配任何資料列，影響 0 行——應用程式檢查「受影響的行數是否為 0」，如果是 0，就知道發生了併發衝突，可以選擇重新讀取最新資料並重試整個流程，或直接告知使用者「資料已被他人修改，請重新操作」。

**兩者的適用場景權衡**：悲觀鎖適合「衝突機率高、且衝突的代價很高（例如絕對不能出錯的金融交易扣款）」的場景，用「犧牲並行度」換取「絕對的正確性保證，且不需要處理衝突後重試的複雜邏輯」。樂觀鎖適合「衝突機率相對低、讀多寫少」的場景（例如電商的庫存扣減，雖然熱門商品可能有一定的併發修改，但多數情況下同一件商品被同時搶購修改的機率不算太高），優點是「大部分時候完全不需要等待鎖，並行效能好」，缺點是「一旦真的發生衝突，需要應用程式自己處理重試邏輯，且如果衝突機率其實很高，頻繁的重試反而可能比直接用悲觀鎖排隊等待還沒效率」。

## 面試回答方式

先用一句話對比核心假設的差異（悲觀鎖假設衝突常發生、先鎖再做；樂觀鎖假設衝突少發生、先做再檢查）。接著具體講出樂觀鎖最常見的實作方式——版本號機制，並用完整的 SQL 範例展現「UPDATE ... WHERE id=? AND version=?」這個核心手法，以及「影響行數為 0 代表衝突」的判斷邏輯，這是這題的核心考點，一定要講清楚具體機制而不只是抽象概念。最後給出適用場景的判斷準則（衝突機率高低、對正確性和效能的權衡），展現你能根據實際業務場景選擇合適的併發控制策略。

## 常見追問

### 除了版本號（version 欄位），還有其他常見的樂觀鎖實作方式嗎？

**核心答案**：另一種常見的樂觀鎖實作方式是用「時間戳（timestamp / updated_at）」取代顯式的版本號欄位——原理相同，只是用「最後更新時間」而非遞增的整數版本號，來判斷「這筆資料自讀取以來是否被修改過」，更新語句變成 `UPDATE table SET data=?, updated_at=NOW() WHERE id=? AND updated_at=讀取時的舊時間戳`。另一種思路是用「所有欄位值本身」作為判斷依據（Hibernate 等 ORM 框架有時採用這種方式）——更新時的 WHERE 條件包含「讀取時的所有原始欄位值」，只要任何一個欄位在中間被改過，WHERE 條件就不會匹配，效果上等同於一種「隱式版本號」，但不需要額外新增一個 version 欄位，缺點是 WHERE 條件變得冗長、且如果有大文字欄位放進比對條件，效能較差。

**詳細解析**：這題延伸樂觀鎖的其他實作變體，展現你不是只認識「version 欄位」這一種教科書式的標準答案。用時間戳取代版本號的做法，本質上和版本號機制完全相同（都是「檢查這個代表『資料狀態』的標記值，在讀取和更新之間有沒有變化」），差別只在於這個標記值選擇用「單調遞增的整數」還是「時間戳記」；用時間戳的一個實務考量是，如果系統本來就已經有 `updated_at` 這個欄位（很多表為了記錄稽核軌跡本來就會加這個欄位），可以直接複用它做樂觀鎖判斷，不需要額外新增欄位，但要注意時間戳的精度問題——如果兩次修改發生在同一毫秒（甚至同一秒，取決於時間戳欄位的精度設定），可能出現「時間戳相同但實際上是兩次不同的修改」這種邊界情況，導致樂觀鎖的判斷失準，這是版本號（每次修改保證嚴格遞增 1，不會有這種精度重疊問題）相對於時間戳的一個優勢。用「全部欄位值」做比對的方式（有時稱為「影子比對」或部分 ORM 框架的預設樂觀鎖行為），好處是完全不需要修改表結構（不用新增任何額外欄位），純粹依賴「資料本身有沒有變化」來判斷衝突，但缺點也很明顯——WHERE 子句要把所有欄位都列進去做比對，語句變得冗長且不易維護，如果表裡有 TEXT/BLOB 這類大型欄位，把它們也放進 WHERE 條件做相等比對，效能開銷可能不小（尤其某些資料庫對大欄位的相等比較沒有索引可用，需要做全文比對）。回答這題時，能講出至少一種替代方案（時間戳)並指出其優缺點(精度問題)，展現對樂觀鎖實作細節的延伸理解。

**面試回答方式**：介紹時間戳方案（原理和 version 欄位相通，用 `updated_at` 判斷可以複用已有欄位但要注意時間戳精度可能造成的邊界問題）。可以補充「全欄位比對」這種不需要額外欄位但 WHERE 條件冗長、大欄位效能較差的方案。強調「這些方案的核心原理都相同——檢查一個代表資料狀態的標記，在讀取和更新之間是否被改變過」，展現你理解樂觀鎖的本質而不只是記住一種具體實作。

### 樂觀鎖在高併發、衝突機率其實很高的場景下使用，會有什麼問題？

**核心答案**：如果實際的衝突機率比預期高很多（比如熱門商品秒殺場景，大量使用者同時搶購同一件庫存有限的商品），樂觀鎖會導致「大量的更新請求因為版本號不匹配而失敗，需要重試」如果重試邏輯設計成「立即重試」，會在極短時間內產生大量重複的失敗更新和重試請求，對資料庫造成不必要的額外負擔（大量的無效 UPDATE 語句被送到資料庫執行、又失敗），甚至可能出現「重試了很多次仍然搶不到」導致使用者體驗不佳（明明庫存還有，但因為版本衝突一直重試失敗、最終超過重試次數上限而失敗）的情況。這種場景下，直接用悲觀鎖（讓請求排隊依序處理）、或引入其他專門的高並發解決方案（如用 Redis 做庫存預扣、訊息佇列（Message Queue）削峰、或資料庫層面用 `UPDATE ... SET stock = stock - 1 WHERE stock > 0` 這種不依賴讀取-比較-寫入三步驟、而是直接用一條原子性的 SQL 完成「檢查並扣減」的方式），通常比堅持用樂觀鎖重試更合適。

**詳細解析**：這題考察對樂觀鎖「衝突機率低」這個核心假設一旦不成立時，會出現什麼問題的理解，以及在真正高併發場景下更合適的替代方案。樂觀鎖的效能優勢建立在「大多數時候不會真的發生衝突」這個假設上——如果這個假設成立，樂觀鎖確實比悲觀鎖有更好的並行度（因為不需要排隊等鎖）；但如果實際場景是「大量請求同時針對同一筆資料做修改」（如秒殺場景，可能同時有幾萬個請求都想扣減同一件商品的庫存），這時候「衝突」不是偶發的例外情況，而是幾乎必然會發生的常態，樂觀鎖的「先讀取、本地修改、最後用版本號比對寫回」這個流程，在這種場景下會導致大量的請求在最後一步「撞版本號」而失敗，如果應用程式簡單粗暴地「立即無腦重試」，會在極短的時間窗口內，對資料庫送出海量的、其中絕大多數注定失敗的 UPDATE 請求，這些請求雖然最終沒有成功修改資料，但仍然消耗了資料庫的處理資源（每一次嘗試都要重新讀取、重新比對、執行一次 UPDATE），造成資源的巨大浪費，甚至可能因為請求量過大而拖垮整個資料庫。針對這種「衝突是常態而非例外」的場景，更好的做法反而是回到「悲觀鎖」（讓請求老實排隊，一個一個依序處理，雖然單一請求的延遲會增加，但避免了大量無效重試造成的資源浪費）、或者更進一步採用專門為這種高並發競爭場景設計的方案——例如把「庫存扣減」這個操作簡化成一條原子性的 SQL（`UPDATE stock_table SET stock = stock - 1 WHERE product_id = ? AND stock > 0`，這條語句本身在資料庫內部是原子執行的，不需要應用程式自己做「讀取-判斷-寫回」三個步驟，也就不存在「讀取後、寫回前被別人搶先修改」的競爭視窗，效果上比樂觀鎖的版本號比對更直接、更沒有無謂的重試開銷），或是引入 Redis 等記憶體資料庫做「庫存預扣」（利用 Redis 單執行緒天然的原子性操作、及其遠高於資料庫的吞吐能力，先在 Redis 層面快速篩掉大部分注定搶不到庫存的請求，只有真正搶到名額的少數請求才需要進一步和資料庫互動），這些方案在真正的高併發秒殺場景下，比單純套用樂觀鎖或悲觀鎖都更合適。

**面試回答方式**：先指出核心問題——「樂觀鎖假設衝突少發生，如果實際衝突機率很高（如秒殺），會導致大量請求版本號比對失敗、觸發大量無效重試，浪費資料庫資源」。給出更合適的替代方案——「這種場景下悲觀鎖(排隊處理)可能反而更合適；更進一步可以用原子性的 UPDATE ... WHERE stock > 0 語句(不經過讀取-比較-寫回三步驟，沒有競爭視窗)，或引入 Redis 預扣庫存搭配訊息佇列削峰」。展現你理解樂觀鎖不是萬能的並行控制方案，能根據衝突機率的實際高低選擇合適的技術。

### MVCC（多版本並行控制）和樂觀鎖是同一回事嗎？

**核心答案**：不是同一回事，但兩者有相似的設計精神——**都試圖用「不加鎖」的方式來提升並行度，並在某個時間點透過比對「版本」來判斷是否有衝突**。MVCC（見 [[009-mvcc.md]]）是資料庫**引擎內部、自動運作**的機制，主要用來實現「讀取不需要加鎖、也不會被寫入阻塞」（讀寫互不干擾），它保證的是「交易隔離性」這個資料庫本身的特性，對應用程式開發者來說是透明的，不需要應用程式自己寫任何額外程式碼去維護版本資訊。**樂觀鎖**則是一種需要**應用程式或開發者自己主動實作**的並行控制「設計模式」（透過在表裡自行加上 version 欄位、自己寫 SQL 判斷版本是否匹配），主要解決的是「業務邏輯層面的更新衝突偵測」（例如兩個使用者同時編輯同一筆訂單，怎麼發現並阻止其中一方的修改覆蓋掉另一方），是應用層的責任，資料庫本身並不知道「這是一個樂觀鎖」。

**詳細解析**：這題釐清兩個經常被放在一起討論、看似相似、但作用層次完全不同的並行控制機制，展現對底層機制和應用層設計模式之間邊界的清晰認識。MVCC 是資料庫引擎（如 InnoDB）為了實現「交易隔離級別（Transaction Isolation Level）」（尤其是可重複讀、讀已提交這類要求「讀取不阻塞、且能看到某個一致性快照」的隔離級別）而設計的內部機制——它讓每一行資料在被修改時，都保留舊版本（透過 undo log 串成版本鏈），使得不同的交易可以根據自己開始的時間點（或第一次讀取的時間點），透過 ReadView 判斷應該看到哪個版本的資料，整個過程完全由資料庫引擎自動管理，應用程式開發者完全不需要知道或介入這個機制的運作，甚至可能根本不知道 MVCC 的存在，仍然可以正確地使用資料庫進行交易操作。樂觀鎖則完全是另一個層次的東西——它解決的問題不是「資料庫內部怎麼讓讀寫互不阻塞」，而是「業務邏輯上，怎麼偵測並防止『兩個並行的業務操作，基於同一份舊資料做修改，導致其中一個的修改被另一個不知情地覆蓋』這種情況」，這個問題即使在資料庫完全不支援 MVCC（比如更早期、更簡單的儲存引擎）的情況下也依然存在，且解決這個問題的「版本號欄位」和相應的 SQL 判斷邏輯，完全是應用程式開發者自己在資料表設計和程式碼裡主動加上去的，資料庫本身並不會自動提供這種「業務層面的樂觀衝突偵測」功能。之所以兩者容易被混為一談，是因為它們確實共享了「用『版本』的概念、不透過加鎖、而是在某個時刻做比對來判斷是否有變化」這個設計精神上的相似性，但一個是資料庫引擎為了交易隔離而設計的底層機制（MVCC），一個是應用開發者為了業務層面的衝突偵測而設計的上層模式（樂觀鎖），兩者運作的層次、目的、以及「維護的責任在誰身上」都完全不同——不能因為概念相似就把兩者混為一談，回答時清楚點出「MVCC 是資料庫內部自動的、樂觀鎖是應用層手動實作的」這個核心區別，是這題的關鍵得分點。

**面試回答方式**：明確回答「不是同一回事，但設計精神相似——都用『不加鎖 + 版本比對』取代加鎖來提升並行度」。點出核心區別——「MVCC 是資料庫引擎內部自動運作的機制，用來實現交易隔離性（讀寫互不阻塞），開發者不需要介入；樂觀鎖是應用層開發者自己主動實作的設計模式（自己加 version 欄位、自己寫判斷邏輯），用來解決業務層面的更新衝突偵測」。強調「一個是底層機制、一個是上層模式，運作層次和維護責任完全不同，不能混為一談」。展現你能清楚區分容易被混淆的、看似相似但本質不同的兩個並行控制概念。
