# 題目

聚簇索引和非聚簇索引（Non-Clustered Index）（二級索引）有什麼區別？什麼是「回表（Bookmark Lookup）」？怎麼避免回表？

## 核心答案

聚簇索引（Clustered Index）是「資料本身按照索引的順序存放」——InnoDB 中，資料是按「主鍵」的順序組織的，主鍵索引的葉子節點直接存「整行資料」，一張表只能有一個聚簇索引（因為資料的物理順序只能有一種）。非聚簇索引（二級索引，Secondary Index）是「除主鍵外的其他索引」——它的葉子節點不存整行資料，而是存「索引欄位值 + 主鍵值」；用二級索引查詢時，先在二級索引的 B+ 樹裡找到「主鍵值」，如果查詢需要的欄位不在二級索引裡，還要「拿著這個主鍵值，再去聚簇索引裡查一次，找到完整的行資料」——這個「二級索引查完還要再查一次聚簇索引」的過程就叫「回表」。避免回表的方法是「覆蓋索引（Covering Index）」——讓查詢需要的所有欄位都包含在這個二級索引裡（索引欄位本身 + 主鍵），這樣查完二級索引就有了全部需要的資料，不用再回表查聚簇索引。

## 詳細解析

**聚簇索引**：

- InnoDB 的資料是「按主鍵順序」物理存放的——主鍵索引的 B+ 樹葉子節點，存的就是「這一行的完整資料」（不只是主鍵值）。
- 一張表只能有一個聚簇索引（資料只能按一種物理順序排列）——通常就是主鍵；如果表沒有顯式定義主鍵，InnoDB 會找一個唯一非空索引作為聚簇索引，都沒有就自己生成一個隱藏的 rowid。

**二級索引（非聚簇索引）**：

- 除主鍵外建立的其他索引（如給 `name` 欄位建的索引），葉子節點存的是「索引欄位的值 + 對應的主鍵值」（而非整行資料）。
- 一張表可以有多個二級索引。

**回表的過程**：

假設有 `idx_name`（name 上的二級索引），查詢 `SELECT * FROM users WHERE name = 'Tom'`：

1. 先在 `idx_name` 這棵 B+ 樹裡查找 `name = 'Tom'`，找到對應的「主鍵值」（如 id=5）。
2. 因為查詢要 `SELECT *`（需要所有欄位，但 `idx_name` 只有 name 和主鍵值，沒有其他欄位），所以要「拿著 id=5，再去主鍵索引（聚簇索引）的 B+ 樹裡查一次，找到 id=5 對應的完整行資料」。
3. 這第二次查詢（拿主鍵值去聚簇索引再查一次）就是「回表」——多了一次 B+ 樹查找（可能多次磁碟 IO）。

**覆蓋索引——避免回表**：

如果查詢只需要「索引裡已經有的欄位」（不需要回表去拿其他欄位），就不用回表。例如 `SELECT name FROM users WHERE name = 'Tom'`——`idx_name` 這個二級索引本身就包含 `name`（索引欄位）和主鍵值，查詢只要 `name`查完 `idx_name` 就已經有答案了，不需要回表。設計索引時，如果能讓「常用查詢所需要的欄位都包含在索引裡（透過建立聯合索引（Composite Index）把常查詢的欄位都放進去）」，就能讓查詢「覆蓋」在索引裡完成，避免回表大幅提升效能。

## 面試回答方式

先講「聚簇索引」——InnoDB 資料按主鍵物理排序、主鍵索引葉子存整行資料、一表只能一個。然後講「二級索引」——葉子存「索引值+主鍵值」不存整行、一表可多個。「回表」是核心考點——用一個具體例子（查 name、如果查詢要其他欄位）講清「先查二級索引拿主鍵、再拿主鍵去聚簇索引查一次、這第二次就是回表」。最後講「覆蓋索引」作為避免回表的解法——「查詢只需索引裡已有的欄位就不用回表」，並舉例（查詢只選 name 或設計聯合索引包含常查欄位）。能用具體例子講清整個「查詢→回表→覆蓋索引優化」的流程，展現你理解索引結構如何影響實際查詢效能。

## 常見追問

### 為什麼 InnoDB 推薦用自增整數作為主鍵，而不是 UUID？

**核心答案**：因為 InnoDB 的資料是按「主鍵順序」物理存放的（聚簇索引），如果主鍵是「自增整數」，每次插入新資料的主鍵值都是遞增的、比之前所有的都大，新資料只需要「追加」在 B+ 樹的最後（順序寫入，不需要移動已有資料）；如果主鍵是「UUID」這種隨機值，新插入的主鍵值可能落在 B+ 樹中間的任意位置，會導致「頁分裂（page split）」——為了保持 B+ 樹和資料的順序性，可能要在中間插入、移動大量已有資料以騰出空間，甚至導致頁面利用率下降（分裂後每頁的資料變少、更碎片化）。所以自增主鍵能讓插入更高效（順序寫、少分裂），UUID 這種隨機主鍵會讓插入效能明顯下降、且索引更碎片化、佔用更多空間。

**詳細解析**：這題深入到聚簇索引「資料按主鍵物理排序」這個特性帶來的實務影響。因為聚簇索引的葉子節點（存整行資料）必須按主鍵值的順序排列，每次插入一行新資料，這行資料要「插到 B+ 樹葉子節點中正確的位置（按主鍵值排序）」。如果主鍵是自增的（1, 2 3 4...），每次插入的新主鍵值都比現有的都大，直接加在最後一個葉子節點的末尾即可，如果這個頁還有空間就直接寫入，滿了才分裂出新頁——這是「順序追加」，非常高效且頁分裂很少發生（只在頁滿時才會、且分裂位置固定在最後）。如果主鍵是隨機的（如 UUID，或雜湊值）新插入的主鍵值可能落在 B+ 樹已有資料的「中間任何位置」——例如已有主鍵 1000-2000 的資料整齊地排在某些頁裡，突然插入一個主鍵是 1500 的新行，這行必須插進「1000-2000 這個範圍對應的頁」的中間，如果這個頁已經滿了，就要「分裂」這個頁（把一部分資料移到新頁，騰出空間）這個分裂操作涉及資料的移動和頁面重新組織，開銷較大；且隨機插入導致的頻繁分裂，會讓頁面「利用率不高、碎片化」（分裂後的頁往往沒填滿），使得整個索引結構佔用更多空間、且分散在磁碟各處（不再是連續的、對快取不友善）。所以「自增主鍵」是 InnoDB 場景下的最佳實踐——保持插入的「順序性」，避免隨機插入導致的頁分裂和碎片化。

**面試回答方式**：講出「聚簇索引資料按主鍵物理排序、自增主鍵新資料的主鍵值總是最大、直接追加在最後(順序寫、少分裂)；UUID 隨機主鍵新資料可能插到中間、導致頁分裂(移動資料、開銷大)和碎片化(頁利用率低、佔更多空間)」。強調「這是為什麼推薦自增整數而非 UUID 做主鍵」。展現你理解聚簇索引的物理排序特性帶來的實務影響。

### 如果一定要用 UUID 做業務唯一標識，該怎麼設計？

**核心答案**：常見做法是「業務唯一標識用 UUID（作為一個唯一索引的欄位、用於業務層面的查詢和展示），但資料庫的主鍵（聚簇索引）仍然用自增整數（或其他遞增的 ID，如雪花演算法生成的、大致遞增的分散式 ID）」——把「聚簇索引效能」和「業務需要全域唯一標識」這兩個需求分開解決：自增主鍵保證了插入效能和聚簇索引的緊湊性；UUID 作為一個普通的二級唯一索引欄位，滿足業務上「不暴露自增 ID（避免洩漏資料量、被遍歷）、跨系統唯一」等需求。查詢時如果透過 UUID 查詢，會先查 UUID 的二級索引拿到主鍵、再回表查完整資料（多一次回表，但因為 UUID 索引查詢頻率通常不是插入頻率那麼高，可以接受）。

**詳細解析**：這題考的是「理解問題後、給出兼顧兩種需求的實務方案」。UUID 的價值——全域唯一（不同系統/表生成的 ID 不會衝突，適合分散式系統）、不暴露遞增規律（自增 ID 容易被猜測，如看到 id=1000 就知道大概有 1000 條資料，也容易被遍歷爬取，有安全和隱私考量）。但 UUID 直接做「聚簇索引的主鍵」有前面說的插入效能和碎片化問題。解法是「分離關注點」——讓資料庫層面的主鍵（聚簇索引）繼續用「遞增的」值（自增整數、或雪花演算法這類「趨勢遞增」的分散式 ID，見系統設計的分散式 ID 生成題），保證插入效能和聚簇索引的緊湊性；而業務層面需要的「全域唯一、不暴露規律」的標識，額外用一個 UUID 欄位存放，並在這個欄位上建一個普通的唯一索引（二級索引）。這樣——插入效能不受影響（主鍵仍遞增）；業務查詢可以用 UUID（透過二級索引查、多一次回表，但可接受）；對外暴露的是 UUID（不洩漏自增規律）。這種「內部用遞增 ID 做主鍵、外部暴露不透明的唯一標識」的設計在很多系統中都很常見（如很多 API 對外回傳的是一個不透明的字串 ID，內部資料庫主鍵是遞增整數）。理解這個「分離內部效能需求和外部業務需求」的設計思路，展現你有實務的資料庫設計經驗。

**面試回答方式**：講出「業務唯一標識用 UUID(額外的欄位+唯一索引)、資料庫主鍵(聚簇索引)仍用自增整數或趨勢遞增的分散式 ID(如雪花演算法)——分離『插入效能需求(主鍵遞增)』和『業務唯一標識需求(UUID 全域唯一不暴露規律)』」。點出「查 UUID 會多一次回表、但可接受、換來的是插入效能和安全性」。展現你有實務的資料庫設計經驗。

### 什麼情況下，即使查詢用了索引，還是會做全表掃描？

**核心答案**：即使有索引，優化器在以下情況可能仍選擇全表掃描（或索引失效，見 [[005-index-invalidation.md]]）——(1)**索引選擇性太低**：如果索引欄位的值「區分度很低」（如一個「性別」欄位只有男/女兩種值），透過索引查詢一半的資料，優化器會判斷「全表掃描比走索引更快」（走索引要先查索引樹再回表，如果符合條件的資料量占比很高，這些額外的樹查找和回表開銷反而比直接順序掃描全表更慢）；(2)**查詢返回的資料量占全表比例很大**：即使有索引，如果 WHERE 條件篩選出的資料是全表的大部分（如超過 20-30%，具體閾值取決於優化器的成本估算），優化器可能認為全表掃描更划算；(3)**索引失效的各種情況**（欄位上用了函式、隱式型別轉換、LIKE 以萬用字元開頭等）會讓索引用不上，退化成全表掃描。核心原則是——優化器會根據「統計資訊（資料分佈、選擇性）」估算「走索引」和「全表掃描」哪個成本更低，選擇成本更低的那個，不是「有索引就一定會用」。

**詳細解析**：這題澄清一個常見誤解——「建了索引，查詢就一定會走索引」，實際上資料庫的查詢優化器是「基於成本」做決策的，不是「有索引就無腦用」。優化器會維護欄（Guardrails）位的「統計資訊」（如這個欄位有多少種不同的值、資料分佈情況），根據這些資訊估算「如果走某個索引，大概要掃描多少行、要回表多少次」和「如果直接全表掃描，要掃描多少行」，選擇「估算成本更低」的方案。當索引的「選擇性」很低（如性別欄位只有 2 種值，走索引查 `WHERE gender = '男'` 可能要取出全表一半的資料，每筆還要回表——這比直接全表掃描更慢，因為全表掃描是連續順序讀，而索引查詢+回表可能涉及大量隨機讀取磁碟不同位置）時，優化器可能直接選擇忽略索引、做全表掃描。這也是為什麼「選擇性低的欄位（如性別、狀態這種只有幾種值的欄位）通常不適合單獨建索引」——即使建了，查詢時也可能用不上（優化器判斷不划算）。理解「索引能不能用、要不要用，是優化器基於成本估算動態決定的，不是有索引就必用」，是理解 EXPLAIN 執行計劃（Execution Plan）、以及設計「有效索引」的重要前提。

**面試回答方式**：講出「優化器是基於成本估算決策，不是有索引就必用——索引選擇性太低(如性別欄位)、或篩選出的資料佔比很大時，優化器可能認為全表掃描比走索引+大量回表更快、選擇忽略索引」。給出結論——「選擇性低的欄位通常不適合單獨建索引、即使建了也可能用不上」。展現你理解查詢優化器是動態成本決策、而非索引存在就必然被使用，這是正確理解 EXPLAIN 和索引設計的重要基礎。
