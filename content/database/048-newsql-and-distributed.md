# 題目

TiDB、CockroachDB 這類 NewSQL 解決了什麼問題？什麼時候值得用？

## 核心答案

它們要解決的是**「分庫分表的複雜度」與「單機的容量上限」之間的矛盾**。傳統的路徑是「單機 MySQL → 讀寫分離 → 分庫分表」，**而分庫分表把大量複雜度推給了應用**：跨庫 JOIN、分散式交易、全域 ID、重分片。NewSQL 的主張是**把這些複雜度收回資料庫層**——對應用而言仍然是一個支援 SQL 與 ACID 交易的資料庫，**而水平擴展由它自己處理**。

**技術上的關鍵是分散式交易與共識協定**。資料按範圍或雜湊分片存在多個節點，**每個分片用 Raft 複製到多個副本**（提供高可用與強一致），**跨分片的交易用兩階段提交或 Percolator 模型**（TiDB）保證原子性。

**代價很實在**：**延遲較高**（跨節點的共識與兩階段提交需要多次網路往返，單筆交易可能是單機 MySQL 的數倍）、**運維複雜度高**（多個元件、需要理解分散式系統的故障模式）、**資源需求大**（最小的生產部署就要多個節點）、以及**生態較新**（工具、經驗、故障案例都遠少於 MySQL）。

## 詳細解析

**「什麼時候值得」的判斷要看是否真的撞到單機上限**。現代硬體上，**單一 MySQL 實例處理幾 TB 資料與數萬 QPS 是可行的**——而多數系統從未接近這個規模。**所以 NewSQL 的適用場景是「資料量已經是幾十 TB 或寫入吞吐已經超出單機」且「無法接受分庫分表的應用複雜度」**。**如果只是「將來可能會很大」，那是過早的架構決定**，付出的是當下的延遲、成本與複雜度。

**延遲的差距值得具體理解**。單機 MySQL 的一次簡單寫入是**次毫秒級**（記憶體加上 redo 的順序寫）；NewSQL 的一次寫入需要**Raft 的多數確認**（至少一次跨節點往返）加上可能的**兩階段提交**（再多幾次），**所以是幾毫秒級**。**對於「每個請求要做十幾次資料庫操作」的應用，這個差距會累積成明顯的回應時間上升。** **緩解的方式是減少往返**（批次操作、把邏輯下推到資料庫）——**而那本身就是好的實踐，只是在 NewSQL 上變成必要的。**

**它們與「MySQL 相容」的程度需要驗證**。TiDB 宣稱高度相容 MySQL 協定，**但仍有差異**：某些函式與語法不支援、執行計畫與最佳化器的行為不同、**隔離級別的實作不同**（TiDB 的預設是快照隔離而非可重複讀）、以及某些 DDL 的行為差異。**「協定相容」讓遷移的第一步很容易（連上就能跑），但「行為相同」需要完整的測試驗證**——**而這個落差是遷移專案最常見的低估之處**。

**中間選項值得考慮**。**Vitess**（YouTube 開源，Slack、Square 等使用）在 MySQL 之上提供分片的中介層——**它保留了 MySQL 本身（成熟的引擎與生態）而在上層處理路由與重分片**。**代價是它不提供跨分片的強一致交易**（有限的支援），所以應用仍然要設計成盡量避免跨分片操作。**這是一個「用架構約束換取成熟度」的選擇**，對於「主要是單分片操作但需要水平擴展」的場景很合適。

## 面試回答方式

先給它們要解決的**矛盾**——分庫分表把複雜度推給應用，NewSQL 主張把它收回資料庫層。給技術上的關鍵（分片加 Raft 複製、跨分片用兩階段提交或 Percolator）。**代價要給具體**：延遲較高（**單機次毫秒 vs NewSQL 幾毫秒**，因為需要 Raft 的多數確認加兩階段提交）、運維複雜、資源需求大、生態較新。加分點有三個：**判斷要看是否真的撞到單機上限**——現代硬體上單一 MySQL 處理幾 TB 與數萬 QPS 是可行的，**「將來可能會很大」是過早的架構決定**；**「協定相容」不等於「行為相同」**，隔離級別的實作、最佳化器的行為、DDL 都有差異，**這個落差是遷移專案最常見的低估之處**；以及 **Vitess 是值得考慮的中間選項**——保留 MySQL 本身而在上層處理分片，**用架構約束換取成熟度**。

## 講稿

它們要解決的是分庫分表的複雜度跟單機容量上限之間的矛盾。傳統路徑是單機、讀寫分離、然後分庫分表，而分庫分表把大量複雜度推給了應用。NewSQL 的主張是把這些複雜度收回資料庫層，對應用而言仍然是一個支援 SQL 跟交易的資料庫。

技術上的關鍵是每個分片用 Raft 複製到多個副本提供強一致，跨分片的交易用兩階段提交保證原子性。

代價很實在。延遲差距值得具體說。單機的一次簡單寫入是次毫秒級，NewSQL 需要 Raft 的多數確認加上可能的兩階段提交，所以是幾毫秒級。對於每個請求要做十幾次資料庫操作的應用，這個差距會累積成明顯的回應時間上升。

什麼時候值得用，我的判斷是看有沒有真的撞到單機上限。現代硬體上，單一 MySQL 實例處理幾 TB 資料跟數萬 QPS 是可行的，而多數系統從未接近這個規模。如果只是將來可能會很大，那是過早的架構決定。

還有一個常見的低估。協定相容讓遷移的第一步很容易，連上就能跑，但行為相同需要完整的測試驗證。隔離級別的實作、最佳化器的行為、DDL 都可能不同。

## 常見追問

### 分散式交易的延遲成本具體是多少？

**核心答案**：取決於協定與部署拓撲。**單一分片的交易**只需要一次 Raft 的多數確認——**同機房大約 1 到 2 毫秒，跨可用區可能 3 到 5 毫秒**。**跨分片的交易**需要兩階段提交：prepare 階段要所有參與者確認、commit 階段再一次——**至少兩輪往返，加上每輪內部的 Raft 確認，可能是 10 毫秒以上**。**跨地域部署則以幾十毫秒計**（光速決定了跨大陸往返至少幾十毫秒，這是物理限制）。

**詳細解析**：**「跨地域的強一致」是物理上就昂貴的**——紐約到倫敦的單程光速延遲約 28 毫秒，往返 56 毫秒，**而共識協定至少需要一次往返**。**所以「全球部署且強一致」的系統，單筆寫入不可能低於幾十毫秒**——這不是實作問題而是物理問題。**理解這一點能避免不切實際的期待**，也能引導出正確的架構：**把資料就近放在使用者所在的地域**（CockroachDB 的 geo-partitioning）、或者**接受最終一致**（多數全球服務的選擇）。**「有些限制是物理的，不是工程能力的問題」是分散式系統設計中最需要先建立的認識**——而它決定了哪些需求根本不該被承諾。

**面試回答方式**：給三種情況的具體數字（單分片 1 到 2 毫秒、跨分片 10 毫秒以上、跨地域幾十毫秒）。真正的加分點是指出**跨地域的強一致是物理上就昂貴的**——用紐約到倫敦的光速往返 56 毫秒說明，**共識至少需要一次往返，所以不可能低於幾十毫秒，這不是實作問題而是物理問題**。收在認識：**有些限制是物理的**，理解它能引導出正確架構（就近部署或接受最終一致），也決定了**哪些需求根本不該被承諾**。

### NewSQL 的運維難在哪？

**核心答案**：三方面。**元件多**——TiDB 有 TiDB（SQL 層）、TiKV（儲存層）、PD（調度層）三種角色，**每一種的故障模式與監控指標都不同**。**分散式的故障模式難以推理**——網路分割、部分節點慢、以及「多數派可用但少數派落後」這類狀態，**在單機資料庫上完全不存在**。**調優的維度更多**——除了傳統的索引與查詢，還有分片的分佈、熱點的處理、以及副本的放置策略。

**詳細解析**：**「熱點」是分散式資料庫特有且最常見的問題**。按範圍分片時，**遞增的主鍵會讓所有新寫入集中在最後一個分片上**——那個節點成為瓶頸而其他節點閒置。**這與單機 MySQL 上「自增主鍵是好事」的直覺完全相反**。處理方式是**打散寫入**（用雜湊分片、或在主鍵前加一個隨機或雜湊的前綴），**代價是失去了範圍查詢的效率**。**「在單機上是優點的設計，在分散式上可能是缺點」是遷移時最需要重新檢視的一類假設**——而它們往往深植在既有的 schema 與程式碼裡，不會自動浮現。

**面試回答方式**：給三方面（元件多、分散式故障模式難推理、調優維度更多）。重點展開**熱點是分散式特有且最常見的問題**——按範圍分片時遞增主鍵讓所有寫入集中在最後一個分片，**這與單機上「自增主鍵是好事」的直覺完全相反**。給處理方式與代價。收在關鍵認識：**「在單機上是優點的設計，在分散式上可能是缺點」是遷移時最需要重新檢視的假設**，而它們往往深植在既有 schema 與程式碼裡、不會自動浮現。

### 如果不用 NewSQL，還有哪些擴展路徑？

**核心答案**：按複雜度遞增有五條。**垂直擴展**（更大的機器——**現代雲端上單機可以到數 TB 記憶體與百萬 IOPS，比多數人以為的高得多**）。**讀寫分離**（讀取擴展到多個從庫）。**快取層**（把熱點讀取擋在資料庫之前）。**垂直拆分**（不同業務用不同的資料庫，各自獨立擴展）。**水平分片**（用 Vitess 或應用層分片）。

**詳細解析**：**「垂直擴展的空間比多數人以為的大」值得強調**。雲端上的實例規格持續增長，**而擴展一台機器的成本與風險遠低於引入分散式架構**。**很多「我們需要分散式資料庫」的結論，是在還沒充分利用單機能力時就下的**——沒有優化索引、沒有加快取、沒有處理慢查詢，就直接跳到架構層面的方案。**正確的順序是「先窮盡低成本的優化，再考慮高成本的架構變更」**，因為前者的收益往往更大且風險更低。**而「垂直拆分」是一個特別被低估的中間步驟**——把不同業務的資料分到不同的資料庫，**它不引入跨庫查詢的問題（因為那些業務本來就不該互相 JOIN），卻能顯著降低單庫的負載與故障影響範圍**。

**面試回答方式**：給五條路徑並強調**垂直擴展的空間比多數人以為的大**——雲端上單機可以到數 TB 記憶體，**而擴展一台機器的成本與風險遠低於引入分散式架構**。指出**很多「需要分散式」的結論是在還沒充分利用單機能力時就下的**。收在正確的順序（先窮盡低成本優化再考慮架構變更）與**「垂直拆分」這個被低估的中間步驟**——它不引入跨庫查詢問題卻能顯著降低單庫負載與故障影響範圍。
