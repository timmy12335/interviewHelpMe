# 題目

binlog 的三種格式差在哪？半同步複製能提供什麼保證？

## 核心答案

**STATEMENT** 記錄執行的 SQL 語句本身——**體積小，但有不確定性問題**：`NOW()`、`RAND()`、`UUID()`、以及帶 `LIMIT` 而沒有明確排序的更新，在從庫重放時可能產生不同的結果。**ROW** 記錄每一列變更前後的實際值——**絕對確定，但體積大**（一個 `UPDATE ... WHERE 1=1` 影響百萬列就是百萬筆記錄）。**MIXED** 是混合：預設用 STATEMENT，遇到不安全的語句自動切成 ROW。

**現在的標準答案是 ROW**（MySQL 5.7 之後的預設）。理由不只是安全：它讓「從 binlog 還原資料」與「變更資料捕捉（CDC）」成為可能——Canal、Debezium、以及 gh-ost 都依賴 ROW 格式解析出實際的資料變更。**體積問題可以用 `binlog_row_image=MINIMAL` 緩解**（只記主鍵與被改的欄位，而非整列）。

**半同步複製**（semi-sync）讓主庫在**至少一個從庫確認收到 binlog 之後**才回應客戶端提交成功。它縮小了「主庫故障時丟失資料」的窗口，但不消除它——`AFTER_SYNC` 模式下從庫已收到但可能還沒重放，而主庫在寫 binlog 之後、收到確認之前故障仍可能有不一致。

## 詳細解析

「ROW 格式讓 CDC 成為可能」是它最被低估的價值。有了逐列的變更記錄，就能建立一整套下游生態：把資料同步到搜尋引擎、更新快取、餵給資料倉儲、觸發事件驅動的業務流程。這讓 binlog 從一個「複製的內部機制」變成了「資料變更的事實來源」，而那是很多現代架構的基礎（Outbox 模式的變體、事件溯源的實作、以及各種資料整合）。選 ROW 格式的理由，長期來看這一項可能比複製安全性更重要。

**半同步的兩種模式差別關鍵**。`AFTER_COMMIT`（5.7 之前的行為）——主庫先提交再等從庫確認，所以在等待期間其他交易已經能讀到這筆資料；如果主庫此時故障且該交易沒有複製出去，就出現了「幻讀已提交但實際丟失」的資料。`AFTER_SYNC`（5.7 起的預設）——主庫先等從庫確認再提交，避免了上述問題，代價是提交延遲增加一個網路往返。這個差別很細微但後果嚴重，是評估半同步時必須確認的設定。

**半同步的降級行為要理解**。如果所有從庫都不回應（網路問題或從庫故障），主庫會等待 `rpl_semi_sync_master_timeout`（預設 10 秒）之後降級成非同步複製並繼續服務。**這是一個可用性優先的選擇**——但它意味著半同步的保證在最需要的時候（網路異常時）恰好失效。如果業務要求「寧可不可用也不能丟資料」，需要的是「無損半同步」的配置或者共識協定（MySQL Group Replication、或者 Galera）。

**GTID 是現代複製的基礎**。它給每個交易一個全域唯一的識別碼，讓「從庫已經執行到哪裡」變成一個明確的集合而非檔案名加偏移量。這讓故障轉移大幅簡化（新主庫可以直接告訴其他從庫「我執行了哪些 GTID」）、也讓複製的監控更準確（比較 GTID 集合的差集比看 `Seconds_Behind_Master` 可靠）。**新部署應該一律開啟 GTID。**

## 面試回答方式

先給**三種格式**與各自的取捨，並指出 **ROW 是現在的標準答案**。**理由不只是安全**——**它讓 CDC 成為可能**（Canal、Debezium、gh-ost 都依賴它），這讓 binlog 從複製的內部機制變成資料變更的事實來源，而那是很多現代架構的基礎。給半同步的定位——**縮小丟失窗口但不消除**。加分點有三個：`AFTER_COMMIT` 與 `AFTER_SYNC` 的差別——前者在等待期間資料已可被讀到，主庫故障就出現「已提交但實際丟失」，這個差別細微但後果嚴重；半同步會在逾時後降級成非同步，意味著保證在最需要的時候恰好失效，要求更強就得用共識協定；以及 GTID 讓故障轉移與監控都大幅簡化，新部署應該一律開啟。

## 講稿

語句格式記錄執行的 SQL 本身，體積小但有不確定性問題。像是取當前時間、亂數、或是帶限制筆數而沒有明確排序的更新，在從庫重放時可能產生不同結果。列格式記錄每一列變更前後的實際值，絕對確定但體積大。混合格式則是預設用語句，遇到不安全的自動切成列。

現在的標準答案是列格式。但理由不只是安全，我認為最被低估的價值是它讓變更資料捕捉成為可能。有了逐列的變更記錄，就能把資料同步到搜尋引擎、更新快取、餵給資料倉儲、觸發事件驅動的流程。這讓 binlog 從一個複製的內部機制，變成了資料變更的事實來源。

半同步複製讓主庫在至少一個從庫確認收到之後才回應提交成功。它縮小了丟失資料的窗口，但不消除它。

有一個細微但後果嚴重的差別。舊的模式是主庫先提交再等確認，所以在等待期間其他交易已經能讀到這筆資料。如果主庫此時故障而該交易沒有複製出去，就出現了幻讀已提交但實際丟失的資料。新的預設是先等確認再提交，避免了這個問題。

還有一點要理解，半同步在所有從庫都不回應時會降級成非同步。這意味著它的保證在最需要的時候，也就是網路異常的時候，恰好失效。

## 常見追問

### 為什麼 STATEMENT 格式在 RC 隔離級別下不安全？

**核心答案**：因為 RC 沒有間隙鎖，所以語句的執行順序在主從之間可能不一致。在 RC 下，兩個交易可以在重疊的範圍上並行修改；binlog 是按提交順序寫的，而那個順序未必等於實際的執行順序——從庫按 binlog 順序重放時，可能得到與主庫不同的結果。這就是為什麼 MySQL 在 RC 下不允許 STATEMENT 格式（會報錯要求切換）。

**詳細解析**：這個約束是「RR 是 MySQL 預設隔離級別」的歷史原因之一——早期只有 STATEMENT 格式，而 STATEMENT 需要 RR 的間隙鎖來保證語句的可序列化順序。ROW 格式出現之後這個約束就消失了，因為 ROW 記錄的是實際的資料變更而非語句，**順序問題不再存在**。所以「MySQL 預設 RR」這個選擇，在 ROW 格式成為標準之後其實已經失去了原本的理由——而那正是前面說過「降到 RC 減少死鎖」值得考慮的背景。認出「一個預設值的歷史理由已經不成立」是重新評估技術決定的重要契機，而這類情況在長壽的系統中相當常見。

**面試回答方式**：給機制——RC 沒有間隙鎖，binlog 按提交順序寫而那未必等於執行順序，從庫重放可能得到不同結果，所以 MySQL 在 RC 下不允許 STATEMENT。真正的加分點是把它連到 **「RR 是 MySQL 預設」的歷史原因**——早期只有 STATEMENT 格式需要間隙鎖保證順序，而 ROW 格式出現後這個理由已經消失。收在觀點：認出「一個預設值的歷史理由已不成立」是重新評估技術決定的重要契機。

### 並行複製是怎麼做的？

**核心答案**：目標是讓從庫的重放不再是單執行緒。演進有三代：**基於資料庫（5.6）**——不同 schema 的交易可以並行，在單一資料庫的系統上完全沒用。**基於 group commit（5.7）**——主庫上「同一組提交」的交易在主庫必然沒有衝突，所以從庫可以並行重放，**效果取決於主庫的併發度**。**基於 WRITESET（8.0）**——主庫計算每個交易修改了哪些列的雜湊，**沒有交集的交易就能並行**，這是最有效的一代。

**詳細解析**：WRITESET 的關鍵是它「不依賴主庫的併發度」——即使主庫是單執行緒依序提交的，只要交易之間沒有修改相同的列，從庫就能並行。這讓「主庫低併發但從庫延遲高」這個常見問題得到解決（例如批次作業依序執行大量小交易）。設定是 `binlog_transaction_dependency_tracking=WRITESET` 加上從庫的 `slave_parallel_type=LOGICAL_CLOCK` 與足夠的 `slave_parallel_workers`。**但要注意它需要 ROW 格式與主鍵**——沒有主鍵的表無法計算 writeset，會退回到較保守的依賴判斷。「所有表都應該有主鍵」除了效能之外，這是另一個實際的理由，而它常常在遇到複製延遲時才被發現。

**面試回答方式**：給三代演進與各自的限制，並指出 **WRITESET 是最有效的一代**。重點展開它**不依賴主庫的併發度**——即使主庫單執行緒依序提交，只要沒有修改相同的列從庫就能並行，這解決了「主庫低併發但從庫延遲高」的常見問題。加分點是指出它**需要 ROW 格式與主鍵**，沒有主鍵的表會退回保守判斷——這是「所有表都應該有主鍵」的另一個實際理由，而它常在遇到複製延遲時才被發現。

### 怎麼準確監控複製延遲？

**核心答案**：**不要只看 `Seconds_Behind_Master`**，它有幾個已知的失真：從庫正在重放一個很久以前開始的大交易時，這個數字會持續上升但不代表落後那麼多資料；IO 執行緒與 SQL 執行緒的延遲被混在一起；網路中斷時它可能顯示 0（因為從庫沒收到新事件）。更可靠的方式有兩種：比較 GTID 集合的差集（主庫的 `gtid_executed` 減去從庫的，直接得到「還差幾個交易」），或者**用心跳表**（主庫定期寫入時間戳，從庫讀取後與當前時間相減）。

**詳細解析**：心跳表的方式最直觀也最貼近業務關心的問題——「從庫的資料有多舊」。它的實作很簡單：一個定時任務每秒在主庫更新一列 `heartbeat(id=1, ts=NOW())`，從庫查詢這一列並計算 `NOW() - ts` 就是實際的資料延遲。它的優勢是不受大交易與網路狀態的影響，也直接對應「讀寫分離時可能讀到多舊的資料」這個業務問題。 這個「用業務可理解的量測取代技術指標」的思路值得推廣——技術指標（`Seconds_Behind_Master`）需要理解它的定義才能正確解讀，而心跳延遲是任何人都能理解的。在設計監控時，優先選擇「不需要解釋就能理解」的指標，能大幅降低誤讀的機率。

**面試回答方式**：明確反對只看 `Seconds_Behind_Master` 並列出它的三個失真情況。給兩種可靠方式（GTID 差集、心跳表）。重點展開心跳表最直觀也最貼近業務問題——直接回答「從庫的資料有多舊」，實作簡單且不受大交易與網路狀態影響。收在監控設計的思路：用業務可理解的量測取代需要解釋的技術指標，優先選擇「不需要解釋就能理解」的指標能大幅降低誤讀機率。
