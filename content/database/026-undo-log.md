# 題目

InnoDB 的 undo log 有什麼用？它與 redo log 的分工是什麼？

## 核心答案

兩者的職責完全不同。**redo log 記錄「頁面被改成什麼樣子」**（物理日誌），用途是**崩潰恢復**——重啟後把已提交但還沒刷到磁碟的修改重做一遍。**undo log 記錄「怎麼把資料改回去」**（邏輯日誌），用途有兩個：**交易回滾**與 **MVCC 的一致性讀**。

undo log 的內容是**反向操作**：`INSERT` 的 undo 記錄是刪除、`DELETE` 的是插入、`UPDATE` 的是把舊值寫回。回滾時從後往前套用這些反向操作。

第二個用途才是它在日常運作中真正的角色。每一列的隱藏欄位裡有 `DB_ROLL_PTR` 指向它的 undo 記錄，而那筆 undo 又可能指向更早的版本——這串指標形成了一列的「版本鏈」。一致性讀時，如果當前版本對這個交易不可見（修改它的交易在 read view 之後才開始或還沒提交），就沿著版本鏈往回找到可見的那一版。所以 MVCC 的「多版本」不是另外存了多份資料，就是 undo log。

## 詳細解析

**undo log 的清理由 purge 執行緒負責**，而它的清理條件是「沒有任何活躍的 read view 需要這個版本」。這帶出一個關鍵的後果：一個長時間不提交的交易會讓 undo log 無法被清理——因為它的 read view 可能還需要那些舊版本。在 MySQL 5.7 之前，undo 表空間無法收縮，這會讓資料檔案永久膨脹；8.0 之後支援 undo 表空間的截斷，但長交易期間仍然會持續增長。

「歷史清單長度」（History list length）是應該被監控的指標。`SHOW ENGINE INNODB STATUS` 裡的這個數字表示尚未被 purge 的 undo 記錄數量，它持續上升就代表有長交易或 purge 跟不上。這個指標比「有沒有慢查詢」更早反映問題——因為長交易本身可能完全不慢，它只是開著沒有提交。

版本鏈的長度直接影響讀取效能。一列被頻繁更新且有長交易存在時，版本鏈可能累積到成千上萬個版本，而一致性讀必須從最新版沿著鏈往回走直到找到可見的那一版——這讓一個看起來很簡單的查詢變得極慢。這是「明明有索引但查詢突然變慢」的一個少見但真實的成因，而且症狀會隨著長交易結束而消失，非常難重現。

回滾的成本與交易的大小成正比，而且通常比執行更貴。一個修改了一百萬列的交易，回滾時要逐列套用反向操作，**可能比原本的執行還久**——而且回滾期間持有的鎖不會釋放。這是「不要做超大交易」最實際的理由之一：不只是鎖持有時間長，一旦需要回滾（或崩潰後的恢復回滾），中斷時間會非常可觀。

## 面試回答方式

先給**職責的區分**：redo 是物理日誌、記錄「改成什麼樣子」、用於崩潰恢復；undo 是邏輯日誌、記錄「怎麼改回去」、用於回滾與 MVCC。接著把**第二個用途講成重點**——每列的隱藏欄位指向 undo 記錄形成版本鏈，一致性讀沿鏈往回找可見版本，所以 MVCC 的多版本不是另外存資料，就是 undo log。加分點有三個：**長交易會讓 undo 無法被清理**（purge 的條件是沒有活躍 read view 需要它），5.7 之前 undo 表空間還無法收縮；**「歷史清單長度」應該被監控**，它比慢查詢更早反映問題，因為長交易本身可能完全不慢，只是開著沒提交；以及版本鏈過長會讓簡單查詢變極慢，而症狀隨長交易結束消失、非常難重現。

## 講稿

兩者的職責完全不同。redo log 是物理日誌，記錄頁面被改成什麼樣子，用途是崩潰恢復。undo log 是邏輯日誌，記錄怎麼把資料改回去，用途有兩個，交易回滾跟多版本併發控制。

第二個用途才是它在日常運作中真正的角色。每一列的隱藏欄位裡有一個指標指向它的 undo 記錄，而那筆 undo 又可能指向更早的版本，這串指標形成了一列的版本鏈。一致性讀的時候，如果當前版本對這個交易不可見，就沿著版本鏈往回找到可見的那一版。

所以多版本併發控制的多版本，不是另外存了多份資料，它就是 undo log。

這帶出一個很重要的後果。undo 的清理條件是沒有任何活躍的讀取視圖需要這個版本，所以一個長時間不提交的交易會讓 undo 無法被清理，資料檔案持續膨脹。

我會監控歷史清單長度這個指標，它比有沒有慢查詢更早反映問題。因為長交易本身可能完全不慢，它只是開著沒有提交。

而且版本鏈太長會讓一個看起來很簡單的查詢變得極慢，症狀還會隨著長交易結束而消失，非常難重現。

## 常見追問

### 為什麼 redo log 是物理的、undo log 是邏輯的？

**核心答案**：因為它們要滿足的需求不同。**redo 需要「快且冪等」**——崩潰恢復時可能要重放大量記錄，而且同一筆記錄可能被重放多次（恢復過程本身也可能崩潰）；物理日誌（記錄某個頁的某個偏移量被改成什麼位元組）重放起來就是直接覆寫，天然冪等且不需要理解資料的語意。**undo 需要「能表達反向操作」**——而反向操作必須是邏輯的（「把這一列的 name 欄位改回舊值」），因為回滾時頁面的物理佈局可能已經因為其他交易的修改而完全不同了。

**詳細解析**：這個差異解釋了一個容易困惑的點：為什麼 undo log 本身也需要 redo 保護。undo log 是寫在資料頁裡的（undo 表空間也是頁的集合），**所以修改 undo log 這件事本身也要記 redo**——否則崩潰後 undo log 可能不完整，回滾就做不了。這形成一個順序：先寫 undo 的 redo、再寫 undo、再改資料頁、再寫資料頁的 redo。理解「undo 也受 redo 保護」是理解 InnoDB 崩潰恢復完整流程的關鍵，也是很多人只知道「redo 重做、undo 回滾」卻說不清楚兩者如何協作的原因。

**面試回答方式**：從**需求推導形式**——redo 需要快且冪等，物理日誌重放就是直接覆寫、天然冪等；undo 需要表達反向操作，而回滾時頁面的物理佈局可能已經完全不同，所以必須是邏輯的。真正的加分點是**undo log 本身也需要 redo 保護**——它寫在資料頁裡，修改它也要記 redo，否則崩潰後 undo 不完整就無法回滾；並給出順序（先寫 undo 的 redo、再寫 undo、再改資料頁、再寫資料頁的 redo）。

### 崩潰恢復時 redo 與 undo 怎麼協作？

**核心答案**：分兩個階段。**第一階段（redo 重做）**——從最後一個檢查點開始，把所有 redo 記錄無條件重放，不管那個交易最後有沒有提交。這讓資料頁回到「崩潰那一刻的狀態」，包含了未提交交易的修改。**第二階段（undo 回滾）**——掃描此時的交易狀態，找出所有「崩潰時尚未提交」的交易，用它們的 undo log 回滾掉。

**詳細解析**：「先無條件重做、再選擇性回滾」這個順序常讓人困惑——為什麼要先把未提交的修改也重做一遍再回滾掉？原因是redo 是物理日誌，它不知道哪些屬於哪個交易的語意，只能按順序全部重放；而且未提交交易的 undo log 本身也在 redo 裡，必須先重做才能拿到完整的 undo 用來回滾。**這是 ARIES 恢復演算法的核心思路**（Analysis、Redo、Undo 三階段），被幾乎所有主流資料庫採用。能說出「這是 ARIES 的思路」以及「先重做才能得到完整的 undo」這個因果，比只背兩個階段有價值得多。

**面試回答方式**：給兩個階段並強調第一階段是**無條件重放、不管有沒有提交**。重點解釋為什麼是這個順序：redo 是物理日誌不知道交易語意只能全部重放，而且未提交交易的 undo 本身也在 redo 裡，必須先重做才能拿到完整的 undo 用來回滾。收在定位：這是 ARIES 恢復演算法的思路，被幾乎所有主流資料庫採用。

### 長交易還有哪些危害？

**核心答案**：四類。**undo 膨脹與版本鏈變長**（前面提過）。**鎖持有時間長**——交易期間取得的行鎖直到提交才釋放，阻塞其他交易並增加死鎖機率。**複製延遲**——大交易在主庫執行完才寫 binlog，從庫要重放整個交易，延遲會突然跳高。**回滾成本高**——如果最後失敗或需要中斷，回滾可能比執行還久且期間不釋放鎖。

**詳細解析**：最陰險的是「長交易不一定是慢查詢」。一個交易可能執行了一個很快的 `SELECT` 然後就開著不動（應用在等待一個外部 API 回應、或者一個沒有正確關閉的連線），它在慢查詢日誌裡完全不會出現，但它會持續阻止 undo 的清理。**排查的手段是 `information_schema.innodb_trx` 裡的 `trx_started`**——找出開始時間很久的交易。**防護方式有兩層**：應用層面，交易裡絕對不要有外部呼叫或使用者互動（這是最重要的一條）；資料庫層面，設定合理的 `innodb_lock_wait_timeout` 與交易逾時，讓卡住的交易被強制中止而不是無限期地存在。

**面試回答方式**：給四類危害並各配機制。重點強調最陰險的是「長交易不一定是慢查詢」——執行一個很快的查詢然後開著不動（等外部 API、或連線沒關），慢查詢日誌完全看不到但持續阻止 undo 清理。給出排查手段（`innodb_trx` 的 `trx_started`）與兩層防護：交易裡絕對不要有外部呼叫或使用者互動（最重要的一條）、以及設定交易逾時讓卡住的交易被強制中止。
