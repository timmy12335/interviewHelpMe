# 題目

MySQL 的索引為什麼用 B+ 樹？和二元查找樹、紅黑樹、雜湊索引比，各有什麼優劣？

## 核心答案

核心原因是「B+ 樹能最大程度減少磁碟 IO 次數」——資料庫索引存在磁碟上，效能瓶頸在磁碟 IO 次數（而非 CPU 計算），B+ 樹的「多路、矮胖」結構讓每個節點對應一個磁碟頁、每層只需一次 IO、樹的層數極少（幾層就能索引海量資料）。相比之下——**二元查找樹**每個節點只有 2 個子節點，資料量大時樹會很「高」（層數多，接近 O(n) 在最壞情況、平均 O(log₂n) 但底數是 2，層數遠多於 B+ 樹），需要更多次磁碟 IO；**紅黑樹**（平衡二元樹）雖然保證了 O(log n) 且不會退化，但仍是「二元」的，層數比 B+ 樹（多路）多得多，磁碟 IO 次數更多，且紅黑樹常用於「記憶體」中的資料結構（如 Java 的 HashMap 紅黑樹化）而非磁碟索引；**雜湊索引**能做到 O(1) 的等值查詢，但「不支援範圍查詢和排序」（雜湊打亂了順序），這是資料庫查詢的常見需求，所以不適合做通用索引。

## 詳細解析

**核心比較維度——磁碟 IO 次數（樹的高度）**：

資料庫的索引通常無法完全放入記憶體（資料量大），大部分要存在磁碟上，每次查詢一個節點的內容都可能要一次磁碟 IO（如果沒被快取在記憶體）。所以「樹的高度（層數）」直接決定了「一次查詢最多需要幾次磁碟 IO」，高度越低越好。

- **B+ 樹（多路）**：一個節點能存幾百上千個 key（對應一個磁碟頁），所以即使索引十億級資料，樹高只有 3-4 層——查詢只需 3-4 次磁碟 IO。
- **二元查找樹 / 紅黑樹（二路）**：每個節點只有 2 個子節點，索引 n 條資料需要約 log₂(n) 層——n 是十億級時，log₂(10億) ≈ 30 層，需要 30 次磁碟 IO！比 B+ 樹的 3-4 次多了近 10 倍，效能差距巨大。

**雜湊索引的問題——不支援範圍查詢**：

雜湊索引把 key 雜湊成一個雜湊值、直接定位，等值查詢（`WHERE id = 5`）是 O(1)，比 B+ 樹的 O(log n) 更快。但問題是——雜湊打亂了原本資料的順序，雜湊索引裡的資料不是有序的，所以「範圍查詢（`WHERE age > 20`）」、「排序（`ORDER BY`）」、「模糊比對前綴（`LIKE 'abc%'`）」這些需要「順序性」的操作，雜湊索引完全無能為力（只能全表掃描）。而資料庫的查詢中，範圍查詢、排序極其常見，所以雜湊索引不適合作為通用索引（InnoDB 用 B+ 樹作為主要索引結構，雖然也有自適應雜湊索引作為輔助優化）。

**為什麼不用「B 樹」（不是 B+ 樹）**：B 樹和 B+ 樹很像（都是多路平衡樹），差別是——B 樹的「非葉子節點也存實際資料」，而 B+ 樹的非葉子節點「只存 key」。這個差別讓 B+ 樹的非葉子節點能容納更多 key（不用存資料，同樣大小能塞更多 key），樹更矮胖、IO 次數更少；且 B+ 樹的葉子節點鏈結串列讓範圍查詢更高效（B 樹的資料分散在各層、範圍查詢要跨層走）。所以資料庫選 B+ 樹而非 B 樹。

## 面試回答方式

核心論點是「磁碟 IO 次數 = 樹的高度、B+ 樹多路矮胖 IO 少」——這一句話要能講清楚。然後逐一對比——二元查找樹/紅黑樹（層數多、IO 次數多，用具體數字如「十億資料 log₂ 約 30 層 vs B+ 樹 3-4 層」對比最有説服力）、雜湊索引（O(1) 快但不支援範圍查詢/排序，資料庫需求常見範圍查詢所以不適合）。能補充「B 樹 vs B+ 樹」的差異（非葉子節點是否存資料）作為加分。用具體的層數數字對比是這題最有力的論證方式，展現你不只知道結論還能量化説明差距。

## 常見追問

### InnoDB 的自適應雜湊索引是什麼？它和普通雜湊索引有什麼不同？

**核心答案**：InnoDB 的「自適應雜湊索引（Adaptive Hash Index，AHI）」是 InnoDB 在 B+ 樹索引之上「自動、額外」建立的一層雜湊索引優化——當 InnoDB 發現「某些 B+ 樹索引的頁被非常頻繁地以相同的方式（等值查詢）存取」時，會自動為這些熱點資料在記憶體裡建立一個雜湊索引，讓後續對這些資料的等值查詢能直接 O(1) 命中（不用再走 B+ 樹的多層查找）。它和「普通雜湊索引」的不同是——它不是使用者建立的、是 InnoDB「自動、透明」地根據存取模式決定要不要建立和維護的，且只是 B+ 樹的「輔助加速層」（B+ 樹本身仍然存在，AHI 只是給熱點資料加速），不像普通雜湊索引是「替代」B+ 樹的獨立索引結構。

**詳細解析**：這題展現「B+ 樹和雜湊索引不是非此即彼、可以結合」的理解。AHI 的動機是——B+ 樹的等值查詢需要「從根到葉」多次比較（雖然層數少，但仍需要幾次比較和可能的 IO），如果某些資料被非常頻繁地做「完全相同的等值查詢」，每次都走一遍 B+ 樹有點浪費；AHI 讓 InnoDB 監控查詢模式，一旦發現某個索引頁被頻繁存取，就把這個頁的內容也做一份雜湊索引放進記憶體的「自適應雜湊索引快取」，之後對這些資料的等值查詢可以直接雜湊命中、跳過 B+ 樹的多層查找。這是完全自動、透明的（使用者不用配置任何東西，InnoDB 自己判斷），且只加速「等值查詢」（雜湊索引的固有限制——不支援範圍查詢），對範圍查詢無效（仍然走 B+ 樹）。理解 AHI 展現你對 InnoDB 底層優化有深入了解，也理解「B+ 樹和雜湊各有所長、InnoDB 結合兩者取長補短」。

**面試回答方式**：講出「AHI 是 InnoDB 在 B+ 樹之上自動建立的記憶體雜湊層——監控查詢模式、對頻繁被等值查詢的熱點資料自動建雜湊索引加速、只加速等值查詢不影響範圍查詢仍走 B+ 樹」。強調「自動透明、是 B+ 樹的輔助加速而非替代」。展現你理解 InnoDB 如何結合 B+ 樹和雜湊索引的優點。

### 為什麼說紅黑樹更適合記憶體中的資料結構，而不適合做磁碟索引？

**核心答案**：因為紅黑樹是「二元」樹——每個節點只有 2 個子節點，索引大量資料時樹的「層數」會很多（log₂n），如果放在記憶體中，這不是問題（記憶體隨機存取、沒有磁碟 IO 那樣的高延遲代價，多幾層的比較開銷微不足道）；但如果放在磁碟上，每一層都可能對應一次「磁碟 IO」（延遲是記憶體存取的幾個數量級），層數多意味著磁碟 IO 次數多，效能會嚴重下降。而 B+ 樹的「多路」設計正是為了在磁碟場景下「用更寬的節點（一個磁碟頁的容量）換取更少的層數（更少的磁碟 IO）」，這個設計的收益只有在「存取延遲高的媒介（磁碟）」上才體現得出來——在記憶體中，紅黑樹的簡單性（不需要像 B+ 樹那樣管理多路節點的複雜分裂合併）反而更有優勢。這也是為什麼 Java 的 HashMap 用紅黑樹處理雜湊衝突（記憶體結構）、而 MySQL 索引用 B+ 樹（磁碟結構）。

**詳細解析**：這題揭示了「資料結構選型要考慮儲存媒介的特性」這個核心原則，也連結到了 JVM 中 HashMap 用紅黑樹的知識點做對比。記憶體和磁碟最根本的差異是「隨機存取的延遲」——記憶體存取任何位置的延遲幾乎相同、且極低（奈秒級）；磁碟（尤其機械磁碟）存取有「尋道時間」，且延遲遠高於記憶體（毫秒級，慢了幾個數量級），但「一旦定位到某個位置，讀取一整頁的資料」和「只讀一小部分」耗時差不多（傳輸速度遠快於尋道時間）。這個特性決定了資料結構設計的取捨——在記憶體中，多走幾層樹（紅黑樹）的額外比較開銷微不足道（都是奈秒級），所以紅黑樹「結構簡單、實現容易」的優勢就更重要（Java 的 TreeMap、HashMap 的紅黑樹化都是記憶體結構，用紅黑樹合理）；但在磁碟中，每多一層樹「可能」就多一次磁碟 IO（毫秒級延遲），層數的差異（B+ 樹 3-4 層 vs 紅黑樹 30 層）會被放大成巨大的效能差距，所以磁碟索引必須用「多路、矮胖」的 B+ 樹，用「一次讀一整頁（利用磁碟一次讀一頁成本不高的特性）」的方式把層數壓到最低。理解「儲存媒介的存取特性決定了最優的資料結構」，展現你能從更底層的原理理解不同場景下的資料結構選型，這是連結 JVM 知識和資料庫知識的一個很好的例子。

**面試回答方式**：講出「記憶體隨機存取延遲低且均勻、多幾層樹的開銷微不足道，紅黑樹的簡單性優勢更重要；磁碟存取延遲高(尋道)、且一次讀一頁成本不高，每多一層樹可能多一次昂貴的磁碟 IO，所以要用多路矮胖的 B+ 樹壓低層數」。連結到「Java HashMap 用紅黑樹(記憶體結構)、MySQL 索引用 B+ 樹(磁碟結構)」的對比。展現你理解儲存媒介特性決定資料結構選型這個更底層的原則。

### 全文檢索為什麼不用 B+ 樹索引，而要用倒排索引？

**核心答案**：因為 B+ 樹索引適合「精確匹配或範圍匹配某個欄位的值」（如 `WHERE id = 5`、`WHERE age > 20`），但全文檢索的需求是「在一段文字內容中，查詢包含某個關鍵字的所有記錄」——這是「內容包含關係」的查詢，不是「欄位值的大小/範圍比較」。B+ 樹按「整個欄位值」排序建索引，無法有效支援「在文字內容中搜尋某個詞」這種需求（除非整個欄位剛好等於這個詞，但全文檢索要的是「詞出現在文字任何位置」）。倒排索引（Inverted Index）則是「反過來」建索引——不是「按文件建索引指向詞」，而是「按每個『詞』建索引，記錄這個詞出現在哪些文件（及位置）」，查詢時直接透過詞找到包含它的所有文件，這正是全文檢索需要的「以詞找文件」的存取模式。

**詳細解析**：這題透過對比展現「不同的查詢模式需要不同的索引結構」，是索引選型的一般性原則的延伸。B+ 樹索引的本質是「給定一個或一個範圍的『欄位值』，快速找到對應的記錄」——它假設你查詢的是「這個欄位的整個值」（相等或範圍比較）。但全文檢索的查詢模式完全不同——你不是查「某個欄位等於某段完整文字」，而是查「這段文字（一篇文章、一段描述）裡面，有沒有包含某個關鵱字」，這是「內容的一部分是否匹配」，B+ 樹索引對此無能為力（用 B+ 樹索引配合 `LIKE '%關鍵字%'` 這種前後都有萬用字元的模糊查詢，索引完全用不上，只能全表掃描，效能極差）。倒排索引解決這個——它預先把每篇文件「分詞」（拆成一個個詞），然後建立「詞 → 出現在哪些文件（及位置）」的映射（這就是「倒排」，正常是「文件 → 詞」，倒排索引是「詞 → 文件」）。查詢「找出包含『資料庫』這個詞的所有文件」時，直接在倒排索引裡查「資料庫」這個詞，立刻拿到所有包含它的文件列表，非常高效。這也是為什麼全文檢索需要專門的引擎（如 Elasticsearch，底層核心正是倒排索引），而不是靠關聯式資料庫的 B+ 樹索引來做。理解「B+ 樹索引和倒排索引服務於不同的查詢模式（欄位值比較 vs 內容包含）」，展現你對索引選型有超越單一結構的全面認識。

**面試回答方式**：講出「B+ 樹適合『欄位值的精確/範圍匹配』、全文檢索需要『內容包含某詞』這種完全不同的查詢模式、B+ 樹對此無能為力(LIKE '%詞%' 用不上索引)」。説明「倒排索引反過來——建『詞→文件』的映射、查詢時直接以詞找文件、高效支援全文檢索」。點出「這是 Elasticsearch 等全文搜尋引擎的核心結構」。展現你理解不同查詢模式需要不同索引結構的一般性原則。
