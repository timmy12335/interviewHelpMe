# 題目

什麼是索引下推（ICP）？它與 MRR 各自解決了回表的什麼問題？

## 核心答案

兩者都在優化**回表**——用二級索引找到主鍵後，再回聚簇索引取完整資料的那一步。

**索引條件下推（Index Condition Pushdown）** 解決的是**「回表次數太多」**。沒有 ICP 時，儲存引擎只用能走索引的那部分條件篩選，其餘條件由 Server 層在回表之後才判斷——於是很多列被回表取出來又被丟掉。ICP 讓儲存引擎在索引上就評估那些「索引裡有欄位但無法用於範圍掃描」的條件，不符合的直接跳過，**大幅減少回表次數**。`EXPLAIN` 的 `Extra` 出現 `Using index condition` 就是它生效了。

**多範圍讀取（Multi-Range Read）** 解決的是**「回表的順序太亂」**。二級索引給出的主鍵是按索引順序排的，**對聚簇索引而言那是隨機的**——於是回表變成大量隨機 IO。MRR 先把要回表的主鍵**收集到一個緩衝區並排序**，再按主鍵順序批次回表，**把隨機 IO 變成接近順序的 IO**。`Extra` 裡的 `Using MRR` 表示它生效。

**兩者是互補的**：ICP 減少回表的「次數」，MRR 改善回表的「順序」。

## 詳細解析

**ICP 的適用條件很具體**：條件涉及的欄位**必須在索引中**（否則引擎層看不到那個欄位），而且**不能用於索引的範圍定位**（否則本來就會被用上）。典型的例子是聯合索引 `(a, b, c)` 上的查詢 `WHERE a = 1 AND c LIKE '%x%'`——`a` 用於定位，`c` 無法用於範圍掃描（前綴是萬用字元），但 `c` 在索引裡，所以 ICP 可以在索引上先篩掉不符合的。沒有 ICP 的話，所有 `a = 1` 的列都要回表，然後才發現大部分 `c` 不符合。

**MRR 的收益依儲存媒介而異**。在機械硬碟上，把隨機 IO 變成順序 IO 的收益是數量級的；**在 SSD 上收益小得多**（隨機讀取的懲罰輕），但仍然存在（減少了讀取的頁數，因為排序後相鄰的主鍵可能在同一頁）。**MySQL 預設對 MRR 較保守**（`optimizer_switch` 裡的 `mrr_cost_based=on` 讓最佳化器依成本決定要不要用），**而成本模型在 SSD 上未必準確**——這是「最佳化器的假設可能與你的硬體不符」的一個具體例子。

這兩個優化的存在說明了一件事：回表是二級索引查詢的主要成本。所以覆蓋索引（索引裡就有全部需要的欄位，完全不必回表）永遠是最好的——ICP 與 MRR 都只是「不得不回表時的減損」。設計索引時應該先問「能不能做成覆蓋索引」，這比任何回表優化都有效。

`Extra` 欄位是判斷這些優化的直接證據，而幾個容易混淆的值要分清：**`Using index`** 是覆蓋索引（完全不回表，最好）；**`Using index condition`** 是 ICP（有回表但被減少了）；**`Using where`** 是 Server 層做了額外過濾（**可能意味著有優化空間**）；**`Using filesort`** 是需要額外排序；**`Using temporary`** 是用了臨時表。**看懂 `Extra` 比看懂 `type` 更能發現問題**，因為 `type` 只說明了存取方式，`Extra` 說明了額外付出的代價。

## 面試回答方式

先指出**兩者都在優化回表**，再分別給出它們解決的問題：**ICP 減少回表次數**（讓引擎層在索引上就評估那些「索引裡有但無法用於範圍掃描」的條件），**MRR 改善回表順序**（收集主鍵排序後批次回表，把隨機 IO 變成接近順序）。用 `(a, b, c)` 索引上 `WHERE a = 1 AND c LIKE '%x%'` 這個具體例子說明 ICP 的適用條件。加分點有三個：**MRR 的收益依儲存媒介而異**，SSD 上小得多，而 MySQL 的成本模型在 SSD 上未必準確——這是「最佳化器的假設可能與硬體不符」的具體例子；這兩個優化的存在說明回表是主要成本，所以**覆蓋索引永遠是最好的**，設計索引時該先問「能不能做成覆蓋」；以及**`Extra` 的幾個值要分清**（`Using index` 是覆蓋、`Using index condition` 是 ICP、`Using where` 可能意味著有優化空間），**看懂 `Extra` 比看懂 `type` 更能發現問題**。

## 講稿

兩者都在優化回表，也就是用二級索引找到主鍵之後、再回聚簇索引取完整資料的那一步。

索引下推解決的是回表次數太多。沒有它的時候，儲存引擎只用能走索引的那部分條件篩選，其餘條件由上層在回表之後才判斷，於是很多列被取出來又被丟掉。下推讓引擎在索引上就評估那些條件，不符合的直接跳過。

舉個例子。聯合索引是 a、b、c，查詢是 a 等於一而且 c 像某個模式。c 因為前綴是萬用字元無法用於定位，但 c 在索引裡。有下推的話就能在索引上先篩掉不符合的，沒有的話所有 a 等於一的列都要回表。

多範圍讀取解決的是回表的順序太亂。二級索引給出的主鍵是按索引順序排的，對聚簇索引而言那是隨機的。它先把主鍵收集起來排序，再按主鍵順序批次回表，把隨機 IO 變成接近順序的。

不過我想強調，這兩個優化的存在說明回表是二級索引查詢的主要成本。所以覆蓋索引永遠是最好的，它完全不必回表。設計索引時應該先問能不能做成覆蓋索引，這比任何回表優化都有效。

## 常見追問

### 覆蓋索引的代價是什麼？

**核心答案**：**索引變大**。把更多欄位放進索引以達成覆蓋，會讓索引的每一項變寬——索引檔案變大、能快取在記憶體的索引頁變少、寫入時要維護的資料變多。所以它不是免費的，是「用空間與寫入成本換讀取成本」。判斷划不划算要看這個查詢的頻率與重要性。

**詳細解析**：MySQL 8 的「函式索引」與「降序索引」擴大了覆蓋索引的適用範圍，而 PostgreSQL 的 `INCLUDE` 子句提供了一個更精確的工具——它讓欄位只出現在葉節點（用於覆蓋）而不進入索引的排序鍵，於是索引的內部節點保持小巧，只有葉節點變寬。MySQL 沒有直接對應的語法（把欄位加在聯合索引最後大致等效，但那些欄位會進入排序鍵而影響索引結構）。這個差異在需要覆蓋很多欄位時很明顯。 更一般的判斷是：覆蓋索引適合「欄位少、查詢頻繁、值不常變」的組合；如果要覆蓋的欄位很多或很寬（例如一個 text 欄位），那通常表示應該調整查詢或表結構，而不是硬做覆蓋。

**面試回答方式**：給代價（索引變大、快取的索引頁變少、寫入維護成本上升）並定位成「用空間與寫入換讀取」。加分點是提到 PostgreSQL 的 `INCLUDE` 子句——讓欄位只在葉節點用於覆蓋而不進入排序鍵，MySQL 沒有直接對應。收在判斷：覆蓋索引適合「欄位少、查詢頻繁、值不常變」，要覆蓋很多或很寬的欄位時通常該調整查詢或表結構而非硬做。

### 為什麼有時候最佳化器不用索引，寧可全表掃描？

**核心答案**：因為最佳化器估算「走索引的總成本」高於「全表掃描」。走索引的成本包含索引掃描加上**回表的隨機 IO**，而全表掃描是順序讀。當要回表的列數超過一定比例（經驗上大約 20% 到 30%）時，全表掃描反而更快——因為順序讀的每頁成本遠低於隨機讀。這通常是最佳化器的正確判斷，不是 bug。

**詳細解析**：**但它依賴統計資訊的準確性**。如果統計資訊過期（表剛剛大量寫入但還沒重新分析），最佳化器可能嚴重誤估選擇性而做出錯誤的決定。**`ANALYZE TABLE` 會重新採樣統計資訊**，而 `innodb_stats_persistent_sample_pages` 控制採樣的頁數——採樣太少在資料分佈不均勻的表上會產生很差的估算。排查「為什麼不走索引」的順序應該是：先看 `EXPLAIN` 的 `rows` 估算與實際筆數的差距（MySQL 8 的 `EXPLAIN ANALYZE` 直接給出兩者的對比）、差距大就先 `ANALYZE TABLE`、仍然不對再考慮 hint（`FORCE INDEX`）。**但 hint 應該是最後手段**——它把最佳化器的決定寫死了，資料分佈變化後可能反而更糟。

**面試回答方式**：給正確的機制——走索引的成本包含回表的隨機 IO，超過一定比例（約 20% 到 30%）時全表掃描更快，並強調這通常是正確判斷而非 bug。展開它**依賴統計資訊的準確性**，並給排查順序：看 `EXPLAIN` 的 `rows` 估算與實際的差距（MySQL 8 的 `EXPLAIN ANALYZE` 直接對比）、先 `ANALYZE TABLE`、最後才用 hint。強調 **hint 是最後手段**，因為它把決定寫死了、資料分佈變化後可能更糟。

### 索引下推對哪些查詢沒有幫助？

**核心答案**：三種情況。**條件涉及的欄位不在索引裡**——引擎層看不到那個欄位，只能回表後由 Server 層判斷。**條件本來就能用於索引定位**——那它會被用作範圍條件，不需要下推。**覆蓋索引的查詢**——本來就不回表，沒有可減少的東西。

**詳細解析**：第一種情況是最常見的，而它指出了一個索引設計的機會：如果某個過濾條件經常出現但不在索引裡，把它加進索引（即使它無法用於定位）也能讓 ICP 生效，減少回表。這是一個容易被忽略的索引設計技巧——索引欄位不一定要能用於範圍定位才有價值，**能用於下推過濾也是價值**。例如 `WHERE status = 'ACTIVE' AND name LIKE '%foo%'`，索引 `(status)` 只能定位；索引 `(status, name)` 則讓 `name` 的模糊比對能在索引上完成，**回表的只剩真正符合的列**。判斷值不值得的方式是看選擇性：如果 `name LIKE` 能過濾掉大部分列，加進索引的收益很大；如果過濾不掉多少，那只是讓索引變寬。

**面試回答方式**：給三種沒有幫助的情況。真正的加分點是把第一種轉成**索引設計的機會**：索引欄位不一定要能用於範圍定位才有價值，能用於下推過濾也是價值。用 `WHERE status = 'ACTIVE' AND name LIKE '%foo%'` 的例子對比 `(status)` 與 `(status, name)` 兩個索引。收在判斷方式：**看選擇性**——能過濾掉大部分列就值得，過濾不掉多少就只是讓索引變寬。
