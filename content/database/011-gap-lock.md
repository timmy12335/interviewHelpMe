# 題目

什麼是間隙鎖（Gap Lock）？Next-Key Lock 是什麼？它們怎麼防止幻讀（Phantom Read）？

## 核心答案

間隙鎖（Gap Lock）是 InnoDB 特有的一種鎖，鎖定的不是「一行具體的記錄」，而是「兩個索引記錄之間的間隙（範圍）」，作用是「阻止其他交易在這個間隙裡插入新的資料」。Next-Key Lock 是「記錄鎖（鎖住行本身）+ 間隙鎖（鎖住這行前面的間隙）」的組合，是 InnoDB 在可重複讀隔離級別下，做「當前讀」操作（如 `SELECT ... FOR UPDATE`）時預設使用的鎖。它們防止幻讀的原理是——普通的行鎖只能鎖住「已經存在的行」，無法阻止「新行插入到符合條件的範圍內」；間隙鎖直接把這個「範圍」也鎖住，讓其他交易的 INSERT 操作，如果落在這個被鎖定的間隙內，就會被阻塞，從物理上杜絕了幻影行的產生。

## 詳細解析

**間隙鎖的作用**：假設一個索引裡有值 10 和 20 這兩筆記錄，"10 和 20 之間"就是一個間隙（可能有 11、12...19 這些值還沒有對應的記錄）。如果一個交易查詢 `WHERE id > 10 AND id < 20 FOR UPDATE`，InnoDB 會鎖定「10 到 20 之間的這整個間隙」，這意味著——即使 15 這個具體的值目前在表裡不存在（沒有記錄），其他交易也「不能」`INSERT` 一筆 `id=15` 的新記錄（會被間隙鎖阻塞），因為這會落在被鎖定的間隙裡。

**Next-Key Lock = 記錄鎖 + 間隙鎖**：這是 InnoDB 在 RR 隔離級別下、對「等值查詢」和「範圍查詢」做當前讀時，預設使用的鎖策略——它鎖定的範圍是「某條記錄本身」加上「這條記錄前面（左側）的那個間隙」，形成一個「左開右閉」的區間。例如索引有 10、20 兩筆記錄，對 20 加 next-key lock，鎖定的範圍是 `(10, 20]`——既鎖住了 20 這條記錄本身，也鎖住了 10 到 20 之間的間隙。

**為什麼能防止幻讀**：幻讀的產生根源是「INSERT 插入了符合查詢條件的新行」。行鎖（記錄鎖）只能鎖住「已經存在的、被查到的行」，對「還不存在的、之後可能被插入」的行毫無辦法；間隙鎖直接封鎖了「兩個記錄之間可能插入新資料的空間」，讓任何想在這個範圍內插入資料的操作都被阻塞，直到持有間隙鎖的交易提交或回滾。所以 Next-Key Lock（記錄鎖 + 間隙鎖）能同時保護「已有的行不被修改」和「這個範圍內不會有新行插入」，從根本上防止了幻讀（在當前讀場景下）。

**間隙鎖的一個代價——可能鎖住比預期更大的範圍**：因為間隙鎖鎖的是「一段區間」而非「一個具體值」，即使你的查詢條件實際上很精確、鎖住的間隙裡可能大部分值根本不存在對應的資料，這整個範圍在鎖定期間都不能插入任何新資料，這在高並發插入的場景下，可能造成比預期更多的鎖等待（見追問）。

## 面試回答方式

先講「間隙鎖是什麼」——鎖定索引記錄之間的間隙（範圍）、而非具體的行，作用是阻止插入。然後講 Next-Key Lock 是「記錄鎖+間隙鎖的組合」，並用「(10,20]」這種左開右閉區間的具體例子說明鎖定範圍。核心是講清「為什麼能防幻讀」——「行鎖鎖不住不存在的行、間隙鎖直接封鎖插入空間、讓 INSERT 被阻塞」。能補充「間隙鎖的代價——可能鎖住比預期更大的範圍、影響並發插入」作為加分，展現你不只知道間隙鎖的好處還了解它的代價。這題和前面 MVCC/隔離級別的追問有重疊，可以更聚焦在間隙鎖本身的機制細節。

## 常見追問

### 間隙鎖會不會導致「本來不衝突的插入」也被阻塞？舉例說明。

**核心答案**：會。因為間隙鎖鎖定的是「一段範圍」，而不是「某個具體的值」，所以只要「新插入的值落在這個被鎖定的範圍內」，即使這個具體的值和已有資料完全不衝突，插入操作也會被阻塞。舉例——索引有 10 和 20 兩筆記錄，交易 A 執行 `SELECT * FROM t WHERE id BETWEEN 10 AND 20 FOR UPDATE`這會鎖定 `(10, 20)` 這整個間隙（假設用範圍鎖）；此時交易 B 想插入一筆 `id=15` 的新記錄，即使 15 這個值本身和任何現有資料都不衝突，但因為它落在被鎖定的 `(10,20)` 範圍內，B 的插入操作會被阻塞，必須等 A 的交易結束（提交或回滾）釋放鎖之後才能繼續。

**詳細解析**：這題揭示間隙鎖「保守但有效」的特性——為了保證「不會有新行悄悄插進來破壞當前讀查詢的一致性（防幻讀）」，它必須「連帶」鎖住整個範圍，而不能精確地只鎖住「未來可能會被插入、恰好衝突的那個具體值」（因為在鎖定的當下，資料庫並不知道未來會有誰、要插入什麼值）。這意味著間隙鎖在實現「防幻讀」這個目標時，代價是「犧牲了一部分本來不衝突的並發插入操作」——它是一種「寧可錯殺、不可放過」的保守策略：只要新插入的值落在被保護的範圍內，不管這個具體值和現有資料是否真的有衝突，一律阻塞。這在「插入操作很頻繁、且插入的值分散在各個範圍」的高並發寫入場景下，可能會造成明顯的鎖等待，成為效能瓶頸——這也是為什麼有些對「高並發插入」有極致要求的系統，會考慮調整隔離級別（如降到讀已提交，讀已提交下對於非唯一索引的等值查詢，通常只加記錄鎖不加間隙鎖）、或重新設計交易的範圍和邏輯，來減少間隙鎖帶來的並發影響。理解間隙鎖「連帶鎖住整個範圍、可能誤傷本不衝突的插入」這個特性，展現你理解防幻讀機制的代價，而不只看到它的好處。

**面試回答方式**：用具體例子講清「間隙鎖鎖的是範圍(10,20)而非具體值、即使插入的 id=15 和現有資料不衝突、只要落在這個範圍內就會被阻塞、要等鎖釋放」。強調「這是保守策略——為了防幻讀、寧可錯殺(阻塞本不衝突的插入)、不可放過(漏掉可能導致幻讀的插入)」。可以提到「高並發插入場景下可能因此造成明顯的鎖等待、是防幻讀機制的代價」。展現你理解間隙鎖機制的雙面性。

### 讀已提交（RC）隔離級別下還有間隙鎖嗎？

**核心答案**：在讀已提交（RC）隔離級別下，InnoDB 基本上「不使用間隙鎖」（除了外鍵約束檢查、唯一性約束檢查等少數特殊情況）——這是因為 RC 級別本身就「不保證解決幻讀」（幻讀在標準定義裡本來就是 RC 允許存在的問題），既然這個級別不追求防幻讀，也就沒有必要為此付出間隙鎖帶來的並發代價。所以在 RC 級別下，普通的等值查詢或範圍查詢做當前讀時，通常只加「記錄鎖」（只鎖住實際符合條件、已存在的行），不會鎖住間隙，這意味著其他交易可以在「符合範圍條件但目前沒有資料」的間隙裡自由插入新行——RC 級別因此比 RR 級別有更高的並發插入能力，但代價是可能出現幻讀。

**詳細解析**：這題把「隔離級別」和「鎖策略」對應起來，說明「更高的隔離級別，其實是用更保守的鎖策略換來的」，是理解 InnoDB 鎖機制和隔離級別關係的關鍵。RR 級別因為要盡量提供「可重複讀、且很大程度上防止幻讀」的保證，所以在做當前讀時，預設使用 Next-Key Lock（間隙鎖+記錄鎖），寧可犧牲一些並發插入的效能，換取更強的一致性保證。RC 級別的設計哲學不同——它從一開始就只承諾「解決髒讀（Dirty Read）」，並不承諾解決不可重複讀（Non-Repeatable Read）或幻讀，所以它沒有必要（也不應該）像 RR 那樣為了防幻讀而付出間隙鎖的並發代價；InnoDB 在實現 RC 級別時，就簡化了鎖策略——只用記錄鎖精確鎖住「確實符合條件、且存在」的行，不鎖間隙這讓 RC 級別在「插入操作頻繁」的場景下，通常有比 RR 更好的並發插入效能（因為間隙沒被鎖住，其他交易能自由插入新資料）。這清楚地展現了「隔離級別的選擇，本質上是在『一致性保證的強度』和『並發效能』之間做取捨」——RC 犧牲了一部分一致性保證（可能幻讀），換來更少的鎖範圍、更好的並發插入效能；RR 提供更強的一致性保證（防幻讀），代價是間隙鎖帶來的更多並發限制。這也解釋了為什麼有些對「高並發寫入」有極致要求、又能接受「偶爾幻讀」風險的系統，會選擇用 RC 而不是 MySQL 預設的 RR。理解「隔離級別的選擇直接影響底層鎖策略、進而影響並發效能」這個具體的因果鏈，展現你能把抽象的隔離級別和具體的鎖實現串聯起來理解。

**面試回答方式**：講出「RC 級別基本不用間隙鎖(除了少數特殊情況如外鍵/唯一性檢查)——因為 RC 本來就不保證防幻讀、沒必要為此付出間隙鎖的代價；只加記錄鎖鎖住已存在的符合條件的行、不鎖間隙、其他交易能自由在間隙裡插入」。強調「這是隔離級別選擇本質上是一致性保證強度和並發效能的取捨——RC 犧牲一致性換並發插入效能、RR 犧牲並發插入效能換一致性」。展現你理解隔離級別選擇如何直接影響底層鎖策略。

### 唯一索引的等值查詢會加間隙鎖嗎？

**核心答案**：不會（或者說，InnoDB 會做優化，退化成只加記錄鎖）——如果查詢條件是「唯一索引（包括主鍵）」上的「精確等值查詢」（如 `WHERE id = 10 FOR UPDATE`，id 是主鍵），因為唯一索引保證了「這個值最多對應一行資料，不可能有另一行資料也是 id=10」，所以根本不存在「在這個值周圍插入一個同樣值的新行」導致幻讀的風險（唯一約束本身就阻止了重複值），InnoDB 因此對這種「唯一索引 + 精確等值」的查詢做了優化——只加記錄鎖（鎖住這一行），不加間隙鎖，避免不必要地限制並發插入。但如果是「普通（非唯一）索引」的等值查詢，或者唯一索引的「範圍查詢」，因為可能有多行符合、或範圍內可能插入新行，仍然會用 Next-Key Lock（記錄鎖+間隙鎖）。

**詳細解析**：這是一個很細節但很實務的優化點，展現 InnoDB 在「防幻讀」和「並發效能」之間做的精細權衡，而不是「一刀切」地對所有當前讀都無腦加間隙鎖。理解這個優化的關鍵是——間隙鎖存在的意義，是為了防止「有新行插入到查詢範圍內、導致幻讀」；但如果查詢條件是「唯一索引上的精確等值」，這個「新行插入導致幻讀」的風險根本不存在——因為唯一索引的約束保證了「不可能有第二行資料的這個唯一索引值和查詢的值相同」，也就是說不管你怎麼查、範圍鎖不鎖間隙，都不可能有「另一行 id=10 的資料」冒出來讓你的查詢結果變化（因為 id 唯一，最多只有一行）。既然這個風險不存在，InnoDB 就沒必要為此付出間隙鎖的並發代價，優化成只加記錄鎖——這讓「基於主鍵/唯一索引的精確查詢並修改」（這是最常見、最高頻的資料庫操作模式之一，如 `SELECT ... FOR UPDATE WHERE id = ?` 這種典型的「先查詢後更新」場景）能有更好的並發效能，不會不必要地阻塞其他交易在附近插入新行。但要注意這個優化的邊界——只適用於「唯一索引 + 精確等值」，一旦是「範圍查詢」（即使在唯一索引上，如 `WHERE id > 10`）或「非唯一索引的等值查詢」（如 `WHERE name = 'Tom'`，name 不是唯一的，可能有多行、且範圍內插入新的同名行是有意義的、可能導致幻讀），仍然需要 Next-Key Lock 的完整保護。理解這個「唯一索引精確等值可以優化掉間隙鎖」的細節，展現你對 InnoDB 鎖機制的理解已經深入到具體的優化策略層面，而不只是知道「RR 級別會加間隙鎖」這種籠統的規則。

**面試回答方式**：講出「不會——唯一索引精確等值查詢時、InnoDB 優化成只加記錄鎖不加間隙鎖，因為唯一約束本身就保證了不可能有另一行同樣值的資料插入進來導致幻讀、風險不存在、沒必要為此犧牲並發效能」。強調「這個優化只適用於唯一索引+精確等值、範圍查詢或非唯一索引等值仍需完整的 Next-Key Lock」。展現你對 InnoDB 鎖機制的理解深入到了具體優化策略層面。
