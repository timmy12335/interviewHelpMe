# 題目

什麼時候需要考慮「分庫分表」？常見的分片策略有哪些？分庫分表之後會帶來哪些新問題？

## 核心答案

當「單一資料庫實例的容量或效能已經無法再透過垂直優化（升級硬體、加索引、讀寫分離（Read-Write Splitting）等）解決」時，就需要考慮分庫分表——常見的訊號包括單表資料量達到千萬甚至億級（索引也大到記憶體放不下）、單機的寫入吞吐量已達硬體瓶頸、或磁碟容量接近上限。常見的分片策略有**垂直分片**（按「業務模組」拆分，把不同業務的表拆到不同資料庫，如訂單庫、使用者庫分開）和**水平分片**（把「同一張表」的資料按某個規則拆到多個庫/表，如按使用者 ID 取模、按範圍、或按一致性雜湊（Consistent Hashing）分佈），兩者常常搭配使用。分庫分表之後會引入的新問題主要有：**跨分片的 JOIN 和聚合查詢變困難**（資料分散在不同庫，無法直接用 SQL JOIN）、**分散式交易一致性**（一個業務操作涉及多個分片時，無法再用單機交易保證原子性）、**分散式 ID 生成**（不能再依賴單機自增主鍵）、以及**擴容/縮容時的資料遷移複雜度**。

## 詳細解析

**分片策略**：

- **垂直分庫**：按業務領域拆分，例如把「使用者相關的表」放進 user_db、「訂單相關的表」放進 order_db、「商品相關的表」放進 product_db，本質上是把一個大的單體資料庫，按照業務邊界拆成多個獨立的資料庫，這和微服務（Microservices）架構「按業務拆分服務」的思路是一致的。優點是每個資料庫的職責更清晰、容量壓力被業務邊界自然分散；缺點是原本可以用一次 JOIN 完成的查詢（例如「查詢某訂單及其使用者資訊」），現在因為表在不同的資料庫裡，必須改成「查兩次、在應用層組裝」。
- **垂直分表**：把「同一張表裡使用頻率差異很大的欄位」拆到不同的表，例如把商品的「基本資訊（名稱、價格）」和「詳細描述（大文字欄位）」拆成兩張表，讓高頻查詢（列表頁只需要基本資訊）可以避免讀取又大又少用的欄位，提升查詢效率和快取命中率。
- **水平分庫分表**：把「同一張表」的資料，按照某個規則（分片鍵），拆分到多個資料庫或多張結構相同的表裡。常見的分片規則：
  - **取模 / 雜湊分片**：如 `user_id % 16` 決定資料落在哪個分片，優點是資料分佈相對均勻；缺點是「擴容時（比如從 16 個分片擴到 32 個）需要重新計算大量資料應該落在哪個分片、遷移成本高」。
  - **範圍分片**：如按 `user_id` 或時間的範圍（0-100萬 一個分片、100萬-200萬 下一個分片），優點是範圍查詢效率高、擴容時只需要加新的分片而不用遷移舊資料；缺點是容易出現「熱點分片」（比如最新註冊的使用者、最近的訂單都集中在最後一個分片，導致負載不均）。
  - **一致性雜湊**：在雜湊分片的基礎上改進，讓「新增或移除分片節點」時，只需要遷移「一小部分」資料（通常是相鄰節點間的資料），而不是像簡單取模那樣，幾乎所有資料都要重新計算位置，大幅降低擴容/縮容時的遷移成本。

**分庫分表帶來的新問題**：

- **跨分片 JOIN/聚合困難**：資料分散在不同的物理資料庫，資料庫層面無法直接跨庫 JOIN，通常要在應用層（或透過中介軟體如 ShardingSphere、MyCat）把多次查詢的結果在記憶體裡組裝，或透過「冗餘欄位」（犧牲一定的資料一致性和儲存空間，換取避免跨庫查詢）來規避。聚合查詢（如 `COUNT`、`SUM`）也要改成「分別在各分片算出部分結果、再彙總」的模式。
- **分散式交易**：如果一個業務操作要同時修改分佈在不同分片的資料（比如「轉帳」涉及兩個使用者，可能剛好落在不同分片），單一資料庫的 ACID 交易不再適用，需要引入分散式交易方案（如 2PC/3PC、TCC、Saga 模式，或依賴訊息佇列（Message Queue）做最終一致性（Eventual Consistency）），複雜度顯著提升。
- **分散式主鍵**：分片之後不能再簡單依賴單一資料庫的自增主鍵（會在不同分片產生重複的 ID），需要引入分散式 ID 生成方案（如雪花演算法 Snowflake、資料庫號段模式），見 [[018-distributed-id.md]]。
- **擴容遷移**：業務成長導致需要增加分片數量時，如何在盡量不停機、不影響線上服務的前提下，把資料從舊的分片佈局遷移到新的分片佈局，是一項複雜的工程挑戰，一致性雜湊等分片策略的選擇，很大程度就是為了降低這個遷移成本。

## 面試回答方式

先講「什麼時候需要分庫分表」——強調這是在垂直優化（加索引、升級硬體、讀寫分離）都無法解決容量或效能瓶頸時的最後手段，而非一開始就上分庫分表（分庫分表帶來的複雜度成本很高）。接著分別講垂直拆分（按業務/按欄位冷熱）和水平拆分（取模/範圍/一致性雜湊，各自優缺點）。最後一定要主動講「分庫分表之後帶來的新問題」（跨分片查詢、分散式交易、分散式 ID、擴容遷移），這部分往往是面試官真正想聽到的——因為它體現你理解分庫分表不是免費的午餐，而是用架構複雜度換取擴展性的權衡決策。

## 常見追問

### 如果選擇了「取模分片」（如 user_id % 16），未來業務成長需要擴容到 32 個分片，會遇到什麼問題？怎麼解決？

**核心答案**：取模分片擴容時的核心問題是——**分片數量一變，幾乎所有資料的「應該落在哪個分片」的計算結果都會改變**（比如原本 `user_id=17` 在 `% 16` 下落在分片 1，改成 `% 32` 後可能落在分片 17），導致幾乎全部資料都需要重新計算並遷移到新的分片，遷移成本和對線上服務的影響都非常大。常見的解決方式是：**（1）一開始就「預留足夠多的分片數量」**（比如即使目前資料量只需要 4 個分片，也先規劃 64 個邏輯分片、分佈在較少的物理資料庫上，未來擴容時只需要把部分邏輯分片遷移到新增的物理資料庫，不需要重新計算分片規則）；**（2）改用一致性雜湊**，讓擴容時只需要遷移「相鄰節點間」的一小部分資料。

**詳細解析**：這題深入取模分片在擴容場景下的根本缺陷，以及業界常見的兩種應對策略。取模分片的問題在數學上很直觀——`% N` 到 `% 2N` 的變化，對於任意一個 ID，其取模結果幾乎沒有規律可循（不像「範圍分片」那樣，擴容只是新增一個範圍區間，舊資料完全不需要動），這意味著取模分片一旦需要擴容，基本上等於要把整個資料集重新洗牌一次，這在資料量巨大時是一個代價極高、且很難做到「不停機」的操作。第一種解法「邏輯分片與物理分片解耦」是業界（如很多分庫分表中介軟體）常用的實務手法——不直接把 `user_id % 物理資料庫數量`，而是先 `% 一個較大的固定邏輯分片數（比如 1024）`，再透過一張「邏輯分片到物理資料庫」的映射表，決定這 1024 個邏輯分片實際落在哪幾個物理資料庫上；一開始可能只有 4 台物理機、每台機器負責 256 個邏輯分片，未來要擴容到 8 台機器時，只需要把其中一半的邏輯分片（各自完整地、不需要拆分和重新計算）搬到新的機器上，資料本身在邏輯分片內部完全不需要重新雜湊或搬動，大幅降低了擴容的複雜度和風險。第二種解法「一致性雜湊」則是從演算法層面解決這個問題——它把節點和資料都映射到一個環狀的雜湊空間上，每個資料歸屬於「順時針方向第一個遇到的節點」，新增一個節點時，只有這個新節點和它「前一個節點」之間的資料需要重新分配，其餘資料完全不受影響，這也是很多分散式系統（如分散式快取 Redis Cluster 的雜湊槽概念、DynamoDB）採用的核心設計思想。

**面試回答方式**：先精確地指出問題本質——「取模的除數一變，幾乎所有資料的取模結果都變了，等於要全量重新洗牌和遷移」。給出兩個解法——「預先規劃足夠多的邏輯分片、用邏輯分片到物理資料庫的映射表來解耦，擴容時只搬邏輯分片不用重算資料」以及「改用一致性雜湊，讓擴容只影響相鄰節點間的一小部分資料」。如果能提到 Redis Cluster 的雜湊槽概念作為類比，能展現你把這個分散式系統的通用設計模式和其他系統（不只是 MySQL 分庫分表）串聯起來的能力。

### 分庫分表之後，原本可以用資料庫自增主鍵保證唯一，現在要怎麼生成全域唯一的 ID？

**核心答案**：常見的分散式 ID 生成方案包括：**（1）資料庫號段模式**——用一張獨立的表，每次批量分配一段 ID 範圍（比如一次拿 1000 個）給應用伺服器快取使用，用完再去要下一段，減少對資料庫的頻繁請求；**（2）雪花演算法（Snowflake）**——用「時間戳 + 機器 ID + 序列號」組合成一個 64 位元的長整數，不依賴任何中心化的資料庫或協調服務，各節點各自生成，天然保證全域唯一且趨勢遞增；**（3）UUID**——生成簡單、不需要任何協調，但缺點是無序（不利於索引效能，因為插入位置隨機會導致 B+ 樹頁分裂頻繁）且佔用空間較大，通常不適合直接作為聚簇索引（Clustered Index）的主鍵。實務上高併發場景最常見的是雪花演算法或其變種。

**詳細解析**：這題考察分散式 ID 生成方案的具體選型和權衡，是分庫分表配套設計中的常見考點。資料庫號段模式的核心思路是「用空間換時間」——不是每次要一個 ID 就查一次資料庫（那樣資料庫會成為瓶頸），而是「一次要一批」（比如向一張專門的 `id_generator` 表要「從 5000 到 6000」這個號段），應用伺服器把這個號段快取在記憶體裡，後續的 ID 請求直接從記憶體裡的號段中分配，用完了才再去資料庫要下一段，這樣把「對資料庫的請求頻率」降低了幾個數量級（比如每 1000 次 ID 請求才打一次資料庫），但代價是如果應用伺服器重啟，記憶體裡還沒用完的號段會被浪費（ID 不連續但仍然保證唯一，這通常是可接受的）。雪花演算法是目前業界最常用的方案之一（Twitter 最早提出），其 64 位元的結構通常是「1 位元符號位（固定 0）+ 41 位元時間戳（毫秒級，可用約 69 年）+ 10 位元機器 ID（區分不同的生成節點，最多支援 1024 個節點）+ 12 位元序列號（同一毫秒內同一節點的自增序號，支援每毫秒最多 4096 個 ID）」，這個設計的巧妙之處在於——完全不需要任何「中心化的協調」（每個節點只要知道自己的機器 ID，就能獨立生成，不會和其他節點衝突），且因為前面是時間戳，生成出來的 ID 是「趨勢遞增」的（雖然同一毫秒內多個節點生成的 ID 之間沒有嚴格的全域順序，但整體上是隨時間遞增的），這對於用作資料庫聚簇索引的主鍵非常友善（避免了 UUID 那種完全隨機的 ID 導致頻繁的頁分裂，見 [[003-clustered-index.md]] 裡關於聚簇索引最好用自增或趨勢遞增鍵的討論）。UUID 雖然生成最簡單（本地產生，完全不需要協調），但正是因為「趨勢遞增」的特性在它身上不成立（完全隨機），如果直接拿來當聚簇索引的主鍵，每次插入都可能落在 B+ 樹的任意位置，導致頁分裂和碎片化嚴重，通常不建議直接用 UUID 做聚簇索引主鍵（可以考慮用 UUID 做業務層面的唯一識別符，但資料庫的實際主鍵/聚簇索引鍵仍用趨勢遞增的方案）。

**面試回答方式**：列舉三種方案並各自點出核心機制和優缺點——號段模式（批量分配減少資料庫壓力，重啟有 ID 浪費但可接受）、雪花演算法（時間戳+機器ID+序列號組合、不需協調、趨勢遞增對索引友善，是最常用方案）、UUID（最簡單但無序、不適合直接做聚簇索引主鍵）。如果能主動連結「趨勢遞增對聚簇索引頁分裂的影響」這個知識點，展現跨主題的知識串聯能力。

### 分片鍵（Sharding Key）要怎麼選擇？選得不好會有什麼問題？

**核心答案**：分片鍵的選擇原則是「**這個欄位要能讓資料盡量均勻分佈到各個分片，同時盡量讓最高頻的查詢，都能『帶著分片鍵』一起查詢**（這樣中介軟體或應用程式才能直接算出該去哪個分片查，不用掃描所有分片）」。常見選擇如電商場景的 `user_id`（使用者主要以自己的 ID 查詢自己的訂單）或訂單場景的 `order_id`。選得不好的典型問題包括：**（1）資料傾斜**——如果分片鍵的區分度不夠（例如按「地區」分片，但業務在某幾個大城市高度集中），會導致某幾個分片的資料量和負載遠高於其他分片，出現「熱點分片」；**（2）高頻查詢無法帶分片鍵**——如果最常見的查詢條件（如「查詢某個時間範圍內的所有訂單」）不包含分片鍵，就必須「廣播查詢」到所有分片再彙總結果，效能和分片的初衷背道而馳。

**詳細解析**：這題考察分片鍵選擇這個分庫分表設計中最關鍵、也最容易被誤解的決策點。分片鍵的選擇本質上是在回答「未來這個系統最主要、最高頻的查詢模式是什麼」這個問題——如果選了一個和「主要查詢模式」脫節的分片鍵，即使資料分佈得再均勻，也無法發揮分片架構「讓每次查詢只需要命中少數幾個分片」的優勢，因為應用程式或中介軟體光看查詢條件，根本無法判斷「這筆資料應該去哪個分片找」，只能無奈地「廣播」到所有分片、各自查一遍再彙總，這種查詢模式的效能和維護成本，某種程度上比不分片還更糟（因為要協調多個分片的查詢和彙總邏輯）。以電商訂單系統為例，如果按 `user_id` 分片，「使用者查詢自己的訂單列表」這個最高頻的查詢天然就「帶著」分片鍵（因為要查的就是這個使用者自己的訂單），可以直接路由到對應的分片，效率很高；但如果換成「客服人員根據訂單編號查詢某一筆訂單」，如果訂單編號本身沒有蘊含 user_id 的資訊，就需要額外的機制（比如維護一張「order_id 到 user_id」的映射索引表）才能知道去哪個分片查，這也是為什麼很多系統設計「訂單編號」時，會刻意把 user_id 或分片資訊編碼進訂單號本身，讓「按訂單號查詢」也能直接推算出分片位置。資料傾斜問題則提醒我們，分片鍵不能只考慮「查詢是否方便」，也要考慮「資料本身的分佈特性」——如果按照某個天然不均勻的維度分片（比如按照「使用者所在城市」，而業務高度集中在一線城市），會導致某些分片承擔了遠超其他分片的資料量和查詢壓力，違背了分片架構想要「分散負載」的初衷，這也是為什麼很多系統即使有一個看似自然的業務欄位可以拿來分片，最終還是選擇用 `user_id` 取雜湊值（而非直接用城市名稱）這種能保證均勻分佈的方式。

**面試回答方式**：先給出選擇原則——「分片鍵要能讓資料均勻分佈,同時要讓最高頻的查詢天然帶著這個欄位」。舉例電商場景 user_id 作為分片鍵，「使用者查自己訂單」天然帶分片鍵、效率高，但「客服按訂單號查詢」若訂單號沒編碼分片資訊，就需要額外的映射索引表。點出資料傾斜的風險——「分片鍵區分度不夠或業務天然不均勻（如按城市），會導致熱點分片」。展現你理解分片鍵選擇是「業務查詢模式」和「資料分佈均勻性」兩者的權衡，而非隨便選一個欄位就好。
