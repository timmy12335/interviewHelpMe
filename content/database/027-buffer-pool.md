# 題目

InnoDB 的 Buffer Pool 是什麼？為什麼它的 LRU 要分成 young 與 old 兩區？

## 核心答案

Buffer Pool 是 InnoDB 在記憶體中快取**資料頁與索引頁**的區域，**所有的讀寫都先經過它**——讀取時如果頁面已在池中就直接返回（不碰磁碟），寫入時先改記憶體中的頁面（標記為髒頁）再由背景執行緒非同步刷回磁碟。**它是 InnoDB 效能的核心**，`innodb_buffer_pool_size` 通常設成機器記憶體的 50% 到 70%。

LRU 分區的原因是「防止全表掃描沖掉熱資料」。標準的 LRU 下，一次大表的全表掃描會把整個池的熱頁全部擠出去——而那些掃描出來的頁往往只用一次。InnoDB 的做法是把 LRU 鏈分成 **young（前 5/8，熱區）** 與 **old（後 3/8，冷區）**：**新讀入的頁先放在 old 區的頭部**，只有當它在一段時間之後（`innodb_old_blocks_time`，預設 1000 毫秒）再次被存取，才會被移到 young 區。

**這個「時間門檻」是關鍵**——全表掃描會在極短的時間內連續存取同一個頁的多列，如果沒有時間門檻，它會立刻被判定為熱頁而晉升；加上門檻之後，掃描過的頁停留在 old 區並很快被淘汰，**熱資料不受影響**。

## 詳細解析

「預讀」是另一個需要被 old 區保護的機制。InnoDB 有線性預讀（一個區內連續讀取的頁數超過門檻時，預讀下一個區）與隨機預讀，它們讀進來的頁不一定會被用到——放進 old 區意味著沒用到的話很快被淘汰，不會汙染熱區。

髒頁的刷新時機決定了效能的穩定性。髒頁太多時，InnoDB 必須同步刷新才能騰出空間，**那會直接阻塞使用者的查詢**。相關的控制參數是 `innodb_max_dirty_pages_pct`（髒頁比例的目標）與 `innodb_io_capacity`（告訴 InnoDB 磁碟每秒能做多少 IOPS，讓它據此決定刷新速度）。`innodb_io_capacity` 設得太低是一個常見的錯誤——預設值是為機械硬碟設計的，在 SSD 上會讓 InnoDB 刷得太慢，髒頁堆積後突然爆發同步刷新，表現為週期性的延遲毛刺。

**Buffer Pool 的命中率是首要指標**，但它的解讀需要小心。`Innodb_buffer_pool_reads`（真的讀磁碟的次數）除以 `Innodb_buffer_pool_read_requests`（總的讀請求）得到未命中率——**健康的系統應該遠低於 1%**。但**命中率高不代表沒問題**：如果查詢本身掃描了大量頁面（缺索引導致的全表掃描），即使全部命中記憶體，CPU 與時間仍然被浪費了。所以命中率要與「每次查詢掃描的頁數」一起看。

**多實例的設定值得知道**。`innodb_buffer_pool_instances` 把緩衝池切成多個獨立的實例，**每個有自己的 LRU 鏈與互斥鎖**——這降低了高併發下的鎖爭用。只有在緩衝池較大（1GB 以上）時才有意義，太小的池切分反而讓每個實例的命中率下降。

## 面試回答方式

先給 Buffer Pool 的定位（快取資料頁與索引頁、所有讀寫都經過它、通常設機器記憶體的 50% 到 70%）。接著把 **LRU 分區的動機講清楚**——防止全表掃描沖掉熱資料，並給出機制：新頁先進 old 區，只有在時間門檻之後再次被存取才晉升到 young 區。**強調「時間門檻」是關鍵**：全表掃描在極短時間內連續存取同一頁的多列，沒有門檻就會被誤判為熱頁。加分點有三個：**預讀也需要 old 區保護**（讀進來的頁不一定會用到）；`innodb_io_capacity` 預設值是為機械硬碟設計的，在 SSD 上設太低會讓髒頁堆積後爆發同步刷新，表現為週期性的延遲毛刺；以及命中率高不代表沒問題——缺索引導致的全表掃描即使全部命中記憶體也浪費了 CPU，所以要與「每次查詢掃描的頁數」一起看。

## 講稿

Buffer Pool 是 InnoDB 在記憶體中快取資料頁跟索引頁的區域，所有讀寫都先經過它。讀取時頁面已經在池裡就直接返回，寫入時先改記憶體再由背景執行緒非同步刷回磁碟。

LRU 分成兩區的原因是防止全表掃描沖掉熱資料。標準的 LRU 下，一次大表的全表掃描會把整個池的熱頁全部擠出去，而那些掃描出來的頁往往只用一次。

InnoDB 的做法是把鏈分成熱區跟冷區，新讀入的頁先放在冷區的頭部，只有當它在一段時間之後再次被存取，才會被移到熱區。

這個時間門檻是關鍵。全表掃描會在極短的時間內連續存取同一個頁的多列，如果沒有時間門檻，它會立刻被判定為熱頁而晉升。加上門檻之後，掃描過的頁停留在冷區並很快被淘汰，熱資料就不受影響。

還有一個常見的設定錯誤要提。告訴 InnoDB 磁碟每秒能做多少 IO 的那個參數，預設值是為機械硬碟設計的。在 SSD 上設太低會讓刷新太慢，髒頁堆積之後突然爆發同步刷新，表現為週期性的延遲毛刺。

## 常見追問

### Buffer Pool 該設多大？

**核心答案**：起點是**機器記憶體的 50% 到 70%**，但要留出其他部分：**每個連線的執行緒本地緩衝**（`sort_buffer_size`、`join_buffer_size`、`read_buffer_size` 等，這些是每連線分配的，連線數多時總量可觀）、**redo log buffer**、**作業系統與檔案系統快取**、以及**其他行程**。理想的狀態是「熱資料集能放得下」——如果活躍的資料只有 20GB，開 100GB 的緩衝池沒有額外收益。

**詳細解析**：「每連線緩衝」是最容易被低估的一項。`sort_buffer_size` 設成 8MB 看起來不大，**但 500 個連線同時執行排序就是 4GB**——而這些是在緩衝池之外額外分配的。很多「MySQL 突然被 OOM 殺掉」的案例，根因就是連線數暴增加上過大的每連線緩衝。 所以這些參數應該保守設定（通常幾百 KB 到 2MB 就夠），需要更大的排序空間時，正確的做法是優化查詢讓它不需要排那麼多資料，而不是調大緩衝。判斷緩衝池夠不夠的方式是看命中率與磁碟讀取量的趨勢，而不是憑記憶體大小的比例。

**面試回答方式**：給起點比例並列出要留出的部分。重點展開**每連線緩衝最容易被低估**——`sort_buffer_size` 8MB 乘以 500 連線就是 4GB，而它們在緩衝池之外額外分配，很多 MySQL 被 OOM 殺掉的案例根因就是這個。給出建議：這些參數保守設定，需要更大排序空間時該優化查詢而非調大緩衝。收在判斷方式：看命中率與磁碟讀取量的趨勢，而非憑記憶體比例。

### 為什麼重啟後資料庫會變慢？

**核心答案**：因為 **Buffer Pool 是空的**——所有查詢都要從磁碟讀取，直到熱資料被重新載入。這個「暖機」過程在大緩衝池上可能持續幾十分鐘，期間的延遲可能是穩態的十倍以上。MySQL 5.6 之後提供了 **Buffer Pool 的傾印與載入**（`innodb_buffer_pool_dump_at_shutdown` 與 `innodb_buffer_pool_load_at_startup`，預設開啟）——關閉時把熱頁的頁號記下來，啟動時在背景重新載入。

**詳細解析**：要注意它記錄的是「頁號」而非「頁的內容」，所以載入時仍然要真的從磁碟讀——它省的是「不知道哪些頁是熱的」，不是「讀取本身」。載入是背景進行的，`innodb_buffer_pool_load_now` 可以手動觸發，`Innodb_buffer_pool_load_status` 可以看進度。實務上更重要的是「不要在流量高峰重啟」以及「重啟後給暖機時間再放全量流量」——在 Kubernetes 或負載平衡的環境下，這意味著 readiness 探針不應該在資料庫剛啟動就回報就緒。這與 JVM 的 JIT 預熱是同一類問題：系統的「準備好接受流量」與「行程已經啟動」是兩件事，而把它們混為一談是滾動更新期間效能下降的常見原因。

**面試回答方式**：給原因（緩衝池是空的、暖機期延遲可能是穩態的十倍）與 MySQL 的傾印載入機制。真正的加分點是精確指出**它記錄的是頁號而非內容**，省的是「不知道哪些頁是熱的」而非讀取本身。收在實務建議：不要在高峰重啟、重啟後給暖機時間再放全量流量，並連到 JVM 的 JIT 預熱——「準備好接受流量」與「行程已啟動」是兩件事，混為一談是滾動更新期間效能下降的常見原因。

### 髒頁刷新造成的延遲毛刺怎麼排查？

**核心答案**：看三個訊號。**`Innodb_buffer_pool_pages_dirty` 的比例**——持續接近 `innodb_max_dirty_pages_pct` 表示刷新跟不上。**`Innodb_data_fsyncs` 與 `Innodb_os_log_written` 的速率**——判斷磁碟的實際負載。**redo log 的空間使用率**——`SHOW ENGINE INNODB STATUS` 裡的 checkpoint age 接近 redo log 總大小時，InnoDB 會**強制同步刷新**（因為 redo 空間要被覆寫了），那是最劇烈的一種停頓。

**詳細解析**：「redo log 太小」是這類毛刺最常見的根因。redo log 的大小（`innodb_log_file_size` 乘以檔案數）決定了「可以累積多少未刷新的修改」——太小的話 checkpoint 被迫頻繁推進，表現為持續的刷新壓力與週期性的同步刷新停頓。實務上寫入密集的系統應該把 redo log 開大（幾 GB 甚至更多），**代價是崩潰恢復的時間變長**（要重放更多 redo）。這是一個明確的取捨：redo log 大則平時順暢但恢復慢，小則平時有毛刺但恢復快。 判斷的方式是量測「一小時內產生多少 redo」——理想的 redo log 大小應該能容納一到兩小時的寫入量，讓 checkpoint 不必被迫推進。

**面試回答方式**：給三個訊號並特別點出 checkpoint age 接近 redo log 總大小時會強制同步刷新，那是最劇烈的停頓。展開**「redo log 太小」是最常見的根因**——它決定了能累積多少未刷新的修改，太小則 checkpoint 被迫頻繁推進。給出明確的取捨：redo log 大則平時順暢但恢復慢，小則平時有毛刺但恢復快。收在判斷方式：量測一小時產生多少 redo，理想大小能容納一到兩小時的寫入量。
