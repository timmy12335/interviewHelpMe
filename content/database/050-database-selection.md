# 題目

什麼情況下不該用關聯式資料庫？面對一個新系統你會怎麼選？

## 核心答案

**預設應該是關聯式資料庫**——它提供了交易、約束、成熟的生態、以及**最重要的：靈活的查詢能力**。在需求還會變的階段，「能用 SQL 查任意組合」的價值極高，而那正是多數新系統的處境。

**不該用的情況有五類**。**資料模型天生是圖**（社交關係、推薦、權限的傳遞閉包）——多層的遞迴 JOIN 在關聯式上極其昂貴，圖資料庫的遍歷是原生操作。**時序資料的極高寫入**（監控指標、IoT）——專門的時序資料庫在壓縮率與寫入吞吐上高一到兩個數量級。全文檢索與複雜的相關性排序——搜尋引擎的能力遠超 `LIKE` 與全文索引。**極大規模的鍵值存取**（單純依鍵讀寫、無需交易與查詢）——鍵值儲存更簡單也更便宜。**分析型的大規模聚合**——列式儲存在掃描與聚合上快幾個數量級。

判斷的核心問題是：「這個系統的主要存取模式是什麼？」——而不是「哪個資料庫比較潮」。

## 詳細解析

「先用關聯式資料庫」的理由值得說清楚，因為它常被當成保守而非正確。新系統的需求是不確定的——你不知道之後會需要按哪些條件查詢、需要哪些聚合、以及資料之間會產生哪些關聯。關聯式資料庫的價值正是「不必事先知道」：schema 加上 SQL 讓任意的查詢組合成為可能，而多數 NoSQL 要求你依查詢模式設計資料模型——猜錯了就要重新建模與遷移。所以在需求不確定的階段，關聯式資料庫的靈活性是一個真實且巨大的優勢，而不只是「保守的選擇」。

「多存儲」的成本必須被誠實計入。引入第二種資料庫意味著：**資料同步的管線**（以及它的延遲、失敗、與監控）、**雙寫的一致性問題**、**兩套維運知識**、**兩套備份與恢復流程**、以及**團隊的認知負擔**。這些成本是持續的，而收益往往是一次性的（某類查詢變快了）。 所以引入新的儲存系統應該有明確的門檻：那個需求真的無法在既有系統上滿足嗎？滿足它的收益能持續超過維運成本嗎？很多「我們需要 Elasticsearch」的結論，其實只需要一個好的索引加上分頁的調整。

PostgreSQL 的功能廣度改變了很多選型結論。它的 JSONB 加 GIN 索引處理了大部分半結構化資料的需求、全文檢索（`tsvector`）處理了中小規模的搜尋、PostGIS 處理了地理資料、TimescaleDB 這類擴充處理了時序資料。「先看看 PostgreSQL 能不能做」應該是引入任何專門資料庫之前的必要步驟——因為留在一個系統裡的價值（交易、一致性、單一維運）常常超過專門系統的效能優勢，尤其在規模還沒到極端時。

選型應該是可逆的決定，而不是一次性的賭注。務實的做法是：先用關聯式資料庫實作、量測、找出真正的瓶頸、再針對那個瓶頸引入專門的系統——而且是**以「加一層」而非「換掉」的方式**（例如把搜尋同步到 Elasticsearch，而交易資料仍在 PostgreSQL）。這讓每一步都可以回退，也讓引入的複雜度與已驗證的收益對應。

## 面試回答方式

先給明確的預設立場——**應該是關聯式資料庫**，並把理由說清楚：在需求還會變的階段「能用 SQL 查任意組合」的價值極高，而多數 NoSQL 要求你依查詢模式設計資料模型，猜錯就要重新建模。給**五類不該用的情況**並各配一句理由。給判斷的核心問題：這個系統的主要存取模式是什麼。加分點有三個：**「多存儲」的成本必須誠實計入**——同步管線、雙寫一致性、兩套維運與備份、認知負擔，這些是持續成本而收益往往是一次性的；PostgreSQL 的功能廣度改變了很多選型結論，「先看看它能不能做」應該是引入任何專門資料庫前的必要步驟；以及**選型應該是可逆的決定**——先實作、量測、找出真正的瓶頸、再以「加一層」而非「換掉」的方式引入專門系統。

## 常見追問

### 什麼時候真的需要圖資料庫？

**核心答案**：當查詢的本質是「多層的關聯遍歷」且深度不固定時。關聯式資料庫可以用遞迴 CTE 做圖遍歷，但每一層都是一次 JOIN——三層還可以，六層就會爆炸（每層的中間結果乘上分支因子）。圖資料庫把關聯存成鄰接表並直接以指標遍歷，遍歷的成本與「實際經過的邊數」成正比而非與表的大小成正比。

**詳細解析**：判斷的方式是看「典型查詢的深度」。深度 1 到 2（「這個使用者的朋友」「這篇文章的標籤」）用關聯式完全沒問題；深度 3 以上且需要找路徑或計算中心性時，圖資料庫的優勢才顯現。要注意的是「圖」這個資料模型與「圖資料庫」是兩件事——很多系統的資料在概念上是圖，但查詢從來不超過兩層，**那就不需要圖資料庫**。引入它的成本包括：一套新的查詢語言（Cypher、Gremlin）、較弱的交易與一致性保證（多數圖資料庫在這方面不如關聯式）、以及較小的生態。 所以應該問的不是「我的資料是不是圖」而是「我的查詢是不是深度遍歷」。

**面試回答方式**：給判準——查詢的本質是多層關聯遍歷且深度不固定，並解釋成本差異（每層一次 JOIN、中間結果乘上分支因子 vs 遍歷成本與實際經過的邊數成正比）。給具體的深度界線（1 到 2 層用關聯式沒問題、3 層以上才顯現優勢）。真正的加分點是區分「圖這個資料模型」與「圖資料庫」是兩件事——很多系統的資料概念上是圖但查詢從不超過兩層。收在正確的問題：不是「我的資料是不是圖」而是「我的查詢是不是深度遍歷」。

### 混合使用多種資料庫時怎麼保證一致性？

**核心答案**：接受最終一致並明確定義「事實來源」。指定一個系統為權威（通常是關聯式資料庫），其他系統的資料都是它的衍生——透過 CDC 或事件驅動同步。這樣「不一致」有明確的解決方向（以事實來源為準重建衍生資料），而不是兩邊都可能對也都可能錯。

**詳細解析**：「雙寫」是這裡最常見也最危險的錯誤——應用同時寫兩個系統，**中間沒有交易保證**：寫了 A 成功、寫 B 失敗，兩邊就永久不一致。**而且失敗的處理很難做對**（重試可能重複、回滾 A 可能已經被別人讀到）。正確的模式是「先寫事實來源，再由一個可靠的機制同步」——Outbox（在同一個交易裡寫業務資料與待同步記錄）或 CDC（讀 binlog 產生變更事件）。兩者的共同點是「同步這件事有一個可以重試的、持久的來源」，而雙寫沒有。**另外必須有「對帳」機制**——定期比對兩邊的資料並修補差異，因為任何同步管線都會有失敗，而沒有對帳的話那些失敗會靜默累積。

**面試回答方式**：給原則——接受最終一致並明確定義事實來源，其他系統的資料是它的衍生，這樣不一致有明確的解決方向。重點指出「雙寫」是最常見也最危險的錯誤——中間沒有交易保證，而失敗的處理很難做對。給正確的模式（Outbox 或 CDC）與它們的共同點：同步這件事有一個可以重試的、持久的來源。收在必要的配套：**必須有對帳機制**，因為任何同步管線都會失敗，沒有對帳的話那些失敗會靜默累積。

### 選型時最常見的錯誤是什麼？

**核心答案**：三個。依「聽說很快」而非實際的存取模式選擇——一個系統在別人的場景下快，不代表在你的場景下快。**低估維運成本**——只評估功能與效能，忽略了部署、監控、備份、升級、以及故障處理的持續投入。**過早地為想像中的規模設計**——為「將來可能有一億使用者」引入的複雜度，在只有一萬使用者時是純粹的負擔，而且它讓迭代變慢，反而降低了到達那個規模的機率。

**詳細解析**：第三點是最需要被說出來的，因為它聽起來像是「不夠有遠見」。但實際上，過早的架構複雜度會拖慢產品的迭代速度，而在早期階段，迭代速度才是決定成敗的因素。正確的做法是「為當前的規模設計，但保留可以演進的空間」——例如用關聯式資料庫但確保 schema 設計不阻礙日後分片（有合適的分片鍵候選）、用 ROW 格式的 binlog 讓日後能接 CDC、以及把資料存取集中在一個層次而非散落各處（讓日後換儲存時只要改一個地方）。這些「留空間」的做法成本極低，而它們保留的選項價值很高——這比直接引入複雜的架構務實得多。

**面試回答方式**：給三個常見錯誤。重點展開第三點最需要被說出來，因為它聽起來像是不夠有遠見——但過早的複雜度拖慢迭代，而在早期階段迭代速度才是決定成敗的因素。給出正確的做法：為當前規模設計但保留演進空間，並舉三個低成本的例子（schema 不阻礙日後分片、ROW 格式讓日後能接 CDC、資料存取集中在一個層次）。收在判斷：這些「留空間」的做法成本極低而保留的選項價值很高，比直接引入複雜架構務實得多。
