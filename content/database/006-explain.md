# 題目

怎麼用 EXPLAIN 分析一條 SQL 的執行計劃（Execution Plan）？重點看哪些欄位？

## 核心答案

`EXPLAIN` 顯示 MySQL 執行一條查詢時「打算怎麼做」的執行計劃，不真正執行查詢。重點看的欄位——**type**（存取類型，反映查詢效率，從好到差大致是 `system/const > eq_ref > ref > range > index > ALL`，`ALL` 是全表掃描、要盡量避免）、**key**（實際使用的索引，如果是 NULL 説明沒用上索引）、**rows**（預估需要掃描的行數，越少越好）、**Extra**（額外資訊，如 `Using filesort`（需要額外排序，可能較慢）、`Using temporary`（用了臨時表）、`Using index`（覆蓋索引（Covering Index），好現象）、`Using where`（在儲存引擎層取出資料後、伺服器層還要過濾）。分析 SQL 效能，主要就是看這幾個欄位判斷「有沒有用上索引、用得好不好、掃描量大不大、有沒有額外的排序/臨時表開銷」。

## 詳細解析

**核心欄位詳解**：

- **`type`（存取類型）**——從好到差大致排列：
  - `system`/`const`——最快，通常是透過主鍵或唯一索引查到唯一一行。
  - `eq_ref`——多表關聯時，對於前一張表的每一行，後一張表都能透過主鍵/唯一索引精確匹配一行。
  - `ref`——透過普通索引（非唯一）查找，可能匹配多行。
  - `range`——範圍查詢（如 `BETWEEN`、`>`、`<`），利用索引掃描一段範圍。
  - `index`——掃描整個索引樹（比全表掃描好一點，因為索引通常比整行資料小，但仍要掃描全部索引項）。
  - `ALL`——全表掃描，最差，資料量大時要重點關注和優化。
- **`key`**——實際使用的索引名稱。如果是 `NULL`，説明這條查詢沒有用上任何索引（走了全表掃描）。有時 `possible_keys`（可能可用的索引）有值、但 `key` 是另一個或 NULL，説明優化器最終選擇了別的方案，可能需要進一步分析為什麼。
- **`rows`**——優化器預估「這一步大約需要掃描多少行」（不是精確值，是基於統計資訊的估算）。這個數字越小越好，能直觀反映查詢的效率。
- **`Extra`**——重要的補充資訊：
  - `Using index`——「覆蓋索引」，查詢只需要索引裡的資料就夠了、不用回表（Bookmark Lookup），是好現象。
  - `Using where`——在儲存引擎層取出資料後，還需要在 MySQL 伺服器層再做一次條件過濾（通常代表索引沒有完全覆蓋所有的過濾條件）。
  - `Using filesort`——需要「額外的排序步驟」（不是用索引的順序直接得到排序結果），資料量大時可能較慢，通常提示可以考慮加索引來避免這個額外排序。
  - `Using temporary`——需要建立臨時表（常見於複雜的 GROUP BY、DISTINCT、某些子查詢），資料量大時開銷可觀，也是需要關注優化的信號。

## 面試回答方式

按查看的優先順序講幾個核心欄位——先看 `type`（存取類型，判斷查詢方式的效率等級，能講出從 const 到 ALL 的大致排序、尤其要避免 ALL）、再看 `key`（是否用上索引、用了哪個）、`rows`（預估掃描行數）、最後看 `Extra`（Using index 是好事、Using filesort 和 Using temporary 是需要關注的警訊）。能結合這幾個欄位判斷「查詢效率如何、有沒有優化空間」。這是一個實務工具題，重點是展現你能實際看懂並分析 EXPLAIN 的輸出、知道哪些欄位重要、什麼樣的值是好是壞，而不只是背欄位名稱。

## 常見追問

### 看到 EXPLAIN 顯示 type 是 ALL（全表掃描），該怎麼排查和優化？

**核心答案**：排查思路——(1)先確認「這個查詢的 WHERE 條件對應的欄位有沒有建索引」，沒有就考慮建；(2)如果已經有索引但還是 ALL，檢查是不是有前面講的「索引失效」的情況（函式運算、隱式轉換、LIKE 萬用字元開頭、不符合最左前綴（Leftmost Prefix））；(3)如果索引和寫法都沒問題，可能是「優化器判斷全表掃描更划算」（索引選擇性太低、或篩選出的資料佔比太大），這種情況即使有索引也可能是合理的選擇，不一定是問題；(4)檢查表的統計資訊是否過時（`ANALYZE TABLE` 更新統計資訊，有時統計資訊不準確會讓優化器誤判）。優化的方向——為常用查詢條件建合適的索引、修正索引失效的寫法、如果是資料量太大導致全表掃描本身就慢，考慮分頁、加限制條件縮小範圍、或用資料倉儲/搜尋引擎做這類分析查詢。

**詳細解析**：這是一個系統性的排查流程，體現「發現問題（type=ALL）→ 逐步排查原因 → 對症優化」的思路。第一步是最基礎的檢查——這個查詢用到的欄位有沒有索引，如果連索引都沒建，那全表掃描是必然的，優化的第一步就是建索引。第二步是「有索引但沒用上」——這是最需要仔細排查的情況，對照前面講的索引失效清單逐一檢查（是不是在索引欄位上用了函式、型別是否匹配、LIKE 是不是萬用字元開頭、聯合索引（Composite Index）是否符合最左前綴），這些都是常見的、可以透過改寫 SQL 解決的問題。第三步是「檢查了寫法都沒問題、但優化器還是選擇全表掃描」——這時候要理解，這可能不是 bug 而是「優化器基於成本估算的合理選擇」（見前面聚簇索引（Clustered Index）題的追問），例如查詢條件的選擇性確實很低（篩選出的資料佔全表的大部分），全表掃描（連續讀取）確實比「索引查詢+大量隨機回表」更快，這種情況下即使強行用 `FORCE INDEX` 逼優化器用索引，也可能適得其反。第四步是檢查統計資訊——資料庫的統計資訊（如各欄位的基數、值分佈）如果因為大量資料變更後沒有及時更新，可能導致優化器的成本估算不準確，做出錯誤的判斷，執行 `ANALYZE TABLE` 更新統計資訊有時能解決這類問題。理解這個「由淺入深」的排查流程，展現你有系統性解決效能問題的實務能力，而不只是「看到全表掃描就一律説要加索引」。

**面試回答方式**：講出排查步驟——「先看有沒有索引(沒有就建)、有索引檢查是否索引失效(函式/型別/LIKE/最左前綴)、都沒問題可能是優化器判斷全表更划算(選擇性低、屬合理)、檢查統計資訊是否過時(ANALYZE TABLE)」。強調「不是看到 ALL 就一定要加索引、有時是優化器的合理選擇」。展現你有系統性的排查思路而非機械化的「加索引」反應。

### Extra 顯示 Using filesort，一定代表效能有問題嗎？該怎麼優化？

**核心答案**：不一定，但通常是「值得關注的信號」——`Using filesort` 表示 MySQL 需要「額外的排序步驟」（不能直接利用索引的有序性得到排序好的結果），如果排序的資料量很小（如結果集只有幾十行），這個額外排序的開銷微不足道，不算問題；但如果需要排序的資料量很大，這個排序（尤其如果記憶體不夠、要用磁碟臨時檔案排序）可能成為明顯的效能瓶頸。優化的核心思路是——「盡量讓 ORDER BY 的欄位能直接利用索引的順序，避免額外排序」。具體做法——為 `ORDER BY` 涉及的欄位建立合適的索引（如果 `WHERE` 和 `ORDER BY` 都有欄位，考慮建一個「WHERE 欄位在前、ORDER BY 欄位在後」的聯合索引，讓查詢在利用索引篩選的同時，順帶得到已排序的結果，不需要額外排序）。

**詳細解析**：`Using filesort` 的名字容易讓人誤解成「一定要寫到磁碟檔案排序」，但實際上它泛指「任何不是直接利用索引順序、需要額外進行的排序操作」，可能在記憶體中完成（資料量小、`sort_buffer_size` 足夠時），也可能真的要用磁碟臨時檔案（資料量大、超過記憶體排序緩衝區大小時）。所以看到 `Using filesort` 先不用恐慌，要結合「大概要排序多少行資料」（可以參考 `rows` 欄位或實際測試）來判斷影響大不大。如果確實是效能瓶頸，核心優化思路是「讓排序這件事，透過索引的有序性『順便』完成，而不是額外算一遍」——例如查詢 `SELECT * FROM orders WHERE user_id = 5 ORDER BY create_time`，如果只有 `user_id` 上的索引，MySQL 會先用索引篩選出 user_id=5 的所有行，然後對這些行「額外地」按 create_time 排序（Using filesort）；但如果建立一個聯合索引 `INDEX(user_id, create_time)`，因為這個索引本身就是「先按 user_id、再按 create_time」排序的，篩選出 user_id=5 的這批資料在索引裡本身就已經是按 create_time 排好序的了，不需要額外排序，`Using filesort` 就會消失。這是「用聯合索引同時滿足 WHERE 過濾和 ORDER BY 排序需求」的經典優化手法，設計聯合索引時，「等值查詢的欄位在前、需要排序的欄位在後」正是為了達成這個效果（這也呼應了聯合索引欄位順序設計的原則）。理解 `Using filesort` 不一定是問題、但「用聯合索引消除額外排序」是常見且有效的優化手法，展現你能把「聯合索引設計」和「EXPLAIN 分析」串聯起來實際優化查詢。

**面試回答方式**：講出「不一定是問題——資料量小時開銷微不足道、資料量大或要用磁碟臨時檔案時才是明顯瓶頸」。給出核心優化思路——「讓 ORDER BY 能直接利用索引順序、避免額外排序——建聯合索引(WHERE 欄位在前、ORDER BY 欄位在後)、讓篩選出的資料在索引裡本身就是排好序的」。用具體例子(user_id 過濾 + create_time 排序、建 INDEX(user_id, create_time))説明。展現你能把聯合索引設計和 EXPLAIN 分析結合起來實際優化查詢。

### EXPLAIN 顯示的 rows 是精確的掃描行數嗎？為什麼有時候和實際情況差很多？

**核心答案**：不是精確值，是優化器根據「統計資訊」做的「估算」——MySQL 定期（或在特定操作觸發時）收集每張表、每個索引的統計資訊（如索引的基數 cardinality、資料分佈的抽樣），優化器用這些統計資訊估算「這條查詢大概要掃描多少行」，並不是真正執行查詢後的精確計數。如果統計資訊「過時」（比如表的資料量或分佈自上次統計後發生了很大變化、卻沒有重新統計），這個 rows 估算就可能和實際情況差很多——導致優化器基於不準確的估算做出錯誤的執行計劃選擇（如本該用索引卻選了全表掃描，或反之）。可以用 `ANALYZE TABLE` 主動觸發重新收集統計資訊，讓估算更準確。

**詳細解析**：這題澄清 EXPLAIN 輸出的本質——它是「優化器基於統計資訊的預估計劃」，而非「真正執行後的精確結果」。MySQL（InnoDB）維護統計資訊的方式，是「抽樣」估計而非精確全量統計——它不會為了知道「某個索引欄位有多少種不同的值」而去真的掃描全表精確計數（那樣開銷太大），而是抽取一部分頁面樣本、估算出大致的分佈情況。這意味著統計資訊本身就有一定的誤差，而且——如果表的資料在「上次統計之後」發生了大量的變化（大批量插入、刪除、更新），統計資訊會變得「過時」，和實際情況的偏差可能更大。當統計資訊不準確時，優化器基於它做出的「rows 預估」和「選擇哪個索引」都可能是錯誤的——最典型的問題是「明明有更好的索引可用，但因為統計資訊過時、優化器誤判某個索引的效果不好，選擇了次優的執行計劃甚至全表掃描」。這也是為什麼資料庫維運中，會定期（尤其在大批量資料變更後）執行 `ANALYZE TABLE` 來主動觸發重新收集統計資訊，讓優化器的判斷基於更準確的資料。理解「EXPLAIN 的 rows 是估算、依賴統計資訊、統計資訊可能過時導致誤判」，展現你理解查詢優化器工作的內部機制，而不是把 EXPLAIN 的輸出當成絕對精確的事實。

**面試回答方式**：講出「rows 是優化器基於統計資訊(抽樣估算的資料分佈)的預估、不是精確執行後的計數」。解釋「統計資訊如果過時(大量資料變更後沒重新統計)、估算會不準確、可能導致優化器選錯執行計劃」。給出解法——「定期用 ANALYZE TABLE 主動更新統計資訊、尤其在大批量資料變更後」。展現你理解 EXPLAIN 輸出的本質是基於統計資訊的估算，而非絕對事實。
