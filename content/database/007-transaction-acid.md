# 題目

資料庫交易的 ACID 分別是什麼？MySQL（InnoDB）是怎麼保證它們的？

## 核心答案

ACID 是交易必須滿足的四個特性——**原子性（Atomicity）**：交易內的所有操作要麼全部成功、要麼全部失敗回滾，不存在「做了一半」的狀態，靠 **undo log** 實現（記錄回滾所需的資訊）；**一致性（Consistency）**：交易執行前後，資料庫都必須處於「合法有效」的狀態（滿足所有約束，如外鍵、唯一性），這是「目標」，靠原子性、隔離性、持久性共同保證，也依賴應用層邏輯正確；**隔離性（Isolation）**：多個並發交易之間互不干擾，靠 **鎖 + MVCC** 實現（見隔離級別、MVCC 專題）；**持久性（Durability）**：交易一旦提交，其結果永久生效（即使系統崩潰也不丟失），靠 **redo log**（配合刷盤機制）實現。

## 詳細解析

**原子性（Atomicity）**：

- 定義——交易中的一組操作是「不可分割的整體」，要麼全部執行成功、要麼一個都不執行（回滾到交易開始前的狀態）。
- 實現——InnoDB 用 **undo log**（回滾日誌）——每次修改資料前，先把「修改前的舊值」記錄到 undo log；如果交易需要回滾（顯式 ROLLBACK、或發生錯誤），就用 undo log 把資料還原回修改前的狀態。

**一致性（Consistency）**：

- 定義——交易執行的結果必須讓資料庫從「一個合法狀態」轉移到「另一個合法狀態」（滿足所有的完整性約束：主鍵唯一、外鍵引用有效、業務規則如「餘額不能為負」等）。
- 這是四者中最「目標性」的一個——它不像其他三個有單一的具體實現機制，而是「原子性+隔離性+持久性都做好了，加上應用層業務邏輯本身正確」，才能共同達成一致性。可以説一致性是「果」，其他三者是「因」。

**隔離性（Isolation）**：

- 定義——多個並發執行的交易，彼此的中間狀態不應該互相干擾、影響。
- 實現——透過「鎖」（悲觀地阻止衝突的並發存取）和「MVCC」（多版本並發控制，樂觀地讓讀不阻塞寫、透過版本鏈實現不同交易看到不同的資料快照），具體的隔離程度由「隔離級別」配置決定（見 [[008-transaction-isolation.md]]）。

**持久性（Durability）**：

- 定義——一旦交易提交成功，這個結果就必須「永久有效」，即使之後系統當機、斷電，重啟後資料也不會丟失。
- 實現——InnoDB 用 **redo log**（重做日誌）——交易提交時，先把「修改的內容」寫入 redo log 並刷盤（相對於直接把資料頁刷盤，寫 redo log 是「順序寫」更快），只要 redo log 落盤成功就算持久化完成；即使資料頁本身還沒來得及刷盤系統就當機了，重啟後可以用 redo log「重做」這些修改，恢復資料。

## 面試回答方式

按 ACID 四個字母逐一講，每個都要講「定義 + 靠什麼實現」——原子性(undo log)、一致性(目標性的、靠其他三者+業務邏輯共同達成)、隔離性(鎖+MVCC)、持久性(redo log)。核心是要能區分「一致性」和其他三者不同——它不是一個獨立的機制，而是其他三者共同作用的結果，這個理解上的區分是這題的深度所在。能講出 undo log 和 redo log 分別對應原子性和持久性，展現你理解 ACID 不是抽象概念、而是有具體的技術實現支撐，這也自然銜接到後面 redo/undo log 的專題。

## 常見追問

### 為什麼説「一致性」是目標，其他三個是手段？

**核心答案**：因為「原子性、隔離性、持久性」都有「明確、獨立的技術機制」來實現（undo log、鎖/MVCC、redo log），它們是資料庫可以「自己保證」的技術層面特性；而「一致性」指的是「資料始終滿足業務和完整性約束的合法狀態」，這個目標的達成，一方面依賴前三者都做對（如果原子性沒保證好、交易做了一半就失敗沒回滾，資料就不一致了；如果隔離性沒做好、並發交易互相干擾，也可能導致資料不一致），另一方面還依賴「應用層業務邏輯本身寫得對」（比如轉帳交易要求「A 帳戶減多少、B 帳戶就要加多少」，這個邏輯本身要正確，資料庫的原子性只能保證「這個扣款和加款操作要麼都做要麼都不做」，但不能保證「你寫的扣款金額和加款金額是否真的相等」——這是應用層的責任）。所以一致性是「原子性+隔離性+持久性 + 正確的業務邏輯」共同達成的最終目標，而非資料庫單獨就能保證的一個獨立機制。

**詳細解析**：這個區分揭示了 ACID 四個特性之間的層次關係，是理解交易理論的一個重要細節。可以這樣理解——資料庫作為一個系統，能夠透過技術手段保證的是「原子性（要嘛全做要嘛全不做）」、「隔離性（並發交易互不干擾）」、「持久性（提交了就不會丟）」，這三者是資料庫「自身能力範圍內」能完全掌控和保證的。但「一致性」的定義是「資料始終處於合法有效的狀態」，這個「合法有效」的標準本身，很大程度上是「業務規則」定義的（如「訂單金額必須等於商品單價乘以數量」、「轉帳前後兩個帳戶的餘額總和不變」），資料庫並不知道你的業務規則是什麼，它只能保證「你在交易裡寫的那些操作，要嘛一起生效要嘛都不生效（原子性）」，但如果你在交易裡寫的操作本身就是錯的（比如轉帳時忘記從 A 帳戶扣錢、只給 B 帳戶加錢），資料庫的原子性只會忠實地把這個「錯誤的、不一致的操作」原子地執行掉，資料庫並不能發現「這樣做讓資料不一致了」。所以，一致性最終能否達成，除了依賴資料庫做好原子性、隔離性、持久性這些技術保證外，還「必須」依賴應用開發者寫出邏輯正確的交易程式碼。這就是為什麼説「一致性是目標，其他三個是實現這個目標的技術手段（但還需要正確的業務邏輯配合）」。

**面試回答方式**：講出「原子性/隔離性/持久性有明確獨立的技術機制(undo log、鎖/MVCC、redo log)、是資料庫自己能保證的；一致性是『資料始終合法有效』這個目標，依賴前三者都做對、還依賴應用層業務邏輯本身正確(資料庫不知道你的業務規則、只能原子地執行你寫的操作，即使邏輯本身是錯的)」。用轉帳的例子(扣款金額和加款金額是否相等是應用層責任)説明。展現你理解 ACID 四者之間的層次關係。

### undo log 除了實現原子性（回滾），還有什麼作用？

**核心答案**：undo log 還是實現 **MVCC（多版本並發控制）** 的核心機制——它記錄的「修改前的舊版本資料」，不只是用來「回滾」，還被用來「為其他並發的交易提供這行資料的歷史版本」。具體來説，當一個交易要讀取某一行資料，但這行資料已經被其他交易修改（且還沒提交，或者按隔離級別的規則不應該看到最新版本）時，資料庫會沿著這行資料的 undo log「版本鏈」往回找，找到「這個交易應該看到的那個版本」返回。所以 undo log 一身兼兩職——既是「交易失敗時用來回滾的資料」，也是「MVCC 實現『不同交易看到不同資料快照』的基礎」。

**詳細解析**：這題揭示了 undo log 一個容易被忽略但很重要的雙重作用。傳統認知裡，undo log 就是「為了回滾」——記錄修改前的值，交易失敗時拿出來恢復。但在 InnoDB 的 MVCC 實現裡，undo log 有第二個、甚至可以説更常用的作用——支撐「快照讀」。具體機制是——InnoDB 每一行資料除了實際的欄位值，還有隱藏的欄位記錄「這行資料是被哪個交易修改的、以及一個指向 undo log 中『這行資料上一個版本』的指標」，這樣多次修改就形成了一條「版本鏈」（就像連結串列，從最新版本一路連到最舊的版本）。當一個交易（在可重複讀等隔離級別下）要讀取一行資料時，它不一定讀「當前最新的版本」，而是要根據「這個交易開始時的時間點（或它建立的 Read View）」，判斷「哪個版本的資料是這個交易『應該』看到的」——如果最新版本是「在這個交易開始之後、由其他交易修改」的，那這個交易就不應該看到這個新版本，而要「沿著 undo log 的版本鏈往回找」，找到一個「這個交易建立之前就已經提交」的版本返回。這就是「快照讀（不加鎖的普通 SELECT）」能實現「讀到一致性視圖、不被其他並發交易的修改干擾」的關鍵機制，而支撐這條「版本鏈」的資料，正是 undo log。所以 undo log 不只是「失敗時的後悔藥」，更是「日常讀取操作實現隔離性（不同交易看到不同快照）」的基礎設施，這也自然連結到 MVCC 這個更深入的主題。

**面試回答方式**：講出「undo log 除了回滾、還是 MVCC 的核心——每行資料的多次修改形成一條版本鏈(靠 undo log 連接)、其他交易讀取時根據自己該看到哪個版本、沿版本鏈找到對應的舊版本、實現快照讀的隔離性」。強調「undo log 一身兼兩職——回滾的後悔藥 + MVCC 版本鏈的資料來源」。展現你理解 undo log 在交易系統中的雙重作用，並自然引出 MVCC 這個進階話題。

### redo log 和 undo log 是同一種東西嗎？分別記錄什麼？

**核心答案**：不是同一種東西，兩者的目的、記錄內容、寫入時機都不同。**redo log**（重做日誌）記錄的是「這次修改『做了什麼』（物理層面，如某個資料頁的某個位置改成了什麼值）」，目的是「持久性」——交易提交前確保修改已經記錄在 redo log（且落盤），即使資料頁本身還沒刷盤就當機，重啟後可以用 redo log「重做」這些修改，不丟失已提交的資料。**undo log**（回滾日誌）記錄的是「這次修改『之前是什麼』（修改前的舊值）」，目的是「原子性」（回滾用）和「MVCC」（提供舊版本快照）——如果交易需要回滾，用 undo log 把資料改回修改前的值；其他交易需要讀取舊版本時，也是查 undo log。簡言之——redo log 是「這次改成了什麼（面向未來、確保修改不丟）」，undo log 是「改之前是什麼（面向過去、用於撤銷或提供舊快照）」。

**詳細解析**：這是一個非常容易混淆名字和作用的知識點，釐清它們是理解 InnoDB 交易機制的基礎。可以用一個簡單的類比理解——如果把資料庫的一次修改想像成「編輯一份文件」，redo log 就像是「操作記錄（我把第 3 行的『蘋果』改成了『香蕉』）」，這份記錄的作用是——如果你的編輯器（資料庫）在儲存到最終檔案之前當機了，重新打開時可以「重放」這份操作記錄，把修改重新做一遍，確保你剛才做的修改不會因為當機而丟失（這正是持久性的核心）。而 undo log 則像是「備份的舊內容（第 3 行原本是『蘋果』）」，它的作用是——如果你反悔了（交易回滾），可以用這份備份把內容改回去（原子性）；或者如果有另一個人（另一個交易）此刻正在讀這份文件，但按規則他應該看到「你修改之前」的版本，那就把這份舊內容給他看（MVCC 快照讀）。兩者在「寫入時機」上也不同——redo log 通常在交易提交時（或更早，取決於策略）被寫入並確保刷盤，是「面向未來確保已提交的不丟」；undo log 在修改資料的當下就被記錄（在實際修改資料頁之前），是「面向過去保留可以復原或查詢的軌跡」，且 undo log 在交易提交、且沒有其他交易再需要這些舊版本時，可以被清理回收（不會永久保留）。理解兩者「記錄的內容方向相反（做了什麼 vs 之前是什麼）、服務的目的不同（持久性 vs 原子性+MVCC）」，是掌握 InnoDB 交易日誌機制的關鍵。

**面試回答方式**：講出「不是同一種——redo log 記錄『改成了什麼』(面向未來、確保已提交的修改不因當機而丟、實現持久性)、undo log 記錄『改之前是什麼』(面向過去、用於回滾或 MVCC 提供舊版本快照、實現原子性)」。用「操作記錄(redo)vs 備份舊內容(undo)」的類比説明。強調「兩者記錄方向相反、服務目的不同(持久性 vs 原子性+MVCC)」。展現你能清楚區分這兩個容易混淆的核心機制。
