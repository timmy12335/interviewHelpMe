# 題目

最佳化器怎麼決定用哪個索引？統計資訊不準會造成什麼問題？

## 核心答案

最佳化器是**基於成本**的：它為每個候選的執行計畫估算一個成本（主要是「要掃描多少頁」與「要做多少次隨機 IO」），選成本最低的。**成本的估算依賴統計資訊**——每個索引的**基數**（cardinality，不重複值的數量）、表的總列數、以及頁面數。

**基數決定了選擇性的估算**。一個有一百萬列的表，某個索引的基數是 100，**最佳化器就估計每個值平均對應一萬列**——用它過濾要回表一萬次，那可能不如全表掃描。基數是 90 萬的話，每個值平均一列，走索引明顯划算。

**InnoDB 的統計資訊是採樣得來的**（`innodb_stats_persistent_sample_pages` 預設 20 頁），**所以它是估算而非精確值**。這帶來兩類問題：**採樣不足**（資料分佈不均勻時，20 頁的採樣可能完全不代表整體）與**過期**（大量寫入後統計沒更新）。

**症狀是「同樣的查詢突然變慢」**——執行計畫變了。排查的第一步是 `EXPLAIN` 看估算的 `rows` 與實際筆數的差距，差很多就先 `ANALYZE TABLE`。

## 詳細解析

**「估算 rows 與實際差很多」是最直接的訊號**。MySQL 8 的 `EXPLAIN ANALYZE` 會同時給出估算與實際執行的筆數與時間，**兩者差一個數量級以上就表示統計資訊有問題**（或者查詢的形狀讓最佳化器無法準確估算）。**在 8.0 之前只能靠 `EXPLAIN` 的估算對比實際跑一次的結果，麻煩得多。**

**直方圖（MySQL 8.0 引入）解決了「資料分佈不均勻」的問題**。基數只告訴你「有多少不重複值」，**但不告訴你它們的分佈**——一個 `status` 欄位有 5 個值，但 99% 的列是 `'ACTIVE'`，**基數 5 讓最佳化器估計每個值 20%，而實際上查 `'ACTIVE'` 會命中 99%、查其他值只有 0.25%**。直方圖記錄了值的分佈，讓估算準確得多。用 `ANALYZE TABLE ... UPDATE HISTOGRAM ON column` 建立。**它特別適合「低基數但分佈極不均勻」的欄位**——而那正是最容易被估算錯的一類。

**統計資訊的自動更新有其限制**。InnoDB 在表的修改量超過 10% 時會自動觸發重新統計（`innodb_stats_auto_recalc`），**但那是背景的、非同步的，而且採樣頁數不變**。**大批次匯入之後應該手動 `ANALYZE TABLE`**，不要等自動更新——否則接下來的查詢可能用了完全錯誤的計畫。**直方圖則完全不會自動更新**，必須手動維護，這是它最大的實務障礙。

**最佳化器的限制不只在統計**。它的成本模型有幾個固定的假設：**隨機 IO 比順序 IO 貴多少**（`innodb_page_size` 與相關成本常數，**預設值是為機械硬碟設計的**）、**資料在記憶體中的機率**、以及**條件之間相互獨立**（`WHERE a = 1 AND b = 2` 的選擇性被估成兩者相乘，**但如果 a 與 b 高度相關，這個估算會嚴重偏低**）。**最後一項是最難處理的**——多欄位的相關性需要多欄位統計，而 MySQL 對此的支援有限（PostgreSQL 有 `CREATE STATISTICS` 專門處理）。

## 面試回答方式

先給**基於成本**的框架與成本估算依賴的統計資訊（基數、列數、頁數），用具體數字說明**基數如何決定選擇性的估算**。指出 **InnoDB 的統計是採樣得來的**（預設 20 頁），因而有採樣不足與過期兩類問題，**症狀是「同樣的查詢突然變慢」**。給排查第一步：`EXPLAIN` 對比估算與實際、差很多就 `ANALYZE TABLE`。加分點有三個：**直方圖解決分佈不均勻**——用「status 有 5 個值但 99% 是 ACTIVE」說明基數為何不夠，並指出**直方圖不會自動更新，必須手動維護**，這是它最大的實務障礙；**大批次匯入後應該手動 `ANALYZE`** 而非等自動觸發；以及**最佳化器的成本模型假設條件之間相互獨立**，欄位高度相關時估算會嚴重偏低，**而 MySQL 對多欄位統計的支援有限**（PostgreSQL 有 `CREATE STATISTICS`）。

## 講稿

最佳化器是基於成本的。它為每個候選的執行計畫估算成本，主要是要掃描多少頁跟要做多少次隨機 IO，然後選成本最低的。而成本的估算依賴統計資訊，主要是每個索引的基數，也就是不重複值的數量。

基數決定了選擇性的估算。一百萬列的表，某個索引基數是一百，最佳化器就估計每個值平均對應一萬列，走索引要回表一萬次，那可能不如全表掃描。

InnoDB 的統計資訊是採樣來的，預設只採樣二十頁，所以它是估算而不是精確值。這帶來兩類問題，採樣不足跟過期。症狀是同樣的查詢突然變慢，因為執行計畫變了。

排查我會先用 EXPLAIN 看估算的筆數跟實際的差距，差一個數量級以上就先重新分析表。

MySQL 8 的直方圖解決了分佈不均勻的問題。基數只告訴你有多少不重複值，不告訴你分佈。一個狀態欄位有五個值，但九成九的列是同一個值，基數五會讓最佳化器估計每個值兩成，而實際上差很多。直方圖記錄了分佈讓估算準確得多。但它不會自動更新，必須手動維護，這是它最大的實務障礙。

## 常見追問

### 執行計畫為什麼會「突然」改變？

**核心答案**：因為最佳化器的決定是**每次執行都重新評估的**（除非用了預存的計畫），而它的輸入會變：**統計資訊更新了**（自動重新統計在修改量超過 10% 時觸發）、**資料量或分佈變了**（表成長讓某個索引的選擇性下降）、**參數值不同**（`WHERE status = ?` 傳入不同的值時，如果有直方圖，估算的選擇性也不同）、以及**版本升級改變了成本模型或加入了新的優化**。

**詳細解析**：**「參數值不同導致計畫不同」在有直方圖時特別明顯**，而它其實是**正確的行為**——查 `status = 'ACTIVE'`（99% 的列）該走全表掃描，查 `status = 'DELETED'`（0.1%）該走索引。**但它讓「同一句 SQL 的效能不穩定」成為常態**，而那對監控與容量規劃是個挑戰。**Oracle 的「自適應游標共享」與 SQL Server 的「參數嗅探」處理的都是同一個問題**——而它們的複雜度說明了這件事沒有簡單的答案。**實務上的處理是：對效能關鍵且參數分佈極端的查詢，考慮把不同情況拆成不同的 SQL**（讓每一句的計畫穩定），而不是期待最佳化器每次都做對。

**面試回答方式**：給四個輸入變化的來源。重點展開**參數值不同導致計畫不同在有直方圖時特別明顯**，並指出**那其實是正確的行為**（查 99% 的值該全表掃描、查 0.1% 該走索引），**但它讓「同一句 SQL 的效能不穩定」成為常態**。加分點是提到 Oracle 的自適應游標共享與 SQL Server 的參數嗅探處理的是同一個問題，**它們的複雜度說明沒有簡單答案**。收在實務處理：對關鍵且參數分佈極端的查詢，把不同情況拆成不同的 SQL 讓計畫穩定。

### 什麼時候該用 FORCE INDEX？

**核心答案**：**幾乎總是最後手段**。合理的時機只有：**已經確認統計資訊是準確的**（`ANALYZE` 過了）、**已經確認最佳化器的選擇確實更差**（實測而非猜測）、而且**理解為什麼它會選錯**（通常是成本模型的假設不符，例如 SSD 上的隨機 IO 成本被高估）。**在那之前，`ANALYZE TABLE`、加直方圖、或改寫查詢都是更好的選項。**

**詳細解析**：**`FORCE INDEX` 的風險是它會過期**。今天正確的選擇，在資料量成長十倍、或者新增了一個更好的索引之後，可能變成最差的選擇——**而 hint 會忠實地執行那個過時的決定**。**更糟的是如果那個索引後來被刪除，查詢會直接報錯**（`FORCE INDEX` 引用不存在的索引是錯誤，不是靜默忽略）。**所以每一個 hint 都應該有註解說明「為什麼加、什麼情況下該重新評估」**——這與前面說過的「把決定與它的前提一起記錄」是同一個原則。**沒有這個註解的 hint，幾年後沒有人敢動也沒有人知道還需不需要，它就成了永久的技術債。**

**面試回答方式**：明確定位為**最後手段**並給出三個前提（統計已準確、已實測確認更差、理解為什麼選錯）。展開它的兩個風險：**會過期**（資料成長或新增索引後可能變成最差選擇）、以及**索引被刪除時查詢直接報錯**。收在可操作的建議：**每個 hint 都要有註解說明為什麼加、什麼情況下重新評估**，這與「把決定與前提一起記錄」是同一個原則，**沒有註解的 hint 幾年後就成了永久技術債**。

### 怎麼系統地優化一個慢查詢？

**核心答案**：按順序做五步。**第一，確認它真的是問題**——看它在總負載中的佔比（`performance_schema` 的 `events_statements_summary_by_digest`），一個跑 5 秒但一天只跑一次的查詢不值得優化。**第二，看執行計畫**——`EXPLAIN ANALYZE` 找出估算與實際的差距、以及最貴的那一步。**第三，確認統計資訊**。**第四，改索引或改查詢**——優先改查詢（減少掃描的資料量），其次加索引。**第五，量測並比對**。

**詳細解析**：**「優先改查詢而非加索引」值得說明理由**。加索引的成本是持續的（每次寫入都要維護、佔用空間與緩衝池），**而且索引越多，最佳化器的選擇越多、計畫越不穩定**。改查詢則往往沒有持續成本——**把 `SELECT *` 改成只取需要的欄位可能就達成了覆蓋索引；加一個原本就該有的過濾條件可能減少 99% 的掃描；把 `OR` 改寫成 `UNION ALL` 可能讓兩邊都能走索引。** **實務上很多「需要加索引」的查詢，其實是查詢寫得不好。** 所以看到慢查詢時，**先問「這個查詢真的需要掃描這麼多資料嗎」**，而不是直接看該加什麼索引——**前者常常能找到數量級的改善，後者只是讓掃描變快一點。**

**面試回答方式**：給五步順序，並特別強調**第一步「確認它真的是問題」**——看在總負載中的佔比，跑 5 秒但一天一次的不值得優化。重點展開**「優先改查詢而非加索引」的理由**：索引的成本是持續的且讓計畫更不穩定，而改查詢往往沒有持續成本。給三個具體例子（`SELECT *` 改成需要的欄位可能達成覆蓋、加該有的過濾條件、`OR` 改寫成 `UNION ALL`）。收在判斷：**先問「這個查詢真的需要掃描這麼多資料嗎」**，那常常能找到數量級的改善。
