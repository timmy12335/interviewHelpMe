# 題目

唯一約束、外鍵這些該由資料庫還是應用層保證？為什麼很多團隊不用外鍵？

## 核心答案

判斷的核心是「誰能提供真正的保證」。應用層的校驗**在併發下不可靠**——「先查詢是否重複、不重複就插入」中間有競態窗口，兩個並行的請求都會通過檢查。只有資料庫的唯一約束能真正保證唯一，因為它是在寫入時由儲存引擎原子地檢查的。

所以唯一約束幾乎總是應該有——即使應用層也檢查（為了給出更好的錯誤訊息），資料庫的約束是最後的正確性防線。

**外鍵的情況比較複雜**，不用它的理由有四個：**寫入效能**（每次插入都要檢查父表是否存在、每次刪除父列都要檢查子表）、**鎖的範圍擴大**（外鍵檢查會對父表加鎖，增加死鎖機率）、**分庫分表後無法跨庫使用**、以及**遷移與變更的阻力**（有外鍵的表在批次匯入、schema 變更、以及資料清理時都更麻煩）。

**但放棄外鍵的代價是真實的**：孤兒資料會累積、而且**通常在很久之後才被發現**。務實的立場是「依表的重要性分級」：核心的業務關聯保留外鍵，日誌與統計類的關聯則不用。

## 詳細解析

「應用層校驗在併發下不可靠」是這題的核心論點，值得說得具體。註冊流程檢查使用者名稱是否已存在，兩個請求同時進來：A 查詢→不存在、B 查詢→不存在、A 插入→成功、B 插入→**成功**（如果沒有唯一索引）。測試環境永遠測不出來，因為那需要精確的時間重疊。 而唯一索引讓 B 的插入直接失敗，應用只需要捕捉那個錯誤並轉成友善的訊息。正確的模式是「應用層檢查是為了體驗，資料庫約束是為了正確性」——兩者都要，但角色不同。

外鍵的效能成本要看實際的量級。在寫入不密集的表上，外鍵的開銷微不足道；在高頻寫入的表上，每次插入多一次索引查找加上鎖，可能是可觀的。**更關鍵的是鎖**——InnoDB 的外鍵檢查會對父表的對應列加共享鎖，這讓「更新父表」與「插入子表」之間產生了額外的衝突路徑，是一些難以理解的死鎖的來源。

「孤兒資料在很久之後才被發現」的代價常被低估。沒有外鍵時，刪除一個使用者而忘了刪除他的訂單，那些訂單會一直存在並可能出現在報表、統計、甚至被錯誤地處理。發現的時機往往是「對帳對不上」或「某個查詢回傳了不該存在的資料」，而那時候已經累積了大量髒資料且難以判斷哪些該刪。如果決定不用外鍵，就必須有替代的保障：定期的一致性檢查腳本（找出孤兒記錄並告警）、以及應用層明確的級聯刪除邏輯。「不用外鍵」是一個需要配套的決定，而不是單純的省略。

分庫分表是放棄外鍵最正當的理由——跨庫的外鍵根本不可能。但這也意味著資料完整性完全成為應用的責任，而那需要明確的設計（例如用領域事件驅動的級聯清理、或者定期的對帳）。很多分庫分表的系統在這一點上是「預設沒有人負責」的狀態，直到資料問題累積到無法忽視。

## 面試回答方式

先給核心論點——**應用層校驗在併發下不可靠**，並用註冊流程的競態具體說明（兩個請求都查到不存在、都插入成功），強調**測試環境永遠測不出來**。給出正確的分工：應用層檢查是為了體驗，資料庫約束是為了正確性。接著給不用外鍵的四個理由並指出鎖的擴大是難以理解的死鎖的來源。加分點有三個：孤兒資料在很久之後才被發現，發現的時機往往是對帳對不上，而那時已累積大量髒資料；「不用外鍵」是一個需要配套的決定——必須有定期的一致性檢查與明確的級聯邏輯，而不是單純的省略；以及**分庫分表是最正當的理由**，但那意味著完整性完全成為應用的責任，而很多系統在這一點上是「預設沒有人負責」的狀態。

## 講稿

判斷的核心是誰能提供真正的保證。應用層的校驗在併發下不可靠。註冊流程檢查使用者名稱是否存在，兩個請求同時進來，A 查詢不存在、B 查詢也不存在、然後兩個都插入成功。測試環境永遠測不出來，因為那需要精確的時間重疊。

所以唯一約束幾乎總是應該有。即使應用層也檢查，那是為了給出更好的錯誤訊息，而資料庫的約束是最後的正確性防線。我的分工是應用層檢查為了體驗，資料庫約束為了正確性。

外鍵的情況比較複雜。不用它的理由有四個，寫入效能、鎖的範圍擴大增加死鎖、分庫分表後無法跨庫、還有遷移與變更的阻力。

但放棄的代價是真實的。孤兒資料會累積，而且通常在很久之後才被發現，往往是對帳對不上或某個查詢回傳了不該存在的資料。那時候已經累積了大量髒資料，而且難以判斷哪些該刪。

所以我認為不用外鍵是一個需要配套的決定，不是單純的省略。必須有定期的一致性檢查腳本找出孤兒記錄並告警，還有應用層明確的級聯刪除邏輯。

分庫分表是放棄外鍵最正當的理由，但那意味著完整性完全成為應用的責任。而很多這樣的系統，在這一點上其實是預設沒有人負責的狀態。

## 常見追問

### 檢查約束（CHECK）值得用嗎？

**核心答案**：**值得，而且它是被低估的**。MySQL 8.0.16 之後才真正支援（之前的版本會解析但忽略——這是一個危險的行為，因為你以為有保護但其實沒有）。它讓「金額必須為正」「狀態必須是這幾個值之一」「結束時間必須晚於開始時間」這類規則在資料庫層被強制執行。

**詳細解析**：它的價值在於「約束跟著資料走」——不管是應用寫入、批次匯入、還是有人手動執行 SQL，**約束都會生效**。而應用層的校驗只保護「經過應用的那條路徑」，而資料進入資料庫的路徑往往不只一條（遷移腳本、資料修復、後台管理工具、以及各種一次性的手動操作）。「非預期路徑寫入的髒資料」是很多資料品質問題的來源，而 CHECK 約束正好防護這一類。 代價是它增加了寫入的成本並讓某些變更變麻煩（改變約束需要 DDL）。務實的用法是「用它表達不會變的業務不變量」——金額非負、日期順序、狀態的合法集合；而不是用它表達會頻繁調整的業務規則（例如「訂單金額不能超過 10 萬」這種可能因為業務調整而改變的上限）。

**面試回答方式**：給明確立場（值得用、被低估）並提醒 **MySQL 8.0.16 之前會解析但忽略**——你以為有保護但其實沒有。重點展開它的價值：**約束跟著資料走**，保護所有路徑，而應用層校驗只保護經過應用的那條，但資料進入的路徑往往不只一條（遷移腳本、資料修復、後台工具、手動操作）。收在務實用法：用它表達不會變的業務不變量，而非會頻繁調整的規則。

### 資料庫層與應用層的校驗重複，該怎麼組織？

**核心答案**：**接受重複，但明確它們的角色**。應用層的校驗負責**快速失敗與友善的錯誤訊息**（在寫入之前就告訴使用者哪個欄位有問題），資料庫的約束負責**最後的正確性保證**（防護併發競態與非預期的寫入路徑）。重複不是浪費，因為它們保護的是不同的失敗模式。

**詳細解析**：組織上的關鍵是「約束的定義只有一份真相」——如果應用層寫死「名稱最多 50 字」而資料庫是 `VARCHAR(100)`，**兩者遲早會不一致**。**處理方式有兩種**：**從 schema 生成應用層的校驗**（某些 ORM 與工具支援讀取 schema 的中繼資料）、或者把約束定義在一處並生成兩邊（例如用一個共用的規格檔生成資料庫的遷移與應用的驗證註解）。多數團隊做不到這種自動化，那麼至少應該在 code review 中把「schema 變更是否對應更新了應用層的校驗」列為檢查項。 「同一個事實在多處定義」是不一致的根源，這個問題在 schema、API 契約、以及設定上反覆出現——而解法永遠是「單一真相加上生成」，或者退而求其次的「明確的同步流程」。

**面試回答方式**：給明確立場——**接受重複但明確角色**（應用層為了體驗與快速失敗、資料庫為了正確性），並強調重複不是浪費因為它們保護不同的失敗模式。重點是組織的關鍵：**約束的定義只有一份真相**，否則遲早不一致。給兩種做法（從 schema 生成、或從共用規格生成兩邊）與退而求其次的檢查項。收在一般問題：「同一個事實在多處定義」是不一致的根源，解法是單一真相加生成，或明確的同步流程。

### 沒有外鍵時怎麼發現孤兒資料？

**核心答案**：**定期執行一致性檢查腳本**。做法是用 `LEFT JOIN` 找出「子表有但父表沒有」的記錄：`SELECT o.id FROM orders o LEFT JOIN users u ON o.user_id = u.id WHERE u.id IS NULL`。這類檢查應該自動化、定期執行、並把結果上報成監控指標——孤兒記錄的數量持續上升就是一個明確的告警訊號。

**詳細解析**：**在大表上這種全表 JOIN 很昂貴**，所以實務上有兩個調整：**只檢查最近的資料**（依 `created_at` 限制範圍，因為舊的孤兒如果之前檢查過就不會再出現）、以及在低峰時段執行或在從庫上執行。更根本的做法是「在刪除時就處理」——把「刪除使用者」做成一個明確的領域操作，它負責級聯清理所有相關資料（同步或透過事件非同步），而不是讓任何人都能直接 `DELETE FROM users`。這需要限制對資料庫的直接寫入權限，而那本身就是一個好的實踐。「一致性檢查是安全網，正確的刪除流程才是主要防護」——只有安全網而沒有主要防護，等於接受了持續產生髒資料然後定期清理，那是一個不斷累積技術債的模式。

**面試回答方式**：給檢查的做法（`LEFT JOIN` 找孤兒）並強調要**自動化、定期執行、上報成指標**。給大表上的實務調整（只檢查最近資料、在從庫執行）。真正的加分點是提出更根本的做法：**在刪除時就處理**——把「刪除使用者」做成明確的領域操作負責級聯清理，並限制對資料庫的直接寫入權限。收在定位：一致性檢查是安全網，正確的刪除流程才是主要防護，只有安全網等於接受持續產生髒資料然後定期清理。
