# 題目

資料庫該監控哪些指標？出現效能問題時你會按什麼順序看？

## 核心答案

指標分四層，**每一層回答一個不同的問題**。

**業務層**——查詢的延遲分布（P50／P99／P999）與錯誤率。這是唯一直接對應使用者體驗的一層，也應該是告警的主要依據。

**負載層**——QPS、TPS、活躍連線數、以及**連線數的飽和度**（活躍除以上限）。這一層回答「壓力有多大」。

**資源層**——CPU、記憶體、磁碟 IOPS 與延遲、網路。其中磁碟延遲是最有診斷價值的，因為資料庫的多數停頓最終都表現為 IO 等待。

**內部層**——Buffer Pool 命中率、鎖等待與死鎖數、History list length、複製延遲、慢查詢數量、以及臨時表與排序的統計。這一層回答「為什麼」。

排查的順序應該是**由外而內**：先確認業務層真的有問題（不是監控誤報）、看負載層是不是流量變了、看資源層有沒有飽和、最後才進內部層找原因。跳過前面直接調參數是最常見的浪費。

## 詳細解析

「連線數的飽和度」是一個被低估的領先指標。連線數接近 `max_connections` 時，新的連線會被拒絕，而那通常表現為應用層的大量錯誤——但在達到上限之前，連線數的持續上升就已經是訊號了：它通常意味著查詢變慢（每個查詢佔用連線更久）或者連線洩漏。監控「活躍連線數」比「總連線數」更有意義，因為閒置的連線不消耗資源。

慢查詢的統計要看「總影響」而非「單次時間」。`performance_schema.events_statements_summary_by_digest` 提供了每個查詢範本的執行次數、總耗時、平均耗時、以及掃描的列數。一個平均 50 毫秒但每秒執行一千次的查詢，總影響遠大於一個 5 秒但每天執行一次的查詢——**而慢查詢日誌只會記錄後者**。所以「慢查詢日誌裡沒有東西」不代表沒有查詢問題，這是一個常見的誤判。

幾個「內部層」的指標特別值得建立告警：**History list length**（長交易的領先指標）、**複製延遲**（用心跳表量測）、**鎖等待的時間分布**（`performance_schema` 的 `events_waits_summary`）、以及**臨時表寫到磁碟的比例**（`Created_tmp_disk_tables` 除以 `Created_tmp_tables`，比例高表示有查詢的排序或分組超出了記憶體）。

**監控的設計原則是「能歸因」**。「資料庫變慢了」是一個沒有行動指引的告警；「訂單查詢的 P99 從 50 毫秒升到 500 毫秒，同時 Buffer Pool 命中率下降、磁碟讀取量上升」則直接指向了原因。**所以指標應該帶上維度**（依查詢範本、依表、依使用者），**而不是只有全域的總量**——全域指標告訴你有問題，帶維度的指標告訴你問題在哪。

## 面試回答方式

先給**四層指標**與**每一層回答的問題**（業務層對應使用者體驗、負載層是壓力、資源層是飽和、內部層是原因），並指出**告警應該主要基於業務層**。給排查順序**由外而內**並強調跳過前面直接調參數是最常見的浪費。加分點有三個：「連線數的飽和度」是被低估的領先指標，在達到上限之前的持續上升就已經意味著查詢變慢或連線洩漏；慢查詢要看總影響而非單次時間——一個 50 毫秒但每秒千次的查詢總影響遠大於 5 秒但每天一次的，**而慢查詢日誌只會記錄後者**，所以「日誌裡沒東西」不代表沒問題；以及**監控的設計原則是「能歸因」**——指標要帶維度（依查詢範本、依表），全域指標告訴你有問題，帶維度的告訴你問題在哪。

## 講稿

我把指標分四層，每一層回答一個不同的問題。

業務層是查詢的延遲分布跟錯誤率，這是唯一直接對應使用者體驗的一層，也應該是告警的主要依據。負載層是每秒查詢數、活躍連線數，回答壓力有多大。資源層是 CPU、記憶體、磁碟，其中磁碟延遲最有診斷價值，因為資料庫的多數停頓最終都表現為 IO 等待。內部層是緩衝池命中率、鎖等待、歷史清單長度、複製延遲這些，回答為什麼。

排查的順序是由外而內。先確認業務層真的有問題、看負載層是不是流量變了、看資源層有沒有飽和、最後才進內部層找原因。跳過前面直接調參數是最常見的浪費。

有一個常見的誤判我想提。慢查詢要看總影響而不是單次時間。一個平均五十毫秒但每秒執行一千次的查詢，總影響遠大於一個五秒但每天執行一次的。而慢查詢日誌只會記錄後者。所以慢查詢日誌裡沒有東西，不代表沒有查詢問題。正確的做法是看效能綱要裡按查詢範本聚合的統計。

最後，監控的設計原則是能歸因。指標應該帶上維度，依查詢範本、依表、依使用者，而不是只有全域的總量。全域指標告訴你有問題，帶維度的指標才告訴你問題在哪。

## 常見追問

### performance_schema 的開銷大嗎？

**核心答案**：預設設定的開銷通常在 5% 以內，值得開啟。它的成本取決於啟用了哪些 instrument 與 consumer——**預設只開了一部分**（語句統計、部分等待事件），全開則開銷明顯上升。MySQL 8 的預設設定已經是一個合理的平衡，多數系統可以直接使用。**要注意它的記憶體佔用**（依 `performance_schema_max_*` 系列參數配置，可能數百 MB），在小記憶體的實例上要留意。

**詳細解析**：它相對於「慢查詢日誌」的優勢是「完整的取樣」——慢查詢日誌只記錄超過閾值的，而 `performance_schema` 統計**所有**查詢的執行次數與總耗時。**這讓「總影響」的分析成為可能**，而那是慢查詢日誌做不到的。代價是它的資料在記憶體中且會被輪替（`events_statements_history_long` 有容量上限），所以需要定期抓取並存到外部的監控系統——只在需要時才去查，可能已經被覆蓋了。這與「診斷能力必須在問題發生前準備好」是同一個原則：`performance_schema` 提供了能力，但如果沒有持續採集並保存，出事時仍然拿不到歷史資料。

**面試回答方式**：給開銷的量級（預設 5% 以內、值得開啟）並提醒記憶體佔用。真正的加分點是它相對於慢查詢日誌的優勢——完整的取樣讓「總影響」的分析成為可能，而慢查詢日誌只記錄超過閾值的。收在實務要點：資料在記憶體中會被輪替，需要定期抓取存到外部監控系統，否則需要時可能已被覆蓋——這與「診斷能力必須在問題發生前準備好」是同一個原則。

### 該對哪些指標設告警？

**核心答案**：**優先對「症狀」告警而非「原因」**。症狀是使用者感受得到的：查詢的 P99 延遲超過閾值、錯誤率上升、連線被拒絕。原因類的指標（Buffer Pool 命中率、鎖等待）**適合做儀表板而非告警**——因為它們的正常範圍隨負載變化，容易產生誤報，而且它們異常時症狀通常已經先反映了。

**詳細解析**：**少數原因類指標值得例外**，因為它們是**領先指標**（在症狀出現前就異常）：**磁碟空間**（滿了就是全面故障，而且沒有漸進的症狀）、**複製延遲**（讀寫分離下直接影響資料正確性）、**History list length**（長交易的早期訊號）、以及**連線數的飽和度**。這四個的共同特徵是「問題發生時已經來不及」，所以必須提前告警。 告警設計的一般原則是：每個告警都應該對應一個明確的行動——「Buffer Pool 命中率 92%」不知道該做什麼，「磁碟剩餘空間低於 15% 且以當前速度 3 天內會滿」則有明確的行動。沒有對應行動的告警會被忽略，而被忽略的告警會訓練團隊忽略所有告警，那才是真正的代價。

**面試回答方式**：給原則——**優先對症狀告警而非原因**，並說明原因類指標的正常範圍隨負載變化、容易誤報。真正的加分點是給出**四個值得例外的領先指標**（磁碟空間、複製延遲、History list length、連線飽和度）與它們的共同特徵：**問題發生時已經來不及**。收在告警設計的一般原則：每個告警都應該對應明確的行動，並指出被忽略的告警會訓練團隊忽略所有告警，那才是真正的代價。

### 怎麼建立資料庫的效能基準？

**核心答案**：在系統健康時記錄下關鍵指標的正常範圍，包含：各主要查詢的延遲分布、QPS 與 TPS 的日常曲線（含尖峰與低谷）、資源使用率、以及內部指標的穩態值。基準的價值在於「知道什麼是不正常」——沒有基準的話，看到「CPU 60%」不知道那是平常還是異常。

**詳細解析**：基準必須定期更新，因為系統會變——資料量成長、新功能上線、查詢模式改變，都會讓「正常」的定義改變。所以基準不是一次性的文件，而是持續累積的歷史資料（監控系統的長期保留就是最好的基準）。更有價值的是「同比」而非「絕對值」：與上週同一時間相比、與上個月相比——這自動處理了日常的週期性變化，也讓成長趨勢可見。很多監控系統支援這種比較，但很少被實際使用。 另一個實用的做法是在每次重大變更（版本發布、schema 變更、參數調整）前後刻意記錄一次基準，這讓「這次變更造成了什麼影響」有明確的答案，而不是靠事後的印象爭論。

**面試回答方式**：給基準的內容與它的核心價值——**知道什麼是不正常**。真正的加分點是指出基準必須定期更新且不是一次性文件，而是持續累積的歷史資料；並提出**「同比」比絕對值更有價值**（自動處理週期性變化、讓成長趨勢可見），而很多監控系統支援但很少被實際使用。收在實用做法：在每次重大變更前後刻意記錄基準，讓「這次變更造成了什麼影響」有明確答案而非事後印象爭論。
