# 題目

資料庫索引的原理是什麼？B+ 樹的結構是怎樣的？為什麼索引能加速查詢？

## 核心答案

索引是「額外建立的一份有序資料結構，用來加速查詢」——本質是「用空間換時間」，透過維護一份按某欄位排序好的結構（大多是 B+ 樹），把原本需要「全表掃描（逐行比對）」的查詢，變成「在有序結構中快速定位」。MySQL（InnoDB）的索引底層用 B+ 樹——一種「多路平衡樹」，每個節點能存多個 key、樹很矮胖，非葉子節點只存「索引 key + 指向子節點的指標」（不存實際資料），所有實際資料（或主鍵值）都存在「葉子節點」，且葉子節點之間用鏈結串列相連（便於範圍查詢）。查詢時從根節點開始，逐層比較 key、決定往哪個子節點走，樹的層數很少（通常 3-4 層），所以查詢極快（O(log n)，且因為矮胖、log 的底數很大，實際層數很少）。

## 詳細解析

**為什麼需要索引**：沒有索引時，查詢一個條件（如 `WHERE name = 'Tom'`）要「全表掃描」——逐行讀取、逐行比對，資料量大時極慢（O(n)）。索引預先建立一份「按這個欄位排序」的結構，查詢時能直接定位，不用全表掃描。

**B+ 樹的結構**：

- **多路平衡樹**——不像二元樹每個節點只有 2 個子節點，B+ 樹每個節點可以有「很多個」子節點（如幾百個），這讓樹「矮胖」（層數少）。
- **非葉子節點只存索引 key**——不存實際資料，只存「key + 指向子節點的指標」，這讓每個節點能容納更多 key（節點大小固定，不存資料就能塞更多 key），樹更矮胖。
- **葉子節點存實際資料（或指向資料的指標）、且相連**——所有實際資料都在葉子節點；葉子節點之間用「雙向鏈結串列」相連，這讓「範圍查詢」（如 `WHERE age BETWEEN 20 AND 30`）能高效地「定位起點後，沿著葉子鏈結串列順序讀取」，不用每次都從根節點重新查。

**為什麼查詢快**：因為樹「矮胖」（非葉子節點不存資料、能容納大量 key，一個節點對應一個磁碟頁），從根到葉子只需很少的層數（幾層）就能定位到目標資料——每一層對應一次磁碟 IO，層數少意味著磁碟 IO 次數少，這是資料庫索引效能的核心（磁碟 IO 是資料庫的主要瓶頸，見 [[002-why-btree.md]]）。

**索引的代價**：索引不是免費的——它佔用額外的儲存空間、且「寫入（INSERT/UPDATE/DELETE）」時要同步維護索引結構（可能導致樹的分裂/合併），所以索引越多，寫入效能越差。這是「索引加速讀、犧牲寫」的取捨，索引不是越多越好。

## 面試回答方式

先講「為什麼需要索引」——沒索引全表掃描 O(n)、索引預建有序結構加速查詢，這是「用空間換時間」的思路。然後講 B+ 樹的結構——重點三個特徵：多路（矮胖）、非葉子節點只存 key（能容納更多、更矮胖）、葉子節點存資料且相連（便於範圍查詢）。核心是解釋「為什麼查詢快」——樹矮、層數少、磁碟 IO 次數少。最後補一句「索引的代價」（佔空間、拖慢寫入），展現你理解索引不是免費午餐、也為選擇題目「該不該建索引」鋪墊。能講清 B+ 樹三個關鍵特徵和它們如何共同實現「矮胖樹減少 IO」，展現你理解索引加速的根本原因。

## 常見追問

### 索引為什麼能加速範圍查詢（如 BETWEEN、>）？

**核心答案**：因為 B+ 樹的所有葉子節點「按索引 key 排序、且用鏈結串列相連」——做範圍查詢時，只需先透過樹「定位到範圍的起點（一次 O(log n) 的樹查找）」，然後「沿著葉子節點的鏈結串列，順序往後讀」直到超出範圍為止，不需要每讀一個值就重新從根節點查一次。這讓範圍查詢的效率接近「找到起點後線性掃描這一段」，而不是「對範圍內每個值都做一次完整的樹查找」。

**詳細解析**：這是 B+ 樹「葉子節點鏈結串列」設計的核心價值。如果沒有這個鏈結串列（假設每個資料獨立存、彼此不相連），做範圍查詢 `WHERE age BETWEEN 20 AND 30` 理論上要「對範圍內每一個可能的值都做一次樹查找」，效率不高。B+ 樹的設計讓範圍查詢變得優雅——因為葉子節點本身就是「按 key 排序、首尾相連」的鏈結串列，你只要找到「20」對應的葉子節點位置（一次樹查找定位起點），之後直接「順著鏈結串列往右讀」，讀到的每一個值都是遞增的、直到讀到超過 30 就停止，整個過程只有「一次樹查找 + 一段順序掃描」，效率很高。這也是為什麼 B+ 樹特別適合「資料庫需要頻繁做範圍查詢、排序、分頁」這類場景——葉子鏈結串列讓這些操作都能高效完成。

**面試回答方式**：講出「葉子節點按 key 排序、用鏈結串列相連——範圍查詢先樹查找定位起點(一次 O(log n))、再沿鏈結串列順序讀到終點、不用對每個值重新查樹」。展現你理解葉子鏈結串列這個設計對範圍查詢的價值。

### 為什麼 B+ 樹的節點大小通常設計成一個磁碟頁的大小？

**核心答案**：因為磁碟 IO 是「以頁（page，通常 4KB 或 16KB）為單位」讀取的——讀一個位元組和讀一整頁的耗時差不多（因為磁碟定址/尋道的耗時遠大於實際傳輸資料的耗時）。如果 B+ 樹的一個節點正好對應一個磁碟頁，那麼「讀取一個節點」只需要「一次磁碟 IO」，且這次 IO 能拿到這個節點裡的「所有 key」（幾百個）。這讓每一層的查找都只需一次磁碟 IO，樹的層數（通常 3-4 層）直接對應「查詢一次資料最多需要幾次磁碟 IO」，把磁碟 IO 次數降到最低。

**詳細解析**：這揭示了 B+ 樹「多路、矮胖」設計背後的真正動機——一切都是為了「減少磁碟 IO 次數」，因為磁碟 IO 是資料庫效能的頭號瓶頸（比記憶體操作慢幾個數量級）。InnoDB 的一個資料頁預設是 16KB，一個 B+ 樹節點就對應一個 16KB 的頁；如果索引 key 是 bigint（8 位元組）+ 指標（6 位元組），一個節點大約能存 16KB / 14位元組 ≈ 1000 多個 key（實際會有其他開銷，但數量級是幾百到一千）。這意味著——一個 3 層的 B+ 樹（根、中間層、葉子），能索引的資料量是「1000 × 1000 × 1000」量級（十億級），而查詢任何一筆資料，只需要「3 次磁碟 IO」（讀根節點、讀中間節點、讀葉子節點）。這就是為什麼說 B+ 樹「矮胖」——因為每個節點能容納大量 key（一個磁碟頁的容量），所以即使索引十億級資料，樹的高度也只有 3-4 層，把磁碟 IO 次數控制在極少的幾次。理解「節點大小 = 磁碟頁大小 → 減少磁碟 IO 次數 → 這是 B+ 樹設計的核心動機」，是理解整個索引效能原理的關鍵。

**面試回答方式**：講出「磁碟 IO 以頁為單位、讀一頁和讀一部分耗時差不多——所以節點大小設計成一個磁碟頁、讀一個節點只需一次 IO、且能拿到節點裡所有 key(幾百到上千個)」。用「3 層樹能索引十億級資料、查詢只需 3 次磁碟 IO」的具體數量級説明。展現你理解 B+ 樹矮胖設計的真正動機是減少磁碟 IO。

### 一個表可以建多少個索引？索引越多越好嗎？

**核心答案**：技術上一個表可以建多個索引（沒有嚴格上限，但實務上不建議太多），但「索引越多越好」是錯誤觀念——索引有明顯的代價：（1）每個索引都要「額外的儲存空間」（每個索引都是一份獨立的 B+ 樹結構）；（2）每次「寫入（INSERT/UPDATE/DELETE）」都要「同步維護所有相關索引」（不只改資料、每個索引的 B+ 樹都要跟著調整），索引越多、寫入越慢；（3）查詢優化器在「選擇用哪個索引」時，索引太多也會增加優化器決策的複雜度。所以索引數量應該「按需建立」——只為「真正常用的查詢條件、且能提升效能的欄位」建索引，而非「什麼欄位都建一個索引」。

**詳細解析**：這是索引使用的核心權衡——「讀寫之間的取捨」。索引的價值是加速「讀」（查詢），但代價是拖慢「寫」（因為每次寫入資料都要同步更新索引結構，可能觸發 B+ 樹的節點分裂、合併等調整，這都是額外開銷）且佔用額外空間。如果一個表被大量寫入（如日誌表、高頻更新的表），建太多索引會顯著拖慢寫入效能；如果一個表主要是讀（如設定表、字典表），適當多建幾個索引利大於弊。所以正確的做法是「根據實際的查詢模式來決定建哪些索引」——分析常用的查詢語句、WHERE 條件、排序（ORDER BY）、分組（GROUP BY）用到的欄位，為這些「真正被頻繁查詢用到」的欄位（組合）建索引，而不是盲目地為每個欄位都建索引。同時要注意「聯合索引」的最左前綴原則（見 [[004-composite-index.md]]）能讓一個聯合索引覆蓋多種查詢模式，減少需要建立的索引總數。理解「索引是讀寫之間的權衡、按需建立而非越多越好」，展現你有實務的索引設計判斷力。

**面試回答方式**：講出「技術上無嚴格上限、但索引越多越好是錯誤觀念——代價是額外空間、且每次寫入都要同步維護所有索引(拖慢寫)、優化器選擇也更複雜」。給出正確做法——「按實際查詢模式(WHERE/ORDER BY/GROUP BY 常用的欄位)按需建索引、而非每個欄位都建」。能提到「聯合索引配合最左前綴能一個索引覆蓋多種查詢、減少索引總數」，展現你有實務的索引設計判斷力。
