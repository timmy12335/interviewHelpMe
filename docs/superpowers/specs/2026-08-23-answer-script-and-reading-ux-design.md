# 講稿區塊與答案閱讀體驗設計

**日期：** 2026-08-23
**狀態：** 已實作
**範圍：** `content/` schema 新增 `## 講稿`；parser 與型別；答案欄的閱讀 UI；內容生成器

## 背景與目標

使用者的問題有兩個：

1. **每題缺少一份可以照著念的稿子。** 既有的 `## 面試回答方式` 是**後設描述**，寫成
   「先給出核心答案——「…」。解釋核心價值——「…」」的形式。它告訴你「該講什麼」，
   但不是「講出來的話」——使用者得自己把引號串起來才能開口。

2. **解鎖後的答案是一整片文字，字多又擠，讀不完。** 這是耐心問題，不是資訊量問題。

### 現況量測

先量再決定，避免憑感覺改設計：

| 項目 | 數字 |
|------|------|
| 題目檔案 | 273 篇（另有 11 個 README） |
| 有 `## 面試回答方式` | 273 篇，平均 335 字 |
| 其中含長引號 | 264 篇（97%），平均每篇 3 段 |
| `## 核心答案` | 中位數 **423 字，且是單一段落** |
| `## 詳細解析` 段落 | 1290 段；中位 216 字、p90 522 字 |
| 其中以 `**小標**：` 開頭 | **968 段（75%）** |
| 答案欄實際行寬（1440 螢幕） | **21 個中文字/行**（中文舒適值為 32–36） |

兩個關鍵發現決定了整個設計：

- **75% 的詳細解析段落已經有天然結構**，把它解析出來就能得到一份目錄，零內容成本。
- **答案欄的行寬才是「太擠」的真正瓶頸**，不是行高或字級。

### 成功標準

1. 273 篇題目全數有可逐字念的講稿。
2. 詳細解析可先掃描小標、再決定讀哪一段。
3. 答案欄行寬達到中文舒適區間。
4. 使用者在點開任何一塊內容前，知道它要花多少時間。

## 決策摘要

| 項目 | 選擇 | 否決的替代方案 |
|------|------|----------------|
| 講稿來源 | 新增獨立 `## 講稿` 區塊 | 就地改寫「面試回答方式」（會失去策略提示這一層） |
| 講稿覆蓋 | 只有主題目 | 連常見追問（1100+ 篇，使用頻率低） |
| 生成方式 | 腳本產骨架 + 分批潤飾 | 全部 LLM 逐篇改寫（不可重現、無法一次完成） |
| 解析呈現 | 小標可見、內文收合 | Tabs 分頁（無法並排對照） |
| 核心答案 | 只調行寬與節奏 | 抽出首句當導言（見「明確不做」） |

## 內容 schema

`## 講稿` 插在 `## 面試回答方式` 之後、`## 常見追問` 之前：

```markdown
## 面試回答方式

先給出核心做法——「…」。可以誠實補充實務侷限——「…」。

## 講稿

我的理解是，……。

不過要誠實說，……。
```

兩者刻意並存而非二選一：**面試回答方式是策略提示，講稿是逐字稿。**

段落即口說節奏——一段一口氣。這讓 md 原始檔和 UI 都不需要額外的斷句規則。

## 解析層

| 檔案 | 職責 |
|------|------|
| `lib/content/parseQuestionMarkdown.ts` | 解析 `講稿`；呼叫 `splitDetailBlocks` |
| `lib/content/detailBlocks.ts` | 把 `詳細解析` 依 `**小標**：` 切成 `DetailBlock[]` |
| `lib/content/readingTime.ts` | 閱讀分鐘（300 字/分）與口說秒數（4.5 字/秒） |
| `lib/content/resolveLinks.ts` | 解析 `detailBlocks` 與 `script` 裡的 `[[...]]` |
| `types/question.ts` | `script?: string`、`detailBlocks?: DetailBlock[]` |

### DetailBlock 切分規則

- 段落以 `**小標**：` 開頭 → 開一個新區塊（冒號是必要條件，純粗體強調句不算）。
- 沒有小標的段落 → 併入上一個區塊。
- 開頭就沒有小標 → 自成一個無標題的開場塊，UI 直接攤開。
- 程式碼區塊內的空行不算段落分隔。

`講稿` 不進入相容用的合併 `answer` markdown，否則舊版面會重複同一段話。
`講稿` 也不套用 `emphasizeQuotedPhrases`（「」轉粗體）——跟稿時視線被打斷比看不到重點更糟。

## UI

### 答案欄寬度（收益最大的單一改動）

`grid-template-columns` 從 `minmax(0, 1fr) minmax(380px, 40%)` 改為
`minmax(0, 1fr) minmax(460px, 52%)`。行寬從 21 字提升到 28 字。

**先前加在 markdown 段落上的 `max-width` 完全沒生效，因為欄寬才是瓶頸。**
題目欄只放標題、題幹與作答框，讓寬度給答案欄是划算的。

### 三個新元件（皆在 `components/PracticeQuestion/index.tsx`）

- **`AnswerGuide`** — 解鎖後的第一列，交代各分區份量：
  `核心答案 2 分鐘 · 詳細解析 3 段 5 分鐘 · 講稿 約 2 分鐘 · 常見追問 3 題`。
  知道成本才決定要不要點開。段數與時間只在這裡講一次，解析標題不重複。

- **`DetailBlockList`** — 小標全部可見、內文預設收起，附「全部展開／收起」。
  移除原本的外層摺疊，避免兩層點擊。`DETAIL_OPEN_KEY` 語意改為「預設全開」，
  只有這個偏好會被記住；個別小塊的開合只活在這次瀏覽。

- **`AnswerScript`** — 琥珀色卡片，與解析（青）、總結（紫）明確區隔。
  字級 16.5px、行高 2.15、行寬 32em、每段左側標號。
  目的是講話時眼睛跟得上，而不是拿來讀懂內容。

## 內容生成器

`scripts/gen-scripts.mjs`，可重跑、可 diff。

### 主要來源：引號抽取

依據是 `emphasizeQuotes.ts` 已確認的既有訊號——**「」標的正是面試當下要講出口的那句話**。
掃出頂層 `「」`（內容用 `『』` 做巢狀，只需追蹤一層），過濾掉短於 16 字的行內強調，
補上口語銜接詞串成段落。

銜接詞依**引號前那段旁白的語意**挑選，而非固定順序。旁白本身帶著資訊
（「一定要誠實補充核心侷限」vs「可以延伸提到」），一律換成同一個連接詞會把這層丟掉。
同一段講稿內不重複用同一個銜接詞。

### 回退來源：核心答案

引號抽出的結果短於 120 字時，改用核心答案重建——洗掉粗體、反引號、
`（見 [[...]]）` 出處註記，把 `**（1）小標**——` 這類列舉切成段落。

**這道防線是事後補的。** 第一版沒有它，產出過「我的理解是，定位 → 分析 → 優化 → 驗證。」
這種 4 秒碎片，161 篇短於 40 秒。加上門檻與回退後中位數從 28 秒拉到 68 秒。

門檻定在 120 字（約 27 秒）而非更高：兩個完整段落約 130 字就是一段合理的簡答，
把它也判成不合格，只會逼著用更生硬的核心答案去取代更好的原句。

| 來源 | 篇數 |
|------|------|
| 生成器 | 245 |
| 手寫 | 28 |
| **合計** | **273** |

那 28 篇的「面試回答方式」是純後設敘述（先講X、接著講Y），沒有引號素材可抽，
核心答案也太短，規則轉換產出的東西不能念。

## 明確不做

- **核心答案抽首句當導言。** 量測後否決：只有 48% 切得出可用的導言，
  而切不出來的那些首句本身就 175–354 字，正是最該拆的案例。
  做了會是「一半頁面有、一半沒有」的不一致效果，且完全沒解到最糟的情況。
  **核心答案中位 423 字單段是內容問題，不是 CSS 能解的**，留給潤飾階段。

- **全螢幕唸稿模式**（大字 overlay、逐句高亮、方向鍵換句）。基本卡片先用起來再說。

- **常見追問的講稿。** 追問通常是短回應，維持既有的「面試回答方式」即可。

## 踩到的坑

**`\Z` 在 JS 正則裡是字面上的 Z，不是檔尾。** 用它當區塊結尾錨點，
會讓任何含大寫 Z 的內容（`ZGC`、`ZSet`、「大寫 A 到 Z」）在該處被攔腰截斷。
影響 4 個檔案的生成結果，已修復並補上回歸測試。正確寫法是 `$(?![\s\S])`。
